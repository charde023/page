강의는 어떤 내용이었나

이번 실습은 Google Workspace CLI, 줄여서 GWS를 설치하고 인증한 뒤, AI 에이전트가 그 CLI를 호출할 수 있게 만드는 흐름을 다뤘다. 앞부분에서는 왜 브라우저 클릭을 CLI 명령으로 바꾸는지 설명했고, 중반부터는 실제 터미널과 Google Cloud Console을 오가며 설치·OAuth·권한 설정을 진행했다.

후반부에서는 GWS가 단독으로 캘린더 정보를 불러오는지 확인한 다음, Claude Code 같은 에이전트에 GWS 스킬을 만들게 했다. 핵심은 API 코드를 직접 작성하는 것이 아니라, 이미 준비된 CLI와 스킬 문서를 에이전트가 읽고 자연어 요청을 실행 가능한 명령으로 바꾸게 하는 것이다.

1. Workspace 제어는 왜 CLI와 에이전트로 넘어가는가

기존에는 구글 캘린더, 드라이브, 지메일을 쓰려면 웹 브라우저에서 직접 클릭하고 입력했다. 내부적으로는 API 호출이 일어나지만, 사용자는 API를 직접 다루지 않고 화면을 조작한다. GWS는 이 과정을 터미널 명령으로 감싼다.

강의에서 강조한 변화는 다음과 같다. 사용자가 직접 Google API를 호출하는 코드를 만들지 않아도, gws calendar ..., gws drive ..., gws gmail ... 같은 명령으로 구조화된 JSON 결과를 받을 수 있다. 여기에서 한 단계 더 가면 AI 에이전트가 사용자의 자연어 요청을 읽고, 적절한 GWS 명령과 인자를 구성한다.

방식 사용자가 하는 일 시스템이 하는 일 장점 한계
브라우저 클릭 화면을 열고 버튼을 누른다 웹 앱이 API를 호출한다 익숙하다 반복 작업 자동화가 어렵다
직접 API 호출 API 문서를 보고 코드를 작성한다 코드가 API를 호출한다 세밀한 제어가 가능하다 설정·권한·코드 부담이 크다
GWS CLI 터미널 명령을 실행한다 CLI가 Workspace API를 감싼다 빠르고 구조화된 결과를 얻는다 명령 구조를 알아야 한다
AI 에이전트 + GWS 자연어로 요청한다 에이전트가 GWS 명령을 구성한다 업무 요청에 가깝게 실행된다 초기 스킬과 인증 설정이 필요하다

2. GWS와 Google Cloud CLI 설치

실습은 먼저 환경 점검에서 시작했다. 강사는 실습 자료에 빠른 시작 명령을 준비해 두었고, 참가자들은 그 순서대로 터미널에 명령을 넣어 진행하는 흐름이었다.

GWS 설치는 환경에 따라 다르다. npm이 준비되어 있으면 npm 방식으로 설치할 수 있고, macOS에서는 Homebrew를 사용할 수 있다. 강사 환경에서는 Homebrew로 설치한 뒤 gws --version으로 설치 완료를 확인했다.

준비물 역할 확인 방법 비고
Visual Studio Code 실습 폴더 열기 공유된 실습 자료 폴더를 연다 강의 화면은 VS Code 기준

3. OAuth 인증은 실습의 가장 큰 분기점이다

GWS를 설치해도 바로 Google Workspace 데이터를 읽을 수 있는 것은 아니다. 캘린더, 지메일, 드라이브 같은 개인 데이터에 접근하려면 Google Cloud 쪽 인증 설정이 필요하다. 강의에서는 gws auth setup 흐름을 중심으로 계정 로그인, 프로젝트 선택, OAuth 클라이언트 생성, 권한 범위 선택을 진행했다.

실습 중 강사 환경에서는 새 프로젝트 생성이 프로젝트 한도 문제로 실패했고, 기존 프로젝트를 선택해서 진행했다. 이 장면은 중요하다. 새 프로젝트 생성이 막히더라도, 권한이 있는 기존 프로젝트를 선택해 이어갈 수 있다.

단계 어디서 하는가 해야 할 일 성공 신호
1 터미널 gws auth setup 실행 Google Cloud CLI 확인 단계로 진입

4 Google Cloud Console Workspace API 활성화 필요한 API 목록이 켜짐
5 Google Cloud Console OAuth 동의 화면 구성 앱 정보 저장 완료

환경 변수 주입 CI/CD나 서버 환경일 때 개인 실습보다 자동화 환경에 적합

4. OAuth 동의 화면과 클라이언트 ID 만들기

OAuth 설정에서 참가자들이 가장 헷갈릴 수 있는 지점은 동의 화면과 클라이언트 생성이다. 강의에서는 Google Cloud Console에서 OAuth 동의 화면을 열고, 앱 정보를 저장한 뒤, 사용자 인증 정보에서 OAuth 클라이언트 ID를 만들었다.

애플리케이션 유형은 데스크톱 앱으로 설정했다. 생성이 끝나면 클라이언트 ID와 보안 비밀번호가 나오고, 이 값을 터미널의 gws auth setup 흐름에 붙여 넣는다.

설정 항목 값 또는 방향 이유
앱 유형 데스크톱 앱 로컬 CLI에서 사용자 인증을 진행하기 때문
클라이언트 ID 생성된 값을 그대로 복사 GWS가 Google OAuth 클라이언트를 식별하는 값
클라이언트 시크릿 생성된 보안 비밀번호 복사 OAuth 인증 요청을 완료하는 데 필요
앱 상태 테스트 중이어도 실습 가능 확인되지 않은 앱 경고가 뜰 수 있음
권한 범위 처음에는 추천 읽기 권한 불필요한 쓰기·삭제 권한을 피하기 위해
화면에 보이는 문제 의미 대응
Google Cloud CLI가 설치되지 않았다는 메시지 gcloud가 로컬에 없음 Google Cloud CLI를 먼저 설치
프로젝트 생성 실패 프로젝트 수 한도 또는 ID 중복 가능성 기존 프로젝트 선택
확인되지 않은 앱 경고 앱이 Google 검토를 받지 않은 테스트 상태 고급 설정에서 계속 진행
권한 범위 선택이 많음 서비스별 접근 권한이 나뉘어 있음 처음에는 Recommended 권한 선택
success가 안 보임 브라우저 승인이나 터미널 입력이 완료되지 않음 인증 URL 승인과 터미널 로그 재확인

5. GWS 명령 구조는 서비스명, 액션, 플래그다

GWS 명령은 크게 세 부분으로 이해하면 된다. 첫 번째는 서비스명, 두 번째는 액션, 세 번째는 옵션 플래그다. 예를 들어 캘린더 일정을 보려면 Calendar 서비스와 agenda 또는 event list 계열 액션을 조합한다.

강의에서는 설치와 인증을 마친 뒤 캘린더 조회를 예시로 들었다. 직접 명령으로 일정이 조회되면, 에이전트를 붙이기 전의 기반은 완성된 것이다.

구성 요소 예시 역할
CLI 이름 gws Google Workspace CLI 호출
서비스명 calendar, drive, gmail, docs, chat 어떤 Workspace 서비스를 다룰지 지정
액션 agenda, events list, files get, about 서비스 안에서 수행할 작업
플래그 --limit 2 같은 옵션 출력 개수, 기간, 포맷 등 세부 조건

6. AI 에이전트 스킬로 연결하기

단독 CLI가 동작하면 다음 단계는 에이전트 연결이다. 강의에서는 Claude Code를 예로 들었다. Claude Code에 GWS CLI를 통해 스킬을 생성해 달라고 요청하고, 설치 범위를 프로젝트 범위로 지정했다.

스킬이 생성되면 바로 끝이 아니다. 강사는 Claude Code를 종료하고 다시 시작해야 스킬을 인식한다고 설명했다. 재시작 후에는 "오늘 일정 불러줘" 같은 자연어 요청을 입력했고, 에이전트가 백그라운드에서 GWS 캘린더 명령을 실행해 일정을 가져오는 흐름을 확인했다.

단계 에이전트에서 하는 일 목적 확인 기준
1 GWS CLI 스킬 생성을 요청 CLI 사용법을 에이전트 도구로 만들기 계획 또는 설치 범위 질문이 나온다
2 프로젝트 범위 설치 선택 현재 실습 폴더에 필요한 스킬만 적용 스킬 파일이 프로젝트 안에 생성된다
3 생성 계획 승인 에이전트가 파일을 만들게 허용 GWS 관련 스킬 목록이 보인다
4 에이전트 재시작 새 스킬을 로드 재시작 후 스킬이 인식된다
5 자연어 요청 실행 CLI 명령을 직접 외우지 않고 사용 오늘 일정 조회 결과가 나온다
자연어 요청 에이전트가 해야 할 해석 예상되는 GWS 작업
오늘 일정 불러줘 캘린더에서 오늘 일정 조회 Calendar agenda 조회
이번 주 일정 요약해줘 기간 조건을 잡아 캘린더 읽기 Calendar events list
내일 오전 10시에 일정 추가해줘 쓰기 권한이 있는지 확인 후 일정 생성 Calendar event create
받은 편지 요약해줘 Gmail 접근 권한으로 메일 조회 Gmail message list/read
드라이브 파일 찾아줘 Drive에서 파일 검색 Drive files list/search

이번 세션은 특정 하나의 도구만 보는 강의가 아니라, 로컬 CLI, Google Cloud Console, OAuth, AI 에이전트를 이어 붙이는 실습이었다. 그래서 어디에서 무엇을 하는지 분리해서 보는 것이 중요하다.

도구 쓰인 위치 맡은 역할 주의할 점
VS Code 실습 파일 열기 공유된 실습 자료와 스크립트 확인 화면 확대와 폴더 위치를 맞춘다
터미널 설치·검증·명령 실행 GWS와 Google Cloud CLI 실행 PATH 문제와 명령 오타를 확인한다

Google Cloud CLI 계정과 프로젝트 인증 gws auth setup 흐름에서 사용 설치되어 있지 않으면 먼저 설치한다

8. 맥 기준 실습과 윈도우 사용자의 차이

강의 자료는 주로 맥 기준으로 준비되어 있었다. 강사는 윈도우도 큰 흐름은 비슷하다고 봤지만, 윈도우 전용 준비는 충분하지 않았다고 말했다. 그래서 윈도우 사용자는 별도로 공유된 링크를 참고하라고 안내했다.

핵심 흐름 자체는 운영체제와 무관하다. GWS 설치, Google Cloud CLI 설치, OAuth 인증, GWS 명령 테스트, 에이전트 스킬 연결이라는 순서는 같다. 다만 설치 명령, 터미널 환경, PATH 반영 방식은 달라질 수 있다.

구분 맥 윈도우

터미널 macOS 터미널 또는 VS Code 터미널 PowerShell 또는 VS Code 터미널
PATH 반영 brew 설치 후 바로 잡히는 경우가 많음 설치 후 새 터미널을 열어야 할 수 있음
강의 준비도 강사 화면 기준 추가 참고 자료 안내
공통 순서 GWS 설치 후 OAuth 인증 동일

막히는 지점 증상 원인 해결 방향

권한 범위가 너무 많다 어떤 scope를 골라야 할지 모른다 서비스별 권한이 세분화됨 처음에는 Recommended 읽기 권한으로 시작
CLI 단독 조회가 안 된다 캘린더나 메일 결과가 안 나온다 API 비활성화 또는 권한 부족 Workspace API 활성화와 OAuth 범위 재확인
에이전트가 스킬을 못 본다 자연어 요청이 GWS로 연결되지 않는다 생성 후 재시작을 안 함 Claude Code를 종료 후 재시작
