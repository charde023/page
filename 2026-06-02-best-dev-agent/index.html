# 메시지 한 줄
1 목적 먼저 에이전트 선택은 도구 선호가 아니라 해결할 문제에서 시작해야 한다.
2 작게 운영 맥미니, 도커, 로컬 모델, 대형 아키텍처는 필요해진 뒤에 붙여도 늦지 않다.
3 컨텍스트 절약 모델이 보는 것은 사용자의 한 줄이 아니라 시스템 지시문, 메모리, 툴 설명까지 포함한 전체 입력이다.
4 스키마 우선 LLM 위키나 지식 도구는 파일 수보다 어떤 규칙으로 저장하고 갱신할지가 중요하다.
5 승인 설계 자동 실행은 편하지만 데이터, 배포, 개발, 개인정보 영역에는 사람의 검토 지점이 필요하다.
6 법적 경계 투자, 개인정보, 사진 분류처럼 민감한 도메인은 출력 금지선과 저장 분리를 코드로 박아야 한다.
7 반복 개선 첫 결과가 어설퍼도 피드백 데이터, 비용 측정, 실패 기록이 쌓이면 실제 서비스에 가까워진다.

강의는 어떤 내용이었나

지피터스 22기 베스트 발표회 중 개발과 에이전트 사례를 모은 세션이다. 진행자는 각 스터디에서 나온 우수 발표를 12분 내외로 소개하도록 안내했고, 발표자들은 실제로 만든 제품, 운영 환경, 지식 관리 구조, 로컬 모델 튜닝, 비전 자동화 사례를 공유했다.

세션의 공통점은 단순한 도구 소개가 아니라 "어디까지 자동화하고 어디서 사람이 승인할 것인가"에 있었다. 투자 서비스는 법적 가드레일을, LLM 위키는 스키마를, 로컬 모델은 토큰 예산을, 오픈클로와 헤르메스 비교는 거버넌스를, 사진 분류 서비스는 비용과 정확도 실험을 중심으로 다뤘다.

0. 한눈에 보는 개발과 에이전트 사례

  1. 문제를 좁힌다. 투자 판단, 서버 운영, 지식 재사용, 사내 자동화, 사진 분류처럼 각 발표는 아주 구체적인 문제에서 시작했다.
  2. 최소 실행 단위를 만든다. 모바일 MVP, VPS, 최소 스키마, 4K 로컬 모델, 프로토타입처럼 작게 돌릴 수 있는 형태부터 만들었다.
  3. 모델이 아니라 운영 구조를 정한다. Gemini, Claude, 로컬 모델, OpenRouter보다 중요한 것은 어떤 입력을 주고 어떤 결과를 허용할지였다.
  4. 컨텍스트를 저장한다. LLM 위키와 KFOS는 대화와 산출물이 다음 작업의 맥락으로 이어지지 않는 문제를 정면으로 다뤘다.
  5. 자동화의 위험선을 둔다. 투자 추천, 개인정보, 사진 데이터, 개발 배포처럼 위험한 지점은 승인과 분리 저장을 붙였다.
  6. 실패 원인을 측정한다. 40분 지연, 오버피팅, 비용 1원, 정확도 90퍼센트처럼 감각이 아니라 수치와 로그를 기준으로 개선했다.
  7. 도구별 역할을 나눈다. 헤르메스는 상시 수집과 반복 운영에, 오픈클로는 승인형 개발 워크플로우에 더 맞는 식으로 구분했다.
  8. 결과를 제품으로 밀어본다. 단순 자동화에서 끝내지 않고 실제 사용자, 알파 테스트, 서비스 비용, 프라이버시까지 고민했다.

1. 프리폭스 — 투자 시그널을 모바일 검진센터로 만들기

프리폭스 발표의 출발점은 개인 투자자에게 종합검진센터가 없다는 문제였다. KRX, FRED, DART, 뉴스, 트위터에 정보는 많지만 각각 흩어져 있고, 환율이나 금리 변화가 내 ETF에 어떤 의미인지 연결해 주는 구조가 부족하다는 것이다.

발표자는 이를 "동네 의료원" 비유로 풀었다. 약사는 정해진 시간에 데이터를 가져오는 런치 데몬, 의사는 LLM, 진료기록부는 GraphRAG, 건물은 4층 아키텍처, 환자는 사용자다.

구성 역할 구현 포인트
홈 매크로 종합검진 S&P, 나스닥, VIX, 달러, 10년 국채 등 KPI와 헤드라인 합성
시그널 뉴스와 군중심리 네이버 검색 API와 Gemini Flash로 6개 카테고리 태깅
학습 카드 투자 교육 자산 배분 코스, 투자 용어, 퀴즈와 시그널 지수 누적
VIP AI 정밀진단 200포인트 게이트 이후 세금, GraphRAG, 백테스트 기능 연결
로컬 별관 심화 분석 서버린 위키, 검색 트렌드, 페어트레이딩, 실데이터 검증

가장 중요한 설계는 금융 도메인의 경계였다. 모든 진단서에는 투자자문이 아니라 정보 교육 목적이라는 디스클레이머를 자동 삽입하고, 매수 매도 추천은 출력 후 처리 가드레일로 막았다. 메인 DB와 볼트 DB도 분리해 이메일과 진단 본문을 별도로 저장했다.

에이전트는 내가 시키지 않아도 일하고 결과를 쌓아두는 구조라는 점에서 일반 챗봇과 다르다.

회고도 실용적이었다. 로컬 LLM을 통제하려는 욕심은 인프라 부채가 되었고, 영상 요약은 직접 처리보다 사용자의 LLM 구독으로 위임하는 편이 나았다. 데몬을 많이 두기보다 30분 캐시와 레이지 컴퓨트로 필요한 순간에만 계산하는 쪽이 1인 운영에 맞았다.

2. 에프킬라 — 맥미니 대신 VPS로 24시간 에이전트 켜기

에프킬라 발표는 헤르메스 입문자가 처음 마주하는 장비 부담을 다뤘다. "24시간 나를 도와주는 에이전트라면 24시간 켜둘 컴퓨터가 필요하고, 그러면 맥미니를 사야 하나"라는 생각이 자연스럽게 나오지만, 비용은 학생 할인 기준으로도 70만 원 이상이고 사양을 올리면 200만 원대까지 간다.

대안으로 선택한 것은 호스팅어 같은 VPS였다. 월 15,000원에서 25,000원 수준이면 1년에 약 20만 원으로 운영할 수 있고, 몇 년을 써도 맥미니 한 대 가격보다 낮다.

선택지 장점 막힌 지점 발표자의 판단
맥미니 로컬에서 안정적으로 상시 운영 초기 비용이 높음 꼭 처음부터 살 필요는 없음
VPS 저렴하고 24시간 운영 가능 리눅스, SSH, 권한, 네트워크 이해 필요 강력 추천
도커 컨테이너 격리와 배포에 유리 루트 계정, 파일 권한, 컨테이너와 서버 연결이 어려움 초보자에게는 과할 수 있음
전용 미니 PC 로컬 운영과 비용 절충 직접 관리 필요 VPS와 함께 현실적 대안

핵심 메시지는 "닭 잡는데 소 잡는 칼을 쓰지 마라"였다. 헤르메스는 생활을 쉽게 만들기 위한 도구인데, 도구를 쓰기 위해 더 어려운 방식을 먼저 선택하면 본말이 전도된다는 것이다.

발표자는 시행착오 끝에 VPS IP, 생성할 유저 이름, 비밀번호, SSH 별명 등을 입력하면 Tailscale, SSH, 유저 설정, 헤르메스 설정까지 한 번에 잡아주는 스킬도 만들었다. 질의응답에서는 리전에 따라 응답 속도 차이가 조금 있고, 싱가포르나 한국 리전이 유리하며, 헤츠너는 저렴하지만 유럽 리전이라 약간 느릴 수 있다고 설명했다.

3. 유피테르 — LLM 위키는 설치물이 아니라 운영 원리다

유피테르 발표는 LLM 위키의 원리를 정리하고, 이를 리서치 하네스와 카드 뉴스 자동화에 연결한 사례였다. 발표자는 처음에는 남이 만든 LLM 위키나 자료를 그대로 가져와 쓰려 했지만 실패했고, 이유는 원리와 스키마를 이해하지 못했기 때문이라고 봤다.

LLM 위키는 LLM이 운영하고 관리하는 온라인 백과사전으로 이해할 수 있다. 위키의 기본 요소는 문서, 문서 간 연결, 지속 업데이트다. LLM 위키에서는 이 운영을 AI가 맡는다.

원리 의미 발표자의 설명
Raw 원본 자료 사람이 모으거나 외부에서 들어온 원자료
Wiki 컴파일된 지식 LLM이 원본을 규칙에 맞춰 바꾼 문서
Schema 운영 규정 어떤 메타데이터와 본문 구조로 저장할지 정하는 헌법
Query 질문으로 항목 생성 필요한 문서를 질문에서 끌어냄
Ingest 원본을 잘게 나눠 등록 자료를 청킹해 위키 구조로 편입
Lint 낡은 문서 정비 스키마 변경, 오래된 문서, 규칙 위반을 점검

발표의 핵심은 스키마였다. 처음부터 완벽한 헌법전을 만들기보다 최소 규칙으로 시작해, 출처를 나타내는 origin, 큰 분야를 나타내는 field, 세부 키워드인 tags, AI 접근 횟수 같은 항목을 필요에 따라 추가했다.

하네스 적용 사례도 중요했다. 예전에는 긴 프롬프트 하나로 뉴스레터나 카드뉴스를 만들다 보니 결과가 들쭉날쭉하고, 오류가 나면 처음부터 다시 해야 했다. 발표자는 원문 수집부터 인포그래픽 생성, 최종 조립까지 7단계 하네스로 나누고, 특히 인포그래픽은 한 장씩 승인하도록 바꿨다.

쉬는 시간 시연에서는 옵시디언 그래프 뷰도 공유했다. 기존부터 쌓아둔 MD 파일은 약 5,700개였고, 아직 본격적인 인제스트보다는 스키마를 다듬는 단계라고 설명했다. 진행자는 자주 참조되는 문서의 접근 횟수가 뇌의 기억 강화와 닮아 있다는 관점도 덧붙였다.

4. 켱 — 로컬 모델은 컨텍스트부터 줄여야 한다

켱 발표는 가성비 LLM 스터디의 초보 대표 시행착오였다. 목표는 보안이 강한 회사 환경에서 외부 AI 에이전트를 쓰기 어려울 때, 로컬 모델이 자연어로 미리 만든 스킬을 호출하게 만드는 것이었다.

문제는 속도였다. 헤르메스에 텔레그램을 붙이고 로컬 모델 봇을 돌렸는데, "하이"라는 짧은 메시지에도 답이 오기까지 약 40분이 걸렸다. 원인을 찾아보니 사용 중인 Qwen 4B급 모델은 실제 컨텍스트가 약 4K인데, 시스템이 유지하려는 정보량은 약 14K였고, 헤르메스에 붙이기 위해 컨텍스트 길이를 64K처럼 설정해 둔 상태였다.

문제 원인 대응
첫 응답이 40분 지연 작은 모델에 너무 큰 시스템 프롬프트와 메모리가 들어감 입력을 4K 이하로 줄이는 전략 수립
모델 언로드와 재로드 반복 실제 처리량보다 설정 컨텍스트가 과장됨 헤르메스 연결용 설정과 실제 운영 입력을 분리
한 줄 질문도 무거움 사용자 말 외에 메모리, 유저 프로필, 툴 설명이 함께 들어감 메모리와 유저 프로필 비활성화
기본 툴셋 부담 웹검색, 브라우저 자동화, 터미널 등 도구 설명이 프롬프트를 차지 로컬 모델에 필요 없는 툴 비활성화

전략은 단순했다. "입장할 때는 64K인 척하고, 실제로는 4K만 하자"는 것이다. 메모리, 유저 프로필, 불필요한 툴을 끄자 4K급 모델도 대화할 정도로 빨라졌다.

이 발표의 메시지는 로컬 모델에만 해당하지 않는다. 프론티어 모델을 쓰더라도 요청은 사용자의 한 줄만이 아니라 시스템 지시문, 메모리, 도구 설명과 함께 움직인다. 좋은 자동화는 모델을 키우는 것만큼 입력을 줄이는 설계가 중요하다.

5. 조용준 — 오픈클로와 헤르메스는 승부가 아니라 역할 차이다

조용준 발표는 오픈클로와 헤르메스를 직접 비교한 사례였다. 발표자는 개발자이자 서비스 PO로 자동화에 관심이 많았고, 오픈클로를 약 2주, 헤르메스를 약 1주 사용한 뒤 두 에이전트에게 서로의 구조를 읽고 토론하게 했다.

처음에는 두 도구 모두 LLM을 붙이고, 기억을 파일에 기록하고, 외부 도구를 불러 쓰는 점에서 출발선이 비슷해 보였다. 하지만 학습과 운영 방식이 달랐다.

비교 축 오픈클로 헤르메스 판단
스킬 축적 사람이 요청하고 승인한 뒤 스킬화 루프를 돌며 스킬 후보를 모으고 개선 전자는 통제, 후자는 상시성에 강함
혼자 일하기 사람이 켤 때 명확한 흐름으로 실행 맥미니 등에서 24시간 루프 운영 가능 반복 수집과 모니터링은 헤르메스가 자연스러움
메모리 탐색 벡터 기반 텍스트 검색 텍스트 직접 검색 중심 설계 철학이 다름
검토 비용 승인형이라 틀린 결과를 막기 쉬움 잘못된 지식도 쌓일 수 있어 필터가 필요 자동화에는 거버넌스가 필요
적합 업무 개발, 배포, 승인 필요한 작업 슬랙, CS, GA, 보고서, 반복 데이터 수집 업무 위험도에 따라 나눈다

발표자는 "시키는 걸 배운다"와 "스스로 배운다"의 차이가 있지만, 이것을 우열로 보면 안 된다고 봤다. 영상 요약, 회의록, 데이터 수집, 반복 모니터링처럼 틀려도 치명적이지 않은 운영 업무는 헤르메스에 맞고, 개발과 배포처럼 승인과 검토가 필요한 흐름은 오픈클로가 더 맞을 수 있다.

결론은 거버넌스였다. 헤르메스도 사전 린팅과 검토 구조를 붙이면 더 안전해질 수 있고, 오픈클로도 스킬 저장과 재사용 흐름을 더 부드럽게 만들 수 있다. 중요한 것은 도구 선택 자체보다 검토 비용을 낮추는 운영 방식이다.

6. 제스테로 — KFOS로 지식 흐름을 하나의 제품으로 묶기

제스테로 발표는 비개발자 출신이 바이브 코딩 3개월 차에 만든 지식 흐름 관리 프로덕트 시연이었다. 발표자는 노션이나 옵시디언 같은 도구를 직접 만들어보겠다는 생각에서 KFOS라는 도구를 만들었다. 전사에는 이름 일부가 불명확하지만, 발표 맥락상 지식 흐름을 관리하는 OS를 의미한다.

KFOS는 "알아서 쓰고, 찾고, 쌓이고, 최신화까지 해주는" 도구를 목표로 한다. 옵시디언의 마크다운, 웹 클리퍼, LLM 답변, 코딩 과정, 프롬프트, 결과물을 한곳에 모으고, 사람이 승인한 뒤 볼트에 저장한다.

기능 역할 발표에서 보인 사용
옴니 검색 엔진과 LLM 입구 Perplexity 연결 검색과 인박스 진입점
볼트 옵시디언형 문서 저장소 마크다운 임포트와 익스포트, 관련 문서와 태그 표시
챔버 매트릭스 보드 시간, 행동, 단계별 프리셋으로 카드를 배치
코스모스 그래프 뷰 문서 연결을 다크모드와 타임라인 관점으로 시각화
펄스 최신화 흐름 X, Threads, 웹 정보와 기존 문서를 비교해 갱신 후보 생성
노바 합성 보드 문서, 코드, 프롬프트, HTML, 무드보드를 재활용 가능한 산출물로 뽑음

특히 클로드 코드 연동 버튼이 인상적이었다. API 키를 생성해 클로드 설정에 넣으면 클로드 코드에서 진행한 대화 내용이 연동되고, 결과만이 아니라 과정의 핵심 내용을 다시 사용할 수 있다. 발표자는 코덱스 연동은 아직 더 연구해야 한다고 했다.

질의응답에서는 개발 과정도 공유했다. 코딩이 끝나면 그 자료를 요약해 일반 클로드로 넘기고, 밖에서도 계속 토론하면서 모듈을 발전시켰다. 코드 작성은 클로드 코드에 맡기고, 큰 구조와 세부 논의는 바닐라 클로드와 오퍼스를 오가며 이어갔다. 이 경험 자체가 컨텍스트를 연결해 줄 도구가 필요하다는 문제의식으로 다시 KFOS에 반영됐다.

7. 이창환 — 루이 사진 분류에서 시작한 비전 자동화

이창환 발표는 헤르메스 입문반 사례였다. 발표자는 도구 자체보다 어떤 용도로 무엇을 만들지가 중요하다고 보고, 실제로 주변에서 필요한 자동화를 찾다가 반려견 루이 사진 분류 문제를 잡았다.

루이는 유치원에 다니고, 유치원에서는 알림장과 앨범 사진을 보낸다. 매번 약 100장씩 오는 사진 중 루이가 있는 사진만 골라 저장하는 일이 번거로워, 루이 사진을 탐지하고 다운로드하는 자동화를 만들었다.

단계 한 일 배운 점
1차 학습 루이 사진과 아닌 사진을 폴더로 나눠 피드백 단순 대화와 예시만으로도 분류가 개선됨
오류 확인 다른 날 사진에서 오버피팅과 오류 발생 같은 데이터만 반복하면 실제 환경에서 흔들림
서비스화 시도 누구나 쓸 수 있는 모바일 프로토타입 제작 개인 자동화도 제품 흐름으로 바꿔볼 수 있음
모델 비교 Gemini 2.5 Flash, Pro, GPT-4o, 4o mini 등 비교 서비스 전제에서는 정확도만큼 비용이 중요함
비용 튜닝 배치 10, 하드 네거티브, 정답지 비교 장당 약 0.6원 수준으로 합리화
현재 결과 원하는 사진을 약 90퍼센트 정확도로 수집 취향과 기준이 섞이는 비전 분류는 100퍼센트가 어렵다

흥미로운 지점은 정확도의 정의였다. "루이가 맞는가"만 보는 것이 아니라 뒷모습은 받을지, 너무 작은 사진은 뺄지, 비슷한 포메라니안은 어떻게 걸러낼지까지 사용자의 취향이 모델 기준에 섞인다.

질의응답에서는 사진 앨범 기능과 연결하면 더 넓은 수요가 있을 수 있다는 의견이 나왔다. 아이 사진, 배우자와 함께 나온 사진, 캡처 화면 분류처럼 "앨범에서 원하는 장면만 모으는 문제"로 확장할 수 있기 때문이다. 다만 아이 얼굴이나 반려견 사진을 다루는 서비스라면 프라이버시가 핵심 리스크가 된다.

8. 자주 막히는 곳

증상 대응
에이전트를 쓰려면 맥미니부터 사야 할 것 같다 로컬 PC, 저가 VPS, 미니 PC 중 하나로 먼저 24시간 운영 가능성을 작게 검증한다.
VPS에 헤르메스를 설치하다 리눅스, SSH, 권한에서 막힌다 서버, 컨테이너, 로컬 PC의 네트워크 경계를 나눠 이해하고, 자동 설정 스킬이나 Tailscale 같은 보조 도구를 쓴다.
LLM 위키를 설치했는데 잘 안 돌아간다 남의 폴더 구조를 복사하기보다 Raw, Wiki, Schema와 Query, Ingest, Lint 원리부터 최소 구조로 구현한다.
로컬 모델이 너무 느리다 모델 크기만 보지 말고 실제 컨텍스트, 시스템 프롬프트, 메모리, 툴 설명을 합친 입력량을 줄인다.
자동화 결과를 믿기 어렵다 한 장씩 승인, 정답지 비교, 봇 간 토론, 린트 같은 검토 단계를 중간에 넣는다.
에이전트가 잘못된 지식을 계속 쌓을까 걱정된다 상시 루프에는 사전 필터, 사후 린트, 사람 승인, 저장소 분리를 붙인다.
금융, 사진, 개인정보 서비스가 위험해 보인다 추천 금지선, 디스클레이머, 메인 DB와 볼트 DB 분리, 민감 데이터 마스킹을 설계 초기에 넣는다.
개인 자동화가 서비스로 확장될지 모르겠다 비용, 정확도, 예외 케이스, 개인정보 리스크를 작은 실험으로 수치화한다.

막히는 지점 대부분은 모델 성능보다 운영 경계가 불명확할 때 생긴다. 어떤 일을 자동화할지, 어떤 정보까지 줄지, 어디서 사람이 승인할지를 먼저 정하는 편이 빠르다.
