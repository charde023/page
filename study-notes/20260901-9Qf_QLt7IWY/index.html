30초 파인만 설명

AI는 질문 전체를 먼저 읽고(prefill), 그다음부터 답을 한 조각씩 쓴다(decode). 답을 이어 쓰려면 앞의 대화에서 만든 단서를 계속 봐야 하므로, 그 단서를 빠른 GPU 메모리에 둔다(KV 캐시). 대화가 길어지면 단서가 더 많은 자리를 차지하고, 다음 조각을 쓸 때 읽어야 할 데이터도 커진다. 그래서 GPU의 계산기가 빨라도 단서를 저장하고 옮기는 속도와 자리가 병목이 될 수 있다.

한 줄로 다시

긴 AI 대화의 비용은 “더 많이 계산해서”만이 아니라, 앞선 단서를 빠른 메모리에 유지하고 계속 읽어야 해서 커진다.

한 장면으로 이해하기

속기사가 긴 회의록을 보며 답변을 한 단어씩 쓰는 장면을 떠올려 보자.

"회의록을 매번 다시 읽기는 느림" 문제
→ "이미 정리한 단서 카드를 비싼 책상 위에 펼쳐 둠" 작동 방식
→ "답은 빨라지지만, 회의가 길수록 책상이 차고 동시에 받을 손님이 줄어듦" 결과

  • 비유의 대응: 속기사가 모델, 앞의 회의록이 문맥, 단서 카드가 KV 캐시, 비싼 책상이 GPU의 HBM이다.
  • 비유가 깨지는 지점: KV 캐시는 원문이나 사람의 장기 기억이 아니다. Transformer의 층별로 이전 토큰에서 계산한 Key·Value 숫자 표현이며, 크기와 읽기 비용은 모델 구조·정밀도·문맥 길이·배치에 따라 달라진다.

정확한 이름 붙이기

개념 쉬운 말 정확한 말 흔한 오해
Prefill 질문 전체 읽기 입력 토큰을 병렬 처리해 첫 출력을 준비 답 전체를 이미 쓰는 단계는 아니다.
Decode 답을 한 조각씩 쓰기 이전 출력 다음 토큰을 순차 생성 요청 간 배칭까지 불가능한 것은 아니다.
KV cache 앞 문맥의 단서 보관함 이전 토큰의 Key·Value를 저장해 재계산을 줄임 원문 복사본이나 영구 기억이 아니다.
산술 강도 한 번 가져온 데이터로 계산하는 양 이동한 데이터 대비 연산량 칩의 최대 FLOPS 그 자체가 아니다.
Roofline 어디서 속도가 막히는지 보는 지도 연산 성능·메모리 대역폭과 산술 강도로 상한을 분석 실측 속도를 보장하는 성적표는 아니다.

Prefill은 compute-bound, decode는 memory-bound가 되기 쉽다는 것이 이 글의 핵심이다. 다만 이는 모델·입출력 길이·배치·커널·하드웨어에 따라 달라질 수 있는 경향이지, 모든 요청에 적용되는 법칙은 아니다.

내가 설명해 보기

1. 원인

모델 크기는 같은데 문맥이 길어지면, 왜 한 사용자의 다음 토큰이 더 비싸질 수 있을까?

모범 답안 보기

재계산을 아끼려고 이전 토큰의 Key·Value를 KV 캐시에 저장한다. 문맥이 길어지면 이 캐시가 자리를 더 많이 차지하고, decode attention이 다음 토큰을 만들 때 읽어야 할 데이터도 늘어난다. 그래서 메모리 용량과 대역폭이 비용·속도의 병목이 될 수 있다.

2. 대조

Prefill과 decode는 무엇이 다르고, 사용자는 각각을 어떤 지표로 느낄까?

모범 답안 보기

Prefill은 입력 전체를 병렬로 처리하여 가중치를 여러 토큰에 재사용하기 쉽고, 보통 연산 병목이 되기 쉽다. Decode는 앞 출력에 의존해 토큰을 하나씩 만들며 KV를 계속 읽으므로 보통 메모리 병목이 되기 쉽다. 사용자는 prefill을 첫 토큰까지의 시간(TTFT), decode를 토큰 사이 시간(TBT·TPOT)으로 느낀다.

3. 적용

에이전트 사용자가 결과를 보고 25분 뒤에 돌아올지 모른다면, KV 캐시를 계속 HBM에 둘까?

모범 답안 보기

항상 두거나 바로 버리는 단일 정답은 없다. 사용자가 돌아올 확률과 예상 시점, KV 용량, 다른 요청의 HBM 수요, DDR·SSD로 옮기고 다시 가져오는 시간, 버린 뒤 재계산하는 비용을 함께 비교해야 한다. 영상에서 제시한 25분과 40GB는 분석 workload의 median이지 모든 서비스의 고정 기준은 아니다.

이번 글의 통찰

1. 빠른 칩이 느린 서비스를 자동으로 고치지는 않는다

  • [원문] Prefill은 보통 compute-bound, decode는 memory-bound가 되기 쉽고, decode attention은 사용자별 KV가 달라 배치를 키워도 병목이 남는다고 설명한다.
  • [해석] 제품에 필요한 것은 “가장 빠른 칩”이 아니라 내 workload의 병목을 줄이는 조합이다. 최대 FLOPS보다 문맥 길이·배치·TTFT·TBT를 함께 봐야 한다.
  • [경계] 어떤 단계가 실제 병목인지는 모델·커널·하드웨어·요청 분포를 계측하기 전에는 확정할 수 없다.

2. 사람의 대기 시간도 인프라 workload가 된다

  • [원문] 소개된 agentic workload에서 사람의 대기·검토가 session의 약 92%, request 사이 median 대기가 약 25분이며, 이 동안 유지할 KV가 median 약 40GB라고 설명한다.
  • [해석] 에이전트의 비용 문제는 LLM이 계산하는 시간만이 아니라, 사용자가 돌아올 때까지 문맥을 어디에 둘지의 문제다.
  • [경계] 이 수치는 소개된 분석 workload의 결과다. 업무·사용자·제품별 분포를 재지 않고 보편 법칙으로 쓰면 안 된다.

3. 최적화의 목표는 최대 토큰이 아니라 약속을 지킨 유효 작업이다

  • [원문] Interactivity와 throughput에는 trade-off가 있고, PD 분리는 raw throughput보다 SLO를 만족하는 goodput을 높이는 데 목적이 있다고 설명한다.
  • [해석] 서비스의 성능은 “초당 토큰” 하나가 아니라 사용자 속도 약속을 지키며 처리한 요청의 양과 비용으로 보아야 한다.
  • [경계] PD 분리는 새 KV 전송 비용을 만든다. 규모가 작거나 네트워크가 느리면 이득이 사라질 수 있다.

교육자 · 구조적 비유

  • 관련성: 작업 메모리와 HBM은 같은 것은 아니지만, 핵심과 근거를 한꺼번에 다 펼쳐 놓으면 전체 처리가 어려워진다는 구조는 닮았다.
  • 통찰: 설명은 “30초 설명→정확한 이름→스스로 회상→필요할 때 근거” 순서로 부하를 조절할 수 있다.
  • 질문/행동: 학습자가 보지 않고 30초 설명하게 한 뒤, 막힌 단어만 근거로 다시 열게 할 수 있을까?

사업가 · 직접 전이

  • 관련성: AI 제품의 원가와 사용자 경험을 함께 결정하는 문제다.
  • 통찰: 모델과 GPU 가격만으로는 수익성을 알 수 없다. 실제 요청 분포에서 TTFT·TBT·완료율·동시성·원가를 묶어야 한다.
  • 질문/행동: 내 AI 업무 하나의 SLO를 만족한 완료 작업당 원가를 재 본 적이 있는가?

마케터 · 직접 전이

  • 관련성: “최신 GPU”나 “초당 토큰”은 기술 주장이지, 고객이 느끼는 가치 자체는 아니다.
  • 통찰: 고객에게는 “첫 답이 언제 오는가”, “중간에 멈추지 않는가”, “일을 끝내는가”로 증명해야 한다.
  • 질문/행동: 내가 쓴 “빠르다”는 카피를 TTFT·TBT·완료 시간 중 하나의 검증 가능한 약속으로 바꿀 수 있을까?

AI/SW 엔지니어 · 직접 전이

  • 관련성: 아키텍처 선택 전에 workload의 prefill·decode·KV 생명주기를 측정해야 하는 문제다.
  • 통찰: 문맥 압축·prefix caching·continuous batching·KV offload·PD 분리는 같은 병목을 풀지 않는다. 측정한 병목에 맞는 도구를 골라야 한다.
  • 질문/행동: 최근 에이전트 작업 20개의 입력 길이·출력 길이·TTFT·TBT·유휴 시간을 한 번에 볼 수 있는가?

가치 지도

"긴 문맥과 유휴 agent session이 비싼 메모리를 점유" 문제
→ "같은 사용자 경험을 더 적은 자원으로 제공" 수혜자: 최종 사용자·AI 제품 운영자
→ "AI 제품 팀 또는 기업 고객이 인프라·API 비용을 지불" 지불자

가장 먼저 볼 가치 지표

SLO를 만족한 완료 작업당 원가. 초당 토큰이 늘어도 완료율이 떨어지거나 응답 약속을 어기면 가치가 늘었다고 할 수 없다.

작은 실험 하나

  • 행동 1개: 반복하는 AI 업무 20건을 같은 모델로 짝지어 실행한다. A는 누적 대화 전체를 넣고, B는 필수 사실만 남긴 1쪽 브리프를 넣는다.
  • 측정 1개: 1,000 입력 토큰당 검수 통과 완료 작업 수를 A·B에서 비교한다.
  • 중단 기준 1개: 20건 후 B가 A보다 이 지표를 15% 이상 높이지 못하면, 문맥 축약을 상시 규칙으로 확대하지 않는다.

더 깊이 읽기

기존 상세 정리 펼치기 — 개념·수치·화자 디테일·15개 섹션·체크리스트

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
추론(inference)의 두 단계 LLM 서비스 속도와 비용을 이해하는 출발점 입력을 한 번에 처리하는 prefill과 토큰을 하나씩 생성하는 decode는 완전히 다른 성격의 작업이다.
KV 캐시(KV cache) 긴 문맥과 대화형 AI의 메모리 비용을 결정 이전 토큰의 Key·Value를 저장해 재계산을 피하지만, 문맥이 길어질수록 메모리를 폭발적으로 사용한다.
산술 강도(arithmetic intensity) 칩 성능 병목을 판단하는 핵심 지표 메모리에서 데이터를 한 번 읽고 얼마나 많이 계산에 재사용하는지를 나타낸다.
루프라인 분석(roofline analysis) GPU·AI 반도체 벤치마크를 읽는 기준 어떤 작업이 연산 병목인지, 메모리 병목인지 하드웨어 관점에서 보여준다.
상호작용성(interactivity)과 처리량(throughput) AI 서비스의 사용자 경험과 사업성 사이의 균형 한 명에게 빠르게 응답할수록 서버 전체 처리량은 줄어들 수 있다.
연속 배칭(continuous batching) 실제 서비스에서 GPU 빈칸을 줄이는 기술 요청 단위가 아니라 토큰 생성 iteration 단위로 스케줄링한다.
PagedAttention KV 캐시 메모리 낭비를 줄이는 핵심 기법 운영체제의 페이지 테이블처럼 KV 캐시를 동적으로 할당한다.
추측 디코딩(speculative decoding) decode 속도를 높이는 대표 기법 작은 모델이 후보 토큰을 빠르게 만들고 큰 모델이 한꺼번에 검증한다.
Prefill-Decode 분리(PD disaggregation) prefill과 decode의 성격 차이를 인프라 구조로 해결 prefill 서버 풀과 decode 서버 풀을 나누어 goodput을 높인다.
Agentic AI의 KV 캐시 문제 에이전트 시대에는 연산보다 “기억 유지”가 병목 사람이 기다리는 동안 KV 캐시를 HBM에 계속 둘 수 없어 계층형 메모리 관리가 중요해진다.

내가 모를 만한 것 / 처음 보는 것

  • KV 캐시(KV cache) — Transformer가 이전 문맥을 다시 계산하지 않도록 각 토큰의 Key와 Value를 저장한 것.
  • TTFT(Time To First Token) — 사용자가 프롬프트를 보낸 뒤 첫 토큰이 나오기까지의 시간.
  • TBT(Time Between Tokens), TPOT(Time Per Output Token) — decode 단계에서 토큰 사이 간격 또는 출력 토큰당 시간.
  • 산술 강도(arithmetic intensity) — 메모리에서 1바이트를 읽었을 때 수행할 수 있는 연산량.
  • 루프라인 분석(roofline analysis) — 하드웨어의 연산 성능과 메모리 대역폭을 기준으로 병목을 시각화하는 방법.
  • GQA(Grouped Query Attention) — 여러 Query head가 하나의 Key·Value를 공유해 KV 캐시를 줄이는 attention 구조.
  • MQA(Multi-Query Attention) — 모든 Query가 하나의 Key·Value를 공유하는 더 강한 KV 절감 방식.
  • MLA(Multi-head Latent Attention) — DeepSeek 계열에서 쓰는 KV 압축 attention 방식.
  • PagedAttention — KV 캐시를 고정 크기 블록으로 나누어 동적 할당하는 vLLM 핵심 기술.
  • Chunked prefill — 긴 prefill 요청을 작은 조각으로 잘라 decode 지연을 줄이는 기법.
  • Speculative decoding — 작은 draft model이 후보 토큰을 만들고 큰 target model이 검증하는 디코딩 가속 기법.
  • PD disaggregation — prefill과 decode를 별도 서버 풀에서 처리하는 구조.
  • Goodput — 단순 처리량이 아니라 서비스 품질 목표(SLO)를 만족하는 유효 처리량.
  • 계층형 메모리(hierarchical memory) — SRAM, HBM, DDR, SSD, flash 등을 역할별로 나눠 KV 캐시를 이동·저장하는 구조.
  • 이종 컴퓨팅(heterogeneous computing) — GPU, LPU, NPU, CPU, 스토리지 가속기 등을 역할별로 섞어 쓰는 방식.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Google GCP의 토큰 사용량은 12개월 만에 50배, 14개월 만에 100배, 이후 2024년 대비 약 330배 수준까지 증가했다고 언급했다.
  2. 전 세계 데이터센터 투자 규모는 2030년까지 약 6.7조 달러로 제시됐다.
  3. 한국의 4대 메가프로젝트는 2035년까지 18.4GW 규모 데이터센터를 목표로 한다고 언급됐다.
  4. 미국에서 데이터센터 전력 연결까지 평균 약 5년이 걸린다는 점이 병목으로 제시됐다.
  5. Anthropic의 inference 마진은 70~80%로 알려져 있고, 상한은 90% 정도라 추가 마진 개선 여지가 크지 않다고 설명했다.
  6. HyperAccel Bertha는 HBM이 아니라 LPDDR을 사용하며, Samsung 4nm 공정으로 제작됐다.
  7. Bertha의 메모리 대역폭은 546GB/s, H100은 약 3TB/s로 비교됐다.
  8. HyperAccel은 내부 아키텍처상 메모리 대역폭 활용률을 90% 이상으로 목표한다고 설명했다.
  9. Bertha의 목표 가격은 약 5,000달러, 메모리 용량은 칩당 192GB라고 말했다.
  10. Llama 3.1 70B 기준 KV 캐시는 토큰당 약 320KB가 필요하다.
  11. 128K context를 KV 캐시로 저장하면 약 40GB가 필요하다.
  12. H100 80GB 메모리 기준, 한 사용자의 128K context만으로도 메모리 절반이 KV 캐시에 쓰일 수 있다.
  13. Llama 3.1 405B를 batch 32, 평균 context 128K로 serving하면 단순 용량 기준 H100 약 27개, 실제로는 32개 수준이 필요하다고 설명했다.
  14. H100의 BF16 연산 성능은 약 1PFLOP/s, 메모리 대역폭은 약 3.35TB/s로, ridge point가 약 300 근처라고 설명했다.
  15. Decode attention은 batch를 늘려도 사용자별 KV가 달라 arithmetic intensity가 잘 올라가지 않는다고 강조했다.
  16. Agentic AI workload에서 평균 session은 62.6분, request는 약 9.2개, request당 step은 약 9개라고 제시했다.
  17. Agent session에서 사람의 대기 시간이 약 92%, tool call이 4.8%, LLM call이 3.3%라고 설명했다.
  18. request 사이 median 대기 시간은 약 25분, 이때 점유되는 KV 캐시 median 용량은 약 40GB라고 언급했다.
  19. KV 캐시의 “골든타임”은 5~10분 정도로 보고, 이후 evict 여부를 예측한다고 설명했다.
  20. Groq LPU는 약 500MB SRAM 기반이고, NVIDIA Vera Rubin 계열에서는 FFN 일부를 맡기는 식의 이종 구조가 논의된다고 설명했다.

1. AI 인프라로 이동하는 가치 포착

영상은 AI 산업의 가치 포착(value capture)이 어디에서 일어나고 있는지로 시작한다. 모델 자체의 발전 속도가 너무 빨라지면서, 모델만으로 장기 차별화를 만들기 어려워지고 있다. 그 결과 돈을 버는 지점은 크게 두 방향으로 이동한다.

첫째는 아래쪽의 인프라(infrastructure) 다. 데이터센터, 전력, 칩, 메모리, 네트워크, inference serving stack이 여기에 들어간다. 둘째는 위쪽의 애플리케이션(application) 이다. 실제 고객 문제를 해결하고 과금하는 서비스가 여기에 해당한다.

이번 강의는 그중에서도 아래쪽, 즉 AI 반도체와 inference engineering을 다룬다. 노정석 대표는 SemiAnalysis, NVIDIA 발표, AI 칩 회사의 벤치마크를 이해하려면 이 내부 원리를 알아야 한다고 강조한다.

2. 영원한 compute 부족과 토큰 수요 폭증

이진원 CTO는 Sam Altman의 “compute crunch에서 영원히 벗어나지 못할 수도 있다”는 발언을 인용한다. Training이든 inference든 compute는 계속 부족할 가능성이 크다는 뜻이다.

토큰 수요도 폭발하고 있다. Google은 GCP의 토큰 사용량이 12개월 만에 50배, 이후 14개월 만에 100배, 더 최근에는 2024년 대비 약 330배 수준까지 늘었다고 발표했다. 모델 크기도 한동안 정체된 것처럼 보였지만 다시 수조~10조 파라미터급 논의가 나오고 있다.

이 수요를 감당하기 위해 전 세계적으로 대규모 데이터센터 투자가 진행된다. 하지만 병목은 전력이다. 데이터센터를 지어도 전기가 들어오기까지 시간이 오래 걸리고, 한국 수도권에서도 전력 심사 탈락 사례가 많다.

또한 frontier lab은 매출이 빠르게 늘지만 compute 확보 속도는 그보다 느리다. 매출이 10배 늘고 compute가 3배 늘면, 결국 inference 단가 상승 압력이 생긴다. 마진을 더 올리기도 어렵고, training GPU를 inference로 더 돌리는 것도 한계가 있기 때문이다.

3. HyperAccel Bertha: HBM 대신 LPDDR을 택한 AI 반도체

HyperAccel의 첫 데이터센터형 AI 반도체 Bertha는 HBM이 아니라 LPDDR을 사용한다. HBM은 대역폭이 크지만 비싸고 구하기 어렵다. LPDDR은 상대적으로 저렴하고 전력 소모가 낮다.

Bertha는 Samsung 4nm 공정으로 제작됐고, 칩 bring-up 중이다. Bring-up은 실제 칩 위에 소프트웨어를 올려 동작시키고 서비스 가능한 수준으로 만드는 과정이다.

Bertha의 특징은 다음과 같다.

항목 내용
메모리 LPDDR
공정 Samsung 4nm
메모리 대역폭 약 546GB/s
대역폭 활용률 목표 90% 이상
메모리 용량 칩당 192GB
목표 가격 약 5,000달러
포지션 저전력·저비용 inference 칩

H100의 이론 메모리 대역폭은 약 3TB/s로 Bertha보다 훨씬 높지만, 실제 workload에서 대역폭을 얼마나 활용하느냐가 중요하다. 이진원 CTO는 HyperAccel 아키텍처가 높은 utilization을 목표로 한다고 설명한다.

4. LLM 추론의 두 단계: prefill과 decode

LLM inference는 크게 두 단계로 나뉜다.

단계 설명 성격
Prefill 사용자의 입력 prompt 전체를 한 번에 처리해 첫 출력 토큰을 만든다. 병렬 처리에 유리
Decode 이전에 생성한 토큰을 다시 입력으로 넣어 다음 토큰을 하나씩 만든다. 순차 처리

예를 들어 사용자가 “토마토는 과일인가?”라고 묻는다면, 입력 prompt 전체를 처리해 첫 토큰 “예”를 만드는 과정이 prefill이다. 이후 “예” 다음에 “그것은”, 그다음 “과일입니다”처럼 한 토큰씩 생성하는 과정이 decode다.

여기서 중요한 사용자 경험 지표가 나온다.

  • TTFT(Time To First Token): 입력 후 첫 토큰이 나오기까지의 시간
  • TBT(Time Between Tokens): 출력 토큰 사이의 시간
  • TPOT(Time Per Output Token): 출력 토큰 하나당 걸리는 시간

Prefill은 긴 문서도 한 번에 병렬 연산할 수 있어 GPU의 장점을 잘 살린다. 반면 decode는 이전 토큰이 나와야 다음 토큰을 만들 수 있어 구조적으로 sequential하다.

5. Transformer 내부: attention과 FFN

Transformer의 핵심 연산은 크게 두 가지다.

  1. Attention
  2. FFN(Feed-Forward Network)

Attention은 토큰들 사이의 관계를 계산한다. Query, Key, Value를 만들고, Query와 Key의 유사도를 계산한 뒤 Value를 섞어 문맥 정보를 만든다.

FFN은 각 토큰의 embedding vector 내부 차원들 사이의 연산을 담당한다. Dense model 기준으로 parameter 비중은 대략 attention 20%, FFN 80% 정도다. MoE(Mixture of Experts) 모델로 가면 FFN 쪽 비중이 더 커진다.

정리하면 다음과 같다.

구성 요소 역할 직관
Attention 토큰 간 관계 학습 “이 단어가 앞의 어떤 단어를 참고해야 하는가”
FFN 토큰 내부 feature 연산 “이 토큰 벡터 안의 의미 차원을 변환”

6. KV 캐시: 긴 문맥의 진짜 비용

Decode 단계에서는 새 토큰의 Query를 만들 때, 이전 모든 토큰의 Key와 Value가 필요하다. 이전 Key와 Value를 매번 다시 계산하면 비효율적이므로, inference 시스템은 이를 메모리에 저장한다. 이것이 KV 캐시(KV cache) 다.

KV 캐시는 ChatGPT가 이전 대화 문맥을 계속 참고할 수 있게 해주는 핵심 장치다. 하지만 비용이 크다.

Llama 3.1 70B 기준으로 토큰 하나의 KV 캐시는 약 320KB다. 128K context를 저장하면 약 40GB가 필요하다. H100 80GB 메모리의 절반이 한 사용자의 KV 캐시에 쓰일 수 있다는 뜻이다.

KV 캐시를 줄이는 대표 방법은 다음과 같다.

방법 설명
작은 모델 사용 parameter와 KV 크기 자체를 줄인다.
양자화(quantization) BF16/FP16 대신 8-bit, 4-bit 등으로 저장한다.
GQA 여러 Query head가 하나의 Key·Value를 공유한다.
MQA 모든 Query가 하나의 Key·Value를 공유한다.
MLA Key·Value를 latent vector로 압축한다.
Sliding-window attention 전체 문맥이 아니라 가까운 window만 본다.
KV offloading CPU DRAM, SSD, flash 등으로 KV를 내보냈다가 다시 읽는다.

7. 산술 강도와 Roofline 분석

AI 칩의 성능 병목은 단순화하면 두 가지다.

  1. 초당 얼마나 많이 계산할 수 있는가
  2. 메모리에서 데이터를 얼마나 빨리 가져올 수 있는가

산술 강도(arithmetic intensity) 는 메모리에서 데이터를 한 번 읽고 얼마나 많은 연산을 하는지를 나타낸다. 데이터 재사용이 많으면 산술 강도가 높고, 적으면 낮다.

  • Prefill: 여러 토큰이 한 번에 들어오므로 같은 weight를 많은 토큰에 재사용한다. 산술 강도가 높다.
  • Decode: 한 토큰씩 처리하므로 weight 재사용이 적다. 산술 강도가 낮다.

루프라인 분석(roofline analysis) 은 하드웨어의 최대 연산 성능과 메모리 대역폭을 기준으로 workload가 어디에서 병목인지 보여준다.

영역 의미
Compute-bound 메모리는 충분히 공급되지만 연산 유닛이 부족한 상태
Memory-bound 연산 유닛은 놀고 있지만 메모리에서 데이터가 늦게 오는 상태
Ridge point compute-bound와 memory-bound가 갈리는 지점

H100 기준 BF16 연산 성능은 약 1PFLOP/s, 메모리 대역폭은 약 3.35TB/s로, ridge point는 약 300 근처라고 설명된다. Prefill은 보통 이보다 오른쪽에 있어 compute-bound가 되고, decode는 왼쪽에 있어 memory-bound가 된다.

8. Decode가 어려운 이유: attention은 batch로도 잘 해결되지 않는다

Decode의 효율을 높이는 쉬운 방법은 batch size를 늘리는 것이다. 여러 사용자의 다음 토큰을 모아 한 번에 처리하면 weight를 재사용할 수 있어 산술 강도가 올라간다.

하지만 attention에서는 문제가 생긴다. 각 사용자의 KV 캐시는 서로 다르기 때문이다. 내 Query는 내 이전 대화의 Key·Value와 곱해야 하고, 다른 사용자의 Key·Value를 공유할 수 없다.

그래서 FFN이나 QKV projection은 batch를 늘려 효율을 높일 수 있지만, attention의 KV 읽기는 여전히 병목으로 남는다. 긴 context 시대에 decode attention이 특히 어려운 이유다.

GQA, MQA, MLA, KV quantization, prefix caching은 모두 이 문제를 완화하기 위한 기법이다.

9. Interactivity와 Throughput의 Trade-off

AI 반도체나 GPU 성능은 하나의 숫자로 말하기 어렵다. 서비스에서 중요한 축이 두 개이기 때문이다.

지표 의미
Interactivity 사용자 한 명이 초당 받는 토큰 수
Throughput 서버 또는 GPU 전체가 초당 생성하는 총 토큰 수

맥도날드에서 여러 명의 햄버거를 한꺼번에 만들면 가게 전체 처리량은 올라가지만, 첫 번째 손님 입장에서는 기다림이 길어질 수 있다. AI inference도 같다.

Batch를 크게 하면 GPU utilization과 throughput은 올라가지만, 사용자 한 명의 응답 속도는 떨어질 수 있다. 반대로 한 명에게 빠르게 응답하려면 batch를 줄여야 하고, 그러면 throughput이 떨어진다.

SemiAnalysis의 InferenceX 그래프는 이 trade-off를 Pareto curve로 보여준다. 특정 서비스가 “사용자당 최소 100 tokens/s가 필요하다”고 정하면, 그 조건에서 어떤 GPU·소프트웨어 stack이 가장 높은 throughput을 내는지 비교할 수 있다.

10. vLLM과 실제 serving 최적화

실제 사용자의 요청은 동시에 규칙적으로 들어오지 않는다. 누군가는 짧은 대화를 하고, 누군가는 긴 코드를 붙여 넣는다. 그래서 serving framework가 중요하다.

대표 framework는 vLLM, SGLang 등이다.

Continuous batching

과거의 static batching은 여러 요청을 묶은 뒤, 가장 긴 요청이 끝날 때까지 다음 요청을 못 받았다. 그러면 짧은 요청이 끝난 자리도 빈칸으로 낭비된다.

Continuous batching은 요청 단위가 아니라 토큰 생성 iteration 단위로 스케줄링한다. 어떤 요청이 끝나면 다음 iteration에서 새 요청을 바로 넣는다. 이를 통해 GPU의 빈칸을 줄인다.

PagedAttention

LLM이 몇 토큰을 출력할지는 미리 알 수 없다. 최악의 길이를 기준으로 KV 캐시 메모리를 미리 잡아두면 대부분 낭비된다.

PagedAttention은 운영체제의 page table처럼 KV 캐시를 block 단위로 동적 할당한다. 필요한 만큼만 physical memory block을 연결해 사용하므로 메모리 효율이 올라간다.

단, 모든 사용자가 동시에 최악의 길이로 출력하면 메모리가 부족할 수 있다. 이 경우 KV를 밖으로 evict하고 다시 불러오는 복잡한 처리가 필요하다.

Chunked prefill

긴 prefill 요청이 한 번에 들어오면 decode 중인 요청들이 멈칫할 수 있다. 그래서 긴 prefill을 작은 chunk로 잘라 decode 사이사이에 끼워 넣는다.

보통 우선순위는 다음과 같다.

  1. Decode 우선
  2. 이미 시작된 prefill chunk
  3. 새로 들어온 prefill

이 방식은 TTFT를 약간 희생하더라도 TBT를 안정적으로 유지하는 데 유리하다.

11. Speculative decoding

Speculative decoding은 decode가 느리다는 문제를 줄이기 위한 대표 기법이다.

아이디어는 단순하다.

  1. 작은 draft model이 여러 후보 토큰을 빠르게 생성한다.
  2. 큰 target model이 그 후보들을 prefill처럼 한꺼번에 검증한다.
  3. 맞는 토큰은 받아들이고, 틀린 지점부터 다시 생성한다.

Decode를 한 토큰씩 큰 모델로 처리하는 대신, 작은 모델의 빠른 예측과 큰 모델의 병렬 검증을 조합하는 방식이다.

Meta 계열 연구에서는 같은 모델의 중간 layer에 LM head를 붙여 draft 역할을 하게 하는 방식도 있다. DeepSeek의 DSpark는 diffusion transformer 같은 구조를 draft model로 활용해 여러 토큰을 동시에 제안하는 방식으로 설명됐다.

핵심은 decode 일부를 prefill처럼 바꾸어 arithmetic intensity를 높이는 것이다.

12. Prefill-Decode Disaggregation

Prefill과 decode는 성격이 다르다. Prefill은 긴 입력을 병렬 처리하고, decode는 짧은 토큰을 순차 생성한다. 두 작업을 같은 GPU pool에서 처리하면 서로 방해한다.

그래서 prefill 전용 pool과 decode 전용 pool을 나누는 방식이 등장했다. 이것이 PD disaggregation(Prefill-Decode disaggregation) 이다.

Prefill pool에서 생성한 KV 캐시는 decode pool로 전달되어야 하므로, 두 pool 사이의 네트워크 대역폭이 중요하다. 규모가 작으면 이점이 작을 수 있고, 충분한 규모와 빠른 interconnect가 있을 때 효과가 크다.

이 방식은 총 raw throughput 자체를 늘린다기보다, SLO를 만족하는 유효 처리량인 goodput을 높이는 데 목적이 있다.

효과가 큰 상황은 다음과 같다.

  • 입력이 길고 출력이 짧은 workload
  • SLO가 엄격한 서비스
  • 대규모 GPU cluster
  • 고속 interconnect가 있는 환경

13. Agentic AI가 만드는 새로운 inference workload

Chatbot이나 reasoning 모델을 넘어 agentic AI로 가면 workload가 크게 달라진다.

Agent session은 사람이 한 번 prompt를 넣고 끝나는 구조가 아니다. 사람이 요청을 주면 agent가 LLM과 tool을 여러 번 호출하고, 결과를 만든 뒤 사람이 다시 확인하고 다음 요청을 준다.

용어를 정리하면 다음과 같다.

용어 의미
Session agent 사용 시작부터 종료까지 전체 기간
Request 사람이 prompt를 넣고 agent가 결과를 만들 때까지의 단위
Step LLM call 또는 tool call 한 번

분석된 workload에서는 평균 session이 62.6분, session당 request가 9.2개, request당 step이 약 9개였다. 즉 한 session 안에 약 100개 step이 들어간다.

더 중요한 점은 사람이 대부분의 시간을 차지한다는 것이다.

구분 비중
사람 대기·검토 약 92%
Tool call 약 4.8%
LLM call 약 3.3%

사람은 agent가 일하는 동안 다른 일을 한다. 문제는 그동안 KV 캐시를 비싼 HBM에 계속 들고 있어야 하느냐다. request 사이 median 대기 시간은 약 25분이고, median KV 캐시 점유량은 약 40GB로 제시됐다.

따라서 agentic AI 시대에는 KV 캐시를 언제 HBM에 남기고, 언제 DDR·SSD·flash로 내보내고, 언제 다시 가져올지가 중요해진다. 이진원 CTO는 5~10분 정도를 KV 캐시의 “골든타임”으로 보고, 이후에는 가벼운 ML 모델로 사용자가 곧 돌아올지 예측해 eviction 여부를 결정하는 접근을 설명했다.

14. 이종 컴퓨팅과 AI 반도체의 미래

앞으로는 하나의 GPU가 모든 일을 처리하기보다, 각 하드웨어가 잘하는 부분을 맡는 이종 컴퓨팅(heterogeneous computing) 으로 갈 가능성이 크다.

예를 들어 Groq LPU는 SRAM 기반으로 낮은 arithmetic intensity 영역에서 강점이 있다. 하지만 KV 캐시를 많이 저장하기에는 메모리 용량이 작다. 그래서 NVIDIA Vera Rubin 계열에서는 prefill과 attention 일부는 GPU가 맡고, FFN 일부를 Groq LPU가 맡는 식의 구조가 논의된다.

MoE 모델에서는 expert별 batch가 작아져 FFN도 낮은 arithmetic intensity 영역에 놓일 수 있다. 이 경우 Groq 같은 LPU가 적합할 수 있다.

결국 미래 AI 인프라는 다음과 같은 조합이 될 가능성이 크다.

  • GPU: 범용 대규모 연산
  • LPU/NPU: 특정 inference 단계 가속
  • CPU DRAM: 대용량 KV cache 임시 저장
  • SSD/Flash: 장기 KV cache offload
  • 고속 interconnect: prefill-decode pool 연결
  • orchestration software: 전체 스케줄링과 비용 최적화

15. AI가 바꾸는 반도체 설계

마지막으로 AI가 반도체 설계 자체를 바꾸는 이야기도 나온다. RTL, Verilog, CUDA kernel, verification, layout, placement, routing 등 반도체 설계에는 검증 가능한 영역이 많다.

이진원 CTO는 3년 뒤에는 AI가 본인보다 더 잘할 수도 있다고 표현한다. 특히 verification은 소프트웨어 기반이고, 통과 여부가 명확한 경우가 많아 AI 적용 가능성이 크다.

OpenAI가 Codex를 활용해 CUDA 관련 작업을 빠르게 만들었다는 사례도 언급된다. AI 반도체를 만드는 과정 자체가 AI에 의해 점점 자동화될 가능성이 있다.

교정 전사 (한국어)

전체 전사 펼치기

노정석은 오늘 주제가 AI 인프라의 아래쪽, 즉 데이터센터·칩·메모리·추론 시스템에서 실제로 어떤 일이 일어나는지 이해하는 것이라고 소개한다. 모델 발전이 빨라지면서 가치 포착(value capture)은 인프라와 애플리케이션 양쪽으로 이동하고 있으며, 이번 편은 그중 inference engineering의 핵심을 다룬다.

이진원 CTO는 Sam Altman의 compute crunch 발언을 인용하며, 앞으로도 compute 부족은 계속될 가능성이 크다고 설명한다. Google의 토큰 사용량은 12개월 만에 50배, 14개월 만에 100배, 이후 2024년 대비 약 330배까지 증가했다. 데이터센터 투자는 폭발적으로 늘고 있지만 전력 공급이 병목이며, frontier lab은 매출 증가 속도에 비해 compute 증가 속도가 느려 inference 단가 상승 압력을 받고 있다.

HyperAccel의 Bertha 칩은 HBM 대신 LPDDR을 사용하는 저전력·저비용 AI 반도체다. Samsung 4nm 공정으로 제작됐고, 메모리 대역폭은 약 546GB/s, 목표 가격은 약 5,000달러, 메모리 용량은 칩당 192GB다. H100보다 이론 대역폭은 낮지만, 내부 아키텍처로 대역폭 활용률 90% 이상을 목표로 한다. LPU라는 이름은 NPU 계열의 제품명에 가깝고, PCIe 카드 형태로 단독 사용이 가능하다고 설명한다.

이어 LLM inference는 prefill과 decode로 나뉜다고 설명한다. 사용자의 prompt 전체를 한 번에 처리해 첫 token을 만드는 과정이 prefill이고, 이후 한 token씩 autoregressive하게 다음 token을 만드는 과정이 decode다. 첫 token까지의 시간은 TTFT(Time To First Token), token 사이 시간은 TBT(Time Between Tokens) 또는 TPOT(Time Per Output Token)라고 부른다.

Transformer 내부에는 attention과 FFN(Feed-Forward Network)이 있다. Attention은 Query, Key, Value를 만들어 token 간 관계를 계산하고, FFN은 token embedding vector 내부 차원들을 변환한다. Dense model 기준 parameter는 attention보다 FFN에 훨씬 많이 들어가며, MoE(Mixture of Experts) 모델에서는 이 경향이 더 커진다.

Decode에서는 이전 token들의 Key와 Value가 필요하다. 이를 매번 다시 계산하지 않고 메모리에 저장해 두는 것이 KV 캐시(KV cache)다. Llama 3.1 70B 기준 token 하나당 KV 캐시는 약 320KB이고, 128K context는 약 40GB가 필요하다. H100 80GB 메모리의 절반이 한 사용자의 KV 캐시에 쓰일 수 있다는 뜻이다.

KV 캐시를 줄이기 위해 quantization, GQA(Grouped Query Attention), MQA(Multi-Query Attention), MLA(Multi-head Latent Attention), sliding-window attention, CPU DRAM·SSD로의 offloading 같은 기법이 사용된다. 특히 agentic AI에서는 KV 캐시가 이전 reasoning model보다 훨씬 많이 생성되므로, 전부 HBM에 유지하기 어렵다.

성능 병목을 이해하기 위해 이진원 CTO는 arithmetic intensity를 설명한다. 이는 메모리에서 데이터를 한 번 읽고 얼마나 많은 연산을 수행하는지를 뜻한다. Prefill은 여러 token에 같은 weight를 재사용하므로 arithmetic intensity가 높고, decode는 token 하나씩 처리하므로 낮다.

Roofline analysis는 하드웨어의 최대 연산 성능과 메모리 대역폭을 기준으로 workload가 compute-bound인지 memory-bound인지 보여준다. H100은 BF16 기준 약 1PFLOP/s와 3.35TB/s 대역폭을 가지며 ridge point는 약 300 근처다. Prefill은 대체로 compute-bound이고, decode는 memory-bound가 된다.

Decode 효율을 올리려면 batch size를 늘릴 수 있다. 여러 사용자의 token을 모으면 weight 재사용이 늘어나 arithmetic intensity가 올라간다. 하지만 attention에서는 사용자별 KV 캐시가 다르기 때문에 batch를 늘려도 효과가 제한적이다. 이 때문에 GQA, MQA, MLA, prefix caching, KV quantization이 중요해진다.

AI 서비스 성능은 interactivity와 throughput의 trade-off로 봐야 한다. Interactivity는 사용자 한 명이 초당 받는 token 수이고, throughput은 서버 전체가 초당 생성하는 token 수다. Batch를 키우면 throughput은 올라가지만 사용자 개별 속도는 느려질 수 있다. SemiAnalysis의 InferenceX Pareto curve는 이 관계를 보여 주며, 사업자는 요구 SLO에 맞춰 어떤 GPU와 software stack이 수익성이 좋은지 판단할 수 있다.

실제 serving framework로는 vLLM과 SGLang이 언급된다. Static batching은 batch 내 가장 긴 request가 끝날 때까지 다음 request를 못 받아 낭비가 생긴다. Continuous batching은 token generation iteration마다 scheduling을 새로 해 빈 slot을 줄인다.

PagedAttention은 KV 캐시를 운영체제의 page table처럼 block 단위로 동적 할당하는 기술이다. 출력 길이를 미리 알 수 없기 때문에 worst case 기준으로 메모리를 잡으면 낭비가 크다. PagedAttention은 필요한 만큼만 physical block을 연결해 더 많은 사용자를 serving할 수 있게 한다.

Chunked prefill은 긴 prefill 요청을 작은 조각으로 나누어 decode 지연을 줄이는 방식이다. 일반적으로 decode를 우선 처리하고, 남은 자리에 prefill chunk를 태운다. 이는 TTFT를 약간 희생하더라도 TBT를 안정화하는 데 유리하다.

Speculative decoding은 작은 draft model이 여러 token을 빠르게 예측하고, 큰 target model이 이를 한꺼번에 검증하는 방식이다. Decode를 큰 모델로 한 token씩 처리하는 대신, 후보 token들을 prefill처럼 병렬 검증해 속도를 높인다. Meta의 self-speculative 방식, DeepSeek의 DSpark, EAGLE-3 같은 기법이 언급된다.

Prefill과 decode의 성격 차이가 크기 때문에 PD disaggregation이 등장한다. Prefill 전용 pool과 decode 전용 pool을 나누고, prefill에서 생성한 KV를 decode pool로 전송한다. 네트워크 대역폭이 중요하며, 대규모 cluster와 엄격한 SLO 환경에서 goodput을 높이는 데 효과적이다.

Agentic AI에서는 session, request, step 개념이 중요하다. 평균 session은 62.6분, session당 request는 9.2개, request당 step은 약 9개로 분석됐다. LLM call의 90%는 사람이 아니라 agent loop 안에서 발생한다. 사람은 결과를 검토하거나 다른 일을 하느라 전체 session 시간의 약 92%를 차지하고, LLM과 tool 실행은 약 8%에 불과하다.

이 때문에 KV 캐시를 HBM에 계속 유지하는 것이 큰 비용 문제가 된다. request 사이 median 대기 시간은 약 25분이고, median KV 캐시 점유량은 약 40GB다. 시스템은 5~10분 정도를 골든타임으로 보고, 이후 사용자가 곧 돌아올지 가벼운 ML 모델로 예측해 KV 캐시를 evict할지 결정한다.

KV 캐시를 완전히 버리고 나중에 재계산할 수도 있지만, 대부분은 CPU DRAM, SSD, flash 등으로 옮겼다가 다시 읽는 편이 낫다. 재계산은 비용과 시간이 크기 때문이다. 앞으로는 SRAM, HBM, DDR, SSD, high-bandwidth flash를 계층적으로 활용하는 KV cache scheduling이 핵심이 된다.

마지막으로 AI 반도체의 미래는 heterogeneous computing으로 갈 가능성이 크다고 설명한다. GPU가 모든 일을 처리하기보다, LPU, NPU, CPU, memory system, storage accelerator가 각자 잘하는 부분을 맡는다. Groq LPU는 낮은 arithmetic intensity 영역과 FFN 일부에 강점이 있을 수 있고, NVIDIA Vera Rubin 계열에서도 이런 조합이 논의된다.

반도체 설계 자체도 AI의 영향을 받는다. RTL, Verilog, CUDA kernel, verification 등은 검증 가능한 부분이 많아 AI가 빠르게 도입될 수 있다. 칩 설계, 검증, 배치, 배선까지 모두 AI가 도와주는 방향으로 발전할 가능성이 있다.

노정석은 이제 AI 산업이 단순히 “새 모델이 나왔다”는 수준을 넘어, 어떻게 inference cloud를 수익성 있게 만들 것인가의 산업화 단계로 들어섰다고 정리한다. 이진원 CTO는 inference engineering의 핵심 병목과 최적화 방법을 설명하며, 앞으로 AI 인프라와 AI 반도체 경쟁이 더 빠르게 전개될 것이라고 마무리한다.
