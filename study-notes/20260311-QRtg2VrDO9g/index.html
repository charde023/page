화자의 디테일 (놓치기 쉬운 포인트)

  1. Vercel 폴링 주기는 정확히 45초. 빌드 실패 시 자동으로 수정 재시도.
  2. 스킬 실행 중 사람이 개입해야 하는 유일한 지점은 "리서치 방향이 맞는지" 확인하는 한 번뿐. 나머지는 완전 무인.
  3. Auto Commit = false(펄스)로 설정하면 스킬이 커밋 직전에 대기 → 사람이 코드 확인 후 "계속해" 명령으로 재개. 프로덕션 배포 전 마지막 안전장치.
  4. 리뷰 단계에서 한 에이전트가 "뷰 영수증 다이얼로그를 닫을 때 이전 데이터를 정리하지 않는 문제" 를 추가로 발견 — 원래 티켓에 없던 결함을 멀티 에이전트가 잡아냄.
  5. 데모 버그의 근본 원인: 영수증 페이지로 navigate 하는 대신 ID로 영수증을 fetch해 다이얼로그로 열었어야 했음 — 페이지 이동 없이 같은 페이지에서 모달 처리.
  6. 스킬은 Jira 티켓의 댓글까지 읽음 (이 데모에서 댓글 2개 파싱).
  7. 멀티 에이전트 리뷰 팀 구성: 3개 에이전트 (각각 다른 관점) + PR 리뷰 전용 5개 에이전트 (Devils Advocate) — 용도가 다름.
  8. startup-claude-skills 리포 내부에 개발팀(계획·리뷰·구현·PR 생성)·리뷰팀·리뷰픽스(병렬 에이전트)·Playwright 스킬 등이 모두 포함된 패키지.
  9. Jira 프리픽스(KAN)를 본인 프로젝트에 맞게 교체하면 즉시 커스터마이징 가능.
  10. 이 스킬이 자동화하는 업무 목록: 티켓 읽기 → 버그 재현 → 리서치 → 분석·계획 → 구현 → 빌드·린팅 → 코드 리뷰 → QA 검증 → 커밋·푸시 → 배포 모니터 → Jira 핸드오프 — 주니어 엔지니어 업무의 90% 해당.

1. Fix Ticket 스킬 개요

화자가 만든 Fix Ticket 스킬은 Claude Code의 에이전트팀 기능을 활용해 버그 수정 파이프라인 전체를 자동화한다.

파이프라인 흐름: 1. 브랜치 전략 결정 (메인 / 피처 브랜치 / 격리 워크트리) 2. Jira 티켓 + 댓글 읽기 → 요약 3. Playwright 스킬로 실제 앱에서 버그 재현 4. 리서치 에이전트팀 → 근본 원인 분석·계획 5. 구현 → 빌드·린트 자동 실행 6. 멀티 에이전트 코드 리뷰 (3개 에이전트) 7. Playwright 스킬로 수정 검증 8. 자동 커밋·푸시 → Vercel 배포 모니터 → Jira 핸드오프

화자 주장: "이것을 사용하면 주니어 엔지니어 업무의 90%를 대체할 수 있다. 주니어가 하는 일이 바로 이거다 — 티켓 가져오고 읽고 리서치하고 분석하고 리뷰하고 구현하는 것."

2. 파라미터 설계

스킬 호출 시 다음 파라미터로 워크플로우를 제어한다:

파라미터 설명 기본값
티켓 번호 처리할 Jira 티켓 ID 필수
브랜치 전략 main / 피처 브랜치 / 격리 워크트리 실행 시 선택
auto_commit 자동 커밋 여부 false 권장 (수동 확인)
skip_review 코드 리뷰 단계 스킵 false
skip_vercel Vercel 배포 모니터 스킵 false
skip_qa QA 검증 단계 스킵 false
assignee 완료 후 Jira 티켓 담당자 선택

3. 데모 — KAN-191 버그 수정

버그 내용: 매칭 트랜잭션 페이지의 "뷰" 버튼 클릭 시 영수증 상세 다이얼로그가 열려야 하는데 일반 영수증 페이지로 이동(리다이렉트)되는 문제.

근본 원인: navigate 방식으로 영수증 페이지로 이동하도록 구현 → ID로 영수증 fetch 후 다이얼로그를 현재 페이지에서 열어야 했음.

멀티 에이전트 리뷰에서 추가 발견된 결함: 영수증 다이얼로그를 닫을 때 이전 데이터(stale data)를 정리하지 않는 문제 → 리뷰 단계에서 수정.

수정 검증: Playwright 스킬이 로그인 → 트랜잭션 페이지 이동 → 영수증 클릭을 자동 실행 → 다이얼로그가 리다이렉트 없이 현재 페이지에서 열리는 것 확인.

Vercel 배포: 45초 주기 폴링으로 빌드 성공 확인 → 복지로 AI(Welfarely AI)에 완전 배포.

전체 전사 펼치기

이 영상에서는 제가 만든 에이전트팀 스킬인 Fix Ticket 스킬을 보여드리겠습니다. 목표는 애플리케이션의 버그 수정 파이프라인을 자동화하는 것입니다.

제 애플리케이션을 예로 들면, 현재 Jira의 '백로그 버그' 컬럼이 있는데, QA 엔지니어가 발견한 모든 버그를 이 Jira 보드에 등록합니다. 제가 만든 Fix Ticket 스킬을 사용해 버그 수정 파이프라인을 자동화합니다. 버그가 있을 때마다 티켓을 읽기 시작하고, 지난 영상에서 만든 Playwright 스킬을 사용해 버그가 실제로 존재하는지 확인합니다. 버그가 존재하면 리서치를 하고 구현을 시도한 다음 멀티 에이전트팀을 실행해 리뷰를 진행하고 최고의 정확도를 보장합니다. 그리고 최종적으로 Playwright 스킬을 다시 실행해 수정 사항이 실제로 제대로 고쳐졌는지 확인합니다. 스킬이 모두 완료되면 커밋하고 GitHub에 푸시하고 Vercel에서 배포를 모니터링하고, 최종적으로 그 티켓을 Jira 보드에서 완료 또는 QA 상태로 이동시킬 수 있습니다.

이 스킬 덕분에 아무것도 건드리지 않고도 버그에서 완료까지 갈 수 있습니다.

들어가기 전에 간단히 소개하겠습니다. 저는 Eric이고, Amazon·AWS·Microsoft 같은 회사에서 시니어 소프트웨어 엔지니어로 수년간 일했습니다. AI와 코딩부터 자동화, 커리어 개발 등 제가 배운 모든 것을 실용적인 튜토리얼로 공유하기 위해 이 채널을 시작했습니다. Skool 커뮤니티도 있어서 모든 리소스·템플릿과 커뮤니티 지원을 받으실 수 있습니다.

[데모 시작]

여기 제 Jira 보드가 있고 이 프로젝트에서 작업하는 모든 태스크를 추적합니다. '백로그 버그' 컬럼에 있는 티켓 KAN-191을 사용합니다. 이 티켓 번호와 실제 설명이 있습니다.

스킬에서 사용할 수 있는 파라미터를 보면: 어떤 브랜치에서 작업할 것인지(메인·피처 브랜치·격리 워크트리), 리뷰 과정이나 Jira 프로세스 단계를 건너뛸 수도 있고, Vercel 배포 과정도, QA 검증 단계도 건너뛸 수 있습니다. Auto Commit 기능도 있어서 수정 완료 후 자동으로 커밋할지 선택할 수 있습니다. 마지막으로 티켓 완료 후 다른 사람에게 할당할 수도 있습니다(예: QA 엔지니어).
