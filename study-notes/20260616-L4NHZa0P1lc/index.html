어드버서리얼 루프 셀프체크의 한계 극복 만드는 모델과 검증하는 모델을 분리(builder vs verifier)

내가 모를 만한 것 / 처음 보는 것

  • 루프 엔지니어링 (loop engineering): 새 유행어처럼 보이지만 핵심은 "프롬프트를 직접 쓰지 말고, 프롬프트를 대신 만들어 에이전트를 굴리는 시스템을 설계하라". 상시 실행 에이전트와 결합될 때 진짜 의미가 생김. (재사용 → 루프 엔지니어링 용어노트 후보)
  • Hermes 에이전트: AI Labs가 미는 상시 실행(always running) 에이전트. 셀프-에볼빙 스킬(self-evolving skills) 기능이 핵심. (차드 환경의 mason Hermes/차미와 같은 계열 개념)
  • 셀프-에볼빙 스킬 (self-evolving skills): 워크플로를 돌리며 스킬을 자동 생성·진화시키는 Hermes 기능. AI slop이 또 발견되면 스킬이 스스로 그 피드백을 반영해 갱신.
  • 결정론적 / 비결정론적 루프 (deterministic / non-deterministic loop): 완료 판정이 객관적으로 가능한가로 나뉨. 테스트 통과=결정론적, UI 품질=비결정론적.
  • 어드버서리얼 루프 (adversarial loop): 빌더와 검증자를 다른 모델로 두고 서로의 작업을 검사. 영상에선 Claude 모델=빌더, GPT 모델=코드 리뷰 검증자.
  • Claude Code 비대화형 모드 (non-interactive mode): 사람이 개입하지 않고 헤드리스로 도는 모드. Hermes가 이걸 띄워 테스트 통과까지 루프.
  • Ralph 루프 (Ralph loop): 초창기 오픈소스 자율 루프. hook(특정 이벤트에 자동 실행되는 스크립트)으로 조건 미충족 시 "완료" 마킹을 강제 차단. (차드의 loop-md 스킬이 이 계열)
  • Claude의 goal 커맨드: Ralph의 hook이 경직된 문제를 해결. 하드코딩 체크 대신 또 다른 모델이 완료 여부를 판단(유연).
  • GoalBuddy2 [?GoalBuddy2]: 위에서 발전 — 에이전트가 로컬 파일로 진행 상황을 추적하고 "done의 정의"를 사전에 명시.
  • OpenClaw [?OpenClaw]: Hermes와 같은 철학(사람을 완전히 빼고 에이전트가 다 처리)의 오픈소스 시스템. 그 창작자가 "더 이상 코딩 에이전트에 프롬프트하지 말라"고 처음 주장.
  • AI Slop Detector: AI 특유의 뻔한 UI 패턴(AI slop)을 피하는 지침·패턴 목록을 담은 스킬. 비결정론적 루프의 검증자 역할.
  • Scrimba: 영상 스폰서(파이썬 강의 플랫폼) — 학습 내용 아님, 스킵.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 두 거장 인용: OpenClaw 창작자 "코딩 에이전트에 더는 프롬프트하지 말고, 에이전트를 대신 프롬프트하는 루프를 설계하라". 보리스 체르니(Claude Code 창작자) 도 Anthropic 연례 개발자 컨퍼런스에서 같은 주장 — "나는 더 이상 Claude에 프롬프트하지 않는다. 루프가 Claude를 프롬프트하고 스스로 할 일을 알아낸다."
  2. "You were the loop": 예전엔 사람이 프롬프트→모니터링→출력 확인→이슈 발견→재프롬프트를 했다. 사람이 곧 루프의 에러체크·코스교정 부분이었다. 루프 엔지니어링은 이걸 사람 손에서 떼어낸다.
  3. 크론잡(cron job)도 루프의 일종 — 정해진 시간에 자동 반복. 유일한 차이는 고정 시간에 돈다는 것.
  4. 강화학습(RL)과의 유비: 정답을 보여주지 않고 잘했을 때/못했을 때만 신호를 줘서 스스로 길을 찾게 함. 단, 여기선 모델이 학습되는 게 아니라 에이전트가 작업 완료를 향해 반복 개선.
  5. "네 역할은 줄지 않고 더 중요해진다" — 결국 end goal을 정의하는 건 너의 도메인 지식과 경험. 그게 만들고 출시하는 모든 것에 드러남.
  6. 모델 발전이 루프를 가능하게 했다. Opus 4.5부터 장기 실행 작업이 극적으로 좋아짐 — 더 이상 정교하게 가이드된 하네스 없이도, 단계를 안내하는 구조화된 셋업만 있으면 됨. 초점이 "단계별 핸들링"에서 "프로젝트를 장기 실행 가능하게 준비"로 이동.
  7. Fable 5 사례: Anthropic이 AI 개발 속도조절을 외치면서도 출시 — 모델이 따라잡기 힘든 속도로 강해져서. 출시 후 잠시 내리기도 함(pulled). 길고 복잡한 작업용으로 만들어졌고, 작업이 길고 복잡할수록 더 잘함 (과거 모델과 정반대).
  8. 루프의 6요소 (각각 특정 문제 해결): ① 컨텍스트 관리(100만 토큰이어도 대화가 길면 시스템 프롬프트가 최근 도구 출력에 묻힘, 어텐션이 최신으로 쏠림) ② 피드백 품질(테스트 출력·UI 스크린샷 등, 에이전트의 다음 수를 결정) ③ 검증 게이트(피드백을 명확한 판정으로) ④ 종료 조건(명시 안 하면 너무 일찍 끝내거나 무한 진행) ⑤ 에러 처리(도구 호출 실패 시 행동을 명시 — 가장 자주 빠뜨림) ⑥ 턴 간 상태 관리(파일로 진행 추적, 맥락 손실 방지).
  9. 루프는 토큰을 많이 먹는다 — 경로 탐색을 모델에 넘기므로 비쌈. 언제 쓸지 신중히. 루프가 다룰 수 있는 토큰이 많을수록 작업을 더 잘 처리하는 경향.
  10. 결정론적 루프 데모 (Hermes): end goal = 너의 테스트. 배포한 앱+테스트케이스에 Hermes를 겨눠 모니터링. 프로덕션이 깨지면 자동화로 포착 → Claude Code를 비대화형 모드로 띄워 모든 테스트 통과까지 자동 수정 → GitHub CLI로 커밋. 로드하는 스킬: sub-agent driven development 스킬, GitHub PR workflow 스킬.
  11. 비결정론적 루프 데모 (Hermes): AI Slop Detector 스킬로 UI의 AI slop 패턴 검사 → 있으면 Claude Code 비대화형으로 고칠 게 없을 때까지 수정. 어드버서리얼 루프 = 빌더와 검증자를 다른 모델로. 영상에선 Claude 모델=빌더, GPT 모델(코드 리뷰 강점)=검증자. 결과 UI가 "요즘 Opus 모델이 내놓는 제네릭 출력"보다 훨씬 나았다.
  12. 셀프-에볼빙 스킬의 진가: 루프 후에도 AI slop이 남으면 언급만 하면 스킬이 스스로 갱신 → 검증자가 강화됨. AI Labs Pro 커뮤니티에서 스킬 배포.

1. 루프 엔지니어링이란

핵심은 단순하다 — 에이전트를 굴리는 프롬프트를 쓰는 사람이기를 멈추고, 에이전트가 스스로를 굴리게 하라. 예전에 중요했던 스킬은 프롬프트 엔지니어링(코딩 에이전트를 제대로 굴릴 올바른 지시 시퀀스 작성)이었다. 루프 엔지니어링은 이를 뒤집는다 — 프롬프트를 직접 쓰는 대신, 프롬프트 엔지니어링을 대신 해주고 에이전트를 스스로 굴리는 시스템을 설계한다. 초점이 "지시 작성"에서 "스스로 도는 시스템 설계"로 이동.

2. 프롬프트 vs 루프 엔지니어링

OpenClaw 창작자가 시작점: "코딩 에이전트에 더는 프롬프트하지 말고, 대신 프롬프트해주는 루프를 설계하라." 그만이 아니다 — Claude Code 창작자 보리스 체르니 도 Anthropic 연례 개발자 컨퍼런스에서 "나는 더 이상 Claude에 프롬프트하지 않는다. 루프가 Claude를 프롬프트하고, Claude가 무엇을 할지 스스로 알아낸다"고 했다.

관건은 프롬프트를 전혀 걱정하지 않아도 되는 시스템을 얼마나 잘 세우느냐. 너는 필요한 것을 정의하고, 에이전트가 나머지를 한다.

3. 루프란 무엇인가

루프 = end goal을 정의하면 에이전트가 거기 도달할 단계를 스스로 알아내는 프로세스. 도중에 자기교정하고 문제를 우회하며 목표에 도달한다.

몇 달 전, 모델이 긴 작업을 지탱할 만큼 강하지 않았을 때는 불가능했다. 앱을 만들려면 프롬프트→모니터링→출력 확인→이슈 발견→수정 재프롬프트. 네가 곧 루프였다 — 매 단계 사이의 에러체크·코스교정을 네가 했다.

크론잡도 이미 본 루프의 예다(고정 시간 자동 반복). RL과도 닮았다 — 정답 대신 잘함/못함 신호만 주고 스스로 길을 찾게 함. 단 여기선 모델이 학습되는 게 아니라 에이전트가 작업 완료를 향해 반복 개선한다. 실패하면 루프가 "완료"로 마킹하지 않고 목표 도달까지 다시 시도한다.

4. 그럼 네 역할은?

모든 게 자율화되면 할 일이 없어 보이지만, 역할은 줄지 않고 더 중요해진다. end goal을 정의하는 건 결국 너의 도메인 지식과 경험이고, 그게 만들고 출시하는 모든 것에 드러난다.

5. 모델 발전이 루프를 열었다

자율 루프로의 흐름은 가속 중이고 신규 기능마다 드러난다. Fable 5 가 가장 명확한 예 — Anthropic이 속도조절을 외치면서도 출시했고(이후 잠시 pulled), 길고 복잡한 작업용이라 길고 복잡할수록 더 잘한다(과거와 정반대).

전환은 Opus 4.5 에서 본격화됐다. 장기 실행 작업이 극적으로 좋아져, 정교하게 가이드된 하네스로 끙끙댈 필요가 사라졌다. 단계를 안내하는 구조화된 셋업만 있으면 됐다. 초점이 "단계별 핸들링"에서 "프로젝트를 장기 실행 가능하게 준비"로 옮겨갔다. 하지만 루프만 중요한 게 아니다 — 에이전트가 오래 혼자 일하도록 프로젝트를 구조화해야 한다.

Hermes / OpenClaw 사람을 완전히 빼고 에이전트가 다 처리하는 철학

7. 5단계 시스템 + 잘 도는 6요소

5단계 (먼저 Claude Code 기준, 뒤에 Hermes): 1. 프로젝트가 어떤 상태인지 확인 2. 모델이 다음 행동을 결정 3. 그 결정대로 행동 (도구 호출·파일 쓰기·명령 실행 — 실제 작업) 4. 무슨 일이 일어났는지 피드백 수집 5. 그걸 근거로 작업이 done인지 판정

프롬프트 엔지니어링은 ②(결정) 한 단계만 통제. 루프 엔지니어링은 5단계를 모두 다룬다.

6요소 (각각 특정 문제 해결):

요소 해결하는 문제
컨텍스트 관리 대화가 길면 시스템 프롬프트가 최근 도구 출력에 묻힘. 어텐션이 최신으로 쏠림 (100만 토큰이어도)
피드백 품질 에이전트가 다음 수를 정하는 핵심 신호 (테스트 출력·UI 스크린샷 등)
검증 게이트 피드백을 "done/not done"의 명확한 판정으로 전환
종료 조건 명시 안 하면 너무 일찍 끝내거나 진척 없이 계속 돔
에러 처리 도구 호출 실패 시 행동 명시 — 가장 자주 빠뜨림. 깨진 상태 방치 방지
턴 간 상태 관리 파일로 진행 추적, 컨텍스트 한계에도 맥락 유지

주의: 경로 탐색을 모델에 넘기므로 루프는 토큰이 비싸다. 언제 쓸지 신중히. 다룰 토큰이 많을수록 더 잘 처리하는 경향.

8. 결정론적 루프 (Hermes)

"done"이 명확한 작업용 — 테스트 통과, 컴파일 성공 등. 기준이 분명해 모델이 정확히 무엇을 해야 할지 안다.

Hermes는 상시 실행이라 이 루프에 적합. end goal = 너의 테스트. 배포한 앱+테스트케이스에 Hermes를 겨눠 모니터링하고, 커밋이 프로덕션을 깨면 자동화로 포착. 셀프-에볼빙 스킬이 워크플로 기반으로 스킬을 자동 생성·진화시켜 앱 헬스를 유지.

흐름: 모니터링 자동화 설정 → Claude Code 비대화형 모드 실행 → 모든 테스트 통과까지 혼자 수정. sub-agent driven development 스킬 + GitHub PR workflow 스킬을 로드 → 깨진 이슈 식별 → Claude Code 비대화형으로 테스트 통과 후 커밋 → GitHub CLI로 변경 커밋. 배포 체크가 다 통과됐음을 확인했으므로 앱은 실패 없이 돈다.

9. 비결정론적 루프 (Hermes)

깔끔한 완료 규칙을 세울 수 없는 작업 — UI 빌드, 판단이 필요한 기능. 사람이 보고 판단하는 종류.

AI를 UI에 적용하면 늘 같은 패턴(AI slop)으로 회귀하는 걸 안다. 그래서 AI Slop Detector 스킬 — slop을 피하는 지침과 드러나는 패턴 목록. Hermes를 다시 쓰는 이유는 셀프-에볼빙 스킬: 스킬 실행 후에도 slop이 남으면 스킬이 그 피드백을 직접 반영해 갱신.

Hermes에 스킬로 UI 패턴 검사 요청 → 있으면 Claude Code 비대화형으로 고칠 게 없을 때까지 수정.

핵심 — 어드버서리얼 루프: 작업을 리뷰하는 모델을 만드는 모델과 다르게. 코드 리뷰에 강한 GPT 모델을 검증자로, Claude 모델을 빌더로. 둘이 서로의 작업을 검사한다. 이 루프 후 결과 UI가 요즘 Opus 모델의 제네릭 출력보다 훨씬 나았다. 이후에도 slop이 보이면 언급만 하면 스킬이 갱신되어 검증자가 강화됨.

교정 전사 (한국어)

전체 전사 펼치기

요즘 도는 새 용어가 있습니다 — 루프 엔지니어링(loop engineering). 다른 모든 유행어처럼 다들 뭔가 새로운 것처럼 말하지만, 새롭지 않습니다. 하지만 Hermes 같은 상시 실행 에이전트와 결합되면 더 이상 hype가 아니게 됩니다. 이걸 세팅하려는 대부분은 루프는 맞게 짜면서 정작 작동하게 만드는 핵심을 놓칩니다. 루프에 두 종류가 있다는 걸 안다면, 그중 하나에는 거의 아무도 안 하는 특정 셋업이 있습니다. 이걸 보고 나면 에이전트로 만드는 사고방식이 완전히 바뀝니다. 영상 끝엔 그게 뭔지 정확히 이해하고, Hermes와 Claude Code [?Cloud Code]에서 네 개입 없이 돌아가게 만들 수 있습니다.

핵심 아이디어는 단순합니다 — 에이전트를 굴리는 프롬프트를 쓰는 사람이기를 멈추고, 에이전트가 스스로를 굴리게 하세요. 예전에 중요했던 스킬은 프롬프트 엔지니어링 — 코딩 에이전트를 제대로 굴릴 올바른 지시 시퀀스 작성에 모든 초점이 갔습니다. 루프 엔지니어링은 이를 뒤집습니다. 프롬프트를 직접 쓰는 대신, 프롬프트 엔지니어링을 대신 해주고 에이전트를 스스로 굴리는 시스템을 설계합니다. 초점이 지시 작성에서, 스스로 도는 시스템 설계로 옮겨갑니다.

이 모든 건 OpenClaw [?OpenClaw] 창작자가 "이제 코딩 에이전트에 프롬프트하지 말고, 대신 에이전트를 프롬프트해주는 루프를 설계하라"고 말하면서 시작됐습니다. 그만이 아닙니다. Claude Code 창작자 보리스(체르니) 도 Anthropic [?Anthropix] 연례 개발자 컨퍼런스에서 같은 주장을 했습니다 — "나는 더 이상 Claude에 프롬프트하지 않는다. 루프가 Claude를 프롬프트하고, Claude가 무엇을 해야 할지 스스로 알아낸다." 그래서 질문은, 어떻게 시작하느냐입니다. 전부 프롬프트를 전혀 걱정하지 않아도 되는 시스템을 얼마나 잘 세우느냐로 귀결됩니다. 네가 필요한 것을 정의하면 에이전트가 나머지를 합니다. 그게 바로 AI 기반 개발이 향하는 곳입니다.

만드는 법에 들어가기 전에, 루프가 뭔지 분명히 해야 합니다. 루프는 기본적으로 end goal을 정의하면 에이전트가 거기 도달할 단계를 스스로 알아내는 프로세스입니다. 도중에 자기교정하고 문제를 우회하며 네가 정한 목표에 도달합니다. 몇 달 전, 모델이 긴 작업을 지탱할 만큼 강해지기 전엔 불가능했습니다. 앱을 만들려면 에이전트에 프롬프트하고, 뭘 하는지 모니터링하고, 출력을 직접 확인하고, 이슈를 찾아 고치라고 재프롬프트했죠. 네가 곧 루프였습니다. 매 단계 사이의 에러체크와 코스교정을 네가 했습니다. 대부분에게 개발은 여전히 이렇게 보이고, 루프 엔지니어링이 바로 그걸 네 손에서 떼어내려 합니다.

새 개념처럼 들리지만 루프는 한동안 있었습니다. 크론잡(cron job) 이 좋은 예입니다 — 매번 트리거하지 않아도 자동으로 반복 실행되는 작업. 유일한 차이는 크론잡이 고정 시간에 돈다는 것입니다. 루프가 자리 잡으면, 일은 더 이상 프롬프트 작성이 아닙니다. 작업에 대한 에이전트 성능은 end goal을 얼마나 잘 정의하느냐로 결정됩니다.

어떤 분께는 이게 강화학습(reinforcement learning) 처럼 들릴 겁니다. 강화학습은 정답을 보여주지 않고, 잘했을 때와 못했을 때만 알려줘서 스스로 더 나아지게 훈련하는 방식입니다. 모델이 여러 시도를 하며 옳은 방향엔 긍정 신호, 아니면 부정 신호를 받습니다. 같은 아이디어가 여기 적용되지만, 모델 자체가 훈련되는 게 아닙니다. 에이전트가 네가 원하는 작업 완료를 향해, 훈련 중 모델이 개선되듯 반복합니다. 실패하면 에이전트에 씌운 루프가 작업을 "완료"로 마킹하지 않습니다. 다시 시도하고, 계속 가고, 목표 도달까지 자기교정합니다.

이 얘길 듣고 나면, 다 자율화되면 네가 할 일이 뭐가 남나 싶을 겁니다. 하지만 역할은 줄지 않고 더 중요해집니다. 애초에 end goal을 정의하는 건 너의 도메인 지식과 경험이고, 그게 만들고 출시하는 모든 것에 드러나기 때문입니다.

자율 루프로의 추진이 가속되는 이유가 이것이고, 지금 나오는 모든 신규 기능에서 드러납니다. Fable 5 가 가장 명확한 예입니다. Anthropic은 AI 개발 속도조절을 외치고 있었음에도 이걸 출시했습니다 — 모델이 따라잡기 힘든 속도로 강해지고 있어서요. 출시 후 얼마 뒤 내리기도 했습니다(pulled). 길고 복잡한 작업용으로 만들어졌고, 작업이 길고 복잡할수록 더 잘합니다 — 과거 모델과 기본적으로 정반대죠. 이 전환은 Opus 4.5 에서 본격 시작됐습니다. 그게 나온 뒤 장기 실행 작업이 극적으로 좋아졌습니다. 더 이상 정교하게 가이드된 하네스로 에이전트를 세팅하며 끙끙댈 필요가 없어졌습니다. 각 단계를 안내하는 구조화된 셋업만 있으면 됐습니다. 초점은 대신 프로젝트를 장기 실행 가능하게 준비하는 쪽으로 옮겨갔습니다 — 모델이 이제 단계별 핸들링 없이도 스스로 처리할 만큼 강하니까요.

하지만 루프만 중요한 게 아닙니다. 에이전트가 네 개입 없이 오랫동안 혼자 일하도록 프로젝트를 구조화해야 합니다. 그래서 많은 사람이 이런 셋업을 위한 시스템을 만들고 오픈소스화해 왔습니다. Ralph 루프가 최초 중 하나였습니다. end goal을 정하고 에이전트가 거기서 벗어나지 못하게 하는 방식 — hook(특정 일이 일어나면 자동 실행되는 스크립트)으로, 조건을 실제로 충족하지 않으면 작업을 "완료"로 마킹하지 못하게 엄격히 막았습니다. 하지만 hook은 경직돼 있어서, Claude가 자체 goal 커맨드를 도입했습니다 — 같은 일을 더 유연하게. 하드코딩 체크 대신 또 다른 모델이 작업이 실제로 끝났는지 판단합니다. GoalBuddy2 [?GoalBuddy2] 는 여기서 발전해, 에이전트가 로컬 파일로 진행 상황을 추적하고 끝나기 전에 "done의 모습"을 정확히 정의하게 했습니다. Hermes 에이전트와 OpenClaw 는 둘 다 같은 철학 위에 세워졌습니다 — 너를 완전히 그림에서 빼고 에이전트가 모든 걸 혼자 처리하게 합니다.

이 루프를 만들고 싶다면, 간단한 5단계 시스템이 있습니다. 루프가 두 종류라 일부 단계는 조금 다르게 작동하지만, 두 유형은 뒤에서 다룹니다. 우선 Claude Code에서 시작하고, 뒤에서 Hermes에서 같은 걸 어떻게 하는지 봅니다. 첫째, 프로젝트가 어떤 상태인지 확인. 모델이 다음 행동이 뭐여야 할지 결정. 그 결정대로 행동 — 실제 작업이 일어나는 곳. 에이전트가 도구를 호출하고, 파일에 쓰고, 명령을 실행해 작업을 완수합니다. 끝나면 무슨 일이 실제로 일어났는지 피드백을 수집하고, 그걸 근거로 작업이 done인지 아닌지 결정합니다. 여기서 프롬프트 엔지니어링과 루프 엔지니어링의 차이가 명확해집니다. 프롬프트 엔지니어링은 오직 결정 단계만 통제하지만, 루프 엔지니어링은 다섯 단계를 모두 다룹니다.

잘 도는 루프를 만들려면 몇 가지를 제대로 해야 하고, 각각은 특정 문제 때문에 존재합니다. 첫째, 컨텍스트 관리. 매 턴 컨텍스트에 뭐가 들어가는지 주의해야 합니다 — 그게 그 시점에 에이전트가 실제로 아는 것을 결정하니까요. 100만 토큰처럼 큰 컨텍스트 창이라도 채팅 컨텍스트만 의존할 수 없습니다 — 대화가 커지면 시스템 프롬프트와 지시가 최근 도구 출력 아래 묻히기 때문입니다. 에이전트의 어텐션은 자연히 가장 최근 것으로 쏠립니다. 그래서 컨텍스트 관리가 그토록 중요합니다.

다음은 피드백 품질. 피드백은 에이전트가 어떻게 했는지 알려주는, 시스템 전체에서 가장 중요한 신호 중 하나입니다. 테스트 실행 출력이나 방금 만든 UI 스크린샷 등 여러 형태일 수 있고, 어떤 형태든 그게 에이전트가 다음 수를 정하려 읽는 것입니다. 검증 게이트(verification gates) 는 그 피드백을 명확한 판정으로 바꿉니다 — 작업이 실제로 done인지 알려주는 체크포인트. 종료 조건(termination condition) 도 필요합니다 — 루프가 언제 멈출지 알려주는 규칙. 명시적으로 설정해야 합니다. 안 그러면 너무 일찍 끝내거나, 진짜 진척 없이 계속 갑니다. 사람들이 가장 자주 간과하는 건 에러 처리입니다. 도구 호출이 실패할 때 모델이 뭘 해야 할지 명시해야 시스템이 깔끔하게 처리하고, 더 많은 문제를 만드는 깨진 상태로 두지 않습니다. 마지막으로 턴 간 상태 관리 — 대화가 커져도 작업이 어디 있는지 추적. 컨텍스트 창이 모든 걸 영원히 담을 수 없으니, 에이전트용 정보를 추적하는 파일들을 관리해 맥락을 잃지 않고 계속 일하게 합니다.

한 가지 유념할 점 — 경로를 알아내는 일을 네가 아니라 모델에 넘기므로 루프는 토큰이 비쌉니다. 언제 실제로 쓸지 신중해야 합니다. 루프가 다룰 수 있는 토큰이 많을수록 작업을 더 잘 처리하는 경향이 있습니다.

(스폰서 — Scrimba 파이썬 강의 광고 구간, 학습 내용 아님 생략.)

앞서 말했듯 루프는 두 종류입니다. 첫째는 결정론적 루프(deterministic loop). done의 정의가 명확한 작업에 쓰세요 — 테스트 통과, 코드 컴파일 성공 등. end goal이 분명해 모델이 작업을 done이라 부르기 전 정확히 뭘 해야 할지 알기에 비교적 단순합니다. Hermes는 상시 실행이라 이 루프를 구현하기 정말 좋은 에이전트입니다. 전에 여러 워크플로를 만들었고 이전 영상에서 Hermes가 우리 일 상당수를 혼자 처리하는 걸 보여줬습니다. 결정론적 루프의 핵심은 end goal이 명확하다는 것이고, 호스팅한 앱이라면 그 정의는 너의 테스트입니다. 배포한 앱+테스트케이스에 Hermes를 겨눠 모니터링시킬 수 있습니다. 변경/커밋이 프로덕션을 깨면 Hermes에 자동화를 설정해 잡을 수 있습니다. 여기서 가장 잘 작동하는 이유는 셀프-에볼빙 스킬 기능 — 워크플로 기반으로 스킬을 자동 생성·진화시켜 앱 헬스를 유지합니다. 모니터링 자동화를 세팅하면, Claude Code를 비대화형 모드(non-interactive mode) 로 띄우라고 요청할 수 있고, 네가 굴리지 않아도 스스로 돌며 모든 테스트케이스가 통과할 때까지 루프로 이슈를 고칩니다. 거기서 자동화 워크플로를 세팅하고 sub-agent driven development 스킬과 GitHub PR workflow 스킬을 로드해 GitHub에서 앱을 관리하는 법을 익힙니다. 먼저 프로덕션을 깨던 이슈를 식별하고, Claude Code를 비대화형으로 띄워 테스트를 받아 전부 통과하면 변경을 커밋합니다. 모든 테스트를 돌리고 프로덕션 실패 원인을 고친 뒤 GitHub CLI로 변경을 커밋합니다. 성공 배포에 필요한 모든 체크가 갖춰졌음을 확인했으므로 앱은 실패 없이 돕니다.

둘째는 비결정론적 루프(non-deterministic loop) — 결정론적 루프처럼 done 여부를 깔끔한 규칙으로 확인할 수 없는 작업입니다. 그래서 결과를 검증할 깔끔한 방법이 없습니다. 우리가 인간으로서 직접 보고 판단하는 종류 — UI 빌드나 판단이 필요한 기능 구현 같은 것. 그래서 비결정론적 루프의 워크플로는 다릅니다. AI를 UI에 적용하면 늘 같은 패턴으로 회귀하는 걸 압니다. 그래서 AI Slop Detector 라는 스킬을 만들었습니다 — AI slop을 피하는 모든 지침과 그것을 드러내는 패턴 목록을 담습니다. Hermes를 다시 쓰는 이유는 셀프-에볼빙 스킬입니다. 스킬 실행 후에도 UI에 AI slop이 남으면, 스킬이 그 피드백을 직접 반영해 스스로 갱신할 수 있습니다. 그래서 이 워크플로를 Hermes에 세팅했습니다. Hermes에 스킬을 써서 UI에 그런 패턴이 있는지 확인해 달라고 요청합니다. 있으면 고치고 Claude Code를 비대화형 모드로 띄워, 고칠 게 없을 때까지 찾은 걸 수정합니다.

Hermes에서 얻는 또 다른 이점은 작업을 리뷰하는 모델이 만드는 모델과 다르다는 것입니다. 코드 리뷰에 최고로 꼽히는 GPT 모델을 쓰고 있어서, Claude 모델이 빌더가 되고 다른 에이전트가 검증자가 됩니다. 그게 둘이 서로의 작업을 검사하는 어드버서리얼 루프(adversarial loop) 를 완성합니다. 이 루프를 돌리니 요즘 Opus 모델이 내놓는 제네릭 출력보다 훨씬 나은 UI가 나왔습니다. 그리고 에이전트 루프가 끝난 뒤에도 UI에 AI slop 징후가 보이면 AI Slop Detector로 확인할 수 있습니다. 그냥 언급만 하면 스킬을 갱신해줘서 이미 가진 검증자를 강화합니다. 우리와 Hermes가 함께 식별한 여러 AI slop 패턴에 맞게 이 스킬을 강화했습니다. 이 스킬을 쓰고 싶으면 커뮤니티 AI Labs Pro에서 받을 수 있습니다(링크는 설명란).
