AI 에이전트가 캡차를 인간처럼 뚫는 법 (웹 자동화의 어둠의 기술)

한 줄 요약

AI 에이전트가 브라우저를 사람처럼 다루게 하려면 CLI 기반 재사용 코드, Chrome DevTools Protocol(CDP), 감지-행동-검증 루프, 그리고 점진적으로 인간 행동을 흉내 내는 미트백 사다리(Meatbag Ladder)가 필요하다는 발표다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Chrome DevTools Protocol(CDP) 브라우저 내부에서 실제 사용자 입력과 같은 경로로 클릭·키보드·탐색을 보낼 수 있음 AI 에이전트가 브라우저를 “진짜 사람처럼” 조작하는 핵심 통로
CLI(Command Line Interface) 반복 작업을 코드로 저장하고 재사용할 수 있어 빠르고 저렴함 모델이 매번 판단하게 하지 말고, 되는 경로는 코드로 고정
MCP(Model Context Protocol) 대비 CLI MCP는 매 단계 모델 호출이 들어가 느리고 비쌀 수 있음 발표자는 웹 자동화에는 MCP보다 CLI가 유리하다고 주장
감지-행동-검증(Sense, Act, Verify) 루프 자동화가 실패하는 지점을 찾고 다음 전략으로 올라가기 위한 기본 구조 보고, 한 번 행동하고, 다른 채널로 성공 여부를 확인
미트백 사다리(Meatbag Ladder) 웹페이지의 방어 수준에 맞춰 자동화 방식을 단계적으로 올림 JS 클릭 → CDP 신뢰 클릭 → 인간형 마우스·비전
신뢰 이벤트(Trusted Event) 페이지가 “사람이 한 입력인지” 판별할 때 중요한 신호 단순 자바스크립트 클릭은 차단될 수 있고, CDP 입력은 더 사람 입력에 가까움
결정론적 해결사(Solver)와 AI 운영자(Operator) 분리 빠른 반복은 코드가, 시각 판단은 AI가 맡아야 시간 제한을 통과할 수 있음 AI는 꼭 필요한 “눈과 판단”에만 사용

내가 모를 만한 것 / 처음 보는 것

  • Chrome DevTools Protocol(CDP) — 크롬 개발자도구가 브라우저와 통신할 때 쓰는 프로토콜. 자동화 도구가 브라우저 내부 기능을 직접 제어할 수 있다.
  • MCP(Model Context Protocol) — 모델이 외부 도구와 상호작용하게 해주는 프로토콜. 발표자는 브라우저 자동화에서는 매 단계 모델 호출 때문에 느리고 비싸질 수 있다고 설명한다.
  • CLI(Command Line Interface) — 셸 명령어 기반 도구. 한 번 만든 자동화 절차를 코드처럼 반복 실행하기 좋다.
  • DOM(Document Object Model) — 웹페이지의 HTML 구조를 프로그램이 읽고 조작할 수 있게 표현한 트리.
  • 접근성 트리(Accessibility Tree) — 스크린리더 등 보조기술이 이해할 수 있도록 페이지 의미를 정리한 구조.
  • 신뢰 클릭(Trusted Click) — 브라우저 내부 입력 경로를 통해 발생한 클릭으로, 웹페이지가 실제 사용자 입력처럼 받아들일 수 있는 이벤트.
  • Shadow Root — 웹 컴포넌트 내부 구조를 감추거나 캡슐화하는 기술. 자동화 도구가 요소를 찾기 어렵게 만들 수 있다.
  • Cross-Origin iframe — 다른 출처의 페이지를 현재 페이지 안에 넣는 프레임. 보안 경계 때문에 접근이 까다롭다.
  • Cloudflare Turnstile — Cloudflare의 봇 방지용 체크박스형 검증 도구.
  • reCAPTCHA v2 — 구글의 캡차 시스템. 체크박스와 이미지 그리드 문제를 포함한다.
  • Chrome Agent — 발표자가 만든 CDP 기반 브라우저 자동화 도구. GitHub에 공개되어 있다.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. OpenAI가 발표 준비 과정에서 계정 정지를 경고했다고 언급 — 캡차 자동화가 플랫폼 정책상 민감한 영역임을 보여주는 장치다.
  2. CLI와 MCP의 성공률은 둘 다 약 83%였다고 소개 — 능력 자체보다 재사용성·속도·비용 차이를 강조한다.
  3. 같은 작업에서 MCP는 71회 왕복(round trips), 8분이 걸렸고 CLI는 7턴, 1분 미만이었다고 설명 — 시간 제한이 있는 캡차에서는 이 속도 차이가 결정적이다.
  4. Anthropic 자료를 인용해 CLI가 토큰 비용 측면에서 최대 75배 저렴할 수 있다고 말함 — 모델 호출을 줄이는 것이 비용 최적화의 핵심.
  5. CDP는 당시 기준 57개 도메인(domains)과 수백 개 메서드·이벤트가 있다고 설명 — 전부 알 필요는 없고 필요한 감각만 쓰면 된다는 메시지.
  6. 에이전트의 디지털 감각을 DOM, 접근성 트리, 스크린샷, 네트워크, 콘솔·로그, 입력으로 나눔 — 사람의 시각·청각·손에 해당하는 브라우저 신호다.
  7. Turnstile은 닫힌 Shadow Root, Cross-Origin iframe, 추가 Shadow Root라는 여러 경계 뒤에 있다고 설명 — 단순 요소 선택으로는 접근하기 어렵다는 맥락.
  8. 퍼즐형 캡차는 정답 위치뿐 아니라 마우스 이동 궤적, 속도 변화, 흔들림(jitter), 오버슈트(overshoot)까지 본다고 설명 — “정답”보다 “사람다운 움직임”이 중요하다.
  9. reCAPTCHA v2에서는 코드 기반 해결사(Solver)와 AI 기반 운영자(Operator)를 분리 — 코드는 빠른 반복, AI는 이미지 판단만 수행한다.
  10. 핵심 결론은 캡차 우회 그 자체가 아니라 한 번 해결한 웹 자동화 경로를 코드·스킬로 저장해 재사용하는 엔지니어링 방법론이라고 정리한다.

# 섹션 요지
1 문제 제기 AI 에이전트가 웹을 사람처럼 쓰려 하면 캡차와 봇 방어에 막힌다
2 핵심 전제 CDP 브라우저는 웹사이트 입장에서 마우스를 든 사람과 거의 같은 입력 경로를 쓴다
3 CLI가 필요한 이유 반복 가능한 자동화는 모델 루프보다 CLI 코드가 빠르고 싸다
4 CDP의 디지털 감각 에이전트는 DOM, 접근성, 스크린샷, 네트워크, 콘솔, 입력을 통해 페이지를 감지·조작한다
5 감지-행동-검증 루프 한 번 보고, 한 번 행동하고, 다른 경로로 성공 여부를 확인한다
6 미트백 사다리 JS 클릭, CDP 신뢰 클릭, 인간형 움직임·비전 순서로 필요할 때만 올라간다
7 실제 예시 Outlook, 쇼핑몰 장바구니, Turnstile, 이미지 캡차, 퍼즐 캡차, reCAPTCHA v2를 사례로 설명
8 최종 메시지 AI 자동화의 핵심은 일회성 트릭이 아니라 반복 가능한 엔지니어링 체계다

1. 발표의 출발점: 웹 자동화의 “어둠의 기술”

화자는 이 발표를 “웹 자동화의 어둠의 기술”이라고 부른다. 말 그대로 불법적인 해킹을 가르치겠다는 뜻이라기보다, 웹사이트가 봇을 막기 위해 만든 장벽을 AI 에이전트가 어떻게 통과할 수 있는지 보여주는 발표다.

발표 준비 중 OpenAI로부터 계정 정지 경고를 받았다는 일화를 먼저 꺼낸다. 이는 캡차 자동화가 단순 기술 문제가 아니라 정책·윤리·서비스 약관과 맞닿은 민감한 영역임을 암시한다.

화자의 목표는 명확하다. AI 에이전트가 사람이 하듯 웹을 사용하게 만드는 것이다.

  • 예약하기
  • 이메일 보내기
  • 양식 작성하기
  • 반복적인 웹 업무 대신 처리하기

하지만 사람이 아닌 무언가가 웹페이지를 클릭하기 시작하면, 많은 웹사이트는 이를 봇으로 의심하고 방어한다. 이 발표는 그 “방어와의 싸움”을 브라우저 자동화 관점에서 설명한다.

2. 핵심 전제: CDP 브라우저는 마우스를 든 사람과 비슷하다

화자의 핵심 전제는 다음과 같다.

Chrome DevTools Protocol(CDP)로 제어되는 브라우저는, 웹사이트 입장에서 마우스를 들고 있는 사람과 매우 비슷하게 보일 수 있다.

CDP는 크롬 개발자도구가 브라우저와 통신할 때 사용하는 프로토콜이다. 우리가 F12를 눌러 개발자도구를 열 때 내부적으로 쓰이는 통로라고 보면 된다.

이 통로를 AI 에이전트가 사용할 수 있다면, 에이전트의 클릭과 키 입력은 일반 사용자의 입력과 같은 브라우저 내부 경로를 지나갈 수 있다. 발표자는 이것이 AI 브라우저 자동화의 핵심이라고 본다.

3. 왜 MCP보다 CLI인가

화자는 브라우저 에이전트에게 MCP 서버(Model Context Protocol Server)보다 CLI(Command Line Interface)를 주는 편이 낫다고 주장한다.

이유는 세 가지다.

기준 CLI MCP
재사용성 한 번 명령 시퀀스를 코드로 만들면 반복 실행 가능 매 단계 모델 호출이 개입되기 쉬움
속도 모델 판단 없이 바로 실행 가능 라운드트립이 많아 느려질 수 있음
비용 토큰 사용이 적음 매번 모델을 쓰면 비용 증가

화자는 한 연구를 인용해, 같은 작업에서 CLI와 MCP의 성공률은 둘 다 약 83%였다고 말한다. 즉 “할 수 있느냐”만 보면 큰 차이가 없지만, 실제 운영에서는 속도와 비용이 중요하다.

특히 같은 작업에서 MCP는 71회 왕복과 8분이 걸렸고, CLI는 7턴과 1분 미만이 걸렸다고 설명한다. 나중에 reCAPTCHA처럼 시간 제한이 있는 작업에서는 이 차이가 결정적이다.

4. CDP가 에이전트에게 주는 디지털 감각

CDP의 기능 범위는 매우 넓다. 발표 당시 기준으로 57개 도메인과 수백 개의 메서드·이벤트가 있다고 한다.

하지만 웹을 사람처럼 조작하는 데 모든 기능이 필요한 것은 아니다. 화자는 필요한 기능을 “디지털 감각”으로 이해하라고 말한다.

사람의 감각·행동 에이전트의 브라우저 감각
눈으로 봄 DOM, 접근성 트리, 스크린샷
소리를 들음 네트워크 트래픽, 콘솔, 로그
손으로 조작 클릭, 키 입력, 페이지 이동

즉 에이전트는 페이지 구조를 읽고, 화면 픽셀을 보고, 네트워크 반응을 확인하고, 클릭과 키보드 입력을 수행한다.

5. 기본 루프: 감지-행동-검증

화자가 제안하는 기본 자동화 루프는 감지-행동-검증(Sense, Act, Verify)이다.

  1. 감지(Sense)
    DOM, 접근성 트리, 스크린샷 등으로 현재 페이지 상태를 파악한다.

  2. 행동(Act)
    클릭, 입력, 선택 등 한 가지 행동만 한다.

  3. 검증(Verify)
    행동이 성공했는지 확인한다. 이때 중요한 점은 행동한 채널과 다른 채널로 확인하는 것이다. 예를 들어 클릭했다면 클릭 이벤트 자체를 믿지 말고, 화면 변화나 네트워크 반응을 확인한다.

이 루프가 닫히지 않을 때, 즉 보고 행동하고 확인했는데도 페이지가 원하는 대로 움직이지 않을 때, 페이지가 자동화를 막고 있다는 뜻이다. 그때 다음 단계로 올라간다.

6. 미트백 사다리: 필요할 때만 더 사람처럼 행동하기

화자는 자동화 전략을 미트백 사다리(Meatbag Ladder)라고 부른다. 여기서 미트백은 “살덩어리 인간”을 농담처럼 부르는 표현이다.

핵심은 처음부터 복잡하게 사람 흉내를 내지 말고, 가장 낮은 단계에서 해결되는지 먼저 확인하는 것이다.

단계 방식 설명
1단계 합성 JavaScript 클릭 페이지 안에서 노출된 기능을 코드로 직접 호출
2단계 CDP 신뢰 입력 브라우저의 실제 입력 경로를 통해 클릭·키 입력
3단계 인간형 입력과 비전 마우스 궤적, 머무름, 흔들림, 화면 인식까지 사용

1단계는 가장 싸고 빠르다. 예를 들어 단순 버튼 클릭이나 폼 입력은 JavaScript로 충분할 수 있다.

2단계는 웹페이지가 “이 클릭이 진짜 사용자 입력인가?”를 확인할 때 필요하다. 단순 JavaScript 클릭은 신뢰되지 않은 이벤트(Untrusted Event)로 표시될 수 있다. 반면 CDP 입력은 실제 마우스 입력과 유사한 경로를 탄다.

3단계는 캡차처럼 봇을 적극적으로 탐지하는 영역이다. 여기서는 화면을 보고 해석하거나, 사람 같은 마우스 이동을 만들어야 한다.

7. 예시 1: Outlook 이메일 자동화

첫 번째 예시는 Outlook 웹 클라이언트에서 개인화된 이메일을 여러 개 보내는 작업이다.

Outlook 작성창은 특별히 방어할 대상이 없기 때문에 1단계로 충분하다. 합성 클릭으로 작성창을 열고, 내용을 프로그램으로 채운 뒤, 다시 합성 클릭으로 전송한다.

중요한 점은 이 작업이 단순히 “AI가 매번 생각하며 클릭하는 것”이 아니라는 점이다. 한 번 순서를 캡처한 뒤에는 프로그램처럼 반복 실행한다.

화자는 여기서 웹 UI를 권한 없는 만능 API(permissionless API)처럼 사용할 수 있다고 말한다.

예를 들어 회사의 Office 365 API를 쓰려면 앱 등록과 관리자 승인이 필요할 수 있다. 일반 직원은 그 권한을 얻기 어렵다. 하지만 웹 로그인 권한은 이미 있다. 따라서 웹 UI를 자동화하면 별도 API 승인 없이도 사용자가 화면에서 할 수 있는 작업을 반복할 수 있다.

8. 예시 2: 쇼핑몰 장바구니와 신뢰 클릭

다음 예시는 대형 쇼핑몰의 “장바구니 담기” 버튼이다.

Outlook에서 통했던 JavaScript 클릭을 장바구니 버튼에 적용하면 아무 일도 일어나지 않는다. 에러도 없고 실패 메시지도 없다. 페이지가 그냥 무시한다.

이유는 클릭 이벤트가 신뢰되지 않은 이벤트(Untrusted Event)로 찍히기 때문이다. 웹페이지는 브라우저가 붙여준 이벤트 정보를 보고, 이것이 진짜 사람 입력인지 아닌지 판단할 수 있다.

이때 화자는 2단계로 올라간다. CDP의 입력 도메인(Input Domain)을 통해 클릭하면, 브라우저 내부에서는 실제 마우스 입력과 유사한 경로를 거친다. 그러면 이벤트가 신뢰 이벤트(Trusted Event)로 처리되어 페이지가 받아들일 수 있다.

9. 예시 3: Cloudflare Turnstile

Cloudflare Turnstile은 겉보기에는 단순한 체크박스다. 하지만 내부 구조는 자동화 도구가 쉽게 잡지 못하도록 여러 격리 경계를 가진다.

화자는 이 체크박스가 다음과 같은 구조 뒤에 숨어 있다고 설명한다.

  • 닫힌 Shadow Root
  • Cross-Origin iframe
  • 또 다른 Shadow Root

따라서 단순히 “체크박스 요소를 찾아 클릭”하는 방식은 잘 통하지 않는다.

이때 접근 방식은 요소 자체를 잡으려 하지 않는 것이다. 브라우저에게 iframe이 화면 어디에 있는지 묻고, 체크박스가 있을 위치를 계산한 뒤, 화면 좌표에 신뢰 클릭을 보낸다.

핵심은 웹 요소를 직접 조작하는 것이 아니라, 사람이 화면을 보고 마우스로 누르듯 브라우저 표면 위의 위치를 클릭하는 관점이다.

10. 예시 4: 이미지 캡차와 AI 비전

이미지 캡차는 글자가 왜곡되어 있거나 배경 노이즈가 들어간 문제다.

여기서 에이전트는 사람이 하듯 문제 이미지를 본다.

  • 캡차 영역 스크린샷을 찍음
  • AI 비전으로 글자를 판독함
  • 답을 키보드 입력으로 넣음
  • 서버가 검증하면 토큰이 발급됨

이 예시는 AI가 모든 클릭을 담당하는 것이 아니라, 시각적으로 판단해야 하는 부분에만 AI가 쓰일 수 있음을 보여준다.

11. 예시 5: 퍼즐 드래그 캡차

퍼즐형 캡차는 빠진 조각 위치를 찾고, 조각을 끌어서 맞추는 방식이다.

이 문제는 Shadow Root나 iframe이 핵심 장애물이 아니다. 조각은 페이지에 보인다. 어려운 점은 드래그 동작 자체다.

이런 캡차는 마우스 이동 경로를 샘플링한다.

  • 이동 속도 변화
  • 미세한 흔들림(jitter)
  • 곡선 움직임
  • 목표 지점 근처에서 살짝 지나쳤다가 돌아오는 오버슈트(overshoot)

즉 정답 위치만 맞히면 되는 것이 아니라, 그 위치까지 가는 움직임이 사람다워야 한다.

화자는 에이전트가 비전으로 빈 곳을 찾고, 인간형 마우스 궤적으로 퍼즐 조각을 이동시킨다고 설명한다.

12. 최종 보스: reCAPTCHA v2

마지막 사례는 reCAPTCHA v2다. 체크박스를 누른 뒤, 횡단보도·자전거·버스·신호등 같은 이미지를 고르는 그 캡차다.

화자는 이 문제를 두 부분으로 나눈다.

구성 역할
해결사(Solver) 순수 코드. 체크박스 클릭, iframe 진입, 이미지 그리드 캡처, 반복 처리
운영자(Operator) AI 에이전트. 이미지 그리드를 보고 어떤 타일을 골라야 하는지 판단

이 구조에서 중요한 점은 AI가 모든 행동을 하지 않는다는 것이다.

반복적이고 결정론적인 작업은 코드가 빠르게 수행한다. AI는 흐릿한 이미지에서 대상을 판단하는 한 가지 일만 맡는다.

reCAPTCHA는 각 라운드에 시간 제한이 있고, 여러 라운드가 이어질 수 있다. 따라서 매 클릭마다 모델을 호출하면 시간이 부족해진다. 발표자는 이 때문에 기계 속도로 움직이는 결정론적 코드 + 라운드당 한 번의 빠른 AI 시각 판단이 필요하다고 말한다.

13. 발표의 진짜 결론: 캡차보다 방법론

화자는 캡차를 통과한 사례 자체보다, 이를 가능하게 한 엔지니어링 방법론이 더 중요하다고 말한다.

정리하면 다음과 같다.

  1. 에이전트에게 CLI를 제공한다.
  2. 브라우저는 CDP로 제어한다.
  3. DOM, 접근성 트리, 스크린샷, 네트워크, 콘솔 등 디지털 감각을 사용한다.
  4. 감지-행동-검증 루프를 돌린다.
  5. 가장 낮은 미트백 사다리 단계부터 시도한다.
  6. 페이지가 막을 때만 더 사람다운 단계로 올라간다.
  7. 성공한 경로는 코드나 에이전트 스킬로 저장한다.
  8. 다음부터는 다시 풀지 않고 재사용한다.

차드 입장에서 이 발표의 실무적 의미는 단순하다.

AI 자동화는 “AI가 매번 알아서 해주는 것”이 아니라, 사람이 한 번 찾아낸 절차를 코드화하고, AI는 꼭 필요한 판단 지점에만 배치하는 방식이 훨씬 강력하다.

이커머스·물류 업무에 적용하면, 주문 조회, 운송장 입력, 재고 확인, 거래처 포털 작업처럼 API가 없거나 권한이 복잡한 웹 업무를 자동화할 때 중요한 사고방식이 된다.

단, 캡차나 봇 방지 장치를 우회하는 행위는 서비스 약관·법률·플랫폼 정책을 위반할 수 있으므로, 반드시 본인 소유 시스템이나 허가받은 환경에서만 실험해야 한다.

전체 전사 펼치기

웹 자동화의 어둠의 기술에 대해 이야기하겠습니다.

제목이 좀 불길하게 들리죠. 마치 변호사가 필요할 만한 내용을 가르칠 것처럼 들립니다. 변호사 이야기는 잠시 뒤에 다시 하겠습니다. 먼저 배경부터 말씀드리겠습니다.

이 발표를 준비하는 동안, OpenAI가 제가 하던 작업만으로도 제 계정을 정지시킬 수 있다고 경고했습니다. 며칠 전 받은 이메일이 바로 그것입니다. 꽤 놀랄 만한 일이죠.

그렇다면 웹브라우저로 무엇을 했길래 사이버 악용(cyber abuse)으로 계정 정지 경고를 받았을까요? 제가 한 것은 바로 이런 일이었습니다.

여기 보이는 각각의 문제는 사람이 개입하지 않은 상태에서 AI 에이전트가 해결한 것입니다. 약 15분 뒤면 이것이 어떻게 가능한지 이해하게 될 것입니다.

저는 제 에이전트들이 제가 웹을 쓰는 것과 똑같이 웹을 사용할 수 있기를 바랍니다. 예약하고, 이메일을 보내고, 양식을 작성해서 제가 직접 하지 않아도 되게 만들고 싶습니다. 하지만 사람이 아닌 무언가가 페이지를 클릭하기 시작하는 순간, 웹페이지는 종종 반격합니다.

이 발표는 그 싸움에서 이기는 방법에 관한 것입니다. 그리고 약간은 비전통적인 아이디어 하나에서 시작합니다. 전체 발표의 전제는 이것입니다.

CDP 브라우저는 마우스를 든 인간과 같다.

농담이 아닙니다. 적어도 Google, Cloudflare, 그리고 다른 서비스들이 보기에는 그렇습니다. Chrome DevTools Protocol(CDP)을 사용하는 에이전트 구동 브라우저가 있다면, 에이전트의 클릭과 키 입력은 크롬 내부에서 여러분의 입력과 정확히 같은 경로를 지나갑니다. 이것이 핵심 아이디어입니다.

나머지 발표는 이것을 어떻게 구현하느냐에 관한 것입니다. 필요한 것은 세 가지입니다. MCP가 아니라 CLI가 필요합니다. Chrome DevTools Protocol(CDP)이 필요합니다. 여기서 제가 만든 Chrome Agent라는 도구가 등장합니다. 그리고 사다리 위에서 루프를 돌려야 합니다.

먼저 논쟁을 부를 수 있는 첫 번째부터 시작하겠습니다. 에이전트에게 MCP 서버가 아니라 CLI를 줘야 합니다. 여기서 CLI는 셸 기반 도구를 뜻합니다.

이 주장에 반박하고 싶은 분들도 있겠지만, 여기에는 구체적인 이유가 있습니다. 먼저 능력 자체는 비슷하다는 점을 짚고 넘어가야 합니다. Arise AI 사람들이 진행한 최근 연구에 따르면, 같은 작업을 CLI와 MCP에 맡겼을 때 둘 다 약 83% 정도의 성공률을 보였습니다.

하지만 CLI는 재사용성, 속도, 비용 면에서 MCP를 이깁니다.

먼저 재사용성입니다. CLI 시퀀스는 프로그램으로 만들 수 있습니다. 한 번 작성하면 모델을 매번 루프에 넣지 않고도 천 번 실행할 수 있습니다. 반면 MCP는 매 턴마다 모델을 호출합니다.

CLI는 같은 이유로 더 빠릅니다. 매 단계 중간에 모델이 끼어 있지 않기 때문입니다. 앞서 언급한 연구에서, MCP는 같은 작업에 71번의 왕복과 8분이 걸렸습니다. 반면 CLI는 7턴, 1분 미만이었습니다.

이 속도 이야기를 기억해두십시오. 마지막에 다시 중요해집니다.

마지막은 토큰 비용입니다. Anthropic 스스로도 CLI가 토큰 비용 측면에서 최대 75배 저렴할 수 있다고 보고했습니다.

그렇다면 커맨드라인에서 실제로 무엇을 실행하는 것일까요? 우리는 Chrome DevTools Protocol(CDP)로 브라우저를 구동합니다. 이것이 에이전트가 사람처럼 보이기 위해 필요한 두 번째 요소입니다.

여러분은 이름을 몰라도 이미 이 프로토콜을 알고 있습니다. F12를 눌렀을 때 뜨는 개발자도구 패널이 바로 이 프로토콜로 브라우저를 조작합니다. 에이전트도 이 프로토콜로 말할 수 있습니다. Chrome Agent 도구를 사용할 수 있습니다. Chrome Agent는 에이전트가 CDP 상호작용을 재생하는 코드를 쉽게 작성하게 해줍니다.

CDP의 범위는 엄청나게 넓고 자주 바뀝니다. 현재 기준으로 57개의 도메인이 있고, 그 안에는 수백 개의 메서드와 이벤트가 있습니다.

저는 이 도메인들을 머릿속에 넣기 쉽게 여덟 묶음으로 나눴습니다. 하지만 걱정하지 않아도 됩니다. 사람처럼 브라우저와 상호작용하기 위해 57개 도메인이 전부 필요한 것은 아닙니다.

필요한 것은 그중 작은 부분집합입니다. 그리고 그 부분집합을 이해하는 가장 좋은 방식은 에이전트에게 주어지는 디지털 센서로 생각하는 것입니다.

에이전트는 페이지를 봅니다. DOM(Document Object Model)에서 구조를 읽을 수도 있고, 접근성 트리(Accessibility Tree)에서 의미를 읽을 수도 있고, 픽셀이 필요하면 스크린샷을 찍을 수도 있습니다.

에이전트는 페이지를 듣습니다. 이는 페이지와 오가는 네트워크 트래픽일 수도 있고, 콘솔이나 로그일 수도 있습니다.

그리고 에이전트는 클릭, 키 입력, 탐색으로 페이지를 조작합니다.

에이전트가 사람처럼 보이기 위해 필요한 세 번째이자 마지막 요소는 제가 “사다리 위의 루프”라고 부르는 것입니다.

루프는 감지, 행동, 검증입니다. 페이지가 굴복할 때까지 이것을 반복합니다.

감지 단계에서는 DOM, 접근성 트리, 스크린샷 등 하나 이상의 채널을 통해 페이지를 인식합니다.

그다음 행동합니다. 클릭하거나, 입력하거나, 선택하는 식으로 한 가지 일을 합니다.

그다음 검증합니다. 검증은 다시 감지이지만, 상호작용에 사용한 채널과 다른 채널로 감지해야 합니다. 예를 들어 클릭했다면, 클릭 자체에 성공했는지 묻지 마십시오. 네트워크를 확인하거나 화면을 확인하십시오.

현재 위치를 감지하고, 한 번 움직이고, 그 움직임이 먹혔는지 확인한 다음 다시 반복합니다.

이 루프가 닫히지 않을 때, 즉 감지하고 행동하고 검증했는데도 페이지가 원하는 대로 움직이지 않을 때, 그것은 페이지가 반격하고 있다는 뜻입니다. 그때 사다리를 올라가야 합니다. 저는 이것을 미트백 사다리(Meatbag Ladder)라고 부릅니다.

이 사다리는 올라갈수록 점점 더 사람다워지는 기법들의 단계입니다. 세 단이 있으며, 페이지가 강제하는 만큼만 올라갑니다.

다르게 말하면, 실제로 작동하는 가장 낮은 단계까지만 올라갑니다.

1단계에서는 전혀 사람처럼 행동하지 않습니다. 페이지 안에 노출된 API를 그냥 사용하고 합성 JavaScript 클릭을 보낼 수 있다면 그렇게 하면 됩니다. 쉽고, 무료이고, 즉각적이며, 기본값으로 적합합니다.

가짜 클릭이 더 이상 통하지 않을 때 2단계로 올라갑니다. 예를 들어 CDP의 Input 도메인을 사용해 실제 클릭을 보내야 할 때입니다. 이것은 페이지가 여러분의 입력과 구분하기 어려운 에이전트 입력입니다.

3단계로 올라가는 경우는 인간 입력과 인간 행동이 필요할 때입니다. 실제 마우스 경로, 약간의 머무름(dwell), 흔들림(jitter), 또는 실제로 보고 해석하기 위한 비전(vision)이 필요할 수 있습니다.

싸게 시작하고, 페이지가 요구할 때만 한 단계씩 올라가며, 각 단계에서 루프를 돌리고, 작동한 경로를 기록합니다. 이것이 완전히 자동화된 AI 에이전트 기반 브라우징에 도달하는 방식입니다.

먼저 탐색합니다. 직접 루프를 돌리고, 실제로 작동할 때까지 단계를 올라갑니다. 그다음 자동화합니다. 해결책을 기록해 다시는 같은 것을 다시 알아내지 않아도 되게 합니다. 코드로 기록하거나, 에이전트 스킬로 기록하거나, 매우 자주 둘 다로 기록합니다.

이제 이 모든 것이 어떻게 합쳐지는지 보여드리겠습니다. 하지만 먼저 제 변호사의 한마디가 있겠습니다.

변호사 이야기가 다시 나온다고 했죠. 지금부터 보게 될 것은 모두 실제 현장에서의 에이전트 브라우저 사용 사례에서 나온 것입니다. 실제 경험에서 가져온 것입니다. 다만 법률 자문에 따라, 여러분이 보는 모든 것은 제가 소유한 인프라와 제가 운영하는 계정에서만 실행됩니다.

이제 에이전트가 브라우저에서 일하는 모습을 볼 준비가 되셨나요?

좋습니다.

먼저 간단하고 일상적인 사용 사례부터 시작하겠습니다. Outlook 웹 클라이언트에서 서로 다른 개인화 이메일을 한꺼번에 보내보겠습니다.

슬라이드 왼쪽에는 코드로 어떻게 작동하는지 쉽게 볼 수 있도록 의사코드(pseudocode)가 있습니다.

Outlook의 작성창에는 우리가 물리쳐야 할 것이 없습니다. 이것은 미트백 사다리 1단계입니다. 전혀 사람처럼 행동하지 않습니다. 합성 클릭으로 작성창을 열고, 내용을 프로그램으로 채운 다음, 또 다른 합성 클릭으로 보냅니다.

그다음 그대로 실행하면 됩니다. 이 작업이 부드럽게 진행되는 이유는 프로그램을 실행하고 있기 때문입니다. 한 번 시퀀스를 캡처하고 나면, 이메일이 20개든 200개든 하나의 명령으로 반복할 수 있습니다.

한 번 해결하고 영원히 재사용하는 것입니다. 여기서 에이전트는 각 이메일 내용을 개인화하기 위해 문장을 조금씩 바꾸고 있지만, 모든 상호작용 구동은 프로그램으로 수행하고 있습니다.

여기서 이런 질문을 할 수 있습니다. 왜 웹 UI를 조작하나요? 그냥 API를 쓰면 되지 않나요?

기업 환경에서 Office 365 테넌트의 API를 쓰려면 앱 등록이 필요하고 관리자 승인도 필요합니다. 직원 입장에서는 그런 승인을 받기 어려운 경우가 많습니다.

반면 이미 가진 웹 로그인만으로도 화면에서 보는 일을 그대로 할 수 있습니다. 이 패턴에서는 웹 UI 자체가 범용 API, 즉 권한 없는 API(permissionless API)가 됩니다. 꽤 흥미로운 방식입니다.

이것이 1단계입니다. 그렇다면 페이지가 반격하기 시작하면 어떻게 될까요?

여러분이 좋아하는 대형 온라인 쇼핑몰을 둘러본다고 해봅시다. 그냥 Amazon이라고 부르겠습니다. Amazon은 꽤 영리한 사람들이 있는 곳이고, 봇을 좋아하지 않습니다.

Outlook에서 작동했던 같은 JavaScript 클릭을 장바구니 담기 버튼에 적용하면 아무 일도 일어나지 않습니다. 정말 아무 일도 없습니다. 실패도 없고 오류도 없습니다. 그냥 아무 반응이 없습니다. 페이지가 그것을 무시하는 것입니다.

이유는 페이지가 이 클릭이 사람에게서 온 것인지 확인하기 때문입니다. Chrome은 모든 이벤트에 그 답을 찍습니다. 신뢰됨(trusted)인지, 신뢰되지 않음(untrusted)인지 표시합니다.

앞서 보낸 JavaScript 클릭은 신뢰되지 않음으로 찍힙니다. 이 경우 페이지는 조용히 그 입력을 버립니다.

하지만 괜찮습니다. 미트백 사다리를 올라가면 됩니다. 2단계로 이동해 Chrome의 Input 도메인을 사용해 클릭합니다. 이것은 실제 마우스가 사용하는 것과 같은 입력 경로를 사용합니다.

이제 이벤트는 신뢰됨으로 찍히고, 페이지는 여러분의 마우스와 에이전트를 구분할 수 없습니다. 상품은 바로 장바구니에 담깁니다.

여기에서 Amazon.com의 내부 시야를 꽤 잘 볼 수 있습니다. 아래쪽 패널을 보면 페이지 로그가 이렇게 생겼을 것이라고 상상할 수 있습니다. 신뢰되지 않은 클릭은 모두 실패하지만, 신뢰된 클릭은 문제없이 통과합니다.

앞으로 화면에서 마우스 커서가 움직이는 것을 볼 때 참고하십시오. 그 커서는 에이전트가 Chrome Agent와 CDP를 사용해 브라우저에 보내는 마우스 입력을 시각적으로 보여주기 위해 프로그래밍 방식으로 추가된 것입니다. 실제로 제 물리적 마우스가 움직이는 것은 아닙니다.

2단계는 진짜 미트백 입력이 시작되는 지점입니다. 하지만 이것만으로 브라우저 안에서 여러분을 완전히 대체할 수는 없습니다. 그래서 미트백 사다리의 꼭대기인 3단계로 올라갑니다. 이곳은 페이지들이 적극적으로 봇을 사냥하는 좁은 최전선입니다.

여기서는 여러 기법을 사용하게 됩니다. 몇 가지를 살펴보겠습니다.

이 녀석은 익숙하실 겁니다. Cloudflare Turnstile입니다. 보기에는 아주 단순하지만, 지금까지 만난 것 중 가장 어려운 대상입니다. 그 작은 체크박스가 일반적인 웹 자동화 프로그래밍으로 쉽게 닿을 수 없기 때문입니다.

영리한 사람들이 이 체크박스를 세 개의 격리 경계 뒤에 숨겨두었습니다. 먼저 닫힌 Shadow Root 아래에 캡슐화되어 있습니다. 그리고 위젯 전체가 Cross-Origin iframe 안에 있습니다. 그 iframe 안에도 또 다른 Shadow Root가 있습니다.

값싼 꼼수들 입장에서는 그 체크박스는 클릭할 수 없습니다. 잡을 요소가 없습니다.

그래서 어떻게 할까요? 잡으려 하지 않는 것입니다. 브라우저에게 iframe이 화면 어디에 있는지 묻습니다. 약간의 계산으로 체크박스 위치를 추정합니다. 그리고 화면 유리 위의 그 위치에 신뢰 클릭을 보냅니다.

나머지는 Chrome이 처리합니다. 실제 클릭이 체크박스에 떨어지고, 작업이 진행됩니다. 사람은 루프 안에 없습니다. 전부 에이전트가 구동합니다.

이것으로 첫 단계는 통과했습니다. 여기서의 핵심은 상호작용하는 방법을 알아내는 것이었습니다. 하지만 다음 단계들은 이제 실제로 볼 수 있음을 증명하라고 요구합니다.

이것은 이미지 CAPTCHA입니다. 이 녀석 기억하시죠? 이런 것들은 아직도 존재합니다.

에이전트는 실제로 이 CAPTCHA를 읽습니다. 사람이 하는 일을 흉내 냅니다. 챌린지의 스크린샷을 찍고, 그것을 보고, 자체 비전 능력으로 노이즈 속 문자들을 골라냅니다. 그런 다음 정답을 Cross-Origin iframe 안의 위젯으로, 실제 신뢰 키 입력을 통해 한 글자씩 입력합니다.

이것은 여러분이 보내는 것과 같은 키보드 입력입니다. 그다음 서버가 동의하고, 텍스트가 검증되며, 토큰이 발급됩니다.

최종 보스 전에 한 단계가 더 있습니다. 이번 문제는 미트백처럼 움직일 수 있느냐에 따라 이기거나 집니다.

이것은 Lemon의 퍼즐입니다. 작은 직소 퍼즐인데, 조각이 들어갈 위치를 찾고 끌어다 빈틈을 채우는 방식입니다. 이런 CAPTCHA 부류가 많이 있습니다.

이 문제는 다른 방식으로 까다롭습니다. Shadow Root도 없고, Cross-Origin iframe도 없으며, 조각은 페이지에 그대로 보입니다. 어려운 부분은 드래그 자체입니다.

퍼즐 조각을 놓을 때 이런 CAPTCHA는 전체 마우스 이동을 점들의 궤적으로 샘플링합니다. 여기에는 흔들림, 속도 변화 등이 포함됩니다. 따라서 퍼즐을 푸는 것만이 아니라, 사람처럼 움직이며 풀어야 합니다.

에이전트는 손이 드래그하듯 정확히 같은 방식으로 드래그합니다. 움직임을 보면 부드럽게 시작하고, 약간의 곡선이 있으며, 의도적으로 퍼즐 조각을 살짝 지나쳤다가 다시 부드럽게 돌아옵니다. 마우스를 든 미트백처럼 말입니다.

에이전트는 비전을 사용해 빈틈을 식별하고, 사람 같은 움직임으로 그곳까지 이동합니다.

여기까지 Turnstile, MT CAPTCHA, Lemon입니다. 에이전트를 막기 위해 만들어진 세 개의 관문을 각각 통과했습니다. 이제 남은 것은 마지막 보스 하나뿐입니다.

바로 이것입니다. 인터넷의 최종 보스, reCAPTCHA v2입니다.

작은 체크박스 다음에 흐릿한 격자가 나오고, 횡단보도나 신호등 같은 흐릿한 사진을 고르게 하는 그것입니다. 우리 모두 이런 문제를 눈을 가늘게 뜨고 본 적이 있습니다. 하지만 이제 이 녀석도 상대할 전체 도구 세트를 갖췄습니다. 디지털 센서, 그것을 배치할 루프, 미트백 사다리까지 모두 있습니다.

시작해보겠습니다. 전체 기계는 두 부분으로 나뉩니다.

한쪽에는 해결사(Solver)가 있습니다. 이것은 순수 코드입니다. 에이전트도 없고 모델도 없습니다. 모든 것을 프로그램 방식으로 합니다. 체크박스에 신뢰 클릭을 수행하고, 챌린지 iframe 안으로 들어가며, 매 라운드마다 격자 스크린샷을 찍습니다. 어떤 이유로 라운드가 만료되면 다시 준비하고 반복합니다.

이 모든 것은 결정론적이고 빠르며 무료입니다. 하지만 루프 안에는 코드가 할 수 없는 한 단계가 있습니다. 흐릿한 타일 격자를 보고 그 안에 무엇이 있는지 알아내는 일입니다. 예를 들어 이것이 버스인지 판단하는 일입니다.

이것은 비전과 사고가 필요한 일입니다. 눈과 뇌가 필요합니다. 그래서 에이전트에게 주는 일은 오직 이것뿐입니다. 이 부분을 운영자(Operator)라고 부릅니다.

해결사가 에이전트의 어깨를 두드리면, 에이전트는 격자를 한 번 보고, 찾고 있는 대상이 들어 있는 타일을 고른 뒤, 그 답을 해결사에게 넘겨주고 다음 라운드를 기다립니다.

이것이 사실상 발표 전체를 하나의 시스템으로 실행한 모습입니다. 코드는 결정론적인 조작을 담당하고, 에이전트는 눈과 뇌가 필요한 부분만 담당합니다.

보고 싶은 분 계신가요?

여기 있습니다.

재생되는 동안 한번 보십시오. 이 중 일부는 정말 어렵습니다. 에이전트는 제가 보지 못한 타일 속 자전거까지 찾아냈습니다. 결국 서버가 검증했고, 해결되었습니다. 그리고 빠릅니다.

여기서는 빠른 것이 전부입니다. 이 큰 보스는 시간 제한이 있기 때문입니다. 각 라운드는 만료되고, 하나의 챌린지 안에서 여러 라운드가 연속으로 나올 수 있습니다. 매 클릭과 매 시각 확인마다 모델을 왕복 호출하는 에이전트는 시간을 태워버리고 집니다. 챌린지는 끝나기도 전에 만료됩니다.

제가 이 복잡한 문제를 이기는 데 발견한 유일한 방식은 지금 보고 있는 그대로입니다. 기계 속도로 실행되는 결정론적 코드와 라운드당 한 번의 빠른 AI 시각 판단입니다.

아까 속도를 기억해두라고 했던 이유가 바로 이것입니다. 이것이 CDP를 실행하는 CLI여야 했고, 모델이 모든 상호작용 한가운데 앉아 있는 구조가 아니어야 했던 이유이기도 합니다.
