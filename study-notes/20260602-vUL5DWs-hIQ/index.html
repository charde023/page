시니어 엔지니어는 왜 AI 에이전트 개발에 어려움을 겪을까요?

한 줄 요약

에이전트 개발은 "단계를 제어하는" 교통 통제자가 아니라 "목표를 주는" 디스패처 방식으로, 기존 소프트웨어 사고방식 5가지를 전환해야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
텍스트가 새로운 상태 (Text as State) 기존 Boolean/플래그로는 의미·맥락을 담을 수 없음 모든 상태를 자연어·컨텍스트로 표현해야 함
제어권 이양 (Handing Over Control) 에이전트는 비결정적 — 모든 분기를 미리 코딩 불가 목표만 주고 경로는 모델에게 맡겨야 함
오류를 입력으로 처리 (Errors as Inputs) 장시간 실행 에이전트가 중간 실패 시 처음부터 재실행하면 비용·컨텍스트 손실 오류를 모델 입력으로 넘겨 흐름을 이어가야 함
단위테스트 → Eval 같은 입력이 항상 같은 출력을 보장하지 않음 성공률(pass rate)·LLM-as-a-judge로 평가해야 함
에이전트용 API 설계 에이전트는 코드나 배경 지식 없이 스키마·doc string만 봄 툴은 자기문서화(self-documenting) + 시맨틱 인터페이스 필수

내가 모를 만한 것 / 처음 보는 것

  • Eval (에발): 에이전트의 신뢰성을 측정하는 평가 체계. 단위테스트처럼 pass/fail이 아니라 "10번 중 몇 번 성공했나"로 측정.
  • LLM-as-a-judge: 에이전트 출력의 품질을 사람 대신 다른 LLM이 평가하는 패턴.
  • Semantic interface: 함수 시그니처뿐 아니라 doc string·스키마에 의미를 담아 에이전트가 용도를 추론할 수 있게 하는 API 설계 방식.
  • 비결정적 에이전트 (Non-deterministic agent): 같은 프롬프트·입력에도 실행 경로와 결과가 달라질 수 있는 에이전트 특성.
  • Dispatcher 패턴: 에이전트에게 최종 목표만 지정하고 세부 경로는 모델이 선택하게 하는 운영 모델.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 화자는 Google DeepMind에서 Gemini API 에이전트 전담 — 내부·외부 양쪽에서 매일 이 문제를 관찰한다고 명시.
  2. "교통 통제자 vs 디스패처" 비유: 전통 소프트웨어는 신호등·속도·차선까지 제어하는 교통 통제자. 에이전트는 "독일에서 런던 가고 싶어 — 기차든 비행기든 알아서"라고 목적지만 주는 디스패처.
  3. Deep Research 에이전트 예시: 초기 계획(plan)을 "승인/거절" 이진 버튼이 아니라, 자연어로 "미국 시장 집중, 캘리포니아 제외"처럼 추가 지시와 함께 승인할 수 있어야 한다.
  4. 개인화 예시 — 섭씨/화씨: "유럽 사람이라 보통은 섭씨 쓰는데 요리할 때만 화씨 쓰고 싶다"는 선호는 기존 user.temperatureUnit 플래그로 표현 불가 → 컨텍스트로 다뤄야 함.
  5. 고객 이탈(churn) 예시: 기존 분류 모델 → 고정 워크플로(할인 제안 → 취소)는 사용자가 응답 중 의도를 바꾸는 상황을 처리 못함. 에이전트는 대화 흐름에서 동적으로 대응 가능.
  6. Go 언어 오류 처리 비유: Go에서 함수가 에러 or 값을 동등하게 반환하듯, 에이전트 흐름도 오류를 일반 입력으로 취급해 계속 진행해야 한다.
  7. 에이전트가 5분~15분 실행 중 중간에 실패하면, 처음부터 재실행 시 컴퓨팅 비용 + 컨텍스트 모두 손실 — 이 점을 명시적으로 강조.
  8. 생산 배포 기준: 동일 프롬프트가 10번 중 1번만 성공하면 프로덕션에 올리면 안 된다. "Flaky"가 되어서는 안 됨.
  9. delete_item(id) 같은 API는 개발자에게는 자명하지만 에이전트는 스키마와 doc string만 보므로, 에이전트가 이해할 수 있게 doc string을 상세히 작성해야 한다.
  10. "Build to delete": 더 나은 모델·에이전트가 나오면 기존 코드를 버리고 재구축하는 일이 반복될 것 — 소프트웨어는 소모품(disposable).
  11. 발표 후 본인 블로그에 코드 예제 포함 상세 글을 올렸다고 언급 (링크는 x.com/_philschmid 또는 github.com/philschmid 참조).

1. 전통 소프트웨어 vs 에이전트 개발

전통 소프트웨어 개발은 사양(spec) 작성 → 코드 작성 → 테스트 → 배포 → 사용자 이용의 선형 흐름이었다. 에이전트 개발은 다르다: 에이전트에게 지침(instructions)을 정의하고, 실행시킨 뒤, 무엇을 하는지 관찰하고, 프롬프트·툴을 조정하고, 다시 실행하는 반복 루프다.

비유: 전통 SW = 교통 통제자(신호등·속도·차선 제어), 에이전트 = 디스패처(목적지만 지정, 경로는 에이전트가 결정). 코딩 에이전트가 가끔 이상한 경로로 가도 결국 원하는 결과를 내는 것이 이 패러다임이다.

2. 텍스트가 새로운 상태 (Text is the New State)

전통적으로 애플리케이션 상태는 Boolean, 정수, 열거형 등 구조화된 데이터였다. 에이전트 시대에는 텍스트·컨텍스트가 상태를 대체한다.

  • Deep Research 에이전트 예시: 계획 승인 시 "승인/거절" 이진값 대신 자연어 추가 지시("미국만, 캘리포니아 제외")를 함께 전달 가능.
  • 개인화 예시: "유럽인이라 보통 섭씨 쓰지만 요리할 때는 화씨 선호" — 기존 플래그(isEurope, useFahrenheit)로 표현 불가. 컨텍스트로 처리해야 함.
  • 텍스트뿐 아니라 이미지·비디오·오디오도 상태로 처리 가능. 명확한 구조화 데이터 개념에서 벗어나야 한다.

3. 제어권을 이양하라 (Hand Over Control)

기존 고객 지원 시스템: 분류 모델이 인텐트("구독 취소") 분류 → 미리 정의된 워크플로 실행. 동적 대응 불가.

에이전트: 대화 중 사용자 의도가 바뀌어도 동적으로 반응할 수 있다. 이 모든 상태·분기를 결정론적으로 미리 코딩하는 것은 불가능하다. 모델을 신뢰하고 제어권을 넘겨야 한다. 순수 결정론적 환경에서 벗어나야 한다.

4. 오류는 그냥 입력이다 (Errors are Just Inputs)

에이전트 흐름에서 무언가 실패하면, 이를 처음부터 재실행하지 말고 모델에 입력으로 다시 제공해야 한다.

  • Go 언어 비유: 함수가 에러 or 값을 동등하게 반환하듯, 에이전트도 오류를 일반 입력으로 취급.
  • 과거 HTTP 요청 실패 시 단순 재시도는 저비용이었으나, 5분~15분 실행 에이전트가 중간에 실패하면 재실행 시 컴퓨팅 비용 + 기존 컨텍스트 손실이 크다.
  • 오류를 모델에 전달하고, 우회 방법(workaround)이나 추가 검사를 통해 흐름을 앞으로 이어가야 한다.

5. 단위테스트에서 Eval로 (Unit Tests → Evals)

전통 SW: 입력 A → 코드 B → 출력 C (항상 동일). 에이전트: 비결정론적 — 같은 입력이 같은 경로·결과를 보장하지 않는다.

  • 단위테스트·통합테스트·스모크테스트만으로는 부족.
  • 얼마나 자주 성공하는가를 측정해야 한다. 같은 프롬프트가 10번 중 1번만 성공하면 프로덕션 불가.
  • 평가 방식: LLM-as-a-judge, 도메인 전문가 인간 평가.
  • 출력 자체도 주관적 — 리서치 보고서와 고객 피드백 응답의 "좋은 출력"은 다르다.
  • 에이전트가 한 사용자에게는 4단계 추가 리서치를 하고 다른 사용자에게는 하지 않을 수 있다. 결국 최종 출력(outcome)이 측정 기준이다.

6. 에이전트용 API 설계 (Agents Evolve, APIs Don't)

백엔드 개발자에게 deleteItem(id)는 자명하지만, 에이전트는 함수 스키마와 doc string만 보고 판단한다. 수년간 쌓인 개발자 암묵지를 에이전트는 갖고 있지 않다.

  • ID가 무엇인지, 실패 시 어떻게 되는지를 doc string에 명시해야 함.
  • 에이전트가 사용하기 위해 작성된 툴·API여야 한다 — 사람 개발자를 위한 것이 아니라.
  • 자기문서화(self-documenting) + 시맨틱 인터페이스 구현 필요.

7. 요약 — 6가지 핵심 원칙

# 원칙 설명
1 신뢰하되 검증 (Trust but Verify) 모델을 신뢰하되 결과를 측정·검증
2 모델과 싸우지 말 것 특정 워크플로를 강제하지 말고 목표를 줄 것
3 의미 보존 (Preserve Meaning) 모든 것이 컨텍스트 — 구조화 데이터 집착 금지
4 회복 설계 (Design for Recovery) 모델·에이전트는 완벽하지 않음. 특히 장시간 에이전트에서 이상 상황 대비 필수
5 주장이 아니라 평가 (Evaluate, Don't Assert) 신뢰성 = 성공률. 적절한 pass rate 기준 설정
6 삭제를 위해 구축 (Build to Delete) 더 나은 모델·에이전트로 반복 재구축될 것. 소프트웨어는 소모품

전통 소프트웨어 vs 에이전트 개발 흐름 비교

전통적으로 소프트웨어를 개발할 때는 사양(spec)을 만들고, PRD를 작성하고, 코드를 작성하고, 테스트를 만들고, 배포한 뒤 사용자가 사용했습니다. 에이전트를 구축할 때는 조금 다릅니다. 에이전트에게 무엇을 하길 원하는지 지침을 정의하고, 실행시키고, 무엇을 하는지 관찰하고, 프롬프트나 툴을 조정하고, 다시 실행하는 반복 루프가 됩니다.

비유하자면, 전통 소프트웨어는 교통 통제자처럼 신호등·속도·도로까지 제어합니다. 에이전트 시대에는 디스패처가 됩니다. 에이전트에게 "독일에서 런던에 가고 싶어 — 기차를 타든 비행기를 타든"이라고 목적지만 줍니다. 세부 경로는 에이전트가 결정합니다. 코딩 에이전트가 가끔 이상한 방식으로 진행하더라도 결국 원하는 결과를 달성하는 것, 그것이 우리가 원하는 것입니다.

1. 텍스트가 새로운 상태 (Text is the new state)

전통적으로 데이터 구조를 사용했고 모든 것이 Boolean이나 플래그로 매핑되었습니다. 예를 들어 Deep Research 에이전트를 처음 만들면 에이전트가 "이것과 저것을 리서치하겠습니다"라는 계획을 반환합니다. 전통 소프트웨어에서는 계획 수락 또는 거절 버튼이 있었을 것이고, 의미를 파악할 수 없었습니다.

이제 LLM은 의미(semantic meaning)를 이해할 수 있습니다. 예를 들어 시장 조사 요청에서 초기 계획을 승인하면서 "미국 시장에 집중하고 캘리포니아는 제외해줘"라는 추가 정보를 함께 제공할 수 있습니다. 전통 방식이라면 거절 → 추가 입력 → 새 계획 생성의 여러 단계가 필요했을 것입니다.

개인화 예시: 저는 유럽 출신이라 보통 섭씨를 쓰지만, 요리할 때는 화씨를 쓰고 싶다면 어떻게 할까요? 과거에는 사용자 프로필에 isCelsius, isEurope, useFahrenheit 같은 플래그를 두었겠지만, 사용자 선호에 따라 동적으로 조정할 수 없었습니다. 이제는 텍스트와 컨텍스트가 전부입니다. 이미지·비디오·오디오도 포함됩니다. 우리는 더 이상 명확한 구조화 데이터 개념 안에서만 작동하지 않습니다.

2. 제어권을 이양하라 (Start handing over control)

이전 고객 지원의 예: 사용자가 "구독을 취소하고 싶어요"라고 하면 분류 모델이 인텐트(이탈 의도)를 분류하고, "할인 제안할지 취소할지"의 사전 정의된 워크플로가 실행됩니다. 동적으로 반응할 옵션이 없었습니다.

에이전트는 구독 취소 흐름 중에 무언가를 제안하고, 사용자 의미를 이해하고, 구독 대신 다른 무언가를 제안할 수 있습니다. 그러면 사용자는 마음을 바꾸고 전혀 다른 의도로 이어질 수 있습니다. 이 모든 상태 기반 워크플로의 차이와 고유함을 모델링하는 것은 매우 어렵습니다. LLM을 신뢰하고, 우리가 더 이상 순수 결정론적 환경에서 작동하지 않는다는 것을 받아들여야 합니다.

3. 오류는 그냥 입력이다 (Errors are just inputs)

에이전트 흐름에서 무언가 실패하면, 일반 사용자 입력처럼 취급해야 합니다. Go 언어에서는 이미 이렇게 합니다 — 함수 호출이 에러 또는 값을 반환하고 동등하게 처리합니다. 에이전트도 마찬가지여야 합니다.

과거에 HTTP 요청이 실패하면 그냥 재실행했습니다. 하지만 5분, 15분짜리 에이전트가 중간에 실패하면 처음부터 다시 시작해야 합니다 — 많은 컴퓨팅을 다시 쓰고 기존 컨텍스트도 잃습니다. 전체 프로세스를 처음부터 다시 시작할 수 없습니다. 오류를 이해하고 다르게 처리하고, 모델에 다시 제공하고, 우회 방법이나 추가 검사를 통해 흐름을 앞으로 이어가야 합니다.

4. 단위테스트에서 Eval로 (Move from unit tests to evals)

이전에는 통합 테스트, 단위 테스트, 스모크 테스트 등을 작성하고 입력 A → 코드 B → 출력 C가 항상 동일하다고 가정했습니다. 에이전트는 비결정론적입니다. 같은 입력이 항상 같은 단계와 같은 결과로 이어진다고 보장할 수 없습니다.

단위 테스트에서 Eval로 이동해야 합니다 — 얼마나 자주 성공하는지를 테스트해야 합니다. 에이전트가 정말 신뢰할 수 있어야 성공입니다. 고객 에이전트에서 같은 프롬프트가 10번 중 1번만 성공한다면 프로덕션에 올리고 싶지 않을 것입니다. 매우 불안정(flaky)해집니다. Eval에서 몇 번 성공하는지 테스트해야 합니다.

결과도 매우 주관적입니다 — 리서치 보고서 작성과 고객 피드백 시나리오 결과는 다릅니다. LLM-as-a-judge나 인간 전문가 같은 정성적 피드백이 필요합니다. 에이전트가 어떤 사용자에게는 4단계 추가 리서치를 하고 다른 사용자에게는 하지 않을 수 있습니다. 토큰을 더 소비할 수 있지만 최종적으로 outcome이 성공의 측정 기준이어야 합니다.

5. 에이전트용 API 설계 (Agents evolve and APIs don't)

백엔드에서 API를 구축해본 적 있다면 많은 메서드와 엔드포인트들이 자명하게 느껴질 것입니다 — 예: 제품 API의 deleteItem. 하지만 에이전트는 코드를 보지 않고, API를 구축하면서 수년간 쌓인 배경 지식도 없습니다.

에이전트는 함수 스키마와 doc string, 툴 정의만 봅니다. 처음 보면 deleteItem이 무엇을 하는지 실제로 보이지 않습니다. 그래서 메서드·툴이 에이전트가 사용하기 위해 작성되어야 하고, 오랜 개발자 경험이나 API를 구축한 사람의 암묵지를 가정하지 않아야 합니다.

요약 — 6가지 핵심 원칙

  • 신뢰하되 검증하라 (Trust, but also verify). 모델과 싸우지 마라 — 특정 워크플로를 강제하지 말 것.
  • 의미를 보존하라. 이제 모든 것이 컨텍스트다. 더 이상 명확하게 정의된 데이터 구조가 없다.
  • 회복을 위해 설계하라. 모델·에이전트는 완벽하지 않다. 특히 장시간 에이전트에서는 이상한 일이 생긴다.
  • Eval하라, 단순 assert만 하지 말라. 에이전트는 100% 신뢰할 수 없다. 사용자에게 제공하기 위해 얼마나 자주 성공해야 하는지 적절한 균형을 찾아야 한다.
  • 삭제를 위해 구축하라 (Build to delete). 우리 모두가 배우는 교훈 — 소프트웨어는 소모품이다. 더 나은 모델·에이전트로 같은 것을 몇 번이나 재구축하게 될 것이다.

제 블로그에도 올라와 있으니 코드 예제와 함께 더 깊게 보고 싶으신 분은 참고해주세요. 질문 있으시면 언제든 연락주세요. 감사합니다.
