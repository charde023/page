Cursor&xAI 개발자 Lauren Tan: 한 달에 PR 2,000개를 프로덕션에 반영한 워크플로우

원작자 Lauren Tan · T · 업로드 2026-09-25 · 38.0분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

Lauren Tan의 중심 주장은 단순하다. 에이전트를 더 많이 실행한다고 생산성이 바로 높아지는 것은 아니다. 먼저 에이전트가 실수하기 어렵고, 자기 결과를 확인할 수 있는 환경을 만들어야 한다. 화자는 이런 환경을 바탕으로 지난달 2,000개의 풀 리퀘스트(PR)를 프로덕션에 반영했다고 말한다. PR은 코드 변경을 기존 제품에 합쳐 달라는 요청이고, 프로덕션은 실제 사용자가 쓰는 운영 환경이다.

에이전트 한두 개를 사람이 계속 지켜보는 단계에서는 잘못된 방향을 바로 고칠 수 있다. 그러나 같은 방식으로 에이전트 수만 늘리면 사람의 검토 시간이 병목이 된다. 화자는 신뢰가 부족한 상태에서 100개의 하위 에이전트를 실행하면 나쁜 PR, 성능 저하, 버그가 대량으로 생길 수 있다고 경고한다. 따라서 확장의 출발점은 에이전트 수가 아니라 실패를 발견하고 막는 환경이다.

읽는 법: 왼쪽에서 오른쪽으로 갈수록 사람의 직접 개입이 줄고 환경의 역할이 커진다. 아래의 점선은 자동화가 끝이 아니라는 뜻이다. 운영 중 새로운 실패를 발견하면 다시 코드 구조와 검사 규칙을 고쳐야 한다. 이 그림은 화자의 논리를 정리한 개념도이며 성능을 수치로 측정한 그래프가 아니다.

검증은 “에이전트가 스스로 증거를 모으게 하는 일”이다

화자가 Cursor에 합류했을 때 맡은 일은 에이전트 창의 성능 문제를 개선하는 일이었다. 당시에는 Chrome DevTools로 성능 기록을 만들고, 메모리 상태를 찍는 힙 스냅샷을 조사하는 작업을 사람이 직접 반복했다고 한다. 들어오는 PR이 많아지자 앱의 성능이 다시 나빠지는지 계속 확인하기 어려웠다.

여기서 화자는 검증 스킬(verification skill)을 만들기 시작했다. 이것은 에이전트에게 “잘했어?”라고 묻는 문장이 아니라 다음 두 가지를 제공하는 작업 도구다.

  1. 재현 가능한 실행 도구: 매번 다른 임시 스크립트를 만들지 않고, 정해진 명령줄 도구(CLI)로 앱을 실행하고 성능 기록과 증거를 수집한다.
  2. 기능 지도(feature map): 앱에 어떤 기능이 있고, 사용자가 키보드나 화면 요소를 통해 어떻게 그 기능에 도달하는지 기록한다.

기능 지도가 필요한 이유는 실제 요청이 항상 친절하지 않기 때문이다. 화자는 사용자가 화면의 작은 부분만 캡처하고 물음표 세 개를 붙여 보낸 사례를 든다. 실행 도구만 가진 에이전트는 앱을 조작할 수 있어도 사용자가 어느 기능을 가리키는지 알기 어렵다. 기능 지도를 함께 제공하면 무엇을 시험해야 하는지와 어떻게 시험할지를 연결할 수 있다.

화자는 이 조합을 Control Glass라는 스킬로 만들었다고 설명한다. 기능 지도도 코드 저장소 안에 두고 자동화로 관리했다고 말한다. 그 결과 에이전트가 앱을 실행하고 성능 기록을 수집할 뿐 아니라, 내부와 외부 사용자의 요청을 해석하는 데에도 도움을 받았다고 주장한다.

읽는 법: 위쪽 화살표는 한 번의 작업 흐름이고, 아래쪽 되먹임은 실패에서 팀의 도구가 개선되는 흐름이다. 핵심은 에이전트가 “완료했다”고 말하는 것이 아니라 같은 절차로 실행한 결과를 남기는 것이다.

다만 기능이 실제로 작동한다고 해서 코드가 자동으로 좋은 것은 아니다. 화자는 결제 버튼이 실제로 결제를 수행하는지는 검증할 수 있지만, 그것만으로 성능과 코드 품질까지 보장하지는 못한다고 구분한다. 그래서 디버깅, 기능 개발, 시제품 제작 등의 작업 방식을 가르치는 PStack이라는 스킬 모음도 만들었다고 말한다. 검증 스킬은 작동 여부를 확인하고, 작업 스킬은 원하는 개발 방식을 안내한다.

가장 강한 규칙은 설명문보다 구조다

화자는 에이전트가 현재 읽고 있는 코드의 기존 패턴을 따라가는 경향이 있다고 본다. 좋은 패턴이 저장소에 많으면 그것을 확장하지만, 임시방편과 나쁜 패턴이 있으면 그것도 복제한다. 따라서 코드베이스는 단순한 결과물이 아니라 에이전트가 다음 코드를 만들 때 참고하는 물질화된 기억이다.

이 관점에서는 모든 규칙의 힘이 같지 않다. 사람이 읽는 스타일 가이드는 잊거나 무시할 수 있다. 에이전트용 규칙과 스킬도 유용하지만 항상 읽힌다고 보장할 수 없다. 반면 컴파일러, 린트, CI 같은 자동 검사는 기준을 어긴 변경을 기계적으로 찾아낼 수 있다. 가장 강한 방법은 잘못된 선택 자체가 불가능하도록 데이터 구조와 아키텍처를 바꾸는 것이다.

읽는 법: 위쪽일수록 실수를 사후에 발견하기보다 처음부터 선택할 수 없게 만든다. 아래쪽 장치가 쓸모없다는 뜻은 아니다. 화자의 제안은 한 가지만 고르는 것이 아니라 강한 제약 위에 안내와 사람의 판단을 겹치는 것이다.

화자는 이 원리를 GrokBot의 클라이언트 프레임워크인 Dune에 적용했다고 말한다. 예를 들어 기능별 코드를 정해진 위치에 모으고, Electron의 메인 프로세스와 렌더러 스레드 사이의 가져오기 경계를 코드로 강제한다. Cursor 에이전트 창에서 렌더러로 잘못 들어온 코드가 성능을 떨어뜨린 경험을 구조적 제약으로 바꾼 사례다.

화자는 부드러운 화면을 위해 60fps에서는 16밀리초, 120fps에서는 8밀리초보다 긴 작업을 렌더러에 두지 않아야 한다고 설명한다. Dune은 가져오기 관계와 의존성 그래프로 이런 경계를 강제한다고 한다. 이 수치와 구현 효과는 전사 속 화자의 설명이며, 별도의 측정 자료는 제공되지 않았다.

더 극단적인 사례는 코드 주석 금지다. 화자는 에이전트가 주석을 어려운 문제의 설명이 아니라 실제 해결을 피하는 근거로 사용하고, 다른 에이전트가 그 임시방편을 복제하는 모습을 보았다고 말한다. 그래서 Dune에서는 주석을 금지했다고 한다. 이것은 모든 코드베이스에 주석이 해롭다는 일반 법칙이 아니라, 화자가 관찰한 특정 실패를 막기 위해 선택한 강한 규칙이다.

자동화는 신뢰 장치 뒤에 붙는다

화자는 GrokBot을 Slack, Datadog, Sentry, PlanetScale 같은 외부 도구의 사건을 모으는 바깥 고리(outer loop)로 설명한다. 알림이나 사용자 보고가 들어오면 GrokBot이 정보를 모으고 Claude 에이전트나 Cursor 자동화를 시작할 수 있다는 구상이다. 화자는 실제로 버그 보고를 자동 재현하고 PR을 자동으로 여는 자동화가 있다고 말한다.

그러나 이런 자동 시작 장치가 먼저 오면 위험하다. 에이전트가 잘못된 패턴을 반복하는 환경에서 사건 감지와 병렬 실행만 늘리면 오류도 더 빨리 퍼질 수 있다. 화자의 순서는 다음과 같다.

반복 오류 발견 → 코드 구조나 자동 검사로 차단 → 규칙과 스킬로 절차 안내 → 실행 결과를 검증 → 그 뒤에 자동 시작과 병렬화를 확대

화자는 이를 조립식 공장보다 미슐랭 주방에 가깝다고 비유한다. 제품 개발은 창의적인 작업이지만, 좋은 주방은 조리사 개인의 능력에만 의존하지 않는다. 도구의 위치, 훈련, 역할 배치, 청소와 안전 절차가 함께 최종 결과를 만든다. 마찬가지로 사람은 에이전트가 작성하는 코드 한 줄마다 직접 손대지 않더라도, 어떤 환경에서 어떤 증거를 남기며 일할지는 계속 책임져야 한다.

전체 통찰은 “좋은 프롬프트를 더 많이 쓰자”가 아니다. 사람이 반복해서 하는 교정을 저장소, 검사기, 실행 도구와 기능 지도에 옮겨 놓아야 신뢰가 개인의 주의력에서 시스템의 성질로 바뀐다. 그 뒤에야 자동 대응과 병렬 작업이 가치로 이어질 가능성이 커진다.

다만 중요한 경계가 있다. 2,000개 PR이라는 수치는 화자의 자기 보고이며 PR 크기, 실패율, 되돌림 수, 품질 기준이 제시되지 않았다. 또한 제목은 Cursor&xAI, META의 추정 소속은 T, 전사 속 자기소개는 SpaceX AI를 사용하므로 소속 표기가 서로 일치하지 않는다. 전사에서는 “다섯 관점”을 보라고 말하지만, 슬라이드 없이 읽을 수 있는 설명은 코드베이스, 정적 분석, 규칙·Bugbot·스킬, 스타일 가이드라는 네 묶음으로도 해석된다. 아키텍처와 “잘못된 패턴을 불가능하게 만드는 설계”를 별도 항목으로 세면 다섯이 되지만, 정확한 원래 목록은 확인할 수 없다.

여기까지만 이해하면 충분

  • 에이전트 신뢰는 답변을 믿는 감정이 아니라 실수를 막고 결과를 재현·검증하는 환경에서 생긴다.
  • 반복되는 교정은 대화로 끝내지 말고 코드 구조, 린트, CI, 규칙, 스킬과 공통 실행 도구에 옮겨야 한다.
  • 자동화와 병렬화는 먼저 늘릴 대상이 아니라, 검증과 강제 장치가 갖춰진 뒤 확대할 대상이다.
  • 2,000개 PR과 조직·소속 표기는 화자의 주장과 제공된 META에 의존하며 독립 검증되지 않았다.

비유와 깨지는 지점

미슐랭 주방

에이전트는 조리사, 스킬은 조리 절차와 훈련, CLI는 반복해서 쓰는 조리 도구, 아키텍처와 린트는 위험한 행동을 막는 주방 구조에 대응한다. 사람은 모든 재료를 직접 손질하지 않더라도 주방 설계와 최종 결과에 책임을 진다.

비유가 깨지는 지점: 실제 소프트웨어 규칙은 일부 행동을 기계적으로 금지할 수 있지만, 주방의 사람은 상황을 해석하고 예외를 판단한다. 또한 모든 코드 품질과 제품 판단을 정해진 조리법처럼 완전히 표준화할 수 있다는 뜻은 아니다.

신뢰가 낮은 환경에서는 각 에이전트가 요청을 다르게 해석하고, 임시 스크립트와 기존의 나쁜 패턴을 반복할 수 있다. 실행 수가 늘면 사람이 확인해야 할 결과도 함께 늘어난다. 공통 실행 절차, 검증 증거, 자동 검사와 구조적 제약이 없으면 병렬화가 생산성이 아니라 오류 생성 속도를 높일 수 있다.

검증 스킬과 규칙 문서는 무엇이 다르며, 왜 둘 중 하나만으로 충분하지 않은가?

검증 스킬은 앱을 실행하고 결과와 성능 증거를 수집하는 구체적인 능력을 제공한다. 규칙 문서는 어떤 방식으로 일해야 하는지 안내하지만 읽히지 않거나 무시될 수 있다. 반대로 실행 검증만으로 코드 품질과 아키텍처가 좋아지는 것은 아니다. 따라서 실행 증거, 강제 가능한 검사, 작업 지침을 겹쳐야 한다.

1. 2,000개 PR과 신뢰

Lauren은 자신을 X에서 Potato로 알 수 있으며, GrokBot에서 일한다고 소개한다. 지난달 프로덕션에 2,000개의 PR을 반영했다고 말하지만, 처음부터 월 2,000개를 목표로 삼은 것은 아니었다고 설명한다.

화자의 논지는 에이전트가 자리를 비운 동안에도 높은 품질의 작업을 만들도록 환경을 잘 구성하면 개인 또는 팀 단위의 “소프트웨어 공장”에 가까운 생산 체계를 만들 수 있다는 것이다. 다만 화자는 공장이라는 표현보다 창의적 작업과 환경 설계의 책임을 함께 드러내는 “미슐랭 주방”을 선호한다.

초기에는 한 명이 한 개에서 다섯 개 정도의 에이전트 대화를 계속 지켜보며 방향을 수정한다고 설명한다. 이런 상태에서 100개의 하위 에이전트를 실행하면 나쁜 PR, 성능 저하와 버그가 늘 수 있다는 것이 화자의 경고다. 여기의 1~5와 100은 실제 운용 대수로 확정된 수치가 아니라 신뢰 수준에 따른 확장 차이를 설명하는 예시다.

2. 수작업 성능 분석에서 검증 스킬로

화자는 Cursor에 합류했을 때 새로운 에이전트 창의 성능 문제를 맡았다. Chrome DevTools, 성능 추적과 힙 스냅샷을 직접 다루는 과정이 매우 수동적이었다고 회고한다.

여기에서 앱을 실행하고 성능 기록을 수집하고 병목을 찾은 뒤 더 나은 성능으로 반복 개선하는 작업을 에이전트가 수행할 수 있는지 질문했다. 형식 검증의 어려운 끝에는 Lean이나 TLA+ 같은 방법이 있지만, 화자는 그런 방법을 사용하지 못하더라도 실행 기반 검증 스킬로 상당한 진전을 만들 수 있다고 주장한다. 형식 검증은 여전히 어려운 열린 문제라고 구분한다.

3. CLI와 기능 지도

첫 검증 스킬의 이름은 Control Glass다. Chrome DevTools Protocol을 통해 앱을 실행하고 추적 자료를 수집하도록 가르친다고 설명한다.

첫 구성 요소는 CLI다. 세션마다 다른 임시 스크립트를 만들지 않고 같은 방식으로 앱을 실행하고 증거를 모으도록 한다. 화자는 다양한 사용 사례를 안정적으로 처리하려면 이 CLI 자체에도 지속적인 투자가 필요하다고 말한다.

두 번째 구성 요소는 기능 지도다. Slack에서 작은 UI 조각과 물음표 세 개만 담긴 보고가 들어오자, 실행 능력만 있는 에이전트는 사용자가 무엇을 뜻하는지 추측해야 했다. 기능 지도에는 기능 목록, 키보드 단축키, 클릭해야 할 DOM 요소와 각 기능의 의미가 저장된다. 화자는 이를 사이트맵에서 영감을 받은 물질화된 기억이라고 부른다.

4. 품질 스킬과 강제 장치

화자는 기능이 원하는 동작을 수행하는 정확성과 성능·코드 품질을 구분한다. 결제 버튼이 실제로 결제를 수행하는지는 실행 검증으로 확인할 수 있지만, 그것만으로 구현 품질이 좋다고 말할 수는 없다.

PStack은 디버깅, 기능 개발과 시제품 제작 등 화자가 사용했던 개발 절차를 스킬로 묶은 플러그인이라고 설명한다. 숙련 개발자가 팀 저장소에 이런 스킬을 기여하면 에이전트가 팀의 작업 방식을 따르는 데 도움을 줄 수 있다는 주장이다.

화자가 설명한 보호 장치는 다음처럼 정리할 수 있다.

  • 코드베이스와 기존 패턴
  • 잘못된 선택을 불가능하게 만드는 아키텍처·데이터 구조
  • 린트, 컴파일러 진단과 CI 같은 정적·자동 검사
  • 규칙, Bugbot과 스킬
  • 스타일 가이드와 사람의 코드 리뷰

사람의 리뷰에서 반복되는 지적은 더 강한 앞단의 장치로 이동시켜야 한다고 제안한다.

5. Dune과 정원사

Dune은 GrokBot을 구동하기 위해 만든 에이전트 친화적 클라이언트 프레임워크라고 설명된다. 핵심은 에이전트가 선택하기 쉬운 지름길을 올바른 길로 만드는 것이다.

화자는 코드베이스의 임시방편이 에이전트에 의해 바이러스처럼 복제될 수 있다고 말한다. 이를 막는 역할을 정원의 잡초를 일찍 제거하는 “정원사”에 비유한다. 주요 원칙은 기존 기술 부채를 삭제하고, 하나의 권장 경로를 유지하며, 나쁜 패턴을 발견하면 우선 린트 규칙을 추가해 확산부터 막는 것이다.

Dune에서는 기능별 코드를 한 폴더에 모으고, 애플리케이션 영역 사이의 가져오기 경계를 엄격하게 둔다. Electron의 메인 프로세스용 코드가 렌더러 스레드에 들어오지 못하도록 의존성 그래프로 강제한다는 사례가 제시된다.

화자는 60fps를 원하면 16밀리초, 120fps를 원하면 8밀리초보다 오래 걸리는 작업을 렌더러에 남기지 말아야 한다고 설명한다. 또한 에이전트가 주석을 실제 문제를 해결하지 않는 근거로 사용하고 그 패턴을 복제하는 현상을 보고 Dune에서 주석을 금지했다고 말한다.

6. 바깥 고리와 자동화

GrokBot은 Slack, Datadog, Sentry, PlanetScale 같은 도구를 연결해 사건을 모으는 바깥 고리로 설명된다. GrokBot 루틴이 Slack 스레드나 Sentry 경보를 구독하고 Claude 에이전트를 시작할 수 있다고 한다.

코드베이스, 규칙, 스킬과 검증 도구가 준비되면 Cursor 자동화와 SDK 기반 봇도 같은 기반을 재사용할 수 있다. 화자는 버그 보고를 자동으로 재현하고 PR을 여는 자동화가 이미 작동한다고 말한다.

마지막 제안은 에이전트를 교정할 때마다 어느 층에서 고치는 것이 가장 효과적인지 묻는 것이다. 우선 코드 구조와 데이터 구조로 잘못된 패턴을 불가능하게 만들고, 그다음 정적 분석을 검토하며, 규칙·Bugbot·스킬을 겹치라고 권한다.

안녕하세요, 제 이름은 Lauren입니다. X에서는 Potato라는 이름으로 알려져 있을 수도 있고, 저는 SpaceX AI에서 GrokBot을 만들고 있습니다.

제가 이렇게 할 수 있었던 방법의 상당 부분은 신뢰를 통해서였습니다. 저는 제가 자리에 없을 때에도 에이전트가 높은 품질의 작업을 만들어 낼 것이라고 어떻게 신뢰할 수 있을지 많이 고민합니다.

오늘 제 주장이자 발표의 핵심 논지는 이렇습니다. 에이전트를 위한 환경을 정말, 정말 잘 설정하면, 개인용 또는 심지어 팀 단위의 소프트웨어 공장처럼 보이는 무언가를 만들 수 있습니다. 이전보다 훨씬 빠른 속도로 매우 높은 품질의 코드를 생산하는 것이죠.

하지만 저는 “소프트웨어 공장”이라는 표현을 좋아하지 않습니다. 저는 미슐랭 주방에 비유하는 편이 더 좋습니다. 기술자로서 우리는 실제로 무언가를 생산하는 것, 즉 조립 라인에서 제품을 대량 생산하는 일을 하는 게 아닙니다. 우리가 하는 일은 매우 창의적으로 보입니다. 제품을 만들어 가는 행위이고, 어떤 의미에서는 예술입니다.

에이전트와 함께 제품을 구성하는 개별 요소를 더 이상 우리가 직접 요리하지 않는다고 해도, 최종 결과와 주방을 어떻게 구성할지 고민하는 책임은 여전히 우리에게 있습니다. 라인 쿡(line cook)과 수셰프(sous-chef)를 어떻게 배치하는지, 그들이 어떤 장비와 교육을 받는지, 식기 세척 담당자는 어떻게 두는지, 라인 쿡과 식기 세척 담당자의 비율은 어떤지에 따라 달라집니다. 이 모든 요소가 최종 결과물을 만드는 데 들어갑니다. 저는 이 비유가 정말 적절하다고 생각합니다.

시작하기 전에 짧게 이야기를 하나 하고 싶었습니다. 6개월 전, 제가 Cursor에 처음 합류했을 때, SpaceX AI의 일부가 되기 전이었죠. 물론 저는 활용할 수 있는 에이전트 스킬(agent skill)이 전혀 없었습니다. 막 회사에 합류한 상태였고, 제가 작업하던 코드베이스와 제품도 새로 만들어진 것이었습니다.

당시 Cursor는 Cursor IDE를 대체할 새로운 에이전트 창(agent window)을 만들고 있었습니다. 제가 합류하기 전에는 Cursor 에이전트 창에 성능 문제가 꽤 많았고, 당시 제 매니저가 제가 그들을 도울 수 있는지 물었습니다.

Cursor에 합류하기 전에 React 팀에서 어느 정도 일한 경험이 있었기 때문에, 잘 맞는 일처럼 보였습니다. 하지만 처음 시작하자마자 이 과정이 얼마나 수작업 중심인지 빠르게 깨달았습니다.

이전에도 성능 작업을 해본 적은 있었지만, 풀 리퀘스트가 반영되는 속도를 보니 계속 들어오는 풀 리퀘스트의 벽을 도저히 넘을 수 없을 것처럼 느껴졌습니다. 앱의 성능이 퇴보하고 있는지 아닌지도 알 수 없었습니다.

Cursor 팀에서 초기에 보낸 시간의 상당 부분은 Chrome DevTools를 확인하고, 성능을 분석하고, 성능 트레이스(performance trace)를 실행하고, 힙 스냅샷(heap snapshot)을 수집하는 일이었습니다. 정말, 정말 수작업이 많았습니다. 너무 수작업 중심이라 저는 아주 답답해졌고 이렇게 생각하기 시작했습니다. “잠깐, 우리에게 에이전트가 있잖아. 내가 지금 뭘 하고 있는 거지?”

저는 검증 스킬(verification skill)에 대해 생각하기 시작했습니다. 에이전트가 직접 애플리케이션을 실행하고, 저 대신 트레이스를 수집하고, 트레이스를 이해하고, 병목 지점을 찾고, 기본적으로 애플리케이션의 성능을 자동으로 더 나은 방향으로 언덕 오르기(hill-climbing)할 수 있다면 어떨까?

지난 6개월 동안 Cursor와 SpaceX AI에서 일하면서 제 생산성이 폭발적으로 증가한 것을 분명히 볼 수 있습니다. 저는 한 달에 풀 리퀘스트 2,000개를 반영하겠다는 목표를 세운 적이 없습니다. 전혀 제 목표가 아니었습니다. 하지만 제가 만들고 있던 모든 스킬과 도구, 코드베이스 변경이 결국 신뢰라는 개념으로 연결된다는 것을 깨달았습니다.

당시에는 몰랐지만, 머릿속 한구석에는 이런 생각이 있었습니다. 내가 병목이다. 엔지니어로서 가진 모든 지식을 에이전트 팀에 전달할 수 있어야 한다. 모든 일에서 내가 방해 요소가 되지 않아야 한다.

그리고 이것이 성과로 이어졌다는 점은 분명합니다.

그래서 결국 핵심은 신뢰라고 생각합니다. 하지만 정확히 어떻게 그 신뢰를 쌓을 수 있을까요? 에이전트를 활용하는 여정에서 지금 어느 단계에 있든, 어디서부터 시작해야 할까요?

제가 시작했을 때는 분명 1~5개 정도의 범위에 있었습니다. 모든 채팅과 대화를 계속 지켜봐야 한다고 느끼는 단계입니다. 에이전트가 올바른 일을 하도록 끊임없이 방향을 수정하고, 개입하고, 교정해야 합니다. 여러분이 자리에 없으면 기본적으로 아무 일도 일어나지 않고, 에이전트는 잘못된 일을 합니다.

저는 실제로 에이전트 사용의 이 단계에서 벗어나는 것이 가장 어렵다고 주장하고 싶습니다. 정확히 어떻게 벗어날 수 있는지가 항상 명확한 것은 아니기 때문입니다. 다시 말하지만, 핵심은 신뢰입니다. 에이전트 1~5개에서 100개에 가까운 규모로 늘리지 못하는 이유는 아직 에이전트의 작업을 신뢰하지 못하기 때문입니다.

신뢰가 없는 상태에서 하위 에이전트(sub-agent)나 Claude 에이전트 100개를 생성하려고 하면, 곧 형편없는 풀 리퀘스트가 잔뜩 생기고, 수많은 퇴행(regression)과 버그가 배포되는 상황을 보게 될 것입니다. 아무도 그것을 달가워하지 않을 겁니다.

그렇다면 이런 질문이 생깁니다. 에이전트를 어떻게 더 신뢰할 수 있을까요?

저에게는 앞서 말했듯 Cursor 팀에 합류해 성능 작업을 시작하면서, 검증이 필요하다는 것을 깨달은 때부터 본격적으로 시작됐습니다.

제가 검증이라고 말할 때는 여러 단계가 있습니다. 낮은 수준에서는 제가 말한 검증 스킬 같은 것이 있습니다. 에이전트에게 애플리케이션을 실행하는 방법과 Chrome DevTools 프로토콜(Chrome DevTools Protocol) 또는 디버깅에 사용하는 다른 프로토콜을 가르치는 것입니다. 애플리케이션을 디버깅하고, 성능 트레이스를 수집하고, 힙 스냅샷을 수집하는 등의 방법을 가르칩니다.

스펙트럼의 반대편에는 훨씬 더 어렵고 여전히 열린 질문으로 남아 있는 보다 형식적인 검증(formal verification)이 있습니다. 형식적 방법(formal methods)이나 Lean, TLA+ 같은 언어에 의존해 검증을 수행할 수도 있습니다. 이를 통해 비즈니스 수준의 불변식(invariant)이 항상 참인지 확인하고, 애플리케이션이 항상 올바른 상태에 있는지 형식적으로 검증할 수 있습니다.

하지만 형식적 방법을 실행할 수 있는 능력이 없더라도—실제로 그런 능력을 가진 사람은 매우 적습니다—검증 스킬만으로도 아주 멀리 나아갈 수 있다고 생각합니다.

제가 Cursor에 합류해 Cursor 에이전트 창 작업을 시작했을 때 처음 만든 스킬은 Control Glass라는 스킬이었습니다. 앞서 말했듯 이 스킬은 에이전트에게 애플리케이션을 실행하고 트레이스를 수집하는 방법을 가르치는 검증 스킬이며, Chrome DevTools 프로토콜을 통해 이를 수행합니다.

이 스킬에서 흥미로운 점은 제가 반복해서 개선해 가며 만들었다는 것입니다. 처음부터 이런 형태였던 것은 아니지만, Control 또는 검증 스킬에는 실제로 두 가지 구성 요소가 있습니다.

첫 번째 부분은 당연히 CLI입니다. 에이전트가 애플리케이션을 재현 가능하게 실행하고, 트레이스와 증거, 즉 코드가 작동하고 있으며 성능 기준을 충족하고 있다는 경험적 증거를 수집할 수 있어야 합니다.

에이전트 세션마다 달라질 수 있는 스크립트를 매번 에이전트가 만들게 하는 대신, 스킬 디렉터리 안에 CLI를 만들 수 있습니다. 그러면 에이전트는 매번 그것을 사용하게 됩니다. 물론 이를 위해서는 투자해서 다양한 사용 사례를 처리하고 애플리케이션을 올바르게 실행할 수 있도록 잘 만들어야 합니다.

또 하나 정말 중요한 것은 기능 지도(feature map)라는 개념입니다. 기능 지도는 Cursor에서 이러한 Control 스킬을 사용하기 시작했을 때 제가 만든 표현이라고 할 수 있습니다.

곧 우리는 Slack 보고서가 들어오고, 사용자가 UI의 아주 작은 일부만 담긴 매우 모호한 스크린샷을 올린 뒤 물음표 세 개만 붙이는 상황을 발견했습니다. Control 스킬을 사용하는 에이전트는 사용자가 무슨 뜻인지 전혀 알 수 없었습니다. 애플리케이션은 실행할 수 있었지만 사용자가 정확히 무엇을 의미하는지는 추측할 뿐이었습니다.

그래서 저는 기능 지도라는 것을 만들자는 아이디어를 냈습니다. 일종의 사이트맵(sitemap)에서 영감을 받은 것입니다. 본질적으로 이는 구체화된 메모리(materialized memory)입니다. 애플리케이션이 정확히 어떻게 작동하는지, 어떤 기능이 있는지, 키보드 단축키나 클릭해야 할 DOM 요소의 관점에서 사용자가 해당 기능에 어떻게 도달하는지, 각각의 기능이 무엇을 하는지를 담습니다.

이 기능 지도는 스킬 자체, 즉 코드베이스의 스킬 디렉터리 안에 저장됩니다. 또한 이 기능 지도를 유지 관리하는 자동화도 갖추고 있습니다.

CLI와 기능 지도를 결합하자, 우리는 곧 이 조합이 매우 강력하다는 것을 깨달았습니다. 이제 에이전트는 애플리케이션을 재현 가능하게 제어하고 트레이스를 수집할 수 있을 뿐 아니라, 내부 및 외부 사용자로부터 들어오는 요청도 이해할 수 있었습니다.

얼마 지나지 않아 우리는 Control 검증 스킬이 매우 유용해서 팀의 핵심 인프라가 되었다는 사실을 깨달았습니다. 우리는 이를 계속 유지 관리합니다.

에이전트가 자신의 작업을 검증할 수 있는 능력은 대단히 강력합니다. 우리는 이 스킬에 많은 시간을 투자했고, 신뢰를 쌓는 데 매우, 매우 큰 도움이 되고 있습니다.

검증과 더불어, 에이전트가 실제 소프트웨어 엔지니어처럼 일하도록 가르치는 스킬도 필요합니다. 검증은 본질적으로 정확성에 관한 것입니다. 저에게 정확성이란 기능이나 코드가 여러분이 원하는 일을 하는지를 의미합니다. 체크아웃 버튼이 실제로 장바구니를 결제하는지와 같은 것입니다.

기능이 실제로 작동한다는 경험적 증거를 얻을 수 있기 때문에 검증은 매우 중요합니다. 하지만 그 기능의 성능이나 코드 품질에 대해서는 많은 것을 알려 주지 않습니다.

여기서 에이전트가 실제 소프트웨어 엔지니어처럼 일하도록 가르치는 스킬을 생각하기 시작합니다. 저는 PStack이라는 플러그인을 만들었습니다. 오늘은 이 플러그인에 대해 너무 많이 이야기하지 않겠지만, 제가 만든 스킬 모음인 이 플러그인의 상당 부분은 다양한 소프트웨어 엔지니어링 작업을 하면서 개인적으로 사용해 온 워크플로에서 영감을 받았습니다.

디버깅, 기능 개발, 프로토타이핑, 그 밖의 여러 작업을 위해 PStack에는 다양한 플레이북과 스킬이 포함되어 있습니다. 이 스킬들은 에이전트가 여러분이 원하는 방식으로 코드를 작성하도록 가르칩니다.

여러분 팀의 숙련된 엔지니어들은 에이전트를 훨씬 더 똑똑하게 만들어 주는 스킬의 팀 저장소를 구축함으로써 이 지점에 크게 기여할 수 있습니다.

그러한 스킬을 검증 스킬과 결합하면, 에이전트가 자신이 하는 작업이 정확할 뿐 아니라 높은 품질이라는 사실까지 검증할 수 있는 단계에 도달할 수 있습니다.

다시 말하지만, 검증을 통해 애플리케이션의 실제 성능 지표를 수집하고 성능에 관한 실제 수치, 통계, 텔레메트리(telemetry)를 얻을 수 있습니다. 저는 이 부분에 투자하는 것이 정말 중요하다고 생각합니다.

또 하나 정말 중요하다고 생각하는 것은 아키텍처를 리팩터링하고 재작성해서 에이전트 친화적으로 만드는 것입니다. 이것이 소프트웨어 엔지니어링 팀으로서 할 수 있는 가장 중요한 일 중 하나라고 말하고 싶을 정도입니다. 미래에 에이전트가 모든 코드를 작성하게 될 것이라고 진정으로 믿는다면, 기본적으로 올바르게 작동하도록 코드베이스를 설계해야 하기 때문입니다.

에이전트에 대한 신뢰를 구축하는 서로 다른 요소들 사이에는 일종의 규모, 또는 연속체가 있다는 것을 알게 될 것입니다. 여기에는 다섯 가지 항목이 있는데, 코드베이스는 사실상 가장 좋은 형태의 메모리입니다. 에이전트는 자신이 발견한 기존 패턴을 확장하는 것을 좋아하기 때문입니다.

이것은 LLM이 작동하는 방식의 본질이라고 생각합니다. LLM은 다음과 같이 할 가능성이 더 높습니다.

컨텍스트 윈도우(context window)에 있는 것을 사용해 변경하는 것입니다. 그리고 물론 에이전트가 읽고 여는 파일은 컨텍스트 윈도우의 일부입니다. 따라서 코드베이스는 여기서 정말 중요한 역할을 합니다. 에이전트가 모든 PR마다 코드를 리팩터링하지는 않기 때문입니다. 에이전트는 이미 존재하는 것을 살펴보고 그것을 확장할 것입니다.

그다음 단계는 정적 분석(static analysis)입니다. 린터(linter), 컴파일러 진단(compiler diagnostics), 지속적 통합(continuous integration)이 여기에 해당합니다. 이는 코드베이스에 적용할 수 있는 지침과 제약입니다. 에이전트가 계속 같은 실수를 해서 여러분이 수정해 줘야 할 때마다 그 내용을 린트 규칙으로 추가할 수 있습니다. 또는 더 나은 방법으로, 에이전트가 하는 실수 자체가 원천적으로 불가능하도록 코드베이스를 리팩터링할 수도 있습니다.

그보다 한 단계 위로 올라가면, 엄격한 제약과 강제에서 조금 벗어나 지침의 영역으로 들어가기 시작합니다. 규칙(rules), Bugbot, 스킬(skills) 같은 것들이 있습니다. 에이전트는 작업할 때 당연히 때로는, 그리고 대부분은 이것들을 사용합니다. 하지만 여러 이유로 규칙을 읽는 것을 잊을 수도 있고, 에이전트를 조종하는 사용자가 이를 무시할 수도 있습니다. 따라서 이것들은 강제 적용 가능성이 그만큼 높지는 않지만, 에이전트가 하는 일을 실제로 신뢰할 수 있도록 환경을 구성하는 데 중요한 요소이기도 합니다.

마지막으로 스타일 가이드(style guide)가 있는데, 이는 사실상 코드 리뷰(code review)에서 사람이 시행할 수밖에 없습니다. 물론 이것들도 규칙, Bugbot, 스킬에 넣을 수 있습니다. 하지만 그렇게 하지 않으면 리뷰 프로세스에 크고 분명한 구멍이 생깁니다. 사람이 변경된 모든 줄을 하나씩 살펴보고 댓글을 남기는 것을 기억해야 하기 때문입니다. 풀 리퀘스트가 들어오는 속도를 고려하면 이는 불가능해집니다. 따라서 스타일 가이드에만 의존하는 것은 절대 추천하지 않습니다. 무엇이 빠져 있는지 파악하는 출발점으로 스타일 가이드, 또는 사람의 리뷰를 살펴보는 것은 좋다고 생각합니다.

하지만 나머지 네 가지 요소에 대해 생각하는 데 시간을 투자해야 합니다. 코드베이스, 더 나은 데이터 구조나 알고리즘을 통해 문제를 원천적으로 불가능하게 만드는 것, 정적 분석, 그리고 물론 여기에 규칙과 스킬을 계층적으로 추가하는 것입니다.

코드베이스 측면에서 보면, GrokBot 코드베이스에서는 실제로 Dune이라는 것을 구축하는 데 투자했습니다. 이것은 에이전트 친화적인 프레임워크입니다. Dune의 영감은 Cursor 에이전트 창에서 보았던 여러 성능 문제에서 비롯되었습니다. 그 탐색 과정에서 많은 교훈을 얻었지만, 우리가 도달한 핵심 원칙은 에이전트가 지름길을 택하는 것을 좋아한다는 것이었습니다.

그렇다면 지름길, 즉 가장 쉬운 경로가 에이전트에게 올바른 경로가 되도록 프레임워크를 설계하면 어떨까요? 또한 사람이 작업하기에는 할 수 있는 일과 할 수 없는 일이 지나치게 엄격하게 제한되어 꽤 성가신 코드베이스이지만, 특히 컨텍스트가 매우 제한적인 에이전트에게는 완벽한 환경이 되도록 만들면 어떨까요? 이제 코드베이스에 기여하는 모든 사람이 엔지니어일 필요는 없습니다. 디자이너, 제품 관리자, CEO도 코드베이스에 들어가 기능을 출시할 수 있습니다.

따라서 컨텍스트가 많지 않은 바쁜 사람이 조종하는 에이전트라도 기본적으로 좋은 결과를 낼 수 있도록 코드베이스에 어떻게 투자하고 구성할지 많이 고민해야 합니다.

앞서 말했듯이 코드베이스는 에이전트에게 일종의 메모리입니다. 에이전트는 자신이 발견한 기존 패턴을 확장하는 것을 좋아하기 때문입니다. 실제로 그 반대도 맞습니다. 시간을 투자해 나쁜 패턴이 원천적으로 불가능하도록 코드베이스를 구성할 수도 있고, 나쁜 패턴을 막는 린트 규칙을 둘 수도 있습니다. 하지만 그 반대의 경우도 마찬가지입니다. 기존에 안티패턴(antipattern)이 있다면, 그것이 바이러스처럼 퍼지는 것을 보게 될 것입니다.

작은 우회 방법 하나나 그 우회 방법을 설명하는 주석 하나가 있을 수 있습니다. 그러면 에이전트가 그것을 그대로 복사하는 것을 곧 발견하게 될 것입니다. 며칠 또는 몇 주만 지나도 그 우회 방법이 사방으로 퍼지고, 모든 에이전트의 사실상 표준 패턴이 된 것을 보게 될 것입니다. 이는 정말, 정말 나쁜 상황입니다.

이는 에이전트를 수정할 때 코드베이스 변경과 정적 분석을 고민하는 데 시간을 투자하고, 물론 그 이유로 규칙, 좋은 규칙, Bugbot, 스킬을 계층적으로 추가하는 것이 왜 중요한지에 대한 제가 앞서 한 말로 다시 이어집니다.

미슐랭 주방에 더해 제가 좋아하는 또 다른 비유는 코드베이스가 일종의 정원과 같다는 것입니다. 처음에는 무해해 보이는 우회 방법이 있을 수 있습니다. 하지만 에이전트의 특성상 그 패턴을 계속해서 복사하게 되고, 곧 유지 관리가 고통스럽고 성능 문제가 많은, 아주 바이브 코딩된(vibe-coded) 코드베이스가 되어버립니다.

따라서 제 생각에 완벽한 에이전트용 코드베이스는 사람이 코드를 작성하기에는 정말 성가실 정도로 엄격하게 제한되어 있지만, 매우 관례적이고 표준화되어 있어서 무해해 보이는 패턴조차 금지되는 코드베이스입니다.

제가 가진 가장 좋은 예는 겉으로 보면 아주아주 무해해 보이지만, 생각해 보면 실제로는 매우 나쁜 것입니다. 바로 에이전트가 코드에 주석을 남기는 패턴입니다.

에이전트가 처음 이런 일을 하기 시작했을 때, 처음에는 많은 에이전트가 대충 작업한다고 생각했습니다. 하지만 에이전트가 코드에 주석을 남기는 것이 반드시 나쁜 일은 아니라고도 생각했습니다. 인간은 엣지 케이스를 발견했거나, 우회 방법을 구현해야 했거나, 코드베이스에서 특히 까다로운 부분에 대해 자신이나 동료에게 메모를 남기고 싶을 때 코드에 주석을 남겼기 때문입니다.

하지만 Cursor 코드베이스에서 이런 일이 일어나는 것을 보면서 곧 깨달은 것은, 에이전트가 코드 주변의 주석을 실제 문제를 해결하지 않는 이유로 사용하고, 대신 반창고식 처방이나 단기적인 해결책으로 문제를 덮어버린다는 사실이었습니다.

그래서 GrokBot을 구동하는 프레임워크인 Dune에서는 에이전트가 그 패턴을 단순히 복사해 코드베이스 전체로 퍼뜨리지 못하도록 주석을 금지하기로 했습니다.

제가 여기서 주장하고 싶은 것은 모든 팀에 제가 ‘가드너(gardener)’라고 부르는 역할의 사람이 정말 필요하다는 것입니다. 실제 정원과 마찬가지로, 원하지 않는 방식으로 자라거나 침투할 수 있는 것들을 많이 고민하는 사람이 필요합니다. 잡초, 원치 않는 해충, 그 밖의 여러 유기적 성장이 코드베이스에 스며들 수 있습니다. 이것들이 사방으로 퍼지기 전에 싹부터 잘라내야 합니다.

Dune의 많은 원칙은 크게 세 가지에 초점을 맞추고 있습니다.

우선, 방금 말씀드린 이유로 이미 존재하는 기술 부채를 제거하고 싶습니다. 가장 권장되는 패턴을 위한 단일한 포장도로(single paved path)를 유지하거나 강제하고 싶습니다. 일을 처리하는 관례적인 방법이 하나 있어야 에이전트가 추측할 필요가 없고, 코드베이스와 CI, 린트 규칙에 충분한 지침이 있어 에이전트가 그 경로를 따르도록 유도해야 합니다.

그리고 마지막으로, 기술 부채나 나쁜 패턴을 발견할 때마다 본능적으로 “이것에 대한 린트 규칙을 작성해야 한다”고 생각해야 합니다. 항상 즉시 정리할 필요는 없습니다. 린트 규칙을 작성하면 적어도 문제가 더 악화되는 것은 막을 수 있기 때문입니다. 이것이 문제를 완전히 해결하지는 않지만, 적어도 더 커지는 것은 방지합니다.

따라서 안티패턴이 바이러스처럼 퍼지지 않도록 어떻게 막을 수 있을지 정말 고민하고, 동시에 에이전트가 그것들을 정리하도록 하는 데 시간을 투자할 것을 강력히 권합니다. 그래야 코드베이스가 계속해서 에이전트가 복사해도 괜찮은 상태로 유지됩니다. 이것이 제가 권하고 싶은 사고방식입니다.

Dune 자체의 세부 사항을 전부 다루지는 않고, 흥미로운 부분 몇 가지만 간단히 훑어보겠습니다. 다시 말씀드리면 Dune은 GrokBot을 구동하기 위해 우리가 구축한 아키텍처, 즉 클라이언트 프레임워크입니다.

앞서 말한 모든 것에 많은 투자를 했습니다. 코드가 어디에 위치해야 하는지, 애플리케이션의 서로 다른 부분 사이에서 코드를 어떻게 임포트해야 하는지에 관한 규칙도 포함됩니다. Dune 애플리케이션에는 서로 다른 개념들이 있습니다. 예를 들어 기능(feature)은 모두 하나의 폴더에 함께 배치됩니다. React 코드 부분에는 엔트리 포인트(entry point)가 있고, 이것이 일종의 라우트(route)라고 생각할 수 있는 것을 결정합니다.

GrokBot 애플리케이션에 표시되는 트랜스크립트 카드(transcript card)가 있습니다. GrokBot 가상 머신에서 실행되는 호스트(host)가 있습니다. 그리고 물론 전체 Dune 애플리케이션을 구동하는 클라이언트(client)가 있습니다.

이들 사이에는 엄격한 경계를 많이 두고 있습니다. 예를 들어 Electron의 메인 프로세스, 또는 메인 스레드에서 실행되는 것은 렌더러 스레드에서 실행될 수 없습니다. Cursor의 에이전트 창에서 얻은 교훈에 따라 이러한 분리를 매우 의도적으로 유지하고 있습니다. 코드가 실수로 렌더러 스레드에 임포트되어 코드 실행을 느리게 만드는 경우를 가끔 보았기 때문입니다.

UI가 렌더 스레드(render thread)에서 매우 부드럽고 성능 좋게 작동하길 원한다면, 60프레임/초를 목표로 할 때는 16밀리초보다 오래 걸리는 장기 작업(long task)이나 그런 작업이 없어야 하고, 120프레임/초를 목표로 한다면 8밀리초보다 오래 걸리는 작업이 없어야 합니다.

렌더러는 모든 작업을 한 번에 처리하는 대신 작업을 잘게 나눌 수 있는 상태를 항상 유지해야 합니다. Dune에는 import 및 의존성 그래프를 통해 이러한 경계를 강제하는 코드가 있습니다.

이것은 성능을 매우 나쁘게 만든 패턴의 한 예일 뿐이며, 우리는 Dune의 아키텍처를 통해 이를 단호하게 제거했습니다.

이 외의 요소들은 그다지 흥미롭지 않지만, 다시 말해 여기서 핵심 주제는 Dune이 아닙니다. 자신만의 에이전트 친화적인 프레임워크를 만드는 것이 매우, 매우 강력하다는 아이디어입니다. 여러분과 팀의 최고 엔지니어들이 경험적으로 알고 있는 모든 지식을 코드에 담을 수 있습니다.

제가 생각하는 교훈은 이렇습니다. 엔지니어들이 다른 엔지니어의 작업을 검토하고 의견을 남기는, 과거의 스타일 가이드 프로세스에서 그 지식을 어떻게 분리해 내고, 거의 추출하듯이 뽑아내서 프레임워크와 코드베이스 자체에 인코딩할 것인가?

그렇게 하면 코드베이스가 기억으로 작동합니다. 이 아이디어로 돌아가면, 코드베이스는 에이전트가 확장하길 바라는 상태를 구체화한 스냅샷입니다. 코드베이스가 아주 정제되고 훌륭해서, 다음에 오는 에이전트가 그 패턴을 계속 따르고 이를 정말, 정말 좋은 상태로 유지할 가능성이 높아야 합니다.

제가 말씀드린 것처럼 이 과정에 충분한 시간을 투자하면, 미슐랭 주방이나 소프트웨어 공장을 실제로 구축할 수 있습니다. 에이전트를 신뢰할 수 있게 해주는 이 모든 요소에 많은 시간을 투자했기 때문입니다. 코드베이스든…

린트 규칙, 진단, 규칙, Bugbot, 스킬이든, 이런 계층들이 함께 작동해 큰 신뢰를 제공합니다. 잠시 GrokBot 코드베이스에서 작업한다고 상상해 보세요. 모든 것이 매우 엄격하게 통제되어 있어서 나쁜 코드를 작성하기가 거의 불가능합니다. 따라서 맥락이 거의 없거나 추론 능력이 뛰어나지 않은 에이전트라도 들어와서 실제로 좋은 코드를 작성할 수 있습니다.

미슐랭 주방에 대한 제 예로 돌아가면, 여기에는 많은 시사점이 있다고 생각합니다. 우리는 에이전트와 봇에 스킬과 도구를 설정해 주고 있습니다. 이들을 훈련하며, 에이전트와 봇이 기본적으로 올바른 일을 하도록 주방을 합리적인 방식으로 구성하고 있습니다.

예를 들어 주방에서 요리사나 설거지 담당자 중 한 명이 계속 무언가에 걸려 넘어지는 것을 본다면, 당연히 그것을 고쳐야 합니다. 다른 사람들도 넘어지지 않도록 문제를 해결해야 합니다. 주방은 매우 위험한 장소이고 다치고 싶지 않기 때문입니다. 코드베이스에도 같은 관점을 적용해야 한다고 생각합니다. 지식이 많지 않은 에이전트라도 일을 잘할 수 있도록 어떻게 구성할 것인가?

GrokBot과 Cursor는 함께 흥미로운 역할을 한다고 생각합니다. GrokBot은 제가 ‘외부 루프(outer loop)’라고 부르는 것을 제공하는 데 매우 뛰어납니다. Slack, Datadog, Sentry, PlanetScale 또는 여러분이 사용하는 어떤 서비스든 다양한 커넥터를 GrokBot에 연결할 수 있기 때문입니다. 그 모든 정보를 한데 모아 스스로 매우 좋은 의사결정을 내리는 데 사용할 수 있습니다.

어떤 사람들은 이것을 회사의 두뇌(company brain)라고 부릅니다. 하지만 저는 여기서 그렇게 정교한 것이 필요하다고 생각하지 않습니다. 에이전트는 도구를 매우 잘 사용하기 때문입니다. 이러한 도구들을 GrokBot에 연결하고 Claude 에이전트 같은 것들을 GrokBot이 자동으로 실행하게 만들기 시작하면, 소프트웨어 공장을 구축하기 위해 많은 인프라에 투자할 필요가 실제로 없다는 것을 알게 될 것입니다.

사실 이 용어에는 줄을 긋겠습니다. 저는 이 표현을 좋아하지 않기 때문입니다. GrokBot을 통해 자신만의 개인적인 미슐랭 주방을 구축할 수 있다고 생각합니다. 예를 들어 GrokBot 루틴을 사용하면 Slack 스레드와 Sentry 알림을 구독하고 작업을 자동으로 시작할 수 있습니다.

지금까지 말씀드린 모든 것, 즉 코드베이스와 규칙, 스킬을 결합하면 이 모든 요소가 서로의 효과를 누적시킵니다. GrokBot은 외부 루프에서 발생하는 이벤트에 자동으로 응답한 다음 Claude 에이전트를 실행할 수 있습니다. Cursor 자동화를 설정할 수도 있고, SDK를 사용해 추가적인 봇을 설정할 수도 있습니다. 이 봇들은 여러분이 구축한 에이전트 인프라의 많은 구성 요소를 재사용하면서 훨씬 더 복잡한 작업을 수행할 수 있습니다.

이 모든 것을 해냈다면, 우리가 Cursor에서 작동하는 일부 자동화와 에이전트의 스크린샷을 여기 보여드렸는데, 버그 리포트를 자동으로 재현하고, 풀 리퀘스트를 자동으로 열며, 본질적으로 팀 전체에 큰 가치를 더하는 단계에 도달할 수 있다고 생각합니다. 이 모든 요소가 서로의 효과를 누적시키기 때문입니다.
