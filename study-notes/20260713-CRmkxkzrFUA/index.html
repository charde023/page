AI 코딩 에이전트의 진짜 최적화 대상은 토큰이나 CPU가 아니라 사람이 얼마나 자주 개입해야 하는가이며, Peter는 전사 공유, 자동 리뷰, 격리 실행환경(Crabbox)으로 그 개입 지점을 줄인다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
사람의 집중력(Attention) 병목 AI가 코드를 많이 만들수록 사람이 검토하고 판단해야 할 양이 폭증한다 에이전트 시대의 핵심 병목은 “사람이 언제 끼어드느냐”다
에이전트 전사(Transcript) 공유 PR 작성자가 실제로 얼마나 이해하고 작업했는지 판단하는 근거가 된다 PR에 작업 대화 기록을 붙이면 리뷰 신뢰도가 올라간다
자동 리뷰(Auto Review) 별도 리뷰 에이전트의 피드백을 원래 작업 세션으로 되돌려 맥락을 살린다 리뷰는 “새 세션”보다 “기존 맥락을 가진 세션”에 돌려줘야 한다
격리 실행환경(Crabbox) 로컬 컴퓨터 CPU를 태우지 않고 테스트·설치·브라우저 검증을 독립 환경에서 수행한다 에이전트에게 깨끗한 테스트 머신을 제공하면 검증 품질이 오른다
루프(Loop)와 워크플로(Workflow) 이슈 생성부터 검증, PR, 리뷰, 수정까지 에이전트가 이어서 처리할 수 있다 루프는 거창한 개념이라기보다 자동화된 작업 흐름이다
시각 검증(Visual Verification) 코드만 보는 대신 전후 화면, GIF, 브라우저 결과로 버그 수정 여부를 확인한다 비개발자도 결과 화면을 보고 피드백할 수 있다

내가 모를 만한 것 / 처음 보는 것

  • OpenClaw — Peter가 만든 오픈소스 프로젝트로, AI 코딩 에이전트를 활용한 PR·이슈 워크플로를 실험하는 맥락에서 언급된다.
  • 스킬(Skill) — 에이전트에게 특정 작업법을 알려주는 작은 지침 묶음. 예: 전사 찾기, 정리, PR 설명에 붙이기.
  • 전사(Transcript) — 사람과 AI 코딩 에이전트가 나눈 대화 기록. PR의 의도와 노력 정도를 판단하는 자료가 된다.
  • 정제된 전사(Sanitized Transcript) — 민감정보를 제거한 대화 기록. 완벽하진 않지만 PR 검토에 유용하다.
  • 자동 리뷰(Auto Review) — Codex, Claude, OpenCode 같은 다른 CLI 도구를 호출해 코드 리뷰를 받고, 피드백을 다시 원래 코딩 세션에 전달하는 방식.
  • 불변조건(Invariant) — 에이전트가 과도하게 수정하지 않도록 “앱 시작 후 이 파일들은 바뀌지 않는다” 같은 전제 조건을 명시하는 것.
  • Crabbox — 에이전트용 격리 실행 박스. 저장소 변경사항을 동기화하고 CI와 유사한 환경에서 테스트를 실행한다.
  • VNC — 원격 화면 접속 방식. Crabbox 안에서 실행되는 깨끗한 환경을 사람이나 다른 팀원이 클릭하며 확인할 수 있게 한다.
  • 컴퓨터 사용(Computer Use) — AI가 화면을 보고 클릭하고 입력하는 기능. Peter는 Crabbox로 저렴한 방식의 컴퓨터 사용을 구현했다고 말한다.
  • GitHub Actions — GitHub의 CI/CD 자동화 도구. Crabbox는 기존 CI 상태와 유사하게 시작해 테스트를 돌릴 수 있다.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 작년에는 토큰(Token)이 병목이었고, OpenAI로 옮기며 해결했다고 말한다 — 이후 병목은 CPU, 지금은 집중력(Attention)으로 바뀌었다.
  2. 일부 사람들은 코딩 에이전트에 “fix + 번호”만 입력해 PR을 만든다고 한다 — 이런 PR은 4,000줄짜리일 수도 있어 리뷰어 입장에서는 신뢰 판단이 어렵다.
  3. PR에 정제된 전사(Sanitized Transcript)를 붙이면 리뷰받을 확률이 높아진다고 말한다 — 작업자가 1분만 프롬프트했는지, 1시간 동안 고민했는지 구분할 수 있기 때문이다.
  4. 전사 업로드 기능은 복잡한 훅(Hook)이 아니라 기본 스킬(Default Skill)로 구현했다 — 저장소를 체크아웃하면 에이전트가 자동으로 해당 스킬을 알게 된다.
  5. 자동 리뷰는 PR 또는 커밋(Commit)을 만들 때 기본 스킬이 로드되도록 했다 — 시스템에 있는 Codex, Claude, Pi, OpenCode 등을 찾아 CLI로 호출한다.
  6. 리뷰 피드백을 원래 코딩 세션으로 돌려보내는 것이 핵심이다 — 원래 세션이 가장 많은 맥락(Context)을 갖고 있기 때문이다.
  7. Crabbox는 로컬 MacBook의 CPU 과부하 문제에서 출발했다 — 여러 코딩 세션을 동시에 돌리면 노트북 팬이 미친 듯이 돌고 느려졌다고 한다.
  8. Crabbox는 약 30개 제공자(Provider)를 지원한다고 한다 — 보안이 높은 회사 환경, OpenAI, Parallels 같은 특이한 환경까지 언급한다.
  9. 처음에는 macOS 중심이었지만, 이후 Windows와 Linux 지원을 추가했다 — 에이전트가 “이 OS에 OpenClaw를 설치해줘”라는 요청을 처리할 수 있다.
  10. Crabbox 환경은 공유 가능하다 — 링크를 보내면 조직 내 다른 사람이 VNC 세션을 열어 새 기능을 직접 클릭해볼 수 있다.
  11. Slack 같은 피드백 채널에서 “이 기능 어때?”라는 의견이 나오면 봇이 구현 후 VNC 링크를 답하는 흐름을 상상한다 — 비개발자도 실제 결과를 보고 아이디어가 좋은지 판단할 수 있다.
  12. PR 등급 봇이 1~5점을 주었는데, 사람이 2점을 5점으로 수동 수정한 사례가 있었다고 한다 — 전사나 평가도 조작 가능성을 배제할 수 없다.
  13. 에이전트는 국소 문제에는 강하지만 “큰 그림에 어떻게 맞는가”는 아직 약하다고 본다 — 그래서 사람의 사고와 제품 판단은 여전히 필요하다.

# 섹션 요지
1 병목의 변화 토큰과 CPU는 해결 가능했지만, 이제 가장 큰 병목은 사람의 집중력이다
2 PR 전사 공유 에이전트 작업 대화 기록을 PR에 붙여 리뷰어가 신뢰도를 판단하게 한다
3 자동 리뷰 리뷰 결과를 원래 코딩 세션에 되돌려 맥락 있는 수정과 의사결정을 하게 한다
4 Crabbox 테스트와 실행을 격리 환경에서 수행해 로컬 자원 부담과 환경 오염을 줄인다
5 시각 검증과 공유 브라우저·스크린샷·VNC로 결과물을 직접 확인하고 비개발자도 피드백하게 한다
6 루프와 인간 개입 에이전트 루프를 길게 만들수록 사람은 최종 판단과 큰 그림에 집중할 수 있다
7 한계 에이전트는 아직 제품적 판단, 시스템 전체 맥락, 사고 부담을 완전히 대체하지 못한다

1. 병목은 토큰과 CPU에서 사람의 집중력으로 이동했다

Peter는 AI 코딩을 하며 병목이 계속 바뀌었다고 말한다.

처음에는 토큰(Token) 이 부족했다. 긴 작업을 맡기면 대화 맥락이 부족하거나 모델이 충분히 처리하지 못했다. 이후 OpenAI 쪽으로 옮기면서 이 문제는 어느 정도 해결했다고 본다.

다음 병목은 CPU였다. 여러 에이전트 세션을 동시에 돌리면 로컬 MacBook이 느려지고 팬이 크게 돌았다. 테스트, 빌드, 설치 같은 무거운 작업이 로컬 자원을 잡아먹었기 때문이다.

그다음 병목은 사람의 집중력(Attention) 이다. AI가 코드를 더 많이 만들수록, 사람이 확인해야 할 PR과 이슈, 리뷰 결과가 많아진다. 그래서 Peter가 지금 최적화하려는 것은 “에이전트가 얼마나 똑똑한가”보다 내가 얼마나 자주 루프 안에 들어가야 하는가다.

핵심은 에이전트의 능력을 프롬프트 작성에서 끝내지 않고, 검증·리뷰·수정·공유까지 확장하는 것이다.

2. PR에 에이전트 대화 전사를 붙여 신뢰도를 높인다

Peter가 소개한 첫 번째 도구는 OpenClaw에서 쓰는 전사 공유 스킬(Transcript Skill) 이다.

오픈소스 저장소에는 많은 PR이 들어온다. 문제는 어떤 PR은 사람이 깊이 고민해 만든 것이 아니라, 코딩 에이전트에게 “fix 123” 같은 식으로 짧게 지시한 결과물일 수 있다는 점이다. 그런데 이런 PR도 4,000줄짜리로 커질 수 있다. 리뷰어는 이 PR이 진지한 작업인지, 단순 자동 생성 결과인지 판단하기 어렵다.

그래서 Peter는 PR을 만들 때 에이전트와의 대화 기록, 즉 전사(Transcript) 를 PR에 붙이도록 했다. 단, 민감정보는 제거한 정제된 전사(Sanitized Transcript) 다.

이 전사는 두 가지 점에서 유용하다.

첫째, 리뷰어가 작업자의 이해도와 노력 정도를 추정할 수 있다.
1분 동안 대충 프롬프트한 것인지, 1시간 동안 문제를 파고든 것인지 알 수 있다.

둘째, 사람뿐 아니라 다른 에이전트도 전사를 읽고 맥락을 이해할 수 있다.
PR 설명만 보는 것보다, 어떤 의도로 어떤 대화를 거쳐 결과가 나왔는지 보는 편이 더 낫다.

처음에는 Peter도 훅(Hook)이나 복잡한 자동화를 고민했지만, 결국 단순한 스킬(Skill) 로 구현했다. 에이전트에게 “전사를 어디서 찾고, 어떻게 정제하고, PR이나 이슈에 붙이는지” 알려주면 됐다. 그는 자신이 프로젝트의 “자비로운 종신 독재자(Benevolent Dictator for Life)”이므로 이 스킬을 기본값으로 넣었다고 농담한다.

3. 자동 리뷰는 원래 작업 세션으로 피드백을 되돌려야 한다

두 번째 도구는 Peter가 가장 좋아한다고 말한 자동 리뷰(Auto Review) 스킬이다.

일반적인 흐름은 이렇다.

  1. 에이전트가 코드를 만든다.
  2. PR을 생성한다.
  3. 다른 에이전트가 새로 떠서 리뷰한다.
  4. 리뷰 결과를 사람이 보거나 다른 세션에서 수정한다.

Peter는 이 방식이 느리고 실용성이 떨어진다고 본다. 특히 새 리뷰 세션은 원래 작업의 맥락을 충분히 모른다. 겉으로 보기에는 문제가 있어 보이는 부분도, 실제로는 설계상 의도된 결정일 수 있다.

그래서 Peter의 자동 리뷰 스킬은 PR이나 커밋 시점에 CLI를 호출한다. 시스템에 설치된 Codex, Claude, Pi, OpenCode 등을 찾아 “이 변경사항을 리뷰해줘”라고 요청한다.

중요한 점은 리뷰 결과가 원래 코딩 세션으로 돌아간다는 것이다. 원래 세션은 지금까지의 대화, 제약 조건, 설계 의도를 가장 많이 알고 있다. 따라서 리뷰 의견을 보고 이렇게 판단할 수 있다.

  • “맞다, 이건 고쳐야 한다.”
  • “아니다, 이건 의도된 설계다.”
  • “겉보기에는 문제지만 이 제약 때문에 유지해야 한다.”

또한 Peter는 이 판단 결과를 PR 설명에 반영하게 했다. 예를 들어 자동 리뷰가 특정 부분을 지적했지만, 원래 세션이 “이건 의도된 결정”이라고 판단했다면 그 내용을 PR 설명에 남긴다. 그러면 다음 리뷰어가 같은 부분을 다시 잘못 고치지 않는다.

4. Crabbox는 에이전트에게 깨끗한 실행 박스를 준다

세 번째이자 Peter가 가장 좋아하는 도구는 Crabbox다.

AI 코딩을 많이 하다 보면 여러 장기 실행 세션(Long-running Session)을 동시에 돌리게 된다. 한 세션이 테스트를 돌리고, 다른 세션이 빌드하고, 또 다른 세션이 설치를 시도한다. 그러면 MacBook CPU가 과부하되고 전체 작업이 느려진다.

Peter는 한때 여러 대의 Mac을 사용했다. 로컬 컴퓨터, 클라우드 Mac, Mac Studio 등 여러 기계를 나눠 썼지만 이것도 번거롭고 이상적인 해결책은 아니었다.

Crabbox는 에이전트에게 작은 격리 실행환경을 제공한다. 저장소의 변경사항을 동기화하고, GitHub Actions 같은 CI 환경과 유사한 상태에서 테스트를 실행한다. 무거운 작업은 로컬 컴퓨터가 아니라 이 박스 안에서 수행된다.

Crabbox의 장점은 다음과 같다.

  • 로컬 CPU 부담을 줄인다.
  • 깨끗한 환경에서 설치와 테스트를 검증한다.
  • 기존 CI와 비슷한 출발 상태를 만든다.
  • 여러 OS 환경에서 재현성을 높인다.
  • 에이전트가 직접 실행·검증할 수 있는 공간을 갖는다.

Peter는 Crabbox가 약 30개 제공자(Provider)를 지원한다고 말한다. 회사 보안 정책이 엄격한 환경, OpenAI, Parallels 같은 환경도 언급한다. 핵심은 팀이나 회사가 선호하는 실행 제공자를 선택할 수 있다는 점이다.

5. 깨끗한 OS에서 설치와 브라우저 검증까지 시킨다

Crabbox는 처음에는 macOS 중심으로 출발했지만, Peter는 Windows와 Linux 지원도 추가했다.

이유는 단순하다. 내 컴퓨터에서 테스트하면 이미 여러 설정이 되어 있을 수 있다. 과거에 설치한 패키지, 설정 파일, 권한, 캐시 때문에 실제 신규 사용자 환경과 다르다. 그래서 “내 컴퓨터에서는 된다”는 착각이 생긴다.

Peter가 원하는 것은 깨끗한 머신(Fresh Machine) 에서 정말 설치와 실행이 되는지 확인하는 것이다.

예를 들어 에이전트에게 이렇게 시킬 수 있다.

  • “이 OS에 OpenClaw를 설치해줘.”
  • “브라우저를 열고 이 기능을 확인해줘.”
  • “설정 화면을 열고 이 옵션을 바꿔줘.”
  • “전후 화면을 캡처해서 비교해줘.”

Crabbox에는 화면을 보고 클릭할 수 있는 기능도 있다. Peter는 이를 저렴한 방식의 컴퓨터 사용(Computer Use) 이라고 표현한다. 에이전트는 스크린샷을 보고 클릭하고, 브라우저를 열고, 설정을 바꾸고, 결과를 확인할 수 있다.

일반적인 컴퓨터 사용 방식은 내 마우스 커서나 포커스와 충돌할 수 있다. 반면 Crabbox는 별도의 깨끗한 박스에서 돌고, 사람은 VNC로 접속해 보기만 하면 되기 때문에 더 편하다고 설명한다.

6. 실행환경을 링크로 공유하면 비개발자도 검증할 수 있다

Crabbox의 또 다른 장점은 환경을 공유할 수 있다는 점이다.

새 기능을 테스트하기 위한 실행환경을 만들고, 그 링크를 친구나 팀원에게 보낼 수 있다. 인증은 GitHub 조직(Organization)을 사용할 수도 있고, 다른 인증 계층을 붙일 수도 있다. 링크를 받은 사람은 VNC 세션에 접속해 실제 기능을 클릭해볼 수 있다.

Peter는 가상의 예로 피드백 채널을 든다.

누군가 Slack 같은 곳에서 “이 기능 있으면 좋지 않을까?”라고 말한다. 그러면 봇이 “제가 구현해볼게요”라고 답하고, 잠시 후 VNC 링크를 준다. 코드를 모르는 사람도 그 링크를 열어 실제 기능을 눌러본다. 그리고 깨닫는다.

  • “아, 이거 별로 좋은 아이디어가 아니었네.”
  • “아니면 이렇게 바꾸면 괜찮겠네.”
  • “생각보다 진짜 유용하네.”

이 흐름의 가치는 크다. 모든 피드백을 개발자가 직접 읽고 판단할 필요가 줄어든다. 일부 아이디어는 에이전트와 비개발자 검증만으로 걸러진다. 개발자는 이미 어느 정도 검증된 피드백만 보면 된다.

AI 에이전트의 루프가 길어질수록, 사람은 코드 작성보다 제품 판단과 최종 승인에 더 집중할 수 있다.

7. 루프는 거창한 말이 아니라 워크플로다

질문자가 “루프(Loop)를 사용하느냐”고 묻자 Peter는 루프라는 말이 사실 워크플로(Workflow) 의 멋진 표현에 가깝다고 답한다.

예를 들어 OpenClaw 오픈소스 저장소에 이슈가 생성되면 에이전트가 먼저 그 아이디어가 좋은지 나쁜지 검토한다. 이때 프로젝트 방향을 적은 vision.md 같은 문서를 기준으로 삼는다.

에이전트가 괜찮은 아이디어라고 판단하면 PR을 만든다. 그다음 다른 에이전트가 PR을 리뷰한다. 필요하면 PR을 수정하고, 병합 가능한 상태로 만든다.

이런 구조 덕분에 Peter가 나중에 오픈소스 프로젝트를 볼 때는 “이건 이미 처리됐고, 병합 준비가 됐다”는 상태로 확인할 수 있다. 그는 20분 동안 코딩 에이전트가 작업하는 스트림을 지켜볼 필요가 없다.

8. 인간 개입은 줄었지만, 사고 부담은 사라지지 않았다

Peter는 처음 AI 코딩을 시작했을 때는 모델이 원하는 대로 움직이지 않아 Claude에게 소리를 지르는 시기였다고 말한다. 지금은 좀 다르다. 앞에서 더 많이 생각하고, 작업은 에이전트가 1시간 또는 10시간 동안 수행할 수 있다.

Crabbox가 있으면 시각 검증도 쉬워진다. 예를 들어 버그 수정 전후 상태를 GIF로 만들 수 있다. GitHub에서 비디오가 잘 안 되면 GIF로 만들어, 프롬프트부터 결과 화면까지 확인한다. 사람은 “여기 버그가 있었고, 여기서 고쳐졌네”를 보고 병합 버튼을 누를 수 있다.

하지만 Peter는 집중력 문제를 완전히 해결했다고 보지는 않는다. 에이전트에게 더 많은 도구를 주면 베이비시팅(Babysitting)은 줄어든다. 그러나 “이게 정말 우리가 원하는 것인가?”라는 판단은 여전히 사람이 해야 한다.

9. 에이전트의 한계: 큰 그림과 제품 감각

마지막에 Peter는 현재 워크플로에서 가장 불편한 점이 “아직도 너무 많은 생각이 필요하다”는 것이라고 말한다.

AI 에이전트 덕분에 더 많은 코드를 생산하고, 더 복잡한 시스템을 만들 수 있다. 하지만 그만큼 전체 구조를 이해하고 판단해야 할 부담도 커진다.

에이전트는 특정 문제 하나에 집중하는 데 강하다. 그러나 그 문제가 전체 제품, 아키텍처, 사용자 경험, 장기 방향과 어떻게 맞물리는지는 아직 잘 보지 못한다. Peter는 에이전트가 마치 시야가 좁은 말처럼 한 방향만 본다고 표현한다. 그래서 사람이 계속 주변을 보게 만들어야 한다.

결론적으로 Peter의 방식은 에이전트에게 더 많은 일을 맡기는 방법이지만, 사람을 없애는 방법은 아니다. 사람은 덜 자주 개입하되, 더 중요한 지점에서 판단해야 한다.
