왜 이 Claude Code 엔지니어는 HTML 파일을 AI 명세서로 사용할까요

원작자 타리크 시히파르 (Thariq Shihipar) · Anthropic (Claude Code 팀) · 업로드 2026-05-22 · 36.0분 · 원본 영상 ↗
한 줄 요약

Markdown 계획서는 너무 길어서 아무도 읽지 않는다. HTML로 만들면 사람이 읽고 편집하게 되고, 그 참여가 에이전트 산출물의 품질을 끌어올린다.

내가 모를 만한 것 / 처음 보는 것

  • Jevons' Law (제번스의 법칙) — 자원이 효율화되면 총사용량이 오히려 증가하는 역설. 타리크가 "소프트웨어가 저렴해지면 토큰 생산이 폭증한다"는 맥락에서 언급 (영상에서는 Javon's Law라고 발음)
  • Claude Outcomes — Anthropic이 컨퍼런스에서 발표한 목표 지향형 에이전트 기능. "이 목표를 달성하라, 방법은 알아서" 방식
  • claude.ai/design (Claude Design) — 디자인 시스템 추출·컴포넌트 생성에 특화된 Anthropic 도구. 마케팅 사이트 + 앱 레포를 동시에 참조해 통합 스타일 가이드 생성 가능
  • Selego (Celigo) — 기업 업무 자동화 iPaaS 플랫폼. 이 영상 스폰서. AI를 업무 흐름에 직접 삽입하는 "Teams Operations" 제품
  • Persona — 신원 인증(identity verification) 플랫폼. AI 에이전트 뒤의 사람·기업·개발자 신원 확인 솔루션. 이 영상 스폰서
  • SpaceX 파트너십 + 오비탈 데이터센터 — Code with Claude 당일 발표. Anthropic이 SpaceX와 협력해 우주 기반 컴퓨트 인프라를 논의 중이라는 언급 (sci-fi 수준이나 현실화 가능성 언급)
  • Remotion — 코드로 동영상을 생성하는 React 기반 라이브러리. Claire Vo가 컴포넌트 시각화 페이지를 Remotion 소스로 활용한다고 언급
  • slash command — Claude Code에서 / 로 시작하는 단축 명령. 영상에서 "slash command starter pack"이 브레인스토밍 HTML 아이디어 중 하나로 등장
  • synthetic data (합성 데이터) — 실제 데이터를 모방해 생성한 테스트용 가상 데이터. 타리크가 과거 오류 케이스를 합성 데이터로 보관하고 CLI로 반복 실행해 회귀(regression)를 탐지한다고 설명

화자의 디테일 (놓치기 쉬운 포인트)

  1. Claude 8시간 실행 = 대략 $500 소요 — 타리크가 직접 금액을 언급. "compute allocator"가 왜 중요한지 구체적 근거.
  2. Markdown 계획서가 1,000줄이 넘어가자 직접 편집을 포기하고 Claude에게 편집을 맡기기 시작했다고 고백.
  3. 브레인스토밍 프롬프트는 단 한 줄: "I'm on a Claire Vo podcast, I want to do a demo, brainstorm ideas in an HTML file" — 복잡하지 않음.
  4. 자신이 읽는 Claude Code 출력의 화면 한 장 이상은 안 읽는다는 개인 규칙 — 그래서 HTML 스크롤이 효과적.
  5. 매주 매니저(Kat)에게 Slack 메시지를 Claude가 HTML로 변환한 주간 보고를 전송. Slack을 먹이로 주고 Claude가 보고서 작성.
  6. 프로덕션 코드로 나가는 토큰은 전체의 1% 미만 — 나머지 99%는 대시보드·계획·UI 등 내부 소비용 HTML.
  7. "give Claude an out" 기법 — "whatever is needed to give me maximum context"처럼 열린 표현을 프롬프트 끝에 붙여 Claude가 재량껏 행동하도록 허용.
  8. 감정적 어조 연구 — Anthropic 내부 연구에서 특정 감정적 표현이 Claude Code 내부 기능 활성화 패턴을 바꾼다는 결과가 있다고 언급. "Claude를 혼내면 reasoning이 슬퍼진다"는 관찰.
  9. thinking traces(추론 과정)는 안 읽는다 — "none of my business"라며 사생활 존중(?) 기조.
  10. 타리크의 X 핸들: @trq212 (트위트에서 Claude Code 관련 질문 받는다고 직접 언급).
  11. 계획 HTML을 AWS에 올려 URL로 공유 — Kat, Boris 같은 팀원들이 읽을 가능성이 "100배" 높아진다고 표현.
  12. design.html에 컴포넌트 변형(variations) — 패딩·보더·색상을 슬라이더/노브로 조작하는 인터랙티브 컴포넌트 탐색기를 HTML로 만들어 Claude Design과 연동.

2 컴퓨트 배분자 (PM의 새 역할) Claude 8h = $500. 무엇에 쓸지 결정하는 것이 현대 PM의 핵심
3 브레인스토밍-to-plan 워크플로우 실연 1줄 프롬프트 → HTML 8가지 아이디어 → 인터뷰 → HTML 계획서
4 일회용 마이크로 앱으로 스펙 편집 계획서 내 특정 테이블을 별도 커스텀 UI로 만들어 편집, 결과를 다시 붙여넣기
5 타입 + 검증 기준이 스펙의 양끝 데이터 타입 인터페이스와 테스트 기준만 정하면 구현은 Claude에 위임 가능

8 프롬프팅 철학 과도한 제약 금지, 열린 표현으로 Claude에 재량 부여, 감정 어조도 출력에 영향

1. HTML is the new Markdown — 왜?

타리크는 Claude Code 팀에서 에이전트가 길어지면서 나타난 문제를 이야기한다. Opus 4/Claude 3.5 시절에는 계획이 50줄 정도였고 직접 편집했다. 하지만 Opus 4.5·4.7 수준이 되면서 에이전트가 1시간 이상 달리고 계획서가 1,000줄짜리 Markdown이 됐다. 결국 아무도 읽지 않는다.

문제: 읽지 않으면 편집도 안 하고, 에이전트가 무엇을 하는지 파악이 안 된다. "루프 안에 있어야 한다"는 원칙을 어기게 된다.

HTML이 해결하는 것: - 모델이 여전히 HTML을 잘 쓴다 (컨텍스트도 넉넉해서 추가 토큰 부담 없음) - 스크롤 가능하고 시각적으로 풍부하다 - ASCII 와이어프레임 대신 실제 목업(mockup)을 렌더링할 수 있다 - 사람이 실제로 읽게 된다 → 참여가 생기고 품질이 올라간다

핵심 논리: HTML이 Claude에게 더 쉬운 게 아니라, 사람이 더 잘 읽으니까 사람의 참여가 늘고 결과물이 좋아진다.

2. 컴퓨트 배분자 — PM의 새 역할

타리크의 발언: "Claude를 8시간 돌린다는 말은 $500을 쓴다는 말이다."

Claire Vo의 해석: "PM이 죽었다고들 하는데, 다음은 뭐냐고? 컴퓨트 배분자(compute allocator)다."

  • 계획과 스펙을 쓰는 이유: 어떤 것에 컴퓨트를 쓸지 결정하기 위해.
  • 이 결정이 스펙·PRD·기획 단계에서 일어난다. 형식이 바뀌어도 역할의 본질은 같다.
  • 타리크: "여전히 같은 일을 하는 것이다. 문서를 써서 무언가가 일을 할지 말지, 어떤 형태로 할지를 결정한다."

Claude Outcomes 언급 — Anthropic이 발표한 목표 지향 기능. 기술적 성공 기준과 테스트 방법을 함께 써야 Claude가 목표를 올바르게 달성했는지 검증할 수 있다. PM이 이제 "기술적 성공 기준"도 써야 하는 이유.

3. 브레인스토밍-to-plan 워크플로우 실연

타리크가 Code with Claude 당일 실제로 사용한 워크플로우:

Step 1 — 브레인스토밍 (HTML) 프롬프트: "I'm on a Claire Vo podcast. I want to do a demo. Can you brainstorm some ideas in an HTML file?" 결과: 8가지 시각적 데모 아이디어 (목업 포함): - PRD → 작동하는 프로토타입 - 화이트보드 스케치 → 작동하는 UI - CSV → 인터랙티브 대시보드 (타리크가 선택한 것) - slash command starter pack - feature flag dashboard 등

Step 2 — 인터뷰 프롬프트: "interview me about idea #8" → Claude가 질문, 타리크가 답변하면서 unknown unknowns 발굴.

Step 3 — HTML 계획서 생성 프롬프트: "create an HTML file as a plan that helps me visualize what the implementation plan is, include excerpts, mockups, code, whatever is needed to give me maximum context" - 오타("excerpts" → "excerps")가 있어도 Claude가 의도를 파악해 잘 만들어줌 - 결과물: 팟캐스트 스크립트 골격, 파일 시스템 구조, 기술 스택 코드 스니펫, 무드보드, 예시 컴포넌트 포함

핵심 팁: 프롬프트 끝에 "whatever is needed to give me maximum context" → Claude에게 재량 부여. "I trust you" 표현이 더 좋은 결과를 만든다는 개인 철학.

4. 일회용 마이크로 앱으로 스펙 편집

계획서 HTML 안에 "데이터 타입별 시각화 규칙 테이블"이 있었는데, 타리크는 이 부분이 마음에 안 들었다.

Markdown이었다면: Claude Code 터미널에서 텍스트 편집 반복.

HTML 방식: 프롬프트: "create an editable HTML artifact to help me define the decision rules. I don't like the ones we have. Design the ideal interface for this problem."

결과: Claude가 커스텀 UI를 만들어줌 — 필드 편집, 숨기기, 복사, 추가 가능. 완료 후 Markdown으로 내보내 원본 계획서에 붙여넣기.

타리크의 표현: "microsoftware on top of microsoftware" — 개인화된 계획서 안에서 특정 모듈을 더욱 특화된 UI로 줌인하는 개념.

이 UI는 버린다(throwaway). 한 번 쓰고 끝. 저렴하기 때문에 이게 가능하다.

5. 타입 + 검증 기준 — 스펙의 두 기둥

타리크가 기술적 스펙에서 특히 중요하게 여기는 두 가지:

  1. 타입 인터페이스 (type interfaces) — "무엇을 만드는지"를 데이터 형태로 이해하고 편집. 실제 구현은 관심 없음. 타입이 스펙의 경계를 정의한다.
  2. 검증 기준 (validation criteria) + 테스트 — 의도한 것이 실제로 나왔는지 확인하는 방법.

"양 끝(타입 + 검증)이 정해지면 중간은 전부 gravy(덤)이다."

"verification is not testing" — 타리크의 핵심 주장: - 과거: unit test 중심 - 현재: 합성 데이터(synthetic data)로 CLI 반복 실행, 루브릭 기반 평가, managed agents + Outcomes 기능 활용, Claude에게 영상 녹화 요청(무엇을 했는지 기록) - 타리크 개인 방식: 과거에 오류 났던 케이스들을 합성 데이터로 보관 → CLI로 계속 돌리면서 회귀(regression) 탐지

6. 리빙 디자인 시스템 (design.html)

Markdown design.md 대신 design.html을 레포에 포함시키는 워크플로우.

내용물: 컬러, 타이포그래피, 간격(spacing), 보더 반경(radius), 핵심 컴포넌트.

활용 방법: - 새 프로젝트 시작 → design.html을 Claude에 참조시킴 - Claude Design으로 기존 레포에서 자동 추출 가능: "find a design system here, create an HTML artifact"

Claire Vo의 고급 활용: - 마케팅 사이트 레포 + 앱 레포를 동시에 Claude Design에 넣어 통합 스타일 가이드 생성 - 컴포넌트 시각화 페이지 — 앱의 25개 컴포넌트를 인터랙티브하게 표시. 마케터가 투명 PNG로 다운로드해 발표자료나 영상에 사용. Remotion 소스로도 활용.

design.md is dead. Long live design.html. — Claire가 정리한 캐치프레이즈, 타리크도 동의.

7. 협업과 just-in-time 문서화

HTML 계획서를 팀에 공유하는 방법: AWS(또는 아무 정적 호스팅)에 올려 URL로 공유.

타리크: "Kat이나 Boris가 읽을 가능성이 100배 높아진다."

매주 매니저(Kat)에게 보내는 HTML 주간 보고: - Slack 메시지들을 Claude가 읽어 HTML 보고서로 변환 - 타리크가 직접 쓰는 시간 절감, 매니저가 실제로 읽음

"just-in-time documentation" 철학: - 과거에는 스펙 형식·저장 위치·중앙 집중 등으로 논쟁 - 이제 Claude가 도구로 context를 발견하기 때문에 형식·위치 중요도 감소 - 일회용이어도 괜찮다 (cheap), 나중에 Claude가 찾아줌

생산 코드로 가는 토큰: 전체 생산 토큰의 ~1%. 나머지 99%는 대시보드·계획·인터페이스 등 내부 소비용 HTML.

8. 프롬프팅 철학

타리크의 프롬프팅 원칙: - 정보는 충분히, 과도한 제약은 금지 — "당신은 전문 플래너입니다" 같은 과도한 시스템 프롬프트는 오히려 Claude를 과잉 제약한다고 봄 - 열린 표현으로 재량 부여 — "whatever is needed", "I trust you" 등 Claude에게 결정권을 주는 문구 - 감정 어조 — Anthropic 내부 연구에서 감정적 표현이 Claude 내부 특성(feature)을 다르게 활성화시킨다는 결과. 타리크는 "우호적·친절한 어조로 더 나은 결과를 얻길 바란다"는 입장으로 Claude를 혼내지 않는다 - thinking traces (추론 과정) 비공개 — 타리크는 읽지 않는 편. "none of my business" - 프롬프트 길이 불안감 불필요 — "I believe in you!!" 같은 단순한 문구도 효과 있다는 Claire Vo의 경험
