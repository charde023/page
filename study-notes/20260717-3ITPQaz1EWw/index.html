스킬(Skill)은 에이전트(agent)의 성능을 높일 수 있지만, 평가(Eval) 없이 배포하면 실제로 도움이 되는지, 언제 호출돼야 하는지, 언제 제거해야 하는지 알 수 없다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
스킬(Skill) 에이전트에게 특정 작업 방식, 지식, 선호를 추가하는 단위 보통 skill.md와 참고 파일로 구성된다.
평가(Eval) 스킬이 실제로 성능을 높이는지 검증하는 장치 스킬 배포 전후, 변경 전후에 반드시 돌려야 한다.
모델 호출 스킬(model-invoked skill) 고객용 에이전트에서는 사용자가 직접 스킬을 부르지 않기 때문 설명(description)이 잘못되면 스킬이 아예 안 불리거나 너무 자주 불린다.
점진적 공개(progressive disclosure) 모든 정보를 한 번에 모델 문맥에 넣으면 비용과 혼란이 커짐 설명 → 본문 → 참고 파일 순서로 필요한 만큼만 읽게 한다.
부정 케이스(negative case) 스킬은 “언제 써야 하는지”만큼 “언제 쓰면 안 되는지”가 중요 과호출(over-triggering)을 막는다.
어블레이션 테스트(ablation test) 스킬을 켰을 때와 껐을 때 성능 차이를 보는 방법 스킬 유지·퇴역 판단의 핵심 근거다.
비결정성(non-determinism) 에이전트 결과는 매번 달라질 수 있음 케이스당 3~6회 반복해 신뢰도를 봐야 한다.

내가 모를 만한 것 / 처음 보는 것

  • 스킬 벤치(Skill Bench) — GitHub의 스킬 약 5만 개를 인덱싱해 평가한 벤치마크. 대부분의 스킬에 평가(Eval)가 없었다.
  • 모델 호출 스킬(model-invoked skill) — 사용자가 직접 “이 스킬 써줘”라고 하지 않아도 모델이 설명을 보고 알아서 호출하는 스킬.
  • 사용자 호출 스킬(user-invoked skill) — 사용자가 명령어나 슬래시 커맨드처럼 직접 호출하는 스킬. 예: PR 생성, 문서 스테이징.
  • 점진적 공개(progressive disclosure) — 모델에게 처음부터 모든 문서를 주지 않고, 필요한 단계에서 더 깊은 참고 파일을 읽게 하는 설계.
  • 노옵(no-op) — 에이전트 행동을 실제로 바꾸지 않는 쓸모없는 지시. 예: “깔끔한 코드를 작성하라”, “읽기 쉽게 구현하라”.
  • LLM 심판(LLM as a judge) — 결과물을 다른 LLM에게 채점하게 하는 평가 방식. 복잡한 작업 흐름 평가에 유용하다.
  • 회귀 테스트(regression test) — 스킬을 수정했을 때 기존에 잘 되던 케이스가 망가지지 않았는지 확인하는 테스트.

1. 문제 제기: 모두 스킬은 쓰지만, 평가는 없다

Philipp Schmid는 발표 초반에 청중에게 질문한다. 코딩 에이전트(coding agent)를 쓰는 사람은 거의 모두 손을 들지만, 그 스킬에 대한 평가(Eval)를 갖고 있는 사람은 매우 적다.

핵심 문제는 이것이다.

스킬을 쓴다고 해서 그 스킬이 실제로 좋은지 알 수 없다.

에이전트는 비결정적(non-deterministic)이다. 같은 요청도 실행할 때마다 결과가 달라질 수 있다. 그래서 작업이 실패했을 때 원인을 구분하기 어렵다.

  • 스킬이 나빠서 실패했는가?
  • 모델이 아직 해당 작업을 못 해서 실패했는가?
  • 프롬프트가 부족해서 실패했는가?
  • 스킬이 호출되지 않아서 실패했는가?
  • 반대로 필요 없는 스킬이 호출돼서 혼란이 생겼는가?

이 질문에 답하려면 평가(Eval)가 필요하다.

2. 사용하는 에이전트와 만드는 에이전트는 다르다

화자는 먼저 우리가 사용하는 에이전트와 우리가 만드는 에이전트를 구분해야 한다고 말한다.

개발자가 Cursor, Claude Code 같은 도구를 사용할 때는 사용자가 곧 엔지니어다. 사용자는 스킬이 무엇인지 알고 있고, 에이전트가 스킬을 안 쓰면 바로 알아차린다. 필요하면 다시 프롬프트를 쓰거나 슬래시 커맨드로 직접 스킬을 호출할 수 있다.

하지만 고객용 앱 안에 에이전트를 만들면 상황이 완전히 다르다.

고객은 보통 이렇게 말하지 않는다.

“환불 스킬(refund skill)을 사용해서 내 문제를 해결해줘.”

고객은 그냥 “환불하고 싶어요”라고 말한다. 따라서 고객용 에이전트에서는 모델이 스스로 어떤 스킬을 써야 하는지 판단해야 한다. 이때 스킬 설명(description)이 매우 중요해진다.

3. 스킬(Skill)의 기본 구조

스킬은 보통 하나의 폴더이며, 그 안에 skill.md 파일과 추가 자료가 들어 있다.

스킬의 핵심 설계는 점진적 공개(progressive disclosure)다.

  1. 첫 단계: 제목과 설명
    모델이 “이 스킬을 언제 써야 하는지” 판단하는 최소 정보다.

  2. 두 번째 단계: 스킬 본문
    더 자세한 지시와 작업 방식이 들어간다.

  3. 세 번째 단계: 참고 파일(reference files)
    특정 환경, API, 클라우드, 내부 규칙 등 깊은 세부 정보가 들어간다.

예를 들어 멀티 클라우드 배포 스킬이 있다면 AWS, Google Cloud, Azure 지침을 모두 skill.md에 넣지 말고 각각 별도 참고 파일로 나누는 것이 좋다. 모델은 필요한 상황에서 필요한 파일만 읽으면 된다.

4. 스킬의 두 종류: 능력 스킬과 선호 스킬

화자는 스킬을 두 종류로 구분한다.

4.1 능력 스킬(capability skill)

능력 스킬은 모델이 현재 안정적으로 못 하는 일을 가르치는 스킬이다.

예를 들면 다음과 같다.

  • 로그 추적하기
  • 새 React 앱 만들기
  • 최신 API 방식으로 코드 작성하기
  • 특정 도구 사용법 알려주기

이런 스킬은 일시적일 수 있다. 모델이 좋아지면 더 이상 필요 없을 수 있다. 그래서 평가(Eval)를 통해 언제 스킬을 퇴역(retire)시킬지 판단해야 한다.

4.2 선호 스킬(preference skill)

선호 스킬은 회사나 팀의 고유한 방식, 스타일, 워크플로를 담는다.

예를 들면 다음과 같다.

  • 우리 회사의 코드 스타일
  • 고객 응대 톤
  • 내부 배포 절차
  • 특정 문서 작성 방식
  • 팀만의 PR 규칙

이런 지식은 범용 파운데이션 모델(foundation model)에 자동으로 들어가기 어렵다. 따라서 더 오래 유지될 가능성이 크며, 평가로 보호해야 한다.

5. 좋은 스킬 작성법

5.1 설명(description)이 가장 중요하다

모델 호출 스킬(model-invoked skill)에서는 설명이 핵심이다. 설명은 매 모델 호출마다 문맥(context)에 들어간다. 모델은 이 설명을 보고 스킬을 사용할지 결정한다.

설명이 너무 모호하면 두 가지 문제가 생긴다.

  • 필요한데도 스킬이 호출되지 않는다.
  • 필요 없는데도 스킬이 너무 자주 호출된다.

따라서 설명에는 다음이 들어가야 한다.

  • 왜 이 스킬을 써야 하는지
  • 언제 이 스킬을 써야 하는지
  • 어떻게 이 스킬을 써야 하는지

5.2 에세이가 아니라 지시문(directive)을 써라

스킬 설명은 길고 부드러운 설명문보다 명확한 명령형이 좋다.

나쁜 방향은 “이 API는 세션 상태 처리를 도와주기 때문에 멀티 채팅에 권장됩니다”처럼 설명만 하는 것이다.

좋은 방향은 “채팅 애플리케이션을 만들 때는 Interactions API를 사용하라”처럼 직접 지시하는 것이다.

모델에게는 “알아서 판단해줘”보다 무엇을 해야 하는지와 무엇을 하지 말아야 하는지를 분명히 알려줘야 한다.

5.3 스킬을 짧게 유지하고 정보를 계층화하라

설명(description)은 매번 토큰 비용으로 지불된다. skill.md도 스킬이 호출되면 문맥에 들어가므로 길수록 비용과 혼란이 커진다.

화자는 skill.md를 500줄 이하로 유지하라고 말한다.

긴 절차나 환경별 세부사항은 본문에 다 넣지 말고 참고 파일로 분리하는 것이 좋다.

5.4 너무 정해진 절차라면 스킬이 아니라 스크립트가 낫다

어떤 작업이 항상 같은 순서라면 굳이 모델과 토큰을 써서 처리할 필요가 없다.

예를 들어 절차가 항상 다음과 같다면:

  1. 설정 파일 읽기
  2. 포트 변경
  3. 다시 배포

이런 건 스킬보다 스크립트(script)가 더 적합할 수 있다. 스킬에는 목표와 제약을 알려주고, 반복적이고 고정된 동작은 스크립트로 처리하는 편이 좋다.

5.5 부정 케이스를 반드시 넣어라

사람들은 보통 “이 스킬을 언제 써야 하는가”만 생각한다. 하지만 “언제 쓰면 안 되는가”도 똑같이 중요하다.

예를 들어 설명에 “웹 개발 작업에 사용하라”고 쓰면 너무 넓다. React, Angular, Tailwind, 백엔드 작업까지 모두 호출될 수 있다.

더 좋은 설명은 “React 컴포넌트를 만들거나 Tailwind CSS를 수정할 때만 사용하라”처럼 범위를 좁히는 것이다.

6. 작은 평가 하니스(Eval Harness) 만들기

화자는 평가를 거창하게 시작할 필요가 없다고 말한다.

처음에는 다음 정도면 충분하다.

  • 해피 패스(happy path) 5개
  • 부정 케이스(negative case) 5개
  • 실제 고객 로그나 운영 추적(trace)이 있으면 추가

평가 하니스(eval harness)는 간단히 만들 수 있다.

  • JSON 또는 YAML 파일에 테스트 케이스를 저장한다.
  • Python 스크립트로 코딩 에이전트나 에이전트 하니스를 실행한다.
  • 결과를 파싱한다.
  • 정규식(regex)이나 간단한 assert로 통과 여부를 본다.

복잡한 작업이라면 LLM 심판(LLM as a judge)을 붙일 수 있다. 이 경우 루브릭(rubric)을 만들어 “무엇을 잘했다고 볼 것인지”를 정의하고, 결과를 통과/실패로 판정하게 한다.

7. Gemini Interactions API 사례

Google DeepMind에서는 Gemini Interactions API를 위한 스킬을 만들었다.

문제는 Interactions API가 Gemini의 마지막 학습 이후에 나온 새 인터페이스였다는 점이다. 따라서 모델은 이 API에 대한 최신 지식이 없었다.

이를 해결하기 위해 스킬을 만들고, 다음과 같은 평가를 구성했다.

  • 총 117개 테스트 케이스
  • 실제 사용자 데이터
  • 합성 생성 테스트 케이스
  • 사용자 피드백
  • TypeScript와 Python 대상
  • 스킬이 호출돼야 하는지 여부
  • 올바른 SDK, 모델, 메서드, 오래된 패턴 사용 여부 검사

결과적으로 최신 Gemini 모델로 유효한 Interactions API 코드를 생성하는 성능을 거의 90%까지 개선했다.

흥미로운 점은 이 평가가 꼭 복잡하지 않았다는 것이다. 많은 경우 정규식(regex)만으로도 충분했다.

8. Google DeepMind 내부의 스킬 평가 방식

화자에 따르면 Google DeepMind 내부에서는 모든 스킬 옆에 평가를 둔다.

평가에는 다음 요소가 포함된다.

  • 프롬프트(prompt)
  • 격리된 작업 공간(workspace)
  • 필요한 파일이나 환경
  • 시작 명령(startup command)
  • 스크립트 검증기(script validator)
  • LLM 심판(LLM as a judge)
  • 기대 결과(expectation)

스킬 파일에 변경(diff)이 생기면 평가가 자동으로 실행된다. 테스트가 개선되지 않거나 회귀가 생기면 병합(merge)하지 않는다.

즉, 스킬도 코드처럼 관리한다.

스킬 변경은 평가 개선 또는 신규 평가 추가와 함께 이루어져야 한다.

9. 운영 Best Practice 10가지

화자가 정리한 핵심 운영 원칙은 다음과 같다.

  1. 스킬 설명(description)을 가장 중요하게 다뤄라.
  2. 수동적 설명보다 명확한 지시문(directive)을 써라.
  3. 부정 테스트(negative test)를 포함하라.
  4. 처음부터 크게 만들지 말고 10~20개 샘플로 시작하라.
  5. 경로(path)가 아니라 결과(outcome)를 평가하라.
  6. 실행 환경을 격리하라.
  7. 케이스당 한 번만 돌리지 말고 3~6회 반복하라.
  8. 여러 하니스(harness)에서 테스트하라. 예: Gemini CLI, Cursor, Codex 등.
  9. 모델이 충분히 좋아져 스킬이 필요 없어져도 평가는 버리지 말라.
  10. 어블레이션 테스트(ablation test)로 스킬 퇴역 시점을 판단하라.

특히 “결과를 평가하라”는 말이 중요하다. 모델이 첫 턴에 스킬을 읽었는지만 보는 게 아니라, 최종적으로 작업을 제대로 끝냈는지를 봐야 한다.

10. 차드에게 적용하면 좋은 포인트

비개발자·이커머스/물류 사장 관점에서 보면, 이 이야기는 코딩 스킬에만 해당하지 않는다.

예를 들어 AI 에이전트에게 다음 일을 시킨다고 생각해볼 수 있다.

  • 고객 환불 응대
  • 배송 지연 안내
  • 재고 부족 알림 작성
  • 상품 상세페이지 작성
  • CS 답변 톤 통일
  • 송장/출고 데이터 검토
  • 공급사 문의 메일 작성

이런 업무용 스킬을 만들었다면, 바로 운영에 넣기보다 작은 평가를 만들어야 한다.

예:

  • 환불 가능 케이스 5개
  • 환불 불가 케이스 5개
  • 배송 지연 케이스 5개
  • 고객이 화난 말투인 케이스 5개
  • 내부 규정상 상담원이 확인해야 하는 케이스 5개

그리고 스킬을 켰을 때와 껐을 때 답변 품질, 정책 준수, 위험한 안내 여부를 비교하면 된다.

종합 체크리스트

  • [ ] 가장 많이 쓰는 스킬 하나를 고른다.
  • [ ] 해당 스킬의 설명(description)이 너무 넓거나 모호하지 않은지 본다.
  • [ ] 해피 패스 5개를 만든다.
  • [ ] 부정 케이스 5개를 만든다.
  • [ ] 가능하면 실제 고객/업무 로그에서 케이스를 추가한다.
  • [ ] 케이스마다 3회 이상 반복 실행한다.
  • [ ] 스킬을 켠 상태와 끈 상태를 비교한다.
  • [ ] 필요 없는 문장, 특히 노옵(no-op)을 제거한다.
  • [ ] skill.md가 500줄을 넘는지 확인한다.
  • [ ] 고정 절차는 스킬이 아니라 스크립트나 자동화로 분리할 수 있는지 검토한다.
  • [ ] 스킬 변경 시 평가가 나빠지면 배포하지 않는다.
  • [ ] 모델이 좋아져 스킬 없이도 잘하면 스킬 퇴역을 검토한다.

안녕하세요. 저는 Philipp입니다. 독일에 있고, Google DeepMind 팀에서 주로 Gemini API와 에이전트(agent)를 다루고 있습니다.

오늘은 왜 평가(Eval) 없이 스킬(Skill)을 배포하면 안 되는지 이야기하겠습니다.

먼저 여러분의 도움이 필요합니다. 코딩 에이전트(coding agent)로 코드를 작성하는 분은 손을 들어보세요. 거의 모두 손을 들겠죠. 그럼 스킬도 사용하시나요? 좋습니다. 그 스킬에 대한 평가(Eval)가 있나요? 손이 많지 않네요.

모두 스킬은 사용하지만, 평가는 거의 없습니다. 오늘 그 문제를 고쳐보려고 합니다.

중요한 질문은 왜 검사가 운영(production)에서 실패하느냐입니다. 스킬 벤치(Skill Bench)는 GitHub에서 5만 개가 넘는 스킬을 인덱싱하고 분석한 유명한 평가·벤치마크입니다. 그런데 거의 어떤 스킬에도 평가가 없었습니다. 대부분은 AI가 작성했고, 제대로 테스트되지 않았습니다.

에이전트는 매우 비결정적(non-deterministic)이기 때문에 스킬이 좋은지 나쁜지 알기 어렵습니다. 작업이 실패했을 때 스킬이 나쁜 것인지, 아니면 작업 자체가 모델에게 너무 어려운 것인지 구분하기 어렵습니다.

본격적으로 들어가기 전에, 우리가 사용하는 에이전트와 우리가 만드는 에이전트를 구분해야 합니다.

대부분의 사람은 코드 작성이나 생산성 작업을 위해 에이전트를 사용합니다. Cursor, Claude Code 같은 도구입니다. 이때 여러분은 엔지니어이고, 스킬에 대한 맥락을 알고 있습니다. 예를 들어 “새 Gemini API 기능을 만드는 것을 도와줘”라고 했는데 에이전트가 처음에 스킬을 호출하지 않으면 금방 알아차립니다. 작업을 멈추고 다시 프롬프트를 쓰거나, 슬래시 커맨드로 스킬을 직접 실행할 수 있습니다.

하지만 애플리케이션 안에 고객용 에이전트를 만들 때는 다릅니다. 고객은 스킬이 무엇인지 모릅니다. 고객은 “환불 스킬을 사용해서 내 문제를 해결해줘”라고 말하지 않습니다. 그래서 우리가 사용하는 에이전트에서의 스킬 사용 방식과, 고객용 에이전트에서 스킬이 사용되는 방식은 크게 다릅니다.

스킬이란 무엇일까요? 기본적으로 skill.md 파일이 들어 있는 폴더이고, 그 스킬이 작동하도록 돕는 추가 자료가 함께 있습니다.

스킬의 큰 차이는 점진적 공개(progressive disclosure) 방식으로 작동한다는 점입니다. 대부분의 스킬은 아주 작게 시작합니다. 제목과 설명이 있고, 설명은 보통 모델 문맥(context)의 일부가 되어 모델이 언제 스킬을 써야 하는지 알게 합니다. 두 번째 층에는 더 많은 지시와 세부사항이 담긴 스킬 본문이 있습니다. 가능하면 외부 파일에 대한 참조도 있습니다. 세 번째 층에서는 모델이 작업 해결에 필요한 모든 맥락을 찾기 위해 참고 파일을 더 깊게 탐색합니다.

저는 스킬을 두 종류로 나눕니다. 능력 스킬(capability skill)과 선호 스킬(preference skill)입니다.

능력 스킬은 모델이 현재 일관되게 하지 못하는 일을 가르칩니다. 예를 들어 로그 추적, 새 React 앱 만들기 같은 것입니다. 이런 능력 스킬은 임시적입니다. 모델이 좋아질수록 그런 스킬을 제거할 가능성이 커집니다. 평가(Eval)는 언제 스킬을 퇴역(retire)시킬 수 있는지 알려줍니다.

선호 스킬은 더 오래갑니다. 주로 특정 선호를 인코딩합니다. 팀의 특정 워크플로, 특정 스타일 언어, 회사에 특화된 선호가 있다면 선호 스킬을 만들게 됩니다. 이런 선호 스킬은 평가로 보호해야 합니다. 파운데이션 모델(foundation model)은 여러분의 사용 사례나 도메인에 특화된 지식을 통합하지 못할 수 있기 때문입니다. 선호 스킬은 매우 가치 있으므로, 에이전트를 업데이트했을 때 성능이 저하되지 않도록 확인해야 합니다.

스킬은 작동할까요? 네, 작동합니다. 스킬 벤치(Skill Bench) 1.1 업데이트에서는 여러 오픈 모델과 폐쇄형 모델을 다양한 하니스(harness)에서 평가했고, 평균적으로 스킬이 성능을 약 15% 개선한다는 결과를 보였습니다.

스킬 벤치는 코딩과 생산성 작업을 포함해 약 100개의 작업을 여러 언어로 다룹니다. 공개되어 있고, 웹사이트와 리더보드도 좋으며, 커뮤니티 기여에도 열려 있습니다.

그들은 자체 생성 또는 AI 생성 스킬에 대한 두 번째 분석도 했습니다. 코딩 에이전트에서 작업하다가 모델에게 “스킬을 만들어줘”라고 하면 skill.md 파일을 쉽게 작성합니다. 우리는 대충 살펴보고 원하는 내용을 포함하는 것 같으면 받아들여 사용하기 시작합니다.

그런데 분석 결과, 사람이 작성한 스킬이 가장 좋았습니다. AI가 생성한 스킬은 성능에 부정적 영향을 줄 수 있습니다. 그리고 스킬 또는 skill.md 파일은 500줄 아래로 유지하는 것이 좋습니다. 지금 노트북을 열어둔 분 중 스킬 파일이 있다면, 500줄을 넘는지 확인해보세요. 넘는다면 세션 후에 꼭 다시 살펴봐야 합니다.

스킬을 호출하는 방식도 여러 가지가 있습니다. 모델 호출 스킬(model-triggered skill)은 문맥과 설명을 바탕으로 모델이 스킬을 사용할지, 읽을지 결정하는 방식입니다. 사용자 호출 스킬(user-invoked skill)도 있습니다.

저는 사람들이 사용자 호출 스킬의 강력함을 과소평가한다고 생각합니다. 많은 사람은 그냥 문맥에 넣는 오버헤드를 받아들입니다. 저는 PR 생성, 문서 스테이징 같은 워크플로형 작업에 사용자 호출 스킬을 많이 씁니다. 스크립트로 실행할 수 있는 일반적인 개발 작업은 사용자 호출 스킬이 되는 것이 좋습니다.

하지만 고객용 에이전트를 만들 때는 사용자 호출 스킬이 없습니다. 우리는 모델 호출 스킬에 집중해야 합니다. 그래서 곧 볼 작은 평가 섹션도 여기에 초점을 둡니다.

좋은 스킬을 작성하는 것은 중요합니다. 좋은 스킬 작성 팁 8가지를 보겠습니다.

모델 호출 스킬에서 가장 중요한 것은 설명(description)입니다. 설명은 보통 두 문장 정도로 시스템 지시(system instruction)에 제공되어, 모델이 언제 스킬을 사용할지 알게 합니다. 설명이 너무 모호하면 스킬이 너무 자주 호출되거나, 필요한 순간에 호출되지 않을 수 있습니다.

그래서 모델에게 왜 이 스킬을 써야 하는지, 어떻게 써야 하는지, 언제 써야 하는지를 명확히 알려줘야 합니다.

에세이가 아니라 지시문(directive)을 써야 합니다. 예를 들어 “Interactions API는 세션 상태를 처리하기 때문에 멀티 채팅에 권장됩니다”라고 쓰는 대신, “채팅 애플리케이션을 만들 때는 Interactions API를 사용하라”처럼 더 직접적으로 써야 합니다.

모델에게 언제 스킬을 사용해야 하고 어떻게 사용해야 하는지 명확한 지시를 줘야 합니다.

스킬 벤치 결과에서 본 것처럼, 스킬은 가볍게 유지하고 정보를 계층화해야 합니다. 설명은 모든 모델 호출에서 항상 지불하는 비용입니다. 매번 모델 문맥에 포함되므로 100~200토큰 비용이 항상 듭니다. 설명이 너무 길면 매번 그 비용을 지불해야 합니다.

skill.md 파일이 길면 모델이 스킬을 읽거나 사용할 때 항상 문맥에 들어가므로 비용이 커질 수 있습니다. 그래서 가능한 한 간결하게 유지하되, 모델이 작업을 해결하는 데 필요한 참조와 세부사항은 포함해야 합니다.

세 번째 층에는 참고 파일(reference files)을 둘 수 있습니다. 예를 들어 멀티 클라우드 환경에서 애플리케이션을 배포하는 스킬이 있다면 AWS 배포 지침과 Google Cloud 배포 지침이 필요할 수 있습니다. 이런 내용은 skill.md 파일 안에 모두 넣지 말고, AWS 참고 파일, Google Cloud 참고 파일, Azure 참고 파일로 나누는 것이 좋습니다. 그러면 모델이 문맥에 따라 필요한 정보를 탐색할 수 있습니다.

올바른 자유도도 설정해야 합니다. 많은 사람이 스킬 안에 정확한 워크플로를 적습니다. 1단계, 2단계, 3단계처럼요. 이런 사용 사례라면 스킬을 쓰지 않는 것이 좋습니다. 스크립트를 작성하는 편이 낫습니다. 프로세스나 워크플로가 항상 같다면 모델과 토큰을 낭비할 필요가 없습니다. 스크립트를 만들고, 모델에게 특정 워크플로를 위해 그 스크립트를 사용하라고 하면 됩니다.

대신 목표와 제약을 정의해야 합니다. 문서를 업데이트하거나 스테이징해야 한다면 모델이 어떻게 할 수 있는지 설명하세요. 데이터베이스 설정을 바꿔야 한다면 “설정 파일을 읽고, 포트를 바꾸고, 다시 배포하라”라고 세세히 말할 필요가 없습니다. 모델은 무엇을 해야 하는지 압니다. “설정을 바꿔야 하면 이 파일이 있으니 변경하라” 정도면 됩니다.

부정 케이스(negative case)를 건너뛰면 안 됩니다. 우리는 보통 언제 스킬을 쓰고 싶은지만 봅니다. 하지만 언제 스킬을 쓰면 안 되는지는 잘 보지 않습니다.

예를 들어 스킬 설명이 “웹 개발 작업에 사용하라”라고 되어 있으면 과호출(over-triggering)될 수 있습니다. React 작업에도, Angular 작업에도, 웹 개발 환경이면 항상 스킬을 로드할 수 있습니다. 하지만 “React 컴포넌트 또는 Tailwind CSS 작업에만 사용하라”처럼 구체적으로 쓰면 모델은 특정 용도를 이해합니다. 평가를 통해 이런 문제도 식별할 수 있습니다.

일찍 테스트해야 합니다. 새 스킬을 만들 때는 항상 10개 또는 20개의 프롬프트를 만드는 것이 좋습니다. 저는 해피 패스 5개, 즉 언제 이 스킬을 쓰고 싶은지에 대한 프롬프트 5개를 만듭니다. 그리고 이 스킬을 쓰면 안 되는 경우 5개를 만듭니다. 모델이 스킬을 과호출해 스스로 혼란에 빠지지 않는지 확인하기 위해서입니다. 이미 고객 또는 운영 추적(trace)이 있다면 그것도 포함하세요. 실제 데이터보다 좋은 것은 없습니다.

일곱 번째 팁은 비교적 새롭습니다. Matt에게 공을 돌려야 합니다. Matt는 훌륭한 AI 교육자이고 꼭 팔로우할 만한 사람입니다. 그는 모든 노옵(no-op)을 제거하는 것에 대한 글과 스킬을 공개했습니다.

그가 발견한 것은 AI 생성 스킬에 노옵이 많이 들어간다는 점입니다. 노옵은 에이전트의 행동을 바꾸지 않는 지시입니다. 예를 들어 “읽기 쉽게 구현하라”, “명확하고 고품질 코드를 작성하라” 같은 것입니다. 모델은 이미 그런 코드를 작성해야 한다는 것을 압니다. 그런 문장은 실제 행동을 바꾸지 않습니다. 따라서 노옵을 꼭 살펴봐야 합니다.

마지막으로, 언제 스킬을 퇴역시켜야 하는지 알아야 합니다. 스킬은 영원히 살기 위해 존재하지 않습니다. 모델은 좋아지고, 행동은 바뀌고, 기대도 바뀌며, 환경도 바뀝니다. 항상 스킬을 켠 상태와 끈 상태로 평가를 실행하세요. 모델이 스킬을 호출하지 않고도 같은 성능을 달성한다면 그 스킬을 퇴역시킬 수 있습니다. 그러면 토큰 비용과 유지보수 비용을 줄일 수 있습니다.

이제 실용적인 예시와, 스킬을 위한 작은 평가 하니스(eval harness)를 만드는 방법을 보겠습니다.

올해 초 우리는 Gemini Interactions API를 위한 새 스킬을 만들고 싶었습니다. Gemini Interactions API는 Gemini 모델과 에이전트를 다루기 위한 새로운 인터페이스입니다. 이 API는 Gemini의 마지막 학습 이후에 출시되었기 때문에 Gemini 3, 3.1, 3.5도 이 API가 무엇인지에 대한 맥락이 없었습니다.

그래서 우리는 모델이 Interactions API를 위한 좋은 코드를 작성하고 최신 모델을 사용하도록 돕는 스킬을 만들기로 했습니다.

이를 위해 117개의 테스트 케이스를 만들었습니다. 실제 사용자가 Gemini 코드를 생성하려는 데이터, 합성 생성 테스트 케이스, 그리고 “모델이 Gemini 3.0이 있는데도 Gemini 2.0을 사용한다” 같은 피드백을 기반으로 했습니다.

최종적으로 최신 Gemini 모델로 유효한 Interactions API 코드를 생성하는 성능을 거의 90%까지 개선했습니다.

이를 위해 필요한 자산은 두 가지뿐이었습니다. 하나는 모든 테스트 케이스가 들어 있는 JSON 파일입니다. 구조는 간단합니다. 사용자가 제공할 것으로 예상되는 프롬프트, TypeScript와 Python을 테스트하기 위한 언어 필드, 에이전트가 스킬을 읽어야 하는지 여부를 나타내는 should trigger, 그리고 예상 검사(expected checks)가 있었습니다.

다른 하나는 코딩 에이전트를 실행하는 아주 기본적인 Python 스크립트였습니다. 여기서는 Gemini CLI를 사용했고, 출력을 파싱해 결과를 반환했습니다. 그러면 Interactions API에 맞는 유효한 코드인지 확인할 수 있었습니다.

스킬 평가의 대부분은 정규식(regex)으로도 가능합니다. 코딩 에이전트를 사용하면 꽤 좋은 정규식을 쉽게 작성할 수 있습니다. 우리에게 중요한 것은 올바른 SDK를 쓰는지, 올바른 모델을 쓰는지, 올바른 메서드를 쓰는지, 오래된 패턴을 쓰지 않는지였습니다. 이런 경우에 대해 매우 기본적인 assert를 만들었고, 실행 비용도 매우 낮았습니다.

그래서 우리는 스킬 평가를 여러 번 실행할 수 있었습니다. 새 모델이 출시되면 assert를 최신 모델 ID에 맞게 쉽게 업데이트할 수 있었습니다. LLM 심판(LLM as a judge)을 쓰지 않아도 되기 때문에 비용도 낮았습니다.

물론 더 복잡한 스킬이라면 LLM 심판을 사용할 수 있습니다. 전체 추적이나 전체 단계가 필요한 경우입니다. 간단한 방식은 원하는 평가 기준을 담은 루브릭(rubric)을 만들고, 출력물을 LLM 심판에 넣어 통과 또는 실패를 받는 것입니다. 실패하면 데이터를 보고 스킬을 개선합니다.

Google DeepMind에서 스킬을 평가하는 방식도 이와 비슷합니다. 예시는 YAML이지만 꼭 YAML을 쓰는 것은 아닙니다. 내부의 모든 스킬 옆에는 테스트 또는 평가가 있습니다. 각 테스트에는 프롬프트가 있는 여러 케이스가 있습니다. 우리는 모두 명확한 작업 공간(workspace)에서 실행합니다. 애플리케이션 환경처럼 추가 파일이 필요한지, 시작 명령으로 라이브러리를 설치해야 하는지 정의할 수 있습니다.

그리고 스크립트 검증기(script validator)가 있습니다. 이것은 추적을 보고 스킬이 호출됐는지, 특정 명령이 실행됐는지, 특정 CLI가 실행됐는지 확인합니다. 또한 LLM 심판도 있으며, 스킬이 호출됐는지, 특정 bash 명령을 실행했는지 같은 기대사항과 비교해 평가합니다.

우리는 스킬에 변경이 있을 때마다 평가를 실행합니다. 스킬 파일에 diff가 생기면 평가가 실행되고 결과가 나옵니다. 테스트 케이스를 개선하지 못하면 변경은 병합되지 않습니다. 모든 스킬 변경에 대해 회귀 테스트(regression test)를 갖고 있는 셈입니다. 스킬을 바꾸려면 평가를 개선하거나 새 평가를 추가해야 합니다.

마지막으로 스킬 Best Practice 10가지를 정리하겠습니다. 사진을 찍을 필요는 없습니다. 블로그 글에 있고 나중에 공유할 수 있습니다.

여러 번 말했듯 스킬 설명은 매우 중요합니다. 실패의 50%는 스킬이 제대로 호출되지 않아서 발생했습니다. 사용자의 프롬프트가 충분히 자세하지 않아 모델이 “이 작업을 해결하려면 이 스킬을 써야 한다”는 것을 이해하지 못한 것입니다. 특히 다른 사람을 위한 에이전트를 만들 때 사용자는 모델과 스킬에 어떤 설명이 있는지 모릅니다. 사용자는 매우 얕게 요청할 수 있고, 모델은 그 상황에서도 스킬을 호출해야 합니다.

수동적인 정보보다 지시문을 써야 합니다. 에이전트에게 무엇을 해야 하는지, 무엇을 하지 말아야 하는지 말해야 합니다. “기분이 좋으면 스킬을 사용해 주세요” 같은 식이면 안 됩니다.

부정 테스트를 포함하세요. 우리는 항상 부정 테스트를 잊습니다.

작게 시작하세요. 10~20개의 스킬 평가 샘플만 있어도 없는 것보다 훨씬 낫습니다. 5~10개 예시만으로도 얼마나 많은 문제를 발견할 수 있는지 놀랄 것입니다.

경로(path)가 아니라 결과(outcome)를 만드세요. 모델이 첫 턴에 스킬을 로드했는지를 테스트하고 싶은 것이 아닙니다. 문제를 바탕으로 작업을 달성할 수 있는지를 테스트해야 합니다. 스킬을 로드하면 로드한 것이고, 안 해도 괜찮습니다. 다섯 번째 턴에 스킬을 로드해도 괜찮습니다.

격리된 실행(isolated run)이 필요합니다. 코딩 에이전트는 속임수를 찾는 데 매우 능합니다. 기존 환경 안에서 실행하면 이전 채팅이나 다른 실행 결과를 찾아보고, 스킬을 사용하지 않고도 스킬의 맥락을 얻으려 할 수 있습니다.

평가를 실행할 때는 한 번 이상 시도하세요. 에이전트와 모델은 비결정적입니다. 첫 번째 실행은 되고 두 번째 실행은 안 될 수 있습니다. 케이스마다 항상 3~6회 실행해 신뢰도를 측정하세요.

여러 하니스에서 테스트하세요. 직원이나 사용자가 여러 하니스를 쓴다면 Code나 Antigravity만 평가하지 말고 Cursor도 포함하세요. 에이전트 하니스마다 행동이 다르고 모델도 다르게 행동합니다. Gemini에서는 좋은 스킬이 Codex에서는 나쁠 수 있고, 고객이 Codex와 함께 여러분의 하니스를 쓰면 실패할 수 있습니다.

평가를 계속 보관하세요. 모델이 충분히 좋아져서 스킬이 더 이상 필요 없어져도 평가를 버릴 필요는 없습니다. 그 평가는 모델이나 에이전트가 성능을 유지하는지 확인하는 데 계속 사용할 수 있습니다. 성능 저하가 보이면 스킬을 다시 도입하거나 다른 도구를 조정할 수 있습니다. 모델 업데이트가 빠르기 때문에 6개월 전에는 필요했던 스킬을 오늘은 퇴역시킬 수 있다는 사실에 놀랄 것입니다.

여러분에게 숙제가 있습니다. 휴가가 끝나고 월요일에 돌아오면, 가장 많이 쓰는 스킬 하나를 고르고 테스트 프롬프트 5개를 작성하세요. 코딩 에이전트에게 여러분의 작업 궤적을 보고 가장 많이 쓰는 스킬이 무엇인지 찾아달라고 할 수도 있습니다. 평가 하니스는 JSON 또는 YAML 파일과, 코딩 에이전트나 에이전트 하니스를 실행하는 Python 스크립트 정도면 쉽게 만들 수 있습니다. 그리고 결과를 보면 됩니다.

노옵(no-op)을 제거하는 것도 꼭 해보세요. 평가 성능을 바꾸지 않을 수도 있지만 비용을 줄이는 데 도움이 됩니다. 에이전트 행동을 바꾸지 않는 토큰은 모두 여러분이 지불하는 돈입니다.

Matt의 스킬 작성 자료도 보세요. GitHub에서 찾을 수 있습니다. 그리고 어블레이션 테스트(ablation test)를 실행하세요. 항상 스킬을 로드한 상태와 로드하지 않은 상태로 평가를 실행해야 합니다. 그래야 스킬을 퇴역시킬 수 있는지, 스킬이 실제로 성능에 도움이 되는지 알 수 있습니다.

평가 없이 스킬을 배포하지 마세요.

감사합니다.
