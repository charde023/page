검증이 새 병목 (Verification bottleneck) 코드 생성이 빨라질수록 검증·피드백 루프가 진짜 제약이 됨 빠른 생성 = 빠른 쓰레기가 될 수 있다
생산성 역설 (Productivity paradox) AI 도입이 개인 생산성은 올리지만 팀 생산성을 낮출 수 있음 Dora 연구 결과 — 팀 협업 설계가 필수
AI는 거울이자 증폭기 기존 강점도, 약점도 더 크게 만든다 내부 플랫폼이 엉망이면 AI가 기술 부채를 더 빠르게 쌓는다

내가 모를 만한 것 / 처음 보는 것

  • DORA 팀 (DevOps Research and Assessment): Google 산하 엔지니어링 생산성 연구 조직. 이 발표의 연구 근거 출처.
  • Shepherding agent: CICD 파이프라인을 통해 변경사항을 안내하고, 리뷰 에이전트를 반복 호출하며, 위험도 높은 변경은 사람에게 플래그하는 에이전트.
  • Risk assessor agent: 인플라이트 변경을 스캔해 고위험 변경을 사람에게 에스컬레이션하는 에이전트.
  • Adversarial review agent (적대적 리뷰 에이전트): 에지 케이스와 결정을 밀어붙여 시스템 취약점을 찾는 에이전트. Red team 역할.
  • Agent journaling (에이전트 저널링): 에이전트가 하루 작업을 반성·문서화하게 해서 막힌 지점·혼란 지점·생산적 지점을 파악하는 기법.
  • Tiered risk environment (계층화 위험 환경): 내부 앱 → 프로토타입 → 프로덕션으로 점진 이동하며 blast radius를 최소화하는 배포 전략.
  • Skill files / Rule files: 팀 관례·기대치·기관 지식을 에이전트에게 일관되게 주입하는 파일. 용어노트 참조 필요.
  • Agent sprawl: 에이전트가 너무 많아지면 추적·관리가 어려워지는 현상. 발표자 권장: 3~5개가 스위트스팟.
  • Value translator: 사용자·비즈니스 니즈를 AI가 실행 가능한 정밀 요구사항으로 변환하는 엔지니어 역할.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Google 전체 코드의 75%가 AI가 작성한다 (2025-2026 기준). 동시에 시스템 장애나 안정성 저하는 측정 가능한 수준으로 증가하지 않았다고 밝힘.
  2. AI를 가장 많이 쓰는 엔지니어들은 코딩 시간이 줄지 않고 오히려 더 많은 시간을 코딩·아이디에이션·협업에 씀 — 역설적 결과.
  3. TensorFlow 마이그레이션 예시: 단일 챗봇 대신 플래너 에이전트 → 오케스트레이터 에이전트 → 코더 에이전트 3-에이전트 아키텍처를 엄격히 분리해 사용. 각 에이전트에 YouTube 영역이면 YouTube 전용 플레이북을 주입.
  4. Search 팀에서 PM이 전통 코드 없이 내부 플랫폼만으로 프로덕션 피처를 출하하고 있음 — 플랫폼에 스케일링·보안·신뢰성 요구사항이 모두 내장되어 있어 가능.
  5. "delegate tasks, not judgment" — 발표자가 두 번 인용한 핵심 격언. 에이전트에게 맡기되 판단은 인간이 보유.
  6. 일부 주니어 엔지니어들이 불투명한 성능 메트릭·미묘한 분산 시스템 회귀에 막히는 문제가 있었음 → observability 도구 + 통합 데이터 에이전트(코드·에러로그·성능데이터·스택 트레이스 접근)를 투자해 해결.
  7. 재구현(Reimplementation)을 학습 도구로 적극 권장: 초안 그대로 수용하지 말고, AI에게 분해 후 재구현하게 하고 다른 접근 방식을 문서화하게 할 것.
  8. 에이전트 저널링 예시: "하루가 끝날 때 내 에이전트가 오늘을 어떻게 인식했는지 보면 정말 흥미롭다 — 어디서 막혔는지, 어디서 지시가 헷갈렸는지, 어디서 생산적이었는지."
  9. 생산성 측정에서 PR 처리량·수락된 코드 라인 수 측정을 중단하고, 비즈니스 아웃컴과 사용자 니즈 충족으로 전환하라고 리더에게 명시적으로 요청.
  10. 화이트보딩이 다시 프리미엄이 됨 — 에이전트 실행 전에 아키텍처·데이터 맵을 수동으로 추적해 초기 가정을 검증하는 아날로그 접근법.
  11. Peter Senge 인용: "가장 효과적인 사람은 비전을 붙들면서도 현재 현실을 명확히 보는 데 헌신할 수 있는 사람."
  12. Deming 인용: "나쁜 시스템은 언제나 좋은 사람을 이긴다." — 깨진 조직에서 T자형 개발자를 요구할 수 없다는 맥락.

1. 현황: 무슨 일이 일어나고 있는가

Andrew와 Nicole은 Google Developer Intelligence Team 리드로, 소프트웨어 엔지니어·프로세스·도구·시스템·문화를 연구한다.

Google 내부에서 확인된 수치: - 전체 코드의 75%가 AI가 작성 - AI를 가장 많이 쓰는 엔지니어 = 코딩·아이디에이션·협업 시간이 오히려 증가 - DORA 연구: AI 도입 증가 → 개인 생산성↑, 팀 생산성↓ 가능 (생산성 역설)

핵심 전제: 소프트웨어 엔지니어링은 코딩 그 이상이고, 코딩은 원래 병목이 아니었다. AI 혜택을 얻으려면: 1. 코드 생성 너머 전체 SDLC에 AI를 적용 2. 기존 방식에 AI를 얹지 말고, 프로세스 자체를 변환

2. 5가지 AI 네이티브 패턴

패턴 1 — 고도 상승 (Operating at higher altitudes)

엔지니어링 지식 + 비즈니스 컨텍스트 + 사용자 니즈를 결합. 무엇을·어떻게 만드는가를 넘어 왜 만드는가를 깊이 사고. 시니어 엔지니어에게 늘 기대했던 것이지만, AI가 실행을 가속할수록 더 중요해진다.

패턴 2 — 의도를 앞당기기 (Shift left on intent)

기존 "Shift left" = 테스팅·보안을 SDLC 앞으로 당기기.
새로운 의미: 에이전트가 자율 실행을 맡을수록, 계획·명확한 지시·트레이드오프·컨텍스트 제공에 더 많은 에너지를 선행 투자. 코드 자체에서 구조화된 의도로 진실의 원천이 이동. 엔지니어들이 명세 파일(specification files)을 작성하는데 이것은 제품 사고를 명시화하는 것.

패턴 3 — 환경 설계 (Designing environments)

바이브 코딩(vibe coding) 아님. 프롬프트로 코드를 요청하는 것이 아니라, 에이전트·인간이 협력할 수 있는 시스템을 설계. 가드레일 설정, 에이전트 팀 구성, 올바른 컨텍스트와 스킬 부여. 핵심 인용: "delegate tasks, not judgment."

패턴 4 — 마이크로팀의 부상 (Rise of the micro team)

소규모 크로스펑셔널 애자일 팟. 소통 오버헤드 감소, 긴밀한 협업 루프. 에이전트가 실행을 담당하기에 소수 인원으로 대규모 속도 달성. 단, 에이전트에게 컨텍스트·제약·목표·트레이드오프·성공 기준을 명확히 전달하는 게 전제.

패턴 5 — 과학적 마인드셋 (Scientific mindset)

최첨단에서 일하려면 실패에 열려 있어야 함. 매주 새 접근법을 실험하고, 학습을 시스템에 코드화. 무작위 탐색이 아니라 탐색 → 캡처 → 적용의 사이클. 의도와 피드백 루프가 핵심.

3. T자형 엔지니어 확장 모델

        ← 인접 엔지니어링 (보안·프라이버시·인프라)
        ← AI 활용 역량 (새 수평 축)
        ← 인접 비엔지니어링 (비즈니스·사용자 맥락)
├─────────────────────────────────────────────────┤  ← 광폭 T 상단
                       │
                       │  핵심 소프트웨어 엔지니어링 심층
                       │
  • 기존 T: 폭넓은 기반 지식 (상단) + 특정 분야 깊은 전문성 (줄기)
  • 새 수평 축 추가: AI의 제약을 이해하고, 태스크별 출력 품질을 평가·조종하는 능력 — 필수 불가결
  • 새 날개 1 — 인접 엔지니어링: AI가 더 많은 기능 코드를 만들수록, 보안·신뢰성·사이버보안·배포 인프라 고려가 선두에 와야 함
  • 새 날개 2 — 인접 비엔지니어링: AI가 "어떻게"를 담당하니, 엔지니어는 비즈니스·사용자 니즈("무엇을·왜")에 더 집중

중요 경고: 인접 지식이 없으면 AI가 틀린 방향으로 더 빨리 달리게 만든다.

4. 핵심 소프트웨어 엔지니어링 스킬

현실 사례: Google Search PM이 직접 프로덕션 피처 출하

PM이 내부 플랫폼을 통해 의도 → 작동하는 피처로 변환. 전통 코딩 없음. 이것이 가능한 이유: 플랫폼에 시스템 아키텍처·언어 프레임워크 강점·스케일링·신뢰성 요구사항이 모두 내장됨 → 더 많은 엔지니어링 깊이, 더 적은 것이 아님.

3가지 구체적 전환

1. 검증이 병목
코드 생성이 빨라질수록, 유능한 검증이 제약이 됨. 줄줄이 수동 검증은 불가능 → 효과적 피드백 루프 설정이 핵심. 내부 플랫폼이 안전한 환경에서 성능 데이터를 빠르게 수집하고, 엔지니어가 가장 가치 있는 지점에만 투입되도록 설계.

2. 바이브 코딩 금지 — 정밀 엔지니어링
깊은 엔지니어링 이해 없이 AI를 쓰면 기술적·인지적 부채가 믿을 수 없는 속도로 쌓인다. 내부 플랫폼은 의도 → 작동하는, 고품질, 신뢰성 있는, 안전한 코드로 가도록 설계됨. 에이전트가 따라야 할 스타일 가이드 컨벤션 명세 + 드리프트 감지 체크 포함.

3. 피드백 루프와 Observability
지적 수동성(intellectual passivity) = 가장 큰 위험. 엔드유저 피드백·성능 피드백으로 의도 준수 여부를 측정. Observability로 가드레일 부재 또는 에이전트의 잘못된 가정을 식별.

실용 팁 3가지

  1. 재구현을 학습 도구로: AI 초안을 바로 수용하지 말고, 분해 후 재구현 지시. 왜 다르게 접근했는지 문서화 요청.
  2. 낯선 코드 워크스루: 자신이 쓰지 않은 코드·시스템·에이전트 결정 트레이스를 설명하게 함. 화이트보딩 병행.
  3. 스킬 파일·룰 파일 버전 관리: 팀 관례·기대치·기관 지식을 에이전트에 일관 주입. 코드처럼 버전 컨트롤 + observability 적용.

5. AI 활용 스킬 — 오케스트레이터로 전환

단일 에이전트 지휘자 → 비동기 AI 에이전트 팀 오케스트레이터.

3가지 원칙

1. 에이전트 팀 관리
각 에이전트는 자체 컨텍스트 윈도우와 책임 영역을 가짐. 인간 엔지니어가 환경 설정 + 플로우 지시. 에이전트에게 스킬(레시피·도구·도메인 지식) 부여.

2. 자동화 트랩 회피
언제 위임하고 언제 안 할지 파악. 명확한 인간 기준선 수립, 검증 오버헤드 측정. 성공 확률 높은 태스크부터 실험.

3. 코드 리뷰 에이전트 + 셰퍼딩 에이전트
기능성·신뢰성·성능·사용성·보안·유지보수성 평가하는 리뷰 에이전트 구축. 인간 리뷰어 교체가 목표가 아니라, 피드백 루프를 더 촘촘히 만드는 것이 목표. 셰퍼딩 에이전트가 CICD 파이프라인을 안내하고, 위험 평가 에이전트가 고위험 변경을 사람에게 플래그.

실용 팁 3가지

  1. Evals(평가 역량) 업스킬: 검증이 병목인 시대에 AI 출력 평가 능력 필수. Evals = AI·소프트웨어 엔지니어링·사용자·비즈니스 스킬 모두 필요. 팀 공유 지식이자 의도 캡처의 핵심 산출물.
  2. 에이전트 저널링: 에이전트에게 매일 반성·문서화하게 함. 막힌 지점·혼란 지점을 파악 → 시스템 전체를 개선. 에이전트가 내부 도구 접근에 반복 어려움을 겪으면 → 도구 사용성 문제 신호.
  3. 3~5 에이전트 팀 아키텍처: TensorFlow 마이그레이션 예시 — 플래너(검증 가능한 마이그레이션 스텝 생성) + 오케스트레이터(스텝 그룹화) + 코더(실행). 에이전트 스프롤 주의. 베스트 프랙티스를 플레이북으로 코드화해 에이전트에 주입.

6. 인접 엔지니어링 스킬 — AI가 기술 부채를 더 빠르게 쌓는 위험

AI는 증폭기이자 거울: 강점을 확대하고, 약점을 반사. 인접 엔지니어링 영역은 AI가 조용하고 치명적인 부채를 가장 쉽게 쌓는 곳.

3가지 원칙

1. 고품질 내부 플랫폼
Search PM 사례: 배포 환경·보안·신뢰성 요구사항이 플랫폼에 내장. AI가 강력한 협력자가 되려면 좋은 플랫폼·명확한 API·문서화된 워크플로가 전제. 파편화된 도구·사일로 데이터·취약한 인프라에서 AI는 기술 부채를 더 빠르게 생성.

2. 계층화 위험 환경 (Tiered risk environments)
내부 앱 → 프로토타입 → 프로덕션으로 점진적 이동. 각 단계는 다른 환경 요구사항. 10배 속도, 10배 위험은 안 됨. Blast radius 억제 + 빠른 피드백 루프 병행. Google: AI 코드 증가에도 측정 가능한 장애 증가 없음.

3. 효과적 실험 + Observability
피처가 빠르게 이동할수록, 격리된 실험이 중요. Observability 도구 + 통합 데이터 에이전트(코드·에러로그·성능데이터·스택 트레이스 접근)로 주니어 엔지니어들이 복잡한 분산 시스템을 진단할 수 있게 지원.

실용 팁 4가지

  1. 비난 없는 포스트모텀 문화: 장애·인시던트를 문서화·토론. 에지 케이스·스케일 한계·신뢰성 위협에 대한 직관 구축. 에이전트 자기반성 + observability 트레이스와 삼각 검증.
  2. AI로 스트레스 테스트: Red team 에이전트를 명시적으로 설정해 악의적 행위자 관점에서 시스템을 보게 함. 에이전트가 시스템을 어떻게 익스플로잇할지 설명하게 함.
  3. 화이트보딩 아날로그 접근: 파이프라인을 수동으로 추적해 엔터프라이즈 컴플라이언스 같은 것의 멘탈 모델을 구축. 코드 한 줄 전에 의도를 화이트보드에.
  4. Observability 우선 투자: 10배 속도에서는 10배 모니터링이 필요.

7. 비즈니스·사용자 맥락 스킬 — 가치 번역자

에이전트가 루틴 실행을 담당하면, 엔지니어는 무엇을·왜에 집중. 많은 개발자에게 불편한 전환 — DORA 연구: 개발자들이 정체성 위협을 느낌 (코딩 장인 정신에서 가치를 많이 끌어왔기 때문).

가치 번역자 (Value translator)

"퍼포먼스 개선" 요청이 오면: - AI: 비효율적 루프를 찾아 리팩터링 - 가치 번역자: 누구를 위한 퍼포먼스? 어떤 조건에서? 먼저 질문. 특정 사용자 세그먼트 파악, 실제 영향을 주는 코드 경로에 AI를 조준.

실용 팁 2가지

  1. AI로 사용자 피드백 합성만 하지 말 것: LLM에 수백 개 피드백 로그 던지는 것은 위험. 대신 고터치 사용자 피드백 세션 직접 참여 — 사용자 목소리의 기쁨·좌절을 듣는 것이 공감을 쌓고 "왜"를 현실로 만든다.
  2. 스펙을 최우선 제품 산출물로: 팀의 인지 에너지를 목표·비즈니스 로직·엣지케이스 제약 토론에 투자. 스펙을 코드처럼 취급 → 리뷰 에이전트로 스트레스 테스트도 가능.
