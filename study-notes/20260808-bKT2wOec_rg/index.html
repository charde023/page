개념 왜 중요한가 한 줄
슬롭(slop) AI 시대에는 사람이 읽지 않는 코드가 급증하기 때문 슬롭은 “나쁜 코드”라기보다 읽히지 않는 코드다.
코드 리뷰 없는 개발 AI 속도에서는 모든 코드를 사람이 읽는 방식이 병목이 됨 코드 리뷰 대신 불변 규칙(invariant)과 자동 검증을 둔다.
architecture.md 에이전트와 사람이 공통으로 이해하는 최소한의 설계 기준 오래 바뀌지 않을 구조만 작게 적어야 한다.
설계 문서(design doc) 문화 코드는 AI가 써도 되지만, 설계 의도는 명확해야 함 “코드는 슬롭이어도 글은 슬롭이면 안 된다.”
에이전트 검증(agent inspection) 사람이 모든 실행 기록을 볼 수 없기 때문 Claude 기록을 다른 에이전트가 읽고 문제를 찾게 한다.
도구 호출 수(tool calls) 에이전트 생산성의 실질 지표 같은 결과라면 도구 호출이 적고 오류가 적은 설계가 좋다.
실행 추적(execution trace) 코드를 다 읽지 않고 시스템을 이해하는 핵심 수단 모든 실행을 추적 가능하게 만들면 사람과 에이전트 모두 디버깅이 쉬워진다.
타입 안전성(type safety) AI가 만든 코드의 신뢰도를 올리는 기반 타입 시스템이 거짓말하지 않아야 에이전트 속도로 개발할 수 있다.
BAML Boundary가 만든 에이전트 친화적 언어·도구 체계 기존 언어의 한계를 보완하면서 Python, TypeScript 등과 연결된다.
기반 계층 재설계 TypeScript 같은 기존 언어에는 인간 생산성 중심의 타협이 있음 AI 시대에는 Git, DB, 언어 같은 기초 도구도 다시 상상해야 한다.

내가 모를 만한 것 / 처음 보는 것

  • 슬롭(slop) — AI가 대량 생성한 저품질 코드·문서·결과물을 뜻하지만, 화자는 특히 “아무도 읽지 않는 코드”로 정의한다.
  • 불변 규칙(invariant) — 시간이 지나도 깨지면 안 되는 구조적 규칙. 예: 컴파일러 계층 구조, 패키지 의존성 방향.
  • architecture.md — 에이전트가 항상 참고할 수 있는 초소형 아키텍처 문서. 상세 설명서가 아니라 바뀌지 않는 원칙만 담는다.
  • 설계 문서 도구(design doc tool) — Notion과 GitHub 이슈/PR의 일부 역할을 대체하는 내부 문서 시스템. 버전 관리와 댓글을 지원한다.
  • 의미적 경계(semantic boundary) — 코드베이스 내부에서 모듈·패키지·계층이 지켜야 할 의미적 분리선.
  • 의존성 그래프(dependency graph) — 패키지나 모듈 간 의존 관계를 시각화한 그래프.
  • 도구 호출(tool call) — 에이전트가 검색, 파일 읽기, 코드 실행 등 외부 도구를 호출하는 행위.
  • A/B 테스트(A/B test) — 두 설계나 기능을 실제 에이전트 작업에서 비교해 어느 쪽이 더 오류가 적고 효율적인지 확인하는 방식.
  • 실행 추적(execution trace) — 프로그램 실행 중 어떤 함수가 언제, 얼마나 실행됐는지 기록한 흐름.
  • ripgrep — grep보다 빠른 코드 검색 도구. 화자는 일반 grep 대신 ripgrep을 쓰라고 말한다.
  • 센티널 값(sentinel value) — 오류 상황을 표현하기 위해 반환하는 특별한 값. 예: 예외 대신 0을 반환.
  • 완전성 보장(exhaustive guarantee) — 발생 가능한 모든 오류나 케이스를 처리했는지 컴파일러가 증명해주는 성질.
  • 함수 색깔(function coloring) — 동기 함수와 비동기 함수가 언어 차원에서 분리되어 호출 방식이 달라지는 문제.
  • FFI 경계(FFI boundary) — 서로 다른 프로그래밍 언어가 함수를 호출하거나 데이터를 주고받는 경계.
  • Wasm(WebAssembly) — 브라우저와 서버 등 여러 환경에서 실행 가능한 저수준 실행 포맷.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 3년 전 프로그래밍 언어를 만들기 시작했다 — 프로그래밍 언어는 대충 만들어서는 안 되며, 한 번 잘못 설계하면 나중에 바꾸기 어렵다는 맥락.
  2. Boundary 팀은 코드 리뷰(code review)를 하지 않는다 — 대신 병렬 작업, 최소 규칙, 자동 검증 도구를 쓴다.
  3. 사람마다 Claude, Codex, Hacker News에서 본 최신 도구를 자유롭게 쓴다 — AI 도구 표준화를 강제하지 않는다.
  4. architecture.md에는 몇 달 또는 몇 년 동안 바뀌지 않을 내용만 넣는다 — 모델이 이해하기 쉬운 단순한 Markdown 파일이어야 한다.
  5. 컴파일러 깊은 계층을 수정할 때는 에이전트에게 최소 한 명과 대화하라고 지시한다 — 속도를 일부러 늦춰 위험한 변경을 줄이는 장치.
  6. 설계 문서 채널은 회사에서 가장 인기 있는 Slack 채널이 되었다 — 새벽 2시에 설계 문서가 올라와도 세 명이 바로 읽을 정도였다고 한다.
  7. 설계 문서 도구는 실제로 Markdown 파일과 간단한 CLI 스크립트로 뒷받침된다 — GitHub처럼 행동하지만 GitHub 자체는 아니다.
  8. 화자 본인도 한때 하루 10개 설계 문서를 올리며 슬롭을 만들었다 — 그래서 문서 발행 시 실제 독자를 요구하는 규칙을 추가했다.
  9. 의존성 그래프 도구는 내부 의존성과 일부 외부 의존성을 시각화한다 — CI/CD나 Git 커밋 기록으로 어디서 경계가 깨졌는지 추적한다.
  10. 최근 3~4개월간 아키텍처를 바꾸지 않았다 — 불변 규칙과 도구 덕분에 구조가 안정됐다는 주장.
  11. Python은 25년 뒤에도 버그가 있다고 언급한다 — 프로그래밍 언어의 안정성이 얼마나 어려운지 강조.
  12. BAML 프로그램을 에이전트가 계속 생성하고, 다른 에이전트가 실행 기록을 읽는다 — 사람만 검토하는 것이 아니라 에이전트가 에이전트를 평가한다.
  13. 평가 기준은 “맞냐 틀리냐”뿐 아니라 3번 도구 호출할 일을 1번에 했는가까지 본다.
  14. 전통적으로 언어 개발에는 수백, 수천, 수만 인시(man-hours)가 필요하지만 이제는 수십억 토큰을 써서 가능하다고 표현한다.
  15. TypeScript의 목표를 정확성과 생산성의 균형이라고 설명하면서, 실제로는 인간 생산성(human productivity) 중심이라고 비판한다.
  16. JavaScript의 정렬(sort) 동작에서 문자열 변환을 예로 들며 “언어에 박힌 슬롭”이라고 말한다.
  17. BAML은 코드 자체보다 시각화, 실행 추적, 에이전트 탐색을 중심에 둔 언어 경험을 지향한다.
  18. 실행 추적을 처음부터 설계하면 사실상 성능 비용 0에 가깝게 만들 수 있다고 주장한다.
  19. 모든 함수가 CLI 명령처럼 즉시 실행 가능하면 에이전트가 코드를 검색하지 않고도 빠르게 검증할 수 있다.
  20. BAML의 오류 시스템은 divide 함수의 0으로 나누기 오류(division by zero error)를 상위 함수까지 추론한다.
  21. Python, TypeScript, Rust, Go, Ruby, Java 등 기존 언어에서 BAML 함수를 호출할 수 있게 만드는 방향을 제시한다.
  22. 발표 전날 한 엔지니어가 BAML만으로 부분 C 컴파일러(partial C compiler)를 만들었다고 말한다.
  23. 마지막에는 새로운 Git, 새로운 데이터베이스, 새로운 프로그래밍 언어가 필요하다고 결론낸다.

# 섹션 요지
1 슬롭의 정의 슬롭은 사람이 읽지 않는 코드이며, AI 시대에는 피할 수 없다.
2 코드 리뷰 없는 팀 운영 도구 표준화 대신 작은 불변 규칙으로 팀을 통제한다.
3 설계 문서 문화 코드는 AI가 써도 되지만 설계 글은 고품질이어야 한다.
4 아키텍처 검증 의존성 그래프와 CLI 규칙으로 구조적 위반을 잡는다.
5 에이전트가 에이전트를 평가 Claude 실행 기록을 다른 에이전트가 분석하고 개선점을 찾는다.
6 기존 언어의 한계 TypeScript와 JavaScript에는 인간 중심 타협이 깊이 박혀 있다.
7 BAML의 접근 코드 읽기보다 시각화, 실행 추적, 타입 안전성을 중심에 둔다.
8 에이전트 우선 도구 검색, 문서, 실행, CLI를 에이전트가 쓰기 쉽게 재설계한다.
9 오류 처리 재설계 컴파일러가 오류 타입을 추론하고 처리 여부를 증명한다.
10 기존 언어와 연결 BAML을 새 언어로 강요하지 않고 Python 등에서 호출하게 한다.
11 결론 AI 속도에 맞는 프로세스와 기반 도구를 새로 만들어야 한다.

1. 슬롭은 “읽지 않는 코드”다

Vaibhav Gupta는 발표를 “슬롭에는 슬롭으로 맞선다”는 농담 섞인 문장으로 시작한다. 여기서 슬롭(slop)은 단순히 못 짠 코드가 아니라, 팀 안에서 아무도 제대로 읽지 않는 코드를 뜻한다.

AI 코딩 도구가 보편화되면 코드 양은 빠르게 늘어난다. 문제는 개발자가 그 모든 코드를 읽을 시간이 없다는 점이다. 그래서 화자는 현실을 인정해야 한다고 말한다. 지금의 코드베이스가 앞으로 경험할 가장 적은 슬롭 상태일 수 있으니, 슬롭을 없애겠다는 환상보다 슬롭을 통제하는 방법을 만들어야 한다는 것이다.

Boundary는 3년 전부터 BAML이라는 프로그래밍 언어를 만들었다. 프로그래밍 언어는 대충 만들 수 없는 영역이다. 컴파일러, 타입 시스템, 실행 의미가 항상 같은 방식으로 작동해야 하고, 나중에 설계 실수를 쉽게 되돌릴 수 없다. 그런 분야에서 Boundary는 코드 리뷰 없이, 각 엔지니어가 원하는 AI 도구를 쓰면서도 개발을 이어왔다.

2. 코드 리뷰 대신 작은 불변 규칙을 둔다

Boundary는 코드 리뷰를 하지 않고, Claude, Codex, 최신 AI 도구 등 어떤 도구를 써도 허용한다. 대신 표준을 강제하지 않고 불변 규칙(invariant)을 만든다.

대표적인 예가 architecture.md다. 이 파일은 거창한 문서가 아니라, 모든 모델이 이해할 수 있는 작고 단순한 Markdown 파일이다. 여기에 들어갈 내용은 몇 달, 몇 년 동안 바뀌지 않을 구조여야 한다. Boundary의 경우 컴파일러 계층 구조가 여기에 해당한다.

핵심은 “모든 AI 도구가 따라야 할 최소한의 경계”를 만드는 것이다. 도구 사용 방식은 자유롭게 두되, 깨지면 안 되는 구조만 명확히 고정한다. 특히 컴파일러의 깊은 계층으로 들어가는 변경은 에이전트에게 최소 한 명의 사람과 대화하도록 요구해 속도를 일부러 늦춘다.

3. “코드는 슬롭이어도 글은 슬롭이면 안 된다”

화자는 설계 문서가 진짜 전장이라고 말한다. Boundary의 규칙은 단순하다.

코드는 슬롭이어도 되지만, 글은 슬롭이면 안 된다.

AI가 코드를 많이 생성하더라도 설계 의도와 결정 이유는 사람이 이해할 수 있어야 한다. 그래서 Boundary는 Notion과 GitHub를 일부 대체하는 내부 설계 문서 도구를 만들었다. 이 도구는 버전 관리, 댓글, 문서 업데이트를 지원한다.

처음에는 사람들이 잘 쓰지 않았다. 그래서 Slack 연동을 추가했다. 설계 문서가 업데이트될 때마다 Slack 채널에 알림이 올라가게 한 것이다. 그 결과 이 채널은 회사에서 가장 인기 있는 채널이 되었다. 새벽 2시에 누군가 설계 문서를 올리면 여러 사람이 바로 읽을 정도였다고 한다.

다만 이것도 과해질 수 있다. 화자 본인도 한때 AI에 취해 하루 10개씩 설계 문서를 올렸고, 팀이 그 문서 슬롭과 싸우게 됐다. 그래서 마지막 규칙을 추가했다. 설계 문서를 올리려면 실제로 사람들이 읽게 만들어야 한다는 것이다. 이 규칙 덕분에 설계 문서 품질이 높아졌다고 설명한다.

4. 아키텍처는 의존성 그래프와 CLI로 지킨다

코드베이스가 여러 사람이 병렬로 작업해도 한 방향으로 수렴하려면 아키텍처를 자동으로 검증해야 한다. Boundary는 내부 의존성 그래프(dependency graph)를 시각화하는 도구를 만들었다.

이 도구는 내부 패키지와 일부 외부 의존성을 보여주고, 의미적 경계(semantic boundary)가 깨지는지 감시한다. 여기에 CLI 도구를 붙여 특정 불변 규칙이 깨지지 않도록 보장한다.

예를 들어 Claude가 새 패키지를 만들거나, 새 의존성을 추가했는데 계층이 새는 구조가 되면 CI/CD 또는 Git 커밋 기록을 통해 어디서 문제가 생겼는지 알 수 있다. 이런 시스템 덕분에 Boundary는 최근 3~4개월간 아키텍처를 바꾸지 않고 유지할 수 있었다고 한다.

5. 에이전트가 만든 코드는 에이전트가 검사한다

프로그래밍 언어에는 제네릭(generics), 클로저(closures), 메모리 할당(memory allocation), FFI 경계(FFI boundaries) 등 수많은 불변 조건이 있다. 사람이 AI가 만든 모든 코드를 읽지 않는다면 어떻게 신뢰할 수 있을까?

Boundary는 에이전트가 계속 BAML 프로그램을 만들고, 또 다른 에이전트가 그 프로그램과 실행 기록을 검사하게 한다. Claude가 어떤 도구를 썼는지, 어디서 실패했는지, 어떤 선택이 좋았는지 기록을 분석한다.

중요한 점은 단순히 “언어 기능이 맞게 작동했는가”만 보지 않는다는 것이다. 어떤 작업이 원래 한 번의 도구 호출(tool call)로 끝날 수 있었는데 세 번이 걸렸다면 그것도 문제로 본다. 이후 사람과 에이전트가 함께 이슈를 분류한다. 진짜 버그인지, 환각(hallucination)인지, 취향이 없는 제안인지 판단한다.

더 나아가 Boundary는 언어 기능이나 스킬을 A/B 테스트할 수 있다고 말한다. 어떤 기능이 도구 호출을 줄이는지, 오류를 줄이는지, 올바른 결과를 더 잘 내는지 데이터로 비교한다. 즉, 코드를 직접 많이 쓰지 않아도 데이터 기반 시스템을 만들 수 있다는 주장이다.

6. 기존 언어에는 이미 슬롭이 박혀 있다

화자는 슬롭과의 전투에서는 이길 수 있어도 전쟁에서는 질 수 있다고 말한다. 이유는 우리가 쓰는 기초 도구 자체가 이미 깨져 있기 때문이다.

예로 TypeScript를 든다. TypeScript의 주요 설계 목표는 정확성과 생산성의 균형이지만, 실제로는 인간 생산성(human productivity)을 중심에 둔 타협이 많다고 본다. JavaScript 위에 CoffeeScript, TypeScript, Effect 같은 레이어를 계속 얹었지만, 밑바닥의 문제는 그대로 남아 있다는 것이다.

정렬(sort) 시 값이 문자열로 변환되는 동작 같은 JavaScript의 특성을 예로 들며, 이런 것은 언어 안에 내장된 슬롭이라고 말한다. 인간이 직접 코드를 많이 쓰던 시대에는 생산성을 위해 감수할 수 있었지만, 에이전트가 코드를 대량 생성하는 시대에는 이런 모호함이 시스템 전체에 슬롭을 퍼뜨린다는 관점이다.

7. BAML은 코드 읽기보다 시스템 이해를 돕는 방향을 택한다

화자는 “코드를 다 읽지 않는다면, 코드를 어떻게 이해할 것인가?”라는 질문을 던진다. BAML의 방향은 코드 자체를 읽는 대신, 코드 구조와 실행을 시각화하고 추적하는 것이다.

예를 들어 코드를 볼 때 단순한 텍스트가 아니라, 전체 구조를 빠르게 시각화하고 클릭하면 정확한 코드 라인으로 이동할 수 있다. 큰 그림을 보고 필요한 부분만 확대해서 읽는다. 모든 코드를 이해하려 하기보다, 사람이 관심 있는 부분만 선택적으로 파고든다.

실행 중인 프로그램은 실행 추적(execution trace)으로 이해한다. 어떤 부분에서 시간이 쓰였고, 어떤 함수가 어떻게 호출됐는지 추적한다. Python이나 TypeScript에서 모든 것을 추적하면 성능 비용이 커질 수 있지만, 처음부터 그런 목적을 염두에 두고 설계하면 거의 비용 없이 만들 수 있다고 주장한다.

이 추적 시스템은 사람뿐 아니라 Claude 같은 에이전트도 탐색할 수 있다. 에이전트가 버그, 오류, 비효율을 찾아 최적화할 수 있게 되는 것이다.

8. 에이전트 우선 도구는 검색과 실행 방식도 달라야 한다

화자는 IDE와 검색 도구도 에이전트 시대에 맞게 바뀌어야 한다고 말한다. grep보다 ripgrep을 쓰는 예를 들면서, 단순 문자열 검색은 여전히 여러 단계의 도구 호출을 필요로 한다고 지적한다.

대신 “Calculate를 설명해줘”라고 하면 관련 문서 문자열(doc strings), 실제 소스 코드, 사용 위치까지 한 번에 보여주는 도구를 상상한다. 외부 라이브러리도 웹 검색이 아니라 실제 코드 기반으로 설명해줄 수 있어야 한다.

화자가 배운 중요한 원칙은 “코드는 항상 진실의 원천(source of truth)”이라는 것이다. 문서, README, 아키텍처 설명은 틀릴 수 있지만 코드는 거짓말하지 않는다는 믿음이다. 물론 이상한 아키텍처에서는 예외가 있을 수 있다고 농담한다.

마지막으로 그는 모든 함수가 즉시 CLI 명령처럼 실행 가능하면 어떻겠냐고 묻는다. 예를 들어 add 함수가 있으면 add라는 CLI 명령이 생기고, a와 b 파라미터를 넣어 바로 실행할 수 있다. 더 나아가 함수가 독립 실행 가능한 CLI 바이너리로 패키징된다면, 에이전트가 배포 환경이나 운영체제 차이를 덜 신경 쓰고 빠르게 검증할 수 있다.

9. 오류 처리는 타입 시스템이 증명해야 한다

화자는 JavaScript의 깊은 문제 중 하나로 오류 처리(error handling)를 든다. AI 에이전트는 try-catch를 중첩하다가 결국 console.log로 “에러가 났다”고 찍고 포기하는 식의 코드를 만들기 쉽다고 말한다.

BAML에서는 오류를 처음부터 다르게 다루려 한다. 예를 들어 divide 함수는 0으로 나누기 오류(division by zero error)를 던질 수 있다. 이때 개발자가 별도로 적지 않아도 함수는 자신이 어떤 오류를 던질 수 있는지 안다. 그리고 divide를 호출하는 상위 calculate 함수도 그 오류 가능성을 자동으로 안다.

즉, 오류 타입(error type)이 추론된다. 이후 오류를 잡거나 처리할 때 컴파일러가 모든 오류를 빠짐없이 처리했는지 증명할 수 있다. API가 “절대 예외를 던지지 않는다”고 보장하려면, 처리되지 않은 오류가 없어야 한다. 처리하지 않은 오류가 있다면 컴파일러가 제약을 만족하지 못한다고 알려준다.

이런 방식은 AI 코드에 대한 신뢰와 연결된다. 우리가 컴파일러를 믿는 이유는 컴파일러가 충분히 엄격한 규칙을 제공하기 때문이다. LLM 코드를 맹목적으로 믿지 못하는 이유도 그 밑의 시스템이 충분히 단단하지 않기 때문이라고 설명한다.

10. 새 언어를 강요하지 않고 기존 언어와 연결한다

화자는 모든 사람에게 BAML로 코드를 다시 쓰라고 요구하면 슬롭과의 전쟁에서 질 것이라고 말한다. 새 언어는 문제를 해결하는 동시에 새로운 문제도 만들기 때문이다.

그래서 Boundary는 BAML을 독립 실행 언어로만 쓰는 것이 아니라, 기존 언어 안에서 호출할 수 있게 만들고 있다. Python, TypeScript, Rust, Go, Ruby, Java, 그리고 앞으로 나올 언어에서도 BAML 함수를 쓸 수 있게 하는 방향이다.

예를 들어 BAML의 calculate 함수를 Python에서 직접 호출할 수 있고, 타입 안전성(type safety)도 유지된다. 비동기 코드가 필요한 경우 calculate async도 제공된다. 또한 언어 경계를 넘어 람다(lambda), 제네릭(generics), 클로저(closures)를 전달하는 방식도 구상한다.

핵심은 에이전트가 작업할 때 타입 시스템이 절대 거짓말하지 않게 하는 것이다. 타입 시스템이 진실의 중심이 되면, 불변 조건이 코드베이스에 침투하는 것을 막을 수 있다.

11. 결론: AI 속도에 맞는 프로세스와 기반 도구가 필요하다

Vaibhav Gupta가 말하고 싶은 핵심은 특정 도구 하나가 아니다. 전통적인 코드 리뷰 없이도, 병렬 작업과 자유로운 AI 도구 사용 속에서도 복잡한 시스템을 만들 수 있다는 가능성이다. 단, 팀이 내부 시스템을 어떻게 쓰는지 매우 신중하게 설계해야 한다.

그는 예전 회사들이 CI/CD를 도입할 때 “느려질 것”이라고 걱정했지만, 실제로는 몇 달의 적응 후 훨씬 빨라졌던 사례를 든다. AI 에이전트 속도로 개발하려면 프로세스도 진화해야 한다.

마지막 메시지는 실천적이다. 각자 돌아가서 다소 조잡해 보여도 내부 도구를 만들고, 시스템과 프로세스를 더 견고하게 하라는 것이다. 더 용감한 사람은 Git, 데이터베이스, 프로그래밍 언어 같은 기반 계층 자체가 어떻게 깨져 있는지 다시 생각해보라고 말한다.

화자는 새로운 Git, 새로운 데이터베이스, 새로운 프로그래밍 언어가 필요하다고 결론내린다.

제가 처음 코딩을 배울 때 얻은 중요한 교훈은 코드가 항상 진실의 원천(source of truth)이라는 것이었습니다. 코드 자체 외에는 읽지 마십시오. 문서는 거짓말할 수 있고, 설명이나 아키텍처 파일, README는 분명 거짓말할 수 있습니다. 하지만 코드는 거짓말할 수 없습니다. 이상한 아키텍처에서 일하는 경우는 예외일 수 있습니다.

이 길로 가면, 코드를 읽지 않고도 아키텍처를 이해하는 단계로 갑니다. 코드를 검색하지 않고도 한 번의 도구 호출로 정확히 무엇을 얻는지 이해하는 단계로 갑니다.

그다음에는 무엇을 해야 할까요? 제가 코드를 진짜 이해하기 위해 마지막으로 하는 일은 코드를 실행하는 것입니다.

여러분이 실행하는 모든 것, 작성한 모든 함수가 즉시 간단한 CLI 명령(command)으로 사용 가능하다면 어떨까요? add를 실행하면 add가 a와 b 파라미터를 가진 CLI 명령이 됩니다. 바로 실행해서 무슨 일이 일어나는지 볼 수 있습니다.

모든 CLI 도구를 완전히 독립 실행 가능한 CLI로 패키징할 수 있다면 어떨까요? 실제 코드를 따로 실행하지 않아도 함수가 포함된 완전한 CLI 바이너리(binary)가 되는 것입니다.

그러면 에이전트가 무슨 일이 일어나는지 grep으로 뒤질 필요가 없는 빠른 도구를 만들 수 있습니다. 모든 것이 타입 안전(type safe)하고, 결정론적(deterministic)이며, 추측 가능합니다.

더 좋은 점은 어떤 시스템에서도 빌드할 수 있다고 상상해보십시오. 에이전트가 Windows, Mac, Linux 배포를 걱정할 필요가 없고, 원하는 계층을 대상으로 삼을 수 있으며, Wasm 시스템을 포함한 어떤 아키텍처에도 빌드할 수 있습니다. 그러면 엔지니어는 엄청나게 강화됩니다. 밑의 시스템이 막고 있는 것 때문에 병목에 걸리지 않습니다. 매우 빠르게 움직일 수 있고, 에이전트 속도로 움직일 수 있습니다.

지금까지 이야기한 많은 것은 도구(tooling)에 관한 것이었습니다. 그렇다면 JavaScript의 진짜 죄악 중 일부를 고치려 한다면 어떨까요? 언어 깊숙한 곳에 있는 것들 말입니다. 표면적인 것이 아니라 더 중요한 것, 예를 들면 오류(errors)입니다.

Rust를 제외하고 오류 처리가 아름다웠던 적을 본 적이 있습니까? 여기서 제가 보는 에이전트의 행동은 try-catch를 쓰고, 또 try-catch를 중첩하고, 또 중첩하다가 결국 포기하고 console.log로 “어떤 오류가 발생했다. 알아서 처리하라”고 하는 것입니다.

오류 처리를 완전히 새로운 원칙에서 할 수 있다면 어떨까요? 그 세계에서는 어떤 일이 벌어질까요? 앞서 add, multiply, subtract는 보여드렸지만 divide는 보여드리지 않았습니다.

divide는 위험합니다. 무섭습니다. 그래서 divide를 봅시다.

여기서 divide는 0으로 나누기 오류(division by zero error)를 던집니다. 그런데 또 무엇이 일어날까요? 이 함수는 여러분이 코드를 따로 쓰지 않아도 자신이 0으로 나누기 오류를 던진다는 것을 압니다.

calculate 함수로 올라가면, 이 함수는 어느 시점에 divide를 호출합니다. 이 함수도 0으로 나누기 오류를 던질 수 있다는 것을 압니다. 이제 오류 타입(error type)이 추론됩니다. 추측할 필요가 없습니다.

이것은 오류를 잡거나 처리할 때 완전성 보장(exhaustive guarantee)을 할 수 있다는 뜻입니다. 컴파일러가 여러분이 오류를 처리했는지 처리하지 않았는지 증명할 수 있습니다. 더 이상 추측이 아닙니다. 알 수 없는 것이 없습니다. 증명됩니다.

만약 절대 예외를 던지지 않는 API를 배포하고 싶다면, 이 시스템은 제약을 만족하지 못하기 때문에 깨진 것입니다. 처리하지 않은 오류가 두 개 있기 때문입니다.

그것을 잡고 싶다면 코드를 금방 쓸 수 있습니다. 특정 오류를 잡기 시작할 수 있습니다. 지금은 센티널 값(sentinel value)을 반환하겠습니다. 그러면 이전에 0으로 나누기 오류를 던지던 parse 부분은 이제 더 이상 그 오류를 던지지 않는 것이 보장됩니다. 여기서 예외를 잡으면 매번 0 값을 반환하기 때문입니다.

컴파일러와 도구는 우리를 위해 많은 일을 할 수 있습니다. 우리는 이미 코드베이스에서 이것에 익숙합니다. 많은 사람이 컴파일러가 내부에서 어떻게 작동하는지 모르지만 컴파일러를 신뢰합니다. 코드는 신뢰의 문제입니다.

우리가 LLM 코드를 맹목적으로 쓰지 않는 이유는 아직 그것을 신뢰하지 않기 때문입니다. 그리고 그 밑의 시스템에 충분한 강성(rigidity)이 없기 때문입니다.

그렇다면 모든 코드를 다시 쓰지 않아도 되는 해결책은 어떤 모습일까요? 우리는 약 2년 전부터 이것을 생각하기 시작했습니다.
