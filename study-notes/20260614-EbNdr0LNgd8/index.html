Headroom: AI 에이전트를 10배 더 싸게 만드는 Netflix 도구입니다

Headroom은 AI 에이전트의 도구 호출 결과를 LLM에 보내기 전에 프록시에서 압축해 토큰 비용을 최대 98%까지 줄이는 오픈소스 도구다. 압축 내용에 해시 단서를 남겨 모델이 원본을 다시 요청할 수 있다.

내가 모를 만한 것 / 처음 보는 것

  • Headroom — Netflix 시니어 개발자 Tejas Chopra가 만든 오픈소스 토큰 압축 프록시. Python 서버 형태.
  • CompressBase — Headroom이 일반 텍스트 압축에 사용하는 자체 로컬 모델. 외부 LLM 없이 로컬에서 실행.
  • 해시 브레드크럼 (hash breadcrumb) — 압축 결과에 원본 데이터를 식별할 수 있는 해시를 삽입해, 모델이 필요하면 retrieve 요청으로 원본을 돌려받는 메커니즘.
  • AST(Abstract Syntax Tree) 기반 코드 압축 — 코드 파일을 텍스트 수준이 아닌 문법 트리 수준에서 파싱해 중요한 구조만 보존.
  • Caveman — 모델의 응답 출력 토큰을 줄이는 도구. Headroom과 반대 방향(입력이 아닌 출력 측).
  • uv — Python 패키지 관리자. Headroom 설치 예시에서 pip 대신 uv를 사용.
  • cross-agent memory — Claude Code, Codex 등 여러 에이전트 하네스가 동일한 압축 컨텍스트를 공유하는 Headroom 기능.
  • Headroom Learn — 과거 실패 세션을 분석해 과도하게 압축했던 패턴을 학습, 향후 같은 실수를 줄이는 기능.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Python 3.12 필수 — 더 높은 버전에서는 동작하지 않음. uv로 설치 시 버전 명시 필요.
  2. Headroom은 도구 호출 출력(tool call output)만 압축한다 — 텍스트 파일을 직접 주면 압축 안 됨.
  3. 로그 파일 데모: 98% 토큰 절감, 17,000토큰 이상 절약. 419개의 유사한 info 로그를 요약 1개로 압축.
  4. Claude Code + Headroom 데모: 89.1K 토큰 사용. Headroom 없이는 더 많은 토큰 사용 (정확 수치는 컨텍스트 창 차이로 직접 비교 어려움).
  5. Opus 저노력(low effort) 모드에서는 Headroom이 토큰 절감 효과 없음 — medium 이상에서 효과 확인됨.
  6. Headroom이 $700,000 이상의 토큰 비용을 사용자들에게 절약시켰다고 주장.
  7. 2차 왕복(second round trip) 트레이드오프 — 모델이 압축 결과로 충분하지 않다고 판단하면 원본을 재요청해 오히려 토큰이 더 늘어날 수 있음.
  8. 압축은 Rust로 구현된 엔진이 수행 — 성능 최적화.

1. Headroom이란 무엇인가

Headroom은 Netflix 시니어 개발자 Tejas Chopra가 만든 오픈소스 도구다. Claude Code 같은 AI 에이전트 하네스(harness)는 매 도구 호출마다 방대한 JSON 로그, 코드 파일, RAG 결과를 컨텍스트 창에 쌓는데, 이게 전부 비용으로 이어진다. Opus Ultra 모드처럼 병렬 서브에이전트를 무제한으로 돌리는 경우 특히 심각하다.

Headroom은 앱과 LLM API 사이에 Python 프록시 서버로 앉아서, 도구 호출 결과(tool call output)가 LLM에 도달하기 전에 Rust 엔진으로 압축한다.

2. 콘텐츠 타입별 압축 전략

Headroom은 단순히 텍스트를 자르지 않는다. 콘텐츠 타입을 감지해 의미 있는 정보를 선별 보존한다:

  • JSON 배열 — 이상값(anomaly)과 엣지케이스만 보존.
  • 코드 — AST(문법 트리)를 읽어 중요한 구조 보존, 반복 보일러플레이트 제거.
  • 빌드 로그 — 실패(failure)만 남기고 통과한 테스트는 버림.
  • 일반 텍스트 — CompressBase라는 Tejas 직접 학습 로컬 모델로 압축.

3. 해시 브레드크럼 메커니즘

압축된 결과에는 원본 데이터의 해시가 포함된다. 모델이 압축 결과만으로는 태스크를 완료할 수 없다고 판단하면, 이 해시를 이용해 Headroom 프록시에 원본 데이터를 재요청할 수 있다. 즉, 압축은 비가역적이지 않고 가역적(reversible) 이다.

단, 이 재요청이 발생하면 2차 왕복(second round trip)이 생겨 오히려 토큰이 더 늘어날 수 있다. Headroom Learn 기능이 이런 실수를 점진적으로 줄이도록 설계됐다.

4. 기본 데모 — 서버 로그 분석

설치:

uv pip install headroom --python 3.12
uv pip install headroom[sdk] anthropic

프록시 실행:

headroom proxy

Python SDK로 compress 함수를 호출해 도구 호출 결과 메시지를 압축한 뒤, 압축된 메시지를 Claude API에 전달한다. 실제 모델 호출에는 Haiku가 아닌 지정 모델을 사용하지만, 토큰 카운팅 정확도를 위해 compress 함수에 모델명을 전달한다.

결과: 서버 로그 419개의 유사 info 로그가 요약 1개로 압축 → 98% 토큰 절감, 17,000토큰 이상 절약.

초기 실행 시 Claude가 "정보가 부족하다"고 응답하는 경우가 있었는데, 재실행하자 98% 절감 유지 상태에서 올바른 답변이 나왔다.

5. Claude Code 연동 데모

더 많은 파라미터로 프록시를 실행:

headroom proxy --ml --code-aware
  • --ml: CompressBase 로컬 모델로 일반 텍스트 압축 활성화.
  • --code-aware: 코드 인식 압축기 활성화.

Claude Code의 base URL을 프록시로 설정한 뒤, TypeScript 프로젝트 전체를 읽고 깊은 개요를 요청. 5개 패키지의 모든 TS 파일을 읽고 응답 완료. /context 명령어로 확인한 토큰 사용량: 89.1K 토큰. Headroom 없이 동일 프롬프트 실행 시 더 많은 토큰 사용(컨텍스트 창 크기가 달라 직접 비교 제한됨).

curl + jq로 프록시 엔드포인트를 조회하면 압축으로 절약된 토큰 수와 절약된 비용을 확인할 수 있다.

6. 트레이드오프와 고급 기능

트레이드오프: - 모델이 압축 결과만으로 충분하지 않다고 판단 → 원본 재요청 → 2차 왕복 → 토큰 증가 가능. - Headroom Learn이 완화책: 과거 실패 세션을 분석해 과압축 패턴 학습. - Opus 저노력(low effort) 모드에서는 절감 효과 없었음 — medium 이상에서 효과 발생.

아직 다루지 않은 고급 기능: - Cross-agent memory — Claude Code, Codex 등이 동일한 압축 컨텍스트 공유. - Headroom Learn — 실패 세션 학습으로 과압축 방지. - 인기 SDK 통합.

7. Caveman과의 조합

Caveman은 모델에게 짧은 단편으로 응답하도록 지시해 출력 토큰을 줄인다. Headroom은 모델이 읽는 입력을 줄인다. 방향이 반대이므로 두 도구를 함께 사용하면 입력(Headroom) + 출력(Caveman) 양방향 최대 절감이 가능하다.

교정 전사 (한국어)

전체 전사 펼치기

이것이 Headroom입니다. AI 에이전트가 읽는 모든 것 — 도구 호출, 코드 파일, RAG 결과 — 을 LLM에 도달하기 전에 압축하는 오픈소스 도구입니다. 토큰을 60%에서 최대 95%까지 줄이면서도 동일한 답변을 얻을 수 있습니다. 영리한 점은 가역적(reversible)이라는 것입니다. 모델이 전체 정보가 실제로 필요할 때는 언제든 다시 요청할 수 있습니다.

그런데 압축은 보통 무언가를 잃는다는 뜻인데, 대부분의 컨텍스트를 제거하고도 올바른 답을 얻을 수 있을까요? 이건 진짜 흥미로운 질문입니다. 구독하고 함께 알아봅시다.

Claude Code 같은 하네스(harness)를 써봤다면 토큰을 엄청나게 소모한다는 걸 알 겁니다. 매 도구 호출마다 대용량 JSON 로그를 쏟아내는데, 대부분이 중요한 정보를 방해하는 노이즈입니다. 이게 전부 컨텍스트 창에 쌓이고, 그게 곧 비용입니다. 특히 Opus Ultra 모드처럼 동적 워크플로를 돌리면서 토큰 한도 없이 병렬 서브에이전트를 띄우면 더욱 심각합니다. 이게 바로 Netflix 시니어 개발자 Tejas Chopra가 Headroom을 만든 이유입니다.

Headroom은 콘텐츠 타입을 감지해 중요한 정보만 보존합니다. JSON 배열에서는 이상값(anomaly)과 엣지케이스를 보존합니다. 실제 문법 트리를 읽는 코드 압축기도 있습니다. 빌드 로그를 읽을 때는 실패만 남기고 통과한 테스트는 버립니다.

흥미로운 부분은 일반 텍스트의 경우입니다. Headroom은 CompressBase라는 자체 모델을 사용하는데, Tejas가 압축 전용으로 직접 학습시킨 모델이며 여러분의 로컬 머신에서 실행됩니다. Headroom은 이미 사용자들에게 약 $700,000의 토큰 비용을 절약시켰다고 주장합니다.

정말 영리한 점은, 압축된 텍스트에 해시를 포함한 브레드크럼(breadcrumb)을 남긴다는 것입니다. 모델은 이 해시로 필요할 때 압축 해제된 데이터를 다시 가져올 수 있습니다.

Caveman에 대한 James의 영상을 봤다면, 그것도 컨텍스트를 줄이지만 반대 방향에서 접근합니다. 이에 대해서는 나중에 더 설명하겠습니다. 지금은 Headroom의 기본 예제를 보면서 어떻게 작동하는지 이해해봅시다.

Headroom은 여러분의 앱(Claude Code 등)과 Anthropic 서버 사이에 앉는 Python 서버로 동작합니다. 도구 호출 결과가 돌아오면 프록시가 Rust 엔진으로 압축해 압축된 버전만 API로 전송합니다.

pip로 서버를 설치할 수 있지만, 저는 uv를 사용하겠습니다. Python 3.12 버전을 맞춰야 합니다 — 상위 버전에서는 동작하지 않습니다. 그 다음 headroom proxy 명령으로 프록시를 해당 포트에서 실행합니다. Headroom에는 TypeScript 또는 Python SDK도 있습니다. 데모에서는 Python SDK로 Claude SDK를 사용하는 앱을 만들겠습니다.

앱의 계획은 이렇습니다. 사용자 프롬프트는 모든 로그 파일을 읽고 오류와 근본 원인을 찾아달라는 것입니다. 도구 호출을 가짜로 만들 겁니다 — Claude가 bash 도구로 서버 로그 파일을 cat하도록 하고, 파일에는 가짜 로그가 담겨 있습니다. 그 도구 호출 결과를 반환합니다.

Headroom에 텍스트 파일을 직접 주지 않는 이유는, Headroom이 도구 호출 출력만 압축하기 때문입니다. 여기서 모델을 지정하고, 그 아래에 headroom compress 함수를 사용합니다 — 정확한 토큰 카운팅을 위해 메시지와 모델을 넘깁니다(Headroom이 실제로 Haiku를 사용하지는 않습니다). 그리고 프록시의 base URL을 지정합니다. 압축 전후 메시지와 절약 비율을 보여주는 로그도 추가했습니다. 그 다음 Headroom에서 압축된 메시지를 사용자 프롬프트와 함께 Claude Code에 전달합니다.

실행하면 Headroom이 98%의 토큰을 절약한 것을 볼 수 있습니다. 전: 17,000토큰 이상. 후: 훨씬 적음. 압축 전후를 스크롤해서 보면 명확합니다. 전에는 사용자 프롬프트, 도구 호출, 전체 로그 파일이 담긴 도구 응답이 있습니다. 후에는 같은 사용자 메시지와 도구 호출이 있지만, 도구 응답이 훨씬 짧습니다. 통계적 압축으로 419개의 유사한 info 로그를 요약 하나로 압축했습니다.

Headroom이 Claude에게 이게 압축된 출력이며 이 해시로 원본을 다시 가져올 수 있다고 알려주는 것도 볼 수 있습니다.

Headroom의 즉각적인 단점 중 하나는, Claude가 태스크를 완료하기에 정보가 부족하다고 생각한다는 점입니다 — 실제로는 충분히 있는데도. 다시 실행하면 이번에는 98% 절감을 유지하면서 Claude가 훨씬 더 많은 정보를 제공합니다.

다음 데모입니다. 마찬가지로 Headroom 프록시를 실행해야 하는데, 이번에는 더 많은 파라미터를 줍니다. --ml 값을 추가하면 일반 텍스트 압축에 로컬 압축 모델을 사용합니다. --code-aware 플래그도 추가해 코드 인식 압축기를 활성화합니다. 이제 활성화된 것을 확인할 수 있습니다.

그 다음 Claude Code를 실행하되, 먼저 base URL을 프록시로 설정합니다. 이 상태에서 "이 프로젝트의 모든 TS 파일을 읽고 관련 코드 인용과 함께 프로젝트가 무엇을 하는지 깊이 있는 개요를 달라"는 프롬프트를 줍니다. 잠시 후 5개 패키지의 모든 TypeScript 파일을 읽고 전체 개요를 제공했습니다.

/context 명령어로 확인하면 89.1K 토큰을 사용했습니다. Headroom 없이 유사한 프롬프트로 실행했을 때는 토큰이 더 많이 사용됐습니다. 왜 여기서는 Opus 1M 컨텍스트 창을, 저기서는 200K 창을 선택했는지 정확히는 모르겠습니다만, 이 엔드포인트를 curl과 jq로 포맷하면 프록시의 압축 세부 사항을 볼 수 있습니다. 정보가 많아서 찾는 데 시간이 걸렸지만, 스크롤해서 올라가면 Headroom 압축으로 절약된 토큰 수와 비용을 확인할 수 있습니다.

물론 이건 프롬프트 하나에서 나온 결과입니다. 여러 Claude Code 세션을 동시에 돌리면서 Headroom이 모든 도구 호출을 압축한다면 얼마나 더 많은 토큰을 절약할 수 있을지 상상해보세요.

한 가지 더: 저노력(low effort) Opus로 동일한 프롬프트를 실행했을 때 Headroom은 토큰 절감 효과가 없었습니다. medium으로 올리자 절감 효과가 나타났습니다. high, x-high, max라면 더 많이 절약될 것입니다.

Headroom의 빠른 개요를 살펴봤습니다. 물론 다루지 못한 기능이 훨씬 많습니다 — 여러 하네스가 동일한 압축 컨텍스트를 공유하는 cross-agent memory, 실패 세션을 분석해 과압축 패턴을 학습하는 Headroom Learn, 인기 SDK 통합 등.

단, 중요한 고려사항이 있습니다. 모델이 필요한 정보를 얻지 못해 Headroom에 전체 데이터를 요청할 때마다 2차 왕복이 발생합니다. 경우에 따라서는 Headroom을 안 쓸 때보다 토큰을 더 많이 쓰게 될 수도 있습니다. 이게 Headroom Learn의 장점입니다 — 점점 그런 일이 덜 발생하도록 학습합니다.

앞서 Caveman 이야기를 했죠. Caveman은 모델에게 짧은 단편으로 응답하고 불필요한 단어를 빼도록 지시해 토큰을 줄입니다. 반면 Headroom은 모델이 읽기 전에 입력을 줄입니다. 하나는 출력을 줄이고 다른 하나는 입력을 줄입니다. 토큰 절약에 정말 관심 있다면 두 가지를 함께 사용해 최대 절감을 달성할 수 있습니다.
