Claude Code는 실제로 어떻게 동작할까요

한 줄 요약

LLM은 텍스트만 생성하며, 하네스(harness)는 tool calling 루프·컨텍스트 관리·권한 검사를 담당하는 실행 환경이다. 같은 모델도 어떤 하네스 위에서 돌리느냐에 따라 성능이 크게 달라진다.

개념 왜 중요한가 한 줄
하네스(Harness) AI 코딩 도구 품질을 결정하는 핵심 모델에 도구·컨텍스트·권한 검사를 묶어주는 실행 환경
Tool Calling 루프 에이전트가 "계속 작업"하는 메커니즘 툴 호출 → 실행 → 결과를 채팅 히스토리에 추가 → 모델 재호출
컨텍스트 관리 토큰 낭비·성능 저하 방지 전체 코드베이스를 우겨넣는 것보다 필요할 때 탐색하는 방식이 낫다
시스템 프롬프트 튜닝 하네스 품질 격차의 원인 도구 설명 한 단어(deprecated)만 바꿔도 모델 행동이 달라짐
CLAUDE.md / agents.md 컨텍스트 선주입 수단 탐색 툴콜 없이 모델에게 프로젝트 정보를 미리 전달
컨텍스트 크기 vs 정확도 큰 컨텍스트 = 나쁜 성능 5~10만 토큰 구간을 넘으면 정확도가 50% 수준으로 급락
표준화된 Tool Call API 멀티 모델 하네스 구축 기준 Anthropic·OpenAI·Google 모두 전용 tool format 지원

내가 모를 만한 것 / 처음 보는 것

  • harness: 에이전트가 도구를 호출하고, 그 실행 결과를 다시 받아 모델에게 전달하는 실행 환경 전체. Claude Code·Cursor·Codex CLI가 harness. T3 Code는 harness 위에 얹힌 UI. → Harness-하네스
  • tool calling (툴콜링): 모델이 특별 문법으로 응답하면 하네스가 그 코드/명령을 실제로 실행하고 결과를 채팅 히스토리에 추가하는 패턴
  • repomix (리포믹스): 코드베이스를 XML 하나로 압축해 컨텍스트에 통째로 붙여넣는 구식 방법. 이제 사실상 사용 안 됨
  • bootstrapping (부트스트래핑): CLAUDE.md 같은 파일로 초기 컨텍스트를 미리 채워 모델이 탐색 없이 바로 작업하게 만드는 과정
  • openrouter: 여러 AI 모델을 단일 API로 라우팅해주는 중간 플랫폼. 각 모델에 맞게 tool format을 자동 변환해줌
  • 매크로스코프 (Macroscope): PR 요약·팀 활동 인사이트를 슬랙봇으로 제공하는 도구 (영상 스폰서)
  • edit_file 도구 구현: old_string → new_string 치환. old_string이 비어있으면 파일 신규 생성, 없으면 에러 반환

화자의 디테일 (놓치기 쉬운 포인트)

  1. 벤치마크 수치: Matt Maier의 독립 벤치마크에서 Claude Opus가 Claude Code 하네스에서 77%, Cursor 하네스에서 93%를 기록. 차이는 하네스뿐임.
  2. 컨텍스트 크기 임계치: Sonnet 모델 기준 약 5만~10만 토큰 구간을 넘기면 컨텍스트 내 반복 단어 찾기 정확도가 이전 대비 약 50% 수준으로 급락.
  3. 미니 에이전트 코드 크기: 도구 3개(read_file, list_files, edit_file) + 루프 구조 = 총 약 200줄 미만. bash 도구만 남기면 75줄로 줄어듦.
  4. 툴콜 순간 모델 연결 끊김: 모델이 tool call 문법으로 응답하는 순간 해당 연결·스레드는 종료. 채팅 히스토리는 클라이언트(하네스) 쪽에만 존재하고, 결과를 붙여서 새 API 요청을 보냄.
  5. 하네스는 모델을 속일 수 있음: read_file 이름의 도구가 실제로는 "Hello World"만 반환해도 모델은 그것이 파일 내용이라고 믿음. 도구 이름과 실제 구현이 일치할 필요가 없음.
  6. Gemini 모델과 deprecated 반응 차이: deprecated 표시를 넣었을 때 Claude는 여전히 read_file 툴을 쓴 반면, Gemini는 나머지 툴도 멀쩡한데 전부 bash로 이동. 모델마다 툴 설명 반응이 다름.
  7. Cursor의 하네스 전담팀: 새 모델 출시나 얼리 액세스 시점에 시스템 프롬프트를 수백 가지 방식으로 조금씩 바꾸며 미세 조정하는 전담 인력이 있음.
  8. Anthropic·Google의 구독 제한: Gemini 월 $250, Opus 월 $200 구독은 자사 하네스 외에서 쓰기 어렵게 되어 있음. OpenAI는 사실상 어디서나 구독 사용 허용.
  9. T3 Code 구조: 자체 도구가 없음. 모델 선택 시 컴퓨터에 설치된 Claude Code 하네스 또는 Codex CLI를 직접 호출하는 UI 레이어.
  10. 병렬 툴 호출: 하네스는 한 번의 응답에서 여러 툴 호출을 받아 병렬로 실행 후 결과를 한 번에 컨텍스트에 추가할 수 있음.
  11. 리포믹스 패망 이유: 코드베이스 전체를 컨텍스트에 넣는 것은 "30초마다 기억이 리셋되는 사람에게 2천 개 파일을 주고 버그 2개 있는 파일을 찾으라는 것"과 같음.
  12. Ampcode 글 인용: "도구 3개(read, list, edit)와 200줄 미만 코드로 동작하는 코딩 에이전트를 만들 수 있다"는 글을 직접 실증함.

1. 하네스(Harness)란 무엇인가

"하네스"는 AI 코딩 도구에서 자주 쓰이는 용어다. 단순하게 말하면 에이전트가 작동하는 도구 세트와 실행 환경이다. Claude Code·Cursor·Codex CLI가 harness이고, T3 Code는 harness 위에 얹힌 UI다.

하네스가 중요한 이유는 같은 모델이라도 어떤 하네스 위에서 돌리느냐에 따라 성능이 크게 달라지기 때문이다. Matt Maier의 독립 벤치마크에서 Opus는 Claude Code 하네스에서 77%, Cursor 하네스에서 93%를 기록했다. 달라진 건 하네스뿐이다.

2. LLM의 한계 — 텍스트만 생성한다

LLM은 근본적으로 텍스트 자동완성 엔진이다. 주어진 텍스트를 받아 다음에 올 가능성이 높은 텍스트를 계속 이어 붙인다. 파일 수정·명령 실행·인터넷 검색을 직접 하지 못한다.

그렇다면 Claude Code는 어떻게 파일을 수정하는가? → Tool Calling 덕분이다.

3. Tool Calling 메커니즘

Tool Calling의 흐름:

  1. 시스템 프롬프트에서 모델에게 "이 도구들이 있고, 이 문법으로 호출하라"고 안내한다.
  2. 모델이 특별 문법(예: <bash_call>ls -a</bash_call>)으로 응답하는 순간 모델과의 연결은 종료된다.
  3. 하네스가 그 툴 호출을 감지해 실제로 실행한다. 설정에 따라 사용자에게 허용 여부를 묻기도 한다.
  4. 실행 결과를 채팅 히스토리 맨 뒤에 붙인다.
  5. 같은 모델에 새 API 요청을 보내 작업을 이어간다.

이 루프가 반복되면서 에이전트는 마치 "계속 작업"하는 것처럼 보인다. 실제로는 매 툴 호출마다 모델이 멈췄다가 다시 시작된다.

병렬 툴 호출: 하나의 응답에서 여러 툴 호출을 한 번에 보낼 수 있고, 하네스는 이를 병렬로 실행해 결과를 한 번에 컨텍스트에 추가할 수 있다.

4. 컨텍스트 관리 — 채팅 히스토리에 없으면 모델은 모른다

모델은 채팅 히스토리에 있는 것만 안다. 코드베이스에 무엇이 있는지는 탐색 전까지 모른다.

컨텍스트를 채우는 두 가지 방법:

  • 선주입(CLAUDE.md / agents.md): 파일에 프로젝트 설명을 써두면, 하네스가 대화 시작 전 이를 시스템 메시지/히스토리에 미리 넣어준다. 탐색 툴콜이 줄거나 생략된다.
  • 후주입(탐색 툴콜): 모델이 list_files → read_file 등을 호출하며 스스로 컨텍스트를 구성한다. 결과가 히스토리에 쌓이면 다음 쿼리에서 탐색이 줄어든다.

같은 스레드를 유지하면 좋은 이유: 파일 위치를 이미 히스토리에서 알고 있으니 새 스레드에서 매번 다시 탐색하지 않아도 된다.

5. 컨텍스트 크기 함정 — 많이 넣을수록 나빠진다

"리포믹스(repomix)"처럼 코드베이스 전체를 XML 한 파일로 만들어 컨텍스트에 붙여넣는 방식은 이제 사실상 사라졌다. 이유:

  • 2천 개 파일을 주고 버그 2개짜리 파일을 찾으라는 것과 같다.
  • 약 5만~10만 토큰 구간을 넘기면 컨텍스트 내 반복 단어 정확도가 이전의 50% 수준으로 급락한다는 연구 결과가 있다.

모델이 스스로 탐색해 필요한 컨텍스트만 가져오는 방식이 훨씬 낫다. Opus 4.5·4.6, Sonnet 4, GPT-5.3·5.4 같은 최신 모델들은 이 탐색을 잘 수행한다.

6. 미니 에이전트 직접 구현 (Python)

Theo가 직접 만든 미니 에이전트 구조:

도구 3개: - read_file(path) — 파일 전체 내용 반환 - list_files(path) — 파일명·타입 목록 반환 - edit_file(path, old_string, new_string) — old_string → new_string 치환. old_string이 빈 문자열이면 파일 신규 생성

핵심 루프: 1. 사용자 입력 → 메시지 히스토리에 추가 2. Anthropic SDK로 모델 호출 (시스템 프롬프트 + 메시지 배열) 3. 응답에서 툴 호출 파싱 4. 툴 실행 → 결과를 히스토리에 추가 5. 툴 호출이 없으면 최종 응답 출력

코드 크기: - 도구 3개 + 루프: 약 200줄 미만 - bash 도구만 남기면: 75줄 (read_file·list_files·edit_file을 bash 명령으로 대체)

7. 시스템 프롬프트 튜닝이 하네스 품질을 결정한다

실험: read_file 도구 설명에 "deprecated"를 추가하자: - Claude: 여전히 read_file 선택 (합리적이라 판단) - Gemini: 나머지 도구도 멀쩡한데 전부 bash로 이동

모델마다 툴 설명에 대한 반응이 다르다. 그래서 Cursor는 지원 모델마다 시스템 프롬프트와 툴 설명을 별도로 조정하는 전담 인력을 두고 있다.

하네스가 모델을 속일 수 있다는 사실: read_file 이름의 도구가 항상 "Hello World"만 반환해도 모델은 그것을 파일 내용으로 믿는다. 도구 이름과 실제 구현이 일치할 필요가 없다. 가짜 bash 환경을 만들거나, 다른 모델을 도구처럼 연결하는 것도 가능하다.

8. T3 Code vs Cursor vs Claude Code — 구조 비교

도구 harness 여부 설명
Claude Code 자체 harness Anthropic이 직접 만든 harness
Cursor 자체 harness 모델별 시스템 프롬프트 전담 튜닝
Codex CLI 자체 harness OpenAI harness
Open Code 자체 harness 오픈소스
T3 Code harness 아님 Claude Code / Codex CLI harness 위에 UI를 얹은 것

T3 Code는 모델 선택 시 해당 하네스(Claude Code 또는 Codex CLI)가 로컬에 설치·로그인되어 있어야 작동한다. 자체 도구(bash, read 등)를 가지지 않는다.

9. 왜 Cursor harness가 더 나은가

Theo의 답: 더 많이 테스트했기 때문. 새 모델이 나오면 시스템 프롬프트를 수백 가지 방식으로 조금씩 바꾸며 모델이 원하는 대로 움직일 때까지 반복한다. Anthropic은 Claude Code용 프롬프트를 초기 작성 후 거의 수정하지 않았을 가능성이 높다. (그리고 모델이 대신 써줬을 가능성도 높다.)

Theo 개인 선호: Gemini와 Opus 모두 직접 쓰는 것보다 Cursor를 통해 쓰는 편이 낫다. GPT 모델은 차이가 거의 없다.

교정 전사 (한국어)

전체 전사 펼치기

이 채널을 운영하면서 배운 게 있다면, 여러분은 "에이전트 코딩"이니 "바이브 코딩"이니 하는 딱히 뜻도 없는 모호한 용어를 정말 좋아한다는 거예요. 그리고 저도 이제 에이전트가 뭔지는 알 것 같은데, 또 하나 다뤄야 할 새 용어가 생겼어요. 바로 하네스(harness)예요.

요즘 하네스 얘기를 훨씬 더 많이 하는 이유는, AI로 코딩할 수 있게 해주는 T3 Code라는 앱을 막 내놨기 때문이에요. 중요한 건 T3 Code는 하네스가 아니고, Open Code는 하네스라는 점이에요. 커서도, Claude Code도, Codex도 그래요.

하네스는 아주 특정한 뜻을 가진 용어예요. 그리고 어떤 하네스를 쓰느냐가 이런 도구에서 나오는 코드 품질에 정말 큰 영향을 줘요. Matt Maier가 최근 Cursor 안팎에서 여러 모델을 비교한 독립 벤치마크에 따르면, 대부분의 모델이 유의미한 성능 향상을 보였고, Opus는 Claude Code에서 77%였던 게 Cursor에서는 93%까지 올라갔어요. 여기서 다른 건 하네스뿐이에요.

그럼 대체 하네스가 뭘까요? 지금부터 자세히 설명하고 직접 하나 만들어 보겠습니다.

(스폰서 구간 — Macroscope 슬랙봇 소개 생략)

하네스가 뭔지 아주 단순하게 말하면, 하네스는 에이전트가 작동하는 도구 세트와 환경이에요. AI가 활용할 수 있는 기반 같은 거죠. 텍스트를 만들어서 무언가를 하게 하는 거예요.

더 쉽게 말씀드릴게요. 평범한 채팅에서 "이 폴더에 어떤 파일이 있어요?"라고 물어봤다고 해봅시다. 그 폴더에서 ls -a를 실행하면 되겠죠. 그런데 AI는 어떻게 명령어를 실행할까요?

기본적으로, LLM은 그냥 텍스트로만 답합니다. 우리가 매일 쓰는 LLM은 사실 엄청 고도화된 자동완성에 가깝습니다. 텍스트를 주면 다음에 올 내용을 예측하는 거죠. 가장 가능성 높은 다음 글자들을 계속 이어 붙이는 겁니다. 직접 코드를 작성하거나 파일을 수정할 수 없어요. 텍스트를 받으면 텍스트를 더 만들어 낼 수 있을 뿐입니다.

그런데 텍스트만 생성할 수 있다면, 모델이 어떻게 파일을 수정하고, 데이터베이스를 바꾸고, 인터넷에서 정보를 찾을 수 있을까요? 그래서 모델에 더 많은 능력을 주기 위한 방법들을 만들어 냈습니다. 가장 핵심은 툴 콜링(tool calling)이에요.

쉽게 말해 툴 콜은 특별한 문법으로 작동해요. 예를 들어 bash 명령을 실행할 수 있는 도구가 하나 있다고 해볼게요. 모델은 시스템 프롬프트에서 "이 도구가 있고, <bash_call> 태그로 감싼 다음 명령을 쓰고 닫아라"는 안내를 받아요. 이 문법으로 응답하고 나면 거기서 응답을 멈춰요. 그러면 시스템에서 그걸 실행하고, 끝나면 결과를 다시 돌려줘요.

여기서 정말 흥미로운 점은, 모델이 이 문법으로 응답하는 순간 연결이 끊기고 모델 응답이 끝난다는 거예요. 그 순간 채팅 기록은 오직 여러분 쪽(하네스)에만 남아요.

그럼 다음엔 뭐가 일어날까요? 이게 바로 하네스가 하는 일이에요. 툴 콜이 하네스로 넘어가면, 하네스는 전통적인 코드로 그걸 실행해요. 설정에 따라 바로 실행하거나 사용자에게 허용 여부를 물어봐요.

Claude Code에서 일반 모드로 실행하면 ls 같은 안전한 명령은 그냥 실행하지만, 파일을 수정하는 경우엔 사용자에게 허용 여부를 묻습니다. 파괴적인 툴 호출임을 AI 수준이 아니라 코드 수준에서 감지해서 묻는 거예요.

실행이 끝나면 출력을 채팅 히스토리 맨 뒤에 붙이고, 같은 모델에 새 요청을 보내서 이어서 진행합니다. 결국 툴 호출이 있을 때마다 모델은 잠깐 멈췄다가 다시 시작되는 거예요.

하네스가 관리하는 것들: - 모델에 전달할 도구 목록과 그 설명 - 툴 호출 실행 및 권한 검사 - 채팅 히스토리 관리 및 API 재호출

컨텍스트도 중요해요. 채팅 히스토리에 없는 정보는 모델이 몰라요. 코드베이스를 모르면 탐색 툴을 써서 파일 목록과 내용을 하나씩 읽어 히스토리에 쌓아야 합니다. 처음에 여러 read 호출을 병렬로 돌리기도 해요. 이 모든 과정이 컨텍스트를 채우는 거예요.

CLAUDE.md 파일이 하는 일은, 그 내용을 히스토리 맨 앞에 미리 넣어줘서 탐색 없이 바로 작업하게 만드는 거예요. CLAUDE.md가 있으면 모델이 "이 프로젝트가 뭐예요?"라는 질문에 파일 탐색 없이 바로 답할 수 있어요. 없으면 search 툴을 먼저 호출해야 하죠.

컨텍스트 크기 문제: 리포믹스(repomix)처럼 코드베이스 전체를 컨텍스트에 우겨넣는 방식은 이제 사실상 사라졌어요. "버그가 있는 파일 두 개를 주는 것과 2천 개를 주는 것 중 뭐가 더 쉽냐"고 생각해보세요. 컨텍스트가 많아질수록 모델이 더 멍청하게 동작해요. 약 5만~10만 토큰 구간을 넘기면 정확도가 50% 수준으로 급락합니다.

그래서 하네스가 흥미로운 이유가 바로 이것이에요. 하네스는 모델에 스스로 컨텍스트를 만들 도구를 줘서, 뭘 바꿔야 하는지 찾게 하고, 실제로 변경까지 하게 해줍니다.

미니 에이전트 구현 살펴보기: Ampcode 글에 나온 것처럼 도구 3개면 됩니다. - read_file: 파일 이름을 받아 내용 반환 - list_files: 디렉토리 내 파일 목록과 타입 반환 - edit_file: old_string → new_string 치환. old_string이 빈 문자열이면 파일 신규 생성

도구 레지스트리에 이 함수들을 등록하고, 각 도구에 이름·설명·파라미터 문서를 붙여요. 시스템 프롬프트에는 "이 도구들이 있고, TOOL:도구이름 {json인자} 형식으로 한 줄로만 호출하라"고 명시합니다.

루프: 사용자 입력 → 모델 호출 → 응답에서 TOOL: 파싱 → 해당 함수 실행 → 결과를 히스토리에 추가 → 다시 모델 호출. 툴 호출이 없으면 텍스트 응답 출력 후 다음 사용자 입력 대기.

bash 도구만 남기면 75줄로 줄어들고, read_file·list_files·edit_file 없이도 bash 명령(cat, ls, sed)으로 대체해서 똑같이 동작해요.

하네스가 모델을 속일 수 있다: read_file 이름의 도구가 항상 "Hello World"만 반환해도 모델은 그것을 파일 내용으로 믿어요. 실제로 이를 활용하면 가짜 실행 환경을 만들거나, 한 모델이 다른 모델의 응답을 도구 결과로 받는 구조도 가능해요.

현대 API의 표준 tool format: Anthropic·OpenAI·Google 모두 요청 바디에 도구 목록을 전달하는 표준 포맷을 지원해요. openrouter 같은 플랫폼은 모델마다 내부 포맷이 다른 것을 대신 변환해줘요.

시스템 프롬프트 튜닝 실험: read_file 설명에 "deprecated"를 추가했을 때, Claude는 여전히 read_file을 선택했고, Gemini는 전부 bash로 이동했어요. 모델마다 반응이 달라서, Cursor는 지원 모델마다 시스템 프롬프트를 따로 튜닝하는 전담 인력이 있어요.

T3 Code 정리: T3 Code는 자체 harness가 없어요. 모델 선택 시 로컬에 설치된 Claude Code 또는 Codex CLI harness를 호출합니다. T3 Code = 그 harness 위의 UI 레이어예요. harness 직접 구현이 가능했다면 훨씬 유연했겠지만, 지금은 기존 harness를 감싸는 방식으로 운영 중입니다.

마지막으로: AI 코딩 어시스턴트의 핵심은 마법이 아니에요. 파이썬 60~75줄짜리 루프와 도구 3개예요. 그게 Claude Code나 Cursor의 핵심을 이루는 구조이기도 합니다.
