먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 3분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 대담에서 말하는 오픈 모델은 기업이 직접 내려받거나 여러 제공자를 통해 실행할 수 있는 AI 모델을 뜻한다. 화자에 따르면 기업이 먼저 느끼는 장점은 비용 절감이다. 모델 사용료가 낮아지면 사람이나 에이전트가 더 많은 토큰을 쓰며 긴 작업을 시도할 수 있고, 기업은 이후 자사 용도에 맞춘 통제와 조정을 검토할 여유를 얻는다. 다만 싸다는 사실만으로 맞춤화·보안·품질이 자동으로 해결되지는 않는다.

모든 작업에 가장 강한 모델을 쓰는 대신, 쉬운 반복 작업은 저렴한 모델이나 로컬 모델에 맡기고 어려운 작업만 강한 클라우드 모델로 보내는 방식이 제안된다. 어떤 작업을 어디로 보낼지 정하는 장치가 라우터이고, 여러 모델과 도구를 연결해 일을 끝내는 과정이 오케스트레이션이다. 중요한 기준도 토큰 하나의 가격보다 실제 작업 하나를 통과시키는 비용과 품질로 바뀐다.

모델이 많아질수록 새로운 병목도 생긴다. 모델마다 실행 방식, 도구 호출, 하드웨어, 속도와 안전 장치가 다르기 때문이다. 그래서 모델 자체보다 이를 안정적으로 연결하는 실행 환경, 보안, 데이터 저장, 평가와 큐레이션의 가치가 커진다는 것이 대담의 중심 주장이다.

여기까지만 이해하면 충분

  • 저렴한 모델은 같은 예산으로 더 많은 작업을 시도하게 하지만, 품질과 안전을 보장하지는 않는다.
  • 쉬운 작업과 어려운 작업을 나눠 서로 다른 모델에 보내는 혼합 구조가 제안된다.
  • 모델이 흔해질수록 라우팅·실행·보안·평가처럼 모델 위의 계층이 새로운 병목이 된다.
  • 선택 기준은 모델 이름보다 작업 성공률, 비용, 지연과 위험이어야 한다.

  • 비용 절감 주장을 실제 업무에서 검증하려면 무엇을 측정해야 하는가?

비유와 깨지는 지점

파트너와 여러 실무자가 있는 조직

대담은 강한 모델을 어려운 판단을 맡는 파트너에, 저렴한 모델을 세부 업무를 나눠 수행하는 실무자에 비유한다. 라우터와 오케스트레이션은 업무를 배정하고 결과를 모으는 운영 체계에 해당한다.

비유가 깨지는 지점: 사람은 책임과 맥락을 스스로 협상하지만 모델은 그렇지 않다. 권한, 데이터 접근, 실패 처리와 최종 검증을 시스템이 명시해야 하며, 여러 저가 모델을 묶는다고 항상 강한 모델과 같은 결과가 나오지는 않는다.

1. 원인

모범 답안 보기

비용이 낮아지면 더 긴 작업과 더 많은 재시도를 허용할 수 있다. 에이전트는 그 과정에서 도구와 데이터를 반복해서 사용하므로 토큰 소비가 증가한다. 여러 저가 모델을 작업별로 배치하려면 선택, 상태 저장, 권한, 실패 처리와 평가가 필요해져 모델 위 계층의 수요도 커진다.

2. 대조

‘토큰당 가장 싼 모델’과 ‘작업당 가장 경제적인 모델’은 어떻게 다른가?

모범 답안 보기

토큰당 가격은 입력과 출력의 단가만 본다. 작업당 경제성은 성공률, 필요한 재시도, 처리 시간, 검수 비용과 실패 위험까지 함께 본다. 싼 모델이 반복 실패하면 최종 작업 비용은 더 높아질 수 있다.

3. 적용

반복 업무 하나를 오픈 모델로 옮길지 판단한다면 어떤 순서로 시험해야 하는가?

모범 답안 보기

먼저 입력과 합격 기준이 분명하고 실패 위험이 낮은 작업을 고른다. 같은 사례를 후보 모델과 기준 모델에 실행한 뒤 합격률을 비교한다. 기준을 통과한 경우에만 비용과 속도를 추가로 비교하고, 보안·권한·예외 처리가 필요한 작업은 별도로 검토한다.

이번 글의 통찰

1. 모델의 풍요는 연결 계층의 희소성을 만든다

  • [원문] 화자는 오픈 모델과 제공자가 늘면서 모델 토큰은 풍부해졌고, 지식 연결·조정·실행·보안·큐레이션이 새로운 문제로 떠오른다고 주장한다.
  • [해석] 원재료가 싸지고 많아질수록 차별점은 원재료 자체보다 알맞게 선택하고 안전하게 완제품으로 만드는 운영 능력으로 이동한다.
  • [경계] 소개된 성장률과 사용 분포는 Ollama 측 관찰과 대담 속 그래프에 근거하지만 원자료·산식·표본은 제공되지 않았다.

2. 최강 모델 하나보다 작업별 배치가 경제적일 수 있다

  • [원문] 화자는 쉬운 작업은 로컬·저비용 모델로, 어려운 작업은 강한 클라우드 모델로 보내는 혼합 실행을 예상한다. 오픈 모델이 기업 토큰의 80~90%를 맡을 수 있다는 전망도 제시한다.
  • [해석] 모델 선택은 브랜드 순위가 아니라 업무 난이도, 실패 비용, 지연과 데이터 조건을 함께 보는 자원 배분 문제다.
  • [경계] 80~90%는 화자의 미래 전망이며 검증된 시장 비율이 아니다. “80%의 작업에 충분하다”는 Flash 모델 평가도 구체적인 업무 목록과 평가 기준이 제시되지 않았다.

3. 사용자의 사랑과 수익화는 서로 다른 검증이다

  • [원문] Ollama 공동창업자는 2021년 YC 참여 후 여러 아이디어를 거쳤고, 2023년 로컬 모델 실행 도구를 빠르게 출시해 사용자를 얻었지만 클라우드 수익화는 그보다 뒤에 시작했다고 설명한다.
  • [해석] 배포와 반복 사용은 문제 적합성의 증거가 될 수 있지만, 누가 무엇에 돈을 내는지는 별도의 고객 검증이 필요하다.
  • [경계] 현재 178,000 GitHub 스타와 과거 100,000 스타는 서로 다른 시점의 수치로 보이지만 각 측정 날짜가 없다. Fortune 500 확산 기간도 대담에서 “2년 정도”, “18개월”, “12개월”로 다르게 언급된다.

1. 기업의 오픈 모델 이동

진행자는 Jeffrey Morgan을 Ollama 공동창업자이자 CEO로 소개한다. 또한 Ollama가 개발자 900만 명에게 사용되고, GitHub 스타 178,000개를 받았으며, Fortune 500의 85%에서 사용된다고 말한다. 이 수치의 산식과 사용 강도는 제시되지 않는다.

Morgan은 기업이 오픈 모델로 이동하는 가장 큰 단기 이유를 비용이라고 말한다. 비용이 낮아지면 기업별 통제와 맞춤화를 추진할 수 있다는 설명이다. AT&T가 토큰 소비의 40%를 오픈 모델로 옮겼다는 The Information의 전날 기사를 사례로 들지만 기사 제목과 원문은 제공되지 않았다.

미세조정은 모델 출시가 빨라질수록 새 모델에 밀릴 위험이 있지만, 도구가 좋아져 계속 활용될 가능성도 있다고 본다. 기업 도입의 주요 장애물로는 보안과 안전을 꼽는다.

2. 토큰 사용 폭증

Ollama Cloud에서 사용자당 주간 토큰 사용량이 크게 증가했으며, 초기 증가는 코딩 에이전트, 이후 증가는 OpenClaw와 Hermes 같은 동료형 에이전트가 이끌었다고 설명한다. 에이전트는 도구 선택과 데이터 탐색을 반복하고 긴 작업을 수행하므로 많은 토큰을 쓴다.

대담에는 다음 수치가 등장한다.

  • OpenClaw 전후 사용자당 변화: 대략 5배로 표현
  • 당시 기준점으로 추정된 사용량: 약 1,500만 토큰
  • Cloud 전체 증가: 10~20배 이상이라는 표현
  • 연초 이후 Cloud 성장: 150배
  • 컨텍스트 창: 128K에서 100만 이상으로 확대

이 숫자들은 사용자당·전체·특정 변곡점·연초 이후라는 서로 다른 범위를 가리킨다. 하나의 성장률로 합치면 안 된다.

3. 출시와 모델 위의 숨은 계층

새 모델을 출시하려면 추론 엔진 지원, 속도와 정확도 확인, 도구 호출 방식, 하네스, 클라우드 용량, 하드웨어 최적화가 함께 준비돼야 한다. 사전 접근이 몇 주 주어질 때도 있지만 마지막 24시간에 작업이 몰리는 경우도 있다고 한다.

Ollama의 역할은 운영체제처럼 하드웨어·추론 계층과 애플리케이션 실행 환경을 연결하는 것으로 설명된다. 모델과 앱 사이에는 다음 문제가 남는다.

  1. 지식: 기업 데이터와 최신 맥락을 어떻게 연결할 것인가.
  2. 조정: 여러 하위 에이전트와 로컬·클라우드 실행을 어떻게 나눌 것인가.
  3. 실행: 샌드박스와 계산 자원을 어떻게 제공할 것인가.
  4. 상태와 보안: 기억, 저장, 자격 증명, 안전 정책을 어디에서 관리할 것인가.

화자는 저장이 필요한 상태 문제는 학습이 끝난 모델 안으로 완전히 들어가기 어렵다고 본다. 모델과 제공자가 풍부해지면 이를 일관되게 연결하고 고르는 큐레이션이 희소해진다는 결론이다.

4. 오픈·폐쇄형, 로컬·클라우드의 혼합

Morgan은 장기적으로 기업 토큰의 80~90%가 오픈 모델을 통과할 수 있지만 비용 비중은 10~20%에 그칠 수 있다고 전망한다. 가장 어려운 작업은 강한 폐쇄형 모델에 남고, 세부 업무는 저렴한 모델이 처리하는 혼합 구조다.

로컬에서는 미국·유럽·중국 계열 모델이 섞여 사용되지만, Ollama Cloud에서는 중국 계열 모델이 우세하다고 설명한다. 쉬운 문서 처리는 로컬에서 잘 작동하고, 복잡한 코딩 에이전트는 대형 클라우드 모델이 더 효과적이라는 관찰도 제시한다.

하드웨어와 관련해서는 다음 주장이 나온다.

  • 일반적인 로컬 실행 범위: 200억~400억 파라미터, 때로는 1,280억
  • DGX Spark: 통합 메모리 128GB, 약 200억~1,200억 파라미터 범위
  • 여러 장치를 연결하면 4,000억 파라미터 모델도 실행 가능하다는 주장
  • Qwen3 8B가 코딩 벤치마크에서 Claude Opus 4.6과 동급이라는 발언

이 수치는 모델 압축, 정밀도, 메모리, 속도 조건이 빠져 있어 일반적인 실행 보장으로 읽으면 안 된다.

5. Ollama의 창업 과정

공동창업자들은 과거 Docker Desktop을 만들었고, 2021년 겨울 YC에 다른 아이디어로 참여했다고 설명한다. 초기에는 Kubernetes와 데스크톱 보안 문제를 탐색했으며, Benchmark와는 2022년에 협력했다고 말한다.

2023년 토론토에서 기존 아이디어를 버리고 팀의 VMware·Docker 경험에 맞는 문제를 다시 찾았다. 모든 모델에 접근하는 게이트웨이와 오픈 모델을 쉽게 실행하는 시스템이라는 두 후보를 검토했고, 2주 안에 첫 제품을 출시하기로 했다. Llama 2 출시에 맞춰 공개한 뒤 이전 제품보다 빠르게 사용자를 얻었다고 회고한다.

Ollama는 2023년 7월 출시됐고 GitHub 스타 100,000개를 빠르게 달성했지만 당시에는 수익이 없었다. Ollama Cloud를 통한 수익화는 대담이 말하는 “올해 초”에 시작됐다. 공동창업자는 오픈소스 사용자를 인터넷의 익명 집단으로만 보지 말고 실제 고객을 만나 미래 요구를 확인해야 한다고 강조한다.

마지막에는 과거 인프라 업계의 규칙이 AI에 그대로 적용되지 않는다고 말한다. AI에서는 상위 계층이 고객과 가까워 오히려 유리할 수 있고, LLM의 비결정성은 제거할 결함만이 아니라 활용해야 할 특성이라는 주장이다.

6. 수치·이름·표현 경계

  • [경계] 성장률: 사용자당 약 5배, Cloud 전체 10~20배 이상, 연초 이후 150배는 범위와 기간이 다르다. 원본 그래프가 없어 상호 환산할 수 없다.
  • [경계] 클라우드 모델 국적: Morgan은 “주로 중국 계열”이라고 했지만 진행자는 그래프를 “거의 100% 중국 모델”이라고 표현했다. 정확한 비율이 없으므로 두 표현을 같은 수치로 취급할 수 없다.
  • [경계] 확산 기간: Fortune 500 확산을 두고 “2년 정도”, “18개월”, “12개월”이 연달아 언급된다. 합의된 기간이 아니다.
  • [경계] GitHub 스타: 현재 소개의 178,000개와 과거 이정표 100,000개는 시점이 다른 것으로 보인다. 각 측정일은 없다.
  • [경계] 장비 가격: 진행자가 워크스테이션 가격을 20만~30만 달러로 추정하자 Morgan은 더 경쟁력 있다고 답했지만 확정 가격을 제시하지 않았다.
  • [경계] 벤치마크: Qwen3 8B와 Claude Opus 4.6의 코딩 성능 비교에는 벤치마크 이름, 설정과 실제 업무 검증이 없다.
  • [경계] 안전성 표현: 한 부분에서는 선별 검사를 거친 모델 동작을 결정론적으로 표현하지만, 후반에는 LLM이 본질적으로 완벽하지 않고 비결정적이라고 말한다. 적용 범위가 설명되지 않아 일반화할 수 없다.
  • [경계] 고유명사: 전사에 등장하는 GPT Luna, Mythos, NERA는 문맥상 이름이 불명확하거나 전사 오류 가능성이 있다. 확인 없이 정확한 제품·회사명으로 확정하지 않는다.
  • [경계] 원작자 정보: META의 provenance는 Collapsing The Cost를 원작자 후보로 적으면서도 “화자 이름+SNS 기준 추정 출처”라고 명시한다. 원작자가 확인되지 않았으므로 frontmatter의 original_creator는 비워 두었다. affiliation도 META에서 null이므로 별도 소속을 확정하지 않았다.
  • [경계] 용어: 대담은 open model, open-source model, open-weight model을 느슨하게 섞어 쓴다. 공개 범위가 동일하다고 단정할 수 없다.

다양한 모델을 선택할 수 있다는 점에서 OpenRouter가 그 좋은 예라고 생각합니다. 개발자들은 수많은 제공업체에 각각 가입할 필요 없이 한 곳에 가서 한 곳에서 결제하면 됩니다. OpenCode를 통해서는 어떤 모델과도 통합되는 하나의 하네스를 사용할 수 있다는 점도 확인했습니다. 다음 모델을 시험해 보고 자신의 사용 사례에 더 잘 맞는지 확인하려는 개발자들에게는 정말 강력한 경험입니다.
