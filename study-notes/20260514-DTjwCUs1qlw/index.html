컨텍스트가 새로운 코드입니다

원작자 Patrick Debois · Tessl · 업로드 2026-05-14 · 27.2분 · 원본 영상 ↗
한 줄 요약

AI 코딩 에이전트의 성능은 LLM이 아니라 컨텍스트(프롬프트·규칙·스킬·문서)의 품질이 결정하므로, 컨텍스트를 코드처럼 생성·테스트·배포·관찰하는 엔지니어링 사이클을 갖춰야 한다.

원작자 Patrick Debois · Tessl · 추정 출처 https://x.com/patrickdebois · 업로드 2026-05-14 · 27분 · 전사 Whisper large-v3 (auto)

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Context Development Lifecycle (CDL) 컨텍스트도 소프트웨어 생명주기가 필요하다 Generate → Evaluate → Distribute → Observe 4단계
컨텍스트 eval (평가) 변경이 실제로 에이전트 행동에 어떤 영향을 주는지 측정 필요 LLM-as-a-judge + 반복 실행으로 통과율 측정
에러 버짓 (error budget) eval 결과가 비결정론적이라 단순 pass/fail 불가 5회 중 몇 회 통과 — 허용 실패율 사전 설정
컨텍스트 린터 / Grammarly 유사 도구 작성한 컨텍스트가 에이전트에 실제 이해되는지 검증 스펙 포맷 검증 + LLM 피드백 루프
스킬(Skill) 패키지 포맷 재사용 가능한 컨텍스트 단위 — 코드의 라이브러리에 해당 컨텍스트 + 스크립트 + 문서를 묶어 설치·공유
컨텍스트 레지스트리 팀·조직 간 컨텍스트 검색·설치 표준화 코드 패키지 레지스트리와 동일한 개념
컨텍스트 필터 (웹 방화벽 유사) 외부 스킬 다운로드 시 프롬프트 인젝션 차단 필요 샌드박스만으로는 agent.md 자동 로드를 막을 수 없음

내가 모를 만한 것 / 처음 보는 것

  • Tessl — Patrick Debois가 소속된 회사. 컨텍스트 관리·스킬 레지스트리 기능을 구현한 제품
  • SBOM (Software Bill of Materials) → "AI SBOM" 개념: 어떤 모델로 어떻게 빌드된 스킬인지 기록하는 메타데이터
  • spec-driven development — 프롬프트를 사양서(specification)로 작성하면 에이전트가 플래닝 모드로 단계별 프롬프트로 분해해 실행
  • Snyk의 컨텍스트 스캔 — 스킬 패키지에 포함된 자격증명 노출·서드파티 위험 탐지 (기존 코드 취약점 스캐너와 동일 역할)
  • Open Claw (OpenClaw) — 컨텍스트 보안 인식을 높인 계기로 언급됨 용어노트
  • 하네스 엔지니어링 (harness engineering) — 에이전트 실행 환경 전체(로그·트레이스·피드백)를 래핑하는 관찰가능성 레이어
  • AI DevCon — Patrick이 콘텐츠를 큐레이션하는 런던 컨퍼런스 (6/1-2 언급)

화자의 디테일 (놓치기 쉬운 포인트)

  1. agent.md 표준화 — Claude는 여전히 CLAUDE.md라고 부르는데, 화자는 공개적으로 "Boo Claude"라고 비판. 업계 표준은 agent.md로 수렴 중
  2. 레지스트리 스킬 품질 — "99.9%의 스킬은 쓰레기(crap)"라고 단언. 학습용으로는 유용하나 실제 eval을 돌려보면 품질 기준 미달
  3. 비결정론적 eval 실행 전략 — 1회 실행 결과로 pass/fail 판단 금지. 5회 이상 실행 후 통과율로 판단. 중요도에 따라 에러 버짓 차등 설정
  4. CI/CD에 eval 통합 — 컨텍스트 커밋마다 eval 실행 가능. 단, 반드시 반복 실행 통과율 기반이어야 함
  5. 에이전트 로그를 피드백 채널로 — 팀 전체 에이전트 로그를 집계해 "모두가 놓치는 컨텍스트" 자동 탐지 → 공통 컨텍스트 개선 → 전체 팀 혜택
  6. PR 피드백 = 컨텍스트 피드백 — PR 리뷰 코멘트는 단순히 그 코드가 아니라 그 코드를 생성한 컨텍스트의 문제이므로, 반복 방지를 위해 컨텍스트를 고쳐야 함
  7. 샌드박스 우회 한계 — 코딩 에이전트는 기본적으로 agent.md·skill.md를 자동 로드. 샌드박스가 있어도 이를 막지 못함. 별도 컨텍스트 필터 레이어 필요
  8. 음성 코딩(voice coding) 권장 — 타이핑보다 말로 코딩할 때 컨텍스트가 훨씬 풍부해진다고 개인 경험 공유 (두 손가락 타이핑으로 수십 년)
  9. "일관성 테스트"로 정의 품질 측정 — 동일 rough 플랜을 여러 에이전트에 병렬 투입 후 결과가 수렴하면 좋은 정의, 발산하면 원점 재검토
  10. DevOps 유추 — 2009년 "ops가 dev처럼 되면?"이라는 질문이 DevOps를 낳았듯, 지금 "context가 code가 되면?"이 CDL을 낳는다고 주장
  11. 컨텍스트 의존성 지옥 — 프론트엔드용 컨텍스트 패키지와 React 컨텍스트 패키지가 충돌하는 시나리오 이미 발생 중

# 섹션 요지
1 Generate (생성) 프롬프트·CLAUDE.md·문서·MCP·스펙 기반 컨텍스트 생성 방법
2 Evaluate (평가) 린터·Grammarly 유사 피드백·LLM-as-a-judge·E2E 테스트·에러 버짓
3 Distribute (배포) Git 체크인·스킬 패키지·레지스트리·보안 스캔·AI SBOM
4 Observe (관찰) 에이전트 로그 집계·PR 피드백·프로덕션 계측·컨텍스트 필터
5 확장 모델 개인 → 팀 → 팀의 팀으로 플라이휠 형성

1. Generate — 컨텍스트 생성

기본 수준: 사용자가 직접 타이핑해 프롬프트를 만든다.

중급: 재사용 가능한 프롬프트(instructions / agent.md / CLAUDE.md)를 작성해 팀과 공유.

고급 방식 3가지: - 라이브러리 문서 주입 — LLM 학습 데이터에 없는 최신 버전 문서를 pull해 환각 방지 - MCP 활용 — GitLab, GitHub, Slack 등에서 컨텍스트를 실시간 수집 - 스펙 기반 개발 (spec-driven development) — 프롬프트를 사양서로 작성 → 에이전트가 플래닝 모드로 단계별 실행

코드가 컨텍스트로 변환되는 사례: 복잡한 온보딩 로직을 "패키지 매니저 파악 → 에코시스템 파악 → 단계 안내"라는 스킬로 만들면, 직접 코딩으로는 불가능한 다양한 환경 처리가 가능해진다.

2. Evaluate — 컨텍스트 테스트

왜 필요한가: agent.md 두 줄을 바꿨을 때 에이전트 동작에 어떤 영향을 주는지 모른다면 YOLO 방식이다.

3단계 테스트 피라미드:

수준 코드 유사체 컨텍스트 적용
린팅 IDE 빨간줄 스킬 포맷 스펙 자동 검증 (description 길이, 필드 존재 여부 등)
단위 테스트 함수 단위 검증 "API 경로에 /awesome/ 접두가 있는가?" — LLM-as-a-judge로 판정
E2E 테스트 통합 실행 판사 에이전트에 툴(curl 등)을 주어 실제 실행 환경에서 검증

비결정론 대응: 동일 eval을 5회 실행 후 통과율로 판단. 중요한 케이스는 에러 버짓을 0에 가깝게, 덜 중요한 케이스는 느슨하게 설정.

CI/CD 통합: 컨텍스트 커밋마다 eval 스위트 실행. 단, 1회 통과가 아닌 통과율 기준으로 파이프라인 판정.

3. Distribute — 컨텍스트 배포

Git 체크인: 가장 단순한 공유 방법. 동료가 pull하면 즉시 동일한 컨텍스트 사용 가능.

스킬 패키지: 컨텍스트 + 스크립트 + 문서를 묶어 라이브러리처럼 설치. 코딩 에이전트들이 이를 준표준 패키지 포맷으로 지원하기 시작.

레지스트리: 스킬 검색·설치 인프라. 공개 레지스트리는 품질 편차가 크므로 팀 내부 레지스트리가 실제로 더 많이 쓰임.

보안 이슈: - 의존성 충돌: 컨텍스트 패키지 간 dependency hell 발생 가능 - Snyk 스캔: 자격증명 노출, 서드파티 위험 탐지 - AI SBOM: 어떤 모델이 어떻게 빌드한 스킬인지 메타데이터로 기록

4. Observe — 관찰과 피드백

에이전트 로그 집계: agent.md 표준화로 로그 포맷이 통일되면서 가능해짐. 팀 전체에서 에이전트가 반복적으로 "이 컨텍스트가 없다"고 신호를 보내면 공통 컨텍스트를 만들어 배포.

PR 피드백: PR 리뷰 코멘트 = 그 코드를 생성한 컨텍스트의 부족. 다음 이터레이션이 같은 실수를 반복하지 않으려면 컨텍스트를 고쳐야 한다.

프로덕션 계측: 코드를 래핑해 실패 시 어떤 입출력이 문제였는지 캡처 → 자동으로 테스트 케이스 생성 → 피드백 루프.

보안 관찰: - 샌드박스 에이전트가 환경변수를 읽거나 메모리 파일을 열람하는 행동을 실제로 확인 - 코딩 에이전트는 agent.md·skill.md를 기본으로 자동 로드하므로 샌드박스만으로 차단 불가 - 컨텍스트 필터 = WAF(웹 방화벽)처럼 프롬프트 인젝션 패턴을 차단하는 별도 레이어 필요

5. 확장 모델 — 개인에서 조직으로

개인(solo)
  └─ 팀(team): 컨텍스트 누락 발견 → 즉시 추가 → 팀 전체 혜택
       └─ 팀의 팀(org): 플라이휠 — A팀이 고치면 B팀도 재사용

핵심 메시지: LLM은 엔진이다. 잘못된 연료(컨텍스트)를 주면 성능이 나오지 않는다. LLM 자체를 바꿀 수 없는 개발자가 최적화할 수 있는 유일한 변수는 컨텍스트다.

운영 방법: 개인 마크다운 파일을 다듬는 것에서 시작해, 팀 반사 행동(문제 발생 → 컨텍스트 추가)으로, 최종적으로 Sonar + CI/CD 모델처럼 조직 전체 품질 개선 사이클로 확장.

교정 전사 (한국어)

전체 전사 펼치기

일찍 시작하길 원하는 분들이 계셔서, 아키텍트 트랙을 공식적으로 열겠습니다. 트랙 호스트가 없어서 제가 직접 합니다. 참석해주셔서 감사합니다. 좋은 컨퍼런스 보내셨길 바랍니다. 이렇게 많은 분들이 오셨다니 정말 대단합니다.

시작 전에 — 이 방에서 AI 코딩 에이전트를 써본 분 손 들어보세요. (손 내려주시고) 안 써본 분 손 들어보세요. 제 스타일의 사람들이네요. 완벽합니다.

"컨텍스트가 새로운 코드다" — 혹은 컨텍스트 개발 생명주기(Context Development Lifecycle)라고 할 수 있습니다. AI 엔지니어링 행사에서 올 때마다 영광입니다. 이번 발표는 조금 미완성된 생각입니다. 모든 게 갖춰진 건 아니지만, AI에서 뭔가 의미 있는 게 있는지 살펴봅니다.

여러분 모두 이제 프롬프트로 바이브 코딩(vibe coding)을 하고 있다고 가정합니다. 저는 더 이상 코드에 직접 손을 거의 안 댑니다. AI에게 무언가 다르게 해달라고 말하기만 합니다. 그래서 "컨텍스트가 새로운 코드"라고 하는 겁니다 — 코드가 생성되고 있으니까요.

조금 더 고급 단계를 보면, 저는 대형 코드 조각들을 가지고 있었고 헬퍼나 다른 조각들을 사용하다가 그것들을 스킬로 바꿨습니다. 제품에 적용했는데, AI 에이전트의 온보딩 문제였습니다. 사람들이 Python, Node.js 등 다양한 것을 쓰고, 패키징 도구도 다 달랐습니다. 그걸 직접 코딩하는 건 불가능했을 겁니다. 하지만 스킬 하나를 만들어서 "먼저 패키지 매니저를 파악하고, 에코시스템을 파악하고, 사용자와 함께 이 단계를 진행하라"고 하니까 직접 코딩으로는 해결 못했을 훨씬 많은 문제를 해결했습니다. 코드가 컨텍스트로(스킬·워크플로우 형태로) 역변환되고 있는 겁니다.

병렬 사고를 좋아합니다. 2009년에 DevOps 사람들에게 "ops가 dev처럼 보이면 어떨까?"라고 했더니 협업, 배포 자동화 등이 나왔습니다. 작년에 저는 "컨텍스트가 코드라면 어떻게 더 일관되게 다룰 수 있을까?"를 생각하기 시작했습니다. 소프트웨어 개발 생명주기가 있다면, 컨텍스트 개발 생명주기는 어떻게 생겼을까?

저는 DevOps 배경이 있어서 무한 루프로 구성했습니다. 핵심은: 컨텍스트를 생성(Generate)하고, 테스트하고(Evaluate), 동료·조직에 배포(Distribute)하고, 동작 여부를 관찰(Observe)하고, 작동 안 하면 적응해서 다시 생성하는 루프입니다.

Generate (생성): 여러분 모두 프롬프팅을 하고 있습니다. 인간이 직접 컨텍스트를 타이핑하는 것이죠. 저는 "제 AI 엔지니어링 강연이 언제냐?"고 물었더니 웹사이트를 fetch해서 바로 알려줬을 때 놀랐습니다. 제가 "나는 Patrick이다"라는 컨텍스트를 줬기 때문이죠.

조금 더 고급 — 프롬프팅이 반복적이면 재사용 가능한 프롬프트를 원하게 됩니다. 에이전트별로 instructions, agent.md(표준화 중), 혹은 여전히 CLAUDE.md라고 부르는 경우(Claude에 야유를 보내지만)가 있습니다. 재사용 가능한 컨텍스트 조각들입니다.

다른 컨텍스트 가져오기 — 사용하는 라이브러리의 최신 문서를 pull해야 합니다. LLM이 최신 문서를 모를 수 있어서 환각이 발생합니다. "버전 2인지 3인지" 모르죠. 그래서 문서를 에이전트 최적화 형태로 제공하면 해당 버전에 맞는 코드를 더 잘 생성합니다.

MCP가 핵심 역할 — GitLab, GitHub, Slack 등 어디서든 컨텍스트를 pull합니다. 티켓도 컨텍스트를 만들어줍니다.

그 다음 — 스펙 기반 개발(spec-driven development). 프롬프트를 사양서로 작성하면 에이전트가 플래닝 모드로 단계별 프롬프트로 분해해서 실행합니다.

Evaluate (평가): 컨텍스트를 모두 타이핑하고 만들었는데, agent.md 두 줄을 바꾸면 영향이 뭔지 압니까? YOLO인가요? "괜찮아 보이니까 그냥 하자"인가요? 컨텍스트를 테스트하는 방법을 생각해야 합니다. 코드도 있고 컨텍스트도 있는데, 둘 다 테스트를 써야 합니다. 새로운 코딩 에이전트가 어디서 기존 규칙을 깨는지 모릅니다. AI 엔지니어링 세계에서는 새롭지 않지만 AI로 코딩하는 세계에서는 아직 흔하지 않습니다.

eval(=컨텍스트 테스트)을 작성합니다. 코드 테스트의 여러 레벨처럼:

  • 린팅 수준: IDE의 빨간 물결처럼, 스킬의 description이 있는지·길이가 맞는지 포맷 검증. 간단한 린터를 실행.
  • Grammarly 유사: 컨텍스트가 실제로 에이전트에 이해되는가? "이 컨텍스트를 보고 당신이 이해한 게 뭐냐?"고 LLM에 물으면 "너무 짧다, 명시적이지 않다"는 피드백을 받을 수 있습니다. 그래서 저는 음성 코딩을 더 선호합니다 — 타이핑보다 말할 때 훨씬 더 자세하게 설명하게 됩니다.
  • 단위 테스트 수준: agent.md에 "모든 API 경로는 /awesome/ 접두를 써야 한다"는 규칙이 있다면, "save user 엔드포인트를 추가해라"고 했을 때 생성된 코드에 /awesome/user가 있는지 LLM에게 판정 요청. 규칙 없이 물으면 어떤 LLM도 /awesome/를 쓰지 않습니다.
  • E2E 테스트 수준: 판사(judge) LLM에게 툴을 줘서 실제로 curl을 실행하게 합니다. 코드만 보는 게 아니라 실제 실행 결과 검증. 특정 커밋 기준으로 "이 컨텍스트가 있을 때와 없을 때 차이가 있는가?"를 확인.

비결정론 대응: eval을 한 번 돌려서 pass/fail 판단 금지. 다섯 번 돌려서 몇 번 통과했는지로 판단. 어떤 테스트는 항상 100% 통과하지만 어떤 건 그렇지 않습니다. 컨텍스트 변경이 어떤 테스트 통과율에 영향을 주는지 확인. 에러 버짓 개념: 중요한 테스트는 실패를 최소한만 허용, 덜 중요한 건 느슨하게.

Distribute (배포): Git에 체크인하면 동료가 pull 시 즉시 사용 가능. 더 나아가 여러 프로젝트·팀에 재사용하려면 라이브러리처럼 패키지화해 설치. 이게 스킬입니다. 스킬은 컨텍스트뿐 아니라 스크립트, 문서 등을 포함할 수 있습니다. 코딩 에이전트들이 이를 준표준 패키지 포맷으로 지원하기 시작했습니다.

레지스트리: 어떤 패키지가 있는지 검색·설치하는 인프라. 공개 레지스트리 스킬의 99.9%는 품질이 낮다고 솔직하게 말합니다. 하지만 다른 사람들이 어떻게 하는지 배우기에는 좋습니다. 실제로는 조직 내부 레지스트리를 원하는 경향이 있습니다.

의존성 지옥: 코드 패키지처럼 컨텍스트 패키지 간에도 충돌이 발생합니다. 라이브러리 버전을 미러링하는 컨텍스트 패키지도 필요해집니다.

보안: 외부에서 받아온 스킬이 내 노트북에서 실행될 수 있습니다. OpenClaw 사건 이후 보안 인식이 높아졌습니다. Snyk이 컨텍스트를 스캔해 자격증명 노출·서드파티 위험을 탐지합니다. 누가 만든 스킬인지, 어떤 모델로 만들었는지를 기록하는 AI SBOM 개념도 등장했습니다.

Observe (관찰): 남이 쓰는 컨텍스트 라이브러리를 유지하고 싶다면 그것이 여전히 잘 동작하는지 어떻게 알 수 있을까요?

에이전트 로그 활용: 개발자가 에이전트가 원하는 대로 안 한다고 느끼면 직접 컨텍스트에 추가할 수 있습니다. 또는 팀·조직 규모에서 "모든 사람이 이 부분이 없다"고 신호를 보낸다면 그 컨텍스트를 만들어 배포 → 전체 개선 효과. agent.md처럼 로그 표준도 생기고 있어서 피드백 채널로 활용 가능.

PR 피드백: PR에 달린 "이건 맞지 않다"는 코멘트는 그 PR을 만든 컨텍스트의 피드백입니다. PR 논쟁보다는 컨텍스트를 개선해서 다음 이터레이션이 같은 실수를 안 하도록.

프로덕션 관찰: 생성된 코드가 프로덕션에서 실패하면 어떤 입출력이 문제였는지 자동 캡처 → 테스트 케이스 자동 생성 피드백 루프.

보안 관찰: 에이전트를 샌드박스에서 돌리면서 시스템 탈출을 시도해봤는데 환경변수를 읽고, 메모리 파일을 열람하는 등 여러 문제를 발견했습니다. 코딩 에이전트는 기본적으로 agent.md·skill.md를 자동 로드하므로 다운로드하면 즉시 로드됩니다. 샌드박스로 막을 수 없습니다. 별도의 컨텍스트 필터 — 웹 방화벽(WAF)처럼 프롬프트 인젝션 패턴을 차단하는 레이어 — 가 필요합니다.

하네스 엔지니어링 자체도 로그·트레이스·피드백 등 완전한 관찰가능성을 가지며, 훈련뿐 아니라 자체 운영에도 유용합니다.

마무리: 많은 분들에게 있어 "컨텍스트 생성 → 컨텍스트 테스트"가 라이브러리 작성 루프입니다. 엔터프라이즈로 가면 조직 루프: 라이브러리 만들고, 누군가 쓰고, 동작하는지 확인합니다. Sonar + CICD 모델의 컨텍스트 버전입니다.

지금 여러분은 아마 개인 솔로 모드로 자신의 마크다운을 다듬고 있을 겁니다. 팀으로 확장하면: 무언가 빠지면 컨텍스트를 추가하는 반사를 만드세요. 팀의 팀으로 가면: 여기서 고치면 다른 팀도 재사용하는 플라이휠이 됩니다.

LLM과 코딩 에이전트는 대단합니다. 하지만 그것들은 단지 엔진입니다. 잘못된 연료(컨텍스트)를 주면 작동하지 않습니다. LLM 자체는 바꿀 수 없지만, 컨텍스트는 최적화할 수 있습니다. 복사 붙여넣기에 의존하지 말고, 더 엔지니어링된 방식으로 합시다.

질의응답: 아키텍처 문제를 범위 정의하고 에이전트에 투입해 객관적 테스트를 만드는 것에 대한 질문 — "일관성을 eval의 형태로 쓰는 방법을 테스트 중입니다. 느슨한 정의를 에이전트 시스템에 여러 번 병렬 투입해서 얼마나 동일한 명확한 정의가 나오는지 확인합니다. 결과가 다 다르면 원래 정의가 나쁜 것 — 아키텍트에게 돌아가야 합니다. 다 같으면 좋은 정의입니다." eval을 엄격히 하다 보면 코드 절약이 아니라 right eval 작성에 많은 시간이 드는 현실도 있고, 고급 사용자들은 비즈니스 케이스에 맞는 eval을 빌드하는 자체 프로세스를 만들기도 합니다.
