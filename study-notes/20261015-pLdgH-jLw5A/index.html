큰 그림: “좋아 보인다”를 “비교 가능한 근거”로 바꾸기

이 발표의 중심 주제는 AI 기능이 좋아 보인다는 느낌만으로 출시하지 말고, 미리 정한 사례와 기준으로 시험하자는 것이다. 이런 시험 체계를 평가, 즉 eval이라고 부른다.

화자는 엔지니어나 제품 관리자가 프롬프트 몇 개를 직접 써 본 뒤 “괜찮아 보인다”고 출시를 결정하는 상황을 문제로 든다. 몇 번의 성공만으로는 실제 사용자의 다양한 입력, 실패하기 쉬운 조건, 비용 증가, 이전보다 나빠진 부분을 알기 어렵기 때문이다.

평가는 질문에서 시작한다. 어떤 모델이 목적에 맞는지, 영어와 일본어에서 성능이 다른지, Python과 TypeScript에서 차이가 나는지, 회사의 말투를 지키는지, 변경 후 무엇이 나빠졌는지를 묻는다. 그런 다음 같은 조건에서 결과를 비교할 수 있도록 데이터와 판정 규칙을 만든다.

읽는 법: 위에서 아래로 읽는다. 빨간 상자는 피하려는 상태, 가운데 상자들은 평가를 만드는 과정, 마지막 상자는 평가가 지원하는 결정이다. 이 그림은 수치 그래프가 아니라 발표 내용을 정리한 개념도다.

평가를 이루는 네 가지

화자는 평가를 네 요소로 나눈다.

  1. 데이터셋: AI에 넣을 입력 사례다. 잘 풀어야 하는 대표 사례뿐 아니라 경계 사례와 이전 실패 사례도 포함할 수 있다.
  2. 태스크: 입력을 받았을 때 AI가 무엇을 어떻게 해야 하는지 정의한다. 발표에서는 시스템 프롬프트와 선택한 모델 등이 여기에 포함된다고 설명한다.
  3. 채점 기준: 결과가 좋은지 나쁜지를 판단하는 규칙이다. 고정된 규칙으로 판정하거나, 다른 언어 모델을 심판으로 사용하거나, 사람이 검토할 수 있다.
  4. 실험: 특정 데이터셋·태스크·채점 기준을 묶어 실행한 한 구성이다. 구성을 바꾼 실험끼리 비교하면 무엇이 개선됐고 무엇이 악화됐는지 볼 수 있다.

발표에 나온 “200개 사례 중 94%가 통과했다”, “정확도는 5% 올랐지만 말투 점수는 5% 내려갔다”는 평가로 가능한 설명의 예시다. 뒤의 검색 비교 실험에서 실제로 측정된 정확도 수치라는 뜻은 아니다.

한 번의 시험이 아니라 운영과 연결되는 순환

평가는 출시 전에만 하는 시험으로 끝나지 않는다. 실제 사용에서 생긴 기록, 즉 생산 로그를 일부 골라 데이터셋으로 만들고, 평가를 실행하고, 배운 내용을 코드나 프롬프트에 반영한 뒤 다시 배포할 수 있다. 그러면 변경된 시스템에서 새로운 로그가 쌓이고 같은 과정이 반복된다.

읽는 법: 가운데를 위에서 아래로 읽은 뒤, 마지막 배포 상자에서 오른쪽의 긴 화살표를 따라 첫 번째 생산 로그로 돌아간다. 발표자가 설명한 관측과 평가의 반복 구조를 나타낸 개념도다.

실제 사례: 두 코드 검색 방식을 같은 조건에서 비교하기

화자는 Microsoft의 오픈소스 TypeScript-Go 저장소에서 제목에 fix가 들어간 병합된 PR을 찾았다. 수정 직전의 부모 커밋으로 돌아가 버그가 남아 있는 상태를 만들고, 버그 코드와 수정 코드의 차이를 이용해 Claude가 버그 작업 설명을 생성하게 했다. 이렇게 만든 약 20개의 PR 사례에서 AI가 버그 위치를 찾고 수정하도록 했다.

비교 대상은 다음 두 방식이었다.

  • Vector Search: 코드 조각을 의미를 나타내는 숫자 표현인 임베딩으로 바꾸고, 질문과 의미상 가까운 코드 조각을 가져오는 방식이다.
  • Agentic Search: 언어 모델에 grep, find, ls, cat, Bash 같은 도구를 주고, 파일을 열고 함수 호출을 따라가며 필요한 코드를 찾게 하는 방식이다.

두 방식 모두 Claude Code 실행 틀을 사용했다. Vector Search 조건에서는 프롬프트로 Agentic Search를 쓰지 말라고 지시하는 것만으로 부족하다고 보고, 일부 도구 호출을 금지하는 설정도 사용했다.

채점은 단순했다. 수정 결과가 Microsoft TypeScript-Go 테스트 모음을 통과하면 100%, 실패하면 0%였다.

읽는 법: 각 행을 왼쪽 기준부터 양쪽으로 비교한다. 마지막 행은 모든 환경에 통하는 일반 법칙이 아니라, 화자가 구성한 약 20개 사례의 실험 결과다.

정확도가 같은데 왜 비용은 달랐을까?

화자의 해석은 가까운 코드와 코드 사이의 연결 관계는 다르다는 것이다.

Vector Search는 정답과 가까운 코드 조각을 찾을 수 있었지만, 그 조각만으로 버그를 이해하기에 필요한 import, 위쪽의 호출 코드, 다른 파일의 함수 관계가 빠질 수 있었다. 그러면 모델은 다시 검색하고, 또 다른 조각을 받아 읽고, 부족하면 다시 검색한다. 검색과 언어 모델 호출이 반복되면서 비용이 쌓였다는 설명이다.

반면 Agentic Search는 함수 이름을 검색한 뒤 파일을 열어 전체 함수를 읽고, 해당 함수를 부르는 다른 코드로 이동할 수 있었다. 화자는 Vector Search가 정답 코드에 대한 근접성을 주었다면 Agentic Search는 조각 사이를 잇는 연결 조직을 더 잘 제공했다고 표현한다.

실행 과정을 보는 기록인 trace도 중요했다. Claude Code를 하위 프로세스로 실행했을 때 내부 기록이 부모 실행과 연결되지 않는 문제가 있었고, 화자는 부모 span ID를 환경 변수로 전달해 이를 연결했다고 설명한다. 연결 후에는 모델 호출과 grep, bash, ls, find 등의 명령을 볼 수 있었다. 최종 점수만 봐서는 “비용이 왜 늘었는가”를 알기 어렵지만, trace를 보면 반복 검색이 쌓이는 과정을 조사할 수 있다.

이 결과를 어디까지 믿을 수 있는가

화자는 이 실험을 최종 판결로 제시하지 않는다. 언어 모델의 결과는 실행할 때마다 달라질 수 있는데, 각 태스크를 여러 번 반복하지 않았다. Vector Search 구현도 비교적 약했다고 스스로 평가했다. 데이터셋도 약 20개 사례였으며, 다른 저장소로 넓히지 않았다.

따라서 “Agentic Search는 언제나 Vector Search보다 싸고 좋다”가 결론은 아니다. 더 안전한 결론은 다음과 같다.

  • 같은 최종 정확도라도 정보를 찾는 과정과 호출 횟수에 따라 비용이 달라질 수 있다.
  • 최종 점수와 함께 trace를 봐야 차이가 생긴 원인을 설명할 수 있다.
  • 평가 결과는 데이터셋, 구현 품질, 반복 횟수, 채점 방식이라는 조건 안에서 해석해야 한다.
확인해야 할 경계
  • META의 provenance.creator는 Vector Search라고 적혀 있지만, 전사에서 화자는 자신을 Jess라고 소개한다. META 설명은 Jess Wang이라고 쓰며, provenance note는 화자 이름과 SNS를 바탕으로 원출처를 추정했다고 밝힌다. 이 이름 정보들은 서로 일치하지 않으며 독립적으로 확인되지 않았다.
  • 화자는 Cursor가 사용했다는 “semantic search”를 “Agentic Search”라고도 부르지만, 같은 발표에서 Vector Search 역시 임베딩을 이용한 의미 검색으로 설명한다. 용어 경계가 불명확하므로 두 말을 일반적인 동의어로 확정하면 안 된다.
  • “같은 정확도”의 정확한 백분율은 전사에 없다. 비용 4배는 화자가 해당 실험 결과로 보고한 수치다.
  • 200개 중 94%, 정확도 5% 상승, 말투 5% 하락은 실제 검색 실험 결과가 아니라 평가로 할 수 있는 설명의 예시다.

여기까지만 이해하면 충분

  • 평가는 데이터셋·태스크·채점 기준을 정하고 실험끼리 비교해 AI 변경의 근거를 만드는 방법이다.
  • 생산 로그를 평가 데이터로 바꾸고, 결과를 반영해 다시 배포하는 순환을 만들 수 있다.
  • 이 사례에서는 두 검색 방식의 정확도가 같았지만, 반복 검색이 많았던 Vector Search의 비용이 4배였다고 보고됐다.
  • 이 결과는 약 20개 사례, 약한 Vector Search 구현, 반복 실행 부족이라는 조건 안에서 해석해야 한다.

비유와 깨지는 지점

같은 시험장에서 두 내비게이션 비교하기

데이터셋은 두 내비게이션이 함께 달릴 고정 경로, 태스크는 목적지와 운전 조건, 채점 기준은 도착 성공 여부다. 실험에서는 목적지 도착뿐 아니라 한쪽이 같은 길을 몇 번 되돌아갔는지도 살핀다. 둘 다 도착했더라도 반복 탐색이 많으면 시간이나 비용이 더 들 수 있다.

비유가 깨지는 지점: AI 시스템은 같은 입력에도 결과가 달라질 수 있고, 코드 검색의 맥락은 실제 도로처럼 고정되어 있지 않다. 따라서 한 번의 주행만으로 안정성을 판단해서는 안 된다.

1. 원인

Vector Search가 반환한 코드 조각에는 import, 호출 코드, 다른 함수와의 관계가 빠질 수 있었다. 모델은 부족한 맥락을 채우기 위해 검색과 언어 모델 호출을 반복했고, 그 호출 비용이 누적됐다는 설명이다. 한 사례에서는 26번 검색하고도 세 함수의 관계를 조립하지 못했다고 한다.

2. 대조

Vector Search와 Agentic Search의 차이를 “의미 검색 대 단어 검색”으로만 설명하면 왜 부족한가?

모범 답안 보기

발표의 핵심 대조는 검색어 종류보다 탐색 과정에 있다. Vector Search는 의미상 가까운 코드 조각을 반환했고, Agentic Search는 도구로 파일을 열어 전체 함수를 읽고 호출 관계를 따라갔다. 다만 발표자가 semantic search와 Agentic Search를 연결해 부른 부분은 용어가 불명확하므로 확정된 정의로 일반화하면 안 된다.

두 설정에 같은 데이터셋과 성공 기준을 적용하고, 가능하면 태스크별로 여러 번 실행한다. 최종 통과 여부뿐 아니라 trace에서 호출 횟수, 반복 행동, 실패 지점과 비용이 어디서 생기는지 확인한다. 데이터셋이 실제 사용을 대표하는지와 구현 품질이 공정한지도 함께 검토한다.

이번 글의 통찰

1. 평가는 점수표보다 의사결정 구조에 가깝다

  • [원문] 화자는 평가를 AI 시스템에 관한 질문에 답하는 방법으로 정의하고, 데이터셋·태스크·채점 체계·실험의 네 요소를 제시했다.
  • [해석] 좋은 평가는 숫자를 많이 만드는 일이 아니라, 출시·수정·보류 결정을 내리기 전에 질문과 성공 기준을 고정하는 일이다.
  • [경계] 발표의 200개 중 94%, 정확도와 말투의 5% 변화는 설명용 예시다. 실제 검색 실험의 정확도 수치로 사용하면 안 된다.

2. 같은 정확도는 같은 효율을 뜻하지 않는다

  • [원문] 화자는 두 검색 방식의 정확도가 같았지만 Vector Search 비용이 4배였고, 반복 검색과 언어 모델 호출이 원인이라고 설명했다.
  • [해석] 최종 성공률만 비교하면 내부의 낭비를 놓칠 수 있다. 품질이 같은 후보라면 성공까지 필요한 탐색과 비용을 함께 봐야 한다.
  • [경계] 약 20개 사례에서 나온 결과이며 정확한 정확도 수치는 없다. 화자도 Vector Search 구현이 약했고 여러 번 반복하지 않았다고 인정했다.

3. Trace는 점수의 원인을 찾는 증거다

  • [원문] 하위 프로세스 trace가 부모 실행과 분리되자 부모 span ID를 환경 변수로 넘겨 연결했고, 이후 모델 호출과 터미널 명령을 볼 수 있었다.
  • [해석] 결과 점수는 무엇이 일어났는지를 보여주지만, trace는 왜 그런 비용과 실패가 생겼는지 조사하게 한다.
  • [경계] 이 연결 방식은 화자가 설명한 해당 구현의 해결책이다. 모든 관측 시스템과 하위 프로세스에 그대로 적용된다고 단정할 수 없다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 발표는 “몇 번 해 봤더니 괜찮았다”와 고정 사례·채점 기준으로 확인한 결과를 대조한다.
  • 통찰: 학습자의 이해도 말로 “알겠다”고 하는지보다, 같은 과제를 보지 않고 설명하고 적용하는지로 확인할 수 있다.
  • 질문/행동: 같은 개념을 원인 설명·대조·새 사례 적용의 세 방식으로 답하게 하면 어느 지점에서 이해가 끊기는가?

사업가 · 구조적 비유

  • 관련성: 같은 정확도에서도 반복 호출 때문에 비용이 4배가 될 수 있다는 사례는 품질과 자원 사용을 함께 봐야 함을 보여준다.
  • 통찰: APOM에 실제 적용됐다는 근거는 없다. 다만 자동화 후보를 검토할 때 완료 여부만 보지 않고 성공 1건에 필요한 비용과 재작업을 비교한다는 가설은 시험할 수 있다.
  • 질문/행동: 동일한 업무 사례에서 결과 품질을 유지하면서 성공 1건당 자원 사용을 줄이는 설정은 무엇인가?

마케터 · 구조적 비유

  • 관련성: “같은 정확도, 4배 비용”은 강한 대조지만 약 20개 사례와 약한 구현이라는 조건이 붙는다.
  • 통찰: 숫자를 카피로 사용할 때 결과뿐 아니라 데이터셋, 비교 조건, 한계를 함께 제시해야 과장을 줄일 수 있다.
  • 질문/행동: 성과 숫자 옆에 표본, 기준선, 판정 방식, 적용 범위를 한 문장으로 붙일 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 데이터셋 구성, 도구 제한, 테스트 기반 채점, trace 연결, 비용 분석까지 실제 평가 절차가 제시됐다.
  • 통찰: 모델이나 검색 기술의 이름만 비교하지 말고, 같은 workload에서 성공까지의 호출 경로와 자원 사용을 측정해야 한다.
  • 질문/행동: 후보 설정의 최종 점수는 같아도 반복 검색, 고아 trace, 도구 우회 같은 실패가 숨어 있지 않은가?

# 섹션 요지
1 평가가 필요한 이유 감에 의한 출시 대신 질문과 데이터로 변경을 판단한다.
2 평가의 네 요소 데이터셋·태스크·채점 체계·실험으로 구성된다.
3 관측과 평가의 순환 생산 로그를 데이터셋으로 만들고 변경 후 다시 배포한다.
4 검색 비교 실험 TypeScript-Go의 약 20개 수정 사례로 두 방식을 비교했다.
5 결과와 trace 정확도는 같았고 Vector Search 비용은 4배였다고 보고됐다.
6 실험의 한계 반복 실행 부족, 약한 구현, 작은 데이터셋을 화자가 인정했다.

1. 평가가 필요한 이유

화자는 자신을 Jess라고 소개하고 Braintrust의 DevRel 엔지니어라고 말했다. 고객과의 대화에서 엔지니어나 제품 관리자가 준비됐다고 판단했거나 프롬프트 몇 개가 좋아 보여 기능을 출시한 사례를 들었다. 화자는 이를 분위기나 느낌에 의존한 출시 결정이라고 비판했다.

“200개 테스트 중 94% 통과”, “정확도 5% 증가와 말투 5% 감소”는 더 구체적인 의사결정 문장의 예시로 제시됐다. 검색 비교 실험에서 실제로 얻은 수치는 아니다.

평가로 물을 수 있는 질문에는 모델 선택, 실제 환경별 성능, 언어나 프로그래밍 언어에 따른 차이, 비용 효율, 브랜드 말투, 사용자 피드백 반영, 변경 후 악화 여부가 포함됐다.

화자는 2025년 4월 OpenAI의 모델 변경이 도움을 늘리려 했으나 지나치게 동의하는 성향을 만들었다는 사례를 언급했다. 이는 화자의 주장으로, 제공 자료 안에서 독립 검증되지는 않았다.

2. 평가의 네 요소

첫째는 데이터셋이다. 대표적인 정답 사례, 경계 사례, 실패 유형이 포함될 수 있다.

둘째는 태스크다. AI가 입력을 받아 어떻게 출력해야 하는지를 정하며, 시스템 프롬프트와 선택 모델 등이 포함된다.

셋째는 채점 체계다. 결정론적 채점, LLM-as-a-judge, 사람 검토 등이 언급됐다.

넷째는 실험이다. 특정 데이터셋·태스크·채점 체계를 결합한 구성이 한 실험이 된다. 서로 다른 실험의 전체 결과와 개별 행을 비교해 개선이나 회귀를 찾을 수 있다.

화자는 Braintrust UI에서 자연어로 trace와 실험을 조회할 수 있고, CLI와 MCP 서버도 제공한다고 설명했다. 이는 Braintrust 기능에 대한 화자의 설명이다.

3. 관측과 평가의 순환

문서 페이지에 AI 챗봇을 배포한 가상 사례가 사용됐다. 실제 사용이 시작되면 생산 로그가 쌓인다. 그중 10~20행 정도를 표본으로 골라 데이터셋을 만들고, 태스크와 채점 체계를 작성해 여러 평가를 실행한다.

비교를 통해 배운 내용을 코드나 AI 시스템에 반영해 다시 배포하면, 변경된 시스템에서 새로운 생산 로그가 쌓인다. 이 순환에는 실제 데이터를 가져오는 엔지니어, 성공 가설을 만드는 제품 관리자, 정답을 제공하는 분야 전문가, 결과를 분석하는 데이터 분석가가 참여할 수 있다고 설명했다.

4. Agentic Search와 Vector Search 비교 실험

화자는 CEO Ankur가 Cursor의 글을 보내 평가를 요청했다고 말했다. 이 과정에서 Cursor가 사용한 semantic search를 Agentic Search라고도 표현했지만, 발표 안에서 Vector Search 역시 의미 기반 검색으로 설명돼 용어가 불명확하다.

Vector Search는 코드나 텍스트를 임베딩으로 바꾸고 Qdrant나 Pinecone 같은 벡터 데이터베이스에 저장한 뒤, 질문과 의미상 가까운 조각을 찾는 방식으로 설명됐다.

Agentic Search는 언어 모델이 grep, find, ls, cat, Bash 같은 도구를 사용해 함수명과 파일을 찾고 호출 관계를 따라가는 방식으로 설명됐다.

데이터셋은 Microsoft TypeScript-Go 저장소에서 제목에 fix가 들어간 병합 PR을 찾고, 부모 커밋으로 이동해 버그가 남은 상태를 만드는 방식으로 구성됐다. 수정 전후 차이로 Claude가 버그 작업 설명을 만들었고, 약 20개 PR에 대해 평가를 실행했다.

두 방식 모두 Claude Code 실행 틀을 사용했다. Vector Search 조건에서는 프롬프트로 Agentic Search를 금지하고, disallowed tools 플래그로 관련 도구 호출도 막았다고 설명했다.

5. Trace와 평가 결과

Claude Code를 하위 프로세스로 실행하자 내부 trace가 부모 실행과 연결되지 않는 문제가 생겼다. 화자는 부모 span ID를 환경 변수로 전달해 하위 실행을 연결했다고 말했다. 이후 각 모델 호출과 grep, bash, ls, find 명령을 확인할 수 있었다.

채점은 TypeScript-Go 테스트 모음을 통과하면 100%, 실패하면 0%인 이진 방식이었다.

화자가 보고한 결과는 다음과 같다.

  • 두 검색 방식의 정확도는 같았다.
  • Vector Search 비용은 Agentic Search의 4배였다.
  • 한 사례에서 Vector Search는 26번 검색하고도 파일 안의 세 함수가 어떻게 상호작용하는지 조립하지 못했다.
  • Agentic Search는 함수명을 검색하고 전체 함수를 읽은 뒤 다른 파일의 호출 관계를 따라갔다.
  • 화자는 Vector Search가 정답 코드에 대한 근접성을 제공했고 Agentic Search가 코드 조각 사이의 연결 관계를 더 잘 제공했다고 해석했다.

정확도의 정확한 백분율과 비용 계산 방식은 전사에 제시되지 않았다.

6. 한계와 충돌 목록

화자가 직접 인정한 한계는 다음과 같다.

  • 비결정적인 언어 모델을 고려한 태스크별 다회 반복을 하지 않았다.
  • Vector Search 구현이 비교적 약했다.
  • 데이터셋은 약 20개 사례였고 다른 저장소로 넓히지 않았다.
  • 발표의 목적은 최고의 평가를 만드는 것이 아니라 평가의 전체 과정을 보여주는 것이었다.

자료 사이에서 확인되는 충돌과 불확실성은 다음과 같다.

  1. META provenance의 원작자 후보는 Vector Search지만, 전사 화자는 자신을 Jess라고 소개한다.
  2. META 설명은 화자를 Jess Wang이라고 쓰지만 전사에는 성이 나오지 않는다. 연결된 SNS에는 Jessica Wang을 가리키는 주소가 있으나, provenance note는 이를 추정 출처라고 밝힌다.
  3. provenance note는 화자 이름과 SNS를 기준으로 원출처를 추정했다고 쓰면서 creator 값에는 사람 이름이 아닌 Vector Search를 기록했다.
  4. 발표자는 Cursor의 semantic search를 Agentic Search라고도 부르지만, Vector Search 또한 임베딩을 통한 의미 검색으로 설명한다.
  5. “같은 정확도”의 정확한 값은 없고, 비용 4배만 비율로 제시된다.
  6. 200개 중 94%, 정확도 5% 상승, 말투 5% 하락은 검색 비교의 결과가 아니라 설명용 예시다.
  7. “약 20개 PR”과 “약 20개 행”은 같은 데이터셋을 가리키는 것으로 보이지만, 정확히 동일한 단위를 뜻하는지는 전사만으로 확정할 수 없다.

여러분, 저는 Jess입니다. Braintrust에서 왔습니다. Braintrust의 DevRel 엔지니어이고, 오늘 이 발표에서는 eval이 무엇인지, 왜 중요한지 가르쳐 드린 다음, 제가 방금 설명할 개념들을 확실히 이해하기 위해 진행했던 비교적 복잡한 실제 eval 사례를 함께 살펴보겠습니다.

시작하기 전에, eval에 대해 들어본 적이 있거나 eval이 무엇인지 자신 있게 설명할 수 있는 분은 손을 들어 주시겠어요? 네, 좋습니다. 거의 모두 알고 계시네요. 그럴 만합니다.

먼저 eval이 무엇이고 왜 중요한지 기본적인 내용부터 시작하겠습니다. 고객들과 통화하다 보면, 엔지니어링 팀에서 준비됐다고 했기 때문에 기능을 출시했거나, PM이 프롬프트 몇 개를 직접 사용해 보고 괜찮아 보였기 때문에 기능을 출시했다고 말하는 경우가 있습니다. 이런 말을 듣고 싶지는 않을 겁니다. 본질적으로 이런 팀들은 감에 의존해 출시 여부를 결정하고 있기 때문입니다.

좋지 않은 방식입니다. 여러분이 듣고 싶은 말은 이런 것에 더 가깝습니다. “서로 다른 테스트 케이스 200개를 실행했고, 그중 94%가 통과했기 때문에 이 기능을 출시합니다.” 또는 “이 기능을 출시하면서 정확도는 5% 높아졌지만, 실제로는 말투 점수가 5% 낮아졌습니다”처럼 미묘한 내용까지 말할 수 있어야 합니다.

사람들이 eval이 무엇인지 물어보면, 저는 eval이 AI 시스템에 관한 질문에 답하기 위한 방법이라고 설명하는 것이 가장 좋다고 생각합니다. 예를 들어, 우리에게 필요한 것은 어떤 LLM일까요? 특히 새로운 모델이 계속 출시되는 상황에서는 의사결정을 뒷받침할 데이터가 있는 것이 좋습니다.

다양한 실제 상황에서 AI는 어떻게 성능을 발휘할까요? 예를 들어 시스템이 영어 출력에서는 매우 잘 작동하지만 일본어에서는 그렇지 않을 수 있고, 영어 입력에서는 잘 작동하지만 일본어 입력에서는 그렇지 않을 수 있습니다. 또는 어떤 타입은 Python에서는 매우 잘 작동하지만 TypeScript에서는 그렇지 않을 수도 있습니다.

비용 효율성도 중요한 항목입니다. 과도한 비용 없이 높은 성능을 달성하려면 어떻게 해야 할까요? 이는 확실히 요즘 더욱 중요한 주제가 되고 있습니다.

브랜드 일관성: AI가 우리 회사의 목소리와 기준을 안정적으로 반영하고 있을까요?

피드백: 사용자에게서 배우고 반복적으로 개선하고 있을까요?

가장 큰 질문 중 하나는, 무언가가 망가지거나 성능이 나빠졌을 때 우리가 어떻게 알 수 있느냐는 것입니다.

제가 자주 사용하는 실제 사례는 약 1년 전인 2025년 4월의 사례입니다. OpenAI가 모델 변경 및 업데이트를 출시했는데, 모델을 더 유용하게 만드는 것이 목적이었습니다. 하지만 실제로는 아첨하고, 지나치게 동의하며, 따라서 진실성이 떨어지는 모델이 되었습니다. AI 시스템은 매우 복잡하고 비결정적이기 때문에, eval이 이를 포착하는 데 어떻게 도움이 되는지 보여 주는 정말 좋은 예입니다. 회사에서, 또는 여러분이 만들고자 하는 무언가에서 이런 eval 시스템을 갖추는 것은 매우 중요합니다.

이제 eval이 구체적으로 무엇으로 구성되는지 살펴보겠습니다. eval은 네 가지 주요 요소로 구성됩니다.

첫 번째는 데이터셋(dataset)입니다. 이는 AI 시스템에 전달하는 데이터이며, 일반적으로 골든 스탠더드(golden-standard) 케이스, 엣지 케이스(edge case), 실패 모드(failure mode) 등이 포함됩니다.

데이터셋이 있으면 태스크(task)를 작성해야 합니다. 태스크는 AI 시스템이 입력을 받고 출력을 생성할 때 어떻게 동작하기를 원하는지 정의합니다. 구체적으로는 보통 시스템 프롬프트와 이 태스크를 실행하도록 선택한 모델이 포함됩니다.

다음으로 AI의 출력이 좋은지 나쁜지 알려 주는 평가 시스템을 작성해야 합니다. 일반적으로 무엇이 좋은 결과이고 나쁜 결과인지 구성하는 기준은 PM이나 엔지니어가 작성합니다. 결정론적 스코어링(deterministic scoring), LLM-as-a-judge, 사람 검토(human review) 같은 용어를 들어 보셨을 수도 있습니다. 이는 서로 다른 유형의 스코어링 프레임워크입니다. 이것이 스코어링 시스템을 작성하는 방식입니다.

마지막으로 해야 할 일은 eval을 작성하는 과정에서 가장 재미있는 부분인 실험입니다. 특정 데이터셋, 특정 태스크, 특정 스코어링 시스템의 각 조합이 하나의 실험이 됩니다. 시스템을 개선하기 위한 여러 가설을 테스트하면서 데이터셋, 태스크, 스코어링 시스템 중 하나를 조정하게 되고, 이 모든 것이 서로 다른 실험으로 이어집니다.

서로 다른 실험이 생기면 이를 비교하기 시작합니다. 실험 1과 실험 2를 실행하고 개선이나 회귀가 있었는지 확인할 수 있습니다. 특정 행을 클릭해 어떤 테스트 케이스가 정확히 변경되었는지도 볼 수 있습니다. 이 스크린샷은 Braintrust UI에서 가져온 것입니다.

자연어를 사용해 트레이스와 실험 전반을 질의할 수도 있습니다. 예를 들어 “내 실험을 요약해 줘” 또는 “이 실험들의 문제를 강조해 줘”와 같이 요청할 수 있습니다.

특히 긴 다중 턴 대화가 포함된 트레이스를 보면서 실험을 실행할 때 유용하다고 생각합니다. 수동으로는 포착하기 어려운 환각이나 드리프트 같은 문제를 발견하는 데 도움이 됩니다.

서로 다른 실험을 실행하고 있다면, 그중 어떤 실험의 성능이 가장 좋았는지 물어볼 수도 있습니다. 이는 트레이스에서 패턴을 찾는 또 다른 방법입니다.

이 기능은 Braintrust의 UI를 사용하지만, 원하는 방식에 따라 CLI와 MCP 서버도 제공합니다.

Braintrust의 마지막 기둥은 정기적인 옵저버빌리티(observability)입니다. Braintrust SDK를 사용해 코드를 감싸고, 운영 로그가 Braintrust에 표시되도록 하며, 운영 로그를 모니터링하고 대시보드 등을 만드는 전통적인 옵저버빌리티를 수행할 수 있습니다.

이 내용을 연결해 보기 위해, 옵저버빌리티와 eval을 사용해 AI 시스템을 개선하는 흐름을 보여 드리겠습니다.

왼쪽 위에 “app”이라고 표시된 곳에서 시작하겠습니다. 어떤 AI 애플리케이션이 있다고 상상해 보세요. 이 시나리오에서는 AI 챗봇이 내장된 새로운 문서 페이지를 방금 출시했고, 사용자는 이 챗봇에게 문서에 관해 질문할 수 있습니다. 어제 이 기능을 출시했다고 해 보겠습니다.

그러면 고객들이 AI 챗봇을 사용하기 시작합니다. 사용하기 시작하면 실제 운영 로그가 시스템으로 들어오기 시작합니다.

운영 로그가 들어오면 그중 일부를, 예를 들어 10~20개의 행을 샘플링해 데이터셋을 만들 수 있습니다. 데이터셋이 있으면 그 위에서 eval을 실행할 수 있습니다. 데이터셋이 있고, 태스크를 작성하고, 스코어링 시스템을 작성한 다음 이를 실행할 수 있습니다. 데이터셋, 프롬프트 또는 점수를 조정하면서 여러 eval을 실행할 수도 있습니다.

몇 가지 eval을 실행하고 어떤 eval의 성능이 가장 좋은지 보기 시작하면, 시스템에 대해 무언가를 알게 될 수 있습니다. 그런 다음 코드 변경이나 사용 중인 AI 시스템의 변경을 적용하고 이를 애플리케이션에 다시 배포합니다. 그러면 변경 사항이 운영 로그에 나타나기 때문에 전체 흐름이 반복됩니다.

이것이 전체적인 흐름입니다.

구체적인 예로 들어가기 전에 보여 드릴 마지막 슬라이드는 제가 아주 좋아하는 슬라이드입니다. 개념적으로 eval은 팀 스포츠라는 점을 강조하고 싶기 때문입니다. 실제 데이터를 플랫폼으로 가져오는 일부터 데이터에 라벨을 지정하고 가설을 세우는 일까지, eval을 만들기 위해서는 정말 많은 작업이 필요합니다.

AI 엔지니어는 코드 변경 작업뿐 아니라 데이터를 플랫폼으로 가져오는 작업도 담당합니다.

제품 관리자도 매우 중요합니다. 제 생각에 회사에서 eval을 주도하는 사람은 보통 제품 관리자입니다. 성공이 어떤 모습인지에 대한 가설을 세우고, 프롬프트 등을 조정하는 일을 돕는 사람이 바로 제품 관리자입니다.

특히 보험, 의학, 법률처럼 더 전문적인 분야에서는 도메인 전문가(subject-matter expert)가 매우 중요합니다. 이들은 데이터에 라벨을 지정하거나 탁월함이 어떤 것인지에 대한 정답(ground truth)을 제공할 수 있습니다.

그리고 데이터를 분석하는 데이터 분석가도 있습니다. 저는 이 슬라이드를 살펴보는 것이 항상 매우 유용하다고 생각합니다.

이제 eval을 어떻게 활용할 수 있는지 보여 주는 흥미로운 실제 사례를 살펴보겠습니다. 여기서는 Agentic Search와 Vector Search를 비교합니다.

이 특정 eval의 배경은 이렇습니다. 제 CEO인 Ankur는 가끔 트위터에 들어가서 제가 평가해 보길 원하는 내용의 글을 보내 줍니다. 어느 날 Cursor가 올린 트윗을 보내 왔는데, Cursor는 시맨틱 검색(semantic search), 즉 Agentic Search를 사용해 코딩 에이전트의 성능을 크게 향상한 방법에 대해 이야기하고 있었습니다. Ankur가 “Jess, 이거 eval해 줄 수 있어?”라고 했고, 저는 “알겠어요”라고 답했습니다.

바쁘긴 했지만 해 보기로 했습니다. 트위터에 들어가 보니 이 주제에 관해 많은 의견과 논의가 오가고 있었고, 평가해 보면 흥미롭겠다는 생각이 들었습니다.

Vector Search와 Agentic Search를 평가해 보겠습니다. 모두가 같은 내용을 이해할 수 있도록 각각이 무엇인지 간단히 요약하겠습니다.

Vector Search는 본질적으로 코드나 텍스트 같은 데이터를 가져와 임베딩(embedding)으로 변환하는 과정입니다. 임베딩은 해당 텍스트나 코드 조각의 의미를 나타냅니다.

여기 그래프를 보면 좋은 시각적 예시가 됩니다. 늑대, 개, 고양이의 임베딩은 의미적으로 모두 동물이기 때문에 서로 매우 가깝습니다. 바나나와 사과의 임베딩도 과일이기 때문에 서로 가깝지만, 과일과 동물은 서로 다른 것이므로 동물 임베딩과는 멀리 떨어져 있습니다.

실제 Vector Search를 구현할 때는 이러한 임베딩을 가져와 Qdrant나 Pinecone 같은 벡터 데이터베이스에 저장합니다.

“내 코드베이스에서 데이터베이스 로직은 어디에 있지?”와 같은 쿼리를 작성하면, 벡터 데이터베이스는 쿼리의 단어와 의미적으로 가장 유사한 임베딩 조각, 즉 “데이터베이스”나 “로직” 같은 항목에 가장 가까운 조각을 반환합니다.

이것이 Vector Search의 작동 방식입니다.

Agentic Search는 약간 다릅니다. Agentic Search는 인간이 하는 방식과 더 비슷하게 작동합니다. 본질적으로 Agentic Search에서는 LLM에 grep, find, ls, cat, Bash 명령어 같은 도구를 제공합니다. 그러면 LLM이 인간처럼 코드베이스를 탐색합니다.

함수 이름을 찾아보고, 파일을 열고, 파일을 읽고, 해당 함수 호출을 따라 다른 파일로 이동한 다음, 그 파일을 열어 읽습니다. 필요한 것을 찾을 때까지 이 과정을 계속합니다. 이는 사람이 코드베이스를 살펴보며 특정 로직을 찾는 방식과 훨씬 더 유사합니다.

이것을 어떻게 평가했을까요? 평가(evaluation)를 만드는 첫 번째 단계는 데이터셋을 만드는 것입니다. 이를 위해 오픈 소스인 Microsoft의 TypeScript Go 저장소를 사용했습니다.

제목에 “fix”가 포함된 모든 병합된 PR을 찾고, 부모 커밋을 체크아웃했습니다. 즉, 버그가 아직 존재하던 시점의 커밋을 체크아웃한 것입니다.

그런 다음 Claude를 사용해 diff, 즉 버그가 있는 코드와 수정된 코드의 차이를 바탕으로 버그 작업(bug task), 또는 Linear 작업(Linear task)을 생성했습니다. 이를 LLM에 입력하고, 해당 LLM이 Vector Search 또는 Agentic Search를 사용해 버그가 있는 코드를 찾고 버그 로직이 위치한 곳을 찾도록 했습니다.

이렇게 데이터셋을 만들었습니다. 약 20개의 서로 다른 PR을 찾았고, 이를 대상으로 평가를 실행했습니다.

작업과 관련해서는 실제로 vector search와 agentic search를 구현해야 했습니다. 물론 Claude Code는 기본적으로 agentic search를 사용하기 때문에 agentic search 구현은 매우 쉬웠습니다. 그래서 이 작업들에 Claude Code를 그대로 설정했습니다.

vector search를 구현하는 일은 조금 더 복잡했습니다. 실험의 일관성을 유지하기 위해 여전히 Claude Code 하네스(harness)를 사용해 vector search를 실행하고 싶었기 때문입니다. 하지만 Claude Code가 기본적으로 agentic search를 사용하지 못하게 해야 했습니다.

그래서 두 가지를 했습니다. 첫 번째는 프롬프트 지시사항에 agentic search를 사용하지 말라고 명시적으로 적은 것입니다. 하지만 이런 일을 해본 적이 있다면 알겠지만, 프롬프트만으로는 절대 충분하지 않습니다. 그래서 Claude Code가 agentic search에서 일반적으로 사용할 특정 기능을 호출하지 못하도록 disallowed tools 플래그(flag)도 사용해야 했습니다. 이것이 Claude Code 하네스를 사용해 vector search와 agentic search를 모두 구현한 방법입니다.

또 한 가지 흥미로운 문제는 trace를 실행할 때 Claude Code 실행을 subprocess로 실행했는데, 이 때문에 trace가 사실상 고아(orphaned) 상태가 되었다는 것입니다. 저희의 해결책은 부모 span ID를 환경 변수로 전달하는 것이었습니다.

이해가 되지 않아도 괜찮습니다. 그림으로 보여드리겠습니다. 이 그림은 고아 subprocess로 실행될 때 trace가 어떻게 보이는지를 보여줍니다. 왼쪽 패널의 강조된 부분에 “Run Claude Agent”라고 표시된 것을 볼 수 있습니다. trace는 “좋아요, Claude subprocess가 실행 중입니다”라고 말하고 있지만, 실제로 해당 Claude 프로세스가 실행되는 동안 무슨 일이 일어나는지는 전혀 볼 수 없습니다.

저희가 구현한 수정 사항을 적용하면 trace에서 이제 이렇게 보입니다. Claude Code subprocess를 호출하고 있다는 것을 볼 수 있을 뿐 아니라, 그 subprocess 안에서 실행되는 모든 내용도 볼 수 있습니다.

모든 턴(turn), 모든 LLM 호출, 그리고 grep, bash, ls, find 같은 호출된 각각의 터미널 명령을 볼 수 있습니다. 실제 실행에서 무슨 일이 일어나고 있는지 확인할 수 있는 것입니다. 나중에 디버깅할 때 무슨 일이 일어나는지 투명하게 볼 수 있는 것은 중요하기 때문에, 이 수정 사항을 구현하는 일은 매우 중요했습니다.

점수 산정은 매우 간단했습니다. Microsoft TypeScript-Go 저장소를 사용하고 있으므로, Microsoft TypeScript-Go 테스트 스위트를 통과하면 100%, 실패하면 0%를 부여했습니다. 따라서 매우 이진적인 점수 산정 방식이었습니다.

결과를 요약하면, vector search와 agentic search는 정확도에서 같은 수준을 보였지만 vector search가 agentic search보다 비용이 네 배 더 많이 들었습니다.

실제 trace를 살펴보고 무슨 일이 일어났는지 이해하기 위해 수동으로 검토했을 때, 몇 가지 배운 점이 있었습니다.

첫 번째는 vector search가 코드 청크(chunk)를 반환하지만, 이 코드 청크에는 import, 도구 호출(tool call), 또는 그 위에 있는 호출 코드 같은 내용이 빠져 있는 경우가 많다는 것입니다. 그 결과, 에이전트가 실제로 버그를 어떻게 해결해야 하는지에 필요한 정보가 충분하지 않습니다. 한 가지 예로, 어느 행에서는 vector agent가 26번 검색을 수행했는데도 파일 전체에 걸쳐 세 함수가 어떻게 상호작용하는지 파악하지 못했습니다.

반면 agentic search는 사람처럼 작업할 수 있었습니다. 함수 이름을 grep하고, 전체 함수를 읽고, 로직의 결함을 찾아낸 다음, 호출 로직을 따라 다른 파일로 이동했습니다.

trace를 살펴본 것을 바탕으로 제가 생각하는 방식은 이렇습니다. vector search는 올바른 코드에 매우 가까운 위치 정보를 많이 제공했지만, agentic search는 해당 코드 청크들의 실제 로직을 연결해 주는 연결 조직(connective tissue)을 더 많이 제공했습니다.

제가 얻은 세 번째 배움과 연결해보면, vector search가 agentic search보다 훨씬 비쌌던 이유는 더 많은 검색을 수행했기 때문입니다. 계속 검색하고, 코드 청크를 반환하고, 다시 검색하고, 또 다른 코드 청크를 반환하고, 다시 검색했습니다. 그 결과 모든 LLM 호출이 누적되어 실행 비용이 훨씬 더 커졌습니다.

이것이 마지막 슬라이드입니다. 아마 여기 앉아서 “이 평가에는 구멍이 정말 많네”라고 생각하고 있을 수도 있는데, 충분히 타당한 생각입니다. 제가 할 수 있었던 일은 많습니다. 평가를 실행할 때는 여러 모범 사례가 있는데, 예를 들어 작업마다 여러 번의 trial을 실행하는 것입니다. 특히 LLM은 매우 비결정적이기 때문입니다. 여러 번의 trial을 실행하면 얻은 점수를 훨씬 더 신뢰할 수 있습니다. 제 vector search 구현도 상대적으로 약했습니다.

더 나은 방식으로 구현할 수도 있었습니다. 데이터셋을 확장하는 것도 도움이 되었을 것입니다. 이 평가를 약 20개의 서로 다른 행에 대해서만 실행했던 것 같기 때문에, 다른 저장소 등으로 확장했으면 더 좋았을 것입니다.

하지만 이 발표의 목적은 지금까지 가장 뛰어난 평가를 만드는 것이 아닙니다. 평가를 처음부터 끝까지 만드는 개념을 보여주는 것이 목적입니다.

제가 그 목적을 달성했기를 바랍니다. 이것으로 제 발표를 마치겠습니다. 평가가 무엇인지, 왜 중요한지, 실제로 어떻게 평가를 수행할 수 있는지에 대해 조금이나마 배우셨기를 바랍니다. 이상입니다. 들어주셔서 감사합니다.
