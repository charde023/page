[한글자막] Anthropic은 하루 코드 변경 3만 건을 어떻게 병합할까요? | Addy Osmani

원작자 Addy Osmani · Anthropic · 업로드 2026-10-30 · 11.1분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상의 중심 문제는 AI가 코드를 쓰는 속도와 팀이 그 코드를 믿고 배포하는 속도가 같지 않다는 것이다. 화자들은 코드 작성 자체보다 검토와 검증이 새로운 병목이라고 본다. CircleCI가 “올해” 2,800만 개의 CI 작업 흐름을 분석한 결과 처리량은 약 59% 증가했지만, 프로덕션에 코드를 병합하려는 시도의 10건 중 3건은 여전히 실패했다는 수치가 제시된다. 또한 AI 코드를 생성하는 개발자의 76%가 사람이 확인하기 어려운 속도로 코드가 만들어진다고 답했다는 주장도 나온다.

따라서 목표는 “AI가 더 많이 코딩하게 만들기”가 아니라 각 변경이 올바르고 완전하다는 증거를 싸게 만들고, 책임자가 그 증거를 확인한 뒤 병합하게 하는 것이다. 화자들은 이를 반복 작업을 큰 규모로 돌리는 소프트웨어 공장(software factory)이라고 부른다.

큰 그림: 코드는 생산물이 아니라 검증이 필요한 후보 변경이다

읽는 법: 위에서 아래로 진행한다. 파란 상자는 기준과 생성, 초록 상자는 독립 검사, 노란 상자는 사람의 판단이다. 왼쪽의 붉은 복귀선은 검토 중 결함이 발견되면 수정 단계로 돌아간다는 뜻이다. 핵심은 에이전트가 코드만 넘기는 것이 아니라 검증 증거까지 함께 내놓게 하는 것이다.

영상에서 든 UI 사례는 구체적이다. 브라우저에서 쓰는 기능이라면 에이전트가 실제 브라우저에서 기능을 열고 클릭할 수 있어야 한다. 모바일과 데스크톱이 중요하다면 화면 캡처나 동영상을 남길 수 있다. 사람은 코드 전체를 처음부터 다시 읽는 대신, 테스트 결과와 실행 장면이 요구한 경험을 보여주는지 확인한다. 다만 이 증거가 사람의 책임을 없애는 것은 아니다.

자동화의 정도가 달라도 사람의 판단은 사라지지 않는다

화자들은 소프트웨어 공장을 두 모습으로 설명한다. 첫째는 에이전트가 계획·구현·검사·배포를 반복하지만 사람이 계속 판단과 취향을 넣는 불이 켜진 공장(lights-on factory)이다. 둘째는 대부분의 반복 작업이 계속 자동으로 돌아가고, 사람은 의도를 정하거나 예외가 생길 때 개입하는 어두운 공장(dark software factory)이다.

읽는 법: 데스크톱에서는 A가 왼쪽, B가 오른쪽에 놓인다. 모바일에서는 A가 위쪽, B가 아래쪽에 놓인다. 어느 화면에서든 A에서 B로 갈수록 사람이 반복 과정에서 멀어지고 의도와 예외 처리에 집중한다. 그러나 B도 무책임한 완전 방치가 아니라 검증과 통제가 더 강해야 하는 상태다.

한 종류의 검사로는 서로 다른 실패를 잡을 수 없다

영상의 두 번째 핵심은 여러 겹 검증(multilayered verification)이다. 정해진 입력에 같은 규칙을 반복 적용하는 검사인 결정론적 검사는 린트, 규칙 위반, 알려진 보안 문제처럼 명확한 패턴을 찾는 데 쓰인다. 에이전트 리뷰는 코드가 의도와 논리에 맞는지 살핀다. 공급망 보안 검사는 알려진 취약점(CVE), 악성코드, 악성 패키지 문제를 겨냥한다. 브라우저 실행과 화면 증거는 실제 사용 경험이 요구와 맞는지 보여준다.

작은 화면에서는 아래 표를 좌우로 이동해 각 행의 검사 대상과 증거를 함께 읽는다.

읽는 법: 행은 잡으려는 문제의 종류이고, 열은 검사 방식과 남겨야 할 증거다. 같은 변경을 여러 번 무작정 검사한다는 뜻이 아니다. 각 검증층이 잘 잡는 실패가 다르므로 역할을 나눠 겹친다는 뜻이다.

검증만으로 충분하지도 않다. 에이전트가 수백·수천 개로 늘어나 시스템과 데이터에 접근하거나 프로덕션에 배포한다면, 조직은 누가 어떤 에이전트를 실행했는지 추적해야 한다. 화자들이 강조한 세 질문은 통제(control), 권한(permissions), 샌드박스(sandbox)다. 에이전트가 허용된 공간을 벗어나지 않는지, 어떤 데이터와 시스템에 접근했는지, 누가 변경의 책임자인지 남겨야 한다.

AI가 작성한 PR에는 표시를 붙이자는 의견도 나온다. 한 화자는 적어도 앞으로 6~9개월 동안은 표시해야 감사 가능성을 확보할 수 있다고 말한다. 그러나 표시의 목적은 “AI가 썼으니 사람이 책임지지 않는다”가 아니다. 에이전트가 작성했더라도 각 변경에는 사람 소유자가 남고, 문제가 생기면 그 사람이 고쳐야 한다는 것이 영상의 결론이다.

원문 주장: 화자들은 하루 약 3만 건의 코드 변경을 병합한다고 말하며, 검증 방법을 주면 결과 품질이 2~3배 좋아질 수 있다고 주장한다.
해석: 코드 생산량을 늘린 뒤 검증을 붙이는 것이 아니라, 처음부터 코드·검사·증거·책임자를 하나의 작업 단위로 설계해야 한다.
경계: 하루 3만 건, 2~3배 개선, 76%, 85% 같은 수치는 영상 밖의 자료로 독립 검증되지 않았다. 이전 처리량도 한 대목에서는 “약 3,000 또는 2,500”, 다른 대목에서는 “5월에 약 2,500”으로 표현된다. Claude.ai 개편 때 짧은 기간에 병합했다는 3,000개 PR은 하루 기준 3만 건과 다른 수치이므로 서로 바꿔 쓰면 안 된다.

여기까지만 이해하면 충분

  • AI가 코드를 빨리 쓰는 것과 팀이 안전하게 병합하는 것은 다른 문제다.
  • 에이전트는 코드뿐 아니라 테스트 결과, 화면, 동영상 같은 검증 증거도 내놓아야 한다.
  • 결정론적 검사, 에이전트 리뷰, 공급망 보안, 실제 실행 검증은 서로 다른 실패를 겨냥한다.
  • 자동화가 커져도 권한 통제와 변경 책임자는 사람에게 남는다.

오늘 대답할 질문

  • 왜 코드 생성 속도가 빨라져도 실제 배포 속도는 자동으로 빨라지지 않는가?

한 장면으로 이해하기

에이전트가 UI 변경 PR을 만들고 “완료”라고 보고한다. 사람은 이 말만 믿지 않는다. 브라우저 테스트 결과와 실제 클릭 동영상, 정적 검사 결과를 확인한다. 문제가 보이면 수정 훅이 변경 차이를 분석하고 PR을 고친다. 모든 필수 증거가 준비된 뒤에도 최종 책임자는 사람으로 남는다.

"코드 생성량이 사람의 검토 능력을 앞선다" 문제
→ "서로 다른 검증층을 실행하고 실제 동작 증거를 남긴다" 작동 방식
→ "사람이 증거와 책임자를 확인한 변경만 병합한다" 결과

비유와 깨지는 지점

출고 전 여러 검문소를 지나는 공장

한 검문소는 규격을 재고, 다른 검문소는 주문 의도와 맞는지 보고, 또 다른 검문소는 외부 부품의 위험을 검사한다고 생각할 수 있다. 마지막 책임자는 검사 기록을 보고 출고 여부를 판단한다.

비유가 깨지는 지점: 소프트웨어 검증은 완성품을 한 번 검사하고 끝나는 과정이 아니다. 결함이 발견되면 코드와 검사 기준을 수정하고 같은 흐름을 다시 돌아야 한다. 또한 영상은 각 검증층이 모든 문제를 완벽하게 잡는다는 독립 증거를 제시하지 않는다.

정확한 이름 붙이기

개념 쉬운 말 정확한 말 흔한 오해
소프트웨어 공장 반복 개발을 큰 규모로 돌리는 체계 계획·구현·검사·배포 루프를 에이전트와 자동화로 규모화한 작업 방식 사람 없이 코드를 무제한 생성하는 시스템만 뜻하지 않는다.
검증 증거 제대로 작동했다는 확인 자료 테스트 결과, 실행 기록, 스크린샷, 동영상 등 변경의 정확성과 완전성을 판단할 자료 에이전트의 “완료” 보고 자체가 증거는 아니다.
다층 검증 서로 다른 검사를 겹치는 것 문제 유형별로 결정론적 검사, 에이전트 리뷰, 공급망 검사 등을 배치하는 방식 같은 검사를 여러 번 반복하는 것과 다르다.
제로 트러스트 검증 자동 생성 결과를 처음부터 믿지 않는 것 각 루프에서 독립적으로 결과를 확인하고 필요한 권한만 허용하는 접근 모든 에이전트를 금지한다는 뜻이 아니다.
변경 책임자 문제가 생기면 고칠 사람 에이전트가 작성했더라도 PR과 결과에 최종 책임을 지는 사람 소유자 AI 작성 표시가 사람의 책임을 없애지 않는다.

내가 설명해 보기

1. 원인

AI가 코드 작성 속도를 높였는데도 안전한 배포가 같은 속도로 빨라지지 않는 이유는 무엇인가?

모범 답안 보기

생성된 코드의 양이 사람이 읽고 확인할 수 있는 양보다 빨리 늘기 때문이다. 작성이 끝났다는 사실만으로 정확성, 완전성, 실제 사용자 경험, 공급망 안전, 권한 준수를 알 수 없다. 따라서 병목은 코드 작성에서 검증 증거 생성과 책임자의 판단으로 이동한다.

2. 대조

불이 켜진 소프트웨어 공장과 어두운 소프트웨어 공장의 차이는 무엇인가?

모범 답안 보기

불이 켜진 공장에서는 사람이 계획·구현·검사·배포의 반복 과정에 계속 참여해 판단과 취향을 적용한다. 어두운 공장에서는 반복 작업이 더 자율적으로 돌아가고 사람은 의도 설정과 예외에 주로 개입한다. 후자가 무검증 자동화를 뜻하지는 않으며, 오히려 독립 검증과 권한 통제가 더 강하게 필요하다.

3. 적용

새로운 에이전트 자동화를 검토할 때 자율성을 늘려도 되는지 어떻게 판단할까?

모범 답안 보기

먼저 실패 유형을 나누고 각 유형을 잡을 검사와 증거가 있는지 본다. 실제 사용 환경에서 실행했는지, 권한과 샌드박스 경계가 있는지, 행동을 추적할 수 있는지, 문제가 생겼을 때 책임질 사람이 지정됐는지를 확인한다. 필수 증거가 빠져 있다면 생성 속도가 빨라도 자율성을 확대하지 않는다.

이번 글의 통찰

1. 검토 비용을 줄이려면 코드보다 증거의 형식을 먼저 설계해야 한다

  • [원문] 화자는 Claude가 1차 리뷰를 하고, 종단 간 테스트·브라우저 실행·린트 등을 수행하며, 사람은 에이전트가 남긴 증거를 확인한다고 설명한다.
  • [해석] 에이전트의 산출물 계약을 “코드 제출”에서 “코드와 재현 가능한 검증 증거 제출”로 바꾸면 사람은 중요한 판단에 집중할 수 있다.
  • [경계] 영상은 증거를 확인하는 데 걸리는 시간이나 결함 감소율을 제시하지 않는다. 결과 품질이 2~3배 좋아질 수 있다는 수치도 적용 조건과 측정 방식이 설명되지 않았다.

2. 자율성은 기능이 아니라 검증과 통제에서 얻는 신뢰의 결과다

  • [원문] 화자들은 모든 루프에서 독립 검증을 수행하고, 통제·권한·샌드박스를 관리하며, 에이전트가 작성한 변경에도 사람 소유자를 남겨야 한다고 말한다.
  • [해석] 더 강한 모델을 도입했다는 이유만으로 권한을 넓히기보다, 실패를 탐지하고 되돌릴 수 있다는 증거가 쌓인 범위에서만 자율성을 확대해야 한다.
  • [경계] “모든 것을 검증하라”, “자율성은 획득해야 한다”는 방향은 제시되지만, 허용 가능한 위험 수준이나 자동 병합 기준은 조직별로 구체화해야 한다.

3. 큰 처리량 수치는 병합의 안전성을 증명하지 않는다

  • [원문] 하루 약 3만 건의 변경 병합, 과거 약 2,500건, Claude.ai 개편의 짧은 기간 약 3,000개 PR이라는 수치가 각각 등장한다.
  • [해석] 처리량은 검증 체계를 설명하는 배경일 뿐이다. 안전성을 판단하려면 실패율, 결함 유출, 증거 충족 여부 같은 별도 지표가 필요하다.
  • [경계] 이전 일일 처리량은 “약 3,000 또는 2,500”이라는 표현과 “5월에 약 2,500”이라는 설명이 함께 나온다. 3,000개 PR은 개편 프로젝트의 짧은 기간 수치이며 일일 3만 건과 단위·기간이 다르다. 하루 3만 건의 주체도 해당 대화 맥락상 Anthropic으로 제시되지만 별도 원자료는 이 노트에서 검증하지 않았다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 영상은 “검증하라”는 말만으로는 부족하며 어떤 검사가 유용한지 구체화해야 한다고 말한다.
  • 통찰: 학습자의 “이해했습니다” 대신 보지 않고 설명하기, 새 사례 적용하기, 오류 수정하기 같은 관찰 가능한 증거를 요구할 수 있다.
  • 질문/행동: 설명·대조·적용 가운데 어떤 증거가 없으면 아직 이해하지 못한 것으로 볼지 먼저 정한다.

사업가 · 구조적 비유

  • 관련성: 코드 생산량이 늘어도 검증과 책임이 따라오지 않으면 실제 출고가 막힌다는 구조는 운영 자동화의 품질 병목과 닮아 있다.
  • 통찰: APOM에 적용한다면 현재 사실이 아니라 가상 검토로 한정해야 한다. 주문·상품·물류 자동화 후보마다 실행 속도보다 오류 탐지, 권한 범위, 책임자와 되돌리기 증거를 먼저 볼 수 있다.
  • 질문/행동: 자동화 후보 하나에서 결과를 출고하거나 고객에게 노출하기 전에 반드시 확인해야 할 증거는 무엇인가?

마케터 · 직접 전이

  • 관련성: 영상은 하루 3만 건, 59%, 76%, 2~3배처럼 강한 숫자와 브라우저 동영상이라는 구체적 장면을 함께 사용한다.
  • 통찰: 큰 숫자는 관심을 만들지만 실제 신뢰는 작동 장면과 검증 증거에서 생긴다. 카피에서는 주장, 측정 조건, 증거를 분리해 보여줘야 한다.
  • 질문/행동: 상세페이지의 핵심 주장 하나에 고객이 직접 확인할 결과 화면이나 재현 가능한 증거를 붙일 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 결정론적 검사, 에이전트 리뷰, 종단 간 테스트, 공급망 보안, 권한과 샌드박스가 영상의 직접 주제다.
  • 통찰: 모델 이름보다 작업의 실패 유형을 먼저 나누고, 각 실패를 잡을 독립 검사와 증거를 설계해야 한다.
  • 질문/행동: 다음 저위험 에이전트 PR에서 필수 검증 항목, 실행 증거, 허용 권한, 사람 책임자를 병합 전에 명시한다.

작은 실험 하나

  • 행동 1개: 다음 저위험 에이전트 PR 1건에서 병합 전에 결정론적 검사, 실제 실행 증거, 사람 책임자를 포함한 필수 검증 목록을 적용한다.
  • 측정 1개: 병합 판단 시점의 필수 검증 항목 미충족 개수를 센다.
  • 중단 기준 1개: 수정 후에도 필수 검증 항목 미충족 개수가 1개 이상이면 병합하거나 다른 작업으로 확대하지 않는다.

# 섹션 요지
1 생성량과 병합의 간극 코드 처리량은 늘었지만 프로덕션 병합 실패와 검토 부담이 남아 있다.
2 두 소프트웨어 공장 사람의 반복 개입 정도에 따라 불이 켜진 공장과 어두운 공장을 구분한다.
3 Anthropic의 검증 흐름 Claude의 1차 검토, 실제 실행, 수정 훅, 사람이 확인할 증거를 결합한다.
4 다층 검증 결정론적 검사, 에이전트 리뷰, 공급망 보안이 서로 다른 문제를 겨냥한다.
5 통제와 책임 권한·샌드박스·추적·PR 표시와 사람 소유자를 강조한다.
6 역량과 전망 리더와 주니어 모두 테스트 종류와 안전한 자동 병합 기준을 학습해야 한다.
7 수치와 출처 경계 수치의 단위·기간 충돌과 원작자 추정 상태를 구분한다.

1. 생성량과 병합의 간극

  • CircleCI가 “올해” 2,800만 개의 CI 작업 흐름을 분석했고 처리량이 약 59% 증가했지만, 프로덕션 병합 시도의 10건 중 3건이 실패했다는 수치가 제시된다.
  • 이 수치는 CircleCI의 독립 연구라고 소개되지만, 영상 안에서 연구 링크나 측정 정의는 제시되지 않는다.
  • 조직의 85%가 코딩 에이전트를 이미 사용하고 있으며 95%, 곧 100%까지 갈 것이라는 전망이 나온다. 근거 자료는 전사에 없다.
  • AI 코드를 생성하는 개발자의 76%가 확인하기 어려운 속도로 코드가 생산된다고 답했다는 주장도 출처 설명 없이 제시된다.
  • 화자들은 코드 작성은 빨라졌지만 검토 시간이 늘었으며, 핵심 질문은 “어떻게 확신을 갖고 더 빨리 배포할 것인가”라고 정리한다.
  • 좋은 테스트, 벤치마크, 명세처럼 품질에 대한 확신을 주는 검사물을 에이전트가 더 싸고 빠르게 생성할 수 있다고 본다.
  • 에이전트에게 정확성과 완전성을 확인할 방법을 주면 결과 품질이 2~3배 좋아질 수 있다는 주장이 나온다. 측정 방식과 적용 조건은 제시되지 않는다.

2. 두 소프트웨어 공장

  • 소프트웨어 공장은 반복 루프를 큰 규모로 활용하는 방식으로 정의된다.
  • 불이 켜진 공장에서는 에이전트가 계획·구현·검사·배포를 반복해서 돕지만, 사람이 과정 안에서 판단과 취향을 계속 적용한다.
  • 어두운 공장에서는 범위 설정·구현·검사가 계속 자동으로 수행되고, 사람은 의도와 예외 처리 쪽으로 이동한다.
  • 화자는 많은 팀이 이 두 모습 사이에 있으며, 신뢰할 수 있는 방식으로 자동화 수준을 높이는 여정에 있다고 설명한다.

3. Anthropic의 검증 흐름

  • 하루 약 3만 건의 코드 변경을 병합한다는 주장이 나온다.
  • 이전 처리량은 처음에 “약 3,000 또는 약 2,500”이라고 표현되고, Addy Osmani의 답에서는 5월에 약 2,500건을 병합했다고 설명된다.
  • Claude.ai 개편 사례에서는 짧은 기간 약 3,000개 PR을 병합해 성능을 약 3배 개선했다고 주장한다. 엔지니어, 제품 디자이너와 여러 기능 조직이 참여했다고 한다.
  • 검증 흐름은 Claude의 1차 리뷰에서 시작한다.
  • 에이전트가 실제 사용자처럼 경험을 시험할 수 있어야 한다. 종단 간 테스트, 브라우저 실행, 도구 실행, 린트와 필요한 검사를 예로 든다.
  • 버그나 기능 공백이 발견되면 수정 때 실행되는 훅이 변경 차이를 살피고 PR을 빠르게 고치는 루프를 만든다고 설명한다.
  • 팀이 중요하게 여기는 모범 사례와 취향은 공유 CLAUDE.md, AGENTS.md처럼 에이전트가 코드 리뷰 중 참고할 수 있는 곳에 규칙으로 남길 수 있다.
  • 사람은 에이전트의 검증 증거를 확인한다. UI라면 브라우저 테스트, 클릭 동영상, 모바일·데스크톱 화면 캡처나 영상을 예로 든다.

4. 다층 검증

  • 화자들은 다음 개선이 모델 품질과 검증의 결합에서 나올 것이라고 본다.
  • Claude Opus 4.5의 품질이 이미 꽤 좋은 수준이라는 평가가 나오지만, 이는 화자의 평가이며 비교 결과는 제시되지 않는다.
  • “그냥 검증하라”가 아니라 어떤 검사가 유용한지 설명해야 한다고 강조한다.
  • 종단 간 테스트, 속성 테스트, 시각 검증 테스트가 자동 병합에 필요한 확신을 주는 예로 제시된다.
  • 모든 회사가 제로 트러스트 다층 검증을 채택해야 한다는 강한 의견이 나온다.
  • 첫 번째 결정론적 층은 SQL 인젝션, 버퍼 오버플로 같은 버그와 보안 문제를 겨냥한다.
  • 두 번째 에이전트 리뷰 층은 결정론적 검사에 맞지 않는 논리와 의도 문제를 겨냥한다.
  • 세 번째 공급망 보안 층은 CVE, 악성코드, 악성 패키지 탐지를 담당한다.
  • “모든 문제가 해당 층에서 잡힌다”는 식의 표현은 화자의 강한 주장이다. 실제 탐지 범위와 누락률은 제시되지 않는다.

5. 통제와 책임

  • 일부 회사에서는 에이전트가 수백 또는 수천 개로 늘어 무엇을 하는지 알기 어려워졌다는 관찰이 제시된다.
  • 에이전트가 여러 시스템과 데이터에 접근하거나 프로덕션에 배포할 수 있기 때문에 에이전트 신원, 원격 측정과 행동 추적이 중요하다고 말한다.
  • 핵심 운영 질문은 통제, 권한, 샌드박스다. 에이전트가 허용된 공간을 벗어나지 않도록 해야 한다.
  • Addy Osmani는 에이전트 작성 코드를 PR에 표시하는 것이 좋다는 개인 의견을 밝힌다. 표시를 통해 추가 제약과 검사를 결정할 수 있다고 본다.
  • 다른 화자는 적어도 앞으로 6~9개월 동안은 PR 표시가 필요하다고 본다. 공장의 신뢰가 충분하지 않고 금융 고객의 감사 가능성에도 중요하다는 이유다.
  • 이 6~9개월은 녹화 시점을 기준으로 한 전망이지만 정확한 녹화일은 제공되지 않았다.
  • 에이전트가 작업을 시작했더라도 각 변경에는 사람 소유자가 남는다. 문제가 발생하면 그 사람이 고쳐야 한다는 책임 원칙을 강조한다.

6. 역량과 전망

  • 리더는 현재 테스트 방식과 에이전트가 스스로 병합을 승인할 만큼 편안한 상태 사이의 간극을 정의해야 한다.
  • 주니어 개발자는 종단 간 테스트와 속성 테스트 등 여러 검사 방식을 직접 경험해야 한다고 조언한다.
  • 안전한 병합은 아무 일도 일어나지 않을 것이라는 충분한 확신이나 위험을 가능한 만큼 완화했다는 근거가 있을 때 가능하다고 설명한다.
  • “코드를 빨리 쓰는 것은 빨리 배포하는 것이 아니다”라는 문장으로 작성 속도와 출하 속도를 구분한다.
  • 병합되는 변경을 세고 살피며, 에이전트가 샌드박스를 벗어나 프로덕션에 들어가지 않는지 확인해야 한다고 말한다.
  • 자율성은 검증을 통해 얻어야 하며, 소프트웨어 공장이 “곧, 빠르면 내년”에 올 것이라는 전망을 제시한다. 이는 실현된 사실이 아니라 미래 예측이다.

7. 수치와 출처 경계

  • 이전 일일 변경량: “약 3,000 또는 약 2,500”과 “5월 약 2,500”이라는 표현이 함께 나온다. 하나로 통일하지 않는다.
  • 3,000개 PR: Claude.ai 개편의 짧은 기간 수치다. 하루 3만 건이나 과거 일일 처리량과 같은 단위로 취급하지 않는다.
  • 하루 3만 건: 화자의 주장으로 보존한다. 이 노트에 제공된 자료만으로 독립 검증하지 않았다.
  • 59%와 10건 중 3건: CircleCI 독립 연구라고 소개되지만 “올해”의 기준 연도와 측정 정의는 전사에서 확인되지 않는다.
  • 85%, 95%, 100%, 76%, 2~3배: 전사에 원자료와 측정 조건이 없다.
  • 화자와 원작자: 전사에는 Addy Osmani와 Manish Kapur가 등장한다. META의 원작자 후보는 Addy Osmani, 소속 후보는 Anthropic이지만, 채널이 원본 영상 링크를 제공하지 않아 이름과 관련 링크를 기준으로 추정한 값이라고 명시되어 있다.
  • 제작·업로드 주체: 제공된 META의 채널과 업로더는 모두 Tech Bridge다. 이를 원작자나 Anthropic의 공식 채널로 해석하지 않는다.

하루 코드 변경 3만 건, 사람이 전부 읽을 수 있을까요? Anthropic의 Addy Osmani와 Manish Kapur가 실제 코드 리뷰 방식을 설명합니다. Claude의 1차 검토부터 브라우저에서 남기는 검증 증거, 여러 겹의 테스트까지, 에이전트에게 어디까지 맡기고 무엇을 사람이 확인해야 할지 함께 살펴보겠습니다.

CircleCI는 올해 2,800만 건의 CI 워크플로를 분석했고, 처리량(throughput)이 약 59% 증가했다는 사실을 발견했습니다. 하지만 그 코드를 프로덕션에 병합하려는 시도 10건 중 3건은 여전히 실패하고 있습니다. 이는 CircleCI의 독립 연구에서 나온 통계입니다.

그리고 제가 매일 대화하는 대부분의 고객에게서도 같은 추세가 보인다고 생각합니다. Addy의 말을 인용하면 이렇습니다. “소프트웨어 팩토리(software factory)는 규모에 맞게 루프를 활용하는 것이다.”

이 말이 제게 상당히 와닿았습니다. 여기 계신 많은 분이 “소프트웨어 팩토리”라는 용어를 들어보셨을 텐데, 적어도 염두에 둘 만한 팩토리 유형은 두 가지가 있습니다. 소프트웨어 팩토리는 규모에 맞게 루프를 활용하는 것입니다. 라이트온 팩토리(lights-on factory)는 에이전트가 계획 수립, 빌드, 점검, 코드 배포를 반복해서 도와주지만, 그 과정에서 사람인 여러분이 여전히 판단력과 취향을 적용하는 형태입니다.

그리고 다크 소프트웨어 팩토리(dark software factory)가 있습니다. 이는 로봇이 작동하는 자동차 공장과 조금 더 비슷한 형태로, 계속해서 작업을 수행합니다. 범위를 정하고, 빌드하고, 점검합니다. 사람인 여러분은 의도에 대해 생각하는 쪽으로 더 이동하고, 정말 예외적인 경우에만 관여하게 됩니다. 많은 팀이 이 스펙트럼의 어딘가에 있으며, 신뢰할 수 있는 방식으로 자동화를 점점 더 확대하려면 어떻게 해야 할지 알아가는 여정에 있다고 생각합니다. 좋습니다.

이제 AI 코딩은 사실상 해결된 문제입니다. 우리 모두 에이전트가 등장했다는 것을 알고 있습니다. 조직의 85%가 이미 코딩 에이전트를 사용하고 있습니다. 이 비율은 95%로, 그리고 아주 가까운 시일 내에 100%로 올라갈 것입니다.

AI 코드를 생성하는 개발자의 76%는 코드가 자신들이 검증할 수 없는 속도로 만들어지고 있다고 말합니다. 그래서 코드 리뷰에 점점 더 많은 시간을 쓰고 있습니다. 지금 엔지니어링 리더들이 가장 시급하게 생각하는 질문은 무엇이라고 보시나요?

지난 1년 동안 팀들은 에이전트와 협업하는 데 더 능숙해졌다고 생각합니다. 모델과 하네스(harness)도 더 좋아졌습니다. 제가 많은 리더에게서 듣는 관심사는 이것입니다. 어떻게 하면 여러분이 확신을 가지고 코드를 더 빠르게 배포하도록 지원할 수 있을까?

그리고 이 확신이라는 부분이 매우 중요합니다. 이제 에이전트는 그 어느 때보다 훨씬 저렴하게 코드를 점검할 방법을 만들어낼 수 있습니다. 고품질 코드라고 부를 수 있게 해주는 요소를 생각해 보면, 좋은 테스트, 벤치마크, 사양(spec)처럼 확신을 주는 것들이 있습니다. 요즘 에이전트는 이런 것들을 더 쉽고 빠르게 생성하도록 도와줄 수 있습니다. 물론 우리는 그런 것들을 다듬을 수 있지만, 저는 이런 점검이 요즘 우리가 시간을 써야 할 가장 중요한 일 중 하나라고 생각합니다.

에이전트에서 최고 품질의 결과물을 얻고 싶다면, 작업이 올바른지 검증할 방법을 에이전트에 제공해야 합니다. 이를 갖추고 코드가 정확하면서도 완전한지 확인할 수 있다면, 결과물의 품질을 쉽게 2~3배 향상할 수 있습니다.

네, 네, 정말 맞는 말씀입니다. 정확합니다. 그들은 매일 약 3만 건의 코드 변경을 병합하고 있습니다.

불과 몇 달 전만 해도 약 3천 건, 혹은 2,500건 정도의 코드 변경을 처리했습니다. 하루 코드 변경 건수를 2,500건에서 3만 건으로 확대한 것입니다. 정말 놀라운 일입니다.

그렇다면 Addy, Anthropic의 Claude Code와 여러분이 함께 일하는 Claude Code 팀에서 코드 리뷰는 어떤 모습인가요?

네, 훌륭한 질문입니다. 저희는 훨씬 전인 5월에도 약 2,500건의 변경을 병합하고 있었습니다. 그리고 최근 Claude.ai를 개편할 때도 성능을 약 3배 향상했다고 사례 연구를 통해 공개했습니다. 이는 엔지니어, 제품 디자이너, 그리고 여러 직군의 사람들이 참여해 아주 짧은 기간에 약 3,000개의 풀 리퀘스트(pull request)를 병합함으로써 달성했습니다.

검증과 코드 리뷰를 도입하기 위한 저희의 워크플로는 먼저 Claude가 1차 리뷰를 수행하도록 하는 것입니다. 여기서 매우 중요한 점은 실제 사용자와 비슷하게 경험을 직접 시도해 볼 방법을 Claude에게 제공하는 것입니다. 여기에는 엔드투엔드 테스트(end-to-end test), 경험을 열어 보기, 브라우저에서 확인하기, 필요한 도구 실행하기, 린팅(linting), 그리고 확신을 쌓는 데 필요한 기타 점검이 포함될 수 있습니다.

사람들은 보통 이렇게 묻습니다. “좋아요. 그런데 버그나 기능상의 공백을 발견하면 어떻게 하나요?” 저희에게는 편집이 발생할 때마다 실행되는 훅(hook)이 있습니다. 이 훅은 diff를 살펴보고, PR을 최대한 빠르게 수정하는 루프를 구축할 수 있게 해줍니다.

그리고 점점 더 중요해지는 것은 팀이 모범 사례와 팀의 취향이라고 생각하는 것을 팀의 공유 CLAUDE.md, AGENTS.md 또는 코드 리뷰 중 에이전트가 참고할 수 있는 다른 곳에 어떻게 명문화할지 고민하는 것입니다. 그런 다음 사람은 에이전트가 제시한 근거를 확인할 책임을 집니다.

그럼 어떻게 알 수 있을까요? 브라우저에서 사용자가 이용할 UI를 만들고 있다면, 브라우저에서 테스트되었는지 확인하고 싶을 것입니다. 에이전트가 그 경험을 클릭하며 돌아다니는 영상을 생성해 확신을 줬을 수도 있습니다. 그렇다면 좋습니다. 작동하는 것입니다.

모바일이나 데스크톱 경험이 중요하다면 스크린샷이나 동영상을 생성하게 할 수도 있습니다. 기본적으로 에이전트가 가능한 한 많은 검증 증거를 제공하는 단계까지 가고 싶은 것입니다.

좋습니다. 네, 검증이 핵심입니다. 다음 단계의 발전은 검증을 제대로 해내는 것과 모델 품질을 개선하는 일이 결합되어 나타날 것이라고 생각합니다. 하지만 이미 모델은—Claude Opus 4.5를 보면—모델 품질이 꽤 좋은 수준에 도달했습니다.

검증 단계에 관한 모범 사례를 공유하는 우리의 역량이 점점 더 중요해질 것이라고 생각합니다. 사람들에게 “작업을 검증하세요”라고 말하면, 다음 질문은 “그게 대체 무슨 뜻인가요?”가 되기 때문입니다.

네, 맞습니다. 대화는 어떤 종류의 테스트가 유용한지 구체적으로 다루는 방향으로 발전해야 한다고 생각합니다. 저희는 엔드투엔드 테스트, 프로퍼티 테스트(property test), 시각적 검증 테스트(visual verification test)에 많이 의존합니다. 이런 것들이 변경 사항을 자동으로 병합할 수 있다는 확신을 얻는 데 도움을 줍니다.

저희는 모든 회사가 제로 트러스트(zero-trust), 다층 검증(multilayered verification) 접근 방식을 도입해야 한다고 절대적으로, 100% 믿습니다.

검증은 모든 루프에서 수행되어야 합니다. 에이전트 루프 안에서 작업하든, CI 검증 루프 안에서 작업하든, 코드 유지보수를 하든 마찬가지입니다. 각각의 모든 루프에서 팩토리의 출력물, 즉 에이전트가 생성하는 코드를 검증하는 것이 중요합니다.

저희는 이를 계층의 관점에서 바라봅니다. 이렇게 생각해 보세요. 첫 번째 계층은 SQL 인젝션과 버퍼 오버플로 버그 같은 버그와 보안 문제를 잡아내는 결정론적 계층(deterministic layer)입니다. 이런 문제는 모두 여기서 잡힙니다.

그다음 두 번째 계층에서는 에이전트 기반 리뷰(agentic review)가 진행됩니다. 에이전트가 해당 코드를 리뷰하는 것입니다. 이 에이전트 기반 리뷰에서는 결정론적 계층이 잡기에 적합하지 않은 로직과 의도 관련 문제를 찾아냅니다.

저희는 각 계층을 사용해 특정 유형의 문제를 대상으로 삼습니다. 세 번째 계층은 소프트웨어 공급망 보안 계층(software supply-chain security layer)이 될 수 있습니다. 여기서는 모든 CVE를 살펴보고, 멀웨어와 악성 패키지 탐지를 수행합니다. 이 모든 작업이 세 번째 계층에서 이루어집니다.

각 계층이 특정 유형의 문제를 잡도록 조정되고 최적화된 다층 접근 방식입니다.

저는 몇 달 전만 해도 엔지니어링 팀이 에이전트를 가지고 자유롭게 실험하도록 허용하는 것이 가장 큰 걱정 중 하나였다는 회사들을 아주 많이 만났습니다. 어떤 경우에는 에이전트가 수백 개, 수천 개에 이르는 단계에 도달했는데, 그들이 무엇을 하는지 전혀 알 수 없었습니다.

이 에이전트들은 실제로 무엇을 하고 있을까요? 모든 시스템을 건드리고 온갖 종류의 데이터에 접근하고 있습니다. 어쩌면 프로덕션에 배포하고 있을 수도 있습니다. 많은 기업은 에이전트의 신원과 텔레메트리(telemetry), 그리고 실제로 무슨 일이 일어나고 있는지 추적할 수 있는 능력에 대해 우려합니다.

많은 회사에 가장 중요한 세 가지는 다음과 같다고 생각합니다. 통제를 어떻게 생각할 것인가? 권한을 어떻게 생각할 것인가? 샌드박스(sandbox)를 어떻게 생각할 것인가? 에이전트가 샌드박스에서 빠져나와 해서는 안 되는 일을 하지 않도록 어떻게 보장할 것인가?

네. 에이전트가 작성한 코드는 PR에 표시해야 할까요? 저는 개인적으로 표시해야 한다고 생각합니다. 역사적으로 우리는 코드에 대해 강한 주인의식과 자부심을 느껴왔습니다. “내가 이걸 작성했다. 내 이름을 걸겠다”는 식이었죠. Anthropic에서는 이를 조금 다르게 생각합니다.

저희는 Claude가 “이걸 작성한 사람은 나다”라고 표시되는 것을 그다지 신경 쓰지 않는 단계까지 발전했습니다. 사용자가 받게 될 코드와 기능이 올바른 것인지 확인하고 결과에 더 집중하기 때문입니다.

저는 코드가 에이전트가 작성한 것이라고 표시되어도 괜찮다고 생각합니다. 그렇게 하면 이런 것도 파악하는 데 도움이 됩니다. “좋아요, 에이전트가 작성했다면 어떤 제약과 추가 점검을 계속 유지해야 할까?”

저도 같은 관점입니다, Addy. 단기적으로, 적어도 앞으로 6~9개월 동안은 PR에 표시해야 한다고 생각합니다.

팩토리에 대해 충분히 확신할 수 있을 때까지는 이를 알고 추적하고 싶습니다. 감사 가능성(auditability) 측면에서 금융 고객에게도 중요합니다.

표시하면 누가 코드를 작성했는지 알 수 있습니다. 결국 우리는 여전히 책임을 져야 하기 때문입니다.

네, 맞습니다. 여기서 가장 중요한 부분은 책임성(accountability)입니다. 저희는 여전히 각 변경 사항의 소유자가 누구인지 표시합니다. 제가 작업을 완료하도록 Cloud Run을 실행했을 수도 있지만, 여전히 책임은 제게 있습니다. 문제가 생기면 제가 가서 고쳐야 합니다.

네, 네. 핵심적인 지적입니다.

올해 주니어 개발자나 리더가 키워야 할 역량 하나는 무엇일까요?

리더라면 팀이 검증(verification)의 의미가 무엇인지 정말 깊이 생각하도록 이끌어야 한다고 생각합니다. 이미 테스트 같은 것을 어떻게 접근하고 있나요? 현재 방식과, 에이전트가 코드가 충분히 괜찮아서 스스로 병합해도 된다고 확신할 수 있는 지점 사이에는 어떤 격차가 있나요?

그걸 알아내야 합니다. 주니어라면 그 반대편에 있는 셈입니다. 엔드투엔드 테스트(end-to-end tests), 속성 기반 테스트(property tests) 등 다양한 종류의 테스트에 대해 실제로 더 많은 경험을 쌓아야 합니다.

네. 에이전트가 PR(pull request)을 열었습니다. 아무것도 잘못되지 않을 것이라고 완전히 확신하거나, 문제가 생길 가능성을 최대한 완화했다면 병합해도 안전합니다.

코드를 작성하는 것이 가장 빠른 부분이고, 그 문제는 해결됐습니다. 모든 팀을 위한 철저한 검토와 검증이 그 속도를 유지하는 데 도움이 될 것입니다. 작성이 빠르다고 배포까지 빠른 것은 아닙니다.

무엇이 병합되고 있는지 세고, 무엇이 병합되고 있는지 살펴보고, 프로덕션에 들어가기 전에 샌드박스(sandbox) 밖으로 빠져나가지 않는지 확인해야 합니다. 모든 것을 검증해야 하며, 자율성은 노력으로 얻어지는 것입니다. 소프트웨어 팩토리(software factories)에 대해서는 아주 곧, 늦어도 내년에는 다루게 될 것입니다. 팩토리의 각 루프 안에 독립적인 자동 검증을 넣어야 합니다. 팩토리가 만들어 내는 결과물을 신뢰할 수 있도록 해야 합니다.
