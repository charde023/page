완전한 Claude 운영체제의 설계도입니다

한 줄 요약

Claude Code는 CLAUDE.md(커널)·MCP(드라이버)·Skills(프로그램)·Loops(스케줄러)·Dynamic Workflow(조율자)로 구성된 하나의 운영체제이며, Workflow는 결정적(deterministic)·병렬 분리 가능·검증 필요·단일 컨텍스트 초과 작업에만 써야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
CLAUDE.md = OS 커널 에이전트 전체 동작의 근간 잘못 설정하면 나머지 컴포넌트가 전부 무너진다
Dynamic Workflow Opus 4.8에서 새로 출시된 장기 작업 조율 기능 JS 코드로 서브에이전트 흐름을 엄격히 정의
Workflow vs Goal 결정성(determinism) 차이로 적합 작업이 다름 Workflow=폭(wide)·병렬, Goal=깊이(deep)·순차
Workflow 사용 4기준 토큰 낭비 방지를 위해 기준이 명확해야 함 독립 분리 가능·컨텍스트 초과·검증 필요·결정적
Schema 강제 출력 서브에이전트 결과를 일관된 형식으로 받음 에이전트마다 엄격한 JSON 폼 지정, 통과 시 반환
Deep Research Workflow 내장 멀티스텝 리서치 파이프라인 검색→소스 페치→적대적 검증→합성 4단계
Workflow 지속성(persistence) 세션 종료 후에도 진행 상태 유지 /resume 명령으로 캐시된 에이전트 작업 복원

내가 모를 만한 것 / 처음 보는 것

  • Dynamic Workflow: .claude/workflow/ 디렉토리 안에 저장되는 JavaScript 파일 — 마크다운이 아닌 코드로 서브에이전트 흐름을 정의
  • Goal command: 종료 조건이 될 때까지 에이전트가 루프를 돌리는 비결정적(non-deterministic) 방식 — Workflow와 구별됨
  • Loops / Routines: Claude Code의 크론잡 — 반복 작업을 스케줄링, 사용자 모니터링 불필요
  • Adversarial verification: Deep Research 3단계 — 수집된 주장들을 교차 검증하는 단계 (단순 팩트 체크보다 강함)
  • Morning Brief Workflow: 여러 소스에서 서브에이전트가 정보를 수집해 일일 브리핑을 반환하는 커스텀 워크플로우 예시
  • Audit Workflow: Second Brain의 끊어진 링크·설정 오류를 검사하고 보고서로 반환
  • /workflow 슬래시 명령: 실행 중인 워크플로우의 각 단계·모델·토큰 소비량을 확인하는 명령

화자의 디테일 (놓치기 쉬운 포인트)

  1. Dynamic Workflow는 현재 Research Preview 상태 — 일반 Claude Code 세션보다 토큰 소비가 훨씬 많음. $200 플랜도 몇 시간이면 소진 가능.
  2. Deep Research 단일 실행에 100만 토큰 소비 — 작은 주제 하나 리서치에서도 이 정도 소비. 신중하게 사용.
  3. 경쟁사 분석 Workflow 실행 결과: 679,000 토큰, 34개 에이전트 사용 → 완전한 마크다운 보고서 생성.
  4. 워크플로우는 자기 개선(self-improvement) 기능이 있음 — 실행 중 오류를 만나면 수정 패치를 적용해 다음 실행 시 같은 문제를 반복하지 않음.
  5. 마이그레이션 테스트 수치: Workflow 없이 1시간 이상 걸리던 코드베이스 라이브러리 변환이 Workflow 적용 후 21분으로 단축.
  6. 서브에이전트는 각자 독립된 컨텍스트 윈도우를 가짐 — 추론 과정은 코드 파일에 남고 메인 컨텍스트 윈도우에는 결과만 진입.
  7. workflow 키워드가 프롬프트에 있어도 Workflow를 생성하겠다는 의도가 명확하지 않으면 트리거되지 않음 — 매우 구체적인 의도 표현 필요.
  8. Second Brain 구성 시 Google Calendar + Notion MCP를 연결 → 캘린더 읽기·일정 생성·Notion 프로젝트 파일 접근 가능.
  9. Hooks 예시: 에이전트가 파일 편집을 마치면 자동으로 포맷팅을 실행하도록 설정 가능 (hooks 설정).
  10. Skills 생성 팁: 긴 세션 도중 "이걸 자주 할 것 같다" 싶으면 해당 세션의 학습을 Skill로 묶어달라고 요청하는 것이 최선.

1. Claude Code는 운영체제다

Anthropic이 지속적으로 업데이트를 출시하면서 Claude Code는 단순 코딩 에이전트를 넘어 풀 운영체제(OS) 처럼 작동하게 됐다. 전통적인 OS가 머신 위의 모든 작업을 조율하듯, Claude Code도 그 역할을 맡는다. 핵심은 이 OS를 구성하는 컴포넌트들을 제대로 이해하고 설정하는 것이다.

2. OS 컴포넌트 5가지

전통 OS Claude Code 동등 요소 역할
커널 CLAUDE.md + 컨텍스트 파일 에이전트 전체의 핵심 구동 프로그램
드라이버 MCP (Model Context Protocol) 외부 도구·기기와의 인터페이스
일반 프로그램 Skills + Commands 반복 가능한 작업의 구조화된 지침
스케줄러/크론잡 Loops + Routines 정해진 시간·조건에 작업 자동 실행
조율자 Dynamic Workflow 위 모든 요소를 묶어 장기 작업 완성

CLAUDE.md가 잘못 설정되면 에이전트가 프로젝트의 목적을 파악하지 못하고, 나머지 컴포넌트도 연쇄적으로 무너진다.

3. Dynamic Workflow 작동 원리

Opus 4.8과 함께 출시된 기능. 기존 Skills·Goal command와 다른 점:

  • Skills: 단일 에이전트가 지침을 읽고 수행. 장기 작업 부적합.
  • Goal command: 종료 조건까지 에이전트가 반복 루프. 비결정적 — 시스템이 다음 행동을 결정.
  • Dynamic Workflow: 결정적 — JS 코드가 정확히 무엇이 일어날지 정의. 서브에이전트들을 스폰해 병렬 수행.

작동 방식: 1. 프롬프트에서 Workflow 생성 의도를 감지 2. .claude/workflow/ 에 JS 파일 생성 3. 서브에이전트마다 엄격한 출력 스키마(JSON form) 지정 → 스키마를 통과할 때까지 반복 후 반환 4. /workflow <이름> 슬래시 명령으로 실행 5. 백그라운드 실행 → /workflow 명령으로 진행 상태·모델·토큰 소비 확인 6. 세션 종료 후 /resume 으로 캐시 복원, 중단 지점부터 재개

4. Workflow 사용 기준 4가지

Research Preview 단계 — 토큰 소비가 매우 많으므로 기준을 엄격히 적용해야 한다.

기준 설명
독립 분리 가능 서브태스크들이 서로 의존하지 않아야 병렬 효과를 얻음
컨텍스트 초과 단일 컨텍스트 윈도우로 처리하기엔 너무 큰 작업이어야 함
검증 필요 보안 발견·버그 주장·마이그레이션처럼 틀리면 비용이 큰 작업
결정적 작업 실행 전에 단계가 명확히 정해지는 작업. 런타임에 다음 스텝을 결정해야 하면 Goal 사용

Wide vs Deep 프레임: - Wide(폭) → Workflow: 여러 서브태스크를 동시에 실행 - Deep(깊이) → Goal: 한 번에 하나씩, 단계를 거치며 깊이 파고듦

5. 내장 Deep Research Workflow

Claude Code에 기본 탑재된 멀티스텝 리서치 파이프라인.

  1. 검색(Search): 관련 정보 검색
  2. 페치(Fetch): 찾은 소스에서 세부 내용 수집
  3. 적대적 검증(Adversarial verification): 주장들을 교차 검증
  4. 합성(Synthesis): 최종 문서 한 개로 통합

특징: 서브에이전트가 부모 에이전트의 도구를 상속받음. 토큰 집중적(작은 주제도 100만 토큰 가능).

6. 커스텀 Workflow 예시

경쟁사 분석 Workflow (4단계, 리서치 Workflow 구조와 유사): - 사용량: 679,000 토큰, 34개 에이전트 - 결과: 비교 지표와 발견 사항이 담긴 완전한 마크다운 보고서 - 자기 개선: 실행 중 문제 발생 → 패치 적용 → 다음 실행 시 동일 오류 없음

모닝 브리프 Workflow: - 여러 소스에서 서브에이전트들이 정보 수집 → 하루 시작용 브리핑 반환

7. Second Brain에 OS 적용

비코딩 프로젝트에도 동일한 OS 구조 적용 가능:

  • CLAUDE.md: 따라야 할 형식·규칙 문서화 (커널)
  • Vault 파일들: OS의 메모리 — 무엇을 어떻게 하는지 기록
  • MCP: Google Calendar + Notion 연결로 외부 소스 접근
  • Skills: 반복 수행하는 작업에 구조화된 지침
  • Workflow: 모닝 브리프, 감사(audit) 등 병렬화 가능한 루틴

Audit Workflow 활용 권장: 시간이 지나면 끊어진 링크·설정 오류가 누적됨 → 주기적으로 감사 후 수정.

8. 코딩 프로젝트에 OS 적용

컴포넌트 코딩 프로젝트 적용 예시
CLAUDE.md 프로젝트 전체 정보 + 에이전트 설정
Hooks 파일 편집 완료 후 자동 포맷팅 실행
Skills 새 엔드포인트 추가 — 항상 동일 스키마 준수
Workflow 배포 전 변경 검토, DB 마이그레이션, E2E 테스트

마이그레이션 실증: Workflow 없이 1시간+ → Workflow 적용 후 21분.

교정 전사 (한국어)

전체 전사 펼치기

중세 왕국을 다스리는 왕을 상상해보라. 왕국 전체를 운영해야 하는데, 사실 아무것도 안 하고 다른 사람들이 알아서 처리해주기를 바란다. 문제는, 직원들이 일일이 지시를 받는 데만 익숙하다는 것이다. 진짜 필요한 건 왕국 전체가 스스로 돌아가는 시스템이다. 그것이 바로 Claude Code가 된 것이다.

Anthropic이 업데이트를 계속 출시하면서, Claude Code는 단순한 코딩 에이전트를 넘어 완전한 운영체제(OS) 가 됐다 — 머신 위의 모든 것을 조율하는 OS. 그 핵심을 완성하는 것이 Dynamic Workflow다. 왕이 왕국 전체를 에이전트에게 넘기기 전에, 이 시스템이 어떻게 작동하는지 먼저 살펴보자.

컴퓨터 OS와 Claude Code OS의 유일한 차이는, 설정에 그다지 많은 노력이 필요하지 않다는 것이다(Arch 리눅스를 쓰지 않는 한). 마이크 드라이버를 잔뜩 설치할 필요도 없다. 실제 OS처럼, 여러 파트로 구성되며 각 파트가 없으면 시스템이 완성되지 않는다.

OS 컴포넌트와 Claude Code 동등 요소:

  • 커널: OS에서 가장 중요한 계층. Claude Code에서는 CLAUDE.md 파일과 컨텍스트 파일이다. 커널이 에이전트 전체의 구동 프로그램이며, 제대로 설정되지 않으면 에이전트가 프로젝트가 원하는 것을 파악하지 못하고 나머지 컴포넌트도 무너진다.
  • 드라이버: 시스템이 외부 기기와 상호작용하게 하는 것. Claude Code에서는 MCP다. Claude가 외부 도구가 필요할 때 MCP를 통해 접근하고 호출한다.
  • 일반 프로그램: Claude Code에서는 Skills와 Commands다. 반복 가능한 작업에 대한 구조화된 지침을 담고 있으며, 필요할 때 언제든 호출한다.
  • 스케줄러/크론잡: Claude Code에서는 최근 추가된 Loops와 Routines다. 반복 작업을 자동화하여 수동으로 모니터링할 필요를 없앤다.
  • 조율자: 이 모든 것을 하나의 완전한 OS로 묶어주는 요소 — Dynamic Workflow. Opus 4.8과 함께 출시됐다.

Dynamic Workflow가 기존 아키텍처와 다른 점:

  • Skills: 한 에이전트가 지침을 읽고 수행. 에이전트를 더 나은 방식으로 안내하지만, 그 에이전트 혼자만 수행한다. 장기 작업에는 부적합.
  • Goal command: 사전 정의된 종료 목표를 향해 에이전트가 루프를 돌린다. 장기 작업 개선에 뛰어난 시도였고, 우리 팀도 출시 이후 많이 써왔다. Goal과 Workflow 모두 여러 에이전트를 조율할 수 있지만 다르다. 핵심 차이는 결정성(determinism)이다. Goal은 비결정적 — 시스템이 다음에 할 일을 결정. Workflow는 결정적 — 코드가 정확히 무엇이 일어날지 정의.

Workflow는 workflow 키워드로 생성한다. 프롬프트에서 Claude가 작업에 필요한 Dynamic Workflow를 식별한다. 프롬프트에서 이 단어를 자주 쓰더라도, Workflow를 생성하겠다는 명확한 의도가 없으면 트리거되지 않는다.

기존의 마크다운 대신 JavaScript 코드를 생성한다. .claude/workflow/ 디렉토리 안에 저장되며, 이 스크립트 전체로 흐름을 제어한다. 계획이 컨텍스트 윈도우에 존재하는 대신, 코드에 작성돼 서브에이전트들의 단계별 동작을 정의한다. 각 에이전트는 엄격한 출력 스키마(폼)가 지정되며, 스키마를 통과할 때까지 반복 후 결과를 반환한다.

/workflow <이름> 슬래시 명령으로 실행. 백그라운드에서 실행되므로 다른 작업을 계속할 수 있다. 진행 상황을 확인하려면 /workflow 명령 실행 — 각 단계, 각 에이전트가 호출한 모델, 소비 토큰 수를 볼 수 있다.

세션이 종료돼도 진행 상태가 유지된다. /resume 명령으로 캐시된 에이전트 작업을 불러와 중단된 곳부터 재개한다. 각 Workflow는 고유 ID를 갖는다.

주의: Research Preview 단계이므로 일반 Claude Code 세션보다 토큰을 훨씬 많이 소비한다. 여러 서브에이전트가 각자 독립된 컨텍스트 윈도우에서 실행되기 때문이다. $200 플랜도 몇 시간이면 소진될 수 있다.

Workflow를 써야 하는 경우 4가지:

  1. 독립적으로 분리 가능한 단위: 에이전트들이 서로 의존하면 기다려야 하고 병렬 효과가 없어진다. 태스크 간 의존성이 낮을수록 더 좋은 병렬 처리와 빠른 결과를 얻는다.
  2. 단일 컨텍스트 윈도우를 초과하는 작업: Workflow는 각자 컨텍스트 윈도우를 가진 여러 서브에이전트를 쓰므로, 실제로 이 창을 필요로 할 만큼 큰 작업이어야 한다. 그렇지 않으면 시간과 토큰 낭비다. 각 서브에이전트는 자체 신선한 컨텍스트에서 실행하고 결과만 반환한다. 추론 과정은 코드 파일에 남아 메인 컨텍스트 윈도우에 진입하지 않는다.
  3. 검증이 필요한 작업: 잘못된 답이 비용이 클 때 — 보안 발견, 버그 주장, 마이그레이션. 하지만 검증에 추가 에이전트가 필요해 토큰과 시간이 소비된다. 실제로 가치 있는 작업인지 확인해야 한다.
  4. 결정적인 작업: Workflow는 코드로 에이전트를 고정된 구조로 호출한다. 런타임에 다음 태스크를 결정해야 하는 비결정적 작업이면 Workflow가 적합하지 않다.

Wide vs Deep: 작업의 형태로 Workflow와 Goal 중 선택하라. Wide(넓음) = 동시에 실행 가능한 여러 서브태스크로 분리 → Workflow. Deep(깊음) = 한 번에 하나씩 더 깊이 파고듦 → Goal.

내장 Deep Research Workflow: 예전에 컨텍스트 파일과 CLAUDE.md로 직접 만들던 멀티스텝 리서치 파이프라인. 이제 어느 프로젝트에서든 호출 가능한 Workflow로 내장됐다.

5단계로 실행: 정보 검색 → 소스에서 세부 내용 페치 → 주장들을 교차 검증하는 적대적 검증 → 하나의 최종 문서로 합성. /workflows 명령에서 각 서브에이전트가 부모 에이전트의 도구를 상속받는 것을 확인할 수 있다. 토큰 집중적 — 이 한 번의 실행에서 작은 주제로 100만 토큰이 소비됐다.

멀티스텝 리서치 외에도 다른 리서치 Workflow를 구축해 리서치 시스템의 일부로 만들 수 있다. 우리가 직접 만든 경쟁사 분석 Workflow는 경쟁사들을 조사하고, 성과를 확인하고, 경쟁 우위를 찾는다. 4단계로 분리돼 있고, 실행 완료 후 결과를 보고한다. 이 실행에서 679,000 토큰과 34개 에이전트를 사용했고 완전한 마크다운 보고서를 작성했다. 또한 실행 중 문제를 만나면 수정을 적용해 다음 실행 시 같은 문제를 반복하지 않는다.

Everyday 프로그램 — Skills: OS의 일반 프로그램. 반복하는 작업에 대한 지침을 담는다. 긴 세션 중 "이걸 자주 하겠다"고 느끼면, 해당 세션의 학습을 Skill로 묶어달라고 Claude에게 요청하면 된다.

메모리 — Vault 파일들: OS의 메모리. 무엇을 하는지, 어떻게 하는지를 기록한다. 사용자 자신보다 더 많이 알고 있다. 외부 소스에도 접근할 수 있도록 Google Calendar와 Notion MCP를 연결했다. Notion의 프로젝트 파일 접근, 캘린더 읽기·일정 생성·업데이트가 가능하다. CLAUDE.md 파일에 따라야 할 정확한 형식을 문서화하는 것이 중요하다. 반복 작업을 병렬화하고 서브에이전트에게 넘기는 Workflow를 만드는 것이 핵심이다.

모닝 브리프 Workflow: 서브에이전트들을 스폰해 여러 소스에서 정보를 수집하고 하루를 시작하는 브리핑을 반환한다. 이 모든 것이 설정되면, 프롬프트를 주면 알맞은 Skill과 컨텍스트를 로드하고, 올바른 위치에 파일을 생성하고, 관련 파트들을 자동으로 연결한다.

Second Brain을 오래 써왔다면 Audit Workflow를 만들어야 한다. 끊어진 링크를 확인하고 설정의 모든 문제를 노출해 보고한다. 수정을 실행하고 Second Brain을 최상의 상태로 유지할 수 있다.

코딩 프로젝트에도 동일하게 적용 가능하다. CLAUDE.md를 커널로 설정하고 모든 프로젝트 정보를 안에 넣는다. 프로젝트용 에이전트를 구성(일반 프로그램 역할). 에이전트가 파일 편집을 마치면 자동으로 포맷팅하는 등 다양한 케이스에 Hooks를 설정한다. 새 엔드포인트 추가처럼 반복 작업에 Skills를 만든다 — 모든 엔드포인트가 원하는 스키마를 따르게 된다. 배포 전 변경 검토, 코드베이스·DB 마이그레이션, E2E 테스트 실행에 Workflow를 만든다.

마이그레이션 실증 결과: Workflow 없이 1시간 이상 걸리던 것이 Workflow 적용 후 21분으로 단축됐다.

이것이 OS가 코딩 유즈케이스로 확장되는 방식이다. 프로젝트를 빌드할 때 모든 것을 직접 처리하지 않아도 된다. OS가 대신 해준다.
