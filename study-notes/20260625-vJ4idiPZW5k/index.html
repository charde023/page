OpenClaw 제작자의 새로운 비밀 프로젝트입니다

한 줄 요약

OpenClaw 제작자 Peter Steinberg가 만든 Crabbox는 수십 개 에이전트를 병렬로 돌릴 때 생기는 "PR 검증·병합" 병목을 풀기 위한 클라우드 샌드박스 도구다 — 워크트리마다 격리된 클라우드 박스에서 dev 서버를 띄우고, 커밋 없이 로컬 변경분(diff)만 동기화해 몇 초 만에 재테스트한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
병목이 "코드 작성"에서 "병합"으로 이동 에이전트를 10~15개씩 병렬로 돌리면 PR이 폭증하고, 리뷰·병합·검증이 진짜 병목이 된다 코드는 싸졌고 검증이 비싸졌다
코드베이스 하니스(harness)의 1단계 = 에이전트가 스스로 검증·증거 산출 에이전트가 자기 작업을 증명해야 사람이 안심하고 병합 Playwright로 테스트 + 영상·스크린샷 아티팩트를 PR에 첨부
로컬 워크트리만으로는 테스트가 안 된다 워크트리는 코드 격리만 해줄 뿐, dev 서버·DB·포트·Docker는 공유 → 한 에이전트가 스키마 바꾸면 다 깨짐 격리는 코드가 아니라 "실행 환경"까지 필요
에이전트별 격리 샌드박스에서 dev 서버 실행 각 에이전트가 자기 DB·환경을 가진 박스를 소유 → 충돌 0 병렬 세션 수만큼 클라우드 박스
Crabbox = 커밋 없이 로컬 diff 동기화 + 클라우드 실행 git commit/push/CI 흐름은 불필요한 커밋이 쌓이고 박스 재빌드가 느림 → 수정 후 몇 초 만에 재테스트가 핵심 가치 warmup → run(자동 diff sync) → stop

내가 모를 만한 것 / 처음 보는 것

  • Crabbox — 이 영상의 주인공. 로컬 워크트리의 미커밋 변경분을 클라우드 박스로 SSH 동기화해 그 안에서 임의 명령(dev 서버·테스트)을 실행하는 도구. (재사용 개념 → English-한국어에 용어 정리)
  • OpenClaw — Peter Steinberg가 만든 (앞선) 프로젝트. 화자가 그를 "OpenClaw 제작자"로 소개.
  • 워크트리(git worktree) — 한 리포에서 여러 브랜치를 각각 다른 폴더로 동시에 체크아웃하는 git 기능. 에이전트마다 독립 작업 디렉터리를 줄 때 쓴다. 단, 코드만 격리될 뿐 dev 서버·DB는 공유라는 게 이 영상의 핵심 한계.
  • Daytona — Crabbox가 쓰는 샌드박스 프로바이더(클라우드 박스 제공). 빠른 부팅이 장점. snapshot(미리 만든 이미지)으로 박스를 띄움.
  • snapshot (Daytona) — Dockerfile + 컨텍스트로 미리 구워둔 박스 이미지. 새 샌드박스를 이 스냅샷에서 빠르게 시작.
  • eval harness / codebase harness — 화자가 반복 강조하는 "에이전트가 일을 잘 끝내도록 코드베이스에 깔아두는 도구·스킬·검증 장치" 묶음.
  • artifact (아티팩트) — 테스트 증거물(스크린샷·영상). Crabbox가 artifact collect/videos/publish 명령으로 캡처·S3 업로드·PR 인라인 첨부까지 지원.
  • Playwright CLI — 에이전트가 브라우저로 직접 E2E 테스트하고 영상·스크린샷을 남기게 해주는 도구. 화자가 "검증 증거 산출에는 Playwright가 최선"이라 평가.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 화자는 상시 최소 10개, Peter는 사진상 최소 15개 에이전트 세션을 병렬로 돌린다 — 이게 PR 폭증의 출발점.
  2. 로컬 한 대엔 Docker 데몬 1개, DB 1개, OS 1개뿐 → 모든 워크트리가 같은 인스턴스를 공유. 한 세션이 새 스키마를 시험하면 나머지가 다 깨진다.
  3. 포트 하드코딩 문제 — 많은 코드베이스가 (합당한 이유로) 포트를 하드코딩해 다중 인스턴스 동시 실행이 어렵다.
  4. Crabbox 흐름: warmup → run setup(의존성 설치+dev 서버 기동) → 테스트 → stop. run은 매번 로컬 미커밋 변경분을 박스로 먼저 sync한 뒤 명령 실행 → 로컬에서 돌리는 것과 거의 동일.
  5. .crabbox.yml 설정 파일 — 프로바이더 지정, sync 제외 폴더(node_modules·.next·turbo는 보통 gitignore라 자동 제외, 추가로 무거운 증거/에셋 폴더를 exclude), 박스로 넘길 환경변수 키 정의. 환경키는 SSH 위 암호화 데이터 플레인으로 전달.
  6. setup.sh — 에이전트가 한 스크립트만 돌리면 dev 서버가 뜨도록.
  7. Daytona 60초 타임아웃 — setup이 길면 끊기므로 백그라운드로 실행 + 10초마다 상태 리포트하는 헬퍼 cbx.sh를 따로 만들었다(cbx.sh up).
  8. --no-sync 플래그 — 파일 읽기나 Playwright CLI 테스트처럼 재동기화가 불필요한 명령에 붙여 sync 생략.
  9. SSH 터널로 로컬 3000↔박스 3000을 연결하면 로컬 브라우저로 샌드박스 dev 서버를 직접 볼 수 있지만 — 로컬 포트를 점유해 충돌나므로 화자는 비추천. 에이전트가 클라우드 안에서 Playwright로 테스트하고 증거만 회수하는 쪽을 선호.
  10. crabbox test 스킬을 정의해 에이전트가 "박스 띄우고 → dev 서버 → Playwright E2E → 증거 회수" 절차를 알게 함. pw preview 명령(id·provider·no-sync)도 사전 정의.
  11. 증거 업로드는 S3 버킷 또는 GitHub release assets(PR에 파일 인라인 첨부 가능)로.
  12. 화자가 만든 crabbox setup 스킬과 codebase harness 스킬은 오픈소스 — Claude Code/Codex에 물려 Dockerfile·프로바이더 연결·.crabbox.yml 전 과정을 자동 셋업.

# 섹션 요지
1 새 병목: 병합 병렬 에이전트 → PR 폭증 → 검증·병합이 병목
2 하니스 1단계 에이전트가 스스로 검증·증거(Playwright 아티팩트)
3 로컬의 한계 워크트리는 코드만 격리, dev 서버·DB·포트는 공유 → 충돌
4 해법: 격리 샌드박스 에이전트별 클라우드 박스에서 dev 서버 실행
5 Crabbox 동작 커밋 없이 diff sync → 클라우드 실행 → 초 단위 재테스트
6 구성 파일 Dockerfile + .crabbox.yml + setup.sh
7 실전 셋업 Daytona 스냅샷 → warmup → cbx.sh → Playwright 테스트 → 증거 PR 첨부

1. 새 병목은 "코드 작성"이 아니라 "병합"이다

지난 몇 달간 화자의 가장 큰 변화는 동시에 돌리는 병렬 에이전트 세션 수. 팀이 각종 루프를 깔아두자 에이전트가 알아서 이슈를 찾아 작업을 집어가고, 상시 10개 이상이 돈다. 결과는 전에 없던 엄청난 양의 PR — 그러나 그만큼 리뷰·병합 부담도 폭증한다. 각 PR은 시스템을 깨뜨릴 리스크를 안고 있어서, 이제 병목은 "코드를 쓰는 것"이 아니라 "어떻게 코드를 코드베이스에 병합하느냐"로 옮겨갔다.

2. 코드베이스 하니스의 첫걸음 — 에이전트가 스스로 검증하고 증거를 남긴다

화자가 콘텐츠에서 반복하는 핵심은 올바른 코드베이스 하니스 구축. 그 1단계는 에이전트에게 자기 작업을 검증하고 증거를 산출할 도구·스킬을 주는 것이다. Playwright API가 최선의 선택 — 에이전트가 브라우저로 직접 테스트할 뿐 아니라 영상 녹화 같은 아티팩트를 출력한다. 에이전트가 이 증거를 PR에 첨부하면 사람이 훨씬 안심하고 병합할 수 있다.

3. 로컬 워크트리만으로는 안 깨지던 게 깨진다

이 셋업은 에이전트 3~4개일 땐 잘 돌았다. 진짜 문제는 수십 개가 동시에 돌 때다. 동시에 DB 스키마를 바꾸거나 테스트를 돌리면 충돌한다. Claude Code가 워크트리로 티켓별 코드 격리를 해줘도, 그건 코드를 쓰고 고치는 데만 좋다. 테스트하려면 그 워크트리 코드로 dev 서버를 띄워야 하는데 로컬에선 어렵다: 포트 하드코딩, 로컬 Supabase 단일 인스턴스, Docker 데몬 1개·DB 1개·OS 1개 공유. 한 세션이 새 스키마를 시험하면 나머지가 다 깨진다. 설령 코드베이스를 그런 문제가 없게 정리해도, 현대 프로덕션 리포는 자원을 많이 먹어 스케일이 어렵다.

4. 올바른 해법 — 워크트리마다 격리된 샌드박스에서 dev 서버

로컬에서 모든 세션을 병렬로 돌리는 대신, 워크트리마다 개별 격리 환경을 띄워 dev 서버를 시작한다. 각 에이전트가 자기 샌드박스를 소유하고, 그 안에 자기 DB·환경이 있어 실제로 dev 서버를 띄울 수 있으며 서로 영향을 주지 않는다. 그러나 이런 파이프라인 구축은 결코 사소하지 않다 — 박스를 띄우고, 디스크 모니터링, 코드 복사, 의존성 설치, 앱 기동, 브라우저 열어 테스트, 끝나면 종료·삭제. 화자 팀은 이걸 직접 다 구현했고(엄청난 작업이지만 동작하면 강력) — 그래도 남는 문제: dev 서버를 띄워 테스트 중 버그를 만나 로컬에서 코드를 고치면, 그 더러운(미커밋) 파일을 샌드박스로 넣을 쉬운 방법이 없다. 일반 commit/push/CI 흐름은 불필요한 커밋이 쌓이고, 박스를 다시 빌드하긴 싫다(앞 과정 반복). 이상적인 건 수정 후 몇 초 만에 재테스트다.

5. Crabbox가 주는 가치

Crabbox는 에이전트가 ① 클라우드에 박스를 매핑하고 ② 로컬 워크트리 폴더의 diff를 동기화하고 ③ 실시간으로 테스트를 돌리게 한다. crabbox warmup으로 박스를 데우고, crabbox run <명령>으로 임의 배치 명령을 — 단 클라우드 박스에서 — 실행한다. 매 실행 시 먼저 로컬의 미커밋 변경분을 박스로 sync한 뒤 명령을 돌리므로(폴더가 git init만 돼 있으면 됨), 로컬에서 돌리는 것과 거의 같다. 끝나면 crabbox stop으로 박스 종료·삭제. 전체 흐름:

crabbox warmup        # 샌드박스 기동
crabbox run setup     # 의존성 설치 + dev 서버 기동
crabbox run <test>    # 또는 Playwright E2E. 버그 만나면 로컬 수정 → 다음 run에서 자동 sync
crabbox stop          # 종료·삭제

6. 구성 파일 3종

  1. Dockerfile — 로컬이 가진 모든 것(Supabase CLI 등 필요한 CLI/도구)을 캡슐화. 에이전트에게 프롬프트로 생성시켜도 됨.
  2. .crabbox.yml — 프로바이더(여기선 빠른 부팅의 Daytona), 사용할 snapshot, 기본 워크루트, sync 제외 폴더(node_modules·.next·turbo는 보통 자동, 추가로 무거운 증거/에셋 폴더 exclude), 박스로 넘길 환경변수 키. 환경키는 SSH 위 암호화 채널로 전달돼 비교적 안전.
  3. setup.sh — 에이전트가 한 번에 dev 서버를 띄우도록.

7. 실전 셋업 흐름

daytona login → daytona organization list/use → daytona snapshot create(이름·Dockerfile·컨텍스트, CPU/메모리/디스크/리전 지정)로 스냅샷 생성 → Daytona API key를 환경변수로 등록 → crabbox warmup --provider daytona --slug <세션ID>로 박스 기동. 화자는 여러 Crabbox 명령을 묶은 헬퍼 cbx.sh를 만들어 cbx.sh up(박스 기동 + ready까지 상태 확인 + setup.sh 실행)을 한 방에. Daytona 60초 타임아웃 때문에 setup은 백그라운드 + 10초마다 리포트.

실행은 crabbox run --provider daytona --id demo bash <명령>. --no-sync 플래그로 재동기화 불필요 명령(파일 읽기·Playwright) 처리. 화자는 SSH 터널(로컬 3000↔박스 3000)로 로컬 브라우저 테스트도 가능하지만 포트 점유 충돌 때문에 비추천 — 대신 에이전트가 클라우드 안에서 Playwright로 테스트하고 증거만 회수. crabbox test 스킬과 pw preview 명령을 정의해 "박스 띄우고 → dev 서버 → Playwright E2E → 스크린샷/영상 증거 회수" 자동화. 증거는 S3 또는 GitHub release assets로 PR에 인라인 첨부. 이렇게 하면 원하는 만큼 병렬 세션을 충돌 없이 돌릴 수 있다.

마무리로 화자는 자신의 crabbox setup 스킬(Dockerfile·프로바이더 연결·yaml 전 과정 자동화)과 codebase harness 스킬(Crabbox 외 효율적 작업에 필요한 필수 요소 전반)을 오픈소스로 공개했다고 안내.

OpenClaw 제작자인 Peter Steinberg가 Crabbox라는 새 프로젝트를 만들고 있다. 수백 개의 에이전트를 병렬로 돌리는 사람들이 에이전트 작업을 아주 쉽게 검증하게 해주는 도구다.

지난 몇 달간 내게 가장 큰 변화는 동시에 돌리는 병렬 에이전트 세션 수다. 특히 우리 팀이 온갖 루프를 셋업한 뒤로는, 에이전트가 스스로 이슈를 찾아 자율적으로 작업을 집어간다. 거의 항상 최소 10개의 에이전트 세션이 돌고 있다. Peter의 사진을 보면 최소 15개 세션을 병렬로 돌리고 있다. 이게 전엔 불가능했던 어마어마한 양의 PR을 만들어낸다. 그러나 동시에 PR 리뷰와 실제 고객 배포에 큰 부담을 만든다. 각 PR과 작업이 시스템을 깨뜨릴 리스크를 안고 있기 때문이다. 그래서 병목은 더 이상 코드 작성이 아니라 "어떻게 코드를 코드베이스에 병합하느냐"가 됐다는 게 꽤 분명해졌다.

내 콘텐츠를 봐왔다면 알겠지만, 내가 사람들에게 시키려는 핵심 중 하나가 올바른 코드베이스 하니스 셋업이다. 그 1단계는 에이전트에게 자기 작업과 증거를 검증할 도구·스킬을 주는 것이다. Playwright API가 아마 최선이다. 에이전트가 브라우저로 직접 테스트할 뿐 아니라, 이런 영상 녹화 같은 아티팩트를 출력한다. 그러면 에이전트가 그 아티팩트·증거를 PR에 포함시켜, 우리가 에이전트 작업을 실제 코드베이스에 병합하기 훨씬 쉬워진다.

이 셋업은 에이전트 3~4개를 돌릴 때는 잘 됐다. 진짜 깨지는 건 그렇게 많은 에이전트가 병렬로 돌 때다 — 동시에 DB 스키마를 바꾸거나 테스트를 돌려야 할 수 있다. 여기서 오늘날 진짜로 깨진다. Claude Code가 엔지니어 티켓마다 워크트리를 줘도, 그건 에이전트가 격리된 환경에서 코드를 쓰고 고치는 데만 좋다. 테스트할 때는 그 워크트리 코드로 dev 서버를 띄워야 하는데, 로컬 환경에서 그건 매우 어렵다. 예컨대 많은 사람의 코드베이스는 여러 인스턴스를 동시에 돌릴 수 있게 셋업돼 있지 않다. 어떤 포트는 합당한 이유로 하드코딩돼 있다. 또 로컬 Supabase로 돌 수도 있는데, 컴퓨터 한 대엔 Docker 데몬 1개·DB 1개·OS 1개뿐이라 그 환경들이 같은 인스턴스를 공유한다. 그중 하나가 새 스키마를 시험하면 나머지를 다 쉽게 깨뜨릴 수 있다. 코드베이스를 그런 문제가 없게 정리해도, 현대 프로덕션 리포에서 돌리면 자원을 많이 먹어 스케일이 어렵다.

올바른 해법은, 로컬에서 모든 세션을 병렬로 돌리는 대신 워크트리마다 개별 격리 환경을 띄워 dev 서버를 시작하는 것이다. 즉 에이전트마다 자기 샌드박스를 소유하고, 그 안에 자기 DB와 그 외 모든 게 있어 진짜 dev 서버를 띄울 수 있으며, 각 샌드박스는 격리돼 서로 영향을 안 준다. 하지만 그런 파이프라인 셋업은 사소한 일이 아니다 — 박스를 즉석에서 띄우고, 디스크를 모니터링하고, 코드를 복사해 넣고, 의존성을 설치하고, 앱을 띄우고, 브라우저를 열어 테스트하고, 끝나면 꺼서 삭제해야 한다. 우리 팀은 이 과정을 직접 다 셋업했고, 동작하면 굉장하다. 그래도 문제가 더 있다 — dev 서버를 띄워 테스트하는 목적은 이슈·버그를 드러내는 것인데, 이 과정에서 버그를 만나면(에이전트가 박스에서 테스트하다 뭔가 깨진 걸 발견) 로컬에서 코드를 고쳐 버그를 고친다. 그런데 다음에 뭘 해야 하나? 그 더러운(미커밋) 파일을 샌드박스로 넣을 쉬운 방법이 없다. 일반 commit·push·CI 흐름은 잘 안 통한다 — 리포에 불필요한 커밋이 잔뜩 쌓이기 때문이다. 또 방금 거친 과정을 다시 거치고 싶지 않으면 박스를 다시 빌드하기도 싫다. 이상적인 건, 변경하면 몇 초 만에 재테스트해서 되는지 확인하는 것이다. 바로 여기서 Crabbox가 큰 가치를 준다.

Crabbox는 에이전트가 클라우드에 박스를 매핑하고, 로컬 워크트리 폴더의 diff를 동기화하고, 실시간으로 테스트를 돌리게 해주는 도구다. crabbox warmup 명령으로 박스를 데우고, 에이전트는 crabbox run 명령으로 로컬 컴퓨터에서 하듯 임의의 배치 명령을 돌리되, 그 명령은 클라우드 박스에서 실행된다. 이 명령이 돌 때마다 먼저 로컬의 diff를 클라우드 박스로 동기화한다 — 커밋할 필요조차 없고, 그 폴더가 git init만 돼 있으면 모든 미커밋 변경분을 클라우드로 sync한 뒤 명령을 돌린다. 그래서 로컬에서 명령을 돌리는 것과 거의 같다. 끝나면 crabbox stop으로 박스를 꺼서 삭제한다. 그게 거의 전부다. 에이전트에게 Crabbox를 줘서, 태스크를 끝낼 때마다 crabbox warmup으로 샌드박스를 띄우고, crabbox run setup으로 의존성을 설치하고 dev 서버를 띄운 뒤, 사전 정의된 테스트를 돌리거나 Playwright 같은 도구로 스스로 E2E 테스트를 한다. 버그를 만나면 로컬에서 고치고, 다음에 명령을 돌리면 최신 변경분이 자동으로 클라우드에 sync돼 항상 최신 버전을 테스트할 수 있다. 끝나면 crabbox stop. 필요한 건 로컬이 가진 모든 것(Docker나 필요한 CLI)을 캡슐화한 Dockerfile을 정의하고, 작은 .crabbox.yml 파일을 정의하는 것뿐이다. 이 yaml에는 어떤 샌드박스 프로바이더인지, sync하기 싫은 파일은 무엇인지, 넘길 환경변수 키는 무엇인지 정의한다. 여기 나열한 환경키는 SSH 연결 위로 박스에 바로 푸시되므로 암호화된 데이터 플레인이라 비교적 안전하다. 이 파일이 모든 Crabbox 명령의 전체 설정을 정의한다. 한편 setup 스크립트도 둬서 에이전트가 그 스크립트만 돌리면 dev 서버가 다 뜨게 한다. 또 이미지·영상 같은 증거 아티팩트를 생성해 데이터 스토리지에 publish하는 유용한 명령들도 있다. 매 run마다 artifact global 명령이 끝난 뒤 매칭되는 아티팩트를 자동 다운로드한다. 에이전트가 E2E 테스트 스크립트를 쓰면 끝나는 즉시 파일이 로컬로 자동 회수돼 특히 유용하다. 또 artifacts collect(컴퓨터 스크린샷), artifacts videos(클라우드 컴퓨터 화면 녹화), artifacts publish(S3 버킷 직접 업로드) 명령으로 이미지·영상을 PR 코멘트에 인라인으로 올릴 수 있다.

그게 거의 전부다. 같이 하나 셋업해보자. 로그인 기능이 있는 웹 인터페이스를 가진 웹앱이 있고, 어시스턴트 에이전트와 채팅할 수 있다. 이 앱은 프런트엔드가 있고 로컬 Supabase 인스턴스도 돌린다 — 즉 워크트리 2~3개가 병렬로 작업하면 다 같은 Supabase 인스턴스를 바꾸므로 쉽게 못 바꾼다. 하지만 Crabbox를 셋업하면 에이전트 워크트리마다 클라우드에서 테스트할 수 있다. 먼저 필요한 패키지·도구(여기선 Supabase CLI 등)를 캡슐화한 Docker 이미지를 정의한다. 보통 에이전트에게 이런 Dockerfile을 만들라고 프롬프트하면 된다. 그다음 .crabbox.yml을 정의한다. 여기선 빠르게 뜨는 Daytona를 쓴다. 프로바이더를 정의하고, Daytona 안에선 snapshot을 넘긴다 — 스냅샷은 Daytona에 미리 만들어둔 이미지로, 새 컴퓨터를 띄울 때 그 이미지를 쓴다. 기본 워크루트를 정의하고, 그 아래 sync 동작을 정의한다. exclude 태그가 있는데, node_modules·.next·turbo는 보통 이미 gitignore라 넣을 필요 없고 env 파일도 마찬가지다. 다만 이것의 이점은, 꽤 무겁고 sync에 필요 없는 폴더(내 경우 과거 증거나 액세스 파일 폴더)를 exclude할 수 있다는 것이다. 또 샌드박스에 넘길 특정 환경변수도 정의할 수 있다. 이게 .crabbox.yml이다. 마지막으로 setup.sh를 정의한다 — 에이전트가 이 스크립트 하나만 돌리면 단계별로 안 하고 자동으로 dev 서버를 띄우게.

해보자. 새 터미널을 연다. 보통 제일 먼저 할 일은 샌드박스 프로바이더에 스냅샷을 만드는 것이다. 우리는 Daytona를 쓰니 daytona login. 나는 Daytona 조직이 여러 개라 daytona organization list로 두 프로젝트를 보고, 이 super design 프로젝트를 쓰겠다 — daytona organization use. 활성화됐다. 다음은 스냅샷 생성이다 — daytona snapshot create에 이름을 주고 Dockerfile·컨텍스트 폴더를 가리킨다. 그다음 원하는 CPU·메모리·디스크, 리전을 정의하고 엔터. 나는 이미 스냅샷을 만들어서 여기서 멈추지만, 끝나면 프로바이더에 스냅샷이 뜬다. 그다음 Daytona를 Crabbox에 연결해야 한다. 프로바이더마다 방식이 좀 다르다. Daytona는 API key를 써야 했는데, Daytona에서 키를 만들어 로컬에 환경변수로 설정한다. 그러면 crabbox warmup --provider daytona에 slug(세션 ID, 예: all-tests)를 줘서 그 세션용 샌드박스를 띄운다. 나는 cbx.sh라는 헬퍼 스크립트를 따로 만들었다 — 몇몇 Crabbox 명령을 하나로 묶은 것이다. up 명령은 박스를 띄우고 ready까지 상태를 확인한 뒤, ready되면 우리가 정의한 setup.sh(의존성 설치 + 전체 기동)를 백그라운드로 실행한다. 프로바이더마다 한계가 있는데, Daytona는 60초에 타임아웃된다고 봐서, 명령을 백그라운드로 돌리고 끝날 때까지 10초마다 결과를 리포트하게 했다. 그래서 개별 명령을 일일이 돌리는 대신 에이전트는 bash cbx.sh up만 돌리면, 명령을 떼어내 setup을 시작한다 — 내 리포는 Supabase 인스턴스가 있어 좀 걸리지만, 그런 의존성이 없으면 훨씬 빨리 뜬다. ready된 걸 볼 수 있다.

다음은 보통 crabbox run --provider daytona --id demo bash <명령>으로 여러 명령을 돌린다. --no-sync 플래그도 있는데, 이 명령에 대해 파일을 sync하지 말라고 Crabbox에 알리는 것으로, 파일 읽기 액션이나 Playwright CLI 테스트처럼 재sync가 싫은 시나리오에 특히 유용하다. 내 cbx.sh엔 프로바이더와 no-sync 플래그를 언제 줄지 등 많은 걸 미리 정의해뒀다. 그래서 bash cbx.sh로 아무 명령이나 돌릴 수 있다. 한편 유용한 것들 — Crabbox 샌드박스가 뜨면 샌드박스로 SSH 터널을 열 수 있다. 첫 명령은 샌드박스 키를 얻고, 둘째 명령은 로컬 3000 포트를 샌드박스 3000 포트로, 로컬 백엔드 포트를 샌드박스 백엔드 포트로 연결한다. 이러면 로컬에서 샌드박스 dev 서버를 테스트할 수 있다. 새 브라우저 탭을 열면 샌드박스 버전 앱이 열려 테스트할 수 있어 그 자체로 매우 유용하다. 하지만 우리 경우엔 좋은 해법이 아니다 — 여전히 로컬 포트 하나를 점유해 충돌을 일으키기 때문이다. 대신 나는 에이전트가 그런 Playwright CLI 배치 명령을 클라우드에서 돌려 증거를 받아오거나, 사전 정의된 E2E 테스트를 돌리게 한다. 우리 경우 에이전트용으로 crabbox test라는 스킬을 정의했다. 그래서 절차를 안다 — 클라우드에 dev 서버를 띄우고, Playwright CLI로 테스트한다. 여기 정의한 pw 명령(id·provider·no-sync 플래그가 붙은 preview 명령)도 있다. 그래서 에이전트를 띄워 "Crabbox로 내 앱 테스트해줘"라고 하면, 박스를 띄우고 dev 서버를 시작해 Playwright로 전체 E2E 테스트를 하고, 동작함을 보여주는 스크린샷이나 영상 녹화 증거를 들고 돌아온다. 이 증거를 S3 버킷에 올리거나, GitHub의 release assets(PR에 파일을 인라인 에셋으로 올릴 수 있음)에 올릴 수 있다. 그리고 원하는 만큼 병렬 세션을 동시에 돌려도 충돌이 없다.

이렇게 Crabbox를 쓸 수 있다. 자기 코드베이스에 셋업하고 싶다면, 내가 만든 crabbox setup 스킬을 Claude Code나 Codex에 주면 Dockerfile 셋업·프로바이더 연결·.crabbox.yml·전 과정을 따라갈 수 있다. Crabbox뿐 아니라 에이전트가 코드베이스에서 훨씬 효율적으로 일을 끝내게 돕는 필수 요소들까지 셋업하는 codebase harness 스킬도 있다. 오픈소스이니 자유롭게 써도 된다. 한편 기초를 넘어선 바이브 코딩을 위한 더 심층적인 단계별 워크숍도 있다 — 실제 프로덕션 코드베이스에서 루프를 만드는 것에 대해 내가 배운 것들과 다른 유용한 자료들. 관심 있으면 아래 링크로 AI Builder Club에도 가입할 수 있다. 유용했길 바란다. 고맙고 다음에 보자.
