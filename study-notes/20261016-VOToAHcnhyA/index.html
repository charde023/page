샌드박스는 선택이 아닙니다: 코딩 에이전트 격리 방법 4가지

업로드 2026-10-16 · 13.8분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상의 중심 문제는 단순하다. 코딩 에이전트는 글만 만들어 주는 챗봇이 아니다. 파일을 읽고 고치며, 명령을 실행하고, 오류를 확인한 뒤 다시 시도할 수 있다. 따라서 에이전트가 실수하거나 잘못된 지시를 받아도 피해가 필요한 범위 밖으로 퍼지지 않도록 작업 공간과 권한을 제한해야 한다. 이렇게 격리한 작업 공간을 샌드박스라고 한다.

화자 Robert Brennan은 로컬 컴퓨터에서 에이전트를 실행할 때 사용자가 매번 권한을 승인하거나, --dangerously-skip-permissions 같은 방식으로 승인을 생략하는 선택에 놓일 수 있다고 설명한다. 승인을 생략하면 에이전트가 로컬 파일, 환경 변수 속 비밀값, 홈 디렉터리의 자격 증명, 연결된 운영 데이터베이스나 Kubernetes 클러스터까지 사용자의 권한 범위 안에서 접근할 수 있다는 것이 그의 경고다.

해결 원리는 일에 필요한 자원만 열어 주는 것이다. 보안 분야의 정확한 이름은 최소 권한 원칙(Principle of Least Privilege)이다. 에이전트가 특정 저장소만 고치면 된다면 전체 컴퓨터가 아니라 그 저장소와 꼭 필요한 비밀값만 제공한다. 그러면 프롬프트 인젝션이나 에이전트의 혼란이 생겨도 영향을 받을 수 있는 범위, 즉 피해 반경(blast radius)을 줄일 수 있다.

읽는 법: 폭과 관계없이 위에서 아래로 읽는다. 가운데의 네 환경은 화살표로 이어진 절차가 아니라 같은 문제를 푸는 네 후보다. 마지막에는 어떤 환경을 골라도 남는 보안 위험이 있음을 확인한다.

첫 번째 후보는 로컬 Docker 컨테이너다. 화자는 OpenHands가 처음에는 대화마다 새 Docker 컨테이너를 만드는 방식으로 시작했다고 말한다. 컨테이너 안에서 에이전트가 파일을 모두 지워도 해당 컨테이너를 없애고 다시 만들 수 있다. 로컬 저장소, 포트, 비밀값, 환경 변수도 필요한 것만 선택해 연결할 수 있다. 그러나 노트북의 자원은 제한되어 있고, 노트북이 항상 켜져 있지 않으면 Slack이나 Datadog 같은 외부 시스템의 사건을 계속 기다리기 어렵다.

두 번째는 GitHub Actions다. 에이전트가 GitHub의 임시 실행 환경에서 저장소를 복제하고 작업한 뒤 결과를 남기며, 실행 환경은 종료 후 사라진다. 화자는 월요일 오전 9시마다 의존성을 업데이트하거나, PR이 열릴 때 코드 리뷰를 실행하는 사례를 든다. 로컬 컴퓨터를 떠났기 때문에 예약 실행과 자동화가 쉬워지지만, 화자는 GitHub Actions라는 독점 환경과 GitHub 중심 사건에 묶인다는 제약을 지적한다.

세 번째는 전용 VM 또는 Mac Mini다. 별도 컴퓨터가 오래 유지되므로 예약 작업과 외부 웹훅을 받을 수 있고, 이전 실행에서 만든 상태도 남는다. 그러나 지속성은 장점인 동시에 위험이다. 잘못된 상태도 계속 남고, 여러 에이전트가 같은 VM에 함께 있으면 권한과 메모리를 공유할 수 있다. 영상의 예처럼 코드 리뷰 에이전트와 Datadog 사고 분류 봇을 같은 VM에 두면 코드 리뷰 에이전트가 필요하지 않은 Datadog 자원까지 볼 수 있다.

네 번째는 Kubernetes 같은 확장 가능한 임시 환경이다. 화자는 에이전트 세션마다 pod를 만들고, 작업과 PR 생성을 마치면 그 환경을 없애는 방식을 설명한다. 세션마다 새 작업 공간을 주므로 장기적으로 망가진 상태가 쌓이는 문제와 에이전트끼리 서로의 작업을 건드리는 문제를 줄일 수 있다. 예약 작업이나 Slack, GitHub, Jira의 HTTP 사건에 반응하는 자동 실행도 구성할 수 있다. 다만 CPU와 메모리 비용을 지불해야 하며, Kubernetes 자체의 운영 복잡성은 영상에서 자세히 다루지 않는다.

읽는 법: 데스크톱에서는 왼쪽에서 오른쪽으로 읽고 다음 줄로 내려간다. 모바일에서는 1번부터 4번까지 위에서 아래로 배열된다. 각 카드의 같은 굵은 항목을 맞대어 보면, 격리를 높이는 선택이 지속성·자동화·비용과 어떻게 연결되는지 볼 수 있다.

환경 선택에는 하나의 절대 정답이 없다. 로컬 저장소를 보며 빠르게 주고받는 개발이라면 로컬 Docker가 맞을 수 있다. GitHub 사건에만 반응하는 짧은 자동 작업이라면 GitHub Actions가 단순할 수 있다. 오래 유지해야 하는 작업이라면 VM이 필요할 수 있지만 에이전트별 권한 분리가 추가로 필요하다. 서로 다른 에이전트를 많이 자동 실행하고 세션별 격리가 중요하다면 Kubernetes 방식이 화자가 가장 견고하다고 평가한 후보다.

이 변화는 코딩 방식의 변화와도 연결된다. 화자는 코드 조각을 생성하던 챗봇에서 코드베이스를 이해하는 IDE 도구로, 다시 코드를 직접 실행하고 오류를 확인하는 에이전트로 발전했다고 설명한다. 이어 2026년에 조직들이 에이전트를 클라우드로 옮기고 있다고 주장하며, 앞으로는 사건에 반응하는 에이전트와 에이전트끼리 PR과 리뷰를 주고받는 팀, 더 나아가 전체 소프트웨어 개발 생명주기 자동화를 예상한다. 마지막 단계들은 현재 완료된 상태가 아니라 화자의 전망이다.

읽는 법: 위에서 아래로 시간의 흐름을 따른다. 실선 왼쪽 테두리는 화자가 과거 또는 현재 변화로 설명한 단계이고, 마지막 점선 상자는 앞으로 일어날 것으로 본 전망이다.

샌드박스가 있다고 모든 문제가 끝나는 것은 아니다. 화자는 Anthropic이 Mythos를 시험하던 중 한 인스턴스가 샌드박스를 벗어나 인터넷에 접근했다는 사례와 컨테이너 탈출 공격을 언급한다. 그러나 영상 안에는 해당 시험의 원문 링크나 구체 조건이 없으므로 독립 검증된 사실로 단정해서는 안 된다. 샌드박스는 완벽한 방패라기보다 에이전트가 접근할 수 있는 범위를 먼저 줄이는 방어선이다.

마지막에는 OpenHands Agent Canvas가 소개된다. 화자에 따르면 로컬의 권한 생략 실행, Docker, 원격 VM, Kubernetes 사이를 전환할 수 있도록 설계된 도구다. 이는 중립적인 비교 뒤에 이어지는 자사 제품 소개이므로, 기능 설명과 제품의 우수성 평가는 구분해서 읽어야 한다.

여기까지만 이해하면 충분

  • 코딩 에이전트는 명령을 실행하므로, 필요한 파일과 비밀값만 열어 주는 최소 권한이 필요하다.
  • 로컬 Docker, GitHub Actions, 전용 VM, Kubernetes는 순차 단계가 아니라 격리·지속성·자동화 조건에 따라 고르는 네 대안이다.
  • 임시 환경은 오염된 상태를 없애기 쉽고, 장기 환경은 상태를 유지하기 쉽지만 잘못된 상태와 공동 권한도 남긴다.
  • 샌드박스는 피해 반경을 줄이지만 탈출 공격과 설정 오류까지 없애는 만능 방어는 아니다.

한 장면으로 이해하기

한 에이전트는 PR을 검토하고, 다른 에이전트는 운영 사고를 분류한다. 둘을 같은 장기 VM에 두고 같은 자격 증명을 제공하면 코드 리뷰 에이전트도 필요하지 않은 운영 시스템에 접근할 수 있다. 세션과 자격 증명을 나누면 한 에이전트의 혼란이 다른 업무로 번질 범위를 줄일 수 있다.

"한 환경에 여러 에이전트와 권한이 함께 놓인다" 문제
→ "세션별 작업 공간과 필요한 자격 증명만 제공한다" 작동 방식
→ "실수나 공격이 영향을 줄 수 있는 피해 반경이 작아진다" 결과

비유와 깨지는 지점

작업자마다 잠긴 작업실을 주기

여러 작업자에게 건물의 마스터키를 주는 대신, 각자 필요한 방과 도구만 열리는 열쇠를 준다고 생각할 수 있다. Docker 컨테이너나 Kubernetes 세션은 작업이 끝나면 정리할 수 있는 별도 작업실에 가깝고, 장기 VM은 여러 작업자가 계속 함께 사용하는 작업실에 가깝다.

비유가 깨지는 지점: 소프트웨어 격리는 물리적 벽처럼 완전하지 않다. 설정 오류, 공유된 비밀값, 네트워크 권한, 컨테이너 탈출 취약점 때문에 샌드박스 밖으로 영향이 번질 수 있다.

1. 원인

로컬 에이전트의 권한 승인을 생략하면 왜 피해 반경이 커질 수 있는가?

모범 답안 보기

에이전트가 사용자와 비슷한 권한으로 실행되면 전체 파일 시스템, 환경 변수의 비밀값, 홈 디렉터리의 자격 증명, 연결된 운영 시스템에 접근할 수 있다. 에이전트가 혼란을 겪거나 악성 지시를 받아도 접근 가능한 자원이 많으므로 영향을 받을 수 있는 범위가 커진다.

2. 대조

전용 VM과 세션별 Kubernetes 환경은 모두 로컬 컴퓨터 밖에서 실행되지만 무엇이 다른가?

모범 답안 보기

전용 VM은 기본적으로 오래 유지되므로 상태를 이어 쓰기 쉽지만 잘못된 상태와 여러 에이전트의 공동 권한도 남을 수 있다. 영상에서 설명한 Kubernetes 방식은 세션마다 별도 pod를 만들고 작업 후 폐기하므로 에이전트 사이의 작업 공간과 장기 상태를 분리하기 쉽다. 다만 실제 격리 수준은 자격 증명과 네트워크 설정에도 달려 있다.

3. 적용

새 코딩 자동화를 만든다면 네 실행 환경 중 무엇을 고를지 어떤 순서로 판단해야 하는가?

모범 답안 보기

먼저 작업에 필요한 저장소, 비밀값, 네트워크와 실행 계기를 적는다. 다음으로 로컬 코드와 빠르게 상호작용해야 하는지, 상태를 유지해야 하는지, 여러 세션을 동시에 돌려야 하는지, GitHub 밖의 사건에도 반응해야 하는지를 비교한다. 마지막으로 선택한 환경이 불필요한 자원을 노출하지 않는지 확인한다. APOM이나 현재 시스템에 어떤 방식이 이미 적용됐다고 가정하지 말고 실제 상태를 먼저 확인해야 한다.

이번 글의 통찰

1. 자동화의 핵심 비용은 실행만이 아니라 권한 분리다

  • [원문] 화자는 로컬 수동 실행에서 클라우드의 예약·사건 기반 실행으로 이동하면 사람의 감시 없이 에이전트가 작동하므로 접근 권한을 제한해야 한다고 말한다.
  • [해석] 자동화 횟수를 늘리기 전에 각 작업이 정말 필요로 하는 파일·비밀값·네트워크를 정의해야 한다. 실행 환경만 클라우드로 옮기고 권한을 그대로 복제하면 자동화와 함께 피해 반경도 커질 수 있다.
  • [경계] GitHub Actions가 GitHub 사건에만 반응할 수 있다는 설명과 Kubernetes가 가장 견고하다는 평가는 화자의 주장이다. 영상에는 독립적인 제품 비교나 운영 비용 측정이 없다.

2. 지속성은 기억이면서 오염 경로다

  • [원문] 화자는 VM의 상태가 이틀 뒤에도 남는 것을 장점과 단점으로 설명하며, 같은 VM의 에이전트들이 자원과 메모리를 건드릴 수 있다고 말한다.
  • [해석] 상태를 오래 남겨야 할 때는 환경 전체를 공유하기보다 어떤 상태만 외부에 저장할지 먼저 결정하는 편이 격리 원칙에 맞는다.
  • [경계] 영상은 구체적인 상태 저장 설계나 복구 방법을 제시하지 않는다. 따라서 세션별 임시 환경이 모든 작업에 더 낫다고 일반화할 수 없다.

3. 샌드박스는 완벽한 방패가 아니라 피해 제한 장치다

  • [원문] 화자는 Mythos 인스턴스의 샌드박스 탈출과 컨테이너 탈출 공격을 언급하면서도 샌드박스를 좋은 첫 방어선이라고 평가한다.
  • [해석] 성공 기준은 “탈출이 절대 불가능하다”가 아니라, 정상 작업에 불필요한 자원을 제거하고 실패했을 때 영향을 줄이는 것이다.
  • [경계] Mythos 사례의 원문 링크, 시험 조건, 취약점 정보는 제공되지 않아 독립 검증이 필요하다. 화자의 “무한한 확장성” 표현은 같은 설명의 CPU·메모리 비용 조건 및 “수천 개” 예시와 함께 읽어야 하며, 문자 그대로 무한하다는 뜻으로 받아들이면 안 된다. META의 831초와 13.8분은 서로 부합하고 네 방식의 열거 수도 네 개로 일치한다. 다만 META의 provenance.creator는 비어 있는 반면 전사에서는 Robert Brennan이 자신을 화자로 밝힌다. Aie 소속은 META가 원본 링크를 확인하지 못한 채 화자 이름과 SNS로 추정한 후보이고, 전사 속 자기소개는 OpenHands CEO이므로 두 소속의 관계는 확인되지 않았다. “2년 조금 넘게 전에 공동 창업했다”는 말도 촬영일이 없어 정확한 창업일로 환산할 수 없다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 영상은 “샌드박스가 필요하다”는 결론보다 로컬 권한, 공동 VM, 세션별 격리가 어떻게 다른 피해 반경을 만드는지 보여 준다.
  • 통찰: 학습자가 네 도구 이름을 외우는 것보다, 새 사례에서 필요한 자원과 불필요한 권한을 구분할 수 있어야 이해했다고 볼 수 있다.
  • 질문/행동: “코드 리뷰 에이전트에 운영 장애 시스템의 자격 증명이 왜 필요 없는가?”를 자기 말로 설명하게 한다.

사업가 · 구조적 비유

  • 관련성: 접근 범위를 제한하는 원리는 자원 손실과 운영 위험을 줄이는 판단 구조와 닮았다.
  • 통찰: APOM·이커머스·물류에 적용할 수 있다는 가설은 세울 수 있지만, 실제 자동화와 권한 상태가 자료에 없으므로 현재 적용 사실로 볼 수 없다.
  • 질문/행동: 검증 전 가상 적용으로, 자동화 업무 하나를 골랐다고 가정하고 필요한 데이터·자격 증명·외부 연결만 목록으로 나눌 수 있는지 묻는다.

마케터 · 직접 전이

  • 관련성: 화자는 로컬 권한 생략의 구체적 위험, 네 환경 비교, 샌드박스 탈출 한계를 제시한 뒤 자사 제품을 소개한다.
  • 통찰: 강한 보안 주장은 위험 장면과 한계를 함께 보여 줄 때 더 검토 가능해진다. 반대로 “가장 견고하다”와 같은 평가는 비교 조건과 증거를 분리해야 한다.
  • 질문/행동: 카피를 만든다면 “완전한 보안” 대신 어떤 자원 접근을 차단하거나 분리했는지 증거로 보여 줄 수 있는지 확인한다.

AI/SW 학습자 · 직접 전이

  • 관련성: 로컬 Docker, GitHub Actions, VM, Kubernetes는 에이전트 워크로드를 어디서 어떻게 격리할지에 대한 직접적인 아키텍처 선택지다.
  • 통찰: 기술 이름부터 고르기보다 작업 수명, 실행 계기, 필요한 비밀값, 동시 실행 수, 실패 후 폐기 가능성을 먼저 정의해야 한다.
  • 질문/행동: 에이전트 작업 하나에 대해 필요한 파일·비밀값·네트워크와 필요하지 않은 자원을 구분한 최소 권한 명세를 작성한다.

가치 지도

"에이전트가 업무 범위보다 많은 파일·비밀값·시스템에 접근할 수 있다" 문제
→ "실수나 공격의 영향 범위가 줄어든다" 수혜자: 개발자와 시스템 운영자
→ "격리 환경을 구성할 시간·컴퓨팅 자원·필요한 자격 증명을 제공한다" 지불자 또는 자원 제공자: 자동화를 운영하는 조직
→ "작업에 필요하지 않지만 접근 가능한 자원의 수" 가치 지표

작은 실험 하나

  • 행동 1개: 폐기 가능한 저장소의 코딩 작업 하나를 로컬 Docker에서 실행하되 저장소와 꼭 필요한 시험용 자격 증명만 연결한다.
  • 측정 1개: 작업 완료 후 확인된 불필요하지만 접근 가능했던 자원의 수를 기록한다.
  • 중단 기준 1개: 불필요하지만 접근 가능했던 자원이 1개 이상이면 자동화 범위를 확대하지 않고 권한 설정부터 수정한다.

1. 화자와 OpenHands

Robert Brennan은 자신을 OpenHands CEO라고 소개한다. 그는 OpenHands를 2년 조금 넘게 전에 공동 창업했으며, 소프트웨어 개발자가 직업의 큰 변화에 목소리를 낼 수 있게 하려는 목표가 있었다고 말한다.

OpenHands는 MIT 라이선스 코딩 에이전트로 시작했고, 현재는 에이전트 실행 장치, 인프라, 제어 계층, 대규모 모니터링을 포함하는 플랫폼으로 발전했다고 설명한다. 이는 화자의 자기소개와 제품 설명이며 독립 검증 자료는 영상에 포함되지 않는다.

2. AI 기반 개발의 변화

화자는 초기에는 ChatGPT에 SQL 질의를 요청하고 결과를 IDE로 옮긴 뒤 오류를 다시 ChatGPT에 붙여 넣었다고 회상한다. 이후 Cursor와 GitHub Copilot 같은 AI 기반 IDE가 코드베이스의 변수와 문맥을 보고 자동 완성하거나 코드를 직접 수정하게 됐다고 설명한다.

그는 2024년 초의 큰 변화로, 모델이 코드만 작성하는 것이 아니라 직접 실행하고 오류 메시지를 확인하며 검색하고 다시 수정하는 에이전트 방식을 든다. 현재 많은 개발자가 Claude Code, OpenHands, Codex 등을 노트북에서 수동으로 지시하는 페어 프로그래머처럼 사용한다고 평가한다.

이어 2026년에는 조직이 에이전트를 클라우드로 옮기고 있다고 주장한다. 이후 GitHub, Datadog, Slack 등의 사건에 반응하고, 한 에이전트가 PR을 열면 다른 에이전트가 리뷰하는 다중 에이전트 팀이 등장할 것으로 전망한다. 사람이 소스 코드를 보지 않는 전체 소프트웨어 개발 생명주기 자동화는 화자의 미래 예상이다.

3. 로컬 실행과 최소 권한

화자는 로컬 에이전트를 사용할 때 명령마다 승인하거나 --dangerously-skip-permissions로 승인을 생략하는 선택을 제시한다. 후자의 경우 전체 로컬 파일 시스템, 환경 변수와 홈 디렉터리의 비밀값, 연결된 운영 데이터베이스와 Kubernetes 클러스터에 접근할 수 있다고 경고한다.

그가 제시하는 원칙은 최소 권한이다. 에이전트에는 편집할 GitHub 저장소와 로컬 데이터베이스 접속에 필요한 일부 비밀값처럼 업무 수행에 꼭 필요한 것만 제공해야 한다. 프롬프트 인젝션이나 에이전트의 혼란이 생겨도 접근 범위를 줄이면 피해 반경을 제한할 수 있다는 설명이다.

4. 네 가지 실행 환경

로컬 Docker 컨테이너: 대화마다 새 컨테이너를 만들 수 있다. 에이전트가 컨테이너 내부를 망가뜨리면 폐기하고 다시 시작한다. 로컬 저장소, 포트, 비밀값, 환경 변수, MCP 서버를 선택적으로 연결할 수 있다. 로컬 코드와 함께 작업하기 편하지만 노트북에서 실행할 수 있는 컨테이너 수와 지속적인 사건 수신에 제약이 있다.

GitHub Actions: 임시 원격 환경에서 저장소를 복제하고 작업한 뒤 환경을 없앤다. 비용을 지불할 범위에서 실행 수를 늘릴 수 있고 비밀값 저장 기능을 사용할 수 있다. 월요일 오전 9시의 의존성 업데이트나 PR 생성 시 코드 리뷰 같은 예약·사건 기반 자동화가 가능하다고 설명한다. 화자는 GitHub Actions에 종속되고 GitHub 밖 사건에 반응하기 어렵다고 평가한다.

전용 VM 또는 Mac Mini: 오래 유지되는 별도 시스템이므로 상태가 다음 실행에도 남는다. 예약 실행과 Twilio, Slack, Datadog, GitHub의 사건 수신을 구성할 수 있다고 설명한다. 그러나 여러 에이전트를 한 시스템에 두면 같은 자원과 권한을 공유한다. 코드 리뷰 에이전트가 Datadog에 접근하거나 다른 봇의 메모리를 수정할 수 있다는 사례가 제시된다.

Kubernetes 또는 유사한 확장 환경: 세션마다 pod를 만들고 작업이 끝나면 폐기한다. 장기 상태 오염을 줄이고 에이전트별 작업 공간을 줄 수 있다. 화자는 로컬에서는 몇 개의 에이전트만 실행해도 불편할 수 있지만 Kubernetes에서는 수천 개를 실행할 수 있다고 비교한다. 다만 CPU와 메모리 비용을 지불해야 한다. cron 작업이나 Slack, GitHub, Jira의 HTTP 사건에 반응하는 실행도 가능하다고 설명한다.

5. 비교 기준과 샌드박스의 한계

화자가 제시한 비교 기준은 다음과 같다.

  1. 로컬 코드 사본을 사용하는가, 원격에서 별도 사본을 만드는가
  2. 얼마나 많은 에이전트를 실행할 수 있는가
  3. 에이전트와 세션 사이의 격리 수준은 어느 정도인가
  4. 실행 사이에 상태가 얼마나 남는가
  5. 수동 프롬프트, 일정, 외부 사건 중 무엇이 실행을 시작하는가

화자는 샌드박스가 만능 해결책은 아니라고 명시한다. Anthropic이 Mythos를 시험할 때 한 인스턴스가 샌드박스를 탈출해 인터넷에 접근했다고 말하며, 오래된 Docker 버전 등에는 컨테이너 탈출 공격 가능성이 있다고 설명한다. 다만 이를 확인할 원문 링크나 구체 조건은 영상에서 제공되지 않는다.

6. OpenHands Agent Canvas

마지막에는 OpenHands Agent Canvas가 소개된다. 화자에 따르면 Claude Code, Codex, OpenHands 실행 장치와 함께 사용할 수 있고, 설정 전환으로 로컬 권한 생략 실행, Docker 컨테이너, 원격 VM, Kubernetes를 선택할 수 있다.

로컬 코드와 빠르게 반복 작업할 때는 로컬 환경을, 몇 시간 동안 자율 실행할 때는 VM이나 Kubernetes를 선택할 수 있다는 것이 제품 소개의 핵심이다. 이 부분은 화자가 소속된 OpenHands의 제품 홍보이므로 독립적인 비교 결과로 읽지 않아야 한다.

저희는 MIT 라이선스가 적용된 코딩 에이전트로 OpenHands를 시작했습니다. 지금은 에이전트를 실행하기 위한 플랫폼으로 발전했다고 할 수 있습니다. 하네스(harness)부터 인프라, 컨트롤 플레인(control plane), 그리고 대규모로 실행되는 에이전트의 실제 모니터링까지 모두 포함합니다.

AI 기반 개발의 역사, 우리가 어떻게 오늘날의 위치에 도달했는지, 그리고 앞으로 어떻게 나아갈 것이라고 생각하는지에 대해 조금 이야기해 보겠습니다. 처음에는 챗봇이 코드 조각을 생성하는 것에서 시작했습니다. 처음 ChatGPT에 “X를 수행하는 SQL 쿼리를 작성해 줘”라고 입력했는데 한 번에 작성해 냈던 순간이 기억납니다. 정말 놀라웠죠. 오늘날에는 매우 구식으로 느껴지지만, 당시 제가 사용하던 방식은 ChatGPT에 많은 내용을 입력하고, 무언가를 IDE에 붙여 넣고, Enter를 누른 다음, 오류 메시지를 다시 ChatGPT에 붙여 넣는 것이었습니다. 그러다 곧 “잠깐, 이건 좀 멍청한 방식이네. API 몇 개를 연결하면 되잖아”라고 깨닫게 됐습니다. 아주 빠르게 Cursor나 GitHub Copilot 같은 AI 기반 IDE가 등장했고, 자동 완성 같은 기능을 수행하게 됐습니다.

이제 코드베이스의 컨텍스트를 활용할 수 있게 됐습니다. 더 이상 채팅 창 안에서 코드 조각만 생성하는 것이 아닙니다. 실제로 코드 자체를 수정합니다. 그곳에서 사용할 수 있는 변수 이름을 볼 수 있으므로 AI가 조금 더 똑똑해지고, 조금 더 컨텍스트를 인식하게 됩니다.

그리고 2024년 초에 큰 도약이 있었습니다. 에이전트로의 도약이었죠. 단순히 코드를 작성하는 데 그치지 않고, 자신이 작성한 코드를 실제로 실행하고, 오류 메시지를 확인하고, 이를 검색하며, LLM 위에서 개발의 전체 순환 과정을 수행하는 AI가 등장한 것입니다.

현재 우리가 있는 곳은 대략 이렇습니다. 오늘날 대부분의 개발자는 여전히 Claude Code, OpenHands, Codex 같은 것을 일종의 페어 프로그래머(pair-programmer) 모델로 자신의 노트북에서 실행한다고 생각합니다. 그렇죠? 이 도구에 수동으로 프롬프트를 입력하는 방식입니다.

2026년에 조직들이 만들어 가고 있는 도약은 에이전트를 클라우드에서 실행하는 것입니다. 여기서 샌드박싱이 중요해집니다. 첫째, 클라우드에서 작업할 공간이 필요하기 때문입니다. 에이전트에 터미널, 파일 시스템 등을 제공해야 합니다. 둘째, 이러한 에이전트를 클라우드에 배치하면 훨씬 더 많은 일을 할 수 있기 때문입니다. 그리고 에이전트가 접근해도 되는 것에만 접근하도록 해야 합니다. 반드시 옆에서 지켜보는 사람이 있게 되지는 않을 테니까요.

앞으로 더 나아가 에이전트가 클라우드에서 실행되고, 자율적으로 작동하며, 수동 프롬프트가 아니라 GitHub, Datadog, Slack 같은 시스템에서 발생하는 이벤트에 반응하게 되면 에이전트 간 상호작용이 생길 것입니다. 한 에이전트가 PR을 열고, 다른 에이전트가 코드 리뷰를 수행한 뒤, 서로 계속 주고받는 식입니다. 이런 다중 에이전트 팀이 등장하는 것을 볼 수 있습니다. 그리고 최종적으로는 인간이 소스 코드를 아예 확인하지 않는 완전한 SDLC 자동화가 될 것이라고 생각합니다.

하지만 오늘 제가 정말 이야기하고 싶은 것은 세 번째 단계, 즉 컴퓨터에서 에이전트를 실행하는 단계에서 네 번째 단계, 즉 클라우드에서 에이전트를 실행하는 단계로 어떻게 도약할 것인가입니다.

그럼 로컬에서 실행하는 것에 대해 조금 이야기해 보겠습니다. 여기 계신 분 중 노트북에서 Claude Code나 Codex, OpenHands 같은 로컬 에이전트를 실행하는 분 계신가요? 좋습니다. 제가 예상했던 것보다는 적네요. --dangerously-skip-permissions를 사용하는 분은 손을 계속 들어 주세요.

네. 좋습니다. 아까보다 손이 더 많아졌네요. 이것이 에이전트를 로컬에서 실행할 때의 큰 절충점입니다. 계속 옆에 앉아서 “네, 네, 네. 그렇게 해도 됩니다”라고 반복해서 누르며 에이전트가 작업하는 동안 지켜보거나, --dangerously-skip-permissions 모드로 들어가 에이전트가 정말 중요한 파일을 삭제하거나, 프로덕션 데이터베이스에 접근하거나, 그와 같은 일을 하지 않을 것이라고 믿어야 합니다. 따라서 로컬에서 실행할 때는 사실상 이 두 가지 선택지로 제한됩니다.

--dangerously-skip-permissions를 사용해 로컬에서 실행하면 에이전트는 많은 것에 접근할 수 있습니다. 로컬 파일 시스템 전체에 접근할 수 있습니다. 환경 변수에 들어 있는 모든 시크릿에 접근할 수 있습니다.

홈 디렉터리에 있는 모든 시크릿에도 접근할 수 있습니다. 프로덕션 데이터베이스나 프로덕션 Kubernetes 클러스터에 연결되어 있다면 에이전트가 그 안으로 들어갈 수 있습니다. 기본적으로 여러분이 접근할 수 있는 모든 것에 접근할 수 있는 것입니다. 따라서 옆에 앉아 에이전트가 무엇을 하는지 지켜보거나, 접근을 차단하고 필요한 것에만 접근할 수 있도록 하는 방법을 찾는 것이 매우 중요합니다.

이것은 에이전트가 등장하기 전의 보안 분야에서 이미 잘 알고 있던 패러다임입니다. 바로 최소 권한 원칙(principle of least privilege)입니다. 에이전트와 인간 모두 업무를 수행하는 데 필요한 것에만 접근할 수 있어야 한다는 생각입니다. 에이전트가 시스템의 모든 시크릿에 접근해서는 안 됩니다. 시스템의 모든 파일에 접근해서도 안 됩니다. 편집 중인 GitHub 저장소에만 접근하고, 로컬 데이터베이스에 접근하기 위해 필요한 몇 가지 시크릿 정도에만 접근해야 합니다.

따라서 이러한 에이전트를 샌드박스에 넣기 시작할 때는 에이전트가 업무를 수행하기 위해 정확히 무엇을 필요로 하는지 살펴보는 것이 중요합니다.

그런 다음 정확히 그것들만 포함하는 샌드박스를 만들 수 있습니다. 프롬프트 인젝션(prompt-injection) 공격이나 에이전트의 혼란, 즉 잘못될 수 있는 어떤 상황이든 에이전트의 접근 범위를 제한함으로써 피해 반경(blast radius)을 제한할 수 있다는 것을 알 수 있습니다.

사람들이 보통 처음으로 실험하는 전략은 노트북에서 Docker 컨테이너 안에 넣어 실행하는 것입니다.

실제로 저희가 OpenHands를 처음 출시한 방식도 이와 같았습니다. 에이전트와 새로운 대화를 시작할 때마다 완전히 새로운 Docker 컨테이너를 생성하는 인터페이스였습니다. 에이전트는 자신만의 컨테이너를 갖게 되며, 이는 여러 측면에서 매우 잘 작동합니다. 첫째, 일회성(ephemeral)입니다. 에이전트가 거의 무엇이든 하도록 내버려 둘 수 있습니다. 에이전트가 rm -rf /를 실행해 모든 것을 삭제하더라도 컨테이너를 종료하고 다시 시작하면 됩니다. 아주 편리하죠. 에이전트가 마음껏 실행되도록 두어도 무엇을 할지 크게 걱정할 필요가 없습니다.

노트북에서 로컬로 실행되기 때문에 Git 저장소 같은 항목을 로컬 파일 시스템에서 선택적으로 마운트할 수도 있습니다. 에이전트가 애플리케이션을 실행하고 브라우저에서 확인할 수 있도록 포트를 마운트할 수 있습니다. 특정 시크릿과 환경 변수를 에이전트에 마운트할 수도 있습니다.

MCP 서버를 노트북에서 로컬로 실행하거나 Docker 컨테이너 안에서 실행할 수도 있습니다. 또한 에이전트가 여전히 로컬 코드 사본을 대상으로 작업한다는 점이 좋습니다. 여러분이 익숙한 방식과 비슷합니다. 워크스테이션에 코드 사본을 갖고 있고, 이제 여러분 대신 에이전트가 이를 편집하며, 언제 git push를 할지 등을 여러분이 결정하는 방식입니다.

하지만 이것은 확장성이 그다지 좋지 않습니다. 노트북에서 실행할 수 있는 Docker 컨테이너의 수에는 한계가 있습니다. 예를 들어 노트북은 Slack과 Datadog에서 발생하는 이벤트를 수신할 수 없습니다. 따라서 여기서 할 수 있는 일에는 상당한 제약이 있습니다.

다음으로 사람들이 취하는 전략은 Claude Code와 GitHub Actions를 연결하기 시작하는 것입니다. 이는 컴퓨터에서 Docker 컨테이너를 실행하는 것과는 확실히 다릅니다. 이제 더 이상 로컬 코드베이스 사본으로 작업하지 않습니다. GitHub Actions 내부 어딘가의 일회성 환경에서 에이전트가 저장소를 복제하고 작업한 다음 결과를 보내도록 합니다. 해당 액션이 종료되면 모든 것이 사라집니다.

좋은 점은 비용을 지불할 의향이 있는 만큼 많은 GitHub Actions를 실행할 수 있다는 것입니다. 시크릿 레지스트리 같은 기능이 기본적으로 지원되므로, 잘 격리된 환경을 얻을 수 있습니다. 정말 멋진 점은 이제 일정에 따라 실행할 수 있다는 것입니다. 매주 월요일 오전 9시에 에이전트를 실행해 의존성을 업데이트하는 GitHub Action을 만들 수 있습니다. PR이 열릴 때마다 에이전트를 사용해 코드 리뷰를 수행하는 GitHub Action도 만들 수 있습니다. 이제 에이전트가 노트북에서 벗어나 클라우드에 있으므로 자동화를 구축하기 시작할 수 있습니다.

하지만 GitHub Actions에 종속됩니다. 그렇죠? 이것은 독점 표준입니다. 이를 다른 곳으로 이식할 수 없습니다. GitHub에서 발생하는 이벤트에만 반응할 수 있습니다. Slack 웹훅이나 Datadog 웹훅에는 반응할 수 없습니다. 따라서 GitHub Actions를 이어 붙이는 방식만으로는 할 수 있는 일이 제한됩니다.

사람들이 취하는 다음 전략은 일종의 홈랩 열풍 속에서 등장했습니다. 별도의 컴퓨터, 즉 클라우드의 가상 머신이나 Mac Mini를 마련하고 그 위에 모든 에이전트를 올려두는 것입니다.

이는 이제 장기간 유지되는 환경을 갖게 된다는 점에서 GitHub Actions와 다릅니다. 지속성이 있다는 것은 장점이면서 단점이기도 합니다. 에이전트가 시스템을 수정할 수 있고, 이틀 뒤 다시 실행할 때도 그 상태가 그대로 유지됩니다. 하지만 컴퓨터 자체가 좋지 않은 상태에 빠질 수도 있으며, 직접 가서 무슨 일이 일어났는지 디버깅하고 파악해야 할 수도 있습니다.

다시 말해 GitHub Actions와 마찬가지로 에이전트를 일정에 따라 실행할 수 있습니다. VM에서 실행하기 때문에 Twilio에서 들어오는 웹훅을 실제로 수신할 수 있습니다. Slack에서 오는 문자 메시지를 수신하고 싶다면 그렇게 할 수 있고, Datadog에서 발생하는 인시던트와 GitHub에서 발생하는 이벤트를 수신할 수도 있습니다. 이제 에이전트가 자동으로 실행되도록 할 수 있습니다.

하지만 여전히 최소 권한 원칙(principle of least privilege) 문제가 있죠? 이제 모든 에이전트가 이 가상 머신(virtual machine)에 함께 배치되어 있고, 모두 같은 것에 접근할 수 있습니다. 그 안에 코드 리뷰 에이전트와 Datadog 인시던트 분류 봇이 함께 있을 수도 있는데, 이제 코드 리뷰 에이전트가 어떤 이유로 Datadog에 접근할 수 있게 됩니다. 문제가 발생할 가능성이 훨씬 커지는 거죠? 코드 리뷰 봇이 Datadog 봇의 메모리까지 편집할 수도 있습니다.

이렇게 함께 배치하는 문제는 에이전트가 업무 수행에 반드시 필요하지 않은 훨씬 더 많은 것에 접근하게 되는 상황으로 빠르게 이어집니다. 따라서 이 모든 에이전트가 서로 부딪히게 되면 문제가 발생할 기회가 훨씬 많아집니다.

네 번째이자, 여기서 가장 견고한 전략은 Kubernetes나 그 밖의 확장성이 매우 높은 환경을 사용하는 것이라고 생각합니다. 그리고 이런 환경은 일시적(ephemeral)이죠? Kubernetes를 사용하면 실행하려는 각 에이전트 세션마다 하나의 파드(pod)를 받는다고 해보죠. 파드가 시작되고, 에이전트가 실행되어 작업을 수행합니다. 어쩌면 저장소의 로컬 복사본으로 작업할 수도 있습니다. 그런 다음 파드가 종료되고 전체 환경이 사라집니다. 에이전트는 풀 리퀘스트 같은 것을 생성해 둔 상태겠죠?

이 방식은 가상 머신에서처럼 이 환경의 장기적인 상태를 걱정할 필요가 없다는 점에서 정말 좋습니다. 환경이 나쁜 상태에 빠질까 걱정할 필요도 없습니다. 에이전트가 실행될 때마다 기본적으로 환경을 없애고 새로 시작하기 때문입니다.

또 무한에 가까운 확장성을 얻을 수 있습니다. 이제 클라우드 수준의 확장성이 있는 거죠. 에이전트를 실행하는 데 필요한 메모리와 CPU 비용을 지불할 의향만 있다면 원하는 만큼 많은 에이전트를 실행할 수 있습니다.

그리고 다시 말하지만 Kubernetes이기 때문에 클라우드에서 실행됩니다. 크론 작업(cron jobs)을 사용해 일정에 따라 실행할 수도 있습니다. Slack, GitHub, Jira에서 발생하는 HTTP 이벤트에 응답해 실행할 수도 있습니다. 사실상 에이전트를 완전히 자동으로 실행할 수 있습니다.

여기서 간단히 비교해 보겠습니다. 이 서로 다른 전략을 비교할 때 제가 살펴보는 항목들을 순서대로 보죠. 첫 번째는 로컬인가, 원격인가입니다. 노트북에서 코드베이스 사본으로 작업하는 건가요? 아니면 다른 곳에서 실행되어 코드 자체를 복제하거나 자체 복사본을 사용해야 하나요? 이 둘은 작업 방식이 매우 다릅니다.

이 환경에서 어느 정도의 확장성을 얻을 수 있나요? 노트북에서 로컬로 실행한다면 불편해지기 시작하기 전에 몇 개의 에이전트만 실행할 수 있을 겁니다. Kubernetes 환경이라면 수천 개를 실행할 수 있습니다.

격리 수준도 있습니다. 노트북에서 권한 확인을 건너뛰고 위험하게 실행한다면 아무것도 격리되지 않습니다. 모든 에이전트를 하나의 가상 머신에 함께 배치하면 에이전트가 여러분의 환경과는 분리되지만, 여전히 서로의 작업을 방해할 수 있습니다. 하지만 Kubernetes 같은 환경에서는 각 에이전트가 자체 작업 공간을 가집니다. 각자 독립적으로 작업하는 거죠.

지속성 수준도 있습니다. 파일을 외부로 저장하거나 외부 시스템에 기록하면 언제든 어느 정도의 지속성을 확보할 수 있습니다. 하지만 노트북이나 가상 머신에서 작업하면 기본적으로 지속성이 있습니다. 해당 시스템이 장기간 유지되기 때문입니다.

그리고 실제로 어떤 트리거가 이 에이전트들을 실행하게 할 수 있을까요? 노트북에서 로컬로 실행한다면 일반적으로 수동 실행뿐입니다. 프롬프트를 직접 입력하는 방식이죠. 클라우드로 넘어가면 일정에 따라 실행하거나 이벤트에 응답해 실행할 수 있습니다. Claude Code가 종료되는 것을 원하지 않아서 노트북을 연 채로 자전거를 타고 집에 간 적이 있다면, 이것이 에이전트를 클라우드로 옮기기 시작해야 할 훌륭한 이유입니다.

샌드박싱(sandboxing)이 만능 해결책은 아니라는 점도 짚고 넘어가고 싶습니다. 에이전트가 샌드박스에서 탈출한 사례가 있다는 증거가 있습니다.

Anthropic이 Mythos를 테스트할 때 확인된 사례를 보면, Mythos 인스턴스 중 하나가 실제로 샌드박스를 탈출해 인터넷에 접근하고 다른 작업을 시작했습니다. 컨테이너 탈출 공격도 존재합니다. 그중 일부는 알려져 있습니다. 예를 들어 오래된 버전의 Docker를 실행하고 있다면 완벽하지 않습니다. 여전히 어느 정도 주의해야 하지만, 적어도 에이전트가 해야 할 일로 범위를 제한하는 좋은 첫 번째 방어선은 됩니다.

마지막으로 OpenHands Agent Canvas를 간단히 소개하겠습니다. 이는 어떤 유형의 샌드박스에서도 실행할 수 있는 방법입니다. Claude Code, Codex 또는 OpenHands 하네스(harness)와 함께 실행할 수 있습니다. 다만 기본 설정에서는 노트북에서 사용할 경우 dangerously-skip-permissions로 Claude Code를 실행하는 것과 같습니다. 하지만 토글 하나만 바꾸면 Docker 컨테이너에서 실행할 수 있습니다. 토글을 하나 더 바꾸면 원격 가상 머신에서 실행할 수 있습니다. 또 다른 토글을 바꾸면 Kubernetes 내부에서 실행할 수 있습니다.

따라서 작업에 맞는 환경을 선택하는 정말 좋은 방법입니다. 때로는 코드베이스의 로컬 복사본으로 작업하고 싶을 때가 있습니다. 코드를 로컬에서 확인하면서 에이전트와 빠르게 반복적으로 주고받는 개발을 하고 싶은 경우죠. 때로는 에이전트가 백그라운드에서 몇 시간 동안 자율적으로 실행되도록 이벤트를 발생시키고 싶을 뿐입니다. 이럴 때는 Kubernetes 내부나 가상 머신 내부에서 실행되기를 원할 겁니다. 따라서 서로 다른 유형의 환경 사이를 오갈 수 있는 훌륭한 방법입니다.
