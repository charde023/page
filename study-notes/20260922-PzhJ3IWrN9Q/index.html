큰 그림: 모델만으로는 에이전트가 되지 않는다

이 영상은 AI 에이전트의 성능이 언어 모델의 지능만으로 정해지지 않는다고 주장한다. 언어 모델은 받은 글을 읽고 다음에 할 일을 말할 수 있지만, 혼자서는 파일을 열거나 날씨를 조회하거나 명령을 실행하지 못한다. 모델의 의도를 실제 행동으로 연결하고, 필요한 정보를 다시 모델에 넣어 주며, 결과가 기준을 통과했는지 확인하는 주변 구조가 필요하다. 영상은 이 전체를 에이전트 하네스(agent harness)라고 부른다.

예를 들어 “비옷을 입어야 할까?”라는 질문에는 현재 날씨가 필요하다. 모델이 날씨를 알아봐야 한다고 판단하면, 하네스가 조회 도구를 실행해 “맑다”는 정보를 얻고 원래 질문과 함께 모델에 다시 전달한다. 모델은 그제야 답을 만들 수 있다. 즉, 모델이 판단을 담당한다면 하네스는 정보를 가져오고, 행동을 실행하고, 결과를 다시 연결하는 운영 구조다.

읽는 법: 가운데의 왕복 화살표가 핵심이다. 하네스는 모델을 한 번 호출하는 포장지가 아니라, 외부 정보와 실행 결과를 모델에 계속 되돌려 주는 구조다. 이 그림은 성능 수치를 나타내는 그래프가 아니라 영상의 개념을 정리한 지도다.

좋은 프롬프트보다 재사용되는 환경을 만든다

Ryan Lopopolo는 모델이 좋아져도 사용자가 원하는 결과를 저절로 이해하지는 않는다고 말한다. 그래서 매번 긴 지시를 프롬프트 앞에 붙이는 대신, 문서·도구·코딩 규칙·정적 검사·테스트처럼 반복해서 사용할 수 있는 환경에 기준을 넣어야 한다고 주장한다. 그는 필요한 도구와 맥락이 준비되어 있다면 짧게 요청해도 되는 “게으른 프롬프터”가 되고 싶다고 표현한다.

영상에서 말하는 시프트 레프트(shift left)는 실패한 뒤 사람이 프롬프트를 다시 쓰는 개입을 더 이르고 자동화된 단계로 옮기는 것이다. 같은 프롬프트를 다시 시도하는 것은 개인의 순간적인 대응에 그친다. 반면 문서와 AGENTS.md에 기준을 적고, 검증기와 테스트가 위반을 잡게 만들면 팀과 다음 작업에도 남는다. 더 나아가 에이전트가 필요한 문서를 스스로 찾을 수 있게 하면 모든 맥락을 사람이 프롬프트에 미리 넣지 않아도 된다.

읽는 법: 왼쪽은 실패할 때마다 사람이 다시 개입하는 방식이고, 오른쪽으로 갈수록 기준이 환경과 도구에 남는다. 모든 작업이 반드시 다섯 단계를 거친다는 뜻은 아니다.

Ryan이 든 구체적인 사례는 문서 링크의 위치다. 그는 링크 때문에 본문 맥락이 흐트러지지 않도록 이름이 붙은 링크 기준점을 관련 문단이나 목록 가까이에 두고, 그 위치 관계를 테스트한다고 말한다. 이는 사람에게 읽기 쉬운 문서와 에이전트가 효율적으로 읽을 수 있는 맥락을 동시에 만들려는 개인적 설계 사례다.

긴 자율성은 작은 검증 단위를 이어 붙여 얻는다

에이전트에게 더 긴 작업을 맡길 때의 문제는 한 번의 응답 품질만이 아니다. 여러 변경이 이어지는 동안 처음의 목적과 품질 기준을 계속 지키는지가 중요하다. Ryan은 조직이 중요하게 여기는 기준을 “황금 실”처럼 계속 다시 맞춰야 한다고 설명한다.

그가 제시한 방법은 검토하기 쉬운 작은 변경부터 시작하는 것이다. 작은 변경의 상태 범위를 좁히고, 테스트와 검토로 합격 여부를 확인한다. 이 작은 단위를 안정적으로 이어 붙일 수 있을 때만 더 큰 작업 루프로 확대한다. 그는 충분한 가드레일이 있다면 장기적으로는 언어 전체를 바꾸는 마이그레이션 같은 큰 작업도 다룰 수 있다고 주장하지만, 영상은 이를 일반적으로 검증한 결과로 제시하지는 않는다.

읽는 법: 실패는 단순히 다시 실행하라는 신호가 아니다. 오류 내용을 다음 반복의 정보로 돌려주고, 같은 실패가 반복되면 문서·도구·검증 규칙을 바꾸는 입력으로 삼는다.

작업에 따라 반복 방식과 안전장치를 고른다

Billy의 시연은 하네스를 세 형태로 나눈다. 첫째, 선형 하네스는 파일을 한 번 읽고 권고를 출력한 뒤 끝난다. 흐름이 고정되어 있어 같은 단계를 반복해야 하는 작업에 적합하다고 설명한다. 둘째, 폐루프 하네스는 코드를 고치고 테스트한 뒤, 실패 이유를 다시 기억에 넣어 통과할 때까지 반복한다. 시연에서는 약 다섯 번의 반복 뒤 반환할 수 있다고 말한다. 셋째, Google의 Agent Development Kit(ADK)를 이용한 예에서는 메모리 압축과 가드레일을 활용하고, 파일 삭제·데이터베이스 삭제·GitHub 푸시 같은 명령을 실행 전에 막는 함수를 둔다.

읽는 법: 반복이 많을수록 무조건 좋은 것이 아니다. 결과를 한 번 만들면 되는 고정 작업에는 선형 구조가 단순하다. 수정과 검증이 이어져야 하는 작업에는 폐루프가 맞지만, 테스트 같은 명확한 종료 조건과 위험 명령 차단이 필요하다.

모델·하네스·지식을 하나의 스택으로 본다

Smitha는 고성능 에이전트 개발 환경을 세 층으로 설명한다. 첫째는 판단을 수행하는 모델, 둘째는 실행을 조정하는 하네스, 셋째는 특정 분야에서 추측하지 않도록 돕는 지식이다. 영상에서 제시한 조합은 Gemini 3.8 Flash, Antigravity의 Boost 명령, Google Skills다.

그녀는 에이전트가 디렉터리 확인, 함수 수정, 테스트 실행을 20회·40회·60회처럼 연속해서 반복할 수 있으므로, 매 호출의 속도와 비용이 누적된다고 주장한다. 따라서 가장 무거운 모델만 고르는 대신 반복 작업에 충분히 빠르고 비용 부담이 낮은 모델을 고려해야 한다는 설명이다.

Boost는 오케스트레이터가 전문 하위 에이전트에 병렬로 일을 나누고 마지막에 독립 검증을 수행하는 기능으로 소개된다. 다만 일상적인 기능 추가나 코드 탐색이 아니라 복잡한 공학 문제에 선택적으로 쓰라고 권한다. Google Skills는 필요할 때 불러오는 정리된 분야 지식으로 설명되며, 전사 시점에 GitHub 별 19,000개를 넘었고 Google Cloud·Firebase·Flutter·Maps 등을 포함한 기술이 100개가 넘는다고 발표자가 말한다.

읽는 법: 세 층 가운데 하나만 바꾸면 전체 병목이 그대로 남을 수 있다. 빠른 모델도 실행 구조가 없으면 행동하지 못하고, 좋은 하네스도 필요한 분야 지식이 없으면 추측할 수 있다. 반대로 모든 작업에 가장 복잡한 하네스를 쓰면 비용과 제약이 불필요하게 커질 수 있다.

전체 메시지는 “더 똑똑한 모델을 사면 해결된다”가 아니라 실패가 발생하는 위치를 보고 모델·도구·맥락·반복·검증 중 어디를 고칠지 결정하라는 것이다. 다만 제품 성능, 공개 수치, 장기 자율성에 관한 설명은 영상 발표자들의 주장이다. 서로 다른 작업이나 시스템에서도 같은 결과가 난다는 독립 검증은 이 자료에 없다.

여기까지만 이해하면 충분

  • 언어 모델은 판단을 만들고, 하네스는 외부 정보·도구 실행·반복·검증을 연결한다.
  • 자율성은 긴 프롬프트보다 문서·도구·테스트처럼 재사용되는 환경에 기준을 넣을 때 커질 수 있다.
  • 긴 작업은 작은 변경과 검증을 이어 붙이고, 통과가 반복될 때만 범위를 넓혀야 한다.
  • 모델·하네스·지식은 서로 다른 층이므로 작업의 병목에 맞춰 선택해야 한다.

실력 좋은 요리사와 주방

모델은 조리법을 판단하는 요리사에 가깝고, 하네스는 재료·도구·위생 규칙·검수 절차가 갖춰진 주방에 가깝다. 좋은 요리사도 재료와 도구가 없으면 결과를 만들 수 없고, 검수 기준이 없으면 원하는 품질과 어긋날 수 있다.

1. 하네스의 정의

영상은 AI 에이전트를 대규모 언어 모델과 에이전트 하네스의 결합으로 정의한다. 단순한 지식 질문은 모델이 바로 답할 수 있지만, 현재 날씨처럼 외부 정보가 필요한 질문은 하네스가 조회 결과를 가져와야 한다.

예시에서는 사용자의 비옷 질문을 모델이 받고 날씨 정보가 필요하다고 판단한다. 하네스가 “맑고 98”이라는 정보를 가져와 원래 질문과 함께 다시 모델에 전달한다. 온도 단위는 전사에서 명시되지 않는다.

2. Ryan의 하네스 엔지니어링

진행자 Tilda는 Ryan Lopopolo를 만나 하네스라는 용어와 에이전트 중심 개발을 묻는다. Ryan은 자율 코딩 에이전트를 연구하면서 모델 주변에 여러 장치를 만들었고, 그 작업을 2026년 2월에 공개했다고 말한다.

Ryan은 2026년 9월 시점의 대화에서 작년 5월 무렵부터 편집기를 열지 않았다고 주장한다. 진행자는 자신은 8주째라고 말한다. 이 발언은 개인 경험이며 코드 작성이나 검토가 일반적으로 불필요하다는 검증 결과는 아니다.

그가 제안한 개입의 흐름은 다음과 같다.

  1. 같은 프롬프트를 다시 시도한다.
  2. 문서와 AGENTS.md에 기준을 넣는다.
  3. 정적 검증기와 테스트를 추가한다.
  4. 도구가 문서 집합에서 필요한 맥락을 찾게 한다.
  5. 반복 실패를 평가 자료로 올려 모델 개선에 활용한다.

Ryan은 관측 데이터를 PromQL 같은 기존 도구 형태로 모으고 CLI로 제공하면, 모델의 추론 일부를 결정적인 도구 실행으로 바꿀 수 있다고 설명한다. 또한 문서 본문과 링크 기준점의 위치를 가깝게 유지하는 테스트를 만들어 사람의 가독성과 에이전트의 맥락 효율을 함께 추구한다고 말한다.

3. 긴 시간의 일관성

Ryan이 해결하려는 중심 문제는 에이전트가 긴 시간 동안 같은 기준을 유지하는지다. 그는 조직의 결과물도 한 번에 만들어지는 것이 아니라 많은 사람의 반복적인 기여로 형성된다고 설명한다.

작은 PR은 사람이 검토하기 쉽고, 일부 검토를 에이전트에 맡길 가능성도 높인다. 작은 변경이 취할 수 있는 상태 범위를 좁히고, 이를 차례로 쌓으면 사람의 개입이 적은 더 긴 루프로 확장할 수 있다는 주장이다.

그는 팀원의 전문성을 중앙 에이전트에 더하는 모습을 RPG 캐릭터의 능력치가 높아지는 장면에 비유한다. React 아키텍트가 합류하면 아키텍처와 성능을 보는 관점이 추가되는 식이다. 작업을 먼저 분류하고 필요한 전문 맥락을 동적으로 불러오는 능력도 높은 자율성의 일부라고 말한다.

다만 그는 자신이 하네스를 직접 만든 적은 없다고 밝힌다. Antigravity와 같은 기반 하네스는 고정하고, 좋은 모델을 채택하면서 실패를 관찰해 주변의 도구와 맥락을 개선하는 일을 하네스 엔지니어링이라고 구분한다.

4. Billy의 구현 패턴

Billy의 설명에 따르면 모델은 도구 사용 의도를 출력할 수 있지만 자체적으로 파일이나 환경을 조작하지 못한다. 하네스가 그 의도를 실제 동작에 연결한다.

  • 선형 하네스: 파일을 검사하고 권고를 출력한 뒤 종료한다. 같은 흐름을 한 번 실행하는 결정적인 작업에 맞는다.
  • 폐루프 하네스: 코드를 수정하고 테스트를 실행한다. 실패 여부뿐 아니라 실패 이유를 메모리에 넣어 다시 수정한다. 시연에서는 약 다섯 번의 반복 뒤 반환할 수 있다고 말한다.
  • ADK 기반 하네스: Google Agent Development Kit의 메모리 압축과 가드레일을 이용하면서 사용자 규칙을 추가한다. 시연의 block_destructive_commands 함수는 파일 삭제, 데이터베이스 삭제, GitHub 푸시 같은 위험 행동을 실행 전에 막는다.

Billy는 모든 문제에 가장 좋은 단일 하네스는 없다고 말한다. 설계할 때 반복 횟수, 사용할 도구, 도구 사용 시점과 방식, 메모리의 중요성과 조회 시점을 결정해야 한다.

5. Smitha의 세 층 스택

Smitha는 코딩 에이전트가 한계에 부딪혔을 때 더 무거운 기반 모델로 즉시 바꾸는 반응을 경계한다. 그녀가 제시한 세 층은 다음과 같다.

  1. 모델: Gemini 3.8 Flash를 그 주의 주 사용 모델로 소개한다.
  2. 하네스: Antigravity의 Boost 명령을 소개한다.
  3. 지식: Google Skills 저장소를 소개한다.

여기 제가 준비한 코드를 살펴보겠습니다. 이 코드를 실행하면 모델은 파일을 검사해야 한다는 내용의 텍스트만 출력할 수 있습니다. 하네스는 그 의도를 행동으로 연결하는 작업을 수행해야 합니다.

그 연결의 목표는 모델이 우리가 원하는 일을 하도록 최적화하는 것입니다. 코딩일 수도 있고, 글쓰기나 조사일 수도 있으며, 에이전트 하네스는 이를 가능하게 하는 방법입니다.

모든 것을 지배할 단 하나의 최고의 하네스는 없습니다. 여기에도 하나의 최선의 해법은 없으며, 바로 이것이 우리가 현재 에이전트 하네스라는 문제 공간에서 탐구하고 있는 내용입니다. 어떤 문제에서 중요한 것이 다른 문제에서는 중요하지 않을 수도 있습니다.

각 하네스(harness)에서는 몇 가지를 결정할 수 있습니다. 루핑(looping), 즉 몇 번 반복할지, 도구(tools), 어떤 도구를 언제 어떻게 사용할지, 그리고 메모리(memory), 해당 워크플로에서 메모리가 얼마나 중요한지와 언제 검색할지입니다.

여기서는 서로 다른 세 가지 하네스를 살펴보겠습니다. 먼저 보여드릴 패턴은 루핑이 없는 선형 하네스(linear harness)입니다. 이 하네스는 파일을 검사하고 권장 사항을 출력한 뒤 종료할 수도 있고, 파일을 살펴볼 필요가 없었다면 답변만 반환할 수도 있습니다. 항상 똑같은 흐름을 따릅니다. 어느 정도의 결정성(determinism)이 필요할 때 매우 좋습니다. 매번 같은 작업을 수행하게 만들고 싶은 경우입니다.

이것도 실행해 보겠습니다. 이 파일을 살펴본 뒤, 파일의 정보와 원하는 분석 결과를 종합해 결과를 출력했습니다. 하지만 매번 항상 똑같은 흐름을 따릅니다. 도구를 한 번 읽고, 응답을 출력한 다음 종료합니다.

코드 편집 등에서 매우 흔한 또 다른 패턴은 종료 상태에 도달할 때까지 계속 반복해서 실행하는 폐쇄 루프(closed loop)입니다.

코드에서 작업을 수행하고 코드를 수정하고 싶다면 이런 폐쇄 루프 하네스를 사용하고 싶을 것입니다. 문제가 해결될 때까지 실행되게 하는 것입니다. 여기서는 코드 수정 사항을 적용한 다음 테스트를 실행합니다. 테스트가 통과할 때까지 반환하지 않습니다. 아마 다섯 번 정도 반복한 뒤 반환하도록 하겠습니다.

이렇게 하면 코드를 변경하고 테스트 모음을 실행한 뒤 실패 출력을 수집할 수 있습니다. 단순히 통과 여부만 확인하는 것이 아니라 왜 실패했는지도 확인하고, 그 오류를 메모리에 다시 입력해 테스트가 통과할 때까지 계속 반복할 수 있습니다.

오늘 살펴볼 마지막 유형은 더 많은 안전장치(safety guardrails)가 있는 방식입니다. 무언가를 처음부터 구축하고 싶지만 이 모든 기능을 한 번에 한 부분씩 구현하고 싶지는 않다면, Google의 에이전트 개발 키트(Agent Development Kit)인 ADK 같은 도구를 사용할 수 있습니다. 이를 이용하면 더 많은 안전장치와 메모리 압축(memory compaction)이 기본으로 포함된 고급 기능을 구축할 수 있습니다. 이러한 기능을 모두 직접 코딩할 필요는 없으면서도, 기성 솔루션을 사용하는 것보다 훨씬 더 많은 사용자 지정이 가능합니다.

여기에도 block_destructive_commands 함수가 있고, 코드를 실행하는 등의 작업을 수행하기 전에 파일 삭제, 데이터베이스 삭제, GitHub로 푸시처럼 위험한 명령을 실행하지 않도록 확인하고 있습니다. 여기서는 완전히 기성 방식인 도구를 사용하지 않고도 에이전트 도구를 활용하면서 많은 사용자 지정을 적용할 수 있습니다.

현재 가장 인기 있는 에이전트 하네스는 Google Antigravity, Claude Code, Cursor 같은 도구입니다. 모두가 “지금은 이게 최고야”라고 말할 것입니다. 이 도구들은 모두 훌륭하지만, 무엇에 가장 적합할까요? 무엇을 가장 잘할까요?

이들 중 상당수는 특정한 방식으로 컴퓨터를 사용하고, 특정한 방식으로 메모리를 사용하며, 특정한 방식으로 문제를 해결하는 데 뛰어납니다. 하지만 여러분이 해결하려는 문제에는 특정한 관점을 가진 도구가 필요할 수도 있습니다.

이 도구들이 컴퓨터로 작업하거나 코드를 작성할 때 매우 잘 작동하고 매끄럽게 느껴지는 이유는 모델 자체에 있지 않습니다. 모델들은 정말 똑똑합니다. 핵심은 모델을 둘러싼 하네스 엔지니어링(harness engineering)입니다. 이 도구들은 엔지니어링 원칙과 현재 소프트웨어를 효과적으로 작성하는 데 필요한 모든 도구를 바탕으로 영리하게 설계되어 있습니다.

자, 이제 Smitha와 Luke에게 돌아가겠습니다.

에이전트 하네스에 대한 훌륭한 심층 분석이었습니다. 하지만 지금 AI 분야에서는 멋진 일들이 많이 일어나고 있고, Smitha, 공유하고 싶은 다른 내용도 많으시죠. 그 이야기들을 해보겠습니다.

코딩 에이전트에는 더 똑똑한 모델이 필요한 것이 아니라 더 나은 스택이 필요합니다. 개발자들이 코딩 에이전트가 한계에 부딪혔다고 느낄 때마다 가장 먼저 하는 반응은 더 무거운 기반 모델(foundational model)로 바꾸는 것입니다. 하지만 AI 워크플로를 매일 사용하다 보면 모델은 퍼즐의 한 조각일 뿐이라는 사실을 깨닫게 됩니다.

진정으로 높은 성능을 내는 에이전트 개발 스택은 서로 연결된 세 가지 계층으로 구성됩니다. 첫 번째는 모델, 두 번째는 하네스, 세 번째는 지식입니다. 이 세 가지가 모두 맞물리면 모든 것이 달라집니다.

오늘은 이번 주에 제가 마음에 들어 하며 사용한 세 가지 도구를 소개하겠습니다. 스택의 각 계층에 하나씩 해당하는 도구입니다.

첫 번째 계층은 모델 계층이고, 이번 주에 제가 매일 주로 사용한 모델은 Gemini 3.8 Flash였습니다. 여러분은 처음에 이렇게 반응할 수도 있습니다. “왜 Flash죠? 가장 강력한 추론 등급을 가진 모델을 원하지 않나요?” 에이전트 워크플로의 비밀은 에이전트가 전통적인 단일 턴 프롬프트 상자처럼 작동하지 않는다는 데 있습니다. 에이전트는 지속적인 루프를 실행합니다.

에이전트는 디렉터리를 검사하고, 함수를 업데이트하고, 단위 테스트를 실행한 다음, 하나의 작업을 끝내기 위해 그 과정을 20번, 40번, 심지어 60번 반복할 수도 있습니다. 이렇게 많은 순차적 단계를 사용하는 경우 속도와 비용은 크게 누적됩니다.

빠르고 비용 효율적인 모델은 성능이 낮은 선택이 아닙니다. 실제 에이전트 루프를 실용적이고 반응성 있게 만드는 바로 그 요소입니다. Flash는 매우 가볍기 때문에 수십 번의 반복을 쉽게 처리하고, 비용을 크게 늘리지 않으면서 제가 진행 상황을 계속 파악할 수 있게 해줍니다.

빠른 모델을 갖췄다면 이를 조율하는 동적인 구조가 필요합니다. 이것이 두 번째 계층인 하네스입니다.

여기서 제가 사용하는 도구는 Antigravity, 그중에서도 Boost 명령입니다. 한 문장으로 말하면 Boost는 하나의 모델을 조율된 팀으로 바꾸는 슬래시 명령(slash command)입니다. 하나의 에이전트가 모든 일을 순차적으로 처리하도록 하는 대신, Boost는 오케스트레이터(orchestrator)를 실행하고 전문화된 하위 에이전트들을 병렬로 배정하며, 코드베이스에 어떤 변경도 적용하기 전에 작업을 철저히 감사하는 독립적인 검증 단계를 거쳐 마무리합니다.

이를 최대한 활용하는 방법은 다음과 같습니다. 일상적인 작업에 사용할 필요는 없습니다. 예를 들어 일반적인 기능을 작업하거나, UI 구성 요소를 추가하거나, 코드베이스를 탐색할 때는 기본 에이전트가 빠르고 효율적입니다. Boost는 깊이 복잡한 엔지니어링 문제를 위해 아껴 두는 것이 좋습니다.

이 표는 Boost가 유용한 상황을 잘 보여주는 사용 사례입니다. Antigravity의 세 가지 실행 모드를 비교하고 Boost가 어떻게 상황을 바꿀 수 있는지 보여줍니다. Boost는 이 표에 설명된 깊이 복잡한 엔지니어링 문제를 위해 아껴 두어야 하며, 표는 정확히 언제 Boost를 사용해야 하는지 알려줍니다.

이제 세 번째이자 마지막 요소인 세 번째 계층, 지식 계층으로 넘어가겠습니다. 첫 번째와 두 번째 계층을 통해 빠른 모델과 조율된 하네스를 갖췄습니다. 하지만 에이전트가 예를 들어 여러분의 클라우드 인프라를 구성하기를 원한다면 어떻게 될까요? 에이전트는 그 방법을 어떻게 알까요?

바로 이 지점에서 Google Skills가 등장합니다. 이 저장소는 최근 GitHub에서 별 19,000개를 돌파했습니다. 아직 초기 단계이며 활발히 발전하고 있기 때문에, 참여하고 싶다면 지금은 기여의 문이 활짝 열려 있습니다.

간단히 말해 스킬(skill)은 코딩 에이전트가 필요할 때 불러오는 선별된 도메인 지식입니다. 단순한 MCP 서버도 아니고 무거운 플러그인도 아닙니다. 에이전트에 제공되는 깔끔하고 정확한 컨텍스트로, 에이전트가 추측하지 않도록 하고 작업 방법을 알려줍니다.
