추론 하드웨어(Inference Hardware) 앞으로 AI 비용과 속도의 병목은 추론에서 커진다 지연시간과 에너지 효율이 제품 가능성을 결정한다

컨텍스트 엔지니어링(Context Engineering) 모델을 직접 학습시키지 않아도 성능을 크게 높일 수 있다 검색, 도구, 메모리, 지침을 잘 엮는 능력이 중요하다
장기 실행 에이전트(Long-running Agents) 에이전트가 몇 시간, 며칠, 몇 주 동안 일하면 업무 구조가 바뀐다 실패를 줄이려면 스킬, 평가자, 다중 에이전트 구조가 필요하다
스타트업의 승부처 대형 모델 회사가 모든 세부 도메인을 깊게 커버하진 못한다 범용 모델이 0~1%만 성공하는 영역을 찾아야 한다
좋은 문제를 고르는 감각(Taste) 코드 생산이 쉬워질수록 무엇을 만들지가 더 희소해진다 창업자의 핵심 역량은 실행보다 문제 선택으로 이동한다
자동 실험 루프(Automated Experimentation Loop) AI가 AI와 과학·공학 시스템을 개선할 수 있다 목표와 평가자가 명확한 영역은 자동화 속도가 빨라진다

내가 모를 만한 것 / 처음 보는 것

  • TPU(Tensor Processing Unit) — 구글이 머신러닝 추론·학습을 위해 만든 특수 목적 칩. 저정밀도 조밀 선형대수(low-precision dense linear algebra)에 최적화되어 있다.
  • 배칭(Batching) — 여러 입력을 묶어 한 번에 처리해 데이터 이동 비용을 나누는 방식. 지연시간은 늘 수 있지만 에너지 효율은 좋아진다.
  • HBM(High Bandwidth Memory) — AI 가속기에서 많이 쓰는 고대역폭 메모리. 연산보다 데이터를 메모리에서 가져오는 비용이 더 클 수 있다.
  • 컨텍스트 엔지니어링(Context Engineering) — 모델에 넣는 정보, 도구, 검색 결과, 지침, 작업 절차를 설계해 성능을 높이는 방법.
  • 스킬(Skill) — 에이전트가 특정 도구나 절차를 잘 쓰도록 작성한 지침·작업 패턴.
  • 추론 시점 연산(Inference-time Compute) — 답을 한 번에 내지 않고 여러 경로를 탐색·평가하며 더 나은 결과를 찾는 방식.
  • 지식 증류(Distillation) — 큰 교사 모델(teacher model)의 능력을 작은 학생 모델(student model)에 옮겨 빠르고 저렴하게 만드는 기법.
  • AlphaFold — 단백질 접힘(protein folding)을 예측하는 구글 딥마인드의 특화 AI 모델.
  • AlphaChip, AlphaEvolve — 칩 설계나 해법 탐색처럼 제안·평가·개선을 반복하는 AI 시스템 계열.
  • ECC 메모리(ECC Memory) — 오류를 감지·수정하는 메모리. 하드웨어 신뢰성 논의에서 등장한다.
  • Reed-Solomon 인코딩(Reed-Solomon Encoding) — 일부 데이터가 손상되어도 복구 가능하게 하는 오류 정정 기법.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 2001년 구글 검색 인덱스가 전체 서버의 RAM에 들어갈 수 있다는 계산을 했고, 며칠 만에 RAM 기반 검색 버전을 배포했다 — 디스크 기반 검색에서 메모리 기반 검색으로 전환해 속도를 크게 높인 사례.
  2. 2013년 음성인식이 하루 사용자당 3분만 쓰여도 구글 서버 함대를 두 배로 늘려야 한다는 계산이 나왔다 — 이 병목이 TPU 개발의 출발점이 되었다.
  3. 초기 TPU는 당시 CPU·GPU 대비 에너지 효율이 30~80배, 지연시간이 20~30배 좋았다 — 특수화 하드웨어의 파급력을 보여준다.
  4. 연산 1회는 약 1피코줄(picojoule)이지만, 데이터를 가져오는 I/O는 그 1,000배 수준일 수 있다 — AI 시스템 설계가 사실상 에너지 문제라는 주장.
  5. 지연시간이 50배 좋아지면 완전히 다른 제품이 가능하다고 말한다 — 사용자 경험과 제품 범위가 바뀌는 수준의 차이.
  6. 스타트업은 범용 모델이 20% 성공하는 문제가 아니라 0~1% 성공하는 문제를 찾아야 한다 — 이미 성능이 나오기 시작한 영역은 곧 대형 모델이 따라잡을 가능성이 크다.
  7. 에이전트는 10단계쯤은 잘하지만 30~50단계에서 흔들릴 수 있다 — 장기 실행에는 평가, 분기 탐색, 스킬 설계가 필요하다.
  8. 구글 내부에서는 로그 조회, 코드리뷰, 성능 측정 같은 내부 도구 사용법을 스킬로 만들어 에이전트 성능을 높인다 — 모델 학습 없이 업무 적합성을 높이는 방식.
  9. 양자화학 시뮬레이터를 신경망 근사 모델로 대체해 300,000배 빠르게 검증한 사례를 든다 — 실험 루프의 속도가 과학 방법론 자체를 바꾼다는 예시.
  10. 대형 모델은 인간이 18세까지 보는 데이터보다 약 1,000배 많은 데이터를 볼 수 있다고 언급한다 — 현재 AI의 데이터 효율성이 아직 낮다는 문제의식.

1. AI는 이미 주니어 엔지니어 수준인가

Jeff Dean은 2025년에 “AI가 주니어 엔지니어 수준에 도달했다”고 말했는데, 2026년 기준으로 그 예측이 꽤 맞았다고 본다. 특히 에이전트 기반(agent-based) 코딩 작업, 긴 시간 동안 이어지는 작업, 복잡한 코드 변경에서 모델의 능력이 빠르게 올라왔다고 한다.

중요한 점은 이 변화가 코딩에만 머물지 않는다는 것이다. 그는 과학, 엔지니어링, 머신러닝 연구처럼 측정 가능한 목표(measurable objective)가 있는 분야라면 AI 에이전트가 문제를 쪼개고 실험하고 개선하는 방식으로 큰 진전을 만들 수 있다고 본다.

2. 2027년 예측: AI 시스템이 스스로 개선된다

Jeff Dean의 다음 예측은 ML 시스템이 자기 자신을 개선하는 자동화다. 흐름은 다음과 같다.

  1. 큰 문제를 하위 문제로 분해한다.
  2. 각 하위 문제에 대해 많은 실험을 자동으로 돌린다.
  3. 실험 결과를 평가한다.
  4. 좋은 결과를 다시 합쳐 전체 시스템을 개선한다.

이것은 단순히 “AI가 코드를 짠다”가 아니라, AI가 실험 설계자이자 실행자이자 평가 보조자가 되는 구조다. 특히 목표가 명확하고 결과를 측정할 수 있는 영역에서 강력하다.

3. 구글 검색의 “메모리에 들어간다” 순간

2001년 구글 검색은 하드드라이브 기반으로 동작했다. Jeff Dean과 Sanjay Ghemawat은 전체 검색 인덱스가 구글이 가진 컴퓨터들의 RAM에 들어갈 수 있다는 계산을 했다. 그리고 며칠 만에 RAM 기반 검색 버전을 배포했고, 검색 속도가 크게 개선되었다.

이 이야기가 중요한 이유는 기술적 디테일보다 사고방식에 있다. 모두가 기존 방식을 당연하게 볼 때, 누군가는 “이제 조건이 바뀌었는데, 완전히 다르게 풀 수 있지 않나?”라고 계산한다.

현재 AI 시대의 비슷한 순간으로 Jeff Dean은 고성능·저에너지 추론 하드웨어(inference hardware)를 든다. 앞으로 AI 에이전트가 대중적으로 쓰이려면 응답 지연시간(latency)과 에너지 비용이 낮아져야 하기 때문이다.

4. TPU를 만든 냅킨 계산

2013년 구글에서 딥러닝 기반 음성인식이 좋아지기 시작했다. 기존 시스템보다 계산 비용은 컸지만 오류율을 절반으로 줄였다. 이는 음성인식 분야에서 20년치 발전에 해당하는 개선이었다.

문제는 사용량이었다. 만약 모든 구글 사용자가 하루 3분씩 음성인식을 쓴다면, 당시 CPU 기반 인프라로는 구글 서버를 두 배로 늘려야 할 정도의 비용이 필요했다. 이 계산이 TPU 개발의 계기가 되었다.

TPU는 Chrome이나 Word를 실행하는 범용 칩이 아니다. 대신 현대 머신러닝의 핵심인 저정밀도 조밀 선형대수(low-precision dense linear algebra)에 집중했다. 너무 좁게 특화하지는 않되, 충분히 특화해서 큰 성능 이득을 얻은 것이다.

5. AI 시스템은 에너지 문제다

Jeff Dean은 AI 시스템에서 중요한 숫자가 바뀌었다고 말한다. 예전 분산시스템 엔지니어가 캐시 미스, 디스크 탐색, 네트워크 왕복 시간을 외웠다면, AI 시대 엔지니어는 다음 숫자를 알아야 한다.

  • 가속기 메인 메모리와 온칩 메모리 간 대역폭
  • 곱셈 연산 1회의 에너지 비용
  • 칩 간 인터커넥트 대역폭
  • 500개 칩에서 10,000개 칩으로 늘릴 때 네트워크 성능 저하
  • 데이터 이동 비용과 연산 비용의 차이

특히 연산 자체보다 데이터를 가져오는 비용이 훨씬 크다. 그래서 배칭(batching)이 필요하다. 여러 입력을 묶으면 데이터 이동 비용을 나눠 부담할 수 있다. 하지만 배칭은 낮은 지연시간이 중요한 서비스에는 불리하다. 즉, 어떤 AI 제품이 가능한지는 모델 성능뿐 아니라 데이터 이동 비용과 지연시간 구조가 결정한다.

6. 컨텍스트 엔지니어링이 다음 전장이다

AI 발전은 더 큰 모델, 더 많은 데이터만의 문제가 아니다. 이제는 모델 주변 시스템이 중요해진다.

  • 검색(retrieval)
  • 도구 호출(tool calling)
  • 메모리(memory)
  • 과거 작업 이력
  • 작업 지침
  • 문제 분해
  • 결과 평가
  • 다중 에이전트 오케스트레이션(orchestration)

Jeff Dean은 이것을 전체 시스템 설계로 본다. 모델이 훈련 데이터 속에 희미하게 배운 정보보다, 현재 컨텍스트에 직접 들어온 정보가 훨씬 명확하게 작동한다. 그래서 창업자나 작은 팀도 API만 있으면 컨텍스트 엔지니어링으로 경쟁력을 만들 수 있다.

예를 들어 Jeff Dean과 Sanjay는 성능 최적화 작업을 위해 모델에게 벤치마크 측정, 코드 변경, 성능 비교, 반복 개선 절차를 가르치는 스킬(skill)을 만들었다. 인간 전문가가 하던 접근법을 모델이 사용할 수 있는 형태로 정리한 것이다.

7. 장기 실행 에이전트가 실패하는 이유

에이전트는 짧은 작업에서는 잘 작동하지만 30단계, 50단계로 길어지면 흔들릴 수 있다. 이유는 모델이 훈련 분포 밖(out of distribution)으로 벗어나기 때문이다. 익숙하지 않은 도구 사용, 낯선 절차, 누적된 작은 오류가 성능을 떨어뜨린다.

해결 방향은 세 가지다.

  1. 모델이 잘 아는 밝은 길에 머물도록 스킬과 힌트를 준다.
  2. 여러 에이전트가 다른 접근을 시도하게 한다.
  3. 별도 평가자 모델이나 에이전트가 어떤 경로가 유망한지 고른다.

Jeff Dean은 이를 추론 시점 연산(inference-time compute)을 이용한 탐색(search)이라고 본다. 한 번에 답을 내기보다 여러 가능한 해법을 탐색하고 평가하면 장기 작업의 신뢰도가 올라간다.

8. 스타트업은 어디서 이길 수 있나

구글 같은 회사는 모델, 하드웨어, 제품까지 전체 스택을 공동 설계한다. 그렇다면 2~3명 팀은 어디서 이길 수 있을까?

Jeff Dean의 답은 특정 도메인이다. 범용 모델은 모든 것을 잘하려고 하기 때문에 아주 구체적인 문제, 특정 데이터, 세밀한 사용자 경험에는 빈틈이 있다.

좋은 창업 아이템의 조건은 다음과 같다.

  • 창업자가 진심으로 관심 있는 문제
  • 세상에 실제로 유용한 문제
  • 현재 범용 모델이 거의 실패하는 문제
  • 6~12개월 안에 대형 모델이 쉽게 따라잡기 어려운 문제
  • 제품이 접근할 수 있는 독자적 데이터가 있는 문제
  • 특화 모델이나 특화 워크플로가 강한 정확도를 낼 수 있는 문제

그는 범용 모델이 20% 성공하는 영역은 위험하다고 말한다. 이미 능력이 생기고 있다는 신호이기 때문이다. 반대로 0~1%만 성공하는 문제는 더 좋은 기회일 수 있다.

9. AI-native 창업자의 핵심 역량

AI가 코드를 많이 써주는 시대에는 스펙(specification)을 잘 쓰는 능력이 더 중요해진다. 에이전트에게 원하는 결과를 명확히 전달하지 않으면, 에이전트는 사용자의 의도를 추측해야 한다. 그 추측은 자주 빗나간다.

Jeff Dean은 좋은 예로 언어 변환 작업을 든다. Python 구현을 Go 구현으로 바꾸는 작업은 AI가 매우 잘한다. 이유는 원래 코드와 테스트가 매우 상세한 스펙 역할을 하기 때문이다. 기대 동작이 명확하므로 모델이 검증하고 비교하며 수정할 수 있다.

앞으로 모두가 수십, 수백 개의 에이전트를 운영하게 된다면 희소한 능력은 코딩이 아니라 무엇을 시킬지 고르는 감각(taste)이다. 좋은 문제를 고르고, 중요한 방향을 정하고, 높은 수준의 판단을 내리는 능력이 창업자의 핵심이 된다.

10. 가정을 의심하는 사고실험

Jeff Dean은 가끔 모두가 당연하게 여기는 전제를 뒤집어보라고 말한다. 예를 들어 반도체 업계는 수십 년 동안 “같은 설계의 칩은 모두 동일하게 작동해야 한다”는 전제를 갖고 발전했다. 그런데 만약 트랜지스터가 하루에 20번 오류를 내도 되는 시스템을 만든다면 어떨까?

이는 당장 하자는 제안이 아니라 사고실험이다. 대규모 분산시스템에서는 이미 불완전한 부품으로 신뢰성 있는 시스템을 만든다. 디스크는 고장 나지만 데이터는 복제와 오류 정정으로 보호한다. 이런 관점을 트랜지스터 수준까지 밀어붙이면 완전히 다른 설계 가능성이 나올 수 있다.

그는 MapReduce도 비슷한 사고에서 나왔다고 설명한다. 복잡한 병렬화, 체크포인트, 장애 복구 코드를 매번 섞어 쓰는 대신, 많은 작업을 Map과 Reduce라는 추상화로 볼 수 있지 않을까 생각했다. 그 결과 대규모 계산을 안정적으로 처리하는 공통 기반이 만들어졌다.

11. AI가 AI를 만들고 과학을 가속한다

AlphaChip, AlphaEvolve 같은 시스템은 제안, 실행, 평가, 개선의 루프를 자동화한다. Jeff Dean은 이것을 과학적 방법(scientific method)의 자동화로 본다.

핵심은 실험 루프의 지연시간을 줄이는 것이다. 어떤 실험이 하룻밤 걸리면 10개만 해도 오래 걸린다. 그런데 검증 모델이 300,000배 빨라지면 점심시간 동안 수천, 수만 개를 걸러볼 수 있다.

그는 양자화학 사례를 든다. 원래는 밀도범함수이론(density functional theory) 시뮬레이터가 분자 하나의 특성을 계산하는 데 밤새 걸릴 수 있다. 하지만 비싼 시뮬레이터의 입출력 데이터를 학습한 신경망 근사 모델을 만들면 거의 비슷한 정확도로 훨씬 빠르게 검증할 수 있다.

이런 구조는 머신러닝 자체, 재료과학, 칩 설계, 과학 연구 전반에 적용될 수 있다.

진행자는 Jeff Dean에게 AI가 주니어 엔지니어 수준이라는 과거 예측이 얼마나 맞았는지 묻는다. Jeff Dean은 에이전트 기반(agent-based) 코딩 작업과 장기 실행 작업에서 모델이 빠르게 좋아졌고, 주니어 엔지니어라는 표현이 꽤 맞는다고 답한다. 특히 코딩 밖의 영역에서도 에이전트 시스템이 빛나기 시작했다고 본다.

그는 2027년쯤에는 ML 시스템 자체를 자동화하는 흐름이 커질 것이라고 예측한다. AI가 문제를 하위 문제로 쪼개고, 각 문제에 대해 자동 실험 루프를 돌리고, 결과를 합쳐 더 나은 시스템을 만드는 방식이다. 측정 가능한 목표가 있는 과학·공학 분야에도 같은 방식이 적용될 수 있다고 말한다.

진행자는 2001년 구글 검색이 하드디스크에서 동작하던 시절을 언급한다. Jeff Dean과 Sanjay Ghemawat은 전체 검색 인덱스가 서버들의 RAM에 들어갈 수 있다는 계산을 했고, 며칠 만에 RAM 기반 검색 버전을 운영에 반영했다. Jeff Dean은 지금의 유사한 순간은 고성능·저에너지 추론 하드웨어(inference hardware)라고 본다. 에이전트 시스템을 더 많은 사람에게 제공하려면 지연시간(latency)과 에너지 효율이 핵심이기 때문이다.

그는 많은 사람이 아직 에이전트가 며칠 또는 몇 주 동안 복잡한 작업을 수행할 수 있다는 가능성을 충분히 내면화하지 못했다고 말한다. 예를 들어 에이전트에게 소프트웨어를 더 안전하거나 더 빠른 다른 프로그래밍 언어로 새로 구현하라고 지시할 수 있고, 실제로 꽤 진지한 수준으로 수행할 수 있다고 설명한다.

진행자는 2013년 음성인식 관련 냅킨 계산(back-of-the-envelope calculation)을 이야기한다. 딥러닝 기반 음성인식은 오류율을 절반으로 줄였지만 계산 비용이 컸다. 모든 사용자가 하루 3분씩 음성인식을 쓰면 구글 서버 함대를 두 배로 늘려야 한다는 계산이 나왔고, 이것이 TPU 개발의 출발점이 되었다. TPU는 저정밀도 조밀 선형대수(low-precision dense linear algebra)에 특화되었고, 당시 CPU·GPU보다 에너지 효율은 30~80배, 지연시간은 20~30배 좋았다.

Jeff Dean은 좋은 냅킨 계산이란 현재 병목을 보고, 완전히 다른 방식으로 풀면 성능이나 능력이 10배, 100배 좋아질 수 있는지 생각하는 것이라고 말한다. 기존 방식에 묶이지 말고 제1원리(first principles)로 문제를 다시 보라고 조언한다.

진행자는 Jeff Dean의 유명한 “엔지니어가 알아야 할 지연시간 숫자들(Latency Numbers Every Engineer Should Know)”을 AI 시대 버전으로 업데이트해 달라고 한다. Jeff Dean은 AI 시스템에서는 가속기 메모리 대역폭, 온칩 메모리, 곱셈 유닛, 연산당 에너지, 칩 간 인터커넥트, 수천·수만 칩으로 확장할 때의 네트워크 성능 저하를 알아야 한다고 말한다.

그는 연산보다 데이터 이동이 훨씬 비싸다고 강조한다. 계산 1회는 약 1피코줄(picojoule)이지만, HBM에서 데이터를 가져오는 비용은 그 1,000배일 수 있다. 이 차이 때문에 배칭(batching)이 필요하다. 여러 예시나 토큰을 묶어 처리하면 데이터 이동 비용을 나눌 수 있지만, 낮은 지연시간이 중요한 서비스에는 배칭이 불리하다.

진행자는 AI를 압축(compression) 문제로 보는 관점을 언급한다. Jeff Dean은 데이터를 진정으로 이해한다면 잘 압축할 수 있어야 한다고 동의한다. 그리고 트랜스포머(transformer)는 지금까지 잘 작동하는 방식이라고 말한다.

이어서 컨텍스트 엔지니어링(context engineering)이 논의된다. Jeff Dean은 모델은 전체 시스템의 한 부분일 뿐이며, 도구 사용, 검색(retrieval), 메모리, 과거 정보, 현재 컨텍스트, 문제 분해, 도구 호출 순서, 여러 접근 시도와 평가가 모두 중요하다고 말한다. 훈련 데이터는 거대한 파라미터 속에 섞여 있지만, 현재 컨텍스트에 들어온 정보는 모델이 직접 볼 수 있어 더 명확하다.

그는 컨텍스트 엔지니어링을 잘하려면 실제 문제를 모델과 도구로 풀어보며 모델이 어디서 실패하는지 관찰하라고 조언한다. 모델 파라미터를 바꾸지 않아도, 좋은 지침과 스킬(skill)을 주면 특정 문제에서 훨씬 잘 작동할 수 있다.

Jeff Dean은 Sanjay와 함께 저수준 라이브러리 성능 최적화를 하며 만든 스킬 사례를 설명한다. 구글 내부의 마이크로벤치마크(microbenchmark) 라이브러리로 자료구조나 연산의 성능을 측정하고, 코드를 바꾸고, 다시 측정하는 반복 절차를 모델에게 가르쳤다. 인간 전문가가 쓰는 최적화 접근법을 모델이 사용할 수 있는 형태로 제공한 것이다. 또한 두 사람이 작성한 “Performance Hints” 문서를 모델에 요약해 넣으면 코드 성능 문제를 더 잘 추론할 수 있다고 말한다.

장기 실행 에이전트가 30~50단계쯤에서 흔들리는 문제에 대해 Jeff Dean은 모델이 훈련 분포 밖으로 벗어나기 때문이라고 설명한다. 해결책은 스킬과 힌트로 모델을 익숙한 경로에 머물게 하고, 여러 에이전트가 서로 다른 접근을 시도하게 한 뒤, 다른 모델이나 에이전트가 평가하게 하는 것이다. 이는 추론 시점 연산(inference-time compute)을 사용해 가능한 해법 공간을 탐색하는 방식이다.

스타트업이 구글 같은 회사와 경쟁할 수 있는 영역에 대해 Jeff Dean은 특정 도메인에서 잘 설계된 제품 표면, 특화 스킬, 특화 모델이 장점이 될 수 있다고 말한다. 하지만 범용 모델이 계속 넓은 영역에서 좋아지고 있으므로, 지금 하는 일이 6~12개월 안에 대형 모델에 흡수될지 판단해야 한다고 경고한다. 범용 모델이 20%쯤 성공하는 문제보다 0~1%만 성공하는 문제를 찾으라고 조언한다.

좋은 문제의 형태로는 제품이 접근할 수 있는 개인 데이터나 특수 데이터가 있는 경우, 특정 도메인에서 저렴하게 특화 모델을 학습해 높은 정확도를 낼 수 있는 경우를 든다. AlphaFold처럼 단백질 접힘(protein folding)에 매우 특화된 모델이 큰 성과를 낸 사례도 언급한다. 비슷하게 재료과학, 칩 설계 같은 영역도 가능성이 있다고 본다.

AI-native 창업자가 되는 방법에 대해 Jeff Dean은 명확한 설계 문서와 스펙(spec)이 중요하다고 말한다. 에이전트에게 원하는 바를 분명히 지정할수록 성공 가능성이 높아진다. Python 구현을 Go 구현으로 번역하는 작업처럼 기존 코드와 테스트가 상세한 스펙 역할을 할 때 모델은 매우 잘 작동한다.

모든 사람이 수십, 수백 개 에이전트를 운영하게 되면 희소한 능력은 무엇이냐는 질문에 그는 “무엇을 시킬지 고르는 감각(taste)”이라고 답한다. 연구에서도 좋은 도구보다 중요한 것은 어떤 문제에 시간을 쓸지 결정하는 것이다. 지루한 문제를 완벽히 실행하는 것보다 중요한 문제를 잘 고르는 것이 훨씬 낫다.

감각을 기르는 방법으로 그는 경험, 과거 문제에서 얻은 패턴, 앞으로 12개월 동안 중요해질 것 같은 아이디어를 적어두고 나중에 실제로 무엇이 중요했는지 복기하는 방법을 제안한다. 또한 모두가 당연하게 여기는 가정을 의심하는 사고실험도 중요하다고 말한다.

그는 반도체 설계에서 “모든 트랜지스터는 거의 완벽해야 한다”는 가정을 뒤집는 사고실험을 소개한다. 만약 하루에 20번 오류가 나는 트랜지스터로 시스템을 만든다면 어떤 설계가 가능할까? 대규모 분산시스템은 이미 불완전한 디스크와 서버를 복제, 오류 정정, Reed-Solomon 인코딩으로 신뢰성 있게 만든다. 이런 발상을 더 낮은 수준으로 가져갈 수 있는지 생각해보자는 것이다.

과거의 성공 사례로는 TPU와 MapReduce를 든다. MapReduce는 복잡한 병렬화와 장애 복구 코드를 매번 직접 작성하는 대신, 많은 대규모 계산을 Map과 Reduce 추상화로 표현하고, 체크포인트와 신뢰성 처리는 하위 라이브러리에 넣은 시스템이다.

Jeff Dean은 AlphaChip, AlphaEvolve처럼 AI가 제안하고 평가하고 개선하는 시스템이 과학적 방법(scientific method)을 자동화할 수 있다고 말한다. 고수준 목표를 하위 문제로 나누고, 각 하위 문제에서 자동 실험 루프를 돌린 뒤 결과를 합치면 머신러닝, 과학, 공학이 빨라질 수 있다.

평가자(evaluator)가 느린 경우에는 빠른 근사 모델이 중요하다. 예를 들어 양자화학에서 밀도범함수이론(density functional theory) 시뮬레이터는 한 분자 계산에 밤새 걸릴 수 있지만, 그 입출력 데이터를 학습한 신경망 근사 모델은 300,000배 빠르고 거의 비슷한 정확도를 낼 수 있다. 이렇게 되면 수개월 걸릴 탐색을 점심시간 동안 할 수 있게 된다.

머신러닝 자체도 이런 자동 실험 루프의 대상이다. 현재는 연구자가 아이디어를 내고 작은 실험을 돌린 뒤 큰 규모로 확장하지만, 앞으로는 모델이 스스로 많은 실험을 제안하고 실행하고 좋은 결과를 통합하는 루프가 가능하다고 본다. 목표는 투입한 컴퓨트당 발견(discoveries per unit of compute)을 최대화하는 것이다.

진행자는 지식 증류(distillation) 논문이 NIPS에서 거절당했던 이야기를 꺼낸다. Jeff Dean은 당시 리뷰어가 “큰 영향이 없을 것”이라고 봤지만, 큰 모델의 능력을 작고 저렴한 모델로 옮기는 것은 대규모 AI 서비스를 위해 매우 중요한 문제였다고 말한다. 그 논문은 arXiv에 올라갔고 널리 쓰이게 되었으며, Gemini Flash 모델을 만드는 데도 이런 접근이 활용된다고 설명한다.

마지막으로 젊은 Jeff Dean이라면 프런티어 랩에 갈지 창업할지 묻자, 그는 개인 선택이라고 답한다. 중요한 질문은 자신이 정말 신경 쓰는 문제인지, 함께 일하고 싶은 동료들과 진전을 만들 수 있는지, 성공했을 때 세상에 긍정적 영향을 줄 수 있는지다. 큰 조직은 훌륭한 동료와 플랫폼이 있고, 작은 스타트업은 위험이 크지만 보람도 크다. 다만 최상의 결과가 나와도 세상이 별로 나아지지 않는 문제라면 시간을 쓰지 말라고 말한다.

좋은 동료에 대해서는 필요한 역량을 갖추고, 함께 있는 것이 즐겁고, 낮은 자아(low ego)를 가진 팀플레이어가 좋다고 말한다. 서로 다른 도구와 기술을 가진 사람들이 작은 팀에서 함께 일하면 혼자서는 못 할 일을 해내고 각자도 성장한다. 그는 커리어를 다양한 기법이 담긴 도구 벨트(tool belt)를 채워가는 과정으로 보라고 조언한다.

끝으로 그는 앞으로 중요한 문제로 더 효율적인 추론 하드웨어, 새로운 하드웨어 접근, 훨씬 데이터 효율적인 머신러닝 알고리즘, 지속 학습(continual learning), 다중 에이전트 상호작용, 더 나은 사회적 대화와 사람 연결 방식을 든다. 그리고 모두가 세상을 더 멋지게 만드는 문제에 도전하길 바란다고 마무리한다.
