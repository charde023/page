큰 그림: 코드를 잘 쓰는 것만으로 개발 전체가 빨라지지는 않는다

이 워크숍의 중심 주장은 단순하다. AI가 코드를 생성하는 능력이 좋아져도, 실제 소프트웨어 개발에는 코드 앞뒤로 해야 할 일이 많이 남는다. 무엇을 만들지 정하고, 관련 문서와 기존 코드를 찾고, 요구사항을 확인하고, 변경 사항을 검토하고, 운영 중 생긴 장애를 처리해야 한다. 발표자들은 코드 도구가 늘어날수록 생산성 향상이 둔화되고 있으며, 더 큰 기회는 이처럼 코드의 왼쪽과 오른쪽, 즉 계획·조정·리뷰·운영에 있다고 주장한다.

여기서 소프트웨어 개발 수명 주기(SDLC)는 아이디어가 작업으로 정리되고, 코드로 구현되고, 검토와 배포를 거쳐 운영되는 전체 흐름을 뜻한다. 에이전트형 시스템은 질문에 답만 하는 AI가 아니라, 티켓을 읽고 자료를 찾고 코드를 실행하며 다음 행동까지 수행하는 시스템이다. 발표자들이 말하는 핵심 변화는 “코드를 대신 작성한다”보다 “개발 흐름의 여러 단계를 연결해 맡긴다”에 가깝다.

읽는 법: 위에서 아래로 읽는다. 자료를 한곳에 모으는 것으로 끝나는 것이 아니라, 필요한 맥락을 각 개발 단계에 공급하고 그 단계의 결과를 다음 단계로 넘기는 구조다. 이는 수량을 나타내는 그래프가 아니라 발표 내용을 연결한 개념도다.

맥락은 자료의 양보다 최신성과 권위를 판단하는 문제다

큰 조직에서는 관련 정보가 한곳에 있지 않다. 현재 동작은 코드에 있고, 요구사항은 Jira나 Confluence에 있으며, 과거 결정의 이유는 문서나 대화에 남아 있을 수 있다. 발표자들은 Atlassian 내부에 회사 전체 기준 15,000개의 저장소가 있다고 말하며, “이 변경은 어디에서 해야 하는가?” 같은 단순한 질문도 답하기 어렵다고 설명한다.

AI Context Engine은 그래프 데이터베이스와 검색을 이용해 Jira, Confluence, Bitbucket과 연결된 외부 도구의 정보를 엮고, 필요한 검색 범위를 좁히려는 구상이다. 특히 발표자들은 현재 동작에 관한 진실은 코드에 있는 경우가 많다고 강조했다. 문서는 작성 당시의 상황을 기록한 스냅숏이므로 오래될 수 있지만, 왜 그런 결정을 했는지는 여전히 유용하다.

그렇다고 최신 코드만 보면 충분한 것도 아니다. 현재 코드는 “무엇이 동작하는가”를 보여주지만, 과거 기록은 “왜 그렇게 만들었는가”를 설명할 수 있다. 따라서 좋은 맥락은 둘 중 하나를 버리는 것이 아니라, 현재 코드와 과거 결정의 역할을 구분해 함께 읽는 것이다.

읽는 법: 위의 두 자료 유형을 비교한 뒤 맨 아래의 판단 단계로 내려간다. 파란 상자는 현재 상태, 갈색 상자는 역사적 이유를 뜻한다. 색만으로 구분하지 않도록 상자 안에 역할을 함께 적었다.

정보가 충돌할 때 에이전트가 자동으로 하나를 진실로 선언하면 위험하다. 발표자들은 사람이 “이 정보는 검증되었다”, “특정 경우에만 맞다”라고 권위를 지정해야 한다고 말했다. Confluence의 검증 표시도 이런 목적으로 언급됐다. 최근 자료를 우선하는 방식은 도움이 되지만, 오래됐다는 이유만으로 여전히 유효한 문서를 버릴 수도 없다.

실행 가능한 작업에는 분명한 합격 조건이 필요하다

에이전트가 티켓을 처리하려면 “무엇을 만들라”는 문장만 있어서는 부족하다. 작업이 끝났다고 판정할 수 있는 합격 조건, 즉 인수 기준(acceptance criteria)이 필요하다. 발표자들은 “Do the thing”처럼 한 줄만 있는 백로그 항목은 가치가 있을 수 있어도 목표가 불분명해 자율 실행할 자신이 없다고 설명했다.

Jira Coding Agent는 작업 항목에 체크리스트 형태의 인수 기준이 있다고 가정한다. 발표자 설명에 따르면 에이전트는 별도 실행 공간인 샌드박스에서 필요한 것을 설치하고 실행하며, 저장소에 실행 방법이 적혀 있으면 브라우저를 열어 검증 단계도 수행할 수 있다. 중요한 점은 실행을 시작하기 전에 요구사항이 충분한지 판단하고, 부족하면 사람에게 보완을 요청한 뒤 다시 판단해야 한다는 것이다.

읽는 법: 맨 위에서 마름모까지 내려간다. 충분함이면 녹색 화살표를 따라 곧바로 샌드박스 실행으로 간다. 부족함이면 오른쪽 사람 보완 상자로 이동하고, 바깥쪽 주황 화살표를 따라 마름모로 돌아가 다시 판단한다. 충분한 작업이 사람 보완 단계를 반드시 거치는 구조가 아니다.

자율성은 자유 방임이 아니라 한도가 있는 조정이다

AutoDev의 구상은 백로그에서 에이전트가 처리할 수 있다고 판단한 작업을 가져와 PR을 만드는 것이다. 그러나 발표자들이 설명한 자율 개발은 무제한 실행이 아니다. 팀이 한 주에 검토할 PR 수, 티켓별·주별 비용, 적용할 저장소, 사용자별 실행 수를 제한하고 사람이 중간에 개입할 수 있어야 한다.

이 한도가 필요한 이유는 에이전트가 많은 코드를 만들수록 사람의 검토 부담도 커지기 때문이다. 발표에서는 하루 50개의 PR을 검토하고 싶어 하는 사람은 없다는 예와, 개인에게 주당 3개 또는 5개의 PR만 배정하는 설정이 언급됐다. 이 수치는 일반적인 권장값이 아니라 발표자가 든 구성 예시다.

리뷰 단계에서도 댓글 수가 많다고 좋은 것은 아니다. AI Reviewer는 버그, 기준 위반, 요구사항을 확인하면서도 낮은 가치의 지적을 걸러내려 한다. 발표자들은 자체 필터링 모델을 사용했을 때 코드 리뷰 의견의 해결률이 40% 정도였고 사람 기준선은 45%였다고 주장했다. 다만 해결률의 정확한 정의, 표본, 측정 기간은 전사에 없다.

또한 저장소 기준은 자연어와 Markdown으로 작성해 여러 저장소에 적용하는 방식으로 소개됐다. 그러나 자연어 기준을 결정적인 예·아니요 검사로 자동 변환하는 기능은 당시 기본 제공되지 않는다고 답했다. 즉, 유연한 AI 리뷰와 항상 같은 결과를 내야 하는 결정적 검사는 구분해야 한다.

실제 워크숍이 보여준 운영상의 교훈

워크숍은 참가자들이 Jira Coding Agent를 직접 써 보는 구성으로 준비됐지만, 현장에서 Wi-Fi 문제가 길게 이어졌다. 이는 발표의 공식 결론은 아니지만, 에이전트 시스템도 네트워크·로그인·실행 환경이 막히면 작동하지 않는다는 현실을 보여준다.

발표자들은 참가자 계정의 보안 수준이 낮다며 GitHub Gist나 Bitbucket Snippet에 공개해도 괜찮은 정보만 입력하라고 경고했다. 기능 검증용 환경과 실제 조직 데이터를 처리하는 환경을 같은 것으로 보면 안 된다는 뜻이다.

제품들의 시행 상태도 하나로 묶어 읽으면 안 된다. Jira Coding Agent는 발표자가 “이미 나와 있다”고 말했지만, AutoDev는 현재 기능처럼 소개되는 부분과 “초기 릴리스가 앞으로 집중할 범위”라는 설명이 함께 나온다. AI Planner도 “나올 제품”으로 소개됐다. 따라서 전체 그림은 제품 비전과 현재 기능, 시험 중인 기능이 섞인 로드맵으로 읽어야 한다.

결국 이 워크숍의 인과는 다음과 같다.

조직 지식이 흩어지고 작업 기준이 모호하다
→ 코드 생성기만 늘리면 잘못된 작업과 리뷰 부담도 함께 늘 수 있다
→ 최신 코드와 역사적 결정을 연결하고, 요구사항을 검증하며, 비용·작업량·승인 한도를 둔다
→ 에이전트가 개발 흐름의 일부를 맡되 사람은 권위 판단과 최종 검토를 유지한다.

여기까지만 이해하면 충분

  • 에이전트형 SDLC의 핵심은 코드 생성 하나가 아니라 계획·구현·리뷰·운영을 조직 맥락으로 연결하는 것이다.
  • 현재 코드는 지금의 동작을, 과거 문서는 결정 이유를 알려주며, 충돌할 때 무엇을 믿을지는 사람이 판단해야 한다.
  • 요구사항과 합격 조건이 충분하면 실행하고, 부족하면 사람이 보완한 뒤 실행 가능성을 다시 판단해야 한다.
  • 자율 실행에는 비용·작업량·검토 부담의 한도와 사람의 승인 절차가 함께 있어야 한다.

한 장면으로 이해하기

백로그에 제목만 있는 작업이 하나 있다. AutoDev가 바로 코드를 만드는 대신 목표와 합격 조건이 부족하다고 표시한다. 사람이 체크리스트를 보완하자 에이전트가 샌드박스에서 구현과 검증을 수행하고 PR을 만든다. 마지막 병합 여부는 검토자가 판단한다.

"작업은 있지만 목표·합격 조건과 관련 맥락이 부족하다" 문제
→ "사람이 요구사항을 보완하고 에이전트가 샌드박스에서 구현·검증한다" 작동 방식
→ "검토 가능한 PR이 만들어지고 사람은 병합·수정·폐기를 결정한다" 결과

비유와 깨지는 지점

품질 검사대가 있는 생산 라인

작업 티켓은 생산 지시서, 조직 맥락은 도면과 작업 이력, 에이전트는 작업 장비, 인수 기준은 품질 검사표에 대응한다. 지시서가 불완전하면 작업을 시작하지 않고 사람에게 돌려보내며, 비용과 작업 수의 한도로 생산량을 제한한다.

비유가 깨지는 지점: 소프트웨어 작업은 같은 제품을 반복 생산하는 일과 다르다. 요구사항 자체가 변할 수 있고, 코드가 검사표를 통과해도 설계 의도나 장기 위험까지 자동으로 옳다고 보장되지는 않는다.

1. 원인

코드 생성 능력이 좋아져도 SDLC 전체의 생산성이 같은 비율로 늘지 않을 수 있는 이유는 무엇인가?

모범 답안 보기

실제 개발에는 작업 선택, 요구사항 정리, 조직 자료 검색, 검증, 리뷰, 운영 대응이 필요하다. 코드가 빨리 생성돼도 요구사항이 모호하거나 리뷰할 PR이 과도하게 쌓이면 병목은 다른 단계로 이동한다. 그래서 발표자들은 코드 앞뒤의 계획·조정·리뷰·운영을 더 큰 기회로 보았다.

2. 대조

현재 코드와 과거 문서 중 하나만 선택해서 에이전트에게 제공하면 안 되는 이유는 무엇인가?

정답을 특정 도구 이름으로 정하지 말고 작업 조건을 본다. 목표와 인수 기준이 구체적인지, 필요한 코드·문서에 접근할 수 있는지, 샌드박스에서 검증 가능한지, 실패 위험이 감당 가능한지, 비용과 실행 횟수에 한도가 있는지, 결과를 검토할 사람이 있는지를 확인한다. 하나라도 불명확하면 바로 자율 실행하지 말고 보완 또는 작은 시험으로 낮춘다.

이번 글의 통찰

1. 맥락 엔진은 검색보다 권위 판단의 문제다

  • [원문] 발표자들은 Jira·Confluence·Bitbucket과 외부 도구를 연결하고, 현재 코드와 과거 결정을 함께 검색하는 Context Engine을 설명했다. 충돌하는 정보에는 사람이 검증 여부와 권위를 지정해야 한다고 말했다.
  • [해석] 에이전트의 품질은 자료의 양만으로 결정되지 않는다. 어떤 자료가 현재 사실이고 어떤 자료가 역사적 이유인지 구분할 수 있어야 한다.
  • [경계] 최근 결과를 우선하고 검증 표시를 활용한다는 설명은 있었지만, 충돌 해결 정확도나 최신성 판정 성능을 입증하는 자료는 제시되지 않았다. 발표 초반에는 AI Reviewer가 Jira·Confluence·SCM·Slack 맥락을 종합한다고 했지만, 후반에는 AI Reviewer가 Context Engine을 “오늘은 많이 사용하지 않으며” 더 끌어오는 실험을 시작한다고 설명했다. 실제 통합 범위와 시행 시점이 불명확하다.

2. 자율성의 단위는 코드가 아니라 검토 가능한 작업이다

  • [원문] AutoDev는 자신 있게 처리할 수 있는 백로그 항목을 골라 PR을 만들고, 요구사항이 부족하면 사람에게 명세 보완을 요청하는 방향으로 설명됐다. 티켓별·주별 비용과 주당 PR 배정량 같은 한도도 언급됐다.
  • [해석] 에이전트가 많이 만드는 것보다 사람이 감당할 수 있는 크기와 속도로 검토 가능한 결과를 내는 것이 중요하다. 작업량 한도는 생산성 방해물이 아니라 리뷰 병목을 막는 제어 장치다.
  • [경계] AutoDev는 이미 동작하는 대시보드·설정처럼 소개된 부분과 “초기 릴리스가 앞으로 집중할 범위”, “우리가 가려는 비전”이라는 설명이 함께 나온다. 현재 제공 기능, 시험 기능, 향후 계획의 경계가 전사만으로 확정되지 않는다. 주당 3개 또는 5개 PR은 설정 예시이며 보편적 권장값이 아니다.

3. 제품 주장과 측정 근거를 분리해서 읽어야 한다

  • [원문] 발표자들은 AI Reviewer 의견 해결률이 약 40%이고 사람 기준선은 45%라고 말했다. 비용과 ROI 대시보드, 여러 모델, SCM 지원, 워크숍 계정 운영도 설명했다.
  • [해석] 에이전트 도구를 평가할 때는 기능 목록보다 지표의 정의, 비용 귀속, 지원 범위, 사람이 실제로 줄인 일을 확인해야 한다.
  • [경계]
  • 40%와 45%는 해결률의 분모, 표본, 기간, 리뷰 난이도가 없어 독립적으로 검증할 수 없다.
  • 결제 설명에서 “자체 API 키를 사용한다”는 답과 “Atlassian 크레딧이며 사용량 기반”이라는 답이 이어져 실제 과금 구조가 충돌한다.
  • 모델은 Anthropic·OpenAI 모델을 지원한다고 했지만 Gemini 지원 여부는 발표자가 기억하지 못했다.
  • “모든 SCM 플랫폼”을 지원한다고 말하면서 GitHub, GitLab, Bitbucket Cloud만 이름을 들었다. 보편 지원 범위는 확인되지 않았다.
  • 데모 계정을 세션 종료 때 지운다는 설명과 워크숍 환경을 행사 기간 동안 열어 둘 수 있다는 설명이 함께 나왔다. 서로 다른 환경인지 전사만으로 확정할 수 없다.
  • 행사명은 전사에서 AI Engineers World Fair와 AI Engineers World's Fair 형태로 달리 발화된다.
  • META는 원본 영상 링크를 확인하지 못했고 화자 이름과 SNS를 기준으로 출처를 추정했다고 명시한다. original_creator의 Andy Wong과 original_affiliation의 Andrei Bocan, Shane Wolf (Atlassian)은 그 추정 메타데이터를 그대로 보존한 값이며, 독립 확인된 원작자·소속 표기가 아니다.

1. 도입과 문제 정의

Andy Wong은 Atlassian에서 4년, AI 분야에서 2년 반 일했다고 소개했다. 함께한 사람으로 Dev AI 분야의 매니저 Shane Wolf와 Andrei Bocan을 소개했다.

발표자는 약 1년 반 동안 Atlassian에서 만든 도구들을 개괄하며, AI 코딩 도구가 많아질수록 생산성 향상이 둔화되고 있다고 주장했다. 더 큰 기회는 코드 앞뒤의 계획, 오케스트레이션, 코드 리뷰와 운영에 있다고 보았다.

제품군으로 Teamwork Graph, AI Planner, AI AutoDev, Reviewer, SRE와 그 중심의 AI Context Engine을 제시했다.

2. Jira Coding Agent와 자동화

Jira Coding Agent는 Jira 티켓, Confluence 문서, 이메일과 Slack 메시지 등에서 맥락을 수집해 특정 작업을 계획하고 구현하는 에이전트로 소개됐다. PR과의 상호작용은 Jira 생태계와 클라우드 환경에서 이뤄진다고 설명했다.

작업을 Atlassian 에이전트뿐 아니라 Claude, Cursor, Codex 같은 선호 에이전트에 배정할 수 있다고 말했다. Jira 자동화 조건이 충족되면 선택한 에이전트로 코드를 생성하는 흐름도 언급했다.

발표자는 Jira Coding Agent가 이미 출시됐다고 답했다. 모델은 상위 하네스에서 선택하고, 특정 스킬이나 하위 에이전트에 다른 모델을 지정할 수 있다고 설명했다. 자동으로 난이도에 맞는 모델을 고르는 스마트 라우팅은 당시 제공하지 않으며 AutoDev에서 작업 중이라고 말했다.

3. AI Reviewer와 저장소 기준

AI Reviewer는 PR에서 버그를 찾고, 기준을 적용하며, 요구사항을 확인하려는 도구로 소개됐다. 초반에는 Jira, Confluence, SCM, Slack의 자료를 종합해 리뷰한다고 설명했지만, 후반에는 AI Reviewer가 Context Engine을 많이 사용하지 않으며 더 많은 맥락을 끌어오는 실험을 시작했다고 말했다.

기준은 자연어와 Markdown으로 작성하고 대상 저장소 전체, 직접 선택한 저장소 또는 이름 패턴이 맞는 저장소에 적용하는 방식으로 시연됐다. GitHub, GitLab, Bitbucket Cloud가 이름으로 언급됐다.

발표자는 낮은 가치의 리뷰 댓글을 자체 모델로 걸러냈으며, 의견 해결률이 약 40%로 사람 기준선 45%에 가깝다고 주장했다. 측정 정의와 표본은 제시되지 않았다.

기준을 결정적인 예·아니요 검사에 연결하는 기능에 대한 질문에는 기본 제공되지 않으며 Markdown 안에서 구현해야 할 것 같다고 답했다. 관련 팀에 사용 사례를 전달하겠다고 말했다.

4. AI Context Engine과 Code Context

Context Engine은 Atlassian 내부의 여러 그래프 데이터베이스를 통해 Jira, Confluence, Bitbucket의 데이터를 연결하며 Notion과 Slack 같은 외부 제품도 연동한다고 설명됐다. 연결은 제품 사용 중 추론하거나 사용자가 명시적으로 만들 수 있다고 했다.

발표자는 대규모 저장소를 하나의 모노레포로 합치면 에이전트가 맥락에 접근하기 쉬워지지만, 속도 저하와 자체 도구 구축 부채가 생긴다고 설명했다. Code Context Engine은 제품별 저장소를 그대로 두고도 필요한 코드를 즉시 찾아 모노레포처럼 느끼게 하려는 접근이다.

Shane은 Atlassian 전사에 15,000개의 저장소가 있다고 말했다. 검색 공간을 먼저 좁히고 관련 코드로 확장해 “어디를 변경해야 하는가?”, “어떤 서비스가 이 서비스를 사용하는가?” 같은 질문에 답하려 한다고 설명했다.

문서는 오래되고 부정확할 수 있지만, 과거 결정을 되풀이하지 않도록 선택 이유를 제공한다. 현재 코드는 지금의 사실을, 과거 기록은 결정 당시의 이유를 제공한다는 설명이다.

5. 오래된 정보와 권위

한 질문자는 Confluence를 10년 또는 15년 사용한 조직의 오래된 자료를 정리해야 하는지 물었다. 발표자는 최근 결과를 우선하는 방식 때문에 경험상 큰 문제는 없었다고 답했다.

그러나 오래된 문서라도 여전히 최신 기준일 수 있으므로 단순히 나이만으로 제거해서는 안 된다고 했다. Confluence의 검증 표시를 사용해 여전히 유효한 자료임을 나타낼 수 있다고 설명했다.

정보 충돌에는 사람이 “검증된 사실”, “우연히 맞는 정보”, “특정 경우에만 맞는 정보”를 판단해야 한다고 말했다. 자동화된 정보가 자동으로 권위를 얻는 상황도 위험으로 언급했다.

6. 요구사항 검증과 샌드박스

Jira Coding Agent가 처리하는 작업 항목에는 인수 기준 체크리스트가 있어야 한다고 설명했다. 에이전트가 작업을 마쳤다고 판단하면 그 기준을 검증한다.

에이전트는 Atlassian의 전용 샌드박스인 컨테이너에서 실행된다. Docker를 사용할 수 있고, 저장소에 실행 방법이 적혀 있으면 필요한 설치와 실행, 브라우저 검증을 수행할 수 있다고 말했다.

다만 샌드박스 관련 질문의 일부가 전사에서 누락돼 있으며, “그 능력은 아직 없다”는 답이 정확히 어떤 기능을 가리키는지는 확인되지 않는다.

7. AutoDev의 목표와 안전장치

AutoDev는 백로그에서 에이전트가 자율적으로 처리할 수 있다고 판단한 작업을 찾아 PR을 만들려는 오케스트레이션 제품으로 소개됐다. 초기 릴리스는 엔지니어링팀이 기능 개발에 집중하도록 일부 작업 부담을 돌려주는 데 초점을 맞춘다고 했다.

한 줄짜리 “Do the thing” 같은 항목은 목표가 불명확하므로 바로 실행하기 어렵다. 사람이 요구사항을 보완한 뒤 충분한 명세가 되면 작업을 시작한다. 작업 완료 뒤에는 사람이 PR을 검토한다.

리뷰 단계가 방치되는 문제를 줄이기 위해 적절한 시점에 Slack으로 사람을 호출하는 흐름을 초기 릴리스의 주요 수단으로 설명했다.

발표자들은 팀이 하루 50개 PR을 검토하고 싶어 하지는 않을 것이라고 말했다. 개인별 주당 3개 또는 5개 PR처럼 작업 진행량을 제한하는 설정을 예로 들었다. 티켓별·주별 비용 한도도 필요하다고 설명했다.

기존 코드 전체를 새 기준에 맞추는 경우 한 번에 절반을 바꾸는 대형 PR 대신, 작은 PR을 점진적으로 만들어 검토 부담과 변경량을 관리하려는 비전도 제시됐다.

8. AI Planner, AI SRE와 단계적 작업

AI Planner는 아이디어를 입력받아 Context Engine으로 저장소와 관련 자료를 확인하고, 구현 가능성과 필요한 단계를 제시하는 제품으로 소개됐다. 발표자는 “나올 제품”이라고 표현했으므로 완전한 현재 기능으로 확정할 수 없다.

AI SRE는 과거 장애 기록에서 맥락을 가져와 장애의 근본 원인 후보와 완화 방법을 제안하려는 제품으로 소개됐다. Slack에서 영향 범위와 가능한 대응 단계를 요약하는 구상이 설명됐다.

Jira Coding Agent에 Epic을 작은 작업으로 나누게 하고, 자동화 규칙으로 각 작업에 새 세션을 시작하는 흐름도 가능하다고 답했다. 기초 작업, V0, V1, V2처럼 여러 단계로 계속 분해하는 것도 막는 요소는 없다고 했지만, 실제 대규모 실행 결과는 제시하지 않았다.

9. 워크숍 운영과 보안 경고

참가자들은 배포받은 번호로 student와 번호를 조합한 계정을 사용하도록 안내받았다. 현장 Wi-Fi 문제로 실습이 반복해서 지연됐다.

발표자는 계정 보안이 강하지 않으므로 GitHub Gist나 Bitbucket Snippet에 올려도 괜찮은 정보만 입력하라고 경고했다.

한편 계정을 세션 종료 때 지운다는 설명과 워크숍 환경을 AI Engineer World’s Fair 기간 동안 열어 둘 수 있다는 답이 함께 있었다. 두 설명이 같은 환경을 가리키는지는 명확하지 않다.

그녀가 돌아다니면서 숫자를 나눠 줄 겁니다. 처음에는 조금 이상하겠지만, 소개를 마치고 나면 훨씬 더 잘 이해하실 수 있을 겁니다.

먼저 소개 슬라이드부터 빠르게 시작하겠습니다. AI Engineers World’s Fair: We want to build에 와 있으니, 이 부분은 아주 빠르게 진행하고 싶습니다. 지난 1년 반 정도 동안 Atlassian에서 개발해 온 것들을 간단히 소개해서, Atlassian 자체에서 제공할 모든 도구를 전체적으로 보여 드리고자 합니다.

아시다시피 AI 에이전트(agent)는 소프트웨어 개발 수명 주기를 크게 바꿨습니다. 시간이 지나면서 AI 코딩 도구가 더 많아지고 있지만, 이러한 도구에서 얻는 생산성 향상은 점차 둔화되고 있습니다.

도구가 점점 더 많이 출시되는 상황에서 Atlassian은 코드의 왼쪽과 오른쪽에 있는 모든 영역, 즉 계획 수립, 오케스트레이션, 코드 리뷰 과정, 운영에 가장 큰 기회가 있다고 생각합니다.

그래서 소프트웨어 개발 수명 주기에서 상대적으로 눈에 잘 띄지 않는 부분을 많이 개발해 왔습니다.

Teamwork Graph가 출시될 예정이고, 코드의 왼쪽과 오른쪽을 지원하기 위해 AI Planner, AI AutoDev, Reviewer, SRE 같은 여러 에이전트도 개발하려고 시도하고 있습니다. 이 모든 것의 중심에는 AI Context Engine이라고 부르는 것이 있습니다.

이 도구들을 빠르게 살펴보면, 오늘 주로 테스트할 것은 Jira Coding Agent입니다. Atlassian의 네이티브 코딩 에이전트로, Atlassian 생태계 내 조직에 대한 깊은 지식을 갖고 있습니다.

이는 엔터프라이즈 컨텍스트를 깊이 이해하는 에이전트로, Atlassian 생태계 내의 모든 것을 깊이 있게 파악합니다. Jira 티켓이나 Confluence 문서뿐 아니라 이메일과 Slack 메시지도 읽어, 여러분이 가진 특정 Jira 티켓을 계획하고 구현하는 데 필요한 모든 컨텍스트를 수집합니다.

Jira Coding Agent 자체에서 Jira 생태계 내의 풀 리퀘스트(pull request)와 상호작용할 수 있습니다. 모든 내용은 클라우드에서 유지되고 편집됩니다.

또한 작업을 특정 에이전트에 직접 할당할 수도 있습니다. Jira Coding Agent를 사용하고 싶지 않다면 괜찮습니다. Claude, Cursor, Codex 등 개인적으로 선호하는 에이전트에 작업을 할당할 수도 있습니다. 그 과정에서 Jira 티켓을 Jira 에이전트에 할당할 수도 있습니다.

마지막으로 SDLC 자동화도 있습니다. 아시다시피 Jira 자체에 자동화 프로세스가 있습니다. 특정 조건이 충족되면 Jira Coding Agent나 여러분이 직접 선택한 에이전트를 사용해 코드를 생성할 수 있습니다.

코드의 오른쪽으로 더 이동하면 AI Reviewer가 있습니다. 오늘날 업계에서 볼 수 있는 많은 도구와 비슷합니다. 풀 리퀘스트를 검토하고, 버그를 찾아내며, 표준을 적용하고, 풀 리퀘스트를 생성할 때마다 요구 사항을 확인하는 리뷰어 에이전트를 구현하려고 합니다.

리뷰는 코드에만 국한되지 않습니다. 다시 말해 Jira, Confluence, 사용하는 SCM, Slack에 있는 모든 컨텍스트를 가져와 PR이 구현해야 하는 내용을 종합적으로 파악하고, 이를 기반으로 리뷰를 제공하는 무언가를 만들려고 합니다.

그 위에는 중앙 집중식으로 관리되는 표준이 있습니다. 모든 팀과 조직에는 각 저장소에 적용하고 싶은 자체 표준이 있습니다. 이것 역시 번거로운 작업입니다. 표준 기능을 통해 특정 저장소의 모든 풀 리퀘스트에 이러한 표준을 훨씬 쉽게 적용할 수 있도록 관리자와 소프트웨어 엔지니어를 지원하려고 합니다.

또한 이 기능은 모든 SCM 플랫폼에서 작동합니다. GitHub, GitLab, Bitbucket Cloud 중 무엇을 사용하든 풀 리퀘스트에 표준을 적용할 수 있습니다.

Atlassian에서 AI Reviewer로 해결하려는 문제 중 하나는 코드 리뷰 과정 전체에서 발생하는 노이즈를 줄이는 것입니다. 일부 코드 리뷰 과정은 지나치게 사소한 부분을 지적하거나 가치가 낮은 댓글을 너무 많이 남긴다고 생각합니다. Dev AI에서는 이러한 댓글을 필터링하기 위해 몇 가지 모델을 직접 학습시켰습니다.

가치가 낮은 댓글이나 우리가 노이즈라고 판단한 댓글을 예로 들어 보겠습니다. 이러한 모델을 사용해 풀 리퀘스트 댓글에서 불필요한 댓글을 걸러 냅니다.

전체적으로 댓글 해결의 품질이 더 높아졌습니다. 아래에서 보시다시피 이러한 모델을 사용해 약 40%의 코드 해결률을 달성했으며, 이는 인간 기준선인 45%에 상당히 가까운 수치입니다.

늘 그렇듯이 이러한 도구들이 얼마나 큰 영향을 미치는지 측정하고 확인할 수 있습니다. Atlassian에서는 다양한 도구를 위한 대시보드를 많이 만들고 있습니다. 실행한 리뷰나 에이전트의 수를 확인해 Dev AI 분야의 모든 도구가 제공하는 가치를 파악할 수 있도록 하기 위해서입니다.

최근 구현하고 있는 마지막 제품 몇 가지로 넘어가겠습니다. 그중 하나가 AI AutoDev입니다. 무엇을 할 수 있는지는 이름만 봐도 꽤 분명합니다. Jira 보드를 살펴보고 자율적으로 실행할 수 있는 티켓을 식별합니다.

모든 표준 이니셔티브를 적용한 다음 리뷰할 준비가 된 풀 리퀘스트를 생성합니다. 이 모든 과정은 Jira 생태계 자체에서 트리거할 수 있습니다. 월별로 사용하고 싶은 최대 크레딧 수, 각 사용자가 AutoDev를 실행할 수 있는 최대 티켓 수, 실행할 저장소 등 다양한 설정을 구성할 수 있습니다. Jira 조직 내 모든 저장소에서 실행할 수도 있습니다.

늘 그렇듯이 모든 AutoDev 실행 내역과 작동 현황, 리뷰가 필요한 AutoDev 풀 리퀘스트 수, 아직 요구 사항이 필요한 항목 수를 보여 주는 대시보드가 있습니다. 엔지니어와 팀이 AutoDev의 전반적인 성능을 이해할 수 있도록 가능한 한 많은 메타데이터를 제공하려고 합니다.
