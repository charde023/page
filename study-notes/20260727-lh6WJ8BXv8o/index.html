핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
블라인드 루프(blind loop)의 위험 AI 에이전트가 4만 줄짜리 PR처럼 사람이 검토하기 어려운 결과를 만들 수 있음 루프는 강력하지만, 측정과 제어 없이 돌리면 위험하다
제어 루프(control loop) 온도조절기, 쿠버네티스 오토스케일링처럼 복잡한 시스템을 안정적으로 바꾸는 방식 센서, 목표 상태, 컨트롤러, 액추에이터, 피드백으로 구성된다
센서(sensor) 현재 코드베이스의 문제를 측정해야 다음 행동을 정할 수 있음 ESLint, ast-grep, 에이전트, 텔레메트리 등이 센서가 될 수 있다
컨트롤러(controller) 너무 큰 변경이나 잘못된 변경을 막는 핵심 장치 “다음에 무엇을 얼마나 바꿀지” 결정한다
액추에이터(actuator) 실제 코드를 고치는 실행 주체 코딩 에이전트와 스킬(skill)을 조합해 작은 변경을 수행한다
골든 패턴(golden pattern) 에이전트가 인터넷의 일반 예시가 아니라 팀의 코드 스타일을 따라 하게 함 사람이 직접 만든 모범 예시를 에이전트에게 제공한다
흐름 제어(flow control) PR이 쌓이고 충돌하는 문제를 방지 루프별로 열린 PR이 있으면 새 작업을 만들지 않는다
사람을 루프 위에 두기(human on the loop) AI가 잘못 갔을 때 낮은 마찰로 방향을 바꿀 수 있음 피드백 파일과 PR 댓글 트리거로 루프를 재조정한다

내가 모를 만한 것 / 처음 보는 것

  • 제어 이론(control theory) — 동적인 시스템을 목표 상태로 안정적으로 이동시키는 공학 분야. 여기서는 코드베이스를 안정적으로 개선하는 모델로 사용된다.
  • 설정값(set point) — 시스템이 도달해야 하는 원하는 상태. 예: “모든 RPC API가 Effect로 마이그레이션된 상태”.
  • 측정 오차(measured error) — 현재 상태와 목표 상태의 차이. 예: 아직 마이그레이션되지 않은 프로시저 목록.
  • 액추에이터(actuator) — 컨트롤러가 정한 변경을 실제 시스템에 적용하는 실행 장치. 여기서는 코딩 에이전트.
  • ast-grep — 코드의 추상 구문 트리(AST)를 기준으로 패턴을 찾는 도구. 단순 문자열 검색보다 코드 구조를 잘 이해한다.
  • Effect — TypeScript 생태계의 함수형 효과 시스템 라이브러리. 에러 처리, 비동기, 의존성, 계측 등을 구조화하는 데 사용된다.
  • 골든 패턴(golden pattern) — 에이전트가 따라 할 수 있도록 사람이 직접 만든 좋은 코드 예시.
  • 방해 완화 장치(disturbance dampener) — 팀원이 새로 나쁜 패턴을 추가하는 등 루프의 진전을 되돌리는 일을 막는 장치.
  • 슬래시 이터레이트(/iterate) — PR 댓글에 남겨 루프가 다시 실행되도록 하는 트리거 예시.
  • 읽기 전용 코드(read-only code) — 생성은 됐지만 사람이 실제로 읽고 이해하지 않는 코드라는 비판적 표현.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 4만 줄짜리 PR — 프롬프트와 반복문만으로 코딩 에이전트를 돌릴 때 생기는 대표적 실패 사례로 제시된다.
  2. 6개월 — Claude Code의 터미널 깜빡임 문제를 고치는 데 걸린 기간으로 언급된다. AI 루프가 항상 빠르고 안정적이지 않다는 근거다.
  3. 위반 항목당 약 50개 키 — ast-grep 결과가 너무 상세하므로, 실제 루프에서는 필요한 4개 정도로 필터링하고 결정적으로 정렬한다고 말한다.
  4. 하루 한 번 실행 — GitHub Actions 등 CI에서 루프를 하루 한 번 돌려 매일 아침 작은 PR 하나를 받는 운영 방식을 제안한다.
  5. PR 라벨(label) — 각 루프가 자신이 만든 PR을 식별하기 위해 라벨을 붙인다. 피드백 수집과 중복 방지에 필요하다.
  6. 열린 PR이 있으면 루프 중단 — 사람이 이전 결과를 아직 리뷰하지 않았다면 새 PR을 만들지 않는다.
  7. RPC 프로시저 150개 — HumanLayer 내부에서 마이그레이션해야 하는 규모. 하나씩 하면 약 6개월이 걸릴 수 있다고 말한다.
  8. 속도 높이는 방법 — 한 번에 3개나 5개를 선택하거나, 각각 별도 구현 단계로 나누거나, 워크플로를 4번 실행해 팀원 4명에게 나눠 줄 수 있다.
  9. GitHub Actions/GitLab/CircleCI 활용 — 별도 클러스터를 만들지 말고 기존 CI의 코드 접근, 시크릿 접근, 스케줄링 기능을 쓰라고 한다.
  10. 피드백 파일은 마크다운으로 버전 관리 — 에이전트에게 주는 지시를 코드 저장소 안에서 추적, 변경, 되돌리기 가능하게 만든다.

# 섹션 요지
1 문제 제기 프롬프트와 루프만으로는 사람이 읽기 어려운 거대 PR이 나온다
2 제어 이론 코드베이스도 센서, 목표, 컨트롤러, 액추에이터로 안정적으로 바꿀 수 있다
3 코딩 루프 설계 측정 가능한 문제를 찾고, 작은 변경을 적용하고, 피드백을 받아야 한다
4 HumanLayer 사례 RPC API를 Effect로 점진 마이그레이션하는 루프를 만든다
5 센서 구축 ast-grep으로 마이그레이션 안 된 코드를 찾고 정렬한다
6 컨트롤러 설계 어떤 프로시저를 먼저 바꿀지 위험과 효과를 기준으로 고른다
7 액추에이터 설계 에이전트와 스킬, 골든 패턴으로 실제 코드를 수정한다
8 CI 운영 하루 한 번 작은 PR을 만들고, 피드백과 흐름 제어로 관리한다
9 확장 한 번에 여러 작업을 선택하거나 병렬로 나눠 속도를 높인다

1. 문제: 루프가 강력해도 “눈먼 반복”은 위험하다

화자는 최근 개발자들이 모두 루프(loop)를 만들고 있지만, 많은 방식이 잘못됐다고 말한다. 업계에는 “프롬프트(prompt)와 반복문(loop)을 코딩 에이전트(coding agent)에 연결하면 소프트웨어를 만들 수 있다”는 분위기가 있다.

하지만 현실에서는 검증기(verifier)를 많이 붙이고, 코드 리뷰 에이전트를 여러 개 둬도 결국 사람이 읽기 싫은 4만 줄짜리 PR이 만들어질 수 있다.

화자는 Ralph 같은 도구 자체를 비난하는 것은 아니라고 선을 긋는다. Ralph는 개인 프로젝트나 중요도가 낮은 시스템에는 잘 맞을 수 있다. 그러나 대부분의 개발자는 팀에서 일하고, 실제 고객, 규제, SLA(service level agreement)가 있는 시스템을 다룬다. 이런 환경에서는 “일단 4만 줄을 프로덕션에 밀어 넣기” 방식이 통하지 않는다.

핵심은 루프를 버리는 것이 아니라, 현실의 코드베이스에서 작동하는 루프를 설계하는 것이다.

2. 현재 AI 코딩 담론에 대한 비판

OpenCode, Claude Code 같은 도구와 여러 프런티어 랩(frontier lab)의 주장은 “앞으로는 에이전트가 코드를 만들고, 리뷰하고, 병합하고, 버그를 고칠 것”에 가깝다.

심지어 에이전트가 루프를 만들고, 그 루프가 다시 에이전트를 프롬프트하는 식으로 끝없이 자동화될 수 있다는 식의 이야기도 나온다.

화자는 이런 흐름이 흥미롭지만, 현실적인 문제가 있다고 본다.

첫째, 너무 많은 코드가 생성되어 사람이 다 읽을 수 없다. 그러다 보면 “어차피 못 읽으니 아예 읽지 말자”는 분위기가 생긴다.

둘째, 비용이 크다. 프런티어 랩처럼 토큰 예산이 무제한이 아니라면, 이런 방식은 매우 비싸다.

셋째, 나쁜 코드는 에이전트 시대에 더 비싸다. AI가 빠르게 코드를 늘릴수록 유지보수 비용과 품질 문제가 더 커진다.

따라서 화자의 결론은 단순하다.

루프를 만들되, 코드를 읽을 수 있게 만들어야 한다.

3. 제어 이론으로 보는 코드베이스

화자는 루프 설계를 설명하기 위해 제어 이론(control theory)을 가져온다.

제어 이론은 동적인 시스템을 원하는 안정 상태 또는 최적 상태로 이동시키는 방법이다. 여기서 동적인 시스템은 코드베이스(codebase)다.

구성 요소는 다음과 같다.

  • 센서(sensor): 현재 상태를 측정한다.
  • 설정값(set point): 원하는 목표 상태다.
  • 측정 오차(measured error): 현재 상태와 목표 상태의 차이다.
  • 컨트롤러(controller): 오차를 읽고, 어떤 작은 변경을 적용할지 결정한다.
  • 제어 신호(control signal): 컨트롤러가 액추에이터에게 보내는 작업 지시다.
  • 액추에이터(actuator): 실제 시스템에 변경을 적용한다.
  • 피드백(feedback): 변경 후 다시 측정해 다음 반복을 결정한다.

이 모델은 복잡해 보이지만 일상에도 많다. 온도조절기(thermostat), 쿠버네티스 오토스케일링(Kubernetes autoscaling), Infrastructure as Code, Postgres auto-vacuum, React virtual DOM 등이 모두 제어 루프와 유사한 방식으로 작동한다.

중요한 점은 제어 루프가 시스템을 한 번에 끝 상태로 밀어붙이지 않는다는 것이다. 대신 작은 변경을 반복해서 적용한다. 이 방식은 과조향(oversteering)을 막고 시스템 불안정을 줄인다.

4. 블라인드 Ralph 루프와 에이전틱 제어 루프

화자는 단순 bash 반복문처럼 동작하는 루프를 “블라인드 Ralph 루프(blind Ralph loop)”라고 부른다. 이런 루프는 큰 변경을 한 번에 만들 가능성이 높고, 사람이 리뷰하기 어려운 PR을 만든다.

반대로 좋은 루프는 제어 이론을 적용한다.

코딩에 적용하려면 먼저 코드베이스의 특정 속성에 대한 목표 상태를 정의해야 한다. 예를 들면 “모든 RPC API가 Effect로 작성되어야 한다”가 목표 상태가 될 수 있다.

그다음 센서를 만든다. 센서는 결정론적(deterministic)일 수도 있고 비결정론적(nondeterministic)일 수도 있다.

  • 결정론적 센서: ESLint 규칙, ast-grep, Packwerk 등
  • 비결정론적 센서: 에이전트와 자연어 규칙
  • 혼합형 센서: 정적 분석과 에이전트 판단을 함께 사용

Aiden Bai의 React Doctor는 센서와 컨트롤러가 섞인 예다. React 코드의 문제를 찾아줄 뿐 아니라, 무엇을 먼저 고칠지와 어떻게 고칠지도 제안한다.

5. HumanLayer 사례: RPC API를 Effect로 점진 마이그레이션

HumanLayer에서는 내부적으로 RPC API를 Effect로 점진 마이그레이션하는 루프를 사용한다.

Effect는 TypeScript에서 에러 처리, 비동기 흐름, 계측 등을 더 구조적으로 다루게 해주는 라이브러리다. 문법은 독특하지만, HumanLayer 팀은 경합 조건(race-prone)이 있는 코드에 써보고 유용하다고 판단해 나머지 코드베이스에도 확장하고 있다.

여기서 목표 상태는 “RPC 프로시저들이 Effect 기반으로 마이그레이션된 상태”다.

루프는 다음 순서로 작동한다.

  1. 아직 마이그레이션되지 않은 프로시저를 찾는다.
  2. 그중 하나 또는 소수를 선택한다.
  3. 에이전트가 골든 패턴을 참고해 마이그레이션한다.
  4. PR을 만든다.
  5. 사람이 리뷰한다.
  6. 피드백을 루프에 반영한다.
  7. 다시 반복한다.

6. 센서: ast-grep으로 안 바뀐 코드를 찾는다

센서는 마이그레이션되지 않은 프로시저를 찾는 역할을 한다.

단순히 grep이나 ripgrep을 쓸 수도 있지만, 화자는 ast-grep을 추천한다. ast-grep은 코드의 구조를 기준으로 패턴을 찾기 때문에 단순 문자열 검색보다 강력하다.

특히 TypeScript 설정이나 ESLint 규칙과 별개로 동작한다는 점이 장점이다. 화자는 Claude가 인라인 주석으로 TypeScript나 ESLint 규칙을 비활성화하는 경우를 언급한다. ast-grep은 이런 회피를 줄이는 데 도움이 된다.

ast-grep으로 규칙을 만들면 다음을 할 수 있다.

  • 특정 패턴의 안 바뀐 프로시저 찾기
  • 시간이 지나면서 제거하고 싶은 패턴 규칙 추가
  • include/exclude 경로를 세밀하게 지정
  • 다국어 모노레포(multilingual monorepo)에서도 사용

다만 결과가 너무 자세할 수 있다. 위반 항목마다 약 50개 키가 나오므로, 실제 루프에서는 필요한 4개 정도로 줄이고 결정적으로 정렬한다.

7. 새 나쁜 코드 유입을 막는 장치

점진 마이그레이션을 시작하기 전에 먼저 해야 할 일이 있다. 기존 코드를 하나씩 바꾸는 동안 팀원이 새로 마이그레이션 안 된 코드를 추가하면 안 된다.

그래서 화자는 메인 브랜치(main)에서 전체 스캔을 한 번 실행하고, 위반 목록을 결정적으로 정렬한 뒤 버전 관리에 넣는 방식을 설명한다. 이후 새 PR이 들어올 때 브랜치가 새로운 미마이그레이션 프로시저를 추가했는지 확인할 수 있다.

이것은 전통적 제어 루프의 구성 요소와 정확히 일치하지는 않지만, 화자는 이를 방해 완화 장치(disturbance dampener)처럼 볼 수 있다고 말한다.

즉, 루프가 개선한 것을 팀의 새 코드가 되돌리지 못하게 막는 장치다.

8. 컨트롤러: 다음에 무엇을 고칠지 정한다

컨트롤러는 센서가 찾은 문제 중 무엇을 고칠지 정한다.

가장 단순한 방식은 위반 목록의 첫 번째 항목을 고르는 것이다. bash와 jq로도 가능하다.

조금 더 나은 방식은 ast-grep으로 가장 작은 미마이그레이션 프로시저를 찾아 고르는 것이다. 작은 변경부터 하면 위험이 줄어든다.

에이전트에게 선택을 맡길 수도 있지만, 화자는 결정론적으로 처리할 수 있는 일에는 굳이 에이전트를 보내지 말라고 말한다.

더 발전된 방식은 텔레메트리(telemetry)를 보는 것이다. 예를 들어 다음 정보를 함께 고려할 수 있다.

  • 에러가 가장 많이 나는 프로시저
  • 계측(instrumentation)이 가장 부족한 프로시저
  • APM(application performance monitoring)에 빈틈이 있는 프로시저

이렇게 하면 단순한 1:1 마이그레이션이 아니라, 실제로 에러 처리와 관측 가능성(observability)을 개선하는 변경을 만들 수 있다.

9. 액추에이터: 에이전트와 스킬로 코드를 바꾼다

액추에이터는 실제 변경을 적용하는 부분이다. 여기서는 코딩 에이전트와 스킬(skill)의 조합이다.

화자는 어떤 CLI 코딩 에이전트를 쓰든 상관없지만, 스킬 작성에 시간을 많이 써야 한다고 말한다. 단, 처음부터 완벽하게 만들려고 하기보다는 실행하면서 반복적으로 개선해야 한다.

HumanLayer에서는 에이전트를 풀어놓기 전에 골든 패턴(golden pattern)을 손으로 만든다. 골든 패턴은 팀이 원하는 스타일로 직접 작성한 관용적 예시다.

에이전트는 결국 패턴 복제기(pattern replicator)에 가깝다. 좋은 예시를 주지 않으면 문서나 인터넷에서 본 일반적인 방식으로 코드를 만들 가능성이 높다.

실행 흐름은 다음과 같다.

  1. 스킬과 제어 신호를 에이전트에 전달한다.
  2. 스킬에는 응답 템플릿(response template)을 포함한다.
  3. 에이전트가 코드를 수정한다.
  4. 마지막 응답을 만든다.
  5. 시스템이 결정론적으로 커밋, 푸시, PR 생성을 수행한다.
  6. 에이전트의 마지막 메시지를 PR 설명으로 사용한다.

10. CI에 연결해 하루 한 번 작은 PR 만들기

화자는 루프 실행 환경으로 GitHub Actions, GitLab, CircleCI 같은 기존 CI를 추천한다.

이유는 간단하다.

  • 코드에 접근할 수 있다.
  • 시크릿(secrets)에 접근할 수 있다.
  • 스케줄링과 수동 실행(dispatch) 기능이 있다.
  • 별도의 클러스터를 새로 만들 필요가 없다.

워크플로는 한 번의 루프 반복을 실행한다.

  1. 감지(sense)
  2. 제어(control)
  3. 실행(actuate)
  4. PR 생성

이 워크플로를 하루 한 번 실행하면, 매일 아침 낮은 위험의 작은 PR 하나를 받을 수 있다.

11. 사람의 피드백을 낮은 마찰로 반영하기

처음 HumanLayer가 이 루프를 돌렸을 때는 오히려 답답했다고 한다. 스킬을 계속 수정해야 했고, 브랜치를 체크아웃하고, 코드와 스킬을 고치고, 커밋하고 푸시해야 했다. 루프의 마찰이 너무 컸다.

이를 해결하기 위해 화자는 피드백 파일(feedback file)을 제안한다.

방법은 다음과 같다.

  • 저장소에 마크다운 피드백 파일을 둔다.
  • 이 파일을 버전 관리한다.
  • 액추에이터 에이전트가 실행될 때마다 이 파일을 컨텍스트에 넣는다.
  • PR에는 루프를 식별하는 라벨을 붙인다.
  • 사용자가 PR에 /iterate 댓글을 남기면 워크플로가 다시 실행된다.
  • 워크플로는 PR 설명, diff, 댓글, 리뷰 댓글 등을 모두 에이전트 컨텍스트에 넣는다.
  • 에이전트는 코드를 고치고, 동시에 피드백 파일도 업데이트한다.

이 방식의 장점은 피드백이 저장소 안에서 추적된다는 것이다. 시간이 지나며 어떻게 지시가 바뀌었는지 볼 수 있고, 필요하면 되돌릴 수도 있다.

12. 흐름 제어: PR이 쌓이지 않게 하기

또 다른 문제는 PR이 쌓이는 것이다. 팀이 고객사 방문, 출장, 발표 준비 등으로 며칠간 리뷰를 못 하면 루프가 계속 PR을 만든다. 그러면 작업이 중복되고 충돌이 생기며, 결국 중요하지 않은 잡무가 쌓인다.

해결책은 간단하다.

각 루프가 만든 PR에는 라벨이 있으므로, 워크플로 시작 시 해당 라벨의 열린 PR이 있는지 확인한다. 만약 열려 있다면 루프를 중단한다.

논리는 이렇다.

이전 PR이 아직 열려 있다는 것은 사람이 아직 마지막 결과를 리뷰하지 않았다는 뜻이다. 그러면 다음 결과를 또 쌓을 이유가 없다.

이렇게 하면 루프마다 동시에 열린 PR은 최대 하나가 된다. 쌓임, 중복, 충돌을 줄일 수 있다.

13. 속도 높이기: 신뢰가 쌓인 뒤 확장한다

루프가 안정적이라고 느껴지면 속도를 높일 수 있다.

화자는 HumanLayer에 마이그레이션할 RPC 프로시저가 150개 있다고 말한다. 하나씩 하루에 하나만 처리하면 약 6개월이 걸릴 수 있다.

속도를 높이는 방법은 여러 가지다.

  • 컨트롤러가 한 번에 3개 또는 5개 프로시저를 선택한다.
  • 3개 또는 5개를 선택하되 각각 별도 구현 단계로 나눈다.
  • 각 마이그레이션에 별도 컨텍스트 창(context window)을 줘서 더 싸고 안정적으로 만든다.
  • 워크플로를 4번 실행해 팀원 4명에게 PR을 하나씩 나눠 준다.

중요한 것은 처음부터 속도를 최대화하지 않는 것이다. 먼저 작은 변경을 사람이 읽고 검토할 수 있게 만든 뒤, 신뢰가 생기면 병렬화한다.

14. 결론: 루프는 소프트웨어 공장이어야 하지만, 사람을 배제하면 안 된다

화자의 주장은 AI 코딩 루프를 반대하는 것이 아니다. 오히려 루프는 매우 강력하다고 본다.

다만 좋은 루프는 다음 조건을 만족해야 한다.

  • 코드베이스를 점진적으로 개선한다.
  • 사람이 실제로 코드를 읽을 수 있다.
  • 열린 PR이 쌓이지 않는다.
  • 사람이 낮은 마찰로 방향을 다시 잡을 수 있다.
  • 피드백과 지시가 버전 관리된다.
  • 측정 가능한 문제를 기준으로 움직인다.

즉, 프롬프트를 반복 실행하는 것이 아니라 엔지니어링된 제어 루프를 만들어야 한다.

종합 체크리스트

  • [ ] 우리 코드베이스에서 측정 가능한 반복 개선 대상을 하나 고른다.
  • [ ] 목표 상태(set point)를 한 문장으로 정의한다.
  • [ ] ESLint, ast-grep, 테스트, 로그, APM 중 센서로 쓸 수 있는 것을 정한다.
  • [ ] 새로 나쁜 패턴이 추가되지 않도록 기준 목록을 버전 관리한다.
  • [ ] 컨트롤러가 한 번에 너무 큰 변경을 고르지 않게 제한한다.
  • [ ] 작은 변경부터 처리하도록 정렬 기준을 만든다.
  • [ ] 에이전트에게 줄 스킬(skill) 문서를 작성한다.
  • [ ] 팀 코드 스타일을 보여주는 골든 패턴(golden pattern)을 만든다.
  • [ ] CI에서 한 번의 sense-control-actuate 워크플로를 실행해 본다.
  • [ ] PR 라벨을 붙여 루프가 만든 PR을 식별한다.
  • [ ] 열린 PR이 있으면 새 PR을 만들지 않도록 흐름 제어를 넣는다.
  • [ ] 피드백 파일을 마크다운으로 만들고 버전 관리한다.
  • [ ] /iterate 같은 댓글 트리거로 사람이 쉽게 재실행하게 만든다.
  • [ ] 안정화 후 한 번에 3개, 5개 또는 병렬 PR 방식으로 확장한다.

요즘 우리 모두 루프를 만들고 있다고 생각합니다. 그런데 최근에 깨달은 것은, 우리가 대부분 잘못하고 있다는 점입니다. 루프는 정말 강력합니다. 그 점은 부정하지 않습니다. 하지만 루프에 대한 많은 논의가 과장에 의해 움직이고 있고, 실제로는 별로 도움이 되지 않습니다.

업계 전체에 이런 생각이 퍼져 있습니다. 프롬프트(prompt)와 루프(loop)를 코딩 에이전트(coding agent)에 연결하면, 이런 방식으로 소프트웨어를 만들 수 있다는 생각입니다. 검증기(verifier)에 많은 시간을 투자할 수도 있고, 코드 리뷰 에이전트를 여섯 개쯤 둘 수도 있습니다. 하지만 결국 이런 식으로 하면 아무도 읽고 싶어 하지 않는 4만 줄짜리 PR을 만들고 있는 것입니다.

이것은 Jeff Huntley를 비난하려는 말은 아닙니다. Ralph는 혁신적이고 날카로운 도구이며, 특정 종류의 문제에는 아주 잘 작동합니다. 팀으로 개발하지 않을 때, 그리고 중요한 시스템을 다루지 않을 때도 잘 작동합니다. 하지만 우리 대부분은 팀에서 일하고 있고, 그 범주에 들어맞지 않습니다.

그래서 오늘은 실제 고객, 실제 사용자, 실제 규제 의무, 서비스 수준 계약(SLA), 그리고 4만 줄짜리 YOLO PR을 곧장 프로덕션에 배포하지 못하게 만드는 여러 제약이 있는 크고 복잡한 코드베이스에서 작동하는 루프를 만드는 방법에 대해 이야기하려고 합니다. 다시 말해 현실 세계를 위한 루프를 만드는 방법입니다.

혹시 모르시는 분들을 위해 말하면, 이 글은 사실 7월에 올라온 것입니다. 지난 1월에 바이럴이 되었고, 아마 그때 많은 사람이 루프를 만들기 시작했을 것입니다. 그리고 더 최근에는 Peter Steinberger가 이제 코딩 에이전트에게 프롬프트를 직접 던지면 안 된다고 말했습니다. 대신 에이전트를 프롬프트하는 루프를 설계해야 한다는 것입니다.

OpenCode도 루프 위에 만들어진 것으로 유명합니다. 루프가 코드를 만들고, 루프가 코드를 리뷰하고, 병합하고 릴리스하고, 버그를 찾고 고칩니다. 심지어 병합하는 루프 안의 버그를 찾고 고치는 루프도 있습니다. 말 그대로 루프 아래에 또 루프가 있는 구조입니다.

Claude Code의 창시자인 Boris Cherny도 최근에 엔지니어로서 자신의 일은 이제 Claude에게 프롬프트를 주는 루프를 작성하는 것뿐이라고 말했습니다. 결국에는 루프조차 필요 없어질지도 모릅니다. 에이전트 떼(swarm)가 루프를 설계하고, 그 루프가 에이전트에게 프롬프트를 주고, 또 다른 루프를 위한 에이전트 떼를 만들 것입니다. 어딘가에서는 프로덕션 코드를 쓰고 있겠죠. 아마도요.

실제로 우리가 만들고 있는 모든 루프는 너무 많은 코드를 만들어내고 있어서, 우리가 그것을 전부 읽을 수 없습니다. 그러니 차라리 아무것도 읽지 말자는 식이 됩니다. 우리는 검증과 코드 리뷰에 투자하고 있지만, 이 모든 코드는 사실상 읽기 전용(read-only) 코드입니다. 지난달 이 도시에서 열린 한 콘퍼런스의 논지도 바로 그것이었습니다.

많은 똑똑한 프런티어 랩(frontier lab) 사람들이 이것이 소프트웨어 개발의 미래라고 생각합니다. 이 방식을 쓰면 10배 빠르게 움직이고, 나머지는 뒤처진다는 이야기입니다. 하지만 이것이 실제로 얼마나 잘 작동하는지는 아직 명확하지 않습니다. Claude Code의 터미널 깜빡임 문제를 고치는 데 6개월이 걸렸습니다. OpenCode 팀은 그보다 훨씬 짧은 시간에 렌더러(renderer)를 만들었지만, OpenCode도 안정성 문제가 있는 것으로 유명합니다.

다만 아주 분명한 것이 있습니다. 프런티어 랩에서 일하며 무제한 토큰 예산을 가진 사람이 아니라면, 이런 방식은 정말 비쌉니다. 그리고 우리가 쓰는 이 모든 코드 자체도 사실 매우 비쌉니다. Matt Pocock도 최근 이 이야기를 했습니다. 에이전트 시대의 나쁜 코드는 과거 어느 때보다 훨씬 더 비쌉니다.

그래서 오늘은 현실 세계에서 작동한다고 생각하는 것, 그리고 HumanLayer에서 우리가 시작한 방식을 이야기하려고 합니다. 분명히 말하지만, 우리도 여전히 루프를 만들고 있습니다. 저는 루프가 매우 강력하다고 생각합니다. 하지만 우리는 루프를 설계하면서도 코드를 읽을 수 있습니다. 오히려 코드가 더 좋아지기 때문에 코드를 읽기 쉬워지는 루프를 설계할 수도 있습니다. 복잡한 코드베이스의 어려운 문제를 루프로 해결할 수 있고, 소프트웨어 공장(software factory)을 점진적으로 만들 수도 있습니다. 하지만 그러려면 진짜 엔지니어링이 필요합니다.

이제 제어 이론(control theory)에 대해 이야기해 봅시다.

제어 이론은 동적인 시스템(dynamic system)을 원하는 안정 상태나 최적 상태로 이끄는 방법을 다룹니다. 여기서 동적인 시스템은 코드베이스입니다. 현재 세계의 상태를 측정하는 센서(sensor)가 있습니다. 원하는 세계의 상태인 설정값(set point)이 있습니다. 이 둘의 차이가 측정 오차(measured error)입니다. 컨트롤러(controller)는 이 측정 오차를 읽고, 시스템에 적용할 점진적 변경에 대한 제어 신호(control signal)로 바꿉니다. 액추에이터(actuator)는 그 변경을 시스템에 적용합니다. 그사이 시스템에는 방해(disturbance)가 생길 수 있습니다. 그런 다음 다시 측정하고, 측정 오차를 다시 계산하며, 처음 위치로 돌아옵니다.

이 설명은 복잡하게 들립니다. 실제로 복잡할 수도 있습니다. 제게는 항공우주 엔지니어인 쌍둥이 형제가 있는데, 전투기가 하늘에서 떨어지지 않게 하는 데 이런 방식이 쓰입니다. 하지만 여러분이 생각하는 것보다는 아마 조금 더 단순합니다.

온도조절기(thermostat)를 가진 분이 있나요? 온도조절기는 제어 루프를 사용합니다. 유럽에서 오신 분들을 위해 설명하면, 미국에는 에어컨이라는 것이 있고, 그 일부입니다.

사실 우리 대부분은 매일 제어 루프를 사용합니다. 쿠버네티스 오토스케일링(Kubernetes autoscaling) 시스템은 제어 루프 위에 만들어졌습니다. Infrastructure as Code는 원하는 상태(desired state), 현재 상태(current state), 반복적 변경(iterative change) 같은 제어 루프 패턴을 사용합니다. Postgres auto-vacuum과 React virtual DOM도 제어 루프를 사용하거나 그에 가까운 방식으로 작동합니다.

제어 루프는 바꾸고 싶은 시스템이 있고, 측정할 수 있는 문제가 있으며, 변경 결과에 대한 피드백을 받을 수 있을 때 이상적입니다. 좋은 소프트웨어 엔지니어가 늘 배워온 것처럼, 제어 루프는 시스템을 한 번에 최종 상태로 보내려 하지 않습니다. 대신 점진적으로 바꿉니다. 그렇게 해야 모든 것을 날려버릴 위험을 줄일 수 있습니다. 제어 루프는 과조향(oversteering)을 피하고, 시스템을 불안정하게 만들지 않으며, 위험을 최소화합니다.

그래서 제어 루프는 제가 블라인드 Ralph 루프(blind Ralph loop)라고 부르는 것의 반대입니다. 이런 PR을 피하는 방법입니다. 아무도 이런 PR을 리뷰하고 싶어 하지 않습니다.

그렇다고 모든 Ralph 루프가 눈먼 루프라는 뜻은 아닙니다. 가장 좋은 Ralph는 실제로 제어 이론을 적용하고 있습니다. Jeff Huntley가 아마 복도 어딘가에 있을 텐데, 그에게 물어보면 같은 말을 할 것입니다. Ralph는 교육용 장치이고, 우리 중 일부가 그것을 너무 문자 그대로 받아들였다고 생각합니다. 사실 우리는 처음부터 이런 방식으로 루프를 만들었어야 합니다.

Ralph 루프의 또 다른 문제는 점진적이지 않다는 것입니다. 그냥 bash 루프입니다. 그래서 우리는 에이전틱 제어 루프(agentic control loop)를 만들어야 합니다.

그러려면 먼저 설정값(set point)을 정의해야 합니다. 이것은 코드베이스의 어떤 속성에 대해 원하는 최종 상태입니다. 그리고 센서를 추가합니다. 센서를 만드는 방법은 많습니다. 엄격하게 결정론적일 수도 있습니다. ESLint 규칙, ast-grep, Packwerk 같은 것이 그렇습니다. 비결정론적일 수도 있습니다. 에이전트와 스킬(skill), 자연어 규칙을 많이 사용할 수도 있습니다. 또는 둘을 조합한 파이프라인일 수도 있습니다.

지금까지는 이론입니다. 실제로는 에이전트를 사용하기 때문에 시스템 구성 요소 사이의 경계를 조금 흐릴 수 있습니다. 예를 들어 Aiden Bai의 React Doctor는 훌륭합니다. Claude가 지난주 여러분의 코드베이스에 몰래 넣은 React 잡코드(slop)를 잡아내는 좋은 방법입니다. 하지만 이것은 센서와 컨트롤러의 하이브리드입니다. React 코드의 모든 문제를 알려주면서, 추가로 고쳐야 할 상위 세 가지와 고치는 방법도 알려줍니다.

마찬가지로 컨트롤러와 액추에이터도 실제로는 하나의 에이전트일 수 있습니다. 같은 컨텍스트 창(context window) 안에서 점진적 변경을 결정하고 곧바로 적용하는 식입니다.

하지만 저는 컨트롤러를 조금 더 자세히 보고 싶습니다. 컨트롤러가 없거나 잘 조정되어 있지 않으면 한 번에 너무 큰 변경을 만들 수도 있고, 완전히 잘못된 변경을 만들 수도 있습니다. 그리고 그것을 루프에 넣으면 꽤 빠르게 곤란해집니다.

제어 루프는 나쁜 패턴을 뿌리 뽑고 코드를 정리하는 데 사용할 수 있습니다. 하지만 사실 훨씬 더 다양한 일에 쓸 수 있습니다. API가 다른 사람의 OpenAPI 명세(OpenAPI spec)를 준수하는지 확인할 수 있습니다. MCP 서버가 현재 버전의 MCP 명세(MCP specification)를 준수하는지 확인할 수도 있습니다. Python 프로젝트를 TypeScript로 미러링하거나 그 반대로 할 수도 있습니다. Vite 기반의 조잡한 Next.js 포크를 업스트림에 맞춰 유지할 수도 있습니다.

핵심 질문은 세 가지입니다. 측정할 수 있는 것을 찾을 수 있는가? 변경을 점진적으로 적용할 수 있는가? 그 변경의 품질에 대한 피드백을 받을 수 있는가?

이를 설명하기 위해 HumanLayer 내부에서 사용하는 제어 루프를 살펴보겠습니다. 이 루프에서 우리는 RPC API를 Effect로 점진적으로 마이그레이션하고 있습니다. 경합 조건이 생기기 쉬운 코드에 Effect를 도입했는데 마음에 들어서, 나머지 코드베이스에도 적용하고 있습니다.

Effect 코드를 본 적이 없다면, 오른쪽 코드는 왼쪽의 간단한 프로시저를 Effect로 다시 쓴 것입니다. 문법이 꽤 이상합니다. 우리는 좀 이상한 사람들이라 좋아하지만, 모두에게 맞는 것은 아닙니다. 괜찮습니다. 이 발표는 Effect에 대한 발표가 아니니 넘어가겠습니다.

첫 번째 단계는 마이그레이션되지 않은 프로시저를 찾는 센서를 만드는 것입니다. 에이전트에게 시킬 수도 있고, grep이나 ripgrep을 쓸 수도 있습니다. 하지만 우리는 ast-grep을 사용합니다. ast-grep은 매우 강력합니다. 루프를 만들 때 도구상자에 넣어둘 만한 훌륭한 도구입니다. 언어에 구애받지 않고, TypeScript 설정이나 ESLint 규칙과 별도로 동작합니다. TypeScript 개발자라면 Claude가 인라인 주석으로 그런 규칙을 비활성화하는 모습을 본 적이 있을 것입니다.

그래서 위의 패턴을 기준으로 마이그레이션되지 않은 프로시저를 찾는 간단한 규칙을 작성할 수 있습니다. 시간이 지나면서 제거하고 싶은 다른 패턴을 설명하는 규칙도 더 쌓을 수 있고, include/exclude 경로도 세밀하게 지정할 수 있습니다. 우리처럼 여러 언어가 섞인 모노레포(multilingual monorepo)가 있다면, 상상할 수 있는 거의 모든 언어에 사용할 수 있습니다.

코드베이스를 스캔하면 긴 위반 목록이 나옵니다. 사실 너무 깁니다. 위반 하나당 약 50개의 키가 나오므로, 우리는 4개 정도로 줄이고 결정적으로 정렬합니다.

왜 이렇게 할까요? 처음에 실용적인 이야기를 하겠다고 했으니, 잠깐 제어 루프 패러다임 바깥으로 나가 보겠습니다. 프로시저를 하나씩 점진적으로 마이그레이션하기 전에, 새로 작성되는 모든 프로시저가 Effect를 사용하도록 강제해야 합니다. 그래서 main에서 전체 스캔을 한 번 실행하고, 모든 위반을 결정적으로 정렬한 뒤, 그것을 버전 관리에 넣습니다. 그러면 이후 모든 새 PR에서 해당 브랜치가 마이그레이션되지 않은 프로시저를 추가했는지 확인할 수 있습니다.

이것이 우리의 제어 루프입니다. 시스템에는 방해가 생깁니다. 여기서는 팀원들이 Claude 잡코드(slop)를 배포하는 것이 방해입니다. 이 방식은 그들이 루프가 해놓은 일을 되돌리지 못하게 합니다. 제어 루프의 특정 구성 요소에 직접 대응되지는 않지만, 조금 관대하게 보면 방해 완화 장치(disturbance dampener)라고 부를 수 있습니다.

이제 출혈을 막았으니 컨트롤러를 설계할 수 있습니다. 단순한 컨트롤러라면 목록에서 첫 번째 위반을 결정론적으로 고르면 됩니다. bash와 jq를 사용할 수 있습니다. 조금 더 영리하게 하려면 ast-grep으로 가장 작은 마이그레이션 안 된 프로시저를 찾아 항상 가장 작은 것을 고르면 위험을 줄일 수 있습니다. 정말 원한다면 에이전트가 결정하게 할 수도 있습니다. 하지만 결정론적 코드가 할 수 있는 일에 에이전트를 보내는 것은 저는 권하지 않습니다. 물론 할 수는 있습니다.

에이전트가 마이그레이션할 프로시저를 고르고 동시에 작업하게 할 수도 있습니다. 하지만 이것을 더 강력하게 만들 수도 있습니다. 우리는 단순히 마이그레이션 자체를 위해 하는 것이 아닙니다. 에러 처리와 코드 계측(instrumentation)을 더 잘하기 위해 하는 것입니다.

그래서 더 영리하게 하려면 텔레메트리(telemetry)를 보고 어떤 프로시저에 에러가 가장 많은지, 계측이 가장 부족한지, APM(application performance monitoring)에 빈틈이 있는지 파악할 수 있습니다. 그리고 액추에이터 에이전트에게 제어 신호를 보낼 때, 마이그레이션할 프로시저뿐 아니라 이 마이그레이션으로 고치려는 문제에 대한 데이터까지 함께 줄 수 있습니다. 그러면 액추에이터 에이전트가 단순한 1:1 마이그레이션이 아니라 실제로 코드를 더 좋게 만들 수 있습니다.

다음은 액추에이터를 만드는 것입니다. 액추에이터는 에이전트와 스킬(skill)입니다. 원하는 CLI 코딩 에이전트를 가져오면 됩니다. 스킬에는 많은 시간을 써야 합니다. 다만 그 시간을 모두 처음에 쓸 필요는 없습니다. 무엇이 잘 작동하는지에 따라 시간이 지나며 반복 개선해야 합니다.

HumanLayer에서는 에이전트를 풀어놓기 전에 우리가 골든 패턴(golden pattern)이라고 부르는 것을 손으로 만듭니다. 이것은 에이전트가 따라 할 수 있도록 사람이 직접 작성한 관용적인 예시입니다. 에이전트는 결국 패턴 복제기(pattern replicator)이기 때문입니다. 그렇지 않으면 문서에 있는 방식이나 인터넷에서 에이전트가 배운 방식을 얻게 됩니다.

그래서 스킬과 제어 신호를 액추에이터 에이전트에 전달합니다. 스킬에는 당연히 응답 템플릿(response template)이 포함되어야 합니다. 에이전트는 계속 작업하고, 최종 응답을 만들어냅니다. 그런 다음 우리는 결정론적으로 커밋하고 푸시하고 PR을 만듭니다. 최종 메시지는 PR 설명으로 사용합니다.

이제 루프를 실제로 실행하기만 하면 됩니다. 제 추천은 GitHub Actions, GitLab, CircleCI 등 여러분이 이미 쓰고 있는 것을 사용하는 것입니다. 이런 도구는 코드에 접근할 수 있고, 시크릿(secrets)에 접근할 수 있으며, 디스패치(dispatch)와 스케줄링(scheduling) 기능이 좋습니다. 이를 위해 새 클러스터를 만들 필요는 없습니다.

우리는 루프 한 번의 반복을 실행하는 워크플로를 작성할 수 있습니다. 감지(sense), 제어(control), 실행(actuate)을 하고 PR을 만듭니다. 그리고 이것을 하루에 한 번 실행하도록 스케줄링할 수 있습니다. 그러면 매일 아침 사무실에 와서 위험이 낮은 작은 점진적 PR 하나를 보게 됩니다.

우리가 처음 이것을 했을 때는 사실 꽤 답답했고, 루프를 꺼버렸습니다. 스킬을 계속 업데이트해야 했고, 브랜치를 계속 체크아웃해서 스킬을 바꾸고, 코드를 바꾸고, 커밋하고 푸시해야 했습니다. 루프의 마찰이 매우 컸습니다.

하지만 더 나은 방법이 있습니다. 사람이 루프 위에 있으면서, 루프가 잘못 갔을 때 아주 낮은 마찰로 다시 방향을 잡게 하는 방법입니다. 방법은 단순합니다. 버전 관리되는 마크다운 파일로 피드백 파일(feedback file)을 만드는 것입니다. 컨트롤러 실행 후 액추에이터 에이전트가 실행될 때마다 이 파일을 결정론적으로 컨텍스트에 넣습니다.

그런 다음 PR에 라벨(label)을 추가합니다. 여러 루프가 동시에 실행될 수 있으므로, 각 워크플로는 자신이 만든 PR을 식별할 수 있어야 합니다. 또한 자신의 PR 댓글에서 나온 피드백에만 반응해야 합니다.

그리고 각 루프 워크플로에 댓글 트리거(comment trigger)를 추가합니다. 사용자가 PR에 /iterate 댓글을 남기면, 루프 워크플로가 그것을 감지합니다. 그런 다음 PR 컨텍스트, diff, 댓글, 리뷰 댓글, 설명을 모두 결정론적으로 에이전트 컨텍스트에 넣고, 스킬도 함께 넣습니다. 그리고 에이전트에게 코드를 고치되, 피드백 파일도 업데이트하라고 지시합니다. 대략 이런 모습입니다.

이 방식의 장점은 지시가 담긴 피드백 파일이 버전 관리된다는 것입니다. 시간이 지나며 어떻게 바뀌었는지 볼 수 있고, 필요하면 되돌릴 수 있습니다.

다음으로 할 일은 흐름 제어(flow control)를 추가하는 것입니다. 우리가 겪었던 또 다른 문제는 고객사에 일주일간 가 있거나, 출장을 가거나, 코드를 쓰는 대신 발표 슬라이드를 6일 동안 만들면, 모든 루프의 PR이 계속 쌓인다는 것이었습니다. 작업이 중복되고, 충돌하고, 결국 처리하지 못했습니다. 루프의 작업이 중요하긴 하지만, 그렇게까지 중요하지는 않습니다. 그러다 보니 중요하지 않은 잡동사니가 잔뜩 생겼습니다.

이 문제는 사실 매우 쉽게 고칠 수 있습니다. 각 루프와 워크플로에는 PR에 붙는 라벨이 있습니다. 워크플로가 처음 실행될 때, 코드를 체크아웃하고 의존성을 설치하고 sense-control-actuate 단계를 실행하기 전에, 마지막으로 만든 PR 또는 해당 루프 라벨이 붙은 PR이 열려 있는지 확인하면 됩니다. 열려 있다면 그냥 종료합니다. 이는 마지막으로 사람이 이 루프의 코드를 리뷰한 시점이 루프가 실행되기 전이라는 뜻입니다. 즉, 마지막 출력물을 사람이 아직 리뷰하지 않았으므로, 사람이 리뷰해야 할 일을 더 쌓을 이유가 없습니다.

이렇게 하면 각 루프당 동시에 열린 PR은 최대 하나가 됩니다. 쌓임도 없고, 중복도 없고, 바라건대 충돌도 없습니다.

물론 루프에 자신감이 생기면 속도를 높이고 싶어질 것입니다. 저는 마이그레이션해야 할 RPC 프로시저가 150개 있습니다. 하나씩 하면 6개월이 걸립니다. 제가 기다리고 싶은 시간보다 훨씬 깁니다.

다행히 루프의 속도를 높이는 방법은 많습니다. 컨트롤러가 한 번에 하나가 아니라 세 개 또는 다섯 개의 프로시저를 고르게 할 수 있습니다. 컨트롤러가 세 개나 다섯 개를 고르되, 각각을 별도의 구현 단계에서 처리하게 할 수도 있습니다. 각 마이그레이션이 자기만의 컨텍스트 창(context window)을 갖기 때문에 더 싸고 더 안정적입니다. 또는 워크플로를 네 번 실행해서 팀의 네 사람에게 PR을 하나씩 줄 수도 있습니다.

이제 모두 합쳐봅시다. 우리는 코드를 점진적으로 개선하는 제어 루프를 만들었고, 실제로 그 코드를 읽고 있습니다. 적응형 흐름 제어(adaptive flow control)가 있어서 아무도 리뷰하고 싶어 하지 않는 일을 잔뜩 만들지 않습니다. 그리고 잘못 갔을 때 매우 낮은 마찰로 즉석에서 방향을 다시 잡을 수 있습니다.
