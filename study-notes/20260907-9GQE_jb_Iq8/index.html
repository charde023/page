스킬 vs MCP vs RAG vs 메모리: AI 에이전트에게 필요한 핵심 4가지 지식입니다 — Codex 버전

업로드 2026-09-07 · 9.0분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상은 웹 결제 페이지에서 500 오류가 났을 때 AI 에이전트에게 무엇을 줘야 하는지 설명한다. 관련 자료를 처음부터 전부 넣으면 에이전트가 중요한 단서를 놓치거나 불필요한 경로로 갈 수 있다. 그래서 지식을 역할별로 나눈다.

반복할 조사 절차와 사람에게 넘길 판단 기준은 스킬이 맡는다. 로그나 지표처럼 외부 시스템의 실제 정보에 접근하는 통로는 MCP(Model Context Protocol)가 제공한다. 매뉴얼과 의존성 지도처럼 사람이 미리 저장한 문서에서 필요한 부분을 찾는 방식은 RAG(검색 증강 생성)다. 이전 오류에서 에이전트가 얻은 경험을 다시 쓰고, 해결 결과를 다음 작업을 위해 남기는 것은 메모리다. 네 방식은 경쟁 관계라기보다 서로 다른 빈칸을 채우므로, 과제에 따라 필요한 것만 선택하거나 함께 조합해야 한다.

여기까지만 이해하면 충분

  • 스킬은 해야 할 절차와 판단 기준을 알려 주지만 외부 정보에 직접 접근시켜 주지는 않는다.
  • MCP는 외부 시스템에 연결하고, RAG는 사람이 저장한 문서를 찾아오며, 메모리는 이전 작업에서 얻은 경험을 재사용한다.
  • 자료를 무조건 많이 넣기보다 현재 과제에 필요한 지식의 종류를 먼저 구분해야 한다.

한 장면으로 이해하기

결제 페이지에 500 오류가 발생했다. 에이전트는 스킬에 적힌 순서대로 오류율과 최근 배포 상태를 확인하려 하지만, 실제 지표를 읽으려면 외부 시스템에 연결되어야 한다. MCP로 로그와 지표를 가져오고, RAG로 매뉴얼과 의존성 지도를 찾으며, 메모리에서 이전의 비슷한 오류 경험을 불러온다.

"많은 자료가 있지만 무엇을 보고 어떻게 조사할지 불명확하다" 문제
→ "절차·외부 연결·문서·경험을 서로 다른 장치로 공급한다" 작동 방식
→ "현재 오류에 필요한 정보와 행동을 골라 조사한다" 결과

비유와 깨지는 지점

정비사의 네 가지 도구

스킬은 정비 순서표, MCP는 차량 상태를 읽는 진단 연결선, RAG는 제조사가 작성한 정비 설명서, 메모리는 정비사가 이전 고장에서 남긴 작업 기록에 가깝다.

비유가 깨지는 지점: 실제 에이전트에서 MCP는 단순한 연결선이 아니라 호스트와 서버 사이의 표준 통신 방식이다. 또한 메모리가 경험을 저장한다고 해서 그 내용이 자동으로 정확하거나 안전하다는 뜻은 아니다.

RAG 필요한 문서 조각을 그때 찾아오는 방식 외부 문서를 의미 기반으로 검색해 관련 부분을 문맥에 넣는 검색 증강 생성 모든 문서를 처음부터 문맥 창에 넣는 것과 같다고 보는 것
메모리 이전 작업에서 얻은 경험 기록 에이전트가 과거 작업과 해결 과정에서 얻어 저장한 정보를 다시 사용하는 장치 사람이 작성해 넣은 문서 저장소와 항상 같다고 보는 것

1. 원인

관련 자료를 문맥 창에 전부 넣어도 에이전트가 효과적으로 문제를 해결하지 못할 수 있는 이유는 무엇인가?

모범 답안 보기

정보가 많다고 조사 순서, 외부 시스템 접근 권한, 현재 상황에 맞는 문서, 과거 경험이 자동으로 구분되는 것은 아니다. 화자는 에이전트가 길을 잃거나 막다른 경로로 가고, 특정 결제 페이지에 맞지 않는 일반적인 행동을 할 수 있다고 설명한다.

2. 대조

RAG와 메모리는 모두 필요한 지식을 불러오는데, 무엇이 다른가?

모범 답안 보기

영상의 구분 기준은 지식의 출처다. RAG는 사람이 의도적으로 저장한 매뉴얼이나 의존성 지도 같은 문서를 검색한다. 메모리는 에이전트가 이전 작업과 문제 해결 과정에서 얻어 저장한 경험을 불러온다.

3. 적용

새로운 에이전트 과제를 설계할 때 네 방식을 어떻게 골라야 하는가?

모범 답안 보기

먼저 필요한 것이 반복 절차인지, 외부 시스템의 실제 정보인지, 사람이 작성한 문서인지, 이전 작업에서 얻은 경험인지 분류한다. 각각 스킬, MCP, RAG, 메모리에 대응시킨 뒤 필요한 역할만 선택한다. 네 가지를 항상 모두 써야 한다고 미리 정하지 않는다.

이번 글의 통찰

1. 지식의 양보다 역할 구분이 먼저다

  • [원문] 화자는 모든 런북·대시보드·고객 이력을 문맥 창에 넣으면 에이전트가 길을 잃거나 특정 시스템에 맞지 않게 행동할 수 있다고 주장한다.
  • [해석] 에이전트 설계의 첫 질문은 “얼마나 많이 넣을까?”가 아니라 “이 정보는 절차·접근·문서·경험 중 무엇인가?”다.
  • [경계] 영상은 이 구분의 효과를 비교 실험이나 수치로 검증하지 않는다. 500 오류와 결제 페이지는 설명용 가상 사례이며, 네 방식을 모두 결합한 시스템을 실제로 시험했다는 진술도 없다.

2. 절차와 사람 이관 판단은 구분해서 읽어야 한다

  • [원문] 트리아지 스킬의 순서 있는 점검 단계는 ① 오류율 확인, ② 최근 배포 상태 확인 두 가지다. 사람에게 이관할 시점을 아는 것은 이 단계들과 별도로 스킬이 담을 수 있는 판단 기능이다.
  • [해석] 좋은 스킬은 행동 순서뿐 아니라 에이전트가 혼자 계속하지 말아야 할 조건도 표현할 수 있다.
  • [경계] 사람 이관을 세 번째 점검 단계로 세면 원문의 열거 구조가 바뀐다. 수량 대조 결과, 네 방법이라는 표현과 실제 네 개의 열거는 일치하며 538초와 9.0분도 반올림 관계로 충돌하지 않는다. META에는 원작자 이름이 없고 소속 후보만 Ibm으로 기재되어 있으며, provenance.note는 원본 링크가 확인되지 않은 추정 출처임을 밝힌다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 영상은 비슷해 보이는 네 개념을 “절차·연결·문서·경험”이라는 역할로 나눈다.
  • 통찰: 이름을 암기시키기보다 새로운 사례에서 어떤 빈칸을 채우는 기술인지 설명하게 해야 이해 여부를 관찰할 수 있다.
  • 질문/행동: “로그를 읽어야 하는데 스킬만 있다면 무엇이 부족한가?”를 영상 없이 설명해 보게 한다.

사업가 · 구조적 비유

  • 관련성: 업무에서도 절차, 시스템 접근, 공식 문서, 현장 경험이 한곳에 뒤섞이면 필요한 자원을 찾기 어렵다는 구조가 닮아 있다.
  • 통찰: APOM에 적용한다면 현재 상태에 대한 주장이 아니라, 물류·고객 대응 지식을 네 역할로 분류해 볼 수 있다는 검증 전 가설이다.
  • 질문/행동: 특정 운영 문제 하나에서 필요한 것이 절차인지, 실시간 조회인지, 문서인지, 경험인지 먼저 구분할 수 있는가?

마케터 · 직접 전이

  • 관련성: 500 오류라는 장면과 네 역할의 대조가 추상적인 기술 이름을 구체적인 필요와 연결한다.
  • 통찰: 기능 이름만 나열하기보다 “무엇이 부족할 때 쓰는가”를 보여 주면 차이를 설명하기 쉽다. 다만 영상의 사례는 성능 증거가 아니라 설명 장치다.
  • 질문/행동: 카피의 각 효익 옆에 실제 검증 증거가 있는지, 아니면 이해를 돕는 예시만 있는지 표시한다.

AI/SW 학습자 · 직접 전이

  • 관련성: 스킬·MCP·RAG·메모리는 에이전트 아키텍처에서 서로 다른 문제를 담당한다.
  • 통찰: 도구 이름부터 선택하지 말고 작업이 요구하는 절차, 외부 접근, 문서 검색, 경험 재사용을 먼저 식별해야 한다.
  • 질문/행동: 가상 장애 과제에서 각 정보 요구를 네 역할 중 하나로 분류하고, 불필요한 구성요소는 제외해 본다.

가치 지도

"에이전트가 많은 정보 속에서 조사 순서와 필요한 근거를 구분하지 못한다" 문제
→ "더 분명한 조사와 문제 해결 흐름" 수혜자: 에이전트 운영자와 서비스 사용자
→ "절차·시스템 접근·문서·검토된 경험을 제공" 지불자 또는 자원 제공자: 시스템 운영 조직
→ "필수 정보 역할을 올바르게 선택한 수" 가치 지표

작은 실험 하나

  • 행동 1개: 가상 500 오류 과제 하나를 만들고 필요한 지식을 스킬·MCP·RAG·메모리 역할로 분류하는 구성을 1회 시험한다.
  • 측정 1개: 사전에 정한 네 가지 지식 요구 중 올바른 역할에 연결한 수(0~4개)
  • 중단 기준 1개: 올바르게 연결한 수가 3개 이하이면 확대하지 않고 분류 기준부터 수정한다.

# 섹션 요지
1 모든 문맥 넣기의 한계 많은 자료만으로는 올바른 조사와 행동이 보장되지 않는다.
2 스킬 반복 절차와 적용·이관 판단을 제공한다.
3 MCP 에이전트를 로그·지표 같은 외부 시스템에 연결한다.
4 RAG 사람이 저장한 문서에서 관련 부분을 검색한다.
5 메모리 이전 작업에서 얻은 경험을 저장하고 다시 사용한다.
6 선택 기준 절차·외부 조회·문서·경험이라는 출처와 역할로 구분한다.

1. 모든 자료를 넣는 방식의 문제

화자는 결제 페이지에서 500 Internal Server Error가 발생한 가상 장면을 제시한다. 런북, 대시보드, 고객 이력을 모두 문맥 창에 넣는 방법은 직관적으로 보이지만, 에이전트가 길을 잃거나 막다른 경로로 가고 특정 결제 페이지에 맞지 않는 일반적인 행동을 할 수 있다고 주장한다.

2. 스킬: 절차와 판단 기준

에이전트 스킬은 특정 작업을 위한 지침이며 코드가 붙을 수도 있다. 과제가 요구할 때만 스킬을 불러오는 방식을 화자는 점진적 공개(progressive disclosure)라고 부른다.

가상의 트리아지 스킬에는 순서가 있는 점검 단계 두 개가 제시된다.

  1. 오류율을 확인한다.
  2. 최근 배포 상태를 확인한다.

사람에게 문제를 이관해야 할 시점을 판단하는 기능은 위 순서의 세 번째 단계가 아니라, 스킬이 추가로 담을 수 있는 별도의 판단 기준이다. 스킬은 무엇을 확인할지는 알려 주지만 대시보드에 직접 접근하게 해 주지는 않는다.

3. MCP: 외부 시스템에 접근하는 통로

MCP는 Model Context Protocol이다. 화자의 설명에서 에이전트는 MCP 호스트이고, 접근할 시스템은 MCP 서버 뒤에 놓인다. 특정 로깅 시스템에 연결하는 방법을 모델이 몰라도 해당 MCP 서버가 연결 기능을 호출 가능한 형태로 노출할 수 있다.

이 구조를 이용하면 에이전트는 로그와 지표를 가져와 실제 오류율을 읽을 수 있다. 다만 MCP가 해당 시스템의 정상 상태, 의존 관계, 과거 원인까지 자동으로 알려 주는 것은 아니다.

4. RAG: 사람이 저장한 문서 검색

RAG는 Retrieval-Augmented Generation, 즉 검색 증강 생성이다. 모든 자료를 미리 넣는 대신 필요할 때 외부 자료에서 관련 부분만 찾는다. 예시 자료는 매뉴얼과 의존성 지도다. 에이전트의 질문과 의미가 맞는 문서 조각을 검색하고 그 결과를 문맥 창에 돌려준다.

5. 메모리: 작업에서 얻은 경험

영상은 RAG와 메모리를 지식의 출처로 구분한다. RAG가 사람이 의도적으로 벡터 데이터베이스에 저장한 문서를 읽는다면, 메모리는 에이전트가 이전 상황에서 얻어 저장한 경험을 사용한다.

예를 들어 과거의 같은 오류 원인이 런북에 없었고 별도의 조사로 밝혀졌다면 그 해결 경험을 다시 참고할 수 있다. 오류를 해결한 뒤 실제 수정 내용을 다음 작업을 위해 메모리에 쓸 수도 있다고 화자는 설명한다.

6. 화자가 제시한 선택 기준

  • 누군가 작성해 둔 지식이면 RAG
  • 에이전트가 경험에서 얻은 지식이면 메모리
  • 반복해서 따를 절차이면 에이전트 스킬
  • 에이전트가 외부 세계의 정보를 실제로 조회해야 한다면 MCP

이는 화자가 제시한 대략적인 선택 기준이다. 영상은 상황에 따라 일부 또는 전부를 함께 사용할 수 있다고 제안하지만, 특정 조합의 성능을 실험으로 검증하지는 않는다.

교정 전사 (한국어)

전체 전사 펼치기

AI 에이전트가 학습 데이터에 포함된 지식 외에 작업을 완료하는 데 필요한 지식을 제공하는 방법에는 여러 가지가 있습니다. 그중 네 가지인 스킬(skills), MCP, RAG, 메모리(memory)를 살펴보고, 각각 어떤 상황에 가장 적합한지 정의해 보겠습니다.

여기 어떤 웹 앱이 있다고 생각해 봅시다. 이 웹 페이지를 보니 오류가 발생하고 있습니다. 악명 높은 500 내부 서버 오류(500 Internal Server Error)입니다. 이 문제를 해결해야 합니다. AI 에이전트의 목표는 바로 이 오류를 해결하는 것입니다.

제 생각에 이 500 오류에 대해 에이전트의 도움을 받는 본능적인 방법은 가능한 한 많은 컨텍스트를 수집한 다음, 그것을 에이전트 자체의 컨텍스트 창(context window)에 넣는 것입니다. 이 컨텍스트 창에는 여러 런북(runbook)을 저장할 수 있습니다. 그런 다음 대시보드도 여러 개 전달하고, 고객 이력도 함께 넣은 뒤, 전부 컨텍스트 창에 던져 넣고 AI 에이전트가 이 오류를 어떻게 해결할지 알아내도록 하는 것입니다.

하지만 이는 이런 오류를 해결하는 데 꽤 비효율적인 방법일 수 있습니다. AI 에이전트가 길을 잃거나, 막다른 길로 빠지거나, 이 특정 결제 페이지가 실제로 작동하는 방식을 제대로 반영하지 못한 채 일반적인 방식으로 행동할 여지가 충분하기 때문입니다. 그러니 컨텍스트를 그냥 불 속에 던져 넣는 것이 최선의 방법은 아닐 수 있습니다.

아마 더 나은 접근법은 스킬, MCP, RAG, 메모리 중 하나를, 혹은 이 모든 것을 사용하는 것일 겁니다. 이제 이것들을 하나씩 살펴보면서 AI 에이전트로 이 웹 페이지의 문제를 어떻게 해결할 수 있는지 알아보겠습니다.

첫 번째인 에이전트 스킬(agent skill)부터 시작해 보겠습니다.

에이전트 스킬은 실제로는 특정 종류의 작업을 수행하기 위해 에이전트에 전달할 수 있는 지침 모음일 뿐입니다. 때로는 약간의 코드가 함께 포함되기도 합니다. 따라야 할 단계와 함께, 그 단계를 언제 따라야 하는지에 대한 판단 기준 같은 절차가 나열될 수 있습니다. 에이전트는 작업에 실제로 필요할 때만 점진적 공개(progressive disclosure)라는 방식을 통해 해당 스킬을 불러옵니다.

이 결제 오류를 위해 우리가 만든 특별한 스킬을 에이전트에 제공할 수 있습니다. 이를 트리아지 스킬(triage skill)이라고 해 보겠습니다. 이 스킬에는 런북이 정리되어 있습니다. 아마 우선 오류율을 살펴봐야 한다고 되어 있을 겁니다. 가장 먼저 해야 할 일입니다. 그런 다음 이 작업을 마치면, 최근 배포 상태를 확인하는 것이 다음 단계라고 스킬이 알려줍니다.

따라야 할 단계들입니다. 하지만 좋은 스킬은 수행할 단계뿐만 아니라, 에이전트가 언제 자체 조사를 중단하고 실제 사람에게 문제 해결을 요청해야 하는지와 같은 판단 기준도 담을 수 있습니다.

이 트리아지 스킬이 없다면 에이전트는 아마 이런 일을 모두 해야 한다는 것을 알지 못할 겁니다. 이 정보가 모델의 학습 데이터 어디에도 들어 있지 않기 때문입니다. 스킬은 에이전트에 명확한 절차와 그 절차를 어떻게 실행할지에 대한 판단 기준을 제공하지만, 거기서 멈춥니다.

스킬은 에이전트에 오류율을 확인하라고 말할 수 있지만, 에이전트가 대시보드에 접근해 실제로 오류율을 읽을 수 있다는 보장은 여전히 없습니다. 오류율과 유사한 정보를 얻는 한 가지 방법은 MCP를 사용하는 것입니다.

MCP는 모델 컨텍스트 프로토콜(Model Context Protocol)입니다. MCP는 에이전트를 외부 세계에 연결해 실제로 외부에 나가 작업을 수행할 수 있게 합니다. 작동 방식은 에이전트와 에이전트가 접근해야 하는 대상 사이에 표준 MCP 프로토콜이 위치하는 것입니다.

에이전트 자체는 MCP 호스트(host)로 간주되며, 에이전트가 대화하려는 각각의 시스템은 MCP 서버(server) 뒤에 놓입니다. 이 모델 자체만으로는 특정 로깅 스택(logging stack)을 사용하는 백엔드를 어떻게 조회해야 하는지 전혀 모를 수 있지만, 해당 로깅 스택용 MCP 서버는 그 스택에 연결하는 방법을 알고 있습니다. 그리고 그 연결을 에이전트가 호출할 수 있는 기능으로 공개합니다.

500 오류로 돌아가 봅시다. 스킬은 오류율을 확인하라고 했습니다. MCP를 사용하면 에이전트가 이 모든 정보에 접근할 수 있습니다. MCP 호출을 수행해 모든 로그를 가져올 수 있습니다. 같은 방식으로 메트릭도 가져올 수 있고, 실제 오류율을 읽을 수도 있습니다.

오류율을 가져오는 문제는 MCP로 해결됩니다. 다른 서비스에 호출을 보내는 것입니다. 하지만 에이전트가 여전히 모르는 것은 이 웹 페이지의 특정 설정이 어떻게 작동하는지입니다. 무엇이 정상인지, 의존성이 무엇인지, 그리고 이런 문제 중 일부가 이전에 무엇 때문에 발생했을 수 있는지 알지 못합니다.

그렇다면 그 지식은 어디에서 올까요? 아마 예상하셨겠지만, 제 목록에 있는 나머지 두 가지에서 옵니다.

RAG부터 시작해 보겠습니다. 이는 검색 증강 생성(retrieval-augmented generation)입니다. 모든 것을 처음부터 컨텍스트 창에 집어넣는 대신, 에이전트가 필요한 정보, 즉 외부 소스에서 가져온 관련 정보를 실제로 필요할 때만 불러온다는 개념입니다.

결제 오류의 경우, RAG가 우리가 보유한 문서 모음을 참조하도록 할 수 있습니다. 여기에는 매뉴얼, 의존성 맵 및 유사한 리소스가 포함될 수 있습니다. 에이전트가 질문을 하면 RAG는 시맨틱 검색(semantic search)이라는 작업을 수행해 일치하는 부분을 가져옵니다. 관련성이 높은 일치 청크가 에이전트의 컨텍스트 창으로 반환됩니다.

이것이 RAG입니다.

마지막으로 이야기할 것은 메모리입니다. 처음 보면 메모리는 에이전트가 필요할 때 관련 지식 일부를 불러온다는 점에서 RAG와 상당히 비슷하게 들립니다. 하지만 이 둘에는 차이가 있으며, 그 차이는 지식이 어디에서 오는가에 있습니다.

RAG는 벡터 데이터베이스(vector database)에 저장된 문서를 읽습니다. 누군가 그 문서를 벡터 데이터베이스에 넣었고, 의도적으로 저장한 것입니다. 반면 메모리는 이전에 일어난 일에서 에이전트가 스스로 습득해 나중에 사용하기 위해 저장한 것입니다.

에이전트는 이전 오류 상황과 같은 일종의 메모리를 되돌아볼 수 있습니다. 아마 지난번에 똑같은 오류가 발생했을 때 실제 원인은 런북에 문서화되어 있지 않았고, 힘든 방식으로 해결해야 했을 겁니다. 그 메모리는 그 힘든 방식이 무엇이었는지 알려줄 수 있습니다.

이 성가신 500 오류가 마침내 해결되면, 메모리는 실제 해결 방법이 무엇이었는지도 다시 기록할 수 있습니다. 그러면 다음번에 에이전트가 그 정보를 사용할 수 있습니다. 여기서 에이전트의 에이전틱 메모리(agentic memory)에 경험이 축적됩니다.

이것이 네 가지 전부입니다. 각각을 언제 사용할지에 대한 대략적인 경험칙은 다음과 같습니다.

누군가가 글로 작성해 둔 지식이라면 RAG입니다.

에이전트가 경험을 통해 습득한 지식이라면 메모리입니다.

따라야 할 절차, 즉 반복 가능한 작업이라면 에이전트 스킬입니다.

그리고 에이전트가 독점 코드를 사용하지 않고 실제 세계에서 무언가를 찾아봐야 한다면 MCP를 사용할 수 있습니다.
