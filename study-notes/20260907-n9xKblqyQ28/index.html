먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 3분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상에서 하네스는 언어 모델을 현실의 일과 연결하는 운영 장치다. 모델 자체가 두뇌라면 하네스는 기억, 파일, 도구, 실행 공간, 하위 에이전트, 사용 한도와 권한을 관리한다. 발표자들은 같은 모델도 이 장치를 어떻게 구성하느냐에 따라 문제 해결 성능과 비용이 크게 달라질 수 있다고 주장한다.

문제는 모델이 한 번에 볼 수 있는 정보가 제한되고, 긴 작업에서는 맥락을 잃거나 너무 일찍 포기한다는 점이다. 이를 풀기 위해 필요한 정보를 외부에 저장하고, 오래된 정보를 정리하며, 작업을 다른 에이전트에게 나누고, 결과를 평가해 다음 실행 규칙을 고친다. 이를 에이전트형 맥락 관리와 자기개선 하네스라고 부른다.

다른 발표는 개인 기기에서 모델을 실행해 비용과 데이터 전송을 줄이거나, 업무용 에이전트가 작업에 맞는 모델과 실행 환경을 고르게 하는 방법을 소개한다. 그러나 기능을 많이 주는 것만으로 충분하지 않다. 비용이 폭증할 수 있고, 잘못된 평가를 따라 시스템 전체가 아니라 일부 사례에만 맞춰질 수 있으며, 권한이 약하면 비공개 정보가 새어 나갈 수 있다. 따라서 좋은 하네스는 기능 수가 아니라 고정된 예산에서의 성공률, 장기 작업의 진전, 사람의 검토가 필요한 지점, 정보 접근 범위로 평가해야 한다.

여기까지만 이해하면 충분

  • 하네스는 모델의 기억·도구·실행·권한을 관리해 실제 능력을 바꾸는 운영 계층이다.
  • 긴 작업에는 맥락 정리, 하위 에이전트, 외부 상태 저장과 평가가 필요하다.
  • 더 많은 자율성은 성능뿐 아니라 비용·오류·정보 유출 위험도 함께 키울 수 있다.
  • 모델 이름보다 같은 작업과 예산에서 얻은 성공률과 안전성을 비교해야 한다.

비유와 깨지는 지점

작업자와 작업장

언어 모델이 작업자라면 하네스는 공구함, 창고, 작업일지, 동료 호출 장치와 출입 규칙이 있는 작업장이다. 같은 작업자라도 필요한 도구와 기록을 제때 쓸 수 있으면 더 복잡한 일을 처리할 수 있다.

비유가 깨지는 지점: 하네스는 단순한 시설이 아니라 다음 입력을 직접 구성하고 모델의 행동 범위를 바꾼다. 또한 모델의 판단은 일정하지 않으므로 도구를 제공했다고 올바르게 사용한다는 보장은 없다.

1. 원인

같은 모델 가중치를 사용해도 하네스에 따라 결과가 달라질 수 있는 이유는 무엇인가?

모범 답안 보기

모델은 현재 입력과 제공된 행동 수단 안에서만 다음 결정을 내린다. 하네스가 외부 기억, 계산 도구, 하위 에이전트, 피드백과 지속 실행을 제공하면 모델이 접근할 정보와 가능한 행동이 달라진다. 다만 성능 차이가 모델이 아니라 하네스 때문이라고 말하려면 같은 과제·예산·평가 조건으로 비교해야 한다.

2. 대조

‘표현력 높은 하네스’와 ‘얇은 하네스’는 어떻게 함께 이해할 수 있는가?

모범 답안 보기

표현력은 모델이 필요한 도구·메모리·실행 환경을 선택할 수 있게 한다는 뜻이다. 얇다는 말은 하네스가 고정된 작업 절차를 과도하게 강제하지 않는다는 뜻으로 볼 수 있다. 선택지는 넓게 주되 핵심 제어 계층은 작게 유지할 수 있으므로 반드시 반대 개념은 아니다.

3. 적용

새 에이전트 기능을 도입할 때 모델 이름보다 먼저 무엇을 비교해야 하는가?

모범 답안 보기

같은 실제 과제와 같은 시간·토큰·비용 한도를 정하고 성공률을 비교한다. 이어 실패 시 중단 가능성, 사람 검토가 필요한 쓰기 작업, 접근 가능한 정보 범위까지 확인한다. 성능이 좋아도 비용이나 권한 위험이 허용 범위를 넘으면 확대하지 않는다.

이번 글의 통찰

1. 모델 성능은 모델 파일만의 속성이 아니다

  • [원문] 진행자는 ARC-AGI 사례에서 같은 모델이 기본 구성에서는 30%, 하네스로는 95%에 이르렀다고 주장했다. Seth는 Prime Agent에서 Opus가 95.5%를 기록했다고 말했다.
  • [해석] 실제 제품 성능은 모델과 하네스가 결합된 결과다. 따라서 모델 교체와 하네스 개선을 별도의 투자 선택지로 비교해야 한다.
  • [경계] 30%, 95%, 95.5%, NVIDIA AVO의 100%는 평가 버전·예산·샌드박스 조건이 충분히 제시되지 않았다. Seth의 GPT-4o 결과도 78%와 25.7%가 모두 등장하지만 차이를 설명하는 조건이 불분명하다. 99.9% 결과는 발표자가 로그를 확인한 뒤 부정행위가 있었다고 폐기했다.

2. 장기 작업에는 기능 추가보다 상태 관리가 중요하다

  • [원문] Seth는 맥락 압축, 외부 상태, 지속형 하위 에이전트, 에이전트 간 메시지와 과거 실행을 반영하는 개선 기능을 제시했다. QM 발표자는 에이전트가 너무 일찍 포기하지 않도록 시간이나 토큰 예산을 부여했다고 말했다.
  • [해석] 장기 작업의 핵심은 한 번의 영리한 답보다 작업 상태를 보존하고, 실패를 발견하며, 제한된 자원을 다음 시도에 배분하는 능력이다.
  • [경계] 발표된 장기 실행 사례만으로 각 기능의 개별 효과를 분리할 수 없다. Seth도 8대의 H200을 일주일 사용한 실험에서는 하네스와 모델의 효과를 구분하기 어렵다고 밝혔다.

3. 개인 AI의 병목은 비용에서 권한과 검증으로 이동한다

  • [원문] OpenJarvis 발표자는 로컬 실행의 비용·지연·개인정보 이점을 주장했다. QM 발표자들은 중앙화된 대화 상태, 사람 검토 후 데이터베이스 쓰기, 세밀한 권한 체계가 필요하다고 말했다.
  • [해석] 실행 비용이 내려가고 연결 가능한 자료가 늘수록, 어떤 정보에 누가 접근하고 어떤 변경을 사람이 승인할지가 더 중요한 설계 문제가 된다.
  • [경계] OpenJarvis의 800배 비용 절감과 로컬 모델의 6~12개월 격차는 발표자의 주장으로, 작업·하드웨어·비용 산식이 이 전사에 없다. META의 원작자·소속 값은 추정 자료이며 실제 발표자 구성과 일치한다고 검증되지 않았다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 발표자들은 모델 능력을 단일 답이 아니라 장기 실행, 도구 사용, 수정 행동으로 관찰했다.
  • 통찰: 학습자의 이해도 정답 한 줄보다 설명, 도구 선택, 오류 수정 과정으로 확인할 수 있다.
  • 질문/행동: 같은 문제를 다시 보지 않고 설명하게 한 뒤, 틀린 부분을 스스로 찾아 고칠 수 있는지 관찰한다.

사업가 · 구조적 비유

  • 관련성: 하네스 선택은 성능뿐 아니라 API 비용, 하드웨어, 사람 검수와 정보 유출 위험을 바꾼다.
  • 통찰: APOM에 적용한다면 아직 검증되지 않은 가상 적용으로 두고, 특정 반복 업무의 절감 시간보다 오류 검수 비용과 권한 위험까지 함께 계산해야 한다.
  • 질문/행동: 어떤 한 업무가 같은 비용 한도에서 더 자주 완료되는지부터 시험할 수 있는가?

마케터 · 직접 전이

  • 관련성: 30%에서 95%, 800배 절감 같은 숫자는 강한 대조를 만들지만 비교 조건이 생략돼 있다.
  • 통찰: 큰 숫자를 카피로 옮기기 전에 과제, 기준선, 비용 범위, 실패 사례를 함께 보여줘야 증거가 된다.
  • 질문/행동: 주장 옆에 동일 조건의 전후 결과와 폐기된 실패 실행도 공개할 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 맥락 관리, 하위 에이전트, 샌드박스 선택, 평가와 권한은 자동화 시스템에서 직접 시험할 수 있는 요소다.
  • 통찰: 기능을 한꺼번에 늘리지 말고 동일 작업에서 하네스 요소 하나가 성공률과 비용을 어떻게 바꾸는지 분리해 측정해야 한다.
  • 질문/행동: 고정 예산에서 외부 메모리 하나를 추가했을 때 검수 통과율이 실제로 높아지는가?

가치 지도

→ "더 안정적으로 완료된 업무와 줄어든 대기·반복 작업" 수혜자: 에이전트 사용자와 검수자

→ "동일 예산에서 사람 검수를 통과한 작업의 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 같은 반복 정보정리 과제 10건을 동일한 시간·토큰 한도에서 기본 구성과 외부 메모리를 추가한 구성으로 각각 실행한다.
  • 측정 1개: 두 구성의 사람 검수 통과율 차이
  • 중단 기준 1개: 외부 메모리 구성의 검수 통과율이 기본 구성보다 높지 않으면 확대를 중단한다.

5 수치·이름·열거 충돌 전사 안에서 확정할 수 없는 불일치와 미검증 주장

1. 하네스의 역사와 자기개선

진행자는 하네스를 단순한 프롬프트 포장이 아니라 모델과 환경 사이에서 맥락, 도구, 상태와 실행을 관리하는 계층으로 설명했다. Harness One과 Harness Two 사이에 18% 향상이 있었다고 주장했으며, METR의 장기 작업 그래프에서 나타난 발전의 상당 부분도 하네스 덕분이라고 해석했다.

발표에서 제시된 흐름은 GPT-2의 단순 반복 실행에서 시작해 few-shot 예시, 생각 과정을 여러 토큰에 펼치는 chain of thought, WebGPT·Toolformer의 도구 호출, MemGPT의 맥락 읽기·쓰기, Voyager의 재사용 가능한 기술, ReAct·Self-Refine·Reflection의 평가와 수정, 재귀형 하위 에이전트로 이어진다.

정적 하네스 다음 단계로는 시스템 프롬프트를 탐색하는 DSPy, 하네스 코드까지 바꾸는 Darwin machines, 실행 이력으로 메모리·기술·프롬프트를 수정하는 Continual Harness가 소개됐다. 진행자는 ICL이 40~50개 예시 이후 검증 성능을 더 높이지 못했던 자신의 실험도 언급했다.

자동 연구 사례에서는 여덟 아이디어를 여덟 개의 H100 노드에 배정하고 각 노드에 H100 여덟 대를 사용한다고 말했다. 이는 진행자가 자신의 연구 초기 아이디어를 시험하는 현재 방식이라고 주장한 내용이며, 논문의 품질이나 비용 대비 효과는 독립적으로 검증되지 않았다.

2. Prime Agent

Seth Karten은 원시 언어 모델을 고정 가중치와 현재 맥락을 이용해 다음 토큰을 내는 순차 처리기로 설명했다. Prime Agent는 그 위에 지속 상태, IPython 실행 환경, 도구, 메모리와 하위 에이전트를 제공한다. 노트북을 닫아도 작업이 계속되도록 로컬 데몬을 사용한다고 말했다.

맥락은 캐시에 비유됐다. 모델 가중치와 활성 맥락은 빠르게 접근하는 층이며, RAM의 변수·실행 중인 하위 에이전트와 파일 시스템은 더 바깥의 상태다. 압축, 불필요한 변수 정리, 기술과 메모리의 수정·삭제를 통해 장기 실행 중 자원 고갈을 막는다는 구상이다.

평가 주장에는 다음 수치가 포함됐다.

  • 부정행위가 섞인 첫 ARC-AGI 실행: 99.9%로 나왔으나 발표자가 폐기
  • GPT-4o: 설명 중 78%와 25.7%가 각각 등장
  • Opus: 95.5%
  • Air Agent 비교: 약 5,000달러를 쓴 뒤 진전이 적어 중단
  • H200 여덟 대를 일주일 사용한 자동 연구: 변동성이 높아 하네스 효과를 분리하기 어렵다고 인정
  • Factorio 7일 실행: 총 633개 에이전트와 2,300만 출력 토큰 사용

Seth는 장기 작업을 비교할 때 동일한 지출 한도를 사용하고, 추가 토큰을 투입해도 성능이 조금만 증가하는 실용적 정체점을 찾아야 한다고 주장했다.

3. OpenJarvis

Jon Saad-Falcon은 개인 AI가 주로 클라우드 모델에 의존해 비용, 개인정보, 에너지와 소유권 문제가 생긴다고 주장했다. 로컬 모델은 당시 최상위 클라우드 모델보다 6~12개월 뒤처진 수준이며 격차가 줄고 있다고 말했다. 예시로 Qwen 3.8 27B와 과거 Claude 4.6 Opus를 비교했지만, 전사에는 평가 조건이 없다.

OpenJarvis는 사용자 인터페이스, 에이전트 논리, 언어 모델, 추론 엔진과 하드웨어, 도구·메모리, 학습·최적화를 조합하는 구상이다. 클라우드 모델이 로컬 구성을 진단하고 개선안을 만든 뒤 실제 반복 실행은 로컬에서 수행하는 방식도 제안됐다.

발표자는 특정 개인 AI·코딩·에이전트 작업에서 로컬 구성이 클라우드와 경쟁할 수 있었고 실행 비용이 800배 낮았으며 지연도 줄었다고 주장했다. 동시에 로컬 크기의 모델로 부족한 작업이 여전히 많다고 인정했다. 향후 일상 추론의 큰 비중, 어쩌면 과반이 로컬 기기로 이동할 것이라는 내용은 전망으로 제시됐다.

4. QM

Josh France와 Regan Bell은 QM을 직원마다 개인 맥락, 샌드박스, 파일과 예약 작업을 제공하고 Slack과 웹에서 사용할 수 있는 업무용 하네스로 소개했다.

내부 개발 흐름은 다음과 같이 설명됐다.

  • 2025년 1월: 시스템 프롬프트와 도구 반복 구조의 ‘general agent’
  • 2025년 6월: Claude Code와 Codex를 VM에서 실행하고 Slack 태그, CI와 개발 환경에 연결
  • 발표 시점 기준 ‘올해’ 1월: 파트너들이 OpenClaw 사용
  • 4월: VM에서 50개가 넘는 Hermes 에이전트 운영
  • 5월 무렵: 개별 컴퓨터에 갇힌 구조를 벗어나는 QM 구상

QM은 대화 상태를 Postgres에 중앙화하고 샌드박스를 에이전트가 필요할 때 선택하는 자원으로 취급한다. 무거운 개발 작업에는 더 강한 환경을, 단순 작업에는 가벼운 환경을 고르게 하며 모델 제공자도 바꿀 수 있다고 설명했다.

핵심 하네스는 원격 샌드박스 실행, 객체 저장소 읽기·쓰기, 내부 앱 게시의 세 도구를 중심으로 얇게 유지하려 한다. 데이터베이스는 주로 읽기 전용이며 쓰기는 사람이 검토한 일괄 upsert를 사용한다. 다만 검토자가 제안을 습관적으로 승인하는 현상도 관찰돼 계속 살펴볼 계획이라고 했다.

자동 개선은 혼합된 결과를 보였다. 여러 에이전트가 각자 본 실패만 고치게 하면 시스템 전체를 보지 못하는 ‘주인공 증후군’이 생겼고, 사람의 개입이 계속 중요했다고 밝혔다. 또한 긴 조사에서 너무 빨리 포기하지 못하도록 몇 시간이나 토큰 지출을 목표 예산으로 주는 ‘grind tool’을 시험했다고 말했다.

마지막 위험은 사회적 맥락이다. 에이전트는 전달받은 정보가 어느 대화에서 공유 가능한지 자연스럽게 판단하지 못하며, 권한 체계가 약하면 비공개 정보가 다른 맥락으로 유출될 수 있다고 경고했다.

5. 수치·이름·열거 충돌

  • 진행자는 “세 명의 저자”가 있다고 말한 뒤 Seth Karten, Jon Saad-Falcon, Josh France, Regan Bell의 네 이름을 발표자로 소개했다. Ben의 불참도 언급됐지만 ‘세 명’의 집계 기준은 설명되지 않았다.
  • OpenJarvis는 “다섯 가지 기본 요소”라고 했지만 첫 설명에는 사용자 인터페이스, 에이전트 논리, 모델, 추론 엔진·하드웨어, 도구·메모리, 학습의 여섯 묶음이 등장한다. 뒤에서는 intelligence, engine, agentic logic, tools or learning systems, optimization의 다섯 묶음으로 다시 설명해 구성도 일치하지 않는다.
  • GPT-4o의 ARC-AGI 결과로 78%와 25.7%가 모두 제시됐지만 서로 다른 설정인지 명확하지 않다.

  • 99.9% ARC-AGI 결과는 발표자가 샌드박스 문제로 부정행위가 있었다고 확인했으므로 유효한 성능으로 사용할 수 없다.

아주 신나네요. 좋습니다. 왜 하니스(harness)일까요?

제 말은, 이건 그냥 래퍼(wrapper)일 뿐입니다. 그냥 스캐폴딩(scaffolding)입니다. 그냥 프롬프트 엔지니어링(prompt engineering)입니다. 이런 것이 대체 왜 하룻밤을 할 만한 주제가 될까요? 한 달 전쯤 올라온 아주 좋은 Reddit 게시물이 있는데, 사실 가장 공격적인 말입니다. “이런 종류의 프롬프트 엔지니어링이 최상위 머신러닝 학회에 어울리는지 모르겠다.”

또 다른 좋은 글입니다. “컨텍스트 엔지니어링(context engineering)은 연구 문제가 아니다.”

그러니까 하니스는 오랫동안 수준 낮은 연구라며 폄하되어 왔다고 생각합니다. 하지만 실제로는 Harness One과 Harness Two의 차이에서 18% 향상을 만들어 냅니다. Seth가 말해 주겠지만, ARC-AGI를 작동하게 만드느냐 못 만드느냐의 차이입니다. 그러니 이것은 분명 어느 정도 연구할 가치가 있습니다.

이 고전적인 METR 플롯을 보면—출시일과 에이전트가 실행될 수 있는 시간의 관계를 나타낸 것인데—이 발전의 상당 부분은 말 그대로 하니스 덕분이었다고 생각합니다. 저는 이를 정적 하니스(static-harness) 시대라고 부릅니다. 하니스 자체의 자기개선(self-improvement)이 없던 시기죠. 그리고 최근의 시기, 아마 지난 6개월 정도는 모두 자기개선 하니스에 관한 것이었습니다.

사실 저는 Trajectory의 CEO가 발표에서 이 플롯을 보여 주는 것을 봤습니다. 정말 마음에 들었습니다. 그는 우리가 계속 퍼플렉서티(perplexity)를 측정하고 있다고 말했습니다. 퍼플렉서티는 IQ와 모델의 지능이 어느 정도 상관관계가 있죠. 우리는 이 지능, 즉 IQ 차원을 계속 더 밀어 올리고 있지만, 테스트 타임 경험(test-time experience)은 별로 활용하지 않고 있습니다.

우리는 테스트 타임 경험을 이토록 많이 생성하고 있습니다. 새로운 도메인이 생겼는데도 실제로 빠르게 적응하지 못합니다. 예전에 진행했던 첫 YC Paper Club 중 하나를 기억하신다면, 저는 온라인 샘플 수를 늘려 가면서 배치 크기 1만으로 어떻게 학습할 수 있는지 실험하고 있었습니다. 우리에게는 그런 구조가 정말 없습니다.

우리에게는 ICL(in-context learning)이 있고, 약 40~50개의 예시를 불러온 뒤 ICL이 포화되면 검증 세트에서는 전혀 더 나아지지 않습니다. 그러고 나면 작은 랭크의 LoRA로 가고, 큰 랭크의 LoRA로 가고, 그다음에는 SFT(supervised fine-tuning)로 갑니다. 이런 서로 다른 학습 절차가 있다는 것이 조금 이상합니다. 저는 바로 그 지점에서 하니스가 빛을 발한다고 생각합니다.

ARC-AGI가 드러내는 것, 그리고 ARC-AGI의 핵심은 새로운 문제와 새로운 분포에 얼마나 빠르게 적응하고, 그 안에서 얼마나 잘 수행하는가입니다.

어떤 일이 일어나는지 상상해 볼 수 있습니다. 하니스와 시스템 프롬프트로 구성된 서로 다른 에이전트가 많이 들어 있는 아카이브가 있고, 그중에서 샘플을 뽑습니다. 이들을 실행하고, 어떤 적합도 함수(fitness function)에서 얼마나 잘했는지 평가한 다음, 다시 아카이브 상태에 추가합니다.

자기 수정(self-modification)을 건너뛰었네요. 에이전트가 자신의 하니스를 수정해 다른 하니스가 될 수 있도록 하는 메타 하니스(meta-harness)를 실제로 만들 수 있습니다. 그러면 이 과정이 계속 순환하고, 결국 시간이 지날수록 점점 더 나은 에이전트를 얻게 됩니다. 메타 하니스, 즉 메인 하니스의 역할은 하니스를 생성하는 것이죠. 정말 메타적인 개념입니다.

생각해 보면—소개와 모든 배경 문헌이 정말 좋았고, 매우 멋지다고 생각했으며, 제가 이 문제를 생각하는 방식과도 상당히 잘 맞습니다—순수한 LLM 자체는 사실 고정된 가중치와 가시적인 컨텍스트를 가진 순차 처리기(sequential processor)일 뿐입니다. 다음 결정을 내리기 위해 토큰을 입력받고 토큰을 출력합니다.

요즘 우리는 LLM을 실제로 그런 식으로 생각하지 않습니다. LLM이 접근할 수 있는 파일 집합이 있고, 끝없이 많은 프로그램과 도구를 사용할 수 있게 합니다. 진행 중인 다른 LLM 세션에 메시지를 보내고, 이런 멋진 일들을 수행하기 위해 서브 에이전트를 만들 수도 있습니다. 하지만 기본적으로는 토큰 입력, 토큰 출력입니다. 예측을 수행하는 신경망인 것이죠.

하니스 자체는 LLM과 세계 사이에 있는 계층으로, 영속 상태(persistent state), 도구, 컴퓨팅 같은 것을 추가합니다.

여기에는 사람이 보는 관점에서 Prime Agent를 어떻게 생각하는지에 대한 다이어그램이 있습니다. Claude Code, Codex, Pi 등을 사용할 때처럼 컴퓨터에서 Prime Agent를 엽니다. 그러면 에이전트 뷰로 들어가는데, 이 에이전트 뷰는 병렬로 진행 중인 모든 세션의 모든 에이전트를 개괄적으로 보여주며, 현재 사용 중인 내용을 매우 간결하게 요약합니다. 그런 다음 그중 하나로 들어가 살펴볼 수 있습니다.

그곳에서는 루트 세션(root session)에 있게 됩니다. 이 루트 세션은 기본적으로 자신이 제어하는 서로 다른 모든 서브 에이전트 위에서 작동하는 프로젝트 오케스트레이터입니다. 서브 에이전트를 시작하라고 요청할 필요가 없습니다. 유용할 때 스스로 서브 에이전트를 활용합니다.

이 모든 것은 프로그래밍 방식으로 호출됩니다. 전체가 재귀적 언어 모델(Recursive Language Model) 원리에 기반하고 있으며, 모든 도구, 메모리, 서브 에이전트가 이 IPython 셸 안에 있기 때문입니다. 더 나은 조정을 위해 이러한 메시징 패러다임을 노출하므로, 이 모든 것을 관리할 수 있습니다. 에이전트는 여러분의 환경과 직접 상호작용할 수 있습니다. 환경은 컴퓨터에 있는 프로그램과 파일일 수도 있고, 자동 연구(auto-research)를 위한 H200 노드 클러스터를 실행하는 것일 수도 있습니다.

각 에이전트는 컴퓨터에서 실행되는 이 영속 데몬(persistent daemon)에 의해 뒷받침됩니다. 따라서 노트북을 닫거나 세션에서 Control-C를 눌러도 백그라운드에서 계속 실행됩니다. 계속 실행되는 것을 확실히 멈추려면 실제로 세션을 중지해야 합니다.

또한 Continual Harness에서 제공하는 다른 기능들도 노출되어 있습니다. 이를 통해 앞서 언급한 모든 구성 요소에 대해 실시간 CRUD 작업을 수행할 수 있습니다. 메모리, 스킬, 서브 에이전트, 지속성을 관리하고 자체 시스템 프롬프트를 지속적으로 프롬프트할 수 있습니다.

우리가 구축하고 있는 이 모든 컨텍스트를 생각하는 제가 좋아하는 방식은 다음과 같습니다. 여기에는 L1, L2, L3가 있는데, 일종의 캐시와 같습니다. 우리가 작업하는 정보 중 가장 접근하기 쉬운 것은 무엇일까요? 가장 빠르고 즉시 이용 가능한 수준에서 모델이 정보를 매우 빠르게 검색할 수 있게 해주는 것은 모델 가중치입니다.

모델 가중치에 모든 정보를 넣고 싶어 하는 것이 일반적입니다. 하지만 그러면 우리는 이렇게 말하죠. Fine-tuning을 매번 해야 업데이트할 수 있는 것은 아니라고요. 그건 매우 비용이 많이 들기 때문입니다. 그래서 우리에게는 이 능동 입력 컨텍스트(active input context)가 있습니다. 입력에 아주 많은 토큰을 사용하고 있죠. 서로 다른 능력을 추가하기 위해 이전에 봤던 인컨텍스트 예시(in-context examples)를 넣기도 하지만, 어느 시점이 되면 컨텍스트가 고갈됩니다.

지금까지 본 하니스(harness)의 가장 초기 형태이자, 가장 최소한의 하니스만 원한다고 말하는 사람들도 오늘날 여전히 사용하는 것은 압축(compaction)입니다. 압축은 에이전트가 자신의 컨텍스트 기록을 요약해 컨텍스트 길이로 제한된 작업 창을 넘어 계속 작업할 수 있도록 하는 매우 일반적인 도구입니다.

여기서 모델의 직접적인 입력과 출력인 부분을 넘어 L2와 L3로 들어간다고 생각해 봅시다. L3는 디스패치 상태(dispatch state)에 가깝다는 점에서 익숙할 수도 있습니다. 파일 시스템을 다룬다면 주 메모리에서 읽고 쓸 수 있죠.

제가 능동 컨텍스트와 파일 시스템 작업 사이의 중간 단계라고 생각하는 L2에서는, 라이브 리플(live ripple)[?source]이 있을 수 있습니다. 이는 주피터 노트북에 있는 것처럼 Python이나 IPython 셸에서 직접 실행하는 것일 수 있습니다. 모든 변수는 RAM에 바로 저장됩니다. 그러면 에이전트가 이를 프로그래밍 방식으로 조작하고, 그 안의 정보에 대해 온갖 프로그램을 직접 실행할 수 있습니다. 정보를 컨텍스트에 직접 넣는 대신 토큰을 엄청나게 절약할 수 있죠.

서브에이전트(sub-agent)를 만들 수도 있는데, 이것도 같은 방식입니다. 특정 정보 집합을 바탕으로 어떤 작업을 수행하도록 에이전트에 맡긴 다음 마지막에 결과를 보고하게 할 수 있으므로, 기본적으로 여기서 컨텍스트를 저장하는 셈입니다.

여기서 흥미로운 점은 능동 컨텍스트에 대한 압축과 관련해 우리가 이야기했던 부분입니다. 컨텍스트 기록이 있죠. 이것은 시간이 지나면서 그 기록을 업데이트해 계속 활용할 수 있도록 도와줍니다.

하지만 이 단계를 넘어가면, 이런 업데이트를 어떻게 수행할지 생각해야 합니다. 우리는 CRUD에 대해 이야기했죠. 단순히 생성하고 읽는 것을 넘어 어떻게 할 것인가요? 컨텍스트 한계를 넘어, 시간에 따른 상태를 넘어, 시간이 지나면서 컨텍스트를 어떻게 업데이트하고 삭제할 것인가요?

저는 이것을 에이전트형 가비지 컬렉션(agentic garbage collection)이라고 생각합니다. 상태에 있는 변수들을 정리하고, 어떤 서브에이전트를 사용할 수 있을지도 생각하는 것이죠. 이렇게 해야 RAM 때문에 제 노트북이 매일 다운되지 않습니다.

그 위에는 정제(refinement)라는 개념이 있습니다. 시스템에 저장된 기술(skills), 메모리(memories), 프롬프트를 업데이트하고 삭제하는 것입니다. 이는 하드 드라이브의 공간이 실제로 고갈되지 않도록 하는 방법이라고 생각할 수도 있습니다. 본질적으로는 이렇게 표현할 수 있습니다. 이것이 우리가 이 항목을 표현하는 방식이고, 시간이 지나면서 이렇게 수정하는 방식입니다.

제가 정말 좋아하고, 하니스가 우리가 만들고 있는 에이전트형 운영체제(agentic operating system)로 향하고 있기 때문에 특히 강조하고 싶은 또 다른 관점은 이를 좀 더 은유적으로 생각하는 것입니다. 원시 LLM을 보면 튜링 머신(Turing machine)에 더 가까워 보입니다. 티커 테이프(ticker tape)가 있고 모든 지시가 들어간 다음, 어떤 연산을 수행하고 빠져나오는 형태죠.

하지만 하니스를 보면 폰 노이만 컴퓨터(von Neumann computer)에 훨씬 가까워 보입니다. 외부 메모리에 대해 읽기와 쓰기 연산을 수행할 수 있고, 그 덕분에 튜링 머신이 스스로 표현할 수 있는 것보다 훨씬 강력해지며 다른 종류의 문제도 처리할 수 있습니다.

좋은 하니스를 만드는 방법은 상상할 수 있는 것 중 가장 표현력이 높은 것으로 만드는 것입니다. 모델이 스스로 개선될 수 있는 데이터 플라이휠(data flywheel)에 들어가기 전의 초기 하니스들은 매우 구체적입니다. 계획하고, 행동하고, 비평하고, 정확히 정해진 특정 단계들을 수행하죠.

이제 모델은 그런 일을 스스로 할 수 있습니다. 따라서 ReAct 루프(ReAct loop)를 명시적으로 강제할 필요는 없다고 생각할 수 있습니다. 모델이 이를 본래적으로 터득했기 때문입니다. 하지만 아직 터득하지 못한 것은 압축을 호출할 수 있는 표현력을 갖춰야 한다는 점입니다. 프로그램을 실행할 수 있도록 Python REPL이 필요하고, 프로그래밍 방식으로 서브에이전트를 만들고, 상태에 접근하고, 서로 다른 피드백 메커니즘을 사용할 수 있어야 합니다.

이것들은 모델이 제어하는 표현력 기능(model-controlled expressibility features)입니다. 그중 하나라도 제거하면 모델이 다른 방식으로는 사용할 수 없는 능력을 실제로 제거하는 셈입니다.

여러분 모두 제 공동 저자인 Alex의 RLM 논문을 잘 알고 있을 것입니다. 정말 훌륭한 작업입니다. 우리가 RLM 논문에 있던 내용을 넘어 하는 일은 에이전트와 서브에이전트를 지속적인 하위 세션(persistent subsessions)으로 생각하는 것입니다.

부모 세션은 새로운 RLM 서브에이전트를 생성하거나 가동할 수 있고, 각각의 서브에이전트는 작업을 수행한 다음 종료되어 부모 세션의 어떤 최종 상태로 결과를 보고합니다. 그 후에는 유휴 상태가 됩니다. 여전히 RAM에서 작동하고 있는 상태죠. 어느 시점이든 부모 세션은 서브에이전트 중 하나에 메시지를 보내 계속 작업하게 할 수 있습니다. 그러면 그동안 쌓아 온 유용한 컨텍스트를 모두 가지고 있으므로, 정보를 놓치거나 이전 컨텍스트에서 이미 개발된 정보를 다시 사용할 필요가 없습니다.

물론 RAM을 많이 사용하고 싶지는 않으므로, 서브에이전트를 비활성 상태로 오프로드할 수 있습니다. 이후 지속적인 서브에이전트 구조에서 메시지를 보내 언제든 다시 호출할 수 있습니다.

제가 이전 논문에서 다룬 지속적 하니스(continual harness)에 대해서도 조금 이야기했습니다. 이 논문은 전체 하니스 상태를 지속적으로 개선하는 방법을 다룹니다. 이것은 코딩 에이전트에 우리가 원하는 또 하나의 기능입니다. 이전의 모든 기록을 활용하는 것이죠.

각 단계에서 어떤 행동과 결과가 있었던 일련의 궤적(trajectories)을 생각해 볼 수 있습니다. 에이전트가 미래의 하니스가 어떤 모습일지 업데이트할 수 있도록 그 모든 정보를 활용하는 능력을 제공하고 싶습니다.

시스템 프롬프트를 바꿔야 할까요? 어떤 스킬을 만들어야 할까요? 저는 스킬을 특정 목표를 달성하기 위한 지시사항이나 프로그램의 집합이라고 생각합니다. 메모리는 중요한 것들에 대한 장기 저장소일 수도 있고, 우리가 이야기한 서브에이전트 사양일 수도 있습니다. 그것도 매우 지속적인 방식으로 말이죠.

나중에 다시 사용하고 싶은 특정 서브에이전트가 있었을까요? 그 컨텍스트가 유용하기 때문입니다. 시간이 지나면서 이런 종류의 성찰이나 정제를 수행할 수 있는 능력만으로도 모델에는 매우 강력합니다.

지금 모델이 이를 완벽하게 수행하는 것은 아니지만, 현재 모델이 할 수 있는 것보다 하니스를 조금 더 뛰어나게 만들려면 갖춰야 할 능력 중 하나입니다. 그러면 그런 추론 기록(reasoning traces)을 얻어 다음 모델 반복에 활용할 수 있고, 모델은 하니스를 다루면서 스스로를 부트스트랩해 점점 더 높은 성능으로 나아갈 수 있습니다.

Prime Agent에서 가장 멋진 기능 중 하나이자, 제가 이 작업을 시작했을 때부터 있었던 기능은 특정 핵가족(nuclear family) 구조 안에서 부모, 자녀, 형제자매 등 어떤 두 에이전트 사이에서도 메시지를 주고받을 수 있는 능력입니다. 제가 작업하면서 처음 추가한 기능 중 하나이기도 합니다.

이 기능을 만든 이유는, 제가 매일 다섯 가지 방향, 아니 50억 가지 방향에서 저를 대신해 모든 일을 수행하는 에이전트들을 관리할 최선의 방법을 계속 고민하고 있었기 때문입니다. 에이전트들이 서로 컨텍스트를 직접 공유하고 조율할 수 있다면 훨씬 나을 것 같았습니다.

그리고 이것은 일반적인 소프트웨어 엔지니어링과 장기 작업에도 매우 훌륭한 것으로 드러났습니다.

하니스를 어떻게 설계할지와 관련해 마지막으로 살펴보는 것은 장기 작업 성능(long-horizon performance)입니다. 저는 작업을 실행해 놓고 에이전트를 내내 돌봐야 하는 상황은 원하지 않습니다. 다시 확인할 준비가 되었을 때 돌아와서 에이전트들에게 무슨 일이 일어나고 있는지 확인하고 싶습니다.

이런 관점은 우리가 살펴보는 평가의 상당수에서 정말 부족하다고 느끼는 부분이기도 합니다. 모델을 충분히 오래 실행하지 않으면 사람들이 이렇게 말하곤 합니다. “이 모델은 이 정도 예산 이후 작동을 멈췄지만, 저 모델은 더 많은 예산으로 계속 작동했다.”

우선 두 모델을 비교할 때 동일하게 고정된 지출을 사용한 것이 아닙니다. 하지만 둘째로, 그렇게 하면 우리가 놓치고 있는 성능이 가려질 수도 있습니다.

장기 작업 성능을 평가할 때 제가 보고 싶은 것은 실질적인 성능의 정체기(practical plateau)입니다. 테스트 시점 토큰(test-time tokens)을 더 투입해도 어느 시점부터 성능이 점진적으로만 향상될까요?

Prime Agent를 어떻게 만들었는지에 대한 설계 철학을 공유한 뒤 보여드릴 실험이 몇 가지 있습니다. 테스트 시점 스케일링(test-time scaling)과 ARC-AGI 결과에 대해 조금 이야기하고, 이것이 실제로 도움이 되는지, 또 왜 도움이 되는지 살펴보겠습니다. 정보 관리, 우리가 작업 중인 REPL, 그리고 이런 긴 컨텍스트에 어떤 도움이 되는지도 보겠습니다.

정말 길고 거의 초장기(ultrahorizon) 작업에 가까운 과제를 수행할 때, 며칠에 걸친 작업을 어떻게 지속할 수 있을까요? 일주일 또는 그 이상 지속될 수 있는 설정에 대해 이런 정제가 일어날 때 실제로 무슨 일이 일어날까요?

이 결과는 아마 여러분 모두 본 적이 있을 것입니다. 하니스 간 비교를 위해 원래 결과에는 포함하지 않았던 데이터 포인트를 하나 추가했습니다.

우리는 이 문제를 해결했습니다. 요즘 하니스를 실행할 때 사람들이 중요하게 생각하는 최선의 평가가 무엇인지 알아보려고 했고, ARC-AGI를 해야겠다고 생각했습니다. 지속적 하니스로 몇 가지 결과를 실행해 Gemini Flash에서 20%를 얻었던 것이 기억났습니다. 아니, Gemini Pro였네요.

적어도 20%는 얻을 수 있다고 생각했습니다. ARC-AGI에 맞게 구조화되지도 않은 일반 하니스가 아주 좋은 성능을 냈다는 점을 사람들이 정말 멋지게 생각했습니다.

그래서 온라인에서 찾아보다가 “좋아, 좋은 시스템 프롬프트(system prompt)를 찾아야겠다. 정보가 손실되지 않도록 해야 하니까”라고 생각했습니다. Prolong이라는 또 다른 커뮤니티 리더보드(community leaderboard)를 발견했고, 그들의 시스템 프롬프트를 가져왔습니다. “좋아, 시스템 프롬프트를 가져오고 나머지는 잊은 다음, 이걸 Prime Agent에 바로 넣어보자”라고 생각했습니다.

이걸 실행하고는 “맙소사, 첫 실행에서 99.9%를 기록했잖아”라고 생각했습니다. 그런데 로그를 살펴보니 제가 치팅을 하고 있었습니다.

“좋아, 여기서는 제대로 샌드박싱(sandboxing)을 해야겠다. 제대로 설정해보자”라고 생각했습니다. 이 작업에 하루를 더 썼습니다. 그런 다음 다시 확인하고는 “맙소사, GPT-4o로 78%를 얻었어. 이건 훌륭한 결과가 되겠는데”라고 생각했습니다.

그다음에는 “다른 몇 가지와 비교해보자”고 생각했습니다. 이번에도 기본 프롬프트만 사용했습니다. 기본 프롬프트는 대략 “월드 모델(world model)을 사용해 ARC-AGI-3를 해결하라. 사용할 수 있는 액션은 다음과 같다”라고 말합니다.

그리고 Prime Agent의 일반 시스템 프롬프트가 있습니다. REPL이 있고, 서브에이전트를 호출할 수 있으며, 프로그래밍 방식으로 사용할 수 있다는 내용입니다.

트레이스(trace)를 살펴보니, 여러 시나리오를 확인하고 이미지를 분석하며 이미지 처리를 하기 위해 다양한 코딩 호출을 많이 수행하고 있었습니다. 우리가 핵심 요소 중 하나로 제공한 REPL을 활용하면서, 합리적으로 추론하고 있는 것처럼 보이는 정말 흥미로운 작업을 많이 하고 있었습니다.

몇 가지 다른 것도 실행했습니다. GPT-4o에서는 25.7%를 기록했는데, 정말 흥미롭습니다. 우리가 이 작업을 하기 전 주에 일어났던 일과 비교해볼 수 있습니다. OpenAI는 평가를 수행할 때 하니스(harness)가 매우 중요하다고 말하고 있었습니다. 우리는 Responses API를 사용했습니다. 이것이 우리가 얻은 결과입니다.

Terra도 실행했는데 거의—이건 끝까지 실행하지는 않았지만—비교했을 때 매우 좋은 결과를 얻었습니다. 이미 GPT-4o extra-high 결과 중 일부보다 더 높은 결과를 내고 있었는데, 정말 놀라운 일이었습니다.

그다음 Opus를 실행해 95.5%를 기록했습니다. 우리는 “이건 말도 안 되게 좋다”고 생각했습니다.

다른 많은 하니스와도 비교했습니다. 어떤 분들은 “Claude Code로도 실행해봤나요?”라고 물었습니다. 실행해봤습니다. 안타깝게도 결과는 좋지 않았습니다. 결과가 좋지 않은 상태로 두기보다는 원래 Claude Code 결과를 사용했습니다. 이후 다른 사람들이 Prime Agent와 유사한 구성으로 실행해 훨씬 좋은 결과를 얻었습니다.

흥미로운 점은 정말 인기 있는 하니스 중 상당수가 Prime Agent가 잘하는 상황에서 반드시 잘 작동하지는 않는다는 것입니다. 예를 들어 Air Agent의 경우, 아주 빠르게 많은 돈을 썼고, 큰 진전 없이 약 5,000달러를 썼기 때문에 중단해야 했습니다. 이것이 그들이 낼 수 있는 최선이었다는 뜻은 아니지만, 실행하는 데 많은 비용이 들었습니다.

저는 비용 대비 성능 비율이 매우 중요하다고 생각합니다. 비용을 절약해주는 요소 중 하나는 컨텍스트(context)를 프로그래밍 방식으로 다룰 수 있다는 점입니다.

OOLONG이나 곧 공개될 코딩용 EmulatorBench 같은 장기 작업(long-horizon) 평가도 여러 개 실행했습니다. 이는 program-bench의 대안입니다. Pimonos, Claude Code, GLM 5.2, Opus 5, 그리고 5.6을 설정으로 사용해 실행했을 때, 여러 모델에 걸쳐 다른 하니스들과 대체로 비슷하거나 약간 더 나은 결과를 얻었습니다.

제가 정말 멋지다고 생각한 것 중 하나는 EmulatorBench라는 벤치마크 대안이 있다는 점입니다. 여기서는 컴퓨터 시스템의 전체 에뮬레이터를 재현하려고 합니다. 또는 이 경우에는 Game Boy Color를 만드는 것입니다. 한번 확인해보세요. 여기서 정말 흥미로운 점은 RLM에서 REPL에 접근할 수 있기 때문에, 최종 해답을 그레이더에 제출하기 전에 프로그램을 사용해 루프 밖 실험(out-of-loop experiments)을 수행하고, 훨씬 더 표현력 있고 자유로운 방식으로 여러 가지를 시도할 수 있다는 것입니다.
