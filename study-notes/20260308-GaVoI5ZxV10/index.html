Claude Code + Playwright = 놀라운 브라우저 자동화입니다

업로드 2026-03-08 · 14.4분 · 원본 영상 ↗
한 줄 요약

Playwright CLI는 MCP·Claude in Chrome 대비 토큰을 약 9만 개 절약하면서 병렬 헤드리스 브라우저 테스트를 Claude Code 안에서 바로 실행할 수 있게 해준다.

내가 모를 만한 것 / 처음 보는 것

  • Playwright CLI — Playwright에 비교적 최근(2026년 초) 추가된 커맨드라인 인터페이스. MCP 서버·확장 프로그램과 별개.
  • 접근성 트리 (Accessibility Tree) — 시각장애인 보조기술을 위해 웹사이트 전체 구조를 매핑한 데이터. Playwright가 브라우저 조작에 이를 활용.
  • 헤드리스 (headless) 브라우저 — GUI 없이 백그라운드에서 실행되는 브라우저. 화면에 창이 뜨지 않음.
  • 헤디드 (headed) 브라우저 — 실제로 화면에 브라우저 창이 보이는 모드. 디버깅·데모 시 사용.
  • 스킬 크리에이터 (Skill Creator) — Claude Code에서 반복 워크플로우를 /스킬명 하나로 패키징하는 도구. (관련 영상 별도 존재)
  • Chase A Plus (Chase AI Plus) — 화자가 운영하는 Claude Code 마스터 클래스·무료 커뮤니티 플랫폼.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Playwright 팀이 직접 MCP vs CLI 비교 영상을 제작했고, 동일 작업에 약 9만 토큰 차이가 났다고 언급.
  2. Claude in Chrome 확장 프로그램은 스크린샷 기반으로 작동 — 스크린샷 한 장이 토큰을 대량 소모하는 구조.
  3. Claude in Chrome은 헤드리스 불가 + 병렬 처리 불가 — 셋 중 가장 비효율.
  4. Playwright CLI는 접근성 트리를 디스크에 저장 후 요약본만 Claude에 전달 → MCP는 전체 트리를 Claude에 직접 주입.
  5. 기본 동작은 헤드리스. 화면을 보려면 명시적으로 "헤디드로 해줘" 라고 말해야 함.
  6. 설치 순서: ① CLI 설치 → ② npx playwright install chromium (브라우저 엔진) → ③ playwright cli install skills (스킬 설정).
  7. Claude Code에 GitHub 저장소 링크를 주면 설치를 알아서 처리해준다고 소개.
  8. 스킬 패키징 방법: 워크플로우 글로 정리 → 스킬 크리에이터에 붙여 넣기 → "메타 스킬로 만들어줘" → 이후 /폼테스터 한 마디로 3개 병렬 에이전트 실행.
  9. 활용 사례로 아마존 쇼핑 자동화, 로그인 세션 유지, 쿠키 관리도 가능하다고 언급.
  10. 자기 프로젝트 코드베이스에서 테스트할 때 접근성 트리 오류가 훨씬 적음 — 페이지 구조를 Claude가 이미 알기 때문.

1. 도입 데모 — 병렬 브라우저 자동화

Claude Code에 "3개의 병렬 서브 에이전트를 띄워서 각각 Playwright 스킬로 폼 제출을 테스트해줘"라고 입력하는 것만으로 서브 에이전트 3개가 생성된다. 각각 엣지케이스·유효성 검사·정상 경로를 동시에 테스트한다. 기존 방식(개발 서버 직접 열고 수동 입력)과 비교하면 속도·커버리지 모두 압도적.

Playwright는 Microsoft가 만든 완전 오픈소스 브라우저 자동화 프레임워크다. CLI는 비교적 최근(2026년 초 기준 몇 주 전) 추가된 기능.

2. 세 도구 비교 — 왜 CLI인가

항목 Playwright CLI Playwright MCP Claude in Chrome
토큰 효율 최고 (요약본만 전달) 낮음 (전체 트리 주입) 최악 (스크린샷 기반)
헤드리스 지원 O O X
병렬 처리 O O X (탭 1개 한정)
속도 빠름 보통 느림

MCP 대비 동일 작업에 약 9만 토큰 절약. Claude in Chrome은 스크린샷을 찍어 화면을 인식하는 구조라 토큰 소모가 크고, 헤드리스·병렬도 안 된다.

3. 작동 원리 — 접근성 트리

Playwright는 접근성 트리 (Accessibility Tree) 를 사용해 웹사이트를 조작한다. 접근성 트리는 시각장애인 보조기술을 위해 전체 웹사이트 구조를 텍스트로 매핑한 데이터다.

  • MCP 방식: 접근성 트리 전체를 Claude에 직접 주입 → 토큰 폭발
  • CLI 방식: 트리를 디스크에 저장 후 요약본만 Claude에 전달 → 토큰 절약

이 차이가 약 9만 토큰 격차의 원인이다.

4. 설치 3단계

# 1. Playwright CLI 설치
npx playwright ...   # (화자가 구체 명령어 언급, GitHub 저장소 참고 권장)

# 2. 브라우저 엔진 설치
npx playwright install chromium
# 다른 엔진 필요 시 문서 참고 or Claude Code에 물어보기

# 3. 스킬 설정
playwright cli install skills

또는 Claude Code에 GitHub 저장소 링크를 주고 "필요한 것 다 설치해줘"라고 하면 자동 처리 가능.

스킬은 Microsoft가 만든 것을 그대로 쓰거나, 직접 수정하거나, 스킬 크리에이터로 검토·개선할 수 있다.

5. 단일 에이전트 UI 테스트 데모

입력한 명령: "Playwright CLI 도구로 폼 제출을 테스트해줘. 단일 에이전트로, 헤디드로 해서 볼 수 있게 해줘."

Claude Code가 스킬을 호출 → 프로젝트 구조 파악 → 브라우저 실행 → 페이지 열기 → 스크롤 → 폼 채우기 → 체크박스 클릭 → 자동 종료 → 테스트 결과 + 스크린샷 제공.

기본값은 헤드리스. 화면에 브라우저를 보고 싶으면 반드시 "헤디드로 해줘"라고 명시해야 한다.

6. 병렬 에이전트 테스트 및 모범 사례 요청

"3개의 병렬 에이전트로 여러 각도에서 공격해줘"

두 문장이면 엣지케이스·유효성검사·정상 경로를 동시에 커버하는 멀티 UI 테스트 완료.

"이 폼을 스트레스 테스트하는 가장 좋은 방법이 뭐야?"라고 Claude Code에 물어보면 최선의 테스트 전략도 제안받을 수 있다. 사용자가 모르는 모범 사례를 Claude가 채워준다.

7. 스킬 패키징 — 워크플로우의 재사용

반복되는 Playwright 테스트 워크플로우를 매번 설명하는 대신, 스킬로 패키징하면 된다.

  1. 워크플로우를 글로 명확하게 정리 ("3개 병렬 에이전트 A, B, C가 X·Y·Z를 해라")
  2. 스킬 크리에이터 열기 → "이 워크플로우를 메타 스킬로 만들어줘" + 전체 내용 붙여 넣기
  3. 폼 테스터 스킬 생성 완료

이후: "폼 테스터 스킬 사용해줘" 한 마디 → 3개 병렬 에이전트 자동 실행.

사고 방식: "이 워크플로우를 표준화할 수 있나? → 표준화했으면 스킬로 만들 수 있나?" 이 루프가 Claude Code 생산성의 핵심.

자, Claude Code. 3개의 병렬 서브 에이전트를 띄워줘. 각각 Playwright 스킬을 사용하고, 방금 변경한 웹사이트의 폼 제출을 테스트해줘. 시작!

지금 보시는 것은 Claude Code가 3개의 서브 에이전트를 생성한 것입니다. 모두 Playwright를 사용하고 있습니다. Playwright는 Microsoft에서 만든 완전 오픈소스 브라우저 자동화 도구입니다. 이것은 Claude Code에 있어 엄청난 돌파구입니다. Claude in Chrome 확장 프로그램이 있음에도 불구하고, 브라우저 자동화는 Claude Code가 정말 어려워하는 영역이었거든요.

여기서 보시는 것이 브라우저 자동화의 훌륭한 활용 사례 중 하나입니다. UI 테스트에 활용할 수 있다는 것이죠. 이 예시에서는 제 웹사이트의 폼 제출 부분을 수정했습니다. 바로 화면 가운데 보이는 부분입니다. 그리고 지금 Claude Code로 여러 각도에서 테스트하고 있는 거죠. 엣지케이스, 유효성 검사, 그리고 정상 경로까지 확인하고 있습니다.

평소라면 이걸 어떻게 했을지 생각해보세요. 직접 개발 서버를 띄우고, 수동으로 하나하나 확인하면서 테스트했을 겁니다. 이름 넣으면 되나, 이메일 넣으면 되나 하면서요. 하지만 이제는 여러 각도에서 동시에 테스트할 수 있습니다. Playwright CLI를 통해 다른 어떤 브라우저 자동화 방식보다 더 효과적이고, 더 효율적이고, 더 쉽게 할 수 있습니다. 다시 말하지만, 저는 아무것도 건드리지 않았습니다. Playwright 스킬이 이 모든 걸 해주고 있습니다.

Claude Code 안에서 이런 걸 할 줄 안다면, 활용 사례와 장점은 정말 엄청납니다. 브라우저와 상호작용이 필요한 모든 곳에서 이걸 사용할 수 있습니다. 이 영상에서는 Playwright CLI의 작동 방식, 설치 방법, 모범 사례, 그리고 가장 중요한 Claude Code 생태계에서 최대한 활용하는 방법을 보여드리겠습니다.

(스폰서: Chase AI Plus에서 Claude Code 마스터 클래스 출시. 기술 배경 무관, 제로에서 AI 개발자까지 실용적으로 안내. 고정 댓글 링크 및 무료 커뮤니티 참고.)

Playwright가 뭘까요? 웹 테스트와 자동화를 위한 프레임워크입니다. Microsoft 제품이지만 오픈소스로 무료 사용 가능합니다. 브라우저를 프로그래밍 방식으로 제어할 수 있습니다.

그런데 Playwright MCP 서버도 있지 않나요? 왜 Playwright CLI에 대해 이야기하는 걸까요? CLI는 사실 Playwright에 비교적 최근에 추가된 기능입니다. 몇 주 전에 나온 겁니다. 그 전에는 MCP를 사용했고, 지난 한 달 정도 Claude in Chrome 확장 프로그램을 보셨을 겁니다.

CLI가 이 두 가지보다 훨씬 나은 이유: 토큰 사용량이 압도적으로 적습니다. MCP는 토큰을 엄청나게 소모합니다. Playwright 팀에서 직접 MCP와 CLI를 비교한 영상이 있는데, 같은 작업에 약 9만 토큰 차이가 났습니다. Claude in Chrome도 토큰을 매우 많이 사용합니다. Claude in Chrome은 웹페이지의 스크린샷을 찍는 방식으로 작동하기 때문입니다. 스크린샷은 토큰을 엄청나게 소모합니다.

사실 이 셋 중에서 Claude in Chrome 확장 프로그램이 가장 비효율적입니다. 헤드리스가 안 되고 병렬 처리도 못하거든요.

헤드리스가 뭐냐고요? 헤드리스 브라우저란 Playwright가 브라우저를 실제로 화면에 열지 않고도 조작할 수 있다는 뜻입니다. 헤디드 브라우저는 실제로 화면에 보이고 상호작용할 수 있는 겁니다. 헤드리스는 백그라운드에서 돌아갑니다. 보이지 않고 마치 투명한 것처럼요. 헤드리스 브라우저가 좋은 이유는 컴퓨터에 부하가 적고 더 효율적이기 때문입니다. 데스크톱의 창이 수십 개 뜨지도 않고요.

MCP도 헤드리스가 가능하고, CLI도 가능합니다. 또 병렬 처리 — 데모에서 3개의 CLI 서브 에이전트가 동시에 테스트를 돌렸죠. Claude in Chrome으로는 이게 안됩니다. 한 번에 하나의 탭만 처리할 수 있고, 느리고 비용도 많이 듭니다. MCP는 가능하고, CLI도 가능합니다.

이 차트를 보면 왜 CLI에 집중하는지 명확하실 겁니다. MCP Playwright 서버가 할 수 있는 모든 걸 CLI로 할 수 있고, 그 이상도 가능하며, 토큰 사용량은 훨씬 적습니다.

왜 이렇게 큰 토큰 차이가 나는지에 대한 흥미로운 이야기입니다. Playwright가 실제로 작동하는 방식은 접근성 트리 (Accessibility Tree) 라는 걸 사용합니다. 웹사이트에 접속하면 접근성 트리라는 것이 있는데, 기본적으로 볼 수 없는 사람도 사용할 수 있도록 전체 웹사이트를 매핑한 것입니다. 시각장애인이 웹사이트를 사용할 수 있도록 돕는 전체 구조, 그 뒤에 있는 기술이 바로 접근성 트리입니다.

하지만 Playwright MCP 서버는 전체 접근성 트리를 통째로 Claude Code에 넣습니다. 접근성 트리는 실제로 꽤 큽니다. 그래서 토큰이 엄청나게 소모됩니다. Playwright CLI는 조금 다릅니다. 같은 접근성 트리를 가져오긴 하지만, 그 모든 정보를 Claude Code에 넣지는 않습니다. 대신 그 트리를 가져와서 컴퓨터의 디스크에 저장하고, Claude Code에는 트리의 요약본만 전달합니다. 모든 정보를 주는 게 아니라 필요한 정보만 줍니다. 이렇게 하면 토큰 비용이 훨씬 낮습니다.

설치 방법입니다. 세 가지가 필요합니다. 첫째, Playwright CLI를 설치. 둘째, 브라우저 엔진 설치 (npx playwright install chromium). 다른 브라우저 엔진을 사용하려면 문서를 참고하거나 Claude Code에게 명령어를 물어보세요. 셋째, playwright cli install skills 명령어로 스킬을 설치합니다. 직접 명령어를 입력할 수도 있지만, Claude Code를 열고 GitHub 저장소 링크를 주면서 필요한 것 다 설치해주라고 해도 됩니다. 스킬은 Microsoft가 만든 것으로 그대로 사용하거나, 직접 만들거나, 스킬 크리에이터로 검토할 수 있습니다.

Playwright CLI로 할 수 있는 것들은 꽤 폭넓습니다. 처음에 Claude Code와 대화하면서 Playwright 스킬로 뭘 할 수 있는지 물어보는 걸 추천합니다. 오늘 집중할 내용은 UI 테스트 워크플로우입니다. 하지만 아마존에서 쇼핑을 대신 시킬 수도 있습니다. 로그인하고 지속적인 세션을 설정하고, 자체 쿠키를 관리하는 것도 가능합니다.

UI 테스트 실행 측면에서, 기본적으로 헤드리스로 작동합니다. 테스트를 시키면 브라우저가 전혀 보이지 않습니다. 브라우저를 보고 싶다면, 구체적으로 "헤디드 브라우저로 해줘, 보고 싶어"라고 말해야 합니다. 이번 데모에서는 단일 헤디드 브라우저로 폼 제출을 테스트했습니다. 제가 한 말은 "Playwright CLI 도구로 폼 제출을 테스트해줘, 단일 에이전트로 하고 헤디드로 해서 볼 수 있게 해줘"가 전부입니다.

페이지가 어떻게 생겼는지 완전히 아는 자기 프로젝트에서 특히 효과적입니다. 접근성 트리 관련 문제가 발생할 가능성이 훨씬 낮습니다. 작업이 끝나면 자동으로 브라우저를 닫고, 폼 제출 테스트 결과를 보여주고, 스크린샷까지 제공합니다.

더 나아가서 "3개의 병렬 에이전트로 여러 각도에서 공격해줘"라고 하면 됩니다. 두 문장이면 모든 UI 테스트를 대신 해줍니다. 게다가 "이 폼을 스트레스 테스트하는 최선의 방법이 뭐야?"라고 물어볼 수도 있습니다. 사용의 단순함이 바로 핵심 가치입니다.

하지만 이 프로세스를 정말 강화하고 싶다면, 이 워크플로우를 스킬 자체로 패키징하는 방법을 배워야 합니다. 먼저 실제 워크플로우를 명확하게 정리합니다. "3개의 병렬 에이전트 X, Y, Z를 해라." Claude Code에게 정리해 달라고 해도 됩니다. 다음으로 스킬 크리에이터 도구를 사용합니다. 스킬 크리에이터를 열고 "이 다음 워크플로우 프로세스를 메타 스킬로 만들어줘"라고 하고 전체 워크플로우를 붙여 넣었습니다. 그래서 폼 테스터 스킬을 만들어 줬습니다. 이제 "폼 테스터 스킬 사용해줘"라고만 하면 데모에서처럼 3개의 병렬 에이전트가 생성됩니다.

Claude Code에서 워크플로우를 다룰 때 이런 사고 방식을 가져야 합니다. 표준화할 수 있을까? 표준화했다면 그 표준 플로우를 스킬로 만들 수 있을까? 그러면 정말 쉬워집니다.

Playwright 세계는 정말 깊습니다. 하지만 그 복잡함 아래에는 엄청나게 다양한 활용 사례가 있습니다. 다행히 Claude Code가 그 격차를 메워줍니다. 엄청나게 기술적이고 세부 사항에 빠질 필요 없이 많은 것을 얻을 수 있습니다. Claude Code가 많은 부분을 추상화해 주니까요.
