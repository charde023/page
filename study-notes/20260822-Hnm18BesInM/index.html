먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상은 AI 에이전트가 큰 작업에서 일부만 처리하고도 완료했다고 보고하는 문제를 다룬다. 화자는 대화가 길어질수록 이전 메시지가 쌓여 모델이 각 요구에 집중하기 어려워진다고 설명한다. Unlazy는 일을 작은 단위로 나누고, 각 단위마다 무엇이 참이어야 하는지, 어떤 명령으로 확인할지, 어떤 출력이 나와야 하는지를 파일에 적는다. 검사기가 명령을 실행해 실제 출력 증거를 남겨야 완료로 인정하고, 불가능한 항목은 이름과 이유를 보고하게 한다. 원본 방식은 하위 작업을 차례로 처리해 느렸고, 화자 측은 담당 파일을 나눈 뒤 여러 에이전트를 동시에 실행하도록 수정했다고 말한다. 핵심은 AI에게 성실하라고 부탁하는 대신 완료 판정을 다시 실행할 수 있는 증거에 묶는 것이다.

여기까지만 이해하면 충분

  • 긴 작업에서는 실제 완료와 AI의 완료 보고가 어긋날 수 있다.
  • Unlazy는 작업을 나누고 각 부분의 완료 조건과 검사 명령을 파일에 남긴다.
  • 체크 표시만으로는 부족하며, 검사 명령이 만든 증거가 있어야 완료로 본다.
  • 병렬 실행은 속도를 높일 수 있지만 파일 충돌과 검증 품질을 따로 관리해야 한다.

오늘 대답할 질문

AI 에이전트가 일부 작업을 빼먹고도 완료했다고 말하는 문제를 Unlazy는 어떻게 줄이며, 화자 측은 속도 문제를 어떻게 바꿨다고 주장하는가?

한 장면으로 이해하기

에이전트가 여러 파일 중 쉬운 파일만 고친 뒤 “모두 완료”라고 보고한다. Unlazy는 각 작업에 검사 명령과 기대 결과를 붙이고, 검사 결과가 증거란에 기록될 때만 완료로 인정한다.

"완료 보고와 실제 결과가 일치하는지 알 수 없다" 문제
→ "작업을 나누고 각 완료 조건을 명령으로 다시 검사한다" 작동 방식
→ "증거가 없거나 실패한 항목을 완료에서 제외한다" 결과

비유와 깨지는 지점

공사 검사표

작업 트리는 공사를 구역별로 나눈 계획이고, 게이트는 각 구역의 검사 항목이다. 시공자가 “끝났다”고 말하는 대신 검사 결과가 남아야 통과하는 구조와 닮았다.

비유가 깨지는 지점: 소프트웨어의 검사 명령과 기대 문구가 실제 품질을 완전히 대표하지는 않는다. 잘못 설계된 검사는 실행에 성공해도 사용자가 원한 결과를 놓칠 수 있다.

병렬 에이전트 실행 여러 작업을 동시에 처리함 서로 다른 하위 작업을 여러 에이전트에 동시 배정하는 화자 측 수정 동시 실행만 하면 충돌 없이 빨라진다고 보는 것

1. 원인

화자는 왜 긴 작업에서 AI의 누락과 잘못된 완료 보고가 늘어난다고 설명하는가?

모범 답안 보기

화자에 따르면 이전 메시지가 계속 컨텍스트에 쌓이면 모델이 한 번에 주의를 기울일 정보가 많아진다. 그 결과 일부 파일만 보거나 어려운 부분을 생략하고도 전체를 끝냈다고 요약할 수 있다.

2. 대조

에이전트가 체크박스를 선택한 것과 게이트가 통과한 것은 무엇이 다른가?

모범 답안 보기

체크박스는 에이전트의 자기 보고일 수 있다. 게이트 통과에는 지정된 명령을 실행해 기대한 출력이 나오고, 그 결과가 증거란에 기록되어야 한다. 체크됐어도 증거가 pending이면 미충족으로 본다.

3. 적용

새 자동화 작업에 게이트를 만든다면 무엇부터 완료 조건으로 삼아야 하는가?

모범 답안 보기

사용자가 반드시 받아야 하는 결과를 먼저 적고, 그 결과를 실제 산출물에서 확인할 수 있는 명령을 연결한다. 실행 성공처럼 좁은 신호만 보지 말고 누락, 실패, 예외도 드러나는지 확인한다.

이번 글의 통찰

1. 완료는 선언이 아니라 증거다

  • [원문] 화자는 검사기가 명령을 실행하고 기대 문구를 확인해 증거를 기록해야 게이트가 닫힌다고 설명한다.
  • [해석] 에이전트의 말투를 더 엄격하게 만드는 것보다 완료 판정권을 관찰 가능한 결과에 연결하는 편이 중요하다.
  • [경계] 검사 명령과 기대 출력 자체가 부실하면 증거가 있어도 실제 요구를 충족했다고 보장할 수 없다.

2. 작업 분해와 병렬화는 서로 다른 문제를 푼다

  • [원문] 작업 트리는 각 하위 작업의 목표와 컨텍스트를 줄인다. 화자 측은 원본의 순차 배정을 수정해 10개 에이전트를 동시에 실행했다고 말한다.
  • [해석] 분해는 집중 범위를 줄이고, 병렬화는 대기 시간을 줄인다. 병렬화할 때는 담당 파일을 나눠 덮어쓰기를 막아야 한다.
  • [경계] 전사는 모든 말단 작업이 각자의 하위 에이전트에 배정된다고 설명한 뒤, 깊이 3 이하는 같은 에이전트가 처리하는 솔로 모드라고도 말한다. 적용 범위가 명확히 구분되지 않는 서술이다.

3. 수치와 출처는 성능 증명과 분리해야 한다

  • [원문] 수정 전 실행은 3~4시간 뒤 로그인 페이지만 있었다고 하며, 수정 후에는 10개 에이전트가 거의 2시간 실행해 데모 앱을 만들었다고 보고한다.
  • [해석] 흥미로운 전후 사례이지만, 같은 작업을 동일 조건에서 비교한 통제 실험으로 읽어서는 안 된다.
  • [경계] META는 결과를 “2시간”으로 적고 전사는 “거의 2시간”이라고 말해 정밀도가 다르다. “GitHub 1위”의 시점과 부문도 제시되지 않았다. 원작자 이름은 전사와 META에 확정되어 있지 않으며, Leonxlnx는 제공된 GitHub URL의 계정 문자열을 근거로 한 추정 후보일 뿐이다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 완료 선언 대신 설명과 실행 결과로 이해를 확인한다는 구조가 평가 설계와 직접 닿는다.
  • 통찰: 학습 목표마다 “무엇을 설명하거나 수행하면 통과인지”를 먼저 정하면 자기평가의 허점을 줄일 수 있다.
  • 질문/행동: 정답 체크 대신 학습자가 원인·대조·적용을 직접 설명하게 할 수 있는가?

사업가 · 구조적 비유

  • 관련성: 업무 완료 보고와 실제 산출물의 불일치는 비용, 재작업, 후속 위험으로 이어질 수 있다.
  • 통찰: APOM에 적용한다면 주문·출고 같은 실제 절차에 쓰기 전에, 기계적으로 확인할 수 있는 조건이 있는지부터 검증해야 한다.
  • 질문/행동: 완료 보고 뒤에 반드시 남아야 하는 관찰 가능한 증거는 무엇인가?

마케터 · 직접 전이

  • 관련성: 영상은 3~4시간과 거의 2시간의 장면을 강한 전후 대조로 제시한다.
  • 통찰: 숫자는 설득력을 높이지만, 다른 설정과 산출물을 비교했다면 사례 보고와 성능 증명을 구분해야 한다.
  • 질문/행동: 카피의 주장 옆에 재현 조건과 실제 결과물을 함께 보여줄 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 작업 분해, 실행 가능한 검사, 증거 기록, 파일 소유권은 에이전트 자동화의 핵심 설계 문제다.
  • 통찰: 모델 이름보다 작업 단위, 검증 명령, 병렬 충돌 가능성을 먼저 설계해야 한다.
  • 질문/행동: 실행 전에 실패와 누락까지 드러내는 게이트를 작성할 수 있는가?

가치 지도

"AI의 완료 보고와 실제 산출물이 일치하는지 알기 어렵다" 문제
→ "누락과 후속 재작업 위험을 더 빨리 발견한다" 수혜자: 에이전트 운영자와 결과 사용자
→ "검사 명령을 설계하고 실행 시간·연산 자원을 제공한다" 지불자 또는 자원 제공자: 운영자
→ "증거가 비어 있거나 검사에 실패한 게이트 수" 가치 지표

작은 실험 하나

  • 행동 1개: 다음 자동화 작업 하나에 결과·검사 명령·기대 출력·증거로 구성된 게이트 3개를 실행 전에 작성한다.
  • 측정 1개: 작업 종료 시 증거가 비어 있거나 검사에 실패한 게이트 수를 센다.
  • 중단 기준 1개: 그 수가 1개 이상이면 적용 범위를 확대하지 않고 게이트와 작업 분해를 수정한다.

3 작업 트리 큰 작업을 깊이에 따라 분해하고 모드를 선택한다
4 게이트 원장 명령과 기대 출력, 실행 증거로 완료를 판정한다
5 설치 구조 프로젝트 범위 설치와 .agents, .claude 폴더를 설명한다
6 병렬 실행 수정 순차 배정을 병렬 배정으로 바꾼 화자 측 사례다

1. 완료 보고와 실제 완료의 차이

화자는 Opus와 GPT-5.6을 포함해 어떤 모델에서도 이른바 “게으름”이 나타날 수 있으며, 작은 모델에서 더 빨리 눈에 띈다고 주장한다. 여기서 게으름은 주로 두 형태다.

  1. 여러 파일을 확인하라고 했지만 일부만 열어 보고 전부 처리했다고 보고한다.
  2. 다섯 부분 중 쉬운 네 부분만 만들고 어려운 한 부분은 언급 없이 생략한다.

화자는 대화 기록이 컨텍스트에 계속 쌓이면 모델이 각 작업에 집중하기 어려워진다고 설명한다. “모델에 내장 기억이 없다”는 설명도 제시하지만, 이는 영상 속 작동 설명이며 독립적으로 검증된 기술 명세는 아니다.

2. 기존 완료 루프에 대한 비판

화자는 기존 접근을 다음과 같이 비교한다.

  • Ralph loop: 출력에 완료 표시가 나타날 때까지 같은 프롬프트를 반복한다. 하지만 완료 문구만으로 기능의 실제 품질을 판단할 수 없다고 말한다.
  • Claude의 goal 명령: 다른 모델이 대화를 읽고 완료 여부를 판단하지만, 실제 산출물보다 대화 내용에 의존해 목표에서 벗어날 수 있다고 주장한다.
  • 화자 측의 이전 루프: 실제 체크 항목은 있었지만 에이전트가 스스로 채점했기 때문에 자기 보고의 문제가 남았다고 설명한다.

3. 작업 트리와 실행 모드

Unlazy는 큰 작업을 바로 수행하지 않고 더 작은 작업으로 반복 분해한다. 프롬프트에 붙이는 숫자는 트리의 깊이다.

  • 숫자를 생략하면 요청에 맞는 가장 작은 깊이를 선택한다고 한다.
  • 각 작업은 사람이 실제로 수행할 때 최소 10분가량의 가치가 있어야 한다는 규칙을 제시한다.
  • 지나치게 잘게 나뉘면 깊이를 기본값 3으로 낮춘다고 설명한다.
  • 깊이 3 이하는 솔로 모드로, 한 세션에서 같은 에이전트가 처리한다.
  • 깊이 4 이상은 오케스트레이션 모드로, plan.md와 작업별 체크리스트를 기록한다.

다만 전사 앞부분의 “각 말단 작업을 각자의 하위 에이전트에 넘긴다”는 설명과 솔로 모드 설명은 적용 범위가 분명하게 정리되어 있지 않다.

4. 게이트와 증거 원장

각 게이트에는 완료 전에 참이어야 하는 결과가 적힌다. 그 아래에는 다음 정보가 놓인다.

  1. 결과를 증명할 명령
  2. 명령이 반환해야 할 정확한 문구
  3. 처음에는 pending으로 표시되는 증거

검사기는 각 명령을 직접 실행하고 기대 문구가 나오면 체크박스를 선택한 뒤, 판정에 사용한 출력 일부를 증거란에 기록한다. 체크박스가 선택됐더라도 증거가 pending이면 미충족으로 보며, 화자는 이를 빈 체크박스보다 더 나쁜 상태라고 표현한다.

오케스트레이션 모드에서는 하위 에이전트가 완료를 보고해도 메인 에이전트가 해당 검사를 다시 실행한 뒤 다음 작업을 배정한다. 작업이 불가능하다면 게이트 이름과 포기 이유를 보고서에 남기는 경로도 제공한다고 설명한다.

5. 설치와 폴더 구조

화자는 제공된 GitHub 페이지의 설치 명령을 프로젝트 터미널에서 실행하라고 안내한다. 설치 과정에서 사용하는 에이전트와 적용 범위를 선택한다.

  • Codex는 기본적으로 .agents 폴더를 읽는다고 설명한다.
  • Claude Code는 설치 메뉴에서 선택한다.
  • 화자 측은 특정 프로젝트에서 먼저 시험하기 위해 프로젝트 범위를 골랐다고 말한다.
  • 설치 후 .agents와 .claude 두 폴더가 보이지만, 별도 복사본은 아니라고 설명한다.
  • 실제 스킬은 .agents에 있고 .claude는 Claude Code가 이를 인식하게 하는 바로가기라고 한다.

6. 순차 실행의 병목과 병렬화

화자 측은 앱 제작 시험에서 원본 설정을 3~4시간 실행했지만 로그인 페이지만 만들어졌다고 보고한다. 원인으로 하위 작업을 하나씩 배정하고 완료될 때까지 기다리는 순차 실행을 지목한다.

수정한 방식은 plan.md에 작업별 담당 파일을 적어 동시 작업의 덮어쓰기를 피하고, 여러 에이전트에 작업을 동시에 배정한다. 데모 앱에는 트리 깊이 5를 사용했고, 10개 에이전트가 동시에 작업했다고 말한다. 이 실행은 거의 2시간 이어졌으며 원하는 기능을 갖춘 첫 버전이 완성됐다고 화자 측은 주장한다.

이 결과는 자체 보고다. 수정 전후의 정확한 작업 범위, 모델, 비용, 검사 결과가 제공되지 않아 일반적인 속도 향상 수치로 확정할 수 없다. 마지막에는 단순 작업을 저렴한 모델로, 어려운 작업을 강한 모델로 보내는 모델 라우터 스킬과 결합할 수 있다고 제안한다.

전체 전사 펼치기

AI 모델에는 근본적인 문제가 있습니다. 모델에게 어떤 작업을 맡겨도 절대 그 작업을 책임지고 끝까지 수행하지 않기 때문에, 에이전트의 결과물을 항상 검토해야 합니다. 믿을 수 없기 때문이죠.

하지만 이 게으름 문제가 이제 해결됐습니다. GitHub에서 현재 트렌딩 1위인 개발자가 해결책을 내놓았습니다. 그는 지금 가장 인기 있는 디자인 스킬(design skill) 중 하나인 Design Taste를 만든 사람이기도 합니다. 그리고 AI 에이전트의 이 문제를 정확히 해결하는 Unlazy라는 새로운 스킬을 만들었습니다.

Unlazy의 작동 방식은 정말 창의적이지만, 직접 실행해 본 결과 속도가 너무 느리다는 큰 문제를 발견했고, 그 문제를 해결할 방법도 찾아냈습니다.

처음 오셨다면 환영합니다. 저희는 소프트웨어 회사이고, 여기는 AI Labs입니다. 이번 영상에서는 Unlazy가 무엇인지, 실제로 어떻게 작동하는지, 어떤 문제가 있는지, 그리고 그 문제를 해결하기 위해 저희가 어떤 변경을 했는지 살펴보겠습니다.

게으름은 어떤 모델을 사용하든 기본적으로 나타나는 문제입니다. Opus나 GPT-5.6처럼 가장 강력한 모델에서도 마찬가지입니다. 다만 더 작은 모델에서는 기능이 훨씬 적고 한계가 훨씬 빨리 드러나기 때문에 이 문제가 더 쉽게 눈에 띕니다. Unlazy는 바로 이 문제를 해결하기 위해 만들어졌습니다.

이 스킬은 내장된 메커니즘을 통해 에이전트가 게으르게 행동하지 못하도록 강제하고, 여러분이 실제로 필요한 결과를 내놓게 합니다. 핵심은 에이전트가 작업을 끝냈다고 말하는 것이 아니라, 끝냈다는 것을 증명하게 한다는 데 있습니다. 작업을 장부(ledger)와 대조하는데, 이 장부는 모든 항목에 실제로 완료됐다는 증거가 있어야 하는 체크리스트와 같습니다. 단순히 작업이 완료됐다고 말하는 대신, 각 부분에 대한 증거를 보여줍니다.

Claude Code, Codex 등 인기 있는 모든 에이전트에서 작동합니다. 하지만 이 스킬이 왜 중요한지 이해하려면, 스킬이 없을 때 어떤 일이 일어나고 이 스킬을 추가하면 그 문제가 어떻게 해결되는지 알아야 합니다.

더 깊이 들어가기 전에 채널을 구독하고 좋아요 버튼을 눌러주시면 좋겠습니다. 이런 작은 응원이 저희에게 큰 도움이 됩니다.

실제로 스킬을 살펴보기 전에, 에이전트가 애초에 왜 게을러지는지 이해해야 합니다.

새로운 컨텍스트 창(context window)에서는 이 문제가 전혀 눈에 띄지 않을 수도 있습니다. 아직 그 안에 들어 있는 내용이 거의 없기 때문에 모델이 여러분이 맡긴 작업에 훨씬 더 집중할 수 있습니다. 하지만 컨텍스트가 채워질수록 문제가 더 뚜렷해집니다.

이 모델들에는 내장 메모리가 없기 때문에, 여러분이 이전 메시지에서 무엇을 보냈는지 실제로 알지 못합니다. 그렇다면 이전에 무슨 일이 있었는지 어떻게 알 수 있을까요? 에이전트가 이전 메시지를 모두 새로운 프롬프트와 함께 보내기 때문에 모델이 지금까지 어떤 일이 있었는지 알 수 있는 것입니다.

하지만 메시지를 점점 더 많이 보내면 그 내용이 계속 쌓이고, 모델이 한 번에 주의를 기울여야 하는 것이 훨씬 많아집니다. 바로 이것 때문에 에이전트가 작업의 각 부분에 명확하게 집중하지 못하고, 작업을 처리하는 동안 대충 하게 됩니다.

이런 게으름은 두 가지 방식으로 나타납니다. 첫 번째는 실제로 끝내지 않았는데도 끝냈다고 말하는 것입니다. Claude Code에 여러 파일을 검토하라고 요청했는데, 실제로는 전부 살펴보지 않고 몇 개만 연 다음 모든 파일을 확인했다고 보고하는 경우가 여러 번 있었습니다.

실제로 비용을 초래하는 부분이 바로 이것입니다. 작업이 분명히 끝나지 않았는데 모델이 일찍 멈추는 것은 받아들일 수 있습니다. 하지만 일찍 멈춘 뒤 모든 작업을 끝냈다고 말하면 문제가 됩니다. 직접 확인하기 전까지는 작업이 완료됐는지 실제로 알 수 없습니다. 확인하지 않은 채 완료되지 않은 작업 위에 더 많은 작업을 쌓으면 장기적으로 문제가 생깁니다.

두 번째는 여러분에게 알리지 않고 작업의 범위를 줄이는 것입니다. 예를 들어 다섯 부분으로 이루어진 작업을 요청했는데, 그중 한 부분이 어렵다고 해보겠습니다. 그러면 쉬운 네 부분만 만들고 어려운 부분은 건너뛰며, 마지막에 받는 요약에는 무엇인가 빠졌다는 말이 전혀 나오지 않습니다.

이게 새로운 문제가 아니라고 생각할 수도 있는데, 맞습니다. 이런 에이전트에는 늘 이런 문제가 있었고, 사람들은 오랫동안 이를 해결하기 위한 방법을 만들어 왔습니다.

아마 Ralph 루프(Ralph loop)에 대해서는 이미 알고 있을 겁니다. Ralph 루프는 출력에 있는 어떤 지표가 작업 완료를 나타낼 때까지 에이전트에 같은 프롬프트를 계속해서 다시 보냅니다.

Claude의 goal 명령(goal command)도 있습니다. 이 명령은 다른 모델을 심판으로 사용합니다. 저희도 이와 비슷한 루프를 직접 만든 적이 있는데, 작업 목록에 각 작업이 통과해야 하는 검사를 넣는 방식이었습니다.

하지만 이 모든 방법에는 한계가 있습니다.

Ralph에서는 완료 기준이 에이전트가 작업 중에 작성하는 약간의 텍스트일 뿐입니다. 하지만 많은 작업은 완료 기준만으로 판단할 수 없습니다. 어떤 기능이 실제로 제대로 구현됐는지를 알려주는 단 하나의 단어는 존재하지 않습니다.

goal 명령은 더 작은 모델을 사용해 대화를 읽고 작업이 완료됐는지 판단합니다. 따라서 작업 자체가 아니라 대화 내용에 근거해 판단하며, 실제로 여러분이 필요로 했던 것과 어긋날 수 있습니다.

저희가 만든 루프에서는 검사 항목이 실제로 존재했지만, 그 검사를 평가하는 것은 에이전트 자체였습니다. 결국 완료 여부를 결정하는 주체가 여전히 에이전트였던 것입니다.

컨텍스트 창이 새로 시작된 상태에서는 이 방법들이 모두 아주 잘 작동할 수 있습니다. 하지만 실제 작업을 깊이 진행하고 나면 제대로 작동하지 않기 시작합니다. 바로 그 시점에 이런 방법들이 버텨줘야 하는데 말이죠.

이제 이 시스템을 어떻게 설정하는지 보여드리기 전에, 내부에서 실제로 어떤 일이 일어나고 그것이 어떻게 문제를 해결하는지 살펴보겠습니다.

이 스킬에 큰 작업을 맡기면 곧바로 작업을 시작하지 않습니다. 먼저 그 작업을 더 작은 작업으로 나누고, 그 각각을 다시 더 작은 작업으로 나눕니다.

전체 작업은 가지를 뻗듯 확장됩니다. 하나의 작업이 몇 개로 나뉘고, 각각이 다시 몇 개로 나뉩니다. 그래서 이를 트리(tree)라고 부릅니다.

더 이상 나누지 않게 되면, 마지막에 남은 각각의 작은 작업은 각자의 서브에이전트(sub-agent)에게 전달됩니다. 이 분할이 몇 번 일어날지는 여러분이 제어합니다.

프롬프트를 작성할 때 이 스킬을 사용하고 싶다고 말하면서 숫자도 함께 지정합니다. 그 숫자가 트리의 깊이입니다. 5라고 하면 작업이 다섯 번 분해되고 그 이상은 분해되지 않습니다. 숫자를 전혀 지정하지 않으면 요청한 작업에 맞는 가장 작은 숫자를 자동으로 선택합니다.

이렇게 하는 이유는 앞에서 언급한 어텐션(attention) 문제와 직접 연결됩니다. 작업을 이렇게 나누면 각 작업에 명확한 목표가 하나씩 생기고, 그 작업을 수행하는 에이전트는 전체 작업을 함께 짊어지지 않아도 됩니다.

하지만 작업이 너무 작아도 안 됩니다. 이 스킬이 제시하는 규칙은 각각의 작업이 실제 작업 기준으로 최소 10분은 걸릴 만한 것이어야 한다는 것입니다. 에이전트가 스스로 맡아 끝낼 수 있는, 작업의 제대로 된 한 부분이어야 하기 때문입니다.

그 숫자를 너무 높게 설정해 작업이 10분보다 짧아지면, 스킬은 분할 작업의 깊이를 기본값인 3으로 낮춥니다.

이 숫자는 작업이 실행되는 방식도 결정합니다. 3 이하를 스킬에서는 솔로 모드(solo mode)라고 부르며, 이것이 기본값입니다. 모든 작업이 하나의 세션 안에서 진행되고, 같은 에이전트가 전부 처리합니다.

4 이상이면 오케스트레이션 모드(orchestrated mode)로 전환됩니다. 이 모드에서는 훨씬 더 많은 내용을 파일에 기록합니다. 전체 분해 내용을 담은 계획 파일을 작성하고, 그 안의 모든 작업마다 별도의 체크리스트를 작성합니다.

파일에 기록하는 이유는 이 스킬의 이전 버전이 실패했던 방식과 관련이 있습니다. 이전 버전은 에이전트에게 철저하게 하라고 말함으로써 게으름을 해결하려 했습니다. 하지만 긴 세션에서 가장 먼저 잊히는 것이 바로 지시사항이며, 이는 애초에 해결하려던 문제와 정확히 같은 문제였습니다.

그래서 이번 버전은 요청하는 대신, 작업을 시작하기 전에 파일에 내용을 기록합니다. 그 파일이 바로 gates 파일이며, 처음에 언급한 장부이기도 합니다. 이 파일의 각 항목을 gate라고 부릅니다.

각 gate는 옆에 결과가 적힌 체크박스입니다. 해당 작업이 완료된 것으로 인정되기 전에 참이어야 하는 한 가지 조건입니다. 그 결과 아래에는 세 줄이 있습니다.

첫 번째 줄은 해당 결과가 달성됐음을 증명하는 명령어입니다. 두 번째 줄은 그 명령어가 반환해야 하는 정확한 문구입니다. 세 번째 줄은 증거이며, 처음에는 단순히 “pending”이라고 적혀 있습니다.

이 스킬에는 검사기(checker)가 포함되어 있습니다. 이를 실행하면 파일을 따라 내려가며 모든 명령어를 직접 실행합니다. 반환된 답변에 gate가 기대하는 문구가 포함되어 있으면 체크박스를 선택하고, pending이라고 적힌 줄을 그 판단을 내리게 한 답변의 일부로 교체합니다.

이 증거 줄이 앞에서 나열한 모든 해결책의 허점을 막아줍니다. 체크박스가 선택되어 있지만 그 아래에 여전히 “pending”이 적혀 있다면, 에이전트가 스스로 체크한 것이므로 결국 에이전트가 다시 완료됐다고 말하는 것과 같습니다. 따라서 충족되지 않은 것으로 처리됩니다. 스킬은 빈 체크박스보다 이것을 더 나쁜 상태로 봅니다. 빈 체크박스는 적어도 작업이 실제로 어디까지 진행됐는지 정직하게 보여주기 때문입니다.

이 규칙이 더 큰 작업도 정직하게 유지합니다.

오케스트레이션 모드에서는 하나의 작업을 새로운 에이전트에게 전달합니다. 이 에이전트는 계획과 자신에게 할당된 gates 파일만 받고, 작업의 나머지 내용은 전혀 받지 않습니다.

하지만 그 에이전트가 완료됐다고 돌아와도 메인 에이전트는 그 말을 그대로 믿지 않습니다. 해당 작업의 검사를 다시 직접 실행하고, 그제야 계획 파일에 한 줄을 기록한 뒤 다음 작업을 전달합니다.

정직하게 빠져나갈 방법도 있습니다. 때로는 작업이 불가능한 것으로 드러나기 때문입니다. 에이전트가 작업을 포기하고 아무 말도 하지 않는 대신, 해당 gate의 이름과 포기하는 이유를 적은 줄을 작성합니다. 이 내용은 마지막에 받는 보고서에 포함됩니다.

따라서 Unlazy는 마지막에 한 번 검사하는 단일 검사가 아니라 하나의 전체 시스템입니다. 이 과정에서 에이전트가 작업 완료 여부를 결정할 수 있는 순간은 한 번도 없습니다.

실제로 이 스킬을 사용하려면 먼저 설치해야 합니다. 공식 GitHub 페이지로 가서 설치 섹션을 찾은 다음, 거기에 있는 명령어를 복사하세요. 링크는 아래 설명에서 확인할 수 있습니다.

그다음 작업 중인 프로젝트 안에서 터미널을 열고 명령어를 실행합니다. 실행하면 설치 프로그램이 시작되고, 가장 먼저 어떤 에이전트를 사용하는지 묻습니다.

Codex를 사용 중이라면 아무것도 변경할 필요가 없습니다. Codex가 이미 읽는 .agents 폴더에 설치되기 때문입니다. Claude Code를 사용 중이라면 열리는 메뉴에서 이를 선택하세요. 나머지 항목은 원하는 만큼 동시에 선택할 수 있습니다.

그런 다음 범위(scope)를 선택하라는 메시지가 표시됩니다. 이는 기본적으로 이 스킬이 현재 작업 중인 프로젝트 안에서만 작동하도록 할지, 아니면 앞으로 만드는 모든 것에서 사용할 수 있도록 할지를 정하는 것입니다.

우리는 먼저 특정 프로젝트 하나에서 테스트하고 싶었기 때문에 프로젝트 범위를 선택했습니다. 그 후 권장 옵션을 선택하면 설치가 완료됩니다.

VS Code에서 해당 프로젝트를 열면 .agents와 .claude라는 새 폴더 두 개가 보입니다. 이 둘은 서로 별개의 복사본이 아닙니다. 스킬 자체는 실제로 .agents 폴더에 있고, .claude 폴더는 Claude Code도 이를 인식하고 사용할 수 있도록 만든 바로 가기일 뿐입니다. 따라서 같은 프로젝트 안에 중복 파일이 생기지 않습니다.

그 폴더 안의 스킬 파일에는 에이전트가 이를 사용하는 방법에 대한 모든 지침이 들어 있습니다. 여기까지 완료되면 스킬이 설치되고 바로 사용할 수 있습니다.

하지만 사용하기 전에 알아야 할 것이 하나 있습니다. 이 스킬을 있는 그대로 실행하면 의미 있는 결과물이 만들어지기까지 정말 오랜 시간이 걸립니다.

앱에서 테스트하다가 이 사실을 알게 됐습니다. 해당 세션은 약 3~4시간 동안 계속 실행됐는데, 진행 상황을 확인해 보니 로그인 페이지 하나만 있고 다른 것은 아무것도 없었습니다.

스킬을 살펴본 결과 문제는 지침에 있었습니다. Claude Code와 Codex 모두 여러 에이전트를 동시에 실행할 수 있고, 각 하위 에이전트(sub-agent)는 서로 다른 작업을 병렬로 수행할 수 있습니다.

하지만 이 스킬은 작업 하나를 할당하고 완료될 때까지 기다린 다음에야 다음 작업을 할당합니다. 따라서 에이전트를 실행하고는 있었지만 에이전트의 역량을 최대한 활용하지 못했고, 그 때문에 그 많은 시간이 소요된 것입니다.

그래서 프로젝트를 다시 열고 스킬 자체를 수정했습니다. 직접 변경하고 싶다면 여기서 잠시 멈추고 우리가 사용한 프롬프트를 복사해도 됩니다.

이 수정은 이러한 도구들이 여러 에이전트를 동시에 실행할 수 있다는 점을 스킬이 실제로 활용하도록 합니다. 실행하려면 스킬 이름을 입력한 다음 트리의 깊이를 입력하고, 만들고 싶은 것을 모두 적으면 됩니다.

우리는 이 데모 앱을 처음부터 만들고 있었기 때문에 5를 선택했습니다. 하지만 자신의 작업 규모에 따라 그 숫자를 정하면 됩니다. 앱 전체가 아니라 한 번에 기능 하나를 작업하려는 경우라면 2나 3이면 충분합니다.

잘못된 옵션을 선택할까 봐 걱정할 필요도 없습니다. 필요한 것보다 높은 숫자를 선택하면 스킬이 자동으로 깊이를 낮춰 줍니다.

무언가를 만들기 전에 가장 먼저 하는 일은 plan.md 파일을 작성한 다음 gates.md 파일을 작성하는 것입니다. plan.md에는 어떤 작업이 어떤 파일과 함께 작업해야 하는지도 나와 있어서, 두 에이전트가 동시에 작업하더라도 서로의 작업을 덮어쓰지 않습니다.

그런 다음 기반을 마련하고 작업을 에이전트들에게 할당하기 시작하는데, 모든 에이전트가 동시에 실행됩니다. 이렇게 수정한 뒤에는 10개의 에이전트가 동시에 작업했고, 각자 서로 다른 부분을 담당했습니다.

그 실행은 거의 2시간 동안 계속됐습니다. 마지막에는 모든 기능이 우리가 원했던 대로 정확히 작동하는 데모 앱의 첫 번째 버전을 실행할 수 있었습니다.

이 정도 규모로 개발한다면 모델 라우터 스킬(model router skill)과 함께 사용할 수도 있습니다. 이는 기본적으로 각 작업을 그 작업에 적합한 모델로 보내는 스킬입니다. 단순한 기계적 작업은 더 저렴한 모델이 맡고, 어려운 부분은 더 강력한 모델이 맡도록 해서 한도에 너무 빨리 도달하지 않게 합니다.

여기서 사용한 스킬은 여러 차례의 테스트와 개선을 거쳐 만들어졌습니다.
