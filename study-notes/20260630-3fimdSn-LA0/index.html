프로토타이핑 문화 비개발자도 자연어로 실제 앱 프로토타입을 만들어 내부 앱스토어에 공유 아이디어 검증 주기가 몇 주에서 하루 단위로 단축

내가 모를 만한 것 / 처음 보는 것

  • monorepo / polyrepo — monorepo는 여러 프로젝트 코드를 저장소 하나에 몰아넣는 방식, polyrepo는 프로젝트마다 저장소를 따로 두는 방식. Spotify는 소수의 거대 monorepo(2천만 줄 이상)로 옮겨가는 중이지만 수천 개의 작은 polyrepo도 여전히 남아 있다.
  • tmux(티맥스) 세션 — 터미널 하나에서 여러 화면(창)을 나눠 쓰게 해주는 터미널 멀티플렉서. Niklas는 tmux 세션과 워크트리(worktree)를 매칭시켜 5~10개 터미널 탭에서 동시에 여러 Claude Code 세션을 돌린다.
  • 워크트리(work tree) — 같은 git 저장소를 여러 개의 독립된 작업 폴더로 동시에 열어두는 기능. 브랜치를 바꿔가며 옮겨다니지 않고 폴더별로 다른 브랜치를 동시에 작업할 수 있다.
  • AST 변환(Abstract Syntax Tree transformation) — 코드를 문자열이 아니라 문법 구조(트리)로 분석해 기계적으로 바꾸는 전통적 정적 분석 기법. Spotify가 LLM 이전에 쓰던 방식인데, 변수에 별칭을 붙이는 식의 변칙 코드가 나오면 추적이 폭발적으로 복잡해지는 한계가 있었다.
  • LLM 심판(LLM as judge) — 한 AI의 출력이 맞는지 다른 AI(또는 같은 모델의 별도 호출)로 검증시키는 기법. Honk 초기 버전엔 필수였으나 모델 자체 성능이 오르면서 제거됐다.
  • Kubernetes 파드(pod) — 컨테이너를 격리 실행하는 단위. Honk의 에이전트 SDK는 이 파드 안에서 도구 접근 권한을 부여받은 채 실행된다.
  • allow-listed tools (허용목록 도구) — 에이전트가 쓸 수 있는 도구를 사전에 정해둔 목록으로만 제한하는 방식. Honk v1까지는 이렇게 제한했고, v2부터는 사용자가 임의 내부 도구를 자유롭게 붙일 수 있게 열었다.
  • work items (워크 아이템) — Spotify 내부에서 "계획된 작업"을 추적하는 단위. PR·배포를 이 work item에 연결해 A/B 테스트·롤아웃까지 추적성을 확보하려는 시도 중이다.
  • DoD (Definition of Done) — "완료의 정의". 특정 work item이 어떤 조건을 만족해야 끝난 것으로 볼지 정한 기준. 여기서는 PR이 어떤 DoD·유저 가치에 기여했는지 역추적하는 맥락으로 언급됨.

1. 도입 — IDE 없는 세상이 두 달 만에 왔다

Boris가 작년 9월 "연말이면 아무도 IDE를 안 쓸 것"이라 말했을 때 Niklas는 내심 "그건 말도 안 된다, 2년은 걸릴 일"이라 생각했다. 그런데 실제로는 두 달 뒤 본인이 IDE를 쓰지 않고 있었고, 일하는 방식 자체가 30년 경력에서 본 적 없는 수준으로 바뀌었다. 재미있게도 Anthropic 내부에서 체감한 변화 속도와 Spotify 외부에서 체감한 속도가 거의 동일했다 — Anthropic이 몇 주 정도 먼저 겪었을 뿐.

Niklas의 원래 전공은 분자생물학(molecular biology)이다. 박사과정 중 유전체 서열분석에서 나온 빅데이터를 다루려 프로그래밍 능력을 키워야 했고, "1년 안식년(sabbatical year)"으로 전향한 게 지금 거의 30년 커리어가 됐다.

2. 첫 AI 감동의 순간 — 임팩트는 여러 번 있었다

Spotify는 LLM 초창기부터 코드 변경 자동화를 시도했다. 처음엔 고전을 면치 못했지만("real struggle"), LLM에 심판(judge)을 붙이는 방식을 발견하면서 점점 고무적인 결과가 나왔다. 이 시기는 사전 Claude(pre-Claude), 초기 GPT 시절이었고, 당시 결과는 "모든 문제를 해결한다"는 수준은 아니었지만 앞으로의 방향성을 보여주는 신호였다.

개인적으로 가장 큰 전환점은 작년 11~12월 Opus 4(원문 "Opus 4 or 5") 무렵이었다. 이전에는 모델이 "똑똑한 자동완성" 수준이었다면, 이 시점부터는 실제 문제를 던져도 별다른 프롬프트 엔지니어링 없이 처리되기 시작했다. 가장 크게 체감한 변화는 "코드를 더 이상 직접 편집하지 않아도 된다"는 것이었다. 이전 워크플로는 모델이 코드의 70~80%를 작성하면 나머지 "라스트 마일(last mile)" 편집을 IDE에서 직접 해야 했는데, 이 작업 자체가 사라졌다.

3. 오늘의 개인 워크플로 — tmux 세션 5~10개

Niklas는 스스로 "꽤 평범한(fairly vanilla)" 방식으로 Claude Code를 쓴다고 말한다. 터미널에서 tmux 세션을 여러 개 띄워 5~10개 탭을 왔다갔다하며, 여러 워크트리(work tree)에 세션을 매칭시켜 diff를 바로 확인할 수 있는 tmux 창(panes)까지 갖춘 구성이다.

Spotify는 소수의 거대 monorepo로 점점 이전 중이지만 아직 수천 개의 작은 polyrepo도 남아 있다. 대부분의 작업은 monorepo에서 이뤄지고, polyrepo에 들어갈 때만 임시로 세션을 하나 더 연다.

Boris는 monorepo와 agent 조합이 걱정스러웠다고 밝힌다 — 기존 도구에서 인덱싱 문제를 자주 봤기 때문. Spotify의 주력 monorepo는 2천만 줄이 넘는데, 실제로는 Claude가 그 안에서 놀라울 만큼 잘 작동했다. 특히 Claude가 저장소 내 다른 코드를 참고해 문제 해결의 "영감(inspiration)"을 얻는 능력이 좋았다는 점이 발견이었다.

4. Fleet Management와 Honk 탄생 배경

5~6년 전 Spotify는 코드베이스가 엔지니어 증가 속도보다 7배 빠르게 늘어나고 있다는 것을 확인했다. Spotify는 아이디어가 끝없이 나오는 회사라 유지보수에 발목 잡히는 상황이 좋지 않았고, 그래서 유지보수 자동화를 시작했다. 자바 버전 업그레이드나 라이브러리 업데이트, API 마이그레이션 같은 반복 작업이 대부분이었다.

과거에는 마이그레이션이 있으면 튜토리얼을 전 팀에 보내 각자 수동으로 처리하게 했다 — 수백 개 팀이 사실상 똑같은 작업을 각자 반복하는 구조였다. 이를 대신해 "전체 코드베이스에 걸쳐 변형(mutation)을 가할 수 있는 방법"을 고민한 것이 fleet management의 시작이다. 자동화 이전엔 마이그레이션 하나에 몇 달씩 걸려 연간 10건 정도만 소화할 수 있었고, 지원 프레임워크 버전을 겨우 따라가는 수준이었다.

전통적 정적 분석(AST transformation, Abstract Syntax Tree 기반 변환)으로 이를 처리하려 했으나 한계가 뚜렷했다 — 코드의 API 표면이 워낙 넓어서, 예를 들어 API를 변수에 별칭(alias)으로 저장하는 패턴 하나만 나와도 변수·상태 추적(variable and state tracking)이 필요해지고 스크립트가 수천 줄짜리 예외 처리 덩어리가 됐다.

이 한계 때문에 초기 LLM이 등장하자마자 "이걸 적용해볼 수 있을까"라는 시도가 시작됐다. 처음엔 잘 안 됐다 — 모델 성능도 부족했고, 접근 방식(코드를 통째로 모델 앞에 던지고 원샷으로 바꾸게 하는 방식)도 너무 순진했다. 모델이 개선되고 접근법도 발전하면서 LLM 심판(judge)을 도입해 출력을 검증하고, 문제를 잘게 분해(decompose)하는 방식으로 바뀌었다. 수많은 반복과 내부 실험을 거쳐 이것이 통합된 것이 지금의 Honk다.

5. Honk 아키텍처 — 심판을 없앨 만큼 모델이 좋아졌다

Honk는 원래 Claude 위에서 만든 게 아니라 홈그로운(homegrown) 방식의 집합체였다. 이후 계속된 반복 끝에 이번에 공개한 버전을 "V2"라 부르지만, 실은 반복 횟수를 정확히 추적하지 못했을 정도로 V8쯤 될 거라고 Niklas는 농담조로 말한다. 처음엔 "코드 변경을 자동화하고, 스케줄링하고, 전 저장소에 걸쳐 오케스트레이션하는" 도구였는데, 엔지니어들이 곧 다른 용도(Slack에서 멘션해서 작업 시키기 등)로도 쓰기 시작하면서 지금은 훨씬 더 범용적인 도구로 성장했다.

아키텍처: Honk는 Claude Agent SDK가 Kubernetes 파드(pod) 안에서 돌아가는 구조이고, 정해진 도구 집합에 접근한다. v2 이전에는 신뢰할 수 있다고 검증된 허용목록(allow-listed) 도구만 쓸 수 있었지만, v2부터는 사용자가 자체 도구를 자유롭게 추가할 수 있어 내부의 어떤 도구든 에이전트가 쓸 수 있게 됐다. 가장 중요한 도구 중 하나는 CI 빌드를 실제로 돌릴 수 있는 검증(verification) 기능이며, Linux와 macOS 양쪽에서 실행 가능하다(iOS 개발은 macOS 빌드가 필수라 특히 중요). 실제로 iOS 시뮬레이터와 Claude를 연동해 Figma 디자인을 UI 구현으로 바로 옮기거나, TV 앱을 iOS 앱에서 포팅하는 데도 활용 중이다.

심판(judge)의 흥망: 초기 Honk에는 LLM 심판이 있었지만 지금은 제거됐다. 심판이 있을 때 성공률이 20~30%에서 80%로 뛰었을 만큼 초기엔 결정적이었지만, 이후 모델과 에이전트 하네스(agent harness) 자체가 좋아지면서 더 이상 필요 없어져 v2에서 제거했다.

6. 검증(verification)이 가장 중요한 이유

Boris는 "사람 개입 없이 폐쇄 루프(closed-loop)로 작업을 완료시키는 구조에서 검증이 단연 가장 중요한 요소"라 짚으며, 많은 회사가 이 검증 루프 투자를 과소평가한다고 지적한다. Niklas도 이에 동의하며, Spotify가 한 가장 큰 엔지니어링 관행 변화는 테스트 자동화 강화였다고 말한다.

Spotify는 코드베이스를 수천 개의 컴포넌트로 나누고 각각 명확한 소유팀(ownership)을 지정해왔다. 원래는 각 팀이 자신의 코드베이스에 머지되는 모든 변경을 직접 확인하는 구조였기 때문에 테스트 자동화가 다소 허술해도(sloppy) 괜찮았다 — 사람이 PR을 매번 확인하니까. 그런데 PR을 자동화하기 시작하면서 팀의 기대치 자체를 바꿔야 했다: "이제 당신 팀은 이 변경들을 직접 확인하지 않을 수도 있다. PR을 보지도 못한 채 대부분 자동 병합(auto-merge)될 것이다." 이 전환을 지탱하려면 소프트웨어가 자동 변경을 견뎌낼 수 있을 만큼 훨씬 더 나은 테스트 자동화가 필요했다.

지금은 이 검증 인프라 덕분에 에이전트를 그 위에 얹어 같은 검증 체계를 재사용할 수 있게 됐다.

7. 속도와 품질은 거짓 이분법이다

엔지니어링에서 늘 회자되는 "신뢰성·품질 대 속도"의 트레이드오프를, Boris는 "거짓 이분법(false dichotomy)"이라 표현한다. 더 빠르게 가려면 품질 관행을 자동화해서 코드에 더 잘 인코딩해야 한다는 것 — 그 지식이 누군가의 머릿속에만 있는 게 아니라 스킬(skill)이나 CLAUDE.md, 혹은 MCP 세트로 구현돼 Claude가 직접 수행할 수 있어야 궁극적으로 속도가 나온다는 논리다. 이는 "엔지니어링 생산성은 결국 인프라 투자의 문제이지, 더 오래 일하는 문제가 아니다"라는 원칙의 또 다른 사례다.

Niklas는 Spotify가 품질 지표를 유지한 채(neutral) 속도만 크게 개선하고 있다고 확인한다. 다만 이건 공짜가 아니다 — 테스트 자동화 투자가 선행돼야 했고, 앞으로도 신뢰성 관행에 계속 투자해야 한다. 빠르게 갈수록 신뢰성에 더 투자해야 한다는 역설이다. 실제로 Spotify는 하루 약 4,500건의 프로덕션 배포(4,500 production deployments every day)를 하는데, 그만큼 잘못될 기회도 많아서 품질 관행이 필수다.

배포를 이렇게 자주 하는 이유는 "아이디어를 최대한 빨리 프로덕션에 태워 피드백을 받기 위함"이다. 예전엔 몇 주~몇 달 걸리던 것이 지금은 약 1시간까지 단축됐다(모든 아이디어가 이렇게 빠른 건 아니고, 많은 아이디어는 여전히 충분한 탐색이 필요하다). 내부 사용자든 외부 사용자든 피드백을 빨리 받을수록 더 나은 제품을 더 빠르게 만들 수 있었다는 것이 Spotify의 경험이다.

8. ROI 측정 — 명확한 지표에서 매출 연결로

Spotify 엔지니어 조직은 약 2,900명 규모다. ROI 측정 관점에서 신호는 매우 명확했다: PR 빈도가 75% 이상 개선됐고, 이는 AI 도구 덕분이라고 직접 귀속할 수 있으며, 현재 PR의 73%가 AI가 작성한 것으로 집계된다.

다음 단계는 이걸 사용자 가치와 매출로 연결하는 것이다. Spotify는 PR·배포 같은 산출물을 "work item"(계획된 작업 단위)에 연결하고, 이를 다시 A/B 테스트와 롤아웃에 연결해 "이 PR이 이 DoD(Definition of Done)에 기여했고, 그것이 이런 사용자 가치로 이어졌다"는 식으로 역추적하는 연결고리를 만드는 중이다.

Boris는 예전 개발자 생산성(developer productivity) 업계에서는 몇 퍼센트 포인트(단 1%p)만 개선돼도 큰 성과였는데, 지금은 개선 폭이 워낙 크고(수십~수백 %) 눈에 명확히 보이는데도 여전히 엔지니어들이 이를 정밀하게 측정하려 한다는 점을 짚는다. Niklas는 ROI 논의 초반엔 개선 폭이 워낙 커서 쉬웠지만, 성숙도가 올라가고 비용이 개선될수록 ROI 추정치에 요구되는 정밀도(precision) 기대치도 함께 올라가고 있다고 말한다 — 결국 "생산성 개선분"과 "그 개선에 든 비용(토큰 수·소요 시간)"을 함께 봐야 한다는 것.

9. 리더에게 주는 조언 — 표준화를 포기하지 마라

마지막 질문 — 다른 CTO·VP of Engineering에게 줄 조언은? Niklas는 테스트 자동화·검증 같은 "기초 역량(foundational capabilities)" 투자와 더불어 표준화(standardization)를 강조한다. Spotify는 코드베이스 일관성, 사용 도구·프레임워크의 정렬(alignment)을 계속 밀어붙여 왔다.

원래 이 투자는 사람을 더 생산적으로 만들기 위한 것이었지만, 그대로 에이전트에도 잘 통했다. 예컨대 Claude가 monorepo 안에서 다른 코드를 참고해 영감을 얻는다고 앞서 언급했는데, 코드가 10가지 다른 방식으로 짜여 있으면 Claude도 더 혼란스러워한다. 일관성이 높을수록 에이전트가 더 잘 작동한다는 것을 Spotify는 확인했다. 조언 하나만 꼽으라면 "이런 투자를 무시하지 말라"는 것 — 기존 엔지니어링 관행의 기본 원칙은 이 새로운 세계에서도 여전히 유효하고(코드베이스에 새로운 행위자가 하나 늘었을 뿐), 이 기본기는 예전만큼 잘 적용된다.

10. 엔지니어 개인에게 주는 조언 — 문제 해결이 본질이다

Niklas는 원래 코딩의 "문제 해결" 부분을 진심으로 즐겨온 사람이고, 여가 시간에 경쟁 프로그래밍(competitive programming)을 취미로 할 정도다. 그래서 내심 걱정이 있었다 — "이 힘든 지적 도전을 놓치게 되는 게 아닐까?" 그런데 지금은 백그라운드에서 다섯 개의 에이전트가 동시에 일하는 방식으로 일하고 있고, 결과적으로 그 걱정은 틀렸음이 드러났다. 좋아하는 건 "문제를 푸는 것"이었지, "그 문제를 푸는 방법 자체"가 자신에게 가장 중요한 부분은 아니었다는 걸 깨달았다는 것.

이 전환은 사람마다 다르게 겪을 수밖에 없지만, "당신이 풀 수 있는 문제의 종류"에 집중하라는 것이 조언이다. Niklas 본인은 더 생산적이 됐을 뿐 아니라, 예전엔 전혀 풀 수 없었던 문제도 풀 수 있게 됐다 — 예전엔 며칠~몇 주 걸려야 이해할 수 있었던 코드베이스에도 곧바로 뛰어들어 기여할 수 있다.

Boris는 자신의 경험도 비슷하다며 "구현 시간"이 크게 줄고, 그 대신 다음에 뭘 할지 고민하기, 고객과 대화하기, 그리고 예상보다 훨씬 많은 프로토타이핑(prototyping)으로 시간이 채워졌다고 덧붙인다.

11. 프로토타이핑 문화 — 비개발자까지 확산

Niklas는 Spotify도 비슷한 변화를 겪고 있다며, 특히 프로토타이핑에 큰 투자를 하고 있다고 말한다. 대상은 엔지니어뿐 아니라 비엔지니어 코호트(non-engineering cohort)까지 포함한다. Claude 같은 도구가 열어준 것은 "누구든 자기 아이디어를 자연어로 표현하면 Claude가 구현해준다"는 가능성이었다.

사람들이 이걸 깨닫기 시작하면서(비개발자 포함) 실제 앱 — 상당히 복잡한 코드베이스 — 에서 시도해보기 시작했고, 조금씩 성과가 보였다. 몇 달 전 Spotify는 이를 위한 인프라를 구축해, 지금은 모바일 앱과 백엔드에서 엔드투엔드 프로토타입을 손쉽게 만들 수 있는 환경과, 그 프로토타입을 공유·체험할 수 있는 내부 앱스토어(internal app store)를 갖췄다. 예전엔 아이디어를 실현하려면 엔지니어 여럿을 설득해서 만들어야 했지만, 지금은 한두 시간 안에 실제 사용자 데이터로 동작하는 프로토타입을 만들어 공유할 수 있다. 1년 전만 해도 상상할 수 없던 일이 지금은 매일 일어나고 있다.

누가 이 프로토타입을 만드는지 묻는 질문에, Niklas는 공동 CEO(co-CEO)를 포함해 사내 모든 층위가 앱스토어에 프로토타입을 올려두고 있다고 답한다. 여러 시니어 임원들도 품질 좋은 프로토타입을 만들었다 — 원래 오래 품고 있던 아이디어인데, 그걸 만들 엔지니어링 팀이 있어도 다들 다른 일에 집중하느라 못 만들었던 것들이다. 이제는 몇 주~몇 달이 아니라 하루 만에 아이디어를 테스트해볼 수 있다.

Boris: 이렇게 많은 배포를 하는 이유가 뭔가요? 과거엔 그냥 지속적 배포(continuous deployment)였는데 이제는 에이전트를 위한 더 빠른 시그널인 건가요? 어떻게 생각하세요?
