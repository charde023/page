언제 나만의 에이전트 하네스를 만들 것인가

원작자 Harrison Chase · LangChain · 업로드 2026-08-13 · 23.9분 · 원본 영상 ↗
한 줄 요약

에이전트 성능은 모델만이 아니라 모델에 적절한 맥락을 제때 넣어주는 하네스(harness)에 달려 있고, 표준 업무는 기성 하네스로 시작하되 도메인 특화 업무는 평가(evals)와 관측성(observability)을 기반으로 점진적으로 직접 조정해야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
에이전트의 3요소 에이전트 성능을 모델 하나로만 보면 개선 포인트를 놓친다 에이전트는 하네스(harness), 모델(model), 맥락(context)의 조합이다
하네스(harness) 모델이 언제 어떤 정보를 보고 어떤 도구를 쓸지 결정한다 하네스의 핵심 역할은 적절한 맥락을 적절한 시점에 모델로 가져오는 것이다
미들웨어(middleware)와 훅(hook) 기본 에이전트 루프를 망치지 않고 도메인별 기능을 끼워 넣을 수 있다 모델 호출 전, 도구 호출 전후 등에 요약·메모리·샌드박스·검증 로직을 삽입한다
기성 하네스 vs 자체 하네스 언제 직접 만들어야 하는지 판단 기준이 필요하다 업무가 모델 학습 분포 안(in-distribution)에 가까우면 기성품, 벗어날수록 커스터마이징
인-디스트리뷰션(in-distribution) 모델이 이미 잘 학습한 방식은 굳이 바꾸면 성능이 떨어질 수 있다 법률 AI처럼 큰 업무는 특수해도 파일 편집 같은 작은 기능은 모델별 표준 방식을 따르는 게 좋다
평가(evals) 조직 안에서 “좋은 결과”의 기준을 정의한다 벤치마크가 있어야 모델·하네스·프롬프트 변경의 성패를 비교할 수 있다
관측성(observability) 에이전트 실패 원인을 추적하려면 내부 흐름을 봐야 한다 많은 실패는 모델 자체보다 모델에 들어간 맥락이 나쁜 것에서 온다
데이터 플라이휠(data flywheel) 운영 데이터가 계속 성능 개선 재료가 된다 실행 흔적(trace) 수집 → 선별 → 실험 → 하네스·모델·맥락 개선

내가 모를 만한 것 / 처음 보는 것

  • 하네스(harness) — 모델, 도구, 메모리, 파일 시스템, 외부 API, 샌드박스를 묶어 에이전트가 반복 실행되게 하는 실행 골격.
  • 맥락 창(context window) — 모델이 한 번에 참고할 수 있는 입력 정보 공간. 너무 길면 요약(summarization)이나 맥락 오프로딩(context offloading)이 필요하다.
  • 미들웨어(middleware) — 에이전트 루프 중간에 끼워 넣는 작은 처리 단위. 예: 모델 호출 전 요약, 도구 호출 후 결과 정리.
  • 인-디스트리뷰션(in-distribution) — 모델이 학습·강화학습 과정에서 많이 본 유형의 작업.
  • 아웃-오브-디스트리뷰션(out-of-distribution) — 모델이 충분히 학습하지 않은 특수 업무나 도메인.
  • 인지 아키텍처(cognitive architecture) — 에이전트가 따라야 할 단계, 분기, 검증 절차를 사람이 명시적으로 설계한 구조.
  • Harbor — 에이전트를 벤치마크하기 위한 오픈소스 평가 실행기(eval runner). 작업별 샌드박스, 테스트, 지시문을 묶어 실행한다.
  • Terminal Bench — 코딩 에이전트 성능을 재는 대표 벤치마크 중 하나.
  • LangSmith — LangChain의 평가(evals)와 관측성(observability) 플랫폼.
  • LangSmith Engine — 실행 흔적(trace)을 분석해 이슈를 찾고 하네스·프롬프트·맥락 개선안을 제안하는 LangSmith의 에이전트.
  • LLM-as-a-judge — 다른 LLM을 심판처럼 사용해 결과 품질을 평가하는 방식.
  • SLM(small language model) — 비용을 줄이기 위해 평가용 등으로 쓰는 작은 언어 모델.
  • 도그푸딩(dogfooding) — 자신들이 만든 제품을 내부에서 직접 사용하며 검증하는 방식.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 발표 구성은 대략 15분 발표 + 15분 질의응답 형식이었다 — 실제 영상은 약 24분.
  2. Harrison Chase는 2022년 GPT-3 시절부터 모델을 단순 자동완성(autocomplete)이 아니라 가상 협업자·에이전트로 쓰기 위한 하네스 개념을 고민한 인물로 소개됐다.
  3. LangChain 관점에서 에이전트는 하네스가 모델과 맥락을 오케스트레이션(orchestration)하는 구조다.
  4. 가장 단순한 에이전트 구조는 LLM이 루프(loop)를 돌며 도구(tool)를 호출하는 것이다.
  5. Deep Agents는 LangChain의 모델 불가지론적(model-agnostic)이고 범용적인 Claude Code 유사 하네스로 설명됐다.
  6. 하네스 커스터마이징 지점은 모델 호출 전, 각 모델 호출 전, 모델 호출 감싸기, 도구 호출 감싸기 등이다.
  7. 요약(summarization)은 모델 호출 직전 맥락이 너무 길어졌는지 확인하고 줄이는 미들웨어로 들어간다.
  8. 맥락 오프로딩(context offloading)은 큰 도구 호출 결과를 그대로 맥락에 넣지 않고 덜어내는 방식이며, 도구 호출을 감싸는 형태로 구현된다.
  9. 2023~2024년에는 모델이 지금보다 약했기 때문에 명시적인 인지 아키텍처(cognitive architecture)를 더 많이 썼다.
  10. 법률 AI 예시에서 전체 업무는 아웃-오브-디스트리뷰션일 수 있지만, 파일 편집(file editing)은 모델들이 이미 강화학습(RL)으로 많이 훈련한 인-디스트리뷰션 작업이다.
  11. OpenAI 모델과 Claude 모델은 파일 편집을 잘하는 방식이 서로 다르므로, Deep Agents는 모델 프로필(model profiles)을 두고 모델별 파일 편집 구현을 바꾼다.
  12. 평가에서는 정확도(accuracy)뿐 아니라 지연시간(latency), 토큰(tokens), 비용(cost)을 함께 봐야 한다.
  13. Harbor 작업(task)은 보통 Dockerfile로 정의한 샌드박스 환경, 정답 예시(solution), 검증 테스트(test), 지시문(instruction.md)으로 구성된다.
  14. 관측성에서 중요한 것은 단순 최종 답변이 아니라 메시지 궤적(trajectory)과 전체 실행 흔적(full trace)이다.
  15. 사용자는 thumbs-up/down을 잘 누르지 않기 때문에, 피드백은 UX 설계를 통해 간접적으로 얻는 것이 중요하다고 강조했다.
  16. 모든 trace에 고성능 모델 Opus를 심판으로 돌리면 비용이 커지므로, 저렴한 SLM이나 코드 기반 검증도 활용할 수 있다.
  17. LangSmith Engine은 내부적으로 LangSmith CLI에 접근하는 코딩 에이전트처럼 동작하며, trace를 필터링하고 공통 이슈를 찾아 issue board를 만든다.
  18. Engine 자체도 Slack 보고와 자체 benchmark인 issue bench로 도그푸딩하고 있다.
  19. Codex가 trace 분석에서 작은 스크립트를 많이 작성해 성능을 잘 냈고, LangChain 팀은 이를 배워 Engine의 codexification 스프린트를 진행했다.
  20. 금융권 고객은 너무 자율적인 Deep Agents를 불안해하며, 예측 가능성과 통제를 위해 더 명시적인 인지 아키텍처를 선호하는 경우가 있다.

1. 에이전트는 하네스, 모델, 맥락으로 구성된다

Harrison Chase는 “지능을 소유한다(own your intelligence)”는 관점에서 에이전트를 설명한다. 일반적으로 사람들은 에이전트를 말할 때 모델을 먼저 떠올리지만, LangChain은 에이전트를 세 부분으로 본다.

첫째는 모델(model)이다. 어떤 LLM을 쓰는지, 모델을 직접 소유하는지, 오픈 웨이트(open weight) 모델을 쓰는지, 여러 모델을 갈아 끼울 수 있는지가 여기에 해당한다. 예전 클라우드 인프라에서 “클라우드 독립성(cloud agnostic)”이 중요했던 것처럼, AI에서는 특정 모델 제공자에 종속되지 않고 필요할 때 가장 좋은 모델로 바꾸는 능력이 중요하다.

둘째는 맥락(context)이다. 에이전트가 참고하는 메모리(memory), 의미 지식(semantic knowledge), 이전 대화, 사용자별 선호, 업무 히스토리가 모두 맥락이다. 모델이 아무리 좋아도 맥락이 부족하거나 잘못 들어가면 좋은 답을 내기 어렵다.

셋째가 이 발표의 핵심인 하네스(harness)다. 하네스는 모델과 맥락을 조율하고, 도구 호출과 외부 시스템 상호작용을 관리하는 실행 구조다.

2. 하네스의 핵심 역할은 “맥락을 제때 가져오는 것”이다

하네스의 가장 중요한 일은 적절한 맥락을 적절한 시점에 모델로 가져오는 것이다.

에이전트는 고정 맥락(fixed context)과 동적 맥락(dynamic context)을 다룬다. 예를 들어 시스템 프롬프트나 정책 문서는 고정 맥락에 가깝고, 도구 호출 결과, 검색 결과, 고객과의 최근 대화, 파일 수정 내용은 동적 맥락에 가깝다.

에이전트가 외부 시스템과 상호작용하면 그 결과가 다시 새로운 맥락이 된다. 예를 들어 물류 시스템에서 주문 상태를 조회하면 “배송 준비 중”, “재고 부족”, “송장 생성 완료” 같은 결과가 나오고, 이것이 다시 에이전트의 다음 판단 재료가 된다. 하네스는 이 흐름 전체를 오케스트레이션(orchestration)한다.

가장 단순한 에이전트 구조는 다음과 같다.

  1. 요청이 들어온다.
  2. LLM이 응답을 생성한다.
  3. 응답 안에 도구 호출(tool call)이 있으면 도구를 실행한다.
  4. 도구 실행 결과(observation)를 다시 LLM에 넣는다.
  5. 필요한 만큼 반복한다.

즉, 오늘날 대부분의 에이전트는 기본적으로 루프를 도는 LLM + 도구 호출 구조다.

3. 미들웨어와 훅으로 기본 루프를 확장한다

Harrison은 LangChain을 매우 기본적이고 최소한의 하네스라고 설명한다. 그 위에 Deep Agents 같은 더 범용적인 하네스를 만들 수 있다. Deep Agents는 Claude Code와 비슷하지만 특정 모델에 묶이지 않는 모델 불가지론적(model-agnostic) 하네스다.

Deep Agents는 파일 시스템(file system), 스킬(skills), 서브에이전트(sub-agents) 같은 기능을 갖는다. 하지만 핵심은 여전히 단순한 LLM-도구 루프다. 차이는 그 루프의 여러 지점에 작은 조정 장치를 넣는다는 점이다.

이 조정 장치를 Harrison은 미들웨어(middleware)라고 부른다. 다른 코딩 에이전트 생태계에서는 훅(hook)이나 플러그인(plugin)이라고도 부른다.

예를 들어 다음과 같은 개입이 가능하다.

  • 에이전트 실행 전에 특정 코드 실행
  • 매번 모델 호출 전에 맥락 길이 확인
  • 모델 호출을 감싸서 로깅이나 라우팅 수행
  • 도구 호출을 감싸서 결과를 요약하거나 필터링
  • 너무 긴 결과를 맥락 밖으로 빼는 맥락 오프로딩(context offloading)
  • 파일 시스템, 샌드박스, 메모리, 서브에이전트 연결

중요한 점은 새로운 에이전트를 완전히 처음부터 만들지 않아도 기본 루프의 적절한 위치에 작은 커스터마이징을 넣을 수 있다는 것이다.

4. 인지 아키텍처는 여전히 필요할 때가 있다

2023~2024년에는 모델이 지금보다 약했기 때문에 에이전트가 단순 루프만으로는 일을 잘하지 못했다. 그래서 많은 팀이 명시적인 인지 아키텍처(cognitive architecture)를 설계했다.

예를 들어 딥 리서치(deep research) 에이전트는 먼저 하위 질문을 만들고, 질문을 여러 갈래로 나누어 조사한 뒤, 결과를 합치는 구조를 가질 수 있다. 코드 리뷰 봇은 코드 변경 확인, 위험 영역 탐지, 테스트 확인, 리뷰 코멘트 생성 같은 단계를 명시적으로 가질 수 있다.

요즘은 모델이 강해져서 많은 기능이 하네스 내부로 흡수됐다. 그래도 특정 업무 흐름에서는 여전히 인지 아키텍처가 필요하다. 특히 예측 가능성, 통제, 승인 절차가 중요한 금융·법률 같은 영역에서는 완전 자율 루프보다 명시적 단계와 검증 게이트가 선호될 수 있다.

Harrison의 추천은 간단하다.

처음에는 일반 하네스(general harness)로 시작한다. 빠르게 가치를 확인할 수 있기 때문이다. 이후 특정 사용 사례에서 정말 뛰어나야 할 부분이 보이면, 그 주변에 게이트(gate), 체크(check), 특화 단계들을 추가한다.

5. 기성 하네스를 쓸 것인가, 직접 만들 것인가

발표의 핵심 질문은 “언제 자체 하네스를 만들어야 하는가?”다.

Harrison의 답은 다음 기준으로 요약된다.

모델이 학습한 분포 안에 있는 작업일수록 기성 하네스가 잘 작동하고, 분포 밖으로 갈수록 하네스를 조정해야 한다.

기성 하네스의 예시는 Claude Code, Claude Agent SDK, Codex 등이다. 이들은 특정 모델 제공자의 모델과 밀접하게 맞춰져 있다.

하지만 법률 AI, 금융 AI, 사내 운영 자동화처럼 특수한 도메인으로 들어가면 전체 업무는 모델이 많이 학습한 범위를 벗어날 수 있다. 이런 경우 전체 하네스는 커스터마이징해야 할 가능성이 커진다.

다만 Harrison은 중요한 예외를 든다. 큰 업무는 특수하더라도 그 안의 작은 기능 중에는 모델이 이미 잘 학습한 기능이 있다. 예를 들어 법률 AI라도 “파일 편집(file editing)”은 OpenAI와 Claude 모델 모두 강화학습으로 많이 훈련한 작업이다.

문제는 모델마다 파일 편집을 잘하는 방식이 다르다는 것이다. 그래서 Deep Agents는 모델 프로필(model profiles)을 두고, 어떤 모델을 쓰느냐에 따라 파일 편집 구현을 바꾼다.

즉, 전략은 다음과 같다.

  • 전체 업무가 특수하면 하네스는 커스터마이징한다.
  • 하지만 모델이 이미 잘 학습한 작은 기능은 모델별 표준 방식에 최대한 맞춘다.

6. 평가(evals)는 조직 안에서 “좋음”을 정의한다

Harrison은 평가(evals)와 관측성(observability)이 지능을 소유하는 데 매우 중요하다고 말한다.

그는 Satya가 쓴 글에서 세 가지 요지를 인용한다.

첫째, 사내 전용 평가(private evals)를 만들어야 한다. 평가는 조직 안에서 무엇이 좋은 결과인지를 정의한다.

둘째, 조직의 메모리, 실행 흔적(traces), 피드백, 의사결정, 제도적 맥락(institutional context)을 소유해야 한다.

셋째, 지속 학습 루프를 만들어야 AI 투자가 회사 가치로 복리처럼 누적된다.

미션 크리티컬한 에이전트를 만드는 회사라면 결국 자기 업무에 맞는 벤치마크를 만들게 된다. 이 벤치마크는 두 가지 용도로 쓰인다.

  • 회귀(regression) 감지: 새 버전이 이전보다 나빠졌는지 확인
  • 힐클라이밍(hill climbing): 모델, 하네스, 프롬프트, 맥락을 바꿔가며 점진적으로 성능 개선

7. Harbor로 에이전트 벤치마크를 구성한다

Harrison은 Harbor를 업계 표준으로 떠오르는 오픈소스 평가 실행기(eval runner)로 소개한다. Harbor는 Terminal Bench 2를 만든 팀이 만든 도구이며, 코딩 에이전트뿐 아니라 다양한 도메인 벤치마크에도 사용되고 있다.

Harbor의 기본 구조는 다음과 같다.

구성 요소 설명
에이전트(agent) 평가할 대상. 모델과 하네스의 조합
데이터셋(dataset) 여러 개의 작업(task) 묶음
작업(task) 에이전트에게 줄 개별 문제
환경(environment) Dockerfile 등으로 정의된 샌드박스 실행 환경
정답 예시(solution) sanity check 용도의 기준 풀이
테스트(test) 에이전트 결과를 채점하는 검증 로직
지시문(instruction.md) 에이전트가 받는 프롬프트

테스트는 단순 단위 테스트(unit test)일 수도 있고, 코드 실행일 수도 있고, LLM-as-a-judge 방식일 수도 있다. 즉, 각 작업마다 “어떻게 성공 여부를 판단할지”를 정의하는 것이 핵심이다.

평가 결과를 볼 때는 정확도만 보면 안 된다. 에이전트 운영에서는 정확도(accuracy), 지연시간(latency), 토큰 사용량(tokens), 비용(cost)을 함께 봐야 한다.

8. 관측성은 에이전트 디버깅의 핵심이다

Harrison은 관측성이 에이전트에서 과소평가되고 있다고 말한다.

에이전트가 실패할 때 겉으로는 “LLM 호출이 잘못됐다”고 보인다. 하지만 그 이유는 보통 두 가지다.

  1. 모델 자체가 충분히 좋지 않다.
  2. 모델이 받은 맥락(context)이 좋지 않다.

Harrison은 두 번째가 더 자주 문제를 일으킨다고 본다. 따라서 디버깅하려면 모델의 맥락 창에 무엇이 들어갔는지, 그 맥락이 어떤 도구 호출과 단계들을 거쳐 쌓였는지 볼 수 있어야 한다.

LangSmith는 이를 위해 두 가지 보기를 제공한다.

첫째는 사용자 친화적인 메시지 궤적(trajectory) 보기다. Claude Code처럼 사용자의 메시지, 에이전트의 도구 호출, 최종 응답이 이어지는 흐름을 훑어볼 수 있다.

둘째는 전체 실행 흔적(full trace) 보기다. 특정 도구 호출, 모델 입력, 모델 출력, 내부 단계까지 더 깊게 들어가 디버깅할 수 있다.

9. 데이터 플라이휠: trace에서 개선으로

평가와 관측성이 있으면 데이터 플라이휠(data flywheel)을 만들 수 있다.

흐름은 단순하다.

  1. 에이전트를 만든다.
  2. 실제로 실행한다.
  3. 많은 실행 흔적(trace)을 수집한다.
  4. trace 데이터를 선별(curate)한다.
  5. 그 데이터로 실험(experiment)을 돌린다.
  6. 하네스, 모델, 맥락을 개선한다.

여기서 중요한 것은 피드백(feedback)이다. 피드백은 환경에서 직접 얻을 수도 있고, 합성 피드백(synthetic feedback)으로 만들 수도 있다.

사용자에게 thumbs-up/down 버튼을 누르라고 해도 대부분은 누르지 않는다. 그래서 UX 설계가 중요하다. 사용자가 어떤 결과를 수정했는지, 어떤 제안을 채택했는지, 어디서 멈췄는지 같은 행동을 통해 간접 피드백을 얻을 수 있다.

또한 온라인 평가자(online evaluator)를 trace 위에 돌릴 수 있다. 예를 들어 LLM-as-a-judge로 결과 품질을 판정할 수 있다. 다만 비싼 모델을 모든 trace에 돌리면 비용이 커지므로, 저렴하고 빠른 SLM을 파인튜닝하거나, 간단한 경우 코드 기반 검증을 사용할 수 있다.

이 데이터는 세 방향으로 쓰인다.

  • 하네스 개선: 하네스 엔지니어링(harness engineering)
  • 모델 개선: 파인튜닝(fine-tuning)
  • 맥락 개선: 메모리(memory), 검색, 프롬프트, 지식 구조 개선

10. LangSmith Engine은 개선 루프를 자동화하려는 시도다

LangSmith Engine은 trace 위에서 동작하는 에이전트다. 목적은 trace를 보고 문제 패턴을 찾아내고, 개선안을 제시하며, 일부 수정까지 제안하는 것이다.

Engine은 LangSmith CLI에 접근할 수 있는 코딩 에이전트처럼 동작한다. trace를 피드백 기준으로 필터링하고, 여러 sub-agent를 사용해 데이터를 탐색한다. 이후 공통 이슈를 찾아 issue board를 만든다.

예를 들어 어떤 문제에 대해 설명을 붙이고, 근거가 되는 trace 링크를 연결하며, 프롬프트나 지시문 변경, 맥락 업데이트, 하네스 코드 수정안을 제안한다.

Harrison은 이를 “run agent, get traces, see patterns, fix”의 자동화라고 설명한다. 즉, 에이전트를 운영하면서 생기는 데이터를 다시 에이전트 개선에 투입하는 구조다.

11. Q&A: Engine을 Engine에 돌리는가

질문자는 “Engine 자체도 에이전트인데, Engine을 Engine에 돌려본 적이 있느냐”고 물었다.

Harrison은 실제로 그렇게 하고 있다고 답한다. Engine은 Slack과 연결되어 자기 자신에 대한 보고도 보낸다. LangChain 팀은 이를 도그푸딩(dogfooding) 방식으로 사용한다.

또한 Engine을 위한 issue bench라는 벤치마크도 만들었다. Harbor 형식의 벤치마크이며, 다양한 모델과 하네스를 계속 비교한다.

한 흥미로운 관찰은 Codex가 trace 분석 작업에서 작은 스크립트를 많이 작성해 실행했고, 그 방식이 성능에 도움이 되었다는 점이다. LangChain 팀은 이를 보고 “codexification of Engine”이라는 스프린트를 진행했다. 즉, Codex가 잘한 전략을 Engine 하네스에 반영한 것이다.

이 사례는 벤치마크의 장점을 보여준다. 여러 하네스와 모델을 같은 문제에 돌려보고, 잘하는 방식을 다시 자기 핵심 에이전트에 가져올 수 있다.

12. Q&A: 하네스는 수렴할까, 분화할까

마지막 질문은 하네스가 하나의 표준 방식으로 수렴할지, 아니면 회사·도메인별로 다양하게 분화할지였다.

Harrison은 솔직한 답은 “모르겠다”고 했다. 다만 몇 가지 경향은 보인다고 말했다.

일반 목적 하네스는 이미 기본 업무에 충분히 좋아지고 있다. 그래서 처음 시작할 때는 Deep Agents, Codex, Claude Code 같은 기성 하네스로 시작하는 것이 좋다. 파일 시스템 접근, 서브에이전트, 도구 사용 같은 패턴은 꽤 보편화되고 있다.

하지만 업무가 분포 밖으로 갈수록 커스터마이징 필요성이 커진다. 극단적으로는 완전히 특화된 인지 아키텍처를 만들어야 할 수도 있다.

또 다른 이유는 예측 가능성과 통제다. 금융 서비스 고객들은 너무 자율적인 에이전트를 무서워할 수 있다. 이들은 더 세밀하게 통제 가능한 단계형 구조를 원한다.

결론적으로 하네스는 일부 공통 기능에서는 수렴하겠지만, 특정 도메인에서는 분화될 수 있다. 예를 들어 한 모델 연구소가 바이오(bio) 분야에 깊게 투자하면, 그쪽 하네스는 바이오 에이전트 작업에 맞춰 특화될 수 있다.

그래서 지금처럼 빠르게 변하는 공간에서는 평가와 관측성이 필수다. 직접 측정하지 않으면 어떤 하네스가 좋은지 알 수 없다.

에이폼 적용 관점

① 이 얘기가 이커머스·물류 운영에 꽂히는 지점: 주문, 재고, CS, 송장, 반품처럼 여러 시스템을 오가야 하는 업무는 모델보다 하네스가 맥락과 도구를 어떻게 연결하느냐가 성패를 가른다.
② 지금 당장 시험해볼 것 하나: “배송 지연 문의 처리” 같은 단일 업무를 정해, 입력·도구 호출·판단·최종 답변 trace를 남기고 성공/실패 기준 평가표를 만든다.
③ 우리 상황과 다른 전제 하나: 발표는 개발자 도구·코딩 에이전트 예시가 많으므로, 이커머스에서는 파일 편집보다 ERP·WMS·택배사 API·CS 정책 같은 운영 맥락 연결이 더 중요하다.

종합 체크리스트

  • [ ] 에이전트를 모델, 맥락, 하네스로 나눠서 현재 병목을 진단한다.
  • [ ] 처음부터 자체 하네스를 만들기보다 기성 하네스로 빠르게 PoC를 한다.
  • [ ] 우리 업무가 인-디스트리뷰션인지 아웃-오브-디스트리뷰션인지 구분한다.
  • [ ] 주문조회, 재고확인, 반품정책 확인 등 도구 호출 결과를 trace로 남긴다.
  • [ ] “좋은 답변” 기준을 사내 평가표로 정의한다.
  • [ ] 정확도뿐 아니라 응답 시간, 토큰 비용, 재시도 횟수를 함께 본다.
  • [ ] 실패 사례에서 모델 문제가 아니라 맥락 누락·오염 문제인지 먼저 확인한다.
  • [ ] 고객 피드백 버튼에만 의존하지 말고 상담원 수정, 채택 여부, 재문의율을 간접 피드백으로 본다.
  • [ ] 반복 실패 패턴을 모아 프롬프트, 도구 설명, 정책 문서, 하네스 로직 중 무엇을 고칠지 분류한다.
  • [ ] 통제가 중요한 업무는 완전 자율 에이전트보다 단계형 인지 아키텍처를 검토한다.

Harrison을 소개하게 되어 기쁩니다. 저는 2022년 GPT-3 시절 Twitter에서 Harrison을 처음 봤습니다. 그는 “이 모델들을 단순 자동완성 작업이 아니라 가상 협업자나 에이전트처럼 작동하게 하려면 어떤 하네스를 둘러야 할까?”를 초기에 고민한 사람 중 하나였습니다. 2022년 이후 생태계는 크게 성장했고, Harrison 역시 에이전트와 하네스 구축, 평가 방식에 대한 생각을 많이 발전시켜 왔습니다.

오늘 발표는 하네스와 평가(evals)에 관한 내용입니다. 형식은 대략 15분 발표와 15분 질의응답입니다. Harrison, 와주셔서 감사합니다.

저는 Harrison이고 LangChain의 공동창업자 겸 CEO입니다. 오늘은 “자신의 지능을 소유한다(owning your own intelligence)”는 맥락에서 평가와 하네스에 대해 이야기하겠습니다.

지능을 이야기할 때 우리는 보통 에이전트를 말합니다. 그렇다면 에이전트는 무엇으로 구성될까요? LangChain에서는 크게 세 부분으로 봅니다. 하네스가 모델과 맥락을 오케스트레이션하는 구조입니다. 지능을 소유하려면 이 세 부분을 모두 소유하고 싶을 것입니다.

모델 소유에 대해서는 깊게 이야기하지 않겠습니다. Fireworks의 Lin이 오픈 웨이트 모델(open weight models)에 대해 이야기했습니다. 여기서 중요한 한 부분은 모델을 바꿀 수 있는 능력입니다. 예전에는 클라우드에 종속되지 않는 클라우드 독립성(cloud agnostic) 개념이 있었습니다. 지금은 모델에서도 같은 개념이 있습니다. 락인(lock-in)을 피하고, 더 좋은 모델이 나오면 그것을 쓰기 위해 모델을 바꿀 수 있어야 합니다.

맥락(context)도 소유해야 합니다. 에이전트가 사용하는 모든 맥락, 즉 메모리(memory), 의미 지식(semantic knowledge), 이전 대화 등이 여기에 해당합니다. 이런 것들은 에이전트를 개인화하고 진행 방향을 안내합니다.

마지막이 하네스이고, 오늘 제가 집중하려는 부분입니다.

하네스를 소유한다는 것은 무엇일까요? 하네스의 주된 일은 무엇일까요? 하네스의 핵심 역할은 적절한 시점에 적절한 맥락을 모델로 가져오는 것입니다.

하네스는 고정 맥락과 동적 맥락을 조율합니다. 그것을 모델의 맥락 창(context window)에 넣고, 모델에게 보여준 뒤 응답을 받고, 그 응답으로 어떤 행동을 합니다.

에이전트는 일을 완수하기 위해 여러 가지를 해야 합니다. 도메인 특화 작업도 많지만, 외부 시스템과 상호작용해야 합니다. 외부 시스템과 상호작용하면 더 많은 맥락이 발생하고, 그 맥락이 다시 에이전트 루프로 들어갑니다. 하네스는 이 모든 것을 함께 조율하는 장치입니다.

사람들이 에이전트를 말할 때 가장 단순한 형태는 루프 안에서 도구를 호출하는 LLM입니다.

이 구조는 단순하지만 매우 일반적입니다. 요청이 들어오면 LLM이 생성을 합니다. 그 생성 안에 호출할 도구가 있을 수 있습니다. 그러면 도구를 실행하고, 관찰 결과(observation)를 다시 LLM에 전달합니다. 이것이 오늘날 거의 모든 에이전트의 핵심 구조입니다.

하지만 에이전트들은 조금씩 다릅니다. 기본 루프는 같지만, 각 하네스는 여러 단계에서 커스터마이징할 수 있습니다.

LangChain은 매우 기본적이고 최소한의 하네스입니다. Deep Agents는 Claude Code의 모델 불가지론적이고 더 범용적인 버전이라고 볼 수 있습니다. Deep Agents는 더 많은 일을 합니다. 파일 시스템에 연결하고, 스킬을 갖고, 서브에이전트를 사용합니다.

이것은 단순한 하네스 위에 만들어졌지만, 여러 레버를 통해 커스터마이징됩니다. 에이전트가 호출되기 전, 각 모델 호출 전, 모델 호출을 감싸는 부분, 도구 호출을 감싸는 부분 등에 특정 코드 조각을 실행할 수 있습니다. 이렇게 작은 미들웨어(middleware) 구조를 사용해 기본 루프를 강력하게 바꿀 수 있습니다.

하네스를 커스터마이징하는 다른 방법도 있지만, 코딩 에이전트 생태계에서는 훅(hooks)과 플러그인(plugins) 개념으로 많이 나타납니다. 기본 루프가 돌아가고, 여러 지점에 작은 훅이나 플러그인을 추가해 커스터마이징하는 방식입니다.

이런 커스터마이징을 통해 샌드박스(sandbox), 파일 시스템, 서브에이전트, 메모리, 요약(summarization) 등을 추가할 수 있습니다. 예를 들어 요약은 모델 호출 전에 들어갑니다. 모델을 호출하기 전에 맥락이 너무 길어진 것은 아닌지 확인하고, 길면 요약합니다. 맥락 오프로딩(context offloading)도 마찬가지입니다. 큰 도구 호출 결과를 덜어내는 방식이고, 도구 호출을 감싸는 형태로 들어갑니다.

핵심은 에이전트에는 매우 단순하고 일반적인 구조가 있다는 것입니다. 더 고급 에이전트 하네스들도 기본적으로 그 루프를 돌지만, 그 위에 여러 기능을 추가합니다. 따라서 자체 하네스를 만들거나 커스터마이징할 때, 어떤 지점에 무엇을 삽입할 수 있는지 생각해야 합니다. 자체 요약 단계를 추가하거나, 특정 도구 호출 처리 방식을 바꾸는 식으로 도메인에 맞게 하네스를 조정할 수 있습니다.

하네스를 커스터마이징하는 또 다른 방식은 더 명시적인 인지 아키텍처(cognitive architecture)를 두는 것입니다.

2023년과 2024년에는 모델이 루프만으로 충분히 잘 작동하지 않았기 때문에 사람들이 이런 방식으로 에이전트를 많이 만들었습니다. 특정 일을 하게 만들려면 맞춤형 인지 아키텍처가 필요했습니다. 예를 들어 딥 리서치에서는 하위 질문을 만들고, 그것을 여러 갈래로 나누어 실행한 뒤 다시 합칩니다. 코드 리뷰 봇에서는 매우 구체적인 단계들이 있습니다.

지금은 이 중 많은 것이 하네스 안으로 들어갔습니다. 그래도 특정 흐름에서는 이런 인지 아키텍처를 사용해 에이전트를 명확히 안내하는 경우가 있습니다. 저희가 추천하는 방식은 일반 하네스로 시작하는 것입니다. 시작하기 가장 쉽고, 가치 확인까지 가장 빠릅니다. 이후 정말 뛰어나야 하는 사용 사례가 좁혀지면, 그 주변에 게이트와 체크를 추가해 특정 방향으로 안내하면 됩니다.

자주 받는 질문은 “언제 자체 하네스를 만들고, 언제 기성 하네스를 써야 하는가?”입니다. 기성 하네스에는 특정 모델과 함께 작동하는 Claude Code, Claude Agent SDK, Codex 등이 있습니다. 이것은 업계의 큰 질문입니다. 제 일반적인 답은 이렇습니다. 모델이 학습한 분포 안(in-distribution)에 가까운 작업일수록 기성 하네스가 더 잘 작동합니다. 작업이 분포 밖(out-of-distribution)으로 멀어질수록 하네스를 조정하고 싶어질 것입니다.

하네스를 조정하는 방법에도 차이가 있습니다. 어떤 큰 작업은 분포 밖이지만, 그 안의 일부 작은 작업은 모델이 이미 잘 학습한 분포 안일 수 있습니다. 예를 들어 법률 AI를 생각해봅시다. 법률 AI 전체는 모델 입장에서 특수한 작업일 수 있습니다. 하지만 파일 편집(file editing)은 주요 모델들이 강화학습(RL)으로 많이 훈련한 작업입니다. 그리고 OpenAI 모델과 Claude 모델은 각자의 하네스 안에서 서로 다른 방식으로 파일을 편집하도록 훈련되어, 실제로 잘하는 방식도 다릅니다.

따라서 법률 AI 같은 큰 작업에는 커스텀 하네스가 필요할 수 있지만, 파일 편집 도구만큼은 사용하는 모델이 학습한 방식에 가깝게 유지하는 것이 좋습니다. Deep Agents에는 모델 프로필(model profiles) 개념이 있습니다. 파일 편집처럼 모델이 잘 학습한 기능은 사용하는 모델에 따라 구현을 바꿉니다. 전체 하네스는 특수 업무에 맞게 조정하되, 작은 인-디스트리뷰션 기능은 모델 계층에 가깝게 유지하는 것입니다.

다음 큰 주제는 평가(evals)와 관측성(observability)입니다.

에이전트의 모델, 하네스, 맥락을 실험하려면 시스템 내부에서 무슨 일이 일어나는지 알아야 하고, 평가할 수 있어야 합니다. 이것은 커스텀 하네스뿐 아니라 커스텀 모델에도 유용합니다.

2주 전 Satya가 쓴 좋은 글이 있었습니다. 그중 세 문장이 인상적이었습니다. 첫째, 사내 전용 평가를 만들라는 것입니다. 평가는 조직 안에서 무엇이 좋은지를 정의합니다. 둘째, 조직의 메모리, 실행 흔적, 피드백, 의사결정, 제도적 맥락을 소유하라는 것입니다. 셋째, 지속 학습 루프, 즉 회사의 AI 투자가 복리처럼 쌓이게 하는 힐클라이밍 머신을 만들라는 것입니다. 이것들은 평가와 관측성, 그리고 그것들이 가능하게 하는 학습 루프가 지능을 소유하는 데 얼마나 중요한지 보여줍니다.

미션 크리티컬한 에이전트를 만드는 회사라면 그 에이전트를 위한 벤치마크를 만들게 됩니다. 벤치마크는 회귀를 정의하고 잡아내는 데 쓰일 수 있고, 하네스나 모델을 조정하며 성능을 끌어올리는 데도 쓰일 수 있습니다.

이런 벤치마크를 정의하는 데 업계 표준으로 떠오르는 것이 Harbor입니다. Harbor는 오픈소스 평가 실행기(eval runner)입니다. Terminal Bench 2를 만든 사람들이 만들었고, 다양한 도메인에서 인기를 얻고 있습니다.

Harbor는 에이전트를 데이터셋에 대해 실행합니다. 데이터셋에는 여러 작업이 있습니다. 이런 작업들은 보통 샌드박스에서 실행됩니다. 병렬화하고 싶을 수 있고, 각 작업이 자체 환경을 갖기 때문입니다.

Harbor 작업은 환경(environment), 정답 예시(solution), 테스트(test), 지시문(instruction.md)으로 구성됩니다. 환경은 에이전트가 실행될 곳이며 Dockerfile로 정의할 수 있습니다. 정답 예시는 sanity check용입니다. 테스트는 더 중요합니다. 테스트는 에이전트 실행을 검증하는 채점기입니다. 테스트 스크립트는 코드 실행, 단위 테스트, LLM 심판, 에이전트 심판 등 무엇이든 할 수 있습니다. 지시문은 에이전트에게 주어지는 프롬프트입니다.

이렇게 여러 작업을 정의하고 샌드박스에서 실행한 뒤, 모델과 하네스로 구성된 에이전트의 점수를 냅니다.

평가 결과에서는 여러 실험을 비교할 수 있습니다. LangSmith는 평가와 관측성을 위한 플랫폼입니다. Harbor와 통합되어 있고 피드백 점수, 지연시간, 토큰 사용량을 볼 수 있습니다. 에이전트를 벤치마크할 때는 정확도만 중요한 것이 아닙니다. 지연시간과 비용도 중요합니다.

관측성은 기본적인 것처럼 들리지만 에이전트에서는 매우 중요하고 과소평가되어 있습니다. 에이전트가 실패하면 LLM 호출이 잘못된 것입니다. 왜 잘못될까요? 두 가지 이유가 있습니다. 하나는 모델이 충분히 좋지 않은 경우입니다. 다른 하나는 LLM이 받은 맥락이 충분히 좋지 않은 경우입니다. 저는 대부분 두 번째가 더 자주 문제를 일으킨다고 생각합니다.

따라서 모델의 맥락 창에 무엇이 들어갔는지, 그 맥락이 어떻게 쌓였는지, 어떤 단계와 도구 호출이 있었는지 잘 관찰할 수 있어야 합니다. 이것이 에이전트 디버깅에 중요합니다.

LangSmith에는 사용자 친화적인 관측성 보기가 있습니다. Claude Code와 비슷하게 일부 도구 호출을 숨겨 흐름을 쉽게 훑어볼 수 있습니다. 요즘 대부분의 에이전트 경로는 궤적(trajectory) 형태입니다. 사용자가 메시지를 입력하고, 에이전트가 여러 도구 호출을 하고, 응답하고, 다시 사용자가 입력하는 메시지들의 목록입니다. 하지만 이것만으로 완전한 디버깅은 부족합니다. 그래서 전체 trace를 보고 특정 항목을 클릭해 모델 내부에서 정확히 무슨 일이 있었는지 볼 수 있어야 합니다.

평가와 관측성이 있으면 데이터 플라이휠(data flywheel)을 만들 수 있습니다. 에이전트를 사용하고, 사용자들이 사용하면서 피드백을 주면 지능이 누적됩니다.

높은 수준에서는 단순합니다. 에이전트를 만들고 실행합니다. 많은 trace를 수집합니다. trace 데이터를 선별합니다. 그 데이터로 실험을 돌립니다. 단순해 보이지만 내부에는 복잡성이 많습니다.

여기서 중요한 것은 피드백입니다. 피드백은 환경에서 얻을 수도 있고 합성 소스에서 얻을 수도 있습니다. 환경 피드백과 관련해 에이전트 설계에서 과소평가되는 것은 UX 설계입니다. 에이전트를 사용자에게 똑똑하게 보여주면 많은 피드백을 얻을 수 있습니다. 사용자가 명시적으로 thumbs-up이나 thumbs-down을 누르지 않더라도, UX를 잘 설계하면 피드백을 얻을 수 있습니다.

합성 피드백도 가능합니다. 온라인 평가자(online evaluators)를 trace 위에 돌려 판단하게 할 수 있습니다. Harvey와 했던 실험에서는 LLM-as-a-judge 유형의 비용을 크게 줄였습니다. 시스템에 들어오는 모든 trace에 Opus를 돌린다고 생각하면 비용이 커집니다. 그래서 저렴하고 빠른 방식이 필요합니다. 저희는 이를 위해 SLM을 파인튜닝하기도 했고, 기성 모델에 커스텀 프롬프트를 넣어 사용할 수도 있습니다. 단순한 검증은 코드로도 할 수 있습니다.

trace 데이터를 선별할 때 피드백이 큰 역할을 합니다. 그리고 이 데이터를 사용해 에이전트의 어느 부분이든 업데이트할 수 있습니다. 하네스 엔지니어링으로 하네스를 개선할 수 있고, 파인튜닝으로 모델을 개선할 수 있고, 메모리로 맥락을 개선할 수 있습니다.

LangChain에서 저희가 가장 많이 생각하는 부분은 하네스 엔지니어링입니다. 그래서 이를 돕기 위해 추가한 기능을 짧게 보여드리겠습니다. 다음 발표에서는 Trajectory가 파인튜닝에 대해 이야기할 것입니다. 과정은 비슷합니다. 에이전트를 실행하고 trace를 얻고, 그 데이터를 사용해 시스템을 개선합니다. 시스템은 모델, 하네스, 맥락 세 부분이며, 어느 부분이든 업데이트될 수 있습니다.

전체 흐름은 이렇게 끝에서 끝까지 이어집니다. 저희가 고민하는 것은 이 과정을 가능한 많이 자동화하는 방법입니다. 이 작업은 어렵고 시간이 많이 걸립니다.

최근 몇 달 동안 저희는 LangSmith Engine이라는 것을 생각해왔습니다. 이것은 trace 위에 앉아 이 모든 작업을 수행하는 에이전트입니다.

trace가 있고, 그다음 작업은 trace를 선별하고 실험을 돌리며 세 부분 중 하나에 대한 수정안을 제안하는 것입니다. 저희는 주로 하네스 엔지니어링에 집중합니다. 데모에서는 이것이 어떻게 보이는지 보여드리겠습니다.

LangSmith에는 많은 trace가 들어오고 있습니다. Engine이라는 탭이 있습니다. 이것은 백그라운드에서 실행되는 에이전트입니다. issue board를 만듭니다. 이것이 데이터 선별 부분입니다. 내부적으로는 LangSmith CLI에 접근할 수 있는 코딩 에이전트입니다. LangSmith CLI는 피드백 등으로 trace를 필터링할 수 있습니다. 저희는 큰 프롬프트와 몇몇 서브에이전트를 주고, 데이터를 탐색하며 공통 문제를 찾게 합니다. 그러면 여기 이슈를 생성합니다.

생성된 이슈에는 설명이 있고, 근거가 되는 trace 링크가 있습니다. 아래에는 프롬프트의 간단한 변경, 맥락 업데이트, 지시문 업데이트, 하네스에 들어갈 코드 추가 등이 보입니다.

이것은 최근 몇 달 사이 출시한 기능이며, 데이터 플라이휠을 보여줍니다. 에이전트를 실행하고, trace를 얻고, 패턴을 보고, 고치는 단순한 흐름입니다. 이것을 자동화하려는 시도입니다.

질문: Engine 자체도 에이전트입니다. 프롬프트를 받고 검색하는 구조인데, Engine을 Engine에 돌려본 적이 있나요?

답변: 네, 실행하고 있습니다. Engine은 Slack에도 연결되어 자기 자신에 대한 보고서를 보냅니다. 그렇게 도그푸딩하고 있습니다.

또한 Engine을 위한 issue bench라는 것도 만들었습니다. Harbor 형식의 벤치마크이며, 여러 모델과 하네스를 계속 벤치마크합니다.

벤치마크가 있으면 여러 하네스에 돌려보고 무엇을 잘하고 못하는지 볼 수 있습니다. 몇 주 전 저희 Deep Agents, Codex, Claude Code를 이 벤치마크에 돌렸습니다. Codex는 trace에 대해 작은 스크립트를 많이 작성해 실행하는 흥미로운 방식을 썼고, 그것을 매우 적극적으로 해서 성능이 좋았습니다.

그래서 저희는 Engine의 codexification이라고 부르는 스프린트를 진행했습니다. 그 배움을 Engine의 핵심 하네스에 가져온 것입니다. 벤치마크의 또 다른 장점은 여러 방식을 돌려보고 실제 성능을 본 뒤, 좋은 것을 핵심 에이전트 하네스에 반영할 수 있다는 점입니다.

질문: 하네스가 하나로 수렴하고 사용자와 모델이 거기에 맞게 교육될까요? 아니면 회사마다 최적화된 방식으로 다양해질까요?

답변: 좋은 질문입니다. 저희도 많이 생각합니다. 솔직한 답은 모르겠다는 것입니다. 다만 제가 본 것은 범용 하네스가 기본 업무에는 충분히 좋아졌다는 점입니다. 시작할 때는 Deep Agents, Codex, Claude Code 같은 기성 하네스로 시작하는 것을 추천합니다.

모델도 충분히 좋아졌고, 모델을 잘 작동하게 하는 요소들, 예를 들어 파일 시스템 접근, 서브에이전트 같은 것도 어느 정도 충분해졌습니다. 하지만 작업이 분포 밖으로 갈수록 하네스를 커스터마이징하고 싶어질 것입니다. 극단적으로는 특정 업무에 완전히 집중한 인지 아키텍처를 만들 수도 있습니다.

또 다른 이유는 예측 가능성과 통제입니다. 금융 서비스 고객 중에는 예측 가능성을 필요로 하는 곳이 많습니다. Deep Agents 같은 것을 보여주면 너무 무섭다고 말합니다. 그들은 더 통제 가능한 커스텀 인지 아키텍처를 원합니다.

반대편에는 기성 하네스를 그대로 쓰는 방식이 있고, 중간에는 훅이나 미들웨어를 쓰는 방식이 있습니다. 이것은 스펙트럼입니다. 작업이 분포 밖으로 갈수록 더 커스텀 하네스를 원하게 됩니다.

또 이상한 점도 있습니다. OpenAI와 Anthropic 모두 코딩에 매우 좋아지고 있지만, 파일을 편집하는 방식은 꽤 다릅니다. 어떤 사람은 한 방식이 다른 방식보다 엄격히 더 우월하다고 생각할 수도 있습니다.

모델 연구소들은 모두 코딩을 잘하는 방향으로 수렴할 것입니다. 하네스도 계속 그 길을 가면 코딩에 좋은 방향으로 수렴할 것입니다. 하지만 동시에 아주 작은 차이들이 있고, 저도 그것들을 완전히 설명할 수는 없습니다.

지금은 이런 차이가 작은 기능에서 가장 구체적으로 보입니다. 하지만 어떤 연구소가 바이오 분야로 깊이 들어가고, 그 하네스가 바이오 에이전트 작업에 매우 좋아진다면 하네스 자체가 분화하기 시작할 수 있습니다.

빠르게 변하는 공간이라 답은 모르겠습니다. 그래서 평가와 관측성이 중요합니다. 모든 것을 측정해야 합니다.
