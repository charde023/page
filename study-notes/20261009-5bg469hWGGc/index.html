대시보드는 끝났습니다: AI 에이전트가 소프트웨어를 쓰는 법

업로드 2026-10-09 · 10.2분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 발표의 중심 주장은 단순하다. 사람은 대시보드나 검색 문법 자체를 원하는 것이 아니라 필요한 답과 완료된 작업을 원한다. 그런데 지금까지의 소프트웨어는 사람이 화면을 열고, 메뉴를 찾고, 앱마다 다른 검색 문법을 익혀야 작동했다. AI 에이전트가 그 일을 대신하려면 단순히 각 앱에 접속할 문만 열어 주는 것으로는 부족하다. 목표에 맞는 도구를 찾고, 호출 순서를 세우고, 여러 앱의 정보를 연결하면서도 모델의 제한된 입력 공간을 낭비하지 않는 인터페이스가 필요하다는 것이 화자의 설명이다.

읽는 법: 위에서 아래로 읽는다. 파란 상자는 연결 수단, 주황 점선 상자는 연결 후에도 남는 문제, 초록 상자는 최종 가치 기준이다. 수치를 표시한 그래프가 아니라 발표의 인과를 정리한 개념도다.

화자는 이 문제를 자신의 Datadog 경험으로 시작한다. 지난 6개월 동안 Datadog을 매일 사용했다고 말하지만, 동료와 함께 화면을 열었을 때 로그아웃되어 있었고 대시보드에서 무엇이 어디에 있는지도 몰랐다. 대시보드를 직접 열지 않고 다른 방식으로 서비스를 사용해 왔기 때문이다. 그는 이것이 Datadog을 비판하는 이야기가 아니라, 사용자가 원한 것은 화면 자체가 아니라 필요한 답이었다는 사례라고 설명한다.

2022년의 버그 조사 사례에서는 Slack의 상황을 읽고, Datadog을 조회하고, PostHog에서 세션을 확인하고, VS Code에서 수정하고, GitHub에서 PR을 여는 다섯 도구를 오갔다고 한다. 화면만 다른 것이 아니다. Datadog의 질의 문법, Jira의 JQL, Slack 검색 수정자처럼 서비스마다 정보를 요청하는 방식도 달랐다. 같은 SQL이라는 이름을 쓰더라도 서비스별 차이가 있다고 지적한다. 대시보드는 사람의 의도를 기계가 이해할 수 있는 요청으로 바꾸는 번역 장치였다는 해석이다.

2023년에는 화자가 ‘반짝이 버튼’이라고 부르는 AI 기능이 등장했다. 대규모 언어 모델이 사용자의 질문을 질의문으로 바꿔 주었지만, 화자 표현으로는 두 번보다 많은 데이터베이스 조인이 필요한 질문에서 한계가 있었다. 2024년 11월 Anthropic이 발표한 MCP(Model Context Protocol)는 AI 시스템과 데이터 소스를 연결하는 공개 표준을 약속했다. 이제 Claude 같은 에이전트가 질의를 만들고 실행해 답까지 가져올 수 있게 되었다는 설명이다.

그러나 MCP는 통신 규칙과 통로일 뿐, 에이전트가 서비스를 잘 쓰도록 설계된 완성된 작업 방식은 아니다. 서비스가 어떤 도구를 어떤 형태로 제공할지는 여전히 서비스 측 선택에 달려 있다.

읽는 법: 세 상자는 순서가 아니라 동시에 생길 수 있는 세 종류의 병목이다. 첫째는 반복 오류, 둘째는 잘못된 도구 선택과 호출 순서, 셋째는 교차 앱 작업의 단절로 이어진다. 색은 구분용이며 우열이나 측정값을 뜻하지 않는다.

화자가 제안하는 해법은 에이전트가 모든 도구 설명을 처음부터 읽게 하지 않는 것이다. 먼저 목표를 받아 필요한 도구와 실행 계획을 찾고, 그때 필요한 정보만 제공한다. Composio는 여러 앱의 복잡하고 자주 변하며 문서가 부족한 API를 에이전트가 사용하기 쉬운 형태로 번역하고, MCP·CLI·네이티브 도구 위에 통합된 경험을 만든다고 설명한다.

첫 번째 사례는 2026년에 버그를 처리하는 방식을 가정한 목업 데모다. 사용자가 Slack 메시지 링크를 Claude에 붙여 넣고 Sentry와 Datadog으로 원인을 찾아 초안 PR을 만들라고 요청한다. Composio Search는 Slack 메시지 가져오기, Sentry 이슈 검색, Datadog 로그 검색이라는 세 검색 과업에 필요한 도구와 사용 계획을 반환한다. Slack에서는 메시지를 찾기 전에 채널 ID를 찾아야 한다는 선행 단계도 알려 준다. 에이전트는 Slack의 불만 내용을 가져오고, Datadog과 Sentry를 병렬로 조사하며 코드베이스를 살핀다. 화자는 원인을 찾은 뒤 5분 이내에 수정 PR이 만들어진다고 시연하지만, 이를 실제 운영 검증 결과가 아니라 목업으로 제시했다.

읽는 법: 위에서 아래로 실행 순서를 따른다. 핵심은 두 번째 단계다. MCP 접속 자체가 아니라 어떤 도구를 어떤 순서로 쓸지 좁히는 층이 추가되어 있다. 마지막의 5분 이내 결과는 화자의 목업 시연 주장이지 이 전사만으로 독립 검증된 성능 수치가 아니다.

두 번째 사례는 화자가 평소 사용하는 전형적인 분석이라고 소개한다. Claude가 PostHog에서 온보딩 때 전자상거래를 선택한 사용자 ID를 찾고, 전체 결과를 모델의 입력 공간에 넣지 않은 채 저장한다. 이어 Metabase에서 데이터베이스 구조와 일부 표본을 확인한다. 충분히 구조를 파악한 뒤 Composio Remote Workbench가 사용자 ID를 찾는 정규표현식이 포함된 SQL 질의를 동적으로 만든다. 그 결과 PostHog와 Metabase의 데이터를 연결해 해당 사용자 집단이 선호하는 도구 모음을 확인한다. 여기서 중요한 설계 원리는 많은 데이터를 전부 모델에 넣는 대신 외부에서 저장·조회·실행하고 필요한 결과만 가져오는 것이다.

화자의 결론은 앞으로 제품이 사람뿐 아니라 에이전트라는 새로운 사용자를 상대해야 한다는 것이다. 사람은 화면을 보고 버튼을 누르지만, 에이전트는 목표와 도구를 가지고 와서 일을 끝낼 수 있는지를 기준으로 서비스를 판단한다는 주장이다. 따라서 “대시보드가 죽었다”는 말은 모든 화면이 실제로 사라졌다는 검증된 예측이라기보다, 제품 설계의 중심이 화면 조작에서 목표 달성 인터페이스로 이동한다는 강한 프레이밍으로 읽어야 한다.

또한 발표가 언급한 Composio와 네이티브 MCP의 비교 결과는 초기·미공개 자료다. 전사에는 과업별 수치, 표본 수, 성공 판정 방식이 없다. 그러므로 “명확한 차이가 있었다”는 화자의 주장까지는 보존할 수 있지만, 우월성이 검증되었다고 단정할 수는 없다.

여기까지만 이해하면 충분

  • MCP는 에이전트가 앱과 통신할 문을 열지만, 필요한 도구 선택과 교차 앱 실행 계획까지 자동으로 해결하지는 않는다.
  • 도구가 많을수록 모든 정의를 모델에 넣는 방식은 오히려 잘못된 선택과 입력 공간 낭비를 만들 수 있다.
  • 에이전트용 인터페이스의 핵심은 목표에 맞는 도구·순서·데이터를 그때그때 좁혀 주는 것이다.
  • “대시보드의 죽음”과 Composio의 성능 우위는 화자의 주장이다. 목업과 미공개 결과를 독립 검증으로 바꾸어 읽으면 안 된다.

오늘 대답할 질문

MCP로 앱을 연결한 뒤에도 에이전트가 교차 앱 작업에 실패하는 이유는 무엇이며, 에이전트용 인터페이스는 무엇을 더 제공해야 하는가?

  • 도구를 많이 제공하는 것이 왜 항상 유리하지 않은가?
  • 사람용 UI와 에이전트용 인터페이스의 평가 기준은 어떻게 다른가?
  • 성능 주장을 실제 시스템에 적용하기 전에 무엇을 측정해야 하는가?

비유와 깨지는 지점

문은 많지만 지도와 기억이 없는 건물

MCP 서버는 각 앱으로 들어가는 문과 같다. 그러나 문이 수천 개 있어도 어느 방에 먼저 들어가야 하는지 알려 주는 지도와 이전 실수를 기억할 방법이 없으면 목적지에 도달하기 어렵다. 에이전트용 인터페이스는 목표에 맞는 방과 이동 순서를 안내하는 안내소에 가깝다.

비유가 깨지는 지점: 실제 MCP와 API는 물리적인 방이 아니다. 권한, 데이터 형식, 도구 정의, 오류 처리와 모델의 입력 제한이 함께 작동한다. 또한 “에이전트는 기억하지 못한다”는 말은 발표에서 설명한 대화 설정에 관한 주장이지 모든 에이전트 시스템이 원리상 기억을 가질 수 없다는 뜻은 아니다.

1. 원인

MCP 서버를 여러 개 연결했는데도 에이전트가 복잡한 작업에서 잘못된 도구를 고르거나 중간에 막힐 수 있는 이유는 무엇인가?

모범 답안 보기

MCP는 통신 통로를 제공하지만 과업별 도구 선택과 호출 순서를 자동으로 정해 주는 완성된 작업 계획은 아니다. 대화가 이전 실패를 기억하지 못할 수 있고, 수많은 도구 정의가 입력 공간을 차지하며, 각 앱은 다른 앱의 구조를 모른다. 따라서 접속 가능성과 과업 완료 능력 사이에 틈이 남는다.

2. 대조

사람용 대시보드에 AI 질의 버튼을 붙이는 것과 에이전트용 인터페이스를 설계하는 것은 무엇이 다른가?

모범 답안 보기

AI 버튼은 주로 현재 화면이나 데이터 소스에서 질의를 만드는 일을 돕는다. 에이전트용 인터페이스는 목표를 받아 필요한 도구를 찾고, 선행 조건과 호출 순서를 계획하며, 여러 앱의 데이터와 작업을 연결해야 한다. 평가 기준도 버튼의 편리함보다 전체 과업을 정확히 끝냈는지에 가깝다.

3. 적용

교차 앱 자동화를 시험한다면, 도구 개수를 늘리기 전에 어떤 기준으로 인터페이스를 비교해야 하는가?

모범 답안 보기

동일한 과업과 동일한 모델을 사용하고, 사람이 중간에 수정하지 않아도 끝까지 완료한 비율을 비교한다. 필요하면 잘못된 도구 선택, 실행 순서 실패, 입력 공간 사용과 같은 실패 원인을 함께 기록한다. 발표의 미공개 벤치마크를 그대로 믿기보다 자신의 권한·데이터·과업 조건에서 재현되는지 확인해야 한다.

1. 연결의 수보다 선택 구조가 중요하다

  • [원문] 화자는 GitHub 도구 모음만 200개가 넘으며, 많은 도구와 스킬 정의를 입력 공간에 넣으면 모델이 잘못된 도구를 고르거나 의존 관계를 풀지 못한다고 말한다.
  • [해석] 에이전트 시스템의 경쟁력은 “몇 개 앱을 연결했는가”보다 “현재 목표에 필요한 도구만 얼마나 잘 좁혀 주는가”에서 생길 수 있다.
  • [경계] 200개 초과는 Composio의 GitHub 도구 모음에 대한 화자의 수치다. 도구 수와 실패율의 정량 관계는 전사에 제시되지 않았다.

2. 맥락을 적게 싣는 것도 실행 능력이다

  • [원문] PostHog에서 찾은 사용자 ID 전체를 모델 입력에 넣지 않고 저장한 뒤, Metabase 구조와 표본을 살피고 외부 작업 도구에서 SQL을 만들었다고 설명한다.
  • [해석] 좋은 에이전트는 모든 데이터를 읽는 시스템이 아니라, 데이터를 외부에 둔 채 필요한 계산과 결과만 가져오는 시스템일 수 있다.
  • [경계] 이 사례의 정확도, 데이터 크기, 비용, 실패 횟수는 제공되지 않았다. 화자가 일상적으로 쓰는 사례라는 진술만 확인할 수 있다.

3. 강한 미래 주장은 검증 상태와 분리해야 한다

  • [원문] 화자는 대시보드가 죽었으며 다음 시대는 에이전트가 사용하기 쉬운 제품의 시대라고 주장한다. Composio가 네이티브 MCP보다 명확한 차이를 보였다는 초기 미공개 결과도 언급한다.
  • [해석] 제품 평가 기준이 화면 사용성에서 에이전트의 과업 완료 능력으로 확장될 가능성을 시험할 가치가 있다.
  • [경계] 첫 번째 버그 해결은 2026년 방식을 상상한 목업이며, 벤치마크는 수치·표본·평가 절차가 없는 미공개 주장이다. META 설명은 “도구 5개와 쿼리 언어 5개”라고 요약하지만, 전사는 Slack·Datadog·PostHog·VS Code·GitHub라는 다섯 도구와 UI를 열거하고 질의 문법 사례로는 Datadog, Jira JQL, Slack 수정자와 서로 다른 SQL을 든다. 따라서 정확히 다섯 개의 질의 언어가 열거·검증되었다고 쓸 수 없다. 또한 META의 provenance.creator는 비어 있지만 설명에는 Sarah Simionescu와 SNS가 있고, 출처가 이름과 SNS를 기준으로 추정되었다고 적혀 있다. 전사에서 확인되는 이름은 Sarah뿐이므로 original_creator는 비워 두었고, Composio 소속도 META의 추정 출처라는 불확실성을 동반한다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 화자는 수많은 도구와 스킬을 한꺼번에 제공하면 에이전트가 오히려 잘못 선택한다고 설명한다.
  • 통찰: 학습자에게 자료를 모두 주는 것과 필요한 순간에 올바른 단서를 제공하는 것은 다르다. 이해는 정보량보다 문제에 맞는 개념을 선택하고 순서를 설명할 수 있는지로 관찰할 수 있다.
  • 질문/행동: 학습자가 자료를 보지 않고 “왜 이 도구를 먼저 쓰는가”를 설명하게 해 본다.

사업가 · 구조적 비유

  • 관련성: 여러 앱의 UI 학습, 수동 전환, 질의 문법 번역은 시간과 오류 위험을 만든다는 것이 발표의 문제 설정이다.
  • 통찰: APOM에 실제로 같은 병목이 있는지는 확인되지 않았다. 다만 교차 시스템 작업이 있다면 연결 개수보다 사람이 개입하지 않고 끝난 과업 비율을 가치 기준으로 삼는 가설은 시험할 수 있다.
  • 질문/행동: 반복 업무 하나를 골라 수동 앱 전환이 어디에서 발생하는지 먼저 기록할 수 있는가?

마케터 · 직접 전이

  • 관련성: “대시보드는 죽었다”는 기억에 남는 주장이고, 6개월 경험·200개 초과 도구·5분 이내 PR이라는 장면과 숫자가 믿음을 강화한다.
  • 통찰: 강한 카피는 관심을 만들지만, 목업·초기 미공개 결과·실제 검증을 구분하지 않으면 증거보다 주장이 앞선다.
  • 질문/행동: 사례를 소개할 때 각 문장에 운영 결과, 데모, 계획, 미래 주장 중 어느 상태인지 표시한다.

AI/SW 학습자 · 직접 전이

  • 관련성: 도구 검색, 호출 계획, 교차 앱 조정, 입력 공간 관리와 과업 완료 평가는 에이전트 아키텍처의 직접적인 설계 문제다.
  • 통찰: 모든 도구를 미리 노출하는 방식과 목표에 따라 도구를 검색하는 방식을 동일 과업으로 비교해야 한다. 정상 실행뿐 아니라 잘못된 도구 선택과 사람의 수정 개입도 실패로 관찰할 수 있다.
  • 질문/행동: 권한이 제한된 시험 환경에서 동일한 교차 앱 과업을 두 인터페이스 방식으로 반복 실행해 본다.

가치 지도

"앱마다 다른 UI·질의 방식과 고립된 도구 때문에 교차 앱 과업이 끊긴다" 문제
→ "목표만 제시하고 필요한 도구와 순서를 안내받아 작업을 완료한다" 수혜자: 에이전트를 사용하는 사람과 개발팀
→ "API 접근 권한, 데이터, 실행 시간과 신뢰를 제공한다" 지불자 또는 자원 제공자: 서비스를 운영하거나 도입하는 조직
→ "사람의 중간 수정 없이 끝까지 완료된 교차 앱 과업 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 권한이 제한된 시험 환경에서 동일한 교차 앱 과업을 네이티브 MCP 도구 묶음과 목표 기반 도구 검색·계획 방식으로 각각 5회 실행한다.
  • 측정 1개: 사람의 중간 수정 없이 완료된 실행 비율
  • 중단 기준 1개: 목표 기반 검색·계획 방식의 무수정 완료율이 네이티브 MCP 방식보다 높지 않으면 확대하지 않는다.

# 섹션 요지
1 대시보드를 쓰지 않은 Datadog 사용자 화자는 6개월 동안 매일 Datadog을 사용했지만 대시보드는 열지 않았다고 말한다.
2 사람용 UI와 질의 언어의 부담 2022년 버그 조사에 다섯 도구와 다섯 UI가 필요했다.
3 AI 버튼과 MCP의 등장 AI 질의 생성에서 에이전트가 직접 실행하는 연결 방식으로 이동했다.
4 MCP 이후에도 남은 세 문제 기억 부재, 도구 과부하, 앱 고립이 교차 앱 작업을 방해한다.
5 에이전트용 인터페이스 데모 도구 검색과 계획, 맥락 절약, 교차 앱 실행을 Composio 사례로 제시한다.
6 제품의 새로운 사용자 화자는 사람뿐 아니라 에이전트가 제품의 사용자가 된다고 주장한다.

1. 대시보드를 열지 않고 Datadog을 사용한 경험

화자는 자신을 Sarah라고 소개한다. 지난 6개월 동안 Datadog을 매일 사용했지만, 동료가 경고를 함께 보자고 했을 때 서비스에서 로그아웃된 상태였고 대시보드의 위치도 파악하지 못했다고 말한다. 이유는 그동안 대시보드를 직접 열어 본 적이 없었기 때문이다.

그는 이를 Datadog에 대한 비판으로 제시하지 않는다. 오히려 “대시보드는 죽었다”는 주장을 설명하기 위한 개인 사례로 사용한다. 자신의 팀이 Composio 대시보드를 담당한다는 점도 덧붙인다.

2. 2022년의 다섯 도구

Slack으로 운영 환경 검색 오류가 접수되면 다음 다섯 창을 열었다고 설명한다.

  1. Slack에서 상황 읽기
  2. Datadog에서 질의 작성
  3. PostHog에서 세션 확인
  4. VS Code에서 버그 수정
  5. GitHub에서 PR 열기

화자는 이를 다섯 도구와 다섯 UI라고 명시한다. 이어 Datadog의 질의 문법, Jira의 JQL 검색, Slack의 검색 수정자와 서비스마다 다른 SQL을 예로 든다. 다만 전사에서는 다섯 개의 질의 언어를 일대일로 열거하지 않는다. Jira는 위의 다섯 도구 목록에도 포함되지 않는다.

화자의 해석에 따르면 대시보드와 질의 언어는 사람의 의도를 데이터 시스템이 받을 요청으로 바꾸는 번역 장치였다. 사용자가 실제로 원한 것은 대시보드가 아니라 답이었다.

3. 2023년 AI 버튼과 2024년 MCP

2023년에는 LLM이 질의를 대신 작성하는 ‘반짝이 버튼’이 등장했다고 설명한다. 화자 표현으로는 질의가 때때로 정확했고, 두 번보다 많은 데이터베이스 조인이 필요하지 않을 때 답을 얻는 데 도움이 되었다.

2024년 11월에는 Anthropic이 MCP를 발표했다고 말한다. MCP는 AI 시스템과 데이터 소스를 연결하는 공개 표준을 약속했다. 사용자가 화면의 AI 버튼을 누르는 대신 Claude 같은 자신의 에이전트가 질의를 만들고 실행해 답을 줄 수 있게 되었다는 설명이다.

하지만 MCP는 프로토콜, 즉 에이전트와 서비스 사이의 통신 채널이다. 서비스가 무엇을 어떤 도구로 노출하고 에이전트와 어떻게 대화할지는 별도의 설계 문제로 남는다.

4. MCP 연결 뒤의 세 가지 문제

화자는 12개 정도의 MCP 서버를 연결해 본 상황을 조건부 사례로 들며 세 문제를 제시한다.

  1. 에이전트가 배우지 않는다: 각 대화가 처음부터 시작되므로 전날 Slack 링크 형식을 잘못 처리한 경험을 다음 날에도 반복할 수 있다.
  2. 도구가 많으면 입력 공간이 넘친다: 스킬로 문제를 보완할 수 있지만 도구와 스킬 정의가 늘수록 입력 공간을 더 사용한다. Composio의 GitHub 도구 모음만 200개가 넘는다고 말한다.
  3. 각 앱이 고립되어 있다: 각각의 MCP 서버는 자기 앱만 알고 다른 앱을 모른다. 과업이 두 앱 이상에 걸치면 연결 책임이 사용자에게 남는다.

화자는 이를 “MCP가 각 앱의 문을 열어 주었지만 에이전트는 지도와 기억 없이 수천 개의 방에 서 있다”는 비유로 정리한다.

5. 2026년 버그 해결 목업

화자는 처음의 버그 신고를 2026년에는 어떻게 해결할지 목업으로 보여 준다고 명시한다. Claude가 Composio MCP에 연결되어 있다고 가정하고, Slack 메시지 링크와 함께 Sentry와 Datadog에서 원인을 찾아 초안 PR을 만들라고 지시한다.

Composio Search가 반환한 세 과업은 다음과 같다.

  1. Slack 메시지 가져오기
  2. Sentry 이슈 검색
  3. Datadog 로그 검색

각 과업에는 필요한 도구뿐 아니라 사용 계획도 포함된다. Slack 메시지를 조회하기 전에 채널 ID를 찾아야 한다는 선행 조건이 예다.

에이전트는 Slack의 사용자 불만을 확인하고, Datadog과 Sentry를 병렬로 조사하며 코드베이스를 살핀다. 화자는 원인을 찾은 뒤 수정 PR이 5분 이내에 만들어졌다고 말한다. 별도의 워크플로나 스킬을 직접 작성하지 않았다고 주장한다. 다만 이 사례는 화자가 목업이라고 밝힌 시연이므로 실제 운영 완료 기록으로 취급할 수 없다.

6. 초기 미공개 비교 결과

화자는 동일한 과업과 동일한 모델을 사용해 Composio와 Claude Marketplace에 등록된 앱별 네이티브 MCP를 비교했으며 명확한 차이를 보았다고 말한다.

그러나 결과는 초기·미공개 상태다. 전사에는 성공률, 비용, 지연 시간, 과업 수, 반복 횟수나 평가 방식이 없다. 따라서 비교가 있었다는 화자의 주장만 보존할 수 있다.

7. Composio가 제안하는 인터페이스

Composio는 에이전트 전용의 새로운 인터페이스를 개발하고 있다고 설명한다. 여러 앱의 복잡하고 문서가 부족하며 계속 변하는 API를 에이전트가 쓰기 쉬운 형태로 번역한다는 주장이다.

MCP, CLI, 네이티브 도구 위에 통합된 경험을 제공해 여러 앱의 복잡한 작업을 끊김 없이 수행하도록 하는 것이 목표다. 이는 완성·검증된 보편 표준이라는 설명이 아니라 Composio가 현재 개발한다고 밝힌 방향이다.

8. PostHog와 Metabase 교차 분석

화자는 자신이 평소 자주 사용하는 더 전형적인 사례를 보여 준다.

먼저 사용자가 온보딩에서 선택한 업종의 분포를 알고 싶다고 Claude에 묻는다. Claude는 Composio Search를 실행하고 PostHog 질의를 작성·실행한다.

다음으로 전자상거래를 선택한 사용자가 어떤 도구 모음을 선호하는지 Metabase 데이터와 연결한다. Claude는 PostHog에서 전자상거래 사용자 ID를 찾고, 전체 결과를 입력 공간에 넣지 않은 채 저장한다.

이후 Metabase에서 데이터베이스 구조를 조회하고 일부 데이터를 표본으로 확인한다. 구조를 파악한 다음 Composio Remote Workbench에서 사용자 ID를 찾기 위한 정규표현식이 포함된 SQL 질의를 동적으로 만든다. 화자는 전체 데이터를 입력 공간에 넣지 않고 두 데이터 소스의 결과를 몇 분 이내에 연결했다고 설명한다.

9. 에이전트라는 새로운 사용자

화자는 많은 스타트업이 GEO를 위해 랜딩 페이지와 웹사이트를 AI 친화적으로 만들기 시작했지만, 에이전트가 실제 애플리케이션을 사용하도록 준비한 경우는 적다고 주장한다.

Composio는 개발자를 돕고 인기 앱을 에이전트가 쓸 도구로 바꾸는 서비스로 시작했다고 말한다. 최근에는 고객이 자신의 에이전트를 통해 서비스를 사용하기 원한다는 스타트업의 요청을 받고 있다고 설명한다.

그는 에이전트를 눈이 없고 AI 버튼을 직접 누르지 않으며, 목표와 도구를 가지고 와서 일을 끝낼 수 있는지만 판단하는 새로운 종류의 사용자라고 표현한다. 지난 10년 동안 사람에게 쉬운 제품을 만들었다면 다음 시대에는 에이전트가 쓰기 쉬운 제품이 중요해질 것이라는 주장으로 발표를 마친다.

안녕하세요, 여러분. 제 이름은 Sarah이고, 고백할 게 하나 있습니다.

저는 지난 6개월 동안 매일 Datadog을 사용해 왔는데, 며칠 전 동료가 제게 다가왔습니다. 동료가 말했죠. “저기, Sarah, 이 알림 좀 봐도 될까요?” 제가 “네”라고 했습니다. 그래서 Datadog을 열었는데 로그아웃되어 있었습니다. 꽤 어색한 상황이라 로그인해야 했죠. 동료가 제 어깨너머로 보고 있었고, 저는 컴퓨터에서 제가 하는 모든 행동을 지나치게 의식하고 있었습니다. Datadog 대시보드를 열었는데, 그대로 얼어붙었습니다. 어디에 뭐가 있는지 전혀 모르겠더라고요.

이건 사실 Datadog을 비난하는 말이 아닙니다. 문제는 제가 정말로 대시보드를 한 번도 열어 본 적이 없었다는 겁니다. 매일 사용하면서도 대시보드를 본 적은 한 번도 없었습니다. 오늘 저는 다소 터무니없게 들리는 주장을 펼친 다음, 사실은 너무나 명백한 이야기라는 걸 보여드리려고 합니다.

대시보드는 죽었습니다. 그리고 저는 이것이 이 자리에 있는 모든 분에게 좋은 소식이라고 생각합니다. 다만 아마 저에게는 별로 좋은 소식이 아닐 겁니다. 제 팀이 Composio 대시보드를 담당하고 있으니까요. 어쨌든, 우리는 어떻게 여기까지 오게 됐을까요? 사후 분석(postmortem)이 필요할 것 같습니다. 시작해 볼까요?

때는 2022년입니다. 암흑시대입니다. 누군가 Slack으로 저에게 메시지를 보냅니다. “저기, prod를 검색하려고 하면 이런 오류가 나요.”

저라면 즉시 창을 다섯 개 띄웠을 겁니다. Slack에서 맥락을 읽고, Datadog에서 쿼리를 작성하고, PostHog에서 세션을 확인하고, VS Code에서 버그를 수정하고, GitHub에서 PR을 여는 식이죠. 도구 다섯 개와 UI 다섯 개를 배워야 하고, 각 도구가 새롭게 디자인될 때마다 다시 배워야 합니다.

솔직히 말해 리디자인은 제 문제 중 가장 작은 문제입니다. 모든 도구가 각자의 쿼리 언어를 사용하기 때문입니다. Datadog에는 자체 쿼리 문법이 있고, Jira에는 JQL 검색이 있으며, Slack에는 자체 검색 수식어가 있습니다. 더 심각한 점은 이 도구들이 같은 언어, 가령 SQL을 사용한다고 주장할 때조차 SQL에 대해 서로 합의하지 않는다는 겁니다.

여러분이 사용해 본 모든 대시보드와 지금까지 만들어진 모든 기묘하고 난해한 쿼리 언어는 여러분과 데이터 사이의 번역 장치였습니다. 반대편에 있는 기계가 여러분이 실제로 원한 것을 이해하지 못하기 때문이죠. 여러분이 원한 건 대시보드나 그 저주받은 쿼리 언어가 아니었습니다. 여러분이 원한 건 답이었습니다.

2023년에 모든 것이 바뀌었습니다. 스파클 버튼(Sparkle button)이 탄생했고, 이 마법 같은 버튼을 클릭하면 LLM이 여러분에게 필요한 답을 얻기 위한 쿼리를, 가끔은 맞게, 작성해 주었습니다. 질문에 데이터베이스 조인이 두 개 넘게 필요하지 않다면 말이죠.

얼마 지나지 않아 이런 스파클 버튼은 어디에나 등장했습니다. 대시보드는 AI 네이티브가 됐습니다. 이제 문제가 해결된 걸까요?

그렇지만 완전히 그렇지는 않았습니다. 2024년 11월, Anthropic은 AI 시스템과 데이터 소스를 연결하기 위한 개방형 표준을 만들겠다는 약속과 함께 MCP 프로토콜을 발표했고, 실제로 그렇게 했습니다. 스파클 버튼을 사용하는 대신, 여러분이 이미 매일 사용하고 있는 자신의 에이전트인 Claude가 여러분을 대신해 쿼리를 생성하고 실행한 뒤 답을 직접 제공할 수 있게 된 겁니다.

이렇게 생각할 수도 있습니다. 문제가 해결됐지? 이야기는 여기서 끝이야.

하지만 전혀 그렇지 않습니다. MCP는 프로토콜입니다. 에이전트와 여러분의 서비스 사이에서 통신하는 채널일 뿐이고, 에이전트와 어떻게 통신할지는 여러분, 즉 서비스가 선택해야 합니다. 그리고 이것이 모든 차이를 만들어 낸다는 사실이 드러났습니다.

MCP 서버를 실제로 열두 개 연결해 본 적이 있다면, 현실이 세 가지 이유로 엉망이라는 걸 알 겁니다.

에이전트는 학습하지 않습니다. 모든 대화는 처음부터 시작합니다. 어제 Slack에서 링크 형식을 제대로 지정하지 못해 헤맸던 일을 기억하지 못하므로, 오늘도 똑같이 헤맬 겁니다.

우리는 이를 스킬(skills)로 보완하지만, 스킬은 반창고일 뿐입니다. 더 많은 컨텍스트를 제공할수록 에이전트는 더 멍청해지기 때문입니다. 도구와 스킬을 더 많이 불러오면 더 많은 컨텍스트가 필요합니다. 서버를 충분히 연결하면 수천 개의 도구 정의가 컨텍스트 창(context window)에 그대로 쏟아져 들어갑니다. GitHub 툴킷만 해도 도구가 200개가 넘습니다. 모델은 그냥 압도당합니다. 잘못된 도구를 선택하거나 의존성을 해결하는 데 어려움을 겪고, 어떤 도구를 먼저 호출해야 하는지도 알아내지 못합니다.

셋째, 모든 앱은 고립되어 있습니다. 각 MCP 서버는 자기 자신에 대해서만 알고 다른 것은 아무것도 모릅니다. 작업이 두 앱에 걸치는 순간, 사실 모든 작업이 그렇지만, 그 둘을 연결하는 것은 여러분의 몫입니다.

MCP는 에이전트에게 모든 앱으로 들어가는 문을 열어 주었지만, 지도도 없고 그곳에 와 본 기억도 없는 채 수천 개의 পৃথ পৃথक한 방에 세워 두었습니다.

이제 처음부터 이 버그 리포트를 어떻게 해결할지, 즉 2026년에 제가 어떻게 해결할지에 대한 목업 데모를 보여드리겠습니다.

이 목업에서 제 Claude가 Composio MCP에 연결되어 있다고 상상해 보세요. 저는 Slack 메시지 링크를 그대로 복사해 붙여 넣고 이렇게 말할 겁니다. “Sentry와 Datadog을 사용해서 근본 원인을 찾고 초안 PR을 만들어 주세요. 실수는 절대 하지 마세요.”

가장 먼저 Claude는 Composio Search를 호출해 자신이 수행하려는 작업을 명시합니다. 이 경우에는 세 가지 작업을 명시했습니다. Slack 메시지 가져오기, Sentry 이슈 검색, Datadog 로그 검색입니다.

이 세 가지 각각에 대해 Composio는 필요한 정확한 도구뿐만 아니라 도구 사용 방법에 대한 계획도 반환합니다. 예를 들어 Slack의 경우 메시지 검색을 시작하기 전에 Slack 채널 ID를 찾아야 합니다.

이제 필요한 모든 컨텍스트를 갖추고 계획도 세웠습니다. 먼저 Slack에서 메시지를 가져와 사용자의 불만이 무엇이었는지 확인합니다. 그런 다음 Datadog과 Sentry에서 병렬로 데이터를 가져오는 동시에 코드베이스를 검사하기 시작합니다.

근본 원인을 파악하면 5분도 안 되어 수정 사항이 반영된 PR이 올라옵니다. 저는 워크플로를 만들거나 이 작업을 수행하는 방법을 가르치는 스킬을 작성할 필요가 없었습니다. 말 그대로 Claude가 Composio의 MCP를 사용한 것뿐이고, 이런 방식으로 일을 처리하는 것이 훨씬 쉬워져서 무언가 해야 할 때 Claude를 여는 일이 제게는 근육 기억처럼 되어 버렸습니다. 예전에 매일 열던 대시보드가 점점 낯설어지고 있습니다.

에이전트를 위해 설계했을 때의 영향은 측정할 수 있습니다. 이것은 아직 공개되지 않은 초기 결과 중 일부로, Claude Marketplace에 등록된 각 앱의 자체 네이티브 MCP와 Composio를 비교한 것입니다. 같은 작업과 같은 모델을 사용했는데, 분명한 차이가 나타납니다.

왜 이 경험이 네이티브 MCP보다 훨씬 나을까요?

Composio에서는 에이전트를 위해 특별히 설계된 완전히 새로운 인터페이스를 개발하고 있습니다. 여러분이 매일 사용하는 모든 앱의 엉성하고 문서화가 부족하며 끊임없이 변하는 API를 에이전트가 정말 사용하고 싶어 하는 형태로 변환합니다.

MCP, CLI, 네이티브 도구 위에 구축해, 에이전트가 이러한 앱 전반에서 복잡한 작업을 원활하게 수행할 수 있도록 일관되고 통합된 뛰어난 경험을 제공합니다.

제가 평소 매일 사용하는 좀 더 전형적인 사례를 보여드리겠습니다.

사용자 데이터에 대해 자세히 살펴보고 싶다고 해 보죠. 온보딩 과정에서 사용자들이 어떤 버티컬(vertical)을 선택하는지 그 분포를 보고 싶습니다. Claude에게 간단히 요청하면 됩니다. Claude는 다시 Composio Search를 실행하고, PostHog에서 쿼리를 작성한 뒤 실행합니다. 간단하죠. 결과가 나왔습니다.

그런데 한 단계 더 나아가고 싶다면 어떨까요? 바로 저기 있는 이커머스 섹션을 살펴보고, 그 사용자들이 어떤 툴킷(toolkits)을 사용하고 싶어 하는지 보고 싶습니다. 툴킷은 Composio에서 사용하는 앱을 가리키는 또 다른 표현입니다.

PostHog의 사용자 ID를 바탕으로 Metabase에서 이 데이터를 가져오는 방법을 Claude가 알아낼 수 있는지 보겠습니다. 이번에도 Composio Search를 사용합니다. PostHog에서 이커머스를 선택한 사용자들의 ID를 쿼리하고, 전체 결과를 컨텍스트에 불러오지 않은 채 실제로 그 ID를 저장합니다.

그런 다음 Metabase에서 데이터베이스 스키마를 확인하고, 일부 데이터를 샘플링하며, 구조가 어떻게 되어 있는지 파악하기 위해 몇 가지 쿼리를 실행합니다. 확신이 들면 Composio Remote Workbench라는 아주 멋진 도구를 사용해 정규식 문자열(regex string)이 포함된 SQL 쿼리를 동적으로 생성하고, 이 모든 사용자 ID를 검색합니다. 이번에도 전체 데이터를 컨텍스트 창에 불러오지 않습니다.

됐습니다. 몇 분도 안 되어 이 사용자 페르소나에서 가장 인기 있는 툴킷을 확인할 수 있고, 두 소스에서 가져온 데이터라는 것도 알 수 있습니다. 라이브 버전을 사용해 보고 싶다면 Composio 부스로 찾아오세요. 직접 사용해 보실 수 있도록 도와드리고 싶습니다.

대시보드는 죽었고, 저는 이것이 미래에 무엇을 의미하는지 점점 더 많이 생각하고 있습니다. 많은 스타트업이 GEO를 위해 랜딩 페이지와 웹사이트를 AI 친화적으로 만들기 시작했지만, 에이전트가 사용할 수 있도록 애플리케이션을 제대로 준비한 곳은 극히 적습니다.

Composio는 개발자를 돕는 도구로 시작했습니다. 사용자들이 좋아하는 인기 앱을 가져와 에이전트가 사용할 수 있는 도구로 바꾸고 있었습니다. 하지만 사람들은 대시보드에 지쳤고, 에이전트는 형편없이 설계된 MCP 서버에 지쳤습니다. 이제 스타트업들로부터, 고객들이 에이전트를 통해 서비스를 사용할 방법을 간절히 원한다는 요청을 받고 있습니다.
