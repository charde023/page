AI 에이전트를 위한 만능 리모컨, ACP를 소개합니다

업로드 2026-09-12 · 10.5분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

무슨 이야기인가

AI 에이전트가 파일을 읽거나 외부 도구를 실행하려면, 가운데에서 모델과 도구 호출을 이어 주는 프로그램이 필요하다. 화자는 이 프로그램을 에이전트 하네스(agent harness)라고 부른다. Goose가 그 사례다. 사용자가 실제로 만지는 편집기·터미널·데스크톱 앱 같은 프로그램은 클라이언트(client)다.

문제는 하네스마다 클라이언트와 대화하는 방식이 제각각일 수 있다는 점이다. 어떤 하네스가 특정 앱 한 개에서만 제대로 작동한다면, 새 클라이언트를 만들 때마다 전용 연결 방식을 다시 구현해야 한다. 화자는 이를 웹사이트마다 지정된 브라우저만 써야 하는 상황에 비유한다.

ACP(Agent Client Protocol)는 이 연결을 공통 규칙으로 만들려는 개방형 프로토콜이다. 쉬운 말로 하면, 클라이언트가 여러 에이전트 하네스에 작업을 전달하고 진행 상황을 받는 데 사용할 수 있는 공통 리모컨 규격이다.

읽는 법: 왼쪽에서 사용자가 만지는 앱을 찾고, 가운데 하네스가 무엇을 조정하는지 본다. ACP는 왼쪽 경계, MCP는 오른쪽 위 경계다. 이 그림은 화자가 제시한 개념 구조이지, 모든 제품에서 이미 호환성이 검증됐다는 배치도는 아니다.

ACP와 MCP는 무엇이 다른가

MCP(Model Context Protocol)는 에이전트가 바깥으로 나가 도구를 호출하고, 다른 시스템에서 행동하거나 자료를 읽도록 돕는 표준이다. 반면 ACP는 클라이언트가 에이전트 하네스에 할 일을 주고 결과와 진행 상황을 받도록 하는 규칙이다.

둘은 경쟁 관계라기보다 서로 다른 연결 구간을 맡는다. ACP로 전달받은 작업을 하네스가 수행하면서 MCP 도구를 호출할 수 있다.

읽는 법: 먼저 ‘연결 경계’ 행을 보면 둘의 차이를 가장 빠르게 이해할 수 있다. 나머지 행은 그 경계에서 오가는 정보와 기대 효과를 보여준다. 화자는 MCP 서버가 “수천 또는 수만” 개라고 말하지만 정확한 집계와 시점은 제시하지 않았다.

ACP는 어떻게 작동하는가

ACP 연결에는 서로 지원하는 기능 정보가 붙는다. 연결한 뒤에는 세션(session)을 만들고, 그 안에서 사용자 메시지를 보낸다. 에이전트는 텍스트뿐 아니라 이미지·오디오, 작업 진행 상황, 도구 호출 정보 등을 돌려줄 수 있다.

위험하거나 확인이 필요한 도구 호출이 있다면 하네스가 권한 요청을 보내고, 클라이언트는 사용자에게 실행 여부를 물을 수 있다. 메시지 형식에는 JSON-RPC를 사용한다. 기본 규격에 없는 기능이 필요하면 이름 앞에 밑줄을 붙이는 관례로 사용자 정의 메서드를 추가할 수 있다고 화자는 설명한다.

읽는 법: 위쪽은 한 세션이 진행되는 순서다. 아래 점선 상자는 모든 단계에서 사용하는 메시지 규칙과 확장 방법을 뜻한다. 사용자 정의 메서드가 생겼다고 바로 공식 표준이 되는 것은 아니다. 여러 구현에서 반복되는 기능을 관찰한 뒤 표준화할 수 있다는 방향이다.

데모가 실제로 보여준 범위

첫 번째 로컬 데모에서 화자는 Zed에 있는 단일 HTML 파일 프로젝트를 열고 Goose에게 “이 프로젝트에 대해 알려 달라”고 요청했다. Goose는 텍스트와 도구 호출 정보를 돌려주고, 파일 하나로 된 프로젝트라고 설명했다.

두 번째로는 Poolside AI에서 나온 터미널 기반 클라이언트를 사용했다. 같은 프로젝트와 같은 Goose 에이전트에 같은 종류의 질문을 보내고, 텍스트·도구 호출·스트리밍 요약을 받았다. 이는 서로 다른 두 클라이언트가 같은 하네스 측 ACP 구현을 로컬 표준 입출력으로 사용한 사례다. 다만 두 번째 클라이언트의 제품명은 전사에 나오지 않는다.

원격 연결도 다룬다. 화자 팀이 프로젝트를 살펴봤을 때는 원격 지원이 아직 없어서 HTTP 전송 방식과 WebSocket 업그레이드를 규정했다고 한다. 새 전송 계층은 발표 시점에 “막 들어오고 있는 중”이라고 표현된다. 원격 데모에서는 화자가 전날 만든 클라이언트로 “시를 써 달라”고 요청했지만, 네트워크를 사용했어도 클라이언트와 실행 프로세스는 같은 기기에 있었다. 컨테이너나 클라우드는 가능한 배치 예시로 제시됐을 뿐, 그 데모에서 직접 검증된 것은 아니다.

왜 중요하다고 보는가

화자는 클라이언트, 하네스, 도구, 모델이라는 네 요소가 표준 전송 방식을 가지면 각각의 위치를 더 자유롭게 바꿀 수 있다고 본다. 모두 한 기기에서 실행하거나, 하네스만 다른 기기로 옮기거나, 모델이나 도구만 원격에 둘 수 있다는 주장이다.

또한 편집기·데스크톱·모바일·터미널 등 다양한 클라이언트가 같은 하네스와 연결되면 사용자가 자신에게 맞는 화면과 사용 방식을 선택할 수 있다고 기대한다. 개인용, 특정 업무 분야용, 회사용, 화이트라벨 클라이언트도 가능성으로 언급한다. 선택지가 늘어나면 클라이언트가 사용자 경험으로 경쟁하고 전체 AI 사용 경험이 좋아질 것이라는 전망이다.

그러나 “만능 리모컨”은 현재 모든 에이전트에 자동으로 통하는 완성 상태를 뜻하지 않는다. 클라이언트와 하네스가 ACP를 실제로 채택해야 하며, 발표에서 직접 보여준 상호운용 사례는 로컬의 두 클라이언트와 같은 기기에서 수행한 네트워크 데모다. 원격 전송의 성숙도, 구현 간 호환성, 권한 처리의 일관성은 별도 검증이 필요하다.

여기까지만 이해하면 충분

  • ACP는 클라이언트가 에이전트 하네스에 작업을 주고 결과·상태·권한 요청을 받는 연결 규칙이다.
  • MCP는 에이전트와 외부 도구 사이, ACP는 클라이언트와 하네스 사이를 표준화한다.
  • 발표는 두 클라이언트가 같은 Goose 하네스를 로컬에서 제어하는 사례를 보여줬지만 모든 구현의 호환성을 증명하지는 않았다.
  • 원격 배치와 UX 경쟁은 가능한 방향이며, 실제 채택과 전송 계층의 성숙도가 전제다.

비유와 깨지는 지점

여러 기기를 조작하는 공통 리모컨

클라이언트는 사용자가 누르는 리모컨이고, 하네스는 명령을 받아 에이전트의 작업을 조정하는 기기 쪽 제어부다. ACP는 버튼을 눌렀을 때 어떤 메시지를 보내고 어떤 상태를 돌려줄지 정한 공통 신호 규격에 해당한다.

비유가 깨지는 지점: 실제 ACP는 단방향 버튼 명령만 보내지 않는다. 세션을 만들고, 텍스트·이미지·오디오·도구 호출 정보를 받으며, 권한 요청도 처리한다. 무엇보다 클라이언트와 하네스 양쪽이 ACP를 지원해야 하므로 규격이 존재한다고 모든 에이전트가 즉시 제어되는 것은 아니다.

1. 원인

하네스마다 전용 인터페이스가 있으면 왜 에이전트 클라이언트 생태계가 커지기 어려운가?

모범 답안 보기

새 클라이언트가 각 하네스의 전용 연결 방식을 따로 구현해야 하기 때문이다. 반대로 하네스도 여러 클라이언트에 맞춘 연결을 각각 유지해야 한다. 공통 경계가 없으면 구현과 유지 비용이 반복되고, 사용자는 특정 하네스와 묶인 클라이언트만 선택하게 될 수 있다.

2. 대조

ACP와 MCP는 각각 어느 경계를 표준화하며, 왜 서로 대체 관계가 아닌가?

모범 답안 보기

ACP는 클라이언트가 하네스에 작업을 전달하고 결과·상태·권한 요청을 주고받는 경계를 맡는다. MCP는 하네스나 에이전트가 외부 도구와 자료에 접근하는 경계를 맡는다. ACP로 받은 작업을 수행하는 과정에서 MCP 도구를 호출할 수 있으므로 두 규격은 서로 다른 층을 보완한다.

3. 적용

새 에이전트 시스템에 ACP를 도입할지 판단하려면 무엇을 먼저 확인해야 하는가?

모범 답안 보기

먼저 여러 클라이언트 또는 여러 하네스를 연결해야 하는 실제 필요가 있는지 확인한다. 그다음 후보 구현이 필요한 세션, 스트리밍 업데이트, 도구 호출 알림, 권한 요청을 지원하는지 작은 과업으로 시험한다. 로컬 성공과 원격 성공을 구분하고, 같은 과업이 서로 다른 클라이언트에서 끝까지 수행되는지를 증거로 삼는다. “표준”이라는 이름만으로 도입 가치를 확정하지 않는다.

이번 글의 통찰

1. 표준의 핵심은 기능 수보다 연결 경계를 합의하는 데 있다

  • [원문] 화자는 MCP가 에이전트에서 도구로 나가는 경계를 표준화했지만, 클라이언트가 하네스에 작업을 주고 업데이트를 받는 경계에는 좋은 표준이 아직 없다고 주장한다.
  • [해석] 에이전트 전체를 하나의 제품으로 묶기보다 클라이언트·하네스·도구·모델의 경계를 나누면 각 부분을 교체하고 비교할 가능성이 커진다.
  • [경계] 네 구성 요소라는 열거는 실제 네 항목과 일치한다. 다만 자유로운 분산 배치는 화자의 설계 전망이며, 모든 조합의 성능·보안·호환성이 검증됐다는 뜻은 아니다.

2. 확장 기능은 사용 흔적이 표준을 이끌게 하는 장치다

  • [원문] ACP는 JSON-RPC 메시지를 사용하며, 밑줄로 시작하는 사용자 정의 메서드를 추가할 수 있다. 화자는 Codex·Goose·Cline 같은 팀에서 반복되는 기능을 관찰해 표준 후보로 올릴 수 있다고 설명한다.
  • [해석] 처음부터 모든 기능을 규격에 넣기보다 실제 구현에서 반복되는 필요를 수집하면, 프로토콜을 작게 유지하면서도 사용에 따라 발전시킬 수 있다.
  • [경계] 사용자 정의 메서드가 많아지면 구현별 차이가 다시 커질 수도 있다. 어떤 메서드가 실제로 공통 표준이 됐는지, 채택 절차가 무엇인지는 전사에서 확인되지 않는다.

3. 데모가 보여준 사실과 생태계 전망을 분리해야 한다

  • [원문] 로컬 데모는 Zed와 Poolside AI에서 나온 터미널 기반 클라이언트가 같은 Goose 하네스와 통신하는 모습을 보여준다. 원격 데모는 네트워크를 사용했지만 같은 기기에서 실행됐고, HTTP·WebSocket 전송은 발표 시점에 막 도입되는 상태로 표현된다.
  • [해석] 두 클라이언트의 상호운용은 초기 가능성을 보여주는 증거지만, 클라우드 배치와 폭넓은 제품 호환성은 다음 검증 단계다.
  • [경계] “두 클라이언트”라는 수량과 Zed·터미널 클라이언트의 열거는 일치하지만 두 번째 제품명은 전사에 없다. “수천 또는 수만 개의 MCP 서버”는 화자의 비정확한 범위 주장이고 독립 집계가 없다. 숫자·열거에서 직접적인 개수 모순은 발견되지 않았지만, 원작 영상 링크와 프로토콜의 발표 이후 상태는 제공 자료로 확인할 수 없다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: ACP는 서로 다른 화면이 같은 하네스와 대화하도록 공통 메시지 구조를 제공한다.
  • 통찰: 학습자의 이해도 한 가지 화면이나 답안 형식에 묶지 않고, 같은 개념을 말·글·새 사례로 설명할 수 있는지 확인하는 구조와 닮았다. 다만 사람의 사고를 프로토콜처럼 완전히 규격화할 수는 없다.
  • 질문/행동: 같은 개념을 두 형식으로 설명하게 했을 때 원인과 경계가 모두 유지되는지 확인한다.

사업가 · 영감

  • 관련성: 화자는 전용 연결의 반복을 줄이고 클라이언트와 하네스를 독립적으로 선택할 수 있는 시장을 기대한다.
  • 통찰: APOM에 직접 적용됐다는 근거는 없다. 다만 여러 도구가 특정 인터페이스에 묶여 교체 비용을 만드는 후보 업무가 있다면, 공통 연결 경계의 가치가 있는지 검증할 수 있다.
  • 질문/행동: 한 후보 업무에서 화면을 바꿔도 같은 실행부를 유지해야 할 실제 이유와 절감되는 연결 작업이 있는지 먼저 묻는다.

마케터 · 구조적 비유

  • 관련성: “만능 리모컨”이라는 표현은 복잡한 프로토콜을 쉽게 이해시키지만, 직접 증거는 두 로컬 클라이언트와 같은 기기의 네트워크 데모다.
  • 통찰: 강한 비유를 사용할수록 검증된 범위와 미래 가능성을 나란히 표시해야 신뢰를 지킬 수 있다.
  • 질문/행동: ACP를 소개하는 카피를 쓴다면 “모든 에이전트”라고 단정하지 말고, 어떤 클라이언트·하네스 조합에서 무엇을 확인했는지 붙인다.

AI/SW 학습자 · 직접 전이

  • 관련성: 영상은 클라이언트·하네스·도구·모델을 나누고, ACP·MCP·모델 원격 연결로 각 경계를 다루는 구조를 제시한다.
  • 통찰: 기술 이름보다 작업 흐름과 병목을 기준으로 경계를 정한 뒤, 로컬과 원격에서 세션·스트리밍·도구 알림·권한 요청이 같은 의미로 유지되는지 측정해야 한다.
  • 질문/행동: ACP 지원 후보를 샌드박스에서 연결해 같은 과업이 두 클라이언트에서 동일한 필수 이벤트를 거쳐 완료되는지 시험한다.

가치 지도

"하네스마다 전용 클라이언트 연결을 구현하고 유지해야 한다" 문제
→ "같은 하네스를 원하는 화면과 사용 방식으로 제어할 선택권" 수혜자: 사용자·클라이언트 개발자·하네스 개발자
→ "구현 시간·유지보수 코드·상호운용에 대한 신뢰를 제공" 지불자 또는 자원 제공자: 프로토콜 구현자와 채택 조직
→ "같은 과업을 서로 다른 클라이언트에서 성공적으로 완료한 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 가상 샌드박스에서 ACP를 지원한다고 표시된 하네스 하나에 서로 다른 두 클라이언트를 연결하고, 같은 단일 파일 프로젝트 설명 과업을 각각 실행한다.
  • 측정 1개: 필수 결과와 도구 호출 정보까지 받은 성공 클라이언트 수를 성공 수/2로 기록한다.
  • 중단 기준 1개: 성공 클라이언트 수가 2/2보다 적으면 적용 범위를 확대하지 않고 연결·기능 차이부터 확인한다.

# 섹션 요지
1 화자와 프로젝트 배경 Alex Hancock은 Block 소프트웨어 엔지니어이며 Goose와 MCP Rust SDK, ACP 작업을 소개한다.
2 전용 인터페이스 문제 하네스마다 다른 클라이언트 연결 방식이 생태계 형성을 막는다고 주장한다.
3 ACP의 설계 연결 기능, 세션, 메시지, 업데이트, 권한 요청과 사용자 정의 메서드를 다룬다.
4 로컬·원격 데모 두 클라이언트의 로컬 연결과 같은 기기에서 수행한 네트워크 연결을 보여준다.
5 네 구성 요소와 전망 클라이언트·하네스·도구·모델을 독립 배치하고 UX 경쟁을 촉진할 가능성을 제시한다.
6 대조 및 경계 수량·고유명사·시행 상태와 출처 불확실성을 구분한다.

1. 화자와 프로젝트 배경

화자는 자신을 Alex Hancock이라고 소개한다. Block의 소프트웨어 엔지니어이며, Block을 Cash App·Square·Tidal의 모회사라고 설명한다. 과거 Square와 Cash App 제품 업무를 했고 최근 몇 년은 오픈소스 AI에 참여했다고 말한다.

그는 Block 내부 프로젝트로 시작한 오픈소스 하네스 Goose에서 일한다. Goose는 오픈소스로 공개된 뒤 Linux Foundation에 기증됐으며, 지식재산권은 그곳에 있지만 Block 구성원 다수가 계속 참여한다고 설명한다.

또한 MCP의 Model Context Protocol Rust SDK 메인테이너이며, 최근에는 ACP 작업도 시작했다고 말한다.

2. 하네스마다 다른 인터페이스

화자는 연구소, 기업, 개방형 표준 진영에서 여러 하네스가 나오고 있지만 인터페이스가 맞춤형인 경우가 많다고 지적한다. 심하면 한 하네스를 제어할 수 있는 클라이언트 앱이 하나뿐일 수 있다고 말한다.

웹사이트마다 지정된 브라우저나 별도 프로토콜이 필요하다면 열린 웹이 만들어지기 어렵다는 비유를 사용한다. 같은 관점에서 에이전트 하네스와 클라이언트 사이에도 공통 표준이 필요하다고 주장한다.

MCP의 강점은 규격 자체보다 많은 사람이 같은 규격을 사용한다는 데 있다고 평가한다. MCP 서버가 세계에 “수천 또는 수만 개” 있다고 말하지만 정확한 수와 집계 근거는 제시하지 않는다.

3. ACP의 탄생과 설계

화자에 따르면 ACP는 Zed와 JetBrains 팀이 함께 제안했다. Zed나 IntelliJ 같은 편집기에서 고품질 클라이언트 하나를 구현한 뒤, 그 구현으로 여러 하네스에 작업을 보내고 결과와 파일 편집 상태를 확인하려는 목적이었다.

Goose 팀은 ACP가 편집기에만 한정되지 않는다고 봤다. 편집기 전용 기능이 많지 않아 더 넓은 클라이언트 소프트웨어에 적용할 수 있다고 판단했다.

ACP가 다루는 항목은 다음과 같다.

  • 클라이언트와 하네스의 연결 및 기능 정보
  • 세션 생성
  • 사용자 메시지 전달
  • 텍스트·이미지·오디오 응답
  • 진행 상황 업데이트
  • 도구 호출 및 관련 메타데이터 알림
  • 사용자에게 보여 줄 권한 요청
  • JSON-RPC 메시지
  • 밑줄로 시작하는 사용자 정의 메서드

화자는 Codex·Goose·Cline 등 여러 구현에서 비슷한 사용자 정의 메서드가 반복되면, 이를 표준화 절차에 올려 기본 프로토콜에 포함할 수 있다고 기대한다.

4. 두 클라이언트의 로컬 데모

첫 번째 데모는 Zed에서 수행된다. 단일 HTML 파일이 있는 프로젝트에서 “이 프로젝트에 대해 알려 달라”고 요청한다. Goose의 ACP 인터페이스를 통해 텍스트와 도구 호출 정보가 표시되고, 에이전트는 프로젝트가 HTML 파일 하나로 구성됐다고 설명한다.

두 번째 데모는 Poolside AI에서 나온 터미널 기반 클라이언트를 사용한다. 같은 프로젝트와 같은 Goose 에이전트에 요청하며 텍스트 결과, 도구 호출, 스트리밍 요약을 보여준다.

화자는 이를 하나의 하네스 측 구현으로 서로 다른 두 클라이언트를 사용할 수 있는 사례라고 설명한다. 두 연결 모두 이 시점에는 로컬 표준 입출력을 사용한다.

5. 원격 전송과 네 구성 요소

화자 팀이 ACP 프로젝트를 처음 살폈을 때는 원격 지원이 아직 없었다고 말한다. 이후 HTTP 전송과 WebSocket 업그레이드를 규정했으며, 메시지와 프로토콜 의미는 같고 전송 방식만 추가됐다고 설명한다. 이 전송 계층은 발표 당시 “막 들어오고 있는 중”이었다.

원격 데모에 사용한 클라이언트는 화자가 전날 빠르게 만들었다고 말한다. “시를 써 달라”는 요청을 네트워크로 Goose에 보냈지만, 실행 위치는 같은 기기였다. 컨테이너나 클라우드에서도 가능하다는 설명은 배치 가능성에 대한 주장이다.

Goose 팀이 보는 에이전트 스택의 네 구성 요소는 다음과 같다.

  1. 사용자가 쓰거나 헤드리스로 실행되는 클라이언트
  2. 도구 호출 루프를 구현하는 하네스
  3. 흔히 MCP로 연결되는 도구
  4. 모델

화자는 ACP의 원격 전송, MCP의 원격 도구 전송, 모델의 원격 엔드포인트를 조합하면 네 요소를 같은 기기나 서로 다른 위치에 배치할 수 있다고 주장한다.

6. 생태계와 UX에 대한 전망

화자는 편집기·데스크톱·모바일·터미널 기반 클라이언트와 에이전트 서버가 이미 나오고 있다고 말한다. 개인 취향에 맞춘 클라이언트, 특정 사업 분야나 기업을 위한 클라이언트, 화이트라벨 클라이언트 가능성도 제시한다.

클라이언트 선택지가 많아지면 사용자가 품질이 낮은 제품을 떠날 수 있고, 제작자는 사용자 경험으로 경쟁하게 된다고 예상한다. 그 결과 AI 전반의 사용 경험이 좋아질 것이라는 전망이다.

이는 발표자의 기대이며, 시장 형성이나 UX 개선이 이미 측정됐다는 보고는 아니다.

제 이름은 Alex Hancock입니다. 오늘은 AI를 위한 만능 리모컨(universal remote control)에 대해 이야기하겠습니다.

시작하기 전에 한 가지만 말씀드리겠습니다. 앞선 발표자께서 MCP 클라이언트 유지 관리자들이 똑똑하기 때문에 tasks 지원을 구현하지 않았다고 하셨는데요. 저는 MCP 클라이언트 유지 관리자입니다. 그냥 제가 게을러서 안 했다고 말씀드릴 수 있습니다. 아직 구현하지 않았습니다.

시작하기 전에 제 소개를 조금 하겠습니다. 저는 Cash App, Square, Tidal의 모회사인 Block에서 소프트웨어 엔지니어로 일하고 있습니다. 지금은 여러 가지 일을 하고 있고, Block에서 오랫동안 일해 왔습니다. Square 제품 관련 업무와 Cash App 관련 업무를 했지만, 지난 몇 년 동안은 오픈 소스 AI 작업을 해 왔습니다.

구체적으로는 Goose라는 오픈 소스 하네스(harness) 프로젝트를 작업하고 있습니다. 이 프로젝트는 Block의 내부 프로젝트로 시작했습니다. 여기에도 Goose 팬이 계시네요. 저희는 Goose를 오픈 소스로 공개하고 Linux Foundation에 기부했습니다. 이제 지식재산권(IP)은 그곳에 있지만, Block 출신인 저희 중 많은 사람은 여전히 이 프로젝트를 작업하고 있습니다.

저는 MCP, 즉 Model Context Protocol의 유지 관리자이기도 합니다. 이 프로젝트의 Rust SDK를 작업하고 있습니다. 더 최근에는 ACP, 즉 Agent Client Protocol 작업도 시작했는데, 오늘 이야기할 주제가 바로 이것입니다.

오늘 여러분께 하네스와 관련해 우리가 가진 문제를 하나 제기하고, 해결책을 제안하고자 합니다.

최근 제가 발견한 것은 훌륭한 하네스가 아주 많다는 점입니다. 연구소에서 만든 것도 있고, 여러 회사에서 만든 것도 있으며, 개방형 표준을 기반으로 한 오픈 소스 하네스도 많습니다. 하지만 이들의 인터페이스는 대개 맞춤형이거나 독자적입니다.

최악의 경우에는 하네스를 제어할 수 있는 클라이언트 애플리케이션이 말 그대로 하나뿐인 경우도 있습니다. 저는 이것이 몇 가지 문제를 일으킨다고 생각합니다.

웹에 비유하자면, 모든 웹사이트에 연결하려면 브라우저 하나나 특정 프로토콜 하나를 사용해야 하는 것과 같습니다. 그렇게는 작동하지 않을 겁니다. 브라우저가 실제로 그랬다면 지금과 같은 개방형 웹은 존재하지 않았을 것입니다. 저는 우리가 더 잘할 수 있다고 생각합니다.

표준의 중요한 점은 생태계와 시장을 만든다는 것입니다.

에이전트형 AI(agentic AI) 분야에서는 에이전트가 밖으로 나가 일을 수행하는 데 좋은 표준이 있다고 생각합니다. 도구를 호출하고, 다른 시스템에서 작업을 수행하고, 리소스를 읽고, 데이터를 읽는 일 말입니다. MCP가 있었기 때문에 커뮤니티 전체가 혜택을 누렸습니다.

MCP의 가장 강력한 점은 MCP 자체에 있는 것이 아니라 모두가 MCP를 사용한다는 데 있습니다. 그렇기 때문에 전 세계에 수천 개, 수만 개의 서버가 있고, 모든 에이전트가 그 서버에 연결해 다른 시스템에서 작업을 수행할 수 있는 것입니다.

반면 아직 클라이언트 소프트웨어가 에이전트에게 무엇을 해야 하는지 알려 주고, 작업을 부여하고, 무엇을 처리할지 말해 주고, 업데이트를 받기 위한 좋은 솔루션이나 표준은 없다고 생각합니다.

오늘 저는 하나의 선택지를 제안하려고 합니다. 저희 팀이 작업해 온 것으로, 개방형 표준 분야에서 좋은 해결책이라고 생각합니다.

이것이 ACP, 즉 Agent Client Protocol입니다. 이 프로젝트는 에디터 회사들에서 시작되었습니다. Zed 텍스트 에디터나 JetBrains 제품을 사용해 보셨다면 아시겠지만, Zed 팀과 JetBrains 팀이 협력해 클라이언트가 하네스를 제어할 수 있도록 하는 표준을 제안했습니다.

그들의 입장에서 생각해 보면 당연한 일입니다. 그들이 원한 것은 에디터, 예를 들면 Zed나 IntelliJ 안에서 고품질 클라이언트 구현 하나를 작성하고, 그 하나의 클라이언트 구현으로 어떤 하네스든 제어하는 것이었습니다. 작업을 보내고, 결과를 받고, 어떤 파일이 편집되고 있는지 확인하는 식입니다.

그들의 입장에서는 매우 합리적인 일입니다.

하지만 Goose 팀에서 이를 보면서, 에디터에만 국한되지 않고 훨씬 더 폭넓게 활용할 수 있다고 생각했습니다. 비교적 중립적이고 에디터에 특화된 기능도 많지 않기 때문에, 더 다양한 클라이언트 소프트웨어로 확장할 수 있다고 본 것입니다.

ACP의 설계와 이를 통해 할 수 있는 일을 조금 더 자세히 말씀드리면, 연결에 특정 능력 집합이 연관된 클라이언트와 에이전트 하네스 사이의 연결을 설정할 수 있습니다. 그런 다음 세션을 만들 수 있습니다.

세션 안에서는 사용자 메시지, 즉 사용자가 앱에 입력하는 내용이나 클라이언트 소프트웨어가 보내려는 내용을 전송할 수 있습니다. 그러면 에이전트는 텍스트, 추가 이미지나 오디오, 그리고 현재 진행 상황에 대한 업데이트로 응답할 수 있습니다.

도구가 호출되면 도구 호출 알림(tool-call notification)을 보내 어떤 도구가 호출되었고 메타데이터가 무엇이었는지 설명할 수 있습니다. 권한 요청 같은 것도 보낼 수 있습니다. 클라이언트 소프트웨어가 사용자에게 “이 도구 호출을 실행할까요, 말까요?”라고 보여 줘야 한다면, 그 요청도 이 프로토콜을 통해 전달할 수 있습니다.

설계는 꽤 단순합니다. JSON-RPC 메시지를 사용합니다. 저희가 가장 마음에 들어 하는 점은 확장 가능하다는 것입니다. 따라서 기본 프로토콜에 포함된 것만 사용할 필요가 없습니다. 사용자 지정 메서드를 추가할 수 있습니다.

관례상 밑줄을 붙인 다음 사용자 지정 메서드를 추가합니다. 제가 이 방식을 좋아하는 이유는 충분히 많은 하네스 프로젝트나 클라이언트 프로젝트가 이를 채택하면, 우리가 모두 동일하게 하고 있는 일이 무엇인지 알아낼 수 있기 때문입니다.

Codex 팀에 사용자 지정 메서드가 있고, Goose 팀에 사용자 지정 메서드가 있고, Cline 팀에 사용자 지정 메서드가 있거나 다른 팀에 있더라도, 생태계에서 무엇이 등장하는지 확인할 수 있습니다. 무엇을 표준화 과정에 올리는 것이 타당한지, 무엇을 프로토콜 자체에 포함할지 판단할 수 있습니다. 이렇게 하면 프로토콜은 사용 방식과 커뮤니티에 의해 형성됩니다.

이제 표준 입출력(standard I/O) 버전으로 데모를 보여 드리겠습니다. Zed를 열고, 여기 아주 간단한 프로젝트가 있습니다. “이 프로젝트에 대해 알려 줘”라고 입력하겠습니다.

단일 HTML 파일입니다. Zed에 질의를 입력할 수 있었고, 여기서 작동하는 에이전트는 Goose이므로 Goose의 ACP 인터페이스를 사용하고 있습니다. 텍스트와 함께 에이전트가 무엇을 읽었고 무엇을 했는지에 대한 도구 호출 정보가 전송되는 것을 볼 수 있습니다.

단일 HTML 파일이라는 것을 확인하고 설명해 주었습니다.

하나 더 해 보겠습니다. 이번에는 Poolside AI라는 회사의 것입니다. 같은 프로젝트에서 “이 프로젝트에 대해 알려 줘”라고 입력하겠습니다.

이것은 터미널 기반 클라이언트인데, 하네스 측에서는 구현을 하나만 사용하면서 동일한 에이전트로부터 정확히 같은 경험을 얻고 있습니다. 이제 어떤 클라이언트든 사용할 수 있습니다.

같은 작업을 수행한 것을 볼 수 있습니다. 텍스트 결과를 보여 주고, 도구 호출을 보여 주고, 요약이 스트리밍되고 있다는 것을 보여 줬습니다.

이것은 표준 입출력을 통해 두 클라이언트가 동일한 에이전트와 통신하는 기본적인 데모입니다. 이번에는 로컬 환경에서 실행했습니다.

하지만 로컬만으로는 충분하지 않습니다. 이 기능이 확산되려면 원격도 지원해야 합니다. 에이전트는 클라우드에서 실행될 것이기 때문입니다.

저희가 이 프로젝트를 시작했을 때는 아직 원격 지원이 없다는 것을 확인했습니다. 그래서 HTTP 전송(transport)을 명세로 추가했습니다. HTTP 버전과 WebSocket 업그레이드가 있습니다.

이제 메시지는 동일하고 프로토콜의 의미도 동일하지만, 원격 연결을 가능하게 하는 새로운 전송 방식이 지금 막 적용되고 있습니다.

Goose 팀에서 에이전트형 스택(agentic stack)을 바라보는 방식에 따르면, 중요한 구성 요소는 네 가지입니다.

클라이언트가 있습니다. 사용자가 사용하는 앱이거나, 어떤 컴퓨터에서 실행되는 헤드리스 앱(headless app)입니다. 하네스는 도구 호출 루프를 구현하는 프로그램입니다. 그리고 도구 자체가 있으며, 대개 MCP입니다. 마지막으로 모델이 있습니다.

Agent Client Protocol에 원격 전송을 사용하고, MCP가 도구 호출을 위한 원격 전송을 지원하며, 모델도 Responses API 같은 원격 엔드포인트를 오랫동안 제공해 왔다면, 이제 이 네 구성 요소를 모두 자유롭게 이동할 수 있습니다.

네 구성 요소가 모두 같은 컴퓨터에 있을 수도 있습니다. 하네스가 클라이언트와 다른 컴퓨터에 있을 수도 있습니다. 모델만 원격에 있을 수도 있고, 도구만 원격에 있을 수도 있습니다.

표준을 통일하고 전송 방식을 제대로 지원하는 것이 에이전트형 스택의 모든 구성 요소를 이동할 수 있게 해 줄 것입니다.

이와 관련해 간단한 데모도 보여 드리겠습니다.

이것은 클라이언트입니다. 클라이언트를 얼마나 쉽게 만들 수 있는지 보여 드리기 위해 어젯밤 바이브 코딩(vibe-coded)으로 만들었습니다. “시를 써 줘”라고 입력하겠습니다.

이번에도 제 컴퓨터에서 같은 프로세스에 연결하고 있습니다. 여기서는 네트워크를 통해 실행하고 있지만, 제 컴퓨터 안에 있습니다. 연결한 뒤 Goose에 원격으로 무엇을 할지 지시를 보내고 있습니다.

이것은 컨테이너 안에 있을 수도 있고 클라우드에서 실행될 수도 있지만, 메시지는 동일하고 사용하는 라이브러리도 동일합니다. 로컬과 원격 사이를 아주 쉽게 전환할 수 있습니다.

이 생태계에 참여하고 싶다면, 직접 클라이언트를 만들거나 하네스에 지원을 추가하는 방식으로 지원 기능을 실험해 보시기 바랍니다. 시작하는 방법은 Agent Client Protocol 사이트에서 확인할 수 있습니다.

이미 여러 클라이언트와 에이전트 서버가 나와 있습니다. 에디터, 데스크톱 애플리케이션, 모바일 애플리케이션, 터미널 기반 애플리케이션 등 다양한 형태가 있으며, 그 수가 빠르게 늘어나고 있습니다.

여기서 상호운용성이 확보된다면 활용 사례는 잠재적으로 매우 커질 것이라고 생각합니다. 사람들이 원하는 방식 그대로 개인용 클라이언트를 만들어 에이전트를 오케스트레이션할 수 있습니다.
