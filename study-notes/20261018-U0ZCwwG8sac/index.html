큰 그림: 직접 서버를 돌보는 대신 작업 구조에 집중한다

이 워크숍의 중심은 단순히 질문에 답하는 챗봇을 만드는 것이 아니다. 화자들은 Claude Managed Agents를 이용해, 오래 걸리는 금융 리서치를 여러 작업자에게 나누고 결과를 검사하며 기억까지 남기는 시스템을 구성한다.

관리형 에이전트에서는 플랫폼이 인프라, 호스팅, 실행용 격리 공간인 샌드박스, 확장, 이벤트 기록 저장을 관리한다고 설명한다. 개발자는 그 위에서 에이전트의 지시문, 모델, 도구, 접근 권한, 평가 기준과 결과물을 설계한다. 즉, 실행 기반 전체를 직접 조립하기보다 에이전트가 무슨 일을 하고 어떻게 성공 여부를 판단할지에 더 집중하려는 접근이다.

읽는 법: 위에서 아래로 내려간다. 앞 단계는 뒤 단계의 기반이다. 이 도식은 성능 수치를 나타내는 그래프가 아니라 워크숍의 개념 구조다.

첫 데모는 매우 단순하다. 사용자가 주제를 주면 농담을 만드는 에이전트를 생성하고, 환경을 만든 뒤 세션을 시작한다. 데모에서는 환경에 제한 없는 접근을 주지만, 화자는 실제 운영 환경이라면 접속 가능한 도메인과 MCP 서버를 좁혀야 한다고 말한다. 이 구분이 중요하다. 데모의 편리한 설정이 운영 권장 설정은 아니다.

채팅 화면의 핵심은 메시지 창이 아니라 이벤트 흐름이다

연구 데스크 애플리케이션에서는 브라우저가 사용자 메시지 사건을 세션으로 보낸다. 백엔드는 에이전트가 내보내는 이벤트 스트림을 듣고, 이를 다시 브라우저로 전달해 화면에 표시한다. 겉으로는 채팅처럼 보이지만 내부에서는 한 번의 요청과 한 번의 답으로 끝나는 것이 아니라, 생각·도구 호출·하위 작업·완료 같은 사건이 계속 흐른다.

화자들은 이 지점까지만 구현해도 채팅형 애플리케이션을 만들 수 있다고 설명한다. 그러나 워크숍의 목표는 몇 분짜리 채팅을 넘어 몇 시간, 며칠, 몇 주 또는 몇 달 동안 이어질 수 있는 비동기 작업이다.

스킬과 하위 에이전트로 일을 나눈다

다음 단계에서는 기본 에이전트에 SEC 웹사이트를 호출하고 기업 공시를 분석하는 스킬을 붙인다. 별도의 금융 분석 담당과 위험 평가 담당 같은 하위 에이전트도 구성한다. 주 에이전트는 전체 목표를 관리하고, 전문 작업은 하위 에이전트에 위임한 뒤 결과를 모은다.

하위 에이전트가 주 에이전트의 복사본으로 만들어질 때도 기존 세션의 전체 대화 기록을 그대로 넘기는 것은 아니라고 설명한다. 전달되는 것은 도구 설명, 스키마와 지시문이다. 따라서 “하위 에이전트가 지금까지의 모든 대화를 자동으로 안다”고 이해하면 안 된다.

스킬은 실행 중인 모든 세션에 즉시 덮어쓰는 고정물이 아니라 갱신 가능한 자원으로 설명된다. 화자는 스킬을 새 버전으로 게시하면 이후 그 스킬을 참조하는 새 세션이 갱신된 정보를 받는다고 말한다.

결과물뿐 아니라 합격 기준도 함께 준다

장기 작업에서는 “알아서 잘 조사해 줘”만으로 부족하다. 워크숍에서는 해야 할 일과 성공 기준을 함께 지정하는 구조를 Outcome이라고 부른다.

Nvidia 분석 예시에서는 최근 분기 자료를 찾고, 이미 저장된 분석이 있는지 메모리에서 확인한 뒤, 정해진 형식의 점수표와 기업별 메모를 파일로 남기도록 한다. 과업에는 채점 기준과 최대 반복 횟수도 포함된다. 주 에이전트가 작업을 마쳤다고 판단하면 별도의 하위 에이전트가 산출물과 세션의 작업 내용을 채점 기준에 맞춰 검사한다. 기준을 충족하지 못하면 다시 시도하도록 설계된다.

읽는 법: 위에서 아래로 읽는다. 마름모에서 기준을 충족하면 아래 결과로 가고, 충족하지 못하면 오른쪽의 붉은 복귀선이 작업 단계로 실제 연결된다. 화자가 설명한 개념 흐름이며 성공률을 나타내는 수치 도표는 아니다.

여기서 중요한 제한도 있다. Outcome은 전체 세션 수준에서 정의된다. 현재는 하위 에이전트별로 별도의 하위 Outcome을 정의하는 기능이 없다고 답한다. 또한 라이브로 시작한 Nvidia 분석은 당시 아직 실행 중이었고, 화자가 성공 사례로 보여준 것은 전날 실행한 별도 세션이다. 따라서 라이브 실행도 성공했다고 바꾸어 말하면 안 된다.

공유 메모리는 세션 사이에 지식을 넘기는 장치다

각 세션이 완전히 처음부터 시작하면 이전 조사 결과를 반복해서 찾을 수 있다. 워크숍에서는 여러 세션이 함께 쓰는 메모리 저장소를 붙여, 기업별로 이미 조사한 내용을 확인하고 새로운 결과를 보태도록 한다.

여러 사용 범위를 분리할 수도 있다고 설명한다. 예를 들어 사용자별 메모리와 조직 전체 메모리를 각각 붙여 한 세션에서 함께 이용할 수 있다는 주장이다. 메모리 내용을 다른 시스템으로 꺼낼 수 있지만, 다른 메모리 제공자를 세션에 바로 연결하는 기능은 현재 기본 지원되지 않는다. 필요하다면 MCP나 맞춤 도구로 직접 연결해야 한다.

여러 세션의 대화 기록과 메모리를 분석해 기억을 정리하는 기능은 dreaming이라고 부른다. 다만 현재 dreaming의 대상은 메모리 저장소로 제한된다. 스킬, 지시문, 에이전트 정의까지 자동 개선하는 기능은 향후 확장 가능성으로만 언급됐다.

현재 제공되는 것과 계획 중인 것을 구분해야 한다

읽는 법: 모바일에서는 표 영역을 좌우로 이동해 읽는다. 가운데 열은 화자가 현재 지원한다고 설명한 내용이고, 오른쪽 열은 현재 없거나 미래 가능성으로 말한 내용이다.

비밀 정보와 사내 데이터는 접근 경로를 제한한다

Vault는 실제 비밀값을 지시문이나 코드에 직접 넣는 대신 자리표시자를 사용하게 한다. 에이전트가 허용된 호스트에 요청할 때만 실제 값으로 바꾼다고 설명한다. 예를 들어 SEC에만 허용된 비밀값이라면 다른 도메인 요청에는 주입하지 않는다는 식이다. Vault ID를 세션에 붙여 여러 인증 정보를 묶어 공급할 수도 있고 OAuth 자격 증명도 지원한다고 답한다.

사내 데이터 연결에 관한 답변에는 중요한 수량 충돌이 있다. 화자는 먼저 “두 가지 방법”이라고 예고하지만 실제로는 다음 세 경로를 제시한다.

읽는 법: 위에서 아래로 우선순위를 뜻하는 것이 아니라, 답변에서 실제로 나온 세 대안을 분리한 것이다. 숫자 불일치를 숨기지 않기 위해 “두 경로”로 합치지 않았다.

이 워크숍에서 실제로 확인된 범위

화자들은 한 종목 분석을 여러 하위 에이전트에 맡기고 점수표와 메모리를 만드는 이전 실행 사례를 보여준다. 이어 10개 또는 100개 종목을 각각 다른 세션에 나누고 결과를 모으는 MapReduce 같은 오케스트레이션을 만들겠다고 설명한다. 정기 실행용 deployments API와 dreaming 데모도 예고한다.

그러나 제공된 전사는 그 구현과 실행 결과를 보여주기 전에 질의응답 도중 끝난다. 따라서 다중 종목 오케스트레이션, 정기 배포, dreaming은 이 전사 범위에서 완료된 시연이 아니라 설명 또는 앞으로 보여주겠다는 계획으로 남겨야 한다.

여기까지만 이해하면 충분

  • 관리형 에이전트는 인프라를 대신 관리하고, 개발자가 지시문·도구·권한·평가 기준과 제품 경험에 집중하게 하려는 구조다.
  • 스킬과 하위 에이전트는 능력과 역할을 나누고, Outcome은 전체 세션의 결과를 채점 기준에 맞춰 검사하고 재시도하게 한다.
  • 공유 메모리는 세션 사이의 지식을 잇지만, 현재 dreaming과 Outcome에는 적용 범위 제한이 있다.
  • 시연된 기능, 현재 없는 기능, 앞으로 보여주겠다는 계획을 구분해야 하며, 사내 데이터 연결 답변에는 “두 가지”와 실제 세 경로의 수량 충돌이 있다.

비유와 깨지는 지점

연구팀장·전문가·검수자의 작업표

주 에이전트는 전체 과업을 맡은 연구팀장, 하위 에이전트는 금융 분석가와 위험 평가자, Outcome의 채점 기준은 납품 검사표에 대응한다. 공유 메모리는 다음 조사에서도 참고하는 공동 연구 노트와 비슷하다.

비유가 깨지는 지점: 하위 에이전트는 인간 전문가처럼 독립적인 책임과 지속적인 전체 맥락을 자동으로 갖지 않는다. 전사에 따르면 복제된 하위 에이전트에는 기존 세션의 전체 대화가 아니라 지시문, 도구 설명과 스키마가 전달되며, 평가는 전체 세션 수준에서 이뤄진다.

왜 채팅 UI만 만든 상태로는 워크숍이 목표로 한 장기 리서치 시스템이 되지 않는가?

모범 답안 보기

채팅 UI와 이벤트 스트림은 사용자 메시지를 보내고 실행 사건을 표시할 수 있게 한다. 그러나 장기 리서치에는 전문 작업 위임, 정해진 형식의 산출물, 성공 기준에 따른 검사, 실패 시 재시도, 세션 간 지식 재사용이 추가로 필요하다. 워크숍은 이를 스킬, 하위 에이전트, Outcome과 공유 메모리로 보완한다.

2. 대조

Outcome 평가와 하위 에이전트 위임은 무엇이 다른가?

모범 답안 보기

하위 에이전트 위임은 일을 전문 역할로 나누는 실행 방식이다. Outcome은 전체 세션이 최종 목표와 채점 기준을 충족했는지 판단하는 평가 방식이다. 전사 기준으로 하위 에이전트별 하위 Outcome은 현재 지원되지 않으므로, 역할 분담과 품질 판정을 같은 기능으로 보면 안 된다.

3. 적용

새로운 내부 리서치 업무를 관리형 에이전트로 옮길지 판단할 때 무엇부터 확인해야 하는가?

모범 답안 보기

먼저 결과물을 관찰 가능한 형식과 채점 기준으로 정의할 수 있는지 확인한다. 다음으로 필요한 데이터의 접근 경로, 허용 도메인, 비밀 정보 주입 방식과 메모리 범위를 정한다. 마지막으로 당시 세션별 토큰·금액 상한이 제공되지 않는다는 설명을 고려해 자체 중단 조건과 비용 관찰 방법을 마련한다. APOM의 현재 시스템이나 데이터 연결 상태는 출처에 없으므로 실제 적용 가능성은 별도로 검증해야 한다.

이번 글의 통찰

1. 에이전트의 핵심 제품 단위는 답변보다 검증 가능한 작업이다

  • [원문] 화자들은 채팅형 인터페이스를 만든 뒤 SEC 스킬, 하위 에이전트, 맞춤 도구, Outcome과 공유 메모리를 추가했다. Nvidia 사례에서는 점수표와 메모리를 정해진 위치에 만들고 평가 하위 에이전트가 채점 기준을 검사했다고 설명했다.
  • [해석] 에이전트가 그럴듯한 문장을 만드는 것보다, 산출물·완료 조건·재시도 구조를 함께 설계하는 것이 장기 작업의 품질을 더 관찰 가능하게 만든다.
  • [경계] 성공 판정은 화자들이 정의한 채점 기준 안의 판단이다. 라이브 Nvidia 세션은 당시 실행 중이었고, 만족 판정이 나온 사례는 전날 실행한 별도 세션이다. 외부 정확성까지 독립적으로 검증됐다는 근거는 없다.

2. 역할 분담만으로는 통제가 완성되지 않는다

  • [원문] 주 에이전트는 금융 분석과 위험 평가를 하위 에이전트에 위임했다. 반면 Outcome은 전체 세션 수준에서만 정의되며 하위 Outcome은 현재 지원되지 않는다고 답했다. 세션별 금액·토큰 상한도 당시 제공하지 않았다.
  • [해석] 다중 에이전트는 병렬화와 전문화에는 도움이 될 수 있지만, 역할마다 품질·비용·실패를 독립적으로 통제하는 구조와 같지는 않다.
  • [경계] 10개나 100개 종목을 여러 세션으로 나누는 오케스트레이션은 설명됐지만 제공된 전사에서는 완성된 실행 결과가 나오지 않는다. deployments API와 dreaming 시연도 예고 상태로 끝난다.

3. 접근 편의성과 운영 안전을 분리해서 읽어야 한다

  • [원문] 데모 환경은 제한 없는 접근으로 만들었지만 실제 운영에서는 도메인과 MCP 서버를 제한해야 한다고 말했다. Vault, MCP 터널과 자체 호스팅 샌드박스를 데이터 접근 방법으로 설명했고, 실행 중에는 한 번에 메시지 10개를 보낼 수 있다고 답했다.
  • [해석] 쉬운 데모 설정은 시작 속도를 높이지만, 운영 판단에서는 네트워크 범위, 비밀값 사용처, 세션 제어와 비용 중단 조건을 별도로 설계해야 한다.
  • [경계]
  • 사내 데이터 연결 답변은 “두 가지 방법”이라고 시작하지만 실제로는 ① Vault 인증을 이용한 MCP/CLI 직접 연결, ② MCP 터널, ③ 자체 호스팅 샌드박스의 세 경로를 열거한다.
  • 크레딧 지급 안내문에는 1~2일이라고 적혀 있지만 화자는 5분 이내에 들어올 것이라고 말했다. 실제 지급 시간은 이 전사만으로 확인할 수 없다.
  • “한 번에 메시지 10개”는 화자의 명시적 설명이다. 대기열의 용량·처리 순서·실패 조건은 추가로 제시되지 않았다.
  • META의 original_creator 후보는 Claude Managed Agents, original_affiliation 후보는 Platform이다. provenance.note는 원본 영상 링크가 제공되지 않아 화자 이름과 SNS를 기준으로 추정한 출처라고 밝히므로 확정된 원작자·소속으로 볼 수 없다.

1. 세션 저장 구조의 변화

첫 질문은 세션 설계의 첫 번째와 두 번째 반복 사이에 무엇이 달라졌는지 묻는다. Gabe는 저장하려는 미래 이벤트를 세션 동작 방식에 강하게 묶지 않기 위해 가능한 많은 요소를 추상화하고 별도 구성 요소로 나눴다고 답한다.

이 원칙을 서비스 경계뿐 아니라 이벤트 계층까지 적용해 인터페이스를 만들고 가상화했다고 설명한다. 구체적인 저장 기술이나 성능 수치는 제공되지 않는다.

2. 농담 에이전트와 연구 데스크 설정

빠른 데모에서는 “주제를 주면 매번 농담을 말하는 에이전트를 만들어 달라”고 입력한다. Claude가 시스템 지시문, 이름, 설명과 모델을 제안하고, 사용자가 에이전트 도구 집합을 허용한 뒤 생성한다.

그다음 샌드박스 템플릿인 환경을 만든다. 데모에는 제한 없는 접근을 주지만, 화자는 운영 환경에서는 접속 가능한 도메인과 특정 MCP 서버를 제한해야 한다고 명시한다. 세션을 시작해 고양이 농담을 요청하고 결과를 확인한다.

화자는 플랫폼이 인프라, 호스팅, 하네스, 샌드박스 관리, 확장과 이벤트 로그 저장을 맡는다고 주장한다. 사용자는 세션을 시작하고 사건을 보내고 돌려받으며 그 위의 제품에 집중할 수 있다는 설명이다.

실습 저장소에서는 QR 코드로 저장소에 접근하고 research-desk 디렉터리에서 npm install 또는 bun i를 실행한다. 서버는 bun run dev로 시작한다.

워크숍은 여섯 막으로 진행한다고 말한다. workshop start로 시작하고 workshop next로 다음 단계로 넘어간다. 전사는 여섯 막의 정식 제목을 모두 번호로 열거하지는 않는다.

환경 설정에서는 .env.example을 .env.local로 복사하고 API 키와 EDGAR 식별 정보를 넣는다. SEC 호출에는 이름과 이메일이 필요하다고 설명한다. 현장의 Wi-Fi 문제로 실제 참가자의 동시 실습은 제한됐다.

3. 이벤트 스트림으로 채팅 UI 만들기

설정 버튼은 두 자원을 만든다.

  • 환경: 샌드박스의 템플릿. SEC 중심의 일부 웹사이트 접근과 Python 패키지를 설정한다.
  • 에이전트: 처음에는 지시문과 기본 도구만 있으며 스킬과 하위 에이전트 조정은 없는 기본 에이전트다.

브라우저 채팅창에서 Enter를 누르면 user.message 사건을 세션에 보낸다. 백엔드는 API의 SSE 스트림을 듣고 그 사건들을 프런트엔드로 다시 전달해 화면에 표시한다.

화자는 여기까지 구현하면 채팅형 애플리케이션이 된다고 말한다. 이후 목표는 몇 분을 넘어 몇 시간, 며칠, 몇 주 또는 몇 달 동안 실행되는 비동기 작업이다.

4. SEC 스킬과 하위 에이전트

다음 버전에는 SEC와 통신하는 스킬, EDGAR 식별 정보 사용법, 이후 오케스트레이션에서 사용할 Dispatch Analysis 맞춤 도구를 추가한다.

새 에이전트 버전에는 여러 하위 에이전트와 자기 자신에 대한 참조가 들어간다. 자기 참조를 이용하면 필요한 작업의 종류를 미리 세세하게 모를 때도 같은 지시문을 가진 하위 에이전트를 만들 수 있다고 설명한다.

이때 기존 세션의 전사 전체가 하위 에이전트에 복사되지는 않는다. 도구 설명, 스키마와 지시문이 전달된다.

화자는 사전에 만들어 둔 스킬을 삭제하고 다시 프로비저닝하는 과정을 보여준다. 구성 후에는 다음을 확인한다고 설명한다.

  • SEC 분석 스킬
  • 각자의 지시문·도구·권한을 가진 하위 에이전트
  • 주 에이전트의 지시문과 모델
  • 여러 세션이 공유할 수 있는 장기 메모리 저장소

스킬은 갱신 가능한 자원이며, 새 양식을 분석하는 내용을 게시하면 이후 그 스킬을 참조하는 새 세션이 새 정보를 받는다고 말한다.

5. Outcome과 Nvidia 분석

Outcome은 과업과 채점 기준을 함께 정의해 자기 평가를 구성하는 방식으로 설명된다. 에이전트가 작업을 완료했다고 판단하면 하위 에이전트가 기준과 결과를 대조한다. 충족하면 끝내고, 충족하지 못하면 다시 시도한다.

UI에서는 Nvidia 분석을 시작한다. 라이브 세션은 약 10분 정도 걸릴 것이라고 말하며 시연 당시 계속 실행 중이었다. 화자는 대신 전날 실행한 세션을 보여준다.

전날 세션에 준 요구사항은 다음과 같다.

  • Nvidia의 가장 최근 분기 자료 분석
  • EDGAR 식별 정보 이용
  • 메모리에서 이전 분석 여부 확인
  • 관심 있는 최근 양식 탐색
  • 기업별 메모리 노트 작성
  • 정해진 구조의 점수표 작성
  • 지정한 파일 위치에 결과 저장

주 에이전트는 메모리에서 기존 노트를 찾지 못한 뒤 금융 분석 또는 추출 담당과 위험 평가 담당 하위 에이전트를 실행한다. 콘솔의 각 줄은 하위 에이전트 작업을 나타내는 스레드로 설명된다.

하위 에이전트들이 결과를 돌려주자 주 에이전트가 JSON 파일을 만들고 메모리를 갱신한다. 이후 평가 하위 에이전트가 채점 기준, 세션 작업과 산출물을 검사한다. 이전 실행에서는 점수표, 수치 정의와 메모리 갱신이 기준을 충족했다고 판단한 것으로 소개된다.

이 판정은 화자의 데모 내부 평가이며 금융 분석의 외부 정확성을 독립적으로 보증하는 근거는 아니다.

6. 다중 세션 오케스트레이션과 예정된 기능

화자는 종목 100개 또는 10개를 동시에 분석하려면 각 종목을 다른 세션에 맡기고 결과를 모으는 맞춤 하네스가 필요하다고 설명한다. 이를 MapReduce와 비슷한 방식이라고 부른다.

주 에이전트가 Dispatch Analysis 맞춤 도구를 호출하면 서버가 여러 세션을 만들고, 완료 후 점수를 집계하는 구조를 만들겠다고 말한다.

또한 다음을 보여주겠다고 예고한다.

  • 정기 실행 일정을 설정하는 deployments API
  • 여러 세션의 기록과 메모리를 정리하는 dreaming
  • 공유 메모리를 장기간 개선하는 과정

제공된 전사는 이 기능들의 완성된 시연 전에 질의응답 도중 끝난다. 따라서 실행·검증 완료 상태로 기록하지 않는다.

7. 인프라와 샌드박스

관리형 에이전트는 화자 측의 자체 인프라에서 실행하는 일차 제공 방식이 있다고 답한다. AWS 크레딧을 이용하려는 경우 AWS의 클라우드 플랫폼도 언급한다.

자체 호스팅 샌드박스 제공자 예시로 Vercel, Modal, Daytona가 나오며 Google Cloud와 AWS 환경도 언급된다. 이는 화자의 지원 범위 설명으로, 전사 밖에서 호환성을 검증한 것은 아니다.

환경 의존성은 실행할 때마다 설치하는 것이 아니라 환경 생성 시점에 설치하고 캐시해 샌드박스 재생성 때 다시 사용한다고 답한다. 패키지는 NPM, Cargo, Pip 등에서 접근 가능해야 하며, 파일을 세션에 직접 올리거나 GitHub 저장소를 이용하는 방법도 말한다.

8. Vault와 인증 정보

SEC 데모에서는 이름과 이메일을 지시문에 직접 넣는다. 실제 운영에서는 Vault를 이용한다고 설명한다.

Vault의 흐름은 다음과 같다.

  1. 환경 변수에 넣을 비밀 정보를 정의한다.
  2. 실제 값 대신 자리표시자를 사용한다.
  3. 자격 증명에 허용된 호스트 도메인을 지정한다.
  4. 에이전트가 그 도메인에 요청할 때 실제 값으로 교환한다.
  5. 허용되지 않은 다른 도메인에서는 교환하지 않는다.

Vault에 이름을 붙이면 ID가 생성되고, 이 ID를 세션에 넣어 MCP나 CLI 인증에 이용한다고 설명한다. 여러 자격 증명을 하나의 Vault에 묶을 수 있고 MCP OAuth와 일부 사전 정의 OAuth 연결도 언급한다.

9. Agent SDK와 관리형 하네스

질문자는 이 시스템이 Claude Agent SDK 위에 있는지 묻는다. 답변에서는 Agent SDK를 헤드리스 Claude Code 또는 어디서든 실행할 수 있는 바이너리 형태에 가깝다고 설명한다.

Managed Agents는 Agent SDK의 장점과 교훈에서 영향을 받았지만 코딩 작업에만 한정되지 않는 별도 범용 하네스를 다시 만들었다고 답한다. “일종의 포크”라는 표현도 사용하지만, 이어 자체 하네스라고 설명한다.

10. 반복 실행, 비용과 세션 제어의 한계

다중 에이전트가 반복에 빠져 토큰을 과도하게 쓰는 것을 막는 장치가 있는지 묻자, 맞춤 하네스의 일부 통제는 사용자가 직접 설계해야 한다고 답한다.

세션별로 다음과 같은 제한을 두는 기능은 탐색 중이지만 당시 제공하지 않는다고 말한다.

  • 특정 금액 이상 쓰지 않기
  • 특정 토큰 수 이상 쓰지 않기

실행 중 잘못된 방향을 발견하면 새 user.message 사건을 보내 조정할 수 있다. 화자는 한 번에 메시지 10개를 보내도 괜찮으며 대기열에 들어간다고 설명한다.

현재는 특정 과거 시점으로 되감은 뒤 수정하고 다시 진행하는 기능이 없다. 세션 분기는 일부 고객이 요청했으며 로드맵에 있다고 답한다.

11. 공유 메모리와 dreaming

여러 사용자의 금융 조사에서 집단 지식을 쌓을 수 있느냐는 질문에, 이미 공유 메모리 저장소를 지원하며 데모에서도 사용한다고 답한다.

여러 메모리 저장소를 한 세션에 붙일 수 있으므로 사용자별 메모리와 조직 전체 메모리를 함께 구성할 수 있다고 설명한다.

데이터는 API로 꺼내 다른 시스템으로 이동할 수 있다고 주장한다. 다만 다른 메모리 제공자를 세션에 바로 연결하는 기능은 현재 기본 지원되지 않는다. MCP나 맞춤 도구를 만들어 연결하는 방식을 제안한다.

dreaming은 여러 세션의 대화 기록과 생성된 메모리를 분석해 메모리를 갱신하는 기능으로 설명한다. 현재는 메모리 저장소에만 제한된다. 스킬, 지시문과 에이전트 정의까지 확장하는 것은 미래 가능성으로 제시한다.

12. 하위 에이전트 평가 범위

Outcome은 전체 세션 수준에서 정의한다. 주 에이전트가 하위 에이전트들과 협력해 작업을 마친 뒤 완료를 선언하면 평가가 시작된다.

현재 하위 에이전트 작업마다 별도의 하위 Outcome을 정의하는 기능은 없다고 명시한다. 따라서 주 에이전트의 전체 결과가 기준을 충족하는지와 각 하위 작업이 독립적으로 올바른지는 같은 평가 단위가 아니다.

13. 사내 데이터 연결 답변의 수량 충돌

화자는 사내 데이터에 안전하게 접근하는 방법이 두 가지라고 먼저 말한다. 하지만 실제 답변에는 다음 세 경로가 나온다.

  1. API가 있는 CLI 또는 MCP를 만들고 Vault 인증을 붙여 직접 호출
  2. MCP를 인터넷에 노출하지 않는 MCP 터널 사용
  3. 조직 네트워크와 연결된 자체 호스팅 샌드박스 사용

이 열거-개수 불일치는 “몇 가지 방법”이나 “두 경로”로 완곡하게 바꾸지 않고 그대로 보존해야 한다.

14. 크레딧 지급 시간 충돌

현장 질문에서 신청 양식은 크레딧 지급까지 1~2일이라고 표시한다고 언급된다. 화자는 실제로는 5분 이내에 받을 것이라고 답한다.

어느 시간이 실제 보장 조건인지는 전사만으로 확인할 수 없다.

결과 정의는 전체 세션 수준에서 이루어집니다. 결과를 정의하고 “내가 달성하기를 원하는 것은 이것이다”라고 말합니다. 그러면 메인 에이전트가 하위 에이전트를 사용해 작업을 수행합니다. 하위 에이전트들 사이에서 협업하고, 최종적으로 “완료했습니다”라고 말합니다. 현재는 하위 결과를 정의하는 기능을 지원하지 않습니다.

이를 스킬, 프롬프트, 에이전트 정의까지 계속 확장해 지속적인 학습 기능을 제공하는 것도 생각해볼 수 있습니다. 하지만 현재는 메모리 스토어에만 적용됩니다.

MCP를 인터넷에 노출하고 싶지 않다면 MCP 터널(MCP tunnels)이라는 기능이 있습니다. 이를 사용하면 네트워크에서 저희 네트워크로 터널을 만들 수 있으므로 MCP를 인터넷에 노출하지 않아도 됩니다. 그런 방식으로 처리할 수 있습니다.

그것도 너무 큰 장벽이라면 셀프 호스팅 샌드박스를 지원합니다. 자체 샌드박스를 가져올 수 있고, 이 샌드박스는 여러분의 네트워크와 피어링되어 애플리케이션과 서비스에 접근할 수 있습니다. 에이전트는 여러분이 관리하고 호스팅하는 샌드박스를 호출하고, 그런 방식으로 리소스에 접근할 수 있습니다.
