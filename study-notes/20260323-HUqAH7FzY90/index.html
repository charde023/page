Claude Code는 비쌉니다. 이 MCP 서버가 해결합니다. (Context Mode)

한 줄 요약

Context Mode MCP 서버는 대용량 도구 출력을 로컬 SQLite FTS 데이터베이스에 인덱싱해 컨텍스트 창 소모를 최대 99% 줄이고, 압축 시 스냅샷 주입으로 세션 연속성을 유지한다.

내가 모를 만한 것 / 처음 보는 것

  • Context Mode MCP 서버 (mksglu/context-mode) — Claude Code 전용 컨텍스트 관리 MCP. MCP 서버
  • SQLite FTS (Full-Text Search) — 로컬 SQLite DB에 청크 단위로 인덱싱해 전문 검색을 수행하는 기법
  • 컨텍스트 가상화 (Context Virtualization) — AI가 실제 OS/파일 대신 샌드박스 레이어와 통신, 원시 데이터는 분리 저장
  • MCP 마켓플레이스 — Claude Code에서 MCP 플러그인을 설치하는 공식 채널
  • 압축 훅 (compression hook) — 대화 압축 이벤트를 감지해 스냅샷을 자동 생성·재주입하는 후처리
  • Gemini CLI / Cursor Copilot 지원 — Context Mode는 Claude Code 외에도 Gemini CLI, Cursor Copilot에서도 동일 방식으로 설치 가능

화자의 디테일 (놓치기 쉬운 포인트)

  1. 웹페이지 Playwright 스냅샷 1회 = 약 56KB → Context Mode 적용 시 299바이트 (99% 감소)
  2. GitHub 이슈 20개 읽기 = 약 59KB → 비슷한 수준의 압축률 적용됨
  3. CSV 분석 파일도 222바이트까지 압축 — 거의 100% 감소
  4. 계획(planning) 단계에서 이런 작업을 여러 번 반복하면 코드 한 줄 쓰기 전에 컨텍스트 창의 70%를 소모하는 상황 발생
  5. 세션 연속성 스냅샷 크기: 보통 2KB 이하로 유지
  6. 데모 기준 절감: 대화 20KB 중 약 5KB를 샌드박스로 분리 → 25% 감소, 약 1,200 토큰 절약
  7. 대형 저장소·프로덕션 로그 규모에서는 1,200토큰 절감이 10만 토큰 절감으로 확장 가능
  8. 설치 방법: Claude Code → MCP 마켓플레이스에 Context Mode 추가 후 플러그인 설치 명령 1회 실행
  9. Gemini CLI: mpam install context-mode 후 설정에 config 추가
  10. 압축 후 AI가 20분 전 실패한 수정안을 반복하지 않게 됨 — 오류 인력(error history)도 스냅샷에 보존

1. 문제: MCP 도구 호출이 컨텍스트를 삼킨다

Claude Code에서 MCP 도구를 한 번 호출할 때마다 해당 출력 전체가 200K 컨텍스트 창에 쌓인다. 도구가 많을수록 소모 속도는 가파르다.

대표 수치: - Playwright 스냅샷 1회: ~56KB - GitHub 이슈 20개: ~59KB - 계획 단계에서 이런 호출을 몇 번만 반복해도 코드 한 줄 작성 전에 컨텍스트의 70% 가 소진된다. - 결과: 약 30분 후 에이전트가 압축(compaction)을 시작하고, 파일·작업·의사결정 맥락을 잃기 시작한다.

2. Context Mode의 동작 원리

Context Mode는 컨텍스트 가상화 레이어처럼 동작한다. AI가 운영체제와 직접 통신하는 대신 샌드박스와 통신하게 만든다.

핵심 메커니즘: - 대용량 출력을 그대로 컨텍스트에 넣는 대신, 로컬 SQLite FTS 데이터베이스에 인덱싱 - 모델에는 인덱싱 완료 확인(수백 바이트)만 전달 - 이후 모델이 필요할 때 DB를 지능적으로 검색해 필요한 부분만 조회

압축률: - Playwright 스냅샷 56KB → 299바이트 (99% 감소) - CSV 분석 파일 → 222바이트 (약 100% 감소)

3. 세션 연속성 (Session Continuity)

토큰 절감은 절반의 가치다. 진짜 핵심은 세션이 끊기지 않는 것이다.

작동 방식: - Context Mode가 훅(hook) 으로 파일 수정·조회·서브에이전트 작업을 모두 모니터링 - 대화 압축이 감지되면 우선순위 스냅샷(~2KB) 을 자동 생성 - 스냅샷을 다시 컨텍스트에 주입 → 작업 맥락 복원

효과: - 세션 유효 시간: 30분 → 이론상 약 3시간 - 20분 전에 실패한 수정안을 압축 후에도 반복하지 않음 (오류 인력 보존)

4. 설치

Claude Code:

# 이후 플러그인 설치 명령 실행

설치 후 MCP 서버, 훅, 라우팅 지시가 자동 처리된다.

Gemini CLI / Cursor Copilot:

# 이후 설정에 config 추가

5. 데모: 접근 로그 분석

시나리오: 5,000줄 access log (100번째 줄마다 500 에러)

  1. Claude에게 "access log를 Context Mode로 인덱싱하고 500 에러 패턴과 관련 IP를 요약해줘" 요청
  2. Context Mode가 5,000줄을 청크로 나눠 SQLite FTS DB에 저장
  3. Claude는 파일 원문 대신 인덱싱 완료 확인만 수신
  4. 이후 지능적 검색으로 필요한 결과만 조회

비용 결과 (context-mode cache-stats 명령): - 대화 20KB 전체 대신 약 5KB만 샌드박스에 유지 - 약 1,200 토큰 절약, 25% 감소 - 프로덕션 규모 로그라면 1,200토큰 절감이 10만 토큰 절감으로 확장 가능

6. 핵심 가치: 비용보다 추론 품질

목표는 API 비용 절감이 아니라 모델의 지능을 유지하는 것이다.

컨텍스트 창에서 잡음을 걷어내면 실제 추론에 쓸 공간이 더 많아진다. Claude가 더 나은 엔지니어로 동작할 여유를 주는 것이 Context Mode의 본질적 가치다.

교정 전사 (한국어)

전체 전사 펼치기

Claude Code로 코딩해보셨다면 컨텍스트가 불어나는 문제를 겪어보셨을 겁니다.

문제는 Claude Code에서 MCP 도구를 한 번 호출할 때마다 비용이 터무니없이 커진다는 점입니다. 각 호출이 전체 출력을 그대로 모델의 20만 토큰 컨텍스트 창에 밀어넣기 때문이죠. 그리고 도구가 많을수록 컨텍스트는 더 빨리 소모됩니다. 어떤 경우에는 컨텍스트가 압축되기 전까지 에이전트를 활발히 쓸 수 있는 시간이 30분 정도뿐입니다. 그러면 AI가 파일, 작업, 중요한 의사결정을 잊기 시작합니다. 거기에 토큰 비용도 많이 듭니다.

그런데 이 핵심 문제를 해결해주는 MCP 서버가 있습니다. 오늘은 Context Mode가 무엇을 하는지, 어떻게 동작하는지, 그리고 간단한 데모로 직접 써보겠습니다.

왜 이런 일이 생기는지 수치로 먼저 보겠습니다. 웹페이지 Playwright 스냅샷 한 번이 대략 56KB입니다. GitHub 이슈 20개를 읽으면 59KB가 됩니다. 이런 작업을 계획 단계에서 세션 동안 여러 번 수행하면, 에이전트가 코드 한 줄 쓰기도 전에 컨텍스트 창의 70%를 써버리기 쉽습니다.

Context Mode는 가상화 레이어처럼 동작합니다. AI가 운영체제와 직접 통신하는 대신 샌드박스와 통신하게 합니다. 그리고 대용량 출력을 그대로 넣는 대신, Context Mode가 이를 로컬 SQLite FTS(Full-Text Search) 데이터베이스에 인덱싱합니다.

결과 차이는 꽤 큽니다. 예를 들어 56KB Playwright 스냅샷은 299바이트로 줄어 99% 감소합니다. CSV 분석 파일도 222바이트까지 줄어 거의 100%에 가까운 감소율을 보입니다.

하지만 토큰 절감은 해결책의 한 부분일 뿐입니다. 진짜 핵심 가치는 세션 연속성입니다. 에이전트 히스토리가 압축되면? 10분 전에 작성한 코드 흐름을 갑자기 놓치는 상황을 다들 겪어보셨을 겁니다.

Context Mode는 훅을 사용해 모든 파일 수정, 조회 작업, 서브에이전트 작업을 모니터링합니다. 대화가 압축되면 Context Mode가 우선순위 스냅샷을 만들고 보통 2KB를 사용합니다. 2KB 이하로 유지한 뒤 다시 컨텍스트에 주입합니다. 코딩 세션용 저장 체크포인트 같은 개념이죠. 그래서 이론적으로 세션 시간을 30분에서 약 3시간까지 늘릴 수 있습니다. 결정과 오류 이력도 유지됩니다. 예를 들어 AI가 20분 전에 실패한 수정안을, 컨텍스트가 리셋된 뒤에도 다시 반복하지 않게 됩니다.

설치도 매우 간단합니다. Claude Code를 쓰신다면 먼저 아래 명령으로 Context Mode 마켓플레이스를 추가한 뒤 플러그인 설치 명령을 실행하세요. 완료하면 바로 사용합니다. 설치가 끝나면 MCP 서버, 훅, 라우팅 지시를 자동으로 처리합니다. Gemini CLI나 Cursor Copilot을 쓰신다면 mpam install context-mode를 실행하고 설정에 config를 추가하면 됩니다.

이제 Context Mode가 실제로 어떻게 동작하는지 보겠습니다. 여기 간단한 Python 명령이 하나 있는데, 이 명령은 더미 데이터를 담은 access log 파일을 만들고 다양한 더미 API 요청과 상태 코드를 넣습니다. 그리고 100번째 줄마다 500 에러 로그가 들어가도록 되어 있습니다.

이제 Claude를 켜고 Context Mode로 access log를 인덱싱해달라고 요청합니다. 그리고 모든 500 에러 패턴을 찾아 관련 IP 주소를 요약해달라고 하겠습니다. 그러면 백그라운드에서 Context Mode가 access log 5,000줄을 청크로 나눠 자체 SQLite FTS 데이터베이스에 저장합니다. Claude는 파일 5,000줄 원문을 받지 않고 인덱싱이 완료됐다는 확인만 받습니다. 이제 Claude는 인덱싱된 데이터베이스를 지능적으로 검색해 내용을 조회할 수 있고, 파일 전체를 파싱하지 않아도 됩니다.

더 중요한 건 비용 절감입니다. context-mode cache-stats 명령을 실행하면 현재 세션에서 Context Mode가 얼마나 데이터를 절약했는지 확인할 수 있습니다. 대화의 20KB 전체를 덤프하는 대신, Context Mode는 원시 데이터 약 5KB를 샌드박스에 유지했습니다. 작은 파일 기준으로도 꽤 인상적인 결과입니다. 컨텍스트 창으로 들어갈 토큰 약 1,200개를 아낀 셈이죠. 전체적으로 이 간단한 테스트에서 25% 감소를 얻었습니다.

크게 안 느껴질 수 있지만, 일반적인 Claude 세션에서는 이런 데이터가 매 메시지마다 계속 재전송되며 그대로 남아있게 됩니다. 반면 샌드박스에 보관하면 세션 수명이 이미 늘어나기 시작합니다. 이번 데모 파일은 작지만, 더 큰 파일을 다룬다면 절감 폭은 훨씬 커질 수 있습니다. 대형 저장소 리서치 프로젝트나 프로덕션 규모 로그 분석을 한다면, 1,200토큰 절감이 쉽게 10만 토큰 절감으로 커질 수 있습니다.
