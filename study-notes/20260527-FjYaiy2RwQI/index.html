핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
OKLCH 색상 시스템 인간 시각 지각 방식에 맞는 색 표현으로 균일한 밝기·그라디언트 구현 RGB·HSL 대신 OKLCH를 쓰면 명도 불균형 없이 일관된 팔레트
Claude.md / design.md 분리 프로젝트 맥락과 시각 시스템을 분리해야 에이전트가 다른 작업 중 디자인 정보에 방해받지 않음 Claude.md = 프로젝트 정보, design.md = 시각 시스템
디자인 TDD (Vizzly CLI) 에이전트 자기 모니터링 대신 픽셀 diff + 메타데이터로 사람이 직접 검증 거절된 diff가 다음 패스의 피드백이 되어 원하는 디자인으로 수렴
안티패턴 명시 금지 목록이 없으면 모델은 매번 Inter 폰트·glassmorphism·중앙 정렬 CTA로 수렴 프롬프트에 "금지 폰트·금지 패턴" 명시가 핵심

내가 모를 만한 것 / 처음 보는 것

  • OKLCH — Lightness, Chroma, Hue 기반 색 공간. CSS Color Level 4 스펙. oklch(70% 0.15 250) 형태. RGB·HSL보다 지각적으로 균일해 그라디언트가 고르게 보임.
  • Vizzly CLI (Vizzly Testing) — UI용 TDD CLI. vizzly tdd 명령으로 로컬 서버 시작 → Playwright 스크린샷 → 브라우저에서 approve/reject → diff 메타데이터(변경 픽셀·위치) 반환. GitHub: https://github.com/vizzly-testing/cli
  • Vercel Labs web-design-guidelines skill — Claude Code용 오픈소스 스킬. 외부 유지관리 중인 원칙 집합을 참조해 항상 최신 베스트프랙티스로 design.md를 검증.
  • glassmorphism (글라스모피즘) — 반투명 흐림 효과 UI 트렌드. AI 생성 AI 슬롭(AI slop)의 대표 안티패턴.
  • AI slop — AI가 반복적으로 생성해 이미 식상해진 패턴(inter 폰트, lucide 아이콘, 보라/흰색 테마 등).
  • Milvus / Zilliz Cloud — 오픈소스 벡터 DB(GitHub 스타 44,000+). Zilliz Cloud는 완전 관리형. 영상 내 스폰서 파트.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Claude (Claude Code) 전용 표현 — 전사에서 "clod.md"로 인식된 것은 Claude.md(Claude Code 설정 파일). 문맥상 명확.
  2. 안티패턴 금지 목록 예시 — Inter, Geist 폰트 / lucide 아이콘 / 중앙 정렬 단순 CTA / glassmorphism 그라디언트. 이것들을 프롬프트에 "금지"로 명시.
  3. design.md 자동 개선 루프 — 파일 첫 줄에 "에이전트가 새 디자인 값을 발견하면 이 파일에 추가하라"는 지시문을 삽입 → 매 세션마다 design.md가 정제됨.
  4. Google 오픈소스 design.md 템플릿 — Google이 공개한 design.md 양식이 있으며, 내장 커맨드로 현재 design.md와 교차 검증해 오류를 플래그 처리 가능.
  5. 테스트 순서 — 디자인 TDD에서도 코드 TDD와 동일하게 구현 전 테스트 먼저 작성. 구현 후 테스트 작성 시 에이전트가 기존 코드에 맞게 테스트를 최적화해버림(슬랙 문제).
  6. Vizzly diff 메타데이터 — 단순 스크린샷 비교가 아니라 어느 픽셀이 얼마나 변했는지 수치 반환 → 리뷰 속도 개선.
  7. Vercel Labs 스킬 선택 이유 — 원칙이 하드코딩 대신 외부 소스 참조 방식 → 스킬 작성 시점의 베스트프랙티스에 고정되지 않음.

# 단계 핵심 행동 요지
1 레벨 1: 단일 페이지 프롬프트 구조화 의도 → 필수 요소 → OKLCH 색상 → 대비 흐름 → 타이포그래피(금지 폰트) → 레이아웃(대칭/비대칭) → 안티패턴 금지
2 레벨 2: 디자인 시스템 Claude.md + design.md 생성 프로젝트 맥락과 시각 시스템 분리 → 세션마다 자동 정제 → Google 템플릿으로 검증 → Vercel Labs 스킬로 감사
3 레벨 3: 디자인 TDD Vizzly CLI + Playwright 구현 전 테스트 작성 → vizzly tdd → approve/reject 반복 → 픽셀 diff 메타데이터로 수렴

1. 레벨 1 — 단일 페이지 프롬프트 설계

AI 모델은 제약이 없으면 안전한 패턴으로 수렴한다. Claude (Opus 4.7 [?Opus 4.7]) 기준으로 보라/흰 테마, Inter 폰트, 중앙 CTA 조합이 "식별 가능한 슬롭"이 됐다.

이를 피하는 프롬프트 구조:

  1. 의도 (intent) — 만들려는 사이트의 목적·분위기
  2. 비협상 요소 (non-negotiables) — 반드시 포함할 UI 요소와 모양
  3. 색상 시스템 — OKLCH로 팔레트 명시. 대비 흐름(contrast flow)도 함께 정의해 시각 계층 형성
  4. 타이포그래피 — 금지 폰트 목록(Inter, Geist 등) + 영역별 허용 폰트
  5. 레이아웃·리듬 — 대칭(전문적·정형) vs. 비대칭(예술적·여백 활용) 선택
  6. 섹션·소재·반응형 동작 나열
  7. 안티패턴 금지 목록 — lucide 아이콘, glassmorphism, 단순 중앙 CTA 등

2. 레벨 2 — 전체 앱 디자인 시스템 유지

랜딩 페이지는 멀쩡한데 대시보드·인증 페이지로 가면 버튼 스타일·간격·타이포그래피가 달라지는 문제.

해결: 두 파일을 항상 먼저 만든다.

  • Claude.md — 프로젝트 정보만. 디자인 내용 금지(세션 내내 로드되므로 디자인 정보가 있으면 다른 작업 시 에이전트를 방해).
  • design.md — 레벨 1의 모든 시각 규칙 포함. 색상 코드(OKLCH), 타이포그래피, 여백 등 세부 명세. 파일 첫 줄에 "새 디자인 값 발견 시 추가" 지시 삽입.

추가 단계: - Google 오픈소스 design.md 템플릿으로 교차 검증 - Vercel Labs web-design-guidelines 스킬 설치 후 실행 → 현행 베스트프랙티스 기준 감사

3. 레벨 3 — 디자인 TDD (Vizzly CLI)

디자인은 주관적이지만 테스트 불가능하지는 않다. 코드 TDD처럼 "핀"을 박는 방식.

순서: 1. Claude.md + design.md 먼저 작성 (구현 전) 2. design.md의 안티패턴·색상 규칙·간격 제약 → 각각 테스트 케이스로 변환 3. Claude Code에 테스트 케이스 작성 지시 (정적 테스트 + Playwright 회귀 테스트 + 헬퍼) 4. Vizzly CLI 설치 (vizzly tdd) → 로컬 서버 시작 5. Claude Code가 vizzly.* 이름의 Playwright 스크린샷 테스트를 작성 → 서버에 이미지 전송 6. 사람이 approve/reject → 거절 diff가 다음 반복의 피드백 7. 몇 번의 반복 후 원하는 디자인으로 수렴

정적 테스트 vs. Vizzly: - 정적 테스트: 안티패턴 직접 코드 검사 - Vizzly: 픽셀 수준 diff + 메타데이터(어디가, 얼마나 변했는지) → 사람 검토 효율화

교정 전사 (한국어)

전체 전사 펼치기

이 채널을 한동안 시청해왔다면 우리가 많은 디자인 워크플로와 도구들을 다뤄왔다는 걸 알 것이다. 몇 달간 전부 테스트하면서 드디어 같은 모델이 왜 어떤 때는 완전히 커스텀해 보이고 어떤 때는 AI 생성 티가 바로 나는지 알아냈다. 세 가지 레벨로 귀결된다.

레벨 1은 단일 페이지 디자인이고, 대부분이 건너뛰는 한 가지가 있는데 그게 결과물이 평범해 보이는 이유의 전부다. 레벨 2는 페이지를 디자인하는 대신 시스템을 디자인하기 시작하는 단계로, 워크플로가 완전히 달라진다. 레벨 3는 디자인을 프로그래밍 방식으로 서로 테스트해 실제로 작동하는 버전을 찾는 방법으로, 지금은 모든 실제 프로젝트에 쓰고 있다.

레벨 1은 단일 페이지에 좋은 디자인을 만드는 것이다. 모든 좋은 디자인의 기초이기 때문에 대부분이 가르치는 레벨이다. 이전 영상에서 Opus 4.7 [?Opus 4.7]의 디자인 역량이 크게 향상됐고 예전에 보이던 AI 슬롭이 많이 사라졌다고 이야기했다. 예전에는 "랜딩 페이지 만들어줘" 같은 단순한 프롬프트를 주면 보라·흰 테마를 그대로 써서 모든 걸 그 위에 얹었다. 그 특정 패턴은 개선됐다. 하지만 어떤 AI 모델이든 마찬가지로 안전한 패턴으로 수렴한다. 온갖 테스트와 실험 끝에, 이 모델도 매번 특정 스타일로 수렴한다는 걸 발견했다. 그래서 그 스타일이 보이면 Opus 4.7 [?Claude Opus 4.7]로 만든 사이트라는 게 바로 티가 난다. 그게 다음 AI 슬롭이 되는 건 시간 문제다.

이 레벨은 주로 프롬프트 엔지니어링과 앱 명세 방식에 달려 있다. 프롬프트를 제대로 구성하면 앱 전체를 원샷으로 뽑을 수 있다. 프롬프트는 만들려는 웹사이트의 의도로 시작해야 한다. 그 다음엔 비협상 요소, 즉 앱에 반드시 들어가야 할 것들과 UI 요소가 어떻게 보여야 하는지를 언급한다. 그 다음엔 색상 시스템을 명시한다. 여기서 OKLCH를 쓰는데, 이는 기본적으로 밝기(Lightness), 채도(Chroma), 색조(Hue)의 측정값이다. 일반적인 RGB나 HSL 대신 OKLCH를 쓰는 게 나은 이유는 인간의 눈이 실제로 색을 인식하는 방식으로 색을 표현하기 때문에 밝기와 균형을 더 잘 처리한다. 불균일하게 보일 수 있는 헥스 코드와 달리 더 부드러운 그라디언트도 만들어낸다.

색상 구성표를 설정했으면 대비 흐름(contrast flow)도 언급해야 한다. 대비는 UI 디자인의 매우 중요한 요소로, 중요한 것들로 시선을 안내하는 계층 구조를 만들어낸다. 명시적인 대비 없이는 모델이 모든 요소를 동등하게 중요한 것으로 처리해 시각적 계층 형성이 어려워진다. 또한 웹사이트가 AI 슬롭처럼 보이지 않으려면 프롬프트에서 타이포그래피도 제어해야 한다. AI 슬롭이기 때문에 금지할 폰트와 디자인의 각 영역에 쓸 폰트를 정의한다. Inter, Geist 같은 폰트는 모든 에이전트가 기본으로 쓰기 때문에 AI 슬롭의 지표가 됐다. 이것들을 명시적으로 지정하면 모델이 다른 곳을 찾게 된다.

그 다음엔 웹사이트의 레이아웃과 리듬을 정의한다. 먼저 대칭과 비대칭에 대해 알아야 한다. 대칭 레이아웃은 균형 잡힌 모양으로 그리드에 구성 요소를 고르게 배치하며 전문적이고 정형적인 디자인에 더 적합하다. 보다 예술적인 느낌을 원하면 비대칭을 택하는데, 실험할 여지가 더 많다. 특히 여백(negative space)을 활용해야 할 때 좋다. 디자인에 숨 쉴 공간을 줄 수 있기 때문이다. 만들고 있는 제품의 종류가 어느 것이 더 맞는지 결정한다. 그 다음 원하는 모든 섹션, 사용할 소재, 웹사이트의 반응형 동작 방식을 정의한다. 그리고 가장 중요한 부분은 안티패턴을 언급하는 것이다. 이것들이 단순 중앙 CTA, lucide 아이콘, glassmorphism 디자인과 그라디언트 같은 AI 슬롭의 특징들이다.

이 프롬프트를 Claude Code (클로드 코드) [?cloud code] 또는 어떤 에이전트를 쓰든 주면, 앱을 분석하고 구현 세부사항을 검토한다. 그 다음 예술적 목표로 인한 비대칭과 여백의 적절한 활용 등 프롬프트가 묘사한 대로 앱을 만든다.

레벨 2는 사이트의 모든 페이지에서 동일한 디자인을 유지하는 것이다. 에이전트가 생성한 대부분의 앱은 랜딩 페이지를 벗어나는 순간 무너지기 때문이다. 에이전트로 전체 앱을 생성할 때 바로 이런 경우를 겪었을 것이다. 랜딩 페이지는 대체로 꽤 좋은데, 다른 페이지로 가면 UI 스타일을 일관성 있게 따르지 않는다. 대시보드는 다른 버튼 스타일, 다른 간격, 다른 타이포그래피로 끝나서 에이전트가 같은 앱을 만들고 있다는 걸 잊어버린 것 같다. 다른 페이지들이 같은 사이트의 일부가 아닌 것처럼 보여서 에이전트가 생성한 사이트라는 게 드러난다.

이를 위해 Claude.md (클로드.md) [?clod.md]와 design.md라는 가장 중요한 두 파일을 만들어야 한다. 이 두 파일이 사이트 전체에서 디자인을 일관되게 유지하는 것이다. Claude.md에는 여러 번 말했듯이 프로젝트 정보만 넣고 디자인은 넣지 않는다. 이 파일은 세션 내내 로드된 상태로 있고, 거기에 디자인 내용이 있으면 에이전트가 다른 작업을 할 때 방해가 되기 때문이다. 하지만 프로젝트의 맥락을 유지해 좋은 디자인을 가능하게 하므로 여전히 핵심 파일이다.

디자인 자체를 위해서는 별도 파일이 필요하다. 레벨 1에서 다룬 모든 세부사항, 즉 시각 시스템, 레이아웃, 색상, 타이포그래피 등 모든 것을 언급하는 파일이다. design.md는 어떤 에이전트든 집어 들고 시각 시스템이 무엇인지 즉시 이해할 수 있는 파일이어야 한다. 이전 레벨과 마찬가지로 여기서도 OKLCH로 색상 시스템을 정의해야 한다.

이 두 파일을 만들기 위해 Claude Code (클로드 코드)에 각 파일에 필요한 것을 상세하게 담은 프롬프트를 줬고, 두 파일을 생성해줬다. Claude.md (클로드.md)는 짧고 프로젝트 세부사항만 담고 있다. design.md는 색상 코드, 타이포그래피 선택 등 모든 세부사항이 담겨 길다. 하지만 design.md가 끝이 아니다. 시간이 지남에 따라 계속 개선해야 한다. 그래서 파일 첫 줄에 에이전트가 발견한 새로운 디자인 값을 이 파일에 추가하도록 지시하는 줄을 넣었다. 그렇게 하면 매 세션이 이전보다 더 정제된 디자인 시스템 버전에서 시작된다.

하지만 Claude (클로드)가 design.md를 생성하도록 놔두는 것만으로는 충분하지 않다. 생성된 것이 모범 사례를 제대로 따르지 않기 때문이다. Google이 design.md 파일 템플릿을 오픈소스로 공개했다. 이 템플릿은 design.md를 교차 검증해 오류를 플래그 처리하는 명령도 포함한다. 에이전트에게 그 명령을 사용해 반복 개선하도록 프롬프트를 주면 된다.

레벨 2의 끝이 아직 아니다. 이 레벨에서 충분히 좋은 디자인을 생성하려면 기존 디자인 원칙에 대해 감사도 해야 한다. 이를 위해 정확히 이 작업을 하는 오픈소스 스킬들이 많다. 아무거나 쓸 수 있지만, 우리는 Vercel Labs (버셀 랩스)의 스킬을 쓴다. 스킬 안에 모든 원칙을 하드코딩하는 대신 그들이 적극적으로 유지관리하는 외부 소스를 가리키기 때문이다. 그래서 원칙이 스킬이 처음 작성될 당시의 최신 기술에 고정되는 대신 현재 모범 사례와 함께 업데이트된 상태로 유지된다. 프로젝트에 이 스킬을 설치하고 실행하면 디자인이 전보다 훨씬 좋아진다.

레벨 3는 TDD로 엔지니어들이 코드를 검증하는 것과 같은 방식으로 디자인을 프로그래밍 방식으로 테스트하는 것이다. 코드처럼 시각적으로 테스트를 작성할 수 없다는 건 안다. 코드에는 모든 것에 대한 명확한 입력과 출력이 있다. 디자인은 그렇지 않다. 더 주관적이고 코드처럼 수량화할 수 없다. 하지만 주관적이라고 해서 테스트를 작성할 수 없다는 뜻은 아니다.

TDD가 코드에 효과적인 이유는 테스트가 동작이 어떠해야 하는지 고정하고 구현이 그 고정점을 충족해야 하기 때문이다. 같은 아이디어가 디자인에도 적용되는데, 다만 다른 종류의 고정점을 쓴다. 우리가 만들던 앱에서 첫 번째 단계는 이전과 같았다. 구현을 생각하기 전에 Claude.md (클로드.md)와 design.md 파일을 먼저 만드는 것이다. 테스트는 항상 코드보다 먼저 작성해야 한다. 그렇게 해야 구현이 실제로 테스트를 통해 검증될 수 있다. 구현 후에 테스트를 작성하면 에이전트가 게으름을 피운다. 이미 컨텍스트에 있는 기존 코드에 최적화된 테스트 케이스를 작성하기 때문이다. 테스트를 먼저 작성하면 구현이 테스트에 맞게 되지, 테스트가 구현에 맞게 되지 않는다.

그래서 design.md에서 프로그래밍 방식으로 검증할 수 있는 모든 안티패턴을 담고 있기 때문에 이 파일들을 테스트의 진실 공급원(source of truth)으로 쓴다. design.md의 모든 안티패턴이 테스트 케이스가 된다. 모든 색상 규칙, 모든 간격 제약, 모든 타이포그래피 선택에 프로그래밍 방식의 검사가 붙는다. Claude Code (클로드 코드)에 집중해야 할 모든 섹션을 명시하는 상세한 프롬프트를 줘서 테스트 케이스를 작성하게 했다.

여러 종류의 테스트를 작성한다. 프롬프트에 언급한 안티패턴을 직접 검사하는 정적 테스트가 있다. 그 다음엔 기본적으로 Playwright를 사용해 사이트를 점진적으로 개선하는 회귀 테스트를 실행하는 시각 테스트가 있다. 스캔, 리포트 같은 다른 컴포넌트와 헬퍼 함수에 대한 테스트 케이스도 작성한다.

이 테스트들이 정적 안티패턴을 검사하지만, 디자인 테스팅에는 다른 것도 필요하다. 이를 위해 Vizzly Test (비즐리 테스트) [?Visley Test]라는 또 다른 도구가 있는데, 기본적으로 UI를 위한 TDD를 수행하는 CLI다. 코드가 변경될 때 디자인을 확인할 수 있는 로컬 TDD를 실행하는 방식이다. 에이전트의 자기 모니터링에 의존하는 대신 직접 diff를 모니터링할 수 있다. 메타데이터와 기타 세부사항이 포함된 더 나은 diff도 얻을 수 있어 리뷰가 빨라진다. 그 메타데이터 없이는 그냥 두 스크린샷을 나란히 놓고 차이를 발견하기를 바랄 뿐이다. 그걸 쓰면 Vizzly (비즐리)가 정확히 어떤 픽셀이 얼마나 변했는지 알려준다.

사용하려면 먼저 문서의 설치 명령으로 CLI를 설치한다. 설정하고 초기화하면 바로 사용할 수 있다. Claude Code (클로드 코드)를 열고 TDD를 사용하고 Vizzly (비즐리) CLI를 테스팅 매개체로 사용해 원하는 UI 부분을 구현하라고 지시하면 된다. vizzly tdd 명령을 실행하면 로컬 서버가 시작돼 스크린샷 변경을 모니터링한다. 스크린샷을 보내려면 Claude (클로드)가 기본적으로 vizzly라는 이름으로 별도의 테스트를 작성한다. 이 테스트들은 Playwright의 스크린샷 메커니즘을 사용해 서버의 뷰어에 이미지를 전송한다. 거기서 디자인을 approve/reject하고 이전 버전과 비교하는 diff를 볼 수 있다. 거절된 각 diff는 에이전트가 다음 패스를 조정하는 데 사용하는 피드백이 된다. 몇 번의 반복 후에 디자인이 에이전트가 원한다고 생각하는 것 대신 실제로 원하는 것으로 수렴된다.

여기서 사용된 프롬프트는 이 영상과 이전의 모든 영상에 대해 AI Labs Pro (AI 랩스 프로)에서 찾을 수 있으며, 자신의 프로젝트에 다운로드해 사용할 수 있다. 채널을 지원하고 싶다면 이것이 가장 좋은 방법이다. 링크는 설명에 있다. 이 영상은 여기서 끝이다.
