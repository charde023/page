핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Plan-Code-Validate 루프 계획에 시간을 더 쓸수록 에이전트가 더 오래 자율 실행된다 짧은 프롬프트 → 에이전트 금방 막힘, 상세 스펙 → 장시간 자율 실행
HTML 계획 아티팩트 (Lavish) 긴 텍스트 벽 대신 시각적으로 클릭하며 피드백 가능 마크다운보다 토큰 비효율적이지만 협업 UX에서 압도적으로 유리
워크트리 풀 관리 (Treehouse) 새 세션마다 의존성 재설치 없이 즉시 병렬 세션 시작 treehouse 한 번 타이핑으로 준비된 워크트리에 진입
신규 컨텍스트 창 리뷰 (No Mistakes) 동일 세션에서 리뷰하면 에이전트가 자신의 이전 작업에 편향됨 새 컨텍스트 창이 엣지 케이스를 훨씬 많이 잡아낸다
서브에이전트 분리 탐색/실험 작업을 메인 세션에서 분리해 컨텍스트 폭발 방지 10개 실험 → 10개 서브에이전트 병렬 실행 후 결론만 반환

내가 모를 만한 것 / 처음 보는 것

  • Lavish (npx lavish-axi) — Kun이 직접 만든 오픈소스 HTML 계획 에디터. 에이전트가 생성한 HTML 아티팩트에 주석 달고 클릭으로 피드백을 돌려보내는 양방향 협업 도구. 용어노트#Lavish
  • Treehouse — 워크트리(git worktree) 풀을 자동 관리하는 CLI. 타이핑 한 번으로 의존성 설치된 워크트리에 진입. 용어노트#Treehouse
  • No Mistakes (nm) — PR 생성부터 리뷰·테스트·문서·린트·푸시까지 파이프라인 자동화. 신규 컨텍스트 창을 열어 intent를 분석한 뒤 명백한 버그는 자동 수정, 판단이 필요한 건 사람에게 에스컬레이션.
  • ProgramBench — SWE-Bench 제작진의 새 벤치마크. 에이전트에게 FFmpeg 같은 도구를 처음부터 구현하게 해 요건 충족률과 테스트 통과율을 측정.
  • OpenCode — 오픈소스 터미널 기반 AI 코딩 CLI. 여러 모델을 빠르게 전환할 수 있어 Kun이 Claude Code (Claude Code) 외에도 활용.
  • git worktree — 같은 저장소를 다른 디렉토리에 병렬 체크아웃. 에이전트 세션 간 파일 충돌을 방지하는 핵심 메커니즘.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 계획 깊이가 자율 실행 시간 결정 — 한 줄 프롬프트는 금방 막히고, 상세 스펙을 넘기면 에이전트가 훨씬 오래 자율 실행된다. "얼마나 계획에 투자하느냐가 에이전트 자율 시간에 직접 영향을 준다."
  2. 평균 20-30개 에이전트 동시 실행 — 최소 5개 세션, 각 세션에 서브에이전트 다수. 동시에 20-30개 에이전트가 돌고 있음.
  3. PR 수 공개 — 26, 14, 27, 30…이 하루 PR 수. 실업 직후 수치가 급증하는 패턴이 차트에서 명확히 보인다고 진행자가 언급.
  4. fresh context window가 핵심 — "같은 세션에서 리뷰를 요청하면 에이전트가 이전 과정을 모두 봤기 때문에 맞다고 편향되어 엣지 케이스를 놓친다." 새 창을 여는 것이 리뷰 품질의 핵심.
  5. No Mistakes 운영 방식 — 모든 변경에 쓰지 않는다. 간단한 문서 업데이트엔 쓰지 않는 것이 토큰 효율적. 의미 있는 변경에만 적용.
  6. Claude Design — 주간 쿼터 대부분을 사용할 정도로 신규 프로젝트 디자인 시스템 구축에 적극 활용.
  7. Claude Code insights 명령 — 세션을 분석해 "어떤 습관을 개선할 수 있는지, 어떤 skill을 추가하면 좋은지"를 리포트로 생성하는 내장 기능. 토큰 소모가 크다.
  8. 에이전트 병렬화는 탐색/실험 비용 때문에도 필요 — 실험 200개 × 8가지 언어 조합 같은 대규모 실험을 단일 세션에서 돌리면 compaction이 반복돼 비효율적.

# 섹션 요지
1 Plan-Code-Validate 개요 세 단계 중 계획에 가장 많은 시간 투자, 코딩·검증은 에이전트에 위임
2 병렬 세션 전략 에이전트가 작업하는 동안 다른 세션으로 즉시 전환 → 항상 생산적
3 Lavish: HTML 계획 에디터 텍스트 벽 대신 시각 아티팩트로 계획 반복, 클릭으로 피드백
4 Treehouse: 워크트리 풀 매번 의존성 재설치 없이 즉시 병렬 세션 시작
5 서브에이전트 활용 기준 탐색·실험처럼 컨텍스트 크고 메인 세션에 불필요한 작업에만 분리
6 AGENTS.md 테스트 지침 엔드투엔드 테스트 방법을 프로젝트별 AGENTS.md에 명시해 에이전트가 자동 검증
7 No Mistakes: 자동 PR 파이프라인 intent 분석 → 리뷰 → 테스트(증거 캡처) → 문서 → 린트 → PR 생성
8 PR 리뷰 철학 줄별 코드 리뷰 대신 리스크 수준으로 집중도 결정, 저위험은 스킴 후 즉시 머지
9 AI 시대 팀 워크플로 변화 월 10-15 PR → 일 20-40 PR로 바뀌면 기존 PR 리뷰 프로세스 붕괴
10 조언: 스케일업 3원칙 많이 만들기, 병렬 에이전트 적극 활용, 코딩 외 모든 수동 작업에 AI 투입

1. Plan-Code-Validate 루프

Kun의 핵심 워크플로는 Plan → Code → Validate 세 단계다. 계획 단계에서 본인이 가장 많은 시간을 쓰고, 코딩은 거의 전적으로 에이전트에 맡기며, 검증도 에이전트가 대부분 처리한다.

중요한 인사이트: 계획에 투자하는 시간이 에이전트 자율 실행 시간을 결정한다. 한 줄짜리 프롬프트를 주면 에이전트가 금방 막혀서 다시 불러야 하지만, 상세한 스펙을 주면 에이전트가 훨씬 오래 자율 실행된다. "얼마나 자세하게 계획하느냐가 에이전트가 얼마나 오래 코딩하느냐에 직접 영향을 준다."

또한 코드 단계와 검증 단계는 에이전트가 루프로 돌릴 수 있어서 실행 시간을 늘리기 위해 에이전트 자율 루프를 최대화하는 방향으로 시스템을 설계했다.

2. 병렬 세션 전략

Kun은 최소 5개의 세션을 상시 유지하고, 각 세션에 서브에이전트 여러 개가 돌면서 평균 20-30개의 에이전트가 동시에 실행된다.

핵심 원리: 에이전트가 작업하는 시간(계획 전 준비, 구현 직후) 동안 사람의 개입이 필요하지 않다. 에이전트를 실행하자마자 다른 세션으로 전환해 다른 일을 한다. 진행자 Peter가 "과거 대기업에서는 회의 사이에 컨텍스트 스위칭을 했다면 이제는 에이전트 스레드 사이를 전환하는 것"이라 표현했고, Kun은 이를 "대규모 범위를 관리하는 사람처럼, 여러 곳에서 일이 진행되고 있고 가장 필요한 곳으로 뛰어든다"고 비유했다.

3. Lavish: HTML 계획 에디터

마크다운 플랜의 문제점은 긴 텍스트 벽이 돼서 읽는 데 시간이 많이 든다는 점이다. Kun은 타리크 시히파르(Tariq Kieshar [?])의 "HTML over Markdown" 아티클에서 영감받아 Lavish 에디터를 직접 만들었다.

동작 방식: 1. 에이전트에게 npx lavish-axi를 사용해 계획을 작성하라고 지시 2. 에이전트가 HTML 아티팩트를 생성 3. Lavish 에디터에서 시각적으로 확인하며 클릭으로 직접 주석·피드백 제공 4. 에이전트가 피드백을 받아 아티팩트를 수정

실제 데모에서 아이들용 AI 튜터 앱 화면 리디자인 과정을 보여줬다. 에이전트가 옵션 A/B/C/D 레이아웃을 HTML로 제안하고, Kun이 옵션 C를 클릭하자 자동으로 에이전트에게 "옵션 C를 선택했다"는 피드백이 전달됐다.

마크다운보다 HTML이 나은 이유: 토큰 효율은 낮지만, 시각적 미리보기와 양방향 인터랙션(클릭 피드백)이 가능해 계획 반복(iteration) 속도가 훨씬 빠르다.

4. Treehouse: 워크트리 풀 관리

여러 세션을 병렬로 돌리려면 같은 디렉토리에서 여러 에이전트가 동시에 작업하면 충돌이 난다. 해결책은 git worktree로 병렬 디렉토리를 만드는 것이지만 두 가지 문제가 있다:

  1. 워크트리마다 이름을 짓고 현황을 추적해야 하는 인지 부하
  2. 새 워크트리에는 node_modules 같은 의존성이 없어서 매번 재설치 필요

Treehouse는 이 두 문제를 해결한다. treehouse를 타이핑하면 풀에서 관리되는(이미 의존성이 설치된) 워크트리를 자동으로 할당하고 진입시켜 준다. 이름을 생각하거나 상태를 추적할 필요가 없다.

5. 서브에이전트 활용 기준

"언제 서브에이전트가 필요한가"에 대해 Kun의 답변: 메인 세션의 컨텍스트 창을 크게 소모하지만, 결론만 메인 세션에 필요한 작업에 서브에이전트를 쓴다.

구체적 예시: - 코드베이스 탐색·조사: 탐색 과정은 메인 세션에 불필요하므로 서브에이전트가 탐색 후 결론만 반환 - 독립된 실험 10개: 각각 서브에이전트를 병렬로 실행 - ProgramBench 실험 200개 × 8개 언어: 서브에이전트 없이 단일 세션에서 돌리면 compaction이 반복돼 비효율

대부분의 현재 모델과 하네스는 서브에이전트를 자발적으로 쓰는 데 훈련이 부족하다고 지적. Claude Code (Claude Code)의 explore 서브에이전트처럼 내장된 경우를 제외하면 명시적으로 지시해야 한다.

6. AGENTS.md 테스트 지침

에이전트는 기본적으로 유닛 테스트(순수 코드 기반)를 선호하는데, 이는 엔드투엔드 검증이 부족하다. Kun은 프로젝트별 AGENTS.md에 이 앱을 어떻게 엔드투엔드 테스트하는지 구체적인 지침을 작성해 놓는다.

예: HiBit (Electron 앱)의 경우 "이 앱은 Electron 앱이므로 브라우저를 직접 구동해서 이렇게 테스트한다"고 명시. 그러면 에이전트가 구현 완료 후 자동으로 앱을 실행하고 스크린샷을 찍으며 엔드투엔드 검증을 수행한다.

원칙: 내가 수동으로 하는 것을 에이전트 지침으로 전환한다. "앱을 열고 화면을 보며 직접 확인"하던 것을 에이전트가 대신하도록 만든다.

7. No Mistakes: 자동 PR 파이프라인

코딩이 끝나면 nm을 실행한다. No Mistakes는 다음 파이프라인을 자동으로 처리한다:

  1. Intent 분석 — 이전 에이전트 세션을 읽어 "무엇을 하려 했는지" 파악 (새 컨텍스트 창에서 진행)
  2. 브랜치 생성 — 브랜치 이름·커밋 메시지 자동 결정, 리베이스(rebase)로 충돌 방지
  3. 리뷰 — 엣지 케이스·논리 오류·버그를 높은 recall로 검출. 명백한 버그는 자동 수정, 판단이 필요한 건 사람에게 에스컬레이션
  4. 테스트 — CI처럼 전체 회귀 검증, 스크린샷/동영상으로 변경 증거 캡처
  5. 문서 — 변경으로 영향받는 문서 일관성 검사
  6. 린트
  7. PR 생성 — intent 기반 설명, 리스크 수준(낮음/중간/높음) 자동 판정

핵심 설계 결정 — 신규 컨텍스트 창: 같은 세션에서 리뷰를 요청하면 에이전트가 모든 이전 과정에 편향돼 버그를 놓친다. 새 컨텍스트 창은 "시니어 엔지니어가 완료한 PR에 주임급이 새 눈으로 들어오는 것"과 같다.

Kun이 직접 리뷰하던 것과 에이전트 리뷰를 병렬 테스트해서 "내가 잡고 에이전트가 못 잡는 것"이 0에 수렴할 때까지 프롬프트를 개선했다. 현재는 에이전트가 못 잡는 것을 자신이 잡는 경우가 없다고 한다.

8. PR 리뷰 철학과 팀 워크플로 변화

리스크 기반 집중: 저위험 PR은 스킴 후 즉시 머지, 중간/고위험 PR만 diff를 열어 직접 확인한다. 줄별 코드 리뷰는 사람을 병목으로 만든다.

팀 워크플로 변화 예측: 평균 소프트웨어팀은 월 10-15 PR을 처리한다. AI로 10배 빨라지면 기존 PR 리뷰 프로세스(사람이 검토 대기)가 붕괴한다. 이미 일부 스타트업은 PR을 기록 목적으로만 올리고 리뷰 대기 없이 바로 머지하는 방식으로 전환 중이다. Kun은 이를 "No Mistakes 없이 그렇게 하는 것"이라며 안정성 저하를 우려했다.

혼자 일하는 것에 대해: 동료와의 브레인스토밍(다양한 관점)은 그리워하지만, "20개의 PR을 올려도 아무도 리뷰 안 해주는" 대기업의 병목은 그립지 않다. "리뷰를 요청하면 항상 즉시 시작해주는 AI"가 그것을 대체한다.

9. 스케일업 3원칙

  1. 많이 만들기 — 아이디어가 생기면 바로 프롬프트를 날린다. "무엇을 할지 결정하는 데 시간을 너무 쓰다가 하나를 해보고 안 되면 포기"하지 않는다. 모든 아이디어를 빠르게 실행해봐야 한다.
  2. 병렬 에이전트로 더 많은 반복 — 하나의 에이전트를 기다리는 것 자체가 병목이다. 더 많은 토큰을 쓰고 더 많은 에이전트를 병렬로 돌리는 것이 스스로를 루프에서 꺼내는 방법이다. 구독 플랜이라면 쿼터를 모두 소진하는 것이 목표다.
  3. 코딩 외 모든 수동 작업에 AI 투입 — 코딩뿐 아니라 PR 생성, 문서 업데이트, 테스트 실행 등 모든 반복적·수동 작업에 에이전트를 투입한다. "내가 수동으로 하는 것을 발견하면 에이전트에게 시킬 수 있는지 생각한다."

[오프닝 인용] 코드를 한 줄 한 줄 전부 리뷰하면 당신이 병목이 된다. 그래서 나는 에이전트가 처음 짠 코드를 리뷰하지 않는다. 결국 에이전트가 잡지 못하는 것을 내가 잡는 경우가 없어졌다. 나는 보통 최소 다섯 개의 다른 세션을 동시에 돌린다. 평균적으로는 20-30개 에이전트가 돌고 있다. 대부분의 경우 하루에 PR을 20-40개 정도 올린다.

우리의 워크플로와 팀 운영 방식은 대부분의 시간을 코딩에 쓰던 시절에 만들어진 것이다. 그런데 PR을 10배 더 쓰기 시작하면 우리는 그 규모를 따라잡을 준비가 안 돼 있다. 에이전트에게서 더 많은 것을 얻으려면 우리 스스로를 루프에서 최대한 빼내야 한다.

[소개] (진행자 Peter Yang) 안녕하세요, 오늘은 Meta와 Microsoft 출신 L8 엔지니어이자 현재 솔로 AI 빌더인 친구 Kun을 모셨습니다. Kun은 에이전트로 어떻게 제품을 만드는지 실제로 보여줄 예정입니다.

(Kun Chen) 고마워요, Peter.

[워크플로 개요: Plan, Code, Validate] (Peter) 에이전트로 제품을 만드는 방법을 전반적으로 설명해 주실 수 있나요?

(Kun) 제 워크플로는 Plan, Code, Validate입니다. 이게 남들과 크게 다르지는 않으니, 제가 다르게 하는 부분을 중심으로 설명할게요. 의미 있는 것을 만들 때 보통 이 세 단계를 거치는데, 요건을 계획하고, 에이전트가 코딩하고, 에이전트가 원하는 대로 했는지 검증합니다.

제가 다르게 하는 건 각 단계에 얼마나 시간을 쓰느냐입니다. 저는 지금 계획 단계에 가장 많은 시간을 씁니다. 계획은 대부분 제가 에이전트의 도움을 받아서 합니다. 코딩은 거의 전적으로 에이전트가 합니다. 요건이 명확하게 계획되면 에이전트를 믿고 대부분의 작업을 맡깁니다. 검증 단계에서도 에이전트를 많이 씁니다.

(Peter) 코드와 검증이 에이전트가 자체적으로 돌릴 수 있는 루프가 되는 거죠?

(Kun) 맞아요. 계획 단계에 얼마나 투자하느냐에 따라 달라지기도 합니다. 상세한 계획을 짜면 에이전트가 더 오래 돌 수 있고, 짧은 프롬프트만 쓰면 에이전트가 금방 작업을 마치고 다시 프롬프트를 받아야 합니다.

(Peter) 저도 에이전트에 게으르게 한 줄짜리 프롬프트만 써왔는데, 역시 안 되더라고요.

[병렬 세션] (Kun) 또 다른 최적화 방법은 타임라인에서 사람이 필요한 건 시작과 끝뿐이라는 거예요. 그래서 저는 많은 세션을 병렬로 돌립니다. 에이전트가 작업하는 동안 항상 생산적으로 다른 일을 하는 거죠. 동시 병렬 세션 수를 늘리는 게 더 많은 일을 하는 데 중요한 부분입니다.

(Peter) 같은 프로젝트 안에서도 병렬로 돌리나요, 아니면 여러 프로젝트를 병렬로?

(Kun) 둘 다요. 서로 다른 프로젝트를 섞기도 하고, 같은 프로젝트 안에서도 다른 세션이 다른 일을 하기도 합니다.

(Peter) 대기업에서는 회의들 사이를 컨텍스트 스위칭하며 다녔는데, 이제는 에이전트 스레드 사이를 전환하는 것 같네요.

(Kun) 맞아요. 대규모 범위를 관리하는 사람처럼, 항상 다양한 곳에서 일이 진행되고 있고 필요한 곳에 뛰어드는 것과 비슷해요.

[스폰서: Linear] (진행자 내레이션) 이 에피소드는 Linear의 후원으로 제작됩니다. Cursor, Claude Code (Claude Code), Codex 같은 도구를 쓰면 많은 작업이 코드 에디터 밖에서 보이지 않게 이루어집니다. Linear는 이런 에이전트 코딩 도구들과 직접 통합돼 누가 무엇을 작업 중인지 팀 전체가 볼 수 있습니다. OpenAI, Ramp, Block이 Linear를 씁니다. linear.app/agents에서 확인하세요.

[데모: 터미널 기반 워크플로] (Kun) 이게 제 터미널입니다. 거의 모든 작업을 여기서 합니다. HiBit라는 아들을 위한 AI 튜터 프로젝트를 예시로 쓸게요. 오늘 아침에 메인 화면을 개편했는데 아직 지저분하고 마음에 들지 않습니다. 전형적인 워크플로로 스크린샷을 찍고 에이전트에게 보여주는 거죠.

OpenCode를 많이 씁니다. 여러 모델을 빠르게 전환할 수 있어서요. 에이전트에게 스크린샷을 붙여넣고 문제점을 말해요. 아이들에게 친화적이지 않은 기술적 세부사항이 너무 많고, 화면 공간이 낭비되고 있다는 것들이요. "어떻게 개선할지 옵션을 제안해 줘"라고 요청합니다.

에이전트가 텍스트 플랜을 냈는데 긴 텍스트 벽이라 읽기 어렵네요. 그래서 저는 다른 방법을 씁니다. Lavish를 사용하라는 지시를 추가해요.

[Lavish: HTML 계획 에디터] Lavish는 제가 직접 만든 시각적 에디터예요. "HTML over Markdown" 아티클을 읽고 만들었는데, 처음엔 HTML이 토큰 비효율적일 것 같았는데 써보니 정말 유용했어요.

(Peter) Lavish가 HTML을 원하는 형식으로 만들어주는 앱인가요?

(Kun) 맞아요. HTML 아티팩트를 생성하고 사람과 에이전트 간의 인터랙티브한 피드백을 지원하는 도구입니다. 에이전트가 HTML을 생성하고, 저는 브라우저에서 열어서 보고, 마음에 들지 않는 부분을 주석으로 달 수 있어요. 이 주석이 에이전트에게 다시 전달됩니다. 이 양방향 피드백이 Lavish가 해결하려는 문제예요.

에이전트가 HTML을 작성하는 동안, 저는 그 시간을 낭비하지 않고 Tmux에서 새 탭을 열어 다른 일을 합니다.

[Treehouse: 워크트리 관리] 문제는 같은 디렉토리에서 다른 에이전트를 돌리면 충돌이 난다는 것입니다. 그래서 git worktree add로 다른 디렉토리를 만드는 게 일반적인 방법인데, 두 가지 문제가 있어요. 어떤 워크트리가 무엇을 하는지 추적하는 인지 부하가 있고, 새 워크트리에는 node_modules 같은 의존성이 없어서 매번 재설치해야 합니다.

(Peter) 워크트리가 뭔지 모르는 분들을 위해 설명해 주실 수 있나요?

(Kun) 워크트리는 현재 Git 저장소를 다른 디렉토리에 복제한 것과 같아요. 병렬 디렉토리라 서로 직접 영향을 주지 않습니다.

그래서 저는 Treehouse를 만들었어요. 매번 새 세션을 시작할 때 treehouse를 타이핑하면, 풀에서 관리되는 워크트리(이미 의존성 설치됨)를 자동으로 할당하고 진입시켜 줍니다. 어떤 워크트리가 있는지 생각할 필요가 없고, 의존성을 재설치할 필요도 없습니다.

[Lavish 데모 결과] (Kun) 이제 HTML이 준비됐네요. 현재 레이아웃의 문제점과 옵션 A/B/C/D를 시각적으로 보여주고 있어요. 텍스트 벽보다 훨씬 보기 쉽고, 버튼을 클릭하면 해당 옵션을 선택했다는 피드백이 에이전트에게 즉시 전달됩니다. 저는 옵션 C가 마음에 들어서 클릭합니다. 에이전트가 이제 옵션 C를 구현하면 됩니다.

[스펙 작성 방법] (Peter) 완전히 새로운 프로젝트를 시작할 때는 어떻게 계획하나요?

(Kun) 새 프로젝트면 같은 Lavish 에디터를 써요. 에이전트에게 초기 아이디어를 말하고, 위험 요소나 제가 생각 못한 약점을 비판해달라고 합니다. 에이전트가 HTML 아티팩트로 돌아오면, 그것을 보면서 아이디어를 스펙으로 다듬어 나갑니다. 자신의 의견이 있어도 에이전트에게 반박할 권한을 줍니다. 더 많은 옵션을 보고 싶기도 하니까요.

실제로 저는 많은 지침을 Lavish 에디터 안에 내장했어요. 에이전트가 Lavish를 쓸 때 이미 그런 best practice들을 알고 있습니다.

(Peter) 비주얼 디자인은 어떻게 처리하나요?

(Kun) Claude Design (Claude Design)을 많이 씁니다. 새 프로젝트의 디자인 시스템을 만드는 데 특히 유용해요. 주간 쿼터를 거의 다 썼을 정도로 자주 씁니다.

[병렬 에이전트 수와 서브에이전트] (Peter) 지금 몇 개의 에이전트 빌딩 세션을 동시에 돌리나요?

(Kun) 보통 최소 다섯 개의 세션을 동시에 돌리고, 각 세션에는 서브에이전트가 여러 개 있어서 총합은 아마 평균 20-30개일 거예요.

(Peter) 서브에이전트를 직접 지시하나요, 아니면 에이전트가 알아서 쓰나요?

(Kun) 좋은 질문이에요. 현재 대부분의 모델과 하네스는 서브에이전트를 자발적으로 쓰는 데 능숙하지 않아요. Claude Code (Claude Code)의 explore 같은 내장된 경우를 제외하면, 명시적으로 지시해야 하는 경우가 많습니다.

제가 서브에이전트를 쓰는 가장 큰 이유는 메인 에이전트의 컨텍스트 창이 폭발하는 것을 막기 위해서예요. 탐색·조사처럼 컨텍스트를 많이 소모하지만 결론만 메인 세션에 필요한 경우에 서브에이전트를 씁니다. 또는 10개의 독립적인 실험을 돌릴 때 10개의 서브에이전트를 병렬로 실행합니다.

지금 돌아가고 있는 게 있는데, ProgramBench(프로그램벤치)를 여러 프로그래밍 언어(TypeScript, JavaScript, Python 등)로 Codex (Codex)에게 돌려보면서 언어별 성능 차이를 측정하는 실험이에요. 200 × 8가지 조합이라 서브에이전트 없이는 비효율적입니다.

[AGENTS.md 테스트 지침] (Kun) 각 프로젝트의 AGENTS.md에 테스트 방법을 명시해 두면 에이전트가 작업 완료 후 자동으로 엔드투엔드 검증을 합니다. HiBit는 Electron 앱이라 "이 앱은 이렇게 브라우저를 구동해서 테스트한다"고 적어뒀어요. 그러면 에이전트가 스크린샷을 찍고 시각적으로 확인합니다.

(Peter) 기술적으로 잘 모르는 사람은 어떻게 하나요?

(Kun) 고수준 원칙은: 내가 수동으로 하는 것을 에이전트에게 시킬 수 있는지 물어보세요. 에이전트가 방법을 알아서 찾을 겁니다.

[검증 단계: No Mistakes 데모] (Kun) 에이전트가 작업을 마쳤네요. 이제 검증을 해야 합니다. AI는 엄청나게 많은 코드를 쓸 수 있어서, 한 줄 한 줄 리뷰하면 당신이 병목이 됩니다. 저는 코드를 리뷰하지 않습니다. 대신 No Mistakes를 씁니다.

nm을 실행하면: 1. 에이전트가 브랜치를 만들고 커밋 메시지도 자동으로 씁니다. 저는 아무것도 생각하지 않아도 됩니다. 2. 제 이전 OpenCode (OpenCode) 세션을 분석해서 제 intent를 파악합니다. 3. 리베이스해서 merge conflict를 방지합니다. 4. 변경을 리뷰합니다 — 엣지 케이스, 논리 오류, 버그를 높은 recall로 찾습니다. 명백한 버그는 자동 수정, 판단이 필요한 건 저에게 에스컬레이션합니다. 5. [신규 컨텍스트 창의 중요성] No Mistakes는 새로운 컨텍스트 창에서 실행됩니다. 의도적인 설계예요. 같은 세션에서 리뷰를 요청하면 에이전트가 모든 이전 단계를 봤기 때문에 맞다고 편향됩니다. 새 컨텍스트 창을 쓰면 훨씬 더 많은 엣지 케이스가 잡힙니다. 이걸 많이 테스트했고, 결국 에이전트가 못 잡는 것을 제가 잡는 경우가 없어졌습니다.
