올해 Claude에게 있었던 일들

한 줄 요약

Claude Code와 Claude Tag는 코딩 에이전트를 개인 도구에서 팀 단위 협업·자동화 인프라로 확장시키고 있으며, 그 결과 개발자의 핵심 역량은 구현력보다 제품 감각, 검증 체계, 보안 설계로 이동하고 있다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
코딩 에이전트(Coding Agent) 개발자가 직접 구현하는 시간이 줄고, 무엇을 만들지 판단하는 시간이 늘어남 실행력보다 제품 감각과 비즈니스 감각이 중요해진다
Claude Code Anthropic의 터미널 기반 AI 코딩 도구 복잡한 작업은 여전히 Claude Code에서 대화형으로 반복하는 방식이 강하다
Claude Tag Slack 같은 협업 도구 안에서 동작하는 팀형 Claude 팀 채널에서 버그 감시, PR 생성, 담당자 태그, 팀 메모리까지 수행한다
재작성(Rewrite) 예전에는 금기였지만 AI 시대에는 더 현실적인 선택이 됨 좋은 테스트 스위트가 있으면 여러 구현을 만들고 비교할 수 있다
평가셋(Eval Set) 새 모델이나 프롬프트 변경이 실제로 좋아졌는지 판단하는 기준 모델 신뢰는 감이 아니라 누적 평가와 회귀 방지로 쌓는다
오토 모드(Auto Mode) 권한 승인 없이 장시간 작업하게 하면서도 보안을 지키는 핵심 기능 프롬프트 인젝션(Prompt Injection), 데이터 유출(Data Exfiltration)을 줄이기 위한 동적 권한 판단 시스템
시스템 프롬프트(System Prompt) 경량화 최신 모델은 세세한 규칙보다 맥락과 판단 여지를 더 잘 활용함 Claude Code의 최신 모델용 시스템 프롬프트는 약 80% 줄었다
도그푸딩(Dogfooding) 내부에서 매일 실제 업무에 써보며 제품을 검증하는 문화 Anthropic은 내부 활성 사용자와 유지율 기준을 넘기기 전에는 외부 출시를 미룬다

내가 모를 만한 것 / 처음 보는 것

  • Claude Tag — Slack 채널 안에서 팀원들과 함께 쓰는 멀티플레이어(Multiplayer) Claude. 버그 리포트를 감시하고 PR을 만들며 팀 메모리도 유지한다.
  • 오토 모드(Auto Mode) — Claude가 명령어 실행, 네트워크 접근, Git 작업 등을 할 때 사용자의 의도와 대화 맥락을 보고 권한을 자동 판단하는 모드.
  • 팀 메모리(Team Memory) — 특정 Slack 채널에서 팀이 Claude에게 알려준 선호나 규칙을 이후 작업에 계속 반영하는 기능.
  • 코드 소유자(Code Owner) — 특정 코드 영역의 품질과 승인 책임을 가진 사람. 핵심 영역은 여전히 사람이 직접 승인한다.
  • 행동 평가(Behavioral Eval) — 단순히 정답을 맞히는지가 아니라, 사용자가 싫어하는 말투나 중단 행동까지 평가하는 테스트.
  • 토큰 프록시(Token Proxying) — 에이전트가 실제 비밀키를 직접 보지 못하게 하고, 요청 시 프록시가 임시로 진짜 토큰을 끼워 넣는 보안 패턴.
  • 안트푸딩(Antfooding) — Anthropic 내부식 도그푸딩 표현. Anthropic의 상징인 ant에서 온 말장난.
  • 원격 제어(Remote Control) — 모바일이나 웹 브라우저에서 로컬 CLI의 Claude Code 세션을 제어하는 기능.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Claude Code는 Sonnet 3.7 출시 때 “불릿 포인트 하나” 수준으로 공개됐고, 공개 후 약 1년 반도 안 됐다고 언급된다.
  2. Anthropic 내부 Claude Tag는 제품 엔지니어링(Product Engineering) PR의 65%를 생성·머지하는 수준까지 쓰이고 있다.
  3. Claude Tag는 기본적으로 멀티플레이어(Multiplayer), 능동형(Proactive), 팀 메모리(Team Memory)를 핵심 차별점으로 가진다.
  4. 최신 frontier 모델용 Claude Code 시스템 프롬프트는 약 80% 줄었다. 단, 구형 모델은 여전히 더 긴 시스템 프롬프트를 사용한다.
  5. 시스템 프롬프트를 줄인 이유는 “예시를 많이 주는 방식”이 최신 모델의 창의성과 판단을 오히려 제한할 수 있기 때문이다.
  6. 코드 리뷰 자동화는 6개월 이상 점진적으로 신뢰를 쌓은 결과이며, 모든 영역에서 갑자기 사람을 뺀 것이 아니다.
  7. Auto Mode는 Anthropic 내부에서 1월부터 사용되어 왔고, 외부 공개 전 오랜 기간 보강됐다.
  8. Auto Mode는 수천 개의 평가(Evals)와 외부 레드팀(Red Team) 테스트를 거쳤다고 설명한다.
  9. 보안 측면에서 Auto Mode는 프롬프트 인젝션, 데이터 유출 같은 주요 위험 범주에서 평균적인 사람 리뷰어보다 위험이 낮다고 주장한다.
  10. Claude Tag의 메모리는 현재 채널별 Markdown 파일 형태로 구현되어 있다고 답변한다.

10 문화적 교훈 공개 채널, 도그푸딩, “스스로와 협상하지 않기”가 생산성을 높임

1. 코딩 에이전트가 바꾼 일상

Claude Code 초기에는 사용자가 매 권한 요청을 꼼꼼히 읽고, 파일을 확인했는지 계속 물어보며, 작은 행동 하나하나를 감시해야 했다. 하지만 모델 세대가 올라가면서 사용자는 점점 한발 물러서서 반복적 구현 작업을 Claude에게 위임할 수 있게 됐다.

이 변화의 핵심은 개발자가 더 이상 “코드를 한 줄씩 작성하는 사람”에 머물지 않는다는 점이다. 이제는 무엇을 만들어야 하는지, 사용자에게 어떤 경험을 제공해야 하는지, 비즈니스에 실제 영향을 주는 기능이 무엇인지가 더 중요해졌다.

사이먼 윌리슨도 같은 흐름을 지적한다. 도구 덕분에 할 수 있는 일의 야망이 커졌고, 그만큼 소프트웨어 엔지니어링은 오히려 더 어려워졌다. 쉬운 일을 빨리 하는 시대가 아니라, 더 큰 문제를 감당해야 하는 시대가 된 것이다.

2. 개발 상식의 변화: 실행력보다 제품 감각

캣 우는 과거의 제품 개발 방식을 이렇게 요약한다. 제품 매니저가 몇 달 동안 고객을 만나고, 여러 팀과 조율하고, 제품 요구 문서(PRD)와 엔지니어링 문서를 쓴 뒤에야 첫 코드가 작성됐다.

하지만 코딩 에이전트가 있는 지금은 아이디어에서 구현까지의 시간이 6개월에서 12개월이 아니라 일주일 수준으로 줄어들 수 있다. 따라서 엔지니어도 제품 감각(Product Taste)과 비즈니스 감각(Business Sense)을 길러야 한다.

타릭은 더 과감하게 말한다. 예전에는 “절대 재작성하지 말라”가 정석이었지만, 이제는 재작성(Rewrite)이 좋은 선택이 될 수 있다. 특히 테스트 스위트(Test Suite)가 탄탄하다면 여러 구현을 동시에 만들어 비교하고, 가장 정확한 구현을 선택할 수 있기 때문이다.

3. Claude Tag: 팀 협업형 Claude

Claude Tag는 Slack 같은 팀 협업 도구 안에 들어간 Claude다. Claude Code가 개인이 터미널에서 사용하는 도구라면, Claude Tag는 팀 채널 안에서 여러 사람이 함께 조작하고 관찰하는 에이전트다.

Claude Tag의 핵심 특징은 세 가지다.

  1. 멀티플레이어(Multiplayer) — 한 Slack 채널에서 여러 팀원이 Claude에게 지시하고 결과를 함께 본다.
  2. 능동형(Proactive) — 매번 호출하지 않아도 버그 리포트를 감시하고 PR을 만들 수 있다.
  3. 팀 메모리(Team Memory) — 채널에서 알려준 선호와 규칙을 이후 작업에 계속 반영한다.

예를 들어 “이 채널의 모든 버그 리포트를 감시하고, 수정 PR을 만들고, 해당 코드 영역을 마지막으로 만진 엔지니어를 태그해줘”라고 시킬 수 있다. 그러면 Claude Tag는 채널이 유지되는 동안 계속 그 일을 수행한다.

Anthropic 내부에서는 Claude Tag가 제품 엔지니어링 PR의 65%를 처리하고 있다고 한다. 이는 단순한 보조 도구가 아니라 실제 개발 흐름의 중심으로 들어왔다는 의미다.

4. 우선순위 결정과 내부 도그푸딩

기능 구현 비용이 낮아지면 오히려 우선순위 결정이 더 어려워진다. 무엇이든 만들 수 있을 때, 정말 만들 가치가 있는 것을 골라야 하기 때문이다.

Anthropic은 이를 해결하기 위해 강한 도그푸딩(Dogfooding) 문화를 사용한다. 내부에서 제품을 매일 쓰고, 불편한 점이 있으면 다른 우회책을 찾기보다 제품 자체를 고친다.

외부 출시 전에는 내부 활성 사용자 수와 유지율(Retention) 기준을 본다. 사람들이 내부에서도 계속 쓰지 않는 기능이라면 외부에 출시하지 않는다. 이 기준이 명확하기 때문에 엔지니어들은 “출시 가능한 품질”이 무엇인지 더 잘 이해한다.

5. 코드 리뷰 자동화와 품질 관리

Anthropic은 모든 코드를 무작정 AI에게 맡기지 않는다. 핵심 영역에는 코드 소유자(Code Owner)가 있고, 해당 영역을 건드리는 PR은 여전히 사람이 직접 승인한다.

다만 외곽 영역의 변경은 점점 Claude Code의 코드 리뷰가 더 많이 담당하고 있다. 중요한 점은 이것이 하루아침에 이뤄진 변화가 아니라는 것이다. 처음에는 사람이 모든 리뷰를 했고, 이후 특정 파일이나 영역에서 Claude의 코드 리뷰가 문제를 100% 잡는다는 신뢰가 생긴 경우에만 사람 리뷰를 줄였다.

사고(Incident)가 발생하면 원인이 된 PR을 분석하고, 코드 리뷰가 그 문제를 잡도록 개선한다. 그리고 해당 PR을 평가셋(Eval Set)에 추가해, 이후 코드 리뷰 시스템이 같은 문제를 놓치지 않도록 만든다.

6. 새 모델을 신뢰하는 법

새 모델이 나오면 “이전 모델이 잘하던 일을 계속 잘할까?”라는 문제가 생긴다. Anthropic은 이를 감으로 판단하지 않고 평가셋으로 확인한다.

새 모델이 나오면 내부 평가와 외부 평가를 모두 돌려보고, 기존 모델보다 확실히 나은지 확인한 뒤 교체한다. Claude Code 팀 자체 평가도 있고, Anthropic 전체 저장소를 대상으로 하는 평가도 있다.

평가는 단순한 기능 성공 여부만 보지 않는다. 예를 들어 Claude Code가 “이제 잘 시간이야”라고 말하거나, “5개 중 2개를 끝냈는데 계속할까요?”처럼 불필요하게 멈추는 행동도 사용자 경험을 해친다. 그래서 이런 행동을 잡기 위한 행동 평가(Behavioral Eval)도 늘리고 있다.

7. 시스템 프롬프트 80% 경량화

타릭은 Claude Code의 최신 모델용 시스템 프롬프트가 약 80% 줄었다고 말한다. 이유는 최신 모델이 더 좋은 판단력을 갖게 되면서, 예전처럼 많은 예시와 강한 금지 규칙이 오히려 방해가 될 수 있기 때문이다.

예전에는 “프론트엔드 변경을 하면 항상 검증하라” 같은 규칙이 유용해 보였다. 하지만 실제로는 단순 문구 수정처럼 굳이 앱 전체를 띄워 검증할 필요가 없는 경우도 있다. “항상”이라는 규칙은 90%는 맞지만 10%에서는 틀릴 수 있고, 시스템 프롬프트는 모든 상황에 적용되므로 이런 예외가 모델을 혼란스럽게 만든다.

따라서 최신 프롬프트 설계는 “절대 하지 마라”를 많이 넣기보다, 맥락을 제공하고 모델이 판단할 여지를 주는 방향으로 바뀌고 있다.

8. 도구 설계 철학

Claude Code는 여러 도구(Tools)의 묶음이다. 하지만 Anthropic은 도구 수를 무작정 늘리기보다 줄이는 방향을 선호한다. 각 도구가 명확히 다른 기능을 가져야 Claude가 어떤 도구를 써야 할지 쉽게 판단할 수 있기 때문이다.

예전에는 검색용 grep, glob 같은 도구가 있었지만, 지금은 네이티브 Bash 사용으로 대체한 부분도 있다. 반면 파일 편집(File Edit) 도구는 남아 있다. 이유는 Claude가 파일을 변경할 때 사용자에게 “이 파일 변경을 승인할까요?”라는 명확한 UI를 보여주기 위해서다.

Auto Mode를 쓰는 고급 사용자에게는 파일 편집 도구가 덜 중요할 수 있지만, 신규 사용자에게는 변경 내용을 명확히 보여주는 UI가 여전히 중요하다.

9. Auto Mode와 보안

Auto Mode는 Claude가 장시간 작업을 할 수 있게 하면서도 위험한 행동을 줄이기 위한 기능이다. Anthropic 내부에서는 대부분의 사람이 Auto Mode를 사용한다고 한다.

Auto Mode는 사용자의 지시, 대화 맥락, 실행하려는 도구를 함께 보고 권한을 판단한다. 예를 들어 사용자가 “GitHub에 push해줘”라고 했다면 git push를 허용할 수 있지만, “push하지 마”라고 했다면 차단한다.

또한 샌드박스(Sandbox)와도 연결된다. 네트워크 요청처럼 샌드박스를 벗어나는 행동이 필요할 때, Auto Mode가 그 요청이 맥락상 타당한지 판단한다.

Anthropic은 Auto Mode를 수천 개의 평가와 외부 레드팀 테스트로 검증했고, 프롬프트 인젝션(Prompt Injection), 데이터 유출(Data Exfiltration) 같은 주요 위험을 낮추기 위해 보강했다고 설명한다. 다만 100% 완벽하다고 주장하지는 않는다.

10. 인간의 역할 변화와 조직 문화

AI가 구현을 많이 대신하면 개발자는 상실감을 느낄 수 있다. 타릭은 이 감정이 실제로 존재한다고 인정한다. 예전과 같은 일을 단순히 프롬프트 하나로 끝내는 데 머문다면 허무할 수 있다.

그가 제안하는 해법은 더 큰 야망을 갖는 것이다. 이전에는 시간이 부족해서 못 했던 더 큰 프로젝트, 더 높은 품질, 더 복잡한 문제에 도전해야 한다.

Anthropic 문화에서 중요한 문장도 나온다. “우리는 스스로와 협상하지 않는다.” 즉, 머릿속에서 미리 “이건 어려울 거야”, “트레이드오프가 있을 거야”라고 단정하고 포기하지 말라는 뜻이다. 먼저 야심찬 목표를 시도하고, 실제 트레이드오프가 나타나면 그때 판단하자는 문화다.

11. 뜻밖의 활용 사례

타릭은 Claude로 영상 편집을 한 사례를 소개한다. 강연 영상, 슬라이드 영상, 오디오 파일, HTML 슬라이드 원본을 Claude에게 주자, Claude는 전체 영상을 전사하고, 슬라이드 영상에 자동 업데이트 팝업이 끼어 있는 문제를 발견한 뒤, 실제 슬라이드 영상 대신 HTML 원본을 사용했다. 또한 무대 위 발표자를 동적으로 크롭하고, FFmpeg와 Remotion을 사용해 편집했다.

캣 우는 암벽등반 앱을 만들었다. 친구들과 등반 프로젝트를 기록하고, 여행지를 조사하며, 항공편, Mountain Project의 난이도 정보, Airbnb, 접근 거리까지 고려해 등반 여행을 계획한다. 기존 앱에서는 수동으로 클릭해야 했던 과정을 Claude Workflows로 자동화한 것이다.

전체 전사 펼치기

사이먼 윌리슨은 Anthropic의 타릭 시히파르와 캣 우를 소개하며, Claude Code와 최근 화제가 된 Fable에 대해 이야기하겠다고 말한다. 대화 직전 Fable 접근이 다시 가능해졌다는 농담도 덧붙인다.

Claude Code는 작년 2월 Claude Sonnet 3.7 출시 때 작은 항목으로 공개됐지만, 1년 반도 안 되는 기간에 개발 업무를 크게 바꿨다. 캣은 초기 Claude Code를 쓸 때는 모든 권한 요청을 꼼꼼히 확인하고, Claude가 어떤 파일을 봤는지 계속 감시해야 했다고 회상한다. 지금은 모델이 발전하면서 반복적 구현을 더 많이 위임하고, 사용자가 더 창의적이고 제품적인 문제를 생각할 시간이 생겼다고 말한다.

타릭은 Opus 4가 나왔을 때 Claude Code를 처음 써보고 Anthropic에서 일하고 싶어졌다고 말한다. 당시에는 권한 승인 버튼을 자주 눌러야 했지만, 지금은 Auto Mode가 너무 자연스러워져 예전의 수동 승인 과정을 잊을 정도라고 한다. 그는 이제 목표가 “더 빠르게”가 아니라 “이전보다 훨씬 높은 품질의 작업을 더 빠르게” 하는 것이라고 설명한다.

사이먼은 소프트웨어 엔지니어링이 오히려 더 어려워졌다고 말한다. 도구가 강력해진 만큼 자신에게 요구하는 야망의 수준도 높아졌기 때문이다.

캣은 과거에는 제품 매니저가 6개월 이상 고객 인터뷰, PRD, 엔지니어링 문서를 거쳐야 코드가 시작됐지만, 이제는 아이디어에서 구현까지의 시간이 일주일 수준으로 줄었다고 말한다. 그래서 엔지니어에게 제품 감각(Product Sense)과 비즈니스 감각(Business Sense)이 더 중요해졌다고 설명한다.

타릭은 예전 소프트웨어 공학의 금기였던 재작성(Rewrite)이 이제는 좋은 선택일 수 있다고 말한다. 코드베이스 자체가 사실상 명세(Spec)이기 때문에, 좋은 테스트 스위트가 있다면 기존 코드를 바탕으로 여러 구현을 만들고 비교할 수 있다는 것이다.

Claude Tag는 Slack 같은 협업 도구 안에 들어가는 Claude다. 기본적으로 멀티플레이어(Multiplayer)이며, 팀원들이 같은 채널에서 Claude에게 지시하고 결과를 함께 본다. 또한 능동형(Proactive)이어서 버그 리포트를 감시하고 PR을 만들며, 마지막으로 해당 코드를 수정한 엔지니어를 태그할 수 있다. 팀 메모리(Team Memory)도 있어서 채널에서 알려준 선호를 이후 작업에 반영한다.

Anthropic 내부에서는 Claude Tag가 제품 엔지니어링 PR의 65%를 처리하고 있다. Claude Code는 복잡한 작업을 대화형으로 반복할 때 강하고, Claude Tag는 사용자가 매번 직접 시작하지 않아도 팀을 대신해 능동적으로 작업할 때 강하다.

타릭은 Claude Tag가 비개발자에게도 유용하다고 말한다. 예를 들어 회사 Slack을 검색해 Fable 출시 시점을 확인하거나, 제품 관련 지표를 찾거나, 마케팅 팀이 특정 기능의 동작을 이해하도록 코드베이스를 클론해 기능을 설명하고 사용 장면을 녹화할 수 있다.

팀 협업에서는 Claude Tag가 첫 구현을 만들고, 디자이너가 피드백을 주고, 엔지니어가 마무리해 배포하는 흐름이 가능하다. 모두가 같은 채널에서 Claude 사용 방식을 보기 때문에, 공개적으로 자랑스러울 수준의 지시를 하려는 사회적 압력도 생긴다.

우선순위 결정에 대해 캣은 도그푸딩(Dogfooding)을 강조한다. Anthropic은 내부에서 매일 제품을 쓰고, 불편하면 다른 해결책을 찾는 대신 제품을 고친다. 외부 출시 전에는 내부 활성 사용자와 유지율 기준을 본다. 기능이 충분히 다듬어지지 않으면 사용자가 이탈하고, 그런 기능은 출시하지 않는다.

예상 밖으로 성공한 기능으로는 원격 제어(Remote Control)가 언급된다. 이 기능은 모바일이나 웹 브라우저에서 로컬 CLI의 Claude Code 세션을 제어하게 해준다. 캣은 처음에는 필요성을 잘 이해하지 못했지만, 많은 사용자가 노트북을 전원에 연결해 둔 채 휴대폰으로 소파에서 Claude Code를 제어한다는 것을 보고 가치를 이해하게 됐다고 말한다.

코드 리뷰에서는 핵심 영역에 코드 소유자(Code Owner)가 있다. 시스템 프롬프트처럼 중요한 영역은 반드시 담당자의 승인을 받아야 한다. 모든 PR에는 GitHub 봇 기반 코드 리뷰가 붙고, 복잡한 PR은 설명용 아티팩트(Artifact)를 만들어 리뷰를 돕기도 한다.

캣은 장기적으로 사람이 항상 루프 안에 있을 필요는 없는 방향을 목표로 한다고 말한다. 단, 핵심 변경은 여전히 사람이 본다. 외곽 영역부터 Claude Code 코드 리뷰가 충분히 문제를 잡는다는 신뢰가 생긴 뒤 사람 리뷰를 줄였다. 사고가 나면 원인 PR을 평가셋에 추가해 이후 회귀를 막는다.

새 모델을 신뢰하는 방법에 대해 캣은 평가셋(Eval Set)을 강조한다. 새 모델이 나오면 전체 평가를 돌려 기존 모델보다 나은지 확인하고 교체한다. Auto Mode의 경우 Anthropic 내부 사용자 전체와 외부 레드팀을 대상으로 프롬프트 인젝션과 악성 입력 환경을 만들어 테스트했다.

제품별 평가에서는 기능 수행 능력뿐 아니라 사용자 경험도 본다. Claude Code가 작업 중간에 불필요하게 멈추거나, “이제 잘 시간” 같은 말을 하는 행동은 사용자가 싫어한다. 이런 행동을 잡기 위한 행동 평가(Behavioral Eval)를 계속 늘리고 있다.

시스템 프롬프트에 대해 타릭은 최신 모델용 Claude Code 프롬프트가 약 80% 줄었다고 말한다. 이유는 최신 모델이 더 많은 판단력을 가지면서 예시와 강한 제약이 오히려 방해가 되기 때문이다. 예전 모델은 예시가 필요했지만, 최신 모델은 주어진 예시보다 더 창의적인 해결책을 낼 수 있다.

캣은 프롬프트 지시가 90%는 맞아도 10% 예외가 있으면 문제가 된다고 설명한다. 예를 들어 “프론트엔드 변경은 항상 검증하라”는 말은 대체로 맞지만, 단순 문구 변경에는 과할 수 있다. 따라서 “항상” 같은 강한 표현보다 맥락을 주고 모델이 판단하게 하는 쪽이 낫다.

단, 이 경량 프롬프트는 frontier 모델에만 적용된다. 구형 모델은 판단력이 부족할 수 있어 여전히 더 긴 시스템 프롬프트를 사용한다.

도구 설계에서는 도구 수를 줄이고 각 도구의 역할을 명확히 하는 방향을 선호한다. 검색용 grep, glob 도구 일부는 Bash 사용으로 대체됐다. 파일 편집 도구는 사용자가 변경 사항을 명확히 승인할 수 있는 UI 때문에 유지되고 있다.

Auto Mode에 대해 캣은 Anthropic 내부 대부분의 사람이 사용한다고 말한다. 장시간 작업을 안전하게 수행하는 가장 좋은 방식으로 보고 있으며, 수천 개 평가와 외부 레드팀을 통해 보강했다고 설명한다. 주요 위험인 프롬프트 인젝션과 데이터 유출은 평균적인 사람 리뷰어보다 낮은 위험을 보인다고 주장한다. 다만 100% 완벽하다고는 하지 않는다.

타릭은 Auto Mode가 대화 맥락과 도구 호출을 함께 보고 권한을 판단한다고 설명한다. 사용자가 push를 요청하면 허용할 수 있지만, push하지 말라고 했다면 차단한다. 또한 샌드박스와 연결되어 네트워크 요청처럼 샌드박스를 벗어나는 행동도 맥락에 따라 판단한다.

Claude Tag가 안전하게 작동하는 이유도 Auto Mode와 관련 있다. Slack 봇은 다양한 사용자가 입력을 넣을 수 있어 공격 표면이 넓다. Anthropic은 권한, 샌드박스, 레드팀, 강화학습(RL) 등을 조합한 “스위스 치즈”식 방어를 사용한다고 설명한다.

추가 보안 기능으로는 신뢰할 수 있는 기기(Trusted Devices), 원격 환경의 자격 증명 주입(Credential Injection)이 언급된다. 예를 들어 Claude Code가 Datadog에 접근해야 하지만 실제 Datadog 토큰은 보지 못하게 하고, 요청 시 프록시가 토큰을 삽입하는 방식이다.

인간의 역할 변화에 대해 타릭은 상실감이 실제로 있다고 인정한다. 예전과 같은 일을 단순히 프롬프트로 끝내는 데 머물면 허무할 수 있다. 이를 극복하려면 더 큰 야망을 가져야 한다. 더 큰 프로젝트, 더 높은 품질, 더 어려운 문제를 시도해야 한다는 것이다.

캣은 제품 매니저 역할도 매달 바뀌고 있다고 말한다. 팀의 PM들은 엔지니어, 디자이너, PM이 섞인 역할을 한다. 아이디어가 있는데 엔지니어가 바로 움직이지 않으면 직접 프로토타입을 만들고, 디자인이 부족하면 첫 디자인을 만들고, 출시 일정과 상태 업데이트도 자동화한다.

Claude가 놀라웠던 사례로 타릭은 영상 편집을 든다. 강연 영상, 슬라이드 영상, 오디오, HTML 슬라이드를 주자 Claude는 전체 영상을 전사하고, 슬라이드 영상의 팝업 문제를 발견해 HTML 원본을 대신 사용했다. 발표자의 위치를 추적해 동적으로 크롭하고, FFmpeg와 Remotion으로 편집했다. 이 작업은 Fable로 거의 한 번의 프롬프트에 가까운 방식으로 이뤄졌다고 한다.

아직 부족한 점으로 캣은 디자인과 UX 감각을 꼽는다. 기능 동작은 잘 구현하지만 패딩이나 인터페이스의 즐거움은 아직 부족하다고 본다. 타릭은 더 넓은 현실 세계와 상호작용하고 과학 실험까지 조율하는 능력을 기대한다고 말한다.

Anthropic의 생산성 문화로 캣은 공개 채널을 강조한다. Claude Tag는 공개 채널이 많을수록 더 많은 맥락을 검색해 정확한 답을 낼 수 있다. 타릭은 “스스로와 협상하지 않는다”는 문화를 말한다. 머릿속에서 미리 트레이드오프를 상상해 야심찬 일을 포기하지 말고, 실제 제약이 나타날 때까지 먼저 시도하라는 뜻이다.

재미로 만든 프로젝트로 타릭은 자신과 친구들을 캐릭터로 한 2D Street Fighter 스타일 게임을 소개한다. Claude Code가 Gemini를 프롬프트해 스프라이트와 애니메이션을 만들고, 프레임을 검증하며, JSON 히트박스까지 그린다고 한다.

캣은 암벽등반 앱을 소개한다. 친구들과 등반 프로젝트를 기록하고, Workflows를 이용해 여행지, 직항 항공편, Mountain Project의 난이도, Airbnb, 짧은 접근 거리까지 조사한다. 사이먼은 이를 “암벽등반용 JIRA를 바이브 코딩하는 것”이라고 표현한다.

청중 질문에서는 평가 도구와 메모리 설계가 다뤄진다. 캣은 평가 도구 자체보다 고품질 평가셋을 만드는 역량이 더 큰 병목이라고 말한다. Claude Tag의 메모리는 현재 채널별로 공유되며, 각 세션이 메인 메모리에 기여할 수 있다. 타릭은 현재 Claude Tag의 메모리가 채널당 Markdown 파일 형태라고 설명한다.

마지막으로 사이먼은 캣 우와 타릭 시히파르에게 감사를 전하며 대화를 마무리한다.
