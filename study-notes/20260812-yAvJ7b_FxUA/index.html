개념 왜 중요한가 한 줄
포스트 트레이닝(Post-Training) 범용 모델을 내 제품의 취향, 기준, 전문성에 맞게 바꾸는 핵심 방법 API를 빌려 쓰는 단계에서 벗어나 내 지능을 소유하는 과정
데이터 품질(Data Quality) 튜닝 성능은 데이터 양보다 품질에 좌우됨 좋은 데이터 판단은 ML팀만이 아니라 제품팀이 해야 함
RAG 자주 바뀌는 사실과 내부 데이터를 모델에 연결하는 방법 모델이 모르는 최신 정보는 학습보다 검색 결합으로 해결
지도 미세조정(SFT) 출력 형식, 구조, 기본 동작을 교정하는 데 적합 “이렇게 답해야 한다”는 예시를 모델에 가르침
선호 튜닝(Preference Tuning, DPO) 제품 고유의 취향과 판단 기준을 반영 좋아요/싫어요, 선택 로그가 제품 취향의 재료가 됨
강화학습(RL) 특정 도메인의 전문성과 목표 달성 능력을 높이는 데 사용 보상 함수가 잘못되면 모델이 목표를 편법으로 달성함
보상 해킹(Reward Hacking) 모델이 의도와 다른 방식으로 점수를 최적화하는 위험 “컴파일 오류 최소화”를 시켰더니 코드를 0줄 작성한 사례
증류(Distillation) 큰 모델의 능력을 작은 모델로 옮겨 비용과 속도를 개선 운영 비용을 5~10배 낮출 수 있는 전략
학습-서빙 정렬(Training-to-Serving Alignment) 학습 때 좋던 모델이 실제 서비스에서 품질 저하될 수 있음 학습 스택과 서빙 스택의 수치 계산 차이를 조심해야 함
도입 시점 너무 이른 도입보다 PMF 이후가 효과적 PMF 이후 축적되는 고품질 제품 데이터가 연료가 됨

내가 모를 만한 것 / 처음 보는 것

  • 포스트 트레이닝(Post-Training) — 이미 학습된 기반 모델을 특정 제품, 도메인, 사용자 취향에 맞게 추가 훈련하는 과정.
  • RAG(Retrieval-Augmented Generation) — 모델이 내부 문서나 데이터베이스를 검색한 뒤 답변하게 만드는 방식.
  • 지도 미세조정(Supervised Fine-Tuning, SFT) — 입력과 정답 예시를 이용해 모델의 출력 패턴을 교정하는 학습.
  • 선호 튜닝(Preference Tuning) — 사용자의 선택, 평가, 비교 데이터를 바탕으로 모델이 더 선호되는 답을 내도록 조정하는 방식.
  • DPO(Direct Preference Optimization) — 강화학습보다 단순한 방식으로 선호 데이터를 모델에 반영하는 기법.
  • 강화학습(Reinforcement Learning, RL) — 보상 신호를 기준으로 모델이 목표 달성 행동을 학습하는 방식.
  • 보상 함수(Reward Function) — 모델의 결과가 얼마나 좋은지 점수화하는 기준.
  • 보상 해킹(Reward Hacking) — 보상 점수는 높지만 실제 의도와 어긋나는 답을 모델이 찾아내는 현상.
  • 증류(Distillation) — 큰 교사 모델(Teacher Model)의 능력을 작은 학생 모델(Student Model)에 옮기는 기법.
  • 평가(Evals) — 감으로 보는 대신 반복 가능한 테스트 세트와 기준으로 모델 품질을 측정하는 체계.
  • 바이브 평가(Vibe Evaling) — 창업자나 팀원이 결과를 보고 “느낌상 괜찮다”고 판단하는 비체계적 평가.
  • RL 롤아웃(RL Rollout) — 강화학습에서 모델이 행동을 수행하고 그 결과를 수집하는 실행 과정.
  • 하네스(Harness) — 에이전트, 도구, 평가 환경을 묶어 모델이 작업을 수행하게 하는 실행 프레임워크.

  7. 학습 스택과 서빙 스택이 다르면 행렬 곱셈(Matrix Multiplication), 라이브러리, 수치 정밀도(Numerics), 최적화 차이로 품질이 조용히 떨어질 수 있다고 경고한다.

1. 왜 포스트 트레이닝이 중요한가

Lin Qiao는 Fireworks AI가 수많은 AI 애플리케이션을 운영하는 플랫폼이기 때문에, 스타트업부터 대기업까지 AI 앱 개발 패턴을 폭넓게 본다고 말한다.

그녀가 보는 가장 큰 변화는 애플리케이션 개발 비용과 시간이 급격히 줄었다는 점이다. 예전에는 좋은 아이디어를 실제 제품으로 만들고 운영 규모까지 키우려면 강한 제품 엔지니어, PM, 여러 분기의 시간이 필요했다. 지금은 코드를 거의 몰라도 한 사람이 몇 주 만에 비슷한 수준의 앱을 만들 수 있다.

이 변화는 좋은 점도 있지만, 동시에 경쟁 장벽을 낮춘다. 누구나 비슷한 앱을 빠르게 만들 수 있다면, 단순히 범용 폐쇄형 API(Off-the-Shelf Black-Box API)를 붙여 만든 앱은 오래 버티기 어렵다.

그래서 Lin은 기업이 자기만의 방어력을 만들려면 제품에 담긴 판단(Judgment), 취향(Taste), 확신(Conviction), 고객 이해(Customer Understanding) 를 모델 자체에 녹여야 한다고 강조한다.

즉, 포스트 트레이닝은 단순한 기술 옵션이 아니라, AI 시대에 회사의 차별성을 지키는 전략이다.

2. “지능을 소유한다”는 말의 의미

Lin은 “지능을 빌리지 말고 소유하라(owning intelligence, not renting it)”는 말을 여러 단계로 설명한다.

첫 출발은 데이터다. 지능은 데이터의 파생물이다. 현재 우리가 쓰는 기반 모델(Foundation Model)은 공개 데이터와 일반적인 라벨 데이터로 만들어졌다. 하지만 각 회사는 특정 고객, 특정 문제, 특정 워크플로우를 다룬다.

따라서 각 회사가 해야 할 일은 다음과 같다.

  1. 제품에서 나오는 고품질 운영 데이터(Production Data)를 선별한다.
  2. 필요하면 합성 데이터(Synthetic Data)를 만들어 데이터를 보강한다.
  3. 그 데이터를 기존 모델 위에 반영해 모델 가중치(Weights)를 소유한다.
  4. 모델을 실제 서비스에 올리고 A/B 테스트로 제품 지표가 개선되는지 본다.
  5. 다시 데이터를 모아 반복한다.

여기서 핵심은 모델을 한 번 학습시키고 끝나는 것이 아니다. 데이터 → 모델 → 서빙 → 제품 지표 → 다시 데이터로 이어지는 반복 루프를 운영하는 것이다.

3. 프롬프트에서 RL까지의 단계

Lin은 처음부터 포스트 트레이닝을 하라고 말하지 않는다. AI 제품 개발에는 자연스러운 단계가 있다.

첫 단계는 프롬프트(Prompt)다. 기존 모델을 그대로 쓰면서 몇 개의 예시(Few-Shot)를 넣어 아이디어를 빠르게 검증한다. 이 단계는 매우 빠르다.

다음은 RAG다. RAG를 쓰면 모델을 회사 내부 데이터, 문서, 지식베이스에 연결할 수 있다. 특히 자주 바뀌는 정보나 제품별 데이터는 모델을 다시 학습시키는 것보다 RAG가 적합하다.

그다음은 지도 미세조정(Supervised Fine-Tuning, SFT)이다. 어느 정도 데이터가 쌓이면, “우리 제품에서는 이런 입력에 이런 구조로 답해야 한다”는 예시를 모델에 학습시킨다. 출력 형식이나 기본 동작을 안정화하는 데 좋다.

이후에는 선호 튜닝(Preference Tuning) 또는 DPO(Direct Preference Optimization)로 간다. 사용자의 좋아요/싫어요, 선택, 비교, 클릭, 수정 행동 등을 통해 제품의 취향을 모델에 반영한다.

마지막으로 강화학습(Reinforcement Learning, RL)은 특정 도메인 전문성을 키우는 데 쓰인다. 법률, 금융, 의료, 고객지원, 채용, 마케팅, 영업처럼 분야별로 정답 기준과 업무 방식이 다르기 때문이다.

Lin은 이 흐름이 사람이 배우는 방식과 비슷하다고 비유한다. 사람도 먼저 책을 읽으며 정답과 오답을 배우고, 시간이 지나면서 자기만의 판단과 취향을 만들고, 이후 특정 직업이나 분야에서 전문성을 쌓는다.

4. 어떤 문제에 어떤 기법을 써야 하는가

Lin은 포스트 트레이닝 기법을 유행어처럼 쓰면 안 되고, 실제 문제가 무엇인지에 맞춰 선택해야 한다고 말한다.

모델이 사실을 모르는 문제이고 그 사실이 자주 바뀐다면 RAG가 적합하다. 예를 들어 재고, 가격, 정책, 내부 문서, 고객별 상태처럼 계속 변하는 정보는 모델에 박아 넣기보다 검색해서 넣는 편이 낫다.

모델 출력 형식이나 구조가 자꾸 틀린다면 SFT가 좋다. 예를 들어 JSON 형식, 리포트 형식, 상담 답변 톤, 업무 처리 순서 같은 것은 예시 데이터로 교정할 수 있다.

답변 품질이 제품의 고유한 취향과 관련된다면 선호 튜닝이 필요하다. 같은 질문에도 어떤 답이 더 좋은지는 회사마다 다르다.

모델이 특정 전문 문제에서 약하다면 RL을 사용한다. 단순히 말투나 포맷이 아니라, 실제로 더 어려운 문제를 풀게 만드는 데 초점이 있다.

마지막으로 모델은 좋은데 너무 느리거나 비싸다면 증류(Distillation)를 사용한다. 큰 교사 모델의 능력을 작은 학생 모델로 옮기면, 실제 운영에서 속도와 비용을 개선할 수 있다.

5. 팀들이 자주 막히는 지점

첫 번째 실패 지점은 데이터다. 많은 팀이 데이터를 많이 넣으면 좋아질 것이라고 생각하지만, Lin은 양보다 품질이라고 강조한다. 저품질 데이터를 많이 넣으면 오히려 원하는 결과에 도달하지 못한다.

특히 데이터 품질은 연구팀이나 ML팀만 판단할 수 있는 문제가 아니다. 제품이 어떤 답을 좋아하는지, 고객이 무엇을 원하는지, 어떤 응답이 브랜드에 맞는지는 제품팀이 가장 잘 안다. 그래서 생성형 AI 시대에는 제품팀과 ML팀의 경계가 점점 가까워진다.

두 번째 실패 지점은 평가(Evals)다. 많은 창업자가 바쁘기 때문에 모델 결과를 보고 “느낌상 괜찮다”는 방식으로 판단한다. Lin은 이것을 바이브 평가(Vibe Evaling)라고 부른다.

하지만 그 느낌 자체도 사실은 창업자의 판단 기준이다. 중요한 것은 그 판단을 반복 가능한 평가 체계로 바꾸는 것이다. 전통 소프트웨어 개발에서 단위 테스트와 통합 테스트가 품질을 보장하듯, AI 모델도 자체 평가 세트와 기준이 있어야 한다.

세 번째 실패 지점은 RL 환경이다. 시뮬레이션이 현실을 제대로 반영하지 못하면, 모델은 엉뚱한 방향으로 점수를 올린다. 이를 보상 해킹(Reward Hacking)이라고 한다.

대표 사례가 “컴파일 오류를 최소화하라”는 목표였다. 모델은 코드를 0줄 작성했다. 그러면 컴파일 오류는 없다. 하지만 사용자가 원하는 것은 작동하는 코드이지, 아무 코드도 없는 상태가 아니다.

6. 학습 모델을 서비스에 올릴 때 생기는 품질 저하

Lin은 모델을 학습시키는 것만으로 실험이 끝나는 것이 아니라고 말한다. 최종 판단은 제품 지표가 움직이는지 여부다. 그래서 학습된 모델은 실제 서빙(Serving) 계층에 올라가 A/B 테스트를 거쳐야 한다.

이때 중요한 문제가 학습-서빙 정렬(Training-to-Serving Alignment)이다.

모델은 거대한 수학 계산이다. 학습할 때와 서빙할 때 사용하는 라이브러리, 행렬 곱셈 방식, 수치 정밀도, 최적화 방식이 다르면 결과가 달라질 수 있다. 학습 환경에서는 좋았던 모델이 실제 서비스에서는 품질이 조용히 떨어질 수 있다.

따라서 포스트 트레이닝을 할 때는 학습 스택과 서빙 스택을 따로 보지 말고, 실제 운영까지 포함한 전체 파이프라인으로 봐야 한다.

7. 포스트 트레이닝 사례

Lin은 Cursor를 대표 사례로 든다. Cursor는 모델 공급망을 스스로 통제하고 싶어 했고, 사용자 참여와 선호 데이터도 풍부했다. 그래서 2025년 초부터 포스트 트레이닝에 깊게 들어갔고, 몇 달마다 새로운 모델을 발표했다.

Cursor의 목표는 프런티어 모델(Frontier Model) 수준과 경쟁하는 것이다. Lin은 Composer 2, Composer 2.5 같은 결과가 매우 인상적이며, 집중력과 올바른 도구가 있으면 충분히 가능하다고 말한다.

의료 분야에서는 Doximity를 언급한다. 의사가 깊은 의료 질문을 하고, 증상과 약물, 부작용을 연결하며, 의료 연구를 종합하는 클리닉 AI(Clinic AI)를 만든 사례다. Stanford-Harvard 클리닉 안전 벤치마크에서 좋은 성과를 냈다고 한다.

보안 분야에서는 Factory를 예로 든다. 코딩 보안은 허용 오차가 낮은 어려운 분야다. Factory는 보안 영역 벤치마크에서 좋은 성과를 내는 모델을 튜닝했다.

또 Jen Spark는 전문가용 딥 리서치와 슬라이드 생성을 제공하는 범용 협업(Co-Work) 애플리케이션으로, 프런티어 모델과 경쟁하면서도 비용을 5~10배 낮춘 사례로 소개된다.

8. 코딩을 넘어 모든 업무 도메인으로 확장

Lin은 2025년이 코딩 AI의 해였다고 말한다. Fireworks는 많은 코딩 회사가 중간 학습(Mid-Training)과 포스트 트레이닝을 통해 강한 모델을 만드는 것을 지원했다.

하지만 이제는 코딩만의 이야기가 아니다. 법률, 금융, 마케팅, 채용, 영업, 고객지원, 의료 등 다양한 협업 도메인에서 포스트 트레이닝이 시작되고 있다.

각 회사는 자기 분야에서 고유한 문제를 풀고, 고유한 기준으로 좋은 답을 정의한다. 이 기준을 모델에 심는 것이 앞으로의 경쟁력이 된다.

Lin은 앞으로 수백만 개의 특화 모델(Specialized Model)이 생길 수 있다고 본다. 하나의 앱, 하나의 유스케이스마다 특화 모델이 존재할 수 있다는 관점이다.

9. 비용 문제와 “파산으로 스케일하지 않기”

포스트 트레이닝은 품질만의 문제가 아니다. 비용 문제이기도 하다.

스타트업은 사용자가 늘수록 추론 비용(Inference Cost)이 폭증할 수 있다. 대기업도 마찬가지다. 기존 고객 트래픽이 큰 회사가 AI 기능을 전면 배포하면 비용 부담이 너무 커질 수 있다. Lin은 CFO가 AI 기능 출시를 막는 경우도 있다고 말한다.

그래서 포스트 트레이닝과 증류는 비용을 낮추는 전략이 된다. 같은 예산으로 5~10배 더 많은 트래픽을 감당할 수 있다면, 단위 경제성(Unit Economics)이 훨씬 좋아진다.

Lin의 표현대로라면, AI 회사는 “스케일하다가 파산하는 것”을 피해야 한다.

10. 언제 포스트 트레이닝을 시작해야 하는가

Q&A에서 Vercel의 Raj는 포스트 트레이닝을 언제 시작해야 하는지 묻는다. 비용이 커졌을 때인지, 사용량이 폭증할 때인지, 프런티어 모델보다 2% 더 좋아지는 것이 투자할 만큼 가치 있는지에 대한 질문이다.

Lin의 답은 명확하다. AI 제품에서는 제품-시장 적합성(Product-Market Fit, PMF)과 확장 가능한 사업(Scalable Business)이 서로 다른 단계가 되었다.

SaaS 시대에는 PMF를 찾으면 그대로 확장하면 됐다. 하지만 AI 시대에는 PMF를 찾았다고 바로 건강한 사업이 되는 것은 아니다. 추론 비용과 모델 의존성 때문이다.

초기에는 프런티어 모델을 써서 빠르게 PMF를 찾는 것이 합리적이다. 이때는 비용을 감수하고 제품 검증에 집중한다. 하지만 PMF를 찾은 뒤에는 제품 표면에서 의미 있는 고품질 데이터가 쌓이기 시작한다. 이 데이터가 포스트 트레이닝의 연료가 된다.

PMF 이후 회사는 두 가지를 고민한다.

  1. 경쟁 우위를 계속 유지할 수 있는가.
  2. 매출과 비용 구조가 건강한가.

포스트 트레이닝은 이 두 문제를 동시에 해결할 수 있다. 제품의 고유한 취향과 사용자 데이터를 모델에 코드화하면 경쟁자가 쉽게 훔칠 수 없다. 동시에 비용을 5~10배 낮추면 같은 예산으로 훨씬 큰 트래픽을 감당할 수 있다.

11. 좋은 보상 신호는 어떻게 만드는가

Q&A에서 좋은 보상 신호(Reward Signal)의 예시에 대한 질문이 나온다.

Lin은 보상을 코드처럼 생각하라고 답한다. 보상은 하나의 점수가 아니라 여러 평가 기준(Rubric)의 조합이다.

예를 들어 채용 에이전트(Recruiting Agent)를 만든다면 후보자 평가 기준은 회사마다 다르다. 어떤 회사는 후보자의 배고픔, 거절을 받아들이지 않는 태도, 벽을 부수고 나아가는 성향을 중요하게 볼 수 있다. 또 다른 기준은 빠르게 만들고 진척을 내는 능력일 수 있다.

각 기준을 점수화하고, 회사만의 방식으로 가중치를 섞는다. 바로 이 조합이 회사의 고유한 비밀 소스(Secret Sauce)가 된다.

이것이 산업에서 일어나는 변화이고, 저희가 보고 있는 흐름이며, 포스트 트레이닝이 여러분에게 중요할 수 있는 이유입니다.

아마 “지능을 빌리지 말고 소유하라(Own Your Intelligence, Not Rent It)”는 말을 많이 들어보셨을 겁니다. 자기 지능을 소유한다는 것은 여러 의미가 있습니다.

첫째, 데이터에서 시작합니다. 지능은 데이터의 파생물입니다. 우리가 사용하는 기반 모델(Foundation Model)은 공개 데이터와 일반적인 과제를 해결하는 라벨 데이터 위에 만들어졌습니다. 하지만 여러분은 특정 과제를 해결하고 있습니다. 그래서 회사를 만들고 사업을 하는 것입니다. 고품질의 운영 데이터(Production Data)를 선별하고, 필요하면 합성 데이터(Synthetic Data)를 만들어 보강하는 것이 자기 지능을 소유하는 첫 단계입니다.

데이터를 확보한 다음에는 그 데이터를 모델로 바꿔야 합니다. 기존 모델 위에 쌓고, 가중치(Weights)를 소유해야 합니다. 이를 위해 여러 기술을 사용할 수 있습니다. 각 기술은 서로 다른 문제를 해결하도록 설계되어 있고, 서로 조합될 수도 있습니다.

특정 문제를 잘 해결하는 자기 모델을 갖게 되면, 그다음에는 서빙(Serving)을 해야 합니다. 먼저 A/B 테스트를 통해 실제 제품 지표가 움직이는지 확인하고, 다시 이 루프로 돌아가야 합니다.

물론 처음부터 포스트 트레이닝에 뛰어들 필요는 없습니다. 여러 단계가 있습니다.

먼저 프롬프트(Prompt)입니다. 모두가 프롬프트에서 시작합니다. 모델을 있는 그대로 쓰고, 퓨샷(Few-Shot) 방식으로 아이디어를 빠르게 시험합니다. 다음으로 RAG를 사용해 AI 사용을 자기 데이터에 접지(Grounding)합니다. 이 단계에서 많은 컨텍스트 엔지니어링(Context Engineering)을 할 수 있습니다. 이런 단계는 몇 분에서 몇 시간의 상호작용으로 진행됩니다.

그다음에는 데이터가 조금 있으니, 이 데이터가 모델을 우리 제품에 더 잘 맞게 만드는지 보고 싶어집니다. 이때 지도 미세조정(Supervised Fine-Tuning, SFT)을 시작합니다. 보통 몇 시간이 걸립니다.

이후에는 모델이 우리 제품의 개인화된 취향, 고유한 선택을 반영하길 원합니다. 그래서 사용자 상호작용에서 수집한 선호 정보, 예를 들어 좋아요, 싫어요 같은 데이터를 사용해 모델이 제품의 취향을 배우게 합니다.

마지막으로 모델이 특정 도메인의 전문성을 이해하고 담아내도록 만들고 싶어집니다. 법률, 금융, 의료, 고객지원, 채용, 마케팅, 영업 등 어떤 영역이든 가능합니다. 한 산업 안에도 수많은 하위 도메인이 있습니다. 이 모든 것이 여러분 제품의 고유한 부분입니다. 여기서 많이 듣는 강화학습(Reinforcement Learning, RL)이 사용됩니다. RL은 전문성을 향해 모델을 만드는 방식입니다.

이 흐름은 사람이 지식을 배우는 방식과도 비슷합니다. 사람은 문헌을 읽으며 많은 지식을 배웁니다. 문헌에는 무엇이 맞고 무엇이 틀린지 나옵니다. 이는 SFT와 비슷합니다.

성장하면서 우리는 특정 문제를 어떻게 접근할지에 대한 자기 취향과 판단을 발전시킵니다. 이는 선호 학습이나 DPO(Direct Preference Optimization)와 비슷합니다. 시간이 지나면 특정 영역에 능숙해집니다. 회계사가 되어 재무 데이터를 깊게 이해하거나, 치과의사가 되어 치과 진료의 세부를 배우는 것과 같습니다.

서로 다른 기술은 서로 다른 문제를 해결합니다. 모델이 사실을 모르고, 그 사실이 동적이라면 보통 RAG로 해결합니다.

하지만 모델 출력이나 구조가 잘못된다면 데이터를 선별해 SFT로 고칩니다. 모델 답변의 품질이 제품의 개인적 취향이나 고유한 기준과 관련된다면 선호 튜닝(Preference Tuning)을 사용합니다. 모델이 해결하려는 특수 문제에서 약하다면 강화학습을 사용합니다.

모델의 최종 결과가 너무 느리거나 비싸다면 증류(Distillation)를 사용합니다. 교사 모델(Teacher Model)이 훨씬 작은 학생 모델(Student Model)을 가르치게 해서 더 빠르고 경제적으로 만듭니다. 물론 증류는 LLM, VLM, 이미지 생성 모델에 따라 의미가 조금씩 다릅니다.

많은 팀이 이런 기술을 시험하려고 하지만, 돈과 시간을 쓰고도 원하는 결과에 도달하지 못해 불만족할 수 있습니다. 좌절할 수 있는 지점들이 있습니다.

데이터 측면에서는, 데이터가 튜닝의 본질이지만 양이 가장 중요한 것은 아닙니다. 실제로는 품질이 가장 중요합니다. 많은 데이터를 무작정 학습 과정에 넣는다고 좋은 결과가 나오는 것은 아닙니다. 데이터 품질을 통제해야 합니다.

데이터 품질을 가장 잘 판단하는 사람은 누구일까요? 사실 제품팀입니다. 생성형 AI 이전에는 제품팀과 연구팀 또는 ML팀이 별도 조직이었습니다. 하지만 이제는 함께 손잡고 일해야 합니다. 요즘 생성형 AI 모델을 포스트 트레이닝할 때는 제품팀이 데이터 품질에 대한 판단을 해야 하고, 좋은 결과를 보장하기 위해 깊이 관여해야 합니다.

두 번째는 평가(Evals)입니다. 여러분은 모두 바쁘고 빠르게 출시해야 하기 때문에, 많은 평가는 바이브 평가(Vibe Evaling)가 됩니다.

창업자가 결과를 보고 “맞는 것 같은가, 아닌가”를 느끼는 방식입니다. 사실 이것도 판단입니다. 최종 결과에 자기 판단을 적용해 좋은지 아닌지 결정하는 것입니다. 중요한 것은 그 판단을 체계적인 평가로 바꾸는 것입니다. 전통적인 소프트웨어 개발에서 단위 테스트(Unit Test)와 통합 테스트(Integration Test)로 품질을 보장하는 것과 다르지 않습니다. 포스트 트레이닝을 생각한다면, 자기 판단을 반복 가능한 프로세스로 만드는 평가 체계를 갖추는 것이 매우 중요합니다.

강화학습을 할 때는 엉성한 RL 환경(Sloppy RL Environment)도 문제가 됩니다. 시뮬레이션이 현실을 제대로 반영하지 않으면 모델은 나쁜 시뮬레이션 위에서 점수를 올리는 방향으로 최적화합니다. 보상 해킹(Reward Hacking) 같은 이상한 일도 생깁니다.

재미있는 보상 해킹 사례가 있습니다. 저희가 모델에게 컴파일 오류를 최소화하는 코드를 생성하라고 했습니다. 모델이 무엇을 했을까요? 코드 0줄을 생성했습니다. 컴파일 오류는 없습니다. 하지만 우리가 원한 것은 절대 아닙니다. 이것이 보상 해킹의 한 예입니다. 모델은 매우 똑똑해서 목표를 달성하기 위해 다양한 방법을 시도하지만, 그 방식이 우리가 원하는 것과 다를 수 있습니다. 이런 디테일에 주의하고, 모델이 여러분을 앞지르지 못하게 해야 합니다.

실험 과정도 생각해야 합니다. 모델 학습이 실험의 끝이 아닙니다. 최종 판단자는 제품 지표가 움직이는지 여부입니다. 그래서 최종 모델을 서빙 계층으로 가져가 A/B 테스트를 해야 합니다.

이 전환은 매우 중요합니다. 학습 스택에서 서빙 스택으로 옮길 때 두 환경이 정렬되어 있지 않으면 품질이 떨어질 수 있기 때문입니다. 모델은 수많은 계산과 수학으로 구성되어 있습니다. 행렬 곱셈(Matrix Multiplication) 방식, 사용하는 라이브러리, 수치 계산(Numerics), 최적화가 다르면 결과가 달라집니다. 따라서 학습 결과가 재현되지 않거나, 서빙 중 정밀도가 손실될 수 있습니다. 이 정렬은 매우 중요합니다.

포스트 트레이닝의 선구자들이 있습니다. Cursor가 그중 하나입니다. Cursor는 2025년 초부터 이 흐름에 올라탔습니다. 이유는 여러 가지입니다. 하나는 모델 공급에서 자기 운명을 통제하고 싶었다는 점입니다. 또 사용자 참여가 많고, 고객 선호와 데이터도 많이 이해하고 있었습니다. 이것이 여정의 시작이 되었습니다. 그들은 중간 학습(Mid-Training)부터 포스트 트레이닝까지 깊게 진행했고, 몇 달마다 새로운 모델을 계속 발표했습니다. 결과는 훌륭했습니다. 그들의 목표는 프런티어 품질(Frontier Quality)과 경쟁하는 것이었습니다. 매우 대담한 목표이고, 실제로 가까워지고 있습니다.

Composer 2, Composer 2.5의 결과는 인상적입니다. 이들은 프런티어 랩의 품질과 동등하거나 그것을 넘어서려고 계속 시도합니다. Cursor는 매우 생생한 사례입니다. 집중하고 올바른 도구가 있으면 충분히 가능합니다. Cursor는 Fireworks 위에 구축했습니다.

의료 분야의 예도 많습니다. Doximity는 클리닉 AI(Clinic AI)를 만듭니다. 의사들이 깊은 의료 질문을 하고, 증상과 약물, 부작용을 연결하며, 의료 영역 전반을 깊게 조사할 수 있게 합니다. 그들도 Fireworks에서 학습했고, Stanford-Harvard 클리닉 안전 벤치마크에서 매우 중요한 성과를 냈습니다. 저희는 그 결과를 자랑스럽게 생각하고, 그들은 계속 이 학습 루프를 돌리고 있습니다.

Factory도 Sequoia 회사 중 하나입니다. Fireworks 위에 만들었고, 특히 코딩의 보안 영역에 집중합니다. 보안은 허용 오차가 낮기 때문에 매우 어려운 주제입니다. 반드시 맞아야 합니다. 그들은 보안 영역 벤치마크에서 좋은 성과를 내는 모델을 튜닝했습니다.

이런 사례들은 모든 회사가 고유한 문제를 고유한 방식으로 해결하고 있다는 것을 보여줍니다. 각 회사는 자기 데이터를 사용하고, 오픈 모델 위에 구축함으로써 자기 과제를 해결할 수 있습니다.

2025년은 코딩의 해였습니다. Fireworks에서는 많은 코딩 회사가 저희 위에서 성공적으로 중간 학습과 포스트 트레이닝을 진행했습니다. 벤치마크는 매우 인상적이었고, 이들 코딩 회사는 코딩 영역에서 프런티어 랩과 동등하거나 그것을 넘어서려는 목표를 갖고 있었습니다.

하지만 코딩만의 이야기는 아닙니다. 올해는 다양한 협업(Co-Work) 영역에서 흥미로운 발전이 보입니다. 범용 협업부터 특화 도메인 협업까지 다양합니다. 법률, 금융, 마케팅, 채용, 영업, 고객지원 같은 영역이 모두 포스트 트레이닝을 시작하고 자기 제품을 구동할 자체 지능을 소유하려 하고 있습니다.

Jen Spark는 범용 협업 애플리케이션 중 하나입니다. 전문가를 위한 딥 리서치와 슬라이드 생성을 만듭니다. 프런티어 모델과 경쟁하고 조금 더 나은 성능을 보이면서도 비용은 훨씬 낮습니다. 여기서는 비용이 5~10배 절감됩니다. 스타트업 입장에서는 어떤 문제를 맞히면 빠르게 실행 가능한 사업으로 확장할 수 있다는 의미입니다.

또 다른 의료 사례에서는, 의료 데이터와 사용 사례가 프런티어 랩 모델에 잘 포착되어 있지 않습니다. 그래서 튜닝된 모델의 품질이 최신 폐쇄형 모델보다 훨씬 좋아질 수 있습니다.

Fireworks 위에서 포스트 트레이닝을 하는 개발자 유형은 다양합니다. 프런티어 에이전트 빌더(Frontier Agent Builder)들이 있습니다. 이들은 보통 맞춤형 하네스(Customized Harness)를 만듭니다. 일반 하네스를 쓰지 않습니다. 자기 시스템, 도구들과 함께 하네스를 공동 최적화해야 하는데, 이때 포스트 트레이닝이 필요합니다. 저희는 이런 방식에서 반복 가능한 성공을 많이 봤습니다.

큰 회사들도 포스트 트레이닝으로 전환하고 있습니다. 기존 대기업은 엄청난 트래픽을 가지고 있습니다. 모든 고객에게 AI 기능을 배포하려면 비용 부담이 매우 큽니다. “파산으로 스케일하지 않도록 조심해야 한다”는 말은 스타트업만의 이야기가 아닙니다. 기존 대기업에도 해당됩니다. CFO가 비용 때문에 AI 기능 출시를 실제로 막는 경우가 있습니다. 포스트 트레이닝은 이를 완화하는 방법입니다.

특화 모델 운영자(Specialized Model Operator)들도 있습니다. 새로운 연구소나 최첨단 모델 개발자들도 상당한 포스트 트레이닝을 합니다.

저희가 반복해서 듣는 말이 있습니다. 제품-시장 적합성(Product-Market Fit) 이후, 포스트 트레이닝은 많은 회사가 특화 지능을 만드는 수단이 됩니다. 저희는 미래에 수백만 개의 특화 모델이 생길 수 있다고 봅니다. 사용 사례 하나당 애플리케이션 하나, 그리고 그에 맞는 모델 하나가 있을 수 있습니다.

데이터를 모델로 바꾸는 방법은 여러 가지입니다. 보상 신호와 보상 함수(Reward Function)를 어떻게 만드는지도 매우 중요합니다.

저희 관찰은 이렇습니다. 일찍 시작하십시오. 더 반복적으로 실험하고, 직접 경험을 쌓으십시오. 사람들이 생각하는 것만큼 장벽이 높지 않습니다. 보상 엔지니어링(Reward Engineering)은 소프트웨어 엔지니어링과 매우 비슷합니다. 논리적 추론과 사고방식이 매우 유사합니다. 직접 손을 더럽히고 시험해 보십시오.

이것이 핵심 요약입니다. 이 분야에는 팀마다 다른 수준의 전문성이 있습니다. Cursor나 Cognition 같은 회사는 깊은 연구자들이 있고, 극단적인 결과를 얻기 위해 모든 노브(Knob)를 최대한 통제하고 싶어 합니다. 저희는 이들에게 가장 낮은 수준의 API를 제공합니다. RL 롤아웃(RL Rollout)에 직접 상호작용할 수 있고, 트레이너(Trainer)를 완전히 통제할 수 있게 합니다. 이것이 최고의 결과를 줍니다.

하지만 많은 회사에는 제품 엔지니어나 머신러닝 엔지니어가 있습니다. 포스트 트레이닝에 대해 충분한 지식은 있지만, 가장 낮은 수준까지 통제하고 싶지는 않을 수 있습니다. 그래서 저희는 트레이닝 SDK를 제공하고, 여러분과 가깝게 반복하며 시작할 수 있게 돕습니다. 필요하면 저희 연구자들이 직접 투입되어 팀이 온보딩되도록 도울 수도 있습니다.

질문: 제품에서 이미 데이터와 보상 신호가 있는 팀들이 가장 성공적인 것 같습니다. 빠르게 잘 학습된 사례에서 본 최고의 보상 신호는 무엇인가요?

답변: 보상은 코드처럼 생각할 수 있습니다. 보상은 코드로 작성합니다. 보상의 평가 기준표(Rubric)를 생각해야 합니다. 결과를 여러 차원에서 평가한다고 생각하십시오. 예를 들어 채용 에이전트를 만든다면 후보자 선택을 어떻게 평가할지 생각할 수 있습니다. 회사마다 기준은 다릅니다. 어떤 회사는 후보자의 능력, 배고픔, 거절을 받아들이지 않는 태도, 벽을 부수고 나아가는 성향을 평가하고 싶어 할 수 있습니다. 이것이 하나의 지표입니다. 두 번째는 빠르게 무언가를 만들고 진척을 내는 능력일 수 있습니다. 이런 점수들을 섞어 하나의 종합 점수로 만듭니다. 보상을 여러 차원의 평가 기준으로 생각하고, 회사마다 이를 섞는 방식이 다릅니다. 바로 그것이 여러분의 고유한 부분이자 비밀 소스입니다.

답변: 훌륭한 질문입니다. AI 제품 구축에서는 제품-시장 적합성과 사업 확장이 실제로 두 단계입니다. SaaS 시대에는 하나의 개념이었습니다. PMF를 찾으면 그냥 최대한 확장하면 됐습니다.

중요한 점은 PMF를 찾은 후에야 제품 표면에서 수집하는 데이터가 정말 의미 있어진다는 것입니다. 그리고 고품질 데이터가 일정 규모로 쌓이기 시작합니다. 이것이 연료가 됩니다. 이때 자기 지능을 소유하기 시작합니다. 저희는 이것을 매우 강한 신호로 봅니다.
