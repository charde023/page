AI 엔지니어링의 황금기가 왔습니다

원작자 Romain Huet, Alexander Embiricos, Peter Steinberger · OpenAI · 업로드 2026-07-10 · 24.7분 · 원본 영상 ↗

AI 시대의 핵심은 개발자가 사라지는 것이 아니라, 에이전트(agent)가 일하는 루프(loop)를 설계하고 검토하며 더 큰 문제를 푸는 엔지니어로 역할이 확장되는 것이다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
AI 엔지니어링(AI Engineering) 코딩 자동화가 아니라 문제 해결 방식 자체가 바뀌고 있음을 이해해야 함 엔지니어의 일은 코드 작성에서 루프 설계와 판단으로 이동한다
에이전트 루프(agent loop) AI가 한 번 답하는 도구가 아니라 목표를 받아 실행, 테스트, 수정하는 작업자가 됨 좋은 결과는 좋은 프롬프트보다 좋은 작업 루프에서 나온다
Codex 앱(Codex app) 채팅과 협업형 UI를 결합한 개발 환경의 방향성을 보여줌 “터미널만 쓰는 개발”에서 “AI 동료와 대화하고 필요할 때 깊게 들어가는 개발”로 전환
Responses API OpenAI 내부 제품과 외부 개발자가 같은 기반을 쓰게 하는 핵심 API Codex도 같은 API 위에서 만들어지며, 필요한 기능은 API에 먼저 반영하려 함
AGENTS.md 에이전트에게 프로젝트별 지침을 전달하는 표준화된 파일 역할 여러 AI 도구가 같은 지침을 읽을 수 있게 하려는 시도
오픈소스 하네스(open source harness) 에이전트 실행 환경을 개발자가 직접 검사, 수정, 확장할 수 있음 OpenAI가 쓰는 루프를 외부도 포크(fork)하고 응용 가능
가치 극대화(value maxing) 토큰을 많이 쓰는 것이 아니라 비용, 속도, 지능의 균형으로 실제 가치를 내야 함 “토큰 최대화”가 아니라 업무 성과 최대화가 목표
사람의 주의력(human attention) 토큰과 컴퓨트보다 사람이 어디를 봐야 하는지가 병목이 됨 앞으로의 병목은 모델보다 사람의 판단 시간일 수 있다

내가 모를 만한 것 / 처음 보는 것

  • Codex 앱(Codex app) — OpenAI의 AI 코딩 및 작업 에이전트 인터페이스. 단순 코드 자동완성보다 채팅, 작업 위임, 검토, 실행을 묶는 방향.
  • Responses API — 모델 호출, 도구 사용, 장기 작업, 컨텍스트 관리 등을 제품화하기 위한 OpenAI API.
  • 하네스(harness) — 에이전트가 도구를 호출하고 환경을 탐색하며 작업을 수행하도록 감싸는 실행 틀.
  • AGENTS.md — 프로젝트 안에서 AI 에이전트에게 “이 저장소에서는 이렇게 일하라”는 지침을 제공하는 파일.
  • 압축(compaction) — 장기 작업 중 길어진 컨텍스트(context)를 요약·압축해 에이전트가 계속 일할 수 있게 하는 기술.
  • 앱 서버(App Server) — Codex 하네스를 앱에서 통제하고 로그인·구독·상태를 연결하기 위한 오픈소스 서버 계층.
  • 플러그인(plugin) — 브라우저 사용(browser use), 컴퓨터 사용(computer use), 직무별 기능 등을 확장하는 구조.
  • TerminalBench — 터미널 기반 작업 수행 능력을 평가하는 벤치마크로 언급됨.
  • Cerebras — 고속 추론(inference)을 제공하는 AI 하드웨어·인프라 회사.
  • VNC — 원격 화면 접속 방식. 에이전트가 만든 실행 빌드를 사람이 직접 확인할 때 쓰일 수 있음.
  • 매니저/워커 구조(manager/worker) — 장기 실행 매니저 에이전트가 여러 작업자 에이전트에게 일을 위임하는 구조.

1 AI 엔지니어링의 시대 AI는 엔지니어를 없애는 것이 아니라 엔지니어링의 본질인 문제 해결을 확장한다
2 모델 발전과 작업 루프 변화 자동완성에서 테스트, 장기 목표 수행까지 모델 역할이 빠르게 진화했다
3 Codex 제품 철학 채팅과 협업형 UI를 통해 AI 동료와 일하는 경험을 만든다

5 가치 극대화 비용, 속도, 지능을 조합해 실제 업무 가치를 극대화해야 한다
6 로컬과 클라우드의 경계 약화 에이전트가 작업에 맞는 환경을 스스로 선택하는 방향으로 간다
7 Peter의 에이전트 운영 방식 여러 터미널을 직접 관리하는 방식에서 매니저/워커 에이전트 루프로 이동한다
8 새로운 병목 토큰이나 컴퓨트보다 사람의 주의력과 판단이 병목이 된다

1. AI 엔지니어링은 개발자를 없애는 흐름이 아니다

화자들은 현재의 AI 엔지니어링 흐름을 세계박람회(World’s Fair)에 비유한다. 과거에는 불가능해 보이던 기술이 공개된 장소에서 실제로 전시되고, 사람들이 직접 보고 믿기 시작했던 것처럼, 지금 AI 엔지니어링도 “미래를 공개적으로 만들어가는 장면”이라는 뜻이다.

중요한 메시지는 AI가 엔지니어를 대체한다는 말은 반대로 봐야 한다는 것이다. 코딩이 추상화되면 엔지니어가 필요 없어질 것이라는 주장이 있지만, 화자들은 엔지니어링의 본질이 원래 코드 작성이 아니라 문제 해결이었다고 말한다.

즉, 엔지니어링은 다음을 결합하는 일이다.

  • 최신 과학과 기술
  • 디자인(design)
  • 취향과 판단(taste and judgment)
  • 상상력(imagination)
  • 실제 사용 가능한 제품화

그래서 AI 시대는 엔지니어링의 끝이 아니라, 오히려 엔지니어링의 뿌리로 돌아가는 시기라고 주장한다. 코드를 손으로 더 많이 치는 사람이 아니라, 문제를 정의하고 AI가 실행 가능한 구조를 만드는 사람이 더 중요해진다.

2. 모델 개발 주기가 빨라지며 작업 방식도 바뀌었다

OpenAI의 모델 출시 주기는 과거 약 15개월 단위였지만, 지금은 약 6주 단위로 빨라졌다고 한다. 이 속도 변화는 단순히 모델 성능이 좋아졌다는 의미가 아니라, 제품 개발과 엔지니어링 문화 자체를 바꾼다.

화자는 최근 몇 년의 변화를 다음 흐름으로 설명한다.

  1. 완성(completion)
    코드 일부를 예측하거나 이어 쓰는 단계.

  2. 인라인 예측(inline prediction)
    개발자가 입력하는 중간에 코드 제안을 넣어주는 단계.

  3. Command-K 방식
    “이 부분을 이렇게 바꿔줘”라고 명령하면 모델이 수정해주는 단계.

  4. 모델이 직접 테스트(test)하는 단계
    단순히 코드를 쓰는 것이 아니라 실행하고 검증하기 시작.

  5. 장기 목표(long, hard goals)를 끝까지 수행하는 단계
    모델이 긴 작업을 받아 완료될 때까지 여러 단계를 수행.

특히 불과 2년 전만 해도 모델이 코드를 실행하고 검증하는 build-and-test loop를 제대로 수행하지 못했다는 점을 강조한다. Dev Day 2024에서는 O1 preview로 미니 드론 인터페이스를 만들었지만, 모델이 자기 코드를 실행하거나 확인할 수 없어서 데모가 될지 확신하기 어려웠다고 한다.

현재는 모델이 테스트를 수행하고, 더 긴 목표를 추적하면서 작업할 수 있게 되었기 때문에 개발자가 AI를 쓰는 느낌 자체가 달라졌다는 것이다.

3. Codex와 에이전트는 코딩 전후의 일까지 확장된다

화자들은 Codex가 단순한 코딩 도구가 아니라, 사람이 컴퓨터에서 하는 다양한 작업을 수행할 수 있는 에이전트로 발전하고 있다고 설명한다.

핵심은 코딩 자체만 돕는 것이 아니라 다음까지 연결하는 것이다.

  • 코딩 전: 왜 이 작업을 해야 하는지 이해
  • 코딩 중: 구현, 수정, 테스트
  • 코딩 후: 리뷰(review), 배포(deploy), 결과 반영

여기서 중요한 단어가 루프(loop)다. 에이전트가 단순히 “명령 한 번에 답변 하나”를 내는 것이 아니라, 목표를 이해하고 실행하고 확인하고 다시 수정하는 반복 구조를 갖게 해야 한다.

특히 “왜 해야 하는지”와 “끝난 뒤 무엇을 해야 하는지”까지 에이전트에게 연결하면, 에이전트가 훨씬 더 많은 일을 실제로 완료할 수 있다고 말한다.

제품 관점에서는 AI 덕분에 더 많은 아이디어를 빠르게 프로토타입(prototype)하고, 사용자와 더 많은 시간을 보내며, 무엇을 만들지에 대한 의사결정도 좋아진다고 한다.

4. 원하는 제품 경험은 자동화가 아니라 엔지니어의 강화다

화자들은 AI 제품의 목표가 엔지니어를 자동화해서 없애는 것이 아니라, 엔지니어를 최대한 강하게 만드는 것이라고 말한다.

그들이 생각하는 제품 형태는 크게 두 가지다.

  1. 채팅(chat)
    어디서든 무엇이든 부탁할 수 있는 하나의 AI 동료.

  2. 직접 조작 가능한 협업 UI(collaborative UI)
    필요할 때 세부사항을 들여다보고, 방향을 조정하고, 직접 수정할 수 있는 화면.

이 비유는 팀원과 일하는 방식과 비슷하다. 대부분의 시간에는 팀원에게 말로 요청하고 결과를 기다린다. 모든 작업을 옆에서 지켜보지는 않는다. 하지만 중요한 순간에는 같이 깊게 들어가서 문제를 세부적으로 다룬다.

Codex 앱은 이 철학을 제품으로 구현한 예다. 기본은 간단한 채팅 인터페이스지만, 필요할 때 특정 코드나 화면 요소를 가리키며 “여기를 이렇게 바꿔줘”라고 요청하거나 직접 수정할 수 있다.

흥미로운 점은 처음에는 터미널(terminal), Vim, Emacs를 절대 떠나지 않겠다고 말하던 개발자들도 결국 이런 도구를 사용하게 됐다는 점이다. 화자들은 CLI는 협업형 인터페이스를 만들기 어렵고, IDE는 코드에서 출발하기 때문에 순서가 다르다고 본다. 앞으로는 코드에서 시작하는 것이 아니라 대화로 시작하고 필요할 때 코드로 깊게 들어가는 방식이 중요하다는 주장이다.

5. Codex는 닫힌 제품이 아니라 여러 계층의 오픈 생태계다

OpenAI는 Codex를 OpenAI만 개선할 수 있는 닫힌 제품으로 만들고 싶지 않다고 말한다. 그래서 Codex를 여러 계층(layer)으로 나누고, 개발자들이 각 계층 위에서 만들 수 있게 설계했다고 설명한다.

주요 계층은 다음과 같다.

계층 설명
모델(model) 빠르게 발전하는 OpenAI 모델군
Responses API Codex 앱도 사용하는 동일한 API 기반
Codex 하네스(Codex harness) 에이전트 실행 구조. 오픈소스로 공개되어 검사, 포크, 수정 가능
AGENTS.md 에이전트 지침 파일. Codex만이 아니라 다른 에이전트도 활용 가능하게 설계
앱 서버(App Server) Codex 하네스를 앱에서 통제하고 로그인·구독을 연결하는 서버
앱·플러그인(app/plugin) 브라우저 사용, 컴퓨터 사용, 직무별 확장 기능

중요한 원칙은 OpenAI 내부용 시스템과 개발자용 축소판을 따로 만들지 않는다는 점이다. Codex 앱도 외부 개발자에게 제공하는 API와 같은 기반 위에 만들어진다.

예를 들어 Codex가 장기 작업을 위해 긴 컨텍스트를 압축하는 기능이 필요했을 때, 이를 내부에만 넣지 않고 API의 기본 기능으로 반영했다고 한다. 그래서 외부 개발자도 같은 원시 기능(primitives)을 쓸 수 있다.

또한 Codex 하네스는 오픈소스이므로 개발자는 이를 확인하고 포크하고 자신들의 방식으로 바꿀 수 있다. OpenCode 팀이 Codex의 참조 구현(reference implementation)을 보고 필요한 부분만 재사용하거나 바꾼 사례도 언급된다.

6. 가치 극대화: 토큰을 많이 쓰는 것이 목표가 아니다

화자들은 에이전트가 점점 유용해질수록 질문은 “어떻게 더 많은 토큰을 쓰게 할까”가 아니라 “어떻게 더 많은 가치를 얻을까”가 된다고 말한다. 이를 가치 극대화(value maxing)라고 부른다.

여기에는 세 가지 축이 있다.

  1. 지능(intelligence)
    가장 뛰어난 모델을 쓰고 싶은 욕구.

  2. 비용 효율(cost efficiency)
    같은 지능을 더 낮은 비용으로 쓰는 능력.

  3. 속도(speed)
    모델이 빠르게 응답할수록 더 많은 접근법을 병렬로 시도할 수 있음.

예시로 GPT-5.6 Terra는 GPT-5.5 수준의 지능을 절반 비용으로 제공한다고 언급된다. Luna는 TerminalBench에서 의미 있는 성능을 보이면서도 입력 100만 토큰당 1달러, 출력 100만 토큰당 6달러라는 비용을 제시한다.

속도 측면에서는 GPT-5.6 Sol이 Cerebras에서 초당 750토큰으로 동작한다고 설명한다. 화자들은 이 속도가 단순히 답변 하나를 빨리 받는 의미를 넘는다고 본다. 예를 들어 한 에이전트가 5~6개의 접근법을 병렬로 시도하고, 그중 가장 좋은 것을 고르는 것이 가능해진다.

즉, 빠른 모델은 사람이 기다리는 시간을 줄이는 정도가 아니라 작업 전략 자체를 바꾸는 요소다.

7. 로컬과 클라우드의 경계는 흐려진다

많은 사람이 에이전트를 계속 돌리기 위해 노트북을 열어두는 모습을 언급한다. 하지만 화자들은 이상적인 미래가 “내 컴퓨터에서 실행할지, 클라우드에서 실행할지 매번 사람이 결정하는 것”이 아니라고 말한다.

원하는 형태는 다음과 같다.

  • 사람은 어디서든 에이전트에게 말한다.
  • 에이전트가 작업 성격을 판단한다.
  • 어떤 환경이 적합한지 스스로 선택한다.
  • 로컬 머신, 클라우드, 테스트 박스 등을 필요한 대로 사용한다.

즉, “로컬 작업(local task)”과 “클라우드 작업(cloud task)”의 구분이 사용자 경험에서 사라지는 방향이다.

이 관점은 비개발자 사업가에게도 중요하다. 예를 들어 쇼핑몰 상품 데이터 정리, 물류 송장 검증, 재고 분석, CS 분류 같은 업무를 AI에게 맡길 때도 “내 노트북에서 돌릴지 서버에서 돌릴지”보다 “업무 목표와 데이터 접근 권한, 검토 방식”이 더 중요해지는 것이다.

8. Peter Steinberger: 10개 터미널에서 매니저 에이전트로

Peter Steinberger는 본인의 작업 방식 변화를 설명한다. 몇 달 전만 해도 그는 10개 이상의 터미널 창을 띄우고, 각 에이전트가 끝나기를 기다렸다가 방향을 수정하고 새 작업을 넣었다고 한다.

당시에는 이것이 생산성의 정점처럼 느껴졌지만, 지금 돌아보면 자신은 오케스트레이션(orchestration)을 한 것이 아니라 단순히 계속 상태를 확인하는 폴링(polling)을 한 것에 가까웠다고 말한다.

그는 자신이 사실상 다음 역할을 하고 있었다고 표현한다.

  • 스케줄러(scheduler)
  • 라우터(router)
  • 메모리(memory)

처음에는 하나의 에이전트와 페어 프로그래밍(pairing)을 했다. 하지만 터미널이 10개가 되면 더 이상 페어링이 아니라 10명의 직원을 직접 관리하는 것과 비슷해진다.

현재는 장기 실행 매니저(long-running manager) 에이전트와 주로 대화하고, 이 매니저가 작업자(worker) 에이전트들에게 일을 위임하는 방식으로 바뀌었다. 어려운 작업에서는 여전히 특정 워커와 직접 페어링할 수 있지만, 기본 방식은 “에이전트 회사의 매니저를 관리하는 것”이 되었다.

9. 확장 가능한 에이전트 루프를 만든 세 가지 변화

Peter는 이런 변화가 가능해진 이유를 세 가지로 정리한다.

  1. 서버 측 압축(server-side compaction)
    긴 작업을 안정적으로 계속할 수 있게 해준다. 세션(session) 한계에 맞춰 사람이 계속 최적화하지 않아도 된다.

  2. 조율(coordination)
    하나의 스레드(thread)가 적절한 프로젝트를 만들고 방향을 조정할 수 있다.

  3. 자동화 트리거(automation triggers)
    어떤 일이 발생했을 때 같은 매니저 에이전트가 다시 깨어날 수 있다.

이를 요약하면 다음 세 가지다.

  • 지속적 컨텍스트(persistent context)
  • 위임(delegation)
  • 트리거(triggers)

이 세 가지가 합쳐지면 에이전트 루프가 된다. 그리고 루프가 작동하기 시작하면 병목은 다른 곳으로 이동한다.

10. 새로운 병목은 사람의 주의력이다

Peter는 예전에는 토큰(tokens)이 병목이었다고 말한다. 그리고 OpenAI에 합류하면서 농담처럼 그 문제를 해결했다고 한다. 그다음 병목은 컴퓨트(compute)였다. 여러 스레드가 동시에 돌아가면 맥북이 제트 엔진처럼 소리를 냈기 때문이다. 이 문제는 테스트 박스(test boxes)를 사용해 에이전트가 별도 머신에서 테스트를 돌리게 하며 어느 정도 해결했다.

하지만 지금의 병목은 사람의 주의력(attention)이다.

토큰과 컴퓨트는 더 추가할 수 있지만, 사람의 집중 시간은 쉽게 늘릴 수 없다. 그래서 중요한 능력은 에이전트가 하는 모든 것을 지켜보는 것이 아니라, 어디에 내 주의를 쓸지 결정하는 것이 된다.

초기 모델에서는 에이전트가 코드를 생성하는 과정을 지켜보다가 방향이 이상하면 중단하고 수정해야 했다. 그러나 최신 모델은 의도(intent)를 훨씬 잘 이해하므로, 코드가 생성되는 장면을 계속 보는 것은 시간 낭비가 될 수 있다고 한다.

11. 오픈소스 이슈 처리 자동화 예시

Peter는 오픈소스 프로젝트에 이슈(issue)가 등록되는 상황을 예로 든다.

이상적인 흐름은 다음과 같다.

  1. 누군가 GitHub에 이슈를 등록한다.
  2. 매니저 에이전트가 깨어난다.
  3. 프로젝트 목표, 메모, 비전과 비교해 해당 이슈가 적합한지 판단한다.
  4. 적합하면 워커 에이전트를 만든다.
  5. 워커가 조사하고 구현하고 테스트를 실행한다.
  6. 다른 에이전트가 결과를 리뷰한다.
  7. 매니저가 사람에게 PR, 원본 이슈, 변경 diff, 영상, 실행 빌드 등을 가져온다.
  8. 사람은 한 번 검토하고 코멘트하거나 승인한다.
  9. 체크가 통과되면 루프가 계속 진행되고 머지된다.

여기서 핵심은 내부 실행 루프(inner execution loop)는 에이전트가 돌리고, 사람은 외부 루프(outer loop)에서 방향을 정하고 결정을 내린다는 점이다.

Peter는 Paul Salt의 사례도 언급한다. Paul은 chief of staff 에이전트를 고정해 두었고, 이 에이전트가 10분마다 깨어나 GitHub 작업을 조율한다. 필요한 경우 사이드바에 스레드를 만들어 사람이 개입할 수 있게 한다.

12. 미래는 20개의 터미널이 아니라 더 나은 루프다

Peter의 결론은 명확하다. 장기 실행 매니저 에이전트가 가능해진 이상, 그것을 노트북 안의 세션에 묶어두는 것은 어색하다.

그가 원하는 형태는 다음과 같다.

  • 에이전트가 어떤 머신이든 연결할 수 있어야 한다.
  • 어떤 작업은 클라우드에서 가능한지, 어떤 작업은 로컬 머신이 필요한지 알아야 한다.
  • 앱 안에 갇힌 세션이 아니라, 문자(text), Slack, 다른 인터페이스에서 조종 가능한 에이전트여야 한다.
  • 궁극적으로는 사람이 에이전트에게 말하면, 에이전트가 전체 루프 자체를 설계할 수 있어야 한다.

아직 이 문제는 완전히 해결되지 않았다. 모델은 하네스와 조직 구조보다 더 빠르게 발전하고 있다. 그래서 앞으로의 엔지니어링 문제는 단순히 더 많은 코드를 쓰는 것이 아니라, 모델이 잘 일할 수 있는 루프와 조직을 설계하는 것이다.

마지막 메시지는 다음과 같다.

미래는 20개의 터미널이 아니라, 더 나은 루프다.

엔지니어가 되기에 지금보다 좋은 때는 없었습니다. 엔지니어링은 원래 코드를 쓰는 일이 아니었기 때문입니다. 엔지니어링은 자신과 다른 사람을 위해 문제를 해결하는 일이었습니다. 최신 과학을 디자인(design), 취향(taste), 판단(judgment), 그리고 무엇보다 상상력(imagination)과 결합해 사람들이 실제로 사용할 수 있는 것을 만드는 일입니다. 그런 의미에서 이것은 엔지니어링의 끝이 아닙니다. 우리는 이것이 엔지니어링의 뿌리로 돌아가는 일이라고 생각합니다.

우리가 기반으로 삼는 기술은 점점 더 빠르게 가속되고 있습니다. 예를 들어 예전에는 새 모델을 약 15개월마다 출시했지만, 지금은 대략 6주마다 출시하고 있습니다. 혹시 놓치셨다면, 지난주에 5.6 시리즈 preview를 공개했고, 여러분이 곧 사용할 수 있게 되어 매우 기대하고 있습니다.

이런 모델 위에서 제품 발전 속도도 멈추지 않고 빨라지고 있습니다. 그 결과 엔지니어링의 느낌이 완전히 달라졌습니다. 지난 몇 년 동안 저에게 연속적으로 충격적이었던 경험을 간단히 되짚어보겠습니다. 오랫동안 완성(completion)이 있었고, 그다음 인라인 예측(inline prediction)으로 갔고, 이후 Command-K가 등장했습니다. 모델에게 변경을 요청할 수는 있었지만, 모델이 자기 작업을 테스트하지는 않았습니다. 그다음 모델이 작업을 테스트하기 시작했고, 이제는 길고 어려운 목표를 끝날 때까지 수행하는 모델이 있습니다. 저에게 각 단계는 처음에는 충격적이었고, 이후에는 금세 익숙해졌습니다. 결국 우리는 일을 끝내려고 하니까요.

불과 2년 전만 해도 build-and-test loop가 모델의 일부가 아니었다는 것이 믿기지 않습니다. 이 사진은 Dev Day 2024의 제 모습입니다. 당시 저는 O1 preview를 사용해 미니 드론 인터페이스를 처음부터 만들었습니다. 조금 미친 부분은, 모델이 실제로 코드를 실행하거나 자기 작업을 검증할 수 없었다는 점입니다. 데모가 대부분은 작동하리라는 것을 알았지만, 항상 작동하리라고는 확신할 수 없었습니다. 그래서 손가락을 꼬고 빌어야 했습니다. 여기서 제가 꽤 긴장한 모습이 보일 겁니다. 하지만 저는 라이브 데모만 하는 사람이라, 매번 실제로 무슨 일이 일어날지 모릅니다. 다행히 작동했습니다. 그리고 2025년 Dev Day쯤에는 모델이 자기 작업을 테스트할 수 있다고 충분히 확신했기 때문에, 전체 카메라 시스템과 조명 시스템을 라이브로 제어할 수 있었습니다. 정말 먼 길을 왔습니다.

우리는 Homa를 데모의 신(demo god)이라고 부릅니다. 데모 전에 제가 “데모가 얼마나 자주 성공하나요?”라고 물으면, 그는 “네 번 중 세 번 정도요”라고 답합니다. 그러면 우리는 “좋아요, 행운을 빕니다”라고 하죠. 분명히 그때 이후로 엄청나게 발전했고, 올해만 해도 정말 미친 속도였습니다.

여기 보여드리는 것은 올해 지금까지 우리가 출시한 것들입니다. 사실 전부도 아니고 일부만 뽑은 것입니다. 제가 가장 좋아하는 출시물은 Codex 앱(Codex app), 목표 모드(goal mode), 원격(remote)입니다. 이런 것들은 일을 하는 느낌 자체를 바꿉니다. 물론 Codex를 만들 때 Codex를 쓰지 않았다면 이런 것들을 만들 수 없었을 것입니다.

제게 가장 흥미로운 점은 이제 Codex와 에이전트(agent)가 여러분이 자기 컴퓨터에서 할 수 있는 거의 모든 작업을 할 수 있다는 것입니다. 이는 단지 코딩을 돕는 것이 아니라, 코딩 전에 일어나는 일과 코딩 후에 일어나는 일까지 돕는다는 뜻입니다. 이것이 정말 핵심입니다. 오늘 루프(loop)에 대한 이야기가 많이 나올 것입니다. 에이전트를 해야 할 작업뿐 아니라 왜 그 작업을 해야 하는지와 연결할 수 있다면, 에이전트가 훨씬 더 많은 일을 시작할 수 있습니다. 그리고 그 작업 이후에 여러분이 하는 일, 즉 리뷰(review)와 배포(deploy)까지 연결할 수 있다면, 에이전트가 더 많은 작업을 실제로 마무리하도록 도울 수 있습니다.

이 모든 덕분에 우리는 훨씬 빠르게 움직일 수 있습니다. 하지만 제품 담당자인 저에게 가장 흥미로운 것은 실제로 무엇을 만들지에 대한 더 나은 결정을 내릴 수 있다는 점입니다. 예를 들어 우리는 훨씬 더 많은 아이디어를 시도하고 프로토타입(prototype)을 만들며, 사용자들과 더 많은 시간을 보냅니다. 그러니까 여기 계신 여러분입니다. 잠시 멈추고 여러분 모두에게 감사드리고 싶습니다. 애정 어린 반응과 건설적인 피드백 모두에 감사드립니다. Codex와 사실상 전체 산업이 여러분 없이는 여기까지 오지 못했을 것입니다. 피드백을 주셔서 정말 감사합니다. 우리는 항상 여러분의 목소리를 듣고 있습니다.

좋습니다. 모델은 정말 좋아지고 있습니다. 중간 길이의 컴퓨터 작업을 하나 고르고, 저와 모델에게 같은 시간을 준다면, 적어도 제 경우에는 평균적인 작업에서 모델이 저보다 더 잘할 가능성이 큽니다. 어떤 면에서는 모델이 우리보다 똑똑하고 거의 무엇이든 할 수 있게 되고 있습니다. 그렇다면 우리는 이것을 어떻게 만들어야 할까요? 우리가 사용하는 제품은 어떤 느낌이어야 할까요?

그 답을 찾기 위해 우리는 우리의 미션을 봅니다. 여기서 강조하고 싶은 부분은 모든 인류에게 이로운 AGI(AGI that benefits all of humanity)입니다. 이를 위해 지금 제가 생각하는 큰 질문은 두 가지입니다. 첫째, 에이전트가 실제 세계에서 일을 하도록 어떻게 설정할 것인가입니다. 무엇을 할 수 있는가, 그리고 어디에서 실행되는가의 문제입니다. 이에 대해서는 뒤에서 더 이야기하겠습니다. 둘째, 우리는 이 에이전트를 어떻게 사용할 것인가입니다. 우리에게 제품은 어떤 느낌이어야 하는가입니다. 우리의 목표는 명확히 엔지니어를 자동화해 없애는 것이 아닙니다. 우리가 원하는 제품 형태는 엔지니어를 최대한 강화하는 것입니다.

우리가 원하는 제품 형태는 생각보다 단순합니다. 저는 SF를 많이 읽고 슈퍼히어로 영화를 보는데, 그 안의 단순한 아이디어들이 대체로 맞다고 생각합니다. 크게 두 가지 방식이 있습니다. 하나는 채팅(chat)입니다. 어떤 사람들은 채팅은 끝났다고 생각하지만, 저는 채팅이 과소평가되어 있다고 생각합니다. 다른 하나는 손으로 직접 다룰 수 있는 경험(hands-on experience)입니다. 여러분이 원하는 것은 어디서든 무엇이든 도움을 요청할 수 있는 하나의 존재입니다. 그리고 직접 검사하고, 방향을 조정하고, 스스로 형태를 잡고 싶을 때 사용할 수 있는 강력한 협업 UI(collaborative UI)입니다.

Codex에게 이 개념을 이해하기 위한 이미지를 만들어달라고 했습니다. 여러분에게 드릴 비유는 팀과 일하는 것과 같다는 것입니다. 대부분의 시간에는 그냥 이야기하고, 팀은 일을 합니다. 모든 단위 작업마다 팀원의 어깨너머를 보거나 작업대까지 걸어가고 싶지는 않습니다. 대체로는 말하고, 그들이 일하게 두고 싶습니다. 그러다 가끔은 아주 깊게 들어가서 문제의 세부사항까지 함께 파고들고 싶을 때가 있습니다.

제품을 만들면서 우리는 여러분이 하고 있는 일에 대한 숙련감(mastery)을 유지할 수 있게 만들고 싶다는 생각을 갖고 있습니다. 그것은 매우 강력합니다. 세부사항에 접근하기 어렵거나, 이 경우처럼 하드웨어를 분해하기 어렵게 느껴지게 만들고 싶지 않습니다.

우리가 이것을 구현하기 시작한 방식이 바로 Codex 앱입니다. 여러분은 코딩과 그 외 모든 것에 사용할 수 있는 매우 단순한 채팅 인터페이스를 얻습니다. 대화를 나누다가 원하는 만큼 깊게 들어갈 수 있습니다. 여기 예시에서는 Romain이 다가오는 월드컵 경기의 예상 점수를 다루고 있습니다. 제가 맞기를 바랍니다. 지켜보죠.

여기서 특정한 것을 가리키며 “이 변경을 해줘”라고 말할 수도 있고, 직접 변경할 수도 있습니다. 재미있는 이야기가 있습니다. 우리가 이 아이디어를 시작하기 전에, 오늘 관객 중에도 있는 몇 분께 설명한 적이 있습니다. 그때 그분들은 단호하게 “나는 그런 도구를 절대 쓰지 않을 것이다. 터미널이나 Vim, Emacs를 절대 떠나지 않을 것이다”라고 말했습니다. 그런데 지금은 그분들도 사용하고 있습니다.

내부 팀에서도 “왜 이것을 만들어야 하지?”라는 질문이 많았습니다. 사람들은 CLI와 IDE를 좋아합니다. 미묘하지만 우리의 관점은 이렇습니다. CLI에서는 어떤 종류의 작업이든 가능한 협업형 인터페이스를 만들기 어렵습니다. 대부분 채팅에 가깝습니다. IDE에서는 순서가 반대입니다. 코드에서 시작하기 때문입니다. 이제는 팀원과 일하는 방식으로 전환할 때입니다. 먼저 대화하고, 필요할 때 깊게 들어가는 방식입니다.

맞습니다. 우리는 제품 표면(product surface)과 모델 계층(model layer) 모두에서 매우 빠르게 움직이고 있습니다. 동시에 여러분의 속도에 맞추려고 노력하고 있습니다. 솔직히 말해 제가 X를 열 때마다, 이 방 안의 누군가가 Codex로 제가 가능하다고 몰랐던 일을 하는 것을 봅니다. 이것이 개척자들이 하는 일입니다. 여러분은 실험하고, 자신과 팀을 위한 도구를 설정합니다. 그리고 우리는 그로부터 영감을 얻습니다. 여러분에게 배우고, 결국 모두가 혜택을 받습니다.

여러분은 우리가 다음에 무엇을 만들지, 그리고 엔지니어링의 미래가 어떤 모습이어야 할지 알아내는 데 도움을 주고 있습니다. 하지만 그것이 작동하려면, Codex가 OpenAI만 개선할 수 있는 닫힌 제품이 되어서는 안 됩니다. 그래서 우리는 Codex를 누구나 그 위에 만들 수 있는 계층들의 집합으로 의도적으로 설계했습니다. 오늘 그 스택(stack)이 어떻게 구성되어 있고 어떻게 나타나는지 조금 보여드리겠습니다.

먼저 모델에서 시작합니다. Alexander가 모델이 얼마나 빠르게 발전하고 있는지 보여주었습니다. 여러분은 이 모델들을 Responses API를 통해 사용합니다. 그리고 Codex 앱도 바로 그 방식으로 만들어집니다. 우리는 같은 모델을 같은 API를 통해 사용합니다. 실제로 개발자에게 제공하는 것과 같은 기반 위에서 만들고 있습니다. Codex에 새로운 것이 필요할 때마다, 우리는 먼저 그것을 API에 녹여 넣으려고 합니다. 그래야 여러분도 혜택을 받을 수 있습니다. 최근 예시는 압축(compaction)입니다. Codex는 장기 실행 작업을 위해 긴 컨텍스트(context)를 압축할 방법이 필요했고, 그래서 우리는 그것을 API에 넣었습니다. 이는 여러분의 에이전트도 우리가 우리 자신을 위해 만든 것과 같은 기본 기능(primitives)을 사용할 수 있다는 뜻입니다.

다음 계층으로 가면, Codex 하네스(Codex harness)도 오픈소스(open source)입니다. 여러분은 이를 검사하고, 포크(fork)하고, 수정할 수 있습니다. AGENTS.md에도 같은 접근을 취했습니다. Codex가 지시를 따르기 위한 새 파일 형식을 또 만들기보다, 다른 에이전트도 실제로 사용할 수 있는 이름을 쓰자고 생각했습니다. 하네스의 기본 모델은 OpenAI 모델이지만, 하드코딩(hard-coded)되어 있지는 않습니다. 오픈 모델(open model)을 사용하면서 같은 에이전트 루프를 유지하고 싶다면 그렇게 할 수 있습니다. 또한 우리는 이 Codex 하네스를 모델의 사후 학습(post-training) 과정에도 가져옵니다.

이는 모델이 도구를 호출하고 환경을 탐색하는 법을, 실제로 오픈소스인 무언가 안에서 배울 수 있다는 뜻입니다.

예를 들어 OpenCode 팀을 보겠습니다. 그들은 우리의 참조 구현(reference implementation)을 살펴보고, 자신들에게 맞는 부분은 재사용하거나 나머지는 완전히 바꾸고 다른 선택을 할 수 있었습니다.

제가 알기로 그들은 ChatGPT로 로그인(sign in)하는 방식을 우리가 어떻게 구현했는지 보려 했습니다. 그래서 코드를 보고 배울 수 있었습니다. 우리는 개발자들이 우리가 어떻게 빌드하고 실행하는지 역공학(reverse-engineer)해야 하는 것보다 이것이 더 낫다고 생각합니다.

이제 구독(subscription) 이야기가 나온 김에, 한 단계 더 올라가서 이 하네스를 앱 안으로 어떻게 가져오는지 생각해봅시다. 그리고 사람들이 기존 Codex 구독으로 로그인하게 하려면 어떻게 해야 할까요?

알고 보니 우리도 같은 문제가 있었습니다. VS Code 확장(extension)과 Codex 앱을 만들고 싶었고, 이 하네스를 통제할 통합된 방식이 필요했습니다. 그래서 우리는 앱 서버(App Server)를 만들었고, 이것도 오픈소스로 공개했습니다.

앱 서버는 단순한 커뮤니티 어댑터(community adapter)가 아닙니다. 우리 자체 제품에도 실제로 사용하는 경로입니다. 여러분도 사용할 수 있습니다.
