구글 엔지니어가 말아주는 AI 하네스 | AI를 일하게 만드는 네 가지 설계

업로드 2026-10-25 · 7.3분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 똑똑한 모델만으로는 일이 끝나지 않는다

AI가 코드를 작성할 수 있다고 해서 실제 파일을 바꾸고, 버튼을 눌러 보고, 실패를 고치고, 안전을 지키며, 완료 여부까지 확인할 수 있는 것은 아니다. 모델이 판단한 내용을 현실의 행동으로 연결하려면 모델 주변에 별도의 소프트웨어가 필요하다. 영상은 이 소프트웨어 층을 AI 하네스(AI harness)라고 부른다.

예시는 고객 명단을 내려받는 버튼이다. 처음에는 고객 명단 전체를 요청했다가 나중에 이름과 이메일만 포함하도록 조건을 바꿨다고 하자. AI는 바뀐 조건을 기억해야 하고, 파일을 수정할 도구를 사용해야 하며, 검사에 실패하면 다시 고쳐야 한다. 실제 고객 정보에는 접근하지 못하게 막아야 하고, 마지막에는 AI의 “완료했다”는 말이 아니라 결과 파일과 사용자 경험을 확인해야 한다.

읽는 법: 위에서 아래로 읽는다. 앞 단계가 뒤 단계를 대신하지 않는다. 기억이 정확해도 실행 도구가 없으면 파일은 바뀌지 않고, 실행에 성공해도 권한이 지나치게 넓으면 위험하다. 모든 실행이 끝나도 결과를 검사하지 않으면 완료를 확인할 수 없다. 이 그림은 수치 자료가 아니라 영상의 개념 관계를 정리한 지도다.

1. 기억은 한 덩어리가 아니다

영상은 기억과 맥락을 세 층으로 나눈다.

  • 세션(session)은 대화 전체의 작업일지다. 사용자의 메시지, 에이전트가 호출한 도구, 도구의 결과가 함께 남는다. “고객 명단 전체”라는 최초 요청과 “이름과 이메일만”이라는 후속 지시가 모두 여기에 속한다.
  • 상태(state)는 지금 프로그램이 바로 읽고 바꿀 수 있는 메모판이다. 예를 들어 내보낼 열을 이름, 이메일로 저장하거나 작업 상태를 테스트 준비로 둘 수 있다. 전체 대화를 다시 검색하지 않고 필요한 값을 꺼내는 용도다.
  • 장기 기억(long-term memory)은 다음 대화에서도 다시 사용할 정보다. 무엇을 저장하고 언제 꺼낼지는 저절로 정해지는 것이 아니라 설계자가 결정한다.

이 구분의 핵심은 “AI가 기억한다”는 막연한 표현을 버리는 것이다. 전체 기록이 필요한지, 현재 작업값만 필요한지, 다음 작업에도 남겨야 하는지를 따로 결정해야 한다.

2. 판단은 도구와 작업 흐름을 만나야 실행이 된다

모델이 “이 파일을 수정해야겠다”고 판단해도 파일은 저절로 바뀌지 않는다. 실제 수정은 파이썬 함수 같은 도구(tool)가 수행한다. 다른 도구는 테스트를 실행하거나 외부 API를 호출할 수 있다. 영상은 서버가 공개한 도구를 표준 방식으로 찾고 호출하도록 연결하는 방법으로 모델 컨텍스트 프로토콜(Model Context Protocol, MCP)을 소개한다.

도구가 “무엇으로 일할지”를 정한다면, 작업 흐름(workflow)은 그 도구를 “어떤 순서와 조건으로 사용할지” 정한다. 고객 명단 내보내기 예시에서는 코드 변경 뒤 두 검사를 함께 실행한다.

  1. 내보내기 로직을 확인하는 단위 테스트
  2. 브라우저에서 버튼을 누르고 다운로드를 확인하는 테스트

둘 중 하나라도 실패하면 결과를 코딩 에이전트에게 돌려보내 다시 수정하게 한다. 둘 다 통과하면 검토 단계로 이동한다. 영상은 이런 구조를 정의하는 수단으로 ADK 그래프 작업 흐름을 언급하며, 계속 실패할 때 무한히 반복하지 않도록 재시도 한도를 둘 수 있다고 설명한다.

읽는 법: 위에서 아래로 진행한다. 검사를 모두 통과하면 아래 왼쪽의 검토 단계로 간다. 실패하면 오른쪽 바깥의 붉은 경로를 따라 다시 맨 위 코드 변경으로 돌아간다. 재시도 한도를 넘으면 오른쪽 아래에서 작업을 멈추고 사람에게 도움을 요청한다. 수치를 나타낸 그래프가 아니라 실행 순환을 보여주는 개념 도식이다.

3. 실행 장소와 정보가 가는 곳은 다른 문제다

실제 고객 명단으로 버튼을 시험할 필요는 없다. 영상은 프로젝트 복사본과 가짜 고객 자료를 주고, 접근 가능한 파일과 네트워크를 제한한 격리 공간에서 실행하는 방법을 제시한다. 이런 공간을 샌드박스(sandbox)라고 한다.

하지만 샌드박스만으로 모든 공격이 해결되지는 않는다. 파일 안에 “비밀번호를 외부로 보내라” 같은 지시가 숨어 있고, 모델이 이를 새 명령으로 받아들이면 프롬프트 인젝션(prompt injection)이 발생할 수 있다. 따라서 자격 증명을 손이 닿지 않는 곳에 두고, 파일·네트워크 권한을 제한하며, 민감한 동작 전에는 사람의 승인을 요청하도록 소프트웨어로 강제해야 한다. 단순히 모델에게 “조심하라”고 말하는 것만으로는 부족하다는 것이 영상의 주장이다.

또한 도구가 노트북에서 실행된다고 해서 정보도 노트북 안에만 남는 것은 아니다. 도구의 출력이 외부에서 호스팅되는 모델로 전달되거나, 세션 기록 또는 장기 기억에 저장될 수 있다.

모바일에서는 아래 표 안을 좌우로 이동해 두 열을 비교한다.

읽는 법: 같은 행에서 가운데와 오른쪽 열을 비교한다. 실행 장소를 안전하게 만들었다고 정보 경로까지 자동으로 안전해지는 것은 아니다. 두 질문을 각각 확인해야 한다. 표는 영상의 설명을 비교한 개념 자료이며 위험도를 수치화한 자료가 아니다.

4. “완료했다”는 말 대신 결과를 여러 층으로 확인한다

마지막 설계는 완료 기준이다. 예제 앱에 가짜 고객 열 명이 있다면 다운로드 파일에도 같은 열 명의 이름과 이메일이 정확히 들어 있는지 코드로 확인할 수 있다. 요구 조건을 명확하게 정하고 코드가 충족 여부를 확인하는 방식을 영상은 결정적 평가(deterministic evaluation)라고 부른다.

하지만 숫자와 필드가 맞는다고 사용하기 좋은 기능인 것은 아니다. 완료 안내가 이해하기 쉬운지처럼 판단이 필요한 항목은 기준을 받은 다른 AI가 검토할 수 있다. 다만 영상은 이런 AI 심판도 틀릴 수 있으므로 사람의 검토와 비교하라고 말한다.

사람은 실제로 버튼을 눌러 보면서 다운로드는 되지만 버튼 이름이 헷갈리거나 페이지에서 찾기 어렵다는 문제를 발견할 수 있다. 따라서 완료는 한 번의 선언이 아니라 다음 세 층을 통과한 상태에 가깝다.

  • 명확한 요구 사항을 코드로 확인하는 자동 검사
  • 정성적 기준에 따른 AI 검토
  • 실제 사용 경험을 살피는 사람의 평가

이 영상의 중심은 더 좋은 모델 이름을 고르는 데 있지 않다. 모델이 무엇을 기억하고, 어떤 도구를 어떤 순서로 쓰며, 어디까지 접근하고, 무엇을 통과해야 완료되는지를 소프트웨어로 설계하는 것이다.

다만 사례는 고객 명단 내보내기 기능을 중심으로 한 설명이다. 모든 AI 시스템에 같은 도구와 검사 조합이 그대로 적용된다고 검증한 자료는 아니다. 또한 화자와 원출처의 신원은 META에서 검증된 값으로 제공되지 않았다. “구글의 애니 왕”이라는 소개와 구글 엔지니어라는 표현은 영상과 전사의 주장으로만 다뤄야 한다.

여기까지만 이해하면 충분

  • AI 하네스는 모델 주변에서 기억, 도구 연결, 권한, 실행 피드백과 완료 검사를 관리하는 소프트웨어 층이다.
  • 세션·상태·장기 기억은 역할이 다르며, 판단을 실제 행동으로 바꾸려면 도구와 실패 복귀가 있는 작업 흐름이 필요하다.
  • 샌드박스와 권한 통제는 피해 범위를 줄이지만, 프롬프트 인젝션과 정보의 외부 전달을 자동으로 해결하지는 않는다.
  • 완료는 AI의 선언이 아니라 자동 검사, AI 검토, 사람의 실제 사용 평가로 확인해야 한다.

오늘 대답할 질문

AI가 코드를 아는 것을 안전하고 검증 가능한 실제 완료로 바꾸려면, 하네스의 네 가지 설계 질문을 어떻게 연결해야 하는가?

  • 세션, 상태, 장기 기억은 각각 무엇을 보관하는가?
  • 검사 실패는 어떤 경로로 코드 변경에 다시 연결되어야 하는가?
  • 실행 장소와 정보의 이동 경로, 자동 평가와 사람 평가는 왜 따로 확인해야 하는가?

비유와 깨지는 지점

숙련공과 안전한 작업장

모델은 작업 방법을 제안하는 숙련공에 가깝고, 하네스는 작업일지, 공구함, 출입 권한, 검사표, 재작업 절차를 갖춘 작업장에 가깝다. 숙련공이 유능해도 공구가 없거나 출입 범위가 무제한이거나 검수가 없다면 안전하게 일을 끝냈다고 보기 어렵다.

비유가 깨지는 지점: 실제 하네스는 사람처럼 상황을 이해하는 감독자가 아니라 세션 저장소, 도구 인터페이스, 권한 통제, 작업 그래프, 평가 코드로 이루어진 소프트웨어다. 작업장 비유만으로 모델의 오류 가능성이나 정보가 외부 모델과 기록으로 전달되는 경로까지 설명할 수는 없다.

코드를 아는 것과 파일을 수정하고 도구 결과를 받아 실패를 고치며 권한을 지키고 완료를 검증하는 것은 서로 다른 일이다. 모델의 판단을 실제 행동에 연결하는 도구, 순서를 정하는 작업 흐름, 실행 환경, 권한 통제, 평가 기준이 없으면 코드 생성 이후의 과정이 비어 있게 된다.

세션과 상태의 차이, 샌드박스와 정보 이동 통제의 차이를 각각 설명해 보라.

모범 답안 보기

세션은 메시지, 도구 호출, 결과가 포함된 전체 대화 기록이고 상태는 프로그램이 현재 작업에 필요한 값을 직접 읽고 바꾸는 메모판이다. 샌드박스는 코드가 접근할 수 있는 파일과 네트워크를 제한하지만, 도구 출력이 외부 모델이나 기록 저장소로 전달되는 것까지 자동으로 막지는 않는다. 따라서 실행 위치와 정보의 목적지를 따로 검사해야 한다.

3. 적용

다음 AI 코딩 작업에서 무엇을 하네스가 확인해야 완료라고 판단할 것인가?

모범 답안 보기

먼저 요구 결과를 관찰 가능한 조건으로 적는다. 이어 어떤 맥락을 세션·상태에 둘지, 어떤 도구를 어떤 순서로 호출할지, 실패 결과를 어디로 되돌릴지, 파일·네트워크·데이터 접근을 어디까지 허용할지 정한다. 마지막으로 코드로 판정할 검사와 사람만 발견하기 쉬운 사용성 검사를 구분한다. 실제 작업과 시스템 상태는 확인되지 않았으므로, 이 기준을 다음 저위험 작업에서 먼저 시험한다.

이번 글의 통찰

1. 모델의 능력과 시스템의 완료 능력은 다르다

  • [원문] 화자는 모델 주변의 하네스가 맥락을 제공하고, 도구를 연결하며, 권한과 환경 사이의 반복 통신을 관리한다고 설명한다.
  • [해석] AI 시스템을 평가할 때 생성된 코드만 보지 말고, 실패가 다시 수정으로 돌아가는 경로와 완료 증거까지 함께 봐야 한다.
  • [경계] 고객 명단 내보내기라는 한 사례의 설명이며, 모든 작업에서 동일한 구성 요소가 충분하다고 검증한 자료는 아니다. 제목의 “네 가지”는 마지막 네 질문과 대응하지만, 각 질문 아래에는 여러 하위 구성 요소가 있다.

2. 보안은 주의 문구가 아니라 강제 가능한 경계다

  • [원문] 화자는 제한된 권한, 자격 증명 격리, 네트워크 제한, 민감 작업 전 사람의 승인을 소프트웨어가 집행해야 하며 샌드박스만으로 프롬프트 인젝션이 해결되지는 않는다고 말한다.
  • [해석] 안전 설계의 핵심은 모델이 지시를 잘 따르기를 기대하는 것이 아니라, 잘못 판단해도 실행 가능한 피해 범위를 줄이는 것이다.
  • [경계] 영상은 구체적인 공격 성공률이나 방어 성능을 제시하지 않는다. 로컬 실행 여부만으로 정보의 목적지와 보관 기간을 판단할 수도 없다.

3. 완료 기준은 자동 검사와 사람의 관찰을 겹쳐야 한다

  • [원문] 예제 고객 열 명의 이름과 이메일을 자동으로 확인하고, AI 심판의 판단은 사람의 검토와 비교하며, 사람이 버튼의 문구와 위치까지 직접 살피라고 설명한다.
  • [해석] 정확한 데이터, 실제 작동, 이해하기 쉬운 경험은 서로 다른 증거가 필요하다. 하나의 검사로 세 항목을 모두 증명하려 하면 사각지대가 생긴다.
  • [경계] AI 심판도 실수할 수 있고 사람의 검토도 모든 문제를 보장하지 않는다. 전사 내부에서 두 검사는 단위 테스트와 브라우저 테스트로 일치하고, 열 명의 입력과 열 명의 기대 결과도 충돌하지 않지만 실제 시험 결과는 제공되지 않았다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 영상은 “AI가 완료했다고 말함”과 “검사를 통과하고 실제로 작동함”을 구분한다.
  • 통찰: 학습자의 “이해했다”는 말도 세션 기록처럼 참고 자료일 뿐이다. 보지 않고 설명하는 검사와 새 사례에 적용하는 행동 검사를 함께 두는 구조로 옮길 수 있다.
  • 질문/행동: 한 개념을 가르친 뒤 설명 검사와 적용 검사 중 어느 쪽에서 막혔는지 따로 기록해 볼 수 있는가?

사업가 · 구조적 비유

  • 관련성: 가짜 고객 자료, 접근 권한, 재시도 한도, 사람 승인에는 품질·비용·위험·자원 배분 문제가 함께 들어 있다.
  • 통찰: APOM·이커머스·물류 업무에 적용한다면 실제 고객 자료를 주기 전에 샘플 자료로 결과와 권한 범위를 검증해야 한다는 가설을 세울 수 있다. 현재 적용 여부는 확인되지 않았다.
  • 질문/행동: 자동화 후보 하나에서 실제 데이터 없이 검증할 수 있는 샘플 입력과 완료 증거는 무엇인가?

마케터 · 구조적 비유

  • 관련성: “기능이 완성됐다”는 문장은 주장이고, 버튼을 눌러 받은 파일과 정확한 필드는 관찰 가능한 증거다.
  • 통찰: 상세페이지의 효능 문장도 주장만 반복하기보다 사용자가 수행할 행동과 확인할 결과를 짝지어야 한다. 다만 소프트웨어 테스트가 마케팅 주장을 자동으로 입증하는 것은 아니다.
  • 질문/행동: 핵심 주장 하나를 골라 고객이 직접 관찰할 수 있는 결과와 아직 검증되지 않은 부분을 분리해 쓸 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 세션·상태, MCP 도구, ADK 그래프, 샌드박스, 권한, 결정적 평가가 에이전트 시스템의 직접 구성 요소로 제시된다.
  • 통찰: 기술 이름보다 작업에 필요한 기억, 도구 순서, 접근 범위, 완료 증거를 먼저 정해야 한다. 특히 실패 결과가 코드 수정으로 실제 복귀하는 경로와 재시도 한도가 필요하다.
  • 질문/행동: 다음 저위험 코딩 작업을 시작하기 전에 네 질문과 실패 복귀 경로를 한 장에 적어 볼 수 있는가?

작은 실험 하나

  • 측정 1개: 두 검사가 모두 통과할 때까지 발생한 재시도 횟수
  • 중단 기준 1개: 실험용 한도인 재시도 2회 안에 두 검사가 모두 통과하지 않으면 자동 확대를 멈추고 사람이 원인을 검토한다.

# 섹션 요지
1 코드와 실제 완료의 간격 모델 주변의 하네스가 맥락, 도구, 권한, 환경 통신을 연결한다.
2 세션·상태·장기 기억 전체 기록, 현재 작업값, 다음 대화에 남길 정보를 구분한다.
3 도구와 작업 흐름 MCP로 도구를 연결하고 ADK 그래프로 검사·분기·재시도를 구성한다.
4 실행 환경과 권한 샌드박스, 제한 권한, 자격 증명 격리, 사람 승인을 사용한다.
5 정보가 가는 곳 로컬 실행과 데이터의 외부 전달·저장은 별개다.
6 완료 평가 결정적 검사, AI 심판, 사람의 실제 사용 평가를 겹친다.
7 네 가지 질문 기억, 도구와 순서, 접근 범위, 완료 기준을 확인한다.

1. 코드 생성과 실제 완료의 간격

영상은 고객 명단을 내려받는 버튼을 예로 든다. 코드를 아는 것과 파일을 수정하고 결과를 확인하는 것은 다른 일이라고 설명한다.

전사에서 “구글의 애니 왕”으로 소개된 인물의 영어 발화를 인용하며, 모델 주변의 소프트웨어 층인 AI 하네스가 다음 역할을 맡는다고 설명한다.

  • 맥락 제공
  • 도구 연결
  • 권한 집행
  • 모델과 환경 사이의 반복 통신 관리

이 신원과 소속은 전사와 영상의 소개이며, META provenance의 검증된 creator·affiliation 값은 아니다.

2. 세션, 상태, 장기 기억

최초 요청은 고객 명단 전체였지만 후속 지시에서 이름과 이메일만 포함하도록 조건이 바뀐다. 영상은 긴 작업에서도 이 변경 조건을 잃지 않아야 한다고 말한다.

  • 세션: 사용자 메시지, 에이전트의 도구 호출, 결과를 포함한 전체 대화 기록
  • 상태: 이름, 이메일, 테스트 준비 같은 값을 키-값 형태로 저장하고 코드가 직접 읽고 갱신하는 메모판
  • 장기 기억: 다음 대화에서도 사용할 정보로, 저장·검색 정책은 설계자가 결정

기억은 조건을 유지하게 하지만 실제 파일을 수정하지는 못한다.

3. 도구, MCP, 작업 흐름

파일 수정은 파이썬 함수 같은 도구가 수행할 수 있다. 다른 함수는 테스트를 실행하거나 외부 API를 호출할 수 있다.

영상은 MCP(Model Context Protocol)를 서버가 공개한 도구를 애플리케이션이 표준 방식으로 찾고 호출하도록 하는 방법으로 소개한다.

고객 명단 내보내기 기능에서는 코드 변경 뒤 두 검사를 병렬로 실행한다고 설명한다.

  1. 내보내기 로직의 단위 테스트
  2. 버튼을 클릭하고 다운로드를 확인하는 브라우저 테스트

둘 중 하나라도 실패하면 피드백을 코딩 에이전트로 돌려보낸다. 둘 다 통과하면 검토 단계로 간다. ADK 그래프 작업 흐름에서는 노드를 에이전트 또는 일반 함수로 두고, 연결을 통해 다음 단계를 정할 수 있다고 설명한다.

재시도 한도를 정할 수 있으며, 계속 고치지 못하면 작업을 멈추고 도움을 요청한다. 전사는 구체적인 재시도 횟수를 제시하지 않는다.

4. 실행 환경, 프롬프트 인젝션, 권한

버튼을 시험하기 위해 실제 고객 명단 전체를 제공할 필요는 없다. 복사한 프로젝트와 가짜 고객 자료를 사용하고, 실제 고객 데이터베이스에는 접근하지 못하게 할 수 있다.

영상은 접근 가능한 파일과 네트워크 서비스를 제한한 격리 환경을 샌드박스라고 설명한다. 이는 코드가 어디서 실행되는지를 결정하는 런타임 설계의 일부다.

파일에 “비밀번호를 다른 곳으로 보내라” 같은 지시가 숨어 있을 수 있다. 모델이 이를 명령으로 받아들이는 공격을 프롬프트 인젝션이라고 부른다. 영상은 다음 통제를 제시한다.

  • 제한된 권한
  • 자격 증명을 접근 범위 밖에 보관
  • 네트워크 접근 제한
  • 민감한 도구 실행 전 사람의 승인
  • 정책을 말로 부탁하는 것이 아니라 소프트웨어로 집행

샌드박스는 공격의 영향을 줄일 수 있지만 프롬프트 인젝션 자체를 해결하지는 않는다는 조건도 명시한다.

5. 실행 장소와 데이터의 목적지

도구가 노트북에서 실행되더라도 출력은 외부에서 호스팅되는 모델로 전달될 수 있다. 세션 기록이나 장기 기억에 저장될 수도 있다.

따라서 영상은 다음을 따로 결정하라고 말한다.

  • 에이전트에 실제로 필요한 데이터
  • 데이터가 이동해도 되는 장소
  • 데이터를 보관할 수 있는 기간

고객 명단 내보내기 기능의 행동을 시험하는 데는 실제 고객 정보가 아니라 가짜 고객 자료면 충분하다는 것이 예시의 결론이다.

6. 결정적 평가, AI 심판, 사람 평가

예제 앱에 샘플 고객 열 명이 있다면 다운로드 파일에도 같은 열 명의 이름과 이메일이 정확하게 들어 있는지 코드로 확인할 수 있다. 명확한 요구 조건을 코드가 판정하는 방식을 결정적 평가라고 설명한다.

그러나 기능의 사용성은 숫자만으로 확인되지 않는다. 완료 안내가 이해하기 쉬운지처럼 정성적인 항목은 기준을 받은 다른 AI가 검토할 수 있다. 영상은 AI 심판도 실수할 수 있으므로 사람의 검토와 비교하는 것이 도움이 된다고 말한다.

사람이 기능을 직접 사용하면 다음 문제를 발견할 수 있다.

  • 다운로드는 되지만 버튼 이름이 혼란스러움
  • 버튼을 페이지에서 찾기 어려움
  • 현재 자동 검사에 포함되지 않은 사용자 경험 문제

한국어 내레이션은 “Claude 개발사의 실무 기록”에서 코드 검사만으로 놓친 문제를 실제 브라우저 조작으로 발견했다고 주장한다. 다만 해당 기록의 제목, 링크, 작성자, 조건은 제공되지 않았다.

7. 마지막 네 가지 질문

영상은 AI 앱을 볼 때 다음 질문을 던지라고 정리한다.

  1. 무엇을 기억하는가?
  2. 어떤 도구를 어떤 순서로 사용하는가?
  3. 어디까지 접근할 수 있는가?
  4. 무엇을 확인해야 완료인가?

제목의 “네 가지 설계”와 마지막 열거의 개수는 일치한다. 전사 내부 수량 대조에서도 다음 항목은 충돌하지 않는다.

  • 두 검사: 단위 테스트와 브라우저 테스트
  • 샘플 고객 열 명: 입력 열 명과 결과 파일의 기대 열 명
  • 네 질문: 기억, 도구·순서, 접근 범위, 완료 기준

다만 네 질문 아래에 세션·상태·장기 기억, MCP, ADK, 샌드박스, 데이터 경로, 세 평가 층 등 여러 하위 요소가 있으므로 “구성 요소가 정확히 네 개뿐”이라는 뜻으로 확대하면 안 된다.

출처 정체성의 경계

  • 전사와 META 설명은 인물을 Annie Wang 또는 애니 왕으로 소개하고 구글과 연결한다.
  • META의 provenance.creator와 provenance.affiliation은 모두 비어 있다.
  • META의 provenance note는 원본 영상 링크를 검증하지 못했고 화자 이름과 SNS를 기준으로 추정했다고 적지만, 실제 social link 값도 제공되지 않았다.
  • 따라서 원작자와 소속은 독립 확인된 사실이 아니라 영상·전사의 소개로만 보존한다.

교정 전사 (한국어)

전체 전사 펼치기

코드는 잘 짜는데 왜 일을 끝내지는 못할까요? 고객 명단을 내려받는 버튼 하나를 만든다고 해볼게요. 코드를 아는 것과 파일을 바꾸고 결과를 확인하는 건 서로 다른 일이에요. 구글의 애니 왕은 그 사이를 이어주는 소프트웨어를 하네스라고 설명해요.

그런 일들을 가능하게 하려면 모델 주변에 소프트웨어가 필요하며, 우리는 그 소프트웨어 계층을 AI 하네스(AI harness)라고 부릅니다. AI 하네스는 컨텍스트를 제공하고, 도구를 연결하며, 권한을 적용하고, 모델과 환경 사이에서 오가는 모든 통신을 관리합니다.

이제 같은 버튼을 만드는 과정을 따라가 볼게요. 처음에는 고객 명단 전체를 달라고 했다가 이름과 이메일만 달라고 바꿨어요. 작업이 길어져도 이 조건을 놓치면 안 되겠죠.

세션(session)은 대화 스레드입니다. 세션에는 여러분의 모든 메시지, 에이전트의 도구 호출(tool call), 그리고 그 결과가 기록됩니다. 즉, 대화 전체의 기록이 들어 있습니다. 여러분의 최초 요청과 그에 대한 후속 지시도 모두 세션에 포함됩니다. 그리고 상태(state)가 있습니다.

상태는 애플리케이션을 위한 스크래치패드(scratchpad)에 더 가깝습니다. 예를 들어 상태에 이름과 이메일, 그리고 ‘테스트 준비 완료’와 같은 상태를 키-값 쌍(key-value pair)으로 저장할 수 있습니다. 코드는 전체 대화를 검색하지 않고도 해당 값을 직접 읽고 업데이트할 수 있습니다.

대화 기록은 작업일지, 상태는 지금 필요한 값을 적는 메모라고 보면 돼요. 여기에 다음 대화에서도 쓸 취향을 보관하면 장기 기억이 돼요. 무엇을 저장하고 다시 꺼낼지는 설계자가 정해요. 그런데 기억만으로 파일을 고칠 수는 없어요. 실제로 손을 움직일 도구가 필요해요.

“이 파일을 수정해야겠다”고 결정할 수는 있지만, 그 결정만으로 파일 자체가 바뀌지는 않습니다. 실제로 수정하려면 도구가 작업을 적용해야 하며, 그 도구는 Python 함수일 수 있습니다. 또 다른 함수는 테스트를 실행하거나 외부 API를 호출할 수 있습니다. MCP 서버를 통해 도구들을 연결할 수도 있습니다. MCP는 Model Context Protocol(모델 컨텍스트 프로토콜)의 약자입니다. MCP는 애플리케이션이 서버에서 제공하는 도구를 표준적인 방식으로 검색하고 호출할 수 있도록 해줍니다.

도구는 일을 하는 방법이고 작업 흐름은 그 방법을 어떤 순서로 쓸지 정하는 거예요. 파일을 잘 만들었어도 버튼을 눌렀을 때 내려받기가 안 될 수 있죠. 그래서 코드 검사와 실제 버튼 검사를 함께 돌려요.

CSV 기능의 경우, 코딩 에이전트가 먼저 변경 작업을 수행하고, 그다음 두 가지 검사가 병렬로 실행되도록 할 수 있습니다. 한 검사는 내보내기 로직(export logic)에 대한 단위 테스트(unit test)이고, 다른 검사는 버튼을 클릭해 다운로드를 확인하는 브라우저 테스트(browser test)입니다. 둘 중 하나라도 실패하면 워크플로가 그 피드백을 코딩 에이전트에 전달합니다.

두 검사 모두 통과하면 다음 단계인 검토 단계(review step)로 넘어갑니다. ADK 그래프 워크플로(ADK graph workflow)를 사용하면 이러한 구조를 정의할 수 있습니다.

노드는 에이전트일 수도 있고 일반 함수일 수도 있으며, 연결은 다음에 어떤 일이 일어날지를 결정합니다. 재시도 제한(retry limit)도 설정할 수 있습니다. 에이전트가 문제를 해결하지 못한 채 계속 시도하면 워크플로가 중단되고 도움을 요청합니다.

이제 실행할 장소를 정할 차례예요. 버튼 하나 시험하려고 실제 고객 명단 전체를 맡길 필요는 없겠죠. 연습용 프로젝트와 가짜 고객 자료를 따로 주면 돼요. 이렇게 접근할 파일과 네트워크를 제한한 공간을 샌드박스라고 해요.

코딩 에이전트(coding agent)에는 흔히 샌드박스(sandbox)가 필요합니다. 샌드박스는 어떤 파일과 네트워크 서비스에 접근할 수 있는지 제한된 격리 환경입니다. 내보내기 작업(export task)을 위해서는 프로젝트 사본과 일부 샘플 고객 데이터를 제공할 수 있습니다. 운영 고객 데이터베이스에는 접근하지 않고 그곳에서 작업할 수 있습니다. 이것이 바로 런타임 설계(runtime design)의 일부로, 코드가 어디에서 실행될지 결정하는 일입니다.

하지만 연습 공간 안에도 수상한 글이 들어올 수 있어요. 파일에 비밀번호를 다른 곳으로 보내라는 지시가 숨어 있을 수 있어요. 이런 공격을 프롬프트 인젝션이라고 불러요. 파일에서 읽은 글을 새 명령으로 받아들이지 않고, 실제 도구가 할 수 있는 일도 따로 제한해야 해요.

실제로 수행할 수 있는 작업을 제한하는 통제 장치도 필요합니다. 제한된 권한, 접근할 수 없도록 보관된 자격 증명(credential), 네트워크 접근 제한 등이 이에 해당합니다.

민감한 작업의 경우, 하네스(harness)가 일시 중지한 뒤 도구 실행을 계속하기 전에 승인을 요청하도록 할 수 있습니다. 이러한 통제 장치는 소프트웨어로 강제되어야 합니다. 단순히 모델에게 주의하라고 지시하는 것만으로는 충분하지 않습니다. 샌드박스(sandbox)는 공격의 영향을 제한하는 데 도움이 되지만, 그 자체로 프롬프트 인젝션(prompt injection)을 해결해 주지는 않습니다.

여기서 한 가지를 더 확인해야 해요. 프로그램이 내 컴퓨터에서 돈다고 해서 자료도 전부 그 안에만 남는 건 아니에요. 도구가 읽은 내용이 모델에 전달되거나 기록으로 저장될 수 있거든요.

실행 장소와 정보가 가는 곳을 따로 살펴야 해요. 원본은 이 차이를 이렇게 설명해요.

도구(tool)가 노트북에서 실행되더라도 그 출력이 호스팅 모델(hosting model)로 전송될 수 있습니다. 또한 세션 기록 로그(session history logs)나 장기 메모리(long-term memory)에 저장될 수도 있습니다. 에이전트(agent)에게 실제로 어떤 데이터가 필요한지, 그 데이터가 어디로 이동해도 되는지, 얼마나 오래 보관해야 하는지를 생각해 보세요. 저희 내보내기 기능(export feature)은 실제 고객 정보를 노출하지 않고도 동작을 테스트할 수 있으므로, 가짜 고객 데이터(fake customer data)만으로도 충분합니다.

마지막은 완료를 판단하는 기준이에요. AI가 다 됐다고 말해도 실제 파일을 확인하기 전에는 알 수 없죠. 예제 고객의 이름과 이메일이 결과 파일에도 빠짐없이 들어갔는지 확인해야 해요.

테스트 앱에 샘플 고객이 10명 있다고 해보겠습니다. 다운로드한 파일에 올바른 이름과 이메일 주소를 가진 동일한 10명의 고객이 들어 있나요? 이를 자동으로 확인하는 코드를 작성할 수 있으며, 이것이 결정론적 평가(deterministic evaluation)입니다. 명확한 요구 사항을 정의하고, 코드가 결과가 이를 충족하는지 확인하는 것입니다.

하지만 숫자가 맞는 것만으로 사용하기 좋은 기능이 되지는 않아요. 완료 안내가 이해하기 쉬운지는 다른 AI에게 기준을 주고 검토하게 할 수 있어요. Claude 개발사의 실무 기록에서도 코드 검사만으로 놓친 문제를 실제 브라우저 조작으로 찾아냈어요.

평가기(judge)는 실수할 수 있으므로, 평가 결과를 사람의 검토와 비교하는 것이 매우 유용합니다.

이제 사람의 평가(human evaluation)로 넘어가겠습니다. 직접 해당 기능을 사용해 보세요. 다운로드는 작동하지만 버튼의 라벨이 혼란스러울 수도 있고, 페이지에서 버튼을 찾기 어려울 수도 있습니다. 사용자 경험을 검토하는 사람은 현재 자동화된 검사로는 다루지 못하는 문제를 발견할 수 있습니다.

한 앱을 볼 때는 이런 질문을 던져 보세요. 무엇을 기억하나요? 어떤 도구를 어떤 순서로 쓰나요? 어디까지 접근할 수 있나요? 무엇을 확인해야 완료인가요? 이 기준을 정하면 똑똑한 모델이 실제 일을 끝내도록 도울 수 있어요.

영상이 도움이 되셨다면 구독과 좋아요 부탁드립니다. 시청해주셔서 감사합니다. 다음 영상에서 뵙겠습니다.
