먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

회사가 AI로 더 많은 코드를 만들수록 새 병목은 코드 작성이 아니라 검토와 검증으로 옮겨간다. 여기서 풀 리퀘스트(PR)는 작성한 코드 변경을 기존 코드에 합치기 전에 검토해 달라고 올리는 제안이다. 화자 닥시 굽타는 PR이 열리면 AI가 변경 내용을 읽고 리뷰 댓글을 남기는 기본 구조부터 출발한다.

이 기본 구조는 비교적 단순하다. 격리된 실행 환경인 샌드박스에 Codex나 Claude Code 같은 에이전트를 넣고, GitHub 또는 GitLab에서 PR이 열렸다는 신호를 받는다. 에이전트는 변경 내용을 검토한 뒤 GitHub 리뷰 API 등을 통해 댓글을 돌려준다. 특정 모델에 묶이지 않으려면 OpenCode나 Pi 같은 실행 틀을 사용할 수 있다고 화자는 제안한다.

하지만 댓글이 돌아온다는 사실과 믿을 만한 리뷰가 된다는 사실은 다르다. 실제로 쓰려면 놓친 버그, 맥락 부족, 비용, 사소한 지적, 반복 실행 때마다 달라지는 결과를 함께 다뤄야 한다.

읽는 법: 위에서 아래로 읽는다. 첫 상자 안에서도 PR 열림 → 변경 내용 전달 → AI 검토 → 댓글 반환 순서로 세로 이동한다. 실패 요인과 개선책 안의 카드들은 서로 앞뒤가 정해진 단계가 아니라 같은 층에 놓인 병렬 항목이다. 이 그림은 측정값이 아니라 영상의 주장 구조를 정리한 개념도다.

왜 “버그를 못 찾지 않았다”는 것을 증명하기 어려운가

프롬프트를 “이 PR을 리뷰해 줘”에서 더 구체적인 지시로 바꾸면 댓글 수와 내용이 크게 달라질 수 있다. 화자는 과거 장애와 사고를 조사해 자주 발생한 버그 유형을 목록으로 만들고, 그 유형을 집중적으로 찾게 하라고 말한다. 동시에 스타일이나 과도한 방어 코딩처럼 사소한 지적은 제외하도록 정의해야 한다.

문제는 리뷰 에이전트가 버그를 발견하면 버그가 있다는 것은 보여줄 수 있지만, 아무것도 찾지 못했다고 해서 버그가 없다는 것까지 증명하지는 못한다는 점이다. 특히 화자는 치명적 버그가 매우 드물다고 주장한다. 그래서 평소 PR에서 별문제가 없었다는 관찰만으로 새 프롬프트가 안전하다고 판단하면, 실제로는 중요한 버그를 놓치고 있어도 오랫동안 알아차리지 못할 수 있다.

읽는 법: 모바일에서는 표 안을 좌우로 이동한다. 각 행을 왼쪽에서 오른쪽으로 읽으며 관찰 → 알 수 있는 것 → 남는 불확실성 → 보완 방법을 비교한다. 수치 그래프가 아니라 검증 논리를 나타낸 비교표다.

화자가 제안하는 평가법은 과거 장애나 사고를 일으킨 PR을 모아, 새 버전의 리뷰 에이전트가 당시 버그를 얼마나 자주 찾아내는지 반복해서 확인하는 것이다. 다만 과거 데이터만으로 모든 미래 버그를 덮을 수는 없다. 화자는 버그의 약 80~90%가 과거 실수의 반복이라고 주장하면서도, 코드 작성 속도가 빨라질수록 전에 없던 실패도 생긴다고 말한다. 따라서 데이터셋을 계속 갱신해야 한다는 결론을 낸다.

같은 모델의 눈으로 자신을 검사하지 않기

화자는 코드 작성 모델과 리뷰 모델의 실패 양상이 다르다고 주장한다. 같은 모델이 작성과 검토를 모두 맡으면 작성할 때의 맹점을 검토할 때도 반복할 수 있으므로, Claude Code가 작성했다면 GPT 계열로 검토하는 식의 모델 교차 검토(model inversion)를 권한다.

어떤 모델이 작성했는지는 브랜치 이름이나 커밋·PR 설명의 흔적으로 추정할 수 있지만, 화자에 따르면 약 80% 정도만 그렇게 식별할 수 있고 나머지는 별도 휴리스틱이나 사용 현황 자료가 필요하다. Greptile에서 모델을 뒤집었을 때 검출률이 10% 높아졌다는 주장도 나온다. 그러나 데이터셋, 표본, 기준이 제시되지 않았으므로 이 수치는 화자의 내부 관찰로만 읽어야 한다.

코드를 읽는 것과 시스템을 이해하는 것은 다르다

검색 도구로 관련 파일을 많이 읽는 것만으로는 충분한 맥락을 얻기 어렵다고 화자는 말한다. 인증 우회 여부를 판단하려면 특정 코드가 인증된 환경에서 실행되는지, 어떤 흐름과 파일이 연결되는지를 알아야 한다. 코드가 문법적으로 맞고 버그가 없더라도 작성자가 원한 기능과 다를 수도 있다.

그래서 코드 자체뿐 아니라 Jira·Linear 같은 티켓, Confluence·Notion 같은 문서, 코드 구조를 정리한 지식 기반이 중요하다고 설명한다. Greptile은 코드, 문서, 티켓, 운영 로그와 텔레메트리를 연결한 “살아 있는 위키”를 사용한다고 주장한다. 이는 필요한 파일만 더 정확히 고르고, 회사의 의도와 시스템 흐름을 리뷰에 공급하기 위한 장치다.

읽는 법: 위에서 아래로 읽는다. 첫 상자의 세 재료는 병렬 입력이며, 가운데에서 결합된 뒤 정적 검토와 실행 검증이라는 두 갈래로 나뉜다. 두 갈래는 우열이 아니라 서로 다른 실패를 찾는 보완 관계다.

실행 검증이 필요한 이유는 코드를 읽었을 때 정상으로 보여도 실제 화면에서는 버튼이 휴대전화에서 가려질 수 있기 때문이다. 화자는 의존성이 갖춰진 가상 머신에 PR 버전의 앱을 띄우고, 인증이나 가입 같은 흐름 지도를 제공한 뒤, 에이전트가 컴퓨터 사용 기능과 시각 모델로 처음부터 끝까지 시험하게 한다고 설명한다. 다만 이를 위해서는 앱을 쉽게 띄울 수 있는 빌드 스크립트와 문서화된 흐름이 필요하며, Greptile도 이 구성을 어려운 부분으로 본다고 말한다.

모든 작업에 가장 비싼 모델을 쓰지 않기

이런 검증을 모두 수행하면 비용이 여전히 높다. 화자는 중요한 버그 분석과 핵심 리뷰에는 성능이 높은 최전선 모델을 쓰고, 탐색적 파일 읽기나 맥락 선별에는 작은 모델을 배치하는 방식을 설명한다. Greptile의 현재 사용량은 약 20%가 최전선 모델이며, 실제로는 약 20개의 세부 작업마다 모델을 따로 고른다고 주장한다.

핵심 원리는 싼 모델로 바꾸는 것 자체가 아니라, 어떤 작업을 바꿔도 검출 능력이 유지되는지 데이터로 확인하는 것이다. 평가 자료가 없다면 비용은 줄었지만 중요한 버그를 더 많이 놓치는지 알 수 없다.

결국 이 영상의 중심은 “AI에게 PR을 읽혀 댓글을 달게 하는 법”이 아니다. 드문 실패를 어떻게 평가할지, 작성 모델의 맹점을 어떻게 교차 검토할지, 코드 밖의 의도와 실행 환경을 어떻게 제공할지, 비용 절감이 성능 저하로 이어지지 않았는지 어떻게 확인할지가 실전 문제다.

다만 영상의 수치와 성능 평가는 대부분 화자 또는 Greptile의 내부 관찰로 제시되며 독립 검증 자료는 제공되지 않는다. 또한 비용 범위, 치명적 버그의 빈도 단위, 개선 단계의 개수에는 전사 안의 불일치나 모호함이 있다. 따라서 숫자를 보편적 기준으로 옮기기보다, 자신의 과거 사고 데이터와 작업별 평가로 다시 검증해야 한다.

여기까지만 이해하면 충분

  • AI가 PR에 댓글을 남긴다는 사실만으로 버그를 충분히 잡았다고 결론 내릴 수 없다.
  • 과거 사고 PR을 이용해 검출 능력을 시험하고, 새 사고가 생기면 평가 자료를 갱신해야 한다.
  • 작성 모델과 다른 모델의 교차 검토, 코드·문서·티켓 맥락, 샌드박스 실행 시험은 서로 다른 맹점을 보완한다.
  • 작은 모델로 비용을 줄일 때도 같은 평가 지표로 버그 검출 성능이 유지되는지 확인해야 한다.

비유와 깨지는 지점

공항 보안 검색대

기본 AI 리뷰는 가방을 한 번 훑는 검색대와 비슷하다. 과거 사고 PR은 금지 물품이 들어 있다는 사실을 미리 아는 시험 가방이고, 모델 교차 검토는 다른 방식의 검색 장비로 다시 확인하는 일에 가깝다. 코드베이스 맥락은 승객과 수하물의 이동 경로를 함께 보는 정보에 대응한다.

비유가 깨지는 지점: 공항의 금지 물품은 비교적 고정된 분류를 가질 수 있지만, 화자는 소프트웨어의 버그 유형과 코드 구조가 계속 변한다고 말한다. 또한 코드 리뷰는 물건의 존재만 찾는 일이 아니라 작성 의도와 실행 결과까지 판단해야 한다.

먼저 파일 선별처럼 단순한 작업과 핵심 버그 판단처럼 중요한 작업을 구분한다. 작은 모델로 바꿀 후보 작업을 하나만 정하고, 같은 과거 사고 PR 데이터에서 교체 전후의 핵심 버그 검출 여부를 비교한다. 비용이 줄어도 알려진 버그를 놓친다면 확대하지 않는다. 차드의 현재 코드 리뷰 시스템 상태는 출처에 없으므로 실제 적용 여부는 별도로 확인해야 한다.

이번 글의 통찰

1. 자동화의 병목은 생성에서 검증으로 이동한다

  • [원문] 화자는 AI로 코드를 작성하는 사람이 늘면서 리뷰와 검증이 새 병목이 되었다고 말한다. 기본 에이전트는 PR을 받아 약 5분 뒤 댓글을 돌려줄 수 있지만, 버그 누락과 맥락 부족이 남는다고 설명한다.
  • [해석] 자동화가 산출물 생산을 빠르게 만들수록 다음 경쟁력은 더 많이 만드는 능력보다, 드문 고위험 실패를 골라내는 평가 체계에서 생길 수 있다.
  • [경계] 코드 생산량과 병목 이동의 정도를 보여주는 외부 자료는 제공되지 않았다. 약 5분이라는 시간도 화자의 예시이며 모든 환경의 응답 시간을 뜻하지 않는다.

2. 평가 자료가 없으면 성능 개선과 비용 절감을 구분하기 어렵다

  • [원문] 화자는 과거 사고 PR을 평가 데이터로 사용하고, 작은 모델로 세부 작업을 바꿀 때도 이 데이터로 버그 검출 저하를 확인해야 한다고 말한다.
  • [해석] 프롬프트, 모델, 검색 방식, 비용 정책을 바꿀 때 같은 시험 문제를 반복해야 변화가 개선인지 단순한 출력 차이인지 판단할 수 있다.
  • [경계] 과거 데이터는 미래의 새로운 버그를 완전히 대표하지 않는다. 화자가 언급한 “버그의 80~90%는 과거 실수의 반복”이라는 수치의 표본과 계산법도 제시되지 않았다.

3. 영상의 수치는 평가 가설이지 보편 기준이 아니다

  • [원문] 화자는 PR당 비용, 치명적 버그 빈도, 모델별 오류 유형, 교차 모델의 검출률 향상 등 여러 내부 수치를 제시한다.
  • [해석] 이 숫자는 그대로 도입 기준으로 쓰기보다 무엇을 측정해야 하는지 알려주는 후보 지표로 읽는 편이 안전하다.
  • [경계]
  • 비용은 앞부분에서 PR당 3~25달러, 뒤에서는 3달러에서 15달러 또는 20달러라고 말해 상한이 일치하지 않는다.
  • 치명적 버그 빈도는 PR 1,000건당 1건 또는 코드 1,000줄당 1건으로 제시된다. 분모가 달라 같은 빈도로 합칠 수 없다.
  • “Codex 모델이 GPT 모델보다 일회성 오류를 약 3배 더 만든다”는 표현은 두 모델 범주의 분류 기준이 설명되지 않아 범주가 겹치는지 판단할 수 없다.
  • 모델 교차 검토의 검출률 10% 향상을 교차 검토하지 않을 때의 사고 가능성 10% 증가로 이어 말하지만, 두 비율이 수학적으로 같은지는 근거가 없다.
  • 자율 테스트를 “마지막”이라고 했다가 “다섯 개 중 네 번째일 수 있다”고 말한다. 프롬프트, 과거 PR, 모델 교차, 코드 맥락, 자율 테스트, 모델 배분이 모두 제시되어 개선 단계의 정확한 개수가 불명확하다.
  • “추론이 전년도 GDP 성장의 한 자릿수 퍼센트포인트를 차지했다”는 주장의 출처와 계산 근거는 제공되지 않았다.
  • 화면 예시의 “iPhone Duo”라는 기기 명칭은 전사상 정확한 고유명사인지 확인되지 않았다.
  • META의 원본 출처 메모는 원본 영상 링크를 확인하지 못했고 화자 이름과 SNS를 기준으로 출처를 추정했다고 밝힌다. 화자는 전사 도입부에서 닥시 굽타로 소개되지만 원작자와 원본 링크는 독립 확인되지 않았다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 화자는 리뷰 에이전트가 버그의 존재는 알려도 부재는 증명하지 못한다고 구분한다. 이는 학습자가 답을 한 번 맞혔다는 사실과 개념을 안정적으로 이해했다는 사실을 구분하는 문제와 직접 닿는다.
  • 통찰: 정답을 아는 과거 사례를 바꿔 가며 설명과 적용을 반복하게 해야 이해의 범위를 관찰할 수 있다.
  • 질문/행동: 학습자가 익숙한 예시뿐 아니라 새 사례에서도 원인과 판단 기준을 설명하는지 확인한다.

사업가 · 구조적 비유

  • 관련성: 영상은 자동화의 가치가 검토 시간 절약만이 아니라 사고 위험, PR당 비용, 잘못된 경고로 인한 노동에 의해 결정된다고 보여준다.
  • 통찰: APOM·이커머스·물류의 실제 시스템 상태는 출처에 없지만, 자동 검수 도입을 검토한다면 처리량 증가와 함께 치명적 누락·오탐·검수 비용을 같이 봐야 한다는 구조적 가설을 세울 수 있다.
  • 질문/행동: 검증 전 가상 적용으로, 자동화가 놓치면 가장 손실이 큰 과거 사례를 평가 문제로 만들 수 있는지 묻는다.

마케터 · 구조적 비유

  • 관련성: PR당 비용, 10% 검출률, 80~90% 반복 버그 같은 숫자는 주장을 기억하게 만들지만 대부분 내부 관찰이며 검증 조건이 생략되어 있다.
  • 통찰: 상세페이지나 카피에서도 강한 숫자를 제시할 때는 대상, 분모, 비교 기준, 측정 기간을 함께 보여줘야 증거가 된다.
  • 질문/행동: 숫자 주장을 사용할 때 “누가, 무엇과 비교해, 어떤 자료에서 측정했는가”를 바로 옆에 표시한다.

AI/SW 학습자 · 직접 전이

  • 관련성: 프롬프트 개선, 역사적 회귀 평가, 모델 교차, 맥락 검색, 샌드박스 테스트, 모델 라우팅이 모두 에이전트 평가와 아키텍처에 직접 연결된다.
  • 통찰: 모델 이름보다 실패 유형과 작업을 먼저 나누고, 변경 전후를 같은 사고 데이터셋으로 비교해야 한다.
  • 질문/행동: 후보 리뷰 에이전트가 알려진 사고 PR의 핵심 버그를 찾는지부터 확인하고, 통과한 뒤에만 비용 최적화를 시험한다.

가치 지도

"AI가 만든 코드가 늘지만 검토가 병목이 되고 드문 치명적 버그를 놓칠 수 있음" 문제
→ "중요한 버그를 더 일찍 발견하고 불필요한 댓글을 덜 읽음" 수혜자: 개발자와 운영 책임자
→ "과거 PR 데이터·문서·컴퓨팅 비용·검토 시간을 제공" 지불자 또는 자원 제공자: 리뷰 시스템을 운영하는 조직
→ "과거 사고 PR에서 알려진 핵심 버그를 찾아낸 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 사용 가능한 과거 사고 PR이 있다면, 알려진 핵심 버그를 숨긴 채 후보 AI 리뷰 설정으로 PR 한 건을 다시 검토한다.
  • 측정 1개: 알려진 핵심 버그 검출 여부를 검출/미검출로 기록한다.
  • 중단 기준 1개: 핵심 버그가 미검출이면 실제 적용 확대를 중단하고 프롬프트·맥락·모델 구성을 다시 검토한다.

# 섹션 요지
1 기본 구조 샌드박스, 에이전트, PR 웹훅, 리뷰 API를 연결한다.
2 초기 실패 버그 누락, 맥락 부족, 비용, 사소한 댓글, 실행별 결과 차이가 생긴다.
3 프롬프트 개선 자주 발생하는 버그 유형과 제외할 사소한 지적을 명시한다.
4 과거 PR 평가 실제 사고를 일으킨 PR로 검출 능력을 시험하고 계속 갱신한다.
5 모델 교차 검토 작성 모델과 다른 모델을 리뷰에 배치해 공유된 맹점을 줄인다.
6 코드베이스 맥락 코드, 문서, 티켓, 흐름, 로그를 연결해 필요한 맥락을 공급한다.
7 자율 실행 시험 샌드박스에서 앱을 띄워 사용자 흐름과 화면 결과를 확인한다.
8 비용별 모델 배분 핵심 판단과 탐색 작업을 나누어 서로 다른 모델을 배치한다.

1. 기본 리뷰 에이전트

화자는 AI 코딩이 늘면서 코드 리뷰와 검증이 병목이 되었다고 진단한다. 기본 구성은 다음과 같다.

  • Firecracker 같은 도구 또는 상용 서비스를 이용해 샌드박스를 준비한다.
  • Codex나 Claude Code 같은 에이전트를 샌드박스에 넣는다.
  • 특정 모델에 묶이지 않으려면 오픈 소스 실행 틀인 OpenCode나 Pi를 사용할 수 있다고 권한다.
  • GitHub 또는 GitLab을 연결한다.
  • PR이 열리면 웹훅으로 변경 내용을 에이전트에 보낸다.
  • 에이전트가 리뷰한 결과를 GitHub 리뷰 API로 돌려준다.

화자는 이 정도면 약 5분 뒤 피드백을 받을 수 있지만, 이것만으로 완성된 리뷰 시스템이라고 생각하면 문제가 생긴다고 말한다.

2. 기본 구조에서 생기는 문제

첫째, 중요한 버그를 놓친다. 화자는 버그가 계속 더 작은 형태로 나타날 수 있다는 의미로 “프랙탈처럼 무한하다”는 표현을 인용한다.

둘째, 코드베이스의 구조와 방향, 라이브러리 사용법, 저장소 사이의 관계를 오해할 수 있다. 특히 많은 저장소가 연결된 환경에서는 한 PR만 읽어서는 판단하기 어렵다고 말한다.

셋째, 비용이 높다. 앞부분에서는 코딩 에이전트를 이용한 리뷰가 PR당 3~25달러라고 말한다.

넷째, 기술적으로 맞지만 지나치게 사소한 댓글이 쌓인다. 사람에게는 중요한 경고를 찾기 어렵게 만들고, 코딩 에이전트가 댓글을 모두 고치면 지나치게 방어적인 코드가 생길 수 있다고 주장한다.

다섯째, 같은 PR을 다시 실행할 때마다 새로운 지적이 나타날 수 있어 결과가 안정적이지 않다.

3. 프롬프트 최적화

화자가 제안하는 첫 개선은 다음 두 가지다.

  1. 과거 장애와 사고를 조사해 자주 만드는 버그 유형을 목록으로 만들고, 그 유형을 구체적으로 찾게 한다.
  2. 무엇을 사소한 지적으로 볼지 정의하고 그런 댓글은 남기지 말라고 명시한다.

프롬프트를 조금만 바꿔도 댓글 수가 크게 달라질 수 있다. 그러나 댓글 수의 변화만으로 버그 검출이 좋아졌는지는 알 수 없다.

4. 과거 사고 PR로 검증

화자는 치명적 버그가 매우 드물다고 말하며 다음 두 표현을 함께 사용한다.

  • PR 1,000건당 약 1건
  • 코드 1,000줄당 약 1건

두 수치는 분모가 다르므로 같은 통계로 결합할 수 없다. 데이터의 표본과 계산법도 제시되지 않았다.

평가 방법은 과거 장애나 사고를 일으킨 PR을 모으고, 리뷰 에이전트의 각 버전이 당시 버그를 잡는지 확인하는 것이다. 화자는 버그의 80~90%가 과거 실수의 반복이라고 주장하지만 새로운 유형도 계속 생기므로 실시간으로 갱신되는 데이터셋이 필요하다고 말한다.

또한 충분한 버그 유형을 덮으려면 수백만 건의 PR이 필요할 수 있다고 주장한다. Greptile은 여러 회사의 큰 PR 자료 집합을 시험할 수 있어 내부 리뷰 에이전트보다 작은 성능 개선을 더 자신 있게 할 수 있다고 설명한다. 이는 화자 측 주장으로, 자료 규모와 평가 결과는 공개되지 않았다.

5. 모델 교차 검토

화자는 Claude와 Codex 계열이 서로 다른 유형의 버그를 만든다고 주장한다.

  • Codex 모델은 GPT 모델보다 일회성 오류를 약 3배 더 만들 가능성이 있다고 말한다.
  • GPT 모델은 Claude 모델보다 인증 우회를 만들 가능성이 더 높다고 말한다.
  • 이러한 차이는 사후 학습의 결과로 이해한다고 덧붙인다.

다만 Codex와 GPT의 범주 관계가 설명되지 않아 첫 비교의 정확한 분류 기준은 알 수 없다.

같은 모델이 작성과 리뷰를 모두 맡으면 같은 방식으로 실패할 수 있으므로 Claude Code로 작성했다면 GPT 모델로 리뷰하는 식의 교차 검토를 권한다.

작성 모델의 흔적은 다음과 같이 추정할 수 있다고 한다.

  • Codex가 Codex/branch-name 형식으로 브랜치를 만드는 경우
  • Claude가 PR 설명이나 커밋 메시지에 Co-authored by Claude를 남기는 경우

화자는 약 80%는 이런 흔적으로 식별할 수 있지만 나머지 20%는 휴리스틱, 내부 사용 현황, 개발 장비 텔레메트리 등이 필요하다고 말한다. 모델을 뒤집었을 때 검출률이 10% 높아졌다는 Greptile의 관찰도 제시하지만 측정 조건은 설명하지 않는다.

6. 코드베이스와 의도의 맥락

화자는 grep 기반 검색이 부정확하고 토큰 비용이 크다고 비판한다. 코딩 에이전트의 많은 토큰이 grep, 파일 읽기, 파일 내용 캐시 쓰기에 사용된다고 주장한다.

인증 우회를 찾으려면 다음과 같은 정보가 필요하다고 설명한다.

  • 현재 코드가 인증된 환경에서 실행되는지
  • 인증 흐름에 어떤 파일들이 참여하는지
  • 변경이 다른 서비스와 어떻게 연결되는지

또한 버그가 없어도 작성자의 의도를 충족하지 못할 수 있다. Slack 메시지 한두 문장처럼 요구사항이 짧고 모호하면 에이전트가 잘못 해석할 수 있다는 사례를 든다.

화자는 특히 다음 맥락이 중요하다고 말한다.

  • Jira와 Linear의 티켓
  • Confluence와 Notion의 문서
  • 코드 인덱서나 내부 지식 기반
  • 운영 텔레메트리와 로그
  • 제품 로드맵과 앱 흐름

Greptile은 이를 “살아 있는 위키”로 연결해 에이전트의 맥락 이해와 파일 검색 정밀도를 높인다고 주장한다.

7. 샌드박스 자율 테스트

정적 코드 리뷰만으로는 실제 화면 문제를 잡지 못할 수 있다. 화자는 React 코드가 정상으로 보여도 휴대전화에서 요소가 가려지는 사례를 든다.

Greptile의 접근은 다음과 같이 설명된다.

  • 필요한 의존성을 포함한 가상 머신형 샌드박스를 준비한다.
  • PR 브랜치의 앱을 해당 환경에서 실행한다.
  • 인증, 가입 등 앱의 흐름 지도를 문서화한다.
  • 에이전트가 컴퓨터 사용 기능으로 처음부터 끝까지 시험한다.
  • 시각 모델로 버튼이 보이는지, 첫 화면 영역에 있는지 등을 확인한다.

화자는 새 GPT 및 Opus 모델에서 컴퓨터 사용 성능이 좋아져 종단 간 QA가 거의 해결되었다고 평가한다. 이는 화자의 의견이며, 동시에 앱을 쉽게 띄우는 빌드 스크립트와 정확한 흐름 문서를 만드는 일이 어렵다고 인정한다.

8. 작업별 모델 배분

뒤쪽에서 화자는 PR 한 건 리뷰 비용을 3달러에서 15달러 또는 20달러까지라고 다시 말한다. 앞의 3~25달러와 상한이 일치하지 않는다.

비용을 줄이기 위해 다음과 같이 작업을 나눈다고 설명한다.

  • 맥락 탐색: 작은 모델
  • 사용자 흐름 시험: 가벼운 컴퓨터 사용 모델
  • 버그 분석과 핵심 리뷰: 최전선 모델

Greptile의 현재 사용량은 약 20%가 최전선 모델이며, 약 20개의 세부 작업에 각각 특정 모델을 배치한다고 주장한다. 단순한 작업을 단순한 모델로 바꾸면 전체 목표의 70~80%까지 갈 수 있다고 말하지만, 이 비율의 정확한 평가 기준은 제시되지 않는다.

Jina 또는 Cohere Rerank API 같은 결정·재정렬 도구로 어떤 맥락을 최전선 모델의 캐시에 넣을지 고르는 방안도 제시한다. 그러나 작은 모델로 바꾼 뒤에도 버그 검출이 유지되는지는 충분한 평가 데이터가 있어야 알 수 있다고 강조한다.

교정 전사 (한국어)

전체 전사 펼치기

AI가 작성한 코드를 AI가 리뷰하면 버그를 얼마나 잘 찾아낼 수 있을까요? 간단한 리뷰 에이전트를 만들 수 있지만, 실제로 쓰려면 비용과 사소한 지적, 놓친 버그가 문제입니다. Greptile 공동창업자 닥시 굽타가 프롬프트와 과거 풀 리퀘스트 데이터부터 모델 교차 검토, 코드베이스 맥락, 자율 테스트까지 개선 방법을 설명합니다. 리뷰 에이전트를 실전에 적용할 때 무엇을 살펴야 하는지 함께 보겠습니다.

기업들은 엄청난 양의 코드를 작성하고 있습니다. 사람들은 바이브 코딩(vibe coding)을 하고 있죠. 물론 엔지니어들도 바이브 코딩을 하고 있는데, 그중 일부는 태양에 너무 가까이 날아가고 있습니다. 마케팅 담당자들도 코드를 작성하고 있고, 이제 새롭게 생긴 문제는 리뷰 병목과 검증 병목입니다. 바로 그 문제를 해결하려는 것입니다.

가장 먼저 해야 할 일은 샌드박스(sandbox)를 마련하는 것입니다. 여기에는 샌드박스를 판매하는 회사가 많습니다. 아니면 그냥 Firecracker 같은 것을 사용해도 됩니다. 그리고 그 샌드박스 안에 에이전트를 넣어야 합니다. 에이전트로 Codex나 Claude Code를 사용할 수 있습니다. 개인적으로는 모델 독립적(model-independent)인 방식을 권합니다. 그 이유는 뒤에서 설명하겠습니다. 따라서 OpenCode나 Pi 같은 것을 하네스(harness)로 사용할 수 있습니다. 둘 다 오픈 소스입니다. 그런 다음 GitHub나 GitLab을 연결해야 합니다.

PR 웹훅(webhook)을 설정하세요. 풀 리퀘스트(pull request)가 열리면 그 풀 리퀘스트의 내용을 보내도록 합니다. 에이전트에는 어떤 형태로든 프롬프트가 있을 수 있습니다. 단순히 “이걸 리뷰해 줘”라고 말하고 피드백을 돌려보내는 것입니다. 그런 다음 GitHub의 리뷰 API를 사용해 그 결과를 다시 연결하면 됩니다. 아주 간단합니다. 실제로 많은 사람은 리뷰 에이전트를 만드는 데 필요한 것이 사실상 이것뿐이라고 생각합니다.

이것을 사용하기 시작하면 몇 가지 문제가 발생하겠지만, 실제로 풀 리퀘스트가 올라가고, 그 내용이 에이전트로 전달되며, 약 5분 후 풀 리퀘스트에 대한 피드백을 받게 될 것입니다. 하지만 이 시스템을 만드는 데 걸리는 시간 동안 어떤 문제가 발생할지 보겠습니다.

첫 번째 문제는 많은 버그를 놓치게 된다는 것입니다. 버그는 본질적으로 규모가 큽니다. 얼마 전 버그는 프랙털처럼 무한하다는 트윗을 본 적이 있습니다. 따라서 특정 코드 조각에서 버그가 바닥나는 일은 절대 없습니다. 첫 번째로 발생할 문제는 버그를 놓친다는 것입니다. 물론 시스템이 해야 할 일은 바로 이것입니다. 적어도 매우 치명적인 장애와 사고를 방지해야 합니다.

두 번째로 발생할 문제는 맥락을 놓치고, 코드베이스가 작동하는 방식의 일부를 잘못 이해한다는 것입니다.

코드베이스가 어떤 방향으로 나아가고 있는지 이해하지 못할 수도 있습니다. 코드베이스의 특정 부분이 어떻게 작동하는지도 이해하지 못할 것입니다. 사용 중인 라이브러리들이 어떻게 작동하는지 이해하지 못할 수도 있습니다. 여러분이 2010년대의 마이크로서비스 아포칼립스(microservices apocalypse)에서 아직도 회복하지 못한 회사 중 하나일 가능성도 있습니다. 그래서 저장소가 수천, 수만 개에 이르고, 제대로 작동하려면 그 모든 저장소의 맥락이 필요한 것입니다. 이것이 두 번째로 발생할 문제입니다.

세 번째 문제는 비용이 매우 많이 든다는 것입니다. 사람들은 이 점에 상당히 놀랍니다. 저희가 시도하는 사람들을 지켜본 바로는, 코딩 에이전트를 사용해 풀 리퀘스트를 리뷰하는 데 대체로 건당 3달러에서 최대 25달러를 지출하게 됩니다. 토큰은 정말, 정말 빠르게 누적될 수 있습니다. 아주 조용히 비용이 크게 증가합니다.

네 번째로 발견하게 될 문제는 지나치게 꼬투리를 잡는 댓글입니다. 이것은 생각보다 중요합니다. 꼬투리를 잡는 댓글은 기술적으로는 맞지만 지나치게 현학적인 댓글입니다. 이런 댓글이 있으면 두 가지 문제가 발생합니다. 사람이 그 댓글을 읽는다면 매우 짜증 납니다. 양치기 소년 이야기와 같습니다. 댓글이 계속해서 많이 보이고, 그중 어떤 것이 사소한 스타일 지적이고 어떤 것이 실제로 치명적인 문제인지 읽어 보며 구분하는 일이 성가시게 됩니다.

두 번째 문제는 코드베이스가 망가진다는 것입니다. 일반적으로 리뷰 에이전트가 작동하는 방식은 GitHub에 댓글을 남기고, 코딩 에이전트가 그 댓글을 가져와 해결하는 것입니다. 코딩 에이전트는 분별력이 없습니다. 리뷰 댓글을 보고 전부 처리하려고 하며, 결국 극도로 고통스러울 정도로 방어적인 코드가 만들어집니다. 저희가 보기에 코딩 에이전트는 특히 그런 코드를 작성하는 데 능숙합니다.

다음으로 발생할 문제는 같은 풀 리퀘스트에 리뷰 에이전트를 실행할 때마다 어떻게든 새로운 버그를 발견한다는 것입니다. 즉, 풀 리퀘스트에서 계속 새로운 것을 잡아내는 일이 매우 성가시게 반복됩니다. 앞서 말했듯 버그는 프랙털처럼 무한한 것처럼 보일 것입니다.

따라서 가장 먼저 해야 할 일, 가장 손쉽게 얻을 수 있는 성과(low-hanging fruit)는 프롬프트를 최적화하는 것입니다. 처음에는 “이 PR을 리뷰하고” GitHub API 스키마 형식으로 댓글을 출력하라는 식의 아주 단순한 프롬프트로 시작했을 것입니다.

일반적으로 버그에는 두 가지 주제가 있습니다. 구체적인 버그 유형을 찾는 것, 그리고 두 번째로 꼬투리 잡는 지적을 건너뛰는 것입니다. 프롬프트의 방향을 이 두 가지에 맞춰야 합니다. 구체적인 버그 유형을 요청하고, 코드베이스에서 발생했던 기존 장애와 사고를 대상으로 내부 데이터 분석(data science)을 수행해 어떤 유형의 버그가 가장 자주 발생하는지 파악할 수 있습니다. 그런 버그 유형의 목록을 만들고, 프롬프트가 그 구체적인 버그 유형을 찾도록 하세요. 두 번째로, 꼬투리 잡는 지적이 무엇인지 명시적으로 설명하고 그런 지적은 찾지 말라고 해야 합니다.

꼬투리 잡는 지적은 특정 항목에 왜 세 겹의 방어 계층이 없는지 묻는 것부터, 오류 처리가 왜 이렇게 약간 허술한 방식으로 되어 있는지 묻는 것까지 무엇이든 될 수 있습니다. 그런데 이런 프롬프트를 변경할 때 마주하게 되는 문제는 프롬프트의 작은 부분을 바꾸기만 해도 에이전트가 풀 리퀘스트에 작성하는 댓글 수에 이상할 정도로 큰 영향을 미친다는 것입니다. 이는 꽤 무서운 일입니다. 버그를 놓치고 있는지 실제로 알 수 없다는 뜻이기 때문입니다. 반사실(counterfactual)을 알 수 없습니다.

검증 에이전트, 또는 사실상 어떤 리뷰어나 테스터도 버그의 존재에 대해서는 알려줄 수 있지만, 안타깝게도 버그의 부재에 대해서는 알려줄 수 없습니다. 이는 형식 자체의 한계라고 할 수 있습니다. 특히 어려운 점은 버그가 극도로 드물고 날이 갈수록 더 드물어지고 있다는 것입니다. 실제로 저희의 데이터 분석에 따르면, 풀 리퀘스트 1,000개 중 약 하나에만 진정으로 치명적인 버그가 들어 있거나, 코드 1,000줄당 하나에만 치명적인 버그가 들어 있습니다.

따라서 이런 버그가 매우 드물기 때문에, 여러분은 매우 훌륭하다고 생각하는 에이전트 버전을 출시했지만, 그 버전이 풀 리퀘스트에 있는 치명적인 버그를 몰래 놓칠 수도 있습니다. 그런 버그를 자주 만들어 내는 것이 아니기 때문에, 오랫동안 그 사실을 알지 못할 것입니다.

이것이 두 번째 개선 사항으로 이어집니다. 과거 PR의 데이터셋(dataset)이 필요합니다. 코드베이스에서 문제가 발생할 때마다 이를 아주 잘 기록해 두는 회사라면 비교적 쉽게 할 수 있습니다. 그런 데이터가 있다면 과거에 장애와 사고를 일으킨 풀 리퀘스트 목록을 확보할 수 있습니다. 이를 목록화한 다음, 리뷰 에이전트의 각 버전이 그 사례들을 실행해 보고 해당 버그를 얼마나 자주 잡아내는지 확인하면 됩니다.

이렇게 하면 프롬프트를 좀 더 자신 있게 조정할 수 있습니다. 하지만 동시에 버그의 흥미로운 점은, 변화하는 세상에서 버그의 위상(topology)과 존재론(ontology)이 시간에 따라 변한다는 것입니다. 따라서 실시간으로 업데이트되는 데이터셋이 필요합니다.

이것은 어려운 일입니다. 풀 리퀘스트가 수백만 개가 있지 않다면 버그 유형을 상당히 높은 수준으로 포괄하기가 실제로 어렵기 때문입니다. 버그의 약 80~90%는 과거의 실수를 반복하는 것에 불과한 것이 사실입니다. 하지만 코드 작성 주기가 빨라질수록 새로운 실수를 저지르기 시작할 것입니다. 우리가 전에 예상하지 못했던 새로운 방식으로 실패하게 되고, 이 지점에서 한계에 부딪히기 시작합니다.

여기서 짧게 덧붙이자면, 이것이 저희가 Greptile에서 하는 일과 어느 정도 비슷합니다. 다만 저희는 실제로 아주 많은 회사의 코드를 보유하고 있고, 매우 거대한 풀 리퀘스트 집합을 대상으로 테스트할 수 있기 때문에 에이전트를 매우 자신 있게 개선할 수 있습니다. 이것이 내부 리뷰 에이전트로는 할 수 없는 방식으로 성능을 조금씩 끌어올릴 수 있는 이유 중 하나입니다. 하지만 특히 여러분의 회사에 대해서라면 내부 데이터를 활용해 이 작업을 수행하는 것만으로도 상당히 좋은 수준까지 도달할 수 있습니다.

그리고 그 연구를 통해 흥미로운 패턴을 발견했습니다. Claude 모델이 생성하는 버그 유형과 Codex 모델이 생성하는 버그 유형은 실제로 서로 상당히 다릅니다.

여러 가지 면에서 다릅니다. 예를 들어 Codex 모델은 GPT 모델보다 일회성 오류(one-off error)를 발생시킬 가능성이 약 3배 높습니다. 반면 GPT 모델은 Claude 모델보다 인증 우회(auth bypass)를 발생시킬 가능성이 훨씬 높습니다. 제가 이해하기로 이것들은 모두 사후 학습(post-training)의 산물입니다.

이를 방지하려면, 코드를 작성한 모델과 같은 모델을 사용해 코드를 리뷰할 경우 실제로 발견되는 버그 수가 상대적으로 적어진다는 점을 알게 될 것입니다. 코드 생성 때와 리뷰 때 같은 방식으로 실패하기 때문입니다. 따라서 모델을 반대로 사용해야 합니다. Claude Code로 코드를 작성했다면 GPT 모델을 사용해 리뷰하고, 그 반대도 마찬가지입니다.

이 작업은 80번째 백분위수까지는 어느 정도 간단하지만, 마지막 20%는 상당히 어렵습니다. 코딩 에이전트를 사용하고 있다면 특정 풀 리퀘스트에 어떤 코딩 에이전트가 사용되었는지 알려주는 일종의 지문(fingerprint)을 남긴다는 것을 알 수 있습니다. 예를 들어 Codex는 Codex/branch-name 형식으로 브랜치 이름을 지정하고, Claude는 PR 설명과 커밋 메시지에 “Co-authored by Claude”라고 작성합니다.

그리고 약 80%의 경우에는 이것이 맞습니다. 마지막 20%의 경우, 직접 브랜치 이름을 만들었거나 다른 이유로 다른 코딩 에이전트가 사용되었을 수 있다면, 생성 과정에서 어떤 모델이 사용되었는지 파악하기가 훨씬 어렵습니다. 어떤 모델이 사용되었는지 그 특징을 알아내려면 일종의 휴리스틱(heuristic)을 개발해야 합니다.

요즘 사람들이 어떤 코딩 에이전트를 사용하는지 보고하는 내부 카탈로그가 있거나, 개발 장비와 엔지니어들의 컴퓨터에서 나오는 일종의 텔레메트리(telemetry)가 있을 수도 있습니다. 저희는 모델을 바꾸면 탐지율이 10% 더 높아진다는 사실을 발견했습니다. 아주 작은 수치처럼 들릴 수 있지만, 여기서 10%는 사고와 서비스 중단을 기준으로 한 수치라는 점을 알아야 합니다. 실제로는 상당히 큰 수치입니다. 즉, 모델 반전(model inversion)을 사용하지 않으면 무언가 잘못될 가능성이 10% 더 높다는 뜻이며, 이는 상당히 치명적일 수 있습니다.

따라서 저희는 프로세스에 어떤 형태로든 모델 반전을 사용할 것을 적극 권장합니다. 세 번째로 개선할 수 있는 부분은 코드베이스 컨텍스트(codebase context)입니다. 이 부분은 제가 매우 중요하게 생각합니다. 코드 검증을 하기 전에는 코드베이스 컨텍스트를 다루고 있었습니다. 매우 큰 코드베이스에서 RAG를 더 잘 수행하는 방법을 알아내려 했고, 오늘날에도 사람들은 grep만으로 코드베이스 컨텍스트 문제를 사실상 모두 해결할 수 있다고 생각합니다.

하지만 저는 여러 이유로 그것이 사실이 아니라고 생각합니다. 첫째, grep은 매우 부정확하고, 둘째, 매우 비쌉니다. 규모를 가늠할 수 있도록 말씀드리면, 지난해 GDP 성장률의 한 자릿수 퍼센트포인트가 추론(inference)이었습니다. 추론의 매우 큰 비율은 코딩 에이전트가 차지했습니다. 실제로 코딩 에이전트의 트레이스(trace)를 살펴보면, 코딩 에이전트가 사용하는 토큰의 압도적인 다수는 모두 같은 작업입니다. grep, 파일 읽기, 파일 내용 캐시 쓰기입니다.

즉, GDP 성장률의 무시할 수 없는 비율이 grep, 파일 읽기, 캐시 쓰기라는 뜻입니다.

이는 매우 좋지 않습니다. grep이 매우 부정확하기 때문입니다. 파일을 매우 많은 양으로 읽고 있으며, 저도 잘 모르겠습니다. 토큰 단위로 보수를 받는 회사들이 더 많은 토큰을 소모할 방법을 찾도록 만드는 역인센티브가 있을 수도 있습니다. 하지만 그렇더라도 어디를 읽어야 하는지 알아내려면 조금 더 정밀한 방법을 사용해야 한다는 사실을 알게 될 것입니다. 저희가 사용하는 방법은 내부 지식 베이스를 구축하는 것입니다. 여기서는 코드베이스 전체를 살펴보며 서로 다른 부분을 사실상 모두 확인합니다.

그것들을 분류하고 색인화한 다음 이렇게 말합니다. “좋아요, 이 부분은 인증(authentication)입니다. 작동 방식은 이렇습니다. 흐름은 이렇습니다. 흐름을 나타낸 다이어그램은 이렇습니다. 관련된 파일은 모두 이것입니다.” 코드베이스 컨텍스트가 중요한 한 가지 예는 인증 우회(auth bypass)를 잡아내려 할 때입니다.

인증 우회가 발생했는지 알아내는 일은 실제로 매우 어렵습니다. 코드베이스의 해당 부분에서 자신이 인증된 환경에 있는지 아닌지를 상당히 구체적으로 이해하고 있어야 하기 때문이며, 이는 매우 까다롭습니다. 따라서 이를 수행하려면 어떤 형태로든 코드베이스 컨텍스트가 필요하다는 것을 알게 될 것입니다. 지금까지는 버그라는 개념에 매우 집중했지만, 코드에 버그가 없더라도 매우 나쁠 수 있습니다. 우선 품질이 끔찍할 수 있고, 둘째로 작성자가 표현한 의도를 단순히 충족하지 못할 수도 있습니다.

최근에 사람들이 Slack을 IDE로 점점 더 많이 사용하고 있다는 글을 봤습니다. 조금 재미있는 이야기라고 생각하지만, 동시에 Slack 메시지에는 표현된 의도가 그다지 많이 담겨 있지 않습니다. 에이전트에게 무언가를 고쳐 달라고 요청하면서 한두 문장, 혹은 그보다 적은 말만 하는 경우도 있습니다. 이는 지시에 많은 모호성이 있다는 뜻입니다. 그 결과 코딩 에이전트가 지시를 잘못 해석하거나, 지시가 너무 모호해서 정확히 무엇을 해야 할지 모르는 상황이 생길 수 있습니다.

따라서 올바른 코드도 실제로는 상당히 잘못된 코드일 수 있습니다. 저희가 이에 대응하는 방법 중 하나는 에이전트에 점점 더 많은 컨텍스트를 제공하는 것입니다.

저희가 보기에 가장 중요한 두 종류의 컨텍스트는 문서와 티켓이고, 물론 코드베이스 인덱서(indexer)나 지식 베이스에서 가져오는 코드베이스도 중요합니다. Jira와 Linear, 그리고 Confluence나 Notion, 또는 문서를 저장하는 어떤 도구든 에이전트에 접근 권한을 주면 놀라울 정도로 많은 일을 해낼 수 있습니다. 여러분이 더 나은 코드를 작성하는 데 무의식적으로 도움을 주는 암묵지가 아주 많다는 사실을 알게 될 것입니다. 에이전트가 같은 일을 하게 하면 에이전트가 아무것도 모르는 것처럼 느껴집니다. 여러분 자신이 얼마나 깊은 지식을 갖고 있는지 과소평가하기 때문입니다.

Greptile이 이 문제에 접근하는 방식은 실제로 이런 모든 컨텍스트 소스를 살아 있는 위키(living wiki)로 중재하는 것입니다. 이 위키는 본질적으로 회사가 어떻게 운영되는지를 나타내는 일종의 월드 모델(world model)입니다.

여기에는 코드베이스에 대해 알고 있는 모든 것, 프로덕션 텔레메트리와 로그를 통해 애플리케이션에 대해 알고 있는 모든 것, 문서와 Linear 티켓 등을 통해 로드맵에 대해 알고 있는 모든 것이 담깁니다. 이 위키를 사용해 컨텍스트를 제공하면 에이전트가 컨텍스트를 더 잘 인식하게 될 뿐 아니라 코드 검색도 훨씬 더 정확해집니다. 읽을 필요가 없는 파일은 절대 읽지 않기 때문입니다.

마지막으로 해야 할 일은, 아니면 다섯 가지 중 네 번째일 수도 있는데, 자율 테스트(autonomous testing)입니다. 저희가 많이 생각하는 것 중 하나는, 예를 들어 UI 변경의 경우 React 코드에서 변경된 파일을 여러 개 읽고 코드에 문제가 없다고 결론 내릴 수 있다는 것입니다. 하지만 실제로 렌더링해 보면 예를 들어 iPhone에서 숨겨져 있을 수도 있습니다.

이는 기술적으로 해결하기 더 어려운 문제 중 하나입니다. Greptile에서는 본질적으로 의존성이 풍부한 샌드박스(dependency-rich sandbox)를 구축하는 방식으로 접근합니다. 이는 완전히 설정 가능한 가상 머신입니다. 저희는 고객들과 협력해 그들의 스택을 이러한 샌드박스에서 실행합니다. 그런 다음 Greptile의 에이전트가 컴퓨터 사용(computer use)을 통해 처음부터 끝까지 테스트합니다.

여러분이 주의를 기울이지 않았다면 모르실 수도 있지만, 컴퓨터는 매우 뛰어난 수준에 도달했습니다. 새로운 세대의 GPT 모델과 Opus 모델에서는 이전보다 훨씬 좋아졌습니다. 제 생각에 처음으로 엔드투엔드 QA(end-to-end QA)가 거의 해결되었습니다. 다만 해야 할 일은 애플리케이션을 통과하는 모든 흐름을 문서화하는 것입니다. 둘째로, 에이전트가 여러분의 환경에서 스택을 실행할 수 있도록 충분히 단순한 빌드 스크립트가 필요합니다.

저희에게는 기업들이 이를 수행할 수 있도록 돕는 현장 파견 엔지니어(forward-deployed engineer) 팀이 있습니다. 이미 매우 좋은 개발 박스를 갖고 있는 경우가 아니라면, 이 부분이 더 까다로운 부분 중 하나라는 사실을 발견했습니다. 이것이 제가 보여드릴 다이어그램입니다. 개발 박스가 필요합니다. 앱을 실행하는 PR 브랜치 의존성이 필요하고, “이것은 인증 코드이고, 이것은 회원가입 흐름이다”라고 말해 주는 일종의 흐름 맵(flow map)이 필요합니다. 이를 사용하면 에이전트가 코드를 처음부터 끝까지 테스트할 수 있고, 비전 모델(vision model)을 사용해 “이 버튼은 기술적으로 나타나지만 실제로는 iPhone에서 숨겨져 있거나, iPhone Duo에서 첫 화면 영역에 들어오지 않는다”라고 말할 수 있습니다.

이 모든 것을 수행하면 비용이 여전히 상당히 높다는 사실을 알게 될 것입니다. 풀 리퀘스트 하나를 검토하는 데 3달러에서 15달러 또는 20달러까지 들 수 있습니다. 이제 해결해야 할 문제는 일부 작업에 더 저렴한 모델을 사용하는 것입니다.

제가 보기에 프런티어 모델(frontier model)은 일반적으로 여전히 오픈 소스 모델보다 성능이 뛰어납니다. 격차가 좁혀지고 있기는 하지만, 이는 한동안 사실이었습니다. 현재 저희의 사용 비율은 가장 중요한 작업에 프런티어 모델을 약 20% 사용하고, 나머지 긴 꼬리의 토큰, 즉 탐색적 파일 읽기 등의 작업에는 다양한 소형 모델을 사용하는 방식입니다.

이렇게 하면 리뷰 에이전트를 실행하는 비용을 실제로 상당히 줄일 수 있습니다.

저희가 하는 일을 보여주는 일종의 예시는 이렇습니다. 컨텍스트를 찾는 데는 소형 모델을 사용하고, 사용자 흐름을 테스트하는 데는 매우 가벼운 컴퓨터 사용 모델을 사용하며, 버그 분석, 리뷰 프로세스 적용, 첫 번째 제출물 검토 같은 작업에는 프런티어 모델을 사용합니다. 실제로는 약 20개의 서로 다른 하위 작업이 있고, 각각에 사용하는 모델의 구성이 매우 구체적으로 정해져 있습니다. 저희에게는 어떤 작업에 어떤 모델을 사용할지 끊임없이 반복해 개선하는 소규모 연구팀이 있습니다.

이와 같은 방식을 사용하면, 매우 단순한 작업을 매우 단순한 모델로 바꾸는 것만으로도 아마 70~80% 정도까지는 도달할 수 있을 것입니다. 이것은 매우 큰 데이터셋을 보유하는 것이 왜 큰 도움이 되는지를 보여주는 또 다른 예입니다.

좋은 데이터셋이 없다면 여러 하위 에이전트를 더 작고 빠른 모델로 대체하고 싶어질 수 있습니다. 그러면 해당 에이전트가 실제로 버그를 잡아내는 능력이 상당히 떨어졌다는 사실을 알지 못할 것입니다. 나중에 장애나 사고를 일으키는 무언가를 놓쳤을 때에야 알게 될 것입니다.

또한 모든 컨텍스트 조각을 살펴보고 실제로 포함해야 할 것들을 판단하는 저렴한 모델을 사용하면, 파일을 과도하게 읽는 문제에도 어느 정도 대응할 수 있다는 사실을 알게 될 것입니다. 이론적으로는 이를 위해 Jina나 Cohere Rerank API 같은 의사결정 모델(decision model)을 사용할 수 있습니다. 서로 다른 항목을 모두 효과적으로 재순위화하고, 프런티어 모델의 캐시에 무엇을 로드해야 하고 무엇을 로드하지 말아야 할지 결정하는 것입니다. 이는 어떤 면에서 가장 비싸고 가장 부족한 리소스입니다.
