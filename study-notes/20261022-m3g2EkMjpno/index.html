AI가 코딩하는데 왜 내가 더 바쁠까? | Stripe의 AI 개발 워크플로

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

AI가 코드를 빨리 작성한다고 해서 개발 작업 전체가 같은 속도로 끝나는 것은 아니다. 코드를 받은 뒤에는 요구 사항에 맞는지, 다른 기능을 깨뜨리지 않는지, 테스트가 충분한지, 다른 변경과 안전하게 합칠 수 있는지를 확인해야 한다. 코드 생산만 빨라지고 이 확인 과정이 그대로라면, 사람이 검토해야 할 변경이 더 빠르게 쌓일 수 있다.

이 영상은 이 간격을 줄이는 방법으로 작업 공간 분리, 검증 자동화, 병렬 작업 계획이라는 세 가지를 제시한다. Stripe의 개발 환경과 자체 코딩 에이전트 사례를 소개하면서, 작은 팀에서 시험할 수 있는 가상 예시도 함께 든다.

읽는 법: 위에서 아래로 읽는다. 세 가지 방법은 무조건 한꺼번에 도입하는 순서가 아니다. 현재 가장 자주 막히는 지점에 맞춰 하나를 먼저 고르는 선택지다.

왜 코드가 나왔는데도 일이 끝나지 않는가

영상은 로그인 기능 수정이라는 가상 장면을 든다. AI가 코드와 테스트를 돌려줬더라도, 서비스의 권한 규칙을 지켰는지와 다른 화면을 깨뜨리지 않았는지는 사람이 다시 판단해야 한다. 이 예시는 Stripe에서 실제로 벌어진 사건이 아니라 영상 제작자가 설명을 위해 만든 사례다.

핵심은 코드 생성 완료와 배포 가능한 변경 완료가 서로 다른 상태라는 점이다. 테스트가 통과해도 요구 사항을 잘못 이해했을 수 있고, 버튼이 정상적으로 눌려도 다른 사람의 계정에 접근하지 못하게 하는 보안 조건은 별도로 확인해야 한다. 따라서 모델의 “잘했습니다”라는 답보다 사람이 확인할 수 있는 검사 결과와 변경 근거가 필요하다.

읽는 법: 각 묶음을 위에서 아래로 읽는다. 아래쪽이 위쪽을 버리는 것이 아니라, 주관적인 기대만으로는 부족한 부분을 시스템 제한과 추가 검토로 보강한다는 뜻이다.

1. 작업 공간을 분리한다

Stripe의 공식 기술 글에 등장한다고 소개된 devbox는 코드와 개발 중인 서비스를 담는 클라우드 개발 환경이다. Stripe의 자체 에이전트인 Minions도 이 환경에서 작업한다고 영상은 설명한다. 작업마다 환경을 나누면 어떤 변경과 실행 기록이 어느 작업에서 나왔는지 살펴보기 쉬워지고, 실패한 작업을 버린 뒤 같은 조건에서 다시 시작하기도 쉬워질 수 있다.

작은 팀은 브랜치와 Git 워크트리로 파일 작업 공간부터 나눠볼 수 있다. 하지만 워크트리는 파일 공간을 나누는 도구일 뿐이다. 테스트 데이터, 환경 변수, 포트, 데이터베이스와 외부 서비스 접근 권한까지 자동으로 격리하지는 않는다. 따라서 “폴더가 분리됐다”와 “위험한 자원에 접근할 수 없다”를 혼동하면 안 된다.

영상의 검색 API와 관리 화면 예시는 작업 분리를 설명하기 위한 소규모 팀의 가상 사례이며, Stripe가 직접 제시한 실제 사례로 다루지 않는다.

2. 모델의 선의보다 단단한 제한과 증거에 의존한다

Patrick Collison의 발언으로 소개된 부분은 모델이 올바르게 행동할 가능성만 믿기보다, 시스템이 반드시 지켜야 할 조건과 단단한 장벽에 의존해야 한다는 취지다. 예를 들어 운영 데이터를 만지지 말라고 프롬프트에 적는 것은 요청이다. 반면 개발 환경에서 운영 자격 증명을 사용할 수 없게 만드는 것은 시스템 제한이다.

검사도 같은 원리로 구성할 수 있다. 영상은 Stripe의 Minions 흐름이 모델의 판단 단계와 정해진 코드가 실행하는 단계를 함께 사용하며, 공식 기술 글에서 이를 블루프린트(blueprint)라고 부른다고 설명한다. 에이전트는 구현하고, 포맷 검사·타입 검사·관련 테스트와 같은 정해진 검사는 일반 코드가 실행한다. 검사 결과가 없거나 실패했다면 다음 단계로 넘어가지 않게 만드는 방식이다.

다만 자동 검사가 모든 의미를 판단해 주지는 않는다. 테스트가 기존에 정의된 동작만 확인할 수도 있으므로, 요구 사항과 위험을 판단하는 사람의 검토 항목은 남는다.

3. 저장소의 맥락과 병렬 작업의 경계를 먼저 정한다

영상에 인용된 표현은 “모든 코드베이스가 이제 다른 코드베이스를 위한 프롬프트”라는 관점이다. AI는 저장소 안에서 발견한 코드와 설명을 다음 구현의 참고 자료로 사용할 수 있다. 같은 일을 하는 코드가 서로 다른 방식으로 흩어져 있거나 오래된 예제가 남아 있다면, 이미 버린 설계를 다시 가져올 수 있다.

영상 제작자는 모든 규칙을 긴 문서 하나에 몰아넣기보다, 작업하는 디렉터리 가까이에서 필요한 안내와 권장 예제를 찾게 하는 방법을 권한다. 금지 사항만 적는 것이 아니라 대신 사용해야 할 모듈의 위치도 함께 알려주는 방식이다. 이는 Stripe의 직접 발언이라기보다 대담 내용을 작은 팀에 옮긴 해설이다.

병렬 실행도 에이전트 수부터 늘리는 일이 아니다. 영상에 인용된 Stripe 사례에서는 한 사람이 복잡한 계획을 충분히 만든 뒤 서로 다른 에이전트가 있는 devbox 열 개에 작업을 나누며, 작업이 하루 또는 여러 날 계속될 수도 있다고 말한다. 그러나 devbox 열 개가 생산성 열 배를 뜻하지는 않는다.

먼저 입력과 출력, 오류 형식, 수정할 파일, 완료 조건을 합의해야 한다. 독립적으로 진행할 작업과 다른 결과를 기다려야 하는 작업도 구분해야 한다. 작업 중 전제가 바뀌면 멈춰서 다시 나눌 조건도 필요하다.

읽는 법: 위에서 아래로 읽는다. 마지막은 자동으로 처음으로 되돌아간다는 뜻이 아니라, 전제가 달라졌을 때 현재 실행을 계속 밀어붙이지 말고 새 계획을 세워야 한다는 중단 지점이다.

무엇부터 바꿀 것인가

세 방법 중 첫 선택은 현재 병목에 따라 달라진다. 파일과 실행 환경이 자주 뒤섞인다면 공간 분리, 같은 검사와 오류 확인을 사람이 반복한다면 검증 자동화, 각 작업은 되지만 합칠 때 자주 막힌다면 병렬 작업 계획을 먼저 점검한다.

읽는 법: 각 카드의 ‘관찰’과 ‘첫 선택’을 한 쌍으로 읽는다. 이 표는 세 방법의 우열을 매기지 않는다. 실제 프로젝트가 어느 상태인지는 별도로 관찰해야 한다.

영상이 권하는 시험 대상은 재현 방법이 있는 버그 수정이나 영향 범위가 좁은 테스트 보강처럼 작고 경계가 분명한 작업이다. 결과에는 변경 이유, 실행한 명령, 남은 문제를 붙이고, 사람은 요구 사항과 위험을 검토한다. 이때 측정할 것은 AI가 첫 코드를 내놓은 시간만이 아니다. 사람이 검토해 받아들인 시간과 프롬프트 수정, 테스트 실패 해결, 병합 충돌 정리에 든 부담까지 봐야 한다.

이 방법들은 아직 차드의 프로젝트에서 검증된 상태가 아니다. 또한 출처는 Stripe 관련 대담과 기술 글을 바탕으로 하지만, 소규모 팀의 검색 기능·로그인·작업 분담 사례는 영상 제작자의 해설이다. Stripe의 Minions는 goose를 기반으로 만든 자체 에이전트로 소개되며 Claude Code와 동일한 제품이 아니다.

여기까지만 이해하면 충분

  • AI가 코드를 빨리 만드는 것과 사람이 검토해 배포 가능한 변경을 완성하는 것은 다른 단계다.
  • 병목이 작업 간 간섭이면 공간 분리, 반복 검사면 검증 자동화, 통합 실패면 병렬 작업 계획을 먼저 본다.
  • 프롬프트의 요청보다 접근 제한과 자동 검사처럼 시스템이 강제하는 경계가 더 단단하다.
  • 에이전트 수가 아니라 첫 코드부터 사람의 수용까지 걸린 시간을 기준으로 개선 여부를 판단한다.

비유와 깨지는 지점

주문이 몰린 주방

요리사를 늘리기만 하면 조리대와 주문 규칙이 뒤섞일 수 있다. 담당 구역을 나누고, 같은 조리 기준을 적용하고, 완성된 음식의 주문 일치 여부를 확인해야 전체 주문이 빨라진다. 작업 공간은 담당 조리대, 자동 검사는 정해진 조리 기준, 사람의 리뷰는 주문과 실제 결과가 맞는지 확인하는 과정에 대응한다.

비유가 깨지는 지점: 소프트웨어 작업은 파일뿐 아니라 자격 증명, 데이터베이스, 외부 서비스 권한과 변경 이력이 얽힌다. 또한 자동 테스트는 음식의 상태를 직접 감각으로 확인하는 것과 달리, 미리 정의된 조건만 검사할 수 있다.

파일과 실행 환경이 뒤섞이면 작업 공간 분리, 같은 검사를 사람이 반복하면 검증 자동화, 개별 작업은 되지만 합칠 때 문제가 생기면 병렬 작업 계획을 우선 후보로 삼는다. 실제 선택은 가장 자주 생기는 병목을 관찰한 뒤 작고 경계가 분명한 작업으로 검증해야 한다.

이번 글의 통찰

1. 생산 속도는 첫 출력이 아니라 사람의 수용까지 측정해야 한다

  • [원문] 영상은 코드가 처음 나온 시간과 사람이 검토해 받아들인 시간을 함께 기록하고, 프롬프트 수정·테스트 실패 해결·병합 충돌 정리에 쓴 시간도 살펴보라고 권한다.
  • [해석] AI 개발 도구의 가치는 생성량보다 검토 가능한 증거를 포함한 결과가 얼마나 빨리 수용되는지로 평가해야 한다.
  • [경계] 영상은 이 측정법을 권하지만 특정 팀에서 시간이 실제로 얼마나 줄었다는 결과 수치는 제시하지 않는다. 차드의 시스템에서 검증된 효과도 아니다.

2. 모델이 판단할 일과 시스템이 강제할 일을 나눠야 한다

  • [원문] Collison의 발언으로 소개된 부분은 모델의 올바른 행동 가능성뿐 아니라 불변 조건과 단단한 장벽에 의존해야 한다고 강조한다. Minions 흐름에는 모델 판단과 정해진 코드 실행이 함께 있다고 설명한다.
  • [해석] 구현처럼 열린 판단은 에이전트에 맡기더라도 접근 권한, 필수 검사, 다음 단계 진입 조건은 가능한 범위에서 시스템으로 고정하는 편이 낫다.
  • [경계] 자동 검사의 통과는 요구 사항·보안·사용자 영향 전체의 충족을 보장하지 않는다. 무엇을 자동화하고 무엇을 사람이 판단할지는 작업별로 정해야 한다.

3. 이름과 숫자를 섞어 읽지 않아야 한다

  • [원문] 영상은 Minions가 goose를 기반으로 Stripe가 만든 자체 에이전트이며 Claude Code와 동일하지 않다고 구분한다. 인용된 사례에는 devbox 열 개와 하루 또는 여러 날의 실행이 등장한다.
  • [해석] 제품 이름과 실행 환경, 에이전트 수를 생산성 주장으로 뭉뚱그리지 말고 각각의 역할과 측정 결과를 분리해야 한다.
  • [경계] 숫자 대조 결과, 영상이 제시한 방법은 작업 공간 분리·검증 자동화·병렬 작업 계획의 세 가지로 실제 열거와 개수가 일치한다. 다만 devbox 열 개는 생산성 열 배라는 수치가 아니다. META에는 creator가 없고 affiliation만 Claude로 기록되어 있으나, 전사는 Patrick Collison과 Boris Cherny의 대담을 다룬다. provenance.note도 원작 출처를 화자 이름과 링크를 근거로 한 추정이라고 밝히므로 원작자와 전체 소속을 확정할 수 없다. 로그인·검색 기능·소규모 팀 작업 분담은 Stripe의 실제 사례가 아니라 영상 제작자의 설명용 예시다.

# 섹션 요지
1 검토와 통합의 간격 코드 생성 뒤에도 요구 사항·테스트·통합 판단이 남는다
2 분리된 작업 환경 devbox와 워크트리의 역할 및 격리 한계를 구분한다
3 제한과 자동 검증 모델 판단과 정해진 검사를 함께 사용한다
4 저장소 맥락과 병렬 계획 권장 예제와 작업 계약을 먼저 정한 뒤 병렬 실행한다
5 작은 시험과 측정 첫 출력이 아니라 사람의 수용까지 걸린 시간을 기록한다

1. 검토와 통합의 간격

영상은 AI가 로그인 기능의 코드와 테스트를 반환해도 권한 규칙, 다른 화면에 미치는 영향, 요구 사항 충족 여부를 사람이 확인해야 하는 가상 사례로 시작한다. 이 사례는 Stripe의 실제 사건이 아니다.

코드 작성 시점과 배포 가능 시점 사이에는 요구 사항 확인, 테스트 적합성, 다른 변경과의 통합이 남는다. 코드만 빨라지면 검토를 기다리는 변경이 쌓일 수 있다는 것이 영상의 문제 설정이다.

2. Stripe 사례와 작업 환경 분리

영상은 Stripe를 결제 인프라 회사로 소개하고, Patrick Collison과 Boris Cherny의 대담 및 Stripe 기술 글을 자료로 사용한다.

Stripe 기술 글에 등장한다고 설명된 devbox는 코드와 개발 서비스를 담은 클라우드 개발 환경이다. Minions는 goose를 기반으로 Stripe가 만든 자체 에이전트로 소개된다. Claude Code와 Minions는 같은 제품이 아니며, Minions의 처리 순서를 Claude Code의 내부 구조로 해석하면 안 된다.

작은 팀에 제시된 대안은 브랜치와 워크트리로 파일 작업 공간을 분리하는 것이다. 그러나 다음 항목은 별도로 정해야 한다.

  • 테스트 데이터
  • 환경 변수
  • 실행 포트
  • 데이터베이스와 외부 서비스 접근 권한
  • 실패한 작업을 같은 조건에서 다시 시작하는 방법

검색 API와 관리 화면을 서로 다른 에이전트에 맡기는 사례는 영상 제작자의 설명용 예시다.

3. 단단한 제한과 자동 검증

Collison의 발언으로 제시된 핵심은 모델의 성향이나 올바른 행동 가능성보다 시스템이 보장하는 불변 조건과 단단한 장벽을 중시해야 한다는 것이다.

영상은 다음 두 가지를 구분한다.

  • 운영 데이터를 건드리지 말라는 요청
  • 개발 환경에서 운영 데이터에 접근할 수 없게 만드는 제한

Minions의 흐름에는 모델이 판단하는 단계와 정해진 코드가 실행하는 단계가 함께 있으며, Stripe 기술 글에서는 이를 블루프린트라고 부른다고 설명한다. 작은 팀의 적용 예시는 포맷 검사, 타입 검사, 관련 테스트를 순서대로 실행하고 결과가 없으면 다음 단계로 넘어가지 않게 하는 것이다.

검사 실패 시에는 실패한 명령과 오류를 에이전트가 확인할 수 있어야 한다. 다만 테스트 통과가 요구 사항 충족을 보장하지 않으므로, 사람이 판단할 검토 항목을 남겨야 한다.

4. 저장소를 맥락으로 관리하기

대담에서 인용된 관점은 모든 코드베이스가 다른 코드베이스를 위한 프롬프트가 된다는 것이다. 저장소에 오래된 예제나 서로 다른 구현 방식이 섞여 있으면 AI가 잘못된 패턴을 따라갈 수 있다.

영상 제작자가 권하는 방법은 다음과 같다.

  • 작업 디렉터리 가까이에 필요한 안내를 둔다.
  • 금지 사항과 함께 권장 모듈이나 구현 예제를 알려준다.
  • 같은 실수가 반복되면 프롬프트만 고치기 전에 오래된 코드와 설명을 확인한다.

이는 대담의 관점을 소규모 팀에 옮긴 해설이며, Stripe가 직접 제시한 세부 운영 방식으로 확정할 수 없다.

5. 계획한 뒤 병렬로 실행하기

영상에 인용된 Stripe 사례에서는 한 사람이 복잡하고 상세한 계획을 세운 뒤 서로 다른 에이전트가 있는 devbox 열 개에 작업을 나눈다. 작업은 하루 동안 또는 극단적인 경우 여러 날 진행될 수 있다고 말한다.

이 수치는 생산성 열 배를 의미하지 않는다. 병렬 실행 전에 맞출 항목은 다음과 같다.

  • 입력과 출력
  • 오류 형식
  • 각 작업이 수정할 파일
  • 독립 작업과 선행 결과가 필요한 작업의 구분
  • 코드 작성, 테스트 통과, 리뷰 요청 중 어디까지를 완료로 볼지
  • 전제가 바뀌었을 때 중단하고 다시 나눌 기준

새 검색 기능의 API와 화면을 병렬로 만드는 사례도 영상 제작자가 설명을 위해 든 소규모 팀 예시다.

6. 첫 적용과 측정

영상은 현재 병목에 따라 첫 개선점을 고르라고 권한다.

  • 파일과 실행 환경이 뒤섞임: 작업 공간 분리
  • 같은 검사와 오류 확인을 사람이 반복함: 검증 자동화
  • 개별 결과는 되지만 통합에서 막힘: 병렬 작업 계획

시험 대상은 재현 가능한 버그 수정이나 범위가 좁은 테스트 보강처럼 경계가 분명한 작업이다. 결과에는 변경 이유, 실행한 명령, 남은 문제를 붙이고 사람은 요구 사항, 실패 상황, 배포 판단과 되돌릴 책임을 확인한다.

측정 시에는 코드가 처음 나온 시간과 사람이 검토해 받아들인 시간을 함께 기록한다. 프롬프트 수정, 테스트 실패 해결, 병합 충돌 정리에 든 시간도 병목 판단의 근거로 삼는다. 영상은 이를 적용 권고로 제시하며 실제 개선 수치는 제공하지 않는다.

AI가 코드를 다 짰다는데 왜 나는 더 바빠졌을까요? 이 영상에서는 Stripe의 사례를 통해 작업 환경을 분리하고 검증을 자동화하고 병렬 작업을 설계하는 세 가지 방법을 살펴봅니다. 보고 나면 내 프로젝트에서 무엇부터 바꿀지 정할 수 있을 겁니다.

예를 들어보겠습니다. AI에게 로그인 기능을 고쳐달라고 했더니 코드와 테스트까지 돌아옵니다. 그런데 우리 서비스의 권한 규칙과 맞는지, 다른 화면을 깨뜨리지는 않는지 확인하다 보면 어느새 저녁입니다. 이런 검토와 통합의 부담은 AI를 쓰는 개발자가 겪을 수 있는 상황입니다. Stripe에서 실제로 벌어진 일을 옮긴 예시는 아닙니다.

오늘 살펴볼 자료는 Stripe CEO Patrick Collison과 Claude Code를 만든 Boris Cherny의 대담입니다. Stripe는 결제 인프라를 만드는 회사입니다. 개발 속도를 높이면서 서비스의 신뢰성도 지켜야 합니다. 대담의 내용을 Stripe 공식 기술 글과 함께 살펴보겠습니다.

AI가 코드를 작성한 시점과 우리가 그 코드를 배포할 수 있는 시점 사이에는 간격이 있습니다. 요구 사항이 맞는지, 테스트가 충분한지, 다른 변경과 합쳤을 때도 동작하는지 확인해야 합니다. 이 간격을 그대로 둔 채 코드만 더 빨리 만들면 검토를 기다리는 변경이 쌓일 수 있습니다. 먼저 AI가 작업할 공간부터 보겠습니다.

Stripe의 공식 기술 글에 등장하는 devbox는 코드와 개발 중인 서비스를 담은 클라우드 개발 환경입니다. Minions라는 자체 에이전트도 이 환경에서 일합니다. 사람이 쓰던 개발 기반을 에이전트에도 활용한 겁니다. 여기서 두 이름을 구분하겠습니다. Claude Code와 Minions는 같은 시스템이 아닙니다. Minions는 goose를 바탕으로 Stripe가 만든 자체 에이전트입니다. 지금부터 설명할 Minions의 처리 순서를 Claude Code의 내부 구조로 받아들이시면 안 됩니다.

작업 환경을 나누면 무엇이 달라질까요? 설명을 위해 한 에이전트는 검색 API를 고치고 다른 에이전트는 관리 화면을 만든다고 해보겠습니다.

같은 작업 폴더에서 동시에 파일을 바꾸면 누가 만든 변경인지부터 확인해야 할 수 있습니다. 각자 독립된 환경에서 일하면 변경과 실행 기록을 작업별로 살펴보기 쉬워집니다. 작은 팀이라면 우선 작업별 브랜치와 워크트리로 파일을 분리해 볼 수 있습니다. 다만 워크트리는 파일 작업 공간을 나누는 도구입니다. 접근 권한이나 데이터베이스까지 자동으로 격리해 주지는 않습니다.

테스트 데이터, 환경 변수, 실행 포트, 외부 서비스 권한은 따로 정해야 합니다. 실패한 작업을 버리고 같은 조건에서 다시 시작할 수 있는지도 확인해 보시면 좋겠습니다. 환경을 나눴다면 그 안에서 어디까지 할 수 있는지 정할 차례입니다. 대담에서 Collison은 모델이 올바르게 행동할 가능성에만 기대기보다 시스템이 지켜야 할 조건과 단단한 제한을 강조합니다. 그 대목을 짧게 보겠습니다.

좀 더 구체적으로, 세부적인 내용도 말씀해 주세요. AI를 활용해 안정성과 품질을 희생하지 않으면서 어떻게 더 빠르게 배포하나요? 구체적으로 어떤 가드레일(guardrail)을 두고 있나요?

결국 이는 다소 주관적이거나 재량에 좌우되거나 확률적인 것보다는 불변성(invariance)과 강력한 장벽(hard barrier)에 의존한다는 생각으로 귀결됩니다. 물론 모델이 잘 정렬되어 있고, 올바른 코드나 보안성이 높은 코드 등을 작성할 가능성이 더 높다면 좋겠죠. 하지만 아무것도 완벽할 수는 없습니다. 정말로 의존해야 하는 것은 보장(guarantee)입니다.

이 말을 우리 팀의 작업으로 옮겨보겠습니다. 운영 데이터를 건드리지 말라고 적어두는 것과 개발 환경에서 운영 데이터에 접근할 수 없게 만드는 것은 다릅니다.

전자는 요청이고 후자는 시스템의 제한입니다. 어떤 파일을 수정할 수 있는지, 어떤 자격 증명을 쓸 수 있는지, 어디에 배포할 수 있는지 경계를 먼저 정하는 겁니다.

코드 검증도 같은 방식으로 생각할 수 있습니다. Stripe는 Minions의 흐름에 모델이 판단하는 단계와 정해진 코드가 실행하는 단계를 함께 둡니다. 구현에는 에이전트를 쓰고 정해둔 검사에는 일반 코드를 쓰는 방식입니다. 공식 기술 글에서는 이를 블루프린트라고 부릅니다.

예를 들어, 우리 팀에서는 변경이 생기면 포맷 검사, 타입 검사, 관련 테스트를 순서대로 돌리도록 만들 수 있습니다. 매번 프롬프트에 테스트를 부탁하는 데서 끝내지 않고 검사 결과가 없으면 다음 단계로 넘어가지 않게 하는 겁니다. 검사에 실패했다면 어떤 명령이 실패했고 어떤 오류가 나왔는지 에이전트가 확인할 수 있어야 합니다.

물론 테스트가 통과했다고 요구 사항까지 맞다는 뜻은 아닙니다. 로그인 버튼이 잘 눌리는 것과 다른 사람의 계정으로 들어갈 수 없는 것은 서로 다른 확인 항목입니다. 팀이 지켜야 할 동작을 구체적으로 적고 사람이 검토할 항목도 남겨야 합니다. 모델에게 결과를 물어보는 것에 더해 우리가 확인할 수 있는 증거를 함께 받는 방식입니다.

Stripe에서 우리가 자주 언급하는 친구의 말은 이렇습니다. 이제 모든 코드베이스는 또 다른 코드베이스를 위한 프롬프트(prompt)입니다.

이 관점을 적용하면 저장소 정리도 AI와 함께 일하는 준비가 됩니다.

새 API를 만들어 달라고 할 때 같은 일을 하는 코드가 세 가지 방식으로 흩어져 있다면 어떤 방식을 따라야 할까요? 오래된 예제를 먼저 읽었다면 이미 버린 설계를 다시 가져올 수도 있습니다.

팀에서 권장하는 구현 예제와 테스트 실행 방법을 찾기 쉽게 두면 이런 혼선을 줄이는 데 도움이 됩니다. 여기서 제가 권하는 방법은 모든 규칙을 긴 문서 하나에 넣는 것보다 작업하는 디렉터리에서 필요한 안내를 발견하게 하는 겁니다. 예를 들어 결제 코드에는 금액 처리 규칙을, 화면 코드에는 컴포넌트 사용 예제를 연결하는 식입니다.

문서에는 하면 안 되는 일만 적지 말고 무엇을 쓰면 되는지도 보여주면 좋겠습니다. 새 인증 로직을 만들지 말라는 문장 옆에 기존 인증 모듈의 위치를 적어두는 겁니다. AI가 같은 실수를 반복한다면 프롬프트를 다시 쓰기 전에 잘못된 예제나 오래된 설명이 저장소에 남아 있는지 확인해 보십시오.

Stripe의 한 사람은 자신이 일하는 방식으로, 가장 뛰어난 모델을 사용해 매우 복잡하고 방대한 계획을 세우되 계획 수립 과정에 많은 투자를 합니다. 그런 다음 서로 다른 에이전트들이 계획의 각기 다른 부분을 실행하도록 열 개의 서로 다른 개발 환경(devbox)을 배정할 수도 있죠. 이들은 하루 종일 작업할 수도 있고, 극단적인 경우에는 며칠 동안 작업하기도 합니다.

이 숫자를 생산성이 열 배라는 뜻으로 읽을 수는 없습니다. 먼저 볼 것은 어떤 계획으로 일을 나눴느냐입니다.

작은 팀의 예를 들어보겠습니다. 새 검색 기능의 API와 화면 테스트가 필요합니다. 새 에이전트에게 동시에 검색 기능을 만들라고 하면 응답 형식부터 서로 다르게 정할 수 있습니다. 그래서 시작 전에 입력과 출력, 오류 형식, 각자 바꿀 파일을 맞춰줍니다. API가 아직 없어도 화면 작업을 할 수 있도록 임시 응답도 합의할 수 있습니다.

이렇게 독립적으로 진행할 수 있는 일을 찾고 다른 결과를 기다려야 하는 일은 순서를 정합니다. 계획에는 완료 조건도 들어갑니다. 코드 작성 완료인지, 테스트 통과인지, 리뷰 요청까지인지가 분명해야 결과를 비교할 수 있습니다. 계획을 자세히 쓴다고 처음 예상이 모두 맞는 것은 아닙니다. 작업 중 전제가 달라졌다면 멈춰서 다시 나눌 기준도 필요합니다. 에이전트가 서로 다른 방식으로 같은 문제를 해결한 뒤 사람이 마지막에 전부 고쳐 붙이는 상황을 줄이려는 겁니다.

그렇다면 내 프로젝트에서는 무엇부터 바꾸면 좋을까요? 방금 본 세 가지를 기준으로 지금 가장 자주 막히는 곳을 찾아보시면 됩니다. 여러 작업의 파일이나 실행 환경이 뒤섞인다면 작업 공간 분리부터 시작합니다. 같은 검사와 오류 확인을 사람이 매번 반복한다면 검증 자동화부터 손봅니다. 각자 만든 코드는 잘 돌아가는데 합칠 때 문제가 생긴다면 병렬 작업의 계획부터 점검합니다.

입력과 출력, 수정 범위, 완료 조건이 서로 맞는지 확인하는 겁니다. 우선순위를 골랐다면 작고 범위가 분명한 작업 하나로 시험해 보시길 권합니다. 재현 방법이 있는 버그 수정이나 영향 범위가 좁은 테스트 보강이 좋겠습니다. 고칠 문제와 바꿔도 되는 범위, 완료를 확인할 명령을 함께 적습니다.

별도 작업 공간에서 필요한 권한만 주고 결과에는 변경 이유와 실행한 명령, 남은 문제를 붙이도록 합니다. 사람은 그 자료를 보고 요구 사항과 위험을 판단합니다. 테스트가 이미 있는 동작만 확인하고 있지는 않은지, 실패한 경우도 다루는지 살펴봅니다. 배포 판단과 문제가 생겼을 때 되돌릴 책임자도 정해둡니다.

이 실험에서는 코드가 처음 나온 시간과 사람이 검토해서 받아들인 시간을 함께 기록해 보십시오. 프롬프트 수정, 테스트 실패 해결, 병합 충돌 정리에 쓴 시간을 보면 처음 고른 우선순위가 맞았는지 판단할 수 있습니다. 잘된 작업 하나를 기준으로 범위를 넓히면 에이전트를 늘리기 전에 우리 팀의 준비 상태를 확인할 수 있습니다.

AI가 코드를 다 짰는데 왜 나는 더 바빠졌을까요? 코드 작성 뒤에 남아 있던 검토와 통합을 우리가 계속 맡고 있기 때문일 수 있습니다. 오늘은 Stripe의 사례를 통해 작업 환경 분리, 검증 자동화, 병렬 작업 설계를 살펴봤습니다. 이제 다음 작업을 떠올려보십시오.

작업끼리 간섭하는지, 같은 검사를 반복하는지, 결과를 합칠 때 막히는지에 따라 먼저 바꿀 곳을 고를 수 있습니다. 한 번에 모두 바꾸려 하지 않아도 됩니다. 가장 자주 막히는 한 곳을 골라 작은 작업으로 시험하고 검토까지 걸린 시간이 줄었는지 확인해 보십시오. 이번 영상은 여기까지입니다. 도움이 되셨다면 구독과 좋아요 부탁드립니다. 시청해주셔서 감사합니다.
