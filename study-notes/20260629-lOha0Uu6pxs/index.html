한 줄 요약

에이전트는 "질문-응답 프롬프트 루프"에서 "자율적으로 오류를 복구하며 밤새 스스로 일하는 장시간 실행 액터"로 진화했고, Anthropic은 이를 손쉽게 구축할 수 있는 사전 제작 하네스인 Claude Managed Agents로 이 흐름에 베팅했다.

버티컬(수직) 특화 에이전트 향후 산업 트렌드 예측 범용 대신 초니치 용도로 점점 좁아짐

내가 모를 만한 것 / 처음 보는 것

  • Managed Agents (매니지드 에이전트) — Anthropic이 제공하는 사전 구축 에이전트 인프라 제품. 모델·시스템 프롬프트·도구 접근권한·(선택적) 스킬을 콘솔에서 구성해 클라우드에서 장시간 실행되는 세션으로 돌린다. 직접 프롬프트 루프를 처음부터 짜는 대신 이미 만들어진 하네스를 쓰는 개념.
  • 하네스(Harness) — 모델을 감싸는 스캐폴딩. 도구 호출, 메모리 접근, 사람 개입이 필요한 시점 판단 등을 담당한다. 같은 모델이라도 하네스가 다르면 실제 성능·행동이 달라져서, Anthropic은 모델을 평가할 때 항상 특정 하네스와 짝지어 테스트한다.
  • MCP(Model Context Protocol) — 에이전트가 제3자 데이터베이스·내부 시스템과 표준화된 방식으로 통신하게 해주는 프로토콜. 인증 계층이 내장돼 있어 민감한 내부 서비스에 안전하게 접근 가능.
  • 트레이스(Trace) 기반 디버그 에이전트 — Claude 콘솔 안에서 별도 에이전트가 세션 전체 기록(트레이스)을 분석해, 원래 에이전트를 어떻게 개선할 수 있을지 짚어주는 기능.
  • 아웃컴 최적화(Outcome optimization) — 과거에는 "이 JSON 구조를 정확히 지켜라"는 식으로 출력 포맷을 강제했지만, 지금은 "이런 결과(예: 정확도 90% 모델)"라는 목표만 주면 에이전트가 스스로 반복 실행하며 그 기준에 도달할 때까지 조정한다.
  • 트리거 평가(Triggering evals) — 특정 행동(예: 스킬이 적절한 타이밍에 실제로 발동됐는지)이 일어났는지 자체를 검사하는 평가 유형. 스킬의 핵심 원리인 점진적 노출(progressive disclosure)이 실제로 제대로 작동하는지 확인하는 데 쓰인다.
  • 바이브 테스팅(Vibe testing) — 정식 평가 체계를 만들기 전, 실제 베타 사용자 손에 빠르게 쥐여주고 정성적 반응(바이브)을 보는 초기 검증 단계. 화자는 이것이 "가장 중요한 첫 단계"라고 강조.

화자의 디테일 (놓치기 쉬운 포인트)

Jess가 시연·인터뷰 중 흘린 구체적 수치·설정·사례.

  1. 데모 에이전트 = 가상의 식료품점 "Just In Time" 분석기 — 수백만 줄짜리 대용량 파일을 입력으로 주고, 사전에 데이터 스키마를 정의해 초기 탐색 단계를 생략시켰다고 밝힘.
  2. 출력 산출물 3종 — ① 상품/장바구니 패턴 분석, ② 쇼핑객 히트맵·레이더 차트, ③ 고객 재방문 여부를 예측하는 예측 모델(HTML 파일로 렌더링). 전부 "그냥 프롬프트 + Python 패키지 접근"만으로 몇 분 만에 생성됐다고 강조.
  3. 정확도 목표치 90% 예시 — 예측 모델의 정확도 벤치마크를 90%로 설정하면, 에이전트가 그 점수에 도달할 때까지 스스로 반복 테스트하며 모델을 개선한다고 설명.
  4. API 리뷰용 "중립 심판" Claude — Anthropic 내부에서 API 설계가 의견 충돌로 교착 상태에 빠지면 Claude를 불러 "우리 편향이 어디서 작용하는지" 판단하게 한다는 실제 사내 관행 언급.
  5. 4,000개 조직 대기자 명단(waitlist) 자동화 — 고급 기능 대기자 명단에 잘못된 항목·중복이 가득했는데, Jess가 직접 사내 시스템·DB에 접근권한을 준 에이전트를 만들어 무효 항목 걸러내기, 전환 가능성 높은 순 평가, 매일 대기자 명단에서 빼줄 사람 선정까지 자동화. "이 작업은 몇 주만 쓸 거라 예쁘게 만들 필요 없다"는 태도로 약 30분 만에 스핀업.
  6. 새 부모 친구 사례 — 아이 수유·터미타임 스케줄 전체를 Claude가 관리하고, 냉장고 모니터링·장보기 관리 에이전트까지 개인적으로 운용 중인 지인 예시.
  7. 프로덕트 조언: "너무 복잡하게 시작하지 마라" — 기업들이 바로 20개 팀이 얽힌 초거대 워크플로우 자동화를 시도하는 경향을 지적하며, 먼저 개인 1인의 생산성을 극적으로 끌어올리는 작은 에이전트부터 시작하라고 강조("한 회사 안에 여러 개의 1인 스타트업이 있는 셈").
  8. 버티컬 특화 전망 — 회계 에이전트도 "일반 회계"가 아니라 "1인 사업자용 회계 에이전트"처럼 점점 좁고 구체적인 니치로 향한다고 예측. 공유되는 건 "표준 도메인 에이전트 패턴"이 아니라 "컨텍스트 패턴·작업 오케스트레이션 패턴" 자체.
  9. "항상 켜져 있는(always-on)" 에이전트 상호작용 방식 — 트리거된 이벤트·크론잡 기반으로 능동적(proactive)으로 정보를 갱신하며, 사람이 물어볼 때만 반응하는 게 아니라 동료처럼 먼저 다가와야 한다고 정의.
  10. Cloud Managed Agents는 클라우드 호스팅 — 노트북에 종속된 로컬 세션과 달리 클라우드에서 실행되므로 노트북이 꺼져 있어도 계속 작업하고, 그만큼 작업 용량과 지속시간이 늘어난다고 명시.

1. 에이전트 정의와 진화

Jess는 에이전트를 정의해달라는 질문에 "예전에는 단순히 질문과 응답을 반복하는 프롬프팅 루프였다"고 짚으며, 지금은 서드파티 시스템·내부 도구·민감 데이터에 대한 접근과 권한이 필요해지면서 진화했다고 설명한다. 이 접근 수준은 이제 권한 관리(permissioning), 관측성(observability), 조종(steering)을 필요로 한다. 다만 근본 구성요소(모델, 시스템 프롬프트/행동 지침, 실제로 루프를 굴리는 하네스)는 그대로이고, 요구하는 작업의 정교함이 높아지면서 하네스의 정교함도 함께 높아졌다고 말한다.

2. 하네스(Harness)란 무엇인가

하네스는 모델이 도구를 실행하고, 메모리를 호출하고, 사람 개입이 필요한 시점과 계속 실행할 시점을 판단하게 해주는 핵심 스캐폴딩이다. 이것이 "무작위 토큰 샘플링"을 실제로 액션 가능한 제품으로 격상시킨다.

Jess는 "모델과 하네스가 한 몸이어야 하는가"라는 질문에 자신이 편향돼 있음을 인정하면서도, 하네스 없이는 모델의 최대 성능을 끌어낼 수 없다고 답한다. 시간이 지나면서 하네스의 구성요소나 두께는 바뀔 수 있지만, 모델을 테스트·평가할 때는 항상 특정 하네스와 함께 테스트해야 한다는 사실은 변하지 않는다 — 세상의 모든 하네스로 테스트할 수는 없으니 Anthropic이 직접 구축한 하네스(Claude Code, Co-work 등)로 테스트한다. 결국 모든 모델 배포는 어떤 하네스를 통해 이뤄지므로 모델과 하네스는 자연히 짝지어진다.

3. Managed Agents 소개

Managed Agents는 작업 오케스트레이션의 진화 방향이라고 소개된다. 프롬프트 루프에 이런저런 기능을 덧붙인 게 아니라, 복잡한 작업을 대규모로 실행할 수 있는 사전 구축 하네스와 부속 인프라라는 것. 핵심 동기는 "에이전트를 만드는 데 드는 노력 대비 얻는 수익(ROI)이 극단적으로 높아야 한다"는 것 — 쉽게 쌓을 수 있는 프리미티브와 사용하기 쉬운 유연한 API, 즉시 사용 가능한 인프라를 낮은 노력으로 제공하면서도 며칠~몇 달 걸릴 복잡한 작업을 위임할 수 있어야 한다는 철학이다.

4. 데모: 분석 에이전트 구축

Jess는 Claude 콘솔에서 이미 구성해둔 에이전트를 보여준다. 핵심 구성요소는 다음 4가지:

  1. 모델 선택 — 에이전트의 지능 층을 결정
  2. 시스템 프롬프트 — 모델의 행동·가드레일·작업 유형에 대한 상위 인식을 정의하는 원문 텍스트
  3. 도구 접근(built-in toolset) — 파일 시스템과 상호작용하고 결과를 만들 수 있는 권한. 이번 데모에서는 각 도구를 "항상 허용"으로 설정했지만, 사람 개입(human-in-the-loop)이 필요하도록 권한 요청형으로 구성하는 것도 가능
  4. 스킬(선택) — 이번 데모에는 부여하지 않았지만 부여 지점이 존재

이 에이전트는 "Just In Time"이라는 가상 식료품점 데이터를 분석하는 데이터 분석가 역할을 한다. 초기 프롬프트에는 데이터 스키마와 실행 가이드, 그리고 수백만 줄짜리 대용량 파일이 함께 주어진다. 세션이 진행되는 동안 에이전트가 도구를 호출하며 스스로 작업하는 걸 볼 수 있고, 초기 지시 이후에는 조종하지 않는다고 Jess는 강조한다. 최종적으로 브라우저에서 렌더링 가능한 HTML 파일 3종(상품 분석, 쇼핑객 히트맵/레이더 차트, 재방문 예측 모델)이 산출된다.

초기 프롬프트를 만들 때는 데이터셋 구조를 미리 알려줘서 원래 필요했을 탐색 단계를 생략시키고, 작업 단계를 이산적인 세그먼트로 쪼개서 예측 가능한 출력을 얻으려 했다고 설명한다. 에이전트가 근본적으로 무작위성을 가진 액터이기 때문에, 예측 가능한 결과를 원한다면 어느 정도 규정적(prescriptive)으로 지시할 필요가 있다는 것.

5. 스크래치 대비 이점 — 자기 복구형 루프

Managed Agents 없이 처음부터 직접 만들면 어떻게 될지 묻자, Jess는 순수 프롬프트 루프로 작업할 경우 모든 게 고도로 동기적(synchronous)이 된다고 답한다. 앞선 요청이 성공적으로 완료돼야 다음 단계로 넘어갈 수 있는 구조인데, 이는 챗봇에게 하이쿠나 써달라고 하던 단순한 시절엔 통했지만 시간이 갈수록 확장 불가능해졌다.

큰 작업을 위임했는데 첫 메시지에서 뭔가 잘못되면(메시지를 놓치거나 기대와 살짝 어긋나면), 통합을 우아하게 전환하고 처리할 능력이 크게 떨어진다. 그래서 스스로 실행하고 스스로 복구하는(self-running, self-recovering) 에이전트 루프로 진화해야 한다 — 에러에서 회복하고, 경로를 살짝 이탈해도 스스로 다시 조준하면서 사람에게는 그 과정을 계속 알려주는 방식. "자기 복구"란 에이전트가 에러를 만나면 스스로 디버그하고 검색해서 알아내는 것을 의미하며, 더 근본적으로는 산출물이 기대와 다를 때 좋은 산출물이 어떤 모습이어야 하는지 스스로 인지하고 사고를 수정할 수 있다는 뜻이다. 이건 순수 프롬프트 루프로는 엮어내기 매우 어렵다고 Jess는 강조한다.

6. 평가(Evals) 설계

트레이스와 산출물이 쌓인 뒤 "이 에이전트가 궤도를 이탈하지 않는지 어떻게 아는가"라는 질문에, Jess는 evals가 에이전트를 만드는 데 있어 가장 어려운 부분이라고 답한다. 전통적 방식(초기 프롬프트 세트 → 기대 응답 비교)은 여전히 유효하지만, 더 복잡한 다중 스트링 상호작용의 리플레이나 동일 사용자 상호작용 문자열을 보내는 A/B 테스트 같은 더 정교한 방식도 등장하고 있다.

Managed Agents에서 지원하는 또 다른 트렌드는 내장 평가 루프(built-in eval loop) — 에이전트 스스로 자기 산출물을 채점할 줄 알면, 평가를 세션 밖이 아니라 에이전트 작업 안으로 직접 끌어들일 수 있다는 것. Jess는 편향을 피하기 위해 별도 컨텍스트 윈도우에서 에이전트가 자기 작업을 평가하게 하면 항상 더 나은 결과를 얻는다고 말한다.

평가 유형은 크게 3가지: ① 이진 합격/불합격, ② 채점형(LLM-judge 방식으로 등급 매기기), ③ 트리거형(예: 특정 행동이 실제로 제때 발동됐는지 확인 — 스킬이 적절한 타이밍에 트리거되는지가 초기에 공들인 예시). 스킬의 핵심이 점진적 노출(progressive disclosure)이기 때문에 이 트리거 정확도가 중요했고, 예전에는 슬래시 명령으로 수동 트리거해야 할 만큼 성능이 낮았지만 시간이 지나며 개선됐다고 언급한다.

7. 아웃컴 중심 프롬프팅

에이전트가 더 자율적으로 장시간 작업을 수행하게 되면서, "목표가 무엇이고 원하는 결과가 무엇인가"가 프롬프팅의 중심이 된다고 Jess는 말한다. 예전에는 구조화된 출력(structured output)을 엄격히 지정하고 그걸 사람이 직접 아름답게 렌더링되도록 접착제처럼 엮어야 했다면, 이제는 모델과 하네스가 발전하면서 결과(outcome) 자체가 메타 구조화된 출력이 됐다 — 정확한 응답 구조를 지시하지 않고 "이런 풍부하고 인터랙티브한 결과물을 만들자"는 목표만 제시하면, 에이전트가 스스로 궤도를 수정하며 그 목표에 다가간다.

예시로 슬라이드 생성·콘텐츠 제작 같은 시각적 산출물, 그리고 앞서 보여준 예측 모델처럼 "정확도 90%를 달성해야 한다"는 구체적 목표를 주면 에이전트가 그 점수에 도달할 때까지 반복 테스트하며 모델을 개선하는 사례를 든다.

8. Anthropic 내부 활용

Jess는 내부적으로 에이전트를 쓰는 이유를 "깊이(depth)"라는 한 단어로 요약한다. 코드베이스 접근이 가장 큰 언락이었다고 말하며, 엔지니어들을 일일이 찔러보지 않고도 PR이 머지·배포됐는지 직접 추적할 수 있고, Cloud Managed Agents로 빠르게 에이전트를 프로토타입하거나 코드베이스를 직접 질의할 수 있어서 제품을 과거보다 훨씬 깊이 이해하고 상호작용한다고 설명한다. 고객 RFP의 보안 체크마크 작성부터 현장 문제 진단, 사용자 지원, 아키텍처 이해를 통한 확장 지원까지 모든 게 "1만 배 쉬워졌다"고 강조.

구체적으로는 활동을 요약하는 예약 실행(scheduled runs)을 걸어두면서도, 준비 중인 피치나 고객 대화에 맞춰 임시(ad hoc) 딥다이브를 많이 한다고 밝힌다. 또한 슬랙 채널을 모니터링하는 에이전트를 운용해, 직접 대화할 수 없는 고객들의 활동을 요약받는다. 핵심은 ① 데이터 접근 수준, ② 상호작용 스타일(사람처럼 능동적이어야 함) 이 두 축이라고 짚는다.

능동성(proactive)은 트리거된 이벤트와 크론잡을 통해 구현되며, 지속적으로 데이터를 새로고침해 항상 최신 정보를 갖추고 있어야 한다고 설명한다.

Jess는 자신이 동료보다 Claude와 더 많이 대화한다고 인정하며, 특히 낯선 영역을 다룰 때 개념을 붙잡기 위해 Claude와 많은 "치료 시간"을 보낸다고 표현한다. 이는 팀원과의 대화 수준을 끌어올려준다 — 이미 의견과 기초 리서치를 갖고 대화에 들어가기 때문. Anthropic은 의사결정 회의에도 Claude를 불러들이며, API 리뷰에서 팀이 교착 상태에 빠지면 편향을 짚어주는 중립 심판 역할로 Claude를 태그한다고 언급한다.

9. 4,000개 대기자 명단 자동화 사례

Jess는 자신의 하루가 이전보다 훨씬 고객 발굴·통합 여정 논의에 많은 시간을 쓴다고 말하며, 프로토타이핑에도 많은 시간을 쓴다고 밝힌다. Managed Agents의 장점은 에이전트를 빠르게 스핀업할 수 있다는 것 — 자신의 업무는 매주 성격이 바뀌므로 그 순간의 작업에 딱 맞는 에이전트를 만들고, 그 에이전트를 버려도 상관없다는 태도로 임한다(가장 아름답고 제품화된 형태일 필요 없음). 에이전트 하나를 만드는 데 보통 30분 정도 걸리며, 몇 주마다 새로운 것을 돌린다고 밝힌다.

구체 사례: 고급 기능 대기자 명단이 4,000개 조직 규모였는데, 일반 웹 폼에서 흔히 생기는 무효 항목·중복이 가득했다. 이 기능이 셀프서브로 공개되기까지 몇 주만 유효할 임시 작업임을 알았기에, 무효 항목 걸러내기·전환 가능성이 가장 높은 항목 평가·매일 대기자 명단에서 뺄 사람 선정까지 자동화하는 에이전트를 사내 시스템·DB 접근권한과 함께 스핀업했다. "몇 주짜리 작업에 화려한 것을 만들 이유가 없다"는 게 요지이며, 이런 반복 작업을 손쉽게 자동화해주는 사전 구축 인프라가 자신에게 "거대한 언락"이라고 말한다.

이어서 개인 사용자도 API 큐(API queue)만 있으면 회사 없이 이 제품을 쓸 수 있다고 확인하며, 실제로 개인 사용량이 예상외로 많다고 밝힌다. 사례로 신생아 부모인 친구가 수유·터미타임 스케줄 전체를 Claude로 관리하고, 냉장고 모니터·장보기 관리 에이전트까지 돌리고 있다고 소개한다. Jess는 대규모 사용 패턴에는 직접 접근하지 못하지만(내부적으로 상당수가 마스킹/편집됨), 개인 비서처럼 쓰는 사례가 대표적이라고 말한다.

10. 기업 도입 조언 — 개인 단위부터 시작하라

Jess는 자신의 편향을 인정하며, 기업들이 흔히 20개 팀이 얽힌 초거대 워크플로우를 자동화하려는 성급한 시도로 바로 뛰어드는 경향을 지적한다. 이런 야심은 좋지만, 그보다 먼저 "개인 한 명을 어떻게 언락할 것인가"가 정말 가치 있다고 강조한다. 한 사람(예: Peter나 Jeff)이 갑자기 "인간에게 부탁했어야 할 디자인 작업을 이제 에이전트로 확장해서 처리할 수 있다"고 느끼게 되면, 전체 다중분기 컴플라이언스 프로세스를 완전히 없애지는 못하더라도 개인·조직 단위에 창의성과 자율성의 씨앗을 심어준 것이라고 설명한다.

개인 직원들이 스스로 창의적으로 무엇을 만들 수 있는지 느끼게 하는 게 첫 출발점이고, 이후에 다중 팀 메가 프로세스의 복잡도를 높여가면 된다는 것. "한 회사 안에 여러 개의 1인 스타트업이 있는 셈"이라는 비유를 쓴다.

이어 개별 직원에게 자유롭게 자기 에이전트를 만들게 하는지, 아니면 스포트라이트 예시(템플릿)를 주는지 묻자, 사람들에게 템플릿을 주고 그 위에서 자유롭게 반복하게 하는 것이 항상 좋은 접근이라고 답한다. 무엇을 해야 할지 모르는 "작가의 벽(writer's block)"을 피하면서도 창의적으로 반복할 여지를 준다는 것. 그리고 정식 evals를 만들기 전에 실제(베타) 사용자 손에 최대한 빨리 쥐여주는 것이 중요하다고 강조 — 이것이 "고무가 도로에 닿는(rubber meets the road)" 순간이며, 바이브 테스팅(vibe testing)이 정직하게 가장 중요한 첫 단계라고 말한다. 다만 규모가 커지면 정성적 바이브 신호를 집계할 수 없게 되므로 그때 정식 evals로 넘어가야 한다.

11. 향후 전망 — 장시간 실행, 버티컬 특화, 챗 중심 접점

앞으로 3~6개월 뒤를 묻자, Jess는 "자기 전에 '알아서 다 처리해줘'라고 말하고 일어나면 끝나 있는" 세상이 이미 어느 정도 실현되고 있다고 답한다. 장시간 실행 에이전트에게 밤새 작업을 맡기면 깨어났을 때 백로그가 해결되고 버그가 잡혀 있다는 것. 향후 우리가 성취할 수 있는 한계는 "개인의 역량"보다 "한 번에 얼마나 많이 위임할 수 있는가"에 좌우될 것이라고 전망한다 — 에이전트를 파트너로 점점 더 많이 의존하게 될 것이기 때문.

산업 수준에서는 버티컬 특화(vertical specialization)가 점점 좁아지는 흐름에 주목한다. 회계 에이전트 대 헬스케어 에이전트라는 구분조차 모델이 똑똑해질수록 더 좁고 니치한 용도로 세분화될 것이라고 본다 — 광범위한 도메인 전문성은 이미 모델 자체에 내장돼 있으므로, 진짜 가치는 초specific·초niche 사용 사례에서 나온다는 것. 그래서 공유되는 공통 요소는 "정형화된 회계 에이전트 만드는 법" 같은 표준 패턴이 아니라 컨텍스트 패턴과 작업 오케스트레이션 패턴 자체라고 짚는다.

이 트랜스포메이션에서 살아남을 제품은 "사용자가 있는 곳, 워크플로우가 있는 곳을 정확히 만나는" 제품이라고 전망한다 — 초구체적(hyper-specific)이면서도 적응 가능해야 하고, 정확히 필요한 위치에 있어야 한다는 것. 그래서 항상 켜져 있는(always-on) 에이전트 패턴이 중요하다 — 적절한 시점에 등장하면서도, 워크플로우가 처리될 것으로 기대되는 발견 가능한 위치에 있어야 하기 때문. 점점 더 그 위치는 Claude Code나 이런 앱들 안이 될 것이며, Vercel Chat SDK가 "이제 모든 것이 챗이다"라고 본 비전을 언급하며, 결국 챗이 개인 컨텍스트 전체와 연결되는 방향으로 수렴한다고 마무리한다.

진행자: 다들 에이전트, 에이전트 기술 스택 이야기를 하는데, 에이전트를 어떻게 정의하시나요? 에이전트의 주요 구성요소는 뭔가요?

Jess: 정말 무거운 질문이네요(웃음). 예전에는 에이전트가 단순히 질문과 응답을 반복하는 프롬프팅 루프였어요. 그런데 이게 서드파티 시스템, 내부 툴링, 민감 데이터에 대한 권한 부여와 접근으로 진화했다고 봐요. 그 정도의 접근 권한은 이제 예전처럼 그냥 질문에 답하던 것과는 다르게 권한 관리, 관측성, 조종(steering)을 필요로 합니다. 근본 구성요소는 여전히 모델, 시스템 프롬프트와 행동 지침, 그리고 실제로 루프를 굴리는 하네스예요. 다만 우리가 에이전트에게 요구하는 작업의 정교함이 높아졌기 때문에 하네스의 정교함도 함께 높아졌습니다.

진행자: 맞아요, 에이전트는 도구를 쓰고 메모리를 가질 수 있고 여러 가지가 있죠. 하네스가 뭔지도 정의해주실래요?

Jess: 하네스는 모델을 둘러싼 핵심 스캐폴딩이에요. 모델이 도구를 실행하고 메모리를 호출하고, 사람 개입이 필요한 시점과 계속 작업을 진행할 시점을 알게 해줍니다. 그래서 하네스는 무작위 토큰 샘플링을 실제 액션 가능한 제품으로 격상시켜주는 역할을 해요.

진행자: 커브볼 하나 던질게요. 모델은 하네스와 함께 개발돼야 한다고 생각하세요? 서로 엉덩이가 붙어 있는 건가요?

Jess: 저는 편향이 있다는 걸 인정하지만, 하네스와 모델을 함께 엮지 않고는 최대 성능을 끌어낼 수 없다고 생각해요. 하네스의 구성요소나 두께는 모델이 더 유능해지면서 시간이 지나 바뀔 수 있지만, 모델을 테스트하고 성능을 평가할 때는 항상 하네스와 함께 테스트해야 해요. 세상의 모든 하네스로 테스트할 수는 없으니 우리가 구축한 하네스를 선택하는 거고, 그래서 모델을 만드는 데는 하네스와 함께 테스트해야 하는 필연성이 있고 그게 둘을 계속 짝지어줍니다.

진행자: 그러니까 Claude, Co-work, Claude Code, 그리고 일부 서드파티 하네스로 테스트하는 거네요?

Jess: 네, 물론 오픈소스 평가에도 대응하지만, 이제는 모든 모델 배포가 하네스를 거치기 때문에 하네스를 통해서도 테스트해야 합니다.

진행자: 이제 제품 이야기를 해볼게요. Managed Agents가 뭔가요? 그냥 제가 메시지 API랑 대화하는 것과 뭐가 다른가요?

Jess: Managed Agents는 작업 오케스트레이션이 향하는 방향의 진화예요. 앞서 말했듯 에이전트가 프롬프팅 루프에서 자율적으로 자기 발견하고 장시간 실행되는 액터로, 서드파티 시스템에 대한 많은 접근과 권한·가드레일이 필요한 존재로 진화했죠. Cloud Managed Agents는 그걸 염두에 두고 개발됐습니다. 그냥 여러 기능을 덧붙인 프롬프팅 루프가 아니라, 복잡한 작업을 대규모로 실행할 수 있는 사전 구축 하네스와 부속 인프라예요. 우리에게 핵심 동기는 에이전트를 만드는 데 드는 노력 대비 얻는 수익이 극도로 높아야 한다는 거예요. 그래서 쌓기 쉬운 프리미티브, 사용하기 쉽고 유연한 개발자 API, 즉시 사용 가능한 인프라를 낮은 노력으로 제공하면서도, 며칠·몇 주·몇 달 걸릴 수 있는 엄청나게 복잡한 작업을 위임할 수 있어야 합니다.

진행자: 에이전트를 구동하기 위해 직접 만들어야 했던 인프라를 대신 처리해주는 거네요?

Jess: 네, 정확해요.

진행자: 그럼 매니지드 에이전트를 만드는 게 얼마나 쉬운지, 혹은 어려운지 보여주실래요?

Jess: 네, 쉬웠으면 좋겠네요. (콘솔 화면 공유) 여기 클라우드 콘솔에 이미 구성해둔 에이전트가 있어요. 핵심 구성요소를 보면, 첫째는 모델 선택이고 이게 에이전트 아래 깔린 지능 계층을 계속 이끌어가요. 여기 시스템 프롬프트가 있는데, 모델이 행동·가드레일·수행할 작업 종류에 대한 상위 인식을 정의하는 원문 텍스트예요. 모든 Cloud Managed 에이전트와 함께 제공되는 내장 툴셋 접근 권한을 줬고, 파일 시스템과 상호작용해서 결과를 만들어낼 수 있게 했어요. 실제로는 이 도구들 각각을 항상 허용하도록 설정했는데, 권한을 요청하는 방식으로 구성할 수도 있어요. 그러면 이 액션들에 대해 사람이 계속 개입(human in the loop)하게 되는 거죠. 이번엔 스킬을 부여하지 않았지만, 여기가 스킬을 부여할 지점이에요.

진행자: 이건 데이터를 분석하는 에이전트, 데이터 분석가 같은 거네요?

Jess: 맞아요.

진행자: 이 에이전트는 가상의 식료품점 "Just In Time"에 대한 분석을 실행해요. 데이터 스키마와 실제로 작업을 실행하는 방법에 대한 가이드를 주는 초기 프롬프트를 줬고, 분석할 수백만 줄짜리 큰 파일도 함께 줬어요. 세션이 진행되는 동안 모든 도구를 실행하며 모델을 선택적으로 호출하는 걸 볼 수 있어요. 마지막에는 브라우저에서 렌더링될 수 있는 HTML 파일을 출력해서 분석 결과를 볼 수 있게 해요. 이 모든 이벤트가 모델이 취하는 액션들이고, 초기 이벤트 말고는 실제로 조종하지 않는다는 걸 볼 수 있어요. 마지막에 이 산출물들이 저를 위해 만들어져요.

진행자: 이 대화의 초기 프롬프트는 뭐였나요?

Jess: 그냥 "큰 파일을 분석해줘" 정도로 생각할 수 있지만, 저는 알고 있길 원하는 구체적인 스키마를 줬어요. 예를 들어 데이터셋 구조가 어떤지 미리 알려줘서 원래 해야 했을 초기 탐색을 프론트로드시켰죠. 그리고 예측 가능한 출력을 얻으려고 단계를 이산적인 세그먼트로 나눴어요. 에이전트는 무작위 액터니까, 매우 예측 가능한 출력을 원한다면 어느 정도 규정적(prescriptive)일 필요가 있어요.

진행자: 이게 디버깅에도 도움이 되겠네요. 어느 단계에서 문제가 생겼는지 알 수 있으니까요?

Jess: 맞아요. 실제로 Cloud 콘솔에는 에이전트가 실행되고 관련된 전체 세션 히스토리를 분석하는 에이전트가 있어서, 실행 후에 이 디버그 에이전트를 써서 이 에이전트를 더 개선할 수 있는 영역을 찾을 수 있어요.

진행자: 출력은 다시 말하면 HTML 파일인가요?

Jess: 네, 세 가지 다른 HTML 파일을 만들어요. 지금 바로 보여드릴 수 있어요. 그러니까 구성요소는 모델, 프롬프트, 도구 접근, 그리고 선택적인 스킬이 있는 거예요.

진행자: 도구 접근에 대해선, 내부 DB 같은 걸 연결하고 싶으면 전체 프로세스가 있나요?

Jess: 네, 서드파티 데이터베이스나 시스템에 에이전트를 연결하는 방법 중 하나가 MCP예요. MCP는 외부 서비스와 통신하는 표준화된 방법을 노출하고 그 앞에 인증 계층을 포함해서, 아무나 접근하면 안 되는 내부 서비스에 안전하게 접근할 수 있게 해줘요.

진행자: 만약 Cloud Managed Agents를 안 쓰고 처음부터 이걸 직접 만들어야 했다면, 어떤 스캐폴딩이 필요할까요?

Jess: 순수 프롬프팅 루프로 작업한다면, 모든 작업이 굉장히 동기적이에요. 앞선 요청이 성공적으로 완료돼야 다음 단계로 갈 수 있다는 데 계속 의존하게 되죠. 챗봇에게 하이쿠를 써달라고 하는 정말 단순한 작업을 하던 시절엔 통했지만, 시간이 갈수록 확장 불가능해졌어요. 예를 들어 정말 큰 작업을 에이전트에게 위임했는데 첫 초기 메시지에서 뭔가 잘못됐다면, 그러니까 메시지를 놓쳤거나 제 기대와 살짝 어긋났다면, 제 통합을 우아하게 전환하고 처리할 능력이 크게 떨어져요. 그래서 스스로 실행하고 스스로 복구하는 에이전트 루프로 진화하는 게 중요해요 — 에러에서 회복하고, 경로에서 살짝 벗어나도 스스로 재조준하면서 그 과정을 계속 알려주는 방식으로요.

진행자: 자기 복구라고 하면, 에러가 나면 스스로 디버그하고 검색해서 알아낸다는 뜻인가요?

Jess: 네, 맞아요. 그리고 더 기본적으로는, 만약 기대와 다른 출력을 만들었는데 좋은 출력이 어떤 모습이어야 하는지 알고 있다면, 스스로 사고를 수정하고 행동 방침을 조정할 수 있다는 거예요. 이건 순수 프롬프팅 루프로는 엮어내기 정말 어려운 부분이에요.

진행자: 다시 돌아가서, 지금 출력이 생성되고 있나요, 아니면 아직 작업 중인가요?

Jess: 이 에이전트는 3가지 핵심 산출물을 만들어요. 첫째, 상품에 대한 분석 — 장바구니의 일반적인 주문 패턴에 대한 상위 검토예요. 둘째, 쇼핑객에 대한 분석과 그들이 언제 쇼핑하는지에 대한 히트맵, 그리고 정말 흥미로운 레이더 차트들을 만들어요. 마지막으로 제가 개인적으로 가장 좋아하는 건, 고객과 상품의 다양한 속성을 기반으로 이 고객이 재방문할지 예측하는 예측 모델이에요. 이 모든 게 그냥 간단한 프롬프팅과 에이전트 환경 안의 Python 패키지 접근만으로 이뤄졌고, 몇 분 만에 정말 풍부한 수준의 인사이트를 만들어낼 수 있어요.

진행자: 그럼 프롬프트에 원하는 3가지 리포트 형식과 원하는 데이터에 대한 내용이 들어 있는 거네요?

Jess: 네. 시스템 프롬프트에 넣은 건 일반적인 성능 최적화예요, 왜냐하면 이걸 여러 데이터셋에 재사용할 수 있는 범용 에이전트로 만들고 싶었거든요. 그리고 제가 보낸 초기 프롬프트에 넣은 건 매우 구체적인 스키마 발견과, 분석을 순서대로 실행하는 방법에 대한 실제 작업 설명이에요.

진행자: 자, 이제 트레이스랑 산출물이 많이 쌓였는데, 이 에이전트를 위한 평가는 어떻게 만드나요? 이게 궤도를 이탈하지 않는지 어떻게 알죠?

Jess: evals가 오늘날 에이전트를 만드는 데 있어 확실히 가장 어려운 부분이에요. 전통적인 eval 개발 방식은 작업이 더 복잡해지면서 진화하고 있다고 봐요. 초기 프롬프트 세트가 있고 에이전트가 그에 대한 응답으로 어떻게 결과를 만들길 원하는지를 정하는 전통적인 eval 설정은 여전히 통해요. 그런데 사람들이 더 복잡한, 여러 문자열을 이어붙인 상호작용의 리플레이 같은 더 정교한 걸 하거나, 같은 사용자 상호작용 문자열을 보내고 그게 결국 응답을 어떻게 바꾸는지 보는 A/B 테스트 같은 것도 하는 걸 보고 있어요. Cloud Managed Agents에서 우리가 활성화하고 있는 또 다른 트렌드는 내장 eval 루프예요 — 에이전트 스스로 자기 산출물을 채점할 줄 안다면, 그 eval을 세션 밖이 아니라 에이전트의 작업 안으로 직접 끌어올 수 있어요.

진행자: 이건 제가 Cloud Code에서 하는 거랑 비슷하네요. 출력이 나오면 다른 에이전트에게 eval을 돌리게 하고, eval이 별로면 다시 작업하게 하고요.

Jess: 기본적으로 맞아요. 에이전트가 자기 작업을 평가하게 할 수 있고, 그것도 편향을 피하기 위해 별도의 컨텍스트 윈도우에서 하게 하면, 항상 더 나은 출력을 얻게 돼요.

진행자: eval에 대해 빠르게 하나만요 — 이진 합격/불합격 eval을 하나요, 아니면 점수형 eval을 하나요?

Jess: 다 해요. 확실히 이진 합격/불합격도 있고, 더 LLM 심사(judge) 같은, 일종의 등급 매기기(letter grading) 방식에 가까운 점수형도 있어요. 그리고 트리거형 eval도 있어요 — 예를 들어 특정 종류의 액션이 실제로 트리거되는지 확인하는 거요. 예를 들어 스킬 관련해서 아주 초기에 공들인 것 중 하나가 스킬이 적절한 타이밍에 제대로 트리거되는지 확인하는 거였어요. 스킬의 핵심이 점진적 노출(progressive disclosure)이니까요.

진행자: 아 맞아요, 예전엔 그렇게 좋지 않아서 슬래시 명령으로 스킬을 수동으로 트리거해야 했었죠.

Jess: 네, 그런데 시간이 지나면서 조금 나아졌어요.

진행자: 이 에이전트들이 더 자율적이 되고 더 긴 작업을 할 수 있게 되면서, 목표가 뭐고 원하는 결과가 뭔지가 더 중요해지는 것 같은데, 어떻게 생각하세요? 프롬프팅이나 모든 게 바뀌는 거죠?

Jess: 네, 확실히 바뀌죠. 예전엔 구조화된 출력이 있었어요. 에이전트에게 "네 출력은 이 구조화된 코드 포맷을 엄격히 따라야 한다"고 구체적으로 말했고, 그다음 이 크고 구조화된 JSON 데이터 덩어리들을 브라우저에서 아름답게 렌더링되는 무언가로 바꾸기 위해 많은 접착제(glue)를 엮어야 했죠. 모델이 더 유능해지고 하네스가 진화하면서, 결과(outcome) 자체가 구조화된 출력이 된 것 같아요. 이제 결과는 일종의 메타 구조화된 출력이에요 — 이제는 "이게 네 응답의 정확한 구조야"라고 말할 필요 없이, 이 모든 걸 접착제로 엮어서 풍부하고 인터랙티브한 걸 만들 필요가 없어요. 그냥 바로 "이 풍부하고 인터랙티브한 걸 만들자"고 말하는 거고, 이게 좋은 게 어떤 모습인지에 대한 제 취향 판단(tastemaker's assessment)이에요. 그리고 이제 이 에이전트들이 자율적으로 실행할 수 있는 인프라가 있으니까, 우리가 모든 중간 출력을 이어붙이는 데 의존하지 않고도 에이전트가 그 과정에서 스스로 수정할 수 있어요.

진행자: 그러니까 "여기 다섯 섹션을 지켜라, 여기 글자 수를 지켜라"가 아니라 — 사실 더 어려운 것 같은데, 취향 판단 출력의 예시가 뭔가요? "아름답고 인터랙티브하게 만들어" 같은 건가요?

Jess: 네, 슬라이드 생성이나 콘텐츠 제작에 이걸 쓰는 걸 봐요. 그게 결과 최적화가 정말 유용한 영역 중 하나예요 — 시각적 산출물과 편집적 콘텐츠요. 다른 곳은, 예를 들어 방금 보여드린 예측 모델이에요. 만약 제가 정확도 벤치마크에서 90%라는 특정 점수를 달성해야 한다면, 이 에이전트로 그 점수를 항상 맞추도록 최적화하는 모델을 만들려고 테스트를 실행했고, 도달할 때까지 반복했어요.

진행자: 알겠어요, 말이 되네요. 사람의 눈이 개입하기 전에 에이전트가 자기 루프를 먼저 돌리게 하는 게 말이 되죠. 최대한 진행시키는 거니까요.

진행자: 기어를 좀 바꿔볼게요. Anthropic 내부에서 에이전트를 어떻게 쓰는지 얘기해봐요. 슬랙 화면 공유도 할 수 있을 텐데, Anthropic PM이나 기술 스태프들에게 에이전트가 업무에서 어떤 도움과 레버리지를 줬는지 궁금해요.

Jess: 저에게는 정말 "깊이(depth)"에 관한 거였어요. 저희 코드베이스 접근이 가장 큰 언락이었다고 생각해요. 첫째, 여러 엔지니어를 찔러가며 뭘 하고 있는지 묻는 대신 상태를 더 쉽게 관리할 수 있게 해줘요. PR을 직접 추적하고 어떤 게 머지됐고 어떤 게 배포됐는지 볼 수 있어요. 그리고 제 제품을 과거보다 훨씬 더 깊이 이해하고 상호작용한다는 측면도 있어요. Cloud Managed Agents로 에이전트를 프로토타입하거나 Cloud Code를 써서 코드베이스가 정확히 어떻게 작동하는지 직접 캐물을 수 있으니까 훨씬 빠르거든요. 고객 RFP에 들어가서 보안 체크마크를 다 채우는 것부터 현장 문제 진단, 문제 있는 사용자 지원, 우리의 특정 아키텍처를 이해하도록 도와 확장을 돕는 것까지 — 내부에 가진 모든 에이전트 덕분에 그 모든 게 1만 배 쉬워졌어요.

진행자: 몇 가지로 나눠볼게요. 월요일에 출근하면 "Claude, 지난주에 우리 엔지니어들이 뭘 배포했어?" 이렇게 묻나요?

Jess: 저는 활동을 요약하는 예약 실행(scheduled runs)을 몇 개 걸어뒀어요. 하지만 여전히 받는 질문이나 준비해야 할 피치, 앞으로 있을 고객 대화에 기반해서 더 임시적(ad hoc)인 딥다이브를 많이 해요.

진행자: 그러니까 엔터프라이즈 고객에게 매니지드 에이전트 얘기를 하러 갈 때 그 회사에 맞춰 피치를 개인화해야 하는 거네요?

Jess: 네, 맞아요.

진행자: 피드백은 어떻게 받나요? 트위터에서 활동하는 분들도 있잖아요, 좀 독하긴 하지만. 제품 피드백은 어떻게 받으세요? 엔터프라이즈 슬랙 그룹 같은 게 있나요?

Jess: 저는 저희 슬랙 채널을 모니터링하는 에이전트가 있어요. 많은 고객과 함께 있는 여러 슬랙 채널에 들어가 있고, 고객과 직접 대화하는 걸 정말 좋아해요. 하지만 직접 대화할 수 없는 고객들에 대해서는 에이전트가 거기서 일어나는 활동을 요약해주는 게 유용해요. 우리는 에이전트를 "항상 켜져 있는" 존재로 생각하는 쪽으로 진화하기 시작했어요 — 어디서든 태그할 수 있어야 하지만, 진짜 동료처럼 능동적으로 정보를 찾아 알려줘야 한다는 거죠. 저희 에이전트 사용에 정말 강력한 두 측면이 있는데, 하나는 우리가 주는 데이터 접근 수준이고, 둘은 우리가 에이전트에게 기대하는 상호작용 스타일이에요 — 사람처럼, 능동적이고 반응적이지만은 않아야 한다는 거예요.

진행자: 능동성은 트리거된 이벤트와 크론잡을 통해서인가요, 아니면 어떻게 능동적으로 만드나요?

Jess: 네, 능동성은 트리거된 이벤트와 크론잡을 통해서예요. 그리고 사용 가능한 데이터를 계속 새로고침해서, 장시간 실행되고 계속 정보를 빨아들이고 있다면 사용자만큼 최신 상태여야 해요. 그게 그냥 임시로 하는 게 아니라 능동적이어야 해요.

진행자: Claude·에이전트와의 대화 vs 동료와의 대화를 어떻게 비교하세요? 하루 중 어느 쪽이 더 많나요?

Jess: 흥미로운 질문이네요. 솔직히 저는 Claude와 더 많이 대화하는 것 같아요. 특히 새로운 영역에 있을 때 어떤 어려운 개념을 붙잡으려고 Claude와 많은 "치료 시간"을 쓰는 걸 발견해요. 그게 팀원들과의 대화를 한 단계 끌어올려줘요, 왜냐하면 이미 진짜 의견과 빠르게 끝낸 기초 리서치를 갖고 대화에 들어갈 수 있으니까요. "그냥 저를 위해 뭔가 준비해줄래요?" 같은 질문을 하지 않고 더 깊은 수준에서 관여할 수 있어요.

진행자: Anthropic 사람이니까 Claude를 쓰도록 장려되는 게 어느 정도 예상되긴 하네요. 의사결정 회의나 팀 미팅에 Claude를 불러오나요?

Jess: 네.

진행자: 진짜요?

Jess: 네. Claude는 특정 사안에서 정말 좋은 중립 심판이에요. 저희에게 API 리뷰용 Claude가 있는데, API의 특정 구성요소를 어떻게 형성할지에 대해 정말 교착 상태에 빠지면 Claude를 태그해서 우리의 편향이 어디서 작용하고 있는지 말해달라고 해요. 하지만 우리의 모든 프리미티브는 이런 종류의 상호작용, 이런 에이전트 대 에이전트 커뮤니케이션을 가능하게 하려고 만들어져 있어요.

진행자: 이 섹션을 마무리하자면, 보통 하루를 어떻게 보내세요? 전형적인 날은 없겠지만, 엔터프라이즈 고객과 많이 대화하나요, 로드맵 계획을 많이 하나요, 직접 뭔가를 출시하나요?

Jess: 제 하루는 이제 예전보다 고객 발굴과 통합 여정 프로세스에 훨씬 더 많은 시간을 쓰는 것 같아요. 그리고 그게 멋지다고 생각해요. 왜냐하면 우리 모두가 너무 빠르게 움직이고 있어서, 우리가 나누는 대화의 종류가 정말 한 단계 업그레이드됐거든요. 예전엔 고객 대화에 이만큼 시간을 썼다면 "이 작은 걸 디버그해주세요, 제가 백 번 디버그해본 문제예요" 같은 거였을 텐데, 지금은 그들도 에이전트가 있고 우리도 에이전트가 있고 우리가 경계를 밀어붙이고 있으니까 대화가 "이 초미래적인 걸 함께 어떻게 만들까요? 원칙은 뭘까요? 다음 2주 안에 어떻게 밀어붙일까요?" 같은 게 돼요. 그런 대화들이 저에게 정말 흥미롭고, 고객들과 시간 보내는 걸 정말 좋아해요.

프로토타이핑에도 많은 시간을 써요. 매니지드 에이전트가 좋은 이유 중 하나는 에이전트를 스핀업하기가 정말 쉽다는 거예요. 제 업무는 매일매일 바뀌고 주 단위로도 절대 똑같아 보이지 않으니까, 그 순간의 특정 작업에 딱 맞는 에이전트를 스핀업할 수 있어야 해요. 그 에이전트를 버려도 괜찮아요, 세상에서 가장 아름답게 제품화된 게 아니어도 되니까요. 그래서 저는 제 업무를 자동화하면서 우리 제품을 스스로 사용해보는(dogfooding) 데 많은 시간을 써요. 에이전트 하나를 스핀업하는 데 30분 정도 걸리지만, 몇 주마다 다른 걸 돌리려고 해요.

진행자: 예시 하나 들어주실래요?

Jess: 네, 예시 하나 들게요. 저희 고급 기능 중 하나에 대기자 명단이 있었는데, 4,000개 조직 규모였어요. 그리고 전통적인 웹 폼에서 흔히 생기는 무효 항목, 중복 등으로 가득했죠. 저는 이 대기자 명단이 몇 주 안에 이 기능이 공개적으로 셀프서브가 되면 더 이상 관련이 없어질 거라는 걸 알고 있었어요. 그래서 이 대기자 명단으로 몇 주간의 업무를 자동화할 에이전트를 스핀업하기만 하면 됐어요 — 무효 항목을 걸러내고, 전환 가능성이 가장 높은 항목을 평가하고 정말 좋은 피드백을 주는 것까지요. 그리고 그 평가를 하기 위해 저희 내부 시스템과 데이터베이스 등에 대한 접근권한을 기본적으로 내장해서, 매일 누구를 대기자 명단에서 빼줄지 알아내게 했어요.

그냥 몇 주짜리 작업이고, 여기에 뭔가 화려한 걸 만들 이유가 없어요. 그래서 에이전트를 자동으로 구축해주는 정말 좋고 사용하기 쉬운 사전 구축 인프라를 갖는 게 저에게는 거대한 언락이에요. 그리고 저는 그런 작업들을 가져다가 그냥 반복할 수 있어요.

진행자: 그러니까 이 에이전트는 큰 대기자 명단을 보고 정리한 다음 명단에 있는 사람들에게 초대장을 보내는 거네요?

Jess: 네, 맞아요. 저희에게 가장 높은 가치의 테스터가 될 가능성이 가장 높은 사람들이요.

진행자: 트위터에서 가장 활발하게 불만 올리는 사람들인가요? (농담)
