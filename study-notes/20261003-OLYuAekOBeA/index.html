Lauren Tan(SpaceX - Cursor & Grok Bot 개발자)의 AI 에이전트 개발 워크플로우

원작자 Grok Bot · 업로드 2026-10-03 · 11.6분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 좋은 모델만으로는 충분하지 않다

AI 에이전트에게 코드를 맡기면 작성 속도는 빨라질 수 있다. 하지만 에이전트가 “완료했다”고 말한 뒤 사람이 앱을 열어 문제를 발견하거나, 한 곳을 고친 결과 다른 곳이 깨졌다면 사람의 확인 부담은 줄지 않는다. 이 영상의 중심은 더 많은 코드를 생성하는 법이 아니라, 에이전트가 실행 결과를 직접 보고 실패에서 배울 수 있는 작업 환경을 만드는 법이다.

화자 Lauren Tan은 가장 중요한 기술로 검증(verification)을 꼽는다. 여기서 검증은 단순히 코드나 설명을 다시 읽는 일이 아니다. 에이전트가 실제 코드를 실행하고, 일반 사용자처럼 앱과 상호작용하고, 디버깅 정보·실행 흔적·화면 상태를 살펴보게 하는 것이다. 화자는 이를 에이전트에게 “손과 눈”을 주는 것에 비유한다.

읽는 법: 위에서 아래로 읽는다. 각 상자는 독립적인 요령이 아니라 다음 상자를 가능하게 하는 조건이다. 마지막 목표는 검토를 없다고 선언하는 것이 아니라, 관찰된 실패를 작업 환경의 규칙으로 되돌려 같은 실패의 반복을 줄이는 것이다.

1. 먼저 에이전트가 결과를 직접 보게 한다

검증 기능이 없으면 에이전트는 코드를 바꾼 뒤 그 결과가 실제 앱에서 작동하는지 충분히 확인하지 못할 수 있다. 반대로 실행 도구가 있으면 성능 문제를 먼저 측정하고, 가설에 따라 코드를 바꾸고, 다시 측정하는 흐름을 만들 수 있다.

화자는 Cursor에 합류한 뒤 처음 만든 스킬이 검증 스킬이었다고 말한다. 다른 스킬보다 이 기능이 에이전트에 대한 신뢰 수준을 올리는 데 도움이 되었다는 설명이다. 다만 이는 화자의 경험과 평가이며, 모든 코드베이스에서 같은 결과가 난다는 독립 검증은 제시되지 않는다.

검증은 “테스트를 통과했다”는 한 문장보다 넓다. 영상에서 언급된 행동에는 다음이 포함된다.

  • 코드를 직접 실행한다.
  • 실제 사용자처럼 앱과 상호작용한다.
  • 디버깅한다.
  • 실행 흔적을 수집한다.
  • 화면이나 상태의 스냅샷을 남긴다.

2. 기계적인 절차와 판단을 분리한다

모든 단계를 에이전트가 매번 새롭게 생각하게 만들 필요는 없다. 특정 코드 패턴을 다른 패턴으로 바꾸는 것처럼 입력과 절차가 분명한 일은 기계적으로 반복할 수 있다. 화자는 이런 부분을 스크립트나 명령줄 도구인 CLI(Command-Line Interface)로 옮기고, 여러 맥락을 종합해야 하는 판단만 에이전트에 남긴다고 설명한다.

읽는 법: 데스크톱에서는 왼쪽과 오른쪽을 비교하고, 모바일에서는 위쪽 상자 뒤에 아래쪽 상자를 읽는다. 이 도식은 실제 성능 수치를 비교한 그래프가 아니라 영상의 구분을 정리한 개념도다.

핵심은 에이전트의 판단을 모두 제거하는 것이 아니다. 판단이 필요 없는 단계에서까지 판단을 요구하지 않는 것이다. 이렇게 하면 에이전트가 집중해야 할 범위가 좁아지고, 같은 작업이 매번 다르게 수행될 가능성도 줄일 수 있다.

3. 좋은 결과가 나오기 쉬운 코드 환경을 만든다

검증 도구가 있어도 에이전트가 따라갈 기존 코드가 무질서하면 좋지 않은 패턴을 반복할 수 있다. 영상에 나온 코드베이스는 제한적인 린트 규칙과 관례를 사용하고, 기능마다 정해진 디렉터리를 두어 기능을 추가할 경로를 좁힌다. 린트 규칙은 코드에서 금지하거나 권장할 형태를 자동으로 검사하는 규칙이다.

화자는 Grok Bot 초기 버전이 약 여덟 개의 거대한 파일로 구성되었고, 각 파일이 적어도 10,000줄이었다고 말한다. 그는 이를 더 작은 기능 단위로 나누었다고 설명한다. 목표는 에이전트가 기능을 어디에 넣을지 매번 추측하거나 하나의 거대한 파일에 계속 코드를 덧붙이지 않게 하는 것이다.

여기서 제약은 에이전트를 무조건 통제하기 위한 장벽이 아니다. 올바른 기본 경로를 눈에 잘 보이게 만들어 사람과 에이전트가 구조 선택에 쓰는 정신적 부담을 줄이는 장치다.

4. 코드 안의 작업과 외부 제보를 연결한다

영상은 코드 안에서 수정하고 검증하는 흐름과, 외부에서 들어오는 버그 제보를 수집하고 분류하는 흐름을 연결해야 한다고 말한다. 예를 들어 Slack MCP나 특정 채널을 구독하는 자체 도구가 있다면 에이전트가 제보를 받고 다음을 확인하도록 만들 수 있다.

  1. 제보된 현상을 이해한다.
  2. 현재 메인 코드에서도 문제가 남아 있는지 재현한다.
  3. 사용자 설정이나 데이터 차이인지 살핀다.
  4. 필요한 의존성을 설치하지 않은 문제인지 확인한다.

비슷한 제보마다 별도의 에이전트를 붙이면 같은 문제를 중복으로 고칠 수도 있으므로, 여러 작업을 함께 보고 조정하는 역할도 필요하다. 다만 전사에는 “안쪽 루프와 바깥쪽 루프를 연결하는 두 링크”라는 표현이 나오지만, 제공된 발췌만으로는 그 두 링크의 정확한 이름과 구성이 모두 열거되지 않는다.

5. 모든 결과를 직접 보지 말고 표본에서 환경을 고친다

작업량이 늘어나면 사람이 모든 PR을 같은 깊이로 읽는 방식은 유지하기 어렵다. 화자는 공장의 품질 감독자처럼 일부 결과를 표본으로 골라 엄격하게 살피는 방식을 설명한다. 표본에서 비효율이나 좋지 않은 패턴을 발견하면 한 건만 고치는 데서 끝내지 않고, 에이전트가 일하는 규칙과 제약을 교정한다.

읽는 법: 중앙의 네 상자를 위에서 아래로 1→2→3→4 순서로 읽는다. 그다음 4단계 상자 아래에서 시작한 선을 따라 아래로 내려가 왼쪽으로 이동하고, 왼쪽 가장자리를 따라 위로 올라간 뒤, 오른쪽으로 이동해 1단계 상자에 다시 들어간다. 이 반환 경로는 환경 교정이 다음 실행의 조건이 된다는 뜻이다. 수치 자료가 아니라 영상 내용을 묶은 개념도다.

화자는 이런 교정을 충분히 반복하면 사람이 한발 물러설 수 있는 환경에 가까워질 수 있다고 말한다. 그러나 그것을 이미 완전히 달성한 현재 상태로 단정하지 않는다. 직접 “꿈”이라고 표현하며, pstack을 설치하기만 하면 쉽게 도달하는 단계가 아니고 많은 시간과 노력이 필요하다고 경고한다.

주장과 확인 범위
  • 월 2,500 PR은 Lauren Tan이 소개한 본인의 공개 실적이다. 새 기능 2,500개를 만들었다는 뜻은 아니며, 이 자료만으로 수치가 독립 검증되지는 않는다.
  • 제목에는 SpaceX가 포함되지만, 제공된 전사에서 직접 확인되는 소속 관련 발언은 Cursor 합류 경험이다. SpaceX 이력은 이 자료만으로 확인할 수 없다.
  • META의 provenance.creator는 Grok Bot으로 기록되어 있으며, 출처 메모는 화자 이름과 SNS를 근거로 추정한 출처라고 밝힌다. 전사에서 Grok Bot은 코드·도구 사례로도 언급되므로 원작자 후보와 시스템의 관계는 추가 확인이 필요하다.
  • “안쪽·바깥쪽 루프를 잇는 두 링크”라는 수량 표현이 있지만, 제공된 발췌에는 두 링크가 각각 무엇인지 완전하게 열거되지 않는다.
  • 완전한 무인 운영은 검증된 현재 상태가 아니라 어렵게 도달하려는 목표로 제시된다.

여기까지만 이해하면 충분

  • 에이전트의 신뢰는 “완료했다”는 말이 아니라 실제 앱을 실행하고 결과를 관찰하는 검증에서 시작한다.
  • 반복적이고 기계적인 절차는 코드나 CLI로 옮기고, 맥락 판단만 에이전트에 남긴다.
  • 관례·린트·기능별 구조로 올바른 경로를 좁힌 뒤, 표본에서 발견한 실패를 환경 규칙에 다시 반영한다.
  • pstack 같은 도구의 설치만으로 완성되는 방식이 아니며, 지속적인 관찰과 환경 교정이 필요하다.

오늘 대답할 질문

AI 에이전트가 코드를 더 많이 만드는 것을 넘어, 실제 결과를 스스로 검증하고 반복되는 실패를 줄이게 하려면 어떤 작업 환경을 만들어야 하는가?

  • 어떤 일은 코드로 고정하고 어떤 일은 에이전트의 판단에 남겨야 하는가?
  • 검증 결과를 일회성 수정이 아니라 환경 개선으로 연결하려면 무엇을 살펴야 하는가?
  • 자동화 규모가 커질 때 사람의 검토 방식은 어떻게 달라져야 하는가?

비유와 깨지는 지점

공장의 품질 감독자

에이전트가 만든 PR을 생산품, 검증 도구를 검사 장비, 린트와 코드 관례를 생산 규격에 대응시킬 수 있다. 감독자는 모든 결과를 같은 깊이로 보지 않고 표본을 엄격히 검사한 뒤, 반복되는 결함이 보이면 생산 환경을 교정한다.

비유가 깨지는 지점: 소프트웨어 변경은 서로 영향을 주며 드문 조건에서만 실패할 수 있다. 따라서 표본 검토만으로 모든 결함을 발견한다고 보장할 수 없고, 실제 실행 검증과 예외 조건 확인이 함께 필요하다.

1. 원인

에이전트에게 코드를 맡겼는데도 사람의 확인 부담이 줄지 않는 이유는 무엇인가?

모범 답안 보기

코드 생성과 실제 결과 검증은 다른 일이다. 에이전트가 실행·상호작용·디버깅 도구 없이 변경만 만들면, 앱이 실제로 작동하는지와 다른 부분이 깨졌는지를 사람이 다시 확인해야 한다. 코드 구조가 무질서하거나 반복 절차까지 매번 판단하게 하면 결과의 변동과 검토 부담도 커질 수 있다.

2. 대조

검증 도구를 추가하는 것과 에이전트가 실수하기 어려운 환경을 만드는 것은 어떻게 다른가?

모범 답안 보기

검증 도구는 만들어진 결과를 실행하고 관찰하게 한다. 환경 설계는 애초에 기능을 둘 위치와 허용되는 코드 형태를 좁혀 잘못된 결과가 나오기 어렵게 한다. 전자는 결과를 발견하는 장치이고, 후자는 반복되는 실수를 예방하는 장치에 가깝다. 영상은 둘을 함께 사용해야 한다고 설명한다.

3. 적용

차드가 사용하는 자동화 가운데 하나를 고른다면, 무엇을 코드로 고정하고 무엇을 판단으로 남길 것인가?

모범 답안 보기

먼저 입력과 절차가 같을 때 같은 방식으로 수행할 수 있는 단계를 찾는다. 실행 명령, 형식 검사, 결과 캡처처럼 성공 조건을 명시할 수 있는 부분은 스크립트나 체크로 고정할 수 있다. 원인 가설, 예외 판단, 우선순위 결정처럼 여러 맥락을 함께 봐야 하는 부분은 에이전트나 사람의 판단에 남긴다. 실제 적용 가능성은 선택한 작업에서 별도로 검증해야 한다.

이번 글의 통찰

1. 에이전트의 신뢰는 권한보다 피드백에서 자란다

  • [원문] 화자는 검증을 가장 중요한 스킬로 꼽고, 실행·상호작용·디버깅·흔적·스냅샷을 통해 신뢰 수준을 올렸다고 말한다.
  • [해석] 에이전트에게 더 큰 작업을 맡기기 전, 결과를 직접 관찰하고 다시 수정할 수 있는 피드백 경로를 먼저 마련해야 한다.
  • [경계] 이는 화자의 경험과 주장이다. 특정 검증 도구가 모든 코드베이스에서 같은 신뢰 향상을 만든다는 비교 자료는 제공되지 않는다.

2. 반복 실패는 개별 결과가 아니라 환경의 신호다

  • [원문] 화자는 표본에서 비효율과 나쁜 패턴을 찾고, 에이전트가 기본적으로 올바른 일을 하도록 가드레일과 제약을 교정한다고 설명한다.
  • [해석] 같은 문제가 반복되면 매번 산출물만 고치지 말고, 스크립트·관례·린트·작업 경로 중 어느 부분이 실패를 허용했는지 살펴야 한다.
  • [경계] 충분한 표본의 크기나 선택 방법은 제시되지 않는다. 표본 검토가 드문 실패까지 발견한다고 보장할 수 없다.

3. 자동 운영은 현재의 완성 상태가 아니라 어려운 목표다

  • [원문] 화자는 환경이 충분히 제약되고 잘 안내되면 사람이 물러날 수 있는 상태를 “꿈”이라고 부르며, pstack 사용만으로 쉽게 되는 일이 아니라고 말한다.
  • [해석] 도구 설치보다 중요한 것은 실제 실패를 관찰하고 작업 환경을 계속 교정하는 운영 과정이다.
  • [경계] 월 2,500 PR은 화자가 소개한 공개 실적이지 새 기능 수가 아니다. 제목의 SpaceX 이력은 전사에서 확인되지 않으며, “두 링크”도 발췌 안에서 각각 열거되지 않는다. META의 원작자 후보 Grok Bot 역시 추정이라는 출처 메모와 함께 해석해야 한다.

교육자 · 구조적 비유

  • 통찰: 학습자도 이해했다고 말하는 것만으로 판단하기보다, 보지 않고 설명하거나 새 사례에 적용하게 해야 이해를 관찰할 수 있다.

사업가 · 구조적 비유

  • 통찰: APOM·이커머스·물류에 적용할 수 있는지는 아직 검증 전이지만, 반복 오류를 건별 처리할지 운영 규칙의 문제로 볼지 구분하는 질문은 옮길 수 있다.
  • 질문/행동: 실제 반복 업무 하나에서 같은 오류가 다시 생기는 원인이 절차·도구·규칙 중 어디에 있는지 확인할 수 있는가?

  • 관련성: “월 2,500 PR”은 강한 숫자이지만, 영상은 이를 새 기능 2,500개와 구분한다.
  • 통찰: 큰 숫자를 사용할 때는 측정 대상과 의미하지 않는 범위를 함께 밝혀야 주장이 과장되지 않는다.
  • 질문/행동: 상세페이지의 핵심 숫자마다 기간, 단위, 측정 대상, 제외 의미를 함께 제시할 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 실행 검증, 결정적 절차의 코드화, 코드 제약, 외부 제보 연결, 표본 검토는 에이전트 환경 설계에 직접 관련된다.
  • 통찰: 모델 선택만 비교하기보다 에이전트가 실패를 재현하고 결과를 관찰하며 같은 실패를 규칙에 반영할 수 있는지 측정해야 한다.
  • 질문/행동: 현재 자동화에서 사람이 결과를 기다리거나 다시 열어 확인하는 지점 하나를 검증 단계로 바꿀 수 있는가?

1. 문제 제기와 월 2,500 PR

영상은 AI에게 코드를 맡겼지만 확인할 일이 더 많아질 수 있다는 문제에서 시작한다. 에이전트가 완료했다고 보고해도 앱에는 문제가 남을 수 있고, 다시 수정하는 동안 다른 곳이 깨질 수도 있다.

Lauren Tan은 X에서 Potato로 알려진 개발자로 소개된다. 그는 한 달에 2,500개의 PR을 프로덕션에 반영했다고 소개했다. PR은 코드 변경을 검토하고 반영하기 위한 요청이다. 이 수치는 본인의 공개 실적이며 새 기능 2,500개를 의미하지 않는다.

경계: 수치는 제공된 자료에서 독립적으로 검증되지 않는다. 제목에는 SpaceX가 포함되지만 전사에서 직접 확인되는 소속 관련 내용은 Cursor 합류 경험이다.

2. 가장 중요한 스킬로 제시된 검증

화자는 검증을 도구 상자에서 가장 중요한 단일 스킬이라고 말한다. 에이전트에게 손과 눈을 주는 것처럼, 코드를 실행하고 일반 사용자처럼 상호작용하게 한다는 비유를 사용한다.

가능한 행동으로 다음을 언급한다.

  • 코드 실행
  • 앱과의 실제 상호작용
  • 디버깅
  • 실행 흔적 수집
  • 스냅샷 생성

화자는 Cursor에 합류한 뒤 처음 만든 스킬이 검증 스킬이었다고 말한다. 이 기능이 다른 스킬보다 에이전트에 대한 신뢰 수준을 올리는 데 도움이 되었다는 설명이다.

3. 결정적 절차와 판단의 분리

화자는 에이전트 작업을 하나의 연속선으로 본다. 한쪽에는 여러 맥락을 모아 생각해야 하는 판단 중심 작업이 있고, 다른 쪽에는 정해진 절차를 기계적으로 반복할 수 있는 작업이 있다.

코드 패턴을 다른 패턴으로 바꾸는 리팩터링은 기계적인 작업의 예로 제시된다. 이런 단계는 매번 에이전트가 새로운 방법을 생각할 필요가 없으므로 스크립트나 CLI로 추출한다. 실제 판단이 필요한 부분만 에이전트에 남기는 것이 여러 스킬을 만든 배경이라고 설명한다.

4. 코드 구조와 Grok Bot 사례

영상에 나온 코드베이스는 Electron 앱을 위한 내부 Next.js와 제한적인 린트 규칙을 사용한다. 기능마다 디렉터리가 있고, 레지스트리를 통해 기능을 발견하는 관례적 패턴이 언급된다.

화자는 이런 구조가 나쁜 코드를 작성하기 어렵게 만들고 사람과 에이전트의 정신적 부담을 줄인다고 말한다. 기능을 추가할 때 위치를 새로 판단하지 않고 정해진 기능 디렉터리에 넣을 수 있으며, 하나의 거대한 파일에 계속 덧붙이는 일을 피할 수 있다는 설명이다.

Grok Bot 초기 몇 버전은 약 여덟 개의 거대한 파일로 이루어졌고, 각 파일은 적어도 10,000줄이었다고 한다. 화자는 이를 더 작은 단위로 나눌 필요가 있었다고 말한다.

5. 안쪽·바깥쪽 루프와 버그 제보

화자는 pstack을 안쪽 루프와 바깥쪽 루프의 코드라고 설명하고, Grok Bot 도구가 바깥쪽 루프도 자동화하는 데 도움이 된다고 말한다. 두 루프를 연결하면 에이전트가 필요한 맥락을 스스로 얻을 수 있다는 주장이다.

Slack MCP나 특정 Slack 채널을 구독하는 자체 하네스를 예로 든다. 버그 제보가 들어오면 에이전트가 이를 분류하고, 기존 검증 스킬로 재현할 수 있다. 에이전트가 확인할 대상으로는 다음이 언급된다.

  • 버그가 현재 메인 코드에도 남아 있는가?
  • 사용자 설정이나 데이터 때문에 생긴 문제인가?
  • 필요한 의존성을 설치하지 않은 문제인가?

한국어 해설은 비슷한 제보마다 별도의 에이전트를 붙이면 같은 문제를 중복 수정할 수 있으므로 조정자 역할이 필요하다고 설명한다. 좋지 않은 코드 패턴을 발견해도 곧바로 수정하지 않고 문서에 모으는 사례도 소개한다.

경계: 전사에는 “두 링크”가 있다고 하지만 제공된 발췌에서는 두 링크의 이름과 구성이 각각 완전하게 열거되지 않는다.

6. 표본 검토와 환경 교정

작업이 많아지면 모든 항목을 직접 볼 수 없으므로, 화자는 공장의 품질 감독자처럼 표본을 보는 방식을 제안한다. 매일 일부 PR과 에이전트 코드를 엄격히 살펴 비효율과 좋지 않은 패턴을 찾고, 이를 바탕으로 환경의 방향을 교정한다.

이를 충분히 반복하면 환경의 제약과 안내가 강해져 사람이 물러설 수 있는 상태에 가까워질 수 있다고 말한다. 그러나 화자는 이를 “꿈”이라고 표현하며 어렵다고 분명히 밝힌다. pstack을 사용하는 것만으로 쉽게 도달할 수 있는 단계가 아니며 다음이 필요하다고 말한다.

  • 코드 자체를 깊이 살피는 시간
  • 에이전트가 실패하는 지점의 관찰
  • 가드레일과 제약을 의도적으로 설계하는 노력

출처 충돌 및 불확실성 목록

  1. 월 2,500 PR은 화자의 공개 실적으로 소개되지만, 독립 검증 자료는 제공되지 않는다. 새 기능 2,500개와는 명시적으로 구분된다.
  2. 제목은 Lauren Tan을 SpaceX·Cursor·Grok Bot 개발자로 표현하지만, 전사에서 직접 확인되는 소속 관련 발언은 Cursor 합류 경험이다.
  3. META의 provenance.creator는 Grok Bot이며, 메모는 화자 이름과 SNS를 근거로 추정한 출처라고 밝힌다. 전사에서 Grok Bot은 코드·도구 사례로도 언급되어 관계가 명확하지 않다.
  4. “안쪽 루프와 바깥쪽 루프를 연결하는 두 링크”라는 수량 표현이 나오지만, 제공된 발췌에는 두 링크가 각각 무엇인지 모두 열거되지 않는다.
  5. 사람이 물러설 수 있는 환경은 이미 검증된 완료 상태가 아니라, 많은 시간과 노력이 필요한 목표로 제시된다.

META의 출처 메모는 원본 영상 링크을 확인하지 못했고 화자 이름과 SNS를 기준으로 출처를 추정했다고 밝힌다. 따라서 Grok Bot은 확정 원작자가 아니라 META에 보존된 후보 이름이다.

Lauren Tan, X에서는 Potato로 알려진 개발자는
한 달에 2,500개의 PR을
프로덕션에 반영했다고 소개했습니다.
PR은 코드 변경을 검토하고
반영하기 위한 요청입니다.
이 숫자는 본인의 공개 실적이고
2,500개의 새 기능을 만들었다는 뜻은 아닙니다.

오늘은 맷 포코와의 대담에서
이 모든 것의 핵심은 검증(verification)입니다.

가장 중요한 기술을 살펴봅시다.
제 생각에 여러분의 도구 상자에 들어 있어야 할 단 하나의 가장 중요한 기술은 검증입니다.

검증이 없다면 안 되기 때문입니다. 이 말이 무슨 뜻인지 모르는 분들을 위해 설명하자면, 에이전트에게 일종의 손과 눈을 줄 수 있다는 개념입니다. 제가 좋아하는 비유이기도 합니다. 에이전트는 코드를 실행하고, 실제 일반 사용자가 하듯이 코드와 상호작용할 수 있습니다. 또한 코드를 디버깅하고, 트레이스(trace)를 수집하고, 스냅샷(snapshot)을 찍는 일도 할 수 있습니다.

재미있게도, 제가 Cursor에 합류했을 때 처음 만든 기술이 바로 이것이었습니다. 덕분에 자신감이 많이 생겼습니다. 다른 기술들을 살펴보거나 만들어 보았을 때는 얻지 못했던 방식으로, 제가 신뢰의 사다리를 조금씩 올라가기 시작하게 해 준 것이 바로 이것이었습니다.

그리고 이런 작업을 스크립트나 CLI(command-line interface)로 인코딩해, 판단을 줄이거나 달리 말하면 원래 불필요하게 사용되었을 판단을 덜어내는 것입니다.

판단이라는 측면에서 보면, 저는 에이전트와 기술을 일종의 연속적인 스펙트럼으로도 생각합니다. 작업 중에는 전적으로 판단에 기반하는 부분이 있잖아요. 생각이 필요하고, 여러 맥락을 조합해야 하며, 사고해야 하는 부분 말입니다. 그리고 더 결정론적인 부분도 있습니다.

예를 들어 어떤 코드를 한 패턴에서 다른 패턴으로 리팩터링하고 싶다고 해 보죠. 그런 작업은 매우 기계적입니다. 에이전트가 매번 그것에 대해 생각하고 새로운 방식으로 만들어 낼 필요는 없습니다. 이것이 바로 CLI에 대한 영감이었습니다. 제가 만든 다른 많은 기술에서도 이런 방식을 보게 될 겁니다.

저는 결정론적인 부분을 추출해 코드로 만들고, 실제로 판단이 필요한 부분만 에이전트에게 남겨 두려고 합니다.

이렇게 실행하고 결과를 관찰할 수 있으면 수정과 검증을 이어갈 수 있습니다.
성능 문제라면 먼저 측정하고 가설을 세워 코드를 바꾼 뒤 다시 측정하는 거죠.
하지만 검증 도구만으로 모든 문제가 해결되진 않습니다.
에이전트가 읽고 따라하는 기존 코드도 중요합니다.

저희 Electron 앱에는 내부용 Next.js가 있습니다. 하지만 정말, 정말 제한적인 린트 규칙이 많이 적용되어 있습니다. 그리고 코드베이스가 어떤 작업을 수행하는 방법이 사실상 하나뿐인 방식으로 설계되어 있습니다.

그래서 저희는 관례적인 패턴(conventional patterns)을 많이 활용합니다. 모든 기능은 특정 디렉터리에 들어갑니다. 정확히는 모든 기능이 각자의 디렉터리를 가집니다. 예를 들어 레지스트리(registry)를 통해 기능을 찾아내고 코드베이스를 탐색하는 기능 같은 것도 있습니다.

하지만 이러한 관례적인 패턴과 린트 규칙 덕분에 실제로 나쁜 코드를 작성하기가 매우 어려운 환경이 만들어집니다. 그리고 이는 여러분의 정신적 여유뿐 아니라 에이전트의 정신적 여유도 확보해 줍니다. 에이전트는 더 이상 그런 부분을 고민할 필요가 없습니다. 그저 이렇게 생각하면 됩니다. “아, 방법이 하나뿐이구나. 새 기능을 추가하려면 새 기능 디렉터리에 넣으면 돼. 모든 코드는 거기에 들어가고, 거대한 파일(god file)에 덧붙이지 않을 거야.”

그것이 바로 그런 기능 디렉터리를 만든 영감이었습니다. Grok Bot의 최초 버전 몇 개는 약 8개의 거대한 파일로 구성되어 있었고, 각 파일은 적어도 1만 줄 이상이었습니다. 그래서 저는 그것을 더 작은 조각들로 나눠야 했습니다.

Pstack은 내부 루프(inner loop)와 외부 루프(outer loop)에 있는 코드입니다.

내부 루프와 외부 루프를 연결하는 두 링크를 보여드리겠습니다. Grok Bot의 도구들이 정말 좋은 이유는 외부 루프도 자동화할 수 있도록 도와주기 때문이라고 생각합니다.

그리고 이 두 루프를 연결하면 매우 강력해집니다. 이제 갑자기 에이전트가 스스로 컨텍스트를 얻을 수 있게 되기 때문입니다.

예를 들어 간단한 사례로, Slack MCP가 있거나 특정 Slack 채널에 대한 구독 기능을 직접 구축한 하네스(harness)가 있다고 해 보겠습니다. 그러면 이제 에이전트에게 이렇게 말할 수 있습니다. “좋아, Slack 채널을 구독해. 무언가에 대한 버그 리포트가 올라올 때마다 가서 그 문제를 분류하고, 우리가 이미 시간을 들여 구축한 검증 스킬(verification skills)과 그 밖의 다른 스킬들을 사용해서 문제를 재현해 봐. 우리가…

저는 이 에이전트들이 실제로 버그를 이해하고, 그 버그가 여전히 main에 존재하는지, 아니면 사용자의 설정이나 데이터에 관한 문제였는지, 혹은 의존성을 설치하지 않았던 것인지 등을 확인할 수 있다고 상당히 신뢰합니다. 기본적으로 저는 이 두 루프를 만들고 서로 연결하는 것이 요즘 업무에서 정말 중요한 부분이라고 생각합니다. 특히 자기 자신을 어떻게 확장할지 고민하고 있다면 더욱 그렇습니다.

여러 제보를 함께 보는 조정자 역할도 등장합니다.
비슷한 제보마다 에이전트를 하나씩 붙이면 같은 문제를 중복해서 고칠 수 있죠.
로렌은 좋지 않은 코드 패턴을 발견하더라도 곧바로 수정하지 않고 문서에 모아두게 하는 사례를 설명합니다.

같은 방식으로 프로세스를 샘플링하고 생각해 보면—아마 이 부분에서 공장 비유가 조금 더 적절해지는 것 같습니다—공장의 품질 감독자라면 모든 제품을 하나하나 살펴볼 수는 없습니다. 샘플링을 하죠. 매일 들어가 풀 리퀘스트(pull request)의 품질을 확인하고, 에이전트가 작성하는 코드를 살펴보며 매우 엄격하게 검토합니다. 에이전트가 만들어 내는 모든 비효율과 나쁜 패턴을 생각해 보면서, 환경의 방향을 어떻게 바로잡을지 고민하는 겁니다.

그렇게 충분히 반복하다 보면, 다시 말해 코드와 환경이 매우 제한되어 있고 에이전트를 아주 잘 안내해서 여러분이 그냥 손을 떼도 되는 지점에 도달하게 됩니다. 그게 꿈이죠. 하지만 이 단계에 도달하는 건 매우 어렵다고 분명히 말씀드리고 싶습니다. pstack을 사용하기만 하면 쉽게 할 수 있는 일인 것처럼 말하고 싶지는 않습니다.

코드를 깊이 고민하고, 에이전트가 어디에서 실패하는지 살펴보고, 에이전트가 기본적으로 올바른 일을 하도록 안전장치(guardrails)와 제약 조건을 설정하는 방법을 매우 신중하고 의도적으로 생각하는 데는 많은 시간과 노력이 듭니다.

감사합니다.
