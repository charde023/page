한 줄 요약

하네스 엔지니어링은 AI 모델 위에 올리는 규칙·스킬·MCP·훅·서브에이전트 레이어를 설계하고, 매 실수를 시스템 개선 기회로 전환하는 마인드셋이다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
AI Layer (하네스의 핵심) 개발자가 직접 설계할 수 있는 유일한 레이어 글로벌 룰·스킬·MCP·훅으로 구성
하네스 vs 컨텍스트 엔지니어링 혼용되는 개념의 차이를 알아야 올바른 적용 가능 제어(Control) 레이어가 진짜 차별점
스킬 이슈 리프레이밍 실수 발생 시 모델 탓이 아닌 하네스 개선으로 전환 모든 실수 = 하네스 개선 기회
시스템 에볼루션 하네스를 계속 진화시켜 에이전트 성능을 복리로 향상 훅·스킬·룰 업데이트로 반복 오류 제거
Ralph 루프 대형 PRD를 여러 코딩 에이전트 세션에 자동 분배·실행 수동 babysit 없이 장기 작업 자동화
멀티 에이전트 코드 리뷰 병렬 리뷰로 보안·정확성·간결성 동시 체크 각 에이전트에 단일 집중 임무 부여
훅(Hooks) 활용 에이전트 실행 전후에 결정론적 검증 삽입 pre-tool-use 훅으로 보안 강제, stop 훅으로 검증 강제

내가 모를 만한 것 / 처음 보는 것

  • 하네스(Harness): 에이전트의 LLM을 감싸는 모든 레이어의 총칭. Claude Code·Codex 자체가 이미 회사가 엔지니어링한 하네스.
  • AI Layer: 사용자가 직접 정의하는 최상위 래퍼. 글로벌 룰, 스킬, MCP 서버, 훅(hooks), LSP, 서브에이전트 포함.
  • Ralph 루프 (Ralph Loop): Jeffrey Huntley가 만든 오픈소스 패턴. 대형 스펙을 여러 코딩 에이전트 세션으로 자동 분할 실행. done.txt 존재 여부로 루프 종료 판정.
  • Archon: Cole의 오픈소스 하네스 빌더. Ralph 루프보다 커스텀 가능한 에이전틱 하네스 구축 도구.
  • pre-tool-use 훅: 에이전트가 파일 쓰기·명령 실행 전에 트리거되는 코드. .env 읽기 차단, 디렉토리 삭제 방지 등 보안 적용 지점.
  • stop 훅: 에이전트가 구현 완료 선언 시 단위 테스트·린팅·타입 체크를 결정론적으로 실행해 통과 여부 강제 확인.
  • Google AgentSpace (AgencyAlign): Google Cloud의 에이전트 개발 CLI 스킬 모음. Claude Code·Codex에 임포트해 Google Agent SDK 기반 에이전트를 원커맨드 프로덕션 배포 가능. (광고 섹션)
  • LSP (Language Server Protocol): AI Layer 구성 요소 중 하나로 언급. IDE 언어 서버를 에이전트 컨텍스트에 활용하는 개념.
  • plan → implement → validate 세션 분리: 같은 작업을 3개의 별도 코딩 에이전트 세션으로 나눠 토큰 효율·집중도 향상.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Claude Code·Codex 같은 툴 자체가 이미 회사가 엔지니어링한 1차 하네스다 — 도구 선택 자체가 하네스 선택이다.
  2. LLM 단독으로는 파일시스템 접근도, 명령 실행도 불가 — 코딩 에이전트의 기본 기능은 전부 이 1차 하네스가 제공한다.
  3. 하네스 vs 컨텍스트 엔지니어링 차이: 컨텍스트 주입·도구·영속성·관찰성은 사실 컨텍스트 엔지니어링이고, 진짜 새로운 것은 제어(Control) — 즉 Ralph 루프·오케스트레이션·서브에이전트다.
  4. 에이전트 실수를 보면 "Claude가 컨벤션을 몰랐다" → CLAUDE.md에 추가, "파괴적 명령을 실행했다" → 훅으로 차단. 실수의 원인은 거의 항상 읽을 수 있다(legible).
  5. 단일 세션에 대형 PRD를 통째로 넣으면 AI Layer가 아무리 좋아도 LLM이 압도되어 실패한다 — 분할이 핵심.
  6. Ralph 루프는 Python 또는 Bash 스크립트로 구현 가능. 루프 탈출 조건은 done.txt 파일 존재 + 에이전트의 완료 확신 동시 충족.
  7. Ralph 루프 내부 작동: 대형 PRD 입력 → 고정 플랜 생성 → 이터레이션별 Claude Code 세션 실행 → 로그 누적 → 8개 스펙 항목 모두 완료 시 루프 종료.
  8. 스킬은 플랜·구현·검증을 별도 파일로 분리하는 것을 강력 권장 — 세션 간 핸드오프 아티팩트(마크다운)로 연결.
  9. 파일 편집마다 린트를 자동 실행하는 훅이 코드베이스 청결 유지 + 미래 에이전트 신뢰성 향상에도 기여.
  10. Archon은 Cole의 오픈소스 하네스 빌더로, Ralph 루프를 더 커스텀하게 만들 수 있는 진입점으로 추천.

# 섹션 요지
1 하네스 엔지니어링 정의 모델 주변 래퍼 전체를 설계하는 것
2 두 레이어 구조 도구 자체(1차 하네스) + AI Layer(사용자 정의)
3 컨텍스트 엔지니어링과의 차이 제어(Control)·오케스트레이션이 진짜 차별점
4 마인드셋 리프레임 실수 = 모델 탓 X, 하네스 개선 기회 O
5 AI Layer 구성 요소 실전 글로벌 룰, 스킬(플랜·구현·검증), 훅(보안·stop·린트)
6 멀티 세션 오케스트레이션 Ralph 루프로 대형 작업 자동 분할 실행
7 Archon 소개 오픈소스 커스텀 하네스 빌더

1. 하네스 엔지니어링이란 무엇인가

2025년 컨텍스트 엔지니어링이 키워드였다면, 2026년은 하네스 엔지니어링이다. 아직 개념을 제대로 이해하지 못한 채 유행어처럼 쓰이고 있어 정확한 정의가 필요하다.

에이전트 = LLM(추론 엔진) + 그것을 감싸는 래퍼(하네스). 하네스 엔지니어링은 이 래퍼를 어떻게 설계하느냐를 다룬다. 영상은 AI 코딩 어시스턴트 사례에 집중하지만 원리는 모든 에이전트에 적용된다.

두 가지 수준: - 단일 코딩 에이전트 세션 내부 설계 - 여러 코딩 에이전트 세션을 연결하는 상위 워크플로우 (더 중요)

2. 두 레이어 구조

[사용자 AI Layer]
  └─ 글로벌 룰 / 스킬 / MCP 서버 / 훅 / Ralph 루프
[코딩 에이전트 자체 (1차 하네스)]
  └─ Claude Code / Codex / Py 등 — 파일시스템·명령 실행 능력 제공
[LLM 코어]
  └─ Claude / GPT 등 — 추론만 담당

LLM 단독으로는 파일 접근·명령 실행이 불가능하다. Claude Code·Codex가 제공하는 모든 기능은 이미 1차 하네스가 제공한 것이다. 사용자가 실제로 설계할 수 있는 것은 AI Layer뿐이다.

3. 컨텍스트 엔지니어링과의 차이

항목 컨텍스트 엔지니어링 하네스 엔지니어링의 추가분
컨텍스트 주입 O O (포함)
도구·MCP O O (포함)
영속성·관찰성 O O (포함)
제어 (Control) X O — 진짜 차별점

제어란 Ralph 루프, 서브에이전트 오케스트레이션처럼 여러 에이전트 세션을 자동으로 연결·관리하는 것이다.

또한 하네스 엔지니어링은 스킬만이 아닌 마인드셋이기도 하다 — 아래 참고.

4. 마인드셋 리프레임: 실수 = 하네스 개선 기회

흔한 패턴: "에이전트가 멍청한 짓을 했다 → 모델 탓 → 다음 버전 기다림."

하네스 엔지니어링 마인드셋은 이를 거부한다.

  • 에이전트가 컨벤션을 몰랐다 → CLAUDE.md에 규칙 추가
  • 에이전트가 파괴적 명령을 실행했다 → pre-tool-use 훅으로 차단 추가

모든 실수는 하네스를 개선할 기회다. 이를 통해 다음 세션에서 같은 문제가 반복될 확률을 낮추고, 에이전트 성능이 시간이 지날수록 향상되는 시스템 에볼루션이 일어난다.

5. AI Layer 구성 요소 실전

Cole의 데모 레포를 기준으로:

글로벌 룰 (Rules) - 코딩 에이전트가 따를 제약·컨벤션을 마크다운으로 정의 - Confluence 문서 등 on-demand 컨텍스트도 포함

스킬 (Skills) - 플랜·구현·검증을 별도 스킬 파일로 분리 — 세션 간 토큰 효율·집중도 확보 - 각 스킬은 마크다운 아티팩트를 출력 → 다음 세션의 입력으로 핸드오프

훅 (Hooks) — 가장 저평가된 요소

훅 종류 역할
pre-tool-use 파일 쓰기·명령 실행 전 보안 검사 (.env 읽기 차단, 디렉토리 삭제 방지)
stop 구현 완료 선언 시 단위 테스트·린트·타입 체크 강제 실행
post-edit 파일 편집 후 자동 린트 실행

LSP: 언어 서버 프로토콜을 에이전트 컨텍스트에 활용.

6. 멀티 세션 오케스트레이션: Ralph 루프

단일 세션에 대형 PRD를 넣으면 AI Layer가 아무리 좋아도 LLM이 압도된다. 해결책은 각 에이전트에 집중된 단일 임무를 부여하고 세션을 연결하는 것이다.

Ralph 루프 흐름:

사용자 PRD 입력
    ↓
고정 플랜 생성 (이터레이션 1, 2, 3 ... 목록)
    ↓
Claude Code 세션 실행 (이터레이션 1)
    ↓
로그 누적
    ↓
... 반복 ...
    ↓
done.txt + 에이전트 완료 확신 → while 루프 종료

병렬 코드 리뷰 에이전트 예시: - 보안 전담 에이전트 - 구현 정확성 전담 에이전트 - 코드 간결성 전담 에이전트

모두 통과 시 PR 생성. 미통과 시 구현 반복.

Jeffrey Huntley가 Ralph 루프의 최초 구현자로, 여러 Claude Code·Codex 인스턴스를 자동으로 연결하는 선구적 패턴이다.

7. 다음 단계: Archon

Cole의 오픈소스 하네스 빌더. Ralph 루프보다 더 커스텀 가능한 하네스를 본인의 소프트웨어 개발 라이프사이클에 맞게 구축하는 가장 쉬운 진입점.

교정 전사 (한국어)

전체 전사 펼치기

지금 AI 분야에서 점점 더 많이 언급되는 용어가 바로 하네스 엔지니어링(harness engineering)이다. 지난해 컨텍스트 엔지니어링이 그랬듯, 올해의 가장 큰 화두다. 정말 중요한 개념이지만, 컨텍스트 엔지니어링처럼 사람들이 의미도 제대로 모른 채 유행어처럼 던지기 시작했다. 그렇다면 이 스킬 — 혹은 마인드셋 — 이 배울 가치가 있는가? 답은 '그렇다'이다. 오늘은 하네스 엔지니어링이 무엇인지, 알아야 할 핵심 레이어들을 15분 안에 간결하게 정리해 드리겠다. 예시와 데모도 준비했다.

하네스 엔지니어링은 모델 주변을 감싸는 래퍼를 구축하는 것이다. 에이전트는 GPT·Claude 같은 기반 LLM과 그것에 컨텍스트를 제공하고 프로세스를 정의하는 래퍼의 조합이다. 이 영상에서는 주로 AI 코딩 어시스턴트에 집중하지만, 하네스 엔지니어링 개념은 어떤 에이전트에도 확장 적용된다.

하네스 엔지니어링에는 두 가지 차원이 있다. 첫 번째는 단일 AI 코딩 어시스턴트 세션 내부이고, 두 번째는 — 내가 지금 더 집중하는 진짜 진화 — 여러 코딩 에이전트 세션을 큰 워크플로우로 연결해 더 큰 작업을 처리하는 것이다.

먼저 기초부터 시작하자. 단일 세션 내 하네스 엔지니어링의 많은 아이디어는 컨텍스트 엔지니어링과 매우 유사하다. 이것은 컨텍스트 엔지니어링의 직접적인 진화다 — 코딩 에이전트에게 올바른 컨텍스트 생태계를 어떻게 제공할 것인가? 다만 중요한 차이점이 있다.

다이어그램을 보면: 맨 아래 기반 LLM(에이전트의 추론 엔진)이 있고, 그 위의 첫 번째 래퍼는 사용자가 만드는 게 아니다 — 선택하는 툴, 즉 코딩 에이전트 자체다. Claude Code, Codex, Py 등 수많은 코딩 에이전트가 모두 회사가 모델 주변에 엔지니어링한 하네스다. 여기서 뭔가를 직접 정의하는 건 아니지만 올바른 엔진을 선택하는 것이다. Claude Code가 최고의 하네스라는 사람도, Codex가 더 낫다는 사람도 있다 — 논쟁이 많다.

하지만 코딩 에이전트 선택보다 더 중요한 것이 AI Layer다. 이것이 코딩 에이전트 세션을 감싸는 궁극의 래퍼이며, 사용자가 직접 구축할 수 있는 부분이다. AI Layer는 코딩 에이전트의 모든 컨텍스트와 프로세스를 정의한다 — 글로벌 룰, 스킬, MCP 서버.

하네스 엔지니어링을 이해하는 데 도움이 되는 좋은 아티클 두 편을 설명에 링크해뒀다(addyosmani.com, martinfowler.com). 첫 번째 아티클에 이런 비유가 있다: 왼쪽에는 Claude나 GPT 같은 모델 단독의 능력이 있다 — 솔직히 별로 없다. 우리는 Claude Code나 Codex 같은 AI 코딩 어시스턴트가 기본으로 제공하는 모든 능력을 당연하게 여긴다. LLM 단독으로는 파일시스템 접근도, 명령 실행도 불가능하다. 이것들은 전부 우리가 다운받아 쓰는 툴의 1차 하네스 레이어가 제공한다. 그리고 더 상위 레이어로 갈수록 우리가 정의하는 AI Layer — MCP 서버, 스킬, 룰, Ralph 루프 같은 것들이 등장한다.

이제 방 안의 코끼리를 다뤄보자. "Cole, 이게 그냥 컨텍스트 엔지니어링 아닌가요? 2025년에 다 다뤘잖아요?" 어느 정도는 맞다. 하네스 엔지니어링이 버즈워드가 되고 있는 이유도 여기 있다 — 대부분의 사람들이 컨텍스트 엔지니어링과의 진짜 차이를 이해하지 못한다.

두 가지 중요한 구분이 있다. 첫째, 모델 주변의 하네스 대부분은 여전히 컨텍스트 엔지니어링이다 — 컨텍스트 주입, 도구·MCP를 통한 액션, 영속성, 관찰성. 진짜 다른 것은 제어(Control)다 — Ralph 루프, 여러 코딩 에이전트 세션과 서브에이전트 오케스트레이션. 이것이 컨텍스트 엔지니어링으로부터의 진짜 진화라고 생각한다.

두 번째 중요한 구분은 스킬 이슈 리프레임(skill issue reframe)이다. 서두에 언급했듯 하네스 엔지니어링은 스킬만이 아닌 일종의 마인드셋이기도 하다. 아티클 저자가 말하는 패턴이 있다: "에이전트가 멍청한 짓을 했다. 엔지니어가 모델을 탓했다. 그리고 다음 버전을 기다렸다" — Claude가 실수하면 Opus 5를 기다리고, GPT가 실수하면 GPT-6를 기다리는 것. 나도 이런 생각에 빠지고 싶을 때가 있고, 아마 여러분도 마찬가지일 거다.

하지만 하네스 엔지니어링 마인드셋은 이 기본값을 거부한다. 나는 이것을 시스템 에볼루션(system evolution)이라 부른다 — 최근 내가 많이 집중하는 것과 정확히 맞닿아 있다. 실패는 대개 읽을 수 있다(legible). 에이전트가 컨벤션을 몰랐다 → CLAUDE.md에 추가. 에이전트가 파괴적 명령을 실행했다 → 훅으로 차단 추가. 모든 실수는 하네스를 개선할 기회가 된다 — 훅으로 보안 강화, 스킬 업데이트로 프로세스 개선. 그러면 다음 코딩 에이전트 세션에서 그 문제가 재발할 확률이 낮아진다. 이것이 바로 우리가 통제권을 갖고, 선택한 코딩 에이전트 위에서 본인의 AI Layer를 통해 에이전트 성능을 향상시키는 것이다.

(광고 섹션 — Google Cloud AgencyAlign: 에이전트 CLI 스킬 모음으로 Google Agent SDK 기반 에이전트를 쉽게 구축·배포·모니터링 가능. 오픈소스·무료.)

이제 컴패니언 레포(coleam00/harness-engineering-demo)를 보자. AI Layer가 실제로 어떻게 생겼는지 구체적으로 보여주는 레포다. 내가 모든 코드베이스에 가져와 진화시키는 AI Layer의 표현이다. 마지막 진화 — 여러 코딩 에이전트 세션을 오케스트레이션하는 것 — 를 다루기 전에 빠르게 커버하겠다.

AI Layer의 기반은 룰(Rules)이다. 코딩 에이전트가 따를 제약과 컨벤션 — 패턴, 글로벌 룰, 마크다운·Confluence 등 온디맨드 컨텍스트.

스킬(Skills)은 코딩 에이전트를 위한 워크플로우다 — 플랜·구현·검증 방법. 이것들을 별도 스킬로 분리하는 것을 강력 권장한다. 플랜·구현·검증을 각각 별도의 코딩 에이전트 세션에서 처리해 토큰 효율과 집중도를 유지. 각 스킬은 다음 세션으로의 핸드오프를 위한 아티팩트를 출력한다. 아직은 수동 방식 — 플랜 스킬로 플랜 마크다운을 만들고, 그것을 구현 스킬 세션에 넘기는 식.

훅(Hooks)은 정말 저평가되어 있다. - pre-tool-use 훅: 에이전트가 파일 쓰기·명령 실행 전 트리거. .env 파일 읽기 차단(LLM 컨텍스트에 들어가는 걸 원하지 않음), 파괴적 디렉토리 삭제 방지. - stop 훅: 에이전트가 구현 완료를 선언할 때 단위 테스트·린팅·타입 체크를 결정론적으로 실행 — 통과하지 못하면 통과할 때까지 반복 강제. - post-edit 훅: 파일 편집 후 빠른 린트 실행 — 코드베이스 청결 유지, 미래 코딩 에이전트 신뢰성 향상.

AI Layer 사용 기본 방식: plan 스킬로 피처 입력 → 플랜 반복·수정 → 마크다운 산출 → implement 스킬 세션에 핸드오프 → 검증 전략도 마크다운에 포함. 이것이 에이전틱 엔지니어링의 기본 접근이다.

이제 하네스 엔지니어링의 정점 진화: 코딩 에이전트 세션 오케스트레이션.

핵심 아이디어: 거대한 태스크나 PRD를 단일 코딩 에이전트 세션에 그냥 넘기면 안 된다. 토큰 비효율이고, AI Layer가 아무리 좋아도 LLM이 압도된다. 각 에이전트에 매우 집중된 단일 태스크를 부여해야 한다.

예시 하네스: - 사용자 요구사항 → 탐색 에이전트 → 플랜 에이전트 → 구현 에이전트 → 병렬 코드 리뷰 에이전트 3개(보안·정확성·간결성) → 모두 통과 시 PR 생성, 미통과 시 구현 반복.

이것을 수동으로도 할 수 있다 — Claude Code 하나에서 플랜 만들고, 다른 Claude Code에서 구현. 하지만 하네스 엔지니어링의 진짜 힘은 이것을 자동화하는 것이다 — 세션 간 핸드오프 문서·PR 생성 등을 모두 자동으로.

Ralph 루프가 바로 그것이다. Jeffrey Huntley가 만들었다. 여러 Claude Code·Codex 인스턴스를 자동으로 연결하는 초기 선구적 예시 중 하나다. 기술적으로 복잡하지 않다: Python 또는 Bash 스크립트. 대형 PRD를 입력하면 개별 태스크로 분할하고 코딩 에이전트 세션을 차례로 실행한다. 고정 플랜을 생성하고(이터레이션 1, 2, 3 ...), 각 Claude Code 세션이 실행되며 로그를 쌓는다. done.txt 파일이 존재하고 에이전트가 원래 프롬프트의 8개 스펙 항목을 모두 완료했다는 확신이 있을 때만 while 루프에서 탈출한다.

이것이 바로 에이전틱 엔지니어링의 미래다. 모델과 기반 도구가 강력해질수록, 더 큰 범위의 작업을 처리하는 하네스를 구축하는 것이 핵심이다.

그리고 내 오픈소스 하네스 빌더인 Archon도 있다. Ralph 루프를 더 커스텀하게 — 본인의 정확한 프로세스와 소프트웨어 개발 라이프사이클에 맞게 — 만들 수 있는 가장 쉬운 에이전틱 엔지니어링 시작점이다.

이 영상이 도움이 됐길 바란다. 하네스 엔지니어링이 무엇인지, 무엇이 과장이고 무엇이 진짜 알 가치가 있는지 이해하는 데. 유용하셨다면 좋아요와 구독 부탁드린다.
