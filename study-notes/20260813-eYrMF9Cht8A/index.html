개념 왜 중요한가 한 줄
경험 격차(experience gap) 모델의 지능(IQ)은 올라가지만 업무 숙련도는 누적되지 않는 문제 에이전트가 매번 초보처럼 보이는 이유는 “경험”을 저장하고 반영하지 않기 때문
지속 학습(continual learning) 에이전트가 실제 사용될수록 더 빨라지고 싸고 정확해지는 구조 사용 로그, 수정, 재시도, 실패를 학습 신호로 전환하는 접근
추적성(traceability) 무엇을 했고 어디서 실패했는지 알아야 개선 가능 메인 액션뿐 아니라 도구 호출(tool call), 하위 에이전트(sub-agent), 되돌리기까지 기록해야 함
실제 트래픽 기반 평가(evals from traffic) 실험실 평가와 실제 제품 사용이 다르면 개선 방향이 틀어짐 사용자가 실제로 요청한 업무를 평가 세트로 삼아야 함
하네스(harness) 모델 주변의 도구, 컨텍스트, 실행 환경 전체 모델만 고치는 것이 아니라 하네스와 컨텍스트도 함께 최적화해야 함
오픈 웨이트(open weights) 자기 회사의 지능을 직접 소유하고 개선하려면 필요 폐쇄형 API만 쓰면 모델 자체를 지속적으로 개선하기 어렵다
모델 라우터(model router) 업무 난이도와 성격에 따라 적절한 모델을 고르는 장치 모든 요청을 최고가 모델에 보내지 않고 비용·성능을 최적화할 수 있음

내가 모를 만한 것 / 처음 보는 것

  • 지속 학습(continual learning) — 모델이나 에이전트 시스템이 실제 사용 경험을 바탕으로 계속 개선되는 방식.
  • 경험 격차(experience gap) — 모델은 똑똑하지만 특정 회사, 업무, 고객 환경에서 쌓은 숙련도가 없는 문제.
  • 추적(trace) / 추적성(traceability) — 에이전트가 어떤 생각, 도구 호출, 하위 에이전트, 재시도 과정을 거쳤는지 남기는 기록.
  • 하네스(harness) — 모델을 둘러싼 실행 구조. 도구(tool), 프롬프트, 컨텍스트, 권한, UI 연결, 평가 환경 등을 포함.
  • 모델 명세(model spec) — 우리 에이전트가 어떤 행동을 해야 하는지 정의한 목표·규칙·보상 기준.
  • 평가(evals) — 에이전트가 잘하고 있는지 측정하는 테스트 세트와 채점 방식.
  • 롤아웃 가능(task roll-outable) — 과거 사용자의 작업을 다시 재현해 새 모델이나 새 하네스에서 비교 평가할 수 있는 상태.
  • 오픈 웨이트(open weights) — 모델 가중치(weights)가 공개되어 직접 실행·튜닝할 수 있는 모델.
  • SDPO — 긴 에이전트 실행 경로(trace)를 활용해 모델을 개선하는 강화학습 계열 알고리즘으로 언급됨.
  • 차등 프라이버시(differential privacy) — 고객 데이터를 직접 학습하지 않고 통계적 분포나 보호된 신호만 활용하려는 개인정보 보호 기법.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 모델은 매주 이전 모델을 뛰어넘는 것처럼 보이지만, 개선 축은 주로 지능(IQ)이라고 봄.
  2. 에이전트는 “테렌스 타오(Terence Tao)가 회계법인 첫날 출근한 상태”와 비슷하다고 비유함. 똑똑하지만 업무 경험은 없다는 뜻.
  3. 지금 생성되는 수많은 에이전트 토큰(tokens)은 실제 업무 결과인데 대부분 버려진다고 지적함.
  4. 단순한 좋아요/싫어요(thumbs up/down)는 신호가 너무 시끄럽다고 봄.
  5. 진짜 중요한 피드백은 수정(edit), 되돌리기(undo), 재시도(retry), 나중에 깨달은 오류 같은 교정 행동임.
  6. 평가(evals)는 제품 사용 환경과 최대한 같아야 하며, 이상적으로는 실제 제품과 평가 환경이 동일해야 한다고 말함.
  7. 도구 응답(tool response)이 “완료됨(Done)”만 반환하면 에이전트 입장에서는 무엇을 읽고 썼는지 알 수 없어 학습 신호가 없다고 지적함.
  8. 하네스는 과거처럼 에이전트를 제한하는 구조가 아니라, 에이전트가 도구 원시 기능(primitives)을 조율(orchestrate)하도록 설계해야 한다고 주장함.
  9. 오픈 웨이트(open weights)로 전환하는 것은 단순 모델 교체가 아니라 보안, 안전, 권한 관리 등 50가지 고려사항이 따른다고 말함.
  10. Trajectory 제품 데모에서는 벤치마크 가져오기, 모델 학습, 평가, 비교, 배포까지 실제 사용자가 투입하는 작업 시간이 약 15분이라고 언급함.
  11. 고객 데이터는 직접 학습하지 않고, 고객 데이터의 분포(distribution)를 샘플링한 뒤 합성 데이터(synthetic data)를 만들어 비교하는 방법을 언급함.
  12. 피드백에는 전역적으로 반영할 것, 조직 단위로 반영할 것, 사용자 개인 컨텍스트에만 둘 것이 있다는 계층 구조가 있다고 설명함.

# 섹션 요지
1 문제의식 AI는 똑똑해졌지만 경험이 누적되지 않아 매번 초보처럼 행동함
2 지속 학습의 목표 실제 사용 흔적을 학습 신호로 바꿔 에이전트가 쓸수록 개선되게 함
3 추적성 전체 작업 트리, 도구 호출, 하위 에이전트, 교정 행동을 기록해야 함
4 평가 실제 사용자 트래픽에서 평가 데이터를 만들고 실제 하네스로 채점해야 함
5 하네스 에이전트를 막는 구조보다 도구를 조율하게 하는 구조가 필요함
6 모델 오픈 웨이트와 모델 라우터가 자기 지능 소유의 핵심 기반이 됨
7 Q&A 학습 대상은 모델 가중치만이 아니라 하네스, 컨텍스트, 도구 전체 시스템임

1. 문제의식: 모델은 똑똑하지만 경험이 없다

Arjun Karanam은 Trajectory가 지속 학습(continual learning) 플랫폼을 만들고 있다고 소개한다.

그가 보는 현재 AI의 핵심 문제는 모델이 점점 똑똑해지고 있지만, 특정 업무에 대한 경험이 쌓이지 않는다는 점이다. 매주 더 좋은 모델이 나오고, 모델의 지능(IQ)은 분명 올라간다. 하지만 실제로 대화하거나 업무를 맡겨 보면 마치 “입사 첫날”인 사람처럼 행동한다.

그는 이를 경험 격차(experience gap)라고 부른다.

예를 들어 천재 수학자 테렌스 타오가 주머니 속에 있다고 해도, 회계법인 첫날에는 최고의 회계사가 아닐 수 있다. 며칠이나 몇 년 동안 실제 업무를 경험하면 훨씬 나아질 것이다. AI 에이전트도 마찬가지다. 지능만으로는 부족하고, 실제 사용 경험이 누적되어야 한다.

2. 지속 학습: 버려지는 사용 경험을 신호로 바꾸기

현재 수많은 에이전트가 실제 작업을 수행하며 엄청난 양의 토큰(tokens)을 생성한다. 사용자가 그것을 보고 행동하기도 하고, 때로는 보지 않고 지나가기도 한다. 하지만 대부분의 상호작용은 그냥 버려진다.

Trajectory의 관점은 이렇다.

에이전트가 수행한 실제 업무와 그에 대한 사람의 반응은 학습 신호다.

사람도 일을 하며 피드백을 받고, 실수하고, 수정하면서 나아진다. 에이전트도 마찬가지로 사용될수록 더 나아지는 구조가 필요하다.

지속 학습이 잘 작동하면 두 가지 효과가 있다.

첫째, 더 빠르고 더 좋고 더 저렴한 모델을 만들 수 있다.
둘째, 더 중요하게는 사용할수록 복리처럼 좋아지는 시스템을 만들 수 있다.

3. 출발점은 추적성(traceability)

지속 학습의 첫 단계는 추적성(traceability)이다.

에이전트가 무엇을 했는지, 어떤 도구를 호출했는지, 어떤 하위 에이전트를 사용했는지, 어디서 실패했고 사용자가 어떻게 고쳤는지를 기록해야 한다. 이 경험이 있어야 나중에 모델이나 하네스를 개선할 수 있다.

많은 회사는 메인 액션만 기록하고, 도구 호출(tool call)이나 하위 에이전트(sub-agent)의 행동은 버린다. 하지만 실제 학습에는 전체 작업 트리(tree)가 중요하다.

특히 중요한 것은 단순 평가 버튼이 아니다. 좋아요/싫어요(thumbs up/down)는 이론적으로 좋아 보이지만 실제로는 잡음이 많다.

코딩 에이전트를 예로 들면, 사용자는 처음에는 에이전트가 만든 코드를 그냥 수락한다. 그런데 다섯 커밋 뒤에야 “이게 다 망가뜨렸구나”라고 깨닫고 되돌린다. 따라서 진짜 중요한 신호는 다음과 같다.

  • 사용자의 수정(edit)
  • 되돌리기(undo)
  • 재시도(retry)
  • 실패 후 다른 방식으로 해결한 행동
  • 나중에 오류를 발견하고 교정한 행동

이런 교정 행동을 제품 안에서 자연스럽게 유도하고 기록해야 한다.

4. 모델 명세(model spec)와 학습 대상

Trajectory는 단순히 로그를 모으는 데서 끝나지 않고, 상호작용을 바탕으로 모델 명세(model spec)를 만들려 한다.

모델 명세란 “우리 에이전트가 무엇을 해야 하는가”를 정의한 것이다. 사용자의 상호작용에서 보상(reward)을 추출하고, 실행 흔적(trace)에서 에이전트가 배워야 할 정확한 행동 기준을 뽑아내는 연구를 하고 있다고 설명한다.

그다음 개선 대상은 크게 두 가지다.

첫째는 모델(model)이다. 실제 긴 실행 경로(trace)를 활용해 강화학습(RL) 방식으로 모델을 개선한다. SDPO 같은 알고리즘을 언급한다.

둘째는 하네스(harness)다. 하네스는 모델 주변의 실행 환경이다. 도구, 컨텍스트, 프롬프트, 권한, 제품 UI와의 연결 등을 포함한다.

예를 들어 “이 회사는 상장폐지되었다” 같은 사실 정보는 모델 가중치에 학습시키기보다 하네스가 제공하는 컨텍스트에 넣는 편이 낫다. 반대로 특정 도구를 반복적으로 잘못 쓰는 문제는 모델이 배워야 할 수도 있다.

즉, 지속 학습은 모델만 고치는 일이 아니라 모델, 하네스, 컨텍스트 전체 시스템을 어디까지 어떻게 업데이트할지 결정하는 문제다.

5. 평가(evals): 실제 제품 사용과 가까워야 한다

두 번째 소원은 평가(evals)에 관한 것이다.

Arjun은 사용자가 실제로 쓰는 제품 환경과 평가가 이루어지는 환경이 최대한 가까워야 한다고 말한다. 이상적으로는 둘이 같아야 한다.

평가 데이터는 실제 트래픽에서 나와야 한다. 사용자가 지금 어떻게 제품을 쓰는지, 그리고 아직 제품이 잘 못하지만 사용자가 시도하는 경계선의 요청이 무엇인지가 모두 중요하다.

또 하나 중요한 것은 사용자의 과거 작업을 다시 재현할 수 있어야 한다는 점이다. 한 사용자가 어떤 작업을 했다면, 새 모델이나 새 하네스에서 그 작업을 다시 실행해 비교할 수 있어야 한다. 이를 위해서는 인프라가 필요하지만, 에이전트 시대에는 매우 중요한 능력이라고 본다.

마지막으로 평가는 실제 운영 하네스에서 채점해야 한다. 테스트용으로 살짝 바꾼 하네스가 아니라, 실제 프로덕션에서 사람들이 쓰는 하네스를 그대로 평가해야 한다.

6. 하네스(harness): 에이전트를 막지 말고 조율하게 하라

세 번째 소원은 하네스 설계다.

과거의 하네스는 에이전트가 이상한 행동을 하지 못하게 막는 것이 주된 목적이었다. 예전 모델은 출력 형식을 자주 망가뜨리고, 예측 불가능한 행동을 했기 때문에 이런 제한이 필요했다.

하지만 지금은 “에이전트가 해보게 두는(let the agents cook)” 방향으로 가야 한다고 말한다.

하네스는 특정 흐름을 강제하는 구조가 아니라, 제품이 가진 기본 기능(primitives)을 에이전트가 조율(orchestrate)할 수 있도록 제공해야 한다. 예를 들어 검색 도구, 내부 정보, 데이터베이스 접근, 사용자 인터페이스의 기능들이 에이전트에게 도구로 제공되어야 한다.

이상적인 세계에서는 사용자가 UI에서 할 수 있는 모든 일을 에이전트도 도구 호출(tool call)을 통해 할 수 있어야 한다. 그래야 학습과 지속 개선이 쉬워진다.

또한 도구 응답은 충분히 정보가 있어야 한다. 도구가 데이터베이스에 무엇인가를 썼는데 응답이 “완료됨”뿐이면 에이전트는 실제로 무엇이 쓰였는지 알 수 없다. 학습 신호도 생기지 않는다.

따라서 도구는 다음과 같이 응답해야 한다.

  • 무엇을 읽었는지
  • 무엇을 썼는지
  • 어떤 상태가 바뀌었는지
  • 실패했다면 왜 실패했는지
  • 다음 행동에 필요한 정보가 무엇인지

7. 모델: 오픈 웨이트와 라우터

네 번째 소원은 모델에 관한 것이다.

Arjun은 오픈 웨이트(open weights)에 익숙해져야 한다고 말한다. 오픈 웨이트 모델을 운영해야 자기 회사의 모델을 직접 소유하고, 그 위에 지속적으로 개선을 쌓을 수 있다.

다만 단순히 오픈 웨이트 모델로 바꾸면 끝나는 문제가 아니다. 보안, 안전, 접근 권한, 운영 인프라 등 많은 고려사항이 있다. 그럼에도 장기적으로 “자기 지능을 소유”하려면 이 방향이 중요하다고 본다.

또한 모델 라우터(model router)가 중요한 역할을 할 것이라고 말한다. 모든 작업을 같은 모델에 보내는 것이 아니라, 작업의 성격과 난이도에 따라 알맞은 모델로 보내는 방식이다. 이렇게 하면 성능과 비용을 동시에 최적화할 수 있다.

8. Trajectory 제품 방향: 회사가 자기 지능을 소유하게 하기

Trajectory는 기업이 자기 모델과 경험 레이어(experience layer)를 직접 소유하도록 돕는 제품을 만들고 있다.

Arjun은 이 역량이 외부 컨설팅에 맡겨버릴 것이 아니라, 제품의 핵심 역량으로 회사 내부에 쌓여야 한다고 말한다.

데모에서는 벤치마크를 가져오고, 모델을 학습시키고, 평가하고, 기존 모델과 비교하고, 배포하는 흐름을 보여준다. 그는 후처리 학습(post-training)에는 원래 수많은 설정값과 연구자 직관이 필요하지만, Trajectory는 그 과정을 에이전트가 뒤에서 많이 처리하게 하고 사용자는 꼭 필요한 설정만 보게 만들었다고 설명한다.

실제 사용자가 들이는 작업 시간은 모델 학습 대기 시간을 제외하면 약 15분 정도라고 말한다.

9. Q&A: 학습 대상은 모델 가중치만이 아니다

질문자는 지속 학습에서 학습 가능한 대상이 모델 가중치(weights), 하네스(harness), 도구(tools), 애플리케이션 계층(application layer) 중 무엇인지 묻는다.

Arjun은 연구자 6명에게 지속 학습이 무엇인지 물으면 7가지 답이 나올 것이라고 농담한다.

그의 관점은 이렇다.

제품을 움직이는 지능은 하나의 시스템이다. 모델 가중치만이 아니라 하네스, 컨텍스트, 도구, 애플리케이션 계층이 함께 작동한다. 진정한 지속 학습은 이 시스템 전체에서 무엇을 업데이트해야 하는지 최적화하는 것이다.

그는 저장장치 비유를 든다. 사용자는 데이터를 저장할 때 RAM에 넣을지 하드디스크에 넣을지 직접 생각하지 않는다. 시스템이 추상화해서 알아서 결정한다. 마찬가지로 모델에 학습시킬지, 하네스에 넣을지, 컨텍스트로 둘지도 시스템이 판단해야 한다고 본다.

10. Q&A: 고객 데이터를 직접 학습하지 않는 방법

다른 질문자는 고객 데이터로 학습하지 않는 것이 중요하다는 이야기를 언급하며, 지속 학습은 상호작용에서 배워야 하므로 개인정보나 고객별 데이터 계약과 충돌하지 않느냐고 묻는다.

Arjun은 매우 중요한 문제라고 답한다. 그는 이전에 Apple에서도 이 문제를 다뤘다고 말한다.

방법 중 하나는 고객 데이터를 직접 학습하지 않는 것이다. 대신 고객 데이터의 분포(distribution)를 샘플링하고, 그 분포를 바탕으로 합성 데이터(synthetic data)를 만든다. 이후 생성한 데이터가 실제 고객 데이터 분포와 맞는지 비교한다. 이렇게 하면 고객 데이터를 직접 모델에 넣지 않으면서도 유사한 학습 신호를 만들 수 있다.

그는 차등 프라이버시(differential privacy)와 비슷한 방향의 여러 흥미로운 연구가 있으며, 실제 고객과도 이런 문제를 해결하기 위한 작업을 하고 있다고 말한다.

11. Q&A: 에피소드 기억과 피드백 계층

질문자는 에피소드 기억(episodic memory)이 지속 학습에 어떤 역할을 하는지 묻는다. 예를 들어 사용자가 에이전트의 이전 행동을 수정하면, 에이전트 행동을 업데이트해야 하지 않느냐는 질문이다.

Arjun은 피드백에는 종류가 있다고 설명한다.

첫 번째는 “뭔가 잘못됐다”는 신호다. 예를 들어 사용자가 에이전트에게 화를 내거나, 싫어요를 누르거나, 세션을 떠나는 경우다. 이때는 문제가 있었다는 것은 알지만, 정답이 무엇인지는 모른다.

두 번째는 “무엇이 정답인지 알 수 있는” 신호다. 예를 들어 에이전트가 재시도해서 올바른 해결책에 도달했거나, 사용자가 직접 차이를 설명하며 수정한 경우다. 이 경우에는 보상(reward)을 더 확실하게 줄 수 있다.

또 다른 축은 피드백이 누구에게 관련되는가다.

  • 전 세계적으로 맞는 정보
  • 특정 조직에만 맞는 정보
  • 특정 고객에게만 맞는 정보
  • 특정 사용자 개인 취향에만 맞는 정보

예를 들어 특정 도구 호출이 계속 실패한다면 전역적으로 중요한 정보일 수 있다. 모델이 그 도구 사용법을 더 잘 배워야 한다.

반면 어떤 사용자가 “나는 이 하위 에이전트를 절대 쓰고 싶지 않다”고 말한다면, 이것은 모델 전체에 학습시킬 내용이 아니라 그 사용자 컨텍스트에 남길 내용이다.

12. Q&A: 지속 학습이 가장 잘 먹히는 문제

마지막 질문은 어떤 업무에 지속 학습이 특히 중요한지에 관한 것이다. 어떤 작업은 정적으로 학습된 최신 모델과 하네스의 컨텍스트 주입만으로 충분하지 않느냐는 질문이다.

Arjun은 대부분의 작업에 지속 학습이 도움이 되지만, 특히 흥미로운 영역은 프런티어(frontier)에 있는 작업이라고 답한다.

사용자는 제품이 할 수 있다고 기대하는 범위 안에서 요청한다. 때로는 그 경계선에서 어려운 요청을 해보고, 실패하면 “아직 안 되네”라고 생각하며 물러난다.

그는 Cursor를 예로 든다. 2년 전에는 사용자가 지금처럼 복잡하고 이상한 쿼리를 코딩 에이전트에 던질 생각을 하지 못했을 것이다. 하지만 모델이 좋아지면서 사용자는 점점 더 큰 작업을 맡기기 시작했다.

지속 학습의 흥미로운 지점은 여기다. 사용자가 어떤 작업을 시도했지만 모델이 간신히 하거나 실패한다. 그런데 그 실패와 시도에서 학습하면, 이후에는 그 작업이 가능해진다. 이렇게 사용자의 실제 시도와 실패가 제품의 가능 범위를 밀어 올린다.

구체적으로는 두 가지 이점이 있습니다. 당장 더 빠르고, 더 좋고, 더 저렴한 모델을 얻을 수 있습니다. 더 흥미로운 점은 사용할수록 복리처럼 좋아지는 시스템에 도달할 수 있다는 것입니다.

이제 저희가 이 문제에 어떻게 접근하는지 이야기하고, 마지막에는 여러분께 흥미로울 만한 내용을 이야기하겠습니다.

시작점은 Harrison이 앞서 이야기한 내용과도 이어지는데, 바로 추적성(traceability)입니다. 먼저 이런 상호작용을 포착해야 합니다. 버려지고 있는 경험을 포착해야 합니다. 이것이 1단계입니다.

2단계는 저희 연구가 시작되는 지점입니다. 저희가 만드는 회사는 지속 학습을 가능하게 하는 제품을 만드는 회사이지만, 그 각각의 아래에서 최첨단 연구를 하고 있습니다.

이런 모든 상호작용이 있다고 합시다. 그다음 저희가 만드는 것은 모델 명세(model spec)라는 개념입니다. 내가 에이전트에게 무엇을 하게 하고 싶은지 정의하고, 에이전트가 그것에 맞춰 학습하게 하는 방식이 필요하다는 생각입니다. 그래서 사용자 상호작용을 추출해 보상(reward)으로 바꾸고, 실행 흔적(trace)을 추출해 에이전트가 해야 할 정확한 명세(spec)로 바꾸는 연구를 하고 있습니다.

좋습니다. 에이전트가 무엇을 해야 하는지 알게 되었습니다. 그러면 무엇을 해야 할까요? 두 가지 표면(surface)이 있습니다.

하나는 모델입니다. 실제 상호작용에서 모델이 학습하게 하고 싶습니다. 그래서 SDPO 같은 알고리즘과 그와 유사한 방향에서, 강화학습(RL)을 사용해 긴 전체 실행 흔적(trace)을 바탕으로 시간이 지날수록 모델을 개선하는 연구를 하고 있습니다.

하지만 모델만 있는 것은 아닙니다. 하네스(harness)도 있습니다. 좋은 사용자 피드백이 있을 때 그것이 하네스로 가야 하는지, 모델로 가야 하는지에 대해서도 많은 연구를 하고 있습니다.

예를 들어 “이 회사는 상장폐지되었다” 같은 사실이 있다고 합시다. 이런 지식은 모델 안에 학습시키고 싶지 않을 가능성이 큽니다. 하네스가 사용할 수 있는 컨텍스트(context)로 제공하는 편이 낫습니다.

그래서 저희는 이런 식으로 나누고 있습니다. 실제 상호작용에서 출발해, 에이전트가 더 잘해야 하는 것의 명세를 만들고, 더 나은 모델과 더 나은 하네스를 만들고, 그 모델을 바로 배포해 저희 제품에서 사용하게 하는 것입니다.

이것이 저희가 가고 싶은 세계입니다.

여러분이 에이전트를 만들어봤다면, 아마 이 모든 부분에서 정말 많은 일이 잘못된다는 것을 알 것입니다. 그리고 각각은 아직 해결되지 않은 문제입니다. 그래서 나머지 이야기는 제가 알라딘에서 나온 사람처럼 네 가지 소원이 있다고 상상하며 설명하겠습니다. 에이전트 생태계를 더 좋게 만들기 위해 어떤 소원을 빌고 싶은지 말하겠습니다.

오늘날 에이전트가 있고, 이 격차가 있습니다. 에이전트가 어느 수준까지 올라가면 그다음부터는 지속 학습의 지수적 효과를 볼 수 있습니다. 그 조건들이 무엇인지, 제가 말한 네 가지 범주인 추적성, 평가, 하네스, 모델 측면에서 하나씩 설명하겠습니다.

첫 번째 소원은 추적성(traceability)입니다.

여기에는 두 가지 하위 소원이 있습니다. 첫 번째는 하위 에이전트(sub-agent)를 포함해 일어난 일의 전체 트리(tree)를 추적하는 것입니다. 많은 회사는 메인 액션만 추적하고, 도구 호출(tool call)이나 하위 에이전트 호출은 버립니다. 그러면 전체 작업에서 배우기가 매우 어려워집니다.

두 번째 하위 소원이 아마 가장 중요합니다. 제품을 만들 때 상호작용 데이터를 포착할 수 있어야 할 뿐 아니라, 적절한 양의 피드백을 사용자에게서 끌어내고 그것을 포착할 수 있도록 설계해야 합니다.

여기서 흥미로운 점은 1단계식 사고방식은 “좋아요/싫어요 버튼을 두고 그것을 기록하자”입니다. 이론적으로는 훌륭해 보입니다. 하지만 실제로는 잡음이 너무 많습니다. 코딩 에이전트를 써봤다면 알겠지만, 사용자는 에이전트가 한 일을 그냥 다 받아들이는 경우가 많습니다. 그리고 다섯 커밋쯤 지난 후에야 “아, 이게 다 망가뜨렸구나. 되돌려야겠다”라고 깨닫습니다.

그래서 중요한 것은 교정 행동(corrective behavior)입니다. 수정(edit), 되돌리기(undo), 재시도(retry)를 사용자에게서 끌어내야 하고, 동시에 그것을 포착해야 합니다. 이것이 추적성에 대한 제 소원입니다.

두 번째 소원은 평가(evals)에 관한 것입니다.

여기서 사용할 사고 모델은 사용자가 쓰는 제품과 평가가 이루어지는 곳이 최대한 가까워야 한다는 것입니다. 이상적인 세계에서는 둘이 완전히 같습니다. 차이가 없습니다.

이것은 평가가 실제 트래픽에서 나와야 한다는 뜻입니다. 사람들이 실제로 제품을 어떻게 사용하는지, 현재 어떻게 쓰는지, 그리고 아직 가능하지 않을 수 있는 경계선의 요청을 어떻게 하는지 모두 매우 도움이 됩니다.

두 번째는 모든 작업을 다시 실행 가능하게 만드는 것입니다. 이것은 꽤 큰 인프라 과제입니다. 사용자가 어떤 일을 했다면, 그 사용자가 한 일을 somehow 다시 재생할 수 있는가 하는 문제입니다. 이것은 에이전트 시대에 앞으로 나아가는 데 엄청난 도움이 됩니다.

마지막으로 첫 번째와 연결되는 이야기인데, 실제 하네스(real harness)로 채점해야 합니다. 하네스의 변형을 만들어 채점하는 것이 아니라, 사람들이 프로덕션에서 쓰는 실제 하네스를 채점해야 합니다.

이것이 두 번째 소원입니다.

세 번째 소원은 하네스(harness)에 관한 것입니다. 꽤 중요합니다.

첫 번째로, 제가 보기에 많은 제품은 1년 또는 1년 반 전의 모델을 기준으로 하네스를 만들었습니다. 그때 하네스의 주된 기능은 에이전트가 나쁜 일을 하지 못하게 막는 것이었습니다. 에이전트가 무작위로 망가지거나 출력 형식을 잘못 만들던 시절에는 좋은 접근이었습니다. 하지만 지금은 에이전트가 해보게 두는(let the agents cook) 세계에 훨씬 가까워졌습니다.

그래서 하네스를 만들 때 특정 흐름을 강제하는 방식이 아니라, 제품이 가진 원시 기능(primitives)이 무엇인지 생각해야 합니다. 검색 도구든, 비공개 정보든, 그 기능들을 에이전트가 조율(orchestrate)하도록 보고, 그렇게 하게 해야 합니다.

이것이 첫 번째 하위 소원입니다.

두 번째 하위 소원은 저희 제품도 그렇게 만들고 있는데, 에이전트 인터페이스를 사용자 인터페이스와 최대한 가깝게 만드는 것입니다. 이상적인 세계에서는 제가 UI에서 할 수 있는 모든 일을 에이전트도 도구 호출(tool call)을 통해 할 수 있습니다. 그런 세계가 학습과 지속 학습을 훨씬 쉽게 만듭니다.

마지막으로 작은 소원이 하나 있습니다. 도구 응답(tool response)을 정보가 풍부하게 만드는 것입니다.

“상태만 알면 된다. 검색 도구를 호출한다고 해보자. 상태를 알고 싶고, 작동했는지 알고 싶다. 데이터베이스(DB)에 쓰는 작업이라면 그냥 쓰면 된다”라고 생각하기 쉽습니다. 그런데 실제로 자주 보는 것은 도구 호출의 응답이 “완료됨. 끝.”인 경우입니다.

이론적으로는 괜찮아 보이지만, 에이전트 관점에서는 매우 혼란스럽습니다. 그것으로 학습하거나 개선하려고 해도 배울 신호가 없습니다. 실제로 무엇이 쓰였는지 알 수 없고, 실제로 무엇을 읽었는지도 알 수 없습니다. 그래서 하네스에 대한 마지막 하위 소원은 도구 응답을 정말 정보가 풍부하게 만드는 것입니다.

이것이 세 번째 소원입니다. 원래 전통적으로는 세 가지 소원만 받을 수 있지만, 네 가지가 있다고 상상해봅시다.

네 번째는 모델에 관한 것입니다. 오늘 많이 이야기된 주제이기도 합니다.

오픈 웨이트(open-weight) 모델로 전환하는 것이 그저 스위치 하나 바꾸는 것처럼 쉬우면 좋겠지만, 실제로 해보면 보안, 안전, 접근 권한 관리 등 50가지 다른 고려사항이 있습니다. 그래도 오픈 웨이트를 운영하는 데 익숙해지기 시작해야 합니다. 그것이 자기 가중치(weights)를 소유하고 그 위에서 지속적으로 개선할 수 있는 문을 열어주기 때문입니다.

Gabe도 모델 라우터(model router)가 큰 역할을 할 것이라고 이야기했습니다. 작업의 정확한 역량 요구에 맞게 지능을 라우팅하는 것입니다. 라우터를 실험하는 것도 제가 세상에 던지고 싶은 또 하나의 소원입니다.

이것이 큰 그림입니다.

저희가 회사들과 일할 때 가장 먼저 하는 일은 보통 이 항목들을 감사(audit)하고 현재 어디에 있는지 보는 것입니다. 대부분은 여기까지 오기 위해 해야 할 일이 많습니다. 그래서 저희가 함께 구축합니다. 회사에 갔을 때 이런 것들이 많이 구축되어 있다면 정말 꿈같을 것입니다.

물론 많은 회사가 평가를 갖고 있지 않거나, 추적성이 잘못되어 있을 수 있다는 것도 알고 있습니다. 그래서 “평가가 없다고 가정하면 어떻게 극복할까?”, “추적이 틀어져 있다고 가정하면 존재하는 신호에서 어떻게 배울까?” 같은 연구도 하고 있습니다. 이것이 제가 바라는 세상입니다.

빠르게 말씀드리면, 이것은 매우 핵심적인 연구이자 제품 문제입니다. 그래서 저희가 만든 팀에 매우 기대하고 있습니다. 더 중요하게는 오늘 이 자리에 있는 두 분을 포함해, 저희는 매우 프런티어에 있는 고객들과 일하고 있습니다. 현재와 미래의 프로덕션에서 에이전트가 무엇을 할 수 있는지 한계를 밀어붙이는 분들입니다.

그래서 그들과 함께 일하게 되어 매우 기쁩니다.

또 보여드리고 싶은 것이 있습니다. 아, 저건 제 이메일입니다.

저희는 베타가 있습니다. 저희가 가진 핵심 믿음은 자기 지능을 소유하는 능력이 외부 컨설팅에 계속 맡겨야 하는 것이어서는 안 된다는 것입니다. 이 능력은 제품에 너무 중요하기 때문에 회사가 스스로 쌓아야 하는 전문성입니다.

그래서 저희는 어떤 회사든 자기 모델을 소유하고, 주로 실제 상호작용에서 지속 학습에 도달할 수 있게 해주는 제품을 만들고 싶습니다.

여기 저희 제품의 스크린샷이 있습니다. Nico가 여기 있는지 모르겠지만, 오늘 나중에 Nico에게 보여주기로 되어 있어서 미리 보여드리는 셈입니다.

여기 Harvey가 있습니다. Gabe가 이야기한 lab benchmark도 있습니다. 가져오기가 정말 쉽습니다. 모델을 학습시키는 것도 매우 쉽습니다.

저희는 이 인터페이스를 매우 자랑스럽게 생각합니다. 후처리 학습(post-training)을 해봤다면, 잘못될 수 있는 것이 5천만 가지쯤 있고, 조정해야 할 손잡이도 5천만 개쯤 있으며, 모든 것이 연구자의 직관, 상표 표시 같은 것에 의존한다는 것을 알 것입니다.

저희가 하려는 것은 연구자들이 모델을 후처리 학습하는 방식을 가져와, 뒤에서 에이전트가 대부분의 손잡이를 처리하게 하는 것입니다. 사용자는 후처리를 쉽게 하기 위해 꼭 알아야 할 것만 보게 합니다.

그래서 모델을 학습시키고, 모델이 어떻게 되고 있는지 보고, 평가하고, 비교하고, 이전에 쓰던 모델보다 나은지 확인하고, 배포하는 것이 매우 쉽습니다. 실제로 사용자가 들인 작업 시간은 모델 학습 대기 시간을 제외하면 아마 15분 정도였습니다.

이것이 저희가 가고 싶은 세계입니다. 이 방에 있는 더 많은 회사들이 이런 능력을 갖게 하고 싶습니다.

저희의 목표는 모든 회사가 자기 경험 레이어(experience layer)를 소유하게 하는 것입니다. 이 자리에 계신 분들 중 일부와 함께 그것을 만들어가게 되기를 기대합니다.

감사합니다.

질문입니다. 지속 학습을 이야기할 때, 학습 가능한 대상(trainable object)을 어떻게 보시나요? 모델 가중치(model weights), 하네스(harness), 도구(tools), 애플리케이션 계층(application layers) 사이에서 어떻게 생각하고 우선순위를 정하시나요?

좋은 질문입니다. 재미있는 표현을 하나 쓰자면, 연구자 여섯 명에게 지속 학습이 무엇인지 물으면 아마 일곱 가지 답을 얻게 될 것입니다.

아주 순수하게 보면 “사람처럼 되어야 하고, 실시간으로 한 번에 가중치가 적응해야 한다”고 말할 수도 있습니다.

하지만 저희는 제품을 움직이는 지능이 하나의 시스템이라고 봅니다. 여러 구성요소를 가진 시스템입니다. 진정한 지속 학습은 그 시스템 전체를 최적화하고, 새로 배운 정보에 따라 시스템의 어떤 부분을 업데이트해야 하는지 최적화하는 것입니다.

제가 떠올리는 비유는 저장입니다. 우리는 더 이상 어떤 데이터를 RAM에 저장할지, 하드디스크에 저장할지 생각하지 않습니다. 무엇이 가장 적절한지에 따라 추상화되어 있습니다. 모델, 하네스, 컨텍스트도 같은 방식으로 봅니다. 지금처럼 거의 근거가 없는 상태에서 무엇을 업데이트할지 사람이 결정해야 하는 것은 이상합니다.

이것은 해결할 수 있는 과학적 문제입니다. 그것을 풀고 추상화해야 합니다.

또 다른 질문입니다. 오늘 몇몇 발표자는 고객 데이터로 학습하지 않는 것이 중요하다고 이야기했습니다. 그런데 지속 학습의 큰 부분은 이런 모든 상호작용에서 배우는 것이라고 생각합니다. 차등 프라이버시(differential privacy) 같은 문제는 어떻게 생각하시나요? 대부분의 애플리케이션 회사가 고객별 데이터 계약을 갖고 있어 매우 어려울 텐데, 시스템을 실제로 어떻게 더 좋게 만드나요?

100% 맞습니다. 매우 중요한 문제입니다.

사실 저는 이전에 Apple에 있었고, 그곳에서도 이 문제를 꽤 많이 다뤘습니다.

고객 데이터로 실제 학습하지 않는 영리한 방법들이 있습니다. 대신 고객 데이터에서 분포(distribution)를 샘플링하고, 그다음 자체적으로 합성 데이터(synthetic data)를 생성합니다. 암호학적인 사고 모델과 비슷하게, 그 분포들을 비교해 내 데이터가 실제 분포 위에 있는지 확인하지만, 고객 데이터 자체를 직접 학습하지는 않습니다.

그래서 맞는 지적입니다. 여기에는 흥미로운 작업이 많고 매우 핵심적인 문제입니다. 이미 저희 고객들과도 이 문제를 넘어서기 위해 재미있는 일들을 하고 있습니다.

안녕하세요. 저는 Finch의 Sid입니다. 감사합니다. 에피소드 기억(episodic memory)이 지속 학습에 어느 정도 역할을 한다고 생각합니다. 예를 들어 사용자가 저희 플랫폼에서 이전에 에이전트가 한 일을 수정하는 행동을 하면, 에이전트의 행동을 업데이트하고 싶을 수 있습니다. Trajectory는 플랫폼 차원에서 이에 대해 어떤 견해를 갖고 있나요?

에피소드 기억과 서로 다른 피드백 유형이 무엇을 학습하게 하는지에 대한 질문이군요. 생각이 많습니다.

한 가지 관점은 신호에 두 가지 유형이 있다는 것입니다.

첫 번째는 “무언가 잘못됐다”는 신호입니다. 예를 들어 누군가 에이전트에게 “너 정말 못한다”고 화를 내지만 그 뒤에 아무것도 하지 않거나, 싫어요를 누르거나, 세션을 떠나는 경우입니다. 이런 경우에는 뭔가 잘못됐다는 것은 알지만, 올바른 모습이 무엇인지는 모릅니다.

두 번째는 에이전트가 재시도해서 올바른 해결책에 도달했거나, 사용자가 “차이는 이것이다”라고 말하며 고쳐준 경우입니다. 이 경우에는 출력에 연결된 보상(reward)과 우리가 할당하는 값에 대해 매우 확신할 수 있습니다. 앞의 경우에는 그 행동을 벌점 처리해야 한다는 것은 알지만, 반드시 정답을 말할 수는 없습니다.

또 다른 관점은 정보가 누구에게 관련되는지의 계층이 있다는 것입니다. 어떤 정보는 전역적으로 정확하고 전역적으로 참일 가능성이 큽니다. 예를 들어 특정 도구를 호출하려 할 때 도구 호출이 반복적으로 실패한다면, 그것은 아마 모두에게 관련된 정보입니다. 따라서 모델에 학습시켜서 모델이 그 도구를 더 잘 쓰게 해야 합니다.

반면 특정 사용자가 “나는 하위 에이전트를 절대 쓰고 싶지 않다. 제발 쓰지 말아 달라”고 한다면, 그것은 모델에 학습시킬 내용이 아니라 컨텍스트에 남겨야 할 가능성이 큽니다.

저희가 기대하는 것은 Harvey가 이야기한 것처럼 이런 일이 조직별(per-org), 더 나아가 고객별(per-customer)로 일어날 수 있다는 점입니다. 이것도 피드백이 누구에게 관련되는지를 생각하는 또 하나의 방식입니다.

마지막 질문입니다. 오늘의 주제 중 하나는 제품의 어떤 작업이나 부분에서는 더 많이 실험하고, 더 저렴하게 가고, 오픈소스(open source)를 더 넣고 싶을 수 있다는 것이었습니다. 반면 다른 영역에서는 최전선 모델이나 폐쇄형 모델, 폐쇄형 프레임워크를 쓰는 것이 더 유용할 수 있습니다.

이 비유를 지속 학습으로 확장하면, 어떤 작업이나 워크플로에서 이것이 정말 중요하게 보이나요? 반대로 정적으로 학습된 최신 모델이나 정적으로 학습된 오픈소스 모델을 쓰고, 하네스로 관련 정보를 컨텍스트에 주입하는 것만으로도 사용자가 원하는 것을 충분히 달성할 수 있는 문제는 어떤 형태인가요?

좋은 질문입니다.

1단계 답변은 대부분의 작업이 지속 학습에 적합하다는 것입니다. 하지만 제가 가장 흥미롭게 보는 것은 프런티어(frontier)에 있는 작업입니다.

저희가 AI 발전을 보는 사고 모델은 이렇습니다. 사람들은 제품이 할 수 있다고 기대하는 수준에 맞춰 모델이나 제품에 요청합니다. 때로는 제품이 아직 못할 수 있는 경계선의 요청을 합니다. 실패하거나 잘못된 결과를 보면 “아직 충분히 좋지 않구나. 이 용도로는 못 쓰겠다”고 물러납니다.

좋은 예로 Cursor가 있습니다. 2년 전의 저라면 지금 Cursor에 던지는 이상한 쿼리를 입력할 생각이나 했을까요? 절대 아닙니다. 훨씬 낮은 수준의 요청을 했을 것입니다. 그런데 시간이 지나면서 모델이 좋아졌고, 저는 “좋아, 더 크고 더 큰 일을 시켜볼 수 있겠네”라고 생각하게 되었습니다.

저희가 가장 기대하는 것은, 지금까지는 모델이 전반적으로 좋아지고 우리가 특정 방향으로 밀어붙이는 방식으로 이런 일이 일어났다는 점입니다. 그런데 저희 고객들 중에는 사용자가 어떤 일을 요청하고, 모델이 간신히 해내거나 실패했지만, 학습 중에 그 일을 배우고, 이후 사용자가 전에는 못하던 그 일을 할 수 있게 되는 사례가 있습니다.

그 연결고리가 지속 학습에서 정말 흥미로운 부분입니다. 사용자가 시도했지만 하지 못한 것을 바탕으로 가능한 것의 경계를 밀어 올리는 것입니다.
