영상 미시청 기준 · 약 10분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 좋은 요청보다 좋은 작업 구조가 중요하다

Charlie와 Gabriel이 보여주는 Codex 활용법의 핵심은 “멋진 한 문장으로 코드를 만들어 달라고 부탁하는 법”이 아니다. 두 사람은 필요한 맥락을 넘기고, 실제 도구로 행동하게 하고, 긴 작업을 나누고, 완료 여부를 검사하며, 그 흐름을 반복 가능하게 만드는 법을 설명한다.

여기서 맥락은 단순한 프롬프트가 아니다. Slack 대화, 저장소와 변경 기록, 화면에 보이는 내용, 사용자의 선호, 팀의 개발 지침, 외부 서비스 연결까지 포함한다. Codex가 행동하려면 브라우저나 데스크톱 앱을 조작할 통로가 필요하고, 오래 일하려면 “무엇을 끝이라고 볼지” 확인할 기준도 필요하다. 사람은 모든 클릭을 대신하기보다 목표, 권한, 예외와 승인 지점을 관리하는 역할로 이동한다.

읽는 법: 위에서 아래로 내려간다. 앞 단계는 뒤 단계의 재료가 된다. 자동화부터 시작하는 것이 아니라, 먼저 맥락과 완료 기준을 마련해야 한다는 구조다. 실제 성능을 측정한 수치 그래프가 아니라 발표 내용을 연결한 개념도다.

1. 맥락을 다시 설명하지 않게 만든다

발표의 첫 사례는 Slack에서 나눈 아이디어를 이용해 macOS 실시간 번역 앱을 만드는 일이었다. 발표자는 Slack 화면의 글과 화면 정보를 함께 담는 App Shot을 Codex에 넘겼다. 매번 대화를 복사하거나 배경을 처음부터 다시 설명하는 대신, 이미 존재하는 대화를 작업 재료로 쓴 것이다.

Codex는 4분 2초 뒤 앱을 만들었다고 발표되지만, 무대에서 실행했을 때는 오디오 입력과 스피커 소리가 다시 마이크로 들어가는 문제를 조정해야 했다. 이 장면은 “빨리 생성했다”와 “실제 환경에서 안정적으로 작동한다”가 다르다는 점도 보여준다. 만들어진 결과물은 실행과 검증을 거쳐야 한다.

반복해서 필요한 지침은 스킬이나 플러그인으로 묶을 수 있다. 발표에서 플러그인은 팀의 모범 사례를 담은 스킬, 외부 프롬프트, 서비스 연결 설정, 도구를 제공하는 MCP 서버 등을 함께 담는 묶음으로 설명된다. 예를 들어 macOS 앱을 만드는 모범 사례나 OpenAI 개발 서비스 연결을 다음 작업에서도 다시 사용할 수 있게 하는 방식이다.

사용자 선호도 맥락이 된다. 발표자는 메모리가 기본적으로 꺼져 있으며, 설정에서 켤 수 있다고 설명한다. 도구가 돌려준 민감한 정보가 장기 기억에 남지 않도록 도구 사용 대화에서는 메모리 생성을 건너뛰는 선택지도 언급한다. 따라서 개인화는 편리함만의 문제가 아니라 무엇을 기억시킬지 결정하는 문제다.

2. 행동 통로는 작업의 병목에 맞춰 고른다

Codex가 코드를 쓰는 것과 이미 존재하는 프로그램을 직접 조작하는 것은 다른 문제다. 발표에서는 세 가지 통로를 구분한다.

읽는 법: 모바일에서는 표 안을 좌우로 이동해 네 열을 확인한다. “어느 기능이 더 강한가”보다 “어디에 상태와 권한이 있는가”를 기준으로 행을 고른다. 이 표는 발표자의 용도 구분을 정리한 것이며 독립적인 성능 비교 결과는 아니다.

발표 사례에서 컴퓨터 사용은 날짜 범위와 파일 형식을 달리해 대시보드 데이터를 내려받는 데 쓰였다. Chrome 확장은 문서에 있는 질문으로 Google 피드백 폼을 만들고 모든 문항을 필수로 표시하는 데 쓰였다. 둘 다 단순한 코드 생성보다 이미 존재하는 화면에서 반복 클릭을 대신하는 작업이다.

3. 긴 작업은 길게 지시하는 것이 아니라 확인 가능하게 만든다

발표자는 약 400명이 쓰는 실시간 질의응답 사이트, 기존 오픈소스 폼 빌더의 내부용 개조, Julia와 R로 작성했던 연구물을 Python 패키지와 Rust 백엔드로 다시 만드는 작업을 보여준다. 제시된 실행 시간은 각각 약 15시간 30분 55초, 5시간 57분, 7시간 1분 40초였다.

오래 실행된다는 사실만으로 좋은 작업은 아니다. 핵심은 끝났는지를 확인할 수 있는 기준이다. 발표의 Goal 기능은 목표와 성공 조건을 확인하면서 아직 끝나지 않았으면 계속 작업하는 방식으로 설명된다. 발표자는 하나의 막연한 목표 대신 여러 목표를 goals.md에 두고, 진행 상황을 dashboard.html로 보이게 한 사례를 제시한다. 코드 리뷰와 목표 감사도 별도 시점에 실행했다.

완료 기준이 모호하면 에이전트가 문장 그대로는 달성했지만 사용자가 원한 결과와 달라질 수 있다. Charlie는 이를 소원을 문자 그대로 비틀어 이루는 이야기인 “원숭이 손”에 비유한다. 따라서 “좋은 앱을 만들어라”보다 로그인, 화면, 테스트, 배포, 승인처럼 관찰 가능한 조건을 적는 편이 낫다는 주장이다.

긴 작업은 권한에서도 막힌다. Vercel 인증이나 Convex 배포 키가 없을 때 Codex는 해당 경로를 막힘으로 표시했고, 발표자가 별도 인증 흐름이나 원격 환경에 키를 넣는 방법을 제공했다. 에이전트가 오래 일하더라도 사람이 필요한 승인과 비밀 정보까지 저절로 생기는 것은 아니다.

4. 서브에이전트와 별도 스레드는 “누가 봐야 하는가”로 나눈다

발표자가 제시한 구분은 가시성이다.

  • 서브에이전트: 중간 작업을 주로 모델이 관리해도 될 때 쓴다. 코드 리뷰나 문서 조사처럼 역할별 지침과 모델을 따로 둘 수 있고, 주 작업과 맥락을 분리한다.
  • 스레드 간 전달: 사용자가 위임 과정과 대화를 직접 보고 개입해야 할 때 쓴다. 원격 스레드가 로컬 스레드에 브라우저 테스트를 맡기거나, 게임의 미술·음악·애니메이션·규칙 작업이 창작 감독 스레드의 승인을 받는 사례가 제시된다.
  • 사이드 스레드: 진행 중인 본 작업을 멈추지 않고 상태와 다음 계획을 묻는 데 쓴다. 다만 일시적이어서 오래 보존할 내용은 메인 스레드로 돌려보내야 한다고 설명한다.

즉, 일을 많이 쪼개는 것이 목표가 아니다. 모델끼리 처리해도 되는 내용과 사람이 확인해야 하는 내용을 구분하는 것이 목표다.

5. 판단이 필요한 일과 반드시 지킬 검사를 분리한다

언어 모델에게 “끝나기 전에 린터를 실행해”라고 지시할 수도 있다. 그러나 보안 검사, 허용 도구 확인, 로그 전송처럼 특정 시점마다 반드시 실행돼야 하는 일은 훅(Hook)으로 고정할 수 있다고 발표자는 설명한다. 훅은 입력이나 출력에 API 키가 섞였는지 검사하거나, 승인 목록에 없는 도구 호출을 막거나, 매 작업 종료 시 저장소를 정리하는 식으로 사용된다.

이 차이가 중요하다. 모델은 상황을 해석하고 새로운 해결책을 찾는 데 쓰고, 반드시 같은 방식으로 실행돼야 하는 검사는 정해진 코드로 처리한다. 자율 실행 시간이 길수록 이런 고정 검사가 감독의 일부가 된다.

6. 자동화는 기다림과 피드백을 다시 작업으로 연결한다

발표의 Heartbeat 자동화는 같은 스레드가 일정 시간마다 상태를 확인하다가 준비되면 다음 단계로 넘어가는 방식이다. DigitalOcean 서버가 준비됐는지 5분마다 확인하는 사례가 소개됐다. 별도의 예약 자동화는 정해진 때마다 새 스레드를 만들 수도 있다.

Slack 피드백 사례에서는 30분마다 댓글을 읽고 칭찬, 버그, 기능 요청 등으로 나눈 다음, 수정 가능한 항목이면 새 작업 스레드와 작업 트리를 만들고 PR과 리뷰로 연결하는 흐름을 제안한다.

읽는 법: 위에서 아래로 진행한 뒤 마지막 줄에서 다시 1번으로 돌아간다. 단순히 같은 명령을 반복하는 순환이 아니라, 이전 검증 결과를 다음 맥락에 반영하는 순환이다. 발표에서 제안한 구조이며 해당 Slack 자동화가 끝까지 운영·검증됐다는 뜻은 아니다.

7. 마지막 단계는 Codex 자체를 필요한 제품 안에 넣는 것이다

App Server는 Codex 앱, CLI, VS Code 확장이 핵심 에이전트 실행부와 통신하게 하는 프로토콜로 설명된다. 발표자는 이를 사용해 Retrodex라는 별도 사용자 인터페이스를 만드는 작업을 시연했다. 모델과 추론 수준을 고르고 대화를 보내는 화면을 자체적으로 만들면서도, Codex의 도구 호출과 맥락 압축 같은 핵심 기능을 이용한다는 설명이다.

이 단계에서 관점이 바뀐다. 사람이 Codex 앱에서 한 번 요청하는 데서 끝나지 않고, 팀의 내부 플랫폼이나 사용자가 쓰는 제품 안에 작업 흐름을 넣으려는 것이다. 발표의 표현을 빌리면 하나의 소프트웨어를 만드는 데서 소프트웨어를 계속 만드는 시스템으로 확대하는 셈이다.

다만 발표자는 사람을 무조건 없애자고 말하지 않는다. 사람이 필요한 승인, 목표 설정, 권한 제공과 예외 판단은 남겨 두되, 단순 대기와 반복 클릭처럼 사람이 없어도 되는 지점을 찾아내자는 주장이다.

전체 통찰과 적용 경계

이 발표가 제시하는 인과는 다음과 같다.

  1. 맥락이 부족하면 에이전트가 추측하거나 사용자가 반복 설명한다.
  2. 행동 통로가 없으면 결과를 제안할 수는 있어도 실제 시스템을 조작하지 못한다.
  3. 완료 기준이 없으면 오래 일해도 제대로 끝났는지 판단할 수 없다.
  4. 위임 과정이 보이지 않으면 사람이 개입할 시점을 놓친다.
  5. 고정 검사와 권한 경계가 없으면 자율성이 커질수록 위험도 커진다.
  6. 이 요소들을 묶으면 일회성 요청을 반복 가능한 개발 흐름으로 바꿀 수 있다.

그러나 영상은 제품팀 발표와 현장 시연이다. “App Shot이 90% 넘게 올바른 일을 알아낸다”, 수십 시간 작업이 성공했다는 사례, 기능별 적합성은 발표자의 경험과 주장이지 독립적인 비교 시험이 아니다. 또한 기능 이름, 제공 요금제와 출시 상태는 발표 당시 기준으로 읽어야 한다. 실제 적용 전에는 자신의 작업에서 권한, 비용, 실패 복구와 완료 기준을 따로 검증해야 한다.

여기까지만 이해하면 충분

  • Codex의 긴 작업 성패는 멋진 프롬프트보다 맥락, 검증 가능한 완료 기준, 권한과 감독 구조에 달려 있다.
  • 컴퓨터 사용, Chrome 확장, 앱 내 브라우저는 같은 기능이 아니라 작업 대상과 로그인 상태에 따라 고르는 행동 통로다.
  • 서브에이전트는 모델 중심의 내부 위임에, 별도 스레드는 사람이 진행 과정을 보고 개입해야 하는 위임에 더 알맞다는 것이 발표자의 구분이다.
  • 자동화는 반복 실행만이 아니라 감지, 실행, 검증, 기록을 연결해 다음 작업을 개선하는 루프다.

오늘 대답할 질문

Codex의 일회성 요청을 사람이 감독할 수 있는 반복 가능한 개발 흐름으로 바꾸려면 무엇을 연결해야 하는가?

1. 도입과 여섯 단계

Charlie와 Gabriel은 자신들을 OpenAI Developer Experience 팀이라고 소개한다. Gabriel은 싱가포르에서 왔다고 말한다. 도입 사례에는 거의 300개의 서브에이전트를 쓴 세션, Ableton용 신시사이저 플러그인, Premiere를 조작하는 영상 편집, 게임 제작과 자율주행 골프 카트가 포함된다.

Codex를 앱이나 ChatGPT 안에서만 쓸 필요가 없다는 설명과 함께 모바일, Remote, App Server가 언급된다. 한 사용자가 일본에서 이동하며 사용한 사례와 Daniel이 세 개의 전자잉크 기기에 넣었다는 사례도 소개된다.

발표가 묶은 여섯 단계는 다음과 같다.

  1. 문서, 대화, 이메일과 업무 도구의 맥락을 준다.
  2. 그 맥락으로 결과물을 만든다.
  3. 컴퓨터 사용 등으로 실제 행동을 수행한다.
  4. 긴 작업에서 여러 에이전트와 스레드가 협업한다.
  5. 반복성과 일관성을 위한 루프를 만든다.
  6. App Server로 Codex를 다른 제품과 플랫폼에 넣는다.

2. 실시간 번역 앱

금요일 오후 4시 44분, Charlie, Christine과 Gabriel은 워크숍 시연 아이디어를 논의했다. Christine은 실시간 번역기를, Charlie는 GPT 실시간 번역 사용을 제안했다.

Gabriel은 Slack 대화를 App Shot으로 넘기고 macOS 앱을 만들어 달라고 요청했다. App Shot은 화면 이미지뿐 아니라 화면의 텍스트도 담는다고 설명한다. 앱은 4분 2초 뒤 만들어졌다고 발표됐다.

Gabriel은 자신이 macOS 앱을 만든 적이 없고 데이터 과학 배경이며 WebRTC나 WebSocket에 능숙하지 않다고 말했다. Build macOS와 OpenAI Developers 플러그인에서 모범 사례와 서비스 연결을 얻었다고 설명한다. 독일어 번역 시연은 실행됐지만 오디오 입력과 스피커 소리의 마이크 유입을 조정해야 했다.

3. 맥락과 개인화

플러그인은 다음 요소를 함께 묶는 것으로 설명된다.

  • 팀이나 기술의 모범 사례를 담은 스킬
  • 외부 프롬프트와 팀별 실무 지침
  • 외부 서비스 연결 설정을 담은 앱
  • 필요한 도구를 제공하는 MCP 서버

발표자는 어려운 작업을 해결한 대화가 끝나면 “이것을 스킬이나 플러그인으로 만들어라”라고 요청해 다음 작업에서 재사용한다고 말한다.

메모리는 기본적으로 꺼져 있고 설정에서 켤 수 있다고 설명한다. Gabriel은 Python 패키지 관리에서 uv를 선호한다는 내용을 학습하는 예를 든다. 도구가 반환한 정보를 장기 보존하지 않도록 도구 관련 대화의 메모리 생성을 건너뛸 수 있다고 말한다.

Chronicle은 Pro 구독자용 연구 미리보기로 소개됐다. Gabriel은 자신이 Business 요금제를 사용해 해당 옵션이 없다고 말했다. 사용자 지침은 홈 디렉터리의 AGENTS.md처럼 모든 대화에 적용되는 것으로 설명된다.

Charlie는 자신이 App Shot을 쓸 때 90%가 넘는 경우 Codex가 해야 할 일을 알아낸다고 주장한다. 이는 개인 경험에 따른 수치다. 메모리와 Chronicle은 토큰 예산을 더 쓸 수 있다고도 말한다.

4. 컴퓨터와 브라우저 제어

컴퓨터 사용 시연에서는 대시보드에서 최근 7일의 커밋 수를 CSV로, 6월 1일부터 6월 29일까지의 풀 리퀘스트 데이터를 JSON으로 내려받도록 요청했다. 발표자는 자신의 손을 키보드에서 뗀 상태에서 별도 커서가 움직이는 장면을 보여준다.

Chrome 확장 시연에서는 Google 문서에 준비된 질문을 읽고 피드백 폼을 만들며 각 질문을 필수로 표시하게 했다.

Charlie의 구분은 다음과 같다.

  • 앱 내 브라우저는 브라우저 엔진과 더 깊게 연결돼 로컬 웹 앱의 배치와 상호작용 테스트에 적합하다.
  • 컴퓨터 사용은 API가 없는 데스크톱이나 오래된 업무 프로그램을 사람처럼 조작할 때 적합하다.
  • Chrome 확장은 사용자가 로그인한 브라우저 상태와 인증을 허가받아 넘겨야 할 때 적합하다.

5. 장시간 프로젝트

발표에서 구체적으로 소개된 장시간 작업은 다음과 같다.

  • 약 400명이 쓰는 실시간 질의응답 사이트: 관리자, 참가자, 무대 화면과 조정 기능을 요구했다. 한 시점에 15시간 30분 55초 실행 중이라고 표시됐다.
  • 오픈소스 폼 빌더의 내부용 개조: ChatGPT 인증이 포함된 Sites 기반 도구로 만들며 5시간 57초 실행됐다고 말했다.
  • 과거 대학원 연구물 재구현: Julia와 R 자료를 읽고 Python 패키지와 Rust 백엔드로 다시 만들며, 동적 계획법 대신 휴리스틱을 쓰라는 제약을 줬다. 7시간 1분 40초 실행됐다고 말했다.
  • Retrodex: App Server를 사용하는 별도 Codex 사용자 인터페이스를 만드는 네 번째 장시간 작업으로 뒤에서 소개된다.

여러 목표를 goals.md에 기록하고 dashboard.html에 진행 상황을 표시했다. 작업 도중 코드 리뷰와 목표 감사를 별도 스레드에서 실행했다. 원격 작업이 로컬 Chrome 테스트를 요청하고, 결과를 다시 원격 스레드로 보내는 사례도 제시됐다.

사이드 스레드에서는 최근 한 시간 동안 한 일, 다음 계획, 사람이 풀어야 할 막힘을 물을 수 있다. 다만 사이드 스레드는 일시적이므로 중요한 내용은 메인 스레드로 보내야 한다고 설명한다.

Vercel 인증과 Convex 배포 키가 없어 작업이 막힌 사례에서는 사람이 인증 흐름을 실행하거나 원격 환경에 비밀 값을 넣었다. 키를 채팅에 직접 붙이지 않고 셸 명령을 통해 설정하는 방법을 요청했다.

6. 맥락 압축, Goal, 서브에이전트와 훅

발표자는 2025년 11월 GPT-5.1-Codex-Max 출시 때 여러 맥락 창을 거치는 압축 방식으로 모델을 훈련했고, 이것이 장시간 작업을 가능하게 한다고 설명한다. 외부 사용자들의 긍정적인 반응도 인용하지만 독립적인 비교 자료는 제시하지 않는다.

Goal에는 가능한 한 구체적이고 검증 가능한 완료 기준을 주라고 강조한다. 40시간 동안 실행돼 Doom을 네이티브 Swift로 재구현했다는 다른 사용자의 사례도 소개된다.

서브에이전트는 역할별 지침과 모델을 설정할 수 있고 별도 맥락에서 일한다. 스레드 간 전달은 사용자가 위임 과정을 직접 볼 필요가 있을 때 사용한다. 게임 제작 사례에서는 창작 감독 스레드가 미술, 음악, 애니메이션과 게임 규칙 작업을 검토했다.

훅은 config.toml에 설정할 수 있다고 설명한다. 사용 예시는 다음과 같다.

  • 대화 로그 전송
  • 입력과 출력의 민감 정보 검사
  • 허용 목록 밖의 도구 호출 확인
  • 특정 행동 전 보안 검사
  • 작업 종료 시 사용자 정의 검증이나 저장소 정리

7. 자동화

DigitalOcean 서버를 준비하는 사례에서는 약 5분 뒤 다시 확인하는 Heartbeat 자동화를 만들었다. 서버 준비가 끝나면 Codex 앱의 설정 화면으로 이어지는 링크와 SSH 설정을 제공했다고 설명한다. 배포 파이프라인도 5분이나 10분마다 상태를 확인하는 방식으로 확장할 수 있다고 말한다.

Slack 피드백 사례에서는 30분마다 댓글을 확인하고 답변하도록 요청했다. 이어 버그나 기능 요청이면 새 작업 트리의 스레드를 만들고 수정한 뒤 PR을 열고, Dom에게 리뷰와 24시간 안의 승인을 요청하며 그렇지 않으면 계속 알리라는 조건을 추가했다. 이는 즉석에서 구성한 예시이며 전체 흐름의 운영 완료 결과는 제시되지 않았다.

발표 중인 화면을 5분마다 촬영해 60분 안에 발표가 끝날지 추정하게 한 자동화도 실행했다. 발표자는 매주 대화를 검토해 스킬이나 AGENTS.md 개선점을 찾는 자동화, 이메일 초안과 실제 발송 답장을 비교해 지침을 개선하는 자동화도 제안한다.

8. App Server와 결론

App Server는 Codex 앱, CLI와 VS Code 확장의 기반 프로토콜로 소개된다. 도구 호출, 플러그인과 맥락 압축을 포함한 핵심 실행부를 자체 제품에 연결할 수 있다고 설명한다. 다만 컴퓨터 사용처럼 특정 컴퓨터에 있어야 하는 기능은 그대로 포함되지 않는다고 Charlie가 밝힌다.

Retrodex 시연에서는 모델과 추론 수준을 선택하고 App Server로 요청을 보내는 별도 화면을 보여준다. 이를 대규모 조직의 통합 에이전트 인터페이스나 자체 플랫폼으로 확장할 수 있다고 제안한다.

마무리 질문은 다음 흐름을 따른다.

  1. Codex에게 그 일을 시도해 보라고 요청했는가?
  2. 한 번의 요청을 반복 루프로 바꿀 수 있는가?
  3. 막힌 원인이 맥락인지 권한인지 확인했는가?
  4. 그 맥락을 스킬이나 플러그인으로 재사용할 수 있는가?
  5. 한 에이전트에서 여러 에이전트로 어떻게 나눌 것인가?
  6. 사람이 없어도 되는 단계와 사람이 남아야 하는 단계를 구분했는가?

워크숍 말미에는 참가자에게 Codex 크레딧 100달러와 API 크레딧 100달러를 제공한다고 안내했다. 두 시간 일정의 마지막에는 기념품을 받을 수 있다고 말했다.

하지만 웹 페이지를 열고 렌더링하는 것뿐 아니라, Codex는 해당 브라우저 엔진과 매우 깊이 연결되어 있습니다. Chrome 확장 프로그램보다도 더 깊게 연결되어 있죠. 그래서 인앱 브라우저는 로컬 웹 애플리케이션을 만들면서 상호작용 디자인과 렌더링 방식을 깊이 테스트하고 싶을 때 특히 좋다고 생각합니다. 그 시점에는 Codex가 레이아웃 내부를 훨씬 더 깊이 볼 수 있기 때문입니다.

오늘 이야기한 두 가지로 돌아가면, 컴퓨터 사용은 노트북이나 컴퓨터에서 하는 어떤 작업에도 유용합니다. 하지만 진정한 장점은 프로그래밍 방식의 인터페이스가 없는 애플리케이션을 사용할 때 드러납니다.

웹 앱이고 API 호출을 역공학할 수 있다면 좋습니다. 하지만 에이전트에 그런 인터페이스를 쉽게 노출하지 않는 데스크톱 소프트웨어와 레거시 소프트웨어가 많이 있습니다. 여러분 인간이 하는 것과 같은 방식으로 Codex가 앱을 조작하기만 하면 된다면, 컴퓨터 사용은 정말 놀랍고 제가 시도해 본 다른 어떤 것과도 다릅니다. 지금까지도 작은 커서들이 이리저리 날아다니는 모습을 보는 것은 여전히 마법처럼 느껴집니다.

그다음은 로그인된 브라우저인 Chrome 확장 프로그램입니다. 에이전트에 상태나 인증 권한을 넘겨야 할 때 가장 유용하다고 생각합니다. 아마 누구나 에이전트가 우리가 하는 것과 정확히 같은 방식으로 월드 와이드 웹을 사용하도록 만들고 싶었던 경험이 있을 텐데, 에이전트가 처음 부딪히는 문제는 “이런, Gmail 계정에 로그인할 수 없네”입니다. 더 심한 경우에는 Google이 제가 헤드리스 Chromium(headless Chromium)을 사용하고 있다는 것을 감지해서 무한 CAPTCHA 루프로 보내 버립니다.

Chrome 확장 프로그램을 사용하면 여러분의 허가에 따라 Codex가 특정 웹사이트에서 여러분인 것처럼 정보를 읽고 자격 증명을 빌려 사용할 수 있습니다. 따라서 구축 과정에서 인증 단계에 대해 걱정할 필요가 없습니다.

좋습니다. 지금까지 Codex가 직접 작업을 수행하는 모습을 봤습니다. 다음으로는 복잡한 작업에서 협업하는 방법을 살펴보겠습니다. 정말 재미있는 주제입니다. 사람들은 Codex가 복잡한 리팩터링과 장시간 실행되는 작업에 강하다고 이야기해 왔습니다. 앞으로 15분 또는 20분 동안 이런 복잡한 작업에서 Codex와 가장 잘 협업하는 방법에 관한 몇 가지 팁을 공유하겠습니다.

20시간짜리 장시간 작업을 시작해 놓고 우리 모두가 점심, 저녁, 아침까지 여기 앉아 있을 수는 없겠죠. 그래서 전날 밤에 몇 가지 작업을 시작해 두었습니다. 서로 조금씩 다른 형태를 보여 주는 네 가지 작업입니다. 이 작업은 약 15시간이 지난 지금도 실행 중입니다. 아래쪽에서 보이듯이 원격 인스턴스에서 실행되고 있습니다. 목표를 하나 실행 중입니다. 15시간 30분 55초 동안 실행되고 있습니다.

스크롤하고 또 스크롤해서 맨 위로 왔습니다. 약간의 그린필드 프로젝트(greenfield project)입니다. 약 400명이 있는 방을 위한 라이브 Q&A 사이트를 만들고 싶었습니다. 관리자 뷰, 참가자 뷰, 무대 뷰가 있습니다. 관리자는 AI가 생성한 텍스트를 사용할 수 있고, 무대 뷰에는 모더레이션 기능과 16:9 뷰가 있어야 한다고 설명했습니다. 모든 애플리케이션을 저희 모더레이션 API를 통해 실행하고, OpenAI가 출시할 것 같은 느낌의 경험을 만들라는 등의 요구사항도 넣었습니다.

여기서는 설명을 위해 특히 평이하고 구체적으로 프롬프트를 작성했습니다. Codex에게 그냥 장황하게 말해도 작업을 완료할 겁니다. 하지만 설명을 위해, 사람들이 사진을 찍는 것을 좋아한다는 점을 알고 있으므로 명확하게 작성하는 방법의 예를 보여 드리는 겁니다.

요즘 사람들이 흔히 하는 오해 중 하나는 늘 이렇게 묻는다는 것입니다. “프롬프트 엔지니어링이 중요한가요?” 지시사항을 명확하게 작성하는 일은 여전히 중요합니다. 저는 여러분의 생각을 읽을 수 없고 Codex도 여러분의 생각을 읽을 수 없으니, 원하는 것을 Codex에 매우 명확하게 말해야 합니다.

하지만 프롬프트 엔지니어링은 어떤 마법의 문구를 찾는 일이 아닙니다. 이제는 더 이상 그런 단계에 있다고 생각하지 않습니다. 추론 모델(reasoning model)은 정말 지능적이고, 핵심은 맥락입니다. 이는 첫 번째 단계인 맥락을 명확하게 제공하는 것으로 다시 이어집니다.

제가 이 프롬프트를 작성한 방법은 Codex와 대화하는 것이었습니다. 휴대폰으로 Codex에게 계속 말했죠. “Codex, 무대에서 보여 줄 수 있도록 이 프롬프트를 다듬어 줄래?”

네, 지금 이걸 만들고 있습니다. Convex 같은 몇 가지 도구를 사용하고 있습니다. Convex에는 실시간 상호작용을 도와주는 플러그인이 있습니다. Vercel에 배포할 예정이고, 물론 OpenAI 플러그인도 사용합니다. 그리고 좋아요, 피드백 양식이 완성됐습니다. 아주 잘 나왔네요.

이것은 한 가지 예입니다. 그린필드 프로젝트죠. 하지만 모든 작업이 처음부터 시작되는 것은 아닙니다. 여기 5시간 57초 동안 실행된 또 다른 예가 있습니다. 폼 빌더 오픈 소스 저장소가 하나 있는데, 이것을 용도 변경해서 Sites 내부에서 만들 수 있을지 궁금했습니다. SaaS를 구매하고 싶지 않을 수도 있습니다. 약 7명으로 구성된 작은 팀이고 내부용 폼 빌더를 원한다고 해 보죠. 팀원만 사용할 수 있도록 Sites에 포함된 ChatGPT 인증을 사용하고, Codex에게 구축을 맡기는 겁니다. 나중에 이것이 어떤 모습인지 예를 보여 드리겠습니다.

마지막 장시간 작업 예시는, 보자면 7시간 1분 40초 동안 실행되었습니다. 대학원 시절의 대학원 연구 논문 몇 편이었습니다. Julia로 작성되었고, R도 사용했던 것 같습니다. 저는 이렇게 요청했습니다. “Rust 백엔드를 사용하는 Python 패키지를 작성할 수 있을까요?” 다시 Codex에 몇 가지 제약 조건을 제시했습니다. 동적 프로그래밍(dynamic programming)은 사용하지 않고 휴리스틱(heuristics)을 사용해야 한다고 했습니다. Codex는 논문을 읽고 이를 구현했습니다.

이것들이 세 가지 장시간 작업 예시이고, 이제 이런 작업을 진행할 때의 모범 사례 몇 가지를 보여 드리고 싶습니다. 예를 들어 이 작업 중 하나에서 Codex에게 이렇게 말했습니다.

목표를 정의할 수 있습니다. 실제로 OpenAI Skills 저장소에는 Define Goal이라는 스킬이 있습니다. 저는 Codex에 “목표를 하나 만들지 말고, 여러 목표를 만들고 goals.md 파일에 넣어”라고 말했습니다. 다시 말하지만 임의적인 방식이지만, 직접 살펴볼 수 있는 파일 모음입니다. 그런 다음 dashboard.html이라는 진행 상황 대시보드(progress dashboard)를 만들라고 했습니다. 대시보드로 돌아가서 무슨 일이 일어나고 있는지 확인할 수 있게 말이죠. 7시간이 넘게 걸리면 실제로 무슨 일이 일어나고 있는지 알기 어렵습니다. 어떤 일이 일어나고 있는지 확인할 방법이 필요합니다.

스레드(thread) 하나가 모든 작업을 처리하게 하는 대신, 실제로는 새 스레드를 생성합니다. 프로젝트로 가 보면—제가 고정해 둔 것을 볼 수 있습니다—다른 스레드가 많이 생성된 것을 확인할 수 있습니다. 예를 들어 여러 마일스톤에서 코드 리뷰를 실행했고, 목표 감사(goal audit)도 실행했습니다. “지금 제대로 진행하고 있나? 처음에 이야기했던 내용이 있고, 목표도 문서화되어 있는데, 거기서 벗어나고 있지는 않나?”라고 확인하는 것입니다. 벗어나고 있다면 메인 스레드에 “이걸 기억해” 또는 “계획을 다시 생각해 봐야 할까?”라고 알려 줍니다. M2, M3A 등 서로 다른 시점과 마일스톤에서 실행했습니다.

여기 라이브 Q&A 사이트의 또 다른 예가 있습니다. 이것은 여전히 원격 세션에서 실행 중입니다. 제 Codex 원격 세션이고, 테스트를 하고 싶었습니다. 그래서 Codex에 이렇게 말했습니다. “내 컴퓨터에서 로컬 스레드를 생성하고 Chrome 확장 프로그램을 사용해서 이걸 검사해도 돼.” 예를 들어 이 스레드를 보면 “다른 스레드의 Codex가 보냄”이라고 되어 있습니다. 원격 스레드가 로컬 스레드와 통신할 수 있습니다.

“클릭 작업을 해야 해. 브라우저를 사용해야 해. QA 테스트를 해야 해”라고 되어 있습니다. 그러자 로컬 스레드가 모든 QA 테스트를 수행하고 결과를 원격 스레드로 다시 보냈습니다. 이런 장기 실행 작업을 생각할 때 고려할 만한 또 다른 방식입니다.

장기 실행 작업에서 또 무엇을 이야기할 수 있는지 보겠습니다. 바로 커뮤니케이션입니다. 이를 생각하는 또 다른 방법은 Codex에 Slack 메시지를 보내 달라고 요청하는 것입니다.

여기 몇 가지 데모가 있습니다. 라이브 Q&A 사이트를 만들고 있었는데, 추가 인프라를 설정하지 않고도 Slack 플러그인을 사용해서 “이 스레드에 답장하고, 완료된 작업과 아직 완료되지 않은 작업, 그리고 차단 요소(blocker)가 있는지 요약해 줘”라고 말할 수 있습니다. 때로는 차단 요소가 있습니다. 인증 문제일 수도 있고, Codex에 제공해야 하는 API 키일 수도 있습니다. 그래서 Codex가 저와 소통하도록 했습니다. 주말 일요일에 친구들과 외출해 있는 동안에도 정기적으로 확인했습니다. “이 여러 작업에서 Codex가 막힌 부분을 해결하도록 내가 할 수 있는 일이 있나?”

그 과정이 어떻게 보였는지 스크린샷을 몇 장 보겠습니다. 보시죠.

Codex의 또 다른 좋은 기능은 메인 스레드를 사용하면서도, 스크린샷에서 보이듯 왼쪽에는 메인 스레드를 두고 오른쪽에서 사이드 스레드(side thread)를 시작할 수 있다는 점입니다.

여기서 실제로 “ChatGPT로 로그인하는 것부터 먼저 집중하자. 곧 자야 해”라고 말하고 있는 것을 볼 수 있습니다. Codex에 제가 그 작업을 해야 한다고 생각했습니다. 아마 도움이 필요할 것이라는 걸 알고 있었기 때문입니다. App Server에서 새 인스턴스와 새로운 사용자 인터페이스를 만들고 있었기 때문에 자격 증명(credentials)이 필요했습니다. 제 자격 증명이 어디에 있는지도 알아야 했습니다. 그런데 Codex가 “알겠습니다. 사실 자격 증명이 이미 여기 있네요”라고 했습니다. 그래서 “좋아, 메인 스레드를 업데이트해”라고 했습니다.

사이드 스레드를 사용해 메인 스레드를 업데이트할 수 있습니다. 이것도 실시간으로 예를 들어 보겠습니다. 이 작업은 아직 실행 중입니다. /side를 입력하면 사이드 스레드가 생성됩니다. Codex에 “무슨 일이 일어나고 있어?”라고 물을 수 있습니다. 물어보죠. 아마 네트워크 때문인지 시간이 좀 걸립니다. 이렇게 말해 보겠습니다. “지금 무슨 일이 일어나고 있어? 지금까지 한 일을, 아마 지난 한 시간 동안 한 일을 목록으로 정리해 줄래? 다음에는 무엇을 할 계획이야? 네가 막힌 부분을 해결하기 위해 내가 할 수 있는 일이 있어?”

에이전트가 다음에 무엇을 할지 알려 주면, 잘못된 방향으로 가고 있는지도 파악할 수 있습니다. 그러면 “그건 하지 않는 게 좋을 것 같아. 대신 이렇게 해야 해”라고 말할 수 있습니다. 사이드 스레드는 메인 스레드와 통신할 수 있으므로 꽤 좋은 기능입니다.

다만 사이드 스레드는 일시적(ephemeral)이라는 점을 기억할 필요가 있습니다. 프로젝트에서 장기적으로 유지하고 싶은 맥락이 있다면 반드시 메인 스레드에 다시 전달해야 합니다. 사이드 스레드는 시간이 지나면 오래된 상태가 되기 때문입니다.

또 다른 예가 있습니다. 앞에서는 사이드 스레드가 메인 스레드와 대화하는 모습을 봤습니다. 이 예에서는 서로 다른 두 메인 스레드가 대화하고 있습니다. 구체적으로 왼쪽에는 Codex가 이렇게 말하고 있습니다. “로컬 폼 빌더 프로젝트에서 로컬 스레드를 생성하는 것을 테스트해. 성공하면 앞으로 생성하는 모든 로컬 스레드의 기본 위치로 설정해. 특히 Chrome 또는 엔드투엔드 테스트의 경우에 말이야.”

여기서 일어나는 일은 원격 서비스에서 실행되고 있기 때문에 제 Chrome 브라우저에 접근할 수 없다는 것입니다. Codex가 로컬 호스트에 메시지를 보내고, Chrome이 설치되어 있는 것처럼 보인다는 사실을 확인합니다. 그런 다음 Chrome으로 테스트를 수행할 수 있습니다. 원격 세션이 로컬 세션과 함께 작동하도록 만들 수 있는 것입니다.

이것이 Codex가 수행한 테스트입니다. 클라우드에서 작업하는 동안, 제 노트북에서 로컬로, 새벽 3시에 제가 자고 있을 때 Codex는 Chrome을 열고 폼 생성 과정을 거쳐 엔드투엔드로 폼을 하나 만들었습니다.

서브에이전트(subagent)는 이런 장기 실행 작업에서도 특히 유용합니다. 맥락을 잘 분리해야 하기 때문입니다. 에이전트들이 서로 다른 작업에 집중할 수 있습니다. 좋은 예가 하나 있습니다. 애플리케이션을 만들고 있었는데 제가 살펴보니 반드시 모범 사례라고 하기는 어려웠습니다. 그래서 메인 스레드에 “별로 좋지 않다”고 메시지를 보냈습니다.

Codex는 “네, 동의합니다. 기술적으로는 더 깔끔하지만 여전히 좋지 않은 채팅 인터페이스입니다”라고 했습니다. 여기서 Codex가 한 일을 볼 수 있습니다. 서브에이전트에 메시지를 보냈습니다. 서브에이전트는 이미 생성되어 있었지만, 메인 에이전트가 그 서브에이전트에 메시지를 보낸 것입니다. 여기 메시지가 보입니다. “이 새로운 사용자 스크린샷과 지시 사항으로 검증 작업을 업데이트해.” 이런 식의 에이전트 간 통신(inter-agent communication)이 이루어진 것입니다.

그 후 Codex가 한 일은 이렇습니다. 제가 메시지가 아래쪽에 밀려 있는 스크린샷을 보냈고, 그런 상태를 원하지 않았기 때문에 Codex가 자체 테스트를 실행했습니다. 그리고 “Retrodex visible OK를 짧은 한 문장으로 보내”라고 했습니다. 그러자 그것을 보냈습니다. Codex 자체가 제 피드백을 검증하기 위해 QA 테스트를 수행한 것입니다.

이것은 실시간 QA의 예입니다. 메인 스레드가 목표 감사와 코드 리뷰 같은 여러 사이드 스레드를 생성하는 동시에 Slack으로도 정보를 전달했습니다. “Slack 스레드 URL 제공”이라고 되어 있는 이 스레드에서 제가 이런 업데이트를 모두 제공했습니다. 별도의 세션이 그 작업을 관리하고 있었습니다.

앞에서 목표에 대해 이야기했는데, 이것은 Codex가 목표를 위해 만든 대시보드입니다. 완료된 작업, 현재 진행 중인 작업, 아직 시작하지 않은 작업 등 여러 마일스톤을 볼 수 있습니다. 대시보드는 서로 다른 스레드가 무엇을 하고 있는지도 파악하게 해 주었습니다. 이 스레드는 메인 오케스트레이터였고, 커뮤니케이션 스레드가 있었으며, 한 스레드는 시각적 UX를 담당했고, 또 다른 스레드는 App Server 프로토콜을 관리하는 식이었습니다.

Codex는 더 개념적인 작업 흐름(workstream)도 만들었습니다. 인증(auth)을 위한 작업 흐름, 테스트를 위한 작업 흐름, UI 다듬기를 위한 작업 흐름이 있었습니다.

밤새 Codex가 막히는 경우도 있었습니다. Convex와 Vercel을 사용한 예에서 Codex는 이렇게 말했습니다. “인증이나 이러한 외부 서비스에 접근하는 데 필요한 ID가 핵심 경로에 없기 때문에 이 작업을 차단됨으로 표시했습니다.” 그래도 그 시점까지 할 수 있는 작업은 모두 수행했습니다. 스스로 차단됨으로 표시했기 때문에 그 상태가 UI에 나타났습니다.

저는 해당 항목을 선택하고 “Add to Side Chat”을 선택한 뒤 “무슨 일이 일어나고 있는지 설명해 줄래?”라고 말했습니다. 막 일어난 참이라 맥락을 몰랐지만 Codex가 막혔다고 알려 주고 있었기 때문에, 상황을 파악하려고 했습니다.

Codex는 “여기서 내가 막힌 상태를 해결하려면 무엇을 할 수 있는지 단계별로 설명해 줘”라고 했습니다. Vercel 정보와 Convex 정보를 제공할 수 있는 여러 방법을 제시했고, 저는 그대로 진행했습니다.

해당 항목을 선택하고 “그렇게 해”라고 말했습니다. 그러자 사이드 스레드가 메인 스레드에 CLI 로그인 흐름을 만들라고 전달했습니다. 저는 그것을 클릭해 인증했고, 원격 인스턴스에서 실행 중인 Codex에 제 Vercel 프로젝트를 관리할 수 있는 접근 권한과 적절한 권한을 부여했습니다.

Convex의 경우에는 배포 키가 있었습니다. 그것을 채팅에 붙여 넣고 싶지는 않았기 때문에 Codex에 안전하게 전달할 방법을 알려 달라고 했습니다. Codex는 제가 붙여 넣을 수 있는 Bash 코드를 제공했고, 그 코드를 사용해 원격 환경에 키를 설정할 수 있었습니다. 이처럼 원격 인스턴스에서 Codex와 협업하고, 여러 테스트를 수행하고, 권한을 관리하는 등의 작업이 가능했습니다.

이 전체 과정에서 실제로 무엇을 만들었는지 보겠습니다. Site 1에서 사이트를 만든 결과를 살펴보죠.

이것은 내부 폼 빌더입니다. 다시 설명하면, 폼 빌더용 기존 저장소(repository)가 있지만 제 내부 팀에 맞게 사용자 지정하고 싶었습니다. 저희는 아마 다섯 명 정도이고 SaaS에 돈을 쓰고 싶지 않기 때문에 자체 폼 빌더를 만들 수 있습니다.

새 초안을 생성합니다. 이름을 “AI Engineers Workshop”이라고 지정하고 “Hello” 등을 입력할 수 있습니다. Chrome 확장 프로그램에 이 작업을 시켜야 하지만, 여기서는 시연을 위해 직접 하겠습니다.

폼을 미리 본 다음 공유할 수 있습니다. 링크를 복사해 게시하면 공유 가능한 링크가 생깁니다. 링크를 열면 팀의 다른 사람이 작성할 수 있습니다. 다시 말하지만 이것은 Sites에서 호스팅되기 때문에 ChatGPT 워크스페이스에 접근할 수 있는 사람만 이 폼에 접근할 수 있습니다. 정말 유용한 점입니다. 그런 다음 모든 응답 등을 확인할 수 있습니다.

이것이 저희가 한 일입니다. 복잡한 작업을 요약하면 세 가지 프로젝트가 있었습니다. 하나는 Rust 백엔드가 있는 패키지를 다시 구현하고 싶었던 머신러닝 프로젝트였습니다.

또 하나는 그린필드 프로젝트로 라이브 Q&A 사이트를 처음부터 만드는 일이었습니다. 세 번째는 기존 오픈소스 프로젝트를 가져와 제 필요에 맞게 사용자 지정하는 일이었습니다. Codex는 이 경우들에서 작업을 완료할 수 있었습니다.

그 밑바탕에는 몇 가지 개념과 기본 요소(primitives)가 있습니다. 슬라이드로 돌아가 보겠습니다.

첫 번째는 압축(compaction)입니다. Codex가 7시간, 5시간 동안 작동한 것을 보셨고, 지금 다른 하나는 약 12시간 동안 실행 중인 것 같습니다. 여러 번 컨텍스트 윈도(context window)를 압축하고 있습니다.

이건 새로운 기술이 아닙니다. 2025년 11월, GPT-5.1-Codex-Max를 출시했을 때 우리는 압축(compaction)이라는 프로세스를 통해 여러 컨텍스트 윈도에 대해 모델을 네이티브하게 학습시켰고, 이것이 Codex가 이 작업을 정말 잘할 수 있게 해줍니다.

사람들이 압축에 대해 말한 몇 가지 예가 있습니다. “OpenAI가 사실상 압축 문제를 해결한 건가? 5.5와 Codex를 사용하면서 정말 많은 압축을 거치는 초장문 스레드에서도 거의 문제를 겪지 않았다.”

일본의 한 사용자는 이렇게 말했습니다. “사실 Codex는 압축 성능이 뛰어납니다. 그래서 같은 스레드에서 많은 작업을 해도 잊어버릴 가능성이 낮습니다. 그런 의미에서 좋은 내용만 기억하기 때문에, 어느 정도 토큰 효율성이 있는 것 같습니다.” 늘 그렇듯이 사람들은 이것을 꽤 멋지다고 생각합니다. 이 기능을 가능하게 하는 구체적인 기본 요소와 개념, 예를 들어 목표(goal)에 대해서는 Charlie가 좀 더 설명하도록 하겠습니다.

네, 고마워요, Gabe. 보신 것처럼 이미 15시간 동안 실행 중인 목표가 있고, 목표는 올바른 방식으로 사용할 수 있다면 대단히 강력한 기본 요소 중 하나라고 생각합니다.

처음 시도하는 사람들에게 제가 가장 많이 말하는 것 중 하나는, 모델이 언제 작업을 완료했는지 알 수 있도록 제시하는 기준을 매우 구체적으로 작성하라는 것입니다. 특히 그 기준은 가능한 한 검증 가능해야 합니다.

때때로 저는 Goal이 지니(genie) 같다고 느낍니다. 잘 작동할 때는 믿기 어려울 정도로 마법 같습니다. 잘 작동하지 않을 때는, 제가 원숭이 손(monkey’s paw) 상황에 들어온 것처럼 느껴질 때가 있습니다. 기술적으로는 제가 요청한 일을 했지만, 제가 예상한 방식과는 전혀 다르게 해냈기 때문입니다.

따라서 작업을 주면 모델은 실행을 시작합니다. 여러분이 제공한 성공 기준과 검증 가능한 기준에 따라 스스로를 계속 평가하고, 매번 이렇게 확인합니다. “이게 실제로 완료됐나?” 그리고 완료되지 않았다면 계속 진행해야 할까?

이런 방식은 매우 큰 프로젝트에 꽤 많은 활용 사례가 있습니다. 보시다시피 Tama는 40시간 동안 실행되는 /goal을 사용해 Doom을 네이티브 Swift 코드로 재구현했습니다. 이런 작업을 시도해 보고 싶다면 코드 마이그레이션, 대규모 리팩터링, 재시도 루프, 실험, 게임, 또는 상당히 상세한 사양을 바탕으로 앱을 완전히 원샷으로 만드는 작업도 가능합니다. Goal은 정말 대단하다고 생각합니다.

서브에이전트(subagent)도 있습니다. 여기서 조금 미리 보셨죠. Codex의 서브에이전트는 기본적으로 별도의 설정 없이 사용할 수 있습니다. 모델에게 “여기서 서브에이전트에 위임하는 것을 고려해 봐”라고 말할 수 있습니다. 하지만 직접 맞춤 설정할 수도 있습니다. 코드 리뷰어가 되어야 하는 서브에이전트가 있다면, 특정 프롬프트와 개발자 지침을 설정할 수 있습니다. 코드 리뷰어가 빠르게 실행되도록 경량 모델을 사용하게 하거나, 매우 철저하게 검토하도록 훨씬 더 지능적인 모델을 사용하게 하고 싶다면, 자체 subagents.toml 파일에서 이를 맞춤 설정할 수 있습니다. 이름도 지정할 수 있습니다. 무언가를 구현하기 위해 “코드 리뷰어에게 확인해 봐. 문서 조사자에게 확인해 봐”라고 말할 수 있습니다.

서브에이전트는 Codex에서 스레드 간 인계(thread-to-thread handoff)와 함께 작동할 수 있습니다. 스레드 간 인계는 상당히 새로운 기능입니다. 지난 2~3주 안에 출시한 것 같습니다. 이는 더 높은 수준의 추상화입니다. 둘 사이의 균형을 생각하는 방식은, 작업 위임이 사용자에게 보여야 하는지 아니면 모델에게만 보여야 하는지에 따라 나누는 것입니다.

우리는 서브에이전트부터 시작했는데, 작업이 주로 모델에게 보여야 하는 경우라고 생각했기 때문입니다. 하청업체에 일을 위임한다면 그들이 무슨 이야기를 하는지는 크게 신경 쓰지 않습니다. 그저 작업 결과가 돌아오는지만 확인하고 싶을 뿐입니다. 서브에이전트는 이런 경우에 잘 맞고, 모델은 언제 서브에이전트에게 넘겨야 하는지 판단하는 데 능숙합니다.

또한 컨텍스트를 분리해 유지합니다. 컨텍스트 윈도의 효율성을 높이기 위해 Codex에 도입한 다른 여러 도구와 달리, 서브에이전트는 컨텍스트를 분리하고 모델들이 서로 소통하도록 하는 기능입니다.

스레드 간 인계는 여러분이 계속 상황에 관여하고 진행되는 모든 일을 확인하고 싶을 때 유용합니다. 어쩌면 더 중요한 점은, 머릿속으로 이 두 스레드를 분리해 생각하고 있을 때 유용하다는 것입니다.

한 가지 예로, 주말에 저는 게임을 작업하면서 크리에이티브 디렉터 스레드를 두고 있었습니다. 서브에이전트를 사용할 수도 있었고, 그것도 잘 작동했을 겁니다. 하지만 저는 진행되는 여러 작업을 모두 보고 싶었고, 서브에이전트를 통해 그 일이 단순히 보이지 않는 곳으로 위임되는 것을 원하지 않았습니다.
