내가 모를 만한 것 / 처음 보는 것

  • LLM 위키 (LM Wiki / LLM Knowledge Wiki): Andrej Karpathy가 제안한 방식. 벡터 유사도 검색 대신 LLM이 인덱스 파일을 읽고 위키 링크를 따라가며 정보를 탐색.
  • hot cache: 최근 대화 요약 ~500단어를 hot.md로 유지. 매 대화마다 위키 전체를 재크롤하지 않아도 최신 맥락을 제공.
  • linting (위키 린팅): 위키 전체를 주기적으로 돌려 일관성 없는 데이터, 빠진 링크, 보강이 필요한 노드를 발견하고 웹검색으로 채우는 과정.
  • Obsidian Web Clipper: 크롬 확장으로 웹페이지를 바로 Obsidian 볼트로 저장. 기본 저장 폴더를 RAW로 설정해두면 자동으로 수집 파이프라인에 진입.
  • AI2027 (ai-2027.com): 영상에서 시연 예시로 사용된 장문 보고서. AI 2027년 전망을 다룬 글.
  • 볼트 폴더 구조: RAW/ (원본 투입) → wiki/ (Claude가 정리한 위키 페이지) → index.md (허브 인덱스) → log.md (작업 이력).
  • semantic search RAG: 벡터 임베딩 + 벡터DB + 청킹 파이프라인 기반 검색. LLM 위키와 대조적인 전통적 접근.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Karpathy의 원 트윗은 의도적으로 프롬프트를 모호하게 남겼다 — 각자 프로젝트에 맞게 커스터마이징하도록. Gist 주소: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
  2. 화자 본인은 유튜브 대본 36개를 한꺼번에 처리했고 소요 시간은 약 14분. 단일 AI2027 문서 처리는 약 10분, 결과 위키 페이지 23개 생성.
  3. AI2027 처리 후 생성된 항목: 위키페이지 23개, 소스 1개, 사람 6명, 조직 5개, AI 시스템 페이지 1개, 기술적 정렬·개념 등.
  4. 한 사용자가 파일 383개 + 회의 녹취 100개 이상을 압축 위키로 만들고 Claude 검색 시 토큰 사용량 95% 절감 달성.
  5. Obsidian Web Clipper 설정 시 기본 저장 위치(Clippings)를 RAW로 변경하는 것이 핵심 — 안 하면 자동 파이프라인에 안 들어감.
  6. CLAUDE.md가 필수: 프로젝트가 어떻게 돌아가는지, 어떻게 검색하고 업데이트하는지 Claude에게 설명하는 마크다운 파일.
  7. hot cache는 executive assistant 맥락에서 특히 유용. 유튜브 트랜스크립트 위키에서는 불필요.
  8. 린팅은 매일 또는 매주 돌릴 수 있으며, 위키가 자기 스스로 빈칸을 찾아 웹검색으로 메우는 자기완성 루프를 만든다.
  9. 벡터DB가 필요한 임계점: 수백 페이지까지는 LLM 위키로 충분, 수백만 문서부터는 전통 RAG가 유리 (2026년 4월 기준).
  10. claude 코드는 터미널보다 VS Code 내 터미널에서 쓰는 것을 화자가 선호 — 상태 표시줄·부가 기능 때문.

1. 데모 소개 — 지식 시스템이 어떤 모습인가

화자는 유튜브 영상 대본 36개를 정리한 Obsidian 볼트를 보여준다. 그래프 뷰에서 노드 하나하나가 영상·도구·기법이고, 백링크를 타고 이동하면 Claude Code, Perplexity, VS Code, MCP 서버, WF 프레임워크, 권한 우회 모드, 사람 검토 체크포인트 등 연결망이 보인다. 중요한 점은 이 관계를 수동으로 만든 게 아니라, Claude Code에게 "대본 전부 정리해줘"라고만 했다는 것이다.

개인 second brain도 별도로 운영 중: 사업·직원·분기 과제 등. 두 볼트를 합치거나 분리하거나, 다른 AI 에이전트에 연결하는 것도 가능.

2. Andrej Karpathy의 LLM 위키 아이디어

Karpathy가 X(트위터)에 올린 짧은 글이 수일 만에 엄청난 반응을 얻었다. 핵심 아이디어:

  • 데이터 수집: 원본 문서(PDF, 기사 등)를 Claude Code에 투입
  • 자동 정리·연결: Claude가 비교·정리 후 관계까지 맞춰 적절한 위치에 배치
  • 검색: 빈칸 노드 발견 → 직접 리서치해 채움
  • 지속성: 일반 AI 채팅은 대화 종료 시 지식이 사라지지만, LLM 위키는 지식이 은행 이자처럼 축적

X에서는 "게임 체인저", "지치지 않는 동료"라는 반응이 나왔다.

3. Obsidian 설치 및 볼트 구조 설정 (5분)

Obsidian은 완전 무료. 마크다운 파일을 시각적으로 보여주는 도구에 불과 — 이것이 핵심 (복잡한 인프라 불필요).

볼트 기본 구조:

MyWiki/
├── RAW/          ← 원본 자료 투입 폴더
├── wiki/         ← Claude가 정리한 위키 페이지들
│   ├── analyses/
│   ├── concepts/
│   ├── entities/
│   └── sources/
├── index.md      ← 허브 인덱스
├── log.md        ← 작업 이력 (Operation History)
└── CLAUDE.md     ← 프로젝트 설명 (Claude용)

CLAUDE.md는 필수: 프로젝트 목적, 검색 방법, 업데이트 방법을 Claude에게 설명.

4. Claude Code로 볼트 초기화

  1. Obsidian에서 새 볼트 생성 (예: DemoVault)
  2. VS Code 터미널에서 해당 폴더를 열고 Claude Code 실행
  3. Karpathy 원문 프롬프트를 복사 + 앞에 역할 지정 추가:

    "이제 당신은 LLM 위키 에이전트다. 이 아이디어 파일을 완전한 second brain으로 구현하라. CLAUDE.md를 만들고..."

  4. Claude가 폴더 구조 자동 생성 → Obsidian에서 실시간 확인 가능

Karpathy가 프롬프트를 의도적으로 모호하게 남긴 이유: 프로젝트마다 구조가 달라야 하기 때문. 유튜브용은 하위폴더 여러 개, 개인 second brain은 평평한 구조가 더 적합할 수 있음.

5. 문서 수집·처리 시연 — AI2027

Obsidian Web Clipper 설정: 1. Chrome에 Obsidian Web Clipper 확장 설치 2. 옵션 → Location → 기본 저장 위치를 Clippings → RAW로 변경 3. 원하는 웹페이지에서 확장 클릭 → 볼트 선택 → Add to Obsidian

AI2027(ai-2027.com) 문서를 RAW에 넣고 Claude Code에 지시:

"AI2027 글을 RAW에 넣었어. 이걸 가져와 정리해줘. 이 볼트는 AI 관련 리서치 공간이야."

Claude가 맥락 질문(강조 포인트, 세부도, 계획)을 던지고 → 처리 후 결과: - 약 10분 소요 - 위키 페이지 23개 생성 - 사람 6명, 조직 5개, AI 시스템 1개, 기술적 정렬·지정화·분석 개념 포함 - Obsidian 그래프 뷰에서 실시간으로 노드 생성 확인 가능

6. 검색 및 다용도 활용

활용 방법 3가지:

  1. 볼트 내 Claude 검색: 클로드를 해당 프로젝트에서 실행, 인덱스+위키를 참조해 검색
  2. 다른 프로젝트에 볼트 연결: CLAUDE.md에 위키 경로 명시 → 해당 프로젝트의 Claude가 위키를 참조
  3. Executive Assistant 연결: 비즈니스 지식 볼트를 EA Claude에 연결 — "모르면 허브레인 볼트로 가서 위키 읽어"

화자 본인의 경우, 기존에는 프로젝트 안에 컨텍스트 파일을 넣어뒀는데, 볼트 방식으로 바꾼 후 실제 토큰 사용량이 줄었다고 함.

7. Hot Cache

  • 파일명: hot.md
  • 크기: 약 500단어/500자
  • 내용: Claude와 최근 나눈 대화 요약, 최신 업데이트 내용
  • 용도: 전체 위키를 매번 크롤하는 대신 최신 맥락만 빠르게 제공
  • 유튜브 트랜스크립트 볼트에서는 불필요, Executive Assistant 볼트에서 핵심

8. 린팅 (Linting)

Karpathy가 제안한 기능. 주기적으로 실행: - 위키 전체 건강 점검 → 일관성 없는 데이터 찾기 - 빠진 데이터 → 웹검색으로 자동 보완 - 흥미로운 연결 후보 → 새 글 아이디어 발굴

결과적으로 지식 베이스가 외부 입력 없이도 스스로 성장하는 루프를 형성.

9. LLM 위키 vs 시맨틱 서치 RAG 비교

항목 LLM 위키 시맨틱 RAG
검색 방식 인덱스 읽기 + 링크 탐색 벡터 유사도 검색
관계 이해 링크 기반 → 깊은 맥락 "이 청크가 비슷해 보임"
인프라 마크다운 파일만 임베딩 모델 + 벡터DB + 청킹 파이프라인
비용 토큰 비용만 (거의 무료) 지속 임베딩 + 저장 비용
유지보수 린팅 + 문서 추가 변경 시 재임베딩 필요
확장 한계 수백 페이지까지 효율적 수백만 문서도 가능
2026년 기준 추천 개인·팀 규모 지식 베이스 기업 규모

여기 보시면 서로 다른 노드와 여러 패턴이 나타납니다. 더 확대해보면 이 작은 점 하나하나가 무엇을 뜻하는지 알 수 있습니다. 예를 들면 이건 제 영상 중 하나인 1만 달러짜리 에이전팅 워크플로우입니다. 태그도 있고 영상 링크도 있고 원본 파일도 있습니다. 이 영상이 뭔지, 핵심 포인트가 뭔지도 설명해줍니다. 가장 멋진 건 백링크를 따라가면서 원하는 곳까지 갈 수 있다는 점입니다. WF 프레임워크로 가는 백링크도 있고, Claude Code로 가는 백링크도 있고, 제가 말한 여러 도구로 가는 백링크도 있습니다. Perplexity, VS Code, 네이선 허크 (Nate Herk), 그리고 WF2 프레임워크, 권한 우회 모드, 사람 검토 체크포인트 같은 기법도 들어있습니다.

이게 계속 쌓이면 각 노드 사이의 패턴과 관계가 보이기 시작합니다. 각 스킬과, 제가 유튜브에서 언급한 모든 MCP 서버 사이의 패턴과 관계가 보이기 시작합니다. 이런 시스템이 갖춰졌으니 아주 효율적으로 검색할 수 있습니다.

더 놀라운 건 제가 그냥 이렇게 말했다는 겁니다: "Claude Code, 최근 영상들 대본을 가져와서 전부 정리해줘." 정말로 관계를 하나하나 직접 만들 필요가 전혀 없었습니다. 그냥 알아서 다 정리해줬거든요.

그리고 더 작은 버전도 있는데 이건 제 개인 브레인에 가깝습니다. 제 개인적인 삶에서 일어나는 일들 — 사업, 유튜브 채널, 직원들, 2분기 과제 같은 것들. 지식 시스템 하나가 있는 셈이고, 이걸 합칠 수도, 따로 둘 수도 있습니다. 또 지식 시스템을 계속 더 만들고, 이 맥락이 필요한 다른 AI 에이전트들에 연결할 수도 있습니다.

그래서 Andrej Karpathy가 LLM 지식 베이스에 대한 짧은 글을 올리면서 자기가 이걸 어떻게 쓰는지도 설명했습니다. 며칠 만에 X에서 엄청난 반응을 얻었습니다. 간단히 살펴보고, 이어서 이걸 거의 5분 만에 설정하는 방법을 보여드리겠습니다.

제가 최근에 아주 유용하다고 느낀 건, LLM으로 관심 있는 주제별 개인 지식 베이스를 만드는 겁니다. 단계도 여러 개인데, 첫 번째는 데이터 수집입니다. 기본적으로 원본 문서를 넣는 단계입니다. PDF를 Claude Code에 넣으면 나머지는 Claude Code가 알아서 처리합니다.

그는 IDE로 Obsidian을 씁니다. 사실 그렇게 획기적인 건 아닙니다. Obsidian은 마크다운 파일을 시각적으로 보여줄 뿐입니다. 이 Obsidian 프로젝트에 유튜브 대본 관련 자료가 전부 들어있습니다. 원본 유튜브 대본들이 있고, 위키도 있습니다. Claude Code가 유튜브 대본으로 만든 여러 폴더가 들어있죠.

Q&A 단계에서는 유튜브나 리서치에 대해 질문하면, 위키 전체를 훨씬 효율적으로 훑어서 아주 똑똑한 답을 줍니다. 그는 이렇게 말합니다: "처음엔 Pen&Edge [?펜셀에지, 아마도 Perplexity나 특정 도구]까지 써야 하나 했는데, LLM이 꽤 잘해주더라." 모든 문서의 인덱스 파일과 간단한 요약을 꽤 잘 자동으로 관리해줍니다. 이 정도 규모에서는 중요한 관련 데이터를 꽤 쉽게 읽어냅니다. 지금은 기사 100개 정도.

핵심은 원본 데이터를 Claude Code에 넘긴다는 겁니다. 그걸 비교하고 정리한 다음 관계까지 맞춰서 알맞은 곳에 넣어줍니다. 그러면 무엇이든 질문할 수 있죠. 노드나 관계에서 비어있는 부분을 찾아주고, 직접 리서치해서 그 빈칸까지 메워줍니다.

자, 그럼 이게 왜 중요한 걸까요? 일반적인 AI 채팅은 휘발성이 있어서 대화가 끝나면 지식도 사라지기 때문입니다. 하지만 Karpathy의 LLM 위키를 쓰는 이 방식은 지식이 은행 이자처럼 쌓이게 만듭니다. X에서는 이걸 게임 체인저라고 부릅니다. AI가 모든 걸 기억하는 지치지 않는 동료처럼 느껴지고, 정리도 잘 유지되기 때문입니다. 설정하는 데 5분이면 됩니다.

팬시한 벡터 데이터베이스도, 임베딩도, 복잡한 인프라도 필요 없습니다. 그냥 마크다운 파일이 들어있는 폴더 하나면 끝입니다. 볼트 하나만 있으면 됩니다. 이 예시에서는 이름이 MyWiki입니다. RAW 폴더에 모든 자료를 넣습니다. 그리고 wiki 폴더가 있는데, LLM이 RAW에서 가져온 걸 위키로 정리해 넣는 곳입니다. 인덱스와 로그도 따로 있습니다.

제 유튜브 대본 볼트의 인덱스를 보시면 여러 도구가 있고, 클릭하면 바로 해당 페이지로 이동합니다. 그 아래에는 다양한 기법과 에이전트 팀, 서브 에이전트가 있습니다. Permission modes와 WF2 프레임워크도 있습니다. MCP 서버, Nex [?], 바이브 코딩 같은 여러 개념과 자료도 정리되어 있습니다. 사람이나 비교 항목이 생기면 그것들도 인덱스에 들어갑니다. 그리고 Operation History인 로그도 있습니다.

유튜브 프로젝트에서는 아직 로그가 크지 않습니다. 영상 36개를 한꺼번에 돌렸기 때문입니다. 하지만 이제 새 영상이 생길 때마다 가져와서 위키에 넣으라고 시킬 수 있습니다.

그리고 당연히 CLAUDE.md가 필요합니다. 프로젝트가 어떻게 돌아가는지, 어떻게 검색하는지, 어떻게 업데이트하는지 설명해주는 마크다운입니다.

비용 측면에서도 크고, 토큰 효율과 장기적인 가치도 큽니다. 한 사용자가 흩어진 파일 383개와 회의 녹취 100개가 넘는 걸 압축된 위키로 만들고, Claude로 검색할 때 토큰 사용량을 95% 줄였습니다.

또 정말 좋은 점이 하나 더 있습니다. Git 저장소를 복사해 와야 하는 것도 아니고, 복잡한 설정도 없다는 점입니다. 그냥 Claude Code에게 Andrej Karpathy의 이 아이디어를 읽고 구현하라고 말하면 됩니다.

X에서는 이런 식으로 2026년에 에이전트형 소프트웨어와 제품이 만들어질 거라고들 이야기합니다. 큰 아이디어만 주면 알아서 만들어준다는 거죠. Karpathy도 이렇게 말했습니다: "이 프롬프트를 일부러 좀 모호하게 남겨뒀습니다. 여러분이 프로젝트에 맞게 직접 바꿔 쓸 수 있도록요."

좋습니다. 방금 보여드린 게 원래 트윗이고, 그 다음에 그가 이렇게 덧붙였습니다: "이건 바이럴이 됐네요? 그래서 아이디어를 간단히 정리해보겠습니다." 이걸 열어보면 어떻게 작동하는지, 왜 이런 아키텍처와 인덱싱이 필요한지에 대한 핵심 설명이 나옵니다.

그런데 먼저 할 준비 단계가 하나 있습니다. 필수는 아니지만, 관계를 보기 좋은 프론트엔드가 있으면 좋아서 Obsidian을 설치할 겁니다. 완전히 무료인 도구입니다. 운영체제에 맞는 걸 받아서 설치하고 앱을 실행하면, 볼트 관리로 가서 새로 만들고 이름만 정하면 됩니다. 저는 이걸 Demo Vault라고 부르겠습니다. 데스크톱에 저장하고, 이 볼트를 만들겠습니다.

그 다음에는 Claude Code를 실행합니다. 저는 VS Code 안에서 터미널로 실행하는 걸 선호합니다. 상태 표시줄도 볼 수 있고 기능도 조금 더 많아서요. Claude Code를 열고, Karpathy가 올린 LLM 위키 아이디어를 전부 복사해서 붙여넣습니다. 그러니까 이게 바로 프롬프트예요. 그걸 보내기 전에, 이것도 먼저 넣을 거예요: "이제 당신은 LLM 위키 에이전트다. 이 아이디어 파일을 그대로, 재완전한 second brain으로 구현하라. CLAUDE.md를 만들고..." 즉, 방금 Karpathy에게서 얻은 이 아이디어로 무엇을 해야 하는지 알려주는 겁니다.

오른쪽에는 Claude Code가 돌아가고 있고, 왼쪽에는 Obsidian 볼트가 있어요. 방금 두 폴더가 만들어진 게 보이죠? 위키도 만들어졌습니다. 기본으로는 폴더 4개를 넣어놨어요. Analyses, Concepts, Entities, Sources가 들어갔습니다.

이제 내용을 채워가면서 이 구조가 정말 맞는지 다시 얘기해볼 수 있어요. 제 개인 second brain에서는 위키가 그냥 마크다운 파일뿐이에요. 구조가 따로 없죠. Karpathy도 이렇게 말했어요: "가끔은 정말 단순하고 평평하게, 즉 하위 폴더 없이, 너무 과하게 정리하지 않는 방식을 좋아한다고요." 그런데 제 유튜브 대본 예시에서는 서로 다른 하위 폴더들이 있었죠. 그리고 CLAUDE.md도 만들어졌습니다. 인덱스와 로그를 만들고 위키 안에 몇 개 폴더도 만들어놨어요.

이제 이렇게 말하네요: "자, 한번 해보자고요. 첫 번째 소스를 RAW 폴더에 넣고 가져오라고 말하라는 거예요." 좋아요. 저는 지금 AI2027이라는 웹사이트에 와있어요. 아직 안 읽어보셨다면 꽤 흥미롭게 읽을만한 글이에요. 이걸 제 볼트에 넣고 싶다고 해볼게요.

그냥 페이지 전체를 복사할 수도 있어요. 아니면 Obsidian 확장 프로그램을 쓰면 됩니다. 웹에서 바로 글을 가져와서 볼트에 넣을 수 있습니다. 이 확장 프로그램은 Obsidian Web Clipper예요. 크롬에 추가하면 됩니다. 원하는 글에 들어가서 확장 프로그램을 클릭하고, Obsidian Web Clipper를 연 다음, 그냥 볼트에 넣으면 됩니다. 여기서는 RAW로 설정해야 해요. 실제로 들어갈 폴더가 거기거든요. 그 다음 Add to Obsidian을 누르고 Obsidian을 열면 됩니다.

이제 RAW 섹션을 보면 AI2027 소스가 들어와 있어요. 클로드 코드를 열고 이렇게 말할 거예요: "방금 AI2027이라는 글을 RAW에 넣었어요. 이걸 가져와 정리해주실 수 있나요? 참고로 이 프로젝트는 제 second brain 용도예요. 여기에는 제가 배우고 싶은 글이랑 알고 있는 것들을 다 넣을 거예요."

Claude는 이 글을 읽으면서 위키 어디에 넣을지 판단합니다. 그냥 MD 파일 하나로만 만들지는 않아요. 5개를 만들 수도 있고 10개를 만들 수도 있어요. 만들어진 각 섹션끼리 서로 연결도 생길 거예요. 즉, 나름대로 청킹을 하고 있는 셈이죠.

참고로 Obsidian Web Clipper 설정에서 옵션을 열어보면 기본으로 파일이 저장되는 위치를 바꿀 수 있어요. Location 섹션에 있습니다. 기본값은 Clippings인데, 그냥 RAW로 바꿔주세요.

그러면 Claude가 여러 질문이 돌아와요. 예를 들면, "이 글의 핵심 요점은 이렇습니다. 이 글에서 뭘 강조하고 싶나요? 초점은 뭐죠? 어느 정도까지 세세하게 볼 건가요?" 저는 이렇게 답해요: "AI가 어디로 가는지 보는 게 제 관심사예요. 이 볼트에 만드는 이 프로젝트는 기본적으로 AI 관련 리서치를 쏟아넣는 제 공간이 될 거예요. 이걸 잘 정리해줘서 내가 검색도 할 수 있고 생각도 계속 이어갈 수 있게 해주세요."

저는 여기서 그래프 뷰로 바꿔볼 텐데, 위키 파일들이 하나씩 만들어지는 과정을 보면 재미있을 것 같아요. 관련된 연결들이 전부 만들어질 거고, 그걸 실시간으로 볼 수 있습니다.

이 인제스트(ingestion)에는 약 10분 정도 걸렸습니다. 위키페이지 23개를 만들었고: 소스 1개, 사람 6명 (Eliezer, Thomas, Daniel 같은 이름들), 조직 5개, AI 시스템 페이지 1개, 기술적 정렬·지정화·분석 같은 개념도 들어있습니다.

참고로 제 유튜브 대본 36개를 한꺼번에 올렸을 때는 약 14분 걸렸습니다.

그럼 이제 궁금한 건 여기서 뭘 하느냐는 거죠. 이 환경 안에서 바로 검색할 수도 있고, 다른 곳에서 검색할 수도 있습니다. 예를 들어 제 유튜브 프로젝트에서는 이 볼트에 있는 채로 Claude에게 질문합니다. 또 필요하면 다른 프로젝트를 이 폴더에 연결할 수도 있습니다.

제 second brain에는 회의 녹음, 클리퍼 채널, 요약 같은 것들을 다 넣어두는데, 이걸 Executive Assistant에 쓰고 싶습니다. 제 Executive Assistant의 CLAUDE.md를 보면 위키패스가 있는 걸 볼 수 있습니다. 제 이야기나 제 비즈니스에 대해 아직 모르는 게 있으면 허브레인(Hub Brain [?]) 볼트로 가서 위키를 읽는 방식입니다. 인덱스도 읽을 수 있고, 도메인 서브인덱스도 읽을 수 있고, 전부 검색할 수도 있습니다. 정말 필요할 때만 위키를 읽으라고 했습니다. 굳이 안 읽어도 되는 작업들도 있으니까요.

혹시 제 Executive Assistant 설정 영상을 보신 분들은 아시겠지만, 예전에는 프로젝트 안에서 컨텍스트 파일로 이렇게 했습니다. 그런데 이 방식으로 바꾸고 나서는 이 프로젝트에서 실제로 쓰는 토큰 수가 줄어드는 걸 봤습니다.

Hot cache 얘기를 하자면, 제 유튜브 쪽에는 이게 없었습니다. 하지만 허브레인으로 가면 hot.md가 있는 걸 볼 수 있습니다. 대략 500단어 또는 500자 정도를 저장하는 캐시인데, Claude와 방금 나눈 최신 정보나 최근 대화 같은 걸 담아둡니다. 제 Executive Assistant 맥락에서는 이게 정말 유용합니다. 여러 위키 페이지를 일일이 크롤링하지 않아도 되게 해주니까요. 하지만 유튜브 대본 프로젝트 같은 경우에는 hot cache가 크게 필요하지 않습니다.

그리고 제가 언급만 하고 자세히는 안 한 게 하나 더 있는데, 바로 린팅(linting)입니다. Karpathy는 위키 전체의 건강 점검을 돌려서 일관성 없는 데이터를 찾고, 빠진 데이터를 웹검색으로 메우고, 새 글 후보가 될 만한 흥미로운 연결도 찾는다고 말합니다. 그러니까 매일이든 매주든 원할 때 린트를 돌려서 모든 게 확장 가능하고 올바른 구조로 정리되어 있는지 확인해주는 겁니다. 심지어 다시 와서 "이걸 완전히 이해하지 못하겠어요. 조금 더 정보를 주실 수 있나요?"라고 말할 수도 있습니다.

그래서 마지막으로 다루고 싶은 질문은, 이게 시맨틱 서치 RAG를 없애버리느냐는 겁니다. 답은 아니지만 어느 정도는 맞습니다. 프로젝트의 목표와 컨텍스트의 목표, 그리고 얼마나 많은 컨텍스트를 갖고 있느냐의 문제입니다.

그래서 Claude Code로 간단한 비교표를 하나 만들었습니다. 카우퍼시의 [?Karpathy의] LLM 지식 아이디어를 잔뜩 넣어두고, 최대한 쉽게 설명해달라고 했어요. 데이터베이스 대신 잘 정리된 마크다운 파일만 LLM에게 주는 방식이고, 여기서는 실제 시맨틱 서치 RAG와 비교하고 있습니다.

즉, 유사도 검색이 아니라 인덱스를 읽고 링크를 따라가며 찾는 방식입니다. 그래서 단순히 "이 청크들이 비슷해 보이네"가 아니라, 링크라서 관계를 더 깊이 이해하게 됩니다.

인프라 관점에서는 말 그대로 마크다운만 있으면 됩니다. Obsidian도 필요 없습니다. 이 마크다운 파일들만 있으면 됩니다. 반면 시맨틱 서치를 쓰려면 임베딩 모델, 벡터 데이터베이스, 청킹 파이프라인이 필요합니다.

비용 측면: LLM 위키 쪽은 거의 공짜 (토큰 비용 정도). 반면 RAG 쪽은 지속적인 임베딩과 저장 비용이 들 수 있습니다. 유지보수할 때도 그냥 린트 돌리고 정리하고 글을 더 추가하면 됩니다. 무언가 바뀌면 다시 임베딩하는 대신 그냥 컨텍스트를 더 넣어주면 됩니다.

하지만 지금 LLM 위키의 약점은, 당연히 기업 규모로 크게 확장되기 어렵다는 겁니다. 결국 파일 묶음일 뿐이니까요. 인덱스가 잘 된 수백 페이지 정도라면 LLM 위키 그래프로 충분합니다. 하지만 문서가 수백만 개로 늘어나면, 적어도 2026년 4월 기준으로 지금의 모델 상태를 생각했을 때는, 전통적인 RAG 파이프라인을 쓰는 쪽이 좋습니다.
