큰 그림: 자유롭게 떠도는 AI가 아니라 정해진 작업대

이 발표는 Uber에서 만들었다는 디버깅 에이전트 Debug Assist를 다룬다. 디버깅은 프로그램이 왜 잘못 작동했는지 원인을 찾고 고치는 일이다. 실제 장애에서는 오류 메시지가 불명확하고, 코드·로그·설정·담당 팀이 흩어져 있어 출발점부터 찾기 어렵다. 발표자는 Uber에서 Healthline과 Wisdom을 통해 엔지니어에게 연간 거의 5만 건의 문제가 배정되고, 평균 해결 시간이 거의 28일이라고 설명한다.

Debug Assist의 핵심은 AI에게 “알아서 고쳐”라고 맡기는 것이 아니다. 먼저 어떤 순서로 일해야 하는지 정한 하네스, 즉 반복 작업을 붙잡아 주는 공통 실행 틀을 만든다. 이 틀 안에서 일반 프로그램이 데이터를 가져오고 줄이며, 언어 모델은 분류·원인 추론·수정처럼 판단이 필요한 부분만 맡는다. 마지막에는 테스트와 개발자 검토를 거쳐야 수정안이 실제 변경으로 이어진다.

읽는 법: 화면 폭과 관계없이 위에서 아래로 읽는다. 각 아래 화살표는 다음 단계로 넘어가기 위한 입력이 준비된다는 뜻이다. 이 그림은 처리량을 나타내는 수치 그래프가 아니라 발표 내용을 정리한 개념 지도다.

왜 디버깅이 어려운가

사용자가 보는 것은 “화면이 하얗다”, “앱이 멈춘다”, “배터리가 빨리 닳는다” 같은 증상이다. 그러나 원인은 다른 코드 모듈, 외부 라이브러리, 네트워크, 인프라, 잘못 배포된 기능 중 어디에든 있을 수 있다. 큰 공동 코드 저장소에서는 문제를 일으킨 코드와 담당 팀까지 찾아야 한다.

Uber의 Wisdom은 직원과 베타 테스터가 앱 안에서 버그를 신고할 때 자연어 설명, 화면, 앱 버전, 운영체제, 도시와 여러 로그를 함께 수집한다고 발표자는 설명한다. Healthline은 충돌, 멈춤, 화면 끊김, 성능 저하를 자동으로 감지하며 스택 트레이스와 크래시 덤프도 수집한다. 스택 트레이스는 오류가 발생하기 전 어떤 코드 호출을 거쳤는지 보여 주는 기록이다.

첫 사례에서 한 개발자는 Uber 앱이 배터리의 거의 30%를 사용하며 휴대전화가 뜨거워진다고 신고했다. 첨부 화면에는 29%가 표시됐다. 발표에 따르면 약 20분 뒤 Debug Assist는 앱이 17분 동안 백그라운드에 있었는데도 특정 코드 경로가 계속 반복 실행되어 CPU와 배터리를 사용했다는 원인과 수정안을 제시했다.

두 번째 사례는 푸시 알림을 빠르게 눌렀을 때 앱이 충돌한 P1 문제다. Debug Assist가 원인 코드와 수정안을 만들었고, 발표자는 이 문제가 기능의 5% 배포 단계에서 발견되어 같은 날 수정·배포됐다고 말한다.

정해진 일과 AI가 판단할 일을 나눈다

모든 단계를 언어 모델에 맡기면 이미 알고 있는 API 호출에도 시간과 모델 비용이 들고, 너무 많은 로그가 입력에 섞인다. 따라서 Debug Assist는 결과가 정해진 작업과 해석이 필요한 작업을 분리한다.

읽는 법: 넓은 화면에서는 왼쪽의 정해진 작업과 오른쪽의 AI 판단을 비교한다. 좁은 화면에서는 위 카드가 정해진 작업, 아래 카드가 AI 판단이다. 어느 배치에서도 “확실한 일은 일반 코드로, 해석이 필요한 일은 모델로”라는 대조가 같다.

원인 분석 노드는 먼저 Uber 자체 문제인지, 외부 라이브러리·인프라·네트워크 문제인지 분류한다. 정보가 더 필요하면 여러 내부 도구를 연결하는 표준 통로인 MCP 연결을 통해 로그, 분산 추적, 사고 정보를 조회한다. 이후 세션의 사용자 행동을 시간순으로 복원하거나 충돌과 앱 버전의 관계를 찾는 하위 에이전트들이 병렬로 분석하고 결과를 합친다.

발표자는 원인 분석에는 비교적 낮은 모델인 Sonnet과 제한된 대화 횟수를 사용한다고 말한다. 20회를 넘겨도 해결하지 못하면 잘못된 방향으로 파고들 가능성이 높다고 본다. 반면 방대한 코드에서 수정 위치를 찾는 단계에는 Opus와 더 많은 최대 실행 횟수를 배정한다. 즉, 모델의 이름보다 업무 난도, 입력 범위, 허용 비용과 실패 신호에 맞춰 자원을 다르게 쓴다.

수정만 만들지 않고 완화와 검증까지 연결한다

수정 노드는 먼저 기능 플래그와 장애의 상관관계를 살핀다. 기능 플래그는 앱을 다시 크게 배포하지 않고도 특정 기능을 켜고 끌 수 있는 스위치다. 강한 관련성이 확인되면 해당 기능을 되돌려 피해를 먼저 줄이고, 영구 수정은 뒤에서 진행할 수 있다.

그다음 검증 단계에서는 가장 짧고 단순한 재현 방법부터 고른다. 단위 테스트로 재현할 수 있으면 단위 테스트를 사용하고, 필요하면 통합·컴포넌트 테스트로 넓힌다. 코드 수준에서 재현하기 어려운 환경 문제라면 시뮬레이터나 에뮬레이터를 사용한다. 발표의 질의응답에서는 낮은 네트워크 신호에서만 발생한 문제를 예로 들었다. 사용자 로그에서 확인한 네트워크 강도, 배터리 상태, 기능 플래그 조건을 실행 환경에 맞추고 앱 파일을 빌드해 반복 시험했다고 설명한다. 반복 횟수에는 고정된 제한이 있다.

읽는 법: 위에서 아래로 진행한다. 완화는 영구 수정과 같지 않으며, 검증을 통과했다고 자동 병합되는 것도 아니다. 최종 변경은 개발자 검토 대상으로 전달된다.

뼈대는 공유하고 전문 지식은 실행할 때 불러온다

Debug Assist의 기본 단계는 고정되어 있지만, Android 문제를 고치는 법이나 좋은 PR을 작성하는 법 같은 지식은 스킬과 플러그인으로 분리된다. 발표자는 공통 하네스를 제공하고 각 팀이 자기 분야의 전문 지식을 붙이는 구조라고 설명한다.

발표 시점에는 거의 8개의 에이전트가 5개 모노레포에서 하나의 코드베이스를 공유한다고 한다. 공통 Python 코드는 PEX 바이너리로 패키징되어 Artifactory에 올라가고, 에이전트 유형에 따라 필요한 바이너리, Docker 실행 환경, 파이프라인, 스킬과 플러그인을 실행할 때 가져온다. 거의 3천 개라는 플러그인을 전부 모델에 넣지 않고 에이전트 유형으로 범위를 제한한다.

개발자는 결과를 받은 뒤 작은 코드 변경을 요청하는 diff fixer, 원인 분석에 질문하거나 교정하는 Ask AI, 준비된 환경을 로컬 또는 원격 컴퓨터에서 여는 기능을 사용할 수 있다. 발표자는 개발자의 교정이 프롬프트와 스킬을 개선하는 피드백으로 이어진다고 설명한다.

발표된 성과와 아직 남은 경계

읽는 법: 넓은 화면에서는 왼쪽부터 지표를 비교하고, 좁은 화면에서는 위에서 아래로 읽는다. 카드 크기는 성과의 크기를 뜻하지 않는다. 모두 발표자가 말한 값이며 동일한 분모나 평가 방법을 쓴다는 정보도 없다.

정확도 50%는 Debug Assist의 원인 분석이 최종 개발자 수정과 정확히 일치한 비율로 설명된다. 발표자는 남은 50% 중 거의 40%도 올바른 모듈·파일·방향까지는 갔다고 말하지만, 이것이 전체의 40%인지 남은 절반의 40%인지 문장 해석에 주의해야 한다. 또한 정확도를 이상적으로 100%까지 높이겠다는 말은 현재 성과가 아니라 앞으로의 목표다.

수량 범위에도 확인되지 않은 부분이 있다. 앞에서는 Wisdom과 Healthline을 통해 연간 거의 5만 건이 엔지니어에게 배정된다고 했지만, 뒤에서는 Debug Assist가 매달 거의 9천 건을 처리한다고 말했다. 반복 분석, 다른 입력원, 집계 단위의 차이인지 설명되지 않아 두 수치를 같은 사건 수로 직접 비교할 수 없다.

발표자는 현재 고유 하위 에이전트가 대략 30개이며, 분야별 팀이 직접 확장하는 구조를 만들어 “다음 반기 말”에는 약 1만 개까지 늘어날 것으로 전망했다. 1만 개는 현재 운영 수치가 아니라 계획에 가까운 전망이다.

여기까지만 이해하면 충분

  • Debug Assist의 핵심은 거대한 모델 하나가 아니라 수집 → 제한된 추론 → 완화·수정 → 검증 → 사람의 검토를 고정한 하네스다.
  • 데이터 조회처럼 결과가 정해진 일은 일반 코드가 맡고, 분류·원인 추론·수정처럼 판단이 필요한 일만 언어 모델이 맡는다.
  • 입력 범위, 최대 실행 횟수, 테스트와 개발자 검토가 에이전트의 비용과 잘못된 방향을 제한한다.
  • 발표 수치는 가능성을 보여 주지만 집계 범위와 평가 방법이 충분히 공개되지 않았으므로 독립 검증된 일반 성능으로 확대하면 안 된다.

새벽에 “앱이 뜨겁고 배터리를 많이 쓴다”는 짧은 신고가 들어온다. 시스템은 같은 시점의 앱 상태와 로그를 모으고, 반복 실행된 코드 경로를 근거와 함께 찾는다. 수정안을 만든 뒤 재현 테스트와 개발자 검토를 거쳐야 실제 변경 후보가 된다.

비유와 깨지는 지점

응급실의 공통 진료 절차와 전문과 협진

접수 단계는 환자 정보와 검사 결과를 정해진 방식으로 모으고, 전문의들은 각자 다른 원인 후보를 살핀다. 모든 전문의에게 모든 기록을 던지는 대신 필요한 정보만 보내고, 결과를 합쳐 다음 조치를 결정한다. 공통 하네스는 진료 절차, 하위 에이전트는 전문과, 로그와 테스트는 검사 결과에 대응한다.

비유가 깨지는 지점: 소프트웨어 에이전트는 코드와 실행 기록을 직접 검색하고 수정안인 PR까지 만들 수 있다. 환자 진료의 위험·책임·불확실성과 소프트웨어 검증을 같은 수준으로 간주해서는 안 된다.

왜 Debug Assist는 로그 수집부터 수정까지 모든 단계를 하나의 LLM에 맡기지 않는가?

모범 답안 보기

알려진 API에서 데이터를 가져오고 로그를 파싱하는 일은 일반 코드로 더 예측 가능하게 처리할 수 있다. 이 단계까지 LLM에 맡기면 입력이 불필요하게 커지고 지연과 비용이 증가한다. 따라서 결정적 작업은 코드로 고정하고, 분류·원인 추론·수정처럼 판단이 필요한 부분에만 LLM을 사용한다.

2. 대조

즉시 완화를 위한 기능 플래그 롤백과 근본 수정은 어떻게 다른가?

모범 답안 보기

기능 플래그 롤백은 의심되는 기능을 끄거나 되돌려 사용자 피해를 먼저 줄이는 조치다. 근본 수정은 문제를 만든 코드와 조건을 찾아 변경하고 검증하는 일이다. 롤백으로 증상이 멈춰도 코드의 원인이 제거됐다고 단정할 수 없다.

3. 적용

새로운 자동화에 이 구조를 적용한다면 어떤 일을 고정 코드로 두고 어떤 일을 모델에 맡겨야 하는가?

모범 답안 보기

먼저 입력과 출력이 명확하고 기존 API로 반복 가능한 수집·정규화·검증 작업을 고정 코드 후보로 둔다. 여러 증거를 비교하거나 원인 후보를 세우는 작업만 모델 후보로 둔다. 모델 단계에는 입력 범위, 최대 실행 횟수, 근거 표시, 실패 시 사람에게 넘기는 조건을 함께 정의해야 한다.

이번 글의 통찰

1. 에이전트의 신뢰성은 모델보다 작업 경계에서 시작된다

  • [원문] 발표자는 데이터 수집을 결정적 노드로 두고, RCA와 수정에 서로 다른 모델과 최대 실행 횟수를 배정했다고 설명한다. 수정 뒤에는 테스트와 개발자 검토가 이어진다.
  • [해석] 좋은 에이전트는 모든 일을 잘하는 모델이 아니라, 확실한 일과 불확실한 일을 분리하고 불확실성이 커지면 멈추도록 설계한 시스템에 가깝다.
  • [경계] 발표는 내부 평가 설계, 실패 유형별 비율, 잘못된 수정이 검증을 통과한 사례를 공개하지 않는다. 이 구조가 다른 조직에서도 같은 성과를 낸다고 단정할 수 없다.

2. 확장은 모든 지식을 한곳에 넣는 것이 아니라 필요한 범위를 늦게 선택하는 것이다

  • [원문] 공통 하네스는 유지하되 팀별 스킬과 플러그인을 실행 시점에 불러오며, 거의 3천 개의 플러그인을 전부 컨텍스트에 넣지 않는다고 설명한다.
  • [해석] 확장성은 지식의 총량보다 작업마다 필요한 지식과 도구를 얼마나 좁게 선택하는지에 달려 있다. 공통 실행 규칙과 분야별 전문 지식의 소유권도 분리할 수 있다.
  • [경계] 현재 고유 하위 에이전트는 약 30개라는 설명과 “다음 반기 말 약 1만 개”라는 전망은 시행 상태가 다르다. 1만 개는 달성된 운영 규모가 아니며, 관리 비용과 품질 유지 방법도 제시되지 않았다.

3. 성과 숫자는 분모와 평가 기준을 함께 읽어야 한다

  • [원문] 발표자는 월 거의 9천 건의 RCA, 정확도 50%, Jira 해결률 거의 2배, PR 병합률 5%에서 거의 48%로의 상승을 제시했다.
  • [해석] 처리량, 원인 정확도, 올바른 방향 제시, 해결률, 병합률은 서로 다른 지표다. 하나가 높다고 나머지도 자동으로 좋아졌다고 볼 수 없다.
  • [경계] 연간 거의 5만 건의 배정 문제와 월 거의 9천 건의 RCA 사이에는 집계 범위 또는 단위가 설명되지 않은 불일치가 있다. “남은 50% 중 거의 40%가 올바른 방향”이라는 표현도 전체의 40%인지 남은 절반의 40%인지 구분해야 한다. 평가 표본, 비교군, 정확도 판정 절차와 Jira 해결률의 기준값도 공개되지 않았다. 또한 META는 원작자와 소속을 각각 Kriti Dangi와 Hubs로 추정하지만, 발표 내용은 시스템을 Uber에서 구축했다고 말하고 META 설명은 화자를 Uber의 시니어 소프트웨어 엔지니어로 소개해 소속 정보가 충돌하거나 다른 의미일 가능성이 있다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 발표는 쉬운 증상에서 시작해 증거 수집, 원인 추론, 검증으로 이해를 단계화한다.
  • 통찰: 학습자가 결론만 맞히는 것보다 어떤 증거로 원인을 좁혔고 어떤 시험으로 반증했는지를 설명하게 하면 이해를 더 잘 관찰할 수 있다.
  • 질문/행동: 학습자가 답과 함께 “사용한 증거, 버린 가설, 확인할 테스트”를 말하게 하면 설명의 빈틈이 어디서 드러나는가?

사업가 · 구조적 비유

  • 관련성: Debug Assist는 반복 수집 비용을 공통 하네스로 줄이고, 전문 판단과 최종 승인은 필요한 곳에만 배치한다.
  • 통찰: APOM·이커머스·물류에서도 반복 문제를 수집·분류·검증 단계로 나눌 수 있다는 가설은 세울 수 있다. 다만 현재 APOM의 데이터, 자동화, 장애 처리 상태는 출처에 없으므로 실제 적용 사실이 아니라 검증 전 구조적 비유다.
  • 질문/행동: 반복 문제 하나를 골랐을 때 고정 규칙으로 처리할 부분과 사람의 판단을 남길 부분을 근거와 함께 나눌 수 있는가?

마케터 · 직접 전이

  • 관련성: 발표는 배터리 29%, 백그라운드 17분, 5% 배포 단계 같은 구체적 장면으로 문제와 해결을 연결한다.
  • 통찰: “AI가 고친다”는 추상적 주장보다 입력 증거, 원인 경로, 검증 과정, 최종 사람의 결정을 함께 보여 주는 편이 신뢰 형성에 유리하다.
  • 질문/행동: 카피에 성과 숫자를 쓸 때 분모, 기간, 비교 기준과 아직 검증되지 않은 목표를 같은 화면에서 구분할 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 결정적 노드, 병렬 하위 에이전트, 최대 실행 횟수, 추적, 단계별 모델 선택과 테스트가 구체적으로 제시된다.
  • 통찰: 모델 선택보다 먼저 업무 유형, 입력 범위, 도구 권한, 중단 조건, 재현 가능한 평가를 정의해야 한다. 모든 호출과 명령을 추적해야 실패 비용도 분석할 수 있다.
  • 질문/행동: 에이전트가 잘못된 방향으로 갈 때 같은 측정 지표로 감지하고 사람에게 넘길 기준이 정의되어 있는가?

가치 지도

"증상, 로그, 코드와 담당 정보가 흩어져 원인 분석이 늦어진다" 문제
→ "근거와 수정 후보를 더 빨리 받는다" 수혜자: 장애를 맡은 개발자와 영향을 받는 앱 사용자

→ "검토된 분석 중 실제 개발자 수정과 정확히 일치한 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 이미 해결된 소프트웨어 오류 5건에 대해 증거 수집 → 원인 후보 → 반증 테스트 → 사람 검토 체크리스트로 분석 후보를 다시 만들어 본다.
  • 측정 1개: 5건 중 근거를 추적할 수 있고 실제 수정 방향과 일치한 분석의 비율.
  • 중단 기준 1개: 실제 수정 방향과 일치한 분석이 5건 중 3건 미만이면 범위를 확대하지 않고 입력 자료와 단계 구분부터 다시 설계한다.

# 섹션 요지
1 문제 수집 Wisdom은 사람이 신고하고 Healthline은 장애를 자동 감지한다.
2 실제 사례 배터리 소모와 푸시 알림 충돌에서 원인 분석과 수정안을 만들었다고 발표한다.
3 내부 파이프라인 결정적 수집 노드, LLM 기반 RCA·수정 노드, 검증 단계로 구성된다.
4 하네스 확장 공통 코드와 실행 환경을 공유하고 팀별 스킬을 런타임에 불러온다.
5 개발자 상호작용 diff fixer, Ask AI, 준비된 실행 환경으로 결과를 교정한다.
6 성과와 질의응답 운영 지표, 테스트 방식, 추적, 하위 에이전트 통제를 설명한다.

1. 문제 수집과 디버깅의 병목

  • Wisdom: 내부 직원과 베타 테스터의 자연어 버그 신고, 화면, 앱·운영체제·도시 정보와 네트워크·분석·콘솔·GraphQL·UI 상태 로그를 수집한다고 설명한다.
  • 발표자는 캡처 대상이 Uber 화면뿐이므로 보안 우려가 없다고 주장한다. 수집 범위, 동의, 보관 방식에 대한 독립 근거는 발표에 없다.
  • Healthline: 충돌, 멈춤, 화면 끊김, 성능 저하를 자동 감지하고 세션 정보, 사용자 직전 행동, 스택 트레이스와 크래시 덤프를 모은다고 설명한다.
  • 발표 수치로는 두 시스템에서 연간 거의 5만 건이 엔지니어에게 배정되고, 그중 90%가 고객에게 영향을 주며, 엔지니어링 팀에 1만 2천 건의 호출이 전달된다.
  • 평균 해결 시간은 거의 28일이라고 말한다. Stripe의 공개 보고서를 인용해 개발자가 시간의 40%를 디버깅에 쓴다고도 했지만, 보고서 링크와 조건은 제공된 출처에 없다.

2. 두 가지 사례

배터리 소모

  • 신고 문장은 앱이 배터리 사용량의 거의 30%를 차지하고 휴대전화가 뜨거워진다는 내용이었다.
  • 첨부 화면에는 29%가 표시됐다.
  • 발표에 따르면 약 20분 동안 사용자가 별도 버튼을 누르지 않아도 수정안이 생성됐다.
  • 원인 후보는 백그라운드에서 끝나야 할 코드 경로가 계속 반복된 현상이었다.
  • 앱은 17분 동안 백그라운드 상태였고, 결과 화면에는 이를 뒷받침하는 증거 시간축이 표시됐다고 설명한다.

푸시 알림 충돌

  • 푸시 알림을 매우 빠르게 누르면 앱이 충돌하는 문제였다.
  • 심각도는 P1으로 표시됐다.
  • Debug Assist가 원인 코드와 수정안을 만들고 Slack으로 개발자에게 전달했다고 한다.
  • 발표자는 기능이 5% 배포된 시점에 문제를 발견해 같은 날 수정안을 병합하고 배포했다고 말한다.

3. 파이프라인과 모델 역할

  1. Healthline과 Wisdom에서 문제를 발견한다.
  2. 자동 분류 단계에서 우선순위, 심각도와 담당자를 판단한다.
  3. 결정적 수집 노드가 로그와 메타데이터를 가져오고 파싱·전처리·가지치기한다.
  4. LLM 기반 분류·RCA 노드가 문제 유형과 신뢰도를 판단한다.
  5. 필요하면 MCP를 통해 Jaeger 로그·분산 추적·사고 데이터 등을 조회한다.
  6. 세션 시간축 복원, 충돌과 버전의 상관관계 분석 같은 하위 에이전트를 병렬 실행한다.
  7. 결과를 합친 뒤 기능 플래그를 통한 완화 가능성과 코드 수정 위치를 찾는다.
  8. 단위·통합·컴포넌트·모바일 자동화 테스트 중 가장 단순하게 재현 가능한 방식을 사용한다.
  9. diff 또는 PR을 만들고 Jira, Healthline 또는 Wisdom 항목과 연결한 뒤 Slack으로 전달한다.

RCA 노드는 Sonnet과 제한된 턴 수를 사용한다. 발표자는 20턴을 넘기면 잘못된 탐색 경로일 가능성이 높다고 설명한다. 수정 노드는 Opus와 더 많은 최대 턴을 사용한다. 이 모델 배치는 발표자가 시행착오로 정한 내부 선택이며 외부 비교 결과는 제시되지 않았다.

4. 공통 하네스와 런타임 확장

  • 발표 시점에 거의 8개의 에이전트가 5개 모노레포에서 운영되며 하나의 코드베이스를 공유한다고 한다.
  • 공통 코드는 Python 모노레포 안에 있고 PEX 바이너리로 패키징된다.
  • 바이너리는 공통 Artifactory에 업로드된다.
  • 실행할 때 에이전트 유형에 맞는 바이너리, Docker 실행 환경·이미지, 여러 모노레포에 있는 파이프라인을 가져온다.
  • 스킬과 플러그인도 실행 시점에 선택한다.
  • 내부 마켓플레이스에는 거의 3천 개의 플러그인이 있다고 설명하며, 이를 전부 모델 입력에 넣지 않고 에이전트 유형으로 제한한다.

5. 개발자의 검토와 피드백

  • diff fixer: 단위 테스트 추가, 리팩터링, 변수명 변경 같은 작은 수정을 버튼과 한 줄 요청으로 처리한다.
  • Ask AI: 개발자가 원인 분석과 문제에 관해 질문하고 교정할 수 있다.
  • 피드백: 교정 내용이 프롬프트와 스킬을 개선하는 순환으로 이어진다고 발표자는 설명한다.
  • Open in your machine: 문제에 필요한 환경을 로컬 또는 원격 컴퓨터에 준비해 한 번에 열 수 있도록 한다.

7. 질의응답의 추가 설명

  • 테스트는 항상 모바일 앱 전체를 새로 빌드하는 방식이 아니다.
  • 단위 테스트로 재현할 수 있으면 가장 짧은 경로를 사용하고, 필요에 따라 통합·컴포넌트 테스트로 확장한다.
  • 낮은 네트워크 신호처럼 환경이 핵심인 문제는 시뮬레이터나 에뮬레이터를 사용한다.
  • 사용자 로그에서 네트워크 강도, 배터리 수준, 기능 플래그 조건을 가져와 환경을 맞춘 뒤 APK 또는 IPA를 빌드해 올린다고 설명한다.
  • 반복 검증에는 고정된 재시도 횟수가 있다.
  • 에이전트 내부 관찰에는 Arize Tracing을 LangChain 및 LLM 호출과 연결하며, MCP 호출과 Bash 명령까지 추적한다고 한다.
  • 하위 에이전트는 최대 턴 수와 입력 범위로 통제한다. 예를 들어 문제를 만든 커밋을 찾을 때 전체 Git 기록이 아니라 정상 버전과 문제 버전 사이, 관련 모듈로 범위를 줄인다.
  • 분야별 소유자가 자기 지식과 하위 에이전트를 관리하는 domain extensions를 구축 중이라고 설명한다.

전체 전사 펼치기

이 발표는 Uber에서 구축한 디버깅용 AI 에이전트인 Debug Assist에 관한 것입니다. 오늘은 디버깅이 실제 환경에서 어려운 이유와 Debug Assist가 이를 어떻게 지원하는지 이야기하겠습니다. 데모도 진행한 다음 내부 아키텍처를 간단히 살펴보겠습니다. 마지막으로 흥미로운 수치 몇 가지를 공유하겠습니다.

여러분 앞에 보이는 것은 Uber의 인앱 버그 리포터입니다. 모든 Uber 내부 직원과 베타 테스터는 베타 버전을 통해 Uber 앱 자체에서 버그를 신고할 수 있습니다.

시스템에는 다음과 같은 정보가 수집됩니다. 앱을 사용하다가 화면이 빈 상태가 되거나, 멈춤 현상을 겪거나, 배터리 문제가 발생했다고 해보겠습니다. 간단히 클릭해서 버그를 신고할 수 있습니다. 제 입장에서는 “화면이 비어 있어요”라고 말하는 것처럼 보입니다. 그게 전부입니다. 시스템은 이와 관련된 모든 정보를 함께 수집합니다.

참고로 이 제품의 내부 명칭은 Wisdom입니다. 자연어로 작성된 버그 설명과 함께 해당 문제의 메타데이터도 수집합니다. 예를 들어 영향을 받은 앱은 무엇인지, 영향을 받은 앱 버전은 무엇인지, 영향을 받은 운영체제(OS)는 무엇인지, 사용자가 어느 도시에서 문제를 겪고 있는지 등을 수집합니다.

이와 함께 네트워크 로그, 분석 로그, 콘솔 로그, GraphQL 로그, UI 상태 로그 등 매우 다양한 로그도 수집합니다.

보시다시피 기기에서 스크린샷도 수집됩니다. 여기에는 보안상의 우려가 없습니다. 나중에 문제를 디버깅하기 위해 Uber 관련 스크린샷만 수집합니다.

Uber에는 또 다른 제품도 있습니다. Healthline이라고 합니다. Healthline은 기본적으로 앱 품질 분석 도구입니다.

Wisdom과 마찬가지로 문제를 수집합니다. 하지만 자동으로 수집한다는 점이 다릅니다. 앱이 충돌하거나, 멈춤 또는 끊김 현상을 겪거나, 어떤 형태로든 성능 저하가 발생할 때마다 Healthline이 백엔드에서 작동합니다. Wisdom과 마찬가지로 메타데이터도 수집합니다. 예를 들어 세션 ID는 무엇인지, 분석 ID는 무엇인지, 그 직전에 사용자가 무엇을 하고 있었는지 등을 수집합니다.

앞서 나열한 로그와 그 밖의 많은 로그에 더해, Wisdom과 달리 스택 트레이스(stack trace)와 전체 크래시 덤프(crash dump)도 수집합니다. 따라서 실제로 어떤 코드가 이 문제를 일으켰는지 확인할 수 있습니다.

Healthline과 Wisdom을 합치면 매년 거의 50,000건의 문제가 엔지니어에게 할당됩니다. 이 중 90%는 고객에게 영향을 미치는 문제이고, 그 결과 엔지니어링 팀 전체에 12,000건의 페이저 호출이 발생합니다. 누군가는 이것들을 디버깅해야겠죠? 누군가는 수정해야 합니다.

다음 슬라이드로 넘어가기 전에 간단히 손을 들어 보겠습니다. 프로덕션 문제를 해결하는 것을 좋아하지 않는 분은 얼마나 계신가요?

손을 많이 드셨네요. 제가 아픈 곳을 건드렸나 봅니다. 새벽 2시에 페이저 호출을 받고, 밤새 앉아서 디버깅해야 하는데 어디서부터 시작해야 할지도 모르면 정말 짜증 납니다. 머리가 너무 흐릿하기 때문이죠.

실제 환경에서의 디버깅은 이런 식입니다. 오류가 불분명한 경우가 많습니다. 우리 모두 “문제가 발생했습니다”라는 메시지를 받아본 적이 있을 겁니다. 그러면 무엇이 잘못됐는지 알아내야 합니다. 익숙하지 않은 코드 로직을 샅샅이 살펴봐야 하는 것입니다.

컨텍스트도 흩어져 있습니다. 코드, 로그, 설정, 데이터를 모두 확인해야 합니다. 그 데이터에 접근하기 위해 내부적으로 수많은 도구를 사용합니다. 코드베이스에 관해 말하자면, Uber의 코드베이스는 방대합니다.

여러 개의 모노레포(monorepo)가 있습니다. 우리는 모노레포 아키텍처 스타일로 운영하고 있는데, 이는 여러 팀이 하나의 저장소에 기여한다는 뜻입니다. 따라서 문제를 일으킨 사람이 누구인지 알아내는 것 자체가 또 다른 문제가 됩니다. 알아냈다고 해도 팀 간 의존성이 남아 있습니다. 해당 코드는 다른 사람이 소유하고 있을 수 있습니다. 우리 팀이 소유한 코드라고 해도 팀이 작성한 모든 코드를 알고 있는 것은 아니겠죠?

그 결과 Uber의 엔지니어가 문제를 해결하는 데는 평균적으로 거의 28일이 걸립니다. Stripe가 공개한 보고서에 따르면 개발자는 문제를 디버깅하는 데 시간의 40%를 사용합니다.

이것이 우리가 Debug Assist를 개발한 이유입니다. Debug Assist는 앱 품질을 개선하고 개발자의 디버깅 경험을 향상해, 우리가 가장 잘하는 일인 개발을 할 수 있도록 하는 것을 목표로 합니다.

이것이 우리가 일반적으로 따르는 전체 파이프라인입니다. 엔드투엔드 에이전트 기반(agentic) 해결 과정입니다. 발견 단계로 시작합니다. 앞서 본 것처럼 발견은 Healthline과 Wisdom을 통해 이루어집니다. 다음은 자동 분류(Auto Triage) 단계입니다. 이 단계에서는 문제의 우선순위와 심각도를 판단하고 실제 담당자를 찾습니다. 온콜 담당자는 누구인가? 여기서 저를 태그해야겠죠.

그다음 실제 Debug Assist 파이프라인이 시작됩니다. 30분 이내에 심층 근본 원인 분석(RCA)을 수행합니다. 어떻게 하는지는 곧 살펴보겠습니다. 여기서 자세히 알아보겠습니다. 마지막으로 해결을 목표로 합니다. 개발자에게 데이터를 잔뜩 던져주는 것만 원하지는 않습니다. 실행 가능한 결과를 제공하고 싶습니다. 문제를 엔드투엔드로 해결하고 싶은 것입니다.

이제 재미있는 부분입니다. 데모를 시작하겠습니다. 모두 집중해서 봐주시기 바랍니다. 이것은 앞서 본 Wisdom 화면이며, 실제 사례입니다. 어느 날 Uber 개발자 한 명이 잠에서 깨어 사무실로 가기 위해 차량을 호출했습니다. Uber를 기다리던 중 휴대전화가 주머니에서 뜨겁게 달아오르고 있다는 것을 알게 되었습니다. 그래서 Wisdom에 버그를 신고했습니다. 그가 말한 것은 다음과 같았습니다.

“Uber 앱이 배터리 사용량의 거의 30%를 차지합니다. 휴대전화가 뜨거워지고 있어요.” 그게 전부였습니다. 그는 편안하게 Uber를 타고 사무실에 도착한 다음 노트북을 열어 문제를 확인했습니다.

그 20분 동안 Debug Assist는 그가 버튼을 한 번도 누르지 않았는데 이미 수정 사항을 만들었습니다. 개발자가 해야 할 일은 이를 검토하고 배포하는 것뿐이었습니다.

그렇다면 이 마법은 백그라운드에서 어떻게 일어날까요? 보시다시피 Wisdom은 자연어 설명을 수집했습니다. 개발자가 차량을 호출하는 동안 보고 있던 화면의 스크린샷과 개발자가 업로드한 스크린샷도 수집했습니다. 업로드된 스크린샷에는 다음과 같이 표시되어 있었습니다.

“Uber가 제 배터리를 사용하고 있어요.” 실제로 29%인 것을 명확히 확인할 수 있습니다. 관련 메타데이터와 로그도 함께 있습니다.

이것이 실제로 디버깅을 지원한 방식입니다. 이것이 Debug Assist의 출력 결과입니다. 왼쪽을 보면 Debug Assist가 문제의 근본 원인을 핫 루핑(hot-looping) 코드 경로로 파악했습니다. 즉, 백그라운드에서 실행되도록 되어 있던 특정 코드 경로가 실제로는 포그라운드 루프 경로처럼 처리되었고, 그 결과 CPU 사이클 사용량이 높아져 배터리 성능이 저하된 것입니다.

이 RCA와 함께 앱이 17분 동안 백그라운드 상태였다는 것도 알려줍니다. 포그라운드에 있지 않았으며, 이 모든 내용은 증거에 기반합니다. 오른쪽에서는 증거 타임라인을 확인할 수 있습니다. 에이전트가 환각을 일으킨 것이 아니며 수정 사항에 어느 정도 확신을 가질 수 있다는 뜻입니다. 마지막으로 개발자가 상당히 만족한 모습도 볼 수 있습니다.

또 다른 예를 보겠습니다. 잘못된 롤아웃으로 인해 Uber 앱에서 충돌이 발생했습니다. 기본적으로 누군가 푸시 알림을 아주 빠르게 클릭하면 앱이 충돌했습니다. 심각도가 높은 충돌이었기 때문에 P1, 즉 우선순위 1로 표시되었습니다.

Debug Assist는 이 문제에 대해 전체 심층 RCA를 생성했습니다. 원인이 된 코드를 정확히 찾아냈고 수정 사항도 만들었습니다. 이후 수정 사항은 Slack 메시지를 통해 개발자에게 전달되었습니다.

이 경우 수정 사항은 같은 날 병합되고 배포되었습니다. 따라서 5% 롤아웃 단계에서 충돌을 발견하고 바로 그날 수정할 수 있었습니다.

이제 Debug Assist가 실제로 무엇을 하는지 살펴보겠습니다. 어떻게 이를 수행할까요? 보시다시피 이 에이전트는 LangGraph 파이프라인 위에 구축되어 있습니다. 결정론적 노드와 LLM 노드를 혼합한 구조입니다. 왜 LangGraph를 사용했을까요?

일반적으로 에이전트에는 계획 단계와 실행 단계가 있습니다. LangGraph 또는 LangChain을 사용하면 계획 단계를 우회할 수 있습니다. 에이전트에 계획을 제공합니다. 매번 따라야 할 단계가 정해져 있는 것입니다. 따라서 에이전트의 특정 환각 가능성을 줄일 수 있습니다. 문제를 해결하기 위한 좋은 계획을 LLM에 전적으로 의존하지 않아도 됩니다.

우리가 계획을 통제하기 때문에, 먼저 컨텍스트 수집기 노드(context collector node)에서 시작합니다. 이 노드는 Healthline과 Wisdom, 모든 로그 등 앞서 이야기한 데이터를 수집합니다. 결정론적 노드이며 LLM 노드가 아닙니다.

AI의 시대인데 왜 이 과정에 LLM을 사용하지 않을까요? 모든 작업을 에이전트를 통해 수행할 필요는 없습니다. 단순히 데이터를 가져오는 작업이기 때문입니다. 에이전트에 많은 컨텍스트를 넣어 컨텍스트가 비대해지는 것을 원하지 않습니다. 이미 알고 있는 API를 호출하는 데 에이전트의 지연 시간을 추가하고 싶지도 않습니다. 물론 요즘 LLM 비용도 큰 문제이므로 비용을 폭증시키고 싶지 않습니다.

이 구조를 사용하면 로그를 파싱하고 전처리하고 정리할 수도 있습니다. 제가 말하는 로그는 엄청난 규모입니다. 수 메가바이트, 수 메가바이트, 때로는 수 기가바이트에 달하는 로그입니다. 이것을 단순히 에이전트에 넣을 수는 없습니다. 어떤 방식으로든 전처리해야 합니다.

다음으로 분류 또는 RCA 노드로 이동합니다. 보시다시피 파란색으로 강조된 LLM 노드입니다. 이 노드는 우리가 전달한 모든 데이터를 살펴봅니다. 먼저 충돌을 분류합니다. Uber의 문제 때문에 발생한 것인지, 서드파티 라이브러리 코드 때문인지, 인프라 문제인지, 네트워크 문제인지, 아니면 이를 수정하기 위한 PR을 만들어야 하는지 판단합니다.

분류가 끝나면 보시는 것처럼 신뢰도 점수를 산출합니다. 마지막으로 더 많은 데이터가 필요하다고 판단하면 Uber 생태계를 조회합니다. Jaeger 로깅, Jaeger 분산 트레이싱(distributed tracing), 로깅, 인시던트 데이터 등을 위한 MCP 연결을 통해 조회합니다. 사용자에게 전반적으로 영향을 미치는 진행 중인 인시던트가 있는지도 확인합니다.

이 작업이 끝나면 서브에이전트를 통해 RCA를 수행합니다. 여러 서브에이전트를 병렬로 분기해 각각 RCA를 수행하게 합니다. 그런 다음 결과를 통합합니다.

서브에이전트의 예를 하나 들면 브레드크럼 분석(breadcrumb analysis)이 있습니다. 모든 세션 데이터를 에이전트에 제공하고 사용자의 타임라인을 재현하도록 요청합니다. 이는 RCA뿐만 아니라 문제를 재현하는 데도 도움이 됩니다.

제가 여러분과 공유할 수 있는 또 다른 에이전트는 크래시 상관관계 에이전트(crash correlation agent)입니다. 크래시가 발생할 때마다 이를 특정 버전 릴리스와 연관 지을 수 있을까요? 이 버전에서 크래시가 발생하고 있다고 자신 있게 말할 수 있을까요?

다음 단계는 수정 노드(fix node)입니다. 수정 단계로 넘어가기 전에, 각 노드에 특정 설정이 주어져 있다는 점을 보실 수 있을 겁니다. RCA 노드는 제한된 턴 수로 더 낮은 수준의 모델인 Sonnet을 실행합니다. 복잡한 노드라고 생각할 수도 있지만, 실제로는 그렇지 않습니다. 생각해 보면 대부분 데이터를 살펴보고, 정보를 수집하고, 요약하는 작업입니다.

그래서 제한된 턴 수로 Sonnet을 실행합니다. 시행착오를 통해 20턴보다 더 걸리면 대체로 잘못된 방향, 즉 좋지 않은 토끼굴로 들어가고 있다는 사실을 알아냈습니다. 이런 식으로 에이전트에 가드레일(guardrail)을 설정할 수도 있습니다.

다음 단계인 수정 노드로 넘어가겠습니다. 이 노드에는 뛰어난 두뇌가 필요합니다. Uber 코드베이스 전체를 살펴보는데, Uber 코드베이스는 수십억 줄에 달합니다.

이제 어떤 모듈이 영향을 받았을지, 어떤 코드 경로가 영향을 받았을지를 파악하려고 합니다. 그리고 모든 상태는 각 노드 사이에서 전달됩니다. 따라서 이전 노드의 상태도 가지고 있습니다. 아무것도 잊지 않은 것입니다. 수정하기 전에 먼저 이슈를 완화하려고도 합니다.

보시다시피 Uber의 대부분의 이슈는 기능 플래그(feature flag) 뒤에 있으며, 이 노드는 기능 플래그 MCP에 연결됩니다. 이 기능 플래그가 이 이슈를 일으키고 있는지 상관관계를 파악하려고 합니다. 그리고 여러분이 Uber 앱을 사용하는 모든 휴대폰에는,

백그라운드에서 최소 수만 개의 기능 플래그가 활성화되어 있습니다. 따라서 해당 크래시 하나를 그 기능 플래그 중 하나와 연결하는 것만 해도 이미 매우 복잡한 작업입니다. 강한 상관관계가 확인되면 기능 플래그를 즉시 롤백하고 이슈를 완화합니다. 그러면 여러분은 원하는 시간에 직접 수정할 수 있습니다.

여기에는 Opus에서 더 많은 최대 턴 수로 실행되는 수정 및 완화 단계가 있습니다. 다음은 검증 단계입니다. 레거시 이유로 실제 명칭은 Bazel 테스트(Bazel test)이지만, 본질적으로는 검증 단계입니다. 이 경우 에이전트는 단위 테스트(unit test)나 모바일 자동화 엔드투엔드 테스트(mobile automated end-to-end test)를 통해 이슈를 재현하려고 합니다.

Uber의 일부 플로에는 시뮬레이터나 에뮬레이터에서 직접 실행되는 자동화 테스트가 있습니다. 특히 차량 호출 같은 핵심 플로에 그렇습니다. 이 노드는 자신의 수정 사항을 검증하려고 합니다. 따라서 PR을 개발자에게 넘기고 “테스트하세요”라고만 하는 것이 아닙니다. 직접 검증함으로써 자체 수정 사항에 대한 확신도 높입니다.

마지막으로 수정 사항이 만족스러우면 diff 또는 PR을 생성합니다. 이 경우 PR은 Healthline 또는 Wisdom의 Jira 이슈에 첨부됩니다. Slack을 통해 개발자에게 전송되고, 모든 정보는 메타데이터로 내부에 업데이트됩니다.

여기서 몇 가지 핵심 사항을 짚고 넘어갈 필요가 있습니다. 이것이 에이전트의 기본 뼈대입니다. 이 뼈대는 절대 바뀌지 않습니다. 바뀌는 것은 스킬과 플러그인입니다. 각 LLM 노드에는 고유한 스킬이 있습니다. Uber에서 좋은 PR을 만들려면 어떻게 해야 하는가? 테스트 계획을 세울 때 따르는 좋은 관행은 무엇인가? Android에서 이슈를 어떻게 수정하는가? 항상 지연 로딩(lazy loading)을 사용해야 하는가? 어떤 작업을 백그라운드로 미뤄야 하는가? 등입니다.

이러한 스킬과 플러그인은 이름 그대로 플러그인 방식으로 연결할 수 있습니다. 뼈대는 그대로 유지되고, 이 모든 핵심 비즈니스 로직은 뼈대 바깥에 있으며 런타임에 가져옵니다. 즉, 내일 새로운 에이전트를 추가하고 싶다면 스킬을 크라우드소싱하는 일만 하면 됩니다.

이어서 다음 슬라이드로 넘어가겠습니다. Uber 규모에서 에이전트를 어떻게 프로덕션화했을까요? 로컬 머신에서 무언가를 실행하는 것은 한 가지 이야기지만, Uber 규모로 실행하는 것은 완전히 다른 이야기입니다. 말씀드렸듯이, 저희는 개발자들에게 하네스를 제공했습니다. 따라야 할 단계, 런타임 환경, 의존성 등을 제공했습니다.

각 팀이 해야 할 일은 저희가 이미 제공하는 것 위에 자신들만의 전문 스킬을 추가하는 것뿐입니다. 이는 저희의 부담도 줄여 줍니다. 이제 모든 사람을 위해 수많은 스킬과 플러그인을 유지 관리할 필요가 없기 때문입니다. 여러분은 각자의 전문성을 가져오고, 저희는 하네스를 제공합니다.

현재 5개의 모노레포(monorepo)에서 거의 8개의 에이전트가 규모 있게 실행되고 있으며, 모두 하나의 코드베이스를 공유합니다.

모든 코드는 Python 모노레포 안에 있고, PEX라는 Python 바이너리로 패키징됩니다. PEX는 공용 Artifactory에 업로드됩니다. 에이전트가 실행될 때마다 에이전트는 자신의 유형을 알고 있습니다. 에이전트 유형에 따라 올바른 바이너리와 올바른 Docker 런타임 및 Docker 이미지를 가져옵니다. 여기에는 모든 의존성과 런타임 환경이 포함되어 있습니다. 마지막으로 여러 모노레포에 흩어져 있는 모든 파이프라인을 가져옵니다.

다시 강조하고 싶은 점은 이것이 하네스라는 것입니다. 각 에이전트의 스킬과 플러그인도 런타임에 가져옵니다. 모든 마켓플레이스 플러그인을 한꺼번에 넣지는 않습니다. Uber에는 규모가 매우 큰 스킬 마켓플레이스가 있습니다. 현재 거의 3,000개의 플러그인이 있는데, 모든 플러그인의 컨텍스트를 에이전트에 넣을 수는 없습니다. 그러면 에이전트가 제대로 작동하지 않게 됩니다.

PR을 생성한 뒤 그대로 방치하지도 않습니다. 개발자가 에이전트와 대화하고 결과를 직접 다듬고 검증할 수 있는 인터랙티브 환경을 제공합니다.
