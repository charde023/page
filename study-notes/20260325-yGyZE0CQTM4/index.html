핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
컨텍스트 엔지니어링 AI 출력 품질을 좌우하는 근본 레버리지 더 좋은 토큰을 넣어야 더 좋은 토큰이 나온다
Smart Zone / Dumb Zone 컨텍스트 40% 이상 채우면 성능 급락 컨텍스트를 항상 40% 이하로 유지
Intentional Compaction 진행 중 컨텍스트를 마크다운으로 압축·이전 새 에이전트가 탐색 반복 없이 바로 시작
Research → Plan → Implement (RPI) 브라운필드에서 슬롭 없는 구현 워크플로 리서치로 사실 수집, 플랜으로 의도 압축, 구현 신뢰 확보
Sub-agent의 진짜 목적 역할 분리가 아닌 컨텍스트 제어 탐색은 서브 에이전트, 결과만 부모에 전달
Mental Alignment 팀이 같은 이해를 유지하는 것이 코드 리뷰의 핵심 플랜 파일로 리더가 코드 안 읽고도 맥락 유지
Progressive Disclosure 코드베이스 문서를 계층화해 필요한 것만 로드 모노레포 온보딩 컨텍스트 폭발 방지

내가 모를 만한 것 / 처음 보는 것

  • 슬롭(Slop): 저품질 AI 생성 코드. 배포량이 늘수록 슬롭 수정 작업도 함께 늘어나는 함정
  • 브라운필드(Brownfield) vs 그린필드(Greenfield): 기존 레거시 코드베이스 vs 새 프로젝트. AI는 그린필드에선 잘 되고 브라운필드에선 자주 실패
  • Dumb Zone: 컨텍스트 윈도우가 약 40% 이상 채워진 상태. 이 구간에서 작업하면 성능 저하
  • Smart Zone: 컨텍스트 40% 이하 여유 구간. 여기서만 작업하도록 설계
  • Intentional Compaction: 컨텍스트를 의도적으로 마크다운 파일로 압축하는 행위. 태그 포함
  • Progressive Disclosure: 문서를 계층화해 에이전트가 필요한 하위 컨텍스트만 추가로 가져오게 하는 구조
  • HumanLayer: Dex Horthy가 만든 회사/도구. 에이전틱 AI 워크플로 플랫폼
  • 12 Factor Agents: 화자가 6월 AI 엔지니어 컨퍼런스에서 발표한 에이전트 설계 원칙 (별도 학습 필요)
  • On-demand 압축 컨텍스트: 배포할 때마다 문서 갱신하는 대신, 작업 시작 시 실제 코드에서 사실만 스냅샷으로 추출하는 방식

화자의 디테일 (놓치기 쉬운 포인트)

  1. 10만 명 개발자 조사 결과: 배포량 증가와 슬롭 수정 작업 증가가 동시에 일어남 — AI 도입이 기술 부채 공장이 될 수 있음
  2. Claude Code 컨텍스트 윈도우는 약 168,000 토큰. 출력과 컴팩션 용도로 일부 예약됨
  3. 40% 기준은 절대값이 아니라 복잡한 작업 기준 가이드라인 — 환경마다 다름
  4. MCP를 너무 많이 붙이면 시작부터 Dumb Zone에서 작업하게 됨 — MCP 개수 최소화가 중요
  5. 실험 사례 1: 30만 라인 Rust 코드베이스 버그를 RPI 방식으로 원샷 수정 → PR이 팟캐스트 실험인 줄 모르고 다음 릴리스에 포함됨
  6. 실험 사례 2: 토요일 7시간 작업으로 3만 5천 라인 코드 배포 → 동료가 "보통 1~2주 분량"이라고 평가
  7. 실험 사례 3(실패): PowerKit Java + Haydolph 의존성 작업은 결과가 나빠 화이트보드부터 다시 설계해야 했음 — 한계 실재함
  8. 잘못된 트라젝토리: 에이전트가 틀릴 때마다 혼내면, 모델이 "틀리면 혼남" 패턴을 학습해 다음 토큰 확률이 틀리는 쪽으로 기울어짐
  9. 컨텍스트 품질 우선순위: 잘못된 정보 > 누락된 정보 > 과도한 노이즈 순으로 해로움
  10. 플랜이 길어질수록 실행 신뢰도는 오르지만 가독성은 떨어짐 — 팀과 코드베이스마다 최적점이 있음
  11. 스펙 드리번 개발(Spec-Driven Development)이라는 용어는 의미가 퍼져 흐려짐 — 사람마다 "더 자세한 프롬프트"부터 "코드를 조립 단계로 다루기"까지 다 다른 뜻으로 사용
  12. 마틴 파울러가 2006년에 지적: 좋은 용어도 여러 사람이 제각각 쓰면 금방 무의미해진다 — "에이전트"도 이미 100가지 뜻이 됨
  13. 팀 정렬 방법: PR에 에이전트 단계, 프롬프트, 최종 빌드 통과 여부까지 공유하면 코드 diff만 보는 것보다 맥락 전달이 훨씬 좋음
  14. 조직 문화 전환은 위에서부터 시작해야 함 — 주니어가 슬롭을 만들면 시니어가 치우다 AI를 싫어하게 되는 악순환

1. 문제: 브라운필드에서 AI가 실패하는 이유

10만 명 개발자 조사에서 확인된 패턴:

  • 배포량은 늘지만 슬롭 수정 작업도 함께 늘어남
  • 그린필드, 작은 대시보드 — 아주 잘 됨
  • 10년 된 Java 레거시 코드베이스 — 이야기가 다름

슬롭이 쌓이고 기술 부채 공장이 되면, 기존 코드베이스에서 AI는 잘 안 돌아간다. 모델이 더 좋아지면 달라질 수 있겠지만, 지금 모델로 최대 성능을 뽑으려면 컨텍스트 엔지니어링이 필요하다.

화자의 팀(3명)은 8주간 협업 방식과 소프트웨어 제작 방식 전체를 다시 설계했다. 그 결과를 HumanLayer라는 제품과 오픈소스로 공개했고, 해커 뉴스에서 크게 퍼졌다.

목표: - AI가 기존 코드베이스에서도 잘 동작 - 복잡한 문제 해결 가능 - 슬롭 없음 - 팀 멘탈 얼라인먼트 유지 - 토큰 효율 극대화

2. 컨텍스트가 전부다

LLM은 순수 함수에 가깝다. 상태는 없고, 컨텍스트가 전부다.

매 턴마다 에이전트는 다음 행동을 고른다. 다음 결과를 좌우하는 건 지금까지 대화에 들어간 내용뿐이다.

컨텍스트 최적화 4가지 축: 1. 정확성 — 잘못된 정보가 가장 해롭다 2. 완전성 — 누락된 정보가 두 번째로 해롭다 3. 크기 — 과도한 노이즈가 세 번째 4. 방향성 — 틀릴 때마다 혼내면 "틀리는 패턴"이 강화됨

에이전트가 틀려서 혼내면, 모델은 "틀리면 혼남"을 학습하고 다음 확률 높은 토큰이 또 틀리는 쪽이 된다.

3. Smart Zone과 Dumb Zone

Claude Code 기준 컨텍스트 윈도우 약 168,000 토큰. 일부는 출력과 컴팩션용으로 예약.

컨텍스트 약 40% 이상 채워지면 성능이 체감상 떨어지기 시작한다. 이 구간이 Dumb Zone.

  • MCP를 너무 많이 붙이면 시작부터 Dumb Zone에서 작업하게 됨
  • 40%는 절대값 아님. 복잡한 작업 기준 가이드라인
  • 핵심: Dumb Zone을 똑똑하게 피하는 것

4. Intentional Compaction

언제 컨텍스트를 리셋해야 하는가: - Claude가 계속 틀릴 때 - 대화가 어긋나기 시작할 때

Intentional Compaction: 진행이 맞든 틀리든, 현재 컨텍스트를 마크다운 파일로 압축하게 시키는 방식.

압축에 담아야 할 것: - 지금 정확히 어떤 문제를 푸는지 - 어떤 파일의 어떤 라인이 중요한지

태그도 붙여두면 다음 에이전트가 탐색 반복 없이 바로 시작한다.

컨텍스트를 차지하는 요소: 파일 탐색, 코드 흐름 이해, 파일 수정, 테스트·빌드 로그. MCP가 리소스를 잔뜩 밀어넣으면 더 심각해진다.

5. Sub-agent의 진짜 목적

역할 분리(프론트엔드/백엔드/QA 역할 놀이)를 위한 Sub-agent는 멈춰야 한다.

Sub-agent의 목적은 컨텍스트 제어다.

올바른 사용법: 1. 큰 코드베이스에서 새 컨텍스트 윈도우를 분기해 서브 에이전트에게 탐색 위임 2. 서브 에이전트가 필요한 파일을 다 찾고 이해한 뒤 3. 부모 에이전트에는 아주 짧게 결과만 전달 (예: 파일 위치만) 4. 부모 에이전트는 그 파일만 읽고 바로 구현

6. Research → Plan → Implement (RPI) 워크플로

전 구간을 Smart Zone에서 유지하는 것이 목표.

Research (리서치)

목적: 시스템 동작 이해, 핵심 파일 찾기, 최대한 객관적으로 파악

선호하는 방식: 배포할 때마다 문서를 갱신하는 것(현실적으로 꾸준히 못 함)보다, 작업 시작 시 여러 서브 에이전트를 띄워 코드베이스를 훑고 코드 자체를 근거로 지금 진짜 사실인 부분만 스냅샷 연구 문서로 수집.

"진실을 압축하는 것."

Progressive Disclosure 구조: - 각 리포 루트에 파일 하나 - 하위 레벨로 갈수록 필요한 추가 컨텍스트만 계층적으로 배치 - 에이전트가 루트 컨텍스트 먼저 읽고 필요한 하위 컨텍스트만 추가로 가져옴 - Smart Zone 여유가 충분히 남음

Plan (플랜)

목적: "의도를 압축"하는 레버리지

내용: - 파일명과 라인 스니펫까지 포함한 정확한 실행 단계 - 변경 후 테스트 방법 명확히 기술 - 실제 변경될 코드 스니펫도 포함 (점진적으로 추가)

리서치 + PRD + 버그 티켓 등을 합쳐 플랜 파일 생성.

나쁜 코드 한 줄은 나쁜 코드 한 줄이지만, 나쁜 플랜 한 줄은 나쁜 코드 수백 줄을 만든다. 잘못된 리서치 한 줄은 시스템 전체를 망가뜨릴 수 있다.

플랜 길이와 신뢰도 트레이드오프: - 플랜이 길어질수록 실행 신뢰도 상승, 가독성 하락 - 팀과 코드베이스마다 최적점이 다름

Implement (구현)

  • 플랜대로 실행
  • 컨텍스트를 낮게 유지
  • 빌더가 플랜 생성 과정에서 에이전트와 계속 왕복하며 확인
  • 필요하면 동료 리뷰로 플랜 검증

RPI의 가치는 인간이 루프 안에서 정확성을 보장할 때 생긴다.

7. Mental Alignment

코드 리뷰의 핵심은 정확성 검증이 아니라 팀이 같은 이해를 유지하는 것이다.

기술 리더 관점에서: - 코드 1,000줄을 다 읽는 것보다 플랜을 읽는 것으로 업데이트를 따라가고 이해를 유지 - 문제를 더 일찍 잡고 시스템 흐름을 계속 파악 가능

PR에 포함할 정보: - 에이전트 작업 단계 - 사용한 프롬프트 - 최종 빌드 통과 여부 - 수동 테스트 방법

코드 diff만 보여주는 것보다 훨씬 많은 맥락을 전달한다.

8. 스펙 드리번 개발 비판

"스펙 드리번 개발(Spec-Driven Development)"이라는 용어는 의미가 퍼져 흐려졌다.

마틴 파울러의 2006년 경고: 좋은 용어도 여러 사람이 제각각 쓰면 금방 무의미해진다. "에이전트"도 이미 챗봇, 마이크로서비스, 워크플로 등 100가지 뜻이 됐다.

실제로 먹히는 4가지: 1. 리서치 (Research) 2. 플랜 (Plan) 3. 구현 (Implement) 4. 컴팩션 (Compaction) + 컨텍스트 엔지니어링 + Smart Zone 유지

용어보다 이 실질적인 행위가 중요하다.

9. 미래 전망과 조직 문화

코딩 에이전트 자체는 점점 범용화된다. 진짜 어려운 문제는 팀과 워크플로를 AI가 코드의 99%를 만드는 세계에 맞게 바꾸는 것이다.

현재의 악순환: - 시니어: AI가 체감 속도를 못 올려줘서 도입 미룸 - 주니어/미들: 슬롭도 함께 만들면서 사용 - 결과: 시니어가 슬롭을 치우다 AI를 더 싫어하게 됨

문화 변화는 위에서부터 시작해야 한다. 기술 리더라면: 1. 도구 하나를 골라 충분히 반복 2. 여러 도구(Claude, Codex, Cursor 등)를 동시에 최적화하려는 min-max는 비추

전체 전사 펼치기

여러분 안녕하세요. 저는 덱스(Dex)입니다. 저는 에이전트를 오래 다뤄왔고, 6월 AI 엔지니어 컨퍼런스에서 한 12 팩터 에이전트(12-Factor Agents) 발표가 역대 상위권 발표였습니다. 거기서 컨텍스트 엔지니어링 얘기도 조금 했었죠.

오늘은 그 컨퍼런스에서 제가 가장 좋아했던 발표를 소개하려 합니다. 어제 Claude 업데이트 소식 다 받으셨죠? 슬라이드를 미처 못 바꿔서, 오늘은 이전에 정리한 내용을 기준으로 이야기하겠습니다.

핵심 문제: 다양한 규모 회사의 개발자 10만 명을 조사했더니, AI로 개발할 때 재작업과 코드베이스 오염이 많고, 특히 복잡한 브라운필드 코드베이스에서 잘 안 맞는 경우가 많았습니다. 그래프를 보면 배포량은 늘지만 지난주에 만든 슬롭 코드를 다시 고치는 일도 같이 늘어요. 반대로 그린필드나 작은 대시보드 같은 건 아주 잘 됩니다. 하지만 10년 된 Java 코드베이스는 이야기가 다르죠.

슬롭이 쌓이고 기술 부채 공장이 되면, 기존 코드베이스에서는 잘 안 돌아갑니다. 모델이 더 좋아지면 달라질 수 있겠지만, 그래서 컨텍스트 엔지니어링이 중요합니다. 지금 모델로도 최대 성능을 뽑으려면 어떻게 해야 할까요? 컨텍스트 윈도우를 어떻게 관리할지죠?

솔직히 처음 Claude Code를 봤을 때는 크게 감흥이 없었습니다. 그냥 조금 낫네 정도였고 UX는 괜찮다고 느꼈습니다. 그런데 그 뒤에 우리 팀이 중요한 걸 찾아냈습니다. 실제로 처리량을 크게 올릴 수 있었고, 배포량이 너무 많아져서 협업 방식 자체를 바꿀 수밖에 없었습니다. 소프트웨어를 만드는 방식 전부를 다시 설계했어요. 3명 팀이 8주 걸렸고 정말 어려웠습니다. 하지만 이 문제를 풀고 나니 이제는 절대 예전으로 못 돌아갑니다. 이게 HumanLayer의 핵심입니다.

이 내용은 해커 뉴스에서 크게 퍼졌습니다. 수천 명이 GitHub에서 우리 Research/Plan/Implement 프롬프트 시스템을 가져갔죠.

우리가 뒤늦게 정리한 목표: AI가 기존 코드베이스에서도 잘 동작해야 하고, 복잡한 문제를 풀어야 하며, 슬롭이 없어야 합니다. 그리고 멘탈 얼라인먼트(Mental Alignment), 즉 팀이 같은 이해를 유지해야 했습니다. 또 토큰은 가능한 효율적으로 써야 합니다.

가장 단순한 사용법: 에이전트에게 시키고 틀렸다고 고치고, 또 시키는 걸 컨텍스트가 끝날 때까지 반복하는 겁니다. 그런데 우리는 더 똑똑하게 할 수 있습니다. 많은 분이 초기에 깨닫죠 — 대화가 어긋나면 새 컨텍스트 윈도우를 여는 게 더 낫다는 걸요. 같은 작업과 프롬프트로 다시 시작하되, 이번엔 경로를 명확히 지정하는 겁니다.

언제 리셋해야 할까요? Claude가 계속 틀릴 때 새로 시작할 때입니다.

그리고 여기서 한 단계 더 — 제가 인텐셔널 컴팩션(Intentional Compaction)이라고 부르는 방식입니다. 진행이 맞든 틀리든, 현재 컨텍스트를 마크다운 파일로 압축하게 시키는 거예요. 태그도 붙여두면 다음 에이전트가 탐색 과정을 반복하지 않고 바로 시작합니다.

뭘 압축해야 할까요? 컨텍스트를 차지하는 요소: 파일 탐색, 코드 흐름 이해, 파일 수정, 테스트와 빌드 로그가 다 공간을 먹습니다. MCP가 리소스와 내용들을 잔뜩 밀어넣으면 정말 답이 없습니다. 좋은 컴팩션은 지금 우리가 정확히 어떤 문제를 푸는지, 어떤 파일의 어떤 라인이 중요한지를 명확히 적는 것입니다.

왜 이렇게 컨텍스트에 집착할까요? LLM은 순수 함수에 가깝지만 상태는 없습니다. 더 좋은 출력을 얻는 유일한 방법은 더 좋은 토큰을 넣는 것입니다. 매 턴마다 Claude나 다른 코딩 에이전트는 다음 행동을 고릅니다. 다음 결과를 좌우하는 건 지금까지 대화에 들어간 내용뿐입니다. 그래서 컨텍스트는 정확성, 완전성, 크기, 그리고 방향성까지 최적화해야 합니다.

방향성이 중요한 이유: 에이전트가 틀려서 내가 고치고 혼내고, 또 틀려서 또 혼내면? 모델은 대화를 보고 "내가 틀리면 사람이 혼내는 패턴이 반복되는구나"를 학습합니다. 그러면 다음 확률 높은 토큰은 또 틀리는 쪽이 됩니다. 그게 잘못된 트라젝토리입니다.

반대로 보면 최악은 잘못된 정보, 그 다음 누락된 정보, 마지막이 과도한 노이즈입니다. Jeff Huntley가 코딩 에이전트를 많이 연구했는데 — 컨텍스트 윈도우를 과하게 쓸수록 결과가 나빠진다는 것입니다.

그래서 덤 존(Dumb Zone) 개념을 씁니다. 컨텍스트 윈도우가 대략 168,000 토큰인데, 일부는 출력과 컴팩션 용도로 예약됩니다. Claude Code 기준, 보통 40% 지점부터는 작업에 따라 체감 성능이 떨어지기 시작합니다. MCP를 너무 많이 붙이면 계속 Dumb Zone에서만 일하게 됩니다. 40%는 절대값은 아니지만 복잡한 작업 기준으로 꽤 좋은 가이드입니다. 핵심은 Dumb Zone을 똑똑하게 피하는 겁니다.

서브 에이전트: 프론트엔드, 백엔드, QA, 데이터 사이언티스트 식으로 역할 놀이하듯 나누는 건 멈추세요. 서브 에이전트의 목적은 컨텍스트 제어입니다. 큰 코드베이스에서 동작 방식을 찾고 싶다면, 새 컨텍스트 윈도우를 분기해 서브 에이전트에서 읽기와 탐색을 맡기고, 필요한 파일을 다 찾고 이해한 뒤, 부모 에이전트에는 아주 짧게 결과만 올리게 합니다. 예를 들어 파일 위치만 알려주는 식이죠. 그러면 부모 에이전트는 그 파일만 읽고 바로 구현에 들어갈 수 있습니다.

서브 에이전트보다 더 잘 먹히는 건 그 위에 얹는 프리퀀트 인텐셔널 컴팩션(frequent intentional compaction) 워크플로입니다. 단계는 리서치, 플랜, 구현입니다. 전 구간을 Smart Zone에서 유지하려고 합니다.

리서치 단계: 시스템 동작을 이해하고 핵심 파일을 찾되 최대한 객관적으로 보는 데 집중합니다. 영화 메멘토(Memento) 기억하시죠? 컨텍스트 엔지니어링 최고의 영화입니다. 주인공은 기억이 없어서 자신의 문신을 읽어가며 자기 정체와 목적을 확인합니다. 에이전트를 온보딩하지 않으면 에이전트는 없는 내용을 지어냅니다.

각 리포마다 온보딩 정보를 넣는 방법이 있습니다 — 리포가 어떻게 돌아가는지 핵심 컨텍스트를 압축해 미리 제공하는 식입니다. 이 문서는 쉽게 너무 길어집니다. 코드베이스가 커질수록 문서를 더 길게 쓰거나 중요한 정보를 빼야하는 딜레마가 생깁니다. 500만 라인 모노레포 컨텍스트를 읽는 데만 Smart Zone을 다 써버리고 정작 도구 호출은 Dumb Zone에서 하게 됩니다.

그래서 스택 단위로 쪼개는 방식, 즉 프로그레시브 디스클로저(Progressive Disclosure)를 적용합니다. 각 리포 루트에 파일 하나를 두고 하위 레벨로 갈수록 필요한 추가 컨텍스트만 계층적으로 둡니다. 파일 내용 자체는 소스 오브 트루스라 따로 문서화하지 않습니다. 대신 에이전트가 작업할 때 루트 컨텍스트를 먼저 읽고 필요한 하위 컨텍스트만 추가로 가져옵니다.

문제는 이 방식에서 문서가 금방 낡는다는 겁니다. 새 기능을 배포할 때마다 내부 문서를 갱신해야 하는데, 현실적으로 대부분 꾸준히 못합니다. 그래서 우리가 선호하는 건 온디맨드 압축 컨텍스트(on-demand compaction context)입니다. 예를 들어 인증 프로바이더와 결제, Linear 관련 기능을 만든다면, 간단한 방향만 주면 됩니다. 그러면 좋은 리서치 프롬프트나 슬래시 커맨드, 혹은 스킬이 여러 서브 에이전트를 띄워서 코드베이스를 훑습니다. 그리고 코드 자체를 근거로 지금 진짜 사실인 부분만 스냅샷 연구 문서로 모읍니다. 진실을 압축하는 겁니다.

플랜 단계: 의도를 압축하는 레버리지입니다. 실행 단계를 정확히 씁니다. 파일명과 라인 스니펫까지 넣습니다. 내 변경 뒤 어떻게 테스트할지도 아주 명확히 적습니다. 리서치와 PRD, 버그 티켓 등을 합쳐 플랜 파일을 만들고 다시 한번 압축합니다.

여기서 멘탈 얼라인먼트를 짚겠습니다. 코드 리뷰의 가장 중요한 목적이 뭔지 아시나요? 바로 멘탈 얼라인먼트입니다. 정확성 검증도 중요하지만 진짜 핵심은 코드가 왜 어떻게 바뀌는지 팀이 같은 그림을 유지하는 것입니다. 저는 매주 Go 코드 1천 줄도 읽을 수는 있습니다. 어렵지만 가능은 하죠. 다만 그렇게 하고 싶진 않습니다. 기술 리더는 코드를 안 읽는 게 아니라, 플랜을 읽는 것만으로도 업데이트를 따라가고 충분히 이해를 유지하는 것입니다.

PR에 에이전트 스레드를 붙여서 GitHub의 초록 diff만 보여주는 대신, 실제 단계와 프롬프트, 최종 빌드 통과 여부까지 공유하자는 아이디어가 있습니다. 코드량이 2~3배로 늘어날수록 팀 정렬을 유지하려면 내가 어떤 단계로 작업했고 어떻게 수동 테스트했는지 보여줘야 합니다. 그게 레버리지입니다.

플랜을 읽었을 때 실제 어떤 코드 변화가 나는지 감이 와야 합니다. 우리는 플랜에 실제 변경될 코드 스니펫까지 포함하도록 계속 개선해왔습니다. 목표는 의도를 압축하고 실행 신뢰도를 높이는 것입니다. 플랜이 길어질수록 신뢰도는 오르지만 가독성은 떨어집니다. 팀과 코드베이스마다 최적점이 있습니다.

생각을 AI에 외주 주면 안됩니다. AI는 사고를 대체하지 못합니다. 이미 한 생각을 증폭할 뿐이고, 생각이 부족하면 그 부족함도 증폭합니다. 우리 프로세스는 빌더인 당신이 플랜 생성 과정에서 에이전트와 계속 왕복하며 확인하도록 설계됐습니다.

오늘 하나만 가져가신다면: 나쁜 코드 한 줄은 나쁜 코드 한 줄이지만, 나쁜 플랜 한 줄은 나쁜 코드 수백 줄을 만들 수 있고, 잘못된 리서치 한 줄은 시스템 전체를 망가뜨릴 수 있습니다.

스펙 드리번 개발 비판: "스펙 드리번 개발"이라는 용어는 의미가 퍼져 흐려졌습니다. 마틴 파울러(Martin Fowler)가 2006년에 말했죠 — 좋은 용어도 여러 사람이 제각각 쓰기 시작하면 금방 무의미해진다고요. 에이전트도 사람, 마이크로서비스, 챗봇, 워크플로 등 100가지 뜻이 되었습니다. 스펙 드리번 개발도 지금 같은 길을 가고 있습니다. 많은 경우는 마크다운 파일을 많이 쓰는 정도에 그칩니다.

그래서 지금 실제로 먹히는 4가지를 말하겠습니다: 리서치, 플랜, 구현, 그리고 컴팩션 + 컨텍스트 엔지니어링 + Smart Zone 유지입니다. 다들 RPI라고 부르니 그건 받아들여야겠죠. 완벽한 프롬프트도 은총알도 없습니다.
