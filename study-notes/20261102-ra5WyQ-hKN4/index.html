[한글자막] Grok Bot은 매니저, Claude Code는 개발자: AI 에이전트를 함께 쓰는 법

원작자 Grok Bot · X · 업로드 2026-11-02 · 12.6분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상의 중심 생각은 한 AI에게 계획, 코딩, 검사, 보고를 모두 맡기지 말고 역할을 나누라는 것이다. 화자는 Grok Bot을 직접 코드를 쓰는 직원보다, 들어온 요구를 정리하고 적절한 코딩 에이전트에게 일을 넘긴 뒤 결과를 확인하는 매니저로 쓴다. 실제 코딩은 Claude Code, Codex, Cursor 같은 작업 에이전트가 맡을 수 있다.

여기서 매니저 역할은 두 구간을 잇는다. 앞쪽에서는 Slack, 이메일, X, Linear 등에 흩어진 요구와 문제를 모아 무엇을 만들지 정리한다. 화자는 이를 첫 구간이라는 뜻의 퍼스트 마일(first mile)이라고 부른다. 가운데에서는 코딩 에이전트가 분리된 컴퓨터나 실행 환경에서 코드를 작성한다. 뒤쪽에서는 테스트 결과와 변경 증거를 확인하고, 작업 상태를 보고하며, 다음 행동을 결정한다. 이것이 라스트 마일(last mile)이다.

읽는 법: 위에서 아래로 읽는다. 이것은 성능 수치 그래프가 아니라 역할을 나눈 개념도다. 핵심은 특정 제품명이 아니라 의도 관리 → 분리된 실행 → 증거 확인이라는 구조다. 화자도 Grok Bot만 가능한 방식은 아니며, 자체 에이전트나 Claude·Cursor의 프로젝트 기능으로 비슷한 구성을 만들 수 있다고 말한다.

영상은 로런의 일상 흐름을 “다섯 단계”라고 소개한다. Slack 피드백을 보고 Linear 티켓을 만들고, Cursor Cloud Agent를 실행해 문제를 재현하며, 여러 에이전트가 수정안을 공격적으로 시험하는 fix-and-fuzz 풀 리퀘스트를 만든다. 무작위 조작이나 Playwright 같은 도구로 사용자가 실제로 쓰듯 시험해 수정이 깨지지 않는지 확인한다. 검사가 깨끗하면 Slack으로 알리고, 변경 요청이 없을 때 한 시간 뒤 자동 병합한다는 설명이다.

다만 전사의 번호는 완전하지 않다. 1단계 다음에 작업 에이전트 실행을 설명한 뒤 곧바로 “4단계”라고 말하므로 3단계 설명이 빠져 있다. 아래 도식은 이 불일치를 숨기지 않고 그대로 표시한다.

읽는 법: 아래 화살표가 진행 순서다. 노란 상자는 실패 단계가 아니라 자료에서 설명이 누락된 단계다. 따라서 실제 3단계가 무엇인지는 이 전사만으로 확정할 수 없다. 또한 자동 병합은 모든 변경에 적용되는 규칙이 아니다.

화자는 변경이 잘못됐을 때 얼마나 크게 문제가 퍼지는지를 영향 범위(blast radius)로 나누라고 한다. 결제처럼 중요한 변경은 사람이 모든 단계에 참여해야 한다. 반대로 작은 버그나 중요도가 낮은 작업은 충분한 검증을 거쳐 더 많이 자동화할 수 있다는 주장이다. 즉, 자동화 수준은 “에이전트가 똑똑해 보이는가”가 아니라 실패했을 때의 피해와 검증 증거에 따라 정해야 한다.

에이전트를 믿는 기반도 사람의 마지막 코드 리뷰부터 시작하지 않는다. 화자가 소개한 로런의 역피라미드(inverse pyramid)는 코드 구조에 가장 많은 노력을 넣고, 자동 검사와 규칙 파일을 거쳐, 사람 리뷰에는 가장 적게 의존하는 순서를 제시한다.

읽는 법: 위에서 아래로 갈수록 상자의 폭이 좁아진다. 폭은 측정된 데이터가 아니라 화자가 권하는 노력의 우선순위를 나타낸다. 같은 실수를 계속 고친다면 다음 리뷰에서 더 조심하는 데 그치지 말고, 가능하면 코드 구조나 린트 규칙, 테스트로 고정을 옮기라는 뜻이다.

화자는 이 원리를 “에이전트는 이미 있는 것을 복사하고 가장 짧은 길을 택하므로, 쉬운 길이 옳은 길이 되게 하라”는 문장으로 설명한다. Anthropic 사례로는 6월부터 9월 사이 Claude Code를 통한 병합 풀 리퀘스트가 두 배 넘게 늘고, 되돌려야 했던 비율은 40% 넘게 줄었다고 전한다. 또 Alan Wells의 세 명 팀은 사람의 코드 리뷰 없이 풀 리퀘스트를 내보낼 검증 체계를 만들기 위해 약 6주간 새 제품 작업을 멈췄다고 소개한다. 다만 연도와 원자료의 측정 조건은 전사에 없으므로 이 수치들은 독립적으로 확인된 사실이 아니라 영상에서 전달된 사례 주장으로 읽어야 한다.

마지막 조건은 보안이다. 화자 설명에 따르면 Grok Bot의 여러 봇은 하나의 클라우드 컴퓨터에서 파일, 브라우저 세션, 명령줄 자격 증명을 공유할 수 있다. 한 봇이 쓸 수 있는 API 키를 다른 봇도 쓸 가능성이 있으므로, 자율성을 늘릴수록 에이전트 자신의 판단보다 실행 환경의 통제가 중요해진다. 샌드박스에서 실행하고, 필요한 범위의 자격 증명만 주며, 가능하면 읽기 전용 권한을 사용하고, 신뢰가 쌓이기 전에는 풀 리퀘스트 작성만 허용하고 병합 권한은 주지 않는 방식이다.

따라서 시작점은 에이전트 50개가 아니다. 화자의 권고는 작은 작업 루프 하나다. 짧은 질문이 아니라면 관리 봇이 직접 코딩하지 않고, 합격 조건(acceptance test)을 붙여 코딩 에이전트에게 넘긴다. 돌아온 증거를 확인해 풀 리퀘스트를 열고 결과를 보고한다. 같은 오류를 사람이 반복해서 고치게 되면 그 교정을 코드, 린트 규칙, 규칙 파일 순으로 위쪽에 옮긴다. 사람 리뷰는 사라지는 것이 아니라, 기계가 반복적으로 확인할 수 없는 부분에 집중한다.

여기까지만 이해하면 충분

  • 관리 에이전트는 요구 수집과 결과 확인을 맡고, 코딩 에이전트는 분리된 환경에서 실제 작업을 맡는다.
  • 신뢰는 에이전트 수가 아니라 코드 구조, 자동 검사, 명시적 규칙, 제한된 권한에서 쌓인다.
  • 자동 병합 여부는 변경의 영향 범위와 검증 증거에 따라 달라져야 한다.
  • 작은 루프 하나부터 시험하고, 반복되는 교정은 사람의 기억이 아니라 코드와 검사로 옮긴다.

"한 봇이 요구 정리부터 코딩·검사·병합까지 모두 맡으면 결과와 권한을 통제하기 어렵다" 문제

비유와 깨지는 지점

미슐랭 주방의 총괄 셰프

영상에서 소개한 비유에 따르면 개발자는 모든 요리를 직접 만들지 않는 총괄 셰프와 같다. 여러 작업자가 요리하더라도 총괄 셰프는 재료, 절차, 검사 기준, 최종 출고에 책임을 진다. 관리 에이전트는 주문과 진행 상황을 정리하고, 코딩 에이전트는 개별 요리를 만드는 작업자에 대응한다.

비유가 깨지는 지점: 소프트웨어 변경은 한 접시로 끝나지 않고 기존 코드와 사용자에게 계속 영향을 줄 수 있다. 또한 에이전트는 사람 직원과 달리 같은 오류를 빠르게 반복하거나 공유된 자격 증명을 넓게 사용할 수 있으므로 테스트와 권한 격리가 별도로 필요하다.

1. 원인

에이전트 수를 늘리기 전에 코드 구조와 자동 검증에 투자해야 하는 이유는 무엇인가?

모범 답안 보기

에이전트가 늘어나면 잘못된 패턴과 반복 실수도 더 빠르게 복제될 수 있다. 좋은 코드 경계와 자동 검사가 없으면 사람 리뷰가 모든 결과를 뒤쫓아야 하므로 규모가 커질수록 관리가 어려워진다. 반복되는 교정을 코드나 린트 규칙으로 옮기면 이후 작업에도 같은 기준이 자동 적용된다.

2. 대조

관리 에이전트와 코딩 에이전트는 무엇이 다르며, 왜 한 역할로 합치지 않는가?

모범 답안 보기

관리 에이전트는 여러 채널의 요구를 모으고 우선순위를 정하며 작업과 증거를 추적한다. 코딩 에이전트는 제한된 문맥과 실행 환경에서 실제 변경을 만든다. 역할을 나누면 작업별 문맥과 권한을 격리하고, 관리 에이전트가 여러 작업을 동시에 추적할 수 있다. 다만 제품을 나누는 것만으로 안전해지는 것은 아니며 테스트와 환경 통제가 필요하다.

3. 적용

새 자동화 작업 하나를 맡길 때 자동 병합 허용 여부를 어떤 기준으로 판단할 것인가?

모범 답안 보기

먼저 실패 시 영향을 받는 사용자와 데이터, 결제·보안 관련 여부를 확인한다. 이어 합격 조건이 명확한지, 기존 테스트와 재현 절차가 있는지, 에이전트 권한이 필요한 범위로 제한됐는지 본다. 영향 범위가 크거나 증거가 부족하면 풀 리퀘스트까지만 자동화하고 병합은 사람이 맡는다.

이번 글의 통찰

1. 신뢰는 에이전트의 성격이 아니라 시스템의 구조에서 나온다

  • [원문] 화자는 코드베이스, 정적 분석, 규칙 파일, 사람 리뷰 순으로 신뢰 기반을 쌓고, 자율성이 커질수록 통제를 실행 환경에 두라고 말한다.
  • [해석] “이 에이전트를 믿는가?”보다 “잘못해도 발견·차단·복구할 구조가 있는가?”가 더 유용한 질문이다.
  • [경계] 소개된 효과와 보안 원칙은 화자의 주장이다. 각 도구의 실제 격리 방식과 권한 모델은 별도로 확인해야 한다.

2. 자동화 수준은 작업량이 아니라 영향 범위가 결정한다

  • [원문] 작은 수정은 검사 후 자동 병합할 수 있지만, 결제처럼 중요한 변경에는 사람이 모든 단계에 참여해야 한다고 설명한다.
  • [해석] 같은 에이전트와 테스트를 쓰더라도 변경 위험에 따라 승인 절차가 달라져야 한다.
  • [경계] 전사는 초록·노랑·빨강 등급과 AI 검토 1·2·3단계를 언급하지만, 각 등급의 구체적 판정 기준은 제시하지 않는다.

3. 사례의 숫자와 출처는 검증 근거와 분리해서 읽어야 한다

  • [원문] Anthropic의 병합 풀 리퀘스트가 6월부터 9월 사이 두 배 넘게 증가하고 되돌림 비율이 40% 넘게 감소했다는 주장, 세 명의 팀이 약 6주간 검증 체계를 만들었다는 사례가 나온다.
  • [해석] 검증 기반을 만드는 선행 비용이 크더라도 이후 처리량과 안정성에 영향을 줄 수 있다는 사례로 읽을 수 있다.
  • [경계] 해당 기간의 연도, 표본, 측정 정의는 전사에 없다. 또한 로런의 흐름은 “다섯 단계”라고 소개되지만 전사에는 3단계 번호와 별도 설명이 누락됐다. META의 original_creator 후보는 Grok Bot, 소속 후보는 X이지만 provenance.note는 원본 링크를 찾지 못한 추정이라고 밝힌다. 전사 도입부의 로브 쇼크스와 이 후보의 관계도 자료만으로 확정할 수 없다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 영상은 결과를 믿는 기준을 말이나 인상보다 재현, 테스트, 증거로 옮긴다.
  • 통찰: 학습에서도 설명을 들었다는 상태와 보지 않고 원인·대조·적용을 수행하는 상태를 분리해 관찰할 수 있다.
  • 질문/행동: 다음 학습 자료에서 “이해했다”의 합격 조건을 회상 질문 하나와 적용 과제 하나로 먼저 적어 볼 수 있는가?

사업가 · 구조적 비유

  • 관련성: 화자는 RICE의 도달 범위·영향·확신·노력과 별도의 영향 범위 점수로 백로그 우선순위를 정한다고 말한다.
  • 통찰: APOM·이커머스·물류에 가상 적용한다면, 업무의 편리함만이 아니라 실패 비용과 승인 권한까지 함께 분류하는 가설을 세울 수 있다. 현재 APOM에 이런 체계가 있다는 뜻은 아니다.
  • 질문/행동: 자동화 후보 한 건에 수혜 범위, 실패 피해, 필요한 권한, 사람이 승인해야 할 지점을 표시하면 우선순위가 달라지는가?

마케터 · 구조적 비유

  • 관련성: Slack 피드백과 X의 불만을 모아 작업 문맥으로 바꾸고, 수정 결과는 테스트 증거로 확인하는 흐름이 나온다.
  • 통찰: 카피의 주장도 에이전트의 코드처럼 주장과 증거를 분리할 수 있다. 다만 코드 테스트와 고객 설득의 증거는 동일하지 않다.
  • 질문/행동: 상세페이지의 핵심 주장 하나에 대응하는 관찰 자료나 검증 조건이 실제로 있는지 표시해 볼 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 관리 에이전트, 코딩 에이전트, 합격 조건, 풀 리퀘스트, 테스트, 권한 격리를 직접 다룬다.
  • 통찰: 도구 이름보다 작업의 영향 범위, 검증 가능성, 실행 환경, 자격 증명 범위를 먼저 설계해야 한다.
  • 질문/행동: 다음 저위험 작업에서 에이전트에게 병합 권한은 주지 않고, 합격 조건과 풀 리퀘스트 생성까지만 맡겨 결과를 관찰할 수 있는가?

가치 지도

"에이전트가 만든 변경을 빠르게 처리하고 싶지만 결과와 권한을 그대로 믿기 어렵다" 문제
→ "검증 가능한 변경을 더 빠르게 받는다" 수혜자: 개발자·운영팀과 변경의 영향을 받는 사용자
→ "코드 구조, 테스트, 실행 환경, 검토 시간과 제한된 자격 증명을 제공한다" 지불자 또는 자원 제공자: 시스템 운영 주체와 작업팀
→ "병합 뒤 되돌려야 하는 변경의 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 영향 범위가 낮다고 사전 판정한 코딩 작업 3건을 합격 조건과 함께 에이전트에 맡기고, 병합은 하지 않은 채 풀 리퀘스트와 검증 증거까지만 받는다.
  • 측정 1개: 사람의 코드 수정 없이 합격 조건과 기존 테스트를 모두 통과한 작업의 비율.
  • 중단 기준 1개: 3건 중 2건 미만이 사람의 코드 수정 없이 합격 조건과 기존 테스트를 모두 통과하면 자동화 확대를 멈춘다.

# 섹션 요지
1 역할 분리 Grok Bot은 요구와 검증을 관리하고 코딩 에이전트가 실행한다.
2 로런의 작업 루프 피드백에서 티켓, 재현, 공격적 검사, 조건부 자동 병합으로 이어진다.
3 신뢰의 역피라미드 코드 구조와 자동 검사를 사람 리뷰보다 먼저 강화한다.
4 외부 사례 수치 Anthropic과 Alan Wells 팀의 처리량·검증 투자 사례가 소개된다.
5 화자의 운영 구성 Chief가 여러 작업 에이전트와 환경에 일을 위임한다.
6 백로그와 위험도 RICE와 영향 범위 점수로 작업과 검토 수준을 정한다.
7 보안 공유 컴퓨터와 자격 증명 위험 때문에 환경 통제가 필요하다.
8 시작 규칙 에이전트 수를 늘리기보다 합격 조건이 있는 루프 하나부터 시작한다.

1. 관리 에이전트와 코딩 에이전트

화자는 Grok Bot의 역할을 두 부분으로 나눈다.

  • 퍼스트 마일: Slack, 이메일, X, Linear 같은 채널에서 요구와 대화 맥락을 모아 무엇을 만들지 정리한다.
  • 라스트 마일: 작업 결과를 확인하고, 완료 여부를 추적하며, 사용자에게 상태를 보고한다.
  • 가운데 실행: Claude Code, Codex, Cursor 같은 코딩 에이전트가 실제 코드를 작성한다.

Grok Bot이 필수라는 주장은 아니다. 자체 에이전트, Claude 프로젝트, Cursor 프로젝트 등으로 비슷한 작업 흐름을 만들 수 있다고 말한다. 작업자를 분리하면 각자 컴퓨터, 문맥, 중단 수단을 가질 수 있다는 것이 화자가 제시한 장점이다.

화자는 Grok Bot과 Grok, Cursor가 주간 사용량 풀을 공유하는 통합 요금제를 쓴다고 말하며, 모든 코딩을 Grok에 맡기면 할당량을 빨리 소비할 수 있다고 주장한다. 그래서 자신은 Claude Code 구독이나 OpenCode 쪽으로 실행을 넘기는 방식을 선호한다고 설명한다. 이 요금제와 사용량 구조는 전사 밖에서 확인되지 않았다.

2. 로런의 일상 작업 루프

화자가 전달한 흐름은 다음과 같다.

  1. Slack 채널에서 앱 피드백을 관찰하고 Grok Bot이 Linear 티켓을 만든다.
  2. Linear나 Jira에서 Cursor Cloud Agent를 실행해 독립 환경에서 문제를 다루게 한다.
  3. 전사에는 3단계 번호와 별도 설명이 없다.
  4. 버그를 재현한 뒤 여러 에이전트가 수정안을 깨뜨려 보는 fix-and-fuzz 풀 리퀘스트를 만든다. 무작위 조작이나 Playwright 같은 수단이 언급된다.
  5. 검사가 깨끗하면 Slack으로 알리고, 로런이 변경을 요청하지 않을 경우 한 시간 뒤 자동 병합한다.

화자는 이 자동 병합을 모든 버그에 적용해서는 안 된다고 강조한다. 영향 범위를 초록·노랑·빨강으로 나누며, 결제처럼 중요한 변경에는 사람의 참여를 유지해야 한다고 말한다.

3. 신뢰를 쌓는 역피라미드

화자가 소개한 네 층은 다음과 같다.

  1. 코드베이스: 더 나은 구조, 강한 타입, 명확한 경계.
  2. 정적 분석과 결정적 검사: 린트, 테스트, 지속적 통합.
  3. 프롬프트와 규칙 파일: AGENTS.md, CLAUDE.md, 스킬, 버그 봇, 보안 봇.
  4. 사람 리뷰: 필요하지만 규모 확장이 가장 어려운 층.

같은 에이전트 오류를 사람이 계속 정리한다면 그 문제를 반복 가능한 린트 규칙이나 테스트로 옮겨야 한다는 주장이다. 영상은 에이전트가 기존 패턴을 복사하고 짧은 경로를 택하므로 “쉬운 것이 옳은 것”이 되도록 기반을 설계하라고 권한다.

4. 전달된 사례와 수치

화자는 Anthropic 사례에 관해 다음과 같이 말한다.

  • 6월부터 9월까지 Claude Code를 거쳐 병합된 풀 리퀘스트 수가 두 배 넘게 증가했다.
  • 되돌려야 했던 변경의 비율은 40% 넘게 감소했다.
  • 리뷰 자체를 없앤 것이 아니라, 리뷰 읽기의 대부분을 기계 쪽으로 옮겼다는 설명이 나온다.

또 Alan Wells가 세 명의 팀으로 사람 코드 리뷰 없는 출고 체계를 만들기 위해 약 6주간 새 제품 작업을 멈추고 검증을 구축했다고 전한다. 연도, 기준선, 표본과 원자료는 전사에 없으므로 독립 검증된 수치로 단정할 수 없다.

5. 화자가 소개한 자신의 운영 구성

화자는 회사 영역별 봇을 두되 관리 부담 때문에 50개의 봇을 만들지 않으려 했다고 말한다. 주 관리 에이전트는 Chief이며 다른 봇과 작업 에이전트에 일을 위임한다.

마케팅 사이트 작업을 예로 들며 다음 실행 대상을 사용한다고 설명한다.

  • Cursor Cloud Agent
  • Mac에서 실행하는 Claude Code
  • VPS에 연결된 작업 환경
  • 로컬 컨테이너

각 봇에는 연결 대상에 따른 좁은 권한을 부여한다고 말한다. 반면 Grok Bot의 vault에 어떤 기억과 스킬이 저장되고 자격 증명이 어떻게 관리되는지 충분히 보이지 않는다는 불편도 밝힌다. 그럼에도 가능성을 시험하고 공유하기 위해 현재는 위험을 감수하며 실험 중이라는 입장이다.

Theo의 T3 Code 유사 흐름은 nightly build 단계이며 매우 초기라고 소개된다. 이는 이미 안정적으로 검증된 운영 상태가 아니라 초기 시험 상태다.

6. 백로그와 변경 위험

Chief가 Slack이나 대화에서 받은 작업은 백로그에 들어가고 Notion에 저장된다고 설명한다. Linear나 Jira도 대안으로 언급된다.

화자는 백로그 분류에 RICE를 쓴다고 말한다.

  • Reach: 도달 범위
  • Impact: 영향
  • Confidence: 확신
  • Effort: 노력

여기에 실패 시 얼마나 크게 문제가 퍼지는지를 나타내는 영향 범위 점수를 추가한다. 에이전트가 능동적으로 개선안을 제안하게 할 수도 있지만, 목적 없이 실행하면 백로그가 불필요한 작업으로 빠르게 채워질 수 있다고 경고한다. 시간마다 외부 불만을 수집하는 방식도 추론 사용량과 토큰 비용을 크게 늘릴 수 있다고 말한다.

7. 공유 환경과 보안

화자 설명에 따르면 Grok Bot의 봇들은 하나의 클라우드 컴퓨터에서 파일, 브라우저 세션, 명령줄 자격 증명을 공유한다. 한 환경에 등록한 API 키를 다른 봇도 사용할 수 있으므로 주의해야 한다는 주장이다.

화자가 동의하는 보안 원칙은 다음과 같다.

  • 에이전트를 샌드박스에서 실행한다.
  • 필요한 범위의 자격 증명만 부여한다.
  • 가능하면 읽기 전용 권한을 사용한다.
  • 풀 리퀘스트 생성은 허용하되 신뢰가 쌓이기 전에는 병합 권한을 주지 않는다.
  • 통제는 에이전트의 자기 판단이 아니라 실행 환경에 둔다.

Docker와 보안 회사들이 안전한 소프트웨어 팩토리 참조 아키텍처를 발표했다는 언급이 있지만, 참여 회사 목록과 세부 규격은 전사에 없다.

8. 화자가 제안한 첫 운영 규칙

화자는 50개 에이전트를 만들지 말고 루프 하나부터 시작하라고 권한다.

  • 짧은 질문보다 큰 작업이면 관리 봇이 직접 코딩하지 않는다.
  • 합격 조건을 붙여 코딩 에이전트에 넘긴다.
  • 돌아온 증거를 확인한다.
  • 풀 리퀘스트를 열고 결과를 보고한다.
  • 반복 교정은 코드, 린트 규칙, 규칙 파일 순으로 옮긴다.
  • 사람 리뷰는 마지막에 둔다.

확인이 필요한 충돌과 불확실성

  • 로런의 흐름을 “다섯 단계”라고 소개하지만 전사에는 3단계 번호와 별도 설명이 없다.
  • META는 original_creator 후보를 Grok Bot, original_affiliation 후보를 X로 제공한다. 동시에 provenance.note는 채널이 원본 영상 링크를 찾지 못했고 화자 이름과 SNS를 기준으로 추정했다고 밝힌다.
  • 전사 도입부에는 로브 쇼크스가 이 방식을 보여준다고 나오지만, 로브 쇼크스와 META의 원작자 후보 Grok Bot 사이의 제작 관계는 제공 자료만으로 확정할 수 없다.
  • Anthropic 수치의 기간에는 월만 있고 연도가 없으며, 측정 정의와 원자료도 전사에 없다.
  • T3 Code 흐름은 nightly build의 매우 초기 상태로 소개되므로 검증된 운영 사례로 바꿔 쓰면 안 된다.
  • 화자가 소개한 요금제, 공유 컴퓨터, vault 동작은 화자의 설명이며 현재 제품 사양으로 독립 확인되지 않았다.

META의 원작자 후보는 Grok Bot, 소속 후보는 X이다. 다만 provenance.note는 채널이 원본 영상 링크를 찾지 못해 화자 이름과 SNS를 기준으로 추정한 출처라고 밝힌다.

교정 전사 (한국어)

전체 전사 펼치기

코딩 에이전트가 많아질수록 일을 맡기는 것보다 결과를 믿을 수 있는지가 더 중요해집니다. 로브 쇼크스는 Grok Bot을 코더가 아닌 매니저로 활용해 Claude Code와 클라우드 에이전트의 작업을 나누는 방법을 보여줍니다. 백로그에서 풀 리퀘스트까지 이어지는 실제 시연과 변경 사항을 검증하고 공유 환경을 안전하게 관리하는 원칙과 그 이유를 차근차근 살펴보겠습니다.

여기서 봇은 코더가 아니라 매니저 역할을 해야 합니다. Grok Bot은 크게 두 가지 일을 아주 잘합니다. 첫 번째는 Grok 팀이 ‘퍼스트 마일(first mile)’이라고 부르는 일입니다.

이는 무엇을 만들지 정하는 일입니다. 모든 소프트웨어 공장(software factory)에서 중요한 부분은 의도(intent)를 관리하는 것입니다. 예전에 Anthropic의 SDLC를 다룬 영상에서 이 부분을 많이 설명했습니다. 관심이 있다면 확인해 보세요. Grok Bot이 잘하는 일은 여러 채널에 연결되어 의도를 관리하는 것입니다. Slack, 이메일, X, Linear에 연결해서 이 모든 것을 관리하고 직접 지켜볼 수 있습니다.

이는 다음에 무엇을 만들어야 하는지, 문제가 있는지, 기능 개발에 관한 전체 대화가 어떻게 진행되고 있는지 큰 그림을 파악하는 데 매우 유용합니다.

두 번째는 ‘라스트 마일(last mile)’로, 작업을 확인하고, 진행 상황을 독촉하고, 무엇이 완료됐는지 알려 주고, 작업 목록을 지켜보는 일입니다. 여기서 한 가지 덧붙이자면, 오케스트레이터(orchestrator)로 Grok Bot을 반드시 사용할 필요는 없습니다. 직접 에이전트를 구성하거나 Claude 프로젝트, Cursor 프로젝트를 사용할 수도 있습니다. 비슷한 방식으로 작동하는 것이라면 무엇이든 괜찮습니다. 여기서 말하는 모든 내용은 여러분의 워크플로에 그대로 적용할 수 있습니다.

가운데 부분은 실제로 일을 하고 코드를 작성하는 것이며, Claude Code, Codex, Cursor 같은 코딩 에이전트(coding agent)가 바로 이를 위해 만들어졌습니다. 따라서 이 워크플로에서는 Grok Bot이 계획을 세우고 작업을 넘기도록 하면 됩니다. 결과물이 돌아오면 이를 확인하고 어떤 일이 진행되고 있는지 계속 파악할 수 있습니다.

Lauren이 정확히 이 내용을 다룬 글을 올렸습니다. 기본적으로 팀 엔지니어 봇(team engineer bot)을 만드는 방법에 관한 글입니다. 그런 다음 Slack에 봇을 추가하고 코딩 작업이 필요할 때마다 태그하면 됩니다. 클라우드 에이전트(cloud agent)나 여러분의 컴퓨터에서 실행되는 에이전트는 자체 컴퓨터를 갖고 있기 때문에, 주 오케스트레이터 봇이 직접 코드를 작성하는 대신 매니저 역할에 더 집중할 수 있습니다.

제가 Stripe, Vercel 등 여러 대기업의 소프트웨어 공장을 다루면서 흥미롭게 본 점은, 이들이 모두 Slack을 에이전트를 관리하는 방식으로 사용하는 경향이 있다는 것입니다. 따라서 이 워크플로에서는 Grok Bot 자체와 직접 작업하거나, Grok Bot을 Slack에 연결해 나머지 팀이 작업하는 스레드에서 관리할 수 있습니다. 저는 실제 작업은 Claude Code 구독이나 Cursor Cloud 에이전트가 수행하는 방식을 훨씬 선호합니다. 비용 측면에서 보면 Grok Bot은 Grok 및 Cursor와 공유되는 주간 사용량 풀 하나를 사용합니다. 이제 통합 요금제가 있습니다. Grok을 모든 코딩 작업에 사용하면 크레딧이나 할당량을 꽤 빠르게 소진하게 될 것입니다. 저는 Claude Code나 OpenCode에 가입해 둔 구독으로 작업을 넘기는 방식을 훨씬 선호합니다. 작업을 나누면 격리도 가능합니다. 각 작업자는 자체 컴퓨터와 자체 컨텍스트, 자체 종료 스위치(kill switch)를 갖기 때문입니다.

저는 Mac에서 컨테이너로 로컬 환경을 구성해 두었습니다. VPS에도 환경을 구성해 두었고, Grok Bot은 이 모든 환경에서 작업할 수 있습니다. 그렇다면 누군가 이런 워크플로를 매일 실행하면 어떤 모습일까요? 이것이 Lauren의 일일 루프(daily loop)이며, 다섯 단계로 이루어져 있습니다.

첫 번째는 앱에 대한 피드백이 올라오는 Slack 채널을 지켜보는 것입니다. 특정 주제에 대해 팀용 채널을 만들어 두면 누군가 해당 앱에 관한 컨텍스트를 그곳에 올립니다. Grok Bot은 이를 감지해 Linear에 티켓을 생성합니다. 다음으로 Linear나 Jira 등에서 Cursor Cloud 에이전트를 실행해 자체 컴퓨터에서 문제를 재현하도록 합니다. 네 번째 단계에서는 버그를 재현한 뒤, 그녀가 ‘수정 및 퍼즈(fix-and-fuzz)’ 풀 리퀘스트라고 부르는 것을 작은 에이전트 군집(swarm)과 함께 올립니다. 수정 및 퍼즈는 이전에 다른 영상에서 PStack을 다루며 설명했던 퍼징(fuzzing) 기술과 관련이 있습니다.

여기서는 에이전트 군집이 풀 리퀘스트를 열고 문제를 발생시키려고 시도합니다. 무작위로 클릭하거나 Playwright 같은 도구를 사용해 수정이 올바른지 검증하는 방식입니다. 사용자가 하듯이 실행해 아무것도 망가지지 않는지 확인합니다. 그렇기 때문에 이 단계에서 검증이 매우 중요합니다.

다섯 번째 단계에서는 퍼즈 테스트가 깨끗하게 통과하면 Slack으로 그녀에게 알리고, 그녀가 변경을 요청하지 않는 한 한 시간 뒤 자동으로 병합합니다. 여기서 한 가지 덧붙일 점이 있습니다. Anthropic의 접근 방식을 보면 모든 종류의 버그나 이슈에 이 방식을 적용하지는 않을 것입니다. 영향 범위(blast radius)에 따라 녹색, 노란색, 빨간색으로 나눌 수 있습니다. 결제와 관련된 고도로 중요한 문제라면 이 단계에서 자동 병합하지 않을 것입니다. 모든 단계에 사람이 개입하도록 해야 합니다. 하지만 많은 버그와 작은 수정, 중요하지 않은 작업은 이런 워크플로로 처리할 수 있습니다. 그녀는 영상 중 하나에서 소프트웨어 공장이라는 표현을 별로 좋아하지 않는다고도 말합니다. 그녀는 미슐랭 주방(Michelin kitchen)에 비유하며, 자신의 표현으로는 개발자인 우리가 여전히 최종 결과에 책임을 진다고 합니다. Google의 Addy Osmani도 이 개념을 거듭 강조합니다. 따라서 에이전트를 사용할 때 여러분은 기본적으로 총주방장입니다. 더 이상 모든 요리를 직접 만들지는 않지만, 나가는 모든 접시에는 여전히 여러분의 이름이 적혀 있습니다. 여러분을 위해 팀이 일하더라도, 미슐랭 주방이나 소프트웨어 공장에서 중요한 부분은 에이전트가 한 작업을 병합할 만큼 신뢰할 수 있는 때를 아는 것입니다.

이제 과장된 부분을 걷어 내 봅시다. 우리가 배울 수 있는 점은 순수한 소프트웨어 공장 방식으로 운영하는 소수의 회사들이 에이전트를 계속 추가해서 이를 실현하는 것이 아니라는 사실입니다. 이들이 하는 일은 원시 인프라와 신뢰에서 시작하는 것입니다. 에이전트 하나도 신뢰할 수 없다면 에이전트 50개를 어떻게 관리할 수 있을까요? Lauren은 이를 ‘역피라미드(inverse pyramid)’라고 부릅니다. 네 단계가 있으며, 가장 많은 노력을 맨 위에 투입해야 합니다. 첫 번째는 코드베이스 수준입니다. 더 나은 아키텍처, 더 강한 타입 시스템, 명확한 경계가 여기에 해당합니다.

그녀가 정확히 한 말은 에이전트가 기존에 있는 것을 복사하고 가장 짧은 경로를 택하는 것을 좋아한다는 것입니다. 그러니 쉬운 일이 올바른 일이 되도록 만드세요.

두 번째는 정적 분석(static analysis)입니다. 이는 에이전트가 등장하기 오래전부터 사용하던 전통적인 결정론적 테스트(deterministic test), 즉 린트 규칙, 테스트, 지속적 통합(continuous integration, CI)을 의미합니다. 에이전트가 계속해서 같은 실수를 반복한다면 이를 결정론적 린트 규칙으로 바꾸세요. 본질적으로 같은 문제를 매번 에이전트가 처리한 뒤 정리하고 있다면 여러분이 뭔가 잘못하고 있는 것입니다. 다시는 그런 일이 일어나지 않도록 이를 프로그래밍해야 합니다.

세 번째는 프롬프트, 즉 규칙 파일(rule file)입니다. AGENTS.md, CLAUDE.md, 스킬(skills), 버그 봇, 보안 봇이 여기에 해당합니다. 네 번째이자 맨 아래는 사람의 검토입니다. 우리 대부분이 가장 크게 의존하는 부분이지만, 다시 말해 확장되지 않는 부분이기도 합니다.

Anthropic에서도 비슷한 현상을 보고 있습니다. 6월부터 9월까지 Claude Code를 통해 병합된 풀 리퀘스트가 두 배 이상 늘었고, 되돌려야 했던 비율은 40% 이상 감소했습니다. 즉 풀 리퀘스트를 두 배나 많이 만들었지만, 그 풀 리퀘스트는 실제로 작동했습니다. 실제로 반영됐고, 문제를 일으키지 않았습니다. 제 지난 영상에서도 이를 확인할 수 있습니다. 이와 관련해 그들이 한 말은 다음과 같습니다. “검토를 없앤 것은 아니지만, 검토 내용을 읽는 작업의 대부분을 기계로 옮겼습니다.”

제가 다룬 모든 회사는 이 정도의 신뢰에 도달하려면 사전에 상당한 노력이 필요하다고 인정합니다. 예를 들어 Alan Wells는 사람의 코드 검토 없이 공장에서 풀 리퀘스트를 배포할 수 있도록 세 명으로 구성된 팀을 운영합니다. 이들은 모든 검증 기능을 구축하기 위해 약 6주 동안 새로운 제품 작업을 전부 중단했습니다.

그는 당시에는 매우 고통스러웠지만, 결과적으로는 그만한 가치가 있었다고 말합니다. 제 공장의 경우에는 회사의 각 영역마다 봇을 설정해 두었지만, 관리 오버헤드가 너무 커지기 때문에 봇을 50개 만들지 않으려고 최선을 다했습니다. 이상적인 세상이라면 대화할 에이전트 하나만 있으면 됩니다.

그것이 바로 제 주 에이전트인 Chief의 역할입니다. Chief는 다른 봇에 작업을 위임하고 협업하며, 그룹 채팅을 설정해 봇끼리 대화하도록 할 수도 있습니다. 제 봇들은 각각 연결되는 대상에 대해 제한된 권한을 갖고 있으므로, 필요하다면 그 권한을 다른 사람들과 공유할 수 있습니다. Grok Bot에는 모든 자격 증명을 저장하는 볼트(vault)가 있습니다. 저는 이 부분이 얼마나 편안한지 잘 모르겠습니다. Grok Bot이 하는 일의 상당 부분은 복잡성을 추상화하는 것입니다.

하지만 어떤 메모리가 저장되고 있는지, 어떤 스킬이 있는지, 볼트가 어떻게 관리되는지 직접 볼 수 없다는 점은 아쉽습니다. 앞으로도 Grok Bot을 계속 신뢰하려면 저는 그 부분을 더 많이 확인할 수 있어야 합니다. 하지만 현재로서는 Grok Bot을 믿고 가능한 것의 경계에서 실험해 보면서 여러분과 공유하는 위험을 감수할 생각입니다.

예를 들어 프로젝트 하나를 살펴봅시다. 제 마케팅 사이트입니다. 저는 Chief와 대화하고, Chief는 Cursor Cloud 에이전트나 Mac에서 실행되는 Claude Code 인스턴스를 띄웁니다. VPS에도 연결해 두었습니다. 설정은 정말 간단합니다. 기본적으로 Grok Bot에 연결을 요청하고 어떤 방식으로 실행되기를 원하는지만 알려 주면 됩니다. 이 경우 저는 Grok Bot에 특정 기준에 따라 Cursor Cloud 에이전트에서 실행해 달라고 말했습니다. 또는 Claude Code 인스턴스를 실행할 때는 사용할 기본 모델을 항상 지정합니다. Grok Bot은 이를 어딘가에 스킬로 저장하는 것 같습니다. 다시 말하지만 그 스킬이 어디에 저장되는지는 볼 수 없지만, 제게는 잘 작동하는 것 같습니다. 이런 수준의 제어를 불편하게 느끼고 스킬을 직접 볼 수 없다면, 물론 Grok Bot과 비슷한 일을 수행하도록 여러분만의 에이전트를 설정할 수도 있습니다.

제가 Grok Bot에서 가장 마음에 드는 점은 휴대폰에서 사용할 수 있다는 겁니다. 아주 쉽게 작동하죠. Mac에는 데스크톱 앱으로 설치했고, 별도의 PC에도 설치했는데, 이 모든 기기가 서로 협업할 수 있습니다. Tailscale 같은 도구로도 똑같이 할 수 있습니다. 그래서 각 폴더나 환경에서, 그것이 Cursor CLI든 Claude Code든, 보안을 위해 저만의 권한과 규칙을 설정해 둡니다. 그러면 Grok Bot이 제가 선택한 모델로 Claude Code를 헤드리스(headless) 방식으로 실행합니다. 이 채널에서 Opus 5.5에게 시각 자료를 만들도록 할 때도 똑같은 설정을 사용합니다. 여러 에이전트를 동시에 실행하고 서로 다른 터미널 클립을 녹화하죠.

Grok Bot은 클라우드 에이전트나 머신 에이전트의 오케스트레이터(orchestrator) 역할을 하기 때문에, 제 입력 없이도 특정 결정을 내릴 수 있습니다. 제 Slack에 연결되어 있고, 여러 다른 문서 소스에도 연결되어 있어서 하위 에이전트(sub-agent)가 질문을 하면 답을 제공해 막힌 부분을 해결해 줄 수 있습니다. Theo도 T3 Code로 비슷한 워크플로를 시험하고 있습니다. 그중 일부를 트윗으로 기록했죠. 이제 Grok Bot으로 자신의 전체 머신 플릿을 제어할 수 있다고 합니다. 아직 나이틀리 빌드(nightly build) 단계이고 아주 초기 단계지만, 어떤 방향으로 가고 있는지는 대략 알 수 있습니다.

그래서 Chief가 Slack이나 저와의 대화에서 수집하는 모든 내용은 기본적으로 백로그(backlog)로 들어가고, 저는 Grok Bot에게 그 내용을 전부 Notion에 저장하게 합니다. 물론 Linear나 Jira 같은 도구를 사용해도 됩니다.

저는 Grok Bot으로 백로그를 RICE 점수로 분류하는 또 다른 루틴도 설정했습니다. RICE는 처리해야 할 각 이슈나 기능의 도달 범위(reach), 영향도(impact), 확신도(confidence), 노력(effort)을 뜻합니다. 여기에 변경 영향 범위(blast radius) 점수도 매깁니다. 이렇게 설정하면 소수의 수정 작업보다 많은 사람에게 도움이 되는 작은 작업이 우선순위 상단으로 올라갑니다.

Grok Bot은 새로운 개선 사항도 자주 제안합니다. 다음에 무엇을 할지 적극적으로 제안하라고 봇에게 요청하면 됩니다. 다만 단지 무언가를 하기 위해 이렇게 하지는 마세요. 그렇게 하면 금방 백로그가 의미 없이 만든 작업들로 가득 차게 됩니다. Lauren도 개선과 관련해 비슷한 일을 합니다. Grok Bot 루틴을 사용해 Slack의 버그 보고서와 X에 올라오는 불만에서 맥락을 수집합니다.

그런 다음 이를 자신이 ‘외부 루프(outer loop)’라고 부르는 곳에 넣습니다. 다만 한 가지 주의할 점이 있습니다. 이런 방식은 Lauren처럼 이런 작업에 투입할 추론량과 크레딧이 아주 많은 사람에게는 괜찮습니다. 비슷한 일을 매시간 일정에 따라 실행하면 토큰을 엄청나게 소모하게 됩니다.

제가 한다고 말씀드린 또 한 가지는 모든 변경 사항에 변경 영향 범위를 표시하는 것입니다. 정확히 말하면 제가 직접 하는 건 아니고, 에이전트에게 시킵니다. 이것은 해당 변경이 잘못되었을 때 얼마나 많은 것이 망가질 수 있는지를 뜻합니다. 에이전트에게 중요도 수준, 즉 검토 수준을 정의하게 할 수 있습니다. 사람이 검토할지, AI 검토 레벨 1, 2, 3으로 할지도 정할 수 있죠. 여기에는 Playwright 테스트와 보안 테스트의 여러 단계가 포함됩니다.

신뢰와 관련해 마지막으로 해야 할 일은 문을 잠그는 것입니다. Grok Bot의 모든 봇은 파일, 브라우저 세션, 명령줄 자격 증명을 포함한 하나의 클라우드 컴퓨터를 공유합니다. 그러니 주의해야 합니다. Grok Bot 컴퓨터 중 하나에서 코딩 CLI에 API 키로 로그인하면, 여러분이 가진 모든 봇이 그 키를 사용할 수 있습니다.

많은 도구를 단순히 연결하고 에이전트에게 여러분의 모든 워크플로에 접근할 수 있게 하는 것이 정말 매력적이고 강력하다는 점은 저도 가장 먼저 인정하겠습니다. 빠르게 움직이고 일을 망가뜨리는 데에는 멋진 속도감이 있지만, 결국 그 결과가 돌아와 여러분을 곤란하게 만들 수밖에 없습니다.

관심이 있다면 Docker와 여러 보안 기업이 최근 보안 소프트웨어 팩토리(secure software factory) 참조 아키텍처(reference architecture)를 발표했습니다. 핵심 아이디어는 이렇습니다. 에이전트에게 더 많은 자율성을 부여할수록, 에이전트가 스스로를 감시하고 통제할 것이라고 기대하기는 어려워집니다. 통제 장치는 환경에 있어야 합니다. 저도 100% 동의합니다.

실제로는 에이전트를 샌드박스(sandbox)에서 실행하고, 범위가 제한된 자격 증명을 제공하며, 가능한 경우 읽기 전용으로 설정하고, 풀 리퀘스트(pull request)는 열 수 있게 하되 병합은 하지 못하게 해야 한다는 뜻입니다. 적어도 현재 구축된 스택을 신뢰할 수 있을 때까지는 말이죠.

Grok Bot을 오케스트레이터로 사용한다고 해서 이런 문제가 모두 해결되는 것은 아닙니다. 여러분이 설정한 각각의 코드베이스에서 중요도에 따라 결정해야 하는 문제들입니다.

좋습니다. 이 작업을 시작하고 싶다면 제 조언은 이렇습니다. 에이전트 50개를 만들지 마세요. 하나의 루프(loop)로 시작하고, 다음 규칙을 봇에 붙여 넣으세요. Grok Bot에 전달할 기본 규칙은 다음과 같습니다.

짧은 질문이 아닌 모든 요청에 대해 직접 코드를 작성하지 마세요. 인수 테스트(acceptance test)와 함께 코딩 에이전트에게 넘기세요. 증거를 확인하세요. 풀 리퀘스트를 열고 결과를 보고하세요. 그리고 에이전트를 수정해야 할 때마다 그 수정 사항을 스택의 상위 단계로 올리세요. 먼저 코드, 그다음 린트 규칙(lint rule), 그다음 규칙 파일(rules file), 마지막은 검토입니다.
