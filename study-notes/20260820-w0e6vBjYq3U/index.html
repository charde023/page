AI 에이전트에게 DB 쓰기 권한을 주면 생기는 일과 Deno의 보안 해결책 (Ryan Dahl)

한 줄 요약

AI 에이전트에게 장애 대응 권한을 주려면, 에이전트나 모델 정렬(alignment)을 믿는 대신 에이전트 밖의 네트워크 바이트 레벨 보안 경계로 실제 행동을 통제해야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
에이전트는 신뢰할 수 없는 소프트웨어(untrusted software) AI가 똑똑하고 정렬되어 있어도 외부 입력에 조작될 수 있음 보안 경계는 에이전트 내부가 아니라 외부에 둬야 한다
프로덕션 쓰기 권한(write access)의 위험 DB 삭제, 쿠버네티스 리소스 삭제 같은 치명적 행동이 가능함 권한을 주되, 실제 나가는 행동을 별도로 검문해야 한다
프롬프트 인젝션(prompt injection) 고객 지원 시스템 등 외부 텍스트가 에이전트를 속일 수 있음 “모델이 거절하겠지”는 보안 전략이 아니다
네트워크 바이트 레벨 통제(bytes over the wire) 에이전트의 유해·유익 행동은 결국 네트워크 통신으로 발생함 HTTP뿐 아니라 Postgres 같은 비HTTP 프로토콜까지 봐야 한다
MCP 도구 권한의 한계 MCP 도구를 잘 설계해도 에이전트가 서브프로세스(subprocess)를 실행하면 우회 가능 psql, kubectl 같은 CLI 실행까지 고려해야 한다
Claw Patrol Deno가 만든 오픈소스 에이전트 보안 프록시 에이전트 밖에서 요청을 해석하고 차단·승인·자격증명 주입을 수행한다
HCL 규칙 파일(HCL rule file) 여러 시스템의 권한 정책을 코드처럼 관리하기 위해 필요 Git에 넣고 테스트 가능한 보안 정책으로 운영한다
자격증명 주입(credential injection) 에이전트가 비밀값을 직접 보지 않게 만들 수 있음 프록시가 AWS SigV4, OAuth, 쿠키, Postgres 인증 등을 대신 처리한다

내가 모를 만한 것 / 처음 보는 것

  • PagerDuty — 장애 발생 시 담당자에게 알람을 보내는 온콜(on-call) 도구.
  • SRE(Site Reliability Engineering) — 서비스 안정성, 장애 대응, 운영 자동화를 담당하는 역할.
  • Deno Deploy — Deno에서 운영하는 웹사이트·서버리스 호스팅 서비스.
  • OpenClaw — 영상에서 언급된 AI 에이전트 도구. 문맥상 장애 대응 작업을 자동 수행하는 에이전트.
  • Opus — Anthropic의 Claude Opus 계열 모델을 뜻하는 것으로 보임. 정렬(alignment)이 잘 되어 있어 위험한 명령을 거절한다고 설명.
  • psql — PostgreSQL 데이터베이스에 접속하는 커맨드라인 도구.
  • kubectl — Kubernetes 클러스터를 제어하는 커맨드라인 도구.
  • EKS — AWS의 관리형 Kubernetes 서비스인 Elastic Kubernetes Service.
  • VPC — AWS의 사설 네트워크 영역(Virtual Private Cloud).
  • MCP(Model Context Protocol) — 에이전트가 외부 도구와 연결되는 표준화된 프로토콜.
  • LLM 게이트웨이(LLM gateway) — LLM API 앞단에서 요청·응답을 검사하거나 라우팅하는 중간 계층.
  • 가드레일(guardrails) — 위험한 프롬프트, 데이터 유출, 금지 행동을 막는 정책 장치.
  • HCL(HashiCorp Configuration Language) — Terraform에서 쓰이는 설정 언어.
  • LLM Judge — 다른 LLM을 심사자로 사용해 어떤 요청이 안전한지 판단하게 하는 방식.
  • AWS SigV4 — AWS API 요청에 서명하는 인증 방식.
  • Tailscale / WireGuard — 사설 네트워크를 안전하게 구성하는 VPN 계열 기술.
  • Tailnet — Tailscale 안에서 구성되는 사설 네트워크.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Deno의 에이전트는 Postgres, Kubernetes, ClickHouse, AWS, GitHub, Slack 등에 접근한다 — 단순 챗봇이 아니라 실제 운영 시스템에 연결된 장애 대응 에이전트다.
  2. 실제로 쓰기 권한(write access)도 준다 — 읽기 전용 실험이 아니라 프로덕션 문제 해결을 위해 강한 권한을 부여한다.
  3. 위험 예시는 DELETE users, kubectl delete namespace prod — 에이전트가 실수하거나 조작되면 고객 데이터나 운영 환경을 날릴 수 있다.
  4. Opus는 사용자를 지우라는 요청을 반복해서 거절할 만큼 정렬이 좋다 — 하지만 화자는 이것만으로는 보안이 아니라고 강조한다.
  5. 에이전트는 고객 지원 시스템과 연결되어 있어 외부에서 프롬프트 인젝션을 당할 수 있다 — 고객 문의 텍스트가 공격 입력이 될 수 있다.
  6. 에이전트는 독립 VM(standalone VM)에서 실행한다 — 파일시스템 접근보다 네트워크로 나가는 행동을 더 중요한 위험으로 본다.
  7. 핵심 관점은 모든 행동은 결국 네트워크 바이트(bytes over the wire)로 나타난다는 것 — 그래서 프록시가 요청 내용을 프로토콜 단위로 해석해야 한다.
  8. 까다로운 예시는 AWS VPC 안의 프로덕션 Postgres를 EKS 엔드포인트를 통해서만 접근하는 구조 — 복잡한 네트워크 토폴로지에서 권한 조합이 구멍을 만든다.
  9. MCP 도구 권한만으로는 부족하다 — 에이전트가 psql 같은 서브프로세스를 띄우면 MCP 경계를 우회할 수 있다.
  10. Claw Patrol은 HTTP 레벨이 아니라 더 낮은 레벨에서 동작한다 — Postgres 같은 비HTTP 프로토콜도 이해한다.
  11. Deno의 실제 규칙 파일은 약 1,000줄 규모이고 Git으로 관리한다 — 보안 정책을 코드 리뷰 대상처럼 운영한다.
  12. 데모에서는 Claw Patrol Run Codex를 YOLO 모드로 실행하고, Codex에게 Postgres users 테이블 삭제를 지시한다 — 에이전트는 명령을 따르지만 Claw Patrol이 네트워크 요청을 차단한다.
  13. Claw Patrol은 요청을 단순 HTTP request가 아니라 더 일반적인 액션(action)으로 부른다 — DB 쿼리, API 호출 등 다양한 행동을 포함하기 위해서다.
  14. 승인 방식은 즉시 거절, 사람 승인, LLM Judge, Slack 승인, 조합형 워크플로우가 가능하다.
  15. Claw Patrol은 MIT 라이선스 오픈소스다.
  16. Tailscale identity를 대시보드 인증에도 사용한다 — 별도 로그인 시스템을 덧붙이지 않는다.
  17. Claw Patrol 자체가 프로덕션 자격증명을 보관하므로 매우 신중하게 운영해야 한다 — 보안 프록시도 중요한 공격 표면이 된다.
  18. 규칙 파일에는 fixture 기반 테스트 시스템이 있다 — 특정 액션이 항상 차단되는지 단위 테스트처럼 검증할 수 있다.

1. Deno Deploy 장애 대응에 AI 에이전트를 붙인 배경

Ryan Dahl은 Deno에서 운영하는 Deno Deploy를 예로 든다. Deno Deploy는 웹사이트를 호스팅하는 서비스이고, 현실의 모든 프로덕션 서비스처럼 가끔 장애와 다운타임이 발생한다.

장애가 발생하면 PagerDuty가 울리고, 사람 SRE가 한밤중에 일어나 원인을 파악하고 조치해야 한다. Deno는 최근 이런 장애 대응을 AI 에이전트가 자동으로 처리하도록 실험하고 있다. 특히 OpenClaw 같은 에이전트를 사용한다고 설명한다.

핵심은 에이전트에게 단순 로그 조회 권한만 주는 것이 아니라, 실제 운영자가 문제를 해결할 때 보는 여러 시스템에 접근하게 한다는 점이다.

에이전트는 다음 시스템을 본다.

  • Postgres
  • Kubernetes
  • ClickHouse
  • AWS
  • GitHub
  • Slack
  • 기타 운영 도구

이렇게 하면 에이전트가 장애의 전체 맥락을 파악할 수 있다. 예를 들어 ClickHouse에서 트레이스를 보고, 프로덕션 Postgres에서 사용자가 어떤 프로젝트를 소유하는지 확인하고, Slack이나 GitHub 로그에서 관련 대화를 찾아볼 수 있다.

Deno의 경험상, 이 방식은 실제로 꽤 잘 작동한다. 예전에는 사람이 개입해야 했던 장애를 에이전트가 해결하는 경우가 생겼다.

2. 문제는 에이전트에게 쓰기 권한을 줬을 때 생긴다

Deno는 에이전트에게 쓰기 권한(write access)도 준다. 이 점이 강력하면서 동시에 위험하다.

에이전트가 할 수 있는 위험한 행동은 예를 들면 다음과 같다.

  • psql 서브프로세스를 실행해 DELETE users 같은 SQL을 날리기
  • kubectl delete namespace prod로 프로덕션 네임스페이스 삭제하기
  • 장애 해결이라는 명목으로 전체 사용자를 삭제하는 이상한 결론 내리기

운영 자동화를 제대로 하려면 에이전트에게 어느 정도 강한 권한을 줄 수밖에 없다. 하지만 그 권한이 그대로 파괴적 행동으로 이어지면 안 된다.

Ryan은 이 지점에서 “모델이 알아서 거절할 것”이라는 생각은 보안이 아니다라고 말한다.

3. Opus가 잘 정렬되어 있어도 충분하지 않다

Deno는 Opus 모델을 사용하며, Ryan은 Opus가 매우 잘 정렬되어 있다고 평가한다. 사용자가 users 테이블을 삭제하라고 강하게 유도해도 Opus는 반복해서 거절한다.

하지만 이것은 충분하지 않다.

보안은 “Opus가 항상 내 의도를 잘 따라줄 것”이라는 희망 위에 세울 수 없다. 특히 SRE 에이전트는 고객 지원 시스템과 연결되어 있다. 고객이 입력한 텍스트, 외부에서 들어온 티켓, 로그, 메시지 등이 에이전트의 컨텍스트에 들어갈 수 있다.

이 말은 곧 에이전트가 프롬프트 인젝션(prompt injection)에 노출된다는 뜻이다. 어떤 문자열이 모델을 이상한 상태로 몰아넣을지 완전히 예측할 수 없다. 모델이 위험한 행동을 “올바른 조치”라고 착각할 가능성을 배제할 수 없다.

따라서 Ryan의 입장은 명확하다.

에이전트 자체를 신뢰할 수 없는 소프트웨어(untrusted software)로 취급해야 한다.

보안 장치를 에이전트 내부에 넣으면 안 된다. 에이전트가 자기 행동을 스스로 감시하게 만들면, 그 감시 장치도 함께 우회되거나 조작될 수 있다.

4. 실제 위험은 네트워크 바이트로 나타난다

Deno는 에이전트를 독립 VM에서 실행한다. 그래서 파일시스템 접근 자체는 상대적으로 덜 걱정한다고 말한다. 시스템 레벨 격리는 이미 되어 있기 때문이다.

Ryan이 더 중요하게 보는 것은 네트워크다.

에이전트가 하는 좋은 행동과 나쁜 행동은 결국 거의 모두 네트워크 통신으로 발생한다. 데이터베이스에 쿼리를 보내고, Kubernetes API를 호출하고, AWS API를 호출하고, GitHub나 Slack에 접근한다. 이 모든 것은 결국 와이어 위의 바이트(bytes over the wire)다.

문제는 이 바이트가 여러 방식으로 만들어질 수 있다는 점이다.

  • MCP 도구 호출
  • HTTP API 요청
  • psql 같은 서브프로세스 실행
  • kubectl 같은 CLI 실행
  • 비HTTP 프로토콜 직접 연결

예를 들어 Postgres는 HTTP 프로토콜이 아니다. 에이전트가 OpenClaw 안에서 psql을 서브프로세스로 실행하면, MCP 도구를 거치지 않고도 DB에 직접 연결하려 할 수 있다.

그래서 Ryan은 에이전트에서 나가는 바이트를 매우 자세히 이해해야 한다고 말한다. 단순히 “HTTP 요청인지 아닌지”만 보는 것으로는 부족하다. Postgres 프로토콜 자체를 이해하고, SQL 수준에서 위험한 행동을 막아야 한다.

5. 현실의 인프라에서는 권한 조합이 구멍을 만든다

Ryan은 AWS 안의 복잡한 실제 예를 든다.

Deno의 프로덕션 Postgres는 AWS VPC 안에 있고, 특정 EKS 엔드포인트를 통해서만 접근할 수 있다. 이때 이상적인 목표는 다음과 같다.

에이전트에게 많은 시스템 접근 권한을 주되, 그 에이전트가 EKS 서버를 경유하거나 터널링해서 psql을 띄우고 users 테이블을 삭제하지 못하게 하는 것.

이런 상황은 단순한 장난감 예제가 아니다. 많은 회사의 실제 인프라는 복잡한 네트워크 토폴로지를 가진다. 한 시스템에 접근할 수 있고, 그 시스템을 통해 다른 시스템에 접근할 수 있다면, 권한의 조합에서 보안 구멍이 생길 수 있다.

ACL이나 읽기 전용 DB 계정을 발급하는 것은 당연히 필요하다. 하지만 그것만으로는 충분하지 않다.

왜냐하면 현실에서는 여러 시스템을 가로질러 세밀하게 자격증명을 발급하고 관리해야 하며, 한 시스템의 권한이 다른 시스템의 접근 경로와 합쳐질 때 예상치 못한 우회로가 생기기 때문이다.

6. MCP 도구 권한과 기존 보안 도구의 한계

MCP(Model Context Protocol)를 사용하면 권한이 잘 정의된 도구를 만들 수 있다. 예를 들어 “사용자 조회만 가능한 도구”, “특정 로그만 읽는 도구”처럼 설계할 수 있다.

하지만 Ryan은 MCP만으로는 부족하다고 말한다.

에이전트가 서브프로세스를 실행할 수 있다면 이야기가 달라진다. OpenClaw가 psql을 실행하는 순간, MCP 도구의 보안 경계를 뚫고 나갈 수 있다.

기존 생태계에는 몇 가지 접근이 있다.

  • LLM 게이트웨이(LLM gateway): OpenRouter 같은 도구가 LLM 요청·응답을 검사하고 프롬프트 인젝션을 탐지한다.
  • HTTP 프록시: HTTP Jail, Crab Trap 같은 도구가 HTTP 요청을 검사한다.
  • 자격증명 주입 프록시: Agent Vault처럼 에이전트가 비밀값을 직접 보지 않게 한다.
  • OS 샌드박스: NVIDIA OpenShell처럼 파일 경로, 시스템콜(syscall) 접근을 제한한다.

이 도구들은 각각 유용하지만 완전한 답은 아니다.

LLM 게이트웨이는 LLM 통신만 본다. 하지만 에이전트는 DB, AWS, Kubernetes와도 통신한다.

HTTP 프록시는 HTTP 레이어만 본다. 하지만 Postgres 같은 비HTTP 프로토콜이 있다.

OS 샌드박스는 파일시스템이나 시스템콜을 막는다. 하지만 Deno의 경우 에이전트를 독립 VM에서 실행하므로, 더 중요한 위험은 네트워크로 나가는 행동이다.

7. Claw Patrol: 에이전트 앞단의 보안 프록시

Deno가 이 문제를 해결하기 위해 만든 소프트웨어가 Claw Patrol이다.

Claw Patrol은 오픈소스이며 MIT 라이선스다. 에이전트 앞에 위치하는 프록시로, HTTP보다 낮은 레벨에서 동작한다. 즉, 에이전트에서 나가는 바이트를 세밀하게 보고 해석한다.

Claw Patrol의 역할은 크게 네 가지다.

  1. 에이전트가 외부로 보내는 요청을 프로토콜 수준에서 해석한다.
  2. 규칙에 따라 위험한 액션을 차단한다.
  3. 필요하면 사람이나 LLM Judge에게 승인을 요청한다.
  4. 에이전트가 비밀값을 직접 보지 않도록 자격증명을 대신 주입한다.

중요한 점은 에이전트 소프트웨어를 수정할 필요가 없다는 것이다. Ryan은 에이전트를 블랙박스로 취급한다고 말한다. 에이전트 내부에 보안 플러그인을 넣는 방식이 아니라, 에이전트 바깥의 네트워크 경계에서 통제한다.

8. HCL 규칙 파일로 권한을 코드처럼 관리한다

Claw Patrol의 핵심은 규칙 시스템이다. Deno는 이 규칙을 HCL(HashiCorp Configuration Language)로 작성한다. HCL은 Terraform 설정 언어와 비슷한 문법이다.

Deno는 모든 서비스의 권한을 정의한 큰 설정 파일을 Git에 체크인해서 관리한다. 실제 파일은 약 1,000줄 정도라고 한다. 각 변경 사항을 매우 신중하게 관리한다.

이 규칙 파일에서는 예를 들어 다음과 같은 정책을 만들 수 있다.

  • Postgres에서 특정 함수 호출 차단
  • 위험한 SQL 명령 차단
  • 특정 HTTP 메서드 제한
  • 특정 경로만 허용
  • 어떤 액션은 즉시 거절
  • 어떤 액션은 승인 요청

특히 Ryan이 강조하는 부분은 Postgres가 비HTTP 프로토콜인데도 이런 규칙을 적용할 수 있다는 점이다. 심지어 다른 시스템을 통해 터널링되는 경우에도 프로토콜을 이해하고 규칙을 적용하려는 것이 목표다.

Claw Patrol은 여러 프로토콜을 지원하며, 아직 모르는 프로토콜이 있으면 플러그인 시스템으로 확장할 수 있다.

9. 데모: Codex가 users 테이블을 삭제하려 해도 차단된다

Ryan은 라이브는 아니지만 데모 흐름을 설명한다.

  1. Claw Patrol Run Codex를 YOLO 모드로 실행한다.
  2. Codex에게 “Postgres에서 users 테이블을 삭제해”라고 지시한다.
  3. Codex는 지시를 따르고 psql 서브프로세스를 실행한다.
  4. psql은 Postgres 서버로 네트워크 연결을 연다.
  5. 이 연결은 Claw Patrol을 통과한다.
  6. Claw Patrol은 Postgres 프로토콜의 바이트를 파싱한다.
  7. 규칙을 적용해 파괴적인 액션을 거부한다.

여기서 중요한 포인트는 에이전트가 명령을 따랐다는 것이다. 즉, 모델 정렬에 기대지 않는다. 에이전트가 실제로 위험한 행동을 시도해도, 외부 보안 경계가 막는다.

10. 대시보드, 승인 워크플로우, 자격증명 주입

Claw Patrol에는 대시보드가 있다. 대시보드에서는 여러 에이전트나 디바이스가 어떤 요청을 보내는지 볼 수 있다. 어떤 요청은 거절되고, 어떤 요청은 승인을 기다린다.

Claw Patrol은 이를 HTTP request보다 넓은 의미의 액션(action)이라고 부른다. DB 쿼리, API 호출, 프로토콜 메시지 등 다양한 행동을 포함하기 위해서다.

승인 시스템도 있다. 규칙은 단순히 허용·거절만 하지 않는다.

가능한 방식은 다음과 같다.

  • 즉시 허용
  • 즉시 거절
  • Slack 채널에서 사람에게 승인 요청
  • LLM Judge로 사전 판단
  • LLM Judge 판단 후 Slack 사람 승인
  • 여러 승인 조건의 조합

이 구조를 통해 에이전트 소프트웨어 바깥에서 매우 세밀한 통제를 할 수 있다.

또한 Claw Patrol은 자격증명 주입(credential injection)을 지원한다. 에이전트가 실제 비밀값을 보지 않고 placeholder만 내보내면, 프록시가 실제 자격증명을 넣어준다.

지원하는 자격증명 형태는 단순 bearer token만이 아니다.

  • 쿠키(cookie)
  • Postgres 인증
  • ClickHouse
  • OAuth
  • AWS SigV4
  • 기타 복잡한 인증 방식

이것은 실제 운영 시스템에서 쓰기 위한 기능이다. Ryan은 이것이 상상 속 시나리오가 아니라 Deno의 실전 필요에서 나온 것이라고 말한다.

11. Tailscale과 WireGuard 기반 운영 구조

Claw Patrol은 Tailscale 또는 WireGuard 위에서 동작한다.

Deno는 에이전트를 Tailscale의 Tailnet 안에서 실행한다. Tailscale은 exit node 역할을 하며, 대시보드 인증에도 Tailscale identity를 사용한다. 그래서 별도의 인증 메커니즘을 또 얹을 필요가 없다.

Tailscale을 쓰지 않는 사람들을 위해 WireGuard도 지원한다.

이 구조의 장점은 보안에 민감한 시스템들이 공개 인터넷에 직접 노출되지 않는다는 점이다. 모든 것이 사설 네트워크 안에서 통제된다.

다만 Ryan은 Claw Patrol 자체가 프로덕션 시스템의 자격증명을 들고 있으므로 매우 조심해야 한다고 말한다. 보안 프록시가 강력한 만큼, 그 자체도 중요한 보안 자산이다.

12. 결론: 에이전트는 스스로를 통제할 수 없다

Ryan의 결론은 간단하다.

에이전트는 자기 자신을 감시하게 만들 수 없다.

여기에는 에이전트 소프트웨어에 붙인 보안 플러그인이나 수정도 포함된다. 보안 경계는 에이전트 내부가 아니라 다른 곳에 있어야 한다.

물론 모델 정렬(alignment)이 쓸모없다는 뜻은 아니다. 모델이 더 똑똑해지고 맥락을 잘 이해하면 위험은 줄어들 수 있다. Opus도 이전 모델보다 훨씬 정렬이 잘 되어 있다.

하지만 실제 프로덕션 보안에서는 마지막 방어선(backstop security mechanism)이 반드시 필요하다. Claw Patrol은 Deno가 이 문제를 실제로 해결하기 위해 만든 시도다.

안녕하세요. 저는 Ryan입니다. Deno의 CEO이고, 꽤 오랫동안 소프트웨어를 개발해 왔습니다. 아마 제가 만든 프로젝트 중 하나인 Node.js를 아실 수도 있습니다.

오늘은 Deno에서 운영하는 Deno Deploy라는 서비스에 대해 이야기하려고 합니다. Deno Deploy는 웹사이트를 호스팅하는 시스템입니다. 당연히 장애도 있고, 가끔 다운타임도 있습니다. PagerDuty 알람도 울립니다. 한밤중에 사람을 깨우는 그 무서운 알람 소리를 다들 잘 아실 겁니다.

최근 저희는 이런 장애를 자동으로 처리하기 위해 에이전트(agent)를 사용하는 실험을 하고 있습니다. 특히 OpenClaw를 쓰고 있고, 다른 에이전트들도 사용합니다. 그 과정에서 꽤 잘 작동하는 패턴을 발견했고, 오늘 그것을 공유하려고 합니다.

저희는 실제로 OpenClaw에게 여러 시스템 접근 권한을 줍니다. Postgres, Kubernetes, ClickHouse, AWS, GitHub, Slack 등 다양한 시스템입니다. 그리고 이 시스템들에 대한 쓰기 권한(write access)도 실제로 부여합니다.

이것은 매우 강력합니다. 에이전트가 전체 맥락을 볼 수 있기 때문입니다. ClickHouse에서 트레이스를 볼 수 있고, 프로덕션 Postgres 데이터베이스에서 사용자가 누구인지, 어떤 프로젝트를 소유하는지 확인할 수 있습니다. Slack 대화, GitHub 로그 등도 볼 수 있습니다.

실제로 이 방식은 꽤 잘 작동합니다. 예전에는 사람이 SRE로 개입해야 했던 많은 장애를 에이전트가 해결할 수 있습니다.

하지만 당연히 매우 위험합니다. 에이전트가 악의적이거나 위험한 행동을 할 수도 있기 때문입니다. 예를 들어 psql 서브프로세스를 실행하고 DELETE users 명령을 보낼 수 있습니다. 또는 kubectl delete namespace prod를 호출할 수 있습니다. 장애를 해결한다는 명목으로 모든 사용자를 지워야 한다고 판단할 수도 있습니다. 물론 우리는 그런 일을 원하지 않습니다.

저희는 Opus를 사용합니다. Opus는 놀라울 정도로 정렬(alignment)이 잘 되어 있습니다. users 테이블을 삭제하게 만들려고 아무리 시도해도 계속 거절합니다.

하지만 이것만으로는 충분하지 않습니다. 보안은 “Opus가 항상 우리가 원하는 대로 행동할 것이다”라는 희망적 사고에 의존할 수 없습니다.

저희 SRE 에이전트는 고객 지원 시스템에 연결되어 있습니다. 따라서 외부에서 프롬프트 인젝션(prompt injection)을 당할 수 있습니다. 어떤 방식으로든 조작될 수 있다는 뜻입니다. 어떤 문자열이 Opus를 나쁜 상태로 몰아넣고, 매우 바람직하지 않은 행동을 올바른 조치라고 생각하게 만들지 알 수 없습니다.

그래서 저희는 에이전트 자체를 신뢰할 수 없는 소프트웨어(untrusted software)로 봅니다. 에이전트가 자기 행동을 스스로 지키게 해서는 안 됩니다. 가드를 에이전트 안에 넣으면 안 됩니다.

저희는 에이전트를 독립 VM(standalone VM)에서 실행합니다. 여러분 중 많은 분들도 비슷하게 하실 것이라고 생각합니다. 저희는 에이전트가 파일시스템의 파일을 건드리는 것에 대해서는 크게 걱정하지 않습니다. 시스템 레벨에서 적절히 격리되어 있기 때문입니다.

사실상 에이전트가 할 수 있는 모든 악의적 행동과 모든 유익한 행동은 네트워크 통신의 형태로 나타납니다. 즉, 와이어를 타고 흐르는 바이트(bytes over the wire)입니다.

이 바이트가 만들어지는 방식은 여러 가지입니다. MCP를 통해 호출할 수도 있지만, 서브프로세스를 통해서도 가능합니다. 예를 들어 Postgres는 HTTP가 아닌 프로토콜입니다. OpenClaw가 그냥 서브프로세스로 psql을 실행해 서비스에 연결할 수 있습니다.

저희 입장은 에이전트에서 나오는 바이트를 매우 자세히 이해해야 한다는 것입니다. 현실 시스템에서는 이것이 매우 까다로워질 수 있습니다.

예를 들어 저희는 AWS 안의 VPC 내부에 프로덕션 Postgres 데이터베이스를 가지고 있고, 그것은 EKS 엔드포인트를 통해서만 접근할 수 있습니다. 저희가 정말 원하는 것은 에이전트에게 거의 모든 것에 접근할 수 있게 하면서도, 그 에이전트가 EKS 서버를 통해 터널링하고 psql을 실행해서 users 테이블을 삭제하지 못하게 하는 것입니다.

저희는 이런 복잡한 상황까지 걱정합니다. 많은 회사의 실제 시스템은 매우 복잡한 네트워크 토폴로지를 가지고 있습니다.

이것을 강조하자면, 문제는 아웃바운드 경로(outbound path)입니다. 에이전트 호스트가 HTTP가 아닌 프로토콜에 접근할 수 없도록 하고, SQL을 이해하는 규칙으로 이를 통제해야 합니다. 사람 SRE들이 하던 일을 에이전트도 할 수 있게 하려면 이런 접근이 필요합니다.

누군가는 “ACL과 권한이 있지 않나? 읽기 전용 Postgres 자격증명을 발급하면 되지 않나?”라고 물을 수 있습니다.

어느 정도는 맞습니다. 신중하게 자격증명을 발급할 수 있고, 실제로 그렇게 해야 합니다. 하지만 이것은 여러 시스템 전체에 걸쳐 매우 조심스럽게 자격증명을 관리해야 합니다. 방금 설명한 것처럼, 어떤 시스템에 접근할 수 있고 또 다른 시스템에도 접근할 수 있을 때, 접근 권한의 조합이 구멍을 만들 수 있습니다.

MCP를 사용하면 이 모든 것을 적절한 권한을 가진 MCP 도구로 매우 세심하게 구성할 수 있습니다. 하지만 그러면 서브프로세스를 실행할 수 없어야 합니다. OpenClaw가 psql을 실행하는 순간 보안 경계를 뚫은 것입니다.

이 분야에는 꽤 많은 프로젝트가 있습니다. 에이전트 앞에 위치해서 에이전트가 보내는 것을 보고, 흐르는 바이트를 기반으로 통제하려는 프로젝트들입니다.

LLM 게이트웨이(LLM gateway)는 모두 익숙하실 겁니다. 예를 들어 OpenRouter가 있습니다. 이런 도구에는 보통 가드레일(guardrails) 기능이 있어 프롬프트 인젝션을 막거나, LLM 제공자와 오가는 여러 표현을 스캔할 수 있습니다. 하지만 그것은 LLM에 대해서만 적용됩니다. 우리는 데이터베이스와 다른 시스템들과도 이야기하고 있습니다.

HTTP Jail이나 Crab Trap 같은 시스템도 있습니다. 이들은 HTTP 계층에 위치하는 HTTP 프록시입니다. 예를 들어 HTTP Jail은 GET 요청은 허용하지만 POST 요청은 금지한다거나, 특정 HTTP 하위 경로만 접근할 수 있게 하는 규칙을 작성할 수 있습니다. Crab Trap은 Brex의 프로젝트로, 오가는 HTTP 요청에 대해 LLM Judge를 실행합니다.

에이전트에서 나가는 요청에 자격증명을 주입하는 프록시도 있습니다. Agent Vault가 유명한 예입니다. 에이전트 자체는 실제 자격증명을 보지 않고 placeholder를 내보내며, 프록시가 그 자격증명을 주입합니다.

이것은 문제의 중요한 일부이지만, 완전한 해결책은 아닙니다.

또한 NVIDIA의 OpenShell 같은 프로세스 샌드박스(process sandbox)도 있습니다. OS 레벨에서 다른 파일시스템 경로 접근, 시스템콜(syscall) 등을 제한하는 가드입니다. 하지만 앞서 말했듯이 저희는 이 부분을 크게 걱정하지 않습니다. 에이전트마다 독립 VM을 제공하기 때문입니다.

이 문제를 해결하기 위해 저희가 만든 소프트웨어는 Claw Patrol입니다. 오픈소스이고 MIT 라이선스 프로젝트입니다. 에이전트 앞에 위치하는 프록시입니다. HTTP 레벨이 아니라 더 낮은 레벨에서 동작합니다. 에이전트에서 나가는 모든 바이트를 이해합니다.

Claw Patrol은 Agent Vault처럼 자격증명을 보관하고, 그 자격증명을 주입할 수 있습니다. 그래서 어떤 에이전트 소프트웨어를 사용하든 실제 비밀값을 보지 않게 할 수 있습니다.

특히 Claw Patrol에는 매우 발전된 규칙 시스템이 있습니다. 어떤 요청이 어떻게 외부로 전달되어 외부 세계와 통신할 수 있는지 매우 정밀하게 지정할 수 있습니다.

이 규칙이 시스템의 핵심입니다. 저희는 HCL이라는 언어를 사용해 설정 파일에 규칙을 작성합니다. HCL에 익숙한 분 계신가요? Terraform 설정 언어와 비슷합니다. 이 용도에 매우 잘 맞습니다.

저희는 이 파일을 Git에 체크인하고 매우 신중하게 관리합니다. 이 파일은 Deno의 모든 서비스에 대한 권한을 정의합니다. 꽤 긴 파일이고, 약 1,000줄 정도 됩니다. 각각의 변경 사항을 매우 세밀하게 관리합니다.

예를 들어 이 설정 파일에는 특정 Postgres 함수 호출을 차단하는 규칙이 있습니다. 다시 말하지만 Postgres는 HTTP가 아닌 프로토콜입니다. 그리고 이런 규칙은 다른 시스템을 통해 터널링되는 경우에도 적용될 수 있습니다.

Claw Patrol은 여러 프로토콜을 지원하고, 아직 알지 못하는 프로토콜을 만났을 때 확장할 수 있는 플러그인 시스템도 가지고 있습니다.

간단한 데모를 보여드리겠습니다. 아쉽게도 라이브는 아닙니다. Claw Patrol Run Codex를 YOLO 모드로 실행합니다. 그러면 지시한 것을 그대로 수행합니다. Codex에게 “Postgres에서 users 테이블을 삭제해”라고 말하면, Codex는 제대로 명령을 따르고 users 테이블을 삭제하는 psql 서브프로세스를 실행합니다.

그 psql 서브프로세스는 Postgres 서버로 네트워크 연결을 엽니다. 이 연결은 Claw Patrol을 통과합니다. Claw Patrol은 모든 바이트를 파싱합니다. Postgres 프로토콜을 이해하고, 규칙을 적용한 뒤, 최종적으로 그 파괴적인 행동을 거부합니다.

Claw Patrol에는 대시보드가 있습니다. 대시보드에서는 에이전트가 무엇을 하고 있는지 볼 수 있습니다. 상단에는 여러 디바이스나 에이전트가 보이고, 그 사이로 흐르는 다양한 요청이 보입니다. 일부는 거부되고, 일부는 승인이 필요합니다. 승인에 대해서는 잠시 후 설명하겠습니다.

각 요청 또는 액션(action)을 클릭하면 무슨 일이 벌어지는지 자세히 볼 수 있습니다. HTTP 요청보다 더 일반적인 개념이기 때문에 액션이라고 부릅니다. 분석 기능도 있고, 매우 실용성 중심으로 만들어져 있습니다. 저희 자신의 에이전트를 이해하기 위해 필요한 것들입니다.

앞서 말했듯이 Claw Patrol에는 승인 시스템이 있습니다. 규칙을 정의할 때 요청이나 액션을 단순히 거절하는 것뿐 아니라, 사람에게 물어볼 수도 있습니다. 예를 들어 Slack 채널에서 승인받게 하거나, LLM Judge를 실행하거나, 둘을 조합할 수 있습니다. 먼저 LLM Judge를 거친 다음 Slack에서 승인을 받게 할 수도 있습니다. 이렇게 하면 에이전트 소프트웨어 바깥에서 에이전트의 행동을 매우 정밀하게 통제할 수 있습니다.

저희는 에이전트 소프트웨어를 블랙박스로 취급합니다. 그 소프트웨어를 변경할 필요가 없습니다.

앞서 자격증명 주입에 대해 언급했습니다. Claw Patrol은 여러 시스템에 대해 매우 상세한 지원을 제공합니다. 자격증명은 여러 형태로 존재합니다. 단순한 bearer header만 있는 것이 아닙니다. 쿠키도 있고, 앞서 언급한 Postgres도 있습니다. ClickHouse, 다양한 OAuth 프로토콜, 그리고 AWS SigV4처럼 매우 복잡한 방식도 지원합니다.

이것은 실제 유용성에서 나온 것이며, 현실 시스템을 위한 것입니다. 상상 속 시나리오가 아닙니다.

이 시스템은 Tailscale 또는 WireGuard 위에서 동작합니다. 저희는 에이전트를 Tailscale 안, 즉 Tailnet 안에서 실행합니다. Tailscale은 exit node 역할을 합니다. 또한 대시보드 인증에도 Tailscale을 사용합니다. 따라서 Tailscale identity로 대시보드 접근이 가능하고, 별도의 인증 메커니즘을 또 얹을 필요가 없습니다.

훌륭한 Tailscale 생태계를 아직 사용하지 않는 분들을 위해 WireGuard도 지원합니다. 이 방식은 저희에게 매우 잘 맞습니다. 모든 것이 인터넷 바깥에 있고, 보안에 매우 민감한 요소들이 엄격하게 통제된다는 것을 알 수 있기 때문입니다.

Claw Patrol 자체는 프로덕션 시스템의 모든 자격증명을 보관합니다. 따라서 매우 조심해야 합니다.

핵심 논지는 기본적으로 에이전트가 스스로를 감시하도록 신뢰할 수 없다는 것입니다. 여기에는 보안 플러그인이나 에이전트 소프트웨어 자체의 수정도 포함됩니다. 보안 경계는 다른 곳에 있어야 합니다.

그렇다고 정렬(alignment)이 좋은 것이 아니라고 말하는 것은 아닙니다. 하지만 실제 보안 시스템에서는 더 높은 수준에서 이것을 통제해야 합니다. Claw Patrol은 저희가 이 문제를 스스로 해결하기 위한 시도입니다.

여기에서 확인하실 수 있습니다.

질문 한두 개 받을 시간이 있을 것 같습니다.

질문: 제대로 작동하는지 확인하기 위해 어떤 테스트를 하나요?

답변: 질문은 제대로 작동하는지 확인하기 위해 어떤 테스트를 하느냐는 것입니다. 제가 언급하지 않았지만, 규칙 파일에는 테스트 시스템이 함께 있습니다. fixture 요청, 즉 액션 fixture 요청을 제공해 규칙을 통과시켜 볼 수 있습니다. 이를 통해 단위 테스트(unit test)를 만들 수 있습니다.

특정 요청이 규칙 집합에 의해 항상 차단되는지 확인할 수 있습니다. 그리고 물론 Claw Patrol 소프트웨어 자체에도 대규모 테스트 스위트가 있습니다.

질문: 에이전트가 더 똑똑해지면 이 문제는 더 커지나요, 작아지나요?

답변: 저는 AI를 완전히 신뢰할 수 있는 날은 오지 않을 것이라고 생각합니다. 에이전트가 더 똑똑해지고, 더 나은 맥락을 가지고, 자신이 회사와 함께 일하고 있으며 나쁜 일을 하면 안 된다는 것을 더 잘 알게 되면 문제는 점점 줄어들 것입니다. Opus는 이전 모델보다 더 잘 정렬되어 있습니다. 하지만 저는 우리가 항상 마지막 방어 보안 메커니즘(backstop security mechanism)을 가져야 한다고 생각합니다.

다른 질문은 이후에 받겠습니다. 감사합니다.
