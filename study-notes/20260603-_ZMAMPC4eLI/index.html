# 섹션 요지
1 배경 — AI 코딩 현황 50%+ 코드가 LLM 생성, 에이전트 도구로 전환 중
2 pass rate의 한계 기능 정확도 지표 ≠ 엔터프라이즈 품질
3 Sonar 분석 결과 53개 모델 × 4,444 과제 → 보안·버그·복잡도·bloat 수치 공개
4 리더보드 상세 sonar.com/leaderboard, 모델별 세부 지표 제공
5 문제 원인 3가지 학습 데이터 혼합 품질 / 내장 보안 결함 / LLM 비결정성
6 ACDC 프레임워크 Guide(컨텍스트·데이터 정화) → Verify(커밋 전 분석) → Solve(리미디에이션 에이전트)

1. 배경 — AI 코딩 시대의 신뢰 문제

Pragmatic Engineer 2026년 3월 서베이 기준 개발자의 55%가 AI 에이전트를 정기적으로 사용한다. 개발 환경은 VS Code·JetBrains에서 Cursor·Windsurf·Claude Code·Codex·Devin 같은 에이전트 플랫폼으로 이동했고, 영어가 새 프로그래밍 언어로 불린다. 그러나 LLM이 생성한 코드가 유지보수 가능한지, 보안이 충분한지, 읽을 수 있는지는 검증이 필요하다.

2. 현재 LLM 평가의 공백

LLM 업체들은 HumanEval·MBPP·SWE-bench 기반 pass rate(80~84%)를 홍보한다. 이는 기능 정확도 측정이다. 빠져 있는 항목:

  • 보안 취약점 밀도
  • 실세계 신뢰성 (real-world reliability)
  • 엔지니어링 아키텍처 적합성
  • 코드 유지보수성 및 기술 부채 규모

3. Sonar 분석 결과 상세

데이터셋: 4,444개 오픈소스 Java 과제 (공개 데이터셋 기반 분석) 도구: SonarQube Enterprise

주요 발견:

  • 코드 비대화: 최신·고성능 모델일수록 더 많은 라인 생성. GPT 4.0 세대 대비 GPT 5.4 계열은 5배 이상 코드 생성
  • 보안: Claude Sonnet 4.6이 백만 라인당 300건으로 가장 높은 보안 이슈 밀도
  • 복잡도: 새 모델일수록 사이클로매틱 복잡도·인지 복잡도 모두 상승 추세
  • 버그 추세: 전체 버그 수는 모델 성숙에 따라 줄지만, 새로 생기는 버그는 더 미세해서 인간이 탐지하기 어려움
  • 취약점 추세: 전체 건수는 감소하나, 유형이 고도화됨

Sonar 리더보드 (sonar.com/leaderboard): 53개+ 모델 pass rate·버그 밀도·복잡도·보안 이슈를 공개 비교. 모델별 세부 드릴다운 제공.

4. 문제 원인 3가지

  1. 학습 데이터 혼합 품질 — 고품질 코드와 저품질 코드가 섞인 학습 데이터
  2. 내장 보안 결함 — 학습 데이터에 포함된 취약한 코드 예제를 모델이 그대로 학습
  3. LLM 비결정성 — 동일 프롬프트에도 매번 다른 코드 생성. 회사 코드베이스·아키텍처 컨텍스트 부재. 낮은 설명 가능성(explainability)

5. ACDC 프레임워크 (Agent-Centric Development Cycle)

Sonar가 제안하는 3단계 검증 루프:

Guide 단계 (내부 루프) - Sonar Context Augmentation: 전체 코드베이스를 LLM 컨텍스트로 주입 - Sonar Sweep (프라이빗 베타): 학습·참조 데이터의 보안 결함 사전 정화

Verify 단계 - SonarQube Agentic Analysis (오픈 베타): MCP 연동 에이전트가 커밋 전 1~5초 안에 정적 분석 수행. 문제 발견 시 에이전트가 즉시 수정 후 커밋 - PR 단계에서 SonarQube 분석 재실행 → Quality Gate 평가

Solve 단계 - SonarQube Remediation Agent (오픈 베타): Quality Gate 실패 시 자동으로 이슈별 수정 PR 생성. 수정 후 컴파일·분석 재실행, 회귀 발생 시 해당 수정 폐기. 기술 부채 대량 해소 시 이슈 일괄 선택 → 에이전트 할당 가능

지원 범위: 40개+ 프로그래밍 언어 및 프레임워크, 주요 DevOps 툴체인, IDE 마켓플레이스 통합

전체 전사 펼치기

안녕하세요, 저는 Prasenjit Sarkar입니다. 오늘 세션 주제는 "LLM이 엔터프라이즈급 코드를 생성할 수 있는가"입니다.

첫 번째 슬라이드를 보겠습니다. 두 달 전과 비교해 소프트웨어 개발 환경이 많이 바뀌었습니다. 예전에는 IDE에서 직접 코드를 작성했지만, 이제는 에이전트 중심으로 전환됐습니다. 영어로 지시만 하면 에이전트가 실행하고, 인간은 생성된 코드를 리뷰하는 역할로 바뀌었죠.

개발 도구도 VS Code·JetBrains에서 Cursor·Windsurf·Claude Code 같은 에이전트 코딩 플랫폼으로, 그리고 이제는 Codex·Claude·Devin·Gemini CLI 같은 완전 에이전트 플랫폼으로 이동하고 있습니다. Pragmatic Engineer가 2026년 3월에 실시한 서베이에 따르면 LLM이 소프트웨어 개발의 50%를 담당하며, 55%의 개발자가 AI 에이전트를 정기적으로 사용합니다.

그런데 문제가 있습니다. 이 코드를 믿을 수 있는가? 유지보수가 되는가? 보안은 괜찮은가? 가독성은 있는가? 이 질문에 답하기 위해 모델들을 직접 평가해봤습니다.

LLM 업체들은 HumanEval·MBPP·SWE-bench 기반 pass rate를 홍보합니다. 80~84% 수준이죠. 이는 기능 정확도 측정입니다. 그러나 보안, 실세계 신뢰성, 엔지니어링 아키텍처 적합성, 코드 유지보수성, 기술 부채 등은 빠져 있습니다.

Sonar는 자체 평가 프레임워크를 만들어 4,444개 오픈소스 Java 과제에 여러 모델을 적용했습니다. SonarQube Enterprise로 분석하고 결과를 공개했습니다.

[전사 일부 구간은 오디오 품질 저하로 내용 불명확 — 리더보드 데모 전환 구간으로 추정]

예를 들어, 특정 과제 집합에서 Claude Sonnet [4.6]이 생성한 코드 62.7만 라인에서 백만 라인당 300건의 보안 이슈가 발견됐습니다. GPT 5.4·GPT 5.4 Pro High는 같은 4,000개+ Java 과제에 120만 라인을 생성했습니다. 심각한 코드 비대화(bloat)입니다.

왜 이런 일이 생기냐? 세 가지 이유가 있습니다. 첫째, 학습 데이터의 혼합 품질 — 좋은 코드와 나쁜 코드가 섞여 있습니다. 둘째, 내장 보안 결함 — 학습 데이터에 포함된 취약한 코드 예제를 모델이 그대로 학습합니다. 셋째, 학습 데이터의 숨겨진 버그 — 미묘한 로직 오류가 학습 풀에 섞여 들어갑니다. 그리고 LLM 자체의 비결정성 문제도 있습니다. 동일 프롬프트를 같은 모델에 내일 다시 넣으면 다른 코드가 나옵니다. 회사 코드베이스·아키텍처에 대한 컨텍스트도 없고, 설명 가능성도 낮습니다.

이를 위해 sonar.com/leaderboard를 만들었습니다. 53개+ 모델 데이터를 공개했습니다. 현재 1위는 Gemini 2.1 Pro High로, 84.17% pass rate입니다. 이슈 밀도와 복잡도도 나쁘지 않습니다. 80% 이상 모델이 5개 있습니다.

사이클로매틱 복잡도는 if/else/for/while 분기 수를 세는 것입니다. 인지 복잡도는 Sonar 독자 지표로, 인간이 코드를 읽고 이해하기 얼마나 어려운지를 측정합니다. 최신 모델일수록 코드 줄 수가 늘어나고, 복잡도도 높아지는 추세입니다. 총 버그 수는 증가하지만, 모델이 성숙해질수록 기존 버그는 강화학습으로 수정되고 더 미세한 버그가 새로 생겨 인간이 탐지하기 어렵습니다. 취약점 총 건수는 줄지만 유형이 고도화됩니다.

이런 문제를 해결하기 위해 Sonar는 ACDC(Agent-Centric Development Cycle) 프레임워크를 제안합니다. 재미있는 이름이죠. ACDC는 Guide·Verify·Solve 3단계로 구성됩니다.

Guide 단계에는 두 가지 제품이 있습니다. Sonar Context Augmentation은 전체 코드베이스를 LLM에 주입합니다. Sonar Sweep(프라이빗 베타)은 학습·참조 데이터의 보안 결함을 사전에 정화합니다 — 문제 있는 데이터가 들어가면 문제 있는 코드가 나오므로, 데이터 단계에서 처리하는 것입니다.
