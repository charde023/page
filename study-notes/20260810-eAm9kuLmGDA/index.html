에이전트 개발, 하지 말아야 할 것부터 배우세요

원작자 Frank Coyle · UC Berkeley · 업로드 2026-08-10 · 19.6분 · 원본 영상 ↗
한 줄 요약

에이전트 개발은 “무엇을 할지”보다 먼저 무엇을 하지 말아야 하는지, 즉 안티패턴(anti-pattern)을 이해해야 안정적이고 비용 효율적인 시스템을 만들 수 있다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
안티패턴(anti-pattern) 실패하는 설계 방식을 알아야 올바른 설계 방향을 잡을 수 있음 에이전트 개발은 “하지 말아야 할 것”을 피하는 능력이 핵심
에이전틱 루프(agentic loop) 에이전트가 모델 호출, 도구 사용, 결과 확인을 반복하는 기본 구조 루프를 만들 때는 반드시 중단 이유(stop reason)를 기준으로 제어해야 함
중단 이유(stop reason) 모델이 왜 응답을 멈췄는지 알려주는 신호 도구 사용, 토큰 초과, 정상 종료 등을 구분해야 함
Claude.md 계층화 Claude Code가 프로젝트 규칙을 이해하도록 돕는 설정 파일 프로젝트 전체, 폴더, 하위 디렉터리별로 규칙을 나누어 관리
멀티 에이전트 전문화 하나의 에이전트에 모든 도구를 몰아주면 혼란과 성능 저하 발생 에이전트는 한 가지 역할과 제한된 도구를 갖는 것이 좋음
컨텍스트 관리(context management) 컨텍스트는 비용과 정확도에 직접 영향을 줌 모든 내용을 넣지 말고 필요한 정보만 요약해 전달
서브태스크 격리(subtask isolation) 하위 작업 결과가 메인 컨텍스트를 오염시키는 것을 방지 별도 작업 공간에서 처리한 뒤 요약만 본문에 반영
배치 모드(batch mode) CI/CD에서 대화형 모드는 자동화를 방해함 급하지 않은 작업은 배치로 실행해 토큰 비용을 줄일 수 있음

내가 모를 만한 것 / 처음 보는 것

  • Claude Certified Architect Exam — Anthropic 생태계에서 Claude 기반 에이전트 설계 역량을 평가하는 자격시험.
  • 에이전틱 아키텍처(agentic architecture) — LLM이 도구, 루프, 컨텍스트, 제어 흐름을 이용해 목표를 수행하도록 설계하는 구조.
  • 중단 이유(stop reason) — Claude가 응답을 멈춘 이유. 예: 도구 사용 요청, 최대 토큰 도달, 정상 종료.
  • 모델 컨텍스트 프로토콜(Model Context Protocol, MCP) — 외부 도구와 모델을 연결하기 위한 프로토콜 개념.
  • Claude.md — Claude Code에서 프로젝트별 지침, 코딩 규칙, 워크플로를 담는 마크다운 설정 파일.
  • 컨텍스트 포크(context fork) — 메인 대화 흐름과 분리된 별도 작업 맥락에서 하위 작업을 수행하는 방식.
  • 컴팩션(compaction) — 긴 컨텍스트를 압축해 핵심 정보만 남기는 처리.
  • 집단사고(groupthink) — 여러 에이전트가 서로 영향을 받아 독립적 판단을 잃고 비슷한 결론으로 수렴하는 현상.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Claude Certified Architect Exam은 2026년 3월 출시된 신규 시험이라고 설명한다.
  2. 개인 응시자는 99달러를 내고 시험을 볼 수 있으며, 6개월에 한 번 응시 가능하다고 말한다.
  3. 시험은 단순 객관식이 아니라 현실적인 제약과 시나리오 기반 객관식이라고 강조한다.
  4. 시험 도메인 비중: 에이전틱 아키텍처(agentic architecture) 27%, Claude Code 설정과 워크플로 20%.
  5. 시험에는 6개 프로덕션 시나리오가 제공되고, 실제 시험에서는 그중 4개가 무작위 선택된다고 설명한다.
  6. 에이전틱 루프에서 모델은 도구를 직접 실행하지 않는다. 모델은 도구 실행에 필요한 파라미터를 구성하고, 실제 실행은 코드가 한다.
  7. 토큰이 부족해서 멈춘 응답은 부분 출력(partial output)일 수 있으므로 그대로 믿으면 위험하다.
  8. Claude.md는 프로젝트 최상위, 프로젝트 폴더 내부, 하위 디렉터리처럼 계층적으로 둘 수 있다고 설명한다.
  9. 메인 컨텍스트가 150,000토큰 이상 커지면 컴팩션(compaction)을 실행하는 예를 든다.
  10. Anthropic 배치(batch) 기능은 토큰 비용을 50% 절감할 수 있고, 결과는 최대 24시간 내 제공된다고 설명한다.

1. 배경: 에이전트 시대에는 “실험”이 먼저다

Frank Coyle은 30년 이상 컴퓨터 과학을 가르쳤고, 현재 Berkeley에서 학생들을 가르치고 있다고 소개한다. 그가 느끼는 문제는 과거처럼 컴퓨터 과학 전공만으로 안정적인 취업이 보장되지 않는다는 점이다. 이제 학생들은 에이전틱 AI(agentic AI) 시대에 맞는 새로운 역량을 준비해야 한다.

그가 강조하는 태도는 단순하다.

읽기만 하지 말고 직접 만들어야 한다.

그는 “실패는 없다. 오직 만드는 과정만 있다”는 관점을 소개한다. 에디슨의 “작동하지 않는 10,000가지 방법을 찾았을 뿐”이라는 말도 같은 맥락이다. 에이전트 개발에서도 실패 사례를 통해 어떤 설계가 위험한지 알 수 있고, 이것이 안티패턴(anti-pattern) 학습으로 이어진다.

2. Claude Certified Architect Exam이 중요한 이유

화자는 Anthropic의 Claude Certified Architect Exam을 에이전틱 AI 커리어를 준비하는 사람에게 유용한 참고 자료로 본다. 이유는 Anthropic이 실제 사용자들이 Claude를 어떻게 쓰는지, 어떤 문제가 반복되는지 잘 알고 있기 때문이다.

시험은 다음 특징을 가진다.

  • 2026년 3월 출시된 신규 시험
  • 제한 시간 있음
  • 감독 시험(proctored exam)
  • Anthropic 또는 Claude 생태계 기업 대상 제공
  • 개인은 99달러로 응시 가능
  • 6개월에 한 번 응시 가능
  • 현실적인 제약 조건과 시나리오 기반 문제

주요 평가 영역은 에이전틱 아키텍처, Claude Code 설정, 프롬프트 엔지니어링(prompt engineering), JSON 기반 구조화 출력, 도구 설계(tool design), MCP 통합, 컨텍스트 관리, 신뢰성(reliability)이다.

시험을 보지 않더라도 이 영역들은 에이전트 개발자가 반드시 이해해야 할 실무 주제다.

3. 루프는 새롭지 않지만, 에이전트에서 다시 중요해졌다

요즘 에이전트 개발에서 루프(loop)가 핵심 키워드로 떠오르고 있다. 화자는 이것이 완전히 새로운 개념은 아니라고 설명한다.

컴퓨터 과학에서 Böhm과 Jacopini는 1966년에 튜링 완전성(Turing completeness)을 위해 필요한 구조를 설명했다.

  • 순차 실행(sequence)
  • 조건문(if-then)
  • 반복문(loop)

기존 LLM 활용은 주로 프롬프트를 순서대로 실행하거나 조건을 조금 붙이는 수준이었다. 하지만 에이전트는 여기에 루프가 들어가면서 스스로 도구 사용, 결과 확인, 재시도를 반복할 수 있게 된다.

즉, 에이전틱 AI의 힘은 단순히 좋은 프롬프트가 아니라 루프를 어떻게 설계하느냐에서 나온다.

4. 시나리오 1: 고객 지원 에이전트와 stop reason

첫 번째 시나리오는 고객 지원 해결 에이전트다. 여기서 가장 중요한 안티패턴은 다음이다.

에이전트를 그냥 실행시키고 나온 응답을 그대로 사용하는 것.

올바른 방식은 Claude의 중단 이유(stop reason)를 확인하면서 루프를 제어하는 것이다.

예를 들어 모델이 고객 문제를 해결하려고 외부 도구를 사용해야 한다고 판단하면, Claude는 도구를 직접 실행하지 않는다. LLM은 실제로 아무 작업도 실행할 수 없고, 텍스트를 생성할 뿐이다. 다만 도구를 호출하기 위한 파라미터를 구성할 수 있다.

흐름은 다음과 같다.

  1. 코드가 모델을 호출한다.
  2. 모델은 현재 메시지와 컨텍스트를 보고 도구 사용이 필요하다고 판단한다.
  3. 응답의 중단 이유가 도구 사용(tool use)으로 나온다.
  4. 실제 코드는 모델이 만든 파라미터를 받아 도구를 실행한다.
  5. 실행 결과를 다시 모델에 전달한다.
  6. 모델이 최종 답변을 만든다.
  7. 신뢰도가 낮으면 사람에게 에스컬레이션한다.

여기서 stop reason을 확인하지 않으면 위험하다. 예를 들어 모델이 토큰 한도 때문에 멈췄다면 응답은 완전한 답이 아니라 부분 출력일 수 있다. 이런 답을 그대로 고객에게 보내면 문제가 생긴다.

5. 시나리오 2: Claude Code와 Claude.md 계층화

두 번째 시나리오는 Claude Code를 이용한 코드 생성이다. Claude Code에는 Claude.md라는 설정 파일 개념이 있다. 이 파일에는 Claude가 프로젝트에서 따라야 할 규칙, 선호하는 코딩 스타일, 작업 방식 등을 적는다.

Anthropic은 Claude.md를 한 곳에 몰아넣기보다 계층적으로 관리하라고 권장한다.

  • 프로젝트 최상위 Claude.md
  • 프로젝트 폴더 내부 Claude.md
  • 특정 디렉터리별 Claude.md

이렇게 하면 전체 프로젝트 규칙과 특정 폴더의 세부 규칙을 나눌 수 있다. 이커머스나 물류 시스템으로 비유하면, 회사 전체 운영 규칙과 창고별 운영 규칙, 상품군별 예외 규칙을 따로 관리하는 것과 비슷하다.

6. 시나리오 3: 멀티 에이전트는 만능 직원이 아니라 전문가 팀처럼 설계한다

세 번째 시나리오는 멀티 에이전트 리서치 시스템이다. 안티패턴은 하나의 에이전트에 모든 도구를 다 붙이는 것이다.

화자는 이를 집 수리공 비유로 설명한다. 집에 목수를 불렀는데 그 사람이 목공 도구, 배관 도구, 전기 도구를 전부 들고 와서 “저는 뭐든지 할 수 있습니다”라고 말한다면 오히려 불안할 수 있다. 필요한 것은 만능 작업자가 아니라 전문 목수일 수 있다.

에이전트도 마찬가지다.

한 에이전트는 한 가지 역할을 잘하도록 설계하고, 필요한 도구도 하나나 두 개 정도로 제한하는 편이 좋다.

이 원칙은 함수형 프로그래밍(functional programming)의 “함수는 한 가지 일만 해야 한다”는 원칙과도 연결된다.

또 하나의 중요한 점은 각 에이전트의 컨텍스트를 메인 컨텍스트에 그대로 흘려보내지 않는 것이다. 컨텍스트는 곧 토큰이고, 토큰은 비용이다. 또한 컨텍스트가 많아질수록 LLM이 혼란스러워져 답변 정확도가 떨어질 수 있다.

7. 집단사고를 막으려면 에이전트마다 필요한 정보만 줘야 한다

멀티 에이전트 시스템에서는 에이전트들이 서로의 사고 과정을 지나치게 많이 공유하면 집단사고(groupthink)에 빠질 수 있다. 여러 에이전트가 독립적으로 판단하는 것이 아니라 비슷한 결론으로 몰려가는 것이다.

예를 들어 비평가 에이전트(critic agent)를 만든다고 하자. 이 에이전트에게는 전체 사고 과정이나 이전 에이전트들의 모든 대화를 주는 것이 아니라, 다음 정도만 주는 것이 좋다.

  • 주장(claim)
  • 근거(evidence)

즉, 비평에 필요한 정보만 제공해야 한다. 그래야 다른 에이전트의 추론 과정에 휘둘리지 않고 독립적으로 판단할 수 있다.

8. 시나리오 4: 서브태스크 결과를 메인 컨텍스트에 그대로 쌓지 말라

네 번째 시나리오는 개발자 생산성과 코드 작업이다. 여기서 안티패턴은 모든 하위 작업의 전체 결과를 메인 스레드에 그대로 넣는 것이다.

예를 들어 로그 전체를 분석하는 작업이 있다고 하자. 잘못된 방식은 에이전트가 읽은 로그, 중간 추론, 상세 출력, 실패 기록을 전부 메인 컨텍스트에 넣는 것이다. 이렇게 하면 컨텍스트가 빠르게 커지고, 중요한 정보가 묻힌다.

올바른 방식은 다음과 같다.

  1. 로그 분석 작업을 별도 컨텍스트로 분리한다.
  2. 에이전트가 그 안에서 자유롭게 분석하게 한다.
  3. 메인 컨텍스트에는 최종 요약만 가져온다.
  4. 컨텍스트가 너무 커지면 컴팩션(compaction)을 실행한다.

화자는 예시로 토큰 수가 150,000개를 넘으면 압축을 실행하는 방식을 언급한다. Anthropic과 Claude에는 긴 컨텍스트를 압축하는 알고리즘이 있으며, 필요하면 외부 도구나 커스텀 압축 로직을 활용할 수도 있다고 말한다.

9. 시나리오 5: CI/CD에서는 대화형 모드를 피하라

Claude Code를 CI/CD 파이프라인에 넣을 때의 안티패턴은 항상 대화형 모드(interactive mode)를 사용하는 것이다.

대화형 모드는 Claude가 중간에 멈추고 다음과 같이 물어볼 수 있다.

  • 이 작업을 할까요?
  • 이 권한을 허용할까요?
  • 다음 단계로 진행할까요?

자동화 파이프라인에서는 이런 질문이 치명적이다. 사람이 응답하지 않으면 파이프라인이 멈추기 때문이다. 따라서 CI/CD에서는 가능하면 비대화형 실행, 권한 사전 설정, 배치 처리 방식을 써야 한다.

화자는 Anthropic의 배치(batch) 기능도 언급한다. 급하지 않은 작업은 배치로 묶어 실행하면 토큰 비용을 50% 줄일 수 있고, 결과는 24시간 내 제공된다고 한다.

10. 결론: 시험보다 중요한 것은 직접 만들어보는 것

화자의 마지막 메시지는 처음과 같다.

실패를 두려워하지 말고 만들어야 한다.

Claude 자격시험은 에이전트 개발의 중요한 실무 주제를 잘 압축해 보여준다. 하지만 시험 자체보다 중요한 것은 직접 실험하면서 안티패턴을 경험하고, 올바른 패턴으로 고쳐보는 과정이다.

에이전트 개발에서 특히 기억할 점은 다음이다.

  • 루프는 stop reason으로 제어한다.
  • LLM은 도구를 직접 실행하지 않는다.
  • 하나의 에이전트에 모든 도구를 몰아주지 않는다.
  • 컨텍스트를 무한정 키우지 않는다.
  • 서브태스크는 격리하고 요약만 가져온다.
  • CI/CD에서는 대화형 모드를 피한다.
  • 비용과 정확도를 위해 토큰을 관리한다.

작은 기술 문제가 있었지만 해결했습니다.

제 이름은 Frank Coyle입니다. 저는 컴퓨터 과학을 전공했고, 30년 넘게 컴퓨터 과학을 가르쳐 왔으며 지금은 Berkeley에서 가르치고 있습니다. 과거와 현재의 제 학생들이 겪는 큰 문제 중 하나는 AI입니다. 이제 컴퓨터 과학은 더 이상 취업으로 가는 마법 같은 길이 아니기 때문입니다. 그래서 저는 학생들이 에이전틱 AI(agentic AI) 세계에 대비할 수 있도록 돕는 방법을 고민해 왔습니다.

그러던 중 Claude Certified Architect Exam이라는 것이 제 앞에 나타났습니다. 오늘은 이 시험에 대해 이야기하려고 합니다. 여러 측면이 있는데, 에이전틱 AI 분야에서 커리어를 생각한다면 이 시험이 무엇을 다루는지 꼭 살펴보길 권합니다. Anthropic은 사람들이 자기 시스템을 어떻게 사용하는지, 앞으로 어떤 문제가 생길지 잘 알고 있다고 느끼기 때문입니다.

본론에 들어가기 전에 제 철학을 조금 말씀드리겠습니다. Sister Corita Kent라는 분의 말입니다. “실수란 없다. 이김도 실패도 없다. 오직 만드는 것만 있다.” 핵심은 실험하고, 실험하고, 또 실험하라는 것입니다. 읽기만 해서는 안 됩니다. 직접 해야 합니다. 무언가를 만들어야 합니다.

그런데 무언가를 만들면 어떤 일이 생길까요? 많은 경우 잘 작동하지 않습니다. Thomas Edison은 “나는 실패한 것이 아니다. 작동하지 않는 10,000가지 방법을 찾았을 뿐이다”라고 말했습니다. 제가 강조하고 싶은 것은 이것이 디자인 패턴(design pattern) 운동과도 연결된다는 점입니다. 1990년대 초 객체지향 프로그래밍(object-oriented programming)에서 객체를 위한 패턴이 있었습니다. 이제는 에이전트를 위한 패턴이 있습니다. 하지만 안티패턴(anti-pattern)도 있습니다. 저는 안티패턴이 무엇을 하지 말아야 하는지 이해하는 핵심이라고 생각합니다. 무엇을 하지 말아야 하는지 이해하는 것이 결국 무엇을 해야 하는지로 이끌어 주기 때문입니다.

Claude Certified Exam에 대해 조금 설명하겠습니다. 이 시험은 3월에 출시되어 아주 새로운 시험입니다. 시나리오 기반이고, 시간 제한이 있으며, 감독 시험입니다. Claude 생태계, Anthropic 생태계에 있는 회사들이 이용할 수 있지만, 개인도 99달러를 내고 6개월에 한 번 시험을 볼 수 있습니다. 단순한 객관식 문제만 있는 것은 아닙니다. 객관식이긴 하지만 현실적인 제약과 현실적인 시나리오를 바탕으로 합니다.

다섯 개 영역이 있고 각 비중도 공개되어 있습니다. 에이전틱 아키텍처(agentic architecture)는 27%입니다. Claude Code, 즉 Claude Code 시스템과 워크플로를 설정하는 방법은 20%입니다. 프롬프트 엔지니어링(prompt engineering), JSON을 많이 사용해 출력을 구조화하는 방법, 도구 설계(tool design), 모델 컨텍스트 프로토콜(Model Context Protocol, MCP) 통합도 포함됩니다. 시험을 볼지 여부와 상관없이 이 주제들은 이해해야 합니다. 앞으로 에이전틱 세계가 던질 문제에 대비하는 데 도움이 됩니다. 그리고 컨텍스트 관리(context management)와 신뢰성(reliability)도 있습니다. 이런 영역에서 문제가 나옵니다.

시험은 여섯 개의 프로덕션 시나리오를 제공하고, 실제 시험에서는 그중 네 개를 무작위로 선택합니다. 모든 문제는 선택된 네 개 시나리오를 중심으로 나옵니다. 저는 이 프로덕션 시나리오들을 훑어보면서 주의해야 할 안티패턴을 설명하려고 합니다. 문제를 푸는 방법은 여러 가지가 있지만, 중요한 것은 무엇을 하지 말아야 하는지입니다. 이것이 종종 문제를 맞히는 핵심이 됩니다.

첫 번째 시나리오는 고객 지원 해결 에이전트(customer support resolution agent)입니다. 여기에는 에이전틱 루프(agentic loop), 제어(control), 그리고 Claude Code에 있는 중단 이유(stop reason)라는 것이 있습니다. 어떤 일이 발생할 때마다 중단 이유가 생깁니다. 반드시 이것을 확인해야 합니다. 현재 무슨 일이 일어나고 있는지 많은 정보를 주기 때문입니다.

두 번째 시나리오는 코드 생성(code generation)입니다.

세 번째 시나리오는 멀티 에이전트 리서치 시스템(multi-agent research system)입니다. 에이전트를 어떻게 분산할 것인가, 허브 앤 스포크(hub and spoke) 구조를 쓸 것인가, 누가 오케스트레이터(orchestrator)가 될 것인가, 각 에이전트가 얼마나 많은 정보를 알아야 하는가 같은 요소가 중요합니다.

네 번째 시나리오는 코드를 이용한 개발자 생산성(developer productivity)입니다. 하위 작업을 어떻게 격리할 것인가, 각 작업을 작은 우주 안에 유지할 것인가에 대한 내용입니다. 이것은 컴퓨터 과학에서 멀티스레드 프로그래밍(multi-threaded programming)을 하며 배운 것과 연결됩니다. 여러 스레드가 동작하면서 메모리를 공유하면 동기화 문제가 생기고, 락(lock)을 넣어야 합니다. 작은 스레드를 독립적으로 유지하듯, 에이전트도 독립적으로 유지해야 합니다.

그다음은 지속적 통합(continuous integration)을 위한 Claude Code이고, 마지막으로 구조화된 데이터 추출(structured data extraction) 패턴을 살펴봅니다.

모두가 루프(loop)에 대해 이야기합니다. 루프가 새로운 핵심이라는 식입니다. Boris Churny는 자신은 코드를 쓰지 않고, 자기 일은 루프를 작성하는 것이라고 말합니다. OpenAI의 Peter Steinberger는 “나는 더 이상 코딩하지 않는다. 에이전트를 프롬프트하는 루프를 설계할 뿐이다”라고 말합니다. 그래서 루프가 새로운 대세처럼 보입니다.

하지만 사실 새롭지는 않습니다. 초기 컴퓨팅 시절에는 프로그래밍 언어가 폭발적으로 생겨났습니다. Fortran, COBOL이 있었고, 내 언어가 더 낫다, 더 많은 일을 할 수 있다는 논쟁이 많았습니다. Böhm과 Jacopini는 1966년에 어떤 언어가 튜링 완전(Turing complete)하려면, 즉 컴퓨터가 계산할 수 있는 모든 것을 계산할 수 있으려면 세 가지만 필요하다고 증명했습니다. 순차적으로 문장을 실행하는 능력, if-then 조건문, 그리고 세 번째가 루프입니다. 루프를 추가하면 튜링 계산 가능성(Turing computability)을 갖습니다. 지금 에이전틱 세계에서 루프에 초점이 맞춰지며 이것이 다시 등장하고 있습니다. 지금까지는 주로 순서가 있었습니다. 프롬프트가 있고, 어쩌면 if-then이 있었습니다. 이제 루프가 들어왔고, 이것이 힘을 줍니다. 에이전틱한 것이 매우 흥미로워지는 지점입니다.

첫 번째 시나리오인 고객 지원 해결부터 시작하겠습니다. 여기서는 루프가 작동합니다. 바로 안티패턴으로 넘어가겠습니다. 원하지 않는 것은 에이전트를 그냥 실행시키고, 응답을 받아 그대로 사용하는 것입니다. 해야 할 일은 중단 이유(stop reason)를 이용해 루프를 도는 것입니다.

간단한 코드를 보겠습니다. while 루프가 있습니다. while true입니다. 바로 여기서 루프를 돕니다. 첫 번째 작은 블록은 모델을 호출하는 곳이고, 메시지(messages)를 전달합니다. 메시지는 기본적으로 컨텍스트 창(context window)에 존재하는 프롬프트들의 순서입니다. 모델에게 요청합니다. 프롬프트가 있고, 컨텍스트가 있고, 도구(tool)가 있습니다. LLM에게 이 도구를 사용해 무언가를 하도록 요청합니다.

문제는 LLM은 아무것도 할 수 없다는 것입니다. LLM은 확률적인 다음 단어 예측기(probabilistic next-word predictor)일 뿐입니다. 도구를 실행할 수 없습니다. 다만 도구를 가리키면, 여러분이나 여러분의 코드가 그것을 실행할 수 있도록 설정하는 방법을 알아낼 수 있습니다. 따라서 LLM이 도구를 실행하는 것이 아니라는 점을 이해하는 것이 중요합니다. LLM은 아무것도 할 수 없습니다. 때로 매우 지적으로 대답할 수 있지만, 결국 할 수 있는 것은 말로 답하는 것뿐입니다.

모델이 작업을 마치고 결과를 냅니다. 기본적으로 “당신이 원하는 것을 알겠고, 도구가 무엇을 할 수 있는지도 알겠으며, 실제 도구 실행에 사용할 파라미터는 이렇게 설정하면 된다”는 결과입니다. 두 번째 블록에서 LLM이 왜 우리에게 돌아왔는지 봅니다. 그것이 중단 이유입니다. 여기서는 도구 사용(tool use)입니다. LLM이 도구를 사용하고 싶어서 멈춘 것입니다. 그러면 도구를 실행하면 됩니다. 이것이 두 번째 블록입니다.

도구를 실행합니다. 응답은 LLM이 말한 내용이며, 여러분이 제공한 데이터에서 추출한 파라미터입니다. 그것을 실행합니다. 그런 다음 다시 돌아갑니다. 계속한다는 것은 LLM이 결과를 보고 “성공적으로 실행되었군요”라고 판단한다는 뜻입니다. 이제 다시 아래로 내려옵니다. 더 이상 도구를 실행하지 않습니다. 루프가 끝났습니다.

그다음 답변을 가져옵니다. 이 지점에서 사람을 루프에 넣는(human in the loop) 것도 가능합니다. 신뢰도를 확인합니다. 좋아 보이면 유지하고, 그렇지 않으면 사람에게 에스컬레이션합니다. 그래서 중단 이유를 반드시 확인해야 하는 또 다른 이유가 있습니다. 중단 이유 중 하나는 토큰이 부족해졌다는 것일 수 있습니다. 이 응답은 LLM이 멈출 수밖에 없었을 때의 부분 출력(partial output)에 기반합니다. 응답은 나오지만, 토큰이 부족했다면 조치를 취해야 합니다.

다음 시나리오는 Claude를 이용한 코드 생성입니다. Claude Code에는 Claude.md 파일이라는 개념이 있습니다. 원하는 내용을 모두 넣는 마크다운 파일입니다. Anthropic은 Claude.md를 세 단계로 두라고 권장합니다. 프로젝트 최상위에 하나, 프로젝트 폴더 안에 하나, 그리고 디렉터리 내부에도 지정할 수 있습니다. 아이디어는 시스템이 어떻게 응답할지를 제어하는 규칙을 계층적으로 두는 것입니다.

계속해서 멀티 에이전트 리서치 시스템으로 넘어가겠습니다. 문제는 에이전트들이 나가서 무언가를 하고, 답을 합리적인 방식으로 가져오게 만드는 방법입니다. 안티패턴은 하나의 에이전트에 도구를 잔뜩 넣는 것입니다. 저는 이렇게 생각합니다. 집에 목수를 불렀는데, 그 사람이 배관 도구, 목공 도구, 전기 도구를 모두 들고 와서 “저는 뭐든지 할 수 있습니다”라고 말합니다. 아마 이 사람을 원하지 않을 수도 있습니다. 전문 목수를 원할 수도 있습니다. 그런 생각입니다.

이것은 함수형 프로그래밍(functional programming)의 아이디어와도 연결됩니다. 함수는 한 가지 일을 해야 합니다. 에이전트도 한 가지 일을 하게 만들고, 사용할 수 있는 도구를 하나나 두 개 정도로 제한할 수 있다면 좋은 결과가 나올 것입니다. 시험에서도 도움이 됩니다. 그러니 전문화하십시오. 과부하시키지 마십시오.

또 다른 부분은 에이전트의 컨텍스트가 메인 컨텍스트로 흘러넘치게 하지 말라는 것입니다. 컨텍스트는 토큰이고, 토큰은 돈입니다. 컨텍스트가 많을수록 LLM은 답을 내는 데 더 혼란스러워질 수 있습니다. “백만 토큰 컨텍스트 창이 있으니 모든 것을 넣을 수 있다”고 생각할 수 있지만, 아닙니다. 모든 것을 넣지 마십시오. 들어가는 것을 제한해야 훨씬 더 정확한 시스템을 얻을 수 있습니다.

전문화된 하위 에이전트(specialized sub-agent)의 예를 보겠습니다. 이것은 비평가(critic)입니다. 어떤 작업을 실행한 뒤, 이제 에이전트에게 무슨 일이 있었는지 보게 하고 싶다고 합시다. 이때는 비평 문제를 해결하는 데 필요한 것만 줘야 합니다. 여기서는 주장(claim)과 근거(evidence)만 줍니다. 주장은 문제를 해결하는 방식이고, 근거는 그에 대한 증거입니다. 하지만 이 주장을 만들어낸 사고 과정은 주지 않습니다. 왜일까요? 여러 에이전트가 함께 협력하고 대화하면 집단사고(groupthink) 경향이 생깁니다. 모든 에이전트가 하나의 아이디어로 퇴화하는 것처럼 보입니다.

마치 파티에서 모두가 피자를 원하고 나만 원하지 않는 상황과 비슷합니다. 사람들이 설득하고, 파티를 망치고 싶지 않아서 결국 따라가게 됩니다. 에이전트들도 비슷하게 작동하는 것 같습니다. 그래서 각 에이전트에게는 자기 몫의 조각만 줘야 합니다. 모든 에이전트는 자기 조각만 받습니다.

네 번째 시나리오는 개발자 생산성입니다. 안티패턴은 모든 하위 작업이 전체 출력을 기본 스레드(primary thread)에 쏟아붓게 해서 컨텍스트를 밀어내는 것입니다. 방금 이야기한 것과 같습니다. 이것은 나쁩니다. 컨텍스트가 무한정 커지게 두는 것도 나쁩니다. 이유는 이미 말했습니다. 하위 작업 출력을 격리하고, 긴 세션은 압축해야 합니다.

에이전트가 로그를 보고 로그에서 문제가 있는 위치를 요약하게 해야 합니다.

예를 들어 작업은 “모든 로그에서 오류를 스캔하라”입니다.

컨텍스트 포크(context fork)를 합니다. 에이전트를 별도 스레드로 분기시키는 것입니다. 그 안에서 에이전트가 무엇을 하고 생각하고 토큰을 추가하든, 메인 컨텍스트로 돌아와 오염시키지 않습니다.

여기서 어떤 일이 일어나는지 보십시오. 그런 다음 요약을 가져오고, 다른 모든 내용 없이 그 요약만 상위 컨텍스트에 추가합니다.

마지막 작은 블록은 흥미롭다고 생각합니다. 토큰 수를 확인할 수 있고, 토큰 수가 얼마나 큰지 판단할 수 있습니다. 어떤 한도를 설정할 수 있습니다. 예를 들어 150,000토큰보다 많다면 컴팩트(compact)를 실행할 수 있습니다.

Anthropic과 Claude에는 이런 거대한 컨텍스트를 어떤 형태로든 압축하는 컴팩션 알고리즘(compaction algorithm)이 있습니다. 구현이 정확히 어떤지는 모르지만, 컴팩션이 존재합니다.

잠깐 부가적인 이야기를 하겠습니다. 밖을 걸어 다니다 보면 책을 나눠주는 사람들이 보입니다. 혹시 보셨습니까? 그 책을 받으십시오. 꽤 괜찮은 작은 책입니다.

사실 어젯밤에 그 책을 봤는데, Sam Bagua라는 사람이 쓴 내용이 있었습니다. 저는 아무 관련도 없고 Sam을 알지도 못합니다. 온라인 페이지 32에 그의 회사가 컨텍스트 압축을 위한 커스텀 로직을 제공한다고 되어 있었습니다. 앱이 있고, 여러분이 직접 작성할 수 있습니다. 그의 기본 클래스를 확장해서 자신의 데이터에 맞는 압축 로직을 만들 수 있습니다. 무엇이 중요하다고 생각하든 그 기준으로 압축할 수 있습니다. 이 전체 주제에 대한 흥미로운 변형이라고 생각합니다.

이제 지속적 통합을 위한 Claude Code입니다.

안티패턴은 파이프라인에서 항상 대화형 모드(interactive mode)를 쓰는 것입니다. 안 됩니다. 대화형 모드는 Claude가 멈춰서 “이것을 할까요?”, “저것을 할까요?”, “이 권한을 허용해도 될까요?”라고 묻는다는 뜻입니다. 따라서 끝까지 곧장 실행되도록 설정하는 방법이 있습니다.

여기서 또 하나의 팁은 배치(batch)라는 것이 있다는 점입니다. 프롬프트와 작업 위치를 배치에 넣을 수 있고, 토큰 비용을 50% 줄여 결과를 받을 수 있습니다. 결과는 적어도 24시간 이내에 제공된다고 약속합니다.

낮잠을 자러 가거나, 휴가를 가거나, 밖에 나가거나, 하루 쉬려 한다면 배치 모드로 작업을 실행하십시오. 비용을 덜 내게 됩니다.
