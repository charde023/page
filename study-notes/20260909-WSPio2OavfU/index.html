처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

사내 AI가 모든 문서와 도구에 한꺼번에 접근하면, 권한이 낮은 직원도 AI를 거쳐 급여나 고객 정보에 닿을 수 있다. 화자는 이를 막으면서 지식을 공유하는 방법으로 하나의 연결된 위키를 제안한다. 문서마다 읽기·쓰기 가능자를 정하고, AI는 새 지식을 몰래 저장하지 않고 변경안만 제시한다. 사람이 내용과 공개 범위를 확인해 승인하며, 모든 변경에는 책임자의 이름을 남긴다.

AI가 실제 문서나 도구를 사용할 때도 AI 자체의 공용 권한을 쓰면 안 된다. 요청한 사용자의 권한을 매번 적용하고, 자격 증명은 AI가 코드를 실행하는 격리 공간에 저장하지 않는다. 대신 외부의 HTTP·SQL 연결 계층에서 해당 사용자의 자격 증명을 넣는다. 핵심은 지식을 한곳에 모으되, 읽기·쓰기·실행 권한은 사람마다 계속 분리하는 것이다.

여기까지만 이해하면 충분

  • 공유 지식이 많아질수록 문서별 접근 권한과 책임 기록이 필요하다.
  • AI는 지식을 자동 저장하지 않고 변경을 제안하며, 사람이 승인해야 한다.
  • 공유 AI도 요청한 사용자의 권한 안에서만 문서와 도구를 사용해야 한다.
  • 자격 증명은 AI 실행 공간 밖에서 주입해야 권한 상승 위험을 줄일 수 있다.

비유와 깨지는 지점

하나의 건물과 방별 출입증

회사 위키는 하나의 건물이고, 각 문서는 잠긴 방이다. AI는 모든 방을 여는 관리자가 아니라 사용자의 출입증을 대신 들고 움직이는 안내원이다. 새 기록을 붙일 때도 담당자의 확인과 이름이 필요하다.

비유가 깨지는 지점: 실제 AI는 방에 들어가는 것뿐 아니라 검색, 이메일 발송, SQL 실행, 배포처럼 서로 다른 도구를 연속으로 호출한다. 따라서 문서 출입 통제만으로는 부족하고 각 실행에도 별도의 사용자 권한이 적용돼야 한다.

먼저 서로 다른 권한을 가진 가상 사용자가 허용된 문서만 읽는지 확인한다. 다음으로 AI의 변경 제안이 사람의 승인과 이름 없이 저장되지 않는지 본다. 마지막으로 도구 실행이 공용 자격 증명이 아니라 요청자별 권한으로 제한되는지 시험한다. 어느 단계든 권한 밖 접근이 성공하면 다음 단계로 확대하지 않는다.

이번 글의 통찰

1. 유용해진 지식 시스템은 더 많이 가르치게 만든다

  • [원문] 화자는 자체 시스템의 약 5,000개 연결 페이지와 최근 두 달의 기록에서 일일 업데이트 수가 완만하게 증가했다고 말했다. 사람들은 데이터 조회를 가르친 뒤 해석, 행동, A/B 테스트까지 더 가르치기 시작했다고 설명했다.
  • [해석] 지식량 자체보다 사람들이 실제 작업 중 계속 수정하고 확장하는지가 살아 있는 지식 시스템의 신호가 될 수 있다.
  • [경계] 화자도 이 관찰이 초기 단계이며 나중에는 증가세가 평평해질 수 있다고 말했다. 증가 폭이나 원자료는 제시되지 않았으므로 보편적인 건강 지표로 검증된 것은 아니다.

2. 자동 저장과 수동 문서 작성 사이에 승인 가능한 제안이 있다

  • [원문] 화자는 직원이 GitHub에 남을 위한 공유 스킬을 직접 작성하기는 어렵고, AI의 자동 기억은 통제하기 어렵다고 주장했다. 대안으로 AI가 내용과 파일별 범위를 제안하고 사람이 승인하며 이름을 남기는 방식을 제시했다.
  • [해석] 지식 축적을 지속시키려면 작성 부담은 AI가 줄이되, 정확성·공개 범위·책임은 사람이 맡아야 한다.
  • [경계] 단일 위키와 사람 승인은 화자의 설계 제안이다. 이 방식이 모든 조직에서 정보 유출을 막았다는 비교 수치나 사고 감소 결과는 제시되지 않았다.

3. 지식 권한과 실행 권한을 함께 통제해야 한다

  • [원문] 화자는 사용자 권한으로 문서를 읽고, 자격 증명을 샌드박스에 저장하지 않으며, 외부 HTTP·SQL 계층에서 요청자의 자격 증명을 주입하라고 제안했다.
  • [해석] AI가 무엇을 아는지만 제한해서는 부족하다. 이메일 발송, SQL 실행, 배포 같은 행동도 매 요청자의 실제 권한에 묶여야 한다.
  • [경계] 제목의 “결국 유출합니다”는 원문의 “유출할 가능성이 높다”보다 단정적이다. 제목은 “대형 은행에서 막아냈다”고 표현하지만, 전사는 포춘 100 은행 같은 곳에 회사 두뇌의 초기 부분을 배포했다고만 주장하며 특정 은행, 실제 사고 방지 결과, 검증 수치를 밝히지 않는다. META는 15~20개 기업과 5,000페이지 운영을 함께 “증명” 근거처럼 적지만, 전사에서는 15~20개 기업과의 협력과 자사 약 5,000페이지 사용을 구분하며 결과도 초기라고 말한다. 또한 화자는 마지막에 “네 가지 원칙”이라고 했지만 그 자리에서 바로 열거한 항목은 자격 증명 외부 보관, 상호작용 프록시·가상화, 사용자 접근 통제의 세 가지다. 앞부분 원칙을 포함한 것인지 명확하지 않다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: AI가 만든 지식을 그대로 저장하지 않고 사람이 검토하게 하는 구조는 학습자의 설명을 확인하는 과정과 닮았다.
  • 통찰: 정답을 자동 기록하는 것보다 학습자가 제안된 설명의 정확성과 적용 범위를 직접 승인하게 해야 이해 여부가 드러난다.
  • 질문/행동: 학습자가 AI 답변을 고치고, 왜 고쳤는지 자기 이름으로 설명하게 하면 무엇이 달라지는가?

사업가 · 구조적 비유

  • 관련성: 공유 지식은 반복 업무 시간을 줄일 수 있지만, 잘못된 공개 범위는 기밀·신뢰·운영 위험을 만든다.
  • 통찰: APOM에 적용 가능성을 검토한다면 모든 자료를 한꺼번에 연결하기보다 가상 문서로 승인 비용과 권한 오류부터 시험해야 한다.
  • 질문/행동: 공유로 절약되는 시간보다 접근 범위 검토와 사고 대응 비용이 커지는 지점은 어디인가?

마케터 · 구조적 비유

  • 관련성: 강연은 보안 질의서 초안이라는 구체적 장면으로 효용을 보여주지만, 제목은 실제 발화보다 강한 확정 표현을 쓴다.
  • 통찰: 상세페이지에서도 “유출을 막는다”는 약속과 파일별 권한, 승인 기록, 차단 테스트 같은 증거를 구분해야 한다.
  • 질문/행동: 결과를 단정하지 않고도 어떤 승인 화면과 권한 차단 기록을 보여주면 주장의 신뢰가 높아지는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 사용자별 권한, 샌드박스, HTTP·SQL 프록시, 도구 실행은 에이전트 아키텍처의 직접적인 검증 대상이다.
  • 통찰: 정상 답변 품질보다 권한이 다른 사용자에게서 읽기·쓰기·실행 결과가 달라지는지를 먼저 측정해야 한다.
  • 질문/행동: 동일한 요청을 서로 다른 가상 사용자로 실행했을 때 권한 밖 문서와 도구가 모두 차단되는가?

5 공유 AI 보안 샌드박스 밖에서 사용자별 자격 증명을 주입해 도구 실행 권한을 제한한다.

1. 배경과 초기 관찰

화자는 자신을 PromptQL의 CEO이자 공동 창업자 Tanmay라고 소개하고, 마지막에는 Tanmay Gopal이라는 이름을 밝혔다. 팀이 Hasura GraphQL 엔진 제작진 출신이며 데이터 접근과 보안을 다뤄 왔다고 설명했다. Apple, Meta, J.P. Morgan 같은 이름을 언급했지만, 문맥상 이는 Hasura 계열 기술의 배포 범위를 가리키는 것으로 읽히며 PromptQL 회사 두뇌의 개별 고객 목록인지 명확하지 않다.

지난 1년 동안 약 15~20개 기업과 협력했으며 고객을 AI 네이티브 기업, 기술 선도 기업, 포춘 100 은행의 세 유형으로 나눴다. 포춘 100 은행 같은 곳에도 회사 두뇌의 “초기 부분”을 배포했다고 주장했으나 구체적인 기관명과 성과는 공개하지 않았다.

자체 회사 두뇌는 약 5,000개의 연결된 페이지로 구성됐다고 말했다. 최근 두 달의 기록에서는 일일 업데이트 수가 완만하게 증가했지만, 화자도 초기 관찰이며 나중에 평평해질 수 있다고 인정했다.

2. 회사 두뇌의 두 가지 사용 방식

첫 번째는 개인이 회사 지식을 찾아 자기 업무를 처리하는 방식이다. 사례로 고객이 보낸 보안 질의서에 대해 AI가 회사 지식을 조회해 답변 초안을 만들고 이메일을 발송하는 장면을 들었다.

두 번째는 여러 사람이 같은 AI와 대화하며 사고 조사, 로그 조회, 코드 확인, PR 작성, 스테이징·프로덕션 배포, 알림 설정 등을 이어 가는 협업 방식이다. 여러 사람의 토론에서 기존 기술 결정의 오류와 새 해결책이 드러날 때 높은 품질의 지식이 생긴다고 주장했다.

화자는 회사 두뇌를 “코딩 에이전트에 제공하는 Markdown 기반 공유 맥락과 데이터·도구 접근 규칙”으로 정의했다. 범용 LLM 안에 모든 지식을 넣는 거대한 지식 그래프와는 구분했다.

3. 구축보다 성장

화자는 오래된 조직의 모든 지식을 장기 프로젝트로 한 번에 구축하는 접근은 현실적이지 않다고 주장했다. 대신 각 구성원이 실제 업무를 하면서 자기 부분을 추가하도록 회사 두뇌를 “구축”하기보다 “성장”시켜야 한다고 말했다.

GitHub 공유 스킬 방식은 직원이 힘든 업무를 마친 뒤 미래의 다른 사람을 위해 별도 문서를 작성해야 하므로 지속되기 어렵다고 봤다. 팀별 자동 기억은 편하지만 채널이나 팀 안에 갇힌 새로운 사일로가 될 수 있다고 지적했다.

4. 하나의 위키와 사람의 승인

대안은 연결된 Markdown 파일로 구성된 하나의 전사 위키다. 다만 모든 사람이 모든 내용을 보는 구조가 아니라, 파일마다 읽기·쓰기 범위를 둔다.

AI는 새 기억을 자동 저장하지 않고 추가할 사실과 적용할 범위를 제안한다. 사용자는 사실이 맞는지 확인하고 “위키에 추가”하는 식으로 승인한다. 모든 변경에는 AI 이름이 아니라 승인한 사람의 이름이 남아야 한다는 것이 화자의 원칙이다.

이 방식은 사용자가 문서를 직접 쓰고 PR을 검토하는 절차보다 가볍고, AI가 보이지 않게 기억을 저장하는 방식보다 통제 가능하다는 주장이다. 실제 운영 비용이나 오류 감소 수치는 제시되지 않았다.

5. 멀티플레이어 환경의 권한 상승

공유 AI에서는 대화 참여자마다 권한이 다를 수 있다. 한 엔지니어가 PR을 만들 수 있다고 해서 같은 대화의 다른 참여자도 그 AI를 통해 프로덕션 배포를 할 수 있어서는 안 된다.

화자는 문서를 읽을 때마다 요청자의 권한 정보를 사용하고, 도구를 실행할 때도 같은 원칙을 적용하라고 제안했다. 자격 증명은 Claude 샌드박스에 저장하지 않고 HTTP 또는 SQL 계층에서 요청자별로 주입한다. 실제 데이터와의 상호작용은 프록시하거나 가상화하고, 도구를 추가한 사용자가 접근 가능자를 통제하게 한다.

6. 수치·명칭·시행 상태의 경계

  • 영상 길이 1,556초와 META의 25.9분은 서로 일치한다.
  • 약 15~20개 기업과 약 5,000페이지는 서로 다른 범위를 가리킨다. 전자는 협력 기업 수이고 후자는 화자 조직의 위키 규모다.
  • 전사의 고객 유형은 세 가지이며 실제로 세 유형이 열거된다. 회사 두뇌의 사용 방식도 두 가지가 열거된다.
  • 앞부분의 지식 관리 원칙 두 가지와 마지막의 실행 보안 원칙 두 가지는 서로 다른 묶음이다.
  • 마지막에는 “네 가지 원칙”이라고 했지만 그 직후 명시적으로 구분되는 항목은 세 가지여서 정확한 네 항목을 확정하기 어렵다.
  • 원제는 유출과 방지를 확정적으로 표현하지만, 화자는 “유출할 가능성이 높다”고 말하고 제안 아키텍처를 설명한다. 특정 대형 은행에서 실제 유출을 막았다는 검증 결과는 전사에 없다.
  • Claude Cowork의 출시가 “며칠 전”이었다는 말은 강연 시점이 명시되지 않아 업로드 날짜만으로 확인할 수 없다.
  • META의 provenance는 원본 영상 링크를 확인하지 못했고 화자 이름과 SNS를 기준으로 출처를 추정했다고 적는다. Tanmay Gopal과 PromptQL 소속은 전사의 자기소개로 확인되지만 원본 게시물의 제작 주체와 링크는 확인되지 않았다.

알겠습니다. 모두 보이시나요? 안녕하세요, 여러분. 와주셔서 감사합니다.

오늘은 회사의 두뇌(company brain)를 구축하면 회사 기밀이 유출될 가능성이 높다는 이야기를 하려고 합니다. 사실 회사의 두뇌를 구축할 때 우리가 가장 크게 우려하는 부분이기도 하죠. 인턴이 회사에 들어오자마자 보상 정보와 모든 사람의 개인정보에 접근할 수 있게 되는 상황을 생각해 보세요. 이런 일은 막아야 합니다.

이 문제는 우리가 OpenClaw와 Hermes를 회사 전반에 배포하지 못하게 막아 온 가장 큰 요인이었던 것 같습니다. 며칠 전 출시된 Claude Cowork가 가졌던 큰 기회도 바로 이 점과 관련이 있습니다. 회사의 두뇌가 되려고 했던 거죠. 그런데 모두가 “글쎄, 이게 회사의 두뇌가 될 것 같지는 않은데?”라고 말했습니다.

그래서 무엇이 이 일을 어렵게 만드는지 이야기해 보겠습니다. 그전에 회사의 두뇌라는 개념을 조금 이해하고 분석해 보죠.

저는 PromptQL의 CEO이자 공동 창업자인 Tanmay입니다. 나중에 PromptQL도 살펴보실 수 있습니다. 저희 팀은 GraphQL 분야에서 매우 인기 있는 오픈소스 프로젝트인 Hasura GraphQL 엔진을 만든 사람들로 구성되어 있습니다. 저희는 데이터 접근 문제를 많이 해결해 왔습니다.

저희 기술은 Apple, Meta, J.P. Morgan 등 다양한 곳에 배포되어 있습니다. 덕분에 데이터와 데이터 보안에 대해 애증에 가까운 관계를 깊이 경험할 수 있었습니다. 지난 1년 동안 저희가 무엇을 만들었고 무엇을 배웠는지 보여 드리겠습니다. 여러분도 이를 가져가서 직접 적용하고 시험해 보실 수 있을 겁니다. 물론 강연이 끝나면 서로 경험을 나누고, 여러분에게 무엇이 효과가 있을지 혹은 없을지 함께 살펴보겠습니다.

지난 1년 동안 저희는 규모가 어느 정도 급격히 커진 소수의 회사들, 지금까지 약 15~20개 회사와 협력해 왔습니다. 이제 막 다른 사람들에게도 공개하기 시작하는 단계입니다.

그 과정에서 서로 매우 다른 요구 사항을 가진 세 가지 유형의 고객을 살펴봤습니다. 우선, 효과만 있다면 무엇이든 해볼 의향이 있는 AI 네이티브 회사들이 있습니다. 그리고 최첨단 기술을 선호하는 Instacart 같은 기술 선도 기업들이 있습니다. 이들은 빠르게 움직이고 문제가 생기는 것도 감수하지만, 기술이 정말, 정말 뛰어나야 합니다.

그다음에는 보안 수준이 미친 듯이 높은 포춘 100대 은행들이 있습니다. 제 은행이기도 하니, 그렇게 보안이 철저해서 정말 다행입니다. 제 돈이 있는 곳에서 분위기만으로 코딩된(vibe-coded) AI 에이전트가 실행되는 건 절대 원하지 않거든요.

그래서 이들에게는 보안 규칙이 아주 많습니다. 정말 감사합니다. 하지만 저희는 이런 곳에도 회사의 두뇌의 시작점, 또는 전두엽에 해당하는 부분을 배포하고 있습니다. 따라서 그 과정에서 얻은 교훈을 이야기할 수 있습니다.

저희가 회사를 운영하며 구축한 회사의 두뇌는 약 5,000페이지입니다. 저희는 이를 위키로 모델링합니다. 여러분은 원하는 방식으로 모델링하면 됩니다. GitHub의 Markdown 파일 모음으로 모델링할 수도 있습니다. 기억하시죠, GraphRAG? 지식 그래프로 모델링할 수도 있습니다. 원하는 것을 원하는 곳에 배치하면 됩니다. 저희의 경우에는 서로 연결된 약 5,000개의 페이지로 구성되어 있습니다.

여러분께 질문이 있습니다. 회사의 두뇌가 제대로 작동하고 완전히 구축되어 있다고 가정해 보죠. 그러면 이 회사의 두뇌에는 매일 일정한 수의 업데이트가 발생할 겁니다. 회사의 모든 사람, 즉 재무와 인사부터 엔지니어와 그 밖의 모든 사람에게서 학습할 테니까요.

회사 두뇌에 매일 발생하는 업데이트 수를 그래프로 그린다면 어떤 모습일까요? 대략 하향하는 모양일까요? 여기 그래프들은 모두 무작위로 그린 것이지만, 처음에는 높았다가 내려갈까요? 업데이트가 급증하면서 오르내리기를 반복해 일정하게 유지될까요? 아니면 꾸준히 증가할까요?

공유 스킬 저장소(shared-skills repo)의 커밋 기록이 어떻게 보일지 생각해 보세요. 건강한 회사의 두뇌에는 매일 몇 건의 업데이트가 발생할까요? 그 추세는 어떤 모습일까요?

A라고 생각하는 분 계신가요? A라고 생각하시나요?

좋습니다. B는요? C는요? 좋네요.

건강한 회사의 두뇌가 어떤 모습인지 알아보기 위해 저희 데이터를 그래프로 그려 봤을 때, 첫 번째 경우는 기본적으로 열정이 아주 많았다는 뜻입니다. 첫째 날과 둘째 날에 회사의 두뇌를 구축했습니다. 누군가에게 “공유 스킬 저장소 전체를 만들고, Slack 메시지를 전부 스크랩하고, 이메일도 전부 스크랩해서 구축하면 우리 모두 사용하겠다”고 시켰습니다.

그런데 아무도 관심을 갖지 않습니다.

또는 자동 학습하는 시스템을 갖고 있을 수도 있습니다. 예를 들어 내부에 Hermes 같은 것을 배포하면 콘텐츠가 계속 추가될 수 있습니다. 누가 얼마나 열정적인지에 따라 오르내리면서 증가합니다.

지난 두 달간의 기록을 그래프로 그려 봤는데—지금은 조금 오래된 데이터입니다—이런 결과가 나왔습니다. 저는 충격을 받았습니다. “왜 계속 증가하지?”라고 생각했죠. 완만한 곡선이었습니다. 그런데 왜 완만하게 올라가는 걸까요? 하루 업데이트 수가 왜 증가하는 걸까요?

이 현상은 제게 매우 흥미로웠습니다. 제가 깨달은 것은, 작동하기 시작한 시스템이 있으면 사람들이 훨씬 더 많이 가르치기 시작한다는 점입니다. “데이터를 쿼리하는 기술을 가르쳤다면, 내일은 그 데이터를 해석하는 기술을 가르치겠다. 모레는 그걸 바탕으로 행동을 취하는 방법을 가르치겠다. 그다음에는 이를 바탕으로 A/B 테스트를 하는 방법을 알아내겠다”라고 말하는 것과 같습니다.

사람들은 계속 더 많은 것을 추가합니다. 하지만 모든 것이 에이전트이고, 어떤 학습도 완벽하지 않기 때문에 각각의 항목에도 일정한 증가율이 있습니다. 따라서 그 일정한 증가율도 계속 누적됩니다. 저희 시스템에서도 그것이 나타나기 시작했습니다.

아직 초기 단계이므로 결국 정체될지는 아무도 모릅니다. 어쩌면 결국 B와 비슷한 모습이 될 수도 있습니다. 하지만 건강한 두뇌는 전체 규모가 계속 커집니다. 매일 발생하는 업데이트 수도 계속 증가합니다. 이것이 회사에 구축한 두뇌가 건강하고 잘 작동한다는 신호입니다.

첫 번째는 회사의 두뇌가 있고, 이를 AI 에이전트나 다른 도구에서 사용해 업무를 처리하는 경우입니다. 예를 들어 보겠습니다. 고객에게 답변해야 하는 보안 설문지를 이메일로 받았다고 해보죠. 저는 AI에게 “회사 두뇌를 찾아보고 이 보안 설문지에 답하는 것을 도와줘”라고 말합니다. 이는 회사 두뇌의 완전히 타당한 활용 사례입니다. 다른 사람들의 지식이 제게 전달되기 때문에 매우 유용합니다.

예를 들어 협업형 장애 관리가 있을 수 있습니다. “로그를 가져오고 싶어. 장애를 조사해 줘. 로그를 가져오고, 코드베이스를 조사하고, PR을 올리고, 스테이징에 배포하고, 프로덕션에 배포하고, 알림을 설정해 줘”라고 말할 수 있습니다.

제가 정의하는 방식은 이렇습니다. 코딩 에이전트(coding agent)에 제공되는, Markdown 또는 Markdown 파일 모음으로 작성한 공유 컨텍스트(shared context)와, 접근하려는 다양한 데이터와 도구에 대한 접근 제어 규칙(access-control rules)입니다. 제가 말하고 있으니 원하는 대로 정의해도 되겠죠. 이것이 제 정의입니다.

제가 말하는 것은 LLM에 지식을 넣어 도구를 호출하게 하는 시스템이 아닙니다. 범용적인 작업을 수행하는 AI도 아닙니다. 여러분이 던지는 어떤 문제든 해결하는 AI 코딩 에이전트입니다.

여러분 중 일부는 앞선 강연에서 비슷한 아이디어를 들었을 수도 있습니다. 코딩 에이전트 하나만으로 일반적인 문제를 해결할 수 있을까요? 그게 전부입니다.

가장 간단한 경우, “트윗 하나 써 줘”라고 한다면 AI를 호출해 짧은 트윗을 작성하는 작은 스크립트를 만들 수 있습니다. 하지만 아마 그럴 필요는 없을 겁니다. AI 자체가 여러분에게 트윗을 바로 반환하면 되니까요.

하지만 본질적으로 Claude Code를 모든 일에 사용하는 것은 Claude Cowork와 동일한 아키텍처입니다. Codex 앱도 같은 아키텍처를 사용합니다. 코딩 에이전트를 사용해 범용적인 문제를 해결할 수 있다는 깨달음입니다.

그래서 저희는 이를 위한 두뇌를 구축하고 있습니다. 회사 전체를 위한 거대한 지식 그래프나 지식 베이스를 만든 다음 그것을 보호하려는 것이 아닙니다. 그런 방식은 지금까지 성공하지 못했고, 앞으로도 성공하지 못할 것입니다.

회사 두뇌를 어떻게 설계할지 생각해 보면, 회사의 두뇌를 구축해야 할까요? 여러분이 기업에서 빈둥거리며 시간을 보내는 대가로 급여를 받는 사람이라면 회사의 두뇌를 구축한다는 아이디어를 좋아할 겁니다. “좋아, 2년짜리 프로젝트를 맡아서 J.P. Morgan의 회사 두뇌를 구축해 보자”라고 생각할 테니까요.

그런 일은 일어나지 않습니다. 100년 된 조직을 위한 회사의 두뇌를 구축할 수는 없습니다. 몇 달 또는 몇 년밖에 되지 않았을 수도 있는 자기 가족을 위한 두뇌 하나도 간신히 구축할 수 있을 뿐입니다.

회사의 두뇌를 구축하는 아이디어와 방식은, 회사에서 조금이라도 일을 하는 각자가 회사 두뇌의 자기 부분을 소유하고 구축하도록 하는 것입니다. 그렇게 구축해야 합니다.

이것이 두 번째 제약 조건입니다. 첫 번째는 회사 두뇌의 정의였고, 두 번째는 이를 구축할 때 취해야 할 접근 방식입니다.

저는 이를 이렇게 표현하는 것을 좋아합니다. 우리는 회사의 두뇌를 구축하는 것이 아니라 성장시킬 것입니다. 하나를 만들어 내는 것이 아닙니다. 회사의 두뇌가 자연스럽게 형성되도록 할 것입니다. 시스템이 서로 맞물려 형성되어야 합니다. 그렇지 않으면 구축할 수 없습니다.

큰 틀에서 보면, 각자가 회사 두뇌의 자기 부분을 직접 관리하도록 해야 합니다. 따라야 할 단계는 다음과 같습니다. 시간이 있다면 나중에 더 자세히 다시 이야기하겠습니다.

특정 사용 사례부터 시작해 보겠습니다. 이 사용 사례에서는 구체적인 예로 삼고 싶은 상황이 있습니다. 이메일을 하나 받았습니다. 보안 설문(security questionnaire)의 사례입니다.

Stitch Fix의 Dave에게서 이메일을 받았고, 답변하고 싶은 질문이 잔뜩 들어 있었습니다. 이메일을 열어 보니 보안 온보딩 화면의 스크린샷이 첨부되어 있다고 나왔습니다. 그러더니 그 질문들에 답하기 시작했습니다.

어떻게 알았는지 전혀 모르겠습니다. 모든 질문에 답해 놓은 것을 보고 정말 놀랐습니다. 예를 들면 “이게 우리 트러스트 센터(trust center)입니다. 우리 보안 설정은 이렇게 되어 있습니다. 게이트웨이가 있고, 이런 일을 합니다”와 같은 내용이었습니다.

이 모든 정보는 회사 브레인(company brain)에서 나온 것입니다. 그러고 나서 저는 “그냥 이대로 보내 줘. 이 초안 마음에 들어. Dave에게 이 초안을 보내 줘”라고 했고, 이메일이 발송됐습니다. 제가 하고 싶은 일이 어떤 것인지 보여 주는 정말 간단한 예입니다.

이제 여기서의 과제이자 문제는 이런 시스템을 어떻게 구축하느냐는 것입니다…

다른 사람이 여기에 기여할 수 있고, 또 제3자가 그것을 사용할 수 있어야 합니다. 우리 보안 프로세스에 관한 지식은 어떻게 들어온 걸까요? 아마 누군가가 같은 보안 설문을 작업하고 있었을 것입니다.

그래서 그 사람에게 Hermes 에이전트든 뭐든 있었다고 해 봅시다. 그 사람이 작업을 했고, 여러분은 메모리(memory)를 자동 저장했을 수도 있습니다. 누군가 스킬(skill)을 기록했을 수도 있습니다. 어떤 식으로든 그 지식 조각이 제 AI 에이전트로 들어와야 합니다. 어떻게 가능하게 만들 수 있을까요?

이제 첫 번째로 떠올리기 쉬운 방법을 시도해 봅시다. 모두가 서로를 위해 GitHub에 공유 스킬(shared skills)을 작성하는 것입니다.

처음 보안 담당자가 보안 설문에 답하는 장면을 떠올리면, 모두 머릿속에 보안 및 컴플라이언스 담당자를 그렸을 것입니다. 이제 답변하기 끔찍한 그 설문에 답하고, 거대한 엑셀 형식의 설문지를 작성한 뒤, GitHub로 가서 공유 스킬을 업데이트하는 모습을 상상해 보세요.

여러분 중 상당수는 우리 주님이자 구세주이신 그리스도를 본뜬 듯한, 너무나 친절해서 GitHub 저장소의 공유 스킬까지 업데이트해 주는 사람들과 일하는 행운을 누리고 있습니다. 하지만 대부분의 사람은 그렇게 하지 않습니다. 누구도 다른 사람을 위해 GitHub에 스킬을 작성하지 않을 것입니다. 그건 우리에게 자연스러운 일이 아니잖아요?

일상적으로 일을 하면서 우리는 갑자기 “나와 전혀 모르는 사람, 지금 이 상황에서 나와 연결되어 있지도 않은 누군가에게, 미래에 이게 정말 유용할 수도 있겠네”라고 생각하지 않습니다. 그런 일은 일어나지 않습니다. 저는 제 기억과 맥락조차 간신히 정리합니다. 다른 사람을 위해 기록할 시간은 없습니다.

두 번째로, 회사 브레인을 두는 대신 팀 브레인(team brain)을 두면 어떨까요? 그냥 모두 하나의 공유 브레인을 사용하면 안 될까요? 보안팀이 이런 일을 할 수 있는 공유 사일로(silo)를 하나 더 사용하면 안 될까요?

에이전트를 만들고 스스로 메모리에 저장하게 하세요. 아마 여러분 중 많은 분이 가진 아키텍처가 이것일 겁니다. Slack에 Hermes 에이전트 같은 것을 추가하는 방식이죠.

여러 사람이 사용하는 AI가 있고, 그 AI가 메모리를 자동 저장하고 맥락을 자동으로 추가하는 팀 브레인 환경을 갖춘 분이 있나요? 소규모 팀을 위해 이미 그런 일을 하는 스킬을 가진 분이 있나요?

한 분. 또 있나요? 좋습니다. 몇 분이 그런 환경을 갖고 계시네요. 멋집니다.

이 방식도 괜찮지만, 여전히 회사 브레인은 아닙니다. 여전히 고립되어 있기 때문입니다. 사일로가 하나 더 생긴 것뿐입니다. 예를 들어 Claude 채팅에는 채널별 메모리가 있습니다. 각 채널에서 내용이 저장되지만, 이제 그 채널 안에 또 하나의 사일로가 생깁니다. 한곳에 갇혀서 다른 곳에서는 사용할 수 없습니다. 누군가 채널에 추가되면 작동하겠지만, 그렇지 않으면 작동하지 않습니다.

세 번째 방법은 모든 맥락을 하나의 공유 위키(shared wiki)에 넣는 것입니다.

위키는 Markdown 파일들의 모음이고, Markdown 파일들은 서로 링크할 수 있습니다. 거대한 폴더를 상상해 보세요. 그 폴더에는 수많은 Markdown 파일이 있고, Markdown 파일들은 서로 링크할 수 있습니다.

모든 맥락을 폴더 안에 저장해 사일로화하는 대신, Markdown 파일이나 그에 해당하는 곳에 넣고 파일들이 서로 링크되게 하는 것입니다.

두 번째로 할 일은 각 파일에 누가 읽기 및 쓰기 권한을 가질 수 있는지 정의하는 스코프(scope)를 설정하는 것입니다.

세 번째로 할 일, 그리고 가장 중요한 일은 에이전트가 메모리를 자동으로 추가하지 못하게 하는 것입니다. 자동으로 추가하게 두면 무슨 일이 일어났는지 전혀 알 수 없습니다. 뭔가가 추가되고, 그 에이전트의 메모리 안에 있는 동안에는 운이 좋다고 여기는 동일한 세계로 다시 돌아갈 수 없습니다.

에이전트가 자동으로 추가하게 하는 대신, 무엇을 어떤 스코프로 추가할지 에이전트가 제안하게 하고, 사람이 이를 수락하거나 거부하게 하세요.

무언가를 직접 작성하고, 공유 스킬을 업데이트하고, PR 리뷰(pull request review)를 하고, 병합되기를 기다려야 하는 GitHub만큼 무거운 방식은 아닙니다. 그렇다고 에이전트가 메모리를 마음대로 자동 기록하는 YOLO 방식만큼 무모하지도 않습니다.

이것이 가장 적절한 지점입니다. 작업하는 동안 창을 띄우고, 적절한 스코프를 제안하게 한 뒤, 누군가가 추가하도록 하면 됩니다.

이 아주 간단한 추가만으로도 사람들이 거대한 위키에 내용을 추가할 수 있게 하면서, 각자가 무엇을 볼 수 있고 무엇을 볼 수 없는지 책임지게 할 수 있습니다.

제가 금융 위키에 무언가를 추가한다면, 민감한 내용인지 확인하고 싶습니다. 금융 스코프가 지정되어 있는지 확인하고 싶습니다. 개인적인 내용을 추가한다면 개인 스코프가 지정되어 있는지 확인하고 싶습니다.

이것이 사용자 경험(user experience)에서 어떤 모습일지 예를 들어 보여 드리겠습니다.

우리가 하는 방식은 이렇습니다. 최근에 영업 담당자 중 한 명이 저를 통화에 초대하며 보낸 이메일입니다. 저는 그 이메일을 보고 답변을 작성하는 데 도움을 받았습니다. 그러자 추가하려는 내용을 여러 개의 글머리표로 제안하는 작은 상자가 나타났습니다.

“위키에 추가(Add to Wiki)”를 누르면 무엇이 추가되는지 훨씬 쉽게 검토할 수 있습니다. 이것이 이 Markdown 파일에 추가되는지 저 Markdown 파일에 추가되는지, 에이전트가 어떤 링크를 처리하는지는 중요하지 않습니다. 제가 신경 쓰는 것은 이 사실들이 정확한지 여부입니다. 정확하다면 “위키에 추가”를 누르고 끝내면 됩니다.

“위키에 추가” 과정에서 각 위키 페이지에 어떤 스코프를 추가해야 하는지 선택할 수 있습니다. 각 위키 페이지에는 특정한 스코프 집합을 지정할 수 있으므로, 누가 무엇에 접근할 수 있는지 결정할 수 있습니다.

예를 들어 이것은 제 이메일과 이메일 우선순위 지정 방식에 관한 위키 페이지입니다. 이제 누가 이 페이지에 접근할 수 있는지, 소유자는 누구인지, 소유자가 무엇을 책임지는지 결정할 수 있습니다.

시스템이 어떤 모습일지는 여러분에게 달려 있습니다. 하지만 핵심 아이디어는 에이전트가 변경을 직접 실행하는 대신 변경을 제안하게 하는 것입니다.

규칙은 두 가지입니다.

첫째, 모든 내용이 회사 전체의 하나의 위키로 들어가게 하세요. 이 규칙에서 물러서지 마세요.

둘째, 그 과정의 일부로 모든 변경 사항에 사람의 이름이 남도록 하세요. “Claude가 추가함”, “여러분의 AI 에이전트가 추가함”, “Hermes가 추가함”이라고 표시된 내용은 위키 안에 들어갈 수 없어야 합니다.

아니요. “Tanmay가 추가함”이어야 합니다. 모든 사람의 보상 정보를 볼 수 있게 망쳐 놓은 사람, 또는 그런 일이 무엇이든 저지른 사람에게 거슬러 올라갈 수 있도록 그 이름이 있어야 합니다. 이제 그에 맞는 시정 조치를 취할 수 있습니다. 그게 무엇이든 말입니다. PIP(성과개선계획)에 넣을 수도 있겠죠. 위키 편집 방법을 몰랐던 겁니다.

이 점은 정말, 정말 중요합니다.

이를 결정했다면 두 번째 부분으로 넘어갈 수 있습니다. 사람들이 그렇게 하기 쉽게 만들어야 합니다. 그때 스코프가 필요합니다. 각 파일에 누가 접근할 수 있는지에 따라 스코프를 지정하고, 그에 맞는 시스템을 구축해야 합니다.

이것이 그 구조를 나타낸 아키텍처 다이어그램입니다. 사용자들이 있고, 사용자들은 에이전트와 대화합니다. 에이전트가 맥락을 읽을 때는 해당 사용자의 클레임(claim)을 사용합니다.

제가 금융 문제를 해결하기 위해 무언가를 읽는다면, 에이전트는 저를 대신해 금융 클레임을 사용해 읽습니다. 제가 금융 위키에 접근할 권한을 가지고 있기 때문에 읽을 수 있는 것입니다. 이 작업은 매번 수행됩니다. 에이전트는 항상 사용자의 자격 증명(credentials)을 사용해 위키의 올바른 부분을 읽습니다.

두 번째 사용 사례까지 설명할 시간이 거의 없으니, 빠르게 어떤 것인지 보여 드리고 이 아이디어를 확장해 보겠습니다.

이것이 핵심 사용 사례입니다. 가장 중요한 사용 사례입니다. 이제 한 사람이 이메일 하나에 답하는 것이 아니라, 여러 권한 상승(privilege escalation) 수준을 가진 여러 사람이 동시에 공유 맥락을 사용해 문제를 해결하기 때문에 정말 복잡한 사용 사례입니다.

회사 브레인 지식이 가장 많이 생성되는 AI 상호작용은 바로 이런 것들입니다.

예를 들어 이것이 실제로 우리에게 어떤 모습인지 간단한 실사례를 보여 드리겠습니다.

SRE 상황에서 나온 사례입니다. 누군가 이렇게 말했습니다. “이봐요, 우리의 자동 학습(auto-learning)—상당히 메타적인 위키 학습—이 실패하고 있어요. 작동하지 않습니다. 무슨 일이죠?”

그러자 조사를 시작했는데, 스킬이 없어서 실패했습니다. “이봐, 그러지 마세요. 이 OpenTelemetry 스팬 이름(OpenTelemetry span name)을 사용하세요”라는 식이었습니다.

OpenTelemetry 스팬 이름을 사용하자 조금 나아졌지만 여전히 정말 느렸습니다. 그래서 코드를 살펴보더니 이렇게 말했습니다. “아, LIKE 쿼리를 사용하고 있군요. 바보 같은 짓입니다. 이건 Opus 4.5예요. 그러지 마세요.”

그러고 나서 “LIKE 쿼리를 사용하지 마세요. equals 쿼리를 사용하세요”라고 했습니다. equals 쿼리를 실행하자 몇 가지 세부 정보가 나타났습니다. 그러자 “이걸 더 깊이 파고들어 보세요”라고 했고, 에이전트는 “아무튼, 오류가 발생한 코드 라인은 여기입니다”라고 답했습니다.

간단한 일이죠?

이때 에이전트가 지식을 드러내며 이렇게 말합니다. “아하, LIKE가 아니라 equals를 사용해야 한다는 것을 배웠습니다. 위키 페이지 이름에 사용자 지정 접두사(custom prefix)가 추가되어 있으면 문제가 발생할 수 있다는 것도 배웠습니다.”

이런 학습 내용을 수락할 수 있도록 제안합니다. 그는 문제가 무엇인지 더 깊이 파고들었습니다. 그러자 다른 사람이 대화에 참여해 말했습니다. “여기서 우리가 내린 기술적 결정이 잘못됐습니다. 왜 이런 일이 발생하는 거죠?”

이제 두 사람이 논쟁을 시작합니다. “이렇게 되어서는 안 됩니다. 이렇게 되어야 합니다. 그런데 왜 이렇게 되어 있죠? 이렇게 되어야 합니다”라고 논쟁합니다.

그 논쟁이 지식을 만들어 냅니다. 실제 문제는 누군가가 기술적 결정을 내렸지만 그 결정이 문서화되지 않았다는 것이었기 때문입니다.

문제를 수정하기로 결정하고, 이것이 실제 근본 원인임을 확인하고, 어떻게 수정할지 결정하는 순간—“문제를 일으키는 이 접두사를 제거해야 합니다”—여러분의 브레인에 추가될 가장 높은 품질의 맥락이 만들어집니다.

앞서 나온 제안은 페이지에 접두사를 붙여야 한다는 것이었지만, 페이지에 접두사가 있다는 사실 자체가 문제입니다. 따라서 이제 브레인(brain)에 문서화할 내용은 “페이지에는 접두사를 붙이지 않아야 한다”는 것입니다. 접두사가 있으면 프로덕션에서 조회 문제가 발생할 수 있습니다.

여러 사람이 서로 대화하며 함께 문제를 해결할 때 이런 일이 일어납니다. 두 사람이 서로 대화하며 문제를 해결하는 Slack 스레드에서 일어나는 일이 바로 이것입니다. 그것이 가장 품질 높은 컨텍스트를 만들어냅니다.

여기서 원하는 것이 바로 그것입니다.

하지만 이와 관련된 권한 상승(privilege escalation)은 매우, 매우 심각한 문제가 됩니다. 여러 사람이 함께 있는 환경에서 무엇이든 할 수 있는 에이전트를 구축한다면, 무서운 일입니다.

엔지니어는 PR 작업을 하도록 허용되었는데, 이제 저는 같은 에이전트를 사용해 프로덕션에 배포할 수 있습니다. 그건 너무 무섭습니다. 특히 은행에 있다면, 디버깅과 보안을 유지한 배포를 한 대화 안에서 처리할 수는 없습니다.

디버깅하는 사람, 스테이징에 배포하는 사람, 알림을 설정하는 사람, 배포하는 사람은 서로 다릅니다. 하지만 이들을 동일하게 만드는 데는 큰 가치가 있습니다. 모든 지식이 그곳에 있기 때문입니다.

이제 두 번째 아키텍처로 넘어가겠습니다. 너무 자세히 다루지는 않겠습니다. 사용자 자격 증명과 클레임(claim)을 사용해 컨텍스트를 읽는 동일한 아이디어라고 생각해 보세요. 거기에 그치지 말고, 코드가 도구를 실행할 때도 사용자 자격 증명을 사용합니다.

자격 증명을 샌드박스(sandbox)에 절대 저장하지 마세요. 대신 HTTP 계층과 SQL 계층에서 사용자의 자격 증명을 주입해, 특정 상호작용에서 AI가 인간처럼 행동하도록 하세요.

여기에는 흥미로운 세부 사항들이 있지만, 이것이 공유 AI가 공유 컨텍스트와 함께 작동할 수 있게 해주는 방법입니다. 함께 작동하려면 이 두 가지 핵심 요소가 필요합니다.

요약하자면, 이 아키텍처는 특별히 복잡하지 않습니다. 다음 두 규칙에서 거꾸로 생각해 보면 매우 간단합니다.

Claude 샌드박스에 자격 증명을 저장하지 마세요.

둘째, 실제 데이터와의 모든 상호작용을 가상화하세요. 프록시를 사용하든, 가상화하든—어떤 표현을 쓰든 상관없습니다.

그리고 사용자가 이를 통제하도록 하세요. 특정 도구를 추가하는 사용자가 그 도구에 누가 접근할 수 있는지를 통제해야 합니다.

이 네 가지 원칙을 따르고 그 원칙에서 거꾸로 생각하면 전체 구조를 도출할 수 있습니다. 컨텍스트를 어떻게 관리할지, 어떤 제약 조건을 설정할지, 도구를 어떻게 관리할지, 어떤 보안 규칙을 수립할지에 관해서는 타당한 아키텍처가 하나뿐입니다.
