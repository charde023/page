먼저 읽는 쉬운 요약

영상을 대신 읽는 시각 해설

영상 미시청 기준 · 약 11분 · 선수지식: PR은 코드 변경 묶음, CI는 변경 시 자동으로 실행하는 검사 약 한 시간의 대담을 ‘신뢰가 생기는 조건’ 중심으로 재구성했다. 그림은 측정 그래프가 아니라 원문을 정리한 개념 지도다.

1. 숲: 에이전트의 자신감이 아니라 일하는 환경을 믿는다

Lauren Tan은 에이전트를 믿지 못하면 모든 행동을 옆에서 지켜보게 되고, 그러면 여러 에이전트를 늘려도 사람이 병목에 남는다고 설명한다. 반대로 에이전트를 무작정 믿고 수백 개부터 돌리라는 이야기도 아니다. 검증할 수 있는 환경과 잘못된 변경을 막는 구조를 먼저 만들어야 위임의 범위를 넓힐 수 있다는 이야기다.

그녀가 말하는 신뢰에는 두 가지 질문이 있다. ‘지금 수정이 실제 문제를 해결했는가?’와 ‘이 코드베이스가 계속 유지 가능한 방향으로 바뀌는가?’다. 앱을 실행해 동작을 확인하는 일은 첫 번째를 돕지만, 그것만으로 설계가 좋은 코드라고 보장하지는 않는다. 그래서 대담 후반부에는 검증 도구를 넘어 아키텍처와 강제 검사 이야기가 이어진다.

읽는 법: 세 칸은 다른 문제를 해결한다. 앱 제어 도구가 있어도 길을 모르면 헤매고, 길을 알아도 검사가 약하면 잘못된 코드를 넣을 수 있다. ‘좋은 모델을 골랐으니 해결’이 아니라 세 조건이 함께 받쳐줘야 한다는 지도다.

2. 나무: 사람이 스크린샷 전달자가 되면 병렬화가 멈춘다

입사 초기 그녀는 낯선 Agent Window의 성능 문제를 조사했다. 사람이 Chrome DevTools에서 실행 기록을 수집해 에이전트에게 전달하면 에이전트가 원인을 자신 있게 지목했지만, 수정해 보면 실제 문제가 아닌 일이 반복됐다고 한다. 사용자가 증상을 재현하고 화면·오류를 복사해 주어야만 다음 단계로 가는 구조에서는 결국 사람이 여러 작업의 교차로가 된다.

이를 바꾸려고 만든 Control Glass 스킬은 에이전트가 앱을 실행하고 직접 상호작용하며 트레이스 같은 실행 근거를 수집하게 했다. 하지만 도구를 쓸 수 있게 된 것만으로 충분하지 않았다. 에이전트는 사이드바나 PR 탭이 무엇이고 어떻게 열어야 하는지 몰라 무작정 클릭하며 헤맸다. 그래서 기능에 접근하는 경로를 기록한 feature map이 필요했다.

읽는 법: 두 번째 칸의 고리가 끊기지 않으려면 재검증 경로가 있어야 한다. ‘코드를 바꿨다’나 ‘테스트가 통과했다’는 문장만으로 사용자가 겪던 증상이 사라졌다고 결론 낼 수 없다. 이 고리는 작동 여부를 확인하는 방식이며, 모든 코드 품질을 보장하는 만능 검사는 아니다.

3. 나무: 기능 지도와 스킬을 실제 행동으로 시험한다

feature map에는 기능 이름만 들어가는 것이 아니다. 사이드바의 하위 기능, 사용자 관점의 접근 순서, 단축키, DOM 요소를 찾는 속성처럼 실제 화면에 도달할 단서가 들어간다. 그러면 ‘이게 뭐죠?’라는 짧은 제보와 스크린샷도 어떤 기능을 재현해야 할지 찾는 출발점이 될 수 있다. 제품이 바뀌므로 지도를 유지하는 작업도 필요하다.

PStack은 이런 실패를 관찰하며 점진적으로 모인 스킬 묶음이라고 소개한다. 예를 들어 원인을 단정하면서 정작 관련 코드를 읽지 않는 실패를 보고, 추측 대신 코드를 찾고 조사하게 하는 지침을 만든다. 여기에 스킬을 실제 과제로 시험하는 eval을 붙인다. eval은 ‘지침이 잘 쓰였나’를 읽어 평가하는 것보다 ‘그 지침을 받은 에이전트가 원하는 행동을 하는가’를 확인하는 시험에 가깝다.

화자는 작업 에이전트를 분리된 디렉터리에서 실행하고 기준표로 평가하며 여러 모델에서도 확인한다고 말한다. 평가받는다는 사실을 알면 행동이 달라질 수 있다는 점과 심사 모델의 편향도 언급한다. 반복 평가 점수가 높아졌다는 것과 실제 모든 작업에서 안전하다는 것은 다르므로, 같은 시험만 통과했다고 신뢰를 무제한 늘릴 수는 없다.

읽는 법: 번호는 신뢰를 쌓는 방향을 표현한다. 시간만 지나면 다음 단계로 올라간다는 뜻이 아니다. 영상의 Benny 사례에서는 클라우드 에이전트가 버그를 재현하고 main에 수정이 이미 반영됐음을 확인해 새 빌드가 필요하다는 정보를 준다. ‘재현 불가’와 ‘코드는 수정됐지만 아직 배포 전’을 구분할 수 있어 사람이 직접 조사하는 시간을 줄였다는 사례다.

4. 다시 숲: 검증만으로 부족한 이유는 구조가 계속 변하기 때문이다

대담의 두 번째 큰 축은 코드베이스의 구조다. 기존 서비스라도 규칙·권한·검사가 잘 갖춰졌다면 에이전트 작업을 받기 유리할 수 있다. 반대로 새 프로젝트는 빠르게 만들기 쉽지만 안전장치 없이 편한 길만 택하다 보면 사람이 이해하기 어려운 구조가 쌓일 수 있다. ‘새 프로젝트니까 무조건 좋다’도, ‘기존 프로젝트는 무조건 다시 써야 한다’도 아니다.

그녀는 GrokBot을 새로운 아키텍처로 바꾸는 데 600개 넘는 PR을 처리했다고 설명한다. 핵심 설계 원칙은 가장 짧은 길이 가장 좋은 길이 되게 만들기다. 기능 관련 코드를 한곳에 모으고 기능을 만드는 관례를 명확히 하면, 기존 패턴을 복사하는 에이전트가 덜 헤매게 된다. 잘못된 구조를 만든 뒤 사람이 매번 리뷰에서 고치는 대신, 잘못된 방향으로 가기 어렵게 경로를 만든다.

읽는 법: 위쪽 두 층을 아래쪽 문서가 대신하지 못한다. 단, 정적 검사가 통과했다고 사용자 동작이나 권한·업무상 결과가 모두 맞는 것도 아니다. 앞부분의 실제 실행 검증과 이 구조적 제약은 서로 보완한다.

5. 나무: 화면이 버벅이는 문제를 말이 아닌 검사로 막기

영상의 구체 사례는 Electron 앱의 화면 성능이다. 화면을 그리는 렌더러 쪽에 무거운 계산이나 I/O가 들어오면 화면 갱신과 자원을 다투게 된다. 화자는 60 FPS를 목표로 할 때 프레임마다 약 16밀리초라는 짧은 시간이 있다고 설명한다. 작은 변경 하나가 이 시간을 넘기는 작업을 만들면 화면이 끊길 수 있다.

GrokBot에서는 electron-main과 electron-renderer 사이의 잘못된 임포트를 의존성 검사로 막는다고 한다. ‘무거운 처리를 화면 쪽에 넣지 마’라고 문서에 적는 것과 실제 잘못된 의존성을 CI에서 실패시키는 것은 다르다. useEffect나 코드 주석을 금지한 예도 나오지만, 이는 그 팀의 아키텍처와 관찰한 실패에 맞춘 정책이다. 모든 프로젝트에서 똑같이 금지하라는 보편 법칙이 아니다.

읽는 법: 그림은 원문의 원칙을 운영 고리로 재구성한 것이다. 중요한 상태 차이도 있다. 화자는 이 구조를 GrokBot에 적용한 경험을 말하는 한편, Agent Window에는 아직 같은 아키텍처가 없고 리팩터링할 계획이라고 한다. 두 제품에 이미 모두 적용됐다고 읽으면 안 된다.

6. 통찰과 한계: PR 수보다 검증된 위임 범위를 본다

화자는 지난달 PR 1,000개, 이번 달 12일 동안 거의 800개, 잠든 사이 20개 자동 병합이라는 경험을 말한다. 이 숫자는 생산성의 관심을 끄는 사례지만 서로 다른 기간과 상황을 가리키며, 독립 검증된 품질 지표가 아니다. PR 크기도 일정하지 않고 엄격한 상한은 없다고 설명한다. 작은 의미 단위로 나누는 이유는 이력을 이해하고 문제를 되돌리기 쉽게 하기 위해서다.

비용에도 경계가 있다. 화자는 사실상 무제한 토큰을 쓸 수 있는 환경이라고 밝히며 모두가 같은 투자를 해야 한다고 말할 수 없다고 한다. 초기 스킬·검증·리팩터링의 비용과, 이후 팀 전체가 얻는 기여 가능성을 비교해야 한다. 영상의 모델 가격·성능 발언은 당시 화자의 설명이며 현재 구매 판단의 확정 정보로 삼지 않는다.

비개발자에게 익숙한 인터페이스를 제공하고 구조가 잘못된 기여를 막아 주면 PM과 디자이너도 기능 개선에 참여할 수 있다는 것이 마지막 조직적 함의다. 이를 ‘검토를 없애자’보다 ‘사람이 같은 실수를 매번 찾아내지 않도록 환경에 기준을 심자’로 읽는 편이 안전하다. 차드에게 적용한다면 작은 범위에서 반복되는 실패 하나를 재현 가능한 검사로 바꾸는 것부터 생각할 수 있지만, 이 노트는 자동 병합이나 외부 실행을 승인하지 않는다.

여기까지만 이해하면 충분

  • 에이전트 신뢰는 실제 실행 근거·기능 지도·강제 가능한 구조를 함께 쌓아 만드는 것이다.
  • 스킬은 실제 과제로 시험하고, 반복되는 잘못은 문서뿐 아니라 CI와 구조적 제약으로 막는다.
  • GrokBot의 적용 사례와 Agent Window의 향후 계획을 구분하며 자동 병합·대규모 토큰 투자를 그대로 따라 하지 않는다.

비유와 깨지는 지점

주방을 설계하는 수석 요리사

엔지니어는 모든 요리를 직접 만드는 사람이 아니라 조리대, 동선, 조리법과 품질 검사를 설계하는 수석 요리사에 가깝다. 에이전트는 각 작업대에서 일하고, 스킬은 조리법, CI는 기준을 어긴 요리가 나가지 못하게 하는 검사대에 대응한다.

비유가 깨지는 지점: 에이전트는 사람처럼 책임과 상황 이해를 안정적으로 유지하지 않는다. 지시를 잊거나 평가 상황에서 행동을 달리할 수 있으므로 실제 실행 기록과 기계적 검사가 필요하다.

1. 원인

실행 도구를 가진 에이전트도 기능 지도 없이 버그 해결에 실패할 수 있는 이유는 무엇인가?

모범 답안 보기

프로그램을 조작할 수 있어도 어떤 화면으로 이동해야 하는지, 사용자 표현이 어느 기능과 연결되는지 모르면 탐색에 시간을 쓰거나 엉뚱한 코드를 추측한다. 기능 지도는 사용자 관점의 위치와 코드·조작 정보를 연결해 검증을 시작할 문맥을 제공한다.

2. 대조

1. 경력과 관리 비유

Lauren Tan은 Cursor에서 약 5개월 일했으며, 이전에는 Meta의 React 팀에서 React Compiler를 개발했다고 소개했다. 그 전에는 Netflix에서 기술 리드와 약 2년간 엔지니어링 매니저 역할을 맡았다고 말했다.

그는 사람을 관리한 경험과 에이전트를 관리하는 일이 닮았다고 본다. 팀원을 믿지 못하면 관리자가 모든 일을 확인하는 미세 관리에 빠지듯, 에이전트를 믿지 못하면 사용자가 모든 출력과 도구 호출을 감시하게 된다는 설명이다.

2. 자기 보고 생산성 수치

  • Cursor 합류 첫 달에는 코드베이스를 익히느라 생산성이 낮았다고 말했다.
  • 지난달에는 1,000개 PR을 배포했다고 주장했다.
  • 발표 시점이 그달 12일이며 이미 거의 800개 PR이 병합됐다고 말했다.
  • 발표 당일 아침에는 에이전트가 자동 병합한 약 20개 PR을 나중에 main에서 검토했다고 말했다.
  • GrokBot을 새 구조로 리팩터링하는 데 600개가 넘는 PR을 투입했다고 말했다.
  • PR 크기는 50줄, 수백 줄, 약 1,000줄까지 달라질 수 있으며 정해진 상한은 없다고 답했다.
  • 40,000줄 PR은 문제가 섞여 추적과 되돌리기가 어려운 극단적 예시로 들었다.

이 수치들은 기간과 범위가 서로 다르므로 합산하거나 같은 생산성 지표로 직접 비교하면 안 된다.

3. Control Glass와 기능 지도

Agent Window 출시를 약 일주일 앞둔 시점에 Lauren은 성능 문제를 조사해야 했다고 회고했다. 초기에 에이전트는 추적 자료를 보고도 실제 원인을 확인하지 않은 채 자신 있게 추측했다고 한다.

그가 만든 Control Glass 스킬은 Agent Window를 실행하고 추적 자료를 수집할 수 있게 했다. 그러나 에이전트는 제품의 기능 위치를 몰라 화면을 헤맸다. 이를 보완한 것이 기능 지도다. 여기에는 사용자 관점의 기능 위치, 접근 방법, 단축키, DOM 요소와 선택 속성 등이 들어간다고 설명했다.

PStack의 Create Verification Skill은 초기 기능 지도를 만들고, Maintain Verification Skill은 변경된 제품에 맞춰 이를 갱신하는 용도로 소개됐다.

4. PStack과 에이전트 평가

PStack의 P는 Lauren의 온라인 이름인 Potato에서 왔다고 설명했다. Garry Tan의 GStack 또는 GaryStack을 빗댄 이름이며 두 사람은 친족 관계가 없다고 말했다.

PStack은 처음부터 하나의 체계로 계획된 것이 아니라 에이전트의 실패를 관찰할 때마다 스킬을 추가하며 만들어졌다고 한다. 코드 검색 없이 원인을 추측하는 행동이 보이면 실제 코드를 읽고 하위 에이전트를 사용하도록 절차를 적는 방식이다.

에이전트 평가(evals)는 스킬을 위한 단위 테스트처럼 설명됐다. 주 에이전트가 채점 기준을 만들고 여러 하위 에이전트가 격리된 디렉터리에서 작업하며, 다른 모델의 심판 에이전트로 점수를 교차 확인할 수 있다고 했다. /loop로 모든 평가가 10점 만점에 10점이 될 때까지 반복하는 방식도 예로 들었다. 이는 사용 방법의 예시이지 완전한 신뢰를 보장하는 기준으로 제시된 것은 아니다.

5. 로컬에서 클라우드로

Lauren은 검증 스킬을 처음 만들 때는 로컬에서 시작하라고 권했다. 사람이 에이전트의 앱 실행과 API 호출을 관찰해야 실패 원인을 발견할 수 있기 때문이다.

신뢰가 쌓인 뒤에는 클라우드 에이전트로 확대할 수 있다고 말했다. 예시로 Benny라는 내부 에이전트가 버그 신고를 받아 클라우드 데스크톱에서 Cursor를 실행하고 문제를 재현한다고 설명했다. 한 사례에서는 신고된 문제가 main에서 이미 수정됐음을 확인해 새 빌드 출시만 필요하다는 정보를 제공했다고 한다.

그는 검증 없이 100개 또는 수천 개의 클라우드 에이전트를 바로 실행하면 토큰과 비용을 낭비할 수 있다고 경고했다.

6. Dune의 강제 규칙

Dune은 GrokBot을 위해 만든 아키텍처의 코드명으로 소개됐다. Lauren은 이를 에이전트가 작성하는 Electron 앱을 위한 Next.js와 비슷한 정신 모델로 설명했다.

발표에서 언급한 규칙은 다음과 같다.

  • GrokBot에서 useEffect 사용을 금지하고 CI 실패로 처리한다.
  • 에이전트가 일시적 리뷰 지시를 영구 규칙처럼 주석에 남기는 일이 많다는 이유로 코드 주석도 금지했다. “99%”라는 수치는 화자의 비공식적 표현이다.
  • electron-main과 electron-renderer 디렉터리를 나누고 Import CI로 잘못된 의존성을 검사한다.
  • 기능별 코드를 한 디렉터리에 함께 두며, 화자는 작업의 80% 정도가 그 안에 캡슐화된다고 설명했다.
  • 정적 분석, CI, 린트와 컴파일러 진단을 강한 계층으로 보고, 규칙 문서·스킬·BugBot은 잊힐 수 있는 더 부드러운 계층으로 구분했다.

Agent Window의 성능 사례에서는 60 FPS를 위해 프레임을 약 16밀리초 안에 그려야 하며, 무거운 계산이나 입출력이 렌더링과 경쟁하면 긴 작업과 프레임 손실이 발생한다고 설명했다.

검증의 경우, 어떻게 신뢰할 수 있느냐는 것도 매우 비슷한 반복 루프입니다. 저는 실제로 검증 스킬을 검증할 때도 같은 프로세스를 사용했습니다.

eval에서 흥미로운 점 중 하나는 이를 언덕 오르기(hill-climbing) 방식으로 개선할 수 있다는 것입니다. 즉, eval이 점수를 산출하도록 할 수 있습니다. 코디네이터가 점수를 산출하게 할 수도 있지만, 다른 모델을 사용하는 심사 에이전트(judge agent)를 두고 결과를 교차 검증하게 할 수도 있습니다. 첫 번째 모델, 즉 작업을 수행하는 모든 서브에이전트를 평가하는 모델이 편향되지 않았는지 확인하는 것입니다.

언덕 오르기 방식으로 개선할 수도 있습니다. Cursor에서 /loop를 사용하고, 예를 들어 “모든 항목이 10점 만점에 10점이 될 때까지 이 eval을 계속 반복해”라고 말할 수 있습니다.

Control 스킬에도 기본적으로 같은 접근 방식을 사용했습니다. 실제로는 거의 손을 대지 않았습니다. 그 스킬 안에서 CLI를 그런 방식으로 구축했고, 시간이 지나면서 아주 좋아졌습니다. 처음부터 순조로웠던 것은 절대 아니고, 많은 반복 작업이 필요했습니다.

에이전트가 애플리케이션과 어떻게 상호작용하는지 관찰할 수 있습니다. 애플리케이션과 상호작용할 수 있게 해 주는 다양한 API를 어떻게 호출하는지도 볼 수 있습니다.
