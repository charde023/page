먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

새 연구의 모델 파일과 데이터셋이 Google Drive 같은 외부 저장소에 흩어지면 사람들이 찾고 재사용하기 어렵다. 화자는 먼저 논문 확인, 저장소 읽기, 문서 점검, 이슈 작성처럼 순서가 일정한 일을 미리 정한 경로로 실행하는 워크플로로 만들었다. 이 작업은 매일 밤 돌아가는 예약 프로그램이 처리했다. 반면 연구자의 답변에 대응하는 일은 상황마다 달라서, 언어 모델이 도구를 골라 목표를 마칠 때까지 움직이는 자율 에이전트 루프로 바꿨다. 에이전트에는 명령줄 도구, 작업 지침, 격리된 실행 공간을 주고 이슈별로 나눠 병렬 처리했다. 다만 화자는 후속 작업의 시작을 여전히 수동으로 지시한다고 말한다. 입력·출력·비용·지연 시간은 추적했지만, 평가 절차와 결과는 제시하지 않고 평가가 필요하다고 권고했다. 핵심은 모든 일을 에이전트에 맡기는 것이 아니라, 반복성·변동성·실패 위험에 따라 자동화 방식을 나누고 확대 전에 결과 품질을 확인하는 것이다.

여기까지만 이해하면 충분

  • 순서가 일정한 일은 고정 워크플로가 예측하기 쉽다.
  • 상황별 판단이 필요한 일은 에이전트가 유연하지만 결과도 덜 예측 가능하다.
  • 에이전트 실행의 자율성과 전체 작업의 자동 시작 여부는 구분해야 한다.
  • 추적은 과정을 보여 주지만, 결과가 좋은지 판단하는 평가는 별도로 필요하다.

오늘 대답할 질문

반복적인 연구자 아웃리치에서 언제 고정 워크플로를 쓰고 언제 자율 에이전트로 바꾸며, 확장 전에 무엇을 확인해야 하는가?

  • 이 사례에서 자동 실행된 부분과 여전히 사람이 시작한 부분은 무엇인가?
  • 추적과 평가는 어떤 차이가 있는가?

→ "더 많은 작업을 병렬 처리할 수 있지만 품질·비용·오작동을 따로 평가해야 한다" 결과

비유와 깨지는 지점

철도와 현장 작업자

워크플로는 정해진 역만 지나는 철도와 비슷하다. 에이전트는 목표와 도구를 받은 뒤 현장에서 다음 행동을 고르는 작업자와 비슷하다. 샌드박스는 작업자마다 분리된 작업실에 해당한다.

비유가 깨지는 지점: 실제 에이전트는 사람처럼 책임을 지거나 상황을 완전히 이해하지 않는다. 그럴듯한 잘못을 만들 수 있으므로 격리만으로 결과 품질이 보장되지는 않는다.

1. 원인

화자는 왜 처음부터 모든 업무를 자율 에이전트로 만들지 않았는가?

모범 답안 보기

초기 논문 확인과 이슈 작성 과정은 순서가 비교적 일정했다. 화자는 단순하게 시작하고 불필요한 에이전트와 프레임워크를 피하라는 당시 조언에 따라, 단계별 LLM 호출을 넣은 고정 워크플로를 선택했다고 설명한다.

2. 대조

추적과 평가는 어떻게 다른가?

모범 답안 보기

추적은 에이전트가 어떤 입력과 출력을 만들었고 비용과 시간이 얼마나 들었는지를 보여 준다. 평가는 그 결과가 정확하고 유용하며 허용 가능한 실패 범위 안에 있는지를 판단한다. 과정을 기록했다고 결과 품질까지 검증된 것은 아니다.

3. 적용

새 자동화 후보를 만났을 때 워크플로와 에이전트 중 무엇을 선택할 것인가?

모범 답안 보기

단계와 예외가 안정적이면 먼저 고정 워크플로를 검토한다. 응답과 환경에 따라 다음 행동이 자주 달라진다면 제한된 도구와 샌드박스를 갖춘 에이전트를 시험할 수 있다. 실제 게시나 변경 전에는 대표 사례에서 결과 품질을 사람이 확인해야 한다.

이번 글의 통찰

1. 워크플로와 에이전트는 양자택일이 아니다

  • [원문] 화자는 논문 탐색과 이슈 생성에는 고정 워크플로를, 다양한 답변의 후속 처리에는 Claude Agent SDK 기반 루프를 사용했다고 말한다.
  • [해석] 자동화 단위마다 변동성과 실패 비용을 따져 서로 다른 방식을 조합할 수 있다.
  • [경계] 이 선택이 다른 업무에서도 더 낫다는 비교 실험이나 평가 결과는 제시되지 않았다.

2. 자율성의 범위를 정확히 표시해야 한다

  • [원문] 화자는 후속 처리를 완전 자율 에이전트라고 부르지만, 보통 Cursor의 process_unprocessed_modal 스킬을 자신이 직접 실행한다고도 말한다.
  • [해석] 이 사례의 자율성은 호출된 뒤 이슈별 작업을 수행하는 루프에 해당하며, 전체 과정의 시작까지 항상 무인 자동화된 것은 아니다.
  • [경계] “완전 자율”과 “수동 호출”은 시행 범위를 구분하지 않으면 충돌해 보인다. 야간 이슈 생성 워크플로와 수동 호출되는 후속 처리 에이전트도 서로 다른 구성요소다.

3. 규모의 성과 주장과 안전성 검증은 별개다

  • [원문] 화자는 매일 밤 수백 개의 이슈, 누적 수천 개 중 부정적 댓글 두 개, 400GB 데이터셋 문의, PaddleOCR 이전 등의 사례를 제시하고 평가를 잊지 말라고 권고한다.
  • [해석] 많은 처리량과 긍정적 반응은 탐색 신호가 될 수 있지만, 정확성·스팸·수신자 신뢰를 판단하는 평가를 대신하지는 못한다.
  • [경계] 수치 사이의 직접적인 열거·개수 충돌은 발견되지 않았다. 그러나 수치는 화자의 보고이며 독립 검증 자료가 없고, 실제 평가 절차·기준·결과도 제시되지 않았다. 화자는 에이전트임을 공개하지 않는다고 밝혔지만 그 영향이나 수신자 동의 문제는 다루지 않았다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 고정 설명 순서와 학습자별 후속 질문을 나누는 구조가 워크플로와 에이전트의 구분과 닮았다.
  • 통찰: 같은 내용을 전달했는지가 아니라, 학습자가 보지 않고 원인과 차이를 설명하는지 평가해야 한다.
  • 질문/행동: 반복 안내는 고정하고, 오답에 따른 후속 질문만 유연하게 바꿀 수 있는가?

사업가 · 구조적 비유

  • 관련성: 화자는 반복 인력 작업을 자동화하고 이슈별 컨테이너로 병렬 처리했다고 주장한다.
  • 통찰: APOM에 적용한다면 실제 운영 상태가 아니라, 반복 업무와 예외 업무를 분리해 볼 수 있다는 검증 전 가설이다.
  • 질문/행동: 오류가 고객·재고·정산에 영향을 주지 않는 읽기 전용 업무부터 시험할 수 있는가?

마케터 · 직접 전이

  • 관련성: 연구자에게 제안한 명확한 안내와 실제 이전 사례가 아웃리치의 주장과 증거로 사용됐다.
  • 통찰: “자동화했다”보다 어떤 문제가 해결됐고 상대가 무엇을 했는지 보여 주는 장면이 설득력이 높다. 단, 화자의 사례는 독립 검증된 성과 자료가 아니다.
  • 질문/행동: 카피에서 처리량 주장과 검증 가능한 결과 증거를 분리해 표시할 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 단일 CLI, 스킬, 샌드박스, 병렬 컨테이너, 추적이라는 구체적인 설계 단서가 있다.
  • 통찰: 모델 이름보다 업무의 변동성, 도구 권한, 격리, 비용과 지연 시간, 결과 평가를 함께 봐야 한다.
  • 질문/행동: 실제 쓰기 권한을 주기 전에 샌드박스에서 무수정 승인률을 측정할 수 있는가?

# 섹션 요지
1 문제와 수동 업무 외부 저장소의 연구 산출물을 Hub로 옮기고 문서화하는 일이 반복됐다.
2 초기 워크플로 고정 경로와 야간 예약 실행으로 논문 확인과 이슈 생성을 자동화했다.
3 후속 처리 에이전트 CLI·스킬·샌드박스를 주고 이슈별 작업을 병렬 처리했다.
4 화자가 제시한 결과 이전 사례와 반응 수치를 성과로 소개했다.
5 평가와 다른 프로젝트 평가는 권고했지만 절차는 제시하지 않았고, DailyPapers와 Papers With Code 작업을 소개했다.

1. 연구 산출물의 발견 문제

화자는 자신을 벨기에 출신 Niels라고 소개하며 KU Leuven에서 공부했고 Hugging Face에서 머신러닝 엔지니어로 5년간 일했다고 말했다. Community Science 팀은 Google Drive, GitHub Releases, Dropbox, Zenodo 등 외부 서비스에 놓인 모델 가중치와 데이터셋을 Hugging Face Hub로 옮기도록 연구자에게 제안한다.

Hub의 논문 페이지는 arXiv 논문과 모델·데이터셋을 연결하고 메타데이터 태그, 모델 카드, 데이터셋 카드로 검색과 문서화를 돕는다는 것이 화자의 설명이다. 수동 업무는 저장소 찾기, README 확인, 기존 업로드 여부와 문서 확인, GitHub 이슈나 PR 작성, 저자 후속 연락으로 이어졌다.

2. 결정론적 야간 워크플로

화자는 arXiv에서 매일 수백 편의 논문이 나온다고 말하며 수동 작업은 확장하기 어렵다고 판단했다. 2024년에는 단일 LLM API부터 단순하게 시작하고 불필요한 에이전트 프레임워크를 피하라는 Anthropic의 조언에 따라 단계가 정해진 워크플로를 만들었다.

이 워크플로는 Python 스크립트와 LLM API를 사용하고 GitHub Actions의 cron으로 매일 밤 실행됐다. 화자는 이 과정에서 매일 밤 수백 개의 GitHub 이슈가 생성된다고 말했다. Langfuse로 입력·출력, 프롬프트, 비용, 지연 시간을 추적했다고 설명했지만 결과 품질 평가 방식은 제시하지 않았다.

3. 후속 답변을 처리하는 에이전트

연구자의 답변은 경우마다 달라 고정 경로로 처리하기 어려웠다. 화자는 몇 달 전부터 Claude Agent SDK를 사용한 자율 에이전트 루프로 후속 대응을 자동화했다고 말했다.

구성요소는 다음과 같다.

  • Claude Agent SDK
  • Hugging Face CLI와 이를 사용하는 단일 스킬
  • Bash 도구
  • Modal의 이슈별 격리 컨테이너
  • 결과를 게시하는 Slack 연결
  • 처음에는 Claude 모델, 발표 시점의 해당 주부터는 Hugging Face Inference Providers를 통한 GLM 5.2

화자는 Cursor 발표에서 12,000줄의 사용자 정의 코드를 200줄짜리 스킬로 바꾼 사례를 들며, 자신의 경우도 수천 줄의 코드를 단순한 에이전트로 줄일 수 있다고 주장했다. Modal에서는 GitHub 이슈 하나마다 컨테이너와 에이전트 루프 하나를 실행해 병렬 처리한다고 설명했다.

다만 후속 처리는 보통 자동 예약되지 않는다. 화자가 Cursor에서 process_unprocessed_modal 스킬을 직접 호출하면 Composer 2.5가 다른 에이전트들을 실행하고, 몇 분 뒤 결과가 Slack에 나타난다고 설명했다.

4. 화자가 제시한 반응과 성과

화자는 누적 수천 개의 이슈 가운데 부정적인 댓글은 두 개뿐이었다고 말했다. 한 사례에서는 “이 slop을 닫아 달라”는 반응을 받았지만, 대체로 연구자들이 제안을 수용했다고 주장했다.

그 밖에 다음 사례를 소개했다.

  • Apple 연구자와 Google DeepMind를 대상으로 한 에이전트의 아웃리치
  • 400GB 데이터셋을 게시하려는 연구자의 문의
  • PaddleOCR가 OCR 모델을 Hugging Face로 이전한 사례
  • 논문과 README를 바탕으로 모델 카드 템플릿을 채운 사례
  • ‘Tiny Recursive Models’ 관련 이슈가 60개가 넘는 추천을 받은 사례

화자는 자신의 에이전트가 작성했다는 사실을 수신자에게 공개하지 않는다고 말했다. 수동으로 쓰던 것과 같은 내용을 게시하며, 봇이라고 알리면 이슈를 바로 닫을 수 있다고 보는 것이 이유였다. 이 판단에 대한 수신자 동의, 플랫폼 정책, 신뢰 영향은 발표에서 평가되지 않았다.

5. 모델 주장, 평가 권고와 다른 자동화

화자는 GLM 5.2가 CursorBench에서 좋은 성능을 보였고 Post-Train Bench에서는 Opus 4.8보다 높은 성능과 낮은 비용을 보였다고 주장했다. 또한 GLM 5.2와 DeepSeek V4 같은 오픈 모델이 폐쇄형 모델을 대체할 정도로 좋아지고 있다고 결론 내렸다. 이 비교는 발표 안에서 독립 검증되지 않았으며 시점과 업무에 따라 달라질 수 있다.

에이전트가 인터넷에 낮은 품질의 글을 대량 게시하는 문제를 피하려면 평가가 필요하다며 Hamel Husain의 ‘LLM Evals FAQ’를 추천했다. 그러나 자신이 적용한 평가 데이터셋, 판정 기준, 실패율, 배포 기준은 공개하지 않았다.

다른 프로젝트로는 다음을 소개했다.

  • DailyPapers: 4시간마다 또는 새 산출물이 공개될 때 연구 내용을 X에 게시하며, 화자에 따르면 별도 개입 없이 팔로워 9만 명을 넘었다.
  • 게시물 시각 자료 선택: Gemini를 사용하며, NVIDIA의 GLM 5.2 최적화 버전 관련 게시물이 2,000개가 넘는 좋아요를 받았다고 말했다.
  • Papers With Code 부활: paperswithcode.co에서 벤치마크와 기술 용어를 제공하는 작업을 현재 진행 중이라고 밝혔다.

대조한 충돌과 불확실성

  • 수백 개의 야간 이슈, 누적 수천 개의 이슈, 부정적 댓글 두 개, 400GB, 60개 초과 추천, 팔로워 9만 명, 좋아요 2,000개 초과 사이에 직접적인 수치·열거 충돌은 발견되지 않았다.
  • “완전 자율 에이전트”라는 표현과 “보통 화자가 스킬을 수동 호출한다”는 설명은 자동화 범위를 구분해야 한다. 호출 이후의 실행은 자율적일 수 있지만 전체 시작 과정은 무인이라고 볼 수 없다.
  • 전사에서 화자는 자신을 Niels라고만 소개한다. META 설명과 SNS 링크는 Niels Rogge를 가리키지만, provenance.note는 원작자를 Hugging Face로 추정했으며 원본 영상 링크도 확인되지 않았다고 명시한다. 따라서 원작자는 확정하지 않았다.
  • 발표 시점의 “이번 주”, “작년 11월”, “몇 달 전”은 정확한 행사일이 없어 절대 날짜로 바꾸지 않았다.
  • 평가 필요성은 권고됐지만 실제 평가 절차와 결과는 확인되지 않았다.

전체 전사 펼치기

좋습니다. 안녕하세요, 여러분. 와 주셔서 감사합니다. 오늘은 에이전트(agents)를 사용해 Hugging Face에서 제 업무를 어떻게 자동화했는지 이야기하겠습니다.

간단히 소개하자면, 저는 맥주, 감자튀김, 초콜릿의 나라 벨기에 출신인 그냥 Niels입니다. KU Leuven에서 공부했고, 이제 5년째 Hugging Face에서 머신러닝 엔지니어로 일하고 있습니다.

오늘은 제가 속한 Hugging Face의 Community Science 팀에 대해 이야기하겠습니다. 그다음 Community Science 팀의 업무 중 상당 부분을 어떻게 자동화했는지 말씀드리겠습니다. 마지막으로 Hugging Face에서 진행하는 다른 노력들도 몇 가지 다루겠습니다.

먼저 Hugging Face의 Community Science 팀부터 시작하겠습니다. 기본적으로 이 일은 GitHub에서 유행하는 연구를 보면서 시작되었습니다. 새로운 흥미로운 연구를 발견할 때마다, 안타깝게도 가중치(weights)가 Hugging Face에 공개되어 있지 않은 경우가 많았습니다.

연구자들은 Google Drive나 GitHub 릴리스를 사용합니다. Dropbox, Zenodo 또는 다른 서버에 산출물을 올리기도 하는데, 이는 연구의 발견 가능성(discoverability)을 떨어뜨립니다. 사람들이 쉽게 볼 수도, 찾을 수도 없습니다.

제가 GitHub 이슈를 열어 “사실 Hugging Face에 가중치를 무료로 올릴 수 있습니다”라고 말하면, 대부분의 경우 사람들은 “Google Drive에서 Hugging Face로 가중치를 옮기는 것이 정말 합리적이네요”라고 답했습니다.

Community Science 팀은 Google Drive에서 Hub로 옮기는 팀이라고도 설명할 수 있습니다. 왜냐하면 Hugging Face에는 논문 페이지가 있고, 모든 논문은 arXiv에서 가져오기 때문입니다. 오른쪽에는 연결된 모델이나 데이터셋처럼 관련 산출물을 나열할 수 있어서, 사람들이 논문을 쉽게 재현하거나 모델과 데이터셋을 찾을 수 있습니다.

이는 연구의 발견 가능성을 높여 줍니다. 앱에 메타데이터 태그(metadata tags)나 필터가 있기 때문입니다. 예를 들어 관심이 있다면 깊이 추정(depth estimation) 모델이나 LLM을 쉽게 찾을 수 있습니다. 언어별로 찾을 수도 있고, 호환되는 라이브러리로 태그를 지정할 수도 있습니다. 이런 방식으로 연구의 발견 가능성이 향상됩니다.

다음은 Hugging Face의 모든 모델이나 데이터셋에 추가할 수 있는 메타데이터 태그입니다.

우리가 발견한 주요 문제는 많은 연구자가 연구 결과를 공개하기 위해 서드파티 서비스를 사용한다는 것이었습니다. Hugging Face 플랫폼은 사람들이 머신러닝 산출물을 찾을 수 있는 중앙화된 장소입니다. 또한 모델 카드(model card)나 데이터셋 카드(dataset card)를 추가할 수 있기 때문에 문서화도 개선됩니다.

Hugging Face에는 파일을 쉽게 업로드하거나 다운로드할 수 있는 도구도 있습니다. 연구자들이 자신의 연구를 알리는 데 도움이 될 수도 있습니다. 기본적으로 연구자와 연구를 활용하는 다른 사람 모두에게 윈윈(win-win)입니다.

다음은 제가 열곤 했던 전형적인 GitHub 이슈입니다. 항상 같은 템플릿을 사용했습니다. “이 체크포인트를 Hugging Face에 공개해 주실 수 있을까요? 이 데이터셋을 Hugging Face에 공개해 주실 수 있을까요?”라고 요청했습니다.

또한 Hugging Face에서 PR, 즉 풀 리퀘스트(pull request)를 열어 데이터셋 카드나 모델 카드를 추가하고 해당 산출물의 문서를 개선하기도 했습니다.

하지만 문제가 있습니다. 제가 매일 이런 GitHub 이슈나 풀 리퀘스트를 모두 여는 것은 확장 가능하지 않습니다. 특히 최근 AI 붐으로 인해 매일 수백 편의 연구 논문이 arXiv에 올라오기 때문입니다. 예를 들어 주요 AI 학회에서는 엄청난 수의 논문이 발표되고 있습니다.

이 작업을 자동화할 수 있을까요? 에이전트를 사용해 Community Science 팀을 확장할 수 있을까요? 이것이 제 발표의 두 번째 부분입니다. 이 작업을 엄청난 수의 연구 논문으로 확장하려면 어떻게 해야 할까요?

아이디어는 꽤 간단합니다. 연구의 일부로 모델이나 데이터셋을 공개하는 모든 연구자에게 연락하는 일을 도와줄 AI 에이전트를 만들고, 그 연락을 자동화하는 것입니다.

다음은 제가 따르던 전형적인 업무 흐름입니다. 연구 논문을 발견하면 먼저 해당 논문의 GitHub URL이 있는지, 있다면 찾아보았습니다. 그런 다음 GitHub 저장소의 README를 읽고, Hugging Face에서 공유할 만한 새롭고 흥미로운 내용이 있는지 확인했습니다.

이미 Hugging Face에 올라와 있는 경우도 있습니다. 그럴 때는 모델 카드나 데이터셋 카드가 제대로 존재하는지, 메타데이터 태그가 있는지 확인했습니다. 없다면 풀 리퀘스트를 열기도 했습니다.

그렇지 않고 산출물이 아직 Hugging Face에 없다면 GitHub 이슈를 열었습니다. 마지막으로 저자에게도 후속 연락을 했습니다. 이것이 에이전트로 자동화해야 했던 업무 흐름입니다.

이 문제를 해결하는 방법은 여러 가지가 있습니다. 워크플로(workflow)를 사용할 수도 있습니다. 이 그림들은 Anthropic의 “Building Effective Agents”라는 블로그 게시물에서 가져온 것인데, 정말 좋은 글입니다.

왼쪽에는 더 결정론적인 워크플로가 있습니다. 기본적으로 미리 정의된 경로나 파이프라인의 각 단계에서 LLM API를 사용합니다. 더 예측 가능하고 결정론적이며, 작동 방식을 더 많이 제어할 수 있습니다. 물론 유연성은 떨어집니다.

반면 완전한 자율 에이전트(fully fledged autonomous agent)를 사용할 수도 있습니다. 이는 작업이 끝날 때까지 도구를 호출하는 루프 안의 LLM입니다. 더 유연하지만 예측 가능성은 떨어집니다.

반드시 양자택일일 필요는 없습니다. 한쪽에는 워크플로가 있고 다른 쪽에는 완전한 자율 에이전트가 있을 수 있지만, 사용 사례에 맞게 이런 유형들을 섞어 사용할 수도 있습니다.

제 경우에는 상당히 결정론적인 워크플로를 선택했습니다. 왜냐하면 제가 이 작업을 만들던 2024년에 Anthropic이 “Building Effective Agents”라는 블로그 글을 썼고, 정말 필요하지 않다면 에이전트를 만들지 말라고 했기 때문입니다. 단순하게 시작하고, 단일 LLM API로 시작하며, 프레임워크는 피하라는 조언이었습니다.

저는 이것들이 훌륭한 조언이라고 생각합니다. 당시 저는 이 연락 업무에 사용하던 워크플로를 그대로 재현하는 워크플로를 만들기 시작했습니다.

이것이 전체 파이프라인입니다. Excalidraw MCP 서버와 Cursor를 사용해 만들었습니다. 코드를 시각화하는 데 꽤 좋습니다. 세부 사항까지 들어가지는 않겠지만, 기본적으로 제가 연락 업무에 사용하던 워크플로를 재현합니다.

각 단계에 LLM API를 사용하고, 프레임워크나 에이전트 프레임워크는 사용하지 않습니다. 덕분에 상당히 결정론적으로 작동했고, 작동 방식을 많이 제어할 수 있었습니다.

배포 측면에서 이 워크플로는 간단한 크론 작업(cron job)을 사용합니다. 크론은 정기적으로 실행되는 무언가입니다. 제 경우에는 매일 밤 한 번 실행합니다. 제가 자는 동안 이 에이전트가—기술적으로는 LLM API를 사용하는 Python 스크립트인 크론 작업일 뿐이지만—수백 편의 arXiv 논문을 모두 읽습니다. 그리고 Hugging Face에서 GitHub 이슈나 풀 리퀘스트를 열 수도 있습니다.

이를 위해 GitHub Actions를 사용합니다. “Free Cron Jobs with GitHub Actions”라는 아주 좋은 블로그 글을 발견했습니다. 간단한 크론 작업을 설정하고 싶다면 아마 가장 좋은 시작점일 것입니다. GitHub는 간단한 크론 작업을 시작하려는 사람에게 꽤 넉넉한 요금제를 제공하기 때문입니다. 또한 UI에서 이 모든 크론 작업을 관리하기가 매우 쉽습니다.

매일 밤 수백 개의 GitHub 이슈가 생성됩니다.

트레이싱(tracing)에는 Langfuse를 사용합니다. Langfuse는 정말 훌륭합니다. 저는 주로 트레이싱과 관측 가능성(observability)을 위해 사용합니다. LLM이 무엇을 하는지, 입력과 출력이 무엇인지, 프롬프트가 무엇인지, 비용이 얼마나 드는지, 지연 시간은 어떤지 등을 확인할 수 있습니다. 적극 추천합니다.

에이전트가 매일 밤 너무 많은 GitHub 이슈를 열다 보니, 사람들이 해당 GitHub 이슈에 답변하면서 읽지 않은 GitHub 알림이 엄청나게 쌓입니다. 그 이슈에 모두 답변하는 것은 매우 많은 작업입니다. 일종의 우편함을 처리하는 것과 같습니다.

GitHub 이슈에 대한 후속 연락도 자동화할 수 있지 않을까 생각할 수 있습니다. 처음에는 GitHub 이슈 생성은 에이전트가 했지만, 후속 연락은 여전히 제가 직접 처리했습니다.

몇 달 전에는 해당 GitHub 이슈의 후속 연락도 자동화했습니다. 다시 말해, 더 결정론적인 워크플로를 사용해야 할지, 아니면 도구와 스킬을 사용해 실행되는 루프 안의 LLM인 완전한 자율 에이전트를 사용해야 할지 고민할 수 있습니다.

여기서는 완전한 자율 에이전트를 선택했습니다. 유연하고 예측 가능성은 조금 떨어지지만, 꽤 잘 작동합니다.

이 접근 방식을 선택한 이유는 작년 11월 뉴욕에서 열린 AI Engineer에서 Anthropic이 Claude Agent SDK에 관한 꽤 좋은 워크숍을 진행했기 때문입니다. 그들은 에이전트가 워크플로보다 나을 수도 있다고 말했습니다. 서로 모순되는 것처럼 보이기도 했지만, 모델이 매우 좋아졌기 때문에 이제는 워크플로 대신 완전한 자율 에이전트로 작업을 시작할 수 있다고도 했습니다.

그래서 이 접근 방식을 택했고, 이 사용 사례에는 Claude Agent SDK를 사용하고 있습니다.

AI Engineer에서 Cursor가 진행한 또 다른 꽤 좋은 발표도 있었습니다. 몇 달 전 런던에서 열린 유럽 버전 행사였습니다. Cursor는 12,000줄의 커스텀 코드로 구성된 상당히 정교한 워크플로를 아주 단순한 200줄짜리 스킬로 대체한 방법을 이야기했습니다.

제 경우도 매우 비슷합니다. 모델이 매우 좋아졌기 때문에 수천 줄에 달하는 많은 커스텀 코드를 간단한 에이전트로 대체할 수 있습니다. CLI를 도구로 사용하고 스킬 하나를 추가하면 그게 전부일 수도 있습니다.

아키텍처는 대략 다음과 같습니다. 에이전트를 만들기 위한 꽤 좋은 Python SDK인 Claude Agent SDK만 사용합니다.

처음에는 Claude 모델을 사용했지만, 이번 주부터는 Hugging Face Inference Providers를 통해 GLM 5.2 모델을 사용하고 있습니다. Hugging Face는 Together AI, Fireworks, Cerebras 등 여러 추론 제공업체(inference providers)를 감싸는 서비스를 제공합니다. 많은 오픈 모델을 통합된 방식으로 사용할 수 있습니다. OpenAI 호환 또는 Anthropic 호환 방식입니다.

이 에이전트는 Modal에 배포합니다. Modal도 오늘 이 자리에 와 있습니다. 에이전트는 주로 터미널을 통해 Bash를 도구로 사용해 Hugging Face 명령을 실행합니다. Hugging Face CLI를 상당히 많이 사용하기 때문입니다. 여기에 Hugging Face CLI 스킬을 결합하는데, 사실 에이전트에 필요한 것은 그것뿐입니다.

후속 연락으로 GitHub에 댓글을 달 수도 있고, Slack에도 게시합니다. 최종 결과를 우리 Hugging Face Slack 채널에서 확인하고 싶기 때문입니다.

최근에는 GLM 5.2를 둘러싼 과대광고(hype)도 많습니다. 예를 들어 Cursor는 자체 CursorBench에서 훌륭한 성능을 보였고, Post-Train Bench는 GLM 5.2가 Opus 4.8을 실제로 능가하면서도 더 저렴한 또 다른 벤치마크입니다. 특히 제가 Hugging Face에서 일하고 있다는 점을 고려하면 GLM 5.2를 사용하지 않을 이유가 없습니다.

배포에는 앞서 말씀드렸듯이 Modal을 사용합니다. 에이전트를 배포하고 싶다면 Modal은 꽤 훌륭합니다. 제 경우에는 배치 처리(batch-processing) 기능을 사용하고 있습니다. 이 기능을 사용하면 엄청난 수의 컨테이너를 병렬로 실행할 수 있습니다. 각 컨테이너는 기본적으로 하나의 GitHub 이슈를 처리하는 하나의 에이전트 루프입니다.

사용하기가 매우 쉽고 시작 시간도 꽤 빠릅니다. 밤새 실행하는 것처럼 백그라운드에서 작동하는 에이전트를 구축한다면 확실히 추천합니다.

제가 이를 호출하는 방식은, 기술적으로는 Modal에서 크론 작업(cron job)으로 배포할 수도 있습니다. Modal은 이를 지원합니다. 하지만 보통은 여전히 GitHub 이슈에 대한 후속 작업을 스킬(skill)로 호출해 수동으로 처리합니다.

Cursor에서 이를 위한 스킬을 만들었습니다. 이름은 process_unprocessed_modal입니다.

그러면 에이전트를 호출하게 되는데, 이 경우에는 제가 Cursor에서 주로 사용하는 에이전트인 Composer 2.5를 호출합니다. 이 에이전트가 다시 다른 모든 에이전트를 호출합니다. 이것이 사람들이 이야기하는 루프입니다.

마지막으로 모든 결과를 저희 Slack 채널에 게시합니다. 이것이 게시하는 내용입니다. 기본적으로 Hugging Face 논문을 아주 많이 게시합니다. 사람들이 Hugging Face에 공개할 수 있는 연구 논문들입니다. 누군가 모델 카드나 데이터셋 카드에서 논문을 언급할 때마다 Hub에 색인합니다. 그런 다음 GitHub를 통해 진행한 홍보 활동을 바탕으로 사람들이 업로드한 모든 산출물을 게시합니다.

저는 여전히 이 작업을 수동으로 합니다. 스킬을 호출하면 몇 분 후 이런 메시지가 Slack 채널에 나타납니다. 솔직히 말해 사람들이 에이전트와 상호작용하는 모습을 보는 것이 꽤 재미있기 때문에, 재미있는 결과도 몇 가지 포함했습니다.

이게 에이전트라는 사실은 밝히지 않습니다. 왜냐하면 사람들이 봇이라는 것을 알면 이슈를 빠르게 닫을 수도 있다고 생각하기 때문입니다. 제가 이전에 수동으로 게시하던 것과 정확히 같은 내용을 게시하므로, 이를 공개할 이유가 없다고 봅니다.

이런 답변을 볼 수 있습니다. “안녕하세요, Niels. 제안과 명확한 안내를 정말 감사합니다.” 또 사람들이 제 에이전트에 답하기 위해 에이전트를 사용하는 경우도 자주 봅니다. 요즘 인터넷이란 그런 곳이죠.

사람들은 자신들의 모든 산출물을 Hugging Face에 공개하고 있습니다. Hugging Face에서 생성된 수천 개의 이슈 중 지금까지 부정적인 댓글은 단 두 개뿐이었습니다. 한 사람은 “이 슬롭(slop)을 닫아 주세요”라고 말하고 이슈를 닫았습니다. 하지만 대부분의 사람들은 이렇게 말합니다. “사실 내 가중치나 데이터셋을 Hugging Face에 공개하는 게 완전히 말이 되네요. 왜 이런 생각을 못 했을까요?” 그러니 서로에게 이득인 셈입니다.

저는 Slack 채널에 재미있는 결과를 자주 게시합니다. 예를 들어 한 번은 Apple의 한 연구자가 저에게 DM을 보내 “당신이 저에게 연락한 것을 봤습니다”라고 말했습니다. 엄밀히 말하면 Apple 논문의 산출물을 Hugging Face에 공개하자는 내용의 GitHub 이슈를 게시한 것은 제 에이전트였습니다. 또 다른 사례에서는 Google DeepMind에 연락해 수학 데이터셋을 공개하도록 했습니다.

많은 경우, 오른쪽에 있는 것과 같은 이메일을 받습니다. Hugging Face에 400기가바이트짜리 데이터셋을 공개하고 싶다는 사람들의 이메일입니다. 하지만 이것 역시 제 에이전트가 GitHub 이슈를 연 것뿐이었습니다.

이것도 재미있는 결과입니다. 중국 회사인 PaddleOCR은 저를 대신해 이슈를 생성한 에이전트들의 홍보 활동을 바탕으로 모든 OCR 모델을 Hugging Face로 이전했습니다. 꽤 좋은 일이죠.

또 다른 재미있는 결과는 에이전트가 Hugging Face의 기본 모델 카드 템플릿을 완성하는 경우입니다. 역시 Hugging Face에서 일하는 Margaret Mitchell은 “Model Cards for Model Reporting”이라는 유명한 논문의 공동 저자이며, 이 논문은 모델을 제대로 문서화할 것을 장려합니다. 저희는 이 템플릿을 제공합니다. 왼쪽의 Git diff에서 볼 수 있는 템플릿인데, 에이전트는 논문의 GitHub README와 PDF 자체 등에서 찾은 내용을 바탕으로 이를 완성합니다.

이 경우에는 모델 카드에 저를 포함했다는 점도 꽤 재미있습니다. “모델 카드 작성자: Hugging Face Community Science 팀의 일원인 Niels”라고 적었습니다. 제가 그렇게 하라고 프롬프트를 작성한 적은 없지만, 보는 재미가 있었습니다.

사람들은 또 이렇게 답합니다. “제 실수를 고치는 데 도움을 주셔서 감사합니다.” 이 모든 작업을 에이전트가 수행합니다.

에이전트가 생성한 GitHub 이슈 중 가장 인기 있었던 것은 아마 “Tiny Recursive Models” 논문에 대한 이슈였을 것입니다. Hugging Face와 Twitter 양쪽에서 트렌딩하는 것을 보셨을 수도 있습니다. 60명이 넘는 사람들이 이슈에 추천(upvote)했으며, 그 결과 모델이 Hugging Face에 공개되었습니다.

이 역시 서로에게 이득입니다. 연구자는 Hugging Face에서 자신의 연구를 더 쉽게 발견할 수 있게 되어 이득이고, 그 연구를 기반으로 무언가를 만들고 활용하려는 사람들에게도 더 좋습니다.

사람들이 에이전트와 상호작용한 좋은 결과를 보여줄 수 있는 GitHub 이슈가 수백 개 있습니다.

슬롭을 어떻게 피할지도 궁금하실 수 있습니다. “잠깐, 에이전트가 인터넷 전체에 GitHub 이슈를 도배하고 있잖아. 정말 이렇게 해도 되는 건가?”라고 생각할 수도 있습니다. 다시 말씀드리지만, 이미 서로에게 이득이라는 점을 설명했습니다.

에이전트가 슬롭을 게시하는 것을 막고 싶다면 Hamel Husain의 “LLM Evals FAQ”라는 블로그 글을 강력히 추천합니다. LLM 평가와 관련해서는 그가 최고의 전문가라고 생각합니다. 유료 강좌도 운영하지만, 이 블로그 글을 포함해 많은 자료를 온라인에 무료로 공개하고 있습니다. 에이전트 평가에 대해 더 배우고 싶다면 꼭 읽어보시기를 강력히 추천합니다.

제 결론은 오픈 모델이 정말 빠르게 좋아지고 있다는 것입니다. 이제 GLM 5.2, DeepSeek V4 등이 있으므로 폐쇄형 모델을 오픈 모델로 대체할 수 있습니다.

제 사용 사례에서는 에이전트가 워크플로보다 실제로 더 낫다고 생각합니다. 에이전트에는 단 하나의 CLI, 즉 Hugging Face CLI, 단 하나의 스킬, 즉 Hugging Face CLI 스킬, 그리고 샌드박스만 필요합니다. 작업을 수행하는 데 필요한 것은 그게 전부입니다.

마지막으로 평가를 잊지 마세요.

Community Science 팀의 일환으로 저희가 진행하는 다른 작업도 간단히 소개할 수 있습니다. DailyPapers라는 X 계정을 만들었는데, 내부적으로는 제 에이전트와 정확히 같은 워크플로를 사용해 흥미로운 연구 논문을 X에 게시합니다. 최근에는 제 개입 없이 팔로워 90,000명을 돌파했습니다. 저는 이를 배포했을 뿐이고, 이후 4시간마다, 또는 누군가 Hugging Face에 멋진 것을 공개할 때마다 흥미로운 연구 논문과 Hugging Face의 산출물을 게시합니다.

각 트윗에 포함할 가장 좋은 시각 자료를 결정하는 데 Gemini를 사용합니다. 예를 들어 최근에는 NVIDIA가 GLM 5.2의 최적화 버전을 공개했다는 트윗이 2,000개가 넘는 ‘좋아요’를 받았습니다. 정말 보기 좋은 일이죠.

현재 제가 진행 중인 마지막 작업은 한때 존재했다가 Meta에 인수된 후 안타깝게 사라진 웹사이트 Papers With Code를 부활시키는 것입니다. 연구와 최신 성능(state-of-the-art) 결과에 더 쉽게 접근할 수 있도록 되살리려 하고 있습니다.

현재는 paperswithcode.co에서 운영되고 있습니다. 예를 들어 OCR 모델에 대한 벤치마크를 그곳에서 찾을 수 있습니다. OCR 벤치마크는 인기 있는 벤치마크 분야입니다. 또한 사람들이 미드 트레이닝(mid-training), 온폴리시 증류(on-policy distillation) 같은 기술 용어를 배울 수 있도록 교육 자료로도 만들고 있습니다.

제 발표는 여기까지입니다. 무언가를 배우셨기를 바랍니다. 모두 들어주셔서 감사합니다.
