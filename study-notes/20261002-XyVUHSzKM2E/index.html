큰 그림: 제품뿐 아니라 제품을 만드는 시스템을 만든다

이 발표에서 Zach Lloyd가 말하는 소프트웨어 공장은 개발자를 없애는 물리적 공장이 아니다. 아이디어가 들어오면 AI 에이전트와 사람이 역할을 나누어 분류하고, 명세를 쓰고, 구현하고, 검토하고, 검증하고, 배포 후 결과까지 살펴보는 자동화 시스템이다.

핵심 변화는 “AI에게 코드 한 번 써 달라고 부탁하기”에서 끝나지 않는다. 반복되는 개발 절차 전체를 연결하고, 실패 결과를 다음 작업에 반영하는 것이 목표다. 따라서 엔지니어의 일도 코드 작성만이 아니라 어디를 자동화하고, 어디서 사람이 판단하며, 어떤 결과를 측정할지 설계하는 일로 넓어진다는 것이 화자의 주장이다.

읽는 법: 위에서 아래로 읽는다. 각 상자는 확정된 산업 통계가 아니라 발표자가 제시한 인과관계다. 마지막 목표는 코드 양 자체가 아니라 사용자가 쓸 수 있는 제품을 내보내는 것이다.

개발 도구의 다음 단계라는 주장

화자는 최근 개발 방식의 변화를 세 단계로 나눈다. 먼저 Cursor나 Copilot 같은 채팅·자동완성 도구가 있었고, 그다음 Claude Code나 Warp처럼 사람이 컴퓨터 앞에서 지시하는 대화형 에이전트가 나타났다. 그 뒤에는 여러 에이전트가 개발 절차를 더 많이 자동으로 수행하는 단계가 올 것이라고 예상한다.

읽는 법: 실선 상자는 화자가 설명한 기존·현재 방식이고, 점선 상자는 미래 예측이다. “6개월 또는 1년”은 화자도 속도를 예측하기 어렵다는 조건을 붙였다.

공장은 어떻게 한 바퀴 도는가

공장에 들어오는 재료는 코드가 아니라 아이디어와 문제다. 팀이나 사용자가 작업 추적기, Slack, Teams, 터미널, IDE, 모니터링 시스템 등에 요청과 오류를 남기면 분류 단계가 이를 받는다.

  1. 분류: 쉽고 뜻이 분명한 일은 바로 구현 대상으로 보낸다. 어렵거나 모호한 일은 명세 작성으로 보낸다.
  2. 명세: 제품이 반드시 지켜야 할 조건을 적은 제품 명세와, 코드 구조 및 기술적 접근을 적은 기술 명세를 만든다.
  3. 구현: 코딩 에이전트가 코드를 변경하고 차이 내역을 만든다.
  4. 검토: 에이전트가 먼저 코드를 살펴보고, 위험에 따라 사람이 참여한다.
  5. 검증: 테스트와 CI/CD를 실행한다. 화면이 있는 제품이라면 에이전트가 직접 사용해 보고 영상이나 스크린샷을 남길 수도 있다.
  6. 제품 판단과 출시: 사람이 결과물이 의도에 맞는지 확인한 뒤 출시한다.
  7. 모니터링: 충돌하는지, 실제로 사용되는지 관찰하고 결과를 다시 입력으로 보낸다.

읽는 법: 위에서 아래로 작업이 진행되고, 마지막 보라색 문장이 다시 첫 단계로 연결한다. 모든 단계가 완전 자동이라는 뜻은 아니다. 명세 검토, 위험한 코드 검토, 제품의 유용성 판단에는 사람이 들어간다.

공장 안에는 무엇이 필요한가

화자는 공장을 단순한 코딩 에이전트 하나로 보지 않는다. 높은 수준에서는 네 가지가 필요하다고 설명한다.

  • 여러 개발 단계를 움직이는 자동화
  • 에이전트가 프로젝트를 이해하도록 주는 맥락과 스킬
  • 막히거나 위험한 순간에 사람을 부르는 인간 개입 지점
  • 실패를 관찰하고 다음 실행을 바꾸는 자기 개선 기능

구조를 더 나누면, 요청을 받아들이는 여러 입력 통로 위에 작업을 배분하는 제어 영역이 있고, 실제 작업은 클라우드 샌드박스와 에이전트에서 일어난다. 아래에는 에이전트가 이전 작업을 기억하고 배울 수 있도록 하는 데이터 영역이 놓인다.

읽는 법: 위쪽은 일이 들어오는 곳, 가운데는 분배와 실행, 아래쪽은 경험을 남기는 곳이다. 이 그림은 발표자의 개념 구조이며 특정 제품의 검증된 표준 아키텍처를 뜻하지 않는다.

실패를 다음 실행의 개선 재료로 쓴다

화자가 말한 스킬 루프는 에이전트가 사용한 지침이나 작업 방법을 관찰하고 수정하는 반복 과정이다. 예를 들어 코드 검토 에이전트가 부정확한 의견을 남기고 시니어 엔지니어가 이를 바로잡았다면, 관찰 에이전트가 그 차이를 살펴 다음 코드 검토에 쓰일 스킬을 개선한다.

중요한 것은 “에이전트가 스스로 똑똑해진다”는 막연한 표현이 아니다. 어떤 행동이 실패했는지, 사람이 무엇을 고쳤는지, 다음 실행에서 무엇을 바꿀지를 기록해야 한다. 공장의 효율도 출시한 소프트웨어와 그 과정에 든 사람의 시간 및 토큰 비용을 함께 보며 개선해야 한다는 설명이다.

Warp의 공개 개발 사례와 인간의 자리

화자는 Warp가 약 5년 동안 비공개로 개발한 뒤 발표 시점 몇 달 전에 오픈소스로 전환했다고 말한다. 공개 이슈의 상태, 작업 중인 에이전트와 기여자를 보여주는 build.warp.dev를 초기 형태의 공개 공장으로 소개하며, 완벽하지는 않지만 작동하고 있다고 평가한다.

공개 개발에는 시끄러운 이슈, 품질이 낮은 변경 요청, 긴 코드 검토와 검증 부담이 생길 수 있다. Warp는 이런 부담을 관리하는 자동화가 준비되면서 공개 개발을 선택할 수 있었다는 것이 화자의 설명이다. 공개 개발은 생태계, 브랜드, 커뮤니티 형성에 도움이 될 수 있지만 성공을 보장하지는 않는다.

소프트웨어 제작과 복제가 쉬워질수록 좋은 제품만으로 사업 우위를 지키기 어렵다는 주장도 이어진다. 화자는 제품 밖의 우위로 유통, 생태계, 브랜드, 데이터, 자본을 든다. 발표 중 “먼저 코드를 특허 내라”는 말은 즉시 농담이라고 철회했으므로 실제 조언으로 읽으면 안 된다.

마지막으로 공장은 무엇을 만들지 스스로 결정해 주지 않는다. 사용자가 원하는 것이 무엇인지, 결과물이 유용한지, 자동화하면 안 되는 판단이 무엇인지는 여전히 인간의 제품 감각과 안목에 달려 있다는 것이 화자의 결론이다. 즉 엔지니어는 코드를 덜 직접 쓸 수 있지만, 공장을 조정하고 더 가치 있는 제품을 출시하는 책임은 줄어들지 않는다.

해석 경계

“모든 규모 있는 프로젝트가 공장을 갖게 된다”, “엔지니어가 코드를 덜 쓰고 더 많이 출시한다”는 문장은 Zach Lloyd의 전망이다. 발표에는 이를 독립적으로 입증하는 비교 데이터가 없다. Warp의 GitHub 별 6만 개 이상, 수백 명의 기여자, 활성 개발자 80만 명 이상이라는 수치도 발표자의 주장으로만 제공됐다.

여기까지만 이해하면 충분

  • 소프트웨어 공장은 아이디어부터 분류·명세·구현·검토·검증·출시·모니터링까지 연결하고, 결과를 다시 입력으로 돌려보내는 개발 시스템이다.
  • 에이전트가 모든 판단을 대신하는 것이 아니라, 반복 작업은 자동화하고 위험·모호함·제품 유용성 판단에는 사람을 배치한다.
  • 공장의 품질은 코드 생성량만이 아니라 출시 결과, 인간 시간, 토큰 비용, 실패 후 개선 여부로 평가해야 한다.
  • “모든 프로젝트가 이런 방식으로 바뀐다”는 결론은 검증된 사실이 아니라 화자의 미래 전망이다.

1. 자동화의 단위가 코드에서 개발 공정으로 커진다

1. 화자와 Warp 소개

Zach Lloyd는 자신을 전 Google 수석 엔지니어이자 Google Docs 제품군 엔지니어링을 이끌었던 사람으로 소개했다. 엔지니어 경력은 20년 이상이며, 최근 6개월 동안 직접 코드 한 줄을 쓰지 않았지만 계속 자주 출시하고 있다고 말했다.

그는 Warp의 창업자라고 밝혔다. Warp는 터미널에서 시작해 에이전트를 포함한 개발 환경으로 확장했으며, 발표 시점 몇 달 전에 오픈소스로 전환했다고 설명했다.

발표에서 제시된 Warp 관련 수치는 다음과 같다.

  • GitHub 별 6만 개 이상
  • 수백 명의 기여자
  • 활성 개발자 80만 명 이상

이 수치는 발표자의 자기보고이며 제공된 자료만으로 독립 검증할 수 없다.

2. 개발 방식의 변화

화자는 최근 몇 년간 개발 방식이 채팅과 AI 자동완성에서 대화형 에이전트로 이동했다고 설명했다. 발표 당시에는 사용자가 컴퓨터 앞에서 Claude Code나 Warp에 작업을 지시하는 방식이 중심이라고 보았다.

다음 6개월에서 1년 사이에는 자동화 비중이 커질 것으로 전망했지만, 변화 속도는 예측하기 어렵다고 조건을 붙였다.

현장 손들기 조사에서는 다음과 같이 표현했다.

  • 에이전트로 개발하는 사람: 100%
  • 여러 에이전트를 동시에 쓰는 사람: 거의 모두
  • 클라우드에서 에이전트를 실행하는 사람: 절반 미만이지만 상당수
  • 전체 개발 수명주기 자동화 시스템을 구축한 사람: 일부

참석자 수와 실제 집계값은 제공되지 않았다.

3. 소프트웨어 공장 루프

입력은 팀이나 사용자의 아이디어에서 시작한다. 작업 추적기, Slack, Teams, 터미널, IDE, 모니터링 시스템이 입력 통로가 될 수 있다.

분류 에이전트는 쉽고 명확한 이슈를 바로 구현으로 보내고, 어려운 이슈는 명세 단계로 보낸다. Warp 방식에서는 제품 명세와 기술 명세를 구분한다.

  • 제품 명세: 만들 제품이 지켜야 할 불변 조건
  • 기술 명세: 아키텍처와 코드의 형태

구현 에이전트는 클라우드 등에서 실행되어 코드 차이 내역을 만든다. 검토에서는 에이전트를 먼저 활용하고, 위험 관리 관점에서 인간을 언제 투입할지 정한다.

검증에는 CI/CD가 포함된다. 사용자 인터페이스가 있는 제품은 컴퓨터가 직접 결과물을 사용해 보고 영상이나 스크린샷을 만들 수도 있다고 설명했다. 배포 후에는 충돌 여부와 사용 여부를 관찰하고 이를 다시 공장의 입력으로 보낸다.

4. 공개 개발 전략

화자는 소프트웨어 제작 비용이 낮아지면 복제도 쉬워지므로 좋은 제품만으로 사업 가치를 지키기 어렵다고 주장했다. 제품 밖의 우위로 유통, 생태계, 브랜드, 데이터 장벽과 자본을 들었다.

“먼저 코드를 특허 내라”는 문장은 즉시 농담이라고 철회했다. 실제 권고는 공개적으로 만드는 방식을 검토하라는 것이었다.

Warp는 약 5년간 비공개로 개발한 뒤 공개 개발로 전환했다고 말했다. 공개 개발은 생태계·브랜드·커뮤니티에 도움이 될 수 있지만, 시끄러운 이슈와 품질이 낮은 변경 요청, 코드 검토와 검증 부담을 만든다. Warp는 이를 관리하는 자동화를 구축한 것이 전환의 계기가 됐다고 설명했다.

build.warp.dev는 이슈 상태, 작업 중인 에이전트와 기여자를 보여 주는 공개 공장 사례다. 화자는 이를 완벽하지 않지만 작동하는 초기 공장이라고 평가했다.

5. 공장 아키텍처

효과적인 공장에 필요한 요소로 다음 네 가지가 제시됐다.

  1. 자동화 집합
  2. 맥락과 스킬을 제공하는 방법
  3. 적절한 순간에 인간을 참여시키는 방법
  4. 자기 개선 능력

기술 구조는 입력 통로, 작업을 배분하는 제어 영역, 실제 작업이 일어나는 클라우드 샌드박스와 에이전트 실행 환경, 기억과 개선을 담당하는 데이터 영역으로 설명됐다.

화자는 간단한 형태는 직접 만들 수 있지만, 규모 있게 운영되는 기반시설을 만드는 일은 복잡하므로 대부분의 조직이 핵심 제품에 집중할 필요가 있다고 말했다. 동시에 특정 제품과 영역에 맞게 공장을 조정하는 작업은 여전히 중요한 엔지니어링 과제라고 설명했다.

6. 측정과 스킬 루프

공장 관점에서는 얼마나 많은 소프트웨어를 출시했는지와 함께 인간 시간과 토큰 시간이 얼마나 들었는지를 측정해야 한다.

스킬 루프에서는 에이전트가 스킬을 실행하고 관찰 에이전트가 적용 과정과 실패를 살핀다. 코드 검토 에이전트의 의견을 시니어 엔지니어가 수정했다면, 그 수정 사례를 다음 코드 검토 스킬 개선에 이용하는 예가 제시됐다.

이 과정이 실제로 어느 정도 성능을 높이는지 보여 주는 수치나 비교 실험은 발표에 포함되지 않았다.

7. 엔지니어의 역할과 질의응답

화자는 엔지니어가 제품만 만드는 것이 아니라 제품을 만드는 시스템도 구축하게 된다고 설명했다. 이를 공정 공학, 제조 또는 메타 엔지니어링에 비유했다.

직접 코드 쓰기에서 즐거움을 얻는 사람에게는 코드 작성 감소가 손실로 느껴질 수 있지만, 제품 출시에 가치를 두는 사람에게는 더 많은 결과를 낼 기회라는 것이 그의 견해다.

졸업을 앞둔 학생에게는 다음 역량을 강조했다.

  • 적응력
  • 비판적 사고
  • 빠르게 배우는 능력
  • 기반 시스템과 아키텍처 이해

제품 명세는 여러분이 구축하려는 제품 불변 조건(product invariants)을 설명합니다. 기술 명세는 아키텍처와 코드의 형태를 설명합니다.

그다음에는 구현 에이전트가 있습니다. 기본적으로 클라우드 어딘가에서 실행되는 코딩 에이전트입니다. 이 에이전트가 diff를 만듭니다. 이를 위해 온갖 종류의 코딩 에이전트를 사용할 수 있습니다.

그다음은 리뷰입니다. 여러 면에서 가장 고통스러운 부분이죠. 사람들이 에이전틱 슬롭(agentic slop)을 검토하는 데 조금 지쳐 있다고 생각합니다. 저는 먼저 에이전트가 코드 리뷰(code review)를 하게 할 것이고, 시간이 지나면 이는 위험 관리 작업이 됩니다. 언제 사람을 불러 코드 리뷰를 맡길 것인가?

여기에는 사람이 직접 할 수 있는 단계를 두고 싶을 겁니다.

검증 단계는 특정 유형의 앱에서 매우 중요합니다. 여기에는 컴퓨터 사용(computer use) 같은 것이 포함됩니다. UI를 만들고 있다면, 컴퓨터가 에이전트가 만든 코드를 실제로 사용하게 하면서 동영상과 스크린샷을 생성할 수 있습니다. 물론 CI/CD도 여전히 적용됩니다.

그다음은 모니터링입니다. 코드가 배포되었다고 해서 에이전트가 공장에서 멈추는 것은 아닙니다. 에이전트는 배포된 것을 관찰해야 합니다. 충돌하고 있는가? 사용되고 있는가?

이 모니터링 단계의 결과를 다시 공장 최상단으로 보내기 때문에, 계속 순환하게 됩니다.

이걸 직접 만들어 볼 수도 있습니다. 앞서 제 친구 Adam이 한 강연에 갔는데, Uber가 이것의 내부 버전을 구축했더군요. 꽤 멋졌습니다.

대부분의 조직에서는 현재 어떤 단계에 있는지가 정말 중요합니다. 이것의 단순한 버전은 쉽게 만들 수 있겠지만, 실제로 확장 가능한 무언가를 만들려면 아마 이 인프라를 구축하기보다는 자신의 제품에 집중해야 할 겁니다. 결국 원하게 되는 기능이 아주 많기 때문입니다.

직접 구축하든 구매하든, 결국 이런 형태의 무언가를 갖게 될 겁니다. 공장에 작업을 투입할 방법이 여러 가지 생깁니다. 여기 위쪽에 있는 부분이 그것입니다. 또 공장 현장 전체에 작업이 어떻게 분배되는지 결정하는 일종의 컨트롤 플레인(control plane)이 필요합니다.

실제로 작업이 수행되는 장소도 필요하며, 그것은 클라우드 샌드박스(cloud sandbox)가 될 겁니다. 어떤 에이전트를 실행할지 결정해야 합니다. 하네스(harness)는 무엇이고, 모델은 무엇인가? 마지막으로, 저는 이것이 정말 중요한 부분이라고 생각합니다. 공장 아래에 위치하는 일종의 데이터 플레인(data plane)을 구축하고 싶을 겁니다. 이를 통해 에이전트는 자신이 한 일을 기억하고, 배우며, 시간이 지나면서 개선할 수 있습니다.

공장은 단순히 제품이 아닙니다. 하나의 사고방식이기도 합니다. 이것이 처음에 말씀드린 논제로 다시 이어집니다. 측정하고 개선해야 합니다.

공장이라는 비유를 원하는 만큼 확장해도 되지만, 효율성을 생각해야 합니다. 즉, 얼마나 많은 소프트웨어를 배포했는지, 그리고 인간의 시간과 토큰 시간(token time) 측면에서 그 비용이 얼마나 들었는지 물어봐야 합니다. 이를 측정하고 시간이 지나면서 개선하고 싶을 겁니다.

이 과정의 핵심은 루프(loop)를 만드는 것입니다. 루프라는 말이 복잡하게 들리지만, 실제로는 그다지 복잡하지 않습니다. 루프는 기본적으로 에이전트가 자신이 무엇을 하고 있는지, 어디에서 실패하고 있는지를 관찰하면서 개선하도록 하는 방법입니다.

공장에 넣고 싶을 흔한 루프 유형으로 스킬 루프(skill loop)가 있습니다. 공장 에이전트가 스킬을 실행하고, 관찰자 에이전트(observer agent)가 그 스킬이 어떻게 적용되는지 살펴보며 문제를 찾고 스킬을 개선하도록 하는 것입니다.

예를 들어 코드 리뷰 에이전트가 댓글을 남기고, 팀의 시니어 엔지니어가 그 댓글을 수정한다면, 관찰자 에이전트가 그 과정을 살펴보고 다음 실행을 위해 코드 리뷰 에이전트를 개선하도록 하고 싶을 겁니다.

여러분께 남기고 싶은 생각이 하나 있습니다. 그렇다면 엔지니어는 어떻게 되는가? 이런 사고방식을 받아들여야 할 겁니다. 저는 우리 팀이 이런 사고방식을 갖도록 아주 열심히 노력하고 있는데, 항상 쉽지는 않습니다. 단순히 제품을 만드는 것이 아니라, 제품을 만드는 것을 만드는 겁니다. 이는 다릅니다. 프로세스 엔지니어링(process engineering)이나 제조에 더 가깝습니다.

“좋아, 어쩌면 별로 좋은 일이 아닐 수도 있겠네. 정말 그런가?”라고 생각할 수도 있습니다. 소프트웨어 엔지니어링에서 어떤 기쁨을 얻는지에 따라 다릅니다. 코드 작성에서 기쁨을 얻는다면, 여기 있는 소프트웨어 엔지니어 모두가 코드를 덜 작성하게 될 겁니다. 하지만 제품을 배포하는 데서 기쁨을 얻는다면, 지금보다 더 좋은 때는 없었습니다.

사실 이 지점에서 저는 기쁨을 느낍니다. 무언가를 만들고 배포하는 일을 좋아합니다. 그러니 여기 있는 모든 사람이 코딩은 덜 하겠지만, 더 많이 배포하게 될 겁니다. 이것이 하나의 트레이드오프(trade-off)가 될 것입니다.

공장 엔지니어처럼 접근한다면, 여전히 정말 멋진 엔지니어링 과제들이 있다는 것을 알 수 있을 겁니다. 거의 메타 엔지니어링(meta-engineering)이라고 생각할 수도 있습니다. 어떻게 하면 에이전트 시스템을 설계해 최상의 엔지니어링 시스템이 되게 할 수 있는가? 저는 이것이 해결하기에 매우 매력적이고 흥미로운 과제라고 생각합니다.

이상입니다. 관심 있는 분들을 위해 말씀드리면, 이 QR 코드의 링크를 따라가면 누구나 자신만의 공장 에이전트를 만들어 볼 수 있는 오픈 소스 GitHub 저장소를 마련해 두었습니다. 이 저장소는 Warp의 에이전트 플랫폼을 일부 사용하지만, 솔직히 말해 꼭 그것을 사용할 필요는 없습니다. 우리 제품을 홍보하려는 것이 아닙니다.

이를 통해 트리아지(triage)를 수행하는 에이전트나 사양서 작성(spec writing)을 수행하는 에이전트를 어떻게 설정하는지 잘 알 수 있을 겁니다. 공장과 함께 일한다는 이론에서 실제 적용으로 어떻게 나아갈 수 있을까요?
