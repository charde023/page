처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 12분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 작업량보다 먼저 신뢰를 생산한다

이 대화는 AI 에이전트가 많은 코드를 만들게 하는 요령보다, 사람이 모든 작업을 직접 지켜보지 않아도 되는 조건을 어떻게 만드는가를 다룬다. 여기서 PR은 코드를 기존 프로젝트에 합치기 위해 제출하는 변경 단위인 풀 리퀘스트(Pull Request)다.

화자 Lauren Tan은 지난달 많은 PR을 반영했다고 말하지만, 핵심은 에이전트 수 자체가 아니다. 에이전트가 변경한 결과를 직접 실행하고 확인할 수 있어야 하며, 반복해서 틀리는 일은 도구와 규칙으로 막아야 한다. 외부에서 들어오는 버그 신고와 요청도 에이전트가 가져올 수 있어야 한다. 마지막으로 사람이 모든 PR을 통과시키는 문지기가 되는 대신, 결과를 표본으로 살펴보고 반복되는 실패를 환경 개선으로 되돌려야 한다.

읽는 법: 위에서 아래로 읽는다. 각 단계는 앞 단계를 없애는 것이 아니라 보완한다. 좋은 지시만 있고 검증이 없으면 결과를 믿기 어렵고, 검증만 있고 환경이 복잡하면 에이전트마다 같은 준비 작업을 다시 하게 된다.

1. 신뢰는 기대가 아니라 검증에서 생긴다

화자는 초기에 에이전트 하나를 세세하게 지시하면서 자신이 병목이 되었다고 설명한다. 에이전트가 만든 결과를 사람이 대신 실행하고 화면을 확인하면, 사람은 에이전트와 실제 제품 사이를 중계하는 역할에 묶인다. 에이전트 수를 늘릴수록 이 중계 업무도 함께 증가한다.

이를 줄이는 방법이 검증(verification)이다. 쉬운 말로 하면 에이전트에게 자기 결과를 직접 보고 만져 볼 “눈과 손”을 주는 것이다. 에이전트가 코드를 실행하고, 화면을 조작하고, 추적 정보나 스냅샷을 살피고, 실패를 발견한 뒤 다시 고치게 한다. 검증 결과를 점수나 통과 기준으로 표현할 수 있다면, 에이전트는 기준에 가까워질 때까지 반복해서 개선할 수 있다. 화자는 이를 신뢰 사다리를 오르는 데 가장 중요한 기반으로 본다.

읽는 법: 가운데 상자를 위에서 아래로 읽는다. 기준에 미달하면 빨간 회귀선이 마지막 단계에서 맨 위의 에이전트가 변경 단계로 실제로 돌아간다. 기준을 충족한 경우에만 왼쪽 통과 경로를 따라 병합 후보가 된다. 이 그림은 개념 흐름이며 각 단계의 통과율을 나타내는 수치 그래프가 아니다.

화자는 자신의 검증 도구가 Playwright와 Chrome DevTools Protocol 등을 연결하는 CLI라고 설명한다. 중요한 점은 특정 도구 이름보다, 모든 에이전트가 검증 절차를 매번 새로 만드는 대신 같은 도구를 재사용한다는 데 있다. 다만 어떤 검증도 현실의 모든 실패를 잡는다고 볼 수는 없다.

2. 판단할 일과 기계적으로 처리할 일을 나눈다

모든 작업을 언어 모델에게 맡기는 것이 반드시 효율적인 것은 아니다. 화자는 일의 성격을 두 쪽으로 나눈다.

  • 여러 맥락을 합쳐 선택해야 하는 일은 에이전트의 판단에 맡긴다.
  • 같은 입력에 같은 방식으로 처리할 수 있는 일은 스크립트나 CLI로 고정한다.

예를 들어 코드를 한 형식에서 다른 형식으로 일괄 변경하는 작업은 매번 새로운 판단이 필요하지 않을 수 있다. 이런 작업은 코드 구조를 읽어 기계적으로 바꾸는 도구인 코드모드(codemod)나, 추상 구문 트리(AST)를 이용한 변환으로 옮길 수 있다고 화자는 말한다. 반대로 여러 버그가 사실 하나의 상위 문제에서 비롯되었는지 판단하는 일에는 맥락과 선택이 필요하다.

읽는 법: 모바일에서는 표 영역을 좌우로 이동해 읽는다. 왼쪽은 화자가 코드나 규칙으로 옮기려는 부분이고, 오른쪽은 에이전트의 판단 능력을 활용하려는 부분이다. 어느 한쪽이 항상 우월하다는 표가 아니라 역할 분담표다.

3. 좋은 코드 환경은 잘못된 선택지를 줄인다

화자는 에이전트가 반복해서 틀릴 때마다 지시문을 길게 추가하기보다, 그 실수가 일어나기 어려운 환경을 만들려고 한다. 예를 들면 정해진 디렉터리에만 기능을 두게 하고, 린트 규칙과 타입 검사로 허용되지 않는 패턴을 막으며, 공통 작업은 CLI로 제공하는 방식이다.

화자가 설명한 내부 프레임워크 Dune은 Electron 앱을 위한 내부 Next.js 같은 역할을 하며, 기능 디렉터리와 제한적인 린트 규칙을 둔다고 한다. 배경에는 Grok Bot 초기 코드가 약 8개의 거대한 파일로 구성되었고, 각 파일이 최소 10,000줄이었다는 화자의 설명이 있다. 에이전트가 큰 파일에 계속 코드를 덧붙이는 선택을 하지 못하도록 구조를 바꾸었다는 것이다.

이는 에이전트를 더 똑똑하게 만드는 것과 다르다. 가능한 행동 공간을 줄여 쉬운 선택이 올바른 선택이 되게 만드는 것이다. 사람에게도 같은 환경이 적용되므로, 화자는 새 팀원이 관행을 모두 외우지 않아도 비교적 빨리 생산적으로 일할 수 있다고 본다.

읽는 법: 위에서 아래로 내려간다. 도형의 폭은 실제 수량이 아니라 선택지가 줄어드는 개념을 표현한다. 규칙을 많이 넣는 것 자체가 목적은 아니다. 반복되는 실패를 실제로 막는 제약이어야 한다.

4. 외부 정보와 내부 작업을 연결한다

코드를 만드는 과정만 자동화해도 사람은 여전히 Slack, Linear, X, 이메일 등에서 버그와 요구사항을 찾아 에이전트에게 전달해야 한다. 화자는 이 외부 정보 수집 영역을 외부 루프(outer loop), 에이전트가 코드를 만들고 검증하는 영역을 내부 루프(inner loop)라고 부른다.

화자의 설명에서는 Grok Bot이 외부 정보원에 연결되고, Cursor Projects의 조정 에이전트가 작업을 나누는 역할을 한다. 예를 들어 특정 채널에서 버그 신고가 들어오면 에이전트가 이를 가져와 현재 코드에서도 재현되는지 검증하고, 사용자 설정이나 의존성 문제인지 분류하게 할 수 있다는 것이다. 조정 에이전트는 직접 모든 코드를 만들기보다 하위 에이전트에 일을 배분하고 맥락을 전달한다.

그러나 신고 하나마다 곧바로 수정 에이전트를 만드는 것이 항상 좋은 것은 아니다. 화자는 React의 나쁜 패턴을 찾는 루틴에서 발견한 문제를 먼저 문서에 쌓아 두고, 며칠마다 같은 원인인지 묶어 본다고 말한다. 즉, 빠른 실행 앞에 버퍼를 두어 숲을 보는 시간을 확보한다. 비슷한 신고 30개가 들어왔을 때 30개를 따로 고치면 중복 작업을 만들 수 있지만, 한데 모으면 상위 원인을 찾을 가능성이 생긴다는 설명이다.

5. 모든 PR을 읽는 대신 결과와 시스템을 표본 검사한다

작업량이 커지면 사람이 모든 PR을 사전에 읽는 방식은 다시 병목이 된다. 화자는 모든 변경을 전혀 보지 않는 것이 아니라, 일부 결과를 엄격하게 표본 검사하고 반복되는 실패를 환경 개선으로 되돌리는 방식을 설명한다.

한 번만 발생한 오류라면 되돌리거나 수정하고 끝낼 수 있다. 여러 에이전트가 같은 우회 방법이나 나쁜 패턴을 반복하면 린트, 타입, 구조, 스킬 또는 검증 절차를 바꾼다. 사람의 리뷰 대상을 개별 변경만이 아니라 변경을 생산하는 과정까지 넓히는 셈이다.

화자는 자신의 에이전트가 밤에도 PR을 스스로 병합하며, PR마다 여러 검증 에이전트를 투입하고 퍼징을 수행할 수 있다고 말한다. 퍼징은 앱을 실제로 실행하고 여러 방식으로 조작해 예상하지 못한 오류나 회귀를 찾는 시도다. 하지만 화자도 이 방식이 많은 토큰을 쓰며, 환경을 만드는 데 상당한 시간과 노력이 필요하다고 강조한다.

또한 모든 변경이 같은 위험을 갖지는 않는다. 쉽게 되돌릴 수 있는 변경은 “양방향 문”에 가깝지만, 데이터 손실처럼 되돌리기 어려운 변경은 “일방향 문”에 가깝다. 화자는 자동 병합 가능성이 해당 분야를 얼마나 프로그램으로 검증할 수 있는지에 달렸다고 본다. 검증하기 어려운 의료·법률·금융 같은 영역에 동일한 자동 병합 방식을 그대로 권하지 않았으며, 이 문제에는 자신도 완전한 답이 없다고 말했다.

여기까지만 이해하면 충분

  • 에이전트의 신뢰는 막연한 기대가 아니라 결과를 실행하고 실패를 다시 수정으로 연결하는 검증 루프에서 생긴다.
  • 반복적이고 기계적인 일은 CLI·스크립트·린트로 고정하고, 맥락 판단이 필요한 일만 에이전트에게 남기면 편차와 재작업을 줄일 수 있다.
  • 많은 작업을 병렬화하려면 코드 작성뿐 아니라 외부 정보 수집, 작업 분배, 표본 리뷰, 환경 교정까지 연결해야 한다.
  • 되돌리기 어렵고 프로그램으로 검증하기 힘든 변경에는 같은 수준의 자동 병합을 그대로 적용하면 안 된다.

한 명이 재료 손질부터 설거지까지 모두 하면 요리 수를 늘리기 어렵다. 여러 요리사가 함께 일하려면 조리 도구, 재료 위치, 역할, 품질 확인 절차가 필요하다. 화자는 에이전트를 보조 요리사, 조정 에이전트를 총괄 셰프, 코드베이스와 도구를 주방 환경에 대응시킨다.

비유가 깨지는 지점: 음식은 사람이 맛보는 감각적 평가가 크지만 소프트웨어의 일부는 테스트·타입·추적처럼 자동화된 증거로 확인할 수 있다. 반대로 소프트웨어도 모든 품질과 위험을 자동 검증할 수 있는 것은 아니므로, 잘 갖춘 주방이라는 비유가 무인 운영의 안전을 보장하지 않는다.

먼저 결과를 프로그램으로 재현하고 검증할 수 있는지, 실패를 같은 지표로 발견할 수 있는지, 변경을 쉽게 되돌릴 수 있는지 확인한다. 검증 범위가 좁거나 데이터 손실처럼 되돌리기 어려운 결과가 있다면 자동 병합보다 사람의 사전 승인을 유지한다. 처리량보다 실패의 탐지 가능성과 복구 가능성을 우선한다.

이번 글의 통찰

1. 처리량의 선행지표는 에이전트 수가 아니라 검증 가능성이다

  • [원문] 화자는 검증을 가장 중요한 스킬이라고 부르며, 에이전트가 결과를 실행하고 추적·스냅샷·화면 조작을 통해 직접 확인해야 반복 루프가 성립한다고 설명한다.
  • [해석] 병렬 작업을 확대하기 전에는 “몇 개의 에이전트를 돌리는가”보다 “실패를 어떤 증거로 발견하고 다시 수정하게 하는가”를 먼저 설계해야 한다.
  • [경계] 화자의 운영 사례와 주장에 근거한 결론이다. 검증 도구가 잡지 못하는 품질, 보안, 사용자 피해까지 자동으로 해결된다는 증거는 제공되지 않았다.

2. 반복되는 교정은 지시문이 아니라 환경 개선의 후보다

  • [원문] 화자는 같은 실수를 여러 에이전트가 반복하면 린트 규칙, 타입, 프레임워크, 공용 CLI로 그 선택을 어렵게 만든다고 말한다.
  • [해석] 반복해서 같은 말을 입력하고 있다면 그것은 개인의 주의력 문제가 아니라 재사용 가능한 절차나 제약이 빠졌다는 신호일 수 있다.
  • [경계] 모든 예외를 규칙으로 막으면 새로운 상황에 대응하기 어려워질 수 있다. 반복성, 오탐 가능성, 예외 처리 비용을 확인해야 한다.

3. 표본 리뷰는 검토의 제거가 아니라 검토 대상의 이동이다

  • [원문] 화자는 모든 PR을 사전에 읽기보다 결과를 표본 검사하고, 반복되는 나쁜 패턴을 발견하면 개별 에이전트가 아니라 환경을 교정한다고 설명한다.
  • [해석] 규모가 커질수록 사람은 모든 산출물의 문지기보다 산출물을 만드는 시스템의 품질 관리자로 이동할 수 있다.
  • [경계] 인터뷰의 2,500개, 2,000개, 2,000~2,500개 표현은 서로 일치하지 않으며 PR 크기와 위험도도 제시되지 않았다. 처리량만으로 품질이나 사업 가치를 판단할 수 없다.

1. 개인 프로젝트에서 시작된 문제

화자는 Meta에서 React 관련 업무를 한 뒤 한 달 쉬면서 개인 프로젝트를 시작했다고 말한다. 당시 하나의 에이전트를 세세하게 관리하는 데 많은 시간을 쓰고 있었고, 자신이 만든 스킬의 효과를 측정하기 어려웠다고 회고한다.

이 개인 프로젝트가 나중에 pstack의 기반이 되었다고 설명한다. 초기 스킬과 brain 디렉터리는 GitHub의 potato/noodle에서 볼 수 있다고 발화했다. 자신의 코딩 방식과 업무 흐름을 에이전트에게 전달하는 것이 스킬의 출발점이었다.

2. Cursor 합류와 전문지식의 역할

화자는 3월에 Cursor에 합류했다고 말한다. 이후 Agents 창의 성능 문제를 다루면서 flame graph와 heap snapshot을 직접 확인했으며, 자신이 에이전트와 Chrome DevTools 사이의 수동 중계자가 되었다고 표현한다.

다만 같은 대목에서 관련 작업 시점을 “아마 4월 초, 합류했을 때”라고도 말했다. 3월 합류와 4월 초 합류처럼 들리는 표현은 정확히 일치하지 않는다.

화자는 모델이 좋아질수록 전문지식의 가치가 줄어드는 것이 아니라, 전문가가 자신의 의도와 목표를 정확한 언어로 전달하는 능력이 더 중요해진다고 주장한다. TDD와 tautology 같은 단어가 많은 판단 기준을 압축해 전달할 수 있다는 사례를 든다.

3. 미쉐린 주방과 신뢰 사다리

화자는 “소프트웨어 공장”이 품질과 장인정신이 부족한 이미지를 줄 수 있어 “미쉐린 주방”을 선호한다고 말한다. 혼자 요리할 때는 모든 손질과 정리를 직접 하지만, 여러 보조 요리사와 일하려면 도구·재료·역할·품질 기준을 조직해야 한다.

개발자도 코드를 전부 직접 작성하는 사람에서 에이전트가 일할 환경을 설계하는 사람으로 역할이 이동할 수 있다는 주장이다. 그러나 최종 결과에는 여전히 사람의 이름과 평판이 연결되므로 책임까지 사라지는 것은 아니라고 설명한다.

4. 검증과 CLI

화자는 검증을 가장 중요한 스킬로 꼽는다. 에이전트가 코드를 실행하고 사용자처럼 상호작용하며 디버깅·추적·스냅샷을 수행할 수 있어야 한다는 것이다.

검증 결과를 평가 기준으로 삼아 반복 개선하는 방식을 hill climbing과 연결한다. Andre Karpathy의 AutoResearch도 비슷한 발상을 담았다고 언급한다.

검증 CLI는 Playwright와 Chrome DevTools Protocol 등을 연결한 접착 코드라고 설명한다. 목적은 에이전트마다 검증 스크립트를 새로 만드는 낭비를 줄이고, 반복 가능한 부분을 같은 방식으로 실행하는 것이다.

5. 결정성과 비결정성의 분리

화자는 스킬 안에서 기계적인 부분을 코드로 옮기고, 실제 판단이 필요한 부분만 에이전트에게 맡기려 한다. 기술 이전이나 코드 패턴 변환에는 코드모드와 AST 기반 변환을 사용할 수 있다고 말한다.

초기의 맥락 창 관리도 CLI 구축의 동기였다고 한다. 전사에는 “1월 또는 작년 말”, 개인 프로젝트 시점에는 “2월 초 또는 1월”이라는 상대 시점이 등장한다. 녹화일이 주어지지 않아 절대 날짜로 바꿀 수 없다.

6. 코드베이스 제약과 Dune

화자는 좋은 코드베이스를 변경하기 쉽고 변경 때문에 다른 부분이 망가지기 어려운 코드베이스로 설명한다. 타입 검사, 린트, 관례적 폴더 구조가 가능한 행동을 좁혀 준다고 본다.

내부 프레임워크 Dune은 Electron 앱을 위한 내부 Next.js처럼 설명되며 공개 소스가 아니라고 한다. 기능별 디렉터리, 코드 검색을 통한 등록 체계, 제한적인 린트 규칙을 사용한다고 말했다.

Grok Bot 초기 버전은 약 8개의 거대한 파일로 구성되었고 각 파일이 최소 10,000줄이었다고 설명한다. 이를 작은 기능 단위로 나누고, 에이전트가 다시 거대한 파일에 코드를 붙이지 않도록 구조를 제약했다.

대화 중 TypeScript에 25,000줄짜리 타입이 있다는 농담성 발언이 나오며, Go로 다시 작성되었을 가능성을 추측하지만 확인하지 않는다.

7. 외부 루프와 내부 루프

화자는 Slack, Linear, X, 이메일 등에 있는 버그 신고와 요청을 외부 맥락으로 본다. 사람이 이를 에이전트에게 계속 옮기면 사람이 다시 병목이 된다.

설명에 따르면 Grok Bot은 외부 정보원에 연결되고 Cursor Projects는 클라우드의 조정 에이전트 역할을 한다. 조정 에이전트는 직접 작업하기보다 하위 에이전트에 일을 나누고 맥락을 전달한다.

한 번에 약 30개의 문제가 들어오는 예시도 제시한다. 각각을 바로 수정하게 하면 중복 작업이 생길 수 있으므로, 관련 문제를 묶어 상위 원인을 찾을 수 있다는 설명이다.

8. 2,500개 PR과 정리 작업

인터뷰 진행자는 화자가 약 열흘 전에 발표했고 X 게시물이 약 300만 회 조회되었다고 소개한다. 이 수치는 진행자의 소개이며 독립적으로 확인되지 않았다.

PR 처리량은 다음처럼 다르게 표현된다.

  • 진행자: 지난달 프로덕션에 2,500개 PR을 반영했다고 소개
  • 화자: “2,000개 또는 그 정도”
  • 화자: “2,000~2,500개 PR을 지난달 반영했다”

화자는 이 PR들이 모두 기능은 아니며 상당 부분이 코드 정리, 즉 “gardening”이라고 설명한다. 저장소 수, 집계 방식, PR 평균 크기, 실제 프로덕션 반영 여부는 전사만으로 확정할 수 없다.

9. 버퍼와 패턴 발견

화자는 React 코드의 나쁜 패턴을 계속 찾는 에이전트를 예로 든다. 이 에이전트는 발견 즉시 수정하지 않고 문서에 문제를 추가한다. 며칠마다 누적 항목을 검토해 같은 상위 문제인지 판단한다.

이 버퍼는 개별 문제를 빠르게 처리하는 동안 놓치기 쉬운 패턴을 찾기 위한 장치다. 화자는 조정 에이전트도 실행과 동시에 전체 흐름을 보는 역할을 할 수 있다고 본다.

10. 리뷰, 자동 병합, 검증 비용

화자는 모든 PR을 직접 읽지 않는다고 말한다. 대신 매일 일부 코드와 PR 품질을 표본 검사하고, 반복되는 우회 방식이나 나쁜 패턴이 있으면 환경을 수정한다.

밤에도 에이전트가 작업하도록 했으며, 서로 다른 영역을 맡은 총괄 역할의 에이전트가 10개보다 많다고 설명한다. 성능 개선, 사용자 버그 수정, 다른 언어로의 시험적 재작성 등을 예로 든다.

완전 자동 모드에서는 PR마다 여러 검증 에이전트를 실행할 수 있으며, 한 대목에서는 10개의 검증 에이전트를 예로 든다. 그러나 1개만 쓰거나 작업 에이전트가 직접 검증하도록 조정할 수도 있고, 많은 토큰이 든다고 밝힌다.

11. 되돌릴 수 없는 변경의 경계

진행자는 쉽게 되돌릴 수 있는 양방향 문과 데이터 손실처럼 되돌리기 어려운 일방향 문을 구분해 질문한다.

화자는 자동화 가능성이 작업을 얼마나 실제로 검증할 수 있는지에 달렸다고 답한다. 프로그램으로 정확성을 검증하기 어려운 분야에서는 같은 수준의 자동 병합에 도달하기 힘들다고 인정한다.

Bend를 프로그램과 증명을 결합하는 언어의 사례로 들고, Lean과 TLA+도 형식 검증 관련 언어 또는 도구의 예로 언급한다. 다만 이것은 미래에 대한 기대와 예시이며, 모든 소프트웨어 변경을 증명할 수 있다는 뜻은 아니다.

12. 과거 대화에서 개인 스킬 추출하기

화자는 스킬을 업무 과정이 언어로 압축된 것으로 본다. 다른 사람의 스킬을 그대로 경쟁시키기보다 필요한 부분을 조합하고, 자신의 과거 대화에서 반복 개입과 교정을 찾아 새 스킬이나 린트 규칙으로 바꾸라고 제안한다.

pstack의 Recall은 이전 대화의 맥락을 새 작업으로 가져오기 위해 만든 스킬이라고 설명한다. 최신 모델이 더 유능해질수록 세세한 명령보다 업무 흐름을 담는 짧은 스킬이 중요해질 것이라고 예상한다.

그런데 에이전트 하나를 세세하게 관리하는 데 정말 많은 시간을 쓰고 있다는 걸 깨닫기 시작했어요. 당시에는 2월, 아마 2월 초나 1월쯤이었을 거예요. 사람들은 오케스트레이션(orchestration)이라는 아이디어에 정말 열광하고 있었어요. Cursor 같은 것이 나오기 전이었고, 에이전트 창이 대중화되기 전이었죠.

사람들은 여전히 TUI 환경, 즉 터미널 안에 있었고, 모두 이렇게 말하고 있었어요. “좋아, 커스텀 오케스트레이터를 만들었어.” 물론 저도 거기에 약간 덕질하듯 빠져들었어요. 장난감 프로젝트를 만들면서 ‘AI 코딩 환경을 어떻게 더 효율적으로 만들 수 있을까?’라고 생각했죠.

거기서 여정을 시작했어요. 한 걸음 물러나서 보니, 에이전트 하나를 세세하게 관리하는 데 이 모든 시간을 쓰고 있더라고요. 스킬(skills)을 만들고 있었는데, 스킬의 출력이나 결과, 영향력을 측정하기가 꽤 어려웠어요. 앞이 보이지 않는 상태였지만, 정말 빠르게 반복 작업을 하고 있었죠.

그 프로젝트는 결국 pstack의 기반이 됐어요. 당시에는 그 사실을 몰랐지만요. 초기 스킬 모음을 만들면서 배운 많은 요령은 여전히 오픈 소스로 공개되어 있어요. 보고 싶은 분이 있다면 제 GitHub에 있습니다. potato/noodle—N-O-O-D-L-E이에요. 그 안을 보면 몇 가지 스킬과 brain 디렉터리가 있을 거예요.

저는 제 능력 자체를 추출해서, 말이 된다면, 에이전트에게 넘긴다는 아이디어에 정말 관심이 많았어요. 제가 하려는 일이 결국 에이전트에게 저와 비슷한 방식으로 코드를 작성하고, 저와 비슷한 방식으로 워크플로를 수행하도록 가르치는 것이라는 걸 깨달았죠. 스킬은 그 일을 시작하는 진입점이었어요.

Cursor에 합류한 뒤에는 에이전트 창(agents window)을 작업하기 시작했는데, 성능 문제가 정말 많았어요. 상당히 버벅거렸죠. 제가 React를 다뤄 본 경험이 있었기 때문에 “에이전트 창 작업을 도와주러 오겠어요?”라는 요청을 받았어요.

Cursor에서의 여정 초반은 매우 수동적이었어요. 플레임 그래프(flame graph)와 힙 스냅샷(heap snapshot)을 깊이 들여다보면서 앱이 정확히 왜 이렇게 느린지 알아내려고 했죠. 그런데 결국 같은 깨달음으로 돌아왔어요. 병목은 저였어요. 모든 일을 수동으로 하고 있었거든요. 저는 일종의 인간 프록시(meat proxy)였어요. 에이전트와 Chrome DevTools 사이에 끼어 있는 인간 프록시였고, 그게 정말 짜증 났어요.

그게 몇 월이었나요? 시간순으로 보면 언제쯤이죠?

저는 3월에 Cursor에 합류했으니, 합류한 시점은 아마 4월 초였을 거예요. 당시에는 스킬이 전혀 없었어요. 개인적으로 만들었던 스킬은 더 이상 관련이 없다고 생각해서 버린 상태였죠.

그런데 에이전트 창을 작업하고, 지금은 Grok Bot을 작업하면서, 처음 스킬 모음을 만들 때 배운 교훈 중 상당수가 여전히 매우 중요하다는 걸 깨달았어요. 특히 검증(verification)에 관한 부분이요. 작업을 매우 엄격하게 해야 해요. 에이전트는, 심지어 최첨단 에이전트조차도, 지름길을 택하는 경향이 있다고 생각하거든요. 쉬운 일을 하려는 경향이 있어요.

제가 만든 스킬 중 상당수는 이런 질문에 관한 것이었어요. ‘쉬운 일이 올바른 일이 되게 하려면 어떻게 해야 할까? 그 일을 최고의 선택으로 만들려면 어떻게 해야 할까?’

자신의 전문성을 추출하고, 매일 하는 일을 프로세스로 바꾼다는 생각은 저에게 아주 익숙하게 느껴져요. 제가 스킬을 만들면서 정확히 그렇게 해 왔던 것 같아요.

많은 사람은 사람들이 AI에 더 의존하기 시작하면서 이제 도메인 전문성이 덜 중요해지고 있다고 생각하죠. 시작하기 전에 분위기를 한번 점검해 본다는 의미에서, 이 점에 대해 어떻게 생각하시나요?

저는 오히려 도메인 전문성이 그 어느 때보다 중요하다고 느껴요. 언젠가 X에 이 내용을 쓴 것 같기도 한데, 가끔 AI를 이렇게 생각해요. 특히 모델이 더 똑똑하고 유능해지고, 최첨단 모델이 아주 좋아질수록요.

참고로 저는 Claude Opus 4.5를 정말 좋아해요. 모델이 정말, 정말 좋아지면 병목은 더 이상 에이전트가 아니게 돼요. 에이전트가 이해하고 실행할 수 있을 만큼 자신의 의도와 목표를 명확하게 표현하는 능력이 병목이 되죠.

그래서 도메인 전문성이 많은 사람은 엄청난 우위를 갖는다고 생각해요. 특히 기술에 조금이라도 호기심이 있다면요. 의사나 변호사, 또는 특정 비공학 분야에 깊은 전문성을 가진 사람을 떠올려 보세요. 그 사람이 기술을 조금만 다룰 줄 알고 에이전트 사용법을 익힐 수 있다면 정말 훌륭한 제품을 만들 수 있어요.

머릿속에 충분히 명확한 비전이 있고, 에이전트가 구현할 수 있는 방식으로 그 비전을 설명할 수 있다면, 요즘 진짜 병목은 바로 그것이라고 생각해요. 자신의 의도와 비전을 에이전트에게 전달하는 일이요.

저는 에이전트가 등장한 뒤부터 언어에 사로잡혀 있어요. 단어의 조합과 표현을 어떻게 더 날카롭게 만들 수 있을지 끊임없이 생각하죠. 내가 사용하는 문구에 무엇이 숨겨져 있을까 하는 것도요.

제가 좋아하는 순간은 에이전트가 어떤 단어를 붙잡고 이렇게 말할 때예요. “좋아, 이 단어를 강화하겠어. 내 사고 과정에서 계속 다시 사용하겠어.” TDD가 그런 사례 중 하나였어요. 초기의 예시였죠.

최근 TDD에 관한 논의가 많았어요. 에이전트와 TDD를 사용해야 하는지에 대해서요. 사실 그건 중요하지 않아요. 중요한 건 에이전트가 TDD를 생각하고, 테스트를 작성하고, 이전과는 다르게 우선순위를 정하도록 만드는 거예요.

그래서 그릴링(grilling)이 효과적인 거예요. 그릴링은 여러분 안에 있는 단어를 끌어내거나, 적어도 에이전트가 여러분의 사고방식을 이해해서 그런 단어를 제안할 수 있게 해 줘요. 그러면 여러분은 그 단어를 받아서 “그래, 바로 그거야”라고 말할 수 있죠.

저도 공유해 주신 팁 중 일부를 따라 해 봤어요. 최근에 공유하신 팁 중 제가 가장 좋아하는 것 하나는, 아마 지난 몇 주 사이에 올리신 것 같은데, 동어반복적인 테스트(tautological tests)를 줄이거나 없애는 방법에 관한 내용이었어요. 에이전트가 쓸모없는 테스트를 잔뜩 작성하는 건 제가 정말 싫어하는 일 중 하나거든요.

‘동어반복(tautology)’이라는 단어는 특히 영어가 모국어가 아닌 사람들에게는 모두 익숙한 말이 아닐 수 있지만, 그 단어에는 많은 의미가 담겨 있어요. 거의 압축된 표현과 같죠. 단어 하나에 많은 의도와 의미를 압축하는 거예요.

정말 동의해요. 저는 원래부터 언어, 프로그래밍 언어, 자연어, 그리고 언어가 어떻게 생겨났는지에 관심이 많았어요. 이제 에이전트와 함께 자연어와 프로그래밍 언어가 만나는 지점이 생겼다는 게 정말 흥미로워요. 하지만 내부적으로는 모두 언어예요. 모두 소통이죠.

맞아요. 저는 연극 학위를 받았기 때문에 언어와 셰익스피어 같은 것들을 오랫동안 생각해 왔어요. 그래서 이 모든 일이 아주 익숙하게 느껴져요.

본격적으로 들어가기 전에, 제가 듣고 싶은 건 소프트웨어 공장(software factory)에 관한 이야기예요. ‘소프트웨어 공장’이 가장 큰 유행어잖아요. 저도 그걸 생각하고 있어요. 이건 자신의 능력을 비현실적으로 많은 PR 수까지 확장하는 개념이죠. 이 방식이 어떻게 작동하는지 모르는 사람들에게는 터무니없게 들릴 만한 숫자들이요.

오늘 한두 개에서 다섯 개의 에이전트를 운영하는 사람들부터, 동시에 수백 개의 에이전트를 실행하는 단계까지 가는 방법을 알고 싶어요. 그 과정이 어떻게 작동하는지 이해하고 싶습니다. 그리고 소프트웨어 공장 대신 미슐랭 주방(Michelin kitchen)이라는 비유를 사용하신 이야기도 듣고 싶어요. 그 비유가 이 문제를 바라보는 방식을 잘 보여 준다고 생각하거든요.

저는 ‘소프트웨어 공장’이라는 표현을 별로 좋아한 적이 없어요. 부정확해서가 아니라, 많은 사람이 공장을 품질이나 장인정신과 반드시 연결해서 생각하지는 않는 것 같기 때문이에요. 그런 것들은 저와 제품을 만드는 사람들, 기술자들에게 매우 중요해요. 우리는 사용자 경험을 중요하게 생각하고, 우리가 만드는 것들을 중요하게 생각하죠.

‘소프트웨어 공장’이 적절한 표현이라고 생각하기는 하지만, 부정적인 연상을 불러일으킬 수도 있어요. 제가 ‘미슐랭 주방’이라는 표현을 선택한 이유는 훨씬 더 지향적으로 느껴지기 때문이에요.

저는 그 비유가 정말 좋아요. 음식을 좋아하거든요. 물론 제 이름도 Potato이고, 요리하는 것도 좋아해요. 여러 가지 공통점이 보입니다.

예를 들어 혼자 먹을 식사를 요리할 때는 실용적인 일이에요. 자신을 먹여 살리고 생존하려는 거죠. 하지만 실제로는 예술로 바뀔 수도 있어요. 미슐랭 스타 셰프, 혹은 그냥 셰프나 요리사가 음식으로 할 수 있는 일이 바로 그거예요. 평범한 재료를 맛있는 식사로 바꾸고, 그 음식이 여러분을 어린 시절로 데려가게 만드는 것 같은 일이요.

이건 제가 이야기하는 신뢰 사다리를 그대로 보여 줘요. 가정 요리사로서 자신의 여정을 상상해 볼 수 있어요. 가정 요리사라면 모든 요리를 직접 하죠. 채소를 전부 자르고, 모든 준비 작업을 하고, 설거지도 전부 해요. 혼자서 모든 일을 처리하는 일인 쇼인 셈이죠.

흥미로운 사고 실험이 있어요. 식사를 요리한 다음 사람을 추가하면 어떻게 될까요? 파트너가 합류하고, 이어서 형제나 자매가 합류하고, 어느 순간 온 가족이 주방에 있게 되는 거예요.

대부분의 사람은 아마 상당히 스트레스를 받을 거예요. 이렇게 생각하겠죠. “사람들이 내 주방에서 이렇게 많이 어지럽히고 있잖아. 주방 도구가 어디 있는지도 아무도 몰라. 내 주방의 최대 수용 인원은 한 명이야.”

맞아요, 정확해요. 정말 적절한 비유인 것 같아요. 왜냐하면—

혼자 요리하는 사람에서, 그렇죠, 군대까지는 아니더라도 주방에서 나를 돕는 몇 명의 수셰프(sous chef)를 두는 단계로 어떻게 갈 수 있을지 스스로에게 질문하게 되잖아요. 일을 어떤 방식으로 나누는 게 합리적일까요? 단지 일을 나누기 위해 나누는 게 아니라, 부분들의 합보다 전체가 더 나아지도록 나누는 방법은 무엇일까요?

그런 점에서 미슐랭 주방 비유가 정말 잘 들어맞습니다. 셰프가 되면 더 이상 모든 음식을 직접 요리하는 위치에 있는 게 아니라, 생각하는 위치에 있게 되니까요.

주방의 테크 리드(tech lead)와 거의 비슷합니다. 셰프는 요리만 생각하는 게 아니라 기본적으로 주방 전체를 조직하는 일을 생각해야 합니다. 주방의 CEO(최고경영자) 같은 역할이죠. 언제 식재료를 주문할지, 어떻게 보관할지, 어떻게 준비할지, 언제 준비되어 있어야 할지를 생각해야 합니다. 단순히 요리만 하는 일이 아니고, 오늘날 엔지니어들이 코드를 작성하는 방식과도 정말 많이 닮았다고 생각합니다. 이제는 코드를 직접 작성하지 않잖아요. 에이전트가 있으니까요. 하지만 인간인 여러분은 여전히 최종 결과에 책임이 있습니다.

여러분이 하는 일에는 여전히 여러분의 이름과 평판이 함께 따라옵니다. 그러니 주방을 어떻게 구성하는지, 자신의 기술과 환경, 코드베이스를 어떻게 구성하는지가 결국 제품을 만드는 데 들어가는 새로운 재료라고 생각합니다.

네, 저는 당신의 접근 방식에서 에이전트가 작동하는 환경에 집중하는 정도가 정말 마음에 듭니다. 많은 사람은 에이전트가 이미 훌륭하고, 아마 더 나아지게 만들 수는 없을 거라고 생각합니다. “이 마법 같은 모델을 만든 사람들이 하네스(harness)와 모델의 조합에 넣어 둔 것을 그냥 믿자. 내가 할 수 있는 일은 별로 없어. Claude Code의 내부나 우리가 사용하는 무언가를 건드릴 수도 없잖아”라고 생각하죠.

하지만 저는 당신의 접근 방식이 정말 좋고, 저도 주장하는 바인데, 에이전트가 작동하는 환경을 바꿀 수 있다는 겁니다. 코드베이스를 변경할 수도 있고, 검증 도구도 제공할 수 있으며, 에이전트가 자신의 작업을 검증하도록 할 수도 있습니다.

그 발표를 보면서 특히 좋았던 점은 검증에 그렇게 많이 집중했다는 것입니다. 신뢰를 만들기 시작할 때 사용할 수 있는 레버가 바로 그것이죠. 그 부분과 실제로 어떤 모습인지 이야기해 주실 수 있을까요? 사람들이 자신의 프로세스와 주방을 개선할 수 있는 실질적인 방법을 살펴보는 것부터 시작해 보죠.

네, 사실 이 말을 많이 했습니다. pstack이나 여러분의 스킬을 사용하지 않더라도, 도구 모음에 들어 있어야 할 가장 중요한 단 하나의 스킬은 검증이라고 생각합니다.

검증이 없으면—그 의미를 모르는 분들을 위해 설명하자면—에이전트에게 손과 눈을 줄 수 있다는 개념입니다. 제가 좋아하는 비유입니다. 에이전트가 코드를 실행하고, 일반적인 인간 사용자처럼 실제로 코드와 상호작용할 수 있으며, 디버깅을 하고 트레이스(trace)를 수집하고 스냅샷(snapshot)을 찍는 등의 작업도 할 수 있다는 뜻입니다.

재미있는 점은, 제가 Cursor에 합류했을 때 처음 만든 스킬이 바로 이것이었다는 겁니다. 덕분에 저는 에이전트를 많이 신뢰하게 됐습니다. 다른 스킬들을 살펴보거나 만들어서는 얻지 못했던 방식으로, 신뢰의 사다리를 조금씩 올라가기 시작하게 해 준 것이 바로 이것이었습니다.

다른 스킬들이 아무리 뛰어나도—어떻게(how) 스킬, 왜(why) 스킬, 미해결(unsolved) 스킬—저는 여전히 에이전트와 결과물 사이의 중개자로서 제 자신에게 의존하고 있었습니다. 에이전트가 자신의 작업 결과를 실제로 볼 수 없다면, 스스로 반복해서 개선할 방법이 없습니다.

이때 사람들이 루프(loop)에 대해 이야기하기 시작합니다. 루프라는 개념은 다소 추상적으로 느껴집니다. 사람들은 “루프가 뭐죠? 에이전트 루프(agent loop)가 뭐죠?”라고 묻습니다. 하지만 저에게 루프를 루프답게 만들어 주는 가장 중요한 부분은 검증입니다. 에이전트가 자신의 작업을 검증할 수 있기 때문이고, 그렇게 되면 여러분이 방정식에서 빠질 수 있습니다.

이제 저는 예를 들어—검증의 아주 초기 사용 사례 중 하나였는데—Cursor의 에이전트 창에서 진행하던 성능 작업 같은 것을 할 수 있습니다. 저는 힐 클라이밍(hill climbing)이라고 하는 작업을 할 수 있는 지점에 도달하고 싶었습니다. 제가 알기로 연구소들(labs)이 이 용어를 많이 사용합니다.

어떤 것을 판단하거나 점수를 매길 수 있는 일종의 루브릭(rubric)이나 방법이 있고, 이제 루프가 있으므로 에이전트가 그것을 계속 개선하도록 할 수 있다는 개념입니다. Andre Karpathy도 이런 아이디어를 많이 담은 AutoResearch라는 것을 유명하게 공개했습니다.

검증은 pstack과 다른 많은 도구 모음에서 아마 가장 중요한 스킬이고, 집중해야 할 가장 중요한 요소라고 생각합니다.

저는 검증 스킬을 조정하는 데 많은 시간을 썼고, 이제 내부적으로는 검증 스킬이 정말 많습니다. Cursor나 SpaceX AI의 모든 앱에는 자동으로 유지 관리되는 검증 스킬도 있습니다. 모두가 사용하기 때문에 팀의 핵심 인프라가 됐습니다.

그것이 검증 스킬 내부에서 CLI 작업을 하게 된 계기였습니다. 지금은 에이전트가 훨씬 좋아졌고 하네스도 요약 기능이 훨씬 좋아졌기 때문에 컨텍스트 자체가 덜 중요해졌습니다. 그래도 깔끔한 컨텍스트 윈도를 유지하는 데는 여전히 이점이 있다고 생각합니다.

CLI는 본질적으로 스킬이 하는 일 중 결정론적인 부분을 가져와 스크립트나 CLI로 인코딩하는 방법입니다. 그 과정에서 원래 불필요하게 사용됐을 판단을 줄일 수 있습니다.

저는 에이전트와 스킬을 일종의 그라데이션(gradient)으로도 생각합니다. 작업 중에는 전적으로 판단에 기반하는 부분이 있습니다. 생각이 필요하고, 여러 컨텍스트 조각을 조합해야 하며, 사고해야 하는 부분이죠. 그리고 더 결정론적인 부분이 있습니다. 예를 들어 어떤 코드를 한 패턴에서 다른 패턴으로 리팩터링하고 싶다면, 그건 매우 기계적인 작업입니다. 에이전트가 매번 그것에 대해 생각하고 새롭게 고안할 필요가 없습니다.

이것이 바로 이 CLI의 계기였습니다. 제가 만든 다른 많은 스킬에서도 볼 수 있는데, 저는 결정론적인 부분을 추출해 코드로 바꾸고, 실제로 판단이 필요한 부분만 에이전트에게 남기려고 합니다.

어떤 면에서 저는 스킬을 래퍼(wrapper)라고 생각합니다. 스킬 내부에 있는 커스텀 도구를 어떻게 사용할지에 대한 가벼운 지침과 함께 제공되는 래퍼인 셈이죠.

네, CLI 자체가 그렇게 흥미로운 건 아니라고 생각합니다. 독창적인 소프트웨어도 아닙니다. 그저 Playwright와 Chrome DevTools Protocol과 상호작용하고 여러 API를 호출하는 것일 뿐입니다. 그냥 여러 요소를 이어 붙인 접착제 코드(glue) 묶음입니다.

아니요, 흥미로운 점은 스킬에서 정보를 숨기는 방법이라는 것입니다. 스킬을 보존하고 상당히 작게 유지하는 방법이기도 하죠. 그러면 더 복잡한 결정론적 작업을 스킬 안의 스크립트에 위임할 수 있습니다. 거의 정보를 압축하고, 에이전트가 더 일관된 작업을 더 일관되게 하도록 만드는 셈입니다.

신뢰란 결국 자기 도구를 신뢰하는 것입니다. 도구를 갈고닦고 아주 잘 이해하는 데 시간을 들이면 훌륭한 일을 할 수 있습니다. 사람마다 스킬과 도구 세트는 다르게 생길 겁니다.

예를 들어 어떤 사람은 당신의 Grill Me와 Docs 또는 Wayfinder 스킬을 PStack의 실행 스킬 일부와 결합해 큰 성공을 거둘 수 있습니다. 어떤 사람은 당신의 스킬을 더 많이 사용할 수도 있고, 어떤 사람은 제 스킬을 더 많이 사용할 수도 있습니다.

결국 얼마나 저와 매트를 신뢰하느냐의 문제로 돌아옵니다. 우리 둘 다 신뢰한다면 당연히 우리 스킬을 사용하세요. 하지만 자신의 트랜스크립트도 살펴보라고 권하고 싶습니다.

에이전트에게 자신이 사용한 패턴과 개입해야 했던 순간을 찾아보고, 그것을 린트 규칙이나 새로운 스킬로 만들 것을 제안하라고 하세요. 저는 과거 대화가 맥락의 보물창고라고 자주 말합니다. 프로세스가 실제로 구체화되어 있기 때문입니다. 머릿속의 추상적인 아이디어가 아니라 실제 프로세스죠. 실제로 어떻게 진행됐는지 볼 수 있고, 거기서 정말 많은 정보를 추출할 수 있습니다.

저는 실제로 PStack에 Recall이라는 스킬을 갖고 있는데, 바로 그 작업을 합니다. 비슷한 문제, 구체적으로는 Cursor 애플리케이션의 가상화(virtualization)를 작업하고 있었고 버그가 많았습니다. 새 채팅을 시작할 때마다 이렇게 생각했어요. “그런데 이전 채팅에 좋은 맥락이 정말 많이 있잖아. 그걸 새 채팅으로 가져오고 싶어. 어떻게 하면 되지?”

그렇게 과거 트랜스크립트를 살펴보게 됐습니다. Recall은 그 작업 흐름을 하나의 스킬로 축약하고 압축하는 방법이었어요. 그래서 매번 이렇게 말할 필요가 없었습니다.

매번 긴 에세이를 쓸 필요가 없다는 뜻입니다. “이 채팅들을 전부 살펴봐.” 저는 에이전트가 더 유능해질수록, 특히 스킬은 작업 흐름을 인코딩하는 것이라고 생각합니다.

작년의 스킬은 “사용해야 하는 정확한 스크립트 명령어는 다음과 같습니다”처럼 구현 세부 사항에 더 가까웠습니다. 최신 모델에서는 그런 부분을 그냥 삭제하고 작업 흐름에 집중할 수 있다고 생각합니다. 스킬은 일련의 단계, 즉 자신의 프로세스에 가까워집니다. 시간이 지나면서 스킬은 점점 더 작고 간결해질 것 같아요.

네, 서로 아주 잘 맞습니다. 원한다면 우리 스킬을 읽고 자신만의 방식으로 결합하면 되죠. Wayfinder와 Potato Mode를 결합해 자신만의 커스텀 모드를 만들 수도 있습니다. 제가 스킬에서 좋아하는 점은 아주 유연하다는 것입니다.

원하는 것은 무엇이든 할 수 있습니다. 그저 언어일 뿐이죠. 정말로요. 그 안에 마법 같은 것은 없습니다. 단지 단어일 뿐입니다.

네, 정확합니다. 거기에 마법이 있다면 선택된 단어와 사용된 문구, 그리고 추상적인 프로세스를 언어로 바꾸기 위해 이루어진 사고뿐입니다. 일단 그런 사고가 끝나면 그것은 그저 거기에 존재합니다. 표면에 드러나 있고, 그냥 가져다 쓰면 됩니다.
