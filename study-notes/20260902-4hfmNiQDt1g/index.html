먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상은 AI 코딩 도우미에게 일을 맡길 때 모든 지침을 늘 읽히지 않고, 필요한 지침 묶음만 꺼내 쓰는 방법을 설명한다. 한 번의 요청은 프롬프트, 프로젝트 지식을 항상 읽히는 파일은 규칙(Rules), 특정 작업에서만 불러오는 파일·스크립트 묶음은 AI 스킬(Skills)이다. 반복되는 코드 리뷰나 한 번뿐이어도 절차가 큰 작업을 스킬로 만들면 작업 맥락을 재사용할 수 있다.

하지만 인터넷에서 받은 마크다운도 에이전트의 행동을 바꾸는 입력이다. 화자는 숨은 지시가 키 탈취 등을 유도할 수 있다고 경고하며, 공식 출처를 우선하고 내용과 부속 파일을 사람이 확인하라고 권한다. 추천 사례는 스킬 제작, 코드 리뷰, 새 기능 연결, Flutter 레이아웃, 실제 화면 스크린샷 QA다. 핵심은 결과 생성을 AI에 맡기더라도 코드가 정말 필요한지, 출력이 안전하고 쓸 만한지는 사람이 판단하고 실제 화면까지 확인하는 것이다.

여기까지만 이해하면 충분

  • 스킬은 모든 작업에 항상 넣는 규칙이 아니라, 관련 작업에서만 불러오는 지침 묶음이다.
  • 반복 작업이나 절차가 큰 일회성 작업이 스킬 후보가 된다.
  • 마크다운 스킬도 안전하다고 가정하지 말고 출처·내용·부속 파일을 확인해야 한다.
  • 코드와 테스트만 보지 말고 실제 화면과 작업 필요성도 검증해야 한다.

비유와 깨지는 지점

작업별 공구 서랍

규칙이 작업장 벽에 항상 붙어 있는 공통 지침이라면, 스킬은 특정 작업을 시작할 때만 여는 공구 서랍과 비슷하다. 서랍 안에는 설명뿐 아니라 템플릿, 참고자료, 스크립트가 함께 들어갈 수 있다.

비유가 깨지는 지점: 실제 스킬은 에이전트가 설명을 보고 불러올지를 판단하며, 내부 파일이 에이전트 행동에 영향을 준다. 따라서 단순한 공구함과 달리 악성 지시나 잘못된 절차도 담길 수 있다.

1. 원인

왜 프로젝트 지침을 모두 규칙 파일에 넣는 대신 작업별 스킬로 나누려는가?

모범 답안 보기

규칙은 에이전트가 계속 읽어야 하지만 스킬은 관련 작업에서만 불러올 수 있다. 반복 절차와 템플릿을 작업별로 묶으면 필요한 맥락을 재사용하면서 무관한 지침을 항상 읽히지 않아도 된다.

2. 대조

에이전트 코드 리뷰와 실제 화면을 보는 시각적 QA는 무엇을 다르게 확인하는가?

모범 답안 보기

코드 리뷰는 구현 방식과 변경 내용을 살피지만, 화면이 의도대로 배치되고 상호작용하는지는 놓칠 수 있다. 시각적 QA는 실행된 화면을 확인해 코드나 통과한 테스트만으로 드러나지 않는 UI 결함을 찾는다. 반대로 화면 캡처만으로 내부 코드 품질을 판단할 수는 없다.

3. 적용

새 작업을 스킬로 만들지 판단할 때 어떤 기준을 확인해야 하는가?

모범 답안 보기

같은 설명과 절차가 반복되는지, 한 번만 하더라도 단계가 크고 자동화 가치가 있는지부터 본다. 그다음 에이전트가 스킬을 불러올 조건을 분명히 적고, 출처와 파일 내용을 검토한다. 결과 평가는 코드 품질뿐 아니라 작업의 필요성, 실제 실행 결과, 수정 비용까지 포함해야 한다.

이번 글의 통찰

1. 반복 횟수보다 재사용할 절차가 있는지가 중요하다

  • [원문] 화자는 반복되는 코드 리뷰를 대표적인 스킬 후보로 들었고, 모바일 광고 추가처럼 한 번 수행할 큰 절차도 임시 스킬로 자동화할 수 있다고 말했다.
  • [해석] 스킬 후보를 찾을 때는 단순 빈도뿐 아니라 매번 다시 설명해야 하는 판단 기준·순서·템플릿이 있는지를 봐야 한다.
  • [경계] 어떤 작업이 실제로 더 빨라지는지에 대한 비교 수치는 제시되지 않았다. 화자가 공동체용 스킬을 최소 2주마다 확인한다는 사례도 모든 스킬의 보편적 유지 주기는 아니다.

2. 읽는 문서도 에이전트에게는 공격 표면이다

  • [원문] 화자는 인터넷에서 받은 마크다운에 프롬프트 인젝션이나 숨은 유니코드 지시가 들어갈 수 있다며 공식 저장소나 관리자를 우선하고 내용을 확인하라고 말했다.
  • [해석] 스킬 설치는 문서 복사가 아니라 실행 권한이 있는 작업자에게 외부 지침을 전달하는 일처럼 검토해야 한다.
  • [경계] 공식 스킬과 패키지 관리자의 스킬은 위험이 낮거나 거의 없다는 평가는 화자의 주장이지 독립적으로 검증된 보증이 아니다. 구체적인 공격 재현이나 위험률도 제시되지 않았다.

3. 생성 자동화와 판단 자동화는 같은 일이 아니다

  • [원문] 화자는 두 에이전트가 코드 리뷰와 PR 분류 결과를 교차 확인하게 했지만, 코드가 좋은지와 그 코드가 필요한지는 다르다고 말했다. 실제 스크린샷을 이용한 UI 검사도 추천했다.
  • [해석] 에이전트 수를 늘리는 것보다 각 검증자가 무엇을 확인하고 무엇은 판단하지 못하는지 나누는 편이 중요하다.
  • [경계] META는 다섯 스킬을 매일 활용하는 것으로 소개하지만, 전사는 코드 리뷰를 1년 넘게 사용했다는 점과 각 추천 사례를 구분해 말할 뿐 다섯 가지 모두를 매일 쓴다고 확인하지 않는다. META의 ‘단일 코드베이스로 4개 플랫폼을 완성’이라는 표현과 달리 전사에서는 배포 가능성을 조건형으로 설명한다. 또한 화자는 Flutter를 “하나 가격으로 둘”이라고 표현한 뒤 Android·iOS·Windows·macOS 네 플랫폼을 열거하므로 숫자 표현은 서로 일치하지 않는다. 세 병렬 장비와 Claude·Codex·Antigravity의 열거, 다섯 추천 항목의 열거는 각각 개수와 일치한다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 작업별로 필요한 지침만 공개하는 구조는 학습자에게 필요한 설명과 예시를 단계별로 제공하는 방식과 닮았다.
  • 통찰: 이해 여부는 용어 암기보다 프롬프트·규칙·스킬의 차이를 설명하고 새 사례를 분류할 수 있는지로 확인할 수 있다.
  • 질문/행동: 낯선 작업 하나를 제시하고 학습자가 규칙과 스킬 중 무엇이 적절한지 근거와 함께 설명하게 한다.

사업가 · 구조적 비유

  • 관련성: 반복 절차의 자동화는 시간 절감 가능성을 만들지만, 유지보수와 보안 검토라는 비용도 추가한다.
  • 통찰: APOM·이커머스·물류에 적용한다면 현재 운영 사실로 가정하지 말고, 반복 절차 하나에서 재작업 감소가 유지비보다 큰지 검증해야 한다.
  • 질문/행동: 후보 절차의 반복 설명 시간, 자동화 후 수정 시간, 검토 책임자를 먼저 확인한다.

마케터 · 구조적 비유

  • 관련성: 화자의 생산성 주장은 경험담이고, 실제 화면 캡처는 결과를 보여주는 증거에 더 가깝다.
  • 통찰: 상세페이지에서도 “좋다”는 주장보다 실제 결과 장면을 보여주는 편이 강하지만, 소프트웨어 스크린샷이 상품 효능을 자동으로 증명하지는 않는다.
  • 질문/행동: 카피의 각 주장 옆에 실제 화면·비교 결과·검증 조건 중 어떤 증거를 붙일 수 있는지 묻는다.

AI/SW 학습자 · 직접 전이

  • 관련성: 스킬 로딩, 외부 문서 보안, 다중 에이전트 검토, 시각적 QA가 모두 에이전트 개발 흐름에 직접 연결된다.
  • 통찰: 자동화 품질은 생성량보다 올바른 스킬 호출, 안전한 입력, 교차 검토, 실제 실행 결과로 측정해야 한다.
  • 질문/행동: 스킬을 추가하기 전에 호출 조건, 신뢰 출처, 허용 도구, 실패 시 검토 절차를 적는다.

가치 지도

"반복 설명과 구현 누락, 코드만으로 발견하기 어려운 결함" 문제
→ "더 일관된 구현과 빠른 검토" 수혜자: 개발자와 결과물을 사용하는 사람
→ "작성·검토 시간과 저장소 접근 권한 제공" 지불자 또는 자원 제공자: 개발팀 또는 프로젝트 책임자
→ "사람의 수정 없이 검토 기준을 통과한 결과의 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 반복 개발 절차 하나를 골라 로컬 스킬로 작성·검토한 뒤 다음 3회 작업에 적용한다.
  • 측정 1개: 세 작업에서 사람이 수정하지 않고 통과한 검토 항목의 비율을 기록한다.
  • 중단 기준 1개: 사람이 수정하지 않고 통과한 검토 항목의 비율이 70% 미만이면 적용 확대를 멈춘다.

# 섹션 요지
1 프롬프트·규칙·스킬 항상 읽는 규칙과 필요할 때 불러오는 스킬을 구분한다.
2 제작 시점과 보안 반복 또는 큰 일회성 절차를 자동화하되 외부 파일을 검사한다.
3 추천 스킬 다섯 가지 제작, 리뷰, 기능 연결, 레이아웃, 시각적 QA를 제안한다.
4 인간과 다중 에이전트 생성은 자동화해도 필요성·안전성 판단은 통제해야 한다.
5 병렬 작업과 Flutter 세 도구를 병렬 사용하며 Flutter의 다중 플랫폼 가능성을 강조한다.

1. 프롬프트, 규칙, 스킬

화자는 한 번의 메시지로 버그 수정이나 프로젝트 설명을 전달하는 것을 프롬프트로 구분한다. 규칙은 프로젝트 지식을 담아 에이전트가 항상 읽도록 하는 마크다운 파일이다. 스킬은 마크다운뿐 아니라 스크립트·자산·참고자료를 포함할 수 있으며, 특정 작업과 관련될 때 선택적으로 읽힌다.

스킬을 만들 첫 번째 신호는 반복이다. 코드 리뷰처럼 같은 절차를 계속 수행한다면 단계와 기준을 템플릿으로 만들 수 있다. 두 번째 경우는 반복되지 않더라도 모바일 광고 설치처럼 규모가 큰 일회성 작업을 자동화하고 싶을 때다. 이 경우 사용 후 스킬을 제거할 수도 있다고 설명한다.

2. 보안과 유지보수

화자는 마크다운 파일도 프롬프트 인젝션을 포함할 수 있으며, 에이전트가 키를 탈취하도록 유도하는 지시나 눈에 잘 보이지 않는 유니코드 지시가 들어갈 수 있다고 경고한다. Google 저장소의 공식 Flutter·Dart 스킬이나 패키지 관리자가 제공하는 스킬을 상대적으로 안전한 선택으로 제시하지만, 무작위 검색 결과는 직접 확인해야 한다고 말한다.

공동체용 Flutter 스킬 저장소를 관리하는 화자는 변경·업데이트·최적화 필요성을 최소 2주마다 확인한다고 했다. 인터뷰어도 공식 스킬을 별도 저장소처럼 유지해야 하는 부담을 언급했다.

3. 추천한 다섯 스킬

  1. Skill Creator: /skill-creator 명령이나 일반 요청으로 스킬 초안을 만들고, SKILL.md 외에 스크립트·자산·참고자료도 생성하게 한다. 다만 자동 모드에 전부 맡기지 말고 질문에 답하며 결과를 조정하라고 권한다.
  2. Code Review: 화자는 자신의 Code Review 스킬을 1년 넘게 사용했다고 말했다. 자신의 리뷰 스킬과 Kevin Moore의 PR Triage 스킬을 서로 다른 에이전트에 맡기고 보고서를 교차 확인한다.
  3. 새 엔드포인트·기능 연결: 새 화면, 내비게이션, scaffold, 디자인 시스템, repository, data source 등 프로젝트 고유 절차를 묶는다. 설명에는 새 기능을 추가할 때 사용한다는 호출 조건을 명시한다.
  4. Flutter 기본 레이아웃: 에이전트가 과도한 container·padding·고정 위치를 쓰지 않도록 Row, Column, Wrap, Stack, Flexible, Expanded의 사용 조건을 안내한다. 목적은 첫 구현부터 반응형 구조를 유도하는 것이다.
  5. 웹 실행 기반 시각적 QA: 앱을 웹에서 실행한 뒤 실제 스크린샷이나 animated WebP를 생성해 UI 결함과 제스처를 확인한다. 화자는 golden test도 회귀 확인에 쓰지만 폰트와 이미지 로딩 문제를 다뤄야 한다고 설명한다.

4. 인간의 역할과 생산성 주장

화자는 스킬 작성 자체도 에이전트에 맡기되 사람이 관리자로서 질문에 답하고 내용을 확인해야 한다고 본다. 코드 리뷰 에이전트는 코드 품질을 판단할 수 있어도 코드가 정말 필요한지를 항상 판단하지는 못하며, 충분한 맥락과 기억이 없으면 인간 판단이 더 낫다고 말했다.

일상 작업에서는 세 장비에서 Claude, Codex, Antigravity를 병렬로 실행하고 작업을 서로 넘긴다고 설명했다. 세 도구의 사용 한도를 모두 소진할 때까지 작업하는 습관을 생산적이지만 중독적으로 느낀다고 표현했다. 이는 개인 경험이며 생산성 향상 수치는 제시되지 않았다.

RevenueCat의 향후 Shipathon에 참여할 계획이며, 본업 이후 저녁과 주말에 제출할 앱을 만들기 위해 에이전트 팀을 운영한다고 말했다. 이는 앞으로 참여하고 제출하려는 계획이지, 참여나 앱 완성이 끝났다는 보고가 아니다.

5. Flutter와 플랫폼 수 표현

화자는 Flutter가 Python이나 JavaScript만큼 학습 데이터가 많지 않다고 주장하며, 에이전트에게 기본 레이아웃 원칙을 반복해서 알려줄 필요가 있다고 말했다. 동시에 하나의 코드베이스로 Android, iOS, Windows, macOS의 네 플랫폼에 배포할 수 있다는 가능성을 장점으로 제시했다.

[경계] 같은 대목에서 “하나 가격으로 둘”이라는 표현과 네 플랫폼 열거가 함께 나온다. 전사는 이를 조정하거나 설명하지 않으므로 두 숫자를 하나로 합치지 않는다. 또한 배포 가능성을 설명한 것이며 실제로 네 플랫폼용 앱을 이미 완성했다고 확인한 것은 아니다.

제가 개인적으로 추천하는 가장 중요한 스킬 다섯 가지입니다.

첫 번째는 스킬을 만들기 위한 Skill Creator 스킬입니다. 전체 과정을 자동화하는 데 도움이 되고, 스크립트와 참조 자료 등도 대신 작성해줍니다. 우리는 보통 이런 것들을 잊고 SKILL.md만 작성한 뒤 끝내버립니다. 하지만 스크립트, 에셋, 참조 자료도 있습니다. 이런 것들을 모두 활용하면 스킬을 더 강력하게 만들 수 있습니다.

두 번째는 Code Review 스킬입니다. 저는 1년 넘게 사용해 왔고, 정말 잘 작동했습니다.

저는 공개된 스킬 저장소에 제가 직접 만든 Code Review 스킬을 올려두었습니다. Kevin Moore의 PR Triage 스킬도 좋아해서, 두 스킬을 서로 다른 두 에이전트에게 제공합니다. 한 에이전트는 코드 리뷰를 하고, 다른 에이전트는 PR 분류를 합니다. 그런 다음 서로의 보고서를 확인하게 하면 아주 좋은 결과를 얻을 수 있습니다.

에이전트형 코드 리뷰에 아직 남아 있는 유일한 문제는 에이전트가 코드가 좋은지는 평가할 수 있지만, 그 코드가 필요한지는 항상 판단하지 못한다는 점입니다. 에이전트가 필요한 맥락과 기억을 갖고 있지 않다면 이 부분은 인간이 더 잘할 겁니다. 그런 맥락과 기억이 있다면 에이전트도 판단할 수 있겠죠.

이것이 Code Review 스킬입니다.
