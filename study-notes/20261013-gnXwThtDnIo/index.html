AI가 코드를 쏟아내는 시대, 검증은 대체 누가 해야 할까요?

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 코드 생산보다 검증이 느려질 수 있다

이 발표의 출발점은 간단하다. AI가 코드를 빨리 만들면 개발이 무조건 빨라지는 것이 아니다. 새 코드가 실제 서비스에 들어가려면 보안·규정·품질 기준을 통과해야 하고, 다른 개발자가 변경 내용을 확인해야 한다. 이런 중앙 검증 단계가 지속적 통합(CI)과 코드 리뷰다.

화자는 조직이 커질수록 빌드와 검사가 오래 걸리고, 서로 다른 지역의 팀이 비동기로 리뷰하며, 여러 도구와 맞춤 설정을 유지하는 비용도 커진다고 설명한다. 검사에 실패하면 개발자가 고친 뒤 다시 결과를 기다려야 한다. 화자는 이 바깥쪽 재시도 주기가 보통 시간이나 일 단위가 될 수 있다고 말한다.

여기에 AI가 더 많은 코드와 더 큰 변경 묶음인 풀 리퀘스트(PR)를 만들면 검토량도 늘어난다. 모든 PR을 사람이 꼼꼼하게 보면 속도가 느려지고, 빨리 넘기려고 형식적으로 승인하면 운영 장애 위험이 커진다. 즉, 생산 속도만 올리면 병목이 코드 작성에서 검증 쪽으로 이동할 수 있다는 주장이다.

읽는 법: 위에서 아래로 읽는다. 각 화살표는 화자가 제시한 인과 또는 대응 순서다. 수치를 나타내는 그래프가 아니라 개념 지도이며, 마지막 단계가 자동으로 성공한다는 뜻은 아니다.

에이전트는 답만 쓰는 것이 아니라 검증 작업을 반복한다

화자가 소개한 Gitar의 핵심은 AI에게 한 번 질문해 리뷰 의견만 받는 방식이 아니다. PR이 만들어지면 문제를 찾아 줄별 의견을 달고, CI가 실패하면 원인을 요약한다. 불규칙하게 통과와 실패가 바뀌는 플래키 테스트(flaky test)도 찾아 재시도 규칙을 적용할 수 있다고 주장한다.

문제가 발견되면 에이전트에 수정을 요청할 수 있다. 더 나아가 모든 설정된 검사가 통과해 병합 준비 상태인 그린 PR(green PR)이 될 때까지 수정과 검증을 반복하도록 구성할 수 있다. 마지막에는 정해 둔 규칙과 조건을 만족하는 PR만 자동 승인하고 자동 병합하도록 할 수 있다.

중요한 점은 “AI가 코드를 썼으니 AI가 맞다고 판정한다”가 아니다. 코드 리뷰 규칙, CI 검사, 사용자 정의 검사, 병합 차단 조건처럼 이미 정한 기준을 에이전트가 연결해 반복 실행하는 구조다.

읽는 법: 1번부터 아래로 내려간다. 4번에서 실패가 남으면 2번으로 돌아간다. 5번은 모든 PR을 무조건 병합한다는 뜻이 아니라, 사용자가 정한 조건이 허용할 때 실행되는 단계다.

자동화는 한꺼번에 켜는 것이 아니라 권한을 올린다

화자는 사용자가 시스템의 정확성을 경험하며 자동화 수준을 높이는 경향이 있다고 말한다. 처음에는 에이전트가 리뷰 의견만 제시한다. 의견이 정확하고 중요한 문제를 잡는다고 판단하면, 해결되지 않은 문제가 있는 PR의 병합을 막도록 권한을 준다. 그다음 자동 수정을 허용하고, 마지막에는 특정 조건에서 자동 승인과 자동 병합까지 맡긴다.

이 순서는 편리한 기능 목록만이 아니다. 검증되지 않은 신뢰를 먼저 주지 않고, 관찰된 결과에 따라 권한을 확대한다는 운영 방식이다. 앞 단계에서 오탐과 누락을 확인하지 않은 채 바로 자동 병합으로 가면, 검증을 자동화하려다 새로운 위험 경로를 만들 수 있다.

읽는 법: 위에서 아래로 갈수록 에이전트의 행동 권한이 커진다. 상자의 폭은 정량 데이터가 아니라 권한 범위가 확대된다는 개념 표현이다. 화자는 이런 이동 경향을 사용자에게서 보고 있다고 말하지만, 사용자 수나 단계별 성과 수치는 제시하지 않았다.

모든 PR을 처리하면 조직 전체의 반복 문제도 볼 수 있다

화자는 시스템이 모든 PR을 처리하기 때문에 개별 오류 수정 외에 분류 정보도 만들 수 있다고 설명한다. 플랫폼 팀은 CI 실패가 테스트의 불안정성 때문인지, 기반 시설 문제인지, 다른 종류의 실패인지 분류해 자주 발생하는 원인을 볼 수 있다.

리더십 팀은 PR이 기능 개발, 문제 수정, 잡무, 리팩터링 가운데 어디에 쓰이는지 분류할 수 있다. 이는 “누가 코드를 많이 썼는가”보다 개발 자원이 어떤 종류의 작업에 들어가는지를 보는 자료다. 다만 발표에는 분류 정확도를 어떻게 평가했는지, 잘못 분류된 항목을 누가 교정하는지는 나오지 않는다.

내부에는 세 가지 구성 요소가 있다

화자는 Gitar를 이루는 흥미로운 구성 요소를 정확히 세 가지로 열거한다.

  1. 컨트롤 플레인(control plane): PR 작업 흐름을 조정하는 층이다.
  2. 에이전트 런타임 또는 하네스(agent runtime/harness): 여러 에이전트 실행, 문맥과 메모리 관리, 도구 호출, 외부 연동을 담당한다.
  3. LLM 프록시(LLM proxy): 여러 모델 사이의 요청 경로와 장애 시 대체 처리를 맡는다.

자체 에이전트 하네스를 만든 이유로는 검증 작업에 맞춘 토큰 비용, 정밀도, 탐지 범위 최적화를 든다. 화자는 이를 통해 PR당 고정 가격으로 결과를 보장할 수 있다고 주장하지만, 보장의 조건과 품질 기준은 발표에서 구체적으로 설명하지 않는다.

에이전트와 프로그램 분석을 결합하려 한다

에이전트는 여러 도구를 사용하고 상황에 따라 다음 행동을 선택하는 데 강점이 있다. 반면 프로그램 분석은 코드의 흐름과 의존 관계를 알고리즘으로 검사한다. 발표에서는 오염 분석(taint analysis), 제어 흐름 분석, 데이터 흐름 분석, 소프트웨어 구성 분석을 예로 든다.

화자는 Gitar가 Sonar의 일부가 된 뒤 SonarQube와 통합을 진행 중이라고 말한다. 따라서 이 결합은 발표 시점에 완전히 검증이 끝난 결과가 아니라 진행 중인 통합과 앞으로 더 나은 정밀도·탐지 범위를 얻을 것이라는 전망이다.

이 발표에서 주장과 증거를 구분해야 한다

화자는 더 좋은 품질과 보안, 더 빠른 배포, 개발자 생산성과 만족도 향상, 검토 부담 감소를 결과로 제시한다. 그러나 발표 전사에는 표본 수, 비교 기간, 장애 감소율, 오탐률, 누락률 같은 수치가 없다. “검증 마찰을 완전히 없앤다”는 문장도 발표자의 제품 주장이지, 독립적으로 확인된 사실은 아니다.

또한 화자 정보에는 불확실성이 있다. 전사에서 화자는 자신을 Ali라고만 소개하지만 META 설명은 Ali-Reza라고 적는다. META의 provenance.creator는 비어 있고, 출처 메모는 원본 영상 링크를 확인하지 않은 채 화자 이름과 SNS로 출처를 추정했다고 밝힌다. META의 소속 후보는 Sonarsource이지만 전사는 Gitar가 Sonar에 인수되어 그 일부가 됐다고 표현한다. 두 이름의 정확한 관계와 원작자 신원은 제공 자료만으로 확정할 수 없다.

여기까지만 이해하면 충분

  • AI가 코드 생산량을 늘리면 CI와 코드 리뷰의 검증 부담도 늘어 병목이 오른쪽으로 이동할 수 있다.
  • 에이전트 검증은 리뷰, 실패 원인 분석, 수정, 재검증, 조건부 병합을 하나의 반복 루프로 연결한다.
  • 자동화 권한은 리뷰 제안부터 시작해 관찰된 정확성에 따라 차단·수정·자동 병합으로 단계적으로 넓혀야 한다.
  • 발표의 성과와 완전한 마찰 제거는 수치 근거가 제시되지 않은 화자의 주장이며, SonarQube 결합은 진행 중인 통합과 전망이다.

AI가 만든 PR에서 CI 실패가 발생한다. 에이전트가 원인을 설명하고 코드를 수정한 뒤 검사를 다시 실행한다. 실패가 남으면 반복하고, 설정된 조건을 모두 충족했을 때만 승인·병합 단계로 넘어간다.

→ "조건을 통과한 PR만 승인·병합 후보가 된다" 결과

비유와 깨지는 지점

자동 출국 심사대

코드 리뷰 규칙과 CI 검사는 여권·탑승 조건을 확인하는 절차에, 에이전트는 여러 검사 결과를 모아 문제를 설명하고 재검사를 진행하는 심사 장치에 대응한다. 신뢰가 쌓이기 전에는 사람이 최종 판단하고, 검증된 조건에서만 자동 통과 범위를 넓힌다는 점이 닮았다.

비유가 깨지는 지점: 출국 심사는 비교적 고정된 신원과 규칙을 다루지만, 소프트웨어 변경은 PR마다 문맥과 실패 방식이 달라진다. 에이전트가 직접 코드를 수정하면 단순 심사를 넘어 새로운 변경까지 만들기 때문에 추가 검증이 필요하다.

코드 생성량과 PR 크기가 늘면 사람이 읽을 변경량과 CI 실패 가능 지점도 늘어난다. 검증 도구와 팀 리뷰는 비동기로 움직이고, 실패할 때마다 수정과 대기를 반복한다. 따라서 코드 작성 시간이 줄어도 병목이 리뷰·CI·재시도 단계로 이동하면 전체 배포 시간은 줄지 않을 수 있다.

리뷰 제안은 사람이 최종 판단하므로 에이전트의 행동 권한과 실패 영향이 제한된다. 자동 병합은 에이전트 판단이 실제 코드 반영으로 이어지므로 오탐·누락의 영향이 커진다. 그 사이에 미해결 문제 차단, 제한된 자동 수정, 재검증, 명시적 병합 조건 같은 단계가 필요하다.

새 코드 에이전트의 검증 자동화를 도입한다면, 가장 먼저 무엇을 측정한 뒤 다음 권한을 열어야 할까?

먼저 참고용 리뷰만 실행하고 사람이 사후 판정한 오탐과 누락을 기록한다. 중요한 문제를 안정적으로 찾는지 확인한 다음 병합 차단을 검토하고, 자동 수정은 수정 후 기존 검사를 다시 통과하는지 확인해야 한다. 자동 병합은 적용 범위와 조건, 실패 시 되돌리는 절차가 명확할 때만 별도로 판단한다.

이번 글의 통찰

1. 생산 자동화는 검증 비용을 없애기보다 이동시킬 수 있다

  • [원문] 화자는 AI로 PR 수와 크기가 늘어 리뷰할 코드와 운영 실패 가능성도 커지며, 비용이 개발 생명주기의 오른쪽으로 이동한다고 말했다.
  • [해석] 코드 생성 속도만 측정하면 실제 병목을 놓친다. 생성 이후의 리뷰 대기, CI 실패, 재작업, 운영 유출까지 함께 봐야 자동화의 순가치를 판단할 수 있다.
  • [경계] PR 증가량, PR 크기, 운영 장애 증가율은 제시되지 않았다. 모든 조직에서 같은 정도로 비용이 이동한다고 확인된 것은 아니다.

2. 신뢰는 느낌이 아니라 권한을 여는 조건이어야 한다

  • [원문] 화자는 사용자가 리뷰를 먼저 경험한 뒤 병합 차단, 자동 수정, 조건부 자동 승인·병합으로 이동하는 경향을 설명했다.
  • [해석] 자동화의 핵심은 기능 수가 아니라 관찰된 정확성과 실패 영향에 맞춰 권한을 단계적으로 넓히는 것이다.
  • [경계] 사용자 수, 단계별 체류 기간, 오탐률과 누락률, 자동 병합 이후의 장애 결과는 공개되지 않았다. “명확한 경향”은 화자의 관찰이다.

3. 생성형 판단과 알고리즘 검사는 상호 보완 후보지만 아직 결과로 확정할 수 없다

  • [원문] 화자는 Gitar와 SonarQube의 통합을 진행 중이라고 했고, 에이전트와 오염·제어 흐름·데이터 흐름·구성 분석의 결합이 각각을 단독으로 사용할 때보다 나을 것이라고 전망했다.
  • [해석] 에이전트에는 작업 조정과 수정 역할을, 프로그램 분석에는 코드 구조에 근거한 검사 역할을 맡기고 서로의 결과를 재검증하게 하는 구조를 시험할 수 있다.
  • [경계] 발표 시점의 상태는 통합 완료가 아니라 진행 중이다. 정밀도, 탐지 범위, 가격 개선을 뒷받침하는 비교 수치는 없다. 전사상 화자는 Ali, META 설명은 Ali-Reza이며 provenance.creator는 비어 있다. META 소속 후보 Sonarsource와 전사의 Sonar도 제공 자료 안에서 관계가 해소되지 않았다. “약 한 달 전 인수”는 발표일을 알 수 없는 상대적 표현이므로 업로드일에서 인수일을 계산할 수 없다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 발표는 리뷰 제안에서 자동 병합까지 권한을 단계적으로 확대하며 이해와 신뢰를 행동으로 확인한다.
  • 통찰: 학습자가 설명을 들었다는 사실보다, 원인을 설명하고 실패 사례를 구분하며 새 사례에 적용하는지를 단계별 관문으로 볼 수 있다.
  • 질문/행동: 설명, 대조, 적용 과제를 차례로 제시하고 어느 단계에서 오답이 생기는지 기록해 보자.

사업가 · 구조적 비유

  • 관련성: 검증 단계에는 사람의 시간, 도구와 기반 시설 비용, 운영 실패 위험이 집중된다는 원문 단서가 있다.
  • 통찰: APOM·이커머스·물류의 실제 시스템 상태는 출처에 없다. 다만 처리량을 늘렸을 때 검수·예외 처리·재작업이 새 병목이 되는 구조인지 검증할 수 있다.
  • 질문/행동: 주문이나 콘텐츠 생산량이 늘어날 때 최종 검수 대기와 재작업이 함께 늘어나는 구간이 있는가?

마케터 · 직접 전이

  • 관련성: 화자는 “노이즈 없는 리뷰”, “그린 PR”, “완전 자동화”, “마찰 완전 제거”처럼 결과가 선명한 표현을 사용했다.
  • 통찰: 강한 결과 문장은 관심을 만들지만, 오탐률·누락률·비교 기간 같은 증거가 없으면 제품 주장과 검증된 성과를 분리해 표시해야 한다.
  • 질문/행동: 카피에 자동화 결과를 쓸 때 적용 조건, 비교 기준, 실패 사례 가운데 무엇을 함께 제시할 것인가?

AI/SW 학습자 · 직접 전이

  • 관련성: 컨트롤 플레인, 에이전트 하네스, LLM 프록시, CI 연동, 프로그램 분석이 하나의 실제 검증 작업을 중심으로 제시됐다.
  • 통찰: 모델 이름보다 PR 검증이라는 작업량, 오탐·누락, 재시도 비용, 실패 시 대체 경로를 기준으로 아키텍처를 평가해야 한다.
  • 질문/행동: 참고용 리뷰 단계에서 사람의 사후 판정과 비교해 오탐·누락을 먼저 측정할 수 있는가?

가치 지도

"AI가 늘린 PR을 기존 인력과 도구만으로 검증하면 대기와 재작업이 커질 수 있다" 문제
→ "반복 검증 부담을 줄이고 조건을 통과한 PR을 더 빨리 받는다" 수혜자: 개발자·플랫폼 팀·개발 조직
→ "도구 비용, 개발 시간, PR 데이터, 자동화 권한과 신뢰를 제공한다" 지불자 또는 자원 제공자: 개발 조직
→ "검증 기준을 충족한 PR의 생성부터 병합까지 걸린 시간" 가치 지표

작은 실험 하나

  • 행동 1개: 검증용 저장소의 다음 5개 PR에 에이전트 리뷰를 참고용으로만 실행하고, 사람이 최종 검토한 뒤 오탐 또는 누락이 있었던 PR을 표시한다.
  • 측정 1개: 사후 사람 검토에서 오탐 또는 누락이 확인된 PR의 비율.
  • 중단 기준 1개: 오탐 또는 누락이 확인된 PR 비율이 20% 이상이면 병합 차단이나 자동 수정으로 확대하지 않는다.

# 섹션 요지
1 중앙 검증의 역할 CI와 코드 리뷰가 품질 관문이자 배포의 핵심 경로다.
2 AI가 키운 병목 PR 수와 크기가 늘며 검토와 운영 실패 부담이 커진다고 주장한다.
3 에이전트 검증 루프 리뷰, CI 분석, 수정, 재검증, 조건부 병합을 자동화한다.
4 단계적 신뢰 리뷰에서 시작해 차단·자동 수정·자동 병합으로 권한을 넓힌다.
5 조직 수준의 분류 CI 실패 원인과 PR 작업 유형을 분류해 플랫폼·리더십 자료로 쓴다.
6 내부 구성 컨트롤 플레인, 에이전트 하네스, LLM 프록시의 세 부분을 설명한다.
7 프로그램 분석 결합 SonarQube 통합을 진행하며 에이전트와 전통 분석의 결합을 전망한다.

1. CI와 코드 리뷰는 중앙 검증 단계다

화자는 거의 모든 소프트웨어 팀에 CI와 코드 리뷰로 이뤄진 중앙 검증 단계가 있다고 설명한다. 이곳에서 보안, 규정 준수, 코드 품질 기준을 집행하며, 변경 사항이 운영 환경으로 들어가는 핵심 경로이므로 빠를수록 좋다고 본다.

조직이 커지면 빌드와 작업 시간이 길어지고, 서로 다른 지역의 팀이 비동기식으로 리뷰한다. 여러 고가 도구와 기반 시설을 통합해야 하므로 개발자 기반 시설 비용도 집중된다. 플랫폼 팀은 제한된 인원으로 맞춤 설정과 스크립트가 얽힌 시스템을 유지해야 한다고 말한다.

검증 실패는 수정 후 다시 기다리는 바깥 루프를 만든다. 화자는 이 시간이 보통 시간이나 일 단위로 측정되며, 개발자의 작업 흐름을 끊는다고 주장한다.

2. AI는 검증 문제를 더 크게 만든다

AI 덕분에 이전보다 더 많은 PR과 더 큰 PR이 만들어지고, 이들에도 결함이 있을 수 있다는 것이 화자의 문제 정의다. 이에 따라 비용이 개발 생명주기의 오른쪽, 즉 리뷰·검증·운영 단계로 이동한다고 설명한다.

선택지는 두 가지로 제시된다. 모든 PR을 개발자가 꼼꼼하게 검토해 속도를 늦추거나, 형식적으로 승인해 운영 장애를 감수하는 것이다. 화자는 어느 쪽이든 개발자 만족도와 기대 생산성이 낮아진다고 주장한다.

이 대조는 발표를 선명하게 만들지만, 사람 검토와 형식적 승인 사이의 다른 운영 방식까지 모두 배제하는 완전한 선택지 목록은 아니다.

3. Gitar가 제시한 에이전트 검증

PR이 생성되면 에이전트가 리뷰하고 문제와 줄별 의견을 게시한다. 사용자는 자체 규칙과 사용자 정의 검사를 추가하고 별도 자동화 작업을 실행할 수 있다. 해결되지 않은 리뷰 지적이 있으면 병합을 차단하도록 구성할 수도 있다.

에이전트는 CI 실패의 근본 원인을 요약한다. 화자는 특히 플래키 테스트를 잘 찾으며, 규칙에 따라 이를 자동으로 재시도할 수 있다고 말한다.

리뷰 지적이나 CI 실패는 요청에 따라 수정할 수 있고, 설정에 따라 모든 문제가 해결되어 그린 PR이 될 때까지 자동 반복할 수 있다. 마지막에는 사용자가 정한 규칙과 조건에 따라 자동 승인과 자동 병합을 수행한다.

4. 자동화 권한을 넓히는 순서

화자가 설명한 사용자 여정은 다음 순서를 따른다.

  1. 에이전트 리뷰를 받고 정확성과 중요성을 관찰한다.
  2. 신뢰가 형성되면 미해결 지적이 있는 PR을 차단하도록 한다.
  3. 자동 수정 기능으로 리뷰 문제와 CI 실패를 해결하게 한다.
  4. 특정 규칙에서 자동 승인과 자동 병합을 허용한다.

화자는 시간이 지나며 신뢰와 자동화 수준이 함께 올라가고 더 많은 가치를 얻는다고 말한다. 그러나 사용자 규모와 단계별 성과 지표는 제시하지 않는다.

5. 플랫폼 팀과 리더십을 위한 분류

모든 PR을 처리하면서 CI 실패를 테스트 불안정성, 기반 시설 문제, 다른 실패 유형으로 분류할 수 있다고 설명한다. 플랫폼 팀은 반복되는 실패가 어디서 생기는지 보고 테스트 안정성이나 기반 시설을 개선할 수 있다.

PR도 기능 개발, 문제 수정, 잡무, 리팩터링 등의 유형으로 분류한다. 화자는 이 자료가 개발 조직 전체에서 어떤 작업이 이뤄지는지 파악하려는 리더십 팀에 유용하다고 말한다.

분류 정확도의 평가 방식, 사람이 교정하는 절차, 분류를 성과 평가에 사용할 때의 위험은 전사에서 다뤄지지 않는다.

6. 내부 아키텍처의 세 구성 요소

화자는 흥미로운 구성 요소가 세 가지라고 말하고 실제로 다음 세 항목을 열거한다. 열거 개수와 제시된 이름 수 사이의 충돌은 없다.

  • 컨트롤 플레인: PR 작업 흐름을 처리하는 오케스트레이션 층.
  • 에이전트 런타임 또는 하네스: 다중 에이전트 실행, 문맥·메모리 관리, 도구 호출, 연동을 담당하는 자체 실행 환경.
  • LLM 프록시: 여러 모델로 요청을 보내고 장애 시 다른 경로를 사용하는 층.

자체 하네스로 검증 사례에 맞게 토큰 비용, 정밀도, 에이전트의 탐지 범위를 최적화했다고 말한다. 화자는 이를 바탕으로 PR당 고정 가격에서 결과를 사실상 보장할 수 있다고 주장한다. 보장 대상, 예외, 서비스 수준 조건은 제시되지 않는다.

7. SonarQube와 프로그램 분석

화자는 Gitar가 약 한 달 전 Sonar에 인수되어 현재 Sonar의 일부라고 말했다. 발표일이 제공되지 않았으므로 업로드일인 2026년 10월 13일을 기준으로 실제 인수일을 계산해서는 안 된다.

Gitar와 SonarQube의 통합은 진행 중이라고 표현한다. 결합 대상으로는 오염 분석, 제어 흐름 분석, 데이터 흐름 분석, 소프트웨어 구성 분석이 제시된다. 화자는 에이전트 방식과 이러한 전통적 분석을 결합하면 각각을 단독으로 쓸 때보다 정밀도와 탐지 범위가 좋아질 것이라고 전망한다.

발표가 제시한 전체 성과는 품질과 보안 향상, 빠른 배포, 개발자 생산성과 만족도 향상, 플랫폼 팀의 영향력 확대다. 하지만 비교 수치와 독립 검증 자료가 없으므로 화자의 제품 성과 주장으로 보존해야 한다.

전체 전사 펼치기

시작하겠습니다. 여러분, 안녕하세요. 저는 Ali이고 Gitar AI의 공동 창업자 중 한 명입니다. 약 한 달 전 Sonar에 인수되기 전까지는 CEO였고, 이제 저희는 Sonar의 일부가 되었습니다. 지난 며칠 동안 AI 시대에 검증이 얼마나 중요한지 많이 들으셨을 텐데요. 오늘은 코드와 코드 검증에 초점을 맞춰 이야기하겠습니다.

거의 모든 소프트웨어 팀에는 중앙 집중식 검증 단계가 있으며, 기본적으로 CI와 코드 리뷰로 구성됩니다. 엔지니어링 조직을 확장할수록 이 단계는 특히 AI 시대에 매우 중요한 역할을 합니다. 우선 이 단계는 보안, 규정 준수, 코드 품질을 비롯한 모든 품질 게이트를 중앙에서 강제합니다.

변경 사항을 프로덕션에 배포하기 위한 핵심 경로에 있으므로, 빠를수록 항상 좋습니다. 하지만 엔지니어링 규모를 키우면 이것이 문제가 됩니다. 빌드와 작업의 실행 시간이 길어지고, 여러 사이트와 지역에 걸친 팀의 비동기 리뷰 흐름이 생기며, 조직이 성장할수록 자연스럽게 모든 과정이 느려집니다.

또한 이 단계에는 개발자 인프라 비용을 상당히 많이 쓰게 됩니다. 조직이 커짐에 따라 통합하고 확장해야 하는 비싼 도구가 많고, 이 모든 것이 매우 비싼 인프라에서 실행됩니다. 이런 이유로 이 단계는 플랫폼 조직이나 플랫폼 팀의 주요 관심사가 되는 경우가 많습니다.

이 단계에서 발생하는 모든 종류의 장애는 매우 비쌉니다. 장애가 발생하면 일반적으로 시간과 일 단위로 측정되는 외부 루프(outer loop)가 생깁니다. 장애에는 큰 비용이 듭니다. 개발 속도가 실제로 크게 느려집니다. 개발자 시간을 잃고, 여기에 몰입 상태(flow state)가 깨지는 데 따른 차질까지 더해집니다.

최적화하는 것 역시 매우 어렵습니다. 세분화된 시스템이 많고, 이 시스템들이 맞춤형 설정과 스크립트로 통합되어 있습니다. 게다가 보통 인원이 제한된 플랫폼 조직이 이 모든 시스템을 계속 운영하려고 합니다.

이 모든 문제를 AI로 해결하려는 것 역시 복잡합니다. 다양한 비동기 상호작용, 팀 워크플로, 도구 간 통합 등을 포함하는 복잡한 워크플로 오케스트레이션이 필요하기 때문입니다.

사실 AI는 문제를 더욱 악화시킵니다. 이제 AI 덕분에 이전보다 훨씬 많은 PR이 생성되고 있으며, 더 큰 PR도 생성됩니다. 그리고 그 모든 PR에는 결함이 있을 수 있습니다.

개발 생명 주기에서 발생하는 비용이 오른쪽으로 이동하고 있습니다. 검토해야 할 코드가 훨씬 많아지고, 프로덕션에서 장애가 발생할 가능성도 훨씬 커졌습니다. 여기서 선택지는 쉽지 않습니다. 속도를 늦추고 개발자들에게 모든 PR을 매우 신중하게 검토하도록 요청하거나, PR을 대충 승인하고 프로덕션 장애의 위험을 감수해야 합니다. 어느 쪽이든 개발자 만족도와 정서는 낮아지고, 기대했던 것보다 생산성도 훨씬 떨어집니다.

그렇다면 답은 무엇일까요? 물론 AI를 더 사용하는 것입니다. 바로 검증에 에이전트 방식(agentic approach)을 적용하는 것이며, 이것이 저희가 Gitar에서 구축했고 이제 Sonar의 일부로도 제공하는 기능입니다. 기본적으로 저희는 모든 검증 단계를 완전히 자동화하고, 바로 병합할 수 있거나 자동으로 병합할 수 있는 통과 상태의 PR을 제공하는 에이전트를 만들었습니다. 어떻게 작동할까요?

먼저 PR을 생성하면 에이전트가 PR을 검토하고 이슈와 인라인 댓글을 게시합니다. 여기까지는 놀랍지 않습니다. 하지만 저희의 목표는 UX를 처리하는 방식과 실제로 중요하고 진짜인 이슈를 게시하는 방식 모두에서 이 경험에 불필요한 잡음이 최대한 없도록 만드는 것이었습니다.

자체 규칙으로 리뷰를 맞춤 설정하고, 자체 커스텀 검사를 추가하며, 자체 커스텀 워크플로 자동화를 실행할 수 있습니다. 해결되지 않은 코드 리뷰 발견 사항이 하나라도 있으면 병합을 차단하도록 시스템을 구성할 수도 있습니다.

또한 CI 장애를 분석하고 근본 원인의 요약을 게시합니다. 특히 불안정한 테스트(flaky test)를 매우 잘 찾아냅니다. 원한다면 불안정한 테스트를 자동으로 재시도하는 규칙도 설정할 수 있습니다.

이는 매우 인기 있는 기능입니다. 코드 리뷰 이슈나 CI 장애, 즉 CI에서 발생하는 모든 종류의 장애를 자동으로 수정할 수도 있습니다. 에이전트가 직접 수정하고 자신이 제기한 모든 이슈를 해결할 수 있습니다. 특정 이슈를 수정하라고 요청할 수도 있고, 더 흥미롭게는 PR의 모든 이슈가 수정되고 병합 가능한 통과 상태의 PR이 될 때까지 자동으로 반복하도록 설정할 수도 있습니다.

마지막으로 통과 상태인 PR을 자동으로 승인하고 병합할 수 있습니다. PR이 에이전트에 의해 자동 승인되고 자동 병합되는 시점을 제어하는 규칙과 조건을 정의할 수 있습니다.

저희 사용자들 사이에서 매우 흥미로운 추세가 나타나고 있습니다. 사용자가 시스템을 사용하고 AI의 정확성을 신뢰하게 되면서, 완전히 자동화된 PR을 향해 나아가는 뚜렷한 흐름이 보입니다.

사용자들은 완전 자동화를 향해 단계적으로 나아갑니다. 먼저 리뷰를 받고 그 결과에 만족합니다. 리뷰의 정확성을 신뢰하게 됩니다. 리뷰가 정확할 뿐 아니라 정말 중요한 이슈도 제기한다는 사실을 확인합니다. 그런 다음 에이전트가 PR을 차단할 수 있도록 허용해 에이전트에 실질적인 권한을 부여합니다.

코드 리뷰나 CI 장애로 발생한 모든 이슈를 자동으로 수정하고 PR을 통과 상태로 만드는 자동 수정 기능을 사용하기 시작합니다. 이제 나타나기 시작한 정말 흥미로운 도약은 에이전트가 PR을 자동으로 승인하고 병합하는 조건을 정의하는 규칙을 사용자들이 설정하는 것입니다.

시간이 지나 시스템에 대한 신뢰가 쌓이면 더 많은 자동화 수준이 열립니다. 자동화와 신뢰 수준이 높아질수록 시스템에서 더 많은 가치를 얻습니다.

시스템이 모든 PR을 AI로 처리하기 때문에 새로운 유형의 인사이트도 발견할 수 있습니다. 예를 들어 플랫폼 팀에 매우 유용한 인사이트 중 하나는 주요 CI 장애의 분류입니다. CI 시스템에서 장애가 발생하는 지점은 어디인가요? 개발자들은 어디에서 장애를 겪고 있나요? 테스트의 신뢰성을 개선해 해결해야 하는 불안정성 문제인가요, 아니면 해결해야 하는 인프라 문제인가요? 또는 개발자들이 겪는 다른 종류의 장애인가요? 이는 플랫폼 팀에 매우 유용합니다.

AI로 활성화된 인사이트의 또 다른 예로 PR 분류가 있습니다. 배포된 PR을 기준으로 엔지니어링 팀 전체에서 정확히 어떤 일이 일어나고 있나요? 이는 리더십 팀에 매우 유용합니다. 예를 들어 PR 중 몇 퍼센트가 기능 개발에 사용되고 있으며, 몇 퍼센트가 이슈 수정, 잡일, 리팩터링 등에 사용되고 있나요?

시스템 내부를 보면 Gitar를 구성하는 여러 컴포넌트가 있습니다. 여기에는 세 가지 흥미로운 요소가 있습니다. 하나는 PR 워크플로를 처리하는 오케스트레이션 계층 역할을 하는 컨트롤 플레인(control plane)입니다.

그다음은 에이전트 런타임(agent runtime), 즉 하네스(harness)입니다. 저희는 멀티 에이전트 실행, 컨텍스트 관리, 메모리 관리, 도구 호출, 모든 통합 등을 처리하는 자체 하네스를 구축했습니다. 자체 에이전트 하네스를 갖춘 덕분에 검증 사용 사례에 맞게 특별히 최적화하고, 토큰 비용과 에이전트 자체의 정밀도 및 커버리지를 최적화할 수 있었습니다.

이를 통해 매우 높은 품질의 결과를 제공하면서도 PR당 고정된 가격으로 결과를 사실상 보장할 수 있습니다. 또한 여러 모델 간 라우팅과 장애 조치(failover) 같은 기능을 처리하는 LLM 프록시도 있습니다.

이제 저희가 Sonar의 일부가 되었으므로 Gitar와 SonarQube를 통합하고 있습니다. 검증에 에이전트 방식을 적용하는 것과 프로그램 분석을 결합할 수 있는 기회가 매우 많습니다. 에이전트를 오염 분석(taint analysis), 제어 흐름 분석(control flow analysis), 데이터 흐름 분석(data flow analysis), 소프트웨어 구성 분석(software composition analysis)과 같은 기능과 결합하는 것입니다. 이렇게 하면 전통적인 접근 방식과 에이전트를 함께 사용할 수 있습니다.

저희는 이 분야에 엄청난 기회가 있다고 생각하며, 이를 결합하면 정말 훌륭한 가격대에서 훨씬 더 높은 정밀도와 훨씬 더 넓은 커버리지를 얻을 수 있다고 생각합니다.

저희가 확인하고 있는 전반적인 결과와 가치는 훨씬 더 나은 품질과 훨씬 더 높은 보안입니다. 특히 AI가 생성한 코드에서 그렇습니다. 또한 모든 자동화를 통해 제공 속도도 빨라집니다.

PR에서 곧바로 승인 및 병합된 PR로 이어지며, 개발자의 생산성과 정서도 훨씬 높아집니다. 실제로 코드를 검토하고 프로덕션에서 무슨 일이 일어나는지 걱정하는 데 쓰는 시간은 줄어들고, 확신은 커집니다. 자동화가 많고 반복적인 수작업이 줄어들기 때문에 개발자 정서도 훨씬 좋아집니다.

마지막으로 저희가 플랫폼 팀을 위해 구축한 기능은 이 소프트웨어 개발 생명 주기의 핵심 부분에서 문제를 수정하고, 맞춤 설정을 추가하며, 인사이트를 확인할 수 있는 훨씬 더 큰 영향력을 제공합니다.

마무리하자면 PR 검증은 매우 중요하며, AI 시대에는 더욱 그렇습니다. 하지만 AI는 검증을 마찰 지점으로 만들고, 저희가 구축한 Gitar는 이 단계를 자동화해 PR 검증을 완전히 자동화하고 PR 생성부터 병합까지 이어지도록 합니다.

이렇게 하면 이러한 마찰이 완전히 제거되고, AI로 코드를 생성하는 속도를 따라갈 수 있습니다. 마지막으로 에이전트 기반 검증과 알고리즘 기반 프로그램 분석을 결합하면 어느 한쪽만 사용하는 것보다 훨씬 더 나은 결과를 얻을 수 있을 것이라고 생각합니다.
