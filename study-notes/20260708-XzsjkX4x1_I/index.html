DoorDash가 전 직원에게 Claude Code를 제공했습니다

DoorDash는 Claude Code와 Cowork를 단순 개발 도구가 아니라 전사 생산성 인프라로 보고, 개발·보안·CI/CD·리뷰·조직 프로세스까지 함께 바꾸고 있다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
AI 활용 역량의 하한선 높이기 일부 고수만 쓰는 도구가 되면 회사 전체 생산성은 크게 안 오른다 전 직원이 최소한 AI를 업무 도구로 쓰게 만드는 것이 핵심
Claude Code 개발자가 터미널에서 AI 에이전트에게 코드 작성·수정·테스트를 맡기는 방식 “직접 코딩”보다 “AI에게 일을 시키고 검증”하는 일이 중요해짐
Cowork 이메일, 캘린더, 슬랙 등 지식 업무 도구와 연결되는 AI 업무 도우미 비개발자도 AI 생산성 향상을 체감할 수 있음
처리량(Throughput) AI 도입 효과를 보는 대표 지표 같은 인원으로 더 많은 기능·수정·마이그레이션을 더 빨리 처리
CI/CD 병목 코드 작성 속도가 빨라지면 병목은 배포·리뷰·보안으로 이동한다 AI 도입은 코딩만이 아니라 배포 파이프라인 재설계까지 포함
보안 가드레일(Guardrails) AI 도구를 빠르게 열어도 보안은 타협할 수 없다 보안팀과 초기부터 협업해야 전사 도입이 가능
작성된 산출물(Written artifacts) AI 사용 노하우를 조직 전체로 확산하는 가장 확장성 높은 방법 성공·실패 사례를 문서화하면 사람도 AI 에이전트도 재사용 가능
에이전트 친화적 코드베이스 AI가 이해하기 쉬운 규칙과 문서가 있는 코드 환경 아키텍처 원칙을 마크다운으로 남기면 AI 코드 품질이 좋아짐
작은 팀 AI 시대에는 3~5명 팀도 큰 일을 빠르게 처리할 수 있다 조율 비용이 적고 개인별 소유 영역이 명확할수록 속도가 난다
AI 챔피언(AI champions) 각 부서에서 자발적으로 AI를 잘 쓰는 사람 현장 병목을 가장 잘 아는 사람이 자동화 기회를 찾는다

내가 모를 만한 것 / 처음 보는 것

  • Claude Code — Anthropic의 코딩 에이전트. 터미널(Terminal)에서 실행해 코드 작성, 수정, 테스트, 리팩터링을 시킬 수 있다.
  • Cowork — Claude를 이메일, 캘린더, 슬랙 같은 지식 업무 도구에 연결해 업무 자동화를 돕는 제품군.
  • 워크트리(Worktree) — 하나의 깃 저장소(Git repository)에서 여러 작업 공간을 만들어 충돌 없이 병렬 작업하는 기능.
  • CI/CD — 지속적 통합·지속적 배포(Continuous Integration / Continuous Delivery). 코드가 안전하게 합쳐지고 배포되도록 하는 자동화 절차.
  • AI 코드 리뷰 에이전트(AI code review agent) — 사람이 리뷰하기 전에 AI가 코드 품질, 보안, 규칙 위반 등을 확인하는 도구.
  • Agent SDK — AI 에이전트를 제품이나 내부 도구에 붙이기 위한 개발 키트.
  • MCP 통합(MCP integration) — 외부 도구나 데이터 소스를 AI 모델과 연결하는 방식. 잘못 설계하면 토큰만 많이 쓰고 효과가 없을 수 있다.
  • 토큰 예산(Token budget) — AI 모델 사용량에 대한 예산. 많이 실험하려면 회사가 충분한 사용 한도를 열어줘야 한다.
  • QBR — 분기별 비즈니스 리뷰(Quarterly Business Review). 영업 조직이 고객·가맹점 성과를 정리하는 업무.
  • 픽셀 퍼펙트(Pixel-perfect) — 디자이너가 의도한 화면과 실제 구현 화면이 거의 완벽히 일치하는 상태.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. DoorDash는 Claude Code를 2025년 어느 시점에 도입했다 — 실제 큰 변곡점은 2025년 말 또는 2026년 초로 본다.
  2. 화자는 Claude Code를 쓸 때 직접 코드를 쓰지 않는 것을 목표로 삼았다 — AI에게 최대한 작성하게 하고 사람은 지시·검증에 집중한다.
  3. 여러 저장소(Repository)와 여러 세션(Session)을 동시에 돌린다 — 같은 저장소에서 충돌을 줄이기 위해 워크트리(Worktree)를 사용한다.
  4. 한때는 로컬 개발 환경 설정을 AI가 제대로 이해하지 못해 프로덕션 배포까지 못 갔다 — 최신 모델에서는 같은 시도가 “그냥 작동”했다.
  5. 한 사람이 5개 언어로 프로덕션 코드를 배포할 수 있었다 — AI 덕분에 언어 장벽이 낮아졌다.
  6. 어떤 코드 마이그레이션은 과거라면 엔지니어 4명이 한 분기 걸릴 일을 1명이 3주 만에 처리했다.
  7. 팀에 “AI로 프로젝트 기간을 3~5배 단축해보라”는 제약을 줬다 — 이 제약이 병목을 드러내는 도구가 된다.
  8. 성공 사례에서 테크 리드는 코드베이스 원칙을 수십 개, 약 50개 이상 마크다운(Markdown) 파일로 정리했다 — 에이전트가 이를 참조해 더 좋은 코드를 작성했다.
  9. 이상적인 실험 단위는 3~5명 팀으로 언급된다 — 작은 팀이 AI 속도를 가장 잘 흡수한다.
  10. 지식 업무에서는 전 직원 생산성이 10%만 올라가도 회사 규모상 큰 가치가 있다고 본다.

# 섹션 요지
1 전사 AI 역량의 하한선 높이기 AI를 채팅창이 아니라 업무 시스템과 연결된 도구로 쓰게 만든다
2 창업자도 다시 프로덕션 코드를 배포 Claude Code 덕분에 오래 코딩을 멈췄던 리더도 다시 실제 코드를 낸다
3 AI 코딩의 변곡점 최신 모델은 예전엔 실패하던 환경 설정·추론을 스스로 해결하기 시작했다
4 처리량 증가와 새 병목 코딩 속도가 오르면 리뷰, 보안, CI/CD가 새 병목이 된다
5 보안과 빠른 도입의 균형 보안팀을 배제하지 않고, 빠른 조달·검토 프로세스를 따로 만든다
6 성공 사례 확산 방식 AI 챔피언과 작성된 산출물로 팀 간 학습을 전파한다
7 에이전트 친화적 조직 설계 작은 팀, 표준화된 스킬, 마크다운 원칙이 AI 활용도를 높인다
8 리더와 신입에게 주는 조언 리더는 직접 써보고, 신입은 새 패러다임으로 회사를 놀라게 해야 한다

1. 전사 AI 역량의 하한선을 높이는 전략

DoorDash가 Claude Code와 Cowork를 전사적으로 제공한 이유는 단순히 개발자 생산성을 높이기 위해서만이 아니다. 핵심 목표는 회사 전체의 AI 활용 역량(AI fluency) 하한선을 높이는 것이다.

이미 일부 직원은 엔지니어가 아니어도 Claude Code를 터미널에서 사용하고, 직접 코드를 작성·배포하며 빠르게 성과를 내고 있었다. 반면 경영진을 포함한 많은 사람들은 AI의 중요성은 이해하지만 여전히 AI를 “채팅창” 정도로만 보고 있었다.

화자는 사람들이 다음과 같은 연결을 경험하면 눈이 달라진다고 말한다.

  • Gmail과 연결
  • Google Calendar와 연결
  • Slack과 연결
  • 업무 맥락을 이해한 상태에서 지식 노동 보조

즉, AI는 질문 답변 도구가 아니라 업무 흐름 안에 들어오는 생산성 레이어가 된다.

2. 창업자도 Claude Code로 다시 프로덕션 코드를 배포하다

화자는 어릴 때 우연히 코딩 캠프에 참여하면서 코딩을 처음 접했다. 원래는 형을 위한 캠프였지만, 본인이 오히려 코딩을 익히게 되었다.

DoorDash 초기인 2013년에는 스탠퍼드 기숙사에서 직접 코드를 작성했다. 그러나 회사가 커지면서 코딩에서 멀어졌다. 그러다 Claude Code를 사용하면서 오랜만에 다시 DoorDash 코드베이스에 실제 프로덕션 코드를 배포하게 되었다.

그가 세운 개인 목표는 분명했다.

“수동으로 코드를 직접 쓰지 않겠다.”

대신 Claude Code 에이전트에게 코드를 작성하게 하고, 자신은 목표를 정하고 결과를 검토하는 방식으로 일했다. 보통 터미널을 사용하고, 때로는 데스크톱 앱도 실험한다. 여러 저장소와 여러 세션을 동시에 열어 작업하며, 같은 저장소에서 충돌을 피하려고 워크트리(Worktree)를 사용한다.

3. AI 코딩은 “몇 달 뒤 다시 해보면 된다”는 방식으로 바뀌었다

초기에는 Claude Code로 프로덕션 기능을 만들려고 했지만 실패했다. 이유는 AI 에이전트가 로컬 개발 환경 설정을 제대로 이해하지 못했기 때문이다.

하지만 2026년 초쯤 같은 시도를 다시 했을 때는 그냥 작동했다. 최신 모델이 환경 설정, 의존성, 오류 해결을 스스로 처리할 수 있는 수준으로 발전했기 때문이다.

예전 소프트웨어 개발에서는 같은 아이디어를 계속 반복 시도하는 것은 나쁜 습관이었다. 학습 없이 같은 일을 반복하는 셈이기 때문이다. 하지만 LLM 시대에는 다르다.

같은 아이디어라도 더 강력한 새 모델로 다시 시도하면 갑자기 성공할 수 있다.

그래서 DoorDash는 팀들에게 기존 방식을 버리는 법도 배우라고 말한다. 엔지니어는 자신이 만든 설정, 도구, 워크플로에 애착을 갖기 쉽다. 하지만 모델 능력이 빠르게 바뀌기 때문에, 기존 방식을 계속 붙잡기보다 새 능력에 맞춰 다시 설계해야 한다.

4. 코딩 속도가 오르면 병목은 CI/CD, 리뷰, 보안으로 이동한다

Claude Code 도입 후 DoorDash는 조직 전반에서 처리량(Throughput)이 크게 늘었다. 하지만 코드 작성 속도가 빨라지자 새로운 문제가 생겼다.

  • 코드 병합(Merge)이 오래 걸림
  • CI/CD 프로세스가 병목이 됨
  • 코드 리뷰 부담이 커짐
  • 보안 이슈가 더 많이 발견됨
  • 여러 에이전트 작업으로 문맥 전환(Context switching)이 심해짐

DoorDash는 이 문제를 해결하기 위해 AI 코드 리뷰 에이전트에 투자했다. 보안 관련 문제도 AI가 사전에 탐지하도록 만들고 있다.

화자는 이를 약간의 고양이와 쥐 게임(Cat and mouse game)이라고 표현한다. AI가 코드 생산량을 늘리면, 그만큼 검증·보안·자동화도 AI로 강화해야 한다.

5. 빠른 도입과 보안은 같이 가야 한다

DoorDash는 2025년에 Claude Code를 도입했다. 중요한 점은 IT 보안팀과 매우 긴밀히 협력했다는 것이다.

AI 도구 시장은 빠르게 바뀌므로, 기존의 느린 조달·검토 방식으로는 직원들이 최신 도구를 제때 쓰기 어렵다. 그래서 DoorDash는 AI 도구에 대해 별도의 조달(Procurement)과 리뷰 프로세스를 만들었다.

다만 원칙은 명확하다.

보안은 타협 대상이 아니다.

빠르게 접근권을 열어주되, 보안팀이 어떤 도구가 들어오고 어떤 접근 권한을 갖는지 계속 살펴보게 했다. 즉, 실험 자유와 보안 가드레일을 동시에 설계한 것이다.

6. 성공과 실패를 문서화해야 조직 전체가 배운다

DoorDash는 처음에는 도구를 사람들에게 열어주고, 누가 자연스럽게 잘 쓰는지 관찰했다. 이후 성공 사례를 찾아내 팀 내부의 옹호자, 즉 AI 챔피언(AI champions)으로 세웠다.

여기서 가장 강조되는 방식은 작성된 산출물(Written artifacts)이다.

성공 사례만 공유하는 것이 아니라 실패 사례도 공유해야 한다.

예를 들면:

  • 이 워크플로는 잘 작동했다
  • 이 MCP 통합은 토큰만 많이 쓰고 효과가 없었다
  • 이 방식은 코드 리뷰 병목을 줄였다
  • 이 자동화는 보안 이슈를 놓쳤다

문서화가 중요한 이유는 두 가지다.

  1. 사람이 읽고 따라 할 수 있다.
  2. AI 에이전트도 읽고 다음 작업에 활용할 수 있다.

7. 에이전트 친화적인 코드베이스와 작은 팀이 속도를 만든다

DoorDash는 AI 활용이 잘되는 팀의 공통점을 발견했다.

첫째, 작은 팀이 유리하다. 사람이 적을수록 조율 비용이 줄고, 각자가 맡은 영역을 더 명확히 소유할 수 있다.

둘째, 코드베이스를 에이전트 친화적으로 만들어야 한다. 한 성공 사례에서는 테크 리드가 특정 코드베이스의 아키텍처 원칙을 수십 개, 약 50개 이상 마크다운 파일로 정리했다. 에이전트가 코딩할 때 이 문서를 참조하니 결과가 훨씬 좋아졌다.

셋째, 팀 공통 스킬(Skills)을 표준화해야 한다. 예를 들어 모바일 개발 팀은 시뮬레이터를 띄우고 특정 흐름을 테스트하는 과정을 스킬로 만들어두었다. 예전에는 엔지니어가 수동으로 번거롭게 해야 했던 일이 이제는 에이전트가 백그라운드에서 실행할 수 있는 표준 작업이 된다.

8. AI 속도를 제대로 쓰려면 회사 프로세스도 바꿔야 한다

AI 코딩이 잘되는 영역은 단순 플랫폼 변경이나 코드 마이그레이션이다. 반면 사용자-facing 기능은 더 어렵다. 이유는 코드만의 문제가 아니기 때문이다.

  • 제품 방향 합의
  • 디자인 리뷰
  • 제품 리뷰
  • 출시 리뷰
  • 컴플라이언스
  • 여러 부서의 승인

이런 프로세스는 과거에는 필요했다. 하지만 AI로 개발 속도가 3배, 5배 빨라지면 기존 프로세스가 큰 마찰이 된다.

화자는 AI 속도를 활용하려면 엔지니어링만 바꿔서는 안 된다고 말한다. 제품, 디자인, 보안, 운영 등 크로스펑셔널 리더들이 함께 일하는 방식을 바꿔야 한다.

예를 들어 예전에는 엔지니어가 디자인을 픽셀 퍼펙트하게 맞추느라 많은 시간을 썼다. 이제는 엔지니어가 작동 가능한 상태까지 만들고, 디자이너가 직접 코드나 프로토타입에서 마무리하는 방식이 가능하다.

핵심 철학은 다음과 같다.

팀이나 개인이 더 자급자족(Self-sufficient)할수록 더 빠르게 움직인다.

9. ROI는 개발과 지식 업무에서 다르게 봐야 한다

개발 조직에서는 ROI를 비교적 측정하기 쉽다.

  • 코드 처리량 증가
  • 같은 프로젝트를 더 적은 인원으로 완료
  • 출시까지 걸리는 시간 단축
  • 고객이 실제 기능을 더 빨리 경험

물론 코드량 자체는 조작 가능한 지표라 완벽하지 않다. 하지만 방향성은 보여준다. 최종 성공 지표는 코드가 많이 병합되는 것이 아니라 고객 가치가 더 빨리 전달되는 것이다.

지식 업무에서는 아직 탐색 단계다. DoorDash는 두 가지로 본다.

  1. 모든 직원의 기본 업무 시간을 얼마나 절약하는가
  2. 부서별 핵심 워크플로를 자동화해 운영 효율을 얼마나 높이는가

예를 들어 영업팀이 수많은 가맹점과 QBR을 해야 한다면, AI가 자료 수집·정리·검증·일관성 유지에 큰 도움을 줄 수 있다.

10. 리더와 신입에게 주는 조언

엔지니어링 리더에게 주는 조언은 명확하다.

직접 AI를 써봐야 한다.

그래야 팀에게 AI 사용을 권할 수 있고, 엔지니어들이 느끼는 불안도 이해할 수 있다. 많은 엔지니어는 자신이 직접 짠 코드와 장인정신에 정체성을 둔다. AI 코딩은 이 정체성을 흔들 수 있다. 리더가 직접 경험해야 이 변화를 공감하고 이끌 수 있다.

또 하나의 조언은 계속 반복된다.

문서화하라.

성공 사례, 실패 사례, 원칙, 워크플로를 문서로 남기는 것이 대규모 조직에서 학습을 확산하는 가장 좋은 방법이다.

신입 개발자에게는 호기심을 유지하고 도구를 계속 실험하라고 조언한다. DoorDash 같은 회사는 AI 시대의 작업 방식에 익숙한 신입들이 기존 세대가 생각하지 못한 방식으로 기술을 활용해주기를 기대한다.

한 번에 세션 하나만 쓰나요, 아니면 여러 세션을 쓰나요?

여러 저장소(Repository)를 설정해두고, 한 저장소에서 여러 세션을 돌리고 싶으면 워크트리(Worktree)를 사용합니다. 이렇게 하면 충돌 없이 같은 저장소에서 작업할 수 있습니다. 보통 몇 개 세션을 동시에 돌리려고 합니다.

DoorDash 팀들에게도 기존 방식을 버리는 법을 배우라고 말하고 있습니다. 엔지니어들은 자신이 만든 작동하는 무언가에 강한 애착을 갖습니다. 하지만 모델과 역량이 바뀌면, 설정이든 직접 만든 에이전트든 빠르게 바뀌는 능력에 맞춰 다시 상상해야 합니다.

DoorDash에는 Claude Code를 언제 처음 도입했나요?

2025년 어느 시점에 Claude Code를 도입했고 사람들이 쓰기 시작했습니다. IT 보안팀과 매우 긴밀히 협력했습니다. AI 도구는 업계와 환경이 너무 빠르게 변하므로 특별한 조달(Procurement)과 검토 프로세스를 마련해야 한다고 봤습니다. 사람들이 거의 즉시 접근할 수 있게 하고 싶었습니다.

진짜 변곡점은 아마 올해 초나 작년 말쯤이었습니다. 그 이후 Claude Code 도입과 팀 처리량 사이에 상관관계를 보고 있습니다. 이는 임원 리더십의 지원과 IT 보안, 엔지니어링의 협업에서 비롯됐습니다. 가능한 도구에 사람들이 최대한 빨리 접근하게 하고, 초반에는 예산을 너무 엄격하게 보지 않고 사람들이 탐색할 수 있게 했습니다.

이렇게 새로운 도구와 새로운 업무 방식이 생겼을 때, 사람들이 안전하게 실험한다고 느끼게 하려면 어떻게 하나요?

초반에는 도구를 사람들에게 주고 얼리어답터(Early adopter)가 누구인지, 무엇이 잘 작동한다고 느끼는지 보자는 생각이었습니다. 이후 성공 사례, 특정 프로젝트나 잘한 사람들을 뽑아 팀 내 옹호자로 세웠습니다.

강조한 것 중 하나는 가능한 한 작성된 산출물(Written artifacts)을 만들게 하는 것입니다. 이런 것은 회사 전체에 공유할 수 있습니다. 조직 규모가 크기 때문에 균일하게 강제하기는 어렵지만, 각 팀이 자신만의 채널과 포럼을 가지고 성공과 한계를 편하게 공유하도록 장려하고 있습니다.

“이렇게 했더니 멋진 결과가 나왔다”는 것만큼이나, “이 워크플로를 시도했는데 작동하지 않았다”거나 “이 MCP 통합은 토큰을 많이 낭비했다”는 것도 중요합니다. 그런 것도 편하게 공유해야 합니다.

오늘날 DoorDash는 Claude Code를 어떻게 쓰고 있나요?

조직 전반에 꽤 널리 퍼져 있습니다. Claude Code를 직접 쓰거나, 다른 도구 안에서 Claude 모델을 쓰고 있습니다. 저희는 자동화에 더 많이 투자하고, 늘어난 처리량을 활용하려고 합니다.

마찰을 최대한 줄이려면 어떻게 하나요?

CI/CD에 투자하고, Claude를 사용해 AI 코드 리뷰 에이전트를 만들고 있습니다. 또 내부 플랫폼인 Flux를 만들었습니다. DoorDash 클라우드 안의 VM에서 보안 승인을 받은 Claude 세션을 띄울 수 있는 인프라입니다. 올바른 도구 접근 권한을 가진 Claude 세션을 클라우드에서 실행할 수 있습니다. AI 코드 리뷰 에이전트도 이 플랫폼 위에서 작동합니다.

Agent SDK 같은 건가요?

네. Agent SDK와 Claude 모델을 사용합니다. 이런 프레임워크가 내부 도구를 만드는 데 큰 도움이 됐습니다.

처음에는 코딩에서 시작해 병목을 하나씩 만나고, 다음 벽을 계속 허무는 방식이군요.

맞습니다.

저희는 디자이너도 실제 프로덕션 코드를 배포해보도록 목표를 세웠습니다. 100% 매끄럽지는 않았지만 방향은 좋았습니다. 디자이너가 소프트웨어 개발 프로세스에 직접 들어가 생각하게 만들었기 때문입니다. 지금은 좋은 팀일수록 디자이너와 제품 관리자(PM)가 소프트웨어 개발 사이클에 직접 들어와 있습니다.

이들도 Claude를 사용해 스스로를 강화합니다. 전체 팀에 던진 도전은 “AI를 사용해서 프로젝트를 3~5배 더 짧은 시간에 끝내보라”는 것이었습니다. 이런 제약을 두면 사람들이 어떤 문제에 부딪히는지 매우 선명하게 보입니다.

많은 부분은 코딩 에이전트를 어떻게 쓰는지, 가장 많이 성과를 내는 사람들의 학습을 모두가 얻을 수 있도록 표준화된 스킬(Skills)을 어떻게 쓰는지에 관한 것입니다. 어떤 엔지니어는 과거라면 엔지니어 4명이 한 분기 동안 했을 대규모 코드 마이그레이션을 혼자 3주 만에 했습니다. 다른 대형 제품도 일정이 절반 이상 줄어 출시 시점을 크게 앞당겼습니다. 이런 사례를 찾고, 무엇이 성공 요인이었는지 파악하고, 앞서 말한 것처럼 문서화하게 합니다.

지금은 몇몇 팀을 직접 골라 깊게 파고들게 하고, 무엇을 만들어내는지 보고 있습니다.

실험하면서 배운 경고나 교훈은 무엇인가요? 개발을 가속하는 데 효과가 있는 것과 없는 것은 무엇인가요?

확실한 것은 작은 팀이 큰 가속 요인이라는 겁니다. 각자가 하나 또는 몇 개의 영역을 소유할 수 있고, 서로 조율할 필요가 줄어듭니다. 또 하나의 좋은 교훈은 코드베이스를 에이전트 친화적으로 만들기 위해 사전 투자를 하는 것이 보상받는다는 점입니다.

한 성공 사례에서 테크 리드는 특정 코드베이스에 대해 자신이 중요하게 보는 아키텍처 원칙을 수십 개, 아마 50개 이상 적었습니다. 이를 GitHub 저장소 안의 마크다운 파일에 넣었습니다. 그러자 에이전트가 코딩할 때 이 원칙을 참조할 수 있었고, 매우 도움이 됐습니다.

또 도움이 된 것은 팀 전체에서 스킬을 표준화하는 것이었습니다. 예를 들어 모바일 개발에서는 시뮬레이터를 쉽게 띄우고 특정 워크플로를 테스트하는 스킬을 만들었습니다. 엔지니어가 직접 설정하면 매우 수동적이고 귀찮은 일을 이제는 호출해서 백그라운드에서 실행할 수 있습니다.

반대로 어려웠던 점은 사용자-facing 기능입니다. 단순 플랫폼 변경이나 코드 마이그레이션과 달리, 여러 부서의 동의가 필요합니다. 디자인 정렬, 제품 관점의 문제 정의, 제품 리뷰, 출시 리뷰, 디자인 리뷰 같은 프로세스가 필요합니다. 이런 프로세스는 과거에 정렬을 위해 중요했지만, 지금은 큰 마찰점이 되었습니다.

AI 속도를 제대로 활용하려면 엔지니어링 문제만이 아니라 회사 전체의 문제로 봐야 합니다. 크로스펑셔널 리더들도 일하는 방식을 바꾸는 데 동의해야 합니다. 제품 리뷰가 예전과 같은 방식으로 꼭 필요할까, 또는 아예 필요한가를 다시 물어야 합니다.

예전에는 엔지니어가 디자인을 픽셀 퍼펙트(Pixel-perfect)하게 만드는 데 많은 시간을 써야 했습니다. 이제 엔지니어가 작동 가능한 상태까지 만들고, 디자이너가 스스로 픽셀 퍼펙트하게 마무리할 수 있다면 매우 강력합니다. 일반적으로 팀이나 개인이 더 자급자족할수록 더 빠르게 움직인다는 것을 발견했습니다. 이것이 AI-forward한 방식을 장려할 때 밀고 있는 철학입니다.

그러면 프로세스를 줄이고, 디자인 문서와 리뷰도 줄이는 건가요?

네. 디자이너라면 프로토타입에서 직접 작업하고, 코드에서 직접 작업하는 겁니다. 많은 프로세스를 간소화하거나 다시 상상해야 합니다. 물론 어떤 프로세스는 중요한 이유가 있습니다. 컴플라이언스 관련 절차가 필요할 수도 있습니다. 하지만 팀에게 “일정을 3배 줄이려면 에이전트를 어떻게 활용해 자동화하거나 빠르게 만들 수 있을까”라고 물어야 합니다.

팀의 사고방식도 바뀌어야 합니다. 모두가 도메인 전문가일 필요는 없습니다. 오히려 코드베이스 전반을 유동적으로 움직이도록 장려해야 합니다. 모바일 엔지니어들도 이제 더 풀스택(Full stack)에 가까워지도록 장려합니다. 1년 전보다 훨씬 접근 가능해졌습니다.

물론 iOS 같은 영역에는 여전히 도메인 전문가가 필요합니다. 아키텍처, 메모리 관리, 지연 시간, 성능 같은 부분을 봐야 하니까요. 하지만 팀 전체가 iOS 전문가일 필요는 없습니다. 소수의 전문가가 게이트키퍼 역할을 하면서, 에이전트가 확인해야 할 것들을 만들거나 아키텍처 원칙을 마크다운 파일에 적어둘 수 있습니다. 그러면 더 많은 사람이 제너럴리스트(Generalist)로 코드베이스를 유동적으로 움직일 수 있습니다. 이것도 사람들이 익숙해져야 할 사고방식 변화입니다.

이런 작은 팀에 실험 공간을 주려면 어떤 사람들로 팀을 구성해야 하나요?

이런 임무를 주는 팀에는 실험하고 밀어붙여도 안전하다고 느끼게 하려 합니다. 그래서 제가 직접 관여하거나, 엔지니어링 및 인접 기능의 임원들에게 직접 관여하게 합니다. 특정 워크스트림에 대해 EVP 수준의 후원을 주어, 막히는 것이 있으면 높은 리더십의 지원을 받을 수 있게 합니다.

초반에 잘 안 됐던 것은 사람들에게 이런 일을 하라고 하면서도 기존 업무의 제약 안에 그대로 두는 것이었습니다. 그러면 금방 포기합니다. 그래서 단지 토큰 예산을 주는 것이 아니라, 코드 생성 외에 무엇이 방해되는지 크로스펑셔널 리더십 팀에 올리라고 권한을 줘야 합니다. 이것이 사람들이 더 안전하다고 느끼게 하는 데 효과적이었습니다.

아직 이를 어떻게 확장할지는 배우는 중입니다. 이상적으로는 성공 사례가 나타나면 그 문서를 여러 리더에게 공유하고, 사람들이 자연스럽게 실천을 도입하는 것입니다. 예전에는 코딩 속도가 전달 속도를 제한했고, 그것이 팀 구성, 조직 리뷰 프로세스, 임원 체크인 주기 등을 결정했습니다.

이제는 엔지니어링이 너무 빨라졌기 때문에 이 모든 것을 다시 생각하게 됩니다. 3~5명 팀이 할 수 있는 일이 훨씬 많아졌습니다. 그 단위가 가능한 한 빠르게 움직이도록 투자해야 합니다. 그 단위가 3~5배 빨라지면 조직 전체에는 완전히 게임 체인저가 됩니다.

ROI는 어떻게 보고 있나요? 초반에는 가능한 많은 토큰을 주고 실험하게 했고, 이제는 ROI도 생각한다고 했습니다.

엔지니어링에서는 비교적 명확합니다. 코드 처리량(Code throughput)이 완벽한 지표는 아니고 조작될 수 있지만, 방향성은 어느 정도 맞습니다. 같은 프로젝트를 더 적은 사람으로 더 빨리 끝낼 수 있다면, 현재 인력이 가능한 한 많이 이 도구를 쓰게 해야 합니다.

지식 업무(Knowledge work)는 아직 매우 초기입니다. Cowork에는 이메일 분류 같은 사용 사례 외에도 강력한 가능성이 많지만 이제 표면을 긁는 단계입니다. 예를 들어 영업팀이 수만 개 가맹점과 QBR을 해야 한다면 수작업이 많습니다. AI로 이를 간소화하고 더 정확하고 검증 가능하며 일관성 있게 만들 수 있다면 매우 강력합니다.

지금은 두 가지 방식으로 봅니다. 하나는 기본선 높이기입니다. 모든 사람이 해야 하는 작업에서 평균적으로 얼마나 시간을 절약하는가입니다. 다른 하나는 부서나 도메인별로 특정 워크플로를 찾아 자동화함으로써 그 부서를 훨씬 효율적으로 운영할 수 있는가입니다. 지식 업무 영역은 솔직히 아직 탐색 단계입니다.

코딩에서는 코드량 증가, 코드 처리량, 전달 속도, 사람들의 여유 시간을 비교적 쉽게 측정할 수 있겠군요.

맞습니다. 하지만 엔지니어링만의 문제는 아닙니다. 디자인과 크로스펑셔널 지원도 포함됩니다. 결국 우리는 고객 가치가 더 빨리 전달되기를 원합니다. 코드 병합만이 아니라 고객이 실제 제품을 더 빨리 보는 것을 증명할 수 있다면, 그것이 최종 성공 지표입니다.

지식 업무는 아직 파악 중이고 도메인 의존적입니다. 전 직원이 이 도구로 10%만 더 생산적이 되어도 회사 규모에서는 엄청난 가치입니다. 기본선을 높이는 가치도 있고, 도메인 특화 워크플로 탐색도 많이 남아 있습니다.

혁신이 실제로 일어나는 방식과도 연결되네요. 위에서 “이 워크플로를 자동화하라”고 하면 잘못된 워크플로나 잘못된 사람을 고를 수 있습니다.

맞습니다.

하지만 모두에게 실험할 자유를 주면, 어떤 사람이 여기서 무언가를 자동화하고 다른 사람이 저기서 무언가를 자동화합니다. 리더는 그것이 병목인지조차 몰랐을 수도 있습니다.

맞습니다. 그래서 내부적으로 AI 챔피언(AI champions)이라고 부르는 사람들을 찾고 있습니다. 영업, 마케팅, 운영, 지원 같은 각 도메인에서 자연스럽게 떠오르는 사람, 여가 시간에도 이것을 하고 도구에 끌리며 생산적으로 쓰는 사람을 찾습니다. 그들이 자기 도메인의 큰 고통점이 무엇인지 파악하도록 돕습니다. 저는 그걸 모릅니다.

그리고 그 워크플로를 에이전트로 간소화하거나, 동료들이 공통 스킬을 사용해 더 효율적으로 일하게 만들 수 있는지 봅니다.

DoorDash는 꽤 이른 시점부터 코딩 인터뷰에 AI를 사용한 것으로 유명합니다. 이런 환경에서 성공하고 실험을 즐기는 사람은 어떻게 찾나요?

저희 생각은 도구를 주고 누가 자연스럽게 집어 드는지 보는 것입니다. 그런 사람들은 Slack 채널 등을 통해 자연스럽게 드러납니다.

그들이 말해주죠.
