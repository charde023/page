한 줄 요약

Claude Code를 잘 쓰려면 ① Claude가 요구사항을 직접 인터뷰하게 하고 ② Markdown 대신 HTML 명세로 합의하고 ③ DOM 데이터 계약 + Playwright MCP로 에이전트가 스스로 검증하게 만들어야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Claude가 사용자를 인터뷰하게 만드는 프롬프팅 요구사항은 사람이 미리 다 언어화하기 어렵다 ask_user_question 도구를 프롬프트에 명시해 Claude가 턴 바이 턴으로 끌어내게 함
HTML 명세 (Spec as HTML) 200줄 넘는 Markdown은 아무도 안 읽는다 HTML은 정보 밀도가 높고, 스크린샷 피드백·Playwright 연동이 쉬움
DOM 데이터 계약 (data-* 속성) 에이전트가 DOM을 스크레이핑하지 않아도 됨 컴포넌트가 자기 상태를 data-verify-unit 등 속성으로 퍼블리시
에이전트 친화적 검증 3계층 사람 / 브라우저 에이전트 / Headless CI를 같은 계약으로 커버 동일한 DOM 계약을 사람 대시보드·Claude Code·bun verify CI가 다 읽음
Storybook fixture + 불변식(invariants) 모든 컴포넌트의 알려진 상태를 사전 선언 schema, fixture, invariant 3종을 컴포넌트마다 정의
검증 영상 클립 기록 프런트엔드 변경 증거를 S3/공유로 보관 Playwright가 검증 스텝을 녹화 → 번들로 공유
/effort, /fast, auto mode Claude Code 기본 설정이 결과 품질을 바꿈 권장: auto mode + effort xhigh, Fast Mode는 스펙 반복에 유용
Bitter Lesson (Richard Sutton) 인간이 제약을 걸수록 AI 잠재력이 줄어든다는 원칙 모델이 더 잘 뽑아낼 수 있도록 제약을 줄이는 방향으로 워크플로우 설계

내가 모를 만한 것 / 처음 보는 것

  • Bitter Lesson (쓴 교훈) — Richard Sutton (강화학습의 아버지)이 주장: 사람이 규칙·제약을 하드코딩하는 것보다 데이터+컴퓨팅을 쏟아붓는 게 결국 이긴다. Claude Code 워크플로우에도 동일 원칙 적용.
  • ask_user_question 도구 — Claude Code에서 에이전트가 사용자에게 structured 질문을 던지는 내장 도구. 프롬프트에 명시해야 활성화됨.
  • DOM 데이터 계약 — React 컴포넌트가 data-verify-unit, data-total-done, data-active 같은 HTML 속성으로 현재 상태를 DOM에 노출. 에이전트가 React 내부를 모르고도 상태 읽기 가능.
  • Playwright MCP — Playwright를 MCP 서버로 연결하면 Claude Code가 브라우저를 직접 제어하며 검증 실행 가능.
  • Storybook fixtures — 컴포넌트의 "알려진 상태" 목록. 검증할 때 고정된 입력으로 예측 가능한 출력을 테스트.
  • headless 검증 — bun verify (또는 npm run verify) 로 브라우저 UI 없이 CLI에서 검증 매트릭스 실행 → CI 파이프라인에 삽입 가능.
  • CWC Workshops — "Claude with Code Workshops" 의 약자. Anthropic이 운영하는 실습 워크숍 시리즈.
  • Fast Mode — Claude Code의 응답 속도 최우선 모드(/fast). 비용이 더 들지만 스펙 반복 작업에 효과적.
  • auto mode — Claude가 상황에 맞는 모델을 자동 선택. 화자가 강하게 권장.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Arno는 Anthropic Applied AI Team의 아키텍트. 오늘 워크숍은 Tarek이 약 1.5주 전 샌프란시스코에서 발표한 내용을 기반으로 구성됨.
  2. Tarek이 퍼블리시한 블로그 포스트 제목: "The Unreasonable Effectiveness of HTML Files" — Markdown에서 HTML로 명세 형식을 전환하는 주장.
  3. HTML 명세 생성 시 Opus 4.7 사용 권장. 비전 모델이 이전 버전 대비 향상되어 스크린샷 피드백 해석 정확도가 높음.
  4. Markdown 파일이 200줄 초과되면 본인도 읽지 않고 동료도 읽지 않는다고 명시.
  5. effort 권장값: xhigh (max도 가능). /effort xhigh 로 설정.
  6. Fast Mode는 비용이 더 들지만 스펙을 빠르게 반복할 때 효과적. HTML 명세 작업에 특히 추천.
  7. "HTML 명세가 토큰 비효율적이지 않냐?"는 질문에 대한 답: 장기적으로 반복을 줄여서 오히려 절감. 단발성 토큰은 더 쓰더라도 좋은 명세 하나면 재작업이 준다.
  8. 검증 클립 녹화는 Claude Code 팀 내부 실무에서 이미 실제로 사용 중. 프런트엔드 변경마다 기록하며, 자동화 수준이 데모보다 더 높음.
  9. HTML 디자인 방향 4개를 Opus 4.7에게 생성시킨 예시 키워드: Brutalist, Tokyo, Fintech 스타일.
  10. 컴포넌트에 불변식 검증을 심을 때, 일부러 3 + 3 + 4 != 10 이 되도록 실패 케이스를 하드코딩해두고 에이전트가 발견하는 흐름을 시연.
  11. bun verify로 실행하면 테스트 매트릭스 자체는 통과하지만 (일부러 검증과 분리해둠), DOM 계약 기반 검증은 별도로 실패를 잡는다 — 테스트 통과 ≠ 검증 통과 의 차이를 명시적으로 보여줌.
  12. Sonnet으로 이 워크플로우를 돌리는 건 비추천. Opus 4.7을 써야 한다고 두 번 강조.

1. 에이전트 시대의 워크플로우 변화 필요성

모델이 강해질수록 에이전트가 더 오래, 더 복잡한 작업을 수행할 수 있다. 그런데 에이전트가 장시간 실행될수록 초반에 잘못된 방향으로 가면 토큰 소모가 커진다. 따라서 프런트로딩(frontloading) — 명세와 검증을 초반에 풍부하게 만드는 것 — 이 핵심이 된다.

Richard Sutton의 Bitter Lesson과 연결: 인간이 제약을 하드코딩하는 것보다 모델에게 맡기는 게 결국 낫다. 요구사항을 직접 전달하는 것보다 Claude가 인터뷰해서 끌어내도록 세팅하는 게 더 좋은 결과를 낸다.

2. Phase 1: 요구사항 인터뷰 프롬프팅

나쁜 프롬프팅 예시: "더 좋게 만들어줘 (make it better)" — 아무 도메인도, 방향도 없음.

좋은 프롬프팅 조건: - 관심 영역(도메인)을 명시하되 결과를 과도하게 규정하지 않음 - 청중(audience)을 구체화 - 오픈엔드 질문 방식으로 유도

핵심 메커니즘: 프롬프트에 ask_user_question 도구를 명시 → Claude가 탭으로 넘기며 구조화된 질문을 던짐 → 사용자가 답변 → Claude가 명세 생성. "bill splitting app" 예시에서 시연.

Claude Code 설정: - /fast — Fast Mode 활성화 - auto mode — 모델 자동 선택 (강력 권장) - /effort xhigh — 노력 수준 설정

3. Phase 2: HTML 명세로 디자인 방향 합의

Markdown 파일의 한계: 200줄 넘으면 본인도, 동료도 읽지 않는다.

HTML 명세의 장점: - 정보 밀도가 높다 — 같은 내용을 더 적은 공간에 시각적으로 담음 - 스크린샷 피드백 — 결과물을 보고 스크린샷을 Claude에 넘겨 수정 지시 가능 - Playwright MCP 연동 — 이후 에이전트가 직접 브라우저에서 검증 실행 가능 - 시각적 비교 — Brutalist, Tokyo, Fintech 등 4개 방향을 나란히 클릭하며 비교

프롬프트 구조: "4가지 다른 디자인 방향을 탐색하고 각각 HTML로 생성, 비교 설명해줘."

Opus 4.7 권장 이유: 비전 모델이 강화되어 스크린샷에서 미세 UI 오류(정렬 틀어짐 등)를 더 잘 감지함.

4. Phase 3: 에이전트 친화적 검증 프레임워크

대상: React로 만든 To-do 앱 (항목 추가, 완료 체크, 삭제, 완료 항목 전체 삭제).

검증 3계층:

계층 방법 특징
사람(Human) 브라우저 대시보드 시각적 패스/페일 표시, 상세 실행 결과 확인
에이전트(Agent-first) Claude Code + Playwright MCP Claude가 DOM 계약 읽고 검증 스텝 직접 실행
Headless (CI) bun verify 브라우저 없이 CLI에서 테스트 매트릭스 실행

5. DOM 데이터 계약 구현

React 컴포넌트가 자기 상태를 HTML 속성으로 퍼블리시:

<div data-verify-unit="todo-stats"
     data-total-done="2"
     data-active="3">
  • 상태 변경 시 속성값 실시간 업데이트
  • 에이전트는 React 내부 상태 대신 이 속성을 읽음 → DOM이 데이터 계약

각 컴포넌트마다 3종 세트 정의: 1. schemas — 어떤 속성이 있어야 하는가 2. fixtures — 알려진 상태 목록 3. invariants — 항상 성립해야 하는 조건 (불변식)

시연에서 일부러 심어둔 실패: 3 + 3 + 4 = 10 이 아닌 케이스를 불변식 위반으로 설정. Claude + Playwright MCP가 자동으로 발견하고 진단.

6. 검증 클립 기록 및 공유

Playwright가 검증 스텝을 영상으로 녹화 → 클립 단위로 다운로드 가능 → S3 또는 동료 공유.

Claude Code 팀 내부 실무: - 모든 프런트엔드 변경마다 이 방식으로 기록 - 데모보다 더 자동화된 버전 내부 운영 중 - 변경 증거 번들로 활용 (누가, 언제, 어떤 검증을 통과했는지)

자, 현재 상황과 방향을 짚어볼게요. 에이전트가 점점 더 강해지고 있죠. 왜냐면 모델이 강해지고 있으니까요. 모델이 강해지면 에이전트가 더 오래 실행되고 더 복잡한 작업을 맡길 수 있습니다. 그런데 그만큼 우리가 일하는 방식도 바꿔야 합니다. 오늘이 그 이야기입니다 — Claude Code를 어떻게 쓰면 더 많은 걸 뽑아낼 수 있는가.

에이전트를 오래 실행시키면 방향이 잘못됐을 때 토큰을 엄청 태웁니다. 이걸 초반에 막고 싶죠. 그래서 나온 아이디어가 — 인간이 명세에서 하던 검증을 앞당겨서 HTML 파일에 넣자는 것입니다. HTML이 더 풍부하고 인간 친화적으로 에이전트가 만들어갈 결과물을 미리 보여줄 수 있으니까요.

Anthropic 엔지니어링 블로그에 에이전트, 장시간 실행, 하네스 관련 글들이 많이 있습니다. 꼭 읽어보세요. 오늘은 세 가지 레벨로 다루겠습니다 — 기초, 다음 단계, 그리고 좀 더 심화된 것.

모델이 강해질수록 여러분은 오히려 제약을 줄여야 합니다. Richard Sutton의 Bitter Lesson(쓴 교훈)을 들어보신 분 계세요? Sutton은 강화학습의 아버지입니다. 강화학습 교재를 쓰면 그 사람입니다. 그의 주장은 — 인간이 아무리 규칙을 하드코딩해도, 결국 데이터와 컴퓨팅을 쏟아붓는 게 더 나은 결과를 낸다는 것입니다. Claude Code에도 같은 원리가 적용됩니다. 모델이 강해졌으므로, 요구사항을 여러분이 정의하는 것보다 Claude가 여러분에게 질문해서 끌어내게 하는 게 더 낫습니다. 요구사항은 여러분 안에 잠재해 있습니다. 사용자가 "보면 알 것 같은데 말로는 못 하겠어"와 같은 상태처럼요. Claude가 여러분보다 더 잘 뽑아냅니다.

오늘 다룰 내용: - 모호성 제거 - Claude가 여러분을 인터뷰해서 프롬프팅하게 만들기 - 이해와 계획 - HTML 명세로 검증을 네이티브하게 내장하기

이전에는 Markdown으로 다 했습니다. 동료 하나가 "Markdown 파일은 AI 네이티브 소프트웨어 개발 생명주기의 링구아 프랑카"라고 했는데 꽤 시적인 표현이죠. 그런데 그 형식이 이제 좀 제한적이 됐습니다. 줄이 너무 많아지고 있어요. HTML 파일에 더 많은 정보를 압축할 수 있습니다.

검증도 네이티브하게 만들어야 합니다. 에이전트가 인간과 함께, 또는 나중에는 완전히 headless로 검증을 돌릴 수 있도록. 에이전트가 점점 이 모든 걸 알아서 하게 되는 방향이니까요. 그래서 여러분이 만드는 산출물 자체에 검증 가능성을 내장해야 합니다.

Phase 1: 요구사항 인터뷰 (Bill Splitting App 예시)

Bill splitting app (지출 분할 앱)을 만든다고 해봅시다. 친구들이랑 나가서 누가 얼마 내야 하는지 계산하는 앱이요. Claude한테 인터뷰를 맡겨봅시다.

나쁜 프롬프팅 예: "더 좋게 만들어줘." 이건 안 됩니다. 좋은 프롬프팅은 Claude가 구체적인 내용을 끌어낼 수 있도록 영역을 제시하되 결과를 과도하게 규정하지 않는 겁니다. 청중(audience)을 명시하거나 오픈엔드 방식으로 질문하도록 유도하는 것이죠.

Claude Code 두 개 켜놨습니다. Fast Mode 쓰시는 분 얼마나 계세요? 많지 않네요. 그래서 보여드리려고 켰습니다. auto mode는요? 잘 쓰고 계시는군요. auto mode 꼭 쓰세요. 안 쓰시면 지금 당장 켜세요. 훨씬 편해집니다.

effort 파라미터 설정하시는 분 계세요? 저희 권장은 xhigh입니다. max effort도 괜찮아요. 저는 이번에 xhigh로 했습니다.

/effort — effort 파라미터, /fast — fast mode, auto mode는 자동으로 최적 모델 선택.

프롬프트를 복붙하면 Claude가 질문을 탭으로 넘기면서 묻습니다. "친구 전용인가요? 두 번째 청중이 있나요?" 등. 핵심은 프롬프트에 ask_user_question 도구를 명시적으로 언급하는 것입니다. 그게 이 워크플로우를 트리거합니다. 잘 명시할수록 더 좋은 결과가 나옵니다.

답변을 제출하면 Claude가 명세를 생성합니다. 이걸 여러 방식으로 앱 구현에 활용할 수 있죠. 좀 시간이 걸리니 슬라이드로 넘어가겠습니다.

계획이 생겼습니다. 질문에 답하면서 내가 원하는 걸 클로드가 점점 더 잘 뽑아내고 있습니다. 이게 내가 원하는 것과 맞는지 확인하고 싶죠. HTML 파일이 정보 밀도가 훨씬 높습니다. 스크린샷을 찍어서 넣을 수도 있고, 나중에 Playwright MCP도 활용할 수 있습니다. 200줄 넘는 Markdown 파일보다 훨씬 풍부하게 상호작용할 수 있죠. 동료들도 안 읽을 게 뻔한 긴 Markdown 대신에요.

Opus 4.7로 몇 가지 방향을 미리 생성해뒀습니다. 프롬프트: "4가지 다른 디자인 방향을 탐색해줘. HTML로 생성하고 각각 설명해줘." 결과로 나온 방향들: Brutalist, Tokyo, Fintech 스타일 등.

클릭해서 보면 완전히 다른 느낌. Markdown으로 추론하는 것보다 훨씬 직관적입니다. 스크린샷을 찍어서 Claude에 피드백으로 넘기면 됩니다. 프런트엔드 작업에서 특히 유용합니다 — "이게 약간 틀어졌는데"를 말로 설명하기 어려울 때 스크린샷이 훨씬 정확합니다. Opus 4.7의 비전 모델이 강화됐기 때문에 미세 UI 문제도 잘 잡아냅니다.

Phase 3: 검증 프레임워크 (React To-do App)

리포에 있는 Phase 3는 to-do 앱 기준입니다 (bill splitting 앱과는 별개). 아이템 추가, 체크, 삭제, 완료 항목 전체 삭제 기능. 상태 변화가 많아서 검증이 중요합니다.

세 가지 방법으로 검증합니다: 1. 사람이 보는 대시보드 — 브라우저에서 시각적으로 확인 2. 에이전트 구동 방식 — Claude Code + Playwright MCP가 DOM 계약 읽고 검증 실행 3. Headless — bun verify로 CI에서 실행

리포에서 직접 실행하면 결과가 약간 다르지만 원리는 같습니다.

앱 요소를 검사(Elements)하면 data-verify-unit, data-total-done, data-active 같은 속성들이 보입니다. 컴포넌트가 자기 상태를 DOM에 퍼블리시하는 것입니다. 상태가 바뀌면 속성값도 바뀝니다. 에이전트는 React 내부를 모르고도 이 속성을 읽어서 상태를 파악할 수 있습니다. 앱 상태와 독립적으로 검증을 실행할 수 있죠.

각 컴포넌트마다: schemas, fixtures(알려진 상태), invariants(불변식) — 항상 성립해야 하는 조건들. probe로 테스트합니다.

일부러 실패 케이스를 심었습니다. 대시보드에서 전체 실행하면 하나가 걸립니다. 스크롤 내리면 어딘지 보입니다. 에이전트로도 똑같이 잡을 수 있습니다.

에이전트용: DOM에 선언된 검증 스텝 매니페스트를 가져와서 실행. 수동 재생 후 요약에서 의도적으로 심은 실패가 하나 보입니다. 각 케이스의 실행 상세도 확인 가능.

핵심은 해피 패스를 벗어나는 probe를 포함하는 것. 그리고 많은 부분을 Claude가 Claude를 위해 생성할 수 있습니다. 스케일업이 가능한 구조입니다.

3 + 3 + 4 = 10이 아닌 케이스를 하드코딩해서 심었습니다. bun verify로 실행하면 테스트 매트릭스는 통과하지만 (의도적으로 분리) DOM 계약 기반 검증은 실패를 잡습니다. 테스트 통과 != 검증 통과. 이 둘을 분리한 이유를 명시적으로 시연한 것입니다.

data-total-done 속성을 지우면 앱은 정상 동작하지만 계약이 깨져서 모든 관련 검증이 실패합니다. 앱을 안 깨고 계약만 깬 것입니다.

Claude한테 실패한 것 분석 맡기기: Playwright MCP 연결된 상태에서 Opus 4.7이 직접 브라우저 구동하며 4 + 3 != 10 임을 발견하고 진단합니다.

클립 녹화: 검증 스텝을 실행하면서 영상으로 기록. 클립 단위로 다운로드해 동료와 공유하거나 S3에 저장. Claude Code 팀은 이 방식으로 모든 프런트엔드 변경을 기록하고 있습니다. 내부적으로는 데모보다 더 자동화돼 있음. 정기적인 주기로 운영 중.

정리하면 세 가지 서피스: 1. 사람 서피스 — 브라우저 대시보드 2. 에이전트 퍼스트 — 브라우저 기반 에이전트가 같은 방식으로 3. CI — bun verify로 headless

목표: 검증을 산출물 자체에 내장하는 것.
