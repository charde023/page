한 줄 요약

Anthropic이 자체 실험으로 BMAD·GSD·SpecKit·Superpowers 등 기존 하네스 구성 요소를 하나씩 제거해본 결과, Opus 4.6에서는 플래너·생성기·평가기 세 에이전트만 남기면 충분하다는 결론을 냈다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
하네스 요소 가정(Assumption) 검증 각 프레임워크 요소는 "모델이 혼자 못 한다"는 가정에 기댐 — 모델이 강해지면 가정이 낡아 오히려 짐이 됨 프레임워크를 쓰기 전에 가정이 아직 유효한지 검증하라
고수준 계획 vs 마이크로 플래닝 세세한 기술 디테일까지 계획하면 에이전트의 자율 수정 여지가 사라짐 Opus 4.6에서는 "무엇을" 만들지만 알려주면 "어떻게"는 스스로 찾아감
생성기·평가기 분리 코드를 쓴 에이전트가 평가까지 하면 자기 작업을 과신함 생성 에이전트 ≠ 평가 에이전트 — 반드시 역할 분리
스프린트 계약(Sprint Contract) Opus 4.5까지는 완료 기준 합의가 필요했으나 4.6부터 불필요 모델 버전에 따라 계약 필요 여부가 달라짐
컨텍스트 불안(Context Anxiety) 컨텍스트 윈도우가 차면 모델이 일을 너무 일찍 끝내고 완료라고 주장 Opus 4.6은 Claude 기본 압축만으로 해결 — 외부 컨텍스트 리셋 불필요
루브릭(Rubric) 기반 점수 평가 주관적 결과(UI 등)는 통과/실패로 판단 불가 — 기준별 점수가 있어야 에이전트가 "정답"을 인식 디자인 완성도·독창성·완성도·기능성 등 항목별 점수 지정
에이전트 팀 vs 서브에이전트 에이전트 팀은 서로 대화 가능, 서브에이전트는 문서 경유 오버헤드 발생 생성기·평가기는 에이전트 팀으로 구성하라

내가 모를 만한 것 / 처음 보는 것

  • BMAD (Boomerang Method for AI Development) — 작업을 마이크로 태스크 단위로 분해해 에이전트가 따라가게 하는 계획 프레임워크
  • GSD (Get Stuff Done) — 플래너·생성·평가 루프를 기본으로, 기존 계획과 코드 대조 + 사용자 수용 테스트 방식의 프레임워크
  • SpecKit — 스펙을 진실의 기준(SSOT)으로 삼고 에이전트가 문서 기준으로 코드를 검증하게 하는 프레임워크
  • Superpowers — 질문 세션으로 엣지 케이스를 먼저 찾아내고, 테스트 케이스 없이 코드 작성을 막는 엄격한 TDD 강제 프레임워크
  • Playwright MCP — 브라우저를 붙여 사용자 상호작용을 자동으로 흉내 내며 UI 테스트 수행 (평가 에이전트가 사용)
  • 컨텍스트 불안 (Context Anxiety) — 컨텍스트 윈도우가 차오를 때 모델이 조기 완료를 선언하는 현상. 컨텍스트윈도우 참고
  • 스프린트 계약 — 생성 에이전트와 평가 에이전트가 구현 시작 전에 "완료 기준"을 합의하는 약속
  • ailabspro.io — 영상에서 언급된 에이전트·리소스 배포 플랫폼
  • MiniMax Agent (맥스클로) — 영상 스폰서. 클라우드 기반 AI 에이전트, Telegram·Slack·Discord 연동 자동화

화자의 디테일 (놓치기 쉬운 포인트)

  1. Anthropic은 하네스 요소를 하나씩 제거(ablation)하며 영향을 측정했다 — 단순 주장이 아닌 실험 결과.
  2. Opus 4.5 기준으로는 스프린트 계약 없으면 평가자가 여전히 개입해야 했지만, Opus 4.6부터는 계약 없이도 생성 에이전트가 대부분 혼자 처리.
  3. 작은 모델(Haiku 등)은 여전히 작업 문서화 + 스프린트 분해 + 완료 기준 합의가 필수 — 모델 크기에 따라 하네스 복잡도가 달라져야 함.
  4. Anthropic이 제시한 프런트엔드 평가 지표 4개: ① 디자인 완성도(일관성), ② 독창성(AI가 보라색·흰색 그라데이션으로 수렴하는 경향 탈피), ③ 완성도(타이포그래피·간격·색조·대비비), ④ 기능성(컴포넌트의 UX 역할). Claude는 ①④에는 강하지만 ②③이 약점.
  5. 기존 플래너가 구현 세부 사항까지 짜버리면, 작은 오류 하나가 구현 전 단계로 번져 에이전트가 자체 수정하기 어려워진다.
  6. 에이전트 팀(Team) 구성이 서브에이전트보다 나은 이유: 서브에이전트는 대화가 불가능해서 문서를 통한 비동기 통신 오버헤드가 생김.
  7. Anthropic의 예시 플래너는 "앱 아이디어가 무엇이든 한계를 밀어붙여야 한다"고 명시 — 프로젝트를 제품 단계에서 바라볼 것, 구현 단계에서 잡으면 기술 디테일에 매몰.
  8. GSD는 점수가 아니라 통과/실패 판정 — Anthropic 평가 에이전트의 루브릭 기반 점수 체계가 더 엄격.
  9. 평가 에이전트는 "버그가 있다고 가정"하고 비판적으로 검토 — 단순 체크리스트 점검이 아님.
  10. Claude의 플랜 모드도 계획을 주지만 구현 세부사항에 치우쳐 있어 Anthropic 권고(제품 수준 계획)와 불일치.

# 섹션 요지
1 문제 제기 기존 하네스 프레임워크는 "모델이 약했던 시절" 가정에 기댐 — Opus 4.6에서는 오버헤드
2 실험 방법 Anthropic이 요소 하나씩 제거해 실제 영향 측정
3 계획 에이전트 마이크로 플래닝 → 고수준 계획으로 전환. 에이전트에게 "무엇"만 주면 됨
4 생성 에이전트 핵심 구현자, Git 연동, 4단계 하위 워크플로우
5 생성·평가 분리 같은 에이전트가 구현+평가하면 자기 과신 문제 발생
6 평가 에이전트 Playwright로 UI 테스트, 루브릭 기반 점수 평가
7 컨텍스트 불안 해소 Opus 4.6은 Claude 기본 압축만으로 충분
8 실전 권장 GSD + Anthropic 평가 에이전트 조합, 또는 직접 에이전트 팀 구성

1. 기존 하네스 프레임워크의 문제

BMAD, GSD, SpecKit, Superpowers 같은 AI 코딩 프레임워크들은 한 가지 공통 가정을 가진다: 모델이 혼자서는 어떤 일을 못 한다는 것. 각 프레임워크 요소는 이 가정 위에 세워졌다.

문제는 모델이 빠르게 발전한다는 것이다. 이 프레임워크들이 설계될 때 Opus 4.6 수준의 모델은 존재하지 않았다. 그래서 지금 예전 원칙 그대로 작업하고 있다면, 몇 달 전 방식에 머물러 있는 셈이다.

Anthropic은 실험으로 이를 직접 검증했다. 하네스 요소를 하나씩 빼보며 성능 영향을 측정한 결과, 대부분은 이제 오버헤드라는 결론을 냈다.

2. 계획 에이전트 — 마이크로 플래닝에서 고수준 계획으로

예전 하네스는 사용자가 처음부터 매우 상세한 명세를 줘야 했다. BMAD나 SpecKit 같은 프레임워크는 작업을 마이크로 태스크로 잘게 쪼개어 에이전트가 "생각 없이 따라가기만" 하도록 설계했다.

하지만 세세한 기술 플래닝은 역효과가 있다: - 작은 오류 하나가 구현 전 단계로 번짐 - 에이전트가 스스로 방향을 바꾸거나 문제를 고치기 어려워짐 - 기술 디테일에 매몰되어 사용자가 실제 원하는 제품을 놓침

Opus 4.6에서는 제품 수준의 고수준 계획만 필요하다. 에이전트가 "필요한 결과물이 무엇인지" 정도만 알면 그 다음 경로는 스스로 찾아간다. Anthropic의 예시 플래너는 범위를 크게 잡고, 유저 스토리 중심으로 사고하며, 구현 단계가 아닌 제품 단계에서 기능을 분해한다.

3. 컨텍스트 불안과 해소

컨텍스트 불안이란 컨텍스트 윈도우가 차오를 때 모델이 일관성을 잃고 조기에 완료를 선언하는 현상이다. 예전에는 컨텍스트 리셋(외부 문서화된 작업 분해를 기준점으로 삼고 컨텍스트 윈도우를 강제로 비우는 방법)이 필요했다.

하지만 Opus 4.6은 Claude 기본 압축 방식만으로 충분하다. 외부 컨텍스트 리셋도 필요 없고, BMAD·SpecKit처럼 세세한 작업 분해도 필요 없다. 고수준 가이드만으로 한 세션 전체를 이어서 돌릴 수 있다.

단, 작은 모델(Haiku 등)은 여전히 외부 작업 문서화 + 스프린트 분해 + 완료 기준 합의가 필요하다.

4. 생성 에이전트

핵심 구현자 역할이다. 계획에서 나온 명세를 받아 기능별로 앱을 구현하고, Git과 연동해 버전 관리를 한다. 워크플로우는 세 단계: 작업 이해 → 구현 → 다듬기. 구현 단계 안에 4개의 하위 단계가 있어 각기 다른 부분을 처리한다. 구현 후에는 평가 에이전트에게 테스트를 넘긴다.

5. 생성·평가 분리의 중요성

코드를 작성한 에이전트가 그 코드를 평가하면 안 된다.

자신의 작업에 대해 과신하는 경향이 있어, 품질이 부족해도 "잘 됐다"고 평가한다. 수치로 검증 가능한 작업(API 동작 여부 등)은 다소 관리 가능하지만, UI처럼 주관적인 결과는 기준 없이 판단이 불가능하다.

구현을 시작하기 전에 생성 에이전트와 평가 에이전트가 완료 기준(Definition of Done)을 미리 합의해야 한다. Opus 4.5까지는 이 스프린트 계약이 필수였지만, 4.6부터는 생성 에이전트가 충분히 유능해져 계약 없이도 작동한다.

6. 평가 에이전트와 루브릭 기반 점수 평가

평가 에이전트는 단순 버그 점검이 아니라 "버그가 있다고 가정"하고 비판적으로 검토한다. Playwright로 사용자 상호작용을 흉내 내며 앱을 테스트하고, 기준에 따라 버그를 찾아 생성 에이전트에게 피드백한다.

Anthropic이 제시한 프런트엔드 평가 루브릭 4항목:

항목 설명 Claude 현황
디자인 완성도 화면 일관성, 요소가 조화롭게 배치됐는지 강함
독창성 AI의 "보라색·흰색 그라데이션" 수렴 탈피, 인간적 의도가 있는 디자인 약점
완성도 타이포그래피·간격·색조·대비비의 창의적 완성도 약점
기능성 각 컴포넌트가 UX를 높이는 시각적 역할 수행 여부 강함

코드 아키텍처·UX·사용자 흐름 등에도 같은 방식으로 항목별 점수 기준을 만들 수 있다.

7. 프레임워크 선택 실전 가이드

상황 권장
빠른 시작 원할 때 GSD 사용 (기본 플래너·생성·평가 루프 내장)
평가 정밀도를 높이고 싶을 때 GSD + Anthropic 스타일 루브릭 평가 에이전트로 교체
직접 세팅 원할 때 에이전트 팀 구성: 생성기(구현) + 평가기(Playwright 테스트)
소형 모델 사용 시 스프린트 계약 + 작업 문서화 + 완료 기준 합의 필수

프레임워크별 평가 방식 비교:

프레임워크 평가 방식
BMAD 코드 리뷰 + QA 에이전트, 여러 각도 평가
GSD 통과/실패 판정, 사용자 수용 테스트
SpecKit 스펙 문서를 SSOT로, 에이전트가 문서 기준 코드 검증
Superpowers TDD 강제, 테스트 케이스 없으면 코드 작성 불가
Anthropic 루브릭 기반 점수 평가 — 가장 엄격

지난 몇 달 동안 BMAD, GSD, SpecKit, Superpowers 같은 여러 AI 코딩 프레임워크를 다뤄봤습니다. 실제로 많은 분들이 그걸 쓰기 시작했죠. 그런데 Anthropic은 자기들 하네스에 직접 실험을 해서 요소를 하나씩 빼보며 뭐가 진짜 중요한지 측정했습니다. 결론은 대부분은 이제 진작에 가깝다는 거였습니다.

프레임워크의 각 요소에는 모델이 혼자서는 못 한다는 가정이 들어 있습니다. 그런데 Opus 4.6에서는 그런 가정이 이미 낡아버렸습니다. 그래서 무엇이 아직 중요한지, 무엇을 걷어낼 수 있는지, 또 실제 설정은 어떻게 해야 하는지 정리했습니다.

지금 에이전트 하네스는 장기적으로 에이전트가 훨씬 잘 일하게 만드는 데 중요한 역할을 합니다. Anthropic도 이미 에이전트 하네스를 내놨는데, 이건 이전 영상에서 설정하고 사용하는 방법까지 자세히 다뤘습니다. 같은 맥락에서 다른 프레임워크들도 다뤘는데, 구현은 달라도 다들 결국 같은 걸 하려는 겁니다. 하지만 이 프레임워크들이 나왔을 때는 지금의 Opus 4.6만큼 모델이 강하지 않았습니다.

대부분은 컨텍스트 분리에 집중했습니다. 하지만 Opus 4.6에서는 그게 큰 문제가 아닙니다. 100만 토큰 컨텍스트 윈도우 때문만이 아니라, 다른 이유도 있습니다. 그래서 예전에 만든 많은 프레임워크는 이제 새 모델 성능에 비해 오히려 오버헤드가 됐습니다.

Anthropic은 실제로 하네스의 여러 요소를 테스트하면서 하나씩 제거해보고 영향이 어떤지 측정했습니다. 그 결과, 에이전트 하네스에 정말 필요한 건 계획, 생성, 평가를 받는 에이전트뿐이라는 결론을 냈습니다. 나머지는 모델이 워낙 강해진 지금은 그냥 방해일 뿐이고, 오히려 짐이 됩니다.

어떤 에이전트 하네스를 쓰든 각 요소가 다 같은 원리에 기대고 있습니다. 각 요소에는 모델이 혼자 할 수 있는 일에 대한 가정이 들어 있습니다. 이 가정들은 틀릴 수도 있고, 모델이 발전하면 금방 낡기 때문에 꼭 검증해야 합니다. 모델이 진화하면 하네스도 같이 바뀌어야 합니다. 그런데 아직도 예전 원칙 그대로 작업하고 있다면? 몇 달 전에 정리한 방식에 머물러 있는 셈입니다.

계획은 모든 프레임워크에서 공통으로 남는 첫 단계지만, 더 강한 모델일수록 계획 방식은 달라져야 합니다. Anthropic의 예전 장기 실행 하네스는 사용자가 처음부터 아주 자세한 명세를 줘야 했습니다. BMAD나 SpecKit 같은 프레임워크는 작업을 더 작은 조각과 마이크로 태스크로 나눠서 AI 에이전트가 쉽게 구현하도록 돕습니다. 말 그대로 에이전트가 생각 없이 그대로 따라가기만 하면 되는 상세 단계였죠. 그때는 모델이 충분히 강하지 않아서 원하는 대로 움직이게 하려면 세세하게 가이드해야 했습니다.

하지만 Opus 4.5와 4.6부터는 상황이 달라졌습니다. Anthropic이 이걸 테스트해보니, 플래너가 처음부터 아주 세세한 기술 디테일까지 정해버리면 작은 오류 하나가 구현 전 단계로 번져서, 에이전트가 스스로 방향을 바꾸거나 문제를 고치기 어려워졌다고 합니다. 그래서 이제는 계획도 세부 기술 구현이 아니라 높은 수준에서만 잡습니다. 에이전트가 훨씬 똑똑해졌기 때문에, 필요한 결과물이 무엇인지 정도만 알려주면 됩니다. 그 다음 경로는 스스로 찾아갑니다.

이런 변화 때문에 BMAD나 SpecKit 같은 계획 방식은 이제 예전만큼 중요하지 않습니다. BMAD는 PRD를 만드는 계획 단계까지 만들었습니다. 에이전트만 써도 되고, 기술적인 분할 과정까지 들어갈 필요는 없습니다. PRD를 만드는 게 효과적인 이유는 Claude 혼자보다 제품 요구 사항을 더 잘 이해하도록 특화된 에이전트들이 있기 때문입니다. 그 에이전트들에는 작성자가 특정 작업을 위해 외부 컨텍스트를 넣어두기 때문입니다. 아니면 Superpowers의 질문 세션을 써도 됩니다. 원래 엣지 케이스를 찾아내도록 만든 거라, 여러 단계의 작업 문서보다 더 효과적일 수 있습니다.

하지만 계획을 너무 세세하게 짜면 에이전트를 꽁꽁 묶어버려서, 기술자가 스스로 발견하고 알아갈 여지를 남겨주지 못합니다. Anthropic은 플래너 에이전트가 생성한 예시 계획도 함께 제시했는데, 이걸 바탕으로 직접 플래너 에이전트를 설정할 수 있습니다. 그 예시는 계획이 범위를 크게 잡고, 어떤 앱 아이디어를 주더라도 한계를 밀어붙여야 한다고 분명히 말합니다. 핵심은 프로젝트를 구현 단계가 아니라 제품 단계에서 바라보는 것입니다. 프로젝트 계획 안에서 구현까지 다 짜려들면, 기술 디테일에 너무 매달리게 되고, 정작 완성된 제품에 필요한 것을 놓칠 수 있기 때문입니다.

물론 Claude의 플랜 모드도 질문을 던지고 상세한 계획을 주니 비슷해 보일 수 있습니다. 하지만 차이가 있습니다. Claude에도 플래닝 에이전트가 있지만, 여전히 구현 세부 사항에 많이 치우쳐 있고, 진짜 제품 수준에서 움직이지는 않습니다. 이건 Anthropic의 발견과도 맞지 않습니다. 그래서 이걸 세팅해 두면, Claude에게 당신이 만든 에이전트를 써서 앱을 계획하라고만 하면 됩니다. 그러면 완전한 계획을 만들고, 진행하면서 폴더의 문서로 정리해 줍니다. 이 계획에는 제품 수준의 전체 기능 분해가 들어가고, 각 단계마다 유저 스토리도 포함됩니다.

(스폰서: MiniMax Agent — 클라우드 기반 AI 에이전트, Telegram·Slack·Discord 연동, 클릭 한 번으로 10초 내 배포)

코드를 작성한 에이전트가 그 코드를 평가하면 안 됩니다. 이건 두 번째로 흔한 문제인데, 보통은 많이 다뤄지지 않습니다. 코드를 쓴 같은 에이전트가 평가까지 하면 문제가 됩니다. 품질이 분명히 부족해도 자기 작업을 아주 확신 있게, 좋게 말하는 경향이 있기 때문입니다. 이건 수치로 판단할 수 있는 작업이라면 조금 관리하기 쉬울 수 있습니다. 예를 들면, 구현한 API가 실제로 동작하는지 같은 경우입니다. 하지만 결과를 명확하게 검증하기 어려운 작업에서는 이 문제가 훨씬 더 커집니다. 대표적인 예가 UI입니다. 좋은 UI가 무엇인지는 주관적이라서 AI가 의도를 완전히 이해하지 못할 수도 있습니다. 그래서 당신의 기준에는 못 미쳐도 자기 구현을 잘했다고 여길 수 있습니다.

이 문제는 여러 프레임워크 제작자들도 이미 인식했고, 이를 해결하려고 자체 평가 메커니즘을 넣었습니다. GSD 같은 프레임워크들도, BMAD와 Superpowers는 코드 작성자와 품질 평가자를 같은 에이전트로 두지 않도록 합니다. 이 방식은 에이전트 평가의 정확성과 신뢰성을 크게 높여줍니다. 그래서 기존 프레임워크를 쓰든 직접 만들든, 평가자는 구현자와 완전히 분리되어 있어야 합니다.

구현을 시작하기 전에 생성 에이전트와 평가 에이전트가 먼저 계약을 맺고, 작업이 끝났다고 볼 기준을 합의합니다. 이렇게 하면 두 에이전트 모두, 무엇을 달성해야 하고 무엇을 검증해야 하는지 분명히 알 수 있습니다.

아무리 높은 수준의 계획이라도 실행 가능한 단계는 여전히 필요합니다. 하지만 하네스로 테스트하는 동안 스프린트 계약을 제거해봤더니, 이 상황에서는 Opus 4.5가 덜 효율적이었습니다. 평가자가 여전히 문제를 잡으러 개입해야 했기 때문입니다. 하지만 Opus 4.6에서는 모델 성능이 너무 좋아져서 계약이 필요 없었습니다. 생성형 에이전트가 대부분의 일을 혼자 처리할 만큼 충분히 유능해졌습니다. 그래서 Haiku 같은 작은 모델은 아직도 작업을 문서화하고, 스프린트 단위로 잘 쪼개고, 각 에이전트가 완료 기준에 합의해야 합니다. 하지만 더 강한 모델이라면 이런 추가 단계 없이도 Opus에게 전체 계획 실행을 맡길 수 있습니다.

이제 왜 컨텍스트 분리가 중요한지 이야기했죠. 그 이유는 작은 모델이 컨텍스트 불안을 겪기 때문입니다. 모델이 시작하자마자 컨텍스트 윈도우가 차면서 긴 작업에서 일관성을 잃기 시작하는 현상입니다. 이럴 때 모델은 일을 너무 일찍 끝내고, 실제로는 아니더라도 제대로 구현했다고 주장합니다. 효과가 있었던 해결책은 컨텍스트 리셋이었습니다. 컨텍스트 불안이 시작되기 전에 컨텍스트 윈도우를 비우는 방식입니다. 컨텍스트가 비워졌기 때문에 외부의 문서화된 작업 분해를 기준으로 삼을 수 있었고, 그 내용은 컨텍스트 리셋을 해도 유지됐습니다. 하지만 모델의 컨텍스트 불안이 너무 심해서 압축만으로는 충분하지 않았습니다. 그래서 더 긴 작업에서 문제를 막기 위한 추가 조치가 필요했습니다. Opus 4.5까지는요. 하지만 이제는 모델이 더 이상 이런 모습을 보이지 않습니다. 이 에이전트들은 한 세션 전체를 계속 이어서 돌릴 수 있고, Claude의 압축 방식만으로도 충분합니다. 그래서 이제는 컨텍스트 리셋도, 세세한 작업 분해도 필요 없습니다. 고수준 가이드만으로도 충분합니다.

생성 에이전트는 실제로 앱을 기능별로 만들어가는 핵심 구현자입니다. 계획에서 나온 명세를 받아서 계속 구현하고, 버전 관리는 Git과 연동합니다. 생성 에이전트는 평가 에이전트와 함께 움직입니다. 기능을 만들고 나면 테스트를 위해 넘기고, 피드백을 받아 구현을 더 다듬습니다. 워크플로우는 여러 단계로 정리돼 있습니다. 작업을 이해하고, 구현하고, 다시 다듬는 순서입니다. 구현 단계 안에서도 작업은 4개의 하위 단계로 나뉘어 각기 다른 부분을 다룹니다. 디자인 방향을 따르고, 작업을 검증한 뒤 평가 에이전트에게 넘깁니다. 이렇게 하면 에이전트가 앱 전체를 독립적으로, 그리고 체계적으로 구현할 수 있는 단계별 구조가 만들어집니다.

평가 에이전트는 생성 에이전트의 상대 역할을 합니다. 이 역할은 단순한 버그 찾기 점검이 아니라, 버그가 있다고 가정하고 비판적으로 살펴보면서 앱이 제대로 구현됐는지 확인하는 것입니다. Playwright로 사용자 상호작용을 흉내 내며 앱을 테스트하고, 정해진 기준에 따라 버그를 찾아 생성 에이전트에게 다시 피드백합니다. 계획을 읽으면 평가 에이전트는 완료 상태가 어떻게 보여야 하는지 분명히 이해하게 되고, 승인 전에 모든 걸 꼼꼼히 확인합니다.

각 프레임워크마다 자체 검증기는 있지만 접근 방식은 꽤 다릅니다. BMAD는 테스트를 만들고 실행하는 전용 코드 리뷰와 QA 에이전트를 써서 코드를 여러 각도에서 평가합니다. GSD는 검증용 서브 에이전트를 씁니다. 이 에이전트는 구현이 기존 계획과 맞는지 확인하고, 문서 보고서를 만듭니다. Superpowers는 새 서브 에이전트에 의존하고, 테스트 케이스 없이 코드를 먼저 못 쓰게 하는 엄격한 TDD를 강제합니다. 에이전트가 이를 우회하려 하면 막힙니다. 스펙을 진실의 기준으로 삼고, 에이전트가 문서를 기준으로 코드를 검증하게 합니다.

하지만 이 프레임워크들 중 어느 것도 Anthropic이 노렸던 수준의 엄격한 점수 체계를 제공하지는 않습니다. 그래서 Anthropic 하네스의 평가 에이전트가 가장 가까운 방식입니다. Claude에 대한 엄격한 구현 강제와도 비슷해서, 제대로 된 등급 평가 방식으로 에이전트가 실제로 필요한 결과를 내게 됩니다.

특히 구현 결과를 수치로 판단할 수 없는 경우엔, 에이전트가 당신에게 정답이 어떤 모습인지 알 방법이 없습니다. 그래서 등급 평가 메커니즘을 써서 에이전트가 당신 기준의 정답이 어떤 건지 알게 하는 겁니다. Anthropic이 프런트엔드 평가 지표 예시를 들 때도, AI는 대부분 비슷한 결과로 수렴한다고 말했습니다. 생성 에이전트와 평가 에이전트 모두 그렇습니다.

첫 번째는 디자인의 완성입니다. 화면이 일관성 있는지, 아니면 요소만 따로 붙여 놓은 건지 보게 합니다. 그 다음은 독창성입니다. AI는 대부분의 UI에서 자꾸 같은 보라색과 흰색 그라데이션 패턴으로 가기 때문입니다. 사람이 디자인하는 방식과 비교해 보는 겁니다. 사람은 모든 선택에 의도가 있어서, 웹사이트가 별로면 바로 티가 납니다. 세 번째는 완성도입니다. 타이포그래피, 간격, 일관성, 색조와 같은 세부 요소, 그리고 대비 비율이 기술적으로만 맞는지, 아니면 더 창의적으로 보이는지도 봅니다. 마지막은 기능성입니다. UI에서는 각 컴포넌트가 사용자 경험을 높이는 시각적 역할을 하기 때문입니다. Claude는 이미 완성도와 기능성에서는 점수가 잘 나옵니다. 하지만 나머지 항목이 가장 흔한 약점이고, 프롬프트는 좋은 디자인은 퀄리티에서 나온다는 점을 강조해서 Claude를 최대한 끌어내야 합니다.

그래서 앱을 만들 때도 비슷한 기준을, 코드 아키텍처, 프런트엔드, UX, 사용자 흐름 등 원하는 만큼 많이 둘 수 있습니다. 기준에 적힌 각 항목마다 전용 점수를 주면, 모델이 성능에 따라 그 중요도를 파악할 수 있습니다. 이 파일들은 평가 에이전트가 참고합니다.

지금까지 다 봤다면, 이제 실제로 뭘 해야 할지 궁금할 겁니다. 설정을 쉽게 하고 싶다면 GSD를 쓰세요. GSD는 기본적으로 플래너, 생성, 평가 루프를 그대로 사용합니다. 기존 계획과 코드를 대조하고, 사용자 수용 테스트에 의존합니다. 점수로 평가하는 방식이 아니라, 통과와 실패로 판단합니다. 그래서 Anthropic 프레임워크의 좋은 부분을 GSD와 섞어 쓸 수 있습니다. 예를 들어 평가 에이전트를 바꾸고, 기준과 함께 묶어서 에이전트가 올바른 구현이 뭔지 알게 할 수 있습니다.

하지만 Anthropic 프레임워크를 직접 세팅하고 싶다면, 역할별로 에이전트를 만들어 에이전트 팀으로 함께 일하게 하면 됩니다. 한 에이전트는 생성기, 다른 하나는 평가자로 두는 식입니다. 에이전트 팀을 쓰는 이유는 서로 대화할 수 있지만 서브 에이전트는 그럴 수 없어서, 문서에 따로 써야 하는 오버헤드가 생기기 때문입니다. 그래서 Claude는 상위 수준의 계획에서 작업을 만들고, 두 에이전트를 동시에 만듭니다. 하나는 구현을 하고, 다른 하나는 브라우저가 붙은 Playwright MCP로 테스트를 돌리면서, 생성 에이전트의 업데이트를 기다렸다가 테스트를 시작합니다. 평가자는 계속 작업을 검증하고, 문제점을 생성기에게 전달해서, 두 에이전트가 협업하며 기준에 맞는 앱 전체를 구현합니다.
