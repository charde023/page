먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

코딩 에이전트는 사람이 목표를 말하면 코드를 읽고 고치는 AI 도구다. 화자가 겪은 핵심 문제는 대화 횟수보다, AI가 읽고 쓰는 정보 단위인 토큰이 빠르게 쌓인다는 것이다. 작업 기억에 해당하는 맥락이 불필요한 파일과 대화로 가득 차면 사용 한도뿐 아니라 결과 품질도 나빠질 수 있다고 말한다.

해법은 기능을 많이 붙이는 것이 아니라 작업 범위를 줄이는 것이다. 새 작업은 새 대화에서 시작하고, 큰 작업은 먼저 계획을 검토한 뒤 구현한다. 완료 여부는 AI의 말이 아니라 테스트·타입 검사·화면 확인처럼 실제 결과를 점검하는 절차로 판단한다. 반복 지침은 문서형 안내서인 스킬에 넣는다.

코드 밖의 GitHub·데이터베이스·브라우저를 직접 다뤄야 할 때만 외부 도구 연결인 MCP를 쓰고, 조사나 검토를 따로 맡길 때만 독립된 작업 기억을 가진 보조 AI인 서브 에이전트를 쓴다. 둘 다 편리하지만 토큰을 더 쓰므로 필요한 범위에서만 선택해야 한다. 결국 좋은 결과는 특정 제품보다 명확한 요구, 작은 작업 단위, 사전 계획, 검증 가능한 완료 조건에서 나온다는 것이 화자의 중심 주장이다.

여기까지만 이해하면 충분

  • 불필요한 파일 탐색과 긴 대화는 토큰과 작업 맥락을 함께 소모한다.
  • 큰 작업은 계획을 먼저 검토하고, 구현 결과는 실행 가능한 검사로 확인한다.
  • 스킬·MCP·서브 에이전트는 많을수록 좋은 것이 아니라 필요한 역할에만 쓴다.
  • 코딩 지식이 있어야 AI의 계획과 결과를 판단하고 잘못된 출력을 고칠 수 있다.

작업대와 공구함

맥락은 한 번에 펼쳐 놓고 쓸 수 있는 작업대와 비슷하다. 필요한 설계도와 공구만 올리면 작업하기 쉽지만, 이전 작업의 부품과 관계없는 자료까지 쌓이면 필요한 것을 찾고 판단하기 어려워진다. 스킬·MCP·서브 에이전트는 목적이 서로 다른 공구에 해당한다.

비유가 깨지는 지점: 실제 모델 품질은 작업대의 물건 수처럼 토큰 수 하나만으로 결정되지 않는다. 화자가 제시한 품질 저하 구간도 개인 경험이며 모델·작업·요금제별 조건은 확인되지 않았다.

이번 글의 통찰

1. 맥락 관리의 목적은 절약만이 아니다

  • [원문] 화자는 새 작업마다 새 세션을 열고, 불필요한 탐색을 중단시키며, 사용할 파일과 출처를 구체적으로 지정하라고 권한다.
  • [해석] 맥락 관리는 비용 절감과 품질 관리가 만나는 지점이다. 무엇을 더 제공할지뿐 아니라 무엇을 읽지 못하게 할지도 설계해야 한다.
  • [경계] 제목과 META는 1,000시간 넘게 사용했다고 적지만, 제공된 본문 발화에는 정확한 1,000시간 수치가 없다. 화자가 말한 작업당 최소 50,000토큰, 조사 시 100,000토큰 초과, 100,000~200,000토큰 이후 품질 저하도 개인 경험이며 작업·모델·요금제 조건이 제시되지 않았다.

2. 완료 선언과 검증 결과를 분리해야 한다

  • [원문] 화자는 테스트를 먼저 만들고 구현하며, 필요하면 타입 검사·린트·스크린샷·브라우저 테스트를 완료 조건으로 주라고 말한다.
  • [해석] 에이전트의 “완료”는 보고일 뿐 증거가 아니다. 작업 전에 관찰 가능한 성공 조건을 정해야 구현과 검증이 같은 방향을 본다.
  • [경계] 테스트를 먼저 쓰면 항상 올바른 검증이 되는 것은 아니다. 화자는 핵심 부분만 시험하라고 했지만, 무엇이 핵심인지 정하는 구체적 기준이나 비교 결과는 제공하지 않았다.

3. 기능 평가는 시점과 사용 조건에 따라 달라진다

  • [원문] 화자는 Plan mode와 검증을 높게 평가하고, 스킬·MCP·서브 에이전트는 필요한 만큼만 쓰라고 권한다.
  • [해석] 기능의 이름이나 등급보다 작업 크기, 외부 접근 필요, 병렬 역할의 가치, 토큰 비용을 기준으로 선택해야 한다.
  • [경계] 전사에는 시점·상태 충돌이 있다. Ultra Plan은 처음에는 존재하는 기능처럼 소개되지만 한 달 뒤 편집 발화에서는 이미 없어졌다고 한다. Fable 모델도 새 모델로 언급된 뒤 사라졌다고 했다가 곧 없어진 것은 아니지만 사용 크레딧이 필요하다고 정정한다. MCP 등급도 B에서 A로 즉시 수정된다. 맥락 한도는 300,000과 1,000,000토큰이라고 말하면서 기본값은 1,000,000인 것 같다고만 했으며 적용 조건은 확인되지 않았다. 제목의 1,000시간, 6개월 동안 약 10억 달러 수익, 80개가 넘는 명령·기능, 3시간 대기와 1~2회 프롬프트 후 한도 도달 주장도 독립 검증 자료가 없다. META의 Caveman 소속은 원본 영상 링크를 확인하지 못한 상태에서 화자 이름과 SNS를 기준으로 추정한 후보이며, 원작자 이름은 비어 있다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 화자는 AI가 만든 변경을 그대로 승인하지 말고 변경 이유를 설명하게 하며, 테스트 같은 관찰 가능한 검증을 붙이라고 한다.
  • 통찰: 이해 여부도 “알겠다”는 답보다 요약을 덮고 원인·차이·적용을 설명하게 할 때 더 잘 드러난다.
  • 질문/행동: 학습자가 결과를 보기 전에 예상 결과와 확인 방법을 먼저 말하게 해 볼 수 있는가?

사업가 · 구조적 비유

  • 관련성: 토큰, 고급 모델, 서브 에이전트는 품질을 높일 수 있지만 동시에 비용과 사용 한도를 소비한다.
  • 통찰: APOM에 적용한다면 모든 업무에 비싼 자원을 붙이기보다 오류 비용과 검증 가능성에 따라 자원을 배분한다는 가설로 시험해야 한다.
  • 질문/행동: 현재 APOM의 실제 시스템 상태는 자료에 없으므로, 어떤 가상 업무가 추가 AI 비용보다 큰 재작업 감소를 만드는지 먼저 묻는다.

마케터 · 직접 전이

  • 관련성: 영상은 등급, 개인 경험, 구체적인 실패 장면을 이용해 기능별 판단을 전달하지만 독립 비교 자료는 제시하지 않는다.
  • 통찰: 강한 숫자와 사용 후기는 관심을 만들 수 있어도, 검증 조건이 없으면 경험적 주장으로 표시해야 한다.
  • 질문/행동: 상세페이지의 각 문장을 주장·사용자 경험·측정 증거로 나누면 어떤 근거가 비어 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 새 세션, 구체적인 파일 범위, 계획 선행, 테스트 우선, 외부 도구 최소화라는 구체적인 워크플로가 제시된다.
  • 통찰: 에이전트 평가는 생성 속도보다 사전에 정한 검증을 첫 시도에 얼마나 통과하는지로 볼 수 있다.
  • 질문/행동: 다음 중간 규모 작업 한 건에서 읽을 범위와 완료 검사를 구현 전에 고정해 볼 수 있는가?

가치 지도

"에이전트가 불필요한 맥락과 도구를 사용해 비용과 재작업을 늘린다" 문제
→ "더 예측 가능한 구현과 검토 시간을 얻는다" 수혜자: 개발자와 결과물을 사용하는 사람
→ "토큰 예산·검토 시간·테스트 환경을 제공한다" 지불자 또는 자원 제공자: 작업을 운영하는 개인 또는 조직
→ "첫 검토에서 사전 정의 검증을 통과한 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 다음 중간 규모 코딩 작업 한 건을 새 세션에서 시작하고, 읽을 파일 범위와 검증 목록을 적은 뒤 계획을 승인하고 구현한다.
  • 측정 1개: 첫 검토에서 사전 정의 검증 항목을 통과한 비율.
  • 중단 기준 1개: 첫 검토 통과율이 100% 미만이면 같은 방식을 다른 작업으로 확대하지 않고 누락된 계획·검증 조건부터 수정한다.

2 프로젝트 지침과 스킬 CLAUDE.md와 SKILL.md로 프로젝트 맥락과 반복 절차를 전달한다.
3 계획과 검증 큰 작업은 계획을 먼저 보고, 테스트와 도구로 완료 여부를 확인한다.
4 맥락과 편의 기능 새 세션, 구체적인 범위, 수동 압축으로 맥락 낭비를 줄인다.
5 자동화와 병렬 작업 반복 실행, 서브 에이전트, worktree를 쓰되 비용과 격리를 고려한다.
6 대안과 학습 태도 제품보다 코딩 지식과 판단 능력을 유지하는 것이 중요하다고 주장한다.

1. 사용 한도와 도구 선택

화자는 월 20달러 요금제를 사용하면서 한두 번의 프롬프트 뒤 사용 한도에 도달하거나 3시간을 기다린 경험이 있었다고 말한다. 월 100달러를 지불할 생각은 없다고 했다가 뒤에서는 100달러·200달러 요금제 사용자를 함께 언급한다. 이는 서로 다른 요금제를 비교한 것이며, 한도 조건은 제시하지 않는다.

Claude Code를 터미널에서 사용하는 코딩 특화 Claude로 설명하지만, 본인은 화면과 버튼이 있는 IDE와 에이전트의 결합을 선호한다. 개념 상당수가 다른 코딩 에이전트에도 적용된다고 본다.

2. 프로젝트 지침과 스킬

/init은 프로젝트를 분석해 CLAUDE.md를 만드는 명령으로 소개된다. 화자는 이 파일을 프로젝트의 지속적인 기억이라고 표현하며 프로젝트 설명, 현재 상태, 코딩 스타일, 작업 철학, 사용자 화면의 대문자 사용 제한, PR 언어 같은 내용을 넣었다고 한다.

실험 버전 /init은 사용자를 인터뷰하고 스킬과 훅을 추천한다고 설명한다. 화자는 /init 자체를 C 또는 D로 평가하지만 CLAUDE.md의 가치는 더 높게 보게 되었다고 말한다. 다만 이 파일이 필수는 아니며 스킬로 비슷하거나 더 나은 결과를 얻을 수 있다고 덧붙인다.

스킬은 반복 업무의 기준과 절차를 담은 SKILL.md다. 화자는 Skills.sh, Matt Pocock의 Grow with Docs와 Improve Codebase Architecture, Cursor의 Thermonuclear Code Quality Review, shadcn의 Improve를 선호 사례로 든다. shadcn Improve는 당시 시험 중이라고 했고, 똑똑한 모델이 계획하고 더 빠르고 저렴한 모델이 구현하는 방식이 기본 전략이 될 수 있다고 전망했을 뿐 이미 검증된 표준이라고 단정하지 않았다.

3. 계획과 검증

Plan mode는 Shift+Tab으로 들어가며, 에이전트가 코드를 더 살펴본 뒤 계획을 제시하고 승인 전에는 수정하지 않는 방식으로 설명된다. 화자는 큰 작업에는 권하지만 오타, 변수명 변경, 작은 디자인 수정에는 낭비라고 본다. 12개 파일과 3,000줄을 고친 뒤 오류를 찾는 것보다 계획에서 오류를 찾는 편이 쉽다는 예를 든다.

검증은 최고 등급의 실천으로 평가한다. 구현 전에 테스트를 작성하고, 핵심 동작만 시험하며, 언어가 지원하면 타입 검사와 린트를 실행하라고 한다. 프런트엔드는 스크린샷과 브라우저 조작으로 화면을 확인하는 방식을 제안한다. 구현 뒤 해당 코드에 맞춰 통과하는 테스트를 만드는 것은 독립적인 검증이 약하다고 비판한다.

MCP는 GitHub, 데이터베이스, Slack, 분석, 배포, 브라우저 등 코드 밖의 대상을 직접 다룰 때 사용한다. 디자인 자료 수집, 테스트용 가짜 데이터 추가, 조사·문서 탐색, 브라우저 테스트가 사례다. 반면 모범 사례나 구현 절차 전달은 스킬이 맡을 수 있으므로 MCP를 불필요하게 늘리지 말라고 한다.

4. 맥락과 편의 기능

화자는 토큰이 프롬프트 횟수가 아니라 모든 메시지, 읽은 파일, 응답에 따라 사용된다고 설명한다. 맥락 창을 단기 기억에 비유하며, 맥락이 길어질수록 망각·모순·실수가 늘어나는 구간을 개인적으로 dumb zone이라고 부른다.

두 맥락 한도로 300,000토큰과 1,000,000토큰을 언급하고 기본값은 1,000,000인 것 같다고 말한다. 개인 경험상 100,000~200,000토큰을 넘으면 성능이 떨어졌고, 중간 이상 작업은 최소 50,000토큰, 조사·스킬·MCP를 쓰면 100,000토큰을 넘기기 쉽다고 주장한다. 모두 적용 조건이나 측정 자료가 없는 경험적 수치다.

권장 방식은 작업마다 새 세션을 열고, 불필요한 파일·웹 탐색을 즉시 막고, 사용할 파일과 출처를 구체적으로 지정하는 것이다. /context로 현재 맥락을 확인하고, 자동 /compact가 발생하면 새 세션을 고려하라고 한다. 대화를 이어야 한다면 사용자가 직접 압축하면서 보존할 내용을 지정하는 편이 낫다고 말한다.

편의 기능으로 음성을 프롬프트로 바꾸는 /voice, 작업을 방해하지 않고 대화 기록만으로 질문하는 /btw, 앱 사이에서 세션을 옮기는 Teleport와 Remote Control, 명령 앞에 !를 붙여 터미널 명령을 실행하고 출력을 Claude에도 보여 주는 Shell mode, 음악을 재생하는 /radio를 소개한다.

5. 자동화와 병렬 작업

/loop는 시간 간격을 지정해 작업을 반복하는 AI 자동화처럼 설명된다. 화자는 열린 GitHub 이슈 하나를 구현해 PR을 만드는 작업과 보안·버그 점검을 사용 사례로 들고, 코드·PR·이슈를 보고 기능을 제안하는 자동화는 최근 시험 중이라고 말한다. 회사와 오픈소스 프로젝트도 시험하면서 괜찮은 결과를 얻고 있다는 말은 화자의 관찰이며 구체적 사례는 없다.

그 뒤 목표가 달성되거나 사람의 도움이 필요할 때까지 계속 작업하는 기능을 설명하지만, 제공된 전사에서는 해당 기능의 이름이 빠져 있어 /loop와 동일한 기능인지 별도 기능인지 확인할 수 없다.

서브 에이전트는 조사, 검토, 디버깅처럼 한 역할을 맡고 독립된 맥락에서 일한 뒤 주 에이전트에 요약을 돌려준다. 원하는 만큼 만들 수 있다고 표현하지만, 각 에이전트가 별도 대화를 실행하므로 20달러 요금제에서는 작은 다중 에이전트 구성도 작업이 끝나기 전에 한도를 소모할 수 있다고 경고한다.

Worktree는 같은 저장소의 여러 브랜치를 별도 폴더에서 다루는 방식으로 설명된다. 화자는 채팅마다 worktree 하나를 연결해 에이전트끼리 수정이 섞이지 않게 하고 병렬로 작업한다고 말한다.

6. 대안과 학습 태도

대안으로 Codex, OpenCode, Pi, Cursor, VS Code와 GitHub Copilot, T3 Code를 소개한다. Codex는 본인이 가장 많이 사용하는 도구라고 말하고, OpenCode는 여러 모델을 쓸 수 있는 오픈소스 대안, Pi는 직접 워크플로를 구성하는 최소형 도구로 설명한다. Cursor에서는 Grok과 Composer가 빠르고 저렴하다고 평가한다. T3 Code는 해당 웹사이트의 표현을 인용해 코딩 에이전트를 위한 오픈소스 제어판이라고 소개한다.

마지막 주장은 특정 도구를 쓰는 것보다 코딩을 이해하는 것이 중요하다는 것이다. 사용 한도에 도달했을 때 스스로 작업하지 못하는 상태를 경계하며, AI가 변경 내용을 설명하게 하고 무조건 승인하지 말라고 권한다.

나는 매주 프로그래밍 조언과 뉴스를 보내서 여러분이 최신 정보를 따라가고 뒤처지지 않도록 돕는다. 무료라는 말은 했던가? 여러분에게 필요한 건 달콤하고 맛있는 이메일 주소뿐이다.

먼저 /init과 CLAUDE.md 파일부터 시작하자. 프로젝트에서 Claude Code를 처음 열었을 때 실행하도록 되어 있는 명령어다.
