개념 왜 중요한가 한 줄
에이전틱 검색(agentic search) AI 에이전트가 일을 수행하려면 단순 링크가 아니라 정확한 정보 조각이 필요하다 검색 결과의 고객이 인간에서 에이전트로 바뀐다
인간 클릭 데이터(human click data)의 한계 인간은 느리고 게으르며 광고·SEO에 영향을 받는다 에이전트용 검색은 인간 클릭보다 에이전트 피드백(agent feedback)을 써야 한다
인덱스(index)는 지연시간 최적화 전체 웹을 미리 다 저장하지 않아도 초기 제품을 만들 수 있다 먼저 검색 에이전트를 만들고, 고객 문제를 풀며 인덱스를 키운다
품질·비용·지연시간(quality, cost, latency) AI 검색 제품의 경쟁력은 이 세 축의 균형이다 Parallel은 처음엔 지연시간을 포기하고 품질·비용에 집중했다
콘텐츠 경제(content economics) 에이전트가 웹을 읽으면 기존 광고 기반 모델이 무너질 수 있다 콘텐츠 소유자에게 기여도 기반으로 보상하는 새 모델이 필요하다
샤플리값(Shapley value) 여러 콘텐츠가 답변 품질에 기여한 정도를 나누는 이론적 방법이다 웹 콘텐츠 보상의 공정한 계산 틀로 사용될 수 있다
풀에서 푸시로 전환(pull to push) 미래의 웹은 요청받을 때만 검색되는 것이 아니라 변화가 생기면 에이전트를 깨운다 “이런 일이 생기면 알려줘”가 웹 사용의 핵심이 된다

내가 모를 만한 것 / 처음 보는 것

  • 에이전틱 검색(agentic search) — 사람이 키워드를 넣고 링크를 고르는 검색이 아니라, AI 에이전트가 업무 수행 중 필요한 정보를 스스로 여러 번 조회하는 검색.
  • 그라운딩(grounding) — AI 모델이 환각을 줄이기 위해 최신 웹 데이터나 신뢰 가능한 외부 정보에 답변을 연결하는 방식.
  • 신선한 인덱스(fresh index) — 오래된 웹 사본이 아니라 최근 변경 내용을 반영하는 검색용 데이터 구조.
  • 검색 리라이트(query rewrite) — 사용자의 요청을 검색 시스템이 이해하기 좋은 여러 질의로 다시 쓰는 과정.
  • 검색 계층(retrieval layer)과 랭킹 계층(ranking layer) — 후보 문서를 먼저 많이 찾고, 그중 가장 관련 높은 문서·문단을 순서화하는 단계.
  • 샤플리값(Shapley value) — 협력 게임이론에서 전체 성과에 대한 각 참여자의 공정한 기여도를 계산하는 방법.
  • 차등 가격 책정(differential pricing) — 같은 정보라도 사용하는 사람, 사용 목적, 창출 가치에 따라 가격을 다르게 매기는 방식.
  • 백그라운드 에이전트(background agent) — 사람이 직접 요청하지 않아도 계속 웹이나 데이터를 감시하다가 조건이 맞으면 일을 시작하는 에이전트.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 에이전트는 인간보다 웹을 1,000배 더 많이 사용할 것이라고 봄 — Parallel 창업의 핵심 가정.
  2. 기존 웹 검색은 “수천억 페이지와 수천억 질의”를 연결하는 수십억 대 수십억 매칭 문제로 설명됨.
  3. 초기 Parallel은 검색 엔진(search engine)이 아니라 검색 에이전트(search agent)를 먼저 출시 — 전체 인덱스를 미리 만들지 않고도 고객 문제를 풀기 위해.
  4. 초기 검색 에이전트는 쿼리 후 웹을 직접 크롤링할 수 있었고, 딥 리서치(deep research)는 1분에서 10분까지 기다릴 수 있다고 봄.
  5. Parallel Search를 쓰면 에이전트가 사용하는 토큰(token)이 대체로 절반 이하가 된다고 주장.
  6. 기존 제품은 검색 결과 생성에 약 3초의 읽기 시점 컴퓨트(read-time compute)를 썼지만, Turbo 제품은 이를 200밀리초로 줄였다고 말함.
  7. 일반 검색 에이전트도 답변 하나에 5~20회 검색을 할 수 있고, 고급 설정에서는 수백~수천 회 검색까지 갈 수 있음.
  8. 포트폴리오 1만 개 소기업의 신용 리스크 모니터링 예시 — 월 1회 사람이 하던 조사를 주간 자동화로 바꾸면 검색량 승수가 수십만~백만 배가 됨.
  9. 광고 기반 인터넷은 인간의 시선과 클릭을 전제로 하는데, 에이전트가 대신 방문하면 기존 수익 모델이 깨짐.
  10. 콘텐츠 소유자에게 의미 있는 금액이 돌아가는 시점을 12~24개월 내로 예상.
  11. 회사의 원래 법인명은 Shapley Inc.였고, 이후 AI용 병렬 웹(parallel web)이라는 개념에서 Parallel로 바꿈.
  12. 미래 웹은 “지금 찾아줘”에서 “이런 변화가 생기면 내 에이전트를 불러줘”로 바뀐다고 전망.

# 섹션 요지
1 Parallel의 문제의식 AI 에이전트는 인간과 다른 방식으로 웹을 사용하므로 검색도 새로 설계해야 한다
2 검색의 기본 구조 크롤링, 인덱싱, 검색, 랭킹은 방대한 매칭 문제다
3 왜 스타트업이 검색을 할 수 있나 인간 클릭 데이터 대신 에이전트 피드백과 모델 기반 평가를 쓴다
4 검색 에이전트부터 시작한 이유 전체 웹 인덱스 없이도 실무 문제를 풀며 점진적으로 인프라를 구축할 수 있다
5 품질·비용·지연시간 에이전틱 검색은 토큰과 지연시간을 줄여 모델의 능력을 확장한다
6 콘텐츠 경제의 붕괴와 재설계 광고와 구독 중심 웹은 에이전트 방문을 수익화하기 어렵다
7 샤플리값 기반 보상 콘텐츠가 답변 품질에 준 기여도를 추정해 보상하려 한다
8 미래의 웹 웹은 요청 기반 검색에서 변화 감지 기반 푸시 시스템으로 바뀐다

1. Parallel의 문제의식: 인간이 아니라 에이전트가 웹의 새 고객이다

Parallel Web Systems는 AI 에이전트가 웹을 검색하고 사용할 수 있게 만드는 기술을 만든다. Parag Agrawal의 핵심 가정은 단순하다.

에이전트는 인간보다 웹을 훨씬 더 많이 사용할 것이다.

사람은 검색창에 몇 단어를 넣고 결과를 몇 개 클릭한다. 반면 에이전트는 하나의 업무를 수행하기 위해 여러 검색을 반복하고, 문서의 특정 문단을 읽고, 비교하고, 검증하고, 다시 검색한다. 그래서 인간 클릭을 기준으로 만들어진 기존 검색 인프라는 에이전트에게 최적화되어 있지 않다.

그는 Parallel의 관점을 이렇게 요약한다.

인간 클릭 데이터는 에이전트 검색에서는 버그에 가깝다.
에이전트가 일을 하기 위한 검색은 인간 피드백(human feedback)이 아니라 에이전트 피드백(agent feedback)에 의존해야 한다.

2. 웹 검색은 거대한 매칭 문제다

웹 검색의 기본 문제는 “어디 있는지 모르는 정보를 가장 편한 위치에 보여주는 것”이다.

검색 엔진은 이를 위해 다음을 수행한다.

  1. 웹의 URL을 찾는다.
  2. 페이지를 읽는다.
  3. 정보를 인덱스(index)로 정리한다.
  4. 쿼리가 들어오면 관련 후보를 빠르게 찾는다.
  5. 수많은 후보 중 가장 관련성 높은 결과를 랭킹한다.

Parag는 이 문제를 수천억 개 페이지와 수천억 개 쿼리를 연결하는 매칭 문제라고 설명한다. 기존에는 이 규모 때문에 Google과 Bing 같은 거대 기업만 제대로 할 수 있다고 여겨졌다.

하지만 AI 모델과 에이전트가 등장하면서 상황이 달라졌다고 본다. 대규모 언어모델(LLM)은 정보를 압축하고 평가하는 능력이 뛰어나므로, 검색 인덱싱과 랭킹에도 이를 활용할 수 있다.

3. 왜 Parallel은 검색 엔진이 아니라 검색 에이전트부터 만들었나

검색 스타트업이 처음부터 전체 웹 인덱스를 구축하려면 막대한 비용이 든다. Parallel은 이 문제를 피하기 위해 처음에 검색 엔진이 아니라 검색 에이전트(search agent)를 출시했다.

검색 에이전트는 쿼리가 들어온 뒤 필요한 웹페이지를 직접 찾아가며 조사할 수 있다. 특히 딥 리서치(deep research) 업무에서는 사용자가 몇 초가 아니라 1분, 때로는 10분도 기다릴 수 있다. 즉, 지연시간(latency)을 어느 정도 포기하면 전체 웹 인덱스가 없어도 실무 가치를 만들 수 있다.

초기 고객 사례는 다음과 같다.

  • 보험 언더라이팅(insurance underwriting)
  • 보험 청구 처리(claims processing)
  • 영업 데이터 보강(sales data enrichment)
  • 금융 모델링을 위한 웹 데이터 수집
  • 사람이 밤새 수집하던 자료 조사 자동화

Parallel은 이 과정에서 실제 고객 업무에서 평가 데이터(eval)를 모았다. 이론적인 벤치마크보다 실전 사용 사례를 통해 “에이전트를 위한 검색이 무엇이어야 하는지”를 학습한 것이다.

4. 에이전틱 검색은 토큰, 비용, 속도의 최적화 문제다

기존 딥 리서치 방식은 모델이 Google 같은 검색 엔진을 반복 호출하는 구조였다. Parag는 이 방식도 어느 정도 효과가 있지만 충분하지 않다고 본다.

Parallel Search를 사용하면 대체로 에이전트가 쓰는 토큰(token)을 절반 이하로 줄일 수 있다고 말한다. 이는 세 가지 효과를 낸다.

  1. 같은 문제를 더 싸게 푼다.
  2. 같은 문제를 더 빠르게 푼다.
  3. 컨텍스트 한계(context limit) 안에서 더 복잡한 문제를 푼다.

그는 검색을 품질(quality), 비용(cost), 지연시간(latency)의 최적화 문제로 본다. 검색 결과에서 노이즈를 줄이고 신호(signal)만 모델에 넘기면, 모델은 더 적은 비용으로 더 좋은 일을 할 수 있다.

Parallel은 최근 Turbo 제품을 통해 에이전틱 검색을 약 200밀리초까지 줄였다고 설명한다.

5. 에이전트용 검색 인터페이스는 인간용 검색과 다르다

사람은 검색창에 보통 짧고 불완전한 단어를 입력한다. 오타도 있고, 자동완성에 의존한다. Parag는 이를 “인간은 게으르다”고 표현한다.

반면 AI 에이전트는 다음과 같은 특징을 가진다.

  • 더 긴 쿼리를 보낼 수 있다.
  • 오타가 적다.
  • 원하는 맥락을 더 잘 설명할 수 있다.
  • 검색 엔진이 추측해야 할 부분이 줄어든다.

따라서 에이전트용 검색은 단순 키워드 검색(keyword search)과 다른 인터페이스가 필요하다. 검색 엔진은 에이전트가 어떤 일을 수행 중인지 더 많이 알수록 더 좋은 결과를 줄 수 있다.

6. SEO 콘텐츠와 권위 있는 원본의 문제

진행자는 Google 상위 결과에 많은 SEO성 콘텐츠나 제휴 광고성 페이지가 있다고 지적한다. Parag는 이를 단순히 “쓰레기 콘텐츠”로만 보지 않는다.

예를 들어 어떤 상장사의 최신 매출 숫자를 찾는다고 하자. 가장 권위 있는 원천은 SEC 공시 PDF일 수 있다. 하지만 그 숫자는 300페이지짜리 PDF의 73페이지에 있을 수 있고, 로딩도 느리다.

그래서 누군가는 그 정보를 빠르게 읽을 수 있는 페이지로 정리한다. 중요한 숫자 20개를 상단에 배치하고, 사람에게 편하게 보여준다. 이는 게으른 인간에게 실제 가치를 제공한다.

하지만 에이전트에게는 이 우회로가 덜 필요하다. 에이전트는 원본 PDF에서 정확한 문단을 뽑아 컨텍스트 창(context window)에 넣으면 된다. 즉, 에이전트용 검색은 링크를 보여주는 것보다 권위 있는 원천의 정확한 발췌문(excerpt)을 전달하는 데 가까워진다.

7. Parallel 검색 API 내부 흐름

개발자가 Parallel의 에이전틱 검색 API에 쿼리를 보내면 대략 다음 과정이 일어난다.

  1. 모델이 쿼리를 이해하고 확장한다.
  2. 여러 인덱스 중 어떤 곳에 보낼지 결정한다.
  3. 각 인덱스에 맞게 쿼리를 다시 쓴다.
  4. 대규모 검색 계층(retrieval layer)이 후보 문서와 URL을 찾는다.
  5. 랭킹 계층(ranking layer)이 후보를 줄인다.
  6. 더 큰 모델들이 문단과 발췌문을 평가한다.
  7. 최종적으로 AI에게 넘길 약 1,000개 토큰을 고른다.

Parallel은 지연시간과 비용 조건에 따라 이 과정에 투입하는 컴퓨트를 다르게 조절한다.

8. 모델 회사가 직접 검색을 다 만들까

진행자는 LLM 회사들이 어차피 학습 데이터를 위해 웹을 크롤링하니 검색 인프라도 직접 소유하지 않겠느냐고 묻는다.

Parag는 학습용 크롤링과 검색용 크롤링은 다르다고 답한다.

모델 학습 회사는 토큰을 대량으로 모으는 것이 중요하다. 느린 자바스크립트 페이지나 복잡한 사이트를 끝까지 읽는 것은 효율이 떨어질 수 있다. 반면 Parallel은 에이전트가 실제 업무에서 필요로 하는 정보를 완결성 있게 가져오는 것이 중요하다.

즉, Parallel은 모델 자체가 아니라 모델을 강하게 만드는 보완재(complement)를 만든다.

9. Google Cloud와의 파트너십

Parag는 Google Cloud와의 협업을 언급한다. GCP에서 Gemini 모델이나 다른 LLM으로 에이전트를 만들 때 웹 검색을 붙이는 선택지로 Google Search와 Parallel Search가 제공된다는 내용이다.

여기서 Parallel은 그라운딩 제공자(grounding provider) 역할을 한다. 즉, 모델이 최신 웹 정보에 기반해 답하도록 돕는다.

10. 백그라운드 에이전트와 검색량 폭증

Parag는 에이전트가 인간 검색량을 크게 증폭한다고 설명한다.

예를 들어 ChatGPT 같은 앱에서 한 번 질문하면 내부적으로 5~10회 검색할 수 있다. 딥 리서치 모드에서는 수백~수천 회 검색할 수 있다.

더 큰 변화는 백그라운드 에이전트다. 예를 들어 대출을 내준 소기업 1만 곳의 위험도를 매월 사람이 점검하던 업무가 있다고 하자. 에이전트는 이를 매주 수행하고, 각 회사별 웹 데이터를 계속 확인할 수 있다. 이 경우 검색량은 수십만 배, 백만 배까지 늘어날 수 있다.

그는 자신 같은 얼리어답터는 이미 예전보다 100배에서 1,000배 많은 검색을 에이전트를 통해 발생시키고 있을 수 있다고 말한다. 다만 일반 대중 관점에서는 아직 에이전트 도입 초기라고 본다.

11. 광고 기반 인터넷의 균열

Parag는 광고를 단순히 싫어할 대상으로 보지 않는다. 광고는 Google Search, Twitter, 수많은 무료 콘텐츠를 가능하게 만든 효율적인 수익화 모델이었다.

문제는 광고 모델이 인간의 주의(attention)를 전제로 한다는 점이다. 사람이 웹사이트에 방문하고, 광고를 보고, 클릭하거나 구매해야 돈이 된다.

하지만 앞으로는 사람이 아니라 에이전트가 콘텐츠를 읽는다. 그러면 콘텐츠 소유자는 고민하게 된다.

  • 인간 방문은 원한다.
  • 에이전트 방문은 수익화하기 어렵다.
  • 그래서 에이전트를 차단하고 싶어진다.

이렇게 되면 웹 전체의 정보 접근성과 콘텐츠 생산 인센티브가 흔들린다.

12. 샤플리값으로 콘텐츠 보상을 설계한다

Parallel의 해법은 콘텐츠가 에이전트 결과물에 기여한 가치를 계산해 보상하는 것이다. 이를 위해 샤플리값(Shapley value) 개념을 활용한다.

핵심 아이디어는 다음과 같다.

어떤 콘텐츠 하나를 빼고 에이전트를 실행했을 때 결과 품질이 얼마나 떨어지는지 본다. 그 품질 저하를 다른 방법, 예를 들어 더 좋은 모델이나 더 많은 컴퓨트로 복구하려면 얼마가 드는지 계산한다. 그러면 그 콘텐츠의 경제적 가치에 대한 추정이 가능하다.

물론 실제 샤플리값을 완전 계산하려면 너무 비싸다. 그래서 Parallel은 시뮬레이션 데이터와 모델을 통해 이를 추정한다.

Parag가 원하는 보상 구조는 다음 속성을 가진다.

  • 고유하고 차별화된 데이터는 더 많이 받는다.
  • 고부가가치 업무에 쓰인 데이터는 더 많이 받는다.
  • 대형 출판사뿐 아니라 다양한 웹 콘텐츠 소유자가 참여할 수 있어야 한다.
  • 개별 협상 중심이 아니라 확장 가능한 시장 구조여야 한다.

그는 AI 추론(inference)에 쓰이는 지출 중 2~10%만 웹 데이터 보상으로 배분되어도, 현재의 웹 데이터 비즈니스보다 훨씬 큰 시장이 될 수 있다고 본다.

13. 회사 이름이 Parallel인 이유

흥미롭게도 회사의 원래 법인명은 Shapley Inc.였다. 하지만 B2B 제품명으로 적합하지 않았고, Shapley.com도 사용할 수 없었다.

Parallel이라는 이름은 두 가지에서 나왔다.

  1. 기술적으로 병렬 처리(parallel)를 많이 하고 있었다.
  2. 인간용 웹과 AI 에이전트용 웹이 나란히 존재하는 병렬 웹(parallel web)이 생길 것이라고 봤다.

앞으로 콘텐츠를 발행하는 사람은 두 독자를 동시에 고려하게 된다.

  • 인간이 읽기 좋은 페이지
  • 에이전트가 읽기 좋은 구조

14. 미래: 웹은 pull에서 push로 바뀐다

Parag는 에이전트 웹의 발전을 세 단계로 본다.

  1. 단순 에이전트가 웹 검색 도구를 사용한다.
  2. 여러 하위 에이전트(subagent)가 서로 호출하며 복잡한 작업을 한다.
  3. 웹이 pull 방식에서 push 방식으로 바뀐다.

현재는 에이전트가 “지금 이것을 찾아줘”라고 요청한다. 미래에는 “이런 일이 생기면 나를 불러줘”가 된다.

예를 들면 다음과 같다.

  • 특정 고객사가 새 공지를 올리면 알려줘.
  • 위성 이미지에서 특정 변화가 보이면 알려줘.
  • 경쟁사 가격이 바뀌면 내 에이전트를 실행해줘.
  • 어떤 시장 신호가 감지되면 리포트를 만들어줘.

이때 Parallel은 계속 변하는 웹 전체를 감시하고, 고객 에이전트가 행동해야 할 순간을 알려주는 인프라가 될 수 있다.

에이폼 적용 관점

③ 우리 상황과 다른 전제 하나: Parallel은 대규모 웹 인프라와 API 사업 관점이고, 에이폼은 당장 운영 효율을 높이는 내부 자동화부터 시작해야 한다.

전체 전사 펼치기

Parallel의 관점은 인간 클릭 데이터(human click data)가 에이전트 검색에서는 오히려 버그에 가깝다는 것이다. 검색으로 일을 수행하는 에이전트는 인간 피드백이 아니라 에이전트 피드백(agent feedback)에 의존해야 한다. 모델은 정보를 압축하는 능력이 뛰어나고, 모델 연구에서 나온 성과를 검색 인덱싱(indexing)과 랭킹(ranking)에 적용할 수 있다. 그래서 에이전트가 기술일 뿐 아니라 새로운 고객으로 등장한 지금, 웹 검색 문제는 예전보다 훨씬 다루기 쉬워졌다고 본다.

진행자는 Parag Agrawal을 소개한다. 그는 Twitter CEO였고, Elon Musk에게 Twitter를 매각한 뒤 Parallel Web Systems를 창업했다. Parallel은 에이전틱 웹(agentic web)을 위한 에이전틱 검색(agentic search)을 확장하는 회사다.

Parag는 Parallel이 에이전트가 웹을 검색하고 사용할 수 있게 하는 기술을 만든다고 설명한다. 인간이 브라우저, 검색엔진, 클릭, 탐색을 통해 정보를 얻어왔듯이 에이전트도 웹을 사용할 방법이 필요하다. Parallel은 에이전트가 인간보다 웹을 1,000배 더 많이 사용할 것이라는 가정에서 출발했다. 따라서 검색 기술뿐 아니라 그에 맞는 비즈니스 모델도 새로 만들어야 한다.

Twitter 시절과 Parallel 창업의 차이에 대해서는, Twitter는 이미 제품시장적합성(product-market fit)을 찾은 거대 서비스였고 매일 수억 명이 30분 이상 쓰는 제품이었다고 말한다. 반면 Parallel은 아직 오지 않은 새로운 고객, 즉 에이전트를 위해 제품시장적합성 이전 단계에서 기술을 만드는 회사다.

웹 검색의 기본 문제는 사용자가 웹 어디에 있는지 모르는 정보를 찾고 싶을 때, 검색엔진이 가장 편리한 위치에 답을 보여주는 것이다. 검색엔진은 웹의 모든 URL을 찾고, 읽고, 정보를 인덱스에 정리한다. 쿼리가 들어오면 페이지를 새로 읽지 않고 미리 정리된 정보를 바탕으로 관련 결과를 빠르게 찾고 순위를 매긴다. 이는 수천억 페이지와 수천억 쿼리를 연결하는 거대한 매칭 문제다.

검색 인프라는 매우 비싸고 오랫동안 Google과 Bing 같은 대기업만 할 수 있는 일처럼 보였다. 하지만 Parag는 AI 모델과 에이전트 때문에 새 기회가 생겼다고 본다. 과거에는 검색 품질을 평가하려면 인간 평가나 클릭 데이터가 필요했다. 이제는 모델과 에이전트를 통해 더 싸고 풍부한 평가 데이터를 만들 수 있다. Parallel은 인간 클릭 데이터보다 에이전트 피드백이 에이전트 검색에 더 적합하다고 본다.

Parallel은 처음부터 전체 웹 인덱스를 구축하지 않았다. 대신 검색 엔진이 아니라 검색 에이전트를 먼저 출시했다. 검색 에이전트는 쿼리가 들어온 뒤 필요한 페이지를 직접 찾아가며 조사할 수 있다. 딥 리서치 업무라면 사용자는 1분, 때로는 10분도 기다릴 수 있다. 인덱스는 많은 경우 지연시간 최적화(latency optimization)이므로, 초기에는 지연시간을 일부 포기하고 사람이 하던 웹 조사 업무를 대체하는 방식으로 시작했다.

초기 사용 사례는 보험 언더라이팅, 보험 청구 처리, 영업 데이터 보강, 금융 모델링용 데이터 수집 등이었다. Parallel은 외주 인력이 웹에서 데이터를 수집하던 업무를 대체하며 실제 평가 데이터(eval)를 모았다. 이론적 벤치마크가 아니라 실제 고객 문제를 통해 에이전트를 위한 검색이 무엇인지 배운 것이다.

Parallel은 자신들을 새로운 모델 연구소(new lab)로 분류하지 않는다. 그들의 산출물은 모델 자체가 아니라 모델을 보완하는 시스템이다. 더 좋은 모델이 나오면 Parallel의 가치는 줄어드는 것이 아니라 더 많은 사용 사례가 가능해진다고 본다. 그들은 거대한 모델을 사전학습(pre-training)하기보다 작은 랭킹 모델(ranking model)로 정보를 압축하는 일을 한다.

검색은 “웹의 수조 개 정보 중 AI에게 넘길 올바른 1,000개 토큰을 고르는 문제”로 볼 수 있다. 이전에는 읽기 시점에 약 3초 동안 컴퓨트를 사용했지만, 최근 Turbo 제품은 이를 200밀리초로 줄였다. 제한된 비용과 지연시간 안에서 어떤 모델을 어떻게 훈련하고, 메모리 계층(memory hierarchy)에 정보를 어떻게 배치할지가 핵심 연구 문제다.

기존 딥 리서치 방식은 모델이 Google 같은 검색엔진을 반복 호출하는 형태였다. Parag는 이것도 어느 정도 작동하지만 충분하지 않다고 말한다. Parallel Search를 사용하면 에이전트가 쓰는 토큰을 대체로 절반 이하로 줄일 수 있고, 정확도와 속도도 좋아진다고 주장한다. 검색 결과에서 신호는 유지하고 노이즈를 줄이면 모델은 더 많은 일을 할 수 있다.

에이전트용 검색 인터페이스는 인간용 검색과 다르다. 인간은 검색창에 짧고 불완전한 단어를 넣고 오타도 낸다. Parag는 인간이 게으르다고 말한다. 반면 모델은 더 긴 쿼리와 명확한 맥락을 제공할 수 있다. 검색엔진이 사용자의 의도를 추측해야 할 부분이 줄어드는 것이다.

진행자는 Google 상위 결과에 SEO성 콘텐츠나 제휴 광고성 페이지가 많다고 지적한다. Parag는 이를 인간의 게으름에 맞춘 결과로 설명한다. 예를 들어 상장사의 최신 매출 숫자는 SEC 공시 PDF의 73페이지에 있을 수 있다. 하지만 인간은 느린 PDF를 열고 페이지를 찾기 싫어한다. 그래서 누군가 핵심 숫자를 빠르게 로딩되는 페이지 상단에 정리해 올리고, 이는 실제 가치를 제공한다. 에이전트의 경우에는 이런 우회 페이지보다 권위 있는 원본에서 정확한 발췌문을 가져와 컨텍스트 창에 넣는 것이 더 적합하다.

Parallel의 검색 API는 쿼리를 받으면 먼저 모델로 쿼리를 이해하고 확장한다. 그런 다음 큰 인덱스, 신선한 인덱스(fresh index), 구조화 인덱스(structured index), 지식 그래프(knowledge graph)와 비슷한 시스템들 중 어디에 보낼지 결정한다. 각 시스템에 맞게 쿼리를 다시 쓰고, 검색 계층과 랭킹 계층을 거쳐 수십억 문서에서 수천, 수만 후보로 줄인다. 이후 더 큰 모델들이 문단과 발췌문을 평가해 최종적으로 AI에게 전달할 1,000개 토큰을 고른다.

품질의 북극성 지표에 대해 Parag는 이 문제가 영원히 계속되는 최적화 문제라고 답한다. 검색은 수십억 대 수십억 매칭 문제이므로 완성이라는 상태는 없고, 추가 개선의 가치가 비용보다 작아지는 순간만 있을 뿐이다. AI 지능이 몇 달마다 더 싸지고 좋아진다면 검색 품질도 계속 밀어붙일 이유가 있다고 본다.

모델 회사들이 검색 인프라까지 직접 소유할 것이라는 견해에 대해서는, 학습용 크롤링과 에이전트 검색용 크롤링은 다르다고 말한다. 모델 회사는 많은 토큰을 효율적으로 모으는 것이 중요하기 때문에 느린 자바스크립트나 복잡한 사이트를 완결적으로 읽는 데 인내심이 적다. Parallel은 오히려 그런 정보까지 완성도 있게 수집하려 한다. 다만 LLM으로 일을 하는 10개 중 9개 사용 사례는 웹 접근이 필요할 것이므로, 모델 회사가 직접 만들거나 사거나 파트너십을 맺는 흐름은 생길 것이라고 본다.

Parag는 Google Cloud와의 협업을 언급한다. GCP에서 Gemini 모델이나 다른 모델로 에이전트와 채팅 앱을 만들 때 웹 검색을 붙이면 Google Search 또는 Parallel Search를 선택할 수 있다. Parallel은 검색 및 그라운딩 제공자(grounding provider)로 통합되어 있다.

에이전트가 만드는 검색량 증가에 대해서는, 일반 검색 에이전트도 몇 초 안에 답하면서 5~20회 검색할 수 있다고 설명한다. 더 높은 단계에서는 수백, 수천 회 검색도 가능하다. 사람이 한 번 프롬프트를 입력해도 AI 앱 내부에서는 검색량이 한 자릿수 이상 늘어날 수 있다.

더 큰 승수는 백그라운드 에이전트에서 나온다. 예를 들어 1만 개 소기업에 신용을 제공한 금융사가 매월 사람이 리스크를 점검하던 일을 매주 에이전트로 자동화하면 검색량은 수십만 또는 백만 배 늘 수 있다. 회의 준비 문서를 만드는 에이전트도 한 번 프롬프트를 만들어두면 매 회의마다 수십, 수백 번의 웹 검색을 수행할 수 있다.

Parallel은 처음 몇 년간 품질과 비용에 집중하고 지연시간은 덜 신경 썼다. 품질과 비용을 각 가격대에서 충분히 개선한 뒤 지연시간을 줄였고, 그 결과 Turbo를 출시했다고 말한다.

웹 트래픽에서 AI 트래픽이 인간 트래픽과 비슷해지고 있다는 Cloudflare의 관찰도 언급된다. 다만 검색량 기준과 페이지 읽기 기준은 다르며, 아직 에이전트 도입은 매우 초기라고 본다.

인터넷 경제에 대해 Parag는 광고를 지적으로는 좋아한다고 말한다. 광고 덕분에 Google Search, Twitter, 많은 웹 콘텐츠가 무료로 제공될 수 있었다. 광고는 차등 가격 책정(differential pricing)에 뛰어난 수익화 방식이다. 많은 검색이나 사용자는 손해를 보지만, 일부 고가치 광고가 이를 보조한다.

문제는 광고가 인간의 제한된 주의와 클릭을 전제로 한다는 점이다. 인간 대신 에이전트가 웹에 오면 기존 수익 모델이 작동하지 않는다. 구독 사업자도 인간 방문자 1,000명 중 20명을 전환시키는 방식은 알지만, 에이전트 방문이 구독으로 이어지는지는 알기 어렵다. 그래서 콘텐츠 소유자는 에이전트 접근을 차단하려 할 수 있다.

기존에는 고품질 콘텐츠 소유자가 AI 회사와 고정 수수료 계약을 맺는 것이 거의 유일한 선택지였다. 하지만 이는 대형 콘텐츠에만 가능한 방식이고, AI 추론 사용량이 7배, 다시 7배 늘어 50배가 되어도 계약 금액이 50배 늘지는 않는다. 따라서 지속 가능한 모델이 아니라고 본다.

Parallel의 해법은 콘텐츠의 기여도와 사용 가치에 따라 보상하는 것이다. 고유하고 가치 있는 콘텐츠에는 더 많이 지불하고, 같은 콘텐츠라도 고부가가치 업무에 쓰이면 더 많이 지불하는 구조다. 이를 확장 가능하고 인센티브가 맞는 방식으로 만들어야 한다.

모델 회사들이 콘텐츠에 돈을 내는 이유는 세 가지로 설명된다. 첫째, ChatGPT 같은 제품에서 최신 데이터를 추론 시점에 보여주기 위해서다. 둘째, 학습 데이터가 필요해서다. 셋째, 이미 수행한 학습에 대한 법적 책임 보호가 필요해서다.

여러 출처가 하나의 답변에 기여했을 때 어떻게 귀속(attribution)하느냐는 질문에, Parag는 샤플리값(Shapley value)을 설명한다. 샤플리값은 협력 게임이론의 개념으로, 여러 참여자가 함께 만든 더 큰 가치를 각자에게 어떻게 공정하게 나눌지 계산하는 방법이다. 머신러닝에서는 특성 중요도(feature importance)를 계산할 때도 쓰인다.

실제 샤플리값 계산은 매우 비싸다. 모든 조합에서 어떤 콘텐츠가 빠졌을 때 결과가 어떻게 달라지는지 시뮬레이션해야 하기 때문이다. 콘텐츠 소유자에게 1달러를 지급하려는데 계산에 몇 달러가 들면 말이 안 된다. 그래서 Parallel은 시뮬레이션과 모델을 통해 샤플리값을 잘 추정하려 한다.

Parag는 고유한 데이터가 있으면 더 많이 받고, 은행가가 고부가가치 업무에서 데이터를 읽으면 은퇴한 아버지가 읽는 것보다 더 높은 가치가 매겨지는 구조를 예로 든다. AI 지식노동 추론 비용의 2~10%만 웹 데이터에 배분되어도, Facebook이나 LinkedIn 같은 폐쇄형 정원(walled garden)을 제외한 현재 웹 데이터 비즈니스보다 훨씬 큰 시장이 될 수 있다고 본다. 그는 12~24개월 안에 다양한 콘텐츠 소유자에게 의미 있는 금액이 돌아갈 수 있다고 예상한다.

회사 이름에 대해서는 원래 법인명이 Shapley Inc.였다고 말한다. 하지만 B2B 제품명으로 좋지 않았고, Shapley.com은 사용할 수 없는 도메인이었다. 이후 병렬 처리와 AI를 위한 병렬 웹(parallel web)이라는 개념에서 Parallel이라는 이름을 택했다. 앞으로 콘텐츠 발행자는 인간 독자와 에이전트 독자를 동시에 고려하게 될 것이라고 본다.

실적 발표 녹취나 API 문서처럼 이미 에이전트가 더 많이 읽는 웹 영역도 있다. Parallel도 API 문서를 만들 때 인간보다 고객의 에이전트가 읽는 것을 주요 독자로 보고 테스트한다고 말한다.

마지막으로 Parag는 Parallel의 미래를 세 단계로 설명한다. 첫째, 단순 에이전트가 웹 검색 도구를 사용한다. 둘째, 여러 하위 에이전트(subagent)가 서로를 깨우고 조율하는 복잡한 멀티에이전트 시스템이 등장한다. 셋째, 웹은 pull에서 push로 바뀐다. 지금은 에이전트가 “지금 찾아줘”라고 요청하지만, 앞으로는 “이런 일이 생기면 불러줘”가 된다.

미래에는 위성 이미지 변화, 고객 발언, 다른 에이전트의 작업 완료, 인간의 새로운 통찰, 웹의 변경 사항 같은 신호가 다음 에이전트 작업을 촉발한다. Parallel은 변화하는 웹 전체에 컴퓨트를 배분하고, 고객에게 행동 가능한 순간을 알려주는 역할을 하려 한다.
