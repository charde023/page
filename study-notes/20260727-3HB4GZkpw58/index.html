당신은 에이전트 스킬을 제대로 사용하지 못하고 있습니다

한 줄 요약

에이전트 스킬(Agent Skill)은 반복 프롬프트를 저장하는 수준이 아니라, 설명(description), 지식, 참조자료, 자산(asset), 스크립트(script)를 조합해 에이전트가 필요한 순간에 정확한 방식으로 일하게 만드는 재사용 가능한 작업 단위다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
에이전트 스킬(Agent Skill) AI 에이전트가 특정 상황에서 원하는 방식으로 일하게 만드는 기본 단위 skill.md는 시작일 뿐이고, 참조자료·자산·스크립트까지 포함할 수 있다
점진적 발견(Incremental Discovery) 모든 내용을 매번 컨텍스트에 넣지 않아 토큰 낭비와 성능 저하를 줄임 처음에는 메타데이터만 읽고, 필요할 때 본문과 추가 자료를 읽는다
지식 격차(Knowledge Gap) 모델이 특정 라이브러리·도메인을 잘 모를 때 보완 가능 공식 문서나 사내 지식을 스킬로 만들어 반복 검색을 줄인다
실행 격차(Execution Gap) 모델이 “알긴 알지만” 내가 원하는 절차대로 일하지 않을 때 필요 계획 작성, 리뷰, 복잡도 판단 같은 작업 방식을 스킬로 고정한다
스크립트와 스킬의 조합 결정적인 작업은 코드가, 애매한 판단은 에이전트가 맡게 할 수 있음 API 호출·파일 저장은 스크립트, 프롬프트 변환·판단은 스킬이 담당한다
전역 스킬(Global Skill)과 프로젝트 스킬(Project Skill) 모든 세션에 불필요한 스킬이 노출되면 모델 성능이 떨어질 수 있음 어디서나 쓰는 것은 전역, 특정 프로젝트 지식은 프로젝트 안에 둔다
Agents.md / Claude.md와 스킬의 차이 항상 적용되어야 하는 규칙과 필요할 때만 쓰는 도구를 구분해야 함 항상 지켜야 할 규칙은 Agents.md, 자주 쓰지만 항상은 아닌 패턴은 스킬

내가 모를 만한 것 / 처음 보는 것

  • 에이전트 스킬(Agent Skill) — AI 에이전트가 특정 작업을 할 때 참고하는 재사용 가능한 지침 묶음.
  • skill.md — 스킬의 핵심 설명과 작업 지침을 담는 마크다운 파일.
  • 설명(description) — 에이전트가 “이 스킬을 언제 켤지” 판단하게 만드는 메타데이터.
  • 점진적 발견(Incremental Discovery) — 처음부터 모든 내용을 로드하지 않고, 필요할 때 단계적으로 더 많은 자료를 읽는 방식.
  • 자산(asset) — 스킬에서 함께 쓰는 템플릿, 블루프린트, 설정 파일 같은 보조 자료.
  • 블루프린트(blueprint) — 계획서나 산출물의 정해진 구조를 담은 틀.
  • 스크립트(script) — 반복적이고 결정적인 작업을 자동 실행하기 위한 코드.
  • Fal — 여러 AI 모델을 API로 제공하는 서비스. 이미지·텍스트·오디오·비디오 생성 등에 사용 가능.
  • GPT-Image-2 — 화자가 이미지 생성 스킬에서 하드코딩해 둔 이미지 모델.
  • PyCoding agent — 화자가 주로 사용한다고 언급한 코딩 에이전트. 전사상 “Py”로 들리며 정확한 제품명은 [?PyCoding agent].
  • 서브 에이전트(sub-agent) — 큰 작업을 쪼개 병렬 또는 분담 처리하는 보조 에이전트.
  • Agents.md / Claude.md — 에이전트가 항상 참고하는 전역 또는 프로젝트별 규칙 파일.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 스킬은 skill.md 파일 하나로 끝나지 않는다 — 참조자료(reference), 자산(asset), 블루프린트(blueprint), 스크립트(script)를 함께 가질 수 있다.
  2. 스킬은 매 세션에서 전체가 로드되는 것이 아니라, 보통 메타데이터와 설명(description)만 먼저 로드된다 — 이후 에이전트가 필요하다고 판단하면 본문을 읽는다.
  3. 이미지 생성 스킬에는 TypeScript 스크립트가 들어 있고, Fal API를 호출한다 — 요청 전송, 응답 처리, 이미지 추출, 저장 같은 결정적 작업은 스크립트가 맡는다.
  4. 이미지 모델은 화자의 경우 GPT-Image-2로 하드코딩되어 있다 — 여러 모델 중 본인이 쓰고 싶은 모델 하나만 고정한 예시다.
  5. “자전거가 비를 맞는 이미지가 필요해” 같은 모호한 요청은 스킬이 좋은 이미지 생성 프롬프트로 바꾼다 — 이 부분은 스크립트보다 에이전트가 잘하는 영역이다.
  6. 스킬을 쓰는 이유는 크게 두 가지다 — 지식 격차(Knowledge Gap)와 실행 격차(Execution Gap)를 줄이기 위해서다.
  7. Effect 라이브러리(Effect library)는 모델 학습 데이터에 충분히 반영되지 않았을 수 있어 스킬로 보완하기 좋다고 말한다.
  8. 좋은 스킬은 좋은 description + 간결하고 실행 가능한 본문으로 구성된다.
  9. 화자는 긴 산문보다 불릿 포인트(bullet points) 중심의 스킬을 선호한다 — 장황한 스킬은 토큰을 낭비하고 컨텍스트를 오염시킨다.
  10. 스킬은 정적 파일이 아니라 계속 진화해야 한다 — 모델, 코딩 에이전트, 도구, 시스템 프롬프트, 사용자 작업 방식이 계속 바뀌기 때문이다.
  11. 화자는 스킬 유형을 네 가지로 나눈다 — 도메인 지식(domain knowledge), 워크플로(workflow), 컴패니언(companion), 실행형(executable).
  12. 전역 스킬은 최소화해야 한다 — 전역 스킬의 메타데이터는 모든 세션에 로드되므로 많아질수록 모델 성능에 악영향을 줄 수 있다.
  13. 항상 적용되어야 하는 규칙은 스킬이 아니라 Agents.md나 Claude.md에 둔다 — 스킬은 “활성화”되어야 하므로 항상 적용된다고 보장할 수 없다.
  14. 예시 규칙으로 “응답을 짧게 하라”, “레거시 코드나 폴백 코드를 덧붙이지 말라”를 들었다 — 일부 모델은 기존 코드를 지우지 않고 층층이 덧붙이는 경향이 있기 때문이다.

# 섹션 요지
1 스킬은 skill.md 하나가 아니다 참조자료, 자산, 스크립트를 포함할 수 있는 작업 패키지다
2 스킬이 필요한 이유 모델의 지식 부족과 실행 방식 차이를 보완한다
3 스크립트와 스킬의 역할 분리 결정적 작업은 스크립트, 해석과 판단은 스킬이 맡는다
4 좋은 스킬 작성법 description은 명확하게, 본문은 짧고 실행 가능하게 쓴다
5 스킬은 계속 관리해야 한다 모델과 도구가 바뀌므로 스킬도 수정·폐기·개선해야 한다
6 네 가지 스킬 유형 도메인 지식, 워크플로, 컴패니언, 실행형으로 나눠 볼 수 있다
7 어디에 둘 것인가 전역 스킬은 최소화하고 프로젝트 지식은 프로젝트 안에 둔다
8 Agents.md와의 구분 항상 적용할 규칙은 Agents.md / Claude.md, 필요할 때 쓰는 패턴은 스킬이다

1. 스킬은 단순한 skill.md 파일이 아니다

화자는 많은 사람이 에이전트 스킬(Agent Skill)을 알고는 있지만, 실제로는 제대로 활용하지 못한다고 말한다.

일반적으로 스킬은 skill.md 파일로 시작한다. 이 파일에는 두 가지가 들어간다.

첫째, 설명(description)이다. 설명은 에이전트가 “지금 이 스킬을 써야 하는 상황인가?”를 판단하게 해준다.

둘째, 실제 작업 지침이다. 이것은 코딩 에이전트(coding agent)나 다른 에이전트에게 추가로 주입되는 문맥(context)이며, 결국 프롬프트(prompt)의 일종이다.

하지만 중요한 점은 스킬이 반드시 skill.md 하나로 끝나지 않는다는 것이다. 어떤 스킬은 파일 하나로 충분하지만, 많은 경우에는 추가 자료가 필요하다.

예를 들어 다음을 포함할 수 있다.

  • 참조자료(reference)
  • 심화 자료(deep-dive resource)
  • 자산(asset)
  • 블루프린트(blueprint)
  • 스크립트(script)
  • 설정 템플릿(configuration template)

스킬은 점진적 발견(Incremental Discovery) 방식으로 작동한다. 즉, 매번 스킬 전체가 컨텍스트에 들어가는 것이 아니다. 처음에는 메타데이터와 설명 정도만 로드되고, 에이전트가 필요하다고 판단하면 그때 본문을 읽는다. 본문 안에서 추가 참조자료를 가리키면, 필요한 순간에 그 자료도 읽을 수 있다.

이 방식은 토큰을 아끼고, 불필요한 정보가 컨텍스트를 어지럽히는 것을 줄인다.

2. 스킬에는 자산과 스크립트도 들어갈 수 있다

화자는 “많은 사람이 참조자료까지는 알지만, 스킬에 자산(asset)이나 스크립트(script)를 넣을 수 있다는 점은 덜 안다”고 말한다.

예를 들어 화자의 create plan 스킬에는 계획을 만들 때 사용할 계획 블루프린트(plan blueprint)가 들어 있다. 에이전트가 계획서를 만들 때 매번 같은 구조로 작성하게 하기 위한 틀이다.

또 다른 예시는 이미지 생성 스킬(generate image skill)이다. 이 스킬은 AI로 이미지를 생성하는 작업을 돕는다. 내부에는 TypeScript 스크립트가 있고, 이 스크립트는 Fal이라는 서비스를 사용한다.

Fal은 여러 AI 모델을 API로 제공하는 서비스다. 텍스트, 이미지, 오디오, 비디오 등을 생성할 수 있다. 화자의 이미지 생성 스킬에서는 GPT-Image-2 모델을 하드코딩해 사용한다.

여기서 자연스럽게 질문이 생긴다.

“그냥 스크립트만 쓰면 되지, 왜 스킬까지 필요한가?”

화자의 답은 이렇다. 어떤 작업은 스크립트만으로 충분하지만, 어떤 작업은 스킬과 스크립트를 함께 쓰는 것이 좋다.

이미지 생성 예시에서 역할은 이렇게 나뉜다.

  • 스크립트: 요청 보내기, 응답 처리하기, 이미지 추출하기, 파일로 저장하기
  • 스킬: 사용자의 모호한 요청을 좋은 이미지 생성 프롬프트로 바꾸기, 적절한 방식으로 스크립트 호출하기

예를 들어 사용자가 “비 오는 날 자전거 이미지가 필요해”라고 말하면, 스킬은 이 모호한 요청을 이미지 모델에 적합한 프롬프트로 바꾼다. 그 뒤 실제 API 호출과 저장은 스크립트가 처리한다.

즉, 결정적이고 반복 가능한 작업은 스크립트가 맡고, 해석과 판단이 필요한 부분은 에이전트와 스킬이 맡는 구조다.

3. 스킬의 첫 번째 목적: 지식 격차 줄이기

화자는 에이전트 스킬이 필요한 이유를 두 가지로 나눈다. 첫 번째는 지식 격차(Knowledge Gap)를 줄이는 것이다.

AI 모델은 학습 데이터, 파인튜닝(fine-tuning), 강화학습(reinforcement learning)을 통해 어느 정도 지식을 갖고 있다. 여기에 사용자가 주는 프롬프트, 코드베이스(code base), 웹 리서치(web research)를 통해 추가 정보를 얻을 수도 있다.

하지만 특정 도메인이나 특정 라이브러리에 대해서는 모델이 충분히 알지 못할 수 있다.

화자는 Effect 라이브러리(Effect library)를 예로 든다. 이 라이브러리는 모델이 React나 Express처럼 많이 학습했을 가능성이 낮을 수 있다. 따라서 모델이 공식 문서에 맞게 제대로 사용하지 못할 수 있다.

이럴 때 Effect 관련 지식을 스킬로 만들 수 있다.

화자의 방식은 다음과 같다.

  1. AI에게 웹 리서치를 시킨다.
  2. 공식 문서와 중요한 URL을 읽게 한다.
  3. 필요한 지식을 모으게 한다.
  4. 그 내용을 스킬로 변환하게 한다.
  5. 사람이 직접 다듬어 최종 스킬로 만든다.

이렇게 해두면 에이전트가 Effect 코드베이스에서 작업할 때 해당 스킬을 활성화할 수 있다. 매번 공식 문서를 다시 검색하지 않아도 되고, 프로젝트에 맞는 지식을 더 안정적으로 사용할 수 있다.

이 방식은 비개발자 입장에서 보면 “사내 업무 매뉴얼”이나 “상품 등록 규칙”, “CS 응대 기준”, “물류 예외 처리 규칙”을 AI가 매번 검색하지 않고 바로 참고하게 만드는 것과 비슷하다.

4. 스킬의 두 번째 목적: 실행 격차 줄이기

두 번째 목적은 실행 격차(Execution Gap)를 줄이는 것이다.

모델이 어떤 작업을 수행할 지식은 갖고 있어도, 내가 원하는 방식으로 수행하지 않을 수 있다. 예를 들어 계획을 만들 수는 있지만, 내가 검토하기 쉬운 구조로 만들지는 않을 수 있다. 리뷰를 할 수는 있지만, 너무 사소한 지적을 많이 하거나 불필요한 복잡도를 추가할 수도 있다.

화자는 create plan 스킬을 예로 든다. 코딩 에이전트가 작업을 시작하기 전에 계획을 만들게 하는 스킬이다.

일부 코딩 에이전트에는 계획 모드(plan mode)가 내장되어 있지만, 화자가 주로 쓰는 [?PyCoding agent]에는 계획 모드가 없다고 한다. Claude Code 같은 도구를 쓸 때도 요즘은 내장 계획 모드보다 직접 만든 계획 스킬을 선호한다고 말한다.

그 이유는 자신이 원하는 계획 작성 방식을 스킬에 명확히 넣을 수 있기 때문이다.

화자의 계획 스킬에는 다음 내용이 포함된다.

  • 작업 전 리서치를 수행할 것
  • 필요하면 서브 에이전트(sub-agent)에게 위임할 것
  • 일을 어떻게 나눌지 판단할 것
  • 정해진 계획 템플릿을 따를 것
  • 사용자가 검토하기 쉬운 구조로 작성할 것
  • 계획을 제출하기 전에 리뷰 단계를 거칠 것

또 계획 리뷰(code review / plan review)를 위한 별도 스킬도 있다. 이 리뷰 스킬에는 발견 사항을 어떻게 점수화할지, 모든 지적을 계획에 반영하지 말고 실제로 중요한지 판단할 것, 불필요한 복잡도를 추가하지 말 것 같은 규칙이 들어 있다.

복잡도를 판단하는 de-complex 스킬도 따로 있다. 이 스킬은 “무엇이 과도한 복잡도인가”, “복잡도를 어떻게 점검할 것인가”를 정의한다.

이처럼 여러 스킬이 연결되면, 에이전트는 단순히 “계획을 만들어주는 것”을 넘어 화자가 원하는 방식으로 조사하고, 나누고, 리뷰하고, 실행 가능한 계획을 만든다.

5. 반복해서 말하는 요구사항은 스킬로 만들어라

화자는 같은 요청을 반복하고 있다면 스킬로 만들라고 조언한다.

예를 들어 매번 AI에게 다음과 같이 말하고 있다면, 그것은 스킬 후보가 된다.

  • “계획부터 세워줘.”
  • “공식 문서 기준으로 확인해줘.”
  • “너무 복잡하게 만들지 마.”
  • “불필요한 폴백 코드는 넣지 마.”
  • “결과를 이 형식으로 정리해줘.”
  • “리뷰 후 중요한 것만 반영해줘.”

또는 같은 실수에 계속 불평하고 있다면, 그것도 스킬로 만들 수 있다.

다만 남이 만든 스킬을 그대로 모으기만 해서는 안 된다. 화자는 자신의 스킬이나 Matt Pocock의 스킬 등 공개된 좋은 스킬을 시작점으로 쓰는 것은 괜찮다고 말한다. 하지만 반드시 자기 업무 방식에 맞게 고쳐야 한다.

사람마다 일하는 방식이 다르기 때문이다. 화자에게 잘 맞는 스킬이 나에게도 잘 맞는다는 보장은 없다. 따라서 공개 스킬은 참고하되, 자기 워크플로와 반복 문제에 맞게 직접 다듬어야 한다.

6. 좋은 스킬은 짧고 명확해야 한다

좋은 스킬의 핵심은 두 가지다.

첫째, 좋은 설명(description)이다. 설명이 좋아야 에이전트가 적절한 순간에 스킬을 활성화한다.

둘째, 간결하고 실행 가능한 본문이다. 화자는 긴 산문보다 불릿 포인트 중심의 스킬을 선호한다. 꼭 불릿이어야 하는 것은 아니지만, 장황한 설명은 피해야 한다.

AI에게 스킬 작성을 맡길 수도 있다. 화자도 그렇게 한다. 하지만 AI는 종종 지나치게 친절하고 장황한 스킬을 만든다. 그래서 사람이 반드시 다음 방향으로 다듬어야 한다.

  • 짧게 만들기
  • 실행 가능한 지침으로 바꾸기
  • 불필요한 설명 제거하기
  • 너무 일반적인 말 제거하기
  • 실제 반복 업무에 맞게 조정하기

장황한 스킬은 두 가지 문제가 있다.

  1. 토큰 비용이 늘어난다.
  2. 컨텍스트가 오염되어 결과가 나빠질 수 있다.

스킬은 한 번 만들면 반복해서 쓰이므로, 처음 만들 때 시간을 들여 잘 다듬는 편이 낫다.

7. 스킬은 계속 진화해야 한다

스킬은 한 번 설치하고 끝나는 정적 파일이 아니다. 시간이 지나면 계속 바꿔야 한다.

이유는 여러 가지다.

  • 모델이 바뀐다.
  • 어떤 모델은 더 공격적으로 수정하고, 어떤 모델은 더 장황하게 답한다.
  • 코딩 에이전트의 도구와 동작 방식이 바뀐다.
  • 에이전트가 내부적으로 추가하는 시스템 프롬프트(system prompt)가 바뀐다.
  • 사용자 자신이 일하는 방식도 바뀐다.

화자는 1년 전과 지금을 비교하며, 사람들이 직접 코드를 쓰는 양도 달라졌고, 코드를 읽는 방식과 양도 달라졌다고 말한다. 그러면 당연히 스킬도 바뀌어야 한다.

화자는 “스킬 개선 스킬(improve skill skill)”을 만드는 것도 고려해볼 만하다고 말한다. 에이전트가 자주 틀리거나, 사용자가 자주 고치는 내용이 이미 스킬에 들어 있는데도 반영되지 않는다면, 에이전트가 그 스킬 자체를 개선하게 만드는 방식이다.

중요한 결론은 이것이다.

반년 전에 설치한 스킬이 지금도 유용하다고 가정하면 안 된다.

필요하면 개선하고, 필요 없으면 버리고, 자기만의 스킬을 새로 만들어야 한다.

8. 네 가지 스킬 유형

화자는 스킬을 네 가지 유형으로 나눈다. 물론 실제로는 서로 겹칠 수 있다.

유형 설명 예시
도메인 지식 스킬(Domain Knowledge Skill) 특정 라이브러리, 산업, 프로젝트 지식을 담는 스킬 Effect 라이브러리 공식 문서 기반 스킬
워크플로 스킬(Workflow Skill) 반복되는 작업 절차를 정해진 방식으로 수행하게 하는 스킬 계획 작성(create plan), 리뷰, 작업 분할
컴패니언 스킬(Companion Skill) 특정 도구나 CLI 사용법을 에이전트에게 설명하는 스킬 [?PyCoding agent]에서 서브 에이전트를 쓰는 법
실행형 스킬(Executable Skill) 스크립트와 설정 템플릿을 포함해 실제 작업을 수행하는 스킬 이미지 생성, VPS 설정 및 보안 강화

컴패니언 스킬은 특정 도구를 에이전트가 잘 쓰도록 안내하는 스킬이다. 예를 들어 화자의 use Pi sub-agents 스킬은 [?PyCoding agent]에서 서브 에이전트를 띄우고 제어하는 스크립트를 포함한다. 스킬은 이 스크립트를 어떻게 써야 하는지 설명한다.

실행형 스킬의 예로는 VPS 설정 및 보안 강화(VPS setup hardening) 스킬이 나온다. 이 스킬에는 여러 스크립트와 설정 템플릿이 들어 있다. 새 VPS를 설정할 때 에이전트와 함께 작업을 진행할 수 있게 해준다.

물론 VPS에서 에이전트를 자유롭게 실행하게 할지는 각자가 판단해야 한다. 화자는 자신은 좋은 경험을 했다고 말한다.

9. 전역 스킬과 프로젝트 스킬을 구분해야 한다

스킬을 어디에 둘지도 중요하다.

전역 스킬(Global Skill)은 모든 프로젝트와 세션에서 사용할 수 있는 스킬이다. 프로젝트 스킬(Project Skill)은 특정 프로젝트 안에서만 쓰는 스킬이다.

화자의 기준은 단순하다.

여러 프로젝트에서 항상 유용한 스킬은 전역에 둔다. 예를 들어 create plan 스킬은 대부분의 프로젝트에서 사용하므로 전역 스킬이 될 수 있다. 이미지 생성 스킬도 시스템 어디에서나 이미지를 만들 수 있어야 하므로 전역 스킬로 둘 수 있다.

반면 Effect 라이브러리 지식 스킬은 특정 프로젝트에서만 의미가 있다. 이런 스킬을 전역에 두면 불필요하다.

전역 스킬을 많이 두면 문제가 생긴다. 전역 스킬은 적어도 메타데이터와 설명이 모든 세션에 로드된다. 토큰 비용 자체는 크지 않을 수 있지만, 도구와 스킬이 너무 많아지면 모델 성능이 떨어질 수 있다.

그래서 화자는 전역 스킬을 최대한 적고 간결하게 유지한다고 말한다. 프로젝트 안에 둘 수 있는 것은 프로젝트 안에 둔다.

10. Agents.md / Claude.md에는 항상 적용할 규칙만 둔다

마지막 질문은 Agents.md나 Claude.md에 무엇을 넣을 것인가다.

화자의 기준은 명확하다.

Agents.md와 Claude.md에는 항상 적용되어야 하는 일반 규칙만 넣는다.

예를 들면 다음과 같다.

  • 응답을 짧게 유지하라.
  • 레거시 코드(legacy code)나 폴백 코드(fallback code)를 불필요하게 추가하지 마라.
  • 기존 코드를 지우지 않고 계속 층층이 덧붙이는 방식으로 해결하지 마라.

이런 규칙을 스킬로 만들지 않는 이유는 스킬은 활성화되어야만 적용되기 때문이다. 항상 적용되어야 하는 규칙을 “스킬이 켜지길 기대하는 방식”으로 두면 위험하다.

따라서 모든 모델과 모든 에이전트에 반드시 적용되어야 하는 하드 룰(hard rule)은 전역 Agents.md나 Claude.md에 둔다.

반대로 스킬은 항상은 아니지만 자주 필요한 지식, 패턴, 작업 절차, 도구 사용법을 담는다.

정리하면 다음과 같다.

  • 항상 적용: Agents.md / Claude.md
  • 필요할 때 적용: 에이전트 스킬(Agent Skill)
  • 특정 프로젝트에서만 필요: 프로젝트 스킬(Project Skill)
  • 어디서나 반복적으로 필요: 전역 스킬(Global Skill)

전체 전사 펼치기

에이전트 스킬(Agent Skill)에 대해 이야기해보겠습니다.

여러분은 에이전트 스킬이 무엇인지 이미 알고 있을 겁니다. 문제는 많은 사람이 에이전트 스킬을 제대로 쓰지 못하고 있거나, 적어도 그 잠재력을 충분히 활용하지 못하고 있다는 점입니다.

에이전트 스킬은 보통 skill.md 파일입니다. 여기에는 설명(description)이 들어 있고, 이 설명은 에이전트가 적절한 순간에 해당 스킬을 활성화하도록 도와줍니다. 그리고 실제 스킬 지침이 들어갑니다. 즉, 코딩 에이전트(coding agent)나 다른 에이전트에 주입해서 특정 작업을 원하는 방식으로 수행하게 만드는 내용입니다.

결국 스킬은 프롬프트(prompt)입니다. 특정 작업을 실행하기 위해 에이전트에게 보내는 추가 문맥(context)입니다.

그런데 많은 사람이 잘 모르는 첫 번째 중요한 점은, 스킬이 반드시 skill.md 파일 하나만은 아니라는 것입니다. 어떤 스킬은 그 파일 하나로 충분할 수 있습니다. 하지만 많은 스킬은 추가 참조자료(reference)나 심화 자료(deep-dive resource)를 함께 가질 수 있습니다. 에이전트가 필요할 때 이런 자료를 활성화할 수 있습니다. 스킬은 점진적 발견(Incremental Discovery)을 전제로 하기 때문입니다.

즉, 전체 skill.md 파일이 매번 로드되는 것이 아닙니다. 처음에는 메타데이터(metadata)만 모든 에이전트 세션에 로드됩니다. 그다음 description을 보고 에이전트가 스킬을 활성화할지 결정합니다. 스킬이 활성화되면 나머지 skill.md 파일을 읽습니다. 그리고 그 안에서 다른 참조자료를 가리킬 수 있고, 필요할 때 그 자료도 활성화됩니다.

많은 사람이 이 정도는 알고 있습니다. 하지만 스킬이 참조자료보다 더 많은 것을 가질 수 있다는 점은 덜 알려져 있습니다. 스킬은 자산(asset)을 가질 수 있습니다. 예를 들어 제 create plan 스킬에는 계획 블루프린트(plan blueprint)가 있습니다. 저는 에이전트가 계획을 만들 때 이 블루프린트를 사용하길 원합니다. 참고로 여기서 보여주는 모든 스킬은 공개되어 있고, 아래에 링크해두겠습니다.

또한 스킬에는 스크립트(script)도 들어갈 수 있습니다. 예를 들어 제 generate image 스킬은 이름 그대로 AI를 이용해 이미지를 생성하는 데 도움을 줍니다. 그 안에는 TypeScript 스크립트가 있습니다. 이 스크립트는 Fal을 사용합니다. Fal은 여러 AI 모델을 API로 제공하는 서비스입니다. 요청을 보내 이미지, 텍스트, 오디오, 비디오 등을 생성할 수 있습니다. 제 이미지 생성 스킬은 이미지 모델만 다루며, 제 경우에는 GPT-Image-2를 하드코딩해 유일한 이미지 모델로 사용합니다.

물론 이 부분은 바꿀 수 있습니다. 이렇게 저는 이미지를 생성하는 스크립트가 포함된 스킬을 갖고 있습니다.

여기서 “왜 그냥 스크립트만 쓰지 않는가?”라고 물을 수 있습니다. 왜 토큰을 쓰고, 비결정적인 요소를 추가하느냐는 질문입니다. 좋은 질문입니다. 실제로 사람들이 스킬이라고 제공하는 것 중 일부는 그냥 스크립트여도 됩니다. 하지만 어떤 것은 둘 다여야 합니다.

예를 들어 이 스킬에서 결정적인 부분, 즉 요청을 보내고, 응답을 처리하고, 이미지를 추출하고, 이미지를 저장하는 부분은 스크립트가 처리합니다. 하지만 “비 오는 날 자전거 이미지가 필요해” 같은 모호한 지시를 적절한 프롬프트로 바꾸는 부분은 스킬이 담당합니다. 그리고 그 뒤 스크립트를 호출합니다. 여기에 유용성이 있습니다.

제가 직접 그 프롬프트를 쓸 수도 있습니다. 하지만 좋은 점은 두 세계의 장점을 모두 얻을 수 있다는 것입니다. 이것은 프로그래밍과 직접 관련 없는 일반 유틸리티 스킬의 좋은 예입니다.

일반적으로 에이전트 스킬이 필요한 이유는 크게 두 가지입니다.

첫 번째 이유는 지식 격차(Knowledge Gap)를 메우는 것입니다. 모델은 학습 데이터, 파인튜닝(fine-tuning), 강화학습(reinforcement learning)을 통해 어느 정도 지식을 갖고 있습니다. 이것은 모델 안에 내장된 지식입니다. 그리고 사용자가 제공하는 컨텍스트, 코드베이스, 프롬프트, 웹 리서치 등을 통해 추가 지식을 얻을 수도 있습니다.

여기에 더해 사용자는 자신만의 스킬을 통해 특정 작업이나 특정 도메인에 대한 지식을 추가할 수 있습니다. 예를 들어 제가 Effect 라이브러리(Effect library)를 사용하는 프로젝트에서 일한다면, 이 라이브러리는 모델에 충분히 내장되어 있지 않을 수 있습니다. 다른 라이브러리만큼 많은 코드를 보지 못했을 수 있습니다. 그래서 저는 이를 위한 스킬을 만들고 싶습니다.

저는 이것도 AI의 도움으로 만듭니다. AI에게 웹 리서치를 시키고, 문서를 깊이 읽게 하고, Effect 라이브러리에 대한 지식을 모으게 합니다. 중요한 지식이 들어 있다고 아는 특정 URL을 직접 줄 수도 있습니다. 그런 다음 AI가 그 지식을 모아 스킬로 변환하게 합니다.

저는 스킬 생성도 AI에게 맡기는 편입니다. 이후 제가 직접 다듬습니다. 이렇게 지식 스킬을 만들면, 에이전트가 Effect 코드베이스에서 작업할 때 이 스킬을 활성화할 수 있습니다. 공식 문서에 맞게 기능을 제대로 사용하도록 돕고, 매번 문서에 다시 접근할 필요를 줄입니다.

이렇게 지식 격차를 메우는 것이 스킬을 사용하는 중요한 영역입니다.

두 번째 중요한 영역은 실행 격차(Execution Gap)입니다. 지식도 중요하지만, 모델은 특정 작업을 처리하는 자기만의 행동 방식과 접근 방식을 갖고 있습니다. 그 방식이 내가 원하는 방식일 때도 많습니다. 어떤 영역에서는 모델이 나보다 더 잘 알 수도 있습니다. 하지만 때로는 내가 특정 작업이 어떻게 수행되어야 하는지 더 잘 알고 있습니다. 이때도 스킬을 사용할 수 있습니다.

예를 들어 앞서 보여준 create plan 스킬이 있습니다. 저는 코딩 에이전트가 작업을 처리하기 전에 계획을 만들길 원합니다. 계획 작성은 코딩 에이전트에 따라 계획 모드(plan mode)를 이용할 수도 있습니다. 하지만 제가 주로 사용하는 [?PyCoding agent]에는 계획 모드가 없습니다. Claude Code 같은 것을 쓸 때도 요즘은 내장 계획 모드보다 이런 스킬을 사용하는 편입니다.

이 스킬은 description 덕분에 제가 에이전트에게 계획을 만들라고 요청하면 활성화됩니다. description에 그렇게 적혀 있고, 제 경험상 매우 안정적으로 작동합니다.

이 스킬 안에는 “계획을 만든다”는 것이 무엇을 의미하는지에 대한 세부 지침이 있습니다. 예를 들어 리서치를 수행해야 한다는 내용, 서브 에이전트(sub-agent)에 위임해야 한다는 내용이 있습니다. 저는 서브 에이전트를 사용하는 방법, 작업을 나누는 방법, 그리고 제가 주로 쓰는 [?PyCoding agent]에서 이를 어떻게 할지에 대한 별도 스킬도 갖고 있습니다.

또한 계획 작성 방법에 대한 지침도 있습니다. 앞서 보여준 것처럼 계획이 어떤 형식이어야 하는지 템플릿이 있습니다. 저는 그 계획을 검토하기 때문에 명확한 구조가 필요하고, 항상 같은 구조이길 원합니다. 그 모든 것을 스킬에 인코딩해두었습니다. 또한 리뷰 단계도 포함해, 제가 보는 계획은 이미 검토된 상태가 되도록 했습니다.

리뷰와 관련해서도 별도 스킬이 있습니다. 계획 리뷰나 코드 리뷰는 특정 규칙과 패턴을 따라야 하기 때문입니다. 그 코드 리뷰 스킬에서는 작업을 위임하고 나누어야 하며, 메인 컨텍스트 창을 깨끗하게 유지하기 위해 서브 에이전트를 사용해야 한다고 명시합니다. 또한 발견 사항(finding)을 점수화하는 규칙도 있습니다. 생성된 계획이나 리뷰에 모든 발견 사항을 반영하지 않도록 합니다. 대신 판단을 해야 하고, 예를 들어 점점 더 많은 복잡도를 추가하는 일을 피해야 합니다.

이를 위해 저는 de-complex 스킬도 갖고 있습니다. 이 스킬은 과도한 복잡도가 무엇인지, 복잡도를 어떻게 확인할지 정의합니다. 그리고 이런 모든 스킬에서, 어떤 것이 너무 복잡한지 또는 실제 문제인지 명확하지 않다면 사용자에게 물어보라고 명시합니다.

이렇게 여러 층을 쌓아 저에게 잘 맞는 시스템을 만듭니다. 예를 들어 계획 작성 시 리뷰가 다른 스킬들을 트리거하면서, 대체로 실행 가능하고, 검토되었고, 좋은 형태의 계획을 얻게 됩니다. 이것이 제가 말하는 실행 격차입니다.

물론 모델은 제 지침 없이도 계획을 만들 수 있습니다. 하지만 제 경험상 이런 추가 스킬을 사용하면, 계획 작업을 어떻게 하길 원하는지 명확해져 더 좋은 결과를 얻습니다.

이것을 그냥 프롬프트에 넣을 수도 있습니다. 물론 가능합니다. 하지만 그러면 매번 반복해야 합니다. 일반적인 조언은 이렇습니다. 같은 것을 반복해서 요청하고 있거나, 같은 오류에 반복해서 불평하고 있다면, 그것을 스킬에 넣으십시오.

또한 중요한 점은 자기만의 스킬을 작성하라는 것입니다. 제 스킬이나 Matt Pocock의 스킬, 또는 인터넷에서 찾은 다른 스킬을 사용해도 됩니다. 문제는 없습니다. 훌륭한 스킬도 많고, 특히 좋은 출발점이 됩니다. 하지만 그것을 다듬고, 자기 것으로 만들어야 합니다. 자기 워크플로와 에이전트에서 겪는 문제에 맞춰 직접 스킬을 만들어야 합니다. 사람마다 일하는 방식이 다르고, 저에게 잘 맞는 것이 여러분에게도 잘 맞을 필요는 없기 때문입니다.

좋은 스킬을 만드는 것은 단순합니다. 적절한 순간에 활성화되도록 좋은 description을 쓰고, 본문은 간결하고 실행 가능하게 유지하면 됩니다. 저는 불릿 포인트를 선호합니다. 꼭 그래야 하는 것은 아니지만, 긴 산문은 피하십시오. AI를 사용해 스킬을 작성한다면, 저도 그렇게 하지만, AI가 너무 복잡하고 긴 스타일로 쓰지 않도록 유도해야 합니다. 일부 AI 모델은 매우 자세하고 부풀려진 스킬을 만드는 경향이 있습니다.

그런 내용은 모두 비용을 내야 하는 토큰입니다. 그리고 컨텍스트를 오염시키는 정보이기도 합니다. 특히 그런 오염 때문에 결과가 나빠질 수 있습니다. 스킬은 집중되어 있고 간결해야 합니다. AI로 만들되, 시간을 들여 개선하십시오. 그 스킬은 반복해서 사용될 것이기 때문입니다.

게으르게 만들지 마십시오. 좋은 스킬로 만들고, 원하는 방식과 요구사항에 맞게 조정하십시오.

또한 스킬을 정적인 것으로 취급하지 마십시오. 스킬은 시간이 지나며 진화해야 합니다. 다른 모든 것이 변하기 때문입니다. 모델이 바뀌고, 어떤 모델은 갑자기 훨씬 더 공격적이거나 장황해집니다. 이전 모델에서 잘 작동하던 스킬이 새 모델에서 반드시 잘 작동하는 것은 아닙니다.

코딩 에이전트 하네스(harness)도 바뀝니다. 사용할 수 있는 도구도 바뀝니다. 암묵적으로 추가되는 시스템 프롬프트(system prompt)도 바뀝니다. 그리고 사용자도 바뀝니다. 일하는 방식이 바뀝니다. 1년 전에는 우리가 지금보다 훨씬 더 많은 코드를 직접 작성했습니다. 코드를 읽는 방식과 양도 바뀌고 있습니다. 따라서 스킬도 진화해야 합니다.

스킬을 개선하는 스킬(improve skill skill)을 추가하는 것도 고려할 수 있습니다. 에이전트가 특정한 것을 자주 틀리거나, 사용자가 자주 수정하는 내용이 실제로 스킬에 인코딩되어 있다면, 정의한 규칙에 따라 에이전트가 스킬을 자동 개선하게 할 수 있습니다.

이런 것들을 고려해야 합니다. 반년 전에 설치한 스킬이 지금도 유용하다고 볼 수는 없습니다. 발전시키고, 더 이상 일을 제대로 하지 못한다면 버리십시오. 그리고 자기만의 스킬을 만드십시오. 남이 만든 스킬을 수집만 하지 마십시오.

또한 스킬에는 네 가지 주요 유형이 있다고 볼 수 있습니다. 물론 서로 겹치기도 합니다.

첫 번째는 도메인 지식 스킬(Domain Knowledge Skill)입니다. 앞서 말한 Effect 스킬이 그 예입니다. 프로젝트에 중요한 특정 도메인 지식을 스킬에 넣어두면, 에이전트가 매번 요청을 반복하지 않아도 됩니다.

두 번째는 워크플로 스킬(Workflow Skill)입니다. 앞서 보여준 create plan 스킬처럼 반복되는 워크플로를 위한 것입니다. 같은 설명을 반복하고 싶지 않고, 명확한 구조를 원할 때 사용합니다.

세 번째는 컴패니언 스킬(Companion Skill)입니다. 특정 도구의 사용법을 에이전트에게 설명하는 스킬입니다. 예를 들어 저는 use Pi sub-agents 스킬을 갖고 있습니다. 이름 그대로 [?PyCoding agent]와 함께 작업하도록 조정된 스킬입니다. 이 스킬에는 [?Py]를 통해 서브 에이전트를 띄우고 제어하는 스크립트가 있습니다. 확장 기능을 쓸 수도 있지만, 저는 스킬을 사용합니다. 그리고 이 스킬은 그 스크립트를 어떻게 사용할지 설명합니다.

이것은 이미지 생성 스크립트와 비슷하지만, 동시에 모델이 실행 중일 수 있는 [?PyCoding agent]를 어떻게 사용하고, 예를 들어 서브 에이전트와 함께 작업하는 데 어떻게 활용할지를 설명하는 스킬입니다. 시스템에 설치한 다른 CLI를 에이전트에게 설명하고 싶을 때도 이런 스킬을 만들 수 있습니다.

네 번째 유형은 제가 실행형(Executable)이라고 부르는 스킬입니다. 예를 들어 이미지 생성 스킬이 여기에 해당합니다. 더 나아가 제 VPS 설정 및 보안 강화(VPS setup hardening) 스킬도 있습니다. 이 스킬에는 여러 스크립트와 설정 템플릿이 들어 있습니다. 저는 새 VPS를 설정할 때 이 스킬을 사용합니다.

이것을 전부 스크립트만으로 할 수도 있습니다. 하지만 중간중간 결정을 해야 하고, 수행해야 하는 검사도 있습니다. 에이전트가 그것을 함께 처리해주면 좋습니다. 물론 에이전트를 VPS에서 자유롭게 움직이게 할지는 각자 판단해야 합니다. 저는 좋은 경험을 했습니다. 저는 새 VPS 설정 워크플로를 에이전트와 함께 실행하기 위해 이 스킬을 사용합니다. 작동 방식을 명확히 설명하고, 하드코딩된 스크립트와 설정을 함께 둡니다. 이런 모든 경우에 에이전트 스킬은 매우 유용할 수 있습니다.

이제 남은 질문은 두 가지입니다. 첫 번째는 스킬을 어디에 둘 것인가입니다. 스킬은 시스템 전역(global)에 설치할 수도 있고, 프로젝트별(local per project)로 둘 수도 있습니다.

답은 비교적 간단합니다. 제 create plan 스킬처럼 많은 프로젝트, 사실상 제가 작업하는 모든 프로젝트에 적용되는 스킬은 전역 스킬이어야 합니다. 이미지 생성 스킬도 시스템 어디서든 이미지를 만들고 싶을 수 있으므로 전역 스킬입니다. 반면 Effect 라이브러리 지식 스킬은 프로젝트별로 둬야 합니다. 전역에 있어도 가치가 없기 때문입니다.

전역 스킬은 적어도 메타데이터와 description이 모든 세션에 항상 로드됩니다. 토큰 비용만의 문제가 아닙니다. 스킬은 결국 도구(tool)와 같고, 이런 도구가 많아질수록 모델 성능이 나빠질 수 있습니다. 그래서 저는 전역 스킬을 최대한 간결하게 유지하려고 합니다. 일반적으로 가능한 한 적은 수의 스킬만 두고, 프로젝트 안에 둘 수 있는 것은 반드시 프로젝트 안에 둡니다.

다른 질문은 Agents.md나 Claude.md에 무엇을 넣을 것인가입니다. 제 기준으로 이 파일들은 매우 간결해야 합니다. 저는 모델의 행동을 조정하는 일반 지침만 넣습니다. 예를 들어 “응답을 짧게 유지하라” 또는 “레거시 코드나 폴백 코드를 추가하지 말라” 같은 규칙입니다. 일부 모델은 이런 것을 좋아합니다. 코드를 삭제하지 않고 계속 층층이 쌓습니다. Agents.md에 이런 지침을 넣으면 어느 정도 도움이 됩니다.

그렇다면 왜 이것을 스킬로 만들지 않을까요? 스킬은 활성화되어야 하기 때문입니다. 저는 이것이 활성화되기를 기대하고 싶지 않습니다. 모든 모델과 모든 에이전트에 중요한 강한 규칙이 있다면, 전역 Agents.md 파일에 넣습니다. 전역 Agents.md와 Claude.md 파일도 만들 수 있습니다. 프로젝트별 파일만 있는 것이 아닙니다. 그러면 모든 세션에 로드되고 바로 적용됩니다.

제 기준의 간단한 구분은 이렇습니다. 스킬은 도구와 같습니다. 자주 필요하지만 항상은 아닌 추가 패턴이나 지식 조각입니다. 항상 중요한 것은 Agents.md와 Claude.md에 들어갑니다. 이것이 제가 생각하는 스킬 사용 방식입니다.
