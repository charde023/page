[한글자막] Claude Code 에이전트 요약에 비용 12%? 사용량 실험과 끄는 방법

업로드 2026-11-02 · 4.8분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 짧은 문구보다 그것을 만들기 위해 읽는 내용이 크다

Claude Code가 작업을 백그라운드 에이전트에게 맡기면 Agent 패널에 running 7/20 같은 짧은 상태 문구가 나타날 수 있다. 영상이 다루는 것은 Claude의 기본 상태 표시줄이 아니라 Agent 패널에 표시되는 에이전트 상태 요약이다.

문제는 출력 문구의 길이가 아니다. 화자의 설명에 따르면, 작업 중인 에이전트의 대화 기록이 바뀌면 약 30초마다 지금까지의 대화 전체를 다시 보내 상태 요약을 만든다. 결과는 약 130개의 출력 토큰처럼 짧아도, 한 번의 호출에 들어가는 입력은 약 40,000토큰일 수 있다. 이런 호출이 긴 작업과 여러 에이전트에서 반복되면 사용량이 쌓인다.

읽는 법: 위에서 아래로 읽는다. 핵심 인과는 “짧은 출력”이 아니라 변경되는 대화를 시간 간격으로 반복해서 읽는 과정에 있다. 다만 입력 토큰 전부가 같은 가격으로 처리된다는 뜻은 아니다. 프롬프트 캐시가 적용되면 비용 구조가 달라질 수 있다.

첫 실험: 일부러 반복되는 상황을 만들었을 때

화자는 Claude Code의 OpenTelemetry 내보내기를 켜고 요청을 Better Stack으로 보냈다. 각 요청에는 용도를 나타내는 query source가 붙었기 때문에, 에이전트 상태 요약 요청을 따로 묶어 볼 수 있었다.

첫 실험에서는 특별한 설정이 없는 일반 세션에서 백그라운드 에이전트에게 sleep을 28번 실행하도록 지시했다. 약 3분 뒤 agent summary 출처의 요청이 5개 생겼고, 호출 간격은 거의 30초였다고 한다. 디버그 로그에서는 호출이 반복되면서 문맥이 18개 메시지에서 42개 메시지로 늘었다. 호출마다 입력은 약 40,000토큰, 출력은 약 130토큰이었으며, 이 실험에서 에이전트 요약은 전체 세션 비용의 12%로 집계됐다고 한다.

읽는 법: 위에서 아래로 실험 순서를 따른다. 이 시간축은 화자가 보고한 관찰을 정리한 것이며, 모든 Claude Code 세션에서 같은 비율이 나온다는 뜻이 아니다.

여기에는 중요한 수량 불일치가 있다. 실험 지시는 sleep 28회인데, 상태 문구 예시는 running 7/20으로 분모가 20이다. 전사만으로는 이 문구가 같은 실험의 실제 진행 횟수인지, 별도의 예시인지, 또는 28회 지시가 다른 단위로 처리됐는지 확인할 수 없다.

현실에 가까운 실험과 외부 측정치는 왜 다른가

화자는 두 번째 실험에서 Opus로 TanStack 사이트를 만들며 백그라운드 에이전트 3개를 사용했다. 이 실행에서는 에이전트 요약이 사용량의 약 8%였고, 요약 호출도 Haiku 같은 저렴한 모델이 아니라 Opus에서 실행됐다고 한다.

다른 측정은 서로 다른 값을 보였다.

아래 표는 화면이 좁으면 좌우로 이동해 읽는다.

읽는 법: 숫자 크기만 세로로 비교하지 말고, 오른쪽의 조건과 분모를 함께 읽는다. 특히 비용 비중, 사용량 비중, 요청 수 비중은 같은 지표가 아니다. 따라서 2%, 8%, 12%, 15~20%, 4분의 1을 한 줄의 성능 순위처럼 다루면 안 된다.

화자가 제시한 변동 원인은 시간 기준 실행 방식이다. 에이전트가 오래 작동하고 대화 기록이 자주 바뀔수록 약 30초 단위 요약이 많이 생긴다. 첫 실험처럼 에이전트가 약 20초마다 작은 단계를 밟으면 거의 최악에 가까운 상황이라고 화자는 평가한다.

캐시는 비용을 줄일 수 있지만, 구독 사용량은 불명확하다

매번 전체 대화를 보내더라도 이전 내용 대부분은 프롬프트 캐시 읽기로 처리될 수 있다. 화자는 API에서 캐시 읽기 가격이 일반 입력 가격의 약 10분의 1이라고 설명한다. 따라서 약 40,000 입력 토큰이라는 수치만 보고 모두 정상 입력 가격으로 청구된다고 단정할 수는 없다.

반면 구독 환경에서는 Anthropic이 캐시 읽기도 사용량을 소모한다고만 설명하고, 얼마나 소모되는지는 밝히지 않았다고 화자는 말한다. 또 에이전트 요약은 Claude Code의 JSONL 전사에 기록되지 않아, 해당 파일만 읽는 CC Usage 같은 도구에는 이 비용이 보이지 않을 수 있다고 한다. 즉, 측정 도구가 보는 자료의 범위가 좁으면 실제 호출이 있어도 보고서에는 빠질 수 있다.

끄는 방법은 있지만 같은 기능을 그대로 유지하는 스위치는 아니다

전사 기준으로 에이전트 상태 요약만 직접 끄는 설정은 없다. 소개된 선택지는 다음과 같다.

읽는 법: 어느 카드도 비용 없이 같은 기능을 보존하는 완전한 해결책이 아니다. 설정 변경은 “백그라운드 에이전트를 모두 끄는 것”이 아니라, 기존 대화 전체를 물려받는 fork 서브에이전트를 끄는 것이다. 일반 서브에이전트는 백그라운드에서 새 문맥으로 시작할 수 있다고 화자는 설명한다.

preload 우회법은 화자가 직접 재실험했다고 말한 방법이 아니다. Flamerix가 사용한 방법을 소개하면서, 설치 명령이 최신 버전을 가져오고 모든 Claude Code 프로세스에 영향을 줄 수 있으므로 코드를 읽고 자신의 복사본을 특정 버전으로 고정하라고 경고한다.

마지막으로 화자는 상태 요약 자체에는 가치가 있으며 Claude도 이를 활용한다는 Anthropic의 설명을 인정한다. 하지만 전체 대화를 30초마다 처리하면서 사용자가 끌 수 있는 직접 설정이 없는 구조는 좋지 않다고 평가한다. 화자 본인은 현재 터미널에서 Claude Code를 많이 사용하지 않고 요약을 자체 방식으로 처리하는 T3 Code를 쓰기 때문에 Claude Code를 수정하지 않겠다고 말한다.

여기까지만 이해하면 충분

  • 짧은 상태 문구의 사용량은 출력 길이보다 전체 대화를 시간 간격으로 반복해서 읽는 방식에서 생긴다.
  • 2%, 8%, 12%, 15~20%, 4분의 1은 작업 조건과 분모가 달라 직접적인 동일 지표 비교가 아니다.
  • Fork Subagents를 0으로 두면 화자의 재실험에서는 요약이 0이 됐지만, 전체 대화를 상속하는 서브에이전트 기능도 잃는다.
  • 첫 실험의 sleep 28회 지시와 running 7/20 표시는 서로 맞지 않으며 전사만으로 관계를 확인할 수 없다.

비유가 깨지는 지점: 실제 시스템에서는 이전 입력이 프롬프트 캐시 읽기로 처리될 수 있어 매번 처음부터 같은 가격으로 읽는 것과는 다르다. 또한 상태 요약은 사람에게 보여 주는 문구일 뿐 아니라 Claude가 에이전트 상황을 이해하는 데도 쓰인다는 것이 Anthropic 측 설명이다.

내가 설명해 보기

1. 원인

출력은 약 130토큰에 불과한데도 에이전트 요약 사용량이 커질 수 있는 이유는 무엇인가?

모범 답안 보기

에이전트 기록이 바뀌는 동안 약 30초마다 지금까지의 대화를 입력으로 보내기 때문이다. 긴 작업이나 여러 에이전트에서는 큰 입력이 반복된다. 다만 이전 입력은 프롬프트 캐시 읽기로 처리될 수 있으므로 입력 토큰 수와 실제 비용을 그대로 같다고 보면 안 된다.

2. 대조

12%라는 비용 비중과 “요청의 거의 4분의 1”이라는 수치를 왜 직접 비교하면 안 되는가?

모범 답안 보기

12%는 화자의 첫 실험에서 전체 세션 비용 중 에이전트 요약 비용의 비중이다. 4분의 1은 8월 GitHub 이슈에서 한 세션의 전체 요청 중 해당 요청이 차지한 비중이다. 비용 비중과 요청 수 비중은 분모와 단위가 다르므로 큰 숫자만 보고 어느 쪽이 더 비쌌다고 결론 낼 수 없다.

3. 적용

내 자동화에서 상태 요약을 줄이는 설정을 시험한다면 어떤 순서로 판단해야 하는가?

모범 답안 보기

먼저 OpenTelemetry처럼 요약 요청을 분리해서 볼 수 있는 관찰 수단을 마련한다. 같은 작업을 기본 설정과 변경 설정에서 실행해 요약 비용 비중을 비교한다. 절감 여부만 보지 말고, fork 서브에이전트가 전체 대화를 상속하지 못하면서 작업 결과가 달라질 가능성을 별도 검토한다. preload 방식은 실행 범위와 설치 코드를 읽고 버전을 고정할 수 있을 때만 후보로 둔다.

이번 글의 통찰

1. 작은 출력이 작은 작업을 뜻하지 않는다

  • [원문] 첫 실험에서 각 요약 호출은 입력 약 40,000토큰과 출력 약 130토큰이었고, 전체 세션 비용의 12%로 집계됐다고 화자는 말한다.
  • [해석] 자동화 비용은 사용자에게 보이는 결과물의 길이가 아니라, 그 결과를 만들 때 반복해서 읽고 처리하는 문맥으로 측정해야 한다.
  • [경계] 입력 대부분이 프롬프트 캐시 읽기일 수 있으므로 40,000토큰을 모두 정상 입력 가격으로 계산하면 안 된다. sleep 28회 지시와 상태 예시 running 7/20의 분모 20도 일치하지 않으며, 전사에는 두 수량의 관계가 설명되지 않는다.

2. 측정값보다 측정의 분모가 먼저다

  • [원문] 화자는 12%와 약 8%를 보고했고, Flamerix는 15~20%, Anthropic 측은 전체 약 2%와 터미널 약 6%, 다른 사용자는 약 8~10%를 제시했다. 8월 GitHub 이슈는 한 세션 요청의 거의 4분의 1이라고 측정했다.
  • [해석] 에이전트 수, 실행 시간, 대화 변경 빈도, 모델, 캐시, 집계 범위가 다르면 결과도 달라진다. 평균값 하나보다 자신의 작업 형태를 같은 측정 방식으로 비교하는 편이 낫다.
  • [경계] 비용, 사용량, 요청 수는 서로 다른 지표다. Flamerix의 15~20%도 전사에서 정확한 분모가 충분히 제시되지 않았다. 각 수치는 화자와 인용 대상의 보고이며 독립 검증 자료가 이 노트에 제공되지는 않았다.

3. 우회법은 비용과 문맥 상속을 맞바꾸는 선택이다

  • [원문] 화자는 Fork Subagents를 0으로 설정해 두 실험을 다시 실행했을 때 agent summary가 0이 됐고 백그라운드 에이전트는 계속 작동했다고 말한다. 다만 전체 대화를 상속하는 fork 서브에이전트는 사용할 수 없게 된다.
  • [해석] 설정 변경의 평가는 “요약 호출이 사라졌는가”만이 아니라 “문맥 상속 없이도 같은 작업 품질을 유지하는가”까지 포함해야 한다.
  • [경계] 화자는 변경 전후의 작업 품질이나 전체 사용량을 보고하지 않았다. preload 우회법은 Flamerix의 방법으로 소개됐으며 화자가 직접 재실험했다고 말하지 않는다. 더 저렴한 요약 방식도 작업 중이라고 언급될 뿐 완료나 배포는 확인되지 않았다. META에는 원작자와 소속 후보가 없으며, provenance.note의 “화자 이름+SNS 기준 추정 출처”라는 메모만으로 화자를 특정할 수 없다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 짧은 답을 만들기 위해 학습자가 얼마나 많은 문맥을 처리했는지 보이지 않는다는 구조가 에이전트 요약과 닮았다.
  • 통찰: 결과 문장의 길이보다, 학습자가 원인과 조건을 보지 않고 설명할 수 있는지를 관찰해야 한다. 이 영상에서는 서로 다른 퍼센트의 분모를 구분하는 설명이 이해의 증거가 된다.
  • 질문/행동: “12%와 4분의 1을 왜 직접 비교하면 안 되는가?”를 자료 없이 설명하게 한다.

사업가 · 구조적 비유

  • 관련성: 짧은 진행 표시를 유지하기 위해 반복적으로 자원을 쓰는 구조는 운영의 숨은 비용을 찾는 문제와 닮았다.
  • 통찰: APOM에 같은 구조가 실제로 존재하는지는 확인되지 않았다. 적용하려면 고객에게 보이는 작은 기능 뒤에서 어떤 작업·데이터 조회·대기가 반복되는지 먼저 측정해야 한다.
  • 질문/행동: 운영 기록에서 결과물은 작지만 반복 호출이나 반복 확인이 많은 기능을 분리 측정할 수 있는가?

마케터 · 직접 전이

  • 관련성: 영상은 12%라는 강한 숫자를 제시한 뒤 8%, 2%, 6%, 15~20%와 조건을 함께 보여 준다.
  • 통찰: 숫자는 주의를 끌지만 비용·사용량·요청 수를 같은 증거처럼 섞으면 과장이 된다. 카피에서는 숫자 바로 옆에 작업 조건과 분모를 붙여야 한다.
  • 질문/행동: 사례 수치를 제시할 때 “무엇 중 무엇의 비율인가”와 “어떤 작업 조건인가”를 한 문장 안에 표시한다.

AI/SW 학습자 · 직접 전이

  • 관련성: OpenTelemetry에는 보이지만 JSONL 전사에는 보이지 않는 호출이 있다는 관찰은 자동화 평가의 계측 범위 문제다.
  • 통찰: 에이전트 비용을 평가할 때 사용자 전사만 보지 말고 요청 출처, 모델, 캐시, 실행 시간, 백그라운드 호출을 함께 봐야 한다.
  • 질문/행동: 같은 작업을 설정 변경 전후로 실행하고 agent summary의 비용 비중이 실제로 얼마나 달라지는지 분리 측정한다.

# 섹션 요지
1 기능의 위치 기본 상태 표시줄이 아니라 Agent 패널의 백그라운드 에이전트 상태 요약이다.
2 첫 실험 약 30초 간격의 5개 요청, 호출당 약 40,000 입력·130 출력 토큰, 전체 비용의 12%가 보고됐다.
3 현실 작업과 외부 수치 TanStack 실험은 약 8%, 다른 보고는 2%부터 15~20%까지 달랐다.
4 캐시와 계측 캐시가 가격을 낮출 수 있지만 구독 사용량은 불명확하고 JSONL 집계에는 요약 호출이 빠질 수 있다.
5 우회법 Fork Subagents 0 설정과 preload 타이머 차단법이 소개되며 각각 기능·보안 절충이 있다.
6 화자의 결론 요약에는 가치가 있지만 직접 끄는 설정이 없고 전체 문맥을 반복 처리하는 방식은 좋지 않다고 평가한다.

1. 기능의 범위

화자는 이 기능이 Claude의 기본 상태 표시줄이 아니라, 작업을 백그라운드 에이전트에 넘겼을 때 Agent 패널에 표시되는 상태 줄이라고 구분한다.

영향을 측정하기 위해 Claude Code의 OpenTelemetry 내보내기를 켜고 Better Stack으로 요청을 보냈다. 각 요청에는 용도를 나타내는 query source가 있어 agent summary 요청을 별도로 묶을 수 있었다.

2. 첫 번째 반복 실험

특별한 설정이 없는 일반 세션에서 백그라운드 에이전트에게 sleep을 28번 실행하도록 했다. 약 3분 동안 다음 결과가 관찰됐다고 한다.

  • agent summary 요청 5개
  • 호출 간격은 거의 30초
  • 대화 문맥은 18개 메시지에서 42개 메시지로 증가
  • 호출당 입력 약 40,000토큰
  • 호출당 출력 약 130토큰
  • 상태 문구 예시: running 7/20
  • 전체 세션 비용 중 에이전트 요약 비중: 12%

지시된 횟수 28과 상태 문구의 분모 20은 일치하지 않는다. 전사에는 같은 실행의 서로 다른 집계인지, 상태 문구가 별도 예시인지 설명이 없다.

3. 현실 작업과 다른 측정치

두 번째 실험에서는 Opus로 TanStack 사이트를 만들면서 백그라운드 에이전트 3개를 사용했다. 에이전트 요약은 사용량의 약 8%였고, 요약 호출도 Haiku가 아닌 Opus에서 실행됐다고 한다.

화자가 함께 소개한 수치는 다음과 같다.

  • Flamerix: 15~20%. 팀 전체 OpenTelemetry 자료에서 매일 많은 백그라운드 에이전트를 사용한 결과라고 설명된다.
  • Anthropic의 Claude Code 팀 관계자: 지난주 전체 텔레메트리 비용의 약 2%, 터미널에서는 약 6%.
  • 관련 스레드의 다른 사용자: 약 8~10%.
  • 8월 GitHub 이슈: 한 세션 전체 요청의 거의 4분의 1. 비용 비중이 아니라 요청 수 비중이다.

화자는 변동의 이유로 wall-clock 방식을 든다. 작동 중인 에이전트의 전사가 변경되면 약 30초마다 요약한다. 오래 실행되는 에이전트가 많을수록 호출이 누적된다. 첫 실험에서 에이전트가 약 20초마다 작은 단계를 수행한 것은 거의 최악에 가까운 조건이라고 평가한다.

4. 캐시, 구독 사용량, 보이지 않는 요청

화자는 반복 입력 대부분이 프롬프트 캐시 읽기일 수 있다고 인정한다. API에서는 캐시 읽기 가격이 정상 입력 가격의 약 10분의 1이라고 설명한다.

구독 환경에서는 Anthropic이 캐시 읽기도 사용량을 소모한다고 밝히지만, 정확히 얼마나 소모되는지는 공개하지 않았다는 것이 화자의 주장이다.

에이전트 상태 요약은 Claude Code의 JSONL 전사에 기록되지 않는다고 한다. 따라서 JSONL 파일을 바탕으로 사용량을 계산하는 CC Usage 같은 도구는 해당 요청 비용을 보지 못할 수 있다.

5. 논란의 시점과 기존 문제 제기

화자는 사용자들이 Claude 사용 한도가 더 빨리 소모된다고 불평한 사례를 봤다고 말한다. 10월 28일 Claude Code 책임자가 단일 근본 원인을 찾지 못했으며 에이전트를 많이 쓰는 무거운 세션을 지적했다고 전한다. 약 4시간 뒤 Flamerix의 gist가 Hacker News 첫 화면에 올랐다고 한다.

다만 이 문제가 새롭게 발견된 것은 아니라고 덧붙인다. 8월 GitHub 이슈에서 한 세션 요청의 거의 4분의 1이 이 기능과 관련됐다고 측정했으며, 해당 이슈는 Anthropic의 답변 없이 열려 있다고 말한다. 전사에는 10월 28일과 8월의 연도가 직접 제시되지 않는다.

6. Fork Subagents 설정

에이전트 상태 요약만 직접 끄는 설정은 없다고 한다. 소개된 첫 우회법은 Claude Code Fork Subagents를 0으로 설정하는 것이다.

화자는 두 실험을 이 설정으로 다시 실행했고 다음 결과를 보고한다.

  • agent summary가 0이 됨
  • 백그라운드 에이전트는 계속 실행됨
  • 전체 대화와 프롬프트 캐시를 상속하는 fork 서브에이전트는 사용할 수 없게 됨
  • 일반 서브에이전트는 전달받은 작업만 가진 새 문맥으로 백그라운드에서 시작할 수 있음

따라서 모든 백그라운드 에이전트를 끄는 설정은 아니지만, 기존 대화 전체를 상속하는 방식과는 절충이 생길 수 있다. 화자는 변경 후 작업 품질이나 전체 사용량 차이를 제시하지 않는다.

7. Flamerix의 preload 우회법

Flamerix는 번들 preload 스크립트로 setTimeout을 가로채 상태 요약 타이머를 차단했다고 소개된다.

화자는 접근 방식 자체는 마음에 들지만 설치할 때 매우 주의해야 한다고 경고한다.

  • 모든 Claude Code 프로세스에 영향을 줌
  • 설치 명령이 최신 버전을 호출함
  • 설치 전에 코드를 읽어야 함
  • 자신의 복사본을 만들어 특정 버전으로 고정해야 함

전사에는 화자가 이 우회법을 직접 설치하거나 재실험했다는 내용이 없다.

8. 최종 평가와 시행 상태

화자는 상태 요약이 가치를 제공한다고 본다. Anthropic은 Claude 자체도 이 요약을 사용해 에이전트가 무엇을 하는지 이해한다고 설명했다고 한다.

그러나 전체 대화를 약 30초마다 처리하면서 직접 끌 수 있는 설정이 없는 점은 좋지 않다고 평가한다. 더 저렴한 버전을 작업 중인 것으로 언급하며 개선되기를 희망하지만, 전사에는 해당 방식이 이미 완성되거나 배포됐다는 내용이 없다.

화자 본인은 현재 터미널에서 Claude Code를 많이 쓰지 않고 T3 Code를 사용하므로 Claude Code를 수정하지 않겠다고 말한다.

전체 전사 펼치기

Claude Code의 Agent 패널에서 짧은 상태 문구를 만드는 데 생각보다 많은 사용량이 들어갈 수 있습니다. Better Stack은 실제 측정 사례와 Anthropic의 설명을 살펴보고 이 기능을 끄는 방법과 대안까지 소개합니다. 어떤 조건에서 사용량이 발생하는지 함께 확인해 보겠습니다. 짧은 문구가 왜 토큰 사용량과 연결되는지, 그리고 캐시가 비용에 어떤 영향을 주는지도 원본의 설명을 따라 살펴봅니다.

이 표시줄을 본 적이 없다면, Claude Code에서 작업이 백그라운드 에이전트(background agents)로 넘어갈 때 나타나는 표시줄입니다. 이게 상태 표시줄에 영향을 준다고 주장하는 사람들을 봤는데, 메인 Claude의 상태 표시줄이 아니라 에이전트 패널(agent panel)에 있는 에이전트들의 상태 표시줄입니다. 아무튼 이 요약의 영향을 테스트하기 위해 Claude Code의 OpenTelemetry 내보내기를 켜고 Better Stack으로 전송했습니다. 그러면 모든 요청에 용도를 나타내는 쿼리 소스(query source) 태그가 붙습니다. 그런 다음 특별한 설정 없이 일반 세션을 시작하고, 백그라운드 에이전트에게 sleep 28을 실행하도록 요청했습니다.

약 3분 후, 쿼리 소스가 agent summary인 요청이 5개 들어왔고, 거의 정확히 30초 간격이었습니다. 디버그 로그를 보니 각 호출이 지금까지의 전체 대화를 보내기 때문에 컨텍스트가 매번 18개 메시지에서 42개 메시지로 늘어났습니다. 각 호출은 약 130개의 출력 토큰을 받기 위해 약 40,000개의 입력 토큰을 사용했고, “running 7/20” 같은 라벨도 포함했습니다.

이 요청들을 쿼리 소스별로 묶어 보면, 에이전트 요약이 세션 전체 비용의 12%를 차지한 것을 알 수 있습니다. 좀 더 현실적인 테스트도 해봤습니다. 이번에는 Opus를 사용해 세 개의 백그라운드 에이전트로 TanStack 사이트를 만들도록 했습니다.

이 실행에서는 에이전트 요약이 전체 사용량의 약 8%를 차지했습니다. 흥미롭게도 요약 호출은 전부 Opus에서 실행됐고, Haiku 같은 더 저렴한 모델은 사용되지 않았습니다. 제 결과 두 가지 모두 Flamerix가 발견한 15~20%보다는 조금 낮지만, 그래도 굳이 쓰고 싶지 않은 사용량입니다.

그리고 그 수치는 실제로 매일 많은 백그라운드 에이전트를 실행하는 팀 전체의 OpenTelemetry 데이터에서 나온 것입니다. 이 사실을 놓치기도 매우 쉽습니다. 이런 요약은 Claude Code의 JSONL 트랜스크립트(transcript)에 실제로 기록되지 않기 때문입니다. 따라서 CC Usage처럼 해당 파일로 사용량을 계산하는 도구는 이 비용을 전혀 확인하지 못합니다.

Anthropic이 제시한 자체 수치는 조금 더 낮습니다. Claude Code 팀의 한 사람이 Hacker News에 답변을 남겼는데, 전체 텔레메트리 기준으로 지난주 비용의 약 2%, 터미널에서는 약 6%였다고 했습니다. 그리고 이 스레드에서 자신의 사용량을 측정한 다른 사람들은 약 8~10% 정도로 집계했는데, 제 TanStack 테스트와 거의 같은 수치입니다. 이 수치가 크게 달라질 수 있는 이유 중 하나는 벽시계 시간(wall-clock time)을 기준으로 실행되기 때문입니다. 작업 중이고 트랜스크립트가 변경된 모든 에이전트는 30초마다 요약됩니다.

따라서 오래 실행되는 에이전트가 많으면 사용량이 매우 빠르게 누적됩니다. 첫 번째 테스트에서 20초마다 아주 작은 단계 하나를 수행한 에이전트는 사실상 최악의 상황에 가까웠습니다. 물론 이에 대한 한 가지 반론은 이 입력 토큰 대부분이 프롬프트 캐시 읽기(prompt cache reads)에 해당한다는 것입니다. 매번 작은 차이만 전송하기 때문입니다. API에서는 일반 가격의 약 10분의 1이 맞지만, 구독에서는 Anthropic이 사용량을 차감한다고만 할 뿐 얼마나 차감하는지는 밝히지 않습니다. 그리고 다시 말하지만, 사용량은 여전히 사용량입니다. 이 문구들이 정말 그만한 가치가 있어 보이나요?

이번 주에 이 문제가 특히 큰 반응을 일으킨 것은 Claude 사용량 한도가 훨씬 빠르게 줄어든다고 불평하는 사람들이 많이 보였기 때문이라고 생각합니다. 10월 28일에는 Claude Code 책임자가 실제로 단일한 근본 원인은 찾지 못했다고 말하며, 에이전트가 많고 세션이 무거운 경우를 지적했습니다. 그리고 약 4시간 후 이 gist가 Hacker News 첫 화면에 올라왔습니다.

하지만 이것이 실제로 새로운 발견은 아니라는 점도 언급할 만합니다. 8월의 한 GitHub 이슈에서는 한 세션의 전체 요청 중 거의 4분의 1을 차지한다고 측정했으며, Anthropic의 답변 없이 아직도 열려 있습니다. 그렇다면 이 기능을 실제로 끌 수 있을까요? 쉽지는 않습니다. 이를 위한 설정이 없기 때문입니다.

제가 본 한 가지 우회 방법은 Claude Code Fork Subagents 설정입니다. 이 값을 0으로 설정하면 포크 서브에이전트(fork subagents)가 비활성화되고, 따라서 요약도 함께 사라집니다.

이 설정으로 두 테스트를 다시 실행해 보니 에이전트 요약은 0이 되었고, 에이전트는 여전히 백그라운드에서 실행됐습니다. 단점은 전체 대화를 상속하는 포크 서브에이전트를 사용할 수 없게 된다는 것입니다. 분명히 말하면 백그라운드 에이전트를 잃는 것은 아닙니다. Claude는 여전히 일반 서브에이전트를 백그라운드에서 실행할 수 있습니다. 다만 이들은 이전 대화와 프롬프트 캐시의 전체 복사본 대신 Claude가 전달한 작업만 받은 채 새로 시작합니다. 따라서 이 방법을 사용하면 어느 정도의 트레이드오프(trade-off)가 있을 수 있습니다.

다른 해결책은 Flamerix가 만든 우회 방법인데, 이쪽은 조금 더 해킹에 가깝습니다. 번들된 프리로드 스크립트(preload script)를 사용해 setTimeout을 후킹하고 요약 타이머를 차단합니다. 여기서 사용한 접근 방식 자체는 마음에 들지만, 설치할 때는 매우 주의해야 합니다. 모든 Claude Code 프로세스에 후킹하고, 설치 명령이 최신 버전이 무엇인지에 따라 그 파일을 호출하기 때문입니다. 따라서 반드시 내용을 읽고 자신만의 복사본을 고정해 두세요. 지금처럼 시간당 하나씩 치명적인 CVE가 나오고 매일 대규모 공격이 발생하는 것처럼 보이는 상황에서는, 이것이 정말 중요한 조언이라고 생각합니다.

전반적으로 이 요약이 어느 정도 가치를 제공한다고는 생각합니다. Anthropic도 실제로 Claude가 에이전트가 무엇을 하고 있는지 이해하기 위해 이 요약을 사용한다고 말합니다. 하지만 30초마다 전체 대화를 대상으로 실행하면서 끌 수 있는 스위치가 없는 것은 좋지 않습니다. 그리고 이들이 현재 작업 중이라고 하는 더 저렴한 버전이 이 문제를 해결하기를 바랍니다. 개인적으로는 Claude Code를 수정하지 않을 것입니다. 솔직히 말해 요즘은 터미널에서 Claude Code를 많이 사용하지 않기 때문입니다. 저는 실제로 T3 Code를 사용하는데, 이 도구는 자체적인 방식으로 요약을 처리합니다. 그래도 여러분께 최신 상황을 알려드리고 싶었습니다.
