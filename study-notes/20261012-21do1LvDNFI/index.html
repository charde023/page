먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 빠르게 맡기되, 중요한 판단까지 넘기지는 않는다

이 영상에서 기예르모 라우치는 AI 에이전트를 단순한 코드 자동완성 도구가 아니라 질문을 조사하고, 새 프로젝트를 만들고, 기술을 시험하는 작업자처럼 사용한다고 설명한다. 핵심은 에이전트에게 모든 것을 맡기는 데 있지 않다. 작업을 쉽게 시작할 수 있게 준비하고, 결과가 나온 뒤에는 중요한 변화와 성능·보안 상태를 다시 이해하는 데 있다.

문제는 두 방향에서 생긴다. 매번 폴더를 만들고 지침을 설명하느라 준비 시간이 길면 에이전트를 자주 쓰기 어렵다. 반대로 너무 쉽게 실행하고 결과를 자동으로 합치면 코드의 구조, 공개 API의 변화, 성능과 보안 문제를 사람이 놓칠 수 있다. 라우치가 제시하는 흐름은 시작 마찰은 줄이고, 관찰과 검토는 강화하는 방식이다.

읽는 법: 위에서 아래로 읽는다. 첫 상자는 해결할 문제, 가운데 상자는 라우치가 소개한 작동 장치, 마지막 상자는 그가 기대하는 결과다. 이는 수치를 나타내는 그래프가 아니라 영상의 주장을 정리한 개념 지도다.

1. 질문과 프로젝트가 시작되는 자리를 미리 정한다

라우치는 Vercel Labs의 코딩 CLI라고 소개한 FX를 사용한다. CLI는 창과 버튼보다 명령어를 중심으로 사용하는 도구다. 그는 FX가 셸처럼 빠르게 열리도록 작은 실행 파일로 설계됐다고 말한다. 이때 제시한 크기는 다운로드 파일 6MB, 설치 후 디스크에서 11MB다. 둘은 같은 조건의 숫자가 아니므로 하나의 크기로 합치면 안 된다.

리서치 폴더에는 에이전트가 따라야 할 규칙을 적은 AGENTS.md가 있다. 질문하면 에이전트가 이 지침을 읽고 조사 결과를 정해진 폴더에 저장한다. 한 글자 별칭 R은 이 리서치 환경을 열고, P는 프로젝트 폴더에서 새 작업을 시작하는 데 사용된다. 이런 장치가 줄이는 것은 모델의 계산 시간이 아니라 사람이 일을 시작하기 전에 반복하는 준비 동작이다.

그는 새 Next.js 앱, Zig 또는 Rust 프로그램, 로컬 Mac 앱 실험과 벤치마크에 이 방식을 쓴다고 말한다. Vercel Blob을 발표했을 때는 에이전트에게 서비스를 깨뜨려 보고, 경쟁 상태를 찾고, 지연 시간을 측정하고, 대안과 비교하게 했다는 사례도 든다. 다만 이는 화자가 소개한 경험이며, 시험 결과나 원자료가 영상에 제시되지는 않는다.

2. 지침은 한 번 쓰고 끝나는 명령문이 아니라 반복해서 고치는 운영 규칙이다

라우치가 AGENTS.md에 넣는 것은 단순한 말투 지시가 아니다. 결과를 어디에 저장할지, 어떤 변화가 생기면 사람에게 알릴지 같은 작업 관례다. 예를 들어 공개 API의 모양이 바뀌면 Slack이나 Discord로 알려 달라고 정할 수 있다고 설명한다. Slack MCP처럼 외부 도구를 연결하면 알림 과정 자체도 에이전트 작업으로 만들 수 있다는 주장이다.

작업을 마친 에이전트에게 “무엇을 바꿨는가”, “지연 시간이나 메모리 할당은 어떻게 달라졌는가”, “새 API 구조는 무엇인가”를 다시 설명하게 하는 방식도 제안한다. 라우치는 이를 에이전트 기반 탐구(agentic inquiry)라고 부른다. 모든 코드 줄을 사람이 직접 읽지는 않더라도, 현재 시스템에서 중요한 파일·모듈·호출 관계와 측정값은 이해해야 한다는 뜻이다.

읽는 법: 1번부터 5번까지 위에서 아래로 진행한 뒤, 맨 아래의 ‘5 → 1’ 반복 경로를 따라 첫 단계로 돌아간다. 즉, 결과를 관찰해 지침을 고치고 다시 실행하는 구조다. 각 단계의 성능을 수치로 비교한 그래프는 아니다.

라우치는 호출 스택이나 코드의 관계를 그리는 에이전트 기술도 사례로 든다. Dylan Mulroy가 게시한 것으로 보이는 도식은 에이전트가 의사 정적 분석과 AST 그래프 계열 도구를 사용했을 수 있다고 추정한다. 여기서 AST는 코드를 문법 구조에 따라 나무 모양으로 표현한 것이다. 그러나 정확히 어떤 도구와 분석이 사용됐는지는 화자도 확정하지 않는다.

3. 실행 틀과 도구를 분리하면 에이전트 기능을 앱 안에 넣을 수 있다

라우치는 에이전트가 지시를 받고 도구를 호출하며 작업을 이어 가게 하는 실행 틀을 하네스(harness)라고 설명한다. 그는 과거 v0를 만들 때 AI SDK, 모델, 프롬프트, 도구 호출을 연결하는 하네스에 엔지니어링 시간의 90%가 들어갔다고 회고한다.

반면 영상의 FX Zero 예시는 createFXAgent API 위에 약 100줄의 코드를 더한 규모라고 말한다. 첫 예시는 모델이 HTML을 출력하게 하고, 다음 예시는 Vercel Sandbox라는 격리 실행 환경을 도구로 제공해 전체 Next.js 앱을 실행하며, 또 다른 예시는 프롬프트를 받으면 FX 에이전트를 만든다. 라우치는 이를 두뇌와 손이라는 구조로 표현한다. 하네스가 작업을 조정하는 두뇌라면, 샌드박스 같은 도구는 실제 행동을 수행하는 손이다.

하지만 과거의 “90%”와 현재의 “약 100줄”은 서로 다른 단위이며, 범위도 같다고 확인되지 않았다. 따라서 이 숫자만으로 개발 비용이 정확히 얼마나 줄었다고 계산할 수는 없다. 또한 해당 예시는 영상 시점에 오픈소스로 공개할 계획이라고 말한 것이지, 이미 공개됐다고 확인된 것이 아니다.

4. 빠른 생성과 보안 검토는 같은 기준으로 평가하면 안 된다

라우치는 극단적인 바이브 코딩이 기업 환경에서는 역효과를 낼 수 있다고 주장한다. 바이브 코딩은 결과를 빠르게 만들면서 내부 코드를 세밀하게 이해하거나 검증하는 과정을 크게 줄이는 개발 방식을 가리킨다. 개인 실험에서 속도가 중요할 수 있지만, 기업은 데이터가 안전한지, 새 의존성이 공급망 공격의 통로가 되지 않는지 확신해야 한다는 논리다.

따라서 코드 전체를 항상 같은 강도로 검토하는 대신, 공격 표면이나 데이터 위험이 큰 영역은 “질문 없이 진행”하는 방식의 반대로 운영하고 그 엄격함을 외부에도 알리라고 제안한다. 보안 검토가 제품의 신뢰를 만드는 커뮤니케이션이 될 수 있다는 주장이다. 다만 영상은 구체적인 보안 통제 목록이나 검증 결과를 제공하지 않는다.

5. 클라우드와 로컬은 승자 하나를 고르는 문제가 아니다

라우치는 큰 코드베이스, 병렬 작업, 배터리와 CPU·메모리 한계, 밤에도 이어지는 작업 때문에 에이전트 실행이 클라우드로 이동하는 것은 불가피하다고 말한다. 여러 샌드박스에 작업을 나누고, 네트워크 정책과 스캔을 적용하며, 침해가 생겼을 때 피해 범위를 격리할 수 있다는 이유다.

동시에 그는 결과를 로컬 컴퓨터로 가져올 선택도 남겨야 한다고 말한다. 파일 시스템, 프로세스 모니터, 설치된 다른 앱과의 상호작용을 낮은 지연으로 직접 살펴봐야 하는 경우가 있기 때문이다. 영상의 결론은 “항상 클라우드”가 아니라 대규모·병렬·격리 작업은 클라우드가 유리하다는 주장과, 세밀한 현장 관찰에는 로컬이 필요하다는 판단을 함께 유지하자는 쪽에 가깝다.

읽는 법: 번호 순서대로 읽되 세 카드는 점수 순위가 아니다. 첫 두 카드는 화자가 언급한 장점이고, 세 번째 카드는 두 선택을 함께 보존한 영상의 흐름을 정리한 것이다. “클라우드가 무한히 더 낫다”거나 공급망 공격을 없앨 수 있다는 표현은 화자의 강한 견해이지 이 영상에서 검증된 결론은 아니다.

전체를 묶으면 좋은 에이전트 워크플로는 “더 강한 모델을 쓰는 법”만이 아니다. 반복 폴더와 지침으로 시작 비용을 줄이고, 하네스와 도구를 나누며, 결과를 설명·측정하게 하고, 중요한 변화는 자동으로 알리며, 위험과 관찰 목적에 따라 실행 환경을 고르는 운영 설계다.

여기까지만 이해하면 충분

  • 폴더·별칭·AGENTS.md는 에이전트의 지능을 높이기보다 반복 작업의 시작 마찰과 규칙 누락을 줄인다.
  • 에이전트 기반 탐구는 맡기고 끝내는 방식이 아니라 결과를 설명·측정하고 지침을 고쳐 다시 질문하는 순환이다.
  • 모든 코드 줄을 읽지 않더라도 API 변화, 성능, 자원 사용, 보안처럼 시스템에 중요한 것은 사람이 계속 파악해야 한다.
  • 클라우드와 로컬은 절대적인 양자택일이 아니라 작업 규모, 격리, 병렬성, 현장 관찰 필요에 따라 선택할 수 있다.

비유와 깨지는 지점

작업장과 관제실

에이전트는 빠르게 물건을 만드는 작업자, AGENTS.md는 작업 지시서, 하네스는 작업을 배분하는 운영 체계, 샌드박스는 격리된 작업장에 대응한다. 설명·측정·알림은 관제실에서 품질과 위험을 확인하는 장치에 가깝다.

비유가 깨지는 지점: AI 에이전트는 책임을 지는 인간 작업자가 아니며, 설명이 자연스럽다고 해서 실제 코드와 보안 상태가 맞다는 보장도 없다. 또한 클라우드 샌드박스 자체가 모든 공격을 막아 주는 것은 영상에서 검증되지 않았다.

1. 원인

에이전트의 시작 마찰만 줄이고 결과 확인 절차를 만들지 않으면 왜 문제가 될 수 있는가?

모범 답안 보기

폴더·별칭·지침은 더 많은 작업을 빠르게 시작하게 해 주지만, 생성된 코드의 API 변화, 지연 시간, 자원 사용, 보안 위험까지 자동으로 이해하게 해 주지는 않는다. 실행량만 늘면 사람이 모르는 변화도 함께 쌓일 수 있으므로 설명·측정·알림과 위험별 검토가 별도로 필요하다.

2. 대조

에이전트 기반 탐구는 ‘모든 코드를 한 줄씩 읽기’와 ‘검토 없이 자동 병합하기’ 사이에서 무엇이 다른가?

모범 답안 보기

모든 줄을 직접 읽는 대신 현재 시스템에 중요한 파일·모듈·호출 관계와 지표를 선택해 이해한다. 그러나 검토를 없애는 것이 아니라 에이전트의 설명, 구조 도식, 측정, 변화 알림을 이용해 사람이 판단에 필요한 정보를 유지한다.

3. 적용

새 자동화 작업을 맡길 때 로컬, 클라우드, 혼합 실행 중 무엇을 선택할지 어떤 기준으로 판단할 수 있는가?

모범 답안 보기

병렬 작업량, 필요한 CPU·메모리, 장시간 실행 여부, 데이터와 자격 증명의 위치, 격리 필요성, 로컬 앱과의 상호작용, 파일·프로세스를 직접 관찰할 필요를 먼저 적는다. 규모와 격리가 중요하면 클라우드를 후보로 두고, 실제 기기 관찰이 필요하면 로컬을 남기며, 두 조건이 함께 있으면 클라우드 실행 후 로컬 검토 같은 혼합 방식을 시험한다.

이번 글의 통찰

1. 생산성의 출발점은 모델보다 반복 마찰의 제거일 수 있다

  • [원문] 라우치는 리서치용 R, 프로젝트용 P 별칭과 폴더별 AGENTS.md를 사용하며, 질문이나 프로젝트를 빠르게 시작한다고 설명한다.
  • [해석] 자주 반복할 작업에서는 매번 좋은 프롬프트를 새로 쓰는 것보다 시작 위치, 저장 방식, 보고 조건을 고정하는 편이 지속적인 사용에 더 중요할 수 있다.
  • [경계] 영상은 별칭 사용 전후의 시간이나 결과 품질을 측정하지 않는다. FX 크기는 다운로드 시 6MB와 설치 후 디스크에서 11MB로 조건이 다르며, 하나의 숫자로 합치면 안 된다.

2. 에이전트 활용 능력은 위임량보다 관찰 가능한 피드백 구조에 가깝다

  • [원문] 화자는 모든 코드 줄을 읽으라고 주장하지 않는다. 대신 파일·모듈 관계, 호출 구조, 지연 시간, 메모리 할당, API 변화처럼 중요한 내용을 에이전트에게 설명·측정하게 하라고 말한다.
  • [해석] 좋은 자동화는 “실수하지 말라”는 추상적 지시보다 무엇이 달라지면 어떤 방식으로 사람에게 알려야 하는지 정하는 데서 강해진다.
  • [경계] 에이전트가 만든 설명과 도식도 오류가 있을 수 있다. Dylan Mulroy 사례의 분석이 의사 정적 분석인지, AST 그래프 도구인지, 둘의 조합인지는 화자도 추정으로 말한다.

3. 속도·보안·실행 환경에 관한 강한 주장은 적용 전 분리해서 검증해야 한다

  • [원문] 라우치는 v0 초기 하네스에 엔지니어링 시간의 90%가 들었고 FX Zero 예시는 createFXAgent API 위 약 100줄이라고 말한다. 또한 클라우드가 보안 면에서 “무한히 더 낫다”고 표현하며 공급망 공격을 없앨 가능성까지 주장하지만, 로컬 관찰 선택도 남겨야 한다고 말한다.
  • [해석] 재사용 가능한 하네스와 샌드박스가 개발 부담과 피해 범위를 줄일 가능성은 있지만, 실제 선택은 작업 범위·데이터·관찰 요구를 기준으로 시험해야 한다.
  • [경계] 90%, 약 100줄, “수년”은 단위와 범위가 달라 직접 비교할 수 없다. 예시는 공개할 계획이라고 했으며 공개 완료 상태는 확인되지 않는다. DeepSeek가 큰 코드베이스에서 샌드박스를 사용한다는 발언, 클라우드의 절대적 보안 우위, 공급망 공격 근절 가능성도 독립 검증되지 않았다. META의 provenance는 소속을 Fx로 기록하지만 제목·전사는 화자를 Vercel CEO로, FX를 Vercel Labs 도구로 소개하므로 관계를 독립적으로 확정할 수 없다. META 설명에는 David Ondrej의 원본 후보 링크가 있으나 provenance.note는 화자 이름과 SNS를 기준으로 추정한 출처라고 밝혀 원작자·원본 링크는 확정 정보로 다루지 않는다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 화자는 모든 코드 줄을 읽었는지가 아니라 중요한 파일·호출 구조·지표를 설명할 수 있는지를 강조한다.
  • 통찰: 학습자의 이해도 정답 재현보다 “무엇이 바뀌었고 왜 중요한가”를 보지 않고 설명하게 할 때 더 잘 관찰할 수 있다.
  • 질문/행동: 설명 뒤에 원인, 구조, 실패 조건을 각각 한 문장으로 말하게 하면 어디서 이해가 끊기는가?

사업가 · 구조적 비유

  • 관련성: 영상은 시작 비용, 병렬 처리, 자원 한계, 보안 위험과 피해 범위의 관계를 다룬다.
  • 통찰: APOM·이커머스·물류에 적용한다면 자동화를 늘리는 것보다 먼저 어떤 변화가 비용·재고·고객 신뢰에 영향을 주며 누가 알림을 받아야 하는지 묻는 구조적 비유로 사용할 수 있다. 실제 적용 상태는 확인되지 않았다.
  • 질문/행동: 자동 처리 후보 하나에서 사람이 반드시 확인해야 할 금액·재고·고객 영향은 무엇인가?

마케터 · 직접 전이

  • 관련성: 라우치는 보안을 내부 점검에 그치지 않고 기업 고객에게 엄격함을 전달하는 신뢰 요소로 본다.
  • 통찰: “안전하다”는 카피보다 어떤 영역을 격리하고 어떤 변화를 감시하며 문제가 생기면 어떻게 알리는지를 증거로 보여주는 편이 주장과 근거를 분리하기 쉽다.
  • 질문/행동: 보안 우위를 말하기 전에 실제로 공개할 수 있는 절차·로그·검토 기준은 무엇인가?

AI/SW 학습자 · 직접 전이

  • 관련성: AGENTS.md, 하네스, 샌드박스, 구조 설명, 성능 측정, API 변화 알림이 모두 실제 에이전트 운영 요소로 등장한다.
  • 통찰: 모델 이름보다 작업 시작 비용과 실패 시 관찰 가능성, 격리 범위, 사용자 대기 시간을 함께 시험해야 한다.
  • 질문/행동: 작은 작업 하나에 완료 조건뿐 아니라 API 변화·지연 시간·보안 주의점 보고 조건을 넣으면 결과의 이해 가능성이 높아지는가?

# 섹션 요지
1 FX와 시작 속도 셸처럼 빠른 CLI와 조건이 다른 6MB·11MB 수치
2 리서치와 프로젝트 AGENTS.md, R, P로 반복 작업의 시작 절차를 고정
3 하네스와 FX Zero 모델·도구·샌드박스를 앱 안에 연결하는 실행 구조
4 결과 이해 코드 전체 대신 중요한 구조·지표·API 변화를 설명하게 함
5 보안 빠른 생성과 별개로 공급망·데이터 위험을 엄격히 검토
6 클라우드와 로컬 병렬·격리는 클라우드, 세밀한 현장 관찰은 로컬 선택 유지

1. FX의 셸에 가까운 실행 방식

라우치는 FX를 Vercel Labs의 코딩 CLI라고 소개한다. Ghostty에서 새 탭이나 분할 창을 열면 zsh가 시작되는 것처럼 빠르게 부팅하는 것이 설계 원칙이었다고 말한다.

실행 파일은 다운로드 시 6MB이며 설치 후 디스크에서는 11MB라고 설명한다. 두 숫자는 서로 다른 저장 조건이다. 셸 안에서 다시 셸을 시작하는 것처럼 느낄 정도로 빠르게 실행하는 것이 목표였다는 주장이다.

2. 리서치 폴더와 새 프로젝트

리서치 폴더의 AGENTS.md는 질문 결과를 해당 폴더에 저장하는 관례를 만든다. 라우치는 이것이 자신에게 Google 검색을 대신하는 역할도 한다고 표현한다. 이는 개인적 사용 경험이지 검색 도구 전체의 성능 비교는 아니다.

별칭 R은 리서치 디렉터리로 이동해 FX를 실행한다. 별칭 P는 프로젝트 폴더에서 새 프로젝트를 시작한다. P는 Shopify의 Toby가 사용하는 Try와 비슷하다고 언급한다.

실험 대상으로 로컬 Mac 앱, Next.js 앱, Zig·Rust 프로그램과 벤치마크를 든다. 새 인프라를 만들 때 에이전트가 어떻게 접근하는지 처음 원리부터 확인하려 한다고 설명한다.

Vercel Blob 발표 당시에는 에이전트에게 서비스를 깨뜨려 보고, 경쟁 상태를 찾고, 지연 시간을 측정하고, 대안과 비교하게 했다고 말한다. 이어 에이전트에게 실험을 되돌아보고 Vercel이 무엇을 개선할 수 있는지 설명하게 했다고 한다.

3. 재사용 가능한 하네스와 FX Zero

라우치는 v0를 처음 만들 때 하네스를 처음부터 구축해야 했으며 AI SDK, 모델, 프롬프트, 도구 호출에 엔지니어링 시간의 90%가 쓰였다고 회고한다.

영상의 FX Zero 예시는 createFXAgent API 위 약 100줄의 코드라고 주장한다. 모델이 HTML을 직접 출력하는 예시, Vercel Sandbox를 도구로 받아 전체 Next.js 앱을 실행하는 예시, 프롬프트로 FX 에이전트를 만드는 예시가 차례로 언급된다.

그는 하네스와 도구의 관계를 두뇌와 손으로 설명한다. 기업 고객이 내부 시스템에 앱 생성 기능이나 자체 “소프트웨어 공장”을 넣고 싶어 한다는 요청도 소개한다.

예시는 앞으로 오픈소스로 공개할 계획이라고 말했다. 제공 자료에는 실제 공개 완료 여부가 없다.

4. 에이전트가 한 일을 이해하는 방법

에이전트 기반 탐구는 모든 코드 줄을 직접 읽는 것과 아무것도 확인하지 않는 것 사이의 접근이다. 파일·모듈의 역할, 호출 구조, 지연 시간, 메모리 할당, API 구조처럼 시스템에 중요한 내용을 에이전트에게 설명하게 한다.

Dylan Mulroy가 게시한 호출 스택 도식이 사례로 언급된다. 화자는 의사 정적 분석과 AST 그래프 계열 도구를 사용했을 가능성을 추정하지만 정확한 구성을 확정하지 않는다.

Slack MCP와 AGENTS.md를 연결해 공개 API가 바뀔 때 Slack이나 Discord로 알리게 하는 예시도 제안한다. 이는 “실수하지 말고 자동 병합하라”는 지시보다 중요한 변화의 기준과 보고 경로를 명시하는 접근이다.

5. 빠른 개발과 보안 확신

라우치는 극단적인 바이브 코딩이 기업 도입에서 역효과를 낼 수 있다고 말한다. 기업은 데이터가 안전한지와 제품의 보안 상태를 강하게 확신해야 하기 때문이다.

기존 프로젝트를 조사해 처음부터 다시 만들지 않으려는 방식도 사용하지만, 새 소프트웨어가 가져오는 공급망 위험을 이해하기 어렵다고 말한다. 공격 표면이 커진 영역에서는 “질문 없이 진행”하는 대신 매우 엄격하게 검토하고 그 과정을 외부에 전달해야 한다고 주장한다.

영상은 구체적인 보안 감사 결과나 통제 목록을 제시하지 않는다.

6. 클라우드 에이전트와 로컬 관찰

질문자는 로컬 에이전트가 창을 띄우거나 탭을 바꾸고, 배터리를 소모하며, CPU·메모리 한계에 부딪힐 수 있다고 말한다. 라우치는 클라우드 이동이 불가피하며 이미 진행 중이라고 답한다.

그는 큰 코드베이스 처리, 여러 분기와 경우의 수 탐색, 다중 샌드박스 병렬 실행, 야간 작업에 클라우드가 적합하다고 주장한다. 개발 환경을 격리하고 네트워크 정책과 스캔을 적용하면 공급망 공격의 피해 범위를 줄일 수 있다는 논리도 편다.

그 과정에서 DeepSeek를 샌드박스 사용의 예로 들지만 제공 자료만으로 사실 여부를 확인할 수 없다. 공급망 공격을 완전히 없앨 가능성, 클라우드가 보안 면에서 무한히 낫다는 표현도 화자의 강한 견해다.

한편 파일 시스템과 프로세스 모니터를 보고, 실제 Mac과 설치 앱의 상호작용을 낮은 지연으로 확인하려면 로컬 환경이 필요하다고 말한다. 따라서 클라우드 작업물을 컴퓨터로 내려받을 선택은 계속 열어 두어야 한다는 결론이다.

전체 전사 펼치기

AI agent를 잘 쓰는 사람은 실제로 어떻게 일할까요? 버셀 CEO 기예르모 라우치가 자신의 터미널과 작업 방식을 공개했어요. 리서치를 시작하고 새 프로젝트를 만들고 에이전트가 한 일을 확인하는 과정까지 원본을 길게 이어서 볼게요.

저는 Vercel Labs의 코딩 CLI인 FX를 사용하고 있습니다.

이 CLI의 설계 원칙 중 하나는 거의 셸(shell)처럼 느껴지게 하는 것입니다. Ghostty에서 새 탭을 열거나 분할 창을 열면 zsh로 부팅됩니다. 우리가 집요하게 고민한 것 중 하나는 이것이 셸 자체만큼 빠르게 부팅될 수 있느냐는 것이었습니다. 그래서 아주 작은 바이너리입니다.

설치하면 11메가바이트입니다. 오늘 다운로드하면 실제로는 6메가바이트이고, 디스크에서는 11메가바이트를 차지합니다. 시작 속도도 믿을 수 없을 만큼 빠릅니다. 셸 안에서 셸을 시작한다면, 똑같이 빠르게 만들 수 있을까? 이것이 아이디어였습니다.

이제 실제 작업 방식으로 들어가 볼게요. 라우치는 리서치와 프로젝트를 각각 별도 폴더에서 시작해요. 폴더 안에 지침 파일이 에이전트가 일하는 방식을 정해줘요.

저는 FX를 여러 가지 용도로 사용하고 있습니다. 그중 하나는 사실상 어떤 질문이든 생길 때마다 사용하는 것입니다. 참고로 FX가 제게는 Google을 대체했습니다. 이 클라우드 같은 곳에 들어갈 필요 없이, 실험한 내용을 파일 시스템에 많이 보관해 둘 수 있고, 에이전트가 그것을 살펴보게 할 수 있기 때문입니다.

저는 이것이 소프트웨어의 미래를 조금 보여준다고도 생각합니다. 소프트웨어가 훨씬 더 영어 중심(English-driven)이 되는 것입니다.

이 연구 폴더에 있는 제 AGENTS.md 파일이 규칙을 만들어 두기 때문에, 에이전트에게 질문하면 에이전트가 지침을 읽고 제 연구 내용을 이 폴더에 저장합니다. 저는 이런 방식을 시간이 지나면서 계속 개선할 수 있습니다.

제가 한 또 다른 일은 별칭(alias)을 만든 것입니다. 글자 하나, 말 그대로 R입니다. 이 별칭을 실행하면 해당 디렉터리로 이동해서 FX를 실행합니다. 기본적으로 여기서 할 일은 별로 없습니다. 제가 “기술 팟캐스트에 대해 더 알려줘”라고 말한다면, 사실 할 일은 거의 없죠? 폴더로 이동해서 FX를 여는 것뿐입니다. 그래도 이 모든 과정에서 발생하는 지연 시간(latency)을 줄여 줍니다.

깊이 파고들고 싶은 질문이 생길 때마다 그냥 실행해 놓고 제 일을 계속할 수 있기 때문에 중독성이 생깁니다.

제가 만든 또 다른 별칭은 P입니다.

이건 Toby가 Try로 하는 것과 비슷합니다. Shopify의 Toby가 사용하는 CLI를 보셨는지는 모르겠네요. 저는 새 프로젝트를 만들 아이디어가 떠오르는 일이 아주 흔하고, 그럴 때마다 같은 작업을 합니다. 다만 이 별칭은 제 projects 폴더에 프로젝트를 생성해 주고, 그다음에는 여기서 무엇이든 할 수 있습니다.

저는 로컬 Mac 앱으로 실험을 많이 합니다. 새로운 Next.js 애플리케이션을 만들고, 새로운 Zig 또는 Rust 프로그램도 만듭니다. 또한 우리 팀을 돕기 위해 벤치마킹(benchmarking)도 많이 합니다.

새로운 인프라를 만들 때마다, 저는 그것을 제1원리(first principles)에서 검증하고 에이전트가 그 인프라에 어떻게 접근할지 살펴보려고 합니다.

좋은 예가 Vercel Blob을 발표했을 때입니다. 저는 에이전트에게 그것을 깨뜨려 보라고 했습니다. 경쟁 조건(race condition)을 찾고, 지연 시간을 측정하고, 대안들과 비교해 보라고 했습니다.

저는 제가 에이전트 기반 탐구(agentic inquiry)라고 부르는 일을 많이 합니다. 에이전트에게 우리 기술 중 하나를 사용해 보게 한 다음, 이 실험에서 Vercel이 무엇을 더 잘할 수 있었는지 성찰하고 제게 말해 달라고 합니다. 이 방식이 제게 정말 큰 효과를 내고 있습니다.

지금까지는 직접 사용하는 도구였어요. 다음은 같은 에이전트 실행 구조를 다른 앱 안에 넣는 이야기예요. 여기서 말하는 하네스는 모델의 도구를 연결하고 작업을 이어가게 하는 실행 틀이에요.

FX의 아이디어 중 하나는 그것을 임베드할 수 있어야 한다는 것이죠. LibFX에 영감을 준 것 중 하나는 우리가 v0를 만들었을 때의 경험이었습니다.

우리는 처음부터 하네스(harness)를 구축해야 했습니다. 오늘 제가 v0 같은 것이나 어떤 종류의 애플리케이션이든 만든다고 가정해 보죠. 슬라이드를 만들어 주는 Gamma나 Notion 같은 것을 만든다고 생각해 보세요. 에이전틱 인텔리전스(agentic intelligence)를 내장해야 하는 것이라면, 저는 기성 하네스를 선택하고 싶을 겁니다.

우리는 이 예제를 만들었고, 이를 오픈 소스로 공개할 예정입니다. 아마 여러분이 이 예제를 처음 보게 되는 사람 중 한 명일 것 같습니다.

FX Zero 데모를 볼게요. 라우치는 화면을 만드는 기능과 코드를 실행할 환경을 어떻게 연결했는지 설명해요.

FX Zero 데모를 만드는 과정에서 정말 멋졌던 점은, 처음 v0를 만들 당시에는 하네스(harness)에만 쓴 시간이 지나치게 많았다는 것입니다. 엔지니어링 시간의 90%가 AI SDK, 모델, 프롬프트, 툴 호출(tool call) 같은 것들을 파악하는 데 들어갔습니다. 반면 이 예제는 아마도, 정확히 말하면 createFXAgent API 위에 얹은 코드가 100줄 정도일 겁니다.

현재 이 기능은 모델이 HTML을 출력하는 능력만 사용하고 있습니다.

두 번째로 저희가 한 일은 뇌와 손(brain and hands)이라는 멘탈 모델을 사용하는 것이었습니다. 들어보셨는지 모르겠지만, Vercel에서 권장하는 아키텍처는 하네스를 실행한 다음 도구를 제공하는 방식입니다.

이 예제에서 제공하는 도구는 Vercel Sandbox입니다. 이 프롬프트는 “CLI 코딩 에이전트를 위한 랜딩 페이지를 만들어라”라고 지시합니다. 제가 앞에서 보여드린 것과 어느 정도 비슷해 보이지만, 실제로는 뒤에서 완전한 Next.js 애플리케이션을 실행하고 있습니다.

앞의 것은 단순한 HTML이었습니다. 그런 다음 세 번째 것을 제공했는데, 이것은 에이전트이며 프롬프트를 입력하면 FX 에이전트를 생성합니다.

정말 멋진 점은, v0로는 아마 몇 년에 걸친 엔지니어링이 필요했던 일이 이제는 바로 사용할 수 있는 인프라의 일부가 되었다는 것입니다.

저희에게 “시스템 오브 레코드(system of record) 안에 앱 생성 기능을 추가하고 싶다”거나, “v0에서 하는 작업이 마음에 들지만 내부용으로 하나를 갖고 싶다. 여러분만의, 이른바 소프트웨어 공장을 갖는다고 생각해 보라. 그 기능 중 하나가 디자인인 것이다”라고 말하는 고객들이 많았습니다.

작업을 맡겼다면 결과를 어떻게 이해할까요? 라우치가 말하는 agentic inquiry는 에이전트에게 무엇이 바뀌었는지 설명하고 분석하게 하는 방식이에요.

제가 만든 표현이라고 생각하는데—아마 제가 만든 것 같습니다—‘에이전틱 탐구(agentic inquiry)’라는 말이 있습니다. 모든 코드 줄을 읽으라는 뜻은 아닙니다. 하지만 무언가를 해냈다면, 방금 무슨 일이 일어났는지는 이해하려고 해보세요.

네, 저는 이게 가장 큰 뉘앙스라고 생각합니다. 사람들은 이걸 이분법적으로 봅니다. 코드를 한 줄씩 읽으면서 각 줄이 무엇을 하는지 묻거나, 아니면 완전히 YOLO 모드로 가서 전혀 들여다보지 않거나요. 하지만 말씀하신 부분이 정말 핵심입니다. 에이전트를 사용해 이 파일이나 모듈을 이해하는 방법을 알고 있다면, 그걸로 충분합니다. 모든 함수를 알 필요는 없습니다.

그나저나 자연은 치유됩니다. X에서 이 일을 훌륭하게 옹호하는 사람들을 많이 봤습니다. 사람들이 자신의 코드를 다이어그램으로 그리는 데 도움을 주는 스킬(skill)을 만드는 것도 봤습니다. Dylan이라는 사람이 올린 걸 봤는데—아마 그가 만든 것 같습니다—Dylan Mulroy입니다. 그가 호출 스택(call stack) 다이어그램을 보여주고 있었습니다.

에이전트가 의사 정적 분석(pseudo-static analysis)을 하고 있었던 것 같고, 이건 스킬인 것 같습니다. 스킬에 AST 그래프 스타일 도구를 더한 것일 수도 있습니다.

작업이 끝나면 프로그램의 기호 공간(symbolic space)을 감각적으로 이해할 수 있게 해줍니다. 이 메서드가 저 메서드를 호출하고, 저 메서드가 또 다른 메서드를 호출하고, 그 메서드가 또 다른 메서드를 호출한다는 식으로요.

이게 바로 에이전트가 최고의 성능을 발휘하는 순간입니다. 구문 도구와 AST 파싱만으로 이 일을 하려면, 방금 한 작업을 시각화하기 위해 매번 새로운 프로그램을 만들거나 매우 경직된 도구를 사용해야 합니다. AI가 깊이 파고들어 몇 가지 도구를 호출한 다음, 소화된 형태의 이해를 다시 제공할 수 있다는 건 놀라운 일입니다.

지연 시간(latency)을 측정하거나, 할당(allocation)을 측정하거나, 새로운 API 형태를 이해하는 일 등이 될 수 있습니다. 이런 것들은 여러분이 반드시 계속 파악하고 있어야 하는 것들입니다.

그런데 이것 자체도 에이전틱 프로세스(agentic process)로 만들 수 있습니다. 사람들이 Slack MCP를 호출하도록 설정해둔 사례를 봤습니다. 무언가를 할 때마다 이 내용을 에이전트의 AGENTS.md에 넣을 수 있겠죠? 예를 들어 이 프로그램의 외부 공개 API 형태를 변경하는 작업을 할 때마다 저에게 알려달라고 하는 겁니다. Slack이나 Discord로 알려달라고요.

그것만으로도 “그냥 해. 실수는 하지 마. 자동으로 병합해 주고, 거대한 엉망진창 코드 더미를 계속 만들어가자”라고 하는 것보다, 이른바 에이전틱 엔지니어링(agentic engineering)에 더 가깝습니다.

그러니까 기본적으로 그 시스템에서 무엇이 중요한지 파악하고, 에이전트를 활용해 도움을 받을 수 있도록 자동화된 소프트웨어 공장이나 알림을 구축하세요.

빠르게 만드는 과정에서 보안은 따로 살펴봐야 해요.

극단적인 바이브 코딩(vibe coding)을 받아들이는 많은 사람들에게 오히려 역효과를 낼 수 있는 점은, 제가 엔터프라이즈 기업이라면 여러분 제품의 보안 수준에 대해, 그리고 제 데이터가 안전하게 보호될 것이라는 점에 대해 매우 강한 확신을 가져야 한다는 것입니다.

저는 실제로 보안, 그리고 어떤 면에서는 여러분이 바이브 코딩과는 정반대의 작업을 하고 있다는 점을 알리는 것이 여러분에게 상당히 유리하게 작용할 수 있다고 생각합니다.

저는 FX에 무언가를 조사하게 한 다음, 처음부터 직접 만들어내고 싶지 않아서 이미 이 작업을 해낸 프로젝트를 많이 찾아 달라고 요청한 경험이 있습니다.

오늘날 개인적으로도, Vercel 차원에서도 새로운 소프트웨어를 도입할 때 가장 큰 어려움 중 하나는 내가 감수하게 되는 보안 위험을 이해하는 것입니다. 공급망 공격(supply-chain attacks)과 바이브 코딩, 그리고 최근 공격 표면(attack surface)이 너무나 크게 확대된 상황 때문에, 코드베이스의 일부 영역과 제품의 일부 영역에서는 “묻지도 따지지도 않고”의 정반대로 행동하고 싶을 것입니다.

실제로는 극도로 철저하게 검토하고, 그렇게 하고 있다는 사실을 세상에 알리고 싶을 것입니다.

마지막은 에이전트를 어디서 실행할지에 관한 질문이에요. 라우치는 클라우드의 장점을 강조하면서도 로컬에서 직접 살펴볼 수 있는 선택을 남겨두자고 말해요. 인터뷰의 견해로 들어주세요.

클라우드 에이전트(cloud agents)에 대해 이야기해 보죠. 어떻게 생각하시나요? 이전 세대가 온프레미스(on-prem)에서 클라우드로 이동한 것처럼, 에이전트도 노트북에서 클라우드로 이동하는 것이 불가피하다고 보시나요? 최고 사양으로 맞추더라도 결국 한계에 부딪히게 될 텐데요.

에이전트가 창을 띄우거나 탭을 바꾸는 것이 성가시든, 단순히 과열되거나 배터리를 소모하든, 카페에 있다면 에이전트가 테스트를 1,000개 실행하기로 했다고 배터리를 전부 태우고 싶지는 않잖아요?

터미널에서 실행하는 클라우드 코드나 컴퓨터의 FX에서 에이전트를 클라우드로 옮기는 것이 불가피하다고 생각하시나요? 어떻게 보시나요?

불가피합니다. 이미 현실이 됐죠? DeepSeek도 한 가지 예입니다. 아주 큰 코드베이스에서 규모를 확장하려면 자기 컴퓨터에서 실행하는 것은 지속 가능하지 않습니다. 그래서 샌드박스를 사용하죠.

코드베이스는 규모가 커지면 정말 방대해지고, 프로그램의 여러 브랜치와 경우의 수를 로컬 컴퓨터에서 처리한다는 것은 말씀하신 것처럼 메모리와 CPU가 부족해진다는 뜻입니다.

공급망(supply chain)과 관련해서는 보안 우려도 많습니다. 제가 무언가를 제 컴퓨터에서 실행하다가 컴퓨터가 뚫리면 공격자가 무엇에 접근할 수 있을까요? 비밀번호 관리자부터 전부 다 접근할 수 있겠죠?

공급망 공격의 피해 범위를 훨씬 쉽게 구획화하고 제한할 수 있습니다. 개발 수명 주기(development life cycle)를 더 많은 부분 샌드박스로 옮긴다면 공급망 공격을 완전히—대담한 말이지만—근절할 수도 있다고 생각합니다.

왜냐하면 네트워크를 모니터링하는 방화벽과 보안 정책을 더욱 세밀하게 적용할 수 있기 때문입니다. 일반적인 악성 코드, RAT, 즉 원격 접근 트로이목마(remote-access trojan)가 하는 일은 컴퓨터에서 무언가를 가져와 일종의 호스트 이름이나 S3 버킷 같은 곳으로 유출하는 것입니다. 제 생각에는 그렇습니다.

개발 환경을 안전한 클라우드 환경에 유지하면 네트워크 보안에 대해 훨씬 강력한 보장을 설정하고, 스캔을 실행하며, 무언가 침해되더라도 피해를 제한할 수 있습니다. 따라서 보안 측면에서는 클라우드가 압도적으로 더 낫다고 생각합니다. 에이전트가 문제를 병렬로 처리하는 데 정말 뛰어나다는 점은 매우 분명합니다.

병렬화(parallelizing) 측면에서도 더 낫습니다. 여러 샌드박스에 분산할 수 있고, 상태를 공유할 수도 있죠.

효율성 측면에서는 여러분이 잠든 동안에도 작업을 수행할 수 있습니다. 자가 치유 소프트웨어(self-healing software)의 세계를 생각할 때, 예외가 발생하면 어떻게 해야 할까요? 이런 오류가 잔뜩 발생하기 시작했다거나 공격을 받고 있다는 이유로 컴퓨터를 다시 켜야 할까요? 핵심은 바로 이것입니다. 이미 일어나고 있는 일이죠.

그런데 제가 하는 방식은—어쩌면 이 부분에서는 제가 반대 입장일 수도 있는데—여전히 무언가를 컴퓨터로 내려받을 수 있어야 한다고 생각합니다. 중요한 사용 사례입니다. 사람들은 다시 한쪽 극단이나 다른 쪽 극단으로 가려고 하지만, 현실은 우리가 예상하는 것보다 훨씬 복잡하다고 생각합니다. 때로는 현미경으로 들여다보듯 자세히 살펴봐야 하니까요.

부수적으로 이것이 제가 CLI(command-line interface)를 좋아하는 이유이기도 합니다. 가능한 한 하드웨어에 가까이 있어야 하기 때문입니다. 파일 시스템을 확인해야 하고, 프로세스 모니터를 실행해야 합니다.

제가 설치한 다른 애플리케이션들과 상호작용하는 모습을 보고 싶습니다. Mac에서 어떻게 작동하는지도 보고 싶고요. 이론적으로는 이런 일을 클라우드에서도 전부 할 수 있습니다. 하지만 때로는 시스템을 모니터링하면서 가능한 한 낮은 지연 시간으로 로컬 환경에 가져오고 싶을 때가 있습니다. 그 선택지는 계속 열려 있어야 합니다.

작업을 쉽게 시작하고 결과를 이해하고 중요한 변화와 보안을 확인하는 흐름이었어요. 여러분의 개발 방식과 비교해 보셔도 좋겠어요. 도움이 되셨다면 구독과 좋아요 부탁드려요. 시청해 주셔서 감사합니다.
