사람이 아닌 에이전트를 위한 문서 작성법: OpenWiki 내부 공개

한 줄 요약

OpenWiki는 코드 저장소 문서를 사람이 읽기 좋은 설명서가 아니라 코딩 에이전트가 검색·조각 검색·자동 갱신하기 좋은 메모리로 만들려는 오픈소스 CLI 도구다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
에이전트용 문서(Agent-oriented docs) 사람용 문서와 구조가 다르다 에이전트는 전체 문서를 읽기보다 필요한 조각을 검색해 가져온다.
범용 메모리(General-purpose memory) AI 에이전트가 장기적으로 쓸 맥락 저장소가 필요하다 OpenWiki는 코드베이스 문서화를 범용 메모리의 첫 적용 영역으로 본다.
CLI 기반 개발자 도구(CLI developer tool) 설치와 초기 설정이 어려우면 개발자는 바로 이탈한다 openwiki init 한 줄로 위키 생성과 자동화 파일까지 만든다.
자동 갱신(Self-updating docs) 문서는 오래되면 오히려 에이전트를 헷갈리게 한다 Git 변경 이력을 보고 매일 위키를 업데이트하고 PR을 연다.
OKF(Open Knowledge Format) 검색·필터링을 위한 문서 메타데이터 표준이다 각 Markdown 파일 상단에 타입, 제목, 설명, 태그, 시간 등을 넣는다.
검색과 검색 보강(Retrieval) 문서 생성보다 필요한 문서를 정확히 찾는 것이 더 어렵다 구조화된 frontmatter와 링크가 에이전트 검색 품질을 높인다.
DeepSWE 벤치마크(DeepSWE benchmark) 실제 코딩 에이전트 성능을 비교하는 평가다 OpenWiki 사용 시 성공률은 소폭 개선되고 토큰 사용량은 크게 줄었다.
사람도 읽는 문서 초기 가정과 달리 개발자도 위키를 읽고 싶어 했다 그래서 Mermaid 다이어그램 같은 시각적 요소를 추가했다.

내가 모를 만한 것 / 처음 보는 것

  • OpenWiki — LangChain이 공개한 오픈소스 CLI 문서화 도구. 코드 저장소 문서를 코딩 에이전트가 읽기 좋게 생성하고 자동 갱신한다.
  • OKF(Open Knowledge Format) — Google이 제안한 Markdown 문서용 메타데이터 형식. 문서 상단 YAML frontmatter에 타입, 제목, 설명, 태그 등을 넣어 검색하기 쉽게 만든다.
  • YAML frontmatter — Markdown 파일 맨 위에 ---로 감싼 메타데이터 영역. 문서의 제목, 태그, 유형 등을 기계가 읽기 좋게 기록한다.
  • DeepSWE — 코딩 에이전트가 실제 개발 작업을 얼마나 잘 수행하는지 평가하는 벤치마크.
  • agents.md — AI 코딩 에이전트에게 프로젝트 지침을 알려주는 파일. OpenWiki는 여기에 “위키를 참고하라”는 안내를 주입한다.
  • Claude.md — Claude Code 같은 도구가 프로젝트 규칙과 맥락을 읽는 파일.
  • GitHub Actions cron — GitHub에서 정해진 시간마다 자동으로 작업을 실행하는 스케줄 설정.
  • Mermaid 다이어그램(Mermaid diagrams) — Markdown 안에 텍스트로 플로우차트, 시퀀스 다이어그램, 상태 다이어그램 등을 그리는 방식.
  • 검색 보강(Retrieval) — LLM이나 에이전트가 필요한 문서 조각을 찾아 컨텍스트로 가져오는 과정.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. OpenWiki의 핵심 명령은 openwiki init과 openwiki update 두 가지다 — 초기 생성과 이후 갱신 흐름을 분리한다.
  2. 설치는 npm install openwiki로 가능하다고 설명한다 — 개발자 온보딩을 최대한 낮추려는 의도다.
  3. OpenWiki는 quickstart.md를 항상 만든다 — 에이전트가 레포 전체와 위키 구조를 먼저 파악하는 진입점이다.
  4. 생성 파일에는 agents.md, GitHub Actions workflow, index.md, log.md 등이 포함된다 — 문서 자체뿐 아니라 에이전트 안내와 자동화 장치까지 생성한다.
  5. log.md는 changelog처럼 사용된다 — 사람은 전체 위키를 읽기보다 변경 요약만 확인하면 된다.
  6. OKF는 영상 시점에 0.1을 쓰고 있었고, 0.2 지원을 곧 추가할 예정이라고 말한다 — 아직 빠르게 변하는 초기 표준이다.
  7. OKF 주요 필드는 type, title, description, resource tags, timestamp다 — 검색·필터링에 쓰는 결정적 필드다.
  8. DeepSWE 20개 작업에서 OpenWiki 없이 성공 작업이 보통 7~8개, OpenWiki 사용 시 9~10개였다고 한다 — 성공률은 소폭 개선이지만 토큰 절감이 핵심이다.
  9. 토큰 절감의 이유는 에이전트가 코드베이스를 덜 헤매기 때문이다 — 문서가 좋은 네비게이션 역할을 한다.
  10. Git 변경이 없으면 last_update.json을 보고 OpenWiki update를 실행하지 않는다 — 불필요한 비용과 PR 생성을 막는다.
  11. 기본 업데이트 주기는 하루 1회다 — 다만 하루 2,000커밋 수준이면 4시간, 6시간, 8시간 주기로 바꾸라고 말한다.
  12. OpenWiki는 MIT 라이선스다 — 회사 내부 용도에 맞게 포크하고 수정해서 쓰기 쉽다.
  13. 지원 LLM 제공자는 10~15개라고 언급한다 — 특정 모델에만 묶이지 않으려는 설계다.
  14. 현재 에이전트가 OpenWiki를 인식하는 방식은 agents.md 또는 Claude.md에 안내를 쓰는 것이다 — 향후 전용 검색 도구로 발전시킬 계획이다.

# 섹션 요지
1 OpenWiki를 만든 이유 AI 에이전트 시대에는 코드베이스용 범용 메모리가 필요하다.
2 사람용 문서와 에이전트용 문서의 차이 에이전트는 이야기 흐름보다 조각 검색, 정확한 제목, 작은 컨텍스트를 원한다.
3 CLI와 쉬운 온보딩 openwiki init으로 API 키, 모델, 지침 설정 후 자동 생성한다.
4 생성되는 문서 구조 quickstart.md, 디렉터리별 Markdown, OKF frontmatter, index, log를 만든다.
5 OKF와 검색 문서 메타데이터와 링크가 검색·필터링 성능을 높인다.
6 DeepSWE 평가 성공률은 약간 오르고, 토큰과 검색·툴 호출이 줄어든다.
7 개발 중 배운 점 사람도 문서를 읽고 싶어 하므로 다이어그램을 추가했다.
8 CLI 내부 동작 init은 초기 생성, update는 Git 변경 기반 갱신과 PR 생성을 담당한다.
9 현재 상태와 향후 계획 MIT 오픈소스이며, 더 나은 프롬프트와 전용 검색 도구를 준비 중이다.

1. OpenWiki를 만든 이유: 코드베이스용 범용 메모리

OpenWiki는 코드 저장소(repository)의 문서를 생성하고 유지하는 CLI 도구다. 핵심은 이 문서가 사람이 읽기 위한 설명서가 아니라 에이전트(agent)가 소비하기 위한 문서라는 점이다.

화자는 최근 AI 분야의 다음 큰 흐름이 무엇이냐는 질문에 범용 메모리(general-purpose memory)라고 답했다고 한다. 지난 몇 년 동안 에이전트 메모리는 연구 주제로 계속 등장했지만, 범용적으로 잘 작동하는 해결책은 아직 없다고 본다.

그래서 OpenWiki는 범용 메모리의 첫 적용 대상으로 코드베이스 문서화(codebase documentation)를 선택했다. 코드 저장소는 범위가 비교적 명확하고, 에이전트가 실제로 코드를 수정할 때 반복적으로 필요한 맥락이 많기 때문이다.

OpenWiki의 기본 가설은 세 가지다.

  1. 문서는 에이전트가 읽도록 설계되어야 한다.
  2. 개발자 도구이므로 설치와 설정이 아주 쉬워야 한다.
  3. 문서는 자동으로 최신 상태를 유지해야 한다.

2. 사람용 문서와 에이전트용 문서는 구조가 다르다

사람용 문서는 보통 이야기가 필요하다. 예를 들어 빠른 시작(quick start), 배경 설명, 자연스럽게 이어지는 페이지 흐름, 스크린샷, 동영상 등이 중요하다. 사람에게는 이런 구성이 이해를 돕는다.

하지만 에이전트는 다르게 움직인다. 에이전트는 전체 문서 페이지를 처음부터 끝까지 읽기보다, 검색이나 도구 호출을 통해 필요한 문서 조각(fragment)을 가져온다. 그래서 에이전트용 문서는 다음 조건이 중요하다.

  • 각 개념이 독립적으로 이해 가능해야 한다.
  • 제목이 예측 가능하고 정확해야 한다.
  • 검색과 필터링에 적합해야 한다.
  • 컨텍스트 창(context window)에 들어갈 수 있도록 간결해야 한다.
  • Base64 문자열처럼 불필요하게 토큰을 많이 잡아먹는 내용은 피해야 한다.

즉, 에이전트용 문서는 보기 좋고 흐름 있는 문서가 아니라, 검색 가능한 작은 지식 단위에 가깝다.

3. CLI 기반 쉬운 설정

OpenWiki는 개발자 도구이기 때문에 설정이 복잡하면 안 된다. 그래서 CLI(Command Line Interface) 형태를 선택했다.

기본 흐름은 간단하다.

  1. npm으로 설치한다.
  2. openwiki init을 실행한다.
  3. API 키를 설정한다.
  4. 사용할 모델을 고른다.
  5. 레포를 어떻게 탐색해야 하는지 알려주는 위키 지침(wiki brief)을 입력한다.
  6. OpenWiki가 문서를 자동 생성한다.

이 과정에서 OpenWiki는 문서 파일만 만드는 것이 아니라, 에이전트가 위키를 참고하도록 agents.md를 생성하거나 수정하고, 앞으로 문서를 자동 갱신할 GitHub Actions 파일도 만든다.

화자의 관점에서 중요한 것은 “문서 생성 품질”만이 아니다. 개발자가 실제로 써보게 만들려면 초기 경험이 짧고 명확해야 한다.

4. OpenWiki가 실제로 만드는 문서 구조

OpenWiki가 만드는 결과물은 Karpathy의 LLM wiki와 비슷하게 여러 Markdown 파일로 구성된다. 다만 에이전트가 찾고 읽기 쉽도록 구조화되어 있다.

항상 생성되는 핵심 파일은 quickstart.md다. 이 파일은 에이전트가 레포의 전체 구조와 위키 내용을 빠르게 이해하는 출발점이다.

그 외에는 에이전트가 필요하다고 판단한 주제별 디렉터리와 문서가 만들어진다. OpenWiki는 어떤 디렉터리와 주제를 만들지 과도하게 지정하지 않는다. 대신 다음 정도의 가이드만 준다.

  • 대략 몇 개의 파일을 만들 것인가
  • 각 파일의 크기는 어느 정도가 적절한가
  • 각 파일은 하나의 구체적 주제에 집중할 것인가

목표는 에이전트가 한 파일을 읽을 때 여러 곳에서 맥락을 다시 찾아야 하지 않게 만드는 것이다.

또한 OpenWiki는 다음 파일도 생성한다.

  • index.md — 해당 디렉터리의 파일 목록과 요약
  • log.md — 위키 변경 이력
  • OKF 형식의 YAML frontmatter — 각 문서의 타입, 제목, 설명, 태그, 시간 등

특히 log.md는 사람에게도 유용하다. 개발자는 위키 전체를 매번 읽지 않아도, 변경 로그를 통해 이번 업데이트에서 무엇이 바뀌었는지 파악할 수 있다.

5. OKF(Open Knowledge Format)와 검색의 중요성

OKF(Open Knowledge Format)는 Google의 간단한 문서 메타데이터 규격이다. Markdown 파일 상단에 YAML frontmatter를 넣어 문서의 성격을 명확히 기록한다.

예를 들어 다음 같은 정보를 담는다.

  • 문서 유형(type)
  • 제목(title)
  • 설명(description)
  • 리소스 태그(resource tags)
  • 타임스탬프(timestamp)
  • 필요 시 추가 필드

이 작은 메타데이터가 중요한 이유는 검색과 필터링 때문이다. 예를 들어 에이전트가 “아키텍처 문서만 찾아줘”라고 할 때 type 필드로 필터링할 수 있다. 특정 모듈이나 개념 관련 문서만 찾을 때는 태그를 활용할 수 있다.

화자는 문서 생성 자체는 LLM 에이전트로 비교적 쉽게 할 수 있지만, 필요한 문서를 정확히 가져오는 검색(retrieval)이 더 어렵다고 말한다. OKF는 그 검색 문제를 줄이는 장치다.

또한 문서 간 링크도 중요하다. 에이전트가 문서 A에서 어떤 개념을 읽다가 문서 B로 연결된 링크를 발견하면, 관련 맥락을 빠르게 따라갈 수 있다. 이는 에이전트가 코드베이스 안에서 길을 덜 잃게 만든다.

6. DeepSWE 벤치마크 결과

OpenWiki 팀은 아직 초기 평가 단계이지만 DeepSWE라는 코딩 에이전트 벤치마크 일부 작업으로 실험했다.

비교 방식은 다음과 같다.

  1. OpenWiki 없이 일반 DeepSWE 작업을 실행한다.
  2. 같은 작업에 대해 위키를 생성한다.
  3. OpenWiki가 있는 상태로 다시 실행한다.

초기 결과는 다음과 같다.

  • 에이전트의 도구 호출(tool calls)이 줄어든다.
  • 검색 횟수가 줄어든다.
  • 출력량이 줄어든다.
  • 토큰 소비가 크게 줄어든다.
  • 성공률은 소폭 개선된다.

화자는 20개 작업 기준으로 OpenWiki 없이 보통 7~8개 성공, OpenWiki 사용 시 9~10개 성공을 봤다고 한다. 다만 핵심은 성공률보다 토큰 사용량 감소다. 좋은 문서가 있으면 에이전트가 코드베이스를 더 효율적으로 탐색하고 변경을 구현할 수 있다.

7. 개발 중 틀렸던 가정: 사람도 문서를 읽고 싶어 했다

처음에는 “이 문서는 에이전트만 읽을 것”이라고 생각했다. 하지만 사용자 피드백은 달랐다. 개발자들도 이 문서를 읽고 싶어 했다.

그래서 OpenWiki는 사람에게도 조금 더 친화적인 형태로 바뀌었다. 대표적인 변화가 다이어그램 추가다.

초기에는 모든 문서가 Markdown 텍스트 중심이었다. 에이전트는 텍스트를 잘 읽으므로 충분하다고 생각했다. 하지만 사람은 시퀀스 다이어그램(sequence diagram), 상태 다이어그램(state diagram), 플로우차트(flowchart) 같은 시각 자료에서 구조를 훨씬 빨리 이해한다.

화자는 다이어그램이 에이전트에게도 도움이 되는지에 대한 평가 결과는 아직 없다고 했다. 하지만 에이전트가 다이어그램을 생성할 수 있다면 소비도 어느 정도 가능할 수 있고, 무엇보다 사람 사용자에게 큰 도움이 된다.

8. OpenWiki CLI 내부 동작: init

OpenWiki CLI에는 핵심 명령이 두 가지 있다.

  • openwiki init
  • openwiki update

init은 레포에 OpenWiki를 처음 적용할 때 실행한다.

초기 설정 마법사(setup wizard)는 다음을 묻는다.

  • LLM API 키
  • 사용할 모델
  • 에이전트 설정
  • 레포에 대한 고수준 지침

그다음 OpenWiki는 자동으로 필요한 파일을 쓴다.

첫째, GitHub Actions workflow를 생성한다. 이 워크플로는 매일 cron으로 실행되어 위키를 최신 상태로 유지한다.

둘째, agents.md나 Claude.md를 수정하거나 생성한다. 이 파일에는 에이전트가 OpenWiki가 무엇인지, 어디서 접근할 수 있는지, 언제 참고해야 하는지 알려주는 짧은 안내가 들어간다.

셋째, 실제 문서 생성 에이전트를 실행한다. 이 에이전트는 현재 코드만 보는 것이 아니라 Git 이력도 본다. 커밋 메시지와 제목을 통해 코드가 어떻게 변해왔는지 이해하려는 것이다.

마지막으로 결정적 검사 단계(deterministic pass)를 실행한다. 모든 문서가 OKF를 지키는지 확인하고, index.md, changelog 역할의 log.md, 기타 메타데이터 파일을 갱신한다.

9. OpenWiki CLI 내부 동작: update

update는 GitHub Actions의 스케줄 실행에서 자동으로 돌아간다.

첫 단계는 Git 이력을 확인하는 것이다. 마지막 실행 이후 변경이 없으면 OpenWiki를 실행하지 않는다. 이 상태는 last_update.json 같은 파일로 추적한다.

변경이 있다면 에이전트가 실행된다. 마지막 실행 이후 병합된 모든 커밋을 가져오고, 그 변경 내용을 바탕으로 위키를 갱신한다.

기본 주기는 하루 한 번이다. 하지만 하루에 커밋이 2,000개씩 들어가는 큰 레포라면 4시간, 6시간, 8시간마다 실행되도록 바꾸는 것이 좋다고 말한다.

업데이트가 끝나면 OpenWiki는 PR을 연다. 사용자는 그 PR을 확인하고 머지하면 최신 위키를 유지할 수 있다.

10. 현재 상태와 향후 계획

OpenWiki는 오픈소스 저장소로 공개되어 있고 MIT 라이선스다. npm으로 설치할 수 있으며, 다양한 LLM 제공자를 지원한다. 화자는 10~15개 정도의 제공자를 지원한다고 설명한다.

오픈소스로 만든 이유는 두 가지다.

첫째, 개발자는 오픈소스를 좋아하므로 채택이 쉬워진다.

둘째, 에이전트 문서화는 회사와 팀마다 워크플로가 다르기 때문에 직접 포크해서 수정할 필요가 있다. OpenWiki는 일반적인 형태로 만들었지만, 특정 조직의 코드 스타일과 업무 방식에 맞게 바꿔 쓰는 것이 자연스럽다.

향후 계획은 크게 두 가지다.

  1. 더 나은 프롬프트(prompting)
  2. 전용 검색·검색 보강 도구(search and retrieval tools)

현재는 agents.md나 Claude.md에 “OpenWiki를 참고하라”는 안내를 넣는 방식이다. 하지만 이것이 최종 형태는 아니다. 앞으로는 에이전트가 위키를 직접 검색하고 필터링하고 질의할 수 있는 전용 도구가 필요하다.

화자는 내부 평가에서 이런 전용 검색 도구가 이미 성능 개선을 보였다고 말한다. 따라서 다음 단계는 더 큰 레포를 잘 분석하는 프롬프트와, 위키에 특화된 검색 도구를 제공하는 것이다.

와주셔서 감사합니다.

앞서 소개된 것처럼, 오늘은 저희 프로젝트 OpenWiki에 대해 이야기하겠습니다. 왜 만들었는지, 어떤 아이디어에서 출발했는지, 내부적으로 어떻게 작동하는지, 앞으로 어디로 가려 하는지를 설명하겠습니다.

OpenWiki는 무엇일까요? OpenWiki는 코드 저장소(repository) 문서를 생성하고 유지하는 CLI입니다. 특히 에이전트(agent)가 소비하도록 설계되었습니다. 이것이 OpenWiki의 핵심 주제이고, 뒤에서 더 자세히 설명하겠습니다.

먼저 왜 만들었는지부터 이야기하겠습니다. 몇 주 전 저희 CEO Harrison이 “AI 분야의 다음 큰 것은 무엇일까? 작년에는 OpenAI가 큰 흐름이었다”라고 물었습니다. 물론 제가 위키가 OpenAI라고 주장하려는 것은 아닙니다. 대상도 다릅니다. 다만 그가 말한 요지는, 작년에 OpenAI나 개인 에이전트(personal agents)가 큰 주제였다면 올해 또는 지금의 큰 주제는 무엇이냐는 것이었습니다.

제 답은 범용 메모리(general-purpose memory)였습니다. 메모리는 지난 3년 반에서 4년 동안 에이전트 분야의 프런티어 연구 주제였다고 봅니다. 하지만 범용적인 방식으로 정말 잘 해낸 사례는 아직 없다고 생각합니다. 그래서 저는 실제로 작동할 다음 큰 흐름이 범용 메모리라고 봅니다.

저희는 코드베이스 문서(codebase docs)에서 시작하기로 했습니다. 범위가 명확하고, 범용 코드베이스 메모리 솔루션을 만들 수 있다고 믿는 영역이기 때문입니다. 이후 더 많은 메모리 영역으로 확장할 수 있습니다. 최신 LLM과 에이전트 아키텍처 덕분에 이제 이런 일이 가능해졌다고 생각합니다.

저희의 가설은 세 가지입니다. 첫째, 에이전트를 위해 만들어야 한다는 것입니다. 많은 메모리 도구나 문서화 에이전트, 저장소 문서 사이트는 에이전트와 사람을 모두 대상으로 합니다. 하지만 그러면 콘텐츠를 구조화하고 표현하고 생성·유지하는 방식이 크게 달라집니다.

저희 가설은 이제 사람들이 거의 모든 일에 에이전트를 쓴다는 것입니다. 아마 여러분도 예전만큼 많은 코드를 직접 작성하지 않을 것입니다. 에이전트가 상당 부분을 작성하고 있을 가능성이 큽니다. 그렇다면 이 문서도 에이전트가 소비하도록 특별히 만들어져야 합니다. 이는 문서 생성 방식과 구조를 바꿉니다.

둘째, 이것은 개발자 도구이므로 설정이 아주 쉬워야 합니다. 그래서 CLI를 선택했습니다. 설치가 쉽고 온보딩도 간단하기 때문입니다. 개발자에게 무언가를 써보게 하려면 설정이 정말 쉬워야 합니다. 그래서 CLI와 간단한 온보딩이 가장 적합하다고 봤습니다.

셋째, 문서가 스스로 업데이트되어야 합니다. Claude Code에게 코드 저장소의 위키나 문서를 만들라고 하면 꽤 잘 만들어줍니다. 하지만 그 문서를 최신 상태로 자동 유지하는 문제는 훨씬 어렵습니다. OpenWiki는 추가 작업 없이 위키 업데이트를 자동으로 처리할 수 있어야 합니다.

정리하면 세 가지입니다. 에이전트가 소비하도록 문서를 만들 것, 설정과 실행을 매우 쉽게 만들 것, 이후 아무것도 하지 않아도 문서가 자동으로 업데이트되게 할 것입니다.

첫 번째 주제는 사람용이 아니라 에이전트용 문서를 만드는 것입니다. 이것이 실제로 무엇을 바꿀까요?

사람용 문서를 만든다면 이야기를 전달해야 할 가능성이 큽니다. 빠른 시작 문서에는 저장소 배경이 있어야 하고, 각 문서 페이지는 자연스럽게 이어져야 합니다. 여기저기 고립된 조각만 있으면 안 됩니다. 스크린샷이나 영상도 들어갈 수 있습니다. 이런 요소는 사람이 소비하기에는 좋지만, 에이전트가 소비하기에는 최적화되어 있지 않습니다.

에이전트용으로 만든다면, 에이전트는 아마 전체 문서 페이지나 전체 디렉터리를 읽지 않고 조각(fragment)을 검색해 가져올 것입니다. 그래서 각 개념은 자기완결적이어야 합니다. 에이전트가 조각만 가져오기 때문입니다. 또한 필터링과 검색을 위해 예측 가능하고 정확한 제목이 필요합니다. 모든 내용은 컨텍스트 창(context window)에 들어가도록 최적화되어야 합니다. 예를 들어 임의의 Base64 문자열이 도구 호출에 포함되어 5만 토큰을 추가하는 일은 피해야 합니다.

따라서 문서를 어떻게 생성하고 구조화할지는 대상이 사람인지 에이전트인지에 따라 크게 달라집니다. 그리고 저희는 오늘날 에이전트가 우리 대신 코드를 많이 작성한다고 보기 때문에, 문서는 에이전트에 맞게 설계되어야 한다고 봅니다.

설정은 아주 쉬워야 합니다. 앞서 말했듯이 저희는 CLI를 선택했습니다. CLI는 설정하기 쉽습니다. 여기 있는 분들도 모두 CLI를 써봤거나 매일 쓰고 있을 것입니다. 설치는 npm을 통한 한 줄 명령이고, 위키 초기화도 한 줄입니다. openwiki init을 실행하면 API 키 설정, 모델 설정, 위키 브리프(wiki brief) 설정을 안내합니다. 위키 브리프는 에이전트가 저장소를 어떻게 탐색해야 하는지 알려주는 프롬프트 같은 것입니다. 그다음 위키 생성이 자동으로 시작됩니다.

OpenWiki는 여러 파일을 작성합니다. 예를 들어 agents.md를 만들거나 이미 있다면 수정합니다. 이 파일은 에이전트에게 위키를 참고하라고 알려줍니다. 또한 앞으로 위키를 자동 업데이트할 GitHub Actions 파일도 작성합니다.

이 모든 과정이 쉬워야 합니다. 그렇지 않으면 많은 개발자가 이탈합니다. 그래서 저희는 짧은 온보딩을 가진 CLI가 가장 쉽다고 판단했습니다. 이 CLI는 문서뿐 아니라 위키를 사용하기 위해 필요한 다른 파일들도 자동으로 작성합니다.

실제로 무엇을 작성할까요? Karpathy의 LLM wiki를 본 적이 있다면 비슷하게 느껴질 것입니다. 특정 구조를 가진 Markdown 파일들이 있고, 파일들 사이에 링크가 있습니다.

OpenWiki는 항상 quickstart.md를 만듭니다. 저희는 에이전트가 이 파일을 보고 저장소와 위키의 다른 문서 내용을 높은 수준에서 이해하도록 프롬프트합니다. 이후 필요한 문서들을 여러 디렉터리로 나눕니다. 어떤 디렉터리를 만들지, 어떤 주제나 개념을 문서화할지에 대해 저희가 지나치게 많은 지침을 주지는 않습니다. 그것은 에이전트에게 맡깁니다.

대신 대략 몇 개의 파일을 쓸지, 각 파일의 크기는 어느 정도인지, 각 파일이 매우 구체적인 하나의 주제에 집중해야 한다는 정도의 지침을 줍니다. 이렇게 하면 에이전트가 개별 파일을 읽을 때 여러 영역에서 맥락을 가져오지 않아도 됩니다.

그리고 OKF, 즉 Google의 Open Knowledge Format을 채택했습니다. OKF는 각 Markdown 파일에 결정적인 frontmatter, 즉 YAML frontmatter를 추가합니다. 여기에는 타입(type), 제목(title), 설명(description) 등이 들어갑니다. 잠시 뒤 더 설명하겠습니다.

또 디렉터리 안의 모든 파일을 색인화하는 index 파일이 있습니다. 에이전트는 이를 통해 특정 디렉터리에 무엇이 있는지 빠르게 파악할 수 있습니다. 그리고 log 파일도 있습니다. 이것은 changelog와 비슷합니다.

저는 이 부분이 에이전트에게 매우 중요하다고 봅니다. 위키의 이력을 볼 수 있기 때문입니다. 동시에 사람에게도 중요합니다. 사람이 위키를 꼭 읽을 필요는 없지만, 이 위키는 코드베이스에 체크인됩니다. 그러면 위키 업데이트 때 무엇이 바뀌는지는 읽고 싶을 것입니다. 그래서 log.md는 changelog라고 생각하면 됩니다.

저희는 사용자에게 changelog를 보라고 말합니다. 위키에서 무엇이 바뀌었는지 볼 수 있는 곳입니다. 더 깊이 들어가고 싶다면 변경된 개별 파일을 보면 됩니다. 하지만 꼭 그럴 필요는 없습니다. 최근 위키 업데이트에서 무엇이 바뀌었는지 이해하는 데 필요한 정보는 changelog가 제공해야 합니다.

앞서 OKF를 언급했습니다. 이것은 Google의 Open Knowledge Format입니다. 화면에는 0.1이라고 되어 있지만, Google이 방금 0.2를 출시했고 저희도 하루 이틀 안에 지원을 추가할 예정입니다.

OKF는 무엇일까요? 매우 단순한 규격입니다. 본질적으로 모든 Markdown 파일의 상단에 특정 frontmatter를 추가하는 것입니다. 여기에는 type, title, description, resource tags, timestamp가 있습니다. 특정 개념이나 태그를 위해 임의 필드도 추가할 수 있습니다. 하지만 OKF 규격에서 정의한 주요 필드는 이것들입니다.

이 구조는 저장소 안에서 검색(retrieval), 필터링(filtering), 탐색(searching)을 할 때 많은 흥미로운 기능을 가능하게 합니다. 타입으로 필터링할 수 있기 때문입니다. 예를 들어 “모든 아키텍처 문서를 줘”라고 할 수 있습니다. 태그 필드가 있으므로 태그로도 필터링할 수 있습니다.

모든 위키 문서 상단에 이 작은 섹션을 추가하는 것만으로도 검색 측면에서는 효과가 누적됩니다. 문서나 위키 생성보다 검색이 더 큰 문제라고 볼 수 있습니다.

에이전트로 문서를 생성하는 것은 비교적 쉽습니다. 하지만 이 문서에서 필요한 내용을 검색하는 것은 훨씬 어렵습니다. OKF는 필터링과 검색에 빠르게 쓸 수 있는 결정적인 필드를 제공하므로 이 문제를 더 쉽게 만듭니다.

문서 간 링크도 중요합니다. OKF에는 코드베이스의 개별 파일을 가리킬 수 있는 resource tags가 있고, 문서 사이에는 Markdown 링크도 있습니다. 에이전트가 문서 A에서 조각을 가져왔는데 문서 B에 대한 참조 링크를 보면, 그 링크를 통해 빠르게 문서 B를 방문할 수 있습니다. Markdown 링크 자체가 OKF 전용은 아니지만, OKF는 문서 간 교차 링크를 강조합니다. 이를 통해 에이전트는 읽고 있는 맥락과 관련된 다른 맥락을 빠르게 발견할 수 있습니다.

지금까지 OpenWiki가 무엇인지 설명했습니다. 그렇다면 실제로 효과가 있을까요?

저희의 평가(eval) 과정은 아직 매우 초기입니다. 지금은 DeepSWE라는 코딩 에이전트 벤치마크에서 일부 작업을 가져와 OpenWiki 없이 실행하고, 같은 작업에 대해 위키를 생성한 뒤 다시 실행하는 방식으로 보고 있습니다.

지금까지 본 결과는 무엇일까요? 몇 가지 수치가 있습니다. 전반적으로 에이전트 사용이 더 간결해졌습니다. 도구 호출(tool calls)이 줄고, 검색이 줄고, 출력이 줄어들면서도 결과는 같거나 더 좋아졌습니다.

여기에는 없지만, 20개 작업에서 OpenWiki 없이 보통 7~8개 작업이 성공했고, OpenWiki를 사용하면 9~10개가 성공했습니다. 아주 약간 더 나은 수준입니다. 하지만 보시다시피 토큰 소비가 크게 줄어든 것이 핵심입니다. 이 문서는 에이전트에게 더 나은 맥락을 제공해야 하고, 그 결과 에이전트가 코드베이스를 더 효율적으로 탐색하고 변경을 구현할 수 있어야 합니다.

아직 초기 결과입니다. 곧 벤치마크에 대해 더 많이 공개할 예정입니다. 하지만 DeepSWE 작업의 초기 결과는 어느 정도 유망해 보입니다.

지금까지 한 일을 설명했습니다. 그렇다면 무엇을 잘못했을까요?

첫 번째는 에이전트만 읽을 것이라고 생각한 점입니다. 저는 코드를 쓸 때 에이전트만 사용하므로, 이 문서도 에이전트가 소비하도록 만들겠다고 생각했습니다. 그런데 곧 많은 피드백을 받았습니다. 사람들도 이 문서를 읽고 싶다는 것이었습니다. 돌이켜보면 당연합니다. 엔지니어링 과정에는 여전히 사람이 있습니다. 그 사람들도 코드를 읽고 싶어 합니다.

그래서 처음에는 순수하게 에이전트용으로 설계했지만, 이후 사람에게도 조금 더 친화적으로 만들기 위해 몇 가지 수정을 했습니다. 이것이 무엇을 의미할까요? 핵심은 다이어그램입니다. 사람에게는 다이어그램이 매우 중요합니다.

이전에도 모든 문서는 Markdown이었고 자연어였기 때문에 사람이 쉽게 읽을 수 있었습니다. 하지만 큰 변화는 다이어그램을 추가한 것입니다. 처음에는 에이전트에게 덜 중요해 보였기 때문에 추가하지 않았습니다. 에이전트는 텍스트를 읽으면 되니까요.

다이어그램을 추가한 뒤, 이것이 에이전트에게 더 좋은지 나쁜지 증명하는 평가는 아직 없습니다. 하지만 다이어그램이 에이전트에게도 도움이 될 수 있다는 생각은 어느 정도 합리적입니다. 무엇보다 사용자가 시퀀스, 상태 다이어그램, 플로우차트를 통해 훨씬 쉽게 이해할 수 있습니다.

에이전트가 이런 다이어그램을 생성하는 것은 어렵지 않습니다. 에이전트가 생성할 수 있다면 소비도 할 수 있다고 주장할 수도 있습니다. 하지만 여기서 핵심은 사람이 단순 텍스트보다 훨씬 쉽게 문서를 이해하게 된다는 점입니다.

그래서 처음에는 에이전트만 읽을 것이라고 생각했지만, 곧 사람도 읽고 싶어 한다는 사실을 알게 됐습니다.

이제 OpenWiki CLI가 실제로 어떻게 작동하는지 조금 설명하겠습니다. 매우 단순합니다. 명령은 두 개입니다. openwiki init과 update입니다. 먼저 init은 저장소 설정 시 처음 실행하는 명령입니다. 저장소를 초기화합니다.

설정 마법사가 있습니다. API 키를 설정하고, 모델을 선택하고, 지침(instructions)을 설정합니다. 이 지침은 CLI 에이전트에게 저장소에 대한 더 구체적인 내용을 알려주는 고수준 프롬프트입니다. 위키 생성을 위한 유일한 프롬프트는 아니지만, 에이전트에게 제공할 수 있는 추가 맥락입니다. 설정 마법사는 매우 단순합니다. LLM 키, 모델, 에이전트 설정입니다.

그다음 앞서 말한 파일들을 자동으로 작성합니다. GitHub Actions workflow가 있습니다. 이것은 매일 cron을 실행해서 코드베이스 변경 사항을 바탕으로 위키를 자동 최신 상태로 유지합니다.

agents.md나 Claude.md, 또는 둘 다 있으면 수정합니다. 여기에 OpenWiki가 무엇인지, 어떻게 접근하는지, 언제 참고해야 하는지에 대한 작은 맥락을 주입합니다. 지금은 이것이 에이전트가 OpenWiki를 인식하는 유일한 방법입니다. 나중에 추가할 변경 사항도 뒤에서 이야기하겠습니다.

그리고 GitHub Action에 매일 실행되는 cron을 설정합니다. 사용자가 이 파일들을 승인하고 머지하면 GitHub Action의 cron이 동작합니다. 그러면 OpenWiki는 거의 잊어버려도 됩니다. 매일 새 변경 사항을 기반으로 위키가 계속 업데이트됩니다. 에이전트는 이미 OpenWiki를 알고 있고, 사용자는 크게 신경 쓰지 않아도 효율성 향상을 얻습니다.

에이전트를 설정하고 저장소 스캐폴딩(scaffolding)을 만든 뒤에는 실제 에이전트를 실행합니다. 에이전트는 저장소를 보고 계획을 쓰고 Git 이력을 봅니다. 이것은 꽤 중요합니다. 현재 저장소의 코드만 읽는 것이 아니라 Git 이력도 봐야 합니다. 그래야 저장소가 어떻게 바뀌고 발전했는지 볼 수 있습니다. Git 코멘트와 Git 제목도 볼 수 있습니다. 현재 스냅샷만 보는 것이 아니라 변경 이력 속으로 더 깊이 들어가야 합니다.

그런 다음 실제 문서를 씁니다. 마지막에는 결정적 검사 단계가 있습니다. 모든 문서를 훑으면서 OKF를 준수하는지 확인합니다. index.md와 changelog를 자동으로 작성합니다. 이후 에이전트가 무엇을 변경했는지에 대한 구체 내용을 추가하게 합니다. 마지막에는 몇 가지 메타데이터 파일도 업데이트합니다.

이것이 init 실행입니다. 저장소에 OpenWiki를 처음 도입할 때 실행합니다.

다음은 update입니다. 매우 비슷합니다. OpenWiki init이 작성해준 GitHub Action에서 예약 실행이 돌아가고, 이때 openwiki update가 실행됩니다.

처음 하는 일은 Git 이력을 보는 것입니다. 마지막 실행 이후 변경 사항이 없다면, 그리고 이 변경 사항을 last_update.json 파일에서 추적하고 있다면, OpenWiki를 실행하지 않습니다. 변경이 없으면 저장소를 업데이트할 필요가 없습니다.

변경 사항이 있으면 에이전트를 실행합니다. Git log를 보고, 에이전트가 마지막으로 실행된 이후 병합된 모든 커밋을 가져옵니다. 기본적으로 하루 한 번 실행합니다. 만약 매일 저장소에 2,000개 커밋을 넣고 있다면, 반복 실행 액션을 4시간, 6시간, 8시간마다 실행하도록 바꾸는 것이 좋습니다.

이렇게 Git 이력을 보고 변경된 내용을 바탕으로 저장소를 업데이트한 뒤 PR을 엽니다. 사용자는 그 PR을 머지하면 위키가 최신 상태가 됩니다.

현재 상태는 어떨까요? OpenWiki는 오픈소스 저장소입니다. GitHub에 여러 스타가 있고, 많은 포크가 있습니다. 사람들은 이것을 가져가 포크하고 자신의 용도에 맞게 수정하거나 npm에서 그대로 사용합니다. MIT 라이선스입니다. npm으로 설치할 수 있고, 원하는 제공자를 사용할 수 있습니다. 10개나 15개 정도의 서로 다른 제공자를 지원합니다. 또는 포크해서 특정 사용 사례에 맞게 수정한 뒤 저장소에서 사용할 수도 있습니다.

저희는 이것이 오픈소스 프로젝트여야 한다고 생각했습니다. 개발자는 오픈소스를 좋아하므로 채택을 얻는 좋은 방법이기 때문입니다. 또한 각자의 사용 방식에 맞게 커스터마이즈할 수 있습니다. 에이전트 문서에서는 이것이 중요합니다. 저희는 매우 일반적인 방식으로 만들지만, 특정 워크플로나 OpenWiki를 써야 하는 특별한 이유가 있다면 포크해서 직접 수정하고 싶을 것입니다.

다음은 무엇일까요? 당연히 더 나은 프롬프트입니다. 저희는 평가에 더 많이 투자하기 시작했습니다. 이것이 DeepSWE 평가입니다. 더 큰 저장소를 분석하고 스스로 업데이트하기 위한 더 나은 프롬프트가 필요합니다. 그리고 검색과 검색 보강 도구(search and retrieval tools)가 필요합니다.

앞서 말했듯이 지금은 agents.md 또는 Claude.md에 OpenWiki에 대해 알려주는 내용을 씁니다. 하지만 이것이 최종 상태는 아닙니다. 이 방식도 좋고 에이전트가 이를 읽긴 합니다. 하지만 위키를 검색하고 필터링하고 질의할 수 있는 전용 도구를 제공하는 것이 분명한 다음 단계입니다. 아직 머지되지 않은 일부 평가에서도 이 접근으로 개선을 확인했습니다.

그래서 더 나은 프롬프트, 그리고 위키를 위한 더 구체적인 검색 도구를 곧 내놓을 예정입니다.

이상입니다. 문서화가 가장 안 된 저장소에 한번 써보세요. QR 코드는 GitHub 저장소로 연결됩니다. npm install openwiki로 설치할 수도 있습니다.
