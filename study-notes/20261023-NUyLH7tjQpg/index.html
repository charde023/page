하네스는 더 이상 필요 없을까? AI가 똑똑해져도 남는 3가지

업로드 2026-10-23 · 8.5분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상의 중심 질문은 “AI 모델이 스스로 코딩을 잘하게 되면, 모델을 둘러싼 도구도 필요 없어지는가?”이다. 여기서 모델은 생각하는 머리이고, 하네스(harness)는 그 머리가 파일·컴퓨터·외부 서비스에 손을 뻗도록 연결하고 행동 범위를 정하는 장치다. 발표자는 이를 모델의 “눈과 손”이라고 표현한다.

하네스가 맡는 일은 하나가 아니다. 과거에는 모델이 서툰 코딩 동작을 보충하는 역할도 했다. 예를 들어 Cursor에는 파일의 코드 수정을 적용하는 작은 모델과 코드 저장소를 살피고 결과를 확인하는 방법을 알려주는 코딩 전용 지시가 있었다고 한다. 모델이 이런 기술을 직접 잘하게 되자 일부 보조 장치는 삭제됐다.

그러나 “일부 코딩 보조 장치가 줄었다”와 “하네스 전체가 필요 없어졌다”는 같은 말이 아니다. AI가 코딩 창을 벗어나 장시간 일하고 외부 서비스에 접속하며 여러 작업을 나눠 수행하면 새로운 문제가 생긴다. 작업이 계속 실행될 환경, 꼭 필요한 권한만 주는 통제, 예상하지 못한 행동을 막는 안전장치, 같은 결과를 더 적은 비용으로 얻는 운영 설계가 필요하다.

읽는 법: 위에서 아래로 읽는다. 가운데의 1번과 2번은 선후 단계가 아니라 서로 다른 작업 상황이다. 마지막 상자는 두 상황 모두에서 별도로 점검할 운영 역할이다. 이 그림은 수치를 나타내는 그래프가 아니라 영상의 개념 관계를 정리한 지도다.

익숙한 기술은 모델 안으로 들어갈 수 있다

발표자는 이 흐름을 데이터 플라이휠(data flywheel)이라고 부른다. 처음에는 하네스가 어려운 코딩 작업을 시도할 수 있게 돕는다. 더 많은 사용자가 그 작업을 시도하면 코딩 자료가 연구소에 공유되고, 모델이 해당 기술을 직접 배우게 된다는 설명이다. 그러면 하네스는 이전에 필요했던 보조 코드를 일부 삭제할 수 있다.

읽는 법: 첫 상자부터 아래로 내려간다. 마지막 상자에서는 아래쪽과 왼쪽을 잇는 선을 따라 첫 상자로 돌아간다. 다만 “다음 어려운 과제로 돌아간다”는 플라이휠이라는 표현을 풀어 쓴 해석이며, 전사에 같은 문장으로 제시된 것은 아니다. 자료 공유 범위와 실제 학습 경로도 제공 자료만으로 독립 검증되지는 않는다.

새로운 일에는 새 안전장치가 필요하다

모델이 코딩에 익숙해졌다고 해서 메일 발송이나 장시간 업무 조정까지 자동으로 익숙해지는 것은 아니다. 발표자가 소개한 Grokbot 방식에서는 사용자가 총괄 AI에게 일을 맡기고, 총괄 AI가 작업을 여러 작업자 AI에게 나눈다. 발표자는 이를 전략을 맡는 변호사와 세부 업무를 나누는 법률 보조 인력의 관계에 비유했다.

이 새로운 방식에서는 Cursor에서 지웠던 지시와 안전장치를 다시 넣었다고 한다. 새 영역의 작업을 모델이 아직 충분히 해내지 못하기 때문이다. 예를 들어 메일을 언제 보내도 되는지, 오래 걸리는 일을 언제 사용자에게 알려야 하는지는 코드를 잘 만드는 능력만으로 결정되지 않는다.

회사 내부 사례로는 버그 신고가 들어오면 자동 분류가 시작되고, Claude 에이전트가 수정을 시도하며, 전후 영상을 만들어 수정 결과를 보여주고, 병합과 배포가 시작되면 또 다른 에이전트가 운영 환경의 문제를 감시하는 흐름이 소개된다. 핵심은 한 번 답하고 끝나는 채팅이 아니라 여러 단계가 오래 이어지는 업무라는 점이다.

모델이 똑똑해져도 남는 세 가지

첫째는 실행 환경(runtime infrastructure)이다. 발표자는 에이전트의 일반적인 작업 시간이 분 단위에서 시간, 일, 그 이상으로 길어졌다고 말한다. 개인 노트북은 잠자기 상태로 들어갈 수 있으므로, 진정한 자율 업무를 원한다면 클라우드에서 실행해야 한다는 주장이다. 다시 접속했을 때 진행 상태도 찾을 수 있어야 한다.

둘째는 권한과 보안(trust and security)이다. 모델이 명령 실행 도구와 모든 API 키가 담긴 파일에 접근하면 코딩 과제를 풀 수 있을지 몰라도, 실제 조직에서는 그렇게 넓은 권한을 주기 어렵다. 발표자는 에이전트와 사람별로 권한 범위를 좁히고, 큰 피해나 예상 밖 행동을 막는 안전장치가 필요하다고 말한다.

셋째는 효율성(efficiency)이다. 발표자가 언급한 두 연구에서는 하네스 선택에 따라 평가 점수가 크게 달라지지 않았지만 작업당 비용에는 유의미한 차이가 있었다고 설명한다. 같은 설명을 반복해서 보내거나 작업과 맞지 않는 모델을 쓰면 결과 점수는 비슷해도 시간과 비용은 달라질 수 있다는 뜻이다.

읽는 법: 먼저 위쪽 행을 왼쪽에서 오른쪽으로 읽으면 익숙한 기술에서는 보조 장치가 줄고 새로운 기술에서는 다시 늘어나는 차이가 보인다. 이어 아래쪽 행을 읽으면 모델의 코딩 실력과 별개로 실행·권한·비용 문제가 두 상황에 모두 남는다는 관계가 보인다. 색은 작업 상황을 구분할 뿐이며, 판단은 각 칸의 문장으로 한다.

따라서 AI 도구를 볼 때는 네 질문을 분리해야 한다. 어려운 문제를 제대로 푸는가, 장시간 작업을 이어가는가, 필요한 권한만 사용하는가, 작업 하나에 시간과 비용이 얼마나 드는가? 첫 번째는 주로 결과 능력에 관한 질문이고, 나머지는 모델 바깥의 운영 설계까지 포함한다.

전체 통찰과 경계

  • [원문] 발표자는 Cursor에서 일부 코딩 전용 지시와 보조 장치를 없앴지만, 새로운 Grokbot 업무에는 지시와 안전장치를 다시 넣었다고 말했다. 실행 환경, 권한·보안, 효율성도 계속 필요한 역할로 제시했다.
  • [해석] 하네스가 사라지는 것이 아니라 역할의 중심이 이동한다. 모델이 익숙해진 기술을 보충하는 기능은 줄 수 있지만, 실제 업무를 오래·안전하게·감당 가능한 비용으로 운영하는 기능은 별도의 문제로 남는다.
  • [경계] 발표자가 언급한 두 연구의 이름과 구체적인 점수·비용 수치는 제공 자료에 없다. 데이터 플라이휠의 자료 공유 및 학습 경로와 Grokbot의 실제 성과도 독립 검증되지 않았다.
  • [경계] 6개월 안에 에이전트 작업의 90%가 노트북 밖에서 실행될 것이라는 수치는 현재 사용률이 아니라 발표자의 전망이다. 1만 달러 API 요금도 실제 사고 보도가 아니라 위험을 설명하기 위한 예시다.
  • [경계] 제공 전사의 “이런 흐름을 막으려면”이라는 문구는 앞뒤의 연속 업무 설명과 의미가 충돌한다. 흐름을 유지한다는 뜻인지 다른 뜻인지는 임의로 확정하지 않는다.
  • [경계] META 설명에는 Jediah Katz의 원본 강연 제목과 링크가 제시되어 있지만, provenance 기록은 화자 이름과 SNS를 기준으로 추정한 출처라고 밝힌다. 따라서 해당 강연과의 출처 관계는 확정된 사실이 아니라 원본 강연 후보로만 본다.

여기까지만 이해하면 충분

  • 하네스는 모델의 코딩 실력을 보충하는 장치만이 아니라, 모델을 실제 컴퓨터와 서비스에 연결하고 행동을 통제하는 전체 장치다.
  • 모델이 익숙한 코딩 기술을 직접 배우면 일부 코딩 전용 보조 장치는 줄어들 수 있지만, 새로운 업무에는 새 지시와 안전장치가 필요하다.
  • 실행 환경, 권한·보안, 작업당 비용 관리는 모델의 코딩 능력이 좋아져도 별도로 점검해야 한다.
  • 6개월 안에 90%라는 수치는 전망이고, 1만 달러 비용은 실제 사고가 아닌 위험 설명용 예시다.

비유와 깨지는 지점

자전거의 보조 바퀴

코딩을 서툴게 하던 모델에 붙인 전용 지시와 보조 코드는 자전거의 보조 바퀴와 비슷하다. 모델이 해당 기술을 직접 익히면 일부 장치는 떼어낼 수 있다.

비유가 깨지는 지점: 실제 하네스는 균형을 배우기 위한 임시 장치만이 아니다. 실행 환경, 외부 서비스 연결, 권한, 보안, 비용처럼 모델이 기술을 익혀도 따로 관리해야 하는 운영 역할까지 포함한다.

1. 원인

모델이 더 똑똑해졌는데도 하네스의 일부 기능이 다시 늘어나는 이유는 무엇인가?

모범 답안 보기

모델이 익숙한 코딩 기술을 직접 배우면 그 기술을 보충하던 장치는 줄어들 수 있다. 그러나 장시간 업무, 메일 발송, 여러 에이전트 조정처럼 새로운 영역에서는 모델이 아직 익히지 못한 판단과 위험이 생긴다. 그래서 새 지시와 안전장치가 다시 필요해진다.

2. 대조

모델의 문제 해결 능력과 하네스의 운영 능력은 어떻게 다른가?

모범 답안 보기

모델의 문제 해결 능력은 코드를 만들거나 과제를 푸는 능력에 가깝다. 하네스의 운영 능력은 그 작업을 오래 실행하고, 외부 도구와 연결하고, 권한을 제한하며, 비용을 관리하는 능력이다. 하나가 좋아졌다고 다른 하나가 자동으로 해결되는 것은 아니다.

3. 적용

새 AI 도구를 검토한다면 “정답을 잘 만드는가?” 외에 무엇을 확인해야 하는가?

모범 답안 보기

실제 업무가 얼마나 오래 실행되는지, 노트북이 중단돼도 상태가 유지되는지, 사람과 에이전트별 권한을 좁힐 수 있는지, 허용 범위 밖 행동을 막는지, 작업당 시간과 비용이 얼마인지 확인한다. 적용 전에는 가상 작업이나 제한된 환경에서 이 항목을 측정한다.

이번 글의 통찰

1. 지능 향상과 운영 신뢰성은 다른 축이다

  • [원문] 발표자는 일부 코딩 전용 지시와 보조 장치를 Cursor에서 삭제했지만, 장시간 실행 환경과 권한·보안·효율성은 여전히 필요하다고 말했다.
  • [해석] AI 도구를 평가할 때 모델 성능 하나로 전체 시스템의 신뢰성을 대신 판단하면 안 된다. 결과 품질과 운영 조건을 분리해 봐야 한다.
  • [경계] 발표자가 언급한 두 연구의 이름, 평가 점수, 작업당 비용 수치는 전사에 없다. “유의미한 차이”라는 표현은 화자의 설명으로만 보존한다.

2. 안전장치의 양은 작업의 새로움에 따라 달라진다

  • [원문] Cursor에서는 모델이 똑똑해지며 일부 지시와 안전장치를 제거했지만, Grokbot에서는 새로운 업무 때문에 지시와 안전장치를 다시 추가했다고 말했다.
  • [해석] 안전장치가 많거나 적다는 사실만으로 도구의 발전 정도를 판단할 수 없다. 모델이 익숙한 작업인지, 새 영역의 행동인지 먼저 구분해야 한다.
  • [경계] Grokbot의 실제 구성과 성과를 독립적으로 검증할 자료는 제공되지 않았다. 전사의 한국어 설명 중 “이런 흐름을 막으려면 AI가 멈추지 않고 일할 수 있어야” 한다는 문장은 앞서 설명한 연속 업무 흐름과 의미가 충돌하므로, 그 문구의 의도는 확정하지 않는다.

3. 강한 숫자는 관측값인지 전망인지 먼저 나눠야 한다

  • [원문] 발표자는 6개월 안에 에이전트 작업의 90%가 노트북 밖에서 실행될 것이라고 예측했다. 1만 달러 API 요금은 큰 위험을 설명하는 예시로 제시됐다.
  • [해석] 숫자가 구체적이어도 현재 상태를 측정한 값, 미래 전망, 가상 위험 예시는 서로 다른 증거 수준을 가진다.
  • [경계] 90%는 현재 사용률이 아니며 전망의 기준 날짜도 전사만으로 확정할 수 없다. 1만 달러 사례는 실제 사고 보도가 아니다. META 설명의 원본 강연 링크 제시와 provenance.note의 “확인하지 않은 추정 출처” 기록도 서로 일치하지 않는다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 영상은 “코딩 보조 장치가 줄었다”와 “하네스 전체가 사라진다”를 구분하고, 자전거 보조 바퀴 비유의 한계까지 보여준다.
  • 통찰: 학습자가 하네스를 단순 프롬프트가 아니라 실행·권한·비용까지 포함한 구조로 설명할 수 있는지 보면 이해를 관찰할 수 있다.
  • 질문/행동: 학습자에게 모델 능력과 운영 능력을 각각 한 사례로 설명하게 하고, 둘을 혼동한 지점을 확인한다.

사업가 · 구조적 비유

  • 관련성: 장시간 실행, 제한된 권한, 작업당 비용은 자원·위험·운영 효율의 문제다.
  • 통찰: APOM의 현재 시스템 상태는 출처에 없으므로 직접 적용 사실로 볼 수 없다. 다만 검증 전 가상 업무를 대상으로 결과 품질뿐 아니라 중단 위험, 권한 범위, 작업당 비용을 함께 비교하는 구조는 전이할 수 있다.
  • 질문/행동: 자동화를 검토한다면 “성공했는가?”와 함께 “누가 어떤 권한과 비용을 제공했는가?”를 기록할 수 있는지 묻는다.

마케터 · 직접 전이

  • 관련성: 영상은 90%를 전망으로, 1만 달러를 위험 설명용 예시로 분리해 제시한다.
  • 통찰: 구체적인 숫자는 주목을 만들지만 관측값·예측·가상 예시를 구분하지 않으면 증거보다 강한 주장으로 보일 수 있다.
  • 질문/행동: 상세페이지나 카피의 숫자 옆에 측정값, 전망, 예시 중 어떤 성격인지 표시한다.

AI/SW 학습자 · 직접 전이

  • 관련성: 하네스의 역할을 평가 점수, 실행 시간, 권한, 작업당 비용이라는 서로 다른 축으로 나눈다.
  • 통찰: 새 도구는 모델 이름보다 실제 작업의 길이와 병목을 기준으로 검토해야 한다. 정상 완료뿐 아니라 중단, 권한 이탈, 비용 증가도 시험 대상이다.
  • 질문/행동: 제한된 가상 작업에서 허용 도구 목록을 정한 뒤, 모델이 그 범위를 벗어나려 하는지 관찰한다.

  • 측정 1개: 허용 목록 밖 도구 또는 행동을 시도한 건수
  • 중단 기준 1개: 허용 목록 밖 시도가 1건 이상이면 실제 업무로 확대하지 않고 중단한다.

1. 하네스는 모델의 눈과 손이다

화자는 하네스를 모델을 둘러싸고 방향을 잡으며 세상과 연결하는 장치라고 설명한다. 사용자는 앱을 통해 하네스에 연결되고, 하네스는 모델을 컴퓨터와 MCP 같은 제3자 서비스 연결 수단에 이어 준다.

모델이 생각하는 머리라면 하네스는 파일을 수정하고 프로그램을 실행하는 손, 외부 상태를 보는 눈, 행동 범위를 정하는 울타리에 해당한다.

2. Cursor에서 줄어든 코딩 보조 장치

Jediah Katz로 소개된 발표자는 동료 Stefan과 함께 Cursor에서 모델의 지능 부족을 보충하던 안전장치를 제거했다고 말했다.

사례로는 다음이 제시됐다.

  • 파일에 코드 수정을 적용하던 작은 모델
  • 코드 저장소를 탐색하는 방법을 알려주는 코딩 전용 지시
  • 작업 결과를 확인하는 방법을 알려주는 지시

발표자는 두 연구를 근거로 같은 AI에 서로 다른 작업 도구를 붙여도 코딩 머신러닝 시험 점수가 크게 달라지지 않았다고 설명한다. 연구 이름과 구체 점수는 제공된 전사에 없다.

3. 데이터 플라이휠

발표자가 설명한 흐름은 다음과 같다.

  1. 하네스가 더 어려운 코딩 작업을 모델의 범위 안으로 가져온다.
  2. 더 많은 사용자가 에이전트로 그 작업을 시도한다.
  3. 더 많은 코딩 자료가 연구소에 공유된다.
  4. 모델이 해당 기술을 직접 잘하게 된다.
  5. 하네스는 그 기술을 보충하던 장치를 삭제할 수 있다.

이는 화자의 작동 원리 설명이며, 제공 자료만으로 자료 공유 범위와 학습 경로를 독립 검증할 수는 없다.

4. Grokbot과 새로운 업무

Grokbot으로 소개된 방식은 일회성 채팅 대신 장시간 유지되는 총괄 봇이 여러 작업자 에이전트를 조정한다. 발표자는 이를 전략을 맡는 고성능 변호사가 세부 업무를 보조 인력에게 나누는 모습에 비유한다.

Cursor에서는 모델이 좋아지며 프롬프트와 안전장치를 제거했지만, Grokbot에서는 새로운 영역의 과업 때문에 새 프롬프트와 안전장치를 다시 추가했다고 한다. 모델이 아직 이런 새 업무를 충분히 익히지 못했다는 것이 발표자의 설명이다.

5. 버그 처리의 연속 업무 사례

발표자가 소개한 회사 내부 사례는 다음 순서로 이어진다.

  1. 특정 채널에 버그가 보고된다.
  2. 자동화가 버그를 즉시 분류한다.
  3. Claude 에이전트가 수정을 시도한다.
  4. 도구를 사용해 수정 전후 영상을 만들어 결과를 증명한다.
  5. 수정 사항이 병합되고 배포가 시작된다.
  6. 다른 에이전트가 운영 환경에서 문제가 생기는지 감시한다.

제공 전사의 한국어 설명에는 이 사례 직후 “이런 흐름을 막으려면 AI가 멈추지 않고 일할 수 있어야” 한다고 적혀 있다. “흐름을 막는다”는 표현은 앞뒤의 연속 업무 설명과 충돌하므로 의도를 임의로 고쳐 확정하지 않는다.

6. 모델 학습만으로 없어지지 않는 세 역할

실행 환경과 런타임

발표자는 일반적인 에이전트 작업 시간이 분에서 시간, 일, 그 이상으로 길어졌다고 말한다. 잠자기 상태로 들어갈 수 있는 개인 노트북에서는 장시간 자율 업무를 안정적으로 운영하기 어렵고, 클라우드 실행이 필요하다는 주장이다.

신뢰와 보안

명령 실행 도구와 모든 API 키를 담은 파일만으로 코딩 과제를 해결할 수 있더라도, 실제 조직에서는 모델에 모든 키를 주는 것이 문제가 될 수 있다. 발표자는 특정 에이전트와 사람별로 권한 범위를 좁히고 큰 피해를 막는 안전장치를 두어야 한다고 말한다.

1만 달러 API 요금은 실제 사고 보도가 아니라 큰 위험을 설명하기 위한 예시다.

효율성

발표자가 언급한 두 연구에서는 하네스에 따른 평가 점수 차이가 크지 않았지만 작업당 비용에는 유의미한 차이가 있었다고 한다. 같은 설명의 반복 전송이나 작업에 맞지 않는 모델 선택이 시간과 비용에 영향을 줄 수 있다는 설명이다.

7. 노트북 밖에서 실행되는 AI에 대한 전망

발표자는 6개월 안에 에이전트 작업의 90%가 노트북 밖에서 실행될 것이라고 예측했다. 이 수치는 현재 사용률을 측정한 값이 아니라 발표자의 전망이다. 제공 전사만으로는 전망이 시작되는 정확한 기준 날짜와 이후 실현 여부를 확인할 수 없다.

요즘에는 화려한 하네스가 더 이상 코딩 지능을 높여 주지 않는다는 말이 맞다고 생각합니다.

말한 사람은 커서의 AI 작업 도구를 만들던 제다이아 카츠예요. 그런데 발표 뒤로 가면 이 도구가 여전히 중요한 까닭도 나와요.

오늘은 하네스가 뭔지, 어떤 도움은 줄어들고 어떤 일은 남는지 알아볼게요. AI에게 일을 맡길 때 뭘 살펴봐야 하는지도 함께 정리해볼게요.

하네스는 모델의 눈과 손과 같습니다. 하네스는 모델을 감싸고, 모델을 이끌며, 모델을 세상과 연결합니다. 사용자는 앱을 통해 우리의 하네스에 연결됩니다.

그리고 하네스는 모델을 컴퓨터와 연결하고, MCP와 같은 서드파티 서비스에도 연결합니다.

모델을 생각하는 머리라고 해볼게요. 생각만 해서는 파일을 고치거나 프로그램을 켤 수 없죠. 어떤 도구를 쓸지, 어디까지 허용할지, 하던 일은 어디에 남길지 정해줘야 해요. 이렇게 AI가 실제로 일하도록 둘러싼 장치들을 하네스라고 불러요. 한때는 여기에 코딩 요령도 많이 넣었어요.

나와 동료 스테판(Stefan)도 모델의 지능이 부족한 부분을 메우기 위해 커서(Cursor)에 마련해 두었던 이런 가드레일(guardrail)을 모두 제거한 과정을 글로 썼습니다.

예전에는 프런티어 모델(frontier model)이 파일에 코드 수정 사항을 적용하는 작업을 잘하지 못했기 때문에, 코드 수정만 담당하는 소형 모델(small model) 같은 것도 사용했습니다. 또한 코드베이스를 탐색하는 방법과 작업 결과를 확인하는 방법처럼 코딩에 특화된 온갖 지침도 마련해 두었습니다.

발표자는 두 연구도 근거로 들어요. 여기서는 같은 AI에 서로 다른 작업 도구를 붙여도 시험 점수가 크게 달라지지 않았다고 설명해요. 이 주장은 강연에 나온 코딩 머신러닝 시험의 맥락에서 봐야 해요.

그럼 AI는 어떻게 도구의 도움을 덜 받고도 일을 잘하게 됐을까요?

결국 하네스는 제가 ‘데이터 플라이휠(data flywheel)’이라고 부르는 과정을 통해 스스로를 쓸모없게 만들고 있습니다.

이 과정에서 하네스는 점점 더 어려운 코딩 작업을 수행 가능한 범위 안으로 가져옵니다. 그러면 더 많은 사용자가 에이전트를 활용해 그런 작업을 생산적으로 시도할 수 있습니다. 이는 더 많은 코딩 데이터가 연구소들과 공유된다는 뜻이며, 결국 모델은 이러한 기술을 능숙하게 수행하는 방법을 본래적으로 학습하게 됩니다.

결국 모델이 너무 뛰어나져서, 하네스는 애초에 그런 작업을 가능하게 만들기 위해 필요했던 기능들을 실제로 삭제할 수 있게 됩니다.

처음에는 자전거의 보조 바퀴를 달아주는 것과 비슷해요. 발표자가 그린 흐름에서는 도구가 어려운 일을 해볼 수 있게 돕고, 그 경험이 학습 자료가 돼요. AI가 익숙해지면 보조 코드를 덜 써도 되죠.

그런데 새 일을 맡기면 어떨까요? 이제 AI는 코딩 창 밖으로 나가요.

Grokbot에는 일회성 채팅(one-off chats)이 아니라, 여러 작업 에이전트(worker agents)로 구성된 무리를 지휘하는 장기 실행 코디네이터 봇(long-lived coordinator bots)을 기반으로 작동하는 새로운 형태의 하네스(harness)가 생겼습니다.

여러분을 직접 상대하고 전략을 총괄하지만, 업무는 법률 보조원(paralegals) 팀에 맡기는 유능한 변호사를 고용하는 것과 비슷하다고 생각하면 됩니다. 그런 방식입니다.

사용자는 총괄 AI에게 일을 맡겨요. 총괄 AI는 작은 일들을 다른 AI에게 나눠줘요. 자료를 찾고, 내용을 모으고, 결과를 확인하는 식이죠. 이 그림은 역할을 쉽게 이해하기 위한 예예요. 그런데 개발팀은 여기서 예전에 지웠던 장치를 다시 넣게 됐어요.

Grokbot 하네스(harness)와 관련해 흥미로운 점이 있습니다. Cursor에서는 모델이 더 똑똑해지면서 하네스에서 여러 요소를 제거하게 됐다고 말씀드렸습니다. 프롬프팅(prompting)을 없애고, 가드레일(guardrail)을 없앴습니다. 그런데 신기하게도 Grokbot에서는 실제로 이런 요소를 상당 부분 다시 추가하게 됐습니다. 새로운 프롬프팅을 추가하고, 새로운 가드레일을 추가하고 있습니다. Grokbot이 해결하도록 만들어진 새로운 작업 방식과 새로운 영역에는 새로운 과제가 많이 있기 때문입니다.

모델들은 아직 그것을 완전히 해내지 못했습니다.

메일을 언제 보내도 되는지, 일이 길어지면 언제 알려야 하는지, 이런 문제는 코드를 잘 짜는 것만으로 풀리지 않아요. 새 일에서 막히는 곳을 도구가 먼저 도와주는 거죠. 이 변화는 여러 AI가 소프트웨어 작업을 이어받는 흐름에서도 보여요. 발표자가 소개한 회사 내부 사례를 볼게요.

이것이 어떻게 나타날 수 있는지 예를 들면, 내부적으로 누군가 채널에 버그를 제보하면 자동화 시스템이 즉시 그 버그를 자동 분류(auto-triage)합니다. 그런 다음 Claude 에이전트를 실행해 버그를 수정하도록 할 수 있고, 해당 에이전트는 우리 도구를 사용해 수정 전후 영상을 보여 주며 문제가 해결됐다는 것을 입증합니다.

그 수정 사항이 배포되거나 병합되어 배포를 시작하면, 저희에게는 롤아웃(rollouts) 제품이 있어 또 다른 에이전트를 실행하고 프로덕션 환경에서 문제가 발생하는지 모니터링합니다.

Bug을 찾고 고치고 확인하고 배포 뒤에 지켜보는 일까지 이어져요. 이런 흐름을 막으려면 AI가 멈추지 않고 일할 수 있어야겠죠. 여기서 제다이아는 모델이 배우는 것만으로 없어지지 않는 역할을 짚어요. 먼저 작업을 계속 돌리는 환경이에요.

무엇보다도 자율형 동료(autonomous colleague)를 신뢰성 있게 작동시키려면 인프라와 런타임(runtime)이 필요합니다. 지난 1년여 동안 에이전트가 일반적인 작업을 몇 분에서 몇 시간 동안 수행하던 수준에서, 며칠 또는 그보다 더 오래 작업할 수 있는 수준으로 발전했습니다.

한 사람의 노트북에서는 이 작업을 수행할 방법이 없습니다. 노트북은 절전 모드로 전환될 수도 있기 때문입니다. 정말 자율형 동료를 원한다면 클라우드에서 실행되어야 합니다.

노트북을 덮어도 일은 이어지고, 다시 접속하면 하던 작업을 찾을 수 있어야 해요. 발표자는 이런 실행 환경을 강조해요. 다음은 권한이에요. AI가 메일을 쓸 줄 알아도 누구에게 언제 보내도 되는지는 따로 정해야겠죠.

그리고 다음은 신뢰와 보안입니다. 앞서 살펴본 것처럼, Bash만 사용하고 모든 API 키를 파일에 넣은 단순한 하네스(harness)로도 코딩 작업을 해결할 수 있습니다. 하지만 모든 API 키를 파일에 넣어 모델에 제공하고 싶지는 않을 겁니다. 설령 괜찮다고 해도, 보안 책임자가 분명 할 말이 있을 테고요.

이건 분명 정말 중요한 문제입니다. 기업은 특정 에이전트와 특정 사람에게만 권한을 부여하도록 권한 범위를 제한해야 합니다. 하지만 어느 날 아침에 정말 재앙적인 작업이 실행되었거나 1만 달러짜리 API 요금 청구서를 마주하고 싶지 않은 사람들을 위해 안전장치(guardrails)를 마련하는 것도 중요합니다. 그렇죠?

여기서 1만 달러는 위험을 설명하려고 든 예시예요. 실제로 이런 사고가 났다는 보도는 아니에요.

AI가 일을 잘 끝냈는지와 필요한 권한만 썼는지는 함께 살펴봐야 해요. 그리고 같은 일을 해도 비용이 얼마나 드는지 따져봐야겠죠.

그리고 마지막으로 효율성이 있습니다. 앞서 보여드린 두 연구를 떠올려 보면, 하네스(harness)의 선택이 평가 점수(eval scores)에 유의미한 차이를 만들지 않았지만, 두 연구 모두 작업당 비용에서는 유의미한 차이가 있다는 사실을 실제로 발견했습니다.

시험 점수가 비슷해도 실제로 쓰는 경험은 달라질 수 있어요. 같은 설명을 되풀이해서 보내는지, 작업에 맞는 모델을 고르는지에 따라 시간과 비용이 달라지니까요.

그래서 AI 도구를 고를 때는 어려운 문제를 푸는 능력과 함께 오래 일하는지, 권한을 지키는지, 비용을 아끼는지도 보면 좋아요. 발표자는 이런 변화가 노트북 밖에서 일하는 AI로 이어질 거라고 예상해요.

저는 6개월 안에 에이전트 작업의 90%가 노트북에서 실행될 것이라고 예상합니다. 이미 상황은 그런 방향으로 가고 있으며, 우리가 원하는 방식으로 실제로 우리와 협력할 수 있는 진정한 자율 에이전트를 만들려면 이것이 반드시 필요하다고 생각합니다.

방금 수치는 현재 사용률이 아니라 발표자의 전망이에요. 처음 질문으로 돌아가 볼게요. AI가 똑똑해지면 도구도 필요 없어질까요?

익숙한 코딩을 도와주던 일부 장치는 줄어들어요. 그래도 오래 실행하고 권한을 정하고 비용을 줄이는 일은 남아요. 새 일을 맡길 때는 새 도구도 필요하고요. 다음에 AI 도구를 볼 때 이 역할들을 살펴보세요. 도움이 되셨다면 구독과 좋아요 부탁드려요. 시청해주셔서 감사합니다.
