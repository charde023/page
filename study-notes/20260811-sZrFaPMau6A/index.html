  • 유비쿼터스 언어(Ubiquitous Language) — 프로젝트 안에서 모두가 같은 뜻으로 쓰는 용어 체계. 도메인 주도 설계(DDD)에서 자주 쓰이는 개념.
  • Grill with Docs — 문서를 바탕으로 AI가 사용자를 질문하며 요구사항·용어·맥락을 정리하는 흐름.
  • agents.md / CLAUDE.md — AI 에이전트에게 프로젝트 규칙, 작업 방식, 선호사항을 알려주는 설정 문서.
  • GitHub Secrets — API 키, 토큰 등 민감한 값을 GitHub 저장소나 워크플로에 안전하게 저장하는 기능.
  • Wayfinder 세션 — 방향성이나 요구사항을 찾기 위한 AI 질문·탐색 세션으로 보임.

  3. 공식 문서 주소는 aihero.dev/skills — 메인 페이지에서 스킬 흐름과 전체 레퍼런스를 볼 수 있다.

  12. Wizard는 결정론적 스크립트(Deterministic Script) — API 키 입력 등이 AI 모델 서버로 전송되지 않는다는 점을 강조했다.

1. v1.2.0 업데이트 개요

Matt Pocock은 이번 영상을 통해 자신의 AI 코딩 스킬 모음이 v1.2.0으로 업데이트됐다고 소개한다. 이 스킬 저장소는 이미 GitHub에서 매우 인기 있는 프로젝트이며, 화자에 따르면 약 204K star를 받아 전체 저장소 중 24위권에 올랐다.

이 정도로 커진 프로젝트라면 단순한 예제 모음이 아니라, 제대로 된 문서와 설치 흐름, 여러 AI 도구에서의 호환성이 필요하다. 이번 업데이트의 핵심은 바로 그 성숙도다.

즉, 이번 변화는 “스킬 몇 개 추가”가 아니라 다음 네 가지 방향의 개선이다.

  • 공식 문서화
  • Claude Code 설치 간소화
  • Codex 계열 도구 호환
  • 실전 작업을 돕는 신규·개선 스킬 추가

2. 새 공식 문서 사이트

공식 문서 사이트는 aihero.dev/skills에 마련됐다. 이 사이트에서는 Matt Pocock의 스킬들을 단순 목록이 아니라 작업 흐름별로 볼 수 있다.

대표적인 AI 코딩 흐름은 다음과 같다.

  1. Grill with Docs — 문서를 바탕으로 요구사항과 맥락을 캐묻기
  2. Spec — 명세 작성
  3. Tickets — 작업 티켓으로 분해
  4. Implement — 구현
  5. Code Review — 코드 리뷰

왼쪽 패널에는 모든 스킬의 레퍼런스가 있고, 각 스킬이 무엇을 하는지 확인할 수 있다. 화자는 과거에 문서 작성이 풀타임 업무였기 때문에 이번 문서화 작업을 즐겁게 했다고 말한다.

또 하나 중요한 점은, 문서가 단순 사용법을 넘어서 AI 코딩 사전(AI Coding Dictionary)과 연결된다는 것이다. 예를 들어 “티켓(ticket)”이라는 단어가 나오면, 화자가 생각하는 티켓의 정의로 연결된다.

비개발자 입장에서는 이 부분이 특히 중요하다. AI 코딩은 도구 사용법만 아는 것이 아니라, 명세, 티켓, 리뷰, 컨텍스트, 에이전트 설정 같은 개념을 이해해야 제대로 활용할 수 있기 때문이다.

3. Claude Code 공식 플러그인 마켓플레이스 연동

두 번째 큰 변화는 Matt Pocock의 스킬이 Claude Code 공식 플러그인 마켓플레이스(Official Plugin Marketplace)에 등록됐다는 점이다.

이제 Claude Code 사용자라면 다음처럼 설치할 수 있다.

  1. Claude Code를 연다.
  2. 플러그인(plugin) 기능을 실행한다.
  3. “Matt Pocock” 또는 “Matt Pocock Skills”를 검색한다.
  4. 바로 설치한다.

이 방식으로 설치하면 사용자는 읽기 전용 번들(Read-only Bundle)을 받는다. 별도로 파일을 복사하거나 설정을 맞추는 과정이 줄어들고, Matt Pocock이 스킬을 업데이트하면 자동으로 내려받을 수 있다.

초보자나 비개발자에게는 이 변화가 크다. GitHub 저장소를 직접 복제하거나 설정 파일을 옮기는 일은 부담스러울 수 있는데, 마켓플레이스 설치는 앱 설치에 가까운 경험을 제공한다.

4. Codex 호환성 개선

Claude Code 사용자에게는 마켓플레이스가 큰 장점이지만, OpenAI 계열 도구나 Codex UI를 쓰는 사람도 있다. 이번 v1.2.0에서는 이를 위해 모든 스킬에 openai.yaml 파일을 포함했다.

이 파일의 의미는 단순한 호환성 추가가 아니다. 핵심은 사용자 호출 스킬(User-invoked Skill)의 동작을 Codex에서도 유지하는 것이다.

기존에는 스킬이 크게 두 가지로 나뉘었다.

  • 모델 호출 스킬(Model-invoked Skill): AI가 필요하다고 판단하면 자동으로 호출
  • 사용자 호출 스킬(User-invoked Skill): 사용자가 명시적으로 부를 때만 사용

사용자 호출 스킬의 장점은 평소에는 AI의 컨텍스트 윈도우(Context Window)에 들어가지 않는다는 것이다. 즉, AI가 항상 모든 지침을 읽고 혼란스러워하지 않으며, 필요한 순간에만 해당 스킬이 추가된다.

Claude Code나 일부 하네스(harness)에서는 이 방식이 잘 작동했지만, Codex에서는 제대로 작동하지 않았다고 한다. 그래서 이번부터는 각 스킬에 보조 설정 파일을 함께 제공해 allow implicit invocation false 설정이 Codex에도 전달되도록 했다.

쉽게 말하면, Codex에서도 AI가 마음대로 스킬을 꺼내 쓰지 못하고, 사용자가 부를 때만 쓰게 만든 것이다.

5. Wait What?: 장황한 AI 답변을 다시 설명시키는 스킬

화자는 최근 Opus, 특히 Opus 5의 답변이 지나치게 장황하고 읽기 어렵다고 말한다. 표현이 불필요하게 복잡하고, LLM 특유의 이상한 문구가 많아 “무슨 말인지 모르겠다”는 느낌을 받는다는 것이다.

이를 해결하기 위해 만든 신규 스킬이 Wait What?이다.

이 스킬은 사용자가 AI 답변을 보고 이해가 안 될 때, 말 그대로 “잠깐, 방금 무슨 말이야?”라고 다시 묻는 역할을 한다. 그러면 AI는 더 명확한 답변을 생성해야 한다.

Wait What?의 핵심 규칙은 두 가지다.

  1. ASD STE 100 Simplified Technical English 기준을 사용한다.
  2. 짧고 명확한 문장
  3. 선언적인 표현
  4. 어려운 말보다 단순한 말
  5. context.md의 유비쿼터스 언어(Ubiquitous Language)에 맞춘다.
  6. 프로젝트 안에서 이미 합의한 단어를 사용
  7. 사용자가 만든 용어와 맥락에 맞게 설명

화자가 강조한 핵심은 “단순한 언어를 써라”만으로는 부족하다는 점이다. 진짜 해결책은 내 프로젝트에서 쓰는 말, 내 팀이 이해하는 말로 바꾸는 것이다.

비개발자 입장에서 이 스킬은 매우 유용하다. AI가 복잡한 개발 용어로 답할 때, “더 쉽게 설명해줘”보다 Wait What? 같은 구조화된 재설명 스킬을 쓰면 답변 품질이 더 안정적일 수 있다.

6. Grill Me: 질문을 그래프와 라운드로 진행

이번 업데이트에서 큰 변화 중 하나는 인기 스킬인 Grill Me의 개선이다.

기존 Grill Me는 질문을 하나씩 했다. AI가 한 가지 질문을 하고, 사용자가 답하고, 다시 다음 질문을 하는 식이다. 이 방식은 의존성이 있는 질문에는 안전하다. 앞 질문의 답을 알아야 뒤 질문을 할 수 있기 때문이다.

하지만 문제가 있었다. 세션 후반부에 어려운 질문이 거의 끝나면, 쉬운 질문이 한 개씩 계속 나와 속도가 매우 느려진다. 사용자는 계속 “네, 좋아요”, “그것도 좋아요” 같은 답을 반복해야 한다.

그래서 새 Grill Me는 질문을 여러 개씩 묶어서 한다. 다만 무작정 묶는 것이 아니라, 질문들 사이의 의존 관계를 그래프(Graph)로 보고 진행한다.

예를 들어 다음과 같다.

  • 가장 먼저 답해야 하는 핵심 질문이 있다.
  • 그 질문에 답하면 여러 후속 질문이 열린다.
  • 후속 질문의 답에 따라 또 다른 질문이 열린다.

새 Grill Me는 현재 답할 수 있는 질문만 모아 라운드(Round) 단위로 묻는다. 1라운드에서는 핵심 질문 1개만 나올 수도 있고, 2라운드에서는 열린 질문 여러 개가 나올 수 있다.

화자는 이 방식을 “질문의 최전선(frontier)을 빠르게 밀고 나가는 것”이라고 설명한다. 즉, 질문의 순서를 지키면서도 불필요하게 한 턴에 하나씩 묻는 느린 흐름을 줄인 것이다.

사용자는 받아쓰기(dictation)를 활용해 다음처럼 빠르게 답할 수 있다.

  • Q1 동의
  • Q2 동의
  • Q3은 변경 필요
  • Q4도 수정 필요

업무적으로 보면, 이 방식은 요구사항 인터뷰를 빠르게 진행하는 데 유용하다. 쇼핑몰, 물류, CS 자동화 같은 프로젝트를 AI와 설계할 때도 질문 라운드를 통해 빠르게 정리할 수 있다.

7. Writing for Agents: AI가 잘 읽는 문서 만들기

화자는 기존에 “좋은 스킬 작성”을 위한 스킬을 가지고 있었지만, 실제로는 스킬뿐 아니라 다른 문서에도 자주 쓰고 있었다고 말한다.

그래서 이를 확장해 Writing for Agents라는 스킬로 정리했다.

이 스킬의 용도는 다음과 같다.

  • agents.md 작성 또는 수정
  • CLAUDE.md 작성 또는 수정
  • AI가 읽는 설정 문서 개선
  • 스킬 문서 작성
  • 너무 앞부분에 모든 지침을 몰아넣는 문제(front loading) 완화

여기서 중요한 관점은 “사람이 읽기 좋은 문서”와 “AI 에이전트가 읽고 잘 수행하는 문서”가 다를 수 있다는 점이다. AI에게 읽힐 문서는 짧고 명확해야 하며, 조건과 예외가 예측 가능해야 한다.

또한 이 스킬은 모델 호출 가능(Model-invokable)하게 되어 있어, AI가 agents.md를 수정하는 상황이면 스스로 이 스킬을 불러올 수 있도록 설계됐다.

8. Wizard: 인프라 설정을 안내하는 대화형 스크립트

신규 스킬 중 하나인 Wizard는 화자가 한동안 숨겨두고 사용하던 스킬이라고 한다. 목적은 사람이 직접 해야 하는 인프라 설정을 쉽게 만드는 것이다.

예를 들어 AWS에서 어떤 리소스를 만들거나, 원격 서버를 설정하거나, API 키를 붙여 넣고, GitHub Secrets에 저장해야 하는 작업이 있다. 이런 작업을 AI에게 완전히 맡기면 위험할 수 있다. 계정 권한, 결제, 보안 정보가 얽히기 때문이다.

Wizard는 AI가 직접 모든 것을 실행하는 대신, 대화형 배시 마법사(Interactive Bash Wizard)를 생성한다. 이 스크립트는 사람에게 단계별로 안내한다.

예시는 다음 흐름이다.

  1. 스크립트를 실행한다.
  2. “시작할 준비가 되었나요?”라고 묻는다.
  3. 필요한 웹페이지를 자동으로 연다.
  4. 사용자가 로그인한다.
  5. 사용자가 필요한 값을 변경한다.
  6. API 키를 붙여 넣는다.
  7. 필요한 파일이나 GitHub Secrets에 저장한다.
  8. 다음 단계로 넘어간다.

화자는 이 과정이 결정론적 스크립트(Deterministic Script)라는 점을 강조한다. 즉, 사용자가 입력한 API 키가 Anthropic 같은 AI 서버로 전송되는 것이 아니라, 스크립트가 정해진 방식으로 로컬에서 처리한다는 의미다.

이커머스나 물류 사업자 관점에서도 중요하다. 예를 들어 쇼핑몰 API 키, 배송사 API 키, 결제사 키, AWS 설정값은 민감하다. Wizard 방식은 AI의 도움을 받되, 민감한 실행 권한은 사람이 유지하는 균형점이 될 수 있다.

9. To Questionnaire: AI 질문을 사람과 공유 가능한 문서로 바꾸기

마지막으로 소개된 스킬은 To Questionnaire다. 이름은 지루하지만 실제 필요성이 컸다고 한다.

이 스킬은 AI와의 grilling session, 즉 질문·답변 세션에서 나온 결정 사항과 질문들을 뽑아내어, 다른 사람과 함께 검토할 수 있는 문서로 만든다.

화자의 예시는 집 뒤뜰에 정원 사무실을 만드는 프로젝트였다. AI는 화자에게 질문을 던지고 있었지만, 실제로 함께 결정해야 할 사람은 아내였다. 그 공간을 함께 사용할 사람이기 때문이다.

그래서 화자는 AI에게 질문 세션 내용을 Markdown 문서로 바꾸게 했다. 이후 Google Docs에 넣고, 아내와 함께 검토한 뒤, 답변을 다시 AI에게 가져왔다.

이 스킬은 현재 AI 협업의 불편함을 보완하는 임시 도구에 가깝다. 어떤 팀은 Slack 안에 AI 에이전트를 두고, 이해관계자들이 대화에 참여하고, 필요할 때 AI를 태그해 구현까지 이어가는 구조를 갖고 있다. 하지만 많은 사람은 아직 그런 AI 네이티브 환경에 있지 않다.

따라서 지금은 Google Docs나 일반 문서로 질문지를 만들어 공유하는 방식이 현실적으로 유용하다.

비즈니스 현장에서도 마찬가지다. AI와 혼자 정리한 내용을 직원, 외주 개발자, MD, 물류 담당자, CS 담당자와 공유하려면 문서 형태가 훨씬 편하다. To Questionnaire는 그 간극을 메워준다.

여러분, 스킬, 스킬, 또 스킬입니다. 더 많은 스킬을 준비했습니다.

이번 버전은 1.2.0입니다. 이미 매우 인기가 많은 제 엔지니어링 스킬들에 여러 개선을 추가했습니다. 이 스킬 저장소(repo)는 제가 알기로 GitHub에서 역대 별(star)을 가장 많이 받은 저장소 중 24위 정도이고, 현재 204K star까지 올라갔습니다.

이제 성숙한 프로젝트가 되었으니 제대로 된 문서가 필요했습니다. 그래서 만들었습니다. 주소는 aihero.dev/skills입니다. 저와 팀이 함께 정말 훌륭한 사이트를 만들었습니다.

이 사이트를 가장 잘 보는 방법은 메인 페이지인 /skills로 가서, 거기에 있는 그룹들을 살펴보는 것입니다. 예를 들어 주요 흐름을 보면 Grill with Docs로 시작해서 Spec, Tickets, Implement, Code Review로 이어집니다. 왼쪽 패널에는 모든 스킬의 전체 레퍼런스와 각 스킬의 역할이 정리되어 있습니다.

예전에는 문서 작성이 제 실제 풀타임 일이었습니다. 그래서 다시 문서를 쓰게 되어 꽤 즐거웠습니다. 자주 묻는 질문 목록도 있는데, 이 질문들은 사람들이 제게 물어본 내용을 제가 개인 위키에 모아둔 것에서 가져온 것입니다.

이 스킬 문서들은 제가 함께 만들고 있는 AI 코딩 사전(AI coding dictionary)과도 연결되어 있습니다. 예를 들어 작은 “ticket” 링크를 누르면, 제가 생각하는 티켓(ticket)의 사전적 정의로 이동합니다. 그러므로 이 문서는 제 스킬을 더 잘 배우는 데 쓸 수 있을 뿐 아니라, AI 코딩 자체를 배우고 작동 방식을 깊게 이해하는 데도 사용할 수 있습니다.

두 번째 큰 변화는 이제 이 스킬들이 Claude Code 공식 플러그인 마켓플레이스(official plugin marketplace)의 공식 일부가 되었다는 점입니다. 즉, Claude Code를 열고 플러그인(plugin)을 실행한 다음, “Matt Pocock” 또는 “Matt Pocock Skills”를 검색해서 바로 설치할 수 있습니다.

이렇게 하면 읽기 전용 번들(read-only bundle)을 받게 됩니다. 추가 단계가 없고, 제가 스킬을 업데이트하면 그 변경 사항이 자동으로 내려옵니다.

Claude Code 사용자라면 꽤 좋은 소식입니다. 그런데 Codex 사용자라면 어떨까요? 이번 릴리스에서 Codex 사용자를 위한 변화는 무엇일까요?

이제 저는 모든 스킬에 openai.yaml 파일을 포함합니다. 그래서 Codex UI 같은 인터페이스에서도 기본적으로 제대로 작동해야 합니다. 또한 allow implicit invocation false 설정도 Codex 쪽으로 전달됩니다.

이전에는 모델 호출 스킬(model-invoked skills)과 사용자 호출 스킬(user-invoked skills)이 있었습니다. 사용자 호출 스킬의 장점은, 메인 skill.md 파일 안에서 볼 수 있듯이, 사용자가 호출하기 전까지 에이전트의 컨텍스트 윈도우(context window)에 숨겨져 있다는 것입니다. 이 방식은 Claude Code에서 작동하고, [?Pi]나 다른 몇몇 하네스(harness)에서도 작동합니다. 하지만 Codex에서는 작동하지 않았습니다. 제가 그걸 정확히 몰랐습니다.

그래서 이제 모든 스킬과 함께 보조 파일(sidecar file)을 배포합니다. 이를 통해 allow implicit invocation false가 적용됩니다. 그래서 Codex에서도 기본적으로 작동합니다.

다음으로 만들고 싶었던 스킬은, 현재 Opus, 특히 Opus 5가 이상한 말을 많이 한다는 문제를 해결하기 위한 것입니다. 왜 그런지 잘 모르겠습니다. 새 모델이라서 그럴 수도 있지만, 어떤 이유에서인지 제가 Opus와 대화할 때마다 답변이 제 머리 위로 지나가는 느낌입니다. 지나치게 장황하고, 이상한 LLM식 표현을 쓰며, 읽기가 정말 어렵습니다. 많은 사람도 비슷하게 느낍니다.

예를 들면 이런 식입니다. “솔직한 선택지는 AC를 받아들이고 다시 문구화하거나, export와 함께 digest를 유지해서 재개된 변경 없는 publisher가 picking 대신 flagging으로의 read를 건너뛰게 하는 것입니다.” 이게 무슨 뜻일까요? 그래도 실제로 중요한(load-bearing) 말이긴 하니, 그래서 중요하다는 걸 알 수 있습니다.

저는 이를 고치기 위해 여러 방법을 시도했습니다. 출력 스타일(output styles)을 바꾸거나 agents.md에 내용을 추가하는 방식도 해봤습니다. 하지만 제가 필요했던 것은 결국 “잠깐, 방금 뭐라고 했어?”라고 말하는 스킬이었습니다. 그래서 그 스킬 이름은 Wait What?입니다.

이 스킬은 매우 단순합니다. 두 가지를 합니다. 첫째, ASD STE 100 Simplified Technical English라는 특정 표준을 사용하라고 지시합니다. 이는 에이전트에게 매우 단순한 언어를 쓰고, 명확한 선언문으로 말하라는 강력한 단서입니다. 둘째, context.md 안의 유비쿼터스 언어(ubiquitous language)에 기반을 두라고 지시합니다.

장황함에 대한 진짜 치료법은 단순히 “쉬운 말을 써라”라고 하는 것이 아닙니다. 물론 그것도 조금 하긴 합니다. 진짜는 당신의 언어, 즉 Grill with Docs 과정에서 당신이 만들어낸 용어를 사용하게 하는 것입니다. 에이전트가 알 수 없는 이상한 말을 만들었고 무슨 뜻인지 모르겠을 때 이 스킬을 사용합니다. “Wait, what?”이라고 말하면 훨씬 나은 대안 답변을 해야 합니다.

다음 변화는 꽤 큽니다. 제 가장 인기 있는 스킬인 Grill Me의 업데이트입니다. 이전의 Grill Me는 한 번에 질문 하나씩 사용자를 몰아붙였습니다. 즉, 질문을 받고 답하면, 다음 질문을 받고 답하는 방식이었습니다. 한 턴에 질문 하나였습니다.

하지만 이 방식에는 끔찍한 실패 모드가 있습니다. 질문 세션 끝부분에 가면 어려운 내용은 대부분 끝나 있고, 쉬운 질문만 남습니다. 그런데 그것도 한 턴에 하나씩 나오니 사용자는 사실상 “네, 좋아요”, “네, 그것도 좋아요”만 반복하게 됩니다. 매우 답답하고 정말 느리게 느껴집니다. 그래서 한동안 이 과정을 빠르게 만들 방법을 찾고 싶었습니다.

제게 가장 말이 되는 방법은 한 턴에 여러 질문을 하는 것입니다. 쉬운 질문이 많으면 “네, 네, 네, 네”라고 한 번에 답하면 됩니다. 하지만 세 번째 질문의 답이 첫 번째 질문의 답에 의존한다면 어떻게 될까요? 예전에는 문제가 없었습니다. 하나씩 답했기 때문에, 앞 질문에 의존하는 질문은 이미 앞 질문의 답을 받은 뒤에 나왔기 때문입니다.

새 방식에서는 더 혼란스러울 수도 있습니다. 잘못된 질문에 답하거나, 순서가 틀린 질문에 답하거나, 다른 질문보다 먼저 답해야 하는 질문이 뒤에 나올 수도 있기 때문입니다. 그러면 어떻게 작동할까요?

생각해보면 이 질문들은 사실 그래프(graph)와 같습니다. 맨 처음에 반드시 답해야 하는 핵심 질문 하나가 있고, 그 질문이 답변되면 많은 다른 질문이 열릴 수 있습니다. 그리고 그 질문들이 또 다른 질문으로 이어질 수 있습니다. 이제 Grill Me는 이 그래프를 따라가도록 설계되었습니다. 지금 답할 수 있는 질문만 답하게 하되, 그것들을 라운드(round) 단위로 묻습니다.

그래서 첫 번째 라운드의 질문을 받습니다. 이 라운드에는 핵심 질문 하나만 있을 수도 있습니다. 그다음에는 그 답변으로 열린 다음 질문 라운드로 갑니다. 항상 질문의 최전선(frontier)을 가능한 빠르게 밀고 나갑니다.

실제로는 이런 모습입니다. 여기를 보면 라운드 1이 있고 Q1이 있습니다. 그리고 작은 추천 답변도 보입니다. 시각적으로 보기 쉽게 작은 색상 표시를 사용했습니다. 저는 이걸 좋아합니다. 눈으로 탐색하기 매우 쉽습니다. “좋아, 이게 Q1이고, 추천 답변은 이것이구나. Q2도 있고 추천 답변은 이것이구나” 하고 바로 볼 수 있습니다.

저는 받아쓰기(dictation)를 사용하기 때문에 이렇게 빠르게 말할 수 있습니다. “Q1 동의합니다. Q2 동의합니다. Q3은 변경이 필요합니다. Q4도 변경이 필요합니다.” 아래로 내려가면 라운드 2가 나오고 같은 구조가 반복됩니다. 첫 번째 라운드 질문에 답한 뒤, 또 다른 질문 라운드를 받고, 계속 최전선을 뒤로 밀어갑니다.

다음 큰 변화는 제가 기존의 “좋은 스킬 작성” 스킬을 수정했다는 것입니다. 제가 그 스킬을 스킬 작성 외의 일에도 사용하고 있다는 걸 알게 되었기 때문입니다. 에이전트가 읽는 모든 문서에 사용하고 있었습니다. 에이전트를 더 잘 작동하게 만들고, 문서를 더 간결하게 만들고, 출력이 더 예측 가능하게 나오도록 하는 데 사용했습니다.

그래서 이제 Writing for Agents가 있습니다. 이것은 agents.md나 CLAUDE.md를 수정할 때, 또는 스킬을 만들거나 편집할 때 사용할 수 있습니다. 이 안에는 레퍼런스 파일에 추가적인 스킬 메커니즘도 붙어 있습니다. 따라서 스킬 작성에도 사용할 수 있고, 특히 agents.md의 내용을 스킬로 분리해서 끔찍한 앞부분 과부하(front loading)를 막는 데 사용할 수 있습니다.

전반적으로 저는 에이전트 설정을 작성해야 할 때 이 스킬을 정말 자주 사용합니다. 문서가 잘 읽히고, 에이전트가 잘 수행하기를 원할 때 Writing for Agents가 맞는 선택입니다. 이 스킬은 모델이 호출할 수도 있습니다(model-invokable). 설명도 매우 깔끔하게 되어 있습니다. 그래서 agents.md를 수정하는 상황에서는 자동으로 가져와야 합니다. 아주 좋습니다.

다음은 새 스킬입니다. 한동안 숨겨두고 있던 스킬입니다. 바로 Wizard 스킬입니다. 최근 저는 여러 인프라를 프로비저닝(provisioning)하고 AWS 관련 작업을 진행해야 했는데, 그 과정이 정말 싫었습니다. 그래서 “에이전트가 여기서 나를 도와줄 방법이 분명 있지 않을까?”라고 생각했습니다.

그래서 저는 사람이 직접 수행해야 하는 단계들을 안내하는 대화형 배시 마법사(interactive bash wizard)를 생성하는 Wizard 스킬을 만들었습니다. 다시 말해, 에이전트에게 “AWS에 들어가서 컴퓨터 사용(computer use) 같은 방식으로 전부 설정해줘”라고 시킬 수도 있었겠지만, 그건 꽤 찝찝했습니다. 저는 모든 제어권을 갖고 싶었지만, 동시에 가능한 쉽게 하고 싶었습니다.

실제 예시는 이렇습니다. 아마 원격 박스(remote box) 설정으로 마이그레이션하는 작업이었던 것 같습니다. 실행하면 “시작할 준비가 되었나요?”라고 묻고, 저는 “네”라고 답합니다. 그러면 제가 가야 할 정확한 페이지로 보내줍니다. 참고로 그 페이지는 스크립트가 열어준 것입니다. 저는 따로 할 필요가 없었습니다. 로그인하게 하고, 정확히 바꿔야 하는 항목으로 안내합니다. 그다음 API 키를 붙여 넣을 수 있습니다. 그리고 기억해야 할 점은, 이것이 결정론적 스크립트(deterministic script)라는 것입니다. 여기서는 아무것도 에이전트에 닿지 않습니다. Anthropic 같은 곳으로 전송되지 않습니다.

그래서 여기에 값을 붙여 넣으면, 필요한 파일에 저장합니다. 필요하다면 GitHub Secrets에도 저장합니다. 그리고 깔끔한 UI로 단계별 과정을 계속 안내해서 결국 필요한 상태에 도달합니다.

저는 이 방식이 서비스 프로비저닝을 엄청나게 고통스러운 일에서 이상할 정도로 즐거운 일로 바꾼다고 느꼈습니다. 이전에는 얼마나 오래 걸렸는지 알기 때문입니다. 그래서 Wizard는 제 스킬 세트의 필수 요소가 되었습니다. 몇 달 동안 진행 중 상태로 두고 있었는데, 이제 여러분께 보여줄 때가 되었다고 생각했습니다.

다음 스킬은 제가 만든 것 중 가장 지루한 이름일지도 모릅니다. 하지만 정말 필요했습니다. 그리고 제가 처음 사용한 용도보다 더 넓게 유용하겠다는 걸 깨달았습니다. 이름은 To Questionnaire입니다. 목적은 grilling session 안의 결정 사항을 꺼내서, 다른 사람과 함께 검토할 수 있는 문서로 만드는 것입니다.

저는 집 뒤뜰에 정원 사무실을 만들기 위해 Wayfinder 세션을 하고 있었습니다. 그런데 에이전트는 저에게 질문을 하고 있었지만, 사실 제가 그 문제를 상의해야 할 사람은 제 아내였습니다. 아내도 당연히 그 공간을 사용할 것이기 때문입니다. 그래서 우리는 함께 설계해야 했습니다.

그래서 저는 에이전트에게 grilling session에서 물어볼 내용을 Markdown 문서로 바꾸게 했습니다. 그다음 그것을 Google Docs에 넣고 아내에게 보냈습니다. 그리고 함께 검토했습니다. 이후 답변을 다시 에이전트로 가져왔습니다.

이 스킬은 언젠가 삭제하고 싶습니다. 지금 에이전트와 협업하기가 어렵다는 사실에 대한 일종의 패치이기 때문입니다. 제가 보기에 좋은 설정을 가진 일부 팀은 Slack 안에 에이전트를 두고, 그 대화에서 에이전트를 태그할 수 있습니다. 그러면 함께 협업하고, 질문에 함께 답하고, 특히 이해관계자들과 같이 논의할 수 있습니다. 이후 에이전트가 “좋습니다, 그 내용을 바탕으로 구현하겠습니다”라고 할 수 있습니다.

하지만 많은 사람은 아직 그런 환경에 있지 않습니다. 많은 사람은 AI 네이티브(AI native)가 아닙니다. Slack이나 Microsoft Teams조차 없을 수도 있습니다. 그래서 실제로는 문서를 하나 뽑아 다른 사람에게 주고, 그 사람이 Google Docs 같은 곳에 댓글을 달 수 있게 하는 방식이 매우 유용합니다.

여러분, 기본적으로 내용은 여기까지입니다. 새로운 스킬 묶음이 나왔습니다. 저는 특히 Wait What?에 대한 여러분의 반응이 기대됩니다. Opus가 이상한 행동을 할 때 실제로 몇 번은 여러분을 구해줄 것이라고 생각합니다.

여기서 언급하기에는 너무 작은 변경 사항도 몇 가지 있습니다. 전체 변경 로그를 보려면 GitHub 릴리스의 v1.2.0을 확인하면 됩니다. 새 스킬들을 즐겨보세요. 곧 다시 뵙겠습니다.
