컴포넌트를 넘어 MCP 앱용 생성형 UI를 설계하는 방법

원작자 Ruben Casas · Postman (Staff Engineer) · 업로드 2026-06-08 · 17.0분 · 원본 영상 ↗
한 줄 요약

AI 모델이 프런트엔드 코드를 직접 작성할 수 있는 시대에, 에이전트 UI의 진화 단계(정적→선언형→생성형)와 MCP 앱이 생성형 UI의 최적 전달 메커니즘인 이유를 실험과 함께 제시한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
정적 UI (Static Components) 현재 대부분 에이전트의 UI 방식 — 기준선을 알아야 다음 단계를 이해 에이전트가 미리 정의된 컴포넌트에 props/데이터만 전달
선언형 UI (Declarative UI) 오늘날 유연성·일관성의 최적 균형점으로 평가됨 JSON/YAML 디스크립터로 정적 컴포넌트를 동적 조합
생성형 컴포넌트 (Generative Components) 모델이 런타임에 HTML/CSS/JS를 직접 생성 — 다음 단계 LLM이 UI 코드를 on-demand로 작성 → 컴포넌트 불필요
MCP 앱의 샌드박스 역할 생성형 UI는 신뢰할 수 없는 코드이므로 격리 필수 double iframe + 인증 + 도구 호출이 기본 제공
AG-UI 프로토콜 에이전트 → 클라이언트 툴 등록 → React 컴포넌트 매핑 표준 tool call의 props를 정적 컴포넌트에 매핑하는 SDK
서버 드리븐 UI (Netflix 패턴) 선언형 UI의 역사적 선례 — 새 개념이 아님 서버가 JSON 디스크립터 → 클라이언트가 미리 정의된 컴포넌트 렌더
협업형 에이전트 인터페이스 UI의 미래 방향 — 출력 시각화를 넘어 공유 작업공간 사람과 에이전트가 동일 캔버스에서 함께 편집

내가 모를 만한 것 / 처음 보는 것

  • AG-UI 프로토콜: 에이전트가 클라이언트 툴을 등록하고 tool call의 props를 React 컴포넌트에 매핑하는 SDK/프로토콜. 현재 정적 UI 구현의 표준 중 하나.
  • Goose Auto Visualizer: MCP 클라이언트 Goose의 기능. 에이전트가 넘긴 임의 데이터를 자동으로 분석해 미리 정의된 컴포넌트 중 맞는 것으로 렌더.
  • JSON Render (Vercel): JSON/YAML 디스크립터로 UI를 동적으로 구성하는 Vercel의 도구. 최근 YAML 지원 추가. 선언형 UI의 대표 구현체.
  • Excalidraw MCP 앱: 다이어그램 시각화뿐 아니라 사람과 에이전트가 동일 캔버스에서 협업하는 공유 아티팩트 생성. 협업형 UI의 현재 최전선 예시.
  • FastMCP [?FastNCPS] Zoo: Python 디스크립터로 컴포넌트를 매핑하는 선언형 UI 접근법. 화자가 예시로 언급.
  • 역 샘플링 (reverse sampling): 생성형 컴포넌트에서 동일 모델이나 별도 모델을 tool call로 호출해 UI 코드를 생성하는 패턴. 화자가 제안한 아키텍처.
  • double iframe 샌드박스: MCP 앱이 기본 제공하는 격리 구조. 생성형 UI의 신뢰 경계 문제를 해결.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 2022년 11월 ChatGPT 출시 직후 방식 — "가난한 자의 바이브 코딩(poor man's vibe coding)": ChatGPT에서 코드 요청 → code block으로 답변 요청 → 복붙 → 반복.
  2. 2025년 말이 역사적 변곡점으로 지목: GPT 4.5 [?5.2] 와 Claude Opus 4.5 [?4.5] 두 모델 출시가 UI 생성 품질을 급격히 높임. 단일 프롬프트로 블로그를 재작성했더니 검색박스·블러 애니메이션·접근성(accessibility)까지 자동 생성됨.
  3. 선언형 UI가 "오늘날 유연성과 일관성의 완벽한 균형점"이라고 평가 — 이유: 디자인 시스템 유지, 예측 가능성, 속도, 토큰 비용 절감.
  4. Postman에서 직접 실험: 날씨 API + 조크(joke) 생성 + HTML/CSS/JS를 단일 tool call로 생성하는 날씨 에이전트. 컴포넌트 없이 완전히 생성된 UI를 시연.
  5. Anthropic이 visualizer 기능에 MCP 앱을 채택한 것은 전략적 의미가 크다 — 자체 아키텍처를 만들 수도 있었지만 MCP 앱의 샌드박스·인증·메시지 패싱을 그대로 활용. "Anthropic도 MCP 앱을 1st-party UI에 쓴다면, 우리가 못 쓸 이유가 없다."
  6. 라디오-TV 유추: 1930년대 TV 등장 초기에는 카메라를 든 라디오 쇼가 첫 TV 콘텐츠였음 — 새 매체로 뭘 할 수 있는지 상상력이 없었기 때문. 현재 에이전트 UI도 같은 단계("우리는 아직 라디오 시대").
  7. 생성형 UI의 핵심 문제: "신뢰할 수 없는 서드파티 코드를 신뢰하지 않듯, LLM이 생성한 코드도 그냥 사용자에게 전달해선 안 된다" — 배포 모델(distribution model), 경계(boundary), 샌드박스가 필수.
  8. Excalidraw MCP 앱에서 사람이 직접 캔버스를 클릭·수정하면서 에이전트와 앞뒤로 대화하는 방식 — 이것이 화자가 생각하는 미래 협업형 에이전트 인터페이스의 현재 최근접 예시.

1. 2022년 11월에서 2026년까지 — UI 생성의 급격한 진화

2022년 11월 ChatGPT 등장 직후, 개발자들이 하던 일은 "code block으로 응답해줘 → 복붙 → 오류 수정 → 반복"이었다. 화자는 이를 "가난한 자의 바이브 코딩(poor man's vibe coding)"이라고 부른다.

이후 2025년 말, GPT 4.5 [?5.2]와 Claude Opus 4.5가 출시되면서 긴 컨텍스트 작업(long horizon tasks)과 고품질 UI 생성 능력이 함께 도약했다. 화자는 "내 블로그를 재작성해줘" 한 마디에 검색박스·블러 애니메이션·접근성까지 갖춘 UI가 자동 생성된 경험을 공유했다. 3년 만에 "몇 줄 코드를 생성" → "나보다 더 나은 프런트엔드 코드를 쓰는 모델"로 바뀌었다.

2. 문제 제기 — 왜 아직도 텍스트 중심인가?

모델이 UI를 잘 만든다면, 왜 우리는 아직도 주로 정적 텍스트 UI에 머물러 있는가? "Jarvis 같은 떠다니는 UI 창"은 어디 있는가?

Andrej Karpathy의 표현 — "이 새 컴퓨터와 상호작용하는 것은 터미널에 말하는 것과 같다. GUI는 아직 발명되지 않았다." — 를 인용하며 현재 우리가 1970년대 터미널 시대와 같은 위치에 있다고 진단한다. 슈퍼인텔리전스는 있지만 성숙한 인터페이스 언어는 없다.

현재 두 가지 방향이 경쟁 중: - 채팅을 모든 곳에 (chat everywhere): SaaS 기업들이 홈페이지에 채팅창을 붙이는 추세. - 슈퍼 앱 (super app): ChatGPT·Claude·Gemini 같은 단일 허브에서 모든 UI를 중재.

화자는 둘 다 과도기적 형태이며, 더 중요한 질문은 "어디서 UI가 실행되는가"가 아니라 "모델이 무엇을 생성하는가"라고 본다.

3. 정적 UI (Static Components) — 현재 표준

에이전트 (오케스트레이터)
  → MCP tool call
  → props + data
  → 미리 정의된 정적 컴포넌트
  → 클라이언트 렌더

에이전트는 오케스트레이터 역할만 한다. LLM이 컴포넌트를 생성하지 않고, 미리 만들어진 컴포넌트에 데이터를 전달할 뿐이다. 지난 20년간의 서버→클라이언트 UI와 구조적으로 같다.

현재 구현체: - AG-UI 프로토콜: 클라이언트 툴 등록 → tool call의 props → React 컴포넌트 매핑 SDK. - Goose Auto Visualizer: 임의 데이터를 자동으로 분석해 미리 정의된 컴포넌트 중 맞는 것으로 렌더.

4. 선언형 UI (Declarative UI) — 현재 최적 균형점

에이전트
  → JSON/YAML/Python 디스크립터 생성
  → 번역·렌더링 엔진
  → 미리 정의된 정적 컴포넌트
  → 클라이언트 렌더

정적 컴포넌트는 그대로지만, 에이전트가 props 대신 구조화된 디스크립터를 생성한다. 더 동적이고 개인화가 가능하다.

역사적 선례: Netflix의 서버 드리븐 UI — 사용자별 맞춤 홈화면을 서버가 JSON으로 내려주고 클라이언트가 미리 정의된 Netflix 컴포넌트로 렌더링.

현재 구현체: - JSON Render (Vercel): JSON/YAML로 컴포넌트를 매핑. 최근 YAML 지원 추가. - FastMCP [?FastNCPS] Zoo: Python 디스크립터 방식.

LLM은 여전히 컴포넌트가 아니라 JSON을 생성한다. 화자는 이 방식이 "디자인 시스템 유지 + 예측 가능성 + 속도 + 토큰 비용 절감" 면에서 오늘날 최적 균형점이라고 본다.

5. 생성형 컴포넌트 (Generative Components) — 다음 단계

에이전트
  → tool call (역 샘플링 또는 별도 모델 호출)
  → HTML + CSS + JavaScript on-demand 생성
  → 클라이언트로 전달

컴포넌트가 없다. 번역 엔진도 없다. 모델이 UI 코드 자체를 런타임에 생성한다.

Postman 실험 (화자 직접 수행): - 날씨 API에서 데이터 조회 - 조크(joke) 생성 - HTML/CSS/JS를 단일 tool call로 생성 - 매번 독창적이고 시각적으로 풍부한 UI가 출력됨

핵심 문제: 신뢰할 수 없는 서드파티 코드를 그냥 쓰지 않듯, LLM이 생성한 UI 코드도 그냥 사용자에게 전달할 수 없다. 배포 모델(distribution model), 경계(boundary), 샌드박스가 반드시 필요하다.

6. MCP 앱 = 생성형 UI의 최적 전달 메커니즘

MCP 앱이 이 문제를 해결한다:

요구 MCP 앱의 해결 방식
샌드박스 double iframe으로 기본 격리
인증 MCP 프로토콜 기본 제공
도구 호출 tool calling 기본 지원
UI↔에이전트 메시지 패싱 프로토콜 레벨에서 지원
서드파티 UI 전달 표준 이미 업계 표준

Anthropic의 전략적 선택: Claude의 visualizer 기능을 자체 아키텍처로 만들 수도 있었지만 MCP 앱을 채택. "Anthropic이 1st-party UI에 MCP 앱을 쓴다면, 우리도 못 쓸 이유가 없다."

MCP 앱은 서드파티 UI뿐 아니라 1st-party UI 전달에도 유효하다.

7. 미래 전망 — 컴포넌트를 넘어 협업형 에이전트 인터페이스로

라디오-TV 유추: 1930년대 TV 등장 초기에는 카메라를 든 라디오 쇼가 첫 TV 콘텐츠였다. 새 매체로 뭘 할 수 있는지 상상하지 못했기 때문이다. 지금 에이전트 UI도 같은 상태 — "우리는 아직 라디오 시대에 있다."

화자가 제시하는 미래 방향: 컴포넌트 중심 생성형 UI를 넘어, 사람과 에이전트가 공유 공간에서 함께 작업하는 협업형 인터페이스

Excalidraw MCP 앱이 현재 최전선 예시: - 단순 다이어그램 출력이 아닌 공유 아티팩트(shared artefact) 생성 - 사람이 직접 캔버스를 클릭·수정하면서 에이전트와 대화 - "이것 바꿔줘" + 직접 드래그 수정이 같은 공간에서 동시에 가능

생성형 UI의 진화 방향: 개인화된 UI + 사람-에이전트 진정한 협업(true human-agent collaboration).

2022년 11월로 돌아가면, 우리가 하던 일은 ChatGPT에 들어가서 컴포넌트를 만들어달라고 요청하고, 복붙하고, "code block으로 답해줘"라고 해야 했고, 또 다시 고치고, 반복하고 — 이걸 저는 "가난한 자의 바이브 코딩(poor man's vibe coding)"이라고 부릅니다. 우리는 그 이후 많이 왔습니다. 어느 정도 작동했고, 매우 흥미로웠습니다. 모델이 UI를 어느 정도 만들어줄 수 있었으니까요. 분명 그게 오늘 이야기할 내용이기도 합니다. 하지만 그때는 "이 모델이 나보다 더 좋은 코드를 쓰진 못하겠지"라고 생각했습니다.

그리고 지난해, 특히 2025년 마지막 몇 달에 무슨 일이 일어났는지 아신다면 — 믿기 어려운 변곡점이었고, 모든 것이 한꺼번에 매우 빠르게 바뀌었습니다. 역사책에 기록될 일입니다. 이것은 부분적으로 두 가지 매우 중요한 모델 — GPT 4.5 [?5.2]와 Claude Opus 4.5 — 의 출시 때문이었습니다. 이 모델들은 대부분의 작업, 특히 긴 컨텍스트 작업에서 매우 뛰어났을 뿐 아니라, 고품질 UI 생성에도 매우 뛰어났습니다. 사려 깊고 때로는 정말 훌륭한 작동하는 UI를 빠르게 만들어냈습니다.

저는 이 모델들 중 하나를 써서 내 블로그를 재작성하도록 단일 프롬프트를 날려봤는데, 요청하지도 않았는데 블러 애니메이션이 있는 멋진 검색박스를 만들고 기본으로 접근성(accessibility)까지 갖췄습니다. 그때 깨달았습니다: ChatGPT 출시부터 지금까지 3년 동안, "몇 줄 코드 생성, 잘 돌아가네"에서 "이제 나보다 더 나은 프런트엔드 코드를 쓴다"로 왔구나. 자존심 없이 — 그냥 현실입니다.

그렇다면 질문이 생깁니다. 이 모델들이 UI 코드를 이렇게 잘 쓴다면, 왜 우리는 여전히 주로 정적 텍스트라는 옛 패러다임에 갇혀 있는 걸까요? 앞서 이야기한 "Jarvis 같은 순간"은 어디 있나요? 떠다니는 UI 창은 어디 있나요? 왜 아직 거기 못 갔을까요?

제 이름은 Ruben Casas입니다. 저는 Postman의 스태프 엔지니어이고, 지난 1년간 UI와 생성형 UI를 연구해왔으며 MCP 앱 작업도 해왔습니다. 오늘은 현재 우리가 하고 있는 것과 미래의 방향을 보여드리고 싶습니다.

소식은 이렇습니다 — 우리에게 새 컴퓨터가 생겼습니다. Andrej Karpathy가 말했듯, 이 새 컴퓨터와 상호작용하는 것은 터미널에 말하는 것과 같습니다. 이 운영체제에 직접 접근할 수 있습니다. GUI는 아직 발명되지 않았습니다. 마치 우리가 모든 것이 텍스트였던 1970년대에 있는 것 같습니다. 슈퍼인텔리전스는 있는데, 성숙한 인터페이스 언어가 없습니다. 그리고 오늘 우리는 이 새 컴퓨터의 인터페이스가 무엇인지 아직 알아가고 있습니다.

사람들은 묻습니다: 채팅인가요? 보여드리죠 — 최근 트윗에서 많은 SaaS 기업들이 홈페이지에 채팅을 추가하고, 모든 곳에 채팅을 넣고 있다는 불만이 있었습니다. 저는 채팅에 문제가 없습니다. 최종 UI는 아니지만, 지금으로서는 괜찮습니다. 하지만 채팅이 아니라면, 이 새 컴퓨터의 인터페이스는 무엇인가요?

다른 한편, MCP 앱에서 볼 수 있듯이 또 다른 생각이 있습니다: 하나의 앱 또는 슈퍼 앱이 모든 것을 지배한다는 것입니다. MCP 앱이 여기서 등장합니다 — 모든 홈페이지와 모든 앱에 채팅 창을 붙이는 대신, ChatGPT나 Claude나 Gemini 같은 슈퍼 앱 하나에서 오늘날 우리가 가진 대부분의 UI와 웹사이트와 상호작용한다는 것입니다. 이것도 좋습니다. mcpapps.com에서 이를 사용하는 방식입니다 — 하나의 에이전트 환경 안에서 서드파티 UI를 렌더링하는 데 쓸 수 있습니다.

이 두 옵션 모두 유효할 수 있습니다. 둘 다 새 컴퓨터의 인터페이스를 찾아가는 진화 과정의 일부라고 봅니다. 솔직히 어느 쪽이 최종 형태가 될지 모릅니다. 소비자가 알려줄 것입니다. 하지만 이것은 두 가지 다른 질문입니다: "UI가 어디서 실행되는가"(슈퍼 앱인가, 곳곳의 채팅인가). 더 흥미로운 질문은 "모델이 무엇을 생성하는가"입니다. 오늘 제가 이야기하고 싶은 것이 바로 이겁니다.

우리에게는 주로 정적, 선언형, 생성형 UI가 있습니다. 간략히 설명하겠습니다.

정적 컴포넌트 방식: 오늘날 대부분의 에이전트가 하는 방식입니다. 에이전트는 오케스트레이터일 뿐입니다. 에이전트가 MCP 앱이나 직접 에이전트 tool call을 통해 tool call을 합니다. 그러면 개발자가 미리 만든 정적 컴포넌트에 매개변수와 데이터가 전달됩니다. 지난 20년간 UI를 만들던 방식과 매우 유사합니다 — 서버에서 데이터를 보내고 클라이언트가 UI를 렌더링하는 것과 같습니다. 다만 이 경우 에이전트가 그 데이터와 props를 생성합니다.

오늘날 예시로는 AG-UI 프로토콜이 있습니다. React 컴포넌트에 매핑되는 클라이언트 툴을 등록할 수 있는 SDK입니다. tool call이 props를 받으면 그게 정적 컴포넌트에 매핑되어 사용자에게 렌더됩니다. 또 다른 예시는 Goose입니다. Goose는 MCP 기능 대부분을 시험해볼 수 있는 MCP 클라이언트입니다. Goose에는 Goose Auto Visualizer라는 흥미로운 기능이 있어서, 어떤 타입의 데이터든 Goose에 전달하면 Goose가 그 데이터를 분석하고 정리해서 Goose 팀이 만든 미리 정의된 컴포넌트 중 맞는 것으로 렌더합니다. 그게 정적 방식이고, 오늘날 UI를 생성하는 가장 일반적인 방법입니다.

최근 진화를 보면, 우리가 이제 선언형 UI라고 부르는 것이 있습니다. 선언형 UI는 한 단계 더 나아갑니다. 개발자가 만든 미리 정의된 정적 컴포넌트는 여전히 있습니다. 디자인 시스템과 모든 컴포넌트가 거기 있습니다. 하지만 에이전트가 props와 데이터만 전달하는 대신, JSON이나 YAML 또는 FastMCP [?FastNCPS] Zoo처럼 Python으로 된 디스크립터를 사용해서 이 미리 정의된 정적 컴포넌트들에 매핑합니다. 그리고 그 디스크립터를 최종 UI로 변환하는 번역·렌더링 엔진이 있습니다.

어떻게 다른가요? 더 동적이고 개인화가 가능합니다. 컴포넌트는 여전히 정적이지만요. 이게 익숙해 보인다면, 그건 새로운 게 아니기 때문입니다. Netflix가 개인화와 서버 드리븐 UI 시대부터 이걸 오래 해왔습니다 — Netflix 홈페이지에 가면 완전히 개인화된 UI를 받지만, 그건 여전히 Netflix 컴포넌트와 UI 요소에 매핑된 것입니다. 최근 제가 본 매우 좋은 도구는 JSON Render입니다. Vercel이 만들고 있고, JSON과 YAML(최근 YAML 지원 추가)로 컴포넌트를 매핑해서 오늘날 사용할 수 있는 매우 동적이고 좋은 UI 인터랙션을 만들 수 있습니다. 다만 JSON Render도 여전히 정적 컴포넌트에 제약됩니다. LLM이 컴포넌트를 생성하는 게 아닙니다. LLM이 JSON을 생성합니다. 하지만 저는 이 시점에서 선언형 생성형 UI가 아마도 오늘날 유연성과 일관성의 완벽한 균형점이라고 생각합니다 — 디자인 시스템을 유지하고, UI 생성의 예측 가능성을 갖고, 더 빠르고, UI 생성에 많은 토큰을 쓰지 않아도 되니까요.

하지만 처음에 언급했듯, 왜 아직도 여기 갇혀 있을까요? 다음 단계는 무엇일까요?

다음 단계는 생성형 컴포넌트라고 생각합니다. 생성형 컴포넌트는 처음에 제가 제시한 전제로 들어갑니다 — 모델이 프런트엔드 코드를 잘 씁니다. React를 잘 쓰고, JavaScript와 CSS를 잘 만듭니다. 그렇다면 왜 런타임에 on-demand로 그냥 쓰게 하지 않을까요? 뭐가 문제가 될 수 있을까요?

이 UI 생성 모델은 에이전트 능력을 사용합니다. tool call을 쓸 수도 있지만, 레이아웃 렌더링 엔진을 호출하는 대신 역 샘플링(reverse sampling)으로 같은 모델을 호출하거나 다른 모델을 호출해서 HTML, CSS, JavaScript를 on-demand로 생성하고 그걸 클라이언트에 전달합니다.

저는 Postman에서 이 실험을 했습니다 — 날씨 API로 가서 날씨 데이터를 가져오고, 조크를 만들고, HTML/CSS/JS를 단일 tool call로 생성하는 날씨 에이전트를 만들었습니다. 그러면 매번 에이전트가 만든 랜덤하지만 매우 창의적인 UI가 나옵니다. 컴포넌트가 없습니다. 번역도 없습니다.

물론 이 접근법에는 문제가 있습니다. 신뢰할 수 없는 서드파티 코드를 믿으면 안 되듯, LLM이 생성한 코드를 그냥 사용자에게 전달하면 안 됩니다. 생성형 UI와 이 수준의 생성형 UI에는 배포 모델(distribution model)이 필요합니다. 이 배포 모델에는 경계(boundary), 격리(containment), 샌드박스(sandbox)가 필요합니다.

그래서 MCP 앱이 매우 중요하다고 생각합니다. MCP 앱이 생성형 UI의 최고의 전달 메커니즘이기 때문입니다. 인증, tool calling, UI↔에이전트 메시지 패싱을 포함한 MCP의 기능이 있습니다. double iframe으로 기본적으로 샌드박스됩니다. 오늘날 서드파티 UI 전달의 기본값이고, 표준이 됐습니다. 흥미로운 점은 서드파티 UI뿐만 아니라 1st-party UI에도 쓸 수 있다는 것입니다.

그래서 Anthropic이 visualizer 기능으로 하는 것이 전략적으로 매우 흥미롭다고 생각합니다 — Claude에서 이 인터랙션을 전달하기 위해 자체 렌더링 및 아키텍처 메커니즘을 만들 수도 있었지만, MCP 앱을 선택했습니다. MCP 앱이 앞서 언급한 대부분의 기능을 기본으로 제공하기 때문입니다. Anthropic이 1st-party UI에 MCP 앱을 쓰기로 결정했다면, 우리도 왜 못 쓰겠습니까? 매우 강력한 프로토콜입니다. 특히 UI가 에이전트와 코딩 모델에 의해 즉석에서 생성될 때는, 전달을 위한 최고의 메커니즘입니다.

지금은 아마도 최종 형태가 아닙니다. 사람들은 계속 묻습니다, 채팅이 최종 형태인가요? MCP 앱이 최종 형태인가요? 아직 알아가고 있습니다. 명백한 미래는 아마도 너무 명백할 것입니다. Jarvis가 어디 있냐고, 떠다니는 창이 어디 있냐고 했지만 — 생각해보면 그건 사람들이 새 사용자 인터랙션을 만든다면 어떤 모습일지 상상하는 뻔한 것입니다. 하지만 우리에게는 아직 충분한 상상력이 없다고 생각합니다.

최근 들은 유추가 매우 흥미롭습니다: 1930년대 라디오가 나왔을 때, 첫 TV 프로그램은 카메라를 든 라디오 쇼였습니다. 이 새 기술로 뭘 할 수 있는지 상상하지 못했기 때문입니다. 오늘날 우리가 가진 이 새 기술도 비슷합니다. 우리는 아직 라디오 시대에 있고, 이 새 미디어, 이 새 컴퓨터의 새 힘으로 미래에 어떤 놀라운 것들을 할지 다 모릅니다. 그게 어떤 모습일지 상상조차 할 수 없습니다.

물론 투기적이지만, 제가 실제로 일어날 것이라고 생각하는 것은 우리가 컴포넌트를 넘어 더 진정한 사람-에이전트 협업(human-agent collaboration)으로 나아간다는 것입니다. Excalidraw MCP 앱을 아직 모르신다면 꼭 확인해보세요. Excalidraw MCP 앱은 단순히 다이어그램 출력과 시각화를 위한 것이 아닙니다. 매우 흥미로운 것을 합니다 — 공유 아티팩트(shared artefact)를 만듭니다. 사람과 에이전트가 공유 공간에서 함께 협업할 수 있는 캔버스를 만드는데, "이것 바꿔줘"라고 에이전트와 대화하면서도 직접 클릭하고 익숙한 방식으로 UI를 수정할 수 있습니다. 그게 새로운 상호작용 방식, 새로운 에이전트 능력 경험 방식이 됩니다.

현재 우리는 에이전트를 단순히 오케스트레이터와 시각화 전달 메커니즘으로만 쓰기에는 너무 강력하다는 것에 매우 제약받고 있습니다. 그래서 저는 컴포넌트를 넘어, 생성형 UI의 미래는 더 협업적인 경험이 될 것이라고 믿습니다. 감사합니다.

네, 생성형 UI는 있겠지만 그 UI는 매우 개인화되고 협업적일 것입니다. 우리는 여전히 초기입니다. 답을 모릅니다. 사용자 인터랙션의 미래가 무엇인지, 아직 모릅니다. 하지만 우리가 그 미래를 만들어갈 수 있습니다. 감사합니다.
