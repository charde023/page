OpenAI가 직접 밝힌 Codex 하네스 위에 나만의 에이전트를 구축하는 법

업로드 2026-10-13 · 17.7분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 발표의 중심 문제는 코딩 에이전트의 작동 기반을 처음부터 만들지 않고도 자신만의 인터페이스를 만들 수 있는가이다. 코딩 에이전트는 모델에 질문 한 번을 보내는 프로그램으로 끝나지 않는다. 대화를 이어 가고, 파일을 찾고, 명령을 실행하고, 도구를 호출하고, 실행 권한과 작업 공간을 관리해야 한다. 발표자는 이런 기반을 에이전트 하네스(agent harness)라고 부른다.

발표자가 제안하는 방법은 Codex 하네스를 다시 구현하는 대신 그 위에 있는 Codex App Server를 이용하는 것이다. App Server는 사용자가 만든 앱과 Codex 하네스 사이에서 메시지를 주고받게 하는 규약이다. 사용자가 만드는 화면이나 프로그램은 클라이언트가 되고, App Server는 클라이언트의 요청을 하네스로 전달한 뒤 진행 상황과 결과를 이벤트로 돌려준다.

읽는 법: 위에서 아래로 읽는다. 핵심은 에이전트 전체를 새로 만드는 것이 아니라, 이미 있는 하네스는 재사용하고 인터페이스와 목적별 기능에 개발 노력을 집중하는 것이다. 이는 개념 관계도이며 성능이나 비용을 수치로 비교한 그래프가 아니다.

App Server는 JSON-RPC 스타일 프로토콜이라고 설명된다. 쉽게 말하면 클라이언트와 서버가 정해진 형식의 메시지로 요청과 이벤트를 주고받는 방식이다. 발표에서는 실제 Codex 앱과 App Server 사이의 이벤트를 가로채 보여 주는 검사기를 사용했다. 새 스레드가 시작되고, 설정을 읽고, 응답 조각이 스트리밍되며, 파일 검색 같은 기능의 정보가 오가는 장면이 소개됐다.

발표자에 따르면 당시 프로토콜에는 120개가 넘는 클라이언트 메시지가 있었다. 초기화, 스레드와 대화 차례 수정, 목표 설정, 플러그인 목록, 파일 검색, 파일 시스템 변경 등이 포함된다고 한다. 범용 연결 규약인 ACP와 비슷한 면이 있지만, App Server는 Codex 하네스의 개별 기능을 더 세밀하게 제어하도록 만들어졌다는 것이 발표자의 설명이다.

읽는 법: 1번에서 아래로 내려간 뒤 마지막 결과가 다시 첫 번째 클라이언트의 다음 요청으로 이어진다. 한 번의 질문과 답으로 끝나는 선형 과정이 아니라, 상태와 이벤트를 계속 주고받는 순환이다.

기반을 재사용하더라도 에이전트의 행동은 목적에 맞게 바꿀 수 있다. 첫 번째 수단은 개발자 지침(developer instructions)이다. 발표자는 기본 시스템 프롬프트를 통째로 교체하기보다, Codex가 이미 모델별로 조정해 둔 기본 지침 뒤에 목적별 지침을 덧붙이기를 권한다. 그래야 기존 조정 내용을 유지하면서 앱에 필요한 행동을 추가할 수 있다는 주장이다.

두 번째 수단은 동적 도구(dynamic tools)다. 에이전트가 호출할 추가 함수를 직접 노출할 수 있다. 도구가 많다면 모든 설명을 처음부터 문맥에 넣지 않고, 필요할 때 검색해 불러오도록 지연 로딩(deferred loading) 표시를 할 수 있다. 발표자는 이것이 불필요하게 문맥 창을 채우거나 에이전트를 혼란스럽게 하는 일을 줄인다고 설명한다. 스레드마다 모델 제공자, 모델, 네트워크 접근, 수정 가능한 파일 같은 설정도 바꿀 수 있다고 한다.

읽는 법: 아래 계층이 위 계층을 대체하는 구조가 아니다. 기존 기반 위에 목적, 도구, 실행 제한을 차례로 더하는 구조다. 다만 실제 우선순위와 충돌 처리 방식은 이 발표에서 상세히 검증되지 않았다.

배포할 때는 앱이 사용할 App Server 바이너리를 함께 묶으라는 조언이 나온다. 프로토콜이 버전 사이에서 계속 바뀌므로 사용자의 컴퓨터에 설치된 CLI에 의존하면 기능 차이나 깨지는 변경을 만날 수 있다는 이유다. 앱과 호환되는 버전을 함께 배포하면 어떤 기능을 쓸 수 있는지 통제하기 쉽다. 발표에서는 특정 버전에 맞는 TypeScript 바인딩이나 JSON 스키마를 생성할 수 있고, 통신 방식으로 표준 입출력(STDIO)이나 WebSocket을 선택할 수 있다고 설명한다.

모든 자동화에 App Server가 필요한 것은 아니다. codex exec는 사람이 대화 화면을 조작하지 않는 단일 작업이나 CI/CD 스크립트에 어울린다. 반면 App Server는 에이전트의 진행 상태를 직접 보여 주는 종합 클라이언트, 여러 스레드를 동시에 실행하는 평가 하네스, 목표 기능처럼 하네스를 세밀하게 제어해야 하는 경우에 더 적합하다는 것이 발표자의 구분이다.

폭이 좁은 화면에서는 아래 비교 영역을 좌우로 이동해 읽는다.

읽는 법: 어느 쪽이 항상 더 우수하다는 표가 아니다. 사용자와 계속 상호작용하며 상태를 제어해야 하는지, 아니면 정해진 작업을 비대화형으로 실행하면 되는지에 따라 선택한다.

발표의 가장 구체적인 사례는 Doom 게임 안에서 Codex를 실행한 데모다. 발표자는 Electron 앱과 Doom WASM 렌더러를 사용하고, 게임 안의 화면에서 App Server로 메시지를 전달했다고 설명했다. Codex는 대답만 한 것이 아니라 동적 도구를 호출해 방어구·체력·무기를 제공했고, 로컬에서 실행 중인 App Server를 통해 작업 디렉터리를 확인하는 모습도 보였다. 이 사례의 목적은 게임이 실용적인 개발 환경이라는 주장이 아니라, App Server를 쓰면 고전적인 채팅창 밖에서도 에이전트를 작동시킬 수 있음을 보여 주는 데 있다.

따라서 발표의 결론은 세 가지다. 호환되는 하네스 버전을 앱과 함께 배포하고, 목적별 함수를 도구로 노출하되 필요하면 지연 로딩하며, 기본 시스템 프롬프트를 바로 교체하지 말고 개발자 지침부터 추가하라. 다만 이는 발표자가 권한 실전 지침이다. 실제 안정성, 보안, 비용, 버전별 동작은 이 전사만으로 독립 검증되지 않았다.

여기까지만 이해하면 충분

  • Codex App Server는 사용자 앱과 Codex 하네스 사이에서 요청·상태·결과 이벤트를 전달하는 프로토콜이다.
  • 기본 하네스를 다시 만들기보다 개발자 지침, 동적 도구, 스레드별 설정으로 목적에 맞게 확장할 수 있다.
  • 종합 클라이언트와 여러 스레드 제어에는 App Server가, 단순 스크립트 작업에는 codex exec가 더 어울린다.
  • 발표자는 버전 불일치를 줄이기 위해 호환되는 하네스 바이너리를 앱과 함께 배포하라고 권한다.

비유와 깨지는 지점

가전제품과 공용 제어 단자

Codex 하네스를 실제 일을 수행하는 가전제품, App Server를 정해진 신호를 전달하는 제어 단자, 맞춤형 앱을 그 단자에 연결하는 리모컨으로 볼 수 있다. 리모컨의 모양은 달라도 같은 기반 기능을 호출하고 상태를 돌려받을 수 있다.

비유가 깨지는 지점: App Server는 모든 에이전트에 통하는 완전한 범용 단자가 아니다. 발표자는 범용적인 ACP보다 Codex 하네스의 개별 기능을 더 세밀하게 노출한다고 설명했고, 프로토콜도 버전 사이에서 바뀔 수 있다고 말했다.

1. 원인

App Server를 사용하는 것이 자체 에이전트 기반을 처음부터 만드는 부담을 줄이는 이유는 무엇인가?

모범 답안 보기

Codex 앱과 IDE 확장 등에서 사용하는 하네스의 스레드, 스트리밍, 파일 검색, 도구와 설정 기능을 메시지로 이용할 수 있기 때문이다. 개발자는 이 기능들을 모두 다시 구현하기보다 자신의 인터페이스와 목적별 지침·도구에 집중할 수 있다.

2. 대조

App Server와 codex exec를 가르는 핵심 기준은 무엇인가?

모범 답안 보기

정해진 작업을 비대화형 스크립트로 실행하면 되는지, 아니면 에이전트의 상태를 화면에 보여 주고 여러 스레드와 하네스 기능을 계속 제어해야 하는지가 기준이다. 전자에는 codex exec, 후자에는 App Server가 더 적합하다는 것이 발표자의 구분이다.

3. 적용

새 자동화 도구를 설계한다면 App Server 도입 전에 무엇을 확인해야 하는가?

모범 답안 보기

사용자와의 지속적인 상호작용, 스트리밍 이벤트, 여러 동시 스레드, 목적별 도구와 세밀한 샌드박스 제어가 필요한지 확인한다. 단일 명령 실행이면 codex exec가 더 단순할 수 있다. App Server가 필요하다면 사용할 바이너리 버전, 생성된 스키마나 바인딩, 도구 노출 범위와 실패 조건을 먼저 고정한다.

이번 글의 통찰

1. 에이전트 제품의 차별점은 하네스 재구현보다 인터페이스와 도구에 있을 수 있다

  • [원문] 발표자는 Codex 앱, IDE 확장과 제3자 인터페이스가 같은 하네스와 App Server를 사용한다고 설명하고, Doom 안에서도 Codex를 실행하는 데모를 보였다.
  • [해석] 검증된 기반을 재사용할 수 있다면 개발 자원은 사용자 경험, 목적별 도구, 권한과 평가 설계에 더 집중할 수 있다.
  • [경계] “검증된 기반”이라는 평가는 META 설명과 발표자의 주장이다. 안정성·성능·보안은 독립적으로 확인되지 않았으며 Doom 데모도 실용적인 개발 환경의 우수성을 입증하지 않는다.

2. 맞춤화는 기본 능력을 버리는 것이 아니라 제한된 층을 추가하는 방식이다

  • [원문] 발표자는 기본 시스템 프롬프트 교체보다 개발자 지침 추가를 권했고, 추가 함수는 동적 도구로 노출하되 문맥 오염을 줄이기 위해 지연 로딩하라고 조언했다.
  • [해석] 기존 기반을 유지하면서 목적별 지침과 도구를 분리하면 무엇을 변경했는지 추적하고 시험하기 쉬워질 가능성이 있다.
  • [경계] 지연 로딩이 실제 정확도·비용·지연 시간을 얼마나 개선하는지는 수치로 제시되지 않았다. 도구 검색이 실패하거나 잘못된 도구를 선택할 가능성도 이 발표에서는 평가하지 않았다.

3. 프로토콜 선택보다 버전과 실행 조건을 통제하는 일이 먼저다

  • [원문] 발표자는 프로토콜이 버전 사이에서 정기적으로 바뀌므로 사용자 CLI에 의존하지 말고 앱과 함께 하네스 바이너리를 배포하라고 권했다.
  • [해석] 기능이 많은 통합일수록 “최신 버전인가”보다 “앱이 시험한 버전과 같은가”가 운영 안정성에 더 중요한 판단 기준이 될 수 있다.
  • [경계] 전사와 META의 숫자는 1060초, 17.7분, 발표자의 약 18분으로 서로 환산 가능한 범위여서 직접 충돌하지 않는다. 반면 화자는 자신을 Dom, OpenAI의 Codex 개발자 경험 담당이라고 소개했지만 META 설명은 Dominik Kundel, provenance의 affiliation은 Developers, creator는 null로 기록했다. 같은 인물·소속 표기인지 독립 확인되지 않았다. 또한 120개가 넘는 메시지, 올해 초, 약 한 달 전, 내일은 발표 시점 기준 표현이므로 업로드일만으로 정확한 기준일을 확정할 수 없다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 발표는 추상적인 프로토콜 설명 뒤에 실제 이벤트 검사기와 Doom 도구 호출 장면을 연결했다.
  • 통찰: 학습자가 App Server를 이해했는지는 정의 암기보다 클라이언트 요청이 하네스 작업과 반환 이벤트로 이어지는 흐름을 설명하는지로 확인할 수 있다.
  • 질문/행동: “왜 단순 모델 호출이 아니라 하네스가 필요한가?”를 그림 없이 설명하게 하고, App Server와 codex exec의 선택 기준을 새 사례에 적용하게 한다.

사업가 · 구조적 비유

  • 관련성: 기존 하네스를 재사용하고 호환 버전을 함께 배포하라는 조언은 개발 비용과 버전 위험을 배분하는 문제다.
  • 통찰: APOM이나 다른 운영 시스템에 적용할 수 있는지는 미검증이지만, 공통 실행 기반은 재사용하고 고객 접점과 목적별 기능에 자원을 집중한다는 구조는 검토할 가치가 있다.
  • 질문/행동: 새 기능에서 반드시 직접 만들어야 하는 차별화 부분과 이미 있는 기반으로 대체할 부분을 먼저 구분할 수 있는가?

마케터 · 구조적 비유

  • 관련성: “자체 하네스를 만들 필요가 없다”는 주장에 실제 이벤트 검사기, 지원 인터페이스 목록, Doom 데모가 증거 장면으로 붙었다.
  • 통찰: 기능 이름만 나열하기보다 사용자의 명령이 도구 호출과 화면 변화로 이어지는 장면을 보여 주면 작동 방식을 전달하기 쉽다.
  • 질문/행동: 상세페이지에서 “자동화된다”고만 쓰지 말고, 입력·중간 작동·관찰 가능한 결과를 한 장면으로 제시할 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 스레드, 이벤트, 도구, 샌드박스, 버전 고정, STDIO와 WebSocket 등 실제 통합 판단 요소가 제시됐다.
  • 통찰: 기술 이름보다 작업 형태를 먼저 봐야 한다. 단일 비대화형 작업인지, 여러 스레드와 상태 이벤트를 가진 클라이언트인지에 따라 codex exec와 App Server를 선택한다.
  • 질문/행동: 최소 클라이언트에서 정상 응답뿐 아니라 버전 불일치, 도구 검색 실패, 권한 거부와 프로세스 종료를 어떻게 관찰할 것인가?

1. App Server의 위치

발표자는 자신을 Dom이라고 소개하고 OpenAI에서 개발자 경험, 특히 Codex 관련 업무를 한다고 말했다. 발표 초반에는 자체 에이전트 하네스를 만든 사람과 그것을 어렵게 느끼는 사람에게 손을 들게 했다. 이어 약 18분 동안 Codex 하네스 위에 직접 인터페이스를 만드는 방법을 설명하겠다고 했다.

App Server는 Codex 하네스를 감싸는 프로토콜이다. 발표자는 Agent Client Protocol과 비슷한 개념이지만 Codex 하네스에 깊이 통합된다고 설명했다. Codex 하네스와 App Server가 모두 오픈소스이며 Apache 2.0 라이선스라고 말했다. Responses API와 호환되는 API를 제공하는 다른 모델 제공자도 연결할 수 있고, LM Studio와 Ollama를 위한 편의 설정도 있다고 주장했다.

2. 메시지와 이벤트

App Server는 JSON-RPC 스타일 프로토콜이며 Codex 앱, IDE 확장, VS Code 확장과 일차·제3자 인터페이스에 사용된다고 설명됐다. 사례로 Xcode, JetBrains IDE, Theo의 T3 Code, Remodex가 언급됐다. 같은 App Server를 사용해 Codex를 Claude Code 안에 넣은 플러그인도 올해 초 사용했다고 발표자는 말했다.

클라이언트는 App Server에 메시지를 보내 작업을 요청하고 이벤트를 받는다. 발표자는 실제 Codex 앱과 App Server 사이의 이벤트를 가로채는 검사기를 제작해 새 스레드, 설정 읽기, 스트리밍 델타와 파일 검색 관련 정보가 오가는 모습을 보였다.

발표 당시 클라이언트 메시지가 120개를 넘는다고 했다. 초기화, 클라이언트별 설정, 스레드와 대화 차례 수정, 목표 설정, 플러그인 목록, 파일 검색과 파일 시스템 변경이 예로 제시됐다. 발표자는 범용 프로토콜인 ACP보다 App Server를 통해 하네스의 개별 부분을 더 세밀하게 제어할 수 있다고 설명했다.

또한 앱 사용자가 ChatGPT로 로그인해 자신의 구독을 가져오고 사용량을 Codex 사용 한도에 반영할 수 있다고 말했다. 이 동작의 구체적인 요금·계정 조건은 전사에 나오지 않는다.

3. 에이전트 맞춤화

첫 번째 맞춤화 수단은 개발자 지침이다. Codex 시스템 프롬프트는 저장소에서 볼 수 있지만, 발표자는 이를 교체하기보다 개발자 지침으로 내용을 덧붙이기를 권했다. 모델별 프롬프트 조정 결과를 유지하면서 특정 앱에 필요한 행동을 추가하기 위해서다.

두 번째 수단은 동적 도구다. MCP나 ACP에서 사용하는 방식과 비슷한 수단을 쓰거나 함수를 직접 정의할 수 있다고 설명했다. 도구를 지연 로딩으로 표시하면 모든 도구를 시스템 프롬프트에 넣지 않고 도구 검색을 통해 찾게 할 수 있다.

스레드별로 모델 제공자와 모델을 바꾸고, 샌드박스의 네트워크 접근 범위나 수정할 수 있는 파일을 세밀하게 정할 수도 있다고 했다.

4. 배포와 통신

App Server는 Codex CLI와 같은 바이너리에 포함돼 있어 CLI가 설치되어 있다면 바로 시작할 수 있다고 설명했다. Codex 앱은 해당 바이너리를 앱 번들 안에 포함하며, 앱 버전이 바뀔 때 뒤에서 새 CLI 버전도 함께 배포한다고 했다.

Windows에서는 Linux용과 Windows용 바이너리 두 개를 제공한다고 말했다. WSL 모드에서는 Linux 버전을, 그 밖의 경우에는 Windows에서 App Server를 직접 실행한다고 설명했다.

특정 App Server 버전에 맞는 TypeScript 바인딩과 JSON 스키마를 생성할 수 있다. 프로토콜이 버전 사이에서 자주 달라질 수 있으므로, 호환성을 통제하려면 앱이 사용할 바이너리를 함께 묶으라는 것이 발표자의 권고다. 전송 방식은 STDIO 또는 WebSocket을 선택할 수 있다고 했다.

5. 통합 방법

첫 번째 방법은 발표 시점에 최근 공개됐다고 소개한 Python SDK다. 프로세스 수명주기 관리를 대신 처리하고 ChatGPT 로그인 같은 기능을 통합하기 쉽게 해 준다고 설명했다.

두 번째 방법은 Codex 자체에 구현을 요청하는 것이다. 발표자는 문서를 가리키거나 필요한 경우 추가 힌트를 주면 Codex가 이 프로토콜을 잘 구현한다고 주장했다. macOS 앱 제작용 플러그인과 결합하거나 Visual Basic으로 Windows 네이티브 앱 형태의 클라이언트를 대부분 한 번에 만들었다는 사례도 언급했다.

6. Doom 데모

발표자는 약 한 달 전에 “Codex 안에서 Doom을 실행하는 대신 Doom 안에서 Codex를 실행하자”고 생각했다고 말했다. 데모는 Electron 앱과 Cloudflare의 Doom WASM 렌더러를 사용했고, 게임 엔진 대부분은 C로 구현됐으며 Freedoom 게임을 불러왔다고 설명했다.

Codex가 게임 파일을 변경해 Codex 화면을 게임 엔진 안에서 직접 렌더링했고, Electron IPC를 통해 App Server로 메시지를 전달했다. 발표자는 데모에서 GPT-5.5를 사용한다고 말했다.

동적 도구를 통해 방어구와 체력을 얻거나 모든 무기와 탄약을 받는 요청을 실행했다. 또한 App Server가 발표자의 컴퓨터에서 실행 중이기 때문에 zsh를 호출해 현재 작업 디렉터리를 확인하는 장면도 보였다. 발표자는 Doom 안에서 직접 코딩할 수도 있지만 Codex 앱이 더 나을 것 같다고 덧붙였다.

7. App Server와 codex exec

codex exec는 비대화형으로 작업을 시작하는 명령이다. 발표자는 CI/CD에서 PR을 자동 수정하는 것처럼 스크립트로 정해진 작업을 수행할 때 적합하다고 했다.

App Server는 에이전트와 상호작용하는 종합 클라이언트를 만들거나, 여러 Codex 스레드를 동시에 실행하거나, 평가 하네스와 /goal 같은 기능을 구현할 때 더 적합하다고 설명했다. 여러 codex exec 호출을 직접 병렬화하는 대신 새 스레드 이벤트를 보내 작업을 분기할 수 있다는 주장이다.

8. 세 가지 권고

  1. 하네스 버전을 앱과 함께 배포한다. 사용자에게 설치된 CLI에 의존하면 깨지는 변경, 실험 기능 차이, 업데이트 여부 때문에 문제가 생길 수 있다고 했다.
  2. 새 기능을 도구로 노출하되 지연 로딩한다. 추가 함수들을 계속 문맥에 넣지 않고 필요할 때 사용할 수 있게 하라는 조언이다.
  3. 기본 시스템 프롬프트를 교체하기 전에 개발자 지침부터 추가한다. 자체 시스템 프롬프트로 바로 바꾸면 기존 하네스가 모델별로 조정한 내용을 잃을 수 있다고 경고했다.

수치·이름·시점 경계

  • META의 1060초는 17분 40초이고 17.7분과 환산상 일치한다. 발표자의 “약 18분”도 반올림 범위여서 직접 충돌하지 않는다.
  • 120개가 넘는 클라이언트 메시지는 발표 시점의 주장이다. META 설명과 전사는 일치하지만 현재 수량은 확인되지 않았다.
  • 화자는 자신을 Dom이라고 소개했다. META 설명에는 Dominik Kundel이라고 적혀 있으나 provenance.creator는 null이고, 원본 영상 링크를 확인하지 못해 화자 이름과 SNS로 출처를 추정했다는 주석이 있다.

  • 올해 초, 약 한 달 전, 내일 오후, 다음 15분은 발표 현장을 기준으로 한 상대 시간이다. 업로드일 2026-10-13을 실제 촬영일로 간주해 환산할 근거는 없다.

자, 안녕하세요 여러분. 먼저 간단히 손을 들어 보게 하겠습니다. 직접 에이전트 하네스(agent harness)를 만들어 보신 분이 몇 분이나 되나요? 좋습니다. 에이전트 하네스를 만드는 일이 너무 부담스럽다고 느끼시는 분은 몇 분이나 되나요?

앞으로 약 18분 동안 Codex 하네스 위에 구축해서 에이전트 하네스용 인터페이스를 더 쉽고 덜 부담스럽게, 그리고 조금 더 재미있게 직접 만드는 방법에 대해 이야기하겠습니다. 제 이름은 Dom이고, OpenAI에서 개발자 경험, 특히 Codex 관련 업무를 담당하고 있습니다.

손을 들어 보는 질문을 하나만 더 하겠습니다. 약속드리지만 이제 여러분을 쉬게 해 드릴게요. Codex App Server에 대해 들어 보신 분이 몇 분이나 되나요?

좋습니다. 사실 이건 약간 함정 질문이었습니다. 어제 키노트에 참석하셨다면 모두 손을 드셨어야 합니다. 그렇지 않다면 아마 Roman의 발표를 듣지 않으신 것 같네요. 어제 잠깐 언급하긴 했지만, App Server가 무엇인지는 제대로 설명하지 않았습니다.

App Server는 Codex 하네스를 감싸는 프로토콜입니다. Agent Client Protocol 같은 것을 살펴본 적이 있다면, 개념적으로는 매우 비슷합니다. 기본적으로 하네스 위에 직접 구축하고 깊이 통합할 수 있게 해 주는 프로토콜입니다. App Server와 ACP의 차이점에 대해서도 조금 이야기하겠습니다.

기억해 두셔야 할 중요한 점은 Codex 하네스와 App Server 자체가 모두 오픈 소스라는 것입니다. 이를 활용할 수 있는 몇 가지 방법을 살펴보겠습니다.

더 중요한 점은, 내일 오후에 이런 것들이 내부적으로 어떻게 작동하는지 자세히 살펴볼 예정이라는 것입니다. Codex에게 저장소를 읽고 아주 깊이 있게 분석해 달라고 언제든 요청할 수도 있습니다. 라이선스는 Apache 2.0입니다.

자유롭게 포크하고, 수정하고, 여러분만의 것으로 만들고, 즐겁게 사용해 보세요. Responses API 호환 API를 제공하기만 한다면 어떤 모델 제공업체와도 연결할 수 있습니다. LM Studio나 Ollama에 쉽게 연결할 수 있는 편의 설정도 제공합니다.

작동 방식을 설명하자면, App Server 프로토콜은 Codex 앱, IDE 확장 기능, VS Code 확장 기능, 그리고 모든 퍼스트파티 인터페이스와 서드파티 인터페이스를 구동하는 데 사용하는 JSON-RPC 스타일 프로토콜입니다. Xcode나 JetBrains IDE에서 Codex를 사용해 본 적이 있거나, Theo의 T3 Code나 Remodex 같은 오픈 소스 프로젝트를 사용해 본 적이 있다면, 이들은 모두 동일한 하네스와 동일한 App Server로 구동됩니다.

올해 초에는 같은 App Server를 사용해 Codex를 Claude Code에 넣기도 했습니다. 아직 Claude Code를 사용 중이고, 그곳에서 Codex를 사용해 코드를 검토하거나 작업을 Codex에 넘기고 싶다면 해당 플러그인을 사용할 수 있습니다. 이 플러그인은 내부적으로 동일한 App Server와 동일한 하네스를 사용합니다.

ACP 같은 것을 살펴본 적이 있다면, 높은 수준에서는 상당히 익숙하게 느껴질 것입니다. 기본적으로 App Server는 클라이언트, 즉 여러분이 만들고 있는 애플리케이션과 서버, 즉 Codex App Server 사이에 메시지를 주고받으며 다양한 작업을 수행하고 이벤트를 수신하는 방식으로 작동합니다.

가상의 메시지를 잔뜩 보여 드리는 대신, 저는 약간 과하게 해서 실제 Codex 앱과 Codex App Server 사이의 모든 이벤트를 가로채는 작은 인스펙터를 만들었습니다. 이를 통해 실제 이벤트를 살펴볼 수 있습니다.

여기 Codex 앱으로 전환해 보겠습니다. Codex 앱의 인앱 브라우저에 동일한 인스펙터를 로드했습니다. 메시지를 보내면 다양한 이벤트가 들어오는 것을 볼 수 있습니다. 처음에는 부담스러워 보일 수 있지만, 메시지 몇 개를 살펴보면 상당수가 비교적 익숙하게 느껴질 것입니다.

한 번 더 해 보겠습니다. 예전 메시지가 일부 버퍼에 남아 있었던 것 같습니다. 새로 시작하겠습니다. 됐습니다. 그리고 위에 있는 제 CodexPad는 신경 쓰지 마세요.

여러 설정과 함께 스레드가 시작되고, 현재 어떤 일이 일어나고 있으며 어느 프로젝트에서 작업 중인지 설명하는 메시지부터, 설정을 읽는 메시지까지 다양한 메시지를 보게 될 것입니다. 여기에는 새 스레드가 시작되는 모습이 있고, 여기는 데이터가 스트리밍되는 과정을 보여 주는 델타 메시지입니다.

여기서 확인할 수 있는 추가 정보도 많습니다. 이 프로토콜을 매우 유연하게 만드는 중요한 요소 중 하나는 앱의 핵심 기능이라면 무엇이든 노출한다는 점입니다. 무언가를 스트리밍하거나 파일 검색을 수행할 때 그 모든 정보가 App Server와 앱 사이에서 오갑니다. 자체 하네스 통합이나 자체 클라이언트를 구축한다면 동일한 기능을 활용할 수 있습니다.

실제로 현재 클라이언트 메시지는 120개가 넘고, 계속 추가되고 있습니다. 여기에는 클라이언트에 더욱 구체적인 설정을 지정할 수 있는 초기화부터, 예상할 수 있는 일반적인 기능인 스레드 수정과 턴(turn)까지 모두 포함됩니다. 자체적인 목표 모드(goal mode)를 구현하고 싶을 때 목표를 설정하는 기능, 플러그인 목록 조회, 앱에서 볼 수 있는 그 밖의 모든 기능, 파일 검색과 파일 시스템 수정 기능까지 포함됩니다.

모든 기능에 접근할 수 있습니다. 또한 기반 에이전트를 쉽게 구성할 수 있도록 노력하고 있습니다. 이는 더 일반적인 프로토콜인 ACP와는 조금 다릅니다. 이 프로토콜을 사용하면 하네스의 개별 부분도 더 세밀하게 제어할 수 있습니다. 잠시 후 살펴보겠습니다.

많은 분들이 기대할 만한 또 하나의 기능은 이 프로토콜을 사용할 때 ChatGPT로 로그인(Sign in with ChatGPT)을 포함할 수 있다는 점입니다. 누군가 여러분의 앱을 사용한다면 자신의 ChatGPT 구독을 가져올 수 있고, 사용량은 해당 사용자의 Codex 사용량 한도에 포함됩니다. T3 Code 같은 도구나 유사한 도구를 사용해 보셨다면 바로 이 기능을 사용하고 있는 것입니다.

에이전트를 커스터마이즈할 때 이 App Server 위에 구축하며 가장 먼저 살펴볼 만한 중요한 요소는 두 가지입니다. 실제 앱의 시스템 지침을 보강할 수 있는 개발자 지침(developer instructions)과 도구 추가입니다.

개발자 지침을 사용하면 Codex 시스템 프롬프트에 내용을 덧붙일 수 있습니다. 저장소에서 실제 Codex 시스템 프롬프트를 확인할 수 있지만, 일반적으로는 개발자 지침을 사용해 내용을 추가하는 것을 권장합니다. 그러면 개별 모델에 맞춰 프롬프트를 조정하는 데 우리가 기울인 모든 작업을 계속 활용하면서, 여러분의 구체적인 사용 사례에 맞게 하네스를 커스터마이즈할 수 있습니다.

예를 들어 Codex 앱을 로드할 때 이것을 사용합니다. 일부 기능은 IDE 확장 기능이나 CLI보다 앱에 더 특화되어 있기 때문입니다.

다른 한 부분은 동적 도구(dynamic tools)입니다. 이를 통해 에이전트가 사용할 수 있도록 하고 싶은 추가 함수를 노출할 수 있습니다. MCP나 Agent Client Protocol에서 사용하는 것과 유사한 방식을 사용할 수도 있지만, 도구를 직접 정의할 수도 있습니다. 도구를 지연 로딩(deferred loading)으로 표시할 수도 있습니다. 그러면 도구를 시스템 프롬프트에 주입하는 대신 Codex가 도구 검색 도구(tool-search tool)를 사용할 수 있습니다. 이 부분은 내일 다른 세션에서 더 자세히 다루겠습니다. 이를 통해 전체 컨텍스트 윈도우를 오염시키지 않고 도구 검색을 통해 도구를 찾을 수 있습니다.

그뿐만 아니라 스레드별로 다른 에이전트 설정을 수정할 수도 있습니다. 다른 모델 제공업체를 설정하거나, 다른 모델을 선택하거나, 어떤 네트워크 연결에 접근할 수 있는지 또는 어떤 파일을 수정할 수 있는지와 같은 샌드박스 설정을 세밀하게 제어할 수 있습니다.

App Server를 사용하는 방법과 관련해 가장 먼저 알아야 할 점은 이것이 Codex CLI의 일부로 제공된다는 것입니다. 동일한 바이너리이므로, 시스템에 Codex CLI가 이미 설치되어 있다면 지금 바로 App Server를 실행하는 데 사용할 수 있습니다.

Codex 앱과 함께 어떻게 제공되는지도 살펴볼 수 있습니다. Codex 앱에는 실제 번들 안에 바이너리가 포함되어 있습니다. 설치된 Codex 앱 내부를 살펴보면 해당 번들의 콘텐츠에서 바이너리를 찾을 수 있을 것입니다. 앱을 업데이트할 때마다 버전이 바뀌는데, 내부적으로 새로운 CLI 버전을 함께 제공하기 때문입니다.

Windows에서는 바이너리를 두 가지 버전으로 제공합니다. Linux용으로 컴파일된 버전과 Windows 버전입니다. 앱을 WSL 모드로 로드하면 Linux 버전을 사용하고, 그렇지 않으면 Windows에서 App Server를 네이티브로 실행합니다.

추가적인 편의 기능도 많이 제공됩니다. 특정 버전의 App Server에 대한 TypeScript 바인딩(binding)을 생성하거나 JSON 스키마를 생성하도록 Codex에 요청할 수 있습니다. 이 프로토콜은 버전 간에 정기적으로 변경되기 때문에 이는 매우 유용합니다. 또한 Codex 앱에서 하는 것처럼 애플리케이션에 함께 번들링하는 것이 좋은 이유이기도 합니다. 그러면 구축 대상 버전의 기능을 완전히 제어할 수 있습니다.

프로토콜 측면에서는 표준 입력/출력, 즉 STDIO를 사용해 App Server를 시작하거나 WebSockets를 사용할 수 있습니다. 어떤 방식을 쓸지는 사용 사례에 따라 다르며, 솔직히 여러분에게 무엇이 가장 적합한지 알아내는 가장 쉬운 방법은 아마 Codex에게 물어보는 것일 겁니다.

가장 쉽게 통합할 수 있는 방법은 두 가지입니다. 첫 번째는 최근 출시한 Python SDK입니다. 수명 주기 관리의 많은 부분을 대신 처리해 주므로 직접 신경 쓸 필요가 없습니다. 또한 ChatGPT로 로그인 같은 기능을 더 쉽게 통합할 수 있고, 익숙한 인터페이스도 제공합니다.

그렇긴 하지만 우리는 AI Engineer 컨퍼런스에 와 있으니, 여러분 대부분은 두 번째 방법을 선택할 겁니다. 그냥 Codex에게 요청하는 것이죠.

놀랍지 않게도 Codex는 이 프로토콜을 구현하는 데 매우 뛰어납니다. 대부분은 Codex에게 문서 위치만 알려 주면 됩니다. 대개의 경우에는 그렇게 하지 않아도 되지만, 가끔 방향을 조금 잡아 주면 도움이 됩니다. macOS 앱 제작용 플러그인 같은 다른 플러그인과 결합할 수도 있습니다.

무언가를 빠르게 만들거나 완전히 자유롭게 시도하고 싶다면, 저는 실제로 Visual Basic을 사용해 진정한 Windows 네이티브 앱용 클라이언트를 만들어 보기도 했는데, 거의 한 번에 완성했습니다. 에이전트를 구축하는 세세한 내용을 전부 배우지 않고도 상당히 짧은 시간 안에 정말 인상적인 애플리케이션을 만들 수 있습니다.

하지만 이 App Server(앱 서버)에서 제가 가장 흥미롭게 생각하는 점은, 고전적인 에이전트 채팅 인터페이스에만 국한되지 않는다는 것입니다. UI와 기존 앱 안에서 어떻게 트리거할지, 백그라운드에서 실행할지, Maddie가 늘 하듯이 특이한 하드웨어에 올릴지, 아니면 저처럼 비디오 게임에 어떻게 넣을지 등 정말 창의적으로 활용할 수 있습니다.

약 한 달 전, Codex 안에서 Doom을 실행하는 대신 Doom 안에서 Codex를 실행할 수 있을지 생각해 봤습니다. 그래서 라이브로 해보자고 생각했죠. 여기 메시지 몇 개를 닫겠습니다.

Codex 앱의 Doom 버전이 있는데, 잘못된 창에서 실행했네요. 이걸 이쪽으로 옮기겠습니다. 됐습니다.

컨트롤이 망가졌네요. 제 실수입니다. 잠시만요. 이 듀얼 모니터 설정 때문에 가끔 컨트롤 캡처가 방해받는 것 같습니다. 이번에는 더 잘 되길 바라죠.

네. 좋습니다. 이건 Cloudflare의 Doom WASM 렌더러(renderer)를 사용하는 Electron 앱입니다. 게임 엔진 자체의 대부분은 C로 구현되어 있습니다. Freedoom 게임을 불러오는데, 실제로는 제가 Codex를 사용해서 게임 파일을 변경했습니다. 보이시죠? 이 모든 게임 엔진을 사용해 비디오 게임 안에서 네이티브로 렌더링되고 있습니다.

여기서 실제로 상호작용해 보면 Codex가 실행됩니다. 다시 말하지만, 이건 실제 비디오 게임 내부에서 네이티브로 렌더링된 다음 Electron의 IPC 프로토콜을 통해 App Server로 전달됩니다. 여기서 “hello”라고 입력하면 Codex가 응답하는 것을 볼 수 있습니다. GPT-5.5를 사용하고 있습니다.

하지만 재미있는 부분은 동적 도구(dynamic tools)를 사용해 추가 기능을 노출할 수 있다는 점입니다. 그러니 당연히 모든 방어구와 체력을 가져올 수 있습니다. 도구를 호출해서 그 모든 정보를 보여주고 있죠. 또는 “모든 탄약이 포함된 무기를 전부 줘”라고 말할 수도 있고, 그러면 각각의 도구를 모두 호출합니다. 이렇게 상호작용하지만, 다시 말해 이것도 여전히 제 컴퓨터에서 실제로 실행 중인 App Server입니다.

“디렉터리가 어디야?”라고 물으면 실제로 zsh를 호출해 현재 작업 디렉터리를 가져옵니다. 여기서 렌더링되는 것도 볼 수 있습니다. 자체 워크스페이스도 가지고 있죠. 그러니 원한다면 Doom 안의 Codex에 직접 바이브 코딩(vibe-coding)을 할 수도 있습니다. 제가 권할 만한 방식인지는 모르겠습니다. 이런 용도라면 Codex 앱이 조금 더 낫다고 생각하지만, 여기서 정말 재미있게 놀면서 자신만의 인터페이스를 구현할 수 있습니다.

좋습니다. 오늘 행사 중에 이미 몇 분과 App Server에 대해 이야기했는데, 자주 나온 질문이 하나 있었습니다. “이것과 Codex exec의 차이는 무엇인가요?”라는 질문이었죠.

이전에 Codex CLI를 사용해 보셨다면 익숙할 수도 있습니다. Codex exec라는 또 다른 명령이 있는데, 작업을 시작할 수 있도록 비대화형 인터페이스를 실행해 줍니다. Codex exec는 스크립팅에 아주 좋습니다. CI/CD 구현을 만들면서 PR 자동 수정 같은 특정 작업을 스크립트로 처리하고 싶다면 아주 좋은 선택입니다.

하지만 에이전트와 상호작용하고 에이전트를 보여주는 더 종합적인 클라이언트를 만들려는 경우, 또는 더 중요하게는 여러 Codex 스레드를 동시에 실행하려는 경우—예를 들어 자체 평가 하네스(eval harness)를 실행하거나 /goal 같은 것을 사용하려는 경우—App Server가 진가를 발휘합니다. 하네스를 완전히 제어할 수 있기 때문입니다. 모든 Codex exec 호출을 병렬화할 자체적인 방법을 고민할 필요가 없습니다. 대신 새로운 스레드 이벤트를 여러 개 보내서 그런 방식으로 작업을 실행하면 됩니다.

이제 여러분을 키노트로 보내드리기 전에, 오늘 이야기한 내용을 정리하는 팁을 세 가지 더 말씀드리겠습니다. App Server를 사용할 때 염두에 두어야 할 사항들입니다.

첫 번째는 자신만의 하네스 버전을 배포해야 한다는 것입니다. 이렇게 하면 수많은 골칫거리를 없앨 수 있습니다. 사용자가 설치한 CLI에 의존하면, 저희가 변경 사항을 최소화하려고 노력하고 있더라도 호환성을 깨뜨리는 변경 같은 문제를 계속 겪게 됩니다. 실험적 기능에 의존한다면 그런 일이 발생할 수도 있습니다. 또한 사용자가 실제로 자신의 버전을 업데이트했는지, 여러분이 사용하려는 최신 기능을 가지고 있는지 걱정하거나 업데이트하라고 재촉할 필요도 없습니다.

그러니 자신만의 하네스 버전을 배포하세요.

또 한 가지는 인터페이스의 일부로 새로운 함수를 반드시 노출해야 한다는 것입니다. 예를 들어 저희는 Codex 앱에서 Codex 스레드의 일부로 스스로를 제어할 수 있도록, 자동화를 실행하는 등의 기능을 활성화하기 위해 이렇게 합니다. 다만 해당 함수들은 지연(deferred) 상태로 표시하세요. 그러면 추가하는 여러 함수로 컨텍스트 창을 불필요하게 오염시키지 않을 수 있습니다. 대신 에이전트가 혼란을 겪지 않으면서도 해당 함수들을 사용할 수 있게 됩니다.

그리고 지침을 변경하고 있다면, 기본 지침을 바꾸기보다는 개발자 지침(developer instructions)을 추가하는 것부터 시작하세요. 곧바로 자신만의 시스템 프롬프트를 작성하고 싶을 수도 있지만, 하네스를 만들 때 실제 프롬프트가 분포 내에 있고 에이전트가 잘 수행하도록 하기 위해 저희가 계속 고려해야 하는 다양한 요소가 많습니다.

직접 뛰어들어 자신만의 시스템 프롬프트를 작성하면 그 모든 것을 놓치게 됩니다. 그러니 그렇게 하려는 경우에는 주의하세요.
