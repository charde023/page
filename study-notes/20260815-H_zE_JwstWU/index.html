자체 에이전트 하네스를 구축해야 할 때는 언제일까요? | 해리슨 체이스, LangChain

한 줄 요약

에이전트의 성능은 모델(model)만이 아니라 컨텍스트(context)와 하네스(harness) 설계에 좌우되며, 업무가 특수해질수록 자체 하네스·평가(evals)·관측성(observability)을 갖춰야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
에이전트(agent)의 3요소 에이전트를 단순 챗봇이 아니라 운영 시스템으로 이해하게 해준다 모델(model) + 컨텍스트(context) + 하네스(harness)가 함께 작동한다
하네스(harness) 모델에게 언제 어떤 정보를 줄지 결정하는 실행 구조다 도구 호출, 메모리, 파일 시스템, 샌드박스, 서브에이전트를 오케스트레이션한다
미들웨어(middleware) 기본 에이전트 루프를 망가뜨리지 않고 기능을 끼워 넣는다 모델 호출 전후, 도구 호출 전후에 요약·검사·후처리를 삽입한다
인디스트리뷰션(in-distribution) 기성 하네스를 쓸지 자체 하네스를 만들지 판단하는 기준이다 모델이 훈련·강화학습으로 익숙한 작업이면 기성품이 강하다
아웃오브디스트리뷰션(out-of-distribution) 우리 회사 업무처럼 특수한 영역에서 커스텀이 필요해진다 법률·금융·특수 업무는 자체 하네스와 제어 구조가 유리하다
평가(evals) 조직 내부에서 “좋은 결과”의 기준을 정의한다 벤치마크가 있어야 모델·하네스 변경의 효과를 비교할 수 있다
관측성(observability) 에이전트가 왜 실패했는지 추적하게 해준다 실패 원인은 모델보다 잘못 들어간 컨텍스트인 경우가 많다
데이터 플라이휠(data flywheel) 사용 데이터가 개선 데이터로 쌓이는 구조다 트레이스 수집 → 선별 → 실험 → 하네스·모델·컨텍스트 개선

내가 모를 만한 것 / 처음 보는 것

  • 에이전트 하네스(agent harness) — LLM을 반복 실행하면서 도구 호출, 컨텍스트 주입, 결과 처리, 외부 시스템 연동을 관리하는 구조.
  • 컨텍스트 윈도우(context window) — 모델이 한 번에 읽을 수 있는 입력 범위. 여기에 무엇을 넣느냐가 성능에 큰 영향을 준다.
  • 미들웨어(middleware) — 에이전트 실행 중간에 끼워 넣는 작은 확장 로직. 예: 모델 호출 전 요약, 도구 호출 후 검증.
  • 인디스트리뷰션(in-distribution) — 모델이 훈련 과정에서 많이 본 유형의 작업.
  • 아웃오브디스트리뷰션(out-of-distribution) — 모델이 익숙하지 않은 특수한 업무 영역.
  • 인지 아키텍처(cognitive architecture) — “질문 생성 → 분기 → 조사 → 합성”처럼 에이전트의 사고 절차를 명시적으로 설계한 구조.
  • Harbor — 에이전트를 데이터셋의 여러 작업에 대해 실행하고 점수화하는 오픈소스 평가 실행기(eval runner).
  • TerminalBench2 — 코딩 에이전트 평가에 쓰이는 대표 벤치마크 중 하나.
  • LangSmith — LangChain이 만든 평가(evals)와 관측성(observability) 플랫폼.
  • 트레이스(trace) — 에이전트 실행 과정 전체 기록. 어떤 프롬프트, 도구 호출, 응답, 오류가 있었는지 보여준다.
  • LLM as a judge — 다른 LLM을 심판처럼 사용해 결과 품질을 평가하는 방식.
  • SLM(small language model) — 비용과 지연 시간을 줄이기 위해 쓰는 작은 언어 모델.
  • 도그푸딩(dogfooding) — 자기 회사 제품을 내부에서 직접 사용하며 개선하는 방식.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 에이전트는 하네스(harness), 모델(model), 컨텍스트(context) 세 부분으로 본다 — “지능을 소유한다”는 것은 이 셋을 모두 통제할 수 있어야 한다는 뜻이다.
  2. 하네스의 핵심 임무는 적절한 시점에 적절한 컨텍스트를 모델에 넣는 것이다 — 단순 실행기가 아니라 컨텍스트 조립자다.
  3. 현재 대부분의 에이전트 구조는 “LLM이 루프를 돌며 도구를 호출하는 구조”다 — 단순하지만 범용성이 높다.
  4. LangChain은 최소한의 기본 하네스이고, DeepAgents는 Claude Code의 모델 독립적·범용 버전에 가깝다고 설명한다.
  5. 커스터마이징 지점은 모델 호출 전, 각 모델 호출 전후, 도구 호출 전후다 — 이를 미들웨어(middleware), 훅(hook), 플러그인(plugin)으로 구현한다.
  6. 요약(summarization)은 모델 호출 전에 들어간다 — 컨텍스트가 너무 길면 모델에 보내기 전에 요약한다.
  7. 컨텍스트 오프로딩(context offloading)은 큰 도구 호출 결과를 별도로 덜어내는 방식이다 — 도구 호출을 감싸는 미들웨어로 처리한다.
  8. 2023~2024년에는 모델이 약해서 인지 아키텍처(cognitive architecture)를 더 많이 썼다 — 지금도 예측 가능성과 제어가 필요한 업무에서는 여전히 유효하다.
  9. 기성 하네스 예시는 Claude Code, Claude Agent SDK, Codex다 — 각각 Anthropic 또는 OpenAI 모델과 강하게 연결되어 있다.
  10. 파일 편집(editing files)은 모델들이 강화학습(RL)으로 많이 학습한 영역이라 인디스트리뷰션 작업으로 본다 — 하지만 OpenAI와 Anthropic은 파일 편집 방식이 서로 다르다.
  11. DeepAgents에는 모델 프로필(model profiles)이 있다 — 사용하는 모델에 따라 파일 편집 도구 구현을 바꾼다.
  12. 평가(evals)는 조직 내부에서 “무엇이 좋은가”를 정의한다 — 외부 벤치마크만으로는 회사 업무 품질을 판단하기 어렵다.
  13. Harbor 작업(task)은 보통 샌드박스(sandbox)에서 실행된다 — 각 작업마다 Dockerfile로 환경을 정의할 수 있다.
  14. 평가할 때는 정확도뿐 아니라 지연 시간(latency), 토큰(tokens), 비용(cost)도 함께 봐야 한다.
  15. 에이전트 실패의 원인은 모델 자체보다 모델에 들어간 컨텍스트가 나쁜 경우가 더 많다고 본다.
  16. UX 설계를 잘하면 사용자가 명시적으로 좋아요/싫어요를 누르지 않아도 피드백을 얻을 수 있다.
  17. 모든 트레이스에 Opus 같은 고가 모델을 심판으로 돌리면 비용이 크게 늘어난다 — 그래서 작은 모델(SLM)을 파인튜닝하거나 코드 기반 평가를 섞는다.
  18. LangSmith Engine은 트레이스 위에서 동작하는 에이전트다 — 트레이스를 읽고 이슈 보드를 만들며 하네스·프롬프트 개선안을 제안한다.
  19. Engine은 자기 자신에 대해서도 실행된다 — Slack으로 자기 보고서를 보내며 내부적으로 도그푸딩한다.
  20. LangChain 팀은 Issue Bench라는 Harbor 형식 벤치마크를 만들어 Engine을 지속적으로 평가한다.
  21. Codex가 트레이스 분석을 위해 작은 스크립트를 많이 작성하는 방식이 성능에 좋았고, 이를 Engine에 반영하는 “codexification” 스프린트를 했다.
  22. 금융 서비스 고객은 DeepAgents 같은 자유도 높은 에이전트를 “너무 무섭다”고 느끼며, 더 제어 가능한 인지 아키텍처를 선호한다.

# 섹션 요지
1 에이전트의 3요소 모델, 컨텍스트, 하네스를 모두 소유해야 지능을 통제할 수 있다
2 하네스의 역할 적절한 정보를 모델에 넣고 도구 호출과 외부 시스템을 조율한다
3 기본 루프와 미들웨어 LLM 루프에 훅·플러그인·미들웨어를 붙여 도메인에 맞춘다
4 인지 아키텍처 특수하고 통제 필요한 업무에서는 명시적 절차 설계가 여전히 중요하다
5 자체 하네스 판단 기준 작업이 모델 훈련 분포에서 멀어질수록 커스텀 하네스가 필요하다
6 평가와 관측성 벤치마크와 트레이스가 있어야 개선 여부를 알 수 있다
7 데이터 플라이휠 실제 사용 기록을 선별해 하네스·모델·컨텍스트 개선에 쓴다
8 LangSmith Engine 트레이스를 분석해 이슈와 개선안을 자동으로 찾는 에이전트다
9 Q&A 하네스는 일부 수렴하겠지만, 도메인별로 갈라질 가능성도 크다

1. 에이전트는 모델만으로 이루어지지 않는다

해리슨 체이스는 에이전트(agent)를 세 가지 요소로 나눈다.

  1. 모델(model)
  2. 컨텍스트(context)
  3. 하네스(harness)

여기서 “자기 지능을 소유한다”는 말은 단순히 오픈소스 모델을 쓰거나 모델을 직접 호스팅한다는 뜻만이 아니다. 모델을 바꿀 수 있어야 하고, 에이전트가 참조하는 기억·지식·대화 기록을 소유해야 하며, 모델을 어떤 흐름으로 실행할지 정하는 하네스도 통제할 수 있어야 한다.

모델 측면에서는 과거의 “클라우드 독립성(cloud agnostic)”과 비슷한 문제가 생긴다. 특정 클라우드에 종속되지 않으려 했던 것처럼, 이제는 특정 모델 제공사에 묶이지 않고 필요할 때 가장 좋은 모델로 전환할 수 있어야 한다.

컨텍스트 측면에서는 에이전트가 쓰는 메모리(memory), 의미 지식(semantic knowledge), 이전 대화(previous conversations)를 회사가 소유해야 한다. 그래야 개인화와 업무 맥락 반영이 가능하다.

2. 하네스는 컨텍스트를 모델에 공급하는 오케스트레이터다

하네스(harness)의 핵심 역할은 적절한 시점에 적절한 컨텍스트를 모델에 가져다주는 것이다.

에이전트는 외부 시스템과 상호작용한다. 예를 들어 파일 시스템을 읽고, API를 호출하고, 데이터베이스를 조회하고, 도구를 실행한다. 이런 외부 시스템은 다시 새로운 정보를 만들어낸다. 이 정보는 다음 모델 호출의 컨텍스트로 들어간다.

따라서 하네스는 다음을 조율한다.

  • 고정 컨텍스트(fixed context)
  • 동적 컨텍스트(dynamic context)
  • 컨텍스트 윈도우(context window)에 넣을 정보
  • 도구 호출(tool call)
  • 도구 결과 관찰(observation)
  • 다음 LLM 호출

즉, 하네스는 LLM을 그냥 부르는 코드가 아니라 에이전트의 실행 환경과 흐름을 관리하는 구조다.

3. 대부분의 에이전트는 단순한 코어 루프에서 출발한다

오늘날 대부분의 에이전트는 기본적으로 다음 구조를 따른다.

  1. 사용자의 요청이 들어온다.
  2. LLM이 응답을 생성한다.
  3. 응답 안에 도구 호출이 있으면 도구를 실행한다.
  4. 도구 실행 결과를 다시 LLM에 전달한다.
  5. 이 과정을 반복한다.

화자는 이것을 “LLM이 루프를 돌면서 도구를 호출하는 구조”라고 설명한다. 단순하지만 매우 일반적인 구조라서 거의 모든 에이전트의 기반이 된다.

LangChain은 이 기본 구조에 가까운 최소 하네스다. 반면 DeepAgents는 Claude Code와 비슷하지만 특정 모델에 종속되지 않는 더 범용적인 하네스로 설명된다. DeepAgents는 파일 시스템, 스킬(skills), 서브에이전트(subagents) 같은 기능을 추가로 가진다.

4. 미들웨어로 에이전트 루프를 커스터마이징한다

기본 루프는 그대로 두되, 여러 지점에 작은 로직을 끼워 넣을 수 있다. 화자는 이를 미들웨어(middleware)라고 부른다.

삽입 가능한 지점은 다음과 같다.

  • 에이전트 호출 전
  • 각 모델 호출 전
  • 모델 호출을 감싸는 부분
  • 도구 호출 전후
  • 도구 결과를 모델에 다시 넣기 전

예를 들어 컨텍스트가 너무 길어지면 모델 호출 전에 요약(summarization)을 넣을 수 있다. 큰 도구 호출 결과가 나오면 컨텍스트 오프로딩(context offloading)을 통해 전체를 모델에 넣지 않고 별도로 처리할 수 있다.

코딩 에이전트에서 말하는 훅(hook), 플러그인(plugin)도 본질적으로 같은 개념이다. 기본 루프는 유지하면서 특정 시점에 기능을 추가하는 방식이다.

5. 인지 아키텍처는 여전히 필요하다

2023~2024년에는 모델이 지금보다 약했기 때문에, 에이전트를 만들 때 명시적인 인지 아키텍처(cognitive architecture)를 많이 설계했다.

예를 들어 딥 리서치(deep research) 에이전트라면 다음처럼 흐름을 정할 수 있다.

  1. 하위 질문 생성
  2. 질문을 여러 갈래로 분기
  3. 각각 조사 실행
  4. 결과 통합

코드 리뷰 봇도 마찬가지로 “파일 확인 → 변경점 분석 → 위험 지점 판단 → 리뷰 작성” 같은 고정 절차를 가질 수 있다.

요즘은 많은 부분이 일반 하네스 안으로 흡수되었지만, 특정 업무에서는 여전히 명시적 절차 설계가 필요하다. 특히 예측 가능성(predictability)과 통제(control)가 중요한 금융, 법률, 규제 산업에서는 자유롭게 움직이는 에이전트보다 제한된 인지 아키텍처를 선호할 수 있다.

6. 자체 하네스를 만들지, 기성 하네스를 쓸지 판단하는 기준

화자의 핵심 기준은 작업이 모델의 훈련 분포 안에 있는가다.

  • 인디스트리뷰션(in-distribution): 모델이 많이 학습했고 익숙한 작업
  • 아웃오브디스트리뷰션(out-of-distribution): 모델이 덜 익숙한 특수 업무

작업이 모델이 잘 학습한 범위에 있으면 Claude Code, Claude Agent SDK, Codex 같은 기성 하네스가 잘 작동한다. 반대로 회사 고유 업무, 법률 AI, 금융 AI처럼 특수한 도메인으로 갈수록 자체 하네스를 조정하거나 만들어야 한다.

흥미로운 점은 큰 작업은 아웃오브디스트리뷰션이어도, 그 안의 작은 작업은 인디스트리뷰션일 수 있다는 것이다. 예를 들어 법률 AI 전체는 특수 업무지만, 파일 편집(editing files)은 모델들이 강화학습(RL)을 통해 많이 배운 작업이다.

그래서 전체 하네스는 커스텀하더라도, 파일 편집 같은 하위 기능은 모델이 잘하는 방식을 따라가는 것이 좋다. DeepAgents는 이를 위해 모델 프로필(model profiles)을 두고, 사용하는 모델에 따라 파일 편집 도구 구현을 바꾼다.

7. 평가와 관측성이 있어야 에이전트를 개선할 수 있다

에이전트는 모델, 하네스, 컨텍스트가 함께 작동한다. 따라서 성능이 좋아졌는지 나빠졌는지 알려면 평가(evals)와 관측성(observability)이 필요하다.

화자는 Satya의 글에서 세 가지 문장을 인용한다.

  1. 사설 평가(private evals)를 만들어라. 평가는 조직 내부에서 무엇이 좋은지를 정의한다.
  2. 조직의 메모리, 트레이스, 피드백, 의사결정, 기관 맥락을 소유하라.
  3. 지속 학습 루프를 만들어 AI 투자가 회사 가치로 복리처럼 쌓이게 하라.

평가는 단순 점수표가 아니라, 회사가 원하는 결과의 기준이다. 평가 데이터셋이 있어야 하네스를 바꿨을 때 좋아졌는지, 모델을 바꿨을 때 비용 대비 성능이 나아졌는지 판단할 수 있다.

8. Harbor는 에이전트 벤치마크를 실행하는 도구다

Harbor는 오픈소스 평가 실행기(eval runner)다. TerminalBench2 제작자들이 만들었고, 코딩 에이전트뿐 아니라 여러 도메인에서 사용되고 있다.

Harbor의 기본 구조는 간단하다.

  • 데이터셋(dataset)에 여러 작업(task)이 들어 있다.
  • 에이전트를 각 작업에 대해 실행한다.
  • 보통 각 작업은 샌드박스(sandbox)에서 실행된다.
  • 작업마다 환경(environment), 정답 또는 기준 솔루션(solution), 테스트(tests), 지시문(instruction.md)이 있다.
  • 테스트는 유닛 테스트, 코드 실행, LLM 심판, 에이전트 심판 등으로 구성할 수 있다.

이렇게 하면 여러 모델과 여러 하네스를 같은 작업에 대해 비교할 수 있다. 평가할 때는 정확도만 볼 것이 아니라 지연 시간(latency), 토큰(tokens), 비용(cost)도 함께 추적해야 한다.

9. 관측성은 실패 원인을 찾는 핵심 도구다

에이전트가 실패할 때 겉으로는 “모델이 틀렸다”고 보이지만, 실제 원인은 두 가지 중 하나다.

  1. 모델 자체가 부족했다.
  2. 모델에 들어간 컨텍스트가 부족하거나 잘못되었다.

화자는 두 번째가 더 흔하다고 본다. 그래서 관측성이 중요하다.

좋은 관측성 도구는 다음을 보여줘야 한다.

  • 모델에 어떤 컨텍스트가 들어갔는가
  • 그 컨텍스트가 어떤 단계에서 쌓였는가
  • 어떤 도구가 호출되었는가
  • 도구 결과가 어떻게 다음 호출에 반영되었는가
  • 전체 메시지 궤적(trajectory)이 어떻게 이어졌는가

Claude Code 같은 에이전트에서 사용자가 보는 것은 메시지 흐름이지만, 디버깅하려면 그 아래의 전체 트레이스(trace)를 볼 수 있어야 한다.

10. 데이터 플라이휠: 트레이스가 개선으로 이어진다

화자는 에이전트 개선 과정을 데이터 플라이휠(data flywheel)로 설명한다.

  1. 에이전트를 만든다.
  2. 실제로 실행한다.
  3. 많은 트레이스를 수집한다.
  4. 트레이스 데이터를 선별(curate)한다.
  5. 그 데이터로 실험한다.
  6. 하네스, 모델, 컨텍스트를 개선한다.

이 과정에서 피드백(feedback)이 중요하다. 사용자가 명시적으로 좋아요/싫어요를 누르지 않더라도, UX를 잘 설계하면 피드백을 얻을 수 있다. 예를 들어 사용자가 결과를 수정했는지, 다시 질문했는지, 특정 제안을 채택했는지 같은 행동이 간접 피드백이 될 수 있다.

또한 온라인 평가자(online evaluator)를 돌려 트레이스를 자동 평가할 수 있다. 다만 모든 트레이스에 비싼 모델을 심판으로 쓰면 비용이 커진다. 그래서 작은 언어 모델(SLM)을 파인튜닝하거나, 간단한 평가는 코드로 처리할 수 있다.

11. LangSmith Engine은 트레이스 위에서 작동하는 개선 에이전트다

LangSmith Engine은 트레이스를 분석해 문제를 찾고 개선안을 제시하는 에이전트다.

동작 방식은 다음과 같다.

  • LangSmith에 들어오는 트레이스를 본다.
  • LangSmith CLI를 사용해 피드백과 조건으로 트레이스를 필터링한다.
  • 서브에이전트와 프롬프트를 활용해 공통 문제를 찾는다.
  • 이슈 보드(issue board)를 만든다.
  • 관련 트레이스를 근거로 연결한다.
  • 프롬프트, 컨텍스트, 하네스 코드 변경안을 제안한다.

화자는 이를 “에이전트 실행 → 트레이스 수집 → 패턴 발견 → 수정”이라는 단순하지만 중요한 루프를 자동화하려는 시도라고 설명한다.

12. Q&A: Engine 위에서 Engine을 실행하는가

질문자는 LangSmith Engine 자체도 에이전트라면, Engine을 Engine 위에서 실행해봤는지 묻는다.

해리슨은 그렇다고 답한다. Engine은 Slack과 연결되어 자기 자신에 대한 보고서를 보내며, LangChain 팀은 이를 내부적으로 도그푸딩(dogfooding)하고 있다.

또한 Engine을 위한 Issue Bench라는 Harbor 형식 벤치마크도 만들었다. 이를 통해 DeepAgents, Codex, Claude Code 같은 여러 하네스를 비교했다.

흥미로운 발견은 Codex가 트레이스를 분석할 때 작은 스크립트를 많이 만들어 실행했고, 이 방식이 좋은 성능을 냈다는 점이다. LangChain 팀은 이 학습을 Engine 하네스에 반영하는 “codexification” 작업을 했다.

13. Q&A: 하네스는 하나로 수렴할까, 도메인별로 갈라질까

해리슨은 솔직한 답은 “모르겠다”고 말한다.

다만 현재 보이는 경향은 있다.

  • 범용 하네스는 기본 작업을 처리할 만큼 충분히 좋아지고 있다.
  • 시작할 때는 DeepAgents, Codex, Claude Code 같은 기성 하네스를 쓰는 것이 좋다.
  • 작업이 특수해질수록 커스텀 하네스가 필요하다.
  • 예측 가능성과 통제가 필요하면 인지 아키텍처가 필요하다.
  • 중간 단계로 훅(hook), 미들웨어(middleware)를 사용해 일부만 조정할 수 있다.

코딩 영역에서는 모델 연구소들이 모두 잘하는 방향으로 수렴할 수 있다. 하지만 파일 편집 방식처럼 작은 차이는 남아 있고, 특정 연구소가 바이오(bio) 같은 특정 영역에 집중하면 하네스도 그 도메인에 맞게 갈라질 수 있다.

결론은 빠르게 변하는 분야이므로, 무엇이 좋은지 판단하려면 평가와 관측성이 필수라는 것이다.

교정 전사 (한국어)

전체 전사 펼치기

저는 LangChain의 공동창업자이자 CEO인 해리슨입니다.

오늘은 “자기 지능을 소유한다”는 맥락에서 평가(evals)와 하네스(harness)에 대해 이야기하려고 합니다. 우리가 지능을 말할 때 보통은 에이전트(agent)를 이야기합니다. 그렇다면 에이전트는 무엇으로 이루어질까요?

LangChain에서는 에이전트가 크게 세 부분으로 구성된다고 봅니다. 하네스가 모델(model)과 컨텍스트(context)를 오케스트레이션(orchestration)하는 구조입니다. 지능을 소유하려면 이 세 부분을 모두 소유해야 합니다.

모델 소유에 대해서는 길게 말하지 않겠습니다. 앞서 Fireworks의 Lynn이 오픈 웨이트 모델(open-weight models)에 대해 이야기했습니다. 여기에는 모델을 전환할 수 있는 능력도 포함됩니다. 과거에 클라우드 독립성(cloud agnostic)이라는 개념이 있었듯이, 이제는 모델에 대해서도 같은 문제가 있습니다. 특정 모델에 종속되지 않기 위해서도, 더 좋은 모델이 나왔을 때 쓰기 위해서도 전환 가능성이 필요합니다.

컨텍스트도 소유해야 합니다. 에이전트가 사용하는 기억(memory), 의미 지식(semantic knowledge), 이전 대화(previous conversations) 등이 모두 포함됩니다. 이런 정보는 에이전트를 개인화하고 올바른 방향으로 안내하는 데 도움이 됩니다.

마지막이 하네스입니다. 제가 집중하고 싶은 부분도 이것입니다. 하네스를 소유한다는 것은 무엇일까요? 하네스의 주된 일은 적절한 시점에 컨텍스트를 모델로 가져오는 것입니다. 고정 컨텍스트와 동적 컨텍스트를 조율하고, 모델의 컨텍스트 윈도우(context window)에 넣고, 모델의 응답을 받은 뒤 그 결과로 무언가를 합니다.

에이전트는 일을 수행하기 위해 여러 작업을 해야 합니다. 도메인 특화 작업도 많고, 외부 시스템과 상호작용해야 합니다. 외부 시스템과 상호작용하면 다시 새로운 컨텍스트가 생기고, 이것이 에이전트 루프 안으로 들어옵니다. 하네스는 이 전체 과정을 조율합니다.

사람들이 에이전트를 말할 때 실제로는 대개 LLM이 루프를 돌며 도구를 호출하는 구조를 말합니다. 요청이 들어오고, LLM이 생성을 하고, 그 생성 결과에 도구 호출이 포함될 수 있습니다. 도구 호출이 있으면 도구를 실행하고, 그 관찰 결과를 다시 LLM에 넘깁니다. 이것이 오늘날 거의 모든 에이전트의 핵심 구조입니다.

하지만 각 하네스는 조금씩 다릅니다. 기본 코어 루프가 있고, 특정 하네스에서는 여러 단계에 기능을 추가할 수 있습니다. LangChain은 아주 기본적이고 최소한의 하네스입니다. DeepAgents는 Claude Code의 모델 독립적이고 범용적인 버전에 가깝습니다. 파일 시스템에 연결하고, 스킬(skills), 서브에이전트(subagents)를 갖고 있습니다. 이 역시 단순한 하네스 위에 만들어졌지만 여러 조정 지점을 사용해 확장됩니다.

에이전트가 호출되기 전, 각 모델 호출 전, 모델 호출을 감싸는 부분, 도구 호출을 감싸는 부분에 특정 코드를 실행할 수 있습니다. 이런 작은 구조를 미들웨어(middleware)라고 부릅니다. 코딩 에이전트에서 말하는 훅(hooks)이나 플러그인(plugins)도 본질적으로 같은 개념입니다. 기본 루프의 여러 지점에 작은 확장 지점을 추가해 커스터마이징하는 것입니다.

미들웨어를 통해 샌드박스(sandbox), 파일 시스템(file system), 서브에이전트, 메모리(memory), 요약(summarization)을 붙일 수 있습니다. 예를 들어 요약은 모델 호출 전에 들어갑니다. 컨텍스트가 너무 길면 모델을 호출하기 전에 요약합니다. 컨텍스트 오프로딩(context offloading)은 큰 도구 호출 결과를 별도로 덜어내는 방식이고, 도구 호출을 감싸는 형태로 들어갑니다.

핵심은 에이전트에는 단순하고 일반적인 구조가 있으며, 더 고급 하네스도 결국 이 루프를 돌면서 여러 기능을 추가한다는 점입니다. 자체 하네스를 만들거나 커스터마이징할 때는 이런 삽입 지점을 생각하면 됩니다.

다른 방식은 더 명시적인 인지 아키텍처(cognitive architecture)를 두는 것입니다. 2023년과 2024년에는 모델이 루프만으로 충분히 잘 작동하지 않았기 때문에 이런 방식이 많았습니다. 딥 리서치 예시에서는 하위 질문을 만들고, 여러 갈래로 나누어 실행한 뒤 결과를 합칩니다. 코드 리뷰 봇도 매우 특화된 단계를 가집니다.

지금은 이런 것 중 많은 부분이 하네스 안으로 들어갔지만, 특정 흐름에서는 여전히 인지 아키텍처가 필요합니다. 그래서 우리는 보통 일반 하네스로 시작하라고 권합니다. 시작이 쉽고 가치를 빠르게 얻을 수 있습니다. 이후 탁월하게 만들고 싶은 사용 사례가 좁혀지면 게이트(gates)와 체크(checks)를 추가해 특정 방향으로 안내할 수 있습니다.

자주 받는 질문은 자체 하네스를 만들지, 기성 하네스를 쓸지입니다. 기성 하네스에는 Claude Code, Claude Agent SDK, Codex 같은 것들이 있습니다. 각각 Anthropic 모델이나 OpenAI 모델과 함께 동작합니다.

제 답은 보통 이렇습니다. 모델이 훈련받은 분포 안에 있는 작업, 즉 인디스트리뷰션(in-distribution)에 가까울수록 기성 하네스가 잘 작동합니다. 반대로 분포 밖(out-of-distribution)으로 갈수록 하네스를 조정하고 싶어질 것입니다.

예를 들어 법률 AI는 큰 작업으로 보면 모델에게 낯선 영역일 수 있습니다. 하지만 그 안의 파일 편집(editing files)은 주요 모델들이 강화학습(RL)으로 많이 배운 작업입니다. OpenAI와 Claude 모델은 각자의 하네스에서 파일을 서로 다른 방식으로 편집하도록 학습되었습니다. 그래서 전체 업무는 커스텀 하네스가 필요하더라도, 파일 편집 도구는 해당 모델이 익숙한 방식에 가깝게 유지하는 것이 좋습니다.

DeepAgents에는 모델 프로필(model profiles)이라는 개념이 있습니다. 파일 편집처럼 모델 분포 안에 있는 기능은 사용하는 모델에 따라 구현을 바꿉니다. 큰 작업에는 커스텀 하네스를 쓰되, 작은 인디스트리뷰션 기능은 모델 계층에 가깝게 유지하는 예입니다.

두 번째 주제는 평가(evals)와 관측성(observability)입니다. 모델, 하네스, 컨텍스트를 실험할 때 시스템 내부에서 무슨 일이 일어나는지 알아야 하고, 평가할 수 있어야 합니다. 이것은 커스텀 하네스뿐 아니라 커스텀 모델에도 유용합니다.

Satya가 쓴 글에서 세 문장이 인상적이었습니다. 첫째, 사설 평가(private evals)를 만들라는 것입니다. 평가는 조직 내부에서 무엇이 좋은지를 정의합니다. 둘째, 조직의 메모리, 트레이스, 피드백, 의사결정, 기관 맥락을 소유하라는 것입니다. 셋째, 지속적인 학습 루프를 만들어 AI 투자가 회사 가치를 복리처럼 쌓게 하라는 것입니다.

미션 크리티컬한 에이전트를 만드는 회사는 결국 그 에이전트에 대한 벤치마크를 만들게 됩니다. 벤치마크는 회귀(regression)를 잡고, 하네스나 모델을 조정하며 성능을 끌어올리는 데 쓰입니다.

Harbor는 이런 벤치마크를 정의하고 실행하는 오픈소스 평가 실행기입니다. TerminalBench2 제작자들이 만들었고, 여러 도메인에서 인기를 얻고 있습니다. Harbor를 사용하면 서로 다른 에이전트 하네스, 모델, 추론 강도(reasoning effort)를 같은 작업에서 비교할 수 있습니다.

Harbor의 핵심은 데이터셋에 있는 여러 작업을 에이전트에게 실행시키는 것입니다. 작업은 대개 샌드박스에서 실행되며, 각 작업은 환경(environment)을 가집니다. Dockerfile로 환경을 정의하고 그 안에서 실행합니다. 솔루션(solution)은 일종의 골든 솔루션이고, 테스트(tests)는 에이전트 실행을 검증하는 부분입니다. 테스트는 코드 실행, 유닛 테스트, LLM 심판, 에이전트 심판 등 무엇이든 될 수 있습니다. instruction.md는 에이전트에게 주어지는 프롬프트입니다.

이런 실험을 하면 여러 결과를 비교할 수 있습니다. LangSmith는 평가와 관측성을 위한 플랫폼입니다. Harbor와 통합되어 있고, 피드백 점수, 지연 시간(latency), 토큰(tokens)을 추적할 수 있습니다. 에이전트를 벤치마킹할 때는 정확도뿐 아니라 지연 시간과 비용도 중요합니다.

관측성은 기본적으로 들리지만 에이전트에서는 매우 중요하고 과소평가되어 있습니다. 에이전트가 실패하는 이유는 LLM 호출이 잘못되기 때문입니다. 그 이유는 두 가지입니다. 모델이 충분히 좋지 않거나, LLM이 받은 컨텍스트가 충분히 좋지 않은 것입니다. 저는 두 번째가 더 자주 문제를 만든다고 봅니다.

그래서 모델의 컨텍스트 윈도우에 무엇이 들어갔는지, 그 컨텍스트가 어떻게 쌓였는지, 어떤 단계와 도구가 실행되었는지 관찰할 수 있어야 합니다. 에이전트의 경로는 메시지 궤적(trajectory) 형태로 나타납니다. 사용자가 메시지를 보내고, 에이전트가 도구를 호출하고, 다시 응답하는 흐름입니다. 하지만 이것만으로는 충분히 디버깅할 수 없어서 전체 트레이스(trace)를 봐야 합니다.

평가와 관측성은 데이터 플라이휠(data flywheel)을 만듭니다. 에이전트를 만들고, 실행하고, 트레이스를 수집하고, 데이터를 선별한 뒤, 그 데이터로 실험합니다. 피드백이 특히 중요합니다. 사용자가 명시적으로 좋아요나 싫어요를 누르지 않더라도, UX 설계를 잘하면 간접 피드백을 얻을 수 있습니다.

또 합성 피드백(synthetic feedback)을 얻을 수도 있습니다. 온라인 평가자(online evaluators)를 트레이스 위에서 실행해 판단하게 하는 방식입니다. 모든 트레이스에 Opus 같은 비싼 모델을 심판으로 쓰면 비용이 커지기 때문에, 작은 언어 모델(SLM)을 파인튜닝하거나, 기성 모델에 커스텀 프롬프트를 쓰거나, 간단한 것은 코드로 평가할 수 있습니다.

이 데이터로는 하네스, 모델, 컨텍스트 중 어느 부분이든 업데이트할 수 있습니다. 하네스 엔지니어링(harness engineering), 파인튜닝(fine-tuning), 메모리(memory) 개선이 모두 가능합니다. LangChain이 특히 많이 생각하는 부분은 하네스 엔지니어링입니다.

LangSmith Engine은 이런 작업을 자동화하려는 시도입니다. 트레이스를 보고, 데이터를 선별하고, 실험을 실행하고, 세 가지 구성 요소 중 무엇을 고칠지 제안하는 에이전트입니다. 데모에서는 LangSmith 안의 Engine 탭을 보여줍니다. Engine은 백그라운드에서 실행되며 이슈 보드(issue board)를 만듭니다.

내부적으로는 LangSmith CLI에 접근할 수 있는 코딩 에이전트입니다. 피드백 등으로 트레이스를 필터링하고, 큰 프롬프트와 서브에이전트를 통해 데이터를 탐색하며 공통 문제를 찾습니다. 그러고 나서 이슈를 만들고, 근거 트레이스를 연결하며, 프롬프트나 컨텍스트, 하네스 코드 변경안을 제안합니다.

이것은 “에이전트 실행 → 트레이스 수집 → 패턴 발견 → 수정”이라는 단순한 루프를 자동화하려는 것입니다.

질문으로, Engine 자체도 에이전트인데 Engine을 Engine 위에서 실행해봤는지 묻는 내용이 나왔습니다. 답은 그렇다는 것입니다. Engine은 Slack과도 연결되어 자기 자신에 대한 보고서를 보냅니다. 이것이 내부 도그푸딩(dogfooding) 방식입니다.

또한 Engine을 위한 Issue Bench라는 Harbor 형식 벤치마크를 만들었습니다. 여러 모델과 하네스를 계속 벤치마킹합니다. DeepAgents, Codex, Claude Code를 비교했을 때 Codex가 작은 스크립트를 많이 작성해 트레이스에 대해 실행하는 흥미로운 방식을 보였고, 이것이 성능에 도움이 되었습니다. 그래서 그 학습을 Engine 하네스에 반영하는 “codexification” 작업을 했습니다.

마지막 질문은 하네스가 하나로 수렴할지, 회사마다 최적화된 방식으로 갈라질지였습니다. 솔직한 답은 모르겠다는 것입니다. 다만 범용 하네스는 기본 작업에 충분히 좋아졌습니다. 시작할 때는 DeepAgents, Codex, Claude Code 같은 기성 하네스를 쓰는 것을 권합니다.

하지만 업무가 분포 밖으로 갈수록 커스텀 하네스가 필요합니다. 극단적으로는 특정 업무에 집중한 완전한 인지 아키텍처를 만들 수도 있습니다. 예측 가능성과 통제가 필요한 금융 서비스 고객들은 자유도가 높은 에이전트를 부담스러워하고, 더 통제 가능한 구조를 선호합니다.

따라서 이것은 스펙트럼입니다. 한쪽 끝에는 기성 하네스가 있고, 중간에는 훅과 미들웨어가 있으며, 다른 끝에는 완전한 커스텀 인지 아키텍처가 있습니다. 모델 연구소들은 코딩 같은 영역에서는 어느 정도 수렴할 수 있지만, 파일 편집 방식 같은 작은 차이도 존재합니다. 특정 연구소가 바이오 같은 분야에 깊게 들어가면 그 분야의 하네스는 또 달라질 수 있습니다.

이 분야는 빠르게 움직이고 있습니다. 그래서 평가와 관측성이 중요합니다. 그래야 이 모든 차이를 측정할 수 있습니다.
