핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
ADR (Architecture Decision Record) 아키텍처 결정의 "이유"가 사라지면 팀도 LLM도 재발명한다 "왜 이렇게 됐지?" 문서
PRD (Product Requirements Document) 기능의 목적·사용자 여정을 가볍게 남겨야 AI도 맥락을 이해한다 기능 존재 이유 문서
BDD / Cucumber 사람이 읽고 실행까지 가능한 스펙 — spec-driven의 검증 공백을 닫는다 실행 가능한 요구사항
Git hooks + CI 루프 에이전트가 규칙을 게으르게 우회하면 커밋 단계에서 차단 자동화 강제 실행
아키텍처 모듈 경계 강제 "N+1 쿼리 불가", "DB 접근 금지 레이어" 등을 도구로 막아야 실수가 없다 방지 > 발견
디자인 시스템 + 패턴 라이브러리 AI가 만드는 UI의 일관성은 컴포넌트 규칙·프리뷰 스니펫으로만 유지 가능 AI UI 일관성의 유일한 길
Context compact 허용 전략 컨텍스트가 압축돼도 중요 문서를 다시 조회하면 된다 — 긴 세션도 OK 컴팩트 = 정상

내가 모를 만한 것 / 처음 보는 것

  • ADR (Architecture Decision Record): 아키텍처 결정의 이유·방법·적용 범위를 텍스트로 기록. 특정 포맷 없음 — 파일 1개가 곧 1개 결정.
  • BDD (Behavior Driven Development): 동작을 인간 언어로 기술하고 그것을 직접 실행 가능한 테스트로 연결. 오래된 기법이지만 AI 시대에 재유효.
  • Cucumber: BDD를 구현하는 프레임워크. Feature 파일에 시나리오 작성 → 파서가 step으로 변환 → 코드 실행.
  • Spec-driven development vs BDD: spec(MD 문서)은 사람이 읽지만 검증이 없다 → BDD는 그 스펙이 곧 테스트가 돼 검증 루프를 닫는다.
  • Pac-27: 화자가 Safe Intelligence와 함께 출시한 에이전트 테스트 제품 (영상 발표 전날 릴리즈).
  • N+1 쿼리: 렌더링 템플릿에서 DB 직접 호출이 발생하는 패턴 — 모듈 경계 강제로 원천 차단 가능.
  • Import 경계 강제: 린터로 특정 모듈에서 특정 모듈로의 import를 금지 (예: BDD 테스트 스위트 → DB 접근 모듈 import 불가).

화자의 디테일 (놓치기 쉬운 포인트)

  1. 화자는 Safe Intelligence에서 에이전트 테스트 제품 Pac-27을 영상 발표 하루 전에 릴리즈했다고 직접 언급.
  2. Microsoft, Red Hat 포함 10년을 단일 제품에서 일한 경험 — "일관성 문제는 모든 조직에서 봤다"는 주장의 근거.
  3. 다섯 마리 원숭이 실험 비유: 이유를 모르면서도 규칙을 따름 = 맥락 없는 코드베이스에서 팀도 LLM도 같은 문제 겪음.

  8. 컨텍스트 컴팩트에 대한 태도: "한 세션에 20~50번 compact가 일어나도 괜찮다. 중요한 것은 살아남고 에이전트는 다시 조회한다."
  9. AI 코드로 만든 UI의 일관성은 "AI 이전에도, 이후에도 디자인 시스템·패턴 라이브러리가 유일한 방법"이라고 단언.
  10. 코드 스타일 토론(탭 vs 스페이스)에 대한 입장: "이런 것에 쓸 시간 없다. 자동화로 강제. 코드 리뷰는 고수준 개념만."

# 섹션 요지
1 문제 제기 사람도 LLM도 맥락 제한이 있다 — 결정의 이유가 사라진다
2 ADR 아키텍처 결정 이유·강제 방법을 텍스트로 기록, 약 50개로 커버
3 PRD 기능의 목적·사용자 여정을 가볍게 기록, 6주 후의 나를 위해
4 BDD / Cucumber 실행 가능한 스펙으로 검증 루프를 닫는다
5 디자인 시스템 컴포넌트·패턴·프리뷰로 AI UI 일관성 유지
6 강제 루프 git hooks + CI + linter로 에이전트가 규칙 우회 불가
7 스킬 분리 루프는 동일, focus가 바뀜 — ADR/PRD/UI/Test/결정 기록 스킬
8 컨텍스트 전략 compact 허용, 중요 문서 재조회 → 장시간 자율 세션 가능

1. 왜 의사결정 기록이 필요한가

화자는 "다섯 마리 원숭이" 실험으로 시작한다. 원숭이들은 이유를 모르면서도 규칙을 따른다. 코드베이스도 마찬가지다. 창업 엔지니어가 없으면 "왜 이 플로우가 이렇게 됐지?", "이 코드가 왜 이 모양이지?"를 아무도 모른다.

사람은 잊고, LLM은 컨텍스트가 압축되며, 팀원은 떠난다. AI 시대에는 이 문제가 훨씬 빨리 찾아온다.

2. ADR — 아키텍처 결정 기록

ADR은 "무엇"이 아니라 "왜"와 "어떻게 강제할 것인가"를 기록한다.

  • 특정 포맷 없음. 텍스트 파일 1개 = 결정 1개.
  • 도구가 규칙을 위반한 코드를 발견하면 "이 규칙이 있다, 왜 존재하는지 ADR을 읽어라, 어떻게 고쳐라"를 에이전트에게 알려준다.
  • 파일 범위 지정 가능 (예: 특정 Python 파일·폴더에만 적용).
  • 화자 팀은 약 50개의 ADR로 제품 아키텍처 전체를 커버.

3. PRD — 제품 요구사항 문서

기능을 만들 때 "왜 이 기능이 존재하는가", "어떤 문제를 푸는가", "사용자가 앱을 어떻게 통과하는가(여정)"를 가볍게 기록.

  • 방대한 문서일 필요 없다. 문제 + 목표 + 여정 세 가지만.
  • AI 에이전트뿐 아니라 6주 후의 나 자신을 위한 기록이기도 하다.

4. BDD와 Cucumber — 실행 가능한 스펙

스펙 주도 개발의 미완성 고리: 마크다운으로 동작을 기술했지만, 실제로 그렇게 동작하는지 어떻게 아는가?

  • AI가 쓴 코드도 읽기 어렵지만 AI가 쓴 테스트는 더 읽기 어렵다.
  • BDD: 제품이 어떻게 동작해야 하는지를 인간 언어로 기술하는 중간 레이어.
  • Cucumber: 오래된 프레임워크지만 지금 다시 유효. Feature 파일 시나리오 → step → 코드 실행.
  • 리뷰 가능·실행 가능·읽기 가능. PRD·사용자 여정과 직접 연결 가능.
  • 규칙을 어떻게 쓸지는 팀 자유. 포맷 강제 없음.

5. 디자인 시스템 — AI UI의 일관성

AI로 만드는 UI의 일관성을 유지하는 것은 "AI 이전에도, 지금도 디자인 시스템과 패턴 라이브러리가 유일한 방법"이다.

  • 언어 정의: "primary button은 파란색, 이 모양, 이 크기."
  • 규칙 정의: "한 페이지에 primary button은 항상 하나만."
  • 컴포넌트·상태·색상 조합마다 프리뷰 스니펫 생성 → 에이전트도 볼 수 있음.
  • 코드처럼 작은 조각에서 큰 조각으로 조합·재사용. 인라인 스타일 금지 강제 가능.

6. 강제 루프 — git hooks + CI + linter

에이전트 작업 → git commit → hooks 실행 → CI 동일 태스크 → 위반 시 피드백 → 에이전트 ADR 조회 → 수정 반복
  • hooks와 CI는 동일 태스크: 에이전트가 로컬 hook을 건너뛰면 CI에서 차단.
  • 포함 항목: linting, formatting, type checking, 코드 중복, 아키텍처 검사, 문서 linting.
  • 모듈 import 경계 강제 예시:
  • BDD E2E 테스트 스위트 → DB 접근 모듈 import 불가 (브라우저 레이어만 사용 강제)
  • 렌더링 템플릿 → DB 직접 접근 불가 (N+1 쿼리 원천 차단)
  • 방지 > 발견: 문제를 찾는 게 아니라 구조적으로 발생 불가능하게 만드는 것.

7. 스킬 분리와 컨텍스트 전략

루프는 하나지만 focus가 다른 여러 스킬로 분리:

스킬 포커스
ADR 스킬 ADR 조회·적용 방법 안내
PRD 스킬 기능 맥락 파악
UI 루프 일부 검사 생략 + 브라우저 빠른 반복
Test 스킬 커버리지·파일 변경 기반 실행 범위 최소화
의사결정 기록 스킬 모델이 내린 결정을 나중에 리뷰할 수 있게 보존

컨텍스트 컴팩트 전략: "한 세션에 20~50번 compact가 일어나도 된다. 중요한 문서는 살아남고, 에이전트는 필요할 때 다시 찾는다. 그게 목표다."

전체 전사 펼치기

안녕하세요, 저는 Michal입니다. "사람과 AI 모두를 위한 의사결정 기록"에 오신 것을 환영합니다. 어제 Safe Intelligence 팀과 함께 에이전트를 테스트하는 새 제품 Pac-27을 출시했습니다. 그 전에는 Microsoft, Red Hat에서 일했고, 한 제품에서만 10년을 보냈습니다. AI와 함께 우리가 직면하는 일관성 문제와 "의사결정 기록"의 이야기는 제가 봐온 모든 제품에서 반복됩니다. 이 발표의 내용은 그 경험에서 정리한 것입니다. 발표 후 부스에서 만날 수 있습니다.

BDD, PRD, ADR — 약어가 많죠? 왜 이게 중요할까요? 끝에서부터 풀어보겠습니다. 이 이야기를 아실 겁니다. 도시 전설이 아니길 바랍니다. 과학자들이 원숭이 다섯 마리를 바나나가 달린 사다리가 있는 우리에 넣었습니다. 원숭이가 바나나를 가지러 올라가면 찬물 샤워를 줬습니다. 다른 원숭이들이 그 원숭이를 두들겨 팼습니다. 그 다음 원숭이를 한 마리씩 교체했고, 원래 원숭이는 하나도 남지 않았습니다. 그런데도 사다리에 오르려는 원숭이마다 두들겨 맞았습니다 — 이유도 모르면서.

사람과 LLM은 같은 문제를 겪습니다: 제한된 맥락. 사람은 잊습니다. LLM의 컨텍스트는 압축됩니다. 사람은 회사를 떠납니다. LLM은 메모리가 없습니다. 제품을 운영하다 보면 팀이 이런 질문을 하기 시작합니다: "왜 이 플로우가 있지?", "이 기능의 목표가 뭐였지?", "이 코드가 왜 이 모양이지?", "이게 어디에 속하는 거지?" 그리고 그 질문에 답해줄 창업 엔지니어가 없을 수 있습니다. 이 문제는 모든 조직에서 나타나고, AI 시대에는 훨씬 빨리 찾아옵니다.

ADR은 아키텍처 결정 기록(Architecture Decision Record)입니다. 왜 무언가를 하는지, 그리고 그것을 어떻게 강제할 것인지를 기록합니다. 특정 포맷이 필요한 건 아니고 개념입니다. 텍스트이므로 그 자체로 강제력은 없습니다. 강제하려면 별도 도구가 필요합니다. 하지만 그 도구가 "이게 규칙이다, 왜 이게 있는지, 어떻게 고쳐야 하는지"를 알려줍니다. 그러면 에이전트가 이 문서를 찾아가 이유를 읽고 더 많은 수정 정보를 얻습니다. 어떤 파일이나 폴더에 해당하는지도 정의할 수 있습니다. 그리고 코드 스니펫과 참조 문서로 예시를 보여줄 수 있습니다. 화자 팀에는 약 50개의 ADR이 있고 이것이 제품 아키텍처를 정의합니다.

PRD는 제품 요구사항 문서(Product Requirements Document)입니다. 더 가볍습니다. 기능을 만들 때 그 기능이 왜 존재하는지, 어떤 문제를 푸는지, 사용자가 앱을 통해 어떻게 상호작용하는지 — 앱을 통한 여정을 기술합니다. 매우 가벼워도 됩니다. 방대한 문서일 필요가 없습니다. 왜, 문제, 목표, 그것을 잇는 여정만 담으면 됩니다. AI 에이전트를 위한 것만이 아니라 6주 후의 당신 자신이 "왜 이걸 했지?"라고 물을 때를 위한 것이기도 합니다.

이제 BDD — 행동 주도 개발(Behavior Driven Development)입니다. 최근 스펙 주도 개발을 많이 봤을 텐데, 실제로 써보셨다면 저와 같은 고통을 겪으셨을 겁니다. 제품이 스펙을 실제로 따르는지 어떻게 검증하나요? 마크다운 문서에 동작 방식을 기술했는데, 실제로 그렇게 동작하는지 어떻게 알죠? AI 코드보다 읽기 힘든 것은 AI 테스트입니다.

그렇다면 제품이 어떻게 동작하는지를 인간 언어로 기술하는 중간 레이어가 있다면? BDD는 새롭고 반짝이는 건 아닙니다. 하지만 실행 가능하고 읽을 수 있습니다. Cucumber를 소개합니다. 거의 잊혀졌다가 갑자기 다시 유용해진 도구입니다. 평균적인 테스트보다 리뷰하기 훨씬 쉽습니다. 시나리오를 PRD와 핵심 사용자 여정에 직접 연결할 수 있습니다. 읽을 수 있고, 실행 가능하고, 스펙 주도 개발이 열어둔 루프를 닫습니다.

이 규칙들, 이 스펙들은 나중에 step으로 파싱되어 코드로 실행됩니다. 하지만 당신이 이것을 쓰고 읽을 수 있습니다. 리뷰할 수 있고 이해할 수 있습니다. 언어는 자유입니다. 강제되지 않습니다. Feature를 쓰는 방법도 여러 가지입니다. 그게 다입니다. 하지만 이것들은 앱을 어떻게 통과해야 하는지, 왜 이 기능이 존재하는지, 어떻게 실행되는지를 기술합니다. 마찬가지로 왜 이런 것들이 존재하는지에 대한 모든 문서를 역참조할 수 있습니다.

보너스로, 에이전트로 일관된 UI를 만드는 것은 또 다른 차원의 어려움입니다. 디자인 시스템과 패턴 라이브러리가 일관된 UI를 만드는 방법입니다. AI 이전에도 방법이었고 지금도 그렇습니다. 언어를 정의하세요. 예를 들어, primary button은 이렇고 저렇습니다. 파란색입니다. 이 모양입니다. 이 색상입니다. 이 크기입니다. 그리고 규칙을 정하세요: 한 페이지에 한 번에 하나의 primary button만 보여야 한다. 그런 다음 이 규칙을 강제할 수 있습니다. 마찬가지로 컴포넌트와 패턴을 정의하세요. 예를 들어 버튼의 여러 색상과 여러 상태가 있다면, 컴포넌트를 정의하고 프리뷰를 만드세요. 동작 방식을 보여주고 프리뷰 스니펫을 만드세요. 실제로 볼 수 있고 에이전트도 볼 수 있습니다.

그러면 리뷰하면서 "이것이 내가 정한 원칙을 따르는가, 시각적으로 맞는가"를 확인할 수 있습니다. 코드처럼 작은 조각에서 큰 조각으로 조합하고 재사용합니다. 그렇게 하지 않으면 코드처럼 카오스가 됩니다.

좋습니다, 멋진 아이디어들이네요. 그런데 실제로 어떻게 강제해서 팀과 에이전트가 따르게 할까요? 어떻게 일관성을 유지할까요? 루프로 합니다. 클로징 루프, 강화 루프, 하네스라는 말을 들어보셨을 겁니다. 에이전트에게 규칙이 있다는 것을 어떻게 상기시키고 따르게 할까요?

저희 루프는 간단합니다: git hooks, 스킬, CI, linter, 그리고 다양한 검사들. 에이전트의 목표는 pull request를 전달하는 것이고, 그러려면 git을 써야 합니다. 그래서 git hooks를 사용합니다. 사전 정의된 태스크를 실행하고, 이 태스크들은 나중에 CI에서도 동일하게 실행됩니다. 에이전트가 게을러져서 실행하고 싶지 않거나 건너뛰려고 하면 CI에서 잡힙니다. 여기에는 linting, formatting, type checking, 코드 중복, 아키텍처 검사, 문서 linting, 가능한 모든 것이 포함됩니다.

예전에는 코드 리뷰가 스타일, 탭, 스페이스에 대한 것이었습니다. 이제 그럴 여유가 없습니다. 이것들은 규칙이고 강제되며 자동화됩니다. 더 이상 논의할 공간이 없습니다. 이제는 도구로 찾을 수 없는 것들, 고수준 개념에 대한 것입니다.

예를 들어 저희는 제품 및 코드의 아키텍처를 강제합니다. 모듈과 import를 분리합니다 — 어디서 무엇을 사용할 수 있는지. 예를 들어 저희 E2E BDD 테스트 스위트는 데이터베이스에 접근할 수 없습니다. DB에 접근할 수 있는 모듈의 import 자체를 금지해서 모델이 DB 없이 반복하고 애플리케이션의 브라우저 기능만 사용하도록 강제합니다. 마찬가지로 제품 자체에서도 렌더링 템플릿에서 DB로 직접 이야기할 수 없게 강제합니다. 그렇게 해서 N+1 쿼리가 절대 없다는 것을 압니다. 이런 문제들이 발생하지 못하도록 막는 방법을 정의하세요. 계속 찾아내려 해서는 안 됩니다. 원천 차단해야 합니다.

그러면 에이전트가 커밋하고 푸시하려 할 때 커밋 단계에서 피드백을 받고 거절당하며, 해당 문서로 연결됩니다. 에이전트가 그 문서를 읽고 수정하고 반복합니다.

이 루프는 범용적입니다. 작업을 하고, 푸시하고, 피드백을 받고, 반복합니다. 루프는 여러 종류일 수 있습니다 — 제품 기능 작업, UI 작업, 백엔드 작업. 루프는 같지만 focus가 바뀝니다. 그래서 다른 스킬들이 있습니다. ADR 스킬: ADR이 언급되면 ADR을 어떻게 다루는지, 영향받는 코드를 어떻게 찾는지. PRD도 마찬가지. UI 루프: 일부 검사를 건너뛰고 브라우저에서 빠르게 반복하도록 강제. Test 스킬: 코드 커버리지와 파일 변경 기반으로 실행할 테스트를 식별해서 전체 스위트가 아닌 관련 부분만 실행. 그리고 목표 실행 기록으로 모델이 내린 결정을 나중에 리뷰할 수 있게 저장.

모두 루프에서 focus를 제공하지만, 루프 자체는 동일합니다.

단점이 있습니다. 컨텍스트를 매우 많이 씁니다. 조사를 시작하는 데만 컨텍스트의 절반을 쓸 수 있습니다. 하지만 저는 컨텍스트 컴팩트를 두려워하지 않습니다. 지난 반년간 실제로 잘 작동하고 있습니다. 제 세션에는 20~50번의 컨텍스트 컴팩트가 있는데 괜찮습니다. 중요한 것은 살아남고, 에이전트는 필요할 때 다시 찾습니다. 그게 목표입니다 — 에이전트가 당신이 정의한 규칙으로 자율적으로 작동하는 몇 시간짜리 세션.

요약하자면: 기록할 수 있는 결정들이 있습니다. 왜 이것이 존재하는지 기술할 수 있는 제품 파트들이 있습니다. 읽고 리뷰하고 이해할 수 있는 실행 가능한 스펙을 가진 Cucumber/BDD가 있습니다. 디자인 시스템은 컴포넌트에서 일관된 UI를 만드는 데 도움이 됩니다. 그리고 예를 들어 어디에도 인라인 스타일이 없다는 것을 강제하기 위해 하네스를 활용해 모든 것을 루프로 묶습니다.

"스펙이 당신과 함께하길." 이상입니다.
