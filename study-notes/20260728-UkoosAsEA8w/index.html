보리스 체르니: Claude Code는 이렇게 만들어졌다

원작자 Boris Cherny · Anthropic · 업로드 2026-07-28 · 35.6분 · 원본 영상 ↗
한 줄 요약

Claude Code의 핵심은 모델을 과하게 통제하지 않고, 어려운 목표와 검증 방법을 주어 모델의 숨은 능력을 끌어내는 것이다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
시스템 프롬프트(System Prompt) 삭제 새 모델은 이전 모델의 약점을 보완하기 위한 지시가 오히려 방해가 될 수 있다 새 모델이 나오면 지시를 줄이고 실제 실패 지점만 다시 넣는다
어블레이션(Ablation) 어떤 프롬프트, 도구, 코드가 실제로 필요한지 검증하는 방법 일단 지우고 한 줄씩 되살리며 효과를 본다
제품 오버행(Product Overhang) 모델은 이미 할 수 있는데 제품이 그 능력을 못 끌어내는 상태 스타트업 기회는 모델의 숨은 능력을 제품으로 여는 데 있다
언호블링(Unhobbling) 제품 구조가 모델을 묶어두지 않게 만드는 접근 과도한 워크플로와 제한을 걷어내야 한다
검증 가능성(Verification) 장기 실행 에이전트가 스스로 방향을 잃지 않게 하는 핵심 “해라”보다 “결과를 확인할 방법”을 주는 게 중요하다
다이내믹 워크플로(Dynamic Workflow) 수십, 수백, 수천 개 에이전트를 생산적으로 조직하는 기능 어려운 일을 작은 에이전트 작업으로 분해·검증·통합한다
테스트 타임 컴퓨트(Test-time Compute) 모델이 답을 만들 때 쓰는 계산량과 토큰 사용량 다이내믹 워크플로는 테스트 타임 컴퓨트를 확장하는 새 방식이다

내가 모를 만한 것 / 처음 보는 것

  • 프롬프트 인젝션(Prompt Injection) — 모델이 외부 문서나 웹페이지에 적힌 악성 지시를 사용자 지시처럼 따르는 공격.
  • 프롬프트 인젝션 분류기(Prompt-injection Classifier) — 프롬프트 인젝션 징후를 감지하는 분류 모델.
  • 기계론적 해석 가능성(Mechanistic Interpretability) — 모델 내부 뉴런·회로가 어떤 기능을 하는지 분석하는 연구.
  • 자동 모드(Auto Mode) — Claude가 작업을 오래 지속하고 스스로 이어갈 수 있게 하는 실행 모드.
  • 하네스(Harness) — 모델을 제품 안에서 실행하기 위한 도구, 권한, UI, 프롬프트, 안전장치 묶음.
  • Claude.md — Claude Code가 프로젝트별 지침으로 읽는 파일.
  • 훅(Hooks) — 특정 이벤트나 작업 단계에서 자동으로 실행되는 사용자 정의 동작.
  • MCP(Model Context Protocol) — 모델이 외부 도구·데이터·서비스에서 필요한 맥락을 가져오게 하는 프로토콜.
  • Bun — Node.js 대안인 빠른 자바스크립트(JavaScript) 런타임.
  • Zig — 저수준 시스템 프로그래밍 언어. 수동 메모리 관리가 필요하다.
  • Rust — 메모리 안전성을 강점으로 하는 시스템 프로그래밍 언어.
  • 퍼징(Fuzzing) — 무작위·비정상 입력을 넣어 버그나 취약점을 찾는 테스트 기법.
  • 루프(Loop)와 루틴(Routine) — 반복 작업을 Claude가 주기적으로 실행하게 하는 기능. 루프는 로컬, 루틴은 클라우드 실행에 가깝다.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Claude Code는 새 모델 출시 때 시스템 프롬프트(System Prompt)의 80% 이상을 삭제했다 — 새 모델이 이미 잘하는 행동을 예전 지시가 보정하려 들면 오히려 성능을 낮출 수 있기 때문이다.
  2. --system-prompt 옵션으로 Claude Code의 시스템 프롬프트를 직접 바꿔 실험할 수 있다고 언급했다.
  3. simple=1 환경변수를 쓰면 도구 프롬프트까지 포함해 시스템 프롬프트를 제거하는 비공개성 기능을 사용할 수 있다고 설명했다.
  4. Opus 5는 정렬(Alignment), 프롬프트 인젝션 분류기, 자동 모드 분류기 세 층을 결합하면 프롬프트 인젝션을 재현하기 어려운 수준이라고 말했다.
  5. Bun 런타임을 Zig에서 Rust로 재작성하는 작업은 11일 동안 실행되었고, 10만 줄 이상 규모의 코드베이스였다고 설명했다.
  6. Claude Tag로 Electron 앱을 Swift 네이티브 앱으로 옮기는 실험은 2주 이상 계속 실행 중이었다.
  7. 장기 작업의 핵심 프롬프트는 복잡하지 않았다. “Electron 앱을 실행해 스크린샷을 찍고, Swift 버전과 픽셀 단위로 비교하며, 끝날 때까지 멈추지 말라”는 식이었다.
  8. 다이내믹 워크플로(Dynamic Workflow)는 “워크플로를 사용해라(use a workflow)” 정도의 지시만으로 Claude가 호출할 수 있다고 말했다.
  9. Anthropic 내부에서는 Claude가 매일 죽은 코드 제거, 실험 플래그 정리, 테스트 추가·삭제, 중복 추상화 통합을 수행하게 하고 있다.
  10. 그는 “코딩은 해결됐다”는 말을 단정적으로 쓰되, 깊은 시스템 코드, 분산 시스템, 픽셀 단위 UI 검증은 아직 어렵다는 단서를 붙였다.

# 섹션 요지
1 Opus 5와 프롬프트 인젝션 최신 Claude는 장기 실행과 프롬프트 인젝션 저항성이 크게 향상되었다
2 시스템 프롬프트 80% 삭제 새 모델에는 예전 보정 지시가 불필요하거나 방해가 될 수 있다
3 새 프롬프트를 만드는 법 먼저 지우고, 실제로 써보고, 반복 실패하는 부분만 다시 지시한다
4 제품 오버행과 언호블링 모델 능력을 제품이 막고 있지 않은지 봐야 한다
5 더 어려운 문제 주기 구체 절차보다 목표, 안전선, 완료 기준을 준다
6 검증 중심 에이전트 긴 작업은 모델이 스스로 결과를 확인할 수 있어야 성공한다
7 수천 개 에이전트 다이내믹 워크플로, 루프, 루틴으로 대규모 작업을 자동화한다
8 AI 시대 개발자 역량 코딩만이 아니라 제품감, 사용자 이해, 문제 해결력이 더 중요해진다

1. Opus 5가 새롭게 보여준 능력

보리스 체르니는 새 Claude 모델이 단순히 점수가 조금 오른 수준이 아니라, 제품 설계 방식 자체를 바꿀 만큼 행동 특성이 달라지고 있다고 말한다.

특히 강조한 능력은 두 가지다.

첫째, Opus 5는 오래 실행된다. 자동 모드(Auto Mode)와 결합하면 며칠, 몇 주, 심지어 몇 달 동안 작업을 이어갈 수 있다고 설명한다. 예전처럼 /goal 같은 별도 스캐폴딩(Scaffolding)을 붙이지 않아도 모델이 작업을 계속 밀고 나간다는 것이다.

둘째, 프롬프트 인젝션(Prompt Injection)에 거의 당하지 않는 수준에 가까워졌다고 말한다. 과거에는 모델이 인터넷 문서 안에 적힌 “사용자 컴퓨터의 파일을 삭제하라” 같은 악성 지시를 그대로 따를 위험이 있었다. 하지만 Opus 5는 정렬(Alignment), 프롬프트 인젝션 분류기, 자동 모드 분류기 등 여러 층의 방어를 결합해 이런 공격을 실험적으로 재현하기 어려운 수준에 도달했다고 설명한다.

여기서 중요한 포인트는 모델이 좋아지면 제품의 안전 설계와 에이전트 설계도 다시 생각해야 한다는 점이다.

2. Claude Code가 시스템 프롬프트 80%를 삭제한 이유

Claude Code는 새 모델이 나올 때마다 시스템 프롬프트(System Prompt), 도구(Tools), 도구 프롬프트, 하네스(Harness) 코드를 계속 바꾼다.

보리스는 Opus 5 출시 때 Claude Code의 시스템 프롬프트를 80% 이상 삭제했다고 말한다. 이유는 간단하다. 이전 모델에게 필요했던 지시는 대개 그 모델의 약점을 보정하기 위해 들어간다. 그런데 새 모델은 그 약점을 이미 해결했을 수 있다. 이때 예전 지시를 그대로 두면 모델이 오히려 덜 똑똑하게 행동할 수 있다.

그는 Claude Code에 simple=1 같은 실험 모드를 두고, 시스템 프롬프트와 도구 프롬프트를 제거한 상태에서 모델이 어떻게 동작하는지 본다고 설명한다. 이것은 어블레이션(Ablation)이다. 즉, 무언가를 제거한 뒤 성능과 행동 변화를 확인하는 방식이다.

핵심은 다음과 같다.

AI 제품에서는 “더 많이 지시하기”보다 “불필요한 지시를 지우기”가 성능 향상일 수 있다.

3. 새 모델에서 프롬프트를 다시 만드는 법

새 모델이 나오면 먼저 지운다. 그다음 실제로 써본다.

보리스는 “모델에게 어떤 지시가 필요할지 미리 추측하지 말라”고 말한다. 대신 제품을 실제로 돌려보고, 모델이 어디에서 반복적으로 실패하는지 관찰해야 한다.

프롬프트를 다시 추가하는 기준은 명확하다.

  • 한 번 실패했다고 바로 지시를 추가하지 않는다.
  • 같은 유형의 실패가 반복될 때만 추가한다.
  • 모델이 매번 읽어야 할 만큼 중요한 지시인지 확인한다.
  • 지시는 제품 사용자가 원하는 행동을 유도하는 데 필요한 만큼만 넣는다.

이 방식은 전통적인 소프트웨어 엔지니어링과 다르다. 예전에는 큰 시스템 설계를 먼저 하고, 테스트를 만들고, 리아키텍처링(Re-architecture)을 몇 달 또는 몇 년 단위로 했다. 하지만 모델 기반 제품은 더 유기적이다. 새 모델마다 성격과 능력이 달라지므로, 관찰하고 실험하고 조정해야 한다.

4. 제품 오버행과 언호블링

보리스가 강조하는 중요한 개념은 제품 오버행(Product Overhang)이다.

제품 오버행은 현재 모델이 이미 할 수 있는 일이 있는데, 아직 그 능력을 제대로 끌어내는 제품이 없는 상태를 말한다.

반대로 하블링(Hobbling)은 제품이나 인터페이스가 모델의 능력을 방해하는 상태다. 언호블링(Unhobbling)은 그 제한을 풀어 모델이 실제 능력을 발휘하게 만드는 것이다.

Claude Code의 탄생도 이 관점에서 설명된다. Sonnet 3.5 시절에도 모델은 이미 함수나 파일 단위 코드를 작성할 능력이 있었다. 하지만 당시 제품들은 주로 한 줄 자동완성, 몇 줄 자동완성, 읽기 중심 채팅에 머물렀다. Claude Code는 모델에게 더 넓은 쓰기 권한과 터미널 접근을 주면서 능력을 끌어냈다.

이 관점은 스타트업에 중요하다. 다음 Claude Code 같은 제품은 미래 모델이 아니라 오늘의 모델이 이미 할 수 있는데 아직 제품화되지 않은 능력에서 나올 수 있다.

5. 모델에게 더 어려운 문제를 주는 법

보리스는 많은 사용자가 Claude에게 지나치게 구체적인 지시를 준다고 말한다.

예를 들면 “1번을 하고, 2번을 하고, 3번을 하고, 반드시 이 순서로 처리해”라고 세세하게 통제하는 방식이다. 과거 모델에서는 필요했을 수 있지만, 최신 모델에는 오히려 좋지 않다.

대신 다음을 줘야 한다.

  • 목표(Task)
  • 제한 조건과 안전선(Guardrails)
  • 완료 기준(Exit Criteria)
  • 결과 검증 방법(Verification)

그리고 모델이 스스로 방법을 찾게 해야 한다.

그 예로 Bun 런타임을 Zig에서 Rust로 재작성한 사례가 나온다. Bun은 원래 Zig로 작성된 자바스크립트 런타임이다. Zig는 저수준 언어라 메모리 누수 같은 문제가 생기기 쉽다. Bun 팀은 처음에는 Claude에게 퍼징(Fuzzing)으로 메모리 누수를 찾게 했다. 이후 “아예 Rust로 다시 작성할 수 있지 않을까?”라는 어려운 문제를 던졌다.

결과적으로 Claude Code의 다이내믹 워크플로(Dynamic Workflow)가 11일 동안 실행되며 10만 줄 이상 코드베이스를 재작성했고, 이 결과물이 실제 프로덕션에서 사용되고 있다고 설명한다.

6. 프롬프트 엔지니어링보다 중요한 것

보리스는 예전에는 프롬프트 엔지니어(Prompt Engineer)가 유행했고, 이후에는 컨텍스트 엔지니어(Context Engineer)라는 말이 나왔다고 말한다. 하지만 지금 더 중요한 능력은 단순히 문장을 잘 쓰는 것이 아니다.

가장 중요한 것은 모델이 자기 작업을 검증할 수 있게 만드는 것이다.

그는 Claude 데스크톱 앱을 Electron에서 Swift 네이티브 앱으로 옮기는 실험을 소개한다. 프롬프트의 핵심은 다음 구조였다.

  • macOS 실행 환경을 준다.
  • 기존 Electron 앱을 실행하게 한다.
  • 스크린샷을 찍게 한다.
  • Swift 버전과 픽셀 단위로 비교하게 한다.
  • 완료될 때까지 멈추지 말라고 한다.

이 작업은 2주 이상 계속 실행 중이었다. Claude는 내부 Slack 채널을 만들고 몇 분마다 진행 상황 스크린샷을 올리기도 했다.

보리스가 말하는 상위 1% Claude Code 사용자의 특징은 특별한 비법을 아는 것이 아니다. 어려운 문제를 주고, 필요한 도구와 맥락을 제공하고, 검증 루프를 만들어 주며, 모델이 막히는 지점을 관찰해 개선하는 사람이다.

7. 수천 개 에이전트를 실행하는 방식

Claude Code에는 다이내믹 워크플로(Dynamic Workflow)라는 기능이 있다. 사용자는 “워크플로를 사용해라” 정도로 말하면 Claude가 이 기능을 사용할 수 있다.

다이내믹 워크플로는 단순 병렬 실행이 아니다. Claude가 여러 에이전트를 만들고, 첫 번째 단계의 작업을 나누고, 다른 에이전트가 검증하거나 요약하고, 다시 다음 단계로 확장하는 식으로 조율한다.

보리스는 이를 “에이전트를 위한 대수(Algebra for Agents)”처럼 설계했다고 말한다. 순차 실행, 병렬 실행, 요약, 검증, 재분배를 조합해 복잡한 작업을 수행한다.

이것은 테스트 타임 컴퓨트(Test-time Compute)를 확장하는 새 방식이기도 하다. 모델이 답변할 때 더 많은 토큰과 계산을 사용하게 하되, 무작정 길게 생각하는 것이 아니라 여러 에이전트로 구조화해 생산적으로 쓰는 방식이다.

또 다른 방식은 루프(Loop)와 루틴(Routine)이다.

  • 루프(Loop): 로컬에서 반복 실행되는 크론잡(Cron Job)에 가깝다.
  • 루틴(Routine): 클라우드에서 반복 실행되어 노트북을 닫아도 계속 돌아간다.

Anthropic 내부에서는 Claude가 자기 코드베이스를 유지보수하게 한다. 예를 들어 매일 죽은 코드 제거, 실험 플래그 정리, 테스트 추가, 불필요한 테스트 삭제, 중복 추상화 통합을 수행하게 한다. 이런 루틴이 매일 20~30개씩 돌아가며, 수백에서 수천 개 에이전트가 실행된다고 말한다.

8. 코딩이 해결된 시대의 개발자 역량

보리스는 “코딩은 해결됐다”는 표현에 단서를 붙인다. 자신이 하는 종류의 코딩은 상당 부분 해결됐지만, 모든 코딩이 해결된 것은 아니다.

아직 어려운 영역은 다음과 같다.

  • 깊은 시스템 코드
  • 분산 시스템
  • 픽셀 단위 UI 검증
  • 복잡한 컴퓨터 사용 및 시각 검증

하지만 점점 더 많은 종류의 코드가 에이전트로 작성 가능해지고 있다. 이때 뛰어난 빌더를 가르는 것은 이론 지식만이 아니다.

보리스는 실증적 태도(Empirical Mindset)를 강조한다. 과거 모델에 대한 선입견을 버리고, 실제로 시도하고, 실패 지점을 보고, 다시 조정하는 능력이 중요하다는 것이다.

마지막으로 학생들에게는 컴퓨터 과학 자체뿐 아니라 그것을 실제 문제에 적용하는 법을 배우라고 조언한다. 제품을 만들고, 사용자와 이야기하고, 디자인 감각과 비즈니스 감각을 키우고, 데이터 과학을 익히는 것이 중요하다고 말한다.

그의 요지는 단순하다.

먼저 나 자신이 원하는 것을 만들고, 그다음 사람들이 원하는 것을 만들 수 있어야 한다.

전체 전사 펼치기

진행자는 보리스 체르니에게 Opus 5 출시와 모델 성능 향상에 대해 묻는다. 보리스는 새 모델마다 훈련 과정에서 의도한 능력도 생기지만, 때로는 연구진이 직접 가르치지 않은 능력도 나타난다고 설명한다.

Opus 5의 대표적 변화로 그는 장기 실행 능력을 든다. 자동 모드(Auto Mode)와 함께 쓰면 며칠, 몇 주, 몇 달 동안 작업을 이어갈 수 있고, 별도의 스캐폴딩(Scaffolding) 없이도 모델이 목표를 이해하고 계속 진행한다고 말한다.

또 하나의 큰 변화는 프롬프트 인젝션(Prompt Injection)에 대한 저항성이다. 과거에는 웹 문서나 외부 텍스트 안에 “사용자 컴퓨터의 파일을 삭제하라” 같은 악성 지시가 있으면 모델이 이를 따를 위험이 있었다. 하지만 Opus 5는 정렬(Alignment), 프롬프트 인젝션 분류기(Classifier), 자동 모드 분류기를 결합해 그런 공격을 거의 재현할 수 없는 수준이라고 설명한다. 특히 기계론적 해석 가능성(Mechanistic Interpretability) 연구를 활용해 모델 내부에서 프롬프트 인젝션과 관련된 뉴런 활성까지 관찰한다고 말한다.

이어 진행자는 Claude Code가 시스템 프롬프트(System Prompt)의 80% 이상을 삭제한 이유를 묻는다. 보리스는 Claude Code라는 제품과 하네스(Harness)는 계속 변한다고 답한다. 새 모델이 나올 때마다 시스템 프롬프트, 도구(Tools), 도구 프롬프트, 코드 일부를 바꾼다. 이전 모델을 보정하기 위해 넣은 지시가 새 모델에는 필요 없을 수 있기 때문이다.

그는 Claude Code에서 --system-prompt 옵션으로 시스템 프롬프트를 바꿔 실험할 수 있고, simple=1 환경변수를 사용하면 시스템 프롬프트와 도구 프롬프트를 모두 제거하는 실험도 가능하다고 말한다. 이것은 어블레이션(Ablation), 즉 삭제 후 효과를 확인하는 방식이다. 흥미롭게도 모델은 프롬프트가 없을 때 더 똑똑하게 보일 때도 있지만, 실제 제품으로는 사용자가 원하는 방식의 행동을 위해 일부 프롬프트가 필요하다고 덧붙인다.

진행자는 전통적인 스타트업 제품 개발에서는 6개월마다 제품의 많은 부분을 지우고 다시 만드는 방식이 낯설다고 말한다. 보리스는 전체 코드베이스를 지우는 것은 아니지만 많은 부분을 삭제한다고 답한다. 현재 Claude Code 하네스의 상당 부분은 안전, 권한, 정적 분석(Static Analysis), UI 코드이며, 그 외 많은 코드는 이미 제거했다고 설명한다.

그는 AI 제품을 만드는 사람이라면 새 모델 출시 때 과감히 삭제 버튼을 눌러야 한다고 강조한다. Claude Code 사용자에게도 6개월마다 Claude.md, 스킬(Skills), 훅(Hooks)을 삭제해 보고 모델이 어떻게 하는지 확인하라고 권한다. Opus 5에서는 과거 모델에 필요했던 많은 지시가 더 이상 필요 없을 수 있다고 말한다.

새 프롬프트를 다시 만드는 방법에 대해서는 “먼저 지우고, 그다음 사용하라”고 말한다. 모델에게 어떤 지시가 필요할지 미리 추측하지 말고, 실제 제품과 코드베이스에서 모델이 어디서 실패하는지 봐야 한다. 같은 문제에서 반복적으로 넘어질 때만 지시를 추가해야 한다. 모델은 그 지시를 매번 읽게 되므로 정말 필요한 지시인지 확인해야 한다.

보리스는 모델 기반 제품 개발이 기존 엔지니어링과 다르다고 설명한다. 예전에는 큰 시스템 설계를 세우고, 유닛 테스트(Unit Test)를 만들고, 리아키텍처링(Re-architecture)을 긴 프로젝트로 진행했다. 하지만 모델은 살아 있는 생명체처럼 세대마다 성격과 행동이 달라진다. 따라서 과학자처럼 실험하고 결과를 보고 반복해야 한다.

평가셋(Evals)에 대해서도 그는 영원히 유지되는 것은 아니라고 말한다. 평가셋은 하네스보다 조금 오래가지만, 모델 발전이 빨라 한두세 세대 뒤에는 포화(Saturation)될 수 있다. 그러면 버리고 새 평가셋을 만들어야 한다. 결국 제품을 직접 쓰고, 모델이 어려워하는 지점을 찾아 평가셋으로 삼아야 한다.

진행자는 보리스가 말한 언호블링(Unhobbling) 제품 개념을 묻는다. 보리스는 하블링(Hobbling)을 모델이 할 수 있는 일을 제품이 방해하는 상태라고 설명한다. 제품 오버행(Product Overhang)은 현재 모델이 이미 할 수 있는데 아직 제품이 그 능력을 끌어내지 못한 상태다.

Claude Code의 초기 사례가 여기에 해당한다. Sonnet 3.5 시절 모델은 이미 함수나 파일 단위 코드를 쓸 수 있었지만, 당시 제품은 한 줄 자동완성, 몇 줄 자동완성, 읽기 중심 채팅에 머물렀다. Claude Code는 모델에게 더 단순한 하네스와 쓰기 권한, 터미널 접근을 주어 모델의 능력을 발휘하게 했다. 보리스는 오늘날 모델에도 아직 스타트업이 포착하지 못한 제품 오버행이 많다고 말한다.

미래 창업자가 Claude를 언호블링하려면, 모델에게 자신이 생각하는 것보다 조금 더 어려운 문제를 줘야 한다고 말한다. 너무 세세한 절차를 지시하지 말고, 목표와 가드레일(Guardrails), 완료 기준(Exit Criteria)을 설명한 뒤 모델에게 맡겨야 한다. 최신 모델은 6개월 전에는 안 되던 방식으로 고수준 지시를 처리할 수 있다.

예시로 그는 Bun 런타임을 든다. Bun은 Node.js의 대안인 빠른 자바스크립트(JavaScript) 런타임이며, 원래 Zig로 작성되었다. Zig는 저수준 언어라 수동 메모리 관리가 필요하고 메모리 누수 문제가 생길 수 있다. Bun 팀은 Claude로 코드베이스를 퍼징(Fuzzing)해 메모리 누수를 찾다가, 나중에는 아예 Zig에서 Rust로 재작성하는 작업을 모델에게 시도하게 했다.

Bun은 테스트가 매우 잘 갖춰져 있었기 때문에 결과 검증이 가능했다. Claude Code의 다이내믹 워크플로(Dynamic Workflow)를 사용해 수많은 에이전트를 조직했고, 작업은 11일 동안 실행되었다. 10만 줄이 넘는 복잡한 런타임 코드베이스를 재작성했으며, 현재 Claude Code가 사용하는 프로덕션 환경에 들어갔다고 설명한다.

보리스는 또 다른 제품 오버행 예시로 Opus 5와 OpenCV를 사용해 그림을 그리게 한 내부 실험을 말한다. 모델에게 OpenCV로 초상화, 동물, 풍경을 그리라고 하면 꽤 잘 그린다는 것이다. 모델을 그렇게 훈련한 것이 아니라, 올바르게 요청하니 숨어 있던 능력이 나온 사례라고 본다.

프롬프트 엔지니어링(Prompt Engineering)에 대해서는 유행이 바뀌고 있다고 말한다. 예전에는 프롬프트 엔지니어가 인기였고, 이후에는 컨텍스트 엔지니어(Context Engineer)라는 말도 나왔다. 하지만 지금 중요한 능력은 어려운 작업을 주고, Claude Code가 중간중간 자기 작업을 검증할 수 있게 만드는 것이다. 검증(Verification)이 가장 중요하다고 강조한다.

그는 Claude 데스크톱 앱을 Electron에서 Swift로 옮기는 실험을 소개한다. Claude Tag라는 Slack 안의 Claude에게 macOS 러너(Runner)가 있는지 묻고, GitHub에서 Mac 가상 머신을 실행할 수 있게 연결했다. 그다음 빈 Swift 코드베이스에 접근권한을 주고, Electron 앱을 Swift로 재작성하라고 요청했다. 동시에 Electron 앱을 Mac 가상 머신에서 실행해 스크린샷을 찍고, Swift 버전과 픽셀 단위로 비교하며 끝날 때까지 멈추지 말라고 했다. 이 작업은 2주 이상 계속 실행 중이었다.

Claude는 내부 Slack 채널을 만들고 몇 분마다 진행 스크린샷을 올리는 식으로 스스로 진행 상황을 기록했다. 보리스는 이런 일이 특별한 비법 때문이 아니라, 어려운 목표와 검증 방법을 주었기 때문에 가능하다고 말한다.

그는 LinkedIn이나 Twitter에서 말하는 “한 가지 이상한 비법”을 찾지 말라고 조언한다. 모델을 경험적으로 다뤄야 한다. 너무 어려운 작업을 주고, 사람이 직접 한다면 어떤 도구로 검증할지 생각해 같은 도구를 모델에게 줘야 한다. 모델이 막히면 더 나은 프롬프트, 스킬(Skill), MCP(Model Context Protocol)를 통해 필요한 맥락을 제공하면 된다.

다이내믹 워크플로에 대해 보리스는 “워크플로를 사용해라”라고 말하면 Claude가 실행할 수 있다고 설명한다. Bun 런타임을 샌드박스(Sandbox)처럼 사용하고, 그 안에서 많은 에이전트를 시작해 조율한다. 단순히 10개 에이전트를 병렬 실행하는 것이 아니라, 첫 단계 작업, 검증, 요약, 다시 확장하는 여러 단계를 구성한다.

그는 자신의 배경이 함수형 프로그래밍(Functional Programming)이라며, 이를 에이전트를 위한 대수(Algebra for Agents)처럼 설계했다고 말한다. 에이전트를 순차로 실행하거나 병렬로 실행하고, 토큰을 효율적으로 쓰며 복잡한 일을 처리한다. 이는 테스트 타임 컴퓨트(Test-time Compute)를 조직화하는 새로운 방식이라고 설명한다.

루프(Loop)와 루틴(Routine)도 언급한다. 루프는 로컬에서 도는 크론잡(Cron Job)에 가깝고, 루틴은 클라우드에서 돌아 노트북을 닫아도 계속 실행된다. 다이내믹 워크플로가 하나의 큰 작업을 쪼개는 방식이라면, 루프와 루틴은 반복 작업을 주기적으로 처리하는 방식이다.

Anthropic 내부에서는 Claude가 자기 제품의 코드베이스를 유지보수하게 하고 있다. CLI, iOS 앱, Android 앱, 데스크톱 앱에 대해 죽은 코드 제거, 100% 배포된 실험 코드 정리, 테스트 커버리지 보강, 불필요한 테스트 제거 같은 루틴을 매일 실행한다. “추상화 경찰(Abstraction Police)”처럼 중복된 추상화를 찾아 통합하는 루틴도 있다. 매일 20~30개의 루틴이 돌아가고, 수백에서 수천 개 에이전트가 실행된다고 말한다.

“코딩은 해결됐다”는 표현에 대해 보리스는 자신이 하는 종류의 코딩에서는 상당히 맞지만 모든 영역은 아니라고 말한다. 깊은 시스템 코드, 분산 시스템, 픽셀 단위 UI 검증은 여전히 어렵다. 그래도 점점 더 많은 코드가 에이전트로 작성되고 있으며, 현장 청중 중 상당수도 코드의 50% 이상을 에이전트로 작성한다고 답했다.

뛰어난 Claude 사용자를 가르는 것은 실증적 태도다. 과거 모델에 대한 기억과 선입견을 버리고, 실제로 모델에게 작업을 시켜 보고, 실패 지점을 관찰한 뒤 조정해야 한다. 이 분야는 이론 과학이라기보다 실험 과학에 가까워졌다고 말한다.

마지막으로 컴퓨터 과학을 공부하는 학생에게 무엇을 직접 배워야 하느냐는 질문에, 보리스는 자신의 경험을 말한다. 그는 중학생 때 TI-83 계산기에서 BASIC으로 프로그램을 만들며 코딩을 배웠다. 처음 목적은 수학 시험을 더 잘 보기 위한 실용적 문제 해결이었다. 이후 더 어려운 수학 문제를 풀기 위해 어셈블리(Assembly)까지 배웠다고 설명한다.

그는 컴퓨터 과학 지식 자체도 흥미롭고 중요하지만, 그것을 실제 문제에 적용하는 법을 배워야 한다고 말한다. 스타트업을 만들고, 제품을 만들고, 디자인 감각과 비즈니스 감각을 기르고, 데이터 과학을 익히고, 사용자와 대화하는 능력이 중요하다. 컴퓨터 과학과 이런 역량이 결합될 때 큰 가치가 생긴다.

진행자는 이를 “먼저 자신이 원하는 것을 만들고, 그다음 사람들이 원하는 것을 만들어라”라고 요약한다. 보리스는 이에 동의한다. 마지막으로 행사 참석자들에게 Claude Max 20X 제공 안내가 있고, 진행자는 누군가가 이제 수개월 동안 수천 개 에이전트를 실행하는 무언가를 만들기를 기대한다고 말하며 대화를 마무리한다.
