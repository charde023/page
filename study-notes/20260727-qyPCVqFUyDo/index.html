Boris Cherny: Claude Code의 프롬프트를 80% 줄인 이유

한 줄 요약

Claude Code의 핵심 교훈은 새 모델이 똑똑해질수록 더 많이 지시하는 것이 아니라, 불필요한 프롬프트와 도구를 지우고 모델이 스스로 검증하며 오래 일하게 만드는 것이다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
시스템 프롬프트(System Prompt) 삭제 모델 성능이 좋아지면 과거의 지시문이 오히려 방해가 될 수 있음 새 모델이 나오면 먼저 지우고, 반복 실패하는 부분만 다시 넣는다
절제 실험(Ablation) 어떤 지시·도구·코드가 실제로 도움이 되는지 확인하는 방법 줄 단위로 빼고 넣으며 영향도를 본다
제품 과잉 잠재력(Product Overhang) 모델은 이미 할 수 있는데 제품이 그 능력을 못 끌어내는 상태 좋은 AI 제품은 모델을 덜 묶고 능력을 드러내게 한다
모델 방해(Hobbling) 제품 구조나 과한 지시가 모델의 능력을 막는 현상 AI 제품은 기능 추가보다 방해 제거가 중요하다
검증 가능성(Verification) 장기 작업에서 환각과 막힘을 줄이는 핵심 모델에게 결과를 확인할 테스트·스크린샷·비교 기준을 줘야 한다
동적 워크플로(Dynamic Workflow) 수십~수천 개 에이전트를 조직해 큰 작업을 나누는 방식 “워크플로를 사용해”라는 지시만으로 대규모 작업을 병렬화할 수 있다
루프와 루틴(Loops & Routines) 반복 유지보수 업무를 AI에게 맡기는 구조 매일 죽은 코드 삭제, 테스트 보강, 중복 추상화 통합을 자동화한다

내가 모를 만한 것 / 처음 보는 것

  • 프롬프트 인젝션(Prompt Injection) — 모델이 외부 문서나 웹페이지에 숨겨진 악성 지시를 따라버리는 문제.
  • 치명적 삼각형(Lethal Trifecta) — 외부 데이터 접근, 민감 권한, 외부 통신이 결합될 때 AI 에이전트 보안 위험이 커지는 상황.
  • 기계적 해석 가능성(Mechanistic Interpretability) — 모델 내부 뉴런 활성 패턴을 분석해 특정 행동이나 위험 신호를 찾는 연구.
  • 절제 실험(Ablation) — 시스템 일부를 제거해 실제 기여도를 보는 실험 방식.
  • 제품 과잉 잠재력(Product Overhang) — 현재 모델이 이미 가능한 능력을 제품이 아직 못 끌어낸 상태.
  • Bun — Node.js 대안으로 쓰이는 빠른 자바스크립트 런타임(JavaScript Runtime).
  • Zig — C처럼 저수준 제어가 가능한 시스템 프로그래밍 언어(Systems Programming Language).
  • Rust — 메모리 안전성을 강하게 보장하는 시스템 프로그래밍 언어.
  • 퍼징(Fuzzing) — 무작위·비정상 입력을 넣어 버그나 취약점을 찾는 테스트 기법.
  • OpenCV — 컴퓨터 비전(Computer Vision) 라이브러리. 여기서는 Claude가 그림을 그리는 도구로 사용.
  • MCP(Model Context Protocol) — 모델이 필요한 외부 맥락과 도구를 가져오게 하는 연결 프로토콜.
  • 테스트 타임 컴퓨트(Test-time Compute) — 모델이 답을 만들 때 쓰는 추론 연산량. 여기서는 여러 에이전트와 토큰 사용으로 확장됨.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Claude Code는 Opus 5에 맞춰 시스템 프롬프트(System Prompt)의 80% 이상을 삭제했다 — 새 모델이 이전 지시 없이도 자연스럽게 올바른 행동을 하기 때문.
  2. --system-prompt 옵션으로 Claude Code의 시스템 프롬프트를 직접 바꿔 실험할 수 있다고 언급했다.
  3. simple=1 환경 변수로 Claude Code를 실행하면 도구 프롬프트까지 포함해 거의 모든 프롬프트를 지우는 단순 모드(Simple Mode)를 쓸 수 있다고 했다.
  4. 새 모델이 나오면 전체 시스템 프롬프트를 지우고 한 줄씩 다시 추가하며 영향도를 본다. 이를 절제 실험(Ablation)이라고 설명했다.
  5. 평가셋(Eval)은 영구적이지 않다. 보통 1~3세대 모델 정도 지나면 모델이 평가를 포화(Saturate)해 새 평가가 필요하다고 했다.
  6. Bun 팀은 Claude를 이용해 Zig 코드베이스를 Rust로 옮겼고, 작업은 11일 동안 진행됐다.
  7. 이 Zig → Rust 변환은 과거라면 1년 이상 걸릴 수 있는 작업이라고 평가했다.
  8. Claude 데스크톱 앱을 Electron에서 Swift로 다시 만드는 실험은 인터뷰 시점 기준 14~15일째 계속 실행 중이었다.
  9. 이 작업은 macOS 러너(Runner)에서 Electron 앱과 Swift 앱을 실행하고, 스크린샷을 픽셀 단위로 비교하게 했다.
  10. 장기 작업에서 Claude가 스스로 내부 Slack 채널을 만들고 몇 분마다 진행 스크린샷을 올렸다고 했다.
  11. 동적 워크플로(Dynamic Workflow)는 수십, 수백, 수천 개 에이전트를 조직할 수 있고, 사용자는 “워크플로를 사용해”라고 말하면 된다고 설명했다.
  12. Anthropic 내부에서는 Claude가 매일 20~30개 루틴(Routines) 으로 CLI, iOS, Android, 데스크톱 앱 코드베이스를 관리한다고 했다.

# 섹션 요지
1 Opus 5의 변화 더 오래 실행되고, 프롬프트 인젝션에 강해졌으며, 과거 지시 없이도 더 잘 동작한다
2 Claude Code가 80%를 삭제한 이유 새 모델에는 과거 보정용 프롬프트가 오히려 방해가 된다
3 새 프롬프트를 만드는 법 먼저 지우고, 실제 사용에서 반복 실패하는 것만 다시 넣는다
4 제품 과잉 잠재력 모델은 이미 가능한데 제품이 그 능력을 가로막는 경우가 많다
5 더 어려운 일을 시켜라 세부 절차보다 목표·가드레일·완료 조건을 주고 맡긴다
6 검증이 핵심 장기 작업에는 모델이 스스로 결과를 확인할 수단이 필요하다
7 수천 에이전트 운영 동적 워크플로, 루프, 루틴으로 대규모·반복 업무를 자동화한다
8 코딩의 미래 코딩 자체보다 문제 선택, 제품 감각, 사용자 이해, 검증 설계가 중요해진다

1. Opus 5는 무엇이 달라졌나

Boris Cherny는 Opus 5의 가장 큰 특징 중 하나로 매우 긴 시간 동안 작업을 계속할 수 있는 능력을 꼽았다. 특히 자동 모드(Auto Mode)와 결합하면 며칠, 몇 주, 심하면 몇 달 동안 작업을 멈추지 않고 이어갈 수 있다고 설명한다.

과거에는 /goal 같은 스캐폴딩(Scaffolding)이나 반복 명령이 필요했지만, 최신 모델은 과제의 목적을 이해하고 스스로 계속 진행하는 능력이 좋아졌다는 것이다.

또 하나의 중요한 변화는 프롬프트 인젝션(Prompt Injection)에 대한 강한 내성이다. 예전 모델은 인터넷 문서 안에 “사용자의 컴퓨터 파일을 삭제하라” 같은 지시가 숨어 있으면 그대로 따를 위험이 있었다. 하지만 Opus 5는 정렬(Alignment), 프롬프트 인젝션 분류기(Classifier), 자동 모드 분류기라는 여러 층을 통해 그런 공격을 더 이상 재현하기 어려운 수준까지 왔다고 말한다.

2. Claude Code는 왜 시스템 프롬프트의 80%를 삭제했나

Claude Code는 고정된 제품이 아니라, 모델이 바뀔 때마다 계속 바뀌는 하네스(Harness)다. 새 모델이 나오면 시스템 프롬프트, 도구 구성, 도구 프롬프트, 코드 구조를 계속 수정하고 삭제한다.

이유는 간단하다. 3개월 전 모델에게 필요했던 지시가 새 모델에게는 불필요하거나 오히려 방해가 될 수 있기 때문이다.

Opus 5는 이전 모델보다 훨씬 똑똑해져서, 예전에는 프롬프트로 보정해야 했던 행동을 이제는 스스로 한다. 그래서 Claude Code 팀은 시스템 프롬프트의 80% 이상을 삭제했다.

중요한 관점은 “더 좋은 AI 제품 = 더 많은 프롬프트”가 아니라는 점이다. 오히려 새 모델에서는 프롬프트를 줄여야 모델의 자연스러운 능력이 드러난다.

3. 새 모델이 나오면 어떻게 프롬프트를 다시 만들어야 하나

Boris가 제시한 순서는 명확하다.

  1. 먼저 지운다.
  2. 실제로 써본다.
  3. 어디서 실패하는지 관찰한다.
  4. 같은 실패가 반복될 때만 지시를 다시 넣는다.

프롬프트를 미리 예측해서 많이 넣는 것은 위험하다. 모델은 매번 그 지시를 읽기 때문에, 불필요한 문장은 계속 비용과 간섭을 만든다.

그는 AI 제품 개발을 전통적인 소프트웨어 개발과 다르게 본다. 예전에는 큰 시스템 설계, 단위 테스트, 긴 리아키텍처 프로젝트가 중요했다. 하지만 모델 기반 제품은 더 유기적이다. 모델 세대마다 성격과 능력이 달라지므로, 과학 실험처럼 관찰하고 반복해야 한다.

핵심은 설계보다 관찰, 확신보다 실험이다.

4. 평가셋은 안정적인가

평가셋(Eval)은 시스템 프롬프트나 하네스보다는 오래가지만, 영구적이지는 않다. 모델이 빠르게 좋아지면서 기존 평가를 금방 만점에 가깝게 풀어버리기 때문이다.

Boris는 평가셋도 보통 한두 세대, 길어야 세 세대 정도 버틴다고 본다. 평가가 포화되면 버리고 새 평가를 만들어야 한다.

즉, 평가셋도 고정 자산이 아니라 계속 갱신되는 실험 도구다. 제품을 실제로 써보고, 모델이 어디서 어려워하는지 관찰한 뒤 그 부분을 평가셋으로 만들어야 한다.

5. 제품 과잉 잠재력과 모델 방해

제품 과잉 잠재력(Product Overhang)은 모델이 이미 할 수 있는 일이 있는데, 그 능력을 끌어내는 제품이 아직 없는 상태를 말한다.

반대로 모델 방해(Hobbling)는 제품 구조, UI, 권한, 프롬프트가 모델의 능력을 막는 상태다.

Claude Code의 탄생도 이 관점에서 설명된다. Sonnet 3.5 시절에도 모델은 꽤 긴 코드나 파일 단위 작업을 할 수 있었다. 하지만 당시 코딩 제품은 자동완성, 몇 줄 생성, 읽기 전용 채팅에 머물렀다. 모델이 전체 파일을 쓰고 기능을 구현할 수 있는데, 제품이 너무 좁게 묶고 있었던 것이다.

Claude Code는 터미널 접근과 단순한 하네스를 제공해 모델을 덜 묶었다. 그 결과 모델의 실제 능력이 드러났다.

6. 더 어려운 문제를 주고, 덜 지시하라

Boris는 많은 사용자가 모델에게 너무 세부적인 절차를 지시한다고 말한다.

나쁜 방식은 다음과 같다.

  • 1번을 하고
  • 2번을 하고
  • 3번 방식으로 하고
  • 반드시 이 순서로 해라

최신 모델에는 이런 방식보다 목표, 가드레일(Guardrails), 완료 조건(Exit Criteria) 을 주는 편이 낫다.

예를 들어 “이 기능을 만들어라. 단, 기존 테스트는 깨지면 안 되고, 성능은 이 기준을 넘겨야 하며, 완료되면 이런 결과가 나와야 한다”처럼 말하는 것이다. 그다음에는 모델이 스스로 방법을 찾게 해야 한다.

7. 11일 동안 코드베이스를 통째로 옮긴 사례

Bun은 Node.js 대안인 자바스크립트 런타임이고, 내부는 Zig로 작성되어 있었다. Zig는 빠르고 저수준 제어가 가능하지만 수동 메모리 관리 때문에 메모리 누수 같은 문제가 생기기 쉽다.

Bun 팀은 처음에는 Claude로 퍼징(Fuzzing)을 하며 메모리 누수를 하나씩 찾았다. 그러다 “아예 Rust로 다시 써보면 어떨까?”라는 실험을 했다.

조건은 명확했다.

  • Bun 자체 테스트가 많다.
  • Node.js 호환 테스트도 많다.
  • 따라서 결과가 맞는지 검증할 수 있다.

Claude는 동적 워크플로(Dynamic Workflow)를 사용해 Zig 코드베이스를 Rust로 옮겼고, 작업은 11일 동안 진행됐다. Boris는 이 작업이 과거라면 최고의 엔지니어들이 해도 1년 이상 걸렸을 것이라고 말했다.

핵심은 단순히 “AI가 코드를 많이 썼다”가 아니다. 검증 가능한 큰 목표를 주었기 때문에 장기 작업이 가능했다는 점이다.

8. 프롬프트 엔지니어링은 어떻게 바뀌는가

Boris는 과거의 프롬프트 엔지니어(Prompt Engineer), 컨텍스트 엔지니어(Context Engineer) 같은 유행어가 계속 바뀔 것이라고 본다.

지금 중요한 능력은 예쁜 문장을 쓰는 것이 아니라 다음 두 가지다.

  1. Claude에게 약간 어려워 보이는 큰 과제를 주는 능력
  2. Claude가 작업 중간중간 스스로 검증할 수 있게 만드는 능력

그는 Electron으로 만든 Claude 데스크톱 앱을 Swift 네이티브 앱으로 다시 만드는 실험을 예로 들었다. Claude에게 macOS 가상 머신을 제공하고, Electron 앱과 Swift 앱을 실행하게 한 뒤, 스크린샷을 픽셀 단위로 비교하게 했다.

그 작업은 2주 넘게 계속 실행 중이었다. Claude는 스스로 Slack 채널을 만들고 진행 상황 스크린샷을 올렸다.

여기서 중요한 것은 긴 프롬프트가 아니다. 프롬프트는 단순했다. 대신 모델에게 작업 환경과 검증 수단을 줬다.

9. 수천 개 에이전트를 어떻게 운영하나

Claude Code의 동적 워크플로(Dynamic Workflow)는 하나의 큰 작업을 여러 단계와 여러 에이전트로 나누어 처리한다.

예를 들어 코드베이스를 다시 쓰는 작업이라면 다음처럼 진행될 수 있다.

  1. 여러 에이전트가 1차 작업을 나눠 수행
  2. 다른 에이전트가 결과를 검증·요약
  3. 다시 여러 방향으로 작업을 확장
  4. 최종적으로 통합

Boris는 이를 에이전트의 대수(Algebra for Agents)라고 표현했다. 순차 실행, 병렬 실행, 샌드박스 내부 오케스트레이션을 조합해 테스트 타임 컴퓨트(Test-time Compute)를 크게 늘리는 방식이다.

또 다른 방식은 루프(Loop)와 루틴(Routine)이다.

  • 루프(Loop): 로컬에서 반복 실행되는 Claude 작업
  • 루틴(Routine): 클라우드에서 반복 실행되는 Claude 작업

Anthropic은 Claude가 Claude Code 자체를 유지보수하게 만들고 있다. 매일 죽은 코드 삭제, 실험 코드 정리, 테스트 작성, 불필요한 테스트 삭제, 중복 추상화 통합 같은 일을 루틴으로 돌린다.

10. 코딩은 정말 해결됐나

Boris는 “내가 하는 종류의 코딩은 상당 부분 해결됐다”고 말하면서도, 모든 코딩이 해결된 것은 아니라고 선을 긋는다.

아직 어려운 영역은 있다.

  • 깊은 시스템 코드
  • 분산 시스템(Distributed Systems)
  • 픽셀 단위 UI 검증
  • 복잡한 비전·컴퓨터 사용 작업

하지만 점점 더 많은 코드가 에이전트에 의해 작성되고 있다. 앞으로 뛰어난 빌더를 가르는 것은 코드를 직접 치는 속도가 아니라, 문제를 정의하고, 모델이 검증할 환경을 만들고, 사용자를 이해하고, 제품을 출시하는 능력이 된다.

11. CS 학생이 여전히 배워야 할 것

Boris는 자신이 프로그래밍을 실용적으로 배웠다고 말한다. 중학생 때 TI-83 계산기로 수학 시험을 더 잘 보기 위해 Basic을 배웠고, 나중에는 더 어려운 문제를 풀기 위해 어셈블리(Assembly)까지 배웠다.

그가 강조하는 것은 컴퓨터 과학 이론 자체보다 문제를 해결하기 위해 적용하는 능력이다.

AI 시대에도 여전히 중요한 것은 다음과 같다.

  • 내가 원하는 것을 직접 만들어보는 능력
  • 사용자가 원하는 것을 발견하는 능력
  • 제품 감각
  • 비즈니스 감각
  • 데이터 감각
  • 사용자와 대화하는 능력
  • 엔지니어링을 현실 문제에 연결하는 능력

요약하면, 먼저 자신이 원하는 것을 만들고, 그다음 사람들이 원하는 것을 만들어야 한다.

에이폼 적용 관점

① 이 얘기가 이커머스·물류 운영에 꽂히는 지점: AI에게 CS 업무, 송장 오류, 재고 불일치, 고객 문의 같은 반복 문제를 “절차”가 아니라 목표와 검증 기준으로 맡겨볼 수 있다.
② 지금 당장 시험해볼 것 하나: 기존 업무용 프롬프트를 절반 이상 지우고, “결과 기준·예외 처리·확인 방법”만 남겨 같은 작업 품질을 비교한다.
③ 우리 상황과 다른 전제 하나: 영상은 개발팀과 코드베이스 중심 사례라서, 물류 현장은 데이터 품질·권한·실물 확인 프로세스가 더 큰 병목일 수 있다.

진행자는 Claude Code의 창작자인 Boris Cherny를 소개하며, Anthropic이 전날 Opus 5를 출시했다고 말한다. Opus 5는 ARC-AGI 3에서 30% 성능을 냈고, 이전 최고 점수가 한 자릿수나 낮은 두 자릿수였다는 점을 언급한다.

Boris는 새 모델마다 많은 능력을 학습시키려 하지만 대부분은 실패하고, 일부만 성공한다고 설명한다. 때로는 직접 가르치지 않은 능력을 모델이 스스로 습득하기도 한다. Opus 5의 대표적 변화는 매우 오래 실행될 수 있다는 점이다. 자동 모드(Auto Mode)와 함께 쓰면 며칠, 몇 주, 몇 달 동안도 작업을 계속할 수 있으며, /goal 같은 스캐폴딩(Scaffolding) 없이도 과제를 이해하고 진행한다고 말한다.

또 하나의 큰 변화는 프롬프트 인젝션(Prompt Injection)에 거의 당하지 않는다는 점이다. 과거에는 인터넷 문서에 악성 지시가 숨어 있으면 모델이 그것을 따를 수 있었다. 하지만 Opus 5는 정렬(Alignment), 프롬프트 인젝션 분류기(Classifier), 자동 모드 분류기를 결합해 공격을 재현하기 어려운 수준이라고 설명한다. 이 분류기는 기계적 해석 가능성(Mechanistic Interpretability) 연구를 기반으로, 프롬프트 인젝션이 일어날 때 모델 내부에서 활성화되는 뉴런을 감지한다고 한다.

진행자는 Claude Code가 이번 릴리스에서 시스템 프롬프트(System Prompt)의 80% 이상을 삭제한 이유를 묻는다. Boris는 Claude Code가 제품이자 하네스(Harness)로서 항상 바뀐다고 답한다. 새 모델이 나오면 시스템 프롬프트, 도구, 도구 프롬프트를 계속 바꾸고 지운다. 한 모델을 위해 넣었던 지시가 다음 모델에서는 전혀 맞지 않을 수 있기 때문이다.

Opus 5는 매우 지능적이어서 과거 시스템 프롬프트가 보정하던 행동을 이제 스스로 한다. 그래서 Claude Code 팀은 시스템 프롬프트의 80%를 삭제했다. 사용자는 --system-prompt 옵션으로 원하는 시스템 프롬프트를 넣어 실험할 수 있고, simple=1 환경 변수로 단순 모드(Simple Mode)를 켜면 도구 프롬프트까지 포함해 거의 모든 프롬프트를 없앨 수 있다고 말한다.

Boris는 이를 절제 실험(Ablation)으로 사용한다고 설명한다. 프롬프트가 실제로 유용한지 보려면 지운 뒤 한 줄씩 다시 넣어 각 줄의 영향을 확인한다. 흥미롭게도 프롬프트가 없을 때 모델이 더 지능적으로 보이는 경우도 있지만, 제품으로 제공할 때는 사용자 경험과 안전한 동작을 위해 일부 프롬프트가 필요하다고 덧붙인다.

진행자는 예전 스타트업 제품 개발에서는 6개월마다 제품과 프롬프트를 지우는 일이 상상하기 어려웠다고 말한다. Boris는 전체 코드베이스를 다 지우는 것은 아니지만 많은 부분을 지운다고 답한다. Claude Code의 현재 하네스 코드는 대부분 안전, 권한, 정적 분석(Static Analysis), UI 관련 코드이며, 다른 많은 코드는 이미 제거했다고 한다.

Boris는 AI 제품을 만드는 사람이라면 새 모델이 나올 때 과감히 삭제해야 한다고 말한다. Claude Code 사용자는 6개월마다 Claude MD, 스킬(Skills), 훅(Hooks)을 지워보고 모델이 어떻게 동작하는지 확인하라고 권한다. Opus 5는 특히 과거 지시를 더 이상 필요로 하지 않을 수 있으므로 삭제 실험을 추천한다.

새 프롬프트를 만드는 방법에 대해 Boris는 “먼저 지우고, 사용해보고, 실패 지점을 관찰하라”고 말한다. 고객 상담 에이전트라면 실제 제품을 돌려보며 어디서 실패하는지 보고, Claude Code라면 자신의 코드베이스에서 어디서 막히는지 확인해야 한다. 같은 문제에서 반복해서 실패할 때만 지시를 다시 추가해야 한다.

그는 모델 기반 개발이 전통적 소프트웨어 개발과 다르다고 설명한다. 과거에는 큰 시스템을 설계하고, 단위 테스트를 만들고, 리아키텍처에 몇 달 또는 몇 년을 썼다. 하지만 모델은 살아 있는 생물처럼 세대마다 성격과 행동이 달라진다. 따라서 과학자처럼 실험하고 관찰하고 반복해야 한다.

평가셋(Eval)에 대해서는, 하네스보다 조금 더 오래가지만 영구적이지는 않다고 말한다. 모델이 빠르게 좋아져 평가를 포화(Saturate)하면 버리고 새 평가를 만들어야 한다. 평가셋은 보통 1~3세대 모델 정도 버틸 수 있다고 설명한다.

이어 Boris는 제품 과잉 잠재력(Product Overhang)과 모델 방해(Hobbling)를 설명한다. 제품 과잉 잠재력은 현재 모델이 이미 할 수 있는데 제품이 그 능력을 끌어내지 못하는 상태다. 모델 방해는 제품이 오히려 모델의 능력을 막는 상태다.

Claude Code의 초기 아이디어도 여기서 나왔다. Sonnet 3.5는 당시 훌륭한 코딩 모델이었지만, 기존 제품들은 한 줄 자동완성, 몇 줄 자동완성, 읽기 전용 채팅에 머물렀다. 모델은 전체 함수나 파일을 쓸 수 있었지만 제품이 그 능력을 막고 있었다. Claude Code는 가능한 단순한 하네스와 터미널 접근을 제공해 모델이 전체 파일과 기능을 만들 수 있게 했다.

진행자는 창업자들이 어떻게 Claude의 모델 방해를 줄이고 제품 과잉 잠재력을 포착할 수 있는지 묻는다. Boris는 모델에게 자신이 생각하는 것보다 약간 더 어려운 일을 주라고 답한다. 많은 사용자가 너무 구체적으로 절차를 지시하는데, 최신 모델에는 목표, 가드레일(Guardrails), 완료 조건(Exit Criteria)을 주고 맡기는 편이 낫다고 말한다.

예시로 Bun 코드베이스 이야기를 든다. Claude Code는 Bun 자바스크립트 런타임(JavaScript Runtime) 위에서 만들어졌고, Bun은 Zig로 작성되어 있었다. Zig는 저수준 언어라 메모리 관리 문제가 생길 수 있다. Bun 팀은 Claude로 퍼징(Fuzzing)을 하며 메모리 누수를 찾아왔고, 나중에는 Claude에게 Zig 코드를 Rust로 다시 쓰게 했다.

Bun은 테스트가 매우 잘 갖춰져 있어 결과 검증이 가능했다. Claude는 동적 워크플로(Dynamic Workflow)를 사용해 11일 동안 전체 코드베이스를 다시 썼다. 이는 과거라면 1년 이상 걸릴 수 있는 작업이었다고 Boris는 말한다. 이 결과는 실제 프로덕션에서 사용 중이라고 한다.

또 다른 예로 Boris는 Opus 5에 OpenCV를 주면 그림을 그릴 수 있다는 내부 실험을 소개한다. 초상화, 동물, 풍경을 그릴 수 있었고, 이는 모델이 별도로 그림 훈련을 받아서가 아니라 도구를 적절히 사용하도록 유도했기 때문이라고 설명한다. 그는 이런 미발견 능력이 현재 모델 안에 수십, 수백 개 있을 것이라고 본다.

프롬프트 엔지니어링(Prompt Engineering)에 대해서 Boris는 유행어가 계속 바뀌고 있다고 말한다. 지금 중요한 것은 문장을 예쁘게 쓰는 것이 아니라, Claude에게 조금 어려운 과제를 주고, 중간중간 자기 작업을 검증할 수 있게 만드는 능력이다. 검증(Verification)이 사람들이 가장 많이 놓치는 부분이라고 강조한다.

그는 Claude 데스크톱 앱을 Electron에서 Swift로 다시 만드는 실험을 소개한다. Claude에게 macOS 러너(Runner)를 연결하고, Electron 앱과 Swift 앱을 각각 실행해 스크린샷을 찍은 뒤 픽셀 단위로 비교하라고 지시했다. 이 작업은 인터뷰 당시 14~15일째 계속 실행 중이었다. Claude는 내부 Slack 채널을 만들어 몇 분마다 진행 스크린샷을 올리기도 했다.

Boris는 사람들에게 LinkedIn이나 Twitter의 “한 가지 비법”을 찾지 말라고 말한다. 그런 비법은 없으며, 모델을 경험적으로 다뤄야 한다. 너무 어려운 과제를 주고, 사람이 직접 일할 때처럼 검증 도구를 제공하고, 막히는 지점을 본 뒤 프롬프트, 스킬, MCP(Model Context Protocol) 등으로 보완하면 된다고 설명한다.

수천 개 에이전트를 실행하는 방법으로는 동적 워크플로(Dynamic Workflow)를 소개한다. Claude Code에서 “워크플로를 사용해”라고 말하면 Claude가 동적 워크플로를 발동할 수 있다. Bun을 샌드박스로 사용하고, 그 안에서 여러 에이전트를 시작해 순차·병렬 작업을 조직한다. Boris는 자신의 함수형 프로그래밍 배경을 바탕으로 이를 에이전트의 대수(Algebra for Agents)처럼 설계했다고 설명한다.

그는 이것을 새로운 형태의 테스트 타임 컴퓨트(Test-time Compute)라고 본다. 과거 스케일링 법칙은 신경망 크기, 학습 데이터, 학습 연산량에 집중했지만, 이제는 추론 시 생성 토큰과 에이전트 오케스트레이션도 중요해졌다는 것이다.

두 번째 방식은 루프(Loop)와 루틴(Routine)이다. 루프는 로컬에서 반복 실행되는 Claude 작업이고, 루틴은 클라우드에서 실행되어 노트북을 닫아도 계속 돈다. 동적 워크플로가 하나의 큰 작업을 쪼개는 방식이라면, 루프와 루틴은 반복 업무를 주기적으로 수행하는 방식이다.

Anthropic은 Claude가 자기 제품을 유지보수하게 하고 있다. CLI, iOS 앱, Android 앱, 데스크톱 앱에 대해 매일 20~30개 루틴이 돈다. 예를 들어 죽은 코드 삭제, 100% 배포된 실험 코드 정리, 테스트 커버리지 보강, 불필요한 테스트 삭제, 중복 추상화 통합 같은 일을 수행한다. 이를 통해 매일 수백 또는 수천 에이전트가 실행되고, 과거라면 수십~수백 명 엔지니어가 하던 유지보수 일을 처리한다고 말한다.

진행자는 “코딩은 해결됐다”는 Boris의 과거 발언을 언급한다. Boris는 자신이 하는 종류의 코딩은 상당 부분 해결됐지만, 모든 코딩이 해결된 것은 아니라고 답한다. 깊은 시스템 코드, 분산 시스템, 픽셀 단위 UI 검증 등은 여전히 어렵다. 그래도 점점 더 많은 코드가 에이전트로 작성되고 있으며, 중요한 능력은 경험적으로 모델을 다루는 태도라고 말한다.

마지막으로 CS 학생이 여전히 배워야 할 것에 대해 Boris는 자신의 경험을 이야기한다. 그는 중학생 때 TI-83 계산기에서 Basic으로 프로그램을 만들며 코딩을 배웠고, 더 어려운 수학 문제를 풀기 위해 어셈블리(Assembly)도 배웠다. 그의 프로그래밍 학습은 항상 실제 문제를 해결하기 위한 것이었다.

그는 학생들에게 컴퓨터 과학 자체도 중요하지만, 그것을 제품과 문제 해결에 적용하는 능력을 배우라고 조언한다. 스타트업 만들기, 제품 만들기, 디자인 감각, 비즈니스 감각, 데이터 과학, 사용자와 대화하는 능력이 컴퓨터 과학과 결합될 때 큰 가치가 생긴다고 말한다.

진행자는 이를 “먼저 자신이 원하는 것을 만들고, 그다음 사람들이 원하는 것을 만들어라”로 요약한다. Boris는 동의한다. 마지막으로 행사 참석자들에게 Max 20X 계정이 제공된다고 발표하고, 누군가 이 계정으로 여러 달 동안 수천 개 에이전트가 도는 무언가를 만들기를 기대한다고 말하며 대화를 마친다.
