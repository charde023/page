핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
데이터가 병목이라는 관점 모델 구조를 조금 바꾸는 것보다 실제 실패 사례를 보고 데이터를 고치는 것이 성능 개선에 더 직접적이다 모델이 틀린 이유는 대개 아키텍처가 아니라 데이터 분포와 라벨 정의에 있다
전문가 데이터(expert data) 의사, 변호사, 회계사, 시니어 엔지니어 같은 전문가 판단은 일반 크롤링 데이터로 대체하기 어렵다 AI가 전문직 일을 하려면 해당 분야 전문가의 판단 흔적이 필요하다
RL 환경(RL environment) 단순 정답 라벨이 아니라 모델이 행동하고 보상을 받는 환경이 필요하다 에이전트형 AI는 데이터셋보다 환경 제품이 중요해진다
벤치마크(benchmark) 모델 성능을 제대로 재려면 현실 업무와 비슷한 테스트가 필요하다 쉬운 시험은 곧 포화되고, 다음 난이도의 벤치마크가 필요하다
약한 감독(weak supervision) 전문가가 모든 데이터를 직접 라벨링하지 않아도 규칙·휴리스틱으로 대량 라벨을 만들 수 있다 라벨링 함수를 소프트웨어처럼 관리하면 전문가 시간을 확장할 수 있다
검증 에이전트(validation agent) 코드 결과물을 단순 LLM 판정이 아니라 테스트 스크립트로 검증하게 만든다 유연성과 신뢰성 사이의 중간지대다
확산 언어 모델(diffusion language model) 토큰을 왼쪽부터 하나씩 생성하지 않고 병렬로 개선해 속도를 크게 높인다 실시간 음성 AI처럼 지연시간이 중요한 곳에 유리하다
다국어 전이(multilingual transfer) 언어 간 데이터 조합에 따라 성능이 좋아지거나 나빠진다 어떤 데이터가 도움이 되는지는 직관보다 실험으로 재야 한다

내가 모를 만한 것 / 처음 보는 것

  • F1 점수(F1 score) — 정밀도(precision)와 재현율(recall)을 함께 반영하는 분류 성능 지표.
  • 거짓 양성(false positive), 거짓 음성(false negative) — 틀린 예측을 유형별로 나눠 보는 오류 분석의 기본 단위.
  • 온톨로지(ontology) — 데이터 라벨 체계나 클래스 정의. 예: 품절, 재고 있음, 상품 밀대(product pusher)를 별도 클래스로 둘지 결정하는 것.
  • 선호 데이터(preference-style data) — 정답이 하나로 검증되지 않고 사람이 더 낫다고 고르는 데이터. 디자인, 코드 스타일, 의료 판단 등이 해당.
  • 검증 가능한 보상(verifiable reward) — 코드 테스트 통과처럼 자동으로 맞고 틀림을 확인할 수 있는 보상.
  • Snorkel AI — 약한 감독(weak supervision), 데이터 프로그래밍(data programming)으로 유명한 데이터 중심 AI 회사.
  • 라벨링 함수(labeling function) — 사람이 직접 라벨을 다는 대신 규칙·휴리스틱·모델을 코드로 작성해 라벨을 생성하는 함수.
  • SWE-bench — 소프트웨어 엔지니어링 작업을 AI 에이전트가 해결하는지 평가하는 벤치마크.
  • LLM judge — LLM이 다른 모델의 답변이나 산출물을 채점하는 방식.
  • Tasteful pass — 단순히 맞는 코드가 아니라 코드베이스 관습, 간결성, 유지보수성까지 반영한 통과 지표.
  • TowBench/TaoBench [?원문] — 고객지원·도구사용형 에이전트를 평가하는 벤치마크로 언급됨. 전사상 TowBench/TaoBench가 혼재되어 있어 [?원문] 처리.
  • Domo Forge/Tao Forge [?원문] — Inception이 실제 사용 데이터 기반으로 합성 RL 환경을 만드는 시스템으로 소개한 명칭. 전사상 표기가 흔들림.
  • Chinchilla scaling law — 모델 크기와 학습 데이터량의 균형을 설명하는 대표적인 스케일링 법칙.
  • 다국어성의 저주(curse of multilinguality) — 한 모델에 많은 언어를 넣을수록 같은 성능을 유지하기 위해 더 큰 모델과 더 많은 데이터가 필요한 현상.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Focal Systems 면접 질문은 “핫도그/아님 분류 모델이 F1 85%일 때 다음에 뭘 하겠는가?”였다 — 정답은 논문을 읽거나 GELU를 써보는 것이 아니라 오답 데이터를 직접 보는 것.
  2. Francois는 연구 시절에는 데이터 5%, 아키텍처 95%를 생각했지만, 프로덕션에서는 비율이 뒤집힌다고 설명했다 — 지금은 대략 아키텍처 3%, 데이터 97%에 가깝다고 봄.
  3. ImageNet에는 개 품종 이미지가 많고, 사람도 에스키모 쉽독과 시베리안 허스키를 잘 구분하지 못한다고 언급 — “인간 수준”도 실제로 측정해야 한다는 예시.
  4. Salesforce 자동화 예시에서 UI가 바뀌면 과거 화면 캡처와 트레이스가 아무리 많아도 새 데이터가 필요하다고 설명 — 데이터 사업의 가치가 0이 되지 않는 이유.
  5. AI 데이터 회사 카테고리는 지난 10년간 약 1,000억 달러 이상 시장가치를 만들었다고 주장.
  6. 데이터셋과 RL 환경은 “zip 파일”이 아니라 제품(product) 으로 봐야 한다고 강조.
  7. Snorkel의 Data 1.0에서는 라벨 하나가 대략 30초 인간 판단으로 만들어지는 단순 라벨링을 예로 들었다.
  8. Data 2.0에서는 Docker 환경, 루브릭(rubric), 검증기(verifier), 태스크 환경을 만들기 위해 사람이 한 자릿수에서 세 자릿수 시간을 쓸 수 있다고 설명.
  9. Senior SWE Bench는 코딩 에이전트를 주니어가 아니라 시니어 엔지니어처럼 평가하려는 벤치마크.
  10. 검증 방식은 단위 테스트(unit test)의 신뢰성과 LLM judge의 유연성 사이에 validation agent를 둔다.
  11. Inception의 Mercury 2 모델은 1,000 tokens/sec 이상 속도를 낼 수 있다고 주장.
  12. 실시간 음성 AI 파이프라인은 음성-텍스트(STT), LLM, 텍스트-음성(TTS)의 캐스케이드 구조이며, 병목은 LLM 지연시간이라고 설명.
  13. Mercury 2.5는 도메인 특화 데이터 학습 전 약 50% 정확도, Tao Forge 합성 태스크 학습 후 23% 이상 향상되었다고 설명.
  14. YC 스타트업 대상 Inception 크레딧은 50만 달러($500,000) 라고 언급.
  15. 태국어(Thai)는 MadLad 400 기준 영어 토큰 수의 0.6%에 불과하다고 설명.
  16. 다국어 전이는 대칭이 아니다 — 포르투갈어가 스페인어에 도움이 된다고 해서 스페인어가 포르투갈어에 같은 정도로 도움 된다고 볼 수 없다.
  17. 언어 전이에는 언어 계통(language family)보다 문자 체계(script) 가 약간 더 중요하게 나타났다고 설명.

2 데이터셋은 제품이다 도메인별 AI 능력은 앱처럼 독립적인 데이터·환경 회사가 만들 가능성이 크다

5 Inception: 확산 언어 모델 병렬 토큰 생성으로 초고속 추론을 달성하고, 실시간 음성 AI에 유리하다
6 합성 RL 환경 실제 로그와 도메인 지식을 바탕으로 고객지원형 환경과 태스크를 합성한다

1. 왜 데이터가 별도의 밤을 차지할 만큼 중요한가

Francois Chaubard는 2016년 Focal Systems를 시작할 당시만 해도 많은 사람이 데이터를 상품재(commodity)처럼 봤다고 회상한다. “ImageNet을 이미 다운로드했는데 더 얼마나 데이터가 필요하냐”는 분위기였다.

하지만 실제 프로덕션에서는 달랐다. 모델이 F1 85%에 도달한 뒤 다음 개선을 하려면 레이어를 추가하거나 활성화 함수(activation function)를 바꾸는 것이 핵심이 아니었다. 먼저 해야 할 일은 모델이 틀린 데이터를 보는 것이었다.

예를 들어 매대의 재고 있음/품절(in-stock/out-of-stock)을 판단하는 모델에서 냉장고 유리에 김이 서리거나, 사람이 앞을 가리거나, 상품 밀대가 상품처럼 보이면 모델은 틀린다. 이 문제는 레이어 수를 늘려도 해결되지 않는다. 데이터 정의, 라벨 체계, 예외 케이스 수집이 필요하다.

핵심은 “모델을 더 똑똑하게 만들기 전에, 모델이 무엇을 못 보는지 데이터에서 확인하라”는 것이다.

2. 프로덕션에서는 데이터 비중이 압도적으로 커진다

연구실에서는 아키텍처(architecture)와 알고리즘이 중심처럼 보인다. 하지만 제품으로 나가면 학습 데이터와 실제 사용 데이터의 분포 차이(distribution shift)가 드러난다.

훈련 데이터(train distribution)는 깔끔하지만, 실제 서비스의 테스트 분포(test distribution)는 지저분하다. UI가 바뀌고, 조명이 바뀌고, 사용자가 예상과 다르게 행동하고, 예외 케이스가 계속 등장한다.

따라서 AI로 경제 활동을 자동화하려면 두 가지가 필요하다.

  1. 전문가 데이터(expert data)
    의사, 회계사, 변호사, 트레이더, 엔지니어의 실제 판단 데이터.

  2. 전문가 RL 환경(expert RL environment)
    모델이 행동하고 검증 가능한 보상(verifiable reward)을 받을 수 있는 환경.

정답이 명확한 문제도 있지만, 많은 경제 활동은 선호(preference)와 판단(judgment)의 문제다. “이 디자인이 더 좋은가?”, “이 코드는 작동하지만 유지보수 가능한가?”, “이 환자에게 어떤 처방이 적절한가?” 같은 문제는 단순 정답 라벨로 끝나지 않는다.

3. 데이터셋과 환경은 zip 파일이 아니라 제품이다

Francois는 데이터셋과 환경을 단순 파일 묶음이 아니라 제품(product) 으로 봐야 한다고 말한다.

좋은 데이터셋에는 클래스 정의, 라벨 기준, 예외 처리, 검수, 업데이트, 버전 관리, 전문가 네트워크, 실제 분포 반영이 들어간다.

그는 스마트폰 앱에 비유한다. iPhone이 손전등 기능은 직접 만들 수 있지만, 식료품 배송망 전체를 Apple이 직접 만들 필요는 없다. Instacart 같은 전문 회사가 따로 존재하는 것이 자연스럽다.

마찬가지로 LLM 회사가 모든 도메인의 AI 의사, AI 변호사, AI 회계사를 직접 잘 만들 필요는 없다. 각 도메인에 깊게 들어가 전문가 데이터와 RL 환경을 만드는 회사가 생길 수 있다.

4. Snorkel: 전문가 감독을 어떻게 확장할 것인가

Vincent Sunn Chen은 Snorkel의 핵심 관점을 설명한다. 병목은 단순 인력이 아니라 전문가의 머릿속에 있는 판단 기준을 데이터셋으로 옮기는 것이다.

기존 Data 1.0은 사람이 직접 라벨을 다는 방식이었다. 하지만 이 방식에는 문제가 있다.

  • 데이터 포인트마다 사람이 새로 판단해야 하므로 확장성이 낮다.
  • 노이즈를 줄이려면 여러 명이 중복 라벨링해야 한다.
  • 스펙이나 스키마가 바뀌면 처음부터 다시 해야 한다.
  • 왜 그런 라벨이 붙었는지 근거(provenance)가 남지 않는다.

Snorkel의 접근은 데이터 프로그래밍(data programming) 이다. 전문가 판단을 라벨링 함수(labeling function)라는 소프트웨어 형태로 표현한다. 예를 들어 스팸 메일을 판단하는 여러 휴리스틱을 코드로 만들고, 이들이 겹치거나 틀릴 때 약한 감독(weak supervision) 모델로 노이즈를 제거한다.

이 방식의 장점은 라벨링이 소프트웨어처럼 확장, 수정, 감사, 협업 가능해진다는 점이다.

5. Data 2.0: 에이전트 시대의 데이터는 더 복잡하다

Vincent는 지금의 데이터 문제를 Data 2.0이라고 부른다. 이제 데이터는 단순 질문-답변 쌍이 아니다.

에이전트가 실제 환경에서 긴 작업을 수행하려면 다음이 필요하다.

  • 태스크(task)
  • 루브릭(rubric)
  • 검증기(verifier)
  • 도구(tool)
  • Docker 환경
  • 긴 실행 궤적(trajectory)
  • 주관적 품질 평가

소프트웨어 코딩을 예로 들면, HumanEval 같은 기본 코딩 평가 benchmark는 이미 포화되고 있다. 하지만 실제 시니어 엔지니어 업무는 훨씬 복잡하다. 아키텍처 결정, 리팩터링, 코드 스타일, 유지보수성, 기존 코드베이스 관습까지 봐야 한다.

6. Senior SWE Bench: 코딩 에이전트를 시니어처럼 평가하기

Snorkel은 Princeton의 SWE-bench 팀과 함께 Senior SWE Bench를 만들었다. 목적은 코딩 에이전트를 단순 버그 수정자가 아니라 시니어 엔지니어 수준으로 평가하는 것이다.

기존 벤치마크는 지시가 너무 구체적이다. 실제 업무에서는 Slack 메시지처럼 모호한 요청이 많다.

예:

  • “로그를 보니 문제가 있어. 원인을 찾아서 고쳐줘.”
  • “이 사용자 스토리를 보고 기능을 구현해줘.”
  • “전체 코드 구조를 고려해서 리팩터링해줘.”

평가는 단순히 코드가 merge 가능한지만 보지 않는다. 코드가 좋은 취향(taste)을 보이는지, 불필요한 부풀림(bloat)이 적은지, 코드베이스 관습에 맞는지도 본다.

이를 위해 Snorkel은 validation agent를 사용한다. 전문가가 간단한 validation spec을 작성하면, 검증 에이전트가 이를 바탕으로 테스트 스크립트를 만들고 실제 코드 경로를 실행해 검증한다.

7. Inception: 확산 언어 모델과 초고속 추론

Volo Kuleshov는 Inception Labs의 확산 언어 모델(diffusion language model)을 소개한다.

일반적인 자기회귀 모델(autoregressive model)은 토큰을 왼쪽에서 오른쪽으로 하나씩 생성한다. 반면 확산 언어 모델은 처음에 전체 시퀀스의 거친 초안을 만들고, 여러 단계에 걸쳐 병렬로 개선한다.

이 방식의 큰 장점은 속도다. Mercury 2 모델은 1초에 1,000개 이상의 토큰을 생성할 수 있다고 설명한다.

이 속도는 실시간 음성 AI에서 중요하다. 현재 음성 에이전트는 보통 다음 구조를 가진다.

  1. 음성을 텍스트로 변환(STT)
  2. LLM이 응답 생성
  3. 텍스트를 음성으로 변환(TTS)

여기서 LLM 지연시간이 전체 사용자 경험의 병목이 된다. LLM이 빨라지면 더 자연스러운 대화가 가능하고, 같은 지연시간 안에서 더 큰 모델이나 더 긴 추론을 사용할 수 있다.

8. 좋은 음성 AI에도 데이터와 평가가 병목이다

Volo는 알고리즘만으로는 충분하지 않다고 말한다. 음성 고객지원 에이전트를 잘 만들려면 훈련 데이터와 평가 데이터가 모두 중요하다.

현재 널리 쓰이는 TowBench/TaoBench [?원문]는 실제 고객지원 복잡도를 충분히 반영하지 못한다고 지적한다. 실제 비즈니스 환경에는 더 많은 정책, 도구, 예외 상황, 사용자 유형이 있다. 벤치마크 점수는 90점대가 나와도 실제 운영 로그에서는 훨씬 낮은 점수가 나올 수 있다.

그래서 Inception은 Tao Forge/Domo Forge [?원문]라는 시스템을 사용해 실제 데이터 기반의 합성 RL 환경을 만든다.

과정은 다음과 같다.

  1. 만들고 싶은 환경 설명을 입력한다. 예: 은행 고객지원.
  2. 실제 사용 로그나 비즈니스 지식을 바탕으로 정책, 사용자, 계정, 도구, 데이터베이스를 합성한다.
  3. 사용자 목표와 페르소나를 만든다. 예: 계좌 개설, 전화번호 변경, 예약 변경.
  4. 에이전트가 해결할 태스크를 생성한다.
  5. 너무 쉽거나 너무 어려운 태스크를 조정한다.
  6. 실제 사용자 피드백으로 환경 생성 절차를 계속 개선한다.

9. Shayne Longpre: 다국어 사전학습의 전이와 간섭

Shayne Longpre는 다국어 사전학습(multilingual pre-training)을 다룬다. 핵심 질문은 “여러 언어 데이터를 어떻게 섞어야 특정 언어 성능이 좋아지는가?”이다.

영어 중심의 스케일링 법칙 연구는 많지만, 영어 외 언어에 대한 연구는 부족하다. 예를 들어 태국어는 전 세계에 약 8천만 명 화자가 있지만, Common Crawl 기반 MadLad 400에서 태국어 토큰은 영어의 0.6% 수준이다.

태국어만으로 모델을 학습하면 데이터가 적어 같은 데이터를 반복 학습하게 되고, 과적합(overfitting)이 생긴다. 반대로 영어 등 다른 언어를 섞으면 도움이 될 수 있지만, 아무 언어나 섞는다고 좋은 것은 아니다.

어떤 언어는 전이(transfer)를 일으켜 도움을 주고, 어떤 언어는 간섭(interference)을 일으켜 성능을 떨어뜨린다.

10. 언어 간 전이는 직관이 아니라 측정 문제다

Shayne은 언어 간 전이를 행렬(matrix)로 측정한다. 예를 들어 태국어 모델을 학습할 때 영어, 인도네시아어, 말레이어, 라오어, 크로아티아어 등이 얼마나 도움 되는지 실험한다.

중요한 발견은 다음과 같다.

  • 전이는 대칭이 아니다. A가 B에 도움 된다고 B가 A에 똑같이 도움 되는 것은 아니다.
  • 모델이 커질수록 언어 간 간섭이 줄고 시너지가 늘어난다.
  • 모델이 작으면 여러 언어가 내부 공간을 두고 경쟁해 간섭이 커진다.
  • 언어 계통보다 문자 체계(script)가 조금 더 중요하게 나타났다.
  • 그러나 최종적으로는 실제 데이터 품질, 노이즈, 주제 분포가 중요하므로 실험이 필요하다.

이 연구는 언어뿐 아니라 도메인 데이터 혼합에도 적용할 수 있다. 예를 들어 이커머스 상품 데이터, CS 상담 데이터, 물류 클레임 데이터, 리뷰 데이터가 서로 어떻게 도움 또는 간섭을 주는지 같은 문제로 확장 가능하다.

에이폼 적용 관점

① 이 얘기가 이커머스·물류 운영에 꽂히는 지점: 우리 AI의 성능은 모델 선택보다 반품, 품절, 오배송, CS, 재고 예외 케이스 데이터를 얼마나 잘 분류·검수·업데이트하느냐에 달려 있다.
② 지금 당장 시험해볼 것 하나: 최근 CS/물류 오류 100건을 모아 거짓 양성·거짓 음성처럼 실패 유형 버킷을 만들고, 가장 큰 3개 원인을 라벨 기준으로 정리한다.
③ 우리 상황과 다른 전제 하나: 발표는 프런티어 AI 연구·벤치마크 중심이라, 에이폼은 대규모 모델 학습보다 운영 데이터 정리와 업무 자동화 평가셋 구축에 초점을 맞춰야 한다.

  • [ ] 품절, 부분품절, 오배송, 송장오류, 고객변심 등 운영 온톨로지를 다시 정의한다.
  • [ ] 사람이 매번 판단하지 않도록 라벨링 규칙(labeling function) 후보를 만든다.
  • [ ] CS 자동응답이나 물류 판단 AI를 위한 내부 벤치마크 50문항을 만든다.

  • [ ] 실제 업무 로그 기반으로 AI 테스트셋을 주기적으로 업데이트한다.

전체 전사 펼치기

YC Data Club에 오신 것을 환영합니다. 오늘 주제는 데이터입니다.

Francois Chaubard는 2016년 Focal Systems를 시작했을 때 많은 사람이 데이터를 상품재처럼 봤다고 말한다. ImageNet을 이미 다운로드했는데 더 많은 데이터가 왜 필요하냐는 분위기였다. 하지만 이후 데이터 관련 회사들은 약 1,000억 달러 이상의 시장가치를 만들었고, 투자자들의 시각도 바뀌었다.

그는 면접에서 자주 이런 질문을 했다고 한다. “핫도그/아님 분류 모델이 F1 점수(F1 score) 85%에 도달했다. 다음에 무엇을 하겠는가?” 논문을 읽거나 ReLU와 GELU를 비교하거나 레이어를 추가하겠다는 답은 틀렸다. 정답은 데이터를 보는 것이다. 거짓 양성(false positive), 거짓 음성(false negative)을 모아 유형별로 나누고 가장 큰 문제를 찾는 것이다.

Focal의 재고 있음/품절(in-stock/out-of-stock) 문제에서는 냉장고 유리에 김이 서리거나, 사람이 앞을 가리거나, 상품 밀대(product pusher)가 상품처럼 보이는 문제가 있었다. 이런 경우 레이어 수를 늘린다고 해결되지 않는다. 데이터와 라벨 정의를 봐야 한다.

연구에서는 아키텍처에 95%, 데이터에 5%를 쓰는 것처럼 느껴질 수 있지만, 프로덕션에서는 반대다. 지금은 데이터가 97%, 아키텍처가 3%에 가깝다. Transformer가 잘 작동하기 때문에 병목은 데이터가 되었다.

훈련 데이터 분포는 깔끔하지만 실제 서비스에 나가면 테스트 분포가 달라진다. 그래서 경제를 자동화하려면 전문가 데이터(expert data)와 전문가 RL 환경(expert RL environment)이 필요하다. 코드처럼 검증 가능한 보상(verifiable reward)이 있는 영역도 있지만, 디자인 선호, 코드 스타일, 의료 판단, 법적 판단처럼 주관적인 선호 데이터(preference-style data)가 필요한 영역도 많다.

데이터셋과 환경은 단순 zip 파일이 아니라 제품(product)이다. 좋은 데이터셋을 만드는 데는 라벨 기준, 예외 처리, 검수, 업데이트가 필요하다. LLM이 의사, 회계사, 변호사, 트레이더, 치료사 역할을 잘하려면 각 도메인의 최신 고품질 데이터와 RL 환경이 필요하다. 스마트폰에 앱이 많듯이 AI에도 도메인별 데이터·환경 회사가 많이 필요할 수 있다.

이어 Vincent Sunn Chen이 발표한다. 그는 Snorkel의 창립 멤버 중 한 명이며, 현재 벤치마크와 평가 연구를 이끈다. Snorkel의 핵심 논지는 전문가의 머릿속에 있는 판단 기준을 데이터셋으로 옮기는 것이 병목이라는 것이다. 의사, 임상의, 기자, 엔지니어처럼 “좋은 결과가 무엇인지” 아는 사람들의 판단을 확장해야 한다.

Data 1.0은 기본 라벨링과 QA였다. 사람이 30초 정도 판단해서 선호 라벨이나 질문-답변 쌍을 만드는 방식이다. 하지만 지금 Data 2.0에서는 태스크, 루브릭(rubric), 검증기(verifier), Docker 환경, 에이전트가 활동할 세계 전체를 만들어야 한다. 이런 데이터는 사람이 만드는 데 한 자릿수에서 세 자릿수 시간이 걸릴 수 있다.

수동 라벨링은 확장성이 낮고, 노이즈에 약하며, 스키마나 태스크 정의가 바뀌면 처음부터 다시 해야 한다. 또 왜 그런 라벨이 붙었는지 근거(provenance)가 남지 않는다. Snorkel은 이를 해결하기 위해 데이터 프로그래밍(data programming)을 사용했다. 전문가 판단을 라벨링 함수(labeling function)라는 소프트웨어 형태로 표현하고, 여러 약한 신호가 겹치고 틀릴 때 약한 감독(weak supervision) 모델로 노이즈를 제거한다.

Data 2.0에서는 코딩 에이전트 평가가 예시로 나온다. HumanEval 같은 기본 평가는 포화되었지만, 실제 코딩 에이전트는 아키텍처 결정, 리팩터링, 코드베이스 전체 수정 같은 시니어 엔지니어 업무를 맡고 있다. 그래서 Snorkel은 Princeton의 SWE-bench 팀과 Senior SWE Bench를 만들었다.

이 벤치마크는 과도하게 구체적인 지시가 아니라 Slack 메시지처럼 현실적인 지시를 사용한다. “로그를 보고 원인을 찾아라”, “사용자 스토리를 구현하라” 같은 식이다. 평가는 정답 여부뿐 아니라 코드 취향(taste), 유지보수성, 불필요한 코드 부풀림(bloat), 코드베이스 관습 준수까지 본다. 이를 위해 validation agent를 사용한다. 전문가가 validation spec을 쓰면, 에이전트가 테스트 스크립트를 만들고 실제 코드 경로를 실행해 검증한다.

다음 발표자는 Volo Kuleshov다. 그는 Inception Labs에서 확산 언어 모델(diffusion language model)을 개발하고 있다. 전통적인 자기회귀 모델(autoregressive model)은 토큰을 왼쪽에서 오른쪽으로 하나씩 생성하지만, 확산 모델은 전체 토큰을 한 번에 거칠게 만들고 여러 단계에 걸쳐 병렬로 개선한다. 이 방식은 한 단계에서 여러 토큰을 만들 수 있어 매우 빠르다. Mercury 2 모델은 1초에 1,000개 이상의 토큰을 생성할 수 있다고 한다.

초고속 추론은 실시간 음성 AI에서 특히 중요하다. 음성 에이전트는 보통 음성-텍스트(STT), LLM, 텍스트-음성(TTS) 구조를 가지며, 전체 지연시간은 LLM에 의해 크게 제한된다. LLM이 빨라지면 실시간 대화가 자연스러워지고, 더 큰 모델이나 더 긴 추론을 사용할 수 있다.

그러나 좋은 음성 모델을 만들려면 알고리즘뿐 아니라 데이터와 평가가 중요하다. 현재 많이 쓰이는 TowBench/TaoBench [?원문]는 실제 고객지원 환경의 복잡도를 충분히 담지 못한다. 실제 운영에서는 더 많은 정책, 도구, 예외 상황이 존재한다. 벤치마크 점수는 높아도 실제 로그에서는 성능이 낮고 모델 간 차이도 커진다.

Inception은 Tao Forge/Domo Forge [?원문]라는 시스템으로 실제 사용자 상호작용과 데이터 제공자 데이터를 바탕으로 RL 환경을 합성한다. 예를 들어 은행 고객지원 환경을 만들려면 은행 정책, 영업시간, 사용자, 계좌 데이터베이스, 도구를 합성한다. 실제 데이터가 없으면 인터넷에서 수집한 비즈니스 지식 그래프(business knowledge graph)를 사용한다. 이후 계좌 개설, 계좌 해지, 전화번호 변경 같은 시나리오와 사용자 페르소나를 만들고, 에이전트가 해결할 태스크를 생성한다. 너무 쉬운 태스크나 너무 어려운 태스크는 조정한다.

Mercury 2.5는 도메인 특화 학습 전 약 50% 정확도였고, Tao Forge가 만든 태스크로 학습한 뒤 다른 환경에서 23% 이상 향상되었다. YC 스타트업에는 50만 달러 크레딧을 제공한다고 덧붙인다.

마지막 발표자는 Shayne Longpre다. 그는 MIT 박사과정을 마치고 Anthropic에 합류했으며, Google 인턴십 중 수행한 다국어 사전학습(multilingual pre-training) 연구를 소개한다.

기존 스케일링 법칙과 데이터 혼합 연구는 대부분 영어 데이터와 영어 평가에 집중되어 있다. 하지만 영어 외 언어는 데이터가 매우 부족하다. 예를 들어 태국어는 약 8천만 명의 화자가 있지만, MadLad 400에서 태국어 토큰은 영어의 0.6%뿐이다.

태국어만으로 모델을 학습하면 같은 데이터를 반복 학습하게 되어 과적합한다. 반대로 모든 언어를 무작정 섞으면 어떤 언어는 도움이 되고 어떤 언어는 방해가 된다. 따라서 어떤 언어가 특정 언어에 전이(transfer)를 주고, 어떤 언어가 간섭(interference)을 일으키는지 측정해야 한다.

연구진은 언어 간 전이 행렬(cross-lingual transfer matrix)을 만들었다. 빨간색은 시너지, 파란색은 간섭을 뜻한다. 스페인어에는 포르투갈어, 이탈리아어, 프랑스어가 도움이 되었고, 일본어는 해로운 쪽으로 나타났다. 모델이 커질수록 파란색 간섭이 줄고 빨간색 시너지가 늘어난다. 모델이 작으면 언어들이 내부 표현 공간을 두고 경쟁한다.

중요한 점은 전이가 대칭이 아니라는 것이다. 포르투갈어가 스페인어에 도움이 된다고 해서 스페인어가 포르투갈어에 같은 만큼 도움이 되는 것은 아니다. 또 언어 계통(language family)보다 문자 체계(script)가 약간 더 중요하게 나타났다. 이는 토크나이저(tokenizer)와 표현 방식의 영향 때문일 수 있다.

마지막으로 Shayne은 Chinchilla 스케일링 법칙을 다국어 상황에 맞게 확장한다. 단일 데이터량 D만 보는 대신, 목표 언어 데이터, 가까운 전이 언어 데이터, 나머지 데이터, 반복 학습에 따른 수확체감(diminishing returns)을 함께 모델링한다. 이를 통해 특정 언어에 대해 어떤 데이터 혼합과 모델 크기가 좋은지 예측할 수 있다.

그는 이 방법이 언어뿐 아니라 여러 도메인 데이터 소스를 섞는 문제에도 일반화될 수 있다고 말한다. 모델의 능력, 위험, 한계를 이해하려면 데이터 소스들이 어떻게 상호작용했는지 봐야 한다.
