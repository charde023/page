내가 모를 만한 것 / 처음 보는 것

  • Signal Layer — Slack·Linear 같은 외부 채널을 Claude Code MCP로 연결해 에이전트가 대신 우선순위를 판별하게 하는 추상 계층. Proser의 용어.
  • Remote Control (Claude Code) — --remote-control 플래그(또는 config enable remote control)를 켜면 스마트폰에서 동일 세션에 접속·메시지 전송 가능. LTE 환경에서도 동작.
  • Shower Principle (샤워 원리) — 집중 모드(Focus Mode)와 확산 모드(Diffuse Mode)의 구분. 책상을 떠났을 때 창의적 해결책이 떠오르는 신경과학적 현상. 저자는 에이전트 Remote Control이 이를 생산성과 결합시킨다고 주장.
  • JSONL 대화 파일 — Claude Code가 로컬에 저장하는 세션 로그. 경로 지정 후 Claude에게 직접 넘겨 패턴 분석 가능.
  • Codex — 발표 문맥상 GitHub 백로그 태스크를 일괄 큐잉하는 자동화 도구로 언급됨(OpenAI Codex가 아닌 내부 워크플로 용어일 가능성 있음).
  • Oura Ring MCP — Oura 스마트 링의 수면·심박 데이터를 MCP로 Claude에 노출. GitHub에 서드파티 프로젝트 존재.
  • Work Trees (git worktree) — 에이전트 여러 개가 동일 저장소를 동시에 건드려 충돌이 나지 않도록 독립 작업 디렉터리를 분리하는 git 기능. English-한국어

1. 번아웃 문제 — 도구는 핵폭탄, 신경계는 구석기

Claude Code 같은 AI 코딩 도구로 어느 때보다 많은 것을 만들어내면서도 오전 11시에 기진맥진한 개발자가 늘고 있다. 원인은 컨텍스트 전환 비용이 기존보다 훨씬 빨리 쌓이기 때문이다. 에이전트가 빠르게 작업을 처리할수록 인간 쪽에서 판단·검토·다음 지시를 내려야 하는 빈도도 함께 올라간다.

Proser는 이를 "도구는 핵폭탄 수준이 됐는데 우리 신경계는 여전히 고대인"이라고 표현한다.

2. 구체적 사례 — Slack 버그 수정과 닫힌 루프

WorkOS의 Slack 블로그봇에서 acronym(SCIM, SSO 등)을 잘못 처리하는 버그가 보고됐다. 기존 방식이었다면 여러 Slack 창을 오가며 컨텍스트를 잃었겠지만, 이번에는 Claude Code에 Slack 읽기·쓰기 MCP와 Linear 티켓 MCP를 함께 부여했다.

지시는 단 하나: "이 버그를 고치고, 직접 검증하고, 완료될 때까지 멈추지 마라."

결과: Claude가 수정 후 Slack 채널에 테스트 포스트를 게시하고, 블로그봇이 그걸 받아 실행하고, Claude가 출력을 확인해 "이 버그는 완전히 수정됐다"고 스스로 선언했다. 돌아왔을 때 완결된 루프만 기다리고 있었다.

이를 가능하게 한 핵심 조건: - 에이전트에게 검증 도구를 줄 것 (Slack 쓰기 권한) - 완료 기준을 명시할 것 ("직접 검증하고, 완료까지 멈추지 마라") - 인간은 검토만 하면 되는 구조

3. 병목 이동 — 에이전트가 아니라 인간

이제 에이전트는 충분히 맥락을 주고 검증 기준을 제시하면 무한히 루프를 돌 수 있다. Claude API를 통해 에이전트는 무한 확장(infinite scaling)이 가능하다. 반면 인간의 주의력(attention)은 여전히 "고기 공간(meat space)"에 존재하며 부하에 따라 저하된다.

Simon Wilson도 에이전트 4개를 병렬로 돌리면 오전 11시에 녹초가 된다고 말한 바 있다. 에이전트가 병목이 아니라 우리가 병목이다.

4. 지속 가능한 AI 개발 스택 4가지

Proser가 제시하는 네 가지 전략:

① Signal Layer (신호 계층) Slack·Linear 같은 외부 알림 채널을 직접 확인하는 대신, Claude Code에 MCP로 연결해 "고우선도 멘션·DM만 추출"하게 한다. 개발자는 에이전트가 필터링한 결과만 보면 되므로 집중 흐름을 유지할 수 있다.

② 음성 우선 코딩 (Voice-First Coding) 1년 6개월간 사용하면서 분당 속도가 90 WPM에서 184 WPM으로 올랐다. 더 중요한 건 여러 Cursor 창, Claude 탭을 병렬로 구동하면서 동시에 지시를 내릴 수 있다는 것. 타이핑 속도로는 따라갈 수 없는 병렬 워크플로가 가능해진다.

③ Remote Control (원격 제어) Shower Principle: 책상에서 집중 모드일 때는 시야가 좁아지고 창의적 해결책을 놓친다. 산책·샤워·놀이 중 확산 모드에서 오히려 전체 해법이 떠오른다. 그런데 지금까지는 책상 이탈 = 작업 중단이었다.

Claude Code의 remote control 옵션을 켜면 스마트폰에서 동일 세션에 접속해 메시지를 보낼 수 있다. LTE 환경에서도 동작. 아이디어가 떠오르면 그 자리에서 바로 에이전트에 전달 → 책상으로 돌아왔을 때 이미 적용되어 있다.

④ 시스템 자기개선 (Self-Improving System) Claude Code의 모든 대화는 로컬 JSONL 파일로 저장된다. Claude Hooks를 이용해 세션 종료 시(또는 PR 머지 시) "우리가 오래 씨름한 구간, 모호성 제거에 시간이 많이 든 구간을 추출해 별도 저장소에 보관"하는 패스를 자동 실행할 수 있다. 주간 단위로 이 저장소를 Claude로 분석해 skill을 정제하면 루프가 점점 짧아진다.

Claude Code에는 skill 빌드·평가·개선·자연어 → bespoke skill 생성 기능이 내장되어 있다.

5. 검증 게이트 3단계 — "속도는 안전을 전제로 한다"

에이전트에게 원격 제어를 넘기려면 신뢰할 수 있는 자기검증이 먼저다.

단계 내용
Gate 1 lint + build + unit test. 에이전트가 hooks로 매번 자동 실행
Gate 2 브라우저 직접 확인. --chrome 플래그 부여 후 로그인 같은 핵심 플로 클릭 검증
Gate 3 Critic 에이전트. Constitutional AI 방식 — "준수해야 할 원칙 목록"을 별도 에이전트가 검토하고 피드백

6. 균형 잡힌 하루 워크플로 제안

  1. 오전 집중 세션: GitHub 백로그 정리, Codex에 태스크 큐잉, 핵심 기능은 Claude Code나 IDE에서 직접 시작
  2. 에이전트 분배: 진행 방향 확인 후 책상 이탈
  3. 이동 중: LTE로 세션 접속, 아이디어 전달, PR 리뷰 (GitHub Mobile에 자연어 코멘트)
  4. 돌아와서: 에이전트가 이미 처리한 결과 검토 후 다음 배치

이 사이클이 반복되면 RSI(반복성 긴장 손상)도 줄고, 신선한 관점도 유지된다.

7. Q&A 핵심 요약

주니어 개발자 skill 개발 우려

"아직 모르는 것에 AI를 쓰지 마라." TypeScript, AWS 배포 등 기초를 손으로 먼저 쌓아야 Claude가 틀렸을 때 즉시 알아챌 수 있다. LLM으로 오히려 더 빠르고 깊게 공부할 수 있다 — "내가 모른다"는 것을 솔직하게 인정하면 더 빨리 채울 수 있다.

JSONL 파일 처리

직접 가리켜도 동작하지만, hooks로 세션 종료 시 "고난이도 구간만 추출 → Obsidian이나 Markdown 파일에 저장"하는 방식이 더 효율적. 분석 프롬프트: "미래에 더 효율적으로 할 수 있었던 것, 오래 씨름한 패턴을 찾아라."

야간 에이전트 (Night Shift)

Cron 잡으로 야간에 콘텐츠 생성 실험 중. 아침에 일어나서 결과 검토 → 작은 비율만 머지. 향후 목표: Linear에 "agent-ready" 태그 붙이고 15분마다 도는 루프.

복잡한 멀티스택 기능

git worktree로 에이전트가 병렬로 서로 방해 없이 작업. 명확한 프롬프트를 가진 에이전트 팀 구성. unit test + CI 강화. 모델이 발전할수록 이런 큰 기능도 하네스(harness)가 더 안정적으로 처리할 것으로 예상.

맞죠, 전보다 훨씬 많은 걸 해내면서도 하루가 끝나면 완전히 녹아있고, 아드레날린이 계속 쏟아지는 느낌. 저도 그렇습니다. 그 중에서도 제일 힘든 게 컨텍스트 전환(context switching) 비용인데, 원래도 비쌌는데 지금은 더 심해졌습니다.

도구는 말도 안 되게 강력해졌고, 우리 기술은 전보다 더 많이 요구받고 있는데 오전 11시면 탈진 상태가 됩니다.

구체적인 사례를 들어드릴게요. 저는 WorkOS의 Applied AI 팀에서 일합니다. Slack 봇을 만들고 있었는데, 블로그 글을 한 번도 써본 적 없는 사람도 Slack 채널에서 간단한 요청만 하면 제대로 된 블로그 포스트가 나오게 하는 봇이었습니다.

동료 한 명이 "sentence case(문장 첫 글자 대문자) 처리가 SCIM, SSO 같은 약어를 망가뜨리고 있다"는 버그를 보고했습니다. 보통이라면 여러 창을 오가며 정신없이 작업했겠지만, 이번에는 작은 변화를 줬습니다.

Claude Code(제가 현재 주로 쓰는 인터페이스)에 Slack 읽기·쓰기 권한을 줬습니다. Linear 티켓 접근 권한은 이미 있었고요. 그리고 이렇게 지시했습니다: "이걸 고쳐라. 그리고 직접 검증하고, 완료될 때까지 멈추지 마라."

결과: Claude가 코드를 수정하고, MCP로 Slack 채널에 테스트 포스트를 날렸고, 제 작업 디렉터리에 있던 블로그봇이 그걸 받아서 전체 플로를 실행한 후 관련 단계까지 왔고, Claude가 출력을 검증한 뒤 "이 버그는 완전히 수정됐다"고 선언했습니다. 돌아왔을 때 완결된 루프가 기다리고 있었습니다. "이 부분 아직 고장났어"라고 말할 필요가 없었습니다. 그 느낌이 엄청났어요.

그런데 동시에 겁도 났습니다. 이 과정에 상한선이 없다는 게 보였거든요. 도구는 핵폭탄 수준이 됐는데 우리 신경계는 여전히 고대인입니다.

그래서 요즘 고민하는 게 "어떻게 개발자로서 균형을 찾을 것인가"입니다. 왜 그냥 같은 방식으로 하루에 버그 150개를 고치지 않느냐고요? 에이전트는 충분한 컨텍스트와 검증 기준, 도구가 있으면 그게 가능합니다. 하지만 저는 그 위에서 품질을 보장하면서 다음 날 8시간 세션에 또 멀쩡하게 나타날 수가 없습니다.

요즘 저와 주변 사람들이 공통적으로 느끼는 건 에이전트가 병목이 아니라 우리가 병목이라는 겁니다. 에이전트는 Claude API를 통해 무한히 확장할 수 있습니다. 검증 기준과 도구를 주면 됩니다. 하지만 우리의 주의력(attention)은 여전히 고기 공간(meat space)에 있고, 부하에 따라 저하됩니다.

Simon Wilson도 최근 에이전트 4개를 병렬로 돌리면 오전 11시에 녹초가 된다고 말했습니다. 개인별 균형과 한계를 각자가 찾아야 할 때가 됐습니다.

제가 최근에 효과를 본 방법들을 공유하겠습니다.

핵심 프레임: 인간 개발자를 이 새로운 작업 방식과 균형 맞추기. 에이전트는 무한 루프·무한 확장에 더 잘 맞습니다. 하지만 판단·taste, 뭔가가 실제로 해결됐는지, 기준이 진짜 인간적·비즈니스적 필요를 충족하는지는 여전히 우리 영역입니다.

첫째, Signal Layer (신호 계층) 제가 직접 Slack을 뒤지면 80% 확률로 다른 쓰레드에 빠집니다. 대신 Claude Code에 Slack 읽기 MCP를 줘서 루프로 돌게 했습니다. 멘션이 있나, DM이 있나, 진짜 급한 요청이 있나를 확인하고, 동시에 Linear에서 진짜 티켓을 찾아 중복을 제거합니다. 이 작은 필터 하나가 핵심 집중 시간을 지켜줍니다. 앞으로 이런 도구들이 더 많이 나올 겁니다.

둘째, 음성 우선 코딩 (Voice-First Coding) 저는 세 살 때부터 타이핑을 했고, 최고 기록이 90 WPM입니다. 지금은 음성 우선 도구로 184 WPM이 나옵니다. 단순히 하나를 빨리 하는 게 아니라 Cursor 창 3개, Claude 탭 여러 개에 동시에 지시할 수 있습니다. 전통적인 개발자가 첫 프롬프트를 타이핑하는 동안 여러 에이전트가 이미 달리고 있습니다. 이게 1~2년 복리로 쌓이면 어떻게 될까요?

음성 흐름에 익숙해질수록 다음 단계, 즉 실제로 책상에 덜 앉아 있으면서 일이 되는 게 가능해집니다.

셋째, Remote Control (원격 제어) 먼저 Shower Principle(샤워 원리): 집중 모드에서 IDE에 파묻혀 있으면 명확한 청사진은 있지만 창의적 해결책을 놓치고 blind spot이 생깁니다. 역설적으로 일어나서 개를 산책시키거나 아이를 공원에 데려가거나 샤워를 하면 갑자기 완전한 해법이 떠오릅니다. 무의식이 계속 어려운 문제를 돌리고 있다가 긴장이 풀리면 확산 모드(diffuse mode)로 더 창의적인 해결책이 나옵니다. 이건 수십 년간 이야기되어온 현상입니다.

문제는 지금까지 확산 모드 = 일 중단이었다는 겁니다. 이제 Remote Control로 그게 바뀝니다. Claude Code 세션을 remote control 플래그를 켜고 시작하면, 집에서 멀리 떨어진 LTE 환경에서도 스마트폰으로 그 세션을 보고 메시지를 보낼 수 있습니다. 산책 중에 좋은 아이디어가 떠오르면 바로 에이전트에 전달 → 책상으로 돌아왔을 때 이미 적용되어 있습니다. 직접 32분짜리 영상도 찍었습니다. 숲속에서 폰으로 PR을 리뷰하는 장면을요. 실제로 됩니다.

물론 이걸 위해서는 "속도는 안전을 전제로 한다"는 원칙이 필요합니다. 검증 게이트: - Gate 1: 최소 lint, build, unit test — 에이전트가 hooks로 매번 자동 실행 - Gate 2: 브라우저로 직접 확인 — --chrome 플래그, 로그인 같은 핵심 플로 클릭 - Gate 3: Constitutional AI 방식 — "준수해야 할 원칙" 목록을 별도 에이전트가 검토하고 피드백

새로운 하루 워크플로: 오전: GitHub 백로그 전체 확인 → Codex에 태스크 큐잉 → 핵심 기능 IDE/Claude Code에서 시작 → 에이전트가 방향대로 가는지 확인 → 책상 이탈. 폰으로 메시지 전달, PR 리뷰. GitHub Mobile에서 Claude나 Cursor Agent, Vercelbot에 자연어 코멘트로 "이 부분 바꿔" 하면 대부분 맞게 처리. 책상에 덜 앉고, RSI도 줄고, 산책하면서 더 좋은 아이디어를 얻고, 루프는 계속 돌아갑니다.

넷째, 시스템 자기개선 도구만 쓰면 월요일은 놀랍고 금요일은 진이 빠지고 뭘 했는지도 기억 안 납니다. 동료 Nick이 알려줬는데, Claude Code의 모든 대화는 로컬 JSONL 파일로 저장됩니다. 이걸 에이전트가 주간 단위로 분석하게 할 수 있습니다. "우리가 많은 생각 토큰(thinking token)을 쓴 구간, 모호성을 제거하느라 오래 주고받은 구간을 찾아라. 거기서 어떤 도구나 MCP 서버, skill이 있었으면 루프가 짧아졌을지 파악해라." 이게 바로 skill 간격(skill delta) 분석입니다.

hooks로 세션 종료 시 또는 PR 머지 시 자동으로 고난이도 구간을 Obsidian이나 Markdown 파일에 저장할 수 있습니다. 주간 분석 루프를 한 번 돌리면 Claude Code에 내장된 skill 빌드·평가·개선 기능으로 다음 주엔 더 빠르고 정확하게 됩니다.

Oura Ring MCP 연동 오라 링을 MCP로 Claude에 연결했습니다(GitHub에 서드파티 프로젝트 몇 개 있음). Claude가 간혹 "어젯밤에 잠을 못 잤네요. 첫 번째 부분만 하고 나머지는 내일 합시다"라고 합니다. "닥쳐, 넌 기계잖아"라고 하고 그냥 진행하긴 하지만, 적어도 한 번 생각하게 됩니다. 이게 실제로 의미가 있는 방향이라고 생각합니다. 티켓·대화·skill만이 아니라 신체 컨디션까지 전체적으로 보는 것. 의도 없이 그냥 달리면 번아웃, 이번엔 터보 번아웃입니다. LLM이 그걸 그 어느 때보다 빠르게 가능하게 합니다. 의도적인 길은 나를 보존하면서 품질 책임은 유지하고 에이전트에게 세부 사항을 맡기는 것입니다.

마무리 제안: Signal Layer 하나만 만들어보세요. Slack이든 Linear든 컨텍스트 전환 비용이 제일 큰 것 하나를 선택한 인터페이스에 연결하는 것으로 시작. 검증 게이트 추가. Chrome 브라우저 접근은 --chrome 플래그 하나면 됩니다. 그렇게 확보한 여유로 공원 피크닉을 가거나 산책을 하거나 개와 놀아주세요.

도구는 핵폭탄입니다. 신경계는 여전히 고대인입니다. 개발자 균형을 찾는 게 요즘 저의 화두입니다. 감사합니다.

Q&A

Q: 커리어 초반인데 이런 방식으로 hard skill이 줄어들까 걱정됩니다.

A: 제가 본 최고의 조언은 "아직 모르는 것에 AI를 쓰지 마라"입니다. 저는 TypeScript, RAG 시스템, AWS 배포를 오랫동안 힘들게 했기 때문에 Claude가 이상한 말을 하면 바로 알아챕니다. 그 scar tissue(상처 흔적)가 중요합니다. 먼저 깊게 파고, LLM으로 더 빠르고 깊게 배우세요 — "이 부분 내 멘탈 모델이 불명확해"라고 솔직하게 말하면 더 빨리 채울 수 있습니다. Ruby 앱을 충분히 직접 만들어봤으면 그때 LLM으로 더 빠르게 만들어도 됩니다.

Q: JSONL 파일이 AI 소비용이 아닌데 어떻게 처리하나요?

A: 직접 가리키기도 했습니다. 더 좋은 방법은 hooks를 써서 세션 종료 시 "핵심 교훈, 특히 오래 씨름한 구간을 별도 데이터 저장소(Obsidian, 주간 Markdown 파일 등)에 저장"하는 것. 그 파일에 주간 분석을 돌리는 방식.

Q: 야간 백그라운드 에이전트 활용하나요?

A: 네, Cron 잡으로 콘텐츠 생성 실험 중입니다. 아침에 검토하고 일부만 머지합니다. 목표는 Linear에 "agent-ready" 태그를 붙이고 15분마다 도는 루프를 만드는 것.

Q: 에이전트가 음성으로 피드백을 주나요?

A: Claude Code에는 주로 타이핑으로 지시하고 결과를 읽습니다. 하지만 OpenAI 고급 음성 모드(Advanced Voice Mode)로 2시간 산책 중 브레인덤프를 많이 합니다. ChatGPT를 쓰는 유일한 이유입니다. 오픈소스 Whisperflow 계열 로컬 도구도 최근 발견했습니다. OpenClaw를 Twilio에 연결해서 밤에 전화로 "내일 이걸 해달라"고 지시하는 실험도 합니다.

Q: 복잡한 멀티스택 기능 작업은 어떻게 하나요?

A: git worktree로 에이전트별 독립 작업 디렉터리를 분리 → 병렬 충돌 방지. 명확한 프롬프트의 에이전트 팀 구성. 검증 게이트와 unit test 강화. CI를 항상 spec 기반으로 빌드하게. 모델이 발전할수록 이런 큰 기능도 하네스가 더 안정적으로 처리할 것입니다.
