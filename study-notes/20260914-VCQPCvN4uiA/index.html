GitHub 1위 트렌딩 도구가 해결한 AI 에이전트의 치명적인 문제입니다

업로드 2026-09-14 · 11.4분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 영상의 중심 문제는 코딩 에이전트가 코드를 고치는 시간보다 고칠 파일을 찾는 데 더 많은 대화와 도구 호출을 쓸 수 있다는 것이다. Claude Code나 Codex 같은 에이전트에 “이 버튼을 초록색으로 바꿔 줘”라고 시켜도, 에이전트는 처음부터 버튼이 어느 파일과 줄에 있는지 알지 못한다. 먼저 터미널에서 관련 단어를 검색하고, 결과를 읽고, 후보 파일을 열고, 필요한 줄을 확인한 뒤에야 수정한다.

화자의 설명에 따르면 이 과정에서 모델은 다음 행동을 결정할 때마다 앞선 대화와 도구 결과를 다시 전달받는다. 검색이 여러 번 이어지면 읽어야 할 문맥이 커지고, 도구 호출 횟수와 대기 시간도 늘어난다. 영상은 이 반복 탐색이 사용 한도 소진뿐 아니라, 관련 없는 정보가 문맥에 쌓여 모델이 현재 작업에 집중하기 어려워지는 원인이라고 주장한다.

읽는 법: 왼쪽은 에이전트가 검색 결과를 보고 다음 검색을 결정하는 반복 경로다. 오른쪽은 프로젝트의 구조를 미리 정리한 지도를 이용해 관련 코드에 더 빨리 접근하는 경로다. Graft를 써도 모델이 실제 코드를 읽고 수정하는 단계는 사라지지 않는다. 줄이려는 것은 그전에 발생하는 시행착오다.

기존 해결책 중 하나는 코드 조각을 숫자 묶음으로 바꾼 뒤 질문과 의미가 비슷한 조각을 찾는 벡터 검색이다. 이 방법은 문장이 얼마나 비슷한지를 찾는 데에는 도움이 되지만, 코드끼리 실제로 어떻게 연결되는지까지 자동으로 보여 주지는 않는다. 영상은 계정 생성 코드와 계정 삭제 코드가 모두 “계정”이라는 질문에 비슷하게 잡힐 수 있지만, 역할은 반대라는 사례를 든다.

Graft는 이 문제를 코드 지식 그래프로 풀려고 한다. 쉬운 말로 하면 프로젝트의 부품 목록과 연결 관계를 그린 지도다. 지도에 기록된 각 코드 요소를 노드, 두 요소의 사용·참조 관계를 엣지라고 부른다. 에이전트는 특정 요소가 어디에 있고 무엇과 연결되는지 확인한 뒤, 변경의 영향을 받을 수 있는 코드까지 따라갈 수 있다.

읽는 법: 세 방식은 완전히 같은 일을 하는 대체품이라기보다 서로 다른 단서를 사용한다. 단어 검색은 글자, 벡터 검색은 의미의 유사성, Graft가 소개하는 그래프는 코드의 구조적 연결을 중심으로 본다. 영상은 그래프가 벡터 검색보다 항상 우월하다는 독립 검증을 제공한 것이 아니라, 코드 관계를 알아야 하는 작업에서 그래프가 메울 수 있는 빈틈을 설명한다.

Graft는 지도를 컴퓨터에 JSON 파일로 저장하며 브라우저에서 노드와 엣지를 볼 수 있는 뷰어도 제공한다고 소개된다. 이미 코드가 있는 프로젝트에서는 초기화 후 그래프를 만들어야 한다. 빈 폴더라면 처음에는 노드가 0개이고, 파일이 생성된 뒤 지도가 만들어진다. 코드가 바뀌면 전체를 처음부터 다시 만드는 대신 바뀐 부분만 갱신하는 증분 업데이트를 사용한다고 화자는 설명한다.

에이전트가 지도를 조회하는 방식은 두 가지로 나뉜다.

  • CLI 방식: 세션 시작 때 지도 사용법을 알려 주고, 사용자의 메시지와 지도를 대조해 최대 3개의 관련 위치를 매번 첨부한다. 빠르게 후보를 주지만 필요하지 않은 메시지에도 위치가 붙을 수 있다.
  • MCP 방식: 위치를 자동 첨부하지 않고, 에이전트가 필요하다고 판단할 때 Graft에 요청한다. 영상은 Graft 자체 테스트에서 MCP가 몇 개의 답을 더 맞혔고 CLI는 더 빨랐다고 말하지만, 정확한 표본과 차이는 제시하지 않는다.

읽는 법: 화살표는 처리 순서를 뜻하며 성능 수치를 나타내지 않는다. 핵심은 지도도 한 번 만들고 끝나는 정적 문서가 아니라 코드 변경을 따라가야 한다는 점이다. 다만 “항상 최신”이라는 표현은 영상의 주장이고, 누락·파싱 오류·훅 실패에 관한 독립 시험 결과는 제공되지 않았다.

영상은 Graft 팀의 자체 벤치마크 162회에서 평균 작업 시간이 60%, 도구 사용이 46%, 토큰 사용이 42%, 비용이 32% 줄었다고 전한다. 별도로 토큰 사용에서 “최상의 경우 4배 저렴하다”고 표현한다. 그러나 4배라는 표현의 정확한 계산 기준, 162회 시험의 과제 구성, 비교 환경, 성공 판정 방식은 출처에 없다. 따라서 수치는 도구 제작 측의 자체 주장으로 읽어야 하며, 평균 토큰 42% 감소와 최상의 경우 4배라는 표현을 같은 수치로 합치면 안 된다.

영상 제작진이 소개한 예약 앱 사례에서는 Graft 사용 시 39분과 문맥 창 약 31%, 미사용 시 47분과 약 35%가 기록됐다고 한다. 화자도 첫 빌드 당시에는 그래프가 아직 만들어지지 않아 차이가 작았다고 설명한다. 이후 랜딩페이지 전면 수정은 Graft를 사용해 2분 미만이 걸렸다고 하지만, 같은 수정의 미사용 시간은 “훨씬 더 오래”라고만 말해 정확한 비교값이 없다.

또한 Graft가 지도화하는 대상은 코드다. PRD, learnings.md, 분야별 지침 파일 같은 비코드 자료는 기본 지도에 포함되지 않아 기존 방식으로 읽어야 한다고 영상은 밝힌다. 따라서 프로젝트가 크더라도 에이전트 작업의 대부분이 문서 검색이라면 영상에서 말한 이득이 그대로 나오리라고 단정할 수 없다. 반대로 코드가 크고 변경 전 의존 관계 탐색이 많은 작업일수록 절약할 탐색이 많다는 것이 화자의 조건부 주장이다.

마지막으로 제목은 “GitHub 1위 트렌딩”이라고 단정하지만, 제공된 전사는 “최근 GitHub에서 트렌딩 중”이라고만 말한다. 1위였던 시점과 순위 근거는 제공 자료에서 확인되지 않는다. META는 Trailhq를 소속 후보로 보존하지만, provenance 메모는 원본 출처가 추정이라고 밝히고 creator와 social_links는 비어 있다. 따라서 원작자와 소속을 확정 정보로 해석해서는 안 된다.

여기까지만 이해하면 충분

  • 코딩 에이전트는 수정할 위치를 찾기 위해 검색과 도구 호출을 반복하고, 그 결과가 문맥·시간·토큰 부담으로 이어질 수 있다.
  • Graft는 코드 요소와 실제 연결 관계를 지도로 만들어 에이전트가 관련 위치와 변경 영향 후보에 더 빨리 접근하게 한다.
  • CLI는 위치를 자동 첨부하고 MCP는 에이전트가 필요할 때 조회하므로 속도와 선택성 사이의 차이가 있다.
  • 성능 수치는 자체 벤치마크이며, 프로젝트 크기·코드 비중·과제 구성에 따라 실제 이득을 따로 측정해야 한다.

비유와 깨지는 지점

단어 목록과 도시 도로망

벡터 검색은 목적지 이름과 비슷한 장소를 찾는 목록에 가깝고, 코드 지식 그래프는 장소들이 어떤 도로로 연결됐는지 표시한 지도에 가깝다. 이름이 비슷한 두 장소가 있어도 도로 연결을 보면 어느 경로에 속하는지 구분할 단서를 얻을 수 있다.

비유가 깨지는 지점: 실제 코드 관계는 도시 도로처럼 완전히 고정되어 있지 않다. 동적 호출, 도구가 읽지 못한 구조, 갱신 실패가 있으면 지도에 관계가 빠질 수 있다. 제공 자료는 이런 누락률을 측정하지 않았다.

코딩 에이전트가 실제 수정 전부터 토큰과 시간을 많이 사용할 수 있는 이유는 무엇인가?

모범 답안 보기

에이전트는 수정할 파일과 줄을 처음부터 알지 못하므로 검색, 결과 확인, 파일 읽기를 여러 차례 반복할 수 있다. 화자의 설명에 따르면 각 차례에 기존 대화와 도구 결과가 다시 모델에 전달되어 문맥이 커지고, 다음 행동을 정하는 도구 호출과 대기 시간도 늘어난다.

2. 대조

벡터 검색과 Graft의 코드 지식 그래프는 관련 코드를 찾는 기준이 어떻게 다른가?

모범 답안 보기

벡터 검색은 질문과 코드의 의미가 얼마나 비슷한지를 중심으로 찾는다. Graft가 소개하는 그래프는 어떤 코드 요소가 다른 요소를 실제로 사용하거나 참조하는지를 기록한다. 전자는 유사한 후보를 찾는 데 강점이 있고, 후자는 변경 영향과 연결 관계를 따라가는 데 필요한 단서를 제공한다는 것이 영상의 설명이다.

3. 적용

새 코드 탐색 도구를 실제 저장소에 도입할지 판단한다면 무엇을 먼저 비교해야 하는가?

모범 답안 보기

같은 성공 기준을 가진 변경 과제를 도구 사용·미사용 조건에서 수행하고, 완료까지 소비한 토큰처럼 한 가지 지표를 비교한다. 저장소가 충분히 크고 코드 탐색이 실제 병목인지, 비코드 문서 작업이 대부분인지, 초기 지도 생성과 갱신 비용이 절감보다 큰지도 함께 확인해야 한다. 영상의 자체 수치를 그대로 예상치로 쓰면 안 된다.

  • [원문] 화자는 에이전트가 검색 명령과 파일 읽기를 반복할 때 대화와 도구 결과가 계속 문맥에 포함되어 토큰과 시간이 늘어난다고 설명한다.
  • [해석] 고성능 모델을 선택하는 것만큼, 모델이 필요한 근거에 몇 단계 만에 도달하는지를 설계하는 일이 중요하다.
  • [경계] 제공 자료에는 문맥 증가가 실제 출력 품질을 얼마나 낮췄는지 보여 주는 독립 측정이 없다. 영상에 등장하는 GPT-5.6, GPT Astra, Fable 5.1, Opus라는 명칭도 제공 자료 밖에서 확인되지 않았다.

2. 유사성 검색과 관계 탐색은 해결하려는 질문이 다르다

  • [원문] 영상은 계정 생성과 삭제 코드가 모두 계정 질문과 유사할 수 있지만 역할은 반대라고 설명하고, Graft는 노드와 엣지로 실제 사용 관계를 기록한다고 말한다.
  • [해석] “무엇과 비슷한가”를 묻는 검색과 “무엇이 이것을 사용하며 변경 시 어디가 영향을 받는가”를 묻는 탐색은 구분해야 한다.
  • [경계] 영상은 벡터 검색을 단독 방식으로 단순화해 비교한다. 두 방식을 결합한 구성이나 그래프 추출의 누락·오류는 시험하지 않는다.

3. 큰 절감 수치보다 작업 조건과 비교 기준을 먼저 봐야 한다

  • [원문] 자체 벤치마크 162회에서 시간 60%, 도구 사용 46%, 토큰 42%, 비용 32% 감소가 주장됐고, 최상의 경우 토큰 사용이 “4배 저렴하다”고 표현됐다. 예약 앱 사례는 39분·문맥 31%와 47분·35%를 비교했다.
  • [해석] 도구의 가치는 저장소 규모, 반복 탐색량, 코드와 문서 작업의 비율, 초기 그래프 유무에 따라 달라진다.
  • [경계] “4배 저렴”의 계산 기준과 162회 벤치마크 방법이 제공되지 않았으며 평균 토큰 42% 감소와 같은 수치로 취급할 수 없다. 랜딩페이지 수정은 2분 미만이라는 Graft 결과만 있고 정확한 미사용 기준값이 없다. 제목의 “GitHub 1위”도 전사의 “최근 트렌딩”보다 강한 주장으로, 순위 근거가 없다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 에이전트가 정답 전에 여러 검색을 거치는 모습은 학습자가 필요한 개념의 위치를 몰라 자료를 헤매는 구조와 닮았다.
  • 통찰: 이해 여부는 자료를 많이 읽었는지가 아니라, 필요한 근거와 관계를 찾아 자기 말로 설명할 수 있는지로 관찰할 수 있다.
  • 질문/행동: 학습자가 답을 못할 때 지식이 없는지, 개념 사이의 연결 지도가 없는지 구분해 질문한다.

사업가 · 구조적 비유

  • 관련성: 영상의 직접 대상은 코딩 에이전트이며 APOM 운영 상태에 관한 근거는 없다. 다만 탐색 시간과 사용량이 운영비로 새는 구조는 비교해 볼 수 있다.
  • 통찰: APOM·이커머스·물류에 적용한다면 현재 사실이 아니라, 반복 탐색이 많은 업무에서 관계 지도가 시간과 오류를 줄일 수 있다는 가설로만 다뤄야 한다.
  • 질문/행동: 가상 후보 업무 하나에서 실제 병목이 정보 부족인지, 정보 사이 관계를 찾는 시간인지 먼저 확인한다.

마케터 · 직접 전이

  • 관련성: 제목의 “GitHub 1위”, 자체 벤치마크의 절감률, 제작진의 앱 사례는 주장과 증거의 강도가 서로 다른 장면이다.
  • 통찰: 강한 숫자를 카피에 사용할 때 평균·최상 사례·단일 사례를 분리하고, 자체 측정임을 함께 밝혀야 과장을 줄일 수 있다.
  • 질문/행동: 상세페이지의 각 수치 옆에 측정 주체, 조건, 표본, 평균인지 최상 사례인지를 표시할 수 있는지 점검한다.

AI/SW 학습자 · 직접 전이

  • 관련성: 코드 검색, 도구 호출, 문맥 사용량, CLI와 MCP의 조회 시작점은 에이전트 아키텍처에서 직접 측정할 수 있는 요소다.
  • 통찰: 기술 이름보다 작업 특성을 기준으로 선택해야 한다. 코드 의존 관계 탐색이 많으면 그래프가 유리할 수 있지만, 비코드 문서 작업이 많으면 범위 밖 비용이 남는다.
  • 질문/행동: 같은 저장소와 성공 기준에서 도구 사용 전후의 완료 토큰을 비교하고, 그래프가 제시한 위치가 실제 수정 위치와 맞았는지 별도로 기록한다.

1. 반복 검색이 비용으로 이어지는 흐름

화자는 Claude Code와 Codex 같은 에이전트가 변경 요청을 받으면 먼저 관련 파일을 찾아야 한다고 설명한다. 첫 검색에서 정확한 위치를 찾지 못하면 검색어를 바꾸거나 후보 파일의 특정 줄을 읽는 도구를 추가로 사용한다.

영상의 인과는 다음과 같다.

  1. 사용자가 변경을 요청한다.
  2. 에이전트가 관련 단어로 파일을 검색한다.
  3. 검색 결과와 앞선 대화가 모델에 전달된다.
  4. 모델이 다음 도구를 고른다.
  5. 필요한 파일과 줄을 찾을 때까지 반복한다.
  6. 반복된 결과가 문맥에 쌓여 사용량과 대기 시간이 늘어난다.

초록색 버튼 사례에서는 버튼이 들어 있는 파일을 찾고, 해당 파일의 구체적인 줄을 읽은 뒤 수정한다. 화자는 이런 왕복이 많은 작업을 한 세션에서 수행할 때 사용 한도에 빨리 도달하고, 문맥에 정보가 많아져 출력 품질도 나빠질 수 있다고 주장한다.

2. 벡터 검색과 관계 정보

영상은 기존 도구가 코드 조각과 질문을 벡터로 바꿔 의미가 가까운 항목을 찾는 방식을 소개한다. 하지만 계정 생성과 계정 삭제처럼 같은 주제어를 공유하면서 반대 역할을 하는 코드가 함께 선택될 수 있다고 설명한다.

이 영상이 Graft와 벡터 검색을 구분하는 기준은 다음과 같다.

  • 벡터 검색: 질문과 코드 조각의 의미적 유사성
  • Graft 그래프: 코드 요소가 다른 요소를 실제로 사용하거나 참조하는 관계
  • 기대 효과: 수정 대상뿐 아니라 그 변경에 영향을 받을 수 있는 연결 요소 확인

두 방식을 결합한 결과나 벡터 검색 구현별 차이는 다루지 않는다.

3. Graft의 지도와 저장 방식

Graft는 컴퓨터에 설치하는 터미널 명령 도구로 소개된다. 프로젝트 코드를 읽고 각 요소의 이름과 위치를 기록한 뒤, 요소 사이의 관계를 연결한다.

  • 각 코드 요소: 노드
  • 요소 사이의 연결: 엣지
  • 저장 형식: 로컬 JSON 파일
  • 확인 방법: 브라우저에서 여는 그래프 뷰어
  • 선택 기능: 별도 모델을 사용해 코드 구조를 평문 문서로 설명하는 페이지 생성

영상은 기본 지도 기능에는 별도 API 키가 필요하지 않고 기존 구독 환경에서 작동한다고 말한다. 무료·오픈소스라는 주장도 나오지만, 제공 자료에는 저장소 주소나 라이선스 문서가 없다.

4. CLI와 MCP 조회

CLI 구성에서는 세션이 시작될 때 모델에 지도 사용법이 제공된다. 사용자가 프롬프트를 보낼 때 메시지의 단어와 지도를 대조해 최대 3개의 관련 위치를 첨부한다. 실제 코드 내용은 모델이 해당 줄을 읽을 때 문맥에 들어온다고 설명한다.

MCP 구성에서는 위치가 모든 메시지에 자동 첨부되지 않는다. 에이전트가 정보가 필요하다고 판단할 때 Graft에 요청한다.

화자가 전달한 자체 비교는 다음과 같다.

  • MCP: CLI보다 몇 개의 답을 더 맞힘
  • CLI: MCP보다 빠름
  • 정확한 차이·표본·과제별 결과: 제공되지 않음
  • 설치 시 두 방식 모두 제공된다고 설명

5. 설치, 훅, 갱신

사이트에서 설치 명령이나 에이전트별 설정 프롬프트를 복사할 수 있다고 소개한다. 설치 후 프로젝트 폴더 안에서 초기화 명령을 실행해야 하며, 사용 중인 코딩 에이전트를 선택한다.

Claude Code 예시에서는 다음 구성이 설치된다고 설명한다.

  1. 세션 시작 시 지도 사용법을 전달하는 훅
  2. 프롬프트마다 관련 위치를 첨부하는 훅
  3. Claude가 파일을 편집한 뒤 지도를 갱신하는 훅

기존 프로젝트는 별도의 그래프 빌드 명령으로 현재 코드를 지도화한다. 빈 폴더는 처음에 노드가 0개이며 파일이 만들어진 뒤 그래프를 생성한다. 질문에 답하기 전 코드 변경 여부를 확인하고, 변경됐다면 모델을 사용하지 않고 지도부터 갱신한다고 화자는 말한다.

7. 충돌 및 검증 경계

  • 제목과 전사: 제목은 “GitHub 1위 트렌딩”이라고 쓰지만 전사는 “최근 GitHub에서 트렌딩 중”이라고만 말한다. 1위 순위와 시점의 근거가 없다.
  • 최상 사례와 평균: “토큰 기준 4배 저렴”은 최상 사례이고 42% 감소는 162회 평균이다. 같은 수치가 아니며, 4배의 분모와 계산식도 없다.
  • 예약 앱 비교: 39분·31%와 47분·35%는 수치가 제시됐지만 첫 빌드에는 그래프가 아직 구축되지 않았다고 설명한다. 이후 2분 미만 수정에는 정확한 미사용 비교값이 없다.
  • 출처 귀속: META는 Trailhq를 affiliation 후보로 제공하지만 provenance.note는 원본 출처를 추정이라고 표시한다. creator와 social_links가 비어 있어 추정 근거를 자료 안에서 대조할 수 없다.
  • 모델 명칭: 전사의 GPT-5.6, GPT Astra, Fable 5.1, Opus는 제공 자료 안에서 외부 원문이나 제품 링크로 확인되지 않았다.
  • 오픈소스·자동 최신 상태: 무료·오픈소스, 별도 API 키 불필요, 자동 갱신이라는 설명은 화자의 주장이다. 저장소·라이선스·실패율 자료는 제공되지 않았다.
  • 전사 완결성: 전사는 제작진이 비코드 파일을 처리하도록 도구를 수정해 AI Labs Pro에 추가했다는 문장 도중 끝난다. 수정판의 범위와 조건은 확인할 수 없다.
  • 일치하는 수치: META의 162회, 시간 60%, 토큰 42%, 비용 32%는 전사와 일치한다. META에는 전사의 도구 사용 46% 감소가 생략돼 있지만 수치 충돌은 아니다.
  • 영상 길이: META의 687초는 약 11.45분이며 duration_min 11.4는 소수 첫째 자리 표기와 양립한다.
  • 조회 수: META에는 조회 수 13,856회가 있으나 수집 시점이 없어 현재 수치로 해석할 수 없다.

전체 전사 펼치기

Opus와 GPT-5.6 같은 좋은 모델을 사용하면 보통 좋은 결과를 얻습니다. 하지만 이런 모델은 토큰도 많이 소모합니다. GPT Astra와 Fable 5.1 같은 고성능 모델을 사용하면 상황은 더 나빠집니다. 다른 모델을 사용할 때보다 훨씬 빠르게 사용량 제한에 도달하기 때문입니다. 게다가 속도도 매우 느려서 작업 하나가 끝날 때까지 오랫동안 기다리게 됩니다.

이 문제를 정확히 해결하기 위해 최근 GitHub에서 트렌딩 중인 Graft라는 도구가 있습니다. Graft는 에이전트가 기본적으로 프로젝트를 다루는 방식을 바꿉니다. 토큰을 절약할 뿐만 아니라, 에이전트가 혼자 작업할 때보다 훨씬 빠르게 만들어 줍니다. 그리고 이 문제가 처음 발생하는 근본적인 이유를 해결하는 매우 흥미로운 방식으로 작동합니다.

물론 이미 이 문제를 해결하기 위해 만들어진 도구들이 없는 것은 아닙니다. 하지만 그 도구들에는 모두 큰 공백이 있고, 바로 그 부분을 이 도구가 해결합니다. 이 채널이 처음이라면, 저희는 소프트웨어 회사이고 이곳은 저희 채널인 Tech Bridge입니다. 이번 영상에서는 Graft가 이러한 모델을 더 저렴하게 사용하는 방법을 정확히 보여드리겠습니다.

하지만 Graft를 살펴보기 전에, 에이전트가 앱에서 무언가를 변경하기도 전에 왜 그렇게 많은 토큰을 사용하는지 이해해야 합니다. Claude Code와 Codex 같은 에이전트가 파일을 찾을 때 사용하는 기본 방식에는 문제가 있습니다.

작업 중인 앱에 무언가를 추가해 달라고 에이전트에 요청하면, 에이전트는 먼저 그 변경 사항을 작성해야 하는 앱의 부분을 찾아야 합니다. 해당 부분을 찾기 위해 추가하려는 기능과 관련된 단어를 검색하는 여러 터미널 명령을 사용합니다.

모델은 보통 첫 번째 시도에서 찾는 대상을 발견하지 못합니다. 정확히 무엇을 검색하고 있는지 범위를 좁히기 위해 여러 도구를 사용해야 합니다. 그리고 모델이 다음에 어떤 도구를 사용할지 결정할 때마다, 에이전트는 지금까지의 전체 대화를 모델에 다시 보냅니다. 여기에는 이미 사용한 도구들의 응답도 포함됩니다. 그러면 모델은 다음 단계를 결정하기 위해 그 모든 내용을 읽습니다.

이렇게 여러 턴(turn)을 거친 뒤에야 올바른 파일에 도달하고, 각각의 턴이 사용량을 발생시킵니다. 예를 들어 에이전트에 버튼을 초록색으로 바꿔 달라고 요청하면, 먼저 그 버튼의 코드가 들어 있는 파일이 무엇인지 찾아야 합니다. 그래서 해당 버튼이 포함된 파일을 검색하고, 그 결과가 여러분의 메시지와 함께 모델로 전달됩니다. 그런 다음 에이전트는 다른 도구를 사용해 그 파일에서 특정 코드 줄을 읽고, 그제야 실제로 변경을 수행합니다.

여러분이 요청하는 모든 변경은 이런 식의 주고받기를 통해 이루어집니다. 모든 메시지와 도구 결과가 반복해서 전송되기 때문에 컨텍스트 창(context window)은 계속 커집니다. 컨텍스트가 계속 소모될 뿐만 아니라, 모델이 필요한 파일의 범위를 좁히기 위해 여러 턴을 사용하므로 속도도 느려집니다. 새로운 검색을 할 때마다 정보가 더 추가되고, 모델은 그 정보로 무엇을 할지 결정하는 데 토큰을 사용해야 합니다.

이것이 한 세션에서 에이전트로 많은 작업을 수행할 때 사용량 제한에 도달하는 이유 중 하나입니다. 사용량 제한에 도달하는 것은 결과 중 하나일 뿐입니다. 컨텍스트 창에 너무 많은 내용이 들어가서 에이전트가 한 번에 한 가지에 집중하지 못하기 때문에 결과물의 품질도 떨어집니다.

이 문제가 이미 알려져 있기 때문에, 이를 해결하려는 도구들도 존재합니다. 이런 도구들이 사용하는 일반적인 접근 방식은 코드의 일부를 벡터(vector)라는 숫자로 변환해 모델이 쉽게 비교할 수 있게 하는 것입니다. 질문을 하면 검색 도구도 그 질문을 벡터로 변환한 다음, 가장 비슷하게 일치하는 부분을 찾습니다.

이를 벡터 검색(vector search)이라고 하며, 기본적으로 질문한 내용과 의미가 얼마나 비슷한지를 기준으로 정보를 찾는 방식입니다. 하지만 유사성만으로는 앱의 각 부분이 어떻게 연결되어 있는지 알 수 없습니다. 예를 들어 계정을 생성하는 코드와 계정을 삭제하는 코드는 모두 계정에 관한 질문과 일치할 수 있습니다. 하지만 두 코드는 정반대의 작업을 수행하므로, 잘못된 코드를 선택하면 큰 문제가 발생합니다.

그래서 이런 검색은 그다지 효과적이지 않고, 대부분의 코딩 에이전트는 아예 사용하지 않습니다. Graft는 실제로 컴퓨터에 설치하는 터미널 명령어이며, 코딩 에이전트가 매번 변경 전에 프로젝트를 검색하며 돌아다니지 않아도 되도록 기본 방식을 바꾸기 위해 만들어졌습니다.

Graft는 지식 그래프(knowledge graph)를 구축해 이 작업을 수행합니다. 지식 그래프는 프로젝트의 모든 부분을 보여 주고 서로 어떻게 연결되는지 나타내는 지도와 같습니다. 에이전트는 이 지도를 사용해 필요한 코드를 찾고, 해당 코드에 의존하는 다른 부분이 무엇인지 확인합니다.

Graft는 무료 오픈 소스이며, 핵심적인 특징은 별도의 API 키가 필요한 모델을 사용하지 않는다는 점입니다. 따라서 평소 사용하는 구독으로 작동합니다. 앱에 관한 평범한 설명 페이지를 작성하기 위해 모델을 사용하는 선택적 단계도 있습니다. 이 페이지는 코드의 각 부분이 무엇을 하고 각 부분이 어떻게 맞물리는지 설명합니다.

이 단계는 꼭 필요하지 않습니다. 지도만으로도 에이전트에 무엇이 무엇과 연결되어 있는지 알려 줄 수 있기 때문입니다. 이 단계는 코드가 무엇을 하는지에 대한 설명을 추가할 뿐입니다. 따라서 이런 페이지가 있으면 에이전트는 모든 파일을 열어 보지 않고도 각 부분이 무엇을 하는지 파악할 수 있습니다.

Graft를 만든 팀이 이 도구를 실행했을 때, 최상의 경우 에이전트의 토큰 사용량이 4배 저렴해진다는 결과를 얻었습니다. 자체 벤치마크에서 162번 실행한 결과, 작업에 걸리는 시간은 평균 60% 줄었습니다. 에이전트의 도구 사용 횟수는 46%, 토큰 사용량은 42% 감소했고, 비용은 평균 32% 낮아졌습니다.

그리고 이러한 절약은 에이전트가 더 이상 수행하지 않아도 되는 모든 검색에서 발생하므로, 규모가 큰 프로젝트에서 더 큰 효과를 냅니다. 작은 프로젝트에서는 애초에 절약할 검색이 많지 않기 때문입니다.

Graft는 Claude Code와 Codex는 물론, 터미널 명령이나 MCP를 사용하는 다른 코딩 에이전트와도 작동합니다. 하지만 Graft가 구축하는 지도는 앞에서 설명한 벡터 검색과 다릅니다. Graft는 코드를 숫자로 바꾸고 유사성으로 일치시키지 않습니다. 대신 코드를 읽고 실제로 어떤 부분이 어떤 부분을 사용하는지 기록합니다. 따라서 한 부분을 변경하면 그 변경으로 인해 어떤 다른 부분이 영향을 받을 수 있는지 에이전트가 정확히 확인할 수 있습니다.

코드가 변경되면 전체를 다시 구축하지 않고 변경된 부분만 업데이트합니다. 따라서 지도는 자동으로 최신 상태를 유지하고, 에이전트가 오래된 프로젝트 버전을 기준으로 작업하는 일도 없습니다.

무언가를 설치하기 전에 Graft가 실제로 어떻게 지도를 만드는지 살펴봐야 합니다. 지도를 구축할 때 Graft는 컴퓨터의 코드를 읽고, 발견한 모든 부분의 이름과 프로젝트 내 위치를 기록합니다. 그런 다음 어떤 부분이 어떤 부분과 연결되어 있는지도 기록합니다.

지도에 있는 각각의 부분을 노드(node)라고 하고, 두 부분 사이의 각 연결을 엣지(edge)라고 합니다. 따라서 에이전트가 앱의 특정 부분을 사용하는 것이 무엇인지 물으면, Graft는 해당 엣지를 따라가며 검색 대상과 연결된 코드를 제공합니다. 그러면 그 변경이 다른 부분에도 영향을 미치는지 확인할 수 있습니다. 바로 이 작업을 벡터 검색은 수행하지 못했습니다.

Graft는 이 지도를 컴퓨터에 JSON 파일로 저장합니다. JSON으로 저장하는 이유는 이 형식을 사용하면 세부 정보가 포함된 내용을 적절한 구조로 기록할 수 있기 때문입니다. 브라우저에서 열어 지도를 보고 연결을 탐색할 수 있는 뷰어(viewer)도 제공합니다.

Graft가 Claude Code에 연결되면, 매 세션 시작 시 지도 사용 방법에 대한 지침을 모델에 제공합니다. 이후 프롬프트를 보낼 때마다 Graft는 메시지의 단어를 지도와 대조하고, 일치하는 위치를 최대 3개까지 메시지에 첨부합니다. 따라서 모델은 도구를 한 번 사용하기도 전에 어떤 파일과 줄을 읽어야 하는지 이미 알 수 있습니다.

코드 자체는 에이전트가 해당 줄을 읽을 때에만 컨텍스트에 들어옵니다. 따라서 모델은 더 적은 턴으로 올바른 파일에 도달하고, 컨텍스트 창에 추가되는 내용도 훨씬 줄어듭니다. 그러므로 더 빠르고 사용량 제한도 덜 소모합니다.

MCP 옵션도 있으며, 차이점은 조회를 누가 시작하느냐입니다. 방금 설명한 설정에서는 Graft가 프롬프트를 바탕으로 추측하고, 에이전트에 실제로 필요한지와 관계없이 모든 메시지에 해당 위치를 첨부합니다. MCP를 사용하면 프롬프트에 아무것도 첨부되지 않고, 에이전트가 실제로 무언가 필요할 때만 Graft에 요청합니다.

Graft 자체 테스트에서는 MCP 버전이 CLI 버전보다 정답을 몇 개 더 맞혔고, CLI 버전은 더 빨랐습니다. 설치하면 두 버전을 모두 사용할 수 있습니다. 또한 앱을 변경하면 Graft가 지도를 자동으로 계속 업데이트합니다.

질문에 답하기 전에 코드가 지도를 구축한 이후 변경되었는지 확인하고, 변경되었다면 모델을 사용하지 않고 먼저 지도를 업데이트합니다.

Graft를 설치하려면 해당 사이트로 이동해야 하며, 사이트 링크는 설명란에 넣어 두겠습니다. 사이트에서 설치 명령을 복사하거나, 사용 중인 코딩 에이전트에 맞는 설정 프롬프트를 복사해 에이전트에 그대로 붙여 넣을 수 있습니다.

이 설정 프롬프트에는 에이전트가 Graft를 설치하고 프로젝트에 설정하는 데 필요한 모든 명령이 들어 있습니다. 이 부분을 직접 처리하고 싶다면 사이트에서 설치 명령을 복사해 어느 폴더에서든 터미널로 실행하면 됩니다.

설치가 완료되면 CLI를 바로 사용할 수 있습니다. 프로젝트에서 사용하려면 init 명령을 실행해 해당 프로젝트에 Graft를 설정해야 합니다. 이 명령은 작업 중인 폴더 내부의 터미널에서 실행해야 합니다. 해당 프로젝트를 위한 지침을 폴더에 추가하기 때문이며, 다른 곳에서 실행하면 그 지침이 사라집니다.

명령을 실행하면 어떤 코딩 에이전트를 사용하는지 묻습니다. 에이전트마다 자체 설정이 필요하기 때문입니다. 저희는 Claude Code를 사용하고 있었으므로 Claude Code를 선택하고 설치를 진행했습니다.

설치가 끝나면 프로젝트 폴더에 graph 스킬(skill)이 나타납니다. 이 파일은 에이전트에 Graft 사용 방법과 사용할 수 있는 명령을 알려 줍니다. 또한 훅(hook)도 설치됩니다. 훅이 무엇인지 모른다면, 훅은 정해진 시점에 자동으로 실행되는 작은 스크립트입니다.

이러한 훅(hook)들은 에이전트가 그래프 워크플로를 따르도록 강제합니다. 설치되는 훅은 여러 개입니다. 하나는 세션이 시작될 때 모델에 맵을 사용하는 방법을 안내하고, 다른 하나는 여러분이 보내는 각 프롬프트에 일치하는 위치를 첨부하며, 마지막 하나는 Claude가 파일을 수정한 후 실행되어 맵을 최신 상태로 유지합니다.

그다음, 이미 작업 중인 프로젝트에 이를 설정하는 경우에는 같은 폴더에서 그래프 빌드 명령을 실행해야 합니다. 그래야 Graft가 이미 존재하는 모든 코드를 확인하고 그 코드로부터 맵을 구축합니다.

빈 폴더에서 시작하는 경우에는 아직 매핑할 것이 없으므로, 파일이 생기면 스킬이 Claude에게 한 번 맵을 구축하도록 합니다. 그 후에는 평소처럼 Claude Code를 실행하면 되고, 맵 뷰어에는 Graft가 만든 노드와 엣지가 표시됩니다.

빈 폴더에서는 맵이 노드 0개로 시작하고, 파일이 생성되면 Graft가 노드를 추가합니다.

이 CLAUDE.md 파일은 저희 Community AI Labs Pro에서 템플릿으로 업로드한 파일이므로, 같은 템플릿을 사용했습니다. 먼저 PRD를 바탕으로 CLAUDE.md의 빈 부분을 채우라고 요청했습니다. 파일이 템플릿에 불과했기 때문입니다. PRD가 없다면 대신 무엇을 만들고 있는지 프롬프트에 알려주면 됩니다.
