핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
코드 스멜(Code Smell) 코드가 당장 오류는 아니어도 유지보수성을 해치는 신호를 찾는 기준이다 AI에게 “나쁜 냄새”의 이름만 알려줘도 리뷰 기준이 된다
리팩터링(Refactoring) 기능은 유지하면서 코드 구조를 개선하는 핵심 개발 습관이다 AI 에이전트에게 리팩터링 관점을 주면 단순 수정이 아니라 구조 개선을 시킨다
에이전트의 사전지식(Priors) 유명한 개발 개념은 AI가 이미 많이 학습했을 가능성이 높다 긴 설명보다 익숙한 개념명을 호출하는 것이 효율적이다
메시지 체인(Message Chains) 객체가 객체를 타고 들어가는 긴 호출 구조는 결합도를 높인다 “메시지 체인을 찾아 제거해”라고 하면 AI가 패턴을 인식한다
미들맨(Middle Man) 중간 객체가 실제 역할 없이 전달만 하면 구조가 불필요하게 복잡해진다 AI가 “중간 전달자” 역할의 클래스를 찾아 정리할 수 있다

내가 모를 만한 것 / 처음 보는 것

  • 미스터리한 이름(Mysterious Name) — 변수, 함수, 클래스 이름이 의도를 설명하지 못하는 코드 스멜.
  • 기능 편애(Feature Envy) — 어떤 함수가 자기 객체보다 다른 객체의 데이터에 더 관심을 가지는 상황.
  • 데이터 뭉치(Data Clumps) — 여러 데이터가 항상 함께 이동하거나 반복해서 묶여 다니는 구조.
  • 원시 타입 집착(Primitive Obsession) — 도메인 개념을 객체나 타입으로 만들지 않고 문자열, 숫자 같은 원시 타입으로만 처리하는 습관.
  • 반복되는 스위치(Repeated Switches) — 비슷한 조건문이나 분기문이 여러 곳에 반복되는 구조.
  • 산탄총 수술(Divergent Change) — 하나의 변경 때문에 여러 파일이나 클래스가 함께 바뀌어야 하는 문제.
  • 추측성 일반화(Speculative Generalization) — 필요하지 않은 미래 확장성을 미리 과하게 설계하는 문제.
  • 메시지 체인(Message Chains) — a.getB().getC().doSomething()처럼 객체 내부를 연쇄적으로 파고드는 호출 구조.
  • 미들맨(Middle Man) — 실제 로직 없이 다른 객체에 요청만 넘기는 불필요한 중간 계층.

  1. 리팩터링(Refactoring)은 오래되고 많이 인용된 책이라고 표현한다 — 그래서 그 책의 코드 스멜(Code Smell) 개념들이 AI 에이전트의 사전지식(Priors)에 깊게 들어가 있다고 본다.
  2. 코드 스멜을 길게 설명할 필요 없이 한 문장으로 묘사하면 충분하다고 말한다 — 핵심은 AI가 이미 알고 있는 개념명을 “호출”하는 것이다.
  3. 예시로 든 코드 스멜이 매우 구체적이다 — 미스터리한 이름(Mysterious Name), 중복 코드(Duplicated Code), 기능 편애(Feature Envy), 데이터 뭉치(Data Clumps), 원시 타입 집착(Primitive Obsession), 반복되는 스위치(Repeated Switches), 발산적 변경(Divergent Change), 추측성 일반화(Speculative Generalization), 메시지 체인(Message Chains).
  4. AI 에이전트가 사용자의 단어를 되받아 말한다고 한다 — 예: “메시지 체인을 찾았습니다. 제거해야 합니다”, “미들맨(Middle Man) 상황을 찾았습니다. 고쳐야 합니다.”
  5. 화자는 이 방식을 몇 주 동안 테스트했다고 말한다 — 단순 아이디어가 아니라 실제 코드 품질 개선에 유용했다고 평가한다.
  6. 프롬프트나 규칙 추가 비용이 작다고 강조한다 — 대략 10줄 정도만 추가해도 효과가 있다고 말한다.

# 섹션 요지
1 핵심 주장 유명한 리팩터링 개념은 AI가 이미 알고 있으므로 짧게 지시해도 작동한다
2 코드 스멜 예시 메시지 체인, 미들맨, 중복 코드 등 고전적 코드 스멜을 기준으로 삼는다
3 에이전트 활용법 “이런 코드 스멜을 찾아 고쳐라”는 식으로 한 문장 규칙을 넣는다
4 실제 효과 몇 주간 테스트 결과 코드 품질 개선에 매우 유용했고 추가 비용도 낮았다

1. 오래된 리팩터링 지식은 AI가 이미 알고 있다

화자는 리팩터링(Refactoring) 책이 오래되었고, 개발자들에게 매우 많이 인용된 책이라는 점을 먼저 짚는다.
이 말의 핵심은 “AI에게 모든 것을 처음부터 설명할 필요가 없다”는 것이다.

예를 들어 개발 세계에서 오래 반복된 개념들은 대규모 학습 데이터 안에 많이 들어갔을 가능성이 높다. 그래서 AI 에이전트는 코드 스멜(Code Smell), 중복 코드(Duplicated Code), 메시지 체인(Message Chains) 같은 표현을 들으면 이미 어느 정도 의미를 알고 있다.

즉, 에이전트를 잘 쓰려면 긴 설명보다 이미 알려진 개념명을 정확히 호출하는 것이 더 중요하다.

2. 코드 스멜 이름만 알려줘도 리뷰 기준이 된다

화자는 여러 코드 스멜 예시를 나열한다.
여기서 중요한 점은 각 항목을 자세히 설명하지 않아도, AI 에이전트가 해당 개념을 기준으로 코드를 살펴볼 수 있다는 것이다.

대표 예시는 다음과 같다.

  • 미스터리한 이름(Mysterious Name): 이름만 봐서는 역할을 알 수 없는 변수, 함수, 클래스
  • 중복 코드(Duplicated Code): 같은 로직이 여러 곳에 반복되는 구조
  • 기능 편애(Feature Envy): 한 함수가 자기 객체보다 다른 객체의 데이터에 더 의존하는 상황
  • 데이터 뭉치(Data Clumps): 항상 같이 다니는 여러 값들이 구조화되지 않은 상태
  • 원시 타입 집착(Primitive Obsession): 도메인 개념을 문자열, 숫자 등 원시 타입으로만 표현하는 문제
  • 반복되는 스위치(Repeated Switches): 비슷한 조건 분기가 여러 위치에 반복되는 구조
  • 발산적 변경(Divergent Change): 하나의 변경 요구가 여러 곳의 수정을 유발하는 구조
  • 추측성 일반화(Speculative Generalization): 아직 필요 없는 확장성을 미리 과도하게 넣는 설계
  • 메시지 체인(Message Chains): 객체 내부 구조를 연쇄적으로 타고 들어가는 호출 방식

이런 항목들을 AI에게 “찾아봐”라고 지시하면, 에이전트는 이를 코드 리뷰 체크리스트처럼 사용할 수 있다.

3. 에이전트는 문제 이름을 되받아 말하며 수정 방향을 잡는다

화자는 AI 에이전트가 사용자가 던진 개념을 다시 언급하면서 문제를 인식한다고 말한다.

예를 들어 다음과 같은 식이다.

  • “메시지 체인(Message Chains)을 찾았습니다. 제거해야 합니다.”
  • “미들맨(Middle Man) 상황이 있습니다. 이 부분을 고쳐야 합니다.”

이 방식이 유용한 이유는 AI가 단순히 “코드를 예쁘게 고쳐줘”라는 막연한 요청을 받는 것이 아니라, 구체적인 리팩터링 기준을 갖게 되기 때문이다.

좋은 프롬프트는 AI에게 ‘무엇을 고칠지’뿐 아니라 ‘어떤 관점으로 볼지’를 알려준다.

4. 짧은 규칙 추가만으로 코드 품질 개선 효과가 있다

화자는 이 방법을 몇 주 동안 테스트했고, 코드 품질을 개선하는 데 매우 유용했다고 평가한다.
특히 강조하는 부분은 추가 비용이 매우 낮다는 점이다.

복잡한 도구를 새로 만들거나 긴 문서를 붙일 필요 없이, 대략 10줄 정도의 규칙만 추가해도 충분히 효과를 볼 수 있다는 것이다.

예를 들어 AI 코딩 도구의 지침에 다음과 같은 식으로 넣을 수 있다.

  • 리팩터링(Refactoring) 관점에서 코드를 검토하라.
  • 코드 스멜(Code Smell)을 찾아라.
  • 중복 코드(Duplicated Code), 메시지 체인(Message Chains), 미들맨(Middle Man), 원시 타입 집착(Primitive Obsession)을 우선 확인하라.
  • 발견한 코드 스멜의 이름과 수정 이유를 설명하라.
  • 기능 변경 없이 구조를 개선하라.

차드처럼 비개발자 입장에서 AI 코딩을 배울 때도 이 접근은 유용하다.
“코드를 잘 고쳐줘”보다 “리팩터링 책의 코드 스멜 기준으로 문제를 찾아줘”가 훨씬 더 구체적이고 재사용 가능한 지시이기 때문이다.

종합 체크리스트

  • [ ] 내 AI 코딩 지침에 코드 스멜(Code Smell) 점검 항목을 추가한다.
  • [ ] “중복 코드(Duplicated Code)를 찾아 제거해줘”처럼 개념명을 직접 넣어 요청한다.
  • [ ] 코드 리뷰 요청 시 “리팩터링(Refactoring) 관점”을 명시한다.
  • [ ] AI가 발견한 문제에 대해 “어떤 코드 스멜인지 이름을 붙여 설명해줘”라고 요구한다.
  • [ ] 메시지 체인(Message Chains), 미들맨(Middle Man), 원시 타입 집착(Primitive Obsession)부터 실제 코드에 적용해본다.
  • [ ] 기능 변경 없이 구조만 개선하는 리팩터링인지 확인한다.

리팩터링(Refactoring)은 오래된 책이고, 정말 많이 인용된 책입니다. 그래서 이런 종류의 코드 스멜(Code Smell)은 에이전트의 사전지식(Priors) 안에 깊게 들어가 있습니다.

그래서 우리가 해야 할 일은 그 개념을 불러내는 정도입니다. 예를 들어 미스터리한 이름(Mysterious Name), 중복 코드(Duplicated Code), 기능 편애(Feature Envy), 데이터 뭉치(Data Clumps), 원시 타입 집착(Primitive Obsession), 반복되는 스위치(Repeated Switches), 발산적 변경(Divergent Change), 추측성 일반화(Speculative Generalization), 메시지 체인(Message Chains) 같은 것들입니다.

무슨 말인지 아시겠죠? 이런 개념들은 모두 에이전트의 지식 기반(Knowledge Base) 안에 깊게 들어 있습니다.

그래서 우리는 그것들을 정말 한 문장으로 설명하기만 하면 됩니다.

제가 발견한 것은, 그렇게 하면 에이전트가 그 단어를 다시 되풀이하면서 이렇게 말한다는 점입니다. “네, 메시지 체인(Message Chains)을 찾았습니다. 제거해야 합니다.” 또는 “미들맨(Middle Man) 상황을 찾았습니다. 이 부분을 고쳐야 합니다.”

저는 이 방식을 몇 주 동안 테스트해봤고, 말도 안 되게 유용했습니다. 제 코드 품질을 개선하는 데 정말 좋았습니다. 그리고 여기에 추가하는 비용도 매우 낮습니다. 그냥 10줄 정도만 넣으면 됩니다.
