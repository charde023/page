핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
스펙(Spec)과 티켓(Ticket) 분리 막연한 아이디어를 실행 가능한 작업 단위로 바꾸는 핵심 구조 먼저 목적지를 스펙으로 정하고, 그다음 티켓으로 나눠 실행한다.
/to-spec, /to-tickets 이름 변경 기존 /to-prd, /to-issues보다 실제 역할을 정확히 표현 PRD가 아니라 더 넓은 의미의 명세서, 이슈가 아니라 작업 티켓이다.
그릴링(Grilling) 개선 AI가 사용자를 질문하며 요구사항을 명확히 하는 단계 한 번에 여러 질문하지 않고, 합의 전 구현으로 넘어가지 않도록 게이트를 추가했다.
/implement 티켓별 구현 흐름을 표준화 각 티켓을 별도 세션에서 구현하고, 테스트·타입체크·코드리뷰·커밋까지 수행한다.
코드리뷰(Code Review)와 리팩터링 스멜(Refactoring Smell) AI가 코드 품질 문제를 더 잘 잡도록 유도 Martin Fowler의 코드 냄새 개념을 활용해 중복, 메시지 체인, 데이터 뭉치 등을 찾는다.
/wayfinder 한 세션에 담기 어려운 큰 기획을 쪼개는 도구 GitHub 이슈를 지도처럼 써서 조사·질문·프로토타입 작업을 나눠 진행한다.
/research, /prototype Wayfinder를 보조하는 사전 탐색 도구 조사와 프로토타입으로 스펙 작성 전 논의의 해상도를 높인다.
TDD 스킬 단순화 에이전트가 AFK 상태에서도 자연스럽게 테스트 주도 개발을 수행하게 함 이제 TDD는 절차 강제보다 참고 자료에 가깝고, 리팩터링은 코드리뷰 단계로 이동했다.

내가 모를 만한 것 / 처음 보는 것

  • 스킬 저장소(skills repo) — Claude Code 같은 AI 코딩 도구에서 반복 작업을 명령어처럼 실행하도록 정리한 프롬프트·워크플로우 모음.
  • 그릴링(Grilling) — AI가 바로 구현하지 않고 사용자에게 질문을 던져 요구사항, 제약, 의사결정을 끌어내는 과정.
  • 공유 이해(Shared Understanding) — 사용자와 AI가 “무엇을 만들지”에 대해 같은 이해에 도달한 상태.
  • 스마트 존(Smart Zone) — 에이전트가 문맥을 잘 유지하며 품질 있게 사고할 수 있는 실질적 범위. 너무 긴 세션은 이 구간을 벗어날 수 있다.
  • 컨텍스트 윈도(Context Window) — AI 모델이 한 번에 기억하고 처리할 수 있는 입력 범위.
  • 아키텍처 의사결정 기록(Architectural Decision Record, ADR) — 왜 특정 설계를 선택했는지 남기는 문서.
  • 리팩터링 스멜(Refactoring Smell) — 코드가 나빠질 가능성을 보여주는 징후. 예: 중복 코드, 데이터 뭉치, 메시지 체인.
  • AFK 작업(AFK Task) — 사람이 자리를 비운 상태에서도 AI 에이전트가 독립적으로 수행할 수 있는 작업.
  • 스파이크(Spike) — 큰 결정을 내리기 전에 기술 가능성을 짧게 조사·검증하는 실험.
  • 블로킹 관계(Blocking Relationship) — 어떤 티켓이 끝나야 다음 티켓을 진행할 수 있는 의존 관계.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. /to-prd는 /to-spec으로, /to-issues는 /to-tickets로 변경 — 기존 이름이 실제 산출물과 맞지 않아 오래 거슬렸다고 설명한다.
  2. 새 스킬을 받으려면 npx skills add mattpocock skills 실행 권장 — 이름 변경은 기존 설치기가 자동 업데이트로 잘 처리하지 못할 수 있기 때문이다.
  3. 기존 스킬 폴더를 직접 확인하라고 권장 — 옛 이름의 스킬이 남아 있을 수 있으므로 의도적으로 정리해야 한다.
  4. 그릴링에서 “한 번에 여러 질문하지 말라”는 문장을 더 강하게 수정 — AI가 여러 질문을 한꺼번에 던지면 사용자가 혼란스러워지기 때문이다.
  5. “공유 이해에 도달했다고 내가 확인하기 전까지 계획을 실행하지 말라”는 확인 게이트 추가 — 그릴링 직후 AI가 바로 구현에 들어가는 문제를 막기 위함.
  6. 사실(Facts)과 결정(Decisions)을 구분 — 코드를 탐색해 얻을 수 있는 사실과 사용자가 내려야 하는 결정을 분리해 AI가 자기 자신에게 질문하는 문제를 줄였다.
  7. /implement는 일부러 단순하게 유지 — 복잡한 절차보다 “티켓 구현, TDD 가능하면 사용, 타입체크와 테스트, 코드리뷰, 커밋” 정도만 지시한다.
  8. 코드리뷰는 두 축으로 진행 — 저장소의 코딩 표준(Standards) 준수 여부와 원래 스펙(Spec) 충실 구현 여부를 병렬 서브에이전트(Subagent)로 확인한다.
  9. 코딩 표준은 agents.md보다 별도 coding standards.md에 두는 것을 선호 — 코드리뷰 시점에 가장 유용하다고 본다.
  10. Wayfinder는 큰 기획을 GitHub 이슈 지도(Map)로 쪼갬 — 조사, 그릴링, 프로토타입, 일반 작업 티켓을 각각 한 세션 크기로 만든다.
  11. 프론트엔드가 관련된 일에는 Wayfinder를 특히 추천 — 화면·동작을 빨리 구체화해야 논의 품질이 올라가기 때문이다.
  12. TDD는 이제 red → green 중심 — 리팩터링(Refactor)은 구현 루프 안이 아니라 코드리뷰 단계에서 처리하는 편이 낫다고 본다.
  13. 사용량 수치 언급 — 별(star)이 약 160k, skills.sh 다운로드가 700만 회라고 말한다.

1. v1.1 공개와 전체 방향

화자는 오랜만에 영상을 올린 이유가 자신의 Claude Code용 스킬 저장소(skills repo) v1.1 작업 때문이라고 말한다. 이번 업데이트에는 단순한 명령 추가가 아니라, 기획부터 구현·리뷰까지 이어지는 전체 흐름의 변화가 포함되어 있다.

특히 이번 버전은 다음 성격이 강하다.

  • 기존 스킬 이름을 실제 역할에 맞게 정리
  • 그릴링(Grilling) 방식 안정화
  • 구현 단계까지 포함하는 개발 생명주기(Software Development Lifecycle) 보강
  • 큰 기획을 다루기 위한 Wayfinder 도입
  • 코드리뷰와 TDD 방식 재정리

핵심은 “AI에게 바로 코딩시키는 것”이 아니라, AI와 함께 계획을 명확히 만들고, 작은 단위로 나눠, 각 단위를 안정적으로 구현하는 흐름이다.

2. /to-prd는 /to-spec, /to-issues는 /to-tickets로 변경

가장 눈에 띄는 변화는 스킬 이름 변경이다.

기존 /to-prd는 /to-spec이 되었다. 화자는 이전 이름이 오래전부터 마음에 걸렸다고 한다. 실제로 만들고 있던 문서는 제품 요구사항 문서(Product Requirements Document, PRD)라기보다 더 넓은 의미의 명세서(Specification, Spec)였기 때문이다.

PRD는 보통 제품 자체의 요구사항을 설명하는 문서에 가깝다. 하지만 이 스킬에서 다루는 내용은 기술적인 내용일 수도 있고, 비기술적인 내용일 수도 있으며, 둘이 섞일 수도 있다. 그래서 “우리가 만들고 싶은 것에 대한 명세”라는 의미의 스펙(Spec)이 더 정확하다고 본다.

또한 /to-issues는 /to-tickets로 바뀌었다. “이슈(Issue)”라는 말은 GitHub나 Linear에 치우친 느낌이 있는데, 실제 의도는 스펙을 실행 가능한 작업 티켓(Ticket)으로 나누는 것이다.

정리하면 흐름은 다음과 같다.

  1. 아이디어나 요구사항을 스펙(Spec)으로 만든다.
  2. 스펙 아래에 실행 경로가 되는 티켓(Ticket)을 만든다.
  3. 각 티켓을 별도 세션에서 구현한다.

다만 이름 변경 때문에 기존 설치 상태에서는 수동 정리가 필요할 수 있다. 화자는 다음 명령어로 새 스킬을 다시 추가하는 것을 권장한다.

npx skills add mattpocock skills

설치기가 이름 변경을 자동으로 감지해 /to-prd를 /to-spec으로 바꿔주지 못할 가능성이 있기 때문이다. 그래서 새로 필요한 스킬을 고르고, 기존 스킬 폴더에 예전 이름의 스킬이 남아 있지 않은지 확인하라고 말한다.

3. 그릴링 스킬 개선: 질문, 확인, 사실과 결정 분리

이번 업데이트에서는 Grill Me, Grill With Docs 같은 그릴링(Grilling) 관련 스킬도 개선되었다.

그릴링은 AI가 사용자를 심문하듯 몰아붙인다는 뜻이 아니라, 요구사항을 명확히 하기 위해 한 번에 하나씩 질문하는 과정이다. 개발 전 “정말 무엇을 만들려는가?”를 분명히 하는 단계라고 보면 된다.

개선점은 크게 세 가지다.

첫째, AI가 한 번에 여러 질문을 던지지 않도록 문구를 강화했다. 기존에도 “한 번에 하나씩 질문하라”고 되어 있었지만, 일부 모델은 여전히 여러 질문을 한꺼번에 던졌다. 그래서 “여러 질문을 동시에 하면 사용자가 혼란스러워진다”는 이유까지 명시했다.

둘째, 구현 전 확인 게이트(Confirmation Gate)를 추가했다. 일부 사용자는 그릴링 세션이 끝나자마자 AI가 바로 구현에 들어가는 문제를 겪었다. 이를 막기 위해 다음 취지의 지시를 추가했다.

내가 공유 이해(Shared Understanding)에 도달했다고 확인하기 전까지 계획을 실행하지 말라.

셋째, 사실(Facts)과 결정(Decisions)을 분리했다. 어떤 경우에는 AI가 코드베이스를 탐색하다가 자기 자신에게 질문하는 이상한 상황이 생겼다. 이를 줄이기 위해 다음처럼 역할을 나눴다.

  • 사실(Facts): 코드베이스를 탐색해 AI가 직접 찾을 수 있는 정보
  • 결정(Decisions): 사용자가 내려야 하는 선택

이 구분 덕분에 AI가 “조사해서 알 수 있는 것”과 “사장이나 개발자가 결정해야 하는 것”을 덜 혼동하게 된다.

4. 전체 개발 생명주기: 그릴링 → 스펙 → 티켓 → 구현 → 코드리뷰

화자는 사람들이 자주 묻는 질문이 “스킬을 어떤 순서로 써야 하느냐”였다고 말한다. v1.1은 그 답을 더 명확하게 만든다.

기본 흐름은 다음과 같다.

  1. 계획 모드(Plan Mode) 대신 에이전트에게 그릴링을 시킨다.
  2. 그 과정에서 용어집(Glossary)과 아키텍처 의사결정 기록(ADR)을 보강한다.
  3. 그릴링 결과를 스펙(Spec)으로 만든다.
  4. 스펙을 여러 티켓(Ticket)으로 나눈다.
  5. 각 티켓을 별도의 코딩 세션에서 구현한다.
  6. 구현 후 코드리뷰(Code Review)를 수행한다.
  7. 현재 브랜치에 커밋한다.

여기서 새로 강조되는 스킬이 /implement다. 화자는 처음에는 너무 단순해서 굳이 스킬로 만들 필요가 없다고 생각했다. 하지만 사람들이 “그다음 무엇을 해야 하느냐”고 계속 묻자, 흐름을 명확히 하기 위해 추가했다.

/implement의 핵심 지시는 단순하다.

  • 사용자에게 받은 스펙이나 티켓의 작업을 구현한다.
  • 가능하면 사전에 합의한 지점에서 TDD를 사용한다.
  • 타입체크(Type Checking)를 자주 실행한다.
  • 단일 테스트 파일을 자주 실행한다.
  • 전체 테스트 스위트(Full Test Suite)는 마지막에 한 번 실행한다.
  • 완료 후 코드리뷰를 실행한다.
  • 현재 브랜치에 커밋한다.

즉 /implement는 복잡한 마법 명령이 아니라, 티켓별 구현 세션을 안전하게 마무리하는 체크리스트형 스킬이다.

5. 코드리뷰: 표준 준수와 스펙 충실도, 그리고 코드 냄새

코드리뷰(Code Review) 스킬은 두 가지 축으로 코드를 검토한다.

첫 번째 축은 저장소의 코딩 표준(Standards)이다. 저장소 안에 coding standards.md 같은 문서가 있다면, AI가 그 문서를 읽고 코드가 기준을 따르는지 확인한다. 화자는 코딩 표준을 agents.md에 넣기보다 별도 문서로 두는 편이 좋다고 본다. 특히 코드리뷰 단계에서 그 문서가 가장 유용하기 때문이다.

두 번째 축은 스펙 충실도다. 즉, 작성된 코드가 원래의 이슈, PRD, 스펙을 제대로 구현했는지 확인한다.

이번 업데이트에서 특히 흥미로운 점은 Martin Fowler의 리팩터링(Refactoring) 책에 나오는 코드 냄새(Code Smell) 개념을 코드리뷰에 넣었다는 것이다. 이 개념들은 오래되고 유명해서 AI 모델의 사전 지식에도 깊게 들어가 있다. 따라서 이름만 잘 불러줘도 AI가 해당 문제를 잘 찾아낸다는 설명이다.

예시로 언급된 코드 냄새는 다음과 같다.

  • 알 수 없는 이름(Mysterious Name)
  • 중복 코드(Duplicated Code)
  • 기능 편애(Feature Envy)
  • 데이터 뭉치(Data Clumps)
  • 원시값 집착(Primitive Obsession)
  • 반복되는 스위치(Repeated Switches)
  • 산탄총 수술 또는 발산적 변경(Divergent Change)
  • 추측성 일반화(Speculative Generalization)
  • 메시지 체인(Message Chains)
  • 중간자(Middle Man)

화자는 이 접근을 몇 주 동안 테스트했고, 코드 품질 개선에 매우 유용했다고 말한다. 추가 비용도 크지 않다. 짧은 설명 몇 줄만으로 AI가 “여기에 메시지 체인이 있다”, “여기 중간자 문제가 있다”처럼 문제를 짚어내기 때문이다.

6. Wayfinder: 큰 기획을 GitHub 이슈 지도로 쪼개기

이번 업데이트에서 화자가 가장 기대하는 기능은 /wayfinder다.

Wayfinder는 한 번의 AI 에이전트 세션으로 다루기에는 너무 큰 기획을 위한 스킬이다. 예를 들어 다음과 같은 상황이다.

  • 아이디어가 너무 크다.
  • 아직 방향이 흐릿하다.
  • 어떤 결정을 먼저 내려야 할지 모른다.
  • 한 세션에서 다루면 컨텍스트 윈도(Context Window)를 초과할 것 같다.
  • 에이전트의 스마트 존(Smart Zone)을 벗어날 것 같다.

Wayfinder는 이런 큰 기획을 GitHub 이슈 기반의 지도(Map)로 만든다. 지도에는 여러 하위 이슈(Sub-issue)가 생기고, 각 이슈는 한 에이전트 세션에서 처리할 수 있는 크기로 제한된다.

예를 들어 화자는 Sandcastle 저장소에서 AI SDK를 의존성으로 추가할지 검토하는 큰 변경을 예로 든다. 아직 결정은 내려지지 않았고, 내려야 할 결정들이 하위 이슈로 정리되어 있다. 일부 이슈는 다른 이슈가 먼저 해결되어야 하는 블로킹 관계(Blocking Relationship)를 가진다.

Wayfinder의 티켓 유형은 대략 다음과 같다.

티켓 유형 의미
조사(Research) 에이전트가 자료를 조사하고 결과를 가져오는 작업
그릴링(Grilling) 사용자의 판단과 의사결정이 필요한 질문 세션
프로토타입(Prototype) 논의를 구체화하기 위한 거친 산출물 제작
일반 작업(Task) 설정, 접근 권한, 데이터 이동 등 사람이 처리해야 하는 잡무

화자는 특히 프론트엔드 코드가 관련된 작업에는 Wayfinder를 강하게 추천한다. 화면이 어떻게 보여야 하는지, 동작이 어떻게 느껴져야 하는지는 말로만 논의하면 흐릿하기 때문이다. 이때 프로토타입을 만들어두면 논의의 해상도(Fidelity)가 올라간다.

모든 티켓이 닫히면, 각 티켓에서 얻은 정보가 원래 지도에 저장된다. 그다음 이 지도를 일반적인 방식으로 /to-spec에 넘겨 스펙으로 만들 수 있다.

Wayfinder의 장점은 세션 관리 부담을 줄여준다는 점이다. 기존 Grill With Docs에서는 사용자가 “지금 세션이 너무 길어졌나?”, “어디서 끊어야 하나?”를 신경 써야 했다. Wayfinder는 작업이 GitHub 이슈에 저장되므로 협업도 쉽고, 다음 세션으로 넘기기도 쉽다.

7. /research와 /prototype: Wayfinder를 보조하는 스킬

Wayfinder를 지원하기 위해 /research 스킬도 추가되었다.

/research는 단순하지만 유용하다. AI가 백그라운드 에이전트(Background Agent)를 띄워 조사하게 하고, 사용자는 그동안 다른 작업을 계속할 수 있다. 조사 결과는 저장소의 기존 관례에 맞춰 간단한 마크다운 파일로 저장한다.

중요한 점은 “1차 출처(Primary Sources)를 기준으로 조사하라”는 방향이다. 즉 블로그 요약이나 떠도는 정보보다 공식 문서, 원문, 실제 저장소 같은 신뢰도 높은 자료를 우선하라는 뜻이다.

/prototype도 Wayfinder가 호출할 수 있도록 모델 호출형(Model-invoked)으로 바뀌었다. 프로토타입은 크게 두 종류로 나뉜다.

  • 로직 프로토타입(Logic Prototype)
  • UI 프로토타입(UI Prototype)

프로토타입의 목적은 완성품을 만드는 것이 아니다. 싸고 거칠지만 구체적인 산출물을 만들어 “이 방향이 맞는지” 반응할 수 있게 하는 것이다.

이건 이커머스 관점에서도 중요하다. 예를 들어 관리자 페이지, 주문 처리 화면, 물류 출고 플로우를 만들 때 처음부터 완벽한 개발을 시작하기보다, 간단한 화면 흐름이나 버튼 동작을 먼저 만들어 보면 의사결정이 훨씬 빨라진다.

8. TDD 스킬 업데이트: 절차 강제에서 참고 자료로

마지막 주요 변경은 TDD(Test-Driven Development) 스킬이다.

이전 TDD 스킬은 AI에게 따라야 할 여러 단계를 제시했다. 예를 들어 어떤 테스트를 쓸지 사용자와 확인하고, 그다음 구현하는 식이었다. 하지만 이 방식은 사람들이 기대하는 TDD와 맞지 않는 경우가 있었다.

많은 사용자는 TDD 스킬을 AFK 에이전트에게 넘기면 알아서 잘 작동하길 원한다. 그래서 새 TDD 스킬은 특정 절차를 강제하기보다 참고 자료(Reference Material)에 가깝게 바뀌었다.

핵심은 간단하다.

  • 빨강(Red): 실패하는 테스트를 먼저 쓴다.
  • 초록(Green): 테스트를 통과하도록 구현한다.
  • 한 번에 한 조각(Slice)씩 진행한다.

흥미로운 점은 리팩터링(Refactor)을 TDD 루프에서 분리했다는 것이다. 전통적으로 TDD는 Red → Green → Refactor라고 많이 말하지만, 화자는 구현 중 리팩터링까지 넣으면 부담이 커진다고 본다. 대신 리팩터링은 코드리뷰 단계에서 처리하는 편이 더 생산적이라고 말한다.

구현 중에는 Red → Green에 집중하고, 리팩터링은 코드리뷰에서 처리한다.

9. 마이그레이션과 마무리

화자는 업데이트를 놓치는 것이 걱정된다면 기존 스킬을 정리하고 새로 업데이트하라고 권장한다. 특히 이름이 바뀐 /to-spec, /to-tickets는 약간의 마찰을 만들 수 있지만, 이름이 정확해지는 좋은 마찰이라고 설명한다.

또한 Wayfinder를 매우 강하게 추천한다. 본인은 코딩 작업뿐 아니라 다음 강의 기획 같은 비개발 작업에도 Wayfinder를 사용하고 있다고 한다.

마지막으로 사용량도 언급한다.

  • GitHub 별(star): 약 160k
  • skills.sh 다운로드: 약 700만 회

화자는 이 스킬들이 사용자가 더 많이, 더 생산적으로 제품을 출시하는 데 도움이 되길 바란다고 마무리한다.

안녕하세요, 여러분. 오랜만에 올리는 첫 영상입니다. 그동안 제 스킬 저장소(skills repo) v1.1을 작업하고 있었기 때문입니다. 이번 버전에는 정말 많은 내용이 들어갔습니다. 그릴링(Grilling)에 대한 완전히 새로운 접근도 있고, 기존 스킬의 변경도 많으며, 주요 흐름 스킬 두 개는 이름도 바뀌었습니다.

이제 PR이 병합 준비가 되었으니 바로 병합하겠습니다. 이렇게 해서 v1.1이 준비되었습니다.

먼저 사용자 입장에서 가장 성가실 수 있는 변경부터 말하겠습니다. 두 스킬의 이름이 바뀌었습니다. /to-prd는 /to-spec으로, /to-issues는 /to-tickets로 바뀌었습니다.

이유는 명확합니다. 우리가 만들던 것은 사실 PRD(Product Requirements Document)가 아니라 스펙(Spec)이었습니다. PRD는 제품 자체의 요구사항을 설명하는 문서에 더 가깝지만, 기존 스킬에서는 기술적인 것과 비기술적인 것이 섞여 들어갔습니다. 그래서 더 넓은 의미의 명세서(Specification)가 맞습니다.

/to-issues도 마찬가지입니다. 이슈(Issue)는 GitHub나 Linear에 치우친 표현입니다. 실제로 필요한 것은 스펙 아래에서 실행 경로가 되는 티켓(Ticket)입니다.

이 이름 변경 때문에 기존 스킬을 지우고 다시 추가해야 할 수 있습니다. npx skills add mattpocock skills를 실행하는 것이 가장 안전합니다. 설치기가 이름 변경을 자동으로 감지하지 못할 수 있기 때문입니다. 설치 후에는 스킬 폴더를 확인해 오래된 스킬이 남아 있지 않은지 살펴보는 것이 좋습니다.

다음으로 Grill Me와 Grill With Docs 관련 버그를 고쳤습니다. 두 스킬은 LLM이 사람에게 질문하는 방식을 알려주는 중심 그릴링 스킬에 의존합니다. “한 번에 여러 질문을 하면 혼란스럽다”는 문장을 더 명확히 넣었습니다. 또한 “공유 이해에 도달했다고 내가 확인하기 전까지 계획을 실행하지 말라”는 확인 게이트를 추가했습니다.

일부 모델에서는 그릴링 세션이 끝나자마자 바로 구현에 들어가는 문제가 있었습니다. 또 어떤 경우에는 AI가 자기 자신을 그릴링하는 이상한 상황도 있었습니다. 그래서 사실(Facts)과 결정(Decisions)을 구분했습니다. 사실은 코드베이스를 탐색해서 찾을 수 있는 것이고, 결정은 사용자가 내려야 하는 것입니다.

다음 변화는 전체 프로세스를 제대로 된 소프트웨어 개발 생명주기(Software Development Lifecycle)로 만든 것입니다. 기본 흐름은 이렇습니다. 계획 모드(Plan Mode)를 쓰는 대신 에이전트에게 그릴링을 시킵니다. 그 과정에서 용어집(Glossary)과 아키텍처 의사결정 기록(ADR)을 추가합니다. 그릴링 결과는 스펙(Spec)이 되고, 스펙은 개별 티켓(Ticket)으로 나뉩니다. 각 티켓은 별도 에이전트 세션에서 구현합니다.

이를 위해 /implement 스킬을 추가했습니다. 이 스킬은 매우 단순합니다. 사용자에게 받은 스펙이나 티켓의 작업을 구현하고, 가능하면 사전에 합의한 지점에서 TDD를 사용합니다. 타입체크를 자주 실행하고, 단일 테스트 파일도 자주 실행하며, 전체 테스트 스위트는 마지막에 한 번 실행합니다. 완료되면 코드리뷰를 하고 현재 브랜치에 커밋합니다.

코드리뷰(Code Review) 스킬은 두 축으로 작동합니다. 첫째, 코드가 저장소의 문서화된 코딩 표준(Standards)을 따르는지 봅니다. 저장소에 coding standards.md 같은 파일이 있으면 그것을 읽고 검토합니다. 둘째, 코드가 원래 이슈, PRD, 스펙을 충실히 구현했는지 확인합니다.

이번 코드리뷰 스킬에는 Martin Fowler의 리팩터링(Refactoring) 책에 나오는 코드 냄새(Code Smell)를 활용했습니다. 예를 들어 알 수 없는 이름(Mysterious Name), 중복 코드(Duplicated Code), 기능 편애(Feature Envy), 데이터 뭉치(Data Clumps), 원시값 집착(Primitive Obsession), 반복되는 스위치(Repeated Switches), 발산적 변경(Divergent Change), 추측성 일반화(Speculative Generalization), 메시지 체인(Message Chains) 같은 것들입니다.

이런 개념은 오래되고 널리 인용된 책에 나오는 내용이라 AI 모델의 사전 지식에도 깊게 들어 있습니다. 그래서 몇 줄만 설명해도 에이전트가 “여기에 메시지 체인이 있다”, “여기 중간자 문제가 있다”라고 잘 찾아냅니다. 몇 주 테스트해보니 코드 품질 개선에 매우 유용했습니다.

이제 가장 기대하는 새 스킬인 Wayfinder를 소개하겠습니다. Wayfinder는 스펙 이전 단계, 즉 큰 계획을 시작하고 형태를 잡는 단계에 들어갑니다. 어떤 경우에는 Grill With Docs를 대체할 수도 있습니다.

Wayfinder는 한 에이전트 세션으로 다루기엔 너무 큰 기획을 위한 스킬입니다. 아이디어가 크고 흐릿하며, 목적지까지 가는 길이 아직 보이지 않을 때 사용합니다. 이 스킬은 저장소의 이슈 트래커에 공유 지도(Map)를 만들고, 그 지도 위의 티켓을 하나씩 처리해 길을 찾습니다.

이 지도는 GitHub 이슈에 저장됩니다. 예를 들어 Sandcastle 저장소에서 AI SDK를 의존성으로 도입할지 검토하는 스파이크(Spike)를 만들 수 있습니다. 아직 결정은 내려지지 않았고, 내려야 할 결정들이 하위 이슈(Sub-issue)로 저장됩니다. 하위 이슈들에는 블로킹 관계가 있을 수 있습니다. 각 결정은 한 에이전트 세션 크기로 제한됩니다.

티켓 유형에는 조사(Research), 그릴링(Grilling), 프로토타입(Prototype), 일반 작업(Task)이 있습니다. 조사 작업은 에이전트가 자료를 찾아보고 돌아오는 AFK 작업입니다. 그릴링 작업은 사용자와 질문 세션이 필요합니다. 프로토타입은 논의의 해상도를 높이기 위해 싸고 거친 구체적 산출물을 만드는 작업입니다. 화면이나 동작이 핵심 질문일 때 유용하며, 특히 프론트엔드 작업에 매우 중요합니다.

모든 티켓이 닫히면 정보가 지도에 저장되고, 원래 티켓들은 주요 출처 역할을 합니다. 그런 다음 이 지도를 일반적인 방식으로 스펙으로 바꿀 수 있습니다.

Wayfinder를 쓰면 Grill With Docs를 사용할 때처럼 세션이 너무 길어지는지 걱정하지 않아도 됩니다. 세션을 닫고 다음 Wayfinder 티켓을 열면 됩니다. 모든 것이 GitHub에 저장되므로 팀과 공유하기도 쉽습니다. 지도가 완성되면 /to-spec으로 넘어가면 됩니다.

Wayfinder를 지원하기 위해 /research 스킬도 추가했습니다. 이 스킬은 작지만 유용합니다. 백그라운드 에이전트를 띄워 조사를 하게 하고, 사용자는 그동안 계속 작업할 수 있습니다. 질문을 1차 출처(Primary Sources)에 대해 조사하고, 결과를 간단한 마크다운 파일로 저장합니다. 저장 위치는 저장소의 기존 관례를 따릅니다.

/prototype 스킬도 Wayfinder가 직접 호출할 수 있도록 바뀌었습니다. 프로토타입은 로직 프로토타입(Logic Prototype)이나 UI 프로토타입(UI Prototype)으로 나뉘며, 각각 다르게 반응합니다.

마지막 변화는 TDD(Test-Driven Development) 스킬입니다. 이전에는 따라야 할 단계가 많았습니다. 어떤 테스트를 쓸지 확인하고, 함께 진행하는 식이었습니다. 하지만 많은 사람이 기대하는 TDD는 AFK 에이전트에게 넘기면 그냥 작동하는 방식입니다.

그래서 이제 TDD 스킬은 참고 자료에 가깝습니다. 특정 절차를 강제하지 않고, 테스트를 쓰는 순서만 알려줍니다. 빨강(Red) 다음 초록(Green), 한 번에 한 조각씩 진행합니다. 리팩터링(Refactor)은 더 이상 TDD 루프의 일부로 강하게 넣지 않았습니다. 리팩터링은 코드리뷰 단계에서 처리하는 편이 더 생산적이라고 보기 때문입니다.

이것이 이번 스킬 업데이트의 전체 변경 사항입니다. 업데이트를 놓칠까 걱정된다면 기존 스킬을 비우고 새로 업데이트하는 것을 권장합니다. 직접 수정한 스킬이 있다면 제 저장소와 릴리스 노트를 참고해 좋은 새 내용을 가져오면 됩니다.

이번 릴리스에서 기억될 변화는 /to-spec과 /to-tickets일 것입니다. 약간의 마찰이 있겠지만, 이름을 제대로 붙이는 좋은 마찰이라고 생각합니다. 그리고 여러분이 Wayfinder에 빠지기 시작하길 바랍니다. 저는 Wayfinder를 코딩뿐 아니라 다음 강의 기획 같은 비개발 작업에도 사용하고 있습니다.

시청해주셔서 감사합니다. 이 스킬 업데이트를 공유하는 것은 늘 즐겁습니다. 사용량이 계속 늘어나는 것도 정말 멋집니다. 별(star)은 약 160k이고, skills.sh 다운로드는 700만 회입니다. 이 스킬들이 여러분이 더 많이, 더 생산적으로 제품을 출시하는 데 도움이 되길 바랍니다. 곧 다시 뵙겠습니다.
