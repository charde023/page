핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
검증 부채(Verification Debt) AI가 만든 코드와 실제 서비스에 필요한 품질 사이의 차이를 사람이 메워야 하기 때문 AI 코딩이 빠를수록 검증해야 할 양도 함께 늘어난다
정적 분석(Static Analysis) 실행하지 않고 코드 품질, 복잡도, 보안 문제를 자동으로 찾는 기본 장치 AI 코드의 품질 저하를 조기에 발견하는 데 필요하다
제로 트러스트(Zero Trust) 검증 코드가 사람에게서 왔든 AI에게서 왔든 무조건 같은 기준으로 검증해야 하기 때문 “누가 썼는가”가 아니라 “검증을 통과했는가”가 기준이다
다층 검증(Multi-layered Verification) 한 가지 방식으로는 모든 버그, 보안 취약점, 유지보수 문제를 잡을 수 없음 정적 분석, LLM 리뷰, 데이터 흐름 분석, 아키텍처 분석 등을 함께 써야 한다
ACDC, 에이전트 중심 개발 사이클(Agent-Centric Development Cycle) AI 에이전트가 코드를 쓰고, 검증하고, 고치는 반복 구조가 필요함 가이드(Guidance) → 검증(Verification) → 해결(Solve)의 루프
품질 게이트(Quality Gate) 기준 미달 코드를 프로덕션으로 보내지 않기 위한 자동 차단 장치 CI/CD에서 일정 점수를 못 넘으면 배포를 막는다
컨텍스트 관리(Context Management) AI에게 전체 코드베이스를 다 던지면 토큰 낭비와 혼란이 생김 작업에 필요한 맥락만 정확히 제공해야 한다
규정 준수(Compliance)와 감사 추적(Audit Trail) 금융, 의료, 물류 등 규제 산업에서는 검증 기록을 증명해야 함 자동 검증은 “항상 같은 방식으로 검사했다”는 증거가 된다

내가 모를 만한 것 / 처음 보는 것

  • SonarQube — 코드 품질, 보안, 유지보수성(Maintainability)을 검사하는 정적 분석 및 검증 플랫폼.
  • Cursor — AI 기반 코드 에디터. 발표에서는 AI가 코드 작성에 사용한 도구 예시로 등장.
  • Gitar — Sonar가 인수했다고 소개한 AI 코드 리뷰 회사. PR 리뷰와 CI 워크플로 자동화에 사용.
  • SonarVortex — AI 코딩 에이전트의 내부 루프에서 컨텍스트 제공과 실시간 검증을 해주는 Sonar 제품.
  • 리미디에이션 에이전트(Remediation Agent) — 기존 기술부채(Tech Debt)나 백로그 이슈를 자동으로 고치는 에이전트.
  • 품질 게이트(Quality Gate) — 보안, 신뢰성, 유지보수성 기준을 통과하지 못하면 병합이나 배포를 막는 규칙.
  • 시프트 레프트(Shift Left) — 개발 후반이 아니라 코딩 초기에 보안과 품질 문제를 찾는 방식.
  • CVE(Common Vulnerabilities and Exposures) — 공개된 보안 취약점 식별 체계. 발표에서는 공개 당일 악용되는 위험을 언급.
  • 토큰 효율(Token Efficiency) — AI 모델 사용 시 불필요한 입력과 반복을 줄여 비용과 시간을 아끼는 것.
  • 감사 추적(Audit Trail) — 누가, 언제, 어떤 기준으로 검증했는지 남기는 기록.

# 섹션 요지
1 실험에서 엔지니어링으로 AI 코딩은 실험 단계를 넘어 반복 가능하고 안전한 엔지니어링 체계가 필요해졌다
2 AI 코딩의 생산성 착시 초기 생산성은 오르지만 품질 경고와 복잡도가 쌓이면 장기 생산성은 떨어진다
3 검증 부채 서비스 중요도가 높을수록 AI 코드와 필요한 품질 사이의 간극이 커진다
4 사람 리뷰의 한계 사람도 AI 조언을 과신하므로 코드 리뷰만으로는 충분하지 않다
5 제로 트러스트와 다층 검증 작성 방식과 다른 독립적 방법으로 여러 층의 검증을 해야 한다
6 ACDC 프레임워크 가이드, 검증, 해결을 반복하는 에이전트 중심 개발 사이클
7 Sonar 제품 흐름 SonarQube, Gitar, SonarVortex, 리미디에이션 에이전트가 내부 루프와 CI/CD 루프를 지원
8 최종 권고 단일하고 독립적인 검증 플랫폼을 조직 전체에 표준화해야 한다

1. 실험에서 엔지니어링으로 넘어가는 AI 코딩

화자는 올해 AI 개발 분야가 실험(Experimentation) 에서 엔지니어링(Engineering) 으로 넘어가는 전환점에 있다고 본다.

초기에는 AI로 “무엇이 가능한가”를 실험하는 분위기였다면, 이제는 실제 조직과 제품에서 반복 가능하고, 확장 가능하고, 일관적인 방식으로 AI를 소프트웨어 개발에 적용해야 하는 단계가 되었다는 뜻이다.

화자는 이를 과거 클라우드 컴퓨팅(Cloud Computing)이 IT 기술 접근성을 넓혔던 흐름과 비교한다. 클라우드가 작은 기업과 혁신가에게 인프라 접근성을 열어준 것처럼, AI도 앞으로 소프트웨어 개발 접근성을 크게 넓힐 수 있다고 본다.

다만 이를 위해서는 AI 코딩 시스템에 안전성(Safety) 과 신뢰(Trust) 를 넣어야 한다. 그렇지 않으면 중요한 서비스나 대규모 제품에는 적용하기 어렵다.

2. AI 코딩 생산성은 오래가지 않을 수 있다

화자는 Carnegie Mellon 연구를 소개한다. 연구진은 GitHub 프로젝트를 분석해 일반 도구로 작성된 프로젝트와 AI 도구로 작성된 프로젝트를 구분했다. AI 도구 예시는 Cursor였고, 코드 품질 분석에는 SonarQube가 사용되었다.

연구 결과는 단순히 “AI가 생산성을 올린다”가 아니었다.

초기에는 생산성이 올라갔지만, 그 효과는 약 3개월 정도 지속된 뒤 다시 떨어졌다. 반면 정적 분석 경고(Static Analysis Warnings)와 코드 복잡도(Code Complexity)는 3개월이 지나도 계속 높게 유지되었다.

즉 AI가 코드를 빠르게 만들 수는 있지만, 품질 문제와 복잡도가 쌓이면 개발자는 나중에 더 많은 시간을 검토, 수정, 리팩터링에 써야 한다.

차드식으로 이해하면, 물류센터에서 임시 인력을 많이 투입해 출고량은 잠깐 늘었지만, 잘못 포장된 주문과 반품이 계속 쌓여 결국 전체 운영 효율이 떨어지는 상황과 비슷하다.

3. 검증 부채는 서비스 중요도에 따라 커진다

화자는 AI 도구가 만든 코드의 기본 품질과 실제 애플리케이션에 필요한 품질 사이의 차이를 검증 부채(Verification Debt) 라고 설명한다.

개인 실험, 내부용 작은 도구, 단기간 쓰는 비핵심 앱이라면 이 차이가 작다. 약간의 품질 문제가 있어도 감당 가능하다.

하지만 다음과 같은 경우에는 필요한 품질 수준이 훨씬 높아진다.

  • 사용자 수가 많다.
  • 코드베이스가 크다.
  • 동시에 많은 변경이 일어난다.
  • 외부 사용자가 있고, 그중 일부는 악의적으로 시스템을 공격할 수 있다.
  • 장애가 나면 비즈니스 손실이 크다.

이때는 AI가 기본적으로 만들어주는 코드 품질만으로 부족하다. 결국 사람이 그 차이를 메워야 하고, 이것이 검증 부채가 된다.

4. 모델은 좋아지고 있지만 여전히 틀린다

화자는 최신 모델들이 뛰어나고 계속 발전하고 있다는 점은 인정한다. 하지만 모델 구조상 여전히 실수할 수밖에 없다고 말한다.

AI 코드의 문제 원인은 크게 세 가지다.

첫째, 모델은 오류를 낸다. 품질 문제, 보안 문제, 잘못된 구현이 프로덕션 코드로 들어가면 조직에 큰 피해를 줄 수 있다.

둘째, 모델은 맥락(Context)이 부족하다. AI는 사용자가 입력한 것만 안다. 2주 전 회의에서 나온 비즈니스 결정, 코드베이스 다른 영역의 관습, 조직 내부의 암묵적 기준까지 자동으로 알지는 못한다.

셋째, 모델마다 강점과 약점이 다르다. Sonar는 LLM 리더보드를 통해 주요 모델에 약 4,000개 코딩 과제를 주고, SonarQube 기준으로 정확성, 복잡도, 유지보수성, 신뢰성, 보안 등을 평가한다고 설명한다.

예를 들어 Claude Sonnet 4.6은 정확성과 신뢰성에서 강할 수 있지만, 보안이나 유지보수성, 낮은 복잡도가 더 중요한 작업에는 Claude Opus 4.6이 나을 수 있다고 말한다.

핵심은 어떤 모델도 완벽하지 않으므로 검증 루프가 반드시 필요하다는 것이다.

5. 사람 코드 리뷰도 흔들릴 수 있다

전통적으로 검증은 사람이 했다. 개발자가 직접 코드를 읽고, 리뷰하고, 문제가 없는지 판단했다.

하지만 화자는 사람 리뷰도 AI의 영향을 받아 흔들릴 수 있다고 말한다. Wharton 연구에 따르면 참가자들은 AI 조언이 맞을 때 92.7% 따랐고, 틀렸을 때도 거의 80% 따랐다.

이 현상은 코드 리뷰에서도 일어날 가능성이 크다.

AI 에이전트가 여러 개 동시에 코드를 만들고, PR(Pull Request) 양이 늘어나면 사람 리뷰어의 부담은 커진다. 시간이 부족하면 리뷰는 형식적인 승인, 즉 러버스탬핑(Rubber Stamping)이 되기 쉽다.

그래서 사람 리뷰 뒤에 자동 검증 도구가 안전장치로 있어야 한다.

6. 검증은 제로 트러스트와 다층 구조여야 한다

화자가 말하는 좋은 자동 검증은 두 가지 조건을 가져야 한다.

첫째, 제로 트러스트(Zero Trust) 다.

코드가 사람이 쓴 것인지, AI가 쓴 것인지, 어떤 모델이 쓴 것인지와 무관하게 같은 기준으로 검사해야 한다. 또한 코드를 작성한 AI와 같은 방식으로 검증하면 같은 blind spot을 가질 수 있으므로, 작성 방식과 다른 독립적 방법으로 검증해야 한다.

검증은 다음 조건을 가져야 한다.

  • 매번 같은 방식으로 실행된다.
  • 설명 가능하다.
  • 감사 가능하다.
  • 반복 가능하다.
  • 알고리즘 기반으로 일관된다.

둘째, 다층 검증(Multi-layered Verification) 이다.

한두 가지 방법만으로 모든 문제를 잡을 수 없다. 정적 분석, 데이터 흐름 분석, 제어 흐름 분석, 아키텍처 분석, LLM 기반 리뷰 등 여러 접근을 함께 사용해야 한다.

7. ACDC: 가이드, 검증, 해결

Sonar는 에이전트 중심 개발 사이클을 ACDC(Agent-Centric Development Cycle)라고 부른다.

ACDC는 세 단계로 구성된다.

  1. 가이드(Guidance)
  2. 에이전트가 코드를 쓰기 전에 필요한 맥락, 제약, 가드레일을 제공한다.

  3. 예: 아키텍처 규칙, 코딩 표준, 허용 의존성, 로깅 방식, 관찰성(Observability) 기준.

  4. 검증(Verification)

  5. 에이전트가 만든 코드가 품질, 보안, 규정 준수 기준을 만족하는지 검사한다.

  6. 화자는 이 단계가 지금 가장 빨리 도입할 수 있고, 가장 핵심적인 단계라고 본다.

  7. 해결(Solve)

  8. 검증에서 발견된 문제를 에이전트가 스스로 고치게 한다.
  9. 고친 뒤 다시 검증을 돌리는 루프를 반복한다.

핵심은 AI 에이전트에게 자유롭게 코드를 만들게 하되, 중앙의 검증 기준과 제약을 반드시 통과하게 만드는 것이다.

8. 내부 에이전트 루프와 외부 CI/CD 루프

화자는 ACDC가 두 곳에서 모두 돌아야 한다고 설명한다.

첫째는 내부 에이전트 루프(Inner Agentic Loop)다.

AI가 코드를 작성하는 중간에 SonarVortex 같은 도구가 필요한 컨텍스트를 제공하고, 실시간으로 검증을 실행한다. 문제가 발견되면 에이전트가 즉시 수정한다. 이렇게 하면 문제가 다음 루프로 전파되지 않는다.

둘째는 외부 CI/CD 루프(Outer CI/CD Loop)다.

PR이 올라오면 SonarQube와 Gitar 같은 도구가 전체 변경 사항을 자동 검토한다. 품질, 보안, 유지보수성 기준을 평가하고, 품질 게이트를 통과하지 못하면 프로덕션 배포를 막는다.

즉 AI 코딩 검증은 “코딩 중”에도 필요하고, “병합 및 배포 전”에도 필요하다.

9. Sonar 제품들이 맡는 역할

발표에서 소개된 제품들의 역할은 다음과 같다.

  • SonarQube
  • 정적 분석과 품질 게이트를 담당한다.

  • 문법, 데이터 흐름, 제어 흐름, 아키텍처, 보안, 유지보수성 등을 검사한다.

  • Gitar

  • AI 코드 리뷰와 CI 워크플로 자동화를 담당한다.

  • 기본적으로는 이슈를 찾아 사용자와 대화하지만, 신뢰가 쌓이면 수정, 승인, PR 병합까지 자동화할 수 있다고 설명한다.

  • SonarVortex

  • 에이전트 내부 루프에서 컨텍스트 제공과 실시간 검증을 담당한다.

  • Cursor, Claude Code, Codex, Antigravity 등 주요 AI 코딩 도구와 통합된다고 설명한다.

  • 리미디에이션 에이전트(Remediation Agent)

  • 오래된 이슈, 레거시 코드, 기술부채를 자동으로 줄이는 역할을 한다.
  • 사람 개발자는 신규 기능과 혁신 작업에 집중하고, 에이전트가 백그라운드에서 품질 개선을 수행하는 그림이다.

10. 차드에게 중요한 실무적 해석

비개발자 사장 입장에서 이 발표의 핵심은 “AI가 코드를 빨리 짜준다”보다 AI가 짠 코드를 어떻게 믿을 것인가다.

AI 코딩 도구를 도입하면 초기에는 속도가 빨라 보일 수 있다. 하지만 검증 체계 없이 운영하면 나중에 장애, 보안 취약점, 유지보수 비용, 외주 의존도 증가로 돌아올 수 있다.

따라서 AI 개발을 맡기거나 내부 자동화 도구를 만들 때는 다음을 확인해야 한다.

  • AI가 만든 코드에 자동 품질 검사가 붙어 있는가.
  • 보안 취약점 검사가 배포 전에 실행되는가.
  • 누가 어떤 기준으로 승인했는지 기록이 남는가.
  • 코드 리뷰가 사람의 감에만 의존하지 않는가.
  • 중요한 시스템일수록 더 엄격한 품질 게이트가 있는가.
  • AI에게 전체 자료를 무작정 넣지 않고 필요한 맥락만 주는가.

종합 체크리스트

  • [ ] AI 코딩 도구를 쓸 때 정적 분석(Static Analysis)을 함께 붙인다.
  • [ ] 코드 작성자와 무관하게 동일한 품질 기준을 적용한다.
  • [ ] PR 단계에서 품질 게이트(Quality Gate)를 설정한다.
  • [ ] 보안, 유지보수성, 신뢰성 기준을 숫자나 규칙으로 명문화한다.
  • [ ] AI 에이전트에게 필요한 컨텍스트와 제약을 먼저 제공한다.
  • [ ] AI가 만든 코드를 사람이 승인하더라도 자동 검증을 별도로 돌린다.
  • [ ] 내부 실험용 앱과 고객 대상 핵심 서비스의 검증 수준을 다르게 둔다.
  • [ ] 오래된 코드와 기술부채를 리미디에이션 대상으로 분리한다.
  • [ ] 조직 전체에서 여러 도구가 제각각 검증하지 않도록 표준 플랫폼을 정한다.
  • [ ] 감사 추적(Audit Trail)이 필요한 업무인지 확인한다.

하지만 그렇게 되려면 이 시스템에 안전성(Safety)과 신뢰(Trust)를 더해야 합니다. 그래야 다양한 사용 사례에서 더 넓게 활용하고, 새로운 것을 만들고, 더 큰 문제를 해결할 수 있습니다. 오늘은 그 방법에 대해 이야기하겠습니다.

어제 Tarek의 키노트를 들으신 분들은 이 데이터 일부를 보셨을 겁니다. 오늘은 조금 더 깊게 다뤄보겠습니다. Carnegie Mellon에서 한 연구가 있었습니다. 연구진은 GitHub에 올라온 프로젝트를 분석했고, 메타데이터를 사용해 전통적인 도구만 사용한 프로젝트와 AI 도구를 사용해 코드를 작성한 프로젝트를 구분했습니다. 이 경우에는 Cursor였지만, 어떤 AI 도구에도 해당할 수 있습니다.

결과는 흥미로웠습니다. 실제로 생산성이 일시적으로 상승했습니다. 하지만 그 효과는 약 3개월 정도 지속된 뒤 다시 내려갔습니다. 그 이유는 정적 분석 경고(Static Analysis Warnings)와 코드 복잡도(Code Complexity)가 지속적으로 증가했기 때문이라고 봅니다. 연구진은 이 데이터를 수집하는 데 SonarQube를 사용했고, 이런 문제들이 3개월 이후에도 계속 유지되는 것을 확인했습니다. 결국 이런 문제들이 개발자의 속도를 더 늦추게 됩니다.

이것이 AI 도구로 고품질 코드를 제공하기 어려운 이유입니다. 애플리케이션의 중요도(Criticality)에 따라 필요한 품질 수준이 다르기 때문입니다. 실험하거나, 혼자 가능성을 확인하거나, 내부용 비핵심 애플리케이션을 만드는 경우라면 사용자는 몇 명 안 될 수 있습니다. 본인 혼자일 수도 있고, 작은 팀일 수도 있으며, 오래 유지되지 않을 짧은 프로젝트일 수도 있습니다. 이런 경우 AI 도구가 제공하는 품질과 애플리케이션에 필요한 품질 사이의 간극은 작고, 그 차이를 감당할 수 있습니다.

하지만 중요도가 높아질수록 상황은 달라집니다. 많은 사용자를 지원하고, 코드베이스가 크고, 많은 줄의 코드와 변경이 계속 발생하는 상황이 됩니다. 사용자가 많고, 그중 일부는 악의적으로 소프트웨어를 깨뜨리려 할 수도 있습니다. 이런 경우 필요한 품질 수준은 AI 도구가 기본적으로 제공하는 품질보다 훨씬 높습니다.

여기서 검증 부채(Verification Debt)가 생깁니다. 사람, 즉 소프트웨어 엔지니어가 들어와 그 간극을 메우고, 코드를 프로덕션에 내보내기 전에 품질 수준을 받아들일 수 있는 수준까지 끌어올려야 합니다.

왜 이런 일이 생길까요? 왜 이 간극이 발생할까요? 우리는 모델들이 훌륭하다는 것을 압니다. 모델들은 계속 좋아지고 있습니다. [?Fable]이 나왔으니 앞으로 어떤 수준의 코드를 만들 수 있을지 저도 기대하고 있습니다. 하지만 이 기술과 모델의 구조상, 모델은 여전히 실수합니다. 품질 문제가 생길 수 있고, 오류에 취약합니다. 이런 오류가 프로덕션 코드로 들어가면 조직에 치명적인 영향을 줄 수 있습니다.

또한 모델에는 맥락(Context)이 부족합니다. 모델은 여러분이 알려준 것만 압니다. 코드베이스의 다른 곳에서 무슨 일이 일어나는지, 비즈니스에서 무슨 일이 일어나는지, 2주 전 누군가와 한 회의가 오늘 작성하는 코드에 어떤 영향을 주는지 알지 못합니다. 엔지니어인 여러분이 가진 모든 맥락을 모델이 갖고 있지는 않습니다. 그래서 모델은 여러분의 목표를 여러분만큼 잘 알지 못하고, 이것이 필요한 소프트웨어와 실제 구현 사이의 간극을 만들 수 있습니다.

모델들도 다양합니다. 두 모델이 완전히 같지는 않고, 품질 문제도 다르게 나타납니다. 저희는 이를 탐구하고 싶었습니다. 그래서 웹사이트에 LLM 리더보드(LLM Leaderboard)를 운영하고 있습니다. 주요 새 모델이 나오면 약 4,000개의 코딩 과제를 주고 평가합니다. SonarQube가 코드를 평가할 때 사용하는 모든 지표를 활용합니다. 정확성(Correctness), 복잡도(Complexity), 과제 해결률, 그리고 저희의 전통적인 지표인 유지보수성(Maintainability), 신뢰성(Reliability), 보안(Security)을 봅니다.

이런 모델들을 여러 축에 배치해 어디에서 잘하고, 어디에서 개선 여지가 있는지 보여줍니다. 화면에 보이는 것은 Claude Opus 4.6과 Claude Sonnet 4.6입니다. Claude 고객이라면 토큰 사용량을 조절하기 위해 이 두 모델을 오갈 수 있습니다. Claude Sonnet은 정확성, 과제 해결, 신뢰성 측면에서 꽤 좋습니다. 하지만 더 높은 유지보수성이나 보안 수준이 필요하거나, 코드 복잡도를 낮추고 싶다면 Opus를 사용하는 것이 도움이 될 수 있습니다.

저희는 여러 모델에 대해 이런 분석을 수행하고 있으며, 웹사이트에서 최신 분석을 확인할 수 있습니다. 곧 최신 Claude와 OpenAI 모델도 분석할 예정입니다.

이런 데이터는 유용합니다. 모델이 어디에서 강하고 어디에서 약한지 알려주기 때문입니다. 동시에 이런 모델을 사용할 때 계속 경계해야 한다는 사실도 분명히 보여줍니다. 어떤 모델도 완벽하지 않습니다. 여러분이 받은 코드가 실제로 배포하고 싶은 코드인지 확인하기 위해서는 항상 검증이 필요합니다.

전통적으로 그 검증은 사람이 할 수 있습니다. 자신의 눈으로 코드를 읽고, 자신의 판단으로 리뷰해 성공적인지 확인하는 방식입니다. 하지만 경험과 연구를 통해 우리는 사람 리뷰도 흔들릴 수 있다는 것을 알고 있습니다.

올해 초 Wharton에서 진행한 연구가 있습니다. 많은 참가자에게 과제를 주고, 그 과제를 수행할 때 AI 도구를 사용할 수 있게 했습니다. 그런데 참가자들은 몰랐지만, AI는 일부 상황에서 자신 있게 거짓말하도록 설정되어 있었습니다. 데이터에 따르면 참가자들은 AI가 맞는 조언을 했을 때 92.7%의 비율로 그 조언을 따랐습니다. 안타깝게도 AI가 틀렸을 때도 거의 80%의 비율로 조언을 따랐습니다.

이런 일은 코드 리뷰에서도 거의 확실히 일어나고 있을 것입니다. 특히 더 많은 코드가 작성되고, 여러 에이전트가 동시에 코드를 작성하며, 그 조각들을 하나의 소프트웨어 애플리케이션으로 합쳐야 할 때 그렇습니다. 부담이 너무 큽니다. 하루에 쓸 수 있는 시간은 한정되어 있고, 그래도 무언가는 배포해야 합니다. 그래서 조직 안팎에서 형식적인 승인(Rubber Stamping)이 많이 일어나고 있을 것입니다. 우리는 이를 자동 검증 도구로 보완해야 합니다.

그러면 무엇을 할 수 있을까요? 어제 Tarek도 이야기했듯, 많은 사람이 소프트웨어에 끌린 이유 중 하나는 코드가 제대로 작성되면 매번 같은 방식으로 실행된다는 점입니다. 함수를 올바르게 작성하면 항상 같은 방식으로 작동한다는 데서 오는 안정감이 있습니다. 잘 작동할 것을 아는 무언가를 만들 수 있다는 명확성과 자신감이 있습니다.

하지만 코드는 사람이 작성합니다. 사람에게는 요구사항이 있고, 그 요구사항과 외부 요인은 코드가 작동하는 방식에 영향을 줍니다. 애플리케이션에 코드가 점점 더 많이 추가되면 서로 예측 가능한 방식으로 상호작용할 수도 있지만, 사용자가 애플리케이션을 사용하면 예상하지 못한 행동을 할 수도 있습니다. 그래서 소프트웨어는 코드와 같은 방식으로 증명 가능하지 않습니다. 소프트웨어는 흥미롭고 새로운 방식으로 깨질 수 있습니다. AI로 더 많은 소프트웨어를 작성해 더 큰 문제를 해결할수록 이런 한계에 더 자주 부딪히게 됩니다.

따라서 자동 검증(Automatic Verification)을 이 과정의 일부로 넣는 것이 중요합니다. 실제로 작성되는 코드에 대한 통제 일부를 내려놓으면서 생기는 위험을 관리하는 데 도움이 됩니다. 저희는 검증이 앞으로 AI 기반 소프트웨어 개발로 놀라운 성과를 내기 위한 핵심 활성화 요소이자 병목 해소 요소가 될 것이라고 믿습니다.

검증이라고 할 때 무엇을 의미할까요? AI 코딩에서 성공적인 자동 검증에는 두 가지 핵심 요소가 있다고 봅니다. 첫째는 제로 트러스트(Zero Trust)여야 한다는 것입니다. 여기서 제로 트러스트란 코드가 어디서 왔든 상관없다는 뜻입니다. 사람이 썼을 수도 있고, AI가 썼을 수도 있습니다. 앞서 보았듯 서로 다른 AI는 서로 다른 방식으로 코드를 씁니다. 따라서 같은 AI로 그 코드를 검증하고 싶지는 않을 것입니다. 다양한 도구를 사용해야 다양한 문제를 잡을 수 있기 때문입니다.

코드가 어디서 왔든 같은 방식으로 작동하는 포괄적인 검증 체계가 필요합니다. 코드를 작성할 때 사용한 방법과 다른 방법으로 코드를 검토해야 합니다. 완전히 감사 가능하고, 설명 가능해야 하며, 검증이 매번 같은 방식으로 실행되었다는 것을 증명할 수 있어야 합니다. 알고리즘 기반이고, 반복 가능하고, 일관되어야 합니다.

둘째는 다층적(Multilayered)이어야 한다는 것입니다. 생성된 코드를 검토하는 데 여러 방식, 여러 기법, 여러 접근을 사용해야 합니다. 한두 가지 방법만으로 소프트웨어에서 발생할 수 있는 모든 문제를 찾을 수는 없습니다. 계산 기반 리뷰(Computational Review), LLM 기반 리뷰(LLM-driven Review), 그리고 그 사이의 여러 방식을 함께 사용해야 합니다.

이번 주에는 에이전트형 루프(Agentic Loops)에 대한 이야기를 많이 들었습니다. Tarek은 어제 저희의 에이전트형 루프 프레임워크를 소개했습니다. 저희는 이를 ACDC, 즉 에이전트 중심 개발 사이클(Agent-Centric Development Cycle)이라고 부릅니다. ACDC에는 세 단계가 있습니다.

가장 구현이 빠르고, 아마 많은 분이 이미 도입하고 있을 단계는 검증(Verification)입니다. 이 단계는 위쪽 중앙에 위치하며, 에이전트형 루프에서 작성된 코드를 쉽게 배포 가능한 수준으로 만들기 위한 가장 중요한 부분입니다. 다층적이어야 하고, 추론 기반(Reasoning-based)이어야 하며, 품질, 보안, 규정 준수 문제를 모두 가로질러야 합니다.

검증 전에 가이드(Guidance) 단계가 있습니다. 가이드는 에이전트가 처음부터 더 나은 코드를 작성할 수 있도록 가드레일, 맥락, 제약을 제공합니다.

검증 이후에는 발견된 문제를 해결해야 합니다. 이것이 해결(Solve) 단계입니다. 코드에서 발견된 문제를 수정(Remediation)할 수 있어야 합니다. 가능하다면 에이전트에게 필요한 도구 접근 권한을 제공해 스스로 문제를 찾고, 고치고, 다시 루프를 반복하게 해야 합니다. 검증을 중심에 둔 이런 에이전트형 루프가 AI 에이전트를 사용해 품질 있는 소프트웨어를 배포하는 방법입니다.

고객들과 이야기해보면, 모든 AI 코딩 프로세스에 검증을 도입하게 만드는 이유는 대체로 비슷합니다. 먼저 AI 코드가 일관되게 검증되기를 원합니다. 프로젝트나 팀마다 서로 다른 검증 방식이 적용되기를 원하지 않습니다. 어떤 도구를 사용하든 어디에나 적용되는 표준 규칙집을 원합니다.

또한 AI 도구를 효과적으로 사용하고 싶어 합니다. 여기에는 토큰 효율(Token Efficiency)이나 일반적인 효율도 포함되지만, 도구가 잘하도록 설계된 일에 올바르게 쓰이게 하는 것도 포함됩니다. 올바른 모델을 올바른 프로젝트에 사용하는 것도 중요합니다.

세 번째로, 보안 관점의 문제를 개발 사이클에서 가능한 한 초기에 잡고 싶어 합니다. 보안 문제를 왼쪽으로 이동시키는 시프트 레프트(Shift Left)는 수년간 중요했습니다. 이제 AI가 더 많은 코드를 작성하므로 보안 문제를 초기에 잡는 일은 더욱 중요해졌습니다. 요즘은 CVE가 발표되면 악의적 행위자들이 거의 같은 날 즉시 악용하는 경우가 많습니다. 이런 문제가 프로덕션으로 들어가지 않도록 코드를 최대한 견고하게 해야 합니다.

마지막으로 규정 준수(Compliance)를 유지해야 합니다. 규제 산업에서 일하는 분들도 많을 것입니다. 이런 상황에서는 검증이 전반에 걸쳐 지속적이고 일관되게 실행되었다는 것을 증명할 수 있어야 합니다. 이를 증명할 감사 추적(Audit Trail)을 유지하는 것이 매우 중요합니다. 저희는 이를 돕는 여러 솔루션을 갖고 있습니다.

SonarQube는 꽤 오래전부터 존재했습니다. 이 자리에도 이미 SonarQube 사용자가 많을 것입니다. SonarQube는 제로 트러스트, 다층 검증 플랫폼입니다. 문법 문제, 데이터 흐름 문제, 아키텍처 문제, 제어 흐름 문제를 다루며, 사실상 여러분이 사용할 대부분의 언어에서 작동합니다. 또한 에이전트가 SonarQube 검증에 직접 접근할 수 있도록 하는 깊은 연결 지점들을 제공해, 더 효과적으로 고품질 코드를 작성하게 합니다.

그리고 몇 주 전, 저희는 이곳 San Mateo에 기반을 둔 Gitar라는 회사를 인수했습니다. 이 회사는 AI 코드 리뷰를 합니다. 더 나아가 전체 CI 워크플로를 구축하고 자동화합니다. LLM 접근법으로 이슈를 찾는 것뿐 아니라, 그 이슈가 품질 문제를 일으킨다면 자동으로 차단할 수 있습니다. 수정안을 작성하고, 그 수정안을 승인하고, PR을 완전히 자동으로 병합할 수도 있습니다.

물론 그런 신뢰는 얻어야 합니다. 기본값으로 그렇게 작동하지는 않습니다. 보통 기본값은 이슈를 찾아 보여주고, 사용자와 대화하면서 이슈를 고치게 하는 방식입니다. 하지만 더 많이 사용하고 신뢰가 쌓이면 기능을 점점 더 켜서 Gitar로 PR 리뷰 워크플로를 완전히 자동화할 수 있습니다.

이번 주 초의 또 다른 큰 소식은 Tarek이 어제 언급했듯 SonarVortex라는 제품으로 새로운 에이전트형 루프 기능을 발표했다는 것입니다. SonarVortex는 에이전트 내부 루프에서 도구를 제공합니다. 에이전트가 더 나은 코드를 쓰도록 사전에 제약과 가드레일을 제공할 뿐 아니라, 코드를 작성하는 실시간에 검증을 실행해 생성 중인 문제를 찾고 고칠 수 있게 합니다. 또한 리미디에이션 에이전트(Remediation Agent)도 출시했습니다. 이 에이전트는 백로그 이슈를 처리하고, 인간 개발자만으로는 감당하기 어려운 규모의 기술부채를 줄일 수 있게 합니다.

기본적으로 기술부채나 오래된 이슈, 레거시 코드를 리미디에이션 에이전트에 지정하면, 여러분이 현재 진행 중인 혁신 작업에 집중하는 동안 백그라운드에서 코드베이스를 개선할 수 있습니다. 두 제품 모두 이번 주 기준으로 GA(General Availability)되었습니다.

어제 키노트에서 매우 상세한 차트가 소개되었는데, 이제 그 차트의 각 부분이 무엇을 의미하는지 설명하겠습니다. 이는 ACDC가 내부 에이전트 루프뿐 아니라 우리가 코드 개발에 사용하는 외부 CI/CD 루프에도 어떻게 적용되는지를 보여줍니다.

두 루프를 시작하기 전에, 작성하려는 소프트웨어로 실제 무엇을 달성하려는지 명세(Specifications)를 갖는 것이 매우 중요합니다. 여기에는 아키텍처 제약, 원하는 소프트웨어 아키텍처, 허용 가능한 코딩 표준과 코딩 패턴, 사용해도 되는 의존성과 사용하면 안 되는 의존성 목록, 조직에서 따르는 문법 표준, 로깅 관행, 관찰성(Observability)과 트레이싱(Tracing) 관행 등이 포함됩니다. 이 모든 것이 명세에 들어갑니다.

또한 품질 기준(Quality Criteria)을 정의해야 합니다. 저희는 기본으로 제공하는 품질 기준을 갖고 있고, 조직에 맞게 조정할 수 있습니다. 프로덕션으로 보내는 코드에서 받아들일 수 있는 보안, 품질, 유지보수성 수준이 무엇인지 정하고 인코딩해야 합니다. 그러면 LLM 코딩 에이전트를 사용해 코드를 작성할 준비가 됩니다.

에이전트에게 코딩 작업을 시작할 때, 저희가 먼저 도울 수 있는 일은 맥락과 제약을 제공하는 것입니다. 에이전트가 처음부터 해당 순간에 관련된 코드베이스와 가드레일을 이해하고 시작하도록 하는 것입니다. 에이전트의 컨텍스트 창(Context Window)을 관리해야 합니다. 전체 코드베이스를 처음부터 에이전트에게 던져서는 안 됩니다. 그러면 에이전트는 많은 시간을 헤매고, 탐색하고, 토큰을 태우게 됩니다. 저희는 주어진 작업에 필요한 맥락만 효율적으로 제공해 에이전트가 빠르게 생산적인 코드를 작성하도록 합니다.

그런 다음 에이전트는 소스 코드를 생성합니다. 그리고 저희는 에이전트에게 루프 내부 검증(In-loop Verification)을 제공합니다. 코드를 작성하는 중에 에이전트가 저희를 호출해, 작성 중인 코드에서 실시간으로 발견한 이슈 목록을 받을 수 있습니다. 좋은 점은 그 이슈를 에이전트가 즉시 고칠 수 있다는 것입니다. 그래서 그 문제가 이후의 에이전트 루프로 전파되지 않습니다. 이 기능은 이번 주부터 SonarVortex로 제공됩니다.

내부 루프가 모두 실행된 뒤에는, 코드가 공식 리뷰와 배포 프로세스에 들어가는 시점이 옵니다. 이것이 CI/CD 프로세스입니다. 익숙한 PR 흐름이 시작됩니다. Gitar는 이 흐름 안에서 작동할 수 있습니다. SonarQube도 이 흐름 안에서 PR의 모든 코드를 폭넓게 자동 리뷰하고, 품질, 보안, 유지보수성 이슈를 반환하는 자동 검증을 실행합니다. Gitar는 LLM 기반 초인적 리뷰(Superhuman Review)를 수행하고, SonarQube는 계산 기반 리뷰(Computational Review)를 수행해 세 가지 항목에 등급을 부여합니다. 기준을 통과하지 못하면 PR이 프로덕션으로 넘어가지 못하게 합니다.

문제가 발견되면 수정 에이전트(Fix Agent)를 사용해 발견된 모든 문제를 고칠 수 있습니다. 품질 게이트(Quality Gate)를 통과하면 테스트, 빌드, 배포로 진행할 수 있습니다. 검증은 내부 에이전트 루프와 외부 CI/CD 루프 양쪽에서 모두 실행되어야 합니다.

시간이 부족하니 이 영상 데모가 끝나기를 바라겠습니다. 이것은 내부 루프, 즉 에이전트형 루프의 데모입니다. 기본적으로 SonarVortex 데모입니다. 방금 보신 것은 작업을 부여한 장면입니다. 이 작업을 시작하면서 현재 Cursor가 실행 중이고, Cursor가 SonarVortex 컨텍스트 도구를 호출해 사전에 맥락을 가져왔습니다. 그래서 작업 중인 코드를 이해하고 어떻게 작성해야 하는지 알게 됩니다. 이제 코드를 작성하고 있으며, 초기 작성이 끝나면 검증 프로세스를 호출해 발견한 이슈 목록을 받게 됩니다. 이슈가 제공되면 내부 루프에서 즉시 고칩니다. 이 모든 것이 Cursor와의 직접 통합을 통해 자동으로 일어납니다. Claude Code, Codex, Antigravity, 그리고 주요 AI 코딩 도구 대부분과도 비슷한 통합을 갖고 있습니다.

요지는 이렇습니다. 이슈가 표시되면 즉시 수정하고, 다시 분석을 실행합니다. 그리고 검증 통과 점수를 받을 때까지 진행하지 않습니다.

시간이 없으니 이 부분은 넘기겠습니다. 이 발표에서 한 가지만 가져가신다면, 저희는 거버넌스와 검증 엔진(Governance and Verification Engine)이 AI 코딩 도구로 더 큰 성공을 얻고 더 큰 문제를 해결하는 데 매우 중요하다고 강하게 믿고 있다는 점입니다.

저희 데이터에 따르면 Sonar 고객과 사용자는 AI 코딩 도구에서 더 높은 성공 수준을 얻고 있습니다. 시간이 부족해 모두 설명하지는 않겠습니다. 아래층의 큰 빨간 부스에 들러주시면 자세히 이야기해드리겠습니다. 좋은 소식은 많은 분이 이미 이 중 일부에 접근할 수 있을 가능성이 높다는 것입니다. SonarQube는 오늘날 가장 널리 채택된 검증 도구 중 하나입니다. 전 세계 700만 명 이상의 개발자가 사용하고 있습니다.

그리고 저희 솔루션 전반에서 매일 약 7,500억 줄의 코드를 분석합니다.

이 방에 Gartner를 중요하게 생각하는 분이 있다면, 저희가 Gartner Magic Quadrant 리더라는 점도 참고할 만합니다.

마지막 슬라이드입니다. 핵심 요점을 정리하겠습니다.

첫째, AI 에이전트를 위한 제한된 자율성(Bounded Autonomy) 가이드라인을 세우십시오. 코드 생성의 자유는 주되, 중앙화된 검증과 제약 체계를 반드시 강제해야 합니다.

둘째, ACDC를 구현하십시오. 에이전트에게 맥락을 주고, 독립적인 지표로 올바른 작업을 하는지 검증하고, 에이전트가 자기 실수를 고칠 수 있게 하십시오.

셋째, 개발자들이 성공적으로 AI를 활용할 수 있도록 컨텍스트 프레임워크와 프로세스를 설계하는 데 필요한 오케스트레이션 도구(Orchestration Tools)를 갖추게 하십시오.

마지막으로, 모든 프로젝트, 모든 팀, 모든 개발자, 모든 AI 코딩 도구에서 일관되게 사용하는 단일하고 독립적이며 다층적인 검증 플랫폼을 표준화하십시오. 그래야 조직 내 도구 사일로 때문에 생기는 사각지대를 제거할 수 있습니다.

제 발표는 여기까지입니다. 더 알고 싶으시면 아래층의 큰 빨간 부스로 오시면 됩니다. 기꺼이 이야기 나누겠습니다. 감사합니다.
