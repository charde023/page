평가(Eval) 장애나 품질 문제를 자동 감지하는 AI 기반 평가층 트레이스 위에 붙는 사전 처리된 판단 데이터
개발자 역할 변화 직접 대응자에서 검토자·지휘자로 바뀐다 에이전트가 초안을 만들고 사람은 확신과 승인 담당

내가 모를 만한 것 / 처음 보는 것

  • 옵저버빌리티(Observability) — 시스템 내부 상태를 로그, 지표, 트레이스 등을 통해 파악하는 방식.
  • 텔레메트리(Telemetry) — 시스템이 실행 중에 내보내는 관측 데이터. 로그, 트레이스, 메트릭 등이 포함된다.
  • 트레이스(Trace) — 요청 하나가 시스템 안에서 어떤 서비스와 함수 경로를 지나갔는지 보여주는 기록.
  • 하네스(Harness) — Claude Code 같은 코딩 에이전트를 실행하고 도구·파일·프롬프트와 연결하는 실행 틀.
  • 스킬(Skill) — 에이전트가 특정 도구나 데이터 소스에 접근하고 사용할 수 있게 만든 기능 단위.
  • 샌드박스(Sandbox) — 실제 운영 환경을 망치지 않도록 격리된 실행 공간.
  • VPC(Virtual Private Cloud) — 기업 내부망처럼 격리된 클라우드 네트워크 환경.
  • 온라인 평가(Online Eval) — 운영 환경의 실제 트레이스 위에서 실시간 또는 주기적으로 실행되는 평가.
  • LM as a judge — 언어모델(Language Model)이 답변 품질, 안전성, 의도 일치 여부 등을 평가자로 판단하는 방식.
  • 콜드 스타트(Cold Start) — 사람이 문제를 처음 볼 때 아무 정보 없이 시작하는 상태. 여기서는 에이전트가 증거를 미리 모아둬 출발점을 만들어주는 것을 의미.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Arize의 첫 에이전트 버전은 “별로였다”고 표현했다 — 약 2년 전 경험에서 현재 Signal 설계가 나왔다.
  2. 미래의 옵저버빌리티는 Grafana UI를 클릭하는 방식보다 이벤트 기반·주기 기반 에이전트 루프에 가깝다고 봤다.
  3. 트리거(Trigger)는 주기적 실행과 이벤트 기반 실행 두 종류가 핵심이다 — 예: 5분마다 실행하거나 에러 발생 시 실행.
  4. 에이전트가 로그와 트레이스를 레포지토리(Repository)에 임시 파일로 내려받게 한다 — Claude Code 같은 하네스는 파일을 다룰 때 강력하기 때문이다.
  5. 어떤 경우에는 10MB 정도의 데이터 파일을 레포 안에 둔다고 언급했다 — 단순 API 연결보다 파일 기반 문맥 제공이 중요하다는 뜻.
  6. 트레이스와 로그를 지금보다 10배 더 남겨야 한다고 말했다 — 사람에게는 노이즈지만 에이전트에게는 실행 경로 증거가 된다.
  7. Alyx의 실제 버그 사례는 스트림 취소(Stream canceled) 이벤트였고, 수정은 한두 줄짜리였다고 한다.
  8. 큰 수정일수록 사람이 마지막까지 이끄는 경우가 많다 — 완전 자동 수정보다는 “조사와 초안 자동화”가 현재 현실적이다.
  9. Signal은 현재 AX SaaS 플랫폼에서 제공되며, VPC 배포도 가능하다고 설명했다.
  10. Uber, Booking 같은 대형 고객은 외부 Anthropic 연결을 꺼려 VPC 내부에 샌드박스를 설치하는 방식을 선호한다고 했다.
  11. Arize Sandbox 외에도 Daytona 같은 샌드박스 시스템을 쓸 수 있다고 언급했다.
  12. Pyroscope 스킬은 메모리 문제를 찾고, 고객별 코호트(Cohort) 분석도 할 수 있다고 했다.
  13. 평가(Eval)는 보통 이미 본 실패 패턴을 다시 잡기 위해 만든다 — 예: 프롬프트 인젝션(Prompt injection), 안전성 문제, 의도 불일치.

1. Arize와 Alyx: 실패한 v1에서 시작된 Signal

Jason Lopatecki는 자신을 Arize 창업자일 뿐 아니라 직접 많이 만드는 빌더라고 소개한다. Arize에는 Alyx라는 제품 내 에이전트가 있고, 이 에이전트를 실제로 만들고 운영하면서 많은 교훈을 얻었다고 한다.

중요한 점은 첫 번째 버전이 성공적이지 않았다는 것이다. 화자는 첫 버전을 “솔직히 별로였다”고 말한다. 약 2년 전의 경험이고, 그 실패를 통해 지금의 Signal이라는 다음 세대 시스템을 만들게 되었다.

Signal의 목표는 Arize 내부에서 매일 반복하던 운영·디버깅 작업을 자동화하고, 이를 고객도 쓸 수 있는 제품으로 만드는 것이다.

2. 옵저버빌리티는 사람용 대시보드에서 에이전트용 텔레메트리로 바뀐다

기존 옵저버빌리티(Observability)는 사람이 쓰는 도구였다. 사람이 UI를 클릭하고, 그래프를 보고, 로그를 검색하며 문제를 찾았다.

하지만 화자는 지금 옵저버빌리티가 크게 바뀌고 있다고 본다. 앞으로의 핵심 사용자는 사람만이 아니라 코딩 에이전트(Coding agent)다. 시스템이 내보내는 텔레메트리(Telemetry)는 에이전트가 문제를 이해하고 수정하는 데 필요한 “연기” 같은 단서다.

트레이스와 로그가 없으면 에이전트는 추측할 수밖에 없다. 코드에는 가능한 실행 경로가 너무 많기 때문이다. 반대로 충분한 트레이스가 있으면 에이전트는 실제 요청이 어떤 경로를 탔는지 알고, 더 정확히 원인을 좁힐 수 있다.

3. 목표는 스스로 고치는 시스템

화자의 궁극적 목표는 자율적으로 자신을 개선하는 시스템이다. AI를 시스템 안에 넣었다면, 그 AI가 스스로 오류를 찾고 더 나아지게 만들 수 있어야 한다는 관점이다.

현재는 완전 자동보다는 중간 단계에 있다. 사람은 여전히 수정안을 검토하고, 두 번째·세 번째 단계의 조사를 이끄는 경우가 많다. 하지만 이미 병목은 “수정 코드를 만들 수 있느냐”가 아니라 “이 수정이 맞다는 확신을 가질 수 있느냐”로 이동했다.

즉, 코딩 에이전트는 빠르게 수정안을 만들 수 있다. 문제는 그 수정이 운영에 배포해도 될 만큼 정확한지 판단하는 것이다.

4. 루프를 뒤집는다: 사람이 먼저 보지 않고 에이전트가 먼저 조사한다

기존 루프는 사람이 장애를 보고, 로그를 뒤지고, 티켓을 만들고, 에이전트나 도구를 사용해 수정하는 방식이었다.

화자가 말하는 새로운 루프는 반대다.

에러나 이벤트가 발생하면 에이전트가 먼저 운영 데이터를 본다. 트레이스, 로그, 관련 코드, 평가 결과를 모아 이슈를 만들고, 사람이 보기 전에 이미 증거를 정리해둔다.

사람은 아침에 일어나서 “무슨 일이 있었는지” 처음부터 파악하는 것이 아니라, 에이전트가 정리한 증거와 가능한 수정 방향을 보고 검토를 시작한다. 개발자 역할이 대응자(Responder)에서 검토자(Reviewer)로 이동하는 것이다.

5. 핵심은 트레이스와 로그를 파일로 레포에 가져오는 것

화자가 반복해서 강조하는 핵심은 데이터의 형태다.

Claude Code 같은 코딩 에이전트 하네스(Harness)는 파일을 다룰 때 강하다. 그래서 Arize의 스킬(Skill)은 운영 트레이스나 로그를 단순히 보여주는 것이 아니라, 레포지토리 안에 임시 파일 형태로 내려받게 한다.

이렇게 하면 에이전트는 다음을 한 공간에서 함께 볼 수 있다.

  • 실제 운영에서 발생한 트레이스
  • 로그
  • 코드 레포지토리
  • 관련 세션 정보
  • 평가 결과
  • 외부 시스템에서 가져온 진단 데이터

이 조합이 있어야 에이전트가 “어떤 코드가 어떤 운영 데이터와 연결되는지” 이해하고 수정안을 만들 수 있다.

6. 로컬 노트북에서 샌드박스로 이동

많은 개발자는 이미 로컬에서 Claude Code나 Cursor 같은 도구로 디버깅한다. 로그를 복사하고, 코드를 열고, 에이전트에게 물어보고, 수정안을 만든다.

화자는 이 경험이 샌드박스(Sandbox)로 이동할 것이라고 본다. 샌드박스는 이벤트나 주기적 트리거에 따라 자동으로 실행되는 격리 환경이다.

먼저 로컬에서 잘 작동하게 만들고, 그다음에는 옵저버빌리티 플랫폼의 이벤트를 기반으로 자동 실행한다. 예를 들어 5분마다 돌리거나, 특정 에러가 발생할 때마다 돌릴 수 있다.

7. 실제 사례: Alyx의 스트림 취소 버그

화자는 Arize의 제품 내 에이전트 Alyx에서 발생한 실제 사례를 소개한다.

Alyx는 제품 안에서 사용자 작업을 돕는 어시스턴트다. 이 사례에서는 스트림 취소(Stream canceled) 이벤트가 발생했고, Alyx가 할 일 목록을 갱신하는 과정에서 여러 번 호출하다가 에러가 났다.

Signal은 백그라운드에서 이 문제를 감지하고 관련 데이터를 모아 이슈를 만들었다. 이 경우 수정은 한두 줄짜리로 간단했다.

다만 화자는 모든 수정이 이렇게 간단하지는 않다고 말한다. 수정 범위가 커질수록 사람이 개입해 끝까지 이끄는 경우가 많다. 그래도 중요한 것은 사람이 완전히 빈손으로 시작하지 않는다는 점이다. 에이전트가 이미 조사와 증거 수집을 해둔다.

8. 왜 로그와 트레이스를 10배 더 남겨야 하는가

기존에는 로그를 너무 많이 남기면 사람이 보기 어렵기 때문에 노이즈로 여겨졌다. 하지만 에이전트에게는 다르다.

에이전트는 방대한 로그와 트레이스를 읽고 패턴을 찾을 수 있다. 따라서 시스템의 더 많은 부분을 관측 가능하게 만들수록, 에이전트는 실제 실행 경로를 더 잘 이해한다.

화자는 앞으로 지금보다 10배 더 많이 트레이싱하고, 10배 더 많이 로깅해야 한다고 주장한다. 사람 중심 운영에서는 과도했을 수 있는 데이터가, 에이전트 중심 운영에서는 자가 수정 루프의 연료가 된다.

9. 제품 관점: AX, Phoenix, Signal

Arize의 제품 라인은 다음처럼 설명된다.

제품 설명
AX Arize의 SaaS 플랫폼
Phoenix 오픈소스 제품. 바로 시작해볼 수 있는 도구
Signal AX 안에서 제공되는 에이전트 기능. 주기적으로 문제를 찾고 이슈를 만든다

Signal은 GitHub 레포와 연결해 이슈를 만들 수 있고, 특정 문제를 다시 잡기 위한 평가기(Evaluator)를 만들 수도 있다. 문제 사례를 데이터셋(Dataset)에 추가하는 것도 가능하다.

또한 Google Cloud나 다른 로깅 시스템을 위한 스킬을 붙일 수 있고, 사용자가 직접 스킬을 추가할 수도 있다.

10. 오픈 박스 접근: 하네스, 샌드박스, 프롬프트, 스킬을 직접 고른다

화자는 Signal을 블랙박스형 “SRE 에이전트”로만 포장하지 않는다. 오히려 사용자가 구성 요소를 고르는 오픈 박스(Open box) 접근을 강조한다.

사용자는 다음을 선택할 수 있다.

  • 어떤 하네스(Harness)를 쓸지: 예를 들어 Claude Code
  • 어떤 샌드박스(Sandbox)를 쓸지: Arize Sandbox, Cloud Managed Agents, Daytona 등
  • 어떤 프롬프트(Prompt)를 줄지: 예를 들어 보수적으로 조사하라, 보안 문제를 찾아라
  • 어떤 스킬(Skill)을 붙일지
  • 어떤 레포지토리와 연결할지

즉, Arize가 하려는 일은 로컬에서 하던 디버깅 경험을 주기적·이벤트 기반으로 자동 실행하는 시스템으로 옮기는 것이다.

11. VPC와 보안: 대기업은 외부 연결을 꺼린다

많은 고객은 운영 시스템이나 데이터베이스를 Anthropic 같은 외부 서비스에 직접 연결하고 싶어 하지 않는다. 특히 대기업은 운영 데이터와 내부 연결 정보가 외부로 나가는 것을 꺼린다.

그래서 Arize는 Uber, Booking 같은 기업의 VPC(Virtual Private Cloud) 안에 샌드박스를 설치해 연결하는 방식을 제공한다고 설명한다.

핵심은 AI 에이전트가 운영 데이터를 다루려면 보안·네트워크·데이터 거버넌스가 중요하다는 점이다. 단순히 “Claude Code에 데이터 연결하면 되지 않나?”로 끝나는 문제가 아니다.

12. Q&A: 그냥 Claude Code를 데이터에 연결하면 안 되나?

질문자는 Claude Code가 트레이스를 읽고 PR까지 만들면 되는 것 아니냐고 묻는다.

화자는 “그렇게 해야 한다”고 답한다. 다만 중요한 것은 단순 연결이 아니라 잘 설계된 스킬 표면적(Skill surface area) 이다.

좋은 스킬은 다음을 해야 한다.

  • 관련 세션이나 요청에 해당하는 트레이스 묶음을 찾는다.
  • 필요한 데이터를 적절한 파일 형식으로 레포에 가져온다.
  • Claude가 조합해 사용할 수 있도록 여러 기능을 구성 가능하게 만든다.
  • Pyroscope 같은 도구에서 메모리 문제를 찾는다.
  • 고객별 코호트(Cohort)로 문제를 분리해 볼 수 있다.

즉, Claude에게 데이터를 그냥 던지는 것이 아니라, Claude가 잘 사용할 수 있는 형태로 데이터를 찾아주고 정리해주는 계층이 필요하다.

13. Q&A: 평가는 어디에서 관여하는가?

평가(Eval)는 보통 운영 트레이스 위에 덧붙는 데이터다. Arize에서는 이를 온라인 평가(Online eval)라고 부른다.

예를 들어 실제 운영 트레이스마다 다음과 같은 평가 결과가 붙을 수 있다.

  • 답변이 안전한가
  • 사용자의 의도에 맞는가
  • 프롬프트 인젝션이 있었는가
  • 이전에 본 실패 패턴과 유사한가

Signal은 원시 트레이스와 로그뿐 아니라, 이 평가 결과도 함께 사용한다. 평가란 원시 데이터 위에 얹힌 사전 처리된 AI 판단 정보라고 볼 수 있다.

특히 LM as a judge 방식의 평가는 대규모로 실행 가능하다. 고객 중에는 전체 데이터셋에 언어모델 평가를 입히는 경우도 있다고 한다.

저는 Arize의 창업자이기도 하지만, 동시에 실제로 많은 것을 직접 만드는 빌더입니다. 제품 안에는 Alyx라는 에이전트가 있고, 저는 이런 에이전트 어시스턴트를 실제로 잘 작동하게 만들기 위해 많은 경험을 쌓았습니다.

솔직히 말하면 저희가 만든 첫 번째 에이전트 버전은 별로였습니다. 아마 2년 전쯤이었고, 저희가 이 분야에서 처음은 아니었습니다. 지금 만든 많은 것들은 그 에이전트를 직접 만들며 겪은 경험에서 나왔습니다.

Signal은 그다음 세대에 해당합니다. 우리가 매일 하던 여러 작업을 자동화하고, 사람들이 제품으로 사용할 수 있게 만들려는 시도입니다.

스타트업을 만들어본 분들은 이런 경험이 있을 겁니다. 밤늦게 플랫폼이 다운되고, 직접 고치러 가야 합니다. 그런데 그 일을 하려면 많은 에너지가 듭니다. 오늘은 저희가 만든 자동화와 앞으로의 모습을 이야기하겠습니다.

저는 옵저버빌리티(Observability) 분야의 미래가 지금 크게 바뀌고 있다고 믿습니다. 과거의 옵저버빌리티는 사람을 위한 것이었습니다. 클릭하는 UI, 클릭하는 그래프, 사람이 직접 보는 화면이 중심이었습니다.

하지만 지금은 코딩 에이전트(Coding agent)와 결합된 2.0 단계에 가깝습니다. Pyroscope, Google Cloud 같은 도구를 위한 스킬(Skill)을 만들면, 사람이 시스템을 디버깅할 때 도움을 받을 수 있습니다.

텔레메트리(Telemetry)는 시스템이 내뿜는 연기 같은 것입니다. 이 데이터가 있어야 에이전트가 수정할 수 있습니다. 어떤 코드 경로를 탔는지 알려주기 때문입니다. 그것이 없으면 추측해야 합니다. 가능한 경로는 너무 많습니다.

시스템이 내보내는 데이터는 에이전트가 소프트웨어를 디버깅하게 해줍니다. 평가(Eval)는 여기에 또 하나의 층을 더합니다.

결국 우리가 원하는 것은 자율적으로 스스로 고치는 시스템입니다. AI를 시스템에 넣었다면, 그 AI가 스스로 개선되게 만들고 싶습니다.

현재는 사람이 수정하고 검토하는 2.0 단계에 있습니다. 하지만 우리가 향하는 미래는 트레이스(Trace), 로그(Log)를 훨씬 더 많이 남기고, 에이전트가 계속 루프를 돌며 시스템을 개선하는 것입니다.

우리는 에이전트 속도로 만들 수는 있지만, 아직 시스템을 에이전트 속도로 개선하지는 못합니다. 병목은 더 이상 수정 자체가 아닙니다. 코딩 에이전트와 스킬을 써본 사람이라면 알겠지만, 병목은 “이 수정이 정말 맞는가”에 대한 확신입니다. 이 수정안을 배포해도 되는지가 문제입니다.

저희는 이 루프를 뒤집었습니다. 기존에는 사람이 먼저 보고 에이전트가 수정했습니다. 이제는 사람이 아침에 일어났을 때, 시스템에 쌓인 에러를 바탕으로 이미 정리된 이슈를 보게 됩니다.

에이전트가 직접 수정까지 하지 않더라도, 먼저 데이터를 보고 이슈를 올립니다. 사람이 보기 전에 이미 조사해두는 것입니다. 그 결과 사람은 티켓을 집어 드는 것에서, 충분한 증거가 앞에 놓인 상태로 시작하는 방식으로 이동합니다.

물론 지금도 사람의 검토나 사람이 두 번째·세 번째 단계를 이끄는 경우가 많습니다. 하지만 이것이 현재 저희가 보는 루프입니다.

이 루프는 어떤 이벤트(Event)에서 시작하거나, 주기적으로 실행됩니다. 그리고 그 주변 문맥(Context)은 스킬에 의해 모입니다.

옵저버빌리티 플랫폼과 연결되는 스킬의 마법은 문맥을 모을 수 있다는 점입니다. 에이전트는 문제를 해결하기 위해 무엇을 봐야 하는지 결정할 수 있습니다. 트리거(Trigger)는 주기적일 수도 있고 이벤트 기반일 수도 있습니다.

미래의 옵저버빌리티는 Grafana UI를 여기저기 클릭하는 것보다 이런 모습에 더 가까울 것입니다.

시작 증거로는 보통 트레이스가 좋고, 로그도 좋습니다. 요즘 AI 시스템은 에이전트 프레임워크의 중심에 트레이스가 있는 경우가 많습니다. 5분마다 주기적으로 볼 수도 있고, 에러 같은 이벤트 기반으로 볼 수도 있습니다.

보통은 문맥, 스킬, 로그, 레포지토리(Repository)가 함께 필요합니다. 레포는 코드 경로를 알려주고, 운영 로그나 트레이스는 실제 무슨 일이 있었는지 알려줍니다. 저희 스킬은 보통 작은 임시 파일을 레포 안에 내려받습니다. 그러면 에이전트는 실제 발생한 일과 코드를 함께 보고 수정안을 만들 수 있습니다.

핵심은 올바른 데이터와 파일 형식이 코드 레포 안에 함께 있는 것입니다. 그리고 에이전트가 조합해서 쓸 수 있는 스킬이 있어야 합니다.

많은 분들이 이미 로컬에서 이렇게 하고 있을 겁니다. 노트북에서 에이전트를 실행하고, 로컬에서 디버깅합니다. 이제 이 흐름은 노트북에서 샌드박스(Sandbox)로 이동하고 있습니다.

샌드박스는 이벤트나 주기적 이벤트에 따라 실행되는 환경입니다. 로컬에서 하던 것과 같은 일을 자동으로 합니다. 먼저 노트북에서 잘 작동하게 만들고, 그다음 옵저버빌리티 플랫폼 이벤트를 기반으로 실행하면 됩니다. 일정에 따라 실행할 수도 있고, 에러가 나올 때마다 실행할 수도 있습니다.

예를 하나 들겠습니다. 이것은 저희 에이전트 Alyx의 실제 사례입니다. Alyx는 제품 안에 있는 어시스턴트입니다. 여기서는 스트림 취소(Stream canceled) 이벤트가 있었습니다. 할 일 업데이트(To-do update)는 작업 목록을 관리하는 방식인데, 여러 번 호출하다가 에러가 났습니다.

저희에게 중요한 것은 이 문제를 디버깅하기 위한 데이터를 어떻게 자동으로 모으느냐입니다. Signal은 백그라운드에서 실행되며 이런 문제에 대한 이슈를 올립니다.

이 사례는 한두 줄짜리 수정으로 해결됐습니다. 이런 경우는 이상적입니다. 하지만 실제로는 더 큰 수정도 많고, 수정이 클수록 사람이 마지막까지 이끄는 경우가 많습니다. 그래도 중요한 것은 콜드 스타트(Cold start)를 줄이는 것입니다. 사람이 문제를 볼 때 이미 정보가 모여 있고, 나머지를 이어서 진행할 수 있습니다.

이 흐름에서 사람의 역할은 대응자(Responder)에서 검토자(Reviewer)로 이동합니다.

트레이스와 평가가 사라지는 것은 아닙니다. 오히려 루프의 핵심이 됩니다. 앞으로는 지금보다 10배 더 많이 트레이싱하고, 10배 더 많이 로깅하게 될 것입니다. 그래야 소프트웨어가 어떤 경로를 탔는지 알 수 있습니다.

예전에는 사람이 모든 로그를 뒤질 수 없기 때문에 그렇게 하지 않았습니다. 노이즈였기 때문입니다. 하지만 에이전트가 읽는다면 다릅니다. 지금보다 훨씬 더 많은 로그와 트레이스를 남기면, 에이전트가 실행 경로를 알고 스스로 수정하는 지속 루프를 만들 수 있습니다.

이것이 제가 보는 미래입니다.

Signal을 제품 관점에서 보여드리겠습니다. 이것은 금융 트레이딩 에이전트 예시입니다. 앞 발표를 보셨다면 금융 트레이딩 에이전트는 추천하지 않습니다. 아직 돈을 벌 가능성은 낮습니다. 어쨌든 이 예시는 사용자가 주식 거래에 대해 질문하고 답을 받는 시스템입니다. 실패할 수 있는 방식이 많습니다.

Arize에는 AX라는 SaaS 플랫폼이 있고, Phoenix라는 오픈소스 제품도 있습니다. Signal은 현재 AX SaaS 플랫폼에서 사용할 수 있고, VPC 배포도 가능합니다.

Signal은 주기적으로 실행되며 이슈를 찾아냅니다. GitHub 레포와 연결해 이슈를 만들 수 있고, 특정 문제를 다시 잡기 위한 평가기(Evaluator)를 만들 수 있습니다. 데이터셋(Dataset)에 추가할 수도 있고, 증거로 트레이스가 붙습니다.

Google Cloud나 다른 로깅 시스템을 위한 스킬도 있습니다. 저희는 이런 디버깅 스킬을 꽤 잘 만든다고 생각하지만, 사용자가 직접 스킬을 추가할 수도 있습니다.

예시에는 가드레일(Guardrail) 없이 실행되는 트레이스, 안전성 문제, 의도 문제 등이 있습니다. 이것이 블랙박스처럼 느껴질 수 있지만, 실제로는 오픈 박스(Open box)에 가깝습니다. 어떤 하네스(Harness)에서 실행할지 정할 수 있습니다. 여기서는 Claude Code를 사용합니다. 샌드박스와 샌드박스 시스템도 선택할 수 있습니다. Cloud Managed Agents를 쓸 수도 있고 Arize Sandbox를 쓸 수도 있습니다.

Arize Sandbox를 쓰는 이유는 많은 고객이 운영 시스템을 Anthropic에 직접 연결하고 싶어 하지 않기 때문입니다. 샌드박스가 데이터베이스를 디버깅하거나 연결해야 할 수 있습니다. 그래서 저희는 Uber, Booking 같은 큰 기업들의 VPC 안에 설치합니다. 이 기업들은 연결 정보를 외부로 보내고 싶어 하지 않지만, VPC 안에 설치하는 것은 편하게 받아들입니다.

Arize Sandbox를 쓰거나, Daytona 같은 다른 샌드박스를 쓸 수도 있습니다. 편한 것을 선택하면 됩니다.

플랫폼 관점에서는 실행 중인 여러 에이전트를 추적할 수 있습니다. Signal처럼 주기적으로 도는 에이전트도 있고, 다른 에이전트를 실행할 수도 있습니다. 실행 세션을 보고, 전사를 다운로드하고, Claude 세션을 로컬에서 이어받을 수도 있습니다.

사용자는 하네스, 샌드박스, 프롬프트, 스킬을 선택합니다. 예를 들어 “너무 공격적으로 수정하지 말라”거나 “보안 문제를 찾아라” 같은 프롬프트를 정할 수 있습니다. 사전 설정에서 여러 스킬을 추가하고, 직접 만든 스킬도 추가하고, 레포도 연결할 수 있습니다.

옵저버빌리티 플랫폼은 이제 단순히 신호를 보여주는 것이 아니라, 지속적인 수정 루프와 연결되고 있습니다. 로컬에서 하던 디버깅 경험과 실행 중인 평가를 연결해 수정안이나 최소한 좋은 출발점을 만들어야 합니다. 필요하면 로컬에서 이어받아 계속 디버깅할 수 있습니다.

이것이 Signal에서 PR까지 이어지는 흐름입니다.

질문: 그냥 Claude Code를 데이터에 연결해서 이 모든 일을 하게 하면 안 되나요? Claude Code가 트레이스를 읽고 PR을 올리면 되는 것 아닌가요?

답변: 맞습니다. 그렇게 해야 합니다. Arize에서도 실제로 많은 스킬을 갖추고 있습니다. 다만 잘 작동하게 하려면 스킬을 잘 설계해야 합니다. 데이터 영역에서 중요한 것은 올바른 데이터를 먼저 찾는 것입니다. 특정 세션과 관련된 트레이스 묶음을 찾고, 그 데이터를 파일 형식으로 레포 안에 가져와야 합니다. 이런 하네스는 파일을 다룰 때 매우 강력합니다.

어떤 경우에는 10MB짜리 파일이 레포 안에 놓이기도 합니다. 중요한 것은 이 데이터에 맞게 스킬을 아주 잘 설계하고, Claude가 조합해서 문제를 찾을 수 있는 충분한 스킬을 주는 것입니다.

예를 들어 저희는 Pyroscope 스킬로 메모리 문제를 찾을 수 있습니다. Pyroscope의 패싯(Facet)을 스킬이 사용할 줄 알고, 고객별 코호트(Cohort)로 나눠 특정 고객이 문제를 일으키는지도 볼 수 있습니다. 따라서 단순히 Claude에게 데이터를 가리키는 것이 아니라, Claude가 잘 사용할 수 있는 스킬 표면적을 설계해야 합니다.

질문: 평가(Eval)가 여러 번 언급됐는데, 운영에서 무언가 깨졌다는 Signal이 있을 때 평가는 어디에 들어가나요?

답변: 평가는 보통 운영 트레이스 위에 겹쳐 실행됩니다. 저희는 이것을 온라인 평가(Online eval)라고 부릅니다. 평가는 트레이스 자체에 붙는 데이터입니다. 에이전트는 트레이스에서 데이터를 가져오고, 스킬은 여러 트레이스에 걸친 평가의 집계값을 가져올 수 있습니다.

평가, 특히 LM as a judge는 AI 계층으로 볼 수 있습니다. 주기적으로 실행되며 시스템을 평가하고, 원시 데이터 위에 조금 더 사전 처리된 정보를 추가합니다. Signal은 실행될 때 원시 데이터뿐 아니라 그 위에 얹힌 평가 데이터도 사용합니다.

보통 평가는 이전에 본 실패를 다시 잡기 위해 만듭니다. 예를 들어 프롬프트 인젝션(Prompt injection)을 잡고 싶거나, 과거에 특정 방식으로 잘못 응답한 사례를 다시 잡고 싶을 수 있습니다. 흔히 발생하는 실패를 발견하면, 다음번에 잡기 위해 평가기를 만들 수 있습니다. 저는 이것을 항상 실행되는 AI 평가라고 봅니다.

LM as a judge는 큰 규모로 실행할 수 있습니다. 어떤 고객은 전체 데이터셋에 LM as a judge를 입히기도 합니다. Signal은 보통 많은 데이터 위에서 주기적으로 실행됩니다. 감사합니다.
