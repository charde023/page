  • Spec-Driven Development — 베메드(Bemedev?)·SpecHit·OpenSpec 같은 프레임워크. 실제 구현 전에 구조화된 요구사항을 먼저 만듦

  • AI Slop 패턴 — AI가 자주 뽑아내는 뻔하고 밋밋한 결과물. 감점 기준으로 넣어야 할 만큼 실제 문제
  • Playwright MCP — Evaluator 에이전트가 직접 브라우저 앱을 탐색·스크린샷·사용자처럼 테스트하도록 연결하는 MCP 도구 Harness-하네스
  • Stripe Minions — 코드 변경마다 300만 테스트 중 일부를 골라 검증하는 배포 파이프라인 하드코딩 검증 개념 (Evaluator 에이전트와 구분)
  • DAW — Digital Audio Workstation (디지털 오디오 워크스테이션). 브라우저 안에서 Web Audio API로 구현 가능

  1. Claude Sonnet 4.5는 컨텍스트 불안을 보였고, Opus 4는 크게 문제 없었다 — Opus 4.6으로 넘어가면서 컨텍스트 리셋 자체가 불필요해졌다

  4. Evaluator는 피상적 테스트·엣지 케이스 누락 경향이 있어 여러 차례 반복 조정 필요 — 플러그앤플레이 아님
  5. 평가 지표 4가지: 디자인 품질, 독창성(AI Slop 회피), 기술적 완성도(Craft), 기능성 — 이 중 독창성·슬랍 방지 가중치를 높임
  6. Planner 에이전트는 Opus 3([?원문] "오퍼스 3D") → Sonnet 4.5를 썼다고 언급
  7. 2D 게임 메이커 실험: 솔로 하네스는 겉보기만 괜찮고 실제 플레이 불가, 풀 하네스(Planner+Generator+Evaluator)는 실제 동작
  8. DAW 실험 비용 상세: Planner 5분 50초 / 첫 빌드 2시간 71달러 / QA 에이전트 10분 / 2차 빌드 1시간 / 3차 빌드 10분 → 총 약 4시간, 125달러
  9. Claude Agent SDK에는 컨텍스트 컴팩션이 내장됨 — 직접 구현도 가능하며 SDK 강제 사항은 아님
  10. Opus 4.6의 100만 토큰 컨텍스트 창 마케팅에 대해 화자는 회의적: "토큰 처리할수록 돈을 더 받으니까" — 컨텍스트 리셋 설계가 완전히 끝났다고 보지 않음

# 섹션 요지
1 하네스란 무엇인가 모델(엔진)을 신뢰할 수 있는 시스템으로 바꾸는 외부 구조 — 프롬프트·도구·피드백루프·검증 포함
2 장기 실행 에이전트의 근본 문제 컨텍스트 소진·조기 완료 선언·목표 축소 — 하네스 없으면 반복 발생
3 두 가지 실패 패턴 컨텍스트 불안 / 자기평가 편향
4 초기 해법: 초기화+코딩 에이전트 분리 기능 단위 분할, 진행 파일, 컨텍스트 리셋
5 적대적 평가 구조 GAN 발상 — Generator vs. Evaluator 긴장이 품질 상승 유도
6 Evaluator 작동 조건 3가지 점수화 기준 / 가중치 조정 / Playwright MCP로 실제 상호작용
7 실험 1 — 네덜란드 미술관 웹사이트 피드백 10회 반복 → 단일 패스로 불가능한 창의적 도약
8 실험 2 — 2D 게임 메이커 솔로(값싸고 빠름, 작동 불가) vs 풀 하네스(느리고 비쌈, 실제 동작)
9 Opus 4.6 이후 단순화 스프린트·계약협상·컨텍스트 리셋 제거 → 컨텍스트 컴팩션 + 빌드 후 Evaluator
10 실험 3 — 브라우저 DAW 4시간 125달러, 핵심 기능 포함, 전문 DAW 수준은 아님
11 하네스 에볼루션 개념 모델 능력이 올라가면 낡은 하네스 가정을 제거 — 설계는 지속 반복

1. 하네스란 무엇인가

하네스(Harness)는 AI 모델이 길을 잃지 않게 감싸는 소프트웨어 구조다. 모델이 엔진이면, 하네스는 그 엔진을 원하는 방향으로 달리게 하는 자동차 전체다. 더 정확한 비유는 말(야생마=모델)과 마구(하네스) — 하네스가 힘을 통제하고 방향을 잡아준다.

구성 요소: 프롬프트, 도구, 피드백 루프, 제약 조건, 검증. 즉 모델을 신뢰할 수 있는 시스템으로 바꾸는 주변의 모든 요소.

핵심 통찰: 복잡하고 오래 걸리는 작업에서는 하네스 설계가 모델 자체만큼 중요하다.

2. 장기 실행 에이전트의 근본 문제

AI 에이전트에게 복잡한 목표를 주고 몇 시간~며칠 동안 스스로 일하게 만들려면 어떻게 해야 하는가. 하네스 없이 방치하면:

  • 앱 전체를 한 번에 만들려다 컨텍스트 소진
  • 빨리 끝내려고 일이 끝났다고 선언
  • 기능 범위를 지나치게 작게 잡음

3. 두 가지 대표 실패 패턴

3-1. 컨텍스트 불안 (Context Anxiety)

컨텍스트 창이 차오르면 단순히 일관성만 잃는 게 아니라 행동 자체가 바뀐다: - 대화를 너무 일찍 마무리 - 단계를 대충 넘김 - 끝나지 않은 일을 끝났다고 선언

컨텍스트 컴팩션을 써도 Sonnet 4.5는 이 증상을 보였다. Opus 4.6에서는 컨텍스트 리셋 없이 컴팩션만으로도 충분했다.

3-2. 자기평가 편향 (Poor Self-Evaluation)

에이전트에게 자기 일을 평가하라고 하면 자기 편을 든다. 인간이 보기에 밋밋한 결과물도 스스로는 높게 평가한다. Anthropic이 솔직하게 인정한 부분 — 클로드가 프론트엔드 디자인에서 밋밋한 결과를 자주 냈다.

4. 초기 해법 — 에이전트 분리 + 컨텍스트 리셋

Anthropic의 초기 2단계 시스템: 1. 초기화 에이전트: 환경 세팅, 기능 단위 분할, 진행 파일 생성 2. 코딩 에이전트: 기능 하나씩 구현, 각 덩어리마다 git 커밋, 구조화된 핸드오프 작성

→ 다음 에이전트가 새 컨텍스트로 이어받는 컨텍스트 리셋 구조.

Geoffrey Huntley의 Lef Wigdham Loop: 에이전트를 루프 안에서 돌리며 린터·타입체크 같은 객관 검증으로 종료 조건 판단. Spec-Driven Development(SpecHit, OpenSpec 등 프레임워크)와 결합하면 더 강력.

5. 적대적 평가 구조

GAN에서 영감. Generator는 코드·콘텐츠를 만들고, Evaluator 에이전트가 그 결과를 의심하며 점수 매겨 피드백을 돌려준다.

단일 에이전트에게 "더 회의적으로 평가하라"고 시키는 것보다, 전용 Evaluator를 별도로 두는 것이 훨씬 효과적이었다. Evaluator가 피드백을 주면 Generator는 무엇을 고칠지 명확해진다.

차이점: 일회성 평가 도구가 아니라 실제 프로덕션 루프 안에 묶여있다.

6. Evaluator를 제대로 작동시키는 세 가지 조건

  1. 주관적 품질의 점수화: "예쁜가?" 대신 "우리 디자인 원칙을 따르는가?" 로 기준 먼저 정의. 평가 지표: 디자인 품질 / AI Slop 회피(독창성) / 기술적 완성도(Craft) / 기능성
  2. 가중치 조정: 4가지 기준이 동등하지 않음. 실험 끝에 AI Slop 방지 가중치를 높임
  3. 실제 상호작용: Playwright MCP로 Evaluator가 직접 앱을 탐색·스크린샷·사용자처럼 테스트

7. 실험 1 — 프론트엔드 디자인 (네덜란드 미술관)

구조: 한 문장 프롬프트 → Generator(HTML/CSS/JS 생성) → Evaluator(Playwright MCP) → 피드백 5~15회 반복

결과: 초반 결과물에서 피드백 10회 이후, 체크무늬 바닥의 3D 공간 같은 완전히 독특한 결과물. "단일 패스 생성에서는 보기 어려운 창의적 도약."

8. 실험 2 — 2D 레트로 게임 메이커 (풀스택)

프롬프트: 레벨 에디터, 스프라이트 에디터, 엔트 동작, 플레이테스트 모드 포함 2D 레트로 게임 메이커 제작.

구분 솔로 하네스 풀 하네스 (Planner+Generator+Evaluator)
비용·시간 값싸고 빠름 비싸고 오래 걸림
결과물 겉보기 괜찮음, 실제 플레이 불가 실제 동작함

스프린트별 과정: Planner가 명세 확장 → Generator·Evaluator가 Definition of Done 선협상 → 구현 → Evaluator 평가 → 컨텍스트 리셋 + 핸드오프

9. Opus 4.6 이후 — 하네스 단순화

Opus 4.6 출시 후 제거한 것들: - ~~스프린트 구조~~ - ~~계약 협상 (Definition of Done 선협상)~~ - ~~컨텍스트 리셋~~

남긴 것: - 컨텍스트 컴팩션 (Claude Agent SDK 내장) - Planner(명세 확장) → Generator(전체 앱, 긴 단일 세션) → 빌드 완료 후 Evaluator → 재개선

10. 실험 3 — 브라우저 DAW (Digital Audio Workstation)

Web Audio API로 브라우저에서 동작하는 풀기능 DAW 제작.

단계 소요 시간 비용
Planner 5분 50초 -
1차 전체 빌드 2시간 71달러
QA Evaluator 10분 -
2차 빌드 1시간 -
3차 빌드 10분 -
합계 약 4시간 약 125달러

결과: 전문 음악 제작 프로그램 수준은 아니지만, 100달러 선에서 핵심 기능이 동작하는 DAW.

11. 하네스 에볼루션 개념

"하네스의 각 구성요소는 모델이 그 일을 스스로 못할 거라는 가정을 코드로 박아 넣은 것이다. 모델이 좋아지면 이 가정도 낡아버린다."

  • Sonnet 4.5 → 컨텍스트 리셋 필요
  • Opus 4.6 → 컨텍스트 컴팩션만으로 충분, 구조 단순화
  • Evaluator의 효용도 모델 능력에 달림 — 모델이 잘 못하는 영역일수록 Evaluator가 필수, 잘하는 영역이면 불필요할 수도

하네스 설계는 한 번 세팅하고 끝나는 문제가 아니다. 계속 다듬고 반복해야 한다.

전체 전사 펼치기

어제 Anthropic이 장시간 실행되는 에이전트용 하네스 설계에 대한 흥미로운 글을 공개했습니다. 그 안에는 특화된 에이전트 시스템을 만들 때 모두에게 도움이 될 만한 인사이트와 솔직한 고백이 담겨 있습니다. 이들은 6시간 동안 자율 코딩을 돌려 2D 레트로 게임 엔진을 만든 과정을 보여줬습니다. 또 4시간 동안 브라우저에서 돌아가는 디지털 오디오 워크스테이션(DAW)도 만들었습니다.

이런 장시간 자율 에이전트 사례는 코딩에 초점이 맞춰져 있지만, 원리는 컴플라이언스 감사·리스크 분석·콘텐츠 파이프라인·영향 평가 같은 특화 에이전트 시스템 전반에 적용됩니다.

지난주 이 채널에서는 특화 에이전트 하네스를 커스텀 Python·React 앱에 넣는 영상을 올렸습니다. 그런 커스텀 하네스도 Anthropic 글에서 나온 인사이트를 적용하면 더 좋아질 수 있습니다.

하네스(Harness) 가 아직 감이 안 잡히신다면, 쉽게 말해 AI 모델이 길을 잃지 않게 감싸는 소프트웨어 구조입니다. 모델이 엔진이고, 하네스가 자동차 전체인 셈입니다. 더 좋은 비유는 말과 마구(하네스) — 야생마는 힘이 세지만 마음대로 움직이고, 하네스가 그 힘을 통제해 원하는 방향으로 이끕니다. 구성 요소: 프롬프트, 도구, 피드백 루프, 제약 조건, 검증.

이 글의 핵심 인사이트 중 하나: 오래 걸리고 복잡한 작업에서는 하네스 설계가 모델 자체만큼 중요하다.

이번 글은 지난해 11월에 나온 "장시간 실행 에이전트용 효과적인 하네스" 글의 연장선이며, 업계 전체가 풀려고 하는 근본 문제를 다룹니다. AI 에이전트에게 복잡한 목표를 주고 몇 시간~며칠 동안 스스로 일하게 만드는 방법입니다. 개발 관점에서는 큰 기능이나 앱 하나를 통째로 만드는 일, 다른 업계에서는 한 달짜리 컴플라이언스 감사를 대신하는 일일 수 있습니다.

하네스 없으면: 앱 전체를 한 번에 만들려다 컨텍스트 소진, 빨리 끝내려고 완료 선언.

Anthropic의 초기 해법은 두 부분짜리 시스템이었습니다. 초기화 에이전트가 환경을 세팅하고 기능 단위로 분할한 뒤 진행 파일을 만들고, 코딩 에이전트가 기능 하나씩 구현하며 각 덩어리마다 git 커밋, 다음 에이전트를 위한 구조화된 핸드오프를 남기는 방식입니다.

Anthropic이 이 아이디어를 처음 생각해낸 건 아닙니다. Geoffrey Huntley는 몇 달 앞서 Lef Wigdham Loop 아이디어를 내놨습니다. 에이전트를 루프 안에서 돌리며 린터·타입체크 같이 거짓말 못하는 검증으로 종료 조건을 판단하는 방식입니다. 여기에 Spec-Driven Development(SpecHit, OpenSpec 같은 프레임워크)를 묶으면 더 강력해집니다 — 실제 개발 전에 구조화된 요구사항을 먼저 만들어 에이전트가 미리 정한 기준을 따라 움직이게 됩니다. 다만 외부 객관 검증이 반드시 필요하고, 자기 일을 평가하는 것도 에이전트 자신이라는 한계가 있습니다.

이런 배경에서 Anthropic은 하네스와 Lef Wigdham Loop를 써도 두 가지 공통 실패 패턴을 발견했습니다.

첫 번째 — 컨텍스트 불안(Context Anxiety): 컨텍스트 창이 차오르면 모델의 태도가 달라집니다. 단순히 일관성을 잃는 게 아니라 행동 자체가 바뀝니다 — 대화를 너무 일찍 마무리, 단계 생략, 끝나지 않은 일을 끝났다고 선언. 직접 긴 대화 스레드를 써봤다면 느껴보셨을 겁니다 — 시간이 갈수록 답이 짧아집니다.

컨텍스트 컴팩션(대화 스레드를 요약해 활용 가능한 컨텍스트 공간을 늘리는 기법)을 써도 Sonnet 4.5는 여전히 컨텍스트 불안을 보였다고 Anthropic은 말합니다. 깨끗한 새 출발이 아니라 빨리 끝내려는 경향이 있었습니다. 그래서 11월 원래 해법이 컨텍스트 리셋이었습니다 — 새 컨텍스트 창에서 시작해 진행 파일에서 최신 기능을 읽고, 이미 만든 기능을 테스트한 뒤 현재 작업을 구현하고, 완료 후 구조화된 핸드오프를 남기는 방식.

반면 Opus 4는 이 문제가 그 정도로 크지 않았습니다. 이번 글에서는 Opus 4.6으로 넘어가면서 컨텍스트 리셋이 아예 필요 없었다고 합니다 — 컨텍스트 컴팩션만으로도 충분했고, 조기 포기 증상도 보이지 않았다고.

Anthropic이 Opus 4.6의 100만 토큰 컨텍스트 창 성능을 강하게 주장하지만, 저는 냉정하게 볼 필요가 있다고 생각합니다 — 토큰을 처리할수록 돈을 더 받으니까요. 그래서 저는 컨텍스트 리셋 설계가 완전히 끝났다고 보진 않습니다.

두 번째 — 자기평가 편향: 에이전트에게 자기 일을 평가하라고 하면 대체로 자기 편을 듭니다. Anthropic이 예전에는 잘 하지 않던 솔직한 고백입니다. 클로드가 프론트엔드 디자인에서 밋밋한 결과물을 자주 냈다고 합니다. 그래서 이 시스템 안에서 흔한 AI Slop 패턴에는 감점을 줬습니다.

자기평가는 주관적 작업과 객관적 작업에서 접근이 다릅니다. 코딩이 AI 에이전트에서 가장 먼저 성장한 이유가 있습니다 — 린터·타입체커·회귀 테스트·브라우저 테스트처럼 검증 가능한 출력이 있어서 AI가 자기 결과를 스스로 반복 개선할 수 있기 때문입니다. 원래 주관적이던 품질을 점수화하면 AI도 더 객관적으로 평가할 수 있습니다.

적대적 평가(Adversarial Evaluation): GAN에서 영감 — Generator 에이전트와 Evaluator 에이전트가 맞붙는 구조. Generator는 코드·콘텐츠를 만들고, Evaluator가 결과를 평가하며 가능하면 객관 기준으로 점수 매겨 피드백을 돌려줍니다. 단일 에이전트에게 더 회의적으로 평가하라고 만드는 것보다, 전용 Evaluator를 두는 것이 훨씬 효과적이었습니다. Evaluator가 피드백을 주면 Generator는 무엇을 고쳐야 할지 명확해집니다.

이 아이디어 자체는 새롭지 않습니다 — 멀티 에이전트 시스템은 여러 해 전부터 있었고, Evaluator 에이전트 개념도 LLM as a Judge와 크게 다르지 않습니다. 다른 점은 일회성 평가 도구가 아니라 실제 프로덕션 루프 안에 묶여 있다는 점입니다.

기본 상태의 클로드는 QA 에이전트로 성능이 좋지 않았습니다 — 초반 실행에서 실제 문제를 찾고도 큰 문제 아님으로 그냥 통과, 피상적 테스트로 엣지 케이스를 놓쳤습니다. 여러 차례 반복과 개선이 필요했고, 플러그앤플레이가 아니었습니다.

Evaluator 작동 조건 3가지: 1. 주관적 품질 점수화 — "예쁜가?" 대신 "우리 디자인 원칙을 따르는가?"로 기준 정의. 지표: 디자인 품질, AI Slop 회피(독창성), 기술적 완성도(Craft), 기능성 2. 가중치 조정 — 4가지 기준이 동등하지 않았음. 반복 실험 끝에 AI Slop 방지 가중치를 높임 3. 실제 상호작용 — Playwright MCP를 붙여 Evaluator가 직접 앱을 탐색·스크린샷·테스트

(더 결정론적인 테스트도 필요합니다 — Stripe Minions처럼 배포 시스템에 하드코딩된 검증은 별개입니다.)

실험 1 — 네덜란드 미술관 웹사이트 (프론트엔드 디자인): 한 문장 프롬프트 → Generator(HTML/CSS/JS) → Evaluator(Playwright MCP) → 피드백 5~15회. 결과: 체크무늬 바닥의 3D 공간 같은 완전히 독특한 결과물 — "단일 패스로는 보기 어려운 창의적 도약."

실험 2 — 2D 레트로 게임 메이커 (풀스택): 레벨 에디터, 스프라이트 에디터, 엔티티 동작, 플레이테스트 모드 포함. 솔로 하네스(값싸고 빠름) vs 풀 하네스(Planner+Generator+Evaluator). 솔로 결과: 겉보기는 괜찮으나 실제 플레이 불가. 풀 하네스 결과: 실제 동작. Planner는 Opus 3([?원본]) → Sonnet 4.5 사용. 스프린트별 Definition of Done 선협상 — Generator가 목표를 슬금슬금 바꾸지 못하게 했습니다. 이 실험 도중 Opus 4.6이 출시됐습니다.

Opus 4.6 이후 단순화: 스프린트·계약 협상·컨텍스트 리셋 제거. 한 문장 프롬프트 → Planner가 명세 확장 → Generator가 전체 앱을 한 번의 긴 세션으로 제작 (컨텍스트 컴팩션 내장) → 빌드 완료 후 Evaluator → 재개선. Anthropic이 Opus 4.6 성능을 꽤 과감하게 과시하는 면도 있습니다 — 100만 토큰 창에서 하네스 없이 앱 전체를 만들 수 있다는 이야기니까요.

실험 3 — 브라우저 DAW: Web Audio API 기반 브라우저 내 DAW. Planner 5분 50초, 1차 빌드 2시간 71달러, QA 에이전트 10분, 2차 빌드 1시간, 3차 빌드 10분. 합계: 약 4시간, 125달러. 전문 음악 제작 프로그램 수준은 아니지만, 100달러 선에서 핵심 기능이 동작. 모두 컨텍스트 컴팩션이 내장된 Claude Agent SDK 위에서 동작. SDK를 써야만 하는 건 아니고, 직접 구현도 가능합니다.

하네스 에볼루션: 하네스의 각 구성요소는 모델이 그 일을 스스로 못할 거라는 가정을 코드로 박아 넣은 것입니다. Sonnet 4.5에는 컨텍스트 불안이 있었으니 컨텍스트 리셋 구조가 필요했습니다. 모델이 좋아지면 이런 가정도 낡아버립니다 — Opus 4.6에서 직접 확인했습니다. Evaluator의 성능도 모델 자체가 얼마나 좋은지에 달려있습니다. 모델이 못하는 영역이라면 Evaluator 필수, 잘하는 영역이라면 불필요할 수도. 결국 하네스와 컨텍스트 엔지니어링은 한 번 세팅하고 끝나는 문제가 아닙니다 — 계속 다듬고 반복해야 합니다.
