내가 모를 만한 것 / 처음 보는 것

  • GStack — github.com/garrytan/gstack. Claude Code용 스킬 묶음 오픈소스 저장소. Ruby on Rails보다 GitHub Stars가 더 많다고 언급
  • Conductor — conductor.build. GStack 스킬을 GUI로 실행하는 도구. 새 워크트리 생성도 지원
  • Office Hours 스킬 — YC 166명 파트너의 노하우를 압축한 스킬. "이걸 정말 원한다는 가장 강한 증거가 뭔가?" 같은 질문을 자동으로 던짐
  • Design Shotgun — AI가 여러 UI 버전을 동시에 생성하는 비주얼 브레인스토밍 도구. Codex + 이미지 생성 연동
  • Adversarial Review — 디자인 문서를 여러 단계에 걸쳐 AI가 스스로 반박하고 수정하는 프로세스. Plan Score 개념 포함
  • Worktree (Git) — Conductor에서 + 클릭으로 새 Git Worktree 생성, 각 이슈/기능을 독립 환경에서 병렬 처리
  • Supply Chain Attack (공급망 공격) — 오픈소스 PR에 악성 코드가 들어오는 위협. GStack이 리뷰 자동화로 방어한다고 언급
  • AutoPlan — Office Hours 왕복 없이 CEO/Engineering/Design/DX 리뷰를 한 번에 통과시키는 자동화 스킬
  • Plan Show Review — Plan 단계에서 놓친 버그를 Staff 엔지니어 수준으로 탐지하는 코드 리뷰 스킬
  • Ship 스킬 — 메인 브랜치 머지 전 최종 관문 점검 도구

1. 배경 — Garry Tan이 에이전트 코딩에 빠진 이유

Garry Tan은 Stanford 컴퓨터 시스템 공학 출신으로 커리어 첫 10년을 엔지니어로 보냈다. Palantir 10번째 직원, Posterous 공동 창업(Twitter 인수), YC 내부 플랫폼 Bookface 개발 이력이 있다.

1월에 Andrej Karpathy와 Boris Chen이 "이제 코드를 직접 거의 안 쓴다"는 말을 듣고 Claude Code를 쓰기 시작했다. 이후 두 달 만에 2013년 한 해보다 많은 코드를 작성했고, Posterous(엔지니어 10명 × 2년 × 1천만 달러) 수준의 제품을 사실상 재현했다.

핵심 통찰: 모델의 지능이 병목이 아니다. 모델을 제대로 세워주는 구조가 없으면, 추측 기반의 "그럴듯해 보이지만 조용히 망가지는" 코드가 나온다.

2. GStack — 얇은 하네스, 두꺼운 스킬

GStack은 Claude Code를 "전문가 팀처럼 움직이는 스킬 묶음"으로 변환하는 오픈소스 저장소다. 핵심 철학은 "얇은 하네스(thin harness), 두꺼운 스킬(thick skill)" — 프레임워크 자체는 가볍게, 각 스킬이 도메인 노하우를 담는다.

Conductor를 통해 GUI로 킥스타트 가능. 새 워크트리 생성, 스킬 실행, 세션 관리를 시각적으로 처리한다.

주요 스킬 목록: - office_hours — YC 식 아이디어 검증 - auto_plan — CEO/Engineering/Design/DX 리뷰 자동 통과 - plan_show_review — 코드 완성 후 Staff 엔지니어 수준 버그 탐지 - design_shotgun — 여러 UI 후보 동시 생성 및 선택 - adversarial_review — 디자인 문서 반박·수정 자동화 - ship — 메인 머지 전 최종 관문

3. Office Hours 스킬 — YC 식 제품 검증

YC 166명 파트너의 노하우를 압축한 스킬이다. 화자는 "YC에서 매일 하는 일의 10% 압축판"이라고 표현한다. 추론 모드(extended thinking)를 켜면 모델의 사고 과정을 전부 볼 수 있다.

데모 시나리오: 세금 신고 시즌에 1099 양식을 Gmail과 금융기관에서 자동 수집하는 스타트업 아이디어.

Office Hours가 던진 핵심 질문:

"누군가가 이걸 정말 원한다는 가장 강한 증거가 뭔가요?"

이 질문이 나오자 Garry는 실제 경험(5개 계좌, 회계사 재촉 메일, 하나하나 추적하는 고통)을 답했다. 모델은 "큰 페널티보다 생활 불편에 가깝다"고 진단하고, 기존 솔루션(TurboTax, H&R Block, Plaid)이 있는데 왜 해결이 안 되느냐고 추가 질문.

비즈니스 모델 진화: - 단순 문서 수집 → 월 2~5달러 구독 (작은 시장) - 세무사 매칭/리드 생성 → 거래 비율 수수료 (훨씬 큰 시장) - 전형적인 Wedge 전략: 즉각적 문제 해결로 훅(hook)을 만들고 더 큰 비즈니스로 확장

아이디어가 더 발전한 방향: Google OAuth를 건너뛰고, 사용자가 Gmail을 열면 GStack Browser가 받은 편지함에서 1099를 자동 탐색. 다른 은행 계좌도 물어보고, 이미 담당 세무사가 있으면 이메일에서 찾아내 자동 전달.

4. Adversarial Review — 자동 품질 향상

코드나 디자인 문서 생성 후, 여러 단계의 적대적 리뷰를 자동으로 수행한다. 데모에서는: - 실패 처리 누락, 개인정보 섹션 누락, EFA 한도 처리 미비 등 16개 이슈 자동 탐지 - 가능한 것은 자동 수정 - 디자인 문서 점수: 10점 만점에 6점 → 8점 으로 향상 - 나머지 3개 이슈는 이후 처리 플래그

5. Design Shotgun — UI 후보 병렬 생성

비주얼 브레인스토밍 도구. Codex + 이미지 생성을 연동해 여러 화면 후보를 60초 내에 생성한다.

데모 결과물 (세금 문서 추적 대시보드): - A안: 커맨드 센터 스타일. "Linux 해커라면 정말 좋아할 스타일" → 별 4/5 - B안: 친근한 카드형 + 진행률 표시. "일반 사용자에게 더 잘 맞음" → 별 5/5, 채택 - C안: 필요 이상으로 복잡 → 탈락

마음에 안 들면 피드백 입력 후 Regenerate 가능.

6. 브라우저 자동화 — QA 병목 해결

에이전트가 기획·디자인·구현까지 처리하면 개발자는 QA만 하게 된다. "소프트웨어 개발에서 제일 재미없는 부분"이라 자동화가 필수.

claude-in-chrome MCP는 액션 당 2~3초, 컨텍스트 불안정으로 실패 → Playwright + Chromium 위에 직접 래퍼(GStack Browser) 작성.

기능: - 실제 브라우저 열기 + 스크린샷 - 클릭, 폼 입력, 복잡한 상호작용 - 미디어 다운로드 - 핵: 테스트 실행, CSS 수정, JavaScript/CSS 버그 평가

클라우드가 아닌 사용자의 실제 로컬 브라우저에서 실행한다는 점이 핵심 — "클라우드는 그냥 남의 컴퓨터"라는 철학.

7. 병렬 운용 — 소프트웨어 공장 레벨 7~8

실제 워크플로: - Claude Code 세션 10~15개 동시 실행 - 프로젝트마다 1~2개 세션 상시 유지 - Conductor에서 + 클릭 → 새 Git Worktree → 이슈별 독립 환경 - 기능별 브랜치로 병렬 PR 생성 → 거의 동시에 main 머지

공급망 공격 방어: 오픈소스 PR 400개 대기 상태에서 악성 코드 유입 위험. GStack의 자동 리뷰가 1차 방어선.

버그/피드백 처리 루틴: 1. X(Twitter)에서 불만 글 발견 → Conductor + 클릭 2. Office Hours → CO Review → Engineering Review → Adversarial Review 자동 실행 3. 하루 15~50개 PR 처리 (미팅 일정에 따라 변동)

저는 지난 두 달 동안 2013년 한 해보다 더 많은 코드를 짰습니다. 2013년은 제가 엔지니어로 정말 빡세게 일하던 마지막 시기였죠. 1월에 Andrej Karpathy와 Boris Chen 같은 사람들이 이제는 코드를 직접 거의 안 쓴다는 말을 들었습니다. 그 말을 듣고 Claude Code를 만져보기 시작했다가 완전히 빠져버렸습니다. 그 과정에서 사실상 Posterous 전체를 다시 만들었는데, 원래 공동 창업자와 엔지니어 10명이 2년에 걸쳐 만든 제품이었습니다.

하지만 기본 설정 그대로 두면 모델은 당신의 데이터를 잘 모르니까 추측하게 됩니다. 그렇게 규모있게 추측하기 시작하면, 그럴듯해 보이지만 조용히 망가지는 코드가 나옵니다. 여기서 병목은 모델의 지능이 아닙니다. 모델을 제대로 세워주기만 하면, 이미 당신 코드베이스에서 엄청난 일을 해낼 만큼 충분히 똑똑합니다. 문제는 받쳐주는 구조가 없다는 점입니다.

GStack은 제가 구현한 얇은 하네스(thin harness), 두꺼운 스킬(thick skill) 접근 방식입니다. 이건 Claude Code를 당신만의 AI 엔지니어링 팀으로 바꿔줍니다. 전문가 팀처럼 움직이는 스킬들이 들어있죠. 그 중 하나가 Office Hours입니다. 이건 YC 파트너로서 스타트업과 오피스 아워스를 할 때 실제로 거치는 과정을 거의 그대로 본뜬 스킬입니다. 무언가를 만들기 전에, 제품을 다시 보게 만드는 강한 질문들을 던져주죠.

GStack을 시작하는 가장 쉬운 방법은 Conductor를 쓰는 겁니다. Kickstart에서 GStack을 누르면 됩니다. 오늘은 세금 관련 앱을 하나 만들어 보겠습니다. Gmail에 들어가 1099 양식을 찾아내는 도구입니다. 오늘이 세금 신고일이거든요.

GStack은 이런 스킬 묶음으로 되어 있고, 우리가 처음 써볼 스킬 이름이 Office Hours입니다. YC의 166명 파트너가 쌓아온 노하우를 바탕으로 합니다. 수천, 수만 시간짜리 노하우를 압축한 버전입니다. YC에서 매일 하는 일의 10% 압축판이라고 보면 됩니다.

Conductor가 바로 그 자리로 넣어줍니다. YC Office Hours 안으로 들어왔습니다. 지금은 사람들이 1099 양식을 한데 모을 수 있게 돕는 서비스입니다. Gmail과 금융기관에서 한꺼번에 모을 수 있게 돕는 스타트업을 떠올리고 있습니다. 많은 은행이 세금 문서를 이메일로 보내줍니다. 하지만 그렇지 않은 것도 있어서 사용자 메일함도 뒤져야 합니다. 직접 URL을 받아 들어가 1099 PDF를 찾아 내려받는 기능도 필요합니다.

여기서 눈에 띄는 건 Extended Thinking 모드를 켜두었다는 점입니다. 이 모드는 추론 흔적을 전부 보여줍니다. 그래서 제가 GStack을 좋아하는 이유 중 하나가 바로 이겁니다. 모델이 생각하면서 어떤 과정을 거치는지 거의 그대로 볼 수 있거든요.

Office Hours 스킬이 들어간 모델은 생각을 꽤 많이 합니다. 가끔 앱도 검색하면서 지금 하려는 게 정확히 뭔지 파악하죠. 그리고 모든 걸 결정하는 질문이 나옵니다. "누군가가 이걸 정말 원한다는 가장 강한 증거가 뭔가요?" 이건 프로젝트를 해야 하나 스타트업을 해야 하나를 정할 때 스스로 꼭 물어봐야 하는 질문입니다.

저도 며칠 전에 비슷한 경험이 있었습니다. 계좌가 몇 개나 있고, 그 중 어디서 1099를 보내왔는지부터 따져봐야 했습니다. 하나하나 추적하는 과정이 꽤 고통스럽습니다. 그러자 모델이 "보통은 분명하지만 실제 손해라기보다 그냥 번거롭고 짜증나는 문제"라고 짚어줍니다. 즉, 큰 페널티보다 생활 불편에 가깝다는 뜻이죠. 솔직히 말하면 회계사한테 재촉 메일도 받고, 가끔 전화도 옵니다. 제 계좌는 5개가 넘습니다.

여기서 꽤 흥미로운 지점이 나옵니다. TurboTax랑 H&R Block은 사실 1099 가져오기 기능이 있고, Plaid는 은행 연결도 해줍니다. 그런데 왜 그걸로는 해결이 안 되냐고 묻더라고요. 사용자가 단순 문서 수집 도구보다 더 큰 그림을 보고 있다고 하더군요.

핵심 훅은 "1099를 다 찾아 드릴게요"라는 즉각적인 문제 해결입니다. 그런데 거기서 확장하면, 이제 문서를 모았으니 세금 신고 준비까지 이어줄 수 있죠. 즉, 세무사를 연결해주는 매칭과 리드 생성 사업이 됩니다. 전형적인 Wedge 전략이죠. 단순 문서 모으기만 하는 것보다 훨씬 흥미로운 비즈니스 모델입니다. 그걸로는 한 달 2달러나 5달러 정도만 받을 수 있을 겁니다. 세무사 연결 수수료는 거래의 일정 비율을 받을 수 있어서 훨씬 큽니다.

세 가지 접근법이 나왔습니다. 첫 번째는 브라우저 자동화 없이 어떤 은행이 1099를 발급하는지 체크리스트를 출력하는 방식입니다. 노력도 작고 위험도 작지만, 그 정도는 저도 직접 할 수 있어서 굳이 만들 만큼 큰 아이디어가 아닙니다. 두 번째는 Gmail + AI 브라우저 자동화 + 세무사 마켓플레이스까지 포함한 풀 스택 접근인데, 이게 원하는 방향입니다. 세 번째는 세무사를 먼저 공략하는 GTM 전략으로 뒤집는 방식입니다.

Google OAuth를 통째로 건너뛸 수도 있습니다. 사용자가 그냥 Gmail을 열기만 하면 됩니다. GStack Browser가 Gmail 안에서 1099를 자동으로 찾아내게 할 수도 있습니다. 거기서 더 나아가 사용자에게 다른 은행 계좌가 뭐가 있는지도 물을 수 있습니다. 이미 세무사가 있다면 그 정보도 이메일에서 찾아낼 수 있죠. 저 같은 경우엔 세무사가 어떤 계좌 자료가 빠졌는지 재촉하는 메일을 이미 여러 통 보내고 있을 겁니다.

오피스 아워스의 끝부분쯤 왔습니다. 반쯤 덜 익은 아이디어에서 출발했어도 훨씬 더 멀리까지 갈 수 있습니다. 처음에는 세금 문서 수집과 세무사 재촉 메일 정도에서 출발했습니다. 결국 브라우저 자동화로 받은 편지함을 뒤지고, 내려받아야 할 1099를 찾아내고, LLM이 어느 은행 포털을 더 추가해야 하는지도 묻고, 계정으로 로그인해 PDF까지 받아서 세무사에게 메일까지 보내줄 수 있는 데까지 왔습니다.

코딩 모델의 놀라운 점은 1년 전, 2년 전은 물론 심지어 3개월 전만 해도 이런 시도를 진지하게 하긴 어려웠다는 겁니다. 아이디어가 떠오르면 예전보다 훨씬 더 멀리까지 밀어붙일 수 있습니다.

저는 오피스 아워스를 쓰다가 3번 중 1번 정도는 마지막에 "이건 말이 안 되네"라고 결론 내리기도 합니다. 오피스 아워스에는 실현 가능성을 따지는 축이 분명히 들어가 있습니다. 저는 세상이 어떻게 돌아가고 무엇이 통할지에 대해 강한 의견이 있는데, opus 4.6도 비슷합니다. 그걸 비슷하게 비춰주면서 당신의 스타트업이나 제품 아이디어를 같이 정리해 준다는 게 꽤 흥미롭습니다.

지금 모델이 하는 건 여러 단계의 적대적 리뷰(adversarial review)입니다. 아이디어를 진짜로 두들겨 보는 거죠. 실패 처리도 없고 개인정보 섹션도 없습니다. EFA를 넘기는 한도도 아직 없습니다. 이런 항목들을 자동으로 체크하고 채우려 합니다. 가능하면 실제로 채워넣습니다. 이 문서는 두 번의 적대적 리뷰를 견뎠습니다. 자동으로 16개 이슈를 잡아내고 고쳤죠. 이제 이 디자인 문서를 승인하겠습니다. 적대적 리뷰 덕분에 점수가 10점 만점에 6점에서 8점으로 올라갔습니다. 나머지 3개 이슈는 나중에 처리하면 됩니다.

이번에는 바로 Design Shotgun으로 넘어가 보겠습니다. 제가 가장 재미있게 쓰는 방식 중 하나입니다. 여러 화면 후보를 먼저 정리한 다음 실제로 어떤 화면을 디자인할지 묻습니다. 메인 체크리스트 대시보드를 해보죠. Design Shotgun은 제 비주얼 브레인스토밍 도구라서 AI 버전을 여러 개 만든 뒤 질문을 던집니다. 지금은 세 방향이고 60초 정도 걸립니다. 이 작업을 Codex에 넘깁니다. 거기서 이미지 생성을 써서 세 가지 버전 — 커맨드 센터, 프렌들리 프로그레스, 스플릿 뷰를 만듭니다.

A안: 대시보드가 있고 세부 항목도 보입니다. 은행 목록, 1099 목록, 어디서 들어오는지, 상태까지 보여준다면 꽤 좋습니다. 별 5개 중 4개. B안: 훨씬 더 친근한 느낌입니다. A안은 Linux 해커라면 정말 좋아할 스타일 같습니다. B안이 일반 사용자에게 더 잘 맞습니다. 별 5개. B안을 고를 것 같습니다. C안: 필요 이상으로 너무 복잡합니다. 탈락. B안으로 확정됐습니다. 친근한 카드형 구조에 진행 룰링이 들어간 방식이죠.

참고로 이건 28개 명령 중 겨우 2개를 보여드린 것뿐입니다. 지금 GitHub Stars도 7만 개가 넘습니다. 사용자들 얘기를 들어보면 Claude Code를 쓸 때 시간의 80~90%를 Office Hours, Plan Show Review, AutoPlan을 쓴다고 합니다. AutoPlan도 만들었는데, CEO, Engineering, Design, 개발자 경험 리뷰까지 한 번에 묶어 기본 권장 안으로 한 번에 통과시켜주는 도구입니다.

Claude Code는 Plan에서 Approve를 누르면 실제로 코드를 만들기 시작합니다. 코드 작성이 끝난 뒤에는 리뷰를 돌릴 수 있는데 이건 Staff 레벨의 버그 탐지 서비스처럼 동작합니다. 그리고 가장 멋진 부분은 브라우저 자동화입니다. Playwright와 Chromium 위에 직접 래퍼를 하나 썼다는 점입니다. 헤드리스 브라우저가 그 안에 들어 있습니다. 이건 제가 Claude Code를 더 빠르게 쓰기 시작하면서 정말 마법처럼 느껴진 순간이었습니다.

소프트웨어 공장을 레벨 7~8까지 끌어올리자는 아이디어가 있습니다. 서로 다른 프로젝트로 여러 Conductor 창을 동시에 띄울 수 있고, 때로는 같은 프로젝트도 여러 창으로 돌릴 수 있습니다. 프로젝트를 3개, 4개 창으로 동시에 돌릴 수도 있습니다. 서로 다른 브랜치와 서로 다른 기능으로 병렬 PR을 만들고 거의 동시에 메인에 넣을 수 있습니다.

그런데 제가 부딪힌 병목 중 하나는 QA였습니다. 에이전트가 기획, 디자인, 구현까지 다 해버리면 정작 저는 QA를 하며 앉아 있게 된다는 점이었습니다. 소프트웨어 개발에서 제일 재미없는 부분이죠. 그래서 이걸 자동화하는 게 정말 중요해졌습니다. claude-in-chrome MCP를 써봤는데 제가 써본 소프트웨어 중 거의 최악이었습니다. 뭘 하려고 할 때마다 생각만 오래 하고, 컨텍스트도 엄청 불안했습니다. 심지어 동작할 때 조차 액션 당 2~3초가 걸렸습니다.

그래서 GStack에서 직접 해결할 수 있었습니다. Playwright를 Chromium 수준에서 감싸서 GStack Browser를 만들었습니다. 이제 Claude Code와 다른 어떤 에이전트도 실제 브라우저를 쓸 수 있습니다. 브라우저를 여는 것뿐 아니라 스크린샷도 찍을 수 있습니다. 복잡한 상호작용, 클릭, 폼 입력, 미디어 다운로드, 테스트 실행, CSS 수정, JavaScript/CSS 버그 평가까지 가능합니다.

마지막으로 Ship 스킬이 있습니다. 메인에 넣기 전 마지막 관문입니다. PR이 정말 메인에 들어갈 준비가 됐는지 확인하는 마지막 단계라고 보면 됩니다.

저는 실제로 이렇게 일합니다. Claude Code 세션을 10~15개까지 동시에 띄워놓습니다. 어떤 세션에서는 완전히 새로운 아이디어로 Office Hours를 돌리고 있을 수도 있죠. 지금 저는 이미 수만 개의 Stars를 받은 오픈소스 프로젝트를 여러 개 갖고 있습니다. 검토해야 할 PR이 아마 400개 정도 쌓여 있을 겁니다. 프로젝트마다 한두 개의 세션을 띄워두고 커뮤니티에서 올라오는 오픈소스 수정사항을 평가하고 받아들이는 작업을 합니다.

AI 코딩에서 꽤 무섭게 느껴지는 것 중 하나는 공급망 공격(supply chain attack)입니다. 그래서 저는 정말 예민하게 봅니다. 하지만 다행히 GStack이 뒤를 봐줍니다.
