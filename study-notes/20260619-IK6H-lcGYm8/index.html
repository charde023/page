모델 성능 경쟁보다 하네스(harness) 설계와 코드베이스 품질이 AI 생산성의 진짜 레버리지다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
전술적 vs 전략적 프로그래밍 (tactical vs strategic programming) AI가 전술 부분을 대체하므로, 인간은 전략에 더 집중해야 한다 AI 시대에 생존하는 개발자는 전략 담당자
하네스(harness) 우선주의 모델 교체보다 harness 개선이 더 오래 유효하고 더 많은 통제권을 준다 모델은 50%, 하네스도 50%
Procedure skill vs Ability skill procedure는 인간이 직접 호출, ability는 모델이 자동 호출 — 맥락 누수 방지와 제어권 유지에 중요 제어권을 인간이 가져야 한다
AFK(Away From Keyboard) 에이전트 병렬화로 생산성 폭발적 증가 — 에이전트 여러 개를 동시에 돌릴 수 있음 나를 복수화(parallelize)하는 도구
큐(queue) vs 루프(loop) loop는 무한 실행, queue는 목적 있는 작업 목록 — 실제 개발은 queue 모델이 맞다 에이전트에게 backlog를 처리하게 한다
DX vs AX Developer Experience와 Agent Experience는 겹치지만 다르다 — 코드베이스 품질이 AX에도 직결됨 좋은 코드베이스 = 더 싼 모델로도 좋은 결과
지식(knowledge) · 스킬(skill) · 지혜(wisdom) 삼분법 지혜는 실전 경험 없이 얻기 어렵다 — skill 저장소로 knowledge·skill은 공유 가능 팀 전체의 수준을 올리는 절차 공유

내가 모를 만한 것 / 처음 보는 것

  • Sandcastle — Matt이 직접 만든 도구. Docker/Podman 샌드박스 안에서 Claude Code 에이전트를 실행. GitHub Actions와 연동해 AFK 워크플로 구현. 랜덤 홈 디렉토리 삭제나 환경 변수 유출 방지.
  • Superpowers (skills repo) — Matt이 언급한 "가장 인기 있는 skills 저장소". ability 방식의 스킬을 선호하는 반대 철학.
  • skills 설치 CLI — npx skills latest add mattpocock/skills 로 로컬 설치. Claude Code·Codex 모두 호환.
  • teach skill — 존근 근접 발달영역(zone of proximal development), 지식·스킬·지혜 구분 등 교육 이론을 인코딩한 절차형 스킬. stateful: workspace에 mission.md·learning record를 저장해 교사처럼 기억함.
  • grill me skill — 역할이 adversarial interviewer인 절차형 스킬. 4~5문장 분량. plan mode 대체용.
  • Ralph loop / G. Huntley — 2025년 7월 14일 원조 글. Claude Code를 while loop로 반복 호출하는 아이디어. Matt은 loop보다 queue 모델을 선호.
  • AX (Agent Experience) — DX(Developer Experience)의 에이전트판. 코드베이스가 에이전트 친화적인지 측정하는 개념.
  • Bitter Lesson — ML 연구에서 raw compute가 결국 모든 최적화를 이긴다는 교훈. Matt이 하네스 집착이 이 함정에 빠질 수 있음을 스스로 인정하면서도, 그래도 하네스 개선은 가치 있다고 주장.
  • WhisperFlow — 받아쓰기(dictation) 도구. Matt이 코딩 중 구술 입력에 활용.
  • SERP API — 구조화된 검색 결과를 JSON으로 제공하는 API. 이 영상의 스폰서. 에이전트가 실시간 정보를 가져올 때 사용.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 모델 선택: Claude Code Opus 4.8 medium effort — Fable(Claude 4 계열)이 출시됐지만 Matt은 아직 Opus 4.8 medium 유지. "새 모델이 나오면 한 달 기다려서 먼지가 가라앉은 후 전환"이 본인 전략.
  2. 스킬 description 누수 — ability 스킬은 설명이 context window에 자동 주입된다. 100개 스킬이면 100개 설명이 누수됨. disable_model_invocation: true 플래그로 비활성화 가능.
  3. 코드베이스 품질 = 토큰 절약 — "코드베이스가 변경하기 쉬우면 더 싼 모델로도 같은 결과" — 토큰 최적화 질문에 Matt의 실제 대답.
  4. AFK GitHub Actions 설정 — Sandcastle을 GitHub Actions에서 실행. PR에 agent-review 레이블 → 에이전트가 타입 체크·lint·코드 리뷰 수행 → 결과를 PR 댓글로 달아줌.
  5. teach skill = stateful skill — mission.md·learning record·reference cheat sheet·HTML 레슨 파일을 워크스페이스에 저장. 브라우저에서 시각적으로 볼 수 있는 HTML 산출물 생성.
  6. grill me skill = 4~5문장 — "unreasonably effective"라는 표현 반복. plan mode 이전에 먼저 grill me → PRD 작성 → 이슈 분해 순이 Matt의 일반적 workflow.
  7. 큐 관리 — Sandcastle GitHub 이슈를 큐로 사용. explore 레이블 → 에이전트가 탐색 후 agent-implement 레이블로 전환 → AFK 구현.

1. 하네스(harness) 우선주의

Matt의 핵심 주장: 개발자들이 모델(엔진)에만 집착하는 반면, harness — 즉 에이전트가 실행되는 환경, 프롬프트 설계, 코드베이스 품질, 스킬 구성 — 가 동등하게 중요하다.

Formula One 비유: 엔진만 보지 말고 섀시, 공기역학, 전체 시스템을 봐야 한다. 모델과 harness를 50:50으로 보는 것이 Matt의 입장.

Bitter Lesson 반론도 스스로 제기: "harness 최적화보다 그냥 모델이 좋아지길 기다리는 게 낫지 않나?" — 그래도 harness 개선은 가치 있다는 결론.

실용적 귀결: 코드베이스가 좋을수록 더 싼 모델로도 같은 결과. 토큰 최적화 = 더 좋은 코드베이스.

2. 전술 vs 전략 프로그래밍

출처: John Ousterhout의 Philosophy of Software Design.

  • 전술적 프로그래밍 (tactical programming): 코드 작성, 문법 해결, 버그 수정, 커밋 생성 — 일상적 구현 작업.
  • 전략적 프로그래밍 (strategic programming): 코드베이스 설계, 속도 향상 전략, 모듈 인터페이스 설계, 문서화, 장기 로드맵.

AI가 전술을 대체했다. 따라서 전략적 역량이 있는 사람이 "무한한 전술 프로그래머 군단"을 효과적으로 지휘할 수 있다.

"AI는 시니어 개발자를 10배 더 낫게 만들고, 주니어에게는 작은 부스트만 준다" — 본인 스킬이 AI 활용의 천장(ceiling).

좋은 위임을 위한 조건(AI도 동일): - 어려운 부분을 미리 설계 - 작업을 잘 범위 지정(scoped) - 모듈 간 인터페이스 정의 - 테스트 설계 - AI가 올바른 위치를 찾아갈 수 있는 최소한의 문서

Matt의 철학: "나는 드라이버 자리를 내주지 않는다. 모든 스킬은 내가 호출하는 procedure로 만든다."

grill me skill

워크플로: grill me → 공유 이해 도달 → PRD 작성 (2PRD 스킬) → 이슈 분해 → 각 이슈 AFK 구현.

팀 레벨 활용: 절차(procedure)를 스킬로 인코딩 → 팀 전체 배포 → 팀 전체가 같은 방식으로 계획·구현 → 팀 최저선(floor) 상향.

4. teach skill 라이브 데모

핵심 교육 이론 두 가지를 인코딩: 1. Zone of Proximal Development (근접 발달 영역) — 현재 수준 바로 위의 다음 학습 단계 추천 2. Knowledge / Skills / Wisdom 삼분법 — 각 단계별 학습 전략 차별화

Stateful skill: workspace에 다음을 저장. - mission.md — 학습 목표, 현재 수준, 원하는 결과 - learning-record.md — 이미 학습한 내용 기록 - reference-cheatsheet.html — 참고용 치트시트 - lesson-N.html — 각 레슨 (브라우저에서 열기 가능, 퀴즈·연습문제 포함)

데모에서 Matt가 "vibe coder" 페르소나로 요청 → 에이전트가 미션 3문항 확인 → Git 부터 시작 → 브라우저 열 수 있는 HTML 레슨 생성 → 퀴즈로 기억 강화.

Matt 본인은 이 스킬로 루빅스 큐브 독학 완료.

5. AFK + Sandcastle + GitHub Actions

AFK(Away From Keyboard): 에이전트에게 범위 지정 작업을 맡기고 자리를 비움. "나를 복수화하는 순간" — 동시에 여러 에이전트가 병렬로 작업.

Sandcastle: Matt이 만든 오픈소스 도구. Docker/Podman 플러그인 지원. - 에이전트가 홈 디렉토리 삭제·환경 변수 유출 등 위험 행동 차단 - Vercel sandbox 등 원격 환경에서도 실행 가능

GitHub Actions 연동: 1. GitHub 이슈에 explore 레이블 추가 → 에이전트가 탐색·분석 2. 에이전트가 agent-implement 레이블로 변경 3. AFK 에이전트가 구현 → PR 생성 4. PR에 agent-review 레이블 → 리뷰 에이전트가 타입 체크·lint 수행 후 댓글

인간의 역할: 이슈 트리아지, 레이블 추가, PR 최종 승인.

6. 루프(loop) vs 큐(queue) 논쟁

Ralph loop: 2025년 7월 G. Huntley의 원조 아이디어. Claude Code를 while loop로 반복 호출.

Matt의 반론: "루프는 필요 없다. 내가 필요한 건 AFK 에이전트가 특정 작업을 완수하는 것뿐."

큐(queue) 모델이 실제 개발 팀과 더 일치: - Backlog = 처리할 작업 목록 - 여러 노드(개발자·에이전트)가 큐에서 작업을 가져옴 - 완료 조건이 명확 (PR 머지) - 무한 실행·무한 비용 없음

왕과 신하 비유(David의 비유): 왕(인간)이 큐에서 우선순위를 정하고, 신하(에이전트)에게 범위 지정 임무를 부여. 신하를 내보내고 소식이 없으면 위험.

인간 체크포인트 위치: "human-in-the-loop 체크포인트를 최대한 오른쪽으로(마지막 단계 가까이) 밀어야 한다. 하지만 시스템 자체를 관찰·개선하기 위해 일부 체크포인트는 반드시 유지."

7. DX vs AX와 코드베이스 기본기

DX (Developer Experience): 인간 개발자가 코드베이스에서 작업하는 경험.

AX (Agent Experience): 에이전트가 코드베이스에서 작업하는 경험.

두 개의 큰 겹침: 좋은 DX는 대부분 좋은 AX이기도 하다. 단, 접근 방향이 다름 — 시니어는 DX 설계 경험, 주니어 AI 활용자는 AX 최적화 경험에서 출발.

"코드베이스를 변경하기 쉽게 만드는 것이 토큰 비용을 줄이는 최선의 방법" — 아키텍처가 좋으면 더 저렴한 모델도 같은 결과.

가드레일이 좋을수록 모델이 벽에 머리를 박는 시간을 줄이고, 더 효율적으로 탐색 가능.

8. 비즈니스와 제품 방향

Matt의 입장: "AI가 등장해도 비즈니스 근본은 바뀌지 않았다." - 고객과 대화하고 필요를 파악하는 것 → AI 대체 불가 - 프로토타입 구현 속도 → AI로 대폭 향상

"AI에게 어떤 기능을 추가할지 묻지 말고, 어떤 기능을 제거할지 물어라 — 어떻게 더 단순하게 만들지."

SaaS 생사 논쟁에 대해: "나는 시장 예측에 관심 없다. 좋은 제품을 빠르게 만드는 것에 집중."

9. 마무리 — 초보자를 위한 두 가지 조언

Matt의 실용 조언:

1단계: 초기화(reset) - 모든 스킬, 플러그인, MCP 서버 삭제 - CLAUDE.md, agents.md 삭제 - 빈 상태에서 에이전트 관찰 — 기본 동작 파악

2단계: 절차(procedure)만 추가 - 정말 그리운 것만 하나씩 다시 설치 - ability 스킬이 아닌 procedure 스킬 위주로 - mattpocock/skills 저장소가 시작점으로 좋음 - 문제가 보이면 그 문제를 해결하는 스킬을 추가

AFK 워크플로 설정: "설정에 약간의 시간이 들지만, 되고 나면 생산성이 폭발적으로 증가한다."

전체 전사 펼치기

모두가 모델에 집착하는데, 나는 사람들이 하네스(harness)에 더 관심을 가져야 한다고 생각한다. 하네스에서 최대한 활용하기 위해 할 수 있는 것들, 즉 올바른 프롬프트 제공, 작업할 수 있는 올바른 스킬 제공, 모델이 실행되는 환경 개선. Fable과 관련해 말했듯이 모델은 유용하지만, 하네스도 그에 못지않은 작업량을 갖고 있으며 모델보다 하네스를 훨씬 더 많이 통제할 수 있다. 사람들은 잘못된 것에 집중하고 있다. 30, 40년 동안 잘 작동해온 것에 집중하라. 그리고 그건 정말 효과가 있다. 사람들이 항상 묻는다: 토큰을 어떻게 최적화하느냐고. 변경하기 쉬운 코드베이스를 만들어라.

Matt, AI를 사용해 엄청나게 앞서 나가는 사람들과 작은 부스트만 얻는 다수의 사람들 사이의 주요 차이점은 무엇일까요?

John Ousterhout의 Philosophy of Software Design이라는 책에서 전술적 프로그래밍(tactical programming)과 전략적 프로그래밍(strategic programming)의 차이를 이야기한다. 이 구분이 AI를 생각할 때 정말 유용하다. 전술적 프로그래밍은 지상에서의 일상적인 작업이다 — 실제 코드 작성, 문법과의 씨름, 버그 수정, 실제 코드와 커밋 생성. 전략적 프로그래밍은 전쟁에서 이기는 것이지 전투가 아니다. 장기적인 사고다. 코드베이스가 어떻게 생겨야 하는가? 속도를 높이기 위해 어떤 전략을 쓸 것인가?

나에게 전략적 프로그래밍은 항상 가장 흥미롭고 흥미진진한 것이었다. 주니어 때도 그렇게 생각했다. 어떻게 하면 더 적은 것으로 더 많이 할 수 있을까? AI가 전술적 프로그래밍을 다 먹어버렸다. 사라졌다. AI는 전술적 프로그래밍을 더 저렴하게 할 수 있으니 당연히 더 잘한다. 그래서 이 무한한 전술 프로그래머 군단에서 최대한 활용하려면 전략적 프로그래밍을 잘 해야 한다.

즉 에이전트 오케스트레이션과 소프트웨어 설계 기초 지식이 필요하다는 건데, 어떻게 나누어 생각할 수 있을까요?

전략적 프로그래밍은 AI 시대에도 크게 바뀌지 않았다. 우리는 그저 주니어나 미드레벨 프로그래머에게 위임하는 대신 AI에게 위임하는 것이다. 좋은 위임을 위해 필요한 것들은 여전히 같다 — 어려운 부분을 미리 설계하고, 작업을 잘 범위 지정하고, 모듈 간 인터페이스를 생각하고, 테스트를 생각하고, 기본적으로 작업하기 좋고 AI가 변경사항을 효과적으로 만들 수 있는 코드베이스를 설계해야 한다.

많은 사람들이 AI 진보가 빠르다는 것에 동의하면서도, 자신을 업스킬링하는 부분을 놓친다. 구독료를 내고 최신 도구를 살 수 있지만, 그건 누구나 할 수 있다. 결국 이 도구들로 크게 성장하는 사람이 있을 것이다. 어떻게 더 잘하도록 스스로를 가르칠까요?

사람들이 항상 묻는다 — 나는 개발자 강좌를 팔기도 하니 이 말을 약간의 소금과 함께 들어달라 — 하지만 나는 내 스킬이 AI의 배수(multiplier)라고 생각한다. 코드베이스를 감독하고 어떻게 만들어야 할지 AI에게 알려줄 수 있다면, AI는 훨씬 더 풍부한 컨텍스트로 작업할 수 있다. AI는 시니어 개발자를 10배 더 낫게 만들고, 주니어에게는 그냥 작은 부스트만 준다. 당신의 스킬이 AI가 할 수 있는 것의 천장(ceiling)이다. 스킬이 낮으면 AI가 그 이상을 넘지 못한다. 그래서 AI를 잘 활용하는 것은 사실 자신의 도메인을 잘 아는 것이다.

(광고: SERP API — 웹 스크래핑의 어려움 없이 구조화된 검색 결과를 JSON으로 제공하는 API. 캡챠·프록시·HTML 파싱 없음. AI 에이전트의 실시간 정보 수집 도구로 활용 가능. 250 무료 크레딧.)

teach 스킬을 최근 배포했다고요. 나는 10년간 교사를 했다 — 대학 직후 노래와 음성을 가르쳤고, 그 후 개발자가 되어 지난 4년간 개발자를 가르치고 있다. 가르치기에 대해 많이 안다. 근접 발달 영역(zone of proximal development), 지식·스킬·지혜의 차이 등의 교육 원칙들을 스킬에 인코딩해서 기본적으로 모든 주제에 대해 즉석에서 강좌를 만들어내도록 했다. 나는 이것으로 실제로 루빅스 큐브를 독학했다 — 지금 기억으로 풀 수 있다.

시연: "나는 vibe coder이고, 더 나은 소프트웨어를 출시하기 위해 지식 격차를 채우고 싶다. 기본 CLI 명령어 조금과 코드를 읽고 터미널을 사용하는 정도를 안다. 다음에 무엇을 배워야 할까요?" 에이전트가 workspace를 확인하고(teach skill은 workspace에서 실행 필요), 먼저 미션을 명확히 하기 위해 3개의 빠른 질문을 한다.

나는 교육과 학습을 머릿속에 정보를 넣는 것이 아니라 세상에서 당신을 새로운 위치에 두는 것으로 생각한다. 이것은 다소 추상적이고 거의 영적이지만, 사실 이 스킬들을 배우는 것은 세상에서 무언가를 하기 위해서다. 그게 당신의 미션이다.

mission.md를 만든다. 가르치는 노래 선생님 페르소나로 — 스케줄링 앱, 학생 노트, 연습 도구를 만들고 싶다. 인증이 있는 풀스택 앱이지만 현재 능력 밖이다.

WhisperFlow(받아쓰기 도구) 언급 — "구술 입력 안 하는 사람은 너무 느린 거야. 빠른 개발자일수록 언어 유창성이 큰 이점이 된다."

레슨 1 "Get Your Project's Undo Button" (Git): HTML로 생성됨, 브라우저에서 열기 가능. 퀴즈 포함: git commit, git status, git add의 역할, commit은 저장 지점. 퀴즈는 불편하지만 기억 저장 강도를 높이는 데 매우 효과적.

지식은 그래프 같은 것 — 큰 숲을 탐험하는 것. teach skill이 그 그래프를 통한 선형 경로를 만들어 준다. learning record, zone of proximal development, 현재 수준 추정치를 저장한다.

좋은 에이전트 스킬과 나쁜 것의 차이는? "깊은 질문이다." 두 종류: procedure skill(직접 호출), ability skill(모델이 자율 호출).

ability 예시: React 코딩 기준 스킬 — 에이전트가 React 코드를 쓸 때 자동으로 가져와서 useEffect 대신 무엇을 써야 하는지 확인.

procedure 예시: grill me 스킬 — 4~5문장, adversarial interviewer로 변환, unreasonably effective. plan mode 대신 사용. grill me → PRD → 이슈 분해.

나는 절차형(procedure)을 선호한다. 내가 운전석에 있고 싶다. "grill me 하자, 그 다음 PRD 쓰자"식으로 내가 결정한다. Superpowers(오페라의 가장 인기 있는 skills repo)는 반대 접근 — 모델이 더 많이 제어. 각자의 철학.

능력 목록이 있다면 description이 context window에 누수된다 — 100개 스킬이면 100개 description 누수. disable_model_invocation: true로 비활성화 가능.

나는 대부분의 description을 AI에서 숨기고 그 지식을 인간 안에 두는 것을 선호한다. 스킬을 재사용 가능한 덩어리로 절차화하는 것은 흥미로운 시대다. 코드베이스에서 함수를 중복 제거하는 것처럼, 우리 자신의 절차도 스킬로 만들어 팀에 배포할 수 있다. 팀 전체의 최저선을 높이는 것.

현재 에이전틱 엔지니어링 셋업: Claude Code로 계획과 일부 구현(로컬). Opus 4.8 medium effort. 대부분의 작업을 AFK로 한다. Sandcastle 도구로 Docker/Podman 샌드박스 안에서 에이전트 실행. 병렬화 또는 Vercel 샌드박스에서 원격 실행 후 커밋을 로컬 workspace로 가져오기.

GitHub Actions 연동: PR에 agent-review 액션 → 에이전트가 타입 체크, lint, 코드 리뷰 → 댓글로 결과 달아줌.

모델은 어떻게 선택하나? 그냥 Claude Code Opus 4.8 medium. 모델을 크게 바꾸지 않는다. "모두가 모델에 집착한다. 모두가 F1 엔진에 집착한다. 하지만 섀시와 공기역학도 있다. 모두가 모델에 집착하고 harness에는 더 관심을 가져야 한다고 생각한다."

왜 두 개 다 할 수 없냐는 David의 반론: "물론 더 좋은 엔진을 꽂으면 전부 즉시 좋아지지. 하지만 50:50으로 봐야 한다. 모델이 90%고 harness 최적화가 10%가 아니라."

Bitter Lesson: "내가 harness를 최적화하는 대신 그냥 모델이 더 좋아지길 기다려야 할 것 같다는 아이디어에 빠지고 있는 건지 모르겠다. 그래도 harness 개선에는 얻을 것이 많다고 생각한다."

모델 선택 vs harness 최적화 — 나는 중간 어딘가다. 매일 설정을 개선하려 한다. VPS 써야 하나? TailScale 써야 하나? 모델 제외 모든 걸 개선하면서도 최고 모델 사용.

다음 세대 모델(Opus 6, Fable 6 등)이 더 적은 조종을 필요로 할까? "나는 전문가가 아니다. 내가 가진 것으로 최선을 다하는 중. 예측하고 싶지 않다. workspace와 harness를 최대한 에이전트 불가지론적으로 유지하고, 오래된 소프트웨어 기초에 집중하면 미래에도 통할 것이다."

"사람들이 잘못된 것에 집중한다. 30, 40년 동안 통해온 것에 집중해라. 코드베이스를 변경하기 쉽게 만들어라. 그러면 더 저렴한 모델을 쓸 수 있다. 아키텍처가 좋으면 더 멍청한 모델로도 같은 작업을 할 수 있다. 가드레일이 좋으면 모델이 벽에 머리를 박는 시간이 줄어든다."

Fable 보안 이슈 예시 — Cursor + Fable가 Twitter API 콘솔에서 버튼이 안 눌리는 문제를 built-in 브라우저로 직접 해결(보안 비권장 방식). Matt의 반응: "AI의 결과물이 올바른지 판단하는 건 여전히 당신(David)이 필요하다. 더 많이 위임할 수 있지만 완전히 빠지는 게 아니다."

더 나은 모델이 더 많은 버그를 발견한다는 주장에 대해: "그 버그들은 더 싼 모델도 harness만 제대로 있으면 찾을 수 있다. 매일 다른 부분을 검사하는 cron job을 돌려라. harness가 잘 되어 있으면 더 싼 모델도 같은 결과를 낸다. 우리가 harness에서 뒤처진 채 모델에게 떠밀고 있는 것이다."

Fable가 발견한 보안 이슈에서 얻어야 할 교훈: "좋아, Fable가 좋다는 걸 배웠다. 하지만 더 중요한 건 보안 이슈가 있다는 걸 발견한 것이다. 앞으로 더 많은 이슈를 확인하는 무언가가 있어야 한다. 자전거를 자꾸 도난당한다면 잠금장치를 사라. 왜 이 지경이 됐는지 이유를 파악해라."

소프트웨어 엔지니어로서 자기 개선 시스템 구축: 테스트 스위트, 코드 리뷰, 리팩터링 — 오래된 방식이지만 여전히 중요. 모델이 그냥 버그를 고쳐주길 기다리는 대신, 왜 버그가 생겼는지 근본 원인을 찾아라.

루프 논쟁: 루프는 기본적으로 그냥 AFK 에이전트 이야기다. G. Huntley(2025년 7월 14일 원조)의 Ralph loop. 나는 루프보다 큐로 생각한다. Sandcastle 이슈들이 backlog. explore → agent-implement → GitHub Actions에서 AFK 구현. 큐는 작업이 완료되면 소진된다. 팀에서도 마찬가지 — 여러 노드가 큐에서 가져간다.

왕과 신하 비유(David): 신하를 보내고 소식이 없으면 문제. 큐(Q) 접근법이 맞다. 우선순위 정하기, 리소스 배분, 여전히 왕이 통솔.

자동화 추가 예시: Sentry에서 버그 리포트 → 이슈 자동 생성 → explore 레이블 → 에이전트가 탐색 → 즉시 고칠 수 있나 구조화된 데이터로 반환 → 구현 → "자동 머지 가능?" 태그 또는 사용자에게 알림.

인간 체크포인트: "가능한 한 오른쪽으로(최종 출력 가까이) 밀어야 한다. 하지만 코드를 리뷰하는 게 보안·안전만을 위한 게 아니다 — 시스템 플러밍을 관찰하고 harness를 개선하기 위해 일부 PR은 직접 봐야 한다."

AI가 자동으로 처리하는 PR: "그 PR들을 일일 요약 HTML 파일로 받는 것이 낫다. GitHub 인터페이스보다 훨씬 최적화된 방식으로."

AI에게 강한 시니어 vs AI 열성 주니어 채용 비교: "좋은 주니어를 찾는 게 항상 목표였다. 열정이 경험을 이긴다." AI + 소프트웨어 기초 조금 = 강력. DX 설계 능력(시니어)과 AX 최적화 경험(주니어 AI 활용자)은 다른 방향에서 출발하지만 큰 겹침이 있다.

결론: "실험적 마인드셋을 갖고 harness에 집중하면 주니어든 시니어든 잘 된다. 더 이상 코드 원숭이는 없다. 전략적으로 생각해야 한다. 시니어도 물론 최대한 활용 가능하고, 주니어도 배울 수 있다."
