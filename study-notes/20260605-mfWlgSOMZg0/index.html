AI 시대에 코드를 읽는 6가지 방법입니다

업로드 2026-06-05 · 3.9분 · 원본 영상 ↗
한 줄 요약

코드 작성은 AI가 대신하지만, 코드를 제대로 읽고 엣지 케이스를 잡아내는 능력은 여전히 사람 몫이다 — 6가지 체계적 기법으로 어떤 코드베이스든 빠르게 파악할 수 있다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
진입점(entry point)부터 읽기 코드는 책이 아니라 호출 그래프(call graph) 요청이 들어오는 라인을 먼저 찾아라
테스트 케이스로 계약 파악 소스 보기 전에 기대 동작(계약)을 먼저 확정 테스트의 happy path = 입/출력 명세
핵심 데이터 흐름 추적 함수 목록이 아니라 데이터 변환 경로가 로직 user 변수의 생성→변환→반환 경로를 따라가라
첫 패스에서 불필요한 코드 건너뛰기 헬퍼를 모두 파고들면 시간 낭비 rate limiter·audit log는 나중에, 흐름 차단 여부만 판단
실패 경로 한 가지 읽기 happy path만 봐선 보안 버그를 놓친다 오류 메시지 차이와 응답 시간 차이 → 계정 열거(account enumeration) 취약점
한 문장으로 요약 진짜 이해와 그냥 스크롤의 차이 한 줄로 못 쓰면 아직 이해 못 한 것

내가 모를 만한 것 / 처음 보는 것

  • account enumeration(계정 열거) 공격 — 로그인 오류 메시지나 응답 시간의 차이로 공격자가 계정 존재 여부를 알아내는 기법. 동일 에러 메시지라도 응답 시간이 다르면 뚫린다.
  • bcrypt.compare — 저장된 해시와 입력 비밀번호를 안전하게 비교하는 함수. 타이밍 공격 방지를 위해 실패해도 일정 시간 소요.
  • JWT(JSON Web Token) — 사용자 ID 등을 서명해 만드는 토큰. 서버 세션 없이 stateless 인증에 사용.

화자의 디테일 (놓치기 쉬운 포인트)

  1. "코드는 위에서 아래로 읽는 책이 아니다" — 코드는 누가 무엇을 호출하는지의 그래프(graph of who calls what). 파일 맨 위부터 스크롤하는 습관이 가장 흔한 실수.
  2. 응답 시간 차이가 보안 취약점 — 이메일이 존재하지 않을 때와 존재하는데 비밀번호가 틀렸을 때 응답 시간이 다르면, 오류 메시지가 같아도 공격자가 계정 존재를 알아낼 수 있다.
  3. 헬퍼 함수를 즉시 열어보는 습관이 최대 함정 — 대부분의 엔지니어가 헬퍼를 만나면 의무감에 바로 파고드는데, 이게 시간을 가장 많이 잡아먹는다. 흐름을 막는지·요청을 바꾸는지·버그를 설명하는지 — 이 세 가지가 아니면 나중에.
  4. "이해 vs. 그냥 봄(understood vs. just looked at)" — 화자가 명시적으로 구분. 한 문장 요약이 안 되면 후자.
  5. 영상이 약 4분(231초)으로 짧지만 전사 내용은 완결된 강의 구성을 갖추고 있다.

한눈에 보기

# 기법 요지
1 진입점부터 시작 app.post('/login') — 외부 요청이 들어오는 라인이 출발점
2 테스트 케이스 먼저 happy path 테스트로 계약(입력→출력) 확인 후 소스 진입
3 데이터 흐름 추적 user 변수: 조회→비밀번호 검증→JWT 서명→응답 반환
4 첫 패스에서 건너뛰기 rate limiter·audit log·validator는 흐름 차단 여부만 보고 패스
5 실패 경로 하나 읽기 오류 메시지 차이·응답 시간 차이 → 계정 열거 취약점 점검
6 한 문장으로 요약 흐름을 한 줄로 쓸 수 없으면 이해가 부족한 것

1. 진입점부터 시작하라 (Start at the Entry Point)

코드를 위에서 아래로 읽는 것은 책 읽기 방식이다. 코드는 그래프(호출 관계)다. 로그인 엔드포인트 예제라면, 유저 모델이나 미들웨어 폴더를 먼저 열지 말고 외부 요청이 들어오는 라인 — routes/auth.js의 app.post('/login') — 을 먼저 찾아라.

2. 테스트 케이스를 소스보다 먼저 읽어라 (Read Tests Before Source)

auth.test.js의 happy path 테스트를 열면, 이메일과 비밀번호를 POST하면 200 상태코드와 토큰이 반환된다는 계약이 5줄 안에 들어있다. 이 계약을 먼저 확정하고 소스 코드로 넘어가면 전체 구조가 훨씬 빠르게 보인다.

3. 데이터의 흐름을 따라가라 (Follow the Data, Not the Functions)

로그인 핸들러에서 중요한 것은 user 변수의 여정이다.

  1. User.findByEmail(email) — 요청에서 이메일로 사용자 조회
  2. bcrypt.compare(password, user.passwordHash) — 제출된 비밀번호를 해시와 비교
  3. jwt.sign({ id: user.id }, secret, { expiresIn: ... }) — user.id를 JWT로 서명(만료일 포함)
  4. 토큰을 응답으로 반환

이 흐름은 30초 안에 파악된다.

4. 첫 패스에서 필요 없는 것은 건너뛰어라 (Skip What You Don't Need)

rate limiter, audit log 호출, validator 등은 흐름을 차단하거나, 요청을 변경하거나, 조사 중인 버그를 설명하지 않는다면 첫 패스에서 무시한다. 미들웨어와 validator는 핸들러 실행 여부를 결정하기 때문에 영원히 건너뛸 수는 없지만, 큰 그림을 그리는 동안만 보류하면 된다.

5. 실패 경로 하나를 읽어라 (Read Exactly One Failure Path)

happy path가 명확해지면, 다음 두 가지를 확인한다:

  • 오류 메시지 차이: 이메일이 존재할 때와 존재하지 않을 때 오류 메시지가 다른가? 다르면 공격자가 실제 계정을 식별할 수 있다.
  • 응답 시간 차이: 비밀번호 오류 응답이 계정 없음 응답보다 느린가? 느리면 오류 메시지가 같아도 공격자가 타이밍으로 계정 존재를 알아낸다.

happy path는 코드가 무엇을 하는지 보여주고, 실패 경로는 무엇을 틀리는지 보여준다.

6. 한 문장으로 요약하라 (Write the Trace in One Sentence)

읽은 것을 자신의 메모에 한 문장으로 기록한다. 로그인 예시라면:

이메일로 사용자를 조회하고, 제출된 비밀번호를 저장된 해시와 비교하고, user ID로 JWT에 서명한 뒤 반환한다.

한 줄로 압축이 안 된다면 코드를 이해한 게 아니라 그냥 본 것이다.

전체 전사 펼치기

제가 요즘 계속 생각해온 질문이 있습니다.

Claude(클로드)나 Cursor(커서)가 대부분의 코드 초안을 작성해주는 세상에서, 코드를 읽는 능력이 코드를 쓰는 능력보다 더 가치 있어지는 걸까요?

솔직히 말하면 그렇다고 생각합니다.

코드를 작성하는 비용은 매달 점점 낮아지고 있습니다. 코드를 이해하고 모델이 놓친 엣지 케이스를 잡아내는 건 여전히 어렵습니다.

문제는 이겁니다. 대부분의 엔지니어는 코드를 작성하도록 훈련받았지, 낯선 코드를 읽도록 훈련받지 않았습니다. 코드를 읽으라고 하면 파일 위에서 아래로 책처럼 스크롤합니다. 몇 분이 지나도 무슨 일이 벌어지는지 모릅니다.

간단한 로그인 엔드포인트 예제로 보여드리겠습니다. 거의 모든 백엔드에 이런 코드가 있습니다. 세 개 파일, 50~60줄 이하의 코드로, 어떤 실제 코드베이스에서도 적용할 수 있는 6가지 기법을 살펴봅니다.

첫 번째: 파일 맨 위가 아니라 진입점(entry point)부터 시작하세요. 유저 모델이나 미들웨어 폴더를 그냥 열지 마세요. 들어오는 요청을 처리하는 코드 라인을 찾으세요. 우리 예제에서는 routes/auth.js 안의 app.post('/login')입니다. 거기가 외부 세계가 이 코드로 들어오는 지점입니다. 여기서부터 호출을 따라 나가세요. 코드는 누가 무엇을 호출하는지의 그래프이지, 위에서 아래로 읽는 이야기가 아닙니다.

두 번째: 로그인을 처리하는 함수를 열기 전에, 테스트 케이스를 먼저 읽으세요. auth.test.js를 열고 happy path 테스트를 찾으세요. 이메일과 비밀번호를 POST하고 200 상태코드와 응답 본문에 토큰이 있길 기대하는 5줄짜리 테스트가 있을 겁니다. 이게 테스트 케이스 기준의 계약입니다. 자격증명을 넣으면 토큰이 나오는 것이죠. 테스트가 전부를 말해주진 않지만, 소스 코드를 읽기 전에 출발점을 줍니다.

세 번째: 이제 로그인 핸들러를 열고 함수가 아닌 데이터를 따라가세요. 중요한 변수는 user입니다. user의 여정을 추적하세요. 요청에서 온 이메일로 User.findByEmail을 호출할 때 생성됩니다. 제출된 비밀번호는 bcrypt.compare로 user.passwordHash와 비교됩니다. user.id는 서명된 JWT 토큰으로 패킹됩니다 — 보통 만료일도 함께 들어갑니다. 그 토큰이 응답으로 반환됩니다. 이게 핵심 로그인 흐름이고, 약 30초 안에 이해할 수 있습니다.

네 번째: 첫 패스에서 필요 없는 것은 건너뛰세요. rate limiter, audit log 호출, 그 외 validator들을 그냥 지나갔습니다. 요청을 변경하거나, 흐름을 차단하거나, 조사 중인 버그를 설명하지 않는다면 건너뛰어도 됩니다. 미들웨어와 validator는 핸들러가 실행될지 여부를 결정하기 때문에 영원히 건너뛸 수는 없습니다 — 다만 아직 전체 구조를 파악하는 동안만 보류하는 겁니다. 대부분의 엔지니어가 바로 여기서 실패합니다. 헬퍼를 만나면 의무감에 바로 파고들었다가 불필요한 곳에 너무 많은 시간을 씁니다.

다섯 번째: happy path가 명확해지면 실패 경로 하나를 정확히 읽으세요. 로그인이라면 두 가지 간단한 질문을 할 수 있습니다. 첫 번째 질문: 이메일이 존재하는 경우와 존재하지 않는 경우에 오류 메시지가 다른가요? 다르다면 공격자가 어떤 계정이 실제인지 쉽게 식별할 수 있습니다. 두 번째 질문: 비밀번호 오류 응답이 사용자 없음 응답보다 더 오래 걸리나요? 응답 시간이 다르다면 공격자가 그 차이를 측정해서, 오류 메시지가 동일하더라도 어떤 이메일이 등록돼 있는지 알아낼 수 있습니다. happy path는 코드가 무엇을 하는지 보여주고, 실패 경로는 무엇을 틀리는지 보여줍니다.

여섯 번째 — 아무도 안 하는 것입니다. 자신의 메모에 방금 추적한 흐름을 한 문장으로 적으세요. 로그인이라면 이렇게 쓸 수 있습니다: "이메일로 사용자를 찾고, 저장된 해시에 비밀번호를 검증하고, user ID로 JWT에 서명한 뒤 반환한다." 방금 읽은 것을 한 줄로 압축할 수 없다면, 이해한 게 아니라 그냥 본 겁니다.

다음에 코드를 읽을 때 쓸 수 있는 간단한 멘탈 모델을 드렸으면 합니다. 시청해 주셔서 감사합니다.
