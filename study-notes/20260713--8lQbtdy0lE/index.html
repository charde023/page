핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
사전 사고(Up-front thinking) 에이전트가 엉뚱한 방향으로 구현하는 시간을 줄인다 시작 전에 원하는 결과, 제약, 검증 기준을 더 명확히 해야 한다
에이전트 감시 줄이기 사람이 계속 지켜보면 자동화의 장점이 사라진다 구현 과정이 아니라 검증 가능한 결과물을 보도록 워크플로를 바꾼다
시각 검증(Visual verification) UI 버그나 전후 차이를 빠르게 판단할 수 있다 버그 상태와 수정 후 상태를 영상이나 GIF로 비교한다
격리 작업 환경(Crabbox) 에이전트가 안전하게 작업하고 자동화 결과를 만들 수 있다 독립된 환경에서 구현, 테스트, 시각 자료 생성을 맡긴다
병합 판단(Merge decision) 최종 책임은 사람에게 남는다 에이전트 결과를 보고 문제가 해결됐으면 병합한다

내가 모를 만한 것 / 처음 보는 것

  • 크랩박스(Crabbox) — 에이전트가 격리된 환경에서 코드를 실행하고 결과물을 만들 수 있게 해주는 작업 환경으로 언급됨.
  • 클로드(Claude) — Anthropic의 AI 모델. 화자는 예전에는 원하는 대로 작동하지 않아 답답했다고 말함.
  • 시각 검증(Visual verification) — 테스트 결과를 텍스트 로그만 보는 것이 아니라, 수정 전후 화면을 이미지·영상·GIF로 확인하는 방식.
  • 병합(Merge) — 코드 변경 사항을 메인 브랜치나 기준 코드에 반영하는 작업.
  • GIF 생성 — GitHub에서는 영상 표시가 제한적일 수 있어, 전후 상태를 보여주는 짧은 GIF로 대체할 수 있다는 맥락.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. “1년 전쯤”에는 클로드(Claude)에게 소리칠 정도였다고 표현 — 초창기에는 모델이 원하는 대로 움직이지 않아 사람이 계속 개입해야 했다는 의미.
  2. 지금은 “앞에서 더 많이 생각한다”는 방식으로 바뀜 — 구현 중간 감시보다 요구사항 정리와 방향 설정이 더 중요해졌다는 뜻.
  3. 구현에는 “1시간, 10시간”이 걸릴 수 있다고 말함 — 에이전트 작업 시간이 길어져도 사람이 계속 붙어 있을 필요는 없다는 맥락.
  4. 크랩박스(Crabbox)가 있으면 비디오를 만드는 프롬프트를 쉽게 구현할 수 있다고 언급 — 코드 결과를 시각적으로 확인하는 자동화가 가능하다는 예시.
  5. GitHub에서는 영상이 잘 작동하지 않아 GIF를 만들 수 있다고 말함 — 협업 도구에서 결과를 공유하기 쉬운 포맷으로 바꾸는 실용적 디테일.
  6. “버그가 여기 있고, 수정이 여기 있다”를 직접 확인한 뒤 병합(Merge) — 최종 판단은 사람이 하되, 판단 자료를 에이전트가 준비하게 한다.

# 섹션 요지
1 초기의 문제 모델이 원하는 대로 움직이지 않아 계속 감시하고 개입해야 했다
2 방식의 변화 구현 중간을 지켜보기보다 시작 전에 방향과 조건을 더 깊게 정리한다
3 자동 검증 Crabbox를 이용해 전후 화면을 영상·GIF로 만들어 시각적으로 검증한다
4 최종 판단 사람이 결과를 보고 버그와 수정 여부를 확인한 뒤 병합한다

1. 초기에는 에이전트를 계속 감시해야 했다

화자는 처음 AI 코딩 에이전트를 쓸 때 상당히 답답했다고 말한다. 모델이 원하는 대로 작동하지 않았고, 심지어 클로드(Claude)에게 소리칠 정도였다고 표현한다.

여기서 핵심은 AI 모델 자체가 “마법처럼 알아서” 일하는 것이 아니라는 점이다. 초기에 요구사항이 애매하거나, 검증 기준이 부족하거나, 작업 환경이 정리되어 있지 않으면 에이전트는 엉뚱한 방향으로 구현할 수 있다.

그래서 사람은 계속 화면을 보며 “그거 아니야”, “다시 해”, “이 파일 말고 저 파일”처럼 개입하게 된다. 이러면 AI 에이전트를 쓰는 장점이 크게 줄어든다.

2. 지금은 시작 전에 더 많이 생각한다

화자는 현재 방식이 “앞에서 더 많이 생각하는 것”으로 바뀌었다고 말한다. 즉, 코딩 에이전트가 작업을 시작하기 전에 다음을 더 명확히 한다는 뜻이다.

  • 무엇을 고쳐야 하는가
  • 어떤 결과가 맞는가
  • 어떤 제약을 지켜야 하는가
  • 어떤 방식으로 검증할 것인가
  • 수정 전후를 어떻게 비교할 것인가

이렇게 하면 에이전트가 실제 구현에 1시간 또는 10시간을 쓰더라도, 사람이 계속 옆에서 지켜볼 필요가 줄어든다.

핵심은 에이전트가 오래 일하는 것 자체가 문제가 아니라, 사람이 그 시간을 계속 감시해야 하는 것이 문제라는 점이다.

3. Crabbox로 결과 검증 자료를 자동 생성한다

화자는 크랩박스(Crabbox)가 있으면 프롬프트를 통해 비디오를 만드는 기능도 쉽게 구현할 수 있다고 말한다. 이 기능의 목적은 단순히 멋진 영상을 만드는 것이 아니라, 수정 전후 상태를 비교하기 위한 것이다.

예를 들어 UI 버그를 고친다고 하면 다음처럼 볼 수 있다.

  • 수정 전 화면: 버그가 보이는 상태
  • 수정 후 화면: 버그가 해결된 상태
  • 비교 자료: 영상 또는 GIF

GitHub에서는 영상이 잘 동작하지 않을 수 있으므로 GIF로 만들 수 있다고 언급한다. 즉, 협업 도구에서 바로 확인 가능한 형태로 결과를 남기는 것이다.

이 방식은 특히 프론트엔드, 관리자 페이지, 상품 상세 페이지, 장바구니, 결제 흐름처럼 눈으로 봐야 확실한 문제에 유용하다.

4. 사람은 최종 검증과 병합만 한다

화자의 최종 흐름은 간단하다.

  1. 에이전트에게 명확한 작업 지시를 준다.
  2. 에이전트가 격리 환경에서 구현한다.
  3. 에이전트가 수정 전후 화면을 영상이나 GIF로 만든다.
  4. 사람은 그 결과를 보고 “여기에 버그가 있었고, 여기에 수정이 됐다”고 확인한다.
  5. 문제가 해결됐으면 병합(Merge)한다.

이 방식의 장점은 사람이 구현 중간을 계속 감시하지 않아도 된다는 점이다. 대신 사람은 최종 판단자 역할을 한다.

차드의 업무에 비유하면, 물류 직원이 일하는 모든 순간을 CCTV로 감시하는 것이 아니라, 출고 전 검수표와 사진 증빙을 보고 승인하는 방식에 가깝다. AI 에이전트도 마찬가지로, 중간 과정을 일일이 감시하기보다 검증 가능한 결과물을 제출하게 만들어야 한다.

종합 체크리스트

  • [ ] AI 에이전트에게 작업을 맡기기 전에 원하는 결과와 금지 조건을 먼저 적는다.
  • [ ] “어떻게 확인하면 완료로 볼 것인가”를 프롬프트에 포함한다.
  • [ ] UI 작업이라면 수정 전후 스크린샷, 영상, GIF 생성을 요구한다.
  • [ ] 구현 로그보다 사용자가 볼 결과 화면을 우선 확인한다.
  • [ ] 에이전트 작업은 격리 환경에서 실행되도록 구성한다.
  • [ ] 최종 병합 전에는 사람이 직접 버그 위치와 수정 결과를 확인한다.
