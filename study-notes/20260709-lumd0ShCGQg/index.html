이제 무엇을 만들어야 할까요? — Theo Browne, @t3dotgg

한 줄 요약

AI 모델이 단순 코딩 도구를 넘어 작업을 끝까지 수행하는 에이전트(agent)가 되면서, 개발자는 언어·터미널·기존 관행에 대한 집착을 버리고 더 크고 더 넓은 제품을 만들어야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
모델 세대 변화 AI가 단순 코드 생성에서 장시간 작업 수행과 조율로 발전했다 Sonnet 3.5는 도구 호출, Opus 4.5는 장시간 작업, Mythos는 오케스트레이션 시대를 상징한다
개발자 정체성의 해체 언어·터미널·프레임워크 집착이 새 시대의 사고를 막을 수 있다 “나는 JavaScript 개발자다” 같은 정체성보다 문제 해결 능력이 중요해진다
스큐어모피즘(skeuomorphism) 새 기술을 옛 도구의 모양으로만 이해하면 가능성을 제한한다 지금 개발자는 터미널과 Git 같은 기존 방식에 과도하게 묶여 있다
매몰비용(sunk cost) 코드에 들인 시간이 아까워 나쁜 결정을 유지하기 쉽다 AI 에이전트 시대에는 지우고 다시 만드는 비용이 훨씬 낮아진다
마크다운 파일 제품 간단한 자동화가 이제 서비스나 스타트업 수준의 일을 할 수 있다 마크다운(markdown) 지시문을 Claude·Codex에 주기적으로 실행하면 작은 제품이 된다
제품의 깊이와 넓이 AI 덕분에 스타트업이 예전보다 더 넓은 범위를 다룰 수 있다 이제는 특정 기능을 깊게 파는 것뿐 아니라 제품 범위를 넓히는 전략도 가능하다

내가 모를 만한 것 / 처음 보는 것

  • Sonnet 3.5 — Anthropic의 Claude 계열 모델 중 하나로, 화자는 실무 코딩에 안정적으로 쓸 수 있었던 전환점으로 본다.
  • Opus 4.5 — 화자가 장시간 작업 수행 능력의 큰 도약으로 언급한 모델. 실제 모델명은 전사 기준이며 맥락상 Claude Opus 계열을 의미한다.
  • Mythos / Fable — 화자가 언급한 최신 모델명. 실제 공개 모델명 여부는 맥락상 확인 필요.
  • 도구 호출(tool call) — AI가 텍스트만 생성하는 것이 아니라 파일 읽기, 코드 실행, 검색, API 호출 같은 도구를 사용하는 기능.
  • 오케스트레이션(orchestration) — 하나의 AI가 작업을 여러 하위 작업으로 나누고, 다른 모델이나 에이전트를 동원해 조율하는 방식.
  • 스큐어모피즘(skeuomorphism) — 디지털 제품을 실제 물건처럼 보이게 디자인하는 방식. 예전 iOS의 나침반·책장 UI가 예시다.
  • 매몰비용 오류(sunk cost fallacy) — 이미 투입한 시간·비용 때문에 잘못된 선택을 계속 유지하는 심리.
  • Cron — 정해진 시간마다 명령이나 스크립트를 실행하는 스케줄러.
  • S3 — Amazon Simple Storage Service. 정적 파일이나 데이터를 저장하고 URL로 제공할 수 있는 AWS 서비스.
  • Vercel — 프론트엔드와 풀스택 웹 배포에 특화된 플랫폼.
  • RDS — AWS의 관리형 관계형 데이터베이스 서비스.
  • Slack bot API — Slack 안에서 봇이나 자동화 기능을 만들 수 있게 하는 API.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Sonnet 3.5를 “크렘 드 라 크렘”, 즉 당시 최고 모델로 표현했다 — 단순히 성능이 좋았다는 뜻이 아니라, 실무 코딩에서 여러 단계 작업을 맡길 수 있다고 느낀 첫 순간이었다.
  2. Opus 4.5에서 화자의 “AI 정신증”이 시작됐다고 말했다 — 코드 작성뿐 아니라 테스트와 마무리까지 해내며 몇 분이 아니라 몇 시간짜리 작업을 처리한다고 봤다.
  3. Mythos는 코드베이스뿐 아니라 “자기 자신을 이해한다”고 표현했다 — 하위 모델을 생성(spawn)하고 작업을 나누고 검증하는 오케스트레이션 능력을 강조한 말이다.
  4. 과거 직장에서 닫았던 대부분의 Jira 티켓은 Opus 4.5 수준 모델이면 쉽게 해결됐을 것이라고 했다 — 단순 티켓 처리 업무의 가치가 낮아졌다는 지적이다.
  5. 개발자 경력 10년 이상인 청중에게 손을 들게 했다 — 오래된 개발자일수록 도구와 관행에 대한 고정관념이 강하다는 흐름으로 연결했다.
  6. iOS 6 이전과 iOS 7 이후의 나침반 앱을 비교했다 — 예전 UI는 실제 나침반을 흉내 냈고, iOS 7 이후는 정보 전달과 사용성에 집중했다는 예시다.
  7. “환경 파일(environment files)을 왜 Git에 커밋하면 안 되느냐”는 질문을 던졌다 — 기존 보안·협업 관행을 무조건 당연시하지 말자는 논점이다.
  8. “죄책감 병합(guilt-merge)”이라는 표현을 썼다 — 누군가 1~2주 들인 PR이라서 방향이 틀려도 병합해버리는 개발팀의 심리를 비판했다.
  9. Reddit 스크래퍼(scraper)는 2~3일짜리 사이드 프로젝트였다고 했다 — 프로그래밍 밈을 가져와 트위터에 올리기 위한 개인 자동화였다.
  10. Y Combinator에서 진행한 스타트업은 Peng, 설명상 “스트리머용 Zoom(Zoom for Streamers)”이었다 — OBS에서 고품질 협업을 쉽게 하는 도구였다.
  11. 아침 9시 cron으로 마크다운 파일을 실행하고, 9:15~9:20쯤 그날 할 일이 생성된다고 했다 — Claude나 Codex에 지시문을 파이프해 PR 상태를 정리하고 HTML을 S3에 올리는 자동화다.
  12. “너무 큰 것(too big)”의 기준을 더 이상 모르겠다고 했다 — 자체 모델 학습, 운영체제 개발, NPM·Node와 경쟁 같은 예시를 들었다.
  13. Vercel은 AWS만큼 넓지는 않지만 특정 영역에서 깊다고 설명했다 — 프론트엔드 개발자에게는 훨씬 최적화된 경험을 준다는 의미다.
  14. 이제는 하루 이틀 작업으로 제품 안에 데이터베이스 플랫폼 같은 것을 붙일 수 있다고 했다 — RDS급 신뢰성을 말하는 것이 아니라, 사용자가 시작할 수 있을 만큼의 범위를 말한다.
  15. Slack은 의도치 않게 에이전트 실행 플랫폼이 되었다고 했다 — 완벽한 제품이라서가 아니라, 봇 API와 대화형 구조가 사용자가 확장하기 좋은 “형태”였기 때문이다.

# 섹션 요지
1 AI 모델의 세대 변화 Sonnet 3.5, Opus 4.5, Mythos를 거치며 AI는 도구 호출에서 장시간 작업, 오케스트레이션으로 발전했다
2 더 크게 가야 하는 이유 모델이 빨리 발전하므로 개발자는 더 어려운 문제와 더 큰 제품 범위를 시도해야 한다
3 개발자의 낡은 정체성 언어, 터미널, Git, 프레임워크에 대한 집착은 새 가능성을 제한한다
4 코드를 지우지 못하는 문제 매몰비용 때문에 나쁜 코드와 PR을 유지하는 문화가 있다
5 제품 단계의 하향 이동 예전 스타트업급 아이디어가 이제는 사이드 프로젝트가 될 수 있다
6 마크다운 파일이 제품이 되는 시대 지시문과 AI 실행만으로 자동화 서비스가 만들어진다
7 깊이보다 넓이 AI 덕분에 스타트업도 예전보다 훨씬 넓은 범위를 다룰 수 있다
8 지금 만들 것 바보 같아 보일 만큼 큰 아이디어가 오히려 충분히 큰 아이디어다

1. AI 모델의 세대 변화: 도구 호출에서 오케스트레이션까지

Theo Browne는 자신의 최근 상태를 “AI 정신증”이라고 농담처럼 표현한다. 그만큼 AI 모델 발전 속도가 개발자의 사고방식을 흔들고 있다는 뜻이다.

그는 모델 발전을 세 단계로 나눈다.

첫 번째는 Sonnet 3.5다. 이 모델은 단순한 코드 조각 생성이 아니라, 코드베이스 안에서 도구 호출(tool call)을 안정적으로 수행하며 실제 업무에 쓸 수 있는 수준이었다. 화자에게는 “이제 모델이 여러 단계 작업을 끝까지 할 수 있겠다”는 느낌을 준 전환점이었다.

두 번째는 Opus 4.5다. 이 단계에서는 모델이 몇 분짜리 작업이 아니라 몇 시간짜리 작업을 놓치지 않고 이어갈 수 있게 되었다. 코드를 작성하고, 도구를 호출하고, 테스트하고, 결과를 쓸 만한 상태로 만드는 능력이 크게 올라갔다.

세 번째는 Mythos다. 화자는 이 모델을 오케스트레이션(orchestration)의 단계로 본다. 단순히 코드베이스를 이해하는 것이 아니라, 자기 자신이 무엇을 할 수 있는지 이해하고, 필요하면 하위 모델을 만들어 작업을 나누고, 다시 검증할 수 있다는 것이다.

핵심은 모델이 좋아진 만큼 기존과 같은 작은 작업만 시키면 발전의 이점을 체감할 수 없다는 것이다.

2. 더 크게 가야 한다

화자는 이전 직장에서 처리했던 대부분의 Jira 티켓은 Opus 4.5 같은 모델이면 쉽게 풀 수 있었을 것이라고 말한다. 즉, 기존 개발자의 일상 업무 중 상당 부분은 이미 AI가 따라잡았거나 곧 따라잡을 수 있다는 뜻이다.

그렇다면 개발자가 해야 할 일은 무엇인가?

화자의 답은 단순하다. 더 커져야 한다.

모델은 개발자보다 빠르게 좋아지고 있다. 개발자가 같은 속도로 똑똑해질 수 없다면, 더 큰 문제를 정의하고 더 넓은 제품을 상상해야 한다. 작은 티켓 해결이나 단순 기능 구현에 머물면 모델 발전의 이점을 제대로 쓰지 못한다.

3. 개발자는 자기 자신을 넘어서야 한다

화자는 오래 코드를 써온 개발자일수록 도구와 관행에 강하게 묶여 있다고 말한다. 자신도 SSH, Git, GNU Screen, tmux 같은 도구를 오래 사용했고, 그것들이 워크플로에 깊이 박혀 있다고 인정한다.

하지만 바로 그 익숙함이 문제다.

개발자는 터미널, Vim, 프레임워크, 언어 같은 것을 자기 정체성처럼 여긴다. “나는 JavaScript 개발자다”, “저 사람은 JavaScript를 쓰니까 진짜 개발자가 아니다” 같은 태도는 기술 선택을 필요 이상으로 정체성화한 결과다.

화자의 관점에서 이런 구분은 예전에도 과장됐고, 지금은 더더욱 중요도가 낮아졌다.

4. 스큐어모피즘: 우리는 낡은 모양에 갇혀 있다

화자는 iOS 6 이전과 iOS 7 이후의 디자인 변화를 예로 든다.

과거 iPhone 앱은 실제 물건을 그대로 흉내 냈다. 나침반 앱은 실제 나침반처럼 보였고, 책 앱은 실제 책장과 종이책처럼 보였다. 이것은 사용자를 설득하기 위한 디자인이었다. “이 디지털 기기가 당신이 쓰던 물건을 대체할 수 있다”는 메시지가 필요했기 때문이다.

하지만 iOS 7 이후 Apple은 더 이상 그렇게 설득할 필요가 없었다. 사람들은 이미 iPhone이 여러 도구를 대체할 수 있다는 사실을 알고 있었다. 그래서 실제 물건을 흉내 내는 대신, 더 명확하고 유용한 인터페이스로 전환했다.

화자는 현재 개발자들이 바로 이 스큐어모피즘(skeuomorphism) 단계에 있다고 말한다.

우리는 터미널이 최고의 인터페이스인 것처럼 행동하지만, 사실 터미널은 자연어와 잘 맞는 인터페이스가 아니다. 그럼에도 개발자는 터미널이 익숙하고, 자신이 코딩하는 모습을 터미널과 연결해 상상하기 때문에 거기에 집착한다.

5. 왜 환경 파일은 Git에 못 넣는가

화자는 기존 개발 관행을 의심해보라고 한다.

예를 들어 “왜 환경 파일(environment files)은 Git에 커밋하면 안 되는가?”라고 묻는다. 물론 실제로는 비밀키나 보안 문제가 있기 때문에 주의가 필요하다. 하지만 화자의 핵심은 보안 규칙 자체를 부정하는 것이 아니라, 우리가 어떤 관행을 너무 당연하게 받아들이는 태도를 지적하는 것이다.

프로젝트의 다른 파일은 모두 Git으로 공유하면서, 특정 설정 파일만 별도 시스템으로 공유해야 한다면 그것이 정말 최선인지 다시 생각해보자는 것이다.

Git은 특정 목적을 위해 만들어졌고, 이후 업계를 장악했다. 문제는 Git이 업계를 장악한 것뿐 아니라, 개발자의 사고방식까지 장악했다는 점이다.

6. 코드를 지우지 못하는 개발 문화

화자는 개발 업계에 매몰비용(sunk cost) 사고가 강하다고 말한다.

어떤 해결책은 그냥 지우고 다시 시작하는 것이 맞다. 하지만 누군가 1~2주 동안 작업한 PR이라면, 방향이 조금 틀려도 병합해버리는 일이 생긴다. 화자는 이것을 “죄책감 병합(guilt-merge)”이라고 부른다.

AI 에이전트의 장점 중 하나는 여기서 드러난다. 에이전트가 만든 결과물이 틀렸다면, 우리는 사람에게 미안해할 필요 없이 버릴 수 있다. 즉, 코드를 지우는 심리적 비용이 낮아진다.

개발자가 앞으로 배워야 할 것은 코드를 더 많이 쓰는 능력만이 아니다. 필요할 때 과감히 버리고 다시 시도하는 능력이다.

7. 사이드 프로젝트, 스타트업, 그리고 너무 큰 것

화자는 자신이 만들었거나 만들고 있는 세 가지 아이디어를 소개한다.

첫째, Reddit 스크래퍼(scraper)다. 프로그래밍 밈을 Reddit에서 가져와 보기 좋게 정리하고 Twitter에 올리기 위한 도구였다. 2~3일짜리 사이드 프로젝트였다.

둘째, “스트리머용 Zoom”인 Peng이다. Y Combinator에서 진행한 스타트업으로, 라이브 콘텐츠 제작자가 OBS 안에서 더 쉽게 고품질 협업을 하도록 돕는 제품이었다.

셋째, Full Stack Cloud다. Vercel처럼 시작하지만 인증(auth), 데이터베이스(database) 등 더 넓은 방향으로 확장된 플랫폼을 상상한 것이다.

예전 기준으로는 첫 번째가 사이드 프로젝트, 두 번째가 스타트업, 세 번째는 “너무 큰 것”이었다. 하지만 AI 모델이 커지면서 이 단계가 한 칸씩 내려왔다고 말한다.

즉, 예전의 스타트업은 이제 사이드 프로젝트가 될 수 있다. 예전에는 너무 크다고 느껴졌던 아이디어도 이제는 시도 가능한 스타트업이 될 수 있다.

8. 마크다운 파일이 제품이 되는 시대

화자는 아주 중요한 변화를 말한다. 어떤 회사의 전체 제품이 사실상 마크다운 파일(markdown file) 하나로 대체될 수 있다는 것이다.

예를 들어 그는 자신의 PR을 정리하고 우선순위를 매기는 서비스를 만들었는데, 이제는 그것이 마크다운 파일이 되었다고 말한다.

지시문은 대략 이렇다.

GitHub 저장소 네 개에 들어가서 열려 있는 PR을 확인하고, 현재 작업 상태를 파악하고, 우선순위를 정리한 뒤, 정적 HTML 파일을 업데이트하고, S3에 올린 다음 URL을 알려달라는 것이다.

이 마크다운 파일은 매일 아침 9시에 cron으로 실행된다. 9시 15분에서 20분쯤 되면 그날 해야 할 일이 생성된다.

이 사례의 핵심은 AI에게 실행 가능한 지시문을 주기적으로 돌리는 것만으로 작은 서비스가 만들어진다는 점이다.

9. 더 큰 것이 아니라 더 넓게 생각하기

화자는 “더 크게 생각하라”는 표현이 정확하지 않을 수 있다고 말한다. 오히려 지금 필요한 것은 더 넓게(wider) 생각하는 것이다.

소프트웨어에는 두 축이 있다.

하나는 넓이(breadth)다. 제품이 다루는 영역의 범위다.

다른 하나는 깊이(depth)다. 특정 영역에서 제공하는 기능의 세밀함이다.

예를 들어 Vercel은 AWS만큼 넓지 않다. AWS처럼 모든 클라우드 기능을 제공하지 않는다. 하지만 프론트엔드와 풀스택 웹 배포 영역에서는 훨씬 깊고 특화된 경험을 제공한다.

예전 스타트업은 AWS처럼 넓게 경쟁할 수 없었다. 수천 명의 엔지니어를 가진 회사와 기능 범위로 싸우는 것은 말이 되지 않았기 때문이다.

하지만 AI 덕분에 상황이 바뀌었다. 이제는 작은 팀도 훨씬 넓은 범위를 시도할 수 있다.

10. 사용자가 스스로 빈칸을 채우게 하라

화자는 “RDS만큼 안정적인 데이터베이스를 하루 이틀 만에 만들 수 있다”는 뜻으로 말하는 것이 아니라고 선을 긋는다. 대신 제품 안에 사용자가 시작할 수 있을 정도의 데이터베이스 플랫폼은 충분한 프롬프트와 노력으로 빠르게 붙일 수 있다고 말한다.

중요한 것은 모든 기능을 완벽하게 직접 만드는 것이 아니다.

제품 구조를 잘 설계하면, 사용자가 필요한 기능을 스스로 만들 수 있다. 즉, 제품은 완성된 기능 묶음이 아니라 사용자가 확장할 수 있는 형태가 되어야 한다.

Slack이 그 예다. 화자는 Slack을 좋은 제품이라고 보지는 않지만, Slack의 형태는 사람들이 에이전트와 자동화를 올리기에 적합했다고 말한다. Slack bot API가 어느 정도 작동했기 때문에, 사람들은 Slack을 자신들이 원하는 기능을 실행하는 플랫폼처럼 사용하게 되었다.

11. 지금 만들어야 할 것

화자의 결론은 도발적이다.

이제는 Slack과 경쟁하고, 자신만의 AWS를 만들고, Salesforce에 직접 도전하는 식의 아이디어도 생각해볼 수 있다.

물론 이런 말은 바보 같아 보인다. 하지만 화자는 이렇게 말한다.

아이디어가 바보 같아 보이지 않는다면, 충분히 크지 않은 것이다.

AI 시대에는 과거 기준의 현실적인 아이디어가 오히려 너무 작을 수 있다. 개발자는 익숙한 도구, 익숙한 정체성, 익숙한 제품 규모에서 벗어나야 한다.

전체 전사 펼치기

안녕하세요. 여기서 여러분을 보게 되어 정말 반갑습니다. 제가 이런 무대에 서도 된다는 게 아직도 믿기지 않습니다. 저는 그냥 유튜버인 것 같은데요. 그래도 제가 요즘 어떤 생각을 하고 있는지 나누고 싶습니다.

솔직히 말하면 저는 약간의 “AI 정신증” 같은 상태를 겪고 있습니다. 지금 자기 상태가 일종의 AI 정신증에 가깝다고 느끼는 분 있나요? 손 한번 들어보세요.

아직 손을 들지 않은 분들도 걱정하지 마세요. 제가 제대로만 한다면 이 발표가 끝날 때쯤 여러분도 그렇게 될 겁니다.

이 이야기를 하려면 제 개인적인 여정부터 조금 이야기해야 합니다. 요즘 시대의 흐름답게 모델의 변화에 맞춰 설명해보겠습니다.

Sonnet 3.5를 당시 최고 모델로 써본 분 있나요? 이전에 쓰던 것보다 믿기 어려울 정도로 좋았죠. 여러 모델을 도구 안에서 써보던 입장에서 Sonnet 3.5는 제게 큰 전환점이었습니다. 갑자기 모델이 훨씬 더 많은 작업을 처음부터 끝까지 처리할 수 있게 느껴졌습니다. 실제로 여러 단계가 필요한 일을 해낼 수 있었으니까요.

그다음 Opus 4.5가 나왔습니다. Opus 4.5로 바꿨을 때 큰 도약을 느끼지 못한 분 있나요? 손이 많지 않아서 다행입니다. 아마 제 AI 정신증은 작년 11월과 12월쯤 Opus 4.5를 쓰면서 시작된 것 같습니다. 이 모델은 단지 코드를 쓰고 도구를 호출하는 수준이 아니었습니다. 훨씬 더 멀리 갔습니다. 작업을 테스트하고, 실제로 꽤 좋은 상태까지 만들고, 몇 분이 아니라 몇 시간이 걸리는 작업을 끝낼 수 있었습니다. 믿기 어려웠습니다.

그리고 Mythos가 나왔습니다. Mythos와 Fable을 써본 분 있나요? 꽤 훌륭한 모델이라는 데 동의하시죠? 그런데 왜 그럴까요? 단순히 코딩을 더 잘해서는 아닙니다. 예전에 다른 모델에게 줬던 것과 같은 프롬프트를 주면 그렇게 다르게 느껴지지 않을 수도 있습니다.

저는 이제 이런 모델들을 거의 시대별로 생각합니다. Sonnet 3.5는 도구 호출(tool call)의 시대였습니다. 물론 도구 호출을 처음 한 모델이라는 뜻은 아닙니다. 코드베이스 안에서 매일 코딩 업무에 쓸 만큼 일관되고 안정적으로 도구 호출을 해낸 첫 모델이었다는 뜻입니다.

Opus 4.5는 훨씬 더 오래 걸리는 작업을, 자신이 무엇을 하고 있는지 놓치지 않고 수행할 수 있었습니다. 더 이상 “1단계 만들어줘”, “그다음 이 부분 만들어줘”, “그다음 이것도 해줘”라고 나눠 말할 필요가 줄었습니다. 원하는 것을 말하면 모델이 상당 부분 알아서 파악했습니다.

Mythos는 오케스트레이션(orchestration)으로의 또 다른 도약입니다. 제게는 이 모델이 단순히 코드베이스를 이해하는 것이 아니라, 자기 자신도 이해하는 첫 모델처럼 느껴집니다. 추가 모델을 생성하고, 작업을 나누고, 더 안정적으로 완료한 뒤 검증하는 방법을 압니다. 그리고 그렇게 하라고 말하면 그냥 합니다. 특별한 커스텀 도구나 시스템, 거창한 소프트웨어 공장이 필요하지 않습니다. 조금 더 멀리 가보라고 프롬프트를 주면 됩니다. 어디까지 갈 수 있는지 보면 놀랄 겁니다.

제가 말하려는 것은 우리가 더 크게 가야 한다는 것입니다. 앞으로 모델의 이점을 보려면 모델을 더 밀어붙이고, 여러분 자신도 만드는 것의 규모를 더 밀어붙여야 합니다. 제가 이전 직장에서 닫았던 대부분의 Jira 티켓은 Opus 4.5 같은 모델이면 아주 쉽게 해결할 수 있었을 겁니다. 제 이전 업무는 Mythos 같은 모델의 이점을 제대로 살릴 수 없었을 겁니다.

모델이 계속 좋아질 것인가? 저는 이제 그렇다고 자신 있게 말할 수 있습니다. 예전에 제가 모델이 벽에 부딪히고 있다고 말한 것은 틀렸습니다. 모델은 우리보다 더 빨리 좋아지고 있습니다. 우리가 같은 속도로 더 나아질 수 없다면, 대신 더 크게 가야 합니다.

그러기 위해서는 우리 자신을 넘어서야 합니다. 오랫동안 소프트웨어를 작성해온 사람으로서 이것은 제게도 정말 어려웠습니다. 10년 넘게 코드를 써온 분 있나요? 손 들어보세요. 여기 있는 대부분이 그렇군요. 저는 제가 얼마나 오래 코드를 써왔는지 생각하고 싶지도 않습니다. 하지만 시작한 이후로 강한 의견들을 계속 쌓아왔습니다.

저는 예전에 GNU Screen을 썼고, 나중에는 tmux를 썼습니다. 코드를 쓰기도 전에 SSH와 Git 안에서 이런 도구들을 쓰는 법을 배웠습니다. 그리고 이런 것들은 제 워크플로에 깊이 박혀 있습니다.

조금 이상하게 들릴 수 있지만, 옛날 이야기를 해보겠습니다. 잠깐 iOS 이야기를 해야 합니다. iPhone이 이런 모습이던 시절, 그러니까 iOS 6 이전에 iPhone을 갖고 있던 분 있나요? 그런데 어떻게 여러분 중 4분의 1 정도만 그 나이대인데 10년 넘게 코드를 쓴 사람이 이렇게 많죠? 혼란스럽네요. 아마 다들 Android 사용자였기를 바랍니다.

예전 iPhone 앱은 이렇게 생겼습니다. 지금 앱과는 다르다는 것을 알 수 있을 겁니다. 앱이라기보다 누군가 나침반 사진을 찍어서 휴대폰 안에 넣어둔 것처럼 보입니다. 그게 당시 앱의 모습이었습니다.

그런데 지금은 이렇게 생겼습니다. 많은 사람은 이것을 보고 “명백한 다운그레이드다, 훨씬 나쁘다, Apple이 왜 저랬을까?”라고 말합니다.
