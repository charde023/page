내가 모를 만한 것 / 처음 보는 것

  • Labs Team (Anthropic): 차기 주력 제품 프로토타이핑 전담 팀. 현재 부활해 운영 중.
  • product overhang: 모델 능력은 충분한데 그 능력을 포착하는 제품이 없는 상태. 2024년 중반 Claude가 처했던 상황.
  • plan mode: Claude Code 내 계획 수립 전용 모드. 구현 전에 계획만 먼저 작성.
  • Co-work (Claude Co-work): 터미널 없이 Claude Code 기능을 쓸 수 있는 데스크탑 앱. 약 8~9일 만에 Claude Code로 100% 빌드.
  • Hofstadter, Douglas: Gödel, Escher, Bach 저자. 패턴 인식이 인지의 근본이라고 주장. Boris가 "코딩이 AI 연구에 적합한 이유"를 설명할 때 인용.
  • AppleScript: macOS 자동화 스크립팅 언어. Claude가 배시 도구로 자발적으로 작성해 음악 재생 정보를 가져온 사례.
  • log-linear chart: Y축을 로그 스케일로 설정해 지수 성장을 직선으로 표현. Anthropic 내부 대부분의 지표가 이 형태.
  • Member of Technical Staff: Anthropic의 직함 체계. 직군·시니어리티를 감추고 동등한 출발선을 만드는 문화 장치.
  • functional programming (Haskell, Scala): Boris가 선호했으나 모델이 클래스로 코드를 쓰기 시작하면서 포기한 코딩 철학.
  • YC (Y Combinator): Boris가 2010~2011년 초창기 배치 회사에 첫 번째 입사. "사용자가 원하는 걸 만들어라" 철학을 내면화.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Claude Code가 코드를 쓰기 시작한 전환점은 2024년 5월 Sonnet 4 + Opus 4 릴리스였다. 이전엔 10~20%만 작성.
  2. Anthropic 엔지니어 1인당 코드 생산량이 Claude Code 출시 이후 3X 증가 (이 수치도 이미 구식이라 "훨씬 높다"고 언급).
  3. 신입 온보딩이 과거 수주 → 현재 2일로 단축. "데이터베이스 쿼리하는 법?" → "Claude Code 켜고 Claude한테 시켜"가 표준 답변.
  4. Boris는 2024년 11월 IDE를 완전히 삭제(uninstall)했다. "한 달간 안 열었으니 지웠다."
  5. 현재 작업 방식: 수백 개의 Claude 인스턴스가 병렬 실행 중. Twitter 피드백·GitHub 이슈·Slack을 분석해 다음에 무엇을 빌드할지 판단.
  6. Co-work 출시 결정 트리거: 팀원 David가 처음으로 터미널을 연 다음 날 Co-work가 출시됨. "David가 터미널을 열었다 = 이제 메인스트림이다"로 해석.
  7. 슬랙 기반 프로토타입, 다양한 웹 기반 프로토타입이 모두 실패했다. 웹은 파일시스템 접근 불가 문제가 결정적.
  8. Boris는 원래 "코드베이스에 클래스 금지, 함수만" 규칙을 강제했으나 모델이 클래스를 쓰기 시작하자 포기. "결국 비즈니스 결과가 나오면 됐다."
  9. 조직 처방: 토큰 예산을 최대화하고, 인원은 의도적으로 부족하게. 자동화 강제가 복리 효과를 낸다.
  10. 현재 알파는 '제품 취향'이지만, 3~6개월 내 모델 아이디어의 대부분이 좋아질 것이라 예측. 최후의 인간 역할은 모델에게 가치관을 가르치는 것.
  11. Sonnet 3.5 시절, 도구 설명 없이 배시 도구를 넘겼더니 스스로 AppleScript를 작성해 음악 플레이어를 열었다.
  12. Anthropic 전사(재무·스태프·디자이너 포함)가 코드를 배포하고 있다고 언급. "Our finance guy ships code."

# 섹션 요지
1 탄생 배경 Labs Team 프로토타입에서 출발, 안전 연구가 코딩을 낳았다
2 초기 한계와 전환 10% 코드 작성 → 모델 점프로 100% 전환
3 Anthropic 코딩 문화 3X 생산성, 2일 온보딩, IDE 삭제
4 추상화 레벨 진화 프롬프트 → 루프 작성으로 이미 전환
5 채용 기준 변화 제너럴리스트, 직군 경계 붕괴, MTS 구조
6 Co-work 탄생 터미널 없는 UX, 8~9일 빌드, 파일시스템 접근이 핵심
7 조직 처방 인원 언더펀딩 + 토큰 오버펀딩
8 취향과 AI의 미래 취향도 결국 모델이 따라잡는다, 마지막 역할은 가치 교육

1. 탄생 배경 — "사고"가 낳은 제품

Boris가 2024년 말 Anthropic의 Labs Team에 합류했을 때, 팀의 미션은 "다음 대형 제품을 찾는 것"이었다. 동시에 프론티어 모델 발전을 밀어붙이되, 실제 제품이 있어야 모델이 무엇을 잘해야 하는지 알 수 있다는 닭-달걀 문제가 있었다.

Anthropic이 코딩에 집중한 이유는 전략적이다: - AI 안전 연구의 핵심 방법: 모델을 '페트리 접시'가 아니라 실제 세계에서 관찰해야 한다. - 코딩 = 모델의 자연어: 모델이 소프트웨어로 존재하는 한, 세계와 상호작용하는 방식은 코드다. - 명확한 정답/오답 구분: 컴파일·테스트 통과 여부로 품질을 측정할 수 있다. 영어 시는 무한히 올바른 버전이 있지만, 코드는 그렇지 않다. - 상업적 가치: 기업·스타트업 고객이 원하는 것 + 광고 없는 비즈니스 모델 유지 가능.

당시 시장 상황은 product overhang 상태였다. 모델은 할 수 있었는데 자동완성이나 Q&A 수준의 제품만 존재했다. "코딩 에이전트를 만들자"는 결정이 여기서 나왔다.

2. 초기 한계와 모델 점프

처음엔 Claude Code가 코드의 10~20%만 작성했다. 전환점은 모델이었다:

  • 2024년 5월: Sonnet 4 + Opus 4 출시 → 급격한 품질 향상
  • 2024년 11월: Opus 4.5 → Boris가 IDE를 삭제

하네스(CLI, 데스크탑 앱, 모바일 앱, iOS/Android, Slack 앱, GitHub 앱)도 지속 개선했지만, "코드 작성 비율의 계단식 상승"은 순전히 모델이 결정했다.

Anthropic 전 직원이 Claude Code를 매일 사용 → 모델 팀이 Claude Code로 모델을 만든다 → 그 모델이 Claude Code를 더 잘하게 된다는 내부 피드백 루프가 완성됐다.

3. Anthropic 코딩 문화 변화

Claude Code 출시 이후 Anthropic 내부 수치:

  • 엔지니어 1인당 코드량: 3X 이상 증가 (이미 낡은 수치, 실제는 더 높음)
  • 신입 온보딩: 수주 → 2일
  • Boris의 현재 워크플로우: IDE 없음, CLI 없음, 수백 개의 Claude 루프가 병렬 실행

"사람들이 '데이터베이스 어떻게 쿼리해요?' 물으면 정답은 Claude Code 켜고 시키는 것"

4. 추상화 레벨 진화

Boris는 코딩을 기술의 추상화 수준 상승으로 본다:

스위치 → 펀치카드 → 어셈블리 → COBOL/FORTRAN → Java → Python/JavaScript → 프롬프트 → 루프

현재 Boris의 단계: "나는 더 이상 Claude에게 직접 프롬프트하지 않는다. 루프를 작성한다. 루프가 Claude에게 프롬프트하고 판단한다."

5. 채용 기준과 조직 구조 변화

현재 Anthropic Claude Code 팀에서 찾는 인재: 제너럴리스트.

6개월 전부터 팀 전원이: - 사용자 인터뷰 진행 - 디자인 작업 - 데이터 풀·대시보드 구축 - 스코핑·PM 업무

엔지니어·PM·디자이너·UX리서처 경계가 이미 사실상 붕괴됐다. "재무 담당자도, 비서실장도 코드를 배포한다."

Member of Technical Staff(MTS) 직함 체계: 직군·시니어리티를 숨겨 출발선을 동일하게. 신입이 VP에게 아이디어를 들고 가는 문화를 가능하게 한다.

시니어 10~30년 경력자 역설: 오래된 습관을 언러닝(unlearning)하는 데 수개월이 걸린다. 반면 신입은 Claude Code를 네이티브하게 사고해 오히려 더 잘 쓴다.

6. Co-work 탄생

배경: 비개발자들이 터미널 없이도 Claude Code의 힘을 쓰고 싶어 하는 수요 포착. - 데이터 과학자 Brandon이 혼자 터미널·Node.js·API 키 설정해서 사용 → 일주일 후 팀 전체가 Claude Code 창 여러 개 - 방울토마토 재배자가 Claude Code로 식물 영양 관리하는 트윗 → "이제 메인스트림"

실패한 프로토타입들: - 슬랙 봇 기반: 느낌이 좋지 않음 - 웹 기반 여러 프로토타입: 파일시스템 접근 불가가 치명적. 파일 드래그&드롭 마찰만으로도 경험이 깨졌다.

Co-work 결정 순간: Acquired 팟캐스트 진행자 David가 처음으로 터미널을 열었다는 이야기 → "이걸 8~9일 안에 만들어서 내일 출시해야 한다."

Co-work는 100% Claude Code로 빌드됐다.

7. 조직 처방 — 토큰으로 인원을 대체하라

창업자·기업 대상 조언:

  1. 토큰 예산을 최대화하라: "더 살수록 더 절약된다(Jensen 인용)." 실험을 막지 마라.
  2. 인원을 의도적으로 부족하게: 4명짜리 프로젝트에 2명 넣기. 자동화를 강제하면 다음번엔 더 싸고 빠르다. 복리 효과.
  3. 스킬(skills) 문서화: 비즈니스 원칙처럼 모델도 이걸 사용할 수 있다.
  4. 많이 쓰이는 태스크만 최적화: 80% 케이스를 자유롭게 돌리다가 비용이 보이면 그때 최적화.

수식으로 요약: 선행 비용 증가 → 반복 비용 감소. "일종의 사전 컴파일."

8. 취향과 AI의 장기 미래

현재 소위 "알파"로 꼽히는 것은 제품 취향(product taste)이다. 하지만 Boris의 전망:

  • 몇 달 내 모델이 생성하는 아이디어의 80%가 좋아질 것 (현재는 20% 수준)
  • 취향도 결국 모델이 따라잡는다
  • 인간이 끝까지 담당할 영역: 가치관(values) 교육. 자녀에게 좋은 사람이 되는 법을 가르치듯, 모델에게 좋은 모델이 되는 법을 가르치는 것.

개인 사례: Boris는 코드베이스에 "클래스 금지, 함수만" 규칙을 강제했다. 모델이 클래스를 쓰기 시작하자 포기했다. 결과는 나빴지 않았다. "나만의 특별함이라고 생각했던 것이 틀렸음을 계속 증명당한다."

[Boris]: 2배속이요, 아마.

[진행자]: 그리고 편집된 버전으로.

[Boris]: 어떻게 보면 사고에 가까웠어요. 저는 2024년 말 Anthropic에 Labs Team이라는 팀에 합류했는데, 프로토타이핑 팀이었어요. 다시 부활했죠. 아이디어는 "다음 대형 제품이 뭔지 찾아내자"였고, 동시에 모델 프론티어를 밀어붙이며 그 미래 제품을 가장 잘 지원할 방향으로 모델을 어떻게 발전시킬지 파악하는 것이었어요. 제품이 실제로 프론티어를 밀어붙이기 전까진 모델을 어느 방향으로 발전시켜야 할지 알기 어렵거든요. 당시에 'product overhang'이라는 이상한 느낌이 있었어요 — 모델은 할 수 있는데, 그걸 포착하는 제품이 없는 상태요. 코딩 도구만 해도 당시엔 자동완성 도구나 질문은 받지만 코드는 못 쓰는 에이전트 수준이었어요.

[진행자]: 이 시점 전에 Anthropic 내부 코딩 상황은 어땠나요?

[Boris]: 내부적으론 여전히 IDE를 쓰고 있었어요. 하지만 Anthropic은 회사 차원에서 항상 코딩을 중요하게 여겼어요. 도구 사용(tool use), 컴퓨터 사용(computer use) — 이게 항상 핵심 연구 방향이었어요. AI 안전을 연구하기 위해 존재하는 회사니까요. Anthropic 직원을 복도에서 잡고 "왜 여기 있어요?" 물으면 전부 "AI 안전"이라고 답해요. 기계적 해석 가능성(mechanistic interpretability), 정렬 연구(alignment work) 등 여러 방법이 있지만, 결국 모델을 실제 세계에서 연구해야 해요. 그 방법이 코딩이에요. 모델이 세계와 상호작용하는 방식이 코딩이니까요. 코드는 컴파일되거나 안 되거나, 테스트를 통과하거나 못 하거나 — 아주 명확한 합격/불합격 기준이 있어요. 영어엔 올바른 시가 무한히 많지만, 특정 문제를 푸는 올바른 코드는 무한하지 않아요.

[진행자]: Meta에서 오셨는데, 거기서의 경험이 Claude Code 초기에 어떻게 연결됐나요?

[Boris]: 저한테 DevTools는 항상 부업이었어요. 메인이 아니었죠. 제품을 만들다 보면 개발자 경험(DevX)이 안 좋을 때 도구를 만드는 식이에요. YC 정신이기도 하고요 — 저는 2010~2011년 초창기 YC 배치 회사의 첫 번째 입사자였어요. 그래서 여기서도 "내가 쓸 걸 먼저 만들자" 마음으로 접근했어요. 다른 사람들도 유용하게 쓰길 바라면서. 놀랍게도 그렇게 됐고요.

[진행자]: 처음엔 별로였다고 하셨는데, 10% 코드만 썼다가 지금은 6개월간 한 줄도 안 쓰셨다고요. 무엇이 바뀌었나요?

[Boris]: 기억해요. 5월에 Sonnet 4와 Opus 4, 그리고 11월에 Opus 4.5 [?Opus 4.5]. 결국 모델이었어요. 하네스 개선도 많이 했고, Claude Code도 계속 좋아졌어요. CLI에서 시작해서 데스크탑 앱, 모바일 앱, iOS와 Android, Slack 앱, GitHub 앱까지 만들었어요. Plan mode 같은 기능들도 그 과정에서 나왔고요. 하지만 "내 코드에서 모델이 쓰는 비율"이 계단식으로 오른 건 순전히 모델이었어요.

[진행자]: Claude Code 경험이 모델 개선으로 얼마나 피드백됐나요?

[Boris]: Anthropic 전 직원이 매일 Claude Code를 써요. 모델 만드는 연구자도, 제품 만드는 사람도. 그게 사이클이에요.

[진행자]: 회사 생산성 변화를 수치로 표현할 수 있나요?

[Boris]: AI 랩에 있다 보니 지수 함수적 사고에 익숙해졌어요. 내부 차트는 거의 다 로그 선형 그래프예요. 매출도, 사용량도, 코드도 다 지수 성장이에요. Anthropic 직원 1인당 코드량, PR 수가 Claude Code 출시 이후 수백 % 성장했어요. 가장 최근에 공유한 수치가 3X인데, 이미 구식 수치예요. 엔지니어링 팀 규모가 늘면 보통 생산성이 떨어지는데 — 신입이 기존 직원에게 계속 물어보니까요 — 여기선 신입 온보딩이 2일이에요. 예전엔 몇 주였는데. "데이터베이스 어떻게 쿼리해요?" → "Claude Code 켜서 시키면 돼요."

[진행자]: 2026년에 합류한 신입들 중 실제로 코드를 쓴 사람이 있나요?

[Boris]: '코드 쓴다'를 어떻게 정의하냐에 달렸어요. 제 할아버지는 소련에서 펀치카드로 코딩했어요. 아버지는 어셈블리 쓰면서 Python 쓰는 저를 "코딩하는 게 아니다"라고 놀렸고요. 항상 추상화 레벨이 올라가요 — 스위치→펀치카드→어셈블리→COBOL/FORTRAN→Java→Python/JavaScript. 지금 우리가 하는 것도 그 연속선 어딘가에 있어요. 1년 전 저는 IDE에서 자동완성으로 코딩했어요. 11월에 IDE를 삭제했어요 — 한 달간 안 열었으니까. 그때 5~10개의 Claude 인스턴스를 병렬 실행하면서 프롬프팅이 코딩이었어요. 지금은 한 단계 더 올라갔어요. 더 이상 Claude에게 직접 프롬프트하지 않아요. 루프를 작성해요. 루프가 Claude에게 프롬프팅하고 무엇을 할지 판단해요.

[진행자]: Anthropic 팀에 지원하는 엔지니어를 어떻게 평가하나요?

[Boris]: 제너럴리스트를 좋아해요. 6개월 전부터 팀 전원이 사용자 인터뷰, 디자인, 데이터 분석, 스코핑을 다 해요. 예전처럼 UX리서처→디자이너→PM→엔지니어 순서의 폭포수 구조가 아니에요. 모든 직군이 하나의 '빌더'로 합쳐지고 있어요. 그래서 Member of Technical Staff(MTS)라는 직함이 의미있어요 — 직군·시니어리티를 숨겨요. Meta에서도 소프트웨어 엔지니어는 전부 동일한 직함이었어요. 시니어·프린시펄 같은 직급이 없었죠. 그러면 사람들이 아이디어 자체로 평가받아요. 저도 L4 엔지니어였을 때 VP한테 아이디어 들고 갔는데, VP는 제 레벨을 몰랐어요. 결국 세 번째 도전 때 성공했고요. 30년 경력 시니어들은 오래된 습관을 언러닝하는 데 몇 달이 걸려요. 신입은 Claude Code를 네이티브하게 생각해서 오히려 더 잘 가르쳐줘요.

[진행자]: Co-work 이야기를 해주세요.

[Boris]: 4월에 출근했는데 Claude Code 팀 옆에 앉은 데이터 과학자 Brandon이 Claude Code를 쓰고 있었어요. 당시엔 터미널에서만 됐는데, 그는 데이터 분석용으로 혼자 터미널·Node.js·API 키 설정을 다 해냈더라고요. 다음 주엔 데이터 과학자 전원이 Claude Code 창 여러 개 켜놨어요. 그리고 5~6월쯤 Twitter에서 방울토마토 키우는 사람이 Claude Code로 식물 영양 관리하는 걸 봤어요. 웹캠으로 모니터링하고, 몇 주 후에 토마토가 열리자 Claude가 "우리 일이 빛을 발하고 있다"고 했어요. 그 트윗 보고 "이제 메인스트림이다"고 느꼈어요.

실패한 프로토타입이 많았어요 — Slack 봇, 다양한 웹 기반 프로토타입. 웹은 파일시스템 접근이 안 된다는 게 치명적이었어요. 파일 드래그&드롭 마찰만으로도 경험이 깨졌어요. 결국 Co-work는 약 8~9일 만에 100% Claude Code로 빌드했어요. Acquired 팟캐스트 David가 처음으로 터미널을 열었다는 얘길 듣고 하루 만에 출시했어요.

[진행자]: 창업자들이 조직에서 무엇을 바꿔야 할까요?

[Boris]: 토큰을 최대한 많이 주세요. Jensen 말대로 많이 살수록 절약이에요. 그리고 인원을 의도적으로 부족하게 배치하세요. 4명짜리 프로젝트에 2명 넣고 토큰 많이 주세요. 자동화를 강제하면 다음번엔 더 싸고 빠르게 해요. 복리 효과예요. 스킬(skills) 형태로 원칙을 문서화하면 모델도 그 원칙을 쓸 수 있어요. 많이 쓰이는 태스크에 비용이 쌓이면 그때 최적화하면 돼요.

[진행자]: 취향(taste)에 대해 어떻게 생각하세요?

[Boris]: "내가 특별하다"는 느낌이 틀렸다는 게 계속 증명돼요. 코드베이스에 클래스 금지 규칙을 강제했는데 — 함수형 프로그래밍을 좋아해서요, Haskell [?Haskell]·Scala [?Scala] 팬이에요 — 모델이 클래스를 쓰기 시작했어요. 결국 포기했어요. 비즈니스 결과가 나왔으니까요. 지금 '알파'는 제품 취향이라고들 하지만, 저는 이것도 사라질 거라 생각해요. 지금 저는 수백 개의 Claude 인스턴스가 Twitter 피드백·GitHub 이슈·Slack을 분석해서 다음에 뭘 만들지 판단하게 하고 있어요. 현재는 아이디어의 20%만 좋아요. 3~6개월 후 모델이 업그레이드되면 대부분이 좋을 거예요. 인간이 끝까지 맡을 역할은 모델에게 가치관(values)을 가르치는 것이에요. 자녀에게 좋은 사람이 되는 법을 가르치듯이요.
