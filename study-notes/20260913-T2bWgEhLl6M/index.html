AI 시대, 대담한 소프트웨어를 개발하는 법 — Jonathan Kelley (Dioxus Labs & Cognition)

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 발표의 중심은 AI가 코드를 얼마나 많이 쓰느냐가 아니라, 그 코드가 장기간 유지할 제품에 들어갈 수 있느냐다. 화자 Jonathan Kelley는 Rust로 여러 운영체제에서 쓸 앱을 만드는 프레임워크 Dioxus를 사례로 든다. 그의 설명에 따르면 팀은 AI 코딩 에이전트로 수만 줄의 코드를 만들었지만, 실제 품질 기준을 통과해 합칠 수 있었던 코드는 매우 적었다.

실패 원인은 에이전트가 코드를 전혀 못 써서가 아니었다. 오히려 에이전트는 문서를 오래 조사하고, 낯선 API를 추적하고, 반복적인 검증 작업을 수행하며, 복잡한 구현을 빠르게 내놓는 데 강했다. 문제는 빠른 구현과 좋은 제품 구조가 같은 일이 아니라는 점이었다. 기능 하나가 지금 작동해도 미래 기능을 막거나, 공개 API를 깨뜨리거나, 문서·테스트·배포 절차와 어긋나면 장기 프로젝트에는 받아들이기 어렵다.

읽는 법: 왼쪽에서 오른쪽으로 읽는다. 화살표는 자동 성공이 아니라 통과해야 할 과정이다. 수치를 나타낸 그래프가 아니라 발표의 인과를 정리한 개념도다.

Dioxus가 요구한 품질은 무엇이었나

Dioxus는 단순한 시제품이 아니라 다른 개발자와 사업이 의존하는 기반 소프트웨어다. 화자는 이런 프로젝트에서 코드가 항상 작동해야 하고, 깨졌을 때 쉽게 고칠 수 있어야 하며, 공개 API·문서·예제·테스트·성능 측정까지 일정한 수준을 유지해야 한다고 말한다. 기능을 빨리 추가하는 것만으로는 부족하다.

그는 좋은 기존 구조를 건물을 받치는 바닥처럼 설명한다. 새 기능이 올라가는 기초 구조(substrate)가 나쁘면, 그 위에 에이전트가 아무리 빠르게 코드를 쌓아도 결과가 좋아지기 어렵다. 반대로 구조와 요구가 분명하면 에이전트의 속도와 끈기를 유용하게 쓸 수 있다.

화자의 사례에 따르면 Dioxus는 2021년 시작됐고, 2026년에는 크로스 플랫폼 지원, 네이티브 렌더링, Rust 핫 리로드, 번들 분할 같은 기능을 제공한다. 그는 GitHub 별이 거의 37,000개이고 다운로드가 수백만 회이며, Dioxus로 만든 앱의 누적 최종 사용자가 2억 명을 넘는다고 추정한다. 이 수치와 성과 평가는 발표자의 주장으로, 이 노트가 독립 검증한 사실은 아니다.

읽는 법: 시간은 왼쪽에서 오른쪽으로 흐른다. ‘발표 전 6개월’은 화자의 상대적 표현이다. 마지막 칸은 AI 도입 자체의 실패가 아니라, 생성량을 품질로 착각한 초기 사용 방식의 실패를 뜻한다.

왜 Rust의 어려움이 오히려 도움이 됐나

팀은 원래 Rust의 학습 곡선을 줄이려고 읽기 쉬운 코드, 좋은 도구와 오류 메시지에 많은 노력을 들였다. 그런데 에이전트는 사람처럼 언어의 불편함을 크게 느끼지 않았다. 화자에 따르면 에이전트는 까다로운 예외 조건을 처리하고 Rust의 대여 검사기와 씨름하는 부담을 대신 떠맡았다. 사람에게는 진입 장벽이었던 어려움이 에이전트에게는 처리 가능한 작업이 된 것이다.

그렇다고 Rust가 품질을 자동으로 보장한다는 뜻은 아니다. 언어와 도구가 잘못된 코드를 일부 막거나 수정 방향을 알려줄 수 있어도, 어떤 기능이 미래 구조에 맞는지, 공개 API를 어떻게 진화시킬지, 어떤 테스트가 실제 위험을 잡는지는 별도의 판단이다.

에이전트에게 잘 맞은 일과 아직 사람이 이끌어야 한 일

화자는 에이전트를 끈기 있고 지식 범위가 넓은 기술 보조자로 평가한다. 팀이 모든 운영체제, 빌드 시스템, 런타임, 언어, API의 세부 사항을 알 수는 없지만, 에이전트는 많은 문서를 읽고 바이너리와 전용 API를 추적할 수 있었다.

그 사례로 Kotlin과 Swift 플러그인을 든다. 화자에 따르면 구현 자체는 첫날에 끝났고, 전체 출시는 2~3주가 걸렸으며 그중 2주는 실제 기기에서 테스트 사례를 만드는 데 썼다. Blitz라는 웹 엔진에서는 CSS 규격과 Chrome·Safari의 처리 방식을 조사해 레이아웃 문제를 디버깅하는 데 도움을 받았다.

반복적이지만 중요한 작업에도 효과가 있었다. 배포 체크리스트 확인, 안정 버전으로 버그 수정 옮기기, 문서와 예제가 실제 코드와 일치하는지 검사하기 같은 일이다. 세 명의 핵심 엔지니어로 운영된다는 화자의 설명을 기준으로 보면, 이런 반복 검증을 에이전트에 맡기는 것은 사람이 아키텍처 문제에 집중할 시간을 확보하는 방식이다.

반면 테스트 코드를 많이 만드는 것만으로는 충분하지 않았다. 에이전트는 생성자처럼 눈에 보이는 API를 그대로 확인하는 피상적인 테스트를 만들 수 있었지만, 실제로 어떤 실패를 막아야 하는지를 고르는 데는 한계가 있었다. 팀은 여전히 테스트 조건과 테스트용 API, 실행기를 직접 설계했다.

예외는 퍼징 하네스(fuzzing harness)였다. 퍼징은 정상 입력뿐 아니라 잘못되거나 적대적인 입력을 매우 많이 넣어 프로그램이 어디서 깨지는지 찾는 방식이고, 하네스는 그 입력을 자동으로 넣고 결과를 관찰하는 장치다. 화자는 에이전트가 이런 반복 실행 장치를 만드는 데 뛰어났다고 말한다.

읽는 법: 왼쪽은 많은 탐색과 반복 실행이 필요한 작업이고, 오른쪽은 무엇이 좋은 결과인지 먼저 정의해야 하는 작업이다. 에이전트가 오른쪽 작업을 전혀 못 한다는 뜻은 아니다. 최종 방향과 책임을 사람 없이 맡길 단계는 아니라는 화자의 판단이다.

아키텍처에 관한 핵심 주의점

화자는 에이전트가 기능이 기존 구조에 잘 맞지 않을 때 대규모 리팩터링이나 아키텍처 재설계를 자발적으로 감행하는 것을 두려워하지 않는다고 말한다. 즉, 에이전트가 언제나 기존 구조에 작은 코드를 덧붙이는 쪽만 택한다는 설명이 아니다. 오히려 빠른 속도로 큰 변경까지 내놓을 수 있으므로, 그 변경이 장기 방향에 맞는지 사람이 더 신중하게 판단해야 한다.

나쁜 기초 위에서는 에이전트도 스파게티 코드를 더 빠르게 만들 수 있다. 반대로 사람이 의도와 제약을 제대로 전달하고 좋은 구조를 마련하면, 화자는 Claude 수준 도구의 코드 자체 품질이 매우 높을 수 있다고 평가한다. 그래서 미래에는 타이핑보다 아키텍처 설계가 대부분의 시간을 차지할 것이라고 전망한다. 이는 이미 검증된 보편 법칙이 아니라 화자의 예측이다.

Dioxus 팀은 AI 코드 검토를 사용하면서도 배포할 PR을 줄마다 읽는다고 한다. 외부 기여자가 자신의 의도와 장기적 영향을 충분히 설명하지 않으면 모델도 임시방편으로 붙인 해결책을 만들기 쉽기 때문이다. 화자의 결론은 간단하다. 코드는 싸졌지만 품질은 싸지지 않았다. 읽기, 설계, 요구 전달, 테스트 조건 선택, 최종 검토의 중요성은 오히려 커졌다.

경계도 함께 봐야 한다. 성능·사용자·인기도 수치와 “유일한 엔진”, “아무도 해내지 못했다” 같은 표현은 화자의 주장이다. 또한 META의 출처 정보는 creator: Dioxus Labs, affiliation: Jonathan-kelley로 적혀 있지만, 전사에서는 Jonathan Kelley가 자신을 화자로 소개하고 마지막에는 Dioxus 팀이 Cognition에 합류했다고 말한다. META도 원본 영상 링크 없이 화자 이름과 SNS로 추정한 출처라고 밝힌다. 따라서 이 이름과 소속 값은 후보로 보존하되 확정된 원작자·소속 관계로 해석하면 안 된다.

여기까지만 이해하면 충분

  • AI가 코드 생산량을 늘려도, 아키텍처·테스트 조건·문서·검토 기준을 통과하지 못하면 제품 품질은 늘지 않는다.
  • 에이전트는 방대한 조사, 반복 검증, 플러그인 구현, 퍼징 하네스 구축에 강점을 보였지만 무엇을 검증할지는 사람이 정해야 했다.
  • 에이전트는 큰 리팩터링이나 재설계도 주저하지 않을 수 있으므로, 사람은 장기 구조와 의도를 더 명확히 정하고 결과를 읽어야 한다.
  • 발표의 수치와 성과 평가는 화자의 주장이고, 출처의 원작자·소속 정보도 추정 상태다.

비유와 깨지는 지점

빠른 건설팀과 건축 설계

AI 코딩 에이전트는 자료를 많이 알고 지치지 않으며, 벽을 세우거나 반복 검사를 빠르게 수행하는 건설팀과 닮았다. 아키텍처는 건물의 용도, 하중, 동선과 미래 증축을 정하는 설계에 해당한다. 빠른 팀이 있어도 무엇을 지을지와 어떤 검사를 통과해야 할지는 따로 정해야 한다. 이 팀은 기존 설계가 맞지 않으면 큰 철거나 재설계도 주저하지 않을 수 있으므로 감독이 더 중요하다.

비유가 깨지는 지점: 소프트웨어는 실행 결과, 타입 검사, 자동 테스트를 통해 빠르게 피드백을 받을 수 있고 복제·수정 비용도 물리적 건설과 다르다. 또한 에이전트가 설계 제안을 할 수 있으므로 단순한 육체 노동자로만 보면 실제 능력을 과소평가하게 된다.

1. Dioxus의 출발

Jonathan Kelley는 5년 전 학부생으로 보낸 마지막 여름에 Dioxus의 첫 커밋을 했다고 말한다. 친구들처럼 Google 인턴십이나 AI 연구를 택하는 대신 Rust로 크로스 플랫폼 앱 프레임워크를 만드는 아이디어를 탐색했다.

2021년 당시 Rust는 아직 틈새 언어였지만 생태계와 도구가 성장하고 있었다고 회고한다. 네이티브 성능, 견고한 타입 시스템, 단순한 교차 컴파일이 선택 이유였다.

Dioxus의 구상은 여러 도구 체인, 언어, IDE를 오가는 대신 Rust로 앱을 작성하고 HTML과 CSS를 화면 표현에 사용하는 것이었다. 화자는 당시 React Native가 불안정했고 Flutter가 느렸으며 둘 다 네이티브 API 처리에 약했다고 평가한다. 반면 Rust를 사용하면 VM, IPC, JavaScript 없이 네이티브 앱을 만들고, React의 반응형 개념과 웹 도구를 활용할 수 있다고 보았다.

실제로는 반응성, 글꼴 렌더링, 핫 리로드, 앱 번들링까지 직접 만들어야 했으며 웹 브라우저를 만드는 수준의 작업도 필요했다고 설명한다.

2. 2026년의 프로젝트

화자는 2026년 Dioxus가 원래 목표를 달성하고 넘어섰다고 평가한다. 크로스 플랫폼 지원, 네이티브 렌더링, Rust 핫 리로드와 번들 분할을 제공하며, 하나의 코드베이스에서 풀스택 웹 앱과 iOS·Android 앱의 구성 요소를 공유할 수 있다고 말한다.

제시한 규모는 다음과 같다.

  • GitHub 별 거의 37,000개
  • 수백만 회 다운로드
  • Dioxus 앱의 누적 최종 사용자 추정치 2억 명 이상
  • AI 비서, 투표용 소프트웨어, 데이터 과학 도구, 위성 충돌 방지 시스템 등의 사용 사례

이 수치와 사례는 화자의 발표 내용이며 이 노트에서 독립 검증하지 않았다.

Dioxus는 파일 수를 줄이고 빌드 도구, 핫 리로드, 자산 최적화를 통합하는 데 노력했다. Rust 프로젝트의 구조가 서로 비슷해 새로운 프로젝트를 파악하기 쉽고, 플랫폼별 코드나 복잡한 빌드 설정을 자주 다루지 않아도 되며 main.rs 하나로 시작할 수 있다고 설명한다.

3. Blitz와 Subsecond

Blitz는 가볍지만 충분한 기능을 갖춘 HTML·CSS 렌더링 엔진을 목표로 했다. 화자에 따르면 Firefox에서 브라우저급 CSS 엔진을 추출하고 자체 HTML·DOM과 혼합형 GPU 렌더링 파이프라인을 만들었다.

화자가 제시한 Blitz 앱의 수치는 다음과 같다.

  • 번들 크기 5MB 미만
  • 실행 중 RAM 사용량 50MB 미만

이는 Electron 앱과의 대비로 제시됐지만, 비교 조건이나 측정 방법은 발표에 포함되지 않았다.

Subsecond는 Rust, C, C++용 범용 핫 리로드 엔진이다. 변경된 부분을 다시 컴파일하고 실행 중인 앱에 100밀리초 안에 반영한다고 설명한다. 주요 운영체제와 Rust가 WebAssembly로 컴파일되는 웹에서도 작동한다고 말한다. “이 정도의 언어·런타임 지원을 가진 유일한 엔진”과 “이전에 아무도 하지 못했다”는 평가는 화자의 주장이다.

4. AI 도입과 슬롭 캐논

팀은 오랫동안 AI에 회의적이었고 고품질 코드와 에이전트 도구가 양립하기 어렵다고 생각했다. 그러나 발표 전 약 6개월 동안 코딩 에이전트가 크게 발전하고 특히 Rust를 잘 다루게 됐다고 판단해 적극적으로 사용하기 시작했다.

팀은 Claude Code 구독 한도를 채우며 수만 줄의 Rust 코드와 오래 원했던 기능을 만들었다. 하지만 실제 머지 품질 기준을 통과한 코드는 매우 적었다. 수천 줄의 기능, 버그 수정과 통합 작업이 초안 상태에 남았다.

팀은 이런 상태를 ‘슬롭 캐논’이라고 불렀다. 이는 에이전트의 코드가 모두 나쁘다는 뜻이 아니라, 도구를 다루는 법을 모른 채 생성량만 늘린 사용 방식에 대한 표현이다.

5. Rust의 어려움과 품질 기준

팀은 Dioxus를 사람이 읽고 쓰기 쉽도록 만들기 위해 도구와 오류 메시지에 투자했다. 그러나 에이전트는 사람처럼 언어의 불편을 크게 느끼지 않았다. 화자에 따르면 에이전트가 예외 조건과 대여 검사기를 처리하면서 Rust의 학습 곡선이 오히려 특징이 됐다.

화자는 소프트웨어의 종류에 따라 품질 요구가 다르다고 구분한다.

  • 연구 코드에서는 코드 품질이 가장 중요한 요소가 아닐 수 있다.
  • 시제품에서는 빠른 반복이 중요할 수 있다.
  • 내부 코드가 드러나지 않는 앱은 외부 동작이 우선일 수 있다.
  • Dioxus처럼 다른 개발자가 코드·API·문서·아키텍처를 직접 사용하는 제품은 내부 품질이 제품 품질이다.

Dioxus는 항상 작동하고, 문제가 생겼을 때 고치기 쉬우며, 패치 릴리스에서 수많은 사용자가 의존하는 API를 깨뜨리지 않아야 한다고 말한다. 문서, 예제, 테스트, 벤치마크도 릴리스 품질에 포함된다.

6. 지식 문제와 반복 업무

Dioxus 팀은 모든 빌드 시스템, 런타임, 운영체제, 언어, API와 예외를 알 수 없다. 에이전트는 수천 페이지의 문서를 조사하고 전용 API와 바이너리를 파악하며 역공학하는 데 사람보다 더 오래 집중할 수 있다고 평가한다.

Kotlin과 Swift 플러그인은 이런 강점의 사례다. 화자는 전체 작업을 2~3주 안에 출시했으며 구현은 첫날 끝났고 나머지 약 2주는 테스트 사례와 실제 기기 검증에 썼다고 말한다.

Blitz에서는 어려운 CSS 스타일과 레이아웃 문제를 디버깅하는 데 에이전트를 사용했다. CSS 규격과 Chrome·Safari의 처리 방식을 빠르게 찾아 사람이 WebKit 소스까지 직접 탐색해야 하는 부담을 줄였다고 설명한다.

Dioxus의 핵심 엔지니어는 세 명이라고 말한다. 이 작은 팀에서 다음과 같은 반복 업무에 에이전트를 적용했다.

  • 압축 배포 파일의 디렉터리 구조 확인
  • 새 편집기 확장 기능의 릴리스별 점검
  • 배포 체크리스트 확인
  • 안정 버전으로 버그 수정 백포트
  • 문서와 문서 주석의 누락·불일치 확인
  • 모든 문서 항목에 예제가 있는지 점검

화자는 최근 Dioxus 버전에서 이전보다 더 많은 패치 릴리스를 했고, 주간 또는 주 여러 회의 배포 주기를 유지할 수 있었다고 말한다. 정확한 비교 기간과 릴리스 수는 제시하지 않았다.

7. 테스트의 한계와 퍼징

화자는 AI가 테스트를 작성하는 방식, 특히 맹목적으로 테스트를 늘리는 방식에는 확신하지 못한다고 밝힌다. 기반 소프트웨어의 종단 간 테스트는 실제 편집기를 열고 확장 기능을 사용하는 것처럼 환경 전체를 다뤄야 하므로 어렵다.

에이전트는 생성자가 있으면 생성자를 호출하는 식의 피상적인 테스트를 만들 수 있었다. API별 테스트는 쉽게 쓰지만 어떤 테스트가 실제로 중요한지를 선택하는 데는 인간과 비슷하게 실패할 수 있다는 평가다.

팀은 다음 작업을 계속 사람이 맡았다.

  • 테스트 조건 열거
  • 테스트용 API 설계
  • 테스트 실행기 처리

에이전트는 테스트 아이디어와 예외 조건을 넓히는 대화 상대가 될 수 있었다.

퍼징은 수백만 가지 입력, 특히 잘못되거나 적대적인 입력을 넣어 프로그램을 시험하는 방식으로 설명한다. 화자는 에이전트가 이런 퍼징 하네스를 만드는 데 뛰어났다고 평가한다.

8. 아키텍처와 검토

화자는 코드 아키텍처가 여전히 예술의 영역이라고 말한다. 에이전트가 놓일 기존 기반이 나쁘면 기여 결과도 나빠진다.

에이전트는 기능이 기존 구조와 맞지 않을 때 대규모 리팩터링이나 아키텍처 재설계를 자발적으로 감행하는 것을 두려워하지 않을 수 있다. 따라서 에이전트가 기존 구조에만 코드를 붙이고 재설계를 회피한다고 해석하면 원문과 반대가 된다. 큰 변경을 빠르게 내놓는 능력 때문에 장기 방향을 판단하는 사람의 역할이 더 중요하다는 것이 화자의 논점이다.

팀은 이제 개발 시간의 많은 부분을 다음 문제에 쓴다고 말한다.

  • 소프트웨어 아키텍처
  • 미래에 필요할 기능
  • 시스템이 어떻게 진화할지에 대한 판단

의도를 제대로 전달한다는 조건에서 Claude 수준 도구의 코드 자체 품질은 매우 높을 수 있으며, 미래에는 실제 코드 작성보다 아키텍처가 대부분의 시간을 차지할 것이라고 전망한다.

Dioxus 팀은 AI 리뷰로 버그를 미리 찾으면서도 모든 PR을 줄마다 읽는다고 한다. 외부 기여자는 자신의 의도나 장기 구조를 충분히 생각하지 않고 현재의 버그 수정이나 기능만 원할 수 있다. 모델은 사람의 마음을 읽을 수 없으므로 텍스트로 전달된 의도에 제한된다. 화자는 이런 의미에서 프롬프트 엔지니어링이 실제라고 말한다.

9. 결론과 시행 상태

화자의 결론은 “코드는 이제 싸지만 품질은 그렇지 않다”는 것이다. 소프트웨어 엔지니어의 일은 줄을 입력하는 것보다 복잡한 문제에 우아한 해법을 설계하고, 시스템의 진화를 앞서 생각하며, 요구 변경에 대응할 유연성을 남기는 데 있다는 주장이다.

다음 내용은 현재 사실과 전망을 구분해야 한다.

  • 현재 경험으로 제시: 에이전트를 문서 조사, 구현 보조, 반복 검증, 배포 작업, 퍼징 하네스 구축에 사용했다.
  • 현재 유지하는 절차: AI 리뷰를 사용하지만 배포할 코드는 줄마다 읽는다고 말한다.
  • 전망: 앞으로 코드 작성보다 아키텍처 설계가 개발 시간의 대부분을 차지할 가능성이 있다고 본다.
  • 채용 안내와 희망: Dioxus를 인수한 Cognition이 채용 중이며, 청중이 미래의 도구를 만드는 일에 합류하기를 바란다고 말한다.

전체 전사 펼치기

안녕하세요. 제 이름은 Jonathan Kelley이고, 오늘은 AI 시대에 야심 찬 소프트웨어를 개발한다는 것이 무엇을 의미하는지 이야기해 보겠습니다.

5년 전, 저는 Dioxus라는 프로젝트에 최초의 커밋을 남겼습니다. 당시 학부생으로서 보낼 수 있었던 마지막 여름을 활용해, 많은 친구들처럼 Google 인턴십을 하거나 AI 연구를 하는 대신, Rust 프로그래밍 언어로 작성하는 크로스 플랫폼 앱 프레임워크에 대한 아이디어를 탐구하는 데 보냈습니다.

2021년 당시 Rust는 여전히 상당히 틈새적인 기술이었지만 생태계는 성장하고 있었고 도구도 개선되고 있었습니다. 네이티브 성능, 견고한 타입 시스템, 간단한 크로스 컴파일이라는 조합은 정말 매력적이었습니다. 정말 너드스러운 이야기죠.

Dioxus의 아이디어는 간단했습니다. 정말 좋은 크로스 플랫폼 앱 프레임워크가 있다면 어떨까? 수십 가지의 툴체인, 프로그래밍 언어, IDE를 헤매는 대신, HTML과 CSS를 마크업 언어로 사용해 모든 앱을 Rust로 작성하면 어떨까?

때는 2021년이었고, React Native는 불안정했고, Flutter는 너무 느렸으며, 둘 다 네이티브 API를 제대로 활용하지 못했습니다. 반면 Rust를 사용하면 VM도, IPC도, JavaScript도 없이 네이티브 앱을 직접 만들 수 있었습니다. UI에 HTML과 CSS를 조금 사용하고 React에서 반응성(reactivity)에 대한 영감을 얻는다면, 방대한 양의 웹 컴포넌트와 웹 도구를 재사용할 수 있었습니다.

목표는 일반적인 개발자에게 여전히 상당히 익숙하면서도 매우 강력한 앱 프레임워크를 만드는 것이었습니다. 쉬워 보이죠?

하지만 흔히 하는 말처럼, 우리가 앱 프레임워크를 처음부터 만들기로 한 이유는 그것이 쉬워서가 아니라 쉬울 것이라고 생각했기 때문입니다. 실제로 React Native와 Flutter에 도전하는 일은 매우 야심 찬 일이었습니다. 2021년에는 Dioxus를 만드는 데 사용할 수 있는 기성 컴포넌트가 거의 없었습니다. 반응성부터 폰트 렌더링, 핫 리로딩, 애플리케이션 번들링까지 모든 것을 처음부터 만들어야 했습니다. 사용할 수 있는 것이 아무것도 없었습니다.

우리에게 웹 브라우저를 만드는 일 같은 과제는 그저 과정상 반드시 거쳐야 하는 단계였습니다.

그리고 오늘날인 2026년에 Dioxus는 원래의 사명을 달성했을 뿐 아니라 훨씬 뛰어넘었습니다. 크로스 플랫폼 지원, 네이티브 렌더링, Rust 핫 리로드, 번들 분할 등 처음부터 만들고자 했던 모든 기능을 지원합니다. 사실상 앱 개발 스택 전체를 새로 만들고 개선한 셈입니다.

사용자는 정확히 동일한 코드베이스에서 강력한 풀스택 웹 애플리케이션을 배포하고, iOS 및 Android 앱과 컴포넌트를 공유할 수 있습니다. 현재 Dioxus 프로젝트는 GitHub에서 거의 37,000개의 별을 받았고, 다운로드 수는 수백만 건에 이릅니다. Dioxus로 만든 앱은 전 세계에 배포되고 있으며, 누적 최종 사용자는 2억 명이 넘는 것으로 추정됩니다.

사용자들은 AI 어시스턴트, 투표 소프트웨어, 데이터 과학 도구, 심지어 우주에 있는 위성을 위한 충돌 회피 시스템까지 만들었습니다.

우리는 Dioxus를 최대한 사용자 친화적으로 만들기 위해 엄청난 노력을 기울였습니다. 파일 수를 줄이고, 빌드 도구를 통합하고, 핫 리로딩과 에셋 최적화를 제공하는 등 모든 플랫폼에 쉽게 배포하는 데 필요한 모든 것을 갖췄습니다.

Dioxus 앱은 Rust로 작성되기 때문에 구조적으로 매우 단순합니다. 플랫폼별 코드로 내려가야 하는 경우도 거의 없습니다. 모든 Rust 프로젝트의 구조가 비슷하기 때문에 개발자가 새로운 프로젝트에 뛰어들기도 매우 쉽습니다. 성가신 빌드 시스템 설정을 완전히 건너뛸 수 있습니다. 시작하는 데 필요한 것은 main.rs 하나뿐입니다.

Dioxus에서 우리가 세운 가장 야심 찬 목표 중 하나는 Blitz라는 가볍지만 완전한 기능을 갖춘 자체 HTML 및 CSS 렌더링 엔진을 제공하는 것이었습니다. Firefox에서 브라우저 수준의 CSS 엔진을 추출하고, 자체 HTML과 DOM을 구축했으며, 하이브리드 GPU 렌더링 파이프라인을 개발했습니다.

RAM과 저장 공간을 엄청나게 사용하는 Electron 앱과 비교하면 Blitz 앱은 가볍습니다. 번들 크기는 5메가바이트 미만이고, 실행 중 RAM 사용량은 50메가바이트 미만입니다. 게다가 꽤 멋집니다. 직접 커스텀 컴포넌트를 작성하고, 큐브를 회전시키며, 원하는 대로 브라우저를 커스터마이즈할 수 있습니다. 정말 멋진 프로젝트입니다.

또한 우리는 Rust, C, C++를 위한 범용 핫 리로드 엔진인 Subsecond라는 도구도 개발했습니다. Subsecond는 코드가 수정되는 것을 감시하고, 변경된 코드 부분을 다시 컴파일한 다음, 100밀리초 이내에 실행 중인 앱에 해당 변경 사항을 직접 적용합니다.

이는 엄청나게 어려운 기술적 도전이었으며, 이처럼 폭넓은 언어와 런타임을 지원하는 네이티브 컴파일 코드용 핫 리로드 엔진은 이것이 유일합니다. 모든 주요 운영체제에서 작동하며, Rust가 WebAssembly로 컴파일되는 웹에서도 작동합니다. 이런 일을 해낸 사람은 아무도 없었습니다.

제가 이 이야기를 하는 이유는 지난 5년 동안 그 과정에서 우리가 작업한 프로젝트들이 믿을 수 없을 만큼 야심 차고, 소수이지만 역량 있는 고숙련 엔지니어들로 구성된 팀의 결과물이기 때문입니다.

우리는 품질을 위해 공을 들였고, 코드의 모든 줄을 직접 두 눈으로 읽었으며, 빈번하면서도 야심 찬 릴리스 주기를 유지했습니다. 무엇보다 놀라운 점은 아주 최근까지 Dioxus의 모든 코드가 공들여 손으로 작성되었다는 것입니다.

왜 “최근까지”라고 말할까요? 잘 모르실 수도 있지만, 지난 6개월 동안 소프트웨어 엔지니어링과 개발은 엄청난 전환을 맞았습니다. AI 코딩 에이전트(coding agent)가 정말, 정말 좋아졌고, 특히 Rust를 다루는 능력이 아주 뛰어나졌습니다.

고숙련 Rust 엔지니어들로 구성된 우리 팀은 오랫동안 AI에 상당히 회의적이었습니다. 말하자면 AGI를 체감하지 못했고, 일상 업무에서도 AI를 전혀 사용하지 않았습니다. 우리는 고품질 코드를 배포하는 일과 에이전트형 코딩 도구(agentic coding tools)를 사용하는 일이 양립할 수 없다고 생각했습니다.

그런 도구들이 Rust를 아주 잘 다루게 된 것은 우리에게 큰 놀라움이었고, 마침내 우리는 기대에 부풀었습니다. 이렇게 새롭게 생긴 기대감을 바탕으로 우리는 개발을 시작했습니다.

우리 팀은 Claude Code 구독을 한도까지 사용했고, 수만 줄의 Rust 코드를 쏟아냈으며, 오랫동안 원했던 온갖 기능을 만들었습니다. 안타깝게도 우리가 코드를 병합해야 할지 판단하는 품질 기준을 통과한 코드는 거의 없었습니다.

수천 줄에 달하는 새로운 기능, 버그 수정, 그리고 수년 동안 원했던 통합 기능들이 초안 상태로 남아 있었고 계속 초안 상태에 머물렀습니다. 우리는 이런 도구를 제대로 휘두르는 법을 확실히 몰랐고, 이른바 슬롭 캐넌(slop cannon)이 되기도 너무 쉬웠습니다.

그래서 우리는 잠시 돌아보고 무엇이 효과가 있었고 무엇이 그렇지 않았는지 분석했습니다. 그동안 깨달은 한 가지는 Dioxus를 개발자에게 매우 친화적으로 만들기 위해 엄청난 노력을 기울였다는 점이었습니다. 읽기 쉽고, 작성하기 쉽고, 좋은 도구와 좋은 오류 메시지를 제공하도록 말입니다.

하지만 코딩 에이전트는 일반적으로 이런 것에 관심이 없습니다. 우리는 인간이 Rust를 쉽게 사용할 수 있도록 만들려고 했지만, 사실 그것은 그다지 중요하지 않았습니다. 다행히도 코딩 에이전트는 여전히 Dioxus에서 뛰어난 성능을 발휘합니다. Rust는 작성하기 더 어렵기 때문입니다.

코딩 에이전트는 개발 부담을 대신 처리해 줍니다. 엣지 케이스를 다루고 빌림 검사기(borrow checker)와 씨름하며, Rust 앱을 작성하는 데 따르는 인지적 부담을 덜어 줍니다. 우리가 줄이려고 애썼던 학습 곡선이 이제는 기능이 되었습니다.

Dioxus 작업에 코딩 도구를 도입하는 과정에서 우리는 폭넓은 교훈을 얻었습니다. 오늘날 코딩 에이전트가 정말 잘하는 일이 많았고, 아직 제대로 해내지 못하는 일도 많았습니다.

그래서 다음 몇 장의 슬라이드에서는 우리가 배운 것들과 에이전트형 코딩 시대에 야심 찬 소프트웨어 프로젝트를 만든다는 것이 무엇을 의미하는지 이야기하고 싶습니다.

먼저 야심 찬 소프트웨어 프로젝트를 만든다는 것이 무엇을 의미하는지 이야기하는 것이 중요합니다. 매일 무엇을 배포하느냐에 따라 소프트웨어에는 여러 유형이 있습니다.

연구를 하고 있을 수도 있고, 코드의 품질이 가장 중요한 요소는 아닐 수 있습니다. 빠르게 반복하고 신속하게 움직이는 일이 중요한 프로토타입 코드를 작성하고 있을 수도 있습니다. 또는 애플리케이션을 만들고 있을 수도 있는데, 사람들은 내부 코드를 보지 못합니다. 그들은 그저 외부에서 어떻게 보이는지만 봅니다.

하지만 우리와 Dioxus의 경우에는 몇 가지를 중요하게 생각합니다. 무엇보다도 당연히 코드가 항상 작동해야 하고, 문제가 발생하더라도 쉽게 수정할 수 있어야 한다는 점을 중요하게 생각합니다.

요즘 사람들이 충분히 생각하지 않는 부분이라고 봅니다. 계속해서 쉽게 유지보수할 수 있는 코드를 만들어야 합니다. 배포 속도는 여러분이 만든 기반 위에 세워지며, 그 기반이 좋지 않으면 그 위에 무엇을 만들든 좋은 결과가 나오지 않습니다.

두 번째로 우리는 새로운 기능을 배포하는 것을 중요하게 생각합니다. 우리의 로드맵은 정말 깁니다. 먼 미래까지 뻗어 있습니다. Dioxus에 아직 구현하지 않은 기능이 수십 가지나 있고, 시대의 흐름을 따라가기 위해 이를 빠르게 배포하고 싶지만 품질도 유지하고 싶습니다.

Dioxus처럼 규모가 크고 야심 찬 프로젝트를 개발할 때는 빠르게 배포하고 새로운 기능을 추가하는 일과, 동시에 기존 기능을 깨뜨리지 않고 패치 릴리스에서 수백만 명이 의존하는 API를 깨뜨리지 않도록 하는 일 사이에 끊임없는 긴장이 존재합니다.

사람들이 사업의 기반으로 삼는 프로젝트라면 릴리스에도 높은 기준이 요구됩니다. 문서, 예제, 테스트, 벤치마크의 높은 품질을 유지해야 합니다. 무언가 하나라도 어긋나면 사람들은 매우 빠르게 알아차립니다.

그래서 우리는 코딩 에이전트를 매우 어려운 기술적 문제를 해결하는 훌륭한 보조 도구로 정말 좋아합니다. 코딩 에이전트는 대규모 소프트웨어 프로젝트를 혼자 작업하는 개인이 발휘하기 매우 어려운 수준의 인내심과 방대한 지식을 제공합니다.

Dioxus의 많은 문제는 지식의 문제입니다. 우리 팀이 모든 빌드 시스템, 모든 런타임, 모든 운영체제, 모든 프로그래밍 언어, 모든 API, 모든 특이한 동작에 대한 세부 사항을 전부 아는 것은 현실적으로 불가능합니다.

다행히도 이는 코딩 에이전트가 정확히 뛰어난 분야입니다. 코딩 에이전트는 수천 페이지의 문서를 빠르게 훑고, 특수한 API를 모두 읽으며, 바이너리를 파고들고, API를 리버스 엔지니어링할 수 있습니다. 개인 개발자보다 훨씬 더 큰 인내심을 갖고 있습니다.

우리는 Dioxus를 위한 Kotlin 및 Swift 플러그인처럼 빌드 시스템에 깊이 통합된 기능을 구현할 수 있었습니다. 이는 매우 어려운 기능입니다. React Native의 Turbo Modules를 안다면, 이런 기능을 손으로 작성하던 사람들이 제대로 완성하기까지 수년간 개발해야 했다는 사실을 알 것입니다.

코딩 에이전트를 활용해 2~3주 만에 이를 출시할 수 있었고, 아마 더 빠르게도 할 수 있었을 겁니다. 구현 자체는 첫날에 끝났던 것 같습니다. 이후 2주 동안 테스트 사례를 만들고 실제 기기에서 테스트했습니다.

오른쪽에 있는 Blitz, 즉 저희의 맞춤형 웹 엔진(custom web engine)에서는 코딩 에이전트가 까다로운 CSS 스타일링과 레이아웃 문제를 디버깅하는 일을 크게 가속해 주었습니다. 에이전트는 CSS 사양을 놀라울 정도로 잘 알고 있습니다.

어떤 페인팅(painting)이나 레이아웃 문제를 해결하려고 코드 한 줄을 작성하고 있을 때, 에이전트는 Google Chrome과 Safari가 이를 정확히 어떻게 처리하는지 즉시 떠올릴 수 있습니다. 그리고 여러분의 문제에 맞는 올바른 처리 방법을 알려줄 수 있죠. Apple의 Git 저장소 어딘가 깊숙이 묻혀 있는 WebKit 소스 코드를 직접 찾아볼 필요가 없습니다.

저희는 해킹에 가까운 임시방편이 아니라, 올바른 방식으로 작업하는 데 시간을 투자할 수 있게 되었습니다. 예전에 하던 방식과 비교하면 흥미로운 변화입니다. 과거에는 프로젝트의 복잡성을 기준으로 판단하고, 더 빨리 출시하기 위해 인간으로서 지름길을 택하는 경우가 많았습니다. 하지만 높은 품질 기준까지 충족하지는 못했죠.

따라서 코딩 에이전트는 품질을 유지하면서 올바른 방식으로 작업할 수 있게 해줍니다. 매우 흥미로운 점입니다.

야심 찬 프로젝트에서 코딩 에이전트를 활용하는 덜 화려한 사례는 사실 아주 평범하고 지루한 작업을 처리하는 것입니다. 저희 팀은 매우 작습니다. Dioxus에서 일하는 핵심 엔지니어는 세 명입니다.

tarball이 올바른 디렉터리 구조로 압축 해제되는지 확인하는 데 시간을 쓸 때마다, 그 시간은 소프트웨어의 아키텍처와 어려운 문제를 고민하는 데 쓸 수 있었던 시간이 낭비되는 셈입니다.

Dioxus는 규모가 큰 프로젝트이고, 전체 코드베이스와 모든 릴리스에서 높은 품질 기준을 유지하는 일은 어려운 과제였습니다. 한 릴리스에서 Zed 같은 새로운 에디터를 위한 확장 기능을 추가할 수도 있습니다. 패치 릴리스를 할 때마다 그 에디터를 테스트하지 못할 수도 있고, 쉽게 망가뜨릴 수도 있죠.

이 문제에 에이전트를 적용하면 이전에는 수없이 많은 시간이 걸렸을 어렵고 지루한 작업을 상당 부분 자동화할 수 있습니다.

그리고 저희에게는 코드가 곧 제품입니다.

사람들은 코드를 다운로드하고, 그 위에 무언가를 만들며, 사용자들은 API와 상호작용하고, 문서를 읽고, 저희의 아키텍처를 기반으로 개발합니다. 따라서 사용자를 위해 제공하는 코드와 SDK의 품질을 조금이라도 게을리하면 곧바로 더 나쁜 개발자 경험으로 이어집니다. 사람들이 불만을 느끼거나, 비즈니스가 중단되거나, 제품을 꺼버리게 되는 것이죠.

코딩 에이전트는 릴리스 체크리스트를 확인하고, 버그 수정을 안정 릴리스에 백포트(backport)하며, 문서와 문서 주석(doc comment)의 품질을 매우 높게 유지하는 등의 작업을 훌륭하게 수행해 왔습니다. 저희가 직접 문서 주석을 많이 작성하기도 하지만, 모든 것이 제대로 문서화되어 있는지, 모든 항목에 예제가 있는지, 그리고 각 문서가 실제로 설명한다고 적힌 내용을 정확히 설명하고 있는지 확인하는 작업을 에이전트에게 맡기는 것은 매우 쉽습니다.

인간은 코드를 수정하더라도 주석은 수정하지 않는 경우가 있습니다. 그래서 시간이 지나면 많은 주석이 실제 코드와 맞지 않게 되고, 상황이 매우 혼란스러워집니다. 숫자만 보더라도, 최근 Dioxus 버전에서는 그 어느 때보다 많은 패치 릴리스를 출시했습니다. 예전에는 두려워서 하지 못했을 대규모의 야심 찬 소프트웨어에서도 주간 또는 주 2회 이상의 릴리스 주기를 유지할 수 있게 되었습니다.

제가 아직 100% 확신하지 못하는 한 가지는 AI를 사용해 테스트를 작성하는 것, 또는 적어도 테스트를 맹목적으로 작성하는 것입니다. Dioxus에서 저희가 어려움을 겪어온 분야 중 하나가 테스트입니다. 기반 소프트웨어를 테스트하는 일은 매우 어려울 수 있습니다. 특히 복잡한 시스템을 엔드투엔드(end-to-end)로 테스트하는 것은 그렇습니다. 확장 기능이 Zed에 설치되고 원하는 방식으로 작동하는지 확인하려면, 말 그대로 Zed를 열고 확장 기능을 사용해야 하니까요.

코딩 에이전트도 어느 정도는 이 부분에서 어려움을 겪습니다. 또한 엉성한 테스트를 작성하는 경향이 있습니다. 생성자를 주면 생성자를 테스트하는 식인데, 그다지 흥미로운 테스트는 아니죠. 주어진 API에 대한 테스트는 쉽게 작성할 수 있지만, 인간과 마찬가지로 올바른 테스트를 작성하지 못합니다.

저희는 여전히 테스트 조건을 수동으로 나열하고, 테스트 API를 직접 구성하며, 테스트 러너(test runner)를 처리합니다. 하지만 어떤 기능이 충분히 테스트되었는지 확인하기 위해 테스트 아이디어를 생각해 내고 엣지 조건(edge condition)을 나열하는 과정에서 에이전트가 훌륭한 의견 상대가 되기도 합니다.

저희가 테스트에 코딩 에이전트를 활용하면서 실제로 매우 만족했던 한 가지 분야는 테스트 하네스(test harness)를 구축하는 일입니다. 퍼징(fuzzing)은 운영 수준의 소프트웨어를 만드는 데 중요한 부분입니다. 애플리케이션에 수백만 개의 서로 다른 입력을 넣는 것인데, 상당수는 적대적 입력입니다. 기본적으로 잘못 구성된 입력이나 사용자가 사용해서는 안 되지만 사용할 수 있는 방식으로 소프트웨어를 사용하는 경우를 말합니다.

코딩 에이전트는 이런 하네스를 구축하는 데 탁월합니다.

인간 엔지니어와 달리 코딩 에이전트는 어떤 기능이 시스템에 잘 들어맞지 않을 때 자발적으로 대규모 리팩터링을 수행하거나 아키텍처를 재설계하는 일을 대체로 두려워하지 않습니다. 보통은 그냥 출시해 버립니다.

현재 저희 개발 시간의 대부분은 사실 소프트웨어 아키텍처, 앞으로 필요하게 될 기능, 그리고 시스템이 어떻게 발전할지를 고민하는 데 쓰입니다. 인간 엔지니어가 스파게티 코드를 작성할 수 있듯이 에이전트도 그럴 수 있지만, 이제는 그저 더 빠르게 작성할 뿐입니다.

다만 Claude 수준의 도구를 사용하면, 여러분의 의도를 제대로 전달한다는 전제하에 실제 코드 자체의 품질이 매우 높습니다. 따라서 앞으로는 올바른 소프트웨어 아키텍처를 설계하는 일이 대부분의 시간을 차지하게 될 것입니다. 실제 코드 작성은 그렇지 않을 겁니다.
