먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 2분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

AI에게 한 번의 지시만 주고 바로 코드를 만들게 하면 빠르지만, 그 지시가 개인 대화에만 남거나 곧 사라져 팀이 검토하기 어렵다. 코드는 실행돼도 원래 의도와 다를 수 있다.

대안은 원하는 결과를 먼저 문서로 고정하는 명세 중심 개발(스펙 주도 개발)이다. 바꿀 수 없는 원칙은 헌법, 만들 기능과 이유는 명세, 기술과 구현 방법은 계획, 작업 순서는 태스크에 나눠 적는다. 이 문서들을 저장소와 변경 기록에 남기면 사람과 AI가 같은 기준을 다시 사용할 수 있다.

그러나 문서가 있다고 품질이 자동으로 보장되지는 않는다. AI가 만든 헌법·명세·계획·태스크를 사람이 모두 읽고, 빠진 요구와 잘못 선택된 버전 등을 고쳐야 한다. 핵심은 더 긴 프롬프트가 아니라, 검토하고 재사용할 수 있는 합의 문서를 중심 산출물로 만드는 것이다.

여기까지만 이해하면 충분

  • 일회성 프롬프트는 빠르지만 공유·검토·재현이 어렵다.
  • 헌법은 원칙, 명세는 무엇, 계획은 어떻게, 태스크는 작업 순서를 담는다.
  • AI 산출물은 구현 전에 사람이 검토해야 한다.

비유와 깨지는 지점

건축 기준과 설계도

헌법은 반드시 지킬 건축 기준, 명세는 어떤 공간이 왜 필요한지 적은 요구서, 계획은 재료와 공법을 정한 설계, 태스크는 공사 순서에 대응한다. 시공 전에 문서를 검토하면 완성 후의 큰 수정을 줄일 수 있다.

비유가 깨지는 지점: 소프트웨어 명세는 개발 중에도 계속 바뀔 수 있고, AI가 문서를 따랐다고 해서 코드의 정확성이나 보안이 자동으로 보장되지는 않는다.

먼저 기능의 목적과 성공 조건을 적고, 반드시 지킬 규칙을 소수로 정한다. 그다음 기술 선택과 작업 순서를 분리해 작성하고, AI가 만든 각 문서에서 요구 누락·규칙 위반·임의의 버전 선택을 검토한다.

이번 글의 통찰

1. 중심 산출물을 바꾸면 검토 시점이 바뀐다

  • [원문] 화자는 프롬프트 대신 명세를 저장소와 Git 기록에 남기고, 새 기능에서도 같은 기반을 다시 사용하자고 제안한다.
  • [해석] 구현 후 코드를 고치는 것보다 구현 전에 의도와 제약을 검토할 기회가 늘어난다.
  • [경계] 비교 실험이나 품질 수치는 제시되지 않았다. 데모도 준비된 프롬프트와 브랜치를 옮겨 가며 보여 주었으므로 처음부터 끝까지 이어진 실시간 검증은 아니다.

2. ‘무엇’과 ‘어떻게’를 분리해야 선택을 검토할 수 있다

  • [원문] 기능 요구는 명세에, TypeScript·Node.js·HTTP 전송·배포와 같은 기술 선택은 계획에 넣었다.
  • [해석] 목적과 구현 수단을 분리하면 특정 기술이 정말 요구에 필요한지 따로 질문할 수 있다.
  • [경계] 화자는 AI가 지정하지 않은 버전을 채울 수 있으며 최신 버전이 아닐 수도 있다고 경고했다. 계획 역시 사람이 확인해야 한다.

3. 전사의 수량과 명칭에는 확인할 충돌이 있다

  • [원문] 화자는 모든 문서를 검토하라고 반복하며, 마지막에는 작은 실제 기능 하나부터 시작하라고 권한다.
  • [해석] 이 영상의 안전장치는 도구 자체보다 사람의 반복 검토에 있다.
  • [경계] 기능 명세 설명에서는 MCP 도구 3개인 search sessions, get session, happening now를 제시하지만 검사기에서는 get next time을 포함한 4개를 열거한다. 마지막에는 “세 링크”라고 하지만 전사에서 구체적으로 식별되는 것은 SpecKit 문서와 작동 코드 링크 2개뿐이다. 헌법의 여섯 원칙을 처음에는 grounded data, time-aware, agent-safe, HTTP-safe, testable, privacy로 설명하지만 뒤의 요약에는 correctness가 별도 표현처럼 등장해 정확한 원칙명이 불분명하다. 또한 4단계는 헌법·명세·계획·태스크의 문서 구조이며, 분석·명확화·구현까지 포함한 전체 명령 수가 4개라는 뜻은 아니다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 화자는 결과물보다 먼저 목표와 규칙을 문서화하고, 각 문서를 검토하라고 한다.
  • 통찰: 수업에서도 정답 산출보다 학습 목표·평가 기준·수행 단계를 분리하면 이해 여부를 관찰하기 쉽다.
  • 질문/행동: 학습자가 보지 않고 설명해야 할 결과와 반드시 지킬 기준을 먼저 적어 볼 수 있는가?

사업가 · 구조적 비유

  • 관련성: 요구 누락과 재작업 위험을 구현 전에 발견하려는 구조다.
  • 통찰: APOM에 적용한다면 검증 전 가설로만 다뤄야 한다. 작은 운영 기능의 목적·비협상 규칙·기술 선택을 분리했을 때 재작업이 줄어드는지 확인할 수 있다.
  • 질문/행동: 비용을 들이기 전에 승인해야 할 요구와 위험 기준은 무엇인가?

마케터 · 구조적 비유

  • 관련성: 명세의 ‘무엇’과 계획의 ‘어떻게’ 분리는 주장과 표현 수단의 분리와 닮았다.
  • 통찰: 상세페이지를 만든다면 먼저 고객에게 전달할 가치와 필요한 증거를 정하고, 문구·레이아웃은 그다음에 선택하는 가설을 세울 수 있다.
  • 질문/행동: 현재 문서에서 고객 약속과 표현 기법을 서로 구분해 검토할 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: SpecKit을 이용해 헌법·명세·계획·태스크를 만들고 구현으로 연결하는 실제 흐름을 보여 준다.
  • 통찰: 도구 이름보다 요구 누락, 규칙 위반, 버전 선택, 테스트 가능성을 단계별로 측정하는 것이 중요하다.
  • 질문/행동: 작은 후보 기능 하나에서 프롬프트 방식과 명세 방식의 리뷰 결함 수를 비교해 볼 수 있는가?

1. 프롬프트에서 명세로

화자는 자신을 Udo Oliva라고 소개하고 Microsoft MVP이자 Cloud Solution Architect라고 말했다. 현재 고객들의 개발팀이 에이전트형 소프트웨어 개발과 스펙 주도 개발을 받아들이도록 돕는다고 주장했다.

프롬프트 중심 AI 코딩은 시작이 빠르지만, 프롬프트가 개인적이고 임시적이며 리뷰하기 어렵다고 설명했다. 결과물이 빌드되더라도 목적을 완전히 놓칠 수 있으므로, 프롬프트가 아니라 명세를 중심 산출물로 바꾸자고 제안했다.

2. 헌법에서 태스크까지

  1. 헌법: 테스트 가능성, 보안 기준, 기업 지침, 팀 규칙처럼 반드시 지킬 원칙을 둔다.
  2. 명세: 만들 기능과 기능 요구사항을 적되 구현 기술은 넣지 않는다.
  3. 계획: 배포 대상, 기술 스택, 프레임워크, 버전 등 구현 방법을 정한다.
  4. 태스크: 명세와 계획을 구현 가능한 크기와 논리적 순서로 나눈다.

화자는 네 단계가 전체 목록은 아니라고 밝혔다. 생성된 모든 문서를 사람이 읽고 팀이 동의하는지 확인해야 하며, 명세는 저장소와 Git 기록에 남겨 다음 기능에서도 다시 사용한다고 설명했다.

3. SpecKit 설치와 구조

데모 프로젝트에는 GitHub Copilot 지침 폴더, VS Code 설정, 미리 준비한 프롬프트용 데모 폴더, .gitignore, Markdown 파일이 있었다. 따라서 화자도 완전히 빈 프로젝트는 아니라고 바로 정정했다.

Specify CLI가 설치된 상태에서 specify init을 실행하고 Copilot 연동을 선택했다. Windows 환경이라 스크립트 방식으로 PowerShell을 골랐다. 초기화 뒤 specify 폴더가 생겼으며, 화자는 내부가 본질적으로 Markdown과 스크립트이므로 직접 살펴보라고 설명했다.

4. Microsoft Build 세션 플래너 MCP 서버

데모 대상은 Microsoft Build 2026의 세션 데이터를 AI 에이전트가 조회하도록 하는 Session Planner MCP 서버였다. MCP는 AI가 외부 도구와 데이터를 호출할 수 있게 연결하는 규격(Model Context Protocol)이다.

헌법에는 다음 여섯 원칙이 제시됐다.

  • 실제 데이터에만 근거할 것
  • 시간을 정확히 다룰 것
  • 에이전트가 안전하게 사용할 수 있을 것
  • 공개 HTTP 엔드포인트에 안전할 것
  • 처음부터 테스트 가능하게 설계할 것
  • 개인정보 보호를 기본값으로 둘 것

기능 명세에는 세션 검색, 개별 세션 조회, 현재 진행 중인 세션 확인과 JSON 원본 필드가 포함됐다. 계획에는 TypeScript, Node.js, HTTP 전송, 배포와 설정이 들어갔다. 화자는 버전을 명시하지 않으면 AI가 대신 선택하며, 그 선택이 최신 버전이 아닐 수도 있다고 경고했다.

/speckit.tasks는 사용자 이야기와 기술 계획을 구현 순서로 나누고, Node 설정·package.json·Dockerfile·선행 작업 등을 포함한 태스크를 만들었다. 화자는 /speckit.analyze와 /speckit.clarify 같은 중간 검사를 권장한 뒤 /speckit.implement로 코드와 테스트를 생성할 수 있다고 설명했다.

MCP Inspector에서 search sessions, get happening now, get next time, get session의 4개 도구가 표시됐다. 화자는 실행 결과가 작동했다고 시연했지만, 각 생성 단계는 기다리지 않고 준비된 브랜치로 이동했으므로 연속된 전체 실행 데모는 아니었다.

5. 도입 권고와 남는 확인 사항

화자는 전체 작업 방식을 한꺼번에 바꾸지 말고 작지만 의미 있는 실제 기능 하나를 고르라고 권했다.

  1. 프롬프트보다 명세를 먼저 쓰고 무엇과 이유를 기록한다.
  2. 헌법에는 비협상 규칙을 2개에서 5개 정도로 작게 시작한다.
  3. AI가 만든 모든 문서를 검토한 뒤 구현하고 사용해 본다.

헌법은 팀과 조직의 학습을 반영하며 변하는 살아 있는 문서라고 설명했다. 마지막에 세 링크를 공유한다고 했지만, 전사에서 구체적으로 설명된 링크는 SpecKit 문서와 작동 코드 저장소 두 종류뿐이다. 실제 URL은 제공된 전사에 포함되지 않았다.

안녕하세요, 저는 우도 올리바(Udo Oliva)입니다. 저는 Microsoft MVP이자 클라우드 솔루션 아키텍트(Cloud Solution Architect)입니다. 현재 고객들과는 개발 팀이 에이전트형 소프트웨어 개발(agentic software development)을 개선하고 명세 주도 개발(spec-driven development) 방식을 진정으로 받아들이도록 돕는 일만 하고 있습니다. 이를 위해 GitHub를 사용합니다.

저희는 GitHub를 정말 좋아해서 GitHub Enterprise, GitHub Copilot, 그리고 GitHub의 SpecKit을 사용합니다. 가장 큰 단점은 GitHub가 정말 멋진 기능을 너무 많이 출시해서, 이를 따라잡는 것만으로도 거의 본업이 되어 버린다는 점입니다. 그러니 새로운 기능에 대한 릴리스 노트(release notes)를 꼭 확인해 보세요. 분명 머지않아 거기에 나와 있을 겁니다.

가능한 한 빨리 Visual Studio Code와 데모로 넘어가고 싶지만, 그 전에 우리가 어디에서 출발했는지 알기 위해 잠시 되돌아봐야 합니다.

그렇게 오래된 일은 아니지만, 프롬프트 우선 AI 코딩(prompt-first AI coding)이 우리를 시작하게 해 주었습니다. 우리를 움직이게 했고, 빠르고 놀라웠습니다. 앞서 말했듯이 AI와 소프트웨어 개발을 시작하는 데 정말 큰 도움이 됐습니다. 하지만 더 큰 프로젝트, 실제 프로젝트, 기업 환경, 더 큰 팀에서는 프롬프트가 매우 취약한 기반이 될 수 있습니다. 대개 개인적이고 일시적이며, 검토하기 어렵고, 보통은 빌드되지만 때로는 완전히 핵심을 벗어난 결과를 만들어 내기 때문입니다.

오늘 보여 드리고 싶은 변화는 간단합니다. 프롬프트를 주요 산출물로 취급하는 것을 멈추고, 명세를 주요 산출물로 취급하기 시작하는 것입니다. 이 말이 이번 세션 전체를 한 문장으로 요약한 것이지만, 더 살펴볼 내용이 정말 많습니다.

데모로 넘어가기 전에 이 멘탈 모델(mental model)을 먼저 명확히 해야 할 것 같습니다. 그래야 이후의 모든 내용이 이해될 테니까요.

프롬프트 우선 개발은 다음과 같은 모습입니다. 여러분이 지시문을 작성하고, 모델이 코드를 작성한 다음, 여러분은 깜짝 결과를 얻습니다. 많은 경우 아주 기분 좋은 놀라움이지만, 그렇지 않을 때도 있고, 그러면 오후 내내 왜 그런 결과가 나왔는지 알아내느라 시간을 보내게 됩니다.

명세 우선 개발(spec-first development)은 이를 다르게 바라봅니다. 먼저 헌장(constitution)을 작성합니다. 헌장은 우리가 절대 깨서는 안 되는 규칙이며, 대개 프로젝트보다 크고 팀보다도 큽니다. 여기에는 테스트 가능성을 고려한 설계, 보안 표준, 기업 가이드라인, 팀별 규칙 등 프로젝트에 반드시 필요한 요구 사항이 들어갑니다. 즉, 코딩 AI 어시스턴트가 반드시 지키기를 원하는 모든 것이 포함됩니다.

그다음에는 애플리케이션의 기능 명세인 명세(spec)가 있습니다. 이것은 우리가 무엇을 만들고 싶은지 설명합니다. 모든 기능과 기능적 요구 사항을 명시하지만, 기술적인 내용은 포함하지 않습니다. 방법(how)은 포함하지 않습니다. 그것은 계획(plan)을 위해 남겨 둡니다.

계획에서는 배포 대상, 사용할 기술 스택, 프레임워크, 버전 관리 방식 등을 비롯해 모든 기술적 사양을 관리합니다.

그다음에는 이를 관리 가능한 단위로 나누고 싶습니다. 작업 단계(task phase)에서 그렇게 합니다. 코드를 개발하고 구현할 때 의미가 통하도록 논리적인 순서로 나눕니다.

그리고 매우 중요합니다. 아무리 강조해도 지나치지 않습니다. 모든 것을 검토하세요. AI가 생성하는 모든 것을 검토하되, 특히 이런 명세 주도 개발 프레임워크를 사용할 때는 더욱 그렇습니다. 이 도구가 우리 앞에 내놓는 문서를 하나도 빠짐없이 검토하세요. 헌장을 확인하고, 명세를 확인하고, 계획을 확인하세요. 그 내용이 무엇을 말하는지 반드시 이해해야 합니다. 여러분이 동의하고 있는지, 팀도 동의하는지 확인해서 모두가 같은 내용을 공유하도록 해야 합니다. 그래야 나중에 여러분이 원하는 품질의 결과물을 실제로 만들어 낼 수 있습니다.

명세에는 더 많은 측면이 있습니다. 여기서 살펴볼 단계는 네 가지입니다. 이것이 완전한 목록은 아닙니다. 명세 주도 개발 프레임워크를 진행할 때 시작점으로 삼고 다뤄야 할 내용들입니다. 헌장에서 코드까지 모든 것을 포함합니다. 나머지 단계는 SpecKit 문서를 확인해 주세요. 마지막 슬라이드에서 링크를 공유하겠습니다.

이렇게 하면 명세가 저장소의 일부이자 Git 기록의 일부가 됩니다. 다음에 새 기능을 구현할 때도 다시 이 기반에서 시작합니다. 새 기능 명세를 추가하고 이 과정을 다시 따릅니다.

하지만 이제 슬라이드는 충분히 봤으니, Visual Studio Code로 가서 실제로 어떻게 작동하는지 보여 드리겠습니다.

지금 보고 있는 것은 우리가 만들려고 하는 것입니다. 이것은 Microsoft Build 2026 세션이었고, 이를 위해 Session Planner MCP 서버를 만들었습니다.

물론 Microsoft Build에는 정말 멋진 세션이 많이 있습니다. 지금도 온라인에서 시청할 수 있으니 꼭 보시길 권합니다. 이런 행사에서 Session Planner는 일종의 일정표와 같습니다. 그날 무엇을 하고 무엇을 볼지 정해 주죠. 사용할 수 있는 훌륭한 CLI가 있었지만 MCP 서버가 없었습니다. 그래서 제가 MCP 서버를 만들었습니다. 아니, 더 정확히 말하면 오늘 데모에서 우리가 만들 겁니다.

브랜치 이름에서 볼 수 있듯이 이 프로젝트는 비어 있습니다. 완전히 비어 있는 것은 아니지만, 보여 드리자면 특별한 것은 없습니다. GitHub 폴더에는 GitHub Copilot 지침이 들어 있습니다. VS Code 폴더에는 제가 사용하는 VS Code 설정이 들어 있으므로 이 MCP 서버와는 아무 관련이 없습니다. demo 폴더도 있습니다. 이것은 제가 여러분 앞에서 타이핑하는 모습을 보여 드리지 않기 위한 것이므로, 여러분은 볼 필요가 없습니다. 오늘 사용할 프롬프트 몇 가지를 미리 준비해 두었습니다. 그다음에는 .gitignore 파일과 물론 이 Markdown 파일이 있습니다.

이 프로젝트에는 그 외에는 아무것도 없습니다. 시작하려면 SpecKit을 설치해야 합니다. Specify CLI가 설치되어 있으므로 이제 터미널을 열고 다음의 매우 유용한 명령을 복사하겠습니다. 이 프로젝트에 SpecKit을 설치하기 위한 specify init입니다.

여기서 specify init을 실행하면, 사용 중인 AI 하니스(AI harness), 즉 AI 도구에 대한 통합을 지정해야 합니다. 선택한 통합 유형에 따라 해당 사용자 지정 지침을 연결해 주기 때문입니다. 저는 Copilot을 사용하고 있으므로 여기서 Copilot 통합을 사용하겠습니다.

이를 실행하면 멋진 Specify 터미널 창이 나타납니다. “음, 그렇게 비어 있지는 않네요. 계속하시겠습니까?”라고 묻습니다. 물론 계속해야 합니다. 스크립팅에 Bash, PowerShell, Python 중 무엇을 사용할지도 묻습니다. 저는 Windows를 사용하고 있으므로 PowerShell을 사용하는 것이 합리적입니다.

그러면 모든 과정이 매우 빠르게 진행됩니다. SpecKit 프로젝트를 초기화하고, 필수 구성 요소가 설치되어 있는지 확인하며, SpecKit 프레임워크를 사용할 수 있도록 GitHub Copilot을 연결합니다. 자격 증명과 인증 토큰에 관한 유용한 힌트도 제공합니다.

다른 명령들도 여기에 나와 있습니다. 이것이 전체 목록은 아닙니다. 문서에는 더 많은 SpecKit 명령이 있습니다.

이 설치를 통해 새로운 specify 폴더가 생겼습니다. 꼭 둘러보시길 권합니다. SpecKit이 제공하는 기능을 직접 확인하고, 그 안에 있는 마법 같은 요소를 이해하고 싶을 테니까요. 이것은 Markdown과 스크립팅일 뿐이며, 물론 매우 강력합니다. 오해하지 마세요. 저도 SpecKit을 사용하는 것을 좋아합니다. 하지만 결국에는 여기서 별다른 속임수가 일어나고 있지 않다는 점을 이해하는 것이 도움이 됩니다. 그저 Markdown과 스크립팅일 뿐입니다.

SpecKit 설치가 끝났으니 이제 헌장으로 넘어갈 준비가 됐습니다. 말씀드렸듯이 여기에는 프롬프트를 몇 가지 준비해 두었습니다. Build Session Planner용 HTTP MCP 서버에 대한 프로젝트 헌장이 있고, 여기에 몇 가지 내용을 넣었습니다.

이것은 모든 사람이 반드시 사용해야 하는 목록은 아닙니다. Build Session Planner MCP 서버를 만들 때 의미가 있었던 내용들입니다. 저는 근거가 있는 데이터만 사용하고 싶습니다. 존재하지 않는 세션을 만들어 내기를 원하지 않기 때문입니다. 데이터를 근거에 기반하게 하는 것이 매우 중요합니다.

시간을 인식하도록(time-aware) 하고 싶습니다. 시간은 소프트웨어 개발에서 다루기 어려운 개념이므로, AI 어시스턴트가 이러한 세션에서 시간이 얼마나 중요한지 이해하도록 해야 합니다. 곧 시작하는 세션을 보고 있다면 이를 잘못 처리하고 싶지 않습니다.

에이전트 안전(agent-safe)을 원합니다. MCP에서는 보안과 인증을 적용하기가 때때로 어렵기 때문입니다. 안전한 도구 설계를 만들고 싶습니다. 또한 HTTP 안전성(HTTP-safe)을 원합니다. 이것은 MCP이고 공개 엔드포인트에 배포할 수 있으므로, 외부에 공개해도 안전해야 합니다.

설계 단계에서부터 테스트 가능(testable by design)하도록 하고 싶습니다. 이는 언제나 좋은 생각입니다. 그리고 기본적으로 개인정보를 보호하는 프라이버시 기본값(privacy by default)을 원합니다. 공개 세션 목록이지만, 현재로서는 이것을 헌장에 포함하는 것이 여전히 타당합니다.

이것들이 제가 애플리케이션이 반드시 따르기를 원하는 절대 깨서는 안 되는 규칙입니다.

제가 미리 준비해 두었기 때문에 여러분은 제가 타이핑하는 모습을 볼 필요가 없습니다. 이런 프롬프트를 준비하는 일은 꽤 많은 작업이 될 수 있지만, AI가 이를 도와줄 수도 있습니다. 헌장을 시작하려면 헌장에 대한 SpecKit 명령을 사용하고 프롬프트를 붙여 넣으면 됩니다.
