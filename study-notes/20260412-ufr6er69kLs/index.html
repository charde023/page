Claude Code를 이 5가지 에이전트 패턴과 함께 쓰면 훨씬 더 잘 작동합니다

Claude Code를 대화 하나씩 순서대로 쓰는 것은 병목이며, 5가지 에이전트 패턴을 상황에 맞게 골라 쓰면 속도·정확도·자율화 세 가지를 동시에 올릴 수 있다.

서브 에이전트 컨텍스트 분리 정확도 핵심 원리 각 서브 에이전트가 새 컨텍스트 윈도우를 받아 오염 방지

내가 모를 만한 것 / 처음 보는 것

  • Headless 모드 (claude --p "...") — Claude Code를 인터랙티브 세션 없이 터미널 명령으로 구동, 결과만 반환
  • Git Worktree — 하나의 저장소에서 여러 브랜치를 동시에 격리된 디렉토리로 체크아웃하는 git 기능; 세션별 환경 충돌 차단
  • DBOD 스킬 — 화자가 직접 만든 데이터베이스 감사 자동화 스킬 (스키마·보안·인덱스를 서브 에이전트로 병렬 점검)
  • Null Loop (날프 루프) — 조건이 충족될 때까지 Claude Code를 계속 반복 실행하는 자율 루프 패턴
  • Iterative Review 스킬 — 풀 리퀘스트를 N회 반복 리뷰, 매 반복마다 헤드리스 세션으로 새 컨텍스트 할당
  • Playwright (플레이라이트) — 브라우저 자동화 테스트 도구; 버그 재현·검증에 사용
  • Supabase MCP (소파베이스 MCP) — Supabase DB에 연결하는 MCP; 감사 워크플로우에 통합

화자의 디테일 (놓치기 쉬운 포인트)

  1. "대화 하나씩 기다리는 건 팀을 운영하는 방식이 아니라 병목"이라고 명시 — 단일 세션 사용이 근본 안티패턴임을 강조
  2. Sequential Flow에서도 서브 에이전트를 쓸 수 있다 — 순차 패턴 = 서브 에이전트 금지가 아님. 순서만 강제됨
  3. 컨텍스트 분리가 정확도의 핵심 이유 — 서브 에이전트마다 새 컨텍스트 윈도우, 메인 스레드 컨텍스트 오염 방지
  4. Iterative Review에서 헤드리스로 5~7개 서브 에이전트를 동시에 한 반복에서 구동
  5. 리뷰 팀즈 스킬: 특화 리뷰어 4명 + 반대의견 역할 1명 = 총 5명 팀
  6. 오퍼레이터 패턴의 두 가지 실익: ① 병렬 구현으로 속도 향상, ② A/B 테스트처럼 결과 비교 후 최선 선택
  7. 스킬 내에서 sh-script를 실행해 md 파일에 저장된 프롬프트를 읽어 헤드리스 명령 발행 — 스킬 + 헤드리스 조합 구조
  8. 헤드리스 모드를 매일 오전 7시, 20분마다, 특정 트리거 발생 시 등 다양한 스케줄로 구성 가능하다고 언급
  9. 에이전트 팀이 적합한 경우: 같은 기능(예: 결제)을 프론트엔드·백엔드 에이전트가 함께 작업하며 소통해야 할 때. 소통이 불필요하면 팀 불필요
  10. Git Worktree 세션이 마음에 안 들면 그냥 삭제, 나머지 세션에 영향 없음

# 섹션 요지
1 Sequential Flow 순서 의존 작업 자동화 — Jira 읽기 → 재현 → 수정 → 검증 → 배포
2 Split and Merge 큰 작업을 서브 에이전트로 병렬 분할, 오케스트레이터에 합침
3 Agent Teams 공유 소통 채널로 에이전트 간 협업, 반대의견 역할 포함
4 Operator Git Worktree 기반 격리 환경, 세션 충돌 방지 + A/B 테스트
5 Headless --p 플래그 백그라운드 실행, Null Loop + 스케줄 자동화

1. Sequential Flow (순차 흐름)

작업이 반드시 하나씩 순서대로 완료되어야 하는 자동화에 맞는 패턴. 화자의 FixTicket 스킬 예시:

  1. Jira MCP로 티켓 읽기
  2. Playwright로 버그 재현 확인
  3. 조사 및 구현 (서브 에이전트 활용 가능)
  4. 변경사항 코드 리뷰 (프론트/백엔드/테스트 전담 에이전트 팀)
  5. Playwright로 변경 검증
  6. 커밋 + 배포 + QA 세션으로 이관

순차 패턴에서도 서브 에이전트를 쓸 수 있다. "순차"의 의미는 각 단계 사이의 의존관계가 있어 병렬 불가라는 뜻이지, 단계 내부에서 서브 에이전트를 금지한다는 뜻이 아니다.

적합 조건: 앞 단계 결과 없이 다음 단계를 시작할 수 없는 파이프라인

2. Split and Merge (분할 합병)

큰 작업을 병렬 가능한 단위로 쪼개어 여러 서브 에이전트에 분배하고, 완료 후 오케스트레이터 하나로 결과를 수렴.

왜 좋은가: - 속도: 병렬 처리 - 정확도: 각 서브 에이전트가 좁은 영역에 집중, 컨텍스트 오염 최소화

화자의 DBOD 스킬 예시 (DB 감사): - 에이전트 A: 스키마 검토 - 에이전트 B: 보안 점검 - 에이전트 C: 쿼리 최적화·인덱스 추가 검토 - (일부) Supabase MCP 연동 전체 감사 - 전부 완료 후 오케스트레이터로 결과 합산

리뷰 스킬 예시: 코드 리뷰 요청이 들어오면 서브 에이전트 3개를 동시에 구동. 각 에이전트는 코드 품질·테스트·디자인·코드 냄새·리팩터링 용이성 등 특화 영역 담당.

3. Agent Teams (에이전트 팀)

Split and Merge와의 차이점: 서브 에이전트들이 공유 소통 채널을 통해 실시간으로 정보 교환.

구조: - 팀 리더(오케스트레이터) - 공유 소통 채널 (모든 에이전트가 읽고 씀) - 반대의견 역할: 시니어/스태프 엔지니어처럼 모든 결정을 계속 의심하고 질문

역할 분담 예시: - 에이전트 1: 아이디어 생성 - 에이전트 2: 계획 수립 - 에이전트 3: 실행 또는 리서치 - 에이전트 4 (반대의견): 지속적 검증·도전

화자의 실전 활용: - 리뷰 팀즈 스킬: 특화 리뷰어 4 + 반대의견 1, 풀 리퀘스트 전체를 팀 단위 리뷰 - 스펙 팀: 주제 하나를 여러 에이전트가 병렬 리서치 후 결과 합산

적합 조건: 같은 기능을 함께 작업하며 에이전트 간 소통이 필요할 때 (예: 결제 기능의 UI·백엔드 동시 구현). 각 에이전트가 독립 영역만 담당해 소통이 불필요하다면 Split and Merge로 충분.

4. Operator (오퍼레이터 / Git Worktree)

각 Claude Code 세션을 격리된 Git Worktree 환경에서 실행해 세션 간 충돌 방지.

작동 방식: - 터미널 세션 A: 기능 X 구현 (Worktree A) - 터미널 세션 B: 기능 Y 구현 (Worktree B) - 터미널 세션 C: 기능 Z 구현 (Worktree C) - 각 세션은 독립된 환경 → 변경 충돌 없음

실전 A/B 테스트 활용: - 세션 1: 랜딩 페이지 버전 A 디자인 - 세션 2: 랜딩 페이지 버전 B 디자인 - 세션 3: 랜딩 페이지 버전 C 디자인 - 마음에 드는 것 선택 → 나머지 Worktree 삭제 → 메인 브랜치에 합병

두 가지 이점: 1. 병렬 구현으로 전체 속도 향상 2. 결과 비교 후 최선 선택 → AI 실수 리스크 분산

각 세션 내부에서는 순차 흐름·서브 에이전트·에이전트 팀 등 다른 패턴을 그대로 사용 가능.

5. Headless (헤드리스)

화자가 "가장 좋아하는 방식"이라고 언급한 패턴. Claude Code를 인터랙티브 세션 없이 터미널 명령으로 구동.

핵심 명령 형태:

claude --p "프롬프트 내용"

→ 백그라운드에서 실행, 결과만 터미널로 반환

강력한 이유: - 스케줄링 가능: 매일 오전 7시, 20분마다, 특정 트리거 시 - Null Loop 결합: 조건 충족될 때까지 반복 실행 (버그 수정 자동화, UI 다듬기 등) - 스킬 + 헤드리스: md 파일에 저장된 프롬프트를 sh-script가 읽어 헤드리스 명령으로 발행

Iterative Review 스킬 구조 (화자가 직접 구현): 1. 풀 리퀘스트 URL 또는 브랜치명 입력 2. 스킬이 sh-script 실행 → md 파일의 프롬프트 읽기 3. 헤드리스 명령으로 서브 에이전트 5~7개 동시 구동 (각각 새 컨텍스트 윈도우) 4. 반복 횟수 N번 지정 → 매 반복 = 새 헤드리스 세션 5. 전체 반복 결과를 하나의 보고서로 합산

핵심: 커피 마시러 간 사이에도 Claude Code가 혼자 돌아가게 만드는 진짜 자율화 패턴

전체 전사 펼치기

아직도 Claude Code를 대화 하나씩만 쓰고 있다면 완전히 잘못 쓰고 있는 겁니다. 대부분은 일 하나 맡기고 앉아서 기다렸다가 또 다음 일을 주죠. 그건 팀을 운영하는 방식이 아니라 병목입니다. 그래서 이 영상에서는 단순한 방식부터 완전 자율화까지 5가지 에이전트 패턴을 보여드립니다.

커뮤니티 광고 (스킵): Amazon·Microsoft 시니어 AI 소프트웨어 엔지니어 경력 기반으로 운영하는 스쿨 커뮤니티 소개. 100개 이상 영상 자료, 템플릿·워크플로우, 매주 라이브 통화 포함.

패턴 1. Sequential Flow (순차 흐름)

FixTicket 스킬 예시 — 버그 수정 전체 과정 자동화. 순서: Jira MCP로 티켓 읽기 → Playwright로 재현 확인 → 조사 및 구현 → 여러 서브 에이전트 변경사항 검토(프론트/백엔드/테스트 전담) → Playwright로 검증 → 커밋 + 배포 + QA 이관.

순차 패턴이라고 서브 에이전트를 못 쓰는 건 아님. QA 단계에서 서브 에이전트를 호출해 메인 스레드 컨텍스트 절약 가능. 핵심은 이 작업들이 순서대로 진행돼야 한다는 것.

패턴 2. Split and Merge (분할 합병)

큰 작업을 병렬 처리 가능한 서브 에이전트로 나누고, 완료 후 오케스트레이터로 합침. 훨씬 빠르고 컨텍스트가 흐려지는 문제도 줄어 정확도 향상.

DBOD 스킬 예시: 에이전트별로 스키마 검토 / 보안 점검 / 쿼리 최적화·인덱스 개선 / Supabase MCP 연동 전체 감사를 병렬 수행, 완료 후 오케스트레이터로 수렴.

리뷰 스킬 예시: 서브 에이전트 3개 동시 실행. 코드 품질·숨겨진 실패·테스트·디자인·코드 냄새·리팩터링 용이성 등 특화. 리뷰어 8명짜리 병렬 리뷰 + 자동 수정 + 자동 검토 구성도 가능.

패턴 3. Agent Teams (에이전트 팀)

이전 서브 에이전트와의 차이: 에이전트들이 공유 소통 채널로 서로 정보 교환. 팀 리더(오케스트레이터) + 공유 채널 + 반대의견 역할(Devil's Advocate — 시니어/스태프 엔지니어처럼 모든 것에 의문 제기).

역할 분담 예시: 아이디어 / 계획 / 실행·리서치 / 검증·도전. 각자 새 컨텍스트 윈도우 보유 → 정확도 향상.

적합한 경우: 같은 기능을 함께 작업 (예: 결제 기능 — UI 에이전트 + 백엔드 에이전트가 소통하며 진행). 소통이 불필요하면 굳이 팀 쓸 이유 없음.

패턴 4. Operator (오퍼레이터)

각 Claude Code 세션마다 격리된 환경(Git Worktree) 생성. 여러 터미널 세션을 동시에 열고 각 세션에서 Claude Code를 따로 실행해도 세션 간 충돌 없음. 마음에 안 드는 Worktree는 그냥 삭제 → 나머지 세션에 영향 없음.

활용: 랜딩 페이지 버전 A/B/C를 세 세션이 동시 디자인, 가장 나은 것 선택 후 나머지 삭제, 메인 브랜치로 합병. AI 에이전트도 실수하니 결과 하나에 의존하지 않고 비교 후 최선 선택 → 생산성 향상.

패턴 5. Headless (헤드리스)

Claude Code를 인터랙티브 세션 없이 claude --p "프롬프트" 명령으로 백그라운드 구동. 결과만 터미널로 반환.

강력한 이유: ① 스케줄링 (매일 오전 7시, 20분마다, 특정 트리거 시); ② Null Loop 결합으로 조건 충족까지 반복 실행; ③ 스킬 + sh-script + md 파일 프롬프트 조합으로 완전 자율화.

Iterative Review 스킬 구조: 풀 리퀘스트 URL 입력 → sh-script가 md 파일 프롬프트 읽기 → 헤드리스로 서브 에이전트 5~7개 동시 구동 (각각 새 컨텍스트 윈도우) → N회 반복 → 전체 발견 사항을 하나의 보고서로 합산.
