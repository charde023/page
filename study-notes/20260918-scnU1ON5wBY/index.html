Vercel은 어떻게 AI 에이전트 개발 문제를 해결했을까요?

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 모델보다 먼저 업무 구조를 바꿨다

이 영상은 단순히 더 강한 AI 모델을 도입한 이야기가 아니다. 화자가 설명한 핵심은 사람이 실제로 처리하던 업무를 에이전트가 어떤 구조로 따라가게 할 것인가에 가깝다.

Vercel의 데이터 팀은 마케팅이나 영업 부서에서 질문을 받을 때마다 하던 일을 멈추고, 데이터 조회문을 작성하고, 결과를 분석해 다시 전달해야 했다. 회사와 데이터 양은 커지는데 데이터 팀은 상대적으로 작은 상태였기 때문에, 반복 질의가 병목이 됐다는 것이 화자의 설명이다.

화자는 이 문제를 해결하기 위해 데이터 과학 에이전트 D0를 만들었다. 처음에는 거대한 지시문 하나에 질문과 데이터 구조를 넣었다. 그다음에는 업무 단계를 역할별 에이전트로 쪼갰다. 이후에는 하나의 에이전트가 자기 작업 상태를 관리하게 했고, 마지막에는 파일을 읽고 쓰며 필요한 작업을 탐색하는 구조로 바꿨다. 반복 질의에서 얻은 지식은 별도의 스킬(Skills)로 축적했다. 이 개발 경험을 일반화한 프레임워크가 화자가 소개한 Eve다.

읽는 법: 왼쪽에서 오른쪽으로 읽는다. 이것은 성능 수치를 나타내는 그래프가 아니라, 화자가 설명한 문제와 해결 구조의 관계를 압축한 개념 지도다. 중요한 점은 한 번에 완성된 설계를 찾은 것이 아니라, 실제 사용에서 드러난 실패가 다음 구조를 만들었다는 것이다.

첫 시도: 큰 지시문과 역할별 체인

첫 번째 형태는 데이터베이스의 구조를 설명하는 Snowflake 스키마를 하나의 큰 시스템 프롬프트에 붙이고, 질문을 넣어 SQL을 생성하게 하는 방식이었다. SQL의 실행과 결과 확인은 화자가 직접 복사해 처리했다. 이 단계의 목적은 모델이 적절한 구조를 받았을 때 유효한 SQL을 만들 가능성이 있는지 확인하는 것이었다.

다음에는 데이터 과학자의 업무를 질문 해석, 계획, SQL 실행, 보고 같은 단계로 나눴다. 각 단계에는 전용 지시문과 제한된 도구를 가진 별도의 에이전트를 배치했다. 예를 들어 계획 에이전트는 데이터 구조를 읽거나 검색하는 도구만 사용하고, 정리한 내용을 SQL 에이전트에 넘겼다.

이 구조는 질문부터 보고까지 전체 과정을 자동으로 이어 줬지만 한계가 있었다. 다음 에이전트가 이전 작업 전체를 보는 것이 아니라 요약과 작은 일부만 받았기 때문이다. 실행 오류나 비싼 조회가 생겼을 때 이전 판단을 다시 살피고 다른 경로를 찾기가 어려웠다.

한 에이전트가 작업 과정을 되돌아보게 하다

화자는 역할별 체인 대신, 하나의 에이전트가 계획·실행·보고를 오가며 자기 상태를 관리하는 형태로 바꿨다. 이 에이전트는 최대 100단계까지 진행할 수 있도록 구성됐다고 한다. SQL 실행이나 데이터 결합에서 오류가 나면 이전 단계로 돌아가 더 탐색하거나 자료를 다시 읽을 수 있었다.

그러나 내부 평가에서 화자가 표현한 성과는 약 30%였고, 제한된 실제 사용자에게 배포하자 반응은 “형편없다”는 쪽이었다. 미리 만든 평가 질문으로는 실제 사용자가 던질 질문을 충분히 예상하지 못한 것이다. 가능한 상황을 사람이 계속 추가하는 방식도 확장 가능해 보이지 않았다고 설명한다.

읽는 법: 화살표는 “앞 방식이 완전히 틀려 폐기됐다”는 뜻이 아니라, 앞 단계에서 발견한 한계를 다음 구조가 보완했다는 뜻이다. 시간 간격은 표시하지 않는다.

돌파구: 전용 도구를 늘리기보다 파일을 탐색하게 하다

화자는 Claude Code와 Opus 4.5를 사용하며 파일 시스템 중심 구조에서 돌파구를 봤다고 말한다. 에이전트에게 세분된 전용 도구를 계속 추가하는 대신, 파일 목록 확인, 파일 읽기와 쓰기, Bash 실행처럼 모델이 다루기 익숙한 소수의 도구를 제공했다. Vercel의 데이터 업무에 꼭 필요한 도구만 그 위에 더했다.

D0는 격리된 실행 공간인 샌드박스 안에서 데이터의 의미와 연결 관계를 설명하는 자료인 시맨틱 레이어(semantic layer)를 파일로 살펴볼 수 있게 됐다. 필요한 작업 기록도 파일에 쓸 수 있었다. 화자는 이 전환 뒤 평가 점수가 “기본적으로 두 배가 됐다”고 표현한다.

파일 시스템이 자동으로 정답을 보장하는 것은 아니다. 핵심은 에이전트가 미리 고정된 짧은 경로만 따르지 않고, 작업 중 생긴 자료를 다시 읽으며 탐색 경로를 바꿀 수 있게 했다는 데 있다.

읽는 법: 오른쪽 구조가 모든 작업에서 우월하다는 보편적 실험 결과가 아니다. 화자가 D0라는 데이터 질의 업무에서 관찰했다고 설명한 차이다. 구체적인 비용, 지연 시간, 오류율은 전사에 제시되지 않았다.

매번 처음 시작하는 문제를 스킬로 보완하다

파일 시스템 구조가 좋아져도 각각의 새 실행은 기본적으로 처음부터 시작했다. 당시 Vercel에서는 하루에 수천 건의 질의가 들어왔고, 집계, 제품 조회, 청구 정보 확인처럼 형태가 비슷한 질문이 반복됐다고 화자는 말한다.

Vercel은 최근 질의를 정기적으로 살펴 공통 해결법을 스킬로 정제하는 작업을 만들었다. 전사 시점에는 약 100개의 스킬이 있다고 한다. 스킬은 이전 대화를 그대로 저장한 장기 기억이라기보다, 반복해서 유용했던 회사별 지식과 처리법을 다음 실행이 읽을 수 있는 형태로 정리한 자료다.

이 부분은 파일 시스템만으로 충분하지 않다는 점도 보여 준다. 에이전트가 자유롭게 탐색할 수 있어도 회사의 데이터가 무엇을 뜻하는지, 어떤 데이터를 언제 조회해야 하는지, 서로 무엇이 연결되는지를 모르면 업무 품질이 제한된다. 화자는 범용 제품보다 회사 특화 지식이 실무 에이전트의 품질을 크게 좌우한다고 주장한다.

Eve: 마지막 시행착오에서 시작하게 하는 규칙

Vercel 내부에서 다른 사람들이 D0를 바탕으로 각자의 에이전트를 만들려 할 때마다 같은 시행착오가 반복됐다. 화자와 팀은 웹 개발에서 Next.js가 파일 배치 규칙을 제공하듯, 에이전트도 정해진 폴더 규칙으로 조립할 수 있어야 한다고 판단했다.

그 결과 소개된 것이 Eve다. 스킬, 도구, 채널 폴더에 파일을 넣으면 프레임워크가 이를 에이전트로 구성하는 방식이다. 실행 환경에는 지속 실행, 격리 환경, 모델 호출, 외부 연결 같은 요소가 포함된다. 화자는 Postgres, OpenAI Responses API, Docker 등을 위한 오픈소스 어댑터를 연결할 수 있고, 직접 호스팅하는 선택지도 있다고 설명한다.

Vercel에 배포하면 실행 기록, 도구 호출, 단계, 예상 비용과 최적화 가능성을 관찰할 수 있다고 한다. D0도 Eve로 다시 작성했다. 베타 고객 Aura는 기존 Claude Code 기반 방식과 비교해 더 적은 단계, 더 나은 성공과 통찰을 얻었다고 화자가 말하지만, 비교 조건과 수치는 제시되지 않았다.

무엇이 중요하고, 어디까지 믿어야 하는가

이 영상에서 남는 원리는 에이전트를 먼저 만들지 말고 반복되는 업무 병목을 찾으라는 것이다. 그다음 실제 사용자가 던지는 질문으로 실패를 관찰하고, 역할을 더 잘게 쪼개는 것과 에이전트가 스스로 탐색하게 하는 것 중 어느 구조가 맞는지 시험한다. 반복 해결법은 스킬처럼 검토 가능한 자료로 축적한다.

다만 영상 속 수치와 성공 평가는 화자의 발표 주장이다. 약 30%의 평가 성과, 점수 두 배, 블로그가 Vercel.com 트래픽의 70%를 만들었다는 수치, 하루 수천 건의 질의, 약 100개 스킬, 약 20개 에이전트 모두 독립 자료로 검증되지 않았다. “두 배”도 같은 평가 세트에서 30%가 정확히 60%가 됐다는 뜻으로 단정할 수 없다.

또한 “약 1년 전”, “2주 전”, “오늘”은 발표 시점을 기준으로 한 상대 표현이다. 제공된 업로드일만으로 실제 사건 날짜를 확정하면 안 된다.

여기까지만 이해하면 충분

  • D0는 메가 프롬프트에서 역할별 체인, 상태 관리형 단일 에이전트, 파일 시스템·스킬 구조로 발전했다.
  • 역할별 체인은 전문화에는 유리했지만 이전 작업의 전체 맥락을 다시 살피고 오류에서 돌아가는 데 한계가 있었다.
  • 파일 시스템은 자유로운 탐색 공간을 제공했고, 스킬은 반복 질의에서 얻은 회사 특화 지식을 다음 실행에 전달했다.
  • Eve의 핵심은 더 강한 모델 자체가 아니라 폴더와 파일 규칙으로 에이전트 구성 요소를 조립하게 하는 것이다.

비유와 깨지는 지점

공용 작업실과 작업 매뉴얼

역할별 에이전트 체인은 한 사람이 자기 작업을 요약해 다음 사람에게 넘기는 조립 라인과 비슷하다. 파일 시스템 에이전트는 한 작업자가 공용 작업실에서 자료와 중간 결과를 다시 꺼내 보며 순서를 바꾸는 것과 닮았다. 스킬은 자주 성공한 작업법을 정리한 매뉴얼에 해당한다.

비유가 깨지는 지점: 실제 에이전트는 파일의 의미를 사람처럼 안정적으로 이해하지 않는다. 모델, 도구 권한, 실행 환경, 회사별 지식, 평가 기준이 함께 맞아야 하며, 파일과 매뉴얼만 제공한다고 정답이 보장되지는 않는다.

각 에이전트가 이전 작업 전체가 아니라 요약과 일부 결과만 받아 오류의 원인을 다시 탐색하기 어려웠다. 내부 평가 질문도 실제 사용자의 다양한 질문을 충분히 대표하지 못했다. 따라서 정해진 평가에서는 약 30%를 맞혔다고 느꼈지만, 실제 배포에서는 예상하지 못한 질문이 드러났다.

먼저 반복 빈도가 높고 입력과 성공 기준을 관찰할 수 있는 업무인지 확인한다. 단순한 한 번의 응답이면 큰 프롬프트로도 충분할 수 있다. 반대로 여러 자료를 탐색하고, 오류 후 이전 단계로 돌아가며, 회사별 규칙을 반복해서 참고해야 한다면 파일 시스템과 스킬 구조를 시험할 이유가 생긴다. 판단은 모델 이름이 아니라 성공률, 실패 유형, 단계 수, 비용처럼 실제 업무 지표를 기준으로 해야 한다.

  • [해석] 사람의 직무 구분을 그대로 에이전트 구조로 옮기는 것보다, 실패했을 때 필요한 자료로 되돌아갈 수 있는지가 더 중요한 설계 기준이 될 수 있다.

2. 내부 평가는 실제 사용자의 질문 분포를 대신하지 못한다

  • [원문] 화자는 D0가 내부 평가의 약 30%를 맞혔다고 생각했지만, 제한된 실제 사용자의 즉각적인 반응은 좋지 않았다고 말했다. 파일 시스템 구조로 바꾼 뒤 평가 점수가 기본적으로 두 배가 됐다고 주장했다.
  • [해석] 에이전트 평가는 미리 준비한 정답 세트뿐 아니라 실제 사용자가 어떤 표현과 예외를 가져오는지까지 관찰해야 한다.
  • [경계] 평가 항목, 표본 수, 성공 판정법이 없다. “약 30%”와 “두 배”가 같은 평가를 뜻하는지도 명시되지 않았으므로 정확히 60%라고 계산할 수 없다. Aura의 “더 적은 단계·더 나은 성공·더 나은 통찰”도 비교 수치가 없다.

3. 범용 실행 능력과 회사별 지식은 서로 다른 자산이다

  • [원문] 화자는 파일 시스템과 Bash 같은 범용 도구가 돌파구였지만, 실제로 좋은 에이전트를 만드는 데는 회사별 지식이 중요했다고 말했다. 최근 질의를 스킬로 정제해 약 100개를 운영한다고 설명했다.
  • [해석] 모델과 실행 도구가 “일할 수 있는 능력”을 제공한다면, 스킬과 시맨틱 레이어는 “이 회사에서 무엇을 어떻게 해야 하는가”를 제공한다.
  • [경계] 하루 수천 건의 질의, 약 100개 스킬, 약 20개 에이전트, 블로그가 특정 주간 Vercel.com 트래픽의 70%를 만들었다는 수치는 모두 화자의 자체 주장이다. Skills.sh가 가장 인기 있는 스킬 탐색 방식이라는 표현과 Eve가 최선이라는 평가는 검증된 비교 결과가 아니다. 1. Vercel과 에이전트 구상

화자는 자신을 Andrew라고 소개하며 Vercel의 Chief of Software라고 말했다. 내부 엔지니어링, 외부 실험, 새 라이브러리와 프레임워크 개발을 담당한다고 설명했다.

Vercel의 AI SDK는 공급자별로 300줄 또는 400줄의 코드를 바꾸는 대신 한 줄을 바꿔 같은 모델 인터페이스를 사용할 수 있게 한다고 주장했다. 모델 대체 실행, 안전한 코드 실행, 응답 대기 중 가격 개선, 지속성과 재개 기능을 위한 도구도 만들었다고 설명했다.

화자와 CTO는 “모든 책상 위의 컴퓨터”라는 발상에서 “모든 책상 위의 에이전트”라는 구상을 떠올렸다. 이 실험은 발표 시점에서 약 1년 전에 시작됐다고 표현했다.

2. 데이터 팀의 병목

화자는 마케팅, 영업, 재무, 법무 직군에 가장 싫어하는 업무가 무엇인지 물었다. 가장 설득력 있는 사례는 데이터 팀에서 나왔다.

마케팅이나 영업에서 고객 또는 제품에 관해 질문하면 데이터 과학자는 하던 일을 멈추고 조회문 작성, 데이터 처리, 분석, 권고안 작성을 수행해야 했다. Vercel과 데이터 양은 빠르게 커졌지만 데이터 팀은 작은 상태여서 반복 대응이 생산성을 해쳤다고 설명했다.

3. 메가 프롬프트

첫 버전에서는 Snowflake 스키마 전체를 받아 시스템 프롬프트에 붙이고 질문을 넣었다. 모델이 SQL을 생성하면 화자가 직접 복사해 실행했다.

이 실험은 모델이 적절한 구조를 받았을 때 유효한 SQL을 작성할 수 있는지 확인하기 위한 것이었다. 화자는 모델 자체가 충분히 좋지는 않지만 더 나은 맥락과 안전장치를 제공하면 개선할 수 있다는 정도의 자신감을 얻었다고 말했다.

4. 역할별 에이전트 체인

데이터 과학자의 일을 질문 처리, 시맨틱 레이어 탐색, 데이터 결합 관계 파악, SQL 실행, 재시도, 시각화와 보고로 분해했다.

D0의 두 번째 버전에서는 질문 에이전트, 계획 에이전트, 실행 에이전트 등을 연결했다. 각 에이전트는 자기 역할에 맞는 시스템 프롬프트와 도구만 사용했다. 계획 에이전트의 예로 read_entity_yaml과 search_schemas가 제시됐다.

전체 질문에서 보고까지 자동화할 수 있었지만, 다음 에이전트가 이전 작업의 요약과 작은 일부만 받는 문제가 생겼다.

5. 단일 에이전트와 실사용 실패

다음 구조에서는 하나의 에이전트가 계획, 구축, 실행, 보고를 오가며 자기 상태를 관리했다. 한 번의 큰 AI 호출 안에서 최대 100단계까지 작업할 수 있게 했다고 설명했다.

이 구조는 SQL 실행이나 데이터 결합 오류가 나면 다시 탐색하고 자료를 읽어 원인을 찾을 수 있었다. 화자는 내부 평가의 약 30%를 맞혔다고 표현하며 자신감을 가졌지만, 제한된 실제 사용자에게 배포했을 때 즉각적인 반응은 좋지 않았다고 말했다.

예상 가능한 질문을 사람이 계속 추가하는 방식은 확장 가능하지 않다고 판단했다.

6. 파일 시스템 전환

화자는 Claude Code와 Opus 4.5가 기존 D0보다 대부분의 질문에 훨씬 잘 답했다고 말했다. 그 차이를 검토한 결과, 핵심을 파일 시스템에서 찾았다고 설명했다.

파일 목록 확인, 파일 읽기, Bash 실행 같은 소수의 일반 도구를 사용하고, 필요한 곳에 Vercel 데이터 업무용 도구를 추가했다. 샌드박스에는 전체 시맨틱 레이어를 넣고, 에이전트가 Bash와 파일 읽기·쓰기로 필요한 내용을 탐색하게 했다.

화자는 단일 에이전트에서 Claude Code SDK로, 다시 업무 목적에 맞는 일반 파일 시스템 에이전트로 전환한 것이 큰 도약이었다고 평가했다. 이후 평가 점수가 기본적으로 두 배가 됐다고 주장했다.

npm의 bash-tool 도우미를 샌드박스에 연결해 파일을 읽고 쓰고 실행할 수 있다고 소개했다.

이 경험을 다룬 블로그 글은 작성된 주간에 Vercel.com 트래픽의 70%를 만들었다고 화자가 주장했다. 측정 범위나 분석 자료는 제공되지 않았다.

7. 스킬 축적

화자는 당시 D0가 Vercel 전체에 공개돼 하루 수천 건의 질의를 받았다고 말했다. 고객·영업 지표, 수치 지표, npm 다운로드 등에 관한 요청이 포함됐다.

많은 질문이 집계, 제품 조회, 청구 정보 검색처럼 비슷한 형태를 가졌다. Vercel은 최근 질의를 정기적으로 분석해 스킬로 정제하는 작업을 만들었다. 전사 시점에는 약 100개의 스킬이 있다고 했다.

각 에이전트 실행은 시맨틱 레이어와 시스템 프롬프트 외에는 정해진 맥락 없이 시작하지만, 스킬을 넣으면 이전 실행에서 발전한 회사별 지식과 함께 시작할 수 있다고 설명했다.

화자는 Skills.sh를 에이전트 스킬을 찾고 실행하는 가장 인기 있는 방식이라고 소개했지만 외부 검증 자료는 제시하지 않았다.

8. Eve와 확장 주장

Vercel 내부 사람들이 D0를 복제해 새 에이전트를 만들 때마다 이미 지나온 시행착오를 반복했다. 팀은 사람들이 마지막 통찰에서 시작할 수 있도록 “에이전트를 위한 Next.js”를 구상했다.

Eve에서는 스킬, 도구, 채널 폴더를 만들고 정해진 규칙에 따라 파일을 배치하면 프레임워크가 에이전트를 구성한다. 런타임에는 지속성, 격리 실행, 모델 호출, 외부 연결이 포함된다.

Postgres, OpenAI Responses API, Docker 등을 위한 오픈소스 어댑터를 연결할 수 있으며 Vercel에 쉽게 배포하거나 직접 호스팅할 수 있다고 설명했다. Vercel 배포에서는 Workflows, Sandbox, Connect를 사용하고, Connect는 짧게 유지되는 OAuth 토큰을 생성한다고 말했다.

D0도 Eve로 다시 작성됐다. 베타 고객 Aura는 사람들의 서비스를 시험하기 위해 웹사이트를 방문하고 설치·사용해 보는 에이전트를 다시 만들었다. 화자는 기존 Claude Code 방식보다 단계가 적고 성공과 통찰이 좋아졌다고 주장했지만 수치는 제시하지 않았다.

Eve를 Vercel에 배포하면 실행 기록, 도구 호출, 각 단계, 예상 비용과 잠재적 최적화를 볼 수 있다고 설명했다. 발표 시점 기준 “2주 전” 런던 행사에서 완전히 공개했다고 말했다.

화자는 Vercel에 적절한 제품·시장 적합성을 가진 에이전트가 약 20개 있으며, 마케팅 회고, 접촉 대상 찾기, 새 협상의 최초 계약 수정, 데이터 질의 등에 사용된다고 주장했다. 데이터 팀은 반복 조회 대신 Snowflake 성능 개선, 새 데이터 소스 추가, 기존 공백 보완에 더 많은 시간을 쓸 수 있게 됐다고 설명했다.

마지막으로 범용 수직형 에이전트도 시험할 가치가 있지만, 최대 효과를 얻으려면 회사별 지식을 많이 담은 자체 에이전트를 만들어야 한다고 주장했다.

저희는 AI SDK라는 것을 만들었습니다. 제공업체별 코드(provider-specific code) 300~400줄을 바꿔야 하는 대신, 코드 한 줄만 바꾸면 됩니다. 이 서로 다른 제공업체들 모두의 기반에 동일한 모델 인터페이스가 있습니다.

또한 모델 폴백(model fallback), 안전한 코드 실행, 비활성 상태로 응답을 기다릴 때의 더 나은 가격, 그리고 내구성(durability)과 재개 가능성(resumability)을 더 쉽게 지원하는 여러 도구도 만들었습니다.

오늘은 제가 약 1년 전 시작한 이 미친 실험이 Vercel에서 에이전트형 기술의 폭발적인 확산으로 이어지고, 최근에 구축한 정말 멋진 결과물로 이어진 과정을 말씀드리려 합니다.

때는 1980년입니다. 제 시대 이전의 인물인 빌 게이츠는 모든 책상과 모든 가정에 컴퓨터가 한 대씩 있을 것이라고 상상했다는 말을 남겼습니다. 당시에는 아마 상당히 파격적인 생각이었겠지만, 오늘날에는 아주 당연하게 들립니다.

CTO와 저는 이런 생각을 했습니다. 모든 책상에 컴퓨터가 한 대씩 있는 대신, 모든 책상에 에이전트가 하나씩 있을 수도 있을까?

오늘날 우리는 실제로 코딩과 기술 업무에만 에이전트를 주로 사용하고 있지만, 디자인, 제품 관리, 그리고 다른 분야로도 확장되기 시작하는 것을 보고 있습니다. 이때가 아마 1년 전쯤이었으니, 꽤 일찍 시작했다고 할 수 있습니다. 당시에는 Sonnet 4였고, 지금처럼 정교하지도 않았습니다.

저는 이 가능성을 탐색하고 우리가 무엇을 할 수 있을지 알아보기로 했습니다. Vercel의 여러 직무—마케팅, 영업, 재무, 법무—를 찾아가 “업무에서 가장 싫어하는 게 무엇인가요?”라고 물었습니다.

가장 설득력 있는 사용 사례는 데이터 팀에서 나왔습니다. 데이터 팀은 성장하고 있었고 매우 소규모였지만, Vercel은 그보다 더 빠르게 성장하고 있었습니다. 고객, 분석, 지표, 영업에서 들어오는 데이터가 훨씬 많아졌습니다. 데이터 팀은 그 데이터를 계속 집계하고 자신들이 사용할 수 있도록 제공해야 했습니다.

당시 데이터 과학자가 해야 하는 일을 생각해 보면, 마케팅이나 영업 담당자가 고객이나 제품에 대해 질문할 때마다 데이터 과학 팀은 하던 일을 모두 멈추고 쿼리를 작성하고, 처리하고, 분석한 다음, 무엇을 해야 할지에 대한 권고안을 마련해 돌아와야 했습니다.

이것은 생산성에 큰 악영향을 주고 있었습니다. 데이터 팀은 하던 일을 모두 멈추고 하루 종일 쿼리만 작성하고 싶어 하지 않았습니다. 그래서 저는 데이터 부사장(VP of Data)과 함께 더 나은 업무 방식을 구축해 보기로 했습니다.

AI로 문제를 해결하고 싶을 때 가장 먼저 할 법한 일을 생각해 보면, 거대한 메가 프롬프트(mega-prompt)를 만들 수도 있습니다. 질문을 LLM에 전달하고, 답변을 받아서 끝내는 방식입니다.

첫 번째 버전은 실제로 이런 모습이었습니다. 데이터 팀에 Snowflake 스키마를 덤프해 달라고 요청했습니다. 그것을 질문과 함께 시스템 프롬프트에 붙여 넣었습니다. SQL이 생성되면 제가 복사해 붙여 넣고 직접 실행했습니다.

제가 알고 싶었던 것은 모델이 어느 정도 괜찮은 구조만 주어졌을 때 유효한 SQL을 작성할 만큼 충분히 좋은지였습니다. 이 과정을 통해 오늘날의 모델이 아직 그렇게 뛰어나지는 않지만, 컨텍스트 엔지니어링(context engineering)을 하거나 모델 주변의 컨텍스트를 조금 더 개선하고, 더 많은 가드레일을 제공하면 더 잘 작동하게 만들 수 있다는 자신감을 어느 정도 얻었습니다.

데이터 과학자가 질문을 받았을 때 실제로 해야 하는 일을 생각해 보면, 먼저 질문을 처리해야 합니다. 시맨틱 레이어(semantic layer)를 탐색하고 조인 패턴(join pattern)이 무엇인지 파악해야 할 수도 있습니다. SQL을 실행하고, SQL이 실행되지 않거나 비용이 너무 많이 들면 다시 돌아가 같은 작업을 반복할 수도 있습니다. 그리고 결국 데이터를 시각화하고, 몇 개의 문단을 작성하고, 회고를 진행하거나, 그 밖의 작업을 포함해 결과를 보고해야 합니다.

데이터 부사장과 저는 앉아서 이 여러 단계를 구체적인 에이전트 작업으로 나누어 정리했습니다.

D0라고 부르는 이 데이터 과학 에이전트의 두 번째 버전—앞으로 D0를 계속 언급하겠습니다—은 다음과 같이 작동했습니다. 질문을 하면 쿼리 에이전트(query agent)가 그 쿼리를 계획 에이전트(planning agent)에 전달하고, 계획 에이전트는 실행 에이전트(execution agent)를 사용하며, 이런 식으로 이어졌습니다.

이들을 모두 연결하면 각 에이전트가 자신이 맡은 일에 집중하는 전용 시스템 프롬프트를 갖고, 해당 기능에 정확히 맞춰진 도구를 사용하는 구조가 됩니다.

예를 들어 계획 에이전트에는 read_entity_yaml 도구와 search_schemas 도구가 있습니다. 이 에이전트는 SQL 에이전트로 넘길 답을 얻을 때까지 이러한 기능만 사용하고, 이후 보고 단계로 넘어갑니다.

점점 나아지고 있었습니다. 더 이상 SQL을 복사해 붙여 넣고 다시 돌아와 보고서를 작성할 필요가 없었습니다. 이제 질문에서 답변까지의 전체 순환을 수행하고 있었습니다.

하지만 이 아키텍처에서 몇 가지 한계에 부딪히기 시작했습니다. 이 무렵 저희는 실제로 필요한 것은 모든 컨텍스트를 내부에 갖고 자신의 메모리를 관리하는 하나의 에이전트라는 결론에 도달했습니다.

에이전트가 자신이 했던 일을 되돌아보고, 성찰하고, 지금까지 도달하기 위해 어떤 단계를 거쳤는지 파악할 수 있어야 한다는 사실을 깨달은 때였습니다. 이전 모델에서는 다음 에이전트가 받은 것이 앞서 수행된 작업의 요약과 작은 일부 내용뿐이었습니다.

이제 하나의 거대한 메가 에이전트(mega-agent)가 내부적으로 자신의 상태를 관리하는 모습을 상상할 수 있습니다. 어떤 순간에는 계획을 세우고, 어떤 순간에는 구축하고, 어떤 순간에는 실행하며, 또 어떤 순간에는 보고하는 식입니다.

실제 모습은 이랬습니다. 하나의 큰 AI 호출이 있고, 최대 100개의 단계를 설정할 수 있습니다. 그리고 실행 과정에서 현재 어느 지점에 있는지에 따라 자신의 상태를 관리할 수 있는 능력을 부여합니다.

하지만 가장 중요한 점은 에이전트가 충분히 학습된 도구를 사용할 수 있고, 필요한 곳 어디든 탐색하고 작업 결과를 작성할 수 있었다는 것입니다. Claude Code는 매우 처방적인 도구 세트를 제공하지 않았습니다. 그저 에이전트가 마음껏 움직이며 창발적 행동(emergent behavior)을 탐색하도록 내버려 두었습니다.

이 시점에서 저희는 Vercel의 더 많은 사람에게 제공할 준비를 하고 있었습니다. 평가 점수는 사실상 두 배가 되었습니다.

이러한 깨달음을 얻고, 이전에 실패했던 질문을 아주 많이 통과하고 있다는 사실을 확인한 뒤, 저는 정말 대박인 블로그 글을 하나 작성했습니다. 실제로 오늘도 공개되어 있는데, 제가 그 글을 작성한 주에 Vercel.com 트래픽의 70%를 책임졌습니다. 정말 대박인 글입니다.

알고 보니 이러한 쿼리 상당수는 실제로 형태가 비슷했습니다. 집계를 수행하는 방법에는 한계가 있고, 제품을 조회하는 방법에도 한계가 있으며, 결제 정보를 가져오는 방법에도 한계가 있습니다.

가장 최근의 쿼리를 가져와 스킬(skill)로 정제하려는 반복 작업을 운영하고 있습니다. 현재는 집계부터 특정 사람에 대한 세부 데이터 조회까지 모든 것을 다루는 스킬이 대략 100개 있습니다.

이 방식이 매우 효과적이라는 것을 알게 되었습니다. 새로운 에이전트 실행은 기본적으로 아무것도 없는 상태에서 시작하기 때문입니다. 의미 계층(semantic layer)과 시스템 프롬프트 외에는 미리 설정된 컨텍스트가 없습니다. 하지만 스킬이 있으면 이전에 축적된 많은 컨텍스트 지식을 갖춘 상태에서 시작합니다.

우리는 에이전트를 만드는 일도 이렇게 단순해야 한다고 생각했습니다. skills 폴더, tools 폴더, channels 폴더만 만들고, 이를 아주 쉽게 선언할 수 있어야 합니다. 프레임워크가 이를 바탕으로 에이전트를 만드는 방법을 정확히 알아야 합니다.

그래서 2주 전 Eve를 출시했습니다. Eve는 에이전트를 위한 Next.js와 같은 에이전트 프레임워크입니다. 샘플 템플릿에서 완전히 에이전트에 맞춰진 시스템으로 전환하고, 자신만의 맞춤 지식과 맞춤 도구, 익숙한 채널과의 통합을 추가하는 일이 매우 쉽습니다.

우리는 오픈 소스를 염두에 두고 이를 만들었습니다. Postgres, OpenAI의 Responses API, Docker 및 기타 커넥터를 위한 오픈 소스 어댑터를 직접 연결할 수 있도록 Eve를 만들었습니다. 또한 Vercel에 아주 쉽게 배포할 수 있도록 했습니다.

여기서 보이는 유일한 차이점은 모든 것이 이러한 경험을 쉽게 구축할 수 있도록 수년간 개발해 온 Vercel 제품을 사용한다는 것입니다. 내구성을 위한 Vercel Workflows, 안전한 실행을 위한 Sandbox, 그리고 연결을 위한 단기 OAuth 토큰을 쉽게 생성할 수 있도록 방금 출시한 Vercel Connect입니다.
