한 줄 요약

Claude Code의 Agent Teams는 에이전트끼리 직접 대화·병렬 실행·QA 루프가 가능한 멀티에이전트 기능으로, 올바른 설정과 프롬프팅 패턴을 알면 단일 에이전트 대비 품질을 크게 높일 수 있다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Agent Teams vs Sub-agent 쓰임새가 다르다 — 잘못 고르면 과비용 또는 품질 저하 Teams는 팀원끼리 직접 소통, Sub-agent는 독립 실행 후 결과만 반환
활성화 환경 변수 기본값 비활성 — 모르면 기능 자체를 못 씀 settings.local.json에 실험 플래그 추가 1줄로 활성화
Plan Approval Mode 실행 전 계획 승인 → 오류 조기 차단 메인 에이전트 또는 사람이 각 팀원 계획을 승인한 뒤 실행
파일 소유권 명시 안 하면 에이전트끼리 덮어쓰기 충돌 발생 프롬프트에 "A 에이전트는 X 파일만 담당" 명시 필수
팀 규모 비용 구조 세션 수 = 비용 배수 3명 팀 → 약 3배, 5명 → 약 5배; 2~5명이 현실적 상한
tmux 병렬 화면 에이전트별 실시간 모니터링 · 개별 개입 가능 VS Code 확장에서는 내부 동작이 안 보임 → 터미널 실행 권장
종료 프로토콜 강제 종료 시 작업 상태 오염 메인 에이전트가 "저장 후 종료" 확인 → 팀원 응답 받고 닫기

내가 모를 만한 것 / 처음 보는 것

  • Agent Teams: Claude Code의 실험적 멀티에이전트 기능 — 팀장(오케스트레이터) + 팀원 에이전트가 공유 태스크 목록으로 협업
  • Team Lead / 오케스트레이터: 메인 세션이 팀장 역할 — 태스크 생성·배분·품질 관리 담당
  • Shared Task List: 에이전트 팀이 공유하는 작업 목록 — 의존성 설정·담당자 배정이 여기서 이루어짐
  • send_message 도구: 에이전트 간 직접 메시지 전송 도구 — 메인 세션 경유 없이 팀원 → 팀원 직통
  • Plan Approval Mode: 각 팀원이 실행 전 계획안을 제출 → 메인 에이전트(또는 사람)가 승인 후 진행
  • tmux (터미널 멀티플렉서): 터미널 창 분할 도구 — 여기서는 에이전트별 화면을 색상으로 구분해 동시 모니터링
  • Bypass Permissions: 메인 세션의 권한(허용 명령어 목록)이 모든 팀원에게 자동 상속
  • NestJS / React 풀스택: 강의 예시 프롬프트에서 사용한 스택 (NestJS 백엔드 + React 프론트엔드)

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정·명령·의견

  1. 활성화 환경 변수는 settings.local.json에 추가 — 공식 문서의 JSON 스니펫을 그대로 복사해 Claude Code에 "로컬 설정에 넣어줘"라고 요청하면 파일이 자동 생성됨
  2. Agent Teams 문서를 docs/ 폴더에 로컬 마크다운으로 미리 저장해두면 이후 참조 속도가 빨라짐 — 화자는 MCP 서버나 중요 문서가 있을 때마다 이 방식을 씀
  3. 프롬프트 패턴: 목표 → 팀 구성(모델·역할) → 역할별 상세 지시 → 메시지 흐름 → 최종 산출물 명세 순서
  4. 모델 선택: haiku / sonnet / opus 중 선택 — 예시에서는 Sonnet 3명 팀을 주로 사용
  5. 팀원 수 상한: 3~5명. 10명 이상은 비용이 약 10배까지 증가한다고 명시
  6. 세션 비용 구조: 세션 3개 → 약 3배, 세션 5개 → 약 5배 (선형 비례)
  7. 권한 승인 반복 중단법: 프로젝트/로컬 설정에서 특정 명령어 사전 허용 → 매번 중단 없이 진행
  8. 작업 유실 방지: 임시 파일에 중간 결과 저장 지시를 프롬프트에 포함 → 나중에 재로드 가능
  9. 종료 시 주의: 세션을 강제 닫으면 작업 상태가 오염될 수 있음 → 반드시 "저장 후 종료" 확인 메시지 후 닫기
  10. tmux 설치 방법은 화면에서 다루지 않음 — "Claude Code에 물어보며 설정했고 매우 간단했다"고만 언급
  11. Agent Teams로 Agent Teams 자체 문서를 생성하게 시키면 깊은 이해에 도움이 된다고 권장

# 섹션 요지
1 오프닝 데모 Sonnet 3명 팀(프론트·백엔드·QA)으로 A 스타트업 랜딩 페이지를 원샷 생성 — QA가 치명적 이슈 3개 발견 → 재검토 → 통과
2 Sub-agent vs Agent Teams Sub-agent: 독립 실행 후 결과 반환 / Teams: 공유 태스크·팀원 직접 소통·지속 협업
3 활성화 설정 settings.local.json에 실험 플래그 1줄 추가, 문서 로컬 저장 팁
4 프롬프트 패턴 목표 → 팀 구성 → 역할 지시 → 메시지 흐름 → 산출물 순서; Do/Don't 정리
5 tmux 실행 데모 에이전트별 색상 구분 화면, 개별 에이전트 직접 개입 시연
6 내부 동작 원리 권한 상속, Plan Approval Mode, 파일 소유권 명시 원칙
7 흔한 실수·해결책 권한 중단 → 사전 허용 / 덮어쓰기 → 파일 소유자 배정 / 토큰 과다 → 팀 규모 축소
8 언제 쓰고 언제 안 쓰나 복잡·다영역·병렬·검증 필요 → Teams / 단순·순차·집중 → Sub-agent

1. 오프닝 데모 — QA 루프가 있는 랜딩 페이지 생성

Sonnet 기반 3명 팀(프론트엔드 개발자, 백엔드 개발자, QA 에이전트)을 생성하는 데모를 먼저 보여준다. 가상의 A 스타트업 랜딩 페이지를 만들어달라는 프롬프트 하나를 넣었을 뿐인데 텍스트·애니메이션·동적 요소까지 포함된 페이지가 생성됐다.

핵심 흐름: - 프론트엔드·백엔드가 작업 완료 → QA에게 결과 인계 - QA가 치명적 이슈 3개 발견 → 메인 에이전트가 두 에이전트에게 재검토 지시 - 2차 검수에서 QA 통과 → 완성

화자는 "써본 AI 에이전트 기능 중 가장 강력한 축"이라고 평가하면서도 "제대로 쓰는 법을 알아야 한다"고 강조한다.

2. Sub-agent vs Agent Teams 개념 정리

구분 Sub-agent Agent Teams
소통 방식 독립 실행 후 결과만 메인에 반환 팀원 간 직접 메시지·공유 태스크
중간 관리 없음 팀 리드(오케스트레이터)가 지속 관리
적합 작업 단순·순차·집중 결과 복잡·병렬·상호 의존·검증 필요
비용 상대적으로 낮음 세션 수만큼 비례 증가

에이전트 팀즈의 핵심 차별점은 팀원끼리 직접 대화할 수 있다는 것. 팀원 1이 팀원 2에게 필요한 정보를 바로 요청할 수 있어 의존성 처리가 훨씬 자연스럽다.

3. 활성화 설정

기능은 실험적(experimental) 상태라 기본값 비활성. 활성화 방법:

  1. 공식 Claude Code Agent Teams 문서에서 환경 변수 스니펫 복사
  2. Claude Code에 "로컬 설정(settings.local.json)에 넣어줘"라고 요청 → 파일 자동 생성
  3. .claude/settings.local.json 안에 해당 설정 확인

추천 선행 작업: Agent Teams 문서 URL을 복사 후 "docs/ 폴더에 Agent Teams 마스터 레퍼런스 가이드를 만들어줘"라고 요청 → 수백 줄짜리 로컬 마크다운 저장 → 이후 참조 속도 향상. 화자는 큰 MCP 서버나 중요 문서가 있을 때마다 이 방식을 사용한다.

4. 프롬프팅 패턴 — Do / Don't

권장 프롬프트 구조

[목표]
네스타파이 + 리액트 풀스택 앱 개발. 로컬에서 실행, 사용자/게시글/QA/리포트 기능 포함.

[팀 구성]
Sonnet 3명 팀:
- 백엔드 개발자: API 설계, DB 스키마, 라우트 담당
- 프론트엔드 개발자: React 컴포넌트, 상태 관리 담당 (백엔드 완료 후 메시지 받아 시작)
- QA 에이전트: 테스트 작성·실행, 결과를 앞 두 에이전트에게 피드백

[최종 산출물]
- 테스트 통과/실패 리포트
- 핵심 의사결정 문서
- 실행 방법 안내 문서

Do

  • 각 에이전트에게 담당 파일 명확히 지정 (덮어쓰기 방지)
  • 산출물 형식을 프롬프트에 정의
  • 수신 대상 명시 ("끝나면 QA에게 send_message로 결과 전달")
  • 팀원 3~5명 이내로 구성
  • 전체 문맥을 초기 프롬프트에 충분히 포함

Don't

  • 10명 이상 대규모로 시작 (비용 약 10배)
  • 같은 파일을 여러 에이전트가 함께 편집하는 구조
  • 단순·순차 작업에 Teams 사용 (Sub-agent로 충분)

5. tmux 터미널 실행 — 에이전트 병렬 시각화

VS Code 확장에서는 내부 동작이 보이지 않는다. tmux 터미널에서 Claude Code를 실행하면: - 프론트엔드: 파란색 창 - 백엔드: 초록색 창 - QA: 노란색 창

각 창에서 에이전트가 무엇을 하는지 실시간으로 확인 가능. 메인 세션에서 특정 에이전트에게 직접 추가 지시·승인·정보 제공도 가능.

tmux 설정 방법은 영상에서 자세히 다루지 않았고 "Claude Code에 물어보며 설정했고 매우 간단했다"고만 언급.

6. 내부 동작 원리

권한 상속: 메인 세션 권한이 모든 팀원에게 그대로 상속됨. bypass permissions, 허용 Bash 명령 등 모두 포함.

공유 리소스: 프로젝트 파일, MCP 서버, 스케일 등을 팀원 전원이 접근 가능.

Plan Approval Mode: 팀원이 실행 전 계획안 제출 → 메인 에이전트(또는 사용자)가 승인 후 실행. 화자는 "메인 세션이 승인하게 두는 게 더 낫다"고 봄. 특정 팀원을 계획 검토·승인 전담으로 지정하는 것도 가능.

7. 흔한 실수와 해결책

문제 해결책
에이전트가 권한 요청으로 자꾸 멈춤 프로젝트/로컬 설정에서 특정 도구 사전 허용
산출물 덮어쓰기 충돌 각 에이전트에게 담당 파일 명확히 배정
특정 에이전트가 거의 놀고 있음 프롬프트에서 할 일·의존성 더 명확히 지정
토큰 비용 과다 에이전트 수 줄이기
작업 결과가 사라지는 느낌 임시 파일에 중간 결과 저장 지시 추가
승인 흐름이 어긋남 초기에는 사람이 직접 승인자로 들어가 흐름 파악 후 자동화 확장

8. 언제 써야 하나, 언제 쓰지 말아야 하나

Agent Teams 적합 상황 - 복잡한 작업 + 서로 다른 전문성이 필요한 여러 역할 - 여러 영역이 동시에 진행되는 프로젝트 - 병렬 처리 + 상호 반응 + 작업 재할당 + 지속 커뮤니케이션이 필요 - 매우 높은 품질 + 다단계 검증이 필요

Sub-agent가 더 적합한 상황 - 단일 컨텍스트 창에서 히스토리 유지가 필요한 작업 - 같은 파일을 계속 함께 편집하는 작업 - 단순하거나 순차적인 작업 - 에이전트 간 소통이 필요 없을 때 - 토큰 비용을 아껴야 할 때

세션 비용: 3개 세션 = 약 3배, 5개 세션 = 약 5배. 화자 권장 상한은 2~5명.

여기서 보여드리려는 건 최종 산출물 자체가 아닙니다. 핵심은 이 과정을 화면에서 어떻게 시각적으로 볼 수 있는지입니다. 지금 에이전트 팀을 띄우고 있죠. 작업 의존성을 설정하고 담당자를 배정한 뒤 에이전트를 생성합니다. 이제 생성됐습니다. 여기 파란색 에이전트가 프론트엔드 개발자입니다. 여기 또 하나가 백엔드 개발자이고 초록색 에이전트입니다. 그리고 노란색 QA 에이전트도 생성됐습니다. 이제 각 에이전트가 무엇을 하는지 매우 명확하게 보입니다. 필요하면 메인 세션에서 팀 상태를 보고 프론트엔드에게 직접 말하거나 승인하거나 추가 정보를 줄 수 있습니다. QA나 백엔드에게도 완전히 같은 방식으로 할 수 있습니다. 즉 이제는 제가 에이전트 팀을 직접 보면서 각 에이전트와 상호 작용할 수 있습니다. 정말 멋진 기능입니다.

이제 데모를 봤으니 품질을 더 끌어올리는 방법과 내부 동작을 더 이야기해보겠습니다. 핵심 규칙 3가지입니다. 첫째, 각 에이전트는 자기 구역이 있어야 합니다. 자기 파일을 담당하고 자기 산출물을 만드는 구조가 좋습니다. 결과를 주고받으며 소통할 수는 있지만 실제 편집은 각자 담당 범위에서 해야 합니다. 둘째, 직접 메시징입니다. 서로 대화할 수 있습니다. 메인 세션이라는 중간자만 거칠 필요가 없습니다. 셋째, 동시에 작업할 수 있어야 합니다. 에이전트 A가 끝나야 에이전트 B가 시작하는 순차 흐름만 필요하다면 굳이 Agent Teams가 아닐 수 있습니다. Agent Teams는 병렬로 함께 일하고 전체 과정에서 계속 소통해야 합니다.

그렇다면 팀원이 처음 깨어났을 때 즉시 아는 정보는 무엇일까요? 처음에는 문맥이 없다는 건 알고 있죠. 대신 메인 세션의 권한은 그대로 상속받습니다. 예를 들어 메인 세션이 bypass permissions이고 모든 에이전트도 bypass permissions가 됩니다. Bash 명령을 허용해두면 팀원들도 같은 권한을 상속받습니다. 또 중요한 점은 프로젝트 파일, MCP 서버, 스케일 같은 리소스를 팀원 모두가 접근해 사용할 수 있다는 것입니다.

그리고 Plan Approval Mode라는 유용한 기능도 있습니다. 제가 항상 플랜 모드로 시작하라고 말씀드린 거 기억하시죠? 메인 세션에서 먼저 계획을 세우고 시작하면 훨씬 결과가 좋습니다. 이 모드에서는 팀원들도 먼저 계획을 세우고 실행 전에 메인 에이전트의 승인을 받아야 합니다. 정말 유용합니다. 원하면 모든 계획을 여러분이 직접 승인하도록 설정할 수도 있습니다. 다만 저는 메인 세션이 승인하게 두는 편이 더 낫다고 봅니다. 혹은 팀원 중 한 명을 계획 검토·승인 전담으로 두는 것도 가능합니다.

이어서 흔한 실수와 해결책을 말씀드릴게요. 첫 번째, 에이전트가 권한 요청 때문에 자꾸 멈춘다면 특정 도구를 미리 승인해두세요. 이건 프로젝트 설정이나 로컬 설정에서 할 수 있습니다. 일부 명령을 허용해두면 몇 초마다 승인 요청으로 끊기지 않습니다. 산출물이 하나로 잘 안 묶이고 덮어쓰기 느낌이 나면 파일 소유자를 명확히 배정하세요. 팀을 띄웠는데 어떤 에이전트가 거의 놀고 있다면 프롬프트와 계획에서 각 에이전트의 할 일이나 의존성을 더 명확히 배정해야 합니다. 토큰을 너무 많이 쓰고 있다면 에이전트 수를 줄이세요. 작업이 사라지는 느낌이 있으면 임시 파일로 중간 결과를 저장하게 하세요. 나중에 다시 불러올 수 있습니다. 승인 흐름이 자꾸 어긋나면 처음엔 여러분이 직접 승인자로 들어가 팀 동작 흐름을 충분히 이해한 후 자동화 범위를 늘리는 게 좋습니다.

다음은 언제 Agent Teams를 써야 하는지입니다. 앞서 말했듯 느리고 비용이 더 듭니다. 그래서 복잡한 작업이고 서로 다른 전문 에이전트가 여러 명 필요할 때 쓰는 게 좋습니다. 여러 영역이 함께 있는 프로젝트라면 사용을 고려하세요. 그렇게 하면 영역별로 한 명씩 전문화할 수 있습니다. 또 병렬 처리, 상호 반응, 작업 재할당, 지속적인 커뮤니케이션이 필요할 때 적합합니다. 그리고 아주 높은 품질이 필요하고 검증 단계를 많이 거쳐야 한다면 Agent Teams가 괜찮습니다.

Agent Teams가 정답이 아닐 수 있습니다. 그땐 서브 에이전트가 더 맞을 수 있습니다. 모든 내용을 하나의 대화 히스토리나 단일 컨텍스트 창에서 유지해야 한다면 팀을 쓰지 마세요. 같은 파일만 계속 같이 만지는 작업도 팀에 적합하지 않습니다. 아주 단순한 작업이라면 Agent Teams는 과합니다. 서브 에이전트로 충분한 경우가 많습니다. 순차 작업, 매우 집중된 결과가 필요할 때, 에이전트 간 소통이 필요 없을 때, 토큰을 아끼고 싶을 때 서브 에이전트가 좋습니다. 세션 3개를 돌리면 비용도 대략 3배입니다. 5개를 돌리면 비용도 5배가 됩니다. 그래서 보통 2명에서 5명 정도를 최대치로 잡고 병렬 운영하는 걸 권장합니다.

아니면 서브 에이전트를 쓰고 초반부터 잘못된 방향으로 가면 빨리 종료하세요. 이게 tmux 버전을 권장하는 또 다른 이유입니다. 분할 화면에서 진행을 직접 볼 수 있으니까요. 그리고 종료라고 할 때는 세션이 끝날 때 작업 저장을 확인하는 걸 뜻합니다. 아까 메인 세션이 종료 요청을 보낸 장면 기억하시죠? 리서처가 아직 안 끝났으니 저장 후 종료하자고 말할 수도 있습니다. 즉 팀원이 종료 준비가 됐다고 확인할 때 비로소 상태가 깔끔하고 저장도 완료됐다고 볼 수 있습니다. 그렇게 정리된 뒤 세션을 닫고 팀을 종료해야 안전합니다. 바로 강제 종료하면 작업이 정리되지 않고 엉킬 수 있습니다.

네, 여기까지 Agent Teams였습니다. 이제 여러분도 Claude Code에서 Agent Teams를 바로 써보고 싶어지셨으면 좋겠습니다. 재미있었거나 새로 배운 게 있었다면 좋아요를 눌러주세요. 항상 끝까지 시청해주셔서 감사합니다. 다음 영상에서 뵙겠습니다.
