한 줄 요약

LLM은 단순한 도구가 아니라 새로운 컴퓨팅 기반(Software 3.0)이며, 검증가능성이 AI 자동화 속도를 결정하고, 인간의 역할은 취향·판단·감독·이해로 좁아진다.

에이전트 고용 면접 재설계 실무 채용 기준 변화 퍼즐이 아니라 큰 프로젝트 + 에이전트 공격 테스트

내가 모를 만한 것 / 처음 보는 것

  • Open Claw (Open Claude): Claude 기반 에이전트 툴. 설치를 bash 스크립트 대신 "에이전트에 붙여넣기"로 처리 — Software 3.0 설치 철학의 사례
  • menu gen: Karpathy가 직접 만든 식당 메뉴 사진 → 음식 이미지 렌더링 앱. 이후 "Gemini + nano banana 한 줄"로 동일 효과 → Software 3.0의 구체적 교훈
  • nano banana: Gemini 계열 이미지 오버레이 도구 (불확실, 전사 [?nano banana]). 이미지 위에 메뉴 항목을 직접 렌더링
  • Jagged Intelligence: Karpathy 조어. AI 역량이 도메인별로 들쭉날쭉한 현상
  • RL 회로(circuits): 모델이 강화학습 보상을 받은 도메인은 강하고, 그 외는 약함. "회로 안에 있으면 날고, 밖이면 고생"
  • LLM 지식 위키(LLM Knowledge Base): 문서·사실들을 LLM으로 재컴파일해 개인 위키로 만드는 프로젝트 — Karpathy 본인 사용 중
  • micro GPT: Karpathy의 LLM 학습 간소화 프로젝트. "더 단순하게" 프롬프트 줘도 모델이 못 따라옴 → RL 밖 영역의 한계 사례

화자의 디테일 (놓치기 쉬운 포인트)

  1. 전환점은 2024년 12월: 연휴 기간에 최신 모델 써보다가 "청크가 그냥 다 맞게 나온다"는 걸 깨닫고 바이브 코딩 시작. "마지막으로 수정한 게 언제였는지 기억 안 난다"
  2. Open Claw 설치 = 텍스트 복붙: bash 스크립트 대신 텍스트 블록을 에이전트에게 붙여넣는 것 자체가 Software 3.0 패러다임
  3. menu gen 실패 사례: Gemini + nano banana 한 줄로 동일 결과 → "내 앱은 구 패러다임 산물, 존재해선 안 됐다"
  4. 카 워시 역설: opus 4.7이 10만 줄 코드베이스 리팩터링·제로데이 취약점 발견은 하면서, 50m 거리 세차장에 차로 가야 할지 걸어가야 할지는 틀림. 모델명 언급 주목
  5. 체스 데이터 사례 (공개 정보): GPT-3.5→GPT-4 체스 실력 급향상은 단순 스케일업이 아니라 OpenAI 내부에서 체스 데이터를 훈련 세트에 대량 추가했기 때문
  6. 에이전트의 이메일 매칭 버그: menu gen에서 Stripe 이메일과 Google 계정 이메일이 다를 수 있는데, 에이전트가 이메일로 크로스 조회해 결제 미연결 — "왜 이메일로 매칭하려 하냐"
  7. 텐서 API 망각: keep_dims vs keepdim, dim vs axis, reshape vs permute vs transpose — 이미 기억 안 한다. 에이전트 인턴이 처리. 단, 뷰(view)와 스토리지 개념, 메모리 복사 비용은 여전히 알아야 한다고 강조
  8. 10x 엔지니어 재정의: 에이전틱 엔지니어링에서 10x는 "하한선". 잘하는 사람은 그보다 훨씬 더 (수치 미언급)
  9. 코드 품질 불만: AI 생성 코드가 "매우 bloaty, 복붙 많음, 추상화 어색하고 brittle"하다고 본인도 인정
  10. micro GPT 단순화 실패: "더 단순하게" 반복 프롬프트해도 모델이 못 따라 옴 → RL 외부 영역에선 "이가 뽑히는 느낌"
  11. 에이전트 친화 인프라 부재 불만: Vercel 배포 시 DNS 설정·메뉴 클릭이 여전히 수동 → "에이전트에게 한 줄 주면 배포까지" 가 미래 목표
  12. 이해 위탁 불가 트윗: "생각은 위탁할 수 있어도 이해는 위탁할 수 없다"는 트윗을 이틀에 한 번씩 생각한다고 언급
  13. 계획 모드(plan mode) 불호: "plan mode가 유용하긴 한데, 더 일반적인 게 있다 — 에이전트와 함께 매우 상세한 스펙을 먼저 설계하는 것"

1. "나는 지금 가장 뒤처진 기분이다"

2024년 12월 연휴에 Karpathy는 최신 모델을 사용하다 명확한 전환점을 느꼈다. 코드 청크가 "그냥 맞게 나왔고", 마지막으로 수정한 기억이 없어졌다. 시스템을 점점 신뢰하게 됐고 그게 바이브 코딩이었다. Twitter(X)에서 이 변화를 강조한 이유: 많은 사람들이 2024년을 "ChatGPT 비슷한 것" 정도로 경험했기 때문. 12월을 기준으로 다시 봐야 한다고 촉구.

2. Software 3.0 패러다임

  • 1.0: 코드를 직접 작성
  • 2.0: 데이터셋 구성 + 신경망 아키텍처 정의 (프로그래밍 = 데이터 배열)
  • 3.0: 프롬프트가 프로그래밍, 컨텍스트 윈도우가 인터프리터(LLM)에 대한 레버

Open Claw 사례: 설치 스크립트가 bash가 아닌 "에이전트에 붙여넣을 텍스트 블록". 에이전트가 환경을 읽고 인텔리전트하게 설치·디버그. "무엇을 에이전트에 붙여넣으면 되는가? 그게 프로그래밍 패러다임이다."

3. menu gen 역설 — Software 3.0의 교훈

Karpathy가 만든 menu gen: 식당 메뉴 사진을 업로드하면 OCR → 이미지 생성 → 메뉴 아이템별 사진 오버레이. 상당한 코딩 작업.

그런데 Software 3.0 버전: "사진 찍어서 Gemini에 주고, nano banana[?]로 메뉴에 오버레이해달라고 하면 끝." 결과는 동일. 앱 전체가 불필요해진 것.

교훈: 기존 패러다임의 "속도업"이 아니라, 아예 존재하지 않았어야 할 코드가 있다. 새로운 것이 가능해졌고, 그 새것이 더 날 것(raw)이고 강력하다.

4. 극단적 외삽 — 뉴럴 컴퓨터

50-60년대에 컴퓨터가 계산기처럼 될지 신경망처럼 될지 불분명했듯, 지금도 전환기. Karpathy의 예상:

  • 뉴럴넷이 호스트 프로세스, CPU가 코프로세서로 뒤집힘
  • 뉴럴넷이 대부분의 작업을 담당하고, 결정론적 작업에만 도구(tool use)를 부속품처럼 사용
  • 뉴럴넷들이 네트워크로 연결된 극도로 이질적인 컴퓨터 구조

다만 "단계적으로 갈 것이고 정확한 진행은 미정(TBD)"이라고 선을 그음.

5. 검증가능성 (Verifiability)

핵심 프레임: LLM은 검증 가능한 것을 자동화한다.

  • 전통 컴퓨터: 코드로 명세화 가능한 것을 자동화
  • 최신 LLM: 검증 가능한 것을 자동화 (RL이 검증 보상으로 학습하기 때문)

결과적으로 수학·코드·인접 영역에서 역량이 폭발하고, 그 외는 들쭉날쭉.

체스 사례: GPT-3.5→GPT-4 체스 실력 급향상은 단순 스케일업이 아니라 훈련 세트에 대량 체스 데이터 추가. "우리는 어느 정도 랩이 무엇을 넣느냐에 달린 처지다."

카 워시 역설: opus 4.7이 10만 줄 코드 리팩터링과 제로데이 취약점 발견을 하면서, "50m 거리 세차장, 걸어가야 하나 차로 가야 하나"는 틀림. 재거드니스의 증거.

6. 재거드 인텔리전스 — Animals vs Ghosts

Karpathy가 쓴 글의 핵심: AI는 동물 지능이 아니라 유령(ghost). 데이터와 보상함수에 의해 형성된 통계적 시뮬레이션 회로. 진화로 생긴 내재적 동기·호기심·생존욕 없음.

실용적 의미: - 소리 질러도 모델이 더 잘하거나 못하지 않음 - "RL 회로 안에 있으면 날고, 밖이면 파인튜닝이 필요" - 이 모델에 매뉴얼이 없다 — 직접 탐색해야 함

7. 창업자를 위한 조언

검증 가능한 RL 환경 구축 = 자체 파인튜닝 레버. 랩이 집중 안 해도 작동하는 기술.

"내가 직접 말하기 꺼리지만 매우 가치 있는 RL 환경 도메인이 있다" — 구체적으로는 언급 회피.

거의 모든 것이 검증 가능하게 만들 수 있다. 글쓰기 같은 것도 LLM 심사단(council of LLM judges)으로 접근 가능. 결국 쉬운지 어려운지의 차이.

8. Vibe Coding vs Agentic Engineering

구분 Vibe Coding Agentic Engineering
목표 모두의 바닥(floor)을 올린다 기존 전문 소프트웨어 품질 바를 유지한다
주체 누구나 엔지니어
책임 완화 여전히 전적 책임
속도 빠름 훨씬 더 빠름 (10x 이상)

에이전틱 엔지니어링 = "들쭉날쭉하고 확률적이지만 강력한 에이전트들을 품질 바 유지하면서 조율하는 방법"

9. AI 네이티브 사용자의 특징

"도구를 최대한 활용, 모든 기능 투자, 자기 설정(setup) 투자" — 과거에 vim 또는 VS Code를 파고들던 것처럼.

채용 면접 재설계 제안: - 기존: 퍼즐 풀기 (구 패러다임) - 미래: 큰 프로젝트 구현 → 예: 트위터 클론 배포 → 10 Codex 5.4X high로 해킹 시도 → 뚫리면 안 됨

10. 에이전트가 더 할수록 인간은 무엇을?

지금 답: 에이전트는 인턴. 인간이 여전히 담당해야 하는 것:

  • 취향(aesthetics), 판단(judgment), 감독(oversight)
  • 스펙 설계: 에이전트와 함께 매우 상세한 스펙 먼저 작성 → 에이전트가 채워넣기
  • 원칙 이해: API 세부사항은 잊어도 됨. 단, 텐서 뷰(view)와 스토리지, 메모리 복사 비용 같은 근본 개념은 여전히 알아야 함

에이전트 버그 사례: menu gen에서 Stripe 이메일 ≠ Google 이메일일 수 있는데 에이전트가 이메일로 크로스 매칭 시도 → 결제 미연결. "이런 것을 잡아내는 게 인간의 역할."

계획 모드(plan mode)는 유용하지만 Karpathy는 더 선호하는 게 있음: 에이전트와 함께 상세 스펙 문서를 먼저 설계하는 것.

11. 에이전트 네이티브 세계

모든 것이 아직 인간용으로 쓰여 있다 (Docs, API, 서비스 설정). Karpathy의 불만:

"왜 아직도 나한테 어떻게 하라고 말하냐. 나는 아무것도 하기 싫다. 에이전트에게 붙여넣을 게 뭔데?"

미래 인프라 기준: "menu gen을 에이전트에 한 줄 주면 배포까지 끝" — 이게 가능해야 에이전트 네이티브.

장기 방향: 에이전트 대리인(agent representation)이 개인과 조직을 위해 존재. "내 에이전트가 네 에이전트에게 미팅 일정 조율."

12. 무엇을 깊이 배울 것인가

핵심 트윗 (Karpathy가 이틀에 한 번 생각한다는 것):

"생각은 위탁할 수 있어도 이해는 위탁할 수 없다."

자신이 시스템의 일부이고, 정보는 뇌에 들어와야 한다. 에이전트를 지휘하려면 이해가 전제. LLM 지식 위키(기사를 읽으면 위키에 축적 → 질문)가 그 도구 중 하나.

LLM이 이해까지 대신하게 되면 그때 다시 논하자 — 지금은 이해가 인간의 병목.

사회자: 오늘 첫 번째 특별 게스트를 소개해드리게 되어 정말 기쁩니다. 이분은 현대 AI를 구축하고, 설명하고, 가끔씩 현대 AI의 이름을 바꾸기도 했습니다. OpenAI 공동창업자이고, Tesla에서 Autopilot을 실제로 작동시킨 분입니다. 가장 복잡한 기술 변화도 쉽고 필연적으로 느끼게 만드는 드문 재능을 갖고 계십니다. 작년에 '바이브 코딩'이라는 말을 만든 것으로 유명하지만, 불과 몇 달 전 "프로그래머로서 이렇게 뒤처진 느낌을 받은 적이 없다"는 더 놀라운 말씀을 하셨습니다. 바로 그 이야기부터 시작하겠습니다. Andrej, 감사합니다.

Karpathy: 네, 안녕하세요. 오늘 이렇게 함께하게 되어 기쁩니다.

사회자: 몇 달 전 "프로그래머로서 이렇게 뒤처진 느낌은 처음"이라고 하셨는데, 그 느낌이 흥분이었나요 아니면 불안이었나요?

Karpathy: 둘 다 섞인 느낌이었습니다. 저도 여러분처럼 지난 1년쯤 에이전틱 도구들 — Cline [?Claude Code] 같은 것들 — 을 써왔는데, 꽤 잘 작동했지만 가끔 실수가 있어서 수정해야 했습니다. 그러다 2024년 12월이 명확한 전환점이었습니다. 연휴라 시간이 좀 있었고, 최신 모델들과 작업하다보니 코드 청크가 그냥 다 맞게 나왔습니다. 마지막으로 수정한 게 언제였는지 기억도 안 날 정도였습니다. 시스템을 점점 신뢰하게 됐고, 그게 바이브 코딩이었습니다. 매우 급격한 전환이었습니다. Twitter(X)에서 이걸 강조했던 건, 많은 사람들이 AI를 ChatGPT 비슷한 것 정도로만 경험했기 때문입니다. 12월을 기점으로 다시 살펴봐야 합니다. 에이전틱 워크플로우가 실제로 작동하기 시작했거든요.

사회자: LLM이 단순히 더 나은 소프트웨어가 아니라 완전히 새로운 컴퓨팅 패러다임이라고 하셨죠. Software 1.0은 명시적 규칙, 2.0은 학습된 가중치, 3.0이 이것이라면 — 이걸 진심으로 믿는 팀은 무엇을 다르게 만들어야 할까요?

Karpathy: Software 1.0은 코드를 직접 씁니다. 2.0은 데이터셋을 만들고 신경망을 훈련시키는 것이 프로그래밍입니다. GPT 같은 LLM을 충분히 큰 태스크 세트로 훈련시키면, 인터넷 데이터로 멀티태스킹을 하게 되고, 이것이 일종의 프로그래밍 가능한 컴퓨터가 됩니다. Software 3.0은 프로그래밍이 프롬프팅으로 바뀌고, 컨텍스트 윈도우가 LLM이라는 인터프리터에 대한 레버가 됩니다.

좋은 예가 있습니다. Open Claude [?Open Claw] 설치할 때, 보통 bash 스크립트를 실행하죠. 여러 플랫폼·시스템을 지원하면 스크립트가 매우 복잡해집니다. 그런데 Open Claude의 설치는 에이전트에게 붙여넣을 텍스트 블록입니다. 에이전트가 자체 지능으로 환경을 보고, 인텔리전트하게 설치하고 디버그합니다. 훨씬 강력합니다. "에이전트에게 붙여넣을 텍스트가 뭔가?"가 프로그래밍 패러다임입니다.

더 극단적인 예는 제가 만든 menu gen입니다. 식당 메뉴를 찍으면 OCR로 아이템을 추출하고, 이미지 생성기로 각 아이템 사진을 가져와서 보여주는 앱입니다. 직접 코딩했죠. 그런데 Software 3.0 버전은 그냥 사진을 Gemini에 주고 "nano banana로 메뉴에 오버레이해줘"라고 하면 됩니다. Gemini가 픽셀 위에 직접 렌더링합니다. 제 menu gen 전체가 구 패러다임이었던 겁니다. 그 앱은 존재해선 안 됐어요.

새로운 것들이 가능해졌고, 기존 패러다임의 속도업만 보면 안 됩니다. 코드는 구조화된 데이터 위에서 작동했는데, 이제 LLM 지식 위키 같은 것도 됩니다 — 문서들을 받아서 다른 방식으로 재컴파일하고 재정렬해 새로운 것을 만드는 것. 이전엔 불가능했던 것들입니다.

사회자: 그 진행을 계속 외삽하면, 2026년 기준으로 90년대 웹사이트, 2010년대 모바일 앱, 지난 시대의 SaaS처럼 지금 아직 대부분 만들어지지 않은 것 중 나중에 보면 당연했을 게 뭘까요?

Karpathy: menu gen 예로 가면, 많은 코드가 존재해선 안 됩니다. 뉴럴넷이 대부분의 일을 하게 됩니다. 극단적 외삽은 꽤 이상하게 보입니다. 완전히 뉴럴 컴퓨터를 상상할 수 있어요 — 원시 비디오나 오디오를 입력받아, 뉴럴넷이 그 순간에 맞는 UI를 디퓨전으로 렌더링하는 장치. 50-60년대에 컴퓨터가 계산기 형태가 될지 신경망 형태가 될지 불분명했던 것처럼, 우리도 전환기에 있습니다. 뉴럴넷이 호스트가 되고 CPU가 코프로세서가 되는 세계. 도구 사용(tool use)은 결정론적 작업을 위한 역사적 부속품처럼 쓰이고, 뉴럴넷들이 네트워크로 연결된 극도로 이질적인 것이 나올 수 있습니다. 단계적으로 갈 것이고, 구체적 경로는 미정입니다.

사회자: 검증가능성 개념에 대해 이야기해보죠. AI가 출력물을 검증할 수 있는 도메인에서 더 빠르게 자동화된다면, 어떤 분야가 사람들이 생각하는 것보다 훨씬 빠르게 움직일까요? 어떤 직업이 실제로는 검증 가능한데 안전하다고 착각하고 있을까요?

Karpathy: 전통 컴퓨터는 코드로 명세화 가능한 것을 자동화합니다. 최신 LLM은 검증 가능한 것을 자동화합니다. 프론티어 랩들이 이 모델들을 훈련시킬 때 거대한 강화학습 환경을 씁니다. 검증 보상을 주면, 모델이 수학·코드 같은 검증 가능한 도메인에서 최고조가 되고 다른 곳에서는 들쭉날쭉해집니다.

이 들쭉날쭉함을 이해하려고 쓴 글입니다. 랩이 훈련 방식에서 검증 가능한 도메인을 넣는 것뿐 아니라, 경제적으로 가치 있는 분야가 더 많은 RL 환경을 만드는 경향도 있습니다. 코드가 좋은 예입니다. 아직 포함되지 않은 검증 가능한 환경들이 많이 있을 겁니다.

재미있는 예가 딸기 안에 레이어가 몇 개냐는 질문인데 모델들이 틀리곤 했죠. 새 예는 이겁니다: "세차장이 50m 거리에 있는데, 차를 몰고 가야 하나 걸어가야 하나?" 최신 모델들이 "걸어가세요, 너무 가까워요"라고 답합니다. Opus 4.7이 10만 줄 코드베이스 리팩터링·제로데이 취약점 발견을 하면서 이걸 틀리는 건 말이 안 됩니다. 이건 RL에 포함 안 된 것이거나, 모델을 도구로 사용하며 감독해야 한다는 신호입니다.

체스 데이터 사례: GPT-3.5→GPT-4 체스 실력 급향상은 단순 스케일업이 아니라 OpenAI가 훈련 세트에 대량 체스 데이터를 추가했기 때문입니다. 우리는 어느 정도 랩이 무엇을 넣느냐에 달린 처지입니다. 이 것들을 탐색해야 하고, 어떤 회로 안에 있는지 파악해야 합니다. 회로 밖에 있다면 파인튜닝이 필요합니다.

사회자: 오늘날 창업자라면, 검증 가능하지만 랩들이 이미 독점할 것 같은 영역(수학·코딩 등)을 어떻게 생각해야 할까요?

Karpathy: 검증가능성이 랩이 집중 안 해도 작동하는 기술을 줍니다. 검증 가능한 RL 환경을 만들 수 있다면 파인튜닝 레버를 당길 수 있습니다. 크고 다양한 RL 환경 데이터셋을 갖고 있으면 파인튜닝 프레임워크로 꽤 잘 작동하는 것을 얻을 수 있습니다. 구체적으로 어떤 도메인인지 말하기 꺼려지지만, 아직 포함되지 않은 매우 가치 있는 RL 환경들이 있다고 생각합니다. 반대로 무엇이 자동화되기 어려운가? 결국 거의 모든 것이 검증 가능하게 만들 수 있습니다. 글쓰기도 LLM 심사단으로 접근 가능합니다. 쉬운지 어려운지의 차이입니다.

사회자: 바이브 코딩을 만든 분이 이제 에이전틱 엔지니어링을 말씀하시는데, 둘의 차이가 뭔가요?

Karpathy: 바이브 코딩은 모두의 바닥을 올리는 것입니다. 누구나 뭔가를 만들 수 있게 되는 것, 놀랍습니다. 에이전틱 엔지니어링은 기존 전문 소프트웨어의 품질 바를 유지하는 것입니다. 바이브 코딩으로 취약점을 도입하면 안 됩니다. 여전히 내 소프트웨어에 책임이 있습니다. 에이전틱 엔지니어링은 들쭉날쭉하고 확률적이지만 강력한 에이전트들을 품질 바를 유지하면서 조율하는 방법입니다. 잘하면 10x 이상 빠릅니다. 실제로 잘하는 사람들은 10x를 훨씬 넘어 보입니다.

사회자: Sam Altman이 세대별로 ChatGPT를 다르게 쓴다고 했는데, 에이전틱 도구를 잘 쓰는 사람과 못 쓰는 사람의 차이는 뭔가요?

Karpathy: 도구를 최대한 활용하고, 모든 기능을 투자하고, 자기 설정에 투자하는 것입니다. 과거에 vim이나 VS Code를 파고들었던 것처럼요. 채용도 재설계가 필요합니다. 퍼즐은 구 패러다임입니다. 큰 프로젝트를 줘야 합니다 — 예를 들어 에이전트용 트위터 클론을 만들고, 보안을 완벽히 하고, 그러면 10개의 Codex 5.4X high [?]로 해킹을 시도합니다. 뚫리면 안 됩니다. 그런 환경에서 사람을 평가해야 합니다.

사회자: 에이전트가 더 많이 할수록 인간의 어떤 기술이 더 중요해지나요?

Karpathy: 에이전트는 아직 인턴입니다. 취향·판단·감독이 여전히 인간 몫입니다. menu gen 예: 구매 시 Stripe 이메일과 Google 이메일을 매칭하려 했는데, 두 이메일이 다를 수 있다는 걸 몰랐습니다. 이런 것들을 잡아내야 합니다.

저는 계획 모드(plan mode)를 별로 안 좋아합니다. 더 일반적인 것이 있습니다 — 에이전트와 함께 매우 상세한 스펙 문서를 먼저 설계하고, 에이전트가 세부를 채워넣는 것입니다. 예를 들어 PyTorch, NumPy, pandas의 API 세부사항 — keep_dims인지 keepdim인지, dim인지 axis인지, reshape인지 permute인지 transpose인지 — 이미 기억 안 합니다. 인턴이 처리합니다. 하지만 텐서에 뷰(view)와 스토리지 개념이 있고, 같은 스토리지의 뷰를 조작하는 것이 다른 스토리지를 쓰는 것보다 효율적이라는 건 알아야 합니다. 불필요한 메모리 복사를 하지 않으려면요. 취향·엔지니어링·설계는 여전히 인간 몫입니다.

사회자: 이 취향과 판단이 시간이 지나면 덜 중요해질까요?

Karpathy: 지금 안 되는 이유는 RL에 포함이 안 됐기 때문입니다. 미적 비용이나 보상이 없거나 충분하지 않습니다. 생성 코드가 가끔 "심장마비"가 날 만큼 별로인 코드일 때도 있습니다 — 매우 bloaty하고, 복붙이 많고, 추상화가 어색하고 brittle합니다. 작동은 하지만 정말 엉망입니다. micro GPT 프로젝트에서 계속 "더 단순하게"를 프롬프트해도 모델이 못 따라옵니다. RL 회로 밖에 있는 느낌, 이가 뽑히는 느낌입니다. 하지만 근본적으로 막는 것은 없습니다. 랩들이 아직 안 한 것뿐입니다.

사회자: Animals vs Ghosts — AI가 동물이 아니라 유령이라는 프레임이 왜 중요한가요?

Karpathy: 이것들이 무엇인지 이해하려고 쓴 글입니다. 좋은 모델이 있으면 더 잘 사용할 수 있으니까요. 동물 지능과 달리, 소리를 질러도 더 잘하거나 못하지 않습니다. 통계적 시뮬레이션 회로입니다. 기반은 사전학습 통계, 위에 RL이 붙어 있습니다. 이것들에 대해 의심하고, 시간이 지나면서 파악하는 자세입니다. 어떻게 시스템을 더 낫게 만드는 다섯 가지 명확한 결론을 제시하는 게 아니라, 이 마음가짐부터 시작합니다.

사회자: 에이전트들이 채팅을 넘어 실제 권한과 로컬 컨텍스트로 행동을 취하는 세계는 어떤 모습일까요?

Karpathy: 모든 것이 아직 인간용으로 쓰여 있습니다. 가장 싫은 게 Docs가 여전히 인간에게 "이렇게 하세요"라고 말하는 겁니다. 나는 아무것도 하기 싫습니다. 에이전트에게 붙여넣을 게 뭔지 알려달란 말입니다. 미래는 워크로드를 에이전트 우선으로 분해하는 것입니다 — 센서(sensors), 액추에이터(actuators), 에이전트가 읽기 좋은 데이터 구조. menu gen 블로그 글 쓸 때 가장 힘들었던 게 코딩이 아니라 Vercel 배포 — DNS 설정, 메뉴 클릭, 각종 서비스 연결. 이게 다 자동화되는 게 에이전트 네이티브 테스트입니다. 궁극적으로 개인·조직의 에이전트 대리인이 생기고, 내 에이전트와 당신 에이전트가 미팅 조율을 할 것입니다.

사회자: 지능이 저렴해지는 세상에서 무엇을 깊이 배울 가치가 있나요?

Karpathy: 최근에 어떤 트윗을 보고 이틀에 한 번씩 생각합니다 — "생각은 위탁할 수 있어도 이해는 위탁할 수 없다." 정말 잘 표현한 말입니다. 나는 여전히 시스템의 일부이고, 정보가 내 뇌에 들어와야 합니다. "무엇을 만들어야 하는가? 왜 할 가치가 있는가? 어떻게 에이전트를 지휘하는가?" — 이 병목은 여전히 이해에 있습니다. LLM 지식 위키가 그 도구입니다 — 기사를 읽으면 위키에 쌓이고, 질문하고, 다른 투영으로 인사이트를 얻습니다. LLM이 이해까지 대신하면 그때 다시 얘기하죠. 지금은 이해가 인간의 병목입니다.
