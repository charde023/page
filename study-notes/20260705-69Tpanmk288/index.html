좋은 Agent Skill을 만드는 방법

한 줄 요약

좋은 에이전트 스킬(Agent Skill)은 언제 호출될지, 어떻게 작게 구조화할지, 어떤 단어로 에이전트를 유도할지, 무엇을 제거할지를 체크리스트로 관리해야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
스킬 지옥(Skill Hell) 스킬은 많지만 좋은 스킬과 나쁜 스킬을 구분하지 못하면 성과가 안 난다 공통 평가 기준이 필요하다
호출 방식(Trigger) 스킬을 사용자가 부를지, 모델이 자동으로 부를지에 따라 비용이 달라진다 모델 호출은 컨텍스트 부담, 사용자 호출은 사용자 인지 부담
구조(Structure) 스킬이 커지면 유지보수와 실행 품질이 떨어진다 단계(steps)와 참고자료(reference)를 나눈다
컨텍스트 포인터(Context Pointer) 필요한 참고자료만 나중에 불러오게 해 스킬 본문을 작게 만든다 분기별 자료는 외부 참조로 빼라
리딩 워드(Leading Words) 에이전트가 원하는 행동을 반복적으로 떠올리게 만든다 짧고 강한 표현으로 행동을 유도한다
레그워크(Legwork) 에이전트가 특정 단계에서 충분히 조사·질문하지 않는 문제를 해결한다 미래 단계를 숨기면 현재 단계에 더 집중한다
가지치기(Pruning) 오래된 지시, 중복, 효과 없는 문장이 스킬을 망친다 침전물(sediment), 잡동사니(crud), 무효 지시(no-op)를 제거한다

내가 모를 만한 것 / 처음 보는 것

  • 에이전트 스킬(Agent Skill) — AI 에이전트가 특정 작업을 더 잘 수행하도록 하는 절차·지식·참고자료 묶음.
  • 사용자 호출 스킬(User-invoked Skill) — 사용자가 직접 명령해 실행하는 스킬. 모델 컨텍스트 부담은 낮지만 사용자가 기억해야 한다.
  • 모델 호출 스킬(Model-invoked Skill) — 모델이 설명(description)을 보고 스스로 필요하다고 판단해 실행하는 스킬. 편하지만 예측 불가능성과 컨텍스트 비용이 생긴다.
  • 컨텍스트 부하(Context Load) — 모델 컨텍스트에 들어가는 설명·지시·자료가 늘어나면서 생기는 토큰 비용과 판단 부담.
  • 인지 부하(Cognitive Load) — 사용자가 어떤 스킬을 언제 써야 하는지 머릿속에 기억해야 하는 부담.
  • skill.md — 스킬의 핵심 지시와 절차가 들어가는 메인 마크다운 파일.
  • 외부 참조(External Reference) — 메인 skill.md 밖에 두고 필요할 때만 불러오는 참고자료.
  • 리딩 워드(Leading Words) — “vertical slice”처럼 짧지만 많은 의미를 담아 에이전트 행동을 유도하는 핵심 표현.
  • 수직 슬라이스(Vertical Slice) — 기능을 DB, API, 프론트처럼 층별로 만들지 않고 작게라도 처음부터 끝까지 동작하는 단위로 구현하는 방식.
  • 삭제 테스트(Deletion Test) — 문단을 지웠을 때 결과가 달라지는지 확인해, 효과 없는 지시(no-op)를 제거하는 방법.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 모델 호출 스킬(Model-invoked Skill)은 설명(description)이 항상 에이전트 컨텍스트에 들어간다 — 스킬 100개면 설명 100개가 매 요청마다 컨텍스트에 들어가는 셈이다.
  2. disable model invocation true 설정을 쓰면 모델이 자동 호출하지 못하고 사용자에게만 설명이 보인다 — 사용자 호출 스킬(User-invoked Skill)로 만드는 방식이다.
  3. 스킬은 크게 단계(steps)와 참고자료(reference)로 나눌 수 있다 — 모든 스킬이 둘 다 필요한 것은 아니지만 이 구분이 구조화의 기준이 된다.
  4. 2PRD 예시는 세 단계로 구성된다 — 관련 컨텍스트 찾기, 테스트 심(test seam) 확인, PRD 작성.
  5. 2PRD에는 참고자료 두 개가 있다 — 테스트 심(test seam) 설명과 PRD 템플릿.
  6. 스킬의 메인 파일인 skill.md는 가능한 작아야 한다 — 유지보수, 감사(audit), 토큰 비용, 사용성 모두에 영향을 준다.
  7. 분기(branch)가 있는 스킬에서는 특정 분기에서만 쓰는 자료를 skill.md 밖으로 빼야 한다 — 필요할 때만 컨텍스트 포인터(context pointer)로 불러온다.
  8. 도메인 모델링(domain modeling) 스킬 예시는 context.md 로컬 용어집 업데이트와 아키텍처 의사결정 기록(ADR) 생성이라는 두 갈래 작업을 가진다.
  9. 리딩 워드 예시로 “vertical slice”를 든다 — 에이전트가 레이어별 구현 대신 작고 동작하는 끝단 간 기능을 먼저 만들도록 유도한다.
  10. 플랜 모드(plan mode)의 흔한 문제는 “명확화 질문” 단계를 대충 하고 바로 계획을 만든다는 점이다 — 그래서 화자는 질문 단계와 계획 단계를 별도 스킬로 분리한다.

1. 문제 제기: 스킬 지옥(Skill Hell)

화자는 개발자들이 여러 형태의 “지옥”을 겪어 왔다고 말한다. 예전에는 튜토리얼을 계속 보지만 실제로 연결하지 못하는 튜토리얼 지옥(tutorial hell)이 있었고, 자바스크립트 프레임워크가 계속 쏟아지는 프레임워크 지옥(framework hell)이 있었다.

이제는 스킬 지옥(Skill Hell)이 생겼다. 수많은 에이전트 스킬(Agent Skill)을 다운로드하거나 직접 만들 수 있지만, 좋은 스킬과 나쁜 스킬을 구분하는 기준이 부족하다. 그래서 사람들은 여러 스킬을 조합해 보지만 기대한 결과를 얻지 못한다.

이 문제는 개인만의 문제가 아니다. 조직도 마찬가지다. 조직은 자신들의 운영 절차(operating procedures)를 에이전트가 수행할 수 있는 스킬로 바꾸는 방법을 잘 모른다. 그 결과 스킬이 줄 수 있는 생산성 이익을 얻지 못한다.

화자는 자신이 운영하는 Matt Pocock Skills 저장소가 인기 있는 엔지니어링 스킬 모음 중 하나이기 때문에, 사용자들이 스킬 지옥에서 벗어나도록 돕고 싶다고 말한다.

2. 스킬 체크리스트: Trigger, Structure, Steering, Pruning

화자가 제안하는 핵심은 “좋은 스킬을 판단하는 공통 기준”이다. 그는 스킬을 다음 네 가지 관점으로 점검하라고 한다.

  1. 호출 방식(Trigger)
    스킬이 어떻게 호출되는가. 사용자가 직접 부르는가, 모델이 자동으로 부르는가.

  2. 구조(Structure)
    스킬 내부가 어떻게 구성되어 있는가. 단계와 참고자료가 잘 나뉘어 있는가.

  3. 행동 유도(Steering)
    스킬이 에이전트에게 실제로 원하는 행동을 하게 만드는가.

  4. 가지치기(Pruning)
    불필요한 내용, 중복, 효과 없는 지시를 제거해 스킬을 작고 명확하게 유지하는가.

화자는 이 내용을 자신의 저장소에 writing great skills라는 스킬로 만들어 두었다고 말한다. 즉, 이 체크리스트 자체를 에이전트에게 적용해 기존 스킬을 개선하거나 새 스킬을 만들 수 있다.

3. Trigger: 사용자 호출과 모델 호출의 선택

스킬은 크게 두 방식으로 호출된다.

첫째는 사용자 호출 스킬(User-invoked Skill)이다. 사용자가 직접 에이전트에게 “이 스킬을 써라”고 말하는 방식이다. 도구나 실행 환경(harness)에 따라 /스킬명처럼 보일 수도 있고 아닐 수도 있지만, 핵심은 사용자가 직접 호출한다는 점이다.

둘째는 모델 호출 스킬(Model-invoked Skill)이다. 이 경우 스킬의 설명(description)이 에이전트의 컨텍스트에 들어간다. 모델은 그 설명을 보고 “이 작업에는 이 스킬이 필요하겠다”고 판단하면 skill.md를 읽어 실행한다.

여기서 설명(description)은 일종의 컨텍스트 포인터(Context Pointer) 역할을 한다. 모델의 컨텍스트 안에서 “필요하면 이 파일을 읽어라”라고 가리키는 포인터다.

하지만 이 포인터를 반드시 모델 컨텍스트에 넣을 필요는 없다. 모델에게 보이지 않게 만들 수도 있다. 이때 스킬은 사용자 호출만 가능해진다. 예를 들어 화자의 grill me 스킬에는 disable model invocation true가 설정되어 있어, 설명이 모델에게는 보이지 않고 사용자에게만 보인다.

화자의 첫 번째 팁은 명확하다.

스킬을 사용자 호출로 만들지, 모델 호출로 만들지 먼저 결정하라.

모델 호출 스킬은 편리해 보인다. 사용자가 직접 기억하지 않아도 모델이 알아서 부를 수 있기 때문이다. 하지만 비용이 있다. 모델 호출 스킬이 하나 늘어날 때마다 그 설명이 매 요청의 컨텍스트에 들어간다. 스킬이 100개라면 100개의 설명이 모델 컨텍스트에 들어간다. 이는 토큰 비용뿐 아니라 모델이 고려해야 할 선택지도 늘린다. 이것이 컨텍스트 부하(Context Load)다.

반대로 사용자 호출 스킬은 모델 컨텍스트를 가볍게 유지한다. 하지만 사용자가 어떤 스킬이 있는지, 언제 써야 하는지 기억해야 한다. 이것은 인지 부하(Cognitive Load)다.

화자는 자신의 스킬이 주로 사용자 호출 방식이라고 말한다. 이유는 예측 가능성 때문이다. 모델 호출 스킬은 아무리 작업에 잘 맞아도 모델이 호출하지 않을 수 있다. 그러면 “왜 안 불렀는지” 평가(eval)해야 하고, 이것이 또 다른 복잡성을 만든다. 화자는 이런 문제 자체를 없애기 위해 사용자 호출 방식을 선호한다.

4. Structure: 단계와 참고자료로 나누기

스킬의 내부 구조는 크게 두 단위로 나눌 수 있다.

  • 단계(Steps): 스킬이 따라야 할 절차
  • 참고자료(Reference): 단계를 수행하는 데 필요한 보조 정보

어떤 스킬은 단계 없이 참고자료만 있을 수 있고, 어떤 스킬은 참고자료 없이 간단한 단계만 있을 수 있다. 하지만 대부분의 스킬을 이 두 단위로 나눠 생각하면 훨씬 관리하기 쉬워진다.

화자는 2PRD 스킬을 예로 든다. 이 스킬은 현재 컨텍스트를 바탕으로 제품 요구사항 문서(Product Requirements Document, PRD)를 만드는 스킬이다.

2PRD의 단계는 다음과 같다.

  1. 관련 컨텍스트 찾기
  2. 사용자와 테스트 심(test seam) 확인하기
  3. PRD 작성하기

여기서 테스트 심 확인 단계는 인간 개입(Human-in-the-loop) 체크포인트다. 이상한 방향으로 테스트를 진행하지 않도록 사용자에게 확인을 받는 장치다.

이 스킬에는 두 가지 참고자료가 있다.

  • 테스트 심(test seam)이 무엇인지에 대한 설명
  • PRD 작성을 위한 마크다운 템플릿

이처럼 스킬을 처음 만들 때는 먼저 어떤 단계가 필요한지 정하고, 각 단계에 어떤 참고자료가 필요한지 정한 뒤, 참고자료를 별도 위치에 둔다.

5. skill.md는 가능한 작게 유지해야 한다

화자의 세 번째 팁은 매우 중요하다.

메인 skill.md 파일을 가능한 작게 유지하라.

스킬은 보통 설명(description), 메인 skill.md, 그리고 거기서 뻗어 나가는 참고자료로 구성된다. skill.md가 작을수록 유지보수가 쉽고, 감사(audit)하기 쉽고, 에이전트가 처리해야 할 말도 줄어든다. 단어 하나를 줄이는 것은 토큰 비용을 줄이는 일이기도 하다.

스킬을 작게 만드는 좋은 방법은 스킬의 분기(branch)를 살펴보는 것이다. 어떤 참고자료가 특정 분기에서만 필요하다면, 그 자료는 메인 skill.md에서 빼는 후보가 된다.

2PRD는 항상 PRD를 만들고, 항상 테스트 심을 확인하므로 참고자료가 매번 필요하다. 따라서 참고자료가 skill.md 안에 있어도 큰 문제가 없다.

하지만 domain modeling 스킬은 다르다. 이 스킬은 로컬 용어집인 context.md를 업데이트할 수도 있고, 아키텍처 의사결정 기록(Architectural Decision Record, ADR)을 만들 수도 있다. 또는 둘 다 하지 않을 수도 있다. 즉, 여러 분기가 있다.

이 경우 context.md 템플릿이나 ADR 템플릿을 메인 skill.md에 항상 넣을 필요가 없다. 대신 별도 마크다운 파일로 빼고, skill.md에는 “이 템플릿이 필요하면 이 파일을 보라”는 컨텍스트 포인터(Context Pointer)만 둔다. 화자는 이것을 외부 참조(External Reference)라고 부른다.

정리하면, 여러 방식으로 쓰이는 스킬에서는 분기별 참고자료를 컨텍스트 포인터 뒤에 숨겨야 한다. 그러면 메인 스킬이 작고 명확해진다.

6. Steering: 리딩 워드로 에이전트 행동을 유도하기

화자가 가장 강조하는 기법은 리딩 워드(Leading Words)다. 문제는 스킬에 지시를 적었는데도 에이전트가 원하는 대로 행동하지 않는 경우다.

리딩 워드는 짧은 표현 안에 많은 의미를 압축한 단어 또는 구문이다. 문학 이론에서는 라이트보르트(Leitwort)와 비슷한 개념으로 볼 수 있다. 에이전트 스킬에서는 이 표현을 반복적으로 사용해 모델이 그 단어를 자신의 추론 과정과 출력에서 다시 사용하게 만든다. 그렇게 되면 행동이 그 단어가 가리키는 방향으로 유도된다.

예를 들어 에이전트에게 큰 작업을 맡기면 흔히 레이어별로 구현한다. 먼저 데이터베이스 계층을 만들고, 그다음 스키마를 만들고, API 엔드포인트를 만들고, 마지막에 프론트엔드를 만든다. 하지만 사람 개발자는 보통 작은 기능을 먼저 끝까지 동작하게 만들고 피드백을 받은 뒤 확장한다.

그냥 “레이어별로 만들지 말고 작은 단위를 먼저 만들어라”라고 할 수도 있다. 하지만 화자는 “수직 슬라이스(Vertical Slice)”라는 리딩 워드를 쓰라고 한다. 이 표현은 개발자들에게 익숙한 개념이고, 짧지만 많은 의미를 담고 있다.

스킬 안에서 “vertical slice”를 반복하면, 에이전트의 추론 흔적(reasoning traces)이나 계획에 “얇은 수직 슬라이스(thin vertical slice)로 구현하겠다”는 식의 표현이 나타난다. 그러면 실제 구현 계획도 더 좋아질 가능성이 높다.

핵심은 영어가 넓은 API처럼 작동한다는 점이다. 다양한 표현이 서로 다른 행동을 유도할 수 있다. 좋은 리딩 워드를 찾고, 그것을 스킬 안에서 일관되게 사용해야 한다.

7. Legwork: 현재 단계에 더 많은 노력을 쓰게 만들기

에이전트는 특정 단계에서 충분한 노력을 들이지 않는 경우가 많다. 화자는 이것을 레그워크(Legwork)가 부족하다고 표현한다.

대표 사례는 플랜 모드(Plan Mode)다. 플랜 모드는 보통 두 단계로 구성된다.

  1. 명확화 질문하기
  2. 계획 만들기

문제는 에이전트가 최종 목표인 “계획 만들기”를 보고 있기 때문에, 명확화 질문을 대충 하고 빨리 계획을 만들어 버린다는 점이다.

화자의 해결책은 단계를 분리하는 것이다. 그는 grill with docs라는 스킬을 명확화 질문 단계 전용으로 만들고, 계획 수립은 별도 스킬로 나눈다. 즉, 에이전트가 한 번에 전체 미래 단계를 보지 못하게 한다. 현재 단계만 보게 하면 그 단계에 더 집중하고 더 많은 레그워크를 수행한다.

항상 모든 스킬을 단계별로 쪼갤 필요는 없다. 하지만 특정 단계에서 더 깊은 조사, 질문, 분석이 필요하다면 미래 목표를 숨기는 방식이 매우 효과적이다.

8. Pruning: 중복, 침전물, 무효 지시 제거하기

마지막은 가지치기(Pruning)다. 큰 스킬은 보통 다른 문제가 누적된 증상이다.

첫 번째는 중복이다. 같은 내용을 여러 곳에 반복하지 않아야 한다. 각 참고자료와 규칙에는 단일 진실 공급원(Single Source of Truth)이 있어야 한다. 예를 들어 PRD 템플릿이나 테스트 심 설명을 여러 위치에 반복해서 적으면 유지보수가 어려워진다.

두 번째는 침전물(Sediment)이다. 여러 사람이 같은 마크다운 문서에 기여하다 보면, 각자 내용을 추가하지만 남의 내용을 삭제하거나 수정하지 못한다. 그러면 오래되고 관련 없는 내용이 계속 쌓인다. 특히 제대로 구조화되지 않은 자료가 쌓이면 스킬이 무거워진다.

침전물이 많은 스킬은 먼저 구조를 봐야 한다. 추가된 내용이 모든 분기에 필요한지 확인하고, 특정 분기에만 필요하면 해당 분기용 외부 참조로 옮긴다. 완전히 무관하거나 오래된 내용은 제거한다.

세 번째는 무효 지시(No-op)다. 겉으로는 뭔가 하는 것처럼 보이지만 실제로 에이전트 행동에 영향을 주지 않는 문장이다. 예를 들어 구현 스킬 안에 “길고 자세한 커밋 메시지를 작성하라”는 문단이 있다고 해보자. 이 문단을 지워도 에이전트가 여전히 괜찮은 커밋 메시지를 작성한다면, 그 문단은 사실상 무효 지시일 가능성이 높다.

화자는 자신의 스킬이 작은 이유가 바로 이런 삭제 테스트(Deletion Test), 리딩 워드 압축, 무관한 내용 제거, 침전물 제거 때문이라고 말한다.

9. 최종 프레임워크 요약

좋은 스킬을 만들기 위한 전체 점검 흐름은 다음과 같다.

  1. Trigger 확인
    스킬이 적절한 시점에 호출되는지 본다. 모델 호출로 컨텍스트 부하를 만들 것인지, 사용자 호출로 인지 부하를 만들 것인지 결정한다.

  2. Structure 확인
    스킬의 분기를 파악하고, 단계와 참고자료를 나눈다. 특정 분기에만 필요한 자료는 메인 skill.md 밖으로 뺀다.

  3. Steering 확인
    긴 설명을 리딩 워드로 압축하고, 그 리딩 워드가 추론 흔적에 나타나는지 본다. 특정 단계의 레그워크가 부족하면 스킬을 더 작게 나눌지 검토한다.

  4. Pruning 확인
    침전물, 잡동사니(crud), 무효 지시(no-op)를 제거한다.

화자는 이 모든 내용을 Writing Great Skills 스킬 안에 담아 두었으니, 기존 스킬을 개선하거나 커뮤니티에서 가져온 스킬의 품질을 점검하는 데 사용하라고 권한다.

종합 체크리스트

  • [ ] 내가 쓰는 스킬이 사용자 호출(User-invoked)인지 모델 호출(Model-invoked)인지 구분한다.
  • [ ] 모델 호출 스킬이 너무 많아 컨텍스트 부하(Context Load)를 만들고 있지 않은지 확인한다.
  • [ ] 사용자 호출 스킬이 너무 많아 내가 기억해야 할 것이 과도하지 않은지 확인한다.
  • [ ] 스킬을 단계(Steps)와 참고자료(Reference)로 나눠 다시 정리한다.
  • [ ] skill.md에 꼭 필요한 내용만 남긴다.
  • [ ] 특정 분기에서만 쓰는 템플릿·설명은 외부 참조(External Reference)로 분리한다.
  • [ ] 에이전트 행동을 유도할 리딩 워드(Leading Words)를 정한다.
  • [ ] 리딩 워드가 에이전트의 계획·추론·출력에 실제로 나타나는지 확인한다.
  • [ ] 에이전트가 특정 단계에서 대충 넘어가면 그 단계를 별도 스킬로 분리한다.
  • [ ] 중복 문장과 중복 참고자료를 제거한다.
  • [ ] 오래된 지시나 누적된 침전물(Sediment)을 삭제한다.
  • [ ] 지워도 결과가 변하지 않는 무효 지시(No-op)를 삭제 테스트로 찾아낸다.

안녕하세요. 원래 AI Engineer World’s Fair에 꼭 가고 싶었지만, 가족 일이 생겨 참석하지 못하게 되었습니다. 대신 여러분을 빈손으로 두지는 않겠습니다. 제가 샌프란시스코에서 하려고 했던 발표를 여기서 하겠습니다.

이 발표의 제목은 “빠진 매뉴얼: 훌륭한 스킬을 작성하는 방법(The Missing Manual: How to Write Great Skills)”입니다. 저는 좋은 스킬과 나쁜 스킬을 구분하는 능력이 점점 더 중요해지고 있다고 생각합니다.

개발자들은 여러 종류의 지옥을 찾아내는 데 꽤 재능이 있는 것 같습니다. 몇 년 전에는 튜토리얼 지옥(tutorial hell)이 있었습니다. 무언가를 배우기 위해 튜토리얼을 계속 보지만, 전체를 연결하지 못하고 빠져나오기 어려운 반복에 갇히는 상태입니다. 또 프레임워크 지옥(framework hell)도 있었습니다. 10분마다 새로운 자바스크립트 프레임워크가 발표되고, 계속 최신 유행을 배워야 하는 상황이었습니다. 이제는 또 다른 지옥이 생겼다고 봅니다. 바로 스킬 지옥(Skill Hell)입니다.

스킬 지옥은 다운로드하거나 기여하거나 직접 만들 수 있는 스킬이 많이 있지만, 그 조각들이 어떻게 함께 작동하는지 모르는 상태입니다. 좋은 스킬과 나쁜 스킬을 구분하지 못합니다. 그래서 사람들은 다양한 프레임워크와 스킬을 한꺼번에 조합해 보려 하지만, 스킬이 약속하는 결과를 얻지 못합니다.

이 문제는 개인에게도 있고 조직에도 있습니다. 조직은 좋은 스킬을 어떻게 만들지, 자신들의 운영 절차를 에이전트가 수행할 수 있는 것으로 어떻게 바꿀지 이해하지 못합니다. 그렇게 하지 못하면 스킬이 제공할 수 있는 이익을 얻기 어렵습니다. 마치 “스킬 하나만 더 추가하면 돼”라고 말하는 상황과 비슷합니다.

저도 약간의 책임감을 느낍니다. 제 스킬 저장소인 Matt Pocock Skills는 가장 인기 있는 엔지니어링 스킬 모음 중 하나입니다. 그래서 제 스킬을 사용하는 사람들이 스킬 지옥에서 벗어나도록 돕고 싶습니다.

그러면 어떻게 해야 할까요? 무엇이 빠져 있을까요? 제 생각에는 훌륭한 스킬을 만드는 기준을 모른다는 것이 문제입니다. 아직 우리는 어떤 스킬을 보고 “이 부분은 좋고, 이 부분은 나쁘다”고 말할 공통 기준이 없습니다. 스킬을 평가하고 개선하기 위한 공유 루브릭(rubric)이나 프레임워크가 없습니다. 그래서 이 발표에서 그 기준을 드리려고 합니다.

저는 스킬 체크리스트를 제시하겠습니다. 스킬 안에서 확인해야 할 항목들, 스킬이 말한 대로 작동하는지 확인하는 방법, 개선하는 방법, 스킬을 작성하는 방법에 대한 체크리스트입니다.

이 체크리스트는 네 부분으로 구성됩니다. 첫째는 스킬의 트리거(trigger), 즉 스킬이 어떻게 호출되는지와 그 설계 결정입니다. 둘째는 스킬의 내부 구조(structure), 즉 스킬이 내부적으로 어떻게 구성되고 배치되는지입니다. 셋째는 스킬을 통해 어떻게 에이전트를 조종하거나 유도하는지(steering)입니다. 넷째는 스킬을 가능한 작게 만드는 방법입니다. 작동하는 스킬을 만든 뒤에는 불필요한 것과 효과 없는 지시(no-op)를 제거해야 합니다.

제가 현장에 없다는 장점도 하나 있습니다. 여러분은 이 내용을 바로 시도해 볼 수 있습니다. 제가 이 모든 내용을 제 저장소의 writing great skills라는 새 스킬로 만들어 두었기 때문입니다. 당장 쓸 일이 있다면 제 스킬 저장소로 가서 이 스킬을 사용해 기존 스킬을 개선하거나 새 스킬을 작성하면 됩니다.

이제 체크리스트를 살펴보겠습니다. 첫 번째는 트리거(trigger), 즉 스킬이 호출되는 방식입니다. 이를 설명하기 위해 비교를 하나 하겠습니다. 제 스킬은 종종 superpowers라는 매우 인기 있는 엔지니어링 스킬 모음과 비교됩니다. 사람들은 자주 “당신의 스킬과 superpowers는 어떻게 다른가요?”라고 묻습니다.

이를 이해하려면 사용자 호출 스킬(user-invoked skill)과 모델 호출 스킬(model-invoked skill)의 차이를 알아야 합니다. 어떤 스킬이든 사용자가 직접 호출할 수 있습니다. 스킬은 파일 시스템에 있고, 에이전트는 그 스킬을 열어 내용을 이해할 수 있습니다. 실행 환경에 따라 / 형태가 아닐 수도 있지만, 사용자는 항상 스킬을 직접 호출할 수 있습니다.

스킬이 호출되는 또 다른 방식은 에이전트가 직접 호출하는 것입니다. 이것을 모델 호출 가능 스킬(model-invokable skill) 또는 모델 호출 스킬(model-invoked skill)이라고 합니다. 스킬에는 설명(description)이 있고, 그 설명은 에이전트의 컨텍스트에 들어갑니다. 에이전트는 그 설명을 보고 “이 스킬을 호출해야겠다”고 판단한 뒤, 스킬의 핵심 내용이 들어 있는 skill.md 파일을 자신의 컨텍스트 창으로 읽어옵니다. 이것이 스킬 호출이 일어나는 방식입니다.

따라서 설명(description)은 일종의 컨텍스트 포인터(context pointer) 역할을 합니다. 에이전트의 컨텍스트 안에 있으면서, 더 많은 컨텍스트가 필요하면 갈 수 있는 다른 파일을 가리킵니다. 하지만 이 컨텍스트 포인터를 반드시 에이전트 컨텍스트에 넣어야 하는 것은 아닙니다. 에이전트에게 보이지 않게 할 수도 있습니다. 이것이 사용자 호출 스킬(user-invoked skill)입니다. 어떤 스킬은 이 컨텍스트 포인터가 없기 때문에 사용자만 호출할 수 있습니다. 이 포인터는 선택 사항입니다.

예를 들어 제 코드베이스 디자인(code base design) 스킬은 모델 호출 스킬입니다. 설명이 에이전트의 컨텍스트 창에 들어갑니다. 반면 grill me 스킬을 보면 disable model invocation true가 설정되어 있습니다. 이는 이 설명이 사용자에게만 보이고, 에이전트에게는 보이지 않는다는 뜻입니다.

그래서 첫 번째 팁은 이것입니다. 스킬을 사용자 호출로 만들지, 모델 호출로 만들지 결정하십시오. 모델 호출 스킬이 더 좋아 보일 수도 있습니다. 모델이 스스로 호출할 수도 있고, 사용자도 호출할 수 있으니 더 유연해 보입니다. 하지만 모델 호출 스킬을 에이전트 환경에 추가할 때마다 에이전트의 컨텍스트 부하(context load)가 증가합니다. 매 요청마다 토큰을 쓰는 설명이 하나 추가되고, 에이전트가 생각해야 할 선택지도 하나 늘어납니다. 모델 호출 스킬이 100개라면 에이전트 컨텍스트 안에 설명 100개가 들어갑니다.

그렇다면 모델 호출 스킬 수를 줄이거나 전부 사용자 호출 스킬로 쓰는 것이 합리적으로 보입니다. 하지만 사용자 호출 스킬에는 다른 부담이 있습니다. 사용자 호출 스킬이 많아질수록 사용자의 인지 부하(cognitive load)가 커집니다. 즉, 사용자가 머릿속에 기억해야 할 것이 늘고, 조종사인 사용자에게 더 많은 숙련도가 요구됩니다.

Matt Pocock Skills와 superpowers를 비교하면, superpowers는 주로 모델 호출 스킬입니다. 에이전트에게 초능력을 주는 방식입니다. 반면 제 스킬은 제가 완전한 통제권을 갖는 것을 선호합니다. 그래서 에이전트의 컨텍스트 부하는 가능한 작게 유지할 수 있지만, 제게 더 많은 인지 부하가 생깁니다. 스킬을 최대한 활용하려면 제가 스킬을 깊이 이해해야 합니다.

왜 제가 사용자 호출 스킬을 선호할까요? 모델 호출 스킬에는 예측 불가능성이라는 비용이 있습니다. 어떤 리소스에서 다른 리소스로 가리키는 컨텍스트 포인터가 있을 때, 모델은 그것을 따라가지 않기로 선택할 수 있습니다. 작업에 완벽히 맞는 스킬이어도 모델이 호출하지 않을 수 있습니다. 저는 이런 예측 불가능성을 제거하고, 대신 사용자에게 약간의 인지 부하를 주는 편을 선호합니다. 그러면 한 종류의 문제가 아예 문제가 되지 않습니다. 예측 불가능성이 있으면 사람들이 스킬이 적절한 시점에 호출되는지 평가(eval)해야 하는데, 이것은 꽤 까다로운 문제입니다. 저는 피하고 싶은 문제입니다.

여기서 말하고 싶은 것은 모델 호출 스킬과 사용자 호출 스킬 모두 비용이 있다는 점입니다. 어느 쪽을 선택할지는 쉬운 결정이 아닙니다. 이것이 트리거(trigger), 즉 스킬 호출 방식에 대한 이야기입니다.

이제 구조(structure), 즉 스킬의 내부 배치에 대해 이야기하겠습니다. 저는 대부분의 스킬에 넣어야 할 주요 단위가 두 가지 있다고 봅니다. 단계(steps)와 참고자료(reference)입니다. 단계는 스킬이 따라갈 절차입니다. 참고자료는 그 단계를 수행하는 데 도움이 되는 보조 정보입니다. 단계가 전혀 없고 참고자료만 있는 스킬도 있을 수 있고, 참고자료 없이 간단한 단계만 있는 스킬도 있을 수 있습니다. 하지만 스킬을 이 두 단위로 구성된 것으로 생각하면 훨씬 쉽게 분해할 수 있습니다.

예를 들어 제 스킬 중 2PRD라는 것이 있습니다. 이 스킬은 현재 컨텍스트 창을 바탕으로 제품 요구사항 문서(Product Requirements Document, PRD)를 만듭니다. 이 스킬에는 세 단계가 있습니다. 관련 컨텍스트를 찾고, 사용자와 테스트 심(test seam)을 확인합니다. 여기에는 약간의 인간 개입(human-in-the-loop) 체크포인트가 있습니다. 테스트와 관련해 이상한 일을 하지 않도록 확인하는 단계라서 저는 매우 중요하다고 봅니다. 그리고 마지막으로 제품 요구사항 문서를 작성합니다.

이 세 단계를 처리하기 위해 두 가지 참고자료가 있습니다. 하나는 테스트 심(test seam)이 무엇인지에 대한 설명이고, 다른 하나는 제품 요구사항 문서 템플릿입니다. 말 그대로 PRD 작성을 위한 마크다운 템플릿입니다.

따라서 처음부터 스킬을 작성할 때는 이 방식이 좋습니다. 필요한 단계가 있는지 파악하고, 그 단계를 작성한 다음, 각 단계에 필요한 참고자료를 파악해 스킬 안의 별도 참고자료 위치에 둡니다.

그러나 매우 중요한 제약이 있습니다. 세 번째 팁입니다. 메인 skill.md 파일을 가능한 작게 만들어야 합니다. 모든 스킬은 설명(description), skill.md 파일, 그리고 그곳에서 뻗어 나가는 참고자료로 구성됩니다. skill.md를 작게 만들면 여러 방식으로 이득이 있습니다. 작은 스킬은 유지보수가 쉽고, 감사(audit)하기 쉽고, 생각해야 할 단어가 적습니다. 단어 하나를 줄일 때마다 토큰 비용도 줄어듭니다. 그래서 저는 작은 스킬이 유지보수자와 사용자 모두에게 매우 중요하다고 믿습니다.

스킬을 작게 만드는 유용한 방법은 스킬의 여러 분기(branch), 즉 스킬이 사용될 수 있는 여러 방식을 생각하는 것입니다. 특정 분기에서만 사용되는 참고자료가 있다면, 그것은 메인 skill.md에서 제거할 후보입니다.

예를 들어 2PRD에는 테스트 심 설명과 PRD 템플릿이라는 두 가지 참고자료가 있습니다. 우리는 항상 PRD를 만들기 때문에 PRD 템플릿은 매번 필요합니다. 테스트 심도 항상 확인하므로 테스트 심 설명도 매번 필요할 가능성이 높습니다. 따라서 2PRD는 분기가 하나뿐이고, 모든 참고자료가 그 분기에 속합니다. 그러므로 이 자료들이 skill.md에 있어도 됩니다.

하지만 제 다른 스킬인 도메인 모델링(domain modeling)을 보면 상황이 다릅니다. 도메인 모델링은 두 가지 일을 합니다. 하나는 context.md라는 로컬 용어집을 업데이트하는 것이고, 다른 하나는 아키텍처 의사결정 기록(Architectural Decision Records, ADR)을 만드는 것입니다. 즉 두 가지 다른 일을 합니다. 실제로는 둘 중 아무것도 하지 않을 수도 있습니다. 그 경우에는 context.md 템플릿도 ADR 템플릿도 필요 없습니다. 다시 말해 도메인 모델링에는 두 개 또는 세 개의 분기가 있습니다.

따라서 ADR 템플릿이나 context.md 템플릿을 메인 스킬에 포함할 필요가 없습니다. 별도 영역으로 옮길 수 있습니다. 방법은 skill.md 파일에 컨텍스트 포인터를 두고, 컨텍스트 템플릿을 스킬 폴더 안의 별도 마크다운 파일로 가리키는 것입니다. 그 컨텍스트 포인터는 “템플릿이 필요하거나 context.md 파일을 업데이트해야 한다면 이 파일로 가라”고 말하면 됩니다. 저는 이것을 외부 참조(external reference)라고 부릅니다. skill.md 외부에 있는 참고자료이고, 쉽게 참조할 수 있습니다. 스킬과 함께 묶여 있기 때문에 에이전트가 쉽게 가져올 수 있습니다. 이것은 skill.md를 가능한 작게 만드는 기법이고, 많은 장점이 있습니다.

분기별 참고자료는 컨텍스트 포인터 뒤에 숨기십시오. 다시 말해 스킬이 여러 방식으로 사용될 것 같다면, 각 분기에 관련된 참고자료를 컨텍스트 포인터 뒤에 숨기십시오. 이것이 구조(structure)입니다. skill.md를 매우 작게 만드는 것, 스킬의 분기를 생각하는 것, 자료를 컨텍스트 포인터 뒤로 옮기는 것, 그리고 스킬 안의 두 주요 단위인 단계와 참고자료를 생각하는 것입니다.

이제 행동 유도(steering)로 넘어가겠습니다. 에이전트가 우리가 원하는 일을 하게 만드는 방법입니다. 저에게 steering은 아주 멋진 한 가지 기법으로 요약됩니다. 이 발표에서 가장 가져가셨으면 하는 핵심입니다. 이 기법은 “에이전트가 내가 원하는 일을 하지 않는다”는 문제를 해결합니다. 스킬에 뭔가를 명시했고, 분명히 적었다고 생각했는데도 에이전트가 그 일을 하지 않는 상황입니다.

저는 이 일이 일어나는 주된 이유가 리딩 워드(leading words)를 사용하지 않기 때문이라고 봅니다. 리딩 워드, 문학 이론을 좋아한다면 라이트보르트(Leitwort)라고 할 수도 있는 개념은, 아주 작은 공간에 많은 의미를 담는 특정 단어들입니다. 리딩 워드는 에이전트에게 강력합니다. 스킬 텍스트 안에 리딩 워드를 넣으면, 에이전트는 작업 과정, 사고 토큰(thinking tokens), 출력에서 그 리딩 워드를 다시 반복합니다.

그렇게 단어가 재강조되고, 그 단어가 우리가 원하는 행동을 잘 설명한다면, 에이전트의 행동이 바뀝니다.

예를 들어 보겠습니다. 에이전트의 고전적인 문제 중 하나는 레이어별로 코딩한다는 것입니다. 큰 작업을 주면 일반적으로 데이터베이스 계층 전체를 만들고, 스키마 전체를 만들고, API 엔드포인트 전체를 만들고, 프론트엔드 전체를 만듭니다. 보통 사람이 하는 것처럼 빨리 피드백을 받고, 작은 것을 먼저 동작하게 만든 뒤 확장하지 않습니다.

우리는 “레이어별로 코딩하지 말고, 먼저 작은 슬라이스를 만들고 거기서 확장하라”고 말할 수 있습니다. 하지만 대신 리딩 워드를 사용하면 어떨까요? 예를 들어 “수직 슬라이스(vertical slice)”를 리딩 워드로 정하는 것입니다. 작업을 수평 슬라이스(horizontal slice)가 아니라 수직 슬라이스(vertical slice)로 나누라는 뜻입니다. 수직 슬라이스는 개발에서 꽤 잘 알려진 용어이므로, 에이전트의 사전 지식(priors)을 자극해 우리가 의미하는 바를 이해하게 할 수 있습니다.

스킬을 단지 “vertical slice”라는 두 단어로만 만들자는 뜻은 아닙니다. 우리가 하는 일은 많은 의미를 비교적 짧은 구문에 압축하고, 그것을 스킬 전체에서 반복하는 것입니다. 이 기법의 좋은 점은 효과가 있었는지 알 수 있다는 것입니다. 스킬에서 “vertical slice”라고 말하면, 추론 흔적(reasoning traces)에서 “얇은 수직 슬라이스로 하자”는 식의 표현이 나타나는 것을 볼 수 있습니다. 그러면 더 나은 구현 계획을 얻을 수 있습니다.

제가 이 기법을 설명하면 대부분의 사람은 “맞아, 나도 이미 어느 정도 하고 있었어”라고 느낍니다. 작은 표현을 사용해 에이전트가 원하는 일을 하도록 유도해 왔다는 것입니다. 제가 요구하는 것은 이제 그것을 스킬 안에서 일관되게 사용하고, 에이전트가 그 방식을 받아들이는지 사고 흔적에서 관찰하라는 것입니다.

에이전트가 원하는 일을 하지 않는다면, 리딩 워드를 더 일관되고 강력하게 만들 필요가 있습니다. 또 다른 후보도 찾아야 합니다. 영어는 호출할 수 있는 함수가 다양한 넓은 API와 같습니다. 실험할 수 있는 표현이 많습니다. 리딩 워드 후보는 많고, 에이전트도 그런 후보를 생각해 내는 데 꽤 능숙합니다.

에이전트와 함께 사용할 수 있는 또 다른 작은 레버가 있습니다. 때로 에이전트는 충분한 레그워크(legwork)를 하지 않습니다. 여기서 말하는 것은 특정 단계에서 충분한 노력을 들이지 않는다는 뜻입니다. 예를 들어 명확화 질문을 하거나 코드베이스를 탐색하는 단계가 있을 때, 에이전트가 그 단계에 충분한 노력을 쓰지 않는 경우입니다.

이 문제의 아주 전형적인 사례는 플랜 모드(plan mode)입니다. 플랜 모드에는 두 단계가 있습니다. 명확화 질문을 하고, 계획을 만드는 것입니다. 제가 시도해 본 거의 모든 플랜 모드 구현에서 명확화 질문 단계는 충분한 레그워크를 하지 않았습니다. 에이전트는 최종 목표가 계획 작성이라는 것을 봅니다. 그래서 명확화 질문을 조금만 하고, 몇 가지 질문만 한 뒤, 서둘러 계획을 만듭니다.

제 해결책은 무엇이었을까요? 저는 플랜 모드 대신 grill with docs라는 스킬을 둡니다. 이것은 명확화 질문 단계에 해당합니다. 그리고 계획 단계를 별도 스킬로 분리했습니다. grill with docs는 이제 독립적인 스킬이고, 에이전트는 그 과정의 해당 부분만 봅니다. grill with docs가 끝나면 그다음 2PRD를 실행합니다. 즉 1단계와 2단계가 있지만, 에이전트는 한 번에 한 단계만 봅니다.

이것은 현재 단계에서 레그워크를 늘리는 매우 좋은 기법입니다. 미래 목표와 미래 단계를 숨기는 것입니다. 항상 스킬을 개별 단계로 나눌 필요는 없습니다. 하지만 특정 단계에서 훨씬 더 많은 노력이 필요하다면 이만한 기법이 없습니다. 매우 잘 작동합니다.

이것이 steering입니다. 원하는 행동을 작고 재사용 가능한 토큰으로 포착하기 위해 리딩 워드를 사용하고, 각 단계에서 충분한 레그워크를 하도록 만드는 것입니다.

이제 가지치기(pruning)로 가겠습니다. 가지치기는 잘못될 수 있는 실패 모드를 빠르게 훑는 것입니다. 첫 번째는 꽤 명확합니다. 거대한 스킬을 원하지 않습니다. 거대한 스킬은 보통 다른 문제가 잘못되고 있다는 증상입니다.

첫 번째 문제는 간단합니다. 반복하지 마십시오. 중복을 조심해야 합니다. 저는 일반적으로 스킬의 모든 부분에 단일 진실 공급원(single source of truth)이 있기를 바랍니다. 예를 들어 PRD 템플릿 같은 참고자료나, 테스트 심이 무엇인지 같은 작은 설명이 있다면, 여러 곳에 반복하거나 여러 단계에서 중복해서 다루지 않도록 해야 합니다. 참고자료 사이에서도 각 부분이 하나의 진실 공급원을 갖도록 해야 합니다.

스킬이 커지는 다음 이유는 침전물(sediment)입니다. 이는 여러 사람이 같은 문서 작업을 할 때 흔히 생깁니다. 모두가 공유 마크다운 파일에 자기 내용을 추가하지만, 다른 사람이 쓴 내용을 삭제하거나 수정할 용기는 내지 못합니다. 그래서 관련 없는 자료가 거대하게 쌓입니다. 특히 제대로 배치되지 않은 내용이 많아집니다.

침전물이 많은 스킬에서는 구조를 먼저 봐야 합니다. 추가된 내용이 모든 분기에 관련 있는지 확인해야 합니다. 그렇지 않다면 올바른 분기로 옮기십시오. 완전히 무관하다면 제거하거나 없애십시오. 완전히 오래된 내용이라면 확실히 제거해야 합니다.

다음 실패 모드는 에이전트가 스킬을 작성할 때 매우 흔합니다. 바로 무효 지시(no-op)입니다. 스킬 안에서 뭔가를 하는 것처럼 보이지만, 실제로는 스킬의 맥락에서 에이전트 행동에 영향을 주지 않는 것입니다. 예를 들어 구현(implement) 스킬이 있고, 그 안에 에이전트에게 길고 자세한 커밋 메시지를 쓰라고 지시하는 문단이 있다고 해봅시다. 그 문단을 지우면 어떻게 될까요? 아마 에이전트는 여전히 꽤 괜찮고 긴 커밋 메시지를 쓸 것입니다.

사람들은 제 스킬이 어떻게 그렇게 작을 수 있는지 자주 묻습니다. 답은 이런 기법을 쓰는 것입니다. 삭제 테스트(deletion test)를 하고, 내용을 리딩 워드로 압축하고, 무관한 내용을 넣지 않고, 침전물을 제거합니다.

이제 전체 흐름을 정리하겠습니다. 첫째, 트리거(trigger)를 확인합니다. 스킬이 적절한 시점에 실행되는지 확인합니다. 컨텍스트 부하(context load)를 만들고 있는지, 아니면 사용자에게 인지 부하(cognitive load)를 주고 있는지 봅니다. 둘째, 구조(structure)에서는 분기를 생각합니다. 단계를 참고자료와 나누고, 특정 분기에만 관련된 자료는 메인 skill.md 밖으로 옮깁니다. 셋째, steering에서는 텍스트를 리딩 워드로 압축하고, 그 리딩 워드가 추론 흔적에 나타나는지 봅니다. 또한 레그워크를 생각합니다. 현재 단계에 더 집중하도록 미래 단계를 숨기기 위해 스킬을 더 쪼갤 필요가 있는지 검토합니다. 넷째, pruning에서는 전체 스킬에 대해 최종 가지치기를 합니다. 침전물, 잡동사니(crud), 특히 무효 지시(no-op)를 주의 깊게 봅니다.

이 프레임워크를 시작하는 가장 좋은 방법은 Writing Great Skills 스킬을 사용하는 것입니다. Matt Pocock Skills에서 확인하고 다운로드해서 자신의 스킬을 개선하는 데 사용하십시오. 커뮤니티가 만든 스킬에도 적용해, 실제로 가져오는 스킬이 좋은지 점검할 수 있습니다.
