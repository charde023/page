자기 학습 에이전트를 위한 메모리와 드리밍

원작자 Ravi · Anthropic (Platform · API Knowledge Team) · 업로드 2026-05-23 · 21.6분 · 원본 영상 ↗
한 줄 요약

Claude Managed Agents의 Memory는 파일 시스템 형태로 에이전트 간 지식을 공유하고, Dreaming은 세션 외부에서 비동기로 메모리를 자동 정제·개선해 에이전트 전체의 성능 하한선을 끌어올린다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Memory as File System Claude가 이미 잘하는 파일 탐색·bash·grep을 메모리 인터페이스로 그대로 활용 새 추상화 없이 강점을 메모리에 연결
읽기/쓰기 권한 범위 (scope) 조직 전체 읽기 전용 + 태스크별 읽기-쓰기로 계층 분리 메모리 충돌·오염 방지의 핵심 설계
Optimistic Concurrency Control 여러 에이전트가 동시에 메모리에 쓸 때 서로 덮어쓰지 않도록 충돌 제어 멀티에이전트 공유 상태 안전성
Dreaming (드리밍) 세션 외부 배치 프로세스로 전체 세션 기록을 분석해 메모리를 전역 최적화 개별 에이전트가 볼 수 없는 패턴까지 감지
드리밍의 Out-of-Band 구조 에이전트 루프와 완전 분리 → 레이턴시 0, 태스크 목표와 메모리 품질 개선 충돌 없음 설계 원칙: 에이전트 핫패스에서 제거
버전 관리 + Attribution 메모리 변경 이력·diff·에이전트별 작성자 기록 → 엔터프라이즈 감사(audit) 지원 프로덕션 운영에서 필수 가시성
메모리 → 조직 지식으로 확장 공유 메모리 + 드리밍 반복 → 전체 에이전트의 성능 하한선(floor)을 지속 상승 장기 에이전트 시대의 핵심 인프라

내가 모를 만한 것 / 처음 보는 것

  • Claude Managed Agents: Anthropic이 제공하는 에이전트 실행 관리 플랫폼 — 인프라 하드파트를 대신 처리
  • Dreaming: Memory를 전역 최적화하는 비동기 배치 프로세스. Research Preview 상태 (2026-05 기준). API로 ad hoc·야간·시간별·세션 종료 트리거 모두 지원
  • Optimistic Concurrency Control: 잠금(lock) 없이 쓰기 후 충돌 감지·해결하는 방식. 다중 에이전트 동시 쓰기 보호에 사용
  • Skills: 2025년 출시. 모델에 새 능력(capability)을 유연하게 볼트온(bolt-on)하는 추상화. Memory의 설계 철학적 선례
  • MCP (Model Context Protocol): 2025년 출시. 모델이 외부 도구·데이터에 원칙적으로 접근하는 프로토콜. 이 강연의 타임라인 시작점
  • 드리밍 자체가 Managed Agents 위에서 동작: 드리밍이 서브에이전트를 병렬로 띄워 세션 트랜스크립트를 분석 — 메타 재귀 구조
  • read-only / read-write scope 계층: 조직 전체 읽기 전용(org-wide) + 태스크별 읽기-쓰기. 용어노트: RBAC
  • Meter 연구 (2025): 에이전트가 완료할 수 있는 태스크 길이가 7개월마다 2배씩 증가한다는 연구

1. 타임라인 — 에이전트가 더 많이, 더 오래

  • MCP (2025): 모델이 외부 도구·데이터에 접근하는 원칙적 방법론 출시
  • Skills: 모델에 새 능력을 범용적으로 볼트온하는 추상화. 유연하고 단순한 포맷
  • Claude Managed Agents: 에이전트를 안정적으로 실행하는 플랫폼 — 어려운 부분을 대신 처리
  • Memory + Dreaming: 에이전트가 시간이 지나며 학습하고 개선되는 기반
  • Meter 연구: 에이전트가 처리 가능한 태스크 길이 7개월마다 2배 증가. 하지만 장기 컨텍스트 관리는 여전히 미완성 과제 → Memory로 해결

2. 메모리가 필요한 이유

메모리 없는 에이전트는 매 태스크를 동일한 출발점에서 시작한다. 성능이 개선되지 않는다.

Memory가 있으면: - 태스크 → 태스크: 이전 실수에서 학습, 공통 전략 누적 - 환경 → 환경: 다른 코드베이스·파일 시스템에서의 학습 이전 - 에이전트 → 에이전트: 에이전트 군(swarm)이 공유 조직 이해를 구축하고 유지

목표: 태스크 1에서 2, 2에서 3으로 갈수록 성능이 올라가는 학습 곡선

3. 파일 시스템 기반 메모리 설계

핵심 원칙: Claude의 기존 강점을 그대로 활용

  • Claude는 가상 환경·파일 시스템 탐색에 뛰어남
  • bash, grep으로 파일 읽기·수정·정리를 이미 잘 함
  • Opus 4.7: 미래 자신을 위해 어떤 컨텍스트를 저장해야 할지, 어떻게 구조화·표현할지 판단하는 능력이 최고 수준
  • 설계 철학: "Let it cook" — Claude가 알아서 하게 놔둬라

이 접근은 클로드MD(CLAUDE.md) for Claude Code, SDK의 전용 메모리 도구 등 하네스(harness) 중심 이전 방식에서 파일 중심으로의 전환

4. 멀티에이전트 메모리 요구사항

단일 에이전트 → 멀티에이전트 확장 시 새 요구사항 발생:

권한 범위 (Scope) - 조직 전체 읽기 전용(read-only): 잘 바뀌지 않는 정책·지식. 모든 에이전트 접근 가능 - 태스크별 읽기-쓰기(read-write): 에이전트가 자유롭게 읽고 씀. 더 세분화된 범위

쓰기 충돌 방지 - Optimistic Concurrency Control: 에이전트들이 서로의 쓰기를 덮어쓰지 않도록 보장

엔터프라이즈 제어 - 버전 관리: 메모리 변경 이력의 완전한 감사 추적(audit trail) - diff: 버전 간 비교 지원 - Attribution: 어떤 에이전트가 어떤 부분을 썼는지 기록 - Standalone API: CRUD + 엔터프라이즈 전용 오퍼레이션. 어떤 환경에서도 메모리 외부 관리 가능

5. Dreaming — 전역 메모리 최적화

왜 Dreaming이 필요한가?

에이전트가 작업 중 실시간으로 메모리를 업데이트하는 것은 로컬 최적이지만 글로벌 최적은 아님: - 에이전트들이 동일한 실수를 반복하며 각자 독립적으로 학습 - 비효율 패턴이 공유되지 않음 - 중복·단편화 발생

Dreaming의 동작 방식

  • 에이전트 루프 외부에서 실행되는 배치 프로세스
  • 세션 트랜스크립트 분석 → 기존 메모리 상태 검사 → 최적화 제안
  • 출력: 에이전트가 채택할 수 있는 검증된, 더 잘 정리된 메모리 스냅샷
  • 트리거: ad hoc / 야간(nightly) / 시간별(hourly) / 세션 종료 이벤트 — 모두 API 제어

Out-of-Band 설계의 이점

  1. 멀티에이전트 패턴 감지: 단일 에이전트가 격리된 채로는 발견하기 어려운 크로스세션·크로스에이전트 패턴을 포착
  2. 명확한 목표 분리: 에이전트가 태스크 목표와 메모리 품질 개선 사이에서 트레이드오프할 필요 없음
  3. 레이턴시 0 영향: 에이전트 핫패스에서 완전 분리

성과: Harvey(법률 AI) — 법률 벤치마크 완료율 6배 증가

6. SRE 온콜 에이전트 데모

시스템 구성 - 인입 알람·페이지를 보고 자동으로 에이전트를 생성해 트리아지(triage)·수정 - 메모리 스토어 2종: - 조직 전체 읽기 전용: SLO 정책, 런북(runbook), 온콜 매핑 - 태스크별 읽기-쓰기: 현재 태스크에 특화된 정보

크로스세션 메모리 동작 - 에이전트 A가 알람 원인 파악 → 수정 패치 적용 중 → 메모리에 "수정 인플라이트(in-flight)" 기록 - 유사 알람 발생 시 에이전트 B가 공유 메모리 읽음 → "수정 이미 진행 중" 파악 → 이중 대응 방지

드리밍 데모 (Cloud Console) - 팀 SRE 메모리 스토어 선택 → 최근 7일 세션 5개 배치 드리밍 실행 - 드리밍 자체가 Managed Agents 위에서 서브에이전트를 병렬로 띄워 트랜스크립트 병렬 분석 - 결과: CPU 스파이크 후 60초 알람 발생 패턴이 반복됨을 감지 → 재시도(retry) 동작 이슈 추정 → 메모리에 자동 기록 - 트리아지 로그도 단순 이벤트 나열이 아닌 더 총체적인 방식으로 갱신

7. 종합 비전

공유 메모리가 모든 에이전트의 성능 하한선(floor)을 올리고, 드리밍이 그것을 더 높인다.

  • Memory: 에이전트가 태스크 간 학습하고 기억
  • Dreaming: 전역적으로 메모리를 검증·정리·심화
  • 드리밍 = 추론 모델의 테스트타임 컴퓨팅 유추: 선불 작업 투자 → 모든 하위 에이전트 성능에 배당(dividend)

장기 비전: 에이전트가 며칠씩 실행되며 세계관을 지속적으로 구축·개선하는 시대 → 메모리 시스템이 그 핵심 인프라

첫째, 모델 컨텍스트 프로토콜(MCP). 2025년에 출시된 것이 아직도 믿기지 않을 정도입니다. 이것이 모델에게 외부 도구와 데이터에 원칙적으로 접근하는 방법을 제공했습니다.

그해 말에 Skills를 출시했습니다. 특정 태스크를 완료하기 위한 새 능력을 모델에 볼트온(bolt-on)하는 범용 추상화입니다.

지난달에는 Claude Managed Agents를 출시했습니다. 에이전트를 안정적으로 실행하는 플랫폼으로, 어려운 부분들을 대신 처리합니다.

핵심 흐름은 에이전트가 더 많은 것을 할 수 있고, 더 긴 시간 지평선에서 운영될 수 있다는 것입니다. 2025년 Meter [?Meter] 연구에 따르면 에이전트가 완료할 수 있는 태스크 길이가 7개월마다 2배씩 증가한다고 합니다. 하지만 장기 태스크에서의 컨텍스트 관리는 여전히 진행 중인 과제입니다. 그래서 메모리가 필요합니다.

메모리가 필요한 이유

메모리는 에이전트가 학습하게 해줍니다. 이전 태스크의 학습을 다음 태스크로 이어가게 합니다.

단순하게 보면, 태스크 1, 2, 3이 있을 때 목표는 태스크가 진행될수록 성능이 향상되는 것입니다. 메모리 없는 기본 케이스에서는 모든 에이전트가 같은 출발점에서 시작하기 때문에 각 태스크의 성능이 비슷합니다.

최적의 케이스에서는 태스크 1→2→3으로 성능이 향상됩니다. 태스크 간 학습뿐 아니라 환경 간, 에이전트 간 학습도 포함됩니다.

메모리로 에이전트는 공통 전략과 이전 실수에서 학습할 수 있습니다. 접근 가능한 도구·코드베이스·파일에서도 학습하고, 다른 에이전트와 학습을 주고받을 수 있습니다. 에이전트 군(swarm)이 자신이 일하는 조직에 대한 공유 이해를 기여하고 유지하는 모습을 상상해보세요. 이것이 꿈입니다.

Memory for Claude Managed Agents 출시

이것은 이 비전을 향한 중요한 발걸음입니다. 개발자들에게 기본적으로 지능을 극대화하도록 설계된 프런티어 메모리 시스템을 제공합니다. 멀티에이전트 시스템을 지원하고, 엔터프라이즈 제어와 관찰 가능성도 갖추고 있습니다.

파트너사 결과: - Rakuten: 프로덕션 에이전트에서 퍼스트패스 오류 97% 감소 - WiseDocs: 문서 검증 파이프라인에서 크로스세션 메모리로 공통 이슈 감소

공통된 피드백은 메모리 프리미티브(primitive)가 팀이 인프라 대신 제품에 집중하게 해준다는 것입니다.

메모리는 새로운 개념인가?

어느 정도는 그렇지 않습니다. 에이전트를 위한 접근 방식이 크게 진화했습니다. 이전에는 하네스(harness) 역량에 집중했습니다. Claude Code의 CLAUDE.md나 SDK의 전용 메모리 도구가 그 예입니다.

하지만 모델이 향상되면서 보이는 패턴은, Skills 때와 마찬가지로, Claude의 방식을 방해하지 않는 것입니다. Skills는 매우 기본적이지만 유연한 포맷이었습니다. 메모리도 같은 방향으로 파일을 활용합니다.

파일 시스템 기반 메모리 설계

현재 모델로 우리가 아는 것들: - 모델과 Claude는 가상 환경·파일 시스템 탐색에 뛰어납니다 - Claude는 bash와 grep 같은 친숙한 도구로 파일 읽기·업데이트·정리를 매우 잘합니다 - Opus 4.7 (지난달 출시)은 파일 기반 메모리에서 최고 수준의 모델입니다. 미래 자신을 위해 어떤 컨텍스트를 저장해야 할지, 어떻게 구조화하고 표현할지 판단하는 능력이 점점 높아지고 있습니다

핵심 원칙: Claude가 이미 강점을 가진 능력을 활용하도록 길을 비켜주는 것. 흔히 말하듯, "let it cook"입니다.

멀티에이전트 요구사항

단일 에이전트 컨텍스트에서의 메모리 능력을 다뤘지만, 같은 환경에서 동시에 운영되는 여러 에이전트에서도 작동해야 합니다.

새로운 요구사항: - 여러 세션이 동시에 동일한 메모리 스토어를 공유 - 권한 범위: 읽기 전용(read-only)과 읽기-쓰기(read-write) 스코프 제공 - 예: 조직 전체 읽기 전용 메모리 (드물게 업데이트, 모든 에이전트 접근 가능) + 에이전트가 자유롭게 읽고 쓰는 세분화된 메모리 스토어 - 이 계층 구조가 메모리 시스템이 확장되게 합니다

쓰기 충돌 방지: 에이전트가 서로의 쓰기를 덮어쓰지 않도록 Optimistic Concurrency Control(낙관적 동시성 제어) 모델을 사용합니다.

엔터프라이즈급 제어: - 버전 관리: 에이전트가 변경을 만들 때 감사 추적(audit trail) 생성. 메모리가 시간에 따라 어떻게 진화하는지 확인 가능. 버전 간 diff도 지원 - Attribution: 어떤 에이전트가 메모리의 어떤 부분을 작성했는지 확인 - Standalone API: 어디서든 메모리를 관리할 수 있게 해줌. 표준 CRUD 오퍼레이션 + 엔터프라이즈 중심 오퍼레이션 제공

메모리 아키텍처 3요소: 1. 스토리지 레이어: 데이터가 어떻게 관리되고 변경이 어떻게 추적되는지 2. 메모리 구조: Claude가 최대한 활용할 수 있는 포맷으로 최적화 3. Claude 주도 처리: 메모리 업데이트를 위한 처리

드리밍(Dreaming)

에이전트가 작업 중 메모리를 쓰는 것은 마치 "무언가를 하면서 노트 필기"와 같습니다. 하지만 더 복잡한 멀티에이전트 사용 사례로 확장하면서 세션 간 한계를 발견했습니다: - 에이전트들이 같은 실수를 반복하며 각자 독립적으로 학습 - 같은 비효율 패턴을 보임 - 메모리가 로컬 최적으로 업데이트되지만 글로벌 최적은 아님 - 경우에 따라 중복·단편화 발생

이 문제를 깊이 생각한 결과, 지난 몇 달간 처리 레이어에 피드백 루프를 구축했습니다. 이것이 드리밍입니다.

드리밍은 현재 Research Preview로 제공됩니다. Managed Agents와 함께 사용할 수 있습니다.

드리밍은: - 에이전트와 세션 전체에서 패턴과 실수를 찾음 - 메모리를 자동으로 정리하고 큐레이션함 - Harvey: 드리밍으로 법률 벤치마크 완료율 6배 증가

드리밍 동작 방식: - 배치 프로세스. 세션 외부에서 실행. 완전히 분리됨 - 에이전트가 메모리를 쓰고 → 드리밍이 정제 → 반복 - 트리거: ad hoc, 야간, 시간별, 세션 종료 이벤트 등 — 모두 API로 제어 - 각 드리밍 실행은 세션 트랜스크립트를 분석, 기존 메모리 상태 검사, 비효율/실수/개선 필요 시나리오에서 최적화 제안 - 출력: 에이전트가 채택할 수 있는 검증되고 더 잘 정리된 메모리 스냅샷 - 드리밍은 지속적 자기 학습을 가능하게 합니다. 루프를 닫습니다.

Out-of-Band의 중요성: 1. 멀티에이전트 시스템에서 유용 — 격리된 단일 에이전트가 발견하기 어려운 크로스세션·크로스에이전트 패턴 감지 2. 명확한 목표 설정 — 에이전트가 메모리 품질 개선과 태스크 목표 완수 사이에서 트레이드오프할 필요 없음 3. 에이전트에 레이턴시 0 추가 — 핫패스에서 완전히 제거됨

종합: - 에이전트·환경 전체에서 공유 가능한 강력한 메모리 레이어 - 드리밍: 에이전트 전체에서 메모리를 전역 최적화·조정 - 공유 메모리가 모든 에이전트의 하한선을 올리고, 드리밍이 더 올린다

드리밍을 생각하는 한 방법: 추론 모델이나 테스트타임 컴퓨팅처럼, 모델이 토큰을 투자해 문제를 탐색하면 평균적으로 더 좋은 결과가 나오는 것처럼, 드리밍으로 에이전트들은 메모리를 큐레이션하고 높은 품질의 메모리를 만드는 데 선투자합니다. 이것이 모든 하위 에이전트 성능에 배당(dividend)으로 돌아옵니다.

데모: SRE 온콜 에이전트 플랫폼

메모리와 드리밍을 함께 사용하는 데모입니다.

시스템은 인입 알람·페이지를 보고, 일부에 대해 에이전트를 띄워 트리아지와 문제 수정을 결정합니다.

메모리 스토어 2종: - 조직 전체 읽기 전용: SLO 정책, 런북, 온콜 매핑. 자주 변경되지 않지만 모든 에이전트에게 중요한 정보 - 읽기-쓰기 메모리 스토어: 현재 태스크에 특화됨

흥미로운 예시: 에이전트가 알람의 루트 원인을 조사·발견하고 수정을 올림. 메모리에 수정이 인플라이트(in-flight) 상태라고 기록. 이 공유 메모리를 이후 세션이 읽음. 유사한 이슈 발생 시 하위 세션이 수정이 이미 진행 중임을 알고 그 정보를 기반으로 행동할 수 있습니다.

이것이 크로스세션 메모리의 작동 모습입니다. 예전에 저도 SRE였는데, 모든 에이전트 간 조율에 정말 도움이 됩니다.

엔터프라이즈 운영에서 감사 로그와 이력이 중요합니다. 메모리로 전체 버전 이력 확인, 버전 간 전환, 특정 세션에 쓰기 Attribution이 가능합니다. Optimistic Concurrency 모델로 에이전트들이 서로의 쓰기를 덮어쓰지 않게 합니다.

Cloud Console 데모: - 애플리케이션에서 사용한 메모리 스토어 목록 확인 - 팀 SRE 메모리 스토어로 이동해 파일 확인 - Dreams 탭으로 이동 → 드림 시작 - 팀 SRE 메모리 스토어 선택 → 최근 7일 세션 5개 배치 선택 → 드리밍 시작 - 진행 상황 확인 가능. 5개 입력 세션 → 출력 메모리 스토어 컴파일 중 - 드리밍 세션을 열 수 있음. 드리밍 자체가 Claude Managed Agents로 구축됨 — Managed Agents의 Managed Agents 위에서 구현된 기능. 서브에이전트를 병렬로 띄워 트랜스크립트 분석 - 완료된 드림 세션 확인 → 메모리 스토어 업데이트 diff 확인 - 이 예시에서: 세션·에이전트 전체에서 CPU 스파이크 후 60초에 알람이 발생하는 공통 패턴 발견. 재시도(retry) 동작에 이슈가 있을 수 있다고 판단해 메모리에 기록. 다음 에이전트가 이 패턴을 보면 이 정보를 바탕으로 행동 가능. - 트리아지 로그도 단순한 이벤트 나열이 아닌 더 총체적인 방식으로 업데이트됨

마무리

이 데모로 메모리와 드리밍을 사용해 에이전트가 자기 개선하는 프로덕션 에이전트를 어떻게 구축할 수 있는지 보았습니다.

올해는 에이전트가 더 긴 시간 규모—예를 들어 며칠—에서 실행되는 것을 보게 될 것입니다. 주변 세계에 대한 이해를 지속적으로 구축하고 개선하는 것이 그 능력을 여는 데 매우 중요하고, 메모리 시스템이 그것을 가능하게 하는 핵심 요소가 될 것이라고 생각합니다.
