무슨 이야기인가

AI 에이전트를 한두 개가 아니라 여러 개 실행하면 문제는 “어떤 모델이 더 좋은가”에서 끝나지 않는다. 각 에이전트가 어느 컴퓨터에서 실행 중인지, 지금 작업 중인지 끝났는지, 작업 창을 닫아도 계속 움직이는지를 관리해야 한다.

화자 Mehul Mohan은 Herdr를 이런 관리 문제를 풀기 위한 작업 환경으로 소개한다. Herdr는 여러 터미널을 한 화면에 모으는 데 그치지 않고, 로컬 Mac이나 원격 머신에 연결해 에이전트를 실행하고 그 상태를 보여주는 앱이다. 화면은 그래픽 앱처럼 구성되지만, 각 작업에는 명령줄 환경과 터미널을 그대로 사용할 수 있다.

화자가 강조한 핵심은 보이는 앱과 실제 작업이 실행되는 장소를 분리하는 것이다. Herdr 창은 작업을 지시하고 상태를 보는 조종판이고, 실제 에이전트는 로컬 컴퓨터나 원격 작업용 컴퓨터에서 실행된다.

읽는 법: 위에서 아래로 읽는다. 가운데의 두 상자는 우열 관계가 아니라 작업 조건에 따른 선택지다. 이 그림은 성능 측정 결과가 아니라 영상에서 설명한 개념 관계를 정리한 것이다.

왜 명령줄과 그래픽 화면을 함께 쓰는가

화자는 명령줄 도구(CLI)가 세부 실행 옵션을 직접 조절하기 쉽다고 말한다. 예로 Claude Code의 샌드박스 및 권한 우회 설정을 들었다. 그래픽 앱에서는 해당 기능을 지원하는지 먼저 확인해야 하고, 설정이 있더라도 메뉴 안에 숨겨져 있을 수 있다. 반면 명령줄에서는 실행할 때 옵션이나 환경 설정을 직접 전달할 수 있다는 주장이다.

다만 화자의 주장은 “모든 그래픽 앱보다 명령줄이 낫다”가 아니다. 그는 명령줄의 유연성과 그래픽 앱의 상태 표시를 함께 얻는 방식을 선호한다. Herdr는 최소한의 그래픽 화면 위에 전체 터미널, SSH 연결, 원격 머신, 알림과 에이전트 상태 표시를 결합한다.

Herdr가 이름을 알고 있는 에이전트 도구는 작업 중, 유휴 상태, 완료 같은 상태를 더 잘 파악한다고 화자는 설명한다. 다른 명령줄 에이전트도 실행할 수 있지만, 전용 연동이 없는 경우 같은 수준의 사용 경험은 보장되지 않는다고 덧붙인다.

권한을 건너뛰는 설정에 대해서는 주의가 필요하다. 전사에는 새롭고 더 강한 권한 모드가 언급되지만 정확한 새 옵션 이름은 제시되지 않는다. 또한 권한 확인이 줄어든 환경의 안전성을 이 영상이 검증한 것은 아니다.

앱을 닫아도 작업이 계속되는 이유

Herdr 앱 창 자체가 작업을 수행하는 유일한 장소는 아니다. 화자는 원격 worker에서 Claude에게 1부터 100까지 천천히 세게 한 뒤 Herdr 앱을 종료했다. 앱을 다시 실행했을 때 Claude는 작업을 마친 상태였다. 화자의 설명에 따르면 실제 프로세스가 원격 worker에서 실행되었기 때문에 조종 화면을 닫거나 네트워크 연결을 잃어도 원격 작업은 계속될 수 있었다.

로컬 Mac에서도 Herdr가 별도 프로세스로 터미널과 에이전트 세션을 유지하므로 창을 닫았다 다시 열 수 있다고 설명한다. 그러나 로컬 컴퓨터가 잠들거나 실행 조건을 잃으면 작업도 멈출 수 있다. 앱이 사라져도 실행 머신이 살아 있으면 계속된다는 뜻이지, 컴퓨터의 전원이나 절전 상태와 무관하게 항상 실행된다는 뜻은 아니다.

읽는 법: 위에서 아래로 작업의 시간 순서를 읽고, 마지막의 붉은 경계 상자를 함께 확인한다. 화살표는 인과와 순서를 나타내며, 보장된 성공률 같은 수치를 뜻하지 않는다.

어떤 작업을 로컬에 두고 어떤 작업을 원격에 둘까

화자는 영상 편집을 로컬에 두는 사례를 제시한다. 그가 다루는 파일은 각각 8GB 또는 10GB인 경우가 있어 업로드와 다운로드에 몇 분이 걸린다고 한다. 에이전트가 영상을 수정한 뒤에는 사람이 결과를 직접 재생해 확인해야 한다. 화자는 에이전트가 모든 프레임을 보지 못해 실수할 수 있으므로 이 피드백 과정이 로컬에서 더 빠르다고 설명한다.

반면 일반적인 소프트웨어 기능 개발과 버그 수정은 VM에 둘 수 있다고 말한다. 화자는 하나의 가상 머신에 여러 프로젝트를 두고 필요한 에이전트를 배정하는 방식을 사용한다고 설명한다.

따라서 판단 기준은 단순히 “로컬이 빠른가, 클라우드가 좋은가”가 아니다.

  • 파일이 커서 전송 시간이 중요한가?
  • 민감한 작업이라 외부 머신으로 옮기기 어려운가?
  • 결과를 사람이 자주 보고 즉시 수정 요청해야 하는가?
  • 사람이 자리를 비운 동안에도 실행이 이어져야 하는가?

앞의 조건이 강하면 로컬이 유리할 수 있고, 마지막 조건이 중요하면 계속 켜져 있는 원격 머신이 유리할 수 있다. 이는 화자의 사례에서 얻은 판단 구조이지, 모든 작업에 대한 성능 검증 결과는 아니다.

Herdr와 cmux는 무엇이 달랐나

화자는 cmux도 직접 사용해 봤지만 Herdr보다 마찰이 컸다고 평가한다. 특히 cmux에서 SSH로 접속하고 화면을 나눈 뒤 세션을 복구하는 과정이 기대대로 작동하지 않았다고 말한다. tmux ssh tmux 방식은 실험적이고 자주 깨졌으며, 인터넷 연결을 잃으면 터미널 에뮬레이터 자체가 깨진 경험도 있었다고 주장한다.

화면 구성에서도 Herdr는 기본 상태가 단순하고 보기 좋아 곧바로 시작할 수 있었던 반면, cmux는 에이전트에게 UI 수정을 맡겨도 자신이 원하는 만족감을 얻지 못했다고 말한다. 이는 동일 조건의 공식 비교 시험이 아니라 화자 개인의 사용 경험이다.

아래 표는 가로로 길 수 있다. 작은 화면에서는 표 안을 좌우로 이동해 읽는다.

읽는 법: 세로축은 원격 연결, 상태 관리, 화면, 근거 범위이고 가로축은 두 도구다. 각 칸은 화자가 영상에서 보고한 경험만 담으며 제품 전체의 객관적 우열을 뜻하지 않는다.

전체 통찰과 경계

Herdr의 본질은 “터미널을 예쁘게 꾸미는 앱”보다 여러 실행 장소와 에이전트 상태를 한 화면에서 다루는 관리 계층에 가깝다. 중요한 판단은 작업 창을 많이 여는 것이 아니라, 각 작업을 어디에서 실행하고 어떤 조건에서 사람이 개입할지 정하는 것이다.

화자는 Herdr의 분할 화면, 알림, 상태 표시, 사용자 정의 레이아웃과 API 가능성을 높게 평가한다. Mission Control, Slack, Google Meet과 비슷한 형태의 화면도 언급하지만 실제로 유용한지는 확정하지 않는다. 모바일 앱도 출시된 것으로 말하지 않았으며, 현재는 Claude Code의 Remote Control을 이용한다고 설명한다.

[경계] 화자는 Herdr를 몇 시간 사용한 초기 단계에서 “더 필요한 것이 없을 것 같다”고 평가했다. 따라서 장기 안정성이나 다양한 작업에서의 생산성은 검증되지 않았다. META의 provenance.creator는 비어 있지만 설명과 전사 도입부는 화자를 Mehul Mohan으로 지목한다. provenance.affiliation에는 Herdr가 적혀 있으나, 제공된 자료는 그의 공식 소속 관계를 확인하지 않는다. 출처 메모도 원본 영상 연결을 추정이라고 표시한다.

여기까지만 이해하면 충분

  • Herdr는 로컬·원격 머신에서 실행되는 여러 에이전트의 터미널, 상태와 알림을 한 화면에 모으는 관리 도구다.
  • 앱을 닫아도 작업이 이어지는 이유는 실제 프로세스가 worker에 남기 때문이며, 로컬 컴퓨터가 잠들면 로컬 작업은 멈출 수 있다.
  • 큰 데이터와 잦은 사람 확인이 필요한 작업은 로컬에, 독립적으로 오래 실행할 수 있는 작업은 원격 VM에 두는 것이 화자의 구분 기준이다.
  • cmux보다 Herdr가 편하다는 평가는 화자의 개인 경험이며, Herdr 역시 몇 시간 사용한 초기 평가다.

비유와 깨지는 지점

공장과 원격 관제실

Herdr 화면은 여러 공장의 상태를 보는 관제실이고, 로컬 컴퓨터와 원격 VM은 실제 기계가 움직이는 공장이다. 관제 화면을 닫아도 공장의 전원과 기계가 살아 있으면 생산은 계속될 수 있다.

비유가 깨지는 지점: 에이전트 작업은 물리적 생산처럼 결과가 눈에 바로 보이지 않으며, 지원되는 CLI인지에 따라 Herdr가 상태를 이해하는 정도도 달라진다. 관제실이 있다고 해서 작업의 정확성이나 안전성이 보장되는 것도 아니다.

데이터의 크기와 민감도, 업로드·다운로드 부담, 사람이 결과를 확인해야 하는 빈도, 장시간 무인 실행 필요성을 확인한다. 큰 파일을 자주 열어 사람이 검토해야 하면 로컬이 유리할 수 있고, 데이터 이동 부담이 작고 오래 독립 실행할 수 있으면 원격 VM을 시험할 수 있다. 실제 선택 전에는 보안 조건과 세션 복구 여부를 별도로 검증해야 한다.

이번 글의 통찰

1. 지속성은 화면이 아니라 실행 장소의 성질이다

  • [원문] 화자는 원격 worker에서 실행한 Claude가 Herdr 종료 후에도 작업을 마쳤다고 시연했다. 로컬 Mac이 잠들면 로컬 작업은 멈출 수 있다고 구분했다.
  • [해석] 장시간 에이전트 작업을 설계할 때는 어떤 UI를 쓰는가보다 프로세스가 어느 머신에서 어떤 생명주기로 실행되는지를 먼저 확인해야 한다.
  • [경계] 영상은 짧은 세기 작업을 시연했을 뿐 장시간 작업, 머신 장애, 앱 업데이트 뒤 복구까지 검증하지 않았다.

2. 실행 장소는 데이터와 피드백 비용으로 나눈다

  • [원문] 화자는 8GB 또는 10GB 크기의 영상 파일과 사람이 영상을 다시 봐야 하는 피드백 때문에 영상 편집을 로컬에 둔다고 말했다. 일반 기능 개발과 버그 수정은 VM에 둘 수 있다고 했다.
  • [해석] 로컬과 원격의 선택은 유행하는 도구가 아니라 데이터 이동량, 민감도, 사람의 확인 빈도, 무인 실행 필요성으로 판단할 수 있다.
  • [경계] 파일 크기와 소요 시간은 화자의 작업 사례다. 다른 네트워크나 작업에서도 같은 비용이 나온다는 자료는 없다.

3. 좋은 초기 경험과 검증된 생산성은 다르다

  • [원문] 화자는 Herdr를 몇 시간 실제 사용한 뒤 cmux보다 마찰이 적고 더 생산적이라고 느꼈다고 말했다.
  • [해석] 기본 설정만으로 빠르게 시작되는 경험은 중요한 선택 기준이지만, 장기 운영 판단에는 복구 실패와 예외 상황도 함께 측정해야 한다.
  • [경계] cmux 비교는 화자 개인의 경험이며 독립적인 동조건 시험이 아니다. 새 권한 모드의 정확한 이름도 전사에서 확인되지 않는다. META의 원작자 필드는 비어 있으나 전사와 설명은 Mehul Mohan을 화자로 지목한다. Herdr 소속은 provenance 후보 값일 뿐 공식 관계가 확인되지 않았다.

# 섹션 요지
1 CLI를 쓰는 이유 실행 옵션과 권한 모드를 직접 조절하기 쉽다는 주장
2 Herdr 앱의 구성 GUI, 터미널, SSH, 머신, 상태와 알림을 결합
3 작업 지속 조건 앱 종료 뒤에도 worker 프로세스가 남지만 로컬 절전은 한계
4 작업 배치 큰 영상 작업은 로컬, 일반 개발 작업은 VM에 배치
5 확장 기능 레이아웃, 모바일 원격 제어, API와 하위 에이전트 언급
6 cmux 비교 SSH 세션 복구와 UI 구성에서 더 큰 마찰을 경험했다는 평가

1. CLI의 권한과 유연성

화자는 Codex 및 Claude 데스크톱 앱 같은 GUI가 있는데도 CLI 에이전트를 쓰는 이유를 설명한다. CLI에서는 샌드박스와 권한 관련 옵션을 실행 시점에 직접 전달할 수 있다고 말한다.

Claude Code의 --dangerously-skip-permissions와 샌드박스 설정을 예로 들며, 기존 방식에서도 rm -rf 같은 명령이 차단되는 경우가 있었다고 주장한다. 더 강한 권한 모드가 새로 생겼다고 말하지만 전사에는 구별되는 정확한 새 옵션 이름이 없다.

그는 이를 근거로 데스크톱 앱이 나쁘다고 단정하지 않는다. 앱이 기능을 지원하는지, 설정이 어디에 있는지에 따라 접근성이 달라지며 CLI와 네이티브 앱이 수정 가능성과 유연성을 더 많이 줄 수 있다는 의견이다.

2. Herdr의 화면과 머신 관리

Herdr의 기본 화면은 사이드바와 터미널로 구성된다. 터미널만 보이는 화면, Herdr 98 테마, Graphite 테마도 언급한다. 화자는 Herdr의 기본 설정과 Graphite 테마를 선호하며 Herdr 98은 일상적인 작업에 지나치게 화려하다고 평가한다.

머신을 추가할 때 사용자와 호스트 정보를 직접 주거나 SSH 설정에서 불러올 수 있다고 설명한다. 로컬 AI 에이전트에게 설정을 맡길 수도 있다고 말한다. 화자는 원격 머신 하나를 worker one으로 이름 붙인 사례를 보여준다.

Herdr는 여러 패널을 나누고 배치할 수 있으며, 지원하는 에이전트의 작업 중·완료·유휴 상태를 구분하고 알림을 보낸다고 한다. Codex, DeepSeek, OpenCode는 실행 가능한 예로 언급된다. 전용 연동이 없는 CLI도 실행할 수 있지만 같은 수준의 상태 인식은 기대하기 어렵다고 설명한다.

3. 앱 종료와 작업 지속

화자는 원격 worker에서 Claude에게 1부터 100까지 천천히 세라고 지시한 뒤 Herdr를 종료했다. 앱을 다시 실행했을 때 작업이 끝나 있었으며, 실제 작업이 worker에서 실행됐기 때문이라고 설명한다.

로컬 Mac에서도 Herdr가 별도 프로세스로 터미널과 에이전트를 유지하기 때문에 창을 닫을 수 있다고 말한다. 그러나 Mac이 잠들면 로컬 작업이 멈출 수 있다. 원격 worker의 연결 상실과 로컬 컴퓨터의 절전은 같은 조건이 아니다.

4. 로컬과 VM의 역할

화자는 영상 편집 프로젝트를 로컬 Mac에서 실행한다. 편집 파일 하나가 8GB 또는 10GB일 수 있어 업로드와 다운로드에 몇 분이 걸리며, 수정 결과를 사람이 다시 시청해야 한다고 설명한다.

AI가 모든 영상 프레임을 보는 것은 아니어서 실수가 발생할 수 있다는 것이 화자의 주장이다. 이 때문에 영상 편집은 로컬에서 처리하는 편이 피드백 순환에 유리하다고 판단한다.

소프트웨어 기능 개발과 버그 수정은 하나의 VM에 두고 필요한 에이전트를 배정한다고 설명한다. 민감한 작업은 서버로 옮기지 않고 자기 컴퓨터에 남길 수 있다고도 말한다.

5. 모바일 제어, 레이아웃과 API

화자는 Claude Code 세션을 휴대전화에서 제어할 때 Anthropic의 Remote Control을 사용한다. 자신의 경험에서는 버그를 보지 못했고 잘 작동했다고 평가한다. Herdr 전용 모바일 앱은 출시된 것으로 보지 못했으며, 현재는 필요하지 않다고 말한다.

Herdr에는 Mission Control, Slack 미리보기, Google Meet 통화 화면과 비슷한 레이아웃을 만들 수 있는 기능이 언급된다. 화자는 이 화면들이 실제로 유용할지는 확정하지 않는다.

Herdr가 API를 통해 하위 에이전트를 실행하고 방향을 조정하며 주 에이전트에 결과를 보고하게 할 수 있다고 말한다. Claude Code에는 자체 하위 에이전트 기능이 있어 꼭 필요하지 않을 수 있다고 덧붙인다. 혼자서 100개의 에이전트를 직접 운영할 일은 없을 것이라고도 말한다.

6. cmux와의 비교

화자는 cmux에서 cmux ssh와 SSH 명령을 사용한 뒤 Command-Shift-B로 터미널을 나누는 사례를 설명한다. 이 상태에서 tmux를 종료하면 세션을 되찾을 수 없었으며 실제로 tmux 안에서 실행된 것이 아니었다고 말한다.

대안으로 언급한 tmux ssh tmux 방식은 실험적이고 마찰이 크며 자주 깨졌다고 주장한다. 인터넷 연결을 잃었을 때 터미널 에뮬레이터 자체가 깨진 경험도 보고한다.

UI에서는 터미널 탭의 설명을 없애는 등 cmux를 수정하려 했지만 자신이 원하는 만족감을 얻지 못했다고 한다. Herdr는 기본 화면이 단순하고 보기 좋아 수정에 많은 노력을 들이지 않고 시작할 수 있었다고 평가한다.

이 비교는 화자의 개인 경험이다. Herdr는 촬영 전 몇 시간 사용한 초기 단계였으며, 장기 안정성이나 동일 조건의 정량 비교는 제시되지 않았다.

우선 사람들이 제게 자주 묻습니다. “Codex 데스크톱 앱과 Claude 데스크톱 앱을 포함해서 좋은 GUI 애플리케이션이 이렇게 많은데, 왜 CLI 애플리케이션을 사용하나요? 그럼 왜요, Mehul? 왜 CLI AI 하네스(harness)를 선호하나요?”

제가 CLI 하네스만 선호하거나 그것만 사용하는 것은 아닙니다. 단지 CLI로만 가능한 일이 몇 가지 있기 때문입니다. 예를 들어 보겠습니다. Anthropic에서 Claude Code를 담당하는 누군가가 마침내 Claude Code에 더욱 위험한 --dangerously-skip-permissions 플래그가 생겼다고 게시했습니다. 이건 제가 오랫동안 요청해 온 기능이라서 정말 중요합니다.

Claude Code의 문제는 --sandbox 1과 --dangerously-skip-permissions 플래그를 함께 전달해도 rm -rf 같은 명령을 실행할 때 여러 번 차단한다는 것입니다. Anthropic이 왜 이렇게 했는지는 모르겠지만, 사실상 이 권한 건너뛰기 옵션을 약하게 만들어 놓았습니다. 이제 이 플래그를 사용하면 비슷한 방식으로 실행할 수 있습니다.

CLI에서는 이 작업을 아주 쉽게 이해할 수 있습니다. 보세요. CLI에서 실행한다면 이게 전부입니다. 샌드박스 환경 변수를 1로 설정하고, 이것도 1로 설정한 다음 Enter만 누르면 됩니다.

그러면 다시는 중단되지 않을 거라는 걸 확실히 알 수 있는 Claude Code 창 안으로 들어갑니다. 무언가를 시킨 뒤 자리를 떠나도 계속 작업합니다.

GUI에서 이 작업을 하는 것은 상당히 번거롭습니다. 왜냐하면 우선 사용 중인 GUI 하네스가 애초에 이 기능을 지원하는지에 달려 있기 때문입니다.

문제는 Claude Code가 여러 하네스 중 하나일 뿐이라는 점입니다. 다른 플래그와 다른 수준의 권한 모드를 사용하는 하네스가 있을 수 있습니다. 예를 들어 Claude Code에는 자동 모드가 있고, 권한 우회 모드도 있으며, 더욱 위험한 권한 모드로 권한을 우회하는 기능도 있습니다.

제가 말하려는 핵심은 CLI가 곧 유연성이라는 것입니다. 더 중요한 것은 네이티브 앱(native app) 역시 유연성을 제공한다는 점입니다. 이 네이티브 앱은 CLI의 Claude Code일 수도 있고, Claude 데스크톱 앱일 수도 있습니다. 하지만 Claude 데스크톱 앱에서도 이 플래그가 어디에 있는지 찾는 일은 상당히 어려울 것이라고 확신합니다.

데스크톱 앱에는 CLI보다 훨씬 더 숨겨진 기능이 많습니다. --dangerously-skip-permissions 플래그조차 설정(Settings) 안에 숨겨져 있습니다. 먼저 활성화해야 표시됩니다.

이 한 가지 기능만으로 데스크톱 앱은 나쁘고 CLI는 좋다고 말하는 것은 아닙니다. 단순한 데스크톱 앱에 비해 네이티브 앱과 CLI가 일반적으로 훨씬 더 많은 유연성과 우회해서 활용할 수 있는 가능성을 제공한다는 뜻입니다.

그런 점을 바탕으로, 이것이 새로운 herdr 앱의 모습입니다. 여기 있는 여러 부분을 사용자 지정할 수 있습니다. 다만 외관 측면에서의 커스터마이징은 실제로 매우 제한적입니다. 사이드바와 터미널이 있는 전형적인 herdr 형태를 사용하거나, 터미널만 표시하도록 해서 어느 정도 iTerm이나 일반 터미널 에뮬레이터처럼 만들 수 있습니다.

저는 이 모습은 선호하지 않습니다. 그리고 herdr 98도 있습니다. 왜 있는지는 모르겠습니다. 하지만 클래식을 좋아하는 사람들을 위한 기능인 것 같습니다. 잘 모르겠네요. 너무 날것처럼 보입니다. 향수를 불러일으키려는 의도라는 건 알겠지만, 스크린샷 같은 걸 찍고 싶다면 너무 반짝이는 느낌입니다. 매일 진지하게 작업할 때 사용할 모습은 아니라고 확신합니다.

저는 이 herdr 설정이 좋고, Graphite 테마도 마음에 듭니다. 지금은 조금 확대해 둔 상태지만, 실제로 작업할 때는 당연히 100%로 설정해 둘 수 있습니다.

다음으로 마음에 드는 점은 여러 컴퓨터를 여기서 아주 쉽게 관리할 수 있다는 것입니다. cmux에서는 이 작업이 다소 어려웠습니다. 여기서는 이 버튼을 눌러 컴퓨터를 추가하기만 하면 됩니다.

보시다시피 herdr는 호스트(host)를 지원합니다. 올바른 사용자와 호스트를 입력하거나 SSH 설정에 추가하면 바로 선택할 수 있습니다. 또는 로컬 AI 에이전트 자체에 설정을 요청하면 대신 처리해 줍니다.

이렇게 하면 여기에 worker one 같은 항목이 표시됩니다. 제가 이 이름을 worker one으로 지정했는데, 이 컴퓨터 안에서도 사용할 수 있다는 것을 볼 수 있습니다. 따라서 여기서 여러 컴퓨터를 사용할 수 있습니다. 그리고 이 모든 작업은 비동기식(asynchronous)입니다.

무슨 뜻이냐면, 여기서 프로세스를 시작한다고 해 보겠습니다. Claude를 실행하고 “1부터 100까지 아주 아주 천천히 세어 줄래?”라고 말했다고 하죠. Enter를 누른 다음 Herdr를 종료합니다. 지금 앱을 종료했습니다. 이제 앱을 다시 실행해 보겠습니다. 실행하고 나면 Claude가 기본적으로 작업을 끝낸 것을 볼 수 있지만, 백그라운드에서 작업을 계속 수행할 수 있었습니다. 앱을 종료하거나 Wi-Fi 연결이 끊기는 등의 상황에서도 말이죠. 왜냐하면 이 작업은 worker에서 실행되고 있었기 때문입니다.

마찬가지로 컴퓨터 자체에서 에이전트를 실행하고 있다고 해 보겠습니다. 예를 들어 제 동영상 편집 프로젝트 안에서 Claude를 시작했다면, 여기서도 계속 작업할 수 있습니다. 창 전체를 닫아도 됩니다. Herdr가 이 macOS에서 별도의 프로세스를 유지하면서 터미널과 에이전트를 계속 실행 상태로 유지하기 때문입니다.

다만 Mac에서는 Wi-Fi가 끊기거나 컴퓨터가 실제로 잠자기 상태에 들어가도 작업이 계속 실행된다는 보장은 없습니다. 컴퓨터가 그렇게 작동하기 때문에 작업이 중단됩니다. 하지만 바로 이 지점에서 이러한 컴퓨터들이 중요한 역할을 합니다.

이외에도 직접 요청할 수 있습니다. 예를 들어 “항목 1을 주의 깊게 살펴봐 주세요”라고 해 보겠습니다. 이렇게 하면 어떤 에이전트가 작업 중인지 명확히 구분해서 보여 줍니다. “hello”라고 보내고 탭을 전환해 보겠습니다. Video Editor가 이제 작업을 끝낸 것을 볼 수 있습니다.

이 앱은 제게 알림도 보냅니다. 헤드폰을 쓰고 있거나 음악을 듣는 중에 여러 에이전트를 관리하고 있다면, 이 방식이 작업하기에 아주 좋은 방법이라고 생각합니다.

마지막으로 당연히 여러 AI 에이전트를 여기에 설정할 수 있습니다. Codex 에이전트를 여러 개 사용하거나, DeepSeek와 OpenCode 같은 에이전트를 실행하고 있다면 바로 실행할 수 있습니다.

이 에이전트들은 소프트웨어에 직접 일급(first-class) 통합을 제공합니다. 따라서 에이전트가 유휴 상태인지, 작업을 끝냈는지, 작업 중인지 등을 인식할 수 있습니다. 물론 여기에 언급되지 않은 에이전트도 사용할 수 있습니다. 다만 그런 특정 CLI에서는 최상의 에이전트 경험을 얻지 못할 수 있습니다.

이 영상을 보면 저는 Herdr를 완전히 터미널 기반인 시스템이라고 보지는 않습니다. 최소한의 GUI를 사용하는데, 저는 이 점이 정말 마음에 듭니다. 동시에 완전한 터미널 인터페이스와 터미널 에뮬레이터, SSH 연결, 가상 머신을 제공합니다. 관리할 수 있는 worker를 추가할 수 있고, 원하는 알림도 설정할 수 있습니다.

분할 패널(split panel)을 사용하면 여러 패널을 만들고 원하는 대로 배치할 수 있는데, 꽤 대단합니다. 평소 터미널로 작업하는 방식과 비슷한 경험을 제공하면서도, 모든 에이전트를 오케스트레이션할 수 있는 소프트웨어에서 기대하는 기능을 모두 제공합니다.

이 분야가 매우 포화 상태이고 소프트웨어 선택지도 많다는 것은 알고 있습니다. 여러분에게 실제로 유용한 무언가를 찾을 수도 있습니다. 하지만 저는 이 영상을 만들기 위한 목적만으로 사용한 것이 아니라, 지난 몇 시간 동안 이 애플리케이션 Herdr를 실제로 사용해 봤습니다. 원래 이 영상을 만들 계획도 없었지만, 직접 써 보니 여러분 중 더 많은 사람이 CLI를 사용해 봐야 한다고 느꼈습니다. 여러분은 개발자이고 명령줄 사용법을 알아야 하기 때문입니다.

동시에 iTerm 같은 단순한 인터페이스나 단일 인터페이스에 자신을 제한하거나, 에이전트 관리를 위해 모든 것을 tmux로만 처리하지는 마세요. 모두 좋은 도구이고, 각각 그렇게 사용할 만한 실제 사례가 있습니다. 다만 제 생각에는 에이전트 멀티플렉서(agent multiplexer)나 에이전트 관리자(agent manager) 같은 것을 사용하면 훨씬 더 생산적으로 일할 수 있습니다.

사실 이 방식은 훨씬 더 강력합니다. Herdr가 제공하는 것 이상으로 필요한 것이 있을지는 모르겠습니다. 거의 과할 정도로 보이지만, 어떤 이유에서인지 Herdr 안에서는 매우 특이한 레이아웃도 만들 수 있습니다. Mission Control 대시보드 같은 것도 포함됩니다. Slack과 비슷한 미리보기 UI도 만들 수 있습니다. 애초에 이게 어떻게 작동하는지도 모르겠습니다.

에이전트가 통화 중이고 터미널이 함께 표시되는 Google Meet과 비슷한 통화 UI도 만들 수 있습니다. 정말 모르겠네요. 이런 UI 스레드와 기능이 여러분에게 유용한지 알려 주세요. 제게는 확실히 훨씬 더 강력해 보입니다. 이런 스레드 UI를 만들고, 메시지를 보내는 UI와 터미널을 함께 사용할 수 있다는 점은 매우 해킹하기 좋은 구조처럼 보입니다.

이게 그들이 출시한 새 버전입니다. 다시 말하지만, 일부러 이걸 연결해서 굉장히 이상한 무언가를 만들지는 않겠습니다. 지금 여러분이 보고 있는 화면에 제 워크플로가 전부 표시되고 있지 않다는 걸 사실 알고 있기 때문입니다. 하지만 이걸 사용하기 시작하면, AI 에이전트와 작업하는 데 있어 매우 생산적인 방식이 됩니다. 그리고 지금 화면에 보이는 것 이상은 필요하지 않다고 생각합니다.

여러 대의 컴퓨터를 사용하고, 서버로 옮길 수 없는 민감한 작업은 자신의 컴퓨터에서 처리하며, 에이전트를 현재 상태, 즉 지금 어디에 있는지를 기준으로 제대로 정리한다면, 여러분은 다음과 같은 방식으로 업무를 관리하게 될 겁니다.

데이터가 매우 많거나 자주 접근해야 하는 특정 작업은 자신의 컴퓨터에 두는 게 좋습니다. 제가 이렇게 말하는 이유는, 지금 제 macOS에서 로컬로 실행하는 작업 중 하나가 영상 편집이기 때문입니다. 언젠가는 클라우드로 옮길 수도 있겠지만, 이 작업을 옮길 때의 문제는 다음과 같습니다.

Claude와 AI가 편집하는 파일은 한 개에 8~10GB인 경우가 많습니다. 파일을 업로드하고 다운로드하는 것만 해도 몇 분이 걸립니다. AI가 변경 작업을 하면 저는 영상을 확인해야 합니다. Claude와 이런 AI 에이전트는 자주 실수를 하는데, 주로 볼 수 없기 때문입니다. 시각 능력(vision)이 없죠. 시각 능력이 있더라도 이미지 시각 능력일 뿐입니다. 하지만 그렇더라도 모든 프레임을 하나하나 보고 있는 게 아니기 때문에 실수를 많이 합니다. 그래서 영상은 제가 직접 봐야 합니다. 이 전체 피드백 루프에는 많은 데이터가 필요하고, 제 컴퓨터에서 직접 작업을 시키는 것보다 훨씬 오래 걸립니다. 이것이 제 시스템에서 실행되는 워크플로 중 하나입니다.

이외의 작업, 즉 소프트웨어 엔지니어링, 일반적인 기능 개발, 버그 수정 같은 작업은 모두 가상 머신(VM)에 둘 수 있습니다. 저는 다른 프로젝트를 전부 넣어두는 가상 머신 하나를 가지고 있고, 함께 작업하고 싶은 에이전트를 그곳에 배치할 수 있습니다. 예를 들어 현재 작업 중인 예정 프로젝트 하나와, 과거에 작업했던 여러 프로젝트가 있습니다. 가상 머신을 마련해 두면 이런 에이전트를 관리하는 데 도움이 됩니다.

마지막으로, 적어도 Claude Code의 경우 제가 현재 사용하는 기능은 휴대폰의 Remote Control입니다. 가상 머신에서 실행 중이라면 Anthropic의 내장 기능을 사용해 세션을 원격으로 제어할 수 있습니다. Herdr 모바일 앱 같은 것도 있다면 정말 좋을 것 같습니다. 여기서 작업 중인 컴퓨터와 모바일 애플리케이션을 특별히 연결해 주는 무언가를 출시했는지는 모르겠지만, 지금 당장은 필요하지 않다고 생각합니다. 적어도 저에게는 Anthropic의 Remote Control이 완벽하게 작동하기 때문입니다. 버그나 그 어떤 문제도 본 적이 없습니다.

정말 잘 작동합니다. Herdr 내부를 직접 살펴보셔도 됩니다. 링크는 모두 설명란에 남겨두겠습니다. 적어도 이 UI는 매우 자유롭게 수정할 수 있어 보입니다. 로컬 컴퓨터와 로컬 시스템을 두고, 그곳에서 이런 에이전트들을 모두 실행할 수도 있습니다. 매우 기대되는 부분입니다. 하지만 솔직히 말하면, 혼자서 에이전트 100개를 실행하게 되지는 않을 겁니다. 에이전트가 다른 에이전트를 직접 호출한다면 이야기가 다르겠지만요.

그런데 Herdr는 이를 위한 완전한 API도 지원합니다. Claude Code에는 서브 에이전트, 새로운 에이전트 스레드 등을 기본적으로 지원하는 기능이 있어서 아마 필요하지 않을 겁니다. 하지만 Herdr 자체를 사용해 새로운 서브 에이전트를 실행하고, 지시하고, 메인 에이전트에 보고하도록 할 수 있습니다. 다시 말해, 이것은 에이전트가 직접 사용할 수 있는 기능입니다. 여러분이 신경 쓸 필요는 없습니다.

cmux에 대해서 한 가지 말하자면, Herdr보다 사용하기가 확실히 더 번거롭습니다. cmux에 대해 이야기하겠다고 했으니, 마무리로 몇 가지만 덧붙이겠습니다. cmux에서 발견한 문제 중 하나는 SSH가 제대로 작동하지 않는다는 점입니다. SSH로 접속해서 cmux ssh 같은 작업을 한 다음 ssh root@whatever 명령을 실행할 수는 있습니다. 그리고 Command-Shift-B를 눌러 터미널을 분할하면, 여기 터미널 하나와 저기 터미널 하나가 생기고 둘 다 SSH 서버 내부에 직접 들어가게 됩니다. 문제는 tmux를 종료하면 이 상태를 되돌릴 방법이 없다는 겁니다. 사라져 버립니다. 실제로 tmux 안에서 실행되는 방식이 아니기 때문입니다.

여러분이 해야 하는 일은 tmux ssh tmux를 사용하는 것인데, 이건 실험적이고 상당히 번거롭습니다. 자주 망가집니다. 인터넷 연결이 끊기면 터미널 에뮬레이터 자체가 고장 나는 경우도 봤습니다.

두 번째로, cmux의 UI를 커스터마이즈해 보기도 했습니다. 터미널 탭에서 설명을 제거하는 것처럼 UI 일부를 수정해 달라고 에이전트에게 요청하기도 했습니다. 하지만 ‘와우’ 하는 느낌은 얻지 못했습니다. Herdr에는 뭔가 다른 점이 있습니다. 기본 설정만으로도 그냥 보기 좋습니다. 제가 많은 노력을 들일 필요가 없습니다. 단순하고 괜찮으며, 번거로운 설정 없이 바로 시작할 수 있습니다.
