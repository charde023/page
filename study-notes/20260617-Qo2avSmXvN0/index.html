한 줄 요약

스킬(Skills)은 단순 문서가 아니라 모델을 프로그래밍하는 새로운 코드이며, 소프트웨어 개발과 동일한 품질 관리 도구(정적 분석·평가·보안·의존성·관측성)가 필요하다.

개념 왜 중요한가 한 줄
에이전트 소프트웨어 스택 레이어별 역할을 알아야 무엇을 직접 만들지 결정할 수 있다 모델→도구→컨텍스트→하니스→팩토리 라인→팩토리
컨텍스트(스킬)가 새로운 코드 모델을 프로그래밍하는 수단이 코드에서 컨텍스트로 이동 스킬 = 재사용 가능한 라이브러리
하니스(Harness) 확률적 모델을 감싸는 결정론적 소프트웨어 → 통제 가능성 확보 Claude Code가 하니스의 대표 예시
스킬 평가(Evals) 테스트 없이 스킬을 쌓으면 레거시 코드처럼 썩는다 단위 eval → 프로젝트 eval → 조직 eval
스킬 보안·거버넌스 오픈 클로(Open Claw [?Open Claude]) 생태계에서 30% 이상이 악성 공급망 보안이 npm처럼 필수화될 것
의존성 관리 스킬도 버전 관리·충돌·업데이트 문제가 발생한다 package manager for skills

내가 모를 만한 것 / 처음 보는 것

  • Tessl — Guy Podjarny가 2년 전 창업한 agentic 개발 도구 회사. lint, review, eval, 의존성 관리, 에이전트 기능 제공.
  • 하니스(Harness) — 확률적 모델을 감싸는 결정론적 소프트웨어 래퍼. Claude Code, Cursor 등이 해당. 훅(hook), 설정, 툴 목록, 권한 제어 포함.
  • 팩토리 라인(Factory Line) — 여러 하니스를 파이프라인으로 조합한 것. 입력(예: 기능 요청) → 출력(배포된 기능).
  • 컨텍스트 개발 생명주기(Context Development Lifecycle) — 기존 SDLC(소프트웨어 개발 생명주기)를 에이전트에게 위임하고, 인간은 컨텍스트 생성·평가·최적화·배포·관측에 집중하는 새로운 패러다임.
  • 오픈 클로(Open Claw [?Open Claude]) — 오픈소스 Claude 스킬 생태계. 화자가 "OpenClaw"라 언급.
  • 프로그레시브 디스클로저(Progressive Disclosure) — 스킬 설계 원칙 중 하나. Anthropic 베스트 프랙티스 항목.

화자의 디테일 (놓치기 쉬운 포인트)

  1. GitHub에 현재 약 200만 개의 스킬 — 연초 기준 거의 0에서 폭발적 증가. 퀄리티 편차 크다.
  2. Intercom 사례 — 관련 스킬이 로드되지 않으면 GitHub PR 생성 자체를 하니스가 차단. 모델이 선택권을 갖지 않도록 통제권을 뺏는 방식.
  3. OpenAI Ryan Lopopolo 사례 — 테스트 커버리지가 포함되지 않으면 커밋 불가 처리하는 커스텀 하니스.
  4. 스킬 부패(Skill Rot) — 잘 만든 스킬도 2주~3개월 내에 모델 변경·API 변경으로 오작동 또는 잘못된 방향 제시 가능.
  5. Snyk이 스킬 스캐닝 도입 — AppSec 도구들이 이미 스킬 정적 분석 지원 시작. Guy는 Snyk 창업자이기도 함.
  6. eval 시나리오 품질이 핵심 — 100% 커버리지지만 버그를 못 잡는 테스트처럼, 형식적 eval은 낭비. 소수의 고품질 시나리오가 훨씬 유용.
  7. 모델 비교 eval — GLM 5나 Kimi 2.6 같은 저렴한 모델로 충분한지, 아니면 Opus 4.8이 필요한지를 eval로 판단 가능.

# 섹션 요지
1 에이전트 소프트웨어 스택 모델 위에 도구·컨텍스트·하니스·팩토리 라인이 레이어로 쌓인다
2 도구(Tools) CLI, MCP, API — 모델을 에이전트로 만들고 값싸고 빠르게 처리
3 컨텍스트(Context = Skills) 정책·스펙·워크플로 3종. 규칙·스킬·수동 docs로 로딩 방식 구분
4 하니스(Harness) 결정론적 래퍼. 훅·설정·툴 제어. 여러 하니스 → 팩토리 라인
5 스킬 폭발과 3대 과제 보안/거버넌스 · 재사용/협업 · 생명주기(부패)
6 5가지 소프트웨어 툴 적용 정적 분석 · eval · 보안 테스트 · 의존성 관리 · 관측성
7 컨텍스트 개발 생명주기 인간은 컨텍스트 생성·최적화, SDLC는 에이전트에게 위임

1. 에이전트 소프트웨어 스택

소프트웨어 개발의 패러다임이 "코드와 구현 중심"에서 "의도와 지시(Intent & Instructions) 중심"으로 전환되고 있다. 이 위에 새로운 레이어드 스택이 형성된다.

  • 모델(Models) — 새로운 운영체제. 위에 쌓이는 모든 것이 호환성을 맞춰야 한다.
  • 도구(Tools) — 모델을 에이전트로 만드는 유틸리티. CLI, MCP, API 형태. grep, ffmpeg 같은 기존 도구가 그대로 쓰인다. 도구끼리 파이프·조합 가능.
  • 컨텍스트(Context) — 모델이 모르거나 알기 비효율적인 정보를 제공. 세 종류: 정책·관행(Policy), 스펙(Spec), 워크플로(Workflow). 로딩 방식: 항상 주입(규칙/CLAUDE.md), 온디맨드(스킬), 수동 참조(docs).
  • 하니스(Harness) — 확률적 모델을 결정론적으로 감싸는 소프트웨어. 훅·설정·툴 목록·권한 제어 포함. Claude Code가 대표적 예.
  • 팩토리 라인(Factory Line) — 여러 하니스를 파이프라인으로 조합. 반복 가능한 입출력.
  • 팩토리(Factory) — 팩토리 라인이 모여 전체 개발 프로세스 구성.

2. 스킬은 재사용 가능한 컨텍스트 라이브러리

컨텍스트 중에서도 스킬은 재사용성을 목적으로 설계된다. 한 번만 쓸 거라면 그냥 프롬프트로 처리, 반복한다면 스킬로 만든다. 스킬은 라이브러리다.

  • 스킬은 도구를 호출하고, 스킬이 다른 스킬을 호출할 수 있다.
  • 예: 인시던트 대응 워크플로 스킬 → 로그 수집 스킬(Datadog 도구 사용) → 근본 원인 분석 스킬 → 티켓 생성 스킬(Linear/Jira 도구 사용).
  • 조합 가능성(Composability)이 소프트웨어를 강력하게 만드는 원리와 동일하다.

3. 스킬 폭발과 3대 과제

과제 1: 보안·거버넌스 - 악성 스킬(30% 이상 in Open Claw [?Open Claude] 생태계), 부주의 스킬(안전 지시 누락), 취약 스킬(시크릿·API 토큰 노출). - 어떤 스킬을 쓰는지, 누가 쓰는지, 침해 시 감지 가능한지 추적 필요.

과제 2: 재사용·협업 - 1,000명 규모 유니콘 기업 사례: 공유 레포 만들었더니 중복·품질 불명확·"내 머신에서만 되는" 문제 → 결국 아무도 공유 레포를 신뢰하지 않고 다시 개인 작성으로 회귀. - 품질 지표와 의존성 관리 부재가 근본 원인.

과제 3: 생명주기·부패 - 스킬도 소프트웨어처럼 썩는다. AI 세계에서는 2주 만에 구식 가능. - 반면, 에이전트 로그·PR·프로덕션 데이터를 관측하면 자동 최적화도 가능 → 유지보수가 기회가 된다.

4. 5가지 소프트웨어 툴을 스킬에 적용

정적 분석(Static Analysis) - 린트: 필드 형식, 형태 검사 (Tessl lint). - 품질·보안 측정: Anthropic 베스트 프랙티스(프로그레시브 디스클로저, 간결성, 활성화 선언) 매칭 (Tessl review). - 커스텀 에이전틱 리뷰: 스킬 내용 자체를 검토.

평가(Evals = Tests) - 스킬 단위 eval → 프로젝트 eval(20개 스킬 설치, 과거 PR 시나리오 추출) → 조직 전체 eval(모델 교체 가능 여부 판단). - 시나리오 품질이 핵심. 형식적 커버리지보다 실제 버그를 잡는 소수의 고품질 시나리오가 낫다. - 부수 효과: eval 결과를 집계해 품질 점수 산출 → 공유 레포에서 어떤 스킬이 우수한지 판별 가능.

보안 테스트 - 정적 분석: Snyk 등 AppSec 도구들이 스킬 스캐닝 지원 시작. Tessl은 Snyk 레지스트리와 통합. - 동적 테스트(레드팀): 아직 초기 단계. 스킬 기능이 워낙 다양해 정상 동작 기준 정의가 어렵다. - 공급망 보안: 어떤 스킬을 쓰는지 추적.

의존성 관리 - 버전 관리, 설치 기록, tessl update로 업데이트. - 품질·보안 기준으로 설치/게시 게이팅. - 크로스 에이전트 호환성(npm이 OS를 추상화하는 것처럼).

관측성(Observability) - 코딩 에이전트 런타임 모니터링 → 실제 eval 시나리오·문제 추출 → 스킬 업데이트. - 에이전트 성공률 분석 → 새 스킬 기회 발굴 또는 불필요 스킬 삭제.

5. 컨텍스트 개발 생명주기

인간은 컨텍스트 개발 생명주기에 집중해야 한다: 컨텍스트 생성 → 평가 → 최적화 → 패키지 관리로 배포 → 보안 적용 → 소비 → 관측 → 반복.

SDLC(소프트웨어 개발 생명주기)는 에이전트에게 위임한다. 에이전트가 코드를 생성·테스트·배포하고, 인간은 그 에이전트를 위한 컨텍스트를 만들고 관리한다.

에이전트 소프트웨어 스택

Tessl을 창업한 지 2년이 넘었습니다. 소프트웨어 개발이 코드와 구현 중심에서 의도와 지시(Intent & Instructions) 중심으로 전환될 것이라는 믿음으로 시작했습니다. 2년 전에는 논란이 많았지만, 지금은 그렇지 않습니다.

새로운 개발 스택이 보이기 시작했습니다. 레이어드 소프트웨어 스택입니다.

맨 아래에는 새로운 프리미티브(primitives)인 모델이 있습니다. 우리가 모두 그 위에서 개발하는 새로운 슈퍼파워입니다.

그 위에 도구(Tools)가 있습니다. 모델을 에이전트로 만들어 세상에 영향을 주고 정보를 수집할 수 있게 합니다.

컨텍스트(Context)는 모델을 안내합니다.

그리고 점점 더 중요해지는 하니스(Harness)가 모델을 제약하거나 여러 요소를 패키징합니다.

하니스들이 모여 팩토리 라인(Factory Line)이 되고, 이것이 팩토리(Factory)가 됩니다.

도구(Tools)

도구는 가장 이해하기 쉽습니다. 소프트웨어 유틸리티로, 모델을 에이전트로 만들어 세상과 상호작용하게 합니다. 동시에 모델에게 맡기는 것보다 더 싸고 빠르고 정확하게 처리하는 수단이기도 합니다.

종류: CLI 도구, MCP 도구(에이전트에서 직접 호출), API/네트워크 도구.

예: grep은 토큰 낭비 없이 많은 파일에서 정보를 찾습니다. ffmpeg는 모델보다 훨씬 오류 없이 빠르게 영상을 편집합니다.

도구는 소프트웨어이므로 조합할 수 있습니다. 파이프로 연결하거나 커스텀 도구를 만들 수 있습니다.

컨텍스트(Context)

LLM에서는 결국 모든 것이 컨텍스트입니다. 그중에서 우리가 개발하는 컨텍스트 파일은 에이전트가 모르거나 알기 비효율적인 정보에 집중합니다.

세 가지 유형: 1. 정책·관행(Policies & Practices) — 팀이 합의한 프레임워크 사용 방식, 보안 정책, API 설계 원칙. 2. 스펙(Specs) — 개발 중인 제품 정의, 사용 중인 API/빠르게 변하는 정보. 3. 워크플로(Workflows) — 인시던트 대응, 코드 리뷰 방식 등. 에이전트가 혼자 하기 어렵거나, 반복 가능하게 해야 할 때.

로딩 방식: - 규칙(Rules) — 항상 컨텍스트 윈도우에 주입 (CLAUDE.md, agents.md 등). 크기 주의 필요. - 스킬(Skills) — 온디맨드 로드. 사용자가 호출하거나 에이전트가 힌트로 로드. - 수동 컨텍스트(Passive Context) — 레포에 있는 아키텍처 문서 등. 에이전트가 검색해서 찾음.

이후 발표에서는 컨텍스트를 주로 "스킬"로 통칭합니다.

스킬도 조합됩니다. 스킬이 도구를 호출하고, 스킬이 다른 스킬을 호출합니다. 예: 인시던트 대응 스킬 → 로그 수집 스킬(Datadog 도구) → 근본 원인 분석 스킬 → Linear/JIRA 티켓 스킬.

조합 가능성이 소프트웨어를 강력하게 만드는 원리입니다. 웹 페이지 하나 만들 때마다 커널을 작성해야 한다면 말이 안 됩니다.

하니스(Harness)

하니스는 확률적 모델을 감싸는 결정론적 소프트웨어입니다. Claude Code [?Cloud Code]가 하니스의 예입니다.

  • CLAUDE.md에서 규칙을 로드하는 방법, 스킬 로드 방법을 압니다.
  • 모델을 제약하는 설정 파일: 어떤 도구가 사용 가능한지 정의.
  • 훅(hooks): 프롬프트가 들어올 때마다 실행 — 프롬프트 수정, 차단, 도구 호출 시 실행. 결정론적이고 더 싸고 빠르고 확실합니다.

사례: - Intercom: 관련 스킬이 로드되지 않으면 GitHub PR 생성 차단. 모델 선택권 제거, 통제권 확보. - OpenAI (Ryan Lopopolo): 테스트 커버리지 없으면 커밋 불가.

하니스도 조합됩니다: 제품 하니스(기능 요청 정교화) + 코딩 하니스(개발) + 보안 하니스(보안화) + DevOps 하니스(배포) → 시스템 하니스(팩토리 라인). 입력: 기능 요청, 출력: 배포된 기능.

스킬 폭발과 3대 과제

GitHub에 현재 약 200만 개의 스킬. 연초 기준 0에서 폭발적 증가. John Travolta 밈처럼 — 스킬이 늘어나고 통제를 잃고 있다.

과제 1: 보안·거버넌스 스킬은 에이전트가 실행합니다. - 악성 스킬: Open Claw [?Open Claude] 생태계에서 30% 이상이 악성. - 부주의 스킬: 안전 지시 없음 ("테이블을 정확히 업데이트하되, 드롭하지 말 것"이라는 한 줄이 없어서 테이블이 날아간 사례들). - 취약 스킬: API 토큰 등 시크릿이 로그에 노출. 어떤 스킬이 사용되는지, 누가 쓰는지, 침해 시 감지 가능한지 — 공급망 위생(supply chain hygiene) 필요.

과제 2: 재사용·협업 1,000명 이상 개발자를 둔 유니콘 기업 사례: 공유 레포 만들었더니 중복 난립, 7개 코드 리뷰 스킬 중 어느 게 좋은지 불명확, 에이전트마다 동작 다름("내 머신에서만 됨"), PR 협업 도구 없음 → 아무도 신뢰 안 하고 각자 작성으로 회귀. 품질 지표와 의존성 관리 부재가 원인.

과제 3: 생명주기·부패 소프트웨어가 썩듯 스킬도 썩습니다. AI 세계에서는 2주 만에 구식. 모델 변경, API 변경, 인프라 변경. 유지보수를 안 하면 결국 에이전트를 잘못된 방향으로 안내합니다. 반면, 에이전트 로그·PR·프로덕션 데이터를 관측하면 자동 최적화 가능 → 유지보수가 기회.

5가지 소프트웨어 툴을 스킬에 적용

1. 정적 분석(Static Analysis) 코드를 실행하지 않고 검사. 린터(형식 검사) → 품질·보안 분석 → 에이전틱 리뷰(내용 검토). Tessl: lint(필드·형식 검사), review(Anthropic 베스트 프랙티스 매칭 — 프로그레시브 디스클로저, 간결성, 활성화 선언).

2. 평가(Evals = Tests) 환경을 정의하고 에이전트를 실행시켜 결과를 판단. - 스킬 단위 eval: 스킬 하나를 독립적으로 테스트. 저렴한 오픈 모델로도 회귀 방지 가능. - 프로젝트 eval: 20개 스킬 설치, 과거 PR에서 시나리오 추출, 현실에 가까운 테스트. - 조직 전체 eval: 모델 교체 가능 여부 판단(GLM 5, Kimi 2.6으로 충분한지 vs. Opus 4.8 필요한지). 시나리오 품질이 핵심. 부수 효과: 품질 점수 산출 → 공유 레포에서 우수 스킬 판별.

3. 보안 테스트 Snyk 등 AppSec 도구들이 스킬 스캐닝 지원 시작. Tessl은 Snyk 레지스트리 통합. 동적 테스트(레드팀): 아직 초기 단계. 공급망 보안: 사용 중인 스킬 추적.

4. 의존성 관리 npm이 OS를 추상화하듯 스킬 패키지 매니저가 필요. 버전 관리, 설치 기록, 업데이트, 품질·보안 게이팅, 크로스 에이전트 호환성.

5. 관측성(Observability) 런타임에서 코딩 에이전트 모니터링 → 실제 eval 시나리오 추출 → 스킬 업데이트. 에이전트 성공률 분석 → 새 스킬 기회 발굴 또는 불필요 스킬 삭제.

컨텍스트 개발 생명주기

인간은 컨텍스트 개발 생명주기에 집중: 컨텍스트 생성 → 평가·테스트 → 최적화 → 배포(패키지 관리) → 보안 → 소비 → 관측 → 반복. SDLC는 에이전트에게 위임.

요약 및 Tessl 소개

새로운 에이전트 개발 스택: 모델(OS) → 도구(유틸리티) → 컨텍스트(새로운 코드) → 하니스(프레임워크) → 팩토리 라인(파이프라인) → 팩토리(전체 개발 프로세스).

스킬은 새로운 코드이며, 그에 맞는 도구가 필요합니다.

Tessl에서는 스킬·하니스·팩토리 라인 개발을 돕는 Tessl 에이전트를 준비 중. 로컬 개발, 파이프라인 최적화, Tessl 컨트롤 센터에서 활용 가능. 얼리 액세스: tessl.co/agents.

마지막으로, 새로운 개발 패러다임 구축은 특정 벤더나 회사의 일이 아니라 커뮤니티 활동입니다. 배운 것을 공유해 주세요. 감사합니다.
