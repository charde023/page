[한영자막] 엉성한 원샷 SaaS 대체품은 이제 그만 만드세요

업로드 2026-10-18 · 13.3분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 8분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

큰 그림: 작동하는 도구와 매일 쓰는 제품은 다르다

이 영상의 출발점은 “AI 에이전트에게 한 번 지시해 소프트웨어를 만들 수 있으니 SaaS가 필요 없어졌다”는 주장에 대한 보완이다. 화자는 기능이 한 번 실행되는 소프트웨어와 사람이 매일 편하게 사용할 소프트웨어 사이에는 큰 간격이 있다고 말한다.

화자는 Railway의 마케팅 업무에 쓰던 SaaS들을 대신하려고 내부 통합 도구를 만들었다고 설명한다. 이 도구에는 웹사이트 콘텐츠·변경 기록·블로그 관리, 이메일 발송, 여러 소셜 플랫폼 게시, 미디어 관리, 외부 창작자 관리를 위한 소형 고객 관리 기능, 작업 추적, 출시 계획, 달력, 댓글, 실시간 편집이 포함되었다고 한다. 모든 기능을 한 번에 완성했다는 뜻이 아니라, 에이전트를 이용해 도구를 만드는 과정에서 반복적으로 제품 원칙을 다듬었다는 이야기다.

읽는 법: 위에서 아래로 읽는다. 화자의 핵심은 특정 기술 이름 하나가 아니라, 코드 기반 → 제품 경험 → 실제 사용 검증이 함께 있어야 한다는 것이다. 이 그림은 측정 수치가 아니라 영상의 논리를 정리한 개념 지도다.

1. 기술 스택보다 재사용할 구조가 중요하다

화자는 처음에 “스택은 중요하지 않다”고 말하지만, 곧 조건을 붙인다. 프로그래밍 언어나 프레임워크만으로 결과가 결정되는 것은 아니어도, 에이전트에게 잘 정리된 코드베이스와 탄탄한 추상화를 주면 결과가 더 일관된다는 것이다.

여기서 추상화란 여러 기능이 공통으로 쓰는 규칙과 부품을 한곳에 정리해 두는 방식이다. 예를 들어 두 화면이 모두 기록을 만들고, 수정하고, 삭제하는 목록이라면 화면 구조와 데이터 처리 방식도 비슷해야 한다. 기존 패턴이 없으면 에이전트가 기능마다 새 방식을 만들어 낼 수 있지만, 좋은 선례가 있으면 그 방식을 반복해서 사용할 수 있다.

화자는 콘텐츠 관련 도구에는 Payload를 현재 선호한다고 말한다. 직접 처음부터 콘텐츠 관리 시스템을 만들 수도 있지만, 이미 있는 추상화를 활용하는 편을 택했다는 개인적 경험이다. 이는 Payload가 모든 상황의 정답이라는 검증 결과가 아니다.

읽는 법: 왼쪽은 결과가 반드시 나쁘다는 뜻이 아니라 변동 위험이 큰 상태다. 오른쪽도 성공을 보장하지는 않는다. 화자 역시 기존 페이지를 참고하라고 해도 에이전트가 따르지 않을 때가 있다고 인정한다.

2. 제품 완성도는 알아서 생기지 않는다

사용자는 좋은 SaaS를 매일 쓰면서도 그 안에 들어간 작은 배려를 잘 의식하지 않는다. 하지만 비슷한 도구를 직접 만들면 저장, 실패 처리, 삭제, 탐색 같은 세부 흐름이 얼마나 많이 필요한지 드러난다.

화자가 에이전트에게 명시적으로 요구한 대표적인 요소는 다음과 같다.

  • 자동 저장: 사용자가 저장 버튼을 누르지 않아도 뒤에서 작업 내용을 저장한다. 저장 때문에 입력이 멈추지 않아야 한다.
  • 저장 전 탭 닫기 방지: 저장되지 않은 변경이 있으면 브라우저 탭이 바로 닫히지 않게 한다. 화자는 자동 저장과 함께 이를 작업 손실을 막는 두 겹의 보호로 설명한다.
  • 실시간 협업: 여러 사람이 동시에 편집할 수 있게 한다.
  • 먼저 성공한 것처럼 보여 주기: 사용자의 행동이 성공했다고 화면에 즉시 반영하고, 뒤에서 서버와 맞춘다. 이를 낙관적 업데이트(optimistic update)라고 한다. 실패하면 이전 상태로 되돌리고 실패를 알려야 한다.
  • 실행 취소와 지연 삭제: 삭제 직후 몇 초 동안 마음을 바꿀 기회를 주고, 취소하지 않았을 때 실제 작업을 진행한다.
  • 보관과 복원: 당장 보지 않을 기록을 삭제하도록 강요하지 않고 숨겼다가 다시 꺼낼 수 있게 한다.
  • URL에 화면 상태 보존: 필터와 정렬 조건을 주소에 담아 다른 팀원이 같은 화면을 바로 열 수 있게 한다.
  • 무한 스크롤: 사용자가 ‘더 보기’나 다음 페이지를 계속 누르지 않아도 스크롤에 따라 데이터를 불러온다.

낙관적 업데이트는 모든 작업에 무조건 적용하는 규칙이 아니다. 화자도 결과를 확인할 때까지 기다려야 하는 작업에는 로딩 표시가 필요하다고 말한다. 핵심은 빠르게 보이는 효과가 아니라 실패했을 때 되돌릴 수 있는 조건까지 함께 설계하는 것이다.

3. 좋은 방식을 문서화하고 다시 사용한다

화자는 기존 페이지를 참고하라는 요청에서 더 나아가, 팀이 가진 제품 의견을 에이전트 스킬(agent skill)로 묶어야 한다고 말한다. 여기서 스킬은 에이전트가 작업할 때 반복해서 따르게 하는 지침과 규칙의 묶음이다.

그는 내부 도구를 만들며 세 가지 스킬을 사용했다고 설명한다. 두 가지는 디자인 엔지니어링 관련 스킬로, UI·타이포그래피·레이아웃·오류 메시지와 애니메이션 같은 요소를 개선하기 위한 것이었다. 나머지 하나는 Railway에서 저장소, 데이터베이스, 앱, 실시간 서버 등을 배포하고 다루기 위한 Railway Agent 스킬이었다.

즉, 좋은 결과를 매번 긴 대화로 다시 설명하지 않고, 한 번 정한 품질 기준을 반복 가능한 규칙으로 포장한다는 접근이다.

4. 마지막 기준은 “만들었다”가 아니라 “실제로 사용해 봤다”이다

에이전트는 기능 구현 후 “빌드가 통과했고 테스트도 통과했다”고 보고할 수 있다. 그러나 화자는 자신이 실제로 기능을 사용했을 때 경험이 심하게 망가져 있는 경우가 있었다고 말한다. 그래서 가장 중요한 마지막 단계로 실제 인프라에서 기능을 처음부터 끝까지 실행하는 검증을 제시한다.

읽는 법: 1번부터 아래로 진행한다. 통과하면 왼쪽 완료 판단으로 가고, 실패하면 오른쪽에서 수정한 뒤 실제 인프라 사용 단계로 연결된 선을 따라 돌아간다. 이 도식은 화자가 설명한 검증 과정을 정리한 것이며, 특정 성공률을 나타내는 데이터 그래프는 아니다.

전체 통찰과 경계

화자의 결론은 에이전트가 기능을 구현하지 못한다는 것이 아니다. 오히려 구현 능력은 충분할 수 있지만, 사람이 무엇을 요구해야 하는지, 좋은 선례를 어떻게 재사용할지, 실제 업무 흐름을 어떻게 검증할지 알아야 좋은 내부 도구가 나온다는 주장이다.

다만 이 내용은 Railway 내부 마케팅 도구를 만든 한 화자의 경험과 의견이다. 모든 SaaS를 대체했다는 검증이나 비용·속도·오류율 비교 수치는 제시되지 않는다. 화자도 2026년 10월 녹화 당시의 의견이며 몇 달 안에 바뀔 수 있다고 직접 경고한다.

또한 화자는 GPT-6가 나온 시점에 돌파구를 느꼈다고 말하고, 실시간 기능을 얻기까지 “7억 토큰”이 들었다고 표현한다. 두 표현 모두 제공된 자료만으로 독립 확인할 수 없으며, 특히 7억 토큰이 실제 측정치인지 과장된 농담인지 확정할 수 없다. META는 원본 영상 연결과 원작자 귀속을 “화자 이름과 SNS 기준 추정”이라고 밝혔지만 creator와 affiliation 값은 비어 있다. 따라서 이 노트에서는 원작자 이름과 소속을 확정하지 않는다.

여기까지만 이해하면 충분

  • 에이전트가 기능을 실행하게 만드는 것과 매일 쓰기 좋은 제품을 만드는 것은 다른 문제다.
  • 일관된 결과에는 특정 스택보다 탄탄한 코드 구조, 기존 페이지, 반복 가능한 에이전트 스킬이 중요하다는 것이 화자의 주장이다.
  • 자동 저장, 실패 복구, 실행 취소, 보관, URL 상태 같은 제품 경험은 명시적으로 요구해야 한다.
  • 빌드와 테스트 통과만 믿지 말고 실제 인프라에서 처음부터 끝까지 사용하며 실패를 수정해야 한다.

한 장면으로 이해하기

화자가 설명한 장면을 그대로 따라가 보자. 에이전트는 새 기능을 구현한 뒤 빌드와 테스트가 통과했다고 보고한다. 그러나 화자가 직접 사용하면 경험이 심하게 망가져 있을 때가 있다. 실제 인프라에서 처음부터 끝까지 사용하라고 지시하면, 에이전트가 실패를 발견하고 수정한 뒤 다시 검증하는 흐름으로 바뀐다.

"빌드와 테스트 통과 보고만으로는 실제 사용 경험의 고장을 찾지 못함" 문제
→ "실제 인프라에서 기능을 처음부터 끝까지 사용하고, 실패하면 수정 후 다시 확인" 작동 방식
→ "화자의 평가로는 더 제대로 작동하고 일관된 내부 도구에 가까워짐" 결과

비유와 깨지는 지점

가구를 만드는 작업대와 실제 착석 검사

탄탄한 코드 구조와 기존 페이지는 매번 같은 모양을 만들게 돕는 작업대와 틀에 해당한다. 자동 저장·실행 취소·오류 처리 같은 요구는 표면을 다듬고 모서리를 처리하는 마감 기준이다. 실제 인프라에서의 처음부터 끝까지 검증은 완성된 의자를 사람이 직접 사용해 보는 검사에 해당한다.

비유가 깨지는 지점: 소프트웨어는 여러 사용자의 동시 편집, 네트워크 실패, 서버와 화면 상태의 불일치처럼 가구와 다른 문제가 있다. 한 번 정상 작동했다고 모든 조건에서 계속 정상이라는 뜻도 아니다.

1. 원인

에이전트가 기능 구현에는 성공해도 매일 쓰기 좋은 제품을 자동으로 만들지 못하는 이유는 무엇인가?

모범 답안 보기

기능의 핵심 동작과 일상적인 제품 경험은 요구 조건이 다르기 때문이다. 자동 저장, 실패 복구, 실행 취소, 보관, URL 상태, 실제 사용 검증 같은 요소는 사용자가 반복해서 쓸 때 중요하지만, 명시하지 않으면 에이전트가 빠뜨릴 수 있다. 기존 구조와 좋은 선례가 없으면 기능마다 서로 다른 패턴을 만들 가능성도 커진다.

2. 대조

낙관적 업데이트와 무조건 성공한 것처럼 보여 주는 처리는 어떻게 다른가?

모범 답안 보기

낙관적 업데이트는 화면을 먼저 바꾸되, 뒤에서 실제 작업을 동기화하고 실패하면 이전 상태로 되돌리며 사용자에게 알리는 방식이다. 무조건 성공한 것처럼 보여 주는 처리는 실패 확인과 복구가 없다. 화자도 모든 작업에 낙관적 업데이트를 적용해서는 안 되며, 확인이 필요한 작업은 기다려야 한다고 말한다.

3. 적용

에이전트가 새 내부 기능을 만들었다면, 완료 여부를 어떤 기준으로 판단해야 하는가?

모범 답안 보기

빌드와 자동 테스트 통과만 보지 않는다. 기존 페이지와 구조를 제대로 따랐는지, 저장·실패·취소·복구 흐름이 필요한지 검토하고, 실제 실행 환경에서 핵심 사용자 시나리오를 처음부터 끝까지 수행한다. 실패가 나오면 수정 후 같은 시나리오를 다시 검증한다. 업무 위험이 큰 기능이라면 낙관적 처리보다 결과 확인을 우선할 수 있다.

이번 글의 통찰

1. 구현 속도가 빨라질수록 품질 기준을 말로 꺼내야 한다

  • [원문] 화자는 에이전트가 자동 저장, 낙관적 업데이트, 실행 취소 같은 패턴을 구현할 능력은 있지만, 보통 명시적으로 요청해야 한다고 말한다.
  • [해석] 병목은 코드를 생성하는 능력만이 아니라 좋은 제품 경험을 구성하는 조건을 알고 요구하는 능력으로 이동한다. 숨은 품질 기준을 체크리스트와 스킬로 바꾸면 재사용할 수 있다.
  • [경계] 이는 화자의 내부 도구 제작 경험이다. 각 패턴이 실제 사용성이나 생산성을 얼마나 높였는지 보여 주는 측정값은 제공되지 않았다.

2. “스택은 중요하지 않다”는 말에는 구조라는 조건이 붙는다

  • [원문] 화자는 언어나 프레임워크 선택 자체보다 잘 구조화된 코드베이스, 탄탄한 추상화, 기존 페이지 참조가 일관된 결과를 만든다고 설명한다. 콘텐츠 관련 작업에는 Payload를 현재 선호한다고 덧붙인다.
  • [해석] 기술 이름을 고르는 것보다 에이전트가 반복해서 따라갈 선례와 공통 부품을 만드는 일이 중요하다는 주장이다.
  • [경계] 화자도 에이전트가 참조 지시를 따르지 않을 때가 있다고 인정한다. Payload는 화자의 선택이며 모든 작업에 적합하다는 비교 검증은 없다. “스택은 중요하지 않다”를 기술 선택이 어떤 상황에서도 무관하다는 절대 명제로 확대하면 안 된다.

3. 자동 검사 통과와 실제 제품 검증은 서로 다른 증거다

  • [원문] 화자는 에이전트가 빌드와 테스트 통과를 보고해도 실제 사용 경험이 망가져 있을 수 있으며, 실행 중인 인프라에서 종단 간 검증을 시키면 실패를 발견하고 수정하는 흐름이 생긴다고 말한다.
  • [해석] 완료 기준을 “코드가 생성됨”에서 “실제 사용자 흐름이 작동함”으로 옮겨야 한다. 정상 경로뿐 아니라 실패·복구·대기 상태도 관찰해야 한다.
  • [경계] 숫자와 고유명사를 대조하면 ‘세 가지 스킬’은 디자인 관련 두 가지와 Railway Agent 스킬 한 가지로 열거 수가 일치하고, 작업 손실 방지의 ‘두 겹’도 자동 저장과 탭 닫기 방지로 일치한다. 반면 “7억 토큰”은 실제 측정치인지 과장 표현인지 불명확하며, GPT-6·자동 배포·전체 기능의 동작 상태는 독립 검증되지 않았다. META는 출처 귀속이 화자 이름과 SNS를 바탕으로 한 추정이라고 적었지만 원작자와 소속 필드는 비어 있다. 제목의 넓은 SaaS 대체 주장과 달리 영상의 구체 사례는 Railway 내부 마케팅 도구 범위다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 빌드와 테스트 통과만으로 실제 사용을 확인할 수 없다는 원리는, 학습자의 “알겠다”는 말만으로 이해를 판단할 수 없다는 교육 문제와 구조가 닮았다.
  • 통찰: 설명과 실제 적용을 처음부터 끝까지 수행하게 해야 막힌 단계가 드러난다. 다만 소프트웨어 검증과 사람의 이해 평가는 같은 측정 문제는 아니다.
  • 질문/행동: 학습자가 도움 없이 원인·대조·새 사례 적용까지 설명하게 했을 때 어디에서 멈추는지 관찰한다.

사업가 · 구조적 비유

  • 관련성: 화자는 여러 내부 마케팅 기능을 한 도구로 묶고, 외부 SaaS를 대신하는 사례를 설명한다.
  • 통찰: APOM에 이미 이런 시스템이 있다는 뜻은 아니다. 검증 전 가설로는 구독료만 비교하지 말고, 직접 만드는 시간·토큰·인프라·오류 위험과 매일 쓰는 흐름의 편의까지 함께 판단해야 한다.
  • 질문/행동: 실제 운영에서 대체를 검토한다면, 비용 절감보다 먼저 핵심 시나리오의 종단 간 성공 여부와 실패 복구 가능성을 확인할 수 있는가?

마케터 · 구조적 비유

  • 관련성: 화자의 내부 도구는 콘텐츠, 이메일, 소셜 게시, 미디어, 외부 창작자 관리 등 마케팅 흐름을 한곳에 모은 사례다.
  • 통찰: “AI로 만들었다”는 문장은 주장일 뿐이다. 자동 저장 장면, 실행 취소 흐름, 동일한 필터 URL 공유, 실제 검증 기록처럼 관찰 가능한 장면이 제품 완성도의 증거가 된다.
  • 질문/행동: 상세페이지에서 속도와 편리함을 주장한다면, 어떤 실제 작업 전후 장면으로 실패 처리까지 보여줄 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 코드 구조, 참조 페이지, 에이전트 스킬, 낙관적 업데이트, 종단 간 검증이 영상의 직접적인 주제다.
  • 통찰: 모델 이름보다 에이전트가 따를 기존 패턴과 완료 조건을 설계해야 한다. 빌드 통과, 실제 사용 성공, 실패 복구는 서로 다른 검사 항목이다.
  • 질문/행동: 다음 저위험 기능에서 기존 페이지 참조와 실제 인프라 종단 간 검증을 모두 요구하고, 어느 단계에서 처음 실패하는지 기록한다.

# 섹션 요지
1 문제 제기와 내부 도구 작동하는 원샷 소프트웨어와 매일 쓰기 좋은 제품 사이에는 간격이 있다.
2 구조와 추상화 기존 코드 패턴이 에이전트 결과의 일관성을 높인다는 주장이다.
3 일상 사용의 제품 경험 자동 저장, 협업, 낙관적 업데이트, 실행 취소, 보관이 필요하다.
4 탐색과 공유 URL 상태와 무한 스크롤 같은 작은 흐름이 반복 사용에 영향을 준다.
5 참조 페이지와 스킬 좋은 선례와 제품 의견을 에이전트가 재사용할 규칙으로 묶는다.
6 실제 인프라 검증 빌드·테스트 이후에도 종단 간 사용과 반복 수정이 필요하다.

1. 문제 제기와 Railway 내부 도구

화자는 SaaS가 죽었다는 이야기가 더 이상 새로운 주장이 아니라고 소개하지만, 이에 곧바로 동의하기보다 빠진 부분을 지적한다. 에이전트가 한 번에 만든 작동 소프트웨어와 자신이 실제로 사용하고 싶은 세련된 소프트웨어 사이에는 큰 간격이 있다는 것이다.

그는 Railway 내부의 마케팅 목적에 사용하던 여러 SaaS 제공자를 대신하는 통합 도구를 만들었다고 말한다. 제시한 범위는 다음과 같다.

  • Railway 웹사이트 콘텐츠, 변경 기록, 블로그 관리
  • 이메일 발송
  • 여러 소셜 플랫폼 동시 게시
  • 웹사이트 미디어 관리
  • 외부 창작자 협업 기록을 위한 소형 CRM
  • 작업 추적과 출시 계획
  • 달력, 댓글, 실시간 편집

화자는 이 도구가 에이전트를 이용해 만들어졌으며 Railway에서 실행되고 자동 배포된다고 주장한다. 독립된 동작 기록이나 비용 비교는 자료에 없다.

2. 녹화 시점과 화자의 경고

화자는 스코틀랜드 에든버러의 야외 벤치에서 이야기하며, 그 벤치를 “10점 만점에 10점”이라고 표현한다. 녹화 시점을 2026년 가을, 10월이라고 밝힌다. META의 업로드일은 2026년 10월 18일로, 월 정보는 충돌하지 않는다.

그는 기술 환경이 매우 빠르게 바뀌므로 자신의 의견이 몇 달 안에 완전히 달라질 수 있다고 경고한다. 또한 GPT-6가 나왔을 때 돌파구를 느꼈다고 말하지만, 제공 자료 안에는 이를 검증할 별도 근거가 없다.

3. 스택보다 코드 구조와 추상화

화자는 프로그래밍 언어나 프레임워크가 중요하지 않다는 주장에 어느 정도 동의한다. 다만 실제로 사용할 도구를 만들 때는 적절한 코드베이스와 탄탄한 추상화가 에이전트의 결과를 더 일관되게 만든다고 말한다.

그 이유는 새 기능을 추가할 때마다 에이전트가 같은 문제를 다시 풀거나 새로운 패턴을 발명할 필요가 없기 때문이다. 기존 구조가 있으면 에이전트가 그 패턴을 따를 수 있다.

화자는 웹 개발에서 현재 풀스택 라이브러리를 선호하며, 콘텐츠 관련 작업에는 Payload를 추천한다. 콘텐츠 관리 시스템들을 비교해 본 뒤 처음부터 직접 만들기보다 기존 추상화를 사용하기로 했다는 개인적 설명이다.

4. 자동 저장과 실시간 협업

문서 편집기 같은 도구에서 화자가 기본 요건으로 꼽는 첫 요소는 자동 저장이다. 저장 버튼을 누르지 않아도 뒤에서 진행 상황을 저장하고, 저장 동작이 입력을 막지 않아야 한다.

여기에 저장되지 않은 변경이 있을 때 브라우저 탭이 닫히는 것을 막는 보호를 추가한다. 화자는 이 두 겹이 작업 손실을 막는다고 설명한다.

그다음 단계는 여러 사용자의 동시 편집을 지원하는 실시간 협업이다. 화자는 에이전트가 이 기능 구현 자체에는 큰 어려움을 겪지 않았다고 말한다. 다만 “7억 토큰 후에 실시간 기능을 얻었다”는 표현은 실제 사용량인지 과장된 농담인지 자료만으로 판단할 수 없다.

5. 낙관적 업데이트, 실행 취소, 보관

낙관적 업데이트는 사용자의 행동이 성공했다고 화면에 먼저 반영하고, 뒤에서 실제 작업을 동기화하는 방식이다. 작업이 실패하면 화면을 이전 상태로 되돌리고 실패를 알려야 한다.

화자는 이 방식이 로딩 표시를 반복해서 보여 주는 것보다 빠르고 즉각적인 경험을 만들 수 있다고 말한다. 동시에 모든 작업에 무조건 적용해서는 안 되며, 실제 성공을 확인할 때까지 기다려야 하는 상황도 있다고 제한한다.

삭제의 경우 확인 창을 띄워 즉시 지우는 방식보다, 화면에서 먼저 치운 뒤 몇 초 동안 실행 취소 기회를 주는 경험을 선호한다. 사용자가 취소하지 않았을 때 실제 작업을 진행하는 지연 동작이다.

또한 보이지 않게 만들고 싶다는 이유만으로 삭제를 강요하지 말고, 기록을 보관했다가 다시 복원할 수 있게 해야 한다고 주장한다.

6. URL 상태와 무한 스크롤

기록 목록의 필터, 정렬, 여러 조건을 URL에 저장하면 다른 팀원에게 같은 화면을 공유하기 쉬워진다. 링크를 받은 사람은 발신자가 보고 있던 조건을 그대로 볼 수 있다.

화자는 에이전트가 기본적으로 잘 넣지 않는 작은 요소로 무한 스크롤도 언급한다. ‘더 보기’나 다음 페이지 버튼을 반복해서 누르는 대신 스크롤에 따라 데이터를 불러오고, 마지막에는 끝에 도달했음을 보여 주는 방식이다. 사소해 보여도 매일 쓰는 도구에서는 차이가 크다는 것이 화자의 의견이다.

7. 기존 페이지를 참조점으로 사용하기

화자는 에이전트에게 UI, 데이터 불러오기, 전체 구조를 설계할 때 기존 페이지를 참조하라고 명시하면 결과가 좋아졌다고 말한다. 한 번 정의한 좋은 기준을 다른 기능에 재사용할 수 있기 때문이다.

다만 에이전트가 참조 지시를 따르지 않는 경우도 있었다고 인정한다. 성공을 보장하는 방법은 아니지만, 화자의 경험에서는 참조 페이지를 지정했을 때 성공률과 일관성이 높아졌다.

두 기능이 모두 기록을 만들고, 수정하고, 삭제하는 같은 개념을 공유한다면 두 화면도 거의 같은 방식으로 작동해야 한다는 것이 그의 기준이다.

8. 세 가지 에이전트 스킬

화자는 제품에 관한 의견을 에이전트 스킬로 포장해야 한다고 주장한다. 내부 도구를 만들 때 사용했다고 밝힌 스킬은 세 가지다.

  1. UI, 타이포그래피, 레이아웃, 오류 메시지를 개선하기 위한 디자인 엔지니어링 스킬
  2. 애니메이션 등을 개선하기 위한 두 번째 디자인 엔지니어링 스킬
  3. Railway의 저장소, 데이터베이스, 앱, 실시간 서버를 다루고 배포하기 위한 Railway Agent 스킬

“세 가지”라는 수량과 실제 열거된 항목 수는 일치한다.

9. 가장 중요한 마지막 단계: 검증

에이전트는 기능을 만든 뒤 구현 완료, 빌드 통과, 테스트 통과를 보고할 수 있다. 그러나 화자는 직접 사용했을 때 경험이 심하게 망가진 경우가 있었다고 말한다.

검증 루프를 추가하면 에이전트가 다음 흐름을 반복한다고 설명한다.

  1. 기능을 구현한다.
  2. 실제로 사용한다.
  3. 실패를 발견한다.
  4. 문제를 수정한다.
  5. 다시 사용해 확인한다.

화자는 새 기능을 추가할 때 실제 실행 중인 인프라를 사용해 종단 간으로 작동하는지 검증하라고 요청한다고 말한다. 이러한 구조, 제품 경험, 스킬, 검증이 함께 있을 때 빠르게 만들면서도 제대로 작동하고 일관된 내부 도구를 얻을 수 있다는 것이 영상의 결론이다.

수치·이름·귀속 경계

  • 녹화 시점의 “2026년 10월”과 META 업로드일 2026-10-18은 충돌하지 않는다.
  • 작업 손실을 막는 “두 겹”은 자동 저장과 미저장 변경 시 탭 닫기 방지로 열거 수가 일치한다.
  • “세 가지 에이전트 스킬”은 디자인 관련 두 가지와 Railway Agent 스킬 한 가지로 수가 일치한다.
  • “7억 토큰”은 실제 계측값인지 과장 표현인지 확인할 수 없다.
  • GPT-6, 전체 자동 배포, 모든 기능의 정상 동작은 화자의 주장이며 독립 검증 자료가 없다.
  • META의 provenance note는 화자 이름과 SNS를 기준으로 출처를 추정했다고 적었지만 creator와 affiliation은 비어 있다. 링크만으로 이름이나 소속을 추정하지 않았다.
  • 영상 제목은 SaaS 대체를 넓게 표현하지만, 화자가 구체적으로 설명한 사례는 Railway 내부 마케팅 도구다.

전체 전사 펼치기

한동안 사람들은 SaaS가 죽었다고 말해 왔습니다. 이제는 그다지 자극적인 주장도 아닙니다. 우리가 사용하는 도구를 누군가에게 만들고 유지 관리해 달라고 돈을 지불할 이유가 있을까요? 그냥 직접 만들면 되는데요. 에이전트에게 시키면 됩니다. 그런데 제게는 거의 언급되지 않는 한 가지 빠진 부분이 있습니다. 바로 원샷으로 만들어 작동하는 소프트웨어와, 제가 실제로 사용할 소프트웨어 사이에는 큰 격차가 있다는 사실입니다. 즐거움을 불러일으키고, 잘 다듬어져 있고, 사용감이 좋으며, Railway에서 마케팅 목적으로 내부적으로 사용하던 여러 SaaS 제공업체를 실제로 대체하기 위한 여정을 거친 소프트웨어 말입니다.

저는 우리가 사용하는 올인원 도구를 직접 만들었습니다. 이 도구로 Railway 웹사이트의 콘텐츠, 변경 로그(changelog), 블로그를 관리할 수 있습니다. 이메일을 보내고, 모든 소셜 플랫폼에 동시에 게시하고, 웹사이트의 미디어도 관리할 수 있습니다. 미니 CRM도 있어서 외부 크리에이터와 협업할 때 그 내용을 추적할 수 있습니다. 여러 작업과 공개 시점을 조율해야 하므로 작업 추적과 출시 계획 기능도 있습니다. 캘린더도 있고, 동시에 댓글과 실시간 편집도 지원합니다. 이 모든 것이 에이전트를 사용해 만들어졌습니다.

GPT-6가 나왔을 때 돌파구를 느꼈다고 말할 수 있을 것 같습니다. 그리고 이 모든 것이 Railway에서 실행되고 있습니다. 전부 자동으로 배포됩니다. 이제 기능을 추가하고 싶을 때 실제로 잘 다듬어지고 앱의 나머지 부분과 일관되도록 하기 위해 제가 사용하는 원칙들을, 그리고 여러분이 직접 도구를 만들 때 가져다 적용할 수 있는 원칙들을 차근차근 보여드리겠습니다.

그래서 지루한 사무실에서 발표하는 대신, 분위기를 바꿔 야외에서 하기로 했습니다. 지금 정말 아름답습니다. 저는 스코틀랜드 에든버러에 있는데, 정말 믿기지 않을 정도입니다. 밖에 있는 벤치에 앉아 있고, 이것이 제 시야입니다. 단연 10점 만점짜리 벤치입니다.

이런 유형의 발표는 제가 익숙한 것과 조금 다르게 느껴질 겁니다. 우리가 직접 내부 도구를 만들어 온 과정과 그 과정에서 제가 갖게 된 의견을 여러분께 보여드릴 것이기 때문입니다. 하지만 이 분야의 상황이 매우 빠르게 변한다는 것도 알고 있습니다. 제가 하는 말은 몇 달 안에도 완전히 달라질 수 있습니다. 누가 알겠어요? 이 말을 제 면책 조항으로 생각해 주세요. 녹화 시점은 2026년 가을입니다. 10월입니다.

아무튼 이 이야기는 여기까지 하고, 첫 번째 요점인 스택은 중요하지 않다는 이야기부터 해보겠습니다. 많은 사람들이 어떤 프로그래밍 언어나 프레임워크를 사용하는지는 중요하지 않다고 말합니다. 에이전트에게 무엇이든 만들어 달라고 하면 에이전트가 만들어 줄 수 있다는 것이죠.

어느 정도는 동의합니다. 하지만 실제로 사용할 도구를 만들 때 제가 발견한 것은, 에이전트에게 탄탄한 추상화가 갖춰진 제대로 된 코드베이스를 제공하면, 예를 들어 새 기능을 작업할 때마다 이미 만들어 둔 것과 비슷하고 훨씬 일관된 결과물이 나온다는 점입니다.

이유는 아주 간단합니다. 에이전트가 새 기능을 추가하거나 새로운 패턴을 도입할 때마다 같은 바퀴를 다시 발명할 필요가 없기 때문입니다. 기존 패턴을 본질적으로 따르게 됩니다. 무엇을 선택할지는 코드베이스가 제대로 구조화되어 있기만 하다면 크게 중요하지 않다고 생각합니다. 오늘날 제가 웹에서 무엇인가를 만들 때 주로 선택하는 것은 모든 경우에 풀스택 라이브러리(full-stack library)를 사용하는 것입니다.

콘텐츠와 관련된 무엇인가를 만든다면 Payload를 확실히 추천합니다. 경험이 탄탄하고 추상화도 훌륭합니다. 언젠가 CMS들을 비교하는 데 깊이 빠져든 적이 있습니다. 직접 만들 수 있더라도 처음부터 구축해야 한다고 생각하지 않기 때문입니다. 하지만 다시 말하자면, 누가 알겠어요? 미래에는 상황이 바뀔 수도 있습니다. 이것이 제가 처음 마주한 주요 항목입니다.

실제로 좋아하고 매일 사용하는 SaaS 제품을 많이 사용하다 보면, 사용자로서는 알아차리지 못하는 것들이 많습니다. 하지만 실제로 어떤 경험을 재현하려고 해 보면 다양한 플로에 얼마나 많은 세심한 배려와 고민이 들어가는지 금방 알게 됩니다.

“이메일을 보내거나 무언가를 게시할 수 있으면 좋겠다”처럼 간단한 기능은 제출하는 폼이 있는 전통적인 서버 사이드 렌더링(server-side-rendered) 앱으로 쉽게 구현할 수 있습니다. 하지만 매일 사용하고 자주 찾게 될 무언가를 만들려고 하면 이렇게 생각하게 됩니다. “이렇게 느껴져서는 안 되는데.”

에이전트가 명시적으로 요청하지 않으면 일반적으로 구현하지 않는 패턴들이 많이 있습니다. 이것이 제가 정리한 목록이니 하나씩 살펴보겠습니다. 첫 번째는 자동 저장(autosave)입니다. 예를 들어 어떤 형태의 문서 편집기를 만들고 있다면, 자동 저장은 기본적으로 갖춰야 할 기능(table-stakes)이라고 생각합니다.

수동으로 저장 버튼을 눌러 저장하는 대신, 백그라운드에서 진행 상황을 자동으로 저장하도록 요청하는 것입니다. 그리고 이 작업이 비차단(non-blocking) 동작이 되도록 해야 합니다. 입력하는 동안 계속 타이핑할 수 있고, 내용은 자동으로 저장되는 방식입니다.

한 단계 더 나아가면 저장되지 않은 변경 사항이 있을 때 브라우저 탭이 닫히는 것도 막을 수 있습니다. 이 두 가지 계층이 현재 작업 중인 내용이 사라지지 않도록 보장합니다.

실시간 협업도 추가해서 동시 편집이 가능하게 할 수 있습니다. 다시 말하지만 에이전트는 이 기능을 추가하는 데 전혀 어려움을 겪지 않았습니다. 그냥 그 기능에 대해 요청하고 어떻게 작동할지 검토하면 되는 일이었습니다. 그 작업이 끝난 뒤, 7억 토큰이 지나고 나서야 저는 실시간 기능을 갖게 됐습니다.

일반적으로 이것이 제품 경험 측면에서 에이전트가 잘하지 못하는 첫 번째 부분입니다. 제가 발견한 또 다른 패턴은 에이전트가 낙관적 업데이트(optimistic updates)를 완전히 빼먹는다는 것입니다. 사용자가 어떤 작업을 할 때마다 로딩 스피너를 잔뜩 보여주는 대신, 성공 상태를 낙관적으로 먼저 보여주는 것입니다. 백그라운드에서는 사용자가 변경한 내용을 동기화합니다.

동기화나 작업이 어떤 이유로든 실패하면 변경 사항을 되돌리고 “작업이 정상적으로 처리되지 않았습니다”라고 알려주면 됩니다. 물론 모든 것에 낙관적 업데이트를 무작정 적용해서는 안 됩니다. 로딩 스피너를 보여주고 모든 작업이 제대로 처리됐는지 확인할 때까지 기다려야 하는 상황도 있습니다. 하지만 일반적으로 낙관적 업데이트를 적용하면 전체 경험이 훨씬 빠르고, 더 즉각적이며, 훨씬 민첩하게 느껴집니다.

에이전트에게 “적절한 곳에 낙관적 업데이트를 구현하고 싶습니다. 계획을 세워 봅시다”라고 요청하면 됩니다. 그러면 어디에 적용하는 것이 적절한지 모든 영역을 알려줄 것입니다. 다시 말하지만 에이전트가 구현하기 어려운 일은 아닙니다. 무엇을 요청해야 하는지 정확히 알고 요청하기만 하면 됩니다.

제 생각에 낙관적 업데이트의 확장이라고 할 수 있는 것은 사용자가 특정 작업을 취소할 수 있게 하는 것입니다. 예를 들어 에이전트에게 레코드를 삭제하는 기능을 구현해 달라고 하면, 보통 삭제 버튼을 만들어 줍니다. 버튼을 클릭하면 확인 대화 상자를 표시할 수도 있고, 확인을 누르면 실제로 삭제합니다.

훨씬 더 나은 경험은 사용자가 그 작업을 취소할 수 있도록 하는 것입니다. 사용자가 삭제를 누르면 삭제하려는 항목을 UI에서 즉시 제거하되, “잠시 동안은 마음을 바꿀 수 있습니다”라고 알려주는 것입니다. 아무것도 하지 않으면 실제로 삭제하길 원한다는 뜻이므로 작업을 실행합니다. 반대로 실행 취소(Undo)를 누르면 변경 사항을 다시 복원합니다.

작업 자체는 백그라운드에서도 처리합니다. 지연된 작업이며, 이는 다음 요점인 보관(archiving)과도 연결됩니다. 에이전트에게 레코드를 보관하고 다시 보관 해제할 수 있는 기능을 원한다고 말해야 합니다. 예를 들어 어떤 항목을 UI에서 완전히 숨기거나 검색 결과에서 제외하고 싶을 때가 있기 때문입니다.

그럴 때 사용하는 방법이 보관입니다. 사용자가 “이걸 보고 싶지 않다면 삭제해야 한다”고 생각하게 만들어서는 안 됩니다. 레코드를 보관할 수 있는 기능을 제공하는 편이 훨씬 더 나은 경험입니다. 반드시 존재해야 하는 패턴이라고 생각합니다.

제게 또 하나 중요한 것은 URL 상태(URL state)입니다. 적절한 경우 상태를 URL에 유지하도록 에이전트에게 요청해야 합니다. 예를 들어 레코드 목록이 있고 이를 필터링하거나 정렬하고 싶으며 여러 조건이 있다고 해보죠. 이런 내용을 URL에 유지하면 다른 사람에게 전달하기가 매우 쉬워집니다. 그러면 다른 팀원이 여러분이 보여주고 싶은 내용을 정확히 볼 수 있습니다.

에이전트가 기본적으로 구현하지 않는 또 하나의 사소한 세부 사항은 무한 스크롤(infinite scroll)입니다. 계속해서 더 불러오기(Load More)를 클릭하거나 다음 페이지(Next Page) 버튼을 누르고 싶지는 않습니다. 스크롤하면 데이터가 계속 표시되어야 합니다. 다음 페이지를 클릭할 필요가 없어야 하고, 마지막에는 끝에 도달했다는 것을 확인할 수 있어야 합니다. 아주 사소한 일이지만, 매일 무언가를 사용하다 보면 큰 차이를 만든다고 생각합니다.

결과물을 훨씬 더 좋게 만든 또 다른 패턴은 UI, 데이터 가져오기, 작동 방식, 전체적인 구조와 관련해 기존 페이지를 참조로 사용하라고 에이전트에게 명시적으로 말하는 것이었습니다. 이를 통해 무엇이 좋은지 한 번 정의하고, 이후 더 많은 기능에 그대로 재사용할 수 있었습니다.

솔직히 말하면 에이전트에게 “이 페이지 X를 참조로 사용해”라고 말해도 따르지 않을 때가 있습니다. 모델이 가끔 더 멍청해지는 것인지 모르겠지만, 그런 일이 실제로 일어납니다. 전반적으로는 기존 페이지를 참조로 사용하라고 말했을 때 성공률이 더 높았습니다. 경험도 더 일관되게 나오기 때문입니다. 앱을 사용하다 보면 “이건 앱의 다른 부분과 딱 맞아떨어지네”라는 생각이 듭니다.

두 부분이 같은 개념을 공유한다면, 예를 들어 둘 다 생성, 수정, 삭제할 수 있는 레코드 목록이라면 이 두 부분은 거의 동일해야 합니다.

이제 다음 요점으로 넘어가겠습니다. 우리가 어떤 것에 대해 의견을 갖고 있다면, 그것을 에이전트 스킬(agent skills)로 패키징해야 합니다. 그러면 에이전트가 무언가를 만들 때 그 스킬을 상당히 충실하게 따르게 됩니다.

내부 도구를 모두 구축하면서, 저는 세 가지 에이전트 스킬(agent skills)을 사용하게 됐습니다. 그중 두 가지는 디자인 엔지니어링(design engineering)과 관련된 것이었습니다. 하나는 더 나은 UI, 더 나은 타이포그래피, 더 나은 레이아웃은 물론이고 전반적으로 더 나은 오류 메시지를 만들기 쉽게 해줬습니다. 두 번째는 더 나은 애니메이션과 그 밖의 요소들을 만들기 쉽게 해주는 디자인 엔지니어링 스킬 모음이었습니다.

마지막으로, 물론 Railway Agent 스킬도 있습니다. 저희가 Railway 내부용으로 구축한 모든 것은 당연히 Railway에서 실행됩니다. 버킷, 데이터베이스, 앱 자체, 실시간 서버 등 전부요. 에이전트가 Railway를 효과적으로 사용하고 모든 것을 배포할 수 있도록 Railway Agent 스킬을 제공했더니, 에이전트가 해낼 수 있었습니다.

에이전트 스킬과 필요한 모든 것을 갖추고 나면, 제 생각에 마지막 단계이자 가장 중요한 단계는 검증입니다.

보통 에이전트에게 무언가를 만들어 달라고 하면 이렇게 말합니다. “좋아요, 기능을 구현했고, 빌드도 통과했고, 테스트도 통과했어요. 다 잘됐습니다.” 그렇죠? 하지만 실제로 사용해 보면 아주 망가진 경험을 하게 되는 경우가 있습니다. 그래서 검증 루프를 마련해 두면 정말 천지 차이가 납니다. 에이전트가 말 그대로 이렇게 말하는 모습을 볼 수 있기 때문입니다. “좋아요, 이걸 만들었고, 시험해 봤는데 실패했네요. 고치겠습니다.”

그렇게 계속 진행하다가 마지막에는 이렇게 말합니다. “좋아요, 완전히 테스트했습니다.” 컴퓨터 사용(computer use) 기능이 정말, 정말 좋아졌을 때 저는 이런 돌파구를 느꼈습니다. 이제 새로운 기능을 추가하고 싶을 때마다 저는 말 그대로 이렇게 말합니다. “이 기능이 처음부터 끝까지 제대로 작동하는지 검증하고, 실제 인프라를 실행해서 사용해 봐.”

에이전트는 처음부터 끝까지 테스트하는 일을 아주 잘 해낼 수 있습니다. 그저 그렇게 하라고 말해 주면 됩니다. 그리고 이 모든 요소를 갖추면, 빠르게 구축할 수 있고 제대로 작동하며 일관된 방식으로 작동하는 탄탄한 내부 도구를 만들 수 있게 될 겁니다.

이상입니다. 이것이 제가 내부 도구를 만들 때마다 사용하는 원칙들의 목록이었습니다. 이 내용이 도움이 되었기를 바랍니다. 하지만 그보다 더 중요한 것은, 기분 좋고, 잘 다듬어져 있으며, 즐거움을 불러일으키는 자신만의 내부 도구를 만들고 싶다는 영감을 얻으셨기를 바랍니다. 여러분도 여러분 회사의 SaaS 레이어(SaaS layer)가 될 수 있기를 바랍니다. 그럼 시청해 주셔서 정말 감사드리고, 다음 영상에서 뵙겠습니다.
