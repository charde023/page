금융 에이전트의 병목은 당신이다

원작자 Siddhant Emani · Auditoria AI · 업로드 2026-08-07 · 13.7분 · 원본 영상 ↗
한 줄 요약

금융 에이전트를 프로덕션에 빠르게 적용하려면 더 좋은 모델만 기다릴 것이 아니라, QA 티켓부터 배포까지의 개발 루프를 에이전트가 처리하게 만들고 인간은 검증자 역할로 이동해야 한다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
개발 속도(Development velocity) 프로덕션 버그는 모델 교체만으로 해결되지 않고, 문제 발견부터 수정·검증·배포까지의 속도에 좌우된다. 병목은 모델보다 개발 루프에 있다.
서브 에이전트(Sub-agent) 여러 작업을 병렬로 처리해 개발자가 하나씩 대기열을 관리하는 시간을 줄인다. 에이전트 군단을 만들어 각 버그를 독립적으로 처리한다.
Git 워크트리(Git worktree) 같은 저장소에서 여러 작업 공간을 분리해 충돌 없이 병렬 작업할 수 있다. 서브 에이전트마다 격리된 작업 폴더를 준다.
스킬(Skill) 조직 내부의 업무 방식, 규칙, 베스트 프랙티스를 에이전트에게 주입한다. 회사의 “비법”을 자동화 규칙으로 만든다.
MCP 도구(MCP tool) 로그, 인증, 데이터베이스, 외부 SaaS 등 다양한 시스템에 에이전트를 연결한다. 에이전트가 필요한 시스템에 직접 접근하게 한다.
최소 UX(Minimal UX) 개발자가 여러 창을 오가며 관리하는 부담을 줄인다. 하나의 화면에서 전체 루프를 오케스트레이션한다.
인간 검증자(Human verifier) 금융처럼 규제가 강한 환경에서는 책임성과 검증이 필수다. 인간은 처리량의 천장이 아니라 최종 검증자가 되어야 한다.
재귀적 자기 개선(Recursive self-improvement) 반복되는 실패와 병목을 에이전트가 학습해 루프 자체를 개선한다. 프로덕션 실패를 다음 자동화 개선의 입력으로 쓴다.

내가 모를 만한 것 / 처음 보는 것

  • Git 워크트리(Git worktree) — 하나의 Git 저장소에서 여러 작업 디렉터리를 동시에 만들어 각기 다른 브랜치나 작업을 병렬로 진행하는 기능.
  • 하네스(Harness) — 여기서는 에이전트를 개발·테스트·배포하기 위한 내부 개발 도구 묶음, 실행 환경, 자동화 파이프라인을 뜻한다.
  • 서브 에이전트(Sub-agent) — 큰 에이전트 시스템 안에서 특정 작업을 독립적으로 수행하는 작은 에이전트.
  • 스킬(Skill) — 조직의 규칙, 절차, 코드 패턴, 업무 지식을 에이전트가 재사용할 수 있게 만든 지침 또는 모듈.
  • MCP(Model Context Protocol) — 에이전트가 외부 도구, 서버, 데이터 소스와 연결되도록 하는 프로토콜 또는 통합 방식.
  • SOX 컴플라이언스(SOX compliance) — 미국 사베인스-옥슬리법 기반의 재무 보고·내부통제 규정. 금융·회계 시스템에서는 변경 승인과 책임 추적이 중요하다.
  • 원 페인 오브 글래스(One pane of glass) — 여러 시스템을 하나의 대시보드나 화면에서 통합해 보는 UX 개념.
  • 목표와 루프(Goals and loops) — 에이전트에게 목표를 주고, 반복 실행 루프를 통해 문제를 스스로 조사·수정·검증하게 하는 방식.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. 48GB RAM 맥북에서 50개 활성 워크트리 — 서브 에이전트 50개가 각자 독립 작업을 할 수 있다는 예시로 제시했다.
  2. 단계 1과 9에만 인간이 필요 — QA 버그 티켓 처리 흐름에서 처음 작업 확인과 마지막 스테이지 검증만 사람이 맡고, 중간 단계는 에이전트가 더 잘할 수 있다고 주장했다.
  3. QA 티켓 → 원인 분석 → 트레이스·로그 수집 → TDD → 수정 → PR → 리뷰 → 머지 → Docker 이미지 빌드 → 개발·스테이지 배포 — 화자가 제시한 실제 자동화 루프의 흐름이다.
  4. 목 회전 수 감소 — 여러 모니터와 창을 보며 개발자가 계속 컨텍스트 스위칭하는 문제를 “목을 돌리는 횟수”로 표현했다.
  5. 금융에서는 ‘빠르게 움직이고 깨뜨리기’가 다르다 — 규제, 승인, 감사, 책임 추적성 때문에 일반 스타트업식 속도전이 그대로 적용되지 않는다.
  6. 한두 날 동안 루프를 돌려 5~6개 버그 티켓을 처리한 뒤 병목을 분석 — 자기 개선 루프의 초기 운영 예시다.
  7. 한 달 뒤에는 ‘이 버그 고쳐줘’ 한 문장으로 동작하는 루프 — 개발 자동화 성숙도의 목표 상태를 설명했다.
  8. 고객 세션을 백그라운드에서 압축해 제품 개선 데이터로 사용 — 고객들이 반복적으로 겪는 패턴을 에이전트가 모아 기능 개선으로 연결하는 개념이다.

# 섹션 요지
1 문제 제기 프로덕션 에이전트의 병목은 모델이 아니라 개발자의 수동 루프다.
2 데모와 프로덕션의 차이 데모는 쉽지만 고객 데이터와 실제 버그가 들어오면 개발 속도가 중요해진다.
3 네 가지 기본 요소 서브 에이전트, 스킬, MCP 도구, 최소 UX가 핵심이다.
4 병렬 워크트리 전략 여러 QA 티켓을 독립 워크트리에서 서브 에이전트가 병렬 처리한다.
5 자동화된 개발 루프 로그 수집부터 PR, 빌드, 배포까지 중간 단계는 에이전트가 맡는다.
6 금융 분야의 책임 문제 규제 환경에서는 인간 검증과 감사 가능성이 여전히 필요하다.
7 인간을 루프에서 빼기 인간은 작업자가 아니라 검증자가 되어야 한다.
8 자기 개선 루프 프로덕션 실패를 입력으로 삼아 에이전트 개발 루프 자체를 개선한다.
9 결론 인간의 주의력을 처리량 한계로 만들지 말고, 에이전트에게 반복 작업을 넘겨야 한다.

1. 문제 제기: “금융 에이전트의 병목은 당신이다”

화자는 제목이 다소 공격적으로 들릴 수 있지만, 실제로 지적하려는 대상은 개인 개발자가 아니라 프로덕션 에이전트를 만드는 내부 개발 하네스(Harness)라고 설명한다.

Auditoria AI는 금융용 프로덕션 에이전트를 만드는 회사이고, 화자는 금융 에이전트 개발에서 가장 큰 문제를 모델 성능 부족이 아니라 개발자가 직접 관리하는 수동 개발 루프로 본다.

AI 데모는 이제 쉽게 만들 수 있다. 하지만 데모가 파일럿(Pilot)을 거쳐 실제 고객 온보딩으로 넘어가면, 에이전트는 처음 보는 데이터와 복잡한 예외 상황을 만나게 된다. 이때 프로덕션 버그가 빠르게 쌓인다.

핵심 질문은 이것이다.

  • 더 좋은 모델이 필요한가?
  • 더 빠른 GPU가 필요한가?
  • 더 나은 프레임워크가 필요한가?
  • 강화학습 루프(RL loop)가 문제인가?

화자는 이런 것들도 중요하지만, 실시간으로 프로덕션 버그를 고치는 데 가장 중요한 것은 개발 속도(Development velocity)라고 말한다.

2. 모델은 빨리 좋아지지만 개발 루프는 자동화해야 한다

새로운 모델은 몇 달마다 나온다. GPU와 칩도 시간이 지나면 더 빨라진다. 프레임워크도 매일 새로 등장한다.

하지만 프로덕션 버그를 실제로 고치는 과정은 여전히 개발자가 다음 작업을 반복한다.

  • 티켓 확인
  • 로그 확인
  • 원인 분석
  • 코드 수정
  • 테스트
  • PR 생성
  • 리뷰 요청
  • 배포
  • QA 확인 요청

모델 성능은 빠르게 올라가는데, 개발자가 매일 수동으로 처리하는 루프가 그대로라면 전체 속도는 크게 개선되지 않는다.

그래서 화자는 개발자들이 에이전트 하네스를 통해 생산성을 10배 높이는 방법을 고민해야 한다고 말한다.

3. 네 가지 기본 요소: 서브 에이전트, 스킬, MCP, 최소 UX

화자는 프로덕션 에이전트 개발 하네스에서 네 가지 기본 요소를 강조한다.

첫째, 서브 에이전트(Sub-agent)다.
요즘 에이전트 하네스는 여러 개의 하위 에이전트를 생성할 수 있다. 이들을 “에이전트 군단”처럼 운영하면 여러 작업을 동시에 처리할 수 있다.

둘째, Git 워크트리(Git worktree)다.
워크트리는 서로 격리된 폴더처럼 생각하면 된다. 각 폴더 안에서 에이전트가 코드를 작성하고 수정한다. 워크트리를 병렬로 사용하면 서브 에이전트들이 같은 파일을 두고 충돌하지 않고 독립적으로 작업할 수 있다.

셋째, 스킬(Skill)이다.
스킬은 조직의 비밀 레시피다. 회사 내부의 업무 방식, 코드 작성 규칙, 장애 대응 패턴, 고객별 처리 방식 등을 에이전트에게 주입하면 에이전트가 올바른 워크플로우를 따르게 된다.

넷째, MCP 도구(MCP tool)다.
에이전트는 로그 시스템, 인증 게이트웨이, 데이터베이스, 외부 SaaS 등 다양한 서드파티 서버와 연결되어야 한다. MCP는 이런 연결을 위한 통합 프레임워크 역할을 한다.

하지만 도구가 많아질수록 오케스트레이션이 복잡해진다. 그래서 화자는 최소 UX(Minimal UX)가 중요하다고 강조한다.

4. 서브 에이전트와 워크트리로 QA 티켓을 병렬 처리하기

화자는 예시로 48GB RAM이 있는 맥북에서 50개의 활성 워크트리를 운영할 수 있다고 말한다. 이는 50개의 서브 에이전트가 서로 다른 작업을 독립적으로 수행하는 구조다.

작업의 출처는 주로 다음과 같다.

  • QA가 보고한 버그
  • Jira 티켓
  • GitHub 이슈 또는 PR
  • 프로덕션 로그
  • 트레이스(Trace)

예를 들어 QA가 여러 버그 티켓을 올리면, 각 Jira 티켓을 별도의 워크트리에 배정한다. 각 워크트리는 별도 에이전트가 담당하고, 필요하면 그 에이전트가 다시 여러 서브 에이전트를 생성해 문제를 해결한다.

화자의 핵심 주장은 개발자가 작업을 직접 줄 세우지 말라는 것이다.
대기열 관리와 병렬 처리는 에이전트가 사람보다 더 잘할 수 있기 때문이다.

5. 자동화된 개발 루프: 사람은 1단계와 9단계만

화자는 QA 버그 처리 과정을 다음과 같이 설명한다.

  1. QA가 버그 티켓을 보고한다.
  2. 에이전트가 요구사항을 파악한다.
  3. 근본 원인 분석(Root cause analysis)을 한다.
  4. 트레이스와 로그를 수집한다.
  5. 별도 워크트리에 정보를 모은다.
  6. 테스트 주도 개발(TDD) 방식으로 수정한다.
  7. 로컬 테스트와 엔드투엔드 테스트를 실행한다.
  8. PR을 만들고 팀 리뷰에 제출한다.
  9. 리뷰 후 머지하고, Docker 이미지를 빌드해 개발·스테이지 환경에 배포한 뒤 QA에 검증을 요청한다.

화자는 이 과정에서 인간이 꼭 필요한 지점은 처음과 끝이라고 본다.

  • 처음: 에이전트가 어떤 작업을 하는지 확인
  • 끝: 스테이지 환경에 배포된 결과를 검증

중간의 반복적이고 기계적인 단계는 에이전트가 더 잘할 수 있다는 주장이다.

6. 최소 UX: 개발자의 컨텍스트 스위칭 줄이기

화자는 하나의 macOS 위젯 같은 대시보드를 예로 든다. 이 대시보드에는 다음 정보가 들어간다.

  • Kubernetes 서비스
  • Pod 상태
  • 예제 실행 결과
  • 애플리케이션 로그
  • 시스템 로그
  • Jira 티켓
  • GitHub PR
  • Claude Code 세션

개발자는 일반적으로 여러 모니터와 여러 창을 오가며 작업한다. 화자는 이를 “한 변경사항을 배포하기 위해 목을 돌리는 횟수”로 표현한다.

좋은 하네스는 여러 시스템을 하나의 화면, 즉 원 페인 오브 글래스(One pane of glass)로 압축해야 한다. 이렇게 해야 개발자는 에이전트를 관리하느라 다시 병목이 되지 않는다.

7. 금융 분야에서는 책임 추적성이 중요하다

Auditoria AI는 금융 분야에서 일하기 때문에 규제와 정책 문제가 중요하다.

AI가 없는 전통적인 방식에서는 다음 역할이 존재한다.

  • 인간 감사자(Auditor)가 코드를 검토한다.
  • 컨트롤러(Controller)가 SOX 컴플라이언스(SOX compliance)에 따라 승인한다.

문제는 에이전트가 에이전트를 검토하는 구조가 될 때 책임을 어디에 둘 것인가다. 프로덕션에서 문제가 생겼을 때 “Claude가 그렇게 했다”고 말할 수는 없다.

따라서 금융 분야에서 에이전트를 병렬로 운영하더라도 다음이 필요하다.

  • 누가 승인했는가
  • 어떤 에이전트가 무엇을 바꿨는가
  • 어떤 로그와 근거로 수정했는가
  • 어떤 테스트가 통과했는가
  • 최종 검증자는 누구인가

금융에서는 빠르게 움직이는 것도 중요하지만, 책임성과 검증 가능성이 함께 따라와야 한다.

8. 루프에서 개발자 빼기: 인간은 처리량의 천장이 아니다

화자는 앞부분에서 인간이 처음과 끝에는 필요하다고 말했지만, 후반부에서는 더 나아가 인간을 루프에서 점점 빼는 방향을 설명한다.

모델 성능이 향상되고 자기 개선(Self-improvement) 능력이 좋아지면, 내부 개발 하네스도 재귀적으로 개선될 수 있다.

방식은 이렇다.

  1. 프로덕션 실패를 모두 입력으로 모은다.
  2. 에이전트가 개발 루프를 며칠간 수행하게 한다.
  3. 예를 들어 1~2일 동안 5~6개 버그 티켓을 처리한다.
  4. 에이전트에게 전체 과정의 병목을 분석하게 한다.
  5. 병목 목록을 만들고 매일 조금씩 제거한다.

이 과정을 한 달 정도 반복하면, 개발자는 “이 버그 고쳐줘”라는 한 문장만 입력해도 에이전트가 필요한 시스템에 연결해 로그, 트레이스, 티켓을 모으고 QA 파이프라인까지 진행하는 상태에 가까워질 수 있다.

9. 목표와 루프: 노트북을 닫아도 돌아가는 작업

화자는 요즘 에이전트에게 목표(Goal)를 줄 수 있다고 말한다. 단순히 명령 하나를 수행시키는 것이 아니라, 목표를 설정하고 반복 루프를 돌릴 수 있다는 의미다.

예를 들어 다음과 같은 목표를 줄 수 있다.

  • “이 보고서에 데이터 불일치가 있다.”
  • “소스 데이터와 에이전트가 생성한 결과가 맞지 않는다.”
  • “원인을 조사하고 수정하라.”

에이전트는 목표를 기준으로 로그와 데이터를 확인하고, 반복적으로 문제를 좁혀가며 수정할 수 있다. 화자는 이제는 휴대폰에서도 이런 작업을 시작할 수 있고, 심지어 노트북을 닫아도 루프가 계속될 수 있다고 설명한다.

10. 고객 패턴을 제품 기능으로 바꾸기

화자는 “드리밍(Dreaming)”이라는 표현을 사용한다.
고객들이 프로덕션 소프트웨어를 사용하면서 같은 유형의 문제를 반복적으로 겪는다면, 에이전트가 백그라운드에서 고객 세션을 모으고 압축해 데이터 포인트로 만들 수 있다.

그 결과 시스템은 다음을 할 수 있다.

  • 반복되는 고객 문제를 감지한다.
  • 공통 패턴을 정리한다.
  • 제품 기능 개선 아이디어로 전환한다.
  • 내부 스킬이나 워크플로우를 업데이트한다.

즉 고객 사용 패턴이 에이전트의 자기 개선과 제품 개선으로 연결된다.

11. 결론: 인간은 검증자, 에이전트는 처리자

화자의 결론은 명확하다.

개발자는 더 이상 오전 9시부터 오후 5시까지 책상에 앉아 코드만 쓰는 역할로 남아 있기 어렵다. 에이전트가 더 잘할 수 있는 작업은 에이전트에게 넘겨야 한다.

핵심 구조는 다음과 같다.

  • 병렬 워크트리에서 서브 에이전트 팀을 운영한다.
  • 조직의 비밀 레시피를 스킬로 만든다.
  • 고객별 패턴도 에이전트에게 제공한다.
  • 로그, 인증, 데이터베이스 등 외부 시스템은 MCP 도구로 연결한다.
  • 모든 것을 하나의 화면으로 압축한다.
  • 목표와 루프를 설정해 자율성을 높인다.
  • 인간은 처리량의 한계가 아니라 최종 검증자가 된다.

가장 중요한 문장은 이것이다.

인간을 항상 검증자로 두되, 인간의 주의력이 전체 처리량의 천장이 되게 만들지 말라.

종합 체크리스트

  • [ ] 우리 회사의 QA 티켓 처리 과정에서 사람이 반복하는 단계를 목록화한다.
  • [ ] 버그 티켓 하나를 기준으로 로그 수집, 원인 분석, 테스트, PR 생성까지 자동화 가능한지 점검한다.
  • [ ] Git 워크트리(Git worktree)를 사용해 여러 버그 수정 작업을 병렬로 나눌 수 있는지 실험한다.
  • [ ] 조직 내부의 개발 규칙과 장애 대응 패턴을 스킬(Skill) 문서로 정리한다.
  • [ ] 에이전트가 접근해야 할 시스템 목록을 만든다: Jira, GitHub, 로그, DB, 인증, 배포 시스템.
  • [ ] MCP 도구(MCP tool)로 연결 가능한 시스템과 직접 연동이 필요한 시스템을 구분한다.
  • [ ] 개발자가 여러 창을 오가는 지점을 찾아 하나의 대시보드로 통합할 수 있는지 검토한다.
  • [ ] 금융·회계 업무라면 승인자, 변경 이력, 테스트 결과, 감사 로그를 반드시 남긴다.
  • [ ] 에이전트가 처리한 작업의 병목을 주기적으로 분석하게 한다.
  • [ ] 인간의 역할을 “직접 작업자”에서 “검증자”로 바꾸는 운영 원칙을 세운다.

안녕하세요, 여러분.

“왜 금융 에이전트의 병목이 바로 당신인가”라는 주제로 이야기하겠습니다. 제목이 조금 거칠게 들릴 수 있습니다. 여기 있는 청중 여러분을 직접 병목이라고 부르려는 뜻은 아닙니다. 제가 말하려는 것은 여러분이 프로덕션 에이전트를 만들기 위해 개발하고 사용하는 내부 하네스(Harness), 즉 개발 도구와 자동화 환경입니다.

제 이름은 Siddhant Emani이고, Auditoria AI에서 데이터 과학자(Data scientist)로 일하고 있습니다. 저희는 금융용 프로덕션 에이전트를 만듭니다. 혹시 이 자리에 CFO가 계시다면 세션 후에 꼭 이야기 나누고 싶습니다.

이 발표는 하네스 엔지니어링(Harness engineering)과 금융 AI(AI for finance)의 중간 지점에 있습니다. 핵심은 개발자 하네스 안의 병목을 찾는 것입니다. 개발자라면 지금 쓰는 에이전트 하네스로 어떻게 생산성을 10배 높일 수 있는지도 다룹니다.

우리는 AI 엔지니어 행사에서 멋진 데모를 많이 봤습니다. 하지만 데모가 파일럿으로 올라가고, 새 고객을 온보딩하기 시작하면 에이전트는 아직 본 적 없는 실제 데이터를 만나게 됩니다. 그때 프로덕션 버그가 많이 생깁니다. 프로덕션에서는 시간이 지날수록 처리해야 할 일이 계속 쌓입니다.

요즘은 코드를 작성하는 일이 쉬워졌습니다. 멋진 데모를 만들고 많은 사람에게 보여주는 것도 쉬워졌습니다. 그렇다면 무엇이 문제일까요? 왜 데모는 프로덕션에서 실패할까요? 모델이 문제일까요? GPT-5 같은 더 좋은 모델이 필요할까요? 더 빠른 GPU가 필요할까요? 더 나은 프레임워크가 필요할까요? 강화학습 루프(RL loop)가 제대로 작동하지 않는 걸까요?

답은 무엇일까요?

3개월 반 정도 기다리면 시장에 새 모델이 나옵니다. 그러면 모델은 쉽게 교체할 수 있습니다. 1년쯤 기다리면 새 칩과 더 빠른 GPU도 나옵니다. 코드를 쓰는 일도 쉬우니 프레임워크도 매일 새로 생깁니다. 원한다면 프레임워크도 계속 바꿀 수 있습니다.

그렇다면 실시간으로 프로덕션 버그를 어떻게 고칠 수 있을까요? 답은 개발 속도(Development velocity)입니다. 모델 능력은 매우 빠르게 증가합니다. 하지만 개발자는 매일 많은 시간을 들여 개발 루프(Developer loop)를 자동화해야 합니다.

저는 네 가지 기본 요소(Primitive)를 이야기하려고 합니다. 모두가 루프(Loop)를 생각해야 합니다. 이 세션이 끝날 때 여러분이 프로덕션 코드 생산성을 10배 높일 수 있기를 바랍니다.

첫째는 서브 에이전트(Sub-agent)입니다. 요즘 어떤 하네스를 사용하든 새 서브 에이전트를 생성할 수 있습니다. 이들을 군대처럼 많이 둘 수 있습니다. 그리고 Git 워크트리(Git worktree)는 가장 좋은 친구입니다. 워크트리는 격리된 폴더라고 생각하면 됩니다. 그 폴더 안에서 에이전트가 생성하는 코드를 작성합니다. 워크트리는 병렬로 돌아가야 합니다. 그래야 서브 에이전트들이 독립된 작업을 수행하고, 같은 것을 두고 충돌하지 않습니다.

둘째는 스킬(Skill)입니다. 이것은 조직의 비밀 레시피입니다. 스킬을 많이 만들어 두어야 합니다. 에이전트에게 스킬을 주면, 에이전트는 프로덕션 버그를 해결할 때 올바른 워크플로우를 사용하려고 합니다.

셋째로, 요즘 시장에는 MCP 도구(MCP tool)가 많이 나오고 있습니다. 사람들은 에이전트가 어떤 MCP 도구든, 어떤 서드파티 서버든 연결할 수 있다고 말합니다. 고객 데이터는 원하는 어떤 시스템에 있어도 됩니다. 결국 서브 에이전트가 많아지면 오케스트레이션해야 할 일도 많아집니다. 그래서 여기서는 최소 UX(Minimal UX)가 핵심입니다.

서브 에이전트를 살펴보겠습니다. 여러분이 오케스트레이터(Orchestrator)라고 하면, 예를 들어 48GB RAM이 있는 맥북에서 50개의 활성 워크트리를 둘 수 있습니다. 이는 50개의 활성 서브 에이전트가 서로 다른 작업을 독립적으로 수행한다는 뜻입니다. 그렇다면 이 작업들은 어디서 올까요?

배포하려는 프로덕션 소프트웨어에 QA가 보고하는 버그가 많다고 해봅시다. 모든 Jira 티켓을 서로 다른 워크트리로 생각할 수 있습니다. 각 워크트리는 별도 에이전트가 처리합니다. 그리고 그 에이전트들은 특정 작업을 해결하기 위해 여러 서브 에이전트를 다시 생성할 수 있습니다. 작업을 줄 세워 두고 싶어 하지 마십시오. 에이전트가 그것을 여러분보다 훨씬 잘할 수 있습니다.

예시 하네스를 보겠습니다. QA가 많은 버그 티켓을 보고했다고 합시다. 어떤 에이전트가 마치 마법처럼 요구사항을 파악하고, 근본 원인 분석(Root cause analysis)을 하고, 모든 트레이스(Trace)와 로그(Log)를 가져옵니다. 그것을 별도 워크트리에 넣고, 테스트 주도 개발(TDD)을 하고, 수정 사항을 구현합니다. 로컬 시스템에서 작업하므로 테스트 스크립트와 로컬 엔드투엔드 테스트도 실행해야 합니다. 이후 PR을 만들고 팀에 리뷰를 요청합니다. 리뷰 후에는 마스터 브랜치에 머지한다고 해봅시다.

머지한 뒤에는 당연히 Docker 이미지를 빌드하고, 개발 환경에 배포하고, 테스트합니다. 다시 이미지를 빌드해 스테이지 환경으로 보내고, 테스트하고, 스테이지에 배포합니다. 그런 다음 QA에게 “이제 테스트해도 됩니다”라고 알려줍니다.

여기서 청중에게 질문하고 싶습니다. 이 1단계부터 9단계 중 어느 지점에서 사람이 필요하다고 생각하십니까?

저는 사람은 1단계와 9단계에만 필요하다고 봅니다. 중간 단계는 에이전트가 훨씬 더 잘할 수 있습니다. 처음에는 에이전트가 어떤 일을 하는지 사람이 봐야 합니다. 마지막에는 스테이지에 배포된 뒤 사람이 결과를 검증해야 합니다. 그리고 사람은 최소 UX를 좋아하기 때문에 최소 UX가 필요합니다.

화면 이미지를 자세히 보면, 여러분이 만들고 있는 프로덕션 에이전트 소프트웨어와 프로젝트 대시보드가 보입니다. 여기에는 Kubernetes 서비스, Pod, 예시, 로그, 시스템 로그, Jira 티켓, GitHub PR, 그리고 아래쪽의 Claude Code 세션 같은 것이 들어 있습니다.

이것은 기본적으로 macOS 위젯 같은 것입니다. 이 모든 일을 하기 위해 여러 창을 열 필요가 없습니다. 개발자는 소프트웨어 생명주기 안에서 다양한 일을 합니다. 그래서 하나의 위젯만으로 많은 일을 처리할 수 있습니다.

그래프에서도 볼 수 있듯이, 하나의 변경 사항을 배포하기 위해 목을 돌리는 횟수가 크게 줄어듭니다. 여러분도 책상에 모니터가 두세 개 있을 것입니다. 그리고 에이전트들을 오케스트레이션하느라 계속 목을 돌리고 있을 것입니다.

Auditoria는 금융 분야에서 일합니다. 그래서 지금 금융에는 많은 규제와 정책이 있습니다. 그렇다면 금융 분야에서 서브 에이전트 팀을 오케스트레이션하는 것은 어떤 모습일까요?

AI를 제외하고 보면, 보통은 인간 감사자(Auditor)가 코드를 검토하고, 컨트롤러(Controller)가 SOX 컴플라이언스(SOX compliance)에 따라 승인합니다. 그런데 에이전트가 에이전트를 검토한다면 책임은 어디에 둬야 할까요? 프로덕션에서 문제가 생겼을 때 “Claude가 이렇게 했고 뭔가 잘못됐다”고 말할 수는 없습니다.

하지만 이런 서브 에이전트와 하네스를 사용해 실시간으로 버그를 고친다고 해봅시다. 이때 병목은 무엇일까요? 바로 인간의 주의력(Human attention)입니다. 여러분 자신이 서로 다른 작업을 모두 오케스트레이션해야 하기 때문입니다. 그리고 금융 분야에서 “빠르게 움직이고 깨뜨리기”는 다른 분야와 많이 다릅니다.

이제 두 번째 부분, 즉 루프에서 자기 자신을 제거하는 이야기를 하겠습니다.

지금까지 저는 에이전트가 무엇을 하는지 사람이 봐야 하고, 마지막에도 사람이 검증해야 한다고 말했습니다. 하지만 요즘은 에이전트의 자기 개선(Self-improvement)과 모델 능력이 좋아지고 있습니다. GPT-5와 다른 새로운 모델도 나오고 있습니다.

그렇다면 내부 개발자 하네스에서 재귀적 자기 개선(Recursive self-improvement)이 일어나면 어떤 모습일까요? 모든 프로덕션 실패가 입력이 됩니다. 매일 개발 하네스를 자동화하고, 에이전트에게 본질적으로 자기 자신을 업그레이드하라고 요청한다고 해봅시다. 작업을 하나 수행하고 루프를 하루나 이틀 돌립니다. 버그 티켓 5~6개를 해결합니다. 그런 다음 에이전트에게 이 과정의 모든 병목을 분석하고 목록으로 만들라고 합니다. 그리고 매일 조금씩 그 병목을 제거하게 합니다.

한 달이 지나면, 예를 들어 “이 버그 고쳐줘”라고 한 문장만 입력해도 되는 꽤 좋은 자동화 루프가 생깁니다. 에이전트는 여러 데이터베이스 시스템에 연결하고, 로그와 트레이스와 티켓을 가져오고, 그것을 Jira에서 QA로 이어지는 파이프라인으로 옮깁니다. 그러면 여러분은 휴가를 예약하거나 재택근무를 할 수도 있습니다.

내부적으로는 어떤 모습일까요? 덜 조종하고 더 많이 배포하면 어떤 일이 일어날까요? 요즘 에이전트에게 목표(Goal)를 줄 수 있다는 것을 아는 분이 얼마나 됩니까? 목표를 설정하고 잊어버릴 수 있습니다.

목표와 루프를 결합하면 어떻게 될까요? 예를 들어 어떤 보고서에 데이터 불일치가 있고, 프로덕션 버그에서 원본 데이터와 에이전트가 생성한 결과가 맞지 않는다고 합시다. 그러면 “이 문제를 고쳐라, 조사하라”는 목표를 설정하고 루프를 돌릴 수 있습니다. 요즘은 휴대폰에서도 할 수 있으니 노트북을 닫아도 됩니다.

마지막에서 두 번째 포인트는 드리밍(Dreaming)입니다. 많은 고객이 프로덕션 소프트웨어를 사용하면서 같은 유형의 패턴을 보이고 같은 유형의 문제를 겪는다고 합시다. 그러면 에이전트가 인간이 꿈꾸듯 백그라운드에서 꿈꾸게 할 수 있습니다. 고객들이 사용하는 모든 세션을 모으고, 시스템이 사용할 수 있는 데이터 포인트로 압축합니다. 그리고 기본적으로 시스템이 자기 자신을 업그레이드하게 합니다.

이런 기능들을 결합하면 기본적으로 자기 자신을 루프 밖으로 제거할 수 있습니다. 하지만 앞서 말했듯이 개발자는 소프트웨어 개발 생명주기에서 매우 다양한 일을 합니다. 오전 9시부터 오후 5시까지 책상 뒤에 앉아 코드만 쓰는 방식은 더 이상 유효하지 않습니다.

지금까지 다룬 내용을 정리하겠습니다. 병렬 워크트리에서 일하는 서브 에이전트 팀을 둘 수 있습니다. 스킬, 즉 조직의 비밀 레시피와 고객의 레시피를 둘 수 있습니다. 이 모든 것을 에이전트에게 줄 수 있습니다. 에이전트는 어떤 서드파티 서버에도 연결될 수 있습니다. 그것은 로그 시스템일 수도 있고, 인증 게이트웨이일 수도 있습니다. 그리고 이 모든 것을 하나의 화면(One pane of glass)으로 압축해야 합니다. 최소 UX가 핵심이기 때문입니다. 목표와 루프를 설정해 자율성을 만들 수도 있습니다.

어떤 작업이 에이전트가 훨씬 더 잘할 수 있는 일이라고 생각된다면, 그 일을 에이전트에게 보내면 됩니다. 항상 인간을 검증자(Verifier)로 두십시오. 하지만 인간을 처리량의 천장(Throughput ceiling)으로 만들지는 마십시오. 인간의 주의력은 매우 제한되어 있기 때문입니다.
