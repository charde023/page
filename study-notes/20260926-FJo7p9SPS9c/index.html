AI 에이전트와 함께하는 스펙 주도 개발 풀코스 강의

업로드 2026-09-26 · 61.5분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 11분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 강의의 중심 생각은 간단하다. AI 코딩 에이전트가 코드를 빠르게 작성할수록 사람은 코드를 어떻게 쓸지 일일이 지시하는 사람보다 무엇을 왜 만들어야 하며 무엇을 만족해야 하는지 정하는 사람에 가까워져야 한다. 이때 사람의 의도와 제약을 지속해서 보존하는 문서가 명세이고, 그 문서를 중심으로 개발하는 방식을 스펙 주도 개발(Spec-Driven Development, SDD)이라고 부른다.

강의는 프로젝트 전체의 방향을 적은 프로젝트 헌법을 먼저 만들고, 각 기능을 계획 → 구현 → 검증 순서로 개발한 뒤, 기능 사이에서 헌법과 로드맵을 고치는 재계획 단계를 두라고 제안한다. 에이전트는 빠르게 코드를 만들지만 프로젝트의 사업 배경과 사람이 중요하게 여기는 선택을 저절로 알지는 못한다. 그래서 사람은 에이전트가 모르는 목표·대상·제약·성공 기준을 명세에 남기고, 결과가 그 계약을 지켰는지 검토해야 한다.

읽는 법: 왼쪽에서 오른쪽으로 한 번 진행하고 끝나는 선형 절차가 아니다. 기능을 하나 끝낼 때마다 재계획 결과가 헌법과 다음 기능 명세로 돌아간다. 이 도식은 수치를 나타내는 그래프가 아니라 강의가 제안한 작업 관계를 정리한 개념 지도다.

왜 짧은 프롬프트만으로는 부족해지는가

강의는 “버튼 하나 만들어 줘”처럼 높은 수준의 요청을 보내고 결과를 보며 계속 고치는 방식을 바이브 코딩의 예로 든다. 작은 버튼이라면 이런 방식도 쓸 수 있다. 그러나 프로젝트가 커지면 대화가 길어지고, 서로 다른 개발자가 서로 다른 에이전트에게 요청하면서 결정이 엇갈릴 수 있다. 대화 기록이 사라지거나 작업 기억이 복잡해지면 이전에 합의한 중요한 조건도 흐려진다.

강의가 말하는 해결책은 대화를 없애는 것이 아니다. 중요한 대화의 결론을 Markdown 명세로 남겨 영구적인 기술 산출물로 바꾸는 것이다. 사람은 에이전트와 대화하며 선택지를 검토하고, 결정된 목표·제약·성공 기준을 문서로 요약하게 한다. 이후 에이전트는 그 문서를 기준으로 계획하고 코드를 만든다.

읽는 법: 오른쪽이 언제나 무조건 낫다는 표가 아니다. 강사도 짧은 프롬프트로 충분한 일에는 “게으른 프롬프팅”이 괜찮다고 말한다. 차이는 작업 규모가 커졌을 때 의도와 결정이 지속되는가에 있다.

명세가 맡는 세 가지 역할

강의는 SDD의 이점을 세 가지로 설명한다.

첫째, 명세의 작은 수정이 코드의 큰 변화를 통제한다. 예를 들어 명세의 데이터베이스 선택을 SQLite와 Prisma ORM에서 MongoDB로 바꾸면 그 결정이 많은 코드에 영향을 줄 수 있다. 따라서 사람이 모든 코드를 직접 고치기보다 상위 결정을 정확하게 고치는 편이 효율적이라는 주장이다.

둘째, 명세는 세션 사이에 중요한 맥락이 흐려지는 문제, 즉 맥락 감쇠(context decay)를 줄이는 기준점이 된다. 강의는 에이전트를 “상태가 없다”고 표현하면서도 한 세션 안에서는 작업 기억이 가득 차 실수가 늘 수 있다고 설명한다. 핵심은 에이전트의 기억에만 의존하지 말고, 반드시 지켜야 할 결정을 파일로 남기라는 뜻으로 읽는 것이 안전하다.

셋째, 명세는 결과가 사람의 의도와 맞을 가능성, 즉 의도 충실도(intent fidelity)를 높인다. 문제, 성공 기준, 제약, 사용자 흐름을 먼저 쓰면 에이전트가 빈칸을 임의로 채울 범위가 줄어든다. 다만 강의는 명세가 결과를 자동으로 보장한다고 말하지 않는다. 사람이 질문에 답하고, 문서를 검토하고, 실제 결과를 검증하는 과정이 계속 필요하다.

프로젝트 헌법에는 무엇을 쓰는가

프로젝트 헌법은 법률 문서가 아니라 프로젝트 전체에 적용할 상위 기준이다. 강의에서는 다음 세 부분을 사용한다.

  • 미션: 왜 만드는지, 누구를 위한 것인지, 범위와 방향은 무엇인지 적는다.
  • 기술 스택: 개발과 배포에 사용할 기술 및 제약을 합의한다.
  • 로드맵: 어떤 기능을 어떤 단계로 개발할지 기록하며, 진행하면서 수정한다.

강의의 실습 프로젝트는 AI 에이전트를 치료한다는 설정의 Agent Clinic이다. TypeScript와 Git으로 시작해 Next.js 백엔드와 React 프런트엔드를 사용하는 전체 웹 앱으로 설명된다. 에이전트와 대화한 뒤 mission.md, techstack.md, roadmap.md 세 파일을 만들고 사람이 검토한다. 빠른 시제품이라는 이유로 SQLite를 선택한 것도 기술 스택에 반영한다.

여기서 중요한 것은 에이전트가 처음부터 정답을 만들었다고 가정하지 않는 점이다. 실제 예에서 에이전트가 작성한 미션에는 대상 고객이 빠져 있었다. 강사는 직접 한 파일만 고치기보다 에이전트에게 관련 문서들을 함께 수정하게 해 산출물 사이의 불일치를 줄이라고 권한다.

각 기능은 작은 계약으로 개발한다

프로젝트 헌법이 전체 지도라면 기능 명세는 이번 작업의 계약이다. 강의에서는 기능마다 계획, 요구사항, 검증 기준을 만들고 별도 브랜치에서 작업한다.

읽는 법: 각 상자는 다음 상자로 넘어가기 위한 점검 지점이다. 특히 구현과 검증을 한 덩어리로 보지 않는다. 변경이 너무 크면 구현을 더 작은 작업 그룹과 커밋으로 나눈다.

첫 기능인 Hello Nano에서는 범위, 엄격한 TypeScript 사용, 수동 curl 검증 등을 먼저 정한다. 에이전트가 계획·요구사항·검증 문서를 작성하면 사람이 검토하고 커밋한 다음 구현한다. 구현 후에는 홈페이지에 header, main, footer의 명확한 구조가 필요하다는 점이 발견된다. 강의는 이것을 단순한 코드 실수로만 보지 않고 계획에 빠진 요구라고 판단해 명세와 코드 모두를 수정한다.

이것이 휴먼 인 더 루프(human-in-the-loop)다. 에이전트가 만들고 검사한 결과라도 사람이 고수준 요구사항과 실제 동작을 확인한다. 에이전트가 빠르게 많은 코드를 만들수록 사람이 코드의 구조와 변화 과정을 따라가지 못하는 인지 부채(cognitive debt)가 생길 수 있기 때문이다. 강의는 이를 줄이기 위해 작은 변경, 잦은 커밋, 기능 사이의 깨끗한 구분, 테스트와 디버거를 이용한 탐색을 권한다.

재계획은 뒤처리가 아니라 학습 단계다

첫 기능을 끝낸 뒤 강의는 곧바로 다음 기능을 만들지 않는다. 테스트 정책을 프로젝트 헌법에 추가하고, 기존 기능 명세와 구현에도 반영한다. 제품 관리자에게서 “사용자의 40%가 모바일을 쓴다”는 업데이트가 왔다는 예시에서는 반응형 디자인을 제품 명세·기능 명세·코드에 함께 반영한다. 이 40%는 강의 속 사례 수치이며 독립적으로 검증된 통계는 아니다.

변경이 작으면 재계획 단계에서 바로 반영할 수 있지만, 크면 로드맵의 독립 기능으로 잡으라고 설명한다. 즉 재계획은 무엇이든 끼워 넣는 단계가 아니라, 새 정보의 크기와 위험을 보고 다음 작업 구조를 다시 정하는 단계다.

두 번째 기능 Agents and Ailments에서는 일반 SQL, PicoCSS, 별도의 TypeScript 속성 타입 같은 선택이 진행 중에 추가된다. 강의는 처음 명세에서 빠진 사항을 무조건 실패로 보지 않는다. 구현과 검토를 통해 새 결정을 발견했다면 그 결정을 명세에 되돌려 다음 결과를 개선해야 한다고 본다.

새 프로젝트뿐 아니라 기존 코드에도 적용한다

새로 시작하는 프로젝트를 그린필드, 이미 코드가 있는 프로젝트를 브라운필드라고 한다. 강의는 두 경우 모두 헌법과 기능 반복을 쓸 수 있다고 주장한다.

차이는 헌법을 만드는 출발점이다. 그린필드에서는 사람과 에이전트가 목표와 선택을 대화로 정한다. 브라운필드에서는 에이전트가 기존 코드, README, TODO, 커밋과 다른 문서를 살펴 프로젝트의 미션·기술 스택·로드맵을 역으로 정리한다. 이것은 기존 프로젝트의 진실을 자동으로 찾아냈다는 뜻이 아니다. 사람이 추출된 헌법을 검토하고 빠진 배경이나 잘못된 추정을 고쳐야 한다.

반복되는 절차는 기술로 묶되 책임은 남는다

강의 후반부는 기능 명세 작성이나 변경 기록 갱신처럼 반복되는 절차를 에이전트 스킬로 묶는 방법을 보여준다. 스킬은 특정 작업을 수행하는 지침과 자료의 묶음이다. 프로젝트 안에서만 쓰거나 여러 프로젝트에서 공유할 수 있다.

외부 도구 연결에는 MCP, 프로젝트 규칙에는 AGENTS.md, 반복 작업에는 Agent Skills, 에이전트와 편집기 연결에는 ACP를 소개한다. GitHub Spec Kit과 Fission AI의 OpenSpec도 SDD 흐름을 형식화한 사례로 제시한다. 강의의 방향은 특정 IDE나 에이전트에 종속되지 않는 명세와 절차를 만들자는 것이다.

읽는 법: 위쪽일수록 사람이 보존해야 할 장기 기준이고, 아래쪽일수록 교체 가능한 구현 수단이다. 강의의 주장은 에이전트나 IDE를 바꾸더라도 상위 명세와 검증 흐름을 유지할 수 있어야 한다는 것이다. 다만 소개된 표준과 도구가 실제로 모든 조합에서 같은 수준으로 작동하는지는 강의만으로 검증되지 않는다.

결국 SDD는 “길고 자세한 프롬프트를 쓰는 법”만을 뜻하지 않는다. 프로젝트 전체 기준을 문서화하고, 기능을 작은 계약으로 나누고, 구현을 검증하며, 새로 배운 결정을 다시 명세에 반영하는 운영 방식이다. 너무 단순한 일에는 짧은 요청이 더 나을 수 있고, 명세를 지나치게 세밀하게 써 변수명까지 통제하면 에이전트의 장점을 잃을 수 있다. 좋은 명세는 에이전트가 이미 알 수 있는 저수준 구현보다 에이전트가 알 수 없는 사업 목적, 사용자, 제약, 성공 기준과 중요한 선택에 집중한다.

여기까지만 이해하면 충분

  • SDD는 코드를 직접 통제하기보다 목표·제약·성공 기준을 명세에 남겨 에이전트의 빠른 구현을 통제하는 방식이다.
  • 프로젝트 헌법은 미션·기술 스택·로드맵을 담고, 각 기능은 계획 → 구현 → 검증 → 재계획의 반복으로 개발한다.
  • 에이전트가 생성하고 검사했더라도 사람은 작은 변경 단위로 결과를 이해하고 승인해야 한다.
  • 명세는 새 프로젝트와 기존 프로젝트 모두에 쓸 수 있지만, 결과 품질과 도구 독립성은 실제 작업에서 검증해야 한다.

오늘 대답할 질문

AI 코딩 에이전트가 빠르게 많은 코드를 만들 때, 스펙 주도 개발은 어떻게 사람의 의도와 통제력을 유지하는가?

  • 프로젝트 헌법과 기능 명세는 각각 무엇을 보존하는가?
  • 사람의 검증과 재계획은 왜 구현 뒤에도 필요한가?
  • 어떤 작업은 짧은 프롬프트로 처리하고, 어떤 작업은 명세 반복으로 관리해야 하는가?

설계도와 건축 현장

프로젝트 헌법과 기능 명세는 건축가의 설계도에, 에이전트는 빠르게 시공하는 작업자에 대응한다. 사람은 목적과 제약을 설계하고, 공사를 감독하고, 결과를 승인하거나 수정을 요청한다.

비유가 깨지는 지점: 소프트웨어 명세는 공사 전에 완전히 고정된 설계도가 아니다. 구현과 검증 중 발견한 내용을 명세에 되돌려 계속 바꾸며, 에이전트도 단순 시공자가 아니라 질문·계획·검증에 참여한다.

1. 명세의 핵심 가치는 길이가 아니라 지속성이다

  • [해석] 좋은 명세는 모든 구현 세부를 길게 적는 문서가 아니라, 에이전트가 알 수 없는 목표·제약·성공 기준과 중요한 선택을 지속 가능한 형태로 보존하는 문서다.

2. 검증은 실행 성공보다 사람이 이해하고 승인하는 데 가깝다

  • [원문] 강의는 에이전트의 자체 검증 뒤에도 사람이 변경 내용을 검토하고 앱·테스트·디버거를 사용하며, 필요하면 여러 하위 에이전트에 재검토를 요청하는 사례를 보여준다.
  • [해석] 자동 테스트 통과와 에이전트의 완료 보고는 검증의 일부일 뿐이다. 사람이 명세와 실제 동작의 일치 여부를 설명할 수 있어야 변경을 통제하고 있다고 볼 수 있다.
  • [경계] 에이전트가 수행한 재검토는 동일한 도구 계열의 또 다른 판단일 수 있으므로 독립 증거라고 단정할 수 없다. 강의에는 결함 발견률이나 검토 비용을 비교한 수치가 없다.

1. SDD의 문제의식

강의 도입부는 JetBrains와의 협력으로 제작된 과정이라고 소개한다. Andrew라고 불린 도입 화자가 강사 Paul Everett을 JetBrains의 개발자 애드버킷으로 소개한다. 성은 전사에 나오지 않는다.

강사는 SDD의 이점을 다음 세 가지로 설명한다.

  1. 명세의 짧은 변경으로 많은 코드 변경을 통제할 수 있다.
  2. 세션 사이의 맥락 감쇠를 줄이고 반드시 지켜야 할 결정을 보존한다.
  3. 문제·성공 기준·제약·사용자 흐름을 먼저 정해 의도 충실도를 높인다.

예시로 “SQLite와 Prisma ORM을 사용한다”는 한 문장이 수백 줄의 코드에 영향을 줄 수 있고, 이를 MongoDB로 바꾸면 하위 구현도 크게 바뀔 수 있다고 말한다. 또 에이전트가 20~30분 동안 코드를 작성해 전통적인 개발자의 몇 시간에 해당하는 작업을 한다면, 사람이 3~4분 동안 명확한 지침을 쓰는 편이 나을 수 있다고 주장한다. 이 시간 비교는 강사의 경험적 예시이며 측정 조건은 제시되지 않는다.

짧은 요청으로 충분한 작업에는 짧은 프롬프트를 지지하지만, 복잡한 프로젝트에서는 세부 명세가 유지보수성과 일관성을 높인다고 주장한다. 명세 없이 여러 개발자와 에이전트가 작업하면 빠르게 만들더라도 서로 모순되는 구현이 생길 수 있다는 팀 사례를 언급한다.

과정 기여자로 JetBrains의 Konstantin Chaikur, Zina Smirnova와 DeepLearning.AI의 Isabel Zarro를 언급한다. 이름 철자는 제공된 전사를 따른다.

2. 바이브 코딩과 명세의 차이

강의는 “버튼을 만들어 달라”는 요청 후 결과를 보고 계속 수정하는 과정을 바이브 코딩의 예로 든다. 작은 요소에는 작동할 수 있지만 장기 프로젝트에서는 대화가 길어지고 기록이 남지 않으며 기술 부채가 쌓일 수 있다고 말한다.

SDD에서는 무엇과 왜를 설명하는 명세와 어떻게 구현할지를 분리한다. 명세는 사람 사이의 계약이면서 사람과 에이전트 사이의 계약으로 취급된다. 사람은 수석 설계자처럼 목표와 청사진을 제공하고, 에이전트는 기술 지식과 구현 속도를 제공한다는 역할 구분이다.

강의는 이를 컴파일러에 비유한다. 컴파일러가 사람이 읽을 수 있는 소스 코드를 기계 코드로 바꾸듯, SDD는 사람이 읽을 수 있는 명세에서 에이전트가 소스 코드를 만들도록 안내한다. 다만 SDD가 결정론적인 변환을 보장한다는 뜻으로 설명되지는 않는다.

3. 프로젝트 헌법과 Agent Clinic

헌법은 다음 세 요소로 구성된다.

  • 미션: 비전, 대상, 범위와 프로젝트의 이유
  • 기술 스택: 개발·배포 기술과 제약
  • 로드맵: 기능 단계의 순서와 진행 계획

실습에서는 WebStorm과 Claude Code를 사용하지만, VS Code와 Codex CLI, Zed Editor와 로컬 모델도 사용할 수 있다고 말한다. SDD 자체는 특정 IDE나 에이전트에 묶이지 않는다는 주장이다.

실습 프로젝트 Agent Clinic은 AI 에이전트가 인간에게 받은 스트레스와 환각, 맥락 손상, 기억 문제, 하위 에이전트 협업 문제를 치료받는다는 패러디 앱이다. Next.js 백엔드와 React 프런트엔드를 가진 전체 웹 앱이며 예약, 질환, 치료를 관리한다고 설명한다.

에이전트에게 README의 이해관계자 입력을 읽고 미션·기술 스택·로드맵을 함께 작성하게 한다. 질문에 답한 뒤 mission.md, techstack.md, roadmap.md 세 파일을 만든다. 사람이 검토하면서 빠진 대상 고객을 보완하고, 빠른 시제품이라는 이유로 SQLite를 기술 스택에 넣은 뒤 헌법을 커밋한다.

강의는 명령 실행 권한을 요청받을 때 주의하라고 말한다. 안전하지 않은 모드로 실행하지 않는 한 명령마다 승인을 요구하며, 코드에 대한 최종 책임은 사람에게 있다고 강조한다.

4. Hello Nano 기능의 계획·구현·검증

첫 기능은 Phase 1의 Hello Nano다. 별도 브랜치에서 기능의 계획, 요구사항, 검증 점수표를 에이전트와 작성한다. 범위는 로드맵 그대로 유지하고, Nano 버전을 고정하며, 엄격한 TypeScript를 적용하고, 수동 curl로 확인하기로 정한다.

기능 명세를 검토하며 보기 좋은 임시 홈페이지 요구를 추가한다. 강사는 변수명처럼 사소한 구현 세부까지 요구사항에서 지시하지 말라고 말한다. 통제하되 지나치게 조종하지 않는 균형이 필요하다는 설명이다.

구현 전 /clear로 에이전트 문맥을 비운다. 보안이나 데이터베이스처럼 작은 오류가 누적될 수 있는 영역은 작업 그룹별로 구현하고 커밋하는 방법을 권한다.

구현 뒤에는 바로 병합하지 않고 커밋 차이를 검토한다. 홈페이지에 레이아웃 구성요소가 빠진 것을 발견하고, 원인이 계획의 누락이라고 판단한다. 계획에 새 작업 그룹을 추가하고 코드도 수정한다. header, main, footer 세 하위 구성요소를 별도 파일로 옮길 때도 IDE에서 코드만 이동하지 않고 관련 명세와 README를 에이전트가 확인하게 한다.

5. 재계획과 인지 부채

에이전트의 빠른 생성량을 사람이 따라가기 어려운 정신적 부담을 강의는 인지 부채라고 부른다. 작은 변경, 잦은 커밋, 기능별 브랜치, 테스트와 디버거를 통한 탐색으로 부담을 줄이라고 제안한다.

첫 기능 뒤에는 테스트 선호 사항이 헌법에 없었다는 점을 발견한다. 재계획 브랜치에서 테스트 프레임워크 정책을 추가하고, 기존 기능 명세와 구현에도 반영한 뒤 실제 테스트를 작성한다.

제품 관리자가 사용자의 40%가 모바일이라고 알려왔다는 사례를 통해 반응형 디자인을 제품 명세, 기능 명세, 코드에 함께 반영한다. 작은 변경이라 재계획에서 바로 처리하지만 큰 변경이면 별도 로드맵 기능으로 잡으라고 설명한다.

로드맵의 기능 2, 3, 4, 5가 서로 묶인다고 판단해 한 단계로 합친다. 이는 네 개의 번호가 열거된 것이며 수량 불일치는 없다.

변경 기록을 자동으로 갱신하기 위해 Changelog 스킬을 만든다. 이 스킬은 전역 영역에 설치되어 여러 프로젝트에서 사용할 수 있게 된다. 반복 가능한 검증 작업도 README 갱신, 린트, 포맷, 테스트 실행 등을 묶은 스킬로 만들 수 있다고 제안한다.

6. Agents and Ailments와 MVP

다음 기능에 들어가기 전 미완료 작업, 이전 브랜치 병합, 다음 로드맵 항목, 에이전트 문맥 초기화를 점검한다. 두 번째 기능인 Agents and Ailments에서는 관련 기능을 한 단계로 유지하고, 마이그레이션에 일반 SQL을 선택하며, 여러 검증 항목을 정한다.

계획 중 PicoCSS를 사용하기로 추가하고, 구현 검토 중에는 속성 타입을 인라인으로 두지 않고 독립 TypeScript 타입으로 분리하기로 한다. 강의는 처음 명세에서 빠졌다고 해서 바로 실패로 보지 않고, 새 결정을 명세에 기록해 미래 결과를 개선하라고 말한다.

검증 단계에서는 테스트를 읽고 디버거로 실행하며 흐름을 이해한다. 여러 하위 에이전트에 프로젝트 전체의 깊은 검토를 요청하고, 나온 문제와 권고를 적용한 뒤 테스트를 다시 실행한다.

이후 남은 로드맵 전체를 구현해 MVP를 만드는 큰 실험을 한다. 강의는 헌법과 명세의 품질에 확신이 있고 사람이 대규모 결과를 검토할 수 있을 때만 이런 큰 작업을 하라고 경고한다. 결과가 예상과 다르면 무엇이 에이전트를 잘못 이끌었는지 재계획 단계에서 찾아야 한다.

7. 기존 코드에 SDD 도입

기존 Agent Clinic MVP에서 명세 폴더를 제거한 상태를 레거시 프로젝트처럼 취급한다. README와 TODO, 코드 구조를 에이전트가 탐색해 미션·기술 스택·로드맵을 작성한다.

기존 코드에서 프레임워크 버전과 파일 구조를 추출하고, TODO의 작업을 로드맵 단계로 정리한다. 이후 피드백 폼 기능을 별도 브랜치에서 계획·구현·검증하고 병합한다.

강의는 이 과정이 기존 코드에 대한 수동 문서 작업을 줄여준다고 주장한다. 그러나 추출된 헌법이 실제 사업 의도와 일치하는지는 사람이 검토해야 한다. 코드에 없는 배경은 역분석만으로 알 수 없기 때문이다.

8. 스킬, MCP, CLI와 SDD 도구

반복하던 기능 명세 프롬프트를 스킬 생성 도구와 대화해 Agent Skill로 만든다. 스킬은 프로젝트 전용 또는 전역으로 둘 수 있고, 다른 스킬이 호출할 수도 있다. 에이전트가 설명을 보고 스킬 사용 여부를 판단하는 과정을 점진적 공개라고 설명하지만, 문맥이 커지면 판단이 완벽하지 않으므로 원하는 스킬을 직접 이름으로 지정하라고 권한다.

외부 API, 사설 지식 저장소, 데이터베이스 접근에는 MCP를 소개한다. Context7을 예로 들어 MCP 서버 대신 CLI와 스킬을 사용하는 설치 방식을 보여준다. “MCP 서버에서 스킬과 CLI로 이동하는 추세가 빨라지고 있다”는 평가는 강의의 주장이다.

Qodo Code의 플러그인, GitHub Spec Kit, Fission AI의 OpenSpec도 소개한다. Spec Kit의 /speckit.constitution, /speckit.plan, /speckit.tasks, /speckit.implement 명령과 OpenSpec의 propose, explore, apply, archive 흐름을 SDD 구현 사례로 설명한다. 플러그인은 코드를 실행할 수 있으므로 설치와 업데이트 시 신뢰 여부를 확인하라고 경고한다.

기능 개발 중 확정되지 않은 데이터베이스 아이디어를 연구할 때는 바로 로드맵에 넣지 않고 정해진 위치의 백로그 보고서로 남긴다. 나중에 링크와 함께 로드맵에 배치하거나 연구 절차를 스킬로 자동화할 수 있다.

9. 에이전트와 IDE를 바꾸는 표준

강의는 상위 명세가 특정 에이전트나 IDE에 묶이지 않아야 한다고 설명한다.

  • MCP: 외부 도구와 자원 연결
  • AGENTS.md: 프로젝트 규칙
  • Agent Skills: 반복 가능한 절차와 추가 맥락
  • ACP: 에이전트와 클라이언트 연결

Claude Code에서 만든 기능 명세 스킬을 다른 경로에 복사해 Codex에서 실행하는 사례를 보여준다. ACP를 사용해 에이전트와 편집기를 연결하고, JetBrains IDE의 AI Chat에서 ACP 레지스트리를 통해 OpenCode를 설치하는 흐름도 소개한다.

벤치마크 순위는 빠르게 바뀌므로 자신에게 중요한 평가 기준으로 에이전트를 선택하라고 말한다. 강의의 결론은 에이전트가 근육이라면 명세는 두뇌이며, 사람은 운전자의 역할을 유지해야 한다는 것이다.

JetBrains와 협력해 제작한 스펙 주도 개발(spec-driven development) 강의에 오신 것을 환영합니다.

스펙 주도 개발은 현재 에이전트 코딩 어시스턴트(agentic coding assistants)로 진지한 애플리케이션을 구축할 때 가장 좋은 유형의 워크플로입니다.

코딩 에이전트에게 무엇을 만들어야 하는지 정확히 설명하는 Markdown 파일이나 긴 프롬프트를 주면, 에이전트가 그 스펙을 구현합니다. 직접 코드를 작성하는 대신, 에이전트가 이미 알고 있지 않은 맥락을 문서로 작성하는 데 집중하는 것입니다.

이번 강의의 강사가 JetBrains의 개발자 애드보킷(developer advocate)인 Paul Everett라서 정말 기쁩니다.

고맙습니다, Andrew. 그런데 잠깐, 안경을 쓰시는 줄은 몰랐네요.

맞아요. 사실 이 안경은 필요하지 않습니다.

네, 그럴 줄 알았어요.

어쨌든 스펙 주도 개발에는 세 가지 주요 이점이 있으며, 곧바로 그 효과를 확인하게 될 것입니다.

첫째, 스펙을 조금만 수정해도 대규모 코드 변경을 통제할 수 있습니다. “Prisma ORM과 함께 SQLite를 사용하라” 같은 한 문장이 수백 줄의 코드에 영향을 줄 수 있습니다. 같은 하위 단계의 파급 효과를 고려해 이를 MongoDB로 바꿀 수도 있습니다. 따라서 스펙 작성은 코드를 작성하는 것보다 훨씬 효율적입니다.

둘째, 스펙은 세션 간 맥락 감쇠(context decay)를 없애고, 절대 타협해서는 안 되는 사항들을 보존하는 데 도움을 줍니다. 에이전트는 상태가 없으므로, 에이전트가 시작하는 즉시 가장 품질 높은 맥락을 제공하는 것이 중요합니다.

마지막으로, 스펙은 의도 충실도(intent fidelity)를 높여 줍니다. 문제, 성공 기준, 제약 조건 등을 정의하면 에이전트가 이를 구체화해 더 완성도 높은 계획을 만들 수 있습니다.

제가 스펙을 작성하는 한 가지 방법은 Claude Code, Gemini, ChatGPT Codex 같은 에이전트와 대화하며 핵심적인 아키텍처 선택을 하는 것입니다. 이때 여러 트레이드오프를 어떻게 선택하고 싶은지에 대한 제 지식을 활용합니다. 그런 다음 에이전트에게 핵심 결정 사항을 Markdown 파일로 요약하게 합니다.

스펙을 작성하려면 사고가 필요하며, 이는 어려운 작업입니다. 어떤 제품을 만들지, 어떤 기능을 넣을지, 기술 아키텍처는 어떻게 구성할지 결정해야 합니다. 스펙이 없다면 이런 중요한 결정을 코딩 에이전트의 변덕에 맡기게 됩니다. 아주 빠르게 움직이며 운에 맡기고 싶다면 괜찮을 수도 있지만, 이는 확실히 유지 관리하기 어려운 코드와 때로는 상당히 이상한 제품으로 이어집니다.

예를 들어, 명확한 스펙 없이 복잡한 소프트웨어 제품을 개발하는 팀을 본 적이 있습니다. 서로 다른 개발자의 지시를 받은 서로 다른 코딩 에이전트들이 빠르게 개발하면서도 서로 모순되는 방식으로 작업했고, 그 결과 이후 단계에서 많은 골칫거리가 발생했습니다.

스펙 주도 개발에는 프로젝트 수준에서 헌법(constitution)을 만들어 변경할 수 없는 표준을 정의한 다음, 기능 개발 루프를 반복하는 과정이 포함됩니다. 이 루프에서는 각 기능을 별도의 브랜치로 격리하고, 계획 수립, 구현, 검증 단계를 거칩니다. 기능 사이에 깨끗한 상태를 유지하고 골칫거리와 컨텍스트 전환을 줄이는 방식입니다.

이 동일한 워크플로는 그린필드(Greenfield) 프로젝트와 브라운필드(Brownfield) 프로젝트 모두를 지원합니다. 그린필드 프로젝트에서는 처음부터 시작해 에이전트와의 대화로 헌법을 개발합니다. 브라운필드, 즉 기존 코드베이스에서는 기존 코드베이스를 바탕으로 프로젝트 헌법을 생성합니다. 두 경우 모두 이후 이러한 기능 개발 루프를 반복하며 작은 단계로 버전 관리를 수행합니다.

이번 강의에서는 스펙 주도 워크플로를 자동화하기 위해 직접 에이전트 스킬(agent skills)을 작성하는 방법도 살펴봅니다.

짧은 프롬프트 하나만으로 필요한 일을 해낼 수 있다면 훌륭합니다. 가능할 때는 저도 게으른 프롬프팅(lazy prompting)을 지지합니다. 하지만 제가 아는 뛰어난 개발자들은 상당한 복잡성이 있는 프로젝트라면 거의 항상 상세한 스펙을 작성합니다. 그들에게는 고유한 맥락과, 무엇을 어떻게 만들어야 하는지에 대한 의견이 있기 때문입니다. 그런 의견은 그 맥락을 알지 못하는 LLM이 무작위로 선택하게 하는 것보다 우월합니다.

코딩 에이전트가 코드를 작성하는 데 20분이나 30분을 사용하고, 그것이 전통적인 개발자의 작업 몇 시간에 해당할 수 있다면, 대개는 3~4분 동안 앉아서 명확한 지시 사항을 작성하는 편이 낫습니다.

JetBrains의 Konstantin Chaikur와 Zina Smirnova, 그리고 DeepLearning.AI의 Isabel Zarro를 비롯해 많은 분들이 이 강의에 기여했습니다.

다음 영상으로 넘어가 스펙을 작성해 보겠습니다.

에이전트 코딩(agentic coding)이라는 말을 들으면 바이브 코딩(vibe coding)을 떠올릴 수도 있습니다. 둘을 비교해 보고, 스펙 주도 개발이 어떻게 엔지니어링을 되살려 더 나은 결과를 제공하는지 살펴보겠습니다.

바이브 코딩은 빠른 결과를 제공합니다. “버튼을 하나 만들어 줘”처럼 원하는 것을 설명하는 프롬프트를 작성하고 최선의 결과를 기대합니다. 그런 다음 결과를 확인합니다.

버튼이 정말 크네요. 어느 정도 비슷하지만 몇 가지 중요한 부분이 어긋났습니다. 그래서 에이전트에게 실수를 지적하고, 에이전트가 다시 시도하게 하는 식으로 만족할 때까지 반복합니다.

그 결과 에이전트와 긴 대화를 나누게 되지만, 그 대화 기록은 저장되지도 않을 것입니다. 이 방식은 버튼 하나에는 어느 정도 잘 작동하지만, 규모가 크고 지속적으로 진행되는 프로젝트에는 확장되지 않습니다.

높은 수준의 프롬프트는 빠르지만, 폐기할 코드와 누적되는 기술 부채를 만들어 냅니다. 우리에게는 엔지니어링이 필요합니다. 영구적인 기술 산출물을 만들어 내는 잘 유지 관리되는 명세가 필요합니다.

스펙 주도 개발은 감독되지 않은 AI 생성의 혼란에 대한 전문적인 대응입니다. 무엇을 왜 만드는지 설명하는 스펙과 어떻게 구현할지를 분리하는 패러다임의 전환입니다.

스펙을 사용하면 인간 사이뿐 아니라 인간과 에이전트 사이에도 계약이 생깁니다. 이제 인간인 여러분의 주요 과제는 자신의 의도를 명확한 스펙으로 변환하는 방법을 배우는 것으로 바뀝니다.

에이전트 코딩 지원을 활용한 스펙 주도 개발에는 세 가지 주요 이점이 있습니다.

첫째, 스펙을 조금만 수정해도 대규모 코드 변경을 통제할 수 있습니다. 앱의 외관과 느낌을 설명하는 스펙의 몇 문장이 수백 줄의 CSS로 변환될 수 있습니다. 이러한 스펙 주도 방식은 초고속 코딩 에이전트를 사용할 때 필요한 인지 부담을 줄여 줍니다.

둘째, 스펙은 여러 턴으로 진행되는 에이전트 세션을 망가뜨리는 맥락 감쇠 문제를 없애 줍니다. 코딩 에이전트와 작업하다 보면 컨텍스트 윈도(context window)가 가득 차고, 에이전트가 작업 메모리를 모두 사용한 상태에 대처하려 하면서 실수가 늘어나는 경우가 많습니다. 스펙은 세션과 에이전트가 바뀌어도 유지되며, 코드베이스에서 작업하고 기능을 구현하는 데 필요한 핵심 맥락에 에이전트를 고정해 줍니다.

셋째, 스펙은 의도 충실도를 높입니다. 즉, 에이전트가 여러분의 목표에 맞는 코드를 만들어 낼 가능성이 커집니다. 이는 에이전트가 코드를 생성하기 전에 문제, 성공 기준, 제약 조건, 사용자 흐름 등을 정의하도록 스펙이 강제하기 때문입니다.

스펙은 바이브 코딩으로 엉성한 무언가를 만드는 것과 실행 가능한 소프트웨어 제품을 엔지니어링하는 것을 가르는 핵심 요소입니다. 처음부터 새 프로젝트를 시작하든, 수년간 운영해 온 프로젝트에 SDD 방식을 도입하려 하든, 스펙은 방향 이탈과 생산성 문제를 해결하는 데 도움을 줍니다.

비교를 위해, 이해할 수 있는 소스 코드를 기계어 코드로 변환하는 컴파일러를 생각해 보세요. SDD는 에이전트와 프롬프트를 안내해 스펙을 소스 코드로 변환합니다. 더 좋은 점은 스펙이 인간의 언어로 작성되므로 이해관계자들이 쉽게 읽을 수 있다는 것입니다.

스펙 주도 개발은 최근 생산성에 대한 우려를 해결하는 방법으로 빠르게 확산되었습니다. 여러 SDD 프로젝트, 스펙 작성을 중심으로 만들어진 도구, 의도 포착에 관한 컨퍼런스 발표는 모두 소프트웨어 개발 수명 주기에서 얻은 교훈인 엔지니어링을 에이전트 코딩에 적용하려는 더 큰 흐름의 일부입니다.

스펙 주도 개발은 단순한 챗봇이 아니라 코딩 에이전트와 함께 사용됩니다. 챗봇은 코드에 관해 이야기할 수 있지만, 프로젝트의 코드나 설치된 도구에 접근할 수는 없습니다. 그저 프롬프트에 응답할 뿐입니다.

에이전트는 다릅니다. 에이전트는 프롬프트를 받아 계획을 세우고, 그 과정에서 추론을 활용해 스스로 결과를 향해 나아갑니다. 중요한 점은 에이전트가 코드베이스와 개발 도구에 접근할 수 있다는 것입니다.

SDD 워크플로에서는 이러한 에이전트를 매우 유능한 페어 프로그래머(pair programmer)로 취급합니다. 에이전트는 기술 지식과 속도를 제공하고, 선임 아키텍트인 여러분은 청사진을 제공합니다.

이 강의를 계속 진행하면서 다음을 기억하세요. 에이전트가 근육이라면 스펙은 두뇌입니다. 연습을 통해 여러분은 생성된 소프트웨어가 기능하기만 하는 것이 아니라 장기적인 목표에도 부합하도록 만들 수 있습니다.

스펙 주도 개발은 프로젝트를 위해 처음부터 원하는 것을 어떻게 만들지 에이전트에게 알려 주고, 이후 각 기능에 대해서도 알려 주면서 점점 더 나은 결과를 만들어 냅니다.

SDD에서는 먼저 프로젝트에 관한 결정으로, 그다음 각 기능에 관한 세부 사항으로 에이전트에 최고 품질의 맥락을 제공합니다.

이 스펙은 매우 상세합니다. SDD의 핵심 기술 중 하나는 적절한 세부 수준을 아는 것입니다. 에이전트를 매우 유능한 페어 프로그래머로 대한다면 적절한 수준에 도달하는 경우가 많습니다. 목표, 사명, 대상 사용자, 제약 조건에 관한 맥락은 많이 제공하되, 에이전트가 스스로 결정할 수 있는 저수준의 결정 사항은 적게 제공하는 것입니다.

이 SDD 워크플로는 어떤 모습일까요?

먼저 헌법을 명시합니다. 사명은 무엇이고, 기술 스택은 무엇이며, 로드맵은 어떻게 되는가?

헌법은 이러한 프로젝트 수준의 세부 사항을 공식화하는 한 가지 방법일 뿐입니다. 많은 개발자가 이 목적을 위해 최상위 AGENTS.md 파일을 사용하지만, 프로젝트 헌법은 특정 에이전트에 종속되지 않고 더 구조화되어 있습니다.

헌법에는 인간과 에이전트 사이의 핵심 결정에 대한 합의뿐 아니라 인간들 사이의 합의도 담깁니다.

사명은 ‘왜’에 해당합니다. 이 프로젝트의 비전, 대상, 범위 등을 설명합니다. 이러한 매개변수를 미리 정의하는 것은 소프트웨어 프로젝트에서 매우 일반적이며, 지속적인 의사 결정을 안내하는 데 도움이 됩니다.

기술 스택은 엔지니어링 팀을 위한 것으로, 개발 및 배포 기술과 제약 조건에 대한 공통된 이해를 제공합니다.

로드맵은 각 단계가 자체적인 기능 스펙 프로세스로 구현되는 단계들의 순서를 담은 살아 있는 문서입니다.

헌법 초안이 작성되면 반복 가능한 프로세스로 각 기능을 작업합니다. 먼저 기능을 계획하고, 구현한 다음, 마지막으로 결과를 검증합니다.

기능과 기능 사이에는 재계획 단계가 있습니다. 헌법을 수정하고, 로드맵을 업데이트하며, 프로세스 자체도 개선합니다.

조금 전에 들으셨듯이, SDD(spec-driven development)의 핵심 기술 중 하나는 최고 품질의 컨텍스트를 만들 수 있도록 적절한 수준의 세부 정보를 제공하는 것입니다. 기능 단계와 재계획 단계에서는 여러분이 에이전트를 이끕니다.

이렇게 생각해 보세요. 여러분이 건축가이고, 건축업자에게 건물의 상세 도면을 제공한다고 상상해 보세요. 그다음은 건축업자에게 달려 있습니다. 여러분의 역할은 설계하고, 시공을 감독한 다음, 결과를 검토하고 승인하거나 변경을 요청하는 것입니다. 건축업자에게 업무 방식을 지시하는 것은 피하고, 그들이 모르는 컨텍스트를 제공하는 데 집중해야 합니다.

스펙 주도 개발(spec-driven development)은 처음의 구상부터 마지막의 전달까지 이어 줍니다. 무엇보다도, 그 이후에도 계속 개선할 수 있게 해 줍니다.

이것은 현대 개발자들이 사용하기 시작한 SDD 워크플로 중 하나입니다. 곧 시작 단계인 프로젝트 헌법(project constitution)을 살펴보겠습니다. 하지만 먼저 약간의 설정 준비를 해 보겠습니다.

참고로 스킬은 프로젝트별로 만들 수도 있고 전역으로 만들 수도 있습니다. 스킬을 호출하는 방법도 여러 가지입니다. 프롬프트에서 무엇을 할지 말하기 전에 스킬을 언급하세요. 또한 다른 스킬에서 스킬을 호출하도록 에이전트에 요청할 수도 있습니다.

Skills Open Standard에 따르면 에이전트는 점진적 공개(progressive disclosure)라는 프로세스에서 스킬 설명을 사용해 언제 스킬을 호출할지 결정합니다. 하지만 특히 컨텍스트 창이 커질수록 에이전트의 판단이 항상 완벽한 것은 아닙니다.

파일 태깅에 사용한 것과 같은 휴리스틱을 쓰세요. 특정 스킬을 사용하고 싶다는 것을 알고 있다면 그 이름을 명시하세요. 그러면 생각에 사용하는 토큰을 절약할 수 있습니다.

에이전트에는 /clear 같은 슬래시 명령어(slash command)가 기본으로 포함되어 있습니다. 처음에는 인기가 많았지만, 많은 에이전트가 커스텀 슬래시 명령어에서 스킬로 옮겨 가고 있습니다.

때로는 API, 비공개 지식 기반, 데이터베이스 등에 대한 접근처럼 에이전트에 더 많은 리소스를 제공해야 합니다.

지금까지 에이전트를 확장하는 보편적인 방법은 MCP(Model Context Protocol)였습니다. 예를 들어 에이전트에는 패키지에 관한 최신의 양질의 컨텍스트가 필요합니다. 가장 인기 있는 선택지는 Context7입니다. Context7은 업데이트된 패키지 문서를 에이전트의 컨텍스트로 가져오는 MCP입니다.

이제 에이전트가 React 19.0이 아니라 React 19.2 이상에 맞춰 최신 상태를 유지할 수 있습니다. MCP 서버는 여전히 인기가 있지만, CLI 같은 코드 도구를 사용하는 스킬이 같은 목적을 더 우아하게 달성하는 경우가 많습니다.

Context7은 이제 다음을 제안합니다. Context7용 CLI 도구를 호출하는 스킬입니다. Claude Code용 Context7 패키지를 설치해 봅시다.

설치 과정에서 바로 다음을 볼 수 있습니다. MCP 서버를 사용할지, CLI와 스킬을 사용할지 선택하는 화면입니다. 두 번째 선택지를 사용하겠습니다.

처음이라면 계정을 만들어야 합니다. 우리는 이미 계정을 만들고 로그인했습니다. 이제 Claude Code로 돌아가 Context7을 사용하는 예시 프롬프트를 실행해 보겠습니다.

에이전트가 실행되는 동안 Context7을 사용해야 한다는 것을 감지하는 모습을 볼 수 있습니다. 작업이 끝나면 에이전트는 기술 스택에 관한 정보를 찾는 방법을 이제 알고 있다고 보여 줍니다.

MCP 서버에서 스킬과 CLI로 옮겨 가는 흐름이 빨라지고 있습니다. CLI 도구는 설정이 더 적고 컨텍스트 사용량도 적은 상태에서 작업을 수행할 수 있기 때문에 사람들이 MCP를 다시 생각하고 있습니다.

워크플로 구현과 스킬 등을 확장하다 보면 여러 컴퓨터에서 직접 공유하고, 팀원들과 공유하며, 어쩌면 외부 세계와도 공유하고 싶어질 것입니다.

Qodo Code 같은 일부 에이전트에는 설치하고 업데이트할 수 있는 에이전트 확장 모음인 플러그인이 있습니다. 무료 플러그인을 제공하는 커뮤니티도 점점 커지고 있습니다. SDD 생산성을 높여 줄 플러그인이 있는지 살펴보세요.

플러그인은 아직 에이전트 간 표준이 아니라는 점을 기억하세요. 앱이나 종속성과 마찬가지로 플러그인은 코드를 실행할 수 있으므로, 설치하고 업데이트할 때 신뢰할 수 있는 것인지 확인하세요.

GitHub의 Spec Kit은 에이전트를 활용한 스펙 주도 개발 워크플로를 공식화하려는 시도 중 하나입니다. 프로젝트에 Spec Kit을 설치하면 이 과정에서 사용한 워크플로와 비슷한 슬래시 명령어를 에이전트에서 사용할 수 있습니다. /speckit.constitution, /speckit.plan, /speckit.tasks, /speckit.implement 등이 있습니다.

또 다른 인기 있는 대안은 Fission AI의 OpenSpec입니다. OpenSpec은 비슷한 propose, explore, apply, archive 워크플로를 따릅니다. 여기서 propose와 explore는 plan 단계에, apply는 implement에, archive는 replanning에 해당합니다.

또한 빠른 기능을 위한 표준 패턴도 제공합니다. 두 패키지 모두 브랜치 관리, 검증 스크립트, 의견이 반영된 스펙 문서 형식 같은 유용한 기능을 포함합니다.

이러한 오픈 소스 워크플로를 직접 실험해 보며 여러분의 방식을 개선해 보시길 권합니다.

때로는 기능을 작업하는 도중에 아이디어가 떠오릅니다. 에이전트와 함께 그 아이디어를 조사하고 싶지만 현재 브랜치 작업을 중단하고 싶지는 않을 수 있습니다. 예를 들어 데이터베이스 선택 같은 경우입니다. 하지만 아직 이 아이디어를 확정한 것은 아니므로 로드맵에 올리고 싶지도 않습니다.

대화를 통해 좋은 아이디어와 좋은 질문이 나옵니다. 대부분의 제안은 받아들이지만 그중 하나에 대해서는 생각을 바꿉니다. 그렇다고 그 내용을 잃고 싶지는 않으므로, 에이전트에게 잘 알려진 위치에 보고서를 작성하라고 하여 조사 백로그를 유지해 봅시다.

이 파일은 대화와 결과를 기록한 것입니다. 나중에 에이전트에게 이 백로그 파일의 링크와 함께 이 조사를 로드맵에 일정으로 추가해 달라고 요청할 수 있습니다. 이 작업이 커지면 조사를 자동화하는 스킬을 작성할 수도 있습니다.

스펙 주도 개발은 에이전트가 여러분의 방식대로 코드를 작성하도록 돕습니다. 기존 SDD 프레임워크나 도구를 도입한 다음, 스킬을 사용해 팀과 함께 여러분의 방식으로 프로젝트를 운영하도록 맞춤 설정할 수 있습니다.

스펙 주도 개발은 작업의 초점을 어떻게에서 무엇과 왜로 옮깁니다. 에이전트와 모델은 매우 빠르게 발전하므로, 워크플로를 하나의 선택지에만 묶어 두고 싶지는 않을 것입니다.

이번 강의에서는 표준을 통해 워크플로와 도구를 유지하면서 에이전트를 바꿀 수 있는 방법을 살펴봅니다.

이러한 에이전트 표준은 다음 목표를 돕습니다. 외부 도구를 위한 MCP, 규칙을 위한 AGENTS.md, 추가 컨텍스트와 함께 반복 가능한 워크플로를 기록하는 Agent Skills, 에이전트와 클라이언트를 연결하는 ACP입니다.

예를 들어 Codex는 OpenAI의 대표적인 AI 에이전트입니다. 데스크톱 앱, 에디터, 터미널에서 실행할 수 있습니다. 실제로 어떻게 작동하는지 살펴봅시다.

여기에는 Lesson 12에서 만든 Feature Spec 스킬을 Codex에 복사해 두었습니다. Codex는 이를 다른 경로에 저장합니다. 마이그레이션하고 나면 문제없이 실행됩니다.

이를 통해 같은 프로젝트에서 에이전트 사이를 오가면서도 SDD 워크플로를 유지할 수 있습니다.

Agent Client Protocol(ACP) 표준을 사용하면 서로 다른 에이전트와 함께 서로 다른 에디터를 사용할 수도 있습니다. ACP는 에이전트와 에디터를 쉽게 연결해 줍니다. 에이전트와 클라이언트가 ACP를 지원한다면 완벽하게 호환됩니다.

플러그 앤 플레이를 더욱 쉽게 만들기 위해 ACP 레지스트리는 클라이언트 안에서 에이전트를 찾고, 설치하고, 연결하는 작업을 자동화합니다. ACP 레지스트리는 전체 수명 주기를 다루므로 조합을 바꾸어 사용하기가 더 쉬워집니다.

예를 들어 JetBrains IDE에서는 AI Chat 창을 통해 ACP 레지스트리에서 설치할 수 있습니다. 그러면 IDE가 호환되는 에이전트 목록을 보여 줍니다.

OpenCode는 인기 있는 오픈 소스 에이전트입니다. ACP 레지스트리를 사용하면 IDE에 쉽게 추가할 수 있습니다. Install을 클릭하면 필요한 경우 OpenCode 자체를 설치하는 작업과 IDE 통합을 모두 자동화해 줍니다. 이는 꽤 편리합니다.

작업이 끝나면 IDE에 새로운 에이전트가 네이티브로 통합됩니다. SDD의 일부로 같은 에디터에서 다른 에이전트와 함께 이 새로운 에이전트를 사용할 수 있습니다.

이 새로운 에이전트 표준이 새로운 가능성을 열고 있는데, 실제로 어떻게 작동할까요?

ACP 아키텍처는 에이전트와 클라이언트를 쉽게 연결할 수 있도록 설계되었습니다. 실제로 이 프로토콜은 LSP에서 사용되는 것과 일치합니다. ACP는 생각보다 많은 것을 다룹니다. 예를 들어 에디터의 다음 편집 제안(Next Edit Suggestions)과 계획 모드(Plan Mode)도 다룹니다.

ACP를 한 단계 더 활용하면 도구에 로컬로 설치되는 커스텀 에이전트를 직접 작성할 수도 있습니다.

어떤 에이전트를 선택해야 할까요?

업계는 빠르게 변하고 있으며, 여러 평가를 제공하는 리더보드와 함께 벤치마크 사이트도 생겨났습니다. 물론 이런 리더보드도 빠르게 변하므로 최신 정보를 확인하고, 여러분에게 중요한 기준을 바탕으로 결정하세요.

우리의 스펙은 특정 에이전트나 IDE에 종속되지 않고 더 높은 수준에서 작동합니다. 이번 강의에서 이를 증명했습니다. 에이전트와 독립적으로 작동하도록 워크플로와 도구를 구축했습니다. 더 많은 표준이 등장할수록 이러한 유연성은 더욱 커질 것입니다.
