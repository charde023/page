먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 9분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 발표의 질문은 “코딩 에이전트를 몇 개나 동시에 돌릴까?”보다 넓다. 화자는 빠른 개발자가 되려면 새 도구를 시험하는 속도, 어디에 시간을 쓸지 고르는 기준, 사람이 직접 지킬 신뢰 구역, 에이전트가 참고할 조직 정보, 오래 실행할 공간, 최종 방향을 정하는 인간의 역할을 함께 설계해야 한다고 주장한다.

여기서 코딩 에이전트는 사람의 지시를 받아 코드를 살펴보고 수정하는 AI 도구다. 화자가 공동 창업했다고 밝힌 Conductor는 여러 코딩 에이전트를 한 화면에서 관리하는 데스크톱 앱으로 소개된다. 발표의 여섯 원칙은 각각 떨어진 요령이 아니라, 탐색에서 실행과 검토까지 이어지는 하나의 운영 구조다.

읽는 법: 위에서 아래로 읽는다. 새 기술을 고르는 판단이 먼저이고, 그다음 신뢰할 정보와 경계를 준비한다. 이후 에이전트가 지속적으로 일할 공간을 제공하되, 마지막 방향과 품질 판단은 인간에게 남긴다는 구조다. 이는 발표 내용을 재배열한 개념도이며 성능을 측정한 수치 그래프가 아니다.

1. 최신 기술은 빨리 시험하되, 유행 자체가 일이 되게 하지 않는다

첫 원칙은 최전선 위가 아니라 최전선 가까이에 머무는 것이다. 새 모델이나 도구가 나오면 초기에 직접 사용해 봐야 새 가능성과 문제를 발견할 수 있다는 뜻이다.

화자는 원래 팀이 Chorus라는 다른 앱을 만들고 있었다고 말한다. Claude Code를 집중적으로 사용하면서 저장소를 다섯 번 복제해 병렬 작업했고, 이후 Git worktree를 발견했다. 이 과정에서 내부 도구로 만들던 것이 Conductor로 이어졌다는 설명이다. 화자에게는 새 도구의 직접 사용이 제품 아이디어를 발견한 계기였다.

하지만 최신 워크플로를 계속 다듬는 것만으로는 실제 일이 진행되지 않을 수 있다. 그래서 화자는 “왜 이 방식이 아직 기본 기능이 아닐까?”라고 물으라고 제안한다. 누구에게나 필요한 보편적 기능이라면 Anthropic이나 OpenAI 같은 도구 공급자가 기본 실행 환경에 넣을 가능성이 있으니, 사용자가 먼저 많은 시간을 들여 만들 필요가 없다는 논리다.

반대로 자신의 사용자나 코드베이스에만 있는 특별한 정보가 있다면 직접 최적화할 이유가 생긴다. 화자는 이를 남들이 모르는 유리한 정보(실제 알파, real alpha)라고 부른다. 예를 들어 Conductor는 긴 채팅을 빠르게 표시해야 하므로 관련 React 쿼리의 성능에 시간을 쓰며, 이를 위해 코드베이스의 다른 부분에서는 일부 희생도 감수한다고 설명한다.

읽는 법: 모바일에서는 표 영역만 좌우로 이동해 네 열을 확인한다. 핵심 구분은 “최신인가?”가 아니라 “내 사용자나 코드베이스만의 정보 때문에 직접 투자해야 하는가?”이다. 표는 화자의 판단 기준을 정리한 개념 비교이며 효과를 실험한 결과표는 아니다.

2. 에이전트의 자유보다 먼저 신뢰할 경계와 맥락을 만든다

화자는 코드 전체를 같은 수준으로 다루지 않는다. 잘못 바뀌었을 때 영향이 크거나, 에이전트가 반복해서 참고하는 부분은 사람이 엄격하게 검토해야 한다고 말한다. 이를 AI가 만든 저품질 결과를 허용하지 않는 구역(슬롭 없는 청정 구역, slop-free zone)이라고 부른다.

Conductor에서는 마이그레이션 파일이 바뀌면 CI에서 사람의 검토가 필요하다고 한다. Slack에 사람이 쓴 내용, 문서, CLAUDE.md, 스킬 파일도 중요하게 다룬다고 설명한다. 특히 CLAUDE.md나 AGENTS.md는 에이전트가 일을 시작할 때 반복해서 읽는 정보다. 화자는 이것을 새 인턴이 자리에 앉을 때마다 귀에 들려줄 말에 비유한다. 반복해서 들어갈 지시라면 대충 작성해서는 안 된다는 뜻이다.

동시에 에이전트가 회사의 실제 사정을 알아야 한다고 주장한다. Conductor에는 Conductor Internal Agent, 줄여서 CIA라고 부르는 내부 도구가 있으며, Slack 메시지, Discord의 사용자 버그 요청, 녹화된 회의 정보를 중앙 데이터베이스에 넣는다고 설명한다. 예시에서는 Postgres 테이블에 저장하고 에이전트에 SQL 도구를 주는 방식이 제시된다. 화자는 이를 “괴물에게 먹이를 준다”고 표현한다.

두 원칙은 비슷해 보이지만 역할이 다르다. 청정 구역은 무엇을 엄격히 믿을지 정하는 품질 경계이고, 중앙 데이터베이스는 에이전트가 참고할 조직 맥락을 넓히는 장치다. 정보를 많이 모으는 것만으로 신뢰도가 자동으로 높아지는 것은 아니다.

3. 오래 실행할 공간을 주되 사람의 검토와 협업을 연결한다

화자는 노트북을 닫으면 멈추는 에이전트보다, 종료되지 않는 별도 샌드박스에서 코드베이스를 탐색하고 긴 작업을 수행하는 에이전트가 더 유용하다고 본다. 이를 방목형 에이전트(free-range agent)라고 부른다. 여기서 샌드박스는 작업이 본 시스템과 섞이지 않도록 분리해 실행하는 공간이라는 뜻이다.

발표 데모에서는 각 작업 공간이 클라우드 샌드박스에서 실행되고, 팀원이 서로의 작업을 실시간으로 확인하거나 메시지를 남기는 장면을 보여 준다. Caden의 작업 공간에 들어가 “공백 대신 탭을 사용할 수 있는가?”라고 메시지를 보내고, 상대가 입력 중인 상태도 보여 준다.

또한 화자는 OpenClaw인 Lord Crandon에 Conductor API 접근 권한을 주고, 휴대전화에서 “모든 버튼을 파란색으로 만드는 작업 공간을 만들어 달라”고 요청한다. 데모상 작업 공간은 생성되고 에이전트가 작업을 시작한다. 다만 발표에서는 해당 변경의 최종 품질이나 완료 결과까지 검증하지 않는다.

읽는 법: 위에서 아래로 읽는다. 에이전트를 오래 실행하는 것만으로 끝나지 않는다. 먼저 기준과 맥락을 주고, 분리된 공간에서 일하게 한 뒤, 사람이 협업과 검토를 통해 방향을 조정한다. 이는 발표의 원칙을 연결한 과정도이며 각 단계가 안전이나 성능을 보장한다는 뜻은 아니다.

4. 공장보다 오케스트라라는 말이 중요한 이유

화자는 에이전트를 많이 돌리는 미래를 “소프트웨어 공장”이라고 부르는 데 반대한다. 공장은 자동화와 생산량을 떠올리게 하지만, 사람을 버튼을 누르는 조립 라인 관리자로 밀어낼 수 있다는 이유다.

그가 원하는 모습은 오케스트라다. 지휘자는 전체 흐름을 보다가 필요할 때 특정 부분을 자세히 듣는다. 사람과 여러 에이전트가 함께 일하지만, 무엇을 만들고 어떤 품질을 지킬지는 인간이 계속 판단한다. 즉, 이 비유는 자동화를 거부한다기보다 자동화의 목적과 품질을 인간이 지휘해야 한다는 가치 선언에 가깝다.

발표의 인과를 한 문장으로 묶으면 이렇다. 최신 도구를 빠르게 시험하되 고유한 문제가 있을 때만 깊게 투자하고, 중요한 지식과 파일에는 사람의 검토를 남기며, 조직 맥락과 지속 실행 공간을 에이전트에 제공하고, 최종 방향은 인간이 조율해야 빠르면서도 의도 있는 개발에 가까워진다는 주장이다.

다만 이 발표는 비교 실험이나 생산성 수치가 아니라 화자가 Conductor와 다른 개발자들을 관찰하며 정리한 원칙과 제품 데모다. 모든 조직 정보의 중앙 수집에 따르는 개인정보, 접근 권한, 보안, 보존 기간은 다루지 않는다. 클라우드 샌드박스의 비용과 실패 격리, 장기 실행 에이전트의 통제 방법도 구체적인 검증 자료가 없다.

여기까지만 이해하면 충분

  • 최신 AI 도구는 빨리 시험하되, 내 사용자나 코드베이스만의 정보가 없으면 보편 워크플로를 과잉 최적화하지 않는다.
  • 에이전트에게 정보를 많이 주는 것과 믿을 수 있는 기준을 주는 것은 다르므로, 중앙 맥락과 사람이 지키는 청정 구역을 함께 설계한다.
  • 오래 실행되는 클라우드 에이전트는 협업 가능성을 넓히지만, 품질·보안·비용을 자동으로 해결하지는 않는다.
  • 화자의 “오케스트라”는 인간이 전체 방향과 세부 품질을 오가며 에이전트를 지휘해야 한다는 비유다.

비유와 깨지는 지점

오케스트라와 지휘자

지휘자는 모든 악기를 직접 연주하지 않지만, 전체 곡의 방향을 정하고 필요한 순간 특정 파트에 개입한다. 각 연주자는 에이전트와 팀원, 악보와 연습 지침은 신뢰할 문서, 리허설 공간은 샌드박스에 대응한다.

비유가 깨지는 지점: 오케스트라의 연주자는 책임과 판단 능력을 가진 사람인 반면, 코딩 에이전트는 잘못된 맥락을 따르거나 예상하지 못한 변경을 만들 수 있다. 지휘 비유만으로 접근 권한, 검증, 실패 격리, 비용 문제가 해결되지는 않는다.

먼저 해결할 문제가 보편적인지 자신의 사용자·코드베이스에 고유한지 구분한다. 다음으로 사람이 반드시 검토할 파일, 에이전트에 제공할 맥락, 실행을 격리할 공간, 결과를 승인할 사람을 정한다. APOM이나 다른 실제 시스템에 적용할 수 있는지는 현재 상태가 제공되지 않았으므로 별도 확인이 필요하다.

이번 글의 통찰

1. 속도의 핵심은 에이전트 수보다 판단의 배치다

  • [원문] 화자는 최신 도구를 빨리 시험하되 실제 알파가 없으면 보편 워크플로를 과잉 최적화하지 말고, 중요한 코드와 문서는 사람이 엄격하게 검토해야 한다고 말한다.
  • [해석] 빠른 개발은 모든 단계를 자동화하는 일이 아니라, 탐색·위임·검토에 사람의 시간을 다르게 배분하는 일이다.
  • [경계] 발표에는 기존 방식과 비교한 완료 시간, 결함률, 비용 같은 측정 결과가 없다. “가장 빠른 개발자”라는 표현은 화자의 관찰과 주장이지 독립적으로 검증된 순위가 아니다.

2. 많은 맥락과 높은 신뢰는 별개의 설계 문제다

  • [원문] Conductor의 CIA는 Slack 메시지, Discord의 버그 요청, 회의 기록을 Postgres에 저장하고 에이전트가 SQL로 조회하게 한다고 설명된다. 한편 마이그레이션 파일, 문서, CLAUDE.md, 스킬에는 강한 인간 검토를 둔다.
  • [해석] 에이전트가 많이 아는 것과 바른 기준을 따르는 것은 다르다. 조직 기억을 넓히는 저장소와 신뢰를 지키는 검토 경계가 함께 필요하다.
  • [경계] 개인정보, 접근 통제, 잘못된 기록의 수정, 보존 기간, 데이터 유출 위험은 발표에서 다루지 않는다. “모든 정보”라는 표현도 예시로 든 정보원이 실제로 완전 수집됐다는 독립 증거는 아니다.

3. 이름·수량·시행 상태의 불확실성을 그대로 남겨야 한다

  • [원문] 발표 마지막에는 여섯 원칙을 다시 열거하고 기억용 약어로 STICFO를 제시한다. 새 Conductor 버전과 전체 사용자 대상 배포는 “이번 주”에 나온다고 말한다. META 설명은 화자를 Charlie Holtz라고 적지만 provenance의 creator 값은 비어 있고, 이름과 SNS를 기준으로 추정했다고 밝힌다.
  • [해석] 제품 데모, 출시 계획, 화자 식별, 기억용 이름은 서로 다른 확실성으로 기록해야 한다. 데모를 완료된 전체 배포로 바꾸거나 추정 인물을 확정 원작자로 바꾸면 안 된다.
  • [경계] 여섯 원칙의 일반적인 머리글자는 STICFO와 바로 대응하지 않아 약어의 구성 근거가 불명확하다. 두 번째 원칙은 본문에서 번호를 명시하지 않고 세 번째로 넘어가지만 마지막 열거를 기준으로 총 여섯 개는 맞는다. “slash goal”과 “two days of Fable”은 제공 전사만으로 정확한 제품명·사건을 확인할 수 없다. “지난해 2월”, “이번 주”, “올해”, “10년 전”은 발표 시점 기준 상대 표현이며, 클라우드 버전의 실제 배포 완료 여부도 별도 확인되지 않았다.

1. 발표의 출발점과 Conductor

화자는 AI 엔지니어링에 관심 없는 사람을 결혼식에서 만난 일화를 말한 뒤, 관련 청중 앞에서 발표하게 된 기쁨을 표현한다. 자신을 Conductor의 공동 창업자라고 소개한다.

Conductor는 Claude Code, Codex 또는 다른 코딩 에이전트를 여러 터미널 창에서 따로 관리하는 대신 하나의 인터페이스에서 동시에 관리하는 데스크톱 앱이라고 설명한다. 발표의 원칙은 Conductor를 만들며 뛰어난 개발자들의 작업 방식과 피하는 행동을 가까이서 관찰한 결과라고 주장한다.

2. 최전선 가까이 머물기

새 모델이나 코딩 도구가 공개되면 당일에 가깝게 직접 시험하는 태도를 권한다. 스타트업에서는 이런 실험이 새 제품 아이디어로 이어지고, 회사 안에서는 최신 워크플로를 파악하는 역할을 할 수 있다고 말한다.

화자의 팀은 원래 Chorus라는 앱을 만들었으나 Claude Code를 집중적으로 사용하면서 작업 방식을 바꿨다고 한다. 저장소를 다섯 번 복제하다가 Git worktree를 발견했고, 내부 도구로 시작한 것이 Conductor로 이어졌다고 설명한다.

다른 사람의 소셜 관계망을 통해 소식이 전달되기를 기다리면 3~6개월 뒤처질 수 있다고 주장한다. 이 수치는 발표자의 추정이며 별도 근거는 제시되지 않는다.

3. 시장을 이기려 하지 않기

최전선 가까이에 있는 것과 최전선 자체에 과몰입하는 것을 구분한다. 후자는 실제 작업보다 워크플로 설정에 시간을 쓰는 상태로 묘사된다.

판단 질문은 “왜 이 워크플로가 기본값이 아닌가?”이다. Ralph loops처럼 모두에게 필요한 방식이라면 Anthropic, OpenAI 또는 다른 공급자가 기본 실행 환경에 넣을 수 있으므로 기다리는 편이 낫다는 주장이다.

예외는 실제 알파가 있을 때다. Conductor는 긴 채팅을 빠르게 표시해야 하므로 관련 React 쿼리 최적화에 시간을 쓰며, 다른 코드 부분의 일부 희생도 받아들인다고 설명한다.

4. 슬롭 없는 청정 구역

화자는 Conductor가 30,000줄짜리 PR을 무조건 빠르게 통과시키는 팀으로 보일 수 있지만 실제로는 코드베이스의 일부에는 매우 엄격하고 다른 부분에는 느슨하다고 말한다. 30,000줄은 외부의 가정을 묘사한 표현이지 실제 PR 규모를 확인한 수치가 아니다.

청정 구역을 제대로 정하지 않아 전체 앱을 두어 번 다시 작성해야 했다고 주장한다. 구체적인 실패 원인과 횟수별 기록은 제시하지 않는다.

마이그레이션 파일이 바뀌면 CI에서 사람의 검토가 필요하다고 한다. 사람이 작성한 Slack 내용, 문서, CLAUDE.md, 스킬 파일에도 많은 시간을 쓴다고 말한다. 이어 CLAUDE.md와 AGENTS.md를 에이전트가 작업할 때마다 받는 반복 지침으로 설명한다.

5. Conductor Internal Agent

내부 도구 Conductor Internal Agent는 CIA라고도 부른다. 새 Slack 메시지를 감지해 Postgres 테이블에 저장하고, Discord의 사용자 버그 요청과 녹화된 회의도 같은 중앙 맥락에 넣는다고 설명한다.

화자는 회사에서 에이전트가 효과적으로 일하려면 그 회사가 실제로 일하는 방식에 대한 정보와 맥락이 많아야 한다고 주장한다. 모든 정보를 데이터베이스에 넣고 에이전트에 SQL 도구를 주는 방식을 간단한 해법으로 제시한다.

6. 방목형 에이전트와 제품 데모

에이전트가 노트북에 갇히지 않고 종료되지 않는 샌드박스에서 코드베이스를 탐색하고 긴 작업을 수행해야 한다고 주장한다. 다른 에이전트와 사람에게 협업 수단을 주고, 필요하면 추가 작업을 생성할 수 있게 하는 방향도 제시한다.

화자는 이번 주에 공개될 예정인 새 Conductor 버전을 보여 준다. 이전에는 기본적으로 각 작업이 Git worktree를 사용했지만 새 버전은 클라우드 샌드박스를 중심으로 한다고 설명한다. 노트북을 닫아도 에이전트가 계속 실행되는 것이 핵심 주장이다.

모르시는 분들을 위해 설명하자면, Conductor는 코딩 에이전트 팀을 동시에 관리하기 위한 데스크톱 앱입니다. Claude Code나 Codex, 혹은 여러분이 사용하는 코딩 에이전트마다 터미널 창을 여러 개 띄우는 대신, 하나의 인터페이스에서 모두 관리할 수 있습니다.

Conductor를 만들면서 정말 좋았던 점 중 하나는 최고의 빌더들 가운데 많은 사람을 가까이에서 지켜볼 수 있었다는 것입니다. 그들의 워크플로를 관찰했습니다. 어떻게 일하는지, 무엇을 하는지, 무엇을 피하는지 보았습니다. 그래서 최고의 엔지니어들이 사용하는 원칙을 많이 모아서 여러분과 공유해 보면 좋겠다고 생각했습니다.

여기 조직에서 가장 빠른 빌더가 되기 위한 제 원칙이 있습니다. 첫 번째부터 시작하죠. 최첨단에 가까이 머무르세요.

최첨단에 가까이 머무른다는 것은 기본적으로 새로운 것이 출시되는 날에 바로 그것을 항상 시도한다는 뜻입니다. Claude Code가 나오면 사용해 보는 것입니다. slash goal이 나오면 시도해 보는 것입니다.

최첨단에 가까이 머무르는 것이 중요한 이유는 몇 가지 있습니다. 직접 스타트업을 운영하고 있다면, 최첨단에 가까이 머무름으로써 실제로 무엇을 만들어야 할지에 대한 새로운 아이디어를 많이 얻을 수 있습니다.

실제로 우리에게 이런 일이 일어났습니다. 우리는 Chorus라는 완전히 다른 앱을 만들고 있었는데, Claude Code를 사용하기 시작했습니다. 작년 2월 무렵 우리는 Claude Code의 열성 사용자였습니다. 그래서 전체 워크플로를 Claude Code 중심으로 만들기 시작했습니다. 저장소를 다섯 번 복제하기 시작했고, 그다음 worktree를 발견했으며, 조금씩 Conductor를 내부 도구로 만들었습니다. 최첨단에 가까이 머무르지 않았다면 이런 사실을 알아낼 수 없었을 겁니다.

스타트업을 하고 있지 않다면, 회사에서 최신 워크플로가 무엇인지 늘 알고 있는 사람이 되어야 합니다. 예전에는 소셜 그래프를 활용하면 최고의 워크플로에 관한 중요한 정보가 여러분에게 자연스럽게 흘러들어왔습니다. 하지만 지금은 너무 빠르게 움직입니다. 그렇게 하면 항상 3~6개월 뒤처지게 됩니다.

그러니 최첨단에 가까이 머무르는 것이 매우 중요합니다. 여기서 중요한 단어는 ‘가까이’입니다. 최첨단에 있으면 위험이 있습니다. 제가 ‘중간 정도로 똑똑한 밈 만들기(midwit memeing)’라고 부르는 일을 할 수 있습니다. 실제 일을 하지 않고 워크플로를 다듬는 데 모든 시간을 쓰는 것입니다.

우리는 내부적으로 이를 판단하기 위한 경험칙(heuristic)을 만들었습니다. “시장을 이기려 하지 말라(don’t beat the market)”고 부릅니다. 시장을 이기려 하지 마세요.

여기서 사용하는 개념, 즉 최첨단에 가까이 있는지 아니면 최첨단에 도달해 최신 유행에 지나치게 깊이 빠져 있는지 판단할 때 써야 할 경험칙은 스스로 이렇게 묻는 것입니다. “왜 이 워크플로가 기본값이 아닐까?”

예를 들어 Ralph 루프(Ralph loops)가 큰 유행이 되기 시작했을 때, 스스로 이렇게 물어야 합니다. “Ralph 루프와 함께 작동하도록 내 워크플로를 최적화하는 데 엄청난 시간을 써야 할까?” Ralph 루프가 모두에게 효과적이고 기본값이라면, 아마 Anthropic이나 OpenAI, 혹은 누군가가 이 워크플로를 기본 하네스(harness)에 넣어 줄 때까지 기다리는 편이 낫습니다.

이를 일종의 효율적 시장 가설(efficient-market hypothesis)로 생각할 수 있습니다. 진짜 알파(real alpha)가 없다면 워크플로를 지나치게 최적화해서는 안 됩니다.

여기서 ‘진짜 알파’란 사용자나 코드베이스에 관한 정보 중 모델이 알지 못할 수도 있는 어떤 정보를 뜻합니다.

우리의 예를 들면, 우리는 채팅 앱입니다. 매우 긴 채팅을 아주 빠르게 렌더링해야 하고, 성능이 중요합니다. 따라서 채팅을 빠르게 렌더링하도록 React 쿼리를 최적화하는 데 많은 시간을 써야 합니다. 이를 위해 코드베이스의 다른 부분에서는 희생을 감수할 의향이 있습니다.

알파가 있다면, 즉 만들고 있는 앱에 대해 모델이 모를 수도 있는 정보가 있다면 워크플로에 시간을 투자해야 합니다. 그렇지 않다면 중간 정도로 똑똑한 밈을 만들지 마세요. 놀라운 Emacs 설정을 갖추고도 실제로는 일을 해내지 못하는 사람이 되지 마세요.

Conductor에는 슬롭 없는 구역이라는 용어가 있습니다. 슬롭 없는 구역은 코드베이스의 일부나 앱의 일부로, 매우 엄격한 사람의 검토가 필요한 곳입니다.

이런 면에서 우리는 사실 조금 특이합니다. 많은 사람이 우리가 순수한 토큰 극대화자(token maxer)라서 3만 줄짜리 PR을 마구 처리한다고 생각하는 것 같습니다. 하지만 실제로는 그렇지 않습니다. 코드베이스의 특정 부분에는 상당히 신중하고, 다른 부분에는 매우 느슨합니다.

이것이 중요한 이유는 슬롭 없는 구역을 신중하게 관리하지 않으면 코드베이스가 매우 곤란한 상태에 빠질 수 있기 때문입니다. 실제로 우리에게 이런 일이 있었습니다. 슬롭 없는 구역에 주의를 기울이지 않아서 앱 전체를 몇 번이나 다시 작성해야 했습니다.

구체적으로 우리에게는 마이그레이션 파일(migrations file)이 있고, CI에서는 마이그레이션 파일의 변경 사항을 사람이 검토해야 합니다.

또한 Slack에 작성된 것은 무엇이든 슬롭이 없다고 간주합니다. AI가 작성한 것이 아니라 사람이 작성한 것이기 때문입니다.

모든 문서, CLAUDE.md 파일, 모든 스킬(skill)에 대해 우리는 좋은 상태로 만들기 위해 엄청난 시간을 투자합니다. 최고의 빌더들을 가까이에서 지켜보며 본 또 다른 공통점이기도 합니다. 그들은 CLAUDE.md나 스킬 파일에 비정상적으로 많은 시간을 투자합니다.

이 문제를 생각하는 또 다른 방식은 이렇습니다. 새로운 인턴이 회사에 합류했고, 그 인턴이 일을 시작할 때마다, 매일, 자리에 앉을 때마다 귓속말로 무언가를 전해 줄 기회가 있다고 해 봅시다. 아마 그 인턴의 귀에 무엇을 속삭일지 많은 고민을 할 것입니다.

CLAUDE.md나 AGENTS.md가 바로 그런 것입니다. 에이전트가 일을 시작할 때마다 컨텍스트에 불러오는 정보입니다. 따라서 여기에 많은 고민을 기울이고 싶을 겁니다.

Conductor에는 Conductor 내부 에이전트(Conductor Internal Agent)라고 부르는 내부 도구가 있습니다. CIA라고도 부릅니다. CIA는 조직에서 일어나는 모든 일의 중앙 데이터베이스와 기본적으로 같습니다.

새로운 Slack 메시지가 전송될 때마다 CIA가 이를 가져옵니다. CIA 에이전트는 Slack에 새 메시지가 전송된 것을 확인하고, 이를 가져와 Postgres 테이블에 저장합니다.

Discord에서 사용자가 버그를 요청할 때마다 같은 일이 일어납니다. 회의가 있을 때마다 이를 녹화하고, 그 내용이 CIA로 들어갑니다.
