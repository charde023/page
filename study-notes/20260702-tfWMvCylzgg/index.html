FABLE이 돌아왔습니다! (Sonnet 5도 함께 나왔습니다)

한 줄 요약

Fable 5는 수출 제한 해제로 복귀 가능성이 커졌고, Sonnet 5는 하위 에이전트(sub-agent)와 오케스트레이션(orchestration)은 흥미롭지만 실제 코딩 작업에서는 느리고 비싸며 아직 Opus나 GPT-5.5를 대체하기 어렵다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
Fable 5 수출 제한 해제 API로 모델을 서비스에 붙이는 사업자에게 직접 영향이 있다 수출(export), 재수출(re-export), 국내 이전(in-country transfer) 제한이 풀려 API 서비스 제공 가능성이 커졌다
Sonnet 5의 에이전트성(agentic capability) 단순 답변이 아니라 계획, 도구 사용, 하위 에이전트 분배가 AI 코딩의 핵심이 되고 있다 Sonnet 5는 Fable 5처럼 일을 쪼개고 하위 에이전트를 쓰려는 행동을 보인다
토큰 효율(token efficiency) 모델 단가가 싸도 토큰을 많이 쓰면 최종 비용은 비싸진다 Sonnet 5는 토큰을 과하게 쓰며 실제 작업 비용이 Opus나 GPT-5.5보다 높아질 수 있다
벤치마크 오염(contamination) 공개된 테스트 데이터가 학습에 들어가면 점수가 실제 실력처럼 보이지 않는다 SWE-bench 같은 벤치마크는 이미 알려진 PR 재현에 가까워 신뢰도가 낮다
모델 라우팅(model routing) 어떤 작업에 어떤 모델을 부를지 정해야 비용과 품질을 동시에 잡을 수 있다 작은 작업은 Sonnet, 어려운 작업은 Opus/Fable처럼 역할 분리가 필요하다

내가 모를 만한 것 / 처음 보는 것

  • 수출 통제(export control) — 특정 AI 모델을 외국인·해외 사용자에게 제공하는 것을 제한하는 규제.
  • 재수출(re-export) — 한 번 수출된 기술이나 서비스를 다시 제3국 또는 제3자에게 제공하는 행위.
  • 간주 수출(deemed export) — 미국 내에 있어도 외국 국적자에게 기술을 제공하면 수출로 간주하는 개념.
  • 에이전트 오케스트레이션(agent orchestration) — 여러 AI 에이전트에게 일을 나누고 순서를 조율하는 방식.
  • 하위 에이전트(sub-agent) — 큰 작업의 일부를 맡는 보조 AI 작업자.
  • BrowseComp — 웹 탐색 기반 에이전트 검색 평가 벤치마크.
  • OSWorld verified — 컴퓨터 사용 능력을 평가하는 벤치마크.
  • Cursor Bench — AI 코딩 도구 Cursor 환경에서 모델 성능과 비용을 비교하는 벤치마크.
  • SWE-bench — 실제 오픈소스 이슈와 PR을 바탕으로 코드 수정 능력을 평가하는 벤치마크. 화자는 오염 가능성이 높다고 비판한다.
  • 토큰 호그(token hog) — 필요 이상으로 토큰을 많이 소비하는 모델을 비유적으로 부르는 표현.
  • 사고 흔적(thinking trace) — 모델 내부 추론 과정이 사용자에게 노출되는 텍스트.

화자의 디테일 (놓치기 쉬운 포인트)

화자가 흘리듯 말한 구체 수치·설정값·명령어·뉘앙스. 원어 용어 괄호 병기, 맥락까지.

  1. Fable 5는 6월 12일, 출시 3일 만에 제한되었고 이후 제한이 철회되었다 — 보안 취약점 탐색과 탈옥(jailbreak) 능력이 문제였다고 설명한다.
  2. Sonnet 5 초기 가격은 8월 31일까지 입력 100만 토큰당 2달러, 출력 100만 토큰당 10달러 — 이후 일반 Sonnet 가격인 입력 3달러, 출력 15달러로 돌아간다고 한다.
  3. Artificial Analysis 기준 전체 벤치마크 실행 비용에서 Sonnet 5가 약 6,000달러로 가장 비쌌다고 추정 — Fable 5의 약 5,600달러보다 높다고 언급한다.
  4. GPT-5.5 x-high가 실제 작업 기준 Sonnet보다 2배 이상 저렴하다고 주장 — 단가가 아니라 완료 비용(cost per task)을 봐야 한다는 논지.
  5. 물고기 웹 게임 재구현 테스트에서 Opus 4.8은 약 26~27분, GLM 5.2는 약 35~40분, Sonnet 5는 최소 2시간 이상 걸렸다 — Sonnet 5가 하위 에이전트를 과도하게 띄운 사례.
  6. GLM 5.2 테스트 비용은 8.30달러 — Open Code를 사용했기 때문에 비용을 확인할 수 있었다고 한다.
  7. Skatebench에서 Sonnet 5 X High 점수는 37%, Max는 59% — Max는 평균 질문당 15센트, 일부 오답 질문은 1달러까지 들었다고 한다.
  8. Sonnet 5 Max는 평균 토큰이 1,600개에서 6,000개로 증가 — 어려우면 계속 빙빙 도는 성향을 비용 문제의 원인으로 본다.
  9. 악성 요청 거절 테스트에서 Sonnet 5는 악성 요청 거절률 92.3%, 의심스럽지만 정상인 요청 성공률은 92% 미만 — 과잉 거절(false refusal)이 늘었다고 비판한다.
  10. Claude.ai에서 Sonnet 5가 사고 흔적(thinking trace)을 노출하는 버그 사례가 있었다고 전한다 — “let me”가 한 페이지에 21번 등장했다는 예시를 든다.

3 벤치마크와 비용 점수보다 실제 작업당 비용과 토큰 효율이 문제다
4 실제 코딩 테스트 Sonnet 5는 하위 에이전트를 많이 쓰지만 느리고 결과 품질도 아쉬웠다
5 안전성과 과잉 거절 안전성은 강화됐지만 정상 작업까지 거절할 가능성이 커졌다
6 최종 평가 Sonnet 5는 직접 쓰는 대체재보다 더 똑똑한 모델이 호출하는 도구에 가깝다

1. Fable 5 제한 해제: API 서비스에 중요한 이유

화자는 먼저 Claude 팬에게 큰 뉴스가 두 가지 생겼다고 말한다. 하나는 새 모델 Sonnet 5 출시이고, 더 중요한 다른 하나는 Fable 5 제한 해제다.

Fable 5는 출시 직후 보안 문제 때문에 제한되었다. 특히 모델이 소프트웨어 취약점을 찾거나, 탈옥(jailbreak)을 통해 위험한 행동을 할 수 있다는 우려가 있었다. 미국 정부는 외국 행위자(foreign actor)나 외국 국적자(foreign national)가 이런 능력을 쓰는 것을 막고자 했다.

하지만 Anthropic이 미국 정부와 협력해 보안 위험 탐지, 악성 활동 보고, 향후 모델 공개 프로토콜 협의 등을 약속하면서 제한이 철회되었다. 화자가 특히 중요하게 본 부분은 수출(export)과 재수출(re-export) 제한 해제다.

즉, T3Chat 같은 서비스가 API로 모델을 호스팅하고 사용자가 그 모델을 호출하는 방식도 허용될 가능성이 높아졌다는 뜻이다. AI 모델을 직접 판매하지 않더라도, API 기반 서비스 운영자에게 규제는 매우 중요하다.

2. Sonnet 5의 핵심은 “Sonnet”이 아니라 “5”

화자는 많은 사람이 Sonnet 5를 “Sonnet 4.8이어야 했다”고 말하지만 동의하지 않는다. 이유는 Sonnet 5의 핵심이 성능표의 단순 점수가 아니라 Fable 5와 비슷한 에이전트 행동에 있기 때문이다.

Anthropic은 Sonnet 5를 가장 에이전트적인 Sonnet 모델이라고 설명한다. 계획을 세우고, 브라우저(browser)와 터미널(terminal) 같은 도구를 사용하며, 몇 달 전에는 더 큰 모델에서나 가능했던 수준으로 자율 작업을 수행할 수 있다는 주장이다.

화자는 Anthropic의 모델 계층이 한 단계씩 올라간 것 같다고 말한다.

  • 예전 Haiku 역할을 이제 Sonnet이 한다.
  • 예전 Sonnet 역할을 이제 Opus가 한다.
  • 예전 Opus 역할을 이제 Fable이 한다.

이는 사용자 입장에서는 더 비싼 모델을 쓰게 만드는 구조이기도 하다.

3. 벤치마크: 좋아 보이지만 비용까지 보면 애매하다

Sonnet 5는 여러 벤치마크에서 개선을 보인다. Terminal Bench는 60% 후반대에서 80%대로 개선되었고, Humanity’s Last Exam도 상승했다. 지식 작업(knowledge work)에서는 Opus 4.8보다 약간 높게 나온 부분도 있다고 한다.

하지만 화자는 여러 문제를 지적한다.

첫째, SWE-bench는 오염(contamination)이 심하다고 본다. SWE-bench는 과거에 이미 병합된 실제 PR을 설명만 보고 재현하는 테스트에 가깝기 때문에, 모델이 학습 데이터에서 봤을 가능성을 배제하기 어렵다는 것이다.

둘째, 작업당 비용(cost per task) 관점에서 Sonnet 5가 좋지 않다. 토큰 단가는 낮아 보여도, 실제로는 토큰을 많이 쓰기 때문에 전체 작업 비용이 커진다.

셋째, GPT-5.5와 비교하면 비용 대비 성능이 더 애매해진다. Cursor Bench 기준으로 GPT-5.5 Medium이 Sonnet 5 Max에 가까운 점수를 내면서도 비용은 훨씬 낮다고 설명한다.

4. Sonnet 5의 진짜 문제: 토큰을 많이 쓰고 느리다

Anthropic은 Sonnet 5가 더 싸다고 말한다. 실제로 초기 가격은 입력 100만 토큰당 2달러, 출력 100만 토큰당 10달러다. 하지만 화자는 토큰당 가격만 보면 안 된다고 강조한다.

모델이 같은 일을 끝내기 위해 토큰을 두 배, 다섯 배, 열 배 쓰면 최종 비용은 더 비싸진다.

화자는 Sonnet 5가 실제 작업에서 매우 비효율적이라고 말한다. Opus보다 거의 2배 많은 토큰을 쓰고, GPT-5.5 x-high보다도 훨씬 많은 토큰을 쓴다고 한다. 특히 Claude Code에서 $200 요금제를 쓰는 사람도 사용량 퍼센트가 빠르게 줄어드는 사례를 봤다고 한다.

5. 실제 테스트: 물고기 웹 게임 재구현

화자는 자신의 물고기 웹 게임 저장소(repo)를 세 모델에게 주고, 기존 코드를 참고하되 처음부터 새 게임을 다시 만들라고 했다.

Opus 4.8

Opus 4.8은 약 26~27분 만에 결과물을 만들었다. UI에는 패딩 같은 세부 문제가 있었지만, 게임 조작감과 핵심 메커니즘은 좋았다. 특히 게임 경제 밸런스가 잘 맞아 실제로 플레이할 만했다고 평가한다.

GLM 5.2

GLM 5.2는 약 35~40분이 걸렸고, 비용은 8.30달러였다. UI를 더 많이 바꾸었지만 결과가 마음에 들지는 않았다고 한다. 움직임이 끊기고, 배경 렌더링이 이상하며, 경제 밸런스도 나빴다. 또 GLM 모델은 비전(vision)이 없어 브라우저 화면을 직접 보고 판단할 수 없다는 한계가 있었다.

Sonnet 5

Sonnet 5 결과물은 가장 실망스러웠다. 기본 물고기가 없고, 펫 렌더링이 좋지 않으며, 구매 버튼을 누르면 총도 같이 발사되는 식의 버그가 있었다. 이런 버그는 예전 모델에서나 기대하던 수준이라고 말한다.

더 큰 문제는 시간이 최소 2시간, 길게는 2시간 30분 가까이 걸렸다는 점이다. Sonnet 5는 사용자가 요청하지 않았는데도 하위 에이전트를 여러 개 띄웠다. 기존 코드 분석, 계획 작성, 계획 검토, 구현 등으로 일을 쪼개고 각각 에이전트를 호출했다.

이 지점이 Sonnet 5의 장점이자 단점이다. 일을 나누고 오케스트레이션하는 능력은 흥미롭지만, 모델 자체가 충분히 똑똑하지 않으면 불필요하게 빙빙 돌고 비용과 시간이 폭증한다.

6. Sonnet 5는 “주니어 엔지니어” 같은 모델

화자는 Sonnet 5가 왜 Opus보다 비쌀 수 있는지 엔지니어 비유로 설명한다.

시니어 엔지니어가 시간당 100달러이고, 주니어 엔지니어가 시간당 20달러라고 하자. 어떤 작업을 시니어가 10시간에 끝내면 1,000달러다. 주니어가 같은 10시간에 끝내면 200달러로 싸다.

하지만 주니어가 그 일을 해결하지 못하고 100시간을 쓰면 2,000달러가 된다. 즉, 시간당 단가가 낮아도 오래 걸리면 더 비싸다.

Sonnet 5도 마찬가지다. 작은 작업을 잘 맡기면 싸게 끝날 수 있다. 하지만 모델 능력을 넘어서는 작업을 맡기면 계속 시도하면서 토큰을 낭비하고, 결국 Opus나 Fable을 처음부터 쓰는 것보다 비싸질 수 있다.

7. 안전성: 위험하다기보다는 과잉 거절이 문제

화자는 Sonnet 5가 특별히 큰 안전 위험은 아니라고 본다. 오히려 “너무 똑똑하지 않아서” 큰 위험은 낮다고 말한다. GLM 5.2가 보안 위험 측면에서는 더 의미 있는 위험이라고 평가한다.

하지만 문제는 과잉 거절(false refusal) 이다. Anthropic의 테스트에서 Sonnet 5는 악성 요청을 92.3% 거절했지만, 의심스러워 보이지만 정상적인 요청을 제대로 처리하는 비율은 92% 미만으로 떨어졌다. 이전 Sonnet 4.6은 같은 벤치마크에서 97% 수준이었다고 한다.

즉, 정상적인 보안 보고, 개발 작업, 이중용도(dual-use) 작업까지 거절할 수 있다.

8. 사고 흔적 노출과 비효율적 추론

화자는 일부 Claude.ai 계정에서 Sonnet 5가 사고 흔적(thinking trace)을 계속 노출하는 버그가 있다는 제보를 소개한다.

예를 들어 사용자가 “Theo Brown이 누구냐”고 묻자 모델은 웹 검색을 할지, 어떤 도구를 쓸 수 있는지, 시스템 태그가 무엇인지 등을 자기 자신에게 길게 말한 뒤 마지막에야 답변을 생성했다.

9. 최종 평가: 직접 대체재가 아니라 도구로 봐야 한다

화자의 결론은 명확하다.

Sonnet 5는 다음과 같은 용도에 더 맞다.

  • 더 똑똑한 모델이 호출하는 보조 모델
  • Fable 5나 Mythos 5가 나눈 작은 작업을 처리하는 모델
  • 도구(tool), API, 워크플로 내부에서 특정 작업을 맡는 모델
  • 명확하고 작은 범위의 작업을 저렴하게 처리하는 모델

이 실행은 완료까지 최소 2시간이 걸렸습니다. 정확히 시간을 재지는 않았지만 시작과 끝을 대략 알고 있고, 2시간 이상, 어쩌면 2시간 30분에 가까웠습니다. 오래 걸린 이유 중 하나는 작업 중에 하위 에이전트(sub-agent)를 많이 띄웠기 때문입니다. 제가 요청하지 않았습니다. 프롬프트는 단순했습니다. 그런데 이전 코드베이스를 조사하는 에이전트, 계획을 작성하는 하위 에이전트, 계획을 분석하는 에이전트, 구현하는 에이전트를 계속 띄웠습니다. 이후 할 일 목록을 만들고 하나씩 처리한 뒤, 마지막에 빠르게 사용해 보고 완료됐다고 했습니다.

Sonnet에서 흥미로웠던 또 다른 점은 Opus보다 질문을 훨씬 많이 했다는 것입니다. Opus는 질문을 하지 않았고, Sonnet은 몇 가지 질문을 했습니다. 질문 자체는 꽤 좋았습니다. 프로젝트 범위를 정하는 데 도움을 주려는 질문이었습니다.

이것이 앞에서 말한 숫자 5의 의미입니다. 이 모델이 흥미로운 이유는 가성비가 좋거나 벤치마크가 훌륭해서가 아닙니다. Fable 5에서만 봤던 행동을 보이기 때문입니다. 하위 에이전트를 좋아하고, 그것들을 조율할 줄 압니다. 일을 작은 조각으로 나누고 넘겨주며 작업 흐름을 유지하려고 합니다. 이것이 Fable 5를 특별하게 만든 특징입니다. 문제는 Sonnet이 그걸 잘할 만큼 충분히 똑똑하지 않다는 것입니다.

그래서 자주 빙빙 돌고 오래 걸립니다. 쪼갤 필요가 없는 일도 쪼개기 때문에 시간과 비용이 늘어납니다. 저는 Skatebench의 버그도 몇 개 맡겨봤지만 너무 오래 걸려 포기하고 GPT-5.5 Medium fast로 돌아갔습니다. Max 버전은 너무 느려서 Bun의 fetch 구현 내부 타임아웃에 걸리기도 했습니다. Max 버전은 정말 토큰을 많이 먹습니다.

Skatebench는 스케이트 트릭 설명을 보고 이름을 맞히는 벤치마크입니다. 오염이 생겨서 이후에는 공개되지 않은 개인 저장소에 질문 수를 두 배로 늘렸습니다. 요즘은 Gemini 3.1 Pro만 95%로 90점대이고, 나머지는 대체로 80점대 이하입니다. 가장 나쁜 점은 Sonnet 5가 모르는 문제를 만나면 빙빙 도는 것을 좋아한다는 것입니다. X High에서 Max로 올리면 평균 토큰이 1,600개에서 6,000개로 증가했습니다. Max는 해결할 때까지 계속 가도 된다는 허가를 주는 것처럼 보입니다.

왜 Sonnet 모델이 Opus보다 비쌀 수 있는지 헷갈리는 사람이 많았습니다. 비유를 들어보겠습니다. 회사 CEO에게 엔지니어 두 명이 있습니다. 한 명은 아주 뛰어난 시니어 엔지니어이고 시간당 100달러입니다. 다른 한 명은 주니어 엔지니어이고 시간당 20달러입니다.

조금 어렵지만 할 만한 작업을 시니어에게 주면 10시간에 끝냅니다. 비용은 1,000달러입니다. 같은 일을 주니어에게 주면 10시간에 끝낼 수도 있고, 그러면 200달러입니다. 하지만 100시간이 걸리면 2,000달러입니다.

중요한 질문은 이것입니다. 주니어 엔지니어가 더 많은 시간을 쓴다고 정답 가능성이 올라갈까요, 내려갈까요? 그 사람 능력 안에 있는 작업이면 빠르게 해결할 것입니다. 능력 밖이면 오래 붙잡고 있을 것입니다. 이렇게 불필요하게 비싼 실행이 생깁니다. 모델이 비싸게 만들어져서가 아니라, 충분히 똑똑하지 않아도 답을 낼 때까지 계속 가도록 만들어졌기 때문입니다.

그래서 엔지니어의 일이 다시 중요해집니다. 모델이 자기 자신의 어떤 버전을 써야 하는지 도와줘야 합니다. Fable로 오케스트레이션한다면, 작은 작업에는 Sonnet을 고르고 더 지능이 필요한 작업에는 Opus나 Fable을 고르게 해야 합니다. 이 균형을 맞추면 큰돈을 아낄 수 있지만, 틀리면 처음부터 시니어 모델을 쓰는 것보다 Sonnet이 더 비싸집니다.

Sonnet 시스템 카드에도 이를 확인해주는 흥미로운 내용이 있습니다. Frontier Code 수치가 있는데 제가 좋아하는 벤치는 아닙니다. 특히 추론 수준이 올라간다고 성공률이 항상 올라가지는 않습니다. 오르락내리락합니다.

Sonnet은 작업당 1달러 미만, 약 75센트 수준에서 Max 버전의 12달러까지 올라갑니다. 비용이 올라갈수록 성공 가능성은 의미 있게 높아지지만, 달러당 효율이 더 좋은 모델이 많습니다. High 범위에 들어가면 Fable이 같은 계층에서 더 싸고 더 똑똑합니다. Sonnet 5 High는 Fable 5 Low 점수의 대략 3분의 2 수준인데 비용은 비슷합니다. 이런 작업에서는 Sonnet의 가치가 높아 보이지 않습니다. 다만 Low와 Medium 버전은 괜찮은 가치일 수 있고, Fable이 언제 그것들을 하위 에이전트로 써야 할지 배운다면 비용을 절약할 수 있습니다.

Cursor Bench를 보면 더 이상합니다. GPT-5.5와 Fable 5가 가격 대비 성능의 상단선을 만드는 것처럼 보입니다. GPT-5.5로 할 수 있는 작업이면 저는 그것을 씁니다. 주어진 추론 예산에서 일을 잘 끝내기 때문입니다. Fable 5는 보통 2배 이상 비싸지만, 다른 모델이 못 내는 최고 점수를 냅니다.

그래서 Sonnet 5는 제 일상 코딩 작업에 잘 맞지 않습니다. 직접 선택해서 쓰는 모델이라기보다, 에이전트나 도구나 API가 호출하는 모델에 가깝습니다. Claude Code에서 Sonnet 5를 선택하면 멋진 에이전트 행동을 볼 수 있고, 그 점은 기대됩니다. Fable이 큰 작업을 복잡한 워크플로로 나누고, 그 하위 워크플로가 Sonnet을 쓰며, Sonnet도 필요하면 더 나눌 수 있는 세계를 상상해볼 수 있습니다. 그래서 Anthropic이 이 모델에 5라는 숫자를 붙였다고 봅니다.

저는 Opus 5도 기대합니다. 다만 Anthropic이 정부가 그 공개를 허용하지 않을까 봐 두려워했을 수 있고, 그래서 대신 Sonnet 5를 내놓은 것 같습니다.

Anthropic의 안전 벤치마크 중에는 악성 요청은 거절해야 하고, 의심스러워 보이지만 정상인 요청은 처리해야 하는 테스트가 있습니다. Mythos 5는 악성 요청의 90%를 거절하면서도 이중용도 요청은 99.6% 처리했습니다. Sonnet 5는 악성 요청 거절률이 92.3%로 약간 더 높지만, 정상 요청 성공률은 92% 미만으로 떨어졌습니다. 이건 정말 좋지 않습니다. 거절하지 말아야 할 작업까지 거절할 것입니다. 이전 Sonnet 4.6은 같은 벤치에서 97%였습니다.

예시 중 하나는 회사의 AI 모델 가중치를 훔치려는 직원을 보고하기 위해 개발자의 보안 보고 메커니즘을 시뮬레이션하는 작업입니다. 이 모델이 사용자가 자기 가중치를 훔치려 한다고 생각하면 이상하게 행동할 수 있습니다.
