  • Agent View (claude agents): Claude Code 0.x 이후 추가된 터미널 내 멀티에이전트 대시보드

  • Ctrl+X: 특정 인스턴스 삭제
  • 워크트리(Worktree): git worktree를 이용해 같은 레포에서 브랜치별 독립 파일시스템 생성 — 병렬 기능 개발 시 충돌 방지
  • Agent Team: 단일 오케스트레이터 세션이 내부적으로 서브 에이전트를 관리해 merge conflict 자동 조율
  • Haiku 내부 사용: 빠른 자동완성·제안 응답에 Claude Haiku를 under the hood로 사용
  • Self-automated loop: PRD + 테스트 harness 품질이 충분하면 에이전트가 자율 루프 실행 → 사람은 방향만

화자의 디테일 (놓치기 쉬운 포인트)

  1. claude agents를 다시 실행하면 이전에 닫았던 터미널의 모든 인스턴스가 복원된다 — 세션이 백그라운드에서 계속 실행 중이었기 때문.
  2. 인스턴스 이름 포맷: "프로젝트명 + 고수준 태스크" (예: hermes-trip-home-screen) — 라벨이 없으면 무슨 작업인지 금방 잊음.
  3. 핀 기능(pin): 중요한 인스턴스를 상단 고정 가능.
  4. Haiku가 자동완성·빠른 reply에 쓰인다고 명시적으로 언급 — 비용·속도 고려된 내부 설계.
  5. 색상 코드 정확값: 노랑=waiting(실패 체크 중), 초록=done(머지 완료), 회색=working(실행 중), 보라=merging(워크트리 머지 진행 중).
  6. 병렬 워크트리 사용 시 "어떤 기능을 작업하는지 신중하게 구분" 하면 merge conflict가 크지 않다고 강조 — 무작정 병렬화는 지양.
  7. Ctrl+X 두 번: 인스턴스 삭제 확인(두 번 눌러야 적용).
  8. 화자는 tmux 대체로 Agent View를 평가 — "더 이상 tmux가 필요 없다".
  9. 모델 abstraction 방향: "AI 랩들이 supervise에서 멀어지고, 루프 밖에서 guidance/direction을 주는 방향으로 이동 중" — 매 업그레이드마다 스택에서 한 단계 위로 추상화.
  10. 트립 추적 앱 시연 시 한 인스턴스에서 로컬 서브에이전트를 스폰해 동시에 여러 작업을 처리하는 모습을 보여줌.

1. 문제 정의 — 기존 방식의 한계

Claude Code를 혼자 사용할 때 가장 흔한 패턴은 창 하나 + 인스턴스 하나였다. 영상이 끝날 때까지 기다리는 방식. 그 다음으로 많이 시도하는 건 tmux나 터미널 앱의 여러 pane을 만들어 각 프로젝트별로 분리하는 것이다. 화자 본인도 newsletter, booker 같은 이름으로 pane을 라벨링해 여러 인스턴스를 관리했다고 설명한다.

문제는 클럭킹(컨텍스트 전환) 능력이 부족하면 금방 혼란스러워진다는 것. Codex나 Claude 앱이 사이드바로 프로젝트를 구분한 것과 같은 맥락에서, Agent View는 이 오케스트레이션 레이어를 터미널 안에 내장한 것이다.

2. Agent View 개요

claude agents를 입력하면 현재 실행 중인 모든 Claude Code 인스턴스를 한 화면에서 볼 수 있다.

핵심 특성: - 세션 영속: 터미널을 완전히 닫아도 인스턴스가 백그라운드에서 유지된다. 다시 claude agents를 치면 그대로 복원됨. - 디렉토리 기반 그룹핑: 각 인스턴스는 자신의 Claude Code 프로젝트 컨텍스트를 유지 → 컨텍스트 오염 방지. - 시각적 상태: 색상 코드로 즉시 상황 파악 가능. - 내부적으로 빠른 응답에 Haiku 사용.

3. 단축키 실전 정리

단축키 동작
→ 인스턴스 attach (진입)
← (빈 프롬프트) 인스턴스 detach (빠져나옴)
Space Peek 모드 — 진입 없이 빠른 확인·응답
Ctrl+R 인스턴스 이름 변경
Ctrl+S 디렉토리별 그룹핑 노출 토글
Enter (그룹 이름) 그룹 접기/펼치기

권장 이름 포맷: <프로젝트명>-<고수준태스크> (예: hermes-trip-home-screen)

4. 색상 상태 코드

색상 의미
회색 작업 중 (실행 중)
노랑 대기 중 (실패 여부 체크 중)
초록 완료 (모두 통과, 머지됨)
보라 머지 진행 중 (워크트리 머지)

5. 병렬 개발 패턴

워크트리(Worktree) + Agent View 조합이 핵심이다.

새 인스턴스를 생성할 때 git worktree를 활용하면 같은 레포의 서로 다른 브랜치를 독립된 파일 시스템에서 작업할 수 있다. 기능 경계를 잘 나누면 merge conflict가 크지 않다. 더 자동화된 방식은 Agent Team — 단일 오케스트레이터 세션이 내부 서브에이전트의 충돌을 알아서 조율한다.

핵심 선택지:

  • 수동 Worktree: 기능별로 직접 인스턴스를 만들어 병렬 실행. 결과 merge는 직접 처리.
  • Agent Team: 오케스트레이터가 서브에이전트를 스폰·조율. 더 자율적이나 스펙 품질이 전제.

6. Plan-first 워크플로 (가장 중요한 멘탈 모델)

화자가 실제로 쓰는 방식:

  1. Plan Mode에서 몇 시간 — PRD, 투두, 아키텍처를 엔지니어링 수준으로 정제.
  2. 각 인스턴스에 세분화된 기능 스펙 할당.
  3. 자동화 루프를 돌릴 harness(테스트·검증 자동화) 준비.
  4. 인스턴스 실행 → 가끔 들여다보고 방향 수정만.

요점: 에이전트가 자율 루프를 돌게 하려면 PRD와 harness의 품질이 핵심이다. 손잡고 다니는 방식으로는 병렬화의 이점을 못 얻는다.

7. 데모 — 트립 추적 앱

화자는 trip-home-screen 인스턴스와 active-dash-screen 인스턴스를 동시에 열고 각각 다른 화면의 UI를 빌드했다. 각 인스턴스에 PRD와 디자인 참조를 넘기고 자율 실행. Agent View에서 두 인스턴스가 동시에 회색(작업 중) 상태로 표시되는 것을 확인할 수 있었다.

전체 전사 펼치기

안녕하세요, Claude Code가 Agent View를 출시했는데 제가 생각하기에 이게 굉장히 멋진 신기능입니다. 혁명적이라고는 할 수 없지만 분명히 제 일상 작업에서 쓸 기능입니다.

이 영상에서는 문서를 좀 더 소화하기 쉽게 설명하는 고수준 슬라이드를 준비했습니다. 직접 Claude Code 문서를 읽어보셔도 좋고요. 시연을 위해 트립 추적 앱을 준비해서 그냥 재미로 만들어볼 겁니다.

Agent View가 뭔가요? 기본적으로 claude agents를 입력하면 보이는 화면이 Agent View입니다. Claude Code 위에 바로 얹힌 엔드투엔드 오케스트레이션입니다. 마우스 클릭도 지원하고 키보드 단축키도 됩니다.

왜 이게 필요한가 — 기존의 문제점

Agent View 이전에는 창 하나에 인스턴스 하나가 일반적인 방식이었습니다. 그냥 지켜보면서 기다리는 거죠. 그 다음 단계로 많은 분들이, 저도 포함해서, 터미널 pane을 여러 개 만들어서 관리하는 방법을 시도했습니다. newsletter나 booker 같은 이름으로 pane을 만들어 여러 프로젝트를 저글링하는 방식이죠.

문제는 컨텍스트 스위칭을 잘 못하면 압도당한다는 겁니다. 그래서 Codex 같은 경우엔 사이드바를 도입했고, Claude 앱도 비슷한 패턴이 있죠. Agent View가 바로 그 해결책입니다 — 모든 에이전트가 무엇을 하는지 한 화면에 보여주는 것.

터미널에서 진짜 살고 싶은 저에게는 이게 이상적인 형태입니다. 애니메이션이나 다양한 상태 표시에도 많은 공을 들인 것 같아서 마음에 듭니다.

세션 영속성

어떤 세션이 열려있었든, 어떤 디렉토리에서 실행하든 상관없이 유지됩니다. 터미널을 완전히 닫아도 다시 claude agents를 치면 모든 인스턴스가 다 거기 있습니다. 그래서 더 이상 tmux가 필요 없어요.

색상도 다양하게 상태를 표시하고 여러 상태가 있습니다.

키보드 단축키

키보드 단축키는 CLI 도구를 배울 때 정말 중요합니다. 마우스도 되지만 더 빠르고 좋습니다.

첫 번째로, 현재 있는 디렉토리에서 태스크를 시작할 수 있습니다. 여기서 뭔가 입력하면 됩니다. 예를 들어 "프로젝트 페이즈 2를 로드해줘" 같은 거요. 내부적으로 Haiku를 써서 이 응답 부분을 처리합니다.

제가 제일 먼저 하는 건 Ctrl+R로 인스턴스 이름을 바꾸는 겁니다. 프로젝트명 + 고수준 태스크 형태로요. 예를 들어 phase-two라고 이름 붙이면 내가 무슨 작업을 하고 있었는지 기억하기 편합니다.

회색은 작업 중이라는 뜻입니다. → 키를 누르면 해당 인스턴스로 attach(진입)됩니다. 프롬프트에 아무것도 없을 때 ←를 누르면 detach(빠져나옴)됩니다.

Peek 모드: Space를 누르면 peek 모드가 활성화됩니다. 인스턴스에 완전히 들어가지 않고 빠르게 내용을 확인하고 응답을 보낼 수 있습니다.

Pin: 중요한 인스턴스를 상단에 고정할 수 있습니다.

Ctrl+S: 디렉토리별 그룹핑을 노출합니다. 같은 프로젝트 디렉토리에서 여러 인스턴스를 묶어서 볼 수 있습니다. Claude Code에서 컨텍스트 엔지니어링이 중요한 만큼 프로젝트 스코프를 유지하는 게 중요합니다. 각 인스턴스는 자체 Claude Code 프로젝트입니다.

그룹 이름에서 Enter를 치면 그룹을 접을 수 있습니다.

핵심은 인스턴스를 빠르게 오가고 Peek으로 빠르게 확인하는 것 — whisper [?음성입력 도구]를 사용해서 빠르게 입력하는 것도 상상해볼 수 있습니다.

병렬 개발

이걸 쓰고 싶은 또 하나의 이유는 많은 작업을 병렬로 처리할 수 있다는 겁니다. 새 인스턴스를 만들 때 워크트리를 사용하면 여러 태스크를 충돌 없이 동시에 진행할 수 있습니다. 어떤 기능을 작업할지 신중하게 구분하면 merge conflict가 크지 않습니다. Agent Team을 사용해서 하나의 세션이 충돌을 관리하게 하는 방법도 좋은 옵션입니다.

중요한 멘탈 모델 전환

AI 랩들이 supervise 방향에서 멀어지고, 루프 밖에서 지침·방향만 주는 방향으로 이동하고 있다는 걸 이해하기 시작했습니다. 매 주요 모델·도구 업그레이드마다 스택의 한 단계 위로 추상화가 이동합니다.

색상 코드 정리: - 노랑: 대기 중 (실패 체크 중) - 초록: 완료 (통과, 머지됨) - 회색: 작업 중 - 보라: 머지 진행 중 (워크트리 머지)

Ctrl+X를 두 번 누르면 해당 인스턴스를 삭제합니다.

실제 빌드 흐름

트립 추적 앱을 예시로, Agent Team을 만들어 wave 3를 진행하는 방식을 보여줬습니다. 가장 극단적인 예시이고, 보통은 스펙이 잘 갖춰져 있으면 하나의 에이전트 팀이 전체를 처리하게 합니다.

실제로 동작하게 하려면 좋은 스펙, 좋은 PRD, 좋은 harness가 있어야 자동화 루프가 돌아가고 에이전트를 손잡고 다니지 않아도 됩니다.

예를 들어: "트립 홈 화면 작업해줘, PRD와 투두를 보고 디자인에 맞게 스펙을 계속 채워줘" — 이 인스턴스 이름을 hermes-trip-home-screen으로 변경. 또 다른 인스턴스: "액티브 대시 화면 작업해줘, PRD와 투두를 보고 디자인에 맞는지 확인해줘".

평소라면 PRD와 투두에 많은 시간을 쓰고, Plan Mode에서 아키텍처를 엔지니어링 수준으로 계획하고, 에이전트 팀이 실행하게 놔두는 방식입니다. 각 인스턴스에 특정 기능에 대한 매우 세분화된 스펙이 있고, 자동화 루프를 위한 harness가 있으면, Plan Mode에서 몇 시간을 쏟아 품질 높인 계획으로 그냥 실행시킵니다. 가끔 돌아봐서 방향 수정만 하는 거죠.

아이디어는 여러 에이전트가 동시에 실행되는 걸 하나의 뷰에서 보면서 이름 바꾸고 맥락을 조금씩 추가하는 라이브 뷰 — 그게 Agent View입니다.

Anthropic 개발자 데이 발표를 많이 봤는데, 많은 생각이 있어서 관련 영상을 더 만들 것 같습니다. 이 기능은 정말 멋지고, 자체 오케스트레이션 레이어를 찾고 있거나 여러 컨텍스트·인스턴스를 저글링하기 힘들었던 분들에게 도움이 될 것 같습니다. 저는 Claude Code에 더 중독될 것 같네요.
