먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 3분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

오래되어 구조를 파악하기 어렵고 변경 위험이 큰 코드(레거시 코드)는 AI에게 한꺼번에 고치라고 맡길수록 검토하기 어려워진다. 화자가 제시한 해법은 먼저 코드와 테스트의 빈틈을 그림처럼 진단하고(Cursor Canvas), 코드를 쓰기 전에 변경 범위와 검증법을 문서로 정하는 것(Plan Mode)이다. 그 계획을 목표·인수 조건·테스트가 적힌 작은 작업표(Jira 티켓)로 나눈 뒤, 원격 컴퓨터에서 작동하는 AI(Cloud Agent)에게 티켓별 PR을 맡긴다. 사람은 변경 내역과 테스트, 화면 녹화 같은 증거를 검토한다. 마지막으로 의존성 업데이트나 오래된 기능 플래그 정리를 정기 작업(Automations)으로 만들어 문제가 다시 쌓이는 것을 줄인다. 핵심은 AI의 자율성 자체가 아니라 작은 범위, 명시된 기준, 검토 가능한 증거로 변경 위험을 통제하는 데 있다.

여기까지만 이해하면 충분

  • AI가 코드를 쓰기 전에 현재 상태와 테스트 공백부터 확인한다.
  • 큰 변경은 검토 가능한 티켓과 PR로 나눈다.
  • 완료 주장은 테스트·스크린샷·영상 같은 증거와 함께 검토한다.
  • 반복되는 유지보수는 자동화하되 사람이 중단하고 개입할 수 있어야 한다.

비유와 깨지는 지점

건물 전체가 아닌 방별로 하는 보수 공사

먼저 건물 상태를 조사하고 도면을 만든 뒤, 방별 작업 지시서를 발행한다. 작업자는 각 방을 고치고 검사 결과를 남긴다. Canvas는 상태 조사, Plan Mode는 도면, 티켓은 작업 지시서, PR과 테스트는 검사 기록에 대응한다.

비유가 깨지는 지점: 소프트웨어는 저장소 간 의존성, 실행 환경, 비밀키, 자동 테스트와 CI를 함께 다뤄야 한다. 공사처럼 결과가 눈에 보이는 것만으로는 충분하지 않으며, 영상도 모든 내부 동작을 증명하지는 않는다.

1. 원인

AI 리팩터링에서 진단과 계획 없이 큰 작업부터 맡기면 왜 위험한가?

모범 답안 보기

변경 범위, 기존 테스트, 인수 조건이 불명확하면 에이전트가 무엇을 보존해야 하는지 판단하기 어렵다. 결과가 하나의 거대한 PR에 섞이면 사람도 오류 위치와 영향 범위를 검토하기 힘들다.

2. 대조

원격 에이전트가 작업을 끝냈다는 것과 변경이 안전하다는 것은 어떻게 다른가?

모범 답안 보기

작업 종료는 실행 상태에 관한 말이다. 안전성은 합의한 인수 조건, 테스트, CI, 변경 내역, 필요하면 화면 증거까지 검토해야 판단할 수 있다. 영상은 UI 동작의 증거가 될 수 있지만 모든 회귀를 증명하지는 않는다.

3. 적용

새 리팩터링 작업을 AI에게 맡긴다면 어떤 기준으로 범위와 검증법을 정해야 할까?

모범 답안 보기

한 화면이나 한 구성요소처럼 독립적으로 검토할 수 있는 범위를 고른다. 보존할 동작, 통과해야 할 테스트, 허용하지 않을 회귀를 먼저 적고 티켓별 PR을 요구한다. 자동 검증이 어려운 항목은 사람의 검토 지점으로 남긴다.

이번 글의 통찰

1. 좋은 자율 실행은 먼저 경계를 만든다

  • [원문] 화자는 Canvas로 테스트 공백을 살피고, Plan Mode에서 코드를 생성하지 않은 채 범위·구조·테스트 전략을 문서화한 뒤 티켓으로 나눴다.
  • [해석] 에이전트의 성능보다 먼저 결정할 것은 작업 경계와 완료 조건이다. 계획은 문서가 아니라 이후 결과를 판정하는 기준표다.
  • [경계] Canvas가 제안한 우선순위는 도구의 분석 결과이며 독립 검증되지 않았다. 라이브 계획은 profile을 기준으로 삼았지만, 뒤에 보여 준 완료 영상의 comments와 users는 이전 실행 사례이므로 같은 실행 결과로 합치면 안 된다.

2. 신뢰는 “자율성”이 아니라 검토 가능한 증거에서 나온다

  • [원문] 화자는 티켓마다 별도 PR을 만들고 테스트·스크린샷·영상으로 변경을 확인하라고 지시했다. 라이브 Cloud Agent는 세션 안에 완료되지 않아 이전 실행 영상을 대신 보여 줬다.
  • [해석] AI의 완료 보고를 그대로 믿기보다 계획, 코드 차이, 테스트 결과, 사용자 동작 증거를 서로 대조해야 한다.
  • [경계] 화자는 Phase One과 Phase Two를 자신에게 배정하려 했지만 에이전트는 “세 개의 순차 티켓”을 찾았다고 말했다. 실제 배정 수량은 전사만으로 확정할 수 없다. 전체 마이그레이션 비용이 3~4달러일 수 있다는 주장도 작업 조건과 청구 자료가 없어 검증되지 않았다.

3. 예방 자동화는 시연 아이디어와 운영 결과를 구분해야 한다

  • [원문] 화자는 매주 최근 30일 동안 사용되지 않은 기능 플래그를 찾고, 오류 도구와 대조한 뒤 제거 PR과 Slack 메시지를 만드는 자동화 예시를 구성했다.
  • [해석] 리팩터링은 밀린 문제를 한 번 치우는 일이고, 자동화는 같은 문제가 다시 쌓이는 속도를 줄이는 장치다.
  • [경계] 이 자동화는 제안·설정 시연이며 저장, 실행, 성공까지 확인된 사례가 아니다. 발표자 이름은 META에 없고 전사에서는 Amrita로 호명된다. 진행자 이름도 Reagan과 Regan으로 충돌한다. 모델명은 GPT-5.6-SOL과 GPT 5.6으로 달리 표기되어 같은 모델인지 확정할 수 없다. Canvas도 앞에서는 막대그래프로 바꾸라고 했지만 뒤에서는 막대그래프에서 원그래프로 바꿨다고 말해 중간 변경이 전사에 남아 있지 않다.

차드의 4렌즈

교육자 · 직접 전이

  • 관련성: 화자는 설명만 하지 않고 계획서, 티켓, PR, 테스트 영상처럼 관찰 가능한 산출물을 연결했다.
  • 통찰: 이해 여부도 “알겠다”보다 원인 설명, 작업 분할, 검증 기준 작성으로 확인할 수 있다.
  • 질문/행동: 학습자가 낯선 리팩터링 사례를 세 단계로 나누고 각 단계의 완료 증거를 말하게 할 수 있는가?

사업가 · 구조적 비유

  • 관련성: 큰 작업을 작은 단위로 나누면 실패 범위와 검토 비용을 제한할 수 있다는 구조가 있다.
  • 통찰: APOM에 가상 적용한다면 코드가 아닌 반복 운영 절차 하나를 진단, 계획, 작은 작업, 증거 검토로 나눠 시험할 수 있다. 다만 운영 업무에는 자동 테스트나 PR과 같은 판정 장치가 없을 수 있다.
  • 질문/행동: 어떤 운영 절차에 먼저 관찰 가능한 완료 기준을 만들 수 있는가?

마케터 · 구조적 비유

  • 관련성: 화자는 “회귀가 없다”는 주장에 테스트, 스크린샷, 화면 영상을 붙이는 방식을 강조했다.
  • 통찰: 상세페이지에서도 효익 주장과 그 주장을 실제로 뒷받침하는 증거를 한 쌍으로 설계해야 한다. 화면 영상은 보이는 동작만 증명한다는 한계도 밝혀야 한다.
  • 질문/행동: 현재 보여 줄 수 있는 증거보다 더 넓게 말하고 있는 문장이 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 계획용 모델과 실행용 모델을 구분하고, 저장소·환경·비용·검토 방식에 맞춰 에이전트를 선택한다는 주장이 제시됐다.
  • 통찰: 모델 이름만 고르기보다 계획 품질, 실행 속도, 장기 작업 비용, 테스트 가능성을 작업별로 측정해야 한다.
  • 질문/행동: 같은 작은 작업에서 계획의 명확성과 인수 조건 통과율을 모델별로 비교할 수 있는가?

작은 실험 하나

  • 행동 1개: 검증용 저장소의 작은 리팩터링 1건을 계획 문서와 티켓 1개로 제한해 에이전트에 맡기고, 결과 PR을 사람이 검토한다.
  • 측정 1개: 사전에 적은 인수 조건의 통과율.
  • 중단 기준 1개: 인수 조건 통과율이 100%가 아니면 작업 범위를 확대하지 않고 멈춘다.

1. Cursor를 사용하는 이유

화자는 소프트웨어 엔지니어에서 Cursor의 필드 엔지니어가 됐다고 자신을 소개했다. Cursor 사용 표면으로 다음을 제시했다.

  • Agents 창: 여러 저장소와 모델을 오가며 에이전트를 병렬로 실행한다.
  • IDE: VS Code 기반 디버거, 확장 기능, 터미널을 선호하는 사용자를 위한 방식이다.
  • CLI: tmux 흐름이나 Android Studio·Xcode처럼 네이티브 Cursor 환경이 없는 IDE에서 쓸 수 있다고 설명했다.
  • Cloud Agents: 원격 머신에서 실행되므로 노트북을 닫아도 장기 작업을 계속할 수 있다고 주장했다.
  • Slack·브라우저·모바일: Slack에서 문서와 구현의 불일치를 찾아 PR을 열거나, 브라우저와 iOS 앱에서 에이전트를 관리할 수 있다고 했다. Android는 “곧 제공”될 예정이라고 말했다.

2. 모델 유연성과 Cursor harness

화자는 Kimi, GLM, Composer, Grok 4.6 등 여러 모델을 작업에 따라 조합할 수 있다고 설명했다. 무거운 모델은 계획에, 빠르고 저렴한 모델은 코드 실행에 쓰는 방식이 예산에 유리하다고 주장했다. SQLite를 처음부터 다시 만드는 내부 사례와 외부 벤치마크를 언급했지만 해당 자료는 전사에 포함되지 않았다.

모델과 사용 화면 사이에는 도구 실행, 캐시 관리, 동적 문맥 관리, 문맥 조립을 담당하는 Cursor harness가 있다고 설명했다. 화자의 핵심 주장은 큰 저장소 이행에서는 모델 단독 성능뿐 아니라 이 실행 계층이 중요하다는 것이다.

3. 네 단계 리팩터링 흐름

  1. Canvas와 Plan Mode: 현재 코드와 테스트 공백을 진단하고 이행 전략을 작성한다.
  2. 플러그인: 계획을 Jira 같은 작업 관리 도구의 티켓으로 나눈다.
  3. Cloud Agents: 티켓별 구현을 원격 에이전트에 위임한다.
  4. Automations: 의존성이나 기능 플래그가 다시 낡지 않도록 정기 유지보수를 설정한다.

시연 저장소는 WordPress였다. 화자는 PHP와 React가 섞인 코드에서 일부 레거시 구성요소를 React로 옮기려 했다. Canvas에는 관리자 화면별 테스트 커버리지, 테스트가 없는 client.js, 이행 우선순위가 표시됐다고 설명했다.

Plan Mode에서는 한 화면을 먼저 다루고 재사용 가능한 단계별 패턴을 만들기로 했다. 계획의 기준 구성요소로 profile을 선택했다. Confluence에 있는 TDD 템플릿을 불러와 현재·목표 구조, 기능 및 비기능 요구사항, 데이터 흐름, API, 데이터 모델, 기능 플래그를 포함한 Markdown 문서를 만들었다고 설명했다. Plan Mode는 코드를 쓰지 않고 전략 문서만 만든다고 강조했다.

4. 티켓 분할과 Cloud Agent 실행

Atlassian MCP를 이용해 계획을 목표, 범위, 인수 조건, 테스트, 의존성, 메모가 있는 Jira 티켓으로 나눴다. 화자는 티켓마다 별도 PR을 만들고 스크린샷이나 영상으로 검증하라고 지시했다. 하나의 거대한 PR보다 구성요소나 서비스별 PR 묶음을 권했다.

Cloud Agent는 GitHub 저장소와 연결된 원격 Linux VM에서 작동한다고 설명했다. 처음 환경을 만들 때 10~20분이 걸릴 수 있지만 이후에는 저장된 build를 재사용한다고 말했다. 여러 저장소를 함께 선택하는 기능은 마이크로서비스나 공용 SDK 변경에 유용하다고 주장했다.

라이브 에이전트는 Docker 환경과 테스트를 준비했지만 발표 시간 안에 완료되지 않았다. 화자는 대신 이전 PHP→React 이행 실행을 열어 로그인, 댓글 보기, 사용자 보기 동작을 검사하는 영상을 보여 줬다. 이 이전 사례에서는 두 Jira 티켓에 대한 두 PR 사이를 전환하며 변경을 검토했다.

5. 검증과 Automations

Cloud Agent가 가진 원격 데스크톱과 마우스로 전체 화면 흐름을 실행하고 영상을 남길 수 있다고 설명했다. 코드 변경 화면에서는 diff, CI 검사, 커밋 이력을 보고 PR을 열 수 있다고 했다. 사용자는 실행 중 후속 지시를 추가하거나 모바일에서 중단할 수 있다.

Automation은 일정, PR 생성, 라벨 변경, Slack·Teams 메시지, 사용자 웹훅으로 시작되는 Cloud Agent라고 설명했다. 시연한 기능 플래그 정리안은 다음과 같다.

  • 매주 저장소를 검사한다.
  • 최근 30일 동안 사용되지 않은 기능 플래그를 찾는다.
  • Datadog과 Sentry에서 문제가 없었는지 대조한다.
  • 플래그 제거 PR과 회귀 테스트를 만든다.
  • 완료 후 Slack 메시지를 보낸다.

Statsig는 연결되지 않아 사용자 정의 MCP가 필요하다고 말했다. 이 흐름은 설정 예시였으며 실제 실행 결과는 제시되지 않았다. 테스트 커버리지, 취약점 검색, 장애 조사 템플릿도 소개했다. 장애 조사 자동화는 새벽 3시에 사람을 바로 깨우는 대신 초기 조사를 수행하는 용도로 사용한다고 주장했다.

6. 질의응답과 남은 불확실성

  • Cloud 환경의 API 키와 비밀값은 환경 설정에 넣고 IP 허용 목록과 라우팅 규칙을 지정할 수 있다고 설명했다.
  • 사설망 연결 방식으로 Cloudflare Tunnels, AWS PrivateLink, 일부 VPN과 Tailscale, 자체 호스팅 Cloud Agents를 언급했다.
  • Atlassian과 Figma 플러그인은 MCP뿐 아니라 Skills도 제공한다고 했다.
  • 직접 만든 /onboard Skill은 새 저장소의 기술 스택과 구조를 파악하는 데 쓴다고 설명했다.
  • Continual Learning 플러그인은 작업 방식과 코딩 스타일을 AGENTS.md에 기록한다고 주장했다.
  • Automations의 memories.md는 이전 실행의 피드백을 다음 실행에 반영한다고 설명했다.
  • 로컬 Cursor에서 @Chats로 과거 대화를 참조할 수 있다고 했지만, Cloud 실행에도 같은 기능이 적용되는지는 발표자가 확인하지 못했다.
  • 로컬 머신에만 있는 파일은 그대로 접근할 수 없으며, 저장소에 커밋하거나 PrivateLink 같은 연결 방식이 필요하다고 설명했다.
경계

모델 성능·가격·독점 제공, 보안, 사설 연결, 기억 관리에 관한 내용은 발표자의 설명이며 독립 자료로 검증되지 않았다. DeepSeek V4 Flash 또는 Pro의 미국 서버 제공 계획과 Cloud에서 과거 대화를 복구할 수 있는지도 발표자가 확답하지 않았다. META의 원작자 필드는 비어 있고 소속 후보만 Cursor로 기재돼 있다.

오늘 세션은 레거시 코드베이스를 리팩터링하는 방법에 관한 것입니다. 오늘 세션이 끝났을 때 여러분 모두가 두 가지 핵심 내용을 가져가셨으면 합니다.

잊기 전에 녹화가 제대로 되고 있는지 확인하겠습니다. 잠시만요. 아, 네, 되는 것 같네요.

첫 번째 질문은 AI로 레거시 코드베이스를 리팩터링하는 가장 좋은 방법은 무엇인가입니다. 두 번째 질문은 이를 위해 Cursor를 사용하는 이유가 무엇인가입니다.

오늘은 이 두 질문의 순서를 바꾸고 싶습니다. 첫 번째 질문은 슬라이드를 통해 답하면서 Cursor를 특별하게 만드는 요소를 조금 보여드리겠습니다. 두 번째 질문은 단순히 이야기하는 것보다 데모에 가깝습니다. 여러분과 함께 실제로 몇 가지 컴포넌트를 마이그레이션하면서 Cursor로 이를 수행하는 가장 좋은 방법을 보여드릴 것이기 때문입니다.

참고로 저는 이곳 Cursor에서 필드 엔지니어가 되기 전에는 소프트웨어 엔지니어였습니다. 많은 AI 도구를 사용해 봤고, 훌륭한 AI 도구도 많이 있습니다. 오늘은 Cursor를 차별화하는 요소와, 특히 Cursor 안에서 대규모 마이그레이션과 리팩터링, 그리고 모노레포(monorepo)나 여러 서비스에 걸친 작업을 수행하는 것을 제가 왜 좋아하는지 조금 이야기하고 싶습니다.

지난 6개월 정도 동안 Cursor를 사용하지 않았다면 이 화면이 새롭게 보일 수도 있습니다. 이것은 에이전트 창(Agents window)이며, Cursor를 활용한 개발의 미래라고 우리가 생각하는 모습입니다. 보시다시피 에이전트는 저장소 안에서 화면 한쪽에 배치됩니다. 가운데에는 실제로 Cursor와 대화하는 에이전트 또는 채팅 창이 있습니다. 모델을 선택하고 여러 저장소에 걸쳐 작업할 수 있습니다.

Cursor에서는 IDE(통합 개발 환경)를 사용할 수도 있습니다. Cursor는 여기서 시작했고, 지금도 많은 개발자가 이 환경을 계속 선택합니다. VS Code의 포크(fork)이므로 VS Code 디버거, 확장 기능, 그리고 하단에 터미널이 있는 환경을 좋아한다면 작업하기에 아주 좋은 곳입니다.

많은 분이 모를 수도 있지만 CLI도 있습니다. Cursor CLI는 tmux 워크플로를 그대로 유지하고 싶거나, 아직 네이티브 Cursor 솔루션이 없는 Android Studio나 Xcode 같은 IDE에서 작업하고 싶을 때 유용합니다. Cursor CLI는 저희 웹사이트에서 사용할 수 있습니다. 다운로드해서 사용하면 되고, 여러분이 사용해 본 다른 TUI AI 제품과 매우 비슷합니다.

마지막으로 오늘 대부분의 시간을 보낼 곳입니다. Cursor Cloud, 즉 Cursor Cloud Agents가 있습니다. 에이전트가 원격 머신에서 자율적으로 작동하기 때문에 Cursor를 사용하는 정말 좋은 방법입니다. 즉, 에이전트를 실행한 뒤 노트북을 닫아도 에이전트는 계속 실행됩니다.

에이전트와 많은 상호작용을 주고받아야 하는 장기 마이그레이션이나 리팩터링 프로젝트에 특히 유용합니다. Cursor Cloud를 사용하면 곧 해볼 것처럼 대규모 에이전트를 실행하고, 작업이 끝날 때까지 리팩터링을 수행하게 할 수 있습니다. 동영상, 스크린샷, 테스트를 통해 실제로 해야 할 일을 완료했는지도 입증할 수 있습니다.

오늘 일부를 보여드릴 Cursor Browser 외에도 Cursor Cloud Agents를 사용할 수 있는 곳은 여러 군데 있습니다. Cursor에서 매우 흔하게 사용하는 방식은 Slack입니다. 여기 보시면 채널 안에 Cursor 에이전트가 상주하면서 온라인 문서와 실제 구현이 서로 동기화되지 않았는지 확인할 수 있습니다.

정말 좋은 점은 에이전트가 PR을 열고, 누군가가 이를 검토하게 하며, 여러분이 Cursor 앱이나 브라우저를 직접 열지 않아도 Cursor가 무엇을 하고 있는지 자동으로 파악할 수 있게 해준다는 것입니다.

Cursor Cloud를 사용할 수 있는 마지막 장소는 모바일 앱입니다. App Store에서 사용할 수 있는 Cursor 모바일 앱이 있습니다. 현재는 iOS만 지원하고 Android는 곧 지원할 예정입니다. 모든 에이전트를 탐색하고, 에이전트를 로컬에서 클라우드로 넘긴 다음, 어디에 있든 앱에서 작업할 수 있습니다.

노트북에서 한발 물러나 노트북을 닫고, 휴대폰으로 에이전트와 완전히 원격으로 작업할 수 있는 좋은 방법입니다.

Cursor를 특별하게 만드는 또 다른 요소는 모델 유연성입니다. 많은 분이 알고 계시겠지만, Cursor는 현재 모든 주요 프런티어 연구소(frontier labs)의 모델을 제공하며, Kimi와 GLM을 비롯한 다양한 오픈 소스 모델도 제공합니다. 자체 개발한 인하우스 모델도 있는데, 그중 하나가 Composer이며, 가장 최신이자 가장 뛰어난 모델은 Grok 4.6입니다.

Grok 4.6은 제가 알기로 어제 출시되었고, 놀라운 모델입니다. 여기에서 외부 제3자가 공개한 다양한 벤치마크 세트에서 다른 여러 프런티어 연구소의 모델과 비교해 어떻게 벤치마킹되는지 볼 수 있습니다.

정말 강력한 모델이라는 것을 확인할 수 있지만, Grok을 더욱 강력하게 만드는 요소는 이렇게 강력한 모델임에도 저렴하고 효율적이라는 점이라고 생각합니다. 여기에서 Grok이 다른 프런티어 모델들과 비교해 어떤 위치에 있는지 볼 수 있습니다. 더 실행 중심적인 모델인 Composer와 GPT보다는 조금 비쌉니다. 하지만 그 강력함과 장시간 실행되는 작업을 수행하는 능력을 고려하면 다른 프런티어 연구소의 일부 모델에 비해 매우 저렴합니다.

오늘은 Grok 4.6을 사용해 보면서 제가 언제 이 모델을 선택하고 언제 선택하지 않는지 보여드리고 설명하겠습니다. 아직 사용해 보지 않았다면 꼭 한번 사용해 보시기를 권합니다.

원하는 만큼 MCP를 추가할 수 있습니다. Google Drive, Granola, PagerDuty 등 모든 서비스가 여기에 있습니다. 플러스 기호로 추가하기만 하면 Cursor가 즉시 해당 서비스들을 살펴보기 시작합니다.

여기서 “좋아요, 순차적으로 진행해야 하는 티켓을 세 개 찾았습니다. 1단계를 시작하기 전에 상위 티켓을 검사하겠습니다”라고 말하는 것을 볼 수 있습니다.

이제 Cursor가 작업하도록 두겠습니다. 이런 마이그레이션은 티켓 세트에서 시작합니다. 모든 내용을 하나의 거대한 PR에 넣지 않도록 해야 합니다. 그렇게 하면 리뷰가 불가능하기 때문입니다. 하지만 수행할 단계를 차례로 안내하는 데는 매우 유용합니다.

앞에서 본 것처럼 계획을 만들고, 편집하고, 티켓으로 변환했습니다. 이제 이 Cloud Agent가 티켓을 구현할 것입니다. 노트북을 닫고 하루 일과를 마칠 수 있습니다.

Cursor에서는 금요일마다 티켓 백로그를 처리할 때 Cursor에게 작업을 맡기고, 월요일에 돌아와 PR을 검토하기도 합니다. 분산된 팀에 아주 유용합니다. 유럽에 팀이 있고 아시아에 팀이 있다면, 두 팀은 Cloud Agent를 통해 말 그대로 비동기적으로 협업할 수 있습니다. 한 팀이 잠들면 다른 팀이 작업을 이어받을 수 있습니다.

항상 여러분을 위해 일하는 에이전트를 두는 좋은 방법입니다. 많은 워크플로를 빠르게 진행할 수 있어서 정말 마음에 듭니다. 나중에 이야기하겠지만, 이러한 에이전트는 자신의 작업을 검증하고 테스트할 수 있습니다.

이 작업에는 시간이 조금 걸릴 것입니다. 작업이 진행되는 동안 Cloud Agent 환경을 간단히 둘러보겠습니다.

이것이 메인 에이전트 실행 화면으로, 일반적인 Cursor에서 보는 것과 매우 비슷합니다. Cloud Agent의 좋은 점은 에이전트가 접근할 수 있는 데스크톱도 볼 수 있다는 것입니다.

Cursor Cloud Agent는 원격 Linux VM에서 실행됩니다. 따라서 컴퓨터와 마우스에 접근할 수 있습니다. 테스트가 필요한 풀스택 프런트엔드 애플리케이션이 있다면 Cursor가 실제로 그 테스트를 대신 수행할 수 있습니다.

여기에서 그 예를 볼 수 있습니다. 제가 작업하던 다른 저장소인 Grafana에서의 사례입니다. 이것은 Cursor가 촬영한 동영상으로, 제가 구현해 달라고 요청한 기능을 구현하는 모습입니다. 코드베이스에서 테마를 전환하는 기능입니다.

이것은 Cursor가 자체 마우스와 컴퓨터를 사용해 저를 대신하여 무언가를 실제로 테스트하는 모습입니다. 여기서 제가 아무것도 조작하지 않고 있습니다. Cursor가 전체 녹화를 수행한 뒤 저에게 다시 보내고 있습니다.

마이그레이션이나 리팩터링을 할 때는 항상 무언가를 망가뜨리고 있지 않은지 확인해야 합니다. 회귀(regression)가 발생하지 않았는지도 확인해야 하죠. 작업을 Cursor Cloud Agents에 맡기면 에이전트가 스스로 검증하고 이렇게 알려줄 수 있습니다. “스크린샷을 찍었는데, 괜찮아 보이나요?” 또는 “엔드투엔드(end-to-end) 테스트를 완료했는데, 예상하신 워크플로인가요?”

이렇게 하면 에이전트가 아무것도 망가뜨리지 않고 리팩터링을 수행할 수 있다는 확신과 신뢰를 더 가질 수 있습니다.

앞서 말씀드렸듯이, 에이전트는 자체 컴퓨터와 테스트 스위트(test suite)에 접근할 수 있기 때문에 이런 테스트를 진행하기에 아주 좋은 방법입니다. 하지만 변경 사항을 검토하기에도 아주 좋은 환경입니다.

Cursor가 코드를 변경하기 시작하면 여기에서 확인할 수 있습니다. 일반적인 버전 관리(version control) UI처럼 보일 겁니다. 무엇이 삭제되었고 무엇이 변경되었는지 확인할 수 있으며, 이 화면에서 진행 상황을 따라갈 수 있습니다.

마지막으로, 앞서 열어 둔 PR 하나를 보여드리겠습니다. 어떤 변경 사항이 적용되었는지 모두 확인하고 검토할 수 있습니다. CI도 확인해서 어떤 검사들이 통과했는지 볼 수 있습니다. 지금은 Cursor Bugbot 하나만 있습니다.

커밋 기록도 볼 수 있어서 Git 변경 사항을 빠르게 확인하기에 좋습니다. 준비가 되면 PR을 열고 다른 사람에게 검토를 요청할 수 있습니다.

저는 주로 브라우저 화면에서 작업합니다. 정말 좋은 작업 방식이라고 생각합니다. 하지만 이동이 많거나 자주 여행한다면, 그때는 휴대폰을 사용하는 것을 좋아합니다.

휴대폰을 잠깐 연결해서 보여드리겠습니다. Cursor 앱으로 가서 연결해 보죠.

Cursor 앱은 App Store에서 사용할 수 있고, 기본적으로 이렇게 생겼습니다. 여기 보시면 현재 작동 중인 에이전트가 하나 있습니다. 방금 출시한 Jira 티켓 에이전트입니다. 제가 출시한 모든 에이전트를 확인할 수 있습니다. 여기에는 어제 출시한 에이전트 몇 개가 있고, 개발 환경을 설정하는 데 사용한 에이전트도 하나 있습니다. 여러 작업 공간(workspace)도 모두 확인할 수 있습니다.

모바일의 가장 좋은 점은 여기서 에이전트를 실행할 수 있다는 것입니다. “이 특정 저장소에서 에이전트를 만들고 싶어요. 이 특정 브랜치에서 작업하게 하고 싶어요”라고 말할 수 있습니다. 그런 다음 에이전트를 실행하면 브라우저에 즉시 나타나는 것을 볼 수 있습니다.

예를 들어 “이 코드베이스에 대해 알려줘”라고 할 수 있습니다. 간단한 작업을 해보죠. Grafana를 대상으로 하고, 일단 Auto를 사용하겠습니다. 이것은 모델 간 선택을 담당하는 스마트 라우터(smart router)입니다. 이제 전송하겠습니다.

브라우저로 돌아가면 새로운 Cloud Agent가 실행된 것을 볼 수 있습니다. 데스크톱에서 앱으로, 다시 데스크톱으로 이어지는 흐름이 정말 매끄럽습니다. 에이전트를 항상 확인할 수 있고, 에이전트가 정확히 무엇을 하고 있는지도 알 수 있습니다.

좋습니다. 질문을 받기 전에 약 10분 정도 여유가 있습니다. 이 리팩터링 마이그레이션이 어떻게 진행되는지 다시 확인해 보겠습니다. 완료되지 않으면 이전 실행 결과를 보여드릴 수 있습니다.

작업이 진행되는 동안 Automations에 대해 조금 이야기하고 싶습니다. 앞에서 보여드린 네 가지 항목 중 마지막 항목입니다. Cursor의 Automations는 기본적으로 예약되었거나 트리거된 Cloud Agents입니다.

여기서 New Automation으로 가면 자동화를 실행할 수 있는 방법이 여러 가지 있다는 것을 볼 수 있습니다. 시간이나 이벤트를 기준으로 실행할 수 있고, PR이 열리거나 라벨이 변경되는 경우처럼 특정 이벤트를 기준으로 실행할 수도 있습니다. Slack이나 Teams에서 새 메시지가 전송되는 것을 기준으로 실행할 수도 있습니다. 직접 만든 커스텀 웹훅(custom webhook)을 사용할 수도 있습니다.

티켓을 “To Do”에서 “In Progress”로 옮길 때 자동화를 실행하도록 설정하는 경우를 많이 봤습니다. Jira 웹훅을 설정하기만 하면 되기 때문입니다.

Automations는 워크플로를 빠르게 처리하는 데도 좋지만, 유지 관리와 안정성에도 유용합니다. 여러분과 함께 자동화를 하나 만들어 보겠습니다. 저는 이것을 feature flag cleaner라고 부르는데, 엔지니어였을 때 이런 자동화가 있었다면 좋았겠다고 생각했기 때문입니다.

기본적으로 이렇게 말할 수 있습니다. “매주 실행한다고 해보죠.” 조금 과할 수도 있지만 괜찮습니다. 나중에 조정하면 되니까요. “매주 이 저장소를 살펴보고, 지난 30일 동안 사용되지 않은 오래된 feature flag가 있는지 확인해 주세요.”

여기에 MCP를 태그해서 교차 확인할 수도 있습니다. 예를 들어 Statsig을 사용할 수 있습니다. 여기서 연결할 수 있는지 확인해 보겠습니다. Statsig은 연결되어 있지 않으니 괜찮습니다. 커스텀 MCP를 추가할 수 있습니다. 그동안은 Datadog을 사용해 보겠습니다. Datadog과 Sentry를 통해 각 flag에 문제가 발생한 적이 없는지도 교차 확인할 수 있습니다.

이렇게 말할 수도 있습니다. “flag를 제거하는 PR을 올리고, flag를 제거해도 회귀가 발생하지 않았음을 확인하는 테스트를 추가해 주세요.” 그리고 “완료되면 검토할 수 있도록 PR 링크를 Slack 메시지로 보내 주세요”라고 할 수도 있습니다.

저는 자동화를 만드는 것을 정말 좋아합니다. 하루 중 어떤 부분을 에이전트가 대신 처리하거나 지원할 수 있는지 알아보는 창의적인 방법이라고 생각합니다. 여기에는 pull request를 여는 도구가 있는 것을 볼 수 있습니다. Slack으로 메시지를 보내는 도구도 하나 더 추가하겠습니다. Slack 인스턴스를 연결해야 하지만, 이 예시에서는 PR과 함께 제게 다이렉트 메시지를 보낼 수 있다는 것을 보여줍니다.

앞서 말씀드렸듯이 저장소 하나를 연결할 수도 있고, 여러 저장소를 연결해서 여러 저장소에 걸쳐 작업할 수도 있습니다. 코드베이스를 유지 관리하기에 아주 좋은 방법입니다.

feature flag 정리나 의존성 업데이트에도 사용할 수 있습니다. 이는 사후 대응이 아니라 사전 대응 방식입니다. 레거시 코드베이스를 리팩터링할 때 우리는 종종 이렇게 묻습니다. “어쩌다 이런 상태가 됐을까? 왜 이런 일이 생겼을까?” 많은 경우 단순히 충분히 사전 대응하지 않았기 때문입니다. 의존성이 업데이트되지 않았고, 미리 작업을 처리하지 못했던 것이죠.

Cloud Agent Automations가 필요한 이유가 바로 여기에 있습니다. 미리 작업을 처리해서 나중에 리팩터링해야 하는 상황을 피할 수 있습니다. 이것은 제가 엔지니어링을 할 때 늘 가지고 있던 생각입니다. 문제가 커지기 전에 싹을 잘라내자는 것이죠. Automations는 이를 실현하는 좋은 방법입니다.

자동화를 처음부터 만들고 싶지 않다면 전혀 문제없습니다. 여기에는 좋은 템플릿이 있습니다. 테스트 커버리지를 추가하는 템플릿도 있고, 코드베이스에서 취약점을 검사하는 템플릿도 있습니다. 인시던트 분류(incident triage)를 위한 좋은 템플릿도 있습니다. Datadog 알림 채널을 사용하거나 PagerDuty 또는 Incident.io를 사용한다면 여기 있는 템플릿 중 하나로 시작할 수 있습니다.

이것을 사용해 보겠습니다. 또 다른 시간 기반 트리거라는 것을 볼 수 있지만, 에이전트는 인시던트 조사 자동화입니다. 저희는 온콜(on-call) 프로세스에 비슷한 방식을 사용합니다. 새벽 3시에 누군가를 깨우는 대신, 초기 조사를 수행한 다음 온콜 담당자에게 발견한 내용을 간단히 요약해서 보냅니다.

앞서 말씀드렸듯이 Slack으로 메시지를 보내고 Datadog을 사용할 수 있습니다. 사용하는 도구에 따라 Notion이나 Confluence에 게시하도록 사용자 지정할 수도 있습니다.

Cursor의 Automations는 정말 강력합니다. 오늘 시간이 있다면 하나 만들어 보시기를 강력히 권합니다. 정말 재미있기 때문입니다. 코딩을 더 즐겁게 만들어 준다고 생각하고, 자동화를 서로 연결하거나 커스텀 웹훅을 설정하는 방식에 따라 매우 강력하게 사용할 수도 있습니다. Cursor Cloud Agents를 활용하는 좋은 방법입니다.

남은 5분 동안 처음에 실행했던 Cloud Agent로 돌아가 보겠습니다. Docker 환경을 설정하고 실행하는 모든 테스트가 제대로 작동하는지 확인하고 있는 것을 볼 수 있습니다. 제가 원하던 바로 그 작업입니다.

누군가 말씀하셨듯이 Cloud Agents는 자율적으로 작동하도록 설계되었지만, 사용자 입력도 반영하도록 설계되었습니다. 후속 지시를 추가하거나 Cloud Agent의 작업에 개입하고 싶을 때, 또는 에이전트가 하는 일에 동의하지 않을 때는 언제든 여기에 입력할 수 있습니다. 모바일 앱에서도 에이전트를 중단할 수 있습니다.

목표는 Cloud Agent가 대부분의 작업을 수행하되, 원할 때 사용자가 계속 상황을 파악하는 것입니다. 중단하고 싶다면 여기에 후속 지시를 추가하면 에이전트가 이를 반영합니다.
