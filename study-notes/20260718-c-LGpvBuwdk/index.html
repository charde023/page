Matt Pocock의 스킬(skills)은 아이디어를 먼저 정리하고, 필요하면 스펙(spec)과 티켓(ticket)으로 쪼갠 뒤, 구현(implement)과 독립 코드리뷰(code review)까지 자동화하는 AI 개발 흐름이다.

1. 스킬 저장소를 왜 설치하는가

Matt Pocock은 자신의 mattpocock/skills 저장소가 큰 규모로 쓰이고 있지만, 정작 “처음부터 끝까지 어떻게 써야 하는지”를 설명한 튜토리얼이 없었다고 말한다.

이 영상의 목적은 고급 기능이 아니라 실무에서 가장 자주 쓰는 메인 플로우(main flow)를 보여주는 것이다. 예시는 그의 작업 저장소인 AI Hero CLI에서 진행된다.

핵심은 다음과 같다.

  • 새 프로젝트(greenfield)든 기존 코드베이스(brownfield)든 같은 방식으로 쓸 수 있다.
  • 빈 디렉터리에서 시작하면 새 프로젝트용으로 동작한다.
  • 기존 저장소에서 실행하면 현재 코드베이스를 기준으로 설정된다.

2. npx로 스킬 설치하기

설치는 Node.js의 npx를 사용한다.

npx skills@latest mattpocock/skills

이 명령은 Vercel의 skills.sh 계열 설치 도구를 통해 GitHub 저장소의 스킬들을 내려받고, 몇 가지 설정 질문을 진행한다.

설치 화면에서는 38개의 스킬이 보이며 크게 두 그룹이 있다.

  • Matt Pocock 공식 스킬
  • 실험 중인 기타 스킬

Matt은 공식 스킬 전체를 선택하는 것을 권장한다. 다만 Vercel CLI의 선택 UI가 아주 만족스럽지는 않다고 말하며, 추후 직접 만든 설치 도구로 바꿀 수도 있다고 덧붙인다.

3. 에이전트와 설치 범위 설정

설치 도구는 여러 AI 에이전트(agent)를 지원한다. Matt은 Claude Code를 사용하지만, Cursor, Codex 등 다양한 도구에서도 사용할 수 있다.

설치 범위는 두 가지다.

범위 적합한 경우 설명
프로젝트(project) 팀 작업 모든 팀원이 같은 스킬 세트를 사용
전역(global) 개인 작업 개인 환경 전체에서 스킬 사용

Matt은 팀이라면 프로젝트 단위 설치가 낫다고 말한다. 그래야 스킬 변경도 팀이 함께 결정할 수 있기 때문이다.

파일 배치는 복사보다 심볼릭 링크(symlink)를 권장한다. .agents와 .claude 폴더에 중복 복사하는 것보다 관리가 쉽기 때문이다.

4. 설치 후 컨텍스트 부담이 작은 이유

Matt의 스킬은 대부분 사용자 호출형(user-invoked)이다.

즉, 설치했다고 해서 모든 스킬 설명이 매번 에이전트 컨텍스트에 길게 들어가지 않는다. 필요할 때 명령으로 호출한다.

그 결과 많은 스킬을 설치해도 약 660토큰 정도만 차지한다고 설명한다. AI 코딩에서 컨텍스트 창(context window)은 매우 소중하므로, 이 설계가 중요하다.

5. 저장소 설정: setup mattpocock/skills

설치 후에는 저장소 안에서 설정을 해야 한다.

setup mattpocock/skills

이 설정은 세 가지를 준비한다.

  1. 이슈 트래커(issue tracker)
  2. 분류 라벨(triage labels)
  3. 도메인 문서(domain docs)

스펙과 티켓을 저장해야 하므로 이슈 트래커가 필요하다. GitHub, Jira, Linear, Beads, 로컬 Markdown 등 무엇이든 가능하다. Matt은 “이미 지원한다. 그냥 설정할 때 원하는 도구를 말하면 된다”고 강조한다.

영상 예시에서는 로컬 Markdown을 선택한다.

도메인 문서는 context.md와 ADR 같은 문서로 구성된다. 대부분은 단일 컨텍스트(single context)면 충분하고, 다중 컨텍스트(multi-context)는 큰 모노레포처럼 여러 업무 경계가 있는 경우에 적합하다.

6. Ask Matt으로 시작하기

설정 후 막막하다면 Ask Matt 스킬을 사용할 수 있다.

이 스킬은 Matt의 스킬 저장소 사용법을 설명해주는 안내자 역할을 한다. 예를 들어 “코드를 바꾸고 싶은데 어떤 흐름으로 시작해야 하느냐”고 물으면, 다음과 같은 메인 흐름을 제안한다.

  1. Grill with Docs로 아이디어를 정리한다.
  2. 필요하면 Prototype으로 실행 가능한 답을 확인한다.
  3. 작업이 작으면 바로 Implement로 간다.
  4. 작업이 크면 Spec과 Tickets로 나눈다.
  5. 구현 후 Code Review로 마무리한다.

Matt은 AI를 잘 쓰려면 컨텍스트 창과 토큰 사용량을 의식해야 한다고 강조한다.

7. Grill with Docs: 막연한 아이디어를 계획으로 바꾸기

Grill with Docs는 사용자를 인터뷰하면서 요구사항을 선명하게 만드는 스킬이다.

영상의 예시는 다음과 같은 매우 막연한 요청에서 시작한다.

“이 CLI의 내부 도구 대부분을 제거하고, 공개용 기능만 남기고 싶다.”

이 정도로 대충 말해도 된다. 스킬이 코드베이스를 탐색하고 후속 질문을 던진다.

예시에서는 내부 네임스페이스(namespace)에 11개 하위 명령(subcommand)이 있다는 식으로 저장소 구조를 파악한 뒤 질문을 이어간다.

최종적으로 다음과 같은 계획이 나온다.

  • 명령 파일 10개 삭제
  • 테스트 3개 삭제
  • 공유 모듈 재연결

이 단계의 목적은 코딩을 바로 시작하는 것이 아니라, 사용자와 에이전트가 공유된 이해(shared understanding)에 도달하는 것이다.

8. 바로 구현할지, 스펙으로 나눌지 결정하기

Grill with Docs가 끝나면 갈림길이 생긴다.

작업이 작고 현재 컨텍스트 창 안에서 끝낼 수 있으면 바로 실행한다.

/implement this

하지만 작업이 크거나 여러 세션이 필요하면 스펙으로 압축한다.

to spec

Matt은 자신의 기준으로 약 14만 토큰 이후부터 모델이 멍청해지고 환각(hallucination)이 늘어난다고 말한다. 이 구간을 넘기기 전의 안전한 영역을 스마트 존(smart zone)처럼 생각한다.

따라서 큰 작업은 한 번에 밀어붙이지 않고, 스펙과 티켓으로 쪼개야 한다.

9. Spec과 Tickets의 역할

to spec은 지금까지의 대화와 조사 내용을 하나의 스펙 문서로 압축한다.

스펙은 “우리가 최종적으로 어디에 도착해야 하는가”를 설명한다.

스펙에는 보통 다음이 들어간다.

  • 문제 설명(problem statement)
  • 해결책(solution)
  • 사용자 스토리(user stories)
  • 구현 결정(implementation decisions)
  • 테스트 결정(testing decisions)

그다음 to tickets를 실행하면 스펙을 구현 가능한 티켓으로 나눈다.

티켓은 “어떻게 그 목적지까지 갈 것인가”를 나타낸다. 각 티켓은 보통 한 번의 컨텍스트 창, 즉 한 번의 스마트 존 안에서 끝낼 수 있는 크기여야 한다.

Matt은 실제 예시로 하나의 스펙 아래 11개 하위 이슈가 달린 사례를 보여준다. 각 하위 이슈는 한 세션에서 처리할 수 있는 조각이다.

10. Implement와 코드리뷰

스펙과 티켓이 준비되면 컨텍스트를 비우고, 특정 티켓을 대상으로 구현을 시작한다.

권장 방식은 모든 티켓을 한 번에 처리하라고 하지 않는 것이다.

  • 티켓 하나 구현
  • 스마트 존 여유 확인
  • 필요하면 다음 티켓 진행
  • 보통은 티켓 사이에 컨텍스트를 비움

implement 스킬은 구현뿐 아니라 검증도 수행한다.

  • 타입 체크(type check)
  • 빌드(build)
  • 기능 확인
  • 코드리뷰 스킬 호출

코드리뷰는 두 축으로 진행된다.

  1. 원래 스펙과 구현 결과가 맞는지 확인
  2. 저장소의 코드 기준 또는 일반적인 코드 품질 기준으로 확인

저장소에 별도 코딩 표준이 없으면 Martin Fowler식 코드 냄새(code smell) 같은 일반적인 기준을 사용한다.

Matt은 코드리뷰를 서브 에이전트(sub-agent)로 돌리는 것이 중요하다고 말한다. 같은 에이전트가 방금 작성한 코드를 스스로 리뷰하면 관대해지기 쉽기 때문이다. 별도 에이전트는 깨끗한 컨텍스트에서 더 객관적으로 검토한다.

Matt Pocock은 자신의 스킬 저장소(skills repo)가 촬영 시점 기준 별 16.2만 개, 다운로드 750만 회를 기록했지만 제대로 된 튜토리얼을 만든 적이 없었다고 말한다. 그래서 이번 영상에서는 고급 기능이 아니라 처음 시작할 때 필요한 기본 흐름을 설명한다.

예시는 AI Hero CLI라는 실제 작업 저장소에서 진행한다. 새 프로젝트라면 빈 디렉터리에서 같은 절차를 실행하면 되고, 기존 코드베이스에서도 동일하게 사용할 수 있다.

설치는 npx skills@latest mattpocock/skills로 한다. 이 명령은 Node.js의 npx를 사용하며, Vercel의 설치 도구를 통해 mattpocock/skills 저장소의 스킬들을 가져온다. 설치 화면에는 38개의 스킬이 나오며, 공식 Matt Pocock 스킬과 실험용 스킬로 나뉜다. Matt은 공식 스킬을 모두 선택하라고 권한다.

다음으로 사용할 에이전트(agent)를 선택한다. Matt은 Claude Code를 사용하지만 Cursor, Codex 등 여러 도구에서도 사용할 수 있다. 설치 범위는 프로젝트(project)와 전역(global) 중 고른다. 팀이라면 프로젝트 단위가 좋고, 개인이라면 전역도 괜찮다. 파일 연결 방식은 심볼릭 링크(symlink)를 추천한다.

설치 후 Claude Code에서 슬래시(/)를 누르면 Grill me, Grill with Docs, Wayfinder 같은 스킬이 보인다. Matt의 스킬은 대부분 사용자 호출형(user-invoked)이어서, 설치해도 컨텍스트(context)를 많이 차지하지 않는다. 전체 스킬을 설치해도 약 660토큰 정도만 사용한다고 설명한다.

그다음 저장소 설정을 위해 setup mattpocock/skills를 실행한다. 이 설정은 이슈 트래커(issue tracker), 분류 라벨(triage labels), 도메인 문서(domain docs)를 만든다. 스펙(spec)과 티켓(ticket)을 저장할 장소가 필요하기 때문이다. GitHub, Jira, Linear, Beads, 로컬 Markdown 등 원하는 방식으로 설정할 수 있으며, 영상에서는 로컬 Markdown을 선택한다.

도메인 문서는 context.md와 ADR(Architecture Decision Record)을 포함한다. 대부분의 프로젝트는 단일 컨텍스트(single context)면 충분하고, 다중 컨텍스트(multi-context)는 큰 모노레포(monorepo)에 적합하다.

시작이 막막하면 Ask Matt 스킬을 사용할 수 있다. 이 스킬은 Matt의 스킬 저장소 사용법을 안내해준다. Ask Matt은 기본 흐름으로 Grill with Docs를 먼저 사용하고, 필요하면 Prototype을 거치며, 작업이 작으면 Implement로 바로 가고, 크면 Spec과 Tickets로 나누라고 설명한다.

Matt은 AI를 잘 쓰려면 컨텍스트 창(context window)과 토큰 사용량을 의식해야 한다고 강조한다. Grill with Docs는 사용자를 인터뷰해 막연한 아이디어를 구체적인 계획으로 바꾼다. 예시에서는 “CLI의 내부 도구를 대부분 제거하고 공개용 기능만 남기고 싶다”는 모호한 요청으로 시작한다.

Grill with Docs는 저장소를 탐색하고 후속 질문을 던진다. 예시에서는 내부 네임스페이스(namespace)에 11개 하위 명령(subcommand)이 있다는 점을 파악하고 질문을 이어간다. 최종적으로 명령 파일 10개 삭제, 테스트 3개 삭제, 공유 모듈 재연결이라는 계획이 나온다.

이 작업이 한 세션에서 끝날 것 같으면 /implement this로 바로 구현하면 된다. 하지만 여러 세션이 필요할 정도로 크다면 to spec을 실행한다. Matt은 약 14만 토큰 이후부터 모델이 덜 똑똑해지고 주의력 저하(attention degradation)와 환각(hallucination)이 생긴다고 느낀다. 그래서 그 이전 구간을 스마트 존(smart zone)처럼 다룬다.

to spec은 지금까지의 대화를 스펙 문서로 압축한다. 스펙은 최종 목적지를 설명한다. 문제 설명, 해결책, 사용자 스토리, 구현 결정, 테스트 결정 등이 들어간다. 이후 to tickets를 실행하면 스펙을 구현 가능한 티켓들로 나눈다. 각 티켓은 한 번의 컨텍스트 창에서 처리할 수 있는 크기여야 한다.

실제 작업에서는 큰 스펙 하나 아래에 11개의 하위 이슈가 붙을 수도 있다. 각 이슈는 한 세션에서 끝내는 작업 조각이다. 구현할 때는 모든 티켓을 한꺼번에 처리하라고 하지 않고, 하나씩 구현한 뒤 스마트 존 여유를 확인한다. 보통은 티켓 사이에 컨텍스트를 비운다.

implement 스킬은 구현뿐 아니라 타입 체크(type check), 빌드(build), 추가 검증, 코드리뷰(code review)까지 수행한다. 코드리뷰는 두 가지를 본다. 첫째, 구현 결과가 원래 스펙과 맞는지 확인한다. 둘째, 저장소의 코드 기준 또는 일반적인 코드 품질 기준에 맞는지 확인한다.

코드리뷰를 서브 에이전트(sub-agent)로 실행하는 것이 중요하다. 같은 에이전트가 방금 작성한 코드를 스스로 리뷰하면 자기 작업에 관대해질 수 있다. 반면 별도 에이전트는 깨끗한 컨텍스트에서 더 객관적으로 검토한다.

최종 흐름은 이렇다. 먼저 시작 전에 생각을 맞춘다. 필요하면 스펙과 티켓을 만들어 여러 세션에 대응한다. 이후 구현하고, 구현 스킬 안에서 코드리뷰까지 진행한다. Matt은 이 흐름이 자신의 대부분의 작업을 통과하는 메인 플로우라고 설명한다.
