스스로 학습하는 에이전트를 위한 메모리와 드리밍

원작자 Mahesh · Anthropic (Platform PM) · 업로드 2026-05-28 · 24.5분 · 원본 영상 ↗
한 줄 요약

Anthropic의 Memory + Dreaming API는 에이전트가 파일시스템 기반으로 실시간 기억을 쌓고, 배치 프로세스(Dreaming)로 여러 세션의 실수와 패턴을 자동 통합해 다음 세대 에이전트를 더 똑똑하게 만든다.

원작자 Mahesh (Anthropic, Platform PM) · 추정 출처 Anthropic 공식 발표 세션 · 업로드 2026-05-28 · 24.5분 · 전사 Whisper large-v3 (auto)

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
파일시스템 기반 메모리 에이전트가 bash/grep만으로 메모리를 읽고 쓴다 Claude에게 메모리를 파일 트리로 노출, 익숙한 도구 재사용
낙관적 동시성 (Optimistic Concurrency) 수천 개 에이전트가 같은 메모리 쓸 때 덮어쓰기 방지 content hash로 변경 전 충돌 사전 검사
Dreaming (배치 자가학습) 단일 세션 에이전트가 못 보는 교차 패턴을 찾는다 여러 세션 트랜스크립트를 오프라인에서 분석, 메모리 자동 갱신
Read-only vs Read-Write 메모리 스토어 조직 지식베이스는 불변, 작업 메모리만 갱신 권한 단위로 메모리 스토어를 분리 설계
버전 히스토리 + 귀속 메타데이터 어느 에이전트가 언제 왜 썼는지 감사 추적 기업 환경에서 predictable control 핵심 요건
메모리 스케일링 법칙 대규모 에이전트 팜은 메모리가 거대 지식베이스로 성장 Dreaming이 compute를 써서 index를 신선하게 유지
에이전트 목표 분리 작업 완수 목표 ≠ 메모리 품질 목표 Dreaming이 메모리 큐레이션을 별도 목표로 처리

내가 모를 만한 것 / 처음 보는 것

  • Managed Agents API — Anthropic의 클라우드 관리형 에이전트 실행 환경. 메모리·세션·트랜스크립트를 내장 관리.
  • Dreaming (Research Preview) — Managed Agents API에 새로 출시된 배치 자가학습 프로세스. 에이전트가 작업 중일 때가 아닌 오프밴드(out-of-band)로 실행.
  • 낙관적 동시성 (Optimistic Concurrency) — DB 트랜잭션 패턴. 쓰기 전 content hash로 다른 쓰기가 있었는지 확인, 충돌 시 재시도.
  • Content hash (precondition hash) — 메모리 파일의 현재 해시. 에이전트가 업데이트 전 "이 해시가 맞으면 쓰기 허용" 조건으로 사용.
  • Claude.md — Claude Code와 함께 출시된 초기 메모리 형태. 에이전트(또는 사용자)가 노트를 남기는 단일 파일.
  • Skills (Anthropic primitive) — 에이전트가 새 능력을 장착하는 프리미티브. 절차적 메모리(procedural memory)의 일종.
  • SRE 에이전트 데모 — 사이트 신뢰성 엔지니어링(Site Reliability Engineering) 시나리오. P1 알람 → 에이전트가 조사 → 메모리에 학습 기록.
  • Harvey — 법률 AI 스타트업. Dreaming 적용 후 법률 시나리오 작업 완수율 6배 향상.
  • Rakuten — Dreaming 적용 후 내부 지식 에이전트의 첫 시도 실수를 90% 감소.
  • Test-time compute / Thinking model — 모델에 추가 토큰(추론 시간)을 부여해 최종 결과를 높이는 스케일링 법칙. Dreaming이 같은 원리로 메모리 품질을 높임.

화자의 디테일 (놓치기 쉬운 포인트)

  1. Mahesh는 Anthropic Platform 팀 PM으로, MCP·Skills·Memory 3개 프리미티브를 직접 담당했다고 밝힘.
  2. Claude.md는 약 1.5년 전 Claude Code와 함께 출시된 초기 메모리. 단일 파일, 에이전트+사용자 혼용 방식의 한계가 있었음.
  3. 메모리를 "파일시스템"으로 모델링한 이유: Claude가 이미 agentic coding에서 bash·grep을 잘 쓰기 때문에 같은 도구를 재사용하게 한 것.
  4. Claude Opus 4.7 (당시 최신)이 파일시스템 기반 메모리에서 state-of-the-art: 무엇을 기억할지 판단, 파일 구조 설계, 파일 수 분할 결정 등.
  5. Anthropic 내부에서도 수백~수천 개 에이전트가 동시에 같은 메모리 스토어를 공유하며 운영 중.
  6. Dreaming을 시작하는 방법 두 가지: (a) 콘솔에서 cron 방식으로 주기적 실행, (b) 에이전트 작업 완료 후 API로 트리거 (스핀다운 시점).
  7. Dreaming은 트랜스크립트를 보고 중복 엔트리 5개 → 1개로 통합, 더 이상 유효하지 않은 stale 엔트리 제거, 패턴 발견 시 새 학습 노트 추가의 3단계 작업을 수행.
  8. SRE 데모에서 60초 주기로 동일 알람이 반복되는 패턴 — 개별 에이전트는 몰랐지만 Dreaming이 이를 발견해 retry 로직 비효율 원인으로 지목.
  9. 메모리 스토어는 최소 2계층: org-wide read-only (런북·SLO 가이드라인·담당자 목록) + 팀/작업별 read-write (실시간 학습).
  10. 포터블 API — 메모리가 Managed Agents에만 묶이지 않도록 독립 API 제공. 외부 PII 스캔·클린업 파이프라인·외부 시스템 복제에 활용 가능.
  11. Harvey의 법률 벤치마크에서 Dreaming 적용 후 작업 완수율 6배 상승.
  12. Rakuten은 Dreaming으로 첫 시도 실수 90% 감소, 토큰 효율·비용·레이턴시 동시 개선.

1. 프리미티브 진화 흐름

Anthropic은 지난 2년간 에이전트 능력을 확장하는 프리미티브를 단계적으로 출시해왔다.

  • MCP — 외부 도구·데이터 접근
  • Claude Code, Agent harness — 강력한 실행 하네스
  • Skills (2024년 10월) — 다른 에이전트나 사용자가 설계한 새 능력을 에이전트가 장착

그런데도 아직 해결 안 된 것이 있다. 장기 작업에서의 연속 자가학습과 문맥 관리. 여기서 메모리가 등장한다.

2. 왜 메모리가 중요한가

메모리를 통해 에이전트가 학습할 수 있는 대상은 세 가지다.

  1. 작업 자체 — 성공 기준, 흔한 실수, 효과적인 전략
  2. 환경 — 코드베이스, 파일, 지속적으로 변하는 자산
  3. 다른 에이전트 — 같은 환경의 에이전트끼리 학습을 공유, 시스템 전반의 문제를 파악해 자신의 메모리에 통합

특히 멀티 에이전트 시스템에서 에이전트 무리가 시간이 지날수록 자체적인 세계 이해를 구축하는 것이 화자가 가장 주목하는 방향이다.

3. 메모리 설계 요건 3가지

3-1. 지능 극대화 (기본값)

과거 접근법: - claude.md — 단일 파일, 사용자·에이전트 혼용, 제약이 많았음 - Memory tool (SDK) — 파라미터·출력 형식이 사전 규정된 도구 호출

새 접근법: 메모리를 파일시스템으로 모델링. Claude가 bash·grep 같은 익숙한 도구로 직접 관리. Claude Opus 4.7이 이 방식에서 state-of-the-art 성능을 보임.

3-2. 멀티 에이전트 확장성

  • 에이전트가 여러 메모리 스토어를 mix-and-match (read-only + read-write 혼합 접근)
  • 낙관적 동시성: content hash로 덮어쓰기 충돌을 사전 감지. 수천 에이전트가 동시 접근 가능.

3-3. 기업 제어

  • 버전 히스토리: 모든 업데이트의 감사 로그. 어느 에이전트가, 어느 세션에서, 언제 변경했는지 기록.
  • 귀속 메타데이터: 에이전트별 변경 추적.
  • 포터블 독립 API: Managed Agents 외부에서도 사용 가능. PII 스캔, 클린업, 외부 시스템 복제 등 자체 파이프라인 지원.

4. Dreaming — 배치 자가학습 프로세스

기본 동작

  • 오프밴드(out-of-band): 에이전트가 작업 중인 세션과 별개로 실행
  • 최근 에이전트 세션 트랜스크립트를 스캔 → 공통 실수·성공 패턴 발견 → 메모리 자동 업데이트
  • 결과물: diff (변경 파일 셋). 즉시 적용하거나 API로 수동 검토 후 적용 선택 가능.

트리거 방법

방법 설명
콘솔 cron 주기적(예: 매일) 자동 실행
API 트리거 에이전트 작업 완료 후 스핀다운 시점에 직접 호출

설계 이점

  1. 멀티 에이전트 관점 — 단일 에이전트는 자기 컨텍스트만 보지만, Dreaming은 여러 에이전트를 동시에 조망해 공통 패턴을 발견.
  2. 목표 분리 — 작업 완수 목표와 메모리 품질 목표를 분리. 에이전트가 명확한 단일 목표에 집중.
  3. 레이턴시 제로 — 오프밴드이므로 에이전트의 hot path에 추가 지연 없음.
  4. 스케일링 법칙 — test-time compute처럼 추가 compute를 써서 메모리 품질을 높임. 검색 시스템의 "사전 인덱스 구축"과 유사: 비용을 사전에 상각, 다운스트림 에이전트 전체가 효율적으로 사용.

5. SRE 에이전트 데모 요약

시나리오: P1 알람 발생 → SRE 에이전트 자동 스핀업 → 조사 → 학습 기록

메모리 구성:

스토어 권한 내용
조직 지식 베이스 Read-only 런북, SLO 가이드라인, 담당자 목록
SRE 메모리 스토어 Read-write 실시간 조사 결과, 학습 노트

흐름: 1. 1번 SRE 에이전트: CPU 사용률·트래픽 패턴·최근 PR 조사 → 결과를 메모리에 기록 2. 같은 알람 재발 → 2번 SRE 에이전트: 메모리에서 1번 조사 결과 바로 확인 → 중복 조사 생략 → 토큰 절약 + 속도 향상

Dreaming 적용 후: - 60초 주기 알람 패턴 발견 (개별 에이전트는 몰랐던 사실) - 비효율적 retry 로직을 원인으로 지목 - 중복 엔트리 5개 → 1개로 통합 - stale 엔트리 제거 - 검증 노트 추가 ("이 메모리는 최신 트랜스크립트에서 확인됨")

6. 프런티어 메모리 시스템의 전체 그림

[실시간 메모리] ←→ [에이전트 세션들]
      ↓ (오프밴드 분석)
  [Dreaming]
      ↓
[갱신된 메모리 / 대규모 지식베이스]
      ↓ (다음 날 에이전트들이 개선된 상태로 시작)
  • 메모리(왼쪽): 에이전트가 작업 중 실시간 읽기·쓰기
  • Dreaming: 메모리 검증·정리·보강 담당. 중간 규모 메모리와 대규모 지식베이스 사이의 브릿지.

지난 몇 년간 모델 성능이 빠르게 향상되어 에이전트가 수 시간, 때로는 거의 하루에 가까운 시간 동안 작업을 수행할 수 있게 되었습니다. 우리는 모델이 더 강력해질수록 외부 도구와 환경에 접근하고 시간이 지날수록 더 능력 있어질 수 있도록 더 높은 수준의 프리미티브에 투자해왔습니다. MCP는 외부 도구·데이터 접근을, Claude Code·Agent 같은 하네스는 강력한 실행 환경을, 지난 10월에 출시한 Skills는 다른 에이전트나 사용자가 설계한 새 능력을 에이전트가 장착할 수 있게 해줬습니다.

각 프리미티브는 에이전트가 더 긴 기간 동안 더 강력한 것을 할 수 있게 해줬지만, 아직 해결되지 않은 게 있습니다. 바로 장기 작업에서의 연속 자가학습과 문맥 관리입니다. 그래서 메모리입니다.

메모리가 다음 프리미티브입니다. 에이전트가 자신이 작업하는 내용과 경험을 바탕으로 스스로 진화하고 개선하는 자가학습 에이전트로 나아가게 해줄 것이라고 생각합니다. 메모리로 에이전트는 세 가지를 학습할 수 있습니다. 첫째, 자신이 수행하는 작업 — 성공 기준, 흔한 실수, 효과적이거나 그렇지 않은 전략. 둘째, 환경 — 코드베이스, 파일, 지속적으로 최신화해야 하는 자산. 셋째, 같은 환경의 다른 에이전트 — 학습을 공유하고, 시스템 어딘가에서 무슨 일이 잘못되고 있는지 파악해 자신의 메모리에 통합합니다.

세 번째 포인트가 제가 올해 가장 흥미롭게 보고 있는 부분입니다. 자가 관리형 메모리는 비슷한 환경에서 개별 작업을 수행하는 에이전트 무리가 시간이 지날수록 자신이 처한 세계에 대한 이해를 스스로 쌓아나가는 대규모 복잡한 멀티 에이전트 시스템에서 매우 중요해질 것입니다.

이 비전에 다가가기 위해 저희는 몇 주 전 Managed Agents의 공개 베타로 메모리를 출시했습니다. 기본값으로 지능을 극대화하고, 같은 환경에서 동시에 실행되는 다중 에이전트 시스템을 지원하며, 기업과 개발자가 실제 프로덕션에서 실행할 수 있는 유연성과 제어 권한을 제공합니다.

이미 여러 팀이 사용하고 있는데, 예를 들어 Rakuten은 이를 통해 내부 지식 에이전트의 첫 시도 실수를 90% 줄였습니다. 에이전트가 실수를 발견하면 다음 세대 에이전트와 공유했고, 이는 토큰 효율 향상과 비용 절감, 레이턴시 개선으로도 이어졌습니다.

이제 설계 요건을 이야기하겠습니다. 첫 번째이자 가장 중요한 것은 메모리가 기본값으로 지능을 극대화해야 한다는 것입니다. 에이전트 빌더들은 한동안 메모리 시스템을 설계해왔습니다. 저희도 약 1년 반 전 Claude Code와 함께 claude.md를 출시했습니다. 에이전트가 자기 자신에게 노트를 남기는 초기 버전이었고, 사용자도 같은 메모리 파일에 노트를 남기기도 했습니다. SDK 내의 메모리 도구도 출시했는데, 특정 파라미터와 출력 형식이 사전 규정된 도구 호출이었습니다.

에이전트가 개선될수록 저희는 Claude에게 더 많은 결정을 위임하되 과도한 구조화를 피하는 방향으로 나아갔습니다. Skills에서 그랬던 것처럼, 에이전트가 가상 환경과 파일시스템을 이미 잘 관리하고 있으니 메모리도 같은 방향으로 가면 되지 않을까 결론을 내렸습니다. Managed Agents의 메모리는 Claude에게 메모리를 파일 시스템으로 모델링합니다. 특정 계층 구조와 형식을 가진 파일 시리즈로, Claude가 스스로 관리하고 업데이트할 수 있습니다. bash·grep 같은 익숙한 도구를 써서 메모리를 업데이트하고, 정리하고, 작업에 따라 지속적으로 변경합니다.

이는 최신 모델에서 보이는 경향과도 맞닿아 있습니다. 지난 달 출시한 Claude Opus 4.7은 파일시스템 기반 메모리에서 state-of-the-art 성능을 보였습니다. 무엇을 메모리에 넣을지 판단하는 능력, 어떤 구조로 메모리를 구성할지 — 몇 개 파일로 분할할지, 어떻게 정리할지 — 가 모두 Claude가 이미 agentic coding에서 잘 쓰는 bash·grep 도구만으로 이뤄집니다.

두 번째 요건은 멀티 에이전트 시스템으로의 확장성입니다. 멀티 병렬 에이전트는 이미 Claude Code에서 시작되고 있습니다. 10~15개의 Claude Code 세션을 동시에 돌리는 사람들이 생기고 있고, 기업 환경에서도 수백~수천 개의 에이전트가 병렬로 같은 공유 상태와 공유 메모리에 접근하는 상황입니다.

여기서 두 가지 속성이 나옵니다. 첫째, 에이전트가 세션과 작업에 따라 서로 다른 메모리 스토어를 혼합 접근할 수 있어야 합니다. 예를 들어, 조직 전체의 best practice와 런북이 담긴 메모리 스토어는 읽기 전용이고, 특정 작업의 working memory는 읽기-쓰기입니다. 둘째, 동시성(concurrency)입니다. 수백~수천 개 에이전트가 동시에 같은 메모리 상태에 접근할 때 서로의 메모리를 덮어쓰지 않도록 해야 합니다. 저희는 낙관적 동시성을 구현했습니다. 에이전트가 content hash로 자신의 업데이트가 다른 에이전트 메모리를 덮어쓸지 여부를 실제 업데이트 전에 확인합니다.

세 번째이자 고객으로부터 가장 중요하다고 들은 요건은 기업 제어입니다. 첫 번째는 버전 히스토리. 메모리가 업데이트될 때마다의 전체 감사 로그를 개발자가 볼 수 있고, 미래에 에이전트에게도 같은 감사 로그에 대한 접근권을 줄 수 있습니다. 어느 에이전트가, 어느 세션에서, 언제 변경했는지까지 매우 세밀하게 추적할 수 있습니다. 두 번째는 독립형 API. 많은 고객이 Managed Agents 외부에서 별도 시스템으로 메모리를 관리합니다. PII 스캔, 클린업, 외부 시스템 복제 등을 위해 특정 시스템에 종속되지 않는 포터블 API가 필요했습니다.

이제 Dreaming을 이야기하겠습니다. 저희는 에이전트 메모리 API가 메모리의 일부를 해결하지만, 대규모 멀티 에이전트 시스템에서 몇 가지 한계를 발견했습니다. 세션마다 다른 에이전트들이 이미 발견한 학습을 놓치는 경우, 여러 에이전트가 같은 환경에서 공통 실수와 패턴이 반복되는 경우, 그리고 대규모 메모리 스토어를 전체적으로 최신 상태로 유지하는 것이 비효율적인 경우가 있었습니다. 각 에이전트가 자신의 특정 작업에만 집중하는 사일로 문제였습니다.

Dreaming은 이를 해결하기 위해 개발한 프로세스이고, 오늘 Managed Agents API의 리서치 프리뷰로 출시합니다.

Dreaming은 최근 에이전트 세션과 트랜스크립트에서 패턴과 실수를 찾아 자동으로 정리되고 최신화된 메모리 콘텐츠를 생성하는 프로세스입니다. Harvey가 법률 벤치마크에서 Dreaming을 적용했을 때 작업 완수율이 6배 향상됐습니다.

Dreaming은 특정 세션이 특정 작업을 수행하는 것과 별개로 실행되는 비동기 배치 프로세스입니다. 콘솔에서 cron 방식으로 주기적으로 실행하거나, API로 기존 프로세스에 연결할 수 있습니다. 일부 고객은 에이전트가 작업을 마치고 스핀다운할 때 Dreaming을 트리거해 학습을 메모리에 저장합니다. Dreaming은 최근 트랜스크립트를 전반적으로 살피며 — 실패한 도구 호출이나 효과적인 전략 같은 — 공통 실수와 패턴을 찾아 메모리 상태를 개선합니다. 결과로 나온 업데이트된 메모리 상태는 즉시 적용하거나 API로 검토 후 적용할 수 있습니다. Dreaming의 궁극적 목표는 연속 자가학습과 자기 개선입니다. 다음 날의 에이전트가 전날의 학습과 작업 경험을 기반으로 자동으로 더 나아지는 것입니다.

Dreaming을 설계·연구 관점에서 기대하는 이유는 몇 가지입니다. 첫째, 메모리 상태와 달리 Dreaming은 오프밴드입니다. 특정 세션이나 특정 작업 중인 에이전트의 컨텍스트 밖에서 실행됩니다. 단일 에이전트가 자신의 컨텍스트와 작업 관점에서만 메모리를 읽고 쓰는 것과 달리, Dreaming은 한 단계 위에서 여러 에이전트를 동시에 바라보며 단일 에이전트가 자신의 제한된 관점에서는 학습하거나 알아채지 못할 공통 패턴과 학습을 찾아냅니다.

하네스 설계 관점에서도 에이전트가 작업을 시작할 때 명확하고 이산적인 목표를 갖는 것이 중요하다는 것을 일관되게 발견했습니다. Dreaming은 메모리 품질이라는 새 목표를 분리합니다. 앞으로 몇 달 동안 메모리는 에이전트 결과물에 점점 더 중요한 역할을 하게 될 것이므로, 메모리 품질 목표를 많은 에이전트가 이미 갖고 있는 작업 완수·성능 목표에서 분리하는 것입니다. 또 Dreaming은 오프밴드 프로세스이기 때문에 에이전트의 기존 작업 hot path에 어떤 레이턴시도 추가하지 않습니다.

또 한 가지 흥미로운 관점은 대규모 메모리 시스템에서 compute를 효과적으로 활용하는 방법입니다. 오늘날 대부분의 메모리 배포는 특정 사용자나 특정 작업, 혹은 소규모 팀에 국한되어 있습니다. 하지만 에이전트 시스템은 빠르게 기업 규모로 성장하고 있고, Anthropic 내부와 저희가 함께 일하는 기업들에서 이미 수백~수천 개 에이전트가 동시에 공유 상태를 가지고 실행되고 있습니다. 이는 사실상 단순한 작업 컨텍스트 저장소가 아닌 거대한 지식베이스가 됩니다. Dreaming은 test-time compute나 thinking model과 유사한 스케일링 법칙을 따르며, 추가 compute를 써서 이 메모리 시스템을 잘 정리된 상태로 유지합니다. 마치 검색 시스템이 사전에 고품질·최신 인덱스를 구축해두고 검색 시점에 효율적으로 결과를 제공하는 것처럼, Dreaming이 이 인덱스를 사전에 생성하고 큐레이션해 모든 다운스트림 에이전트가 효율적으로 사용할 수 있게 합니다.

이제 간단한 데모를 보겠습니다. 여기는 SRE 에이전트가 들어오는 알람을 보고 반응하는 시스템입니다. 알람에 따라 트리아지 작업을 하는 에이전트나 PR을 제출하는 에이전트를 스핀업합니다. 각 에이전트에는 몇 가지 메모리 스토어가 갖춰져 있습니다. 조직 전체 지식베이스와 SRE·코드 기반 메모리 스토어입니다. 조직 전체 지식 메모리 스토어를 클릭해보면 읽기 전용입니다. 런북과 SLO 가이드라인, 에이전트가 연락해야 할 담당자 목록이 있습니다. 자주 업데이트되지 않으며 에이전트가 작업 중 변경하는 것은 원하지 않습니다.

SRE 메모리 스토어는 읽기-쓰기입니다. SRE 에이전트는 주변 환경에서 반응하고 학습하면서 지속적으로 이를 업데이트합니다. dispatch 서비스에서 P1 알람이 들어오고, SRE 에이전트가 스핀업해 조사를 시작합니다. CPU 사용률을 조사하고, 트래픽 패턴을 확인하고, 최근 배포된 PR을 쿼리합니다. 그리고 SRE 메모리 스토어에 이 학습을 기록하며 새 diff로 업데이트합니다. 몇 분 후 같은 알람이 다시 울립니다. 다른 SRE 에이전트가 같은 메모리 스토어에 접근해 스핀업합니다. 이 에이전트가 제일 먼저 하는 일은 메모리 스토어에서 1번 에이전트가 남긴 노트를 확인하는 것입니다. "우리가 이미 조사했고, 여기서 발견한 것이 있고, 이렇게 단축할 수 있다"는 내용을 바로 파악합니다. 같은 것을 재조사하는 데 소요될 시간을 절약합니다. 즉각적인 토큰 효율 향상과 지능 향상을 볼 수 있습니다.

이것은 훌륭하지만, 엔터프라이즈에서 실제로 신뢰성 있게 배포하고 어떤 의사결정이 어떤 결과로 이어졌는지 보려면 메모리 스토어의 버전 히스토리를 봐야 합니다. 매번 업데이트될 때마다 기록이 남고, 어느 에이전트가 변경했는지, 언제 작성됐는지 확인할 수 있습니다. 그리고 precondition hash — 낙관적 동시성을 위한 도구로, "내가 이 변경을 하기 전에 현재 상태가 내가 알고 있는 것과 같은지 확인한다"는 역할을 합니다.

이제 Dreaming이 이것을 어떻게 더 종합적이고 최신화된 메모리 시스템으로 만드는지 보겠습니다. Claude 콘솔로 이동하면 API의 상태가 그대로 반영됩니다. 팀 SRE 메모리 스토어를 클릭하고 Dreaming 탭으로 가면 Dreaming 작업을 시작할 수 있습니다. "이 메모리 스토어를 업데이트하고, 지난 7일간 이 메모리 스토어에 접근한 세션들을 모두 보겠다"고 설정하고 시작합니다. 어떤 입력 세션을 살펴볼지 보여주고, 실제로 Claude 콘솔 내에서 세션이 생성되어 진행 상황을 볼 수 있습니다. 트랜스크립트 엔트리를 보고, 여러 서브에이전트를 스핀업해 그 트랜스크립트를 살피고, 학습을 식별하고, 업데이트된 메모리 상태를 생성합니다.

몇 분 후 완료된 Dreaming 작업을 보면 diff — 이 메모리 스토어에 적용할 업데이트된 파일 셋 — 가 생성됩니다. 첫 번째 업데이트는 앞서 데모에서 본 dispatch 레이턴시 노트입니다. 여러 에이전트가 CPU 사용률 급등 후 정확히 60초 후에 트리거된 패턴을 발견했습니다. 그리고 그 패턴을 바탕으로 매우 비효율적이고 트리아지 시간 낭비로 이어지는 retry 로직이 트리거되고 있을 수 있다고 판단합니다. 개별 에이전트들은 이 패턴을 알아채지 못했습니다. 다른 에이전트들도 같은 60초 패턴을 보고 있다는 것을 몰랐습니다. Dreaming이 이 학습이 매번 이루어질 수 있도록 하고, 미래 에이전트들이 이 학습을 바탕으로 더 효율적으로 파악할 수 있도록 노트를 남깁니다.

또한 중복 제거와 큐레이션 작업을 합니다. 이전 에이전트들이 이 메모리 스토어에 남긴 동일한 엔트리 5개를 발견하고 단일 엔트리로 통합합니다. 트랜스크립트에서 더 이상 유효하지 않은 stale 엔트리를 제거합니다. 그리고 검증 노트를 추가합니다. "방금 본 이 트랜스크립트에서 이 메모리는 실제로 정확합니다. 에이전트가 하는 작업을 기반으로 검증할 수 있었고, 따라서 같은 메모리 스토어를 사용하기 시작하는 다음 날에도 신뢰할 수 있습니다." 이것이 메모리와 Dreaming이 유용한 검증·백필·정리 작업입니다.

이 데모에서 우리가 본 것은 Managed Agents API의 메모리와 Dreaming API를 사용해 프로덕션 에이전트를 실제로 구축하는 방법입니다. 마무리하자면, 앞으로 몇 달 동안 에이전트가 며칠 혹은 수십 시간씩 실행되는 모습을 보게 될 것입니다. 메모리가 그 시스템의 매우 중요한 부분이 될 것이고, 궁극적으로 그것을 가능하게 하는 요소가 될 것입니다. 메모리와 Dreaming으로 무엇을 만드실지 정말 기대됩니다. 오늘부터 시작해보세요. 감사합니다.
