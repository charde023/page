Claude Code 개발팀이 Claude Code를 쓰는 방법 — Codex 버전

업로드 2026-09-03 · 22.4분 · 원본 영상 ↗

먼저 읽는 쉬운 요약

처음 보는 사람을 위한 읽기 안내

영상 미시청 기준 · 약 3분 · 선수지식: 없음 이 부분만 읽어도 아래 중심 질문에 자기 말로 답할 수 있게 설명한다.

이 대담의 핵심은 AI 코딩 도구를 다루는 단위가 세부 명령에서 목표로 커졌다는 것이다. 초기에는 사람이 함수 작성, 도구 호출, 권한 승인 같은 과정을 하나씩 지켜봤다. 이제 참여자들은 Slack 안의 에이전트인 Claude Tag에 목표와 팀의 맥락을 주고, 결과가 나올 때까지 더 멀리 떨어져 일한다고 말한다.

하지만 큰 목표를 맡기면 생성되는 코드와 정보도 늘어난다. 그래서 여러 에이전트가 문제를 나눠 찾고 다시 반박·검증한 뒤 중요한 결과만 합치는 방식(팬아웃과 테스트 타임 컴퓨트)을 사용한다. 반복 규칙은 코드로 고정하고, 판단이 필요한 부분은 언어 모델에 맡기는 혼합 구조다. 사람은 사소한 표현이나 코드 한 줄보다 API 구조, 서비스 경계, 사용자 반응처럼 더 큰 판단에 집중한다.

또한 모델이 좋아지면 과거의 보조 장치가 불필요해질 수 있다. 예전에는 긴 작업을 끝내도록 할 일 목록이 필요했지만, 이후에는 더 복잡한 기억 방식으로 대체됐다고 한다. 따라서 좋은 AI 제품은 기능을 계속 더하기만 하는 것이 아니라, 현재 모델의 약점을 메우던 장치를 과감히 제거하고 더 큰 작업에서 생기는 새 실패를 검증해야 한다.

여기까지만 이해하면 충분

  • AI 에이전트 활용의 중심이 세부 지시에서 목표와 맥락의 위임으로 이동했다.
  • 작업을 넓게 나누는 팬아웃 뒤에는 반박, 필터링, 요약 같은 검증 단계가 필요하다.
  • 모델이 발전하면 과거의 보조 기능을 계속 유지하지 말고 필요성을 다시 판단해야 한다.
  • 사람의 역할은 줄 단위 감시보다 구조, 우선순위, 최종 책임을 판단하는 쪽으로 이동한다.

오늘 대답할 질문

Claude Code 팀은 더 큰 목표를 에이전트에게 맡기면서 어떻게 통제와 신뢰를 유지하려 하는가?

  • 모델이 발전할 때 기존 기능을 왜 제거하는가?

한 장면으로 이해하기

한 개발자가 Slack에서 “이 기능의 사용 흐름을 개선해 줘”라는 목표를 준다. 에이전트는 팀 대화와 사용 이벤트를 참고하고, 여러 후보를 만든 뒤 검증 결과와 중요한 피드백만 사람에게 보낸다. 사람은 모든 내부 도구 호출을 감시하는 대신 실제 사용 흐름과 구조적 위험을 확인한다.

"사람이 늘어난 코드와 모든 에이전트 행동을 직접 확인하기 어렵다" 문제
→ "목표를 위임하고 작업을 나눈 뒤 반박·검증·요약으로 다시 합친다" 작동 방식
→ "사람은 중요한 예외와 큰 구조적 판단에 집중한다" 결과

비유와 깨지는 지점

운전기사에서 배차 관리자로

사람이 매 순간 운전대를 움직이는 대신 목적지를 정하고, 여러 차량의 진행 상황과 위험 신호를 확인하는 모습과 닮았다. 세부 실행은 에이전트가 맡고 사람은 목표, 우선순위, 예외를 관리한다.

비유가 깨지는 지점: 에이전트는 독립적으로 책임지는 운전기사가 아니다. 맥락을 놓치거나 그럴듯한 오류를 만들 수 있으므로 결과 검증과 최종 책임은 여전히 사람에게 남는다.

1. 원인

모델이 좋아졌는데도 왜 검증과 작업 구조가 더 중요해지는가?

모범 답안 보기

모델이 좋아지면 더 크고 복잡한 작업을 맡기게 되고, 그만큼 생성되는 코드와 정보도 많아진다. 사람이 전부 읽기 어려워지므로 팬아웃 결과를 반박·필터링하고 중요한 항목만 전달하는 검증 구조가 필요해진다.

2. 대조

세부 도구 호출을 감시하는 방식과 목표 수준에서 관리하는 방식은 무엇이 다른가?

모범 답안 보기

전자는 모델의 각 행동과 매개변수를 사람이 가까이서 확인한다. 후자는 목표, 맥락, 검증 조건을 먼저 정하고 사람은 결과와 큰 구조를 확인한다. 후자가 감독을 없애는 것은 아니며 감독의 위치를 바꾸는 것이다.

3. 적용

새로운 에이전트 자동화를 도입할 때 무엇을 먼저 맡기고 무엇을 사람이 남겨야 하는가?

모범 답안 보기

되돌릴 수 있고 결과를 관찰하기 쉬운 작업부터 맡긴다. 반복 규칙은 코드로 고정하고, 에이전트 결과에는 검증 자료를 붙인다. 큰 비용, 권한, 고객 영향, 구조적 선택처럼 실패 비용이 큰 판단은 사람이 확인해야 한다.

이번 글의 통찰

1. 감독은 사라지는 것이 아니라 추상화 수준이 올라간다

  • [원문] 한 참여자는 작업의 70~80%가 Claude Tag에서 이뤄지고, 20%는 TUI나 데스크톱 앱에서 다듬거나 세밀하게 관리한다고 말했다. Robert로 지칭된 참여자는 Slack 메시지 뒤의 전체 내부 과정을 보지 않는 방식이 처음에는 두려웠지만 자유로웠다고 설명했다.
  • [해석] 에이전트 활용의 성숙도는 감시를 포기하는 데 있지 않다. 도구 호출 감시를 줄이고 목표, 증거, 예외, 최종 결과를 확인하는 쪽으로 감독 위치를 옮기는 데 있다.
  • [경계] 70~80%와 20%는 합계가 90~100%이므로 완전한 업무 분류로 단정할 수 없다. 특정 참여자의 체감이며 기간, 측정 방법, 업무 정의도 제시되지 않았다.

2. 현재 모델의 약점을 메우는 기능은 임시 발판일 수 있다

  • [원문] 참여자들은 Sonnet 3.5 무렵 긴 작업을 돕던 할 일 목록이 약 1년 뒤에는 필요성이 줄었다고 말했다. AskUserQuestion 도구도 이후 HTML 아티팩트가 질문, 도표, 모형을 보여주는 방식으로 바뀌었다고 설명했다.
  • [해석] AI 제품에서는 기능 추가뿐 아니라 제거 기준도 설계해야 한다. 모델의 약점을 보완하던 기능인지, 사용자에게 독립적인 가치를 주는 기능인지 구분해야 한다.
  • [경계] “기반 기술이 두 달마다 근본적으로 바뀐다”는 표현과 기능 변화 시점은 화자의 경험적 주장이다. 모델별 비교 실험이나 객관적인 제거 기준은 전사에 제시되지 않았다.

3. 생성량이 늘수록 사람은 중요한 판단을 골라야 한다

  • [원문] 코드 리뷰에서는 여러 방향으로 버그 후보를 찾고, 각 후보를 세 관점에서 반박 검토한 뒤 중요한 항목만 사람에게 전달한다고 설명한다. 사람은 사소한 지적보다 API 구조와 서비스 경계 같은 큰 맥락에 집중한다.
  • [해석] 병렬 생성의 가치는 결과 수가 아니라 유효한 문제를 얼마나 잘 압축해 사람의 제한된 주의에 전달하느냐로 평가해야 한다.
  • [경계] 팬아웃과 추가 계산이 신뢰를 높인다는 주장은 오류율·비용·처리시간 자료로 검증되지 않았다. 한 참여자의 “생산성이 10배 증가했다”는 주장도 기준선이 없다. META는 세 엔지니어의 이름을 적지만 전사는 Sid와 Robert 외 화자를 일관되게 표시하지 않아 발언별 인물 매핑이 불가능하다. META의 소속 필드는 Code, 설명은 Anthropic의 Claude Code 팀이라고 적어 표기가 일치하지 않으며, 원본 출처도 화자 이름과 SNS를 기준으로 추정됐다고 명시돼 있다.

차드의 4렌즈

교육자 · 구조적 비유

  • 관련성: 사소한 코드 지적보다 큰 구조를 설명하게 한다는 대목은 암기보다 원인과 판단을 확인하는 교육과 닮았다.
  • 통찰: 학습자의 모든 과정을 감시하기보다 결과의 이유, 예외, 적용 조건을 설명하게 하면 이해 여부를 더 직접 관찰할 수 있다.
  • 질문/행동: 답만 확인하지 말고 “왜 이 방법이며 언제 실패하는가?”를 덮고 설명하게 할 수 있는가?

사업가 · 구조적 비유

  • 관련성: 반복 실행을 원격 루프로 넘기고 사람의 주의를 중요한 예외에 쓰는 구조는 운영 자원 배분과 연결된다.
  • 통찰: APOM에 적용한다면 현재 사실이 아니라, 되돌릴 수 있는 반복 업무만 자동화하고 비용·고객 영향이 큰 예외는 사람이 맡긴다는 검증 전 가설로 다뤄야 한다.
  • 질문/행동: 결과를 쉽게 검증할 수 있으면서 반복 시간이 큰 업무 후보는 무엇인가?

마케터 · 구조적 비유

  • 관련성: 여러 후보를 만든 뒤 반박과 증거 확인으로 압축하는 방식은 카피와 상세페이지 검토에도 옮겨볼 수 있다.
  • 통찰: 아이디어 수보다 각 주장에 어떤 증거가 붙고, 반박을 견딘 주장만 남는지가 중요하다.
  • 질문/행동: 카피 후보마다 “근거 없음, 조건부, 확인됨”을 표시한 뒤 최종안만 사람에게 보여줄 수 있는가?

AI/SW 학습자 · 직접 전이

  • 관련성: 원격 실행, 팬아웃, 코드 기반 반복, 에이전트 검증이 대담의 직접적인 작업 주제다.
  • 통찰: 기술 이름보다 작업 범위, 실패 비용, 검증 가능성, 사람이 기다리는 시간을 기준으로 구조를 선택해야 한다.
  • 질문/행동: 저위험 작업에서 에이전트 결과와 검증 자료를 함께 제출하도록 만들 수 있는가?

가치 지도

"늘어난 코드와 정보를 사람이 모두 직접 검토하기 어렵다" 문제
→ "중요한 오류와 구조적 판단에 집중할 수 있다" 수혜자: 개발자와 제품 사용자
→ "추론 계산, 이벤트 데이터, 검토 시간과 신뢰를 제공한다" 지불자 또는 자원 제공자: 개발팀과 운영 주체
→ "최종 제시된 이슈 중 실제 수정이 필요하다고 판정된 비율" 가치 지표

작은 실험 하나

  • 행동 1개: 저위험 코드 리뷰 한 건을 세 관점으로 나눠 검토한 뒤, 반박 검토를 거친 상위 이슈만 사람에게 제시한다.
  • 측정 1개: 최종 제시 이슈 중 사람이 실제 수정이 필요하다고 판정한 비율
  • 중단 기준 1개: 그 비율이 50% 미만이면 확대하지 않고 팬아웃과 필터 조건을 다시 설계한다.

5 Claude Tag의 자기 개발 구현, 배포, 사용 관찰, 피드백 연결에 에이전트를 쓴다
6 엔지니어 역할 변화 세부 구현보다 아이디어와 큰 구조에 더 많은 주의를 쓴다

1. 목표 중심 작업

참여자들은 초기 Claude Code가 함수 작성, 도구 호출, 권한 승인처럼 작은 단위를 중심으로 사용됐다고 회고한다. 현재는 Slack 안에서 작동하는 Claude Tag가 제품 맥락과 팀의 과거 결정을 찾아 더 큰 목표를 처리한다고 설명한다.

한 참여자는 업무의 70~80%가 Claude Tag에서 이뤄지고, 20% 정도는 TUI나 데스크톱 앱에서 다듬는다고 말했다. 이는 측정된 팀 전체 통계가 아니라 개인적 사용 비중이며 두 수치가 완전한 분류를 이루는지도 분명하지 않다.

2. 빠르게 낡는 보조 기능

참여자들은 AI 모델 아래의 기술 기반이 두 달 단위로 바뀐다고 표현한다. 현재 사용자에게 가치를 제공하면서도 다음 모델의 능력을 예상해야 하는 균형이 어렵다는 주장이다.

Sonnet 3.5 무렵에는 다섯 가지 일을 주면 세 가지만 하고 멈추는 문제가 있어 할 일 목록을 도입했다고 회고한다. 약 1년 뒤에는 더 복잡한 기억 상태를 사용할 수 있어 그 장치의 필요성이 줄었다고 말한다. 하네스 기능은 현재 모델의 실패를 메우므로 모델이 좋아지면 제거할 수 있어야 한다는 결론을 제시한다.

AskUserQuestion도 처음에는 모델이 적절히 호출하도록 설계하기 어려웠지만, 이후에는 HTML 아티팩트가 질문과 도표, 모형을 직접 보여주는 방식으로 발전했다고 설명한다.

3. 원격 루프

처음에는 노트북에서 에이전트를 실행했기 때문에 퇴근하며 컴퓨터를 끄면 작업도 멈췄다. 이후 원격 개발 환경과 호스팅 컨테이너로 옮겨 노트북이 꺼져도 작업이 계속되도록 했다고 한다.

환경 접근 권한을 설정하는 과정은 번거로웠지만, 한 참여자는 생산성이 10배 증가했다고 평가한다. 다만 기준 작업, 기간, 측정 방법은 제시되지 않았다.

클라우드에서 실행되면 매일 피드백을 중요도별로 나누고, 자신 있게 처리할 수 있는 문제를 고치는 루틴도 만들 수 있다고 설명한다. 이는 한 번의 대화 세션을 넘어 반복 목표를 실행하는 구조다.

4. 팬아웃과 검증

생성 코드가 늘어나면서 사람에게 모든 줄을 읽게 하는 대신 Claude가 작은 지적을 먼저 처리하고, 사람은 API 구조와 서비스 경계 같은 큰 문제를 보게 한다고 말한다.

코드 리뷰 워크플로우는 문제를 여러 갈래로 나눠 버그 후보를 찾는다. 각 후보를 세 가지 관점에서 다시 검토해 실제 버그인지 반박하고, 중요한 항목만 합쳐 사람에게 전달한다. Sid로 불린 참여자는 이 구조를 성능 문제, 심층 조사, 여행 계획 등에도 적용할 수 있다고 설명한다.

병렬 결과가 너무 많아지면 사람이 읽을 수 없으므로 다시 압축해야 한다. 참여자들은 이를 MapReduce와 비슷한 문제로 설명하며, 실행 시점에 더 많은 추론 계산을 사용하는 테스트 타임 컴퓨트로 신뢰를 높이려 한다.

워크플로우에는 코드로 정한 반복문과 언어 모델의 판단이 함께 들어간다. 모든 항목에 같은 작업을 적용하는 부분은 코드로 고정할 수 있어 신뢰에 도움이 된다는 주장이다.

5. Claude Tag의 자기 개발

Robert로 불린 참여자는 Claude Tag를 이용해 Claude Tag 자체를 적극적으로 개발한다고 말한다. 에이전트가 사람이 하던 개발과 종단 간 시험을 수행할 수 있도록 개발 환경과 반복 과정을 정비하는 것이 주요 과제라고 설명한다.

Slack 인터페이스에서는 내부 독백과 전체 전사가 기본적으로 보이지 않는다. 사람은 Claude Tag가 도구로 보낸 메시지를 중심으로 작업하며, 필요하면 전체 전사 링크를 열 수 있다.

다른 참여자는 새 도구의 이해관계자를 찾고, 모형을 만들고, 구현·내부 배포한 뒤 사용 이벤트와 피드백을 Claude Tag가 감시하게 한 사례를 말한다. 다만 최종 확인을 위해 직접 복제해 사용했으며, 장차 그 단계도 생략할 수 있을 것이라는 전망만 제시했다.

6. 엔지니어 역할 변화

참여자들은 성능 최적화나 세밀한 UI 구현처럼 과거 직접 즐기던 작업을 Claude가 더 많이 수행하게 됐다고 말한다. 한 참여자는 Mac OS 10.4 Aqua 버튼을 CSS로 재현하는 데 하루를 쓴 과거 사례를 들며, 지금은 그런 작업을 수동으로 하지 않을 것이라고 설명한다.

그 대신 아이디어에서 시제품과 실제 배포까지 가는 시간이 짧아지고, 관심이 세부 구현에서 새로운 아이디어와 큰 구조로 이동했다고 말한다. 이들은 소프트웨어 엔지니어링의 본질을 특정 기술의 숙련보다 변화하는 도구를 이용한 문제 해결로 정리한다.

수치·이름·출처 경계

  • 영상 길이 1,343초와 META의 22.4분은 반올림 범위에서 일치한다.
  • META 설명은 엔지니어 3인으로 Thariq Shihipar, Sid Bidasaria, Robert Boyce를 열거해 개수와 이름 수는 일치한다.
  • 전사는 Sid와 Robert를 직접 부르는 부분만 있으며, 나머지 발언을 Thariq Shihipar 또는 진행자에게 확정해 배정할 수 없다.
  • 70~80%와 20%는 합계가 90~100%이므로 완전한 업무 비중표로 해석하면 안 된다.
  • 여행 예시는 검색 요청 10개를 만들 수 있다고 말한 뒤 네 가지 범주만 예시하고 “그 밖의 것”을 덧붙인다. 열 개의 구체적인 요청을 모두 열거한 것은 아니다.
  • “두 달마다 기술이 바뀐다”, “생산성이 10배 늘었다”는 참여자 주장으로, 독립 검증 자료는 없다.
  • META의 provenance.creator는 비어 있고 affiliation은 Code다. 설명에는 Anthropic의 Claude Code 팀이라고 적혀 있어 소속 표기가 일치하지 않는다.
  • META는 채널이 원본 영상 링크를 제공하지 않았으며 화자 이름과 SNS를 근거로 출처를 추정했다고 밝힌다. 따라서 원작자와 원본 게시처는 확정할 수 없다.

교정 전사 (한국어)

전체 전사 펼치기

여러분은 내년에 대해 어떤 생각을 갖고 있나요?

저는 앞으로 두 달을 생각하는 것도 어려운데, 하물며 내년을 생각하는 건 더 어렵게 느껴져요.

여러분이 아실지 모르겠지만, 제가 Claude Code에 합류한 지 거의 1년이 됐어요. 1년 전에는 Claude Code에 프롬프트를 입력하고, 피드백을 주고, 권한 요청(permission prompt)을 승인하던 단계였는데, 지금까지 우리가 얼마나 큰 발전을 이뤘는지 생각하면 정말 놀라워요.

지금은 Claude Code와 어떻게 협업하고 있는지 이야기해 주세요.

네, 사실 저는 지금 업무의 상당 부분을 Claude Tag을 통해 하고 있어요. Claude Tag에 맡기는 문제는 “이 클래스를 구현해 줘”나 “이 함수를 작성해 줘”처럼 Claude Code가 처음 시작했을 때의 문제보다 훨씬 더 복잡하고 어려워졌어요.

저는 Slack 안에서 Slack 네이티브 에이전트(Slack-native agent)로 작동하는 Claude Tag의 형태와 이 점이 정말 잘 맞는다고 생각해요. 제품의 맥락이 무엇인지, 이 제품이 어떤 것이어야 하는지에 대해 우리 팀이 어떤 결정을 내렸는지처럼 추가적인 맥락을 모두 찾아볼 수 있기 때문이죠. 그러면 의사결정을 훨씬 더 잘할 수 있어요. 그런 정보에 접근하고, 에이전트가 내리는 선택에 그 정보를 어떻게 반영할지 이해하는 것이 정말 큰 가치가 있어요.

네, 제 업무도 꽤 비슷해요. 지금 제 업무의 70~80%는 Claude Tag에서 이뤄지는 것 같아요. 나머지 20%의 업무에서는 무언가를 다듬기 위해 TUI나 데스크톱 앱을 열기도 해요. 아니면 Claude를 제가 세세하게 관리하고 싶을 때 그렇게 하죠.

우리는 개별 트랜스크립트(transcript), 각각의 도구 호출(tool call), 모델이 내리는 각각의 결정에 그토록 신경 쓰던 단계에서 벗어나, 이제는 한발 물러나 전체를 보는 관점으로 바뀐 것 같아요. 목표가 있고, 그 목표를 달성하고 싶다는 거죠. 그 목표를 모델에게 주고 대신 달성하게 하면 돼요.

제가 계속 생각해 온 것은 소프트웨어 개발 수명 주기(software development life cycle)가 얼마나 많이 바뀌었는지, 그리고 그 과정에서 우리가 얼마나 많은 것을 배웠는지예요. Claude Code를 만들고, 결국 Claude Tag으로 연결되는 여러 프리미티브(primitives)를 구축했죠. 이를 통해 검증부터 코드 리뷰, 브레인스토밍, 모니터링까지 모든 일을 하고 있어요.

Claude Code를 작업하는 것이 이전 소프트웨어 제품을 작업하는 것과 어떻게 다른지 이야기해 주세요.

어떤 제품이든, 아니면 정확히 말하면 그 제품을 구성하는 기술이든, 유효 기간이 있어요. 예전에는 기술의 유효 기간이 몇 년 정도였다고 생각해요. “이 제품을 만들 것이고, 앞으로 몇 년 이상은 계속 존재할 거라고 확신해”라고 말할 수 있었죠.

하지만 모델과 AI 모델에서는 그 기반 기술이 두 달마다 근본적으로 바뀌어요. 시간이 지나면서 그 주기가 더 짧아지고 있는지도 모르겠어요. 최첨단(frontier)을 계속 따라가야 하고, 사실 최첨단을 넘어선 곳까지 가야 그 경계를 느낄 수 있다는 점이 어려워요. 동시에 오늘 당장 모델을 사용하는 사람들에게도 가치를 제공해야 하죠.

결국 균형을 잡는 일이에요. 예술이면서 과학이기도 하죠. 내 밑에서 너무 빠르게 움직이는 이 기술을 위해 어떻게 만들어야 할까?

파도를 제대로 탄 것처럼 느꼈던 순간이 있었나요?

처음으로 “파도를 탄다”는 느낌을 받았던 건 할 일 목록(to-do list)이었던 것 같아요. 아마 Sonnet 3.5 때였을 텐데, 당시 모델은 장기적인 작업을 전혀 수행하지 못했어요. 다섯 가지 일을 시키면 세 가지를 하고 그냥 포기했죠.

그때 우리는 “할 일 목록을 주면 정말 잘하지 않을까?”라고 생각했어요. 실제로 정말 잘했죠. “와, 지금 이 시점에 우리에게 정확히 필요한 게 이거야”라는 느낌이었어요.

그런데 1년이 지나자 할 일 목록은 사라졌어요. 이제는 할 일 목록이 별로 필요하지 않아요. 더 복잡한 메모리 상태(memory state)와 의존할 수 있는 여러 요소가 생겼으니까요.

이 사례는 우리가 만드는 것에 지나치게 집착하지 말아야 한다는 점을 완벽하게 보여준다고 생각해요. 그런 것들은 상당히 빠르게 사라질 테니까요.

우리가 이런 것들을 Claude Code 하네스(harness)에 구축하는 주된 이유는 현재 모델의 상태에서 발생하는 일부 실패 모드를 보완하기 위해서예요. 모델이 더 좋아지면 우리는 “사실 우리가 만든 이 기능들은 더 이상 필요하지 않네. 이것들은 필요 없어. 없애도 돼”라고 자유롭게 말할 수 있어요.

그 균형을 맞춰 주는 것은 이런 질문이에요. “좋아, 이제 Claude Code에서 훨씬 더 크고 어려운 작업을 하고 있어. 모델이 일관성을 유지하면서 그런 더 큰 작업을 제대로 수행하려면 어떤 도구가 필요할까?”

필요한 도구는 작업의 범위가 바뀌면서 달라지기 시작해요.

많은 분이 저에게 “Claude Code 팀은 어떻게 일하나요?”라고 물어요. Claude Code 팀의 독특한 점 중 하나는 모델의 변화를 아주 긴밀하게 따라가야 한다는 거예요. 때로는 매우 빠르게 큰 변화를 만들어야 하죠.

우리는 “와, 모델이 정말 좋아졌어. 이제 완전히 새로운 능동형 에이전트(proactive agent)를 만들어야 해”라고 말하면서, 동시에 권한 시스템을 다시 작성하고 아티팩트(artifacts) 같은 것도 만들어야 해요. 이 일을 해낼 수 있는 소규모 팀이어야 하고요.

어떤 면에서 이는 소프트웨어 개발이 향하는 방향을 압축적으로 체험하는 공간(hyperbolic time chamber)과 같아요. 대부분의 제품이 이렇게 짧은 유효 기간을 갖거나 최첨단을 이렇게까지 따라가야 하는 건 아니라고 생각해요. 하지만 엔지니어라면 어느 정도는 반드시 이런 일을 해야 해요. 역량이 어디로 향하고 있는지 이해해야 하죠.

물론 우리는 제품을 통해 가능한 한 많이 도우려고 해요. 하지만 Claude에 대한 자신의 멘탈 모델(mental model)을 최신 상태로 유지하는 것도 좋아요.

AskUserQuestion 도구를 추가했을 때도 파도를 탄 또 다른 사례였던 것 같아요. 그 도구를 만들 때 무엇을 생각하고 있었고, 머릿속에서는 어떤 일이 일어나고 있었나요?

저는 Claude가 상호작용할 수 있기를 바랐어요. 처음에는 기본적으로 계획 수립 후에 이 기능을 넣었죠. 그런데 모두가 “잠깐, 그냥 Claude가 호출할 수 있는 도구로 만들면 어떨까?”라고 했어요.

도구를 설계하는 데 정말 오랜 시간이 걸렸어요. Claude가 그 도구를 제대로 호출하게 만들기가 정말 어려웠거든요. 결국 제가 설계를 마쳤고, Claude는 도구를 호출하는 데 갑자기 아주 능숙해지기 시작했어요.

최근에는 “나도 이 도구를 그렇게 많이 사용하지 않네. 그냥 아티팩트를 만들면 아티팩트가 나에게 질문을 하잖아”라는 생각이 들어요. 아티팩트는 HTML로 되어 있고, 다이어그램과 목업 같은 것도 포함해요.

“이 일이 정말 빠르게 일어났네, 그렇지?”라는 생각이 들어요. 처음에는 “도구가 간신히 할 수 있었는데” 이제는 할 수 있게 됐으니까요.

Claude Code에서는 이런 일이 자주 일어난다고 생각해요. 우리가 접근하는 방식은 이런 프리미티브를 만드는 거예요. “좋아, 권한은 어떻게 작동하지? 시각화는 어떻게 작동하지?”라고 묻는 거죠. 그러면 이 모든 요소가 차곡차곡 결합돼요.

루프(loop)에 대해 이야기해 주세요. 루프를 어떻게 사용하나요?

네, 어떤 면에서는 우리가 루프에 도달하게 된 과정을 따라가 보는 것이 흥미롭다고 생각해요.

저는 예전에는 모든 것을 노트북에서 로컬로 실행했어요. 어느 순간 사무실에서 집으로 돌아가야 했고, 노트북을 종료해야 했죠. 정말 싫었어요. 그러면 에이전트가 더 이상 실행되지 않으니까요.

켜 둔 채로 두면 안 됐나요?

그렇게 할 수도 있었죠. 하지만 그러려면 주차장까지 가야 했고, 사람들이 저를 이상하게 쳐다볼 거예요.

그때 제가 시작한 건 원격 호스팅 개발 박스(remote-hosted developer box)를 사용하는 일이었어요. “좋아, 노트북을 항상 켜 둘 필요는 없어. 호스팅 환경에서 실행되니까 나는 내 일을 하면 돼”라고 할 수 있게 해 줬죠.

하지만 어떤 면에서는 이것도 만족스럽지 않았어요. 환경에 SSH로 접속해서 호스팅된 작업 공간으로 돌아가야 했으니까요.

그때 Claude Code on the Web이 만들어진 것 같아요. 백그라운드에서 계속 실행될 수 있는 호스팅 컨테이너였죠.

그래도 시작하는 일은 조금 까다로웠어요. 컨테이너를 사용해 개발 환경을 호스팅하려면 그 컨테이너에 개발 환경에 대한 액세스 권한을 줘야 하거든요. 그 설정이 조금 번거로워요.

제 생각에는 충분히 그럴 만한 가치가 있어요. 그렇게 한 뒤로 생산성이 열 배는 높아진 것 같아요. 하지만 그 부분이 어려운 점이었죠.

이것이 우리가 이 문제를 발견하게 된 최초의 이야기라고 생각해요. Claude를 로컬에서 실행하다가, Claude를 클라우드에서 실행해야 했던 거죠.

이제 클라우드에서 실행된다면 정말 흥미로운 일을 할 수 있어요. 루틴을 만들 수도 있죠. “매일 우리가 받는 피드백을 모두 살펴보고, 중요도에 따라 범주로 나눈 다음, 수정할 자신이 높은 것들을 고쳐 줘”라고 할 수 있어요.

이것이 Boris가 자주 이야기하는 전체 루프 여정이기도 해요. 세션에서 모델에 프롬프트를 입력하는 단계에서, 세션이라는 경계를 허물고 그보다 한 단계 위에 있는 무언가에 프롬프트를 입력하는 단계로 나아가는 거죠. 그러면 그것이 버그를 수정하거나 여러분을 대신해 일을 처리해 줘요.

네, 사실 코드 리뷰와 보안에 대해 좀 더 이야기하고 싶었어요. 코드를 훨씬 더 많이 작성하고, 더 많은 코드가 생성되는 상황에서는 자신의 일이 코드를 리뷰하는 것이 되기를 원하지 않잖아요?

물론 지금 우리에게는 코드 리뷰 봇이 있어요. 하지만 전반적으로 코드 리뷰가 팀 내부에서 어떻게 바뀌었고 지금은 어떻게 진행되는지 여러분에게 묻고 싶어요.

가장 큰 변화 중 하나는 Claude가 인간 리뷰어가 시간과 에너지를 어디에 집중할지 선택하는 데 큰 도움을 준다는 점이에요.

전통적인 인간 코드 리뷰에서 흔히 보았던 일은 누군가 코드를 리뷰한 다음, 사소한 지적 세 가지를 골라 게시하는 것이었어요. “내가 이 코드를 읽었다는 걸 알려 주는 거야. 실제로 주의 깊게 읽었다는 걸 증명하기 위해 지적하고 싶은 사소한 세 가지가 여기 있어”라는 식이었죠.

이제 Claude가 그런 사소한 부분을 찾아 자율적으로 처리할 수 있어요. 더 이상 인간 코드 리뷰에서 중요한 부분은 아니죠.

중요한 것은 더 큰 그림을 이해하는 일이에요. Claude가 API가 왜 그런 구조로 되어 있는지, 또는 서비스 경계가 왜 특정 위치에 설정되어 있는지에 대한 이유를 완전히 이해하지 못한 상태에서 PR을 작성했을 수도 있어요.

그런 정보를 코드 리뷰에 가져온 다음 사람에게 넘길 수 있다는 건 Claude가 할 수 있는 정말 가치 있는 일입니다. “코드를 한 줄씩 읽으면서 뭔가 하나를 트집 잡아야지”라는 식으로 빠져들지 않게 해 주고, 대신 인간 코드 리뷰어로서 생각하는 추상화 수준을 한 단계 높여 줍니다.

코드 리뷰가 우리가 이런 대규모 팬아웃(fan-out)을 처음으로 했던 때였던 것 같아요. “좋아, 모든 버그를 어떻게 찾지? 잠재적인 버그를 어떻게 전부 검색하지?”라고 했죠.

우리는 이렇게 크게 팬아웃한 다음 하나로 취합합니다. 이걸 테스트 타임 컴퓨트(test-time compute)라고 부릅니다. 추론 시간(inference time)을 많이 사용해서 문제에 많은 사고와 컴퓨팅을 투입하는 거죠. 이로부터 워크플로가 나왔습니다.

Sid, 그 얘기와 워크플로를 어떻게 만들었는지 들려줄 수 있나요?

코드 리뷰는 애초에 워크플로가 생겨난 과정에서 큰 부분을 차지했습니다.

우리에게는 이 거대한 팬아웃 작업이 있습니다. 거의 커스텀 하네스(custom harness)처럼, Claude에게 나가서 팬아웃하고 버그를 찾으라고 지시하는 방식이었죠. 그런 다음 각 버그에 대해 적대적 리뷰(adversarial review)를 할 수도 있습니다. 버그를 서로 다른 세 가지 의견이나 관점에서 살펴보고, 실제로 버그가 맞는지 확인하라고 요청하는 겁니다.

그러면 이런 버그를 전부 걸러 내고, 여러분의 주의가 필요하거나 실제로 집중해야 하는 가장 중요한 버그만 남겨 줍니다.

이건 코드 리뷰에만 해당하지 않습니다. 여러 종류나 분류의 문제에 같은 방식을 적용할 수 있습니다. 성능 버그나 성능 문제에도 똑같이 할 수 있고, 범용적인 심층 리서치에도 적용할 수 있습니다.

“다음 주에 부모님을 타호에 모시고 가는데, 어디에서 묵어야 할지 알아보고 싶어.” 이런 경우에도 팬아웃을 할 수 있고, 역시 도움이 됩니다.

Claude는 실제로 자신만의 하네스를 만드는 데 아주 능숙합니다.

Claude는 이 팬아웃이 어떤 모습이어야 하는지, 토폴로지(topology)가 어떻게 구성되어야 하는지, 한 에이전트의 출력을 다음 단계에 있는 에이전트에 어떻게 연결해야 하는지 파악할 수 있습니다. 그리고 마지막에는 그 내용을 요약해서 저에게 돌려줍니다.

그게 그 기능의 시작이었습니다. 예를 들어 여행 계획을 세운다고 해 보죠. 타호 전역에 대해 목욕탕, 타호 호텔, 타호 에어비앤비, 가 볼 만한 곳 등을 검색하는 서로 다른 요청 10개를 보내도록 할 수 있습니다.

그러면 많은 결과를 내놓고, 다른 에이전트들이 그 결과를 정렬하거나 가장 흥미로운 결과를 찾아내도록 할 수 있습니다. 다른 에이전트들이 검증하도록 할 수도 있고요.

맞나요?

맞습니다. 최종 결과를 내놓는 거죠.

문제는 일단 팬아웃하고 나면 다시 걸러 내야 할 정보가 너무 많아진다는 겁니다. 맵리듀스(MapReduce) 문제와 비슷합니다. 사람이 소비할 수 있는 형태로 다시 걸러 내야 합니다. 제가 팬아웃 결과를 전부 읽으면 미쳐 버릴 테니까요. 신뢰도를 높이는 데 도움이 되는 무언가가 필요합니다. 이 경우 신뢰도를 높이는 방법은 그 문제에 테스트 타임 컴퓨트를 투입하는 것뿐입니다. 그렇게 하면 더 높은 확신을 얻을 수 있습니다.

워크플로에서 정말 흥미로운 또 다른 점은 에이전트가 하위 에이전트를 오케스트레이션하기 위한 코드를 작성한다는 겁니다. 결정론적인 코드 정의 동작과 에이전트형 LLM 동작이 멋지게 섞여 있습니다.

Claude가 반복 작업을 위한 워크플로를 작성할 때 저는 그 점에서 확신을 얻는 것 같습니다. “여기 이 항목들을 순회하면서 실행할 for 루프가 있네.” 그러면 “아, 그래. 이 for 루프가 항목 중 하나를 건너뛰지는 않겠구나. 이 모든 항목에 똑같은 기법을 동일하게 적용하겠구나”라고 생각하게 됩니다.

그게 제 신뢰를 정말 높여 줍니다. 여기서 Claude가 제가 원하는 일을 하고 있다는 걸 알 수 있으니까요.

Claude Tag에 대해 이야기하고 싶습니다. Robert, 지금 Claude Tag를 만들고 있는 것으로 알고 있어요. 어떻게 사용하고 있나요? 이야기해 주세요.

네, 앞서 말씀드렸듯이 우리는 Claude Tag를 아주 적극적으로 사용해서 Claude Tag를 만들고 있습니다. 실제로 제 업무에서 상당히 큰 비중을 차지하는 건 Claude Tag가 막힘없이 스스로 Claude Tag를 개발할 수 있도록 하는 일입니다.

개발 환경과 개발 루프(dev loop)를 Claude가 정말 쉽게 사용할 수 있도록 만들고 있습니다. 인간인 제가 소프트웨어를 만들고 엔드 투 엔드(end to end)로 제대로 작동하는지 테스트하기 위해 해야 하는 모든 일을 Claude가 할 수 있도록 하는 거죠.

더 복잡하고 통합 수준이 높은 소프트웨어를 만들수록 그 작업은 어려워집니다. Claude가 그런 일을 할 수 있도록 하는 것이 제 주요 업무 중 하나였습니다.

이번에는 사용자 인터페이스가 트랜스크립트와 더욱 완전히 분리되었습니다. 이제 우리는 Claude가 출력하는 실제 토큰에서 한 단계 추상화된 수준에서 작업하고 있습니다.

Slack에서 Claude Tag의 메시지를 보면, Claude Tag가 여러분에게 그 메시지를 보내기 위해 도구를 호출하고 있다는 걸 알 수 있습니다. Claude의 내부 독백은 기본적으로 Slack에서는 보이지 않습니다. Claude의 전체 트랜스크립트를 볼 수 있는 링크는 있지만, 주요 사용자 인터페이스는 메시징 도구를 통해 제공됩니다.

처음에는 그 추상화를 받아들이는 일이 조금 무서웠습니다. Claude가 생각하는 모든 것을 생각하는 즉시 제가 볼 수 없으니까요. 하지만 Claude가 저에게 언제 무엇을 말할지 선택한다는 점에서는 정말 자유로워졌습니다.

Claude가 어떤 도구를 호출하는지, 도구에 어떤 매개변수를 보내는지 세세한 부분을 사용 중에 일일이 생각하지 않게 됩니다. Claude가 작업하도록 내버려둬야 하는 상황에 놓였고, 이제는 트랜스크립트를 자세히 감독하지 않아도 좋은 결과를 얻을 만큼 모델이 충분히 좋아졌다는 걸 확인하고 있습니다.

이건 일종의 강제 장치가 되었습니다. 이제 이 모델들은 실제로 정말 좋아지고 있습니다.

최근에 Claude Tag가 정말 와닿았던 이유는 사람들의 동의를 많이 받아야 하는 새로운 도구를 개발하고 있었기 때문입니다. 처음으로 해 본 일은 “이런 아이디어를 생각하고 있는데, 관심을 가질 만한 사람 중 누구와 이야기해야 할까?”라고 묻는 것이었습니다.
