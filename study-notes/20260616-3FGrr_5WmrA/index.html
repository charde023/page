AI 에이전트 설명 — Google ADK로 첫 에이전트 만들기 (Smitha)

한 줄 요약

에이전트는 "답만 하는" 챗봇이 아니라 추론→행동→관찰→조정 루프로 스스로 결정하는 소프트웨어다. Google ADK의 planner·writer·checker를 loop agent로 감싸면 검증 실패 시 자동 재시도하는 신뢰성 있는 블로그 작성 에이전트를 만들 수 있다.

핵심 학습 포인트 (내가 배워야 할 것)

개념 왜 중요한가 한 줄
에이전트 = 결정+행동 챗봇과의 본질적 차이 단일 응답 대신 단계를 판단하고 도구·API·코드를 실행
ReAct 루프 모든 현대 에이전트의 토대 추론(reason)→행동(act)→관찰(observe)→조정(adjust)의 반복
에이전트 3유형 문제에 맞는 구조 선택 순차형(rigid)·반응형(flexible)·계획형(multi-step)
LLM agent vs workflow agent ADK의 핵심 구분 모델이 생각하는 에이전트 vs 흐름을 통제하는 에이전트(loop 등)
Loop agent로 검증·재시도 모델이 빠뜨리는 항목 자동 보정 checker가 retry라 하면 같은 단계를 최대 3회 재실행
공유 상태(shared state) 에이전트 간 결과 전달 output_key로 저장 → 다음 에이전트가 그 키로 이어받음

내가 모를 만한 것 / 처음 보는 것

  • Google ADK (Agent Development Kit): 구글의 에이전트 개발 프레임워크. LLM 에이전트와 workflow 에이전트(loop·sequential 등)를 조합해 멀티에이전트 시스템을 구성. (재사용 개념 → 차후 Google ADK 용어노트 후보)
  • ReAct (Reasoning + Acting): 논문 "ReAct: Synergizing Reasoning and Acting in Language Models"에서 나온 개념. 모델이 한 번에 텍스트를 뱉는 대신 추론·행동·관찰을 번갈아 수행. 현대 에이전트의 이론적 출발점.
  • LLM agent: 모델이 직접 생각·생성하는 에이전트 (planner, writer 등).
  • workflow agent: 흐름을 결정론적으로 제어하는 에이전트. ADK에서 loop agent가 대표 — 검증 실패 시 자동 재시도를 처리.
  • uv: 파이썬 패키지/환경 매니저. 영상에서 ADK 설치 전 먼저 설치하는 도구. (재사용 → uv 용어노트 후보)
  • output_key / shared state: 에이전트의 출력을 공유 상태의 특정 키에 저장해 다음 에이전트가 자동으로 이어받게 하는 ADK 메커니즘.
  • base agent 서브클래싱: 기본 패턴(LLM/loop/sequential)을 넘어서면 base agent를 상속해 커스텀 에이전트를 만들 수 있음.

화자의 디테일 (놓치기 쉬운 포인트)

  1. 에이전트의 정의는 "결정하고 행동하는" 소프트웨어 — 단일 응답을 생성하는 전통 챗봇과 구분. 요청을 보고 필요한 단계를 파악, API 호출·코드 실행·결과 확인 후 다음 행동을 결정.
  2. ReAct 논문을 명시적으로 인용 — "Reasoning과 Acting을 시너지"하는 게 핵심. 추론→행동→관찰→조정 사이클이 토대.
  3. 에이전트 3유형의 트레이드오프: 순차형(sequential) = 예측 가능하지만 경직, 반응형(reactive) = 유연하지만 계획 없음, 계획형(deliberate/planning) = 다단계 의존 작업에 적합. 단순·예측 가능 → 순차형, 동적 → 반응형, 다단계 목표 → 계획형.
  4. 데모 프로젝트 = 블로그 작성 에이전트: 토픽 입력 → 구조화된 아웃라인 생성 → 전체 블로그 글로 작성 → 대체 제목·훅 제안.
  5. planner의 instruction은 산출물을 구체적으로 명시 — "제목 + 짧은 서론 + 4~6개 섹션(불릿) + 결론"의 마크다운 아웃라인. 산출물을 구체적으로 spelling out 할수록 출력이 훨씬 안정적이다.
  6. validation checker는 아무것도 새로 쓰지 않는다 — 상태의 아웃라인에 제목·서론·4~6섹션·결론이 있으면 정확히 okay, 없으면 retry와 무엇이 빠졌는지 출력하도록 instruction이 엄격하게 작성됨.
  7. loop agent = planner + checker 묶음 ("robust blog planner"). 루프가 planner 실행 → checker 실행. okay면 종료, retry면 planner 재실행. 최대 3회.
  8. writer의 청중 설정: "소프트웨어 엔지니어 대상, 기초는 건너뛰고 실용 인사이트에 집중, how와 why 둘 다 설명, 짧은 코드 스니펫 포함." 아웃라인 구조를 따라 작성. 결과는 blog_post에 저장.
  9. writer에도 별도 checker ("blog post validation checker") + writer 묶은 "robust blog writer" loop agent → 글쓰기도 검증 통과까지 최대 3회 재시도.
  10. 두 loop를 tool로 감싼다 — root agent가 내부를 신경 쓰지 않고 직접 호출 가능. root agent("blogger")는 노출된 planner·writer 두 tool만 접근 → 흐름이 명확·통제됨.
  11. root agent 흐름: 토픽 받음 → planner tool로 아웃라인 → writer tool로 초안 → 마지막에 대체 제목 3개 + 트윗 길이 훅 2개 추가.
  12. 실행 = adk web — 터미널에서 ADK web으로 띄우고 브라우저에서 로컬 링크 열어 에이전트와 직접 상호작용. 데모 질문: "AI 에이전트의 상위 10가지 활용 사례로 블로그 작성".
  13. 다음 영상 예고: 이 에이전트를 MCP 서버에 연결하는 법.

1. 에이전트란 무엇인가

가장 단순하게, 에이전트는 답만 하지 않고 결정하고 행동하는 소프트웨어다. 전통 챗봇이 단일 응답을 생성하는 것과 달리, 요청을 보고 어떤 단계가 필요한지 파악한다 — API를 호출하고, 코드를 실행하고, 결과를 본 뒤 다음에 무엇을 할지 결정한다.

정의상으로도 에이전트는 추론·계획·기억을 갖추고, 사용자를 대신해 적응하고 결정할 만큼의 자율성을 가진 시스템이다.

2. ReAct 프레임워크

가장 명확한 설명은 논문 ReAct: Synergizing Reasoning and Acting in Language Models에서 나온다. 아이디어는 단순하지만 강력하다 — 언어 모델은 한 번에 텍스트를 생성하는 대신 단계적으로 추론(reason) 하고, 도구·API를 호출하는 행동(act) 을 하고, 결과를 관찰(observe) 한 뒤 다음을 결정할 수 있다.

이 추론→행동→관찰→조정 사이클이 현대 AI 에이전트가 작동하는 토대다.

3. 에이전트의 3가지 유형

유형 동작 성격
순차형 (sequential) 조립 라인처럼 step1→step2→step3 예측 가능하지만 경직
반응형 (reactive) 현재 상태를 보고 "지금 뭘 해야 하나" 즉시 결정 유연하지만 미리 계획 안 함
계획형 (deliberate/planning) 잠시 멈춰 계획을 그린 뒤 실행 다단계·의존 작업에 적합

예: 여행 예약은 무작위로 항공권을 사지 않고 날짜·호텔을 정한 뒤 순서대로 진행 → 계획형.

선택 기준: 단순·예측 가능한 흐름 → 순차형, 동적 → 반응형, 의존성 있는 다단계 목표 → 계획형.

4. 프로젝트 개요 — 블로그 작성 에이전트

토픽을 주면 → 구조화된 아웃라인 생성 → 전체 블로그 글로 변환 → 대체 제목과 훅 제안.

여기서 ADK의 카테고리가 등장한다. planner와 writer는 모델로 구동되는 LLM agent이고, 이들은 loop agent(workflow agent) 로 감싸진다. loop agent가 검증 실패 시 재시도를 자동 처리한다. 기본 패턴을 넘어서고 싶으면 base agent를 서브클래싱해 커스텀 에이전트를 만들 수도 있다.

  1. uv 설치 (영상의 명령어 그대로)
  2. google-adk 설치 (ADK를 써야 하므로)

6. planner + checker + loop agent

blog planner: 토픽을 받아 구조화된 아웃라인으로 변환하는 게 유일한 역할. - name: blog_planner (식별 용이) - model: 환경 파일에서 가져옴 - description: 사람이 읽는 메모 - instruction(핵심): 마크다운 아웃라인 — 제목 + 의사결정용 짧은 서론 + 4~6개 섹션(불릿) + 결론을 만들라고 명시. 구체적으로 적을수록 출력이 안정적. - output_key: blog_outline — 출력이 공유 상태에 이 이름으로 저장되어 다음 에이전트가 자동으로 이어받음.

outline validation checker: 새로 쓰지 않고 아웃라인만 검사. 제목·서론·4~6섹션·결론이 있으면 okay, 빠지면 retry + 무엇이 잘못됐는지 설명.

robust blog planner (loop agent): planner → checker 순. okay면 종료, retry면 planner 재실행, 최대 3회. 모델이 뭔가 빠뜨려도 다시 맞출 안전망.

7. writer + root agent

blog writer: blog_outline을 받아 전체 마크다운 글로 변환. instruction — 청중은 소프트웨어 엔지니어, 기초는 건너뛰고 실용 인사이트, how와 why 둘 다, 필요시 짧은 코드 스니펫, 아웃라인 구조를 헤딩으로 따름. 결과는 blog_post에 저장.

blog post validation checker: blog_post에 서론·아웃라인과 맞는 섹션·결론·명확한 설명이 있는지 검사. 통과면 okay, 아니면 retry + 수정 목록.

robust blog writer (loop agent): writer + checker → 검증 통과까지 최대 3회.

두 loop를 각각 tool로 감싼다. 그러면 root agent가 내부 동작을 몰라도 직접 호출할 수 있다.

root agent "blogger": 토픽을 받으면 ① planner tool로 아웃라인 → ② writer tool로 초안 → ③ 대체 제목 3개 + 트윗 길이 훅 2개 추가. root는 노출된 두 tool만 접근하므로 흐름이 명확·통제됨.

8. 실행

터미널에서 adk web 으로 실행 → 브라우저에서 로컬 ADK web 링크 열기 → 에이전트와 직접 상호작용. 데모: "AI 에이전트의 상위 10가지 활용 사례로 블로그 작성" 요청 → 서브 에이전트들이 협력해 블로그 글 완성.

AI 에이전트란? 가장 단순하게, 에이전트는 답만 하지 않고 결정하고 행동할 수 있는 소프트웨어입니다. 전통적 챗봇처럼 단일 응답을 생성하는 대신, 요청을 보고 어떤 단계가 필요한지 파악합니다 — API를 호출하거나, 코드를 실행하거나, 결과를 보고 다음에 무엇을 할지 결정합니다.

가장 명확한 설명 중 하나는 논문 ReAct: Synergizing Reasoning and Acting in Language Models에서 나옵니다. 아이디어는 단순하지만 강력합니다 — 언어 모델은 한 번에 텍스트를 생성만 하는 게 아니라, 단계적으로 추론하고, 도구나 API를 호출하는 행동을 하고, 결과를 관찰한 뒤 다음을 결정할 수 있습니다. 이 추론·행동·관찰·조정의 사이클이 현대 AI 에이전트 작동의 토대입니다. 이는 "추론·계획·기억을 갖추고, 사용자를 대신해 적응·결정할 만큼의 자율성을 가진 시스템"이라는 정의와도 맞아떨어집니다.

모든 에이전트가 같지는 않습니다. 세 가지 넓은 패턴으로 생각하면 유용합니다. 첫째, 순차형 에이전트는 조립 라인처럼 단계별로 — step1, step2, step3 — 실행됩니다. 예측 가능하지만 경직돼 있죠. 둘째, 반응형 에이전트는 그 순간에 결정합니다. 현재 상태를 보고 "다음에 뭘 해야 하지?"를 묻습니다 — 어떤 때는 도구 A, 다음엔 도구 B. 유연하지만 미리 계획하지 않습니다. 마지막으로 계획형(deliberate/planning) 에이전트는 잠시 멈춰 계획을 그린 뒤 실행합니다. 여행 예약을 생각해 보세요 — 항공권을 무작위로 사지 않고 날짜·호텔을 정한 다음 순서대로 진행합니다.

어떤 게 맞을까요? 문제에 따라 다릅니다. 단순하고 예측 가능한 흐름은 순차형으로 충분하고, 동적인 경우는 반응형이 낫고, 의존성이 있는 다단계 목표에는 계획형이 필요합니다. 이게 큰 그림입니다. 이제 실제로 에이전트를 만들어 이 아이디어들을 직접 봅시다.

블로그 작성 에이전트를 만듭니다. 토픽을 주면 구조화된 아웃라인을 생성하고, 그 아웃라인을 전체 블로그 글로 바꾸고, 대체 제목과 훅을 제안합니다. 여기서 ADK의 카테고리가 등장합니다. 코드를 보면 planner와 writer 에이전트는 모델로 구동되는 LLM agent이고, 이들은 loop agent(workflow agent) 로 감싸집니다. ADK에서 이들은 검증이 실패하면 재시도를 자동으로 처리합니다. 그리고 그 이상이 필요하면 ADK는 base agent를 서브클래싱해 커스텀 에이전트를 확장하게 해줍니다.

환경을 설정하고 코드를 한 줄씩 보겠습니다. 먼저 uv를 설치합니다(여기 명령어 실행). 둘째, google-adk를 설치합니다(당연히 ADK를 써야 하니까). 그리고 IDE에서 agent.py 파일을 만들고 핵심 라이브러리들을 import한 뒤 첫 에이전트를 만들기 시작합니다.

첫 번째로 만드는 에이전트는 blog planner입니다. 유일한 역할은 토픽을 받아 구조화된 아웃라인으로 바꾸는 것입니다. 식별하기 쉽도록 이름을 blog_planner로 주고, 어떤 모델을 쓸지 알려줍니다(환경 파일에서). description은 사람이 읽는 메모일 뿐이고, 중요한 부분은 instruction입니다 — 무엇을 만들지 알려줍니다: 제목, 의사결정용 짧은 서론, 불릿이 있는 4~6개 섹션, 그리고 결론을 갖춘 마크다운 아웃라인. 이렇게 구체적으로 적어주면(spelling out) 출력이 훨씬 더 신뢰할 만해집니다. 마지막으로 output_key를 보세요. blog_outline으로 설정합니다. 이 에이전트가 쓰는 내용이 그 이름으로 공유 상태에 저장되어, 다음 에이전트가 자동으로 이어받을 수 있습니다.

다음으로 두 번째 에이전트, outline validation checker를 추가합니다. 이건 새로 쓰는 게 없습니다. 아웃라인만 검사합니다. instruction이 엄격합니다 — 상태의 아웃라인에 제목, 서론, 4~6개 섹션, 결론이 있으면 단어 okay로 답해야 하고, 무언가 빠지면 retry라고 답하며 무엇이 잘못됐는지 설명해야 합니다. 그래야 아웃라인을 받아들일지 다시 시도할지 자동으로 결정할 수 있습니다.

planner와 checker를 연결하기 위해 robust blog planner라는 loop agent로 감쌌습니다. 루프는 먼저 planner를 실행하고 그다음 checker를 실행합니다. checker가 okay라고 하면 끝납니다. retry라고 하면 같은 instruction으로 planner를 다시 실행합니다. 이걸 최대 3회까지 할 수 있습니다. 모델이 뭔가 빠뜨려도 다시 맞출 기회를 주는 안전망입니다.

이제 blog writer라는 또 다른 에이전트를 만듭니다. 방금 blog_outline에 저장한 아웃라인을 받아 전체 마크다운 블로그 글로 바꿉니다. instruction이 쓰는 방식을 알려줍니다 — 청중은 소프트웨어 엔지니어라고 가정, 기초는 건너뛰고 실용적 인사이트에 집중, how와 why를 모두 설명, 도움이 되는 곳엔 짧은 코드 스니펫 포함, 적절한 헤딩으로 아웃라인 구조를 따름. 완성된 초안은 공유 상태의 blog_post에 저장되어 다음 단계를 기다립니다.

다음으로, 이번엔 글(post)에 대한 또 다른 checker를 추가합니다. blog post validation checker입니다. blog_post를 보고 글에 서론, 아웃라인과 맞는 섹션들, 결론, 명확한 설명이 있는지 확인합니다. 통과하면 okay, 아니면 retry라고 하고 필요한 수정 사항을 나열합니다. planning 때와 마찬가지로, writer와 그 checker를 robust blog writer라는 loop agent로 묶습니다. 이렇게 하면 검증이 통과할 때까지 글쓰기 단계를 자동으로 재시도합니다 — 최대 3회.

이제 각 loop(robust blog planner와 robust blog writer)를 tool로 감쌉니다. 이것이 root agent가 내부에서 무슨 일이 일어나는지 신경 쓰지 않고 직접 호출할 수 있게 해줍니다. 마지막으로, blogger라는 root agent로 모두 합칩니다. blogger의 instruction은 단순합니다 — 사용자가 토픽을 주면 먼저 planner tool을 호출해 아웃라인을 만들고, 그다음 writer tool을 호출해 전체 글을 작성하고, 마지막으로 대체 제목 3개와 트윗 길이 훅 2개를 추가합니다. root agent는 우리가 노출한 두 tool(planner와 writer)에만 접근하므로 흐름이 명확하고 통제됩니다. 토픽을 주면 계획하고, 쓰고, 검사하고, 다듬어진 블로그 글을 줍니다.

이제 첫 에이전트 스크립트를 성공적으로 작성했습니다. 다음 단계는 실제로 실행하는 것입니다. 터미널로 가서 adk web으로 실행하면 모든 것을 간단한 화면에서 볼 수 있습니다. 실행되면 브라우저에서 로컬 ADK web 링크를 열고 에이전트와 직접 상호작용합니다. 시작으로, "AI 에이전트의 상위 10가지 활용 사례"에 대한 블로그를 생성해 달라고 요청해 보겠습니다. 어떻게 계획하고, 쓰고, 결과를 내놓는지 봅시다. 서브 에이전트들이 협력해 블로그 글을 만들어 냅니다.

그게 전부입니다. Google ADK로 첫 AI 에이전트를 만들고 실행했습니다. 에이전트가 무엇인지에서 시작해, 코드를 단계별로 살펴보고, 마침내 터미널에서 작동하는 모습을 봤습니다. 시청 감사합니다. 영상에 언급된 모든 리소스와 코드는 설명란을 확인하세요. AI 에이전트를 MCP 서버에 연결하는 법은 다음 영상에서 배웁니다.
