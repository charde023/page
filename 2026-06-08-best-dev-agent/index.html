결론 (TL;DR)

이번 발표회의 핵심은 에이전트를 크게 만드는 것이 아니라, 생각의 연속성을 지키고 지식을 구조화하는 설계가 실제 업무와 생활에 붙는다는 것이다.

# 메시지 한 줄
1 생각의 연속성 AI 대화는 그때그때 즐겁지만 흩어진다 — 다시 읽힐 수 있는 맥락 구조를 먼저 만들어야 한다.
2 렌즈 먼저 자료를 넣기 전에 어떤 눈으로 볼지, 어떤 스키마로 저장할지 먼저 정해야 LLM 위키가 살아난다.
3 재생산으로 검증 분석을 쌓기만 하는 위키는 그 분석이 맞는지 확인할 길이 없다 — 직접 써보게 해서 시험해야 한다.
4 자동화의 윤리선 에이전트도 공정성과 개인정보 문제에서 스스로 선을 제안한다 — 그 선을 받아들이는 설계가 지속 가능하다.
5 없이도 만들 수 있다 백엔드 없이도 자가진단·검색·딥링크·분석 도구까지 붙일 수 있다 — 기술보다 무엇을 알아야 하는지가 중요하다.
6 할루시네이션 수치화 "이 AI가 틀렸다"는 느낌에서 "조문 실존 비율 100%, 내용 일치 60%"라는 측정으로 바꿔야 신뢰할 수 있다.
7 시행착오 기록 안 된 것을 기록하고 다시 요구사항을 만드는 반복이 자동화의 본체다 — 잘 포장하기보다 실패를 공유하는 것이 가장 가치 있다.

강의는 어떤 내용이었나

지피터스 22기 4주차 베스트 발표회 개발·에이전트 세션이다. 진행자 김현우가 각 스터디에서 나온 우수 발표 7개를 12분 내외로 소개하도록 안내했고, 발표자들은 실제로 만든 Thinking OS, ETF 트레이딩 봇, 드라마 대본 분석 위키, 테니스 예약 감시봇, 기획자용 AI 위키, 디스코드 알람봇, IT 법령 위키를 공유했다.

세션의 공통 흐름은 "어떻게 생각과 지식을 잃지 않고 쌓을 것인가"였다. Thinking OS는 AI 대화의 소멸 문제를, 칼날 위키는 분석의 신뢰성 문제를, 기획자 AI 위키는 개념의 분산 문제를, IT 법령 위키는 정확도 검증 문제를 각자 다른 방식으로 정면에서 다뤘다. 테니스 봇과 디스코드 알람봇은 일상의 작은 불편을 에이전트로 해결하면서 자동화의 윤리선까지 찾아냈다.

0. 한눈에 보는 4주차 개발과 에이전트 사례

  1. 문제를 아주 좁힌다. AI 대화 소멸, ETF 데이터 분산, 대본 분석 신뢰성, 코트 예약 경쟁, 기획 개념 분산, 기상 알람, 법령 정확도처럼 각 발표는 자신의 일상이나 업무에서 가장 불편한 한 지점에서 시작했다.
  2. 스키마와 렌즈를 먼저 만든다. 자료를 넣기 전에 어떤 눈으로 볼지, 어떤 구조로 저장할지를 먼저 정하지 않으면 넣어도 쓸 수 없다.
  3. 분석을 쌓기만 하지 않고 검증한다. 칼날 위키의 재생산, IT 법령 위키의 수치 측정처럼 자동화 결과를 믿기 전에 확인하는 단계를 넣는다.
  4. 자동화의 윤리선을 에이전트와 함께 정한다. 테니스봇의 결제 거부, 트레이딩봇의 AI 완전 신뢰 경계처럼 에이전트가 먼저 선을 제안하기도 한다.
  5. 백엔드 없이도 많은 것을 할 수 있다. 자가진단 레이더 차트, 딥링크, 검색, 분석 도구까지 마크다운 + 프론트엔드만으로 구현한 사례가 나왔다.
  6. 헤르메스와 OpenClaw는 잘 되는 것이 다르다. 상시 수집·반복 운영은 헤르메스에, 정밀한 음성 인터럽트와 플러그인 확장은 OpenClaw에 더 맞는 장면이 보였다.
  7. 시행착오를 기록하고 공유한다. 잘 포장하지 않고 1차 실패와 안 된 이유를 공유한 것이 다른 참여자에게 가장 실질적인 참고가 됐다.
  8. 작게 시작해서 반복한다. 맥미니 없이 LightSail, 복잡한 워크플로우 대신 두 가지 N8N 흐름, 전체 공정보다 스킬 하나로 시작해서 단계를 쪼개는 방향으로 모두 진화했다.

1. JJ(정현주) — Thinking OS: 생각이 사라지지 않는 구조 만들기

JJ의 출발점은 AI와의 대화가 즐겁지만 남지 않는다는 문제였다. 3년간 AI와 대화하면서 한 번의 서치로 해결되지 않는 깊은 질문들에 답을 받는 즐거움을 느꼈지만, 노션·블로그에 담으려 해도 흩어지고 연속성이 끊겼다.

순간의 즐거움은 있지만 남지는 않더라.

헤르메스 입문 클래스 수강 동기 자체가 Thinking OS 구축과 자동화였다.

핵심 메시지

AI는 인간 사고를 대체하는 도구가 아니라, 생각의 연속성과 깊이를 확장하는 파트너가 될 수 있다. — JJ

2. 디디 — ETF NAV 괴리율 포착 트레이딩 MVP

디디의 문제 정의는 단순했다. 내가 관심 있는 ETF를 어떻게 하면 적정 가격에 잘 구매할 수 있을까. 개별 종목 대응에 한계를 느낀 ETF 투자자로서, 여러 곳에 흩어진 데이터를 한곳에 모아 괴리율을 포착하는 시스템을 만들었다.

향후: AI가 스스로 가상 매매 후 성과를 측정해 로직을 재개발·진화시키는 구조 구현 중.

아직 AI가 모든 투자 판단을 내려주는 걸 믿을 수는 없다. 자기가 투자하는 영역에서 흩어진 데이터를 모으고 시간을 아끼는 방면으로 AI를 접목하는 것이 좋은 출발점이다. — 디디

3. 이생강 — 칼날 LLM 위키: 분석을 재생산으로 검증하다

이생강 발표는 드라마 프로듀서가 대본 분석·평가를 AI로 하는 사례였다. 단순히 자료를 저장하는 위키가 아니라, 전문 영역의 분석이 맞는지 직접 써보게 해서 검증하는 구조를 만들었다.

섞으면 무뎌지고 나눠야 날이 선다. — 이생강

칼날 위키의 핵심: 렌즈를 장착한 전문 분야 위키. 범용 위키와 분리해 정밀도를 높인다.

2차 범용·기획 위키 분리 + 렌즈 이해 읽는 시점에만 머물러 있어 작가 의도·빌드업은 체크하기 어려움 분리는 필요하지만 검증 수단이 없다
3차 재생산(거꾸로 써보기) 추가 시간이 너무 오래 걸림 (에피소드당 4~5시간) 분석이 정확한지 확인하는 시험지로 재생산이 작동

재생산이 왜 검증인가

레시피에 비유: 맛있는 요리를 먹고 레시피를 적었는데, 그대로 만들었더니 그 맛이 안 나면 레시피에 문제가 있는 것이다. 분석대로 다시 썼는데 원본의 맛을 못 살린다면, 그 분석이 못 짚고 있는 부분이다.

4. 위올라 — 테니스 코트 예약 감시봇

위올라는 반려에이전트 반 수강생으로 수업 시작 당시 "Codex는 뭔가요?"를 물을 정도의 생초보였다. 2주 만에 봇 3개(파파 스모프·똘똘이 스모프·스머팟)를 만든 뒤, 일상의 불편을 해결하는 사례로 테니스 코트 예약 감시봇을 제작했다.

배경: 서울 테니스 코트 예약은 BTS 콘서트 예약 수준. 오픈 즉시 서버 다운. 신규 오픈보다 취소 발생 시 잡는 전략으로 방향을 잡았다.

6. 하유(하이오) — 디스코드 TTS/STT 알람봇: 에이전트가 깨워주는 아침

하유(닉네임: 하이오)의 시도는 단순하고 유쾌했다. 헤르메스와 OpenClaw에 크론잡을 걸어서 디스코드 음성 채널로 TTS 알람을 송출하게 했다. 발표 중 실제로 맞춰둔 알람이 울리는 장면을 실시간으로 시연했다.

동작 원리: 디스코드 음성 채널에 팔로우 모드를 켜면 봇들이 사용자를 따라 들어온다. 아침 9시부터 5~10분 간격으로 크론잡이 TTS를 트리거해 음성 채널로 "하유 일어나", "아직 자고 있어" 같은 메시지를 송출한다.

헤르메스랑 OpenClaw는 각자 잘 되는 게 있고 안 되는 게 있어요. 지금 서로에게 가르쳐 주라고 하면서 하고 있습니다. — 하유

7. 모술 — IT 법령 위키: 할루시네이션을 수치로 잡다

모술은 정보화 업무 담당자로, 정보화 사업에 필요한 법규정·매뉴얼이 너무 많고 흩어져 있어 정확한 답을 얻기 어렵다는 문제를 해결하고자 했다.

핵심 위험

문제 결과
법령이 너무 많아 완벽히 숙지 불가 담당자별 해석 차이 → 감사 리스크
잦은 법령 재개정 현행화 안 되면 옛 버전 오인용
담당자 교체 지식 단절·업무 공백

시스템 구조: 헤르메스 에이전트 2개 (코딩 전담 GPT-o3 + 집사 역할 Claude 에이전트). Amazon LightSail (맥미니 대신). 디스코드 바이브 코딩.

처음엔 RAG 방식으로 구축했다가 법조문처럼 딱딱한 짧은 답변이 나오는 문제가 발생. 옵시디언 스타일 마크다운 볼트로 전환 (자연어 회계처리님 조언). 더 풍성하고 친절한 답변을 얻었다.

UI: 트리 구조 법령 목록 + MD 형식 문서 뷰어. 법령센터 API 자동 수집. 미등록 지침·매뉴얼은 PDF·HWP·MD 직접 업로드 (해시값으로 중복 방지).

할루시네이션 수치화

측정 항목 방법
조문 실존 비율 근거 법령·조문을 법령센터 API로 실존 여부 검사
내용 일치 점수 핵심 토큰 포함율 + 토큰 분포 유사도 계산
비교 대상 조문 적중률 내용 일치 점수
폐쇄망 로컬 모델 9종 (1~2년 된 버전) 일부 없는 조문 근거 제시도 있음 모델별 상이
자체 제작 법령 위키 100% (항상 현행화) 약 59~60% 이상

100%에 달하지 못하는 이유: 생성형 LLM은 조문을 그대로 반복하지 않고 여러 문서를 관통하는 풍성한 답변을 생성하기 때문.

향후 과제: 로컬 모델과 협업 체계 구축. 컨텍스트 연속성 문제 해결(현재 질문마다 새 대화처럼 답변).

검색 결과에만 근거하고, 출처를 붙이고, 위키에 없으면 명시하고, 법정 절차처럼 단정하지 말라고 했기 때문에 더 신중하게 생성하느라 답변 속도가 느린 것이다. — 모술의 에이전트

8. 자주 막히는 곳

증상 대응
AI 대화가 계속 흩어져 연속성이 끊긴다 텔레그램 입력 → 헤르메스 정리 → 옵시디언 축적의 파이프라인을 먼저 만든다. 데일리 의무보다 소스·토픽 입력 습관이 더 중요하다.
LLM 위키를 만들었는데 결과가 이상하다 자료를 넣기 전에 범용과 전문 위키를 분리하고, 렌즈(평가 기준)와 스키마(저장 규칙)를 먼저 만든다.
분석 위키의 분석이 맞는지 확신이 없다 분석한 내용대로 다시 써보게(재생산) 해서 결과를 비교한다. 맛을 못 살리는 부분이 바로 분석이 놓친 지점이다.
에이전트가 자동 결제·자동 예약까지 하려 한다 모니터링 + 알림 + 사람이 링크 클릭하는 방식으로 제한한다. 에이전트 스스로 윤리선을 제안하는 경우도 있다.
네이버 예약 API 호출 시 AI가 직접 접근 불가 AI는 코드 검증만 하고, 실제 API 호출·확인은 WSL이나 로컬 환경에서 분업한다.
RAG로 위키를 만들었는데 법조문처럼 딱딱하다 마크다운 볼트 방식으로 전환해 LLM이 여러 문서를 관통하는 풍성한 답변을 생성하게 한다.
AI 답변이 할루시네이션인지 모르겠다 법령센터 API 같은 신뢰 소스로 조문 실존 여부를 검사하고, 일치 점수를 수치화해 기준을 만든다.
헤르메스와 OpenClaw 중 뭘 써야 하는지 모르겠다 상시 수집·반복 운영·TTS 설정 편의성은 헤르메스. 말 끊기·팔로우 모드·플러그인 확장은 OpenClaw가 더 유리하다.
